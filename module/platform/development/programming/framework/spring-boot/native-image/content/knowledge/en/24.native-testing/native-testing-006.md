# Mocking, Instrumentation, and Testing Features Requiring Version Verification

## 1. Why Are JVM Tests Not Enough to Verify a Native Application?

In the **SPRING_BOOT_NATIVE_IMAGE** module, a Spring Boot application is processed by **Spring AOT** and then compiled into a **GraalVM Native Image** to verify compatibility, startup time, memory usage, container packaging, and operations. Most tests should still be developed and run on the JVM for fast iteration, yet certain behaviors change when code runs inside a native executable: reflection, dynamic proxies, class generation, Java agents, instrumentation, resource loading, and testing libraries relying on those mechanisms.

For instance, a unit test using Mockito to mock a static method can run on the JVM thanks to the inline mock maker and Java instrumentation. Once the test is compiled into a native executable, the JVM instrumentation API and runtime bytecode modification no longer work the same way. Another test using a Spring context, JUnit, and plain DTOs can run fine in a native test image if the required components and metadata are supported.

Therefore, you must clearly distinguish **whether you are testing the native application with a JVM test harness or compiling the test suite itself into a native executable**. These two approaches verify different layers and carry different compatibility requirements.

After this lesson, learners will be able to:

1. Distinguish between JVM unit/integration tests, AOT-on-JVM tests, native tests, and black-box tests for the executable.
2. Explain why the Mockito inline mock maker, Byte Buddy, and Java instrumentation require separate verification.
3. Choose mocks, stubs, fakes, or real test dependencies suitable for native tests.
4. Identify which Spring Test/JUnit features can be used in native testing per version.
5. Configure Maven/Gradle to build and run JUnit Platform tests as a native executable.
6. Separate tests relying on JVM agents, Docker, or external infrastructure from the native test image when needed.
7. Build a test matrix organized by dependency/toolchain/platform.
8. Read native test reports, diagnose failures, and document unverified features.

> **Principle:** use the JVM for broad test coverage and rapid feedback; use AOT-on-JVM to verify generated bootstrap code; use native tests and black-box tests to validate paths with real differences in Native Image.

## 2. Four Testing Layers to Distinguish

| Layer | Where Do Tests Run? | Primary Purpose | Examples |
| --- | --- | --- | --- |
| JVM tests | Standard JVM | Verify most business logic, services, repositories, and fast integrations. | JUnit, Mockito, Testcontainers, MockWebServer. |
| AOT-on-JVM | JVM using generated Spring AOT bootstrap code | Catch errors in generated AOT code before native compilation. | Running the app with spring.aot.enabled=true. |
| Native tests | Test suite compiled into a native executable | Confirm the test engine, test code, and application code run inside the closed-world runtime. | GraalVM Native Build Tools nativeTest. |
| Black-box native tests | Test harness typically running on the JVM calling the native executable/process/container | Verify HTTP contracts, startup, environment, databases, brokers, and target OS. | WebClient, RestAssured, or Selenium calling the native app. |

You do not need to move the entire test suite to native. Native compilation for tests can consume significant time and resources; prioritize high-value tests that detect differences between JVM and native execution.

### 2.1. JVM Tests Remain the Foundation

Use the JVM to run most unit tests and integration tests quickly. This is the right place for mocking libraries, assertions, fixtures, and test infrastructure with full JVM support.

Keep business logic tests independent of native deployment details. For example, testing fee calculation rules, input validation, or data mapping does not require native compilation just to prove an algorithm is correct.

### 2.2. AOT-on-JVM Verifies Generated Initialization

Spring Boot can run on the JVM while executing initialization code generated by Spring AOT. After building an artifact containing AOT-generated code, run:

~~~bash
java -Dspring.aot.enabled=true -jar target/orders-service.jar
~~~

With Maven, the artifact must be built with the profile activating AOT/native according to your project configuration, for example:

~~~bash
./mvnw -Pnative package
java -Dspring.aot.enabled=true -jar target/orders-service.jar
~~~

With Gradle, ensure the GraalVM Native Image plugin is applied and the build task generated AOT outputs before running the application with this property.

AOT-on-JVM confirms that the Spring context initializes via generated code without missing beans/configurations. It does not yet prove that reflection, dynamic proxies, resources, or Java instrumentation will work inside a native executable.

### 2.3. Native Tests Verify the Internal Native Runtime

Native Build Tools can compile a test suite into a native executable. The JUnit Platform test engine is packaged into the test image and executes the tests discovered during the build.

Native tests are well suited for verifying:

- Spring contexts and test slices can be processed by AOT.
- Reflection/resource/proxy metadata is sufficient for both test and application code.
- DTO binding, serializers, configuration, and dynamic access paths work.
- Libraries used inside the test image are compatible with Native Image.

### 2.4. Black-Box Tests Verify the Executable in a Real Environment

A JVM test harness can launch a native executable or container, call HTTP endpoints, verify responses, and clean up resources. The test harness does not need to be compiled into native code simply because the target application is native.

This approach works well with databases, brokers, Testcontainers, Selenium, TLS, networking, filesystems, and testing tools requiring Java agents or dynamic class loading.

## 3. Mocking in Native Image: Identify the Mechanism Before Fixing Tests

Mocking is not a single uniform feature. A mocking framework may generate subclasses, rewrite bytecode of existing classes, create proxies, or use Java instrumentation. These mechanisms have vastly different requirements in a closed-world executable.

### 3.1. Mockito Inline Mock Maker

Mockito 5 made the inline mock maker the default. The inline mock maker modifies class bytecode to intercept method calls; certain paths rely on Java instrumentation and agent attachment.

According to the Mockito 5 release notes, the inline mock maker does not work on GraalVM Native Image; Mockito notes the subclass mock maker as the appropriate option in this case. Accordingly, tests using static method mocking, constructor mocking, or final type mocking via the inline maker should be treated as JVM-specific unless a specific framework version proves otherwise.

Example test relying on the inline maker:

~~~java
@Test
void calculatesUsingStaticClock() {
    try (MockedStatic<ClockProvider> clock =
             Mockito.mockStatic(ClockProvider.class)) {
        clock.when(ClockProvider::now)
             .thenReturn(Instant.parse("2026-01-01T00:00:00Z"));

        assertThat(service.calculate()).isEqualTo(expected);
    }
}
~~~

This test illustrates static mocking. To keep business logic runnable natively, inject time via a replaceable dependency such as java.time.Clock rather than patching static methods.

### 3.2. Subclass Mock Maker

Mockito provides the mockito-subclass artifact to select the subclass mock maker. Depending on the version, the mock maker can be configured via an extension file or the corresponding dependency. Check the Mockito documentation for your exact version before changing dependencies.

Traditional extension file configuration example:

~~~text
src/test/resources/
└── mockito-extensions/
    └── org.mockito.plugins.MockMaker
~~~

File contents:

~~~text
mock-maker-subclass
~~~

The subclass mock maker creates subclasses to represent mocks. This avoids inline instrumentation, though you still must verify dynamic class creation, mocked class types, and Native Image metadata. Do not assume every mock will automatically work just because you switched mock makers.

Notes:

- The subclass mock maker cannot mock final classes/methods the way the inline maker does.
- Constructors, visibility, sealed/final types, and classloaders can restrict subclass generation.
- Some dependencies or plugins may force a different mock maker through their own configuration.
- Run nativeTest with your exact Mockito version to verify, rather than relying only on JVM tests.

### 3.3. When to Use Fakes or Stubs

If a test needs to run on both JVM and native, a simple fake is usually more stable than a dynamically generated mock. Example:

~~~java
interface PaymentGateway {
    PaymentResult charge(PaymentRequest request);
}

final class FakePaymentGateway implements PaymentGateway {
    private final List<PaymentRequest> requests = new ArrayList<>();

    @Override
    public PaymentResult charge(PaymentRequest request) {
        requests.add(request);
        return PaymentResult.approved("test-transaction");
    }

    List<PaymentRequest> requests() {
        return List.copyOf(requests);
    }
}
~~~

A fake implements the interface with an ordinary class, can be analyzed statically, and is easy to control in native tests. It also encourages testing observable behavior rather than coupling tests to internal mocking framework mechanics.

| Behavior Under Test | Suitable Alternative |
| --- | --- |
| Current time | Inject java.time.Clock and use Clock.fixed in tests. |
| Random number generation | Inject Random/RandomGenerator or an ID generator port. |
| HTTP calls | Use a stub HTTP server or fake adapter; verify real requests/responses. |
| Database repository | Use a fake repository for unit tests; use a real database/container for integration tests. |
| Message broker | Fake publisher/consumer for unit tests; real broker in integration tests. |
| Static utility | Wrap behind an interface/adapter or convert into an object with explicit dependencies. |
| Constructor side effects | Inject a factory/provider instead of mocking constructors. |
| Hard-to-mock final class | Use an interface port or a fake implementing the interface. |

A fake should have clear behavior and its own tests if it models important rules. Do not turn a fake into a complex duplicate of the production implementation.

### 3.4. Spring Test Bean Overrides

Spring Test provides mechanisms to replace beans with mocks in the ApplicationContext, such as @MockitoBean in supported Spring Framework versions or equivalent annotations in older versions.

These annotations do not automatically make Mockito native-compatible. Determine:

- Which Spring Framework/Spring Boot version the annotation belongs to.
- Which Mockito mock maker is actually loaded.
- Whether the replaced bean is a final class or requires inline mocking.
- Whether the test context has been processed by Spring AOT.
- Whether the native test can create the mock and initialize the context.

If a mocked bean only serves JVM tests, you can keep that test on the JVM and write another native integration test using an appropriate fake or real bean.

## 4. Java Instrumentation and Java Agents

### 4.1. Instrumentation on the JVM

The JVM can load Java agents via the -javaagent flag or the attach mechanism. Agents can use java.lang.instrument.Instrumentation to transform bytecode as classes load or redefine classes within JVM-permitted boundaries.

Several testing tools use this mechanism:

- Mockito inline mock maker and the Byte Buddy agent.
- JaCoCo Java agent for measuring coverage on the JVM.
- Profiler/APM agents.
- Test framework weaving or instrumentation tools.
- Agents monitoring class loading or method invocation behavior.

### 4.2. Native Executables Do Not Run Under HotSpot JVM

A native executable is not a regular JVM process. You cannot assume Java agents using -javaagent, the attach API, or JVM class redefinition will work inside a native executable.

If a test suite requires an agent, identify clearly what the agent is instrumenting:

- The JVM running the test harness.
- The JVM running the application as a JAR.
- Or the compiled native executable itself.

An agent may continue instrumenting a JVM test harness or an external mock JVM server; that does not mean it can instrument the native process.

### 4.3. JaCoCo and Coverage

The JaCoCo Java agent typically measures coverage by instrumenting bytecode while the JVM executes tests. JVM coverage is valuable for assessing logic coverage, but it does not automatically report coverage for native executable code compiled by GraalVM.

You can maintain two separate reports:

- **JVM coverage:** logic coverage from unit/integration tests running on the JVM.
- **Native execution coverage:** scenarios actually executed natively, recorded via native test reports, black-box results, or coverage/debugging tools supporting the specific GraalVM version.

Do not merge both metrics into a single percentage when the collection mechanisms differ. Explicitly state which tests run on the JVM, which run natively, and which areas lack corresponding coverage instrumentation.

### 4.4. Distinguishing Java Instrumentation from Spring AOP

Spring AOP can use JDK dynamic proxies or class-based proxies. This is a framework proxy mechanism with case-by-case AOT/runtime hints support; it is not synonymous with a Java instrumentation agent.

If the application uses Spring AOP, inspect generated proxies and hints in the AOT/native build. If a test uses an agent to modify bytecode, that is a separate instrumentation concern.

## 5. JUnit Platform and Native Test Conditions

GraalVM Native Build Tools supports compiling JUnit Platform tests into a native executable. The plugin explicitly supports JUnit Jupiter and JUnit Vintage; other TestEngines must be evaluated against Native Image compatibility and corresponding metadata.

Plugin versions specify minimum JUnit Platform/JUnit Jupiter requirements. Current Native Build Tools documentation cites JUnit 5.8.1 as the minimum supported version for the plugin; Maven also requires compatible Surefire and JUnit Platform artifacts. Always check the version matrix for the plugin version you use.

### 5.1. Running Tests Only in Native Image

JUnit provides @EnabledInNativeImage and @DisabledInNativeImage conditions in supported versions. Example:

~~~java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.condition.EnabledInNativeImage;
import org.junit.jupiter.api.condition.DisabledInNativeImage;

class NativeSpecificTests {

    @Test
    @EnabledInNativeImage
    void verifiesNativeOnlyBehavior() {
        // Runs only inside a native image.
    }

    @Test
    @DisabledInNativeImage
    void usesJvmOnlyInstrumentation() {
        // Test relying on JVM instrumentation.
    }
}
~~~

Use these conditions intentionally:

- Tests relying on JVM-only instrumentation can be marked JVM-only.
- Native-specific tests can verify behaviors that only appear in native mode.
- Critical business logic must not disappear from the native suite merely by attaching @DisabledInNativeImage.

If a test is excluded from the native suite, create another native test verifying the same contract with an appropriate fake or integration path. Verify which JUnit version provides these annotations; do not add imports based solely on documentation for a different release.

### 5.2. Test Engines and Extensions

The native test image requires analyzable test engines, extensions, and test classes. Check:

- JUnit Platform launcher, Jupiter engine, and Vintage engine have compatible versions.
- Any custom TestEngine supports Native Image.
- Whether extensions use reflection, service loaders, dynamic class loading, or instrumentation.
- Whether parameterized tests, test templates, and dynamic tests are supported by your plugin/JUnit version in native configuration.
- Whether test discovery locates the expected set of tests.

If native test reports show no tests discovered, inspect engine/launcher versions and discovery configuration before adding reflection hints to application code.

## 6. Spring Test in Native Image

Spring Framework supports AOT for test ApplicationContexts. Current Spring Boot documentation outlines the steps:

1. Analyze tests to determine the required ApplicationContexts.
2. Run AOT processing for those contexts and generate assets.
3. Build a native image containing the generated assets and the JUnit TestEngine.
4. Launch the native image to execute the discovered tests.

According to current Spring Boot documentation, common Spring testing features such as @SpringBootTest and test slices can be used in native tests. Still, an individual test depends on the versions of Spring, the test framework, Mockito, database drivers, and other dependencies.

### 6.1. @SpringBootTest

Use @SpringBootTest to verify the ApplicationContext and wiring close to the real application:

~~~java
@SpringBootTest
class OrderApplicationNativeTests {

    @Autowired
    OrderService orderService;

    @Test
    void createsOrder() {
        OrderResult result = orderService.create(
            new CreateOrderCommand("SKU-1", 2)
        );

        assertThat(result.status()).isEqualTo(OrderStatus.CREATED);
    }
}
~~~

If the test context contains beans requiring reflection/resource/proxy metadata, native tests can catch missing hints. Ensure the context goes through AOT processing and test configurations do not depend on a JVM-only classpath.

### 6.2. Test Slices

Test slices narrow the ApplicationContext, such as @WebMvcTest, @DataJpaTest, or other slices depending on the Spring Boot version. They can shrink context scope and native image test size, though test slices still require compatible dependencies and test doubles.

If a slice uses @MockitoBean or another mock annotation, check the active mock maker. When Mockito is unsuitable, use fake beans or alternative test configurations supported by Spring.

### 6.3. Test Context Caching

Spring Test can cache an ApplicationContext across tests sharing the same configuration. In native testing, each context must be analyzed and processed by AOT accordingly. Many distinct test configurations increase the number of contexts and native test image build times.

Keep the number of contexts intentional:

- Reuse test configurations when sharing the same contract.
- Do not introduce new profiles/contexts unless there is a meaningful difference to verify.
- Separate tests requiring external services from pure unit/native tests when reasonable.
- Inspect AOT logs to see which contexts were discovered and processed.

## 7. Verifying Instrumentation and Mocking by Version

Do not infer native compatibility from a library name or a single passing test. Build a matrix for your exact resolved dependencies.

| Component | Questions to Verify |
| --- | --- |
| Mockito | Version, active mock maker, and whether inline/static/constructor mocking is used? |
| Byte Buddy | Does it generate or instrument classes at runtime? Does the version provide GraalVM Native Image guidance? |
| JUnit | Are Platform/engine versions compatible with Native Build Tools? Are native image conditions available? |
| Spring Test | Does the Spring Framework/Boot version support AOT testing and the annotations in use? |
| JaCoCo | Does coverage reporting only target the JVM, or is there dedicated native executable support? |
| Testcontainers | Do the Docker client, container runtime, and test harness run on the JVM or inside the native test image? |
| WireMock/MockWebServer | Do the server/client and extensions depend on dynamic class generation or a Java agent? |
| Agent/APM | Which JVM can the agent attach to? Does it claim Native Image runtime support? |
| Database test driver | Do the driver and test database have metadata/native libraries for the target OS? |

### 7.1. Inspecting Actual Dependencies

Maven:

~~~bash
./mvnw dependency:tree -Dverbose -Dscope=test
~~~

Filter Mockito and Byte Buddy:

~~~bash
./mvnw dependency:tree -Dincludes=org.mockito:*,net.bytebuddy:*
~~~

Gradle:

~~~bash
./gradlew dependencies --configuration testRuntimeClasspath
~~~

Inspect why a version was selected:

~~~bash
./gradlew dependencyInsight \
  --dependency mockito-core \
  --configuration testRuntimeClasspath
~~~

Check both test-only artifacts and transitive dependencies. For instance, an application might declare one Mockito version while the Spring Boot BOM or starter test pulls another version onto the test runtime classpath.

### 7.2. Verifying the Active Mock Maker

In Mockito, check which artifacts and extension files are present. Mockito 5 defaults to the inline mock maker; if you want to try the subclass mock maker for native tests, consult the instructions for that exact release and configure the test classpath accordingly.

Do not use JVM test results to conclude a native mock maker works. Run at least one native test that creates and exercises mocks of the exact kind your application/tests require.

### 7.3. Documenting Support Scope

A dependency may:

- Work in JVM tests but be unusable inside a native test image.
- Work if the inline mock maker is replaced with the subclass maker.
- Work only with interface mocks, without static/final/constructor mocking.
- Work inside a JVM test harness driving the native app externally.
- Lack sufficient evidence to draw a conclusion.

Record the exact status and tested features rather than slapping on a generic label like "Mockito native supported".

## 8. Structuring Test Doubles for Better Native Compatibility

A design pattern that keeps both JVM and native tests maintainable is exposing external dependencies via interfaces/ports.

Example service:

~~~java
public class OrderService {
    private final PaymentGateway paymentGateway;
    private final OrderRepository orderRepository;
    private final Clock clock;

    public OrderService(
            PaymentGateway paymentGateway,
            OrderRepository orderRepository,
            Clock clock) {
        this.paymentGateway = paymentGateway;
        this.orderRepository = orderRepository;
        this.clock = clock;
    }

    public OrderResult create(CreateOrderCommand command) {
        Instant createdAt = Instant.now(clock);
        PaymentResult payment = paymentGateway.charge(
            new PaymentRequest(command.sku(), command.quantity())
        );
        if (!payment.approved()) {
            return OrderResult.rejected();
        }
        return orderRepository.save(
            Order.create(command, createdAt, payment.reference())
        );
    }
}
~~~

Test using a fake:

~~~java
final class FakePaymentGateway implements PaymentGateway {
    private PaymentResult nextResult = PaymentResult.approved("fake-1");

    void returnResult(PaymentResult result) {
        this.nextResult = result;
    }

    @Override
    public PaymentResult charge(PaymentRequest request) {
        return nextResult;
    }
}
~~~

And a fixed clock:

~~~java
Clock clock = Clock.fixed(
    Instant.parse("2026-05-10T08:00:00Z"),
    ZoneOffset.UTC
);
~~~

This structure brings clear benefits:

- No need to mock static time APIs.
- No need to dynamically generate subclasses for every dependency.
- Tests run identically on both JVM and native.
- Easy to assert outbound gateway requests and repository state.
- Real dependencies can be verified separately via integration tests.

Do not replace every integration test with fakes. Use fakes to test business logic and real services/containers to verify protocols, transactions, schemas, networking, and drivers.

## 9. External Integration Tests and Testcontainers

### 9.1. JVM Test Harness Driving the Native Executable

For databases or brokers, a JVM test harness can:

1. Start Testcontainers or test services.
2. Launch the native executable with appropriate environment variables.
3. Call HTTP endpoints or messaging interfaces.
4. Verify state in the database/broker.
5. Stop the executable and clean up containers.

This is a black-box integration test. It verifies that the native application communicates with real dependencies in a production-like environment without requiring Testcontainers to be compiled into the native test image.

### 9.2. Running Testcontainers Inside the Native Test Image

Only include Testcontainers inside the native test image if its version and entire dependency chain are verified as supported. Testcontainers may use Docker clients, service loading, reflection, dynamic configuration, and process/network access; these features must be verified individually.

If the native test image does not support the Docker client setup or runtime environment, keep Testcontainers orchestration in the JVM harness and test the native app externally.

### 9.3. Stub HTTP Servers

For HTTP clients, WireMock or MockWebServer can be used in JVM integration tests to verify requests, timeouts, retries, and error mapping. To test the native executable, run the stub server as a separate process/container and call it from the native application. Make sure server test libraries are not pulled into the native test image unnecessarily.

## 10. Configuring Native Testing with Maven

Configuration depends on the Spring Boot parent and GraalVM Native Build Tools version.

### 10.1. Spring Boot Parent with the nativeTest Profile

Current Spring Boot documentation instructs using the nativeTest profile when a project inherits from spring-boot-starter-parent and opts into the required plugins. Command:

~~~bash
./mvnw -PnativeTest test
~~~

The nativeTest profile activates test AOT and native test execution according to the corresponding Spring Boot/Native Build Tools configuration.

If a project uses a custom parent POM or does not use the Spring Boot-provided profile, configure appropriate executions for:

- Spring Boot Maven Plugin goal process-test-aot.
- GraalVM Native Build Tools Maven plugin goal test.
- Compatible Maven Surefire and JUnit Platform artifacts.

### 10.2. Checking Surefire and JUnit Platform

Current Maven Native Build Tools requires Maven Surefire 3.0.0 or higher for native test execution. The JUnit Platform launcher must be compatible with the Jupiter/Vintage engine. Inspect the dependency tree to prevent Surefire and Native Build Tools from resolving mismatched JUnit Platform versions.

### 10.3. Separating JVM Tests and Native Tests

CI can be organized into separate jobs:

~~~bash
# Fast: tests on the JVM
./mvnw test

# Verify Spring AOT/native tests per project profile
./mvnw -PnativeTest test

# Build application native image if required by the pipeline
./mvnw -Pnative package
~~~

The final command depends on your project's native build profile. Do not assume nativeTest and native are the same profile or lifecycle; inspect the actual POM and test reports.

If a JVM test harness is needed against the executable, run it in a separate job after native packaging finishes.

## 11. Configuring Native Testing with Gradle

The Spring Boot Gradle plugin automatically configures AOT test tasks when the GraalVM Native Image plugin is applied according to your version's documentation.

Run native tests:

~~~bash
./gradlew nativeTest
~~~

Build the test image without executing tests:

~~~bash
./gradlew nativeTestCompile
~~~

Build the application executable:

~~~bash
./gradlew nativeCompile
~~~

Tasks serve distinct roles:

- test: runs the test suite on the JVM.
- nativeTestCompile: compiles the test suite into a native test executable.
- nativeTest: executes the native test executable.
- nativeCompile: compiles the main application into a native executable.

You can configure the test binary specifically when debugging is needed:

~~~groovy
graalvmNative {
    binaries {
        test {
            debug = true
            verbose = true
            buildArgs.add('-O0')
        }
    }
}
~~~

The DSL may differ across plugin versions; the snippet above is a Groovy DSL example. Debug info and low optimization help when GDB/source stepping is needed on supported platforms, though they can produce larger or slower binaries.

## 12. Classifying Tests to Choose Where They Run

| Test Group | JVM | AOT-on-JVM | Native Test Image | Black-Box Native |
| --- | --- | --- | --- | --- |
| Pure domain logic | Primary | Possible | Selective | Optional |
| Mockito inline/static/constructor | Yes if JVM supports | Yes if JVM supports | Do not assume; usually needs mock maker/test rewrite | Harness can run outside native |
| Interface fakes/stubs | Yes | Yes | Suitable | Yes |
| Spring context wiring | Yes | Very useful | Suitable if version supports | Possible |
| Spring MVC/JSON binding | Yes | Yes | Selective | Very useful over HTTP |
| Database/JDBC | Yes | Yes | Only when driver/test deps are compatible | Very useful with real DB |
| Testcontainers orchestration | Yes | Yes | Only when full stack is supported | Well suited when JVM harness drives native app |
| Java agents/JaCoCo | Yes | Yes on JVM | Do not assume | Can instrument JVM harness |
| Startup/shutdown/environment | Limited | Partial | Possible | Recommended |
| OS libraries/TLS/certificates | Baseline | Partial | Possible | Requires container/platform tests |

### 12.1. Do Not Skip Tests When Native Lacks a Mock Maker

If a test relies on the inline mock maker, you may mark it JVM-only. However, you must replace its native behavioral verification with another test:

- Use a fake or adapter implementation.
- Run a native test for the service with the fake.
- Run a black-box integration test with real dependencies or a stub server.
- Document explicitly that static/constructor mocking is verified only on the JVM.

Do not let disabled tests leave critical logic unverified in the native suite.

## 13. Diagnosing Native Test Failures

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Mockito inline mock maker fails natively | Relies on inline bytecode modification/Java instrumentation. | Use mockito-subclass if supported by your version, or replace with fakes. |
| Failed to create mock subclass | Runtime class generation, final/sealed type, constructor, or missing metadata. | Mock interfaces, use static fake classes, and check Mockito/Byte Buddy native support. |
| Native test cannot find JUnit engine | Missing engine/launcher or incompatible versions. | Check testRuntimeClasspath, Surefire, and Native Build Tools matrix. |
| @SpringBootTest passes on JVM but native test context fails | AOT context not processed or missing metadata/feature support. | Check process-test-aot, generated context, hints, and test slice. |
| Test is skipped in native image | Native image condition or test discovery/filter. | Check @EnabledInNativeImage/@DisabledInNativeImage, tags, and test reports. |
| JaCoCo/Java agent does not work in native tests | Agent requires JVM instrumentation. | Use JVM coverage; separate native runtime verification or native-aware tools. |
| Testcontainers fails to start | Docker client/runtime unsuitable for native test image or missing environment. | Run Testcontainers in a JVM harness and drive the native app externally. |
| Test passes on JVM but resource not found natively | Missing resource metadata or differing path. | Add a native integration test and verify resource hints/packaging. |
| Native test image build is very slow | Too many contexts/test dependencies or compiler optimizations. | Reduce context count, split suites, and run native tests selectively in CI. |
| Native test passes but container deployment fails | Different OS/architecture, certificates, shared libraries, or environment. | Run black-box tests inside the target runtime image. |

### 13.1. Diagnostic Sequence

~~~mermaid
flowchart TD
    A[Native test failed] --> B{Is the error in the test framework or application code?}
    B -->|Test framework| C[Check JUnit, Mockito, Byte Buddy, agents]
    B -->|Application code| D[Check AOT, hints, reflection, resources]
    C --> E{Does it depend on JVM instrumentation?}
    E -->|Yes| F[Separate JVM-only test or replace with fake]
    E -->|No| G[Check versions and native metadata]
    D --> H[Add reproducer scenario and inspect metadata]
    F --> I[Rebuild native test]
    G --> I
    H --> I
    I --> J{Do test and target behavior pass?}
    J -->|Not yet| B
    J -->|Yes| K[Run black-box/container tests]
~~~

### 13.2. Debugging Native Tests

When a test fails inside a native executable, you can build the test binary with debug information and use a debugger such as GDB on supported platforms. Native Build Tools provides a dedicated test compilation task to retain the executable and debug artifacts. Consult GraalVM documentation for your OS/debugger; GDB is generally best suited for Linux.

Before debugging, save:

- The native test executable and build log.
- The test report and failing test name.
- GraalVM/JDK/plugin versions.
- Build arguments and metadata.
- Inputs/fixtures to reproduce.

## 14. Building a Test Matrix and CI Strategy

You do not need to run every native test on every commit if compilation time is prohibitive. Split the pipeline:

| Stage | Contents | Suggested Cadence |
| --- | --- | --- |
| Pull request | JVM unit tests, static checks, focused integration tests. | Every change |
| AOT verification | Build AOT and run app/tests on JVM in AOT mode. | Every major change or PR |
| Native compile | Build the application native executable. | PRs touching native config and main CI |
| Native tests | Selected test suite compiled and run as a native image. | Main CI or nightly depending on build time |
| Black-box native | HTTP, database, broker, TLS, and container runtime. | Nightly, release candidates, or feature PRs |
| Platform matrix | Supported OS/architecture/base image/libc combinations. | Scheduled or pre-release |

### 14.1. Test Matrix to Document

- Spring Boot and Spring Framework versions.
- JDK vendor/major version.
- GraalVM distribution/release.
- Native Build Tools Maven/Gradle plugin version.
- JUnit Platform/Jupiter/Vintage versions.
- Mockito version and active mock maker.
- Byte Buddy version.
- Testcontainers/WireMock/MockWebServer versions if used.
- OS/architecture/libc and runtime container.
- Which tests ran on JVM, AOT-on-JVM, native test image, or black-box.

Whenever upgrading any component in the matrix, re-run the affected test groups. For example, upgrading Mockito can change the default mock maker; upgrading JUnit can change Native Image conditions; upgrading Spring Boot can alter AOT test integration.

### 14.2. Never Merge Test Reports Ambiguously

Report separately:

- JVM tests: pass/fail/skip counts and coverage.
- AOT-on-JVM: verified application contexts/profiles.
- Native tests: number of tests executed inside the native test image.
- Black-box tests: endpoints/scenarios/platforms executed.
- JVM-only tests: reason for excluding from native and replacement tests.
- Known limitations: features lacking verification evidence.

## 15. Hands-on Exercise: Replacing Instrumentation-Dependent Mocking with Native-Compatible Tests

**Scenario:** a Spring Boot order processing service uses Mockito to mock a static clock, mock a payment gateway, and mock a client constructor. JVM tests pass, yet the native test image fails when creating inline mocks. The application needs logic verified natively and communication verified against a payment stub.

### Tasks

1. Inspect the dependency graph for Mockito, Byte Buddy, JUnit Platform, and Native Build Tools.
2. Identify the active mock maker and which tests use static/constructor/final mocking.
3. Classify tests into JVM-only, AOT-on-JVM, native test, and black-box native.
4. Refactor the service to inject Clock, PaymentGateway, and ClientFactory via constructors/interfaces.
5. Write FakePaymentGateway and a fake factory to test domain/service logic.
6. Keep necessary inline Mockito tests on the JVM, documenting why they do not run in the native image.
7. Write native tests using fakes to verify order creation, payment failure, and retry flows.
8. Write a black-box integration test on a JVM harness: launch the native executable, connect to the payment stub, and call APIs.
9. Run AOT-on-JVM, nativeTest, and container smoke tests.
10. Record the version matrix, test reports, disabled tests with reasons, and replacement tests.
11. Compare JVM and native results for the same fixtures and side effects.

## 17. Official Documentation

Native testing features depend on the versions of Spring Boot, Spring Framework, JUnit, Mockito, and GraalVM Native Build Tools. Always cross-check against your project's exact releases:

- [Spring Boot — Testing GraalVM Native Images](https://docs.spring.io/spring-boot/how-to/native-image/testing-native-applications.html): JVM testing, AOT-on-JVM, Spring test contexts, Maven and Gradle native testing.
- [GraalVM Native Build Tools — Gradle Plugin](https://graalvm.github.io/native-build-tools/latest/gradle-plugin): nativeTest, nativeTestCompile, JUnit Platform, and test binary configuration.
- [GraalVM Native Build Tools — Maven Plugin](https://graalvm.github.io/native-build-tools/latest/maven-plugin): native test execution, Surefire/JUnit Platform compatibility, and plugin options.
- [GraalVM — Debug Native Tests in Maven and Gradle Projects](https://www.graalvm.org/latest/reference-manual/native-image/guides/debug-native-tests-maven-gradle/): building/debugging native test executables and resolving missing metadata.
- [Mockito 5 — Release Notes](https://github.com/mockito/mockito/wiki/Draft-Mockito-5-release-notes): default mock maker changes and notes on inline/subclass mock makers in GraalVM Native Image.
- [Mockito API](https://javadoc.io/doc/org.mockito/mockito-core/latest/org/mockito/Mockito.html): mocking mechanisms and release-specific instrumentation notes.
- [JUnit User Guide — Native Image Conditions](https://docs.junit.org/6.0.0/user-guide/#writing-tests-conditional-execution-native-image): @EnabledInNativeImage and @DisabledInNativeImage.
- [Byte Buddy](https://bytebuddy.net/): runtime code generation and instrumentation; verify support by version.

**Key takeaway:** mocking and instrumentation must be evaluated against the real underlying mechanism and exact versions. Maintain logic coverage on the JVM, verify Spring AOT on the JVM, select native tests for paths with divergence risk, and use black-box integration tests to validate the executable in the deployment environment.
