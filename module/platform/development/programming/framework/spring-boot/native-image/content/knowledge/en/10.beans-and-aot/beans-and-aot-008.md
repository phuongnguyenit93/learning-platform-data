# InstanceSupplier, Constructors, and Generated Bean Creation Paths

In a Spring Boot application, the Spring IoC Container creates beans from registered **bean definitions**. When using **Spring AOT** to prepare an application for **GraalVM Native Image**, Spring analyzes those definitions during the build phase and generates Java code to reproduce registration, instantiation, and required injection operations. A key element of that generated creation path is the **instance supplier**.

In the **Beans and AOT** chapter of the **`SPRING_BOOT_NATIVE_IMAGE`** module, this lesson explains `InstanceSupplier`, `BeanInstanceSupplier`, how Spring represents constructors and factory methods, how dependencies are passed into constructors, and how to read generated sources to understand how the container will create beans. This is foundational for handling cases AOT cannot infer, reducing reliance on reflection, and helping Native Image analyze the application more accurately.

> **Version scope:** `BeanInstanceSupplier` belongs to Spring Framework's AOT API starting from 6.0. Exact generated source code may vary across Spring Framework/Spring Boot versions and bean definition kinds. The generated code snippets in this lesson are illustrative examples based on the API structure; read the files generated by your own project version when debugging.

## 1. Learning objectives

After this lesson, you will be able to:

- Distinguish **bean definition**, **bean instance**, and **instance supplier**.
- Explain why Spring AOT generates suppliers instead of dynamically probing constructors/factory methods on every startup.
- Read the structure of `BeanInstanceSupplier.forConstructor(...)` and `forFactoryMethod(...)`.
- Understand how constructor injection, `@Bean` factory methods, and `@Autowired` members participate in the bean creation path.
- Identify configurations that are hard to translate into AOT code, such as hand-written custom instance suppliers, custom arguments, ambiguous multiple constructors, and dynamic bean registrations.
- Trace generated bean definitions and adjust source configurations so AOT processes them reliably.

## 2. How do bean definitions and bean instances differ?

A **bean definition** is a description telling the container how to manage a bean: bean type, scope, constructor/factory method, dependencies, lazy initialization, lifecycle callbacks, and related metadata.

A **bean instance** is the actual Java object created from a bean definition. For example, `OrderService` is a class; the bean definition describes how to create `OrderService`; the instance is a concrete `OrderService` object in the ApplicationContext.

Example:

~~~java
@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
~~~

When Spring scans the application configuration, the container registers a bean definition for `OrderService`. For singleton beans, the object is usually created when the ApplicationContext initializes (unless lazy or deferred). For prototype beans, an object is created each time it is requested. The bean definition describes **how to create**, whereas the instance is **the creation result**.

| Concept | Question answered | Example |
|---|---|---|
| Bean definition | What type and scope does this bean have, and how is it created? | `RootBeanDefinition(OrderService.class)` |
| Instance supplier | When an instance is needed, what logic is called to create the object? | Constructor reference or `BeanInstanceSupplier` |
| Bean instance | Which actual object was created? | `new OrderService(repository)` |

## 3. What is InstanceSupplier?

An **instance supplier** is a function/mechanism attached to a bean definition to create an instance when the container needs one. Instead of storing only a class and letting the container infer the constructor or factory method via reflection, a bean definition can specify an explicit supplier.

Conceptually:

~~~java
Supplier<OrderService> supplier =
        () -> new OrderService(orderRepository);
~~~

The snippet above only illustrates the role of a supplier. In Spring AOT, suppliers are generated according to the actual bean context and dependencies; it is not necessarily a plain `java.util.function.Supplier`.

Spring Framework provides `BeanInstanceSupplier<T>`, a specialized implementation of `InstanceSupplier<T>`. It stores information about the executable used to create the bean (constructor or factory method), supports resolving autowired arguments, and serves as a targeted instantiation mechanism instead of relying solely on reflection-based injection.

| API | Meaning |
|---|---|
| `BeanInstanceSupplier.forConstructor(...)` | Creates a supplier for a constructor with specified parameter types |
| `BeanInstanceSupplier.forFactoryMethod(...)` | Creates a supplier for a factory method, such as a `@Bean` method |
| `withGenerator(...)` | Specifies instance-creation code; can accept `RegisteredBean` and resolved arguments |
| `get(RegisteredBean)` | Container asks the supplier to create an instance for the registered bean |

If `BeanInstanceSupplier` is not given a generator, it can fall back to reflection to create the instance and contribute corresponding invocation hints. When AOT can determine the constructor/factory method, a generated generator expresses bean creation more directly. Therefore, the mere presence of `BeanInstanceSupplier` is not enough to conclude no reflection is used; inspect the `withGenerator(...)` section in the generated source.

A supplier **is not a bean pre-created during the build phase**. It is bean creation logic generated and stored in the bean definition. Only when the application runs and the container needs an instance is the supplier invoked according to the bean's scope/lifecycle.

## 4. How does Spring AOT analyze beans?

At normal runtime, Spring reads configuration, processes component scanning, parses `@Configuration`, locates suitable constructors, resolves dependencies, and instantiates beans. Some steps require metadata or reflection.

With Spring AOT, the engine creates an ApplicationContext for **AOT processing**. This context is refreshed in a special mode: configurations and bean definitions are analyzed and conditions are evaluated, but **regular application beans are not instantiated**. From the known definitions, the AOT engine generates source code, required bytecode, and Runtime Hints.

~~~mermaid
flowchart TD
    A["@Configuration / component scan / @Bean"] --> B["AOT ApplicationContext"]
    B --> C["Analyze and register bean definitions"]
    C --> D["Determine constructor or factory method"]
    D --> E["Generate InstanceSupplier / BeanInstanceSupplier"]
    E --> F["Generate bean definition registration code"]
    F --> G["Compile generated sources"]
    G --> H["Native Image analysis and compilation"]
    H --> I["Native executable"]
    I --> J["Runtime: container calls supplier when bean is needed"]
    J --> K["Bean instance + injection/lifecycle"]
~~~

Key points to remember:

1. **Build time:** Spring analyzes configuration and generates code to reproduce bean definitions and instance creation paths.
2. **Runtime:** Spring uses the generated AOT code and calls the supplier when a bean needs to be created.
3. **Not every bean is instantiated at build time.** Analyzing definitions does not mean creating production objects and baking them into the image heap.

Certain infrastructure beans participating directly in AOT processors may be instantiated to carry out build processing tasks. This is a special case for AOT infrastructure, not a general rule that Spring instantiates all application beans at build time.

### Which decisions are fixed at build time?

AOT operates on a fixed classpath and application configuration. Bean definitions affected by `@Profile` or `@Conditional` are evaluated during AOT processing; profiles/properties affecting whether a bean exists must be selected appropriately at build time. An AOT application cannot arbitrarily swap the entire bean definition set for a different classpath or profile at runtime.

If a bean is only registered by logic running after context creation in a way AOT cannot observe, the generated registration may omit that bean. Move registration logic into mechanisms AOT recognizes.

## 5. How does constructor injection become a supplier?

Consider two classes:

~~~java
@Repository
public class OrderRepository {
    public OrderRepository() {
    }
}
~~~

~~~java
@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
~~~

Spring knows `OrderService` requires an `OrderRepository` via its constructor. AOT can identify the constructor to call and the dependency type to resolve.

### Example shape of a constructor supplier

The snippet below depicts a generated supplier using the `BeanInstanceSupplier` API:

~~~java
private static BeanInstanceSupplier<OrderService> orderServiceInstanceSupplier() {
    return BeanInstanceSupplier.<OrderService>forConstructor(OrderRepository.class)
            .withGenerator((registeredBean, args) ->
                    new OrderService(args.get(0, OrderRepository.class)));
}
~~~

Meaning:

- `forConstructor(OrderRepository.class)` identifies the constructor taking an `OrderRepository` parameter.
- `BeanInstanceSupplier` asks the container to resolve constructor arguments according to the bean's dependencies.
- `args.get(0, OrderRepository.class)` retrieves the resolved dependency at parameter index 0.
- `new OrderService(...)` is a direct object instantiation call that the compiler can analyze without dynamically probing constructors on every bean creation.

A bean definition registered with that supplier can take a concise shape:

~~~java
RootBeanDefinition beanDefinition =
        new RootBeanDefinition(OrderService.class);
beanDefinition.setInstanceSupplier(orderServiceInstanceSupplier());
~~~

This is an **illustrative pattern explaining the mechanism**, not a guarantee of the exact class or method names every Spring AOT version will generate. Actual generated code may extract suppliers into helper methods, use method references, or include additional code for field/method injection and lifecycle.

### How is the constructor selected?

Spring needs to know which constructor is the bean creation path. Some practical rules:

- If a class has a **single constructor**, Spring can use it for constructor injection without `@Autowired`.
- If there are multiple constructors, mark the desired constructor with `@Autowired` when appropriate; avoid leaving selection ambiguous.
- Constructors should declare required dependencies explicitly with specific types.
- Avoid complex parameter structures that AOT cannot reliably express as value-generation code, especially in manually registered bean definitions.

Example with multiple constructors:

~~~java
@Service
public class ReportService {
    private final ReportRepository repository;

    @Autowired
    public ReportService(ReportRepository repository) {
        this.repository = repository;
    }

    public ReportService() {
        this.repository = null;
    }
}
~~~

This example clarifies constructor selection intent, though the default constructor assigning `null` is illustrative only; in real applications, design classes so every valid creation path receives required dependencies. If multiple constructors are unnecessary, keeping a single constructor is usually clearer.

## 6. `@Bean` factory methods also have an InstanceSupplier

A bean does not have to be created via a class's direct constructor. A `@Bean` factory method can create and configure an object:

~~~java
@Configuration(proxyBeanMethods = false)
public class DataSourceConfiguration {

    @Bean
    public SimpleDataSource dataSource() {
        return new SimpleDataSource();
    }
}
~~~

Here:

- `DataSourceConfiguration` is the configuration bean.
- `dataSource()` is the factory method.
- `SimpleDataSource` is the returned bean's type.

Spring AOT can generate a supplier using `BeanInstanceSupplier.forFactoryMethod(...)`. An approximation of the official generated code:

~~~java
private static BeanInstanceSupplier<SimpleDataSource> dataSourceInstanceSupplier() {
    return BeanInstanceSupplier.<SimpleDataSource>
            forFactoryMethod(DataSourceConfiguration.class, "dataSource")
            .withGenerator((registeredBean) ->
                    registeredBean.getBeanFactory()
                            .getBean(DataSourceConfiguration.class)
                            .dataSource());
}
~~~

This supplier invokes the `dataSource()` factory method on the container-managed configuration bean. The `SimpleDataSource` bean definition uses this supplier whenever it needs to create an instance.

### Factory methods with parameters

Example of a factory method depending on another bean:

~~~java
@Configuration(proxyBeanMethods = false)
public class ClientConfiguration {

    @Bean
    public PaymentClient paymentClient(PaymentProperties properties) {
        return new PaymentClient(properties.endpoint());
    }
}
~~~

In generated code, Spring can use `forFactoryMethod(...)` to describe the factory method along with its parameter types, then use a generator accepting `RegisteredBean` and resolved arguments. Illustrative code:

~~~java
BeanInstanceSupplier.<PaymentClient>forFactoryMethod(
        ClientConfiguration.class,
        "paymentClient",
        PaymentProperties.class)
    .withGenerator((registeredBean, args) ->
            registeredBean.getBeanFactory()
                    .getBean(ClientConfiguration.class)
                    .paymentClient(args.get(0, PaymentProperties.class)));
~~~

This focuses on the idea of resolving parameters and invoking the factory method. How the code generator optimizes the call may vary depending on the Spring Framework version and `@Configuration` settings.

## 7. What parts make up a generated bean creation path?

When reading a generated class named like `...__BeanDefinitions`, you typically look for these parts:

1. **Bean type:** the actual type exposed by the definition.
2. **Bean definition:** generated metadata, usually `RootBeanDefinition` or an equivalent registration API.
3. **Instance supplier:** the supplier attached to the definition via `setInstanceSupplier(...)` or an equivalent API.
4. **Constructor/factory method:** the executable creating the object, which may be a constructor reference, factory method, or `BeanInstanceSupplier`.
5. **Injection code:** `@Autowired` fields/methods may be handled by code/hooks generated during AOT.
6. **Initialization/lifecycle metadata:** init/destroy callbacks, post-processing, and required proxies must still be preserved.

Not every bean follows the exact same pattern. A class with a no-arg constructor may use a simple method reference:

~~~java
beanDefinition.setInstanceSupplier(MyConfiguration::new);
~~~

A bean created by a factory method may use `BeanInstanceSupplier`. A bean with multiple constructor arguments needs a supplier capable of resolving arguments. A bean needing field or method injection may have extra generated code.

**The supplier only handles instance creation.** The container remains responsible for scope, dependency relationships, post-processors, AOP proxies, and init/destroy callbacks according to the bean definition.

## 8. Field and method injection in AOT

Example:

~~~java
@Component
public class NotificationService {

    @Autowired
    private MessageGateway gateway;

    @Autowired
    public void setClock(Clock clock) {
        // ...
    }
}
~~~

At normal runtime, Spring can use `AutowiredAnnotationBeanPostProcessor` to discover injection points. In AOT, this processor participates in AOT registration and can generate code to perform the needed operations more explicitly.

Therefore, when reading generated code, do not look only for `new NotificationService(...)`. Check the member-injection handling sections if the bean uses `@Autowired` on fields or methods. Constructor injection is usually easier to read and express, while also allowing dependencies to be clear `final` fields.

Example preferring constructor injection:

~~~java
@Component
public class NotificationService {
    private final MessageGateway gateway;
    private final Clock clock;

    public NotificationService(MessageGateway gateway, Clock clock) {
        this.gateway = gateway;
        this.clock = clock;
    }
}
~~~

With this approach, all required dependencies appear directly in the constructor signature, helping AOT determine the bean creation path directly.

## 9. Bean types should be declared specifically

Spring AOT needs to know the exact bean type to analyze characteristics such as annotations, lifecycle methods, injection points, or proxies.

Suboptimal example:

~~~java
@Configuration(proxyBeanMethods = false)
public class PaymentConfiguration {

    @Bean
    public PaymentGateway paymentGateway() {
        return new StripePaymentGateway();
    }
}
~~~

The method declares return type `PaymentGateway`, whereas the actual object is `StripePaymentGateway`. If the implementation has annotations or special methods that AOT needs to recognize, exposing only the interface may prevent that metadata from being processed completely.

Declare the specific type when possible:

~~~java
@Configuration(proxyBeanMethods = false)
public class PaymentConfiguration {

    @Bean
    public StripePaymentGateway paymentGateway() {
        return new StripePaymentGateway();
    }
}
~~~

Consumers can still inject by interface:

~~~java
public CheckoutService(PaymentGateway gateway) {
    this.gateway = gateway;
}
~~~

The key point is that **the return type of the `@Bean` factory method** lets AOT see the concrete bean type. If the abstraction is intentional and the implementation has no special metadata requiring processing, an interface return type can still be appropriate; base the choice on actual requirements.

## 10. Bean definition patterns that cause difficulties for AOT

### 10.1. Registering beans via callbacks not processed by AOT

Some applications register beans by manipulating `BeanFactory` directly inside a custom callback. If the AOT engine does not see that bean definition during analysis, it may not generate the necessary registration code or Runtime Hints.

When registering beans programmatically, use **`BeanDefinitionRegistry`** to register bean definitions. Suitable approaches commonly include:

- `ImportBeanDefinitionRegistrar` imported from Spring configuration.
- `BeanDefinitionRegistryPostProcessor` when registry processing is needed at the appropriate time.
- AOT contribution mechanisms such as `BeanFactoryInitializationAotProcessor` when custom infrastructure needs to contribute code to AOT.

If a processor is itself registered as a bean and needs to run in both AOT and runtime, understand its lifecycle thoroughly to avoid duplicate processing or missed behavior.

### 10.2. Bean definitions with application-supplied custom instance suppliers

Example:

~~~java
RootBeanDefinition definition = new RootBeanDefinition(MyClient.class);
definition.setInstanceSupplier(() -> createClientDynamically());
registry.registerBeanDefinition("myClient", definition);
~~~

A supplier lambda or method reference **already present on the input bean definition** is not the same as a generated supplier created by Spring AOT. Spring AOT cannot automatically turn every arbitrary supplier into AOT code, because the logic inside the lambda may not be representable from metadata.

If a bean definition needs dynamic creation, design the registration so AOT can analyze it, or contribute dedicated code/hints via the appropriate extension API. Do not assume placing a lambda in `setInstanceSupplier` will let Native Image know every class/resource the lambda accesses.

### 10.3. Calling getBean with custom arguments

The container supports requesting bean creation with custom arguments, but this dynamic invocation forces Spring to probe for a matching constructor or factory method at runtime:

~~~java
// Illustrative example of creating a bean with custom arguments:
MyPrototype prototype = beanFactory.getBean(MyPrototype.class, runtimeArgument);
~~~

These arguments are not necessarily known to AOT in advance. Using custom arguments may require manual reflection hints; it also bypasses the generated instance supplier, causing post-instantiation optimizations (such as field/method injection handled by the supplier) not to execute along the expected AOT path.

For prototypes needing per-request input data, use a **dedicated factory bean/service**:

~~~java
@Component
public class ReportFactory {
    public Report create(String title, ReportRepository repository) {
        return new Report(title, repository);
    }
}
~~~

The factory is a Spring-managed bean with a known creation path; object creation logic with dynamic parameters lives in one clear place instead of asking the container to probe constructors on every call.

### 10.4. Multiple constructors without a clear preferred constructor

The container can select a constructor from multiple candidates, but relying on heuristics makes the bean creation path hard to read and analyze. Do the following:

- Keep a single primary constructor if the design allows.
- Use `@Autowired` to mark the intended constructor when multiple constructors exist.
- If the class cannot be modified, consider the bean definition's `preferredConstructors` metadata when appropriate for the API/version in use.

### 10.5. Circular dependencies

Some dependency cycles through setter or field injection may run at normal runtime thanks to circular reference handling. In an AOT-optimized context, explicit circular dependencies can prevent the application from starting.

Redesign the dependency graph to eliminate cycles. If lazy access is needed, use `@Lazy` at the injection point or `ObjectProvider<T>` to obtain the dependency only when actually needed.

## 11. Constructors and factory methods should be simple and clearly typed

Spring AOT must generate Java code to represent values and dependencies. For manually registered bean definitions, a complex custom data structure passed as a constructor argument or property may not be directly representable by the code generator.

Example:

~~~java
record RuntimeOptions(Map<String, List<CustomRule>> rules) {}

public class RuleEngine {
    public RuleEngine(RuntimeOptions options) {
        // ...
    }
}
~~~

Using a `record` is not automatically wrong for AOT. The issue arises when **a bean definition is created programmatically with a custom structured value** that the code generator does not know how to express. If AOT reports that it cannot generate value code, consider:

- Turning the complex value into a bean with its own bean definition.
- Splitting the structure into simpler types or container-managed dependencies.
- Using a factory method with a specific return type.
- Implementing `ValueCodeGenerator.Delegate` only when genuinely needing to support a special value type and after understanding the extension API.

Do not add a custom code generator before pinpointing the exact value type causing the error.

## 12. How to find and read generated bean definitions

Spring AOT typically generates source classes named like `...__BeanDefinitions` and an `ApplicationContextInitializer` entry point used to initialize the ApplicationContext with AOT optimizations.

Common locations:

| Build tool | Generated AOT sources (typical) |
|---|---|
| Maven | `target/spring-aot/main/sources/` |
| Gradle | `build/generated/aotSources/` |

These are the standard locations described in Spring documentation; plugin output configuration may vary. Search by bean or class name:

~~~bash
# Linux/macOS, e.g., when using Maven
find target/spring-aot -type f -name '*.java'
grep -R "BeanInstanceSupplier" target/spring-aot

# Example when using Gradle
find build/generated -type f -name '*.java'
grep -R "BeanInstanceSupplier" build/generated
~~~

PowerShell:

~~~powershell
Get-ChildItem target/spring-aot, build/generated -Recurse -Filter *.java -ErrorAction SilentlyContinue |
    Select-Object -ExpandProperty FullName

Get-ChildItem target/spring-aot, build/generated -Recurse -Filter *.java -ErrorAction SilentlyContinue |
    Select-String -Pattern 'BeanInstanceSupplier|setInstanceSupplier'
~~~

When you find a generated class, read it in order:

1. Declared bean name and bean type.
2. Method returning the supplier.
3. Described constructor/factory method.
4. Dependency arguments fetched from `AutowiredArguments`.
5. Additional injection/lifecycle code.
6. Where the bean definition attaches the supplier and is registered.

**Do not edit generated sources directly.** Fix the class, constructor, `@Bean` method, bean registration, or Runtime Hints in your managed source code, then rerun AOT.

## 13. Practical walkthrough: from constructor to generated supplier

Create two simple classes:

~~~java
package com.example.checkout;

import org.springframework.stereotype.Repository;

@Repository
public class InventoryRepository {
    public boolean available(String sku) {
        return true;
    }
}
~~~

~~~java
package com.example.checkout;

import org.springframework.stereotype.Service;

@Service
public class CheckoutService {
    private final InventoryRepository inventoryRepository;

    public CheckoutService(InventoryRepository inventoryRepository) {
        this.inventoryRepository = inventoryRepository;
    }

    public boolean canCheckout(String sku) {
        return inventoryRepository.available(sku);
    }
}
~~~

A practical workflow:

**Step 1 — Inspect the bean creation path in source code.** `CheckoutService` has only one constructor accepting `InventoryRepository`; the dependency is explicitly declared.

**Step 2 — Run Spring AOT using your project's build tool.** With Maven, a common goal is:

~~~bash
./mvnw -Pnative package
~~~

With Gradle:

~~~bash
./gradlew processAot
~~~

These commands assume the project has configured the corresponding profile/plugin. If you only want to inspect AOT before native compilation, run the standalone AOT task/goal appropriate for your version.

**Step 3 — Locate the generated bean definition.** Using the paths from the previous section, search for `CheckoutService` or `BeanInstanceSupplier`.

**Step 4 — Verify the supplier targets the right constructor.** In the generated code, look for the `InventoryRepository` parameter type and the `CheckoutService` instantiation block.

**Step 5 — Experiment with design changes to observe the effect.** Add a second constructor or change to a factory method, rerun AOT, and see how code generation changes. Then revert to a clear design, avoiding unnecessary multiple bean creation paths.

**Step 6 — Build and run the native application.** Native Image validates all reachable code and metadata; generated suppliers are one part of the process and do not guarantee every other dynamic library is compatible.

## 14. Distinguishing suppliers from reflection hints

`BeanInstanceSupplier` and `RuntimeHints` are both AOT-related, but solve different problems:

| Mechanism | Purpose | Example |
|---|---|---|
| `InstanceSupplier` / `BeanInstanceSupplier` | Create a bean using a determined constructor or factory method | `forConstructor(OrderRepository.class)` |
| Generated bean definitions | Reproduce bean configuration/registration at runtime | `RootBeanDefinition` + `setInstanceSupplier(...)` |
| Injection code | Supply dependencies to constructors/fields/methods | Generated calls for `@Autowired` |
| `RuntimeHints` | Register required reflection, resources, serialization, JDK proxies | `hints.resources().registerPattern(...)` |

A supplier creating an object does not mean all reflection operations inside that object are registered. If `OrderService` calls a library that loads classes by name or reads files from the classpath, Native Image may still require hints for those operations.

Conversely, adding reflection hints for a constructor will not fix a bean definition that AOT cannot see. Identify the right failure category before adding metadata.

## 15. Self-check exercises

**Q1.** What is `InstanceSupplier`?

**Hint:** it is logic used by a bean definition to create a bean instance when the container needs one; it is not an object pre-created during the AOT build.

**Q2.** Why does AOT use `BeanInstanceSupplier.forConstructor(...)`?

**Hint:** it describes a specific constructor, enabling Spring to resolve dependency arguments and generate direct object creation code, reducing reliance on reflection-based constructor discovery.

**Q3.** When is `forFactoryMethod(...)` used?

**Hint:** when a bean is created by a factory method, such as a `@Bean` method inside a `@Configuration` class.

**Q4.** Does Spring AOT instantiate all bean instances at build time?

**Hint:** no. AOT processing primarily creates bean definitions and generated assets; regular application beans are created when the application runs and the container needs them.

**Q5.** Why should `@Bean` methods declare specific return types?

**Hint:** AOT needs to know the exact bean type to analyze annotations, injection points, lifecycle callbacks, and proxies on the implementation.

**Q6.** What issues can calling `getBean(MyPrototype.class, runtimeArgument)` cause?

**Hint:** custom arguments require dynamic constructor/factory method discovery, may need reflection hints, and bypass optimized instance suppliers, losing some generated injection handling.

**Q7.** If `BeanInstanceSupplier` does not appear in generated sources, can you conclude AOT did not run?

**Hint:** not necessarily. No-arg beans may use a direct constructor reference; simple factory methods may use method references; output directories may also differ. Search for `setInstanceSupplier`, `InstanceSupplier`, and bean definition classes.

## 16. Checklist for AOT-friendly bean design

- [ ] Each bean has a clear instance creation path, preferring constructor injection.
- [ ] If multiple constructors exist, the chosen constructor is marked with an appropriate annotation or metadata.
- [ ] `@Bean` factory methods declare specific return types whenever possible.
- [ ] Required dependencies are expressed as constructor/factory method parameters.
- [ ] Avoid unanalyzable custom instance suppliers unless an appropriate AOT contribution exists.
- [ ] Avoid asking the container to create beans with arbitrary per-call custom arguments; use a factory bean/service for dynamic data.
- [ ] Programmatically registered beans go through `BeanDefinitionRegistry` or appropriate AOT extensions.
- [ ] Minimize circular dependencies; consider `@Lazy` or `ObjectProvider` if deferral is needed.
- [ ] Do not edit generated sources directly; locate and fix the source configurations that produce them.
- [ ] Distinguish bean-creation-path errors from reflection/resource metadata errors.
- [ ] Test Spring AOT and Native Image on the project's exact Spring/GraalVM versions.
