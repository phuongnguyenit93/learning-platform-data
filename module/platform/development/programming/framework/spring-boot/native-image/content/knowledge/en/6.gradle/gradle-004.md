# AOT Compilation Tasks and Adding Generated Resources to the Classpath in Gradle

## 1. Objectives and Context

In the **SPRING_BOOT_NATIVE_IMAGE** module, a Spring Boot application is processed with **Spring AOT** and then compiled into a **GraalVM Native Image** to evaluate startup time, memory usage, and compatibility. When using Gradle, the question is not merely "how do I run `nativeCompile`", but also:

> How are the Java sources and resources generated by Spring AOT compiled, passed across Gradle tasks, and placed onto the classpath used by Native Image?

Understanding this flow helps diagnose three common categories of issues:

- `processAot` fails to analyze the application at **build time**;
- AOT code was generated, yet **was not compiled or did not enter the classpath** of the subsequent step;
- the native application starts up, yet lacks **resources, reflection metadata, or dynamic access behavior** at runtime.

Spring AOT, Gradle, and Native Image have distinct responsibilities: **Spring AOT** prepares code and metadata based on Spring semantics; **Gradle** orchestrates generating/compiling/copying those outputs; **GraalVM Native Image** consumes bytecode and metadata to create the native executable.

## 2. Seeing the Entire Task Graph

For a Spring Boot project configured to support AOT/native, the conceptual flow typically resembles the following diagram:

~~~mermaid
flowchart TB
    S["src/main/java and src/main/resources"] --> M["compileJava / processResources / classes"]
    M --> A["processAot: Spring analyzes configuration and beans"]
    A --> GS["Generated AOT Java sources"]
    A --> GR["Generated AOT resources / metadata"]
    GS --> CJ["compileAotJava"]
    GR --> PR["processAotResources"]
    CJ --> AC["aotClasses: prepared AOT outputs"]
    PR --> AC
    M --> NC["nativeCompile: GraalVM Native Image"]
    AC --> NC
    NC --> E["Native executable"]
~~~

**Note:** this represents a *logical dependency flow*, not a fixed task graph snapshot across all versions. Gradle and plugins may add tasks, rename certain intermediate tasks, or organize dependencies differently. Use `./gradlew tasks --all` and `./gradlew ... --dry-run` to inspect your actual project.

In common Gradle/Spring Boot setups:

| Task or Task Group | Primary Responsibility | Outputs of Interest |
| --- | --- | --- |
| `compileJava` | Compiles application Java code | Application `.class` files |
| `processResources` | Copies/processes resources from `src/main/resources` | Standard resources on classpath |
| `classes` | Aggregates standard compilation and resource outputs | Prepared application inputs |
| `processAot` | Runs Spring AOT on the application with required inputs | AOT Java code and AOT resources/metadata |
| `compileAotJava` | Compiles Java code generated by AOT | Bytecode of AOT code |
| `processAotResources` | Processes/copies resources generated by AOT | AOT resources used on the build classpath |
| `aotClasses` | Aggregates AOT class/resource outputs (if the plugin version provides this task) | AOT outputs ready for the next step |
| `nativeCompile` | Invokes Native Image with the required classpath and configuration | Executable for target OS/CPU |

**Not all tasks execute sequentially in table order.** Gradle executes only necessary tasks according to the dependency graph; some independent tasks may run in parallel.

## 3. Minimal Gradle Configuration to Coordinate AOT and Native

Suppose the project uses **Gradle Groovy DSL** (`build.gradle`), with Java and Spring Boot. The Native Build Tools plugin must be applied if you want native tasks such as `nativeCompile`.

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '<SPRING_BOOT_VERSION>'
    id 'org.graalvm.buildtools.native' version '<NATIVE_BUILD_TOOLS_VERSION>'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

test {
    useJUnitPlatform()
}
~~~

The two strings `<SPRING_BOOT_VERSION>` and `<NATIVE_BUILD_TOOLS_VERSION>` are only **placeholders**: replace them with compatible versions used by your project before running. In projects managing versions via `settings.gradle`, a version catalog, or plugin management, versions may not need to be written directly in the `plugins` block. Depending on project setup, a BOM/dependency management mechanism may also need to be configured.

The **Spring Boot Gradle** plugin creates and configures tasks for the application, including AOT in supported versions. The **GraalVM Native Build Tools** plugin provides integration with GraalVM Native Image. When both are configured compatibly, the native build pipeline consumes the AOT outputs prepared by the Spring Boot plugin.

Verify with the project's own Gradle Wrapper:

~~~bash
# List tasks, including less-visible tasks.
./gradlew tasks --all

# Inspect the planned task graph without executing the build.
./gradlew nativeCompile --dry-run
~~~

On Windows, use `gradlew.bat`; the shell examples here are for Linux/macOS. If `nativeCompile` does not exist, verify `org.graalvm.buildtools.native` application and plugin compatibility. If `processAot` does not exist, check the Spring Boot plugin/version and related configuration.

## 4. `processAot`: Where Spring Turns Configuration into Code and Metadata

`processAot` is the step that processes the application with Spring AOT **at build time**. Conceptually, it inspects the application classpath, Spring configuration, bean definitions, and relevant conditions to generate initialization code and information required for the native environment.

Example:

~~~java
@Configuration(proxyBeanMethods = false)
class BillingConfiguration {
    @Bean
    BillingService billingService(PaymentGateway paymentGateway) {
        return new BillingService(paymentGateway);
    }
}
~~~

Normally, when running on the JVM, Spring reads configuration, creates bean definitions, and resolves factory method calls during startup. With AOT, Spring can generate Java code to handle the corresponding bean registration/instantiation; Spring still instantiates beans according to the lifecycle at runtime, while eliminating discovery work that can be done ahead of time.

Beyond Java code, AOT processing can supply or aggregate **runtime hints** for cases like reflection, JDK dynamic proxies, resources, and serialization. These hints help GraalVM Native Image retain dynamic access capabilities that are not clear enough from standard bytecode analysis.

Run the AOT step by itself:

~~~bash
./gradlew processAot
~~~

In common Spring Boot Gradle configurations, generated directories may include paths like:

~~~text
build/
  generated/
    aotSources/             # Java sources generated by Spring AOT
    aotResources/           # Resources/metadata generated by AOT
~~~

Exact paths are an **implementation detail of the plugin version**. Do not hard-code them as a source of truth in CI setups: locate actual outputs in `build/` or inspect Gradle task outputs. You should not edit generated files directly because the next build may overwrite them.

### Why Can `processAot` Fail Even When `compileJava` Succeeds?

`compileJava` primarily confirms that source code compiles. `processAot` must process **Spring configuration** and the components needed to prepare the bean graph. It can run into issues when:

- a configuration condition depends on an environment variable or profile different from what was expected;
- bean initialization code or a framework extension attempts work that is only valid at runtime;
- dynamic bean registration cannot be predicted during the AOT phase;
- a dependency or plugin does not yet properly support AOT;
- resources or configuration details needed at build time are unavailable.

Do not assume that external services like databases, brokers, or APIs must always be running during AOT processing; that depends on how the application initializes and designs its beans. If AOT processing is attempting unnecessary network work, review the initialization logic rather than blindly starting every external service in CI.

### Build-Time vs. Runtime Configuration

Some conditions determining **bean structure** can be evaluated at AOT time. For instance, if the build configuration causes a bean not to be registered, you cannot assume flipping an environment variable when launching the executable will make that bean appear.

Conversely, ordinary runtime values such as URLs, timeouts, or credentials are **not automatically frozen** simply because AOT is used. Distinguish between "values read at runtime" and "values that determine the bean graph at build time."

## 5. `compileAotJava`: AOT Code Must Become Bytecode Before Native Image Can Use It

The Java source output from `processAot` is not enough for GraalVM Native Image to build the application. Gradle needs to compile the generated `.java` files into `.class` files, in a context that may reference types from application sources and dependencies.

The `compileAotJava` task (in plugin versions that provide it) handles this step:

~~~bash
# Observe the task compiling AOT outputs.
./gradlew compileAotJava
~~~

The classpath for **compiling AOT code** typically requires compiled application classes and corresponding dependencies. Meanwhile, the **Native Image** classpath needs both application classes and compiled AOT classes. These are two distinct classpath purposes:

| Classpath | What Is It Used For? | What Happens If Inputs Are Missing? |
| --- | --- | --- |
| Java compile classpath | Compiling application source code | Missing symbol/type errors in `compileJava` |
| AOT compile classpath | Compiling Java sources generated by Spring AOT | Missing class/symbol errors in `compileAotJava` |
| AOT processing classpath | Letting Spring see code, dependencies, and resources to analyze | Configuration/bean analysis errors or missing data sources |
| Native compilation classpath | Letting Native Image analyze bytecode, AOT outputs, and metadata | Missing classes, missing metadata, or incorrect executable behavior |

With official plugins properly integrated, Gradle generally manages these relationships through tasks/configurations/source sets. Avoid using `files('build/generated/aotSources')` to manually attach generated directories to every source set; doing so risks duplicate classes or coupling to unstable internal paths.

## 6. `processAotResources`: Why Generated Resources Must Enter the Classpath

A Spring Boot project has **two groups of resources** to distinguish:

1. **Application resources**: e.g., `src/main/resources/application.yml`, templates, schemas, message bundles; processed via `processResources`.
2. **AOT-generated resources/metadata**: can include configuration or metadata for Spring bootstrap and Native Image; processed via the AOT resource pipeline such as `processAotResources`.

Illustrative inputs:

~~~text
src/main/resources/
  application.yml
  templates/invoice.txt
~~~

Conceptual outputs after processing:

~~~text
build/
  resources/
    main/                  # Standard application resources
    aot/                   # AOT resources after processing (plugin-dependent)
  classes/
    java/
      main/                # Application bytecode
      aot/                 # AOT bytecode (plugin-dependent)
~~~

`processAotResources` ensures resource files generated during AOT are placed into the corresponding resource output so **subsequent steps can see them**. In Gradle, those outputs participate in the classpath through appropriate task/source set configuration.

Common pitfall: **a resource being on the build classpath does not mean it is guaranteed to be inside the native executable**. Native Image handles resources via reachability/resource metadata mechanisms; files accessed by dynamic names may still need to be declared via runtime hints or library metadata.

### Example: Declaring a Resource the Application Actually Needs

Suppose at runtime a service reads a template by name:

~~~java
try (InputStream in =
         getClass().getResourceAsStream("/templates/invoice.txt")) {
    if (in == null) {
        throw new IllegalStateException("Missing template invoice.txt");
    }
    // Read template contents and generate invoice...
}
~~~

In a JVM application, the resource copied by `processResources` can be found on the classpath. When building native, you must ensure the template is included in the image. If no library/framework supplies the appropriate metadata, you can register:

~~~java
package com.example.invoice;

import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportRuntimeHints;

@Configuration(proxyBeanMethods = false)
@ImportRuntimeHints(InvoiceHints.class)
class InvoiceConfiguration {
}

class InvoiceHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("templates/invoice.txt");
    }
}
~~~

This example satisfies **two independent conditions**:

- `src/main/resources/templates/invoice.txt` must exist and enter the build's input classpath.
- Native Image must have appropriate metadata/resource hints to **package** that resource into the executable.

If the file does not exist in the first place, adding a hint will not create the file. If the file exists yet is omitted from the native image, checking only `processResources` is insufficient. That is why you should verify both Gradle outputs and the actual running native application.

## 7. Classpath Configurations: Understand Before Customizing

Gradle manages classpaths through **configurations** (such as compile/runtime classpaths) and **source set/task** outputs. When the Spring Boot plugin and Native Build Tools combine, they wire AOT outputs into the right places for native compilation.

Principles that prevent errors:

- **Compile classpath** serves source compilation; **runtime classpath** contains what the application needs at runtime or for build-time analysis tools.
- **Generated sources** must be compiled before entering native compilation; placing a raw Java source directory onto a Java runtime classpath is not enough.
- **Generated resources** must pass through resource tasks to appear on the appropriate classpath.
- **Native Image metadata** must be visible to the tool; do not assume every JSON/resource file on the classpath is automatically retained in the binary.
- **Task dependencies** guarantee outputs are produced before downstream tasks consume them. Do not use manual ordering of shell commands as a substitute for Gradle's dependency graph.

Some plugin versions define AOT-related configurations/source sets (such as configurations for AOT compile/runtime). Exact names and relationships vary by version, so customize only after inspecting the configuration/documentation of the plugin version in use.

### When You Have Generated Sources/Resources from Other Tools

Suppose the project also generates Java from OpenAPI or generates templates via a separate task. This differs from Spring AOT outputs:

1. Clearly declare **the task producing the files** and its output directory.
2. Wire the output into the source set or input of consuming tasks through Gradle-supported mechanisms so Gradle tracks the dependency.
3. Ensure files are generated **before** Spring AOT analyzes the classpath if AOT logic depends on them.
4. For resources that must end up in the native image, configure resource hints when needed.

Do not manually copy all of `build/generated` into `src/main/resources` or add every generated directory to every classpath: this can cause duplicate resources, retain unnecessary files, and make caching/incremental builds unpredictable.

## 8. Practice: Observing Step by Step Instead of Just Running `nativeCompile`

### Step 1: Verify Tasks Exist

~~~bash
./gradlew tasks --all
~~~

Look for the relevant tasks: `processAot`, `compileAotJava`, `processAotResources`, `aotClasses`, and `nativeCompile`. Do not insist that every single one appear if your plugin version organizes tasks differently; rely on the actual task graph.

### Step 2: Run AOT Separately

~~~bash
./gradlew processAot
~~~

Check:

- Do AOT logs report any bean configuration, dependency, or build-time execution errors?
- Are generated Java code and resources present in the corresponding build directory?
- If files are generated by another task, did that task run before AOT when required?

If `processAot` fails, do not jump straight to fixing `nativeCompile`; resolve the root cause in the AOT stage.

### Step 3: Observe AOT Compilation and Resource Processing

~~~bash
# Use when these tasks exist in the plugin version you are using.
./gradlew compileAotJava processAotResources
~~~

Verify that generated Java code became bytecode and AOT resources were processed. If `compileAotJava` reports missing types, inspect the AOT compile classpath, dependency scopes, and generated code. If `processAotResources` fails to produce an expected file, check whether `processAot` generated it and whether the task has the right inputs.

### Step 4: Preview What Gradle Plans to Run for Native Build

~~~bash
./gradlew nativeCompile --dry-run
~~~

`--dry-run` displays the planned tasks without executing the build; use it to confirm the AOT chain connects to native compilation. This mode **does not verify classpath contents or linking**. Run the real build when you want to verify final output.

### Step 5: Build and Run the Native Executable

~~~bash
./gradlew nativeCompile
~~~

The executable is typically located in:

~~~text
build/native/nativeCompile/
~~~

The binary name can depend on plugin configuration and project name. On Windows it may have a `.exe` extension. Check logs to distinguish failures originating in AOT, Java compilation, Native Image analysis, or the linker.

Then run the actual binary on a compatible OS/architecture, testing at least one HTTP endpoint along with flows involving resources/reflection. Only then do you verify that generated sources and resources are sufficient at runtime.

## 9. How Does Native Testing Differ from JVM Testing?

`./gradlew test` tests the application in a standard JVM environment. It is necessary, yet insufficient to confirm a native executable works properly, because the JVM can access classes and resources that were never declared to the native image.

Native Build Tools typically provides a **native test** flow such as `nativeTest`; Spring Boot may support separate AOT processing for tests, such as a `processTestAot` task in compatible versions. Native tests themselves must use the right project configuration and tools.

~~~bash
./gradlew test

# When the plugin and test suite support native tests:
./gradlew nativeTest
~~~

Test cases worth prioritizing include:

- Endpoints invoking services with AOP/proxies or transactions.
- JSON binding/serialization with real DTOs.
- Loading templates, schemas, and files from the classpath.
- Code paths using reflection or JNI.
- Spring configuration/profile/conditional branches expected in the native build.

If JVM tests pass while native tests fail, check dynamic operations and metadata before concluding Gradle skipped a task. If the native build does not even contain AOT classes or generated resources, inspect task outputs and the classpath/task graph first.

## 10. Troubleshooting Table for Common Issues

| Symptom | Where to Check | Appropriate Fix |
| --- | --- | --- |
| `Task 'processAot' not found` | Spring Boot Gradle plugin and applied version | Check `plugins`, an AOT-capable Spring Boot version, and the task list |
| `Task 'nativeCompile' not found` | GraalVM Native Build Tools plugin | Apply a compatible native plugin, verify task with `tasks --all` |
| `processAot` fails creating ApplicationContext | Conditions/configs and build-time bean logic | Remove runtime-only assumptions from configuration processing or supply appropriate build config |
| `compileAotJava` reports missing symbol | Application sources/bytecode, dependencies, and AOT compile classpath | Check dependency scopes, `processAot` outputs, and generated code |
| Native Image does not see AOT code | Task dependencies / native input classpath | Confirm plugins are integrated, inspect `--dry-run` and task-version classpaths |
| Resource present in JAR run but missing in native | `processResources`, `processAotResources`, resource hints | Confirm file exists on build classpath and is registered for inclusion in the native image |
| Reflection works on JVM but fails in native | Runtime hints / reachability metadata | Declare accessed classes/members, inspect library-provided metadata |
| Duplicate generated classes or resources | Custom source sets and manual generated paths | Remove duplicate configuration; let plugins manage AOT outputs when possible |
| `nativeCompile` fails due to missing compiler/linker | JDK/GraalVM and OS native toolchain | Install and configure `native-image`, compiler, and appropriate SDK/linker |
| Native fails on target machine/container | OS/CPU/ABI and native libraries | Build for the target platform; do not copy a macOS binary directly into a Linux container |

### Typical Case: "File Exists in Gradle Build, Yet Native Cannot Find It"

Suppose `src/main/resources/templates/invoice.txt` exists, and `build/resources/main/templates/invoice.txt` also exists after `processResources`. When running the JAR, `getResourceAsStream` reads it successfully; the native executable returns `null`.

Do not rush to copy the file into AOT generated directories. First check **resource metadata** so Native Image packages the file properly. A resource being placed on the classpath by Gradle at build time and a resource being embedded into the executable by Native Image for runtime are **two separate conditions**.

Conversely, if the file is missing from resource outputs at build time altogether, even a valid `RuntimeHintsRegistrar` cannot restore a missing file. In that case, inspect `processResources` or the Gradle task that produces the resource.

## 11. Build-Time vs. Runtime Classpath: A Decisive Difference

When running a JAR on the JVM, the **runtime classpath** is tied to classloaders: `.class` files and resources inside the JAR or dependencies can be loaded dynamically at runtime.

With Native Image, the **classpath at the native compilation step** is an input analyzed by the compiler. The produced executable **does not operate like a JVM with a JAR classpath that can be arbitrarily extended after build time**. Classes and resources needed by the executable must be visible to the compiler and retained through the appropriate mechanisms.

Therefore, evaluate three independent questions:

1. **Was it generated?** Did `processAot` produce the expected Java sources/metadata?
2. **Did it enter compilation inputs?** Did `compileAotJava`, `processAotResources`, and related tasks contribute their outputs to the native compile classpath?
3. **Was it retained in the binary?** Did Native Image know about those classes, resources, and dynamically accessed members via reachability analysis/hints?

Missing just one of these steps can cause the application to fail the build or misbehave at native runtime.

## 12. Checklist Before Measuring Startup Time and Memory

Once the Gradle/AOT pipeline is complete:

1. Run `./gradlew test` for a JVM baseline.
2. Run `./gradlew processAot` and confirm code/resources are generated.
3. Inspect `nativeCompile --dry-run` to confirm task wiring, then run the actual build.
4. Run the native executable and test branches involving reflection, proxies, serialization, and resources.
5. Compare JVM JAR and native with **identical endpoints, data, CPU/RAM, configuration, and load**; measure time-to-ready, RSS, latency, and throughput as needed.
6. Record the **native build duration**, Gradle/JDK/GraalVM/plugin versions, and OS/CPU. Native can start fast or use less memory in many scenarios, yet exact numbers must be measured.
7. If packaging a Linux container, build using an environment/builder matching Linux and the target architecture; never copy a macOS native executable directly into a Linux image.

Three key takeaways: **`processAot` generates code and metadata; Gradle compiles/copies AOT outputs and supplies the classpath to Native Image; Native Image creates the executable and decides what gets retained based on reachability/metadata.** Separating these layers clearly makes diagnosing Gradle, AOT, and resource errors far more straightforward.
