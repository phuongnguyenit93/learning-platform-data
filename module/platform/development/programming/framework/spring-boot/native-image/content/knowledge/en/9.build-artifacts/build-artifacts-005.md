# Converting an AOT-Processed JAR Using Buildpacks or GraalVM Native Image

## 1. From a JVM-Run JAR to a Native Product

In the **SPRING_BOOT_NATIVE_IMAGE** module, Spring Boot is processed with **Spring AOT** and then compiled into a GraalVM Native Image to evaluate startup time, memory usage, and operational behavior. A useful way to structure a pipeline is to build a **Spring Boot executable JAR containing AOT outputs**, archive that JAR as an intermediate artifact in CI/CD, and then convert that artifact into a native image in a separate step.

This approach separates two responsibilities:

1. **Packaging the intermediate Java artifact:** compiling source code, running AOT, and packaging a JAR containing generated classes, resources, and AOT metadata. The JAR remains a portable Java artifact that can be distributed across build machines.
2. **Converting the artifact to native:** using Cloud Native Buildpacks to produce a container image containing the native executable, or using GraalVM `native-image` to build the executable directly.

A mandatory prerequisite is that the JAR must contain **the generated AOT assets**, such as generated classes and JSON hint files. An ordinary Spring Boot JAR that has not run AOT does not automatically become a valid native input simply by renaming the file or invoking the compiler.

~~~mermaid
flowchart TB
    S["Spring Boot source + dependencies"] --> A["Spring AOT at build time"]
    A --> J["Executable JAR with generated classes and hints"]
    J --> V["Inspect / test AOT on JVM"]
    J --> B["Cloud Native Buildpacks + BP_NATIVE_IMAGE=true"]
    J --> N["Unpack JAR + GraalVM native-image"]
    B --> C["OCI container image containing native executable"]
    N --> E["Native executable for build machine OS/CPU"]
~~~

The two final branches produce **two different kinds of products**: Buildpacks produces a container image, whereas Native Image directly produces an executable. Do not confuse the intermediate JAR with either of those outputs.

## 2. How Does an AOT-Processed JAR Differ from an Ordinary JAR?

A Spring Boot executable JAR typically contains:

- `BOOT-INF/classes`: application bytecode and resources;
- `BOOT-INF/lib`: dependency JARs;
- `META-INF`: manifest and metadata;
- additional assets generated by AOT, including initialization code, proxy-support bytecode, and reachability hints when needed.

Spring AOT analyzes Spring configuration at build time, generating code and metadata for bean registration/initialization as well as dynamic access behaviors required by GraalVM. These assets must be packaged inside the JAR so the downstream conversion step can use them.

| Artifact | Contents | Purpose |
| --- | --- | --- |
| Standard JVM JAR | Application bytecode, dependencies, resources | Run on the JVM in the usual way |
| AOT-processed JAR | JAR contents plus AOT code/metadata | Test AOT on JVM or serve as input for creating native |
| Native executable | Machine code compiled for target OS/CPU | Run directly without a JVM |
| Native container image | Runtime filesystem and native executable inside the image | Deploy via Docker/container runtime |

**An AOT JAR is still a JAR that runs on the JVM.** To verify the generated AOT code before spending time on native compilation, you can run:

~~~bash
java -Dspring.aot.enabled=true -jar target/myproject-0.0.1-SNAPSHOT.jar
~~~

The JAR must have been packaged with AOT outputs. If the application starts up successfully in this mode, you have additional evidence that the generated initialization code works. This step **does not yet prove** that all reflection, resources, serialization, or proxies are compatible with GraalVM Native Image.

## 3. Producing an Executable JAR with AOT

### 3.1. Maven with Spring Boot Parent

If the project uses `spring-boot-starter-parent`, Spring Boot's `native` profile can configure running `process-aot` and the required settings for native builds. The application module needs the appropriate Spring Boot Maven Plugin and Native Build Tools plugin declarations.

Example plugins section in `pom.xml`:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
        <plugin>
            <groupId>org.graalvm.buildtools</groupId>
            <artifactId>native-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>
~~~

Build the AOT-processed JAR:

~~~bash
./mvnw -Pnative package
~~~

In this case, the goal of the `package` step is to produce a JAR with AOT assets for downstream conversion. Do not confuse this command with `native:compile`: the latter invokes Native Image to compile the executable directly. If the POM does not use Spring Boot Parent, you must configure the `process-aot` execution and corresponding plugins/lifecycle yourself.

### 3.2. Inspecting Assets Inside the JAR

After the build, locate the exact JAR file in `target/`. You can list its contents:

~~~bash
jar tf target/myproject-0.0.1-SNAPSHOT.jar
~~~

Search for relevant paths:

~~~bash
jar tf target/myproject-0.0.1-SNAPSHOT.jar | grep -E 'BOOT-INF/classes|BOOT-INF/lib|META-INF/native-image'
~~~

Exact filenames and counts vary by application and plugin. Verify that the JAR contains the generated AOT classes/resources and required hint metadata. Do not merely check that the JAR exists or is larger than an older JAR.

### 3.3. Build-Time Configuration Considerations

During AOT, Spring prepares the bean graph and evaluates configuration conditions. Therefore, any Spring profile, property, or environment variable that alters bean creation must be set accurately **when building the AOT JAR**.

For example, if `@ConditionalOnProperty` prevents a bean from being registered when AOT runs, changing that property at container runtime will not generate the missing bean. If multiple bean-graph variants are needed, you may have to build separate AOT artifacts for each matching build configuration.

Ordinary runtime properties such as URLs, timeouts, or credentials are not inherently frozen simply because AOT is used. Distinguish values read when the application runs from values that decide `ApplicationContext` structure at build time.

## 4. Branch One: Converting the JAR into a Native Container Image with Buildpacks

### 4.1. What Do Buildpacks Do?

**Cloud Native Buildpacks** accept application source or artifacts, detect the application type, choose required buildpacks, and produce an OCI image. For a Spring Boot AOT JAR, the Java buildpack can be instructed to produce a native executable via the environment variable:

`BP_NATIVE_IMAGE=true`

Advantages of this approach:

- No need to install GraalVM `native-image` directly on the host machine; the compiler and compatible toolchain are supplied inside the builder.
- The same intermediate JAR can be reused to produce an image in a CI/CD pipeline.
- The output is already a container image runnable via Docker or a compatible container platform.

You still need an accessible **Docker daemon** and the `pack` CLI installed if invoking Buildpacks directly.

### 4.2. Building a Container Image from an Existing JAR with `pack`

Suppose the AOT-processed JAR is:

~~~text
target/myproject-0.0.1-SNAPSHOT.jar
~~~

With Spring Boot 4.2, current documentation uses Ubuntu Resolute builder/run images and requires building the artifact with at least **JDK 25** for this Buildpacks conversion path. Verify builder compatibility with your Spring Boot version, Java version, and deployment platform.

~~~bash
pack build --builder paketobuildpacks/ubuntu-resolute-builder --run-image paketobuildpacks/ubuntu-resolute-run-tiny --path target/myproject-0.0.1-SNAPSHOT.jar --env 'BP_NATIVE_IMAGE=true' my-application:0.0.1-SNAPSHOT
~~~

Explanation:

| Component | Role |
| --- | --- |
| `pack build` | Starts the Cloud Native Buildpacks workflow |
| `--builder` | Selects the builder image containing buildpacks/toolchains to build |
| `--run-image` | Selects the base runtime image compatible with the builder |
| `--path` | Path to the AOT-processed JAR |
| `BP_NATIVE_IMAGE=true` | Instructs the Java buildpack to create a native executable |
| `my-application:0.0.1-SNAPSHOT` | Output OCI image name and tag |

Buildpacks builds the image inside the builder environment, so **GraalVM Native Image does not need to be installed on the host**. However, Docker must have enough CPU/RAM/disk for native compilation; the build can take significantly longer than ordinary JAR packaging.

After the build finishes, run the container:

~~~bash
docker run --rm -p 8080:8080 my-application:0.0.1-SNAPSHOT
~~~

Check startup logs, health endpoints, and business APIs. Replace the image name, port, and endpoints according to your actual configuration.

### 4.3. Using Spring Boot Maven Plugin Instead of `pack`

If you want the Spring Boot Maven Plugin to orchestrate building the container from the project, you can run:

~~~bash
./mvnw -Pnative spring-boot:build-image
~~~

With the `native` profile configured per Spring Boot Parent, the plugin sets up the environment for Buildpacks to produce a native image. This is convenient for standard Maven pipelines.

Distinguish the two scenarios:

- `pack build --path target/app.jar` **converts an already-built JAR directly** into an image.
- `spring-boot:build-image` is a goal integrated with the Maven lifecycle/project to build an image from the artifact produced by the plugin.

If the requirement is to archive the JAR as an immutable artifact and convert it in a separate CI/CD job, `pack` with `--path` provides a clearer artifact boundary. If you want one Maven command to orchestrate building and packaging from the project, use `spring-boot:build-image`.

## 5. Branch Two: Converting the JAR into an Executable with GraalVM `native-image`

### 5.1. Why Must the JAR Be Unpacked?

A Spring Boot executable JAR uses a custom nested JAR layout: application classes normally live in `BOOT-INF/classes`, and dependencies in `BOOT-INF/lib`. GraalVM `native-image` requires a classpath consisting of class directories and individual dependency JARs to run reachability analysis.

Therefore, do not assume the command:

~~~bash
native-image -jar target/myproject-0.0.1-SNAPSHOT.jar
~~~

will properly handle a repackaged Spring Boot executable JAR format. Unpack the JAR, build the classpath from `BOOT-INF/classes`, and **list every JAR in `BOOT-INF/lib`**. Native Image does not support classpath wildcards in a way that replaces enumerating dependencies in this scenario.

### 5.2. Environment Requirements

This branch requires:

- A GraalVM distribution with `native-image` compatible with the Java version used to build the application.
- Compiler, linker, SDK, and OS toolchain required by GraalVM.
- JDK/JAR tools to unpack and inspect the artifact.
- A build machine with sufficient RAM/CPU for Native Image compilation.

Check beforehand:

~~~bash
java -version
native-image --version
~~~

Unlike Buildpacks, this branch **uses Native Image installed on the build machine**. The resulting executable is tied to the OS/CPU of the native compilation environment; GraalVM Native Image is not a general-purpose cross-compiler for arbitrarily targeting Linux from macOS or ARM64 from x86_64.

### 5.3. Unpacking the JAR and Building the Classpath

The example below is for Bash on Linux/macOS. Assume the artifact is `target/myproject-0.0.1-SNAPSHOT.jar` and we want to create a binary named `myproject`:

~~~bash
set -euo pipefail

# Create a fresh working directory inside target to avoid mixing with older extractions.
WORK_DIR="$(mktemp -d target/native-work.XXXXXX)"
(
    cd "$WORK_DIR"
    jar -xf ../myproject-0.0.1-SNAPSHOT.jar

    # Native Image requires listing each dependency JAR; do not use BOOT-INF/lib/*
    LIB_CP="$(find BOOT-INF/lib -name '*.jar' -print | paste -sd ':' -)"
    APP_CP=".:BOOT-INF/classes"

    # argfile may not be packaged if no metadata overrides are needed.
    if [ -f META-INF/native-image/argfile ]; then
        native-image -H:Name=myproject @META-INF/native-image/argfile -cp "$APP_CP:$LIB_CP"
    else
        native-image -H:Name=myproject -cp "$APP_CP:$LIB_CP"
    fi

    mv myproject ../myproject-native
)
~~~

Explanation:

1. `jar -xf` unpacks the executable JAR into the working directory.
2. `BOOT-INF/classes` provides application bytecode and resources.
3. `find` lists each dependency JAR; `paste` joins them into a colon-separated classpath on Linux/macOS.
4. If the JAR contains `META-INF/native-image/argfile`, its contents are passed to Native Image as an argument file. This file **does not always exist**; include it only when actually packaged.
5. `-H:Name` names the output executable. The result is moved to `target/myproject-native`.

Do not use a wildcard like `BOOT-INF/lib/*` instead of listing dependencies: Native Image's `-cp` option requires explicitly listed entries. On Windows, adjust the classpath separator, file search command, and Bash syntax; use PowerShell or an appropriate script.

### 5.4. Inspecting and Running the Executable

After the command succeeds:

~~~bash
file target/myproject-native
./target/myproject-native
~~~

`file` helps verify the binary type and generated architecture. Run the executable on a compatible OS/architecture, then test endpoints, resources, serialization, reflection, and proxies in real business flows.

If built on macOS, the output binary is a macOS executable; you cannot copy that Mach-O file directly into a Linux container and run it. To obtain a Linux native binary, build in a Linux environment or a Linux builder matching the deployment architecture.

## 6. Comparing the Two Conversion Approaches

| Criterion | Buildpacks from JAR | Direct GraalVM `native-image` |
| --- | --- | --- |
| Input | AOT executable JAR | Unpacked AOT executable JAR |
| Primary tools | `pack`, Docker daemon, builder/run image | Local GraalVM distribution and `native-image` |
| GraalVM installed on host | Not required | Native Image required |
| Output | OCI container image | Native executable |
| Native toolchain | Inside builder image | On build machine environment |
| Environment control | Via builder, run image, buildpack env | Directly via GraalVM, compiler, and flags |
| Suitability | Container deployment pipelines | Standalone binary needed or fine-grained control over native compilation |
| Output platform | Platform of configured builder/target | OS/CPU of the native compilation environment |

**Both approaches require AOT assets.** Buildpacks does not automatically turn an ordinary JVM JAR into a Spring AOT JAR; Native Image also cannot infer the entire Spring bean graph and missing metadata on its own.

## 7. Handling Reflection, Resources, and Metadata After JAR Conversion

An AOT-processed JAR can carry hints generated by Spring, yet not every dynamic application behavior is automatically detected. Scenarios that commonly need review:

- Reflection instantiating classes/constructors/methods from names read in config.
- Resources looked up by dynamically constructed names or patterns.
- Serialization/deserialization of types not automatically inferred by the framework.
- JDK dynamic proxies or class-based proxies.
- JNI or dependencies performing their own native calls.

You can use `RuntimeHintsRegistrar` and `@ImportRuntimeHints` to declare them precisely:

~~~java
import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportRuntimeHints;

@Configuration(proxyBeanMethods = false)
@ImportRuntimeHints(ReportHints.class)
class ReportConfiguration {
}

class ReportHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("reports/*.txt");
        hints.reflection().registerType(
            CsvReportFormatter.class,
            org.springframework.aot.hint.MemberCategory.INVOKE_DECLARED_CONSTRUCTORS
        );
    }
}
~~~

This example registers resource and constructor reflection for a specific implementation. Replace class/pattern names with actual requirements; do not register the entire classpath or every member of every type unnecessarily.

When metadata is missing, failures may only appear when running the native executable, even though the AOT JAR runs fine on the JVM. You can run the GraalVM tracing agent on the JVM to observe dynamic access paths, then review and place the needed hints in application source/resources before the next build.

## 8. Testing Across Artifact Layers

Test in order so you know where errors originate:

| Layer | How to Check | What Is Confirmed |
| --- | --- | --- |
| JAR exists | `ls target/*.jar` or list directory | Build produced the artifact |
| AOT assets | `jar tf app.jar`, search generated classes and native metadata | JAR contains required AOT outputs |
| JVM AOT mode | `java -Dspring.aot.enabled=true -jar app.jar` | Generated initialization code runs on JVM |
| Buildpacks | `pack build ... BP_NATIVE_IMAGE=true` | Builder produces a native container image |
| Native Image | Run `native-image` and check exit code | Compiler produces an executable |
| Native runtime | Run binary or container, invoke endpoints and business flows | Binary operates correctly in target environment |

A minimal test suite should cover:

1. Health endpoint and a primary business endpoint.
2. JSON binding/serialization with real DTOs.
3. Reading templates/resources from the classpath.
4. Flows involving reflection, proxies, or critical integrated libraries.
5. Database/broker or external service connections if used by the application.
6. Build-time selected profiles/configs and runtime configuration values.

JVM AOT mode provides fast validation of Spring AOT outputs but does not replace native tests. Native compilation can consume significant time and RAM, so run broad JVM test suites first and focus native tests on areas prone to divergence.

## 9. Common Errors and Diagnostic Directions

| Symptom | Possible Cause | How to Check |
| --- | --- | --- |
| Buildpacks fails to detect application | JAR is not executable format or buildpack does not recognize artifact | Confirm Boot executable JAR, builder, and `--path` |
| Buildpacks produces JVM image instead of native | Missing `BP_NATIVE_IMAGE=true` or builder lacks config support | Inspect buildpack env and detect/build logs |
| Builder native build fails due to Java version | JDK in JAR does not meet current builder/native-image requirements | Check Spring Boot/builder JDK requirements; for Boot 4.2, verify JDK 25 requirement |
| Native Image reports missing class | Unpacked classpath missing dependency or class not retained | Inspect `BOOT-INF/classes`, `BOOT-INF/lib` list, and reachability |
| Native Image reports argfile not found | JAR does not contain `META-INF/native-image/argfile` | Pass argfile only when the file actually exists |
| JAR runs in JVM AOT but native hits reflection error | Missing reflection hints for dynamic access path | Add runtime hints or metadata for exact members |
| Native fails to read template | Resource not packaged into image | Check input resources and resource hints |
| Binary runs on build host but fails in container | Wrong OS/CPU or missing system libraries | Use artifact built for Linux and matching architecture |
| Native build runs out of RAM or takes too long | Native compilation is resource-intensive | Increase host/builder CPU/RAM, prune unused dependencies, monitor compiler logs |

## 10. CI/CD Pipeline: Keeping the JAR as an Intermediate Artifact

A practical pipeline can be split into two jobs:

~~~mermaid
flowchart LR
    C["CI: compile + test"] --> A["AOT + package"]
    A --> J["Archive AOT JAR"]
    J --> R["CD: fetch exact archived JAR"]
    R --> B["Buildpacks or native-image"]
    B --> T["Native smoke / integration tests"]
    T --> P["Publish container image or executable"]
~~~

**JAR creation job:**

~~~bash
./mvnw test
./mvnw -Pnative package
jar tf target/myproject-0.0.1-SNAPSHOT.jar
~~~

Archive the exact verified JAR in the artifact repository / CI artifact storage along with checksum, application version, and commit metadata.

**Conversion job with Buildpacks:**

~~~bash
pack build --builder paketobuildpacks/ubuntu-resolute-builder --run-image paketobuildpacks/ubuntu-resolute-run-tiny --path target/myproject-0.0.1-SNAPSHOT.jar --env 'BP_NATIVE_IMAGE=true' registry.example.com/myproject:0.0.1
~~~

**Or conversion job with GraalVM Native Image:** download the exact JAR, unpack it, assemble the classpath, and invoke `native-image` as shown in Section 5. Choose a build environment matching the OS/CPU you intend to release.

Benefits of this split:

- The AOT JAR can be verified and archived before the native step begins.
- If native compilation fails due to resource exhaustion, there is no need to re-run compile/test/AOT when inputs are unchanged.
- The same AOT JAR can be used to produce artifacts for different architectures using corresponding builders/runners, though each native compilation still must run on a matching target platform because Native Image does not cross-compile arbitrarily.
- Easy traceability of input JAR checksum, builder version, GraalVM version, and output image.

## 11. Evaluating Post-Build Products

Do not just check that the build succeeded. Measure and record:

| Metric | How to Measure / Record |
| --- | --- |
| AOT JAR build time | Duration from compile to package |
| Native compilation time | Separate duration of Buildpacks or Native Image |
| JAR size | Size of intermediate artifact |
| Native executable size | Binary file size if using `native-image` directly |
| Container image size | Size of OCI image created by Buildpacks |
| Startup-to-ready time | Measure from process start until health endpoint is ready |
| RSS / memory | Measure under identical container limits and load |
| Latency / throughput | Use identical data, requests, and scenarios |
| Compatibility results | Record pass/fail for reflection, resources, proxies, serialization, and integrations |

Fair comparisons require keeping workload, configuration, CPU/RAM, and runtime environment identical. Do not infer memory usage solely from binary or container image size. Native usually starts faster and can use less memory in many workloads, but sustained load performance, throughput, and latency still must be measured.

## 12. Pre-Release Checklist

- [ ] JAR is a Spring Boot executable JAR and has run Spring AOT.
- [ ] Required generated classes, resources, and JSON hints are inside the JAR.
- [ ] Spring profiles/conditions were chosen correctly at build time.
- [ ] JAR runs with `-Dspring.aot.enabled=true` on the JVM.
- [ ] Chosen Buildpacks vs. GraalVM Native Image according to the release artifact format.
- [ ] JDK, GraalVM, builder, OS, and CPU architecture versions are compatible.
- [ ] Tested endpoints, resources, reflection, serialization, proxies, and critical business flows in native.
- [ ] Recorded checksum/version of input JAR and output native artifact/container image.
- [ ] Measured startup, RSS, latency/throughput, and build time in an equivalent environment.

**Core point:** an AOT-processed JAR is an intermediate artifact carrying the code and metadata Spring prepared. Buildpacks uses that JAR to create a native container image; GraalVM `native-image` uses a classpath built from the JAR to create an executable directly. Choosing the right branch, verifying AOT assets, and testing on the target platform are the three conditions for repeatable conversion in CI/CD.
