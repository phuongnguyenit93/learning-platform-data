# Running the Application on the JVM with Generated AOT Output

## 1. Why Run AOT on the JVM?

In the **SPRING_BOOT_NATIVE_IMAGE** module, a Spring Boot application is processed by Spring AOT and then compiled into a GraalVM Native Image. Before testing the native executable, there is a very useful intermediate step: **running the application itself on the JVM while using the code and resources generated by Spring AOT**.

Running this way helps verify:

- the AOT-generated ApplicationContext initialization code can be loaded and executed;
- bean definitions, injection, proxies, and configurations are prepared properly;
- required runtime hints and AOT resources are present in the artifact;
- the application works with the expected runtime configuration after applying AOT;
- differences between standard Spring startup and AOT startup can be detected before the native compilation step.

This is a separate testing step in the pipeline. It still runs on the JVM, so it does not prove that all reflection, JNI, resources, or native libraries are compatible with GraalVM. Nevertheless, it helps isolate AOT errors earlier and reduces how often you have to wait for a long native build to discover configuration errors.

## 2. What Does Spring AOT Generate?

During AOT processing, Spring analyzes the application's ApplicationContext at build time. From the bean structure and determinable configurations, Spring generates initialization code and metadata so the runtime can create the context more efficiently.

The outputs typically include:

- generated Java code to register bean definitions and initialize the context;
- bytecode compiled from the AOT code;
- resources/metadata describing initializers, reflection, proxies, resources, and required dynamic accesses;
- configurations supporting Native Image reachability analysis.

Directory names and how plugins store outputs depend on the Spring Boot, Spring Framework, Maven/Gradle, and Native Build Tools versions. You should not write application code that depends on internal generated file names unless a public API requires it.

General flow:

~~~mermaid
flowchart TB
    S["Source + dependencies + build environment"] --> A["Spring AOT processing"]
    A --> G["Generated sources, bytecode and resources"]
    G --> C["Compile and package AOT output"]
    C --> J["Run on JVM with spring.aot.enabled=true"]
    C --> N["GraalVM Native Image compilation"]
    J --> V["Verify AOT context on JVM"]
    N --> X["Run native executable"]
~~~

## 3. Enabling AOT When Running on the JVM

Spring Boot provides the property:

~~~properties
spring.aot.enabled=true
~~~

When this property is enabled, Spring uses the ApplicationContext initializer generated during AOT to initialize the context. If the property is not enabled, the application usually follows the standard Spring startup path on the JVM.

With an executable JAR that already contains the AOT output, run:

~~~bash
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

Place the system property before `-jar` so it is present as soon as SpringApplication starts bootstrapping. You can use the corresponding environment variable:

~~~bash
SPRING_AOT_ENABLED=true java -jar target/billing-service.jar
~~~

On Windows PowerShell:

~~~powershell
$env:SPRING_AOT_ENABLED = "true"
java -jar target\billing-service.jar
~~~

If running via an IDE, set the VM option `-Dspring.aot.enabled=true` on the appropriate Run Configuration. Do not just add the property after the ApplicationContext has already started initializing.

**This property only selects the generated AOT initialization path.** It does not run AOT processing itself, does not generate classes automatically, and does not add them to the classpath. The build must complete AOT processing, compilation, and packaging before running.

## 4. Preparing the AOT Artifact on Gradle

The Spring Boot Gradle plugin provides an AOT task, typically named `processAot`. Native Build Tools and the Spring Boot plugin configuration wire that output to the required compile/package steps.

Check available tasks:

~~~bash
./gradlew tasks --all
~~~

Run AOT processing:

~~~bash
./gradlew processAot
~~~

Then compile/package according to the task graph provided by the project's plugin. Some configurations have tasks such as `compileAotJava` and `processAotResources`; check them in the task list and confirm that the output is included in the runtime classpath or executable JAR:

~~~bash
./gradlew compileAotJava processAotResources bootJar
~~~

If your project's plugin version already wires these tasks into `bootJar`, simply run the packaging task per that configuration. Avoid calling non-existent tasks or manually adding generated output twice.

Run the JAR with AOT:

~~~bash
java -Dspring.aot.enabled=true -jar build/libs/billing-service.jar
~~~

### 4.1. Using bootRun

You can configure `bootRun` to enable the property:

~~~kotlin
tasks.named<org.springframework.boot.gradle.tasks.run.BootRun>("bootRun") {
    systemProperty("spring.aot.enabled", "true")
}
~~~

However, `bootRun` must also have both the AOT generated classes and resources on the runtime classpath. Setting only the system property without putting AOT output on the classpath will not produce a valid AOT run. If you are unsure of the plugin's task wiring, run the packaged executable JAR and verify that the AOT output is inside the artifact.

## 5. Preparing the AOT Artifact on Maven

The Spring Boot Maven plugin provides the `process-aot` goal. The project needs to configure this goal in the lifecycle/profile used to generate AOT assets and ensure the output is compiled/packaged with the application.

Example execution declaration in `spring-boot-maven-plugin` if the POM does not yet have a corresponding execution:

~~~xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <executions>
        <execution>
            <id>process-aot</id>
            <goals>
                <goal>process-aot</goal>
            </goals>
        </execution>
    </executions>
</plugin>
~~~

If the project's parent/profile already declares the `process-aot` execution, do not add a second one. Check the effective POM and lifecycle binding of the plugin version in use.

Run the AOT goal according to the project configuration:

~~~bash
./mvnw spring-boot:process-aot
~~~

Then run the compile/package lifecycle so the AOT output is included in the artifact according to the plugin configuration:

~~~bash
./mvnw package
~~~

Run the executable JAR:

~~~bash
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

Profile names, execution IDs, and output locations may vary across projects. If the project uses a `native` profile, only activate that profile when it is actually defined in the POM. Do not assume that `mvn test` runs AOT processing by default.

## 6. Verifying AOT Output Is in the Runtime Artifact

Before running, check that the artifact actually contains the generated output. The `processAot` task completing successfully is not enough if the generated output has not been compiled or packaged.

For a JAR:

~~~bash
jar tf target/billing-service.jar
~~~

With Gradle, substitute the JAR path in `build/libs`. Verify:

- generated AOT classes have been compiled and are present in the artifact;
- required metadata/initializers are packaged;
- resources needed by AOT or the application still exist;
- there are no two conflicting copies of generated output caused by duplicate packaging.

You should not depend on a specific generated class name in application tests. Internal class names can change across Spring versions. Verify by starting the application with `spring.aot.enabled=true` and checking its behavior.

If the artifact is missing the AOT initializer, check the task graph/lifecycle, generated source sets, compile output, and packaging configuration. Do not work around it by disabling `spring.aot.enabled`; doing so simply switches the application back to the standard initialization path and no longer tests the AOT output.

## 7. Build-Time Conditions and Runtime Configuration

This is the most important difference when running an AOT application on the JVM.

Spring AOT processes the ApplicationContext at build time. Conditions that determine bean structure may be evaluated at that time, for example:

- `@ConditionalOnClass`;
- `@ConditionalOnProperty`;
- `@Profile`;
- other auto-configuration conditions;
- bean definitions registered dynamically during context refresh.

If a condition is evaluated during AOT processing, the resulting bean structure has already been baked into the generated output. Changing a property at runtime does not automatically make Spring re-run the entire analysis and bean graph generation process.

Conversely, configuration values bound into beans when the application starts can still come from runtime property sources, such as endpoints, timeouts, buckets, regions, or connection details. You need to distinguish **bean values** from **conditions that decide whether a bean exists**.

| Change | Can be changed when running AOT on JVM? | Explanation |
| --- | --- | --- |
| `app.storage.endpoint` bound into an existing bean | Yes | Binder reads property sources at runtime |
| Timeout or bucket name of an already registered bean | Yes | These are runtime configuration values |
| Enabling `@ConditionalOnProperty` to create an extra bean excluded during AOT | Not automatically | Structural conditions were already processed during AOT |
| Adding a classpath dependency after AOT | No | Generated context does not re-analyze the classpath |
| Changing profiles that alter bean definitions | Unsafe if different from AOT profile | Profile conditions already participated in structural decisions |
| Changing a secret read from a runtime secret store | Yes | As long as the secret is not used as a build-time condition |

Therefore, the build environment must accurately represent the expected application structure at runtime. If staging and production need different bean graphs due to profiles/conditions, you need to generate separate AOT outputs for each variant or design features so that differences only lie in runtime values.

## 8. Example: Running the Same AOT Artifact with Two Runtime Configurations

Suppose the service has `StorageProperties`:

~~~java
@ConfigurationProperties(prefix = "app.storage")
public record StorageProperties(
    URI endpoint,
    String bucket,
    Duration connectTimeout
) {
}
~~~

The bean is registered via `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`. The default file may contain development values:

~~~yaml
app:
  storage:
    endpoint: https://storage-dev.example.internal
    bucket: invoices-dev
    connect-timeout: 3s
~~~

After AOT processing and packaging, run the same JAR with the staging configuration:

~~~bash
APP_STORAGE_ENDPOINT=https://storage-staging.example.internal \
APP_STORAGE_BUCKET=invoices-staging \
APP_STORAGE_CONNECTTIMEOUT=5s \
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

And run the same JAR with the production configuration:

~~~bash
APP_STORAGE_ENDPOINT=https://storage.example.internal \
APP_STORAGE_BUCKET=invoices \
APP_STORAGE_CONNECTTIMEOUT=8s \
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

The two runs can use different values because the properties bean is still bound at runtime. This does not mean you can change the classpath or enable a bean that was excluded during AOT processing.

Do not put passwords/tokens into configuration files used for AOT processing. Secrets must be supplied via a secret manager, environment, or config tree when the application runs.

## 9. Testing AOT on the JVM

The goal is to confirm application behavior after using the generated initializer. You can run the same smoke/integration test suite in two modes:

1. Standard JVM: without `spring.aot.enabled` enabled.
2. AOT JVM: with `spring.aot.enabled=true` and using the artifact containing generated output.

Example testing an endpoint:

~~~bash
java -jar target/billing-service.jar
~~~

In another terminal:

~~~bash
curl -i http://localhost:8080/actuator/health
~~~

Stop the process and run AOT:

~~~bash
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

Call the endpoint and necessary business APIs again. The health endpoint only proves the application started; it does not test binding paths, serializers, resources, providers, or unused lazy beans. Call at least one representative request for each critical integration.

### 9.1. Comparing Results

| Item | Standard JVM | JVM with AOT |
| --- | --- | --- |
| Context initialization | Analyzes configuration and creates beans via standard runtime path | Uses generated initializer and AOT assets |
| Runtime | JVM | JVM |
| Reflection/reachability | JVM reflection model | Still JVM, but uses the generated AOT structure |
| Bean conditions | Evaluated during context initialization | Structural conditions already evaluated during AOT |
| Native executable constraints | No | No |
| Testing objective | Application baseline | Correctness of generated AOT output |

Do not conclude that AOT JVM is faster from just a single run. If benchmarking is needed, measure multiple times under identical conditions, separate build time from startup, control for JVM warm-up, and record heap/RSS. The primary goal of this step is to verify the correctness of the AOT output.

## 10. Testing Sensitive Components

### 10.1. Bean Registration and Dependency Injection

Verify that critical beans exist and dependencies are injected properly. Pay special attention to:

- beans registered via `@Bean` methods;
- beans from auto-configuration;
- conditionally created beans;
- custom factory beans and bean definition registrars;
- beans registered using `BeanDefinitionRegistryPostProcessor`.

Extensions that register beans dynamically at runtime may be incompatible with the AOT model if they need to modify the bean graph after AOT processing time. In such cases, review the design or add AOT mechanisms supported by Spring.

### 10.2. Configuration Properties

Verify that properties beans are registered, bind to the right types, and validation still works. Try overriding a value with an environment variable to confirm that the Binder picks up runtime configuration.

If values are wrong, distinguish binding errors from condition errors that were already processed at build time. A property may bind properly while a bean depending on `@ConditionalOnProperty` still does not appear because the condition was false during AOT.

### 10.3. Reflection, Proxies, and Resources

Exercise the flows that actually use:

- Jackson or frameworks introspecting DTOs;
- JDK/CGLIB proxies;
- resources looked up by dynamic names;
- service providers via `ServiceLoader`;
- third-party libraries using reflection.

AOT JVM can catch bean registration or generated initializer errors, but the JVM still has full reflection and classloaders. A passing test here does not prove that Native Image has retained every constructor, method, resource, or JNI entry point.

### 10.4. Profiles and Conditional Configuration

Record the profiles and properties used during AOT processing. When running, use the same structural conditions that were selected. If you need to test another profile, create an AOT processing run with that profile and use a separate output.

Do not use the same generated output directory for multiple different AOT configurations if they can overwrite each other. Each variant needs an identifiable and reproducible build output.

## 11. Common Issues

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `spring.aot.enabled=true` but AOT initializer not found | AOT processing has not run or output was not packaged | Check `processAot`/`process-aot`, compilation, and packaging |
| Standard run works but AOT run lacks beans | Bean conditions were evaluated with a different build environment | Compare profiles/properties/classpath between AOT and runtime |
| Changing environment variable does not make bean appear | Environment variable was used in a build-time condition | Separate bean structure from runtime values or build AOT separately |
| `bootRun` cannot find generated initializer | Runtime classpath does not contain AOT output | Check task wiring; try the packaged executable JAR |
| AOT generated sources fail to compile | Dynamic configuration code or extension incompatible with AOT | Inspect generated source errors and the extension's AOT support |
| AOT JVM tests pass but native fails with reflection error | JVM still allows dynamic reflection | Add properly scoped reachability metadata and run native tests |
| Resource exists on JVM but is missing in native | Insufficient resource hints or native packaging | Check resource inputs, runtime hints, and native executable |
| Staging profile works but production is missing beans | AOT output was generated from a different profile | Generate AOT output for the corresponding profile structure |
| Startup time does not decrease | Application is dominated by I/O, network, or other runtime tasks | Measure startup separately and find actual costs before optimizing |

When investigating, record the build command, Spring Boot/Framework versions, JDK and Native Build Tools versions, profiles/properties used in AOT, along with stack traces with secrets redacted.

## 12. Practical Workflow from Source to AOT JVM

Suppose the billing service needs to verify its generated AOT context before building a native image.

**Step 1 — check build configuration**

- Confirm the Spring Boot Maven/Gradle plugin is compatible with the project version.
- Confirm the AOT task/goal is configured.
- Identify profiles, classpath, and properties affecting bean conditions.

**Step 2 — run standard JVM tests**

~~~bash
./mvnw test
# Or:
./gradlew test
~~~

This serves as the baseline to compare with the AOT runtime.

**Step 3 — generate AOT output**

Gradle:

~~~bash
./gradlew processAot
~~~

Maven:

~~~bash
./mvnw spring-boot:process-aot
~~~

**Step 4 — compile and package AOT output**

Use the task/lifecycle configured by your project's plugin version. Confirm that generated sources have been compiled and resources/metadata are included in the artifact.

**Step 5 — run JVM with AOT**

~~~bash
java -Dspring.aot.enabled=true -jar target/billing-service.jar
~~~

Substitute the actual JAR path if using Gradle. Call the health endpoint and APIs representative of binding, JSON, resources, proxies, and third-party libraries.

**Step 6 — run tests with different runtime configurations**

Override endpoints, buckets, timeouts, or properties that do not alter the bean graph. Confirm the Binder picks up the new values. Keep profiles and structural conditions matching the AOT processing run.

**Step 7 — move to native build**

Once AOT JVM passes, build the native executable with Maven/Gradle per the module configuration. Continue running native contract tests; AOT JVM does not replace that step.

## 13. Checklist Before Moving to Native Image

- [ ] AOT processing ran successfully.
- [ ] Generated sources/bytecode/resources were compiled and packaged.
- [ ] The artifact contains the required AOT initializers/metadata.
- [ ] Ran with `spring.aot.enabled=true` on the JVM.
- [ ] Bean registration and dependency injection work.
- [ ] Runtime profiles/classpath/conditions match the AOT processing run.
- [ ] Configuration properties still bind runtime values properly.
- [ ] Called business APIs, not just the health endpoint.
- [ ] Critical reflection, proxies, resources, and ServiceLoader were verified on AOT JVM.
- [ ] Secrets were not put into the build environment or generated output.
- [ ] Recorded commands, plugin versions, and AOT configuration for reproducibility.
- [ ] Clearly distinguished AOT JVM errors from errors that only appear in Native Image.

**Remember:** to run an application on the JVM using AOT output, you must first generate, compile, and package the AOT output; then enable `spring.aot.enabled=true` before SpringApplication bootstraps. Standard configuration values can still be bound at runtime, while conditions that determine the bean graph were already processed at build time. Once the AOT JVM step works, continue testing the native executable to verify reachability, resources, JNI, and closed-world constraints.
