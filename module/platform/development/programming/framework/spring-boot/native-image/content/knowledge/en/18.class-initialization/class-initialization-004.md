# --initialize-at-build-time and the Scope of Affected Classes

## 1. Why Do We Need to Control Class Initialization Timing?

In the **SPRING_BOOT_NATIVE_IMAGE** module, we use **Spring AOT** to prepare a Spring Boot application for **GraalVM Native Image**, and then verify compatibility, startup time, memory usage, container packaging, and executable operation. A decision that directly affects both the build and runtime phases is **when class initializers run**: while GraalVM is creating the executable, or when the native process starts running.

Java initializes a class when it is first used according to JVM rules. Initialization includes static field initializers and static initializer blocks (the class initialization method generated by the compiler). Loading or reading metadata of a class does not necessarily mean the class has been initialized.

Native Image can execute class initializers during executable creation. When it does, the computed static values are stored in the **image heap** and become the initial state of the native program. The **--initialize-at-build-time** option allows requesting this policy for specific classes or packages.

After this lesson, learners will be able to:

1. Distinguish class loading, class initialization, build-time initialization, and runtime initialization.
2. Explain which classes/packages **--initialize-at-build-time** affects.
3. Understand how inheritance relationships cause related superclasses or subclasses to be affected as well.
4. Identify static initializers that depend on the environment, time, randomness, files, network, or threads.
5. Configure narrowly scoped class initialization via GraalVM Native Build Tools with Maven/Gradle.
6. Use traces/reports to determine which classes are initialized at build time and why.
7. Test JVM and native behavior after changing policies.

> **Principle:** only move a class to build-time initialization when its static initialization is safe, deterministic, and independent of the runtime environment. This option can reduce startup work, but it can also freeze data or side effects into the executable.

## 2. When Does Class Initialization Occur in Java?

A class typically goes through these phases:

- **Loading:** the JVM locates the bytecode and creates the object representing the class.
- **Linking:** verification, preparation, and resolution as needed.
- **Initialization:** running static field initializers and static initializer blocks exactly once according to class initialization semantics.

Example:

~~~java
public final class CurrencyTable {
    static final Map<String, String> SYMBOLS;

    static {
        Map<String, String> values = new HashMap<>();
        values.put("USD", "$");
        values.put("EUR", "€");
        SYMBOLS = Map.copyOf(values);
    }

    private CurrencyTable() {}
}
~~~

When the class is initialized, the static block runs and creates the map. If the class is initialized in a standard JVM, that work happens during application runtime. If Native Image is configured to initialize this class at build time, the static block runs in the JVM performing the native build; the static state is then placed into the image heap.

### 2.1. Class loading is not class initialization

Some operations only load a class without initializing it yet:

~~~java
Class<?> type = Class.forName(
    "com.example.CurrencyTable",
    false,
    Thread.currentThread().getContextClassLoader()
);
~~~

The second parameter is `false`, so this call does not request initializing the class. Passing `true` causes the JVM to initialize the class when needed under `Class.forName` rules.

Operations such as instantiating an object, calling a static method, or reading/writing a non-compile-time-constant static field can trigger initialization. `static final` variables of primitive/`String` types with compile-time constant values can be inlined by the compiler; reading them does not necessarily trigger class initialization.

Therefore, when investigating an initializer, distinguish:

- Is the class present on the classpath or loaded?
- Was the static initializer actually executed?
- Was it executed in the build JVM or the runtime native process?

### 2.2. What gets stored in the image heap?

For a build-time-initialized class, the static values after the initializer completes can be stored in the executable. For example, the immutable map in `CurrencyTable` was built during the build; when the native executable runs, the program uses the stored state instead of re-running that static block.

This does not mean arbitrary Java state can be stored. Objects reachable from static fields must be compatible with the image heap. Native Image may reject the build if the state contains objects or resources that cannot be transferred into the image. A class required to initialize at runtime must also not have any pre-existing instances in the image heap.

## 3. Native Image's Default Policy

Do not assume every application class is initialized at build time or every class is initialized at runtime.

According to current GraalVM documentation:

- Application classes default to runtime initialization, **except for classes that Native Image proves are safe to initialize at build time**.
- Native Image analyzes static initializers and related calls to identify safe classes.
- Many core JDK classes are handled by Native Image with their own build-time policy.
- Developers can override the default policy for classes/packages using explicit options.

A class is generally considered safe if its relevant supertypes are also safe and its initializer does not call unsafe methods or trigger unsafe classes. This analysis has limits; for example, native code calls or virtual method invocations whose targets are hard to resolve may prevent an initializer from being proven safe.

**Spring AOT does not mean every class in a Spring Boot application is initialized at build time.** Spring AOT generates bootstrap code and metadata for Native Image to analyze; class initialization still follows Native Image's policy and class-init configurations provided by dependencies.

## 4. The --initialize-at-build-time Option

Common syntax:

~~~bash
native-image \
  --initialize-at-build-time=com.example.catalog.ImmutableCatalog \
  -jar application.jar
~~~

The option takes a comma-separated list of fully qualified class names or packages. Example:

~~~bash
# Specify a single class
--initialize-at-build-time=com.example.catalog.ImmutableCatalog

# Specify a package
--initialize-at-build-time=com.example.catalog

# Specify multiple classes/packages
--initialize-at-build-time=com.example.catalog.ImmutableCatalog,com.example.format.FixedTables
~~~

These examples show the shape of the Native Image CLI configuration. When using Spring Boot, pass build arguments through Maven/Gradle Native Build Tools or the appropriate Buildpacks mechanism rather than manually replacing the entire command managed by the plugin.

### 4.1. Single-class scope

Use the fully qualified name for a narrow effect:

~~~bash
--initialize-at-build-time=com.example.catalog.ImmutableCatalog
~~~

This is the easiest choice to review when only one class has an immutable static lookup table to precompute. Do not add an entire package if only one initializer has been proven safe.

### 4.2. Package scope

You can specify a package:

~~~bash
--initialize-at-build-time=com.example.catalog
~~~

Every class within the package scope recognized by Native Image will be subject to this policy, along with related type relationships. A broad package can pull in classes whose static initializers depend on the environment, logging, files, networking, or runtime state.

A Java package name is a configuration scope; do not infer that a parent package automatically includes all subpackages like a filesystem glob. If you want to include subpackages, verify the rules of your GraalVM version and check the class initialization report to see the exact set of affected classes.

### 4.3. Without a class/package list

Using the option without a list has a very broad scope and may request initializing all classes in the scope supported by the version/toolchain. This is unsuitable as a default for production Spring Boot applications. Always check `native-image --help` for your GraalVM version and select specific classes/packages.

### 4.4. Relationship with superclasses and superinterfaces

Java class initialization has hierarchy rules. When a class is initialized, relevant superclasses must be initialized first; superinterfaces with default methods may also belong to the set of relevant supertypes.

Therefore, when specifying a class for build time, Native Image may need to include its relevant supertypes/superclasses in build-time initialization to preserve semantics. Current build-time option behavior covers the specified classes/packages and their relevant superclasses.

Do not treat the flag as an isolated change on a single class in a vacuum. Check the hierarchy if the class inherits from a base class with a runtime-dependent static initializer.

## 5. Comparing with --initialize-at-run-time

The counterpart option:

~~~bash
--initialize-at-run-time=com.example.config.RuntimeSettings
~~~

It instructs Native Image to defer initialization of the class/package until the executable runs. This is the right choice when static state must reflect the process environment, such as environment variables, runtime configuration, or state created at application startup.

Example:

~~~java
public final class RuntimeSettings {
    static final String REGION = System.getenv("APP_REGION");
    static final Instant PROCESS_STARTED_AT = Instant.now();

    private RuntimeSettings() {}
}
~~~

If this class is initialized at build time, `APP_REGION` and the current time may be read from the **build environment**, and the values stored in the image heap. When the container runs in another environment, static fields are not automatically recalculated. If the class is initialized at runtime, the values are read from the native process's environment.

### 5.1. Scope of runtime initialization

**--initialize-at-run-time** also accepts classes or packages. Runtime policy can pull in related subclasses to preserve semantics. This is especially important when a base class is initialized at runtime while a subclass would otherwise enter the image heap from build time.

Avoid configuring the same class or hierarchy with two conflicting policies. If GraalVM reports a conflict, check which classes were specified directly, which were pulled in through inheritance, and what metadata dependencies/plugins provided.

### 5.2. Comparison table

| Criterion | Build-time initialization | Runtime initialization |
| --- | --- | --- |
| When class initializer runs | In the JVM performing the native build. | When the native executable runs and the class is first used. |
| Static state | Can be stored in the image heap. | Created in the runtime process. |
| Environment dependency | Risks freezing values from the build host. | Reads values from the running environment. |
| Startup work | May be reduced since initializer already ran. | Initializer still needs to run when the class is used. |
| Image size | May increase if many objects/caches are stored. | Does not store that initializer's state in the image heap. |
| Suitable for | Immutable, deterministic, safe data. | Time, randomness, environment, file/network, process state. |

## 6. Scope of Affected Classes in a Hierarchy

Class initialization policy is constrained by inheritance relationships:

- A class initialized at build time requires its relevant supertypes to be initialized at build time.
- A class initialized at runtime requires its relevant subtypes to be initialized at runtime.
- Superinterfaces with default methods may be included among relevant supertypes to consider.
- A class initialized at runtime must not have any instances present in the image heap.

Example:

~~~java
class BaseCatalog {
    static final Map<String, String> LABELS = Map.of("A", "Active");
}

class RegionalCatalog extends BaseCatalog {
    static final String REGION = "north";
}
~~~

If `RegionalCatalog` is requested to initialize at build time, its superclass `BaseCatalog` must also be initialized according to hierarchy rules. Conversely, if `BaseCatalog` is requested at runtime, related subclasses cannot arbitrarily be build-time initialized.

Check related classes in the logs rather than checking only the class name written in the build argument.

## 7. When Should Build-Time Initialization Be Used?

### 7.1. Typically suitable candidates

A class may be a candidate if its initializer:

- Computes solely from constants or fixed data shipped with the source/artifact.
- Builds immutable lookup tables, frozen maps/lists, or deterministic normalized data.
- Does not read environment variables, deployment-varying system properties, or the current time.
- Does not create threads, executors, sockets, connection pools, or file handles.
- Does not open network/database connections or depend on build-host secrets.
- Does not initialize frameworks/services with a process-bound lifecycle.

Deterministic lookup table example:

~~~java
final class ImmutableCatalog {
    static final Map<String, String> LABELS = Map.of(
        "PENDING", "Pending",
        "PAID", "Paid",
        "CANCELLED", "Cancelled"
    );

    private ImmutableCatalog() {}
}
~~~

If this class truly only builds immutable data, has no environment dependencies, and its object graph is compatible with the image heap, you can try specifying this individual class. Then measure build time, image size, startup, and memory to verify the benefit.

### 7.2. Classes that usually require caution

Do not automatically place the following groups into build time:

| Group | Risk |
| --- | --- |
| Reading `System.getenv()` or `System.getProperty()` | Values may come from the build host instead of the runtime container. |
| `Instant.now()`, `LocalDateTime.now()`, default timezone/locale | Build timestamp or build environment gets frozen. |
| `Random`, `SecureRandom`, seeds, or key material | Random/security state may be pre-generated and unintentionally reused. |
| Loggers, logging backends, and logging configuration | May initialize sinks, paths, or state tied to the process/build environment. |
| JDBC drivers, connection pools, database clients | May retain connection state or configuration unsuitable for runtime. |
| File watchers, threads, executors, sockets | Lifecycles and OS resources unsuitable for freezing in the image heap. |
| Native library wrappers | May invoke native code or depend on the build machine's libraries/OS. |
| Classes reading secrets or environment-specific certificates | Risks embedding sensitive data into the executable. |

These are groups requiring investigation, not absolute bans for every class in the same package. Read static initializers and indirect calls before deciding.

### 7.3. Sensitive data risk

If a static initializer reads tokens, passwords, private keys, or configuration content from the build host, the data may be stored in the image heap and become part of the executable. Images may be distributed across multiple environments; therefore, never use build-time initialization to load production secrets or pipeline secrets.

## 8. Example Illustrating the Difference

Suppose we have two classes:

~~~java
final class StaticCatalog {
    static final Map<String, String> VALUES = Map.of(
        "A", "Alpha",
        "B", "Beta"
    );
}

final class RuntimeRegion {
    static final String REGION = System.getenv("APP_REGION");
}
~~~

The first class only builds a map from fixed data; the second reads an environment variable. You can try configuring:

~~~bash
native-image \
  --initialize-at-build-time=com.example.StaticCatalog \
  --initialize-at-run-time=com.example.RuntimeRegion \
  -jar application.jar
~~~

Expected policy outcomes:

- `StaticCatalog` is initialized during the build; the map is already in the image heap.
- `RuntimeRegion` is initialized in the native process; the `APP_REGION` value comes from the container/host environment at runtime.

This is a policy example, not a guarantee that both classes will build verbatim if placed in another project. Replace package/class names with real code, check the hierarchy, and verify GraalVM logs.

## 9. Configuring with GraalVM Native Build Tools

In a Spring Boot project, prefer configuring via the active native plugin so other settings provided by Spring Boot/AOT are preserved.

### 9.1. Gradle Kotlin DSL

In `build.gradle.kts`:

~~~kotlin
graalvmNative {
    binaries {
        named("main") {
            buildArgs.add(
                "--initialize-at-build-time=com.example.catalog.ImmutableCatalog"
            )
            buildArgs.add(
                "--initialize-at-run-time=com.example.config.RuntimeSettings"
            )
        }
    }
}
~~~

This snippet assumes the `org.graalvm.buildtools.native` plugin is already applied and the `main` binary exists. Keep the project's existing build arguments; only add classes that have been evaluated.

### 9.2. Gradle Groovy DSL

In `build.gradle`:

~~~groovy
graalvmNative {
    binaries {
        main {
            buildArgs.add(
                '--initialize-at-build-time=com.example.catalog.ImmutableCatalog'
            )
            buildArgs.add(
                '--initialize-at-run-time=com.example.config.RuntimeSettings'
            )
        }
    }
}
~~~

Extension syntax may vary by Native Build Tools version. Read the DSL reference for your exact version if the project uses another binary configuration or has multiple executables.

### 9.3. Maven

In the `native-maven-plugin` configuration:

~~~xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
    <configuration>
        <buildArgs>
            <buildArg>--initialize-at-build-time=com.example.catalog.ImmutableCatalog</buildArg>
            <buildArg>--initialize-at-run-time=com.example.config.RuntimeSettings</buildArg>
        </buildArgs>
    </configuration>
</plugin>
~~~

This is the plugin configuration section inside a POM that already declares the appropriate version and profile. Do not replace the entire existing plugin configuration with the illustrative snippet; merge both `<buildArg>` entries into the existing `<buildArgs>`.

### 9.4. native-image.properties

An artifact can provide Native Image options via a `native-image.properties` file in the appropriate metadata directory on the classpath:

~~~properties
Args = --initialize-at-build-time=com.example.catalog.ImmutableCatalog
~~~

This works well when a library needs to distribute configuration tied to its own artifact. Consider the impact on all consuming applications; do not package broad or environment-dependent policies into shared dependencies.

With Spring Boot, AOT can generate metadata under `META-INF/native-image/{groupId}/{artifactId}/`. If adding files manually, choose a separate subdirectory per the Spring Boot guide for your version to avoid colliding with auto-generated files. For the application itself, configuring `buildArgs` on the native plugin is usually more visible and easier to review.

## 10. Diagnosing Class Initialization

When a build reports that a class was initialized at the wrong time or contains an object that cannot be stored in the image heap, you need to know **which class** was initialized and **why**.

### 10.1. Tracing a specific class

Use Native Image's trace option:

~~~bash
native-image \
  --trace-class-initialization=com.example.config.RuntimeSettings \
  -jar application.jar
~~~

Tracing helps identify where the initializer ran and what path led to initialization. Exact option names/details may change across GraalVM releases; check `native-image --help-extra` or the documentation for your version.

### 10.2. Printing the class initialization report

Some GraalVM versions provide an expert option:

~~~bash
native-image -H:+PrintClassInitialization -jar application.jar
~~~

The report helps you inspect which classes are initialized at build time/runtime and why Native Image classified them that way. This is a version-dependent option; if unrecognized, check `native-image --expert-options-all` and use the corresponding class initialization trace option.

### 10.3. Reading common errors

| Message / symptom | Possible meaning | How to handle |
| --- | --- | --- |
| Class meant for runtime was initialized at build time | Class was triggered indirectly by another initializer or forced by build-time policy. | Use trace to find the caller; adjust policy for the triggering class or dependency. |
| Object of a runtime-init class appears in the image heap | A static field of a build-time class holds a reference to an object that should be created at runtime. | Separate static state, defer object creation, or fix hierarchy policy. |
| Initializer reads different values between build and runtime | Environment/system property/time was read in the build JVM. | Move the class to runtime or pass the value into constructor/configuration at app startup. |
| Build fails due to side effects or native calls | Initializer executes an operation incompatible with build-time execution. | Defer initialization; do not force build time just to silence warnings. |
| Image grows larger after enabling build-time for a package | Many static objects/caches were stored into the image heap. | Narrow scope to needed classes, re-measure image size and memory. |
| Incorrect runtime behavior after successful build | Build-host state was frozen or initialization order changed. | Compare JVM/native, inspect static fields and environment in both phases. |

### 10.4. Isolation workflow

~~~mermaid
flowchart TD
    A[Native build reports class initialization issue] --> B[Read class and timing in message]
    B --> C[Trace class initialization]
    C --> D[Find static initializer and called dependencies]
    D --> E{Runtime dependency or side effect?}
    E -->|Yes| F[Keep class at runtime initialization]
    E -->|No| G[Check image heap and hierarchy]
    G --> H[Test narrow scope on a single class]
    F --> I[Rebuild and run smoke tests]
    H --> I
    I --> J[Compare startup, image size, and behavior]
~~~

Do not add a broad **--initialize-at-build-time** just to make the build pass. If a class requires runtime state, keep it at runtime and fix where the state is created instead of freezing it.

## 11. Hands-on Exercise: Choosing the Right Class Initialization Scope

**Context:** a Spring Boot service has an immutable order-status lookup table, alongside a class that reads region from an environment variable and a class that records a timestamp when the process starts. The team wants to reduce startup time while preserving correct behavior when the same native image is deployed across multiple environments.

### Tasks

1. Create `ImmutableCatalog` with a static lookup table built solely from fixed data.
2. Create `RuntimeSettings` reading `APP_REGION` and `ProcessClock` recording when the process starts.
3. Inspect the static initializers and classify which classes can initialize at build time and which must initialize at runtime.
4. Build native with `--initialize-at-build-time` only for `ImmutableCatalog`, and `--initialize-at-run-time` for the environment/time-dependent classes.
5. Enable tracing for `RuntimeSettings` to confirm the initializer does not run on the build host.
6. Run the same executable twice with different `APP_REGION` values; verify each process picks up the correct runtime value.
7. Compare with JVM execution and record startup, image size, RSS, and build duration.
8. Expand the experiment with package scope, then inspect the report to list all affected classes.
9. Test an inherited class to observe superclass/subclass constraints.
10. Save the final configuration, trace logs, and test results.

### Results log

| Evidence | Details to record |
| --- | --- |
| Build-time designated classes | Full name, safety rationale, static state after initialization. |
| Runtime designated classes | Full name, environment/time source, and deferral rationale. |
| Effective scope | Direct class list, related superclasses/subclasses. |
| Trace/report | GraalVM version, command, output, and initialization reason. |
| Maven/Gradle config | Configuration file, plugin version, and build arguments. |
| JVM/native behavior | Static values, profile, and environment on each run. |
| Performance | Build duration, startup-to-ready, image size, RSS, and measurement conditions. |

### Completion criteria

- [ ] Can distinguish class loading from class initialization.
- [ ] Can explain that static state of build-time initialized classes is stored in the image heap.
- [ ] Can designate a single class using `--initialize-at-build-time`.
- [ ] Can explain the impact on related superclasses and subclasses.
- [ ] Does not freeze environment variables, timestamps, secrets, or process resources into the image.
- [ ] Maven/Gradle passes build arguments accurately to Native Image.
- [ ] Trace/report proves classes initialize at the expected timing.
- [ ] JVM and native exhibit identical behavior for the running environment.
- [ ] Has measurements to evaluate the trade-offs of the choice.

## 12. Self-Assessment Questions

1. How does class loading differ from class initialization?
2. Why can static fields of a build-time initialized class appear in the image heap?
3. Which superclasses of `Foo` can `--initialize-at-build-time=com.example.Foo` affect?
4. Which subclasses can `--initialize-at-run-time=com.example.Base` affect?
5. Why can reading `System.getenv()` in a static initializer cause bugs when a native image is deployed across multiple environments?
6. Why does package scope carry higher risk than specifying a single class?
7. When should logging, database clients, or random generators be left to initialize at runtime?
8. What is `--trace-class-initialization` used to determine?
9. Why does a successful build not prove that the class initialization policy is correct?
10. How do you evaluate the trade-off between startup time, build time, and image size?

Specify concrete classes proven to be safe, understand hierarchy implications, keep environment-dependent data at runtime, and verify with traces and tests on the real executable.
