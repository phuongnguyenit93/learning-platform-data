# Distinguishing Bean Analysis Errors from Native-Compilation-Only Errors

When moving a Spring Boot application to GraalVM Native Image, a single build command may run through several stages: Java compilation, analyzing the ApplicationContext with Spring AOT, generating and compiling AOT code, analyzing/compiling with Native Image, and finally producing an executable. A failure that appears during a native build command does not necessarily belong to the same stage.

Classifying the error accurately saves time: **bean analysis errors** usually happen when Spring prepares the BeanFactory at build time; **native compilation errors** happen after Spring AOT has produced inputs for GraalVM; **native runtime errors** only appear when running the executable. These three groups have different causes and different fixes.

This lesson presents the pipeline by boundary, log signals, how to isolate stages with Maven/Gradle, how to test AOT-generated code on the JVM, and how to collect diagnostics when the Native Image compiler fails.

## 1. Look at the Full Pipeline Before Reading Errors

A native Spring Boot application typically goes through the following steps:

~~~mermaid
flowchart TD
    A["Source Java + dependencies"] --> B["Compile Java"]
    B --> C["Spring AOT: initialize context and prepare BeanFactory"]
    C --> D["Generate AOT sources and runtime hints"]
    D --> E["Compile generated sources"]
    E --> F["GraalVM Native Image analysis and compilation"]
    F --> G["Link native executable"]
    G --> H["Run native executable"]
    C --> X["Bean/configuration analysis error"]
    D --> Y["AOT contribution or code generation error"]
    E --> Z["Generated source compilation error"]
    F --> N["Native Image analysis/compilation error"]
    H --> R["Native runtime error"]
~~~

Errors can be grouped by boundary:

| Stage | Work Performed | Example Errors |
| --- | --- | --- |
| Java compile | Standard source compilation and annotation processing | Java syntax, type mismatch, unresolved dependency |
| Spring AOT bean analysis | Create context, process configuration, and prepare BeanFactory | Missing bean, multiple candidate beans, invalid condition/property, post-processor failure |
| AOT contribution/code generation | Framework and libraries contribute code/hints | AOT processor throws exception, runtime hints registrar fails, invalid generated source |
| Generated source compile | Compile Java sources generated by AOT | Invalid import/type/method in generated source, incompatible API |
| Native Image build | Reachability analysis, class initialization, native compilation, and linking | Unsupported feature, analysis failure, build-time initializer error, C compiler/linker error |
| Native runtime | Run executable and execute business flows | Missing metadata only exposed by dynamic access, missing resource, runtime configuration error |

**Core distinction:** Spring AOT must prepare a valid BeanFactory to generate code; GraalVM must analyze and compile the prepared code. If Spring has not yet built a valid bean model, tuning GraalVM compiler options usually does not address the root cause.

## 2. Where Do Bean Analysis Errors Occur?

Spring AOT analyzes the application in a JVM process at build time. Spring Boot initializes the ApplicationContext using AOT-oriented configuration, processes bean definitions and necessary post-processors, and prepares the model to generate initialization code.

You should not assume every business bean is fully initialized like a production run. However, the steps that prepare the BeanFactory and process configuration can trigger certain infrastructure components, factory methods, or processors. Failures in those steps can cause AOT to stop before the Native Image compiler is even invoked.

### Common Causes

**Missing bean or unresolvable dependency**

~~~java
@Service
public class InvoiceService {

    public InvoiceService(PaymentGateway paymentGateway) {
        // ...
    }
}
~~~

If no bean provides `PaymentGateway`, the context may report `NoSuchBeanDefinitionException` or an `UnsatisfiedDependencyException` wrapping the root error.

**Multiple matching candidate beans**

~~~java
public interface PaymentGateway {
}

@Component
class CardPaymentGateway implements PaymentGateway {
}

@Component
class BankPaymentGateway implements PaymentGateway {
}
~~~

If a service injects `PaymentGateway` without `@Primary`, `@Qualifier`, or an explicit selection rule, Spring may report `NoUniqueBeanDefinitionException`.

**Conditions evaluated at build time**

~~~java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(
        prefix = "billing.audit",
        name = "enabled",
        havingValue = "true"
)
class AuditConfiguration {

    @Bean
    AuditService auditService() {
        return new AuditService();
    }
}
~~~

Spring AOT evaluates conditions while processing the context. If the property is absent in the AOT environment, the `AuditService` bean may be omitted from the generated model. Later, if runtime code expects that bean to always exist, the application may fail when running AOT/native.

Bean conditions are not always errors. The issue is that **the configuration used for AOT analysis must represent the bean graph the binary needs to support**.

**Faulty BeanFactoryPostProcessor or BeanDefinitionRegistryPostProcessor**

Processors can add, modify, or remove bean definitions. If logic depends on a database, HTTP, container-only environment variables, or runtime-only data, AOT processing may fail to reproduce the expected bean structure.

**Invalid configuration properties**

Conversion, validation, or constructor binding errors can prevent the context from initializing. For example, a `Duration` receiving a malformed value or a required property being omitted.

**Static initializers or factory methods with side effects**

A configuration that calls external systems during AOT analysis may fail because the build environment lacks the database, secrets, or network available in production. Check the stack trace to determine whether that code ran during context creation or inside the Native Image compiler.

## 3. Signs of Spring AOT Bean Analysis Errors

Logs may contain classes/exceptions from Spring Framework and Spring Boot, for example:

- `BeanCreationException`
- `UnsatisfiedDependencyException`
- `NoSuchBeanDefinitionException`
- `NoUniqueBeanDefinitionException`
- `BeanDefinitionStoreException`
- `ConfigurationPropertiesBindException`
- `BindException`
- `IllegalStateException` thrown by configuration classes or post-processors

Exception names are only initial clues. Always read the **root cause** and the first stack frame belonging to application code.

Abbreviated log example:

~~~text
Error processing application context
org.springframework.beans.factory.UnsatisfiedDependencyException:
  Error creating bean with name 'invoiceService'
Caused by: org.springframework.beans.factory.NoSuchBeanDefinitionException:
  No qualifying bean of type 'PaymentGateway' available
~~~

This is a BeanFactory analysis error. GraalVM does not need to be involved yet to resolve the missing `PaymentGateway`.

Another sign is that the log stops at the `processAot` task or the Maven goal `spring-boot:process-aot`. If this task fails before invoking `native-image`, there is no evidence that the native compiler is the cause.

### Condition Evaluation Report

When suspecting auto-configuration or `@Conditional...`, enable debug mode for the AOT process to inspect the condition evaluation report:

With Maven, configure application arguments for the AOT goal in the Spring Boot Maven Plugin, then re-run the goal. Example plugin configuration snippet:

~~~xml
<configuration>
    <arguments>
        <argument>--debug</argument>
    </arguments>
</configuration>
~~~

You can use `systemPropertyVariables` or `profiles` on the goal to set values needed for AOT. With Gradle, add an application argument or system property to the `processAot` task.

Look for `Positive matches`, `Negative matches`, and the reason conditions did not match. Do not rush to add beans manually before knowing which property, classpath entry, or profile disabled auto-configuration.

## 4. Why Can Build-Time Configuration Differ from Runtime?

Spring AOT creates a bean model prepared at build time. Conditions such as `@Profile`, `@ConditionalOnProperty`, `@ConditionalOnClass`, and certain auto-configuration conditions are evaluated in that environment.

Therefore, the following values can directly affect the set of generated beans:

- Active profiles.
- Environment variables.
- System properties.
- Application arguments.
- Property sources loaded during AOT.
- Build classpath and dependencies.

For example, if AOT builds with `billing.audit.enabled=false`, while production runs with `billing.audit.enabled=true`, you should not expect the binary to spontaneously create a bean that AOT excluded from the model.

### Configuring the AOT Process

With Maven, the `spring-boot:process-aot` goal can be configured to accept environment variables, system properties, and application arguments. Illustrative example in plugin configuration:

~~~xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <profiles>
            <profile>native</profile>
        </profiles>
        <arguments>
            <argument>--debug</argument>
        </arguments>
        <systemPropertyVariables>
            <billing.audit.enabled>true</billing.audit.enabled>
        </systemPropertyVariables>
    </configuration>
</plugin>
~~~

In this configuration, `profiles` are the Spring profiles applied when AOT processes the context; `arguments` are application arguments; `systemPropertyVariables` pass JVM system properties to the AOT process. If the project uses `spring-boot-starter-parent`, a Maven profile named `native` may automatically bind `process-aot` to the lifecycle; do not confuse that Maven profile with the Spring profile passed to the application. Verify the exact execution and log of the AOT process.

With Gradle, `processAot` is a `JavaExec` task, so you can configure the task's environment, system properties, and arguments. Groovy DSL example:

~~~groovy
tasks.named("processAot") {
    systemProperty("billing.audit.enabled", "true")
    environment("SPRING_PROFILES_ACTIVE", "native")
}
~~~

There is no need to declare the same profile through multiple mechanisms simultaneously if they can conflict. Pick one consistent configuration source and confirm it in the AOT log.

### Runtime Configuration Can Still Change Values, Not Arbitrarily Change the Bean Graph

Values such as endpoints, timeouts, credentials, or feature parameters can still be read at runtime if they do not determine the packaged bean structure. Distinguish:

- **Configuration values of an existing bean:** can come from runtime property sources.
- **Decision of whether a bean exists:** already evaluated when AOT created the context model.

This is why you should use constructor injection/`@ConfigurationProperties` for runtime values and limit bean-creating conditions to choices explicitly decided at build time.

## 5. AOT Contribution and Generated Source Errors Differ from Bean Analysis Errors

Even once the BeanFactory is prepared, Spring AOT still has to generate code and collect runtime hints.

Frameworks or libraries can contribute AOT information through SPIs such as:

- `BeanFactoryInitializationAotProcessor`
- `BeanRegistrationAotProcessor`
- `RuntimeHintsRegistrar`
- `RuntimeHints`

If a custom processor or registrar throws an exception, the failure may occur after most bean analysis is complete but before the native compiler starts.

Example of a faulty registrar:

~~~java
public final class FeatureHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        // Example error: custom code throws an exception when reading a build config file.
        throw new IllegalStateException("Cannot load feature metadata");
    }
}
~~~

If the stack trace stops in `registerHints`, inspect the registrar code, the files it reads, the classloader, and build-time data. Do not try to fix that error by adding `--initialize-at-run-time` for an unrelated class.

### Generated Source Compile Failure

Spring AOT can generate Java sources to register beans and initialize the context. If the generated sources fail to compile, the error belongs to the generated-source compilation step.

Common signs:

- `Compilation failure` or `cannot find symbol`.
- Package/class does not exist on the compile classpath.
- Generated method calls an API missing in the current dependency version.
- An AOT contribution generates code incompatible with the Spring Framework version in use.

Open the generated source file indicated in the compiler output. Check the called API, dependency versions, and custom AOT contributions. **Do not edit generated sources directly** because the next build will overwrite them; fix the processor, configuration, or dependency that produced that code.

## 6. Signs of Native Image Compilation Errors

Only after Spring AOT completes and generated code compiles does GraalVM Native Image perform native analysis and compilation.

Logs typically show the compiler starting stages such as:

- Initializing Native Image build.
- Performing analysis.
- Reachability/points-to analysis.
- Compiling methods.
- Creating image.
- Linking or creating the executable.

Exact stage names vary by GraalVM version and build mode.

Common errors at this stage:

| Error Group | Example Signals | Meaning |
| --- | --- | --- |
| Unsupported feature | `UnsupportedFeatureError` or a message that an API is unsupported | Reachable code uses a feature Native Image does not support in that way |
| Analysis/reachability | Analysis error, unresolved type or method | Static analysis cannot finish determining the code to include in the image |
| Class initialization | Initializer error in hosted/build-time context | Static initializer performs an operation unsuitable at build time |
| Metadata/build configuration | Warnings or errors about reflection/resource/JNI/proxy/serialization registration | Metadata or configuration for dynamic access is improper; depending on the case, the error may only surface at runtime |
| Native toolchain | Compiler, linker, header, or system library not found | Native build environment is missing tools/libraries or target is incompatible |
| Resource/build capacity | Out of RAM, disk, or build time exceeded | Insufficient build environment resources |

For instance, a linker error such as a missing system library is unrelated to whether Spring registered `PaymentGateway`. Conversely, a bean analysis error cannot be fixed by installing a C compiler.

### Not Every Missing Piece of Metadata Causes a Build Failure

Some dynamic accesses may neither be discovered by static analysis nor executed during the build. The native executable can still be built successfully and only fail later when hitting the corresponding reflection, resource, serialization, or proxy branch.

Therefore, distinguish:

- **Build-time metadata/analysis error:** the compiler reports it cannot analyze or process a configuration.
- **Runtime missing metadata:** the executable is created, but a dynamic access fails when running.

Do not conclude that successful native compilation means every reflection/resource entry has been completely declared.

## 7. Using an AOT-Processed JVM to Isolate Errors

Spring Boot lets you run the application on the JVM while using the initialization code generated by Spring AOT, via the system property:

~~~bash
java -Dspring.aot.enabled=true -jar target/myapplication.jar
~~~

The prerequisite is that the JAR already contains the AOT-generated code. With Maven, this usually requires building with the `native` profile; with Gradle, it requires the corresponding AOT plugin configuration.

This test is useful because it separates two questions:

1. Can Spring AOT generate context initialization code and does that code run on the JVM?
2. Can GraalVM compile that code into a native executable?

### How to Interpret Results

| Result | Preliminary Conclusion | Next Step |
| --- | --- | --- |
| `processAot` fails | Spring AOT/BeanFactory analysis or AOT contribution error | Read root cause and fix configuration/processor |
| `processAot` succeeds, generated source compile fails | Generated code compilation error or dependency/API mismatch | Open source and compiler diagnostics |
| AOT JAR fails on JVM with `spring.aot.enabled=true` | Problem with generated initialization code or AOT configuration | Check stack trace during AOT context startup |
| AOT JAR runs on JVM, native compile fails | GraalVM analysis/compiler/toolchain error or Native Image difference | Enable diagnostics and analyze native build log |
| Native compile succeeds, executable fails at runtime | Native runtime, metadata, or runtime difference error | Reproduce on the binary, inspect exception and missing metadata |

This is a very effective isolation technique: **an AOT-processed JVM run succeeding does not guarantee native will succeed, but it rules out a class of errors at the generated Spring context layer**.

## 8. Step-by-Step Isolation Workflow with Maven and Gradle

Do not start with one long build command and only stare at the `BUILD FAILURE` line. Run step by step to find the very first stage that fails.

### Maven

For a project configured with the Spring Boot Maven plugin and Native Build Tools:

~~~bash
# 1. Compile Java sources.
./mvnw clean compile

# 2. Run Spring AOT application processing.
./mvnw -Pnative spring-boot:process-aot

# 3. Package JAR with AOT-generated code.
./mvnw -Pnative package -DskipTests

# 4. Run JAR on JVM using AOT-generated initialization.
java -Dspring.aot.enabled=true -jar target/myapplication.jar

# 5. Run native compilation.
./mvnw -Pnative native:compile -DskipTests
~~~

Goals and profiles depend on the project's plugin configuration. If `spring-boot:process-aot` cannot be resolved, check the Spring Boot Maven plugin version and declared executions; if `native:compile` does not exist, check `native-maven-plugin` and the corresponding profile.

### Gradle

With the Spring Boot Gradle plugin and GraalVM Native Build Tools:

~~~bash
# 1. Compile Java sources.
./gradlew clean compileJava

# 2. Run Spring AOT processing.
./gradlew processAot

# 3. Run JVM tests.
./gradlew test

# 4. Build JAR containing AOT output.
./gradlew bootJar

# 5. Run JAR on JVM with AOT-generated code.
java -Dspring.aot.enabled=true -jar build/libs/myapplication.jar

# 6. Build native executable.
./gradlew nativeCompile
~~~

If the build needs AOT test processing, inspect the `processTestAot` task. The Native Build Tools plugin can configure `nativeTest` to use outputs from application/test AOT processing when the project meets support requirements.

### Stop at the First Failing Step

Example:

- `compileJava` succeeds.
- `processAot` fails with `NoSuchBeanDefinitionException`.

Conclusion: the error is in bean analysis; there is no need to keep trying different GraalVM compiler flags until the AOT context is valid.

Conversely:

- `processAot` succeeds.
- Generated sources compile successfully.
- `nativeCompile` fails at `Performing analysis` with `UnsupportedFeatureError`.

Conclusion: focus on the class/feature GraalVM reported rather than going back to change the bean graph without supporting evidence.

## 9. Checking AOT Tests and Native Tests

Spring Boot can also process test application contexts with AOT. With JUnit 5 and the Spring TestContext Framework, eligible tests can be processed via `processTestAot`; Native Build Tools can provide the `nativeTest` task.

Distinguish three kinds of tests:

| Test Type | What Does It Test? | Limitations |
| --- | --- | --- |
| Unit/integration tests on JVM | Business logic, dependency injection, and most context behavior | Does not prove Native Image metadata is complete |
| AOT-processed tests on JVM | Test context using build-time generated initializer code | Does not run inside a native executable |
| Native tests / native integration tests | Behavior on the native executable or native test binary | Slower build; should focus on native differences |

The recommendation is to keep running most unit/integration tests on the JVM for fast feedback. Reserve native tests for areas prone to divergence:

- Reflection and dynamic access.
- Serialization and JSON binding.
- Resources, resource bundles, and files read from the classpath.
- Dynamic proxies, class generation, or JNI.
- Class initialization and static state.
- Bean conditions locked in at AOT build time.

An AOT test can fail because the test context has a different bean graph than the application context. Identify whether the failing task is running `processAot` or `processTestAot` before concluding the bug is in the production application.

## 10. Collecting Diagnostics When the Native Image Compiler Fails

If both AOT processing and generated source compilation succeed yet the native build still fails, enable diagnostics for GraalVM.

Native Image supports `--diagnostics-mode` to emit additional details about activities such as class initialization and substitutions. Depending on the version, more granular options can be added.

Example running the compiler directly with an illustrative option:

~~~bash
native-image --diagnostics-mode -jar target/myapplication.jar
~~~

With Maven/Gradle Native Build Tools, pass the option via the plugin's `buildArgs` configuration:

~~~groovy
graalvmNative {
    binaries {
        named("main") {
            buildArgs.add("--diagnostics-mode")
        }
    }
}
~~~

Binary names and DSL depend on the plugin version. With Maven, add the build argument to the `native-maven-plugin` used by the project.

When reading diagnostics:

1. Find the very first stage reporting an error, not just the final summary line.
2. Read the exception and every `Caused by`.
3. Note the class, method, or feature indicated by the compiler.
4. For class initialization errors, check static initializers and build-time/runtime policies.
5. For unsupported feature errors, identify the causing API/library and check its compatibility guide.
6. For linker errors, check OS, architecture, compiler, linker, and native system libraries.
7. Record the exact JDK/GraalVM version, Spring Boot version, plugin version, and build command.

Do not turn on batches of optimization flags or force build-time class initialization blindly to try your luck. Every change must tie to a specific error and be verified with the native executable.

## 11. Quick Diagnostic Table by Error Message

| Message or Signal | Likely Stage | Question to Answer First |
| --- | --- | --- |
| `No qualifying bean of type ...` | Spring AOT bean analysis | Is the bean registered, do conditions match, and is the profile right? |
| `NoUniqueBeanDefinitionException` | Spring AOT bean analysis | Are there multiple implementations missing `@Primary`/`@Qualifier`? |
| `ConfigurationPropertiesBindException` | Context/configuration binding | Do AOT property sources have valid values and formats? |
| Exception in `BeanFactoryPostProcessor` | BeanFactory preparation | Does the processor depend on external systems or runtime assumptions? |
| Exception in `RuntimeHintsRegistrar` | AOT contribution | Does the registrar read valid classes/resources and run safely at build time? |
| `cannot find symbol` in generated source | Generated source compilation | Are API/dependency versions or AOT contributions compatible? |
| `UnsupportedFeatureError` | Native Image analysis/build | Does a library use an API unsupported in native? |
| Error initializing class during image build | Native Image class initialization | Does a static initializer read environment, open files/network, or start threads? |
| C compiler/linker error | Native linking | Are the target toolchain and system libraries available? |
| `MissingReflectionRegistrationError` or similar reflection error at runtime | Native runtime | Are hints registered for the exact type/members? |
| Resource not found only in native | Native runtime/resource metadata | Are resource patterns or resource bundles included in the image? |
| Native executable starts but beans are missing | Native runtime/AOT configuration mismatch | Did build-time conditions/profiles differ from runtime configuration? |

Exact exception names and formatting depend on Spring/GraalVM versions. Use this table to narrow down the scope, then confirm via task logs and root causes.

## 12. Hands-On Exercise: Classifying Three Errors in One Application

Create a Spring Boot application with the `billing` prefix, a `PaymentService`, a `PaymentGateway`, and an optional audit configuration.

**Scenario A — bean analysis error**

Remove the bean providing `PaymentGateway`, then run:

~~~bash
./mvnw -Pnative spring-boot:process-aot
~~~

Observe the `NoSuchBeanDefinitionException` or corresponding dependency error. Restore the bean and re-run. Note that the Native Image compiler is not the component to investigate for this failure.

**Scenario B — condition locked incorrectly at build time**

Add the configuration:

~~~java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(
        prefix = "billing.audit",
        name = "enabled",
        havingValue = "true"
)
class AuditConfiguration {

    @Bean
    AuditService auditService() {
        return new AuditService();
    }
}
~~~

Run AOT with `billing.audit.enabled=false`, then run the AOT-processed JAR with a runtime value of `true`. Observe the mismatch between the generated bean graph and runtime expectations. Fix the AOT environment configuration so the required bean is included in the model.

**Scenario C — native-specific error**

Create a code branch that uses reflection to look up a class by name only available at runtime, then test it on native. If the native build or runtime reports missing metadata, pinpoint whether the error occurred during compiler analysis or when the executable invoked reflection. Add the appropriate hints, rebuild, and run the same scenario.

### Execute and Record Results

1. Run compile and `processAot` separately.
2. Run the JAR with `-Dspring.aot.enabled=true`.
3. Run native compilation.
4. Record the first failing task, root exception, involved class/method, and build phase.
5. Fix each scenario individually and re-run the exact failed step.
6. Finally, run native integration tests for the payment and audit flows.

### Self-Check Questions

1. Why is `NoSuchBeanDefinitionException` in `processAot` not a GraalVM compiler error?
2. When does Spring AOT evaluate `@ConditionalOnProperty`?
3. Why can the environment used for AOT processing alter the bean graph?
4. How does a generated source compile error differ from a Native Image analysis error?
5. Why does a successful native compilation not prove all dynamic accesses have metadata?
6. Which errors does an AOT-processed JVM with `spring.aot.enabled=true` help isolate?
7. When should you inspect `processTestAot` instead of `processAot`?
8. At which stage is `--diagnostics-mode` useful?
9. Is a linker error directly related to the Spring BeanFactory?
10. Why is final testing on the native executable necessary?

**Passing criteria:** classify Java compile, Spring AOT bean analysis, AOT contribution/generated source, Native Image compilation, and native runtime errors; know how to isolate with `processAot`, AOT-processed JVM, and `nativeCompile`; understand that bean conditions are evaluated at build time; read root causes and diagnostics; and choose the right remediation without confusing BeanFactory configuration errors with GraalVM compiler errors.
