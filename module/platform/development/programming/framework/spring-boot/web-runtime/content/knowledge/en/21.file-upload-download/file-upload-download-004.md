# FilePart, Part, and Receiving Multipart in WebFlux

## 1. Objectives and Context

When a user uploads an image with a note, the HTTP request typically carries `Content-Type: multipart/form-data`. The body is split into **parts**: one part contains the file, and another contains text or JSON. In **Spring WebFlux**, the primary abstractions for receiving multipart are `Part`, `FilePart`, `FormFieldPart`, and, when processing each event of the data stream, `PartEvent`.

After this lesson, you will be able to:

- Read a `multipart/form-data` structure, distinguish field names (part names) from filenames, and distinguish multipart from a standard JSON body.
- Use `@RequestPart` to receive a `FilePart` and a `FormFieldPart` in Spring WebFlux.
- Understand `Part.name()`, `Part.headers()`, `Part.content()`, `Part.delete()`, `FilePart.filename()`, and `FilePart.transferTo(...)`.
- Choose `@RequestBody Mono<MultiValueMap<String, Part>>` when you need to inspect a collection of parts, or `@RequestBody Flux<PartEvent>` when you need to stream multipart events.
- Write a Java 17+/Spring Boot 3.x endpoint that saves files under server-generated names without blocking the event loop with `block()` or synchronous file operations on event-loop threads.
- Configure size limits, part count limits, error handling, authentication, and authorization for secure uploads.

**Scope:** Reactive Spring Boot WebFlux, exemplified with Reactor Netty. Do not use Servlet/MVC's `MultipartFile` or `jakarta.servlet.http.Part` in place of WebFlux's multipart interfaces.

## 2. What Is Multipart?

A regular JSON HTTP request has **one body** formatted as `application/json`. Multipart is also **a single HTTP request**, but its body consists of multiple parts. Each part has its own headers and its own body.

Simplified example of a request uploading a file and a note:

~~~http
POST /api/uploads HTTP/1.1
Host: localhost:8080
Content-Type: multipart/form-data; boundary=MyBoundary123

--MyBoundary123
Content-Disposition: form-data; name="note"

WebFlux Lab
--MyBoundary123
Content-Disposition: form-data; name="file"; filename="example.txt"
Content-Type: text/plain

Hello from a file.
--MyBoundary123--
~~~

In a real request, there is a standard CRLF blank line between headers and body, and the closing boundary marks part delimiters. The snippet above is for comprehension, not raw bytes to send manually.

Reading top to bottom:

1. The `Content-Type` of the **entire request** is `multipart/form-data`, carrying a `boundary` parameter.
2. `name="note"` and `name="file"` are **part names**; the server uses these names to match and bind parameters.
3. `filename="example.txt"` is the **filename declared by the client**; it is not a trusted storage path.
4. The file part may declare `Content-Type: text/plain`; this is also **client-supplied** data and must be verified before being trusted.
5. Opening and closing boundaries are generated by the HTTP client/browser. Do not manually set a `Content-Type: multipart/form-data` header without a boundary; let `curl -F` or browser `FormData` configure it properly.

A single request can contain multiple files sharing the **same part name** (`files`) or different names. Therefore, the general multipart collection is a **multi-value map**, not a single-valued `Map<String, Part>`.

Do not confuse:

| Body Format | Meaning |
| --- | --- |
| `application/json` | A single standard JSON document |
| `application/x-www-form-urlencoded` | Text form encoding key–value pairs, not multipart files |
| `multipart/form-data` | Form with multiple parts, typically files and text |
| `multipart/mixed` | Collection of parts under another multipart convention, e.g., file + JSON in APIs |
| `multipart/related` | Parts with content relationships between them |

Spring WebFlux codecs support multiple multipart subtypes; however, an endpoint declaring `consumes = multipart/form-data` will only accept media types matching that condition.

## 3. Part, FilePart, FormFieldPart, and PartEvent

Import the correct WebFlux package:

~~~java
import org.springframework.http.codec.multipart.Part;
import org.springframework.http.codec.multipart.FilePart;
import org.springframework.http.codec.multipart.FormFieldPart;
import org.springframework.http.codec.multipart.PartEvent;
~~~

These interfaces **differ** from `org.springframework.web.multipart.MultipartFile` and `jakarta.servlet.http.Part` in the Servlet stack.

| Type | Description | Key Info / Actions |
| --- | --- | --- |
| `Part` | Common interface for a parsed part | `name()`, `headers()`, `content()`, `delete()` |
| `FilePart extends Part` | Part representing an uploaded file | `filename()`, `transferTo(Path)`, inherits `Part` methods |
| `FormFieldPart extends Part` | Part representing a text form field | `value()` returns the decoded string value |
| `PartEvent` | Event in a multipart stream when reading parts/chunks | `headers()`, `content()`, `isLast()` |
| `FilePartEvent` / `FormPartEvent` | File event / form field event | `filename()` or `value()` respectively |

### 3.1. Part.name() vs. FilePart.filename()

Given:

~~~http
Content-Disposition: form-data; name="file"; filename="invoice.pdf"
~~~

- `part.name()` returns `"file"`: the field name that `@RequestPart("file")` matches.
- `filePart.filename()` returns the client-declared filename, e.g., `"invoice.pdf"`.
- Neither method decides where the file should be stored on the server.

A client can send `filename="../../secret.txt"` or strings with unusual characters. **Never concatenate `file.filename()` into a storage path** and pass it to `transferTo(...)`. Generate a server-managed UUID/ID name, enforce access control, and store the original name only as metadata if needed.

### 3.2. Part.content(): Data as a Publisher

`Part.content()` returns `Flux<DataBuffer>`. A `DataBuffer` represents chunks of bytes; it does not mean the whole file is gathered into a single byte array in RAM. When you subscribe to or compose the pipeline, data is consumed according to publisher rules.

- You can process each buffer, forward it via WebClient, or write it to storage.
- Some buffers (e.g., on Reactor Netty) are pooled and reference-counted; when your code handles buffers directly, it must ensure proper **consume/relay/release**.
- Do not casually call `collectList()`, `DataBufferUtils.join(...)`, or turn an entire large file into `byte[]`: that can pile all data into memory.
- Do not manually subscribe inside a controller and return a success response immediately. **Return the Mono/Flux** representing the work so Spring tracks completion or failure.

### 3.3. FilePart.transferTo(...)

`FilePart.transferTo(Path destination)` returns `Mono<Void>`: when the publisher completes, transferring/saving the file to the destination has finished per the API contract. Code should usually chain `then(...)` or `thenReturn(...)` instead of calling `block()`.

This does not claim every filesystem or storage backend is strictly non-blocking: disk I/O may still rely on asynchronous I/O or an appropriate worker pool. At the WebFlux controller layer, compose publishers rather than blocking the event loop.

`Part.delete()` also returns a publisher to delete temporary storage associated with the part when needed. Temporary resource management also depends on the codec and request lifecycle; never treat an uploaded file as safely in durable storage until the write pipeline succeeds.

## 4. How WebFlux Processes Multipart Before Entering the Controller

High-level flow:

~~~text
Client (FormData/curl -F)
    |
    v
HTTP request: Content-Type: multipart/form-data; boundary=...
    |
    v
Reactor Netty + WebFlux HTTP codecs
    |
    +--> reads headers, boundary, and parts
    |      |
    |      +--> form field -> FormFieldPart
    |      '--> file -> FilePart
    |
    v
@RequestPart("file") and @RequestPart("note")
    |
    v
Controller returns Mono/Flux
    |
    +--> validate metadata, pick target path
    +--> file.transferTo(target)
    '--> once write completes: return JSON/status
~~~

The actual processing layers involve decoders/readers, argument resolvers, Reactor publishers, and storage. Do not read the diagram as “the entire file must always be loaded into RAM before the controller.” When the multipart parser uses a memory/temp-file strategy, large files can spool to disk. Conversely, **map-based multipart** may require the framework to parse the whole parts structure before returning the map; that differs from `PartEvent` streaming.

Three common entry points:

1. `@RequestPart("file") FilePart file`: extracts a single part named `file`, ideal for standard upload forms.
2. `@RequestBody Mono<MultiValueMap<String, Part>> parts` or `ServerWebExchange.getMultipartData()`: when you need to inspect all parts by name, including repeated names.
3. `@RequestBody Flux<PartEvent> events`: when you want to process **sequentially by event** and control streaming for large payloads or forwarding.

Three properties governing the WebFlux multipart parser:

The values 10MB/8 parts are only lab settings. In production, also account for total request size, gateway/proxy limits, disk capacity, upload rates, and business limits.     }

~~~

**File `src/main/java/com/example/upload/UploadController.java`**

~~~java
package com.example.upload;

import java.nio.file.Files;
import java.nio.file.Path;
import java.util.UUID;

import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.http.codec.multipart.FilePart;
import org.springframework.http.codec.multipart.FormFieldPart;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestPart;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

import reactor.core.publisher.Mono;
import reactor.core.scheduler.Schedulers;

@RestController
@RequestMapping("/api")
public class UploadController {

    // Do not place under the web application's static/public folders.
    private final Path storageRoot = Path.of("uploaded-files")
            .toAbsolutePath()
            .normalize();

    @PostMapping(
            path = "/uploads",
            consumes = MediaType.MULTIPART_FORM_DATA_VALUE,
            produces = MediaType.APPLICATION_JSON_VALUE
    )
    public Mono<ResponseEntity<UploadReceipt>> upload(
            @RequestPart("file") FilePart file,
            @RequestPart("note") FormFieldPart note) {

        String originalName = file.filename();
        String noteValue = note.value();

        if (originalName == null || originalName.isBlank()) {
            return Mono.error(new ResponseStatusException(
                    HttpStatus.BAD_REQUEST, "Invalid filename"));
        }
        if (noteValue.length() > 200) {
            return Mono.error(new ResponseStatusException(
                    HttpStatus.BAD_REQUEST, "Note exceeds 200 characters"));
        }

        // Server-generated ID; NEVER use the client filename as a path.
        String fileId = UUID.randomUUID().toString();
        Path target = storageRoot.resolve(fileId + ".bin");

        // Files.createDirectories is synchronous I/O:
        // offload this operation to boundedElastic.
        Mono<Path> prepareDirectory = Mono.fromCallable(
                () -> Files.createDirectories(storageRoot))
                .subscribeOn(Schedulers.boundedElastic());

        return prepareDirectory
                .then(file.transferTo(target))
                .thenReturn(ResponseEntity.status(HttpStatus.CREATED)
                        .body(new UploadReceipt(
                                fileId, originalName, noteValue)));
    }

    public record UploadReceipt(
            String fileId, String originalFilename, String note) {}
}
~~~

**Why does the code make these choices?**

1. `@RequestPart("file")` matches `name="file"` in the multipart body; `FilePart` exposes the filename and transfers data.
2. `@RequestPart("note") FormFieldPart` binds a text form field; `note.value()` reads the decoded string.
3. `Files.createDirectories(...)` is a synchronous filesystem call, so it is wrapped in `Mono.fromCallable(...)` and scheduled on `Schedulers.boundedElastic()`. That avoids running it directly on the event loop under high load.
4. `file.transferTo(target)` returns `Mono<Void>`. `then(...)` proceeds only after directory preparation finishes; `thenReturn(...)` builds the response only after the transfer completes.
5. `fileId` is server-generated, while `originalFilename` only demonstrates received metadata. In a real system, you should still bound/sanitize any display name and never trust it as a file path.
6. `ResponseEntity.status(HttpStatus.CREATED)` produces status 201 for a successful upload, with Jackson serializing the `record` to JSON.

**Limitations of the example:** this illustrates the protocol, not a production storage service. It lacks authentication, content-signature verification, virus scanning, quotas, retry/idempotency, database metadata persistence, or orphan cleanup if a request cancels after writing. If you need strict overwrite protection across multiple nodes, use a storage backend with atomic creation semantics; UUID here mainly avoids using client names.

### 5.2. Running and Testing with curl

Inside `webflux-upload`, requiring JDK 17+ and Maven, run:

~~~bash
mvn spring-boot:run
~~~

Create a file to upload; for example in Bash:

~~~bash
printf 'Hello WebFlux\n' > sample.txt
~~~

On Windows PowerShell, you can create similar content with `Set-Content -Path sample.txt -Value 'Hello WebFlux'`, or use any existing file on disk.

Send multipart:

~~~bash
curl -i -X POST http://localhost:8080/api/uploads \
  -F "file=@sample.txt;type=text/plain" \
  -F "note=Learning WebFlux"
~~~

The multi-line command above uses Bash line continuation; on Windows PowerShell you can write it on one line:

~~~powershell
curl.exe -i -X POST http://localhost:8080/api/uploads -F "file=@sample.txt;type=text/plain" -F "note=Learning WebFlux"
~~~

When the endpoint and filesystem work, expect:

- Status **201 Created**.
- JSON-compatible response `Content-Type`.
- Body with three fields: `fileId`, `originalFilename`, `note`. `fileId` is a fresh UUID on every call, so there is no fixed stdout string.
- File saved in `uploaded-files` named `<UUID>.bin`. Its bytes match `sample.txt`; the `.bin` extension is an intentional storage convention and does not validate media type.

Example body **structure** (actual UUID varies):

~~~json
{
  "fileId": "9244ab23-1d77-4bfb-b03e-556179eac90f",
  "originalFilename": "sample.txt",
  "note": "Learning WebFlux"
}
~~~

Do not manually type `Content-Type: multipart/form-data` in `curl -F`: curl automatically generates the exact boundary. Manually forcing a header without a boundary causes the parser to reject the multipart body as invalid.

### 5.3. Testing Basic Error Cases

**Missing required `file` part:**

~~~bash
curl -i -F "note=Learning WebFlux" http://localhost:8080/api/uploads
~~~

Normally returns 400 because a required request part is missing; the exact error body varies with Spring Boot configuration.

**Sending JSON to an endpoint that only accepts multipart:**

~~~bash
curl -i -H "Content-Type: application/json" \
  --data '{"note":"Learning WebFlux"}' \
  http://localhost:8080/api/uploads
~~~

Because of `consumes = multipart/form-data`, expect **415 Unsupported Media Type** in this lab configuration.

**File exceeding parser limits:** the server or proxy layer may reject while reading multipart. Exact status codes and error payloads must be verified on your Spring Boot/server/proxy versions and exception handlers; never assume every upload limit always returns one fixed code.

**File write failure:** when the directory lacks write permission or disk is full, the `transferTo` publisher emits an error signal; unless handled explicitly, the server generally returns a server error. Never return `201` before the save operation completes.

## 6. @RequestPart vs. @RequestParam in WebFlux

In Spring MVC Servlet, `@RequestParam` commonly binds both form fields and `MultipartFile`. However, in **WebFlux `@RequestParam` mainly binds query parameters**, because data sources (query/form/multipart) are modeled distinctly. To receive parts cleanly in WebFlux, use `@RequestPart`, or command-object data binding when appropriate.

| Purpose | Typical Signature in WebFlux |
| --- | --- |
| Query parameter `?page=2` | `@RequestParam("page") int page` |
| Single multipart file named `file` | `@RequestPart("file") FilePart file` |
| Single multipart form field named `note` | `@RequestPart("note") FormFieldPart note` |
| A JSON part with `Content-Type: application/json` | `@RequestPart("metadata") MetaData metadata` |
| All parts by name | `@RequestBody Mono<MultiValueMap<String, Part>> body` |
| Stream parts sequentially with buffers | `@RequestBody Flux<PartEvent> events` |

**JSON part:** if a part named `metadata` contains JSON, e.g. `{"title":"guide","public":false}`, and **that part's own header** is `Content-Type: application/json`, WebFlux can deserialize it directly into a Java object using a message reader.

The following signature is **illustrative** and requires a controller, record/POJO, and file-saving logic to run standalone:

~~~java
record MetaData(String title, boolean isPublic) {}

@PostMapping(path = "/with-meta",
             consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public Mono<String> withMeta(
        @RequestPart("metadata") Mono<MetaData> metadata,
        @RequestPart("file") FilePart file) {
    return metadata.map(m -> m.title());
}
~~~

In this short snippet, `file` is only an illustrative parameter and **is not saved**; do not use it verbatim as a production upload endpoint. The key lesson is that `@RequestPart("metadata") Mono<MetaData>` decodes **one part's** JSON via codecs and integrates into the reactive chain. Testing it:

~~~bash
curl -i -F 'metadata={"title":"guide","isPublic":false};type=application/json' \
  -F "file=@sample.txt" http://localhost:8080/api/with-meta
~~~

This uses Bash syntax, assuming you have actually added that handler path to the controller. In PowerShell, double-quoting/escaping JSON differs from Bash; inspect the raw multipart request in an HTTP client if errors occur.

You can add `@Valid` alongside `@RequestPart` for validation; validation errors in WebFlux may surface as `WebExchangeBindException` (status 400) or method validation errors depending on signature. Do not blindly apply MVC's `MethodArgumentNotValidException` handling to all WebFlux cases.

## 7. Handling the Whole Request as MultiValueMap<String, Part>

When you need to receive **multiple parts**, including repeated part names, WebFlux supports:

~~~java
@PostMapping(path = "/inspect",
             consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public Mono<Integer> inspect(
        @RequestBody Mono<MultiValueMap<String, Part>> body) {
    return body.map(parts ->
            parts.values().stream().mapToInt(List::size).sum());
}
~~~

This is an **illustrative method snippet** that needs to sit inside a `@RestController` with `Mono`, `MultiValueMap`, `Part`, `List`, and `MediaType`/`PostMapping`/`RequestBody` imported to compile. The result is the **part count**—for instance, one file and one note return `2`. This snippet **does not save files**, does not read file contents, and applies no business limits; do not use it in place of an upload endpoint that persists data.

Conceptually, the map may contain:

~~~text
"file"   -> [FilePart(filename="a.txt"), FilePart(filename="b.txt")]
"note"   -> [FormFieldPart(value="Two files")]
~~~

This is a conceptual structure, not the standard `toString()` of these classes. Use `parts.get("file")` to retrieve the list of parts sharing a name instead of assuming there is only one file.

When calling `ServerWebExchange.getMultipartData()`, the framework parses the body and **caches the multipart data result for reuse** through the exchange. Afterward, do not try to re-read the raw request body separately from `getRequest().getBody()`: the request body is a single-consumption stream, and the multipart cache is the proper access mechanism.

**Memory note:** `Mono<MultiValueMap<String, Part>>` represents a **collection of identified parts**, which does not imply all file bytes are a single `byte[]` on the heap. The parser can spool large files to temporary files. Still, the overall multipart structure must be parsed/collected, which creates memory/disk pressure; if you need buffer-by-buffer streaming for large payloads, look at `PartEvent`.

## 8. FilePart.content(), DataBuffer, and Releasing Resources

Suppose you want to read file bytes with the lower-level API:

~~~java
Flux<DataBuffer> buffers = file.content();
~~~

This is an **illustrative snippet where `FilePart file` is already present**; not a complete application. One `DataBuffer` is a chunk of data and does not necessarily correspond to a whole file or full part.

**Buffer lifecycles must be handled properly.** With high-level codecs and `FilePart.transferTo(...)`, the framework manages most lifecycle details. When you hold or manipulate `DataBuffer` directly, you must ensure buffers are consumed, forwarded, or released according to the chosen API, including on error and cancellation paths.

Anti-pattern to avoid:

~~~java
// DO NOT DO THIS in a WebFlux request handler:
byte[] allBytes = file.content()
        .map(buffer -> {
            byte[] bytes = new byte[buffer.readableByteCount()];
            buffer.read(bytes);
            return bytes;
        })
        .collectList()
        .block()
        .get(0);
~~~

The snippet above is **deliberately broken** to illustrate four mistakes:

1. `block()` blocks execution and can be rejected on Reactor event-loop threads.
2. `collectList()` buffers data in memory, unsuitable for large files.
3. `get(0)` only grabs the first buffer, **not the whole file**.
4. Failing to release `DataBuffer` instances after manual reads can leak pooled/direct memory.

If you only need to save the file to the filesystem, prefer `transferTo(target)`. If you need the bytes for object storage, virus scanning, hashing, or network forwarding, design an explicit streaming pipeline with byte limits, buffer management, retry/cancellation handling, and a suitable storage API.

**Do not subscribe manually and return success before work finishes:**

~~~java
// DO NOT DO THIS:
file.transferTo(target).subscribe();
return Mono.just("OK");
~~~

The server may return `OK` before writing finishes; errors inside the subscription happen after the response and are hard to trace. Replace it with:

~~~java
// Correct inside a handler that already has file and target:
return file.transferTo(target).thenReturn("OK");
~~~

The correct version completes only after writing succeeds, and write errors propagate through the publisher.

## 9. Streaming Multipart with PartEvent

With `@RequestBody Flux<PartEvent>`, you do not require WebFlux to assemble parts into a `MultiValueMap` before processing begins. Each part emits one or more events:

- `FormPartEvent`: typically one event carrying a text field's value.
- `FilePartEvent`: one or more events carrying file chunks; the first event can be inspected for filename and headers.
- `PartEvent.isLast()` indicates the final event of **the current part**, not necessarily the final event of the entire request.

A conceptual grouping pattern:

~~~java
Flux<Flux<PartEvent>> windows =
        allEvents.windowUntil(PartEvent::isLast);
~~~

Here `allEvents` is the `Flux<PartEvent>` parameter injected into the controller. Each window corresponds to one part's events; to process them sequentially without swallowing the stream, use `concatMap`. You can use `switchOnFirst` to inspect the first event, check whether it is a file or form field, and then process the remaining events in the window.

### 9.1. Standalone Example Consuming Events Without Saving Files

If you only want to count **events** (not files/parts), you can add this method to a WebFlux `@RestController` with `Flux`, `Mono`, `PartEvent`, `DataBufferUtils`, and annotations imported:

~~~java
@PostMapping(path = "/count-events",
             consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public Mono<Long> countEvents(
        @RequestBody Flux<PartEvent> events) {
    return events
            .doOnNext(event ->
                    DataBufferUtils.release(event.content()))
            .count();
}
~~~

This endpoint **intentionally consumes and releases every buffer** without saving the payload; the response is the number of observed events. Large files emit multiple events, so **do not treat that count as the number of files**. In a real app, add a total byte cap to prevent clients from streaming arbitrarily huge payloads. In complex pipelines with cancellation, audit discard and error paths as well so buffers never leak.

### 9.2. When Actually Streaming Files

Typical design-level streaming pipeline:

~~~text
Flux<PartEvent> from request
    |
    v
windowUntil(PartEvent::isLast)
    |
    v
switchOnFirst to check FormPartEvent / FilePartEvent
    |
    +--> FormPartEvent: read value, check limits
    |
    '--> FilePartEvent:
           - read filename (untrusted metadata)
           - read each DataBuffer inside that exact window
           - count bytes, enforce size limit
           - forward/write to storage
           - consume or release every buffer
           - handle errors, cancellation, and partial files
    |
    v
Complete Mono -> response
~~~

This is a design flow, not ready-made production code. When implementing real streaming, maintain byte counters per part and for the total request, process windows sequentially when needed, bound concurrency, keep blocking I/O off the event loop, and delete partial files on failure.

**Important:** Temporary storage properties of the map-based multipart reader, such as `file-storage-directory` and `max-disk-usage-per-part`, do not provide the same protection layer for `PartEvent` streaming. Do not assume enabling parser disk thresholds automatically protects streaming endpoints.

## 10. Reactive Does Not Automatically Mean Non-Blocking I/O

WebFlux aims to process I/O via publishers over a limited set of event-loop threads. Yet your own code can still block:

| Operation | Risk | How to Handle |
| --- | --- | --- |
| `FilePart.transferTo(Path)` | Exposes a reactive publisher contract; do not block controller with `block()` | Return/compose `Mono<Void>` and handle errors |
| `Files.createDirectories`, `Files.exists`, `Files.readAllBytes` | Synchronous filesystem APIs | When needed in-request, wrap in `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` or use async solutions |
| Traditional JDBC | Blocking database I/O | Use R2DBC if appropriate or isolate in a dedicated blocking pool |
| Synchronous object-storage SDK | Ties up threads during network/disk calls | Use an async client if available; otherwise offload and bound concurrency |
| `Mono.block()` in handler | Blocks thread and breaks reactive flow | Compose `flatMap`, `then`, `thenReturn`, `onErrorResume` |
| Arbitrary `subscribe()` inside handler | Fire-and-forget work with untraceable errors/cancellation | Return a publisher representing the full operation |

Key example from `UploadController`:

~~~java
Mono<Path> prepareDirectory = Mono.fromCallable(
        () -> Files.createDirectories(storageRoot))
        .subscribeOn(Schedulers.boundedElastic());

return prepareDirectory
        .then(file.transferTo(target))
        .thenReturn(receipt);
~~~

This is an **illustrative snippet inside a controller where `receipt` already exists**, not a complete method. `subscribeOn(boundedElastic)` moves the blocking directory creation onto an appropriate scheduler; `then(...)` preserves order between preparation and saving. Also cap task concurrency under thousands of simultaneous uploads; offloading does not make disk or network infinitely fast.

## 11. Resource Limits and Protecting Upload Endpoints

Never rely on a single property to declare uploads safe.

### 11.1. Common WebFlux Properties in Spring Boot 3.3

~~~properties
spring.webflux.multipart.max-in-memory-size=256KB
spring.webflux.multipart.max-disk-usage-per-part=10MB
spring.webflux.multipart.max-parts=8
spring.webflux.multipart.max-headers-size=10KB
# Optionally specify a temporary directory:
# spring.webflux.multipart.file-storage-directory=/var/tmp/webflux-multipart
~~~

Meaning:

- `max-in-memory-size` caps memory for **non-file parts** and sets the spool-to-disk threshold for **file parts** in the standard parser.
- `max-disk-usage-per-part` limits temporary disk **per part** in the corresponding reader mode.
- `max-parts` defends against requests with excessive parts.
- `max-headers-size` limits large headers on individual parts.
- `file-storage-directory` is the multipart parser's temporary directory; distinct from the **durable storage** directory chosen by the service.

These limits **do not replace** total HTTP request byte caps at proxies/gateways/servers or per-user business quotas. Defaults vary by version; check the matching docs before production rollout.

### 11.2. Avoid Confusing Servlet Properties

In pure WebFlux, do not copy Servlet properties thinking they cap `FilePart`:

~~~properties
# The lines below belong to the Servlet/MVC stack,
# not the main configuration for WebFlux multipart:
spring.servlet.multipart.max-file-size=10MB
spring.servlet.multipart.max-request-size=20MB
~~~

For the WebFlux example, the right group is `spring.webflux.multipart.*`. If an app runs Spring MVC because both WebFlux and MVC are on the classpath, verify **which stack is actually running** before tuning configuration.

### 11.3. Security Controls

- **Authentication and authorization:** who may upload, into which folder/store, and who may later download? Enforce at the business layer, never via filenames.
- **Path traversal:** never pass `FilePart.filename()` directly to `storageRoot.resolve(filename)`. Attackers can inject `../`, separators, odd Unicode characters, or special names.
- **Spoofed content type:** `FilePart.headers().getContentType()` is self-declared by the client. If allowing only PNG/PDF, validate **byte contents**, valid structure, and business policy.
- **Malware / active content scanning:** uploaded payloads can harbor malicious content; consider malware scanning, sandboxing, and download controls.
- **Resource limits:** enforce total size, per-file size, part count, request timeouts, per-user quotas, concurrent upload caps, and rate limits.
- **Public files:** never store uploads in `src/main/resources/static` or a public web root where direct URLs accidentally expose them, especially for private data.
- **Error handling:** partial files from dropped connections or quota errors must be cleaned up. Record metadata in DB/object storage in proper order and durability.
- **Logging:** log request ID, size, status, and server-generated file ID; avoid logging full file contents or unsanitized filenames.
- **Downloads:** set `Content-Disposition`, enforce media types, and include security headers so browsers do not execute untrusted uploads unexpectedly.

## 12. Error Codes and Diagnosis

| Symptom | Explanation to Check | Action |
| --- | --- | --- |
| 400 when `file` or `note` is missing | Required `@RequestPart` could not find a matching part name | Match multipart `name` with annotation value exactly |
| 400 on malformed boundary/body | Parser could not split parts structurally | Let HTTP client generate boundary; inspect raw request |
| 415 sending JSON to `consumes=multipart/form-data` | Wrong request media type | Use `curl -F`/`FormData` or adjust API contract |
| Part size error / HTTP 413 or other status | Parser/proxy enforced limit; exact status depends on layer | Check logs, exceptions, and actual WebFlux/gateway limits |
| 500 when writing file | Directory permissions, disk full, storage failure, or bug | Observe error signal from `transferTo` and implement cleanup |
| 201 returned before file is saved | Called `subscribe()` and returned success early | Return the publisher representing the entire save task |
| Event-loop warnings / p99 latency spikes | Blocking I/O or `block()` inside handler | Profile threads; offload blocking work or use async clients |
| Cannot bind `note` field | Confused `@RequestParam` with `@RequestPart` in WebFlux | Bind `FormFieldPart` or an appropriate command object |
| Filename altered / `../` injected | Trusted client-provided `filename` | Generate server-side ID/path and normalize metadata |
| Out of memory on large files | Accumulated `DataBuffer` into an array/collection | Use `transferTo` or bounded streaming |
| `Flux<PartEvent>` leaks memory | Buffers not consumed/released | Audit buffer lifecycle on complete, error, cancel, discard |
| Works locally, fails in production | Proxy size limit, temp dir, container filesystem/permissions | Measure each layer, set quotas, use proper storage |

**Ordered debugging checklist:**

1. Confirm the application actually runs **WebFlux** and the controller executes on the reactive stack.
2. Inspect the HTTP request: `Content-Type`, boundary, part names, part headers, and payload size.
3. Verify annotations: `@RequestPart("file")` matches `name="file"`, media type matches `consumes`.
4. Check exception origin across parser, argument binding, validation, or file I/O; do not guess from status code alone.
5. Check both the parser's temporary directory and the service's storage directory; they can be **two separate locations**.
6. Test small files, oversized files, multiple parts, and aborted uploads; ensure no orphan files remain and no false success is returned.

## 13. Multiple Files, Form Binding, and Functional Endpoints

### 13.1. Multiple Files with the Same Name

A client can send:

~~~bash
curl -i -F "files=@a.txt" -F "files=@b.txt" \
  http://localhost:8080/api/batch
~~~

This command is only a **protocol illustration**, because the section 5 sample app does not define `/api/batch`. On the server, design the handler to accept **multiple parts** named `files`; `MultiValueMap<String, Part>` works well when preserving repeated names. When saving, pick sequential `concatMap` if ordering and tight disk/memory control matter, or `flatMap` with an **explicit concurrency limit** for parallelism.

Do not use `parts.getFirst("files")` and assume the request only contains one file: clients can send extra parts under the same name. Enforce a maximum file count and clearly return an error when exceeded.

### 13.2. Form Binding

WebFlux supports data binding a command object containing a `FilePart` and form fields when the form model fits. This is convenient for forms with many fields. However, for straightforward upload APIs, `@RequestPart` expresses the part name and type contract more explicitly and is easier to test via `curl`.

### 13.3. Functional Routing

Annotated controllers are not mandatory. With `RouterFunction` and `HandlerFunction`, WebFlux exposes APIs on `ServerRequest`:

~~~java
Mono<MultiValueMap<String, Part>> parts = request.multipartData();
~~~

This is **one expression inside a functional handler**, not a standalone Java program. For streaming events, use `request.bodyToFlux(PartEvent.class)`. The rules for validation, byte limits, filename safety, buffer release, and never blocking the event loop **remain unchanged**.

## 14. Quick Comparison: WebFlux vs. Spring MVC

| Aspect | Spring WebFlux | Spring MVC / Servlet |
| --- | --- | --- |
| Primary file type | `org.springframework.http.codec.multipart.FilePart` | `org.springframework.web.multipart.MultipartFile` |
| Part interface | `org.springframework.http.codec.multipart.Part` | `jakarta.servlet.http.Part` when using Servlet API |
| Reading content | `Flux<DataBuffer>` or `FilePart.transferTo(Path)` | `InputStream`, `getBytes()`, `transferTo(...)` per API |
| Saving file | Compose `Mono<Void>`, no `block()` on event loop | Synchronous controller typically performs blocking I/O |
| Reading multiple parts | `Mono<MultiValueMap<String, Part>>` | Servlet multipart resolver / request parts |
| Streaming events | `Flux<PartEvent>` | Different Servlet stream/part mechanisms |
| Spring Boot config | `spring.webflux.multipart.*` | `spring.servlet.multipart.*` |
| `@RequestParam` | Binds query parameters in WebFlux | Can bind form/multipart fields in Servlet MVC |

Both stacks can power solid upload APIs when designed with proper quotas and storage. **Reactive does not automatically make uploads safer or faster**, though publisher APIs cleanly express chaining, streaming, and backpressure in the right architecture.

## 15. Self-Check Exercises

**Q1.** Given part `name="avatar"; filename="pic.png"`, what do `Part.name()` and `FilePart.filename()` return? Why cannot `filename()` serve as a trusted storage path?

**Q2.** In WebFlux, why can using `@RequestParam("note") String note` to receive a text part miss the mark, whereas `@RequestPart("note") FormFieldPart note` expresses intent more clearly?

**Q3.** What type does `file.transferTo(target)` return? If a controller calls `.subscribe()` and immediately returns 201, what is the risk?

**Q4.** You receive 4 files all sharing the part name `files`. Why is `MultiValueMap<String, Part>` more suitable than `Map<String, Part>` when inspecting the full request?

**Q5.** Does `spring.webflux.multipart.max-in-memory-size=256KB` always mean “files larger than 256KB are rejected”? Why or why not?

**Q6.** Why must you release `DataBuffer` when manually working with `Flux<PartEvent>`?

**Q7.** When should you prefer `Flux<PartEvent>` over `Mono<MultiValueMap<String, Part>>`?

**Q8.** A WebFlux endpoint uses `FilePart`, yet config only defines `spring.servlet.multipart.max-file-size`. What should you double-check?

**Guidance answers:**

1. `avatar` and `pic.png`; client-declared names can contain path traversal or malicious names, so generate a server-side storage ID.
2. WebFlux separates query params from multipart; `@RequestPart` selects the exact body part by `name`.
3. `Mono<Void>`; calling subscribe detached separates saving from the response, risking reporting success before writes finish and dropping errors.
4. A single part name can repeat multiple times; `MultiValueMap` retains the list of parts per name.
5. No. In the standard multipart parser, this threshold governs memory buffering/disk spooling for file parts, not a ban on uploads larger than the threshold.
6. Buffers may come from a reference-counted pool; failing to release leaks memory, especially on cancel/error paths.
7. When you want to stream part-by-part/event-by-event without collecting the entire part structure upfront, e.g., large files or direct forwarding.
8. Confirm WebFlux is genuinely running and switch to `spring.webflux.multipart.*` plus gateway limits.

## 16. Takeaways

- `multipart/form-data` contains multiple parts with separate headers and bodies; `boundary` is set by the HTTP client.
- `Part` is the common interface; `FilePart` handles files, `FormFieldPart` handles text, and `PartEvent` handles streaming events.
- `@RequestPart("file")` matches the **part name**, not the filename. `FilePart.filename()` is not a safe storage path.
- `FilePart.transferTo(Path)` returns `Mono<Void>`: compose it into the pipeline and return success **after** writing completes.
- `@RequestBody Mono<MultiValueMap<String, Part>>` suits inspecting a full part map; `Flux<PartEvent>` suits streaming, at the cost of managing buffers and byte limits yourself.
- Do not use MVC's `MultipartFile`/`jakarta.servlet.http.Part` in WebFlux code; do not mistakenly rely on `spring.servlet.multipart.*`.
- Enforce authentication, quotas, content checks, content types, filenames, paths, timeouts, temp storage, error handling, and cancellation cleanup.
