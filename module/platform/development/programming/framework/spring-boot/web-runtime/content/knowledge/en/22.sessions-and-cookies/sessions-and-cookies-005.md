# Distinguishing Server-Managed Cookies from Application-Created Cookies

**Module:** Spring Boot - web-runtime  
**Parent topic:** Sessions and cookies

## 1. Understanding the two kinds of cookies in a web application

In HTTP, a **cookie** is a name–value pair accompanied by scope, lifetime, and security attributes. A server response can send a **Set-Cookie** header; the browser decides whether to store the cookie and sends eligible pairs back in the **Cookie** header on subsequent requests.

In Spring Boot running on the **Servlet stack**, two common cases appear:

1. **Session cookie issued by the Servlet container or session management mechanism**, typically **JSESSIONID**: holds a **session ID** used to look up server-side **HttpSession** state. The application usually creates/reads `HttpSession`; the container manages issuing and receiving the ID via session tracking.
2. **Custom cookie explicitly created by application code**, such as **ui_theme=dark**, **locale=vi**, or a token with its own verification scheme: the application chooses the name, value, issuance point, lifetime, scope, validation, and deletion timing. This cookie **does not automatically become an HttpSession** merely because it was returned by the same server.

**The distinction lies in semantic ownership and lifecycle.** Both are HTTP cookies, both are normally stored and sent automatically by browsers according to Domain/Path/Secure/SameSite; from the browser's perspective there are not two separate cookie protocols. The phrase "server-managed cookie" in this lesson refers to cookies tied to Servlet/Spring Session **session tracking**; it does not mean data bypasses the browser or that application cookies are created only in JavaScript.

### Learning objectives

After this lesson, you will be able to:

- Distinguish a **session ID** from **HttpSession contents**, and demonstrate that `JSESSIONID` does not contain the entire user object.
- Read **Set-Cookie** and **Cookie** headers, recognizing which names/values are generated by the framework/container and which are generated by controllers/services.
- Build a Spring Boot 3.x + Java 17+ demo that both uses **HttpSession** and issues a custom **ui_theme** cookie, then test it using `curl` and a cookie jar.
- Configure session cookies via **server.servlet.session.cookie.*** and custom cookies via **ResponseCookie** or Servlet **Cookie**.
- Distinguish **browser cookie lifetime** from **server-side session data lifetime**.
- Select appropriate **HttpOnly, Secure, SameSite, Path, Domain, and Max-Age** settings and handle logout, cookie deletion, HTTPS, proxies, session fixation, and multi-instance deployment.

## 2. How does HTTP send and receive cookies?

Example of a server returning two cookies in the same response:

~~~http
HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=<opaque-id>; Path=/; HttpOnly; SameSite=Lax
Set-Cookie: ui_theme=dark; Path=/demo; Max-Age=604800; SameSite=Lax
Content-Type: text/plain

OK
~~~

This is an **illustrative example**, not a real ID or a guarantee of attribute ordering. **Each cookie must be emitted in its own Set-Cookie header**; do not concatenate multiple `Set-Cookie` headers into one comma-separated header.

Later, when the browser requests a URL with a matching path and unexpired cookies, the request may contain:

~~~http
GET /demo/session/status HTTP/1.1
Host: example.test
Cookie: JSESSIONID=<opaque-id>; ui_theme=dark
~~~

What to read carefully:

- **Set-Cookie** is a response header from server to browser. **Cookie** is a request header sent from browser to server. The request `Cookie` header **sends only name–value pairs**, without repeating `HttpOnly`/`Secure`/`Path`/`Max-Age`.
- **JSESSIONID** and **ui_theme** can be sent together in the same request, each serving a different purpose.
- The browser does not know which account **JSESSIONID** corresponds to or whether **ui_theme** is validated. Those meanings belong to the server/application.
- Browsers use cookie attributes and their own security policies to decide storage/sending; non-browser HTTP clients can set any **Cookie** header arbitrarily. **Never trust a cookie value merely because it arrived in a header.**
- If a request targets **/public** instead of **/demo**, a cookie with **Path=/demo** should not be sent by the browser under path-matching rules. A **Path=/** cookie has broader scope.

Similarly, JavaScript is allowed to create application cookies via **document.cookie** if unrestricted; however, a cookie created from JavaScript does not turn into a Servlet-container-managed session unless the server configures such a mechanism. Therefore, classify cookies by **role**, not merely by "who called Set-Cookie".

## 3. Session cookies managed by the Servlet container

### 3.1. Where does HttpSession live?

When a Spring MVC controller executes:

~~~java
HttpSession session = request.getSession(true);
session.setAttribute("displayName", "learner");
~~~

**HttpSession** holds the session's logical attributes, managed on the server side (by default usually in the Servlet container's memory when no external session store is configured). The browser does not receive Java objects or the full attribute map. The browser typically receives an **opaque ID**:

~~~text
Browser                        Spring Boot Servlet container
   | POST /demo/session/start            |
   |------------------------------------>|
   |                          create HttpSession S123
   |                          session["displayName"] = "learner"
   |<-- Set-Cookie: JSESSIONID=<id> ------|
   |                                     |
   | GET /demo/session/status            |
   | Cookie: JSESSIONID=<id>             |
   |------------------------------------>|
   |                    lookup ID -> HttpSession S123
   |                    read attribute displayName
   |<-- active:learner -------------------|
~~~

Strings like **S123** and **<id>** are illustrative only. Real IDs are generated by the session mechanism and must be unpredictable. **Never manually embed a user ID, password, or permission into the JSESSIONID string.**

### 3.2. Who creates and manages that cookie?

In a Spring Boot MVC app on default embedded Tomcat, when a new **HttpSession** needs cookie tracking, the Servlet container issues the session cookie (typically named **JSESSIONID**). Applications should interact only with the **HttpSession API**, rather than manually calling **response.addCookie(new Cookie("JSESSIONID", ...))** to simulate a session.

Key APIs:

- **request.getSession()** or **request.getSession(true)**: get the existing session or create a new one if none exists.
- **request.getSession(false)**: only get an existing session, returning **null** if none exists; useful for checking without accidentally creating a session.
- **session.setAttribute("key", value)** / **getAttribute(...)**: store/retrieve server-side session data.
- **session.invalidate()**: invalidate the session on the server side.
- **request.changeSessionId()**: rotate the session ID of an existing session; commonly applied after authentication elevation to defend against **session fixation** (Spring Security provides built-in protection when configured).
- **session.setMaxInactiveInterval(seconds)**: change the idle timeout for a specific session; not synonymous with cookie `Max-Age`.

Pay attention to the word **"typically"**: **JSESSIONID** is the Servlet container convention, yet the name can be changed or **Spring Session** can use another store/resolver (for example, the default **SESSION** cookie when Spring Session uses its corresponding cookie resolver). Never hardcode assumptions about the cookie name when project configuration changes.

### 3.3. The JSESSIONID cookie does not carry login data

Suppose **session.setAttribute("cart", someCart)**. The browser still carries only the ID. The cart resides on the server, or in the configured session store. If someone else steals a valid ID, they **can hijack the session** even without seeing the cart inside the cookie. Thus the session ID must be protected like a credential.

Other custom-designed cookies may hold a **signed token/JWT** or encrypted payload, meaning the server verifies data contained inside the cookie instead of looking up an `HttpSession`. **That is a different model**, with its own rules for expiry, revocation, rotation, CSRF, and key management; never assume any arbitrary cookie string is a secure authentication token.

## 4. Cookies explicitly created by the application

Suppose the user selects a dark theme:

~~~http
Set-Cookie: ui_theme=dark; Path=/demo; Max-Age=604800; SameSite=Lax
~~~

The application chooses the name **ui_theme**, restricts accepted values to **dark/light**, sets a 7-day retention period, and reads the cookie in a controller. No `HttpSession` has to be created just to write this cookie.

Appropriate examples:

| Custom cookie | Intended content | Requires HttpSession lookup? | Notes |
| --- | --- | --- | --- |
| **ui_theme=dark** | Low-sensitivity UI preference | No | Readable by JS if HttpOnly is omitted; validate against an allowlist. |
| **locale=vi** | User's preferred language | No | Client can modify it; treat strictly as a UI hint. |
| **consent=accepted** | An option state | Not necessarily | If required as legal/audit evidence, record it server-side per business rules. |
| **cart_ref=<id>** | Cart reference key | Can look up a separate database/service | Do not blindly treat an ID as access authorization. |
| **refresh_token=<opaque-token>** | Long-lived credential | Not necessarily HttpSession | Requires strict protection, rotation/revocation, HTTPS, HttpOnly, and CSRF defense. |

**Issuing a cookie from the application does not mean data is stored on the server.** The value may live entirely in the browser, serve as a lookup key to another server-side store, or contain a signed/encrypted token. Your design must clearly define the trust boundary.

**Never put secrets, permissions, passwords, plaintext private data, or serialized Java objects into cookies.** Clients can inspect and tamper with payloads (barring restrictions that only limit scripts) and can forge headers with HTTP tools. Signing ensures integrity when implemented properly, yet **does not hide the content**; encryption is required for confidentiality, and both still require key and lifecycle management.

## 5. Direct comparison table

| Criterion | Session cookie managed by container/framework | Custom cookie created by application |
| --- | --- | --- |
| Example names | **JSESSIONID**, sometimes **SESSION**, or a configured name | **ui_theme**, **locale**, **auth_token**... |
| Who chooses the value? | Session mechanism generates an opaque ID | Application chooses the string/ID/token |
| Meaning | Binds requests to a **server-side session** | Business-dependent: preference, tracking, token, reference... |
| Where does the main data live? | **HttpSession**/server session store; cookie holds only the ID | May live in the cookie itself or another server store |
| How it is created | **getSession(true)** or framework needing a session; container/resolver emits cookie | **HttpServletResponse.addCookie** or **ResponseCookie** + Set-Cookie |
| How it is read | **getSession(false)** and session attributes | **@CookieValue**, **request.getCookies()**, or Cookie header |
| How it is deleted | **invalidate()** on the server; deleting browser cookie is a separate step if needed | Re-emit Set-Cookie with same name/scope and **Max-Age=0**, plus delete server state if any |
| Lifetime | Separate **session idle timeout** and **cookie expiry** | App sets Max-Age/Expires, plus server TTL if applicable |
| Security | ID is a secret; needs Secure/HttpOnly/SameSite/TLS, session fixation/CSRF protection | Depends on value; tokens require credential-grade protection |
| Moving to a cluster | Needs a shared session store or suitable strategy | Depends on where the app stores/verifies state |
| Sent automatically by browsers? | Yes, when the cookie matches all rules | Also yes, when the cookie matches all rules |

**Do not equate a “session cookie” (by lifetime) with an “HttpSession cookie”.** A custom cookie **without Expires/Max-Age** is a browser-session cookie by lifetime, even though it has nothing to do with `HttpSession`. Conversely, a cookie identifying an `HttpSession` **can be configured with a Max-Age longer than one browser session**; the server-side session may still expire sooner.

## 6. Cookie attributes to control

| Attribute | How it works | How to use it |
| --- | --- | --- |
| **Name=Value** | Identifier and value stored/sent for the cookie. | Use a distinct name, avoiding collisions with session cookies; store only small, validated data. |
| **Path** | Limits request paths where the browser sends the cookie per path-matching rules. | **/** for app-wide cookies, **/demo** for the demo; Path is not a data security boundary. |
| **Domain** | If present, allows the cookie to go to the specified domain and eligible subdomains. | Omit Domain by default for a **host-only cookie**, preventing unintended sharing. |
| **Secure** | Sent only over HTTPS connections per browser rules (localhost has local exceptions). | **true** for sensitive cookies in HTTPS production. Does not replace TLS configuration. |
| **HttpOnly** | Blocks normal JavaScript from reading the cookie via **document.cookie**. | **true** for session IDs/tokens not needed by JS; does not stop JS from triggering requests carrying cookies. |
| **SameSite=Strict** | Sent only in strict same-site contexts. | Strong protection, though it can disrupt some navigation/auth flows. |
| **SameSite=Lax** | Blocks many cross-site cases; allows certain safe top-level navigations. | Often suitable for traditional apps; does not replace CSRF tokens. |
| **SameSite=None** | Permits cross-site sending per browser policy. | Browsers require **Secure**; still subject to third-party cookie blocking. |
| **Max-Age** | Relative lifetime in seconds; **0** requests immediate expiration. | Common for preference cookies; distinguish from session idle timeout. |
| **Expires** | Absolute expiration timestamp. | Can replace Max-Age; if both are present, Max-Age takes precedence. |

### Host-only, Domain, and Path

If the server at **app.example.test** sends:

~~~http
Set-Cookie: ui_theme=dark; Path=/demo; SameSite=Lax
~~~

Without **Domain**, the cookie belongs to **app.example.test** and is not automatically sent to **api.example.test**. It only accompanies request paths matching **/demo**, such as **/demo/theme**, not **/health**.

If **Domain=example.test** is declared, eligible subdomains can also receive the cookie; this widens scope and increases cookie-injection/session-fixation risk across subdomains. `Domain` may only be set to the current domain or a valid parent domain, never arbitrarily to someone else's domain.

**Path is not an authorization mechanism.** Multiple applications on the same origin can interact with browser data within their capabilities; always protect APIs with server-side authentication and authorization.

### Cookie prefixes

Supporting browsers reject cookies violating prefix constraints:

- **__Secure-**: requires `Secure` and a secure origin.
- **__Host-**: requires `Secure`, **Path=/**, and **no Domain**, narrowing scope to the issuing host.

Names like **__Host-session** or **__Host-auth** help guard against misconfiguration on HTTPS systems, provided you set all attributes properly. Prefixes **do not replace** server-side token or session verification.

### HttpOnly, Secure, and SameSite do not substitute for one another

- **HttpOnly** reduces script access to cookies, yet **XSS can still issue requests using the user's session**. You must fix XSS and maintain authorization checks.
- **Secure** reduces the risk of cookies traveling over HTTP; you still need real **HTTPS/TLS** up to the TLS termination point and proper proxy validation.
- **SameSite** is a supporting defense against **CSRF**, not a replacement for CSRF tokens/Origin checks on protected state-changing actions.
- **CORS** controls cross-origin response access, not whether browsers send every cookie. Cross-origin `fetch` must evaluate **credentials**, CORS `allow-credentials`, `SameSite`, and browser policies together.

## 7. Runnable demo: Spring Boot 3.x, Java 17+, Servlet MVC

### 7.1. Prerequisites and dependencies

Use a Spring Boot 3.x project running Java 17+ with Gradle Wrapper, the Spring Boot plugin, and Maven Central configured. Add **spring-boot-starter-web**:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
~~~

The demo uses a REST controller on default embedded Tomcat; **do not add spring-boot-starter-security** in this demo so curl commands can test without login/CSRF setup. When Spring Security is present in a real system, configure authentication, authorization, and CSRF appropriate to your API.

### 7.2. application.properties: configuring only the session cookie

Create **src/main/resources/application.properties**:

~~~properties
server.port=8080

# HttpSession state expires after 20 minutes of inactivity
server.servlet.session.timeout=20m

# Configure the HttpSession identifier cookie (Servlet stack)
server.servlet.session.cookie.name=JSESSIONID
server.servlet.session.cookie.path=/
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax

# In HTTPS production, also enable:
# server.servlet.session.cookie.secure=true

# Omit max-age: browser-session cookie by cookie default
# server.servlet.session.cookie.max-age=7d
~~~

The **server.servlet.session.cookie.*** properties manage the session cookie issued by the Servlet/session framework. They **do not automatically apply to every cookie** added manually by controllers. Spring Boot 3.3 also supports **server.servlet.session.cookie.domain** and **max-age** when needed.

The example uses **HTTP localhost** for convenient testing. In production, use HTTPS and set **Secure=true** on session cookies. Never copy a `Secure=false` config or omit TLS in real environments. If TLS terminates at a reverse proxy, verify the effective scheme and forwarded headers from a trusted proxy before relying on request properties to choose `Secure`.

**server.servlet.session.timeout** is the **idle timeout of server-side state**. **server.servlet.session.cookie.max-age** is the cookie's lifetime **in the browser**. They are independent: the browser can keep sending an invalidated ID after the server deletes the session, and a cookie can expire while server state has not yet timed out.

### 7.3. Java: one auto-generated session cookie and one custom cookie

Create file **src/main/java/com/example/cookielab/CookieLabApplication.java**:

~~~java
package com.example.cookielab;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;

import java.time.Duration;
import java.util.Set;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseCookie;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.CookieValue;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class CookieLabApplication {
    public static void main(String[] args) {
        SpringApplication.run(CookieLabApplication.class, args);
    }
}

@RestController
class CookieLabController {
    private static final Set<String> THEMES = Set.of("dark", "light");

    @PostMapping("/demo/session/start")
    public String startSession(HttpServletRequest request) {
        HttpSession session = request.getSession(true);
        session.setAttribute("label", "learner");
        return "session-started";
    }

    @GetMapping("/demo/session/status")
    public String sessionStatus(HttpServletRequest request) {
        // Do not create a new session when only checking.
        HttpSession session = request.getSession(false);
        if (session == null) {
            return "no-active-session";
        }
        return "active:" + session.getAttribute("label");
    }

    @PostMapping("/demo/session/end")
    public String endSession(HttpServletRequest request) {
        HttpSession session = request.getSession(false);
        if (session != null) {
            session.invalidate();
        }
        return "session-invalidated";
    }

    @PostMapping("/demo/theme/{theme}")
    public ResponseEntity<String> setTheme(
            @PathVariable("theme") String theme,
            HttpServletResponse response
    ) {
        if (!THEMES.contains(theme)) {
            return ResponseEntity.badRequest().body("invalid-theme");
        }

        ResponseCookie preference = ResponseCookie.from("ui_theme", theme)
                .path("/demo")
                .httpOnly(false) // UI preference only, not a credential.
                .secure(false)   // Only for testing over HTTP localhost.
                .sameSite("Lax")
                .maxAge(Duration.ofDays(7))
                .build();

        // Use addHeader so other Set-Cookie headers in the response are not overwritten.
        response.addHeader(HttpHeaders.SET_COOKIE, preference.toString());
        return ResponseEntity.ok("theme-saved");
    }

    @GetMapping("/demo/theme")
    public String readTheme(
            @CookieValue(name = "ui_theme", required = false) String theme
    ) {
        // Cookie sent by client: revalidate even though the app issued it.
        return theme != null && THEMES.contains(theme) ? theme : "default";
    }

    @PostMapping("/demo/theme/delete")
    public String deleteTheme(HttpServletResponse response) {
        ResponseCookie expired = ResponseCookie.from("ui_theme", "")
                .path("/demo")
                .httpOnly(false)
                .secure(false) // Match the demo scope used when issuing the cookie.
                .sameSite("Lax")
                .maxAge(Duration.ZERO)
                .build();

        response.addHeader(HttpHeaders.SET_COOKIE, expired.toString());
        return "theme-deleted";
    }
}
~~~

**Correctness notes for the example:**

- The file has **one `public` class `CookieLabApplication`** matching the filename; `CookieLabController` is package-private in the same package and discovered by Spring component scanning.
- **startSession** calls **getSession(true)** and stores an attribute. **No line manually generates `JSESSIONID` with `ResponseCookie`**; the Servlet session mechanism handles that.
- **sessionStatus** uses **getSession(false)** to inspect the session without creating a new one; if the user has no valid session, it returns **no-active-session**.
- **endSession** invalidates **HttpSession**. It does not delete **ui_theme**; custom preferences have an independent lifecycle.
- **setTheme** accepts only **dark/light**, using **ResponseCookie** to configure **SameSite=Lax**, **Path=/demo**, **Max-Age 7 days**, and **HttpOnly=false** because it is a non-sensitive UI preference that a client might read. For tokens or credentials, do not copy this pattern; design dedicated protections.
- **secure(false)** is written explicitly only for testing on **http://localhost**. In HTTPS production, switch to **secure(true)** and configure session cookies as `Secure` in server configuration.
- **response.addHeader(Set-Cookie, ...)** allows multiple `Set-Cookie` headers to coexist when needed. Avoid **setHeader** so you do not accidentally overwrite another cookie already emitted by the framework in the same response.
- **readTheme** does not trust the incoming cookie: users can alter values, so the method checks an allowlist before using it.
- **deleteTheme** emits a cookie with the **same name and Path** (and matching domain scope) and **Max-Age=0**. If the original cookie had a **Domain**, the deletion must use the same Domain; changing path or domain can create an extra cookie instead of deleting the old one.

**Another application-created mechanism:** you can use **jakarta.servlet.http.Cookie** and **HttpServletResponse.addCookie(...)**; when you want to declare `SameSite` cleanly, Spring's **ResponseCookie** is a convenient option. Avoid building raw `Set-Cookie` strings via unchecked string concatenation.

### 7.5. Testing with a cookie jar: observing two independent lifecycles

Start with a fresh cookie jar file, such as **cookies.txt** (do not reuse a cookie jar from an older test run).

**A. Create a session on the server:**

~~~bash
curl -si -c cookies.txt -X POST \
  http://localhost:8080/demo/session/start
~~~

Response body:

~~~text
session-started
~~~

Response headers typically include a **Set-Cookie: JSESSIONID=<ID>** with the configured session attributes. The ID changes and is unpredictable; path/attribute ordering may vary by container. **-c cookies.txt** writes curl's cookie jar to disk.

**B. Send `JSESSIONID` back to read server state:**

~~~bash
curl -si -b cookies.txt \
  http://localhost:8080/demo/session/status
~~~

Expected response body:

~~~text
active:learner
~~~

**-b cookies.txt** sends matching cookies from the jar. This proves the ID resolves the `HttpSession`, not that `learner` lives inside the cookie.

**C. Create a custom cookie while keeping the session cookie:**

~~~bash
curl -si -b cookies.txt -c cookies.txt -X POST \
  http://localhost:8080/demo/theme/dark
~~~

Body:

~~~text
theme-saved
~~~

Visible **Set-Cookie** header:

~~~http
Set-Cookie: ui_theme=dark; Path=/demo; Max-Age=604800; SameSite=Lax
~~~

This illustrates the primary attributes; the framework may also generate `Expires` and vary ordering. **-b** reads the existing jar, and **-c** updates the jar after the response.

**D. Read the custom cookie:**

~~~bash
curl -si -b cookies.txt http://localhost:8080/demo/theme
~~~

Expected body:

~~~text
dark
~~~

**E. Invalidate HttpSession without touching the preference:**

~~~bash
curl -si -b cookies.txt -X POST \
  http://localhost:8080/demo/session/end

curl -si -b cookies.txt \
  http://localhost:8080/demo/session/status

curl -si -b cookies.txt \
  http://localhost:8080/demo/theme
~~~

The three response bodies in order:

~~~text
session-invalidated
no-active-session
dark
~~~

**Note:** after invalidation, the browser/curl **may still retain `JSESSIONID` in the jar**. That ID no longer points to valid state. Do not claim `invalidate()` guarantees the browser deleted the cookie; verify deletion if logout policies require erasing client-side traces.

**F. Delete the custom cookie:**

~~~bash
curl -si -b cookies.txt -c cookies.txt -X POST \
  http://localhost:8080/demo/theme/delete

curl -si -b cookies.txt \
  http://localhost:8080/demo/theme
~~~

Body after deletion:

~~~text
default
~~~

The deletion command's header carries **Max-Age=0** with matching name/path. This cookie is independent of the session: deleting **ui_theme** does not require invalidating `HttpSession`.

**G. Send a forged cookie to see the server distrusts client data:**

~~~bash
curl -si -H "Cookie: ui_theme=superadmin" \
  http://localhost:8080/demo/theme
~~~

Expected body:

~~~text
default
~~~

If a UI preference is not validated as in the demo, out-of-allowlist values can trigger errors or unintended code branches. For authorization data, allowlist checks alone are not enough; permission decisions must rely on valid server-side authentication/authorization mechanisms.

## 8. Lifecycle: idle timeout differs from cookie expiry

Suppose the server has:

~~~properties
server.servlet.session.timeout=20m
~~~

and a custom cookie:

~~~http
Set-Cookie: ui_theme=dark; Max-Age=604800; Path=/demo
~~~

If the user sends no requests for 30 minutes:

- **HttpSession** may have timed out due to the 20-minute server-side idle interval, so a resent `JSESSIONID` no longer leads to the old session.
- **ui_theme** may still exist in the browser because it has a 7-day `Max-Age`, and the browser will still send it for matching Path/Domain requests.
- Setting **server.servlet.session.cookie.max-age=7d** only extends the **lifetime of the cookie carrying the ID**; it does not automatically extend session state or keep the user logged in for 7 days.
- Conversely, raising **server.servlet.session.timeout** does not force the browser to keep a session cookie after the browser drops it. Some browsers have session restore so cookies without `Max-Age` sometimes survive restarts; never rely on closing the browser as your sole security logout measure.

**Proper logout** in an authentication system may involve invalidating the server-side session, clearing the authentication context, revoking server-side tokens if any, emitting cookie-expiry headers with the exact scope, and cleaning up permitted client state. If using Spring Security, prefer Spring Security's built-in logout and session management with compatible cookie settings rather than stitching together a fake logout endpoint.

## 9. Who controls cookies in Spring Boot and Spring Security?

### 9.1. Servlet container and Spring Boot

When using only Servlet MVC and `HttpSession`, the container performs **session tracking**. Spring Boot provides these properties:

~~~properties
server.servlet.session.cookie.name=JSESSIONID
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=lax
server.servlet.session.cookie.path=/
server.servlet.session.timeout=20m
~~~

This is an example of **HTTPS production configuration**, not to be used verbatim for HTTP localhost exercises. To use custom app paths, domains, or cookie lifetimes, check **server.servlet.session.cookie.path**, **domain**, and **max-age** in your Boot version's docs and verify real container behavior.

**Spring Boot 3.3** also supports configuring the session cookie's `SameSite` attribute via **server.servlet.session.cookie.same-site** on supported embedded Servlet servers. For other cookies added to `HttpServletResponse` by the application, use **ResponseCookie** or **CookieSameSiteSupplier** per the corresponding docs, rather than assuming the session `SameSite` flag applies to every cookie automatically.

### 9.2. Spring Session

When using **Spring Session** with Redis/JDBC or another `SessionRepository`, the **HttpSession API** may remain unchanged while session data is stored in the shared store rather than only in one Tomcat instance's memory. Spring Session's cookie resolver may issue cookies with a different name or handling (often **SESSION** by default in some setups). Therefore, **never hardcode "every session is always JSESSIONID"** when integration setups vary.

A multi-instance session store lets requests hit different replicas, yet you still must protect cookie IDs and configure TTLs, serialization compatibility, secrets, retention, and logout policies. A cookie carrying only an ID does not automatically solve all HA or consistency challenges.

### 9.3. Spring Security

Spring Security can use `HttpSession` to retain a user's **SecurityContext** on the Servlet stack, while applying session fixation protection, CSRF, and logout strategies. Still, **`SecurityContext` is not `JSESSIONID` itself**. The browser continues sending only an ID; the server uses that ID to locate the session and authentication info when appropriate.

A stateless system may use Bearer tokens or signed tokens in cookies without `HttpSession`, yet that is not automatically safer. Cookies holding authentication tokens still carry CSRF risk because browsers send them automatically; appropriate CSRF defenses, expiry management, revocation, and replay protection are still required. **HttpOnly** guards against script reads, not against script-initiated requests.

## 10. HTTPS, reverse proxies, SameSite, and cross-site requests

In production:

~~~text
Browser -- HTTPS --> CDN / Ingress / Reverse proxy
                                 |
                                 +--> HTTP or HTTPS --> Spring Boot
~~~

Cookie **`Secure`** must match the **browser-to-public-endpoint** leg, not merely whether Spring Boot observes internal HTTP or HTTPS. If computing `Secure` via **request.isSecure()**, verify the forwarded scheme from a trusted proxy, configure forwarded headers properly, and never trust arbitrary client-supplied `X-Forwarded-*` headers. A clean, controllable setting for production session cookies when HTTPS is always present is **server.servlet.session.cookie.secure=true**.

Common pitfalls:

- The web app runs behind an HTTPS reverse proxy, yet `Set-Cookie` omits `Secure` or sets `SameSite=None` without `Secure`; the browser may reject the cookie.
- A backend cookie sets **Domain=internal.local** while the browser accesses **app.example.com**; the browser cannot send the cookie to the public host.
- The app lives under **/portal**, yet cookie `Path` or reverse proxy path rewriting mismatches the URL visited by the browser.
- A frontend on another origin calls the API via `fetch` without **credentials** or without server CORS `allow-credentials`; the response contains `Set-Cookie`, yet the browser does not store or send it as expected.
- Browsers block third-party cookies or restrict cross-site tracking even when the app sets **SameSite=None; Secure**. Never assume this attribute overrides all user-agent policies.

**SameSite is not synonymous with SameOrigin.** Two distinct origins can be same-site in some cases; conversely, differing schemes are treated as cross-site under modern schemeful rules. When designing SSO, iframes, or redirects, verify site boundaries, navigation methods, browser cookie policies, and the actual authentication flow.

## 11. Design mistakes and how to spot them

| Symptom | Possible cause | How to resolve |
| --- | --- | --- |
| Controller calling `getSession(false)` always gets null | No session created yet, browser omits cookie, wrong Domain/Path/Secure/SameSite, or session timed out. | Inspect `Set-Cookie`, `Cookie` headers, server-side session lookup, and cookie jar. |
| Every request gets a new `JSESSIONID` | Client does not retain cookie, domain/path/proxy mismatch, or inconsistent session store. | Check cookie acceptance, HTTPS, instances, sticky routing/session store. |
| Using `ui_theme` cookie works, yet login is lost after restart | `ui_theme` is not the auth session; `HttpSession` can be lost on server restart. | Identify where state lives; configure a shared/persistent session store if needed. |
| Browser still sends `JSESSIONID` after logout | `invalidate()` is server-side; the browser may not delete the cookie automatically. | Confirm server session is invalid; expire the exact cookie scope if required; use standard logout. |
| Deleted `ui_theme`, yet it still appears | Deleted with wrong Path/Domain, or multiple cookies share the name in different scopes. | Inspect browser storage tab and `Set-Cookie`; send `Max-Age=0` with the exact matching scope. |
| JavaScript cannot read `JSESSIONID` | `HttpOnly` is active. | This is the intended protection; do not disable `HttpOnly` for session IDs. |
| Cross-site API does not retain cookies | Missing credentials, CORS, `SameSite=None;Secure`, or browser policy. | Inspect browser Network tab, cookie blocked reasons, and CORS/SameSite config. |
| Session expires before browser cookie | Server idle timeout is shorter than cookie `Max-Age`. | Distinguish server/session TTL from cookie expiry. |
| Login succeeds on one server, fails on another | Session state lives only in one node's RAM. | Use a shared session store or proper topology/affinity; monitor TTL. |
| Cookie holding `role=ADMIN` tampered via curl | App trusts client-controlled data. | Never use plaintext cookies as the authorization source of truth. |
| Custom `Set-Cookie` wipes out the session cookie | Response used `setHeader`, overwriting the earlier header. | Use `addHeader` for multiple `Set-Cookie` headers; inspect actual responses. |
| XSS steals a token from a custom cookie | `HttpOnly` disabled or token placed where JS can read it. | Sensitive tokens require `HttpOnly`/`Secure`/TLS, plus XSS and CSRF defenses. |

## 12. Testing and observing accurately

Valuable tests should cover both controller level and real HTTP:

1. **No cookie:** call **GET /demo/session/status** from a fresh client → **no-active-session** without creating a session just for checking.
2. **Create session:** **POST /demo/session/start** → **Set-Cookie JSESSIONID** (with Servlet container cookie tracking); resend ID → **active:learner**.
3. **Custom cookie:** **POST /demo/theme/dark** → **Set-Cookie ui_theme**, verify **Path, Max-Age, SameSite**; call GET theme → **dark**.
4. **Independent lifecycles:** invalidate the session, verify status is inactive while theme remains **dark**; then delete theme and verify **default**.
5. **Forged cookie:** send **ui_theme=superadmin** and verify the code falls back to **default**; never use a `role=ADMIN` cookie for real permissions.
6. **Cookie expiry:** verify **Max-Age=0** causes the browser to delete the exact cookie by name/domain/path. Handle duplicate cookie names across distinct Paths separately.
7. **TLS/proxy:** on public HTTPS, verify the session cookie carries **Secure/HttpOnly/SameSite**; check in DevTools Network/Application, not just property files.
8. **Multi-replica:** verify `HttpSession`/sessions work when requests hit another node; use a shared session store if topology requires it.
9. **Security:** verify state-changing POSTs have CSRF protection when using cookie auth, session IDs rotate on privilege elevation, and sessions are invalidated on logout.

**MockMvc** can test controllers, `HttpSession` calls, and response cookie headers, but **does not fully represent browser cookie jars, TLS termination, cookie-blocking policies, or proxies**. To verify real Secure/SameSite/Domain/Path behavior, test with real browsers and HTTP clients against the deployed endpoint.

**Never print raw session IDs or tokens into logs, screenshots, or public documentation.** When logs are needed for debugging, log only non-credential request/correlation IDs in compliance with system security policies.

## 13. Scenario questions

**Scenario A.** A controller sets **session.setAttribute("userId", 42)** and the server sends **JSESSIONID=abc...**. Can the browser extract `userId=42` directly from `JSESSIONID`? **No.** The cookie is only the session ID; state resides on the server/session store. There is no direct mapping from the opaque string to `userId` without a server lookup.

**Scenario B.** A user closes the tab, reopens the page, still sees **ui_theme=dark**, yet has to log in again. Is this a contradiction? **No.** The custom cookie has a 7-day lifetime; `HttpSession` may have expired/invalidated or the browser dropped the session cookie.

**Scenario C.** A developer sees **SameSite=Lax** and removes CSRF protection for all POSTs. Is that completely safe? **No.** `SameSite` is defense in depth, not a replacement for CSRF, origin, authorization, and state-changing action checks.

**Scenario D.** A service sets **server.servlet.session.cookie.max-age=7d** while server timeout stays 20 minutes. After 2 hours idle, the browser sends the old ID—is the user still logged in? **Normally no**, the server session has expired; a new session might be created if a handler explicitly creates one. A long-lived cookie does not resurrect expired state.

**Scenario E.** An app calls **response.addHeader("Set-Cookie", "ui_theme=dark; ...")** on the same response where the container emits `JSESSIONID`. Can the browser store both? **Yes**, provided both `Set-Cookie` headers are valid and accepted by browser policy. Using **addHeader** preserves separate headers; using **setHeader** easily overwrites earlier headers unless managed explicitly.

**Scenario F.** Cookie **ui_theme=dark; Path=/demo** does not arrive at endpoint **/health**. Did the server delete the cookie? **No**, it is likely because the `Path` scope does not match. Inspect browser storage and the request path.

**Scenario G.** The server issues **JSESSIONID**, yet the app uses Spring Session Redis. Can we assert the state lives in Tomcat RAM? **No**, the `HttpSession` API can be backed by an external `SessionRepository`; check the actual runtime configuration.

## 14. Knowledge self-check

1. **What does `JSESSIONID` contain?** — Typically an opaque session identifier, not all session attributes.
2. **Does calling `getSession(false)` create a session?** — No.
3. **Does disabling `HttpOnly` help the server manage sessions better?** — No; it only makes the cookie readable by JS.
4. **Are custom cookies always persistent?** — No; without `Max-Age`/`Expires`, they are browser-session cookies.
5. **Is the session-management cookie always named `JSESSIONID`?** — No; the name can be customized or changed by Spring Session.
6. **Does invalidating `HttpSession` automatically delete all custom cookies?** — No; custom cookie lifecycles are independent.
7. **Is `Path=/demo` an authorization control?** — No; it only defines the browser's cookie-sending scope.
8. **Does `Secure` replace HTTPS?** — No; real TLS and proper proxy configuration are still required.
9. **Does `Max-Age=7d` replace a 20m server session timeout?** — No; they are two independent concepts.
10. **Can you trust `role=admin` from the `Cookie` header?** — No; clients can forge or modify cookie values.
11. **What must match when deleting a cookie?** — The corresponding Name, Path, and Domain scope, subject to browser policies.
12. **Does `SameSite=None` require `Secure`?** — Yes, under modern browser rules.
13. **Why does one HTTP response need multiple `Set-Cookie` headers?** — Each cookie is set individually; joining with commas breaks syntax and can break parsers.
14. **When should Spring Session be considered?** — When session state must be managed across multiple instances/stores with appropriate TTL and HA policies.
