# Server Access Logs and Application Request Processing Logs in Spring Boot

## 1. Objectives and Scope

When users report "the API returned 500", "the request took 4 seconds", or "the call does not show up in the service", engineers need to distinguish at least **two sources of information**:

1. **Server access log**: records the requests observed by the HTTP web server/container, typically including timestamp, HTTP method, path, status, byte count, and processing duration.
2. **Application request log**: records the steps known to application code, such as a request entering/exiting a filter, controller execution, downstream calls, business outcomes, exceptions, and **correlation/request ID**.

These two sources **complement each other rather than replacing one another**. Access logs answer "which requests did the server handle and what did the response look like at that layer"; application logs answer "what did the application logic process and what decision led to that outcome". When an application sits behind a reverse proxy, there is also an **edge/proxy access log**, which may capture requests that Tomcat never received.

This lesson targets **Spring Boot web runtime**, using Spring MVC/Servlet with **embedded Tomcat**, Java 17+, and a runnable Maven example. Beyond Tomcat, it also explains differences when using Jetty, Undertow, or WebFlux/Netty; HTTP async/streaming, MDC, Spring Security, reverse proxies, tracing, sensitive data, and testing.

After completing this lesson, you will be able to:

- Enable and configure Tomcat access logs in the right location; distinguish patterns `%m`, `%U`, `%s`, `%b`, `%D`, and `%{X-Request-Id}o`.
- Write a filter using `OncePerRequestFilter` to attach an ID, put it into the response header/MDC, and write application logs **without leaking passwords, cookies, or query strings**.
- Understand the exact limitations of filters with async dispatches, exceptions, and final response status.
- Correlate access logs and application logs by ID instead of relying on thread names or IP addresses.
- Test response status and request ID via a **real HTTP server**, as well as verify the access log file in a way that does not depend on a fixed timestamp log string.
- Diagnose differences between 4xx/5xx responses caused by a proxy, container, filter, Spring Security, or business service.
- Choose log fields, log levels, retention, sampling, and data protection policies for production.

**Principle:** a good log must be at the **right layer**, at the **right time**, carry an **identifier linking across layers**, avoid leaking secrets, and never become a cause of application overload itself.

## 2. Three Log Layers Along the Path of an HTTP Request

Suppose:

```text
Browser / mobile / API client
     |
     | GET https://api.example.com/api/items/42
     v
Reverse proxy / Load balancer / Ingress
     |  -> proxy access log: edge status, public host, upstream time
     |
     | GET http://app-service:8080/api/items/42
     v
Embedded Tomcat
     |  -> Tomcat access log: request/response observed by the container
     |
     +--> Servlet Filters / Spring Security
     |         |
     |         +--> application filter log: request ID, timing at filter
     |         |
     v         v
Spring MVC DispatcherServlet -> Controller -> Service -> Database/HTTP client
                                |
                                +--> business/application logs
     |
     v
Response returns to client through Tomcat, proxy, and network
```

Valid discrepancies may occur:

- The proxy returns **403** due to WAF, so there is **no** Tomcat access log or application log for that request.
- Tomcat rejects a malformed HTTP request **before dispatch**; the app filter/controller does not run.
- Spring Security returns **401/403** inside the filter chain; the Tomcat access log usually still records it if the request reached the container, but an application filter registered **after** the security chain may not run.
- The controller returns **200**, but the proxy fails to finish sending the body because the client disconnects; final metrics at the proxy, Tomcat, and controller log may disagree on duration/bytes.
- The controller logs "started processing" while an async operation/stream has not finished; the access log is written at a different stage.
- A request succeeds across **multiple replicas** and the application log is on pod A while the edge log is at the gateway. A correlation ID/tracing context is needed to link the records.

**Never conclude "the request never happened" just because there is no log in the controller.** First identify which layer the request reached.

## 3. Comparing Server Access Logs and Application Request Logs

| Criterion | Server access log | Application request/business log |
| --- | --- | --- |
| Generated by | Tomcat AccessLogValve, Jetty/Undertow access log, gateway | SLF4J + Logback/Log4j2, filter/interceptor/controller/service |
| Scope | Requests that reached the corresponding HTTP layer | Code/components that executed |
| Typical fields | Time, remote address, method, URI path, HTTP status, bytes, duration | requestId/traceId, route template, service event, outcome, dependency, exception |
| Duration unit | Defined by container/proxy, e.g., Tomcat `%D` is **microseconds** | Measured by code, e.g., `System.nanoTime()` converted to **milliseconds** |
| HTTP result | Can observe the final status at the server layer | An early filter may only see status at filter exit, not necessarily final |
| Sees early-rejected requests? | At container layer: possible; at proxy: depends on hop | Depends on filter order and whether the request entered the app |
| Knows business data? | Usually not | Yes, if code explicitly logs permitted information |
| Includes correlation ID out of the box? | Not guaranteed; must configure pattern/header or tracing | Not guaranteed; must design MDC/tracing |
| Sensitive data risks | Raw URL/query, IP, Referer, cookie, session ID, header | Body, token, secret, PII, exception, user-controlled strings |
| Where is it written? | File/server pipeline or collector configured by container/infrastructure | Console/file/structured JSON/OTLP via logging system |
| Best suited for | HTTP access audit, status, throughput, high-level timing | Business investigation, isolating failing steps, linking trace/span, root cause |

**The same term "access log" can refer to Nginx, Tomcat, or custom middleware written by the dev team.** During incident triage, always specify **which layer's log, which clock, and which fields**.

### 3.1. Access Logs Are Not Business Audit Logs

An HTTP `POST /payments` returning 200 does **not** prove the payment was posted to the ledger or funds were successfully transferred. A request can return 202 while the queued job later fails. If the business requires auditing:

- Record events like `PaymentRequested`, `PaymentAuthorized`, `PaymentSettled` in an appropriate durable audit mechanism.
- Use transactions/outbox/idempotency as needed rather than treating console logs as a transactional database.
- Define principal, tenant, object ID, action, outcome, and timestamp according to privacy policy.
- Specify integrity/retention/access permissions for the audit trail separately from debug logs.

**Access logs are evidence about HTTP**, and do not automatically replace data change history or proof of business completion.

## 4. Tomcat Access Logs in Spring Boot

### 4.1. Enabling Access Logs via application.properties

With **Spring Boot 3.5.x + embedded Tomcat**, use:

```properties
# Local/demo environment example only; choose an approved location for production.
server.tomcat.basedir=./tomcat-demo

server.tomcat.accesslog.enabled=true
server.tomcat.accesslog.directory=logs
server.tomcat.accesslog.prefix=access
server.tomcat.accesslog.suffix=.log

# Create daily files; production requires centralized retention/rotation.
server.tomcat.accesslog.rotate=true
server.tomcat.accesslog.max-days=7

# Use buffered=false only to observe logs quickly in demos;
# buffered=true (default) is generally more efficient under high traffic.
server.tomcat.accesslog.buffered=false

# Method, URL path (without query), status, bytes, and duration (microseconds).
# Trailing token reads X-Request-Id produced by the demo response filter.
server.tomcat.accesslog.pattern=%t %a %m %U %s %b %D %{X-Request-Id}o
```

Key points:

- `server.tomcat.accesslog.enabled` defaults to `false` in Spring Boot 3.5 configuration.
- If `server.tomcat.basedir` is not set, embedded Tomcat may use a temporary directory; the access log file will not necessarily sit next to the source code or JAR.
- `directory=logs` is relative to Tomcat's base dir; with the configuration above, logs are expected under `./tomcat-demo/logs/` relative to the working directory where the app runs.
- `buffered=false` makes file updates easy to observe after each request, but can increase I/O. Production typically uses appropriate buffering and a collector/rotation; **do not treat flushing the log file on every request as mandatory**.
- `max-days=7` only illustrates file lifecycle under Tomcat configuration; enterprises typically handle log aggregation, retention, and legal hold at the infrastructure level.
- These properties are specific to **Tomcat**. If you switch to Jetty or Undertow, they do not automatically configure the new server's access log.
- Depending on deployment, container filesystems may be ephemeral/read-only. Configure a writable path, volume mount, or platform-supported logging pipeline.
- An application can be deployed as a WAR in an external Tomcat; in that case the host Tomcat has its own access log configuration, and you should not assume all embedded Boot server properties take effect.

### 4.2. Understanding Tomcat Pattern Tokens

Tomcat `AccessLogValve` supports patterns; useful tokens include:

| Token | Meaning |
| --- | --- |
| `%t` | Timestamp in Common Log Format |
| `%a` | Remote IP address from Tomcat's perspective (may be a proxy IP) |
| `%m` | HTTP method, e.g., GET |
| `%U` | Request URL path, **excluding query string** |
| `%r` | First line of the request; may contain query/sensitive input |
| `%q` | Query string; **do not enable indiscriminately** |
| `%s` | HTTP response status |
| `%b` | Number of body bytes sent, excluding headers; may be `-` if none sent |
| `%D` | Request processing time in **microseconds** |
| `%T` | Processing time in **seconds** |
| `%F` | Time taken to commit the response (milliseconds) |
| `%I` | Request-layer thread name; not a user/session ID |
| `%X` | Connection status when the response completes |
| `%{X-Request-Id}o` | Value of the `X-Request-Id` response header |
| `%{Some-Header}i` | Value of the specified request header; beware untrusted data |
| `%{attribute}r` | Value of the request attribute, if present |
| `%S` | Session ID — **avoid logging** because it is highly sensitive |

**Specific note on time:** Tomcat's `%D` is in **microseconds**; a value of `2500` corresponds to roughly **2.5 ms**, not 2500 ms. If combined on a dashboard with app logs measured in milliseconds, you must normalize units. For Undertow, Boot documentation states that recording request start time must be enabled to use `%D` timing; servers do not share identical semantics across all tokens.

With the illustrative pattern, a line might **look like**:

```text
[08/Nov/2026:09:10:11 +0700] 127.0.0.1 GET /api/items/42 200 25 4200 79a0b899-1a46-44bf-9dbe-60fe630d3083
```

This is a **format illustration line**, not actual output from the demo, and should not be used as an exact assertion. Timestamp, byte count, duration, response field ordering, and ID all depend on the real request.

### 4.3. Why Not Blindly Enable common/combined Patterns in Production?

The `common` pattern typically includes `"%r"`; `combined` also includes `Referer` and `User-Agent`. These fields may carry:

- Queries containing `token=...`, `password=...`, email addresses, or personal search terms.
- Referer URLs containing password reset codes or client details.
- Client-controlled User-Agent/headers that can cause log injection if collectors/parsers do not handle them safely.
- URL paths containing phone numbers, identifiers, or document names.
- IP addresses, which may constitute personal data under organizational legal policies.
- Cookie/session IDs, Authorization headers, or API keys if someone misconfigures a custom pattern.

Therefore, **do not log request bodies, Authorization, Cookie, Set-Cookie, `%S`, raw queries, or all headers by default**. The illustrative pattern intentionally chooses `%m` + `%U` and omits `%q`/`%r` to reduce query leak risk; **`%U` still contains the path** and still requires checking for PII in route/path design.

If you need to log a route containing an ID, application logs can use a **route template** like `/api/items/{id}` instead of the real path `/api/items/42`. At the standard Tomcat AccessLogValve layer, `%U` is unaware of Spring MVC route templates; achieving similar normalization in access logs requires controlled processing/normalization infrastructure or avoiding raw path storage.

## 5. Application Logs: SLF4J, Logback, and MDC

Spring Boot typically uses the **SLF4J facade** with Logback by default via starters. Inside a service/controller:

```java
private static final Logger log = LoggerFactory.getLogger(ItemService.class);

log.info("item.lookup result={} type={}", "found", "demo");
log.warn("inventory.lookup upstreamStatus={}", 503);
log.error("item.lookup failed", exception);
```

This is a **snippet** requiring valid imports for `org.slf4j.Logger`, `LoggerFactory`, the `ItemService` class, and the `exception` variable. The `{}` form is **parameterized logging**, avoiding manual string concatenation and avoiding string construction when the log level is disabled (for suitable APIs/workloads). It does **not automatically sanitize personal data, escape log injection, or perform redaction**. Pass only carefully selected values to logs.

Common log levels:

- **ERROR:** severe failures affecting a request/job, not simply every HTTP 4xx.
- **WARN:** abnormal/degraded behavior, retries, or states needing attention; avoid logging the same error repeatedly at every layer.
- **INFO:** application lifecycle, significant business events, request summaries when permitted by policy; high traffic should use sampling/quotas.
- **DEBUG:** package-level diagnostic details, enabled only for a limited duration when authorized.
- **TRACE:** deep detail; easily grows huge and exposes data, enable only under strict control.

### 5.1. Mapped Diagnostic Context (MDC)

SLF4J `MDC` lets you attach key-value pairs to the **context of the logging thread**:

```java
MDC.put("requestId", "some-id");

try {
    log.info("processing stage=verify");
} finally {
    MDC.remove("requestId");
}
```

Requires importing `org.slf4j.MDC` and an initialized `log`. A Logback pattern can print MDC:

```properties
logging.pattern.console=%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level [%thread] req=%X{requestId:-none} %logger{36} - %msg%n
```

While handling a request with MDC `requestId`, the log may contain:

```text
2026-11-08T09:10:11.123+07:00 INFO  [http-nio-8080-exec-2] req=79a0b899-1a46-44bf-9dbe-60fe630d3083 c.example.demo.ItemController - item.lookup outcome=found
```

This is only a **presentation example**, not fixed output; UUID, thread name, timing, and logging class vary.

**MDC is not session storage.** It does not store HTTP session state, does not authenticate users, and does not propagate automatically across threads. If a pooled thread serves request A and then B, forgetting `MDC.remove` can cause **request B to inherit request A's ID**. With async/reactive/virtual threads, propagation requires explicit mechanisms; never assume ThreadLocal transfers context automatically.

### 5.2. Request ID, Correlation ID, and Trace ID Are Not Synonymous

| Field | Meaning | Example usage |
| --- | --- | --- |
| `requestId` | ID for **a specific HTTP request** at app/gateway | Joining a Tomcat access line with app logs for the same request |
| `correlationId` | ID linking a group of related tasks/requests by convention | A business workflow spanning multiple services |
| `traceId` | ID for a distributed trace per tracing stack | Linking spans in OpenTelemetry/Micrometer |
| `spanId` | ID of a unit of work/span within a trace | Investigating dependency/latency inside each service |
| `sessionId` | Credential/identifier of an HTTP session | **Do not use as a public correlation ID** |

In Spring Boot with **Micrometer Tracing**, trace/span IDs can be placed into log correlation automatically by the framework. If the system already uses W3C `traceparent` and OpenTelemetry, leverage standardized tracing rather than inventing a parallel mechanism that confuses correlation. Do not replace request IDs with session IDs, tokens, or user emails.

**Untrusted input:** `X-Request-Id` from the Internet is client-controlled data that can be spoofed. In enterprise environments with a trusted gateway, you can adopt a policy: the edge validates length/charset and issues a new ID or propagates a validated ID. Do not accept unbounded values, CR/LF characters, or PII directly into MDC/logs; this risks log injection and index/cardinality explosion.

The lab exercise will **always generate a UUID on the server** and write the `X-Request-Id` response header. When going through a real gateway, agree on which component owns the ID so the proxy and app do not generate two unrelated IDs.

### 6.5. Filter Generating requestId, Setting Response Header, and MDC

**`src/main/java/com/example/demo/RequestIdLoggingFilter.java`**

```java
package com.example.demo;

import java.io.IOException;
import java.util.UUID;
import java.util.concurrent.TimeUnit;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import org.springframework.web.servlet.HandlerMapping;

@Component
public class RequestIdLoggingFilter extends OncePerRequestFilter {

    private static final Logger log =
        LoggerFactory.getLogger(RequestIdLoggingFilter.class);

    private static final String REQUEST_ID_KEY = "demo.requestId";

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain) throws ServletException, IOException {

        // Do not directly trust client-supplied X-Request-Id.
        String requestId = UUID.randomUUID().toString();
        long startNanos = System.nanoTime();

        request.setAttribute(REQUEST_ID_KEY, requestId);
        response.setHeader("X-Request-Id", requestId);

        // MDC for the thread executing the filter.
        String previous = MDC.get("requestId");
        MDC.put("requestId", requestId);

        boolean threw = false;
        try {
            chain.doFilter(request, response);
        } catch (IOException | ServletException | RuntimeException | Error ex) {
            threw = true;
            throw ex;
        } finally {
            long elapsedMs = TimeUnit.NANOSECONDS.toMillis(
                System.nanoTime() - startNanos
            );

            Object pattern = request.getAttribute(
                HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE
            );
            String route = pattern instanceof String
                ? (String) pattern
                : "unmatched";

            // This is when the chain returns to the filter, not guaranteed to be
            // the final status/total time for async or error dispatches.
            log.info(
                "http.filter.exit method={} route={} " +
                "statusAtExit={} durationMs={} asyncStarted={} threw={}",
                request.getMethod(),
                route,
                response.getStatus(),
                elapsedMs,
                request.isAsyncStarted(),
                threw
            );

            if (previous == null) {
                MDC.remove("requestId");
            } else {
                MDC.put("requestId", previous);
            }
        }
    }
}
```

**Why is it designed this way?**

1. `UUID.randomUUID()` generates a new ID for each request passing through the filter. A request ID is **not a security credential** and does not replace `traceId`/`spanId`, authentication, or session ID.
2. `request.setAttribute(...)` lets components handling the same request read the ID if needed. The `X-Request-Id` response header lets clients report the ID on errors, and Tomcat pattern `%{X-Request-Id}o` can log the same value.
3. **Do not accept raw inbound `X-Request-Id` from the Internet**: if propagation is desired, enforce a trusted gateway policy, validate charset/length, and distinguish edge identifiers from local IDs.
4. `MDC.put` attaches the request ID to `log.info(...)` calls running on the **same thread**. `finally` restores the previous MDC or removes the ID to prevent leaking to the next request on a pooled worker thread.
5. `System.nanoTime()` is suitable for measuring elapsed duration; avoid subtracting `System.currentTimeMillis()` because wall-clock time can jump.
6. `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE` provides the route template after Spring MVC mapping, such as `/api/items/{id}` instead of the raw path `/api/items/42`. For requests blocked before DispatcherServlet or unmatched routes, the attribute may be absent → log `unmatched`.
7. `statusAtExit` is named intentionally: it is the **status when the filter finishes**, not necessarily the final response status if an async/error dispatch occurs or the container handles an exception afterward.
8. `threw=true` indicates the filter chain exited with an exception thrown outward; it does not automatically mean the final status is 500. A `ResponseStatusException` may be resolved by Spring MVC without escaping the filter, yielding `threw=false` even for a 4xx response.
9. Never log raw URL queries, request/response bodies, headers, principal names, cookies, or tokens. Personally identifiable information requires separate policies and minimization.
10. Because it is a `@Component`, this filter is auto-registered in a Spring Boot Servlet app. When Spring Security is present, filter registration order determines whether the filter sees security-rejected requests; do not assume every request reaching the container passes through this filter.

**Intentional limitation:** this example is for **synchronous** processing. An async request can cause `chain.doFilter` to return before the body finishes sending; thus `durationMs` here is **time until the filter chain exits**, not total response duration. For `Callable`, `DeferredResult`, `StreamingResponseBody`, and SSE, you must design a completion logger using Servlet `AsyncListener` / lifecycle-aware observability instrumentation. When an exception is unresolved by Spring and triggers an error dispatch, `response.getStatus()` in `finally` may not yet reflect the final 500. **Tomcat access logs** are better suited for total container time, though async and disconnect semantics still matter.

### 6.6. Controller with Safe Business Events

**`src/main/java/com/example/demo/ItemController.java`**

```java
package com.example.demo;

import java.util.Map;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

@RestController
public class ItemController {

    private static final Logger log =
        LoggerFactory.getLogger(ItemController.class);

    @GetMapping("/api/items/{id}")
    public Map<String, Object> item(@PathVariable long id) {
        if (id != 42) {
            log.info("item.lookup outcome=not_found");
            throw new ResponseStatusException(
                HttpStatus.NOT_FOUND, "Item not found"
            );
        }

        log.info("item.lookup outcome=found");
        return Map.of("id", id, "status", "available");
    }

    @GetMapping("/api/conflict")
    public void conflict() {
        log.warn("demo.conflict outcome=rejected");
        throw new ResponseStatusException(
            HttpStatus.CONFLICT, "Conflict for demo"
        );
    }

    @GetMapping("/api/ping")
    public String ping() {
        return "pong";
    }
}
```

This is demo data, not a real database or inventory system. The controller does not log `id`; if the business decides to log object IDs, determine whether they are PII/secrets, whether they can be pseudonymized, and who is authorized to view them.

**Expected results by URL:**

| URL | HTTP status | Main content | Controller app log |
| --- | --- | --- | --- |
| `GET /api/items/42` | 200 | JSON containing `"id":42`, `"status":"available"` | `item.lookup outcome=found` |
| `GET /api/items/99` | 404 | Error body per Spring MVC/Boot configuration | `item.lookup outcome=not_found` |
| `GET /api/conflict` | 409 | Error response per Spring MVC | `demo.conflict outcome=rejected` |
| `GET /api/ping` | 200 | `pong` | No separate business event, only filter log |
| `GET /api/unknown` | 404 | Unmatched route | No controller log; filter route `unmatched` |

Do not hardcode an exact JSON error body: Spring Boot defaults may vary the error structure based on `Accept`, error settings, and version. The status codes above are the key contract to test.

### 7.2. Making a Request and Reading the Response Header

```bash
curl -i http://localhost:8080/api/items/42
```

Expect a response with **status 200** and a header like:

```http

```

The ID above **only illustrates the UUID format**; each real request will produce a different value. Browsers can read this header on same-origin responses; cross-origin frontends need CORS `Access-Control-Expose-Headers` if JavaScript needs to read the custom response header on an allowed origin per the specific CORS policy.

In the console application log, you will normally see two lines with the same `req=...`:

```text
... INFO  req=79a0b899-... ItemController - item.lookup outcome=found
... INFO  req=79a0b899-... RequestIdLoggingFilter - http.filter.exit method=GET route=/api/items/{id} statusAtExit=200 durationMs=... asyncStarted=false threw=false
```

This is a **shape illustration**, not exact stdout. In code, the full request ID is printed by `logging.pattern.console`, and specific calls have different latencies.

The Tomcat access log under `./tomcat-demo/logs/` may contain a line:

```text
[...timestamp...] 127.0.0.1 GET /api/items/42 200 25 4300 79a0b899-1a46-44bf-9dbe-60fe630d3083
```

Do not compare `25` or `4300` as constants. Byte counts and microseconds depend on the actual response; both the Tomcat access log and application log carry the **same response X-Request-Id** generated by the filter for the request it handled.

**Analyzing timing differences:** if Tomcat logs `%D = 4300` microseconds, that equals **4.3 ms**; the filter might log `durationMs=3` due to different start/end points and millisecond truncation. Do not treat small differences as errors.

### 7.5. Why Not Test Against a "Fixed" Log Line?

Access logs contain variable timestamps, request IPs, byte counts, durations, and IDs. Unit tests should not assert an entire log string as a rigid golden string. Instead:

- Verify **HTTP behavior** with request integration tests.
- Verify the response `X-Request-Id` is valid and changes across requests.
- In an isolated test environment, verify the access log file contains the corresponding method/path/status/id (possibly requiring flush synchronization/timeouts); avoid ordering assumptions across parallel requests.
- If testing app log fields is mandatory, use a test appender or mock log collector rather than parsing full stdout with timestamps and thread names.
- Test log aggregation through a production-like pipeline, because local file config does not prove the collector can read the logs.

## 8. Real HTTP Testing with JDK HttpClient + SpringBootTest

Use `@SpringBootTest(webEnvironment=RANDOM_PORT)` to start **real Tomcat**, not just `MockMvc`. Tests require no accounts or external network services because requests hit a local random port.

**`src/test/java/com/example/demo/HttpLogsApplicationTest.java`**

```java
package com.example.demo;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.UUID;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;

import static org.junit.jupiter.api.Assertions.*;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class HttpLogsApplicationTest {

    @LocalServerPort
    int port;

    private final HttpClient client = HttpClient.newBuilder()
        .followRedirects(HttpClient.Redirect.NEVER)
        .build();

    private final ObjectMapper json = new ObjectMapper();

    private URI uri(String path) {
        return URI.create("http://127.0.0.1:" + port + path);
    }

    private HttpResponse<String> get(String path) throws Exception {
        return client.send(
            HttpRequest.newBuilder(uri(path)).GET().build(),
            HttpResponse.BodyHandlers.ofString()
        );
    }

    private String requestId(HttpResponse<?> response) {
        String value = response.headers()
            .firstValue("X-Request-Id").orElseThrow();
        UUID.fromString(value);  // Fail if format is not a UUID.
        return value;
    }

    @Test
    void successHasServerGeneratedIdAndExpectedBody()
            throws Exception {
        HttpResponse<String> response = get("/api/items/42");

        assertEquals(200, response.statusCode());
        requestId(response);
        JsonNode body = json.readTree(response.body());
        assertEquals(42, body.get("id").asInt());
        assertEquals("available", body.get("status").asText());
    }

    @Test
    void missingItemHas404AndRequestId() throws Exception {
        HttpResponse<String> response = get("/api/items/99");

        assertEquals(404, response.statusCode());
        requestId(response);
    }

    @Test
    void conflictHas409AndRequestId() throws Exception {
        HttpResponse<String> response = get("/api/conflict");

        assertEquals(409, response.statusCode());
        requestId(response);
    }

    @Test
    void aNewRequestGetsANewId() throws Exception {
        String first = requestId(get("/api/ping"));
        String second = requestId(get("/api/ping"));

        assertNotEquals(first, second);
    }

    @Test
    void untrustedInboundRequestIdIsNotReflected()
            throws Exception {
        HttpRequest request = HttpRequest.newBuilder(uri("/api/ping"))
            .header("X-Request-Id", "client-tried-to-control-the-id")
            .GET()
            .build();

        HttpResponse<String> response = client.send(
            request, HttpResponse.BodyHandlers.ofString()
        );

        assertEquals(200, response.statusCode());
        String serverId = requestId(response);
        assertNotEquals("client-tried-to-control-the-id", serverId);
    }

    @Test
    void unmatchedRouteStillGetsARequestId()
            throws Exception {
        HttpResponse<String> response = get("/api/unknown");

        assertEquals(404, response.statusCode());
        requestId(response);
    }
}
```

Run:

```bash
mvn test
```

Or `./mvnw test` if the Maven Wrapper is present. With the project and configuration in this lesson, **six tests are expected to pass**. This is a test design for learners to execute, **not a claim that tests were compiled/run in a specific repository**.

**What do the tests prove?**

- Embedded Tomcat actually handles the HTTP requests.
- Responses for 200/404/409 statuses include the filter-generated `X-Request-Id`.
- A client sending a spoofed `X-Request-Id` still receives a server-generated ID.
- Each new HTTP request receives a distinct ID.
- The controller returns JSON matching the specified schema.

**What do the tests NOT prove?**

- They **do not assert the Tomcat access log file** or console JSON output, because those belong to the environment/filesystem/logger appender and have variable timing/rotation. Verify those using the commands in Section 7 or write an integration fixture with a dedicated working-directory/tomcat-basedir and test appender.
- They do not prove a proxy forwarded/logged the correlation ID properly, since the test calls Tomcat directly.
- They do not cover Spring Security, Servlet async/error dispatches, streaming, WebFlux, or multi-replica aggregation.
- They do not prove the log collector receives records across host/container restarts.

If automated testing of the access log file is required, use a **dedicated temp directory for the test context**, set `server.tomcat.accesslog.buffered=false` in the test, send an HTTP request, wait within a bounded timeout for the file to appear/flush, and search for the **specific ID** instead of assuming line position or timestamp. Do not run parallel Maven processes against the same fixed `basedir`; Tomcat access logs may conflict or rotate unexpectedly.

## 9. Logging Request Completion with Asynchronous or Streaming Processing

The filter in the example only measures until `chain.doFilter` returns. With async processing, that can differ **greatly** from when the client finishes receiving the response.

### 9.1. Three Processing Styles with Different Lifecycles

| Style | Example | Is filter `finally` completion? |
| --- | --- | --- |
| Synchronous MVC | Controller returns DTO/String, non-async | Usually near the end of request dispatch; some error flows still differ |
| Servlet async | `Callable<T>`, `DeferredResult<T>` | **Not necessarily**; the request may still be running |
| Streaming MVC | `StreamingResponseBody`, `SseEmitter` | **Not necessarily**; the stream can be long-lived |
| WebFlux/Reactor | `Mono`/`Flux` on Netty | Does not use this Servlet filter; lifecycle follows reactive publisher |

In Spring MVC, `OncePerRequestFilter` provides two important hooks:

```java
// Illustrative snippet; place inside filter subclass when appropriate.
@Override
protected boolean shouldNotFilterAsyncDispatch() {
    return false;
}

@Override
protected boolean shouldNotFilterErrorDispatch() {
    return false;
}
```

By default these hooks return `true` in Spring Framework, meaning the filter **does not automatically re-run on async/error dispatches** without application configuration. However, changing them to `false` does **not automatically produce "log exactly once when the response finishes"**. It simply allows the filter to run on those dispatches; reusing the earlier code as-is could generate multiple request IDs and multiple log summaries for a single request.

### 9.2. Designing an Async Completion Logger

To emit a **request.completed** event once Servlet async truly finishes, design it as follows:

1. On the **first dispatch**, create a state object attached to a request attribute containing `requestId`, `startNanos`, and an `AtomicBoolean logged` flag.
2. If `request.isAsyncStarted()` when the filter returns, register an `AsyncListener` on `request.getAsyncContext()`. Use `onComplete` to log the summary **once** via `logged.compareAndSet(false, true)`.
3. Use `onError` and `onTimeout` to record failure/timeout, noting that status may not yet be final inside the callback; track separate state if needed and log completion when the request closes.
4. If `onStartAsync` creates a new cycle, re-register the listener per your application's Servlet API lifecycle.
5. For sync requests, log when the filter chain actually finishes; for async requests, do not log completion early.
6. In callbacks on another thread, **re-establish requestId/trace context for logging** and clean up in `finally`; never assume MDC follows automatically.
7. Handle error dispatches and client disconnects, avoiding double-logging when multiple completion paths race.
8. Record method/route template/status/bytes according to what can be reliably determined, avoiding calling a response "200 completed" if the stream broke after commit.
9. Test `Callable`, `DeferredResult`, SSE, client disconnects, and timeouts against a real embedded container, not just a sync MockMvc GET.
10. For complex production systems, consider **Micrometer Observation/Tracing** or gateway/server-provided instrumentation instead of writing a large custom filter that is hard to verify.

**Do not copy isolated `AsyncListener` snippets** while ignoring dispatch/error lifecycles: an implementation missing `onStartAsync` or logging in both `onError` and `onComplete` can emit duplicate or mistimed logs.

### 9.3. MDC and Multithreaded Processing

A single request can span:

```text
HTTP thread A -> filter MDC=requestId=R
    |
    +-> @Async executor thread B -> no MDC R by default
    |
    +-> DeferredResult callback thread C
    |
    +-> Servlet async dispatch thread D
```

Because `MDC` is thread-bound, logs on B/C/D may lack the request ID, or retain stale values if copied manually without cleanup. When propagation is needed:

- Use context-propagation/tracing infrastructure supported by Spring/Micrometer for your stack; verify `TaskDecorator` or framework context propagation settings.
- Do not pass a mutable `MDC.getCopyOfContextMap()` across multiple async tasks and forget to restore/clear it.
- Avoid treating `InheritableThreadLocal` as a universal solution for thread pools.
- With Reactor/WebFlux, prefer Reactor Context + Micrometer context propagation. Do not use `HttpServletRequest`/`OncePerRequestFilter` for Netty WebFlux.
- With virtual threads (Java 21+), ThreadLocal has different performance semantics, but **a thread is not a session and is not automatically a distributed trace**.

**Conclusion for async:** the duration measured by a filter **does not necessarily match** the total time observed by access logs/containers or end users.

## 10. Structured JSON Logging in Spring Boot

Text consoles are easy to read during development; production logging pipelines usually prefer **one JSON object per event**. Spring Boot 3.5 has built-in structured logging support for **ECS, GELF, and Logstash** (depending on configuration/version). An example configuration **replacing** `logging.pattern.console`:

```properties
# USE AS AN ALTERNATIVE; DO NOT KEEP SIMULTANEOUSLY WITH
# logging.pattern.console from Section 6.
logging.structured.format.console=ecs
```

In ECS output, log events include timestamp, level, logger, message, service, and MDC keys per Spring Boot's serializer. With MDC `requestId`, that field can appear in the structured log:

```json
{
  "@timestamp": "2026-11-08T09:10:11.123+07:00",
  "log": { "level": "INFO", "logger": "com.example.demo.RequestIdLoggingFilter" },
  "service": { "name": "http-logs-demo" },
  "message": "http.filter.exit method=GET route=/api/items/{id} statusAtExit=200 durationMs=3 asyncStarted=false threw=false",
  "requestId": "79a0b899-1a46-44bf-9dbe-60fe630d3083"
}
```

This is **illustrative JSON** showing useful fields, not a strictly guaranteed schema or exact line output. The real ECS serializer may place level/logger in different structures and add `process`/`ecs.version` or other metadata. **Do not write tests comparing this sample JSON byte-for-byte with real output**.

Advantages of JSON:

- Collectors parse fields cleanly without fragile regex trying to locate threads/timestamps.
- Fast querying by `requestId`, `traceId`, `route`, `status`, and error type.
- Easily attach service name, env, deployment version, and pod/host without repeating them in every message.
- Enables shared schemas and dashboards; compare p95 latency by route template.

Disadvantages and responsibilities:

- JSON does **not automatically redact** tokens/PII.
- MDC will not appear in every formatter/collector if misconfigured; test end-to-end.
- Writing entire request headers/bodies as JSON still creates massive size and data-leak risks.
- Client-controlled log fields can cause **high cardinality**, injection, or index overload.
- Switching from text to JSON can break existing parsers; roll out with consumer agreement and versioning.

### 10.1. SLF4J Fluent Key-Value Logging

In SLF4J 2, you can attach structured fields separately from the text message:

```java
log.atInfo()
   .addKeyValue("route", "/api/items/{id}")
   .addKeyValue("status", 200)
   .addKeyValue("result", "found")
   .log("http.request");
```

This is a snippet in a class that has `log`. Spring Boot's structured logging formatter can include these fields in JSON. When using a normal console pattern, how key-values render depends on the Logback layout; do not assume a JSON property is always enabled.

**Do not use user IDs or raw URIs as field/key names.** Pick a fixed schema with reasonable cardinality.

## 11. Micrometer Observation, Distributed Tracing, and Correlation IDs

When a system spans multiple services:

```text
Client -> API Gateway -> Service A -> Service B -> Database
            |               |           |
         access log       app logs    app logs
            |               |           |
           end-to-end trace ID + distinct span IDs
```

A request ID generated at Service A **only** links logs within Service A and its Tomcat instance. To follow the entire distributed call chain, use OpenTelemetry/Micrometer Tracing and a **standard trace context** like W3C `traceparent` propagated across HTTP clients.

Spring Boot Actuator/observability includes HTTP server/client instrumentation, but you must configure appropriate dependencies, exporters, and sampling. Never assume that merely adding `spring-boot-starter-actuator` provides a complete trace exporter.

In Spring Boot when **Micrometer Tracing** is configured, the default log correlation ID relies on MDC `traceId` and `spanId`. You can customize it via `logging.pattern.correlation` if needed. A service may also emit `X-Request-Id` per gateway contract; define clearly:

- Which ID identifies **a single incoming HTTP request**?
- Which ID identifies the **entire distributed trace**?
- Which ID is issued by a **trusted gateway**?
- Are IDs allowed to be returned to clients/partners?
- Does the gateway strip/normalize untrusted trace context and request IDs?
- When sampling drops a trace, which ID do application logs retain to aid investigation?
- When an HTTP client retries or fans out, does each outbound HTTP exchange get its own span ID or which request ID?

**Relying solely on text logs and ThreadLocal MDC will not produce a complete distributed trace.** Combine span events, metrics, and trace exporters under appropriate data, token security, and sampling policies.

### 11.1. Correlating Access Logs with App Logs

Example investigation:

1. A customer provides the `X-Request-Id` from their response: `79a0...`.
2. Search the Tomcat access log for that ID to inspect `GET /api/items/42`, `status=200`, and `%D`.
3. Search console/structured logs with the same `requestId` to view `http.filter.exit` and `item.lookup outcome=found`.
4. If app logs include `traceId`, open the trace to inspect HTTP/DB spans.
5. If the request is missing from Tomcat, search edge/gateway access logs by ID or time window/user-safe metadata.
6. If the proxy shows a different status, check upstream status, retries, timeouts, circuit breakers, or client disconnects.
7. If logs are still missing, check log collector backpressure/sampling/retention and the active version/instance.

Do not use session IDs or raw bearer tokens to correlate logs. Those values are secrets and can be replayed in attacks.

## 12. Timing Breakdown: Why Do Two Logs Report Different Durations?

Suppose a request travels through a proxy:

```text
Client TCP/TLS -> Edge queue -> Proxy to upstream
                      |
                      v
                Tomcat request
                      |
                Filter begins
                      |
                Controller -> DB
                      |
                Filter exits (app durationMs)
                      |
                Tomcat completes (Tomcat %D)
                      |
                Proxy sends bytes (proxy request_time)
                      |
                Client receives final byte
```

Possible observations:

- **Filter duration = 15 ms**, **Tomcat %D = 17000 µs (~17 ms)**, **proxy time = 25 ms**: reasonable because measurement boundaries differ and include network/queue/serialization overhead.
- **App log = 2 ms**, **Tomcat = 6 s**: streaming/async body may continue after filter exit, or slow client, blocking output, compression, or container overhead.
- **Proxy = 10 s**, **Tomcat = 20 ms**: possible upstream connect queue, slow client download, proxy buffering, retries, or proxy timeout; inspect the exact proxy fields.
- **Tomcat 499?** 499 is typically an **Nginx-specific** code for client-closed request; Tomcat does not necessarily use 499. Do not equate proxy codes with HTTP statuses returned by Spring controllers.
- **HTTP 200 yet client reports failed download**: the server committed 200 and the stream failed mid-transfer; inspect bytes sent, connection status, exceptions/cancellations, and client-side metrics.

Do not rely solely on mean duration; measure **p95/p99 by route**. However, logs do not replace **histogram metrics**: computing latency statistics from full access logs can be storage-heavy and biased by sampling/retention. Metrics are suited for SLOs; traces and logs are suited for root-cause diagnosis.

### 12.1. HTTP/2, Keep-Alive, and Virtual Threads

HTTP/1.1 keep-alive and HTTP/2 multiplexing allow multiple requests over a single connection. **Connection ID is not request ID**, client IP/port cannot uniquely distinguish requests, and thread names do not stably represent a user. With Java 21 virtual threads, each request may run on a short-lived thread, making thread names even less valid for linking business work across requests.

## 13. Proxies, Forwarded Headers, and Accurate Client IP

Behind a reverse proxy, `request.getRemoteAddr()` or Tomcat `%a` may be the Nginx/gateway IP. Headers such as:

```http
Forwarded: for=203.0.113.10;proto=https;host=api.example.com
X-Forwarded-For: 203.0.113.10
X-Forwarded-Proto: https
X-Forwarded-Host: api.example.com
```

are only trustworthy if **authorized proxies** strip/overwrite client-sent values, network rules block direct backend access, and Spring/the container are properly configured.

In Spring Boot, options include:

```properties
# Enable only with a trusted proxy and header verification policy.
server.forward-headers-strategy=framework
```

Or `native` depending on Tomcat/Undertow/Jetty, with proper trusted proxy IP/network configuration. **Do not** enable `framework` to blindly trust arbitrary `X-Forwarded-For` from the Internet for rate limiting, geolocation access control, or audit identity. Tomcat access logs have specific settings around request attributes/RemoteIpValve; if logging the real client IP is required, check how the access log records attributes after forwarded metadata processing. Never assume setting one property makes all access logs, security principals, and edge IPs agree.

**Recommendation:** in logs, distinguish `peerIp` (IP of the directly connected hop) from `clientIp` (verified through the trust chain). Apply retention/redaction to IP addresses per data protection policy. Do not log entire unnormalized `X-Forwarded-For` chains, which are vulnerable to spoofing and injection.

### 13.1. Edge Request ID vs. Application Request ID

If ingress already issues `X-Request-Id`, for example:

```text
Client -> Edge [requestId=EDGE-1]
              -> Spring [requestId=APP-9]
```

then the two records cannot be joined automatically on a single key. Three implementation options:

1. **Use the edge ID, verified/normalized at the trust boundary** (edge strips inbound header, generates a fresh ID, app trusts only the trusted hop).
2. **Use two differently named fields**: `edgeRequestId` and `appRequestId`; the app may emit both via headers/tracing when permitted.
3. **Use distributed tracing**: `traceId` across services, `spanId` per hop, and local request ID for in-process investigation.

The demo chooses the simplest approach: **the app generates a UUID** to join Tomcat and app logs. This only guarantees correlation **inside the app**; production must align policies with the gateway to correlate from the edge.

## 14. Sensitive Data and Log Injection Risks

### 14.1. Values That Should Never Be Logged Raw

- `Authorization: Bearer ...`, Basic credentials, API keys.
- `Cookie`, `Set-Cookie`, `JSESSIONID`, and session identifiers.
- Raw request/response bodies containing passwords, OTPs, payment cards, addresses, health records, or PII.
- Password reset URLs, magic links, OAuth `code`/`state`, query tokens.
- Full request line `%r`, raw query `%q`, Referer, and User-Agent without an approved policy.
- HTTP client/dependency headers containing secrets or cross-tenant data.
- Stack traces containing URLs/tokens in exception messages thrown by external libraries.
- Unvalidated dynamic user input, especially strings with CR/LF, control characters, or ambiguous Unicode.

Never assume "we have a JSON logger" means all fields are sanitized. Data can still leak via collectors, dashboards, retention, exports, and backups.

### 14.2. When User/Tenant IDs Are Needed for Investigation

If an identity field is genuinely needed:

- Log only an **authenticated internal ID** or pseudonymized value (if required by policy), never `?user=...` from the client.
- Never log passwords, cookies, or tokens.
- Avoid putting IDs into high-cardinality **metric labels**; logs and metrics have different strategies.
- Enforce log viewer access controls, encryption in transit/at rest, retention, and policy-driven deletion.
- For broad analytics, aggregate/anonymize; log storage remains a sensitive data system.
- For critical security events, write an **audit record with dedicated integrity/retention**, rather than relying solely on text access logs.

### 14.3. Log Injection

A client can send a parameter containing newlines or control characters. If code does:

```java
// ANTI-PATTERN — do not use in production:
log.info("User said: " + request.getParameter("message"));
```

some downstream parsers can be tricked into interpreting multiple lines or forged fields. Parameterized logging `{}` **does not automatically prevent** newlines or log-forging characters in data. Select fields carefully, enforce length limits, encode/escape or strip control characters, and use an appropriate structured logger. Do not concatenate URLs/headers/bodies into logs by default.

### 14.4. Body Logging Hurts Performance and Security

Spring's `CommonsRequestLoggingFilter` and `ContentCachingRequestWrapper` can help inspect portions of payloads in diagnostic environments, but understand their behavior:

- The caching wrapper retains only **bytes that have already been read**, not necessarily the entire body at filter entry.
- Logging payloads can expose passwords, file uploads, or PII.
- Improper buffering/teeing streams can leave the request body unreadable by controllers or multiply memory usage.
- Response streaming/SSE can stall if a filter buffers the body just to log it.
- Requests can be huge or slow to finish; logging full bodies creates DoS risks and storage costs.
- Production debugging should favor **safe metadata**, tracing spans, and policy-approved sampling rather than app-wide payload dumps.

If capturing bodies for investigation is formally required, enforce route/field allowlists, size limits, redaction, expiration times, approval workflows, testing on synthetic data, and post-incident cleanup.

## 15. Logs and Exceptions: Avoiding Double-Counting 4xx/5xx Errors

Suppose `GET /api/items/99` is a business non-existent item. It returns 404, yet if every 404 is logged at ERROR with a stack trace, dashboards may report "critical system failure" simply because users queried non-existent IDs.

A generally useful design:

| Scenario | HTTP status | Reasonable app log level | Metrics/SLO |
| --- | --- | --- | --- |
| Successful GET | 200 | Optional INFO summary or sampled | Counting + latency |
| Validation error | 400 | INFO/DEBUG, no sensitive raw input | 4xx rate |
| Anonymous needing auth | 401 | INFO/WARN depending on security alerting | Auth reject rate |
| Insufficient permission | 403 | WARN/INFO + security audit per policy | Security denials |
| Not found | 404 | INFO/DEBUG if expected; WARN if anomalous | 4xx route distribution |
| Business conflict | 409 | INFO/WARN per domain | Conflict rate |
| Rate limited | 429 | INFO/WARN, correlation | Rate limit metrics |
| Dependency failure | 502/503/504 | WARN/ERROR depending on impact | Dependency SLO |
| Unhandled server error | 500 | ERROR at **one place** with reliable context | 5xx error budget |

**Avoid logging the same exception redundantly across controller, service, filter, and global handler** as four ERROR stack traces for a single failed request. Designate one error-log owner; other layers can add supplemental context if needed without repeating full stack traces.

In the sample application filter, `threw` only indicates an exception escaped the filter chain, not the error class; do not print exception messages into request summaries. Handle exceptions in `@ControllerAdvice`/error handling with proper schemas, redaction, and classification.

## 16. How Jetty, Undertow, and WebFlux Access Logs Differ

### 16.1. Undertow

Spring Boot provides dedicated properties:

```properties
# Use only when runtime actually uses Undertow.
server.undertow.accesslog.enabled=true
server.undertow.accesslog.pattern=%t %a %r %s (%D milliseconds)
server.undertow.options.server.record-request-start-time=true
```

Per Spring Boot documentation, using Undertow `%D` to measure processing time requires enabling request start-time recording. **Units do not match Tomcat by default**: this example explicitly labels milliseconds for Undertow. Do not copy Tomcat patterns/properties to Undertow assuming identical behavior.

### 16.2. Jetty

A reference configuration:

```properties
# Only for apps where Jetty replaced Tomcat.
server.jetty.accesslog.enabled=true
server.jetty.accesslog.filename=/var/log/jetty-access.log
```

The path is a production-style example requiring volumes/permissions, not a file guaranteed to exist on every machine. Jetty has its own APIs/patterns/rotation; check documentation for your exact version.

### 16.3. Spring WebFlux / Reactor Netty

When using `spring-boot-starter-webflux` on Reactor Netty without a Servlet engine, `server.tomcat.accesslog.*` has **no** effect. Reactor Netty supports its own access logs and options/instrumentation depending on version. Do not use `jakarta.servlet.Filter` or `OncePerRequestFilter` to "log all WebFlux requests" on Netty; use `WebFilter`, Reactor Context, observations/tracing, and appropriate transport logging.

**Beware `wiretap`:** Reactor Netty wiretap can log low-level data, headers/bodies, risking secret exposure and performance degradation. It is not a safe default access log for production. Enable it strictly for limited durations in authorized environments.

## 17. Production Logging Operations: Volume, Rotation, Retention, and Sampling

### 17.1. Separating Human-Facing and Machine-Facing Logs

A common design:

- **Access logs**: used for HTTP status/latency/bytes and request triage, sometimes routed to a separate index with shorter retention.
- **Application/business logs**: structured events and errors tagged by service/environment/version.
- **Security/audit logs**: authentication/authorization-sensitive actions under strict access and integrity controls.
- **Metrics**: request rate, error rate, p95/p99 latency, and dependency stats (using histograms/counters).
- **Traces**: spans showing request traversal across services, typically sampled.

Do not use 100% INFO request logs as a substitute for metric counters/histograms under high request rates. You can sample successful request summaries while retaining error and security events as required by compliance and SLOs; account for sampling bias during data analysis.

### 17.2. Running on Docker/Kubernetes

In container runtimes, console stdout/stderr is generally collected cleanly by the platform; files under `./tomcat-demo/logs` may **not be part of that pipeline**. Options:

1. Mount a volume/sidecar collector to ship Tomcat access logs.
2. Rely on infrastructure-collected web server/gateway access logs combined with app structured logs.
3. Configure access logs to feed into a centralized logging pipeline via a platform-supported method (avoid unapproved file-descriptor hacks).
4. If Tomcat logs are unnecessary because gateway logs already satisfy observability needs, consciously decide coverage/sampling rather than duplicating logs across all three layers without accounting for cost.

Monitor disk quotas, log buffers, write errors, rotation, retention, and collector backpressure. If disk fills up solely due to access logs, the HTTP service can degrade or crash; logging must not become a single point of failure.

### 17.3. Lifecycle and Access Controls

- Restrict read/write access on log files, indices, and dashboards on a need-to-know basis.
- Encrypt logs in transit to collectors; enforce TLS/authentication on log pipelines.
- Redact/allowlist fields before shipping rather than merely hiding them in UI views.
- Define retention and deletion schedules per regulations; never retain PII indefinitely.
- Verify timezone and timestamp parsing across access logs and application logs; standardize on UTC in pipelines for comparison.
- Include service name, deployment version, and pod/instance ID to distinguish replicas.
- Maintain an incident support workflow: look up requests by ID, trace, status, route, and time window without ever asking users to share session cookies.

## 18. Failure Scenarios and Investigation Guide

| Symptom | Possible cause | Verification step |
| --- | --- | --- |
| Tomcat access log file missing | Not enabled, wrong basedir/dir, not writable, not using Tomcat | Check `server.tomcat.accesslog.*` and runtime connector |
| Tomcat log present, app log missing | Request blocked before app filter, security filter order, log level/collector | Check filter order, `logging.level`, edge/container status |
| App business log present, missing requestId | MDC not propagated to async/other thread, filter skipped | Check lifecycle and context propagation |
| App log has requestId, Tomcat line has `-` | Response header not set, wrong log pattern, handled by different handler | Check `%{X-Request-Id}o` and response header |
| Tomcat status 404, no controller log | Route did not match or request never reached method | Check route mapping/context path |
| 403 at gateway, no request in Tomcat | WAF/ingress blocked before app | Check edge access logs and security rules |
| Access log shows 200, client download failed | Stream committed 200 then severed, proxy/client disconnect | Check bytes/status/connection state and stream errors |
| Small app duration, large proxy duration | Queue/connect/slow client download/buffering/async | Compare measurement points, network, proxy upstream time |
| Tomcat duration larger than app duration | Container overhead, async streaming, slow client | Inspect `%D` and async/response lifecycle |
| Too many INFO logs | High request rate / unsampled success logging | Add log volume budget and metrics |
| Logs contain password in URL | `%r`/`%q`/Referer or raw input logged by app | Change fields, rotate/redact, handle incident |
| Debug logs lost after restart | Files stored in temp/ephemeral filesystem | Move to centralized logging/persistent volume |
| Cannot match IDs between edge and app | Both sides generated independent IDs or stripped headers | Establish edge/app correlation contract |
| Log entries duplicated 2–3 times | Multiple filters, duplicate appenders, or error dispatches | Check logger config, async/error dispatches |
| Exception occurred, `statusAtExit=200` | Unhandled exception, error dispatch happened after filter | Use final container access log/observation |
| `X-Forwarded-For` spoofed | Proxy did not strip, backend publicly exposed | Enforce trust boundaries, never trust client headers |
| Metrics p99 differs from log durations | Sampling, different boundaries, different units, async | Standardize definitions and test pipeline |
| Log request count differs from browser requests | CORS preflight, favicon, health checks, proxy retries | Separate methods, routes, edge requests, and tracing |

## 19. Pre-Production Logging Checklist

- [ ] Identified **edge access log**, **container access log**, and **application request log** with clear owners.
- [ ] For Tomcat, verified `server.tomcat.accesslog.enabled`, basedir, directory, pattern, retention, and collector.
- [ ] For Jetty/Undertow/WebFlux, avoided copying Tomcat configuration verbatim.
- [ ] Request ID is issued by a trusted source, echoed in the response header, and included in log correlation.
- [ ] Distributed tracing is enabled if requests span multiple services; `requestId`/`traceId`/`spanId` are clearly distinguished.
- [ ] Authorization/Cookie/session ID/password/token/raw sensitive bodies and queries are never logged.
- [ ] Route templates replace raw paths wherever possible, and URL paths are audited for PII.
- [ ] App MDC is cleaned up in `finally` to prevent ID leaks across pooled thread reuse.
- [ ] Async, streaming, client disconnects, and error dispatches are logged at **final lifecycle**, not mistaking filter exit for full completion without verification.
- [ ] Unit/HTTP integration tests verify status/response headers; the log pipeline is QA-tested separately.
- [ ] Timing units across Tomcat `%D`, app milliseconds, and proxy latency metrics are reconciled.
- [ ] Log budgets/sampling/retention, disk quota/collector alerts, and proper access controls are in place.
- [ ] Log events follow a fixed schema without dynamic keys or high cardinality.
- [ ] Security-specific audit events exist where required by business/compliance, not just HTTP status codes.
- [ ] Reverse proxies enforce a forwarded-header trust policy; client IPs/users are never inferred from untrusted headers.
- [ ] Backups/rotation/log storage comply with data governance policies.
- [ ] Spring Boot/runtime/collector are updated to maintained versions with security patches.

## 20. Self-Check Questions

**1. Do access logs and application logs serve the same purpose?**  
No. Access logs describe HTTP exchanges at the server/proxy; app logs describe events inside application code and business logic.

**2. Why might an HTTP 403 appear at the edge with zero Tomcat access log entries?**  
The gateway/WAF may have blocked the request before it ever reached the application.

**3. Should Tomcat `%D=10000` be read as 10000 ms?**  
No. In Tomcat, `%D` is in microseconds; 10000 µs = 10 ms.

**4. What is the difference between `%U` and `%r`?**  
`%U` is the URL path; `%r` is the request line which can include the query string, making it much more likely to leak tokens/PII.

**5. Why can a `requestId` in MDC "stick" between two requests?**  
MDC is thread-bound; the filter or service failed to clean it up properly before the thread was reused.

**6. Is `OncePerRequestFilter`'s `finally` always the moment the client finishes receiving an SSE stream?**  
No. Servlet async/streaming can continue after the filter chain has exited.

**7. Can Tomcat returning 500 while the filter logs `statusAtExit=200` be valid?**  
Yes, if error handling/dispatch occurred after the filter exited; always label the measurement point clearly.

**8. Should a client-supplied `X-Request-Id` be trusted by default?**  
No. It requires a trusted edge contract, validation, or server-generated IDs as shown in the demo.

**9. To correlate requests across multiple microservices, should you use a local `requestId` or distributed tracing?**  
Use standard trace context/`traceId` or a gateway-standardized identifier; a local `requestId` is insufficient.

**10. Should `logging.level.org.springframework=TRACE` be left enabled long-term in production for easy debugging?**  
No. It can exhaust resources and leak sensitive data; enable only within an authorized scope and duration.

**11. Is access log `%a` behind a proxy guaranteed to be the real browser IP?**  
Not guaranteed; it may be the proxy IP. A proper trust chain and configuration are required.

**12. Body logging helps catch every bug, so should global `ContentCachingRequestWrapper` be enabled?**  
No. It easily leaks PII/secrets, consumes memory, and can break or stall streaming if mishandled.

**13. If Tomcat writes access logs to a file while console logs ship to a collector, is that enough?**  
Not necessarily. A stdout collector does not automatically read access log files; separate integration is required.

**14. What is Java's `System.nanoTime()` used for inside the filter?**  
Measuring elapsed duration on a monotonic clock, not wall-clock timestamps across timezones.

**15. Is HTTP status 200 proof that the business operation completed?**  
No. 200 only states the HTTP response succeeded at that layer; business/audit events require their own contracts.
