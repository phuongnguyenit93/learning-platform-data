# Application Runs but Is Unreachable Due to Port, Address, or Proxy in Spring Boot

## 1. Scenario and Objectives

Spring Boot may log `Started Application` to the console while the browser still returns `ERR_CONNECTION_REFUSED`, `timeout`, HTTP 404, 502, 504, or redirects incorrectly. A **"the application started" message does not prove all clients can reach it**. You can only draw an accurate conclusion after identifying which layer stops the request:

~~~text
Client (browser, curl, mobile app)
  |
  v
DNS + IP routing + scheme + port
  |
  v
Firewall / CDN / HTTPS load balancer / reverse proxy
  |
  v
Docker host port mapping / Kubernetes Service
  |
  v
Spring Boot HTTP listening socket
  |
  v
Servlet / WebFlux router + context path
  |
  v
Spring Security / Controller / Response
~~~

**Three core questions**:
1. Has Java actually opened an **HTTP socket** on the IP:port we are calling?
2. Does every NAT/Service/reverse proxy layer forward the request to the **right IP:port**?
3. Once the request reaches the HTTP server, are **Host, scheme, URL path, context, and security** all aligned?

After this lesson, you should be able to distinguish bind address from client destination, app port from host/Service port; locate configuration overrides; inspect Docker/Kubernetes/NGINX; understand forwarded headers and TLS/redirect loops; and use reproducible commands/tests to confirm the issue is resolved.

**Example scope:** Java 17+, Spring Boot 3.3.x, Spring MVC on embedded Tomcat. The networking principles also apply to Jetty/Undertow/Reactor Netty, though specific properties/semantics must be verified against the actual embedded server. Do not use an unverified proxy configuration to expose public endpoints in production.

## 2. Symptoms Pointing to the Failure Layer

| Client outcome | Possible nature | Next check |
| --- | --- | --- |
| `Connection refused` | No listener at IP:port, or network peer actively rejects | Process, bind address, container port mapping |
| `Connection timed out` | Firewall/routing drop, LB/upstream fails to reply in time | IP path, security group, listener, timeout |
| `Empty reply`/`EOF`/`reset` | Connection closed mid-flight, protocol mismatch, shutdown | HTTP/TLS, process logs, proxy errors |
| `HTTP 404` | An HTTP server responded; mapping/context/rewrite/backend may be wrong | Compare direct route vs. proxy route |
| `HTTP 401/403` | Authentication, authorization, CORS preflight, or gateway/WAF block | Security config, response headers |
| `Repeated HTTP 301/302` | Scheme/Host/forwarded prefix/redirect policy mismatch | Inspect each `Location` header |
| `HTTP 502` | Gateway cannot connect or cannot parse upstream response | `proxy_pass` IP/port/protocol, ingress error log |
| `HTTP 503` | App/gateway unavailable, backend not Ready, shutdown | Endpoints, readiness, node health |
| `HTTP 504` | Gateway waited too long for upstream | Upstream latency, proxy timeout, DB |
| `Browser CORS error, curl 200` | Browser blocks cross-origin HTTP response | Allowed origins, OPTIONS, Security |
| `Certificate invalid` | TLS SNI/cert/chain/hostname | Test TLS at proxy and client |
| `Actuator health UP, controller fails` | Separate management port/context or different API path/auth | Main application port |

**Boundary:** HTTP 404/401/403 already have HTTP communication, so they are not TCP connection-setup failures. HTTP 502/504 can be generated by a gateway **before the request ever reaches Spring**, so the app may have no access log entry.

## 3. "Process Running", "Listener Exists", and "Reachable" Are Different

Four milestones:

~~~text
JVM running
   -> WebApplicationContext initialized?
   -> HTTP server has bound IP:port?
   -> Is that IP:port reachable through actual network path?
   -> Did the requested route answer correctly?
~~~

A process running only a batch job can still print `Started ...`. A Servlet app with `server.port=-1` has a context but **no HTTP endpoints**. A process listening on `127.0.0.1:8080` serves localhost yet does not listen on the machine's private IP.

Therefore, do not rely solely on the `Started` line—look for the HTTP server startup line (e.g., Tomcat started on port), then verify the **actual socket** and test requests across each hop.

### Default Port 8080 and Exceptions

~~~properties
server.port=8080
~~~

is the common Spring Boot embedded port example. However:
- `server.port=9090` changes the port.
- `server.port=0` lets the OS assign a **random** free port.
- `server.port=-1` disables HTTP endpoints while still creating the `WebApplicationContext`.
- `spring.main.web-application-type=none` does not start an HTTP web server.
- `management.server.port=9091` can start a separate Actuator management listener, distinct from the app port.
- When deploying a WAR to **external Tomcat**, the external container dictates the connector port, not `server.port` inside the WAR.

**Example:** if `server.port=0` is enabled and logs report port 51627 (illustrative only), calling `localhost:8080` does not prove the app is broken. You must call the actual port 51627 or use `@LocalServerPort` in tests.

## 4. `server.address`: The Interface the Embedded HTTP Server Binds To

Spring Boot supports:

~~~properties
server.address=127.0.0.1
~~~

or:

~~~properties
server.address=0.0.0.0
~~~

| Bind address | Meaning | Consequence |
| --- | --- | --- |
| Unconfigured | Server/OS selects binding per runtime, often all interfaces | Measure the real socket; do not guess |
| `127.0.0.1` | IPv4 loopback of the **network namespace containing the JVM** | Remote peers cannot reach it via machine/container IP |
| `0.0.0.0` | All IPv4 interfaces in that namespace | Can accept from private/public interfaces if network permits |
| `192.168.1.10` | Only the specific assigned interface | Binding fails if IP changes or does not exist |
| `::1` | IPv6 loopback | Not equivalent to IPv4 `127.0.0.1` |
| `::` | IPv6 wildcard (IPv4 mapping depends on OS) | Test dual-stack explicitly |

Example app binding loopback:

~~~properties
server.port=8080
server.address=127.0.0.1
~~~

On the **same host**:

~~~bash
curl -i http://127.0.0.1:8080/ping
~~~

may succeed. Yet another machine calling `http://192.168.1.10:8080/ping` gets refused because Tomcat is **not listening on 192.168.1.10**.

When the app needs to accept traffic from network interfaces (e.g., container/Pod):

~~~properties
server.port=8080
server.address=0.0.0.0
~~~

**This is not advice to expose the service to the entire Internet.** Binding is a process-level behavior, while network exposure must be controlled by firewalls/security groups, load balancers, Docker publish IP, Kubernetes Service/NetworkPolicy, TLS, and auth. Never disable a firewall to fix a binding issue.

### `localhost` Means Different Things

- `localhost` on your laptop → your laptop.
- `localhost` inside a Docker container → **that container itself**.
- `localhost` inside a Kubernetes Pod → the Pod's shared network namespace; not the node or Service.
- `localhost` inside an NGINX container → the NGINX container, not the Spring container in another service.
- `localhost` inside a CI runner → the runner (unless sharing a network namespace).

When a proxy container calls an app container, you normally use a Docker Compose service name like `web:8080` or Kubernetes Service DNS, not `localhost`.

## 5. IPv4, IPv6, and DNS: Right Name, Wrong Connection Address

`localhost` can resolve to both `127.0.0.1` and `::1`. If Java binds only IPv4 while the client tries IPv6 first, behavior depends on DNS/client fallback.

Compare:

~~~bash
curl -4 -v http://localhost:8080/ping
curl -6 -v http://localhost:8080/ping
curl -v http://127.0.0.1:8080/ping
curl -g -v "http://[::1]:8080/ping"
~~~

For a public domain with both DNS A and AAAA records where only IPv4 is implemented, a subset of clients can fail when trying IPv6. Inspect `A`/`AAAA`, listening sockets, dual-stack load balancers, and IPv6 firewalls. `0.0.0.0` is an IPv4 wildcard; do not claim it is an IPv6 wildcard.

### Testing the Right Host/SNI Before DNS Updates

Example testing HTTP Host with a documentation IP:

~~~bash
curl -v --resolve demo.example.test:80:192.0.2.10 \
  http://demo.example.test/ping
~~~

`192.0.2.10` is an example IP—substitute the actual ingress IP, not a public lab IP. `--resolve` maps the hostname+port to the chosen address while keeping the HTTP `Host` header as `demo.example.test`.

With HTTPS, use:

~~~bash
curl -v --resolve demo.example.test:443:192.0.2.10 \
  https://demo.example.test/ping
~~~

This is suitable for testing TLS SNI/hostname verification. Do not use `-k` as a fix for certificate errors: it disables server identity verification.

### 6.3. Diagnostic Controller

`src/main/java/demo/network/DiagnosticController.java`:

~~~java
package demo.network;

import java.net.URI;
import java.util.Map;

import jakarta.servlet.http.HttpServletRequest;

import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.servlet.support.ServletUriComponentsBuilder;

@RestController
public class DiagnosticController {

    @GetMapping(value = "/ping",
                produces = MediaType.TEXT_PLAIN_VALUE)
    public String ping() {
        return "pong";
    }

    @GetMapping("/where")
    public Map<String, Object> where(HttpServletRequest request) {
        return Map.of(
                "scheme", request.getScheme(),
                "host", request.getServerName(),
                "port", request.getServerPort(),
                "contextPath", request.getContextPath(),
                "requestUri", request.getRequestURI(),
                "remoteAddress", request.getRemoteAddr()
        );
    }

    @GetMapping("/jump")
    public ResponseEntity<Void> jump() {
        URI location = ServletUriComponentsBuilder
                .fromCurrentContextPath()
                .path("/ping")
                .build()
                .toUri();

        return ResponseEntity.status(HttpStatus.FOUND)
                .location(location)
                .build();
    }
}
~~~

- `GET /ping` returns body **`pong`** to check the route.
- `GET /where` returns host/scheme/port/context/remote address as seen on the servlet request by the app. Proxies can alter these values.
- `GET /jump` returns HTTP 302 with a `Location` built by Spring MVC from the current request context, revealing forwarded scheme/host/port or prefix issues.
- The `remoteAddress` field is for learning only. **Do not expose `/where` publicly in production**: it can leak network topology and client IPs; use protected diagnostics/logs instead.

## 7. HTTP Integration Tests: Use a Real Port, Not Hardcoded 8080

`src/test/java/demo/network/NetworkLabHttpTest.java`:

~~~java
package demo.network;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment =
        SpringBootTest.WebEnvironment.RANDOM_PORT)
class NetworkLabHttpTest {

    @LocalServerPort
    int port;

    @Autowired
    TestRestTemplate http;

    @Test
    void pingWorksOverHttp() {
        ResponseEntity<String> r =
                http.getForEntity("/ping", String.class);

        assertThat(port).isBetween(1, 65535);
        assertThat(r.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(r.getBody()).isEqualTo("pong");
    }

    @Test
    void whereShowsRequestPath() {
        ResponseEntity<String> r =
                http.getForEntity("/where", String.class);

        assertThat(r.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(r.getBody()).contains("/where");
        assertThat(r.getBody()).contains("requestUri");
    }

    @Test
    void unknownPathIs404() {
        ResponseEntity<String> r =
                http.getForEntity("/no-such-route", String.class);

        assertThat(r.getStatusCode())
                .isEqualTo(HttpStatus.NOT_FOUND);
    }
}
~~~

Run:

~~~bash
./gradlew test --tests demo.network.NetworkLabHttpTest
~~~

The test starts an HTTP server on a random port and exercises real routes; it **does not prove that the Docker host, Kubernetes Service, ingress, or public DNS are right**. It verifies the application layer in the test environment.

### Port 0 and -1

## 8. Config Precedence: Why Does the File Say 8080 While Logs Show 9090?

Spring Boot reads config from many sources:
- `application.properties` packaged inside the JAR;
- external `application.properties` and `config/`;
- `application-prod.properties` when the `prod` profile is active;
- OS environment variables `SERVER_PORT`/`SERVER_ADDRESS`;
- Java system properties `-Dserver.port=...`;
- command-line args `--server.port=...`;
- test-specific properties or config imports.

For example:

~~~properties
server.port=8080
~~~

Yet when run with:

~~~bash
SERVER_PORT=9090 java -jar build/libs/network-access-lab.jar
~~~

the port is **9090** under default precedence. If you add:

~~~bash
SERVER_PORT=9090 java -jar build/libs/network-access-lab.jar \
  --server.port=7070
~~~

command-line argument `7070` normally takes precedence over env `9090`. Java system properties go **before** `-jar`:

~~~bash
java -Dserver.port=9090 -jar build/libs/network-access-lab.jar
~~~

Whereas Spring args go **after** the JAR:

~~~bash
java -jar build/libs/network-access-lab.jar --server.port=9090
~~~

### How to Find the Override Source

1. Read startup logs from the **right PID/timestamp**, not stale console output.
2. Check command-line args, JVM `-D` flags, and launcher scripts.
3. Inspect env vars `SERVER_PORT`, `SERVER_ADDRESS`, `SPRING_PROFILES_ACTIVE`.
4. Check profile-specific and external configs relative to the working directory.
5. In Docker: image defaults, `docker run -e`, Compose `environment`.
6. In Kubernetes: Deployment `env`, `ConfigMap`/`Secret`, JVM opts.
7. If policy allows, inspect Actuator `env`/`configprops` on a protected network; never expose publicly as they may hold sensitive config.
8. Verify whether the deployed artifact is an embedded JAR or a WAR inside external Tomcat.

Do not conclude a config is "right" just because a source file says so. **Effective runtime values** determine the actual socket.

## 9. Commands to Inspect Listening Sockets

### Linux/macOS

~~~bash
ss -lntp | grep ':8080'
~~~

Or with `lsof`:

~~~bash
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
~~~

Example output:

~~~text
LISTEN 0 100 127.0.0.1:8080 0.0.0.0:* users:(("java",pid=12345,fd=42))
~~~

**Read the local address column**—do not confuse `0.0.0.0:*` in the peer address column. The line above proves the socket is **`127.0.0.1:8080`**, not listening on `192.168.x.x`. If the local address is `0.0.0.0:8080`, it listens on all IPv4 interfaces in that namespace, though firewalls/routing can still block remote traffic.

If Java is inside Docker or a Pod, run the tool inside the **right network namespace** (e.g., a debug container or exec with appropriate tools). `ss` on the Docker host will not always show listeners inside containers.

### Windows PowerShell

~~~powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen |
    Select-Object LocalAddress, LocalPort, OwningProcess

Test-NetConnection 127.0.0.1 -Port 8080
curl.exe -v http://127.0.0.1:8080/ping
~~~

Or:

~~~powershell
netstat -ano | findstr :8080
~~~

In Windows PowerShell 5.1, `curl` can be an alias for `Invoke-WebRequest`; use **`curl.exe`** so `-v`, `--resolve`, and cURL flags behave as shown. Never kill a PID without confirming it is the intended process/container.

### Reproducible cURL Command Structure

~~~bash
curl -v --connect-timeout 3 --max-time 8 \
  http://127.0.0.1:8080/ping
~~~

- `-v`: DNS, TCP/TLS setup, request/response headers, and error details.
- `--connect-timeout 3`: connection phase limit, not total request duration.
- `--max-time 8`: limit for the entire cURL transfer.
- `-i`: prints response headers; `-L`: follows redirects (use sparingly).
- `--noproxy '*'`: bypasses outbound HTTP proxies configured on the client machine.

With HTTP **404**, the socket and HTTP layer are already working on some server; investigate the path/backend instead of blaming TCP connectivity.

## 10. Docker: `EXPOSE`, `-p`, Host Port, and Container Bind Are Four Separate Concepts

`Dockerfile` based on the built project:

~~~dockerfile
FROM eclipse-temurin:17-jre

WORKDIR /opt/app
COPY build/libs/network-access-lab.jar /opt/app/app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/opt/app/app.jar"]
~~~

Build the image:

~~~bash
./gradlew bootJar
docker build -t network-access-lab:1.0 .
~~~

Run:

~~~bash
docker run --rm --name network-lab \
  -p 127.0.0.1:18080:8080 \
  network-access-lab:1.0
~~~

Diagram:

~~~text
Host 127.0.0.1:18080
       |
       v
Docker publish/NAT
       |
       v
ContainerIP:8080
       |
       v
Java listener 0.0.0.0:8080
       |
       v
GET /ping -> 200 pong
~~~

From the host, call:

~~~bash
curl -i http://127.0.0.1:18080/ping
~~~

**Do not call host 8080** in this mapping example. Common mistakes:

| Mistake | Why it fails | Fix |
| --- | --- | --- |
| `Dockerfile` has `EXPOSE 8080` but `docker run` omits `-p` | `EXPOSE` is metadata only, does not publish a host port | Use `-p` / Compose `ports` |
| `-p 18080:8080` yet cURL calls host 8080 | Wrong host port | Call host port 18080 |
| Spring binds `127.0.0.1:8080` inside the container | NAT targets container IP, not container loopback | Bind `0.0.0.0` inside the container |
| `-e SERVER_PORT=9090`, still `-p 18080:8080` | Container listens on 9090, NAT forwards to 8080 | `-p 18080:9090` |
| Proxy container calls `127.0.0.1:8080` | Loopback is the proxy container | Use service DNS `web:8080` |
| Unintended host bind `0.0.0.0:18080` | Publishes on all host IPv4 interfaces | `-p 127.0.0.1:18080:8080` for local testing |
| Two containers using the same host port | Port publish conflict | Pick a different host port or stop the right container |
| Container restarted/OOM | Mapping exists yet Java is not Ready | `docker ps`/`docker logs`/inspect health |

**Security note:** `docker run -p 18080:8080` typically publishes the port on all host interfaces, potentially exposing the service outside the machine. Bind host `127.0.0.1` for labs; production ingress is controlled by LB/firewall policy. Docker NAT/network modes/versions have nuances, so verify empirically.

### Docker Inspection Commands

~~~bash
docker ps
docker port network-lab
docker logs --tail 100 network-lab
docker inspect network-lab
~~~

`docker inspect` can include env vars and secrets; do not paste raw output into public tickets. When containers run on a Docker network, HTTP service-to-service traffic uses **internal** service DNS/ports rather than host published ports.

### Docker Compose

~~~yaml
services:
  web:
    image: network-access-lab:1.0
    environment:
      SERVER_PORT: "8080"
      SERVER_ADDRESS: "0.0.0.0"
    ports:
      - "127.0.0.1:18080:8080"
~~~

~~~bash
docker compose up
curl -i http://127.0.0.1:18080/ping
~~~

If you add an NGINX container **on the same Compose network**, NGINX's upstream should point to `http://web:8080`. Do not point to `localhost:18080`, because that is the NGINX container's loopback and host port mapping is not the service discovery path.

## 11. Kubernetes: PodIP, Service Port, `targetPort`, and Endpoints

A Spring Boot app in a cluster has at least three important endpoints:

~~~text
PodIP:8080                         (Java listens here)
Service ClusterIP:80              (Service port)
Ingress Host:443 / public domain  (if exposed externally)
~~~

**Example Deployment + Service**: the `network-access-lab:1.0` image must be pushed to a registry accessible by the cluster or preloaded into kind/minikube. File `k8s-network-lab.yaml`:

~~~yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: network-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: network-lab
  template:
    metadata:
      labels:
        app: network-lab
    spec:
      containers:
        - name: app
          image: network-access-lab:1.0
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: SERVER_PORT
              value: "8080"
            - name: SERVER_ADDRESS
              value: "0.0.0.0"
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
---
apiVersion: v1
kind: Service
metadata:
  name: network-lab
spec:
  selector:
    app: network-lab
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: http
  type: ClusterIP
~~~

Explanation:

- `containerPort: 8080` **does not make Java listen on 8080**; it is container metadata/port naming.
- `Service.port: 80` is what in-cluster clients connect to.
- `targetPort: http` references the `containerPort` named `http` → value 8080.
- `selector.app=network-lab` must match Pod labels; otherwise the Service has no backends.
- If Pod `Ready = false`, the Service does not route normal traffic to that Pod; check the probe path and Spring Security.
- `type: ClusterIP` does not create a public IP or Ingress.
- `server.address=127.0.0.1` inside a Pod prevents traffic from remote Pods reaching `PodIP:8080`, even though `curl localhost` inside the Pod returns 200.

Run:

~~~bash
kubectl apply -f k8s-network-lab.yaml
kubectl get pods -l app=network-lab -o wide
kubectl get svc network-lab
kubectl get endpointslice \
  -l kubernetes.io/service-name=network-lab
kubectl describe svc network-lab
kubectl logs deployment/network-lab --tail=100
~~~

If using **kind** and the image is on the Docker host, load it with:

~~~bash
kind load docker-image network-access-lab:1.0
~~~

If `ImagePullBackOff`, fix image availability before debugging ports. If `CrashLoopBackOff`, inspect the Java startup exception. If `Running` yet `NotReady`, inspect `kubectl describe pod` and probe HTTP/status.

### Testing Through the Service from Inside the Cluster

A test Pod using cURL:

~~~bash
kubectl run network-client --rm -i \
  --restart=Never --image=curlimages/curl:8.10.1 -- \
  curl -sv http://network-lab:80/ping
~~~

Only run this when the test image is permitted and pullable. Across namespaces, use FQDN `network-lab.<namespace>.svc.cluster.local`. Returning HTTP 200 `pong` proves the in-cluster Service → app route works, not that external ingress is right.

### `port-forward` Is Not an Ingress Test

~~~bash
kubectl port-forward service/network-lab 18080:80
~~~

Afterwards `curl http://localhost:18080/ping` may return 200. However, `port-forward` is a **Kubernetes API server debug tunnel**, usually targeting one Pod; it bypasses public DNS, TLS termination, Ingress rules, and the external LB. Do not use this result to claim Internet users can access the service.

### When a Service Has No Endpoints

1. Check Service selectors and Pod labels.
2. Check `readinessProbe` response/status; is the health path right?
3. Confirm named `targetPort` matches `containerPort`.
4. Confirm Java binds the Pod interface, not loopback-only.
5. Check Pod restarts, HPA/rollouts/draining.
6. Check `NetworkPolicy`/service mesh/mTLS, DNS, and CNI connectivity.
7. Test the Pod IP from an authorized debug Pod; separate Pod listening from Service routing.
8. Record timestamps of Pod/`EndpointSlice` transitions instead of relying on a single snapshot while endpoints are changing.

## 12. Ingress: Host, Path, Service Name, and TLS Must All Align

Illustrative Ingress manifest, assuming an ingress controller class named `nginx` is installed in the cluster:

~~~yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: network-lab
spec:
  ingressClassName: nginx
  rules:
    - host: demo.example.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: network-lab
                port:
                  number: 80
~~~

**Do not treat this manifest as a complete HTTPS config.** Serving port 443 requires an ingress controller, real DNS, LB, and TLS config/certs. `demo.example.test` is an example hostname; use your staging hostname when testing for real.

Common issues:

| Issue | Clue |
| --- | --- |
| Ingress has no controller | Object exists yet nothing serves HTTP |
| `ingressClassName` mismatch | Controller ignores the rule |
| Host mismatch | Default backend returns 404 |
| Path rule mismatch | Ingress 404 or routes to wrong service |
| Backend service port set to 8080 while Service only exposes 80 | Misconfigured upstream target |
| Service has no ready `EndpointSlices` | Gateway may return 503 |
| NGINX Ingress rewrite differs from app context | Spring 404 |
| TLS secret/certificate error | Browser blocked before reaching Spring |
| DNS A/AAAA points to old LB | Only some clients hit the wrong place |

**Distinguish:**
- `Service.port` = 80 in the manifest.
- `Pod.containerPort` = 8080.
- `Ingress.service.port.number` must reference **80**, not 8080.
- Spring's `server.port` must be 8080 matching the container listener.
- If another proxy sits outside the cluster, also inspect that proxy's TLS/Host/path.

## 13. NGINX `proxy_pass` and Trailing Slash: A Very Common Source of HTTP 404

Suppose Spring maps:

~~~java
@GetMapping("/ping")
public String ping() {
    return "pong";
}
~~~

Public clients call `/api/ping`, while upstream Spring expects `/ping`.

### Correct When You Want to Strip the `/api/` Prefix

~~~nginx
server {
    listen 8088;
    server_name localhost;

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Prefix /api;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
~~~

This snippet assumes NGINX is on the **same host** as Spring and NGINX is the trusted entrypoint. Production also requires LB/TLS/security; if NGINX runs in a separate container, change the upstream to the service DNS.

Result:

~~~text
Client  -> GET /api/ping
NGINX   -> GET /ping
Spring  -> HTTP 200, body pong
~~~

Because for prefix location `/api/`, `proxy_pass http://127.0.0.1:8080/;` **includes the `/` URI**, NGINX replaces the matched prefix with that URI.

### Wrong If Expecting Prefix Stripping Without the Trailing Slash

~~~nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
~~~

When there is no URI in `proxy_pass`, the request URI is normally forwarded intact:

~~~text
Client  -> GET /api/ping
NGINX   -> GET /api/ping
Spring  -> 404 because only /ping is mapped
~~~

**Handy table:**

| Location | `proxy_pass` | Client URI | URI sent upstream |
| --- | --- | --- | --- |
| `/api/` | `http://app:8080/` | `/api/ping` | `/ping` |
| `/api/` | `http://app:8080` | `/api/ping` | `/api/ping` |
| `/api/` | `http://app:8080/v1/` | `/api/ping` | `/v1/ping` |

This applies to simple prefix locations; regex locations, rewrites/variables, and URI normalization have different semantics. If Spring already sets `server.servlet.context-path=/api`, the app **expects `/api/ping`**, so do not strip it again.

### Where Is NGINX Running?

- Same VM as the app → upstream `127.0.0.1:8080` can be right.
- NGINX in a different Docker container → `127.0.0.1` is the NGINX container; use `web:8080` on the Compose network.
- NGINX Ingress in Kubernetes → goes through Kubernetes Service `network-lab:80`.
- Host with a Docker published port → upstream can point to the host published port, though you must know host routing, network mode, and firewall rules.

**A wrong upstream IP/port usually yields 502**, whereas the right upstream with the wrong path yields 404. Cross-check NGINX error/access logs with Spring access logs to tell them apart.

## 14. `server.servlet.context-path` and `spring.mvc.servlet.path`

Even a healthy HTTP listener returns 404 if the request URL omits the prefix the app registered.

In Spring MVC:

~~~properties
server.servlet.context-path=/shop
spring.mvc.servlet.path=/api
~~~

With controller `@GetMapping("/ping")`, the embedded Servlet app URL is normally:

~~~text
http://localhost:8080/shop/api/ping
~~~

Path layers:

~~~text
Port                  :8080
Servlet context       /shop
DispatcherServlet     /api
Controller mapping    /ping
Full path             /shop/api/ping
~~~

Do not change ports when the real issue is missing `/shop/api`. Spring WebFlux uses `spring.webflux.base-path`; do not set `spring.mvc.servlet.path` in a WebFlux/Netty app and expect it to govern WebFlux mappings.

**External WAR:** if the app is packaged as `shop.war` and deployed to external Tomcat, the context is typically `/shop` as decided by the container; Boot's `server.port` does not control Tomcat's connector port. The URL also depends on the WAR filename/context descriptor.

### Context Path and Reverse Proxy Must Agree

There are two designs:
1. Spring at root `/ping`, proxy receives `/api/ping` and **strips `/api`**.
2. Spring has context `/api`, proxy receives `/api/ping` and **preserves** the prefix.

Both are valid when configured explicitly. Failures occur when the proxy strips while the app expects the prefix, or the proxy preserves while the app maps only root.

## 15. Forwarded Headers: Hostname, Scheme, Port, and Public Prefix Behind a Proxy

A TLS-terminating deployment:

~~~text
Browser: https://shop.example.test/api/ping
  |
  v
Ingress / NGINX TLS :443
  |
  | proxy HTTP to 10.0.0.20:8080
  | Host: shop.example.test
  | X-Forwarded-Proto: https
  | X-Forwarded-Host: shop.example.test
  | X-Forwarded-Port: 443
  | X-Forwarded-Prefix: /api
  v
Spring Boot HTTP :8080
~~~

If the app does not understand the external URL, `ServletUriComponentsBuilder` or redirect/cookie logic may emit:

~~~http
HTTP/1.1 302
Location: http://10.0.0.20:8080/ping
~~~

instead of `https://shop.example.test/api/ping`. The browser can hit a redirect loop, mixed-content block, or an unroutable internal host.

### `server.forward-headers-strategy`

Spring Boot 3.3 offers three choices:

~~~properties
server.forward-headers-strategy=none
~~~

Disables Spring-level forwarded-header processing. Suitable when there is no trusted proxy; runtime defaults may differ by cloud platform.

~~~properties
server.forward-headers-strategy=native
~~~

Uses the native HTTP server mechanism, such as Tomcat `RemoteIpValve`, which is often sufficient for `X-Forwarded-For`/`X-Forwarded-Proto` when trusted proxies are configured properly. With Tomcat behind TLS-terminating proxies, Boot docs also note:

~~~properties
server.forward-headers-strategy=native
server.tomcat.redirect-context-root=false
~~~

so forwarded proto is evaluated before certain context-root redirects.

~~~properties
server.forward-headers-strategy=framework
~~~

Uses `ForwardedHeaderFilter` in Servlet MVC or `ForwardedHeaderTransformer` in WebFlux; helpful when `X-Forwarded-Prefix` is needed for generated redirects/links or native handling is insufficient.

**Never enable and trust arbitrary headers from the Internet**. An attacker can forge `X-Forwarded-Host: attacker.example`, `X-Forwarded-Proto: https`, or fake `X-Forwarded-For`. The gateway must strip/overwrite untrusted forwarded headers and configure trusted proxy ranges. With multiple proxies, establish which hop is authoritative for external Host/scheme/IP rather than taking client-supplied values.

### Sample NGINX Forwarded Config

The snippet below sits inside a properly configured HTTPS server block:

~~~nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/;

    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Port $server_port;
    proxy_set_header X-Forwarded-Prefix /api;

    # Valid only if NGINX itself is the trusted ingress entrypoint.
    proxy_set_header X-Forwarded-For $remote_addr;
}
~~~

If NGINX sits behind a CDN/LB, `$scheme` and `$server_port` may reflect the *internal hop* rather than the public HTTPS scheme/port. Establish the trusted source and chain. Do not blindly append raw client `$http_x_forwarded_for` for remote identity decisions.

**Crucial point:** `server.forward-headers-strategy=framework` **does not replace** `proxy_pass` URI rewriting. It adjusts request metadata/link generation, not automatic stripping of prefixes from incoming routes. Fix the upstream URI to match controller mappings first.

### Testing Redirects

~~~bash
curl -i http://127.0.0.1:8080/jump
curl -i http://127.0.0.1:8088/api/jump
~~~

Compare `Location`:
- direct may be `http://127.0.0.1:8080/ping`;
- through a trusted proxy with an appropriate forwarded strategy, the public URL should match the public scheme, host, port, and prefix when supported by the framework/server.

Do not assume the result from config alone; verify actual headers, Spring version, and proxy chain.

## 16. TLS: HTTP/HTTPS Mismatch, SNI, and Redirect Loops

A direct HTTP 200 does not prove public HTTPS works. Identify where TLS terminates:

| Client → proxy | Proxy → Spring | Spring |
| --- | --- | --- |
| HTTPS 443 | HTTP 8080 | App HTTP listener |
| HTTPS 443 | HTTPS 8443 | App HTTPS listener |
| No proxy | HTTP 8080 | App HTTP listener |

Failures:
- `https://host:8080` calling an HTTP-only server → TLS handshake failure, not a controller 404.
- `proxy_pass https://app:8080` targeting an HTTP app → upstream SSL failure / 502.
- Expired certificate, SAN mismatch, missing chain, or wrong SNI.
- CDN/ingress upgrades HTTP→HTTPS while the app keeps redirecting back to HTTP because it ignores forwarded proto → loop.
- App emits `Location` pointing to an internal port or private hostname.
- HSTS in the browser silently turns HTTP requests into HTTPS, differing from cURL tests.

Use:

~~~bash
curl -v https://shop.example.test/api/ping
curl -I https://shop.example.test/api/jump
curl -v -L --max-redirs 5 \
  https://shop.example.test/api/jump
~~~

These examples assume staging DNS/certs are valid. `curl -L` reveals the redirect chain; cap redirects when investigating loops. Do not use `curl -k`/`--insecure` as a permanent workaround because it skips certificate verification and hides security flaws.

### When the Proxy Terminates TLS, Does the App Need `server.ssl`?

Not necessarily. In an NGINX TLS-termination + HTTP-upstream design inside a trusted private network, the app listens on HTTP :8080 and the proxy serves HTTPS :443. If policy requires end-to-end TLS, the app must serve HTTPS on an explicitly configured port/certificate and NGINX must use `proxy_pass https://...` to match. Never mix the two designs.

## 17. Firewalls, Security Groups, VPC, and Client Proxy Environment

If the app listens on `0.0.0.0:8080` yet a remote machine times out:

1. Verify the remote caller targets the **right private/public IP** of the VM/node/LB.
2. Test from the same host, then same subnet, then outside the subnet.
3. Inspect OS firewalls, cloud security groups/source CIDRs, NAT, route tables, and network policies.
4. Check DNS A/AAAA records and LB certificate/Host settings.
5. Check cloud LB target health and backend port.
6. Never open inbound `0.0.0.0/0:8080` if architecture only permits traffic from the LB; apply minimal allowed source ranges.

Commands:

~~~bash
# If installed in the OS:
getent hosts shop.example.test
nslookup shop.example.test
curl -v --connect-timeout 3 http://private-host:8080/ping
~~~

PowerShell:

~~~powershell
Resolve-DnsName shop.example.test
Test-NetConnection shop.example.test -Port 443
~~~

**Client-side HTTP proxies** also matter. On corporate machines, `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` can send cURL through the corporate proxy instead of connecting directly. Compare:

~~~bash
curl -v http://127.0.0.1:8080/ping
curl -v --noproxy '*' http://127.0.0.1:8080/ping
~~~

If the second succeeds, inspect outbound proxy settings. Do not treat a corporate proxy's 502 as proof Spring is not listening.

## 18. Management Server Separate from Main App Server

For example:

~~~properties
server.port=8080
management.server.port=9091
~~~

Actuator can run on a separate management web server. Then:

~~~text
GET http://localhost:9091/actuator/health -> HTTP 200
GET http://localhost:8080/ping          -> may still fail
~~~

A passing health check on the management port **does not prove** the main application port accepts connections. When the two ports are separated, health groups do not necessarily share the same server infrastructure.

With Actuator in Spring Boot 3.3:

~~~properties
management.endpoint.health.probes.enabled=true
management.endpoint.health.probes.add-additional-paths=true
~~~

can expose `/livez` and `/readyz` on the **main server port** so probes evaluate the actual listener serving traffic. Test paths against your runtime's context and security mappings.

**Avoid publicly exposing** `/actuator/env`, `/actuator/configprops`, or `/actuator/heapdump` for debugging: they can leak configuration, secrets, and internals. Use strong network/authorization controls and avoid pasting tokens into tickets.

### Readiness/Liveness in Kubernetes

- A `Running` Pod is not necessarily `Ready`.
- A `Ready` Pod does not prove public Ingress/TLS works.
- Management health `UP` does not replace a synthetic HTTP test on the main port.
- A wrong readiness path or Spring Security blocking health can leave Pods permanently `NotReady`, leaving Ingress/Service with no endpoints.
- Liveness should not naively depend on a shared DB, avoiding restart storms during transient dependency outages.

## 19. 404, 401, 403, and CORS Are Not TCP Bind Failures

### 404

If the server returns HTTP 404, check:
- Is `@RestController` covered by component scan?
- Does `@GetMapping` have the right method/URI/casing/trailing slash?
- Are `server.servlet.context-path`/`spring.mvc.servlet.path`/WAR context right?
- Does NGINX strip/preserve the prefix properly?
- Did the request hit the right backend or the ingress default backend?
- Does a React/WebFlux app route differently from Servlet Spring MVC?

### 401 / 403

If you get a response, a security layer received the request. Check:
- Spring Security filter chain, authentication, authorization.
- CSRF for browser sessions and non-safe HTTP methods.
- API gateway auth/WAF/allowlist.
- Whether `OPTIONS` preflight is allowed through filters/proxies.
- Whether `Host`/`Authorization`/`Cookie` headers were dropped or altered by the proxy.

Do not change `server.port` to "fix" 401/403.

### CORS

A browser on `http://localhost:3000` calling an API at `http://localhost:8080` is **cross-origin because the ports differ**, even on the same host. cURL does not enforce CORS like browsers, so cURL returning 200 while the browser reports a CORS error is completely possible.

Allowlist explicit origins/methods/headers and let `OPTIONS` preflight pass through Spring Security/NGINX. Never pair wildcard `Access-Control-Allow-Origin: *` with credentials; safe policies require explicit trusted frontend origins.

## 20. Gateway Errors 502, 503, 504: Separating Upstream Path, Port, and Timeout

### 502 Bad Gateway

The gateway did not receive a valid response from upstream:
- `proxy_pass` points to the wrong port/IP/hostname (`127.0.0.1` in the wrong container namespace).
- Spring binds loopback while the gateway connects to Pod IP.
- TLS mismatch: proxy sends HTTPS → HTTP app, or vice versa.
- K8s Service has no `Ready` backend or wrong `targetPort`.
- Pod stopped/restarted while the proxy reused a stale connection.
- Upstream reset the connection or returned an invalid HTTP response.

Inspect NGINX `error_log` (e.g., `connect() failed`/`connection refused`) alongside Spring logs at the same timestamp. If the request never reached Spring, the app access log will have no entry.

### 503 Service Unavailable

Possible causes:
- Spring/app performing intentional load shedding.
- Gateway/Ingress has no `Ready` upstream.
- Rolling deployment / graceful shutdown.
- Maintenance mode or rate/concurrency limit policy.

A `503` **does not automatically prove** the Spring listener rejected it; identify which layer emitted the response.

### 504 Gateway Timeout

The gateway waited too long for upstream. NGINX `proxy_read_timeout` is the interval between two successive read operations from upstream, **not a fixed total deadline per request**. The app might still be running a DB query or may have already committed even though the client saw 504. For `POST`s with side effects, ensure idempotency/reconciliation before retrying.

### Direct vs. Proxy Comparison Table

| Direct origin | Via proxy | Investigation path |
| --- | --- | --- |
| 200 | 502 | IP/port/upstream scheme/network namespace |
| 200 | 404 | Host route, `proxy_pass` URI rewrite/context |
| 200 | Redirect loop | Forwarded proto/Host/prefix or TLS redirect |
| 200 | 401/403 | Gateway auth/WAF, forwarded headers, CORS |
| Slow | 504 | App/downstream latency and timeout budget |
| Refused | 502 | App listener/port/bind before proxy |
| 200 | Browser TLS error | Certificate/SNI/chain, not controller |

## 21. Differences Across Tomcat, Jetty, Undertow, Reactor Netty, and External WAR

### Embedded Servlet

Spring Boot `spring-boot-starter-web` uses Tomcat by default. You can swap to Jetty/Undertow via starter dependencies, and `server.port`/`server.address` remain shared properties across embedded servers. Certain connector-specific options differ by engine; do not copy `server.tomcat.*` to Jetty expecting it to work.

### WebFlux/Reactor Netty

`spring-boot-starter-webflux` typically runs on Reactor Netty when no Servlet starter is added. `server.port`/`server.address` still matter, whereas `server.servlet.context-path` and `spring.mvc.servlet.path` are not the path-prefix mechanism for WebFlux. Use `spring.webflux.base-path` when a global prefix is needed on the reactive stack.

If both `starter-web` and `starter-webflux` are present, Boot 3.x normally prioritizes Spring MVC Servlet. Do not conclude the server is Netty just because code uses `WebClient`.

### External WAR

When deploying a WAR to external Tomcat:
- Tomcat's connector configuration determines the port and public bind.
- The WAR filename/context descriptor determines the context path.
- `SpringBootServletInitializer` initializes the app on container deploy.
- `server.port` inside the packaged app does not make external Tomcat open a separate port.
- External Tomcat may host multiple WARs in a shared JVM; identify the app context before testing.

### Management Context

If `management.server.port` differs from `server.port`, the health listener is a separate endpoint. Do not treat reaching management `:9091` as proof that the main API `:8080` is reachable.

## 22. 12-Step Debugging Workflow to Avoid Fixing the Wrong Layer

1. **Record the exact failing URL:** scheme, Host, port, prefix, route, HTTP method; e.g., `https://shop.example.test/api/ping`.
2. **Inspect the runtime:** Java process, embedded JAR/Netty, or external Tomcat WAR? Is there a real HTTP listener?
3. **Read current logs:** port, active profiles, context path, startup errors, and PID (do not read stale logs).
4. **Check effective config:** `server.port`, `server.address`, env/profile/CLI, port `0`/`-1`, non-web type.
5. **Inspect listening sockets in the right namespace:** `ss`/`lsof`/`Get-NetTCPConnection`; loopback vs. wildcard, IPv4 vs. IPv6.
6. **Test direct local HTTP path:** does cURL `/ping` return 200 `pong`? If 404/401, inspect app routes/security.
7. **Call the private IP from a network peer:** if it fails, check bind/firewall/SG/routing.
8. **If Docker:** compare Host:Container port mapping, container Java listener, and proxy DNS.
9. **If Kubernetes:** Pod Ready, Service selector/`EndpointSlices`, Service port→`targetPort`, `NetworkPolicy`.
10. **If proxy/Ingress:** Host/path/TLS/upstream scheme+port/rewrite, forwarded-header trust, and proxy error logs.
11. **If browser differs from cURL:** check CORS, cookies, HSTS, client HTTP proxy, certs, redirect chain, and IPv6.
12. **After changing one setting:** restart/roll out, re-test via direct, Service, and public URLs, and record status/body/`Location`/timestamps.

### Decision Flow

~~~text
App logs Started, client cannot reach it
  |
  v
Is there an HTTP listener on the right IP:port?
  | NO -> starter/webApplicationType, server.port=0/-1,
  |       server.address, port conflict, process startup
  v
Does local curl /ping return 200?
  | NO -> protocol, context path, mapping, security
  v
Can a private-network peer reach app IP:port?
  | NO -> loopback bind, firewall, route, container NAT
  v
Does Docker/Kubernetes Service reach the app?
  | NO -> published port, targetPort, selector, readiness
  v
Are public Ingress/DNS/Host/TLS right?
  | NO -> ingressClass, DNS, SNI, certificates, firewall
  v
Does public path /api/ping map properly?
  | NO -> proxy_pass URI, slash, prefix, context
  v
Does redirect /jump use the right https/domain/prefix?
  | NO -> trusted forwarded headers, TLS termination
  v
Does the browser still report errors?
         CORS, auth, CSRF, cookie SameSite,
         HSTS, client proxy/cache
~~~

## 23. Scenario Exercises with Answers

**1.** `server.port=8080` in source, yet the JVM is launched with `--server.port=9090`. Which port actually serves HTTP?

**Answer:** 9090 under default Spring Boot command-line precedence. Confirm via startup logs/socket and locate the override source.

**2.** `server.port=0`, app Started, cURL on 8080 gets connection refused.

**Answer:** The server picked an ephemeral port. Read the actual startup port or `@LocalServerPort` in tests.

**3.** Does `server.port=-1` necessarily crash the app?

**Answer:** No. Boot can still initialize `WebApplicationContext` without exposing HTTP endpoints.

**4.** `server.address=127.0.0.1`, cURL localhost returns 200, yet LAN host IP fails.

**Answer:** The listener is bound to loopback only. Bind the needed interface and open minimal network policy instead of disabling the firewall.

**5.** Docker `-p 18080:8080`, yet calling `localhost:8080` on the host fails.

**Answer:** The host port is 18080. You must call `localhost:18080`.

**6.** Docker container uses `SERVER_ADDRESS=127.0.0.1` and ports are published properly.

**Answer:** NAT sends traffic to the container IP, not container loopback. Bind `0.0.0.0` inside the container, and restrict host publish to `127.0.0.1` if needed.

**7.** NGINX container proxies to `127.0.0.1:8080`, while Spring runs in another container.

**Answer:** Loopback belongs to the NGINX container. Use service DNS `web:8080` or the real network target.

**8.** K8s Pod listens on 8080, Service `targetPort` is 9090.

**Answer:** The Service forwards to a port with no listener. Change `targetPort` to 8080 or a named port matching the Pod.

**9.** `kubectl port-forward svc/network-lab 18080:80` works, yet public Ingress returns 502.

**Answer:** `port-forward` is a debug path separate from Ingress. Check ingress controller/class, backend Service name/port, endpoints, upstream errors, and TLS/LB.

**10.** Where does NGINX `location /api/` + `proxy_pass http://app:8080;` forward `/api/ping`?

**Answer:** It normally preserves `/api/ping`. If the app only maps `/ping`, that returns 404. Add a trailing URI slash to `proxy_pass` to strip the prefix when that is the contract.

**11.** HTTPS browser gets redirected to `http://10.0.0.20:8080/ping`.

**Answer:** The app does not know the external scheme/host/prefix, or proxy forwarded headers/trust policy are missing. Check `server.forward-headers-strategy`, gateway header overwriting, and `Location`.

**12.** Browser reports CORS, while `curl http://localhost:8080/ping` returns 200.

**Answer:** CORS is a browser cross-origin policy, not a TCP socket failure. Configure `OPTIONS`/allowed origins/security.

**13.** Actuator health on 9091 reports `UP`, yet `/ping` on 8080 fails.

**Answer:** The management listener can be separate. Test the main server port and real route; consider enabling additional readiness paths on the main port.

**14.** Proxy gets 504 after 30s and the client retries a `POST` creating an order.

**Answer:** A 504 does not guarantee the server failed to commit; use an idempotency key and durable reconciliation before retrying non-idempotent requests.

**15.** DNS has both A and AAAA; `curl -4` succeeds while `-6` fails.

**Answer:** IPv6 listener/routing/firewall is inconsistent with DNS AAAA; align the dual-stack topology instead of blaming the controller.

**16.** A WAR in external Tomcat sets `server.port=9090`, yet external Tomcat only listens on 8080.

**Answer:** The external servlet container owns connector ports. Configure Tomcat's connector, and test the WAR context path such as `/app/hello`.

## 24. Checklist Before Marking the Incident Resolved

- [ ] Identified the exact **client URL** (scheme, hostname, port, prefix, route)?
- [ ] Is an actual HTTP server running (not a batch/non-web app or `port=-1`)?
- [ ] Effective port is not overridden by CLI/profile/env/management?
- [ ] Listening socket matches the right bind IP/IPv4/IPv6 and process/PID?
- [ ] Direct cURL to the app succeeds within the same network namespace?
- [ ] Remote private-network connectivity works through firewall/SG/VPC?
- [ ] Docker `-p`, `EXPOSE`, and container server port/address are consistent?
- [ ] Kubernetes Service port/`targetPort`, selectors, and Pod Ready/endpoints are right?
- [ ] Ingress controller/class/Host/path/backend Service port/TLS are right?
- [ ] NGINX `proxy_pass` has the right scheme, upstream address, and URI rewrite/trailing slash?
- [ ] Context path/MVC servlet path/WebFlux base path/external WAR context are right?
- [ ] Forwarded headers come only from trusted proxies and generated redirects are accurate?
- [ ] HTTP↔HTTPS, SNI/cert, and HSTS are consistent?
- [ ] CORS/auth/CSRF HTTP errors are not confused with connection refused?
- [ ] Management health and main HTTP listener tested separately?
- [ ] 502/503/504 correlated across edge/proxy/origin rather than reading a single log?
- [ ] Diagnostic `/where` or Actuator config endpoints are not exposed publicly?
- [ ] Re-tested from local, host, in-cluster Service, and public ingress after the fix?
- [ ] Recorded runbook: URL, port map, config source, response, and root cause?

**Conclusion:** When an app reports `Started` yet cannot be reached, inspect **the actual socket, bind address, called port, and caller's network** first. If direct origin works, check Docker/Kubernetes/Ingress/NGINX/TLS and forwarding next. An HTTP 404 is a path/router issue; TCP refused is a socket/network issue; 502/504 can come from the gateway. Classifying the failure accurately and verifying each hop solves the problem without breaking security or changing the wrong layer.
