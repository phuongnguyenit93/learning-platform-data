# 400, 413, or 431 Due to Input Data and Size Limits

## 1. Objectives and Symptoms to Diagnose

In **Debugging and Upgrades** for **Spring Boot - web-runtime**, many request failures are described identically by users: "sending data failed." In reality, a request can be blocked at a proxy, Tomcat's HTTP parser, a Spring MVC message converter, Jakarta Bean Validation, or business code. Three commonly confused codes are:

- **400 Bad Request:** request syntax or content has an issue preventing the server from processing it, such as invalid JSON, wrong data type, failed input constraint, or malformed HTTP request.
- **413 Content Too Large:** the request **content/body** exceeds what the server is willing or able to process. An older name often seen is **413 Payload Too Large**; the code is still 413.
- **431 Request Header Fields Too Large:** one or more **request headers** or the combined header section is too large; e.g., bloated Cookie or Authorization headers.

Key takeaway: **an HTTP status describes the outcome seen by the client, not automatically which component rejected it.** Tomcat may return **400** for an oversized header at parser level, even though 431 is the dedicated status; an ingress may return 413 before the request reaches the app. Searching only for `@ExceptionHandler` in Spring MVC may turn up nothing.

This article provides:
1. How to distinguish 400/413/431 from 414, 415, 422, and gateway errors.
2. A diagram of requests flowing through proxy, connector, filters, converters, validation, and Controller.
3. Actual configuration for **Spring Boot 3.3.13 + embedded Tomcat 10.1** and version-upgrade traps.
4. A runnable **Java 17 + Spring Boot MVC** project returning 400/413/431 via verifiable logic.
5. Real HTTP tests separating application policy errors from Tomcat header-parser or upload-parser rejections.
6. A diagnostic runbook for NGINX/Ingress/Gateway environments, plus security and boundary-testing checklists.

Do not use demo numbers as production thresholds: measure real request sizes, privacy needs, memory capacity, proxies, and service latencies.

## 2. Map of Layers That Can Reject a Request

~~~text
Client (curl, browser, mobile app)
        |
        v
DNS / TLS / WAF / CDN / API Gateway
        |-- header/cookie too large: 400 or 431
        |-- request body too large: 413
        |-- URI too long: 414
        |-- rate limit: 429
        |
        v
Ingress / reverse proxy (if present)
        |-- header buffers / request-line limits
        |-- body limit / buffering / timeout
        |
        v
Tomcat HTTP Connector (Spring Boot embedded)
        |-- HTTP request line + headers parser
        |-- server.max-http-request-header-size
        |-- maxPostSize for form parameter parsing
        |-- maxSwallowSize for aborted uploads
        |
        v
Servlet filters / Spring Security
        |-- authentication / CSRF / custom request limits
        |
        v
DispatcherServlet / Spring MVC
        |-- HandlerMapping: path, method, consumes, produces
        |-- HttpMessageConverter (Jackson JSON)
        |-- MultipartResolver / Servlet Part parser
        |-- @Valid / method validation
        |
        v
Controller / service / domain rules
        |
        v
HTTP 2xx, 4xx, 5xx, or connection closed
~~~

**The exact order depends on deployment.** A CDN, WAF, or API Gateway can stop a request before Tomcat. If the request never enters Spring MVC, **`@ControllerAdvice` cannot rewrite the status or body** of a response generated by the proxy or container.

Therefore distinguish:
- **App received the request and returned an error**: trace/log exists in `DispatcherServlet` or Controller.
- **Connector/parser rejected before mapping**: only Tomcat connector logs/error responses exist; Spring MVC handlers are never invoked.
- **Ingress/WAF rejected before backend**: the app never sees the request at all, even though the client receives an HTTP status.
- **Network abort**: the client receives no complete HTTP response; may observe connection reset, EOF, timeout, or HTTP/2 stream reset.

## 3. Distinguishing 400, 413, and 431 by HTTP Semantics

| Code | What is limited/invalid | Example | Initial fix direction |
| --- | --- | --- | --- |
| **400 Bad Request** | Malformed request or invalid fields | Bad JSON syntax; `quantity=0` with `@Min(1)`; illegal char in header | Fix syntax/data; locate rejecting layer |
| **413 Content Too Large** | Request **body/content** exceeds policy/capacity | 70 KiB file upload with `max-file-size` 64 KiB; raw body over limit | Reduce body, chunk/upload protocol, or raise limits per policy |
| **431 Request Header Fields Too Large** | A header or total headers too large | Accumulated cookies, huge JWT in Authorization | Shrink headers, cookie scope/claims, check proxy limits |
| **414 URI Too Long** | Request-target/path/query too long | Stuffing large JSON into a GET query string | Shorten URI; move payload into body if semantically valid |
| **415 Unsupported Media Type** | Unsupported `Content-Type` | Sending `text/plain` to a JSON-only endpoint | Send the proper `Content-Type` |
| **422 Unprocessable Content** | Syntactically valid body/type failing domain semantics | Custom API rule | Check business rule; do not assume Bean Validation returns 422 |
| **429 Too Many Requests** | Caller exceeds rate limit/quota | API key over call limit | Backoff/quota; do not raise body/header limits |
| **502/504** | Gateway failed communicating with upstream | Upstream close or timeout | Inspect ingress, proxy, and backend accordingly |

**RFC 9110:** 413's current standard name is **Content Too Large**. Many frameworks, constants, and older blogs still say **Payload Too Large**; it is not a different code. **RFC 6585** defines 431. Do not assume from a status code that identical requests will always produce identical error JSON across all servers.

### 3.1. Two Requests with Oversized Headers Can Return 400 or 431

In HTTP semantics, 431 is the natural code when header field(s) are too large, yet **Tomcat's HTTP parser can return 400** when its request header buffer overflows. Another gateway might return 431 for the same request. This is an implementation/layer difference, not evidence of bad JSON body syntax.

If the application inspects a header smaller than Tomcat's limit and deliberately returns 431, the status is predictable; if **Tomcat's limit is exceeded before MVC**, the controller has no opportunity to emit a custom 431.

### 3.2. `Content-Length` Is Not Header Length

Example:

~~~http
POST /api/upload HTTP/1.1
Host: localhost:8080
Content-Type: multipart/form-data; boundary=...
Content-Length: 73000
Cookie: session=...
~~~

- **`Content-Length`** is a header field, yet the **value `73000`** does not make the request header 73,000 bytes long. It declares the advertised HTTP body size.
- If the body exceeds the upload limit, 413 may occur.
- If **`Cookie`** holds tens of kilobytes of characters, the request header section can exceed the limit and trigger 400/431 **before the body is ever read**.
- If HTTP message framing is invalid (e.g., conflicting `Content-Length`/`Transfer-Encoding`), the HTTP parser may return 400 for malformed framing, not 413.

### 3.3. Not Every 400 Is About Size

A 30-byte JSON body can still return 400 due to a missing brace, wrong type, or failed `@Valid`. A 10,000-byte URL can trigger 414 or 400 at the connector; it does not make the body large. When classifying an incident, start from **method, path, headers, body length, `Content-Type`**, and **rejecting layer**.

## 4. Causes of HTTP 400 in Spring MVC

### 4.1. Syntactically Invalid JSON

~~~http
POST /api/orders HTTP/1.1
Content-Type: application/json

{"item":"book","quantity":2
~~~

Jackson cannot parse JSON missing its closing brace. Spring MVC typically throws **`HttpMessageNotReadableException`** and returns 400 via exception resolution. The controller may **never be called**.

Another case: valid JSON syntax that cannot deserialize into the DTO type:

~~~json
{"item":"book","quantity":"many"}
~~~

If `quantity` is `Integer`, Jackson cannot coerce `"many"` into a number. This is not a `@Min` error; it happens before Jakarta Bean Validation.

### 4.2. Valid JSON Violating Constraints

~~~java
record OrderRequest(
    @NotBlank String item,
    @NotNull @Min(1) @Max(100) Integer quantity
) {}
~~~

With **`@Valid @RequestBody OrderRequest`**, payload:

~~~json
{"item":" ","quantity":0}
~~~

triggers **`MethodArgumentNotValidException`**, returning 400 under Spring MVC defaults. **`spring-boot-starter-validation`** must be present for constraints to take effect in Boot 3.3.

**`@NotBlank`** applies to Strings; **`@NotNull`** forbids null; **`@Min(1)`** does not apply to Strings as a length check; **`@Size(max=...)`** bounds String/Collection lengths. These annotations validate **after JSON deserialization**, so they do not protect against a multi-hundred-megabyte HTTP body allocating memory during parsing.

### 4.3. Invalid Query/Path Parameters

For example **`GET /api/orders?limit=abc`** when a controller expects `int limit`: conversion failure can return 400. Missing a required `@RequestParam` can also return 400. In Spring Framework 6.1, constraints placed directly on MVC handler method parameters like **`@Min @RequestParam`** can produce **`HandlerMethodValidationException`** when built-in method validation is active.

**Do not assume every 400 comes from `@Valid`**, and do not rely solely on `@ExceptionHandler(MethodArgumentNotValidException)` to control all input errors.

### 4.4. Malformed HTTP Headers at the Connector

Headers with disallowed characters, malformed request lines, conflicting framing, or oversized headers can be rejected by Tomcat's HTTP parser **before the Controller**. Some oversized-header cases yield 400; this is why you must read connector logs, not just search for validation errors.

### 4.5. 400 Is Not Always a Business "User Error"

A misconfigured reverse proxy can inject invalid headers or duplicate/conflicting framing, causing the backend to return 400. Inspect raw requests across hops without leaking tokens, especially when failures appear right after a deploy or proxy/server upgrade.

## 5. HTTP 413: Body Content and Upload Limits

**413** means the server refuses to process the request content because it exceeds what the server allows or can handle. For transient conditions, RFC 9110 suggests considering **`Retry-After`** to indicate when to retry; however, if the payload violates a fixed policy limit, retrying the **same payload** is futile.

Common sources of 413:
- Reverse proxy body-size limits.
- API Gateway/WAF request-size policy.
- Spring multipart parser sees a **single file** exceeding `max-file-size`.
- Total multipart request exceeds `max-request-size`, even when each individual file is under the limit.
- Application explicitly bounding a raw stream or decoded content.
- A data-processing service returning 413 per business contract.

**Do not automatically raise Spring settings whenever you see 413.** If nginx/ingress returns 413 before the request reaches Tomcat, increasing Spring's multipart `max-file-size` changes nothing.

### 5.1. Spring Boot 3.3 Multipart Defaults

In Spring Boot 3.3:
- **`spring.servlet.multipart.enabled=true`**.
- **`spring.servlet.multipart.max-file-size=1MB`**.
- **`spring.servlet.multipart.max-request-size=10MB`**.
- **`spring.servlet.multipart.file-size-threshold=0B`**.
- **`spring.servlet.multipart.location`** specifies the temporary path when intermediate multipart files are written.

Example:

~~~yaml
spring:
  servlet:
    multipart:
      enabled: true
      max-file-size: 64KB
      max-request-size: 128KB
      file-size-threshold: 0B
~~~

This is a lab setting; 64KB/128KB are intentionally small to trigger errors easily. If a **70KiB** file exceeds `max-file-size` 64KB, the Servlet multipart parser throws a size exception; Spring Framework maps it to **`MaxUploadSizeExceededException`**. In Spring Framework 6.1, this exception implements **`ErrorResponse`** with status **413**. Still, what the client observes **depends on** multipart handling, unread request body, Tomcat swallow behavior, proxies, and the network.

### 5.2. Total Multipart Request Size Differs from File Size

A multipart request contains:
- Bytes of each file.
- Text fields.
- Boundaries and **per-part headers**.
- Multiple parts/files.

Thus a 60KiB file can stay under `max-file-size=64KB` while the total request approaches or exceeds `max-request-size=128KB` when multiple parts exist. Check both per-file limits **and** total request limits; never measure only the size of a single received `MultipartFile`.

### 5.3. Why Isn't the `Content-Length` Header Enough to Protect Bodies?

A client can use **`Transfer-Encoding: chunked`** in HTTP/1.1, where `Content-Length` is absent. Even when `Content-Length` is present, trusting the header without counting actual received bytes is insufficient for a generic body limit. Proxies can decompress/buffer/transform payloads, changing sizes before and after decoding.

**Rule:** enforce limits on **actual bytes** while reading, or configure an ingress/server supporting real body limits. Never write a filter checking only `Content-Length` and claim all requests are protected—especially with streaming/chunked transfers.

### 5.4. Large JSON Is Not Automatically Bounded by Multipart Properties

**`spring.servlet.multipart.max-request-size`** governs **multipart**, not a generic upper bound for **`application/json`**. A large JSON body can be parsed by Jackson and allocate heap before `@Size`/`@Valid` ever sees the DTO. Enforce body limits at ingress/API Gateway or via a streaming parser/bounded reader in the app.

There is no single Spring Boot 3.3 property named `server.max-http-request-body-size` that enforces identical semantics across all embedded Servlet servers and content types. Use the proper server/codec/protocol settings and test each path.

## 6. Tomcat `maxPostSize`, `maxSwallowSize`, and Three Distinct Limits

**Embedded Tomcat 10.1** has settings that must be kept distinct:

| Spring Boot 3.3 property | Boot 3.3 default | What it controls |
| --- | --- | --- |
| **`server.max-http-request-header-size`** | **8KB** | Request line + total header names/values for Tomcat |
| **`server.tomcat.max-http-form-post-size`** | **2MB** | Content size limit when **parsing form request body into parameters** |
| **`server.tomcat.max-swallow-size`** | **2MB** | Max request body bytes Tomcat will swallow after an aborted upload |
| **`spring.servlet.multipart.max-file-size`** | **1MB** | Single uploaded file in a multipart request |
| **`spring.servlet.multipart.max-request-size`** | **10MB** | Entire multipart request |
| **`spring.servlet.multipart.file-size-threshold`** | **0B** | Threshold at which multipart contents are written to disk |
| **`server.tomcat.max-parameter-count`** | Check exact Tomcat/Boot build | Number of parameters parsed from query/form |
| **`server.tomcat.max-part-count`** | Check exact Tomcat/Boot build | Number of allowed multipart parts |
| **`server.tomcat.max-part-header-size`** | Check exact Tomcat/Boot build | Header bytes allowed per individual multipart part |

**Do not consult docs of another Boot/Tomcat version to conclude production defaults.** Defaults such as `max-part-count` and `max-parameter-count` have changed across releases. Check the application properties of **3.3.13** and the effective runtime configuration.

### 6.1. `max-http-form-post-size` Is NOT a Generic POST-Body Limit

The name makes it sound like "all HTTP POSTs are capped at 2MB." Tomcat docs specify **`maxPostSize`** applies when the container parses a request body into **request parameters**, primarily **`application/x-www-form-urlencoded`** and non-file form fields in **`multipart/form-data`**. It is **not** a generic size limit for a full JSON body and does not bound binary upload parts like `spring.servlet.multipart.max-file-size`.

If a client sends 3MB of **`application/json`**, you cannot rely on `max-http-form-post-size=2MB` to guarantee 413. Configure proxy/app body limits or controlled streaming reads.

### 6.2. `max-swallow-size` Is Not `max-upload-size`

Once Tomcat knows an upload will be rejected while the client is still transmitting, it can **read and discard (swallow)** a number of bytes so the connection stays clean enough to send a proper response. **`server.tomcat.max-swallow-size=2MB`** caps how many bytes are swallowed after the request is aborted.

If the client keeps pushing a very large body, Tomcat may **close/reset the connection**, preventing the client from reading the 413 JSON response even though the backend caught the limit. Setting **`max-swallow-size=-1`** for unlimited swallowing avoids some protocol symptoms at the cost of higher bandwidth/CPU risk; **do not use it as an unchecked quick fix**.

**Keep them separate:**
- Multipart `max-file-size`: is this individual file allowed?
- Multipart `max-request-size`: is the total multipart request allowed?
- `maxSwallowSize`: after the body is rejected, how many more bytes are drained before dropping the connection?

### 6.3. Check Per-Part Count and Header Limits Separately

A request with hundreds of empty parts can consume RAM/CPU even when total bytes are low. Tomcat also caps multipart part counts, per-part header sizes, and request parameter counts. These differ from **top-level HTTP request headers**; do not confuse multipart per-part headers with **`server.max-http-request-header-size`**.

In some cases Tomcat may ignore parameters beyond the threshold or return an error depending on implementation/filters/config; never promise it always returns 413. Test against the real runtime.

## 7. HTTP 431 and Oversized Cookie/Authorization Headers

**431 Request Header Fields Too Large** is a header-section failure, not a JSON or file-upload error. Common causes:
- Browser sends many Cookies because the app splits session data or uses overly broad domains/paths.
- JWT carries too many claims/roles, or `Authorization` holds a huge credential.
- Proxies append many `X-Forwarded-*` / tracing headers across multiple hops.
- Client sends a huge number of header keys (header count).
- Frontend/backend stores session data in cookies without clearing old cookies.
- Gateway and Tomcat enforce different request-header-size policies.

### 7.1. How Does Tomcat Compute Header Size?

Spring Boot's **`server.max-http-request-header-size`** on Tomcat applies to the **request line plus header names, values, and framing bytes like spaces and line terminators** per Tomcat's HTTP parser—not a single header value alone.

For example, a request with:
- A long URI/path/query.
- 5KB Cookie.
- 2KB Authorization.
- 1KB tracing headers.
- Host/User-Agent/Accept headers.

can easily exceed **8KB** in total even when each header looks modest on its own. With HTTP/2, header compression and header-list semantics differ from HTTP/1.1; gateways may enforce limits on the **decompressed header list** or header count. Never use raw wire packet size to deduce buffer policies across all hops.

### 7.2. 431 Is Not Guaranteed on Tomcat

Tomcat documentation for **`maxHttpRequestHeaderSize`** describes the byte cap on request line + headers. When exceeded, Tomcat can reject at parser level with **400 Bad Request** or close the connection depending on runtime; the controller **never runs**, so an MVC `@ExceptionHandler` cannot customize it into a `ProblemDetail` 431.

If an API contract requires 431 for a **business header** like `X-Client-Tag`, validate that header inside a controller/filter **once Tomcat has accepted the request**. The lab includes both scenarios to make this clear.

### 7.3. Do Not Raise the Header Limit Unboundedly

Tomcat can allocate request-header buffers across many concurrent requests. Per Tomcat docs, raising `maxHttpRequestHeaderSize` to **1MB** with **100 concurrent requests** can consume roughly **100MB of heap** just for request-header buffers. Raising 8KB to 1MB to accommodate a bloated Cookie opens a memory DoS surface.

**Prefer fixing the root growth:** prune unnecessary cookies, trim JWT claims, drop non-essential forwarding headers, use server-side session storage, or tighten cookie domain/path. Raise the limit only after measuring real distributions and setting a sensible upper bound across all hops.

### 7.4. 431 vs. 414

- **431:** header section too large, commonly Cookie/Authorization.
- **414:** request-target/URI too long, e.g., cramming tens of KB of JSON into a GET query.
- A connector may emit **400** for an overly long request line or header buffer overflow.

Do not take a "URI too long" error and simply raise the header limit. Inspect raw **path/query/header sizes** and exact configs.

## 8. When Upgrading Spring Boot 2 to Boot 3

One migration trap involving HTTP header sizes:

- Spring Boot 2 used **`server.max-http-header-size`** (depending on version).
- Spring Boot 3 introduced **`server.max-http-request-header-size`**, consistently scoping **request headers**.
- The old property was deprecated and earlier behavior varied across embedded servers; do not copy old config expecting it to bound response headers identically.

Spring Boot 3 also uses the **Jakarta Servlet** namespace (`jakarta.servlet.*` instead of `javax.servlet.*`) and Spring Framework 6. Custom filters or multipart code importing old packages may fail to compile.

To debug after an upgrade:
1. Check the dependency tree: which Spring Boot/Tomcat/Servlet versions are actually running?
2. Compare effective configuration and rename properties properly.
3. Check maximum header limits at **Ingress/API Gateway** before tuning the server.
4. Test identical payloads/headers before and after the upgrade.
5. Inspect Tomcat parser logs alongside client HTTP statuses, not just Controller logs.
6. Check `maxPostSize`/multipart defaults and HTTP/2 connection settings if changing servers.
7. Run regression tests for 400/413/431/414, including `Content-Type` and error bodies.

## 9. Spring Boot 3.3.13 Lab: Clearly Separating 400, 413, and 431

The project below exercises each case without **conflating app-level rejections with Tomcat rejections**.

**Endpoints:**
- **`POST /api/items`** — JSON DTO with `@Valid`; invalid or malformed bodies return **400**.
- **`POST /api/raw`** — reads **at most 2,049 bytes** of the raw request to enforce a **2,048-byte** cap; exceeding it returns **413** via application policy, even without `Content-Length`.
- **`GET /api/header-check`** — an `X-Client-Tag` header exceeding **256 UTF-8 bytes** causes the app to deliberately return **431**.
- **`POST /api/upload`** — Servlet multipart with **64KB/file** and **128KB/request** limits; max upload exceptions are converted by advice into `ProblemDetail` 413 when the exception reaches the MVC handler.
- **`GET /api/ping`** — tiny endpoint to test when Tomcat's header parser rejects a request before the Controller.

**Do not confuse the lab cases:** deliberate 431 from `/api/header-check` checks **a single business header**, whereas **`server.max-http-request-header-size=8KB`** is enforced by Tomcat across the entire request header section. A 300-byte `X-Client-Tag` reaches the Controller and gets 431; a 12KB header can be blocked by Tomcat before the Controller with 400.

    @PostMapping(
        path = "/api/raw",
        consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE
    )
    ResponseEntity<?> readRaw(HttpServletRequest request)
            throws IOException {
        // Read at most 2049 bytes instead of calling readAllBytes()
        // before checking: doing otherwise could allocate too much.
        byte[] prefix = request.getInputStream()
                .readNBytes(RAW_LIMIT_BYTES + 1);

        if (prefix.length > RAW_LIMIT_BYTES) {
            return ResponseEntity.status(413)
                    .contentType(MediaType.parseMediaType(
                            "application/problem+json"
                    ))
                    .body(Problems.of(
                            413,
                            "RAW_TOO_LARGE",
                            "Raw request body exceeds 2048 bytes."
                    ));
        }

        return ResponseEntity.ok(Map.of(
                "status", "accepted",
                "bytes", prefix.length
        ));
    }

    @GetMapping("/api/header-check")
    ResponseEntity<?> checkHeader(
            @RequestHeader(
                value = "X-Client-Tag",
                required = false
            ) String tag
    ) {
        int bytes = tag == null ? 0
                : tag.getBytes(StandardCharsets.UTF_8).length;

        if (bytes > HEADER_LIMIT_BYTES) {
            return ResponseEntity.status(431)
                    .contentType(MediaType.parseMediaType(
                            "application/problem+json"
                    ))
                    .body(Problems.of(
                            431,
                            "HEADER_TOO_LARGE",
                            "X-Client-Tag exceeds 256 UTF-8 bytes."
                    ));
        }

        return ResponseEntity.ok(Map.of(
                "status", "accepted",
                "headerBytes", bytes
        ));
    }

    @PostMapping(
        path = "/api/upload",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
    )
    Map<String, Object> upload(
            @RequestParam("file") MultipartFile file
    ) {
        // Multipart parsing happens before this method runs.
        // Never use the client-supplied filename as a server filesystem path.
        return Map.of(
                "status", "accepted",
                "bytes", file.getSize()
        );
    }

    @GetMapping("/api/ping")
    Map<String, String> ping() {
        return Map.of("status", "ok");
    }
}

@RestControllerAdvice
@Order(Ordered.HIGHEST_PRECEDENCE)
class InputErrorAdvice {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalidFields(MethodArgumentNotValidException ex) {
        ProblemDetail body = Problems.of(
                400,
                "INVALID_FIELDS",
                "One or more request fields are invalid."
        );
        // Do not return rejected values: they may contain PII/secrets.
        body.setProperty(
                "fields",
                ex.getBindingResult().getFieldErrors().stream()
                    .map(error -> error.getField())
                    .distinct()
                    .sorted()
                    .toList()
        );
        return body;
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    ProblemDetail invalidJson(HttpMessageNotReadableException ex) {
        return Problems.of(
                400,
                "INVALID_JSON",
                "JSON body is missing, malformed or has invalid types."
        );
    }

    @ExceptionHandler(MaxUploadSizeExceededException.class)
    ProblemDetail tooLarge(MaxUploadSizeExceededException ex) {
        return Problems.of(
                413,
                "UPLOAD_TOO_LARGE",
                "Uploaded multipart content exceeds configured limits."
        );
    }
}
~~~

### 9.5. Why Do Endpoints Behave Differently?

**`POST /api/items`:**
- Jackson reads JSON and binds `name`/`quantity` to the Java record.
- **`@Valid`** enforces `@NotBlank`, `@NotNull`, `@Min`/`@Max`.
- If JSON is malformed, Spring throws `HttpMessageNotReadableException` → advice returns **400 `INVALID_JSON`**.
- If JSON is valid yet `quantity=0`, Spring throws `MethodArgumentNotValidException` → advice returns **400 `INVALID_FIELDS`**.
- When valid, returns **201** with `ItemReply`.

**`POST /api/raw`:**
- Uses `ServletInputStream.readNBytes(2049)`, **never buffering the entire body** in memory.
- Receiving 2048 bytes or fewer → **200**, with `bytes` equal to total read.
- Receiving byte 2049 → **413 `RAW_TOO_LARGE`** immediately, without needing `Content-Length`.
- Stopping past the threshold can leave unconsumed bytes; Tomcat may swallow them or close the connection, especially on very large bodies. The lab uses a 2049-byte payload so the response is easy to observe.
- If a malicious client sends a trickle chunked request without finishing, `readNBytes` can wait; production needs timeouts, max request duration/rate, ingress limits, and cancellation policies.

**`GET /api/header-check`:**
- Measures the **UTF-8 encoded size of `X-Client-Tag` alone**, not the total HTTP wire headers.
- A 300-ASCII-byte header is **below Tomcat's 8KB threshold**, so it reaches the Controller and gets **431 `HEADER_TOO_LARGE`**.
- A 12KB header can be blocked by Tomcat's parser before the Controller, with no custom body/code.
- If duplicated headers occur and the framework merges values, behavior can vary; this is strictly an **application-enforced limit on one field**, not a replacement for HTTP parser protection.

**`POST /api/upload`:**
- Servlet multipart parsing occurs before the controller method; `max-file-size`/`max-request-size` bound intermediate storage.
- `MaxUploadSizeExceededException` carries status 413 in Spring Framework 6.1; the advice produces a stable body when MVC handles the exception.
- With huge bodies while the client keeps uploading, Tomcat can close the connection due to `max-swallow-size`; not every client is guaranteed to read a JSON 413.
- The API returns the byte count without persisting the file; never trust an unsanitized original filename.

**`@RestControllerAdvice`:**
- Uses `ProblemDetail` with a **`code`** extension so clients get machine-readable error codes.
- **Do not catch `Exception.class`** and return 400 for everything, as that hides server bugs.
- Do not echo raw Jackson parse messages or `rejectedValue`; they can expose user data or internal class names.
- Errors emitted by the HTTP parser or Ingress before MVC **bypass** this advice.

### 10.1. What the Tests Guarantee

- **201** for valid JSON.
- **400 `INVALID_FIELDS`** when DTO constraints fail.
- **400 `INVALID_JSON`** when Jackson cannot parse.
- **200 at 2048 bytes** and **413 at 2049 bytes** per `/api/raw`'s own limit.
- **431 when `X-Client-Tag` has 300 ASCII bytes**; the request stays below Tomcat's 8KB cap, so the app returns 431 itself.
- **200 multipart** when the file is small.

**No test claims Tomcat will return exactly 431 for 12KB headers.** Tomcat's parser can reject before MVC with 400 or close the connection, unlike `/api/header-check`'s controlled response.

### 10.2. Why Not Assert Raw JSON Strings?

Jackson can serialize `Map`/`ProblemDetail` with different field ordering, and bodies may include `instance`/`time` or extra fields; matching a literal string is brittle. Tests should verify **status**, **`Content-Type` when part of the contract**, **machine-readable `code`**, and boundary behavior. To check `application/problem+json`, assert `Content-Type` compatibility with `MediaType.parseMediaType("application/problem+json")`.

### 10.3. Reliability of Multipart Overflow Tests

With a 70KiB multipart file and `max-file-size=64KB`, the server can return 413 if the MVC multipart exception is handled and the response reaches the client. However, proxies, Tomcat swallowing, or connection resets can yield different client observations. Run **integration tests in the target deployment** and separate HTTP outcomes from transport errors; never treat `MockMultipartFile` unit tests as proof that the container enforces size limits.

## 12. Comparing Multipart Errors and Raw JSON Errors Across Endpoints

| Request | Limit being checked | Who enforces | Expected outcome |
| --- | --- | --- | --- |
| `POST /api/items` small valid JSON | `@Valid` DTO fields | MVC Bean Validation | 201 |
| `POST /api/items` invalid JSON syntax | JSON deserializer | Jackson/MVC | 400 `INVALID_JSON` |
| `POST /api/items` JSON failing `@Min` | DTO constraints | MVC validation | 400 `INVALID_FIELDS` |
| `POST /api/raw` 2048 bytes | App 2048-byte stream limit | Controller | 200 |
| `POST /api/raw` 2049 bytes | App 2048-byte stream limit | Controller | 413 `RAW_TOO_LARGE` |
| `POST /api/upload` 4 bytes | Multipart size 64KB/file, 128KB/request | Servlet parser | 200 |
| `POST /api/upload` 70KiB | Multipart max file 64KB | Servlet parser/MVC handler | 413 or transport failure per layer |
| `GET /api/header-check` with 300B `X-Client-Tag` | Business header 256B | Controller | 431 `HEADER_TOO_LARGE` |
| `GET /api/ping` with 12KB header | Tomcat request header 8KB | HTTP parser | Often 400; 431 not guaranteed |

Both raw and multipart endpoints return 413 via **different mechanisms**: the raw endpoint counts bytes while reading; multipart is enforced by the Servlet container per `MultipartConfig`. Exceeding 8KB headers **does not mean** the request ever reached the Controller, whereas the 300B tag 431 did.

## 13. Why Can 413 "Turn Into" Connection Reset?

HTTP clients can send request bodies in several ways:
1. Send the entire body right after headers.
2. Send headers and wait for **100 Continue**.
3. Send the body with chunked transfer encoding.
4. Send over HTTP/2 streams with dedicated flow control.

When the server realizes the request is too large, it may send 413 early. If the client keeps pushing megabytes of body, the server may abort the stream/connection. Tomcat **`maxSwallowSize`** caps how many discarded bytes are read to keep the connection healthy enough for a clean response. Once exceeded, the client can see:

~~~text
curl: (56) Recv failure: Connection reset by peer
curl: (52) Empty reply from server
HTTP/1.1 413 Content Too Large
HTTP/1.1 400 Bad Request
~~~

These lines are **illustrative possible outcomes across different scenarios**, not guaranteed stdout from one curl run. Proxies and HTTP protocol versions alter behavior.

### 13.1. Do Not "Cure" Connection Reset by Making `maxSwallowSize` Unlimited

Setting **`max-swallow-size=-1`** can force Tomcat to drain unlimited rejected upload bytes, increasing network/CPU load and DoS exposure. If clients must reliably read a JSON error, examine ingress buffering, HTTP `100-continue`, edge body limits, and client upload behavior; the solution depends on deployment, with no single magic property.

### 13.2. Do Not Trust `Content-Length` from Clients

A body filter that only checks:

~~~java
// INSUFFICIENT SNIPPET for limiting every kind of HTTP body:
if (request.getContentLengthLong() > 2048) {
    response.setStatus(413);
    return;
}
~~~

is an **incomplete snippet**: for chunked requests, `Content-Length` can be `-1`, and proxies/decoders can change representation sizes. If using a filter, count **actual bytes** while handling blocking/async semantics, protecting memory before Jackson or buffering allocates large objects. The lab reads at most 2049 bytes in one explicit raw endpoint.

### 13.3. Gzip and Decompression Bombs

A tiny compressed file can decompress into massive data. **Body limits on received wire bytes** do not automatically cap sizes after decoding/decompression inside the app. For ZIP/image/PDF/archive uploads, verify:
- True format/MIME, not just the file extension.
- Uncompressed size, entry count, recursion depth, and compression ratio.
- CPU time, memory, and scratch disk.
- File scanning and isolation for untrusted content.

Never raise multipart max sizes while ignoring downstream parsing costs.

## 14. Reverse Proxies, Ingress, and Gateways: Limits May Differ

Deployments typically stack multiple thresholds:

~~~text
Browser
  |
  +-- CDN/WAF: body/header/query policy
  |
  +-- Ingress/NGINX/Envoy: max body, header buffers
  |
  +-- Kubernetes Service
  |
  +-- Tomcat: combined request line + headers limit
  |
  +-- Spring MVC multipart: max file/request
  |
  +-- Application: DTO + per-API limits
~~~

The **lowest threshold along the actual path** dictates where the request gets blocked. If ingress caps bodies at 1MB and Spring multipart max is 10MB, a 2MB file gets rejected by ingress before reaching Spring. If ingress allows 20MB while Spring `max-file-size=1MB`, a 2MB request reaches Tomcat and is rejected by the multipart parser.

### 14.1. Illustrative NGINX Config

~~~nginx
server {
    listen 80;
    server_name local.example.test;

    # Example only: size per API policy;
    # do not assume 2m fits every upload.
    client_max_body_size 2m;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
~~~

**`client_max_body_size`** is an NGINX request body limit (returning 413 when exceeded). However, this config is an **illustrative snippet**, not a complete Kubernetes Ingress deployment. In NGINX Ingress Controller, annotations/values use different names, and many controllers/load balancers do not use NGINX.

Likewise, NGINX has its own header/request-line buffer settings; never copy Tomcat property concepts blindly to NGINX. Verify the **actual Ingress Controller + version**, rather than assuming every 431 comes from Spring.

### 14.2. Do Not Arbitrarily Bump All Three Thresholds to 100MB

If file uploads must support 20MB:
1. Pick `max-file-size`/`max-request-size` to fit the business requirement plus multipart overhead.
2. Ensure ingress body limit is at least as large with reasonable headroom.
3. Verify disk/temp directory and **`ephemeral-storage`** quotas.
4. Check scanning/transform memory, timeouts, and concurrency.
5. Consider streaming or resumable uploads when files are genuinely large.
6. Keep header limits small and safe; large files **do not require large headers**.
7. Test along the real network path, not just direct localhost.

Changing one limit can shift failures from 413 at the edge to 413/500 in the app; monitor after deployment.

## 15. Bloated Cookies and Long Authorization Headers: Investigating 431

Diagnostic questions:
- Does the browser send many Cookies with overlapping domains/paths?
- Does the JWT pack an excessive list of roles/permissions?
- Does SSO/OIDC store ID/refresh tokens inside Cookies rather than server-side?
- Are tracing headers appended across multiple proxies without bound?
- Do browser requests fail only after a user has been logged in for a while?
- Does Incognito or a fresh browser profile make the error disappear?
- Does it affect one API or every request to the same host?
- Does the header rejection come from CDN, ingress, or Tomcat?

### 15.1. Do Not Log Raw Cookies or Authorization Headers to Debug

Headers can hold **session IDs, bearer tokens, and personal data**. Never log raw `Cookie`/`Authorization` in access logs, exception traces, or public tickets. Measure **header name + byte count**, estimated total request-header size, and controlled correlation IDs; redact values.

Example safe diagnostic output:

~~~text
request.path=/api/profile
request.header.cookie.bytes=7630
request.header.authorization.bytes=0
request.header.total.estimated.bytes=8050
http.status=400
rejection.layer=tomcat-parser
~~~

This is **illustrative data**, not a default Tomcat metric set. If the parser rejects the request before Spring filters, the app cannot measure every header inside the Controller.

### 15.2. Cookies Do Not Shrink Automatically When Sessions Expire

Browsers retain multiple cookies keyed by `Domain`, `Path`, `Max-Age`, and `SameSite`; logging out of one endpoint may clear only one cookie name/path. Stale cookies on other paths keep getting sent. When debugging session-related 431s, audit `Set-Cookie` and `Cookie` scopes, expirations, duplicate cookie names, and migrations across subdomains.

### 15.3. JWTs Do Not Need the User's Entire Profile

Keep access tokens focused on essential claims (subject, issuer, audience, expiry, and necessary scopes). Large role/tenant lists bloat the `Authorization` header and increase leak surface in logs. Consider server-side permission lookup/versioning instead of embedding thousands of permissions into one JWT.

### 15.4. Why Raising Header Buffers Has a Cost

Tomcat docs warn that request-header buffers consume RAM proportional to concurrency. Setting a 1MB global max to accommodate one oversized JWT lets an attacker send concurrent large-header requests to exert memory pressure. Shrinking tokens/cookies is usually far better than raising global caps unboundedly.

## 16. Problem Details and Machine-Readable Error Codes

**RFC 9457** defines Problem Details for HTTP APIs using media type **`application/problem+json`**. An app-controlled 413 response can look like:

~~~json
{
  "type": "about:blank",
  "title": "Content Too Large",
  "status": 413,
  "detail": "Raw request body exceeds 2048 bytes.",
  "instance": "/api/raw",
  "code": "RAW_TOO_LARGE"
}
~~~

**`code`** is a custom extension added by the lab; **`type`/`title`/`status`/`detail`/`instance`** are Problem Details members. Actual `type`, `instance`, and `title` values can be derived by Spring serialization/exception handlers; do not assert byte-for-byte bodies unless contracted.

For app-returned 431:

~~~json
{
  "type": "about:blank",
  "status": 431,
  "detail": "X-Client-Tag exceeds 256 UTF-8 bytes.",
  "code": "HEADER_TOO_LARGE"
}
~~~

This is a **field-subset example**, with no guarantee on key order or every response member.

**Enabling `spring.mvc.problemdetails.enabled=true`** in Boot 3.3 lets MVC format many framework errors as `ProblemDetail`, yet **does not force Tomcat's connector or Ingress to emit the same schema**. Never treat `ProblemDetail` as cosmetic cover instead of fixing server/proxy limits.

### 16.1. Do Not Put Secrets in Error Bodies

For invalid inputs:
- Return a safe **`code`** and message.
- Avoid echoing raw bodies, original filenames, `Cookie`, `Authorization`, passwords, tokens, SQL queries, or stack traces.
- For validation errors, return field names/constraint codes if permitted by contract, not `rejectedValue` automatically.
- Use opaque trace/correlation IDs rather than credentials.
- Never log huge raw payloads to memory/files just to debug 413.

An attacker can intentionally send giant or malformed payloads to saturate logging systems; sampling and redaction are part of defense.

## 17. At Which Layers Should 400/413/431 Be Tested?

| Test type | Tool | Guarantees well | Does NOT guarantee |
| --- | --- | --- | --- |
| DTO/unit validation | JUnit + Validator | `@Min`/`@NotBlank` constraints | HTTP parser/header buffers |
| MVC MockMvc | `@WebMvcTest`/`@SpringBootTest` MockMvc | Jackson, `@Valid`, `@ExceptionHandler` | Real Tomcat `maxHttpRequestHeaderSize`, OS/network |
| Embedded server HTTP | `@SpringBootTest(RANDOM_PORT)`, `TestRestTemplate` | Multipart parsing, actual HTTP status/body | Ingress/CDN/WAF behavior |
| Local curl | `curl --http1.1 -v` | Request/response through real Tomcat | External LB path |
| Staging E2E | Real DNS/Ingress/Gateway | Limits across every hop | Full production load/traffic mix |
| Client compatibility | Browser/mobile SDK | Cookies/tokens, error UX, retry | Server internal exception details |

**Never use a `MockMvc` oversized-header test as proof that Tomcat enforces an 8KB limit.** `MockMvc` bypasses the container-level parser. Likewise, `MockMultipartFile` can bypass parts of Servlet multipart size enforcement; test with a real-port integration test when container limits are the goal.

### 17.1. Boundary Tests Worth Writing

- 400: `name=""` / `name=" "` / `quantity=0` / `quantity=1` / `quantity=101`.
- 400: JSON missing a brace, `quantity="abc"`, body completely absent.
- 413 raw: **2048 bytes accepted**, **2049 bytes rejected**.
- 413 multipart: file below 64KB and above 64KB; total multipart request exceeding 128KB.
- 431 app header: 256 ASCII bytes accepted, 257 rejected.
- HTTP parser: combined headers under/over 8KB; check real status without hardcoding 431.
- Multi-key cookies, long JWTs, Unicode header policy.
- 414: very long URI; observe status at edge/Tomcat without forcing 414.
- 415: `text/plain` sent to `/api/items` consuming JSON.
- 5xx: unexpected bugs are not turned into 400 by advice.

**At boundaries, align byte units** (KB vs. KiB, UTF-8 bytes vs. Java `String.length()`). Multipart requests add boundary and part-header overhead, so total size != sum(file sizes). Measure empirically rather than promising exact outcomes from character counts alone.

### 17.2. Unit Tests Prove Exception Mapping, Not That Clients Receive the Body

You can unit-test `@ExceptionHandler(MaxUploadSizeExceededException)` returning `ProblemDetail` 413, yet a real multipart request may have its connection closed by Tomcat before the client reads the response. Run **network integration tests** to verify client experience, especially when `max-swallow-size` comes into play.

## 18. Runbook When Errors Appear Only in Production

### 18.1. Step 1: Record a Safe Request Profile

Gather without secrets:
- HTTP method, sanitized route pattern/path.
- `Content-Type`, `Accept`, `Transfer-Encoding`, presence/absence of `Content-Length`.
- Actual total request body size (if measured at proxy).
- Estimated header bytes, Cookie bytes, Authorization bytes—**counts only**, never values.
- Status code, response headers, server/proxy correlation ID.
- HTTP version (`1.1`, `2`, `3`).
- Endpoint/instance and timestamp.

If a client reports "Network Error," do not automatically label it 413; check traces and gateway logs.

### 18.2. Step 2: Identify the First Rejecting Layer

~~~text
Is the request ID in gateway logs?
    |
    +-- No: investigate CDN/WAF/client/DNS/TLS
    |
    +-- Yes: did gateway return 413/431/400 with no backend log?
               |
               +-- Yes: check ingress/header/body limits
               |
               +-- No: did the backend receive the request?
                              |
                              +-- Tomcat parser rejected: check connector logs
                              |
                              +-- MVC mapping/converter: check safe exception type
                              |
                              +-- App Controller: check code/validation/domain policy
~~~

Look for **evidence of how far the request traveled**; never rely solely on the final status code. A gateway can rewrite an upstream status or serve its own HTML error page.

### 18.3. Step 3: Reduce Payload and Binary-Search Under Control

- If body is large: shrink bytes incrementally to find the threshold, testing only on staging/localhost.
- If Cookie is large: test a fresh browser profile or cleaned cookie scopes.
- If a business header is large: substitute measured ASCII strings.
- If URI is long: shorten the query, evaluate moving payload to body.
- If proxy path differs from localhost: compare direct Tomcat vs. through ingress.

Use binary search to locate the blocking threshold, **without blasting unlimited requests** at production or endpoints without load-test permission.

### 18.4. Step 4: Verify Effective Config, Not Just Repo YAML

Sources of overrides:
- Environment variables or command-line overrides.
- ConfigMap/Helm chart values.
- Active profiles.
- CDN/WAF/gateway policies.
- Tomcat Connector customizer.
- Ingress annotations.
- Spring Security filters.
- Custom Spring MVC multipart resolver beans.
- Different embedded server version from a dependency override.

A valid property in `application.yml` is not guaranteed to be active on the instance serving the request. Inspect effective configuration through protected internal tooling—never expose `/actuator/env` publicly to debug.

### 18.5. Step 5: Fix at the Right Layer and Add Regression Tests

| Observation | Change to consider |
| --- | --- |
| 400 `INVALID_JSON` | Fix client JSON, `Content-Type`, and DTO; do not raise header limit |
| 400 `INVALID_FIELDS` | Fix validation/caller data contract |
| 400 "Request header is too large" in Tomcat | Trim Cookie/JWT/header count; raise header buffer only with data |
| 431 at gateway | Shrink headers or tune gateway policy per requirement |
| 413 from ingress before app | Adjust ingress limit and capacity/timeout/streaming |
| 413 multipart in Spring | Tune `max-file-size`/`max-request-size` per business needs and tmp disk |
| 413 raw from app | Design per-endpoint limit or chunked protocol |
| Connection reset on oversize upload | Inspect `maxSwallowSize`/Expect/proxy buffering; do not assume app bug |
| 414 | Shorten URI, move request data into an appropriate body |
| 500 from multipart out-of-disk | Provision scratch/quota, cleanup, error mapping; don't just raise upload limit |

## 19. Common Reasoning Mistakes

| Wrong conclusion | Why it is wrong |
| --- | --- |
| "413 means `@Valid` failed on JSON" | Validation usually returns 400; 413 is body size policy |
| "431 means a huge file body" | 431 is request headers, not body |
| "Tomcat definitely returns 431 for big headers" | Tomcat's parser can return 400 |
| "Raising `spring.servlet.multipart.max-file-size` fixes every 413" | Proxies, raw bodies, and `max-request-size` also enforce limits |
| "`server.tomcat.max-http-form-post-size=2MB` blocks all JSON >2MB" | `maxPostSize` primarily limits form parameter parsing |
| "`server.tomcat.max-swallow-size=2MB` means max file is 2MB" | It is the byte limit swallowed after an aborted upload |
| "`Content-Length` is enough to guard body sizes" | Chunked/streaming requests need not send `Content-Length` |
| "`@ControllerAdvice` catches every request error" | Proxies/Tomcat parser/filters can reject before MVC |
| "Enabling Problem Details makes all 4xx share one JSON format" | Connectors/ingress/security have their own handlers |
| "Testing `HttpStatus` 413 in `MockMvc` is enough" | `MockMvc` does not reproduce multipart parser/network swallowing |
| "8KB means 8KB per individual header on Tomcat" | Tomcat measures combined request line + headers |
| "Raising max header to 1MB is harmless" | Header buffers × concurrency create memory pressure |
| "On 413, the client should just retry" | Payloads over a fixed limit get rejected again |
| "Renaming Boot 2 header property to Boot 3 keeps identical behavior" | The replacement is request-only and server behavior differs |
| "No 413 in app logs means the error never happened" | Ingress/proxy can emit 413 before backend |
| "Network reset means the app didn't reject it" | Tomcat may reject and close due to unread request body |
| "Small upload works so large uploads will work too" | Size/spool/part-count/total-request limits differ |
| "Adding JSON `@Size` prevents memory allocation" | Jackson parses/allocates before Bean Validation runs |

## 20. Self-Check Exercises

**1.** A JSON body is only 50 bytes yet misses a closing brace; what status fits?  
**Answer:** Usually 400, because JSON syntax is invalid; not 413.

**2.** A 70KiB `MultipartFile` when `max-file-size=64KB`?  
**Answer:** Rejected by multipart policy; typically 413 if exception/response completes cleanly, though transport errors can occur when uploads abort.

**3.** A bloated JWT makes `Authorization` 15KB against Tomcat's 8KB cap—is 431 guaranteed?  
**Answer:** No. Tomcat's HTTP parser may return 400 or close the connection; 431 is the dedicated status, not guaranteed by Tomcat.

**4.** Can a 7KB Cookie + 2KB Authorization exceed an 8KB header cap even though each field is under 8KB?  
**Answer:** Yes; Tomcat sums the request line and all headers.

**5.** Does `server.tomcat.max-http-form-post-size=2MB` protect against a 100MB JSON body?  
**Answer:** No. It is not a generic JSON body limit.

**6.** Which size does `server.tomcat.max-swallow-size` control?  
**Answer:** The body bytes Tomcat swallows after an aborted upload, not the allowed upload size.

**7.** Does `@Valid` with `quantity=0` on `@Min(1)` return 422 by default?  
**Answer:** Spring MVC defaults to 400; 422 only happens if explicitly configured by the API.

**8.** Why is `Content-Length` insufficient as a body limit?  
**Answer:** Clients can send chunked transfers without `Content-Length`; actual bytes must be checked.

**9.** How do 431 and 414 differ?  
**Answer:** 431 is for oversized header field(s); 414 is for an overly long URI/request-target.

**10.** Ingress returns 413 and the app logs nothing—where should you fix it?  
**Answer:** Check ingress body limits, request buffering, and proxy policies before touching Spring.

**11.** Multipart `max-file-size=10MB` yet `max-request-size=12MB`—can two 8MB files be uploaded in one request?  
**Answer:** No under total request policy, because 16MB of files plus overhead exceeds 12MB.

**12.** Why doesn't `MockMvc` prove Tomcat's header buffer limit?  
**Answer:** `MockMvc` does not execute the real HTTP connector parser.

**13.** Why shouldn't `rejectedValue` or raw Jackson messages be echoed in `ProblemDetail`?  
**Answer:** They can leak PII, tokens, secrets, internal paths, and implementation details.

**14.** What does lab `/api/raw` do on 2048 bytes? On 2049 bytes?  
**Answer:** 2048 returns 200 with `bytes=2048`; 2049 returns 413 `RAW_TOO_LARGE`.

**15.** Why is 431 deterministic for a 300-ASCII-byte `X-Client-Tag` in the lab?  
**Answer:** It stays below Tomcat's 8KB cap so the Controller receives it, checks the 256-byte limit, and returns 431.

**16.** Should you raise the header cap to 1MB to stop errors from long JWTs?  
**Answer:** Usually shrink Cookies/JWTs/headers first, because buffers scale with concurrency and create memory DoS risk.

**17.** Why can retrying the exact same payload after 413 be pointless?  
**Answer:** If it violates a fixed policy cap, the same payload will be rejected again; change the payload or upload workflow.

**18.** Why might an app accept 5MB JSON over localhost yet return 413 through ingress?  
**Answer:** Ingress has a lower cap or different buffering policy blocking it before Spring.

**19.** Which property does Boot 3 use for request-header size instead of the older property?  
**Answer:** `server.max-http-request-header-size`.

**20.** When Tomcat rejects an oversized header before Spring MVC, can `@RestControllerAdvice` catch it?  
**Answer:** No, because Controller/`DispatcherServlet` never receives a request rejected by the parser.

## 21. Debugging and Upgrade Checklist

- [ ] Distinguished 400/413/431 by **invalid data, oversized body, oversized headers**.
- [ ] Did not confuse 414 URI Too Long, 415 Unsupported Media Type, 422, 429, or 502/504.
- [ ] Identified the exact **first layer** rejecting the request.
- [ ] Checked HTTP method, path, `Content-Type`, `Accept`, `Content-Length`/`Transfer-Encoding`, and HTTP version.
- [ ] Measured body/header sizes in bytes without exposing Cookies/JWTs.
- [ ] For 400, distinguished Jackson parsing, `@Valid`, conversion, and Tomcat parser.
- [ ] For 413, checked ingress body cap, per-file multipart limit, and total request limit.
- [ ] For 431/400 header errors, checked Cookies/Authorization/request line and Tomcat buffers.
- [ ] Did not use `server.tomcat.max-http-form-post-size` as a JSON body limit.
- [ ] Did not use `max-swallow-size` as a max upload limit.
- [ ] Checked multipart temp directory, disk quota, and concurrency.
- [ ] Did not raise header/body limits without capacity planning, rate limits, and timeouts.
- [ ] Understood `Content-Length` does not cover chunked or decoded content.
- [ ] When upgrading Boot 2→3, verified `server.max-http-request-header-size` in place of the legacy property.
- [ ] Used `MockMvc` for MVC validation and a real HTTP server for Tomcat/multipart limits.
- [ ] Included staging tests passing through real ingress/gateway.
- [ ] Kept error responses safe: status, `application/problem+json` when app-controlled, machine code.
- [ ] Avoided logging raw payloads/credentials or exception internals.
- [ ] Added boundary regression tests and appropriate retry/backoff handling.
- [ ] Confirmed resolution from the **client-visible outcome**, not solely from app logs.

## 22. Conclusion

**400, 413, and 431 are not three names for the same error.** 400 normally relates to malformed requests or invalid inputs; 413 relates to **request content/body exceeding limits**; 431 relates to **oversized header fields**. However, a request rejected by Tomcat's parser or an ingress before Spring MVC can produce **400 instead of 431**, or a connection reset instead of the expected 413 body.

When debugging or upgrading, trace **client → gateway/ingress → Tomcat → filters → Spring MVC → Controller**, identify where sizes are enforced, and read the **exact property for your running Spring Boot/Tomcat version**. In Boot 3.3, **`server.max-http-request-header-size`**, **`server.tomcat.max-http-form-post-size`**, **`server.tomcat.max-swallow-size`**, and **`spring.servlet.multipart.max-*`** serve distinct purposes. The durable fix is setting business-aligned limits, measuring real bytes, protecting memory/storage, and testing at the right layer before rollout.
