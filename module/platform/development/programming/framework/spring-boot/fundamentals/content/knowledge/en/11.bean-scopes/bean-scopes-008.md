# Scoped Proxy and the Difference Between a Proxy Reference and the Target Object

In Spring Boot, a service is usually a singleton by default: the container creates one instance and uses that instance throughout the lifetime of the application context. However, some data only makes sense within a shorter boundary, such as details of the **current HTTP request** or **current HTTP session**. If a singleton needs to use a bean with a shorter scope, injecting the target object directly can cause errors or corrupt data boundaries.

Spring solves this situation with **scoped proxies**. A proxy can be injected into a singleton bean and maintain a stable reference. When code invokes a method through the proxy, the proxy locates the *target object* matching the currently active scope and delegates the call to that object.

What must be distinguished:

- **Proxy reference** is the intermediary object retained by the longer-lived bean.
- **Target object** is the actual instance belonging to the scope, such as an instance dedicated to one HTTP request.
- **Scope** decides when the target is created, shared, and invalidated.

A proxy does not turn a request-scoped target into a singleton. It merely lets a longer-lived bean access the properly scoped target at the time of use.

## 1. Why Are Scoped Proxies Needed?

Suppose a web application has a singleton `AuditService` and a request-scoped `RequestInfo`:

```text
ApplicationContext
   |
   +-- AuditService (singleton)
   |       |
   |       +-- holds a RequestInfo proxy reference
   |
   +-- RequestInfo target of request A
   |
   +-- RequestInfo target of request B
```

When request A executes, the proxy forwards calls to target A. When request B executes, that same proxy forwards calls to target B.

```text
Request A
   |
   v
AuditService
   |
   v
RequestInfo proxy -------> RequestInfo target A

Request B
   |
   v
AuditService
   |
   v
RequestInfo proxy -------> RequestInfo target B
```

`AuditService` does not need to be recreated per request and does not have to manage a global variable to track the current request. Spring manages target resolution per scope.

## 2. Reviewing Bean Scopes

Scope describes the lifetime and how Spring provides bean instances. Common scopes:

| Scope | Typical lifecycle | Use cases |
| --- | --- | --- |
| `singleton` | One instance per bean definition within an IoC container | Services, repositories, shared configuration |
| `prototype` | Creates a new instance when the container is asked for the bean | Stateful objects needing fresh creation per retrieval |
| `request` | One instance within an HTTP request | Request ID, caller metadata within a request |
| `session` | One instance within an HTTP session | Data tied to a user session |
| `application` | One instance within `ServletContext` | Shared state of the web application |
| `websocket` | One instance per WebSocket session | Data tied to a WebSocket connection |

`singleton` is the default scope. Request, session, application, and WebSocket are web-aware scopes requiring an appropriate web environment. You cannot by default use request scope inside a console program or a background job without an active HTTP request.

### 2.1. The Problem When a Singleton Holds a Request-Scoped Bean Directly

Example:

```java
@Component
@Scope("request")
public class RequestInfo {
    private final String requestId = UUID.randomUUID().toString();

    public String getRequestId() {
        return requestId;
    }
}
```

And a singleton:

```java
@Service
public class AuditService {
    private final RequestInfo requestInfo;

    public AuditService(RequestInfo requestInfo) {
        this.requestInfo = requestInfo;
    }
}
```

If Spring tries to create `AuditService` at startup while no HTTP request is active, it cannot retrieve a concrete request-scoped target to pass directly into the constructor. Request scope has no valid target object at that point.

Even if it grabbed the first request's target and kept it inside the singleton, every subsequent request could accidentally use the first request's data. That violates the purpose of the scope and can leak data across requests.

Scoped proxies solve the problem by injecting an **intermediary reference**. The target is only resolved when a valid call occurs within an active scope.

## 3. What Is a Scoped Proxy?

A **scoped proxy** is a proxy generated by Spring for a bean belonging to a scope. The proxy is registered under the bean name used by the rest of the application. When a method is invoked, the proxy queries the scope management mechanism to obtain the matching target and forwards the call to that target.

Example:

```java
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.RequestScope;

@Component
@RequestScope
public class RequestInfo {
    // ...
}
```

`@RequestScope` is a specialized annotation for request scope. By default, this annotation uses a class-based scoped proxy (`TARGET_CLASS`). Thus, a singleton can inject a `RequestInfo` reference without requiring a request target to exist when the singleton is constructed.

With the general `@Scope`, you can specify proxy mode explicitly:

```java
@Component
@Scope(
    value = WebApplicationContext.SCOPE_REQUEST,
    proxyMode = ScopedProxyMode.TARGET_CLASS
)
public class RequestInfo {
}
```

The two examples above are alternative ways to declare a request-scoped bean. Do not place both `@RequestScope` and `@Scope` on the same class.

### 3.1. What Options Does `ScopedProxyMode` Offer?

| Value | Meaning |
| --- | --- |
| `DEFAULT` | Uses the default configured for component scanning; in many common configurations, defaults to no scoped proxy |
| `NO` | Do not create a scoped proxy |
| `INTERFACES` | Create a proxy based on the interfaces implemented by the target |
| `TARGET_CLASS` | Create a proxy based on the target's class |

`@RequestScope` and `@SessionScope` default to `TARGET_CLASS`, whereas if you use `@Scope` directly you should specify `proxyMode` explicitly when needed. For example:

```java
@Scope(
    value = WebApplicationContext.SCOPE_REQUEST,
    proxyMode = ScopedProxyMode.TARGET_CLASS
)
```

## 4. How Do a Proxy Reference and a Target Object Differ?

This is the core of the lesson.

### 4.1. The Proxy Reference

Suppose a singleton holds a field:

```java
private final RequestInfo requestInfo;
```

When using a scoped proxy, the `requestInfo` field points to the proxy. That proxy is typically created and injected while the singleton is initialized. That reference can persist for the entire lifetime of the singleton.

### 4.2. The Target Object

The target is the actual `RequestInfo` instance inside the active request. With request scope:

- Request A has target A.
- Request B has target B.
- Accesses within the same request normally receive the same target A or B.
- When the request finishes, the target belonging to that request ends its lifecycle and is cleaned up by the scope according to the corresponding lifecycle rules.

### 4.3. One Proxy Can Serve Many Targets

```text
Singleton AuditService
       |
       | unchanged requestInfo field
       v
   [Proxy P]
       |
       +-- call in request A --> [Target A]
       |
       +-- call in request B --> [Target B]
       |
       +-- call in request C --> [Target C]
```

Proxy P is the stable reference held by the singleton. Targets A, B, and C are distinct instances selected according to the current request.

### 4.4. Direct Comparison

| Aspect | Proxy reference | Target object |
| --- | --- | --- |
| Role | Intermediary forwarding calls | Executes logic and holds scoped state |
| Who holds the reference? | Longer-lived bean can hold the proxy | Scope manages the target; proxy resolves target on call |
| Lifetime | Usually as long as the bean holding the proxy | Scoped, e.g., one HTTP request |
| Changes per request? | Proxy reference usually does not change | Selected target changes per request |
| Callable without a request? | Can hold the proxy, yet calling methods needing a request target fails if scope is not active | No valid request target exists |
| State | Do not treat proxy state as business state of the target | State belongs to the actual instance in scope |

Put concisely: **the proxy is a stable intermediary address; the target is the concrete object that address resolves to in the current active scope**.

## 5. Complete Example: Singleton Service Using a Request-Scoped Bean

The following example uses Spring Boot Web with an embedded servlet server. The project requires appropriate web dependencies (`spring-boot-starter-web` in familiar Spring Boot setups) and component scanning covering the packages.

### 5.1. Request-Scoped Bean

`RequestInfo.java`:

```java
package com.example.demo.request;

import java.util.UUID;
import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.RequestScope;

@Component
@RequestScope
public class RequestInfo {

    private final String requestId = UUID.randomUUID().toString();

    public String getRequestId() {
        return requestId;
    }
}
```

Spring creates a `RequestInfo` target for each HTTP request. `requestId` is initialized when that request's target is created.

### 5.2. Singleton Service Holding the Proxy

`AuditService.java`:

```java
package com.example.demo.service;

import com.example.demo.request.RequestInfo;
import org.springframework.stereotype.Service;

@Service
public class AuditService {

    private final RequestInfo requestInfo;

    public AuditService(RequestInfo requestInfo) {
        this.requestInfo = requestInfo;
    }

    public String currentRequestId() {
        return requestInfo.getRequestId();
    }
}
```

`AuditService` is a singleton by default. Its constructor receives the scoped proxy reference for `RequestInfo`. On each call to `currentRequestId()`, the proxy resolves the target matching the active request and invokes `getRequestId()`.

### 5.3. Controller Calling the Service

`RequestController.java`:

```java
package com.example.demo.web;

import com.example.demo.service.AuditService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class RequestController {

    private final AuditService auditService;

    public RequestController(AuditService auditService) {
        this.auditService = auditService;
    }

    @GetMapping("/request-id")
    public String requestId() {
        return auditService.currentRequestId();
    }
}
```

Main class:

```java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

Call the endpoint multiple times:

```bash
curl http://localhost:8080/request-id
curl http://localhost:8080/request-id
```

Example output:

```text
f1c9bdb2-9a75-4d0f-9e5b-111111111111
7c2f19b0-2f12-4f23-8b3e-222222222222
```

Two independent requests receive two different IDs. Meanwhile, `AuditService` stays a single singleton and its `requestInfo` field keeps the exact same proxy reference. It is the proxy that resolved the proper target per request.

### 5.4. Why Does the Singleton Constructor Not Fail?

While creating `AuditService`, Spring does not need to fetch the request-scoped target immediately. The container can inject the proxy because the proxy is an object compatible with the declared dependency type. Only when code calls a method through the proxy inside an active request is the target resolved.

If you remove the scoped proxy and inject the request-scoped target directly into the singleton, dependency resolution may demand request scope when no request exists yet. That is a common cause of `ScopeNotActiveException`.

## 6. `TARGET_CLASS` and `INTERFACES`

A scoped proxy needs a type that can be injected into consuming beans. Spring supports two common strategies.

### 6.1. Class-Based Proxy (`TARGET_CLASS`)

Example:

```java
@Component
@RequestScope
public class RequestInfo {
    public String getRequestId() {
        return "...";
    }
}
```

With `@RequestScope`'s default, Spring creates a class-based proxy. The proxy is a compatible subclass of `RequestInfo`, so it can be injected into a constructor expecting `RequestInfo`.

Important limitations of class-based proxies:

- The target class cannot be `final` if a subclass proxy must be generated.
- `final` methods cannot be overridden to intercept via subclassing.
- `private` methods cannot be overridden.
- Avoid designing APIs that depend on calling methods the proxy cannot intercept.

### 6.2. Interface-Based Proxy (`INTERFACES`)

If you want to expose the bean via an interface:

```java
package com.example.demo.request;

public interface RequestIdentity {
    String getRequestId();
}
```

Implementation:

```java
package com.example.demo.request;

import java.util.UUID;
import org.springframework.context.annotation.Scope;
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;
import org.springframework.web.context.WebApplicationContext;

@Component
@Scope(
    value = WebApplicationContext.SCOPE_REQUEST,
    proxyMode = ScopedProxyMode.INTERFACES
)
public class DefaultRequestIdentity implements RequestIdentity {

    private final String requestId = UUID.randomUUID().toString();

    @Override
    public String getRequestId() {
        return requestId;
    }
}
```

Singleton using the interface:

```java
@Service
public class AuditService {
    private final RequestIdentity requestIdentity;

    public AuditService(RequestIdentity requestIdentity) {
        this.requestIdentity = requestIdentity;
    }
}
```

A JDK dynamic proxy implements the specified interface. Therefore, inject `RequestIdentity`; do not request `DefaultRequestIdentity` when the publicly exposed bean is only an interface proxy.

### 6.3. Comparison

| Criterion | `TARGET_CLASS` | `INTERFACES` |
| --- | --- | --- |
| Typical mechanism | Subclass proxy | JDK dynamic proxy |
| Interface required? | No | Yes |
| Inject concrete class? | Possible if types match and subclass constraints are respected | No, inject the interface |
| Limitations | `final` class/methods and `private` methods cannot be overridden | Only exposes interfaces; calls go through the interface |
| Suitable when | Applications using concrete types and non-final classes | Interface-based design |

Choose the proxy mode based on the API the consuming bean needs to see. For business code with clear interfaces, interface-based proxies can reduce coupling to concrete implementations.

## 7. Scoped Proxies and Other Web Scopes

### 7.1. Request Scope

```java
@Component
@RequestScope
public class RequestMetadata {
}
```

The target is bound to the current HTTP request. Different requests get different targets. This is the classic case when a singleton service needs to access request information.

### 7.2. Session Scope

```java
@Component
@SessionScope
public class ShoppingCart {
    private final List<String> productIds = new ArrayList<>();

    public void add(String productId) {
        productIds.add(productId);
    }

    public List<String> getProductIds() {
        return List.copyOf(productIds);
    }
}
```

`@SessionScope` uses a class-based scoped proxy by default. A proxy can be injected into the `CartService` singleton, while the `ShoppingCart` target is selected based on the current HTTP session. Requests belonging to the same session access the same shopping cart target; different sessions get separate targets.

Session-scoped state must be designed carefully because a single session can send multiple concurrent requests (for example, multiple browser tabs). Do not assume requests in the same session always run sequentially.

### 7.3. Application Scope

Application scope binds the target to the servlet `ServletContext`. It is not identical to Spring singleton in every respect: application scope belongs to the web application context and may differ in sharing boundary from a singleton bean inside a specific IoC container.

### 7.4. Prototype Scope

Prototype is a case that warrants care. When using a scoped proxy with a prototype target, the target source mechanism may ask the container for a new prototype each time the proxy resolves a target—often on every method call through the proxy. Thus, a proxy does not mean all calls share the same prototype instance.

If you need to create one fresh prototype object **once per business operation** and reuse that object across multiple steps, fetch the object once via `ObjectProvider<T>.getObject()` and keep it in a local variable for that operation. Do not assume a prototype scoped proxy keeps the same target across an entire chain of method calls.

## 8. When Is a Proxy Resolved to a Target?

For a request-scoped bean, the proxy normally does not fetch the target while the singleton's constructor runs. The target is fetched when a method call passes through the proxy and the current scope can supply a target.

Execution flow:

```text
HTTP request begins
        |
        v
Servlet request context is established
        |
        v
Controller calls singleton service
        |
        v
Singleton calls request-scoped proxy
        |
        v
Proxy asks request scope for target
        |
        v
Target for current request is created/fetched
        |
        v
Method is invoked on target
        |
        v
Result returned via proxy
        |
        v
HTTP request ends, request scope terminates
```

If the same request calls the proxy multiple times, request scope normally returns the same target within that request. If another request calls it, the proxy resolves the target matching that other request.

### 8.1. Calling the Proxy When Scope Is Not Active

Example:

```java
@SpringBootApplication
public class DemoApplication implements CommandLineRunner {

    private final RequestInfo requestInfo;

    public DemoApplication(RequestInfo requestInfo) {
        this.requestInfo = requestInfo;
    }

    @Override
    public void run(String... args) {
        System.out.println(requestInfo.getRequestId());
    }
}
```

`CommandLineRunner` executes after the application context starts, not inside an HTTP request. The constructor can receive the proxy successfully; when `getRequestId()` is called, Spring finds no active request scope and can throw `ScopeNotActiveException`.

This does not mean the proxy is broken. The proxy is behaving properly: it cannot supply a request-scoped target when there is no current request.

### 8.2. Background Tasks and Async Execution

Do not fetch a request-scoped object and pass that reference to a background thread or `@Async` task assuming request scope remains active. Request context is not automatically present on every thread. When the task runs after the request ends, the target may no longer be valid.

Instead of passing the request-scoped bean, read the necessary values on the request thread and pass **immutable data** to the task:

```java
public void submitAudit() {
    String requestId = requestInfo.getRequestId();
    backgroundExecutor.execute(() -> auditWriter.write(requestId));
}
```

This example extracts the request ID while the scope is still active and passes a `String` into the task. `auditWriter` is a dependency whose scope suits background execution. If security context or tracing context propagation is needed, use a propagation mechanism designed specifically for that context type.

## 9. How Does a Scoped Proxy Differ from an AOP Proxy?

Both proxy types can appear in the same application, yet their purposes differ:

| Aspect | Scoped proxy | AOP proxy |
| --- | --- | --- |
| Primary purpose | Select target according to active scope | Apply advice around method invocations |
| Example | Request-scoped target inside a singleton service | Transactions, caching, security, logging |
| What the proxy does | Locates the scope-appropriate target and delegates the call | Runs interceptors/advice and may invoke the target |
| Can target change? | Yes, per request/session or scope | Usually the proxied target bean, depending on target source |
| Requires active scope? | Yes if target belongs to a web scope needing context | Not necessarily; depends on advice and target |

Scoped proxies are typically built on Spring's proxy infrastructure. A single bean can also participate in multiple proxy mechanisms; therefore, when debugging, inspect the proxy's purpose and target source rather than relying solely on runtime class names.

For example, a request-scoped service may also need transaction advice. In that case, resolving the target per request and applying transactions are two separate responsibilities. Specific proxy configuration and interceptor ordering depend on how Spring registers post-processors and advisors.

## 10. How Are Scoped Proxies Registered in the Container?

When Spring creates a scoped proxy, it typically registers:

1. The proxy under the original **public bean name**, such as `requestInfo`.
2. The target bean definition under an internal name prefixed with `scopedTarget.`, such as `scopedTarget.requestInfo`.

Diagram:

```text
BeanDefinitionRegistry
   |
   +-- "requestInfo"
   |       |
   |       +-- proxy bean injected into singleton
   |
   +-- "scopedTarget.requestInfo"
           |
           +-- target definition with request scope
```

This is an internal Spring implementation detail. Business code should inject and use beans by their normal public name/interface type. Do not manually fetch `scopedTarget.requestInfo` to store in a singleton, as doing so bypasses scoped target resolution.

### 10.1. How Can You Inspect the Proxy?

During debugging, you can inspect the runtime type of the public bean:

```java
Object bean = applicationContext.getBean(RequestInfo.class);
System.out.println(bean.getClass().getName());
```

The class name may be a proxy class name generated by Spring/JDK. For class-based proxies, it is usually an auto-generated subclass name; for interface-based proxies, it is usually a JDK proxy.

Do not call `getBean(RequestInfo.class)` in a context with multiple beans of the same type without a qualifier. The snippet above only illustrates when there is a single matching candidate.

### 10.2. Do Not Retain the Target Reference in a Singleton Bean

Some infrastructure APIs allow unwrapping proxies or retrieving targets under specific conditions. However, if you grab request target A and assign it to a singleton field, that field holds request A's object and will not automatically switch to target B on the next request.

```java
// Do not do this with a request-scoped target:
private RequestInfo cachedTarget;
```

The proxy needs to perform target resolution **on each scoped usage**. Avoid unwrapping proxies and caching targets in longer-lived beans.

## 11. Using `ObjectProvider` or `ObjectFactory` Instead of Scoped Proxies

Scoped proxies are not the only option. If you want to defer obtaining the target and actively control the timing, you can inject a provider.

### 11.1. `ObjectProvider<T>`

```java
package com.example.demo.service;

import com.example.demo.request.RequestInfo;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.stereotype.Service;

@Service
public class AuditService {

    private final ObjectProvider<RequestInfo> requestInfoProvider;

    public AuditService(ObjectProvider<RequestInfo> requestInfoProvider) {
        this.requestInfoProvider = requestInfoProvider;
    }

    public String currentRequestId() {
        RequestInfo requestInfo = requestInfoProvider.getObject();
        return requestInfo.getRequestId();
    }
}
```

`ObjectProvider` is safely injected into the singleton. Only when `getObject()` is called does Spring resolve `RequestInfo` according to the active scope. With request scope, this call must occur inside an HTTP request.

Unlike a scoped proxy:

- A provider is a factory/lookup dependency that code invokes explicitly.
- A scoped proxy lets code use the bean like a regular dependency.
- Providers are useful when you want to decide explicitly when a target is needed or check availability via APIs like `getIfAvailable()`.

### 11.2. `ObjectFactory<T>`

`ObjectFactory<T>` is a simple abstraction for retrieving objects when needed:

```java
private final ObjectFactory<RequestInfo> requestInfoFactory;

public AuditService(ObjectFactory<RequestInfo> requestInfoFactory) {
    this.requestInfoFactory = requestInfoFactory;
}

public String currentRequestId() {
    return requestInfoFactory.getObject().getRequestId();
}
```

`ObjectProvider` extends `ObjectFactory` with additional utilities. In modern Spring code, `ObjectProvider` is usually chosen when more flexible lookup capabilities are needed.

### 11.3. Comparing Scoped Proxy and Provider

| Criterion | Scoped proxy | `ObjectProvider<T>` |
| --- | --- | --- |
| How it is used | Call methods directly on injected dependency | Call `getObject()` to obtain the bean |
| When target resolves | When call passes through proxy | When `getObject()` is called |
| Business code | More transparent, unaware of proxy | Makes lookup explicit |
| Control over bean retrieval timing | Per method invocation through proxy | Explicitly controlled by code |
| Best suited for | Injecting short-lived bean into longer-lived bean | Deferring lookup or creating a target exactly once per operation |

### 11.4. Retrieving a Prototype Once for One Job

Example of a singleton needing to create a fresh `JobContext` for each execution:

```java
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class JobContext {
    private final String jobId = UUID.randomUUID().toString();

    public String getJobId() {
        return jobId;
    }
}
```

Service:

```java
@Service
public class JobService {
    private final ObjectProvider<JobContext> jobContexts;

    public JobService(ObjectProvider<JobContext> jobContexts) {
        this.jobContexts = jobContexts;
    }

    public void process() {
        JobContext context = jobContexts.getObject();
        validate(context);
        execute(context);
        finish(context);
    }

    private void validate(JobContext context) {
        System.out.println("Validate " + context.getJobId());
    }

    private void execute(JobContext context) {
        System.out.println("Execute " + context.getJobId());
    }

    private void finish(JobContext context) {
        System.out.println("Finish " + context.getJobId());
    }
}
```

In each `process()` execution, the service retrieves one prototype object and passes that same reference through the steps of the job. This clearly expresses "one instance per execution."

## 12. Testing Scoped Beans

Request scope requires a web request context. A unit test instantiating a service with `new` does not supply an HTTP request, so calling a scoped proxy can fail with an inactive scope error.

### 12.1. Testing Through HTTP Requests with `MockMvc`

With Spring Boot Test and Spring MVC Test configured appropriately:

```java
@SpringBootTest
@AutoConfigureMockMvc
class RequestScopeIntegrationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void eachRequestHasItsOwnRequestId() throws Exception {
        String first = mockMvc.perform(get("/request-id"))
                .andReturn()
                .getResponse()
                .getContentAsString();

        String second = mockMvc.perform(get("/request-id"))
                .andReturn()
                .getResponse()
                .getContentAsString();

        assertThat(first).isNotBlank();
        assertThat(second).isNotBlank();
        assertThat(first).isNotEqualTo(second);
    }
}
```

This test assumes the `/request-id` endpoint exists as in the previous example, `MockMvc` is configured, and MockMvc/AssertJ static imports are included. Each `perform` simulates an independent request, so the request-scoped target resolves per request.

### 12.2. Testing Multiple Accesses Within the Same Request

You can create an endpoint returning the request ID twice:

```java
@GetMapping("/request-id/twice")
public List<String> requestIdTwice() {
    return List.of(
        auditService.currentRequestId(),
        auditService.currentRequestId()
    );
}
```

Both values within the same request normally match because the same request scope provides the same target. Two independent HTTP requests will have different IDs.

### 12.3. Unit Testing a Singleton Service with a Provider/Proxy

If testing the service directly via its constructor, supply appropriate fake or mock dependencies. Do not expect a real request-scoped proxy to operate when the test sets up no request context.

With `ObjectProvider`, you can mock the provider to return a test `RequestInfo`. For integration tests, use a web test context to verify real interactions between singleton, proxy, and request scope.

## 13. Common Errors and Resolutions

### 13.1. `ScopeNotActiveException`

The message may state that request scope is not active or there is no current request.

Common causes:

- Calling a request-scoped proxy inside a `CommandLineRunner`.
- Calling the proxy from a scheduled job or background thread.
- Unit test invoking a bean without establishing a request context.
- Asynchronous work continuing after the HTTP request has ended.

Resolution:

1. Verify whether the call actually belongs inside a request/session scope.
2. If only request data is needed, read the data on the request thread and pass immutable values to the background task.
3. If deferred bean retrieval is needed, use `ObjectProvider` while still calling it only when the scope is active.
4. For tests, set up a web request context or test via `MockMvc`.

### 13.2. `BeanCreationException` or Proxy Creation Failure

A class-based proxy may fail to create due to a `final` target class, incompatible constructors/types, or incompatible proxy configuration. Check `proxyMode`, the classes/interfaces exposed by the bean, and the constraints of the proxy type used.

If a stable interface exists, consider `ScopedProxyMode.INTERFACES` and inject via the interface.

### 13.3. Injecting Concrete Class Fails with Interface Proxy

If a scoped proxy only implements an interface, the constructor should accept the interface:

```java
public AuditService(RequestIdentity requestIdentity) {
    this.requestIdentity = requestIdentity;
}
```

Do not request a concrete implementation class when the exposed object is a JDK dynamic proxy.

### 13.4. Request Data Mixed Up Across Requests

Check whether the application:

- Stored a request-scoped target in a singleton field.
- Used a static variable for request data.
- Shared mutable state under the wrong scope.
- Passed a request target reference to another thread.

Keep the proxy in the singleton and read the target through the proxy within the active request. If data must leave the request, pass only the required values.

### 13.5. Treating a Session-Scoped Bean as Always Thread-Safe

One HTTP session can have multiple concurrent requests. Session scope ensures the target is tied to the session, yet **does not automatically guarantee thread safety** for mutable state inside `ShoppingCart`. Design updates, synchronization, and data storage accordingly.

## 14. Common Misconceptions

| Misconception | Accurate understanding |
| --- | --- |
| "Injecting a proxy means the singleton holds the first request's target." | The singleton holds the proxy; the target is resolved per scope at call time |
| "Proxy and target are the same object." | The proxy is the intermediary object; the target executes scoped logic |
| "Scoped proxy makes a request bean live for the whole application." | The target still obeys request/session scope |
| "With a proxy, you can call it anywhere." | Methods requiring a target only work when the corresponding scope is active |
| "`@RequestScope` is a singleton." | Each request has its own target; the shared proxy may live longer |
| "Every bean needs a scoped proxy." | Proxies are only needed when a shorter-scoped dependency is referenced from a longer context or similar lookup needs |
| "`@Order` or AOP proxies replace scoped proxies." | They solve different problems |
| "A prototype proxy always keeps one target across calls." | Prototype lookups can create a new target per resolution; to share one target for one job, fetch once with a provider |
| "Session scope automatically protects data from concurrent access." | Scope does not automatically supply thread safety for mutable state |

## 16. Takeaways

**A scoped proxy is a stable intermediary reference; the target object is the actual instance selected for the active scope.** A singleton can hold a proxy for a request-scoped bean, yet each HTTP request still has its own target. When a call goes through the proxy, Spring locates the matching target and forwards the method invocation.

Distinguish proxies from targets clearly, choose `TARGET_CLASS` or `INTERFACES` based on the exposed bean type, and only call request/session-scoped dependencies when the corresponding scope is active. If you need to actively fetch a target at a specific moment, `ObjectProvider<T>` is an appropriate option. Above all, never store short-lived targets in singletons and never pass request-scoped objects to background threads as though they still belong to the original request.

Understanding the difference between a proxy reference and a target object helps you use request scope, session scope, dependency injection, and Spring Boot proxy mechanisms safely and predictably.
