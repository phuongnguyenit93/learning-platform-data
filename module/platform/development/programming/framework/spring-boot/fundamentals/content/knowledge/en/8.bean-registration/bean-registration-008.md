# Bean Name Collisions, Multiple Same-Type Beans, and Two Conflicts to Distinguish

In a Spring Boot application, you can register many beans using `@Component`, `@Service`, `@Repository`, `@Controller`, or `@Bean`. As the number of beans grows, two errors frequently lumped together as "duplicate bean" appear:

1. **Bean name collision**: two definitions try to register under the same **bean name** in one container, causing a conflict during bean definition registration.
2. **Multiple beans of the same type**: the container has multiple distinct beans matching a required injection type; without an explicit selection rule, Spring does not know which bean to supply.

These are **two different kinds of conflicts**, occurring at different stages and requiring different solutions. Renaming a bean can fix a name collision, yet may not resolve type ambiguity. Conversely, adding `@Primary` or `@Qualifier` helps Spring choose a bean during injection, yet does not allow two bean definitions with the same name to coexist.

This lesson belongs to the **Bean Registration** chapter of **Spring Boot Fundamentals**. We will move from bean registration principles to building deliberate error examples, reading Spring Boot logs, and picking the right fix.

## 1. How Does Spring Manage Beans by Name and Type?

A *Spring bean* is an object managed by the IoC container. The container stores **bean definitions**, from which it can create instances, resolve dependencies, and manage lifecycles.

Each bean definition has a **primary name** (*bean name*); a bean may also have aliases. The container also knows or infers the Java types that an instance of the bean satisfies.

Example:

```java
package com.example.shop.payment;

public interface PaymentGateway {
    String charge(long amount);
}
```

```java
package com.example.shop.payment;

import org.springframework.stereotype.Service;

@Service("cardGateway")
public class CardPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Paid " + amount + " by card";
    }
}
```

Here:

- **Bean name:** `cardGateway`, explicitly declared via `@Service("cardGateway")`.
- **Implementation type:** `CardPaymentGateway`.
- **A type satisfied by the bean:** `PaymentGateway`, because the class implements this interface.
- **Instance:** the object created and managed by Spring when the bean is initialized.

One bean can satisfy multiple types (its class, interfaces, superclasses), without becoming multiple separate beans.

### 1.1. Two Independent Questions

When registering and using beans, Spring answers two corresponding questions in turn:

```text
REGISTRATION
  "Is this name already used by another bean definition?"
                     │
                     ▼
        Bean definitions in container
                     │
                     ▼
USAGE / INJECTION
  "Among the beans matching the requested type,
   which bean should be injected here?"
```

A project can pass the bean registration stage and still fail when injecting dependencies. That happens when **names do not collide**, yet **multiple beans satisfy the same type**.

### 1.2. A Diagram to Distinguish Them

```text
SCENARIO A — NAME COLLISION
    bean name: "paymentGateway"  ← definition from ConfigA
    bean name: "paymentGateway"  ← definition from ConfigB
                    │
                    ▼
       Collides on the same registration key
       (typically fails before injection)

SCENARIO B — MULTIPLE BEANS OF SAME TYPE
    bean name: "cardGateway"      ─┐
                                   ├── both are PaymentGateway
    bean name: "bankGateway"      ─┘
                    │
                    ▼
    OrderService(PaymentGateway gateway)
                    │
                    ▼
      Does not know which bean to pick
      without suitable guidance
```

This is the core distinction of this lesson: **name collision** versus **type ambiguity**.

## 2. Where Do Bean Names Come From?

When reading a name collision error, check where Spring obtained the bean names. Names can be specified explicitly or generated by convention.

| Registration style | Example | Typical bean name |
|---|---|---|
| Default `@Component` | `@Component class FileParser` | `fileParser` |
| Default `@Service` | `@Service class EmailSender` | `emailSender` |
| Default `@Repository` | `@Repository class OrderRepository` | `orderRepository` |
| Default `@RestController` | `@RestController class OrderController` | `orderController` |
| Explicitly named `@Component` | `@Component("csvParser")` | `csvParser` |
| Explicitly named `@Service` | `@Service("fastSender")` | `fastSender` |
| Unnamed `@Bean` | `@Bean PaymentGateway gateway()` | `gateway` |
| Explicitly named `@Bean` | `@Bean("cardGateway")` | `cardGateway` |

Annotations such as `@Service` and `@RestController` are stereotypes built on `@Component`; Spring can discover them via component scanning.

For default component names, Spring normally takes the short class name and applies initial-letter decapitalization rules. Consecutive uppercase letters can be preserved under JavaBeans rules, so do not assume mechanically that every acronym is lowercased.

### 2.1. Bean Names Are Not Fully Qualified Class Names

Two classes:

```text
com.example.shop.mail.EmailSender
com.example.shop.audit.EmailSender
```

have **different fully qualified class names**, yet their default scanned bean names can both be:

```text
emailSender
```

Java packages let the JVM distinguish two classes, **not necessarily guaranteeing that default bean names distinguish them**.

This is a common source of name collisions in multi-package projects.

### 2.2. `@Bean` Can Declare Aliases

Example:

```java
@Configuration(proxyBeanMethods = false)
public class GatewayConfiguration {

    @Bean(name = {"primaryCardGateway", "cardGatewayAlias"})
    public PaymentGateway cardGateway() {
        return new CardPaymentGateway();
    }
}
```

In this configuration, `primaryCardGateway` is the primary name and `cardGatewayAlias` is an alias for the same bean definition. Those two names **do not mean Spring creates two independent objects**. Alias registration must still satisfy container naming rules.

In the following examples, to keep things clear, each bean uses a single primary name.

## 3. Conflict Type 1: Two Bean Definitions Collide on the Same Name

Suppose an application has two configuration classes, both inside scanned packages:

```text
com.example.shop
├── ShopApplication.java
└── config/
    ├── DefaultGatewayConfiguration.java
    └── ExperimentalGatewayConfiguration.java
```

First configuration class:

```java
package com.example.shop.config;

import com.example.shop.payment.PaymentGateway;
import com.example.shop.payment.CardPaymentGateway;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class DefaultGatewayConfiguration {

    @Bean("paymentGateway")
    public PaymentGateway cardGateway() {
        return new CardPaymentGateway();
    }
}
```

Second configuration class:

```java
package com.example.shop.config;

import com.example.shop.payment.PaymentGateway;
import com.example.shop.payment.BankPaymentGateway;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class ExperimentalGatewayConfiguration {

    @Bean("paymentGateway")
    public PaymentGateway bankGateway() {
        return new BankPaymentGateway();
    }
}
```

This example assumes `CardPaymentGateway` and `BankPaymentGateway` have valid no-arg constructors and implement `PaymentGateway`.

Each configuration declares a `@Bean` method with a different Java method name (`cardGateway()` vs. `bankGateway()`), yet both **register the same bean name `paymentGateway`**.

To a bean definition registry, this is like trying to bind two different definitions to one key:

```text
"paymentGateway" -> definition from DefaultGatewayConfiguration

"paymentGateway" -> definition from ExperimentalGatewayConfiguration
                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                     collides with already registered key
```

### 3.1. What Error Does Spring Boot Typically Report?

In modern Spring Boot, bean definition overriding is **disabled by default**. With two definitions sharing the same name, logs may contain a message like:

```text
The bean 'paymentGateway', defined in class path resource
[.../ExperimentalGatewayConfiguration.class], could not be registered.

A bean with that name has already been defined in
[.../DefaultGatewayConfiguration.class] and overriding is disabled.
```

A commonly related exception is:

```text
org.springframework.beans.factory.support.BeanDefinitionOverrideException
```

Depending on registration source and processing phase, name collisions can produce other specific exceptions; for example, component scanner conflicts between two classes with the same bean name can involve `ConflictingBeanDefinitionException`. Do not rely on one fixed exception name; look closely at the **bean name** and the **two bean definition sources**.

Crucially, this is a **name registration conflict**. Spring does not even need to try injecting `PaymentGateway` into any service to hit this error.

### 3.2. Proper Fixes: Redesign Names or Registration Conditions

If both beans genuinely need to coexist, give them **two different names**:

```java
@Bean("cardGateway")
public PaymentGateway cardGateway() {
    return new CardPaymentGateway();
}
```

```java
@Bean("bankGateway")
public PaymentGateway bankGateway() {
    return new BankPaymentGateway();
}
```

Now there is no name collision; however, because both carry type `PaymentGateway`, the application **may shift into Conflict Type 2** when a component injects a single `PaymentGateway` without a clear selection.

If only one bean should exist per environment, use `@Profile` or `@Conditional` so the configurations are **mutually exclusive by condition**. If one bean is an obsolete experiment, removing the redundant definition is also a proper fix.

The fix should reflect business intent: **do you want both gateways simultaneously**, or **only one gateway per environment**?

## 4. Name Collision During Component Scan: Two Classes in Different Packages with the Same Short Name

Another scenario without `@Bean`:

```java
// com.example.shop.notifications.EmailSender
package com.example.shop.notifications;

import org.springframework.stereotype.Component;

@Component
public class EmailSender {
}
```

```java
// com.example.shop.audit.EmailSender
package com.example.shop.audit;

import org.springframework.stereotype.Component;

@Component
public class EmailSender {
}
```

If both packages lie within the component scan scope, the default bean name for each class may be `emailSender`.

When Spring encounters two incompatible candidates with the same name, an error like this may appear:

```text
ConflictingBeanDefinitionException:
Annotation-specified bean name 'emailSender'
for bean class [...] conflicts with existing,
non-compatible bean definition of same name [...]
```

Depending on circumstances, the scanner and existing bean definitions may produce different behavior or messages. The underlying cause, however, is **two registration sources both claiming the name `emailSender`**.

### 4.1. Explicitly Name Components

If both are needed:

```java
@Component("notificationEmailSender")
public class EmailSender {
}
```

and:

```java
@Component("auditEmailSender")
public class EmailSender {
}
```

Each class must reside in its properly declared package. In the example, the two Java classes with the same short name coexist peacefully because their packages differ, while bean names are disambiguated so the registry does not collide on keys.

Naming based on **the bean's responsibility** is usually easier to read than appending arbitrary numbers.

### 4.2. Renaming the Java Class vs. Renaming the Bean

- **Renaming the class** can change the default bean name, but also affects how Java code references the class.
- **Setting the bean name directly** via `@Component("...")` or `@Bean("...")` distinguishes container identity without necessarily renaming the class.
- **Changing the package** of a class does not guarantee changing its default bean name when the bean name is still derived from the short class name.

In multi-module systems, establish bean naming conventions or stereotypes that keep responsibilities clear.

## 5. Should You Enable Bean Definition Overriding?

Spring Boot supports the configuration property:

```yaml
spring:
  main:
    allow-bean-definition-overriding: true
```

When enabled, the container can allow a later-registered bean definition to **replace** an earlier definition with the same name, in cases permitted by the registration mechanism. This does not allow two beans with the same name to coexist in the same registry.

For accidental collisions, however, this is **not the first fix you should reach for**:

- One definition can silently replace another.
- Behavior can depend on bean definition registration order.
- Reading logs and figuring out why a bean "disappeared" becomes harder.
- Having two beans of the same type for different purposes remains unresolved.

Nor should you assume enabling this property resolves **every component scan error**; not every metadata discovery conflict is a registry override case.

**If the goal is two distinct beans working together, give them different names.** If the goal is one bean replacing a library's default bean, understand the library's extension points, conditional configuration, and override conventions first.

### 5.1. How Does Spring Boot Auto-Configuration Avoid Collisions?

Many Spring Boot auto-configurations use conditions such as:

```java
@ConditionalOnMissingBean
```

This keeps auto-configuration from **creating a default bean** when conditions detect that the application already supplies a matching bean.

Conceptual illustration:

```text
Application provides CustomClock
               │
               ▼
Condition checks existing beans
               │
        ┌──────┴──────┐
        ▼             ▼
   Bean exists     No bean yet
        │             │
        ▼             ▼
  Skip default    Create default
```

However, `@ConditionalOnMissingBean` may check by type, name, or annotation depending on configuration, and results also depend on **when bean definitions are registered**. It is not a universal mechanism guaranteeing beans in any project will never collide on names. In normal applications, let Boot auto-configurations manage their defaults and only replace them intentionally.

## 6. Conflict Type 2: Multiple Differently Named Beans Matching One Type

Now consider two beans registered cleanly:

```java
package com.example.shop.payment;

public interface PaymentGateway {
    String charge(long amount);
}
```

First implementation:

```java
package com.example.shop.payment;

import org.springframework.stereotype.Service;

@Service("cardGateway")
public class CardPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Card: " + amount;
    }
}
```

Second implementation:

```java
package com.example.shop.payment;

import org.springframework.stereotype.Service;

@Service("bankGateway")
public class BankPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Bank: " + amount;
    }
}
```

Currently in the container:

| Bean name | Concrete bean type | Satisfies `PaymentGateway`? |
|---|---|---|
| `cardGateway` | `CardPaymentGateway` | Yes |
| `bankGateway` | `BankPaymentGateway` | Yes |

The two beans **do not collide on name**, so registration is completely valid.

Now the following service requires **a single** dependency:

```java
package com.example.shop.checkout;

import com.example.shop.payment.PaymentGateway;
import org.springframework.stereotype.Service;

@Service
public class CheckoutService {

    private final PaymentGateway gateway;

    public CheckoutService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public String checkout(long amount) {
        return gateway.charge(amount);
    }
}
```

Spring must find one bean matching `PaymentGateway` for the constructor parameter `gateway`. The search finds two candidates and lacks sufficient guidance to pick one.

The error message may look like:

```text
Parameter 0 of constructor in com.example.shop.checkout.CheckoutService
required a single bean, but 2 were found:
    - cardGateway
    - bankGateway
```

The associated exception is typically `NoUniqueBeanDefinitionException`; during bean creation, it may also be wrapped in `UnsatisfiedDependencyException`.

This is **ambiguity when resolving dependencies by type**, not a bean name collision. Both beans can exist in the container; the issue arises only where Spring must select **a single bean**.

### 6.1. Why Is `PaymentGateway` Ambiguous?

The injection asks for the interface:

```java
public CheckoutService(PaymentGateway gateway)
```

Both `CardPaymentGateway` and `BankPaymentGateway` implement `PaymentGateway`. Nothing in that snippet says "use card" or "use bank".

If the code asked for a concrete type:

```java
public CheckoutService(CardPaymentGateway gateway)
```

there might be only one matching bean, yet the service would couple directly to the implementation, hurting flexibility and testability. Using an interface paired with explicit bean selection is usually better when business logic should abstract the payment gateway.

### 6.2. Can Spring Use the Parameter Name?

In some situations, when multiple candidates share the same type and the injection point's name matches a bean name, Spring can use the parameter name or field name as a fallback selection rule. This relies on metadata preserved during compilation and the Spring version's resolution rules.

For example:

```java
public CheckoutService(PaymentGateway cardGateway)
```

may resolve by name under suitable conditions, yet **you should not turn accidental variable-name matching into a critical configuration contract**. When a choice carries business meaning, `@Qualifier` expresses intent far more clearly.

Likewise, `@Primary` or other priority rules can take effect before or alongside parameter-name matching. Do not assume Spring always picks the bean matching the parameter name regardless of context.

## 7. Resolving Multiple Beans of the Same Type with `@Primary`

If the application has one default implementation, mark it with `@Primary`:

```java
package com.example.shop.payment;

import org.springframework.context.annotation.Primary;
import org.springframework.stereotype.Service;

@Primary
@Service("cardGateway")
public class CardPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Card: " + amount;
    }
}
```

When injecting a single `PaymentGateway`, Spring prioritizes the `@Primary` bean among matching candidates:

```text
PaymentGateway (single dependency)
           │
           ▼
   Matching candidates
    ├── cardGateway  (@Primary)
    └── bankGateway
           │
           ▼
      cardGateway
```

Key points:

- `@Primary` **does not change the bean name**.
- `@Primary` **does not remove other beans from the container**.
- `@Primary` mainly resolves single-bean selection when autowiring by type.
- If multiple candidates are marked primary without a disambiguating rule, ambiguity can still happen.
- When injecting into a collection or map, Spring can still supply multiple candidates rather than only the primary bean.

`@Primary` can also be placed on a `@Bean` method:

```java
@Bean("cardGateway")
@Primary
public PaymentGateway cardGateway() {
    return new CardPaymentGateway();
}
```

Use `@Primary` when there is genuinely an **application-wide sensible default**. If different workflows need different gateways, `@Qualifier` usually expresses intent better.

## 8. Resolving Multiple Beans of the Same Type with `@Qualifier`

`@Qualifier` lets an injection point state the exact bean or candidate group it wants to use.

Example:

```java
package com.example.shop.checkout;

import com.example.shop.payment.PaymentGateway;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.stereotype.Service;

@Service
public class CheckoutService {

    private final PaymentGateway gateway;

    public CheckoutService(
            @Qualifier("bankGateway") PaymentGateway gateway
    ) {
        this.gateway = gateway;
    }

    public String checkout(long amount) {
        return gateway.charge(amount);
    }
}
```

Here, Spring looks for `PaymentGateway` narrowed down by the `bankGateway` qualifier. Because the bean is named `bankGateway`, the code explicitly communicates that checkout uses the bank implementation.

`@Qualifier` **does not register a new bean**. It only adds selection metadata at the injection point and/or on the bean definition.

### 8.1. Using `@Qualifier` with `@Bean` Methods

If beans are created in configuration:

```java
@Configuration(proxyBeanMethods = false)
public class PaymentConfiguration {

    @Bean("cardGateway")
    public PaymentGateway cardGateway() {
        return new CardPaymentGateway();
    }

    @Bean("bankGateway")
    public PaymentGateway bankGateway() {
        return new BankPaymentGateway();
    }
}
```

You can inject:

```java
public CheckoutService(
        @Qualifier("cardGateway") PaymentGateway gateway
) {
    this.gateway = gateway;
}
```

`@Qualifier("cardGateway")` describes the injection point. Spring can treat a bean's name as a matching qualifier value; Spring also supports explicit qualifier metadata and custom qualifier annotations. Do not think of `@Qualifier` simply as a drop-in replacement for `getBean(String)` in every scenario.

### 8.2. When `@Primary` and `@Qualifier` Both Appear

Suppose `cardGateway` is marked `@Primary`, yet one service needs `bankGateway`:

```java
public RefundService(
        @Qualifier("bankGateway") PaymentGateway gateway
) {
    this.gateway = gateway;
}
```

The qualifier selects the desired candidate for this injection point; `@Primary` does not force every service to receive `cardGateway`. Thus a common combination is:

- `@Primary` for the system's default choice.
- `@Qualifier` wherever an explicit alternative is required.

Both handle **selection at injection time**, not resolving two bean definitions colliding on the same name at registration time.

### 8.3. Domain-Specific Custom Qualifiers

When there are many beans, repeating string names can become brittle. Spring lets you create custom qualifier annotations, for example:

```java
package com.example.shop.payment;

import java.lang.annotation.Retention;
import java.lang.annotation.Target;
import org.springframework.beans.factory.annotation.Qualifier;

import static java.lang.annotation.ElementType.FIELD;
import static java.lang.annotation.ElementType.METHOD;
import static java.lang.annotation.ElementType.PARAMETER;
import static java.lang.annotation.ElementType.TYPE;
import static java.lang.annotation.RetentionPolicy.RUNTIME;

@Target({FIELD, METHOD, PARAMETER, TYPE})
@Retention(RUNTIME)
@Qualifier
public @interface OnlinePayment {
}
```

Marking both the bean and the injection point with `@OnlinePayment` expresses selection by the **online payment** role rather than tying to a bean name string. This is useful when an application has multiple strategies and benefits from a clear configuration vocabulary.

Ensure qualifiers are applied consistently; if multiple beans carry the same qualifier while an injection point asks for a single bean, ambiguity can still occur.

## 9. When You Actually Want All Beans of the Same Type

Having multiple beans of the same type is not always an error. Some designs intentionally register multiple implementations of an interface, such as validators or pipeline steps.

### 9.1. Injecting a List

Example interface:

```java
public interface OrderValidator {
    void validate(Order order);
}
```

Implementations:

```java
@Component
public class StockValidator implements OrderValidator {
    @Override
    public void validate(Order order) {
        // Check inventory
    }
}
```

```java
@Component
public class AmountValidator implements OrderValidator {
    @Override
    public void validate(Order order) {
        // Check order amount
    }
}
```

A service can accept `List<OrderValidator>`:

```java
@Service
public class OrderValidationService {

    private final List<OrderValidator> validators;

    public OrderValidationService(List<OrderValidator> validators) {
        this.validators = validators;
    }

    public void validate(Order order) {
        for (OrderValidator validator : validators) {
            validator.validate(order);
        }
    }
}
```

Spring injects all matching beans into the collection. Here multiple implementations are part of the design, not something to suppress with `@Primary`.

If validator order matters, use `@Order` or `Ordered` per Spring semantics rather than relying on class scanning or registration order.

### 9.2. Injecting `Map<String, T>` to Select by Bean Name

Example:

```java
@Service
public class PaymentRouter {

    private final Map<String, PaymentGateway> gateways;

    public PaymentRouter(Map<String, PaymentGateway> gateways) {
        this.gateways = gateways;
    }

    public PaymentGateway getGateway(String name) {
        PaymentGateway gateway = gateways.get(name);
        if (gateway == null) {
            throw new IllegalArgumentException(
                    "Unknown gateway: " + name
            );
        }
        return gateway;
    }
}
```

When injecting `Map<String, PaymentGateway>` under standard rules, keys are typically **bean names**, and values are the matching beans. You can look up a strategy dynamically by key at runtime.

In real applications, keys arriving from requests must be validated/allowlisted against business rules rather than letting arbitrary user input access internal beans directly.

### 9.3. Injecting `ObjectProvider<T>` for Flexible Access

`ObjectProvider<PaymentGateway>` lets you retrieve beans on demand or iterate over matching beans:

```java
@Service
public class GatewayInspector {

    private final ObjectProvider<PaymentGateway> gateways;

    public GatewayInspector(
            ObjectProvider<PaymentGateway> gateways
    ) {
        this.gateways = gateways;
    }

    public List<PaymentGateway> findAll() {
        return gateways.stream().toList();
    }
}
```

`ObjectProvider` is a handy utility, though it does not turn an ambiguous **single-bean** request into an unambiguous one. Single-item lookup methods still follow resolution rules; when you want all beans, use `stream()` or the corresponding API.

### 9.4. When to Use Collections vs. Qualifiers?

| Goal | How to express it |
|---|---|
| One default gateway used widely | `@Primary` |
| One specific gateway at a service | `@Qualifier` |
| Run all validators | `List<OrderValidator>` |
| Pick strategy by name at runtime | `Map<String, Strategy>` |
| Flexible and deferred access | `ObjectProvider<T>` |
| Separate implementations per environment | `@Profile`/`@Conditional` when appropriate |

These options have different semantics. They should reflect how the business logic needs to use the beans, rather than being added merely to silence a log error.

## 10. A Complete Ambiguity-Free Spring Boot Example

Let's build a small web application that has **two beans of the same type**, with injection selected explicitly.

### 10.1. Source Structure

```text
src/main/java/com/example/paymentdemo/
├── PaymentDemoApplication.java
├── payment/
│   ├── PaymentGateway.java
│   ├── CardPaymentGateway.java
│   └── BankPaymentGateway.java
├── service/
│   └── CheckoutService.java
└── web/
    └── CheckoutController.java
```

### 10.2. Main Class

`PaymentDemoApplication.java`:

```java
package com.example.paymentdemo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class PaymentDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(PaymentDemoApplication.class, args);
    }
}
```

### 10.3. Two Explicitly Named Implementations

`payment/PaymentGateway.java`:

```java
package com.example.paymentdemo.payment;

public interface PaymentGateway {
    String charge(long amount);
}
```

`payment/CardPaymentGateway.java`:

```java
package com.example.paymentdemo.payment;

import org.springframework.stereotype.Service;

@Service("cardGateway")
public class CardPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Paid " + amount + " by card";
    }
}
```

`payment/BankPaymentGateway.java`:

```java
package com.example.paymentdemo.payment;

import org.springframework.stereotype.Service;

@Service("bankGateway")
public class BankPaymentGateway implements PaymentGateway {

    @Override
    public String charge(long amount) {
        return "Paid " + amount + " via bank transfer";
    }
}
```

### 10.4. Service Selecting a Specific Bean

`service/CheckoutService.java`:

```java
package com.example.paymentdemo.service;

import com.example.paymentdemo.payment.PaymentGateway;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.stereotype.Service;

@Service
public class CheckoutService {

    private final PaymentGateway gateway;

    public CheckoutService(
            @Qualifier("cardGateway") PaymentGateway gateway
    ) {
        this.gateway = gateway;
    }

    public String pay(long amount) {
        return gateway.charge(amount);
    }
}
```

### 10.5. Endpoint

`web/CheckoutController.java`:

```java
package com.example.paymentdemo.web;

import com.example.paymentdemo.service.CheckoutService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class CheckoutController {

    private final CheckoutService checkoutService;

    public CheckoutController(CheckoutService checkoutService) {
        this.checkoutService = checkoutService;
    }

    @GetMapping("/pay")
    public String pay(@RequestParam(defaultValue = "100") long amount) {
        return checkoutService.pay(amount);
    }
}
```

In a project with `spring-boot-starter-web`, running on the default port with no overriding configuration, the sample request:

```text
GET http://localhost:8080/pay?amount=500
```

returns:

```text
Paid 500 by card
```

Both `cardGateway` and `bankGateway` register cleanly. `CheckoutService` uses `cardGateway` because the constructor specifies `@Qualifier("cardGateway")`. This is a clean example of **multiple beans of the same type without conflict because the injection point makes the selection explicit**.

### 10.6. Triggering a Type Ambiguity Error

In `CheckoutService`, remove the qualifier:

```java
public CheckoutService(PaymentGateway gateway) {
    this.gateway = gateway;
}
```

Keep both beans of the same type with different names. With no clear selection guidance at the injection point, startup may fail because `PaymentGateway` has two candidates.

Then add `@Qualifier` back. Notice **you do not need to delete either bean**: both are valid; only the single-dependency injection point lacked selection guidance.

### 10.7. Triggering a Name Collision Error

On both implementations, intentionally use the same name:

```java
@Service("paymentGateway")
public class CardPaymentGateway implements PaymentGateway {
    // ...
}
```

```java
@Service("paymentGateway")
public class BankPaymentGateway implements PaymentGateway {
    // ...
}
```

Now the problem is no longer how to choose a bean during injection. Both components try to register the name `paymentGateway`. When the scanner treats them as incompatible definitions, registration can fail before Spring ever resolves `CheckoutService`'s constructor.

**Restore the two distinct bean names** after observing. Adding `@Primary` to one class will not turn two definitions with the same name into two valid beans.

## 11. Distinguishing via Logs: Reading the Right Symptom

### 11.1. Name Collision Log

Illustrative log snippet:

```text
The bean 'paymentGateway' could not be registered.
A bean with that name has already been defined
and overriding is disabled.
```

Key phrases to spot:

- `bean 'paymentGateway'`: pinpoints **the colliding bean name**.
- `already been defined`: the name was already registered.
- `overriding is disabled`: replacing the earlier definition is not permitted.

Question to answer: **Which two definitions are using the name `paymentGateway`?**

Identify the bean name, the classes/methods defining the bean, and why both sources were included in the context. Actions may include renaming, removing redundant definitions, or adjusting registration conditions.

### 11.2. Multiple Beans of the Same Type Log

Another illustrative log:

```text
Parameter 0 of constructor in CheckoutService
required a single bean, but 2 were found:
    - cardGateway: defined in class path resource [...]
    - bankGateway: defined in class path resource [...]
```

Key phrases to spot:

- `required a single bean`: an injection point expected exactly one bean.
- `2 were found`: the container found multiple matching beans.
- The two listed names are **different**: this is not a name collision.

Question to answer: **Which gateway should `CheckoutService` use, or does it actually need both?**

Actions may include `@Primary`, `@Qualifier`, changing the dependency to a collection/map, or redesigning conditions so only one implementation is active per environment.

### 11.3. Comparison Table of the Two Errors

| Characteristic | Bean name collision | Multiple beans of same type |
|---|---|---|
| What collided? | Bean name | Matching type for a dependency |
| Bean names of candidates | Typically identical | Typically different |
| Detection stage | Bean definition registration/scanning | Dependency resolution when creating/fetching beans |
| Common exception | `BeanDefinitionOverrideException` or scanner conflict error | `NoUniqueBeanDefinitionException`, possibly wrapped in `UnsatisfiedDependencyException` |
| Can `@Primary` fix it? | No | Possibly, if it yields a single preferred candidate |
| Can `@Qualifier` fix it? | No | Possibly, if it selects a matching candidate |
| Can renaming one bean fix it? | Possibly | Not enough if multiple same-type beans remain at the injection point |
| Is enabling overriding appropriate? | Only when replacing one definition with another is truly intended | Does not solve selecting between two differently named beans |
| Design fix | Distinct names, separate conditions, remove duplicate | Default selection, qualifier, collection, or conditional registration |

### 11.4. `NoSuchBeanDefinitionException` Is a Third Category

If Spring reports:

```text
No qualifying bean of type 'com.example.PaymentGateway' available
```

and **zero** matching candidates exist, that is a **missing bean**, distinct from both conflicts in this lesson:

- Name collision: two sources both claim the same name.
- Multiple of same type: two or more candidates match, with no single one selected.
- Missing bean: no matching candidate was found.

Fixing a missing bean involves checking component scan, `@Bean`, `@Import`, profiles, conditional configuration, and the classpath. Do not add `@Primary` to a bean that does not exist.

## 12. Profiles and Conditions Can Prevent or Cause Conflicts

Sometimes an application intentionally has multiple implementations, only one of which should run per environment.

Example using profiles:

```java
@Service("paymentGateway")
@Profile("dev")
public class SandboxPaymentGateway implements PaymentGateway {
    // ...
}
```

```java
@Service("paymentGateway")
@Profile("prod")
public class ProductionPaymentGateway implements PaymentGateway {
    // ...
}
```

If only the `dev` profile is active, the sandbox bean is registered and the production bean stays inactive. If only `prod` is active, the reverse happens.

However, watch out for these cases:

- Spring allows **multiple active profiles simultaneously**. If `dev` and `prod` are both active, both definitions may claim `paymentGateway` and collide on name.
- If neither profile is active, **no `PaymentGateway` bean may exist at all**.
- When beans have different names yet are active together, type ambiguity can still happen at a single-bean injection point.

Thus, profiles are a tool for **controlling conditional bean registration**, not a universal bean-selection mechanism by type.

### 12.1. Two Valid Designs Based on Goal

**Design A: only one gateway per environment.**

```text
Active profile = dev
    -> SandboxPaymentGateway

Active profile = prod
    -> ProductionPaymentGateway
```

Use `@Profile` or configuration conditions so each environment gets only the needed definition.

**Design B: multiple gateways active simultaneously.**

```text
cardGateway
bankGateway
walletGateway
     │
     ▼
PaymentRouter or qualified injection
```

Give each bean a distinct name and express the selection strategy in business code.

If the system supports multiple payment gateways at the same time, do not try to remove beans merely to avoid ambiguity when injecting a single interface.

## 13. Advanced Cases Worth Recognizing

### 13.1. One Bean Can Implement Multiple Interfaces

```java
public class CardGateway implements PaymentGateway, HealthCheck {
}
```

A single `cardGateway` bean can appear in candidate sets when injecting either `PaymentGateway` or `HealthCheck`. This is not a bean name collision; it is simply how type assignability works.

If an interface has multiple implementations and you request a single bean, qualifiers or other selection rules may be needed.

### 13.2. Generic Types Can Disambiguate Candidates

Example:

```java
public interface Handler<T> {
    void handle(T value);
}
```

```java
@Component
public class StringHandler implements Handler<String> {
    @Override
    public void handle(String value) {
        // ...
    }
}
```

```java
@Component
public class IntegerHandler implements Handler<Integer> {
    @Override
    public void handle(Integer value) {
        // ...
    }
}
```

Spring can use generic type information during candidate filtering. An injection point requesting `Handler<String>` can be distinguished from `Handler<Integer>` without needing separate bean names at the injection point.

Do not assume raw type `Handler` can still distinguish the two beans: raw types discard the generic metadata used for selection.

### 13.3. `@Primary` Does Not Filter Collections Exclusively

If you inject:

```java
public GatewayRegistry(List<PaymentGateway> gateways) {
    this.gateways = gateways;
}
```

the list can still include both the `@Primary` bean and other matching beans. `@Primary` primarily resolves selection when a dependency expects **one** object.

If only one bean should enter a collection, consider qualifiers or a candidate-filtering setup suited to your actual goal.

### 13.4. Bean Name and Java Variable Name Are Not the Same

```java
PaymentGateway selectedGateway =
        context.getBean("cardGateway", PaymentGateway.class);
```

The Java variable name is `selectedGateway`, whereas the bean name is `cardGateway`. Renaming the variable does not alter the bean definition.

With constructor injection, parameter names can sometimes act as a tie-breaker during dependency resolution; still, the bean name itself is declared or derived by the bean registration mechanism.

### 13.5. Multiple `ApplicationContext` Instances Can Share Bean Names

Bean names are managed within a registry/context scope. Two independent contexts can hold beans with the same name without colliding because they do not register into the same registry.

In a context hierarchy, parent/child bean lookups follow visibility and shadowing rules. When troubleshooting, identify **which context owns the bean**, especially in integration tests or multi-context apps.

In Spring Boot Fundamentals, you typically start with one main `ApplicationContext`; understanding name scoping prevents the misconception that "every bean name must be unique across the whole JVM".

## 14. How to Inspect Actually Registered Beans

When the application starts yet injected beans differ from expectations, you can inspect beans matching a type from `ApplicationContext`.

Example `CommandLineRunner` in Spring Boot:

```java
package com.example.shop;

import java.util.Arrays;
import org.springframework.boot.CommandLineRunner;
import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Component;
import com.example.shop.payment.PaymentGateway;

@Component
public class GatewayInspector implements CommandLineRunner {

    private final ApplicationContext context;

    public GatewayInspector(ApplicationContext context) {
        this.context = context;
    }

    @Override
    public void run(String... args) {
        String[] names = context.getBeanNamesForType(PaymentGateway.class);
        System.out.println("PaymentGateway beans: " + Arrays.toString(names));
    }
}
```

If `cardGateway` and `bankGateway` are registered, illustrative output could be:

```text
PaymentGateway beans: [cardGateway, bankGateway]
```

Display order should not be treated as an implementation selection rule. This code is a learning inspection tool; production apps should use proper logging and diagnostics rather than printing arbitrary bean names.

### 14.1. What If the Application Fails to Start?

If the error occurs early during bean definition registration, `CommandLineRunner` will never run. Read the startup logs and identify which configurations registered duplicate bean names.

If an error occurs while creating a required bean, context startup may also fail, so `CommandLineRunner` is not the only diagnostic tool.

### 14.2. Reading the Root Cause in Logs

Look for:

- **Bean name:** e.g., `paymentGateway`.
- **Required injection type:** e.g., `com.example.shop.payment.PaymentGateway`.
- **Two bean definition sources:** which classes, `@Bean` methods, or auto-configurations?
- **Injection point:** which constructor or field requested the dependency?
- **Profiles/conditions:** which configurations are active?
- **`Caused by` chain:** which exception actually explains the failure?

Spring Boot can output an auto-configuration report when run with `--debug` when you need to inspect conditions. That report shows which conditions matched or did not match, though it does not replace reading direct name-collision or ambiguity errors.

## 15. Troubleshooting Workflow in Your First Project

When Spring Boot reports a bean creation or startup failure, follow these steps:

### Step 1 — Identify Whether the Error Is at Registration or Injection

Does the log say:

```text
A bean with that name has already been defined
```

or:

```text
required a single bean, but 2 were found
```

If the first, investigate **a name collision**. If the second, investigate **type-based selection**.

### Step 2 — List Candidates and Definition Sources

For a bean name collision, write down:

```text
bean name: paymentGateway
definition A: DefaultGatewayConfiguration#cardGateway()
definition B: ExperimentalGatewayConfiguration#bankGateway()
```

For type ambiguity, write down:

```text
required type: PaymentGateway
injection point: CheckoutService(PaymentGateway gateway)
candidate A: cardGateway
candidate B: bankGateway
```

Writing this out makes it obvious what collided: **name** or **type**.

### Step 3 — Decide How Many Beans the Business Requires

Ask whether the application needs:

- A single implementation across all environments?
- A default implementation plus optional alternatives?
- Multiple implementations running simultaneously?
- One implementation only in a specific profile?
- A custom bean replacing an auto-configuration default?

Choose the technical fix only after clarifying that requirement.

### Step 4 — Fix According to the Conflict Type

If it is a **name collision**, fix at the registration site:

- Use distinct bean names when both beans should coexist.
- Remove redundant registration if only one bean is needed.
- Apply `@Profile`/`@Conditional` if one bean is needed per environment.
- Consider overriding only when definition replacement is intentional and tightly controlled.

If it is **multiple beans of the same type**, fix at the selection/design site:

- `@Qualifier` if the service needs a specific bean.
- `@Primary` if there is a default choice.
- `List<T>` or `Map<String, T>` if the service needs multiple beans.
- Redesign conditions if only one bean should actually exist.

### Step 5 — Re-read Logs After Targeted Fixes

When you rename two beans from `paymentGateway` to `cardGateway` and `bankGateway`, registration may succeed and startup may then report `required a single bean, but 2 were found`. That is not regressing to the old error: you have cleared the **registration stage** and uncovered an injection point needing explicit selection.

Conversely, if you add `@Qualifier("cardGateway")` while both bean definitions still share the name `paymentGateway`, the name collision occurs before the qualifier ever gets a chance to apply.

## 16. Practice Exercises for Distinguishing the Two Conflicts

### Exercise 1 — Two `@Bean` Methods with the Same Name

Create two `@Configuration` classes inside the component scan scope, each having a method returning `Clock`, both annotated with:

```java
@Bean("applicationClock")
```

Observe the startup log. Note the colliding bean name and the two definition sources. Then rename them to `utcClock` and `systemClock`.

This exercise demonstrates a **name collision**. After renaming, if a service injects a single `Clock` without guidance, you may encounter **type ambiguity**.

### Exercise 2 — Two `Clock` Beans with Different Names

Configuration:

```java
@Configuration(proxyBeanMethods = false)
public class ClockConfiguration {

    @Bean("utcClock")
    public Clock utcClock() {
        return Clock.systemUTC();
    }

    @Bean("systemClock")
    public Clock systemClock() {
        return Clock.systemDefaultZone();
    }
}
```

Create a service accepting `Clock` via constructor:

```java
public TimeService(Clock clock) {
    this.clock = clock;
}
```

With two same-type candidates, injection can be ambiguous. Try `@Qualifier("utcClock")` and `@Primary` (on one `@Bean`) in turn to observe both selection approaches.

### Exercise 3 — Using Two Implementations Together

Create a `NotificationSender` interface and two beans `emailSender` and `smsSender`. Have a service accept:

```java
public NotificationService(List<NotificationSender> senders) {
    this.senders = senders;
}
```

Explain why this is a valid design with multiple same-type beans, and why `@Primary` is unnecessary if the service intends to use all senders.

### Exercise 4 — Profiles That May Enable Multiple Beans

Create two beans with the same name, one marked `@Profile("dev")` and one marked `@Profile("prod")`. Observe when only `dev` or only `prod` is enabled. Then check what happens if both profiles are active simultaneously.

The goal is to understand that `@Profile` governs **conditional bean registration**, without guaranteeing globally that only one profile is ever active.

### Exercise 5 — Classifying Logs

Identify the error category and first inspection step:

| Log | Issue category | First step |
|---|---|---|
| `bean 'mailSender' already defined and overriding is disabled` | Name collision | Locate the two bean definitions sharing the name |
| `required a single bean, but 3 were found` | Multiple same-type beans | Identify the injection point and the three candidates |
| `No qualifying bean of type 'PaymentGateway' available` | Missing matching bean | Check scan, `@Bean`, profiles, conditions |
| `NoUniqueBeanDefinitionException: expected single matching bean but found 2` | Multiple same-type beans | Choose `@Qualifier`, `@Primary`, or collection |
| `ConflictingBeanDefinitionException ... bean name 'emailSender'` | Scan name collision | Check classes/packages and default naming |
| `NoSuchBeanDefinitionException` on `getBean("cardGateway")` | No bean with requested name | Check actual bean name, aliases, and registration conditions |

## 17. Long-Term Principles

When organizing source code and registering beans in Spring Boot, keep three layers of information distinct:

```text
Bean definition
    ├── Name: cardGateway
    ├── Type: CardPaymentGateway implements PaymentGateway
    └── Conditions: profile, configuration, etc.
                    │
                    ▼
Dependency injection
    ├── Required type: PaymentGateway
    ├── Qualifier/Primary: appropriate selection
    └── Shape: single bean, List, Map, Provider...
                    │
                    ▼
Bean instance delivered to consumer
```

A **bean name collision** occurs when multiple definitions claim the same name in a container. **Multiple beans of the same type** occur when registered beans coexist cleanly, yet an injection point has not specified which candidate to use. Bean names identify entries in the registry; bean types tell Spring which objects satisfy a dependency. Understanding both dimensions helps you fix root causes and design applications with multiple implementations that remain clear and stable.
