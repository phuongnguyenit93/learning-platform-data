# Designing Constructors to Expose Required Dependencies

A Spring bean typically needs other objects to carry out its work: a service needs a repository, a controller needs a service, a publisher needs a message client, or a module needs a shared clock and policy. How these dependencies are declared directly affects whether the class is easy to understand, test, and instantiate.

**Constructor injection** places required dependencies directly in the constructor. A reader inspecting the constructor signature can see what the object needs to exist in a valid state; Spring also knows which beans it must provide before creating the object.

Example:

~~~java
@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final PaymentService paymentService;

    public OrderService(
            OrderRepository orderRepository,
            PaymentService paymentService) {
        this.orderRepository = orderRepository;
        this.paymentService = paymentService;
    }
}
~~~

From this constructor you can read `OrderService`'s contract: the service cannot be created without `OrderRepository` or `PaymentService`. Both fields are `final`, so dependencies cannot be arbitrarily replaced after the object is constructed.

This lesson focuses on designing constructors to distinguish required and optional dependencies, why constructor injection is usually better suited than field/setter injection for core dependencies, how Spring resolves constructors, handling multiple candidates, avoiding circular dependencies, and testing classes without starting the entire application.

## 1. Dependencies Are Part of the Object's Contract

An object should only be created once the prerequisites for it to operate are satisfied.

Suppose an order pricing service always needs a set of tax rules:

~~~java
public class OrderPricingService {

    private final TaxPolicy taxPolicy;

    public OrderPricingService(TaxPolicy taxPolicy) {
        this.taxPolicy = taxPolicy;
    }

    public Money calculate(Order order) {
        return taxPolicy.calculate(order);
    }
}
~~~

`TaxPolicy` is not an optional utility that can be skipped. Without the policy, the service cannot compute prices correctly. Placing it in the constructor makes that a precondition for creating the object.

Compare that with a class using field injection:

~~~java
@Service
public class OrderPricingService {

    @Autowired
    private TaxPolicy taxPolicy;

    public Money calculate(Order order) {
        return taxPolicy.calculate(order);
    }
}
~~~

Reading the default constructor (generated by Java), someone else cannot see that `TaxPolicy` is a dependency. The object can be created with `new OrderPricingService()` without its dependency; only after Spring processes field injection is the field assigned. This couples the class more tightly to container lifecycle and makes it harder to instantiate in a valid state outside Spring.

**An object's creation contract should express the dependencies without which the object cannot function.**

## 2. How Does Constructor Injection Work in Spring?

The Spring IoC container creates beans by locating bean definitions and resolving required dependencies. With constructor injection, constructor parameters are the dependencies that must be resolved before invoking the constructor.

~~~text
ApplicationContext
       |
       v
Needs to create OrderService
       |
       v
Read constructor parameters
       |
       +----------------------+
       |                      |
       v                      v
OrderRepository          PaymentService
       |                      |
       v                      v
Resolve bean             Resolve bean
       |                      |
       +----------+-----------+
                  |
                  v
     Call new OrderService(repo, payment)
                  |
                  v
        Object has dependencies
                  |
                  v
           Managed bean
~~~

If a required dependency is missing or there are multiple candidates from which Spring cannot choose, bean creation fails. This is an important benefit: wiring errors are typically caught at startup, before the first request reaches the service.

### 2.1. Constructor Injection Does Not Mean Creating Dependencies Yourself

Spring is still responsible for finding and supplying beans. The constructor merely declares what the object needs:

~~~java
public OrderService(
        OrderRepository repository,
        PaymentService paymentService) {
    this.repository = repository;
    this.paymentService = paymentService;
}
~~~

Code does not need to call directly:

~~~java
new OrderRepository();
new PaymentService();
~~~

Dependencies may require proxies, transactions, configuration, lifecycle callbacks, or other beans. Letting Spring create and inject them preserves the proper container lifecycle.

### 2.2. A Single Constructor Usually Does Not Need @Autowired

Since Spring Framework 4.3, if a bean class has only one constructor, Spring automatically uses that constructor for dependency injection. Example:

~~~java
@Service
public class OrderService {

    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
~~~

There is no need to add `@Autowired` to a single constructor:

~~~java
// Not required if this is the only constructor.
@Autowired
public OrderService(OrderRepository repository) {
    this.repository = repository;
}
~~~

You can keep the annotation if the project has a specific convention, but usually a single constructor is already clear enough.

## 3. Required Dependencies: Place Them in the Constructor

A dependency should be treated as required when the class cannot fulfill its primary responsibility without it.

Example:

~~~java
@Service
public class InvoiceService {

    private final InvoiceRepository invoiceRepository;
    private final TaxCalculator taxCalculator;
    private final Clock clock;

    public InvoiceService(
            InvoiceRepository invoiceRepository,
            TaxCalculator taxCalculator,
            Clock clock) {
        this.invoiceRepository = invoiceRepository;
        this.taxCalculator = taxCalculator;
        this.clock = clock;
    }
}
~~~

These three dependencies are all core collaborators:

- The repository reads and saves invoices.
- The tax calculator computes tax obligations.
- The clock provides the current time through a testable abstraction.

If any of these beans is not configured, Spring cannot create `InvoiceService`. This is usually better behavior than allowing the service to exist and only fail when a method is called.

### 3.1. Use final for Injected Dependencies

~~~java
private final InvoiceRepository invoiceRepository;
~~~

`final` guarantees the field must be assigned in the constructor and cannot be reassigned afterward. This does not make the object completely immutable if the dependency itself is mutable, but it protects the service's reference structure.

A service normally does not need a setter to swap its repository or payment client after initialization. If runtime configuration changes are required, design a dedicated state-update mechanism with proper synchronization and lifecycle rather than exposing setters for every dependency.

### 3.2. Null Checks and Invariants

Spring normally does not pass `null` for a required dependency if no matching bean exists. However, the class may be instantiated manually in unit tests or other code. You can enforce invariants directly in the constructor:

~~~java
public InvoiceService(InvoiceRepository repository) {
    this.invoiceRepository = Objects.requireNonNull(repository);
}
~~~

With multiple fields, direct constructor assignment is usually sufficient; add `Objects.requireNonNull` when it clarifies the class contract or when the class may be instantiated from many places.

Do not turn the constructor into a place for executing business logic, querying the database, or calling external services. Constructors should accept dependencies, validate parameters, and establish initial state.

## 4. Optional Dependencies Should Not Masquerade as Required Dependencies

Not every dependency is always present. For example, a service may send a notification if a notifier is configured, while order calculation still works when notifications are disabled.

If a dependency is genuinely optional, express optionality in the signature or design structure.

### 4.1. Use Optional<T> When Absence Is a Valid Case

~~~java
@Service
public class OrderSummaryService {

    private final Optional<PromotionBanner> promotionBanner;

    public OrderSummaryService(
            Optional<PromotionBanner> promotionBanner) {
        this.promotionBanner = promotionBanner;
    }

    public Summary summarize(Order order) {
        Summary summary = Summary.from(order);

        promotionBanner.ifPresent(
                banner -> banner.attachTo(summary)
        );

        return summary;
    }
}
~~~

Spring supports injecting `Optional<T>` at dependency injection points. If no matching bean exists, the `Optional` can be empty; if multiple candidates exist and no single one can be chosen, ambiguity still needs to be resolved.

`Optional` makes it clear to callers that the dependency may be absent. Do not use `Optional` for core dependencies just to avoid startup failures.

### 4.2. Use ObjectProvider<T> When Flexible or Lazy Lookup Is Needed

~~~java
@Service
public class ReportService {

    private final ObjectProvider<ReportExporter> exporterProvider;

    public ReportService(
            ObjectProvider<ReportExporter> exporterProvider) {
        this.exporterProvider = exporterProvider;
    }

    public void exportIfConfigured(Report report) {
        ReportExporter exporter =
                exporterProvider.getIfAvailable();

        if (exporter != null) {
            exporter.export(report);
        }
    }
}
~~~

`ObjectProvider<T>` is useful when:

- The bean might not exist.
- You want to defer resolution until needed.
- You need to look up a candidate at the time of use.
- You need to iterate over multiple candidates via `stream()` or `orderedStream()`.

It does not automatically resolve ambiguity. If multiple indistinguishable candidates exist, `getIfAvailable()` can still throw a non-unique error.

### 4.3. Use @Nullable When Null Is Part of the Contract

Some systems use `@Nullable` to indicate a parameter can accept null:

~~~java
public OrderService(
        OrderRepository repository,
        @Nullable PromotionPolicy promotionPolicy) {
    this.repository = repository;
    this.promotionPolicy = promotionPolicy;
}
~~~

Exact handling depends on the annotation package and Spring version. If null is used, the code must handle it explicitly everywhere. In many cases, `Optional` or a default implementation expresses intent better.

### 4.4. Do Not Default to Null for a Required Dependency

Example:

~~~java
public OrderService(OrderRepository repository) {
    this.repository = repository;
}
~~~

If the service cannot work without the repository, do not add another constructor accepting null or use `@Autowired(required = false)` just so the application starts. That only delays the failure until runtime and leaves the object in an invalid state.

## 5. Optional Dependencies Can Be Replaced by a Default Implementation

If a feature should always be callable but the default behavior is "do nothing," you can provide a Null Object/No-op implementation.

~~~java
public interface NotificationSender {
    void send(OrderPlaced event);
}
~~~

~~~java
@Component
public class NoopNotificationSender implements NotificationSender {

    @Override
    public void send(OrderPlaced event) {
        // Do not send notification.
    }
}
~~~

~~~java
@Component
@Primary
public class EmailNotificationSender implements NotificationSender {

    @Override
    public void send(OrderPlaced event) {
        // Send email.
    }
}
~~~

The service always receives a `NotificationSender`:

~~~java
@Service
public class OrderNotificationService {

    private final NotificationSender sender;

    public OrderNotificationService(NotificationSender sender) {
        this.sender = sender;
    }
}
~~~

However, only use a no-op if silently doing nothing is valid behavior. For payments, authorization, or required persistence, a no-op implementation can mask serious errors. A default dependency must reflect business policy, not merely help the context start up.

## 6. How Do Constructor Injection and Setter Injection Differ?

Spring supports multiple dependency injection styles. Each style has different design implications.

### Constructor Injection

~~~java
@Service
public class CatalogService {

    private final CatalogRepository repository;

    public CatalogService(CatalogRepository repository) {
        this.repository = repository;
    }
}
~~~

Use when the dependency is required for the object to operate.

### Setter Injection

~~~java
@Component
public class CatalogFormatter {

    private Locale locale = Locale.ROOT;

    @Autowired
    public void setLocaleProvider(LocaleProvider provider) {
        this.locale = provider.defaultLocale();
    }
}
~~~

Setter injection can be appropriate when a dependency is genuinely optional, can change after object creation, or requires a specific configuration workflow. However, public setters for core dependencies allow the object to exist in an incomplete state or be mutated after initialization.

### Field Injection

~~~java
@Service
public class CatalogService {

    @Autowired
    private CatalogRepository repository;
}
~~~

Field injection is concise but has drawbacks:

- Dependencies do not appear in the constructor/object creation API.
- Fields typically cannot be `final`.
- Unit tests must use reflection, a Spring test context, or a custom injection mechanism.
- The object can be constructed with `new` without its dependencies assigned.
- The class is more tightly coupled to Spring annotations/infrastructure.

### Comparison

| Criterion | Constructor | Setter | Field |
|---|---|---|---|
| Expresses required dependencies | Very clear | Less clear | Hidden from API |
| Allows final fields | Yes | No with standard setters | No |
| Object complete right after construction | Yes, if constructor is sound | Possibly not | No before injection |
| Unit testing with new | Easy | May require calling setters | Difficult without injection |
| Suitable for optional dependencies | Yes, via Optional/Provider | Can be suitable | Possible, but less explicit |
| Likelihood of creating circular dependencies | Constructor cycles are usually caught | Can hide some cycles | Can hide some cycles |
| Recommendation for core dependencies | Usually preferred | Only with good reason | Usually avoided |

Not all setter injection is wrong. The problem is using setters or fields for dependencies that the class cannot function without.

## 7. Designing a Single Constructor for Core Dependencies

A typical bean should have a single constructor describing all required dependencies:

~~~java
@Service
public class CheckoutService {

    private final CartRepository cartRepository;
    private final PaymentGateway paymentGateway;
    private final OrderRepository orderRepository;
    private final Clock clock;

    public CheckoutService(
            CartRepository cartRepository,
            PaymentGateway paymentGateway,
            OrderRepository orderRepository,
            Clock clock) {
        this.cartRepository = cartRepository;
        this.paymentGateway = paymentGateway;
        this.orderRepository = orderRepository;
        this.clock = clock;
    }
}
~~~

When there is a single constructor, Spring automatically uses it for injection; `@Autowired` is unnecessary.

A long constructor may signal that the class has too many responsibilities. Do not solve this by moving half the dependencies to field injection. Consider:

- Is the class orchestrating multiple unrelated use cases?
- Can a group of behaviors be extracted into a collaborator with a clear responsibility?
- Is a dependency truly needed, or only used in a rare branch?
- Are multiple individual repositories being injected when a domain service/facade would express the contract better?

Do not create a "GodService" or an object with 15 dependencies just to reduce code lines. Conversely, do not split a class into meaningless tiny beans just to shorten a constructor. Let business responsibilities determine the boundaries.

### 7.1. Do Not Bundle Dependencies into a Service Locator

Example:

~~~java
@Service
public class CheckoutService {

    private final ApplicationContext context;

    public CheckoutService(ApplicationContext context) {
        this.context = context;
    }

    public void checkout() {
        PaymentGateway gateway =
                context.getBean(PaymentGateway.class);
        // ...
    }
}
~~~

The constructor shows only `ApplicationContext`, while actual dependencies are hidden inside methods. Wiring errors may only surface when the method runs, and unit tests must start a container or mock the service locator.

Prefer injecting concrete dependencies:

~~~java
public CheckoutService(PaymentGateway gateway) {
    this.gateway = gateway;
}
~~~

If you genuinely need to choose among multiple implementations at runtime, inject `List<PaymentGateway>` or `Map<String, PaymentGateway>` and build a registry with explicit business keys.

## 8. When a Class Has Multiple Constructors

A Java class can declare multiple constructors for different ways of creating the object. However, Spring needs to know which constructor to use when creating the bean.

### 8.1. A Single Constructor

~~~java
@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }
}
~~~

Spring automatically selects the sole constructor.

### 8.2. Multiple Constructors and Marking Constructor Injection

~~~java
@Service
public class CustomerService {

    private final CustomerRepository repository;
    private final Clock clock;

    @Autowired
    public CustomerService(
            CustomerRepository repository,
            Clock clock) {
        this.repository = repository;
        this.clock = clock;
    }

    public CustomerService(CustomerRepository repository) {
        this(repository, Clock.systemUTC());
    }
}
~~~

Here, the constructor annotated with `@Autowired` indicates which constructor Spring should use. Secondary constructors can be helpful for specific object-creation needs, but on Spring beans, having multiple construction paths can make the contract harder to follow.

In real applications, if a secondary constructor only serves unit tests, tests can usually pass a mock and clock to the primary constructor instead of keeping a production constructor with an implicit default.

### 8.3. With Multiple Constructors, Do Not Expect Spring to Guess by Parameter Count

Constructor selection rules can depend on annotations, default constructors, and parameter resolvability across Spring versions. For beans needing required dependencies, explicitly annotate the constructor to use with `@Autowired` when a class has multiple options, and test the real context.

Do not create multiple constructors with equally resolvable parameters and hope Spring always picks the constructor with "the most dependencies."

## 9. Lombok and Constructor Injection

Lombok can generate constructors from required fields:

~~~java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository repository;
    private final PaymentService paymentService;
}
~~~

`@RequiredArgsConstructor` generates a constructor for `final` fields and fields marked `@NonNull` according to Lombok's rules. Spring can use the single generated constructor without `@Autowired`.

### 9.1. Be Careful with @AllArgsConstructor

~~~java
@AllArgsConstructor
@Service
public class OrderService {
    private final OrderRepository repository;
    private String lastStatus;
}
~~~

`@AllArgsConstructor` can include non-dependency fields in the constructor. That makes the bean creation signature depend on internal state or fields that Spring should not inject.

For services, `@RequiredArgsConstructor` is usually more suitable if the project uses Lombok and dependencies are declared `final`.

### 9.2. @NonNull Annotation and Null Checks

Lombok can generate null checks for `@NonNull` fields in the constructor. However, do not use this annotation as a substitute for designing optionality. If a dependency can be absent, express it with `Optional<T>`, `ObjectProvider<T>`, or an appropriate default implementation.

### 9.3. Generated Constructors Must Still Be Readable

Even if the constructor is not written manually, reviewers need to see the dependencies via `final` fields. If a class has multiple kinds of state, non-dependency fields, and multiple Lombok annotations simultaneously, the actual constructor can become hard to predict. When the contract is important or complex, an explicit constructor is sometimes easier to read.

## 10. Injecting Collections When a Class Needs Multiple Implementations

A required dependency does not have to be a single object. A service may need all registered handlers.

~~~java
public interface ExportHandler {
    boolean supports(ExportFormat format);
    void export(Report report);
}
~~~

~~~java
@Component
public class PdfExportHandler implements ExportHandler {
    // ...
}
~~~

~~~java
@Component
public class CsvExportHandler implements ExportHandler {
    // ...
}
~~~

The registry receives all of them:

~~~java
@Component
public class ExportHandlerRegistry {

    private final List<ExportHandler> handlers;

    public ExportHandlerRegistry(List<ExportHandler> handlers) {
        this.handlers = List.copyOf(handlers);
    }

    public ExportHandler get(ExportFormat format) {
        return handlers.stream()
                .filter(handler -> handler.supports(format))
                .findFirst()
                .orElseThrow(() ->
                        new IllegalArgumentException(
                                "Unsupported format: " + format));
    }
}
~~~

In this case, the required dependency is **the set of handlers**. If there are no handlers, the constructor still receives an empty list under normal collection injection; if at least one handler is mandatory, enforce that invariant in the constructor or at startup.

If order matters, use `@Order` on handlers or an explicit sorting rule. If multiple handlers support the same format, decide how to handle duplicates rather than taking the first element in an arbitrary order.

## 11. Qualifiers When Multiple Beans Have the Same Type

If a constructor requests a single bean:

~~~java
public CheckoutService(PaymentGateway gateway) {
    this.gateway = gateway;
}
~~~

but the context has multiple `PaymentGateway` beans, Spring can throw `NoUniqueBeanDefinitionException`.

Express the selection in the constructor:

~~~java
@Service
public class BankCheckoutService {

    private final PaymentGateway gateway;

    public BankCheckoutService(
            @Qualifier("bankPaymentGateway") PaymentGateway gateway) {
        this.gateway = gateway;
    }
}
~~~

Or mark a default bean with `@Primary` if most injection points genuinely need the same default.

Constructor injection does not eliminate ambiguity; it surfaces ambiguity right where the dependency is declared. That helps readers determine exactly which service needs which choice.

### 11.1. Custom Qualifiers for Clearer Contracts

If multiple modules need the same selection, you can create a custom qualifier annotation:

~~~java
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier
public @interface Domestic {
}
~~~

~~~java
@Component
@Domestic
public class DomesticPaymentGateway implements PaymentGateway {
}
~~~

~~~java
public BankCheckoutService(@Domestic PaymentGateway gateway) {
    this.gateway = gateway;
}
~~~

Custom qualifiers avoid repeating strings and express the dependency's role in the constructor API.

## 12. Constructor Injection Helps Detect Circular Dependencies

A circular dependency occurs when beans depend on each other in a cycle.

Example:

~~~java
@Service
public class OrderService {

    public OrderService(PaymentService paymentService) {
    }
}
~~~

~~~java
@Service
public class PaymentService {

    public PaymentService(OrderService orderService) {
    }
}
~~~

Diagram:

~~~text
OrderService
     |
     v
PaymentService
     |
     v
OrderService
~~~

Spring cannot finish creating either bean first because each constructor requires the other bean. Usually the context fails with an error related to a circular reference or a bean currently in creation.

### 12.1. Why Not Switch a Constructor to a Setter Just to Avoid the Error?

Setter/field injection can allow certain singleton circular references to be resolved by instantiating objects first and injecting properties afterward, depending on configuration and lifecycle. However, doing so hides a circular dependency in the design.

Since Spring Boot 2.6, circular references are disallowed by default in standard configurations. Behavior can be changed via `spring.main.allow-circular-references` in supported versions, but this is not a preferred architectural solution.

Instead of enabling circular references or moving dependencies to fields, break the cycle:

- Extract a third service containing shared logic.
- Place an abstraction/event between the two services.
- Re-evaluate the dependency direction between domain and application layers.
- Use a coordinator to orchestrate the two collaborators instead of having them call each other.

### 12.2. Example of Separating Responsibilities

~~~java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }
}
~~~

~~~java
@Service
public class OrderService {

    private final PaymentService paymentService;
    private final OrderRepository orderRepository;

    public OrderService(
            PaymentService paymentService,
            OrderRepository orderRepository) {
        this.paymentService = paymentService;
        this.orderRepository = orderRepository;
    }
}
~~~

If `PaymentService` needs to notify that an order has been paid, it can publish a domain/application event or call an abstraction with an appropriate dependency direction rather than injecting `OrderService` back into it.

## 13. Dependencies with Different Scopes and Resolution Timing

Constructor injection resolves dependencies when the bean is created. This has implications when a dependency has a scope other than singleton.

For example, a singleton directly injecting a prototype bean:

~~~java
@Service
public class ReportService {

    private final ReportSession session;

    public ReportService(ReportSession session) {
        this.session = session;
    }
}
~~~

If `ReportService` is a singleton and `ReportSession` is a prototype, the prototype instance is typically created when the singleton is created and stored in the field. It will not automatically create a new instance on every method call.

If you truly need a new prototype each time, inject `ObjectProvider<ReportSession>`:

~~~java
@Service
public class ReportService {

    private final ObjectProvider<ReportSession> sessions;

    public ReportService(ObjectProvider<ReportSession> sessions) {
        this.sessions = sessions;
    }

    public void generate() {
        ReportSession session = sessions.getObject();
        session.generate();
    }
}
~~~

`ObjectProvider` is declared in the constructor; resolving the concrete instance is deferred until `getObject()` is called.

With request-scoped or session-scoped beans, understand Spring Web's proxy/scope semantics. Do not inject a short-lived object into a singleton assuming it automatically changes per request without an appropriate scoped proxy or provider.

## 14. Constructor Injection and @Configuration

In a configuration class, the parameters of an `@Bean` method are also dependencies that Spring needs to resolve:

~~~java
@Configuration(proxyBeanMethods = false)
public class BillingConfiguration {

    @Bean
    BillingService billingService(
            InvoiceRepository repository,
            TaxCalculator calculator) {
        return new BillingService(repository, calculator);
    }
}
~~~

Here Spring invokes the factory method with the corresponding beans. `BillingService`'s constructor can still express the contract:

~~~java
public class BillingService {

    private final InvoiceRepository repository;
    private final TaxCalculator calculator;

    public BillingService(
            InvoiceRepository repository,
            TaxCalculator calculator) {
        this.repository = repository;
        this.calculator = calculator;
    }
}
~~~

If the class is registered with `@Service` or `@Component`, the container uses the class constructor. If the object is created via an `@Bean` factory method, Spring uses the factory method's parameters to resolve dependencies before calling the method.

There is no need to inject `ApplicationContext` into a configuration class just to manually look up beans that the method can already declare as parameters.

## 15. Distinguishing Constructor Injection from @ConfigurationProperties Constructor Binding

Both mechanisms use constructors, but for different purposes.

### Spring Constructor Injection

~~~java
@Service
public class PaymentService {

    private final PaymentGateway gateway;

    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}
~~~

Spring finds a `PaymentGateway` bean and passes it into the constructor.

### Spring Boot Constructor Binding

~~~java
@ConfigurationProperties(prefix = "app.payment")
public record PaymentProperties(
        URI endpoint,
        Duration timeout) {
}
~~~

The Spring Boot Binder reads properties like `app.payment.endpoint` and `app.payment.timeout` and creates the configuration object.

The service can then receive the properties bean via constructor injection:

~~~java
@Service
public class PaymentService {

    private final PaymentProperties properties;

    public PaymentService(PaymentProperties properties) {
        this.properties = properties;
    }
}
~~~

Diagram:

~~~text
application.yml
      |
      v
Spring Boot Binder
      |
      v
PaymentProperties bean
      |
      v
Spring dependency injection
      |
      v
PaymentService constructor
~~~

Do not mistake a properties class constructor for a place to inject `PaymentGateway`, `DataSource`, or business services. Properties classes should hold configuration data; services are where both configuration and required collaborators are received.

## 16. Do Not Perform Heavy Work in Constructors

A constructor should produce an object in a valid state, not launch full business workflows.

Avoid:

~~~java
@Service
public class CatalogService {

    public CatalogService(CatalogRepository repository) {
        repository.findAll();       // I/O in constructor
        remoteClient.warmUp();      // Network call in constructor
        startBackgroundThread();    // Creating thread in constructor
    }
}
~~~

Side effects in constructors cause problems:

- Unit tests must mock many things just to construct the object.
- Startup may fail because an external service is temporarily unavailable.
- The bean may not yet be fully wrapped with proxies/AOP.
- Circular dependencies or lifecycles become more complex.
- It is hard to distinguish object creation from task execution.

Constructors should store dependencies and check invariants. If initialization is needed, choose an appropriate lifecycle hook such as `InitializingBean`/`@PostConstruct` for lightweight setup, or `ApplicationRunner`/`ApplicationReadyEvent` for work requiring a refreshed application. For retryable or background tasks, design a dedicated mechanism rather than blocking the constructor.

## 17. Constructor Injection and Proxies/AOP

A Spring bean may be wrapped by a proxy to support transactions, caching, async execution, or security. Constructor injection ensures the caller receives the bean from the container, usually as a proxy when advisors apply.

~~~java
@Service
public class CheckoutService {

    private final PaymentService paymentService;

    public CheckoutService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
~~~

`CheckoutService` receives its dependency from the container, so it calls through `PaymentService`'s proxy if that bean is proxied.

If created manually:

~~~java
this.paymentService = new PaymentService(...);
~~~

then that object is not a Spring-managed bean and will not automatically get transaction/cache/async proxies.

Constructor injection does not solve every AOP limitation by itself: self-invocation, final/private methods, and proxy strategies still need attention. However, it keeps dependency acquisition flowing through the Spring container instead of manual instantiation.

## 18. Easily Testing Classes When Dependencies Are Passed via Constructors

A service using constructor injection can be unit tested by passing fakes or mocks:

~~~java
class OrderServiceTest {

    private final OrderRepository repository =
            mock(OrderRepository.class);

    private final PaymentService paymentService =
            mock(PaymentService.class);

    private final OrderService service =
            new OrderService(repository, paymentService);

    @Test
    void placesOrder() {
        // arrange
        // act
        // assert
    }
}
~~~

There is no need to start a Spring context if the goal is testing service logic. Tests can use Mockito, fake implementations, or lightweight real objects as needed.

### 18.1. Unit Tests Do Not Replace Wiring Integration Tests

Calling a constructor successfully in a unit test does not prove Spring registered the right bean, qualifier, or profile.

Use `@SpringBootTest` or `ApplicationContextRunner` to verify wiring at the needed scope:

~~~java
@SpringBootTest
class OrderServiceWiringTest {

    @Autowired
    OrderService orderService;

    @Test
    void contextCreatesOrderService() {
        assertThat(orderService).isNotNull();
    }
}
~~~

If multiple implementations of a dependency exist, specifically verify which bean is injected. Small wiring tests catch configuration errors before deployment.

### 18.2. Testing Missing Dependencies

For required dependencies, a context without a matching bean should fail. Use `ApplicationContextRunner` to assert context startup failure and its root cause, rather than letting the service run and checking for null fields at runtime.

## 19. Designing Readable Constructor APIs

A good constructor does not just list parameters. It should also help readers understand responsibilities and dependency order.

### 19.1. Avoid Unmeaningful Primitive/String Parameters

~~~java
public PaymentService(
        String url,
        String key,
        int timeout,
        boolean enabled) {
}
~~~

A signature like this makes it hard to tell what each parameter means, easy to pass arguments in the wrong order, and mixes configuration with service dependencies.

Group configuration data into a properties object:

~~~java
public PaymentService(
        PaymentProperties properties,
        PaymentGateway gateway) {
}
~~~

However, do not dump everything into a massive `ApplicationSettings` just to shorten the constructor. A properties object should represent a cohesive group of settings.

### 19.2. Use Value Objects When Parameters Have Domain Meaning

For example, `Duration` is clearer than a unitless integer:

~~~java
public RetryService(Duration backoff) {
}
~~~

If a data type carries clear business meaning, create a dedicated value object to prevent mixing up parameters of the same primitive type.

### 19.3. Do Not Create Constructor Overloads for Every Optional Combination

A class with 5 optional dependencies can lead to many constructor overloads and implicit defaults. Re-examine:

- Can a capability be extracted into a separate collaborator?
- Can a configuration object hold a group of settings?
- Is the dependency truly optional, or is it a missed requirement?
- Does a default implementation express the policy properly?

Constructor overloads should reflect meaningful ways to create an object, not every combination of booleans and nullables.

## 20. Circular Dependencies Often Signal Unclear Responsibility Boundaries

For example, A calls B to process payment, and B calls A to update the order. The circular dependency makes both classes hard to instantiate independently and hard to test.

You can extract an event abstraction:

~~~java
public record PaymentCompleted(
        UUID orderId,
        Instant completedAt) {
}
~~~

The payment service publishes an event when payment succeeds:

~~~java
@Service
public class PaymentService {

    private final ApplicationEventPublisher events;

    public PaymentService(ApplicationEventPublisher events) {
        this.events = events;
    }

    public void completePayment(UUID orderId) {
        // Complete payment processing.
        events.publishEvent(
                new PaymentCompleted(orderId, Instant.now()));
    }
}
~~~

The order service listens to the event:

~~~java
@Component
public class OrderPaymentListener {

    private final OrderRepository orders;

    public OrderPaymentListener(OrderRepository orders) {
        this.orders = orders;
    }

    @EventListener
    public void onPaymentCompleted(PaymentCompleted event) {
        // Update order status.
    }
}
~~~

This example illustrates decoupling dependency direction within the same application context. For events needing transactional/outbox guarantees, retries, or durable delivery, choose an appropriate event mechanism; Spring in-process events do not automatically provide durability like a message broker.

Do not use events solely to avoid a long constructor. Use them when an event genuinely expresses a domain/application occurrence and decoupling producer from consumer is beneficial.

## 21. When Is Setter Injection Reasonable?

Constructor injection is the good default for required dependencies, but setter injection can be reasonable in certain cases:

- A dependency is genuinely optional and the class has valid behavior without it.
- A configuration property can change according to a well-defined lifecycle.
- A framework/legacy API requires a no-argument constructor and property population.
- A bean has multi-step configuration under a specialized contract.

Example of an optional callback:

~~~java
@Component
public class ImportCoordinator {

    private ImportListener listener = ImportListener.NOOP;

    public void setListener(ImportListener listener) {
        this.listener = listener;
    }
}
~~~

Here, the `NOOP` default is valid behavior and a listener can be configured additionally. However, if `ImportCoordinator` cannot import without a repository, the repository still belongs in the constructor.

Do not move required dependencies to setters just because of a circular dependency or because the constructor "looks long."

## 22. Avoid Dependency Injection via Static Fields

Avoid:

~~~java
@Component
public class LegacyHelper {

    @Autowired
    private static CatalogRepository repository;
}
~~~

Spring dependency injection is designed for bean instances. Static fields belong to the class, not a specific object, and create global state that is hard to manage.

Instead, pass the dependency into the constructor of the bean that uses it:

~~~java
@Service
public class CatalogService {

    private final CatalogRepository repository;

    public CatalogService(CatalogRepository repository) {
        this.repository = repository;
    }
}
~~~

If legacy code uses static utilities, move parts needing I/O or Spring services to an instance collaborator; reserve static methods for pure functions needing no dependencies.

## 23. Constructors and Dependency Initialization Order

When Spring creates bean A requiring bean B via constructor, B must be resolved before A's constructor can run. Thus, constructor dependencies express object creation order in the graph.

~~~text
Controller
    |
    v
OrderService
    |
    +------> OrderRepository
    |
    +------> PaymentService
                 |
                 v
             PaymentClient
~~~

The container manages this graph, including singleton caching, scopes, proxies, and lifecycle callbacks. Do not manually sequence initialization by calling `getBean()` in constructors.

If a specific initialization order is genuinely required, use explicit dependencies, appropriate lifecycle callbacks, or events. Avoid relying on component scan order or configuration file order.

## 24. Just Because a Dependency Can Be a Bean Does Not Mean It Should Be Injected

A class may inject too many beans because it is taking over responsibilities belonging to other modules.

Example:

~~~java
@Service
public class OrderService {

    private final OrderRepository orders;
    private final CustomerRepository customers;
    private final ProductRepository products;
    private final TaxRepository taxes;
    private final CurrencyRepository currencies;
    private final EmailClient email;
    private final SmsClient sms;
    private final PdfRenderer pdf;
    private final AuditRepository audit;
}
~~~

This constructor is a sign to review responsibilities. The service may simultaneously be pricing orders, rendering invoices, sending notifications, and writing audit logs.

You do not necessarily have to wrap every repository in a service wrapper. However, you can split use cases:

- `OrderPricingService` handles pricing calculation.
- `InvoiceService` handles invoice generation.
- `NotificationService` sends notifications.
- `OrderApplicationService` orchestrates the workflow.

Each class receives only the dependencies needed for its own job. The constructor then becomes a concise description of responsibility scope.

## 25. Common Constructor Design Pitfalls

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Bean fails to start due to missing dependency | Constructor requests an unregistered bean | Register the bean, add the right dependency, or review the requirement |
| `NoUniqueBeanDefinitionException` | Multiple beans of the same type exist | Use `@Qualifier`, `@Primary`, or inject a collection |
| `BeanCurrentlyInCreationException` | Constructor dependencies form a cycle | Split responsibilities, use events, or introduce an abstraction to break the cycle |
| Unit test cannot instantiate service | Class relies on field injection/Spring context | Move required dependencies to constructor |
| Field dependency is null in tests | Object created with `new`; Spring did not inject fields | Pass dependencies via constructor |
| Constructor has too many parameters | Class has multiple responsibilities or ungrouped settings | Refactor by responsibility; do not hide with field injection |
| Optional dependency causes NPE | Null used without handling | Use Optional/provider/default implementation or validate |
| Prototype bean does not change per call | Injected directly into a singleton so resolved only once at singleton creation | Use ObjectProvider or a scoped proxy |
| Secondary constructor picked unexpectedly by Spring | Multiple constructors without clear selection rules | Annotate the intended constructor with @Autowired when needed |
| Dependency created with `new` lacks AOP | Object lives outside the Spring container | Inject a container-managed bean |
| Startup runs queries/HTTP too early | Constructor contains side effects | Move work to an appropriate lifecycle hook or application service |
| Runs only when circular references are enabled | Dependency cycle masked by two-phase initialization | Refactor graph to eliminate cycles |

## 26. Workflow for Designing a Spring Bean Constructor

When creating a new class or refactoring an existing bean, follow these steps:

1. List the collaborators the class needs to fulfill its responsibility.
2. Mark which dependencies are required for the object to exist in a valid state.
3. Place required dependencies in the constructor.
4. Declare corresponding fields `private final`.
5. For optional dependencies, choose `Optional<T>`, `ObjectProvider<T>`, or a default implementation according to semantics.
6. If multiple beans share the same type, specify a qualifier or default.
7. Check the graph for circular dependencies.
8. Keep the constructor limited to validation/assignment, performing no I/O or business workflows.
9. Unit test by passing fakes/mocks directly into the constructor.
10. Integration test the context to confirm Spring wiring and profiles/conditions are correct.

~~~

If the dependency is one of multiple implementations, proceed to select `@Qualifier`/`@Primary` or a collection according to the usage intent.

## 27. Principles to Remember

1. **The constructor is the object creation contract.** Required dependencies should appear in the constructor.
2. **Use final fields** to keep dependency references stable after bean creation.
3. With a single constructor, Spring usually injects automatically without `@Autowired`.
4. If a class has multiple constructors, explicitly specify which constructor Spring should use.
5. **Optionality must be explicit.** Use `Optional`, `ObjectProvider`, `@Nullable`, or a default implementation when absence is truly valid.
6. If a required dependency is missing, let the context fail fast instead of creating an incomplete object.
7. When multiple candidates exist, use qualifiers/defaults or inject a collection; do not leave Spring guessing.
8. Constructor injection exposes circular dependencies clearly; refactor the dependency graph instead of switching to field/setter injection to mask cycles.
9. Do not use `ApplicationContext` as a service locator inside business classes.
10. Do not perform I/O, DB queries, or heavy business work in constructors.
11. Inject beans from the Spring container to preserve lifecycle, AOP proxies, and configuration.
12. Unit tests can instantiate classes via constructors with fakes/mocks; integration tests verify container wiring.
13. Long constructors can signal multiple responsibilities; refactor by domain/use case rather than just reducing parameter count.
14. Distinguish service constructor injection from `@ConfigurationProperties` constructor binding.

**Conclusion:** Good constructor design makes an object's valid state explicit at creation time. Spring can resolve required dependencies before instantiating a bean, and developers can read the constructor signature to understand what the class needs. Using constructors for core collaborators, expressing optional dependencies with explicit types, and keeping the dependency graph free of cycles makes Spring Boot applications easier to start, test, and maintain.
