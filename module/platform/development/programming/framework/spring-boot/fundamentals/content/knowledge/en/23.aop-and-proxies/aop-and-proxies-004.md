# JDK Dynamic Proxies and Class-Based Proxies

When using Spring Boot, you can place `@Transactional` on a service and see transactions automatically opened and closed when methods are called. You can use `@Async` to dispatch calls to an executor, or `@Cacheable` to store results in a cache. With Spring AOP, many such behaviors are implemented using a **proxy**: an intermediary object standing between the caller and the real business object.

Spring AOP typically creates proxies using two strategies:

- **JDK dynamic proxy:** creates a proxy object implementing the target's interfaces.
- **Class-based proxy:** creates a subclass of the target using CGLIB technology integrated into Spring.

The two strategies can behave differently when injecting beans by interface or concrete class, when methods are `final`, when a class has no interface, and when one method calls another method within the same object.

This lesson belongs to the **AOP and Proxies** chapter of **Spring Boot Fundamentals**. After this lesson, you should understand why a bean may not share the same runtime class as the class you wrote, how to choose between JDK and class-based proxies in Spring Boot, the limitations of each kind, and how to diagnose when advice does not run.

## 1. What is a proxy?

In Java, instead of handing the business object directly to the caller, we can hand over an intermediary object sharing the same usage interface. The intermediary receives the call, performs additional work, and then forwards it to the real object.

Example:

```text
Controller
    │
    │ paymentService.pay("ORDER-001")
    ▼
Spring AOP proxy
    │
    ├── Before call: start measuring duration
    │
    ▼
Target: PaymentService
    │
    └── Execute payment logic
    │
    ▼
Spring AOP proxy
    │
    ├── After call: record execution duration
    │
    ▼
Controller receives result
```

Components:

| Term | Meaning |
|---|---|
| **Target** | The object performing the original business logic |
| **Proxy** | The intermediary object clients typically receive from the Spring container |
| **Advice** | Additional behavior before, after, or around the call |
| **Join point** | A point where advice can apply; in Spring AOP, primarily method execution |
| **Pointcut** | A rule determining which methods/join points advice applies to |
| **Advisor** | Combination of a pointcut and advice in Spring AOP infrastructure |

Spring AOP follows the proxy model, unlike a mechanism that rewrites bytecode for every object in the JVM. Only calls going through an appropriate proxy have the opportunity to be processed by the proxy's interceptors.

### 1.1. Non-Spring example: manual decorator

Suppose:

```java
public interface PaymentOperations {
    void pay(String orderId);
}
```

Implementation:

```java
public final class DefaultPaymentOperations
        implements PaymentOperations {

    @Override
    public void pay(String orderId) {
        System.out.println("Paying order " + orderId);
    }
}
```

We can write a wrapper manually:

```java
public final class LoggingPaymentOperations
        implements PaymentOperations {

    private final PaymentOperations delegate;

    public LoggingPaymentOperations(PaymentOperations delegate) {
        this.delegate = delegate;
    }

    @Override
    public void pay(String orderId) {
        System.out.println("Before payment");
        delegate.pay(orderId);
        System.out.println("After payment");
    }
}
```

Client usage:

```java
PaymentOperations payment =
        new LoggingPaymentOperations(
                new DefaultPaymentOperations()
        );

payment.pay("ORDER-001");
```

This illustrates a manual proxy/decorator. Spring AOP automatically generates the intermediary layer and wires advice per configuration, so you do not have to write wrappers for every service.

## 2. How does a JDK dynamic proxy work?

JDK dynamic proxy is a built-in Java mechanism in package:

```java
java.lang.reflect.Proxy
java.lang.reflect.InvocationHandler
```

It produces an object whose runtime class is generated by the JDK, **implementing one or more interfaces**. Each supported method call passes through an `InvocationHandler`.

Diagram:

```text
PaymentOperations interface
          ▲             ▲
          │             │
          │             └── DefaultPaymentService (target)
          │
JDK-generated proxy
          │
          ├── InvocationHandler / interceptor
          │
          └── Invoke target.pay(...)
```

Key characteristics:

- The proxy implements the selected interfaces.
- The proxy is **not a subclass** of the concrete target class.
- Clients should work through the interfaces exposed by the proxy.
- `final` on the target class does not prevent a JDK proxy as long as the target implements suitable interfaces.
- Methods not declared in the interfaces exposed by the proxy cannot normally be invoked through a reference typed to that interface.

### 2.1. Pure Java JDK proxy example

Create an interface:

```java
package com.example.proxy;

public interface Calculator {
    int add(int a, int b);
}
```

Implementation:

```java
package com.example.proxy;

public class SimpleCalculator implements Calculator {

    @Override
    public int add(int a, int b) {
        return a + b;
    }
}
```

Create the proxy:

```java
package com.example.proxy;

import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;

public class JdkProxyExample {

    public static void main(String[] args) {
        Calculator target = new SimpleCalculator();

        Calculator proxy = (Calculator) Proxy.newProxyInstance(
                Calculator.class.getClassLoader(),
                new Class<?>[] { Calculator.class },
                (proxyObject, method, arguments) -> {
                    System.out.println("Before: " + method.getName());
                    try {
                        Object result = method.invoke(target, arguments);
                        System.out.println("After: " + method.getName());
                        return result;
                    } catch (InvocationTargetException ex) {
                        throw ex.getCause();
                    }
                }
        );

        System.out.println(proxy.add(2, 3));
        System.out.println(proxy instanceof Calculator);
        System.out.println(proxy instanceof SimpleCalculator);
    }
}
```

Illustrative output:

```text
Before: add
After: add
5
true
false
```

In the example, the JDK generates a runtime class implementing `Calculator`. Because it does not extend `SimpleCalculator`, checking `proxy instanceof SimpleCalculator` returns `false`.

This is a minimal example to understand the Java foundation. Spring AOP does not require you to call `Proxy.newProxyInstance` yourself; the framework manages interceptors, chains, pointcuts, and targets using Spring's abstractions.

### 2.2. Why does a JDK proxy require an interface?

JDK dynamic proxies generate classes implementing a list of interfaces. They cannot automatically create a subclass of an interface-less concrete class using `java.lang.reflect.Proxy` alone.

For instance, this class has no interface:

```java
public class InventoryService {

    public int available() {
        return 42;
    }
}
```

If Spring AOP needs to proxy `InventoryService` and there is no suitable interface to use, Spring generally has to choose a class-based proxy mechanism.

### 2.3. Interfaces are the contract visible to clients

Suppose:

```java
public interface OrderService {
    void placeOrder(String orderId);
}
```

```java
@Service
public class DefaultOrderService implements OrderService {

    @Override
    public void placeOrder(String orderId) {
        System.out.println("Placed " + orderId);
    }

    public void internalRebuildIndex() {
        System.out.println("Rebuilding index");
    }
}
```

With a JDK interface proxy, the client holds an `OrderService` reference and can call `placeOrder`. The `internalRebuildIndex` method is not part of the interface contract, so it cannot be called through `OrderService`.

This is generally good design: the public API of the service is defined by the interface, while implementation-specific details are not directly exposed to consumers.

## 3. How does a class-based proxy work?

Spring's class-based proxies typically use **CGLIB** (Code Generation Library), integrated and repackaged inside `spring-core`.

Instead of generating an object that only implements interfaces, Spring generates a class **extending the concrete target class** and can override eligible methods to insert interceptor logic.

Diagram:

```text
       InventoryService
              ▲
              │ extends
              │
InventoryService$$SpringCGLIB$$...
              │
              ├── Interceptor / advice chain
              │
              └── Delegate to target method
```

The dynamic class name may include markers like `$$SpringCGLIB$$` in certain Spring versions, though you should not depend on that name because it is an implementation detail.

### 3.1. Example of a class without an interface

```java
package com.example.demo.inventory;

import org.springframework.stereotype.Service;

@Service
public class InventoryService {

    public int countAvailable() {
        return 42;
    }
}
```

If an advisor applies to `countAvailable()` and Spring needs to create a proxy, a class-based proxy allows clients to keep using the `InventoryService` type:

```java
@Service
public class InventoryControllerHelper {

    private final InventoryService inventoryService;

    public InventoryControllerHelper(
            InventoryService inventoryService
    ) {
        this.inventoryService = inventoryService;
    }

    public int available() {
        return inventoryService.countAvailable();
    }
}
```

Here, the created proxy is a subtype of `InventoryService`. Therefore injection by concrete class can work.

### 3.2. Differences from JDK proxies

| Property | JDK dynamic proxy | Class-based proxy (CGLIB) |
|---|---|---|
| Java mechanism | Generates class implementing interfaces | Generates subclass of target class |
| Target must have interface? | Needs interface to proxy | No |
| Proxy is instance of interface? | Yes, if interface is proxied | Yes if target implements interface |
| Proxy is instance of concrete class? | No | Usually yes |
| Can proxy `final` target class? | Yes if using interface | Cannot subclass `final` class |
| Can override `final` method? | No need to subclass target to intercept calls via interface | Cannot override `final` method |
| Can intercept `private` method? | Not as a normal contract method | No, because private methods cannot be overridden |
| Injection by concrete target type | Usually unsuitable | Usually suitable |

**Class-based proxy does not mean every method is advised.** Only methods supported by the proxy mechanism and pointcut go through interceptors; final/private/static/constructors are important limitations.

## 4. What rules does Spring AOP use to choose a proxy?

At the Spring Framework level, when using auto-proxying with interface-based defaults, the general rules are:

1. If the target has suitable interfaces and class proxying is not forced, Spring can use a JDK dynamic proxy.
2. If the target lacks suitable interfaces, Spring typically uses a class-based proxy.
3. If `proxyTargetClass = true` is configured, Spring tries to use a class-based proxy even if the target has interfaces.
4. If no advisor applies to the bean, there may be **no AOP proxy at all**.

Diagram:

```text
              Does bean need AOP advice?
                        │
             ┌──────────┴──────────┐
             │                     │
            No                    Yes
             │                     │
             ▼                     ▼
      Bean needs no proxy    Is class proxy forced?
                                   │
                          ┌────────┴────────┐
                          │                 │
                         Yes                No
                          │                 │
                          ▼                 ▼
                    Class-based       Has suitable interface?
                    proxy (CGLIB)         │
                                    ┌──────┴──────┐
                                    │             │
                                   Yes            No
                                    │             │
                                    ▼             ▼
                                JDK proxy      Class proxy
```

This is a mental model for choosing proxy technology. Specific framework integrations may configure their own auto-proxy creators or merge proxying options within the container.

### 4.1. Spring Framework defaults differ from Spring Boot defaults

This is especially important to remember.

In Spring Framework when using:

```java
@EnableAspectJAutoProxy
```

the `proxyTargetClass` attribute defaults to `false`. When a target has interfaces, JDK proxy is the common choice.

In **Spring Boot** with typical AOP auto-configuration, Boot **defaults to class-based proxies**. The property:

```properties
spring.aop.proxy-target-class=true
```

is Boot's common default value. Hence, having an interface does not guarantee Boot will create a JDK proxy.

To use JDK proxies when interfaces exist, configure:

```properties
spring.aop.proxy-target-class=false
```

This is crucial when taking a plain Spring Framework example and running it in Spring Boot: with the exact same service and aspect, the proxy type may differ due to default settings.

### 4.2. The property only applies within the configured AOP system

The `spring.aop.proxy-target-class` property belongs to Spring Boot's AOP configuration. When Boot's AOP auto-configuration/auto-proxying is active, it controls whether class proxies or interface proxies are preferred.

If an application sets up a `ProxyFactory` manually, uses a custom auto-proxy creator, or uses other proxy mechanisms, inspect the configuration of that specific mechanism. Do not assume one property controls every proxy object across the entire JVM.

## 5. Configuring the switch between JDK proxies and class-based proxies

### 5.1. Configuration in application.properties

To prefer JDK dynamic proxies when a bean has interfaces:

```properties
spring.aop.proxy-target-class=false
```

To use class-based proxies:

```properties
spring.aop.proxy-target-class=true
```

### 5.2. Configuration in application.yml

Preferring JDK proxies:

```yaml
spring:
  aop:
    proxy-target-class: false
```

Preferring class proxies:

```yaml
spring:
  aop:
    proxy-target-class: true
```

### 5.3. Configuring with @EnableAspectJAutoProxy

In a Spring Framework application configuring AOP manually, you can write:

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class AopConfiguration {
}
```

To let Spring use an interface-based strategy where appropriate:

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = false)
public class AopConfiguration {
}
```

However, in Spring Boot, avoid setting the Boot property while also adding multiple auto-proxy creator annotations without understanding how they interact. Settings requiring class proxies can be merged by Spring at the stronger level within the same bean factory.

In most Boot applications using `spring-boot-starter-aop`, start with `spring.aop.proxy-target-class` and verify the actual proxy.

### 5.4. What if there is no interface?

Setting:

```properties
spring.aop.proxy-target-class=false
```

**does not force Spring to create JDK proxies for every bean**. If a bean needs advice but has no suitable interface, Spring can still use a class-based proxy.

The value `false` means not forcing all proxies to be class-based; it does not mean every target can use a JDK proxy.

### 5.5. Other configurations can force class proxies

An application may enable transaction management, async support, caching, or other auto-proxy creators. Some configurations forcing `proxyTargetClass=true` can affect the container's proxying policy, not just a single aspect.

Therefore, if you set the property to `false` yet still see a class proxy, check related proxy mechanisms and whether the target has suitable interfaces. Do not immediately conclude the property was ignored.

## 6. Spring Boot demo: service, interface, and @Aspect

We build a small example to directly observe the difference.

### 6.1. AOP dependency

With Gradle:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    implementation 'org.springframework.boot:spring-boot-starter-aop'
}
```

The example assumes the project already has the Spring Boot plugin, Java version, and dependency management configured. The AOP starter provides the dependencies needed to use Spring AOP and AspectJ annotation style.

### 6.2. Service interface

```java
package com.example.demo.payment;

public interface PaymentOperations {
    PaymentReceipt pay(String orderId);
}
```

DTO declaration:

```java
package com.example.demo.payment;

public record PaymentReceipt(
        String orderId,
        boolean successful
) {
}
```

`record` is suitable for projects using Java 17 or higher, such as Spring Boot 3 applications.

### 6.3. Implementation

```java
package com.example.demo.payment;

import org.springframework.stereotype.Service;

@Service
public class DefaultPaymentService implements PaymentOperations {

    @Override
    public PaymentReceipt pay(String orderId) {
        System.out.println("Paying order " + orderId);
        return new PaymentReceipt(orderId, true);
    }
}
```

### 6.4. Timing aspect

```java
package com.example.demo.payment;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class PaymentTimingAspect {

    @Around(
        "execution(* com.example.demo.payment..*.pay(..))"
    )
    public Object measure(ProceedingJoinPoint joinPoint)
            throws Throwable {

        long started = System.nanoTime();

        try {
            return joinPoint.proceed();
        } finally {
            long elapsed = System.nanoTime() - started;

            System.out.println(
                    "Payment method: " + joinPoint.getSignature()
                            + ", elapsed nanos = " + elapsed
            );
        }
    }
}
```

The pointcut selects methods named `pay` in `com.example.demo.payment` and its subpackages. `@Around` calls `proceed()` to forward the call, then records duration in `finally`.

If you forget `joinPoint.proceed()` while still returning a value, the business method may never execute. This is a critical bug when writing around advice.

### 6.5. Main class and runner

```java
package com.example.demo;

import com.example.demo.payment.PaymentOperations;
import org.springframework.aop.support.AopUtils;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @Bean
    ApplicationRunner proxyInspector(PaymentOperations payments) {
        return args -> {
            System.out.println(
                    "Is AOP proxy: " + AopUtils.isAopProxy(payments)
            );
            System.out.println(
                    "Is JDK proxy: " + AopUtils.isJdkDynamicProxy(payments)
            );
            System.out.println(
                    "Is class proxy: " + AopUtils.isCglibProxy(payments)
            );
            System.out.println(
                    "Runtime class: " + payments.getClass().getName()
            );

            payments.pay("ORDER-001");
        };
    }
}
```

If the aspect is detected by Spring and the advisor matches, the bean received by the runner is normally an AOP proxy.

### 6.6. Running with a JDK dynamic proxy

In `application.yml`:

```yaml
spring:
  aop:
    proxy-target-class: false
```

Illustrative log:

```text
Is AOP proxy: true
Is JDK proxy: true
Is class proxy: false
Runtime class: jdk.proxy...$Proxy...
Paying order ORDER-001
Payment method: ..., elapsed nanos = ...
```

The runtime class name may vary by JDK. What to observe is the `AopUtils` output, not a specific class name string.

### 6.7. Running with a class-based proxy

Change to:

```yaml
spring:
  aop:
    proxy-target-class: true
```

Illustrative log:

```text
Is AOP proxy: true
Is JDK proxy: false
Is class proxy: true
Runtime class: com.example.demo.payment.DefaultPaymentService$$SpringCGLIB$$...
Paying order ORDER-001
Payment method: ..., elapsed nanos = ...
```

Both modes execute the business logic and timing advice identically for matching calls. The primary difference lies in the proxy generation mechanism and the types/limits each proxy supports.

## 7. Proxies and dependency injection: why injecting by interface is safer

Suppose `DefaultPaymentService` implements `PaymentOperations`.

Injection by interface:

```java
@Service
public class CheckoutService {

    private final PaymentOperations payments;

    public CheckoutService(PaymentOperations payments) {
        this.payments = payments;
    }

    public void checkout(String orderId) {
        payments.pay(orderId);
    }
}
```

Compatible with both:

- JDK dynamic proxies implementing `PaymentOperations`.
- Class-based proxies extending `DefaultPaymentService` and still implementing `PaymentOperations`.

Conversely, injection by concrete class:

```java
@Service
public class CheckoutService {

    private final DefaultPaymentService payments;

    public CheckoutService(DefaultPaymentService payments) {
        this.payments = payments;
    }
}
```

can fail if Spring creates a JDK proxy for the service.

Reason:

```text
JDK proxy
  implements PaymentOperations
  DOES NOT extend DefaultPaymentService
                │
                ▼
Incompatible with type DefaultPaymentService
```

### 7.1. Symptoms when injecting a concrete class

When using JDK proxies, you may hit a startup error roughly like:

```text
BeanNotOfRequiredTypeException:
Bean named 'defaultPaymentService' is expected to be of type
'DefaultPaymentService' but was actually of type
'jdk.proxy...$Proxy...'
```

Or a dependency injection error indicating no matching candidate of the concrete type.

Preferred solution:

1. Define an interface representing the business contract.
2. Inject the interface into consumers.
3. Ensure needed methods are declared in the contract.
4. Force class-based proxies only if the architecture genuinely requires the proxy to be a subtype of the concrete class.

### 7.2. Do not use casting to work around errors

Wrong:

```java
DefaultPaymentService target =
        (DefaultPaymentService) payments;
```

If `payments` is a JDK proxy, this cast is invalid and can throw `ClassCastException`.

Prefer using the interface:

```java
PaymentOperations payments = context.getBean(
        PaymentOperations.class
);
```

If the goal is debugging, use Spring AOP APIs to inspect proxy/target types. Do not cast arbitrarily or unwrap the target from the proxy for business logic.

### 7.3. Is a class-based proxy always better?

Not necessarily. Class-based proxies allow injection by concrete class, but rely on subclassing/overriding methods and obey Java inheritance limits.

JDK proxies encourage consumers to depend on interfaces; class-based proxies fit when no interface exists or compatibility with a specific class design is required.

Spring Boot defaulting to class-based proxies does not mean you should stop designing services behind interfaces everywhere.

## 8. Final classes and final methods: a crucial difference

Java lets you declare a `final` class:

```java
public final class FinalPaymentService
        implements PaymentOperations {

    @Override
    public PaymentReceipt pay(String orderId) {
        return new PaymentReceipt(orderId, true);
    }
}
```

### 8.1. JDK proxies can work with final target classes

A JDK proxy implements `PaymentOperations` without needing to subclass `FinalPaymentService`. Thus a final target class can still be proxied through an interface.

Setting `spring.aop.proxy-target-class=false` can allow using a JDK proxy in this scenario, provided other AOP conditions match.

### 8.2. Class-based proxies cannot subclass final classes

CGLIB creates a subclass. Java forbids extending a class declared `final`.

Therefore, if Spring actually needs to create a class-based AOP proxy for `FinalPaymentService`, proxy creation may fail.

Do not explain this as "Spring cannot apply AOP to final classes under any circumstances." The accurate statement is: **class-based proxies cannot extend final classes; interface-based proxies may still be a solution**.

### 8.3. Final methods in class-based proxies

Example:

```java
@Service
public class BillingService {

    public final void charge(String invoiceId) {
        System.out.println("Charge " + invoiceId);
    }
}
```

A class-based proxy cannot override `charge` because the method is `final`. Calls to that final method cannot be advised by Spring AOP's class-proxy interceptor via normal overriding.

This is why you should avoid marking methods needing `@Transactional`, `@Async`, or `@Cacheable` as `final` when relying on class-based proxies.

### 8.4. Final methods via JDK interface proxies

If a public final method of the target **is declared in a proxied interface**, calls through the JDK proxy still pass through the `InvocationHandler`, because the proxy intercepts at the interface boundary rather than overriding the target method.

Example:

```java
public interface Operation {
    void execute();
}
```

```java
public class FinalMethodOperation implements Operation {

    @Override
    public final void execute() {
        System.out.println("Executing");
    }
}
```

With a JDK interface proxy for `Operation`, calling `proxy.execute()` still goes through the proxy. `final` on the implementation method does not inherently block the JDK proxy from intercepting this interface call.

**Mechanistic conclusion:** the final-method restriction is an override limitation of **class proxies**, not a universal limitation on all calls through interface proxies.

## 9. Private, static, constructors, and non-public methods

An AOP proxy cannot arbitrarily intercept every Java operation.

### 9.1. Private methods

```java
@Service
public class ReportService {

    public void publish() {
        validateInternal();
    }

    private void validateInternal() {
        // ...
    }
}
```

`private` methods cannot be overridden by subclasses and are not part of a JDK interface proxy's public contract. Hence Spring AOP proxies do not directly advise calls to this private method.

If important behavior requires advice, place the cut point on an appropriate method callable through a proxy, or extract the behavior into another bean.

### 9.2. Static methods

`static` methods belong to the class and are not dispatched as instance methods the way AOP proxies intercept calls. Do not expect `@Transactional` on a static utility method to behave like an instance method invoked via a Spring bean proxy.

### 9.3. Constructors

Spring AOP proxies primarily intercept method executions passing through the proxy. Constructors are not cut points automatically intercepted by this proxy to apply `@Around`.

If you need logic after dependency injection, use appropriate lifecycle callbacks; if you need deep intervention in object construction, that falls outside typical proxy-based Spring AOP.

### 9.4. Protected/package-private methods

JDK interface proxies expose only methods through interfaces, typically public instance methods.

Class-based proxies can override certain `protected` or package-private methods when Java visibility and Spring mechanisms permit. However, **technical proxiability does not guarantee every framework annotation applies to all non-public methods**. You must account for the Spring version and rules of `@Transactional`, `@Async`, `@Cacheable`, or the specific advisor.

The least surprising choice when learning Spring AOP is placing primary cut points on **public service methods called from other beans**.

## 10. Self-invocation: calls inside the same object bypass the proxy

This is one of the most common Spring AOP bugs.

Example:

```java
@Service
public class OrderService {

    @Transactional
    public void saveOrder() {
        System.out.println("Saving order");
    }

    public void createOrder() {
        // Directly call another method on the same object.
        saveOrder();
    }
}
```

Suppose a controller injects `OrderService` and calls:

```java
orderService.createOrder();
```

Conceptual actual flow:

```text
Controller
    │
    ▼
Spring proxy
    │
    ▼
Target.createOrder()
    │
    └── this.saveOrder()
          │
          └── Internal call on target,
              DOES NOT pass through proxy again
```

Thus, advice applies to `saveOrder()` only when that call goes through the proxy, not automatically to a direct `this.saveOrder()` call inside the same target.

### 10.1. Does it differ between JDK proxies and CGLIB?

For regular **proxy-based Spring AOP**, the self-invocation issue exists under **both** strategies.

Even though CGLIB creates a subclass, Spring AOP still manages the call from proxy to target per framework mechanics. An internal call via the target's `this` does not route back through the outer proxy.

Do not conclude that "switching from JDK to CGLIB fixes all `@Transactional` bugs caused by self-invocation."

### 10.2. Recommended fix: extract to another bean

```java
@Service
public class OrderPersistenceService {

    @Transactional
    public void saveOrder() {
        System.out.println("Saving order");
    }
}
```

```java
@Service
public class OrderWorkflowService {

    private final OrderPersistenceService persistence;

    public OrderWorkflowService(
            OrderPersistenceService persistence
    ) {
        this.persistence = persistence;
    }

    public void createOrder() {
        // Call passes through Spring-injected bean dependency.
        persistence.saveOrder();
    }
}
```

When `persistence` is a container-supplied proxy, calling `saveOrder()` goes through the appropriate advice.

This design is generally better because transaction responsibility sits at a clear service boundary.

### 10.3. Can you obtain your own proxy?

Spring AOP provides `AopContext.currentProxy()` in some configurations when `exposeProxy` is enabled.

However, this couples business code heavily to Spring AOP infrastructure and can introduce coupling, testing difficulty, or errors when code runs outside a matching proxy invocation context.

Do not treat calling `AopContext.currentProxy()` as the default solution for self-invocation. Prefer separating responsibilities or changing the call site.

### 10.4. AspectJ weaving differs from proxy AOP

Full AspectJ compile-time or load-time weaving can weave directly into bytecode instead of only intercepting calls through proxies. Consequently, some proxy-based AOP limits like self-invocation can behave differently under weaving.

However, merely adding `spring-boot-starter-aop` **does not mean** the application has AspectJ weaving enabled. This lesson focuses on Spring AOP proxies; weaving requires separate configuration, deployment, and testing.

## 11. How do @Transactional, @Async, and @Cacheable relate?

In common proxy modes, many Spring annotations can be implemented using proxies/advice.

### 11.1. @Transactional

```java
@Service
public class TransferService {

    @Transactional
    public void transfer() {
        // Database calls within an appropriate transaction context.
    }
}
```

The transaction interceptor can start/commit/roll back a transaction around calls through the proxy. If a call bypasses the proxy due to self-invocation, the inner method's transaction advice may not run as expected.

Note that transaction behavior also depends on the transaction manager, configuration, propagation scope, and exception semantics; the proxy is only the interception mechanism.

### 11.2. @Async

```java
@Service
public class MailService {

    @Async
    public void sendMail() {
        // Work can be offloaded to an executor.
    }
}
```

With the default proxy mode of async support, calls from another bean pass through the proxy to dispatch work to an executor.

Calling `this.sendMail()` internally can execute synchronously because it bypasses the proxy.

### 11.3. @Cacheable

```java
@Service
public class ProductCatalog {

    @Cacheable("products")
    public Product findById(String id) {
        // Query data.
        return loadProduct(id);
    }
}
```

The cache interceptor applies only at matching call sites through the proxy. If this method is called internally without going through the proxy, cache advice may have no effect.

### 11.4. Annotations do not create AOP proxies in every case

The corresponding subsystems must be enabled/configured:

- Transaction support and an appropriate `PlatformTransactionManager`.
- Async support (e.g., `@EnableAsync`) and an executor.
- Caching support (e.g., `@EnableCaching`) and a cache manager.
- AspectJ-style AOP with `@Aspect` and suitable infrastructure.

Do not blame every non-running annotation on choosing JDK vs. CGLIB. The subsystem might not be enabled, the advisor might not match, the call might bypass the proxy, or the bean might not be Spring-managed.

## 12. Pay attention to annotations placed on interfaces vs. implementations

With JDK proxies, clients call methods via interfaces; with class-based proxies, clients call proxy subclasses. Still, Spring has mechanisms to look up metadata on target methods, classes, and interfaces per advisor.

Example:

```java
public interface BillingOperations {

    void charge(String invoiceId);
}
```

```java
@Service
public class BillingService implements BillingOperations {

    @Override
    @Transactional
    public void charge(String invoiceId) {
        // ...
    }
}
```

Placing `@Transactional` on the implementation method is usually clearest when you want behavior to apply to concrete business code and reduce reliance on how interface annotations are interpreted.

If you place annotations only on the interface, behavior can depend on annotation matching rules, framework version, and proxy mode; do not assume all annotation types are automatically inherited from interfaces when switching to class-based proxies.

A practical rule is: **test actual behavior under the proxy mode your application uses**, especially when migrating from JDK proxies to class-based proxies or vice versa.

## 13. At which stage of the bean lifecycle is a proxy created?

A typical Spring bean goes through these steps:

```text
Bean definition
      │
      ▼
Instantiate target
      │
      ▼
Dependency injection
      │
      ▼
Lifecycle initialization
      │
      ▼
BeanPostProcessor / AOP infrastructure
      │
      ▼
Proxy exposed to container/consumers
      │
      ▼
Business calls from other beans
```

This is a simplified model. Spring can create early references or proxies at different moments depending on circular dependencies and AOP infrastructure.

Key things to understand:

- The target's constructor is not a method call through an AOP proxy.
- `@PostConstruct` typically runs during target initialization, before the bean is exposed to consumers via its final proxy.
- Calling an annotated method from the same bean's constructor or `@PostConstruct` usually bypasses that proxy.
- An object you instantiate manually with `new` outside the container does not automatically get Spring AOP applied.

### 13.1. Objects created with new are not AOP beans

Example:

```java
PaymentOperations payment = new DefaultPaymentService();
payment.pay("ORDER-001");
```

This call goes straight to the target. Even if `DefaultPaymentService` bears `@Service` or has annotated methods, an object manually created with `new` does not become a Spring-managed proxy.

Proper usage in a Spring application:

```java
@Service
public class CheckoutService {

    private final PaymentOperations payment;

    public CheckoutService(PaymentOperations payment) {
        this.payment = payment;
    }

    public void checkout() {
        payment.pay("ORDER-001");
    }
}
```

The container injects a suitable bean, which can be a proxy if advisors apply.

## 14. Not every bean becomes a proxy

Suppose a project has `spring-boot-starter-aop`, one `@Aspect`, and ten services. Spring does not necessarily create proxies for all ten.

If the pointcut selects only `pay` methods in the payment package, services with no matching join points can remain plain objects.

That leads to a diagnostic rule:

```text
AopUtils.isAopProxy(bean) == false
```

does not by itself prove "Spring Boot failed to enable AOP." The bean may simply not need advice.

### 14.1. Pointcuts determine whether a bean is advised

For example:

```java
@Around("execution(* com.example.demo.payment..*.pay(..))")
```

targets only methods matching this expression.

If the actual service sits in another package or the method is named `checkout`, the pointcut does not match and you will not see advice logs.

Do not change `spring.aop.proxy-target-class` just to fix a mismatched pointcut expression.

### 14.2. Aspects must be discovered by Spring

```java
@Aspect
@Component
public class PaymentTimingAspect {
    // ...
}
```

`@Aspect` describes the aspect. `@Component` or an appropriate bean registration path lets Spring manage that aspect.

If the aspect class lies outside component scan scope and is not imported/registered, advice will not be auto-configured as desired.

## 15. Inspecting proxy types with AopUtils

Spring provides a utility:

```java
import org.springframework.aop.support.AopUtils;
```

Useful methods:

```java
AopUtils.isAopProxy(bean);
AopUtils.isJdkDynamicProxy(bean);
AopUtils.isCglibProxy(bean);
```

Example:

```java
@Component
public class ProxyInspector implements ApplicationRunner {

    private final PaymentOperations payments;

    public ProxyInspector(PaymentOperations payments) {
        this.payments = payments;
    }

    @Override
    public void run(ApplicationArguments args) {
        System.out.println(
                "AOP proxy = " + AopUtils.isAopProxy(payments)
        );
        System.out.println(
                "JDK proxy = " + AopUtils.isJdkDynamicProxy(payments)
        );
        System.out.println(
                "CGLIB proxy = " + AopUtils.isCglibProxy(payments)
        );
    }
}
```

This is clearer than inferring from strings in `getClass().getName()`.

### 15.1. Proxy runtime class differs from target class

With JDK proxies:

```text
proxy.getClass() -> JDK-generated class
target class      -> DefaultPaymentService
```

With class-based proxies:

```text
proxy.getClass() -> Spring/CGLIB-generated subclass
target class      -> DefaultPaymentService
```

Therefore, if the goal is knowing the true business type, do not assume `bean.getClass() == DefaultPaymentService.class`.

In diagnostic code you can use:

```java
import org.springframework.aop.framework.AopProxyUtils;

Class<?> targetType =
        AopProxyUtils.ultimateTargetClass(bean);

System.out.println(targetType.getName());
```

`ultimateTargetClass` is a helpful utility for identifying the target class across common AOP infrastructure. When working with multi-layered proxies or custom `TargetSource`s, consider the specific context and avoid using introspection in place of an explicit business API.

### 15.2. Do not use instanceof as the sole check

Checking:

```java
bean instanceof PaymentOperations
```

can return `true` for both JDK proxies and class-based proxies if the bean supports the interface.

Checking:

```java
bean instanceof DefaultPaymentService
```

can distinguish the two strategies in a simple example, yet does not definitively prove whether AOP is present. An unproxied real target is also an instance of the concrete class.

Use `AopUtils` when the goal is identifying proxy type.

## 16. Experimenting directly with ProxyFactory

Spring provides `ProxyFactory` to create proxies manually. This example isolates proxy selection from component scanning and auto-configuration.

Interface:

```java
public interface GreetingOperations {
    String greet(String name);
}
```

Implementation:

```java
public class GreetingService implements GreetingOperations {

    @Override
    public String greet(String name) {
        return "Hello, " + name;
    }
}
```

Creating a JDK proxy:

```java
import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.ProxyFactory;
import org.springframework.aop.support.AopUtils;

public class ProxyFactoryDemo {

    public static void main(String[] args) {
        ProxyFactory factory = new ProxyFactory();

        factory.setTarget(new GreetingService());
        factory.setInterfaces(GreetingOperations.class);
        factory.setProxyTargetClass(false);

        factory.addAdvice((MethodInterceptor) invocation -> {
            System.out.println("Before greet");
            return invocation.proceed();
        });

        GreetingOperations proxy =
                (GreetingOperations) factory.getProxy();

        System.out.println(AopUtils.isJdkDynamicProxy(proxy));
        System.out.println(proxy.greet("Lan"));
    }
}
```

To use a class-based proxy, in the same example change:

```java
factory.setProxyTargetClass(true);
```

Then the proxy can be a subtype of `GreetingService`:

```java
Object proxy = factory.getProxy();

System.out.println(AopUtils.isCglibProxy(proxy));
System.out.println(proxy instanceof GreetingService);
```

This example illustrates `ProxyFactory`, not how every service should be wired. In Spring Boot apps, auto-proxying normally creates proxies for registered advisors.

### 16.1. Why is ProxyFactory useful for learning?

It lets you control directly:

- The target object.
- The proxied interfaces.
- Class-based proxy enforcement mode.
- The advice/interceptor to execute.
- When the proxy is retrieved.

This helps isolate whether an issue stems from Java proxy mechanics or from the Spring container, pointcuts, component scan, or configuration.

## 17. Proxies and method overloading, generics, and bridge methods

In real Java projects, services may have overloaded methods or generic interfaces:

```java
public interface Repository<T> {
    T save(T value);
}
```

```java
public class UserRepository implements Repository<User> {

    @Override
    public User save(User value) {
        return value;
    }
}
```

The Java compiler can generate **bridge methods** to preserve type compatibility after type erasure. Spring AOP and Spring's reflection utilities handle method resolution/bridge methods where necessary.

However, when writing pointcuts heavily reliant on runtime signatures, overloads or generic methods can make matching trickier than expected.

A few guidelines:

- Prefer clear pointcuts by package, class, annotation, and method.
- Verify which methods are actually matched by advisors.
- Do not infer full behavior solely from a method name.
- Test key overloads if they carry different transaction/caching requirements.

Do not attempt to fix generic bridge-method issues by switching proxy types before verifying pointcuts and annotation metadata.

## 18. CGLIB and Java inheritance limitations

Class-based proxies rely on subclassing, so they must obey Java's constraints.

### 18.1. Final classes

A `final class` cannot be subclassed, so a CGLIB class-based proxy cannot be created for it.

### 18.2. Final methods

A `final method` cannot be overridden, so it cannot be intercepted by a class proxy via overriding.

### 18.3. Private methods

Private methods cannot be overridden; class proxies cannot advise them directly.

### 18.4. Visibility/package boundaries

A package-private method in another package or invisible to a subclass may not be overridden as required.

### 18.5. Java module system

If an application runs with the Java Platform Module System (JPMS), module/package access rules may restrict generating class proxies or reflecting on specific classes.

For example, trying to proxy a class in a JDK package can hit package-opening limits; some cases require `--add-opens`, though you should not add such flags lightly. Prefer proxying application-owned service classes or using interface proxies where appropriate.

### 18.6. Constructors and side effects

CGLIB creates a subclass, yet Spring's proxy instantiation may use Objenesis to avoid invoking the proxy constructor an extra unnecessary time. Do not rely on constructors running once vs. multiple times to detect proxy type or to perform critical side effects.

Regardless of proxy type, the target's constructor is not an AOP-advised method call.

## 19. Kotlin, records, and classes that are final by default

Some language constructs easily run into class-proxy limits.

### 19.1. Kotlin classes are final by default

In Kotlin, classes and methods are closed for inheritance by default. Hence, a Kotlin `@Service` not opened appropriately cannot have a class-based proxy created.

The Kotlin ecosystem provides the `kotlin-spring`/`all-open` plugin to automatically open classes annotated with certain Spring stereotypes.

Checklist:

- Can the class be subclassed?
- Can the advised method be overridden?
- Is the Kotlin plugin configured?
- Does the bean have an interface to use a JDK proxy?

Do not try to fix issues by randomly flipping proxy modes without understanding Kotlin-generated bytecode.

### 19.2. Java records are final

Java `record`s are final classes. They fit DTOs, value objects, and immutable configuration data very well, but are not a natural choice for service beans needing class-based AOP proxies.

You can use records as return values of services; you do not need to turn records into AOP-advised beans.

### 19.3. Immutable domain objects differ from service beans

Entities, value objects, or DTOs do not need Spring AOP proxies just because an application uses Spring Boot. Keep AOP at appropriate service boundaries where cross-cutting behavior makes sense.

## 20. Do not confuse AOP class proxies with other proxies in Spring

Spring has multiple mechanisms that create proxies or enhance classes. They may use similar underlying technology yet **serve different purposes**.

### 20.1. @Configuration(proxyBeanMethods = true)

A `@Configuration` class can be enhanced by Spring to ensure calls between `@Bean` methods are routed properly through the container.

Example:

```java
@Configuration(proxyBeanMethods = true)
public class AppConfiguration {

    @Bean
    public Client client() {
        return new Client();
    }

    @Bean
    public ClientConsumer consumer() {
        return new ClientConsumer(client());
    }
}
```

The configuration class is enhanced via class generation in certain modes. However, this handles `@Bean` method lifecycle/configuration semantics—**it does not mean every configuration class method is advised by Spring AOP aspects**.

With `proxyBeanMethods = false`, Spring does not need to proxy the class to intercept `@Bean`-to-`@Bean` calls in that way. That is a bean-configuration decision, not how JDK vs. CGLIB is selected for `@Transactional`.

### 20.2. Scoped proxies

A request-scoped bean injected into a singleton may need a scoped proxy:

```java
@RequestScope(proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContextData {
    // ...
}
```

The proxy forwards calls to the current request's target instance. It may be a class-based proxy, yet its purpose is scope management, not timing advice.

Do not conclude every bean with a proxy-like runtime class was created by an `@Aspect`.

### 20.3. Lazy proxies and other decorators

Some infrastructure uses proxies to defer creating dependencies or route calls to targets later. Their purpose differs from AOP advice, even though both involve an intermediary object.

When debugging, identify whether a proxy exists for AOP, scope, lazy resolution, or another mechanism before changing config.

## 21. Nested proxies and multiple advisors

A method can carry multiple cross-cutting behaviors:

- Transactions.
- Security.
- Caching.
- Timing/metrics.
- Retries.
- Async.

Spring can create one proxy holding a chain of advisors/interceptors, or in some configurations layered proxies.

Conceptual diagram:

```text
Caller
   │
   ▼
Proxy
   ├── Security advice
   ├── Transaction advice
   ├── Metrics advice
   │
   ▼
Target method
```

Advice ordering **is not decided by JDK vs. CGLIB**. The framework uses ordering/precedence and individual advisor rules.

To control aspect ordering:

```java
@Aspect
@Component
@Order(10)
public class LoggingAspect {
    // ...
}
```

You can use `@Order` to express precedence for that aspect. This is separate from `spring.aop.proxy-target-class`: one chooses **which advice runs first**, while the other chooses **how the proxy is generated**.

### 21.1. A single proxy can implement multiple interfaces

A JDK proxy can implement multiple interfaces:

```java
Proxy.newProxyInstance(
        loader,
        new Class<?>[] {
                PaymentOperations.class,
                Auditable.class
        },
        handler
);
```

Spring AOP can likewise expose appropriate interfaces per configuration. Thus JDK proxies are not restricted to a single interface.

### 21.2. Multiple advisors do not require multiple proxy objects

One Spring AOP proxy can hold an interceptor chain with multiple advisors. Spring does not need to generate a fresh wrapper for every `@Aspect` in all cases.

When investigating proxy type and advisor order, separate two questions:

1. **Proxy type:** interface-based or class-based?
2. **Advisor chain:** which advices apply and in what order?

## 22. Diagnosing when @Transactional or @Aspect does not work

When advice does not run, check in sequence.

### 22.1. Is the bean managed by Spring?

If the object is created with `new`, Spring AOP does not intercept it automatically.

### 22.2. Is AOP or subsystem infrastructure enabled?

Check starters/dependencies and related `@Enable...` annotations/configuration. Having `@Aspect` in source code without component scanning also produces no advice.

### 22.3. Does a proxy actually exist?

Use:

```java
AopUtils.isAopProxy(bean)
```

If false, determine whether no advisor matched the bean or AOP infrastructure is inactive.

### 22.4. What type is the proxy?

```java
AopUtils.isJdkDynamicProxy(bean)
AopUtils.isCglibProxy(bean)
```

Cross-check against `spring.aop.proxy-target-class`, interfaces, and other proxying settings.

### 22.5. Does the call go through the proxy?

For example:

```java
this.save();
```

is self-invocation and bypasses normal Spring AOP proxies. Try calling from another bean via an injected dependency.

### 22.6. Can the method be intercepted?

Check:

- Is the method `private`?
- Is the method `final` with a class proxy?
- Is the target class `final` while class proxying is forced?
- Is the method absent from the interface when using a JDK proxy?
- Is it a `static` method or constructor?
- Does the subsystem's advisor only support certain visibility levels?

### 22.7. Do pointcut or annotation metadata match?

Check package, method name, signature, annotation placement, and framework version.

### 22.8. Does the error occur when injecting the bean by concrete class?

If a JDK proxy is generated, switching constructor injection to the interface is the common fix. Do not work around it by casting the proxy to the target class.

### 22.9. Is it a non-AOP proxy?

If the type looks like a proxy yet `AopUtils` does not show the expected AOP proxy, check scoped proxies, configuration enhancements, lazy resolution, or other mechanisms.

## 23. Common troubleshooting table

| Symptom | Possible explanation | Resolution |
|---|---|---|
| Injecting `DefaultPaymentService` fails under JDK proxy | JDK proxy only implements interfaces, not a subtype of implementation | Inject `PaymentOperations` |
| `ClassCastException` when casting proxy to implementation | Proxy does not extend target class | Do not cast; use the interface |
| `final` class fails to create CGLIB proxy | Cannot subclass a final class | Remove `final` if appropriate or use interface proxy |
| `@Transactional` does not run on final method | Class proxy cannot override final method | Remove `final` or redesign boundaries |
| `@Transactional` does not run on internal call | Self-invocation bypasses proxy | Extract to another bean |
| Added `@Aspect` but no advice runs | Aspect is not a bean or pointcut does not match | Check component scan and pointcut |
| `AopUtils.isAopProxy` is false | Bean has no matching advisor or AOP is not enabled | Check infrastructure and advisors |
| Set `proxy-target-class=false` yet still see CGLIB | Bean has no interface or another setting forces class proxy | Check interfaces and proxy settings |
| Set `proxy-target-class=true` yet private method is not intercepted | Class proxy cannot override private methods | Use an appropriate public service boundary |
| Saw `$$SpringCGLIB$$` and assumed `@Aspect` caused it | Configuration/scoped proxies can also use class generation | Identify the actual proxy mechanism |
| Advice works from other beans but not from `@PostConstruct` | Callback runs during initialization, not an external call via proxy | Move logic or revise lifecycle design |
| JDK proxy still intercepts calls to final target method | Proxy intercepts at interface, no need to override target method | Expected behavior under this mechanism |

## 24. Intentionally testing proxy modes

An application may appear to work fine under class-based proxies yet fail injection when switched to JDK proxies. If a library or module must support both modes, test them separately.

### 24.1. Testing JDK mode

Example with Spring Boot test:

```java
@SpringBootTest(
        properties = "spring.aop.proxy-target-class=false"
)
class JdkProxyTest {

    @Autowired
    PaymentOperations payments;

    @Test
    void usesJdkProxy() {
        assertThat(AopUtils.isAopProxy(payments)).isTrue();
        assertThat(AopUtils.isJdkDynamicProxy(payments)).isTrue();
    }
}
```

The test assumes `PaymentOperations` has an implementation and matching aspect/advisor so the bean is AOP-proxied.

### 24.2. Testing class-based mode

```java
@SpringBootTest(
        properties = "spring.aop.proxy-target-class=true"
)
class ClassProxyTest {

    @Autowired
    PaymentOperations payments;

    @Test
    void usesClassProxy() {
        assertThat(AopUtils.isAopProxy(payments)).isTrue();
        assertThat(AopUtils.isCglibProxy(payments)).isTrue();
    }
}
```

If no advisor matches the bean, `isAopProxy` can be false and this test proves nothing about proxy strategy. Ensure the test produces an advised bean.

### 24.3. Test behavior rather than only class types

A good integration test must also verify that advice actually executes:

- Timing advice records expected invocations.
- Transactions start for matching method boundaries.
- Cache hits do not unexpectedly call the repository again.
- Async methods switch to configured executors.
- Self-invocation is not mistaken for an external proxy call.

Asserting only that a proxy class name contains `CGLIB` does not prove correct business behavior.

## 25. When to choose JDK proxies vs. class-based proxies?

### Choose JDK dynamic proxies when

- You have a clear interface for the service boundary.
- Clients only need methods in the interface.
- You want to decouple contracts from concrete implementations.
- The target class is final yet implements suitable interfaces.
- You want to avoid relying on subclassing concrete classes.
- Compatibility with interface-driven libraries/designs is required.

Example:

```java
public interface InvoiceOperations {
    void issueInvoice(String id);
}
```

Consumers inject `InvoiceOperations`, independent of the concrete type.

### Choose class-based proxies when

- The target has no suitable interface.
- The Spring Boot app uses default configuration and service classes can be subclassed.
- Consumers have valid reasons requiring injection by concrete type.
- Advised methods can be overridden and satisfy visibility limits.
- You accept the constraints of inheritance and runtime class generation.

Example:

```java
@Service
public class SearchIndexer {

    public void rebuild() {
        // ...
    }
}
```

If `rebuild()` is advised and there is no interface, a class proxy is the natural choice.

### 25.1. Decision table

| Question | Suggestion |
|---|---|
| Service has interface and consumers inject interface? | Either JDK or class proxy can fit |
| Service has no interface? | Class-based proxy if AOP is needed |
| Target class is final? | Consider JDK interface proxy if an interface exists |
| Advised method is final? | Avoid class proxy for that method; reconsider API/interface and design |
| Self-invocation present? | Extract bean or adjust service boundary; changing proxy type is not enough |
| Spring Boot using defaults? | Usually class-based proxy with AOP auto-config |
| Want to try interface-based? | `spring.aop.proxy-target-class=false` and verify with `AopUtils` |
| Implementation injection fails with JDK proxy? | Prefer injecting the interface |
| No advice matches? | No AOP proxy may be needed |

Do not choose merely based on folklore like "JDK is always faster" or "CGLIB is always faster." Performance depends on many factors and is usually minor compared to database/network I/O. Choose based on contracts, technical constraints, framework needs, and design clarity.

What matters when working with Spring AOP is understanding that **a proxy is placed between the client and the target to intercept calls**. JDK dynamic proxies implement interfaces and are not subtypes of concrete implementations; class-based proxies use subclasses so they support concrete types while being constrained by `final`, `private`, and inheritance rules. Spring Boot typically prefers class-based proxies by default, though interface-based proxies can be configured via `spring.aop.proxy-target-class=false`. Whichever strategy you choose, advice works only when beans are Spring-managed, advisors match, and calls pass through the right proxy; switching proxy modes will not automatically fix self-invocation or flawed service boundaries.
