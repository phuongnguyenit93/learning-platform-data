# Proxy-Based Spring AOP in the Container

Spring AOP (*Aspect-Oriented Programming*) helps separate shared processing from business logic: logging, execution timing, authorization checks, transaction management, caching, or rules that must apply before/after method calls. Instead of repeating the same code across dozens of services, Spring can place a **proxy** layer in front of a bean to add behavior whenever a matching method is invoked.

The foundational point of Spring AOP is: **advice typically runs when a method call passes through a proxy managed by the Spring container**. Spring AOP does not rewrite the bytecode of every class in the program, cannot intercept every Java call, and does not automatically make an object created with `new` an advised object.

Therefore, understanding AOP is not just remembering `@Aspect` or `@Around` syntax. You need a clear mental model of **who creates the proxy, whether the caller holds a reference to the proxy or the target, which methods can be intercepted, and what happens when the target calls its own methods**.

This lesson builds that model from the ground up, with Spring Boot examples, call-path diagrams, comparisons between JDK dynamic proxies and CGLIB, limitations around `final`/`private`/constructors, ways to inspect proxies in tests, and design rules to avoid "annotation present but not running" behavior.

## 1. The problem: logic cutting across multiple components

Suppose a system has these services:

~~~java
@Service
public class OrderService {
    public String placeOrder(String orderId) {
        // Order creation logic.
        return "order-" + orderId;
    }
}

@Service
public class InvoiceService {
    public String issueInvoice(String orderId) {
        // Invoice issuing logic.
        return "invoice-" + orderId;
    }
}
~~~

You want to measure how long each method takes to record performance. A direct way is inserting timing before and after each method:

~~~java
public String placeOrder(String orderId) {
    long start = System.nanoTime();
    try {
        return doPlaceOrder(orderId);
    } finally {
        long elapsed = System.nanoTime() - start;
        System.out.println("Elapsed: " + elapsed);
    }
}
~~~

When many methods share the same requirement, this creates several problems:

- Business logic and observability logic are mixed together.
- It is easy to forget to instrument a new method.
- Hard to update a system-wide policy.
- Business tests must deal with unrelated infrastructure code.
- A logging/metrics change can touch many classes.

AOP solves this by moving the timing responsibility into an **aspect**. The aspect describes *when* to intervene and *what to do* before/after the call.

However, **Spring AOP**'s interception has a specific boundary: it occurs when the call enters a **Spring AOP proxy**.

## 2. What is a proxy?

A proxy is an object standing in front of another object (the target). The caller invokes a method on the proxy; the proxy can perform extra processing and then forward the call to the target.

~~~mermaid
flowchart LR
    C["Controller / Caller"] --> P["AOP Proxy"]
    P --> A["Interceptor / Advice"]
    A --> T["Target Service"]
    T --> R["Result / Exception"]
    R --> A
    A --> P
    P --> C
~~~

For a `placeOrder` method, the general flow:

1. The controller receives an injected reference.
2. That reference may be a **proxy**, not the raw target.
3. The caller invokes `proxy.placeOrder(...)`.
4. The proxy determines which interceptors/advices apply to the method.
5. Advice executes pre-call logic (e.g., starting a timer).
6. Advice allows the call to proceed to the target.
7. The target runs business logic.
8. Advice handles the result or exception (e.g., recording duration).
9. The result or exception returns to the caller.

If a bean is not proxied or a method matches no advisors, the call can go straight to the target without AOP processing.

### 2.1. Proxy differs from target

Suppose:

~~~java
@Service
public class OrderService {
    public void submit() {
        System.out.println("Saving an order");
    }
}
~~~

When an aspect applies to `submit()`, Spring can expose a proxy in place of the target for other beans to use. That does not mean Spring edits the source code of `OrderService`.

In a class-based proxy, the proxy can be a subclass generated by CGLIB. In an interface-based proxy, the proxy is an object created via JDK dynamic proxies implementing the relevant interfaces. Both can deliver the same AOP behavior while differing in runtime type and interceptable methods.

### 2.2. A proxy is only useful when the caller actually goes through it

Compare two flows:

~~~text
Caller -> Proxy -> Advice -> Target.method()      (intercepted)
Caller -> Target.method()                         (does not pass through proxy)
~~~

This is the root cause of very important limitations such as *self-invocation* and objects created via `new`.

## 3. How is Spring AOP implemented in the container?

The Spring container manages beans across phases: registering bean definitions, instantiating objects, injecting dependencies, applying `BeanPostProcessor`s, initialization, and exposing beans to consumers.

AOP leverages this very mechanism. When AOP infrastructure is enabled, Spring registers components such as an **auto-proxy creator** to identify beans matching advisors and create proxies when needed.

~~~mermaid
flowchart TD
    A["BeanDefinition registered"] --> B["Spring creates target object"]
    B --> C["Dependency injection / initialization"]
    C --> D["AOP BeanPostProcessor inspects bean"]
    D --> E{"Matching advisor?"}
    E -->|Yes| F["Create / expose AOP proxy"]
    E -->|No| G["Expose regular bean"]
    F --> H["Consumer receives proxy from container"]
    G --> I["Consumer receives bean"]
    H --> J["Method call goes through advisor chain"]
    I --> K["Direct method call"]
~~~

The diagram simplifies internal ordering to clarify the idea: Spring manages the target and can expose a proxy to the rest of the application. In special scenarios like circular dependencies or beans created by infrastructure post-processors, exact proxy creation/exposure details can differ.

### 3.1. BeanPostProcessor and auto-proxy creator

`BeanPostProcessor` is an extension point letting infrastructure process beans during initialization. AOP infrastructure uses appropriate post-processors to locate advisors and decide whether a proxy is needed.

For configurations using `@Aspect`, a typical component is `AnnotationAwareAspectJAutoProxyCreator`. It finds advices declared with AspectJ annotation syntax and creates Spring AOP proxies for matching targets.

**Not every bean becomes a proxy.** Having `spring-boot-starter-aop` on the classpath does not mean every service is wrapped. Spring needs an advisor/pointcut matching the bean and method, or another infrastructure feature requiring a proxy.

### 3.2. Is the object passed into a constructor a proxy or a target?

Suppose:

~~~java
@RestController
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping("/orders")
    public void create() {
        orderService.submit();
    }
}
~~~

If `OrderService` is proxied by Spring AOP, the reference received by the controller via injection is normally the **proxy**. The controller does not need to create proxies manually or call a special AOP API.

Spring resolves dependencies and supplies the finally exposed bean. This is why constructor injection from the container and calling from another bean generally make advice work properly.

### 3.3. Spring AOP does not automatically apply to every object in the JVM

An object created with:

~~~java
OrderService service = new OrderService();
service.submit();
~~~

does not pass through the Spring container. It does not automatically receive a proxy/advice just because `OrderService` has `@Service` or a method has an AOP-related annotation.

Annotations are metadata. The container and infrastructure must participate for metadata to become runtime behavior.

## 4. Enabling AOP in Spring Boot

A Spring Boot application can use AspectJ-style annotations backed by **Spring AOP proxies**, without needing AspectJ compile-time weaving.

With Spring Boot 3.x, the commonly used dependency is:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-aop'
}
~~~

With Maven:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
</dependency>
~~~

The starter provides the components needed for Spring AOP and AspectJ-style pointcut parsing. When Boot's AOP auto-configuration conditions match, Spring Boot can enable AOP support automatically. In typical Boot apps that already include the starter, you do not need to add `@EnableAspectJAutoProxy` just to use `@Aspect`.

### 4.1. @EnableAspectJAutoProxy

In Spring Framework or a manually constructed context, `@Aspect` recognition can be enabled via:

~~~java
@Configuration
@EnableAspectJAutoProxy
public class AopConfiguration {
}
~~~

`@EnableAspectJAutoProxy` lets the infrastructure use `@Aspect` beans to create advisors and proxies. The annotation name includes "AspectJ" because it uses the AspectJ-style model/annotations and pointcut language; Spring AOP itself remains proxy-based and does not mean AspectJ weaving is enabled.

In Spring Boot, check existing auto-configuration before adding duplicate configuration.

### 4.2. Related properties

~~~properties
spring.aop.auto=true
spring.aop.proxy-target-class=true
~~~

In Spring Boot, AOP auto-configuration is enabled by default when classpath conditions match. Boot also typically chooses **class-based proxies** (CGLIB) by default via `spring.aop.proxy-target-class=true`.

Set:

~~~properties
spring.aop.proxy-target-class=false
~~~

to prefer JDK dynamic proxies when the target has suitable interfaces. If the target has no interface, Spring may still need a class-based proxy.

`spring.aop.auto=false` affects **Spring Boot's AOP auto-configuration**; it is not a global kill switch turning off every proxy created by other infrastructure features, such as separately configured transaction management.

Do not change proxy strategy in production solely to make a specific class castable; changing it can affect many beans and injection points.

## 5. Two primary mechanisms: JDK dynamic proxy and CGLIB

Spring AOP generally has two options for creating proxies:

| Criterion | JDK dynamic proxy | CGLIB class-based proxy |
| --- | --- | --- |
| How it works | Proxy implements target's interfaces | Proxy creates a subclass of the target class |
| Requires target interface | Usually yes | Not required |
| Runtime type | JDK-generated proxy class | Dynamically generated subclass |
| Injection by interface | Suitable | Suitable if target implements interface |
| Injection by concrete class | Can fail because JDK proxy is not a subtype of the class | Possible if class can be proxied |
| Target class is `final` | Interface proxy can still be used | Cannot subclass a final class |
| Method is `final` | Interface methods can be intercepted by JDK proxy | Cannot override final method |
| Private method | Not intercepted under Spring proxy model | Cannot override/intercept |
| Self-invocation | Bypassed | Bypassed |
| Typical Spring Framework default when interface exists | Yes | Depends on configuration |
| Common Spring Boot default | Selectable via property | Usually preferred by Boot |

### 5.1. Example of target with an interface

~~~java
public interface PaymentService {
    void pay(String orderId);
}

@Service
public class DefaultPaymentService implements PaymentService {

    @Override
    public void pay(String orderId) {
        System.out.println("Paying order " + orderId);
    }
}
~~~

With JDK proxies, callers should work through the interface:

~~~java
@Service
public class CheckoutService {

    private final PaymentService paymentService;

    public CheckoutService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void checkout(String orderId) {
        paymentService.pay(orderId);
    }
}
~~~

If you try to inject concrete class `DefaultPaymentService` while Spring exposes a JDK proxy implementing only `PaymentService`, the container may fail to provide a bean of the expected concrete type.

Interface-based design is also convenient for test doubles, swapping implementations, and reducing coupling between modules.

### 5.2. CGLIB when a class has no interface

~~~java
@Service
public class ShippingService {

    public void ship(String orderId) {
        System.out.println("Shipping order " + orderId);
    }
}
~~~

If the public `ship` method matches an advisor and the class can be subclassed, Spring can create a CGLIB-style proxy. Callers can still inject `ShippingService` because the proxy is a subtype of the class.

CGLIB does not require you to manually write a subclass. Spring generates the proxy dynamically according to its mechanism.

### 5.3. Why does Spring Boot commonly use CGLIB?

Choosing class-based proxies lets many beans without dedicated interfaces still be AOP-proxied and injected by concrete type. This is a convenient default, though it does not make every method interceptable: `final`, `private`, non-overridable methods, and self-invocation remain limitations.

In Spring Framework generally, if a target implements at least one interface and class-based proxying is not forced, JDK dynamic proxy is a common choice. Spring Boot applies its own default configuration, so distinguish **framework default** from **Boot auto-configuration default**.

### 5.4. Proxy strategy can be decided at the container level

When multiple mechanisms use auto-proxying—such as transactions, caching, and AspectJ-style AOP—Spring can consolidate auto-proxy creator settings into unified infrastructure with the stronger proxy setting taking precedence.

Do not assume enabling an annotation for one specific feature only affects that bean in isolation from other proxies. When changing `proxyTargetClass`, check beans using transactions/caching/AOP as well.

## 6. Complete example: custom annotation and timing aspect

We create a `@TimedOperation` annotation to mark methods needing timing, then create an aspect handling calls going through the proxy.

### 6.1. Create the annotation

~~~java
package com.example.demo.aop;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface TimedOperation {
}
~~~

`@Target(METHOD)` lets the annotation be attached to methods. `@Retention(RUNTIME)` keeps metadata at runtime so Spring AOP can detect it.

### 6.2. Create the @Aspect

~~~java
package com.example.demo.aop;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class TimedOperationAspect {

    @Around("@annotation(com.example.demo.aop.TimedOperation)")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long startedAt = System.nanoTime();

        try {
            return joinPoint.proceed();
        } finally {
            long elapsedNanos = System.nanoTime() - startedAt;

            System.out.printf(
                    "Method %s took %.3f ms%n",
                    joinPoint.getSignature().toShortString(),
                    elapsedNanos / 1_000_000.0
            );
        }
    }
}
~~~

Components:

- `@Aspect`: marks the class as declaring AOP logic.
- `@Component`: registers the aspect as a Spring bean via component scanning.
- `@Around(...)`: advice wrapping method calls matching the pointcut.
- `ProceedingJoinPoint`: provides invocation info and `proceed()` to continue the interceptor/target chain.
- `finally`: records duration whether the method returns a result or throws an exception.

The example prints with `System.out` for easy observation. In production, use a logging/metrics framework, limit sensitive data, and consider hot-path overhead.

### 6.3. Attach the annotation to a service

~~~java
package com.example.demo.service;

import com.example.demo.aop.TimedOperation;
import org.springframework.stereotype.Service;

@Service
public class InventoryService {

    @TimedOperation
    public int availableItems(String sku) {
        // Simulate data-reading logic.
        return sku == null ? 0 : 42;
    }
}
~~~

Controller injecting the service:

~~~java
package com.example.demo.web;

import com.example.demo.service.InventoryService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InventoryController {

    private final InventoryService inventoryService;

    public InventoryController(InventoryService inventoryService) {
        this.inventoryService = inventoryService;
    }

    @GetMapping("/inventory")
    public int inventory(@RequestParam String sku) {
        return inventoryService.availableItems(sku);
    }
}
~~~

When an HTTP request hits the controller, the controller calls the service through the Spring-injected reference. If the proxy/advisor is created properly, the aspect will time `availableItems`.

~~~mermaid
sequenceDiagram
    participant Client as HTTP client
    participant Controller as InventoryController
    participant Proxy as InventoryService proxy
    participant Aspect as TimedOperationAspect
    participant Target as InventoryService target
    Client->>Controller: GET /inventory?sku=A-1
    Controller->>Proxy: availableItems("A-1")
    Proxy->>Aspect: @Around measure()
    Aspect->>Target: joinPoint.proceed()
    Target-->>Aspect: 42
    Aspect->>Aspect: Record elapsed time
    Aspect-->>Proxy: 42
    Proxy-->>Controller: 42
    Controller-->>Client: HTTP 200 / 42
~~~

Prerequisites for this to work:

1. The project has suitable AOP infrastructure, such as `spring-boot-starter-aop`.
2. The aspect is within component scan scope or registered as a bean.
3. The service is a Spring-managed bean.
4. The public method bears the annotation and matches the pointcut.
5. The caller uses the container-injected bean, not a manually created target.
6. The call comes **from outside through the proxy**.

### 6.4. Must @Around always call proceed()?

No, and this is why `@Around` is the most powerful yet easiest to misuse. An around advice can decide not to invoke the target, invoke it once, or in special designs invoke it multiple times.

For regular business calls, call `joinPoint.proceed()` **exactly once**, then preserve the result or exception unless there is a very explicit requirement otherwise.

If `proceed()` is omitted:

~~~java
@Around("@annotation(com.example.demo.aop.TimedOperation)")
public Object invalid(ProceedingJoinPoint joinPoint) {
    // Target method does not run.
    return null;
}
~~~

The call is blocked and the business method does not execute. If the method returns a primitive or the caller cannot accept null, errors may surface elsewhere.

## 7. Join point, pointcut, advice, aspect, and advisor

AOP terms frequently appear together:

| Term | Meaning in Spring AOP |
| --- | --- |
| **Join point** | Point where advice can apply; Spring AOP focuses on Spring bean method execution |
| **Pointcut** | Expression determining which method executions are selected |
| **Advice** | Behavior running before/after/around the call |
| **Aspect** | Group of pointcuts and advice addressing a shared concern |
| **Target** | Object providing the original business logic |
| **Proxy** | Intermediary object routing calls through advice |
| **Advisor** | Combination of advice and pointcut condition at Spring infrastructure level |

Some AspectJ documentation also mentions **weaving**: attaching advice to program join points. In regular Spring AOP, behavior is provided by proxies, not by weaving target bytecode directly.

### 7.1. Spring AOP supports method execution join points

Spring AOP is proxy-based, so applicable join points are primarily **method executions on Spring beans**.

It does not provide arbitrary interception for:

- Constructor calls or object instantiation with `new`.
- Direct field reads/writes.
- Execution of code in objects not managed by Spring.
- Special join points supported by full AspectJ weaving, such as field get/set or constructor execution.

If a requirement genuinely needs to intercept field access, constructors, or objects outside the container, Spring AOP proxies may not suffice; consider AspectJ compile-time/load-time weaving or a different architecture.

### 7.2. Pointcuts using execution(...)

Example selecting all public methods in a service package:

~~~java
@Around("execution(public * com.example.demo.service.*.*(..))")
public Object observeService(ProceedingJoinPoint joinPoint)
        throws Throwable {
    return joinPoint.proceed();
}
~~~

The expression `execution(public * com.example.demo.service.*.*(..))` reads as:

- `public`: select only methods with `public` visibility.
- First `*`: any return type.
- `com.example.demo.service.*`: matching classes in the stated package.
- `.*`: any method name.
- `(..)`: accepts any number and types of parameters.

To include subpackages, use a pattern with `..`, for example:

~~~java
@Pointcut("execution(* com.example.demo.service..*(..))")
public void applicationServiceOperations() {}
~~~

Broad expressions can intercept many unexpected methods. Keep the scope narrow enough to avoid logging sensitive data or adding application-wide overhead.

### 7.3. Pointcuts using @annotation

~~~java
@Around("@annotation(com.example.demo.aop.TimedOperation)")
public Object measure(ProceedingJoinPoint joinPoint)
        throws Throwable {
    return joinPoint.proceed();
}
~~~

`@annotation` limits advice to methods carrying the corresponding annotation within pointcut resolution rules. This is very useful when selecting only explicit methods.

Placing the annotation on **concrete implementation methods** is usually the most predictable choice, especially when switching between JDK interface proxies and CGLIB proxies. Do not assume annotations on interface methods, implementation methods, and inherited methods resolve identically across every annotation-driven mechanism.

### 7.4. Reusing named pointcuts

~~~java
@Aspect
@Component
public class ServiceAuditAspect {

    @Pointcut("within(com.example.demo.service..*)")
    public void inServiceLayer() {}

    @Pointcut("execution(public * *(..))")
    public void publicMethod() {}

    @Before("inServiceLayer() && publicMethod()")
    public void beforeServiceMethod() {
        // Shared audit logic.
    }
}
~~~

`@Pointcut` separates method selection conditions from advice. Pointcuts can be combined with `&&`, `||`, and `!` using supported syntax.

Avoid putting frequently changing business logic into overly complex pointcut expressions. When the selection scope genuinely carries business meaning, a custom annotation is usually more readable and stable.

## 8. Common advice types

AspectJ-style advice in Spring includes:

| Annotation | Timing | Key points to remember |
| --- | --- | --- |
| `@Before` | Before the method executes | Cannot directly change the return value |
| `@AfterReturning` | When the method returns normally | Can read the result, cannot replace the returned object by reassigning the parameter |
| `@AfterThrowing` | When the method throws a matching exception | Suitable for error auditing, does not automatically handle all errors |
| `@After` | After the method whether it succeeds or throws an exception | Similar to finally semantics |
| `@Around` | Wraps the invocation | Actively calls `proceed()` and can alter results/exceptions |

`@Before` example:

~~~java
@Aspect
@Component
public class LoggingAspect {

    @Before("execution(* com.example.demo.service..*(..))")
    public void beforeCall(JoinPoint joinPoint) {
        System.out.println(
                "Calling " + joinPoint.getSignature().toShortString()
        );
    }
}
~~~

`@AfterReturning` example:

~~~java
@AfterReturning(
        pointcut = "execution(* com.example.demo.service..*(..))",
        returning = "result"
)
public void afterSuccess(Object result) {
    // Observe result; do not log sensitive content.
}
~~~

`@AfterThrowing` example:

~~~java
@AfterThrowing(
        pointcut = "execution(* com.example.demo.service..*(..))",
        throwing = "error"
)
public void afterFailure(Throwable error) {
    // Record error metrics or appropriate audit.
}
~~~

If you only need to record a milestone before or after a call, a specialized advice may be clearer than `@Around`. If you need total timing, result modification, retry, or deciding whether to proceed, `@Around` is better suited, though side effects require caution.

### 8.1. @AfterReturning and @AfterThrowing do not replace finally

`@AfterReturning` runs only when the invocation returns normally. `@AfterThrowing` handles the exception path. If you always need invocation-scoped cleanup, `@After` or `try/finally` inside `@Around` is more appropriate.

For instance, a timing measurement uses `finally` so duration is logged even if the target throws an error.

### 8.2. Do not log full args and return values by default

`JoinPoint.getArgs()` can contain passwords, access tokens, account numbers, personal data, or huge objects. Calling `toString()` on all arguments for every method can both leak data and cause errors/overhead.

Record only permitted metadata such as operation name, duration, safe correlation IDs, and outcome classification. For sensitive info, apply appropriate masking/redaction rules.

## 9. Multiple advices and the interceptor chain

One method can match multiple advisors: logging, timing, caching, transactions, validation, or authorization.

Diagram:

~~~mermaid
flowchart LR
    A["Caller"] --> P["Proxy"]
    P --> X["Advice A"]
    X --> Y["Advice B"]
    Y --> Z["Advice C"]
    Z --> T["Target method"]
    T --> Z
    Z --> Y
    Y --> X
    X --> P
~~~

Calls can be wrapped in nested layers. If an around advice does not call `proceed()`, inner interceptors and the target may not run.

### 9.1. @Order controls aspect ordering

~~~java
@Aspect
@Component
@Order(10)
public class OuterAspect {
    // ...
}

@Aspect
@Component
@Order(20)
public class InnerAspect {
    // ...
}
~~~

For aspects ordered by Spring, a **smaller order number has higher precedence**. Higher-precedence aspects normally run earlier on entry and finish later on exit in an around chain.

Within a single aspect having multiple advices on the same join point, exact ordering depends on advice type and framework rules. Do not rely on source method ordering as an ordering contract.

### 9.2. @Order is not bean initialization order

`@Order` on an aspect relates to precedence within the advice chain. It does not force one service to be initialized before another across the entire container. If you need initialization/destruction ordering dependencies, use constructor injection or `@DependsOn` when only ordering exists.

### 9.3. Transactions and caching appearing together

If a method is marked with both `@Transactional` and `@Cacheable`, both mechanisms can use proxy-based interceptors. Advisor ordering can affect:

- Whether the transaction starts before or after cache lookup occurs.
- Whether a cache hit enters the transaction interceptor.
- Under what conditions the result is cached.

Do not guess order merely from annotation order in source code. When semantics depend on ordering, design and test transaction/cache behavior explicitly.

## 10. The most important limitation: self-invocation

**Self-invocation** is when a method on a target calls another method on the same target via `this` or a direct call without going through the proxy.

Example:

~~~java
@Service
public class CheckoutService {

    public void checkout(String orderId) {
        validate(orderId);
        charge(orderId); // Internal call on the same object.
    }

    @TimedOperation
    public void charge(String orderId) {
        // Charging logic.
    }

    private void validate(String orderId) {
        if (orderId == null || orderId.isBlank()) {
            throw new IllegalArgumentException("orderId is required");
        }
    }
}
~~~

When a controller calls `checkoutService.checkout(...)` through the proxy, the proxy can intercept `checkout` if a matching pointcut exists. However, the call to `charge(...)` **from inside the target** does not re-enter the proxy.

Therefore, `@TimedOperation` on `charge` may not trigger along the call path from `checkout`, even though another bean calling `checkoutService.charge(...)` directly would run the advice.

~~~mermaid
flowchart TD
    A["Controller"] --> B["CheckoutService proxy"]
    B --> C["Target.checkout()"]
    C --> D["this.charge()"]
    D --> E["Target.charge() directly"]
    F["Another bean"] --> B2["CheckoutService proxy"]
    B2 --> G["@TimedOperation advice"]
    G --> H["Target.charge()"]
~~~

The difference is not in the annotation, but in **the call path**.

### 10.1. Self-invocation affects @Transactional too

Example:

~~~java
@Service
public class OrderApplicationService {

    public void processOrder(String orderId) {
        saveOrder(orderId); // Internal call.
    }

    @Transactional
    public void saveOrder(String orderId) {
        // Write data needing a transaction.
    }
}
~~~

With transaction management in proxy mode, calling `saveOrder` from `processOrder` inside the same target **does not trigger the transaction interceptor** for `saveOrder`.

If `processOrder` was already invoked inside another transaction, the inner logic may still run under that existing transaction; however, `saveOrder`'s own `@Transactional` annotation is not applied *independently* via that internal call. This is a critical distinction when debugging propagation and rollback.

For `@Cacheable`, `@Async`, and other proxy-based features, self-invocation must likewise be evaluated against their respective mechanisms.

### 10.2. Recommended approach: extract responsibilities into another bean

~~~java
@Service
public class PaymentExecutor {

    @Transactional
    public void charge(String orderId) {
        // Perform operation inside a transaction.
    }
}

@Service
public class CheckoutService {

    private final PaymentExecutor executor;

    public CheckoutService(PaymentExecutor executor) {
        this.executor = executor;
    }

    public void checkout(String orderId) {
        executor.charge(orderId); // Call through Spring-injected bean.
    }
}
~~~

`CheckoutService` receives `PaymentExecutor` via constructor injection. When Spring creates a proxy for `PaymentExecutor`, calls from checkout go through the proxy, allowing advisors to run properly.

Advantages:

- Clear transaction or cross-cutting concern boundaries.
- Dependencies are explicit through constructors.
- Easy to write unit tests using test doubles.
- No reliance on internal Spring AOP APIs.
- Aligns with separating application orchestration from specific operations.

### 10.3. Self-injection and AopContext.currentProxy()

Workarounds exist such as injecting the bean's own proxy or calling:

~~~java
((CheckoutService) AopContext.currentProxy()).charge(orderId);
~~~

However, this works only when proxy exposure is properly enabled and the current call is already going through a proxy. It can also fail to cast with JDK dynamic proxies and tightly couples domain code to Spring AOP.

`AopContext.currentProxy()` requires `exposeProxy = true` on the proxy infrastructure, adding coupling and overhead. Do not treat this as a default design. **Refactoring into another bean or adjusting public method boundaries** is usually better.

### 10.4. How does AspectJ weaving differ on self-invocation?

AspectJ compile-time or load-time weaving can intervene at join points directly in bytecode and is not constrained by the exact self-invocation rules of Spring proxy AOP.

That **does not mean** placing `@Aspect` automatically enables weaving. Weaving configuration, build pipelines, and class loading must be configured separately. In a standard Spring Boot app using `spring-boot-starter-aop`, you are using **proxy-based Spring AOP**.

## 11. Which methods cannot be intercepted via Spring proxies?

A proxy is not a tool that "intercepts every line of code." Interceptability depends on proxy strategy and method kind.

### 11.1. Private methods

~~~java
@Service
public class ReportService {

    public void generate() {
        calculateInternal();
    }

    @TimedOperation
    private void calculateInternal() {
        // Not a method interceptable via a Spring AOP proxy.
    }
}
~~~

Private methods are not exposed as externally callable methods via a proxy. CGLIB subclasses also cannot override private methods. AOP annotations on private methods do not cause internal calls to be intercepted.

If a task needs cross-cutting behavior, place it on a **public operation boundary** callable by another caller through a proxy or extract it into a separate bean.

### 11.2. Final methods with CGLIB

~~~java
@Service
public class FinalMethodService {

    @TimedOperation
    public final void execute() {
        // CGLIB cannot override this final method.
    }
}
~~~

Class-based proxies rely on subclass method overriding to intercept calls. Because a `final` method cannot be overridden, it cannot be CGLIB-advised that way.

If using a JDK interface proxy, a method called via the interface can still pass through the invocation handler even when the implementation method is `final`. Thus distinguish **class-based proxy** limits from **interface-based proxy** behavior.

### 11.3. Final classes

~~~java
@Service
public final class FinalReportService {

    @TimedOperation
    public void execute() {
        // CGLIB cannot create a subclass of a final class.
    }
}
~~~

CGLIB cannot subclass a class declared `final`. If that class implements a suitable interface, JDK dynamic proxy may be an option. In Kotlin applications, classes/methods are final by default; Spring open-class compiler plugins typically need to be configured if class-based proxies are desired.

Do not rush to remove `final` from every class. Consider whether the class truly needs a Spring proxy or if the concern belongs on another API or via an interface.

### 11.4. Constructors and static methods

Spring AOP proxies intercept method executions on beans called through a proxy, **not constructor invocations**. A method pointcut annotation does not turn `new Target()` into an intercepted call.

Static methods also do not go through instance proxy dispatch the way Spring AOP needs. Do not rely on Spring `@Aspect` to advise static methods.

### 11.5. Public, protected, and package-private methods

With **JDK dynamic proxies**, interface-based invocations primarily rely on public methods exposed by interfaces. Methods absent from the interface are not naturally part of the API called through a JDK proxy.

With **class-based proxies**, intercepting non-public methods depends on Java override rules and Spring infrastructure. In particular, certain Spring Framework 6 features can apply to `protected` and package-private methods when using class-based proxies. However, **private and final methods still cannot be advised via CGLIB**.

To write predictable code across proxy strategies, design cross-cutting boundaries as **public service methods** and invoke them through Spring-injected bean references.

## 12. @PostConstruct, constructors, and when the proxy is ready

Another pitfall is calling an aspect-advised method from the same bean's constructor or `@PostConstruct`.

~~~java
@Service
public class StartupService {

    public StartupService() {
        // Do not call AOP-dependent methods from constructors.
    }

    @PostConstruct
    public void init() {
        doWork(); // Internal call, does not go through AOP proxy.
    }

    @TimedOperation
    public void doWork() {
        // Logic needing advice.
    }
}
~~~

At constructor time, the object is still being instantiated. `@PostConstruct` is an initialization callback during bean construction; it is not an external call through an injected proxy reference.

Therefore do not rely on `@Transactional`, `@Async`, or custom aspects when calling methods on the same object inside `@PostConstruct`.

### 12.1. What to do when business logic must run after startup?

One option is using `ApplicationRunner` or `CommandLineRunner` in another bean, injecting the service to invoke:

~~~java
@Component
public class StartupRunner implements ApplicationRunner {

    private final StartupService service;

    public StartupRunner(StartupService service) {
        this.service = service;
    }

    @Override
    public void run(ApplicationArguments args) {
        service.doWork(); // External call through an injected bean.
    }
}
~~~

When the runner executes, the context has already refreshed during normal startup. If `StartupService` is AOP-proxied, the call from the runner has the opportunity to pass through the proxy.

If work should only run after all runners complete, consider `ApplicationReadyEvent` or an appropriate lifecycle event. Do not use early startup events before context refresh to fetch services that are not ready yet.

## 13. How do @Transactional, @Cacheable, and @Async relate to proxies?

Spring AOP is often introduced via `@Aspect`, yet proxy infrastructure also powers many Spring features.

### 13.1. @Transactional

~~~java
@Service
public class TransferService {

    @Transactional
    public void transfer(String from, String to, long amount) {
        // Perform multiple data operations in a transaction.
    }
}
~~~

When transaction management is enabled in proxy mode, the transaction interceptor creates transaction boundaries around calls to matching methods **through the proxy**.

The conditions remain that the method is invoked through a Spring-managed bean, the advisor applies properly, and a suitable transaction manager exists. Adding the annotation does not automatically create a database transaction without configured transaction infrastructure.

### 13.2. @Cacheable

~~~java
@Service
public class CatalogService {

    @Cacheable("products")
    public Product findProduct(String id) {
        return repository.findById(id).orElseThrow();
    }
}
~~~

When caching is enabled and appropriate cache infrastructure exists, the interceptor can return cached data without calling the target method.

This clearly illustrates that advice **does not necessarily invoke the target**: on a cache hit, business logic can be skipped per the caching contract.

Self-invocation still needs to be checked with proxy-based caching.

### 13.3. @Async

~~~java
@Service
public class NotificationService {

    @Async
    public CompletableFuture<Void> sendNotification(String recipient) {
        // Run work on an executor per @Async configuration.
        return CompletableFuture.completedFuture(null);
    }
}
~~~

In default proxy mode for asynchronous method execution, only calls through the proxy are dispatched to the asynchronous interceptor/executor. An internal call to an `@Async` method on the same target can unexpectedly execute synchronously.

Proper async execution must be enabled/configured, such as `@EnableAsync`, and exceptions/return types handled per contract. Spring AOP is part of the mechanism; the annotation alone is insufficient for background behavior.

### 13.4. Not everything "annotation-driven" uses the same proxy

Spring MVC request mapping, Jakarta Bean Validation, event listeners, or serialization also rely on annotation metadata, yet not all of them go through **the exact same kind of AOP proxy**.

Do not assume every Java annotation suffers from self-invocation identically to `@Transactional`. Understand the execution mechanism of each specific feature.

## 14. Differences between Spring AOP and AspectJ weaving

The two terms are often mentioned side by side, though their scopes differ.

| Criterion | Spring AOP | AspectJ weaving |
| --- | --- | --- |
| Primary mechanism | Proxies inside the Spring container | Injects advice via compile-time or load-time weaving |
| Object scope | Beans/calls passing through Spring proxies | Can also apply to non-Spring-managed objects |
| Join points | Bean method execution | Broader, including field access and constructor-related join points |
| Self-invocation | Bypasses proxy | Can be advised via weaving |
| Setup requirements | AOP infrastructure / advisors | Weaver and separate configuration tools |
| Uses @AspectJ syntax | Yes | Yes |
| IoC container integration | Very direct | Can combine with Spring but not limited to proxies |

### 14.1. @Aspect does not mean weaving

Code:

~~~java
@Aspect
@Component
public class SecurityAuditAspect {
    // Advice...
}
~~~

merely indicates the class declares an aspect in annotation syntax. With Spring AOP, the aspect enters proxy advice chains; business classes do not necessarily have their bytecode woven.

To use AspectJ compile-time weaving or load-time weaving, a project needs separate configuration. Do not switch to weaving merely to patch a self-invocation that could be solved with cleaner service design.

### 14.2. When is Spring AOP enough?

Spring AOP fits many enterprise use cases:

- Service-layer transaction boundaries.
- Caching method calls.
- Method-level metrics/logging.
- Policies applying to public service methods.
- Certain method-boundary security mechanisms.
- Asynchronous interception per Spring's contract.

If you do not need field/constructor join points or objects outside the container, proxy-based AOP is usually simpler to integrate in Spring Boot.

## 15. this and target in pointcuts

Spring AOP has two easily confused concepts:

- **Proxy object**: the reference the caller invokes.
- **Target object**: the object providing the underlying business implementation.

In Spring AOP, the pointcut expression `this(Type)` checks the type of the **proxy**, whereas `target(Type)` checks the type of the **target**.

With a JDK dynamic proxy implementing an interface:

~~~java
public interface ReportPort {
    String createReport();
}
~~~

the proxy may be an instance of a JDK-generated class, not a subtype of `DefaultReportService`. Thus `this(DefaultReportService)` may fail to match while `target(DefaultReportService)` matches, depending on target and type configuration.

With a CGLIB class-based proxy, the proxy is a subtype of the target class, so both may match more similarly.

This is why when writing advanced pointcuts, you must know which proxy strategy is active. Most applications avoid depending on this distinction by writing clear method/annotation/service-layer pointcuts.

## 16. Proxies and method return types

Around advice must uphold the called method's contract. For example, a method returning `int` or `String` should not have an around advice return `null` or an incompatible type.

~~~java
@Around("@annotation(com.example.demo.aop.TimedOperation)")
public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
    return joinPoint.proceed();
}
~~~

The snippet above preserves the target's result. If transforming results is required, understand actual return types, generics, and exceptions.

### 16.1. Reactive publishers and async return values

A method:

~~~java
public Mono<Order> findOrder(String id) {
    return repository.findById(id);
}
~~~

can return a `Mono` very quickly, while the database call inside the pipeline executes only upon subscription. A timing aspect wrapping `joinPoint.proceed()` may measure only **publisher creation time**, not total reactive pipeline completion time.

Likewise, a method returning `CompletableFuture` can return the future before work actually finishes. If metrics need total work duration, instrument publisher/future completion via the appropriate abstraction rather than only around method invocation.

### 16.2. Thread-local and context propagation

Many aspects use thread-locals to hold correlation IDs or transaction context. With `@Async`, task executors, or reactive pipelines, the executing thread can change.

Do not assume thread-locals propagate across those boundaries. If an aspect needs cross-thread context, use the framework/runtime context propagation mechanism suited to that workload.

## 17. Runtime check: is a bean an AOP proxy?

Spring provides utilities in `org.springframework.aop.support.AopUtils`:

~~~java
import org.springframework.aop.support.AopUtils;

Object bean = applicationContext.getBean("inventoryService");

boolean isProxy = AopUtils.isAopProxy(bean);
boolean isJdkProxy = AopUtils.isJdkDynamicProxy(bean);
boolean isCglibProxy = AopUtils.isCglibProxy(bean);
~~~

These methods are useful when debugging:

- `isAopProxy(bean)`: whether the bean is exposed by Spring AOP as a proxy.
- `isJdkDynamicProxy(bean)`: whether it is a proxy based on JDK dynamic proxies.
- `isCglibProxy(bean)`: whether it is a class-based CGLIB proxy.

Do not make business logic depend on the output of these utilities. They are primarily tools for inspecting infrastructure configuration and testing.

### 17.1. Bean class may be a generated class

~~~java
Object bean = applicationContext.getBean(InventoryService.class);

System.out.println(bean.getClass().getName());
~~~

The class name may contain generated proxy markers like `$$SpringCGLIB$$`, though internal naming is not a stable API contract. To check proxies meaningfully, use `AopUtils`.

### 17.2. @Transactional beans may not behave like production in every test

A plain Java test:

~~~java
InventoryService service = new InventoryService();
~~~

does not create a Spring AOP proxy. Such a unit test checks class logic, not advice.

To confirm AOP actually works, you need a context with appropriate advisors/AOP infrastructure. Depending on the goal, use a minimal test context or `@SpringBootTest`.

### 17.3. Do not cast a JDK proxy to the implementation

Wrong under JDK proxy configuration:

~~~java
DefaultPaymentService service =
        (DefaultPaymentService) context.getBean(PaymentService.class);
~~~

If the bean is a JDK proxy implementing `PaymentService`, it may not be an instance of `DefaultPaymentService`. Use the interface instead:

~~~java
PaymentService service = context.getBean(PaymentService.class);
~~~

If concrete-class injection is genuinely required, check class-based proxy configuration; do not alter dependency design just to support a cast in business code.

## 18. Testing an aspect with a minimal Spring context

You can use `AnnotationConfigApplicationContext` to explicitly enable AOP and verify calls actually go through a proxy. The example below uses classes in the same test package to clarify the mechanics.

### 18.1. Bean to be intercepted

~~~java
package com.example.aoptest;

import org.springframework.stereotype.Service;

@Service
public class GreetingService {

    @Tracked
    public String greet(String name) {
        return "Hello " + name;
    }
}
~~~

Annotation:

~~~java
package com.example.aoptest;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Tracked {}
~~~

### 18.2. Aspect counting invocations

~~~java
package com.example.aoptest;

import java.util.concurrent.atomic.AtomicInteger;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class CountingAspect {

    private final AtomicInteger count = new AtomicInteger();

    @Before("@annotation(com.example.aoptest.Tracked)")
    public void increment() {
        count.incrementAndGet();
    }

    public int invocations() {
        return count.get();
    }
}
~~~

### 18.3. Test context configuration

~~~java
package com.example.aoptest;

import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;
import org.springframework.context.annotation.Import;

@Configuration(proxyBeanMethods = false)
@EnableAspectJAutoProxy(proxyTargetClass = true)
@Import({
        GreetingService.class,
        CountingAspect.class
})
public class TestAopConfiguration {}
~~~

Here `@EnableAspectJAutoProxy` is declared explicitly because the test uses a minimal Spring Framework context without relying on Spring Boot AOP auto-configuration.

### 18.4. JUnit 5 checking proxy and advice

~~~java
package com.example.aoptest;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

class GreetingAopTest {

    @Test
    void adviceRunsThroughContainerProxy() {
        try (var context =
                new AnnotationConfigApplicationContext(
                        TestAopConfiguration.class
                )) {

            GreetingService service =
                    context.getBean(GreetingService.class);
            CountingAspect aspect =
                    context.getBean(CountingAspect.class);

            assertTrue(AopUtils.isAopProxy(service));

            assertEquals("Hello Linh", service.greet("Linh"));
            assertEquals(1, aspect.invocations());
        }
    }
}
~~~

This test proves:

1. `GreetingService` is a Spring-managed bean.
2. The context enabled AOP and detected the aspect.
3. The bean is exposed as a proxy.
4. Calling `greet` through the proxy triggers the advice.

It also illustrates the difference from a unit test creating `new GreetingService()`: directly created objects do not have Spring proxies.

### 18.5. Testing self-invocation

You can add to `GreetingService`:

~~~java
public String greetTwice(String name) {
    return greet(name) + " and " + greet(name);
}
~~~

If only `greet` is marked `@Tracked` and the caller invokes `service.greetTwice("Linh")`, both `greet` calls originate **inside the target**, bypassing the proxy, so the counter does not increment from `greet`'s annotation along the self-invocation path.

If the caller invokes `service.greet("Linh")` directly twice through the proxy, the counter increments twice. This is a short yet effective test for understanding proxy boundaries.

## 19. Why do aspects "not run" in real applications?

When a method has an annotation yet no advice executes, investigate from the outside in.

| Symptom | Common cause | Resolution |
| --- | --- | --- |
| No proxy visible | AOP infrastructure/aspect not registered or no matching advisor | Check dependencies, auto-config, component scan, pointcut |
| Class has `@Aspect` but does not run | Aspect is not a Spring bean | Register `@Component` or `@Bean` |
| Method called from controller runs advice, internal call does not | Self-invocation | Extract to another bean and inject via constructor |
| Annotation on private method has no effect | Private methods cannot be intercepted by proxies | Place concern on a public boundary |
| CGLIB proxy does not advise final method | Cannot override final methods | Redesign method/class or use interface proxy if suitable |
| Final class fails proxying | CGLIB cannot subclass final classes | Check proxy strategy and class design |
| Instantiated with `new` has no advice | Bypasses container | Use Spring-managed bean |
| Advice does not run in `@PostConstruct` | Internal call before bean is ready via proxy | Use caller bean/runner after refresh |
| Bean interface injects, concrete class fails | JDK proxy implements only interfaces | Inject by interface or check class-based proxy |
| Advice runs but does not measure reactive duration | Measuring `Mono` creation instead of completion | Instrument publisher completion |
| Advice order differs from expectation | Advisor precedence/order | Check `@Order` and advisor ordering |
| `@Async` is not actually async | Async support not enabled or call bypasses proxy | Check `@EnableAsync` and call path |
| `@Transactional` does not roll back as expected | Bypassed proxy, exception semantics, or transaction manager | Verify actual transaction boundaries |
| Test sees no aspect | Test creates target directly or context lacks AOP config | Use context with advisors/auto-configuration |

### 19.1. Six-question diagnostic checklist

1. **Is this a Spring bean?** Check that it was created by the container, not `new`.
2. **Are the aspect/advisors registered?** Check the AOP starter, `@Aspect`, `@Component`, and scan scope.
3. **Is the bean actually a proxy?** Use `AopUtils.isAopProxy(...)`.
4. **Does the pointcut match the method?** Check package, signature, annotation, and visibility.
5. **Does the caller go through the proxy?** Check self-invocation, constructors, and `@PostConstruct`.
6. **Is the proxy strategy compatible?** Check interfaces, final classes/methods, and injection types.

Only after that inspect exception behavior, ordering, specific transaction managers, or async executors. Avoid randomly tweaking `@Order` or `proxyTargetClass` before knowing whether calls pass through the proxy.

### 19.2. Check infrastructure logs when needed

In development environments, you can enable appropriate log levels for Spring AOP and auto-configuration packages to observe proxy creation/advisor registration.

~~~yaml
logging:
  level:
    org.springframework.aop: DEBUG
~~~

Specific log levels and output depend on the Spring version. Do not rely on fixed internal log strings as test contracts, and avoid leaving overly broad DEBUG logging in production if it generates high log volume.

## 20. AOP proxies and boundaries in application design

Spring AOP is most effective when applied at business-meaningful boundaries:

~~~text
HTTP Controller
       |
       v
Application Service proxy   <-- transaction / metric / authorization advice
       |
       v
Application Service target
       |
       v
Repository / Gateway
~~~

A typical architecture has:

- Controllers handling requests, input validation, and HTTP protocol details.
- Application services defining operation boundaries.
- Repositories or gateways working with databases/external systems.
- Aspects/advisors handling cross-cutting logic at suitable operation boundaries.

### 20.1. Do not turn every method into an advice point

If aspects intercept every getter, setter, utility method, and mapper, the system becomes hard to debug and incurs unnecessary overhead.

Choose meaningful cut points such as:

- Public methods of application services.
- Methods bearing purpose-built annotations.
- Operations with explicit transaction/cache/authorization contracts.

Do not use AOP to hide dependencies or replace component design.

### 20.2. Do not replace all control flow with AOP

AOP fits logic spanning multiple places that can be expressed by a consistent rule. For business rules requiring branching, domain state decisions, or coordinating multiple tasks, explicit service code is usually easier to understand than aspects.

For example, checking "whether an order can be shipped" is a business rule belonging in domain/application logic; measuring elapsed time of service calls is a cross-cutting concern suited to AOP abstraction.

### 20.3. Avoid overly broad cut points hurting performance

Every call through a proxy and advice chain carries a cost. Often this is not a major bottleneck compared to database/network calls, but pointcuts hitting millions of tiny calls can create noticeable overhead.

If measuring performance, measure and choose metrics at the right granularity. You do not need to attach aspects to every internal method on an object.

### 20.4. AOP does not replace security at every layer

A method security advisor protects methods called through a proxy with proper security infrastructure. However, it does not replace filter chains, input validation, or securing other access paths.

When security relies on proxies, identify where boundaries are invoked from and whether internal paths bypass interception. Better yet, organize clear security boundaries, test with real contexts, and avoid relying on implicit side effects.

## 21. Distinguishing AOP proxies from other proxies in Spring

Not every object with "proxy" in its name is a Spring AOP proxy with identical semantics.

### 21.1. Scoped proxies

For example, injecting a request-scoped bean into a singleton. Spring can use a proxy to defer resolving the target to the current request. This is a proxy aimed at **scope management**, not necessarily aspect logging/transactions.

Scoped proxies and AOP advisors can work together, but treat them as separate abstraction layers.

### 21.2. @Configuration class enhancement

`@Configuration(proxyBeanMethods = true)` can use class enhancement to preserve semantics when one `@Bean` method calls another `@Bean` method inside a configuration class.

This mechanism can use subclassing, yet should not be confused with Spring AOP aspect proxies. `proxyBeanMethods` governs Java configuration semantics, not an on/off switch for service `@Aspect`s.

### 21.3. HTTP client proxies or repository proxies

Spring Data repositories can be created as proxies implementing repository APIs; declarative HTTP clients can expose interface proxies calling remote APIs. These are not necessarily the same kind of proxy created by `AnnotationAwareAspectJAutoProxyCreator`.

When debugging, identify **what the proxy is for**, rather than looking at a generated class name and concluding it is AspectJ-style AOP.

## 22. Questions to test conceptual understanding

### Question 1: Has @Aspect but lacks spring-boot-starter-aop

Does a class with `@Aspect` and `@Component` guarantee advice runs?

**Not necessarily.** AOP infrastructure and appropriate dependencies are required for Spring to recognize the aspect and create advisors/proxies. Other features may transitively pull AOP support onto the classpath, but do not rely on unclear transitive side effects.

### Question 2: Method has @Transactional but is called from the same class

Does the transaction interceptor run?

In proxy mode, internal calls do not pass through the proxy, so the called method's annotation **is not applied through that call**. If a transaction already exists from an outer operation, the code may run inside that existing transaction; distinguish an existing transaction from newly triggered advice.

### Question 3: Service has no interface

Can it be AOP-proxied?

Yes. Spring can use a class-based proxy with CGLIB, provided the class/methods can be subclassed/overridden and infrastructure is configured appropriately.

### Question 4: Method is final

Can it be advised?

With CGLIB class-based proxies, final methods cannot be overridden and therefore cannot be intercepted by that mechanism. With JDK interface proxies, invocations of methods exposed on the interface can pass through the proxy; consider the actual proxy strategy.

### Question 5: Method returns Mono

Does an `@Around` measuring elapsed time capture the entire reactive request?

Not necessarily. Advice timing the method call may finish when the `Mono` is returned, before the pipeline executes and completes. To measure completion, instrument the publisher lifecycle appropriately.

### Question 6: Does @Order replace @DependsOn?

No. `@Order` on aspects adjusts advice precedence; `@DependsOn` relates to bean initialization/destruction ordering dependencies.

### Question 7: Does new Service() run advice?

Not automatically. Objects created with `new` are not Spring AOP proxies. If AOP logic is needed, use a container-exposed bean or consider another architecture.

## 24. Key takeaways

**Spring AOP in typical Spring Boot applications relies on proxies created and exposed by the container to consumers.** Proxies receive external calls, apply matching interceptors/advices, and invoke targets. It does not weave every class in the JVM and does not intercept objects instantiated outside the container.

The two primary proxy strategies are **JDK dynamic proxies** for interface-based invocation and **CGLIB** for class-based proxies. Spring Boot typically prefers class-based proxies by default, though proxy strategy can be changed. CGLIB cannot override final/private methods or subclass final classes; JDK proxies are not automatically compatible with concrete implementation class injection.

The most important limitation is **self-invocation**: a target method calling another method on itself does not re-enter the proxy. Consequently `@Transactional`, `@Cacheable`, `@Async`, or custom `@Aspect`s may have no effect on internal calls. The clearest design places operation boundaries on public methods of separate beans and calls them via Spring-injected dependencies.

When advice does not run, check in order: is the bean Spring-managed, is AOP infrastructure enabled, does the pointcut match, is the bean a proxy, does the call pass through the proxy, and is the proxy strategy compatible with the method. Understanding these points helps you use AOP to separate cross-cutting concerns controllably, rather than relying on annotations as invisible "magic."
