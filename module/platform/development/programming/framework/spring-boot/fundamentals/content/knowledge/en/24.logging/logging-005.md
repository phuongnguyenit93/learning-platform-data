# logging.level by Specific Package or Logger

When developing a Spring Boot application, you often want to see more details in one specific area without flooding the entire console with logs. For example, when investigating a payment failure, you want `DEBUG` lines from package `com.example.payment` while keeping Spring Framework, Hibernate, and remaining services at `INFO`. Or you only want to enable `TRACE` for a single logger while tracking down a hard-to-reproduce processing branch.

Spring Boot allows adjusting this through the **`logging.level.*`** configuration group. You can set log levels for:

- **The root logger**: general default for loggers without a more specific configuration.
- **A package or logger namespace**: e.g., `logging.level.com.example.payment=DEBUG`.
- **A fully-named logger**: e.g., `logging.level.com.example.payment.PaymentService=TRACE`.
- **A logging group**: a collection of multiple loggers or packages controlled under one shared name.

What matters is not only the YAML/properties syntax, but also **how loggers are named, how effective levels are inherited down the hierarchy, and which loggers a given configuration actually affects**.

This lesson uses Spring Boot 3.x, Java, and the common default SLF4J/Logback setup; when an application uses Log4j2 or another backend, backend-specific configuration details may differ, though logger naming and log level concepts remain useful.

## 1. Why scope logging by area?

Consider a commerce application with modules:

~~~text
com.example.shop
├── order
│   ├── OrderService
│   └── OrderController
├── payment
│   ├── PaymentService
│   ├── PaymentGatewayClient
│   └── PaymentRetryScheduler
└── inventory
    ├── InventoryService
    └── StockRepository
~~~

Every service can emit logs, yet at any moment you only need to observe one area:

- Investigating a payment gateway timeout: increase logs for `com.example.shop.payment`.
- Investigating a specific issue inside `PaymentGatewayClient`: raise the level for that class's logger.
- Wanting the whole system to emit only warnings/errors: set root to `WARN`.
- Wanting to see SQL generated by Hibernate: adjust Hibernate's logger rather than enabling DEBUG for the whole application.
- Wanting detailed logs in dev while keeping production concise: use profile-based configuration.

If you only set:

~~~properties
logging.level.root=DEBUG
~~~

many libraries will start emitting DEBUG logs, burying the relevant data in thousands of log lines. Configuring by specific package/logger **narrows the scope**, lowers I/O overhead, and curbs unnecessary logs.

However, a configuration only affects loggers **with that exact name or under that namespace**. Spring Boot does not scan classes and infer levels from source directories; it uses the *logger name* that code actually passes to the logging API.

## 2. Path of a log message

Applications typically log via SLF4J:

~~~java
package com.example.shop.payment;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    private static final Logger log =
            LoggerFactory.getLogger(PaymentService.class);

    public void pay(String orderId) {
        log.debug("Starting payment for orderId={}", orderId);
        log.info("Payment request accepted for orderId={}", orderId);
    }
}
~~~

`LoggerFactory.getLogger(PaymentService.class)` creates or retrieves a logger named after the class, usually:

~~~text
com.example.shop.payment.PaymentService
~~~

When code calls `log.debug(...)`, the logging backend checks whether the message is permitted based on the logger's **effective log level** before formatting and outputting it.

~~~mermaid
flowchart TD
    A["PaymentService calls log.debug(...)"] --> B["Logger name: com.example.shop.payment.PaymentService"]
    B --> C["Find configured/effective level"]
    C --> D{"Is DEBUG enabled?"}
    D -->|No| E["Discard log event"]
    D -->|Yes| F["Create log event"]
    F --> G["Appender / encoder / output"]
    G --> H["Console, file, or log pipeline"]
~~~

`logging.level.*` primarily controls the **log emission threshold per logger name**. It does not itself decide which file logs go to, how they are formatted, whether JSON is used, or how long logs are retained. Those responsibilities belong to appenders, encoders, logging patterns, and backend configuration.

## 3. Log levels and priority order

Common levels from most verbose to least verbose:

| Level | Meaning | Scenario |
| --- | --- | --- |
| `TRACE` | Very detailed; internal processing steps | Investigating tricky execution flows |
| `DEBUG` | Diagnostic information for developers | States, branch choices, safe parameters |
| `INFO` | Normal operational events | Startup, significant business outcomes |
| `WARN` | Anomaly where the system can still recover | Retries, fallbacks, notable config notices |
| `ERROR` | Failure requiring attention | Unable to complete operation |
| `OFF` | Emits no logs for that logger under level config | Mainly used when intentionally silencing |

A logger with **effective level = INFO** normally accepts `INFO`, `WARN`, and `ERROR` events, while ignoring `DEBUG` and `TRACE`.

A logger with **effective level = DEBUG** accepts `DEBUG` and more severe levels, but not `TRACE`.

~~~text
Effective level = INFO
TRACE  -> filtered
DEBUG  -> filtered
INFO   -> logged
WARN   -> logged
ERROR  -> logged

Effective level = DEBUG
TRACE  -> filtered
DEBUG  -> logged
INFO   -> logged
WARN   -> logged
ERROR  -> logged
~~~

**Log level does not reflect an automatic severity derived from an exception.** Code can call `log.debug("Cannot connect", exception)` and that message will still be filtered out when the effective level is INFO. Severity is decided by the log author, not inferred by Spring from the exception type.

### 3.1. More detailed level does not mean better

`TRACE` and `DEBUG` are useful during diagnosis, yet they can produce huge line counts, large log sizes, sensitive metadata leaks, or increased operational cost.

Keep default levels sensible, raise verbosity only for the scope under investigation, and plan to restore the original level once resolved.

## 4. Root logger: logging.level.root

The root logger is the base of the logger hierarchy. A logger without a specific level inherits its effective level from a parent and ultimately from root.

Example `application.properties`:

~~~properties
logging.level.root=INFO
~~~

Or `application.yml`:

~~~yaml
logging:
  level:
    root: INFO
~~~

This sets the general log threshold for the application and libraries when no more specific configuration applies.

If you set:

~~~properties
logging.level.root=WARN
~~~

loggers without individual overrides will not emit `INFO` or `DEBUG`. This can reduce log volume, but also hides normal operational notices from many frameworks.

### 4.1. Root INFO does not erase individual settings

Suppose:

~~~properties
logging.level.root=INFO
logging.level.com.example.shop.payment=DEBUG
~~~

Logger `com.example.shop.payment.PaymentService` can emit DEBUG because it receives a specific level from the `com.example.shop.payment` namespace. Root INFO still applies to loggers without a closer configuration.

Do not read `logging.level.root=INFO` as "every logger is forced to be INFO". It is the **inherited baseline at the root**, not a hard cap blocking all overrides.

### 4.2. Root DEBUG in production requires caution

Setting root to DEBUG allows many libraries to write detailed logs. This can surge log volume and inadvertently leak data that should not be recorded.

In production, prefer raising the level on a specific package or logger, or using Actuator to change it temporarily within a controlled scope rather than enabling DEBUG globally.

## 5. logging.level by package

You can set a log level for a namespace matching a package name:

~~~properties
logging.level.com.example.shop.payment=DEBUG
~~~

Or YAML:

~~~yaml
logging:
  level:
    "com.example.shop.payment": DEBUG
~~~

When using `LoggerFactory.getLogger(SomeClass.class)`, the logger name is usually the package-qualified class name. Therefore, these loggers:

~~~text
com.example.shop.payment.PaymentService
com.example.shop.payment.PaymentGatewayClient
com.example.shop.payment.PaymentRetryScheduler
~~~

all inherit DEBUG from namespace `com.example.shop.payment`, unless the logger itself or a closer parent has its own level.

A logger in `com.example.shop.order` is unaffected by this setting.

### 5.1. "Package" here means logger namespace

The logging backend does not check which Java package a class physically resides in. It processes **dot-separated hierarchical logger names**.

Example:

~~~java
private static final Logger AUDIT =
        LoggerFactory.getLogger("com.example.shop.payment.audit");
~~~

This custom-named logger also sits under namespace `com.example.shop.payment`, even though it does not correspond to a concrete Java class.

Conversely:

~~~java
private static final Logger AUDIT =
        LoggerFactory.getLogger("audit.payment");
~~~

does not automatically inherit `logging.level.com.example.shop.payment` just because it was created inside `PaymentService`. Its logger name is `audit.payment`.

**Levels follow the logger name, not the source-code location of the log call.**

### 5.2. Dot-separated hierarchy, not arbitrary string prefix matching

A logger named `com.example.payment.Client` falls under `com.example.payment`. However, logger `com.example.payments.Client` does **not** fall under `com.example.payment`, because segment `payments` differs from `payment`.

~~~text
com.example
├── payment
│   ├── Client
│   └── RetryWorker
└── payments
    └── Client
~~~

This prevents misunderstandings about arbitrary string prefix matching. The backend evaluates hierarchy strictly by logger name segments.

## 6. logging.level for a specific logger or class

If you only want logs from one service:

~~~properties
logging.level.com.example.shop.payment.PaymentService=TRACE
~~~

Or YAML:

~~~yaml
logging:
  level:
    "com.example.shop.payment.PaymentService": TRACE
~~~

When `PaymentService` uses:

~~~java
private static final Logger log =
        LoggerFactory.getLogger(PaymentService.class);
~~~

the logger name matches the configuration. Calls to `log.trace(...)` can be written to output if the backend/appender applies no other blocking filter.

### 6.1. A class configuration is configuration by logger name

Spring Boot does not require class `PaymentService` to exist in order for you to declare:

~~~properties
logging.level.com.example.shop.payment.PaymentService=TRACE
~~~

The configuration sets the level for **the logger category with that name**. If actual code does not use that logger name, the change will produce no logs.

For example, if the service uses:

~~~java
private static final Logger log =
        LoggerFactory.getLogger("payments");
~~~

the logger name is `payments`, not `com.example.shop.payment.PaymentService`. You must configure:

~~~properties
logging.level.payments=TRACE
~~~

This is one of the most common reasons a configuration looks right yet logs do not change.

### 6.2. Static logger vs instance logger

Both approaches can produce the same logger name:

~~~java
private static final Logger log =
        LoggerFactory.getLogger(PaymentService.class);
~~~

~~~java
private final Logger log =
        LoggerFactory.getLogger(getClass());
~~~

The second approach can yield a different logger name when a class is subclassed or proxied, so be careful if config depends on a fixed logger name. For typical services, a `private static final` logger tied to the declaring class is the predictable choice.

### 6.3. Logger from Lombok @Slf4j

If the project uses Lombok:

~~~java
@Slf4j
@Service
public class PaymentService {
    public void pay(String orderId) {
        log.debug("Paying orderId={}", orderId);
    }
}
~~~

Lombok generates a logger field for the class. By default, the logger name matches the declaring class, so `logging.level.com.example.shop.payment.PaymentService` is an appropriate configuration.

The `@Slf4j` annotation requires Lombok to be configured in the build. It is not a Spring Boot annotation, and it does not change the logging backend or log level on its own.

## 7. Level inheritance and overrides: which config wins?

Let's use an example with multiple layers:

~~~properties
logging.level.root=INFO
logging.level.com.example=DEBUG
logging.level.com.example.shop.payment=TRACE
logging.level.com.example.shop.payment.PaymentService=INFO
~~~

The loggers will have these effective levels:

| Logger name | Effective level | Why? |
| --- | --- | --- |
| `org.springframework.web.DispatcherServlet` | INFO | Inherits from root if no other override exists |
| `com.example.shop.order.OrderService` | DEBUG | Inherits `com.example` |
| `com.example.shop.payment.PaymentGatewayClient` | TRACE | Inherits `com.example.shop.payment` |
| `com.example.shop.payment.PaymentService` | INFO | Has its own level on the logger |
| `com.example.shop.payment.internal.RetryPolicy` | TRACE | Under the payment namespace |
| `audit.payment` | INFO | Not in the `com.example` namespace |

The backend finds the **closest configured level in the logger hierarchy**, falling back up to root if no closer level is set.

~~~mermaid
flowchart TD
    A["root = INFO"] --> B["com.example = DEBUG"]
    B --> C["com.example.shop.order"]
    B --> D["com.example.shop.payment = TRACE"]
    D --> E["PaymentGatewayClient = TRACE inherited"]
    D --> F["PaymentService = INFO override"]
    D --> G["internal.RetryPolicy = TRACE inherited"]
~~~

### 7.1. A more specific level can be less verbose

Many assume you can only turn *up* logging for one class inside a package. In fact, you can dial down a noisy class:

~~~properties
logging.level.com.example.shop.payment=DEBUG
logging.level.com.example.shop.payment.NoisyPollingClient=WARN
~~~

Other classes under payment remain at DEBUG. Only `NoisyPollingClient` is restricted to WARN/ERROR.

This is a useful tool to keep a high-frequency logger from flooding the console while keeping necessary logs for the rest of the package.

### 7.2. An override does not alter the parent configuration

Setting child logger `PaymentService=TRACE` does not turn `com.example.shop.payment` into TRACE; sibling loggers continue inheriting the parent's level.

### 7.3. Nested class names

Java can generate nested classes with binary names containing `$`, such as `OrderService$Worker`. If a logger is created from a nested class, its actual name may contain that character.

Before writing a property for a special logger, verify the **actual logger name** rather than guessing from how the nested class is written in source. Use the logger name printed in the pattern or check `logger.getName()`.

## 8. Distinguishing logger hierarchy from property-source precedence

Two mechanisms are easily confused:

1. **Property-source precedence** decides the effective value when **the exact same property key** appears in multiple sources, such as `application.yml` and the command line.
2. **Logger hierarchy** decides which level a logger inherits across root, package, and specific logger.

Example base file:

~~~yaml
logging:
  level:
    root: INFO
    "com.example.shop.payment.PaymentService": TRACE
~~~

Production profile states:

~~~yaml
logging:
  level:
    "com.example.shop.payment": WARN
~~~

These are **two different keys**. The production profile having higher precedence does not automatically delete the specific `PaymentService` setting from the base source. The specific logger can still receive TRACE, while other loggers under the payment package receive WARN.

If you want production to truly disable TRACE for that class, override **that exact specific key**:

~~~yaml
logging:
  level:
    "com.example.shop.payment.PaymentService": INFO
~~~

Do not assume "the production file comes later so package WARN beats every class-level DEBUG/TRACE". Logger name hierarchy and config-source precedence are two separate axes.

### 8.1. Do not confuse inherited levels with log additivity

In backends like Logback, **additivity** decides whether a log event is forwarded to appenders of ancestor loggers. It differs from **effective level**.

- Logger level determines which events are accepted.
- Appenders and additivity determine where events are written and whether they might be written multiple times.

If a log line appears twice, the cause may be duplicate appender/additivity configuration, not setting levels on both root and package.

## 9. Configuration in application.properties

`application.properties` is convenient when adding entries line by line:

~~~properties
# General level
logging.level.root=INFO

# Focus on application logs
logging.level.com.example.shop=DEBUG

# Increase payment package logs
logging.level.com.example.shop.payment=TRACE

# Reduce logs from a noisy logger
logging.level.com.example.shop.payment.PaymentRetryScheduler=WARN

# Track Spring request mappings
logging.level.org.springframework.web=DEBUG
~~~

Spell logger/class names accurately, including uppercase/lowercase when logger identifiers are case-sensitive. Do not write abbreviated class names like `PaymentService` when the actual logger has a fully-qualified name.

### 9.1. Level values are case-insensitive in standard syntax

In typical Spring Boot configuration, level values such as `debug`, `DEBUG`, and `Info` are bound/interpreted to the appropriate level. Still, use uppercase consistently for readability and alignment with official examples:

~~~properties
logging.level.com.example.shop.payment=DEBUG
~~~

Logger names are not level values; do not arbitrarily lowercase class names when moving configuration between sources.

### 9.2. Do not use arbitrary wildcards like globs

Do not assume the property:

~~~properties
logging.level.com.example.shop.*=DEBUG
~~~

is wildcard syntax applied by Spring Boot to all subpackages. `logging.level` is configured by **logger name or namespace**. To affect child loggers, set directly:

~~~properties
logging.level.com.example.shop=DEBUG
~~~

You do not need `*` because the logger hierarchy already handles inheritance.

## 10. Configuration in application.yml

The same configuration can be written in YAML:

~~~yaml
logging:
  level:
    root: INFO
    "com.example.shop": DEBUG
    "com.example.shop.payment": TRACE
    "com.example.shop.payment.PaymentRetryScheduler": WARN
    "org.springframework.web": DEBUG
~~~

You can write nested branches, though it gets messy with logger names containing uppercase letters or special segments. To manage multiple class/logger names accurately, using **quoted dotted keys** under `logging.level` is usually very readable.

Example:

~~~yaml
logging:
  level:
    "com.example.shop.payment.PaymentService": DEBUG
    "org.hibernate.SQL": DEBUG
~~~

The quotes here are YAML syntax wrapping a key containing dots. They do not change the logger name in the configuration value.

### 10.1. Common YAML mistakes

Wrong indentation:

~~~yaml
logging:
level:
  root: INFO
~~~

This YAML does not create the expected `logging.level.root` structure.

Correct:

~~~yaml
logging:
  level:
    root: INFO
~~~

Mistake from mixing properties' `=` sign:

~~~yaml
logging:
  level:
    root=INFO
~~~

In YAML, key/value pairs must use a colon.

### 10.2. One configuration source is not the only place

Spring Boot can receive `logging.level.*` from multiple property sources such as profile files, environment variables, system properties, command-line arguments, and other supported configuration sources.

When finding out why a level is not as expected, inspect the **effective value**, not just a single `application.yml` file.

## 11. Configuration by profile: dev, test, production

A common requirement is keeping diagnostic logs in development while reducing verbosity in production.

`application.yml`:

~~~yaml
logging:
  level:
    root: INFO
    "com.example.shop": INFO
~~~

`application-dev.yml`:

~~~yaml
logging:
  level:
    "com.example.shop.payment": DEBUG
~~~

`application-prod.yml`:

~~~yaml
logging:
  level:
    "com.example.shop.payment": WARN
~~~

When profile `dev` is active, the payment group can emit DEBUG. When profile `prod` is active, it receives WARN, unless a more detailed configuration or higher-precedence source overrides it.

### 11.1. Checking active profiles

You can activate a profile via property:

~~~properties
spring.profiles.active=dev
~~~

or command line:

~~~bash
java -jar app.jar --spring.profiles.active=dev
~~~

When the application reads configuration from profile files, verify that the file is packaged in the artifact, loaded from the expected location, and not overridden by another source.

### 11.2. Do not leave DEBUG configured permanently in production

Even when a logger covers just one package, TRACE/DEBUG can still record:

- Request identifiers or tokens mistakenly passed into log arguments.
- API payloads or user data.
- Query details and database parameters.
- Internal processing states holding sensitive values.

Enable intentionally, limit the duration, protect log outputs, and lower the level after investigation. Logging configuration does not replace data security policy.

## 12. Configuration via command line and JVM system properties

You do not need to edit config files to temporarily raise a level when running an application instance.

With a Spring Boot command-line argument:

~~~bash
java -jar app.jar --logging.level.com.example.shop.payment=DEBUG
~~~

For a specific logger:

~~~bash
java -jar app.jar --logging.level.com.example.shop.payment.PaymentService=TRACE
~~~

JVM system properties can also supply the same property key:

~~~bash
java -Dlogging.level.com.example.shop.payment.PaymentService=TRACE -jar app.jar
~~~

`-D...` belongs to JVM syntax and must appear before `-jar` in this example. Meanwhile, `--logging.level...` is an application argument passed after the JAR name.

### 12.1. Advantages of runtime/startup configuration

- No source code changes required.
- No new build required just to raise one logger.
- Easy to use in test environments or on a single instance.
- Can integrate with deployment tools to adjust log levels.

If you edit the production start command, changes usually require restarting the process to pick up the new startup arguments. By contrast, the Actuator loggers endpoint allows changing levels at runtime when enabled and appropriately secured.

### 12.2. Command line can override files

If the same key is set in a file:

~~~properties
logging.level.com.example.shop.payment=INFO
~~~

and the command line passes:

~~~bash
java -jar app.jar --logging.level.com.example.shop.payment=DEBUG
~~~

in standard Spring Boot configuration, command-line properties have high precedence, so the effective value of **that exact key** is DEBUG.

However, as distinguished in the hierarchy section, a source override does not automatically erase other child logger keys.

## 13. Environment variables and uppercase class-name issues

This is an important detail when deploying with Docker, Kubernetes, or CI/CD systems.

Spring Boot supports configuring logging via environment variables. For a package logger:

~~~text
LOGGING_LEVEL_COM_EXAMPLE_SHOP_PAYMENT=DEBUG
~~~

can correspond to:

~~~properties
logging.level.com.example.shop.payment=DEBUG
~~~

However, **configuring a logger by fully-qualified class name via standard environment variables has a limitation**: relaxed binding from environment variables typically converts names to lowercase. A Java class logger name can contain uppercase characters, such as `PaymentService`, so the setting may fail to target the expected logger.

For example:

~~~text
LOGGING_LEVEL_COM_EXAMPLE_SHOP_PAYMENT_PAYMENTSERVICE=TRACE
~~~

is not a reliable way to set the level for the exact logger name `com.example.shop.payment.PaymentService`. Logger names are case-sensitive; the class portion with uppercase letters can be lowercased during property-name conversion.

### 13.1. Use environment variables for packages

If you want to set log levels for a whole package, environment variables work very well:

~~~text
LOGGING_LEVEL_ORG_SPRINGFRAMEWORK_WEB=DEBUG
LOGGING_LEVEL_COM_EXAMPLE_SHOP_PAYMENT=TRACE
~~~

Package names are normally lowercase, avoiding uppercase class-name limitations.

### 13.2. Use SPRING_APPLICATION_JSON for exact class names

If you need a class-level logger via environment without editing files, use `SPRING_APPLICATION_JSON`:

~~~json
{
  "logging": {
    "level": {
      "com.example.shop.payment.PaymentService": "TRACE"
    }
  }
}
~~~

On shells supporting JSON in environment variables, set this content in `SPRING_APPLICATION_JSON` before starting the application. The example above illustrates the **JSON value**, not variable names created per key.

The JSON mechanism preserves logger name keys with their intended casing. Another option is passing a command-line argument with the exact name.

### 13.3. System properties are another option

JVM system properties are passed with the full key:

~~~bash
java -Dlogging.level.com.example.shop.payment.PaymentService=DEBUG -jar app.jar
~~~

Unlike uppercase/underscore environment variables, you can express exact logger names with uppercase letters directly in the JVM property key.

### 13.4. Do not rename classes to accommodate environment variables

Do not change `PaymentService` to `paymentservice` or force lowercase logger names in Java solely for deployment convenience. Choose a configuration method that preserves logger names or configure by package. Class names and logger categories should reflect design intent, not accidentally bend to environment-variable limitations.

## 14. logging.group: grouping multiple packages/loggers

Sometimes a feature spans multiple distinct packages:

~~~text
com.example.shop.order
com.example.shop.payment
com.example.shop.inventory
~~~

You want to enable DEBUG for all three using a single key. Spring Boot provides the **logging group** concept.

`application.properties`:

~~~properties
logging.group.shop-flow=com.example.shop.order,com.example.shop.payment,com.example.shop.inventory
logging.level.shop-flow=DEBUG
~~~

Equivalent YAML:

~~~yaml
logging:
  group:
    shop-flow:
      - com.example.shop.order
      - com.example.shop.payment
      - com.example.shop.inventory
  level:
    shop-flow: DEBUG
~~~

When Spring Boot processes a logging group, the level assigned to `shop-flow` is applied to the logger names belonging to the group. This lets you control multiple namespaces that do not share a narrow enough common ancestor.

### 14.1. Groups differ from logger namespaces

`shop-flow` is **a user-defined group name**, not necessarily a real logger name with child hierarchy. It acts as a control key for a set of loggers:

~~~text
logging.level.shop-flow=DEBUG
           |
           v
  +-----------------------+
  | com.example.shop.order|
  | com.example.shop.payment
  | com.example.shop.inventory
  +-----------------------+
~~~

If you simply want to apply it to all of `com.example.shop`, configuring a parent ancestor package can be simpler:

~~~properties
logging.level.com.example.shop=DEBUG
~~~

Groups are more useful when the list of namespaces does not share a single parent or when you want to name them after an operational workflow.

### 14.2. Group defined without a level

~~~properties
logging.group.shop-flow=com.example.shop.order,com.example.shop.payment
~~~

Defining a group alone does not turn on DEBUG. You must set a level on the group to control it:

~~~properties
logging.level.shop-flow=DEBUG
~~~

### 14.3. Built-in groups

Spring Boot provides several convenient groups depending on version, such as `web` and `sql`, to adjust related sets of loggers:

~~~properties
logging.level.web=DEBUG
logging.level.sql=DEBUG
~~~

These groups do not mean every web tool or every database logs full request/SQL contents. The exact member loggers included in a group depend on the Spring Boot version, backend, and present dependencies.

For precise control, check the group definitions of the version you are using or configure specific loggers as needed.

### 14.4. Avoid unintended overlap

If a logger both belongs to a group and has an individual level setting, understand how Spring Boot applies logging levels for the final configuration. When you need to guarantee an exact level for a logger, avoid multiple groups and overrides overwriting each other in hard-to-trace order; keep one clear source of control and inspect the effective level when the app runs.

## 15. Tracking Spring Framework loggers

Many bugs lie inside the framework rather than application code. You can increase logs for a narrow namespace.

Example observing Spring Web:

~~~properties
logging.level.org.springframework.web=DEBUG
~~~

Observing Spring Security:

~~~properties
logging.level.org.springframework.security=DEBUG
~~~

Observing transaction infrastructure:

~~~properties
logging.level.org.springframework.transaction=DEBUG
~~~

Observing bean factory configuration:

~~~properties
logging.level.org.springframework.beans.factory=DEBUG
~~~

These are common example logger names; enable only the ones matching the question you are investigating rather than enabling all of them.

### 15.1. Spring Security logs can be very sensitive

Security-related logs can reflect filter chains, authentication state, request metadata, or data used during authentication. Do not leave DEBUG/TRACE open on security packages broadly in production without checking whether outputs contain sensitive data.

### 15.2. Root DEBUG does not mean everything will emit DEBUG logs

A framework only logs when its code actually contains a log call at that level. If a method never calls `DEBUG`, raising the logger level creates no new messages.

Some logs also have custom conditions, sampling, filters/appenders, or go to a different logger name than you guessed. Always identify the actual logger category when debugging.

## 16. Hibernate and JDBC: finding the right logger category

A common scenario is wanting to inspect SQL statements and bind parameter values.

With Hibernate 6 (commonly paired with Spring Boot 3.x), common loggers are:

~~~properties
# SQL statements logged by Hibernate through the logging backend
logging.level.org.hibernate.SQL=DEBUG

# Bind parameter values (exercise caution with sensitive data)
logging.level.org.hibernate.orm.jdbc.bind=TRACE
~~~

You can add loggers related to result extraction in deep diagnostic cases, but do not habitually enable TRACE levels broadly.

### 16.1. SQL logger contains uppercase letters

`org.hibernate.SQL` is an important example of a logger **not named after a regular Java class** yet containing uppercase letters. When configured via standard environment variables, lowercase conversion can still mis-map the logger name.

Use properties/YAML, JVM system properties, or `SPRING_APPLICATION_JSON` when you need to preserve the exact name `org.hibernate.SQL`.

### 16.2. Do not confuse logger levels with show-sql

Hibernate has the `spring.jpa.show-sql` option in Spring Boot. That option differs from logging via `org.hibernate.SQL`. Printing SQL directly to the console lacks the logging backend's benefits for levels, formatting, and routing.

In operational environments, usually prefer a logger with explicit levels tied to appropriate logging and masking policies.

### 16.3. Spring JDBC uses different logger names from Hibernate

If an application uses `JdbcTemplate` instead of JPA/Hibernate, enabling `org.hibernate.SQL` has no effect on Spring JDBC logs.

You can investigate namespaces such as:

~~~properties
logging.level.org.springframework.jdbc.core=DEBUG
~~~

For more detailed JDBC logs, verify the exact classes and logger names of the Spring version in use. Pick a concrete logger based on observed data rather than assuming all SQL access goes through Hibernate.

## 17. Spring Boot's debug flag is not equivalent to root DEBUG

Spring Boot supports:

~~~bash
java -jar app.jar --debug
~~~

or:

~~~properties
debug=true
~~~

And at a more detailed level:

~~~properties
trace=true
~~~

These flags enable diagnostic logger groups selected by Spring Boot and can surface additional startup/condition evaluation info. They are **not equivalent** to:

~~~properties
logging.level.root=DEBUG
~~~

or:

~~~properties
logging.level.root=TRACE
~~~

To view your application's DEBUG logs:

~~~properties
logging.level.com.example.shop=DEBUG
~~~

is the more direct approach. To view the condition evaluation report when auto-configuration behaves unexpectedly, `--debug` can be especially helpful.

### 17.1. Avoid using --trace as a fix-all

`--trace` can make many logger groups very verbose. Prefer raising the level on the specific logger/package under investigation to keep logs readable and avoid sensitive data exposure.

## 18. Changing log levels at runtime with Actuator

Spring Boot Actuator provides a **loggers endpoint** to view and, if permitted, modify log levels at runtime without restarting the application.

Add Actuator:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}
~~~

Expose the endpoint over HTTP if the environment truly needs it:

~~~yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,loggers
~~~

Exposing an endpoint only makes it reachable over the corresponding transport; **authentication/authorization must still be configured properly**. Never open a log-level control endpoint to a public network unprotected.

### 18.1. Viewing loggers

The base endpoint is typically:

~~~http
GET /actuator/loggers
~~~

To inspect a specific logger:

~~~http
GET /actuator/loggers/com.example.shop.payment.PaymentService
~~~

Typical output includes fields such as:

~~~json
{
  "configuredLevel": "DEBUG",
  "effectiveLevel": "DEBUG"
}
~~~

If the logger has no explicit level:

~~~json
{
  "configuredLevel": null,
  "effectiveLevel": "INFO"
}
~~~

`configuredLevel` shows the level set directly on that logger; `effectiveLevel` reflects the level currently in effect after inheritance.

The responses above are examples of data structure; actual values depend on configuration and the logging backend.

### 18.2. Changing levels at runtime

Send request:

~~~http
POST /actuator/loggers/com.example.shop.payment.PaymentService
Content-Type: application/json

{"configuredLevel":"TRACE"}
~~~

Example with curl:

~~~bash
curl -X POST \
  -H "Content-Type: application/json" \
  -d '{"configuredLevel":"TRACE"}' \
  http://localhost:8080/actuator/loggers/com.example.shop.payment.PaymentService
~~~

When the endpoint permits the operation and the backend supports level changes, that logger receives TRACE configuration at runtime.

Notes:

- This changes **the running process**, and does not write back to `application.yml`.
- When the application restarts, startup configuration once again determines default levels.
- In a multi-replica system, changing one instance does not automatically apply to every other instance.
- The endpoint must be secured; do not grant level-changing access to unauthorized users.

### 18.3. Reverting to inherited level

You can remove an explicit configured level with:

~~~http
POST /actuator/loggers/com.example.shop.payment.PaymentService
Content-Type: application/json

{"configuredLevel":null}
~~~

After this operation, the logger inherits from its parent namespace or root per the current backend configuration. That **differs** from sending `"INFO"`: setting INFO sets an explicit level, whereas `null` clears the direct override so it receives the inherited level.

### 18.4. Are runtime changes persistent configuration?

No. If a level must survive restarts, update the deployed configuration source such as properties/YAML, command line, config management, or appropriate logging backend configuration.

Actuator is suitable for temporary diagnostics while the application is running, with access control and audit/time-box governance.

## 19. configuredLevel and effectiveLevel: a distinction you must understand

Suppose:

~~~properties
logging.level.root=INFO
logging.level.com.example.shop.payment=DEBUG
~~~

Logger `com.example.shop.payment.PaymentService` has not been directly configured.

When querying Actuator (or the logging system API), you may see:

~~~json
{
  "configuredLevel": null,
  "effectiveLevel": "DEBUG"
}
~~~

Even though `configuredLevel` is null, DEBUG is still active because the logger **inherits** from its parent package.

If you set:

~~~properties
logging.level.com.example.shop.payment.PaymentService=WARN
~~~

then:

~~~json
{
  "configuredLevel": "WARN",
  "effectiveLevel": "WARN"
}
~~~

### 19.1. configuredLevel null does not mean logging is disabled

It simply means **no level is configured directly on the queried logger**. The backend continues computing the effective level from the hierarchy.

### 19.2. Effective level does not guarantee the event will appear on the console

Beyond level, logging backends also have appender filters, markers, logging configuration, and output routing.

A logger with effective DEBUG can create a DEBUG event, yet an appender or filter elsewhere may still choose not to write it to the console. When you see "effective DEBUG yet no log lines", verify whether code actually calls the logger, runtime point, filters, and appenders.

## 20. Checking log state in code

Inside a method, you can query the current logger:

~~~java
private static final Logger log =
        LoggerFactory.getLogger(PaymentService.class);

public void execute(String orderId) {
    if (log.isDebugEnabled()) {
        log.debug("Detailed processing for orderId={}", orderId);
    }
}
~~~

`isDebugEnabled()` checks whether the level is currently enabled on the logger API.

However, with standard placeholder logging:

~~~java
log.debug("Payment id={}, status={}", paymentId, status);
~~~

SLF4J/the backend already defers most formatting until the level permits it; you **do not need** to wrap every call in `if (log.isDebugEnabled())`.

### 20.1. When is a guard genuinely helpful?

When log arguments require expensive computation:

~~~java
if (log.isDebugEnabled()) {
    String snapshot = buildExpensiveDebugSnapshot();
    log.debug("Payment snapshot={}", snapshot);
}
~~~

If you write:

~~~java
log.debug("Payment snapshot={}", buildExpensiveDebugSnapshot());
~~~

Java calls `buildExpensiveDebugSnapshot()` to evaluate the argument **before** invoking the logger method, even when DEBUG is disabled. The guard avoids that computation.

If `snapshot` contains sensitive data, logging being enabled is not a license to write the whole snapshot. Filter permitted information before logging.

### 20.2. Placeholder logging beats string concatenation

Prefer:

~~~java
log.info("Order {} transitioned to {}", orderId, state);
~~~

Avoid:

~~~java
log.info("Order " + orderId + " transitioned to " + state);
~~~

String concatenation builds the string before the logger evaluates the level. Placeholders let the logging framework process arguments properly and maintain consistent formatting.

### 20.3. Logging exceptions properly

~~~java
try {
    paymentGateway.call();
} catch (GatewayException exception) {
    log.error(
            "Payment gateway failed for orderId={}",
            orderId,
            exception
    );
    throw exception;
}
~~~

Passing the exception as the final argument per SLF4J convention lets the backend record the stack trace. Avoid logging only `exception.getMessage()` when a stack trace is needed for diagnosis.

Also avoid logging the same exception as ERROR at every layer and rethrowing if an upper layer logs it again; that easily creates multiple duplicate entries for the same failure.

## 21. Logger levels do not create log statements

Suppose the source only contains:

~~~java
log.info("Payment accepted");
~~~

Setting:

~~~properties
logging.level.com.example.shop.payment.PaymentService=TRACE
~~~

does not make Spring automatically generate TRACE/DEBUG lines. Configuration only decides **which log statements already in code** are allowed to emit.

To observe additional state, add appropriate log calls or enable a framework logger that already emits the detailed events you want to see.

This also guides troubleshooting: if you enabled DEBUG on the exact logger yet see no logs, verify whether the code path actually reaches the `log.debug(...)` call.

## 22. Logging backends and advanced configuration

Spring Boot uses a logging abstraction to integrate common backends. In a standard starter project, **Logback** is usually provided via the `spring-boot-starter-logging` dependency.

If an application uses Log4j2, the system can still accept `logging.level.*` from Spring Boot, though the backend configuration file and specific appender/layout rules differ.

### 22.1. When is logging.level sufficient?

Use `logging.level.*` for:

- Setting the root logger threshold.
- Raising/lowering package logs.
- Raising/lowering a specific logger.
- Managing logging groups.
- Overriding levels per profile or environment.
- Adjusting log levels at runtime via Actuator when appropriate.

### 22.2. When is logback-spring.xml or backend config needed?

When you need:

- Multiple appenders sending to files, console, and centralized systems.
- Custom encoders, structured JSON, or complex masking/filters.
- Rolling policies and retention.
- Different formats per logger, environment, or appender.
- Dedicated routing for audit/operational logs.

You may need backend configuration such as `logback-spring.xml`. That does not change logger naming and hierarchy rules, though it introduces additional factors that can affect output.

### 22.3. Avoid unintended overlapping configurations

If a logger has a level in YAML, is also configured in native backend XML, and is modified via Actuator, its runtime state can differ from what you predict from a single file.

When diagnosing, verify the actual effective level via Actuator or logging system inspection rather than concluding from a single config line.

## 23. Startup logging and configuration loaded too late

Logging initializes very early during Spring Boot startup, before the full application context and all beans are ready.

Consequently, not every mechanism that adds properties arrives in time to affect logging initialization.

For example, `@PropertySource` on a `@Configuration` class is usually processed during refresh; that moment is too late for some of Boot's very early log configurations.

Place logging configuration in:

- `application.properties` / `application.yml` and Config Data sources Boot loads early.
- Environment variables or command-line arguments.
- Appropriate JVM system properties.
- Startup logging configuration mechanisms supported by Spring Boot.

If startup logs do not follow your expected level yet runtime logs do, check **the property source and when it is loaded**.

### 23.1. Spring Boot logging and logger APIs are not identical

Application code can call `LoggerFactory.getLogger(...)`, while Boot orchestrates logging backend initialization through its own infrastructure.

This difference does not affect typical `logging.level.*` usage, yet explains why you should not manually tinker with the backend inside a late-initialized bean and expect it to change all logs since JVM start.

## 24. Testing logging configuration

Two things can be verified:

1. **Does the configuration produce the expected effective level?**
2. **Does a log call at that level emit to the configured output?**

A context integration test is more suitable than a unit test instantiating a service with `new` if you want to verify how Spring Boot loads `logging.level.*`.

### 24.1. Testing with OutputCaptureExtension

Spring Boot Test supports capturing output to assert on an observable log line.

Example assuming `PaymentService` has a method calling `log.debug("Payment debug marker")`:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.system.CapturedOutput;
import org.springframework.boot.test.system.OutputCaptureExtension;

@SpringBootTest(properties = {
        "logging.level.root=INFO",
        "logging.level.com.example.shop.payment=DEBUG"
})
@ExtendWith(OutputCaptureExtension.class)
class PaymentLoggingTest {

    @Autowired
    private PaymentService paymentService;

    @Test
    void emitsDebugLogWhenPackageIsEnabled(CapturedOutput output) {
        paymentService.emitDebugMarker();

        assertThat(output.getOut()).contains("Payment debug marker");
    }
}
~~~

The code requires an `emitDebugMarker()` method in `PaymentService` with a corresponding debug call; the example illustrates the idea rather than the entire service source.

This test depends on the console appender/logging output being appropriately configured. If the project changes logging backends or disables console output, an assertion on stdout may no longer match even though the effective level is correct.

### 24.2. Avoid asserting on full log lines

Timestamps, thread names, logger names, ANSI colors, and patterns can change. When testing logging behavior, prefer asserting on the marker message or key structured fields rather than matching an entire console line.

### 24.3. Testing log level via the logging API

If you only need to confirm DEBUG is enabled for a specific logger in the context:

~~~java
import org.slf4j.LoggerFactory;

boolean debugEnabled = LoggerFactory
        .getLogger("com.example.shop.payment.PaymentService")
        .isDebugEnabled();
~~~

Use in an integration test that initialized the logging system with the desired properties. There is no need to construct services or call real business methods just to check the effective logging flag.

Note that tests may share a JVM and context caching with different log configurations. If a test changes log levels at runtime via backend APIs or Actuator, restore the state afterward to avoid test-order dependencies.

### 24.4. Testing the loggers endpoint

If the project exposes the Actuator loggers endpoint, you can use an integration test to read configured/effective levels or change levels in an isolated test environment.

Never let an automated test alter logs of a production instance. All runtime level changes should occur in a test environment with clear permissions and lifecycle.

## 25. Common configuration errors

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| DEBUG configured yet no DEBUG lines | Wrong logger name or code does not log at DEBUG | Check `Logger.getName()` and code path |
| Only some classes in a package emit DEBUG | Child logger has its own override or backend filter | Check effective level of each logger |
| INFO disappears after changing root | Root set to WARN/ERROR | Restore root or add appropriate override |
| Class-level env variable does not work | Class name lowercased by relaxed env binding | Use properties/YAML, JVM property, or `SPRING_APPLICATION_JSON` |
| `logging.level.com.example.*` does not apply as expected | Misunderstanding wildcards | Configure `com.example` without `*` |
| `--debug` enabled yet app logger stays INFO | Debug flag only enables selected logger groups | Set `logging.level.com.example=DEBUG` |
| Logs do not change after editing YAML without restart | Configuration loaded at startup | Restart or use Actuator at runtime |
| Actuator change only affects one pod | Level changed in a single instance | Coordinate change across target instances |
| Actuator returns 404 | Endpoint not exposed, wrong base path, or missing dependency | Check Actuator/exposure/path |
| Actuator returns 401/403 | Endpoint is secured | Use authorized credentials/permissions |
| Two identical log lines appear | Duplicate appender/additivity configuration | Check backend appenders |
| SQL does not appear | Wrong logger category for JDBC/Hibernate version | Identify framework and actual logger |
| Too many logs after enabling TRACE | Too broad a scope or hot-path logger | Lower level, time-box, apply sampling |
| Logger has effective DEBUG yet no console output | Appender/filter discards events | Check backend configuration |
| Test logs differ from production | Different profile, runtime classpath, or test config | Check active sources and effective levels |

### 25.1. Practical troubleshooting sequence

When a `logging.level` configuration has no effect, follow this order:

1. **Locate the log statement**: which `log.trace`/`log.debug`/`log.info` call does code make?
2. **Identify the actual logger name**: `getLogger(Class)`, `getLogger(String)`, or a library-created logger?
3. **Check the level property**: does the key match the exact logger/package name?
4. **Inspect config sources**: do files, profiles, env, system properties, or command line override the same key?
5. **Check hierarchy**: does a child logger have its own configured level?
6. **Inspect effective level**: via Actuator or logging API if available.
7. **Inspect the output pipeline**: do appenders/filters/patterns keep the event?
8. **Verify the running instance**: right pod, process, version, profile, and start command?

Do not tweak multiple things at once; if you rename the logger, switch backends, and set root to TRACE simultaneously, it is hard to tell which change solved the problem.

## 26. Sample configuration for a multi-module system

Suppose you want:

- Root at INFO.
- Application code under `com.example.shop` at INFO.
- Payment package at DEBUG.
- Specific gateway HTTP client at TRACE for diagnostics.
- A noisy scheduler at WARN only.
- Transaction infrastructure at INFO.

~~~yaml
logging:
  level:
    root: INFO
    "com.example.shop": INFO
    "com.example.shop.payment": DEBUG
    "com.example.shop.payment.PaymentGatewayClient": TRACE
    "com.example.shop.payment.PaymentRetryScheduler": WARN
    "org.springframework.transaction": INFO
~~~

When the application runs, the ideal result:

| Logger | Effective level |
| --- | --- |
| `com.example.shop.order.OrderService` | INFO |
| `com.example.shop.inventory.InventoryService` | INFO |
| `com.example.shop.payment.PaymentService` | DEBUG |
| `com.example.shop.payment.PaymentGatewayClient` | TRACE |
| `com.example.shop.payment.PaymentRetryScheduler` | WARN |
| `org.springframework.transaction.interceptor.TransactionInterceptor` | INFO |
| Unconfigured loggers | INFO (from root, unless overridden elsewhere) |

In a real application, auto-configuration or native backend configuration may set additional levels. Check runtime effective levels when exact confirmation is needed, especially with third-party libraries and platform-specific setups.

### 26.1. How to dial levels back down after debugging

After resolving the issue:

~~~yaml
logging:
  level:
    root: INFO
    "com.example.shop": INFO
    "com.example.shop.payment": INFO
~~~

Or if a level was changed temporarily via Actuator, clear the direct configured level using `{"configuredLevel": null}` so the logger returns to appropriate inheritance.

Change procedures should be transparent: who enabled it, which logger, for how long, on which instances, and when it was restored. This is especially important for loggers that may emit sensitive information.

## 28. Remember

`logging.level` in Spring Boot lets you configure log thresholds by **logger name**. `logging.level.root` is the root baseline for inheritance; `logging.level.com.example.shop.payment` applies to the payment namespace; `logging.level.com.example.shop.payment.PaymentService` applies directly to the logger with that name. Child loggers can override parent levels along the dot-separated hierarchy.

Package configuration does not scan bytecode or Java directory locations; it applies to the **logger name used by code or libraries**. Check `LoggerFactory.getLogger(...)` and the actual name when a setting has no effect. Root INFO does not prevent a specific logger from enabling DEBUG/TRACE, and a specific logger can set WARN to reduce logs inside a package currently at DEBUG.

Distinguish **property-source precedence** from **logger hierarchy**: higher-precedence sources override values for the exact same property key, whereas a logger's effective level is resolved by the most specific name in the hierarchy. With environment variables, package settings are convenient, while class names with uppercase letters may require `SPRING_APPLICATION_JSON`, properties/YAML, or JVM/command-line properties to preserve exact casing.

Actuator `/actuator/loggers` can inspect `configuredLevel`/`effectiveLevel` and modify levels while the application is running, but those changes do not automatically survive restarts or synchronize across replicas. In production, raise logs only for the necessary scope, keep outputs safe, and restore levels after diagnostics. **Log levels only control whether messages are permitted to emit; log content, appenders, formats, and data security remain separate design responsibilities.**
