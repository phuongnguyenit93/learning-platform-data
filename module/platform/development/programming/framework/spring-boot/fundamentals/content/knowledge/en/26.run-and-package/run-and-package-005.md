# Main Class, Manifest, Dependencies, and Executable JAR Structure

When learning Spring Boot, we usually start with a class containing `main()`, run the application from the IDE, and watch the server start. However, when packaging for deployment, the more important questions are: **how does the JVM find the main class, where are dependencies loaded from, and why can a Spring Boot JAR file run with `java -jar` without manually building a long classpath?**

To understand that, it is necessary to distinguish four components:

1. **Application main class**: contains `public static void main(String[] args)` and usually calls `SpringApplication.run(...)`.
2. **JAR manifest**: metadata at `META-INF/MANIFEST.MF` that tells the Java launcher the archive's entry point.
3. **Dependencies**: the libraries the application needs at runtime, determined by the build tool from the dependency graph.
4. **Executable JAR structure**: a special layout generated by the Spring Boot packaging plugin, consisting of the boot loader, application classes, and nested library JARs.

Viewing these four components as a single execution flow helps explain errors like `no main manifest attribute`, `ClassNotFoundException`, or situations where a JAR file runs in the IDE but fails when deployed.

## 1. Distinguishing Running in the IDE vs. Running the Packaged Build

When running from an IDE or using `bootRun`, the IDE/build tool typically builds the classpath from:

- The directory containing compiled application bytecode.
- Resource directories such as `src/main/resources`.
- The dependencies required for runtime.
- The main class selected as the entry point.

Diagram:

~~~text
IDE / bootRun
    |
    +-- target/main class: CatalogApplication
    |
    +-- application classes (build/classes/java/main)
    |
    +-- resources (build/resources/main)
    |
    +-- dependency JARs from Gradle/Maven runtime classpath
    |
    v
JVM runs CatalogApplication.main(...)
~~~

Meanwhile, a Spring Boot executable JAR carries most of its runtime dependencies inside the archive:

~~~text
java -jar catalog-service.jar
    |
    v
Read META-INF/MANIFEST.MF
    |
    v
Boot launcher (Main-Class)
    |
    v
Load application classes + nested dependencies
    |
    v
Invoke CatalogApplication.main(...) (Start-Class)
    |
    v
SpringApplication.run(...)
~~~

The key difference: when running `java -jar`, the JVM does **not** natively understand nested JARs as standard classpath entries. Spring Boot provides a launcher/loader to handle the executable archive layout.

## 2. The Application's Actual Main Class

A typical main class:

~~~java
package com.example.catalog;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CatalogApplication {

    public static void main(String[] args) {
        SpringApplication.run(CatalogApplication.class, args);
    }
}
~~~

Three key components:

- `public static void main(String[] args)`: the Java entry point of the program.
- `@SpringBootApplication`: groups the core configuration mechanisms of Spring Boot.
- `SpringApplication.run(CatalogApplication.class, args)`: initializes, refreshes, and runs the application context.

`@SpringBootApplication` is an annotation that combines features such as Spring Boot configuration, auto-configuration, and component scanning. It is not responsible for writing the JAR manifest itself. The manifest is generated by the packaging tool during the **build phase**.

### 2.1. Why Does the Main Class Package Location Matter?

Default component scanning starts from the package containing the class annotated with `@SpringBootApplication` and scans its subpackages.

Recommended organization example:

~~~text
src/main/java/
└── com/example/catalog/
    ├── CatalogApplication.java
    ├── web/
    │   └── CatalogController.java
    ├── service/
    │   └── CatalogService.java
    └── repository/
        └── CatalogRepository.java
~~~

`CatalogApplication` belongs to `com.example.catalog`, so components under the subpackages can be discovered under the default scan configuration.

If you place the main class in `com.example.catalog.launcher` while the service is in `com.example.catalog.service`, the service will lie **outside the launcher's subpackage tree**. The JAR can still be packaged and run, but the application context may be missing beans. That is a component scan configuration issue, not a manifest or dependency packaging error.

This can be resolved by placing the main class in an appropriate root package or configuring scanning/imports explicitly. You should not broaden scanning to all of `com` or third-party library packages just to fix a package placement mistake.

### 2.2. The Main Class Does Not Need to Hold Every Bean

The main class usually only handles bootstrapping. Controllers, services, repositories, and business beans live in other classes. Inside the executable JAR, they are all packaged as class files; the Java launcher does not automatically instantiate every object from those classes. The Spring container decides which beans are registered and instantiated.

## 3. What Is a JAR and What Is a Manifest?

A JAR (Java Archive) is based on the ZIP format and can contain:

- `.class` bytecode.
- Resource files such as YAML, XML, templates, and static assets.
- Library metadata.
- The `META-INF` directory and the manifest file.

The manifest is located at:

~~~text
META-INF/MANIFEST.MF
~~~

A regular Java JAR runnable via `java -jar` needs a manifest with a `Main-Class` pointing to a class that has a suitable main method.

Example for a simple standalone Java JAR:

~~~text
Manifest-Version: 1.0
Main-Class: com.example.tools.CliApplication
~~~

When running:

~~~bash
java -jar tool.jar
~~~

The Java launcher reads `Main-Class` and invokes `com.example.tools.CliApplication.main(...)`.

However, a Spring Boot executable JAR **typically has two entry point roles**: the JVM entry point and the application entry point.

## 4. Main-Class vs. Start-Class in a Spring Boot Executable JAR

For an executable JAR packaged by Spring Boot, the manifest typically looks similar to this:

~~~text
Manifest-Version: 1.0
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.catalog.CatalogApplication
Spring-Boot-Version: 3.x.y
Spring-Boot-Classes: BOOT-INF/classes/
Spring-Boot-Lib: BOOT-INF/lib/
~~~

The illustrative values above use the launcher naming convention from **Spring Boot 3.2+**. On Spring Boot 2.x and earlier Boot 3 releases before the loader package rename, `Main-Class` may be:

~~~text
Main-Class: org.springframework.boot.loader.JarLauncher
~~~

You should not manually edit the launcher class based on an example taken from a different version. The packaging tool matching your Spring Boot version will write the correct value.

Meaning:

| Manifest attribute | Role |
|---|---|
| `Manifest-Version` | Manifest syntax version |
| `Main-Class` | Class that the JVM invokes first when running `java -jar` |
| `Start-Class` | Application main class, launched by the Boot launcher |
| `Spring-Boot-Version` | Boot version metadata written by the packaging tool when applicable |
| `Spring-Boot-Classes` | Location containing application classes/resources inside the archive |
| `Spring-Boot-Lib` | Location containing nested runtime dependency JARs |

Other `Spring-Boot-*` attributes may appear depending on the version and build options; not every executable archive has an identical manifest to the example.

### 4.1. Why Is Main-Class Not CatalogApplication?

If you set `Main-Class: com.example.catalog.CatalogApplication` in an archive where application classes reside under `BOOT-INF/classes` and dependencies reside in `BOOT-INF/lib`, the standard Java launcher does not automatically configure the classpath for that layout.

Spring Boot needs a launcher to:

1. Understand the layout of the executable archive.
2. Locate application classes and nested library JARs.
3. Create an appropriate class loading environment.
4. Find `Start-Class` in the manifest.
5. Invoke the application's `main(String[] args)` method.

Therefore:

~~~text
Main-Class = JVM-level entry point
Start-Class = Spring Boot application-level logical entry point
~~~

Do not confuse these two attributes when investigating "which main class is being executed".

## 5. Typical Layout of a Spring Boot Executable JAR

Example `catalog-service.jar` archive:

~~~text
catalog-service.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── ...
├── org/
│   └── springframework/
│       └── boot/
│           └── loader/
│               └── ... (Boot launcher/loader classes)
└── BOOT-INF/
    ├── classes/
    │   ├── com/
    │   │   └── example/
    │   │       └── catalog/
    │   │           ├── CatalogApplication.class
    │   │           ├── service/
    │   │           └── web/
    │   ├── application.yml
    │   ├── static/
    │   └── templates/
    ├── lib/
    │   ├── spring-boot-....jar
    │   ├── spring-context-....jar
    │   ├── spring-web-....jar
    │   └── ... other runtime dependencies
    ├── classpath.idx       (may be present)
    └── layers.idx          (may be present)
~~~

Exact names and index files depend on the Spring Boot version, plugin type, and build configuration. The tree above is a structural reading model, not a fixed list for every project.

### 5.1. BOOT-INF/classes

Contains:

- `.class` files compiled from the application itself.
- Resources from `src/main/resources` after resource processing.
- `application.yml`, templates, and static resources if packaged.
- Other classpath resources belonging to the application.

Example:

~~~text
src/main/java/com/example/catalog/CatalogApplication.java
    -> BOOT-INF/classes/com/example/catalog/CatalogApplication.class

src/main/resources/application.yml
    -> BOOT-INF/classes/application.yml

src/main/resources/templates/invoice.html
    -> BOOT-INF/classes/templates/invoice.html
~~~

These remain **classpath** resources, not standalone physical file paths sitting next to the executable JAR on disk.

### 5.2. BOOT-INF/lib

Contains the dependency JARs used at runtime and selected for packaging by the build plugin.

Example:

~~~text
BOOT-INF/lib/spring-boot-3.x.y.jar
BOOT-INF/lib/spring-core-6.x.y.jar
BOOT-INF/lib/jackson-databind-2.x.y.jar
BOOT-INF/lib/tomcat-embed-core-....jar
~~~

The names/versions in the example are illustrative, not a verified compatible set of dependencies.

Each dependency is a **JAR nested inside the main JAR**, rather than unpacking all library classes into a single shared directory.

### 5.3. Boot Loader Classes

The launcher/loader classes are part of the executable archive and are placed in a structure that the Java launcher can load when reading `Main-Class`. In newer Boot versions, the Java package usually uses `org.springframework.boot.loader.launch`; in older versions, the package may differ.

The Boot loader constructs the classpath from `BOOT-INF/classes` and the libraries under `BOOT-INF/lib`. It is not business code and generally does not need modification.

### 5.4. classpath.idx and layers.idx

Some executable JARs also include:

- `BOOT-INF/classpath.idx`: describes the classpath order used by the launcher in applicable scenarios.
- `BOOT-INF/layers.idx`: describes how the archive contents are layered so container packaging tools can optimize caching/layers.

These files are **not** where source code or dependency bytecode lives. They are auxiliary metadata. Do not manually add or edit them without a specific packaging pipeline reason.

## 6. Why Use Nested JARs Instead of Unpacking All Dependencies?

There are several ways to bundle libraries into a single artifact:

| Artifact type | Layout | Distinguishing characteristic |
|---|---|---|
| Plain JAR | Application classes/resources | Usually does not contain all runtime dependencies |
| Spring Boot executable JAR | `BOOT-INF/classes`, `BOOT-INF/lib/*.jar`, and launcher | Keeps libraries as nested JARs |
| Shaded/uber JAR | Unpacks and merges multiple dependency classes into a single archive namespace | Requires handling duplicate files, resources/services, and relocation when needed |

A Spring Boot executable JAR is often called a **fat JAR**, though it is not necessarily a shaded JAR.

Advantages of the nested JAR layout:

- Packages the application and dependencies into a single artifact.
- Does not require deployment scripts to list dozens of JARs on `-cp`.
- Keeps individual dependencies as separate archives.
- Supports a launcher and metadata for running in standard environments.
- Enables layered archives to improve container image builds.

Limitations/characteristics to remember:

- Some tools that read the classpath directly may not understand the nested JAR layout if not designed for it.
- Not every library or custom class loading mechanism is compatible if it assumes every JAR is a separate file on the filesystem.
- The archive is larger than a plain JAR because it includes dependencies and the loader.
- The appropriate plugin/version must be used to produce the correct format.

## 7. What Does java -jar Actually Do?

The command:

~~~bash
java -jar catalog-service.jar
~~~

triggers the following sequence:

~~~text
1. JVM opens the JAR
         |
         v
2. Reads META-INF/MANIFEST.MF
         |
         v
3. Loads Main-Class (Boot JarLauncher)
         |
         v
4. Launcher reads the BOOT-INF/ structure
         |
         v
5. Creates class loader for application classes + nested libraries
         |
         v
6. Loads Start-Class (CatalogApplication)
         |
         v
7. Invokes CatalogApplication.main(args)
         |
         v
8. SpringApplication.run(...)
         |
         v
9. Creates ApplicationContext, auto-configuration, embedded server...
~~~

This is a conceptual flow, not the exact internal classes/methods of the loader across all versions.

### 7.1. Why Can't -cp Replace the Boot Loader?

The standard Java launcher does not turn `BOOT-INF/lib/*.jar` files into classpath entries just because they appear inside a ZIP.

A command such as:

~~~bash
java -cp catalog-service.jar com.example.catalog.CatalogApplication
~~~

is not the default way to run a Spring Boot executable JAR with the `BOOT-INF` layout. Application classes are not at the root classpath of the JAR, and nested libraries are not listed on the standard Java classpath.

**The right way:** use `java -jar` to invoke the Boot launcher, or run from an IDE/build tool using the classpath it constructs.

### 7.2. JVM Options and Application Arguments

Example:

~~~bash
java -Xms256m -Xmx1g -Duser.timezone=UTC \
     -jar catalog-service.jar \
     --spring.profiles.active=prod \
     --server.port=8081
~~~

Distinction:

- `-Xms256m`, `-Xmx1g`, `-Duser.timezone=UTC`: JVM options, placed **before** `-jar`.
- `--spring.profiles.active=prod` and `--server.port=8081`: arguments passed to the `main(args)` method and typically processed by Spring Boot as command-line properties.

If running the command on Windows PowerShell, the equivalent example can be written on a single line to avoid line-continuation syntax differences across shells.

### 7.3. Does Running on a Server Require Maven/Gradle?

No. A complete executable JAR can run with a compatible Java runtime using `java -jar`; the deployment server does not need Gradle or Maven just to invoke the application.

However, the server still needs:

- A Java runtime/JDK compatible with the Spring Boot version and bytecode.
- Environment configuration and credentials.
- Permissions to read the JAR, network, filesystem, and related resources.
- Databases, brokers, and external services if the application depends on them.

For Spring Boot 3, the typical minimum Java baseline is **Java 17**. Other Boot release lines have their own baselines and compatibility matrices; you must verify Java runtime compatibility when upgrading.

## 8. Where Do Dependencies Come From?

A Spring Boot project does not decide library versions by itself based on imported package names. It uses the dependency graph generated by Maven or Gradle from the build configuration, including direct and transitive dependencies.

Gradle Groovy DSL example:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
    runtimeOnly 'org.postgresql:postgresql'

    compileOnly 'org.projectlombok:lombok'
    annotationProcessor 'org.projectlombok:lombok'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
~~~

This is a dependencies configuration snippet, assuming the project has already applied the appropriate Spring Boot plugin and version management mechanism.

Meaning:

| Gradle configuration | Typical meaning |
|---|---|
| `implementation` | Required for compilation and runtime |
| `api` in `java-library` | Exposes the API dependency to consumers when appropriate |
| `runtimeOnly` | Not needed as a compile-time API in application code, but required at runtime |
| `compileOnly` | Needed only at compile time; not automatically included in the runtime classpath |
| `annotationProcessor` | Used during annotation processing at build time |
| `testImplementation` / `testRuntimeOnly` | Used for testing; not included as application runtime dependencies |

The Spring Boot packaging task typically relies on the runtime classpath and related packaging rules to include the required libraries in the executable JAR.

### 8.1. Transitive Dependencies

When declaring:

~~~groovy
implementation 'org.springframework.boot:spring-boot-starter-web'
~~~

the starter can bring in multiple dependencies such as Spring MVC, JSON support, and an appropriate embedded servlet container. You do not need to declare each library manually if the starter and dependency management already handle them.

However, **a dependency present in the IDE is not guaranteed to be present in the executable JAR** if it only belongs to a test/compile-only configuration or was excluded by packaging rules.

### 8.2. Do Not Pin Arbitrary Versions for Individual Spring Libraries

Spring Boot dependencies are normally managed as compatible versions through the Boot parent/BOM or corresponding dependency management mechanism. Manually overriding a core library without checking compatibility can allow the build to succeed while causing `NoSuchMethodError`, `NoClassDefFoundError`, or erratic behavior at runtime.

When upgrading a library is needed, inspect the final dependency graph and the dependency management of the exact Boot release line in use.

## 9. Packaging with Gradle: bootJar vs. jar

In a Gradle project using the Spring Boot plugin, related tasks typically include:

- `compileJava`: compiles source code.
- `processResources`: processes/copies resources.
- `classes`: combines compilation and resource outputs.
- `jar`: builds a regular Java archive.
- `bootJar`: builds the **Spring Boot executable JAR**.
- `bootRun`: runs the application using the classpath in the build environment.
- `build`: executes the build lifecycle consisting of the relevant tasks.

Example application configuration with the Spring Boot plugin applied:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot'
}

springBoot {
    mainClass = 'com.example.catalog.CatalogApplication'
}

tasks.named('bootJar') {
    archiveFileName = 'catalog-service.jar'
}
~~~

This is a **fragment**, assuming the Spring Boot plugin version is already specified via plugin management or root project configuration. In a standalone project, proper version/plugin repositories are still required.

Package:

~~~bash
./gradlew clean bootJar
~~~

Illustrative output:

~~~text
build/libs/catalog-service.jar
~~~

Run:

~~~bash
java -jar build/libs/catalog-service.jar
~~~

### 9.1. Why Are There Two JAR Files in build/libs?

Many plugin versions can generate both:

~~~text
catalog-service.jar
catalog-service-plain.jar
~~~

`catalog-service.jar` can be the executable JAR produced by `bootJar`; `catalog-service-plain.jar` is the plain archive from `jar` according to that version's plugin configuration convention.

Do not rely blindly on file names when build scripts customize archive classifiers. Inspect the **manifest and file structure** to determine which artifact runs with `java -jar`.

### 9.2. bootRun Does Not Verify the Executable Archive

~~~bash
./gradlew bootRun
~~~

runs the application using the classpath managed by Gradle. It is useful for development, but it **does not prove** that `bootJar` will have the right manifest, dependencies, and layout.

If the goal is to verify the release artifact, you must inspect and run the exact file produced by `bootJar`.

### 9.3. Does a Library Project Need bootJar?

If a module only provides a shared Java library and has no application entry point, a plain JAR is usually more appropriate than a Spring Boot executable JAR.

Do not force every module in a multi-module build to produce an executable archive. An `application` module can use `bootJar`, while `domain`, `common`, or `client-sdk` modules produce normal library JARs that are then pulled into the application's runtime dependency graph.

## 10. Packaging with Maven: spring-boot-maven-plugin repackage

With Maven, Java source code is typically compiled and packaged via the lifecycle:

~~~bash
./mvnw clean package
~~~

To turn a regular archive into a Spring Boot executable JAR, you can use `spring-boot-maven-plugin` with the `repackage` goal.

Example fragment in `pom.xml`:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
            <executions>
                <execution>
                    <goals>
                        <goal>repackage</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>
~~~

For projects inheriting from `spring-boot-starter-parent`, the plugin execution or defaults may already be configured by the parent's conventions. Do not add a duplicate execution without checking the project's effective configuration.

After `package`, the executable archive is typically located at:

~~~text
target/catalog-service-<version>.jar
~~~

In some repackage configurations, Maven may preserve the original JAR with a suffix such as `.original`. This helps distinguish the pre-repackage archive from the executable archive.

### 10.1. Maven Scopes Affect Dependency Packaging

Maven uses scopes such as `compile`, `runtime`, `test`, `provided`, and the `optional` flag. These scopes affect the dependency graph and how the packaging plugin selects libraries.

Notes:

- `test` dependencies are not runtime libraries for the released application.
- `provided` has specific semantics and its handling in executable JARs vs. WARs may differ; do not infer solely from the scope name that every `provided` file is excluded in every packaging layout.
- `optional` affects how a dependency is propagated transitively to consuming projects; it is not a simple toggle meaning "do not package into the artifact currently being built".
- For an executable WAR, there may be a `WEB-INF/lib-provided` directory for dependencies needed only when running with an embedded container.

Inspect the actual archive and plugin configuration instead of relying on a simplified scope table applied to every archive type.

## 11. Cases with Multiple Main Classes

A project may contain multiple classes:

~~~java
public class CatalogApplication {
    public static void main(String[] args) { /* ... */ }
}
~~~

~~~java
public class MigrationTool {
    public static void main(String[] args) { /* ... */ }
}
~~~

If the packaging plugin cannot unambiguously determine the main class, the build may fail or pick an unexpected entry point depending on configuration and version.

You should declare it explicitly for the application artifact.

With Gradle:

~~~groovy
springBoot {
    mainClass = 'com.example.catalog.CatalogApplication'
}
~~~

Or set it on the `bootJar` task when selecting the main class for a specific task:

~~~groovy
tasks.named('bootJar') {
    mainClass = 'com.example.catalog.CatalogApplication'
}
~~~

With the Maven plugin, you can specify the main class in the plugin configuration:

~~~xml
<configuration>
    <mainClass>com.example.catalog.CatalogApplication</mainClass>
</configuration>
~~~

After packaging, check `Start-Class` in the manifest to confirm the artifact's actual entry point.

**Do not confuse:** the Java application main class setting for another tool/plugin and the main class setting used by the Spring Boot packaging task may be related, but they are not always the same in every customized configuration.

## 12. How to Inspect the Executable JAR Structure

The JDK provides the `jar` tool to list contents:

~~~bash
jar tf build/libs/catalog-service.jar
~~~

To filter key paths in PowerShell:

~~~powershell
jar tf build/libs/catalog-service.jar |
    Select-String 'MANIFEST.MF|BOOT-INF/classes|BOOT-INF/lib|JarLauncher|layers.idx'
~~~

Example entries you might see:

~~~text
META-INF/MANIFEST.MF
org/springframework/boot/loader/launch/JarLauncher.class
BOOT-INF/classes/com/example/catalog/CatalogApplication.class
BOOT-INF/classes/application.yml
BOOT-INF/lib/spring-boot-3.x.y.jar
BOOT-INF/lib/spring-context-6.x.y.jar
~~~

The `JarLauncher.class` line here assumes Spring Boot with a loader package like `org.springframework.boot.loader.launch`. Archives from older versions may have a different path.

### 12.1. Reading the Manifest

If the environment has `unzip`:

~~~bash
unzip -p build/libs/catalog-service.jar META-INF/MANIFEST.MF
~~~

In an environment with only the JDK `jar` tool, you can extract into a temporary directory and read `META-INF/MANIFEST.MF`—avoid extracting over a source code folder containing identically named files.

Example lines to look for:

~~~text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.catalog.CatalogApplication
Spring-Boot-Classes: BOOT-INF/classes/
Spring-Boot-Lib: BOOT-INF/lib/
~~~

Clarification:

- If there is no suitable `Main-Class`, `java -jar` does not know the entry point.
- If `Main-Class` is the Boot launcher but `Start-Class` is wrong, the launcher may fail to load the application main class.
- If loader classes or dependency JARs are missing, the archive may have been packaged incorrectly or corrupted by another tool.

### 12.2. Checking Whether a Dependency Is Inside the JAR

~~~powershell
jar tf build/libs/catalog-service.jar |
    Select-String 'BOOT-INF/lib/'
~~~

If the application encounters `ClassNotFoundException` when running the JAR, cross-check the missing class against the required dependency and the actual archive. Seeing a dependency in the Gradle/Maven cache does not guarantee it is included in the executable archive.

### 12.3. Checking Resources

~~~powershell
jar tf build/libs/catalog-service.jar |
    Select-String 'BOOT-INF/classes/application'
~~~

If code uses `classpath:application.yml` or `classpath:templates/invoice.html`, check whether the resource was copied to the proper location under `BOOT-INF/classes`.

## 13. Spring Boot Loader and Class Loading

A standard Java classpath points to:

- Directories containing class files.
- One or more JAR files accessible as separate archives.

Nested JARs, by contrast, reside **inside** the Spring Boot archive:

~~~text
catalog-service.jar
  └── BOOT-INF/lib/dependency-a.jar
  └── BOOT-INF/lib/dependency-b.jar
~~~

The Spring Boot launcher/loader is designed to load classes and resources in this layout. Exact class loading rules depend on the Boot loader implementation per version, but the operational takeaway is: **there is no need to unpack all dependencies into a folder just to run the application**.

### 13.1. Custom Class Loaders May Encounter Differences

Some older libraries assume that a resource URL always maps to a real file on disk—for example, forcing it into a `java.io.File`:

~~~java
File file = new File(
        getClass().getResource("/config/template.txt").toURI()
);
~~~

This code may work from the resources directory in an IDE but fail when the resource resides inside a JAR or nested archive.

Instead of requiring a resource to be a physical file, use a stream API when you only need to read its contents:

~~~java
try (InputStream input = getClass()
        .getResourceAsStream("/config/template.txt")) {

    if (input == null) {
        throw new IllegalStateException("Template not found");
    }

    byte[] bytes = input.readAllBytes();
    // Process bytes...
}
~~~

With Spring, you can use `ResourceLoader` and `Resource.getInputStream()`. If a library strictly requires a physical file, you may need to copy the resource to a temporary file with appropriate lifecycle/permissions, rather than assuming every classpath resource has a direct File path.

### 13.2. Boot's Classloader Does Not Solve Every Dependency Conflict

The loader can locate nested JARs, but it does not automatically fix issues such as:

- Two incompatible versions of a library.
- A dependency missing from the runtime classpath.
- Duplicate classes/resources from different dependencies.
- A library calling an API that changed in another version.

These issues still need to be resolved in the dependency graph/build configuration.

## 14. Location of application.yml and Externalized Configuration

In an executable JAR, the file:

~~~text
src/main/resources/application.yml
~~~

typically becomes:

~~~text
BOOT-INF/classes/application.yml
~~~

Spring Boot can read resources from the classpath via the loader. However, in production deployments, you should not modify the JAR contents every time you want to change a port or database URL.

Example of running with configuration external to the artifact:

~~~bash
java -jar catalog-service.jar \
     --spring.profiles.active=prod \
     --server.port=8081
~~~

Or providing properties via the environment:

~~~text
SPRING_PROFILES_ACTIVE=prod
SERVER_PORT=8081
DB_PASSWORD=<value provided by secret store>
~~~

These are example environment variable names and a descriptive placeholder, containing no real secrets.

**Separate code packaging from operational configuration:**

- Application classes and dependencies are generally fixed per artifact build.
- Externalized configuration can vary across deployments.
- Secrets should not be hard-coded in an `application.yml` packaged inside the JAR.

An executable JAR does not mean every resource, credential, database, or remote service the application needs is already inside that file.

## 15. Boot JAR vs. Executable WAR

Spring Boot can also package an application as a WAR, for example when deploying to an external servlet container.

Typical WAR layout:

~~~text
catalog-service.war
├── META-INF/
├── WEB-INF/
│   ├── classes/
│   ├── lib/
│   └── lib-provided/    (may be present)
└── org/springframework/boot/loader/... (when executable)
~~~

Comparison:

| Characteristic | Executable JAR | Executable WAR |
|---|---|---|
| Application classes | `BOOT-INF/classes` | `WEB-INF/classes` |
| Main dependencies | `BOOT-INF/lib` | `WEB-INF/lib` |
| Loader | JarLauncher (when using default launcher) | WarLauncher (when executable) |
| Common purpose | Standalone execution via `java -jar` | Standalone execution or servlet container deployment depending on config |
| Embedded server | Usually packaged per starter/runtime | Needs proper configuration for external container if deployed as WAR |

In Spring Boot 3.2+, the launcher package is for example `org.springframework.boot.loader.launch.WarLauncher`; older versions may use a different name.

For a WAR to be deployable into an external container, the application may need to extend `SpringBootServletInitializer` and configure the servlet container dependency scope appropriately.

**Do not confuse:** a traditional WAR generated by Maven/Gradle is not necessarily an executable WAR. Likewise, a plain JAR does not automatically become an executable Boot JAR simply by having an application main class.

## 16. Layered JARs and Docker Image Packaging

When deploying Spring Boot in a container, the executable JAR is often copied into the image:

~~~dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app

COPY build/libs/catalog-service.jar app.jar

ENTRYPOINT ["java", "-jar", "/app/app.jar"]
~~~

The base image example above fits the Java baseline for many Spring Boot 3 applications, though the actual image/tag must be chosen according to the Boot version, target platform, and project security policy.

This approach is simple: the container holds the Java runtime and the executable JAR. However, whenever application classes change, the entire JAR file can change, forcing the layer containing it to be rebuilt and pushed again.

### 16.1. layers.idx for Cache Optimization

Spring Boot packaging supports layered archives in applicable versions/configurations. The `BOOT-INF/layers.idx` file describes groups of contents that can be split into separate Docker layers.

Default groups typically revolve around:

- Rarely changing dependencies.
- Snapshot dependencies that may change more frequently.
- The Spring Boot loader.
- Application classes/resources.

Conceptual example:

~~~text
dependencies
spring-boot-loader
snapshot-dependencies
application
~~~

When application source changes while dependencies stay the same, the dependencies layer can be reused in container build workflows that support layered extraction.

### 16.2. Do Not Equate layers.idx with the Runtime Classpath

`layers.idx` serves packaging/layer tooling; the launcher still needs to load application classes and dependencies according to the executable archive layout or according to how the image has been extracted/configured.

Do not manually edit `layers.idx` to fix a `ClassNotFoundException`. Check the dependency graph and archive layout first.

### 16.3. jarmode layertools Is Version-Dependent

Some Spring Boot versions provide a jarmode/layer tooling mechanism to list and extract layers from an executable archive. Commands and availability vary across Boot release lines, especially as packaging/build-image workflows evolve.

Therefore, follow the documentation for **the exact Boot version** and verify whether the artifact supports that jarmode/layer extraction. Do not copy a command from Boot 2 or 3 into a newer project assuming the syntax remains identical.

Spring Boot build plugins can also support building container images directly using buildpacks. This is an alternative to a hand-written Dockerfile; it does not change the underlying nature of `Main-Class` and `Start-Class` inside the executable JAR.

## 17. Can a JAR File Be Executed Directly as an OS Program?

The standard, widely compatible command is:

~~~bash
java -jar catalog-service.jar
~~~

Some packaging mechanisms on Unix/Linux environments support a **fully executable archive** by prepending a launch script to the JAR file. When configured this way and given execute permissions, it can be invoked directly like a program:

~~~bash
./catalog-service.jar
~~~

However, that is a specialized packaging mode, not a default property of every executable JAR. Moreover, some ZIP/JAR tools do not handle archives with a prepended launch script well.

If there is no specific need to run directly as a script/service, `java -jar` is usually more predictable and less environment-dependent.

## 18. Why Does the Application Run in the IDE but the JAR Fails?

Several common causes:

### 18.1. Running the Plain JAR by Mistake

You may see:

~~~text
no main manifest attribute, in catalog-service-plain.jar
~~~

A plain JAR typically lacks the Boot launcher manifest. Use the artifact from `bootJar` (Gradle) or the `repackage` artifact (Maven); do not try to "fix it by renaming the file".

### 18.2. Wrong Main-Class or Start-Class

If the project has multiple main classes or build customizations cause confusion, the manifest may point to the wrong class.

Check:

~~~text
Main-Class: ...
Start-Class: ...
~~~

In a Spring Boot executable JAR, `Main-Class` must be the launcher matching the packaged loader, while `Start-Class` must be the desired main application class.

### 18.3. Missing Dependency

If at runtime you see:

~~~text
java.lang.NoClassDefFoundError: com/vendor/client/Client
~~~

check whether the dependency containing that class was on the runtime classpath at build time and whether it was packaged into `BOOT-INF/lib`.

A library declared only as `compileOnly` or `testImplementation` is not a runtime dependency under standard configurations.

### 18.4. Version Conflict

You may encounter `NoSuchMethodError` even though the class exists. One cause is running with a different library version than the one compiled against, or a dependency requiring an incompatible API.

Inspect Gradle/Maven dependency resolution, dependency constraints, and overridden dependencies. Do not immediately blame the Boot loader when the root cause is a version conflict.

### 18.5. Incompatible Java Runtime

Example error:

~~~text
UnsupportedClassVersionError
~~~

The bytecode was compiled for a newer Java version than the active runtime, or the runtime does not meet the Spring Boot/framework baseline.

Compare:

~~~bash
java -version
~~~

with the build toolchain, target release, and Spring Boot version.

### 18.6. Resources Accessed as Physical Files

Code using `new File(resource.getURI())` can work in the IDE and fail in a JAR because the resource lives inside the archive.

Use stream abstractions such as `ClassLoader.getResourceAsStream(...)` or Spring `Resource`, unless the target library strictly requires a real file.

### 18.7. Component Scan on the Wrong Package

The JAR starts up, but services/controllers are not registered because the `@SpringBootApplication` class is in the wrong root package or a module's configuration was not imported.

This is a context composition issue, not a `Main-Class` issue.

### 18.8. Port, Database, or Secret Not Ready

The executable JAR may be packaged properly, yet the application still fails because:

- The port is already in use.
- The database cannot be reached.
- An environment variable/secret is missing.
- An external configuration file does not exist.
- Filesystem permissions are insufficient.

Distinguish **archive build errors**, **class loading errors**, and **application context startup errors** to troubleshoot at the right layer.

## 19. Packaging and Startup Troubleshooting Table

| Symptom | Layer to inspect | Action |
|---|---|---|
| `no main manifest attribute` | Manifest/artifact type | Confirm you are using the bootJar/repackaged JAR |
| `Could not find or load main class ...JarLauncher` | Manifest and loader classes | Check launcher class/path and whether the archive was modified/corrupted |
| `ClassNotFoundException` for an application class | Start-Class and BOOT-INF/classes | Check compiled classes, package, and manifest |
| `NoClassDefFoundError` for a dependency | BOOT-INF/lib/runtime classpath | Check dependency scopes and exclusions |
| `NoSuchMethodError` | Dependency compatibility | Check resolved versions and transitive dependency conflicts |
| `UnsupportedClassVersionError` | JVM/toolchain | Use a Java runtime supporting the bytecode and Boot version |
| Resource readable in IDE but missing in JAR | processResources and BOOT-INF/classes | Check source resource path and classpath reading logic |
| `BeanCreationException` / `UnsatisfiedDependencyException` | Spring context/bean definitions | Check component scan, auto-configuration, and dependency injection |
| Server not listening on expected port | Runtime config/embedded server | Check `server.port`, profiles, and startup errors |
| Wrong main class executed | Start-Class | Specify mainClass and inspect the manifest |
| Valid JAR but Docker container exits | Runtime/container environment | Check JVM, entrypoint, ports, env, logs, and external services |
| File too large or contains unneeded dependencies | Build dependency graph | Exclude unnecessary transitive dependencies deliberately |
| Archive has `BOOT-INF/lib` but launched with `java -cp` | Launch strategy | Use `java -jar` to run via the Boot launcher |

## 20. Inspecting the Maven and Gradle Dependency Graph

Before packaging, or when investigating runtime errors, inspect dependency resolution using the build tool commands.

Gradle:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
~~~

To inspect a specific dependency:

~~~bash
./gradlew dependencyInsight \
    --configuration runtimeClasspath \
    --dependency spring-core
~~~

Maven:

~~~bash
./mvnw dependency:tree
~~~

These commands show the graph resolved by the build tool. However, to verify the **release artifact**, you still need to compare against the actual JAR list inside `BOOT-INF/lib`. Custom packaging settings, task exclusions, and artifact transformations can alter the final output.

### 20.1. Does Every Dependency Need to Be Packaged in the JAR?

Not every dependency across the whole project needs to be inside the runtime artifact:

- Unit-test libraries do not need to be present in the production JAR.
- Annotation processors are build-time tools, not typical runtime dependencies.
- Compile-only dependencies should not be assumed present at runtime.
- Embedded server dependencies depend on the application type and JAR/WAR packaging.
- A dependency provided by an external container may require different packaging.

The goal is to include **precisely the libraries required** to run the artifact under the chosen deployment model, not to stuff every library in the repository into one large ZIP.

## 21. Security and Operations of Executable JARs

An executable JAR is an artifact containing bytecode, resources, and dependencies. Therefore, it must be treated as part of the software supply chain.

### 21.1. Do Not Put Secrets in Application Resources

If you put a password in:

~~~text
src/main/resources/application-prod.yml
~~~

it can end up under:

~~~text
BOOT-INF/classes/application-prod.yml
~~~

inside the released JAR. Anyone with access to the JAR file can typically list and extract its contents. **A JAR is not an encrypted secret store**.

Provide secrets from the environment, mounted secret files, or a secret manager according to deployment policy.

### 21.2. Track Dependency Versions

Each nested JAR is a versioned dependency that may contain security vulnerabilities. You should have:

- A dependency update policy.
- Appropriate vulnerability/dependency scanning checks.
- Control over trusted artifact sources and repositories.
- A reasonably reproducible build process.
- Recorded version and provenance information at release time.

File names in `BOOT-INF/lib` can help identify versions, but for some renamed or repackaged JARs, combine this with the dependency graph and build metadata to determine exact components.

### 21.3. Do Not Manually Modify the JAR After Building

Manually editing the manifest or adding JARs to `BOOT-INF/lib` after building can break indexes, signatures, checksums, or reproducibility.

If you need to add a dependency or change the main class, update the build configuration and rebuild the archive with the appropriate plugin. Direct artifact modification should only be used in specialized scenarios with clear engineering controls.

## 22. Release Flow from Source to Runtime

You can use this overall diagram:

~~~text
Source code + application resources
                  |
                  v
Maven / Gradle resolves dependencies
                  |
                  v
Compile main application classes
                  |
                  v
Process resources
                  |
                  v
Spring Boot packaging plugin
                  |
       +----------+-----------+
       |                      |
       v                      v
META-INF/MANIFEST.MF      Executable JAR layout
 Main-Class=Launcher        BOOT-INF/classes
 Start-Class=App            BOOT-INF/lib
       |                      |
       +----------+-----------+
                  |
                  v
        catalog-service.jar
                  |
                  v
        java -jar catalog-service.jar
                  |
                  v
             Boot launcher
                  |
                  v
       CatalogApplication.main
                  |
                  v
         SpringApplication.run
                  |
                  v
          ApplicationContext
                  |
                  v
         Web server / runners
~~~

An artifact verification workflow can follow this order:

1. Identify the main class the application intends to run.
2. Check the build plugin that creates the executable archive.
3. Check the archive filename and artifact type.
4. Read the manifest: `Main-Class` and `Start-Class`.
5. List `BOOT-INF/classes` and `BOOT-INF/lib`.
6. Run with a compatible Java runtime.
7. Verify runtime configuration and startup outcome.
8. Use appropriate logs/health checks to confirm the application is ready.

This verification STEP illustrates the workflow for learners; it does not require every project to re-run the entire pipeline while reading the documentation.

## 23. Common Misconceptions

| Misconception | Accurate understanding |
|---|---|
| "`@SpringBootApplication` automatically creates the executable JAR." | The annotation configures bootstrapping; the build plugin creates the archive. |
| "`Main-Class` must be the class with `@SpringBootApplication`." | In a typical Boot executable JAR, `Main-Class` is the Boot launcher; `Start-Class` is the application main. |
| "`java -jar` natively reads all nested JARs." | The Boot launcher/loader handles nested dependencies; the standard Java classpath does not. |
| "Having a JAR guarantees it runs standalone." | A plain JAR may lack a main manifest or dependencies. |
| "`bootRun` succeeding means `bootJar` is definitely correct." | The two execution modes use different classpath/artifact mechanisms. |
| "All dependencies in the IDE are inside `BOOT-INF/lib`." | It depends on scope, runtime graph, and packaging configuration. |
| "The `application.yml` file sits next to the JAR." | Packaged files usually live inside `BOOT-INF/classes`; external config is a separate source. |
| "A JAR protects passwords because the source cannot be read." | A JAR is an archive that can be listed/extracted, not a secret store. |
| "Renaming a plain JAR to app.jar will make it run." | File names do not create a loader, manifest, or nested dependencies. |
| "Every Spring Boot project needs an executable WAR." | An executable JAR is usually the simpler choice for standalone applications. |

## 24. Key Principles to Remember

1. The **main method** is the application's Java entry point, typically calling `SpringApplication.run(...)`.
2. The **manifest** is metadata telling the Java launcher which class to run first.
3. In a **Spring Boot executable JAR**, `Main-Class` is usually the Boot launcher, while `Start-Class` is the application's main class.
4. `BOOT-INF/classes` holds application bytecode and resources; `BOOT-INF/lib` holds nested runtime JARs.
5. The **Boot loader** is the component bridging the Java launcher to the nested dependencies layout.
6. `bootJar` (Gradle) or `spring-boot-maven-plugin:repackage` (Maven) produces the executable archive; plain `jar` may produce a plain JAR.
7. The **runtime dependency graph** determines which libraries are packaged according to plugin/configuration; test and compile-only dependencies should not be assumed to be runtime.
8. Use `java -jar` for executable archives, not `java -cp app.jar ApplicationMain` as a direct substitute.
9. When multiple main classes exist, **explicitly specify mainClass** and verify `Start-Class` in the manifest.
10. Inspect the **actual archive** using `jar tf`, the manifest, and the `BOOT-INF/lib` listing; do not rely solely on file names.
11. **Plain JARs, executable JARs, shaded JARs, and WARs** have different layouts and purposes.
12. Classpath resources inside a JAR generally cannot be used directly as `java.io.File`; prefer streams/`Resource`.
13. **A JAR does not safely store secrets simply because it is compressed**; use externalized configuration and secret injection.
14. If startup fails, clearly distinguish manifest/launcher errors, missing dependencies, Java version mismatches, and Spring context errors.

**Conclusion:** To understand how Spring Boot runs outside the IDE, view the executable JAR as a bundle containing **the application main class, a manifest directing the JVM, the Boot loader, and runtime dependencies arranged in dedicated locations**. The JVM reads `Main-Class` to start the launcher; the launcher looks up `Start-Class` and sets up the classpath for `BOOT-INF/classes` and `BOOT-INF/lib`; the application then calls `SpringApplication.run(...)` to build the Spring context. Once you grasp this chain, packaging, deploying, and diagnosing `java -jar` failures become much clearer.
