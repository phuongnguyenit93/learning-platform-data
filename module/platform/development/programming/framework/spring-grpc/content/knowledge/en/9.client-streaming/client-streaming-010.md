# Idempotency when the client resends a batch

**Chapter:** Client streaming  
**Scope:** Spring gRPC (SPRING_GRPC), Protocol Buffers contracts, generated Java code, and RPCs receiving multiple requests and returning one response.

## 1. The problem: the client does not know if the previous send succeeded

A client sends a batch of 500 records. The server receives all of them, writes the data, and commits the transaction. Right after committing, the connection drops before the UploadReceipt reaches the client. The client only sees UNAVAILABLE or DEADLINE_EXCEEDED; it does not know whether the server persisted the data.

If the client resends the whole batch with a new identifier, the server may write 500 duplicate records. If the client does not resend, data may be missing if the first attempt never committed. This is the classic **uncertain outcome** when an RPC has side effects.

**Idempotency** ensures an operation can be sent multiple times without producing additional side effects beyond the logical result of the first execution. For client streaming, you need a stable batch identifier, content recognition, per-item deduplication, and persistence of the final receipt to replay when the client retries.

Typical flow:

1. Client sends batch B42.
2. Server persists data and commits B42.
3. The response is lost before the client receives the receipt.
4. Client retries with the same B42 and identical content.
5. Server finds B42 is already COMMITTED and returns the stored receipt without committing again.

Desired outcome: the server does not write data a second time; the client receives the same stored receipt. **Retrying the same batch must preserve both the idempotency key and the batch content.**

## 2. A stable batch_id is necessary, but not sufficient

The client generates batch_id **once before the first send** and retains it until the final outcome is known. When retrying due to a timeout or network drop, the client reuses that exact ID.

Having only batch_id is not enough to distinguish:

- An exact retry of the same batch and payload.
- A client accidentally reusing an ID for a different payload.
- Two concurrent sends with the same ID but different data.
- A retry sending only part of the batch or changing chunk order.

Therefore, the batch identifier must be bound to an **immutable manifest** describing the expected content:

| Attribute | Role |
| --- | --- |
| batch_id | Stable idempotency key generated by the client |
| expected_chunks | Expected number of chunks in the batch |
| content_sha256 | Hash of the batch content in the defined order |
| sequence | Stable position of each chunk, e.g., 0 to N-1 |
| chunk_sha256 | Hash of each chunk payload to detect duplicate sequence with differing content |

The key scope on the server is typically **tenant/owner + batch_id**, not just a global batch_id. The tenant must come from the authenticated identity rather than trusting a self-reported tenant field in protobuf.

If the same idempotency key arrives with a different manifest, the server must reject it instead of silently treating it as a valid retry.

## 3. Designing a streaming contract with a manifest

One representation has the first message declare the batch and subsequent messages carry chunks:

    syntax = "proto3";
    package ingest.v1;
    option java_package = "com.example.ingest.grpc";
    option java_multiple_files = true;

    service BatchUploadService {
      rpc Upload(stream UploadRequest) returns (UploadReceipt);
    }

    message UploadRequest {
      oneof body {
        BatchStart start = 1;
        BatchChunk chunk = 2;
      }
    }

    message BatchStart {
      string batch_id = 1;
      uint32 expected_chunks = 2;
      bytes content_sha256 = 3;
    }

    message BatchChunk {
      uint32 sequence = 1;
      bytes payload = 2;
      bytes chunk_sha256 = 3;
    }

    message UploadReceipt {
      string batch_id = 1;
      uint32 accepted_chunks = 2;
      bytes content_sha256 = 3;
      string committed_record_id = 4;
    }

Contract rules:

1. The first message must be BatchStart; only one manifest is allowed per RPC.
2. Subsequent messages are BatchChunk, each with a unique sequence and a payload matching its hash.
3. The server checks that all expected_chunks arrived, in order, and that the overall hash matches before committing.
4. Success returns exactly one UploadReceipt; errors terminate with a gRPC status.
5. Retries use the same batch_id, expected_chunks, content_sha256, and chunk contents.

The hash must be computed over a **deterministic, canonical** byte representation. For example, the overall hash can be the SHA-256 of chunk payloads concatenated in sequence order; define chunk boundary framing explicitly to avoid ambiguity. Do not hash an arbitrary JSON string if field order, encoding, or serialization can vary across clients.

## 4. Persisting idempotency state durably

Idempotency must survive server restarts. An in-RAM map or observer field is insufficient because the process may stop after committing, or the retry request may hit a different instance.

A simple data model:

| Table | Primary key / constraint | Data |
| --- | --- | --- |
| upload_batch | Unique (tenant_id, batch_id) | Manifest, status, created/updated timestamps, committed receipt |
| upload_chunk | Unique (tenant_id, batch_id, sequence) | Chunk hash, staging payload or staging storage location |
| domain_record | Unique by business/event ID | Committed data, linked back to the batch |

Batch states can be:

    RECEIVING -> COMMITTED
         |
         +----> FAILED / EXPIRED

- **RECEIVING:** manifest registered, server is accepting chunks.
- **COMMITTED:** data and receipt durably committed; successful terminal state.
- **FAILED:** batch cannot proceed under business rules.
- **EXPIRED:** incomplete staging exceeded retention time and was cleaned up per policy.

State transitions must be protected by transactions, unique constraints, or appropriate locking. Never allow two concurrent RPCs to process and commit the same batch along two conflicting paths.

### Rules for accepting batches and chunks

When receiving BatchStart:

1. Authenticate the caller and resolve tenant_id.
2. Find or create upload_batch keyed by (tenant_id, batch_id).
3. If it does not exist yet, create it in RECEIVING state with the manifest.
4. If it already exists, compare manifests. Identical manifest means a retry; a different manifest returns a conflict error.
5. If the status is already COMMITTED, return the stored receipt; the client stops the producer because the work is already done.

When receiving each BatchChunk:

- If sequence does not exist yet, validate sequence, hash, and quota limits, then write to staging.
- If sequence already exists **with the same hash**, treat it as a resend and do not write again.
- If sequence already exists **with a different hash**, reject because the same position has differing content.
- Update progress only after staging data and hash are durably persisted within a transaction.

When receiving inbound onCompleted(), verify expected_chunks are all present and the overall hash matches the manifest. Then commit the domain data, transition the batch to COMMITTED, and store the receipt within the same appropriate transaction boundary. Send the receipt to the client only after the transaction succeeds.

## 5. Handling retries by state

| State when client retries | Server behavior |
| --- | --- |
| Batch ID does not exist yet | Create new batch in RECEIVING if manifest is valid |
| RECEIVING, same manifest | Resume; duplicate chunks with matching hash are no-ops |
| COMMITTED, same manifest | Return the stored receipt; do not commit again |
| Same batch ID but different manifest | Reject with conflict; do not modify existing manifest |
| FAILED or EXPIRED | Apply published policy: require a new batch ID or allow controlled reset |
| Another RPC holds the batch processing lease | Reject/wait per policy; prevent two competing writers |

### Example: first attempt disconnects after chunk 2

Suppose a batch has 5 chunks with sequences 0..4:

1. First attempt stages chunks 0, 1, 2; connection drops before the client finishes.
2. Client retries with the same batch_id and manifest, re-sending chunks 0, 1, 2.
3. Server sees matching sequence and hash, writing no extra duplicates.
4. Client continues sending chunks 3, 4.
5. Client half-closes; server verifies all 5 chunks and overall hash, then commits once.

If chunk 1 on the retry has a different payload, the server must not overwrite the previously accepted chunk. Return a conflict error so the client creates a new batch with a new ID if it actually represents different business data.

## 6. Core layer in Java

Do not embed the entire idempotency policy inside a StreamObserver or a singleton map. Separate durable handling into a service with atomic operations:

    public interface BatchIdempotencyStore {
        BeginResult begin(
                String tenantId, String batchId,
                int expectedChunks, byte[] contentSha256);

        // Same sequence + same hash: no-op.
        // Same sequence + different hash: conflict.
        ChunkResult acceptChunk(
                String tenantId, String batchId,
                int sequence, byte[] payload, byte[] chunkSha256);

        // Verify all chunks/hash, commit, and persist receipt.
        UploadReceipt commit(String tenantId, String batchId);

        UploadReceipt findCommittedReceipt(
                String tenantId, String batchId, byte[] contentSha256);
    }

This is an **illustrative application-layer contract**, not a built-in Spring gRPC API. The implementation must rely on database transactions/unique constraints; never perform an existence check followed by an insert without concurrency protection across requests.

Some server handling branches:

    // When receiving BatchStart:
    BeginResult begin = store.begin(tenantId, batchId, expectedChunks, digest);
    if (begin.isManifestConflict()) {
        responseObserver.onError(Status.ALREADY_EXISTS
            .withDescription("batch_id already bound to a different manifest")
            .asRuntimeException());
        return;
    }
    if (begin.isCommitted()) {
        responseObserver.onNext(begin.receipt());
        responseObserver.onCompleted();
        return;
    }

    // When receiving BatchChunk:
    ChunkResult result = store.acceptChunk(
        tenantId, batchId, sequence, payload, chunkDigest);
    if (result.isConflict()) {
        responseObserver.onError(Status.ALREADY_EXISTS
            .withDescription("sequence already exists with different content")
            .asRuntimeException());
        return;
    }

    // When inbound request onCompleted:
    UploadReceipt receipt = store.commit(tenantId, batchId);
    responseObserver.onNext(receipt);
    responseObserver.onCompleted();

The snippet outlines the main branches; a real implementation must manage observer lifecycle, terminal state, transaction errors, and cancellation. In particular, if the batch is already COMMITTED, the server can return the receipt early as soon as the manifest matches. The client must stop the producer once it receives the completed response and never keep using a closed request observer.

### Synchronization when two retries arrive simultaneously

Two RPCs may share the same batch_id when a client retries too early or another worker also re-sends. A unique constraint prevents creating two batch rows, yet it does not automatically coordinate all chunk writes and commits.

You need one of these mechanisms:

- A lease/lock keyed by (tenant_id, batch_id) so only one active RPC writes the batch at a time.
- Transactions/optimistic versioning to detect contention; the losing request receives ABORTED or an appropriate error and retries per policy.
- A unique constraint on chunk sequence plus hash checking so every repeated write produces a deterministic outcome.

Leases must have an expiration time and a reclamation mechanism if a process crashes; never hold a lock forever because a client lost connectivity.

## 7. Statuses and retry rules

| Scenario | Suggested gRPC status | What the client should do |
| --- | --- | --- |
| Malformed payload or manifest | INVALID_ARGUMENT | Fix data; do not retry as-is |
| Same batch ID with different manifest | ALREADY_EXISTS or FAILED_PRECONDITION per contract | Use a new ID for a batch with new content |
| Same sequence with different hash | ALREADY_EXISTS or FAILED_PRECONDITION | Stop batch; investigate mutated data |
| Batch currently being processed by another RPC | ABORTED or RESOURCE_EXHAUSTED per policy | Wait/check status then retry with same ID |
| Deadline expires or connection drops | DEADLINE_EXCEEDED / UNAVAILABLE | Look up batch status before resending |
| Batch already committed, retry with same manifest | OK with stored receipt | Treat as success; do not reprocess |
| Exceeded message/byte quota | RESOURCE_EXHAUSTED | Split batch per policy; use appropriate IDs for new batches |

Do not retry indefinitely. Use exponential backoff with jitter, cap attempt count, and cap total retry duration. UNAVAILABLE can be transient; INVALID_ARGUMENT generally cannot be fixed by retrying the same payload. For DEADLINE_EXCEEDED, look up status first because the server may have already committed.

## 8. Testing idempotency

Tests must prove that **side effects occur only once**, not merely check that the client received status OK.

| Test case | Expected result |
| --- | --- |
| First send of batch succeeds | One commit and one stored receipt |
| Retry same ID, same manifest after commit | Returns old receipt; record count does not increase |
| Retry same ID with different manifest | Rejected with conflict; committed data unchanged |
| Disconnect after a few chunks then retry same manifest | Duplicate chunks with matching hash are no-ops; remaining chunks continue |
| Same sequence with different payload/hash | Rejected; previously saved chunk is not overwritten |
| Two concurrent RPCs with the same batch ID | Only one writer/commit wins; no duplicated side effects |
| Response lost after commit | Retry/lookup retrieves the stored receipt |
| Staging batch exceeds TTL | Staging cleaned up, status transitions to EXPIRED; no orphaned resources |

Use a real test database or Testcontainers to test unique constraints, transaction rollbacks, and concurrency. Pure mock repositories do not prove atomicity or idempotency under concurrent requests.

## 9. Security and operations

- Scope idempotency keys to the authenticated caller/tenant; prevent other users from guessing batch_id to read receipts.
- Use TLS to protect data in transit; metadata/interceptors can authenticate and attach a correlation ID for the whole RPC.
- Bound message count, per-message size, total batch bytes, concurrent RPCs, and staging retention time.
- Emit metrics for retry count, batches returning cached receipts, manifest conflicts, duplicate chunks, expired batches, and duration from RECEIVING to COMMITTED.
- Do not log sensitive payloads or tokens; log controlled batch IDs and appropriate statuses.
- Run a cleanup job for expired staging; cleanup must be safe alongside active leases or newly committed batches.

## 10. Self-practice

1. Client sends batch B-100, server commits, but the response is lost. Why must the retry reuse both batch_id and the manifest?
2. Two requests arrive with the same batch_id but different content_sha256: what should the server do and why must it not be treated as a valid retry?
3. Server receives chunk sequence 4 again with the same hash. How do you make it a no-op without incrementing the stored chunk count?
4. Two concurrent RPCs retry the same batch. Propose a lease/lock and unique constraints so only one commit occurs.
5. Design a test simulating "commit succeeded, receipt lost, retry returns stored receipt"; which tables or invocation counts should you assert?

**Remember:** Idempotency for client streaming relies on **a stable batch ID + an immutable manifest + chunk recognition + durable commit state**. When a client retries the exact same batch, the server must resume or return the stored receipt without repeating side effects; the same ID with different content must be rejected. Timeouts and lost responses do not prove the server has not committed.
