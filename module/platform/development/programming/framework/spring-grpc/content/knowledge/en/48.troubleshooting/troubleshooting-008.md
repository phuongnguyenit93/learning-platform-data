# RESOURCE_EXHAUSTED Due to Message Size or Quota

`RESOURCE_EXHAUSTED` is a gRPC status code indicating that a required resource has been depleted or a usage limit has been exceeded. In a Spring gRPC service, the error typically appears when a protobuf message exceeds the receive limit, when the client cannot receive a response because it is too large, or when the application rejects requests due to quotas and load limits.

These causes require different fixes. Raising the message size limit will not solve a quota problem; blindly retrying will not help a payload that is already too big. Before fixing, identify which component emitted the status and which limit was reached.

## Identify the Exact Error Source

`RESOURCE_EXHAUSTED` can be generated by the gRPC runtime, an interceptor, the service, or an intermediary component. Record at a minimum:

- The RPC name, RPC type (unary, client streaming, server streaming, or bidirectional streaming), and data direction.
- Status code, description, trailers, and trace/request ID if available.
- Actual message size, the enforced limit, and the component that detected the limit breach.
- Authenticated tenant or principal, quota type, and when the quota resets.

Do not log full payloads, authentication tokens, or sensitive metadata. Message size should be recorded in bytes and measured consistently on both sender and receiver.

| Symptom | High-Probability Source | Resolution Direction |
|---|---|---|
| Large request rejected before service processing | Server or proxy inbound message limit | Shrink/split the request or adjust receiver limit after evaluating memory |
| Server returns large response, client gets `RESOURCE_EXHAUSTED` | Client or gateway inbound message limit | Paginate/split the response or adjust client receive limit |
| Small requests still rejected after several calls | Quota per tenant, user, API, or time window | Check quota policy, call rate, and reset schedule |
| Errors rise as concurrent load rises | Application concurrency, queue, or buffer limit | Shed/limit load, apply backpressure, and check resource capacity |

Note: message size limits are checked on the receiving side. Therefore, inspect the exact receiver's configuration: the server receiving requests, the client receiving responses, and any proxy/gateway along the RPC path. Metadata size limits are configured separately and do not replace message size limits.

## Handle Oversized Messages

### Identify the Direction and Breached Threshold

For unary RPCs, measure request size before sending and response size before returning. For streaming RPCs, check the size of each individual message; if the application also enforces a total stream quota, measure and control that total separately.

In grpc-java, `maxInboundMessageSize` configures the maximum message size a receiver accepts. The examples below illustrate the underlying grpc-java API; when using Spring gRPC, apply the equivalent setting through the `ServerBuilder` or `ManagedChannelBuilder` configuration extension points provided by your starter version.

```java
// Server side: limit the size of requests received by the server.
Server server = ServerBuilder.forPort(port)
    .maxInboundMessageSize(8 * 1024 * 1024)
    .addService(grpcService)
    .build();
```

```java
// Client side: limit the size of responses received by the client.
ManagedChannel channel = ManagedChannelBuilder
    .forAddress(host, port)
    .useTransportSecurity()
    .maxInboundMessageSize(8 * 1024 * 1024)
    .build();
```

Both examples above use an 8 MiB threshold for illustration, not as a universal recommendation for every system. Set limits based on actual payload sizes, available heap, concurrent RPC count, and how many copies of the data may exist during deserialization/processing. A large limit can cause memory spikes when many large requests arrive simultaneously.

Increase the limit only when the payload is legitimate and the system has sufficient resources to handle it. If the data is inherently large, consider:

- Splitting data into bounded-size chunks and transferring via client/server streaming.
- Paginating responses or providing a partial query API.
- Placing large files in object storage, then sending the URI or identifier plus required metadata over gRPC.
- Using compression when appropriate to save bandwidth; still maintain a safe size limit on the receiver because compression does not replace post-decompression size control.

If the error occurs at a gateway or proxy, changing application configuration alone may have no effect. Compare limits across the entire RPC path and inspect the logs of the component returning the status.

## Handle Quotas and Load Limits

Quotas are commonly enforced per tenant, principal, API, operation type, or time window. With Spring gRPC, checks can live in an interceptor or inside the service depending on policy scope. The identity used for quota accounting must come from the authenticated principal, not directly from an unverified tenant ID in the request.

Minimal example of a service rejecting a request when quota is exhausted:

```java
if (!quotaService.tryConsume(authenticatedTenantId, 1)) {
    throw Status.RESOURCE_EXHAUSTED
        .withDescription("Request quota exceeded")
        .asRuntimeException();
}
```

`tryConsume` must behave atomically when multiple instances process requests concurrently for the same tenant. If quotas are stored in Redis or a shared data store, checking and decrementing must prevent two instances from reading the same remaining quota and both accepting requests beyond the threshold. Clearly define whether quotas count requests, bytes, processing time, or a weighted business unit.

When retrying after a delay is possible, return enough information for the client to wait appropriately, such as reset time or retry delay. Systems using the gRPC rich error model can attach `google.rpc.QuotaFailure` and `google.rpc.RetryInfo` in status details. Clients should read details using the agreed structured types; do not parse description strings as a machine-readable protocol.

Error messages should help operations identify which quota was exceeded without exposing internal thresholds, other customers' identifiers, or sensitive data. Server logs can record deeper policy details linked to a trace ID for lookup.

## Handle Errors on the Client

Java clients typically receive errors as `StatusRuntimeException`. You can classify status codes using `Status.fromThrowable`:

```java
try {
    Reply reply = blockingStub.withDeadlineAfter(3, TimeUnit.SECONDS)
        .process(request);
    return reply;
} catch (StatusRuntimeException ex) {
    Status status = Status.fromThrowable(ex);

    if (status.getCode() == Status.Code.RESOURCE_EXHAUSTED) {
        // Read status details/trailers per the service contract.
        // Retry only when the error is a transient quota and the retry window is known.
        throw ex;
    }

    throw ex;
}
```

The snippet above illustrates the error-classification point; the retry policy itself must be implemented separately. For transient quotas, the client can wait based on `RetryInfo` or reset time, add jitter, cap attempts, and still honor the overall operation deadline. For oversized messages, retrying the unchanged payload will keep failing; the client must shrink/split the payload or use an appropriate streaming transport.

Automatically retry only idempotent operations or operations protected against duplicate execution. If a request could create a transaction, submit a payment, or write data, require an idempotency key or equivalent safeguard before retrying. Do not retry immediately in a tight loop, as that worsens quota exhaustion and overload.

## Streaming and Backpressure

Streaming does not eliminate message limits. Each individual message must still fit within the receiver's inbound limit, and the application should enforce additional limits on total bytes, message count, stream duration, and concurrent streams if business rules require.

Do not push all incoming messages into an unbounded queue. With server streaming or bidirectional streaming, produce/send the next chunk only when the receiver is ready; use gRPC's readiness/flow-control mechanisms and keep queues bounded. When a queue is full, the application needs an explicit policy such as pausing reads, rejecting the stream, or cancelling the stream with an appropriate status.

Stream quotas must also be released properly when the client cancels the RPC, the deadline expires, or the connection closes. If quota is held for the lifetime of a stream, ensure both completion and error branches release resources.

## Investigation and Remediation Workflow

1. Extract the trace ID, RPC method, status code, description, and trailers from client logs; find the matching request in server/gateway logs.
2. Identify whether the error originated from the server, client, interceptor, service, or proxy; record explicitly whether the request or response exceeded the limit.
3. Compare actual message size against `maxInboundMessageSize` at the receiver and against gateway limits.
4. If quota-related, inspect the authenticated principal/tenant, quota type, consumption level, reset window, and counter atomicity.
5. Apply the right measure: cap payloads, chunk/stream, paginate, tune thresholds safely, throttle call rates, or apply backpressure.
6. Verify whether the client retries under the right conditions with backoff/jitter, max attempts, and deadlines.
7. Monitor the `RESOURCE_EXHAUSTED` rate, payload sizes, quota rejections, queue depth, heap usage, and concurrent RPCs after deployment.

## Required Tests

- Send requests just below, equal to, and above the server inbound threshold; verify oversized requests are rejected cleanly.
- Produce a response larger than the client's inbound limit to verify the response direction is configured and monitored separately.
- Call repeatedly until quota runs out; verify returned status, reset/retry details, and when quota becomes available again.
- Send concurrent requests from multiple instances for the same tenant to verify quota counters do not allow limit overruns due to race conditions.
- Test streams with large messages, many messages, client cancellation, and expired deadlines; verify bounded buffers and resource release.
- Verify the client does not retry oversized payloads and only retries transient quotas per the published policy.

## Avoid Wrong Fixes

- Do not raise message limits across the board without measuring heap and concurrency.
- Do not continuously retry a quota error or resend a payload already known to be too large.
- Do not use `RESOURCE_EXHAUSTED` for every input error; malformed data typically fits `INVALID_ARGUMENT`, while temporary service unavailability may fit `UNAVAILABLE` depending on cause.
- Do not rely on description text for client behavior decisions; use status codes and structured error details.
- Do not overlook gateways/proxies or receiver-side settings when investigating message size errors.

Once you have identified the limit causing the error, fix the exact layer owning that limit and test both boundary cases and concurrent load. A valid configuration must keep memory, quotas, and processing time within bounds under real operating conditions.
