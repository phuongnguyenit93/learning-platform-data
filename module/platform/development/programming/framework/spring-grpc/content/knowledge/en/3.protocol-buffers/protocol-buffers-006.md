# Default Values and Presence

## Learning Objectives

After this lesson, you will be able to:

- Explain **default value** and **field presence** in Protocol Buffers proto3.
- Distinguish **implicit presence** from **explicit presence** when working with scalars, enums, messages, **optional**, **oneof**, **repeated**, and **map**.
- Read Java APIs generated by **protoc** accurately, such as **getXxx()**, **hasXxx()**, **setXxx()**, **clearXxx()**, and **get...Case()**.
- Predict differences when serializing to binary Protobuf, converting to ProtoJSON, and combining messages with **mergeFrom()**.
- Design and test partial-update requests for Spring gRPC services, avoiding overwriting data by confusing default values with absent fields.

## 1. A Default Value Does Not Answer “Did the Client Send This Field?”

In **SPRING_GRPC**, Protocol Buffers contracts describe messages for unary or streaming RPC clients and servers. The **protoc** tool generates Java classes from the schema; the Spring application receives decoded requests and executes business logic. If the server only inspects values returned by getters, it can misinterpret the sender's intent.

Consider a user editing notification settings:

- Client **does not send** notification status: the server should keep the current setting.
- Client sends **false**: the server should turn notifications off.
- Client **does not send** the access limit: keep the current limit.
- Client sends **0**: set the limit to 0 per business rules.

With a regular proto3 **bool** field, the Java getter returns **false** in both “not sent” and “set to false”. Likewise, **int32** returns 0 and **string** returns an empty string when no data is present. These are the **default values** of the data types.

**Presence** answers a different question: *was the field actually set in the message?* Only fields with **explicit presence** directly express the distinction between “absent” and “present with default value”. Understanding this difference prevents accidental overwrite bugs, especially when multiple Spring gRPC client and server versions operate together.

## 2. What Is a Default Value in proto3?

A default value is what a getter returns when a field has no explicitly set value. In proto3, common default values are:

| Field kind | Value when field is unset | Common Java API |
| --- | --- | --- |
| **string** | Empty string **""** | **getName()** returns String |
| **bool** | **false** | **getEnabled()** returns boolean |
| **int32**, **uint32**, **sint32**, and other 32-bit integers | **0** | Getter returns int |
| **int64**, **uint64**, **sint64**, and other 64-bit integers | **0L** | Getter returns long |
| **float**, **double** | **0.0** | Getter returns float/double |
| **bytes** | **ByteString.EMPTY** | Getter returns ByteString |
| **enum** | Member numbered **0** | Getter returns generated enum |
| **message** | **Default instance** of the message type | Getter returns message object; presence can be checked separately |
| **repeated** | Empty list | **getXxxList()**, **getXxxCount()** |
| **map** | Empty map | **getXxxMap()**, **getXxxCount()** |

Important notes:

1. **Getter default** is not the same as serialized value. A proto3 scalar field without explicit presence that equals its default is normally **not written** to binary.
2. Proto3 **enums** must declare their first value with number **0**. In practice, name it **UNSPECIFIED** or **UNKNOWN**; do not assume 0 is a valid business state by default.
3. **Messages** also have getters returning a default instance when absent, yet the message field itself **has presence**. Check **hasXxx()** when you need to distinguish omitting a submessage from sending an empty submessage.
4. **Repeated/map** fields lack collection-level presence in the usual sense; an empty collection does not indicate whether the sender intentionally sent it empty.

In standard proto3, you **cannot declare arbitrary default values** with syntax like **[default = 10]** as in some older proto2 schemas. For instance, to default a limit to 10 by business logic, the server must apply 10 when the field is absent; you cannot rely on the proto3 getter automatically returning 10.

## 3. Two Presence Models: Implicit and Explicit

**Implicit presence** is the model applied to proto3 scalars/enums not declared **optional** and not inside a **oneof**. A message can hold non-default values, but the API does not independently track whether a scalar was set to its exact default value.

**Explicit presence** records whether a field was set. In proto3, typical cases are **optional scalars**, **message fields**, and **oneof** branches.

Example:

~~~proto
syntax = "proto3";

message PresenceExample {
  bool enabled = 1;
  optional bool enabled_override = 2;
}
~~~

| Situation | enabled | enabled_override |
| --- | --- | --- |
| Setter not called | **getEnabled() == false** | **getEnabledOverride() == false**, **hasEnabledOverride() == false** |
| Setter called with **false** | **getEnabled() == false**, no **hasEnabled()** | **getEnabledOverride() == false**, **hasEnabledOverride() == true** |
| Setter called with **true** | **getEnabled() == true** | **getEnabledOverride() == true**, **hasEnabledOverride() == true** |

If the server needs to know *whether the client requested turning notifications off*, simply reading **getEnabled() == false** is not enough. Design the field with explicit presence and check **hasEnabledOverride()**.

**Optional does not make a field required.** It adds the ability to detect presence; requiring a value to be supplied remains part of application business validation.

## 4. A Complete Illustrative Contract

Suppose a gRPC service manages user preferences. Schema:

~~~proto
syntax = "proto3";

package learning.preferences.v1;

option java_package = "com.example.preferences.v1";
option java_multiple_files = true;

enum DeliveryMode {
  DELIVERY_MODE_UNSPECIFIED = 0;
  DELIVERY_MODE_EMAIL = 1;
  DELIVERY_MODE_PUSH = 2;
}

message ContactInfo {
  string email = 1;
}

message UserPreferences {
  string user_id = 1;
  string locale = 2;
  optional bool notifications_enabled = 3;
  optional int32 daily_limit = 4;
  optional string nickname = 5;
  optional DeliveryMode delivery_mode = 6;
  ContactInfo contact = 7;
  repeated string topics = 8;
  map<string, string> attributes = 9;

  oneof recovery_destination {
    string backup_email = 10;
    string backup_phone = 11;
  }
}

message PatchPreferencesRequest {
  string user_id = 1;
  optional bool notifications_enabled = 2;
  optional int32 daily_limit = 3;
  optional string nickname = 4;
  optional DeliveryMode delivery_mode = 5;
}

service PreferencesService {
  rpc PatchPreferences(PatchPreferencesRequest)
      returns (UserPreferences);
}
~~~

In message **UserPreferences**:

- **locale = 2** is a regular scalar with **implicit presence**.
- **notifications_enabled**, **daily_limit**, **nickname**, and **delivery_mode** have **explicit presence** via **optional**.
- **contact = 7** has presence because it is a message field; no optional declaration is needed to get **hasContact()**.
- **topics** and **attributes** are collections; there is no **hasTopics()** or **hasAttributes()** for the fields themselves.
- **recovery_destination** is a **oneof**: at most one branch is set, identified via **getRecoveryDestinationCase()**.

The **PatchPreferencesRequest** separates out the updatable fields. This organization lets the server apply intentional changes without guessing from the default values of **UserPreferences**.

## 5. Observing Default Values and Presence in Java

From the schema above, **protoc** generates builders and getters. Example:

~~~java
import com.example.preferences.v1.UserPreferences;

UserPreferences empty = UserPreferences.newBuilder().build();

System.out.println(empty.getLocale());                // ""
System.out.println(empty.getNotificationsEnabled());  // false
System.out.println(empty.hasNotificationsEnabled());  // false
System.out.println(empty.getDailyLimit());            // 0
System.out.println(empty.hasDailyLimit());            // false
System.out.println(empty.getNickname());              // ""
System.out.println(empty.hasNickname());              // false
System.out.println(empty.getTopicsCount());           // 0
System.out.println(empty.getAttributesCount());       // 0
System.out.println(empty.hasContact());               // false
~~~

There is no **hasLocale()**, because **locale** is a proto3 string without explicit presence. **getContact()** still returns a default instance, while **hasContact() == false** indicates the submessage has not been set.

Setting default values via the builder:

~~~java
UserPreferences explicitDefaults = UserPreferences.newBuilder()
    .setLocale("")
    .setNotificationsEnabled(false)
    .setDailyLimit(0)
    .setNickname("")
    .build();

System.out.println(explicitDefaults.getLocale());               // ""
System.out.println(explicitDefaults.hasNotificationsEnabled()); // true
System.out.println(explicitDefaults.hasDailyLimit());           // true
System.out.println(explicitDefaults.hasNickname());             // true
~~~

**setLocale("")** does not create separate presence for **locale**. By contrast, setters for optional fields mark them as present, even when equal to default values.

Builders also have **clearXxx()** to erase a field's value:

~~~java
UserPreferences cleared = explicitDefaults.toBuilder()
    .clearNickname()
    .build();

System.out.println(cleared.hasNickname()); // false
System.out.println(cleared.getNickname()); // ""
~~~

Through the getter, both **explicitDefaults** and **cleared** return an empty string for nickname, yet they differ in **hasNickname()**. This affects serialization, merging, and the meaning of update commands.

## 6. Why Do Message Fields Have a Default Instance Yet Still Have Presence?

Given:

~~~proto
message ContactInfo {
  string email = 1;
}

message UserAccount {
  ContactInfo contact = 1;
}
~~~

Two cases:

~~~java
UserAccount absent = UserAccount.newBuilder().build();

UserAccount presentEmpty = UserAccount.newBuilder()
    .setContact(ContactInfo.newBuilder().build())
    .build();

System.out.println(absent.hasContact());       // false
System.out.println(presentEmpty.hasContact()); // true

System.out.println(absent.getContact().getEmail());       // ""
System.out.println(presentEmpty.getContact().getEmail()); // ""
~~~

**getContact()** returns a default instance when absent; setting the submessage to an empty message also yields the default email. Thus, comparing only **getContact().getEmail()** cannot tell the two cases apart. **hasContact()** provides the presence information for the message field.

Message fields inherently have explicit presence in proto3, so you can simply declare **ContactInfo contact = 1;**. When checking existence, adding the **optional** label is not required.

At the business layer, **contact present with no email** might denote a specific action; however, an empty message by itself does **not** dictate whether to clear contact or leave it unchanged. The application must define and test that meaning.

## 7. Enum: Value 0, optional, and Unrecognized Values

Consider:

~~~proto
enum DeliveryMode {
  DELIVERY_MODE_UNSPECIFIED = 0;
  DELIVERY_MODE_EMAIL = 1;
  DELIVERY_MODE_PUSH = 2;
}

message DeliverySettings {
  DeliveryMode mode = 1;
  optional DeliveryMode requested_mode = 2;
}
~~~

When the fields are unset:

- **getMode()** returns **DELIVERY_MODE_UNSPECIFIED** without any **hasMode()**.
- **getRequestedMode()** returns **DELIVERY_MODE_UNSPECIFIED**, while **hasRequestedMode() == false**.

If the builder calls **setRequestedMode(DELIVERY_MODE_UNSPECIFIED)**, **hasRequestedMode()** becomes **true**. The server can distinguish a request to *reset the mode to unspecified* from *not requesting a mode change*.

Enum versions can evolve. If a client receives a numeric value not yet declared in its current Java enum, the standard proto3 Java runtime preserves that number and **getMode()** returns **UNRECOGNIZED**. To inspect the integer, use **getModeValue()**. Business logic must handle unrecognized values; do not automatically treat every unfamiliar value as **UNSPECIFIED**.

Default enum value 0 and the **absent** state are two different concepts. **Optional enum** expresses that difference.

## 8. Repeated and Map: Empty Does Not Mean Deletion Requested

Consider:

~~~proto
message Subscription {
  repeated string topics = 1;
  map<string, string> labels = 2;
}
~~~

If no topics or labels are added, Java returns an **empty list** and an **empty map**. Methods such as **getTopicsList()**, **getTopicsCount()**, **getLabelsMap()**, and **getLabelsCount()** read their contents.

However, repeated and map do not have **hasTopics()** or **hasLabels()** to mark an entire collection as explicitly set to empty. In binary, a collection with zero elements contains no entry items. Thus the server cannot look at an empty repeated/map alone to tell whether the client wants to **clear everything** or **make no changes**.

You cannot declare **optional repeated string topics = 1;** or **optional map<string, string> labels = 2;**. When collection updates are needed, design one of these approaches:

- Dedicated RPCs such as **ReplaceTopics**, **AddTopic**, **RemoveTopic**.
- **FieldMask** to specify which fields to update, paired with explicit collection replace/merge rules.
- A command message with a **oneof** distinguishing **replace** and **clear**, if the problem requires both actions.

Never assume Protobuf merge automatically means *replace the entire list*; merging repeated fields normally **appends elements**.

## 9. Oneof Preserves Presence by Branch Selection

Oneof expresses a group of alternatives where at most one option is chosen at a time:

~~~proto
message Recovery {
  oneof destination {
    string email = 1;
    string phone = 2;
  }
}
~~~

Java provides **getDestinationCase()** to determine which branch is present:

~~~java
Recovery unset = Recovery.newBuilder().build();
Recovery withEmptyEmail = Recovery.newBuilder()
    .setEmail("")
    .build();

System.out.println(unset.getDestinationCase());
// DESTINATION_NOT_SET

System.out.println(withEmptyEmail.getDestinationCase());
// EMAIL

System.out.println(withEmptyEmail.getEmail()); // ""
~~~

If you call **setEmail(...)** then **setPhone(...)**, the later branch replaces the earlier one. A oneof branch with an empty string still has presence; a default value does not mean the choice is unset.

**Optional** suits fields that can be updated independently; **oneof** suits mutually exclusive alternatives. Do not add the optional label to a field inside a oneof, as oneof already manages per-branch presence.

## 10. Binary Wire: When Are Default Fields Written to Bytes?

To see the concrete difference, consider the message:

~~~proto
syntax = "proto3";

message WireProbe {
  bool enabled = 1;
  optional bool enabled_override = 2;
  optional int32 retry_limit = 3;
}
~~~

With the following builder:

~~~java
WireProbe value = WireProbe.newBuilder()
    .setEnabled(false)
    .setEnabledOverride(false)
    .setRetryLimit(0)
    .build();

byte[] encoded = value.toByteArray();
// One valid binary representation:
// 10 00 18 00
~~~

Explanation:

| Hex bytes | Meaning |
| --- | --- |
| No bytes for field 1 | **enabled** is an implicit scalar equal to default **false**, so it is not serialized. |
| **10 00** | Tag **0x10** = field **2**, wire type **0** (varint); data **0** = false. |
| **18 00** | Tag **0x18** = field **3**, wire type **0**; data **0**. |

Both optional fields are written despite holding default values because they have explicit presence. If no setter is called for any of the three fields, the message can encode to an empty byte array.

After decoding:

~~~java
WireProbe parsed = WireProbe.parseFrom(encoded);

System.out.println(parsed.getEnabled());             // false
System.out.println(parsed.hasEnabledOverride());     // true
System.out.println(parsed.getEnabledOverride());     // false
System.out.println(parsed.hasRetryLimit());          // true
System.out.println(parsed.getRetryLimit());          // 0
~~~

Binary Protobuf does not require every serializer to emit fields in the same order. In business tests, parse and inspect **values and presence**. Inspecting hex bytes is useful for learning the wire format or diagnosing serialization, but does not replace contract tests.

## 11. ProtoJSON: Absent Fields vs. Present Default Fields

ProtoJSON explicitly represents optional fields that are present with default values.

Suppose:

~~~proto
message JsonProbe {
  string locale = 1;
  optional bool enabled = 2;
  optional int32 retry_limit = 3;
  optional string nickname = 4;
}
~~~

| Constructed object | Typical ProtoJSON |
| --- | --- |
| No fields set | **{}** |
| Set **locale = ""** | Usually still **{}** under default printing |
| Set **enabled = false** | **{"enabled":false}** |
| Set **retry_limit = 0** | **{"retryLimit":0}** |
| Set **nickname = ""** | **{"nickname":""}** |

Default output converts **retry_limit** to **retryLimit**. Options on **JsonFormat.Printer** can force implicit default values to be printed as well, yet **printing them to JSON does not manufacture presence** when parsed back into implicit field types.

Using the **protobuf-java-util** library with the **com.google.protobuf.util.JsonFormat** API:

~~~java
import com.google.protobuf.util.JsonFormat;

JsonProbe original = JsonProbe.newBuilder()
    .setLocale("")
    .setEnabled(false)
    .setRetryLimit(0)
    .build();

String json = JsonFormat.printer().print(original);

JsonProbe.Builder builder = JsonProbe.newBuilder();
JsonFormat.parser().merge(json, builder);
JsonProbe restored = builder.build();

System.out.println(restored.hasEnabled());    // true
System.out.println(restored.hasRetryLimit()); // true
System.out.println(restored.getLocale());     // ""
~~~

For regular optional scalar fields, the ProtoJSON parser treats **null** as **field not set** when parsing into a new builder:

~~~json
{
  "nickname": null
}
~~~

This differs from **{"nickname":""}**, where the empty string is explicitly present. Do not assign “delete data” semantics to JSON null when the contract has not specified it. A REST gateway system must standardize its policy for **missing**, **null**, and **present default**.

**ProtoJSON** is not identical to JSON automatically generated by generic libraries like Jackson from Protobuf Java classes. When ProtoJSON contract compliance is required, use a serializer/parser that understands Protobuf rules.

## 12. Merge Semantics: Defaults and Presence Affect Merging

**mergeFrom()** merges the contents of one message into another message's builder. For scalars with implicit presence, a default value on the source normally **does not overwrite** the destination. With optional scalars, a set default value still **overwrites** it.

Using the **UserPreferences** schema from section 4:

~~~java
UserPreferences current = UserPreferences.newBuilder()
    .setUserId("u-42")
    .setLocale("vi")
    .setNickname("An")
    .setDailyLimit(10)
    .build();

UserPreferences incoming = UserPreferences.newBuilder()
    .setLocale("")
    .setNickname("")
    .setDailyLimit(0)
    .build();

UserPreferences merged = current.toBuilder()
    .mergeFrom(incoming)
    .build();

System.out.println(merged.getLocale());         // "vi"
System.out.println(merged.getNickname());       // ""
System.out.println(merged.hasNickname());       // true
System.out.println(merged.getDailyLimit());     // 0
System.out.println(merged.hasDailyLimit());     // true
~~~

**locale** remains **vi** because the source only has an implicit scalar equal to default **""**, lacking presence to command an overwrite. **nickname** and **daily_limit** change because the source carries explicit presence of their default values.

Distinguish **message merging** from a **business PATCH operation**. Nested messages may be merged field-by-field, repeated fields append elements, and maps merge entries by key. If the application needs full replacement or deletion of nested data, define explicit replacement logic and do not assume **mergeFrom()** performs it.

## 13. Partial Updates over gRPC: Using Presence Properly

The **PatchPreferencesRequest** schema in section 4 lets clients send only the fields they want to update:

~~~java
import com.example.preferences.v1.PatchPreferencesRequest;

PatchPreferencesRequest request =
    PatchPreferencesRequest.newBuilder()
        .setUserId("u-42")
        .setNotificationsEnabled(false)
        .setDailyLimit(0)
        .build();

System.out.println(request.hasNotificationsEnabled()); // true
System.out.println(request.getNotificationsEnabled()); // false
System.out.println(request.hasDailyLimit());           // true
System.out.println(request.getDailyLimit());           // 0
System.out.println(request.hasNickname());             // false
~~~

The client's intent is to **turn off notifications**, **set daily limit to 0**, and **leave nickname unchanged**. A server relying solely on getters would easily miss false/0 updates or accidentally overwrite nickname with an empty string.

Example handling logic for a unary RPC using generated gRPC classes:

~~~java
import com.example.preferences.v1.PatchPreferencesRequest;
import com.example.preferences.v1.PreferencesServiceGrpc;
import com.example.preferences.v1.UserPreferences;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;

// PreferencesRepository is an application-defined interface providing
// findById(String) and save(UserPreferences) methods.
public final class PreferencesEndpoint
        extends PreferencesServiceGrpc.PreferencesServiceImplBase {

    private final PreferencesRepository repository;

    public PreferencesEndpoint(PreferencesRepository repository) {
        this.repository = repository;
    }

    @Override
    public void patchPreferences(
            PatchPreferencesRequest request,
            StreamObserver<UserPreferences> observer) {

        if (request.getUserId().isBlank()) {
            observer.onError(Status.INVALID_ARGUMENT
                .withDescription("user_id must not be empty")
                .asRuntimeException());
            return;
        }

        UserPreferences current = repository.findById(request.getUserId());
        if (current == null) {
            observer.onError(Status.NOT_FOUND
                .withDescription("preferences not found")
                .asRuntimeException());
            return;
        }

        UserPreferences.Builder updated = current.toBuilder();

        if (request.hasNotificationsEnabled()) {
            updated.setNotificationsEnabled(
                request.getNotificationsEnabled());
        }
        if (request.hasDailyLimit()) {
            updated.setDailyLimit(request.getDailyLimit());
        }
        if (request.hasNickname()) {
            updated.setNickname(request.getNickname());
        }
        if (request.hasDeliveryMode()) {
            updated.setDeliveryModeValue(
                request.getDeliveryModeValue());
        }

        UserPreferences saved = repository.save(updated.build());
        observer.onNext(saved);
        observer.onCompleted();
    }
}
~~~

**PreferencesRepository** in the example is an application-implemented component; the server also needs to register **PreferencesEndpoint** per the specific Spring gRPC configuration. In production, add authorization checks, domain invariants, atomic updates, concurrency conflict handling, and infrastructure error handling.

Using **setDeliveryModeValue(...)** preserves enum numbers if a value is not yet declared in an older Java enum; however, the application still needs a policy for accepting or rejecting unrecognized states. If business rules allow only a fixed set of states, validate before saving.

In gRPC, metadata, deadlines, interceptors, TLS, and statuses address other concerns; they do not change how Protobuf represents presence. For streaming RPCs, presence rules apply **independently to each message** in the stream.

## 14. When “Absent” and “Present” Are Still Not Enough

Optional scalars distinguish:

1. **Field unset**: typically interpreted as no update.
2. **Field set to a value**: update to that value, including false, 0, or empty string.

However, some problems require three independent actions:

- Leave nickname unchanged.
- Set nickname to an empty string, because an empty string is a valid value.
- Clear nickname, making the field unset in storage.

If “set empty” differs from “clear”, a single optional string cannot express all three commands by itself. A clearer design uses a **oneof** with an explicit clear command:

~~~proto
syntax = "proto3";
import "google/protobuf/empty.proto";

message ChangeNickname {
  string user_id = 1;

  oneof operation {
    string set_value = 2;
    google.protobuf.Empty clear_value = 3;
  }
}
~~~

When **operation** is unset, the server can reject the request for missing an action; when **set_value = ""**, the server stores an empty string; when **clear_value** is chosen, the server clears the value per business rules. **getOperationCase()** reports the exact branch selected.

Another option is **google.protobuf.FieldMask** to list fields to modify, combined with a clear or replace policy. FieldMask is especially helpful when updating nested messages and collections, though per-path behavior must be clearly specified; FieldMask itself does not update the database automatically.

## 15. Schema Evolution and Presence Compatibility

Adding a new field with an unused number is generally wire-structurally compatible: old clients unfamiliar with that field can skip it while reading, and the new server must accept requests where the field is absent.

Changing a released field from:

~~~proto
string nickname = 2;
~~~

to:

~~~proto
optional string nickname = 2;
~~~

generally preserves the **field number** and **wire type** in binary. Even so, semantics are not completely identical:

| Situation | Old implicit reader/schema | New optional reader/schema |
| --- | --- | --- |
| Field absent | Getter returns **""**; no has method | Getter returns **""** and **hasNickname() == false** |
| Field has value **"An"** | Getter returns **"An"** | Getter returns **"An"**, **hasNickname() == true** |
| Field explicitly sent as **""** | Getter returns **""**, presence unknown | Getter returns **""**, **hasNickname() == true** |
| Forwarding a message containing a default value | May omit serializing field **""** | Serializes the present-default case |

In particular, if a message passes through an intermediary using the old schema, that intermediary can lose explicit presence of a default value when parsing and re-serializing. Downstream new versions will no longer know it was “intentionally set to empty” at the origin.

Before relying on proto3 optional, ensure **protoc** and your Java code generator/runtime support optional syntax and generate the corresponding presence APIs. Very old Protobuf versions may not support it or may not emit the presence APIs.

Test both **old client → new server** and **new client → old server**, including rolling deployments and paths through JSON gateways. Binary compatibility does not guarantee semantic compatibility if the server starts requiring fields old clients do not know.

## 16. Testing Default Values and Presence

A minimum test suite should verify:

| Case | What must be proven |
| --- | --- |
| Optional unset | Getter returns default, **hasXxx() == false** |
| Optional set to default | Getter returns default, **hasXxx() == true** |
| Optional cleared on builder | **clearXxx()** resets presence to false |
| Implicit scalar set to default | No has method; merging does not overwrite like optional |
| Submessage absent / empty submessage | Getter content may look identical, but **hasMessage()** differs |
| Oneof selecting a branch with default value | **get...Case()** reports the chosen branch |
| Binary/ProtoJSON round-trip | Presence of present-default optionals is preserved |
| Client/server on different versions | No misinterpretation of intent or overwriting unrequested fields |

JUnit 5 example based on the **UserPreferences** schema in section 4:

~~~java
import static org.junit.jupiter.api.Assertions.*;

import com.example.preferences.v1.UserPreferences;
import com.google.protobuf.util.JsonFormat;
import org.junit.jupiter.api.Test;

class PresenceTest {

    @Test
    void distinguishesAbsentFromPresentDefaults() {
        UserPreferences absent = UserPreferences.newBuilder().build();
        UserPreferences present = UserPreferences.newBuilder()
            .setNotificationsEnabled(false)
            .setDailyLimit(0)
            .setNickname("")
            .build();

        assertFalse(absent.hasNotificationsEnabled());
        assertFalse(absent.hasDailyLimit());
        assertFalse(absent.hasNickname());

        assertTrue(present.hasNotificationsEnabled());
        assertTrue(present.hasDailyLimit());
        assertTrue(present.hasNickname());
        assertFalse(present.getNotificationsEnabled());
        assertEquals(0, present.getDailyLimit());
        assertEquals("", present.getNickname());
    }

    @Test
    void survivesBinaryAndJsonRoundTrips() throws Exception {
        UserPreferences original = UserPreferences.newBuilder()
            .setNotificationsEnabled(false)
            .setDailyLimit(0)
            .build();

        UserPreferences fromBinary =
            UserPreferences.parseFrom(original.toByteArray());
        assertTrue(fromBinary.hasNotificationsEnabled());
        assertTrue(fromBinary.hasDailyLimit());

        String json = JsonFormat.printer().print(original);
        assertTrue(json.contains("\"notificationsEnabled\""));
        assertTrue(json.contains("\"dailyLimit\""));

        UserPreferences.Builder jsonBuilder = UserPreferences.newBuilder();
        JsonFormat.parser().merge(json, jsonBuilder);
        UserPreferences fromJson = jsonBuilder.build();
        assertTrue(fromJson.hasNotificationsEnabled());
        assertTrue(fromJson.hasDailyLimit());
    }

    @Test
    void mergeRespectsExplicitDefaults() {
        UserPreferences current = UserPreferences.newBuilder()
            .setLocale("vi")
            .setDailyLimit(10)
            .build();
        UserPreferences change = UserPreferences.newBuilder()
            .setLocale("")
            .setDailyLimit(0)
            .build();

        UserPreferences result = current.toBuilder()
            .mergeFrom(change)
            .build();

        assertEquals("vi", result.getLocale());
        assertEquals(0, result.getDailyLimit());
        assertTrue(result.hasDailyLimit());
    }
}
~~~

The snippets above are educational examples using generated Java APIs, not outputs executed against a repository. Once a project has a full Spring gRPC setup, add real RPC tests (for instance via in-process gRPC) to confirm the server does not overwrite fields missing from the request and properly applies **false**, **0**, and **""** when present.

## 17. Common Mistakes

| Mistake | Consequence | How to fix |
| --- | --- | --- |
| Checking **getEnabled() == false** to infer the field was not sent | Misses intentional requests to turn off notifications | Use **optional bool** and **hasEnabled()** |
| Always writing every field from getters to the entity | Absent fields overwrite stored data with defaults | Only update fields with presence or listed in the mask |
| Calling **clearNickname()** to issue a delete command in a patch request | Field is omitted from request; server may treat as no-op | Use a dedicated delete command or explicit empty-value convention |
| Assuming a submessage lacks presence because getter never returns null | Fails to distinguish absent from empty message | Check **hasContact()** |
| Assuming an empty repeated/map means the client wants to clear it | Unintended data deletion | Use FieldMask, explicit commands, or replacement RPCs |
| Treating enum 0 as a confirmed business state | Misprocesses unspecified values | Name 0 as **UNSPECIFIED** and check presence when needed |
| Assuming a default printed in JSON was always sent | Formatters/printers may emit defaults without presence | Distinguish explicit vs. implicit and test serializers |
| Changing an implicit scalar to optional without checking paths through old versions | Presence of default values may be lost | Test v1/v2 and all involved gateways/intermediaries |
| Treating mergeFrom as a complete PATCH | Repeated/nested data may be appended or merged incorrectly | Build business-specific update semantics |

## 18. Practice Exercise

Build a gRPC API for managing device settings:

~~~proto
syntax = "proto3";

message UpdateDeviceSettingsRequest {
  string device_id = 1;
  optional bool enabled = 2;
  optional int32 sample_interval_seconds = 3;
  optional string alias = 4;
}
~~~

Requirements:

1. Explain what getters and **hasXxx()** return for a request that only sets **device_id**.
2. Create a request with **enabled = false**, **sample_interval_seconds = 0**, and **alias unset**. Check all presence states after building.
3. Serialize/parse the request, proving the two present default values are preserved.
4. Convert the request to ProtoJSON with **JsonFormat** and parse it back; observe the false/0 values.
5. Write an entity update function that only modifies fields where **hasXxx() == true**, keeping the old alias if the client did not send one.
6. If an empty alias is a valid value and deleting the alias from the database is a separate action, propose a command message using **oneof**.
7. Try replacing **optional int32 sample_interval_seconds** with **int32 sample_interval_seconds** in another schema version; analyze the risks when resetting the interval to 0 and passing through an intermediary running the old version.

**Completion criteria:** handle all three values **false**, **0**, and **""** correctly without confusing default getters with presence; describe the limitations of optional for collections and deletion operations; explain why changing presence affects merging and compatibility when clients and servers deploy independently.

## 19. Key Takeaways

- **Default value** is what a getter returns when a field is unset; **presence** indicates whether the field was set.
- Regular proto3 scalars/enums use **implicit presence**; **optional** provides explicit presence and **hasXxx()**.
- Message fields inherently have presence; oneof has per-branch presence; repeated/map lack direct collection-level presence.
- With explicit presence, **false**, **0**, and **""** can be serialized and merged as intentionally set values.
- **clearXxx()** removes presence on the builder; it is not implicitly a command to delete stored server data.
- Test binary, ProtoJSON, merging, and multiple schema versions before relying on presence for partial updates.

Mastering default values and presence enables Spring gRPC applications to interpret client intent accurately and avoid data loss when processing unary requests or individual messages in streaming RPCs. This is the foundation for API design, integration testing, and operating highly reliable services.
