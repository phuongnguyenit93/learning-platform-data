# Debugging TLS Safely

## Lesson Objectives

In **SPRING_GRPC**, connection failures can occur across multiple layers: DNS/TCP, TLS handshake, certificate verification, ALPN/HTTP/2, gRPC transport, or RPC handling. Effective debugging requires identifying the right failure layer, collecting sufficient evidence to reproduce, and limiting logging scope over time. Unsafe TLS debugging can expose certificate metadata, internal identities, tokens, private keys, or RPC data.

This lesson focuses on **debugging TLS safely**: building a layered investigation workflow, using OpenSSL to inspect handshakes/certificates/ALPN, enabling Java TLS diagnostics in a controlled way, observing gRPC channels and servers, protecting logs/packet captures, and concluding the debug session by disabling temporary diagnostic settings.

After this lesson, you will be able to:

1. Distinguish DNS/TCP, TLS, HTTP/2/ALPN, and gRPC errors.
2. Collect handshake details without logging secrets or sensitive payloads.
3. Use OpenSSL to inspect certificate chains, hostnames, SNI, protocols, and ALPN.
4. Enable JSSE diagnostics or Netty logging within a narrow scope.
5. Classify one-way TLS and mTLS errors.
6. Record safe TLS telemetry in Spring gRPC.
7. Write a runbook to reproduce, resolve, and cleanly conclude debugging.

> **Scope:** Examples use gRPC Java, Spring gRPC, Java JSSE, Netty, and OpenSSL. Logger names, TLS APIs, and log verbosity depend on the runtime/transport version. Enable heightened diagnostics only in controlled environments and only for as long as needed.

## 1. Identify the Failure Layer Before Enabling Debug

An RPC over TLS passes through many layers. Without knowing where the failure happens, turning on application-wide tracing usually produces massive logs without revealing the root cause.

| Layer | Question to Answer | Common Symptoms |
| --- | --- | --- |
| DNS/name resolution | Which address does the target resolve to? | Name resolution failure, resolver error |
| TCP | Can a socket open to the host/port? | Connection refused, timeout, no route |
| TLS handshake | Do both sides agree on protocol/key/cipher and authenticate peers? | handshake_failure, protocol_version, certificate error |
| Certificate identity | Are the chain and hostname valid? | unknown CA, PKIX path error, hostname mismatch |
| ALPN/HTTP/2 | Did TLS negotiate h2? | ALPN mismatch, HTTP/2 protocol error |
| gRPC transport | Are HTTP/2 streams being created? | UNAVAILABLE, stream reset, GOAWAY |
| RPC/application | Are service/method and authorization valid? | UNIMPLEMENTED, UNAUTHENTICATED, PERMISSION_DENIED, business errors |

Investigation rules:

1. Record the target hostname, port, UTC timestamp, and environment.
2. Determine whether TLS terminates at the gRPC process, sidecar, ingress, or load balancer.
3. Check DNS and TCP before investigating certificates.
4. Check the handshake and certificate chain.
5. Verify ALPN h2 and HTTP/2.
6. Only once the transport works should you investigate services, methods, metadata, and authorization.

TLS handshake failures usually occur before RPC handlers or business interceptors run. Therefore, a TLS error cannot be fully diagnosed from interceptor logs alone.

## 2. Preparing a Safe Debug Session

Before collecting logs or running diagnostic commands, identify:

- The actual endpoint and hostname the client uses.
- The TLS listener/port and TLS termination point.
- Versions of the JDK, gRPC Java, and Netty/TLS provider.
- Whether mTLS is enabled.
- The trust store/CA bundle currently applied.
- When the error started, frequency, and scope of affected clients.
- A request/correlation ID containing no personal data or secrets.

Establish a short debug window with an owner and exit criteria. Prefer staging/canary or a dedicated instance. If production debugging is unavoidable, restrict instances, loggers, duration, and who can read the logs.

**Do not collect or share:**

- PEM private keys, keystore passwords, secret mounts, or tokens.
- Authorization metadata contents, cookies, or credential headers.
- Plaintext requests/responses or unnecessary business data.
- TLS session keys/key logs in production environments.
- Full environment dumps or full process arguments if they may contain secrets.

Public certificates are presented openly during handshakes, yet subject, SAN, serial, and issuer can still reveal internal topology. Store only necessary fields, and restrict access permissions and retention duration.

## 3. Probing the Endpoint with OpenSSL

OpenSSL helps separate TLS issues from application channel configuration. Directly probe the exact endpoint, SNI, trust root, and hostname:

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -CAfile certs/root-ca.pem \
  -verify_hostname grpc.example.com \
  -verify_return_error \
  -showcerts
```

Read the results in order:

1. Did the TCP connection open?
2. Which TLS protocol and cipher were negotiated?
3. Which leaf certificate and intermediates did the server present?
4. Did the chain verify to the specified root CA?
5. Did the hostname match the SAN?
6. Did ALPN select h2?

You can add options like brief to shorten output depending on the OpenSSL version. When observing handshake progress is necessary, use state or msg in a short test session and protect the output; do not leave this tracing enabled continuously on high-traffic systems.

### 3.1. Checking the Presented Certificate

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -showcerts </dev/null
```

Note: the command above only retrieves the certificate chain from the endpoint; to verify fully, include the CA file and hostname as in the previous example. Compare the certificate presented by the endpoint with the local file by fingerprint:

```bash
openssl x509 -in certs/server.pem -noout \
  -subject -issuer -serial -dates -fingerprint -sha256 \
  -ext subjectAltName -ext extendedKeyUsage
```

If the endpoint presents a different certificate than the local file, investigate SNI mappings, proxies, secret mounts, and listener reloads/restarts. Do not conclude the new certificate was loaded merely because the file on disk changed.

### 3.2. Checking the Chain Offline

```bash
openssl verify \
  -purpose sslserver \
  -CAfile certs/root-ca.pem \
  -untrusted certs/intermediate-ca.pem \
  -verify_hostname grpc.example.com \
  certs/server.pem
```

This command helps isolate chain/hostname errors inside the certificate file. It does not prove the server is presenting that exact file; combine it with probing the real endpoint.

### 3.3. Forcing Protocols to Isolate Issues

You can test TLS 1.2 and TLS 1.3 separately:

```bash
openssl s_client -connect grpc.example.com:9090 \
  -servername grpc.example.com -alpn h2 -tls1_2 \
  -CAfile certs/root-ca.pem -verify_hostname grpc.example.com \
  -verify_return_error

openssl s_client -connect grpc.example.com:9090 \
  -servername grpc.example.com -alpn h2 -tls1_3 \
  -CAfile certs/root-ca.pem -verify_hostname grpc.example.com \
  -verify_return_error
```

If one protocol succeeds and the other fails, compare runtimes/providers, protocol allowlists, ciphers, signature schemes, and certificate key types. Do not weaken production policy just to make a test command succeed.

## 4. Controlled mTLS Debugging

When the server requires a client certificate, verify both directions:

- Client verifies the server chain and hostname using client-side trust roots.
- Server verifies the client chain using server-side CA trust roots.
- Client proves ownership of the private key matching the client certificate.

You can test mTLS with OpenSSL using a test certificate:

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -CAfile certs/server-root-ca.pem \
  -cert certs/client-chain.pem \
  -key secrets/client-key.pem \
  -verify_hostname grpc.example.com \
  -verify_return_error
```

The command reads a local private key to perform the handshake; never copy keys into logs, tickets, or chats. Use test certificates/keys or appropriately permissioned secret mounts. For comparison, run once without cert/key if the server requires mTLS; the handshake is expected to be rejected.

Inspect the client certificate and purpose:

```bash
openssl x509 -in certs/client-chain.pem -noout \
  -subject -issuer -dates -ext subjectAltName -ext extendedKeyUsage

openssl verify -purpose sslclient \
  -CAfile certs/client-root-ca.pem \
  -untrusted certs/client-intermediate.pem \
  certs/client-chain.pem
```

If the TLS handshake succeeds but the RPC returns PERMISSION_DENIED, the certificate may be valid while the application identity is not authorized to call the method. Do not confuse an authorization failure with an mTLS handshake rejection.

## 5. Java JSSE TLS Diagnostics

For gRPC transports using JSSE, you can enable TLS debugging on a test process:

```text
-Djavax.net.debug=ssl,handshake,trustmanager
```

If you need to investigate the certificate path builder, you can try narrower security debugging in a controlled environment:

```text
-Djava.security.debug=certpath
```

These flags are normally set at JVM startup. They can produce huge output, exposing hostnames/certificate metadata and environment details. Enable briefly, restrict log file access permissions, capture one reproduction, and disable.

Do not assume JSSE debug observes every TLS connection. Some gRPC setups use Netty with the native OpenSSL provider; in that case, JSSE diagnostics may not display handshakes for that listener/channel.

### 5.1. Distinguishing JSSE and Netty/OpenSSL

Before raising log verbosity, identify the actual TLS provider:

- JSSE: uses the JDK TLS implementation and JSSE diagnostics.
- Netty with native OpenSSL: uses Netty/OpenSSL SSL contexts/providers; requires diagnostics for that exact transport/provider.
- TLS terminated at proxy: TLS handshake logs must come from the proxy; backend logs only reflect the proxy-to-backend hop.

Logger names and DEBUG/TRACE levels depend on version. Do not enable TRACE across entire Netty/gRPC packages if only one connection is needed. Use narrow loggers, short durations, and controlled reproductions.

## 6. Observing gRPC Channels and Servers

### 6.1. Recording Errors on the Client

On the client, preserve the root cause instead of recording only the final status. Example:

```java
try {
    InventoryGrpc.InventoryBlockingStub stub =
            InventoryGrpc.newBlockingStub(channel)
                    .withDeadlineAfter(3, TimeUnit.SECONDS);

    return stub.getStock(request);
} catch (StatusRuntimeException ex) {
    Status status = ex.getStatus();
    Throwable cause = ex.getCause();

    // Log status code, normalized target, and redacted cause
    // class/message; never log metadata/tokens/secrets.
    throw ex;
}
```

This snippet illustrates a diagnostic collection point; do not swallow exceptions or convert all errors into one generic status. Record the status code, cause chain, and target per logging policy, then preserve error semantics for callers.

Distinguish between:

- Channel failed to connect or TLS handshake failed.
- Deadline expired while connecting/establishing transport.
- HTTP/2 stream reset/GOAWAY.
- RPC reached the server and returned a business status.

A single UNAVAILABLE can have multiple root causes. Combine exception causes, OpenSSL probes, and server/proxy logs.

### 6.2. Observing the SSL Session on the Server

When a gRPC Java transport supports the SSL session attribute, a server interceptor can inspect the negotiated protocol and cipher:

```java
SSLSession session =
        call.getAttributes().get(Grpc.TRANSPORT_ATTR_SSL_SESSION);

if (session != null) {
    String protocol = session.getProtocol();
    String cipherSuite = session.getCipherSuite();

    // Record low-cardinality metrics containing no secrets.
}
```

This snippet belongs in `interceptCall` of a server interceptor. The attribute depends on the transport and is present only when the TLS session is exposed. If TLS terminates at a proxy, the backend may not have the SSL session of the client-to-proxy connection; gather telemetry from the proxy rather than inferring from the backend.

Do not log the entire SSLSession, private keys, trust manager objects, or raw certificate chains. Log only the protocol/cipher and approved fingerprints/issuers when truly necessary.

### 6.3. Health and Connectivity Do Not Replace TLS Diagnostics

Channel state READY indicates the channel has an available transport at the moment of observation; it does not prove every hostname/SNI, certificate rotation, or mTLS identity is correct. Health RPCs only run after the transport is established. Combine health checks with handshake probes and RPC integration tests.

## 7. Diagnosing ALPN and HTTP/2

gRPC over TLS requires negotiating ALPN h2. If certificate validation succeeds but ALPN does not select h2, TLS may have completed while gRPC still fails to work properly.

In OpenSSL output, look for negotiated ALPN. If h2 is missing:

- Check whether client/server advertise h2.
- Check whether the proxy supports HTTP/2 on both downstream and upstream sides.
- Check whether the TLS termination listener has the right gRPC protocol configuration.
- Verify the port being tested is actually the gRPC listener, not a REST/management listener.
- Once ALPN is right, call a generated stub to test HTTP/2 streams and gRPC methods.

A successful TLS handshake does not prove the service name/method exists. If the transport is up but the RPC returns UNIMPLEMENTED, check the Protobuf package, full service name, method, and service registration.

## 8. Error Classification and Investigation Table

| Symptom | Evidence to Collect | First Investigation Direction |
| --- | --- | --- |
| Connection refused | TCP error, host/port | Listener, port, firewall, service lifecycle |
| Connect timeout | DNS result, route, TCP timing | Network path, load balancer, endpoint health |
| Unknown CA / PKIX path failure | Trust store fingerprint, server chain | Root/intermediate, exact trust store |
| Hostname mismatch | Target, SNI, SAN | Logical hostname, DNS alias, certificate SAN |
| Certificate expired/not yet valid | notBefore/notAfter, UTC clock | Renewal, chain expiry, NTP |
| handshake_failure | Protocol, cipher, signature, provider | TLS policy and capabilities of both sides |
| mTLS alert/rejection | Client chain, EKU, server client CA | Client certificate, key pair, and server trust |
| ALPN missing h2 | Negotiated ALPN, listener/proxy config | HTTP/2/gRPC listener and proxy upstream |
| UNAVAILABLE after channel existed | Cause chain, stream/reset, proxy log | Transport, GOAWAY, network, or TLS reconnect |
| PERMISSION_DENIED | Authenticated principal, method policy | Authorization/interceptor, not chain trust |
| UNIMPLEMENTED | HTTP/2 request path and service descriptor | Protobuf package/service/method registration |

Do not assign a cause from a single status alone. One incident can span multiple layers, such as a proxy presenting the right certificate while upstream HTTP/2 is disabled.

## 9. Safe Logging and Telemetry

Design logging to aid investigation without turning logs into a credential repository.

**Allowed when permitted by policy:**

- UTC timestamp, environment, instance/listener, and correlation ID.
- Normalized target hostname, port, and transport/provider.
- TLS protocol, cipher suite, and ALPN.
- Normalized error category: expiry, unknown CA, hostname mismatch, protocol mismatch, mTLS rejection.
- Certificate issuer/serial or fingerprint when needed to verify rotation.
- gRPC status code, latency, and retry/connection attempt count.

**Must be stripped or specially protected:**

- Private keys, keystore/truststore passwords, tokens, and authorization metadata.
- Raw request/response payloads.
- Full environment variables or command lines containing secrets.
- Key logs/TLS session secrets.
- Full certificate dumps when unnecessary; SAN/subject can reveal internal hostnames or workload identities.

Use low-cardinality metric labels. Do not attach arbitrary serials, fingerprints, request IDs, or hostnames to metric labels that could cause high cardinality; those fields belong in controlled logs/events.

## 10. Repeatable Debugging Workflow

A concise runbook applicable to TLS incidents:

1. **Scope:** record target, port, UTC timestamp, environment, and blast radius.
2. **Locate termination:** determine whether TLS ends at client-to-proxy, proxy-to-backend, or the gRPC process.
3. **Probe TCP/TLS:** use OpenSSL against the right listener with SNI, CA, hostname, and ALPN.
4. **Inspect certificate:** check chain, validity, SAN, EKU, issuer, and fingerprint.
5. **Inspect provider:** determine JSSE vs. Netty/OpenSSL; enable only the matching diagnostics.
6. **Check gRPC:** call a generated stub and record redacted status/root cause.
7. **Fix narrow cause:** fix trust/chain/SAN/expiry/protocol/proxy at the exact origin.
8. **Verify:** open a new connection, verify TLS/ALPN, then run an RPC test.
9. **Cleanup:** disable debug, restore log levels, delete temporary files per retention policy, and record redacted findings.

### 10.1. Criteria to End Debugging

Close the investigation session only when:

- New connections verify the right certificate chain and hostname.
- TLS version/cipher are within policy.
- ALPN negotiates h2.
- Representative RPCs succeed.
- mTLS works if required by the endpoint.
- Debug logging has been disabled and configuration restored to normal.
- Temporary logs/artifacts are stored or deleted per policy.
- Root cause, fix, owner, and preventive measures are documented.

## 11. Common Mistakes When Debugging

| Unsafe Debugging Practice | Risk/Consequence | Safe Practice |
| --- | --- | --- |
| Disabling certificate verification or using trust-all | Hides identity errors, allows MITM | Keep verification enabled; use a valid test CA |
| Enabling process-wide TLS TRACE | Huge logs, increases metadata exposure risk | Scope down logger, instance, and duration |
| Sharing private keys so others can reproduce | Exposes workload identity and privileges | Use dedicated test certificates/keys |
| Looking only at gRPC status | Misses TLS root cause | Read cause chain and probe endpoint independently |
| Inspecting only certificate files on disk | Listener may present an old/different cert | Probe endpoint with SNI and compare fingerprints |
| Enabling JSSE debug for Netty OpenSSL | Fails to observe the active TLS provider | Identify the provider before enabling diagnostics |
| Checking only handshake, skipping ALPN | TLS passes while HTTP/2/gRPC fails | Verify ALPN h2 and call a generated stub |
| Logging raw metadata/payloads | Leaks tokens and business data | Redact and log minimal status/metadata |
| Leaving debug flags on after incident | Bloated logs and prolonged exposure | Follow a checklist to disable debug and verify config |
| Using fingerprint/request ID as metric labels | Severe cardinality explosion | Use aggregate metrics; keep details in controlled logs |

## 12. Hands-on Exercises

1. Create a gRPC TLS test endpoint and record target, SNI, certificate SAN, issuer, validity, TLS version, cipher, and ALPN.
2. Use OpenSSL to reproduce unknown CA, hostname mismatch, expired certificate, and missing intermediate; distinguish the output for each case.
3. Enable JSSE debug in a test JVM, reproduce a handshake error, then disable the flag; save the redacted log portion.
4. For Netty/OpenSSL, identify the provider and choose version-appropriate diagnostics rather than relying on JSSE debug.
5. Enable mTLS and test a valid client certificate, missing certificate, untrusted CA, and private key mismatch.
6. Call a generated stub after the handshake to distinguish TLS failures from UNIMPLEMENTED or PERMISSION_DENIED.
7. Write an interceptor/telemetry hook that records only TLS protocol, cipher, and gRPC status; never log secrets or raw payloads.
8. Create a runbook with scope, probe commands, root-cause categories, verification steps, and cleanup.
9. Simulate a certificate rotation incident where the endpoint still presents the old certificate despite the file changing; identify the right listener reload/restart.

- Which parameters does `openssl s_client` need to test SNI, hostname, and HTTP/2?
- Why might the certificate on disk differ from the certificate presented by the endpoint?
- When does JSSE debug fail to observe a gRPC handshake?
- Is `UNAVAILABLE` sufficient to conclude there is a certificate error?
- Why do TLS handshake failures usually bypass application interceptors?
- In mTLS, how must trust roots and key material be verified on both sides?
- Why must ALPN h2 be checked separately?
- Which fields are suitable for TLS telemetry and which fields must be redacted?
- What conditions must be met before ending a TLS debugging session?
