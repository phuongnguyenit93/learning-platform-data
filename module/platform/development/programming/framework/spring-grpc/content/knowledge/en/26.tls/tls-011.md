# Testing TLS with Test Certificates

## 1. Why Are Test Certificates Needed?

In **Spring gRPC**, TLS protects connections between client and server through encryption, integrity checking, and server identity authentication. With mutual TLS (mTLS), the server also requires the client to present a certificate to verify the calling workload.

TLS testing should not merely confirm that a channel can open. A solid test suite needs to prove both valid cases and cases that must be rejected:

- Client trusts the CA that signed the server certificate and verifies the exact hostname.
- Client rejects a certificate not in the trust chain.
- Client rejects a certificate whose SAN does not match the authority/hostname.
- mTLS server accepts a valid client certificate.
- mTLS server rejects a client missing a certificate or presenting an untrusted certificate.
- Handshake errors prevent RPCs from reaching business handlers.

**Test certificates** are certificates and private keys created specifically for testing, signed by a test-controlled test CA. They let you test real handshakes without using production credentials.

## 2. What Does the Certificate Chain Need?

A basic TLS scenario typically includes:

| Component | Role |
| --- | --- |
| Test CA certificate | Trust anchor used by the test client to verify the server |
| Server certificate | gRPC server certificate with a SAN matching the hostname used by the client |
| Server private key | Private key corresponding to the server certificate |
| Client certificate | Client workload certificate when testing mTLS |
| Client private key | Private key corresponding to the client certificate |

The server certificate needs an Extended Key Usage suitable for server authentication. A client certificate used for mTLS needs client authentication. The server certificate must have a Subject Alternative Name (SAN), such as DNS:localhost when testing connections to localhost.

Do not rely on Common Name (CN) to replace SAN in modern hostname checks. Also do not use a certificate without a SAN and disable hostname verification just to make tests pass.

## 3. Generating a Test CA and Certificates with OpenSSL

Certificate fixtures can be generated in a temporary test directory or pre-generated in the test resources directory. The example below uses OpenSSL and a self-signed CA intended strictly for testing.

Create the CA key and CA certificate:

~~~bash
openssl req -x509 -newkey rsa:3072 -nodes \
  -keyout test-ca.key -out test-ca.crt \
  -days 7 -subj "/CN=Spring gRPC Test CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"
~~~

Create the server private key and CSR:

~~~bash
openssl req -newkey rsa:2048 -nodes \
  -keyout server.key -out server.csr \
  -subj "/CN=localhost"
~~~

Create the server certificate extensions file, e.g., server.ext:

~~~ini
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost
~~~

Sign the server certificate with the test CA:

~~~bash
openssl x509 -req -in server.csr \
  -CA test-ca.crt -CAkey test-ca.key -CAcreateserial \
  -out server.crt -days 3 -sha256 \
  -extfile server.ext
~~~

Create the client key and CSR:

~~~bash
openssl req -newkey rsa:2048 -nodes \
  -keyout client.key -out client.csr \
  -subj "/CN=spring-grpc-test-client"
~~~

File client.ext:

~~~ini
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature
extendedKeyUsage=clientAuth
subjectAltName=URI:spiffe://test.local/spring-grpc-client
~~~

Sign the client certificate:

~~~bash
openssl x509 -req -in client.csr \
  -CA test-ca.crt -CAkey test-ca.key -CAcreateserial \
  -out client.crt -days 3 -sha256 \
  -extfile client.ext
~~~

Verify the chain and usage purposes:

~~~bash
openssl verify -CAfile test-ca.crt server.crt
openssl verify -CAfile test-ca.crt client.crt
openssl x509 -in server.crt -noout -text
openssl x509 -in client.crt -noout -text
~~~

The verify results must succeed. When inspecting the certificates, check SAN and Extended Key Usage. The server certificate must have serverAuth; the client certificate must have clientAuth.

These commands use RSA for readability; algorithms and key sizes in real environments must follow organizational security standards and the deployed TLS configuration.

## 4. Rules for Managing Test Private Keys

The test CA and private keys have certificate-signing authority, so their usage scope must be restricted:

- Use only in tests; never reuse production CAs or private keys.
- Do not place test keys in main resources or package them into production artifacts.
- If committing fixtures to the repository, use dummy data, restricted access, and clearly mark them as test-only.
- Better yet, generate certificates during test setup in a temporary directory and delete them when the test finishes.
- Use short validity periods long enough for CI; do not let tests depend on an expiration date that has already passed.
- Do not disable certificate verification just to avoid managing fixtures.

If generating certificates dynamically in Java, you can use a dedicated test library or build pipeline tooling. Either way, tests must still check the trust chain and hostname just like production clients.

## 5. Creating TLS Contexts for gRPC Java

With the Netty transport, gRPC Java provides GrpcSslContexts to create a Netty SslContext from certificates, keys, and trust managers.

The imports in the examples use the grpc-netty artifact with packages io.grpc.netty and io.netty. If the project uses grpc-netty-shaded, use the corresponding shaded packages and do not mix the two types of Netty classes in the same builder.

Example creating a server context for one-way TLS:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.SslContext;

SslContext serverTls = GrpcSslContexts.forServer(
        serverCertificate.toFile(),
        serverPrivateKey.toFile())
        .build();
~~~

Client trusting the test CA:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.SslContext;

SslContext clientTls = GrpcSslContexts.forClient()
        .trustManager(testCaCertificate.toFile())
        .build();
~~~

The client trusts only the specified test CA. Do not use a trust manager that accepts all certificates or skip hostname verification.

## 6. Running a TLS Test Server on a Dynamic Port

You can use NettyServerBuilder to start a real gRPC server on port 0, letting the OS assign an available port:

~~~java
import io.grpc.Server;
import io.grpc.netty.NettyServerBuilder;
import io.netty.handler.ssl.SslContext;

Server server = NettyServerBuilder
        .forPort(0)
        .sslContext(serverTls)
        .addService(testService)
        .build()
        .start();

int port = server.getPort();
~~~

Client connecting to localhost over TLS:

~~~java
import io.grpc.ManagedChannel;
import io.grpc.netty.NettyChannelBuilder;
import io.netty.handler.ssl.SslContext;
import java.util.concurrent.TimeUnit;

ManagedChannel channel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(clientTls)
        .build();
~~~

Then invoke the generated blocking or async stub like a normal RPC. Because the channel and server use the real Netty transport, the test performs a genuine TLS handshake rather than mocking the transport.

In tests, always close the channel and server in a finally block or lifecycle hook:

~~~java
try {
    // Perform RPC assertions.
} finally {
    channel.shutdownNow();
    server.shutdownNow();
    channel.awaitTermination(5, TimeUnit.SECONDS);
    server.awaitTermination(5, TimeUnit.SECONDS);
}
~~~

The finally block illustrates shutting down and waiting with a bounded timeout; if await returns false, record a teardown failure so tests do not mask dangling threads or channels. If a test suite has multiple cases, create shared fixtures in setup/teardown and do not leave servers running between tests.

## 7. Testing Hostname and SAN

The client does not only need to trust the CA; it must also verify the certificate is issued for the exact server name. If the client connects to localhost, the certificate needs SAN DNS:localhost.

Passing test:

~~~java
ManagedChannel channel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(clientTls)
        .build();

CatalogServiceGrpc.CatalogServiceBlockingStub stub =
        CatalogServiceGrpc.newBlockingStub(channel);

GetItemResponse response = stub.getItem(request);
assertEquals("item-42", response.getItemId());
~~~

A hostname mismatch test can use an authority different from the SAN:

~~~java
ManagedChannel wrongHostChannel = NettyChannelBuilder
        .forAddress("localhost", port)
        .overrideAuthority("wrong.example.test")
        .sslContext(clientTls)
        .build();

CatalogServiceGrpc.CatalogServiceBlockingStub wrongHostStub =
        CatalogServiceGrpc.newBlockingStub(wrongHostChannel);

assertThrows(StatusRuntimeException.class,
        () -> wrongHostStub.getItem(request));
~~~

The negative test must verify that the RPC fails due to TLS hostname verification and that the business handler does not receive the request. The surfaced status is typically UNAVAILABLE due to handshake/transport failure; exact cause details depend on the Netty and gRPC Java versions. Do not assert solely on a brittle exception message string.

## 8. Testing Untrusted Certificates

Create another CA that did not sign the server certificate. Use that CA as the client's trust manager:

~~~java
SslContext untrustedClientTls = GrpcSslContexts.forClient()
        .trustManager(otherTestCaCertificate.toFile())
        .build();

ManagedChannel untrustedChannel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(untrustedClientTls)
        .build();
~~~

The RPC must fail during the handshake because the client cannot build a trust chain to its configured CA. Verify the business handler is not called. This proves the test is checking actual certificate validation rather than just verifying that the server opened a port.

Additional cases to include:

- Expired server certificate.
- Server certificate not yet valid at test execution time.
- Certificate missing a matching SAN.
- Certificate with an EKU unsuitable for the server role.
- CA changed or no longer in the trust bundle.

For expiration tests, create fixtures with controlled validity windows or use a dedicated test clock/certificate fixture. Do not make tests depend on the CI run date by using a certificate that will soon expire.

## 9. Testing Mutual TLS

mTLS requires the server to verify the client certificate. With Netty, configure the server SslContext to require a client certificate:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.ClientAuth;
import io.netty.handler.ssl.SslContext;

SslContext mutualTlsServerContext = GrpcSslContexts
        .forServer(serverCertificate.toFile(),
                serverPrivateKey.toFile())
        .trustManager(testCaCertificate.toFile())
        .clientAuth(ClientAuth.REQUIRE)
        .build();
~~~

Client with a certificate signed by a trusted CA:

~~~java
SslContext mutualTlsClientContext = GrpcSslContexts.forClient()
        .trustManager(testCaCertificate.toFile())
        .keyManager(clientCertificate.toFile(),
                clientPrivateKey.toFile())
        .build();
~~~

The connection succeeds when:

- The client verifies the server certificate and hostname.
- The server verifies the client certificate against its trust manager.
- The client certificate has an appropriate clientAuth purpose.
- The certificate and private key match.

Negative test: create a client context with only a trust manager and no key manager, then call a server requiring ClientAuth.REQUIRE. The handshake must fail and the business handler must not run.

Another test uses a client certificate signed by a CA not trusted by the server. The server must reject the handshake.

## 10. TLS Identity Is Not Automatically Application Authorization

mTLS verifies the peer/workload at the transport layer. It does not automatically grant that certificate permission to call every RPC or read every resource.

For example, the server may verify the client's SAN as spiffe://test.local/spring-grpc-client. The application must map this identity to a principal/workload policy and then check method or resource permissions.

If the RPC also carries a user bearer token, the two identities serve different purposes:

| Credential | Identity |
| --- | --- |
| Client certificate | Workload/service opening the connection |
| Bearer token | User or delegated principal represented by the request |

A passing mTLS test only proves the transport accepts the certificate. Separate authorization tests are needed to prove a workload or user is only allowed to call the right methods.

## 11. Integrating Test Certificates with Spring gRPC

There are two complementary layers of tests:

1. **Transport integration test:** start a Netty gRPC server/channel with test certificates to verify handshake, trust chain, SAN, and mTLS. This isolates gRPC Java's TLS behavior.
2. **Spring context integration test:** start the application context with the server/client TLS configuration of the exact Spring gRPC version in use, inject the real service/stub, and invoke RPCs over TLS.

Direct Netty examples do not by themselves prove Spring Boot properties or customizers are configured properly. Spring gRPC may change property names and builder customization mechanisms across versions; use the reference for your project's version to configure the test context instead of copying properties from another version.

In Spring context tests, verify:

- The server starts with the test certificate/key.
- The client bean uses the expected trust store/test CA.
- If mTLS is enabled, the server requires a client certificate.
- The generated stub is injected from the configured TLS channel.
- The application service is invoked when the handshake succeeds.
- When the handshake fails, the handler does not receive the request.

## 12. Checking Whether TLS Tests Are Truly Trustworthy

A high-quality TLS test must fail when a security condition is removed or altered:

| Change in Test | Expected Result |
| --- | --- |
| Switch trust CA to one that did not sign the server cert | Handshake fails |
| Change authority to a hostname absent from SAN | Handshake fails |
| Omit client cert when server requires mTLS | Handshake fails |
| Use client cert signed by an unknown CA | Handshake fails |
| Use the right CA, SAN, and key pair | Handshake succeeds |
| Use a certificate with the wrong EKU role | Handshake rejected by TLS provider |
| Disable TLS on client while server only accepts TLS | Connection fails |

In addition to the handshake, assert server invocation counts to ensure rejected requests do not execute business logic. Do not only assert on exceptions; some errors can happen after the transport creates the channel but before an RPC is sent.

## 13. Common Mistakes

1. **Using a trust-all manager in tests.** The test no longer proves the client verifies the server certificate.
2. **Disabling hostname verification so self-signed certificates work.** SAN mismatches go undetected.
3. **Sharing production certificates in tests.** Exposes private keys and couples tests to real environments.
4. **Testing only successful TLS.** Does not prove trust chains, hostnames, or mTLS are enforced.
5. **Using certificates without SANs.** Can make tests depend on legacy TLS provider behavior.
6. **Confusing clientAuth and serverAuth EKU.** A certificate from the right CA with the wrong purpose is still invalid.
7. **Assuming mTLS replaces authorization.** Peer identity must be mapped and checked for permissions.
8. **Not closing channels/servers after tests.** Can leak threads and affect subsequent tests.
9. **Testing only Netty directly and concluding Spring auto-configuration works.** A Spring context test is needed for real integrated configuration.

## 14. Hands-on Exercises

For a Spring gRPC CatalogService:

1. Create a test CA, a server certificate with SAN DNS:localhost, and a client certificate with EKU clientAuth.
2. Start a Netty server on a dynamic port with TLS.
3. Call an RPC using a client trusting the test CA and verify the response succeeds.
4. Test an untrusted CA and a mismatched hostname; verify the handshake fails and the handler does not run.
5. Enable mTLS with ClientAuth.REQUIRE; verify a client with a certificate is accepted.
6. Omit the client certificate and test a certificate signed by an unknown CA; verify the server rejects both.
7. Run a Spring context test with the TLS configuration for your project's Spring gRPC version.
8. Close servers/channels and delete temporary key material after each test suite.

**Completion Criteria:** learners can generate test certificates with appropriate CA, SAN, and EKU; test TLS server authentication, hostname verification, trust chains, and mTLS; verify handshake failures do not enter business handlers; and distinguish transport identity from application authorization.
