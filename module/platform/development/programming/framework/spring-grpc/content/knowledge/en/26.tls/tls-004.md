# mTLS Client Certificates

## Lesson Objectives

In **SPRING_GRPC**, standard TLS lets the client verify the server. With **mutual TLS (mTLS)**, the server also requires the client to present a certificate to authenticate its identity at the transport layer. The server validates the client's certificate chain against its configured CA; the client simultaneously verifies the server certificate against its own trust roots.

This lesson focuses on **mTLS client certificates**: issuing certificates for workloads/clients, preparing the chain and private key, configuring a gRPC Java channel to present client identity, configuring the server to require and verify certificates, mapping certificate identity to application permissions, and testing successful/failed handshake cases.

After this lesson, you will be able to:

1. Distinguish client-side server trust from server-side client trust in mTLS.
2. Create a client certificate with appropriate usage purposes and SAN.
3. Inspect the client certificate, certificate chain, and corresponding private key.
4. Configure a client using TlsChannelCredentials with a trust manager and key manager.
5. Configure a server using TlsServerCredentials to require a client certificate.
6. Extract the TLS-verified identity and apply authorization per RPC method.
7. Manage private keys, CA rotation, certificate expiry, and negative test cases.

> **Scope:** Examples use gRPC Java, Spring gRPC, and OpenSSL. APIs must match the project's gRPC Java/transport version. When Spring manages the server, provide TLS credentials through the SSL/server factory mechanism supported by your Spring gRPC version; do not create a separate standalone server just to enable mTLS.

## 1. How Does mTLS Authenticate Both Sides?

In one-way TLS, the client verifies the server certificate. In mTLS, the server requires the client to present a certificate and verifies that certificate before the handshake completes.

Both sides have separate trust sets:

| Side | Certificate Presented | Trust Roots Used to Verify Peer |
| --- | --- | --- |
| Client | Client certificate chain and proof-of-possession via private key | CA that issued the server certificate |
| Server | Server certificate chain and proof-of-possession via private key | CA that issued the client certificate |

Do not confuse these two trust stores. The client trust root verifies the server; the server trust root verifies the client. A client certificate should not be placed in the server trust store as a trust anchor if the goal is to trust the CA that issues client certificates. Typically, the server trusts the client CA, then verifies the leaf certificate and chain presented by the client.

    sequenceDiagram
        participant C as gRPC client
        participant S as gRPC server
        C->>S: TLS ClientHello (SNI)
        S-->>C: Server certificate chain
        C->>C: Verify server chain + hostname
        S-->>C: CertificateRequest (mTLS)
        C->>S: Client certificate chain
        C->>S: Proof of private-key possession
        S->>S: Verify client chain + clientAuth purpose
        Note over C,S: TLS handshake succeeds
        C->>S: gRPC request over HTTP/2
        S->>S: Map client identity + authorize method

If the client has no certificate, the certificate was not issued by a trusted CA, or the private key does not match, the server can reject the handshake before any RPC handler/interceptor runs. If the handshake succeeds but the identity lacks permission to call the method, the application returns an authorization error such as PERMISSION_DENIED.

mTLS authenticates the peer at the transport layer. It does not automatically decide which orders the client may read, which tenant it may access, or which RPCs it may invoke. Authorization still belongs to application policy.

## 2. Issuing Client Certificates

A client certificate should be issued to a specific workload, service account, or client identity. Do not share one certificate/private key across all applications when independent auditing and permission revocation are needed.

### 2.1. Choosing Identity in SAN and EKU

A client certificate should have:

- Subject Alternative Name (SAN) representing a system-managed identity, such as a URI SAN per SPIFFE or a DNS SAN for a workload.
- Extended Key Usage (EKU) containing clientAuth to indicate the client authentication purpose.
- Key Usage appropriate for the algorithm, usually including digitalSignature.
- Basic Constraints CA:FALSE because this is a leaf certificate, not a CA.
- Validity period matching issuance and rotation policies.

Example identity URI:

    URI:spiffe://example.org/ns/commerce/sa/inventory-client

URI SAN fits systems that identify workloads by URI/SPIFFE ID. If the infrastructure uses DNS identities, DNS SAN can be used per policy. Do not rely solely on CN or an arbitrary subject string to grant permissions; choose a standard identity field with canonicalization rules and a trusted issuer.

### 2.2. Generating the Private Key and CSR

Example OpenSSL configuration for a client CSR:

    [ req ]
    prompt = no
    distinguished_name = subject
    req_extensions = client_extensions

    [ subject ]
    CN = inventory-client

    [ client_extensions ]
    basicConstraints = critical,CA:FALSE
    keyUsage = critical,digitalSignature
    extendedKeyUsage = clientAuth
    subjectAltName = @client_names

    [ client_names ]
    URI.1 = spiffe://example.org/ns/commerce/sa/inventory-client

Generate the private key and CSR:

    openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out client-key.pem
    openssl req -new -key client-key.pem -out client.csr -config client-san.cnf

A CSR only asks the CA to include extensions in the certificate. The CA may apply its own profile, ignore requester-declared extensions, or only accept pre-registered SANs. After the CA signs it, inspect the final certificate; do not assume SAN/EKU in the CSR are guaranteed to appear in the certificate.

### 2.3. Issuing the Chain and Inspecting the Certificate

Deployments typically have these files:

    client-identity/
    ├── client-chain.pem
    └── client-key.pem

client-chain.pem contains the leaf client certificate first, followed by necessary intermediate certificates. The root CA is normally already configured on the server as a trust anchor, so it does not need to be sent in the chain. client-key.pem is the private key and must be protected.

Inspect the certificate:

    openssl x509 -in client-chain.pem -noout -subject -issuer -dates -ext subjectAltName -ext extendedKeyUsage

Verify the chain for the client authentication purpose:

    openssl verify -purpose sslclient -CAfile client-root-ca.pem -untrusted client-intermediate.pem client-chain.pem

The result should show the chain is valid under the trust root and usage purpose. The verify command does not prove the private key matches the leaf certificate; the public key must be checked separately.

### 2.4. Verifying That the Private Key Matches the Certificate

Compute the public key digest from the certificate and from the private key:

    openssl x509 -in client-chain.pem -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256
    openssl pkey -in client-key.pem -pubout -outform DER | openssl dgst -sha256

Both digests must be identical. If they do not match, the client cannot prove ownership of the private key corresponding to the certificate and the TLS handshake will fail.

Do not print the private key to the terminal, logs, or CI artifacts. Only the public certificate and public key fingerprint are suitable to display during verification.

## 3. Configuring a gRPC Java Client to Present a Client Certificate

gRPC Java uses TlsChannelCredentials to configure server trust roots and client key material.

    import io.grpc.ChannelCredentials;
    import io.grpc.Grpc;
    import io.grpc.ManagedChannel;
    import io.grpc.TlsChannelCredentials;

    import java.io.InputStream;
    import java.nio.file.Files;
    import java.nio.file.Path;

    ChannelCredentials credentials;

    try (InputStream serverRoots =
             Files.newInputStream(Path.of("certs/server-root-ca.pem"));
         InputStream clientChain =
             Files.newInputStream(Path.of("certs/client-chain.pem"));
         InputStream clientPrivateKey =
             Files.newInputStream(Path.of("secrets/client-key.pem"))) {

        credentials = TlsChannelCredentials.newBuilder()
                .trustManager(serverRoots)
                .keyManager(clientChain, clientPrivateKey)
                .build();
    }

    ManagedChannel channel = Grpc.newChannelBuilder(
            "dns:///inventory.internal.example.com:9090",
            credentials)
            .build();

In this configuration:

- trustManager(serverRoots) specifies the CA the client trusts to verify the server certificate.
- keyManager(clientChain, clientPrivateKey) provides the client certificate chain and private key to present to the server.
- Target uses a DNS name included in the server certificate's SAN; hostname verification is still performed.
- A channel with this client identity will present that same identity for RPCs using the channel.

This is a gRPC Java API example; check overloads and PEM format according to the dependency version in use. The private key must be in a format supported by the TLS provider, typically PEM PKCS#8. Do not put the server private key into a client channel and do not put the client private key into a trust manager.

### 3.1. Using the Channel in a Spring Application

In Spring, create the channel as a shared bean per endpoint and inject stubs into adapters:

    @Configuration(proxyBeanMethods = false)
    public class InventoryGrpcClientConfiguration {

        @Bean(destroyMethod = "shutdown")
        ManagedChannel inventoryChannel(MtlsMaterial material)
                throws IOException {
            try (InputStream serverCa = material.serverCa().getInputStream();
                 InputStream clientChain = material.clientChain().getInputStream();
                 InputStream clientKey = material.clientPrivateKey().getInputStream()) {

                ChannelCredentials credentials =
                        TlsChannelCredentials.newBuilder()
                                .trustManager(serverCa)
                                .keyManager(clientChain, clientKey)
                                .build();

                return Grpc.newChannelBuilder(material.target(), credentials)
                        .build();
            }
        }

        @Bean
        InventoryGrpc.InventoryBlockingStub inventoryStub(
                ManagedChannel inventoryChannel) {
            return InventoryGrpc.newBlockingStub(inventoryChannel);
        }
    }

MtlsMaterial represents configuration bound by the application from a secure source, containing the target and corresponding Resources. This is an application-defined configuration type, not a built-in Spring gRPC class.

Do not create a new channel for every RPC. Because a channel carries client identity, all calls over the channel use the same credentials; if two workloads need different identities, create separate channels/credentials for each identity and manage their lifecycles separately. When the context closes, shutdown begins graceful shutdown; if in-flight RPCs must drain within a deadline, add a lifecycle owner with an explicit timeout and forced shutdown.

## 4. Configuring the Server to Require a Client Certificate

The server needs two groups of material:

1. Server certificate chain and server private key so clients can verify the server.
2. CA trust roots so the server can verify client certificates.

With gRPC Java:

    import io.grpc.Server;
    import io.grpc.ServerCredentials;
    import io.grpc.TlsServerCredentials;

    import java.io.InputStream;

    ServerCredentials credentials;

    try (InputStream serverChain = openServerCertificateChain();
         InputStream serverKey = openServerPrivateKey();
         InputStream clientCaRoots = openClientCaBundle()) {

        credentials = TlsServerCredentials.newBuilder()
                .keyManager(serverChain, serverKey)
                .trustManager(clientCaRoots)
                .clientAuth(TlsServerCredentials.ClientAuth.REQUIRE)
                .build();
    }

    Server server = Grpc.newServerBuilderForPort(9090, credentials)
            .addService(new InventoryGrpcEndpoint())
            .build()
            .start();

ClientAuth.REQUIRE requires the client to send a valid certificate during the handshake. The server verifies the client's chain against the CAs in trustManager. If mTLS is not needed, do not accidentally enable the client certificate requirement; one-way TLS server authentication only needs server key material.

### 4.1. Integrating into Spring gRPC

In a Spring application, `@GrpcService` beans and the server lifecycle are normally managed by Spring gRPC. When enabling mTLS:

- Pass the server certificate/key and client CA trust bundle into the TLS configuration of the server factory/transport in use.
- Enable the client certificate requirement mode equivalent to ClientAuth.REQUIRE.
- Keep service definitions bound to the same server instance that has the TLS credentials.
- Use the extension point supported by the documentation of your Spring gRPC version; properties and factory APIs may differ by starter/transport.
- Do not create a second manual server just to configure mTLS if the starter already owns the server handling traffic.

If there are multiple listeners/servers, clearly identify which listener requires mTLS. A management endpoint or separate HTTP listener does not automatically share the same client certificate policy as the gRPC listener.

## 5. From Verified Certificate to Application Identity

After the TLS handshake succeeds, the server knows the peer presented a certificate accepted by the trust manager. The application can retrieve the peer certificate from the transport's SSL session to map it to an internal principal.

In a gRPC Java server interceptor, the transport may provide the SSL session via the attribute Grpc.TRANSPORT_ATTR_SSL_SESSION:

    SSLSession session =
            call.getAttributes().get(Grpc.TRANSPORT_ATTR_SSL_SESSION);

    if (session == null) {
        call.close(Status.UNAUTHENTICATED
                .withDescription("TLS connection required")
                .asRuntimeException(), new Metadata());
        return new ServerCall.Listener<>() {};
    }

    try {
        X509Certificate clientCertificate =
                (X509Certificate) session.getPeerCertificates()[0];

        // Use an application-defined identity mapper to read the SAN,
        // verify issuer/identity policy, and build an internal principal.
    } catch (SSLPeerUnverifiedException ex) {
        call.close(Status.UNAUTHENTICATED
                .withDescription("Unable to verify client certificate")
                .asRuntimeException(), new Metadata());
        return new ServerCall.Listener<>() {};
    }

This snippet shows retrieving the peer certificate inside a server interceptor; place it inside the interceptCall method with the appropriate generics and imports. The SSL session attribute depends on a transport that supports TLS. In mandatory mTLS, the handshake has already verified the certificate before the RPC is dispatched; the interceptor should not attempt to replace TLS signature/chain verification itself.

### 5.1. Identity Mapping and Authorization

A policy can map a verified URI SAN to a principal:

    spiffe://example.org/ns/commerce/sa/inventory-client
        -> principal: inventory-client
        -> allowed methods:
           commerce.v1.Inventory/GetStock
           commerce.v1.Inventory/WatchStock

When authorizing, check at least:

- Identity SAN according to the specified format; avoid relying on arbitrary CN values.
- Approved issuer/CA or trust domain.
- Full method name that the client is calling.
- Tenant, resource scope, and identity status per policy.
- Additional constraints such as environment or audience if defined by the system.

A valid client certificate only proves the peer owns an identity issued by a trusted CA. It does not mean the client is allowed to call every method. Use UNAUTHENTICATED for missing/invalid authentication; use PERMISSION_DENIED when the identity is authenticated but lacks permission.

Do not include full certificates, serials, or sensitive subjects in responses to clients. Log normalized fingerprints/identities per audit policy, and avoid logging private material.

## 6. Distinguishing Handshake Errors and Authorization Errors

mTLS can reject connections before an RPC is created. Therefore, not every client certificate error appears as a gRPC status returned by an interceptor.

| Scenario | Stage | Typical Outcome |
| --- | --- | --- |
| Client sends no certificate in REQUIRE mode | TLS handshake | Handshake rejected; RPC handler has not run |
| Client certificate issued by an untrusted CA | TLS handshake | Chain validation fails |
| Certificate expired or unsuitable EKU | TLS handshake | Certificate rejected per TLS/PKI policy |
| Private key does not match certificate | TLS handshake | Client fails to prove key ownership |
| Handshake succeeds but SAN identity is not permitted by app policy | RPC authorization | PERMISSION_DENIED |
| Valid identity but method requires another role | RPC authorization | PERMISSION_DENIED |

Depending on the transport and client API, handshake failures may be observed as a TLS exception, channel failure, or generic RPC status. When diagnosing, inspect the root cause in client/server logs and appropriate TLS debugging; do not conclude the interceptor ran if the handshake never completed.

## 7. Managing Private Keys and the Certificate Lifecycle

The client private key is a secret. If multiple workloads share a single key, compromising one workload may force revoking the identity of all of them. Recommended practices:

- Store keys in a secret manager, KMS/HSM, or secret mount with least-privilege access.
- Do not commit keys to Git, public images, CI artifacts, or logs.
- Separate keys/certificates by workload, environment, and permissions.
- Prefer short-lived certificates if PKI supports automated issuance/renewal.
- Monitor expiry and alert before certificates expire.
- Have a key and certificate rotation procedure: deploy new credentials, verify connectivity, then revoke old credentials.
- Do not share a channel carrying a client identity across tenants/clients requiring distinct identities.
- Define a revocation mechanism: CRL/OCSP or policy denylist/short-lived certificates depending on PKI and TLS provider capabilities.

Do not assume Java/gRPC automatically checks every CRL/OCSP under default settings. If revocation checking is required, it must be explicitly configured and tested in the trust manager/provider or the system's PKI integration.

### 7.1. Client CA Rotation

When the server migrates from an old client CA to a new CA, deploy an overlapping trust bundle:

1. Install the new CA on the server while the old CA is still trusted.
2. Issue client certificates from the new CA and roll them out to each workload.
3. Verify new clients complete mTLS and authorization properly.
4. Monitor clients still using the old chain.
5. Remove the old CA once no valid workloads need it, except in emergency revocation due to compromise.

If the trust bundle is loaded at server startup, replacing the CA file may not update the running trust manager. Use a supported reload mechanism or perform a controlled rolling restart of the server.

## 8. Testing mTLS

An integration test should start an mTLS server using dedicated CA and certificate fixtures, then create a client channel with appropriate trust roots and client identity.

Cases to include:

| Test | Server Policy | Client Material | Expected Result |
| --- | --- | --- | --- |
| Valid client | REQUIRE | Certificate from trusted CA, matching key | Handshake and RPC succeed |
| No client certificate | REQUIRE | Only server trust roots | Handshake fails |
| Untrusted client CA | REQUIRE | Certificate issued by another CA | Handshake fails |
| Expired certificate | REQUIRE | Expired certificate | Handshake fails |
| Wrong EKU purpose | REQUIRE | Certificate with only serverAuth or unsuitable EKU | Rejected per TLS/PKI validation |
| Key mismatch | REQUIRE | Certificate and private key from different pairs | Handshake fails |
| Unauthorized identity | REQUIRE | Valid certificate but SAN lacks permission | Handshake succeeds, RPC returns PERMISSION_DENIED |
| Unauthorized method | REQUIRE | Valid identity calling forbidden method | RPC returns PERMISSION_DENIED |

Use a dedicated test CA and test private keys never reused in production. Tests should invoke a real generated stub over a TLS channel, not only unit-test the interceptor, because handshake and chain validation are critical parts of mTLS.

OpenSSL can be used to verify the client certificate chain:

    openssl verify -purpose sslclient -CAfile client-root-ca.pem -untrusted client-intermediate.pem client-chain.pem

To test that the server requires a client certificate, use a TLS client with appropriate certificate/key or a gRPC integration test. OpenSSL can verify the handshake, but RPC tests are still needed to confirm HTTP/2, service binding, and authorization.

## 9. Common Mistakes

| Symptom | Cause | Resolution |
| --- | --- | --- |
| One-way TLS client works but mTLS fails | Client does not present a certificate or server does not trust client CA | Configure client key manager and server trust manager |
| Server reports unknown CA when client connects | Client chain does not lead to a CA trusted by the server | Supply proper intermediates and install the right client CA trust root |
| Client certificate rejected despite valid chain | EKU/key usage unsuitable for client authentication | Issue a certificate profile with clientAuth and proper key usage |
| Handshake fails due to key mismatch | Client private key does not match leaf certificate | Compare public key fingerprints and deploy a matching pair |
| Handshake succeeds but RPC is rejected | Identity lacks method/tenant permissions | Check SAN mapping and authorization policy |
| Client does not send cert despite configuration | Channel credentials only have trustManager without keyManager, or another channel is being used | Verify credentials attached to the right ManagedChannel and client key material |
| Client identities mixed across tenants | Reusing a channel with the same client certificate for multiple identities | Create separate channels/credentials per identity or workload |
| CA rotation disconnects old clients | Server removed old CA before client rollout finished | Use trust overlap, monitor migration, then remove old CA |
| Certificate revocation has no effect | Revocation checking not enabled or policy not applied | Define and test CRL/OCSP/denylist/short-lived certs |
| Logs do not show whether handshake or authorization failed | Only logging final status, lacking TLS diagnostics | Classify handshake errors vs. RPC errors; log causes safely on both sides |

## 10. Hands-on Exercises

1. Create a test client CA and issue a client certificate with a URI SAN and EKU clientAuth.
2. Use OpenSSL to verify the certificate chain with -purpose sslclient; compare the public key digest between the certificate and private key.
3. Configure a gRPC Java client using TlsChannelCredentials with server trust root and client key material.
4. Configure a Spring gRPC server to require client certificates using the mechanism supported by your project's server factory.
5. Call an RPC with a valid client certificate, then remove the key manager to verify the handshake is rejected.
6. Use a certificate issued by a CA not trusted by the server; distinguish chain validation errors from hostname errors.
7. Write an interceptor that maps the URI SAN to a principal and checks permissions by full method name.
8. Verify that a valid identity without permissions receives PERMISSION_DENIED, while an invalid certificate is rejected at the handshake.
9. Practice client certificate and CA rotation with a trust overlap period.
10. Test the revocation/denylist process or short-lived certificates according to your system's PKI policy.
