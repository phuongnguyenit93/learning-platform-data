# Testing empty, multi-item, and error streams

## 1. Three outcomes to test in server streaming

In **SPRING_GRPC**, a server streaming RPC accepts one request and returns multiple Protocol Buffers responses on the same RPC. Therefore, tests cannot merely assert that "a message was received." You must verify count, ordering, and the **final RPC outcome**.

Three fundamental cases:

1. **Empty stream:** the server emits zero responses yet completes successfully with `onCompleted()`. The client observes an exhausted iterator or `onCompleted` callback.
2. **Multi-item stream:** the server calls `onNext` multiple times in order and then `onCompleted`. The client receives all messages in the exact order.
3. **Error stream:** the server may call `onError` before the first response or after several responses. The client must observe the exact error status and must not mark the RPC successful.

~~~mermaid
flowchart TD
    A["Client invokes server streaming RPC"] --> B{"Server handles request"}
    B --> C["Zero items"]
    B --> D["N items"]
    B --> E["Error occurs"]
    C --> F["onCompleted / OK"]
    D --> G["onNext × N"]
    G --> H["onCompleted / OK"]
    E --> I{"Response already emitted?"}
    I -- "No" --> J["onError / error status"]
    I -- "Yes" --> K["onError after partial data"]
~~~

The goal of this lesson is to build tests targeting these three outcomes using gRPC Java's **in-process transport**. This tests the proto, stubs, serialization, message ordering, and statuses without opening network ports. Afterward, understand which aspects require additional testing with a Spring context or real transport environment.

## 2. Sample contract used in testing

A small proto keeps the test cases easy to read:

~~~proto
syntax = "proto3";

package teststream.v1;

option java_multiple_files = true;
option java_package = "com.example.streamtest.rpc";

service SampleStreamService {
  rpc ReadItems(ReadItemsRequest) returns (stream StreamItem);
}

message ReadItemsRequest {
  string scenario = 1;
  int32 count = 2;
}

message StreamItem {
  int64 sequence = 1;
  string value = 2;
}
~~~

`scenario` is solely a parameter of the mock service used in tests to pick a behavior; it is not necessarily a field to put in a production business API. The Java classes `ReadItemsRequest`, `StreamItem`, and `SampleStreamServiceGrpc` are generated by `protoc` and the gRPC Java plugin.

## 3. Setting up the in-process server and channel

In-process transport runs both server and client in the same process while still exercising the real gRPC API and generated stubs. A JUnit 5 fixture can start the server before each test and shut down resources afterward:

~~~java
import com.example.streamtest.rpc.ReadItemsRequest;
import com.example.streamtest.rpc.SampleStreamServiceGrpc;
import com.example.streamtest.rpc.StreamItem;
import io.grpc.ManagedChannel;
import io.grpc.Server;
import io.grpc.inprocess.InProcessChannelBuilder;
import io.grpc.inprocess.InProcessServerBuilder;
import io.grpc.stub.StreamObserver;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;

import java.io.IOException;
import java.util.Iterator;

class ServerStreamBehaviorTest {
    private Server server;
    private ManagedChannel channel;

    @BeforeEach
    void startTransport() throws IOException {
        String serverName = InProcessServerBuilder.generateName();

        server = InProcessServerBuilder.forName(serverName)
                .directExecutor()
                .addService(new ScriptedStreamService())
                .build()
                .start();

        channel = InProcessChannelBuilder.forName(serverName)
                .directExecutor()
                .build();
    }

    @AfterEach
    void stopTransport() {
        if (channel != null) {
            channel.shutdownNow();
        }
        if (server != null) {
            server.shutdownNow();
        }
    }

    private Iterator<StreamItem> invoke(String scenario, int count) {
        ReadItemsRequest request = ReadItemsRequest.newBuilder()
                .setScenario(scenario)
                .setCount(count)
                .build();

        return SampleStreamServiceGrpc.newBlockingStub(channel)
                .withDeadlineAfter(3, java.util.concurrent.TimeUnit.SECONDS)
                .readItems(request);
    }
}
~~~

`directExecutor()` runs test callbacks directly on the calling executor, making examples simple and deterministic. It does not fully simulate thread scheduling, backpressure, or production network latency. The short deadline on the stub serves as a guardrail so tests never hang indefinitely if the mock service misbehaves.

## 4. Scripted service simulating three scenarios

Tests need a service with deterministic behavior: returning empty, returning multiple items, or emitting an error. This scripted service is intentionally for test use only:

~~~java
import com.example.streamtest.rpc.ReadItemsRequest;
import com.example.streamtest.rpc.SampleStreamServiceGrpc;
import com.example.streamtest.rpc.StreamItem;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;

final class ScriptedStreamService
        extends SampleStreamServiceGrpc.SampleStreamServiceImplBase {

    @Override
    public void readItems(
            ReadItemsRequest request,
            StreamObserver<StreamItem> responses) {

        String scenario = request.getScenario();

        if ("empty".equals(scenario)) {
            responses.onCompleted();
            return;
        }

        if ("many".equals(scenario)) {
            int count = request.getCount();
            for (int i = 1; i <= count; i++) {
                responses.onNext(StreamItem.newBuilder()
                        .setSequence(i)
                        .setValue("item-" + i)
                        .build());
            }
            responses.onCompleted();
            return;
        }

        if ("error-before-first".equals(scenario)) {
            responses.onError(Status.INVALID_ARGUMENT
                    .withDescription("Invalid test request")
                    .asRuntimeException());
            return;
        }

        if ("error-after-two".equals(scenario)) {
            responses.onNext(StreamItem.newBuilder()
                    .setSequence(1)
                    .setValue("item-1")
                    .build());
            responses.onNext(StreamItem.newBuilder()
                    .setSequence(2)
                    .setValue("item-2")
                    .build());
            responses.onError(Status.UNAVAILABLE
                    .withDescription("Test source interrupted")
                    .asRuntimeException());
            return;
        }

        responses.onError(Status.INVALID_ARGUMENT
                .withDescription("Unknown test scenario")
                .asRuntimeException());
    }
}
~~~

Each branch terminates with exactly one terminal signal:

- Empty stream: `onCompleted`.
- Multi-item stream: multiple `onNext` calls, then `onCompleted`.
- Error before first response: `onError(INVALID_ARGUMENT)`.
- Error after two responses: two `onNext` calls, then `onError(UNAVAILABLE)`.

Never call `onCompleted` after `onError`, and never emit `onNext` after a terminal signal. If the production service depends on a repository or event publisher, integration tests should replace the scripted service with the real implementation and drive the data source through a mock/fake capable of failing at deterministic positions.

## 5. Testing an empty stream

An empty stream is **not an error**. When a query is valid yet yields zero items, the server calls `onCompleted()` without calling `onNext()`. With the blocking stub, the iterator must immediately report no items:

~~~java
import static org.junit.jupiter.api.Assertions.assertFalse;

@org.junit.jupiter.api.Test
void emptyStreamCompletesSuccessfully() {
    Iterator<StreamItem> stream = invoke("empty", 0);

    assertFalse(stream.hasNext());
}
~~~

This test verifies:

- Zero responses were delivered.
- The RPC completed normally instead of throwing `StatusRuntimeException`.
- The client does not confuse "no data" with a source error.

If the API must distinguish "object does not exist" from "object exists with zero events," the contract must state it explicitly: the former can return `NOT_FOUND`, while the latter returns an empty stream and `OK` status. Do not use an empty stream to hide an error the client needs to know about.

## 6. Testing a multi-item stream

A multi-item stream test must verify **exact count**, **ordering**, and **values of each response**. Checking `hasNext()` once does not prove the server emitted the full dataset.

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;

@org.junit.jupiter.api.Test
void streamReturnsAllItemsInOrder() {
    Iterator<StreamItem> stream = invoke("many", 4);

    java.util.List<StreamItem> received = new java.util.ArrayList<>();
    while (stream.hasNext()) {
        received.add(stream.next());
    }

    assertEquals(4, received.size());
    assertEquals(
            java.util.List.of(1L, 2L, 3L, 4L),
            received.stream().map(StreamItem::getSequence).toList());
    assertEquals(
            java.util.List.of("item-1", "item-2", "item-3", "item-4"),
            received.stream().map(StreamItem::getValue).toList());
}
~~~

The loop exits normally only if the RPC completes successfully. If the server emits three responses and then fails, `hasNext()` or the next read operation will throw `StatusRuntimeException` instead of returning `false`.

Also add boundary cases:

- `count = 1`: stream with exactly one response.
- `count` equal to the service's maximum limit: verify request bounds.
- `count = 0` or negative: verify status per contract, if the service does not treat this as an empty stream.
- Multiple messages with identical payloads but different sequences: do not rely on payload text to infer ordering.

## 7. Testing an error before the first response

If a request is invalid or the server cannot open the data source, the server can immediately fail with an error status. The client must receive no fake responses and must not see normal iterator exhaustion:

~~~java
import io.grpc.Status;
import io.grpc.StatusRuntimeException;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

@org.junit.jupiter.api.Test
void errorBeforeFirstItemIsExposedAsStatus() {
    Iterator<StreamItem> stream = invoke("error-before-first", 0);

    StatusRuntimeException error = assertThrows(
            StatusRuntimeException.class,
            stream::hasNext);

    assertEquals(Status.Code.INVALID_ARGUMENT,
            error.getStatus().getCode());
}
~~~

What matters is asserting the status code; avoid coupling tightly to the full `description` string if messages may evolve. When the client needs to branch on errors, rely on `Status.Code` or structured error details per contract.

## 8. Testing an error after receiving partial data

This is the most critical server streaming test case. The client receives two responses before the server returns `UNAVAILABLE`. Those two responses were delivered to the client, yet **the overall RPC failed**:

~~~java
@org.junit.jupiter.api.Test
void errorAfterTwoItemsDoesNotLookLikeSuccessfulCompletion() {
    Iterator<StreamItem> stream = invoke("error-after-two", 0);

    assertEquals(1L, stream.next().getSequence());
    assertEquals(2L, stream.next().getSequence());

    StatusRuntimeException error = assertThrows(
            StatusRuntimeException.class,
            stream::hasNext);

    assertEquals(Status.Code.UNAVAILABLE,
            error.getStatus().getCode());
}
~~~

This test separates two facts:

- The client **received** two messages.
- The RPC **did not complete successfully** because the terminal status is `UNAVAILABLE`.

Never write a test that merely counts two responses and declares success. If the client writes data to a database, separately test application checkpoints/transactions. Transport tests cannot prove side effects were durably committed.

## 9. Testing asynchronous observers

With the asynchronous stub, the client receives each response via `onNext`, followed by one of the two terminal callbacks: `onCompleted` or `onError`. A test should record the callback sequence to verify ordering:

~~~java
java.util.List<String> callbacks =
        new java.util.concurrent.CopyOnWriteArrayList<>();
java.util.concurrent.CountDownLatch terminal =
        new java.util.concurrent.CountDownLatch(1);

SampleStreamServiceGrpc.newStub(channel)
        .withDeadlineAfter(3, java.util.concurrent.TimeUnit.SECONDS)
        .readItems(
                ReadItemsRequest.newBuilder()
                        .setScenario("error-after-two")
                        .build(),
                new io.grpc.stub.StreamObserver<StreamItem>() {
                    @Override
                    public void onNext(StreamItem item) {
                        callbacks.add("next-" + item.getSequence());
                    }

                    @Override
                    public void onError(Throwable error) {
                        callbacks.add("error-" +
                                io.grpc.Status.fromThrowable(error)
                                        .getCode().name());
                        terminal.countDown();
                    }

                    @Override
                    public void onCompleted() {
                        callbacks.add("completed");
                        terminal.countDown();
                    }
                });

assertTrue(terminal.await(3, java.util.concurrent.TimeUnit.SECONDS));
assertEquals(
        java.util.List.of("next-1", "next-2", "error-UNAVAILABLE"),
        callbacks);
~~~

This snippet assumes it runs inside a test with `channel` and required JUnit imports. `CopyOnWriteArrayList` keeps callback collection thread-safe in the test; the latch waits for the terminal callback without arbitrary sleeps. With asynchronous executors, never inspect the list before the latch completes.

Never expect `onCompleted` to fire after `onError`. Those are mutually exclusive terminal callbacks. Nor does the client call them directly; the gRPC runtime invokes the appropriate callback upon receiving the RPC outcome.

## 10. Test matrix and common testing mistakes

| Scenario | Messages client receives | Expected outcome |
|---|---:|---|
| Valid query, zero records | 0 | `OK` / `onCompleted` |
| Valid query, N items | N | All N messages in order, then `OK` |
| Invalid request before emission | 0 | Error status such as `INVALID_ARGUMENT` |
| Source failure after k items | May be k or fewer depending on transport | Error status; do not mark stream complete |
| Single-item error when contract allows continuing | Valid results plus an item-error message | Can terminate `OK` |
| Deadline expires mid-stream | Partial or zero messages | `DEADLINE_EXCEEDED` at client |
| Client proactively cancels | Partial or zero messages | Cancellation; server cleanup |

Common testing mistakes:

- **Asserting only count:** misses wrong ordering or wrong payloads.
- **Asserting only `onNext`:** ignores terminal status; the stream may fail afterward.
- **Using `sleep` to wait for callbacks:** makes tests flaky depending on machine speed; use `CountDownLatch` or futures.
- **Forgetting to close channel/server:** leaks threads and interferes with subsequent tests.
- **Testing a mock service and claiming Spring integration is verified:** in-process tests verify gRPC contracts/transport, not Spring bean registration, interceptors, or TLS configuration.
- **Asserting exact status description strings:** makes tests brittle when error messages are refined; prefer checking status codes and structured metadata.

## 11. When are Spring context and real transport tests needed?

In-process tests are great for core gRPC behavior: empty streams, multiple responses, ordering, and terminal statuses. However, they do not run the full Spring application infrastructure or simulate real networks.

Add `@SpringBootTest` or appropriate integration tests when you need to verify:

- Spring gRPC auto-registers the service bean and endpoint configuration properly.
- Authentication, authorization, and tracing interceptors are applied.
- Real repository errors map to expected gRPC statuses.
- TLS, certificates, proxies/load balancers, and message limits behave properly.
- Cancellation/deadlines close cursors, subscriptions, timers, and source resources.

For data source errors, a fake repository can yield two records and then throw a deterministic exception to test the real service implementation. For transport, tests over real network ports must manage timeouts and cleanup; do not replace fast unit/in-process logic tests with slow network tests.

## 12. Checklist for a server streaming test suite

- [ ] Empty stream test verifying `OK` completion.
- [ ] Multi-response test verifying count, sequence, ordering, and payloads.
- [ ] Error-before-first-response test verifying status code.
- [ ] Error-after-partial-responses test verifying partial data and terminal error.
- [ ] Test verifying `onCompleted` is never emitted after `onError`.
- [ ] Tests for input bounds, deadlines, and cancellation where applicable.
- [ ] Async tests use latches/futures instead of arbitrary `sleep` calls.
- [ ] Server and channel are shut down in `finally`/test lifecycle hooks.
- [ ] Dedicated integration tests cover Spring context, interceptors, and TLS if required for deployment.

**Key takeaway:** Server streaming tests must verify both the **response sequence** and the **terminal status**. An empty stream can complete `OK`; a multi-item stream must deliver all messages in order; an error stream may deliver partial data yet still end in an unsuccessful status. Test all three cases with stubs/transport, then test Spring wiring, real data sources, and network infrastructure separately as needed.
