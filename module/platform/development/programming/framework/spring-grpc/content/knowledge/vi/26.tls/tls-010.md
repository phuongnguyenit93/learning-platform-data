# Debug TLS an toàn

## Mục tiêu bài học

Trong **SPRING_GRPC**, lỗi kết nối có thể xuất hiện ở nhiều lớp: DNS/TCP, TLS handshake, xác minh certificate, ALPN/HTTP/2, gRPC transport hoặc xử lý RPC. Debug hiệu quả cần xác định đúng lớp lỗi, thu thập đủ bằng chứng để tái hiện và giới hạn mức ghi log theo thời gian. Debug TLS không an toàn có thể làm lộ certificate metadata, danh tính nội bộ, token, private key hoặc dữ liệu RPC.

Bài học tập trung vào **debug TLS an toàn**: xây dựng quy trình điều tra theo lớp, dùng OpenSSL để kiểm tra handshake/certificate/ALPN, bật Java TLS diagnostics có kiểm soát, quan sát gRPC channel và server, bảo vệ log/packet capture, và kết thúc phiên debug bằng cách tắt cấu hình chẩn đoán tạm thời.

Sau bài này, bạn có thể:

1. Phân biệt lỗi DNS/TCP, TLS, HTTP/2/ALPN và gRPC.
2. Thu thập thông tin handshake mà không ghi secret hoặc payload nhạy cảm.
3. Dùng OpenSSL kiểm tra certificate chain, hostname, SNI, protocol và ALPN.
4. Bật JSSE diagnostics hoặc logging của Netty trong phạm vi hẹp.
5. Phân loại lỗi TLS một chiều và mTLS.
6. Ghi nhận TLS telemetry an toàn trong Spring gRPC.
7. Viết runbook tái hiện, xử lý và kết thúc debug có kiểm soát.

> **Phạm vi:** Ví dụ dùng gRPC Java, Spring gRPC, Java JSSE, Netty và OpenSSL. Tên logger, API TLS và mức chi tiết log phụ thuộc phiên bản runtime/transport. Chỉ bật diagnostics tăng cường trong môi trường kiểm soát và theo thời gian cần thiết.

## 1. Xác định lớp lỗi trước khi bật debug

Một RPC qua TLS cần đi qua nhiều lớp. Nếu chưa biết lỗi ở đâu, bật trace toàn bộ ứng dụng thường tạo lượng log lớn mà không giúp tìm root cause.

| Lớp | Câu hỏi cần trả lời | Dấu hiệu thường gặp |
| --- | --- | --- |
| DNS/name resolution | Target phân giải ra địa chỉ nào? | Name resolution failure, resolver error |
| TCP | Có mở được socket tới host/port không? | Connection refused, timeout, no route |
| TLS handshake | Hai phía có thống nhất protocol/key/cipher và xác thực peer không? | handshake_failure, protocol_version, certificate error |
| Certificate identity | Chain và hostname có hợp lệ không? | unknown CA, PKIX path error, hostname mismatch |
| ALPN/HTTP/2 | TLS có thương lượng h2 không? | ALPN mismatch, HTTP/2 protocol error |
| gRPC transport | HTTP/2 stream có được tạo không? | UNAVAILABLE, stream reset, GOAWAY |
| RPC/application | Service/method và authorization có hợp lệ không? | UNIMPLEMENTED, UNAUTHENTICATED, PERMISSION_DENIED, lỗi nghiệp vụ |

Quy tắc điều tra:

1. Ghi lại target hostname, port, thời điểm UTC và môi trường.
2. Xác định TLS kết thúc ở gRPC process, sidecar, ingress hay load balancer.
3. Kiểm tra DNS và TCP trước khi điều tra certificate.
4. Kiểm tra handshake và certificate chain.
5. Xác minh ALPN h2 và HTTP/2.
6. Chỉ khi transport hoạt động mới điều tra service, method, metadata và authorization.

TLS handshake thất bại thường xảy ra trước khi RPC handler/interceptor nghiệp vụ chạy. Vì vậy, một lỗi TLS không thể được chẩn đoán đầy đủ chỉ bằng log interceptor.

## 2. Chuẩn bị một phiên debug an toàn

Trước khi thu thập log hoặc chạy lệnh chẩn đoán, xác định:

- Endpoint và hostname client thực sự sử dụng.
- Listener/port TLS và điểm terminate TLS.
- Phiên bản JDK, gRPC Java, Netty/TLS provider.
- Có dùng mTLS hay không.
- Trust store/CA bundle đang được áp dụng.
- Thời điểm bắt đầu lỗi, tần suất và phạm vi client bị ảnh hưởng.
- Một request/correlation ID không chứa dữ liệu cá nhân hoặc secret.

Tạo một cửa sổ debug ngắn, có owner và tiêu chí kết thúc. Ưu tiên staging/canary hoặc một instance riêng. Nếu buộc phải debug production, giới hạn instance, logger, thời gian và người có quyền đọc log.

**Không thu thập hoặc chia sẻ:**

- Private key PEM, keystore password, secret mount hoặc token.
- Nội dung authorization metadata, cookie hay credential header.
- Plaintext request/response hoặc dữ liệu nghiệp vụ không cần thiết.
- TLS session key/key log trong môi trường production.
- Full environment dump hoặc toàn bộ process arguments nếu có thể chứa secret.

Certificate public có thể được trình công khai trong handshake, nhưng subject, SAN, serial và issuer vẫn có thể tiết lộ cấu trúc nội bộ. Chỉ lưu các trường cần thiết, giới hạn quyền truy cập và thời gian retention.

## 3. Kiểm tra endpoint bằng OpenSSL

OpenSSL giúp tách vấn đề TLS khỏi cấu hình channel của ứng dụng. Kiểm tra trực tiếp đúng endpoint, SNI, trust root và hostname:

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -CAfile certs/root-ca.pem \
  -verify_hostname grpc.example.com \
  -verify_return_error \
  -showcerts
```

Đọc kết quả theo thứ tự:

1. TCP connection có được mở không?
2. TLS protocol và cipher nào được thương lượng?
3. Server trình leaf certificate và intermediate nào?
4. Chain có xác minh tới CA root đã chỉ định không?
5. Hostname có khớp SAN không?
6. ALPN có chọn h2 không?

Có thể thêm tùy chọn brief để rút gọn output tùy phiên bản OpenSSL. Khi cần quan sát tiến trình handshake, dùng state hoặc msg trong phiên kiểm tra ngắn và bảo vệ output; không bật trace này liên tục trên hệ thống nhiều kết nối.

### 3.1. Kiểm tra certificate đang được trình

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -showcerts </dev/null
```

Lưu ý: lệnh trên chỉ lấy certificate chain từ endpoint; để xác minh đầy đủ cần thêm CA file và hostname như ví dụ trước. So sánh certificate endpoint đang trình với file local bằng fingerprint:

```bash
openssl x509 -in certs/server.pem -noout \
  -subject -issuer -serial -dates -fingerprint -sha256 \
  -ext subjectAltName -ext extendedKeyUsage
```

Nếu endpoint trình certificate khác file local, điều tra SNI mapping, proxy, secret mount và reload/restart của listener. Đừng kết luận certificate mới đã được nạp chỉ vì file trên disk đã đổi.

### 3.2. Kiểm tra chain offline

```bash
openssl verify \
  -purpose sslserver \
  -CAfile certs/root-ca.pem \
  -untrusted certs/intermediate-ca.pem \
  -verify_hostname grpc.example.com \
  certs/server.pem
```

Lệnh này giúp phân biệt lỗi chain/hostname trong file certificate. Nó không chứng minh server đang trình đúng file đó; cần kết hợp với kiểm tra endpoint thật.

### 3.3. Ép protocol để khoanh vùng

Có thể kiểm tra riêng TLS 1.2 và TLS 1.3:

```bash
openssl s_client -connect grpc.example.com:9090 \
  -servername grpc.example.com -alpn h2 -tls1_2 \
  -CAfile certs/root-ca.pem -verify_hostname grpc.example.com \
  -verify_return_error

openssl s_client -connect grpc.example.com:9090 \
  -servername grpc.example.com -alpn h2 -tls1_3 \
  -CAfile certs/root-ca.pem -verify_hostname grpc.example.com \
  -verify_return_error
```

Nếu một protocol thành công và protocol kia thất bại, so sánh runtime/provider, protocol allowlist, cipher, signature scheme và certificate key type. Không hạ policy production chỉ để làm một lệnh test thành công.

## 4. Debug mTLS có kiểm soát

Khi server yêu cầu client certificate, cần xác minh cả hai hướng:

- Client xác minh server chain và hostname bằng trust roots phía client.
- Server xác minh client chain bằng CA trust roots phía server.
- Client chứng minh quyền sở hữu private key tương ứng với client certificate.

Có thể kiểm tra mTLS bằng OpenSSL với certificate test:

```bash
openssl s_client \
  -connect grpc.example.com:9090 \
  -servername grpc.example.com \
  -alpn h2 \
  -CAfile certs/server-root-ca.pem \
  -cert certs/client-chain.pem \
  -key secrets/client-key.pem \
  -verify_hostname grpc.example.com \
  -verify_return_error
```

Lệnh đọc private key cục bộ để thực hiện handshake; không copy key vào log, ticket hoặc chat. Dùng certificate/key test hoặc secret mount được cấp quyền phù hợp. Để so sánh, chạy một lần không có cert/key nếu server yêu cầu mTLS; handshake dự kiến bị từ chối.

Kiểm tra client certificate và purpose:

```bash
openssl x509 -in certs/client-chain.pem -noout \
  -subject -issuer -dates -ext subjectAltName -ext extendedKeyUsage

openssl verify -purpose sslclient \
  -CAfile certs/client-root-ca.pem \
  -untrusted certs/client-intermediate.pem \
  certs/client-chain.pem
```

Nếu TLS handshake thành công nhưng RPC bị PERMISSION_DENIED, certificate có thể hợp lệ nhưng application identity không được phép gọi method. Không nhầm authorization failure với mTLS handshake rejection.

## 5. Java JSSE TLS diagnostics

Với gRPC transport sử dụng JSSE, có thể bật TLS debug ở một tiến trình thử nghiệm:

```text
-Djavax.net.debug=ssl,handshake,trustmanager
```

Nếu cần điều tra certificate path builder, có thể thử security debug hẹp hơn trong môi trường kiểm soát:

```text
-Djava.security.debug=certpath
```

Các cờ này thường được đặt lúc khởi động JVM. Chúng có thể tạo lượng output lớn, lộ hostname/certificate metadata và chi tiết môi trường. Bật trong thời gian ngắn, giới hạn log file/quyền truy cập, thu thập một lần tái hiện rồi tắt.

Không mặc định JSSE debug quan sát được mọi TLS connection. Một số cấu hình gRPC dùng Netty với native OpenSSL provider; khi đó JSSE diagnostics có thể không hiển thị handshake của listener/channel đó.

### 5.1. Phân biệt JSSE và Netty/OpenSSL

Trước khi tăng log, xác định TLS provider thực tế:

- JSSE: dùng JDK TLS implementation và JSSE diagnostics.
- Netty với OpenSSL native: dùng SSL context/provider của Netty/OpenSSL; cần diagnostics của đúng transport/provider.
- TLS terminate tại proxy: log TLS handshake cần lấy ở proxy; log backend chỉ phản ánh hop proxy-to-backend.

Tên logger và mức DEBUG/TRACE phụ thuộc phiên bản. Không bật TRACE cho toàn bộ package Netty/gRPC nếu chỉ cần một kết nối. Dùng logger hẹp, thời gian ngắn và tái hiện có kiểm soát.

## 6. Quan sát gRPC channel và server

### 6.1. Ghi nhận lỗi ở client

Ở client, giữ lại root cause thay vì chỉ ghi status cuối. Ví dụ:

```java
try {
    InventoryGrpc.InventoryBlockingStub stub =
            InventoryGrpc.newBlockingStub(channel)
                    .withDeadlineAfter(3, TimeUnit.SECONDS);

    return stub.getStock(request);
} catch (StatusRuntimeException ex) {
    Status status = ex.getStatus();
    Throwable cause = ex.getCause();

    // Ghi status code, target đã chuẩn hóa, cause class/message
    // sau khi redaction; không log metadata/token/secret.
    throw ex;
}
```

Đoạn code minh họa điểm thu thập chẩn đoán; không nên nuốt exception hoặc đổi mọi lỗi thành một status mới. Ghi status code, cause chain và target theo chính sách log, rồi giữ nguyên semantics lỗi cho caller.

Phân biệt:

- Channel không kết nối được hoặc TLS handshake fail.
- Deadline hết hạn trong lúc kết nối/thiết lập transport.
- HTTP/2 stream reset/GOAWAY.
- RPC đã tới server nhưng trả status nghiệp vụ.

Một UNAVAILABLE có thể có nhiều root cause. Cần kết hợp exception cause, OpenSSL probe và server/proxy log.

### 6.2. Quan sát SSL session trên server

Với gRPC Java transport hỗ trợ SSL session attribute, server interceptor có thể lấy protocol và cipher đã thương lượng:

```java
SSLSession session =
        call.getAttributes().get(Grpc.TRANSPORT_ATTR_SSL_SESSION);

if (session != null) {
    String protocol = session.getProtocol();
    String cipherSuite = session.getCipherSuite();

    // Ghi metric có cardinality thấp và không chứa secret.
}
```

Đoạn trích cần nằm trong interceptCall của server interceptor. Attribute phụ thuộc transport và chỉ có khi TLS session được expose. Nếu TLS terminate ở proxy, backend có thể không có SSL session của kết nối client-to-proxy; lấy telemetry từ proxy thay vì suy luận từ backend.

Không ghi toàn bộ SSLSession, private key, trust manager object hoặc raw certificate chain vào log. Chỉ ghi protocol/cipher và fingerprint/issuer đã được phê duyệt khi thực sự cần.

### 6.3. Health và connectivity không thay thế TLS diagnostics

Channel state READY cho biết channel có transport sẵn sàng tại thời điểm quan sát; nó không chứng minh mọi hostname/SNI, certificate rotation hoặc mTLS identity đều đúng. Health RPC chỉ chạy được sau khi transport đã thiết lập. Dùng health check cùng handshake probe và RPC integration test.

## 7. Chẩn đoán ALPN và HTTP/2

gRPC qua TLS cần thương lượng ALPN h2. Nếu certificate validation thành công nhưng ALPN không chọn h2, TLS có thể đã hoàn tất trong khi gRPC vẫn không hoạt động đúng.

Trong output OpenSSL, tìm negotiated ALPN. Nếu thiếu h2:

- Kiểm tra client/server có advertise h2 không.
- Kiểm tra proxy có hỗ trợ HTTP/2 ở cả phía downstream và upstream không.
- Kiểm tra TLS termination listener có đúng gRPC protocol configuration không.
- Xác minh port đang kiểm tra thực sự là gRPC listener, không phải REST/management listener.
- Sau khi ALPN đúng, gọi generated stub để kiểm tra HTTP/2 stream và gRPC method.

TLS handshake thành công không chứng minh service name/method tồn tại. Nếu transport đã lên nhưng RPC trả UNIMPLEMENTED, kiểm tra Protobuf package, full service name, method và service registration.

## 8. Bảng phân loại lỗi và hướng điều tra

| Triệu chứng | Bằng chứng cần thu | Hướng điều tra đầu tiên |
| --- | --- | --- |
| Connection refused | TCP error, host/port | Listener, port, firewall, service lifecycle |
| Connect timeout | DNS result, route, TCP timing | Network path, load balancer, endpoint health |
| Unknown CA / PKIX path failure | Trust store fingerprint, server chain | Root/intermediate, đúng trust store |
| Hostname mismatch | Target, SNI, SAN | Logical hostname, DNS alias, certificate SAN |
| Certificate expired/not yet valid | notBefore/notAfter, UTC clock | Renewal, chain expiry, NTP |
| handshake_failure | Protocol, cipher, signature, provider | TLS policy và khả năng hai phía |
| mTLS alert/rejection | Client chain, EKU, server client CA | Client certificate, key pair và server trust |
| ALPN không có h2 | Negotiated ALPN, listener/proxy config | HTTP/2/gRPC listener và proxy upstream |
| UNAVAILABLE sau khi đã có channel | Cause chain, stream/reset, proxy log | Transport, GOAWAY, network hoặc TLS reconnect |
| PERMISSION_DENIED | Principal đã xác thực, method policy | Authorization/interceptor, không phải chain trust |
| UNIMPLEMENTED | HTTP/2 request path và service descriptor | Protobuf package/service/method registration |

Không gán nguyên nhân dựa trên một status đơn lẻ. Một incident có thể liên quan nhiều lớp, ví dụ proxy trình certificate đúng nhưng upstream HTTP/2 bị tắt.

## 9. Log và telemetry an toàn

Thiết kế log để hỗ trợ điều tra mà không biến log thành kho chứa credential.

**Có thể ghi khi được policy cho phép:**

- Timestamp UTC, environment, instance/listener và correlation ID.
- Target hostname đã chuẩn hóa, port và transport/provider.
- TLS protocol, cipher suite và ALPN.
- Nhóm lỗi chuẩn hóa: expiry, unknown CA, hostname mismatch, protocol mismatch, mTLS rejection.
- Certificate issuer/serial hoặc fingerprint khi cần đối chiếu rotation.
- gRPC status code, latency và retry/connection attempt count.

**Phải loại bỏ hoặc bảo vệ đặc biệt:**

- Private key, keystore/truststore password, token và authorization metadata.
- Raw request/response payload.
- Full environment variables hoặc command line chứa secret.
- Key log/TLS session secrets.
- Full certificate dump nếu không cần; SAN/subject có thể tiết lộ hostname nội bộ hoặc danh tính workload.

Dùng metric label có cardinality thấp. Không gắn serial, fingerprint, request ID hoặc hostname tùy ý vào label metric có thể tạo cardinality lớn; các trường này phù hợp hơn với log/event có kiểm soát.

## 10. Quy trình debug có thể lặp lại

Một runbook ngắn có thể áp dụng cho incident TLS:

1. **Scope:** ghi target, port, thời điểm UTC, môi trường và phạm vi ảnh hưởng.
2. **Locate termination:** xác định TLS kết thúc ở client-to-proxy, proxy-to-backend hay gRPC process.
3. **Probe TCP/TLS:** dùng OpenSSL tới đúng listener với SNI, CA, hostname và ALPN.
4. **Inspect certificate:** xem chain, validity, SAN, EKU, issuer và fingerprint.
5. **Inspect provider:** xác định JSSE hay Netty/OpenSSL; chỉ bật diagnostics tương ứng.
6. **Check gRPC:** gọi generated stub và ghi status/root cause sau redaction.
7. **Fix narrow cause:** sửa trust/chain/SAN/expiry/protocol/proxy đúng nơi phát sinh.
8. **Verify:** mở kết nối mới, kiểm tra TLS/ALPN rồi chạy RPC test.
9. **Cleanup:** tắt debug, khôi phục log level, xóa file tạm theo retention policy và ghi lại kết quả đã redaction.

### 10.1. Điều kiện kết thúc debug

Chỉ đóng phiên điều tra khi:

- Kết nối mới xác minh đúng certificate chain và hostname.
- TLS version/cipher nằm trong policy.
- ALPN thương lượng h2.
- RPC đại diện chạy thành công.
- mTLS hoạt động nếu endpoint yêu cầu.
- Debug logging đã tắt và cấu hình trở về mức bình thường.
- Log/artifact tạm được lưu hoặc xóa theo policy.
- Root cause, fix, owner và biện pháp ngăn tái diễn đã được ghi nhận.

## 11. Lỗi thường gặp khi debug

| Cách debug sai | Rủi ro/hệ quả | Cách làm an toàn |
| --- | --- | --- |
| Tắt certificate verification hoặc dùng trust-all | Che giấu lỗi identity, cho phép MITM | Giữ verification; dùng CA test hợp lệ |
| Bật TLS TRACE toàn process | Log quá lớn, tăng rủi ro lộ metadata | Giới hạn logger, instance và thời gian |
| Chia sẻ private key để người khác tái hiện | Lộ danh tính và quyền của workload | Dùng certificate/key test riêng |
| Chỉ xem gRPC status | Không thấy root cause TLS | Đọc cause chain và kiểm tra endpoint độc lập |
| Chỉ kiểm tra file certificate trên disk | Listener có thể đang trình cert cũ/khác | Probe endpoint với SNI và so fingerprint |
| Bật JSSE debug cho Netty OpenSSL | Không quan sát đúng TLS provider | Xác định provider trước khi bật diagnostics |
| Chỉ kiểm tra handshake, bỏ qua ALPN | TLS pass nhưng HTTP/2/gRPC fail | Xác minh ALPN h2 và gọi generated stub |
| Ghi raw metadata/payload vào log | Lộ token và dữ liệu nghiệp vụ | Redact và ghi status/metadata tối thiểu |
| Giữ debug flag sau incident | Tăng log và lộ thông tin lâu dài | Có checklist tắt debug và xác minh cấu hình |
| Dùng metric label theo fingerprint/request ID | Cardinality tăng mạnh | Dùng metric tổng hợp; chi tiết đặt trong log kiểm soát |

## 12. Bài tập thực hành

1. Tạo một test endpoint gRPC TLS và ghi lại target, SNI, certificate SAN, issuer, validity, TLS version, cipher và ALPN.
2. Dùng OpenSSL tạo các tình huống unknown CA, hostname mismatch, certificate hết hạn và thiếu intermediate; phân biệt output từng trường hợp.
3. Bật JSSE debug trong một JVM test, tái hiện handshake lỗi rồi tắt flag; lưu lại phần log đã redaction.
4. Với Netty/OpenSSL, xác định provider và chọn diagnostics đúng phiên bản thay vì dựa vào JSSE debug.
5. Bật mTLS và kiểm tra client certificate hợp lệ, thiếu certificate, CA không được tin và private key mismatch.
6. Gọi generated stub sau handshake để phân biệt TLS failure với UNIMPLEMENTED hoặc PERMISSION_DENIED.
7. Viết interceptor/telemetry chỉ ghi TLS protocol, cipher và gRPC status; không ghi secret hoặc raw payload.
8. Tạo runbook có scope, lệnh probe, root-cause categories, bước verify và cleanup.
9. Diễn tập một incident certificate rotation: endpoint vẫn trình certificate cũ dù file đã thay; xác định reload/restart đúng listener.

### Câu hỏi tự kiểm tra

- Vì sao cần phân loại DNS/TCP, TLS, ALPN và RPC trước khi bật trace?
- openssl s_client cần những tham số nào để kiểm tra SNI, hostname và HTTP/2?
- Vì sao certificate trên disk có thể khác certificate endpoint đang trình?
- Khi nào JSSE debug không quan sát được handshake gRPC?
- UNAVAILABLE có đủ để kết luận lỗi certificate không?
- Vì sao TLS handshake failure thường không đi qua application interceptor?
- Trong mTLS, phải kiểm tra trust roots và key material ở hai phía như thế nào?
- Vì sao ALPN h2 cần được kiểm tra riêng?
- Những trường nào phù hợp cho TLS telemetry và trường nào phải redaction?
- Điều kiện nào cần đạt trước khi kết thúc một phiên debug TLS?
