# MDC and Correlation Context

## 1. Why Is Correlation Context Needed?

In Spring gRPC, a single logical RPC can pass through client interceptors, server interceptors, services, async executors, databases, and downstream services. These components can run on many different threads. When an error occurs, looking at a single isolated log line is often not enough to know which request it belonged to.

A correlation context carries a stable identifier per request or logical operation to link logs and telemetry across layers. SLF4J/Logback's MDC (Mapped Diagnostic Context) stores key/value pairs bound to the current thread, letting the logger automatically attach values such as a correlation ID to each log line.

These two concepts are related but not identical:

- Correlation context is per-request data that must be propagated across execution boundaries.
- MDC is the thread-specific storage used for logging on a given thread.

MDC is typically based on ThreadLocal. If a gRPC callback or task switches to another thread, MDC does not travel with it automatically. Conversely, thread pools reuse threads, which can leak a previous request's MDC values into the next request if state is not restored.

## 2. Distinguishing gRPC Context, Reactor Context, and MDC

| Mechanism | Scope | How It Works | Propagates Across Arbitrary Threads? |
| --- | --- | --- | --- |
| gRPC Context | gRPC call/request | Scoped context; supports attach/detach and wrapping executors/tasks | Only through APIs or executors with propagation support |
| Reactor Context | A reactive subscription | Immutable data attached to the subscriber chain | Follows the reactive chain, not ThreadLocal |
| SLF4J MDC | Current thread | Thread-local-backed map | No |
| OpenTelemetry Context | Trace/span and baggage | Context propagation via instrumentation/propagators | Via instrumentation or context-aware executors |

Do not treat MDC as a source of business data or a mechanism for passing security principals. It exists solely for logging. Principals, verified tenants, and deadlines belong in contexts with proper semantics, such as gRPC Context or a managed security context.

## 3. Correlation IDs and Trace IDs

A correlation ID is typically an application identifier used to find all logs belonging to one operation. A trace ID belongs to distributed tracing and links spans across multiple services. Both IDs can coexist:

- correlationId: a stable ID generated by the application/gateway or accepted after format validation.
- trace_id and span_id: managed by the tracing SDK according to W3C Trace Context/OpenTelemetry.

If OpenTelemetry is already in place, prefer standard trace context to connect traces across services. A correlation ID remains useful for support tickets, log searches, or linking a business workflow that spans longer than one trace.

Never forge a traceparent or manually stuff a trace ID into MDC to replace the tracing SDK. Parsing, child span creation, sampling, and propagation should be handled by OpenTelemetry propagators and instrumentation.

A client-supplied correlation ID is data for correlation only, not proof of identity or access rights. Never put names, emails, access tokens, session secrets, or personal data inside the ID.

## 4. Receiving and Validating Correlation IDs on the Server

A server interceptor can read the x-correlation-id metadata, validate its format, and generate a new ID if missing or invalid. It then stores the ID in gRPC Context so the service and listener callbacks can access it.

The example below restricts IDs to 64 log-safe ASCII characters:

~~~java
import io.grpc.Context;
import io.grpc.Contexts;
import io.grpc.Metadata;
import io.grpc.ServerCall;
import io.grpc.ServerCallHandler;
import io.grpc.ServerInterceptor;
import java.util.UUID;
import java.util.regex.Pattern;

public final class CorrelationContextInterceptor
        implements ServerInterceptor {

    static final Context.Key<String> CORRELATION_ID =
            Context.key("correlation-id");

    static final Metadata.Key<String> CORRELATION_HEADER =
            Metadata.Key.of(
                    "x-correlation-id",
                    Metadata.ASCII_STRING_MARSHALLER);

    private static final Pattern SAFE_ID =
            Pattern.compile("[A-Za-z0-9._-]{1,64}");

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,
            ServerCallHandler<ReqT, RespT> next) {

        String supplied = headers.get(CORRELATION_HEADER);
        String correlationId =
                supplied != null && SAFE_ID.matcher(supplied).matches()
                        ? supplied
                        : UUID.randomUUID().toString();

        Context requestContext = Context.current()
                .withValue(CORRELATION_ID, correlationId);

        return Contexts.interceptCall(
                requestContext, call, headers, next);
    }
}
~~~

Contexts.interceptCall() attaches the gRPC Context while creating the listener and handling its callbacks. Therefore, the service can read the ID via CORRELATION_ID.get() within the scope of the call.

If the system needs to preserve a gateway-issued ID, the gateway should generate the ID at the trust boundary and strip/overwrite headers sent by external clients. Accepting a client-supplied ID is suitable for assisting log searches, but it must never be used as the basis for authorization.

## 5. Bridging Correlation Context into MDC

gRPC Context does not automatically write values into MDC. You need a bridge that populates MDC around code running under the RPC's context and restores the previous MDC once that code finishes.

~~~java
import io.grpc.Context;
import org.slf4j.MDC;
import java.util.Map;
import java.util.function.Supplier;

public final class MdcContext {

    private MdcContext() {}

    public static void run(Context context, Runnable action) {
        call(context, () -> {
            action.run();
            return null;
        });
    }

    public static <T> T call(Context context, Supplier<T> action) {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        String correlationId =
                context.get(CorrelationContextInterceptor.CORRELATION_ID);

        try {
            if (correlationId == null) {
                MDC.remove("correlationId");
            } else {
                MDC.put("correlationId", correlationId);
            }
            try {
                return context.call(action::get);
            } catch (RuntimeException | Error error) {
                throw error;
            } catch (Exception error) {
                throw new IllegalStateException(
                        "Unexpected checked exception from MDC action", error);
            }
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    }
}
~~~

This helper performs two distinct jobs:

1. Places the correlation ID into MDC on the executing thread and restores the previous map in finally.
2. Attaches the gRPC Context while running the supplier via context.call(...).

Never just call MDC.put() and leave it there. Thread pools can reuse that thread for another RPC; without restoring or clearing, logs for a later request can carry the previous request's correlation ID.

## 6. Wrapping Listener Callbacks So MDC Is Present When the Service Runs

A server interceptor can use Contexts.interceptCall() to propagate gRPC Context, yet MDC still needs to be set around actual callbacks. One way is to wrap ServerCall.Listener callbacks:

~~~java
import io.grpc.Context;
import io.grpc.Contexts;
import io.grpc.Metadata;
import io.grpc.ServerCall;
import io.grpc.ServerCallHandler;
import io.grpc.ServerInterceptor;
import io.grpc.ForwardingServerCallListener;

public final class MdcServerInterceptor
        implements ServerInterceptor {

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,
            ServerCallHandler<ReqT, RespT> next) {

        String id = CorrelationContextInterceptor.CORRELATION_ID.get();
        Context requestContext = Context.current()
                .withValue(CorrelationContextInterceptor.CORRELATION_ID, id);

        return Contexts.interceptCall(
                requestContext,
                call,
                headers,
                new ServerCallHandler<ReqT, RespT>() {
                    @Override
                    public ServerCall.Listener<ReqT> startCall(
                            ServerCall<ReqT, RespT> serverCall,
                            Metadata metadata) {

                        ServerCall.Listener<ReqT> delegate =
                                MdcContext.call(
                                        requestContext,
                                        () -> next.startCall(serverCall, metadata));

                        return new ForwardingServerCallListener
                                .SimpleForwardingServerCallListener<>(delegate) {
                            @Override
                            public void onMessage(ReqT message) {
                                MdcContext.run(requestContext,
                                        () -> super.onMessage(message));
                            }

                            @Override
                            public void onHalfClose() {
                                MdcContext.run(requestContext,
                                        super::onHalfClose);
                            }

                            @Override
                            public void onCancel() {
                                MdcContext.run(requestContext,
                                        super::onCancel);
                            }

                            @Override
                            public void onComplete() {
                                MdcContext.run(requestContext,
                                        super::onComplete);
                            }

                            @Override
                            public void onReady() {
                                MdcContext.run(requestContext,
                                        super::onReady);
                            }
                        };
                    }
                });
    }
}
~~~

This example focuses on propagation; in an application, you can combine reading/validating the header and wrapping the listener into a single interceptor to avoid two separate layers. When combining them, keep the order: build the request Context first, then wrap startCall and each listener callback with MdcContext.

Register interceptors in the proper server order. If another interceptor populates the correlation Context, the MDC-wrapping interceptor must run after the ID has been set. Verify the actual chain according to how your project's Spring gRPC version registers global/service interceptors.

## 7. Propagating MDC Across Async Executors

Propagating gRPC Context and propagating MDC are two separate concerns. Context.currentContextExecutor(executor) forwards gRPC Context to tasks, but does not automatically copy MDC. With a Spring TaskExecutor, use a TaskDecorator to capture both at submission time:

~~~java
import io.grpc.Context;
import org.slf4j.MDC;
import org.springframework.core.task.TaskDecorator;
import java.util.Map;

public final class MdcGrpcTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable task) {
        Context grpcContext = Context.current();
        Map<String, String> capturedMdc = MDC.getCopyOfContextMap();

        return grpcContext.wrap(() -> {
            Map<String, String> previousMdc = MDC.getCopyOfContextMap();
            try {
                if (capturedMdc == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(capturedMdc);
                }
                task.run();
            } finally {
                if (previousMdc == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(previousMdc);
                }
            }
        });
    }
}
~~~

Register it with the Spring executor:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration
public class RpcExecutorConfiguration {

    @Bean
    ThreadPoolTaskExecutor rpcWorkerExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(32);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("grpc-worker-");
        executor.setTaskDecorator(new MdcGrpcTaskDecorator());
        return executor;
    }
}
~~~

When a task is submitted inside an RPC callback, the decorator captures the submitting thread's gRPC Context and MDC. When the task runs on a worker thread, grpcContext.wrap() attaches the Context and the decorator installs the captured MDC; after completion, the worker's previous MDC is restored.

Never use a custom ThreadLocal without a capture/restore step. Nor should you assume InheritableThreadLocal solves propagation for thread pools: worker threads are typically created before requests arrive and reused across tasks.

## 8. Client: Generating and Sending Correlation IDs

A client can generate a correlation ID at the boundary of a logical operation and place it into gRPC Context. A client interceptor reads that value and adds metadata to each RPC:

~~~java
import io.grpc.CallOptions;
import io.grpc.Channel;
import io.grpc.ClientCall;
import io.grpc.ClientInterceptor;
import io.grpc.ForwardingClientCall;
import io.grpc.Metadata;
import io.grpc.MethodDescriptor;

public final class CorrelationClientInterceptor
        implements ClientInterceptor {

    @Override
    public <ReqT, RespT> ClientCall<ReqT, RespT> interceptCall(
            MethodDescriptor<ReqT, RespT> method,
            CallOptions callOptions,
            Channel next) {

        return new ForwardingClientCall.SimpleForwardingClientCall<>(
                next.newCall(method, callOptions)) {
            @Override
            public void start(Listener<RespT> listener, Metadata headers) {
                String id = CorrelationContextInterceptor.CORRELATION_ID.get();
                if (id != null) {
                    headers.put(
                            CorrelationContextInterceptor.CORRELATION_HEADER,
                            id);
                }
                super.start(listener, headers);
            }
        };
    }
}
~~~

Create context for a logical operation:

~~~java
import io.grpc.Context;
import java.util.UUID;

String correlationId = UUID.randomUUID().toString();
Context operationContext = Context.current().withValue(
        CorrelationContextInterceptor.CORRELATION_ID,
        correlationId);

operationContext.run(() -> catalogStub.getItem(request));
~~~

If the application already received a correlation ID from an HTTP request or message consumer, reuse that ID after validating its format. Do not generate a new ID on every downstream RPC if the goal is to link logs for the same logical operation.

With an async stub, callbacks may run on another executor. If callbacks need to log with the same context, use a context-aware executor and MDC decorator or an equivalent bridge; a client interceptor that only adds metadata will not automatically make MDC appear on the callback thread.

## 9. Combining with Reactor Context

Reactor Context follows the subscription, whereas MDC follows the thread. In a reactive pipeline, read the correlation ID from Reactor Context at the logging point and temporarily place it into MDC:

~~~java
import org.slf4j.MDC;
import reactor.core.publisher.Mono;
import reactor.util.context.ContextView;
import java.util.Map;

static void logWithCorrelation(ContextView contextView, Runnable logAction) {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        String id = contextView.getOrDefault("correlationId", null);
        if (id == null) {
            MDC.remove("correlationId");
        } else {
            MDC.put("correlationId", id);
        }
        logAction.run();
    } finally {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }
}

Mono<Order> orderMono = orderRepository.findById(orderId)
        .doOnEach(signal -> {
            if (signal.isOnNext()) {
                logWithCorrelation(
                        signal.getContextView(),
                        () -> log.info("Order loaded"));
            }
        })
        .contextWrite(context -> context.put(
                "correlationId", correlationId));
~~~

The helper sets MDC only during logging and always restores it. Never leave MDC open across an entire reactive chain because operators can switch threads. If you use Reactor's automatic context propagation, configuration and semantics depend on the version; always verify actual behavior when switching schedulers.

## 10. Log Formatting

With Logback, you can include the correlation ID in the pattern:

~~~xml
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [corr=%X{correlationId:-}] %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>
    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
~~~

Example log line:

~~~text
2026-11-19 10:20:30.120 INFO [grpc-worker-4] [corr=6a2f...] OrderService - Order loaded
~~~

When MDC has no correlation ID, the pattern outputs an empty value rather than the literal string null. Never dump the entire MDC map into logs if it might contain tokens or sensitive data.

## 11. Common Propagation Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Only calling MDC.put() in interceptor | Callbacks on other threads lack the ID | Wrap listener callbacks or use a task decorator |
| Only propagating gRPC Context | Service can read Context, but MDC pattern is empty | Bridge Context into MDC at execution points |
| Only copying MDC without gRPC Context | Logs have ID, but Context principal/deadline can be lost | Capture and wrap both when submitting tasks |
| Not restoring MDC in finally | Subsequent requests on the same worker inherit old ID | Save previous map and restore/clear |
| Using InheritableThreadLocal with thread pools | Does not guarantee per-task context | Use explicit task decoration |
| Generating a new correlation ID per service | Cannot trace the entire request chain | Propagate the same ID via metadata |
| Trusting correlation ID as a credential | Log correlation spoofing or audit confusion | Never use the ID for authentication/authorization |
| Putting unique IDs into metric labels | Cardinality explosion | Put IDs in logs/traces, never in metric labels |

## 12. Testing Correlation Context

Write an integration test that runs multiple concurrent RPCs through the same server and executor to catch MDC leaks:

| Scenario | Assertion |
| --- | --- |
| Client sends a valid correlation ID | Server Context and logs have the same ID |
| Client sends no ID | Server generates a new ID and uses it consistently throughout the call |
| Client sends an ID with newlines or disallowed characters | ID is replaced with a new ID or rejected per policy |
| Two RPCs run concurrently on a thread pool | Logs for each RPC carry only its corresponding ID |
| Task submitted to Spring executor | Both gRPC Context and MDC propagate to the worker |
| Task finishes and worker handles another RPC | Previous MDC is restored/cleared |
| Reactor pipeline switches schedulers | Logs still retrieve the ID from Reactor Context |
| Async callback runs after call completes | Does not read another request's MDC |
| No correlation context present | Logs do not display an old ID |

Tests should write logs to a test appender or capture the MDC map at log points, then assert IDs per RPC. Use a barrier/latch to force two requests to interleave on a small pool; sequential tests often fail to uncover context leaks.

## 13. Applied Exercises

For orders.v1.OrderService/GetOrder:

1. Create a server interceptor that reads x-correlation-id, validates its format, and puts the ID into gRPC Context.
2. Wrap listener callbacks to configure MDC properly in onMessage, onHalfClose, onCancel, and terminal callbacks.
3. Build a TaskDecorator that propagates both gRPC Context and MDC to a ThreadPoolTaskExecutor.
4. Add a client interceptor to send the correlation ID via metadata.
5. Configure Logback to display %X{correlationId}.
6. Run multiple concurrent RPCs and verify no ID leaks between requests.
7. If using OpenTelemetry, verify trace ID/span ID remain managed by propagators independently of the correlation ID.

**Completion criteria:** learners can distinguish gRPC Context, Reactor Context, and MDC; propagate correlation IDs across metadata and thread boundaries; restore MDC to prevent thread leaks; and test propagation in callbacks, executors, and reactive pipelines.
