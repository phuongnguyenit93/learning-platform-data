# Deadline, cancellation, and status

## Learning objectives

After this lesson, you can:

- Distinguish **deadline**, **timeout**, **cancellation**, and **Status.Code** in a gRPC call.
- Set per-RPC deadlines from a Spring client, understand **grpc-timeout**, and understand time-budget propagation to the server.
- Cancel running RPCs, observe **io.grpc.Context**, and stop work on the server side.
- Choose appropriate gRPC error codes; distinguish status from HTTP/2 status and protobuf response content.
- Handle deadlines and cancellation safely in unary and streaming calls, especially when a write operation may have completed before the caller timed out.
- Test and observe performance/reliability through RPC statuses, metrics, and tracing.

## 1. Three concepts with three roles

In **SPRING_GRPC**, the client calls the server through a Java stub generated from a Protocol Buffers contract. The runtime transmits the call over a Channel and an HTTP/2 stream. An RPC can complete, be cancelled, expire, or fail due to an application error.

| Concept | Meaning | Common outcome |
| --- | --- | --- |
| **Deadline** | **Until what point in time** will the caller wait for a result? | On expiration, the client typically sees **DEADLINE_EXCEEDED** |
| **Cancellation** | Is the call **still needed**? | On explicit cancellation, the caller typically sees **CANCELLED** |
| **Status** | What is the final outcome of the RPC? | **OK**, **NOT_FOUND**, **UNAVAILABLE**, **INTERNAL**... |

A **deadline** is the absolute cutoff time of an RPC. A **timeout** is a relative duration used to compute a deadline, such as "RPC at most 800 ms from now". Meanwhile, cancellation can occur *before* the deadline if the user no longer wants to wait.

**Status** is the mechanism for reporting outcomes with standard gRPC codes. Some statuses are returned by the server per business logic; others are generated by the runtime, such as when the client exceeds its deadline or the transport loses connectivity.

~~~mermaid
flowchart TD
    A["Client invokes stub"] --> B["ManagedChannel opens RPC/HTTP2 stream"]
    B --> C{"Does RPC finish before deadline?"}
    C -->|"Yes"| D{"Outcome?"}
    D -->|"Success"| E["OK + response"]
    D -->|"Error"| F["Non-OK Status"]
    C -->|"Not yet"| G{"Did caller cancel first?"}
    G -->|"Yes"| H["Usually CANCELLED"]
    G -->|"No; deadline expired"| I["Usually DEADLINE_EXCEEDED"]
    H --> J["Server receives cancel signal if transport delivers it"]
    I --> J
    J --> K["Stop work and clean up resources"]
~~~

The diagram illustrates common branches; it does not guarantee both sides always observe the exact same status. In particular, when a deadline expires, the server may have already completed a write operation.

## 2. Protocol Buffers contract used in examples

We declare a unary RPC to fetch an order and a server-streaming RPC to watch updates:

~~~proto
syntax = "proto3";

package demo.orders.v1;

option java_package = "dev.example.orders.v1";
option java_multiple_files = true;

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
  rpc WatchOrder(WatchOrderRequest) returns (stream OrderUpdate);
}

message GetOrderRequest {
  string order_id = 1;
}

message GetOrderResponse {
  string order_id = 1;
  string state = 2;
}

message WatchOrderRequest {
  string order_id = 1;
}

message OrderUpdate {
  string order_id = 1;
  string state = 2;
  int64 sequence = 3;
}
~~~

**protoc** and **protoc-gen-grpc-java** generate message classes, client stubs, and **OrderServiceGrpc.OrderServiceImplBase**. Developers write business logic inside the server implementation.

There is no need to add deadline/status fields to every message: deadline is a call option/context, and status is the RPC outcome. If the business domain has its own payment due date, that is a domain data field to document explicitly, distinct from a network deadline.

## 3. A deadline bounds the entire duration of an RPC

An RPC can spend time across many stages:

~~~text
Caller starts RPC
  -> Pick backend, wait for connection readiness
  -> Send headers, metadata, protobuf request
  -> Wait in server queue/executor
  -> Server queries database or calls downstream
  -> Receive response, trailers, decode
  -> Caller receives result
~~~

**The deadline covers all stages**, not only handler execution time. If a call has an 800 ms budget and already waited 500 ms for a connection, the server only has around 300 ms left to finish and return the result.

Setting a deadline in grpc-java:

~~~java
GetOrderResponse response = blockingStub
        .withDeadlineAfter(800, TimeUnit.MILLISECONDS)
        .getOrder(
                GetOrderRequest.newBuilder()
                        .setOrderId("order-42")
                        .build());
~~~

Here **blockingStub** has type **OrderServiceGrpc.OrderServiceBlockingStub**, and **TimeUnit** is **java.util.concurrent.TimeUnit**. **withDeadlineAfter(...)** returns a new stub with updated call options; it does not mutate the original stub.

**Do not attach a deadline when creating a singleton stub**:

~~~java
@Bean
OrderServiceGrpc.OrderServiceBlockingStub riskyStub(ManagedChannel channel) {
    return OrderServiceGrpc.newBlockingStub(channel)
            .withDeadlineAfter(2, TimeUnit.SECONDS);
}
~~~

This stub's deadline is computed when the bean is created. If used many seconds later, new RPCs can expire immediately. Keep the base stub and call **withDeadlineAfter** per use case, right before invoking the RPC.

### 3.1. grpc-timeout in request headers

gRPC can express remaining time via the **grpc-timeout** protocol metadata:

~~~text
Client -> Server
  HEADERS
    :method: POST
    :path: /demo.orders.v1.OrderService/GetOrder
    content-type: application/grpc
    te: trailers
    grpc-timeout: 800m
  DATA
    [gRPC message prefix][serialized GetOrderRequest]
~~~

**800m** means 800 milliseconds and **2S** means 2 seconds. Units are: **H** hours, **M** minutes, **S** seconds, **m** milliseconds, **u** microseconds, **n** nanoseconds. This is a relative value on the wire; the runtime may adjust it for elapsed time.

Applications should set deadlines through the stub/Context API. **Do not set grpc-timeout manually via Metadata**, as it is a header managed by the gRPC runtime.

### 3.2. Deadlines vs. keepalive and proxy timeouts

- **RPC deadline**: the time budget of a single call.
- **Keepalive PING**: checks connection health according to policy; does not guarantee an RPC finishes in time.
- **Proxy idle timeout**: can sever a long-waiting stream even before its deadline expires.
- **Database/other HTTP client timeouts**: separate dependency limits that must align with the RPC deadline.

A unary cache read and a multi-minute server stream have different timing requirements. Choose deadlines based on product goals, measured latency, and load variance.

## 4. When a deadline expires: what is not guaranteed

If the deadline expires before the RPC finishes, the client usually receives **Status.Code.DEADLINE_EXCEEDED**. The runtime stops waiting and attempts to cancel any still-active RPC.

However, this **does not guarantee**:

1. The server never received the request.
2. The handler did not run business logic.
3. The database did not commit.
4. A blocking Java call was interrupted immediately.
5. Jobs running on other threads or external non-gRPC systems stopped automatically.
6. Client and server observed the exact same status code.

For example, suppose a client calls **CreateOrder** with a 1-second deadline. The server saves the order at 0.9 s, but the response arrives at 1.1 s. The client sees **DEADLINE_EXCEEDED**, yet the order already exists. If the caller retries without an **idempotency key**, it risks creating a duplicate order.

A deadline is a limit on **how long the caller will wait**, not a rollback guarantee. For operations with side effects, design deduplication or post-timeout status reconciliation.

### 4.1. Propagating deadlines across services

~~~text
HTTP request budget: 1500 ms
  Gateway
    -> OrderService
         -> InventoryService
         -> PricingService
              -> Database
~~~

If Gateway already spent 500 ms, downstream layers only have about 1,000 ms left. Do not grant a fresh 1,500 ms at each hop and let budgets compound.

In grpc-java, **io.grpc.Context** can propagate deadlines/cancellation across downstream RPCs initiated inside the current context. When using **@Async**, **CompletableFuture**, schedulers, or custom executors, context can be lost unless explicitly propagated to the execution thread.

A service may set a shorter deadline for a dependency to reserve time for fallback and sending its own response. Any retries must fit within the remaining time budget.

## 5. Cancellation is the act of stopping an RPC

Common cancellation scenarios: the user closes a page, the caller no longer needs a stream, a parent job cancels, a deadline expires, or the connection drops. Cancelling an RPC does not mean closing the **ManagedChannel**. Channels are typically shared across many calls; closing the Channel to cancel one stream can break other RPCs.

### 5.1. Half-close vs. cancellation

In client-streaming or bidirectional streaming:

~~~java
requestObserver.onNext(firstRequest);
requestObserver.onNext(secondRequest);
requestObserver.onCompleted();
~~~

**onCompleted()** on the *request observer* only means **the client has finished sending** (half-close of the send direction). The server can still continue sending responses and finish the RPC. It is not cancellation.

When an RPC is genuinely cancelled, the runtime can terminate the HTTP/2 stream with a signal like **RST_STREAM**, and the client side receives **onError**. Do not use **onCompleted()** as a substitute for cancellation.

### 5.2. Cancelling an async call with CancellableContext

One way to cancel a server-streaming RPC in grpc-java is creating a **Context.CancellableContext** before starting the call. Here **asyncStub** is **OrderServiceGrpc.OrderServiceStub**, built from a shared Channel:

~~~java
import dev.example.orders.v1.OrderUpdate;
import dev.example.orders.v1.WatchOrderRequest;
import io.grpc.Context;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;

Context.CancellableContext callContext =
        Context.current().withCancellation();

Context previous = callContext.attach();
try {
    asyncStub.watchOrder(
            WatchOrderRequest.newBuilder()
                    .setOrderId("order-42")
                    .build(),
            new StreamObserver<OrderUpdate>() {
                @Override
                public void onNext(OrderUpdate value) {
                    System.out.println(value.getState());
                }

                @Override
                public void onError(Throwable error) {
                    System.err.println(
                            "WatchOrder ended: "
                            + Status.fromThrowable(error).getCode());
                }

                @Override
                public void onCompleted() {
                    System.out.println("WatchOrder completed");
                }
            });
} finally {
    callContext.detach(previous);
}

// When the user actually requests to stop watching:
callContext.cancel(
        new java.util.concurrent.CancellationException(
                "User stopped watching"));
~~~

**attach()/detach()** lets the RPC be created inside a cancellable context and then restores the thread's original context. The **cancel()** line appears right afterward only to illustrate the API; in real applications, invoke it only on an actual cancellation event or cleanup hook. Store the cancellation handle in an object tied to the session/stream lifecycle.

Depending on the RPC style, other options include **ClientCall.cancel(...)**, **ClientCallStreamObserver.cancel(...)**, or cancelling the future returned by the API. Simply dropping Java references to an observer does not inform the runtime to cancel the RPC.

### 5.3. Caller and server may observe different statuses

A caller that actively cancels usually sees **CANCELLED**; a caller whose deadline expires usually sees **DEADLINE_EXCEEDED**; a connection drop can lead to **UNAVAILABLE**. On the server, the corresponding signal usually shows up via **Context.isCancelled()** or a cancel handler, which does not necessarily preserve full information about the final status observed by the client. Therefore, track cancellation reasons, timestamps, and metric sources on each side.

## 6. Server detecting cancellation and remaining time

Inside a grpc-java handler, the call's **io.grpc.Context** holds deadline and cancellation state. Example:

~~~java
import io.grpc.Context;
import io.grpc.Deadline;
import java.util.concurrent.TimeUnit;

Deadline deadline = Context.current().getDeadline();

if (deadline != null) {
    long remainingMs = deadline.timeRemaining(TimeUnit.MILLISECONDS);
    System.out.println("Deadline remaining approximately " + remainingMs + " ms");
}

if (Context.current().isCancelled()) {
    // Caller stopped waiting; do not start additional expensive work.
    return;
}
~~~

**getDeadline()** can return **null** if no deadline was set. **timeRemaining(...)** can be zero or negative if the deadline has already expired; it is not an absolute timestamp for storing in business data fields.

Servers should check cancellation before starting heavy work, between long processing steps, or via listeners/hooks to close subscriptions. A blocking call in a database driver or library without cancellation support will not stop immediately just because the gRPC Context state changes. Propagate timeouts/cancellations to dependencies whenever the infrastructure supports them.

### 6.1. ServerCallStreamObserver and cancel handlers

For server streaming, **ServerCallStreamObserver** provides **isCancelled()** and **setOnCancelHandler(...)**. The example below emits three messages to show the check, rather than simulating a long-lived event stream:

~~~java
package dev.example.orders.server;

import dev.example.orders.v1.OrderServiceGrpc;
import dev.example.orders.v1.OrderUpdate;
import dev.example.orders.v1.WatchOrderRequest;
import io.grpc.stub.ServerCallStreamObserver;
import io.grpc.stub.StreamObserver;
import java.util.concurrent.atomic.AtomicBoolean;

public class OrderWatchEndpoint
        extends OrderServiceGrpc.OrderServiceImplBase {

    @Override
    public void watchOrder(
            WatchOrderRequest request,
            StreamObserver<OrderUpdate> responseObserver) {

        ServerCallStreamObserver<OrderUpdate> out =
                (ServerCallStreamObserver<OrderUpdate>) responseObserver;

        AtomicBoolean stopped = new AtomicBoolean(false);

        out.setOnCancelHandler(() -> {
            stopped.set(true);
            // Unsubscribe from events, stop polling/timers, and clean up.
        });

        for (int i = 1; i <= 3; i++) {
            if (stopped.get() || out.isCancelled()) {
                return;
            }

            out.onNext(
                    OrderUpdate.newBuilder()
                            .setOrderId(request.getOrderId())
                            .setState("UPDATE_" + i)
                            .setSequence(i)
                            .build());
        }

        if (!out.isCancelled()) {
            out.onCompleted();
        }
    }
}
~~~

For real streams with large data sources, combine this with **isReady()/setOnReadyHandler(...)**, flow control, buffer bounds, and producer coordination so multiple threads do not emit on one observer simultaneously. **StreamObserver is not inherently thread-safe for concurrent writes**. Cancellation can also arrive right after checking `isCancelled()`; that is a normal race condition to handle safely.

Once the peer has cancelled, do not try to send an extra "cancelled" response over a link that may already be closed. Cleaning up upstream data sources is the higher priority.

### 6.2. Context in asynchronous work

If the server uses a custom executor, propagate Context to the worker thread. **Context.wrap(...)** is the typical pattern:

~~~java
import io.grpc.Context;
import java.util.concurrent.Executor;

void submitRpcWork(Executor executor) {
    Context captured = Context.current();

    executor.execute(captured.wrap(() -> {
        if (Context.current().isCancelled()) {
            return;
        }

        // Execute business logic and check cancellation as needed.
    }));
}
~~~

This snippet illustrates context propagation, not a complete handler. Executors must have their lifecycle/shutdown managed in Spring. If using **Context.attach()** manually, always **detach()** in a `finally` block.

When the server calls another gRPC service, the runtime can propagate deadline/cancellation if the outgoing RPC starts within the active context. If **CompletableFuture**, a scheduler, or **@Async** drops the context, the parent request's deadline may no longer reach downstream as expected.

## 7. gRPC status vs. HTTP status

HTTP/2 exchanges frames and statuses at the transport layer; gRPC uses **grpc-status** to describe the RPC outcome. A successful response might look like:

~~~text
Server -> Client:
  HEADERS
    :status: 200
    content-type: application/grpc
  DATA
    [serialized GetOrderResponse]
  HEADERS (trailers)
    grpc-status: 0
  END_STREAM
~~~

**grpc-status: 0** is **OK**. If the server returns **NOT_FOUND**, the HTTP status may still be **200**, yet **grpc-status** in the trailers is non-zero. When an error occurs early, the server can return **trailers-only**, with no response DATA:

~~~text
Server -> Client:
  HEADERS (trailers-only)
    :status: 200
    content-type: application/grpc
    grpc-status: 5
    grpc-message: Order%20not%20found
  END_STREAM
~~~

This is a readable logical view, not a binary frame dump. **grpc-message** has its own encoding rules and should only carry safe diagnostic descriptions, not a machine-readable contract. Clients must branch on **Status.Code**, never by parsing description text.

### 7.1. Common Status.Code values

| Status.Code | Typical meaning | Handling approach |
| --- | --- | --- |
| **OK** | RPC succeeded | Read the response message |
| **CANCELLED** | Call was cancelled | Stop waiting, clean up |
| **UNKNOWN** | Unclassified error | Investigate error source |
| **INVALID_ARGUMENT** | Request itself is invalid | Caller fixes the input |
| **DEADLINE_EXCEEDED** | RPC did not complete before cutoff | Check latency and actual state if side effects exist |
| **NOT_FOUND** | Business resource does not exist | Handle missing-resource case |
| **ALREADY_EXISTS** | Resource already exists | Handle identifier collision |
| **UNAUTHENTICATED** | Missing or invalid identity/token | Check credentials |
| **PERMISSION_DENIED** | Caller lacks permission for the operation | Check authorization |
| **RESOURCE_EXHAUSTED** | Quota/resource/limit exceeded | Throttle load, conditional retry |
| **FAILED_PRECONDITION** | Current state does not allow the operation | Fix precondition before retrying |
| **ABORTED** | Transaction or concurrency conflict | Consider retrying the whole transaction unit |
| **OUT_OF_RANGE** | Exceeded state-dependent bounds | Adjust cursor/range |
| **UNIMPLEMENTED** | Service/method not supported/registered | Check descriptor and version |
| **INTERNAL** | Serious internal error | Investigate server; do not leak stack traces |
| **UNAVAILABLE** | Service/transport temporarily unavailable | Retry with backoff if safe |
| **DATA_LOSS** | Unrecoverable data loss/corruption | Handle data incident |

Commonly confused pairs:

- **INVALID_ARGUMENT**: request is invalid regardless of state; **FAILED_PRECONDITION**: current system state disallows it; **ABORTED**: conflict aborted the operation.
- **UNAUTHENTICATED**: identity could not be verified; **PERMISSION_DENIED**: request is not authorized.
- **NOT_FOUND**: business resource missing; **UNIMPLEMENTED**: gRPC service or method is not implemented.
- **DEADLINE_EXCEEDED**: caller did not receive a result in time; **UNAVAILABLE**: link/backend temporarily unable to serve.

Not all codes are chosen by the server handler. The runtime/client also produces DEADLINE_EXCEEDED, CANCELLED, UNAVAILABLE, or certain RESOURCE_EXHAUSTED errors. Metrics should distinguish whether an error was observed on the client or the server.

## 8. Spring server returning clear statuses

The unary **GetOrder** method below validates input, simulates a record, and uses appropriate statuses:

~~~java
package dev.example.orders.server;

import dev.example.orders.v1.GetOrderRequest;
import dev.example.orders.v1.GetOrderResponse;
import dev.example.orders.v1.OrderServiceGrpc;
import io.grpc.Context;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;
import org.springframework.stereotype.Component;

@Component
public class OrderEndpoint
        extends OrderServiceGrpc.OrderServiceImplBase {

    @Override
    public void getOrder(
            GetOrderRequest request,
            StreamObserver<GetOrderResponse> observer) {

        String orderId = request.getOrderId().trim();

        if (orderId.isEmpty()) {
            observer.onError(
                    Status.INVALID_ARGUMENT
                            .withDescription("order_id must not be empty")
                            .asRuntimeException());
            return;
        }

        if (!"order-42".equals(orderId)) {
            observer.onError(
                    Status.NOT_FOUND
                            .withDescription("Order not found")
                            .asRuntimeException());
            return;
        }

        if (Context.current().isCancelled()) {
            // Do not emit response when the caller has already given up.
            return;
        }

        observer.onNext(
                GetOrderResponse.newBuilder()
                        .setOrderId(orderId)
                        .setState("PENDING")
                        .build());
        observer.onCompleted();
    }
}
~~~

For a response observer, **onCompleted()** and **onError()** are mutually exclusive terminal branches. Once finished, do not call **onNext()** again. A successful unary call must have one response message. On error, a status can be sent with no success message.

In real services, handlers should call business services/repositories, verify authorization, and map exceptions. Never return stack traces, SQL, or tokens inside **Status.description**. If code catches all exceptions and wraps everything as INTERNAL, clients lose the ability to distinguish input mistakes from infrastructure failures.

### 8.1. Registering the endpoint via Spring

~~~java
package dev.example.orders.server;

import io.grpc.Server;
import io.grpc.ServerBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class GrpcServerConfig {

    @Bean(initMethod = "start", destroyMethod = "shutdown")
    Server grpcServer(OrderEndpoint endpoint) {
        return ServerBuilder.forPort(9090)
                .addService(endpoint)
                .build();
    }
}
~~~

**@Component** registers the implementation in Spring; **addService(endpoint)** registers the handler with the gRPC runtime. This is an example of **Spring-managed grpc-java**, not mandatory configuration names for every Spring gRPC starter version. If the framework auto-creates/registers the server, use that mechanism to avoid opening two servers on the same port.

When the application stops, **shutdown()** requests stopping acceptance of new work; it does not mean the server has finished waiting for all in-flight RPCs. Production setups should implement **graceful shutdown**, reasonable drain timeouts, and cleanup of remaining background jobs.

## 9. Spring client setting deadlines and classifying statuses

One **ManagedChannel** can be reused across many RPCs. The base stub is also lightweight and shareable; individual calls decide their deadline per use case.

~~~java
package dev.example.orders.client;

import dev.example.orders.v1.OrderServiceGrpc;
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class OrderGrpcClientConfig {

    @Bean(destroyMethod = "shutdown")
    ManagedChannel ordersChannel() {
        // Local demo; production requires TLS and proper authentication.
        return ManagedChannelBuilder.forAddress("localhost", 9090)
                .usePlaintext()
                .build();
    }

    @Bean
    OrderServiceGrpc.OrderServiceBlockingStub orderStub(
            ManagedChannel ordersChannel) {
        return OrderServiceGrpc.newBlockingStub(ordersChannel);
    }
}
~~~

The Spring service sets a fresh deadline per call and classifies statuses:

~~~java
package dev.example.orders.client;

import dev.example.orders.v1.GetOrderRequest;
import dev.example.orders.v1.GetOrderResponse;
import dev.example.orders.v1.OrderServiceGrpc;
import io.grpc.Status;
import io.grpc.StatusRuntimeException;
import java.util.NoSuchElementException;
import java.util.concurrent.TimeUnit;
import org.springframework.stereotype.Service;

@Service
public class OrderLookupClient {

    private final OrderServiceGrpc.OrderServiceBlockingStub stub;

    public OrderLookupClient(
            OrderServiceGrpc.OrderServiceBlockingStub stub) {
        this.stub = stub;
    }

    public GetOrderResponse findOrder(String id) {
        GetOrderRequest request = GetOrderRequest.newBuilder()
                .setOrderId(id)
                .build();

        try {
            return stub.withDeadlineAfter(800, TimeUnit.MILLISECONDS)
                    .getOrder(request);
        } catch (StatusRuntimeException error) {
            Status.Code code = error.getStatus().getCode();

            switch (code) {
                case INVALID_ARGUMENT:
                    throw new IllegalArgumentException(
                            "Invalid order ID", error);
                case NOT_FOUND:
                    throw new NoSuchElementException(
                            "Order not found: " + id);
                case DEADLINE_EXCEEDED:
                    throw new IllegalStateException(
                            "GetOrder exceeded deadline", error);
                case UNAVAILABLE:
                    throw new IllegalStateException(
                            "OrderService temporarily unavailable", error);
                default:
                    throw error;
            }
        }
    }
}
~~~

This is an example mapping gRPC statuses to application-layer exceptions; real products may use custom domain exceptions. **Never blindly retry every error code**. INVALID_ARGUMENT requires fixing data; NOT_FOUND is a business outcome branch; UNAVAILABLE may be transient; DEADLINE_EXCEEDED requires checking timing and actual processed state.

**usePlaintext()** is only appropriate for local demos or policy-controlled links. Real deployments require configuring TLS/mTLS, trust chains, credentials, and testing HTTP/2 proxies. TLS protects the link, but does not replace deadlines or cancellation.

### 9.1. Async RPC receiving status in onError()

An async call returns before the result arrives. Any RPC errors occurring later enter **onError(...)** rather than being caught solely by a try/catch around the stub call:

~~~java
asyncStub.withDeadlineAfter(5, TimeUnit.SECONDS)
        .watchOrder(
                WatchOrderRequest.newBuilder()
                        .setOrderId("order-42")
                        .build(),
                new StreamObserver<OrderUpdate>() {
                    @Override
                    public void onNext(OrderUpdate update) {
                        // Handle the next event.
                    }

                    @Override
                    public void onError(Throwable error) {
                        Status.Code code =
                                Status.fromThrowable(error).getCode();
                        System.err.println("WatchOrder status: " + code);
                    }

                    @Override
                    public void onCompleted() {
                        // Stream completed successfully.
                    }
                });
~~~

Here **asyncStub** is **OrderServiceGrpc.OrderServiceStub**. **WatchOrderRequest** and **OrderUpdate** are generated from the proto in section 2; import **TimeUnit**, **Status**, and **StreamObserver** when placing the snippet into real source code.

For streaming, one observer belongs to one specific RPC. Never reuse an observer from a finished RPC, and manage buffering when the server emits faster than the client consumes.

## 10. Retries, idempotency, and time bounds

Retries can improve reliability against transient failures, yet they can also amplify load or execute a write twice. Before retrying, consider:

1. **Status**: UNAVAILABLE may be transient; INVALID_ARGUMENT will not fix itself when resending the same request.
2. **Idempotency**: reading an order by ID is usually safe to retry; creating an order or charging payment needs deduplication.
3. **Remaining deadline**: retries and backoff must fit inside the total budget.
4. **Backoff/jitter**: avoid many clients retrying simultaneously and causing a retry storm.
5. **Actual server state**: DEADLINE_EXCEEDED does not prove the operation failed.

An order-creation request can carry an idempotency key:

~~~proto
message CreateOrderRequest {
  string customer_id = 1;
  string idempotency_key = 2;
}

message CreateOrderResponse {
  string order_id = 1;
}
~~~

Merely adding the field does not guarantee idempotency. The implementation must store, check, and synchronize on the key so multiple requests with the same key do not create duplicate orders. When the caller does not know the outcome of a write after a timeout, look up the status by key or reconcile instead of retrying blindly.

| Scenario | Retry immediately? | Handling approach |
| --- | --- | --- |
| GetOrder returns **INVALID_ARGUMENT** | No | Fix the request |
| GetOrder returns **NOT_FOUND** | Usually no | Handle missing resource |
| GetOrder returns **UNAVAILABLE** | Possibly | Backoff/jitter, capped attempts |
| RPC returns **RESOURCE_EXHAUSTED** | Per quota/policy | Slow down, avoid worsening overload |
| GetOrder hits **DEADLINE_EXCEEDED** | Depends on use case | Retry only if time remains and operation is safe |
| CreateOrder exceeds deadline | Do not retry blindly | Look up via idempotency key / reconcile |
| User actively **CANCELLED** | No | Stop work and clean up |
| RPC returns **PERMISSION_DENIED** | No | Check authorization |

gRPC Java can support retries via service config/policies, yet **transport retries do not replace business-level safety**.

## 11. Rich error details, trailers, and security

The server returns errors with **io.grpc.Status**:

~~~java
responseObserver.onError(
        Status.FAILED_PRECONDITION
                .withDescription("Order is finalized and cannot be modified")
                .asRuntimeException());
~~~

The runtime writes the status into gRPC trailers. **Do not set grpc-status manually** as custom metadata. For complex structured errors, the gRPC ecosystem can use **google.rpc.Status** and error details if both client and server agree to support it.

Blocking-stub client reading status:

~~~java
try {
    blockingStub.getOrder(request);
} catch (StatusRuntimeException error) {
    Status.Code code = error.getStatus().getCode();
    String description = error.getStatus().getDescription();

    // Branch on code; description is for diagnostics only.
    // error.getTrailers() may return null.
}
~~~

**StatusRuntimeException.getTrailers()** can be **null** when an error occurs before receiving a response. Never write logic assuming every failed call carries trailers. Never put tokens, stack traces, SQL, or sensitive infrastructure details into **description** or metadata sent to the client.

## 12. Testing status over grpc-inprocess

Testing by invoking the handler's Java method directly bypasses generated stubs and the gRPC runtime. **InProcessServerBuilder** and **InProcessChannelBuilder** let you verify RPCs/statuses through the runtime without binding TCP ports.

### 12.1. Testing unary success and errors

JUnit 5 example with **OrderEndpoint** from section 8, requiring a grpc-java-compatible **grpc-inprocess** dependency:

~~~java
package dev.example.orders.server;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import dev.example.orders.v1.GetOrderRequest;
import dev.example.orders.v1.GetOrderResponse;
import dev.example.orders.v1.OrderServiceGrpc;
import io.grpc.ManagedChannel;
import io.grpc.Server;
import io.grpc.Status;
import io.grpc.StatusRuntimeException;
import io.grpc.inprocess.InProcessChannelBuilder;
import io.grpc.inprocess.InProcessServerBuilder;
import org.junit.jupiter.api.Test;

class OrderEndpointTest {

    @Test
    void shouldReturnResponseAndExpectedErrors() throws Exception {
        String name = InProcessServerBuilder.generateName();

        Server server = InProcessServerBuilder.forName(name)
                .directExecutor()
                .addService(new OrderEndpoint())
                .build()
                .start();

        ManagedChannel channel = InProcessChannelBuilder.forName(name)
                .directExecutor()
                .build();

        try {
            OrderServiceGrpc.OrderServiceBlockingStub stub =
                    OrderServiceGrpc.newBlockingStub(channel);

            GetOrderResponse found = stub.getOrder(
                    GetOrderRequest.newBuilder()
                            .setOrderId("order-42")
                            .build());
            assertEquals("PENDING", found.getState());

            StatusRuntimeException invalid = assertThrows(
                    StatusRuntimeException.class,
                    () -> stub.getOrder(
                            GetOrderRequest.newBuilder().build()));
            assertEquals(Status.Code.INVALID_ARGUMENT,
                    invalid.getStatus().getCode());

            StatusRuntimeException missing = assertThrows(
                    StatusRuntimeException.class,
                    () -> stub.getOrder(
                            GetOrderRequest.newBuilder()
                                    .setOrderId("missing")
                                    .build()));
            assertEquals(Status.Code.NOT_FOUND,
                    missing.getStatus().getCode());
        } finally {
            channel.shutdownNow();
            server.shutdownNow();
        }
    }
}
~~~

**directExecutor()** is convenient for small tests, yet does not simulate blocking systems or complex concurrency. When testing deadlines/cancellation, use an appropriate executor and synchronize with latches/signals rather than relying on flaky **Thread.sleep** intervals.

### 12.2. Testing DEADLINE_EXCEEDED

In a separate test, you can register a handler that intentionally **never completes the RPC**, letting the client runtime expire its deadline:

~~~java
OrderServiceGrpc.OrderServiceImplBase neverResponds =
        new OrderServiceGrpc.OrderServiceImplBase() {
            @Override
            public void getOrder(
                    GetOrderRequest request,
                    StreamObserver<GetOrderResponse> observer) {
                // Test only: intentionally never calls terminal callback.
            }
        };
~~~

Register **neverResponds** on a separate in-process server; with a blocking stub connected to that server:

~~~java
StatusRuntimeException expired = assertThrows(
        StatusRuntimeException.class,
        () -> stub.withDeadlineAfter(200, TimeUnit.MILLISECONDS)
                .getOrder(
                        GetOrderRequest.newBuilder()
                                .setOrderId("order-42").build()));

assertEquals(Status.Code.DEADLINE_EXCEEDED,
        expired.getStatus().getCode());
~~~

Both snippets fit inside the test skeleton and require importing **StreamObserver** and **TimeUnit**. A hanging handler is for testing only, not a production design. In CI, choose generous enough deadlines to avoid flaky tests under CPU contention.

### 12.3. Testing cancellation

For async streaming, open an RPC from a **CancellableContext**, observe **onError** on the client and **setOnCancelHandler** on the server, then call **cancel()**. Verify:

- The client ends with the expected status, typically **CANCELLED** on explicit cancellation.
- The server receives cancellation and closes its event source/background job.
- No further messages are emitted after a terminal event.
- The Channel remains usable for another RPC.
- No resource leaks occur when cancellation and response completion happen nearly simultaneously.

Cancellation is an asynchronous event; use a **CountDownLatch** or similar signal to await and verify rather than immediately reading a server state variable on the line after `cancel()` and assuming the callback has already executed.

### 12.4. Limitations of in-process testing

In-process tests validate APIs, statuses, context, and registration, yet **do not prove** that TLS, HTTP/2 proxies, DNS, load balancing, reconnection, or TCP failures are handled properly. For real deployment environments, also test TLS/mTLS transports, graceful shutdown, and backend connection drops.

## 13. Monitoring deadlines, cancellation, and reliability

In a Spring gRPC application, measure on both client and server:

| Metric | Meaning |
| --- | --- |
| **p50/p95/p99 latency by full method name** | Which RPCs are slow and at which layer? |
| **Status.Code by method** | Rates of INVALID_ARGUMENT, UNAVAILABLE, DEADLINE_EXCEEDED... |
| **Deadline exceeded rate** | How many callers did not receive results on time? |
| **Cancellation count** | How many streams were cancelled; by user or system? |
| **In-flight RPCs / active streams** | Current backlog load and open long-lived streams |
| **Retry attempts / final outcome** | Are retries helping recovery or amplifying load? |
| **Work after cancellation** | Is any job still running when the caller stopped waiting? |
| **Downstream latency** | Which dependency consumes most of the deadline budget? |

Tracing can link the client RPC to the server handler and downstream calls. Avoid putting high-cardinality tokens, order IDs, or request IDs into metric labels; trace/correlation data needs a clear security policy.

If **GetOrder** p99 is 1,500 ms while the deadline is 800 ms, merely raising the deadline may reduce timeout errors on paper while increasing user wait time and in-flight RPC backlog. First analyze connection time, server queues, handlers, databases, and retry storms.

## 14. Common mistakes and troubleshooting

| Symptom | Possible cause | Remediation |
| --- | --- | --- |
| RPC returns **DEADLINE_EXCEEDED** right at start | Singleton stub had a deadline attached at bean creation | Attach deadline per RPC |
| Cancelling one stream breaks many other RPCs | Closed the shared ManagedChannel | Cancel only the relevant RPC |
| Server keeps running jobs after client cancels | Not checking Context or missing cancel handler | Clean up subscriptions and background tasks |
| Client-streaming receives no response | Client did not half-close request observer | Call onCompleted on send side, wait for response |
| HTTP 200 yet RPC fails | Reading only HTTP status | Read grpc-status / StatusRuntimeException |
| Server returns UNKNOWN/INTERNAL for every error | Not mapping business exceptions | Pick appropriate Status.Code values |
| Retries create duplicate orders | Non-idempotent write RPC; ambiguous timeout outcome | Idempotency key and reconciliation |
| Downstream RPC outlives caller's budget | Context lost across custom executor | Propagate Context and remaining budget |
| Stream still emits after cancellation | Producer did not stop, race with terminal state | Coordinate producer and cleanup |
| Proxy severs streaming despite remaining deadline | Idle timeout or HTTP/2/TLS config | Test proxy and adjust policy |
| Timeouts surge under high load | Deep queues, slow backend, retry storms | Analyze latency, bound in-flight work |
| Status description leaks secrets | Returning raw internal exceptions | Sanitize status, log detailed errors on server |

When diagnosing, trace sequentially: **client deadline → Channel/transport → server queue → handler → downstream → status/trailers**. This separates timing, business errors, and infrastructure causes.

### Self-check questions

**1. How does deadline differ from timeout?**  
A deadline is the final cutoff time for an RPC; a timeout is the duration used to compute that cutoff. **withDeadlineAfter** sets a deadline from a relative duration.

**2. When the client sees DEADLINE_EXCEEDED, is it certain the server did not write data?**  
**No.** The server may have already committed. Always use idempotency or reconciliation for operations with side effects.

**3. Is onCompleted() on the request observer a cancellation?**  
**No.** It is a half-close of the send direction in client/bidirectional streaming.

**4. Why shouldn't you close the Channel to cancel a single RPC?**  
The Channel is shared across many calls. Closing the Channel can disrupt other active RPCs.

**5. How does NOT_FOUND differ from UNIMPLEMENTED?**  
**NOT_FOUND** means a business resource does not exist; **UNIMPLEMENTED** means the gRPC service/method is not supported by the runtime.

**6. Which APIs does the server use to detect cancellation?**  
You can check **Context.current().isCancelled()**, **ServerCallStreamObserver.isCancelled()**, and register **setOnCancelHandler(...)**.

**7. Does HTTP 200 guarantee gRPC OK?**  
**No.** The RPC outcome lives in **grpc-status** inside trailers.

**8. Should you retry every UNAVAILABLE or DEADLINE_EXCEEDED?**  
No. Consider operation safety, remaining deadline, backoff, and the possibility that the server already executed the operation.

**9. Does a deadline automatically propagate into every CompletableFuture?**  
Do not assume so. Propagate **io.grpc.Context** explicitly to custom executors/threads.

## Summary

A **deadline** bounds how long a caller waits for an RPC; **cancellation** stops work that is no longer needed; **gRPC status** describes the outcome with standard codes independent of HTTP status. In Spring gRPC, set deadlines **per call**, propagate **Context** into downstream/async work, manage **StreamObserver** and cancel handler lifecycles properly, and map errors to appropriate **Status.Code** values. For RPCs with side effects, use controlled retries and **idempotency**, because a timeout does not guarantee the server did not commit. In-process testing, real transport testing, and per-method metrics/tracing keep unary and streaming services reliable and diagnosable.
