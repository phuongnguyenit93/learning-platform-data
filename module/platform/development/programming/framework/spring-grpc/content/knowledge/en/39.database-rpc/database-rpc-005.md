# Idempotency When Clients Retry Commands

## 1. Why do commands need idempotency?

In **SPRING_GRPC**, many unary RPCs perform side effects such as creating orders, recording payments, transferring funds, or updating state. A client may send a request and fail to receive the response because the network dropped, the deadline expired, or the client process restarted. Meanwhile, the server may have already committed to the database successfully.

The client cannot always know whether the request was executed. If it resends the command as a new request, the server might execute the side effect a second time. This is an **ambiguous outcome**: the server-side result may have already committed, yet the caller never received confirmation.

**Idempotency** allows multiple submissions of the same business intent to produce a single effective outcome. The client attaches a stable idempotency key to the command; the server stores the key, recognizes duplicate requests, and returns the recorded result instead of executing the side effect again.

Idempotency does not turn the network into exactly-once delivery, nor does it eliminate retries. It provides a mechanism to handle at-least-once delivery safely at the business layer.

This lesson focuses on key and request fingerprint design, storing keys with unique constraints, atomic transactions with business updates, handling concurrent duplicate requests, replaying results, retrying within deadlines, retention, and testing the scenario where commit succeeds but the response is lost.

## 2. A retry does not prove the previous request failed

Suppose a client calls the CreateOrder RPC:

1. The client sends the request.
2. The server validates and writes the order.
3. The database commits successfully.
4. The connection drops before the response reaches the client.
5. The client receives UNAVAILABLE or DEADLINE_EXCEEDED.
6. The client retries.

At step 5, the client only knows it did not receive a response. It does not know whether the server committed at step 3. If the server creates a new order on retry, a single purchase intent can produce two orders.

It is also possible the server has not committed and the transaction rolled back. When the client retries, the new submission needs to execute normally.

Therefore, the server must distinguish between the two cases using a stable identifier for the command intent. Do not use a connection ID, request timestamp, or a fresh ID generated on each retry as the idempotency key.

## 3. Idempotent operations and idempotency keys

An operation is inherently idempotent if repeating it with the same input produces no change beyond the first execution. For example, setting a resource's status to ACTIVE can often be idempotent; incrementing a balance by 10 or creating a new order is not inherently idempotent.

For commands that are not naturally idempotent, the client creates a key for **one business intent**:

```text
idempotency_key = "8f2c...-stable-command-id"
```

Client-side rules:

- Generate the key before the first send.
- Keep the exact same key across all retries of the same command.
- Use a new key only when the user genuinely creates a new command intent.
- Persist the key long enough if retries may resume after a process restart.
- Never share a key across two different commands.

The key is typically a sufficiently strong random UUID or an operation identifier generated by the client. The key scope should include tenant/client identity and the operation/RPC name so two APIs or two tenants do not accidentally share a namespace.

Example scope:

```text
(tenant_id, client_application, full_method_name, idempotency_key)
```

Do not treat the key as an authentication mechanism. The server must still check authentication and authorization on every call, even when only replaying a previous result.

## 4. Request fingerprints detect misused keys

Storing only the key is not enough. A client might send the same key with a different payload due to a bug or mistakenly reusing a key for a new command.

The server should compute a **request fingerprint** from the normalized business content:

- Identify the fields that affect the side effect.
- Normalize the representation before hashing if ordering/maps/defaults can produce different bytes for the same semantics.
- Exclude the idempotency key, trace ID, or metadata that changes per retry from the fingerprint.
- Use a hash such as SHA-256 over a canonical representation or a stable internal encoding.
- Store the fingerprint algorithm/version if canonicalization rules might evolve.

When the key already exists:

- Matching fingerprint: this is a retry of the same command; return the stored result or in-progress state.
- Different fingerprint: reject because the key was already used for a different intent.

Do not blindly hash raw wire bytes if the same message can serialize to different bytes while carrying identical semantics due to field order, unknown fields, or representation. Choose a canonical form suited to the contract.

## 5. Storing idempotency records in the database

An idempotency record table might contain:

| Column | Purpose |
| --- | --- |
| tenant_id | Tenant scope |
| client_id | Calling application scope |
| method_name | RPC/full method identity |
| idempotency_key | Client-generated key |
| request_hash | Command fingerprint |
| state | Processing state |
| result_payload | Result to replay or operation reference |
| grpc_status | Final status if the API also stores error outcomes |
| created_at | Timestamp when first received |
| expires_at | Expiration timestamp for retaining the key |

Create a unique constraint on the chosen scope, for example:

```sql
CREATE UNIQUE INDEX uq_idempotency_scope
ON idempotency_record (
    tenant_id,
    client_id,
    method_name,
    idempotency_key
);
```

A unique constraint is the final safeguard against two requests with the same key passing checks concurrently. A SELECT to check the key followed by an INSERT without a unique constraint still has a race condition.

If storing Protobuf response bytes, manage schema/type versions and maintain readability for as long as the record remains valid. Another option is storing the operation ID or stable domain result and building the response according to the current contract. Choose a replay approach consistent with API versioning and result-preservation requirements.

## 6. Claiming the key, business update, and result in the same transaction

For short-running commands, a simple and robust design places claiming the key, applying the business change, and storing the result in **the same database transaction**:

1. Atomically attempt to create the idempotency record within the scope.
2. If creation succeeds, this request owns execution.
3. Perform the business operation.
4. Save the result/operation ID into the idempotency record.
5. Commit both the business data and the idempotency record together.
6. Only after the transaction commits does the adapter send the gRPC response.

Illustrative service example:

```java
@Service
@RequiredArgsConstructor
public class CreateOrderService {
    private final IdempotencyRepository idempotency;
    private final OrderRepository orders;
    private final RequestFingerprint fingerprints;

    @Transactional
    public CreateOrderResult execute(
            String tenantId,
            String clientId,
            CreateOrderCommand command) {

        String hash = fingerprints.hash(command);

        boolean claimed = idempotency.insertIfAbsent(
            tenantId,
            clientId,
            "commerce.v1.OrderService/CreateOrder",
            command.idempotencyKey(),
            hash
        );

        if (!claimed) {
            IdempotencyRecord existing = idempotency.findRequired(
                tenantId,
                clientId,
                "commerce.v1.OrderService/CreateOrder",
                command.idempotencyKey()
            );

            if (!existing.requestHash().equals(hash)) {
                throw new IdempotencyKeyReuseException();
            }

            return existing.toCreateOrderResult();
        }

        Order order = orders.save(Order.create(command));
        CreateOrderResult result = CreateOrderResult.from(order);

        idempotency.complete(
            tenantId,
            clientId,
            command.idempotencyKey(),
            result
        );

        return result;
    }
}
```

insertIfAbsent should be implemented with an atomic operation suited to the database, backed by a unique constraint; not a plain SELECT-then-INSERT. Depending on the specific database/isolation level, a competing request may wait for the key-owning transaction to commit before reading the record. If a snapshot transaction cannot see the newly committed record, roll back and re-read in a new transaction.

If the business operation fails in a way that requires rollback, the idempotency record rolls back as well. A subsequent retry can then become the executing request. For terminal business rejections that require deterministic replay, the rejection outcome can be stored as a completed result within the transaction, leaving the adapter to map it to a gRPC status after commit.

## 7. Why unique constraints and transactions must go together

A common anti-pattern:

1. SELECT to check that the key does not exist yet.
2. Create the order.
3. INSERT the idempotency record.
4. Commit.

Two requests with the same key can both SELECT and see no record, then both create an order. A unique constraint might block one record insert, but if the order and record are not in the same transaction, the losing request's side effect may already have committed.

A proper design must ensure:

- Key claim has atomic uniqueness.
- Business update and idempotency result commit in the same transaction.
- If the claim fails, no business side effect runs.
- If the business update rolls back, the claim also rolls back.
- If commit succeeds but the response is lost, a retry reads the completed record.

With ORMs, a unique violation may mark the transaction rollback-only or render the current transaction unusable, depending on the database/provider. Do not catch a duplicate-key exception and assume you can query the record in the same transaction. Use a suitable insert-if-absent/upsert primitive or let the transaction roll back and perform the lookup in a new transaction.

## 8. Concurrent duplicate requests and PROCESSING state

Two requests with the same key can arrive almost simultaneously. The system needs a well-defined policy.

### Handling within one short transaction

When claim, business update, and result share a single transaction, the unique index coordinates the two requests. The second request typically waits for the first transaction's outcome:

- If the first request commits, the second request sees the existing key and replays the result.
- If the first request rolls back, the second request can claim the key and execute the operation.
- If it waits too long, the caller may hit its deadline; retrying with the same key remains safe.

This is usually the right choice for short commands.

### Separate reservation for long-running tasks

For long-running tasks that must return an early ACK, you can commit a PROCESSING record before executing the work asynchronously. That additionally requires:

- Owner/worker token.
- Lease expiry and heartbeat.
- Takeover rules when a worker dies.
- A way to distinguish PROCESSING, COMPLETED, and FAILED.
- The worker must be idempotent because lease expiration can cause the same task to be reassigned.
- An API for the client to query operation status or retry with the same key.

Never create a permanent PROCESSING record without lease/recovery. A worker crash must not leave a key locked forever.

## 9. Replaying results and protecting information

When a duplicate request has a matching fingerprint and the operation has completed, the server returns the stored result without running business logic again.

Clearly decide what gets replayed:

- Response payload or operation ID.
- Final business outcome.
- Final gRPC status if the contract requires preserving error outcomes as well.
- Contract-significant metadata/trailers if needed.

Do not replay values meaningful only to the previous transport attempt, such as trace IDs, server timings, or debug metadata. These must be generated fresh for each invocation.

Authentication and authorization must still run on every retry. If the user/tenant no longer has permission to view the result, the server must not return the stored payload solely because the key matched. Key scoping must also prevent one tenant from probing another tenant's results.

If results contain sensitive data, apply the same encryption, access control, and retention policies as for the corresponding business data.

## 10. Choosing policies for errors and unsuccessful outcomes

Not every error should be persisted as a permanent idempotent outcome.

| First Attempt Outcome | Typically Suitable Policy |
| --- | --- |
| Success and commit | Save result; retry with same key replays |
| Terminal validation/business rejection | May save outcome so retries do not change the result |
| Optimistic conflict ABORTED | Transaction rolls back; retry can re-read and re-run if contract allows |
| Database/transient error before commit | Roll back claim and business changes; retry with same key can execute again |
| Error after commit but before response | Record is complete; retry replays the result |
| Duplicate key with different fingerprint | Reject; do not run side effect |

If storing a business rejection, do not throw an exception that rolls back the entire transaction while expecting the record to remain. Instead, represent the rejection as an outcome committed without performing side effects; the adapter translates that outcome into a status after the transaction ends.

For ABORTED, clearly define whether the key represents a fixed intent or an attempt that can be recomputed against fresh state. A common design rolls back the record with the conflicted transaction, letting the client retry with the same key after re-reading; however, if request semantics change, the fingerprint must be computed over stable command inputs and the policy must be documented.

## 11. Client retries: keep the key, respect deadlines

The client creates the idempotency key once for the command, then keeps the same key across all retry attempts:

```java
String key = commandId; // Generated once for the business intent.

CreateOrderRequest request = CreateOrderRequest.newBuilder()
    .setCustomerId(customerId)
    .setIdempotencyKey(key)
    .addAllItems(items)
    .build();

for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
    try {
        return blockingStub
            .withDeadlineAfter(remainingMillis(), TimeUnit.MILLISECONDS)
            .createOrder(request);
    } catch (StatusRuntimeException ex) {
        if (!isRetryable(ex.getStatus().getCode())
                || attempt == MAX_ATTEMPTS) {
            throw ex;
        }
        sleepWithExponentialBackoffAndJitter(attempt);
    }
}
```

This is illustrative pseudocode; a real implementation must properly manage total deadline, cancellation, and interruption. Do not grant an unlimited fresh deadline for every attempt; total retry time must stay within the caller's allowed budget.

Principles:

- Retries of the same command must use the same key and the same payload semantics.
- Do not retry INVALID_ARGUMENT or non-recoverable business rejections.
- UNAVAILABLE or timeouts may have an ambiguous outcome; retry with the same key.
- ABORTED requires re-reading and retrying the full workflow per contract.
- Use backoff with jitter and a bounded number of attempts.
- If the caller runs out of time to wait, it can return a timeout while keeping the key to query/retry later.

Transport-level gRPC retry policies do not automatically provide idempotency. The server must still protect side effects; do not assume enabling retry configuration is sufficient.

## 12. Outbox and external side effects

If a command both updates the database and needs to emit an event, write business data, the idempotency result, and the outbox record in the same transaction:

1. Claim the idempotency key.
2. Perform the business update.
3. Write the outbox event with a stable event ID.
4. Save the command result in the idempotency record.
5. Commit.
6. A worker publishes the outbox event.
7. Consumers process idempotently because publishing may repeat.

Do not send emails, publish to a broker, or call external RPCs before commit expecting a database rollback to undo those side effects.

If the worker publishes an event and crashes before marking it sent, the event may be published again. Consumers must deduplicate by event ID or operation ID. Command idempotency does not automatically make all downstream consumers exactly-once.

## 13. Retention, expiration, and key scope

Idempotency records must be retained at least as long as a client can retry or recover from an incident. Deleting records too early allows a late retry to create a new side effect.

Choose retention based on maximum client deadline and retry window; how long a client may be offline before resending; batch/reconciliation processing time; data retention and audit regulations; and how long downstream systems can replay commands/events.

When a record expires, decide whether the key may be reused. Typically clients must still generate new keys for new intents; do not reuse an old key simply because the record was cleaned up.

Key scope must be tight enough: tenant/client/method/key. Cleanup jobs should delete in bounded batches to avoid holding table locks for long periods. For long-lived operations, retain the operation ID/tombstone longer than the response payload if needed to prevent duplicates after detailed results expire.

## 14. Testing idempotency

A unit test with a single successful call does not prove idempotency. You need to test retries and real concurrency against a database:

| Test | What to verify |
| --- | --- |
| Same key, same payload after commit | Returns the same result; business side effect occurs only once |
| Same key, different payload | Rejected; no second side effect occurs |
| Two concurrent requests with same key | Unique constraint allows only one execution |
| First request rolls back | Retry request can execute according to policy |
| Commit succeeds but response lost | Retry replays the stored result |
| Two tenants using the same key | Scope does not leak or mix results |
| PROCESSING worker crashes | Lease/recovery allows continuation without duplicates |
| Repeated outbox publish | Consumer deduplicates the event |
| Expired record | Late retry behavior matches the retention contract |
| Authorization changes | Replay still enforces current permissions |

Use two independent transactions/threads to trigger race conditions. Testcontainers or a production-like database verifies unique constraints, isolation, and insert-if-absent behavior. A test calling the repository sequentially will not detect races between SELECT and INSERT.

To simulate a lost response, let the server commit successfully and then sever the transport before the client receives the response; invoke the same request/key again and verify the old result is returned without creating a second business record.

## 15. Review checklist

- Client generates a key once for a business intent and keeps it constant across retries.
- Key has a clear tenant/client/method scope; never used as authentication.
- Request fingerprint includes fields affecting side effects and excludes volatile metadata.
- Key reuse with a different payload is rejected.
- Database has a unique constraint on the idempotency scope.
- Key claim, business update, and stored result commit in the same transaction for short commands.
- Does not rely on SELECT-then-INSERT as a concurrency guard.
- Concurrent duplicate requests wait/replay or use a PROCESSING lease with recovery.
- Adapter returns responses only after commit.
- Replayed results do not re-execute side effects and still enforce authorization.
- Policies for success, terminal rejection, ABORTED, and transient errors are defined.
- Client retries have a total deadline, backoff/jitter, and bounded attempts.
- Outbox events have stable IDs; downstream consumers deduplicate.
- Retention exceeds the committed retry/recovery window.
- Integration tests cover races, rollbacks, lost responses, and key mismatches.

In **SPRING_GRPC**, an idempotency key turns a command retry into querying the outcome of the same business intent. The server must coordinate unique constraints, request fingerprints, and transactions to atomically persist side effects alongside the result. When a response is lost after commit, retrying with the same key replays the result; when the first request failed to commit, transaction rollback lets another valid attempt execute. Together with deadlines, backoff, authorization, and outbox, this keeps commands safe against retries and network failures.
