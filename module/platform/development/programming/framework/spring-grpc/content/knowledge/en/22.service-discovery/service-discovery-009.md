# Service Name vs. Proto Package

In gRPC, the service name on the wire is formed from the `package` in the `.proto` file and the name declared after the `service` keyword. That name determines the RPC path that clients call. It is **different** from the Java package used for code generation, and also different from the logical name that service discovery uses to find server addresses.

Distinguishing these three concepts is critical in Spring gRPC. A client can resolve DNS accurately and connect to the server yet still receive `UNIMPLEMENTED` if the service path does not match. Conversely, changing the Java package may require updating imports in source code without necessarily changing the RPC path.

## 1. Three Names with Different Purposes

Consider this example:

```proto
syntax = "proto3";

package acme.orders.v1;

option java_package = "com.acme.platform.orders.grpc";
option java_multiple_files = true;

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
}

message GetOrderRequest {
  string order_id = 1;
}

message GetOrderResponse {
  string order_id = 1;
  string status = 2;
}
```

From this definition, three names must be kept separate:

| Concept | Example Value | Where It Is Used |
| --- | --- | --- |
| Proto package | `acme.orders.v1` | Namespace of services and messages in the Protobuf descriptor |
| Fully qualified gRPC service name | `acme.orders.v1.OrderService` | Identifies the service in the gRPC protocol, health checking, reflection, and RPC routing |
| Java package | `com.acme.platform.orders.grpc` | Package of the Java classes generated by protoc |

The full RPC name is `acme.orders.v1.OrderService/GetOrder`. The call's HTTP/2 `:path` looks like:

```text
/acme.orders.v1.OrderService/GetOrder
```

`java_package` only controls the generated Java package. It does not replace `package acme.orders.v1` in the descriptor and does not change the service name on the wire.

## 2. How Does the Proto Package Form the Full Service Name?

General rule:

```text
fully-qualified-service-name = proto-package + "." + service-name
rpc-method-name              = fully-qualified-service-name + "/" + method-name
HTTP/2 :path                 = "/" + rpc-method-name
```

With the example above:

- Proto package: `acme.orders.v1`
- Service declaration: `OrderService`
- Fully qualified service name: `acme.orders.v1.OrderService`
- Method declaration: `GetOrder`
- RPC path: `/acme.orders.v1.OrderService/GetOrder`

If a `.proto` file omits `package`, the service name has no package prefix. For example, a `OrderService` service with a `GetOrder` method will have the path `/OrderService/GetOrder`. Therefore, declare an explicit package to avoid generic service names and reduce the risk of name collisions across APIs.

Package names and identifiers are case-sensitive. `acme.orders.v1.OrderService` differs from `acme.orders.v1.orderservice`; client and server must use the exact same full name.

## 3. Java Package Does Not Determine the RPC Path

Protoc generates Java classes based on Java options:

- `java_package`: Java package of the generated code.
- `java_multiple_files`: controls whether messages/enums are generated as separate classes or nested inside an outer class.
- `java_outer_classname`: name of the outer class holding the descriptor or nested types in that mode.

These options affect source layout, imports, and Java class names. They do not alter the Protobuf `package` and do not change the fully qualified gRPC service name.

In the example, the generated service class is typically named `OrderServiceGrpc` in the Java package `com.acme.platform.orders.grpc`. You can inspect the service name provided by the generated code:

```java
import com.acme.platform.orders.grpc.OrderServiceGrpc;

class GeneratedNameCheck {
    void inspect() {
        String serviceName = OrderServiceGrpc.SERVICE_NAME;
        // acme.orders.v1.OrderService
        System.out.println(serviceName);
    }
}
```

The generated class name is a Java code-generation detail; `OrderServiceGrpc.SERVICE_NAME` is the value to match against the service name in the descriptor and related gRPC configurations.

Therefore:

- Changing `java_package` from `com.acme.platform.orders.grpc` to `com.acme.orders.api` typically requires updating imports and build artifacts.
- As long as `package acme.orders.v1` and `service OrderService` stay the same, the RPC path remains `/acme.orders.v1.OrderService/GetOrder`.
- Changing `package` in `.proto` to `acme.sales.v1` changes the RPC path, even if `java_package` stays unchanged.

## 4. Service Name Is Different from the Service Discovery Target

This is another common confusion. The channel target tells gRPC **where to connect to the service**; the fully qualified service name tells gRPC **which RPC to invoke over that connection**.

Example:

```java
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;

ManagedChannel channel = ManagedChannelBuilder
    .forTarget("dns:///orders.default.svc.cluster.local:8443")
    .useTransportSecurity()
    .build();

OrderServiceGrpc.OrderServiceBlockingStub stub =
    OrderServiceGrpc.newBlockingStub(channel);

GetOrderResponse response = stub.getOrder(
    GetOrderRequest.newBuilder()
        .setOrderId("ORD-1042")
        .build());
```

In this example:

- `dns:///orders.default.svc.cluster.local:8443` is the target URI for the resolver to find endpoints.
- `acme.orders.v1.OrderService` is the service name in the gRPC descriptor.
- `GetOrder` is the method on the service.
- `OrderServiceGrpc` is the generated Java class used to build stubs.

The resolver can locate a Pod, a ClusterIP, or a group of endpoints from a registry. It does not alter the service or method name in the RPC path. Hence, a successful TCP/TLS connection does not prove the server implements the expected service path.

A registry name like `orders`, a DNS name `orders.default.svc.cluster.local`, and a proto service name `acme.orders.v1.OrderService` can all differ. Establish clear conventions and never substitute one string for all three just because they all contain the word `orders`.

## 5. Which Descriptor Does the Server Register Services With?

The server must register an implementation generated from the matching `.proto` definition. grpc-java uses the implementation's service descriptor to identify the service:

```java
import io.grpc.Server;
import io.grpc.ServerBuilder;
import io.grpc.stub.StreamObserver;

final class OrderServiceImpl
        extends OrderServiceGrpc.OrderServiceImplBase {

    @Override
    public void getOrder(
            GetOrderRequest request,
            StreamObserver<GetOrderResponse> observer) {
        GetOrderResponse response = GetOrderResponse.newBuilder()
            .setOrderId(request.getOrderId())
            .setStatus("CONFIRMED")
            .build();
        observer.onNext(response);
        observer.onCompleted();
    }
}

Server server = ServerBuilder.forPort(8443)
    .addService(new OrderServiceImpl())
    .build()
    .start();
```

The implementation above is registered under the service name from the Protobuf descriptor, not the Java class name or Spring bean name. Naming a bean `ordersGrpcService` does not change the wire service name to `ordersGrpcService`.

In Spring gRPC, you can use the service registration mechanism provided by your installed starter, such as starter-supported beans/annotations. Regardless of the mechanism, the implementation must still extend the corresponding generated service and its descriptor must match the client.

If a client calls `/acme.orders.v1.OrderService/GetOrder` while the server only registers `acme.orders.v2.OrderService`, the connection can still succeed, but the server will not find the requested method path and will typically return `UNIMPLEMENTED`.

## 6. Service Names in Health Checking, Reflection, and Interceptors

The fully qualified service name also appears in other gRPC mechanisms:

**Health checking.** When setting status for a service in `HealthStatusManager`, use the full service name from the proto package and service declaration:

```java
healthStatusManager.setStatus(
    "acme.orders.v1.OrderService",
    ServingStatus.SERVING);
```

If client-side health checking configures a `serviceName`, that value must also match the service name published by the health server. Using `orders.default.svc.cluster.local` here is incorrect because that is a DNS target, not a gRPC service name.

**Server reflection.** Reflection publishes descriptors and services so tools like grpcurl can discover the API. The displayed name is the full Protobuf service name, not the Java package or registry name.

**Interceptors and authorization.** The method descriptor provides the full method name for applying per-service/per-method policies:

```java
String fullMethod =
    call.getMethodDescriptor().getFullMethodName();

// Example: acme.orders.v1.OrderService/GetOrder
if (fullMethod.equals(
        "acme.orders.v1.OrderService/GetOrder")) {
    // Apply policy for the specific RPC.
}
```

In grpc-java, `getFullMethodName()` typically returns `service/method` without a leading `/`; the HTTP/2 path adds a leading `/`. When writing tests or matching in interceptors, use the exact format returned by the API.

## 7. Changing the Proto Package Is a Contract Change

Changing a Java package and changing a Protobuf package have very different impacts:

| Change | Impact on Java Code | Impact on gRPC Wire/Service Identity |
| --- | --- | --- |
| Change `java_package` | Imports, packages, and build output change | RPC path unchanged if proto package/service stay the same |
| Change `java_outer_classname` | Outer class/descriptor holder name changes | RPC path unchanged |
| Change `java_multiple_files` | Generated class structure changes | RPC path unchanged |
| Change proto `package` | Descriptors and full names of types/services change; referencing code may need updates | Changes service/method path; old clients no longer call the right service path |
| Rename `service` | Generated service class and server/client APIs change | Changes service identity and RPC path |
| Rename `rpc` method | Stub method changes | Changes method path |

Changing the proto package is not equivalent to refactoring a Java package. It is a contract change at the Protobuf/gRPC level and can affect:

- Clients generated from the old `.proto`.
- Servers still registering the old descriptor.
- Health checking service names.
- Reflection and operational tooling.
- Authorization/interceptor rules keyed by full method name.
- Metrics, tracing, and dashboards grouped by service/method.
- `Any` type URLs or persisted/emitted descriptor data if related messages are packed by full name.

If you need to migrate from `acme.orders.v1` to `acme.fulfillment.v1`, consider introducing a new service/version or running the old service in parallel during the transition. The rollout must ensure servers can serve both old and new paths while clients upgrade. Only remove the old service after confirming no clients still call that path.

## 8. Checking and Diagnosing Service Names

When encountering `UNIMPLEMENTED`, do not rush to change the DNS target. Check in order:

1. Read `package` and `service` in the `.proto` file used to generate the client stub.
2. Check `OrderServiceGrpc.SERVICE_NAME` or the full method name provided by generated code.
3. Confirm the server registers an implementation generated from the matching proto contract.
4. Check that the HTTP/2 path has the form `/<proto-package>.<Service>/<Method>`.
5. Check whether health config, reflection, and interceptors use the same service name.
6. Only then check resolver target, DNS, port, TLS, and network path if connections are not reaching the server.

For example, with grpcurl, server reflection can list `acme.orders.v1.OrderService`; invoke the method by its full name:

```bash
grpcurl -plaintext localhost:9090 \
  acme.orders.v1.OrderService/GetOrder
```

This command is only suitable for a local plaintext server with reflection enabled. In production, use appropriate TLS flags/trust material and never enable plaintext to work around certificate errors.

## 9. Testing Contract Names

Add automated tests to prevent accidental name changes:

| Check | Expected Result |
| --- | --- |
| Proto descriptor full service name | `acme.orders.v1.OrderService` |
| Generated `SERVICE_NAME` | Matches the fully qualified service name |
| Generated full method name | `acme.orders.v1.OrderService/GetOrder` |
| HTTP/2 path | `/acme.orders.v1.OrderService/GetOrder` |
| Java package | `com.acme.platform.orders.grpc` |
| Server registration | Contains the service descriptor with the exact name |
| Health status key | Uses `acme.orders.v1.OrderService` |
| Health client config | Uses the same service name |
| Resolver target | Uses DNS/registry target independently of the proto service name |
| Interceptor rule | Matches the exact `getFullMethodName()` format |

A small test can lock down the service name:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class OrderServiceDescriptorTest {
    @Test
    void serviceIdentityMatchesProtoContract() {
        assertEquals(
            "acme.orders.v1.OrderService",
            OrderServiceGrpc.SERVICE_NAME);
    }
}
```

Add an integration test calling the method through a channel to a real server to verify both the routing path and registration. Unit testing a constant does not prove the server registered the implementation or that the resolver points to the right endpoint.

## 10. Practice Exercise

A client currently uses a generated stub from a proto with `package acme.orders.v1`, `java_package = "com.acme.legacy.orders"`, and `service OrderService`. The team wants to move Java code to `com.acme.platform.orders.grpc` and change the DNS target to `orders.prod.svc.cluster.local`.

**Requirements:**

1. Identify the current fully qualified service name and RPC path.
2. Explain what changing `java_package` affects and what stays unchanged.
3. Explain how changing the DNS target affects the resolver/endpoints and why it does not change the RPC path.
4. Identify the configurations to check: health service name, health check config, reflection, and interceptors.
5. Propose a process if the proto package later needs to change to `acme.orders.v2`.
6. Write tests locking down `SERVICE_NAME`, full method name, and server registration to catch contract drift.

**Self-Check Questions:**

- Which elements form the fully qualified gRPC service name?
- Does `java_package` change the HTTP/2 `:path`?
- Why does a server bean name not determine the RPC service name?
- Which two different questions do the DNS target and the proto service name answer?
- How can `UNIMPLEMENTED` occur when client and server use different proto packages?
- Which service name must health checking use?
- Which operational components beyond stubs can be affected by changing the proto package?

**Key Takeaways:** The proto `package` combined with the `service` name forms the fully qualified gRPC service name; that name appears in the RPC path. `java_package` only organizes generated Java code, while DNS/registry targets only locate endpoints. In Spring gRPC, keep these three names distinct, verify health/reflection/interceptors against the full service name, and treat changing a proto package as a contract change requiring a compatible rollout.
