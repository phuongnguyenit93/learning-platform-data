# Scalar Types and Corresponding Data Types

## Learning Objectives

After this lesson, you will be able to:

- Identify all **15 scalar types** of Protocol Buffers **proto3** and their corresponding Java types after code generation.
- Choose signed, unsigned, ZigZag, or fixed-size numeric types based on value ranges and encoding.
- Handle **uint32/uint64** properly in Java, avoiding confusion between bit representation and unsigned numeric values.
- Distinguish **string** (UTF-8 text) from **bytes** (binary data), as well as the precision risks of **float/double**.
- Understand default values, **field presence**, Protobuf's JSON representation, and how to validate data at the Spring gRPC client/server boundary.

## 1. Why Does Choosing Scalar Types Matter in Spring gRPC?

When developing **SPRING_GRPC** services, the **.proto** contract defines the types of data the client sends and the server receives. Protobuf generates Java classes with corresponding data types and APIs; gRPC transmits those messages in binary form over unary or streaming RPCs. Choosing a field type therefore directly affects the **valid value range**, **payload size on the wire**, **how Java developers read values**, and **compatibility across versions**.

A **scalar** is a single primitive value type built into the schema language, such as an integer, floating-point number, boolean flag, string, or byte sequence. Scalars differ from **messages** (structures with fields), **enums** (sets of named values), and composite constructs such as **repeated**, **map**, and **oneof**. A scalar field has the form:

~~~proto
int32 retry_count = 1;
string device_id = 2;
bool active = 3;
~~~

Each line consists of a **type**, a **field name**, and a **field number**. The number, not the name, is used to identify the field in the binary encoding. Changing the type of an already deployed field requires a separate compatibility assessment, even when Java still exposes the same primitive type.

## 2. Complete Reference Table of the 15 proto3 Scalar Types

This table describes the common Java API generated by **protoc** when using **protobuf-java**:

| .proto type | Java getter/setter type | Default value | Wire encoding |
| --- | --- | --- | --- |
| **double** | **double** | **0.0d** | Fixed 64-bit |
| **float** | **float** | **0.0f** | Fixed 32-bit |
| **int32** | **int** | **0** | Varint |
| **int64** | **long** | **0L** | Varint |
| **uint32** | **int** | **0** | Varint, treated as unsigned |
| **uint64** | **long** | **0L** | Varint, treated as unsigned |
| **sint32** | **int** | **0** | Varint + ZigZag |
| **sint64** | **long** | **0L** | Varint + ZigZag |
| **fixed32** | **int** | **0** | Fixed 32-bit, unsigned |
| **fixed64** | **long** | **0L** | Fixed 64-bit, unsigned |
| **sfixed32** | **int** | **0** | Fixed 32-bit, signed |
| **sfixed64** | **long** | **0L** | Fixed 64-bit, signed |
| **bool** | **boolean** | **false** | Varint |
| **string** | **String** | **""** | Length-delimited, UTF-8 |
| **bytes** | **com.google.protobuf.ByteString** | **ByteString.EMPTY** | Length-delimited, raw bytes |

**Key takeaway:** multiple .proto types map to the same Java **int** or **long**, yet they are **not equivalent in value range or encoding**. For example, **int32**, **sint32**, **uint32**, **fixed32**, and **sfixed32** all have a Java API based on **int**, but their binary payloads and interpretations are different.

An **enum** has a numeric value at the wire level, but it is a separate schema kind and does not belong to the list of 15 primitive scalars. Proto3 enums normally have their first value equal to 0; the generated Java class produces an enum type rather than using **int** as the primary API.

## 3. Value Ranges: Signed, Unsigned, and Floating-Point

### 3.1. 32-bit and 64-bit Integers

| Type group | Mathematical value range |
| --- | --- |
| **int32**, **sint32**, **sfixed32** | −2,147,483,648 to 2,147,483,647 |
| **uint32**, **fixed32** | 0 to 4,294,967,295 |
| **int64**, **sint64**, **sfixed64** | −9,223,372,036,854,775,808 to 9,223,372,036,854,775,807 |
| **uint64**, **fixed64** | 0 to 18,446,744,073,709,551,615 |

Java **int** and **long** are signed types. Protobuf still encodes the full **uint32/uint64** range, but when read in Java, the highest bit can cause the value to be displayed as negative. This is **not corrupted data**; you must use unsigned APIs to interpret it:

~~~java
// uint32 max is 4_294_967_295, exceeding Integer.MAX_VALUE.
int unsigned32 = Integer.parseUnsignedInt("4294967295");
System.out.println(unsigned32);                    // -1 (signed view)
System.out.println(Integer.toUnsignedString(unsigned32)); // 4294967295

// uint64 max is 18_446_744_073_709_551_615.
long unsigned64 =
    Long.parseUnsignedLong("18446744073709551615");
System.out.println(unsigned64);                    // -1 (signed view)
System.out.println(Long.toUnsignedString(unsigned64)); // 18446744073709551615
~~~

When comparing **uint32/uint64**, use **Integer.compareUnsigned(...)** or **Long.compareUnsigned(...)**; when dividing, use **divideUnsigned(...)** if needed. Do not use ordinary signed comparisons to order values in the upper half of the unsigned range. If you need arithmetic on 64-bit unsigned integers beyond the positive range of **long**, you can convert to **BigInteger**:

~~~java
import java.math.BigInteger;

long raw = Long.parseUnsignedLong("18446744073709551615");
BigInteger value = new BigInteger(Long.toUnsignedString(raw));
System.out.println(value.add(BigInteger.ONE)); // 18446744073709551616
~~~

Do not pass the literal **4294967295** directly into an **int** setter or the literal **18446744073709551615** into a **long** setter; those literals exceed the respective Java ranges. **parseUnsignedInt/parseUnsignedLong** is a convenient way to accept decimal string input.

### 3.2. float and double

**float** uses the IEEE 754 binary32 format (typically around 6–9 significant decimal digits); **double** uses IEEE 754 binary64 (typically around 15–17 significant digits). Both are **approximate** floating-point numbers:

~~~java
float f = 0.1f;
double d = 0.1d;

System.out.println(f == 0.1d); // false: the two types have different precision
System.out.println(d + 0.2d == 0.3d); // false: binary representation rounding error
~~~

When designing a protocol:

- Use **float** for measurement samples that can tolerate lower precision and need smaller payload sizes.
- Use **double** when algorithms require higher precision, while keeping in mind it is still an approximate floating-point number.
- Do not use **float/double** to represent money accurately or decimals where every digit must be preserved. For money, **int64 amount_minor_units** (e.g., the smallest currency unit such as cents) paired with a unit convention, or a decimal structure with an explicit scale, is typically used.
- **NaN**, **+Infinity**, and **−Infinity** can appear in **float/double**; if business rules only accept finite numbers, validate on the server with **Float.isFinite(...)** or **Double.isFinite(...)**.

Field names should indicate units: **duration_ms**, **temperature_milli_c**, and **distance_meters** are clearer than names like **duration**, **value**, or **size**.

## 4. Varint, ZigZag, and Fixed: All Integers, Different Encodings

Protobuf does not write a field as "field name + value". Each field has a **tag** containing its field number and wire type, followed by the encoded value. Conceptually:

~~~text
Message bytes
  |
  +-- tag(field_number, wire_type) -- encoded value
  +-- tag(field_number, wire_type) -- encoded value
  +-- ...
~~~

Some **wire types** relevant to scalars:

| Wire type | Representation | Types using it |
| --- | --- | --- |
| **0 (Varint)** | Integer encoded in 7-bit groups | int32/int64/uint32/uint64/sint32/sint64/bool |
| **1 (64-bit)** | Exactly 8 bytes of data | fixed64/sfixed64/double |
| **2 (Length-delimited)** | Length followed by payload | string/bytes; also packed repeated scalars |
| **5 (32-bit)** | Exactly 4 bytes of data | fixed32/sfixed32/float |

**Varint** uses fewer bytes for small unsigned numeric values and more bytes for large numbers. With **int32/int64**, negative values are encoded inefficiently due to two's complement representation: for instance, **int32 = -1** takes **10 bytes for the varint value alone**, not counting the tag.

**sint32/sint64** apply the **ZigZag** transform before varint encoding, mapping small negative and positive numbers to small unsigned integers:

| Original signed number | Value after ZigZag |
| --- | --- |
| 0 | 0 |
| −1 | 1 |
| 1 | 2 |
| −2 | 3 |
| 2 | 4 |

Thus **sint32 = -1** needs only **1 byte for the varint value**. Conversely, for data that is rarely negative, **int32/uint32** may be preferable because ZigZag doubles positive values. ZigZag **does not change** the Java type: the getter for **sint32** still returns **int**, and for **sint64** still returns **long**.

**fixed32/sfixed32** always use **4 bytes for the value**; **fixed64/sfixed64** always use **8 bytes**, not counting the tag. They can be efficient when values are frequently large, which would force varint to use many bytes. The difference between **fixed** and **sfixed** lies in **signed/unsigned interpretation**, not byte count.

Concrete example of a field:

~~~proto
message Counter {
  int32 retry_count = 1;
}
~~~

If **retry_count = 150**, the tag for field 1/varint is **0x08**, and the value 150 encodes as **0x96 0x01**. The message payload is **08 96 01** (3 bytes). This example shows that actual size includes the tag, not just the value bytes.

### Which Numeric Type Should You Choose?

| Actual data | Usually sensible choice | Why |
| --- | --- | --- |
| Retry counts, small non-negative indices | **int32** or **uint32** | Varint is compact for small values |
| Temperature deltas, positive/negative offsets near 0 | **sint32** or **sint64** | ZigZag optimizes small negative numbers |
| Unsigned counters that may exceed Java's positive range | **uint32/uint64** | Sufficient range, though Java must interpret them as unsigned |
| Very large 32-bit values occurring frequently | **fixed32/sfixed32** | Fixed size can be smaller than varint |
| Very large 64-bit values occurring frequently | **fixed64/sfixed64** | Fixed 8 bytes for the value part |
| Continuous measurements with acceptable rounding error | **float/double** | Floating-point representation, not exact |

Do not change the type of **an already deployed field** merely because another option looks like it saves bytes. Even though **int32** and **sint32** both use wire type 0, they decode values differently; **float** and **fixed32** both use wire type 5, yet their bits mean different things. When you need to change semantics or encoding, the safe approach is usually to **add a new field with a new number**, gradually migrate clients/servers, and then **reserve** the old number.

## 5. string vs. bytes: Text Is Not Binary Data

These two types both use **wire type 2** (length-delimited), but differ completely in semantics:

| Criterion | **string** | **bytes** |
| --- | --- | --- |
| Meaning | UTF-8 encoded Unicode text | Arbitrary sequence of bytes |
| Java type | **String** | Immutable **ByteString** |
| Default | **""** | **ByteString.EMPTY** |
| Suitable data | Names, descriptions, text codes, emails | Binary payloads, compressed data, encrypted content |
| Protobuf JSON | JSON string | Base64 string |

Example:

~~~proto
message PayloadExample {
  string display_name = 1;
  bytes raw_payload = 2;
}
~~~

~~~java
import com.google.protobuf.ByteString;

byte[] raw = new byte[] {(byte) 0x00, (byte) 0xFF};

PayloadExample sample = PayloadExample.newBuilder()
    .setDisplayName("Device 1")
    .setRawPayload(ByteString.copyFrom(raw))
    .build();

String text = sample.getDisplayName();
ByteString payload = sample.getRawPayload();
byte[] copiedBytes = payload.toByteArray();
System.out.println(payload.size()); // 2
~~~

**ByteString.copyFrom(...)** creates an immutable value from the input bytes. When handling content known for sure to be UTF-8, you can use **ByteString.copyFromUtf8("...")** and **toStringUtf8()**; do not automatically decode arbitrary binary data into text.

**string** must represent valid UTF-8 when transmitted via Protobuf. Do not use **bytes** to bypass encoding validation for data that is actually text. Conversely, do not put compressed image data or binary packets into a **string** just because Java can construct a character string from bytes.

**bytes** and **string** can hold large amounts of data; Protobuf does not enforce business limits such as maximum image size on its own. In a Spring gRPC application, you must combine payload size checks, gRPC message size limit settings, and an appropriate storage policy. Avoid placing huge binary blobs into a single unary request if streaming/chunking is a better fit.

## 6. Default Values and Scalar Field Presence

With **regular scalars** in proto3, if the sender omits the field, Java still returns the default value. For example:

~~~proto
message PatchDeviceRequest {
  string device_id = 1;
  bool enabled = 2;
  int32 threshold = 3;
  optional bool calibrated = 4;
  optional int32 calibration_offset = 5;
}
~~~

State when creating a message with only **device_id**:

| Field | Getter value | Has a has...() method? | Meaning |
| --- | --- | --- | --- |
| **enabled** | **false** | No | Cannot distinguish "not sent" from "sent false" |
| **threshold** | **0** | No | Cannot distinguish "not sent" from "sent 0" |
| **calibrated** | **false** | **hasCalibrated()** | Distinguishes absent from intentionally setting false |
| **calibration_offset** | **0** | **hasCalibrationOffset()** | Distinguishes absent from intentionally setting 0 |

With **optional**, explicit presence is remembered in the builder/message, even when the value equals the default:

~~~java
PatchDeviceRequest notSet = PatchDeviceRequest.newBuilder()
    .setDeviceId("sensor-7")
    .build();

PatchDeviceRequest explicitlyFalse = PatchDeviceRequest.newBuilder()
    .setDeviceId("sensor-7")
    .setCalibrated(false)
    .setCalibrationOffset(0)
    .build();

System.out.println(notSet.getCalibrated());       // false
System.out.println(notSet.hasCalibrated());       // false
System.out.println(explicitlyFalse.getCalibrated()); // false
System.out.println(explicitlyFalse.hasCalibrated()); // true
System.out.println(explicitlyFalse.hasCalibrationOffset()); // true
~~~

Scalars without presence are normally **not serialized when equal to their default value**. An **optional** scalar with presence carries the "was set" information when serialized, even if the value equals the default. This is an important difference for partial-update APIs or "reset value" commands.

**Proto3 has no required label**: the application must validate required fields according to business rules, such as **device_id** not being empty. Getters of scalars without presence do not return **null**; setters of generated Protobuf Java code also do not use **null** as a way to indicate "absent".

**repeated** scalar values have list APIs like **getSamplesList()** and **addSamples(...)**, without **hasSamples()**. If an update operation needs to distinguish "do not change the list" from "clear the entire list", design the update request with a field mask (**FieldMask**) or a separate control structure.

## 7. A Telemetry Contract Using Scalars in a Spring gRPC RPC

Suppose a device sends measurements to a Spring gRPC backend. Each field below serves a clear purpose:

~~~proto
syntax = "proto3";

package learning.telemetry.v1;

option java_package = "com.example.telemetry.v1";
option java_multiple_files = true;

message SubmitReadingRequest {
  string device_id = 1;
  uint64 sequence_id = 2;
  sint32 temperature_delta_milli_c = 3;
  double voltage = 4;
  optional bool calibrated = 5;
  bytes raw_payload = 6;
  repeated float samples = 7;
}

message SubmitReadingResponse {
  bool accepted = 1;
  string receipt_id = 2;
}

service TelemetryService {
  rpc SubmitReading(SubmitReadingRequest)
      returns (SubmitReadingResponse);
}
~~~

Choice rationale:

- **device_id** uses **string** because it is a textual identifier, not a number for calculation.
- **sequence_id** uses **uint64** to represent a non-negative counter with a large range; the Java side must pay attention to unsigned interpretation.
- **temperature_delta_milli_c** uses **sint32** because temperature deltas are typically negative/positive values around 0; the field name clearly states the unit in milli-degrees Celsius.
- **voltage** uses **double** because it is a real-valued measurement, though the server must still validate finiteness and business bounds.
- **calibrated** uses **optional bool** because the receiver must know whether the calibration flag was actually provided.
- **raw_payload** holds bytes from the device; **samples** holds multiple **float** samples where sampling order may matter.

### Code Generation and Java Usage

Once code generation is configured with **protoc**, the Java plugin, and the gRPC Java plugin, you will have classes such as **SubmitReadingRequest**, **SubmitReadingResponse**, and **TelemetryServiceGrpc** in the **com.example.telemetry.v1** package. How build plugins are configured depends on the project; the schema determines the Java types and methods, while Spring gRPC handles wiring the client/server with the gRPC channel.

~~~java
import com.example.telemetry.v1.SubmitReadingRequest;
import com.google.protobuf.ByteString;

long sequence = Long.parseUnsignedLong("18446744073709551615");

SubmitReadingRequest request = SubmitReadingRequest.newBuilder()
    .setDeviceId("sensor-7")
    .setSequenceId(sequence)
    .setTemperatureDeltaMilliC(-125)
    .setVoltage(3.3d)
    .setCalibrated(false) // Present even though the value is false.
    .setRawPayload(ByteString.copyFrom(new byte[] {0x01, 0x02}))
    .addSamples(1.25f)
    .addSamples(2.50f)
    .build();

System.out.println(request.getDeviceId()); // sensor-7
System.out.println(Long.toUnsignedString(request.getSequenceId()));
// 18446744073709551615
System.out.println(request.hasCalibrated()); // true
System.out.println(request.getCalibrated());  // false
System.out.println(request.getSamplesCount()); // 2
~~~

The builder accepts **long** for **uint64** because it stores the 64-bit bit pattern. When sent over gRPC, the receiver decodes the same bits and can use **Long.toUnsignedString(...)** to display it accurately. Do not use **String.valueOf(request.getSequenceId())** if you need to display the unsigned meaning.

You can verify Protobuf round-trip serialization without starting a server:

~~~java
import static org.junit.jupiter.api.Assertions.*;

SubmitReadingRequest decoded =
    SubmitReadingRequest.parseFrom(request.toByteArray());

assertEquals(request, decoded);
assertEquals("18446744073709551615",
    Long.toUnsignedString(decoded.getSequenceId()));
assertEquals(-125, decoded.getTemperatureDeltaMilliC());
assertTrue(decoded.hasCalibrated());
assertFalse(decoded.getCalibrated());
assertEquals(2, decoded.getRawPayload().size());
~~~

### Server-Side Data Validation

Scalar types only constrain representation; **they do not automatically guarantee business-valid data**. For example, a **double** can be NaN and a **string** can be empty. The RPC handler below illustrates how the server rejects invalid input:

~~~java
import com.example.telemetry.v1.SubmitReadingRequest;
import com.example.telemetry.v1.SubmitReadingResponse;
import com.example.telemetry.v1.TelemetryServiceGrpc;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;

public final class TelemetryEndpoint
        extends TelemetryServiceGrpc.TelemetryServiceImplBase {

    @Override
    public void submitReading(SubmitReadingRequest request,
            StreamObserver<SubmitReadingResponse> observer) {
        if (request.getDeviceId().isBlank()
                || !Double.isFinite(request.getVoltage())
                || request.getSamplesCount() > 1000) {
            observer.onError(Status.INVALID_ARGUMENT
                .withDescription("Invalid telemetry reading")
                .asRuntimeException());
            return;
        }

        SubmitReadingResponse response = SubmitReadingResponse.newBuilder()
            .setAccepted(true)
            .setReceiptId("receipt-42")
            .build();
        observer.onNext(response);
        observer.onCompleted();
    }
}
~~~

This endpoint class illustrates handling request/response types generated from .proto. To run in a Spring gRPC application, the service must be registered and configured according to the mechanism of the Spring gRPC library version the project uses. Requirements such as metadata inspection, deadlines, detailed statuses, interceptors, TLS, streaming, message size limits, authentication, and reliability monitoring are configured further at the respective application/protocol layers.

## 8. Scalars in Protobuf JSON Are Not Always Like "Regular" JSON

gRPC normally uses binary Protobuf. However, when communicating via gRPC JSON transcoding, writing controlled logs, or converting with **google.protobuf.util.JsonFormat**, you need to know the **Protobuf JSON mapping**:

| Scalar | Protobuf JSON representation | Points to watch |
| --- | --- | --- |
| **int32/sint32/uint32/fixed32/sfixed32** | JSON number | Receiver must still validate 32-bit range and signed/unsigned |
| **int64/sint64/uint64/fixed64/sfixed64** | Decimal number string | Prevents precision loss when JSON is parsed by systems using 64-bit floats, such as JavaScript |
| **float/double** | JSON number | **NaN**, **Infinity**, **-Infinity** are represented as special strings per Protobuf JSON |
| **bool** | **true** or **false** | Does not imply "was sent" if the field lacks presence |
| **string** | JSON string | Unicode text content |
| **bytes** | Base64 JSON string | Not a JSON array of numbers representing bytes |

Example JSON corresponding to the telemetry request above:

~~~json
{
  "deviceId": "sensor-7",
  "sequenceId": "18446744073709551615",
  "temperatureDeltaMilliC": -125,
  "voltage": 3.3,
  "calibrated": false,
  "rawPayload": "AQI=",
  "samples": [1.25, 2.5]
}
~~~

Field names in JSON are normally converted to **lowerCamelCase** under the default mapping (**sequence_id** becomes **sequenceId**). **rawPayload** is Base64 of the two bytes **01 02**; **sequenceId** is a string because it belongs to the 64-bit family. **calibrated: false** appears when the **optional bool** field has been explicitly set.

If you use general-purpose JSON libraries to serialize a Protobuf Java class directly, the output may not follow the Protobuf JSON mapping. Use **JsonFormat** or a dedicated Protobuf converter when converting between the two formats. Avoid using JSON output in logs as proof of whether an implicit-presence scalar was set by the sender.

## 9. Common Mistakes When Working with Scalars

| Situation | Consequence | How to handle |
| --- | --- | --- |
| Treating **uint64** returning a negative **long** as corrupted data | Incorrect display/comparison of unsigned numbers | Use **Long.toUnsignedString**, **Long.compareUnsigned** |
| Using **int32** for counters that may exceed 2,147,483,647 | Range overflow and business bugs | Choose **uint32** or a 64-bit type based on actual range |
| Using **int32** for many small negative deltas | Varint payload is larger than necessary | Consider **sint32** for new schemas |
| Using **float** for money calculations | Rounding errors during addition/subtraction/comparison | Use smallest currency unit as integer or a dedicated decimal type |
| Using **bytes** and calling **toStringUtf8()** by default | Misinterprets binary bytes as text | Decode according to the agreed payload format |
| Relying on **getEnabled() == false** to infer the client sent false | Confuses absence with default value | Use **optional bool** or an explicit update mechanism |
| Changing **int32** to **sint32** on the same field number | Old and new versions decode different values | Add a new field; follow versioning and reserve rules |
| Using **String.valueOf(uint64Long)** to format unsigned numbers | Prints negative numbers for large values | Use unsigned conversion |
| Assuming **double** only accepts finite numbers | NaN/Infinity slip past business rules | Check **Double.isFinite** |
| Putting 64-bit integers directly as JSON numbers for JavaScript | May lose precision | Follow Protobuf JSON mapping using decimal strings |

Scalar selection also affects **performance and reliability**. However, bandwidth optimization requires measuring with real data, including field frequency, tag overhead, RPC style, and compression policy; do not change a production contract based solely on a theoretical size table.

## 10. Practice Exercises

Design an **UpdateSensorConfigRequest** message for a gRPC endpoint with the following requirements:

1. **sensor_id** is a text identifier that must not be empty.
2. **retry_limit** is a small, always non-negative number; explain why to choose **int32** or **uint32**.
3. **calibration_shift_milli_c** is a temperature offset that can be negative or positive around 0; choose an appropriate space-saving numeric type.
4. **firmware_version** is a character string; **firmware_blob** is binary firmware data. Explain why the types of these two fields must not be swapped.
5. **enabled** must distinguish "do not update" from "set to false". Declare the field with explicit presence and verify **hasEnabled()** after serialize/parse.
6. **max_sequence_id** must accept **18,446,744,073,709,551,615**; write Java code to set the value and print it as an unsigned number.
7. **recent_samples** is an ordered collection of measurement samples. Choose **repeated float** or **repeated double** and explain the precision/cost trade-off.

A valid schema draft:

~~~proto
syntax = "proto3";

message UpdateSensorConfigRequest {
  string sensor_id = 1;
  uint32 retry_limit = 2;
  sint32 calibration_shift_milli_c = 3;
  string firmware_version = 4;
  bytes firmware_blob = 5;
  optional bool enabled = 6;
  uint64 max_sequence_id = 7;
  repeated float recent_samples = 8;
}
~~~

Try creating two **UpdateSensorConfigRequest** objects: one **without calling setEnabled(...)**, and the other calling **setEnabled(false)**. Both before and after **parseFrom(toByteArray())**, confirm that the getter returns **false** in both cases, while only the second object has **hasEnabled() == true**. Then use **Long.parseUnsignedLong(...)** and **Long.toUnsignedString(...)** with **max_sequence_id** to test the maximum value.

**Self-assessment:** given that they all map to Java **int**, can you explain why **int32** differs from **uint32**, **sint32**, and **fixed32**? When a value does not appear in a request, can you tell whether it is an implicit default or an explicitly sent value? Answering these two questions is the foundation for reading Protobuf requests/responses accurately and designing stable Spring gRPC contracts.
