# Choosing RPC Types by Data Flow in Spring gRPC

In **Spring gRPC**, before writing a service method, you need to answer one question: **How will data flow between client and server during a single call?** The answer determines whether to use **unary**, **server streaming**, **client streaming**, or **bidirectional streaming RPC**. This choice affects the **Protocol Buffers** contract, the Java code generated by gRPC, client/server lifecycle, testing strategy, deadlines, error handling, and operational costs.

Do not choose streaming merely because you want to process many records or because the data is large. A single Protobuf message can hold many items; conversely, streaming is useful when messages must arrive **over time**, can be processed **incrementally**, or when **both sides must interact continuously**. This lesson provides a decision framework based on data flow and business requirements, accompanied by Java/Spring implementation examples.

## 1. Starting from the Shape of the Data Flow

Every gRPC method has two directions:

- **Request:** client → server.
- **Response:** server → client.

For each direction, determine whether the sender needs to emit **one message** or **a sequence of messages**. This yields four shapes:

| RPC Type | Request Stream | Response Stream on Success | Deciding Characteristic |
| --- | --- | --- | --- |
| **Unary** | 1 message | 1 message | One question/command, one result |
| **Server streaming** | 1 message | 0..N messages | Client asks/subscribes once; server emits results incrementally |
| **Client streaming** | 0..N messages | 1 message | Client sends data incrementally; server returns aggregated/final result |
| **Bidirectional streaming** | 0..N messages | 0..N messages | Both sides exchange multiple messages and can operate concurrently |

These counts are **the number of Protobuf messages in one RPC**, not the number of TCP packets or HTTP/2 frames. With streaming, 0 messages can be protocol-valid; the server may require at least one message per business rules. With unary, a successful call has exactly one request and one response; a failed call may have no application response.

~~~mermaid
flowchart TD
    A["Data exchange requirement"] --> B{"Does the client need to send multiple messages in one RPC?"}
    B -->|"No"| C{"Does the server need to emit multiple messages over time?"}
    B -->|"Yes"| D{"Does the server need to send multiple responses?"}
    C -->|"No"| E["Unary"]
    C -->|"Yes"| F["Server streaming"]
    D -->|"No"| G["Client streaming"]
    D -->|"Yes"| H["Bidirectional streaming"]
~~~

The flowchart is the first filtering step. Next, ask: does the data actually need **continuous transmission**, do results need to arrive **before all sending completes**, how can the client **reconnect**, and does the added complexity of streaming deliver measurable benefits?

## 2. Five Questions for Choosing an RPC Type

### Question 1: Do Results Need to Be Returned Before All Work Finishes?

For example, querying **the current state of a device** returning a single small object: **unary**. A query needing **to watch state changes for 30 seconds**, where the server pushes updates as they occur: **server streaming**.

If the data has 100 items that are easy to compute together and pack neatly into a message with a **repeated** field, unary may fit. If you want to receive millions of items incrementally, avoid waiting for the entire result set, and avoid holding the whole list in RAM, prefer server streaming or paginated unary calls per page.

### Question 2: Does the Client Produce Data Once or Continuously?

If the client already has a small payload and simply wants the server to process it and reply: **unary**. If the client generates many records over time, wants to send them incrementally for server validation/aggregation, and only needs one final result: **client streaming**.

Example: an agent records 10,000 temperature values and sends them to the server. If the values are already available and combining them into one small message makes sense, a unary batch is simpler. If values are produced continuously or you do not want to hold them all in memory, client streaming is advantageous.

### Question 3: Does the Client Need to Adjust Behavior Based on Immediate Responses?

A device sending measurements while needing to receive commands to reduce sampling frequency immediately in the same session: **bidirectional streaming**. The client can send new messages while receiving responses from the server.

If the server only needs to send **one final conclusion** after receiving all requests, use **client streaming**. If the client only needs to send **one initial subscription condition** and receive updates, use **server streaming**.

### Question 4: Is Keeping an RPC Open Worth the Cost?

Each open stream consumes connection resources, state, and tracking/cancellation management. If updates are infrequent, the client can use bounded **unary polling**. If real-time push is needed, server streaming reduces polling. If continuous two-way interaction is needed, bidirectional streaming can reduce the overhead of establishing multiple RPCs and lower round-trip latency.

No single RPC type is always faster in every scenario. Performance depends on message size, frequency, network latency, serialization, memory pressure, backpressure, and concurrent stream count.

### Question 5: When a Mid-Stream Error Occurs, What Level of Recovery Is Needed?

Unary calls are usually easy to pair with an **idempotency key** and retry per operation. With streaming, errors can occur **after part of the requests have been processed or part of the responses have reached the client**. You must design **message IDs**, **sequences**, checkpoints, or resume tokens to continue safely.

Simplicity of data recovery is also a method-selection criterion. When recovering long streams is infeasible, splitting into **multiple idempotent and paginated unary RPCs** is often the more resilient approach.

## 3. Decision Matrix by Practical Use Case

| Problem | Usually Suitable Type | Reason | Condition That Changes the Choice |
| --- | --- | --- | --- |
| Fetch user profile by ID | **Unary** | One request, one result | Need continuous live updates → server streaming |
| Calculate total fee of a shopping cart | **Unary** | All input data available, single result | Cart items streamed incrementally → consider client streaming |
| Track order status | **Server streaming** | One subscription, multiple status events | Very infrequent updates and polling suffices → unary |
| Upload many logs and receive one report | **Client streaming** | Many chunks sent incrementally, one aggregated result | Need ack/checkpoint after each chunk → bidi or auxiliary API |
| Device sends telemetry while receiving commands | **Bidirectional streaming** | Both directions operate independently | Device only sends logs → client streaming |
| Paginate a list of millions of records | **Multiple unary** or **server streaming** | Choose based on pause/resume and incremental processing needs | Need independent pages, caching, or cursor resume → unary pagination |
| Send a small file already in RAM | **Unary** | Less stream-management code | Large file or generated incrementally → client streaming |
| Interactive chat session | **Bidirectional streaming** | Either side emits messages at any time | Only receiving notifications after subscribing → server streaming |

**Pragmatic rule:** prefer the simplest type that still satisfies the **data-flow semantics**. Having a large number of records, by itself, is not sufficient reason to choose streaming.

## 4. Designing a .proto Contract for All Four Options

Suppose we build a **FleetTelemetry** service for a fleet of devices. A device can query its current state, subscribe to changes, upload a batch of readings, and participate in a bidirectional control session.

File **src/main/proto/fleet_telemetry.proto**:

~~~proto
syntax = "proto3";

package demo.fleet.v1;

option java_package = "vn.demo.grpc.fleet.v1";
option java_multiple_files = true;
option java_outer_classname = "FleetTelemetryProto";

service FleetTelemetry {
  // One request -> one response.
  rpc GetCurrentState(DeviceQuery) returns (DeviceState);

  // One request -> multiple responses emitted incrementally.
  rpc WatchState(DeviceQuery) returns (stream DeviceState);

  // Many records sent incrementally -> one final result.
  rpc UploadReadings(stream Reading) returns (UploadReport);

  // Many bidirectional signals -> interactive session.
  rpc ControlSession(stream DeviceSignal) returns (stream ControlEvent);
}

message DeviceQuery {
  string device_id = 1;
}

message DeviceState {
  string device_id = 1;
  bool online = 2;
  int64 version = 3;
}

message Reading {
  string device_id = 1;
  int64 sequence = 2;
  double temperature = 3;
}

message UploadReport {
  int64 accepted_count = 1;
  double average_temperature = 2;
}

message DeviceSignal {
  string device_id = 1;
  int64 sequence = 2;
  string payload = 3;
}

message ControlEvent {
  int64 related_sequence = 1;
  string command = 2;
}
~~~

Read the four **rpc** lines according to the placement of the **stream** keyword:

~~~proto
rpc GetCurrentState(DeviceQuery) returns (DeviceState);
rpc WatchState(DeviceQuery) returns (stream DeviceState);
rpc UploadReadings(stream Reading) returns (UploadReport);
rpc ControlSession(stream DeviceSignal) returns (stream ControlEvent);
~~~

This determines message **cardinality**. It does not mandate that WatchState emit every second, that UploadReadings contain only one device, or that ControlSession produce one response per request. Those rules must be specified separately in the business contract.

In Protobuf, a message can also contain **repeated** to represent a list:

~~~proto
message ReadingBatch {
  repeated Reading items = 1;
}

rpc UploadBatch(ReadingBatch) returns (UploadReport);
~~~

**UploadBatch** is still a **unary RPC**, even though the message contains multiple Readings. Between **UploadBatch** and **UploadReadings**, choose based on how data is generated, size limits, incremental processing needs, and error-recovery cost. Ensure messages do not exceed client/server size limits; for very large payloads, simply raising the message size limit can cause memory spikes.

## 5. How Does the Java API Change with the RPC Choice?

After running **protoc** and the gRPC Java plugin, generated methods have matching signatures. For the Java server:

~~~java
// Unary: receives one request.
public void getCurrentState(
    DeviceQuery request,
    StreamObserver<DeviceState> responseObserver);

// Server streaming: receives one request, emits many responses.
public void watchState(
    DeviceQuery request,
    StreamObserver<DeviceState> responseObserver);

// Client streaming: receives an observer to emit response,
// returns an observer to receive requests sequentially.
public StreamObserver<Reading> uploadReadings(
    StreamObserver<UploadReport> responseObserver);

// Bidirectional: one receiving observer and one sending observer.
public StreamObserver<DeviceSignal> controlSession(
    StreamObserver<ControlEvent> responseObserver);
~~~

These are **illustrative signatures** in a class extending **FleetTelemetryGrpc.FleetTelemetryImplBase**. Depending on the chosen RPC type, writing a service in Spring takes two main forms:

- **Unary/server streaming:** server directly receives one request and one **responseObserver**.
- **Client/bidirectional streaming:** server receives **responseObserver** and returns a **request observer** to receive requests sequentially.

### Client: How to Read and Write Messages

~~~java
// Assume channel is configured and lifecycle-managed.
var blocking = FleetTelemetryGrpc.newBlockingStub(channel);
var async = FleetTelemetryGrpc.newStub(channel);

// Unary: receive one result.
DeviceState state = blocking.getCurrentState(query);

// Server streaming: iterate multiple results from one query.
Iterator<DeviceState> states = blocking.watchState(query);
while (states.hasNext()) {
    DeviceState nextState = states.next();
    // Process each state.
}

// Client streaming: async stub takes final response observer,
// and returns an observer for the client to send multiple Readings.
StreamObserver<Reading> uploadRequests =
    async.uploadReadings(uploadResponseObserver);
uploadRequests.onNext(firstReading);
uploadRequests.onNext(secondReading);
uploadRequests.onCompleted();

// Bidi: simultaneously has a receiving observer and a sending observer.
StreamObserver<DeviceSignal> controlRequests =
    async.controlSession(controlResponseObserver);
controlRequests.onNext(firstSignal);
// Client can still receive ControlEvents while still sending.
controlRequests.onCompleted();
~~~

The variables **query**, **firstReading**, **secondReading**, **firstSignal**, and the two response observers here are assumed to be created from the Protobuf messages; the snippet highlights the API differences among the four types. With streaming, calling **onNext()** on the sender side does not guarantee the server has received, processed, or durably persisted the data.

## 6. Spring Server Illustration: Designing for Stream Needs

The following snippet demonstrates two methods with the same input data but different delivery choices: **GetCurrentState** returns one state and **WatchState** emits three updates. This is a finite example to highlight the difference; in real applications, updates typically arrive from an event source:

~~~java
package vn.demo.app;

import io.grpc.Status;
import io.grpc.stub.StreamObserver;
import org.springframework.stereotype.Service;
import vn.demo.grpc.fleet.v1.DeviceQuery;
import vn.demo.grpc.fleet.v1.DeviceState;
import vn.demo.grpc.fleet.v1.FleetTelemetryGrpc;

@Service
public class FleetTelemetryService
        extends FleetTelemetryGrpc.FleetTelemetryImplBase {

    @Override
    public void getCurrentState(
            DeviceQuery request,
            StreamObserver<DeviceState> responseObserver) {
        if (request.getDeviceId().isBlank()) {
            responseObserver.onError(Status.INVALID_ARGUMENT
                .withDescription("device_id is required")
                .asRuntimeException());
            return;
        }

        responseObserver.onNext(DeviceState.newBuilder()
            .setDeviceId(request.getDeviceId())
            .setOnline(true)
            .setVersion(1)
            .build());
        responseObserver.onCompleted();
    }

    @Override
    public void watchState(
            DeviceQuery request,
            StreamObserver<DeviceState> responseObserver) {
        if (request.getDeviceId().isBlank()) {
            responseObserver.onError(Status.INVALID_ARGUMENT
                .withDescription("device_id is required")
                .asRuntimeException());
            return;
        }

        for (int version = 1; version <= 3; version++) {
            responseObserver.onNext(DeviceState.newBuilder()
                .setDeviceId(request.getDeviceId())
                .setOnline(true)
                .setVersion(version)
                .build());
        }
        responseObserver.onCompleted();
    }
}
~~~

When Spring gRPC is configured to auto-register beans implementing **BindableService**, **@Service** lets Spring manage the service implementation. Registration details may vary by Spring gRPC version or starter. Both methods in the example take one **DeviceQuery**; **the difference lies in how many response messages** the server is allowed to send.

Do not copy the **for** loop above into an infinite update stream. For real server streaming, you need subscription registration/unsubscription, flow control, synchronization across multiple producers, and resource cleanup when the client disconnects.

### Server Example Requiring Per-Request-Stream State

With **UploadReadings**, the server must process multiple Readings within **the same RPC**. Place counters inside the **newly created request observer for each call**:

~~~java
@Override
public StreamObserver<Reading> uploadReadings(
        StreamObserver<UploadReport> responseObserver) {
    return new StreamObserver<>() {
        private long count;
        private double sum;
        private boolean ended;

        @Override
        public void onNext(Reading reading) {
            if (ended) return;
            if (reading.getDeviceId().isBlank()
                    || !Double.isFinite(reading.getTemperature())) {
                ended = true;
                responseObserver.onError(Status.INVALID_ARGUMENT
                    .withDescription("invalid reading")
                    .asRuntimeException());
                return;
            }
            count++;
            sum += reading.getTemperature();
        }

        @Override
        public void onError(Throwable error) {
            ended = true; // Discard incomplete aggregation.
        }

        @Override
        public void onCompleted() {
            if (ended) return;
            ended = true;
            responseObserver.onNext(UploadReport.newBuilder()
                .setAcceptedCount(count)
                .setAverageTemperature(count == 0 ? 0 : sum / count)
                .build());
            responseObserver.onCompleted();
        }
    };
}
~~~

This method snippet is an **addition to FleetTelemetryService** above (requiring the corresponding **Reading** and **UploadReport** imports). In-memory aggregation makes the **many requests → one response** semantics clear. In production, enforce limits on message count, size, and processing time, and decide when data is committed.

If the client needs acknowledgment **immediately after each Reading** and adjusts its subsequent sending rate per server instructions, consider a bidirectional **ControlSession** or a separate acknowledgment API. Do not attempt to emit multiple **UploadReport** messages in a client streaming RPC that declares a single response.

## 7. Subtle Trade-Offs When Choosing Streaming

### 7.1. Payload Size and Memory

**Unary batching** can be easy to cache, retry, and simple at the API level, yet typically requires building a sufficiently large message before sending. **Streaming** enables incremental processing, reducing the need to buffer all data in memory, though it **does not automatically prevent** an application from building unbounded queues.

For large files or continuously generated logs, client streaming is generally advantageous. If data is already available, moderate in size, needs a single result, and poses little risk of hitting message limits, a unary batch may suffice.

### 7.2. Latency, Call Count, and Cacheability

**Server streaming** can deliver the first record sooner rather than waiting for the entire result set. **Bidirectional streaming** can reduce waiting when continuous exchange is needed. Conversely, services with many discrete, short operations needing independent retries may fit unary better.

Caching individual unary requests or pages is usually simpler than caching an evolving stream. However, do not choose an RPC type solely on performance assumptions: measure **p50/p95/p99 latency**, throughput, CPU/memory usage, and concurrent streams under realistic load.

### 7.3. Flow Control and Backpressure

Streaming can encounter cases where **the sender outpaces the receiver**. HTTP/2 and gRPC have transport-level flow control, yet applications still must protect data queues.

In gRPC Java:

- **ClientCallStreamObserver** and **ServerCallStreamObserver** expose **isReady()** and **setOnReadyHandler(...)** to coordinate send rates.
- For async client streaming, send callbacks can be configured in **ClientResponseObserver.beforeStart(...)**.
- **isReady()** indicates write readiness relative to flow control/buffers; **it does not mean the server has processed or durably stored the data**.
- **StreamObserver is not thread-safe by default**. When multiple threads send to the same observer, serialize **onNext**, **onCompleted**, and **onError** calls.

Additionally, set limits on **message size**, **message/batch count**, **concurrent streams**, **queue capacity**, and **lifetime**. Do not keep a stream open forever just because the protocol permits it.

### 7.4. Ordering and Bidirectional Independence

Within a stream, gRPC preserves **per-direction message ordering**. With bidirectional streaming, there is no global ordering between requests and responses; one request may trigger 0, 1, or many response events.

For instance, if the server sends independent control signals, include an **event type** and optionally **related_sequence** to identify which message a response corresponds to. The **stream** keyword does not create an automatic request-response pairing mechanism.

### 7.5. Limits of Transactional Correctness

Client streaming and bidirectional streaming can fail after the server has persisted **part** of the data. **onCompleted()** only indicates that the message stream finished per protocol; it does not guarantee an all-or-nothing business commit.

If atomic transactions are needed, design a **staging** area, separate transaction/commit steps, or explicit final confirmation messages. If resuming after errors is needed, use an **upload ID**, sequence/checkpoints, and deduplication. Blindly resending the whole stream without these mechanisms can cause duplicate side effects.

## 8. How Deadlines, Cancellation, and Status Affect the Choice

A **deadline** is the time limit for the **entire RPC**, even when it carries thousands of messages. For short unary calls, relatively short deadlines are typical; for event-watching streams, deadlines must fit the usage window or reconnection policy.

~~~java
var stub = FleetTelemetryGrpc.newStub(channel)
    .withDeadlineAfter(30, TimeUnit.SECONDS);
~~~

This example sets a 30-second deadline on a stub; sending additional messages **does not automatically extend** the deadline. For streams that may run long, define lifetimes and recovery behavior after deadline expiration or disconnection.

| Status | Meaning | Typical Action |
| --- | --- | --- |
| **OK** | RPC completed successfully | Use final result |
| **INVALID_ARGUMENT** | Invalid request/message | Check input; do not retry verbatim |
| **NOT_FOUND** | Resource does not exist | Handle not-found outcome |
| **UNAUTHENTICATED** | Missing or invalid authentication | Refresh/handle credentials |
| **PERMISSION_DENIED** | Insufficient permissions | Check authorization |
| **RESOURCE_EXHAUSTED** | Quota/memory/limit exceeded | Throttle load, review batch/stream sizing |
| **DEADLINE_EXCEEDED** | Exceeded time budget | Check which work executed |
| **CANCELLED** | Call was cancelled | Clean up resources, stop tasks |
| **UNAVAILABLE** | Service/connection temporarily unavailable | Controlled retry when safe |

On a client using a blocking stub, errors usually surface as **StatusRuntimeException**; with an async stub, errors enter the **onError(Throwable)** callback. On the server, you can call **responseObserver.onError(Status.INVALID_ARGUMENT.withDescription("...").asRuntimeException())**.

With **server streaming**, the client may receive several messages and then hit an error. Already-read messages do not mean the RPC completed successfully. With **client streaming/bidi**, the server may have received/persisted some messages even if the client sees **DEADLINE_EXCEEDED** or **UNAVAILABLE**.

Distinguish **normal completion** via **onCompleted()** from RPC **cancellation**. Client streaming/bidi must half-close the send direction once all requests are sent, while still able to wait for responses. Cancellation may stop ongoing server work, but does not automatically roll back committed operations.

## 9. Metadata, Interceptors, and TLS Across All RPC Types

gRPC **metadata** carries call-wide information such as authorization tokens, request IDs, tenant IDs, or trace context. In streaming, metadata does not repeat automatically per message; data that varies per message belongs in the Protobuf payload.

Client/server **interceptors** are suitable for authentication, tracing, timing, and status metrics. For **streaming**, a single RPC can carry many messages and stay open a long time, so also monitor **open stream counts**, **messages/bytes per direction**, **stream duration**, backlog size, and cancellations.

In production deployments:

1. Protect transport with **TLS**; consider **mTLS** when services must authenticate each other.
2. Verify device and tenant permissions on the server; never blindly trust a **device_id** in the payload.
3. Do not log tokens, sensitive metadata, or entire stream contents.
4. Apply per-user/tenant quotas and resource limits for long-lived RPCs.
5. Configure deadlines, retries, and rate limits per method group rather than using one rigid setting for everything.

In local/dev environments, gRPC Java can use **ManagedChannelBuilder.forAddress(...).usePlaintext()** to keep examples simple; production environments require properly secured channels. Exact bean/stub/server configuration depends on the project's Spring gRPC version and starter.

## 10. How to Test Your RPC Choice

Testing must prove the **intended data-flow behavior**, not just that the code compiles and invokes the method.

| Type | Success Test | Error and Limit Tests |
| --- | --- | --- |
| Unary | One request, one response with accurate data | Invalid input; deadline; connection error |
| Server streaming | One request, multiple ordered responses followed by completion | Mid-stream error, cancellation, slow consumer |
| Client streaming | Send multiple requests, receive exactly one summary | Empty stream per policy; invalid message; mid-batch error |
| Bidirectional streaming | Interleaved send and receive, both streams complete properly | Non-1:1 request/response; cancellation; reconnection; flow control |

Example testing the first two methods with **gRPC in-process** to clearly distinguish unary from server streaming:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;

import io.grpc.ManagedChannel;
import io.grpc.Server;
import io.grpc.inprocess.InProcessChannelBuilder;
import io.grpc.inprocess.InProcessServerBuilder;
import java.util.ArrayList;
import java.util.List;
import org.junit.jupiter.api.Test;
import vn.demo.grpc.fleet.v1.DeviceQuery;
import vn.demo.grpc.fleet.v1.DeviceState;
import vn.demo.grpc.fleet.v1.FleetTelemetryGrpc;

class FleetTelemetryServiceTest {

    @Test
    void unaryAndServerStreamingHaveDifferentCardinality()
            throws Exception {
        String name = InProcessServerBuilder.generateName();
        Server server = InProcessServerBuilder.forName(name)
            .directExecutor()
            .addService(new FleetTelemetryService())
            .build().start();
        ManagedChannel channel = InProcessChannelBuilder
            .forName(name)
            .directExecutor()
            .build();

        try {
            var stub = FleetTelemetryGrpc.newBlockingStub(channel);
            DeviceQuery query = DeviceQuery.newBuilder()
                .setDeviceId("sensor-01")
                .build();

            DeviceState one = stub.getCurrentState(query);
            assertEquals(1L, one.getVersion());

            List<DeviceState> updates = new ArrayList<>();
            stub.watchState(query).forEachRemaining(updates::add);
            assertEquals(3, updates.size());
            assertEquals(3L, updates.get(2).getVersion());
        } finally {
            channel.shutdownNow();
            server.shutdownNow();
        }
    }
}
~~~

Running the example requires JUnit, the **gRPC in-process** library, the classes generated from **fleet_telemetry.proto**, and **FleetTelemetryService**. This in-process test verifies the contract at the gRPC Java level; it does not verify that Spring actually registers the bean or configures TLS/interceptors. An integration test starting the Spring context and gRPC server is needed for that integration layer.

For **client streaming**, test sending multiple Readings, half-closing, and receiving exactly one UploadReport. For **bidirectional**, write a test that actually observes responses **before the client half-closes** if that is required by the protocol, rather than sending everything first and only checking the response list afterward.

Load tests should measure throughput, p95/p99 latency, CPU, memory, quotas, open stream counts, and behavior with slow receivers. Decisions to use streaming should be data-driven, especially when considering replacing many small unary calls with a long-lived stream.

## 11. Design Scenario: Choosing RPC Types for a Delivery Platform

Consider a development requirement with four features:

**Feature A — Delivery Fee Calculation:** The user submits origin address, destination, and parcel type and receives the final amount. All data is ready and only one result is needed. **Choose unary**, e.g., **CalculateFee(FeeRequest) returns (FeeReply)**.

**Feature B — Driver Location Tracking:** The client subscribes by trip ID and receives updated coordinates while the trip is in progress. **Choose server streaming**, e.g., **WatchDriver(TripRequest) returns (stream DriverPosition)**. Cancel the subscription when the user leaves the screen; consider sequence-based resumption on reconnect.

**Feature C — Offline Trip Sync:** The driver app buffers coordinates while offline and uploads them incrementally to the server, finally receiving the accepted count. **Choose client streaming**, e.g., **UploadPositions(stream DriverPosition) returns (UploadResult)**. Design an upload ID, batch limits, duplicate prevention, and data commit policies.

**Feature D — Interactive Delivery Dispatch:** The driver sends online/location/status signals; dispatch can send reroute commands immediately during the session. **Choose bidirectional streaming**, e.g., **Dispatch(stream DriverSignal) returns (stream DispatcherEvent)**. Manage flow control, sessions, correlation IDs, and connection recovery.

If Feature D only needed one update after each discrete action, **multiple unary RPCs** could also be a reasonable design. Add a bidirectional stream only when the requirement is genuinely **continuous two-way or interleaved communication**.

## 12. Decision Checklist Before Locking the Contract

Before finalizing a method, confirm:

1. **Cardinality:** does the client send one or many messages; does the server return one or many messages?
2. **Timing:** must messages be processed incrementally while streaming, or wait until complete?
3. **Interactivity:** must the server respond before the client finishes sending, or push events independently?
4. **Volume:** what are the limits on message size, message count, RAM, and RPC lifetime?
5. **Recovery:** if the connection drops mid-stream, what data has already been processed and how will resumption work?
6. **Operations:** what deadlines, cancellation, flow control, metadata, TLS, interceptors, and metrics are needed?
7. **Testing:** which scenarios prove the chosen RPC type fits real-world requirements?

If the answers are unclear, build a small prototype using unary or the corresponding streaming type and **load-test and simulate mid-stream failures** before locking a long-term contract. Changing cardinality in a method definition alters stub APIs, invocation patterns, and client compatibility; once a service has consumers, a new method or migration strategy is typically required.

## 13. Self-Check Exercises

1. An API returns 500 products already in the DB and the client wants pagination and per-page caching. Should you use unary pagination or server streaming? Explain based on error semantics and resumption.
2. A client streams logs continuously for 10 minutes and only wants one final summary report. Which RPC do you choose? How should you configure deadlines and resource limits?
3. The server must send an alert as soon as an anomalous Reading is detected while the client is still sending. Why might client streaming with one final response be insufficient?
4. A client receives 200 responses from server streaming and then hits **UNAVAILABLE**. Why cannot the RPC be treated as successful? Which field should be used to resume from the last received checkpoint?
5. A team wants to replace 1,000 small unary calls with a single bidirectional stream. Which metrics should be measured to decide whether this change truly helps?

**Takeaway:** Choose an RPC type based on **data direction, message cardinality, and when each side needs to send/receive**, and only then evaluate performance and scalability. In Spring gRPC, this decision appears directly in **Protocol Buffers** via the placement of the **stream** keyword, and determines how Java clients and servers use **stubs** and **StreamObserver**. Good designs always pair with appropriate **deadlines, status handling, cancellation, security, flow control, testing, and monitoring** for the RPC lifecycle.
