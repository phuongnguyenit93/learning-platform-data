# `GlobalOpenApiCustomizer` When Targeting Group Documents

A Spring Boot application can expose multiple OpenAPI documents: the default document and documents generated from `GroupedOpenApi`. When you need to add the same metadata to every document, such as contact info, shared servers, extensions, or common security schemes, writing a separate customizer for each group creates duplicated configuration that easily drifts out of sync.

Springdoc-openapi provides `GlobalOpenApiCustomizer` to customize the OpenAPI model globally, covering both the default document and group documents. It is the right choice when a change must be applied consistently across every document. If you only want to affect a single group, use an `OpenApiCustomizer` attached directly to the `GroupedOpenApi` builder. This article explains its scope, safe implementation patterns, and how to verify each document after customization.

## 1. Why Is a Global Customizer Needed?

Suppose a service has these document groups:

| Document | Scope |
|---|---|
| Default document | Default document generated by springdoc; endpoint scope may overlap with groups |
| `public` | API for external clients |
| `admin` | Administrative API |
| `partner` | Partner integration API |

These documents may share certain common details:

- API team contact information.
- Terms of service link.
- Shared server base URL.
- Extensions for gateways or internal tools.
- Security schemes shared across groups.

If you use an `OpenApiCustomizer` that only applies to the default document, the groups may not receive the changes. When the goal is to affect all documents, `GlobalOpenApiCustomizer` expresses that scope accurately.

## 2. Distinguishing Customizer Types

Springdoc has several extension points with different scopes. Choosing the right type avoids the situation where code runs yet some documents remain unupdated.

| Mechanism | Scope | Purpose |
|---|---|---|
| `OpenApiCustomizer` bean | Default OpenAPI document | Modify the default document |
| `GlobalOpenApiCustomizer` bean | Default document and group documents | Apply shared metadata or changes across all documents |
| `GroupedOpenApi.Builder.addOpenApiCustomizer(...)` | The group configured in that builder | Customize a single group specifically |
| `OperationCustomizer` | Operations in the default document according to the registration mechanism | Adjust individual operations, such as summary or parameters |
| `GlobalOperationCustomizer` | Operations in the default document and groups | Adjust individual operations globally |

The key difference is the level of customization:

- `GlobalOpenApiCustomizer` receives the entire `OpenAPI` document, so it can modify `info`, `servers`, `tags`, `components`, security, and document-level properties.
- `GlobalOperationCustomizer` receives each `Operation`, making it suitable when applying rules to operations across multiple groups.
- `GroupedOpenApi.Builder.addOpenApiCustomizer(...)` restricts changes to a specific group.

Do not use a document-level customizer to handle logic that depends on per-method details when an operation customizer is a better fit. Conversely, do not repeat a group customizer if the change is truly identical across all documents.

## 3. Declaring a `GlobalOpenApiCustomizer` Bean

In springdoc-openapi 2.x, the `GlobalOpenApiCustomizer` interface resides in the `org.springdoc.core.customizers` package. You can register a bean in a Spring configuration class:

```java
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.info.Contact;
import io.swagger.v3.oas.models.info.Info;
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class GlobalOpenApiConfiguration {

    @Bean
    GlobalOpenApiCustomizer commonDocumentMetadata() {
        return openApi -> {
            if (openApi.getInfo() == null) {
                openApi.setInfo(new Info()
                        .title("Application API")
                        .version("1.0.0"));
            }

            if (openApi.getInfo().getContact() == null) {
                openApi.getInfo().setContact(new Contact()
                        .name("API Support")
                        .email("api-support@example.com"));
            }

            if (openApi.getInfo().getDescription() == null) {
                openApi.getInfo().setDescription(
                        "API published by the service platform.");
            }
        };
    }
}
```

Spring manages the bean and springdoc invokes the customizer when building the documents. Because it is a global customizer, the same logic can affect both the default document and each group.

In the example, the customizer only supplements information when the corresponding field is absent. This preserves group-specific metadata already declared for a document, such as a group's custom title or description. If the intent is to force every document to use the exact same value, you can overwrite it explicitly, while understanding that group-specific metadata will be replaced.

Imports and APIs may differ across major versions. For springdoc 1.x projects, check the package and dependency version in use; do not blindly copy 2.x imports.

## 4. Which Documents Does `GlobalOpenApiCustomizer` Affect?

Suppose an application has a default document and two groups:

```java
import org.springdoc.core.models.GroupedOpenApi;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ApiGroupsConfiguration {

    @Bean
    GroupedOpenApi publicApi() {
        return GroupedOpenApi.builder()
                .group("public")
                .pathsToMatch("/api/public/**")
                .build();
    }

    @Bean
    GroupedOpenApi adminApi() {
        return GroupedOpenApi.builder()
                .group("admin")
                .pathsToMatch("/api/admin/**")
                .build();
    }
}
```

A `GlobalOpenApiCustomizer` bean can be applied to:

- `/v3/api-docs` — the default document.
- `/v3/api-docs/public` — the `public` group document.
- `/v3/api-docs/admin` — the `admin` group document.

If YAML is needed, check each document's corresponding YAML endpoint according to your springdoc configuration. Paths may change when the application configures `springdoc.api-docs.path`, a context path, or a reverse proxy prefix.

You do not need to register a separate customizer per group to apply the same metadata. If one group needs an exception, combine a group-specific customizer or structure conditions clearly in configuration design.

## 5. Adding Shared Metadata While Preserving Group-Specific Details

A common mistake is a global customizer overwriting every `Info` with a new object. That can lose titles, versions, or descriptions declared specifically for a group.

Example to avoid if each group has its own title:

```java
return openApi -> openApi.setInfo(new Info()
        .title("Application API")
        .version("1.0.0"));
```

The code above replaces the entire existing `Info`. If the `admin` group already has the title `Admin API`, that title will be overwritten.

Instead, only update shared fields:

```java
return openApi -> {
    if (openApi.getInfo() == null) {
        openApi.setInfo(new Info()
                .title("Application API")
                .version("1.0.0"));
    }

    openApi.getInfo().setTermsOfService("https://example.com/terms");

    if (openApi.getInfo().getContact() == null) {
        openApi.getInfo().setContact(new Contact()
                .name("Platform API Team")
                .email("api-team@example.com"));
    }
};
```

This example keeps the current title/version/description while adding terms of service and contact if absent. If every group must share the exact same contact, you can overwrite contact; if groups have distinct contacts, preserve existing values.

## 6. Adding a Shared Server Across All Documents

Some applications want every document to share the same server base URL. You can use `GlobalOpenApiCustomizer` and load the URL from configuration instead of hardcoding environments:

```java
import java.util.ArrayList;

import io.swagger.v3.oas.models.servers.Server;
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;

@Bean
GlobalOpenApiCustomizer commonServer(
        @Value("${app.openapi.server-url:/}") String serverUrl) {
    return openApi -> {
        if (openApi.getServers() == null) {
            openApi.setServers(new ArrayList<>());
        }

        boolean exists = openApi.getServers().stream()
                .anyMatch(server -> serverUrl.equals(server.getUrl()));

        if (!exists) {
            openApi.addServersItem(new Server()
                    .url(serverUrl)
                    .description("API server"));
        }
    };
}
```

Example property:

```yaml
app:
  openapi:
    server-url: https://api.example.com
```

The code checks whether the URL already exists before adding, avoiding duplicate servers if the customizer is invoked again during document generation. If each group is deployed at a different host or base path, do not add a single shared server to all of them. Configure servers per group or per environment appropriately.

For local, staging, and production environments, properties can be supplied via profiles or environment variables. Do not expose sensitive internal URLs in public documentation.

## 7. Adding Shared Extensions

OpenAPI allows vendor extensions whose names start with `x-`. Extensions are commonly used to pass metadata to API gateways, developer portals, or internal tools.

Example of adding audience and document ownership:

```java
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.context.annotation.Bean;

@Bean
GlobalOpenApiCustomizer commonExtensions() {
    return openApi -> {
        openApi.addExtension("x-api-owner", "platform-team");
        openApi.addExtension("x-api-audience", "service-consumers");
    };
}
```

Document-level output may look like:

```yaml
x-api-owner: platform-team
x-api-audience: service-consumers
```

If an extension was already set by another configuration, `addExtension` can replace the value for the same key. Decide clearly whether the customizer is authoritative to override or should only add when absent. Extensions do not carry standard semantics for all clients; only use them when consuming tools understand that convention.

## 8. Declaring a Shared Security Scheme

A security scheme can be declared in `components.securitySchemes` for multiple operations or groups to reference. Example of adding HTTP Bearer JWT to all documents:

```java
import io.swagger.v3.oas.models.Components;
import io.swagger.v3.oas.models.security.SecurityScheme;
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.context.annotation.Bean;

@Bean
GlobalOpenApiCustomizer commonBearerScheme() {
    return openApi -> {
        if (openApi.getComponents() == null) {
            openApi.setComponents(new Components());
        }

        if (openApi.getComponents().getSecuritySchemes() == null
                || !openApi.getComponents().getSecuritySchemes()
                        .containsKey("bearerAuth")) {
            openApi.getComponents().addSecuritySchemes(
                    "bearerAuth",
                    new SecurityScheme()
                            .type(SecurityScheme.Type.HTTP)
                            .scheme("bearer")
                            .bearerFormat("JWT")
            );
        }
    };
}
```

The security scheme appears in `components`, but declaring a scheme alone does not mean every operation requires authentication. To mark a security requirement at the document level, you can add a `SecurityRequirement`; that requirement then applies by default to operations in the document unless an operation is configured otherwise.

Do not add a global security requirement if some endpoints in a group are public. You can declare the shared scheme using a customizer, then attach `@SecurityRequirement(name = "bearerAuth")` to protected operations. Runtime authentication must still be configured with Spring Security; OpenAPI only describes how clients send credentials.

## 9. When to Use a Customizer Specific to One Group?

Not every change should be applied globally. Example:

- The `public` group has a title, contact, and terms intended for customers.
- The `admin` group has its own description and internal server.
- The `partner` group has extensions containing partner codes or specific policies.

In these cases, use `GroupedOpenApi.Builder.addOpenApiCustomizer(...)`:

```java
import io.swagger.v3.oas.models.info.Info;
import org.springdoc.core.models.GroupedOpenApi;
import org.springframework.context.annotation.Bean;

@Bean
GroupedOpenApi partnerApi() {
    return GroupedOpenApi.builder()
            .group("partner")
            .pathsToMatch("/api/partner/**")
            .addOpenApiCustomizer(openApi -> {
                if (openApi.getInfo() == null) {
                    openApi.setInfo(new Info()
                            .title("Partner API")
                            .version("1.0.0"));
                } else {
                    openApi.getInfo().setTitle("Partner API");
                }
                openApi.addExtension("x-api-audience", "partners");
            })
            .build();
}
```

The customizer attached to this builder applies only to the `partner` group. If there is also a `GlobalOpenApiCustomizer` modifying the same `info.title` or extension, the final result depends on the order in which customizers are applied. Avoid having multiple customizers overwrite the same property unless intentional; consolidate rules or inspect the actual output in the dependency version in use.

## 10. Conditions for Safe and Maintainable Customizers

Customizers may be invoked during document generation or refresh. Therefore, logic should be simple, repeatable, and free of unexpected side effects.

### Idempotent Design

An idempotent customizer can run multiple times without causing the output to diverge further. For example, before adding a server or tag, check whether the item already exists. Avoid repeatedly appending the same tag, server, security requirement, or extension.

### Do Not Depend on a Specific Request

An OpenAPI document is typically a shared artifact, not a per-user response. Do not read the current principal, request headers, or tenant of an active request to mutate a global document. If each tenant needs a different document, design a controlled per-tenant publication mechanism rather than relying incidentally on request state.

### Avoid External System Calls Inside Customizers

Do not call databases, remote APIs, or slow configuration services each time a customizer runs. Doing so makes documentation unpredictable, increases latency, and can cause the docs endpoint to fail when dependent services are unavailable. Load needed configuration via Spring configuration and keep customizers as pure as possible.

### Protect Data in Documentation

Do not include tokens, passwords, secret keys, internal hosts, or personal data in descriptions, examples, extensions, or server URLs of public documentation. If a document has internal scope, still protect the docs endpoint with Spring Security.

## 11. Distinguishing Global Customizers from `@OpenAPIDefinition`

`@OpenAPIDefinition` declares OpenAPI metadata via configuration-level annotations, such as title, version, description, servers, tags, or security. `GlobalOpenApiCustomizer` uses Java code to adjust the document model after springdoc builds it.

| Approach | Suitable When |
|---|---|
| `@OpenAPIDefinition` | Metadata is static, simple, and expressible via annotations |
| `OpenAPI` bean | Wanting to initialize the OpenAPI structure in Java from shared configuration |
| `OpenApiCustomizer` | Wanting to modify the default document using Java logic |
| `GlobalOpenApiCustomizer` | Wanting the same logic to modify the default document and all groups |
| Customizer on `GroupedOpenApi` | Wanting to modify a single group specifically |

You do not need to put every piece of metadata into a customizer. If static values can be expressed clearly via annotations or a bean, use the simpler declarative mechanism. Reserve customizers for parts requiring conditions, existence checks, merging, or programmatic transformation.

## 12. Checking That the Customizer Affects Every Group

After registering the bean, inspect the default document and each group. Example:

```text
GET /v3/api-docs
GET /v3/api-docs/public
GET /v3/api-docs/admin
GET /v3/api-docs/partner
```

If YAML is configured, check the corresponding YAML endpoints. For each document, verify:

1. Shared metadata such as contact, terms, or extensions appears.
2. Group-specific metadata such as title or servers is preserved if the customizer is designed additively.
3. Servers, tags, and security schemes are not duplicated.
4. Security requirements apply only to the intended scope.
5. `$ref` references in `components` remain valid after customization.
6. No operations or schemas were unexpectedly removed.
7. Swagger UI loads the right document for each group.

Documents can be downloaded using curl:

```bash
curl -fS http://localhost:8080/v3/api-docs -o default-openapi.json
curl -fS http://localhost:8080/v3/api-docs/public -o public-openapi.json
curl -fS http://localhost:8080/v3/api-docs/admin -o admin-openapi.json
```

Then use a JSON parser or OpenAPI validator to inspect each file. Do not check only the default document; the purpose of `GlobalOpenApiCustomizer` is to ensure changes also appear in the groups.

## 13. Common Errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Metadata only appears at `/v3/api-docs` | Used an `OpenApiCustomizer` bean instead of `GlobalOpenApiCustomizer` | Switch to a global customizer if groups need to be affected |
| One group does not receive changes | Attached customizer to a different group or group is not registered | Check the bean and registration scope |
| Group title changed unexpectedly | Global customizer replaced the entire `Info` or overwrote title | Modify only shared fields or use a group-specific customizer |
| Duplicate servers | Customizer adds a server on every run without checking | Check whether the URL already exists before adding |
| Duplicate tags or security requirements | Non-idempotent append logic | Check existing elements and add only when missing |
| Public endpoint marked as requiring Bearer | Added a global security requirement to the whole document | Declare only the shared scheme and attach requirements to protected operations |
| Document has wrong environment server URL | Hardcoded URL inside customizer | Move URL into appropriate properties/profiles |
| Customizer slows down or breaks docs | Calling database/remote service or side-effecting logic | Use preloaded configuration and keep customizer simple |
| Changes not visible in Swagger UI | UI cached or viewing a different group document | Reload the right URL and inspect JSON/YAML directly |
| `GlobalOpenApiCustomizer` not recognized | Wrong import or incompatible springdoc version | Check dependency and package for the version in use |

## 14. Implementation Workflow

1. Determine whether the change needs to apply to all documents or only one group.
2. If it needs to affect all documents, create a `GlobalOpenApiCustomizer` bean.
3. If only the default document is needed, use an appropriate `OpenApiCustomizer`.
4. If only one group is needed, attach an `OpenApiCustomizer` to `GroupedOpenApi.Builder`.
5. Keep the customizer idempotent, avoid overwriting specific metadata, and do not depend on requests.
6. Start the application and download the default document along with each group.
7. Compare shared metadata, group-specific details, and security components.
8. Run an OpenAPI validator and open Swagger UI to verify.
9. Re-verify when changing springdoc versions or group configurations.

## 15. Design Principles

- Use `GlobalOpenApiCustomizer` when the same change must appear on the default document and all group documents.
- Use an `OpenApiCustomizer` bean for the default document and a builder-attached customizer for a specific group.
- Use `GlobalOperationCustomizer` if you need to modify individual operations across all documents.
- Preserve group-specific metadata when only supplementing shared information.
- Check before adding servers, tags, extensions, or security schemes to avoid duplicates.
- Only add a global security requirement when every operation in the document actually requires authentication.
- Place server URLs and environment values in configuration instead of hardcoding.
- Do not depend on the current request or call external services inside a customizer.
- Inspect the JSON/YAML of every group, not just the default document.
- Protect documentation endpoints with security independently of schema changes made by customizers.

## Conclusion

`GlobalOpenApiCustomizer` is a document-level extension point for changes that need to apply across the default OpenAPI document and group documents generated by springdoc. It is well suited for adding shared metadata, servers, extensions, or security schemes. An `OpenApiCustomizer` bean has a narrower scope; a customizer attached to `GroupedOpenApi.Builder` targets a single group. Choose the right scope, avoid overwriting specific metadata, design idempotent logic, and inspect every JSON/YAML endpoint to ensure all groups receive the intended changes.
