# Specification Source from a Single URL or a List of Documents

Swagger UI needs to know the URL of the OpenAPI document before it can display endpoints, schemas, and examples. For a single API, configuration typically only needs one URL. When a system has multiple versions, multiple API groups, or multiple independent services, Swagger UI can accept a list of URLs so users can choose a document in the top navigation bar.

In Spring Boot, springdoc-openapi provides configuration properties for both cases. The **springdoc.swagger-ui.url** property points to a single OpenAPI document. The **springdoc.swagger-ui.urls** property group declares a list of documents, each with its own display name and URL. Both approaches are based on official Swagger UI configuration; distinguish the specification URL from the Swagger UI config URL and from the API server URLs declared inside the specification.

## 1. Distinguishing URL types

When configuring Swagger UI, several URL types are commonly confused:

| Property | Role | Example |
| --- | --- | --- |
| **springdoc.swagger-ui.path** | Path of the HTML page that opens Swagger UI | **/swagger-ui.html** |
| **springdoc.api-docs.path** | Base path of the OpenAPI specification generated by springdoc | **/v3/api-docs** |
| **springdoc.swagger-ui.configUrl** | URL returning the configuration document for Swagger UI, including OpenAPI sources and UI options | **/v3/api-docs/swagger-config** |
| **springdoc.swagger-ui.url** | URL of a single OpenAPI document for the UI to load | **/v3/api-docs** |
| **springdoc.swagger-ui.urls** | List of multiple OpenAPI documents for users to choose from | **/v3/api-docs/orders**, **/v3/api-docs/admin** |
| **servers.url** in OpenAPI | Base URL of the API used for requests such as Try it out | **https://api.example.com** |

For example, the UI page may live at **https://docs.example.com/swagger-ui.html**, loading the specification from **https://docs.example.com/openapi/store.yaml**, while actual requests are sent to server **https://api.example.com** declared in the specification's servers property.

**configUrl** is not the URL of the OpenAPI file. With default springdoc integration, configUrl is typically **/v3/api-docs/swagger-config**. This endpoint returns the configuration springdoc builds for Swagger UI, including the document URL or group list. Only change configUrl when you want to use a Swagger UI configuration file managed by the application itself.

## 2. Using a single specification URL with springdoc

If the UI only needs to display one document, you can configure the OpenAPI file URL in application.yml:

~~~yaml
springdoc:
  swagger-ui:
    url: https://docs.example.com/openapi/store.yaml
    disable-swagger-default-url: true
~~~

The **url** property can point to:

- A JSON specification generated by springdoc, for example **/v3/api-docs**.
- A YAML specification generated by springdoc, for example **/v3/api-docs.yaml**.
- A static JSON or YAML file served from the application.
- An OpenAPI document hosted on another documentation server or CDN.

If the application already uses springdoc to generate the default document at **/v3/api-docs**, overriding the url property is usually unnecessary. Keeping the default configuration lets springdoc automatically provide the document source matching the application and group settings.

If the application already declares **GroupedOpenApi** or **springdoc.group-configs**, springdoc can place those groups into the **urls** list in swagger-config. When the **urls** configuration exists, Swagger UI prioritizes that list and ignores the single **url**. If you want the UI to show only one external file in an application with multiple groups, declare a **urls** list with a single item or manage swagger-config separately.

Example specifying a static YAML file packaged in Spring Boot:

~~~text
src/
  main/
    resources/
      static/
        openapi/
          store-api.yaml
~~~

With default static resource mapping, the file is accessible at **/openapi/store-api.yaml**. Configuration:

~~~yaml
springdoc:
  swagger-ui:
    url: /openapi/store-api.yaml
    disable-swagger-default-url: true
~~~

Open the file URL directly to confirm the application serves the right content. If the project changes static resource mappings or deploys under a context path, update the public URL accordingly.

## 3. Configuring a single URL in application.properties

Swagger UI properties are supported by springdoc under the **springdoc.swagger-ui** prefix. In application.properties, configure a single specification source as follows:

~~~properties
springdoc.swagger-ui.url=https://docs.example.com/openapi/store.yaml
springdoc.swagger-ui.disable-swagger-default-url=true
~~~

If using the document generated by springdoc:

~~~properties
springdoc.swagger-ui.url=/v3/api-docs
~~~

Do not set **springdoc.swagger-ui.url** to the Swagger UI HTML page URL or the swagger-config endpoint URL. The value must point to OpenAPI specification content that can be fetched and parsed.

## 4. Using the urls list for multiple documents

When multiple specifications need to be offered in the same interface, use the **urls** property. Each item has two fields:

- **name**: unique name displayed in the document selection dropdown.
- **url**: unique URL pointing to the corresponding OpenAPI specification.

Example configuring three documents:

~~~yaml
springdoc:
  swagger-ui:
    urls:
      - name: Store API v1
        url: /v3/api-docs/store-v1
      - name: Store API v2
        url: /v3/api-docs/store-v2
      - name: Admin API
        url: /v3/api-docs/admin
    urls-primary-name: Store API v2
    disable-swagger-default-url: true
~~~

Swagger UI displays a list for users to switch between Store API v1, Store API v2, and Admin API. When the UI first loads, **urls-primary-name** selects the document with a matching name as the default document. The name must match an item in the list exactly; if there is no match, Swagger UI falls back to the first document.

Names and URLs in the list must be unique. Do not reuse the same name for two documents or repeat the same URL under different names without clear intent. Identifying items by name and URL helps the Topbar plugin distinguish entries in the list.

When **urls** is configured and the Topbar plugin is active, the single **url** property is ignored. Therefore, pick one clear configuration source: a single URL for one document, or a urls list for multiple documents.

## 5. Configuring the list in application.properties

You can declare each element of the list by index:

~~~properties
springdoc.swagger-ui.urls[0].name=Store API v1
springdoc.swagger-ui.urls[0].url=/v3/api-docs/store-v1

springdoc.swagger-ui.urls[1].name=Store API v2
springdoc.swagger-ui.urls[1].url=/v3/api-docs/store-v2

springdoc.swagger-ui.urls[2].name=Admin API
springdoc.swagger-ui.urls[2].url=/v3/api-docs/admin

springdoc.swagger-ui.urlsPrimaryName=Store API v2
springdoc.swagger-ui.disable-swagger-default-url=true
~~~

In YAML, Spring Boot supports list syntax with items containing name and url. In properties files, items are indexed starting from 0. Avoid skipping indices in the middle of the list or repeating indices, as that can prevent binding from creating the expected set of entries.

The property name in springdoc's configuration reference is **urlsPrimaryName**. In YAML, you can use the kebab-case form **urls-primary-name** according to Spring Boot's relaxed binding rules.

## 6. Combining GroupedOpenApi with a document list

A Spring Boot application can generate multiple specifications using **GroupedOpenApi** beans. Each group is accessed at its own document URL, defaulting to **/v3/api-docs/{groupName}**. These URLs can be placed into Swagger UI's urls list.

Example group declarations:

~~~java
import org.springdoc.core.models.GroupedOpenApi;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class OpenApiGroupConfiguration {

    @Bean
    public GroupedOpenApi storeV1() {
        return GroupedOpenApi.builder()
            .group("store-v1")
            .pathsToMatch("/api/v1/**")
            .build();
    }

    @Bean
    public GroupedOpenApi storeV2() {
        return GroupedOpenApi.builder()
            .group("store-v2")
            .pathsToMatch("/api/v2/**")
            .build();
    }

    @Bean
    public GroupedOpenApi admin() {
        return GroupedOpenApi.builder()
            .group("admin")
            .pathsToMatch("/api/admin/**")
            .build();
    }
}
~~~

Swagger UI configuration:

~~~yaml
springdoc:
  swagger-ui:
    urls:
      - name: Store API v1
        url: /v3/api-docs/store-v1
      - name: Store API v2
        url: /v3/api-docs/store-v2
      - name: Admin API
        url: /v3/api-docs/admin
    urls-primary-name: Store API v2
~~~

Each group is generated from its own filter, so the UI list reflects the documents provided by the application. There is no need to create static OpenAPI files just to list groups if springdoc already generates them and Swagger UI can reach the corresponding endpoints.

When springdoc automatically populates the group list in swagger-config, you can keep the default configuration so Swagger UI displays those groups. The explicit **urls** example above is for cases where you want direct control over display names, URLs, or mixing application-generated documents with documents from external services. The **urls** list only controls which documents appear in the UI; it does not create groups and does not replace **GroupedOpenApi** path/package filters.

If **springdoc.api-docs.path** is changed, the default **/v3/api-docs** path changes. If the application has **server.servlet.context-path**, public URLs must also include the context path. Check the actual group URLs in the running environment instead of copying default paths mechanically.

## 7. Using specification sources from multiple services

The urls list can also point to different services; not every document has to be generated by the same Spring Boot application:

~~~yaml
springdoc:
  swagger-ui:
    urls:
      - name: Identity API
        url: https://identity.example.com/v3/api-docs
      - name: Billing API
        url: https://billing.example.com/openapi.yaml
      - name: Inventory API
        url: https://inventory.example.com/openapi.json
    urls-primary-name: Identity API
~~~

This is a way to build a unified documentation page for multiple services. Each document remains independent, with its own servers, security schemes, schemas, and version. Swagger UI only provides a UI to pick and view them; it does not merge paths from multiple documents into a single OpenAPI document.

If you want to create a single merged specification from multiple services, a separate merging step or API gateway/documentation aggregator is required. The **urls** configuration only creates a selection list across documents.

## 8. Using configUrl when managing custom Swagger UI configuration

In springdoc, the default value of **springdoc.swagger-ui.configUrl** is **/v3/api-docs/swagger-config**. This is an automatically generated configuration endpoint provided by springdoc. It typically returns the properties Swagger UI needs to load documents and render the interface.

If you want Swagger UI to load a custom configuration file, you can set configUrl:

~~~yaml
springdoc:
  swagger-ui:
    config-url: /config/swagger-ui-config.json
~~~

The configuration file can contain a single URL:

~~~json
{
  "url": "/openapi/store-api.yaml",
  "deepLinking": true,
  "docExpansion": "none"
}
~~~

Or a list of documents:

~~~json
{
  "urls": [
    {
      "name": "Store API v1",
      "url": "/openapi/store-v1.yaml"
    },
    {
      "name": "Store API v2",
      "url": "/openapi/store-v2.yaml"
    }
  ],
  "urls.primaryName": "Store API v2",
  "deepLinking": true
}
~~~

When replacing configUrl with a custom file, the application is responsible for serving that file and maintaining all required Swagger UI properties. Do not confuse this configuration file with an OpenAPI document: config JSON has keys like url, urls, and docExpansion; an OpenAPI file has openapi, info, paths, and components.

If you only want to change the document source, use **springdoc.swagger-ui.url** or **springdoc.swagger-ui.urls**. There is no need to change configUrl just to point to an OpenAPI file.

## 9. Configuring standalone Swagger UI with JavaScript

When deploying Swagger UI standalone without using the springdoc starter to serve the UI, you can configure it directly in JavaScript:

~~~javascript
const ui = SwaggerUIBundle({
  dom_id: "#swagger-ui",
  url: "https://api.example.com/v3/api-docs",
  deepLinking: true
});
~~~

With multiple documents:

~~~javascript
const ui = SwaggerUIBundle({
  dom_id: "#swagger-ui",
  urls: [
    {
      name: "Store API v1",
      url: "https://api.example.com/v3/api-docs/store-v1"
    },
    {
      name: "Store API v2",
      url: "https://api.example.com/v3/api-docs/store-v2"
    }
  ],
  "urls.primaryName": "Store API v2",
  deepLinking: true
});
~~~

In JavaScript configuration, **url** accepts a URL string; **urls** accepts an array of objects containing name and url. When using urls, the single url is ignored. **urls.primaryName** is a key with a dot in the Swagger UI configuration property name, not a nested JavaScript object.

You can pass **spec** instead of a URL if an OpenAPI object is already available in JavaScript. When spec is used, Swagger UI does not parse the url parameter. That fits embedding the specification directly in a frontend app, not loading an external OpenAPI file from a server.

## 10. Distinguishing Swagger UI url from servers in OpenAPI

A common source of errors is confusing the document loading URL with the API request target URL. These two properties serve different purposes:

- **springdoc.swagger-ui.url** or each entry in **urls** specifies where to load the OpenAPI document from.
- **servers** in OpenAPI specifies the base server where Swagger UI sends requests when users click Try it out.

For example, the document is loaded from **https://docs.example.com/openapi/store.yaml**, while the actual API runs at **https://api.example.com/store**:

~~~yaml
openapi: 3.1.0
info:
  title: Store API
  version: 1.0.0
servers:
  - url: https://api.example.com/store
paths:
  /orders:
    get:
      summary: List orders
      responses:
        '200':
          description: List of orders
~~~

In this case, Swagger UI fetches the file from the docs host, while test requests go to the api host. Configure CORS for both fetching the specification and calling the API if they are on different origins.

If servers is not declared in the document, Swagger UI may use a default server according to OpenAPI rules. Check the URL shown in the Try it out request box to confirm the server points to the right environment.

## 11. CORS, authentication, and document access permissions

Swagger UI loads documents via browser requests. If the UI page and the OpenAPI file have different origins, the server hosting the document must allow CORS from Swagger UI's origin.

Example:

- UI: **https://docs.example.com**
- Specification: **https://api.example.com/v3/api-docs**
- Actual API: **https://service.example.com**

In this case, the browser must be allowed to read the specification from **api.example.com**. When Try it out sends requests to **service.example.com**, that API also needs appropriate CORS.

Swagger UI and an API on the same host, port, and protocol typically do not require CORS setup for loading the document. If they are on different origins, configure appropriate allow-origin, allow-methods, and allow-headers; do not carelessly open wildcards when credentials are used.

If the document is protected by login, ensure the browser can access both the config endpoint and the OpenAPI endpoint. If the document resides on another service, clarify the authentication mechanism used by the browser. Do not embed passwords, client secrets, or static bearer tokens in public configuration files or URL query strings.

Adding a document to the urls list does not grant access to that document. OpenAPI endpoints and API endpoints must still be protected by Spring Security, a gateway, or service authentication. Hiding an item from the list also does not replace access control.

## 12. Relative paths, context path, and reverse proxy

Specification paths must resolve properly in the deployment environment. For example, an application with a context path:

~~~properties
server.servlet.context-path=/store
~~~

The default Swagger UI is then accessible under **/store/swagger-ui.html**, and the default OpenAPI document under **/store/v3/api-docs**. If you configure a root-relative absolute path like **/v3/api-docs**, requests may drop the **/store** prefix.

Within the same application, you can use relative URLs under the context path managed by springdoc or provide full public URLs when a reverse proxy is involved. For documents outside the application, absolute HTTPS URLs are usually easier to manage. When a reverse proxy rewrites prefixes, verify the URLs the browser actually requests.

Do not use **localhost** in configurations deployed for external users. In their browsers, localhost points to their own machines, not the Spring Boot server. Likewise, internal hostnames or private IP addresses may only be reachable inside a development network.

## 13. Configuration precedence and query strings

Swagger UI supports configuration from a JavaScript object, a configuration file loaded via configUrl, and page query strings. According to Swagger UI documentation, the general precedence from lowest to highest is:

1. Configuration object passed directly into SwaggerUIBundle.
2. Configuration file loaded via configUrl.
3. Configuration parameters passed in the UI URL's query string.

However, springdoc sets **springdoc.swagger-ui.queryConfigEnabled** to false by default, and the documentation notes this feature has been disabled since v1.6.0 for security reasons. Do not re-enable it just to let users override the document URL via query string without assessing the risk. Manage specification sources via application.yml, application.properties, or controlled configuration files.

If the UI shows the wrong specification source, check the **/v3/api-docs/swagger-config** endpoint to see the configuration springdoc returns, then inspect the specification fetch request in the browser's Network tab. This helps identify whether the issue lies in configUrl, the urls list, the document URL, or access permissions.

## 14. Verifying specification sources

Before publishing Swagger UI, test each source URL independently:

~~~bash
curl -i http://localhost:8080/v3/api-docs
curl -i http://localhost:8080/v3/api-docs/store-v1
curl -i http://localhost:8080/v3/api-docs/admin
~~~

For the YAML file:

~~~bash
curl -i http://localhost:8080/v3/api-docs.yaml
~~~

Confirm:

- The request returns a success status and valid JSON or YAML content.
- The body has valid OpenAPI structure, containing the openapi and info fields.
- Configured URLs point to the right file or group.
- Names in urls do not duplicate each other and urls-primary-name matches a name.
- If the URL is on a different origin, CORS permits the browser to read the document.
- servers in the document point to the actual API to be tested.

Then open Swagger UI, select each document in the list, and verify:

1. Title, version, and operations belong to the selected API.
2. Switching between documents does not display the wrong specification.
3. Try it out uses the right server and path.
4. There are no CORS, 404, 401, or 403 errors when loading config and documents.
5. Documents load properly after deployment under a context path or reverse proxy.

## 15. Common errors and how to handle them

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Swagger UI still shows Petstore or the default document | Desired URL not configured or default URL not disabled | Set url/urls and consider disable-swagger-default-url |
| Configuring url has no effect | urls or spec is declared, causing url to be ignored | Use only a single url or move the source into the urls list |
| Document selection dropdown does not appear | urls is not configured or Topbar plugin is not active | Inspect config JSON and Swagger UI preset/plugin |
| UI opens the wrong default document | urls-primary-name does not match a name or is not bound | Use the exact name in the list and check swagger-config |
| Document returns 404 | URL missing context path, wrong proxy prefix, or wrong group name | Open the URL directly and cross-check with the public path |
| Swagger UI reports a parse error | URL returns HTML, a login page, or a non-OpenAPI file | Inspect status, Content-Type, and body in Network |
| Document from another service fails to load | CORS, authentication, or TLS blocks the browser | Configure CORS, read permissions, and proper certificates |
| Document loads but Try it out calls the wrong host | Specification loading URL confused with servers.url | Fix servers in OpenAPI and inspect the request preview |
| UI works locally but fails when deployed | Config uses localhost or internal hostnames | Use URLs reachable from users' browsers |
| Changing configUrl removes groups from UI | Custom config file lacks the needed urls or url | Add the document list to config JSON or revert to default configUrl |

## 16. Configuration checklist

- [ ] Decide between a single URL or a urls list based on how many documents to display.
- [ ] URL points to OpenAPI JSON/YAML, not the Swagger UI HTML page.
- [ ] When using multiple documents, every name and URL is unique.
- [ ] urls-primary-name matches one name in the list exactly.
- [ ] Distinguished configUrl from the document URL.
- [ ] Checked paths after context path and reverse proxy.
- [ ] CORS permits loading the specification and calling the API across origins.
- [ ] servers in the document point to the appropriate API server.
- [ ] No static secrets or tokens embedded in public URLs/configs.
- [ ] Opened each document in Swagger UI and tested requests in a test environment.
