# Limits on Setting Cookies and Browser-Managed Headers

Swagger UI runs in the browser and sends requests using the browser's networking stack. Consequently, even when OpenAPI describes a header or cookie, Swagger UI's JavaScript still cannot freely inject arbitrary values into every HTTP request. Browsers control certain headers, manage cookies automatically according to security policies, and enforce CORS before letting JavaScript read responses.

This matters when API documentation involves session-cookie authentication, custom headers, or using Try it out to call APIs on a different origin. If you describe a header that browsers forbid scripts from writing, the UI may display an input field yet the actual request still omits that value.

## 1. Distinguishing OpenAPI, Swagger UI, and the browser

Three layers participate in a request from Swagger UI:

1. **OpenAPI** describes the contract: paths, methods, parameters, security schemes, request bodies, and responses.
2. **Swagger UI** reads the contract, renders forms, and builds requests from user input.
3. **The browser** executes requests, applying its cookie jar, Fetch/XHR rules, CORS, and security restrictions.

OpenAPI can declare a syntactically valid header or cookie. That does not mean the browser allows scripts to set that header. When Try it out runs, requests remain subject to the same policies as any regular JavaScript application.

For example, an API may require:

- An Authorization header containing an access token.
- A SESSION cookie issued by the server after login.
- An X-Request-Id header generated by the client for tracing.
- An Origin header sent automatically by the browser so the server can enforce CORS.

These values are managed differently. Authorization and X-Request-Id can usually be set by JavaScript if CORS allows them. Cookies are sent by the browser from its cookie jar based on domain, path, SameSite, Secure, and credentials mode. Origin is determined by the browser; scripts cannot spoof it arbitrarily.

## 2. What are forbidden request headers?

The Fetch Standard defines a set of header names that JavaScript code is prohibited from setting directly. These are commonly called **forbidden request-header names**. Browsers retain control over them because they govern routing, protocol mechanics, origin identity, or security mechanisms.

Common examples:

| Header | Reason JavaScript cannot set it arbitrarily |
| --- | --- |
| Cookie | Browser populates it from the cookie jar per cookie policy |
| Host | Browser determines the host from the request URL |
| Content-Length | Browser calculates it from the request content |
| Origin | Browser determines the sending origin |
| Connection | Belongs to HTTP connection management |
| Keep-Alive | Belongs to connection management |
| Accept-Encoding | Browser and network stack negotiate encoding |
| Access-Control-Request-Method | Browser generates it during CORS preflight |
| Access-Control-Request-Headers | Browser generates it during CORS preflight |
| Sec-* | Reserved for user-agent-managed security info and mechanisms |
| Proxy-* | Belongs to restricted proxy headers |

The full list is defined by the Fetch Standard and can evolve with specifications and browser implementations. Some headers are silently ignored by browsers, while some operations may throw errors. Never design an API contract around a specific browser appearing to accept a restricted header.

**Referer** is also controlled by the browser according to referrer policy. JavaScript can influence the policy via supported options like referrerPolicy, but cannot arbitrarily set Referer like a normal header.

**Authorization** is not a forbidden request header. Scripts can set it, though on cross-origin calls it usually triggers a CORS preflight because it is not a CORS-safelisted request header.

## 3. Cookies are browser-managed data

A cookie is not an arbitrary header that Swagger UI can freely accept as text and attach. The server sends **Set-Cookie** in a response; the browser decides whether to store the cookie. On subsequent requests, the browser automatically builds the **Cookie** header from cookies matching the URL and security policies.

Example server response:

~~~http
HTTP/1.1 200 OK
Set-Cookie: SESSION=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
~~~

The browser can store the SESSION cookie. When a later request satisfies domain, path, Secure, SameSite, and credentials mode requirements, the browser automatically sends:

~~~http
Cookie: SESSION=abc123
~~~

JavaScript is not allowed to set the Cookie header manually with the Fetch API. Do not declare Cookie as a header parameter expecting users to type it into Swagger UI and have the browser transmit that value.

### Key cookie attributes

| Attribute | Effect | Notes |
| --- | --- | --- |
| Domain | Specifies the host or subdomain scope receiving the cookie | Omitting Domain creates a host-only cookie |
| Path | Limits request paths that receive the cookie | Not a security boundary |
| Secure | Sends cookie only over secure channels, typically HTTPS | Essential for sensitive cookies |
| HttpOnly | Prevents JavaScript from reading the cookie via document.cookie | Browser still sends matching cookies automatically |
| SameSite | Controls cookie transmission in cross-site contexts | None requires Secure in modern browsers |
| Max-Age | Maximum lifetime in seconds | Generally preferred over Expires |
| Expires | Expiration timestamp | May be capped by browser policies |

**Domain:** If Domain is omitted, the cookie belongs only to the host that created it. Set Domain only when sharing cookies across subdomains is genuinely needed. Cookies cannot be set for public suffixes like .com.

**Path:** Path determines which request paths carry the cookie. This is a cookie routing mechanism and should not replace access control.

**Secure:** The cookie is sent only over secure connections per browser rules. Production environments should use HTTPS.

**HttpOnly:** JavaScript cannot read this cookie via document.cookie. This attribute reduces the risk of scripts stealing session cookies, while not preventing the browser from sending the cookie automatically on requests.

**SameSite:** Strict restricts sending cookies in cross-site contexts; Lax allows certain safe top-level navigations; None allows sending in cross-site contexts when Secure and other browser policies are met.

**Max-Age/Expires:** Used to define lifetime. Session cookies may be deleted by the browser when the session ends, though the definition of a browser session varies across browsers.

Browsers also enforce policies on cookie count, per-cookie size, total per-site storage, and third-party cookies. Do not assume specific byte limits or counts are identical across browsers. Keep cookies small, storing only session identifiers or minimal data; never stuff full profiles or large tokens into cookies.

For sensitive cookies, consider browser-supported prefixes:

- **__Secure-** requires the cookie to be set from a secure origin with the Secure attribute.
- **__Host-** requires Secure, Path=/, and no Domain attribute; the cookie is thus locked to the exact host that set it.

For instance, naming a cookie **__Host-SESSION** helps prevent another subdomain from setting a cookie with the same name under a broad Domain scope. Verify target browser prefix requirements before adopting them.

## 4. Configuring cookies in Spring Boot

Spring Framework provides ResponseCookie to build Set-Cookie values with explicit attributes:

~~~java
import java.time.Duration;

import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseCookie;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
class SessionController {

    private final SessionService sessionService;

    SessionController(SessionService sessionService) {
        this.sessionService = sessionService;
    }

    @PostMapping("/api/session")
    ResponseEntity<SessionView> createSession() {
        String sessionId = sessionService.createSession();

        ResponseCookie cookie = ResponseCookie
            .from("SESSION", sessionId)
            .httpOnly(true)
            .secure(true)
            .sameSite("Lax")
            .path("/")
            .maxAge(Duration.ofHours(8))
            .build();

        return ResponseEntity.ok()
            .header(HttpHeaders.SET_COOKIE, cookie.toString())
            .body(new SessionView("authenticated"));
    }
}
~~~

The example assumes SessionService creates and stores sessions on the server. In real applications, session IDs must be sufficiently random, unpredictable, time-bounded, and revoked upon logout or expiration. Never use fixed values like abc123 in production.

Illustrative response type:

~~~java
public record SessionView(String status) {}
~~~

If sharing cookies across subdomains is necessary, Domain can be configured after evaluating trust boundaries:

~~~java
ResponseCookie cookie = ResponseCookie
    .from("SESSION", sessionId)
    .domain("example.com")
    .path("/")
    .secure(true)
    .httpOnly(true)
    .sameSite("Lax")
    .build();
~~~

A broader cookie Domain means multiple subdomains receive the cookie. If a less-trusted subdomain is compromised, broad sharing increases impact. Prefer host-only cookies when sharing is unnecessary.

On logout, send a cookie with the same name, zero duration, and the exact Domain/Path used when issued:

~~~java
ResponseCookie expired = ResponseCookie
    .from("SESSION", "")
    .path("/")
    .secure(true)
    .httpOnly(true)
    .sameSite("Lax")
    .maxAge(Duration.ZERO)
    .build();
~~~

If the original cookie was created with a specific Domain, the cookie-clearing response must also use the matching Domain/Path scope. Otherwise, the browser may retain the old cookie.

## 5. Same-origin, same-site, and CORS are three distinct concepts

**Origin** consists of scheme, host, and port. For example, https://docs.example.com and https://api.example.com are two different origins even though they share the same base domain.

**Site** is a concept used by browsers for policies such as SameSite cookies. Two subdomains with the same scheme and registrable domain are generally treated as same-site, even though they remain cross-origin.

**CORS** is the mechanism that permits or denies JavaScript from reading cross-origin responses. CORS is neither user authentication nor a substitute for cookie policies.

| Scenario | Origin | Site | CORS |
| --- | --- | --- | --- |
| Swagger UI and API share scheme/host/port | Same-origin | Same-site | CORS not needed |
| UI at docs.example.com, API at api.example.com, both HTTPS | Cross-origin | Typically same-site | CORS configuration needed |
| UI at docs.example.net, API at api.example.com | Cross-origin | Cross-site | CORS needed; cookies also subject to SameSite and third-party policies |

When Swagger UI and the API have different origins, the browser only sends cookies cross-origin if credentials mode, cookie attributes, and CORS responses all allow it. Proper CORS configuration cannot force the browser to bypass SameSite or third-party cookie blocking policies.

## 6. Sending cookies in cross-origin requests

The Fetch API defines credentials modes:

| Value | Behavior |
| --- | --- |
| omit | Does not send credentials |
| same-origin | Sends credentials for same-origin requests; this is Fetch's default |
| include | Allows sending credentials cross-origin as well, if other policies permit |

Swagger UI has the **withCredentials** option to enable sending credentials in cross-origin requests. Even with this option configured, the browser still checks cookie Domain, Path, Secure, SameSite, third-party cookie permissions, and CORS.

Standalone Swagger UI configuration example:

~~~javascript
SwaggerUIBundle({
    url: "/v3/api-docs",
    dom_id: "#swagger-ui",
    withCredentials: true
});
~~~

When springdoc manages Swagger UI, how configuration is passed depends on the springdoc version and how the application customizes Swagger UI. Check which Swagger UI properties your version supports; do not assume every JavaScript option shares the exact same property name in application.yml.

## 7. Configuring CORS for cookies and custom headers

For cross-origin requests with credentials, the server must return:

- Access-Control-Allow-Origin equal to Swagger UI's exact origin; never use the wildcard *.
- Access-Control-Allow-Credentials: true.
- Access-Control-Allow-Methods containing the methods to invoke.
- Access-Control-Allow-Headers for custom headers clients are allowed to send.
- Vary: Origin when responses vary by allowed origin.

Spring MVC configuration example:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
class CorsConfiguration implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
            .allowedOrigins("https://docs.example.com")
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders(
                "Authorization",
                "Content-Type",
                "X-Request-Id",
                "X-CSRF-TOKEN"
            )
            .allowCredentials(true)
            .maxAge(3600);
    }
}
~~~

Do not add Cookie to allowedHeaders intending to let JavaScript manually set the Cookie header. The browser sends cookies automatically from the cookie jar; Cookie is a forbidden request header and is not treated like a regular custom header.

If the application uses Spring Security, CORS configuration must integrate properly with the security filter chain. CORS OPTIONS preflight requests must be handled before authentication rejects requests lacking a session cookie.

When a request carries Authorization or X-Request-Id, the browser may send an OPTIONS preflight asking whether the server permits that origin, method, and header. If the server fails to reply with the right CORS headers, the main request will not be sent or the response will be unreadable by JavaScript.

## 8. Documenting cookie authentication in OpenAPI

OpenAPI supports an API key security scheme placed in a cookie. This documents that the API uses a specifically named cookie for authentication:

~~~yaml
components:
  securitySchemes:
    sessionCookie:
      type: apiKey
      in: cookie
      name: SESSION

security:
  - sessionCookie: []
~~~

If only certain operations require the session cookie, place the security requirement on the corresponding operations rather than at the document level:

~~~yaml
paths:
  /api/profile:
    get:
      security:
        - sessionCookie: []
      responses:
        '200':
          description: Current user information
~~~

This can be declared with Swagger annotations:

~~~java
import io.swagger.v3.oas.annotations.security.SecurityRequirement;
import io.swagger.v3.oas.annotations.security.SecurityScheme;
import io.swagger.v3.oas.annotations.enums.SecuritySchemeIn;
import io.swagger.v3.oas.annotations.enums.SecuritySchemeType;
import org.springframework.context.annotation.Configuration;

@Configuration
@SecurityScheme(
    name = "sessionCookie",
    type = SecuritySchemeType.APIKEY,
    in = SecuritySchemeIn.COOKIE,
    paramName = "SESSION",
    description = "Session cookie issued by the server after login"
)
class OpenApiCookieSecurityConfiguration {}
~~~

Attach the requirement to a controller or operation:

~~~java
@SecurityRequirement(name = "sessionCookie")
@GetMapping("/api/profile")
ProfileView getProfile() {
    return profileService.getCurrentProfile();
}
~~~

A security scheme describes the authentication contract. It does not create cookies and cannot force the browser to send a cookie if none exists or if it does not match the request URL.

Swagger UI may render an input box for an API key scheme, yet browsers forbid scripts from setting the Cookie header. Therefore, do not rely on typing SESSION into the Authorize dialog to make the browser send a cookie manually. With session cookies, the proper flow is signing in on the same origin or via a browser-handled login flow so the server returns Set-Cookie; the browser then sends the cookie automatically during Try it out calls.

## 9. Why you should not declare Cookie as a header parameter

The following declaration easily causes confusion:

~~~yaml
parameters:
  - name: Cookie
    in: header
    required: true
    schema:
      type: string
~~~

It describes a header that JavaScript is forbidden from setting itself. Swagger UI may render an input field from OpenAPI, but the Fetch API will not allow scripts to construct a Cookie header this way.

If the API authenticates via cookie, use security scheme **type: apiKey**, **in: cookie**, **name: SESSION**. If the API uses a non-authentication business cookie, OpenAPI can describe a Parameter Object with **in: cookie**, while remembering that the browser manages the Cookie header itself. Do not expect Try it out to send an arbitrary cookie value supplied via JavaScript.

Do not declare Host, Origin, Content-Length, Connection, or Sec-* headers as client-controlled input fields. They belong under the browser/network stack's control.

## 10. Documenting Set-Cookie in responses

OpenAPI can document the Set-Cookie response header so readers know which cookie the server issues:

~~~yaml
responses:
  '200':
    description: Login successful
    headers:
      Set-Cookie:
        description: Browser stores the session cookie with the issued attributes
        schema:
          type: string
~~~

This is metadata for contract readers. In practice, a server may send multiple separate Set-Cookie headers. Never fold multiple Set-Cookie headers into one comma-separated string because the Expires attribute can contain commas and each cookie must be processed individually.

Set-Cookie is a forbidden response-header name for JavaScript. Frontends cannot read this value via response.headers.get("Set-Cookie"), even if the server adds Set-Cookie to Access-Control-Expose-Headers. The browser can still process Set-Cookie and store the cookie if the request/response satisfies credentials, CORS, and cookie policies.

This explains why Swagger UI can complete a login and have the browser store the session cookie while the UI's JavaScript code cannot read the Set-Cookie content.

## 11. Automatic cookie transmission introduces CSRF protection requirements

Browsers automatically attach cookies matching the request URL. While convenient for session authentication, this creates CSRF risk: another website could cause the user's browser to send requests to the logged-in API.

Common safeguards:

- Use appropriate SameSite, typically Lax or Strict if the architecture permits.
- For state-changing requests, validate a CSRF token or equivalent anti-CSRF mechanism.
- Validate Origin or Referer per server policy when appropriate.
- Restrict CORS to trusted origins; never enable credentials for all origins.
- Never treat CORS as the sole CSRF defense.
- Use Secure and HttpOnly on sensitive session cookies.

If the API uses cookie sessions, Swagger UI must also send a CSRF token according to the application's mechanism. A header like X-CSRF-TOKEN can be sent by Swagger UI if it has the token and the server allows that header in CORS. CSRF cookies and CSRF headers can work together via double-submit or synchronizer token patterns depending on the framework.

## 12. When a header is needed that browsers forbid setting

Before trying to alter requests, determine whether the header genuinely needs to come from the client.

| Need | Appropriate approach |
| --- | --- |
| Send session cookie | Have the server issue Set-Cookie; the browser sends matching cookies automatically |
| Send Authorization bearer token | Use an HTTP bearer security scheme and allow Authorization in CORS when cross-origin |
| Send correlation ID | Use a custom header such as X-Request-Id; allow it in CORS |
| Set Origin or Host | Let the browser generate them from the URL and request context |
| Set Content-Length | Let the browser compute it from the request body |
| Call an API requiring special internal headers | Consider a controlled backend-for-frontend or server-side integration |

If an intermediary truly must send a header that browsers forbid setting, you can build a backend-for-frontend (BFF) or server-side proxy. The browser calls a BFF endpoint; the BFF authenticates the user, checks permissions, and calls the target API using a server-side HTTP client.

Any proxy must restrict allowed destinations, prevent SSRF, avoid forwarding arbitrary cookies or credentials, validate allowed headers, and log safely. Never build an open proxy that accepts arbitrary URLs from users and dispatches requests to them.

Do not build a proxy merely to bypass a browser security restriction. If an API requires a genuinely client-controlled header, redesign the contract with a valid custom header or move header generation to the server.

## 13. Inspecting with Swagger UI and Developer Tools

When Try it out fails to send expected cookies or headers, inspect the actual request in Developer Tools:

1. Open the Network tab before clicking Execute.
2. Select the OPTIONS request if a preflight occurred, then select the main API request.
3. Inspect Request URL, method, Origin, and sent headers.
4. Check whether the browser sent Cookie; if not, inspect Domain, Path, Secure, SameSite, and credentials mode.
5. Check whether the response includes Set-Cookie and whether the browser stored the cookie under Application/Storage.
6. Check CORS errors in Console and preflight response headers.
7. Check whether the cookie was blocked by third-party cookie policies or browser privacy settings.

You cannot conclude the browser will send Cookie solely from OpenAPI contents or from Swagger UI showing an input box. The Network panel reveals the request the browser actually dispatched.

### Distinguishing curl tests from browser tests

curl allows users to set many headers that in-browser JavaScript cannot set:

~~~bash
curl -i \
  -H "Cookie: SESSION=abc123" \
  -H "X-Request-Id: req-1001" \
  https://api.example.com/api/profile
~~~

This command may succeed while Swagger UI fails to send a manually entered Cookie header. That is not a contradiction: curl is a standalone HTTP client not bound by Fetch forbidden-header restrictions or browser cookie policies.

To test cookies in the browser, run the login flow so the server returns Set-Cookie, verify the browser stores the cookie, then call the API through Swagger UI with the appropriate credentials mode.

## 14. Common errors

**Swagger UI shows a Cookie header input yet requests lack Cookie.** JavaScript cannot manually set the forbidden Cookie header. Use the browser's cookie jar and a server Set-Cookie flow.

**Cookie is issued yet not sent in Try it out.** Check domain, path, Secure, SameSite, expiration, credentials mode, and third-party cookie policies.

**Cross-origin cookie is not saved.** Check that the request uses credentials, the server returns Access-Control-Allow-Credentials: true, and Access-Control-Allow-Origin is a specific origin. Check SameSite=None; Secure if a cross-site cookie is truly required.

**Server returns Access-Control-Allow-Origin as a wildcard.** CORS prohibits wildcard origins on credentialed requests. Return the exact allowed origin.

**Frontend cannot read Set-Cookie.** It is a forbidden response header for JavaScript. The browser can store the cookie even though app code cannot read that header.

**Added Cookie to Access-Control-Allow-Headers yet still cannot send it.** The Cookie header is not a custom request header writable by JavaScript. The browser manages cookies automatically.

**Entered SESSION in Authorize yet API still returns 401.** Swagger UI cannot force the browser to set an arbitrary Cookie header. Confirm the cookie was issued for the right host/path and is sent automatically by the browser.

**curl succeeds while Swagger UI fails.** curl does not enforce browser CORS or forbidden-header restrictions. Inspect the Network panel and browser configuration.

**Cookie has SameSite=None yet is still blocked.** Check Secure, HTTPS, and browser third-party cookie blocking policies. SameSite=None does not guarantee browsers permit all third-party cookies.

**Cookie remains after logout.** Check that the cookie-clearing response uses the exact same name, Domain, and Path as the original cookie, along with Max-Age=0 or an Expires timestamp in the past.

## 15. Checklist for designing APIs and Swagger UI with cookies/headers

- [ ] Distinguished client-supplied headers from headers managed by the browser/network stack.
- [ ] Do not require Swagger UI to set Cookie, Host, Origin, or Content-Length manually.
- [ ] Use apiKey security scheme with in=cookie to document cookie authentication.
- [ ] Have the server issue session cookies via Set-Cookie.
- [ ] Choose Domain, Path, Secure, HttpOnly, SameSite, and lifetime per requirements.
- [ ] Keep cookies small and avoid storing unnecessary sensitive data.
- [ ] For cross-origin calls, configure credentials mode and CORS with an explicit origin.
- [ ] Never use Access-Control-Allow-Origin: * with credentials.
- [ ] Allow genuinely needed custom headers in CORS preflight.
- [ ] Implement CSRF protection for cookie-authenticated APIs.
- [ ] Inspect requests/responses in browser Developer Tools.
- [ ] Do not use curl results to assume the browser sends identical headers.
- [ ] Use a BFF/proxy only when clear architectural needs exist and destinations are strictly controlled.

## 16. Conclusion

Swagger UI constructs requests inside the browser and is therefore bound by Fetch rules, cookie policies, and CORS. OpenAPI can describe cookies and headers, yet cannot grant JavaScript permission to set browser-managed headers. For session cookies, the server must issue Set-Cookie with appropriate attributes so the browser stores and sends them automatically. For cross-origin requests, coordinate credentials mode, CORS, SameSite, and browser privacy policies. When testing, inspect the Network panel to see exactly which headers were sent rather than relying solely on the Try it out form.
