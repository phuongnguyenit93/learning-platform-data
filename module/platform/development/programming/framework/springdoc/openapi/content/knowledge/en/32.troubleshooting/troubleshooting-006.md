# Duplicate `operationId`, Paths, or Handlers for the Same HTTP Method

When multiple controllers declare the same path, the same HTTP method, or the same `operationId`, a Spring Boot application may fail to start, requests may pick an unexpected handler, or the OpenAPI document generated by Springdoc may become invalid. These errors are related yet belong to different layers: Spring MVC registers and selects handlers at runtime, whereas OpenAPI describes each path and HTTP method pair as a single operation.

To fix the issue properly, first identify where the error occurs:

- **Application fails to start**: usually a mapping conflict detected when Spring registers handlers.
- **Application starts but requests are ambiguous**: multiple mappings match a single request and none takes clear precedence.
- **Application starts but `/v3/api-docs` errors or produces an invalid document**: check operations, paths, `operationId`, and customizers.
- **OpenAPI document returns 200 but code generator/linter reports errors**: the document may contain duplicate `operationId` values, equivalent path templates, or structures overwritten during merging.

Do not fix every case simply by renaming Java methods. Find the exact duplicated identifier and the responsible layer.

## 1. Distinguishing Three Types of Conflicts

| Conflict type | Identifier to inspect | Common consequence |
|---|---|---|
| Duplicate handler mapping | Path pattern + HTTP method + mapping conditions | Spring reports `Ambiguous mapping` at startup or when handling requests |
| Duplicate path operation | Path Item and HTTP method under `paths` | Two handlers attempt to occupy the same operation; document may merge, overwrite, or fail to represent both |
| Duplicate `operationId` | `operationId` value across all operations in a document | OpenAPI validators or client generators report non-unique operation identifiers; client method names may collide |

For example, `GET /orders/{id}` and `POST /orders/{id}` do not conflict because their HTTP methods differ. However, `GET /orders/{id}` and `GET /orders/{orderId}` have equivalent path templates under OpenAPI; renaming the path variable does not create a second endpoint.

`operationId` is an independent logical identifier. Two operations on different paths still fail validation if they share the same `operationId`, even though Spring MVC registers and routes both normally.

## 2. How Does Spring MVC Identify Handlers?

Spring MVC uses `@RequestMapping` and composed shortcuts such as `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, and `@PatchMapping` to register handlers. A mapping can evaluate multiple conditions:

- URL path or path pattern.
- HTTP method.
- Query parameters via the `params` attribute.
- Request headers via the `headers` attribute.
- Request media types via `consumes`.
- Producible response media types via `produces`.
- Custom request conditions if extended by the application.

Class-level mappings typically define a shared prefix; method-level mappings add specific paths and conditions. For example:

```java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping("/{id}")
    OrderResponse getById(@PathVariable Long id) {
        return orderService.getById(id);
    }

    @PostMapping
    OrderResponse create(@RequestBody CreateOrderRequest request) {
        return orderService.create(request);
    }
}
```

The complete mappings are `GET /api/orders/{id}` and `POST /api/orders`. They do not conflict because their paths or methods differ.

If two handlers are registered with identical mapping conditions, Spring usually rejects the second registration and reports `Ambiguous mapping`. If their conditions differ, Spring may keep both; when a request arrives, the best-matching mapping is chosen. If a request matches multiple mappings without a clear winner, Spring can report an ambiguous handler at request-handling time.

## 3. `Ambiguous mapping` Errors at Startup

A typical error seen in logs is:

```text
IllegalStateException: Ambiguous mapping. Cannot map ...
There is already ... mapped.
```

The message usually identifies:

- The handler method currently being registered.
- The handler method that already claimed the mapping.
- The overlapping path pattern and HTTP method.

Example error:

```java
@RestController
@RequestMapping("/api/orders")
class PublicOrderController {

    @GetMapping("/{id}")
    OrderResponse getOrder(@PathVariable Long id) {
        return orderService.getById(id);
    }
}

@RestController
@RequestMapping("/api/orders")
class InternalOrderController {

    @GetMapping("/{orderId}")
    OrderResponse findOrder(@PathVariable Long orderId) {
        return internalOrderService.find(orderId);
    }
}
```

Both methods accept `GET /api/orders/{...}`. Variable names `{id}` and `{orderId}` do not create two distinct URL resources. Depending on how Spring parses path patterns and mapping conditions, they may be flagged as duplicate mappings during registration or cause requests to match multiple handlers.

### How to Fix

If both methods actually access the same resource, merge them into one handler and move the distinction into service or authorization logic:

```java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping("/{id}")
    OrderResponse getOrder(@PathVariable Long id) {
        return orderService.getById(id);
    }
}
```

If the two behaviors differ in business semantics, design distinct paths such as `/api/orders/{id}` and `/api/internal/orders/{id}`, and document each operation clearly in OpenAPI.

Do not merely rename the Java method from `getOrder` to `findOrder`; the method name does not change the path, HTTP method, or mapping conditions.

## 4. Distinguishing Exact Duplicate Mappings from Conditional Mappings

Spring MVC permits the same path and HTTP method when mapping conditions distinguish requests.

Example by query parameter:

```java
@GetMapping(value = "/search", params = "status")
List<OrderResponse> searchByStatus(@RequestParam String status) {
    return orderService.searchByStatus(status);
}

@GetMapping(value = "/search", params = "owner")
List<OrderResponse> searchByOwner(@RequestParam String owner) {
    return orderService.searchByOwner(owner);
}
```

Both mappings share `GET /search` but have different `params` conditions. Spring can distinguish requests with `status` from requests with `owner`.

Similarly, mappings can be differentiated by `headers`, `consumes`, or `produces`. However, the OpenAPI `Paths Object` only has one field per path and the `Path Item Object` only has one operation per HTTP method. Hence, two handlers sharing a path and method cannot be represented as two independent operations solely by relying on Spring MVC conditions.

When two mappings are variants of the same action, represent them in one OpenAPI operation:

- Query/header parameters are declared in `parameters`.
- Multiple request media types are represented in `requestBody.content`.
- Multiple response media types are represented in `responses[*].content`.
- Different payload structures can be described using `oneOf` or appropriate schemas.

If the two behaviors cannot be clearly explained within one operation, consider splitting them into two distinct paths. Do not create two operations with the same path/method expecting Swagger UI or client generators to tell them apart via internal Spring conditions.

## 5. Multiple `consumes` or `produces` on the Same Endpoint

A special case occurs when the same endpoint accepts multiple request body types. Spring MVC may use multiple handler methods with the same path and method, differentiated by `consumes`. The Springdoc FAQ notes that overloaded methods in the same class with the same HTTP method and path to support multiple consuming media types can produce a single OpenAPI operation rather than a separate operation per method.

In OpenAPI, a request body can contain multiple media types:

```yaml
paths:
  /api/orders:
    post:
      operationId: createOrder
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
          application/x-www-form-urlencoded:
            schema:
              $ref: '#/components/schemas/CreateOrderForm'
      responses:
        '201':
          description: Order created
```

If two handlers sharing path/method are differentiated by `consumes`, inspect the OpenAPI output to ensure all required media types are described within the same operation. Do not assume each Java method will always become a separate operation.

For `produces`, a single operation can describe multiple response media types inside `content`. If two handlers differ only by `produces`, verify that Springdoc aggregated the content properly and avoid two operation definitions for the same path/method.

## 6. Duplicate `operationId` Across Operations on Different Paths

OpenAPI requires `operationId` to be unique across the entire API document. Client generation tools may use this value as a method name, so non-unique values easily cause duplicate methods or automatically altered names.

Example error:

```yaml
paths:
  /api/orders/{id}:
    get:
      operationId: getById
  /api/customers/{id}:
    get:
      operationId: getById
```

The two paths differ yet share the same `operationId`. Spring MVC is unaffected because mappings still have distinct paths; the bug lies in the OpenAPI contract.

### Setting Explicit operationId Values

With Springdoc, use `@Operation(operationId = "...")`:

```java
@GetMapping("/api/orders/{id}")
@Operation(operationId = "getOrderById", summary = "Get order by ID")
OrderResponse getOrder(@PathVariable Long id) {
    return orderService.getById(id);
}

@GetMapping("/api/customers/{id}")
@Operation(operationId = "getCustomerById", summary = "Get customer by ID")
CustomerResponse getCustomer(@PathVariable Long id) {
    return customerService.getById(id);
}
```

Name operations by resource and action, such as `getOrderById`, `searchOrders`, `createOrder`, `cancelOrder`. Names should remain stable across builds because client generators may derive method names from `operationId`.

Avoid overly generic names like `getById`, `create`, or `update` if the document covers multiple resources. Also never use timestamps or random numbers just to "make them different"; doing so changes generated client names on every generation run.

## 7. Why Springdoc Auto-Generated operationId Values Can Cause Surprises

If `operationId` is omitted, Springdoc can derive it from handler method names and must handle multiple methods sharing the same name. For instance, multiple controllers having a `getById` method can result in identifiers receiving suffixes to avoid collisions.

Automatic suffixes may depend on handler discovery order or change whenever new operations are added. Clients generated from these names may change method names even though API paths did not change.

For public APIs or shared SDKs, set explicit `operationId` values for important operations and check uniqueness after Springdoc generates the document. Do not rely on automatic suffixing algorithms as a stable naming contract.

## 8. Duplicate Path Templates in OpenAPI

OpenAPI considers two path templates with the same structure to be equivalent, even when variable names differ.

Invalid example:

```yaml
paths:
  /api/orders/{id}:
    get:
      operationId: getOrder
  /api/orders/{orderId}:
    get:
      operationId: getOrderById
```

Both paths represent a single placeholder segment after `/api/orders/`. Changing `{id}` to `{orderId}` does not create a new endpoint. OpenAPI specifies that two templated paths with the same hierarchy differing only in variable names must not coexist.

### How to Fix

Choose one canonical path and one path parameter name:

```yaml
paths:
  /api/orders/{orderId}:
    get:
      operationId: getOrderById
      parameters:
        - name: orderId
          in: path
          required: true
          schema:
            type: integer
            format: int64
```

If different behavior is needed, use a literal path or a different URL structure, such as `/api/orders/recent` or `/api/orders/by-reference/{reference}`.

OpenAPI allows concrete paths and templated paths to coexist. For example, `/api/orders/recent` takes precedence when matching concrete URLs before `/api/orders/{orderId}`. However, two equivalent templates like `/{id}` and `/{name}` must not be declared side by side.

## 9. Concrete Paths and Templated Paths Can Overlap

For example:

```yaml
paths:
  /api/orders/{orderId}:
    get:
      operationId: getOrderById
  /api/orders/recent:
    get:
      operationId: getRecentOrders
```

These are two valid paths. When matching URLs, the concrete path `/api/orders/recent` takes precedence before the templated path `/api/orders/{orderId}`.

However, complex patterns such as:

```text
/{entity}/me
/books/{id}
```

can lead to ambiguous resolution for certain URLs. Avoid designing multiple path templates with hard-to-distinguish overlapping match regions. If tooling warns of ambiguous paths, consider adding a fixed prefix like `/api/books/{id}` or `/api/users/me`.

## 10. Duplicate Paths from Combining Class-Level and Method-Level Mappings

The final path does not live solely in the method annotation. Spring combines class-level and method-level paths.

For example:

```java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping("/{id}")
    OrderResponse get(@PathVariable Long id) {
        return orderService.getById(id);
    }
}
```

The full path is `/api/orders/{id}`. If another class also has `@RequestMapping("/api/orders")` and a `@GetMapping("/{orderId}")` method, the two mappings can overlap.

When diagnosing, always record the combined path rather than looking only at the path in the method annotation. Check meta-annotations, controller interfaces, inherited methods, and custom composed annotations carrying `@RequestMapping`.

Spring Framework also advises against placing multiple `@RequestMapping`-family annotations on the same element expecting them to combine. If multiple mapping annotations are detected on the same class or method, only the first mapping is used and the framework logs a warning. Use one clear mapping annotation per element.

## 11. Do Not Use `@Hidden` to Fix Runtime Handler Conflicts

`@Hidden` hides an operation or controller from the OpenAPI document. It does not remove `RequestMappingInfo`, does not alter the Spring MVC handler registry, and does not resolve two handlers matching the same request.

For example:

```java
@Hidden
@RestController
@RequestMapping("/api/internal/orders")
class InternalOrderController {
    // ...
}
```

This only controls documentation. If the controller still has a mapping conflicting with another controller, the application may still fail to start or requests may remain ambiguous.

Likewise, `springdoc.paths-to-match`, `packages-to-scan`, or `GroupedOpenApi` filter documentation scope; they do not alter Spring MVC handler mappings. Use them only when the goal is splitting documentation, never as a fix for routing errors.

## 12. Conflicts Caused by `OpenApiCustomizer` or Document Merging

Not every duplicate path originates from controllers. An `OpenApiCustomizer`, plugin, or script merging multiple OpenAPI files may add a Path Item that already exists.

Example logic to avoid:

```java
// Pseudocode: overwrite an existing Path Item without checking
openAPI.getPaths().put("/api/orders/{id}", generatedPathItem);
```

`Map.put` can replace the previous Path Item. As a result, the old operation vanishes without any routing error in Spring MVC.

When a customizer adds paths:

- Check whether the path key already exists.
- If the path matches but HTTP methods differ, merge the method into the existing Path Item.
- If both path and method match, explicitly decide which operation is authoritative; never overwrite silently.
- Verify `operationId` values after merging.
- Do not merge documents from multiple sources simply by copying the `paths` map without validation.

`OperationCustomizer` mainly customizes an operation already generated from a handler. `OpenApiCustomizer` can affect the entire OpenAPI model, including `paths`; inspect customizers that operate on the same paths or operations.

## 13. Do Multiple `GroupedOpenApi` Beans Necessarily Mean Duplicates?

No. Each group generates its own OpenAPI document, for example:

```text
/v3/api-docs/public
/v3/api-docs/admin
```

An operation can appear in both documents if the two groups' filters intersect. That is not automatically an error, because `operationId` uniqueness is checked within the scope of each document.

However, if a single group contains two different handlers with the same path and method or contains two operations with the same `operationId`, that group's document still has an issue. Inspect each group URL individually, not just the default document.

## 14. Inspecting the List of Registered Handlers

When the application can start, Actuator mappings can be used to view registered endpoints:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,mappings
```

Access in a development environment:

```bash
curl http://localhost:8080/actuator/mappings
```

The `mappings` endpoint can reveal internal paths and handler details. Only expose it in controlled environments or protect it with Spring Security; never expose it publicly in production just for debugging.

Another option is injecting `RequestMappingHandlerMapping` in a test and inspecting `getHandlerMethods()`:

```java
@SpringBootTest
class HandlerMappingInventoryTest {

    @Autowired
    RequestMappingHandlerMapping handlerMapping;

    @Test
    void printsRegisteredMappings() {
        handlerMapping.getHandlerMethods().forEach((mapping, handler) ->
            System.out.println(mapping + " -> " + handler)
        );
    }
}
```

This inventory test can only run when the `ApplicationContext` starts. If an ambiguous mapping error prevents the context from starting, read the two handlers from the exception stack trace or temporarily isolate the suspected controller so the context can start for inspection.

## 15. Inspecting the OpenAPI Document with `jq`

After the application starts, save the document:

```bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs \
  --output openapi.json
```

List operations with path, method, and `operationId`:

```bash
jq -r '
  .paths | to_entries[] as $path
  | $path.value | to_entries[]
  | select(.key == "get" or .key == "put" or .key == "post" or .key == "delete" or .key == "options" or .key == "head" or .key == "patch" or .key == "trace")
  | [(.value.operationId // "<missing>"), $path.key, .key]
  | @tsv
' openapi.json
```

Find `operationId` values appearing multiple times:

```bash
jq -r '
  .paths[] | to_entries[]
  | select(.key == "get" or .key == "put" or .key == "post" or .key == "delete" or .key == "options" or .key == "head" or .key == "patch" or .key == "trace")
  | .value.operationId // empty
' openapi.json | sort | uniq -d
```

If the second command prints any values, the document has duplicate `operationId` entries in the parsed content. If it prints nothing, that only shows no duplicate `operationId` was found in the JSON file read; it does not prove path templates, YAML duplicate keys, or all OpenAPI rules are valid.

Inspect a specific path:

```bash
jq '.paths["/api/orders/{id}"]' openapi.json
```

If a path or method disappears, compare output against controllers and customizers. JSON parsers usually keep only one value when input has duplicate object keys, so check raw YAML/JSON with a linter supporting duplicate-key detection when suspecting overwrites.

## 16. Running an OpenAPI Linter and Validator

Redocly CLI can be used to lint the document:

```bash
npx @redocly/cli lint openapi.yaml
```

The linter can detect duplicate `operationId` values, path structure issues, parameter issues, or other contract problems depending on the active ruleset. For consistent CI results, pin the CLI version and ruleset configuration in the repository.

If using Swagger Parser or another validator, ensure the parser supports the exact `openapi` version in the document. An older parser may report errors or ignore new constructs; do not downgrade the `openapi` version just to silence a validator.

Linters do not replace Spring MVC runtime checks. A valid document can still mismatch actual mappings; conversely, the application may route requests fine while the document violates uniqueness rules.

## 17. Ordered Diagnostic Procedure

Proceed step by step to find the right failing layer:

1. **Read the first exception**: determine whether the error occurred during ApplicationContext creation, request handling, or calling `/v3/api-docs`.
2. **If a startup error**: extract both handler methods and full mappings from the `Ambiguous mapping` message.
3. **If runtime ambiguity**: record the exact request, including method, path, query, headers, and content type; check which mappings match together.
4. **If the app runs but OpenAPI is wrong**: download raw JSON/YAML and check `paths`, HTTP methods, `operationId`, and parser diagnostics.
5. **Inspect combined paths**: combine class-level and method-level mappings; normalize path templates and variable names.
6. **Inspect mapping conditions**: `params`, `headers`, `consumes`, `produces`, and custom conditions.
7. **Inspect extension points**: `OperationCustomizer`, `OpenApiCustomizer`, `GroupedOpenApi`, and merge scripts.
8. **Fix the mapping source or metadata**: merge handlers, change paths, or set unique operationIds according to the root cause.
9. **Restart and verify runtime**: requests to each endpoint must select the intended handler.
10. **Reload every OpenAPI group and run lint**: ensure no duplicate paths/operationIds remain in any document.

## 18. Symptoms and Quick Fixes Table

| Symptom | Common cause | How to resolve |
|---|---|---|
| App stops at startup with `Ambiguous mapping` | Two handlers have identical mapping conditions | Merge handlers or change path/HTTP method/meaningful conditions |
| App runs but a request reports ambiguous handler | One request matches multiple conditional mappings | Check query/header/content type; make conditions distinct or merge handlers |
| `/v3/api-docs` has two path templates differing only in variable name | `/resource/{id}` and `/resource/{name}` | Choose one canonical path |
| Linter reports duplicate `operationId` | Multiple operations share the same identifier | Set unique `@Operation(operationId=...)` |
| Client generator creates method names with unexpected suffixes | Springdoc had to disambiguate auto-generated operationIds | Set explicit and stable operationIds |
| Two methods with same path/method differing by `consumes` yield one operation | Springdoc aggregates media type variants into one operation | Check `requestBody.content` includes all media types |
| Operation disappears after customizer | `OpenApiCustomizer` overwrites Path Item in map | Merge with checks; avoid blind overwriting `put` |
| `@Hidden` does not resolve startup error | Annotation only hides from documentation | Fix the actual Spring MVC mapping |
| Only one group has duplicates | Group filters pull multiple handlers into the same document | Check group filters and each group's output |
| JSON parser reports no duplicate key while source file repeats | Parser kept one key and discarded the other | Use a YAML/JSON linter with duplicate-key detection and inspect raw source |

## 19. Example Redesigning an API with Two Distinct Behaviors

Suppose two features originally both used `GET /api/orders/{id}`: one fetches an order by ID, while the other looks up an order by reference code. If both have distinct semantics, you should not leave two handlers on the same path hoping variable names distinguish them.

Clearer design:

```java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping("/{id}")
    @Operation(operationId = "getOrderById")
    OrderResponse getById(@PathVariable Long id) {
        return orderService.getById(id);
    }

    @GetMapping("/by-reference/{reference}")
    @Operation(operationId = "getOrderByReference")
    OrderResponse getByReference(@PathVariable String reference) {
        return orderService.getByReference(reference);
    }
}
```

Now both the paths and `operationId` values differ. API consumers can understand exactly how to look up each resource; Spring MVC does not have to guess a handler based on two equivalent templates.

## 20. Preventing Regressions in CI

To catch uniqueness errors before deployment:

- Generate the OpenAPI document from the proper build profile.
- Parse the document using a version-compatible parser.
- Lint `operationId`, path templates, parameters, and responses.
- Compare the new document against a baseline to catch breaking changes.
- Check every published `GroupedOpenApi`.
- Maintain integration tests confirming critical endpoints map to the right handlers.
- Do not merge OpenAPI files from multiple modules without checking duplicate paths/methods/operationIds.
- Set explicit `operationId` values for public APIs or APIs used for SDK generation.

Example minimal CI job:

```bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs \
  --output target/openapi.json

npx @redocly/cli lint target/openapi.json
```

In actual CI, pin Redocly CLI and parser versions; store the OpenAPI artifact after linting passes. If a service has multiple groups, fetch and lint every group URL rather than linting only the default document.

## 21. Checklist for Resolving Duplicate Mappings and Operations

- [ ] Determined whether the error occurs at Spring startup, request routing, or OpenAPI generation.
- [ ] Recorded the complete path after combining class-level and method-level mappings.
- [ ] Checked HTTP method and `params`, `headers`, `consumes`, `produces` conditions.
- [ ] No two handlers share identical mapping conditions unless distinguishable.
- [ ] No two OpenAPI path templates share the same hierarchy differing only in variable names.
- [ ] Each path/method is represented by a single OpenAPI operation.
- [ ] Media type variants are described inside `requestBody.content` or response `content`.
- [ ] `operationId` is unique within each OpenAPI document.
- [ ] Public `operationId` values are explicitly set and stable.
- [ ] `@Hidden` or path filters are not misused to mask routing bugs.
- [ ] `OpenApiCustomizer` does not unintentionally overwrite Path Items or operations.
- [ ] Inspected every document group after generation.
- [ ] Ran parser/linter and checked raw JSON/YAML.
- [ ] Ran request integration tests to confirm actual handlers.

Duplicate handlers, duplicate paths, and duplicate `operationId` values are three distinct errors. Spring MVC needs clear mappings to select one handler per request; OpenAPI allows only one operation per path and HTTP method; `operationId` must be unique throughout the entire document. Start from the exception or OpenAPI output to identify the failing layer, then merge handlers or design appropriate paths, set explicit operationIds, and re-run runtime tests alongside the OpenAPI linter. `@Hidden` only alters documentation, not actual mappings.
