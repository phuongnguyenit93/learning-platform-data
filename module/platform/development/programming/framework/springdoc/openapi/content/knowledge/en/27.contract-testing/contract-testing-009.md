# Contract Testing Generated Specs with WebTestClient in Reactive Applications

In a Spring WebFlux application, springdoc-openapi generates the OpenAPI document from controllers or functional endpoints, DTOs, Spring mappings, and Swagger annotations. You can use `WebTestClient` to call the documentation endpoint right inside integration tests, parse the generated JSON/YAML, and verify that operations, parameters, request bodies, responses, and schemas match the expected contract.

A contract test should examine two related aspects: how the OpenAPI document describes the API and how live HTTP endpoints respond. `WebTestClient` supports sending HTTP requests to both a running WebFlux server and a mocked web context. However, it does not automatically validate payloads against every OpenAPI constraint; tests must check key sections or pair with an OpenAPI/JSON Schema validator.

## 1. Goals of Contract Testing

The OpenAPI document is the contract used by clients, code generators, testers, and developer portals. If a controller changes without properly updating the documentation, clients may be generated from the wrong schema. Conversely, documentation might advertise a `201` response while the endpoint actually returns `200`.

In a Reactive application, testing with `WebTestClient` can verify:

- The `/v3/api-docs` endpoint returns valid OpenAPI JSON.
- The `openapi` field carries the expected version.
- Operations appear at the right paths and HTTP methods.
- `operationId` values are stable and accurately named.
- Path/query/header parameters have the right names, locations, types, and `required` flags.
- Request bodies have the right media types and schemas.
- Responses have the right status codes, content types, and schemas.
- Referenced schemas exist under `components.schemas`.
- Group documents contain only the intended operations.
- Real requests sent to the API behave consistently with the published contract.

Split tests into two groups:

| Test Group | What to Confirm |
|---|---|
| OpenAPI document tests | Metadata and schemas generated by springdoc are accurate |
| Runtime API tests | Live HTTP endpoints return expected statuses, headers, and bodies |

Both groups complement each other. Checking only the document does not prove controllers execute properly; calling only controllers does not prove the OpenAPI document describes them accurately.

## 2. Preparing Dependencies for WebFlux and springdoc

The application needs Spring WebFlux and the matching springdoc starter. If only JSON/YAML endpoints are needed, use the API starter; if Swagger UI is needed, use the UI starter.

Maven example for an application with Swagger UI:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webflux</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-validation</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springdoc</groupId>
        <artifactId>springdoc-openapi-starter-webflux-ui</artifactId>
        <version>SPRINGDOC_VERSION</version>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>

    <dependency>
        <groupId>org.springframework.security</groupId>
        <artifactId>spring-security-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
~~~

Replace `SPRINGDOC_VERSION` with a springdoc version compatible with your project's Spring Boot release. For applications that do not need the UI, replace `springdoc-openapi-starter-webflux-ui` with `springdoc-openapi-starter-webflux-api`.

`spring-boot-starter-test` provides JUnit Jupiter, AssertJ, and Spring Test. Spring Boot auto-configures `WebTestClient` for WebFlux tests when appropriate test annotations are used.

If documentation endpoints are protected by Spring Security and tests need mock users/tokens, include `spring-security-test` in test scope.

## 3. Sample Reactive API for Testing

Assume the application provides endpoints to create, list, and retrieve orders. Place each record DTO in its own Java file. DTOs use clear Java types so springdoc can generate schemas cleanly:

~~~java
import io.swagger.v3.oas.annotations.media.Schema;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Positive;
import java.math.BigDecimal;
import java.util.UUID;

@Schema(name = "CreateOrderRequest", description = "Order creation payload")
public record CreateOrderRequest(
        @Schema(description = "Customer code", example = "CUS-100")
        @NotBlank
        String customerCode,

        @Schema(description = "Total order amount", example = "125.50", minimum = "0.01")
        @Positive
        BigDecimal amount
) {}

@Schema(name = "OrderResponse", description = "Order details")
public record OrderResponse(
        @Schema(description = "Order ID", format = "uuid")
        UUID id,

        @Schema(description = "Customer code", example = "CUS-100")
        String customerCode,

        @Schema(description = "Total amount", example = "125.50")
        BigDecimal amount,

        @Schema(description = "Order status", example = "CREATED")
        String state
) {}
~~~

Controller returning reactive types:

~~~java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.media.Content;
import io.swagger.v3.oas.annotations.media.Schema;
import io.swagger.v3.oas.annotations.responses.ApiResponse;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import java.util.UUID;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@RestController
@RequestMapping("/api/orders")
@Tag(name = "Orders")
class OrderController {

    @PostMapping
    @Operation(operationId = "createOrder", summary = "Create order")
    @ApiResponse(
            responseCode = "201",
            description = "Order created",
            content = @Content(
                    mediaType = MediaType.APPLICATION_JSON_VALUE,
                    schema = @Schema(implementation = OrderResponse.class)))
    Mono<ResponseEntity<OrderResponse>> create(
            @Valid @RequestBody Mono<CreateOrderRequest> request) {
        return request.map(body -> new OrderResponse(
                        UUID.randomUUID(),
                        body.customerCode(),
                        body.amount(),
                        "CREATED"))
                .map(response -> ResponseEntity
                        .status(HttpStatus.CREATED)
                        .body(response));
    }

    @GetMapping
    @Operation(operationId = "listOrders", summary = "List orders")
    Flux<OrderResponse> list() {
        return Flux.just(new OrderResponse(
                UUID.fromString("a8f5f167-f44f-4c5a-9d9c-6f3f3a2b1c00"),
                "CUS-100",
                new java.math.BigDecimal("125.50"),
                "CREATED"));
    }

    @GetMapping("/{id}")
    @Operation(operationId = "getOrderById", summary = "Get order by ID")
    Mono<OrderResponse> getById(@PathVariable UUID id) {
        return Mono.just(new OrderResponse(
                id,
                "CUS-100",
                new java.math.BigDecimal("125.50"),
                "CREATED"));
    }

    @GetMapping("/internal")
    @Operation(operationId = "getInternalOrder", summary = "Get internal order details")
    Mono<OrderResponse> getInternalOrder() {
        return Mono.just(new OrderResponse(
                UUID.randomUUID(),
                "CUS-100",
                new java.math.BigDecimal("125.50"),
                "CREATED"));
    }
}
~~~

This example uses `Mono` to illustrate how Spring WebFlux reads request bodies asynchronously and returns reactive responses. In real applications, handlers typically invoke services and repositories instead of constructing dummy data inline.

Springdoc unwraps reactive wrappers such as `Mono<T>` to document the payload type `T`. For collections, `Flux<T>` and response writing behavior determine what appears on the HTTP wire; inspect the generated schema rather than guessing solely from reactive type names.

## 4. Initializing Integration Tests with WebTestClient

To test the OpenAPI endpoint registered across the full application, use `@SpringBootTest` with a random server port:

~~~java
import com.fasterxml.jackson.databind.JsonNode;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.reactive.AutoConfigureWebTestClient;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.reactive.server.WebTestClient;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureWebTestClient
class OpenApiContractTest {

    @Autowired
    WebTestClient webTestClient;

    // Tests go here.
}
~~~

`RANDOM_PORT` boots a real server on an available port. Spring Boot configures `WebTestClient` to target that server. This tests the web stack, filter chain, security configuration, and springdoc auto-configuration inside a near-production application context.

If tests require databases or external services, use a test profile, test database, or suitable mock beans. Never let integration tests depend on production data or live production services.

## 5. Calling the OpenAPI JSON Endpoint

The first test verifies that the documentation endpoint returns JSON:

~~~java
@Test
void openApiDocumentIsAvailable() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectHeader()
                .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
            .expectBody(JsonNode.class)
            .value(document -> {
                assertThat(document.path("openapi").asText())
                        .startsWith("3.");
                assertThat(document.path("info").path("title").asText())
                        .isNotBlank();
                assertThat(document.path("paths").isObject()).isTrue();
            });
}
~~~

`expectStatus().isOk()` checks HTTP status. `contentTypeCompatibleWith` confirms a JSON-compatible media type. `expectBody(JsonNode.class)` uses Jackson's decoder to parse the document into a JSON tree; AssertJ then checks the required fields.

Do not check merely that the response is non-empty. An HTML login page or proxy error can be non-empty without being an OpenAPI document. Checking media type and parsing JSON catches such mistakes.

## 6. Verifying Paths and `operationId`

In OpenAPI JSON, paths are keys under `paths`; HTTP methods are child keys. Nodes can be accessed via JSON Pointer:

~~~java
@Test
void createOrderOperationHasExpectedIdentity() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                JsonNode operation = document.at(
                        "/paths/~1api~1orders/post");

                assertThat(operation.isMissingNode()).isFalse();
                assertThat(operation.path("operationId").asText())
                        .isEqualTo("createOrder");
                assertThat(operation.path("summary").asText())
                        .isEqualTo("Create order");
            });
}
~~~

In JSON Pointer, `/` inside a key escapes to `~1`, so `/api/orders` becomes `~1api~1orders`. `~` escapes to `~0`. This is standard JSON Pointer syntax, not a springdoc-specific rule.

Verify `operationId` because client generators often use it for method names. Changing `operationId` unintentionally alters the generated SDK's public API surface even when HTTP URLs remain identical.

## 7. Verifying Request Bodies and Schemas

The create-order operation must declare a request body with JSON media type and its corresponding schema:

~~~java
@Test
void createOrderOperationDocumentsRequestBody() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                JsonNode operation = document.at(
                        "/paths/~1api~1orders/post");
                JsonNode requestBody = operation.path("requestBody");
                JsonNode schema = requestBody.at(
                        "/content/application~1json/schema");

                assertThat(requestBody.path("required").asBoolean()).isTrue();
                assertThat(schema.isMissingNode()).isFalse();

                JsonNode requestSchema = document.at(
                        "/components/schemas/CreateOrderRequest");
                assertThat(requestSchema.path("properties")
                        .has("customerCode")).isTrue();
                assertThat(requestSchema.path("properties")
                        .has("amount")).isTrue();
            });
}
~~~

JSON Pointer escapes `/` in media type `application/json` to `application~1json`. If schemas are inlined or component schemas carry different names, adjust assertion paths to match the generated document.

Tests can also assert `requestBody.required`, `content.application/json.schema`, field types/formats, `required` arrays, and constraints such as `minLength`, `minimum`, or `maxLength` when they form key parts of the contract.

Avoid rigidly asserting every schema attribute that is not part of the essential contract. A description tweak or metadata reordering should not break tests when API behavior stays unchanged.

## 8. Verifying Response Statuses and Response Schemas

The `POST` operation in the example returns HTTP `201`. Verify the declared response:

~~~java
@Test
void createOrderDocumentsCreatedResponse() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                JsonNode response = document.at(
                        "/paths/~1api~1orders/post/responses/201");
                JsonNode schema = response.at(
                        "/content/application~1json/schema");

                assertThat(response.isMissingNode()).isFalse();
                assertThat(response.path("description").asText())
                        .isNotBlank();
                assertThat(schema.isMissingNode()).isFalse();
            });
}
~~~

When a controller returns `Mono<ResponseEntity<OrderResponse>>`, springdoc can infer the response body from the generic type and default/annotated status. However, status codes selected dynamically inside handlers may not be fully inferred. When exact contracts matter, declare `@ApiResponse` or `@ApiResponses` explicitly.

Do not check only for a `200` response if endpoints actually return `201`, `204`, `400`, `404`, or `409` across different branches.

## 9. Verifying Path Parameters

For `GET /api/orders/{id}`, OpenAPI must declare a path parameter named `id` with location `path` and `required: true`.

~~~java
@Test
void getOrderDocumentsRequiredUuidPathParameter() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                JsonNode parameters = document.at(
                        "/paths/~1api~1orders~1{id}/get/parameters");

                boolean idFound = false;
                for (JsonNode parameter : parameters) {
                    if ("id".equals(parameter.path("name").asText())) {
                        idFound = true;
                        assertThat(parameter.path("in").asText())
                                .isEqualTo("path");
                        assertThat(parameter.path("required").asBoolean())
                                .isTrue();
                        assertThat(parameter.path("schema").path("format").asText())
                                .isEqualTo("uuid");
                    }
                }
                assertThat(idFound).isTrue();
            });
}
~~~

Path parameters are always required in OpenAPI. If a parameter is missing or its name disagrees with `{id}`, check Spring mappings, `@PathVariable` or `@Parameter`, and the generated document.

## 10. Verifying Component Schemas

Schemas reused across operations typically reside in `components.schemas`. Verify the model exposes all critical properties:

~~~java
@Test
void orderResponseSchemaContainsContractFields() {
    webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                JsonNode schema = document.at(
                        "/components/schemas/OrderResponse");
                JsonNode properties = schema.path("properties");

                assertThat(properties.has("id")).isTrue();
                assertThat(properties.has("customerCode")).isTrue();
                assertThat(properties.has("amount")).isTrue();
                assertThat(properties.has("state")).isTrue();
                assertThat(properties.path("id").path("format").asText())
                        .isEqualTo("uuid");
            });
}
~~~

If a schema is inlined, there will be no `$ref` to `components.schemas`. When using `@Schema(name = ...)`, custom naming strategies, or complex generic models, component names may differ. Inspect the output once to determine the actual structure, then write assertions against your desired contract.

## 11. Testing the Runtime API with the Same WebTestClient

After verifying the OpenAPI document, invoke business endpoints to test real runtime behavior:

~~~java
@Test
void createOrderReturnsDocumentedStatusAndBody() {
    webTestClient.post()
            .uri("/api/orders")
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue("""
                    {
                      "customerCode": "CUS-100",
                      "amount": 125.50
                    }
                    """)
            .exchange()
            .expectStatus().isCreated()
            .expectHeader()
                .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
            .expectBody()
            .jsonPath("$.customerCode").isEqualTo("CUS-100")
            .jsonPath("$.amount").isEqualTo(125.50)
            .jsonPath("$.state").isEqualTo("CREATED");
}
~~~

This test verifies the JSON request is handled and the runtime response carries the expected status and body. It does not automatically prove every response field conforms to the schema; combine with schema assertions or a validator for deeper checking.

Testing `GET`:

~~~java
@Test
void getOrderReturnsTheRequestedIdentifier() {
    String id = "a8f5f167-f44f-4c5a-9d9c-6f3f3a2b1c00";

    webTestClient.get()
            .uri("/api/orders/{id}", id)
            .exchange()
            .expectStatus().isOk()
            .expectHeader()
                .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
            .expectBody()
            .jsonPath("$.id").isEqualTo(id)
            .jsonPath("$.state").isEqualTo("CREATED");
}
~~~

In database-backed applications, seed deterministic test data before calling the API and clean up afterward. Never depend on test execution order or leftover state from prior tests.

## 12. Verifying the YAML Endpoint

If pipelines or consumers rely on YAML, test the YAML endpoint separately:

~~~java
@Test
void openApiYamlDocumentIsAvailable() {
    webTestClient.get()
            .uri("/v3/api-docs.yaml")
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class)
            .value(yaml -> {
                assertThat(yaml).contains("openapi:");
                assertThat(yaml).contains("paths:");
                assertThat(yaml).contains("/api/orders");
            });
}
~~~

This is a basic smoke check for the YAML response. Substring assertions confirm the endpoint returns expected-looking text, yet they are neither a YAML parser nor a substitute for an OpenAPI validator. To guarantee valid syntax and schemas, parse the YAML with an appropriate YAML library and run a validator.

## 13. Verifying Documents per Group

When an application registers multiple `GroupedOpenApi` beans, test group endpoints rather than checking only the default document:

Example defining a `public` group that excludes an internal route:

~~~java
import org.springdoc.core.models.GroupedOpenApi;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class OpenApiGroupConfiguration {

    @Bean
    GroupedOpenApi publicApi() {
        return GroupedOpenApi.builder()
                .group("public")
                .pathsToMatch("/api/**")
                .pathsToExclude("/api/orders/internal")
                .build();
    }
}
~~~

~~~java
@Test
void publicGroupContainsOnlyPublicOperations() {
    webTestClient.get()
            .uri("/v3/api-docs/public")
            .exchange()
            .expectStatus().isOk()
            .expectBody(JsonNode.class)
            .value(document -> {
                assertThat(document.at(
                        "/paths/~1api~1orders/get").isMissingNode()).isFalse();
                assertThat(document.at(
                        "/paths/~1api~1orders~1internal/get").isMissingNode()).isTrue();
            });
}
~~~

The default group path is typically `/v3/api-docs/{group}`. If the application overrides `springdoc.api-docs.path`, use the configured path. Group YAML uses its own endpoint; verify exact URLs for your springdoc version.

Group tests catch unintended changes to `pathsToMatch`, `pathsToExclude`, package filters, or group setup. Remember that hiding an operation from the public group does not replace authorization on the runtime endpoint.

## 14. Testing When the OpenAPI Endpoint Is Protected

If Spring Security restricts documentation to a specific authority, tests must supply an appropriate principal. With reactive security and `spring-security-test`, use `mockUser`:

~~~java
import static org.springframework.security.test.web.reactive.server.SecurityMockServerConfigurers.mockUser;

@Test
void docsAreAvailableToAuthorizedUser() {
    webTestClient.mutateWith(mockUser().roles("API_DOCS"))
            .get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk();
}
~~~

When endpoints use a JWT resource server, use `mockJwt()` from `SecurityMockServerConfigurers` with the required authorities. Test security configuration must mirror actual application rules.

Include control tests for negative cases:

- No principal: receives `401` or configured challenge.
- Authenticated without required role: receives `403`.
- With documentation role: fetches document cleanly.
- User with public-only access: cannot fetch restricted admin groups.

Never configure test security with `permitAll` everywhere and conclude production endpoints are properly secured.

## 15. Using JSON Pointer for Maintainable Assertions

JSON Pointer provides a clean way to navigate deep JSON nodes. Examples:

| Element | JSON Pointer |
|---|---|
| OpenAPI version | `/openapi` |
| `POST /api/orders` operation | `/paths/~1api~1orders/post` |
| `POST` `operationId` | `/paths/~1api~1orders/post/operationId` |
| Request body | `/paths/~1api~1orders/post/requestBody` |
| `201` response | `/paths/~1api~1orders/post/responses/201` |
| `OrderResponse` schema | `/components/schemas/OrderResponse` |

`JsonNode.at(...)` returns a `MissingNode` when a path does not exist. Checking `isMissingNode()` before reading deeper produces clearer failures than reading empty values and getting misleading assertions.

For keys containing special characters:

- Escape `~` to `~0`.
- Escape `/` to `~1`.
- Keep all other characters unchanged.

Extract frequently used pointers into constants or helper methods when multiple tests inspect the same operation. This prevents typos in paths.

## 16. Separating Document Tests from Controller Slice Tests

`@WebFluxTest` works well for testing a web slice such as controller mappings and serialization. However, slice tests load only a curated subset of beans and may omit application-wide springdoc, group, security, or customizer configurations.

| Setup | Appropriate Scope |
|---|---|
| `@WebFluxTest(Controller.class)` | Testing controller, mappings, and web behavior in a slice |
| `@SpringBootTest(webEnvironment = MOCK)` | Loading full application context with a mock web environment |
| `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@AutoConfigureWebTestClient` | Testing HTTP over a real server on a random port |
| `WebTestClient.bindToApplicationContext(context).build()` | Manually binding client to an application context in tests |

When verifying that `/v3/api-docs` is configured properly for the full application, prefer full-context integration tests. If using `@WebFluxTest`, explicitly import required configurations and beans, and confirm the springdoc endpoint is actually registered in that test context.

## 17. Testing Reactive Streams and Collection Responses

In WebFlux, controllers can return `Mono<T>` or `Flux<T>`. Verify schemas against actual wire representations:

- `Mono<OrderResponse>` is typically documented as a single object response.
- `Flux<OrderResponse>` serializes a stream of elements; for `application/json`, responses typically render as a JSON array.
- `text/event-stream` or `application/x-ndjson` carry streaming semantics distinct from a JSON array.

JSON array test example:

~~~java
@Test
void listOrdersReturnsJsonArray() {
    webTestClient.get()
            .uri("/api/orders")
            .exchange()
            .expectStatus().isOk()
            .expectHeader().contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
            .expectBody()
            .jsonPath("$[0].customerCode").isEqualTo("CUS-100");
}
~~~

The OpenAPI document must describe an array schema when clients receive a JSON array. If a route streams Server-Sent Events, verify the matching media type and event format; never assume every `Flux` produces a JSON array.

## 18. Verifying Request Validation and Error Responses

When request DTOs use Bean Validation, runtime tests should send both valid and invalid payloads:

~~~java
@Test
void createOrderRejectsBlankCustomerCode() {
    webTestClient.post()
            .uri("/api/orders")
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue("""
                    {
                      "customerCode": "",
                      "amount": 125.50
                    }
                    """)
            .exchange()
            .expectStatus().isBadRequest();
}
~~~

Exact status codes depend on validation, exception handlers, and your application's error contract. If errors are standardized as `ProblemDetail` or `ApiErrorResponse`, verify the response body too and compare it against the error schema in OpenAPI.

OpenAPI can surface `minLength`, `minimum`, or `required` properties from Bean Validation, yet only when springdoc recognizes the constraints under your configuration. Both document tests and runtime tests should confirm critical constraints so documentation and server enforcement never diverge.

## 19. Validating Beyond WebTestClient

The assertions above lock down core contract guarantees. Still, they neither prove the entire document conforms to the OpenAPI specification nor automatically validate every response body against schemas.

In CI pipelines, you can add:

1. Fetch OpenAPI JSON from `/v3/api-docs`.
2. Parse the document into an OpenAPI model.
3. Run an OpenAPI validator compatible with the `openapi` version in the document.
4. Use a matching JSON Schema validator to check sample payloads if needed.
5. Run contract tests against live requests/responses.
6. Diff the artifact against the prior release to detect breaking changes.

Choose a validator that understands the exact OpenAPI 3.0 or 3.1 output generated. A 3.0-only validator may misinterpret OpenAPI 3.1 Schema Objects based on JSON Schema Draft 2020-12.

## 20. Running Tests in CI

A reactive contract-testing pipeline can include:

1. Compile application and test sources.
2. Boot the application context with `@SpringBootTest`.
3. Run `WebTestClient` tests against `/v3/api-docs` and group endpoints.
4. Run runtime API tests with the same client.
5. Export OpenAPI JSON/YAML artifacts if the pipeline archives them separately.
6. Run OpenAPI validators and contract diffs.
7. Save test reports alongside the build's OpenAPI artifact.

Maven command example:

~~~bash
mvn -B test
~~~

Gradle command example:

~~~bash
./gradlew test
~~~

You do not need to launch a separate server if integration tests use `RANDOM_PORT`; Spring Boot Test manages server lifecycle per test run. If the pipeline runs an external export step outside tests, wait until the application is ready before hitting endpoints.

## 21. Common Pitfalls

| Symptom | Possible Cause | Resolution |
|---|---|---|
| `/v3/api-docs` returns `404` in tests | Springdoc auto-configuration not loaded or API docs disabled | Use full application context and inspect starter/config |
| Controller tests pass yet docs tests fail | `@WebFluxTest` omits required springdoc config | Move docs tests to `@SpringBootTest` or import needed config |
| `JsonNode.at(...)` returns `MissingNode` | Wrong JSON Pointer, different path/method, or operation skipped | Inspect raw document and escape `/` as `~1` |
| Wrong `operationId` | Missing or altered `@Operation(operationId = ...)` | Set stable, unique `operationId` values |
| Request body schema missing | Reactive wrapper or DTO not recognized as expected | Check `@RequestBody`, generic types, and OpenAPI JSON |
| Response schema is inlined | Springdoc does not emit a component `$ref` in current config | Assert against actual schema instead of forcing `$ref` unless contractual |
| `201` response absent from document | Status selected dynamically without metadata | Use `@ApiResponse` to document statuses explicitly |
| Docs test gets `401`/`403` | Endpoint is protected and test lacks valid principal | Use `mockUser()`/`mockJwt()` or test credentials |
| JSON parse failure | Endpoint returned HTML or truncated body | Check status, `Content-Type`, and response body |
| YAML test finds text yet syntax is broken | Checked only substring presence | Parse with a YAML parser and run a validator |
| `Flux` schema is not an array as expected | Media type or writer streams events | Inspect HTTP `Content-Type` and generated schema |
| Tests depend on stale state | Test data not seeded/reset | Prepare isolated fixtures per test |
| Tests pass yet SDK clients fail | Assertions missed constraints or generator interprets differently | Add validator, test SDK generation, and run contract tests |

## 22. Contract Testing Checklist

- [ ] Integration tests load the application context with springdoc.
- [ ] `WebTestClient` successfully calls the OpenAPI JSON endpoint.
- [ ] OpenAPI version and `info` metadata are accurate.
- [ ] Paths and HTTP methods appear as expected.
- [ ] `operationId` values are stable, unique, and properly named.
- [ ] Path/query/header parameters carry right names, locations, and `required` flags.
- [ ] Request bodies declare expected media types and schemas.
- [ ] Response statuses, content types, and schemas are accurate.
- [ ] Component schemas and `$ref` entries resolve cleanly.
- [ ] Group documents contain expected operations only.
- [ ] Security rules for docs endpoints are tested with appropriate principals.
- [ ] Live runtime APIs are invoked and return expected results.
- [ ] Validation and error responses match the contract.
- [ ] YAML is parsed when pipelines distribute YAML.
- [ ] OpenAPI validators and contract diffs run where required.

## 23. Design Principles

- Use `WebTestClient` to test both documentation and business endpoints in Reactive applications.
- Use a full application context when verifying springdoc auto-configuration, groups, and customizers.
- Use `RANDOM_PORT` to test over a real HTTP server.
- Inspect OpenAPI documents with `JsonNode`/JSON Pointer instead of merely checking for a non-empty response.
- Lock down critical contract pieces: `operationId`, parameters, request bodies, response codes, and schemas.
- Test live runtime APIs separately to confirm real behavior.
- Distinguish `Mono`, `Flux`, JSON arrays, and streaming media types.
- Test docs endpoint security with realistic mock users/tokens.
- Never assume `WebTestClient` automatically validates OpenAPI schemas.
- Combine OpenAPI validators, JSON Schema validators, and contract diffs in CI as project scope demands.

## Conclusion

`WebTestClient` lets you verify Springdoc-generated OpenAPI documents directly inside Spring WebFlux integration tests. Use `@SpringBootTest(webEnvironment = RANDOM_PORT)` with `@AutoConfigureWebTestClient` to load full configuration and call `/v3/api-docs`; then parse JSON with `JsonNode` to verify version, paths, `operationId`, parameters, request bodies, responses, and component schemas. Use the same client to call runtime APIs and check real statuses, headers, and bodies. Add dedicated tests for groups, YAML, security, or validation per your application setup. Finally, pair with an OpenAPI/JSON Schema validator when full contract semantics must be verified, because `WebTestClient` assertions do not replace a validator.
