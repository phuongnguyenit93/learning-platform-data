# Reading the YAML Specification at `/v3/api-docs.yaml`

Springdoc-openapi can export an API contract as JSON or YAML from Spring Boot application metadata. When the application runs with default configuration, the `/v3/api-docs` endpoint provides the JSON documentation and `/v3/api-docs.yaml` provides the same documentation in YAML format. The YAML version is convenient for reading, reviewing changes in Git, saving as an artifact, and feeding into testing or client-generation workflows.

For the `SPRINGDOC_OPENAPI` module, it is important to understand YAML as a representation of the OpenAPI model generated by springdoc from controllers, DTOs, annotations, and configuration. Reading this document helps verify the contract that API consumers actually receive, rather than relying only on the intent expressed in the source code.

## 1. How Does the `/v3/api-docs.yaml` Endpoint Work?

During Spring Boot application startup, Spring registers handler mappings and initializes configuration beans. Springdoc integrates with this environment to collect information about endpoints, parameters, request/response types, and OpenAPI metadata. When a request hits the documentation endpoint, springdoc returns the built OpenAPI model in JSON or YAML format.

With the default configuration:

| Endpoint | Content |
|---|---|
| `/v3/api-docs` | OpenAPI documentation in JSON format |
| `/v3/api-docs.yaml` | OpenAPI documentation in YAML format |
| `/swagger-ui.html` | Swagger UI entry point; may redirect to the actual UI page |

Both documentation endpoints represent the same contract. The difference lies in serialization format, not one endpoint containing more APIs than the other. Swagger UI usually loads the JSON document by default, but other tools can read YAML directly.

If the application has a context path, reverse proxy prefix, or custom documentation path configuration, the actual URL will include the corresponding prefix. For example, with context path `/orders`, the default URL becomes `/orders/v3/api-docs.yaml`.

## 2. Accessing and Saving the YAML Document

Start the Spring Boot application normally, then open the URL below in a browser:

```text
http://localhost:8080/v3/api-docs.yaml
```

If the endpoint is protected, send the request with the credentials required by the application. You can use `curl.exe` to download the document to a file:

```bash
curl.exe -fS http://localhost:8080/v3/api-docs.yaml -o openapi.yaml
```

When the API requires a bearer token, add the `Authorization` header:

```bash
curl.exe -fS \
  -H "Authorization: Bearer <access-token>" \
  http://localhost:8080/v3/api-docs.yaml \
  -o openapi.yaml
```

In PowerShell, you can run the command above across multiple lines using a backtick as the line-continuation character, or write it on a single line. Using `curl.exe` invokes the curl program on Windows instead of the `curl` alias that may point to `Invoke-WebRequest` in some PowerShell versions.

After downloading, verify that the file contains YAML starting with the `openapi` field. If you receive HTML, a login page, or an error JSON instead of YAML, check the HTTP status, redirects, access permissions, and URL. Do not feed an HTML error file into OpenAPI tooling, as parser error messages will be misleading.

## 3. Changing the Documentation Path

The default path can be changed using the `springdoc.api-docs.path` configuration. For example:

```yaml
springdoc:
  api-docs:
    path: /internal/openapi
```

With this configuration, the JSON endpoint uses `/internal/openapi`; the corresponding YAML endpoint uses the `.yaml` suffix, namely `/internal/openapi.yaml`. If there is a context path or proxy prefix, prepend that prefix when calling from outside.

The documentation endpoint can be enabled or disabled with configuration:

```yaml
springdoc:
  api-docs:
    enabled: true
```

Setting `false` disables serving API docs through the springdoc endpoint. Configuration can be set per profile so development environments allow access while actual deployment environments apply appropriate documentation publishing and protection policies.

When the URL does not work, check in order:

1. The application has started successfully and the web server is listening on the right port.
2. Whether the path includes the context path and any prefix added by a proxy.
3. Whether `springdoc.api-docs.path` is set in the active profile.
4. Whether `springdoc.api-docs.enabled` is set to `false`.
5. Whether a security filter, gateway, or reverse proxy is blocking the request before it reaches the documentation endpoint.

## 4. Reading the Top-Level Structure of OpenAPI YAML

An OpenAPI document typically starts with the `openapi`, `info`, `servers`, `paths` fields, and may include `components` and `security`. Abbreviated example:

```yaml
openapi: 3.0.1
info:
  title: Order API
  version: v1
  description: Order management API
servers:
  - url: https://api.example.com
paths:
  /api/orders/{id}:
    get:
      tags:
        - Orders
      summary: Get order information
      operationId: getOrderById
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
            format: uuid
      responses:
        '200':
          description: Order found
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/OrderResponse'
        '404':
          description: Order not found
components:
  schemas:
    OrderResponse:
      type: object
      properties:
        id:
          type: string
          format: uuid
        status:
          type: string
```

This is a structural illustration, not a fixed output across all springdoc versions. The `openapi` field indicates the specification version; the actual value depends on the library version and configuration. `info` contains document metadata, `servers` describes server addresses, and `paths` contains HTTP paths and operations.

When reviewing YAML, read from the outside in:

- **`openapi`:** the OpenAPI specification version that the document conforms to. Do not confuse this field with the application version in `info.version`.
- **`info`:** title, published API version, description, and contact or license information if present.
- **`servers`:** base URLs for clients to call the API. Check whether the URLs fit the environment and deployment setup.
- **`paths`:** the set of endpoints included in the documentation. Each path may contain `get`, `post`, `put`, `patch`, `delete`, `options`, or `head` operations.
- **`components`:** where reusable schemas, responses, parameters, request bodies, headers, and security schemes are defined.
- **`security`:** security requirements applied at the document level; an operation can declare its own requirements or override the global policy per OpenAPI rules.

## 5. Reading an Operation in `paths`

Each pair of path and HTTP method describes an operation. For example, `/api/orders/{id}` with `get` corresponds to the operation for retrieving an order. Fields commonly checked include:

| Field | Meaning when reading the contract |
|---|---|
| `tags` | Groups operations in the documentation and Swagger UI |
| `summary` | Short description of the functionality |
| `description` | Detailed explanation of usage or business rules |
| `operationId` | Operation identifier, commonly used during client generation |
| `parameters` | Path, query, header, or cookie parameters |
| `requestBody` | Request content, media type, and schema |
| `responses` | Status codes, descriptions, and response content |
| `deprecated` | Indicates that the operation has been marked deprecated |
| `security` | Operation-specific authentication requirements if declared |

Example of a request body and multiple responses:

```yaml
paths:
  /api/orders:
    post:
      summary: Create an order
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
      responses:
        '201':
          description: Order created
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/OrderResponse'
        '400':
          description: Invalid data
        '409':
          description: Order conflicts with current state
```

Read this section to confirm the endpoint has the right HTTP method, parameters are in the right locations, whether the request body is required, media types are accurate, and responses cover the outcomes the API actually returns. A response with only `description` can still be valid if the operation has no response body; for responses with a body, verify `content` and the corresponding schema.

## 6. Understanding Schemas and `$ref` References

Java DTOs are usually represented as schemas in `components.schemas`. Instead of repeating a type definition across multiple operations, OpenAPI can reference a shared schema using `$ref`:

```yaml
components:
  schemas:
    CreateOrderRequest:
      type: object
      required:
        - customerName
        - amount
      properties:
        customerName:
          type: string
          maxLength: 80
          example: Nguyen Van A
        amount:
          type: number
          format: double
          description: Total amount in VND
          example: 250000
    OrderResponse:
      type: object
      properties:
        id:
          type: string
          format: uuid
        status:
          type: string
```

`$ref: '#/components/schemas/CreateOrderRequest'` means the schema content is resolved from the corresponding location in the same document. When reading an operation, follow `$ref` to inspect all data types, required fields, constraints, enums, formats, and examples.

Points to note:

- `required` at the object level lists mandatory properties; `required: true` on a parameter or request body indicates that component is mandatory.
- `type` and `format` describe the data type and additional formatting, such as `string` with `uuid` or `date-time`.
- `enum`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, and `maxItems` express constraints that may be inferred from types or validation metadata.
- `readOnly` and `writeOnly` help describe read-only or write-only fields in the contract.
- JSON field names, nullable types, inherited properties, and nested structures depend on DTOs, Jackson, validation, and springdoc configuration.

Do not assume the schema always matches the Java declaration word for word. What matters is that the YAML accurately describes the JSON the application accepts and returns at runtime.

## 7. Reading Security Information in YAML

When an API uses bearer tokens, API keys, or OAuth2, the document can define those mechanisms in `components.securitySchemes` and reference them in `security`. Illustrative example of bearer JWT:

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
security:
  - bearerAuth: []
```

This declaration describes how clients send a bearer token. It does not configure Spring Security itself and does not enable authentication on endpoints. Enforcement policy is still determined by the application's security configuration; OpenAPI metadata must be declared or customized to reflect that policy.

If only some endpoints require login, check `security` on individual operations. An operation can be public even when the top-level document declares a general security requirement; OpenAPI allows an operation to override global requirements, including representing an operation that requires no security. Therefore, check that the generated output matches actual access permissions.

## 8. YAML, JSON, and Documentation Groups

JSON and YAML are two representations of the same OpenAPI model. JSON suits many APIs and automated tools; YAML is easy to read and review, and is often used as the specification file in repositories. Switching formats does not change the contract if both versions are generated from the same configuration.

Springdoc also supports splitting documentation into groups via `GroupedOpenApi` configuration. Each group can select specific packages or paths to build a set of endpoints tailored to an API scope. This is useful when an application has multiple functional domains or needs to distribute documentation to different client groups.

Example group declaration:

```java
@Bean
GroupedOpenApi orderApi() {
    return GroupedOpenApi.builder()
            .group("orders")
            .pathsToMatch("/api/orders/**")
            .build();
}
```

With this group, springdoc creates dedicated documentation for the `orders` scope. The group's JSON endpoint usually takes the form `/v3/api-docs/orders`. To download YAML for a group, use the corresponding YAML route exposed by the springdoc version in use; check the group configuration and the URL used by Swagger UI rather than guessing the path when the application has customized `springdoc.api-docs.path`.

When reading grouped documentation, check both the group name and any `pathsToMatch`, `packagesToScan`, `pathsToExclude`, or `packagesToExclude` filters. A missing endpoint may be excluded from the group rather than unrecognized by springdoc.

## 9. Protecting Documentation Endpoints

OpenAPI YAML can reveal internal paths, data models, authentication mechanisms, and supported operations. Therefore, access permissions for documentation must align with the system's API publishing policy.

Common ways to control access:

- Use Spring Security to require authentication or authorization before accessing documentation endpoints.
- Use profiles or deployment configuration to enable/disable API docs per environment.
- Restrict access via a gateway, internal network, or reverse proxy if documentation is only for the development team.
- Do not put tokens, passwords, secret keys, or real personal data in `example`, `description`, or OpenAPI metadata.
- Check permissions across JSON, YAML, and Swagger UI endpoints; protecting the UI while leaving the data endpoint open can still expose the contract.

Do not treat hiding Swagger UI as a documentation protection measure. Clients can still call `/v3/api-docs` or `/v3/api-docs.yaml` directly if those endpoints remain open.

## 10. Checking YAML Quality

After downloading the document, verify both YAML syntax and OpenAPI semantics:

1. **Check the HTTP response:** the request succeeds, returns YAML content, and does not unexpectedly redirect to a login page.
2. **Check the structure:** `openapi`, `info`, and `paths` exist; the specification version is a valid value supported by the tooling ecosystem in use.
3. **Check the paths:** paths and HTTP methods are complete, have the right prefixes, and belong to the right group scope.
4. **Check requests:** parameters are in the right locations, request bodies and media types are accurate, and schemas include required fields and constraints.
5. **Check responses:** status codes, schemas, headers, and examples match actual outcomes.
6. **Check security:** security schemes, scopes, and operation-level requirements reflect Spring Security policies.
7. **Check references:** every `$ref` points to an existing component and creates no invalid references.
8. **Check with tools:** use an OpenAPI parser or validator in the IDE/CI to catch invalid YAML syntax and invalid OpenAPI structure.
9. **Compare with runtime:** call representative endpoints and compare actual payloads against schemas in the documentation.

A YAML file can parse cleanly and still misrepresent the API. For instance, `200` having an `OrderResponse` schema while the application returns `204` with no body is a contract discrepancy even though the syntax is completely valid. Hence, both structural checks and behavioral checks are needed.

## 11. Common Issues When Reading `/v3/api-docs.yaml`

| Symptom | Common Cause | How to Handle |
|---|---|---|
| `404 Not Found` | Wrong path, context path, or `springdoc.api-docs.path`; API docs disabled | Check the running configuration and actual URL |
| `401` or `403` | Security requires authentication or higher privileges | Send appropriate credentials or check access policies |
| Receiving HTML instead of YAML | Request redirected, proxy returning an error page, or URL pointing to Swagger UI by mistake | Check status, `Location` header, and endpoint URL |
| YAML missing expected endpoints | Controller not component-scanned, endpoint filtered out, or belonging to a different group | Check package scan, mappings, and `GroupedOpenApi` configuration |
| Schema missing properties | Jackson, visibility, hidden annotations, or schema settings affecting output | Check DTOs, serializers, and OpenAPI annotations |
| `servers` contains wrong URL | Server configuration, context path, or reverse proxy not reflected | Check OpenAPI configuration and forwarded headers |
| Document rejected by parser | Invalid YAML syntax, invalid `$ref`, or malformed OpenAPI structure | Use a parser/validator and fix source metadata |

If the issue only occurs behind a reverse proxy, compare the URL and headers forwarded by the proxy against the application configuration. If the endpoint returns a document but misses an operation, check startup logs and group filters before modifying the controller.

## 12. Integrating YAML into the Development Workflow

YAML can be saved as an artifact to review and diff contracts across releases. A simple workflow includes:

1. Start the application with a configuration representative of the release version.
2. Download `/v3/api-docs.yaml` or the corresponding group endpoint.
3. Run an OpenAPI parser/validator and check internal rules.
4. Diff against the previous version's specification to detect breaking changes that could disrupt clients, such as removing a path, changing a field type, altering a response, or tightening required constraints.
5. Store the artifact tagged with the application version and distribute it to API consumer teams.

Do not edit the generated YAML file directly and expect the application to pick up those changes automatically. When you discover missing descriptions or incorrect schemas, update the controller metadata, DTOs, OpenAPI annotations, or customizers that serve as the source of generation, then regenerate and verify.

Reading the YAML version at `/v3/api-docs.yaml` reveals the OpenAPI contract in an easily inspectable and automatable form. Once you understand `paths`, `components`, `$ref`, `responses`, and `security`, developers can accurately cross-check documentation against Spring Boot controllers, catch discrepancies before release, and provide a stable specification for both tools and API consumers.
