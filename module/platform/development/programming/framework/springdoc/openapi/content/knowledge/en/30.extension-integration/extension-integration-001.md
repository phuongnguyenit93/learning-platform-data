# Scalar as a UI Option Alongside Swagger UI

## 1. Scalar in the Springdoc Ecosystem

Springdoc OpenAPI analyzes controllers, DTOs, annotations, validation, and application configuration to generate an OpenAPI document. Swagger UI or Scalar uses that document to display the API reference in the browser.

Scalar is an API reference UI that can read OpenAPI JSON/YAML and present endpoints, schemas, parameters, request bodies, responses, and security information. When integrated with Spring Boot, Scalar acts as the UI for the documentation; Springdoc remains responsible for generating the OpenAPI contract from the application.

The processing flow can be visualized as follows:

~~~text
Spring MVC / WebFlux controllers
             |
             v
       Springdoc OpenAPI
             |
             v
       /v3/api-docs
             |
       +-----+------+
       |            |
       v            v
   Swagger UI     Scalar
       |            |
       +-----+------+
             |
             v
      API endpoints
~~~

Scalar does not auto-discover controllers, does not generate schemas from Java DTOs, and does not replace Springdoc. It reads the OpenAPI document published by Springdoc. Therefore, if `/v3/api-docs` is missing an operation or has an incorrect schema, switching the UI to Scalar will not fix the contract on its own.

## 2. When to Choose Scalar Alongside Swagger UI?

Both Scalar and Swagger UI can render an OpenAPI document and help users explore the API. Choosing the UI depends on the needs of the development team, integrators, and the existing documentation system.

| Criterion | Swagger UI | Scalar |
|---|---|---|
| Data source | OpenAPI JSON/YAML | OpenAPI JSON/YAML |
| Role | API documentation UI | API reference UI |
| Operation exploration | Yes | Yes |
| Schema display | Yes | Yes |
| Request testing | Try it out | API client/try request depending on version capabilities |
| Customization | Configuration, plugins, and custom assets | Scalar configuration and themes |
| Springdoc integration | Built-in UI starter | Can embed a custom Scalar UI or use a suitable integration |
| Contract dependency | Requires a valid OpenAPI document | Requires a valid OpenAPI document |

Scalar can be a good fit when a team wants a different API reference UI, different navigation and presentation, or wants to use the same OpenAPI contract on a developer portal website.

There is no need to remove Swagger UI immediately when adding Scalar. Both UIs can coexist at different URLs so the team can compare, test, and transition in stages.

## 3. Minimal Integration Architecture

A low-dependency integration approach is to have Spring Boot serve a static HTML page, and have that page load Scalar JavaScript and read the OpenAPI document from Springdoc.

Request flow:

1. The user opens `/scalar/`.
2. Spring Boot returns the static HTML page.
3. The browser loads the Scalar API Reference bundle.
4. Scalar calls `/v3/api-docs`.
5. Scalar renders the API reference based on the document.
6. When the user tries an operation, the browser calls the API server described in the `servers` field or the selected URL.

This approach does not require a separate Java controller for Scalar. It also keeps the single source of contract as the OpenAPI document generated by Springdoc.

In production environments, you can self-host Scalar assets or use an official integration/starter compatible with your running Spring Boot version. Verify artifact coordinates and configuration against the Scalar release instead of copying a version from an old example.

## 4. Ensure Springdoc Still Exposes the OpenAPI Document

Scalar needs an accessible OpenAPI URL. With the default configuration, Springdoc typically provides:

~~~http
GET /v3/api-docs
GET /v3/api-docs.yaml
~~~

You can keep the default configuration:

~~~yaml
springdoc:
  api-docs:
    enabled: true
    path: /v3/api-docs
  swagger-ui:
    enabled: true
~~~

`api-docs.enabled` controls generating the OpenAPI endpoint. `swagger-ui.enabled` controls the built-in Swagger UI. These two features are independent: you can disable Swagger UI while keeping OpenAPI JSON/YAML for Scalar or other tools to use.

If `springdoc.api-docs.enabled` is disabled, Scalar will no longer have a data source at `/v3/api-docs`. The Scalar page may still load, but the API reference section will report an error when fetching the document.

## 5. Create a Static Scalar Page in Spring Boot

Create the file:

~~~text
src/main/resources/static/scalar/index.html
~~~

Spring Boot automatically serves static resources on the classpath. The file above is typically accessible at `/scalar/`.

Example content:

~~~html
<!doctype html>
<html lang="vi">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Catalog API Reference</title>
</head>
<body>
  <script
    id="api-reference"
    data-url="/v3/api-docs"
    data-configuration='{"theme":"purple"}'
    src="https://cdn.jsdelivr.net/npm/@scalar/api-reference">
  </script>
</body>
</html>
~~~

The Scalar bundle reads `data-url` to know where to fetch the OpenAPI document. `data-configuration` passes UI configuration. The example uses the `purple` theme; available themes and options may vary by Scalar version.

This is a CDN-based embedding approach, convenient for experimentation and quick deployment. Before using it in production, pin the package version rather than referencing an unversioned URL, or self-host the assets to control versioning and security policy.

## 6. Pin the Scalar Bundle Version

An unversioned CDN URL may point to a newer release in the future. When Scalar updates, the UI or behavior could change without any commit in the application repository.

You can pin a specific version in the URL:

~~~html
<script
  id="api-reference"
  data-url="/v3/api-docs"
  data-configuration='{"theme":"purple"}'
  src="https://cdn.jsdelivr.net/npm/@scalar/api-reference@<PINNED_VERSION>">
</script>
~~~

Replace `<PINNED_VERSION>` with a version tested in the project. Track this version in code reviews and the frontend dependency upgrade process.

Do not use `latest` or an unpinned URL for critical production documentation if the team needs reproducibility. Check the release notes and run smoke tests before upgrading Scalar.

## 7. Configure the OpenAPI URL for Scalar

`data-url` must point to a document that the browser can fetch. Common cases:

| Case | Reference URL |
|---|---|
| Springdoc default | /v3/api-docs |
| Springdoc YAML output | /v3/api-docs.yaml |
| `partner` document group | /v3/api-docs/partner |
| `internal` document group | /v3/api-docs/internal |
| Custom API docs path | Path configured in `springdoc.api-docs.path` |

If Scalar is served from the same origin as Springdoc, using a relative/root-relative URL usually avoids additional CORS configuration.

If the UI and the OpenAPI document are on two different origins, the browser enforces the same-origin policy. In that case, the server serving the document must allow the Scalar page's origin according to the CORS policy; do not enable wildcard credentials as a quick workaround.

Verify the URL from the browser's perspective, not only whether the URL is reachable from the Spring Boot host.

## 8. Use Scalar with Document Groups

Springdoc supports creating multiple OpenAPI documents using `GroupedOpenApi`. For example:

~~~java
@Bean
GroupedOpenApi partnerApi() {
    return GroupedOpenApi.builder()
        .group("partner")
        .pathsToMatch("/api/partner/**")
        .build();
}

@Bean
GroupedOpenApi publicApi() {
    return GroupedOpenApi.builder()
        .group("public")
        .pathsToMatch("/api/public/**")
        .build();
}
~~~

Each group has its own document endpoint. A Scalar page can point to the corresponding group.

Example page `src/main/resources/static/scalar/partner.html`:

~~~html
<script
  id="api-reference"
  data-url="/v3/api-docs/partner"
  data-configuration='{"theme":"purple"}'
  src="https://cdn.jsdelivr.net/npm/@scalar/api-reference@<PINNED_VERSION>">
</script>
~~~

The `public.html` page can use `/v3/api-docs/public`.

Splitting groups helps avoid exposing internal operations in public documentation. However, group filtering only controls document content; it does not protect runtime endpoints on its own. Security must be configured separately for the Scalar page, the OpenAPI document, and the API operations.

## 9. Let Swagger UI and Scalar Coexist

During the evaluation phase, you can keep Swagger UI and add Scalar:

- Swagger UI: `/swagger-ui/index.html`
- Scalar: `/scalar/`
- OpenAPI JSON: `/v3/api-docs`
- OpenAPI YAML: `/v3/api-docs.yaml`

Springdoc configuration can continue to keep Swagger UI enabled:

~~~yaml
springdoc:
  swagger-ui:
    enabled: true
  api-docs:
    enabled: true
~~~

Once the team decides to use Scalar as the primary UI, Swagger UI can be disabled:

~~~yaml
springdoc:
  swagger-ui:
    enabled: false
  api-docs:
    enabled: true
~~~

The Scalar page is a separate static resource, so it is not disabled along with the built-in Swagger UI, as long as static resources are still served and the OpenAPI endpoint remains enabled.

Do not remove the Swagger UI dependency immediately if some teams or environments still use it. You can run them side by side, gather feedback, and migrate gradually.

## 10. Use npm When the Documentation Site Has a Separate Frontend Build

If the developer portal is built with Vite, React, or another frontend framework, Scalar can be managed as a frontend dependency instead of loading from a CDN.

Install the package:

~~~bash
npm install @scalar/api-reference
~~~

Example JavaScript entry point:

~~~javascript
import { ApiReference } from '@scalar/api-reference'
import '@scalar/api-reference/style.css'

ApiReference('#app', {
  url: '/v3/api-docs',
})
~~~

HTML containing the mount point:

~~~html
<div id="app"></div>
~~~

The exact import style should follow the documentation of the pinned package version. Ensure the bundler handles CSS and assets properly. If the frontend is deployed on a different domain from Spring Boot, configure CORS and authentication for the OpenAPI endpoint.

Use a package manager lockfile to pin the dependency tree. When upgrading Scalar, update the lockfile and run UI checks as well as test requests.

## 11. Integrate Using an Available Spring Boot Starter or Module

Scalar may provide integration packages for frameworks or Spring Boot depending on the release line. If choosing a starter, verify:

- Artifact `groupId`/`artifactId` and version from the official Scalar documentation.
- Supported Spring Boot and Java versions.
- How to configure the OpenAPI URL.
- The default path created by the integration.
- How to customize theme, layout, and authentication.
- Whether static resources are bundled or loaded from a CDN.
- How the integration interacts with Spring Security and context path.

Do not assume all starters share the same property names or URLs. Packages may change across releases. Pin the version and verify the actual endpoints after startup.

If you only need a single API reference page, a static HTML embed is usually sufficient and avoids increasing backend dependencies. A starter is suitable when a project wants managed framework integration and deeper customization requirements.

## 12. Authentication and Security Schemes

Scalar reads the security schemes described in the OpenAPI document to display authentication details appropriate for each operation. For example, bearer JWT:

~~~yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

security:
  - bearerAuth: []
~~~

Springdoc can generate the corresponding metadata using `@SecurityScheme` and `@SecurityRequirement` or an `OpenAPI` bean.

Example:

~~~java
@SecurityScheme(
    name = "bearerAuth",
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT"
)
@Configuration
class OpenApiSecurityConfiguration {
}
~~~

Declaring a security scheme only describes how the client sends credentials. It does not enable authentication in Spring Security and does not make endpoints any more secure.

Users entering a token in Scalar can send that token to the API when using the try-request feature. Never embed real tokens in HTML, `data-configuration`, query strings, or OpenAPI examples.

## 13. Protect the Scalar Page and OpenAPI Document

Treat these as separate resources:

- `/scalar/**`: the Scalar UI.
- `/v3/api-docs` and groups: the OpenAPI contract.
- `/api/**`: business endpoints.

You can require a role to view documentation using Spring Security:

~~~java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers(
            "/scalar/**",
            "/v3/api-docs",
            "/v3/api-docs/**"
        ).hasRole("API_DOCS")
        .anyRequest().authenticated()
    );

    return http.build();
}
~~~

This example illustrates a Servlet Security policy. Real-world applications need to integrate login/token mechanisms, CSRF, CORS, and existing filter chains.

If the Scalar page is public while the OpenAPI document is protected, the browser needs a way to authenticate when loading the document. If both require login, ensure static resources and API docs use the same session or token mechanism supported by the browser.

Hiding the Scalar link is not a security measure. Users can still call `/v3/api-docs` directly if the endpoint is unprotected.

## 14. CORS When Scalar and Springdoc Are on Different Origins

If the Scalar page is hosted at `https://developer.example.com` while the OpenAPI document is at `https://api.example.com`, the browser sends a cross-origin request to fetch the document.

Configure CORS on the documentation server for the exact origin, method, and headers. Policy-level example:

- Allowed origin: `https://developer.example.com`
- Allowed method: `GET`
- Allowed headers: only headers actually needed, such as `Authorization`
- Allow credentials: enable only when using cookies/sessions and the origin is explicitly specified

Do not use `*` together with credentialed requests. If an `Authorization` header needs to be sent, browser preflight requests may occur and the server must handle `OPTIONS` appropriately.

Scalar's Try it out also calls the API server described in `servers`. If the API server is on a different origin, CORS on the business endpoints must also allow the Scalar page's origin.

## 15. Reverse Proxy and Context Path

When the application runs behind a reverse proxy or has a context path, `data-url` must match the public URL.

For example, if the application is published under the `/catalog` prefix:

- Scalar page: `/catalog/scalar/`
- OpenAPI JSON: `/catalog/v3/api-docs`
- API: `/catalog/api/**`

In that case, the HTML may need:

~~~html
<script
  id="api-reference"
  data-url="/catalog/v3/api-docs"
  data-configuration='{"theme":"purple"}'
  src="https://cdn.jsdelivr.net/npm/@scalar/api-reference@<PINNED_VERSION>">
</script>
~~~

If the same artifact is deployed under multiple context paths, do not hard-code the prefix in HTML. You can use a template engine to generate the URL from deployment configuration or serve a separate Scalar configuration per environment.

Verify forwarded headers, server URLs in the OpenAPI document, and static resource paths. A Scalar page that loads successfully but fetches `/v3/api-docs` with the wrong prefix will still fail to display the API.

## 16. CSP and JavaScript/CSS Sources

When loading Scalar from a CDN, the Content Security Policy must allow the sources actually used by the bundle. Depending on the version and configuration, the browser may load scripts, styles, fonts, or send fetch requests to the OpenAPI/API origin.

Do not widen CSP to `*` just to make Scalar work. Use the Browser Console to identify blocked resources, then add only the required origins to `script-src`, `style-src`, `font-src`, or `connect-src`.

For environments with strict CSP or no Internet access:

- Self-host Scalar assets.
- Pin the version and verify package checksums.
- Serve JS/CSS from the same origin if possible.
- Avoid inline scripts without nonce/hash when disallowed by CSP.
- Verify asset URLs after packaging and deployment.

A CDN enables quick updates but introduces an external dependency and some supply-chain risk. Self-hosting provides control over version, availability, and security policy.

## 17. Customizing Themes and UI

Scalar supports UI configuration via a configuration object. Embed example:

~~~html
<script
  id="api-reference"
  data-url="/v3/api-docs"
  data-configuration='{"theme":"purple"}'
  src="https://cdn.jsdelivr.net/npm/@scalar/api-reference@<PINNED_VERSION>">
</script>
~~~

The theme only changes presentation. It does not alter OpenAPI schemas, paths, security, or runtime behavior.

Options such as theme, layout, default HTTP client, hidden clients, search, or authentication behavior depend on the Scalar version. Take options from the documentation of the exact pinned release rather than copying an old configuration without checking.

Keep UI configuration concise. Changes that affect how clients send requests should be reviewed as integration-experience changes, not merely cosmetic changes.

## 18. OpenAPI Version and Scalar Compatibility

Scalar reads the OpenAPI document, but the ability to display a feature depends on the Scalar version in use. Constructs such as callbacks, webhooks, OpenAPI 3.1 schemas, and JSON Schema dialects may have varying levels of support across versions.

When upgrading the OpenAPI version:

1. Check the `openapi` field in the document.
2. Validate the document using a validator that supports that version.
3. Verify that the pinned Scalar release supports the required features.
4. Open the document and inspect operations, schemas, and security.
5. Test requests with key media types and authentication methods.
6. Check Swagger UI or other code generators if they are still part of the workflow.

Do not conclude a document is invalid just because the UI fails to render an extension. Inspect the raw JSON/YAML to distinguish contract generation errors from renderer limitations.

## 19. Vendor Extensions and Custom Metadata

OpenAPI allows vendor extensions whose names start with `x-`, such as `x-logo`, `x-tagGroups`, or organization-specific extensions. Scalar may support certain extensions to customize display, but support depends on the release and extension type.

Example extension in the document:

~~~yaml
info:
  title: Catalog API
  version: "1.4.0"
  x-logo:
    url: https://developer.example.com/assets/catalog-logo.svg
    altText: Catalog API
~~~

Not every UI handles the same vendor extension identically. Swagger UI, Scalar, generators, and validators may ignore unknown extensions.

Use extensions only for supplementary metadata. Do not place information required to understand requests/responses in a custom extension if it can be described using standard OpenAPI fields.

## 20. Verifying Scalar Working with Springdoc

After deployment, verify step by step:

1. Open `/v3/api-docs` and confirm JSON is returned.
2. Open `/v3/api-docs.yaml` if the page uses YAML.
3. Open `/scalar/` and confirm the HTML is served.
4. Check Browser Network to ensure Scalar fetches the right document URL.
5. Check the Console for CSP, CORS, or JavaScript errors.
6. Verify title, operations, schemas, security, and server URLs.
7. Try a safe operation in a test environment.
8. Verify group endpoints if multiple documents exist.
9. Verify behavior when unauthenticated and when authorized to view docs.
10. Verify URLs behind a reverse proxy/context path.

You can use MockMvc to test the documentation endpoint and static page:

~~~java
mockMvc.perform(get("/v3/api-docs"))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(
        MediaType.APPLICATION_JSON
    ));

mockMvc.perform(get("/scalar/"))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith(
        MediaType.TEXT_HTML
    ));
~~~

Static resource mapping may vary by context path and web configuration. If the application redirects `/scalar/` or uses another page, adjust the test to match the actual runtime URL.

## 21. Common Errors

| Symptom | Cause to Check |
|---|---|
| Blank Scalar page or failure to load API | Wrong `data-url` or OpenAPI endpoint is unreachable |
| HTML loads but document returns 401 | Security policy requires authentication for `/v3/api-docs` |
| Browser reports CORS error | Scalar and OpenAPI document are on different origins |
| JavaScript blocked by CSP | CDN/script/style/font/connect origin is not allowed |
| Scalar displays `localhost` URL | `servers` in the OpenAPI document is incorrect |
| Group page has no operations | Wrong group URL or Springdoc filter does not match |
| Swagger UI works but Scalar does not | Bundle version, JS error, or feature compatibility |
| Scalar works locally but fails after deploy | Context path, reverse proxy prefix, or CDN policy |
| Disabling Swagger UI also breaks Scalar | `api-docs.enabled` was disabled or static resources are not served |
| Scalar does not show webhook/extension | Renderer version does not yet fully support that construct |
| Try request blocked by browser | API server CORS or incorrect security token |
| Theme not applied | Malformed `data-configuration` or unsupported option |

When debugging, separate issues into three layers: the Scalar page, the OpenAPI document, and the API server. Check each URL directly before changing Springdoc configuration.

## 22. Migration Workflow from Swagger UI to Scalar

If currently using Swagger UI, you can migrate step by step:

1. Keep `/v3/api-docs` as the contract source.
2. Add the Scalar page at a separate URL.
3. Pin the Scalar version and verify the package license/policy per organization guidelines.
4. Compare operation, schema, and security rendering against Swagger UI.
5. Verify the Try it out/API client workflows that the team uses.
6. Check CORS, CSP, authentication, and reverse proxy.
7. Have integration teams test on staging.
8. Update links in the developer portal.
9. Disable Swagger UI only when no consumers still need it.
10. Keep OpenAPI JSON/YAML endpoints according to documentation distribution policy.

No changes to controllers or DTOs are needed just to switch UIs. If the two UIs render differently, inspect the OpenAPI document first; then determine whether the difference belongs to the renderer or the contract.

## 23. Principles for Integrating Scalar with Springdoc

When using Scalar alongside Swagger UI:

1. Keep Springdoc as the source that generates the OpenAPI contract.
2. Treat Scalar as a renderer/API reference UI, not a schema generator.
3. Keep `springdoc.api-docs.enabled=true` when Scalar needs the runtime document.
4. Point `data-url` to the right JSON/YAML endpoint or document group.
5. You can keep Swagger UI and Scalar running in parallel during migration.
6. Pin the Scalar package version or self-host assets.
7. Protect the Scalar page and OpenAPI endpoint with Spring Security based on audience.
8. Configure CORS when the UI and document are on different origins.
9. Adjust CSP to only the asset origins actually needed.
10. Verify reverse proxy, context path, and public server URLs.
11. Verify support for OpenAPI 3.1, webhooks, and vendor extensions.
12. Test both document fetching and actual API requests in the browser.

Scalar provides an alternative UI option for the OpenAPI document that Springdoc generates. Keeping the contract in a single canonical source and clearly managing URLs, versions, security, and asset policies enables the team to update the documentation experience without changing the API contract or disrupting integration clients.
