# Verifying Path, HTTP Method, operationId, and Tags

OpenAPI describes the endpoints clients can call, the supported HTTP methods, operation identifiers, and API functional groups. With springdoc-openapi, most of this contract is derived from `@RequestMapping`, `@GetMapping`, `@PostMapping`, OpenAPI annotations on controllers, and documentation configuration.

A working controller does not guarantee that the OpenAPI document describes it accurately. An endpoint may be missing due to scan configuration, a path may be wrong due to mapping composition, an `operationId` may change when a Java method is renamed, or tags may be inconsistent across operations. Conversely, the documentation may list an operation that runtime routing cannot handle as clients expect.

This lesson builds contract tests to verify the document generated by springdoc, compare paths and HTTP methods against actual routes, check `operationId` and tags, and detect contract drift in CI.

## Objectives

After this lesson, you will be able to:

- Read the `paths` structure and operations in OpenAPI JSON.
- Verify paths are composed accurately from class-level and method-level mappings.
- Check that published HTTP methods match endpoint behavior.
- Define and verify stable, unique `operationId` values within an OpenAPI document.
- Standardize tags at the controller and operation levels, and verify tag definitions.
- Write contract tests using Spring Boot Test, MockMvc, and Jackson.
- Distinguish document verification from runtime route verification.
- Verify documentation per `GroupedOpenApi`.
- Detect unexpected path/method additions, removals, or changes.
- Integrate contract checks into a CI pipeline.

## 1. What Does the Path and Operation Contract Consist Of?

In OpenAPI, `paths` is an object mapping path templates to Path Item Objects. Each path item can contain operations keyed by HTTP method. For example:

~~~yaml
paths:
  /api/products:
    get:
      operationId: listProducts
      tags:
        - products
      summary: List products
      responses:
        '200':
          description: Product list
    post:
      operationId: createProduct
      tags:
        - products
      summary: Create product
      responses:
        '201':
          description: Product created
  /api/products/{id}:
    get:
      operationId: getProductById
      tags:
        - products
      summary: Get product by ID
      responses:
        '200':
          description: Product details
~~~

In this example:

- `/api/products` and `/api/products/{id}` are path templates.
- `get` and `post` are HTTP methods, written in lowercase in OpenAPI JSON/YAML.
- `operationId` uniquely identifies an operation across the entire document.
- `tags` group operations in documentation and consuming tools.
- `summary` helps readers understand the operation's purpose.

Paths, methods, `operationId`, and tags are distinct parts of the contract. Changing any one of them can affect routing, generated SDKs, documentation, or client automation.

### 1.1. Distinguishing Server URL and Path

OpenAPI combines the server URL with the path to form the full request URL:

~~~yaml
servers:
  - url: https://api.example.com/catalog
paths:
  /products:
    get:
      operationId: listProducts
~~~

The full URL is `https://api.example.com/catalog/products`. A deployment prefix belongs in the server URL if it is a gateway base path; the path describes the resource relative to the server.

Do not place the same prefix in both `servers.url` and the path unless intended. For instance, if the server already ends with `/catalog` and the path also starts with `/catalog`, the resulting URL will duplicate the prefix.

Context paths, reverse-proxy prefixes, and server URLs can vary by environment. Contract tests should assert resource paths and server URLs separately, avoiding coupling deployment hostnames into path assertions.

## 2. How Are Paths Built from Spring Mappings?

Spring MVC combines controller-level mappings with method-level mappings. For example:

~~~java
@RestController
@RequestMapping("/api/products")
class ProductController {

    @GetMapping
    List<ProductResponse> listProducts() {
        // ...
    }

    @GetMapping("/{id}")
    ProductResponse getProduct(@PathVariable UUID id) {
        // ...
    }

    @PostMapping
    ProductResponse createProduct(
            @RequestBody CreateProductRequest request) {
        // ...
    }
}
~~~

The expected routes are:

| Class mapping | Method mapping | HTTP method | Published path |
|---|---|---|---|
| `/api/products` | `@GetMapping` | GET | `/api/products` |
| `/api/products` | `@GetMapping("/{id}")` | GET | `/api/products/{id}` |
| `/api/products` | `@PostMapping` | POST | `/api/products` |

Verify the composed path after mapping resolution, not just annotations at a single level.

### 2.1. Path Variables

With `@PathVariable`, the variable name in the path template must match the documented parameter:

~~~java
@GetMapping("/{id}")
@Operation(
    operationId = "getProductById",
    summary = "Get product by ID"
)
ProductResponse getProduct(@PathVariable("id") UUID productId) {
    // ...
}
~~~

The path in OpenAPI is `/api/products/{id}` and the parameter name is `id`. The Java variable is named `productId` because the annotation explicitly specifies `id`. Without an explicit name, parameter name inference can depend on compiler metadata and configuration. For public path variables, declaring the name explicitly keeps the contract stable.

A path parameter must be marked required in OpenAPI. This is a requirement of path templates; an optional path parameter is not a valid representation of the same route.

### 2.2. Mappings with Multiple Paths

Spring allows a single handler to map to multiple paths:

~~~java
@GetMapping({"/products", "/items"})
@Operation(
    operationId = "listProducts",
    tags = {"products"}
)
List<ProductResponse> listProducts() {
    // ...
}
~~~

Depending on how springdoc generates the document, each path is published as a Path Item operation. Because `operationId` must be unique within a document, do not assume the same ID can repeat across two paths. If one handler is published under multiple paths, inspect the actual JSON and assign distinct identifiers or design a canonical path matching your API policy.

### 2.3. Case Sensitivity and Trailing Slashes in Paths

The paths `/api/products`, `/api/Products`, and `/api/products/` can be treated as different paths in the contract. Do not rely on redirects or environment-specific path-matching options to consider them equivalent.

Choose a consistent convention, typically lowercase with no trailing slash for collection paths. Contract tests should compare exact path strings to catch unintended changes.

### 2.4. Path Filters and Hidden Endpoints

springdoc can restrict endpoints using `pathsToMatch`, `pathsToExclude`, or `packagesToScan`. A controller missing from the documentation does not guarantee the runtime route does not exist.

Annotations such as `@Hidden` or `@Operation(hidden = true)` exclude controllers/operations from OpenAPI. This is a documentation publishing decision, not a route security control. If an endpoint remains callable, verify authorization separately.

When a contract test runs on a documentation group, compare only against that group's expected path set. Do not require a public group to include internal endpoints excluded intentionally.

## 3. Verifying HTTP Methods

In OpenAPI 3.1, the standard operation methods are:

`get`, `put`, `post`, `delete`, `options`, `head`, `patch`, and `trace`.

HTTP methods are represented as lowercase properties on the Path Item Object:

~~~yaml
paths:
  /api/products/{id}:
    get:
      operationId: getProductById
    put:
      operationId: replaceProduct
    patch:
      operationId: updateProduct
    delete:
      operationId: deleteProduct
~~~

Do not confuse HTTP methods with Java method names. A Java method named `findAll` can handle GET; a method named `create` can handle POST. Contract tests must verify both the HTTP method in OpenAPI and the runtime request method.

### 3.1. Use Explicit Mappings

Prefer specialized mapping annotations:

~~~java
@GetMapping
@PostMapping
@PutMapping("/{id}")
@PatchMapping("/{id}")
@DeleteMapping("/{id}")
~~~

When using `@RequestMapping`, declare `method` explicitly:

~~~java
@RequestMapping(
    path = "/{id}",
    method = RequestMethod.DELETE
)
void deleteProduct(@PathVariable UUID id) {
    // ...
}
~~~

A mapping without a specified method can accept multiple request types at runtime. That makes the contract unpredictable and should not be used for regular resource endpoints.

### 3.2. Multiple Methods on One Path

A single path can contain multiple operations:

~~~yaml
paths:
  /api/products:
    get:
      operationId: listProducts
    post:
      operationId: createProduct
~~~

Contract tests should assert the exact set of methods for each path. Checking only that GET exists will not catch an accidentally published DELETE.

### 3.3. OpenAPI-Version-Dependent Methods

HTTP QUERY is described using the `query` operation in OpenAPI 3.2. If your project's document is OpenAPI 3.1, do not add this property as a standard method. When migrating to 3.2, verify that Springdoc, parsers, validators, Swagger UI, generators, Spring MVC/WebFlux, and gateways all handle it properly.

This lesson uses the OpenAPI 3.1 method set in the basic test examples. If your project has confirmed adoption of OAS 3.2, add `query` to the checked method set and include dedicated fixture/runtime tests.

## 4. `operationId` as a Stable Operation Identifier

`operationId` is a unique identifier for an operation within an OpenAPI document. SDK generators commonly use this value to name client methods or functions. Documentation tools and contract automation also use it to track operations across releases.

Example:

~~~yaml
paths:
  /api/products:
    get:
      operationId: listProducts
    post:
      operationId: createProduct
  /api/products/{id}:
    get:
      operationId: getProductById
~~~

### 4.1. Declaring `operationId` Explicitly

With Springdoc, you can use `@Operation(operationId = "...")`:

~~~java
@GetMapping
@Operation(
    operationId = "listProducts",
    summary = "List products",
    tags = {"products"}
)
List<ProductResponse> listProducts() {
    // ...
}
~~~

If you let Springdoc auto-generate IDs, the generated names can depend on method names, controllers, or configuration. Renaming a Java method during an internal refactor can change `operationId` and consequently rename methods in generated SDKs. For APIs with external clients, declare `operationId` explicitly to control changes.

### 4.2. Naming Conventions

Pick a consistent convention, for example:

| Action | operationId |
|---|---|
| List products | `listProducts` |
| Get by ID | `getProductById` |
| Create new | `createProduct` |
| Full replacement | `replaceProduct` |
| Partial update | `updateProduct` |
| Delete | `deleteProduct` |

Use names that express action and resource. Avoid generic IDs such as `get` or `create`, or controller-coupled names like `productControllerMethod1`.

### 4.3. Verifying Uniqueness

OpenAPI requires `operationId`, if provided, to be unique within the document. Apply a stricter project policy: every public operation must have a non-empty, stable `operationId`.

When checking, iterate over all operations in `paths`, not just the paths a specific test cares about. If the document uses webhooks or callbacks, extend the check to operations inside those constructs as well.

Do not reuse the same `operationId` for two different HTTP methods on the same path. For instance, GET and POST `/api/products` are still two separate operations and require separate IDs.

## 5. Tags for Grouping Operations

Tags organize an API by resource or business domain. For example:

~~~yaml
tags:
  - name: products
    description: Product management operations
paths:
  /api/products:
    get:
      operationId: listProducts
      tags:
        - products
~~~

Swagger UI typically uses tags to group operations into expandable/collapsible sections. SDK generators may use tags to group methods into classes or namespaces. Therefore, changing a tag can alter SDK structure even when URLs and responses remain unchanged.

### 5.1. Declaring Tags on Controllers

You can describe a controller's tag with `@Tag`:

~~~java
import io.swagger.v3.oas.annotations.tags.Tag;

@RestController
@RequestMapping("/api/products")
@Tag(
    name = "products",
    description = "Product management operations"
)
class ProductController {
    // ...
}
~~~

For a clearer contract, attach tags explicitly on each operation:

~~~java
@GetMapping
@Operation(
    operationId = "listProducts",
    tags = {"products"}
)
List<ProductResponse> listProducts() {
    // ...
}
~~~

Do not rely solely on class or package names for tag inference when group names are part of the documentation contract.

### 5.2. Tag Definitions vs. Operation Tags

OpenAPI has two related places:

- Root-level `tags` declares metadata such as group names and descriptions.
- `operation.tags` assigns an operation to one or more groups.

Tag names must match exactly between both places. Under the spec, an operation may reference a tag not declared at root, yet for documentation consistency a project can enforce a policy requiring every used tag to have a root definition.

Tag names are case-sensitive string values. `products` and `Products` should not be treated as the same tag.

### 5.3. An Operation with Multiple Tags

OpenAPI allows an operation to carry multiple tags:

~~~java
@Operation(
    operationId = "searchProducts",
    tags = {"products", "search"}
)
~~~

Use multiple tags only when an operation genuinely belongs to multiple groups. Avoid adding tags arbitrarily just to surface an operation in multiple places, as that can make documentation UIs and SDKs unpredictable.

## 6. Organizing Annotations for a Stable Contract

Example controller with explicit paths, methods, `operationId`, and tags:

~~~java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.tags.Tag;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.*;

import java.util.List;
import java.util.UUID;

@RestController
@RequestMapping("/api/products")
@Tag(
    name = "products",
    description = "Product management operations"
)
class ProductController {

    @GetMapping
    @Operation(
        operationId = "listProducts",
        summary = "List products",
        tags = {"products"}
    )
    List<ProductResponse> listProducts() {
        // Call service and return result
        return List.of();
    }

    @GetMapping("/{id}")
    @Operation(
        operationId = "getProductById",
        summary = "Get product by ID",
        tags = {"products"}
    )
    ProductResponse getProduct(@PathVariable("id") UUID id) {
        // Call service and return result
        return null;
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    @Operation(
        operationId = "createProduct",
        summary = "Create product",
        tags = {"products"}
    )
    ProductResponse createProduct(
            @RequestBody CreateProductRequest request) {
        // Call service and return result
        return null;
    }
}
~~~

`ProductResponse` and `CreateProductRequest` are application DTOs. Method bodies are simplified to focus on contract metadata; in integration tests, replace them with real service calls or appropriate mocks.

Key points to keep consistent:

- Class mapping sets the `/api/products` prefix.
- Method mapping sets the specific path.
- Spring annotations define the runtime HTTP method.
- `@Operation.operationId` sets the public identifier.
- `@Operation.tags` assigns the operation to its defined group.
- `@Tag` supplies the group description.

## 7. Fetching OpenAPI JSON in Contract Tests

Springdoc serves JSON at `/v3/api-docs` by default. If `springdoc.api-docs.path` or groups are configured, the endpoint may differ. Use the exact URL matching your application configuration.

Example dependencies for a Spring MVC application:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

In contract tests, use MockMvc to call the documentation endpoint and Jackson to parse the JSON:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class OpenApiContractTest {

    @Autowired
    MockMvc mockMvc;

    @Autowired
    ObjectMapper objectMapper;

    protected JsonNode readOpenApi() throws Exception {
        MvcResult result = mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andReturn();

        return objectMapper.readTree(
            result.getResponse().getContentAsString()
        );
    }
}
~~~

Core imports at the top of the test file:

~~~java
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import java.util.HashSet;
import java.util.Set;

import static org.junit.jupiter.api.Assertions.*;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;
~~~

If the documentation is protected by Spring Security, the test must supply an appropriate principal or test token. Never make the documentation endpoint public solely to make tests pass authorization.

## 8. Verifying Paths, Methods, operationId, and Tags with Jackson

Reading JSON into `JsonNode` lets you check structure independent of property ordering in the file. Add the following test and helpers to the same `OpenApiContractTest` class:

~~~java
private static final Set<String> HTTP_METHODS = Set.of(
    "get", "put", "post", "delete",
    "options", "head", "patch", "trace"
);

@Test
void documentsProductPathsAndOperations() throws Exception {
    JsonNode document = readOpenApi();
    JsonNode paths = document.path("paths");

    assertEquals(
        Set.of("/api/products", "/api/products/{id}"),
        fieldNames(paths)
    );

    assertEquals(
        Set.of("get", "post"),
        methodsAt(paths, "/api/products")
    );
    assertEquals(
        Set.of("get"),
        methodsAt(paths, "/api/products/{id}")
    );

    assertOperation(
        document, "/api/products", "get",
        "listProducts", "products"
    );
    assertOperation(
        document, "/api/products", "post",
        "createProduct", "products"
    );
    assertOperation(
        document, "/api/products/{id}", "get",
        "getProductById", "products"
    );

    assertEquals(
        Set.of("products"),
        tagNames(paths.path("/api/products").path("get"))
    );
    assertDeclaredTag(document, "products");
    assertUniqueOperationIds(paths);
}

private static Set<String> fieldNames(JsonNode object) {
    Set<String> names = new HashSet<>();
    object.fieldNames().forEachRemaining(names::add);
    return names;
}

private static Set<String> methodsAt(JsonNode paths, String path) {
    Set<String> methods = new HashSet<>();
    JsonNode pathItem = paths.path(path);

    for (String method : HTTP_METHODS) {
        if (pathItem.has(method)) {
            methods.add(method);
        }
    }
    return methods;
}

private static void assertOperation(
        JsonNode document,
        String path,
        String method,
        String expectedOperationId,
        String expectedTag) {

    JsonNode operation = document
        .path("paths")
        .path(path)
        .path(method);

    assertFalse(
        operation.isMissingNode(),
        () -> "Missing operation " + method + " " + path
    );
    assertEquals(
        expectedOperationId,
        operation.path("operationId").asText()
    );
    assertTrue(
        containsText(operation.path("tags"), expectedTag),
        () -> "Operation missing tag " + expectedTag
    );
}

private static boolean containsText(JsonNode array, String expected) {
    if (!array.isArray()) {
        return false;
    }
    for (JsonNode item : array) {
        if (expected.equals(item.asText())) {
            return true;
        }
    }
    return false;
}

private static Set<String> tagNames(JsonNode operation) {
    Set<String> names = new HashSet<>();
    JsonNode tags = operation.path("tags");
    if (tags.isArray()) {
        for (JsonNode tag : tags) {
            names.add(tag.asText());
        }
    }
    return names;
}

private static void assertDeclaredTag(
        JsonNode document, String expectedTag) {

    assertTrue(
        containsNamedTag(document.path("tags"), expectedTag),
        () -> "Root tag not declared: " + expectedTag
    );
}

private static boolean containsNamedTag(
        JsonNode tags, String expected) {

    if (!tags.isArray()) {
        return false;
    }
    for (JsonNode tag : tags) {
        if (expected.equals(tag.path("name").asText())) {
            return true;
        }
    }
    return false;
}
~~~

This method set fits standard OpenAPI 3.1 operations. If your project has upgraded to OAS 3.2 and uses HTTP QUERY, add `query` after verifying that your pipeline tools support it.

## 9. Verifying Global operationId Uniqueness

A dedicated helper detects duplicate IDs across paths:

~~~java
private static void assertUniqueOperationIds(JsonNode paths) {
    Set<String> seen = new HashSet<>();

    paths.fields().forEachRemaining(pathEntry -> {
        String path = pathEntry.getKey();
        JsonNode pathItem = pathEntry.getValue();

        for (String method : HTTP_METHODS) {
            JsonNode operation = pathItem.get(method);
            if (operation == null) {
                continue;
            }

            String operationId =
                operation.path("operationId").asText("");

            assertFalse(
                operationId.isBlank(),
                () -> "Operation missing operationId: "
                    + method + " " + path
            );
            assertTrue(
                seen.add(operationId),
                () -> "Duplicate operationId: " + operationId
            );
        }
    });
}
~~~

This check enforces a project policy: every operation in `paths` must have an ID. Under the specification, `operationId` is optional, though if present it must be unique. For public APIs and code generation, requiring explicit IDs keeps the contract more stable.

If the OpenAPI document has `webhooks` or callbacks containing operations, extend the check to traverse those operations too. Do not treat checking `paths` alone as exhaustive in a complex document.

## 10. Verifying Runtime Routes Alongside Documentation

Document contract tests verify what springdoc publishes. MockMvc route tests verify how the application actually handles requests. Both checks complement each other.

Example:

~~~java
@Test
void routesDocumentedProductMethods() throws Exception {
    mockMvc.perform(get("/api/products"))
        .andExpect(status().isOk());

    mockMvc.perform(
        get("/api/products/{id}",
            "11111111-1111-1111-1111-111111111111")
    ).andExpect(status().isOk());

    mockMvc.perform(post("/api/products")
            .contentType(MediaType.APPLICATION_JSON)
            .content("""
                {
                  "name": "Sample keyboard"
                }
                """))
        .andExpect(status().isCreated());
}
~~~

Required imports for the test:

~~~java
import org.springframework.http.MediaType;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;
~~~

This example assumes controllers/services process these requests and return the corresponding statuses. For protected endpoints, attach a test user or JWT. If a controller returns 404/405 while OpenAPI advertises the operation, the contract and runtime are out of sync.

### 10.1. Checking Undocumented Methods

If a path only supports GET and POST, a contract test can verify DELETE is absent from OpenAPI:

~~~java
assertFalse(
    document.path("paths")
        .path("/api/products")
        .has("delete")
);
~~~

Do not infer a method is unsupported just because a test does not call it. Verify both the OpenAPI structure and HTTP behavior. In an environment with Spring Security, requests may be rejected before reaching a handler; a 401/403 status does not prove whether a route method exists.

## 11. Verifying Tag Definitions and Grouping Conventions

A project can establish conventions such as:

- Lowercase tag names, plural form or business domain names.
- Every operation has at least one tag.
- Every used tag has a root-level definition.
- Every tag has a clear description.
- No duplicate tag names differing only by case.

These are project policies, not all mandated by OpenAPI itself. Example test checking an operation's tag:

~~~java
assertTrue(
    containsText(
        document.path("paths")
            .path("/api/products")
            .path("get")
            .path("tags"),
        "products"
    )
);
~~~

If a tag changes from `products` to `catalog`, URLs may stay identical while Swagger UI and SDK generators regroup operations. Include tags in contract diff reviews whenever clients or developer portals depend on those groupings.

### Multi-Group Tags

If an operation carries tags `products` and `search`, tests should verify both names. Do not assert the first element's index if tag order is not part of the policy. Comparing sets is less brittle against meaningless order changes.

If your project requires specific tag display ordering in Swagger UI, check root-level `tags` separately since declaration order there can be used by renderers to sort groups.

## 12. Verifying by GroupedOpenApi

When an application splits documentation into public, partner, and internal groups, each group produces a separate OpenAPI document. For example:

~~~java
@Bean
GroupedOpenApi publicApi() {
    return GroupedOpenApi.builder()
        .group("public")
        .pathsToMatch("/api/public/**")
        .pathsToExclude("/api/public/internal/**")
        .build();
}
~~~

A group named `public` is typically fetched from `/v3/api-docs/public`. Group tests should verify:

- Public paths appear.
- Internal paths are excluded from the public document.
- Methods and `operationId` values of public operations are correct.
- Public tags are declared and applied properly.
- Internal/partner documents contain their respective path sets according to policy.

Do not inspect `/v3/api-docs` and assume every group is correct. Call each group's exact endpoint and run the assertion suite on each document.

## 13. Detecting Contract Drift

Contract drift occurs when documentation changes unexpectedly or runtime behavior diverges from the released specification. The following changes warrant review:

| Change | Potential Impact |
|---|---|
| Removing a path | Existing clients can no longer call the endpoint |
| Changing a path or path variable | URL and client invocation change |
| Removing an HTTP method | Previous operation is no longer available |
| Adding an unintended method | Exposes unapproved API surface |
| Changing `operationId` | Generated SDK method names may change |
| Changing a tag | Operation moves groups in UI/SDK |
| Renaming a path parameter | Clients must update variable/argument names |
| Changing group filters | Operations may disappear from public artifacts |

### 13.1. Comparing Against a Baseline

Store the previous release's OpenAPI JSON as a versioned artifact. When building a new version:

1. Generate the new document from the application.
2. Normalize JSON to strip meaningless differences such as key ordering.
3. Compare paths and methods.
4. Compare `operationId` values and tags.
5. Compare schemas/parameters/responses if required by the contract pipeline.
6. Classify changes as breaking, non-breaking, or needing review.

Do not run plain text diffs and conclude every difference is breaking. JSON key reordering or YAML formatting changes do not necessarily alter the contract. Use an OpenAPI-aware parser or semantic diff tool to compare structure.

### 13.2. Do Not Auto-Accept New `operationId` Values

Adding a new operation is usually a contract extension, yet still requires review to confirm the endpoint is approved for public exposure. Changing an existing `operationId` can rename client SDK methods. Require reviewers to confirm the rationale and consumer update plan.

### 13.3. Snapshots vs. Targeted Assertions

Snapshotting the entire OpenAPI document can generate noisy diffs due to timestamps, schema ordering, or formatters. Use targeted assertions for core paths/methods/`operationId`/tags, and semantic diffs for everything else. Snapshots should serve as supporting evidence, not the sole gate.

## 14. Integrating Contract Tests into CI

A pipeline can execute in this order:

~~~text
Compile application
        |
        v
Start Spring test context
        |
        v
Fetch /v3/api-docs (and each group)
        |
        v
Assert paths and HTTP methods
        |
        v
Assert operationId uniqueness
        |
        v
Assert tags and group filters
        |
        v
Exercise runtime routes with MockMvc
        |
        v
Compare with released OpenAPI baseline
        |
        v
Publish document / SDK
~~~

Steps should fail clearly if a path/method is missing, an `operationId` is duplicated, or a tag violates policy. Never publish new artifacts if contract tests fail.

### 14.1. Keep Tests Independent of JSON Ordering

Jackson `JsonNode` and `Set` collections work well for checking properties whose order is insignificant. Assert ordering only when display order is an agreed requirement.

### 14.2. Check the Right Documentation Endpoint

If the application configures a custom `springdoc.api-docs.path` or groups, point tests to the exact endpoint. When documentation endpoints require authorization, tests must use the designated test authentication mechanism.

### 14.3. Preserve Contract Evidence

Archive OpenAPI artifacts and semantic diff reports per build/release. This helps trace which changes entered a release and speeds up debugging when SDKs or clients encounter issues.

## 15. Common Contract Testing Pitfalls

| Pitfall | Why It Falls Short | Fix |
|---|---|---|
| Checking only `/v3/api-docs` HTTP status | Document may be valid while paths/methods are wrong | Parse JSON and assert every operation |
| Checking only controller mappings | Misses filters/groups/hidden removing operations | Inspect OpenAPI JSON |
| Checking only Swagger UI rendering | UI can mask missing metadata or operations | Assert the document directly |
| Relying on Java method names as `operationId` | Refactoring can rename SDK methods | Declare `operationId` explicitly |
| Checking only selected `operationId`s | Other IDs may collide | Iterate through all operations in the document |
| Comparing tags by array index | Tag order may not be part of the contract | Compare sets of tags |
| Treating every tag rule as an OpenAPI spec rule | May be an internal policy rather than a spec requirement | Document internal conventions and test per policy |
| Including server prefix in path assertions | Environment differences break tests | Check `servers` and `paths` separately |
| Skipping runtime route tests | Documentation might describe non-working endpoints | Add MockMvc/WebTestClient tests |
| Testing only the default document | Public/internal groups may diverge | Test every group |
| Using verbatim text snapshots | Noisy diffs from formatting/ordering | Use JSON trees and semantic diffs |

## 16. Hands-On Exercise

Build a product management API with these operations:

| HTTP method | Path | operationId | Tag |
|---|---|---|---|
| GET | `/api/products` | `listProducts` | `products` |
| GET | `/api/products/{id}` | `getProductById` | `products` |
| POST | `/api/products` | `createProduct` | `products` |
| PUT | `/api/products/{id}` | `replaceProduct` | `products` |
| DELETE | `/api/products/{id}` | `deleteProduct` | `products` |

Steps:

1. Add class-level `@RequestMapping("/api/products")`.
2. Use specialized mapping annotations for each HTTP method.
3. Declare `@Operation(operationId = "...")` on every operation.
4. Declare the `products` tag with a clear description.
5. Call `/v3/api-docs` with MockMvc.
6. Assert the exact set of paths.
7. Assert the exact set of methods for each path.
8. Assert each operation's `operationId`.
9. Iterate over all operations to detect duplicate or blank IDs.
10. Assert every operation uses tag `products` and that the root-level tag is declared.
11. Call real routes with GET, POST, PUT, and DELETE to verify routing.
12. Create a public group and verify internal paths do not appear.
13. Rename one `operationId` temporarily and observe the contract diff.
14. Integrate tests into CI and block releases on unexpected contract changes.
