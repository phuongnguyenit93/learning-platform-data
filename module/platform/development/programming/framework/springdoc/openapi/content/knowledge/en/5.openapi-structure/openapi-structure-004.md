# Servers and Configuration Variables in Server URLs

In OpenAPI, the **servers** field describes the base address that clients use to invoke API operations. A server can be a full URL such as `https://api.example.com/v1`, a relative URL such as `/gateway/orders`, or a templated URL containing variables such as `https://{tenant}.api.example.com/{basePath}`.

When reading documentation generated by springdoc-openapi, you need to understand how the server URL is combined with paths, which values replace URL variables, and the scope of each declaration. This is critical when an API runs across multiple environments, multiple tenants, gateways, or reverse proxies.

## 1. Servers Describe the Base Address of the API

In an OpenAPI document, `servers` is an array of Server Objects. Each object describes a base address that clients can use to send requests. Example:

```json
{
  "openapi": "3.1.0",
  "info": {
    "title": "Order API",
    "version": "v1"
  },
  "servers": [
    {
      "url": "https://api.example.com/v1",
      "description": "Production API"
    },
    {
      "url": "https://staging-api.example.com/v1",
      "description": "Staging API"
    }
  ],
  "paths": {
    "/orders": {
      "get": {
        "responses": {
          "200": {
            "description": "Order list"
          }
        }
      }
    }
  }
}
```

For operation `GET /orders`, the two request addresses that can be constructed from the two servers above are:

```text
https://api.example.com/v1/orders
https://staging-api.example.com/v1/orders
```

The server URL provides the base address; the path under `paths` provides the operation path. Clients combine them to form the complete request URL.

| Component | Example | Role |
|---|---|---|
| Server URL | `https://api.example.com/v1` | Scheme, host, optional port, and base path |
| Path | `/orders/{id}` | Path of the operation |
| Query parameter | `?status=PAID` | Query value for the request |
| Complete URL | `https://api.example.com/v1/orders/42?status=PAID` | Full request address sent |

`servers` only describes URLs in the API contract. It does not open network ports, configure DNS, provision TLS certificates, or change the address Spring Boot actually binds to listen for requests.

## 2. Forms of Server URLs

OpenAPI allows declaring absolute or relative URLs.

**Absolute URLs** include a scheme and host:

```yaml
servers:
  - url: https://api.example.com/v1
    description: Production
  - url: https://staging-api.example.com/v1
    description: Staging
```

**Relative URLs** are resolved based on the OpenAPI document location or deployment context:

```yaml
servers:
  - url: /api/v1
    description: API on the same origin as the documentation
```

Relative URLs are useful when documentation and API are served under the same domain, yet placed behind different context paths or reverse proxies. Verify how client tooling resolves relative URLs in the actual environment.

A Server URL can include scheme, host, port, and base path. Example:

```text
https://api.example.com:8443/platform/orders
```

Where:

- `https` is the scheme.
- `api.example.com` is the hostname.
- `8443` is the port.
- `/platform/orders` is the server base path.

When a path item in OpenAPI is `/customers`, the final URL appends the path item to the server URL, yielding `https://api.example.com:8443/platform/orders/customers`. Avoid declaring the same path segment in both the server URL and the path item unless you want the segment duplicated.

## 3. Server Object Structure

A Server Object has a required `url` field and may have `description` and `variables`.

```yaml
servers:
  - url: https://api.example.com/v1
    description: Public API
```

| Field | Required | Meaning |
|---|---:|---|
| `url` | Yes | Absolute or relative URL of the server; may contain template variables |
| `description` | No | Short description of the server's environment or purpose |
| `variables` | No | Map of Server Variable Objects used to substitute placeholders in the URL |

Variable names in `variables` must match the placeholder names placed inside curly braces in `url`. For example, `{region}` requires a variable named `region`.

```yaml
servers:
  - url: https://{region}.api.example.com/v1
    description: Regional API
    variables:
      region:
        default: ap-southeast
        description: Deployment region
        enum:
          - ap-southeast
          - eu-central
          - us-east
```

If a server URL has a placeholder without a corresponding variable declaration, the document lacks sufficient information for clients to substitute the URL deterministically. Check variable names, casing, and default values.

## 4. Variables in Server URLs

Server variables allow a single templated URL to represent multiple addresses. The placeholder syntax is `{variableName}`.

Example:

```yaml
servers:
  - url: https://{tenant}.api.example.com/{basePath}
    description: Tenant-specific API
    variables:
      tenant:
        default: demo
        description: Tenant identifier
        enum:
          - demo
          - acme
          - globex
      basePath:
        default: v1
        description: API path version
        enum:
          - v1
          - v2
```

With this configuration, the default values produce the URL:

```text
https://demo.api.example.com/v1
```

If a user selects `tenant=acme` and `basePath=v2`, the URL resolves to:

```text
https://acme.api.example.com/v2
```

Server variables are commonly useful for:

- Tenants or customers when each tenant has its own hostname.
- Deployment regions such as `ap-southeast`, `eu-central`, or `us-east`.
- Base path versions such as `v1` and `v2`.
- Ports or fixed segments with a small set of supported values.
- Testing environments where URLs differ only partially.

Do not use server variables to represent general request input data. Path parameters, query parameters, and header parameters remain separate concepts with their own places and semantics in OpenAPI.

## 5. Server Variable default and enum

Every Server Variable Object must have a `default` field. This is the value used when the client does not pick another value. The `enum` field is optional; if declared, it constrains the set of supported values.

```yaml
servers:
  - url: https://{environment}.example.com/api/{version}
    variables:
      environment:
        default: sandbox
        enum:
          - sandbox
          - staging
          - production
      version:
        default: v1
        enum:
          - v1
          - v2
```

Rules to remember:

1. Every placeholder in the URL must have a variable of the same name in `variables`.
2. Every variable must declare `default`.
3. If `enum` is present, the `default` value must appear in that list.
4. Variable values are strings and are substituted into the URL at the exact placeholder position.
5. `description` helps readers understand the purpose and values of the variable.

The following example is semantically invalid because the default value is not in the enum:

```yaml
variables:
  environment:
    default: production
    enum:
      - sandbox
      - staging
```

Fix it by adding `production` to the enum or selecting a default value that exists in the list.

If you do not need to restrict values, you can omit `enum`:

```yaml
variables:
  tenant:
    default: demo
    description: Default tenant for testing
```

When omitting `enum`, the document does not list a fixed set of choices. That does not mean any arbitrary value exists on the system; the backend still needs to validate the actual tenant or region.

## 6. Declaring servers with springdoc Annotations

With springdoc-openapi, you can describe document-level servers using the `@OpenAPIDefinition`, `@Server`, and `@ServerVariable` annotations from `swagger-annotations`.

```java
import io.swagger.v3.oas.annotations.OpenAPIDefinition;
import io.swagger.v3.oas.annotations.servers.Server;
import io.swagger.v3.oas.annotations.servers.ServerVariable;
import org.springframework.context.annotation.Configuration;

@Configuration
@OpenAPIDefinition(
    servers = {
        @Server(
            url = "https://{tenant}.api.example.com/{basePath}",
            description = "Tenant-specific API",
            variables = {
                @ServerVariable(
                    name = "tenant",
                    defaultValue = "demo",
                    allowableValues = {"demo", "acme", "globex"},
                    description = "Tenant identifier"
                ),
                @ServerVariable(
                    name = "basePath",
                    defaultValue = "v1",
                    allowableValues = {"v1", "v2"},
                    description = "API version"
                )
            }
        )
    }
)
class OpenApiServerConfiguration {
}
```

In Java annotations:

- `@Server(url = ...)` declares the templated URL.
- `variables` declares the variables used in the URL.
- `@ServerVariable(name = ...)` must match the placeholder.
- `defaultValue` maps to the `default` field in OpenAPI.
- `allowableValues` supplies the allowed value set, mapping to `enum`.
- `description` explains the meaning of the server or variable.

After starting the application, call `/v3/api-docs` and check the `servers` section in the JSON. Do not rely only on Swagger UI displaying a dropdown; verify that the JSON has the exact URL, default, and enum as configured.

## 7. Declaring servers with an OpenAPI Model Bean

Annotations work well when the server list is fixed in source code. If the URL depends on environment configuration, you can create an `OpenAPI` model bean and read values from Spring configuration.

Example:

```java
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.info.Info;
import io.swagger.v3.oas.models.servers.Server;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.List;

@Configuration
class OpenApiConfiguration {

    @Bean
    OpenAPI orderOpenAPI(
        @Value("${app.openapi.server-url:/}") String serverUrl
    ) {
        return new OpenAPI()
            .info(new Info()
                .title("Order API")
                .version("v1"))
            .servers(List.of(
                new Server()
                    .url(serverUrl)
                    .description("Current environment server")
            ));
    }
}
```

Development environment configuration:

```yaml
app:
  openapi:
    server-url: http://localhost:8080
```

Production environment configuration:

```yaml
app:
  openapi:
    server-url: https://api.example.com
```

This approach lets the same build produce documentation with different URLs depending on the configuration loaded at runtime. Standardize on a single configuration source for OpenAPI metadata; avoid overlapping annotations and beans unless you have verified how those configurations merge in the springdoc version you use.

If you want one document to list multiple static servers, add multiple `Server` objects to the list. If you want the URL determined from the incoming request or proxy, check springdoc's default base URL resolution and forwarded headers configuration before overriding it manually.

## 8. Scope of Application: Document, Path, and Operation Levels

OpenAPI lets you declare `servers` at three scopes:

- Document level (root): applies by default to the entire API.
- Path item level: applies to the operations under that path.
- Operation level: applies specifically to a single operation.

Root-level server example:

```yaml
servers:
  - url: https://api.example.com/v1

paths:
  /orders:
    get:
      responses:
        "200":
          description: Order list
```

A path can declare its own server:

```yaml
paths:
  /internal/reports:
    servers:
      - url: https://internal.example.com/reporting
    get:
      responses:
        "200":
          description: Internal reports
```

An operation can also declare its own server:

```yaml
paths:
  /health:
    get:
      servers:
        - url: https://status.example.com
      responses:
        "200":
          description: Service status
```

When a server is declared at a more specific scope, it overrides the server list from the broader scope for that path or operation. This is helpful when public APIs and internal APIs have different hosts. Avoid setting separate servers when unnecessary, because readers may overlook that an operation uses a different host than the rest of the API.

With annotations, you can declare servers on `@OpenAPIDefinition` at the document level or inside `@Operation` for an operation. When configuring at the path item level, use the appropriate OpenAPI model or springdoc customizer to ensure the server is placed in the right position.

## 9. Distinguishing Server Variable from Path Parameter

Both concepts use placeholders in curly braces, yet they serve different purposes.

| Criterion | Server Variable | Path Parameter |
|---|---|---|
| Location | Inside the Server URL | Inside the operation path |
| Example | `https://{tenant}.example.com/v1` | `/orders/{orderId}` |
| Declaration | `servers[].variables` | `paths[path][method].parameters` or shared path parameters |
| Purpose | Choose the server address or base URL | Pass identifying data for the request |
| Default value | Required in Server Variable Object | Not a general requirement of path parameters |
| Scope | Can affect many operations | Bound to one operation or path |

Combined example:

```yaml
servers:
  - url: https://{tenant}.api.example.com/{basePath}
    variables:
      tenant:
        default: acme
      basePath:
        default: v1

paths:
  /orders/{orderId}:
    get:
      parameters:
        - name: orderId
          in: path
          required: true
          schema:
            type: string
        - name: includeItems
          in: query
          required: false
          schema:
            type: boolean
      responses:
        "200":
          description: Order details
```

If the client chooses `tenant=acme`, `basePath=v1`, `orderId=ORD-42`, and `includeItems=true`, the request looks like:

```text
GET https://acme.api.example.com/v1/orders/ORD-42?includeItems=true
```

Server variables decide where the request is sent. Path parameters and query parameters pass data for the operation after the server has been selected.

## 10. Servers Across Multiple Environments and Reverse Proxies

A project often has different addresses for local, development, staging, and production. Multiple servers can be listed in the document:

```yaml
servers:
  - url: http://localhost:8080/api
    description: Local development
  - url: https://dev-api.example.com/api
    description: Development
  - url: https://staging-api.example.com/api
    description: Staging
  - url: https://api.example.com/api
    description: Production
```

If all environments are published in one document, Swagger UI users might pick the wrong environment by mistake. For sensitive systems, consider publishing only the server matching the current environment or restricting access to the documentation.

When the application sits behind a reverse proxy or API gateway, incoming requests inside Spring Boot may see the internal scheme, host, or port instead of the public URL. That can make auto-generated server URLs in the document inaccurate.

Check the following:

- Does the proxy send accurate `Forwarded` or `X-Forwarded-*` headers?
- Does the proxy overwrite client-supplied forwarded headers to prevent host spoofing?
- Is Spring Boot configured to handle forwarded headers according to the active infrastructure?
- Does a context path or prefix added by the gateway appear in the server URL?
- Does the public URL use HTTPS while the internal connection to the application uses HTTP?

Spring Boot provides the `server.forward-headers-strategy` property to choose how forwarded headers are processed. The right value depends on the servlet container and deployment architecture; consult the Spring Boot documentation for your exact version. Never trust forwarded headers unless the proxy controls and sanitizes incoming headers.

If the server URL is configured statically via annotations or a bean, ensure the value matches the URL users can actually reach. Static configuration can hide mismatches between internal and public URLs, so verify from the client's perspective.

## 11. Distinguishing servers from Spring Boot Network Configuration

A common misconception is thinking that declaring a server in OpenAPI makes Spring Boot listen on that address. These two configurations have different purposes.

| Configuration | Effect |
|---|---|
| OpenAPI `servers[].url` | Describes the base URL for API consumers and client tools |
| `server.port` | Port the Spring Boot application listens on |
| `server.address` | Interface address the application binds to, if configured |
| `server.servlet.context-path` | Context path of the servlet application |
| Reverse proxy / gateway | Routes traffic and may rewrite external host, scheme, or prefix |

Example:

```properties
server.port=8081
server.servlet.context-path=/shop
```

The application may serve the documentation endpoint internally at:

```text
http://localhost:8081/shop/v3/api-docs
```

While the public URL may be:

```text
https://api.example.com/store/v3/api-docs
```

The OpenAPI server URL should describe the API address that clients need to use, such as `https://api.example.com/store`, rather than necessarily the internal bind address `http://localhost:8081/shop`.

## 12. Inspecting servers in JSON Generated by springdoc

After configuring, call the documentation endpoint:

```bash
curl -fsS http://localhost:8080/v3/api-docs -o openapi.json
```

Use `jq` to view the server list:

```bash
jq '.servers' openapi.json
```

List URLs and descriptions:

```bash
jq -r '.servers[] | [.url, (.description // "")] | @tsv' openapi.json
```

Check variables of the first server:

```bash
jq '.servers[0].variables // {}' openapi.json
```

You can inspect an operation-level server by querying a specific path:

```bash
jq '.paths["/health"].get.servers' openapi.json
```

If the returned value is `null`, that operation has no dedicated server and inherits the server from the appropriate scope.

When checking, verify:

- Does the URL have the right scheme, host, port, and base path?
- Does every placeholder have a corresponding variable?
- Does every variable have a `default`?
- If `enum` is present, is `default` included in `enum`?
- Are the listed servers actually deployed and reachable?
- Does the operation path duplicate any prefix from the server URL?
- Do any operations or paths have dedicated servers that need explanation?

## 13. Common Mistakes

| Symptom | Cause and What to Check |
|---|---|
| Swagger UI calls the wrong host or port | Server URL was generated from internal request or forwarded headers are not processed properly. Check proxy and `server.forward-headers-strategy`. |
| Request URL duplicates `/api/v1/api/v1` | Base path is in the Server URL and repeated in the path item. Pick one place for the prefix. |
| URL variable is not substituted | Placeholder and key in `variables` do not match, or `default` is missing. |
| Default value is rejected | `default` is not in `enum`. Synchronize both fields. |
| Swagger UI displays only one server | JSON document has only one element in `servers`, or a server declared at another scope overrides the broader list. |
| Production URL points to localhost | OpenAPI configuration uses a local URL or wrong default value in the production profile. |
| Relative URL works locally but fails behind gateway | Documentation base URL and public URL have different prefixes; check routing and where the doc is served. |
| Client reaches host but misses the API | Server URL is missing the base path or the operation path is not combined properly. |

## 14. Server URL Design Checklist

- [ ] Identified the exact URL clients actually use to call the API.
- [ ] Server URL has the correct scheme, host, port, and base path.
- [ ] Chose an absolute or relative URL suited to the deployment setup.
- [ ] Placeholders in the URL have corresponding entries in `variables`.
- [ ] Every Server Variable has a `default`.
- [ ] If `enum` is declared, `default` is included in the list.
- [ ] Server Variables are not used instead of path, query, or header parameters.
- [ ] No duplicated base path between server URL and operation path.
- [ ] Document-, path-, and operation-level servers are used at the proper scope.
- [ ] Reverse proxy and forwarded headers produce the right URL from the client's perspective.
- [ ] Checked `servers` in the actual JSON at `/v3/api-docs`.
- [ ] Every published server is an environment that documentation readers are permitted to access.
