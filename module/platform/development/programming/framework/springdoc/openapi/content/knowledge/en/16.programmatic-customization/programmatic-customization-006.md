# Adding Headers, Error Codes, or Extensions by Application Convention

A Spring Boot application often follows shared conventions across its entire API: request correlation headers, response headers for tracing, machine-readable error codes, or custom metadata processed by an API gateway and internal tooling. Repeating every convention across every controller makes OpenAPI documentation hard to maintain and prone to inconsistency.

Springdoc-openapi allows supplementing metadata through programmatic extension points such as `OpenApiCustomizer`, `GlobalOpenApiCustomizer`, `OperationCustomizer`, and `GlobalOperationCustomizer`. Customizers can modify the document after springdoc analyzes controllers: adding parameters, responses, headers, schemas, or vendor extensions. This customization only alters the OpenAPI specification; the application must still actually accept/emit headers and return the corresponding error codes at runtime.

## 1. Choosing the Right Customization Point

Springdoc has multiple customization levels. Choosing the right level keeps changes scoped properly and avoids applying metadata unintentionally.

| Mechanism | Scope | When to Use |
|---|---|---|
| `OpenAPI` bean | Document-level metadata and components | Declaring info, servers, security schemes, and shared schemas and responses. |
| `OpenApiCustomizer` | Default OpenAPI document | Modifying paths, operations, or components after generation. |
| `GlobalOpenApiCustomizer` | Default document and groups | Applying the same document-level rules across every generated document. |
| `OperationCustomizer` | Individual operations with their `HandlerMethod` | Adding parameters, responses, or extensions based on method/controller annotations. |
| `GlobalOperationCustomizer` | Operations across documents/groups | Applying operation-level rules across all groups. |

Some selection guidelines:

- Shared, stable definitions such as `components.responses` should be registered on the `OpenAPI` bean.
- Headers applying to all operations can be added at the document level using `GlobalOpenApiCustomizer`.
- Rules depending on controller/method annotations should use `GlobalOperationCustomizer` or `OperationCustomizer`.
- API-level extensions go on `OpenAPI`; endpoint-specific extensions go on `Operation`.
- If only a few endpoints follow a rule, use marker annotations or conditional customizers instead of adding metadata to every operation.

Customizer package names in springdoc 2.x/3.x generally reside under `org.springdoc.core.customizers`. Check your dependencies and imports for your major version if your IDE cannot find an interface.

## 2. Adding a Shared Request Header

Suppose all requests may send an `X-Correlation-ID` header to correlate logs across gateway, controller, and service. Because this is a request header, it should be described in an operation's `parameters` with `in: header`.

You can add the parameter with `GlobalOpenApiCustomizer`:

```java
import io.swagger.v3.oas.models.parameters.Parameter;
import io.swagger.v3.oas.models.media.StringSchema;
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import java.util.List;

@Configuration
class CommonHeaderOpenApiConfiguration {

    @Bean
    GlobalOpenApiCustomizer correlationIdHeader() {
        return openApi -> {
            if (openApi.getPaths() == null) {
                return;
            }

            openApi.getPaths().values().forEach(pathItem -> {
                boolean inherited = hasHeader(
                        pathItem.getParameters(), "X-Correlation-ID");

                pathItem.readOperations().forEach(operation -> {
                    if (!inherited && !hasHeader(
                            operation.getParameters(), "X-Correlation-ID")) {
                        operation.addParametersItem(
                                new Parameter()
                                        .in("header")
                                        .name("X-Correlation-ID")
                                        .description("Request correlation ID generated by the client or gateway")
                                        .required(false)
                                        .schema(new StringSchema())
                        );
                    }
                });
            });
        };
    }

    private static boolean hasHeader(
            List<Parameter> parameters, String headerName) {
        return parameters != null && parameters.stream().anyMatch(parameter ->
                "header".equalsIgnoreCase(parameter.getIn())
                        && headerName.equalsIgnoreCase(parameter.getName())
        );
    }
}
```

The code checks whether the header is already declared at the Path Item or Operation level before adding it. The comparison is case-insensitive because HTTP header names are case-insensitive. This avoids creating two parameters with the same name when a controller already declares the header itself.

In the application, the request header must be read or generated at runtime by an appropriate filter, interceptor, argument resolver, or controller. The customizer only informs Swagger UI and client generators that the header exists.

### 2.1. Do Not Declare `Authorization` as a Regular Header Parameter

OpenAPI has dedicated rules for authentication. Do not describe `Authorization`, `Accept`, or `Content-Type` headers using regular Parameter Objects. For Bearer tokens, API keys, or OAuth2, declare `components.securitySchemes` and attach security requirements to the document or operations.

Bearer JWT example:

```java
import io.swagger.v3.oas.models.Components;
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.info.Info;
import io.swagger.v3.oas.models.security.SecurityRequirement;
import io.swagger.v3.oas.models.security.SecurityScheme;
import org.springframework.context.annotation.Bean;

@Bean
OpenAPI securityOpenAPI() {
    return new OpenAPI()
            .info(new Info().title("Document API").version("1.0.0"))
            .components(new Components().addSecuritySchemes(
                    "bearerAuth",
                    new SecurityScheme()
                            .type(SecurityScheme.Type.HTTP)
                            .scheme("bearer")
                            .bearerFormat("JWT")
            ))
            .addSecurityItem(new SecurityRequirement().addList("bearerAuth"));
}
```

A security scheme both describes the authentication method and tells Swagger UI how to prompt for a token. Adding a parameter named `Authorization` does not replace this mechanism.

If the application already has an `OpenAPI` bean registering schemas or response components, add the security scheme to that existing bean instead of creating a second bean with duplicate configuration.
`addSecurityItem` at the document level applies the Bearer requirement to every operation. For public endpoints, declare an empty security requirement on those operations to indicate they do not require this scheme.

## 3. Adding Response Headers

Request headers are described in `parameters`; response headers are described inside the Response Object. For example, the server returns `X-Request-ID` so clients can provide an identifier when contacting support.

You can add the header to a shared response component:

```java
import io.swagger.v3.oas.models.headers.Header;
import io.swagger.v3.oas.models.media.StringSchema;
import io.swagger.v3.oas.models.responses.ApiResponse;

ApiResponse notFoundResponse = new ApiResponse()
        .description("Resource not found")
        .addHeaderObject(
                "X-Request-ID",
                new Header()
                        .description("Request ID used to look up server logs")
                        .schema(new StringSchema())
        );
```

If multiple responses return that header, place the header in a response component or use a customizer to add it to selected responses. Do not add response headers to `parameters`: the two locations have different meanings in OpenAPI.

You can add headers to already-declared error responses:

```java
import io.swagger.v3.oas.models.headers.Header;
import io.swagger.v3.oas.models.media.StringSchema;
import org.springdoc.core.customizers.GlobalOpenApiCustomizer;
import org.springframework.context.annotation.Bean;

@Bean
GlobalOpenApiCustomizer requestIdOnErrorResponses() {
    return openApi -> {
        if (openApi.getPaths() == null) {
            return;
        }

        openApi.getPaths().values().forEach(pathItem ->
                pathItem.readOperations().forEach(operation -> {
                    if (operation.getResponses() == null) {
                        return;
                    }

                    operation.getResponses().forEach((status, response) -> {
                        boolean isError = status.matches("[45][0-9]{2}")
                                || "default".equals(status);
                        if (isError) {
                            // Skip response references; declare the header in the target component.
                            if (response.get$ref() != null) {
                                return;
                            }
                            boolean alreadyDefined = response.getHeaders() != null
                                    && response.getHeaders().keySet().stream()
                                            .anyMatch(name -> name.equalsIgnoreCase("X-Request-ID"));
                            if (!alreadyDefined) {
                                response.addHeaderObject(
                                        "X-Request-ID",
                                        new Header()
                                                .description("Request ID used to look up logs")
                                                .schema(new StringSchema())
                                );
                            }
                        }
                    });
                })
        );
    };
}
```

This customizer adds the header to `4xx`, `5xx`, and `default` error responses while avoiding overwriting an existing header with the same name. For responses that are `$ref`s, the customizer skips the entry; declare the header directly in the corresponding `components.responses` to avoid creating invalid sibling fields. Only apply this rule globally if the server truly emits `X-Request-ID` on those responses. If some endpoints lack this header, restrict it by path, group, or marker annotation.

## 4. Standardizing Error Bodies and Error Codes

Error codes are usually a field in the JSON body so clients can handle them with stable logic. Example:

```json
{
  "code": "DOCUMENT_NOT_FOUND",
  "message": "Document not found",
  "traceId": "a8b7c6d5e4",
  "timestamp": "2026-11-20T10:30:00Z",
  "path": "/api/documents/42"
}
```

`code` is a machine-readable identifier stable across languages; `message` is human-readable text that may be localized; `traceId` supports tracing; `timestamp` and `path` provide context. Do not require clients to parse `message` text for business decisions because wording may change.

Create a shared DTO:

```java
import java.time.Instant;

public record ApiError(
        String code,
        String message,
        String traceId,
        Instant timestamp,
        String path
) {}
```

Register the schema in the `OpenAPI` bean:

```java
import io.swagger.v3.oas.models.Components;
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.media.Schema;
import io.swagger.v3.oas.models.media.StringSchema;
import io.swagger.v3.oas.models.media.Content;
import io.swagger.v3.oas.models.media.MediaType;
import io.swagger.v3.oas.models.info.Info;
import io.swagger.v3.oas.models.responses.ApiResponse;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ApiErrorSchemaConfiguration {

    @Bean
    OpenAPI apiErrorSchema() {
        Schema<?> errorSchema = new Schema<>()
                .type("object")
                .addRequiredItem("code")
                .addRequiredItem("message")
                .addProperty("code", new StringSchema()
                        .description("Stable error code for client handling")
                        .example("DOCUMENT_NOT_FOUND"))
                .addProperty("message", new StringSchema()
                        .description("Error message describing the failure"))
                .addProperty("traceId", new StringSchema()
                        .description("Request trace identifier"))
                .addProperty("timestamp", new StringSchema().format("date-time"))
                .addProperty("path", new StringSchema());

        Components components = new Components()
                .addSchemas("ApiError", errorSchema)
                .addResponses("BadRequest", apiErrorResponse("Invalid parameters or request body"))
                .addResponses("Unauthorized", apiErrorResponse("Unauthenticated or invalid token"))
                .addResponses("Forbidden", apiErrorResponse("Not authorized to perform this operation"))
                .addResponses("NotFound", apiErrorResponse("Resource not found"))
                .addResponses("Conflict", apiErrorResponse("Data conflicts with current state"));

        return new OpenAPI()
                .info(new Info().title("Document API").version("1.0.0"))
                .components(components);
    }

    private static ApiResponse apiErrorResponse(String description) {
        return new ApiResponse()
                .description(description)
                .content(new Content().addMediaType(
                        "application/json",
                        new MediaType().schema(
                                new Schema<>().$ref("#/components/schemas/ApiError")
                        )
                ));
    }
}
```

If the application already has another `OpenAPI` bean, merge the components into the existing bean instead of declaring multiple beans for the same purpose and relying on initialization order. Another option is to use `OpenApiCustomizer` to add schemas into `openApi.getComponents()` after checking that components exist.

### 4.1. Defining Reusable Error Responses

The bean above registers `ApiError` in `components.schemas` and five responses in `components.responses`. Each Response Object has its own description while sharing the body schema. If actual responses use `application/problem+json` or another error envelope, update the media type and schema to match.

When the application already has an `OpenAPI` bean, add schemas and responses to its existing `Components` rather than declaring a second bean. An `OpenAPI` bean is the right place for components that should appear consistently in the default document and groups.

## 5. Automatically Attaching Error Responses by Convention

Do not automatically add `404` to every operation if not every endpoint can return a not-found error. One way to control scope is using an internal annotation to mark methods or controllers that need standard responses.

Marker annotation:

```java
import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Documented
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface DocumentedApiErrors {
    String[] value() default {"400", "401", "403", "404"};
}
```

Place the annotation on a controller if every operation in that controller shares the same error set, or on a method if only one operation needs them:

```java
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import jakarta.validation.Valid;
import java.util.UUID;

@RestController
@RequestMapping("/api/documents")
class DocumentController {

    @DocumentedApiErrors({"400", "401", "403", "404"})
    @GetMapping("/{id}")
    DocumentResponse findById(@PathVariable UUID id) {
        return documentService.findById(id);
    }

    @DocumentedApiErrors({"400", "401", "403", "409"})
    @PostMapping
    DocumentResponse create(@Valid @RequestBody CreateDocumentRequest request) {
        return documentService.create(request);
    }
}
```

Create a `GlobalOperationCustomizer` to translate the annotation into response references:

```java
import io.swagger.v3.oas.models.responses.ApiResponse;
import org.springdoc.core.customizers.GlobalOperationCustomizer;
import org.springframework.core.annotation.AnnotatedElementUtils;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ApiErrorOperationCustomizerConfiguration {

    @Bean
    GlobalOperationCustomizer documentedApiErrors() {
        return (operation, handlerMethod) -> {
            DocumentedApiErrors marker = AnnotatedElementUtils.findMergedAnnotation(
                    handlerMethod.getMethod(), DocumentedApiErrors.class);

            if (marker == null) {
                marker = AnnotatedElementUtils.findMergedAnnotation(
                        handlerMethod.getBeanType(), DocumentedApiErrors.class);
            }

            if (marker == null) {
                return operation;
            }

            for (String status : marker.value()) {
                String componentName = responseComponentName(status);
                if (componentName == null) {
                    throw new IllegalArgumentException(
                            "No response component registered for status " + status);
                }

                if (operation.getResponses() == null) {
                    operation.setResponses(new io.swagger.v3.oas.models.responses.ApiResponses());
                }

                if (!operation.getResponses().containsKey(status)) {
                    operation.getResponses().addApiResponse(
                            status,
                            new ApiResponse().$ref(
                                    "#/components/responses/" + componentName)
                    );
                }
            }
            return operation;
        };
    }

    private static String responseComponentName(String status) {
        return switch (status) {
            case "400" -> "BadRequest";
            case "401" -> "Unauthorized";
            case "403" -> "Forbidden";
            case "404" -> "NotFound";
            case "409" -> "Conflict";
            default -> null;
        };
    }
}
```

The customizer above only attaches responses requested by the annotation and does not overwrite responses already declared directly on the operation. If a method already defines a `404` response with a specific schema, that explicit definition is preserved.

In the example, the list of statuses is bounded by `responseComponentName`. When adding a new error code, add the corresponding component and update the mapping. Never generate a `$ref` to a component that does not exist.

If you do not need a custom annotation, you can declare `@ApiResponse(ref = "#/components/responses/NotFound")` directly on the method. A customizer is helpful when conventions repeat across many controllers or when metadata comes from application annotations.

## 6. Adding `x-*` Vendor Extensions

OpenAPI allows adding vendor extensions to store organization-specific metadata. Extension names must begin with `x-`, for example:

- `x-owner-team`: team responsible for the operation.
- `x-audit-event`: audit event name to record.
- `x-rate-limit-tier`: rate limit tier enforced by the gateway.
- `x-internal`: marks internal metadata for build tools or portals.

Extensions can be attached at the document, operation, parameter, schema, or response level depending on where they are used. Values should be valid JSON data types such as string, boolean, number, array, or object.

### 6.1. Document-Level Extensions

```java
import org.springdoc.core.customizers.OpenApiCustomizer;
import org.springframework.context.annotation.Bean;

@Bean
OpenApiCustomizer apiCatalogMetadata() {
    return openApi -> {
        openApi.addExtension("x-api-domain", "document-management");
        openApi.addExtension("x-owner-team", "platform-documents");
        openApi.addExtension("x-contract-tier", "internal");
    };
}
```

The result appears at the OpenAPI root level:

```yaml
x-api-domain: document-management
x-owner-team: platform-documents
x-contract-tier: internal
```

### 6.2. Per-Operation Extensions

If metadata varies per endpoint, use `OperationCustomizer` or `GlobalOperationCustomizer`:

```java
import org.springdoc.core.customizers.GlobalOperationCustomizer;
import java.util.Map;

@Bean
GlobalOperationCustomizer auditMetadata() {
    return (operation, handlerMethod) -> {
        if (handlerMethod.getMethod().getName().startsWith("find")) {
            operation.addExtension("x-audit-event", "resource.read");
        } else if (handlerMethod.getMethod().getName().startsWith("delete")) {
            operation.addExtension("x-audit-event", "resource.delete");
        }
        return operation;
    };
}
```

Method-name rules are only suitable for simple examples. In larger projects, use an explicit annotation like `@AuditEvent("document.read")` so renaming a method during refactoring does not accidentally change contract metadata.

An extension can hold an object:

```java
import java.util.Map;

operation.addExtension("x-rate-limit", Map.of(
        "requests", 100,
        "windowSeconds", 60,
        "scope", "user"
));
```

This snippet requires `import java.util.Map;` and is placed inside a customizer or method that has an `operation` variable.

Only add extensions if there is a specific consumer such as an API portal, gateway plugin, internal docs, or code generation. Consumers that do not understand an extension may ignore it; never use extensions to replace standard OpenAPI fields like `security`, `parameters`, `responses`, or `deprecated`.

## 7. Using `@Extension` When Static Metadata Is Sufficient

Not every extension requires a customizer. For fixed metadata on a single operation, you can use `@Extension` and `@ExtensionProperty`:

```java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.extensions.Extension;
import io.swagger.v3.oas.annotations.extensions.ExtensionProperty;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import java.util.UUID;

@Operation(
    summary = "Get document by ID",
    extensions = @Extension(properties = {
        @ExtensionProperty(name = "x-owner-team", value = "platform-documents"),
        @ExtensionProperty(name = "x-audit-event", value = "document.read")
    })
)
@GetMapping("/{id}")
DocumentResponse findById(@PathVariable UUID id) {
    return documentService.findById(id);
}
```

Annotations suit static values, while customizers suit metadata derived from configuration, internal annotations, environments, or shared rules. Inspect the output to confirm the extension's data type matches expectations; `@ExtensionProperty` typically represents string values, whereas customizers can add typed objects, numbers, or booleans.

## 8. Avoiding Duplicates and Overwriting Metadata

Customizers may run on a document that already contains annotations or inferred metadata. Unconditionally calling `addParametersItem` or `addApiResponse` can produce duplicate entries or alter a response already specifically described by a controller.

Some safety rules:

- Check parameters by both `name` and `in`; the same name in query and header represents two distinct parameters.
- Compare header names case-insensitively.
- Check `responses.containsKey(status)` before adding a new response.
- Only add error responses to operations capable of returning those errors.
- Use component `$ref`s to avoid duplicating bodies/schemas across multiple operations.
- When modifying a shared component, assess the impact on all operations referencing it.
- Design customizers to be idempotent: running again must not create duplicates.
- Do not overwrite an explicitly declared extension if the existing value has higher precedence.

Example helper to add an extension when absent:

```java
import io.swagger.v3.oas.models.Operation;

private static void addExtensionIfAbsent(
        Operation operation, String name, Object value) {
    if (operation.getExtensions() == null
            || !operation.getExtensions().containsKey(name)) {
        operation.addExtension(name, value);
    }
}
```

If overrides should be allowed, establish a clear precedence order, such as method-level annotations overriding class-level annotations, and method metadata overriding global defaults.

## 9. Distinguishing OpenAPI Documentation from Runtime Behavior

Customizers only modify the specification. They do not implement filters, emit HTTP headers, change status codes, or generate error bodies.

| OpenAPI Change | Required Runtime Work |
|---|---|
| Add request header `X-Correlation-ID` | Filter/interceptor/controller reads or generates the correlation ID. |
| Add response header `X-Request-ID` | Response filter, interceptor, or controller actually writes the header. |
| Document `ApiError.code` | Exception handler returns a body with a stable `code` field. |
| Declare `429` response and `Retry-After` | Rate limiter/gateway returns `429` with the `Retry-After` header. |
| Add `x-rate-limit-tier` | Gateway or internal consumer understands and enforces that metadata. |
| Add security scheme | Spring Security/gateway actually protects the corresponding endpoints. |

Do not publish a header or response just to make Swagger UI look nicer. Clients may generate code from that contract and fail when the server does not behave as documented.

## 10. Verifying OpenAPI After Customization

After adding customizers, start the application and access `/v3/api-docs`. For groups, access the corresponding group documents. Check:

1. Request headers appear in `parameters` with `in: header`.
2. Response headers appear in `responses.<status>.headers`.
3. Error schemas are in `components.schemas` and response components are in `components.responses`.
4. Operations reference the right components via `$ref`.
5. Extensions have the `x-` prefix and appear at the right level.
6. There are no duplicate parameters or responses.
7. All published groups receive their expected customizers.
8. Security schemes are described with `securitySchemes`, not an `Authorization` parameter.

Example OpenAPI structure after customization:

```yaml
paths:
  /api/documents/{id}:
    get:
      parameters:
        - name: X-Correlation-ID
          in: header
          required: false
          schema:
            type: string
      responses:
        '200':
          description: Document found
        '404':
          $ref: '#/components/responses/NotFound'
      x-owner-team: platform-documents
      x-audit-event: document.read
components:
  schemas:
    ApiError:
      type: object
      required: [code, message]
      properties:
        code:
          type: string
        message:
          type: string
        traceId:
          type: string
  responses:
    NotFound:
      description: Resource not found
      headers:
        X-Request-ID:
          schema:
            type: string
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/ApiError'
```

This is an illustrative example. Actual component, schema, and extension names must match your application's configuration and conventions.

## 11. Testing Customizations with Integration Tests

You can use MockMvc to verify the generated JSON document. Example testing a request header and extension:

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;
import org.junit.jupiter.api.Test;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class OpenApiCustomizationTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void addsCommonHeaderAndOperationExtensions() throws Exception {
        mockMvc.perform(get("/v3/api-docs"))
                .andExpect(status().isOk())
                .andExpect(jsonPath(
                        "$.paths['/api/documents/{id}'].get.parameters[?(@.name=='X-Correlation-ID')]"
                ).isNotEmpty())
                .andExpect(jsonPath(
                        "$.paths['/api/documents/{id}'].get['x-owner-team']"
                ).value("platform-documents"));
    }
}
```

For response components, check both the definition and the reference:

```java
@Test
void documentsReusableNotFoundResponse() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andExpect(jsonPath(
                    "$.components.responses.NotFound.description"
            ).exists())
            .andExpect(jsonPath(
                    "$.paths['/api/documents/{id}'].get.responses['404']['$ref']"
            ).value("#/components/responses/NotFound"));
}
```

OpenAPI tests do not replace runtime HTTP tests. Verify that requests carry correlation IDs, responses include request IDs, and exception handlers actually return the expected `ApiError` and status codes.

## 12. Common Mistakes

- **Adding `Authorization` as a header parameter**: use OpenAPI security schemes and security requirements.
- **Confusing request headers with response headers**: request headers go in `parameters`; response headers go in the Response Object.
- **Adding a header to every operation when the server does not handle it**: documentation and runtime drift apart.
- **Attaching `404` to every endpoint**: some operations cannot return `404`; use annotations or filtering rules.
- **Referencing an unregistered response component**: `$ref` fails to resolve.
- **Overwriting an already declared response**: customizer erases custom schemas or descriptions; check the key before adding.
- **Using extensions instead of standard fields**: when OpenAPI already provides `security`, `deprecated`, `tags`, or `responses`, use standard fields.
- **Extensions with no consumers**: metadata unused by any tool clutters the specification; document purpose and ownership.
- **Using `OpenApiCustomizer` expecting it to apply to all groups**: choose `GlobalOpenApiCustomizer` when processing all group documents.
- **Non-idempotent customizers**: multiple runs can introduce duplicate parameters or extensions.
- **Not verifying runtime**: OpenAPI displays headers or error codes, yet controllers/filters do not emit matching data.

## 13. Workflow for Implementing API Conventions

1. **Define conventions**: specify exact header names, error codes, error bodies, and extensions to publish.
2. **Choose scope**: entire API, one group, one controller, or one operation.
3. **Register shared components**: error schemas, responses, security schemes, or document-level metadata.
4. **Choose customizers**: document-level or operation-level; use global variants when applying across groups.
5. **Prevent overwrites**: check existing parameters, responses, and extensions before adding.
6. **Sync runtime**: implement matching filters/interceptors, exception handlers, rate limiters, or security policies.
7. **Inspect `/v3/api-docs`**: verify locations, schemas, `$ref`s, headers, and extensions.
8. **Run HTTP tests**: confirm the server actually reads/writes headers and returns the documented statuses/bodies.
9. **Review consumers**: ensure gateways, SDK generators, or portals understand any extensions.

## 14. Review Checklist

- [ ] Request headers are declared in the proper location with `in: header`.
- [ ] Response headers are declared in the corresponding responses.
- [ ] Regular parameters are not used for `Authorization`, `Accept`, or `Content-Type`.
- [ ] Error bodies have stable error codes and shared schemas.
- [ ] Response components are registered before operations reference them.
- [ ] Error codes are attached only to operations capable of returning those statuses.
- [ ] Extensions are prefixed with `x-`, placed at the right level, and have clear consumers.
- [ ] Customizer scope matches either the default document or all groups.
- [ ] Logic avoids duplicates and does not overwrite explicit metadata.
- [ ] Runtime filters/interceptors/exception handlers enforce the published conventions.
- [ ] `/v3/api-docs` and all groups have been inspected.
- [ ] Integration tests verify both OpenAPI output and real HTTP responses.
