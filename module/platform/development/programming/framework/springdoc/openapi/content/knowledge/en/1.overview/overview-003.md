# JSON or YAML Documentation and Interactive UI

## 1. Role of the OpenAPI Document in a Spring Boot Application

An HTTP API needs a clear contract so clients know which endpoints exist, how to send parameters and request bodies, what responses to expect, which data types are used, and how to authenticate. If the contract lives only in source code or is documented manually elsewhere, the documentation easily drifts from the application's actual behavior.

Springdoc OpenAPI helps generate an OpenAPI document from a Spring Boot application. The library analyzes request mappings, controller methods, DTOs, Jackson metadata, Bean Validation, and Swagger annotations to describe the API as a structured document.

In the SPRINGDOC_OPENAPI module, the goal is to use springdoc-openapi to generate and customize OpenAPI specifications and Swagger UI from Spring Boot controllers. The documentation needs to describe requests, responses, schemas, security, document groups, JSON/YAML export, contract testing, version management, and API document distribution.

The overall flow can be viewed as follows:

~~~text
Spring Boot application
  |
  +-- Controllers / request mappings
  +-- DTOs / Jackson / Bean Validation
  +-- Swagger annotations / OpenAPI configuration
  |
  v
Springdoc OpenAPI
  |
  +--> OpenAPI JSON
  +--> OpenAPI YAML
  |
  +--> Swagger UI reads OpenAPI document
  |
  +--> CI, validator, code generator, API catalog
~~~

The OpenAPI document is a machine-readable contract. Swagger UI is an interface that helps humans explore and try the API based on that contract.

## 2. Distinguishing OpenAPI, JSON/YAML, and Swagger UI

These concepts often appear together, yet play distinct roles:

| Component | Role |
|---|---|
| OpenAPI Specification | Standard for describing HTTP APIs in a unified structure |
| OpenAPI document | A specific document conforming to the OpenAPI standard |
| JSON | One serialization format for an OpenAPI document |
| YAML | Another serialization format for an OpenAPI document |
| Springdoc OpenAPI | Generates and customizes the document from a Spring application |
| Swagger UI | Browser interface that reads the document and supports trying requests |

JSON and YAML are not two different types of contracts. They represent the same OpenAPI model; the main difference is syntax and presentation.

JSON is convenient for scripts, API tooling, and automated processing. YAML is often easier to read when reviewing pull requests or inspecting deeply nested schemas.

Swagger UI is not a contract generator. It reads the document generated by Springdoc and displays operations, parameters, request bodies, responses, schemas, and security metadata.

If the JSON/YAML is wrong, Swagger UI will usually display wrong information as well. Changing the UI does not fix errors in the contract.

## 3. Where Does Springdoc Generate Documentation From?

Springdoc combines multiple information sources in the application:

- Spring MVC or WebFlux request mappings.
- HTTP method names and paths from mapping annotations.
- Path variables, query parameters, headers, and cookie parameters.
- Request body and response types.
- DTOs, Java records, enums, and generic types.
- Jackson annotations and serialization settings.
- Bean Validation constraints such as @NotNull, @NotBlank, @Size, @Min, and @Pattern.
- Swagger annotations such as @Operation, @ApiResponse, @Parameter, @Schema, and @Tag.
- OpenAPI beans, customizers, and document group configurations.

For example, the following controller provides initial information for Springdoc to describe an operation:

~~~java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @GetMapping("/{id}")
    public OrderResponse getOrder(@PathVariable String id) {
        return orderService.getOrder(id);
    }
}
~~~

Springdoc can recognize the GET /api/orders/{id} operation, the id parameter, and the OrderResponse return type.

However, the framework cannot automatically understand every business rule. Details such as the meaning of order statuses, error conditions, business limits, or how tokens are used must be additionally described using annotations, schema descriptions, or OpenAPI configuration.

## 4. Installing Springdoc for Spring MVC or WebFlux

For Springdoc lines targeting Spring Boot 3, the starter dependency for Spring MVC is typically:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>PINNED_VERSION</version>
</dependency>
~~~

For a Spring WebFlux application, use the corresponding starter:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webflux-ui</artifactId>
    <version>PINNED_VERSION</version>
</dependency>
~~~

Replace PINNED_VERSION with a version pinned according to the official compatibility matrix for the Springdoc, Spring Boot, and Java versions in use.

Do not mix the WebMVC starter with a WebFlux application or vice versa. Also do not mix legacy Springdoc 1.x dependency generations with 2.x starters. Spring Boot 2 or Spring Boot 4 projects may require different artifact/version lines; check the corresponding documentation before adding dependencies.

Starters with the ui suffix typically bundle both the OpenAPI endpoint and Swagger UI. If only the API document is needed for CI or a code generator, choose the API module matching the version line so you do not package an unnecessary UI.

## 5. Default JSON and YAML Endpoints

With default configuration, Springdoc typically provides:

~~~http
GET /v3/api-docs
GET /v3/api-docs.yaml
~~~

The JSON endpoint returns the OpenAPI document in JSON format. The YAML endpoint returns the same document in YAML format.

Example invocation from the terminal:

~~~bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs \
  --output openapi.json

curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs.yaml \
  --output openapi.yaml
~~~

Use --fail so the command fails when the server returns an error HTTP status. In pipelines, also check that the file is non-empty and its content is genuinely OpenAPI; an HTML login page can return status 200 without being a valid document.

The endpoints can be changed via Springdoc configuration. If the project changes the path, CI tools, Swagger UI, Scalar, or code generators must use the new URL.

## 6. Swagger UI as an Interactive Interface

When using the UI starter, Swagger UI is typically accessed via:

~~~text
/swagger-ui.html
/swagger-ui/index.html
~~~

The first path usually redirects to the index page. The actual URL may vary depending on swagger-ui.path configuration, context path, or reverse proxy.

Swagger UI reads the OpenAPI document and renders:

- List of tags and operations.
- HTTP methods and endpoint paths.
- Summaries and descriptions.
- Path, query, header, and cookie parameters.
- Request bodies and content types.
- Response statuses, headers, and response schemas.
- Security schemes and authentication requirements.
- Schemas under components.

Users can expand an operation to view details and use Try it out to send test requests.

Try it out actually calls the API server described in the document. It is not an offline simulation. Therefore, choose a safe environment and avoid sending operations with side effects to production without controlled procedures.

## 7. What Sections Make Up an OpenAPI Document?

Condensed document example:

~~~yaml
openapi: 3.1.0
info:
  title: Order API
  version: "1.2.0"
  description: Order management API

servers:
  - url: https://api.example.com

tags:
  - name: Orders
    description: Operations on orders

paths:
  /api/orders/{id}:
    get:
      tags:
        - Orders
      summary: Get order information
      operationId: getOrderById
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        "200":
          description: Order found
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/OrderResponse"

components:
  schemas:
    OrderResponse:
      type: object
      properties:
        id:
          type: string
        status:
          type: string
~~~

Key sections:

| Section | Content |
|---|---|
| openapi | OpenAPI Specification version used by the document |
| info | API name, version, and description |
| servers | Base URLs for clients to call the API |
| tags | Operation groups |
| paths | Endpoints, methods, parameters, requests, and responses |
| components | Reusable schemas, responses, parameters, and security schemes |
| security | Security requirements at the document or operation level |
| externalDocs | Links to supplementary documentation |

Do not confuse the openapi field with info.version. The openapi field describes the OpenAPI specification version; info.version is the API contract version published by the team.

## 8. Describing API Information with an OpenAPI Bean

General information can be provided via an OpenAPI bean:

~~~java
@Configuration
public class OpenApiConfiguration {

    @Bean
    OpenAPI orderOpenAPI() {
        return new OpenAPI()
            .info(new Info()
                .title("Order API")
                .version("1.2.0")
                .description(
                    "API for managing the order lifecycle."
                )
            )
            .servers(List.of(
                new Server()
                    .url("https://api.example.com")
                    .description("Production")
            ));
    }
}
~~~

This bean helps control metadata that Springdoc cannot infer from controllers, such as title, contract version, overview description, and server URLs.

Do not hard-code production URLs if the same artifact must run across multiple environments. URLs can come from profile configuration or environment properties, while ensuring the OpenAPI document exported in CI uses the canonical base URL per policy.

When using multiple document groups, determine which metadata is shared and which is specific per group. Do not let a public document accidentally carry internal API server URLs or descriptions.

## 9. Describing Operations with Annotations

The @Operation annotation adds semantics to each method:

~~~java
@GetMapping("/{id}")
@Operation(
    operationId = "getOrderById",
    summary = "Get order information",
    description = "Returns order details by identifier."
)
public OrderResponse getOrder(@PathVariable String id) {
    return orderService.getOrder(id);
}
~~~

The fields play different roles:

- operationId is the stable identifier of the operation, often used by client generators.
- summary is a short description shown in the operation list.
- description explains usage details.
- tags categorizes operations in the UI.
- deprecated marks an operation as no longer recommended for use.

Do not let operationId change arbitrarily with method names or refactors if client SDKs depend on this value. For public APIs, operationId should follow a convention and be checked in CI.

## 10. Describing Requests and Responses

OpenAPI needs to tell clients what data must be sent and what data can be received.

Example DTOs:

~~~java
public record CreateOrderRequest(
    @NotBlank
    String customerId,

    @NotEmpty
    List<@Valid OrderLineRequest> lines
) {
}

public record OrderLineRequest(
    @NotBlank
    String productId,

    @Min(1)
    int quantity
) {
}

public record OrderResponse(
    String id,
    String status,
    Instant createdAt
) {
}
~~~

Springdoc can use Java types and Bean Validation to infer schemas. You can add @Schema to explain fields:

~~~java
public record CreateOrderRequest(
    @Schema(
        description = "ID of the customer creating the order",
        example = "CUS-1001"
    )
    @NotBlank
    String customerId
) {
}
~~~

Examples help readers understand data formats and semantics. Do not use production data or real personal information in examples.

If requests and responses have different structures, use separate DTOs. Do not reuse one class just because a few fields overlap, if clients need clarity on which fields are sent and which are returned.

## 11. When Should You Use JSON vs YAML?

| Need | JSON | YAML |
|---|---|---|
| CI and scripts | Very suitable | Suitable if supported by tools |
| Manual review | Readable, but bracket-heavy | Often easier to read |
| Code generation | Widely supported | Widely supported |
| Storing release artifacts | Suitable | Suitable |
| Debugging with jq | Yes | Requires parsing/conversion first |
| Comments in file | Standard JSON does not support comments | Supports comments |

Both formats should represent the same contract. If JSON and YAML differ in content, check the export process, customizers, or how the files are saved.

You can choose one canonical format for CI and also publish the other for human readers. Avoid editing JSON and YAML independently by hand, as they will drift apart over time.

## 12. Configuring API Docs and Swagger UI Paths

Configuration example:

~~~yaml
springdoc:
  api-docs:
    enabled: true
    path: /v3/api-docs
  swagger-ui:
    enabled: true
    path: /swagger-ui.html
~~~

api-docs.enabled enables/disables the OpenAPI endpoint. api-docs.path changes the document path. swagger-ui.enabled controls the Swagger UI interface. swagger-ui.path adjusts the UI URL according to configuration supported by the version.

You can disable Swagger UI while keeping the OpenAPI endpoint so other tools can read the document:

~~~yaml
springdoc:
  api-docs:
    enabled: true
  swagger-ui:
    enabled: false
~~~

This is useful when production does not need an interactive UI, while CI, a developer portal, or an API catalog still needs the contract. However, the API docs endpoint must still be protected if the document contains internal information.

## 13. Grouping APIs into Multiple Documents

A large application may serve APIs for multiple audiences:

- Public API for customers.
- Partner API for partners.
- Internal API for internal services.

Springdoc supports grouping operations with GroupedOpenApi:

~~~java
@Bean
GroupedOpenApi publicApi() {
    return GroupedOpenApi.builder()
        .group("public")
        .pathsToMatch("/api/public/**")
        .build();
}

@Bean
GroupedOpenApi partnerApi() {
    return GroupedOpenApi.builder()
        .group("partner")
        .pathsToMatch("/api/partner/**")
        .build();
}
~~~

Document groups have their own endpoints, typically structured as:

~~~text
/v3/api-docs/public
/v3/api-docs/partner
~~~

Each group can be exported and checked separately. Verify the actual endpoint against the Springdoc version and application path configuration.

Group filters split document content, but do not replace authorization. An internal endpoint must still be protected at runtime even if it does not appear in the public document.

## 14. Describing Security in OpenAPI

OpenAPI can describe how clients send credentials. Example using a bearer token:

~~~java
@Configuration
@SecurityScheme(
    name = "bearerAuth",
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT"
)
public class ApiSecurityConfiguration {
}
~~~

Attach a security requirement to an operation:

~~~java
@GetMapping("/{id}")
@Operation(
    summary = "Get order",
    security = @SecurityRequirement(name = "bearerAuth")
)
public OrderResponse getOrder(@PathVariable String id) {
    return orderService.getOrder(id);
}
~~~

A security scheme describes the contract; it does not configure Spring Security itself. The application must still validate tokens, check roles/scopes, and reject invalid requests.

Swagger UI can display an Authorize button for users to enter credentials. Do not embed real tokens in OpenAPI examples, descriptions, or UI configurations.

## 15. Using Swagger UI to Try Requests

Try it out lets users:

1. Select an operation.
2. Enter path/query/header parameters.
3. Enter a request body.
4. Choose a server URL.
5. Enter credentials if required by the operation.
6. Send the request.
7. Inspect HTTP status, response headers, and body.

This is a useful tool for quickly checking the API contract and helping integrators understand real requests.

However, trying a request sends a real request to the backend. A POST can create data, a PUT can update resources, and a DELETE can delete data. Use a staging or test environment with recoverable data.

If the browser reports CORS errors, check the Swagger UI origin and policy on the API server. If requests go to the wrong host, check the servers field in the OpenAPI document and reverse proxy configuration.

## 16. Securing Swagger UI and API Docs

Swagger UI and OpenAPI endpoints can expose:

- Internal endpoints.
- Request/response schemas.
- Security schemes.
- Dependent system names.
- Server URLs.
- Administrative operations.

Not every API should expose its documentation publicly to all users.

Docs URLs can be protected with Spring Security:

~~~java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers(
            "/swagger-ui/**",
            "/swagger-ui.html",
            "/v3/api-docs",
            "/v3/api-docs/**"
        ).hasRole("API_DOCS")
        .anyRequest().authenticated()
    );

    return http.build();
}
~~~

This example illustrates Servlet Security. A real application must integrate with the existing filter chain, login mechanism, CSRF, and CORS.

Disabling Swagger UI does not mean API docs are hidden. If /v3/api-docs remains open, clients can still download the document directly.

## 17. Using the Document Outside the Application

The OpenAPI document does not only serve Swagger UI. It is also input for many tools:

- OpenAPI Generator to generate client SDKs or server stubs.
- Validators to check document structure.
- Linters to enforce naming conventions and governance.
- Contract tests to compare the API implementation with the specification.
- API gateways or developer portals.
- Breaking-change comparison tools.
- Catalog systems to manage APIs by service and version.

Therefore, the OpenAPI document needs to be stable and traceable. It should not be treated as a temporary file just for Swagger UI rendering.

At release time, store the document alongside the API contract version, application artifact version, source revision, and checksum according to organizational release policy.

## 18. Validating the OpenAPI Document in CI

A basic pipeline can:

1. Build the application from the current commit.
2. Run unit/integration tests.
3. Start the exact artifact with the contract profile.
4. Wait for the application to become ready.
5. Fetch /v3/api-docs or /v3/api-docs.yaml.
6. Verify the file is non-empty and parseable.
7. Validate against the OpenAPI Specification version.
8. Lint according to organizational conventions.
9. Compare against a baseline to detect breaking changes.
10. Store the artifact after all gates pass.

Example:

~~~bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs.yaml \
  --output target/openapi.yaml

test -s target/openapi.yaml

openapi-generator-cli validate \
  -i target/openapi.yaml

oasdiff breaking \
  previous/openapi.yaml \
  target/openapi.yaml
~~~

Tools must be version-pinned in CI. The baseline must belong to the same service, audience, and document group.

If fetching or validation fails, the pipeline must stop and not publish the candidate. Do not use an old document as a fallback for a new build.

## 19. Common Errors When Using JSON/YAML and Swagger UI

| Symptom | Causes to Check |
|---|---|
| /v3/api-docs returns 404 | API docs disabled or path configured differently |
| Swagger UI opens but shows no operations | Wrong document URL or empty OpenAPI document |
| Swagger UI reports a parse error | Invalid JSON/YAML or unsupported version |
| JSON works but YAML fails to load | Wrong YAML endpoint or export configuration |
| Swagger UI displays localhost | Incorrect server URL or forwarded headers |
| Try it out hits CORS errors | API server does not allow the UI origin |
| Docs endpoint returns 401/403 | Spring Security does not permit the current user |
| Schema missing fields | Jackson visibility, DTO accessors, or annotations |
| Operation missing responses | Responses/errors not fully documented |
| Document group missing endpoints | pathsToMatch or packagesToScan do not match |
| CI receives HTML instead of JSON | Login redirect or proxy error page |
| Client generator produces wrong models | Inaccurate schema, enum, type, or component name |

When debugging, inspect the OpenAPI JSON/YAML directly first. Only then inspect Swagger UI. This separates errors in document generation from errors in the renderer.

## 20. Daily Workflow with Springdoc

A practical workflow:

**When adding an endpoint**

- Create the controller mapping and DTOs.
- Add input validation.
- Add summary, description, operationId, and responses.
- Describe security requirements if needed.
- Fetch JSON/YAML to check operations and schemas.

**When changing a DTO**

- Check Jackson serialization.
- Check required, nullable, enum, and format.
- Inspect components.schemas and $refs.
- Compare the contract with the previous release.

**When releasing**

- Export the document from the exact application artifact.
- Validate and lint.
- Check for breaking changes.
- Attach the API contract version and source revision.
- Store JSON/YAML with the release.

**When supporting clients**

- Use Swagger UI to explore and try requests.
- Provide JSON/YAML documents for code generators.
- Publish migration guides when contracts change.
- Protect documentation by audience.

## 21. Documentation Quality Checklist

Before considering an OpenAPI document ready for clients:

- Title and API contract version are meaningful.
- Server URL matches the environment.
- Every operation has a summary and a stable operationId.
- Parameters are described with accurate locations and data types.
- Request bodies have appropriate schemas and required flags.
- Responses have necessary status codes and media types.
- Error responses are documented consistently.
- Schemas have accurate types, formats, enums, and validation constraints.
- Security schemes match runtime authentication mechanisms.
- Components and $refs resolve cleanly.
- Document groups contain only operations meant for that audience.
- JSON/YAML validates successfully.
- No secrets or production data appear in examples.
- Contract diff has been reviewed.

Swagger UI makes documentation easier to view, yet contract quality still depends on the schemas and metadata supplied by the application.

## 22. Principles for Using JSON/YAML Documentation and Interactive UI

When implementing Springdoc OpenAPI:

1. Treat the OpenAPI document as the official API contract.
2. Use JSON for automated processing and YAML for review when appropriate.
3. Keep Springdoc as the document generator from controllers and models.
4. Use Swagger UI to explore and test requests in a safe environment.
5. Distinguish the OpenAPI Specification version from the API contract version.
6. Clearly describe operations, parameters, requests, responses, and security.
7. Separate document groups by audience while still protecting endpoints at runtime.
8. Inspect JSON/YAML directly before debugging the UI.
9. Validate, lint, and diff contracts in CI.
10. Publish the document alongside its corresponding source revision and application artifact.

JSON/YAML provides a contract readable by machines and tools; Swagger UI provides an interface for humans to explore and test the API. When Springdoc generates the document from accurate controllers, DTOs, validation, and security metadata, and the development team verifies the document before release, documentation stays aligned with API behavior and reliably supports client integration.
