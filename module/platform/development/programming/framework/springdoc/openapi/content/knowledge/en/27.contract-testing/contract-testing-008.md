# Contract Testing Generated Specs with MockMvc in Servlet Applications

In a Spring MVC application running on the Servlet stack, `MockMvc` dispatches requests through `DispatcherServlet`, handler mappings, controllers, converters, and exception handlers directly inside tests. There is no need to open an HTTP port or start an embedded server. This makes it convenient to test the contract in two places: live endpoint responses and the OpenAPI document generated by springdoc from controllers.

A test confirming only that a controller returns `200` does not prove the OpenAPI document describes that response properly. Conversely, testing `/v3/api-docs` alone does not prove the endpoint actually returns the right status and `Content-Type`. Use the same test context to verify both sides and cross-check them against each other.

## 1. What Does MockMvc Test?

In a Servlet application, a request flows through these core components:

1. `MockMvc` builds a simulated HTTP request.
2. `DispatcherServlet` resolves the matching handler.
3. The controller executes and returns a result.
4. `HttpMessageConverter` writes the response body and `Content-Type`.
5. `@ControllerAdvice` handles exceptions if thrown.
6. The test asserts status, headers, and body.

springdoc also runs inside the Spring application context, collecting metadata from controllers, annotations, and configuration. Thus, the same test context can call `/v3/api-docs`, parse the JSON document, and assert documented status codes and media types.

`MockMvc` does not open a real HTTP socket. It tests Spring MVC request handling inside the application context. When you need to verify reverse proxies, TLS, Servlet containers, gateways, or external deployment configuration, add smoke tests over a real HTTP server in an appropriate environment.

## 2. Preparing Dependencies and the Test Context

The application needs Spring MVC, springdoc WebMVC, and Spring Boot Test:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springdoc</groupId>
        <artifactId>springdoc-openapi-starter-webmvc-api</artifactId>
        <version>SPRINGDOC_VERSION</version>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>

    <!-- Required only if tests use Spring Security / @WithMockUser -->
    <dependency>
        <groupId>org.springframework.security</groupId>
        <artifactId>spring-security-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
~~~

If Swagger UI is also needed in the application, use `springdoc-openapi-starter-webmvc-ui`; the UI starter already includes OpenAPI document generation. Use the API starter alone when tests and consumers only need the JSON/YAML documentation endpoints.

Pick a springdoc release line compatible with your Spring Boot version. `spring-boot-starter-test` provides JUnit Jupiter, MockMvc, JSONPath, AssertJ, and Mockito integration.

### Using a Full Application Context

To verify documents generated by springdoc, the minimal setup is:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class MvcTestSetup {

    @Autowired
    MockMvc mockMvc;
}
~~~

This is an abbreviated setup skeleton; complete tests follow in the next sections.

`@SpringBootTest` loads the full application context, including springdoc auto-configuration and beans. `@AutoConfigureMockMvc` configures `MockMvc` to dispatch requests through Servlet MVC without booting an embedded server.

`@WebMvcTest` works well when testing an isolated controller slice. However, slice tests do not necessarily load all springdoc auto-configuration and beans. When the goal is testing `/v3/api-docs` generated by the application, use a full context or explicitly import the required configuration. Never conclude springdoc is broken simply because an MVC slice test lacks the documentation endpoint.

## 3. Sample Controller with a Clear Response Contract

Suppose an order-lookup API has two outcomes: finding the order returns `200 application/json`; missing orders return `404 application/problem+json`.

DTO:

~~~java
public record OrderResponse(
    long id,
    String status
) {}
~~~

Controller:

~~~java
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.media.Content;
import io.swagger.v3.oas.annotations.media.Schema;
import io.swagger.v3.oas.annotations.responses.ApiResponse;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping(
        value = "/{id}",
        produces = MediaType.APPLICATION_JSON_VALUE
    )
    @Operation(
        operationId = "getOrderById",
        summary = "Get order by ID",
        responses = {
            @ApiResponse(
                responseCode = "200",
                description = "Order found",
                content = @Content(
                    mediaType = MediaType.APPLICATION_JSON_VALUE,
                    schema = @Schema(implementation = OrderResponse.class)
                )
            ),
            @ApiResponse(
                responseCode = "404",
                description = "Order not found",
                content = @Content(
                    mediaType = MediaType.APPLICATION_PROBLEM_JSON_VALUE,
                    schema = @Schema(implementation = ProblemDetail.class)
                )
            )
        }
    )
    public OrderResponse getById(@PathVariable long id) {
        return orderService.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }
}
~~~

Exception handler:

~~~java
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(
            OrderNotFoundException exception) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND,
            exception.getMessage()
        );
        problem.setTitle("Order not found");

        return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .contentType(MediaType.APPLICATION_PROBLEM_JSON)
            .body(problem);
    }
}
~~~

`produces` is a Spring mapping condition affecting runtime content negotiation. `@ApiResponse` describes responses in OpenAPI. The exception handler controls the actual error response. Tests must confirm all three stay aligned.

## 4. Testing the OpenAPI Endpoint with MockMvc

First, invoke the springdoc documentation endpoint:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class OpenApiContractMvcTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void apiDocsEndpointReturnsOpenApiJson() throws Exception {
        mockMvc.perform(
                get("/v3/api-docs")
                    .accept(MediaType.APPLICATION_JSON)
            )
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(
                MediaType.APPLICATION_JSON
            ))
            .andExpect(jsonPath("$.openapi").exists())
            .andExpect(jsonPath("$.info.title").exists())
            .andExpect(jsonPath("$.paths").exists());
    }
}
~~~

This test verifies the documentation endpoint itself:

- HTTP status is `200`.
- Response `Content-Type` is compatible with `application/json`.
- Body contains `openapi`, `info`, and `paths`.

If your project changes `springdoc.api-docs.path`, replace `/v3/api-docs` with your configured path. If documentation is split into groups, call `/v3/api-docs/{groupName}` to verify the target document.

Do not assert status `200` alone: a reverse proxy or error handler can return HTML with a 200 status. Asserting both `Content-Type` and JSON structure confirms the endpoint actually returned an OpenAPI document.

## 5. Verifying Generated Response Codes and Media Types

A valid OpenAPI document might still omit expected responses. Assert `paths`, `responses`, and `content` directly:

~~~java
@Test
void generatedDocumentDeclaresOrderResponseContract() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.operationId"
        ).value("getOrderById"))
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['200'].description"
        ).value("Order found"))
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['200'].content['application/json']"
        ).exists())
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['404'].description"
        ).value("Order not found"))
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['404'].content['application/problem+json']"
        ).exists());
}
~~~

These assertions lock down critical contract elements:

| JSONPath | What Is Verified |
|---|---|
| `paths['/api/orders/{id}'].get.operationId` | Operation has a stable ID |
| `responses['200'].description` | Success response is present |
| `responses['200'].content['application/json']` | `200` response advertises JSON |
| `responses['404'].description` | Not-found error response is present |
| `responses['404'].content['application/problem+json']` | `404` response advertises Problem JSON |

JSONPath uses bracket notation to access paths with `/`, `{}`, and media types with `/` or `+`. This prevents syntax errors on special property names.

Avoid locking down every document detail that does not belong to the protected contract. For example, JSON property ordering changes usually do not change the API contract. Prioritize assertions on paths, methods, statuses, media types, schema references, and fields meaningful to consumers.

## 6. Verifying Response Schemas

Checking that a media type exists does not guarantee the right schema is attached. Verify `$ref` as well:

~~~java
@Test
void generatedDocumentReferencesExpectedSchemas() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['200'].content['application/json'].schema['$ref']"
        ).value("#/components/schemas/OrderResponse"))
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['404'].content['application/problem+json'].schema['$ref']"
        ).exists())
        .andExpect(jsonPath(
            "$.components.schemas.OrderResponse.properties.id.type"
        ).value("integer"))
        .andExpect(jsonPath(
            "$.components.schemas.OrderResponse.properties.status.type"
        ).value("string"));
}
~~~

Schemas may be inlined or referenced via `$ref`, depending on configuration and how springdoc processes models. If your project changes schema resolution strategies, assertions should verify equivalent semantics rather than coupling to a single serialization format.

If `OrderResponse.id` changes from `long` to `String`, the schema test flags the contract document change. If that change breaks consumers, treat it as an API change rather than a mere Java model edit.

## 7. Testing Live Controller Responses with MockMvc

After checking the document, call the endpoint itself to verify runtime behavior. Inside the full test context, mock the service for deterministic data.

With Spring Framework 6.2 and Spring Boot 3.4 or later, use `@MockitoBean`:

~~~java
import org.springframework.test.context.bean.override.mockito.MockitoBean;

import static org.mockito.BDDMockito.given;

@SpringBootTest
@AutoConfigureMockMvc
class OrderEndpointContractMvcTest {

    @Autowired
    MockMvc mockMvc;

    @MockitoBean
    OrderService orderService;

    @Test
    void existingOrderReturns200AndJson() throws Exception {
        given(orderService.findById(42L))
            .willReturn(Optional.of(new OrderResponse(42L, "PAID")));

        mockMvc.perform(
                get("/api/orders/{id}", 42)
                    .accept(MediaType.APPLICATION_JSON)
            )
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(
                MediaType.APPLICATION_JSON
            ))
            .andExpect(jsonPath("$.id").value(42))
            .andExpect(jsonPath("$.status").value("PAID"));
    }
}
~~~

On older Spring Boot versions lacking `@MockitoBean`, use `@MockBean` from Spring Boot Test. Annotation names vary by platform version; MockMvc testing remains unchanged.

This test confirms the controller actually returns `200`, JSON, and the right body fields. Testing only the document while skipping endpoints can miss bugs in exception handlers, converters, or controller logic.

## 8. Testing Error Responses and Content-Type

Stub the service to return `Optional.empty()` to test the not-found branch:

~~~java
@Test
void missingOrderReturns404AndProblemJson() throws Exception {
    given(orderService.findById(999L))
        .willReturn(Optional.empty());

    mockMvc.perform(
            get("/api/orders/{id}", 999)
                .accept(
                    MediaType.APPLICATION_JSON,
                    MediaType.APPLICATION_PROBLEM_JSON
                )
        )
        .andExpect(status().isNotFound())
        .andExpect(content().contentTypeCompatibleWith(
            MediaType.APPLICATION_PROBLEM_JSON
        ))
        .andExpect(jsonPath("$.status").value(404))
        .andExpect(jsonPath("$.title").value("Order not found"));
}
~~~

The client accepts both success and error media types. The error response must preserve `404` and `application/problem+json` as published in the OpenAPI document.

If the exception handler returns `application/json` instead of `application/problem+json`, the test must fail. Resolve the intended contract and fix either the handler or the docs; never relax assertions merely to make tests pass.

## 9. Testing Request Content-Type and Content Negotiation

MockMvc can simulate `Content-Type` and `Accept` headers to test mapping conditions:

~~~java
@PostMapping(
    path = "/api/orders",
    consumes = MediaType.APPLICATION_JSON_VALUE,
    produces = MediaType.APPLICATION_JSON_VALUE
)
public OrderResponse create(@RequestBody CreateOrderRequest request) {
    return orderService.create(request);
}
~~~

Request sending an unsupported media type:

~~~java
mockMvc.perform(
        post("/api/orders")
            .contentType(MediaType.TEXT_PLAIN)
            .content("not-json")
    )
    .andExpect(status().isUnsupportedMediaType());
~~~

Request asking for an unsupported response media type:

~~~java
mockMvc.perform(
        get("/api/orders/{id}", 42)
            .accept(MediaType.TEXT_HTML)
    )
    .andExpect(status().isNotAcceptable());
~~~

`415` and `406` outcomes depend on mappings, converters, exception handlers, and content negotiation settings. If the application standardizes error bodies, assert `Content-Type` and error schemas as well. If no fixed error body policy exists yet, start by locking down status codes per confirmed behavior.

## 10. Using ObjectMapper When JSONPath Is Insufficient

For large documents or complex assertions, read the response body into a `JsonNode`. This works well when inspecting multiple operations in one test:

~~~java
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.test.web.servlet.MvcResult;

import static org.assertj.core.api.Assertions.assertThat;

@Autowired
ObjectMapper objectMapper;

@Test
void generatedDocumentContainsExpectedStatusAndMediaTypes() throws Exception {
    MvcResult result = mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andReturn();

    JsonNode document = objectMapper.readTree(
        result.getResponse().getContentAsByteArray()
    );

    JsonNode operation = document
        .path("paths")
        .path("/api/orders/{id}")
        .path("get");

    JsonNode responses = operation.path("responses");

    assertThat(responses.has("200")).isTrue();
    assertThat(responses.has("404")).isTrue();
    assertThat(
        responses.path("200").path("content").has("application/json")
    ).isTrue();
    assertThat(
        responses.path("404").path("content")
            .has("application/problem+json")
    ).isTrue();
}
~~~

`JsonNode.path()` returns a missing node if a field is absent, so `has(...)` assertions pinpoint missing sections accurately. You can write helpers to check response codes and media types across many operations without repeating long JSONPath strings.

Avoid comparing the entire JSON string via `content().json(expected)` unless your goal is truly locking down the whole document. OpenAPI may reorder properties or auxiliary metadata without altering the contract. Structural assertions are generally more resilient.

## 11. Testing OpenAPI Groups

When an application defines multiple `GroupedOpenApi` beans, each group exposes a separate document. Tests must call the right endpoint:

~~~java
@Test
void partnerGroupContainsOnlyPartnerOperation() throws Exception {
    mockMvc.perform(get("/v3/api-docs/partner"))
        .andExpect(status().isOk())
        .andExpect(jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['200']"
        ).exists())
        .andExpect(jsonPath(
            "$.paths['/admin/users'].get"
        ).doesNotExist());
}
~~~

Never test only the default document if Swagger UI points to dedicated groups. A group can have broken package/path filters even while the default document looks complete.

If group names or `springdoc.api-docs.path` change, update test URLs accordingly. You can configure properties for a test profile, yet never let test configuration diverge so far from production that tests stop verifying the actual published document.

## 12. Testing Security When Documentation Is Protected

In Servlet applications, Spring Security filters run before controllers. When `/v3/api-docs` requires authentication, tests must provide an authorized user:

~~~java
import org.springframework.security.test.context.support.WithMockUser;

@Test
@WithMockUser(roles = "API_READER")
void authorizedUserCanReadOpenApiDocument() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andExpect(content().contentTypeCompatibleWith(
            MediaType.APPLICATION_JSON
        ));
}
~~~

Add a dedicated test for unauthenticated callers:

~~~java
@Test
void anonymousUserCannotReadProtectedOpenApiDocument() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isUnauthorized());
}
~~~

Actual status may be `302` if the application uses form login or redirects instead of `401`. Write assertions matching your API's security policy.

Never set `@AutoConfigureMockMvc(addFilters = false)` in security contract tests. That flag disables the filter chain and can make protected documentation endpoints appear public in tests while production blocks them. Only disable filters when a test's scope is explicitly restricted to controllers and security is tested separately.

## 13. Testing YAML Documents

springdoc can serve OpenAPI YAML at `/v3/api-docs.yaml`. When your project publishes YAML for an API portal or code generator, test that endpoint with MockMvc as well:

~~~java
@Test
void yamlApiDocsEndpointIsAvailable() throws Exception {
    mockMvc.perform(get("/v3/api-docs.yaml"))
        .andExpect(status().isOk())
        .andExpect(content().string(org.hamcrest.Matchers.containsString(
            "openapi:"
        )));
}
~~~

The YAML `Content-Type` can vary across springdoc versions and configurations. Inspect the response header of your running application and add the exact assertion matching your project contract; never guess a media type and lock down the wrong value.

To inspect YAML structure more deeply, parse the body using a YAML parser on the test classpath and check the same `paths`, `responses`, and `content` fields. Avoid checking only the substring `openapi:` when pipelines depend on the YAML endpoint's status and media type.

## 14. Organizing Tests to Prevent Duplication and Flakiness

An MVC suite can be organized by responsibility:

| Test Class or Group | Purpose |
|---|---|
| `OpenApiDocumentMvcTest` | `/v3/api-docs` endpoint, generated paths, operations, statuses, and media types |
| `OrderEndpointMvcTest` | Runtime controller responses: status, `Content-Type`, body, and headers |
| `ApiErrorMvcTest` | Exception handlers, `ProblemDetail`, and error responses |
| `OpenApiGroupMvcTest` | Per-group documents and operation scope |
| `OpenApiSecurityMvcTest` | Documentation access permissions and unauthorized responses |

Practices for stable tests:

- Use deterministic fixtures or stubbed services; avoid shared databases when testing HTTP contracts alone.
- Avoid asserting full OpenAPI JSON strings when only specific contract parts need locking down.
- Assert `Content-Type` only on responses with bodies; `204` responses need no content.
- Use `contentTypeCompatibleWith` unless parameters like `charset` must be enforced.
- Use `@SpringBootTest` for full-application document generation; reserve `@WebMvcTest` for controller slices where springdoc auto-configuration is unnecessary.
- Keep security filters enabled when testing access control.
- Do not rely on operation or JSON property ordering.

## 15. Common Pitfalls

| Symptom | Possible Cause | Resolution |
|---|---|---|
| `/v3/api-docs` returns `404` in `@WebMvcTest` | MVC slice skips springdoc auto-configuration | Use `@SpringBootTest` or explicitly import required config |
| `/v3/api-docs` returns `401`/`403` | Spring Security protects documentation endpoint | Provide an authorized user/role or check anonymous policy |
| Document returns `200` with HTML `Content-Type` | Redirect/login/error page or another route answered | Inspect filter chain, redirects, and endpoint path |
| OpenAPI lacks `404` response | Missing `@ApiResponse` or exception response metadata | Document error responses and check generated spec |
| Document response has status but no `content` | Annotation omitted schema/media type or response is bodyless | Verify `@Content` and response contract |
| Runtime returns Problem JSON yet OpenAPI lists JSON | Exception handler disagrees with annotations | Document `application/problem+json` for error responses |
| JSONPath misses paths containing `{id}` | JSONPath failed to escape path key | Use bracket notation `['/api/orders/{id}']` |
| Test fails after OpenAPI version change | Assertion pins a version string that changed | Pin version only if required; otherwise check existence and validate |
| Tests pass yet production behaves differently | Test profile alters mappings, security, or converters | Keep test config close to production and add server/proxy smoke tests |
| `@MockitoBean` does not exist | Older Spring Framework/Boot lacks this annotation | Use `@MockBean` matching your Boot version or upgrade test stack |
| `204` test demands `Content-Type` | Bodyless response | Assert only status and empty body |
| `406`/`415` tests are flaky | Converters, filters, or error handlers changed | Lock content negotiation settings and check live status/headers |

## 16. Integrating MockMvc Contract Tests into CI

A CI pipeline for a Servlet application can run in this order:

1. Resolve springdoc dependencies compatible with Spring Boot.
2. Boot the full application context in tests.
3. Call `/v3/api-docs` via MockMvc and verify status/`Content-Type`.
4. Assert critical operations, response codes, media types, and schema references.
5. Call business endpoints via MockMvc to verify live status/headers/bodies.
6. Verify exception handlers, content negotiation, and security branches.
7. Diff the new document against the baseline if breaking-change detection is used.
8. Publish release artifacts only when both documentation and endpoints satisfy the contract.

Document and endpoint tests should run on pull requests since they are much faster than cross-service end-to-end tests. When reverse proxies, gateways, or container-specific behavior exist, add a smoke-test layer against a live server to cover what sits outside MockMvc's scope.

## 17. Pre-Merge Checklist

- [ ] Tests use `@SpringBootTest` and `@AutoConfigureMockMvc` when verifying full springdoc output.
- [ ] `/v3/api-docs` returns a success status.
- [ ] Documentation endpoint returns the appropriate JSON `Content-Type`.
- [ ] OpenAPI document includes expected paths and HTTP methods.
- [ ] Success and error response codes are advertised.
- [ ] Every body-bearing response declares the right media type.
- [ ] Response schemas or `$ref`s point to expected components.
- [ ] MockMvc confirms runtime endpoints return accurate statuses and `Content-Type`s.
- [ ] Exception handlers return error bodies matching documentation.
- [ ] Group documents are tested individually when multiple groups exist.
- [ ] Security filters remain enabled during security contract tests.
- [ ] Tests do not depend on property ordering or full JSON string equality.
- [ ] CI runs the suite prior to publishing OpenAPI artifacts.
