# Safe Idempotency and Avoiding Data Duplication When Rebuilding Documents

A Spring Boot application can supplement OpenAPI metadata using annotations, OpenApiCustomizer, or GlobalOpenApiCustomizer. Customizers commonly add servers, tags, security schemes, default responses, headers, or extensions to the OpenAPI model that springdoc builds from controllers. When a document is rebuilt, generated for multiple document groups, or processed multiple times in the same pipeline, uncontrolled additive operations can produce duplicate elements or overwrite existing metadata.

Therefore, customization logic needs to be **idempotent**: applying the same customizer multiple times to the same model must produce an outcome equivalent to applying it once. This property keeps documentation stable across application restarts, document refreshes, test runs, CI spec exports, or adding new groups.

## 1. Idempotency in OpenAPI Construction

An idempotent operation can be repeated without altering the result after the first application. For a customizer, this can be expressed as:

\[
F(F(D)) = F(D)
\]

Where:

- D is the OpenAPI model generated by springdoc.
- F is the customization function.
- F(D) is the document after applying the customizer once.
- F(F(D)) is the document after applying the customizer again to the prior result.

Both outcomes must be contract-equivalent: no extra servers, tags, parameters, responses, or operations appear merely because the customizer ran again.

For example, if a customizer unconditionally calls addServersItem(...), each run can append a server identical to the existing one. If it unconditionally calls addParametersItem(...), an operation can receive multiple copies of the same header. Conversely, checking whether an element already exists by a stable key before adding makes the operation safe to repeat.

Idempotency must be designed into the customization logic itself. Never rely on an assumption that springdoc invokes a customizer exactly once across the entire application lifecycle. Document generation, caching, document groups, and testing can execute the same logic in multiple contexts.

## 2. Places Prone to Data Duplication

Some OpenAPI components are list structures, while others are maps or sets. How duplicates are prevented depends on each element's structure and identifier:

| Component | Operation Prone to Duplication | Identifying Key to Use |
| --- | --- | --- |
| servers | Always appending a new server | Server URL |
| document-level tags | Always appending a new tag | Tag name |
| operation tags | Always appending a tag string | Tag name |
| parameters | Re-adding a header or query parameter | Pair of in + name |
| responses | Adding default responses multiple times | Status code |
| security | Re-adding security requirements | Scheme name and scopes |
| components.schemas | Creating components with the same name repeatedly | Schema name |
| components.securitySchemes | Re-registering a scheme | Scheme name |
| paths and operations | Recreating an existing path/method | Path + HTTP method |
| Extensions | Writing multiple values for the same concept | Extension name |

Map-like structures such as responses or components.schemas inherently maintain unique keys in the model, yet can still be unintentionally overwritten if a customizer calls put outside its proper scope. List-like structures such as servers, tags, parameters, and security require closer checks because append operations can create duplicate entries.

## 3. Design Rules for Repeatable Customizers

A stable customizer should follow these principles:

1. **Identify the natural key of each element.** For example, a parameter is identified by location in and name; a server is identified by URL.
2. **Check before adding.** If the element already exists, do not append a duplicate.
3. **Update intentionally.** If the customizer owns that metadata, replace the current value with the canonical value; if it does not own it, preserve metadata declared by annotations or controllers.
4. **Use upsert operations.** Create when absent, update when present, and keep element counts stable.
5. **Do not store changing state in shared mutable fields.** Each run must rely solely on the passed-in OpenAPI model and current configuration.
6. **Maintain deterministic ordering.** When constructing lists, use deterministic order so documents do not change due to unstable iteration order.
7. **Do not generate random or time-dependent values.** Avoid current timestamps, random UUIDs, or external service results unless they are a fixed part of the contract.
8. **Do not blindly replace existing operations.** Add a new operation only when the path and HTTP method do not yet exist; if present, update only the parts the customizer owns.

A helpful distinction:

- **ensure:** guarantee the element exists; if already present, keep or normalize it.
- **upsert:** create or update the element by key.
- **replace:** replace the entire value owned by the customizer.
- **append:** add to the end of a list; use only when elements are genuinely repeatable and multiple additions are intentional.

For OpenAPI metadata, append almost always requires a pre-check.

## 4. Example Customizer Adding Tags, Servers, and Responses Idempotently

The example below illustrates three common operations:

- Ensure the document has an Orders tag, keeping only one tag with that name.
- Ensure server https://api.example.com exists without adding duplicates.
- Add a 429 response for operations under /api/orders without overwriting responses declared by controllers.

~~~java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.Operation;
import io.swagger.v3.oas.models.PathItem;
import io.swagger.v3.oas.models.Server;
import io.swagger.v3.oas.models.tags.Tag;
import io.swagger.v3.oas.models.responses.ApiResponse;
import io.swagger.v3.oas.models.responses.ApiResponses;
import org.springdoc.core.customizers.OpenApiCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class StableOpenApiConfiguration {

    @Bean
    OpenApiCustomizer stableOpenApiCustomizer() {
        return StableOpenApiConfiguration::apply;
    }

    static void apply(OpenAPI openApi) {
        ensureTag(openApi, "Orders", "Order management APIs");
        ensureServer(
            openApi,
            "https://api.example.com",
            "Official API server"
        );

        if (openApi.getPaths() == null) {
            return;
        }

        openApi.getPaths().forEach((path, pathItem) -> {
            if (!isOrderPath(path) || pathItem == null) {
                return;
            }

            for (Operation operation : pathItem.readOperations()) {
                ensureOperationTag(operation, "Orders");
                ensureRateLimitResponse(operation);
            }
        });
    }

    private static boolean isOrderPath(String path) {
        return "/api/orders".equals(path)
            || path.startsWith("/api/orders/");
    }

    private static void ensureTag(
            OpenAPI openApi,
            String name,
            String description
    ) {
        List<Tag> existing = openApi.getTags() == null
            ? new ArrayList<>()
            : openApi.getTags();

        Map<String, Tag> unique = new LinkedHashMap<>();
        for (Tag tag : existing) {
            if (tag != null && tag.getName() != null) {
                unique.putIfAbsent(tag.getName(), tag);
            }
        }

        Tag target = unique.get(name);
        if (target == null) {
            unique.put(name, new Tag().name(name).description(description));
        } else {
            // The customizer owns the description of the Orders tag.
            target.setDescription(description);
        }

        openApi.setTags(new ArrayList<>(unique.values()));
    }

    private static void ensureServer(
            OpenAPI openApi,
            String url,
            String description
    ) {
        List<Server> existing = openApi.getServers() == null
            ? new ArrayList<>()
            : openApi.getServers();

        Map<String, Server> unique = new LinkedHashMap<>();
        for (Server server : existing) {
            if (server != null && server.getUrl() != null) {
                unique.putIfAbsent(server.getUrl(), server);
            }
        }

        Server target = unique.get(url);
        if (target == null) {
            unique.put(url, new Server().url(url).description(description));
        } else {
            // Standardize the server description managed by the customizer.
            target.setDescription(description);
        }

        openApi.setServers(new ArrayList<>(unique.values()));
    }

    private static void ensureOperationTag(
            Operation operation,
            String tag
    ) {
        List<String> existing = operation.getTags() == null
            ? new ArrayList<>()
            : operation.getTags();

        Set<String> unique = new LinkedHashSet<>(existing);
        unique.add(tag);
        operation.setTags(new ArrayList<>(unique));
    }

    private static void ensureRateLimitResponse(Operation operation) {
        ApiResponses responses = operation.getResponses();
        if (responses == null) {
            responses = new ApiResponses();
            operation.setResponses(responses);
        }

        // Keep controller-declared 429 response if it already exists.
        responses.putIfAbsent(
            "429",
            new ApiResponse().description("Request rate limit exceeded")
        );
    }
}
~~~

Key highlights of the example:

- Tags and servers are deduplicated by key before reassigning the list, so any prior duplicates are also removed.
- Operation tags are collected into a LinkedHashSet, preserving order while eliminating duplicate strings.
- The 429 response uses putIfAbsent, so the customizer does not replace a detailed response already declared on the controller.
- Fresh model objects are created per run rather than sharing one mutable instance across multiple operations.
- The customizer retains no counters or change lists in static fields.

In real applications, only normalize tags/servers owned by the customizer. The example treats URL as the server's identifying key. If the document uses templated server URLs whose server variables produce different destinations, the key must include both the URL and variable definitions; never merge two servers merely because their URL template strings match.

## 5. Upserting Parameters by Location and Name Pair

Parameters in OpenAPI can live in path, query, header, or cookie. Two parameters with the same name but different in values are two distinct parameters. Therefore, the identifying key must be the pair:

\[
(\text{in}, \text{name})
\]

Example customizer ensuring the X-Request-Id header is present on an operation:

~~~java
import java.util.ArrayList;
import java.util.List;

import io.swagger.v3.oas.models.Operation;
import io.swagger.v3.oas.models.parameters.Parameter;

static void ensureRequestIdHeader(Operation operation) {
    List<Parameter> parameters = operation.getParameters() == null
        ? new ArrayList<>()
        : new ArrayList<>(operation.getParameters());

    Parameter existing = parameters.stream()
        .filter(parameter -> "header".equals(parameter.getIn()))
        .filter(parameter -> "X-Request-Id".equals(parameter.getName()))
        .findFirst()
        .orElse(null);

    if (existing == null) {
        parameters.add(
            new Parameter()
                .name("X-Request-Id")
                .in("header")
                .required(false)
                .description("Request correlation ID sent by the client")
                .schema(new io.swagger.v3.oas.models.media.StringSchema())
        );
    }

    // Reassign the list only after checking for missing parameters.
    operation.setParameters(parameters);
}
~~~

The example adds the header only when absent. If you need to normalize the description or schema of an existing parameter, update that parameter directly instead of adding a duplicate. Never delete or replace a parameter that shares the same name in a different location.

OpenAPI also allows parameters declared at the Path Item level to be inherited by operations. When checking for duplicates, inspect both path-level and operation-level parameters. An operation-level parameter with the same name and in as a path-level parameter overrides it per OpenAPI rules; avoid accidentally creating duplicates at both levels.

## 6. Avoiding Overwriting Existing Metadata

Customizers typically run after springdoc has read controller annotations and built the model. If a customizer reassigns an entire list or map, it can erase details declared by controllers.

Unsafe example:

~~~java
operation.setResponses(new ApiResponses()
    .addApiResponse("200", new ApiResponse().description("OK")));
~~~

The snippet above replaces all existing responses with a brand-new map. Previously declared 400, 404, 409, or 500 responses can vanish.

If you only want to add a default response:

~~~java
operation.getResponses().putIfAbsent(
    "429",
    new ApiResponse().description("Request rate limit exceeded")
);
~~~

If the customizer has full ownership of a specific response and needs to standardize its content, use put for that specific status code. Do not replace the entire collection when only one entry needs updating.

Similarly:

- Use putIfAbsent or ownership-based put for schema components.
- Look up parameters by (in, name) before adding.
- Look up tags by name before updating.
- Look up servers by URL before adding.
- Do not change a stable operationId if the customizer does not own operation naming rules.

## 7. Components and References Need Stable Names

components.schemas, components.parameters, components.responses, components.examples, and components.securitySchemes are keyed by name. When adding components from a customizer, use stable names and avoid generating names dependent on time or execution order.

Example:

~~~java
import io.swagger.v3.oas.models.Components;
import io.swagger.v3.oas.models.media.StringSchema;
import java.util.LinkedHashMap;

static void ensureCorrelationIdSchema(OpenAPI openApi) {
    if (openApi.getComponents() == null) {
        openApi.setComponents(new Components());
    }

    if (openApi.getComponents().getSchemas() == null) {
        openApi.getComponents().setSchemas(new LinkedHashMap<>());
    }

    openApi.getComponents().getSchemas().putIfAbsent(
        "CorrelationId",
        new StringSchema()
            .description("Request correlation identifier")
            .example("req-1001")
    );
}
~~~

The CorrelationId component name stays fixed. When the customizer runs again, putIfAbsent does not create another component. Operations can reference the same component using $ref.

If you need to update an existing schema, use put only when the customizer owns that component. If a component could be created by annotations or another customizer, align on naming and ownership before modifying it. Two customizers writing different expectations under the same key create order-dependent output.

## 8. Avoiding Duplicate Security Requirements and Extensions

Security requirements are represented as a list. Unconditionally calling addSecurityItem(...) can create duplicate requirements. Check scheme and scopes before adding:

~~~java
import java.util.ArrayList;
import java.util.List;

import io.swagger.v3.oas.models.security.SecurityRequirement;

static void ensureBearerRequirement(Operation operation) {
    String scheme = "bearerAuth";

    List<SecurityRequirement> requirements =
        operation.getSecurity() == null
            ? new ArrayList<>()
            : new ArrayList<>(operation.getSecurity());

    boolean exists = requirements.stream()
        .anyMatch(requirement -> requirement.containsKey(scheme));

    if (!exists) {
        requirements.add(new SecurityRequirement().addList(scheme));
    }

    operation.setSecurity(requirements);
}
~~~

If a scheme carries scopes, the comparison key must include both the scheme name and the list of scopes. Do not compare only by scheme name if two requirements carry different semantics.

For x-... extensions, the OpenAPI model stores them by key. Use the same key and update values deliberately:

~~~java
openApi.addExtension("x-build-source", "springdoc-customizer");
~~~

Do not generate a fresh key on each run such as x-build-source-1, x-build-source-2. Extensions are contract metadata; key names should remain stable and meaningful.

## 9. Do Not Share Mutable State Across Invocations

A subtle bug occurs when a customizer holds a list or model object in a field and keeps appending elements when the callback runs again:

~~~java
// Do not use this approach.
private final List<Tag> generatedTags = new ArrayList<>();

OpenApiCustomizer customizer() {
    return openApi -> {
        generatedTags.add(new Tag().name("Orders"));
        openApi.setTags(generatedTags);
    };
}
~~~

The generatedTags list outlives a single document build. Each time the callback runs again, it retains prior data and keeps growing. If multiple groups or threads share this object, unintended cross-state contamination can also occur.

Create data fresh inside each customizer invocation:

~~~java
OpenApiCustomizer customizer() {
    return openApi -> {
        ensureTag(openApi, "Orders", "Order management APIs");
    };
}
~~~

Immutable configuration values such as tag names, server URLs, or descriptions can be kept in constants. Model objects like Tag, Server, ApiResponse, and Parameter should be created or looked up per OpenAPI model, never sharing a single mutable instance across multiple documents.

## 10. Determinism When Rebuilding Documents

Idempotency focuses on repeating the same transformation on the same state. Determinism additionally requires that identical inputs and configuration produce identical output content.

Avoid injecting the following into documentation without a contract reason:

- Current wall-clock time captured each time the customizer runs.
- Random UUIDs for operationIds or component names.
- Incrementing values from an in-memory counter.
- External API results that can change between builds.
- Collection ordering tied to HashMap or unstable data sources.

If the document needs to reflect a build version, read a fixed value from build configuration or artifact metadata. Do not call external systems inside a customizer to synthesize content that can be determined from application configuration.

A stable document generation pipeline typically looks like:

~~~text
Controller + DTO + annotations
              |
              v
       Springdoc builds model
              |
              v
        Apply customizers
              |
              v
  Upsert metadata by stable key
              |
              v
     Serialize OpenAPI JSON/YAML
              |
              v
   Diff and verify the contract
~~~

When re-run, the same model and configuration must produce the same metadata, without increasing element counts merely because the pipeline ran again.

## 11. Scope Across the Default Document and Document Groups

An application can generate a default document and multiple groups. The same customizer may apply across multiple scopes depending on bean type and springdoc configuration.

Clarify explicitly:

- Which metadata is shared across all groups, such as contact details or baseline servers.
- Which metadata belongs to a single group, such as tags or responses specific to an admin API.
- Which customizers apply to the default document.
- Which customizers must apply across every group.

If a tag or server is added to each group, every document must be independent and free of duplicates. Never share a single OpenAPI model and mutate it sequentially across multiple groups without explicit cloning and isolation.

When groups have their own customizers, verify the same logic on each documentation endpoint such as /v3/api-docs, /v3/api-docs/customer-api, and /v3/api-docs/admin-api. One group may have different controllers and metadata from another; do not assume the default document represents them all.

## 12. Testing Repeated Customizer Execution

A direct test can apply the same customization function twice to the same OpenAPI model and compare outputs:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import com.fasterxml.jackson.databind.ObjectMapper;
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.Operation;
import io.swagger.v3.oas.models.PathItem;
import io.swagger.v3.oas.models.Paths;
import io.swagger.v3.oas.models.responses.ApiResponses;
import org.junit.jupiter.api.Test;

class StableOpenApiConfigurationTest {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Test
    void applyingCustomizerTwiceProducesSameDocument() throws Exception {
        OpenAPI openApi = new OpenAPI();

        Paths paths = new Paths();
        paths.addPathItem(
            "/api/orders",
            new PathItem().get(
                new Operation()
                    .operationId("listOrders")
                    .responses(new ApiResponses())
            )
        );
        openApi.setPaths(paths);

        StableOpenApiConfiguration.apply(openApi);
        String afterFirstRun = objectMapper.writeValueAsString(openApi);

        StableOpenApiConfiguration.apply(openApi);
        String afterSecondRun = objectMapper.writeValueAsString(openApi);

        assertThat(afterSecondRun).isEqualTo(afterFirstRun);
        assertThat(openApi.getTags())
            .extracting("name")
            .containsExactly("Orders");
        assertThat(openApi.getServers())
            .extracting("url")
            .containsExactly("https://api.example.com");
        assertThat(openApi.getPaths()
            .get("/api/orders")
            .getGet()
            .getResponses()).containsKey("429");
    }
}
~~~

This test verifies:

- The JSON content after the second run equals the first run.
- The tag list contains only one Orders tag.
- The server list contains only the one defined server URL.
- The 429 response exists and was not added multiple times.

If a document contains collections whose order is semantically insignificant, you can normalize order before comparing. Nevertheless, keeping deterministic order directly in the customizer makes diffs readable and highlights real contract changes.

### Checking Documentation Endpoints Across Repeated Requests

Beyond unit testing functions, you can call the OpenAPI endpoint multiple times in an integration test. The snippet below is a test method in a class with MockMvc and ObjectMapper injected:

~~~java
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

import static org.assertj.core.api.Assertions.assertThat;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class OpenApiDocumentRepeatRequestTest {

    @Autowired
    MockMvc mockMvc;

    @Autowired
    ObjectMapper objectMapper;

    @Test
    void repeatedApiDocsRequestsDoNotDuplicateTags() throws Exception {
        String first = mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andReturn()
            .getResponse()
            .getContentAsString();

        String second = mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andReturn()
            .getResponse()
            .getContentAsString();

        JsonNode firstDocument = objectMapper.readTree(first);
        JsonNode secondDocument = objectMapper.readTree(second);

        assertThat(secondDocument.path("tags").size())
            .isEqualTo(firstDocument.path("tags").size());
    }
}
~~~

This is a supplementary check at the HTTP layer. If springdoc caches the document, two requests may return the same cached output without re-executing the customizer. Thus, calling the endpoint repeatedly does not replace unit tests that apply the customizer twice directly to the same model.

## 13. Diffing the Specification After Generation

In CI, you can store OpenAPI JSON/YAML as an artifact and diff it against the released version. When documents are rebuilt, diffs should help distinguish:

- Intentional contract changes: adding responses, changing schemas, adding operations.
- Metadata changes: description, tags, servers, or security.
- Unintended changes: duplicate tags, duplicate servers, duplicate parameters, changed operationIds, or colliding components.

Normalize order-insensitive sections before diffing if your diff tool treats list order as a difference. However, avoid aggressive normalization that strips away real contract changes.

Useful automated checks:

1. No duplicate tag names.
2. No duplicate server URLs.
3. No operation has two parameters with the same in + name pair.
4. Every operationId is unique within a document.
5. No duplicate security requirements.
6. Schema and security scheme names are stable.
7. Two document generations from the same commit and configuration produce equivalent content.

## 14. Common Pitfalls

**Every call to /v3/api-docs adds another server.** The customizer is appending servers without checking. Use URL-based upserts and deduplicate existing entries.

**Headers appear multiple times in Swagger UI.** Check addParametersItem(...) calls and use the (in, name) key so only one parameter exists at the proper scope.

**Default responses wipe out controller-declared responses.** Check whether the customizer calls setResponses(new ApiResponses()). Add single statuses with putIfAbsent or update only the entry owned by the customizer.

**Global tags are duplicated.** Deduplicate the list by Tag.name, maintain deterministic order, and update descriptions on existing tags.

**One group gets another group's metadata.** Check whether the customizer is registered at default or global scope, and avoid sharing mutable OpenAPI models across groups.

**Output changes across restarts.** Look for timestamps, random UUIDs, counters, or external data inside customizers. Switch to fixed configuration and deterministic transformation functions.

**Repeated endpoint tests still miss the bug.** The document may be cached. Add unit tests invoking customizer logic multiple times directly on the same OpenAPI model.

**Two customizers write to the same component.** Establish component ownership and application order. Use stable names and avoid having two customizers update the same key with different contents.

## 15. Checklist for Idempotent Customizers

- [ ] Identified which components the customizer is allowed to create or update.
- [ ] Selected stable identifying keys for tags, servers, parameters, responses, and components.
- [ ] Checked for existence before appending to collections.
- [ ] Used upserts or clearly scoped replacements.
- [ ] Preserved metadata declared by controllers when the customizer does not own it.
- [ ] Kept no shared mutable objects or collections across invocations.
- [ ] Avoided generating timestamps, UUIDs, or random values in the document unnecessarily.
- [ ] Maintained deterministic ordering for readable diffs.
- [ ] Verified the default document and each document group separately.
- [ ] Applied the customizer twice to the same model and compared results.
- [ ] Diffed OpenAPI artifacts in CI to catch unintended changes.

## 16. Conclusion

Programmatic OpenAPI customization must be safely repeatable because documents can be built in multiple contexts and multiple times. Identify each element by a stable key, check before adding, update only what you own, and preserve controller-declared metadata. Avoid shared mutable state and random data. Most importantly, test customizers by applying them twice to the same OpenAPI model; if the output does not change, the logic satisfies transformation-level idempotency.
