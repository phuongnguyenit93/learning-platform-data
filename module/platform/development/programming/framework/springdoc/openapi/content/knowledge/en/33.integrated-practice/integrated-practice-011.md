# Diagnosing a Schema or Mapping Bug from Observed Data

When an API runs successfully but the OpenAPI documentation describes the request or response inaccurately, jumping straight to editing annotations often makes the issue harder to find. Start from observed data: the request the client sends, the response the server actually returns, the configuration loaded by Swagger UI, and the schema generated by springdoc-openapi. Comparing these four sources pinpoints whether the bug lies in HTTP mapping, Jackson serialization, validation, DTO declarations, or a downstream transformation layer.

This hands-on exercise uses an order lookup endpoint to diagnose mismatched property names in the response, then extends the methodology to query parameters, request bodies, generic responses, and nullable fields. The goal is to fix the responsible layer and prove the contract aligns via both runtime checks and documentation checks.

## 1. Distinguishing runtime data from the OpenAPI contract

A request passes through several layers before becoming the data seen by clients:

1. Spring MVC or WebFlux maps URL, HTTP method, path variables, query parameters, headers, and body to controller parameters.
2. Jackson or the corresponding converter reads JSON into a DTO and writes the DTO out as a JSON response.
3. Bean Validation and application logic validate data against endpoint rules.
4. springdoc-openapi analyzes controllers, data types, annotations, Jackson configuration, and related components to generate the OpenAPI description.
5. A gateway or reverse proxy may further alter paths, headers, or payloads before the client receives the response.

OpenAPI describes the HTTP contract clients rely on. Therefore, the final payload observed through the public URL is the strongest evidence when an application runs behind a gateway. A schema generated from a DTO can match the Java model yet still misrepresent the response if a custom serializer runs, the controller returns a different type, or a proxy transforms the JSON.

Distinguish these concepts:

| Component | Question to answer |
| --- | --- |
| Request mapping | Which HTTP method and URL must the client call? |
| Parameter mapping | Does the value reside in path, query, header, cookie, or request body? |
| Serialization | What are the actual field names, data types, date/time formats, and JSON structure? |
| Validation | Which values are accepted or rejected? |
| OpenAPI schema | Which properties, required flags, nullability, formats, and responses does the doc describe? |
| Gateway transformation | Does the client receive the exact payload returned by Spring, or a modified payload? |

Do not rely on a single source to draw conclusions. For instance, a DTO having a **createdAt** field does not prove the external JSON uses the name **createdAt**; Jackson may rename properties during serialization.

## 2. Gathering evidence before making changes

Pick a request that reproduces the bug and record everything thoroughly:

- HTTP method, public URL, and query string.
- Key request headers such as **Content-Type**, **Accept**, and authorized authentication credentials.
- Raw request body if the endpoint takes a body.
- HTTP status, response headers, and response body.
- URL of the OpenAPI JSON loaded by Swagger UI.
- Schema of the corresponding operation in OpenAPI JSON.
- Application logs at the same timestamp if binding, conversion, or validation errors occurred.

Example fetching the actual response:

~~~bash
curl -i -H "Accept: application/json" http://localhost:8080/api/orders/42
~~~

Fetching the OpenAPI document:

~~~bash
curl -s http://localhost:8080/v3/api-docs -o openapi.json
~~~

If the environment requires authentication, execute the request with an authorized account or token. If the application runs under a context path, custom API docs path, or behind a proxy, substitute the real URL. Never draw conclusions from default URLs when deployment configuration has changed.

You can use jq to quickly inspect the operation's response schema:

~~~bash
jq '.paths["/api/orders/{id}"].get.responses["200"].content["application/json"].schema' openapi.json
jq '.components.schemas.OrderView' openapi.json
~~~

Schema names and response codes in the commands must match the actual document. If the operation returns 201, 204, or another media type, query the corresponding branch.

Record findings in a comparison table before editing:

| Item | Observed from HTTP | Observed from OpenAPI | Hypothesis to verify |
| --- | --- | --- | --- |
| URL and method | Request client actually sends | Path and operation in document | Does controller mapping match? |
| Property names | Keys in JSON response | Properties in schema | Does Jackson or a transformer rename fields? |
| Data types | JSON values and token types | type and format in schema | Does runtime return string, number, object, or array? |
| Required | Does the field always appear? | required list | Is the field omitted or truly required? |
| Nullable | Can the field be JSON null? | nullable or null-allowing schema | Does the contract express nullability properly? |
| Parameters | Where the client passes values | in: path, query, header, cookie | Does the mapping annotation match the location? |

## 3. Hands-on scenario: JSON response uses snake_case names

Suppose endpoint **GET /api/orders/42** returns:

~~~json
{
  "order_id": 42,
  "created_at": "2026-11-20T08:15:00Z",
  "status": "PAID",
  "customer": {
    "full_name": "Nguyen An"
  },
  "total": 125000.00
}
~~~

Meanwhile, the OpenAPI schema displays:

~~~yaml
OrderView:
  type: object
  properties:
    id:
      type: integer
      format: int64
    createdAt:
      type: string
      format: date-time
    status:
      type: string
    customer:
      $ref: '#/components/schemas/CustomerView'
    total:
      type: number
CustomerView:
  type: object
  properties:
    fullName:
      type: string
~~~

Clients generated from the schema will read **id**, **createdAt**, and **customer.fullName**, whereas the server sends **order_id**, **created_at**, and **customer.full_name**. This is a property-name contract mismatch. Renaming fields solely in the documentation without understanding how the serializer behaves can leave requests or responses broken in another environment.

First, inspect the payload at two points if a gateway is present:

1. Call the Spring Boot application directly and save the response.
2. Call the public URL through the gateway and save the response.

If the two payloads differ, the gateway or external adapter is transforming the data. The public schema must describe the payload the client actually receives, and you must clearly decide which layer owns that transformation. If the two payloads are identical, inspect Jackson configuration, serializers, mixins, annotations, and the response type returned by the controller.

Common root causes include:

- ObjectMapper uses a naming strategy such as **SNAKE_CASE**.
- DTOs or getters carry **@JsonProperty** specifying a JSON name different from the Java field name.
- **@JsonAlias** is used to accept alternate input names but mistaken for the serialized field name.
- Custom serializers, mixins, or Jackson modules alter the JSON structure.
- The controller returns a **Map**, **JsonNode**, projection, or different DTO than the documentation author assumed.
- The gateway renames fields or wraps the response after Spring Boot finishes serialization.

Inspect the actual ObjectMapper used by MVC/WebFlux and every serializer configuration applied to the endpoint. If only one endpoint uses a custom response mapping, do not assume the entire module shares the same naming strategy.

## 4. Fixing property names at the right layer

If the JSON names are a stable part of the API contract, declare them explicitly on the DTO using Jackson annotations. Example using Java records:

~~~java
public record CustomerView(
    @JsonProperty("full_name")
    String fullName
) {}

public record OrderView(
    @JsonProperty("order_id")
    Long id,

    @JsonProperty("created_at")
    Instant createdAt,

    OrderStatus status,
    CustomerView customer,
    BigDecimal total
) {}
~~~

The controller must return the exact declared response type:

~~~java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @GetMapping("/{id}")
    public OrderView getOrder(@PathVariable Long id) {
        return orderService.getView(id);
    }
}
~~~

Imports and service declarations are omitted to focus on mapping. In a real project, add constructor injection and service implementations following your existing structure.

**@JsonProperty** controls the JSON property name used by Jackson. springdoc-openapi typically reads Jackson metadata to document the corresponding property names. After editing, re-check both the runtime response and **/v3/api-docs**; never assume annotations are picked up if the app uses a custom serializer or converter.

Distinguish key annotations:

| Annotation | Primary effect | Pitfall to avoid |
| --- | --- | --- |
| @JsonProperty | Sets JSON property name or access mode | Renaming Java fields without checking actual JSON |
| @JsonAlias | Accepts extra names when deserializing input | Assuming aliases become the serialized output field name |
| @JsonNaming | Applies a naming strategy to a type's properties | Assuming every ObjectMapper or gateway uses the same strategy |
| @Schema | Adds metadata to the OpenAPI schema | Treating it as a way to alter runtime JSON |
| @JsonFormat | Controls JSON formatting for certain types | Using it instead of query-parameter date mapping |

If a response is produced by a custom serializer or transformed by a gateway so springdoc cannot infer it from the DTO, document the public schema explicitly. You can use **@ApiResponse**, **@Content**, **@Schema**, or **OpenApiCustomizer** to adjust the documentation. These configurations only update OpenAPI metadata; they do not change the runtime payload.

Example explicitly documenting the response schema:

~~~java
@ApiResponse(
    responseCode = "200",
    description = "Order details",
    content = @Content(
        mediaType = "application/json",
        schema = @Schema(implementation = OrderView.class)
    )
)
@GetMapping("/{id}")
public OrderView getOrder(@PathVariable Long id) {
    return orderService.getView(id);
}
~~~

This annotation helps when specifying the schema for an operation. If runtime returns a structure different from **OrderView**, create a view type reflecting the actual payload or document a separate schema. Never use **implementation** to paper over runtime discrepancies that clients still hit.

## 5. Diagnosing incorrect parameter locations

Another mapping bug occurs when a value is passed in the query string while documentation describes it as a request body, or vice versa. Inspect the controller signature before adding **@Parameter**.

Example order filtering endpoint:

~~~java
@GetMapping
public List<OrderView> search(
    @RequestParam(required = false) OrderStatus status,
    @RequestParam(required = false) LocalDate from,
    @RequestParam(required = false) Integer page
) {
    return orderService.search(status, from, page);
}
~~~

Clients must call with a query string, for example:

~~~http
GET /api/orders?status=PAID&from=2026-11-01&page=0
~~~

In OpenAPI, these parameters belong in **parameters** with **in: query**. **LocalDate** is typically documented as **type: string**, **format: date**. If the documentation shows a request body object instead, check whether annotations or the controller signature were altered.

Common mapping locations:

| Spring annotation | HTTP data location | OpenAPI counterpart |
| --- | --- | --- |
| @PathVariable | Segment inside URL path | parameters with in: path |
| @RequestParam | Query string | parameters with in: query |
| @RequestHeader | HTTP header | parameters with in: header |
| @CookieValue | Cookie | Cookie parameter or appropriate security definition |
| @RequestBody | JSON or media-typed body | requestBody |
| @RequestPart | Multipart section | requestBody with multipart/form-data |
| @ModelAttribute | Form data or bound request parameters | Corresponding parameters, depending on types and binding |

For flat query DTOs, **@ParameterObject** helps springdoc expand properties into query parameters:

~~~java
public record OrderFilter(
    OrderStatus status,
    LocalDate from,
    Integer page
) {}

@GetMapping
public List<OrderView> search(@ParameterObject OrderFilter filter) {
    return orderService.search(filter);
}
~~~

Inspect the generated schema to verify each field appears as a query parameter with the right name and type. Do not use **@ParameterObject** to turn a nested JSON structure into a request body; for nested objects or complex query rules, design explicit parameters and document query serialization to match client expectations.

For path parameters, OpenAPI requires **required: true**. If **@PathVariable** does not match the placeholder name in **@GetMapping**, requests may fail to map as intended. Compare the path template, variable name, and operation in the documentation directly.

## 6. Checking request body, media type, and nested types

If a JSON request is rejected while Swagger UI lets users submit a differently structured payload, check step by step:

1. Does the controller have **@RequestBody** on the right parameter?
2. Does the client's **Content-Type** match the media type supported by the endpoint?
3. Are JSON property names recognized by Jackson?
4. Are token types right—e.g., number vs. string, object vs. array?
5. Does Bean Validation reject values after deserialization?
6. Does the request body schema reference the right DTO and schema version?

Example body:

~~~json
{
  "customer_id": 42,
  "items": [
    {
      "product_id": 9,
      "quantity": 2
    }
  ]
}
~~~

The corresponding schema must show **customer_id** as an integer, **items** as an array, and array elements as objects containing **product_id** and **quantity**. If the schema shows **items** as a string, check the collection's generic type, DTO declaration, and custom converters.

For file uploads, **@RequestPart** and **multipart/form-data** are usually better suited than a plain JSON DTO. Document each part with its own media type and schema. If the endpoint accepts JSON metadata alongside a file, check actual requests for proper boundaries, part names, and per-part Content-Types.

Do not confuse **@DateTimeFormat** with **@JsonFormat**. **@DateTimeFormat** generally applies to values Spring binds from path or query parameters; **@JsonFormat** applies when Jackson reads or writes JSON. If dates fail to parse, determine whether the data is in the query or the body before choosing an annotation.

## 7. Distinguishing required, nullable, and validation

These three concepts are related but not synonymous:

- **required** in a schema object indicates the property must be present in the object.
- **nullable** or a schema structure allowing null indicates the property may appear with a null value.
- Bean Validation constraints such as **@NotNull**, **@NotBlank**, and **@Positive** define valid runtime values when validation is active.

For example, a property can be required to appear while allowing a null value. Conversely, a property may be optional to include, yet if present must carry a valid non-null value. Document these two dimensions independently.

Example DTO:

~~~java
public record CreateOrderRequest(
    @NotNull
    @Positive
    Long customerId,

    @NotBlank
    String reference,

    String note
) {}
~~~

In this DTO, **customerId** and **reference** carry validation constraints, whereas **note** does not. However, the generated schema also depends on Bean Validation configuration, annotations on properties, data types, and the OpenAPI version. Read **/v3/api-docs** to verify the outcome rather than inferring it solely from source code.

OpenAPI 3.0 and 3.1 represent nullability differently. OpenAPI 3.0 typically uses **nullable: true**; OpenAPI 3.1 is based on JSON Schema and can express null inside type or schema composition. Do not copy syntax from one version into documentation targeting the other.

**@Schema(requiredMode = Schema.RequiredMode.REQUIRED)**, **@Schema(nullable = true)**, **@NotNull**, and **@NotBlank** address different aspects. Use schema annotations to clarify the contract when needed, while still checking runtime validation. If the API actually permits omitting a field, never mark it required merely to make Swagger UI display an asterisk.

For enums, compare actual JSON values with the schema's enum list. If a serializer uses **toString()**, **@JsonValue**, or a custom serializer to emit codes different from Java enum constant names, document the exact set of values clients receive. Do not assume enums always serialize as Java constant names.

## 8. Inspecting generic responses, wrappers, and schema references

A common bug occurs when a controller returns a response wrapper, yet OpenAPI documents only the raw type or fails to resolve the inner data type.

Example of an explicit response type:

~~~java
public record ApiEnvelope<T>(
    String code,
    String message,
    T data
) {}

@GetMapping("/{id}")
public ApiEnvelope<OrderView> getOrder(@PathVariable Long id) {
    return new ApiEnvelope<>("OK", "Success", orderService.getView(id));
}
~~~

Keeping concrete generic type arguments in controller signatures gives type-analysis tools enough information to infer schemas. Using a raw type like **ApiEnvelope** may leave **data** without a concrete schema. Also inspect actual return types when using **ResponseEntity**, interfaces, base classes, projections, or multiple response branches.

If responses vary by subtype, inspect **oneOf**, **anyOf**, **allOf**, and discriminators. A schema using **oneOf** must list valid alternatives; if clients cannot distinguish subtypes, consider a discriminator property and mappings. Do not use **allOf** merely to merge JSON examples when no inheritance or structural composition exists.

When schemas reference via **$ref**, follow the ref into **components.schemas**. Inspect the root schema, nested schemas, and all compositions. If an expected property appears missing, it may reside in a referenced schema or be omitted by access-mode settings.

**readOnly** and **writeOnly** also affect schema interpretation. A read-only response field may be omitted from requests; a write-only field may be omitted from responses. If the same DTO is used in both directions, consider creating separate request and response DTOs for a clearer contract.

## 9. Determining whether the bug is in springdoc or the application

Once you have runtime data and OpenAPI JSON, classify the bug by evidence:

| Evidence | Where to inspect first |
| --- | --- |
| Request returns 404 or 405 | @RequestMapping, path, HTTP method, context path, gateway route |
| Request returns 400 when parsing body | Jackson deserialization, Content-Type, DTO, and converters |
| Request returns 400 with validation errors | Bean Validation, validation groups, and error messages |
| Runtime JSON is right but schema property is wrong | Jackson metadata, controller type, custom serializer, model converter |
| Schema is right but UI shows something else | OpenAPI URL loaded by UI, browser cache, config URL, or multiple groups |
| App returns right data but public URL fails | Gateway, proxy, response transformation, or caching |
| Schema lacks an operation or parameter | Controller scanning, annotation mapping, group/package/path filters |
| Response schema uses a raw type | Erased generic type, raw wrapper, or non-specific return type |

To see which document Swagger UI is reading, open the Network tab and find the swagger-config request. Read the URL or URL list in the response, then open that exact OpenAPI JSON URL. Applications may publish multiple document groups; inspecting the wrong group leads to false conclusions that operations are missing or schemas are stale.

If **/v3/api-docs** changes after a restart while the browser still shows an old schema, check browser cache, reverse proxy cache, and CDN cache. If multiple instances run different versions, send several requests through the load balancer to verify all instances return the same contract.

## 10. Fixing documentation via annotations or customizers?

Choose the fix matching the root cause of the discrepancy:

| Root cause | Preferred fix |
| --- | --- |
| Runtime JSON has wrong field names | Fix the DTO or Jackson mapping |
| Controller maps wrong parameter location | Fix @PathVariable, @RequestParam, @RequestBody, or @RequestPart |
| Schema misses generic type | Declare concrete return types |
| Missing required/format/description | Add appropriate Bean Validation or @Schema |
| Custom serializer prevents schema inference | Use a dedicated schema or ModelConverter |
| Gateway transforms public payload | Document the public contract with matching schema and test transformation |
| Need metadata edits on one group or operation | Use an appropriate OpenApiCustomizer or GroupedOpenApi |

Do not use **OpenApiCustomizer** to patch every schema when the root cause is the DTO or runtime serializer. A customizer alters only the generated document. If clients still receive the old payload, documentation and application remain out of sync.

When using a customizer, scope changes to specific paths, methods, or groups. Avoid mutating shared **components.schemas** globally if multiple operations reference the same schema. After editing, check other operations sharing that component to ensure no unintended contract changes occurred elsewhere.

## 11. Verifying with runtime and contract tests

Every fix needs two independent sets of checks.

**Runtime checks**

- Send valid requests and assert status codes, Content-Type, property names, data types, and nested structure.
- Send requests missing required fields, with wrong field types, or invalid enums; verify validation/parse errors match API design.
- Test query parameters, path variables, and headers using real URLs.
- If behind a proxy, test responses via both internal and public addresses.

**OpenAPI checks**

- Call the exact docs endpoint or group URL used by Swagger UI.
- Verify paths, methods, parameter locations, requestBody, and response codes.
- Follow $ref links to verify properties, types, formats, required, nullable, and enums.
- Confirm schemas are neither duplicated nor altered outside intended operations.
- Verify the document parses as valid JSON and passes an appropriate OpenAPI validator.

For example, a MockMvc test can verify the runtime response:

~~~java
mockMvc.perform(get("/api/orders/42")
        .accept(MediaType.APPLICATION_JSON))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.order_id").value(42))
    .andExpect(jsonPath("$.created_at").exists())
    .andExpect(jsonPath("$.customer.full_name").value("Nguyen An"));
~~~

Check OpenAPI with a separate request:

~~~java
mockMvc.perform(get("/v3/api-docs"))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.paths['/api/orders/{id}'].get").exists())
    .andExpect(jsonPath("$.components.schemas.OrderView").exists());
~~~

These assertions are illustrative examples. Adjust URLs, schema names, and JSONPath expressions to match your actual document structure. If components are named differently or schemas are inlined, inspect OpenAPI JSON before locking down assertions.

When a project has contract tests, you can store a snapshot or run semantic OpenAPI comparisons between versions. Review diffs to spot breaking changes such as renamed properties, type changes, removed response codes, required changes, or narrowed enums. Do not treat every snapshot diff as a failure; distinguish intentional changes from regressions.

## 12. Comprehensive diagnostic exercise

Follow this sequence on a Spring Boot application using springdoc-openapi:

1. Pick a GET operation with a path variable and a nested response DTO.
2. Call the endpoint with an HTTP client and save the actual JSON response.
3. Call swagger-config to identify the OpenAPI document loaded by Swagger UI.
4. Locate the path and method in OpenAPI JSON; follow $ref to the response schema.
5. List every discrepancy in property names, types, formats, required flags, nullability, and nested structure.
6. Inspect the controller signature, DTOs, Jackson annotations, ObjectMapper, validation, and gateway transformations.
7. Choose the right layer to fix: runtime mapping, data types, validation, or OpenAPI metadata.
8. Resend the same request, re-read OpenAPI JSON, and compare both results.
9. Send an invalid request to verify validation and error responses remain accurately documented.
10. Check other operations or groups sharing the schema to ensure the change caused no side effects.

You have completed the exercise when you can explain with evidence: which request was sent, which controller handled it, how Jackson produced the JSON, which schema springdoc generated, where the mismatch occurred, and which change fixed the root cause. Save sample requests, actual responses, relevant schema excerpts, and test results so future upgrades can detect contract drift.
