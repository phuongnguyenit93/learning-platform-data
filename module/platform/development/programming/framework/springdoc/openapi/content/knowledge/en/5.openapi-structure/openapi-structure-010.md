# externalDocs and Links to Supplementary Documentation

An OpenAPI specification describes how to call an API, request/response structures, and possible responses. However, some information needed by integrators sits outside the HTTP contract: business guides, onboarding flows, pagination conventions, data dictionaries, end-to-end examples, or operational documentation. OpenAPI provides the `externalDocs` object to attach links to those reference resources right at the appropriate place in the document.

With `springdoc-openapi`, you can declare `externalDocs` using `swagger-core` annotations or by configuring the OpenAPI model in Java. Springdoc includes this information in the generated JSON/YAML so readers and rendering tools can follow links to detailed documentation.

## 1. What Is the External Documentation Object?

`externalDocs` is a reference documentation object with a simple structure:

| Field | Required | Meaning |
| --- | --- | --- |
| `url` | Yes | URL of the supplementary documentation. |
| `description` | No | Short description of the link's content or purpose. |

Example:

```yaml
externalDocs:
  description: Order API integration guide
  url: https://docs.example.com/order-api/guide
```

`externalDocs` only publishes a link and its description. It does not embed webpage contents into the specification, verify whether readers have permission to access the URL, or guarantee that the target document still exists. Opening the link depends on the OpenAPI viewer, browser, and access policies of the target system.

The `description` field can use Markdown/CommonMark text as supported by OpenAPI and rendering tools. Write a brief description stating clearly what the reader will find at the link. The URL must be a valid absolute value per the contract, typically HTTPS.

## 2. Choosing the Right Placement for externalDocs

OpenAPI permits placing `externalDocs` at several different levels. Choose the level based on the documentation's scope of applicability:

| Location | Scope | Example Documentation to Link |
| --- | --- | --- |
| OpenAPI Object (document root) | Entire API | Integration handbook, general policies, developer portal page |
| Tag Object | A group of operations | Business guide for orders, customers, or payments |
| Operation Object | A specific operation | Webhook handling guide, refund workflow, endpoint call examples |
| Schema Object | A data type | Data dictionary, status code conventions, complex structure guide |

For instance, service-wide documentation belongs at the root level; a guide dedicated to the `Orders` group belongs on the tag; instructions for sending an idempotency key on order creation belong on the operation; and detailed conventions for `Money` belong on the schema.

Do not place every link at the root level if they relate only to a single endpoint or data type. Placing links close to where readers need them makes documentation easier to navigate and reduces ambiguity.

## 3. Declaring externalDocs at the API-Wide Level

For service-wide links, use the `externalDocs` attribute in `@OpenAPIDefinition`:

```java
import io.swagger.v3.oas.annotations.ExternalDocumentation;
import io.swagger.v3.oas.annotations.OpenAPIDefinition;
import io.swagger.v3.oas.annotations.info.Info;
import org.springframework.context.annotation.Configuration;

@Configuration
@OpenAPIDefinition(
    info = @Info(
        title = "Order API",
        version = "v1",
        description = "Order management API"
    ),
    externalDocs = @ExternalDocumentation(
        description = "Integration handbook, authentication, and general conventions",
        url = "https://docs.example.com/order-api/guide"
    )
)
class OpenApiDocumentationConfig {
}
```

When springdoc generates the document, the general link appears at the root of the OpenAPI document:

```yaml
openapi: 3.1.0
info:
  title: Order API
  version: v1
  description: Order management API
externalDocs:
  description: Integration handbook, authentication, and general conventions
  url: https://docs.example.com/order-api/guide
```

The `openapi` version in the example merely illustrates the top of the document; the actual specification version is configured and generated by springdoc according to the project's compatible version.

## 4. Attaching Links to Tags to Guide by API Group

Tags group operations sharing a topic. You can describe supplementary documentation directly on a tag in `@OpenAPIDefinition`:

```java
import io.swagger.v3.oas.annotations.ExternalDocumentation;
import io.swagger.v3.oas.annotations.OpenAPIDefinition;
import io.swagger.v3.oas.annotations.tags.Tag;

@OpenAPIDefinition(
    tags = {
        @Tag(
            name = "Orders",
            description = "Order management operations",
            externalDocs = @ExternalDocumentation(
                description = "Order lifecycle workflows and statuses",
                url = "https://docs.example.com/order-api/orders/lifecycle"
            )
        )
    }
)
class OrderApiTagsConfig {
}
```

Controllers can use the same tag name to assign operations to the group:

```java
import io.swagger.v3.oas.annotations.tags.Tag;

@RestController
@RequestMapping("/api/orders")
@Tag(name = "Orders")
class OrderController {
    // Endpoints in the Orders group
}
```

In the generated YAML, the tag object can contain `externalDocs`:

```yaml
tags:
  - name: Orders
    description: Order management operations
    externalDocs:
      description: Order lifecycle workflows and statuses
      url: https://docs.example.com/order-api/orders/lifecycle
```

Tag names must match consistently between metadata declarations and operations. If tag names differ due to typos or formatting, UIs may create separate groups and the link will not appear under the intended group.

## 5. Attaching Links to a Specific Operation

When documentation applies only to one operation, use `externalDocs` inside `@Operation`:

```java
import io.swagger.v3.oas.annotations.ExternalDocumentation;
import io.swagger.v3.oas.annotations.Operation;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;

@Operation(
    summary = "Create order",
    description = "Create a new order from a confirmed cart.",
    externalDocs = @ExternalDocumentation(
        description = "Order creation examples, idempotency rules, and error handling",
        url = "https://docs.example.com/order-api/orders/create"
    )
)
@PostMapping
OrderResponse create(@RequestBody CreateOrderRequest request) {
    return orderService.create(request);
}
```

The generated specification places the link inside the corresponding operation:

```yaml
paths:
  /api/orders:
    post:
      summary: Create order
      description: Create a new order from a confirmed cart.
      externalDocs:
        description: Order creation examples, idempotency rules, and error handling
        url: https://docs.example.com/order-api/orders/create
```

Operation-level links are useful when readers need workflows or examples beyond the endpoint's short description. Required information for calling the API—such as parameters, request bodies, responses, and security—must still be documented directly in OpenAPI; do not force clients to open an external page just to learn field names or basic HTTP codes.

## 6. Attaching Links to a Schema

Some data types require deeper explanation than can comfortably fit in `description`. Use `externalDocs` in `@Schema` to point to a data dictionary or domain convention:

```java
import io.swagger.v3.oas.annotations.ExternalDocumentation;
import io.swagger.v3.oas.annotations.media.Schema;
import java.math.BigDecimal;

@Schema(
    name = "Money",
    description = "Monetary value with amount and currency code",
    externalDocs = @ExternalDocumentation(
        description = "Decimal precision, rounding, and currency code conventions",
        url = "https://docs.example.com/data-models/money"
    )
)
public record Money(
    @Schema(description = "Monetary amount", example = "125000.00")
    BigDecimal amount,

    @Schema(description = "Currency code", example = "VND")
    String currency
) {
}
```

The corresponding schema section can be represented as follows:

```yaml
components:
  schemas:
    Money:
      type: object
      description: Monetary value with amount and currency code
      externalDocs:
        description: Decimal precision, rounding, and currency code conventions
        url: https://docs.example.com/data-models/money
      properties:
        amount:
          type: number
          example: 125000.00
        currency:
          type: string
          example: VND
```

If a schema is reused across multiple operations, the link attached to the schema travels with that data type across reference sites. This works well for documentation explaining the shared meaning and conventions of a model.

## 7. Configuring with an OpenAPI Bean

In projects that need conditional documentation or centralized Java configuration, you can set `ExternalDocumentation` on the `OpenAPI` model:

```java
import io.swagger.v3.oas.models.ExternalDocumentation;
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.info.Info;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class OpenApiModelConfig {

    @Bean
    OpenAPI orderOpenAPI() {
        ExternalDocumentation docs = new ExternalDocumentation()
            .description("Order API integration handbook")
            .url("https://docs.example.com/order-api/guide");

        return new OpenAPI()
            .info(new Info().title("Order API").version("v1"))
            .externalDocs(docs);
    }
}
```

The `ExternalDocumentation` model class belongs to `io.swagger.v3.oas.models`; the `@ExternalDocumentation` annotation belongs to `io.swagger.v3.oas.annotations`. Both types serve similar purposes yet are used in two different configuration styles. Do not mix up their imports.

You can combine an `OpenAPI` bean with annotations on controllers/models, though you should organize configuration intentionally and inspect the final document to prevent duplicate or unexpectedly overwritten metadata. Pick one primary configuration source for root-level links; keep annotations close to controllers or DTOs for operation- and schema-specific links.

## 8. Using Multiple Links and Organizing Target Documentation

The External Documentation Object has a single `url` field. If an operation needs to point to multiple pages, select one landing page as the primary link; that page can contain sub-links to examples, workflows, and FAQs. The `description` field can also include Markdown links when the viewer supports CommonMark.

Example:

```yaml
externalDocs:
  description: |
    See the [integration guide](https://docs.example.com/order-api/guide),
    [sample code](https://github.com/example/order-api-samples),
    and [FAQ](https://docs.example.com/order-api/faq).
  url: https://docs.example.com/order-api/guide
```

To keep links useful and durable:

- Prefer public HTTPS URLs or internal URLs with a clear access process.
- Use stable URLs and avoid links to preview pages, URLs containing tokens, session IDs, or sensitive data.
- If documentation varies by API version, include the version in the path or use a landing page supporting version navigation.
- Describe the destination specifically, such as "Retry and idempotency rules", rather than "Learn more".
- Ensure Swagger UI users and OpenAPI reading tools can access target documentation per organizational policy.
- Check links periodically in documentation workflows or CI to catch broken URLs.

Never embed secrets or credentials in URLs. OpenAPI specs may be shared more broadly than internal docs, so review access controls and data classification before publishing links.

## 9. Verifying externalDocs in Generated Documentation

After configuring, inspect the actual JSON or YAML output by springdoc. By default, endpoints are typically `/v3/api-docs` and `/v3/api-docs.yaml`; paths may have been customized in application configuration.

Example using `curl` to fetch the document:

```bash
curl -sS http://localhost:8080/v3/api-docs
curl -sS http://localhost:8080/v3/api-docs.yaml
```

In the output, verify each configured location:

- Does the root `externalDocs` field have the right general handbook URL?
- Do entries in `tags` have the right tag name, description, and URL?
- Do operations under `paths` link accurately to endpoint guides?
- Do schemas under `components.schemas` link accurately to model documentation?
- Do URLs include `https://` cleanly without truncation, bad escaping, or pointing to the wrong environment?

If an annotation does not appear in the specification, check annotation imports, annotation placement, whether springdoc scans the class/method, and the `swagger-core` version bundled with springdoc. If YAML contains the URL yet the UI fails to open it, test the URL directly in a browser and check DNS, TLS certificates, access permissions, or redirects on the documentation host.

## 10. Distinguishing externalDocs from Other Linking Mechanisms

| Mechanism | Role | When to Use |
| --- | --- | --- |
| `description` | Explain the API or schema inline | Concise details readers need right inside the contract |
| `externalDocs` | Link to an external reference document | Detailed guides, workflows, data dictionaries |
| `$ref` | Reuse an OpenAPI/schema component within the spec | Sharing models, parameters, or responses across locations |
| `servers` | Declare API server URLs for client requests | Distinguishing environments or base URLs |
| `tags` | Group operations by topic | Organizing the UI and API catalog |

`externalDocs` does not replace `$ref`: a link to a page explaining a model does not produce a schema that clients can use for code generation. Similarly, `externalDocs.url` is not a server URL for sending requests; server URLs are declared in `servers`.

## 11. Implementation Workflow

When adding documentation links to an API, follow these steps:

1. Determine at which level readers need supplementary documentation: whole API, tag, operation, or schema.
2. Choose a stable, versioned destination page with appropriate access permissions.
3. Write a `description` stating specifically what readers will find.
4. Declare via `@OpenAPIDefinition`, `@Tag`, `@Operation`, `@Schema`, or an `OpenAPI` bean accordingly.
5. Fetch `/v3/api-docs` or the YAML file to verify `externalDocs` sits in the right place.
6. Open each URL from the documentation reader's environment and check access permissions.

For example, put the Order API overview at the root level; attach the order lifecycle guide to the `Orders` tag; attach idempotency rules to the create-order operation; and attach the currency data dictionary to the `Money` schema. Each link helps readers go deeper on the right topic without cluttering the HTTP contract.
