# Multipart with Single File, Multiple Files, and Regular Form Fields

Upload APIs often need to accept one or more files alongside descriptive fields such as title, document category, notes, or metadata. HTTP represents this combination using `multipart/form-data`: each part has its own name, headers, and content. Spring Boot provides binding mechanisms to turn parts into `MultipartFile`, DTOs, or appropriate types; `springdoc-openapi` describes that structure in OpenAPI so Swagger UI and clients know how to construct requests.

The key point is that each part can carry a different content type. Files are usually binary data; text fields are usually `text/plain`; metadata can be JSON with `application/json`. Therefore, the documentation must accurately describe part names, data types, media types, and how parts repeat when uploading multiple files.

## 1. How does `multipart/form-data` work?

Unlike a regular JSON request, multipart splits the request body into multiple sections. Each section is separated by a boundary string generated by the client and declared in the `Content-Type` header.

Example of a request containing a `title` field, JSON metadata, and a file:

```http
POST /api/documents HTTP/1.1
Content-Type: multipart/form-data; boundary=----UploadBoundary

------UploadBoundary
Content-Disposition: form-data; name="title"
Content-Type: text/plain

Sales contract
------UploadBoundary
Content-Disposition: form-data; name="metadata"
Content-Type: application/json

{"category":"LEGAL","reference":"HD-2026-001"}
------UploadBoundary
Content-Disposition: form-data; name="file"; filename="contract.pdf"
Content-Type: application/pdf

<binary file content>
------UploadBoundary--
```

A multipart request can contain:

- **Text parts**: single values such as `title`, `description`, `category`.
- **JSON parts**: structured objects such as `metadata`, `options`, or complex business details.
- **File parts**: binary data, usually with a `filename` and its own content type.
- **Multiple parts with the same name**: for example, `files` appearing multiple times to send multiple files.

The boundary, `Content-Disposition`, and per-part headers belong to the transport format. HTTP clients or browsers normally generate these values. Never concatenate boundaries manually in application code when using an HTTP library with multipart support.

## 2. Declaring an endpoint to receive a single file

In Spring MVC, the `MultipartFile` type represents a file sent in a multipart request. You can use `@RequestPart` to retrieve the exact part by name:

```java
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestPart;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.multipart.MultipartFile;

@RestController
class DocumentController {

    @PostMapping(
            path = "/api/documents/upload",
            consumes = MediaType.MULTIPART_FORM_DATA_VALUE
    )
    UploadResponse upload(
            @RequestPart("file") MultipartFile file) {
        return documentService.store(file);
    }
}
```

`consumes = MediaType.MULTIPART_FORM_DATA_VALUE` declares that the endpoint accepts `multipart/form-data`. `@RequestPart("file")` specifies that the part named `file` is bound to the `MultipartFile` parameter.

For a simple single file, `@RequestParam("file") MultipartFile` can also be used in Spring MVC. `@RequestPart` makes it explicit that the parameter is a part of a multipart body; it is especially helpful when the request also has complex parts requiring conversion via an `HttpMessageConverter`.

In OpenAPI, a file is typically described using a string schema with format `binary`:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required:
          - file
        properties:
          file:
            type: string
            format: binary
```

Springdoc can infer the file schema from `MultipartFile`. If the generated result is unclear or needs explicit schema control, you can place `@Schema(type = "string", format = "binary")` in the appropriate location or declare an explicit OpenAPI request body.

## 3. Receiving files alongside text fields

An upload endpoint often needs both a file and some simple fields. In Spring MVC, you can receive them using `@RequestPart` for the file and `@RequestParam` for form fields:

```java
@PostMapping(
        path = "/api/documents",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
DocumentResponse createDocument(
        @RequestParam("title") String title,
        @RequestParam(name = "description", required = false) String description,
        @RequestPart("file") MultipartFile file) {

    return documentService.create(title, description, file);
}
```

Corresponding request:

```text
POST /api/documents
Content-Type: multipart/form-data

title       = Sales contract
description = Signed copy
file        = contract.pdf
```

`@RequestParam` can bind form fields and multipart files in Spring MVC. When used with `String`, `Integer`, enums, or simple types, Spring converts values via its conversion service. Optional fields should be marked `required = false` or use an appropriate type to express optional presence.

### 3.1. Using `@ModelAttribute` for a form DTO

If there are many simple form fields, grouping them into a DTO keeps the controller easier to read:

```java
public class DocumentUploadForm {
    @NotBlank
    private String title;

    private String description;

    private MultipartFile file;

    // getters and setters
}
```

Controller:

```java
@PostMapping(
        path = "/api/documents",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
DocumentResponse createDocument(
        @Valid @ModelAttribute DocumentUploadForm form) {
    return documentService.create(
            form.getTitle(),
            form.getDescription(),
            form.getFile()
    );
}
```

Spring MVC binds form fields by property name. `@ModelAttribute` fits forms consisting of simple values and files; it does not mean a nested object field will automatically be parsed from a JSON part. When a part contains standalone JSON, use `@RequestPart` so Spring selects an `HttpMessageConverter` based on the part's content type.

### 3.2. Describing regular fields in OpenAPI

A multipart request body can describe both text fields and files:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required:
          - title
          - file
        properties:
          title:
            type: string
            description: Document title
          description:
            type: string
            description: Optional note
          file:
            type: string
            format: binary
```

The `required` list specifies the mandatory parts. It must match server-side binding and validation logic. If `file` may be absent, omit it from `required`; if the controller requires a file, document it in the schema and enforce it at runtime.

## 4. Receiving JSON metadata and files in the same request

When metadata has multiple properties or nested structures, send the metadata as a dedicated JSON part. Use `@RequestPart` for both metadata and file:

```java
public record DocumentMetadata(
        @NotBlank String title,
        @NotBlank String category,
        String reference
) {}
```

```java
@PostMapping(
        path = "/api/documents/import",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
DocumentResponse importDocument(
        @Valid @RequestPart("metadata") DocumentMetadata metadata,
        @RequestPart("file") MultipartFile file) {
    return documentService.importDocument(metadata, file);
}
```

Spring uses each part's content type to select its conversion strategy. The `metadata` part needs `Content-Type: application/json` to be converted into `DocumentMetadata` via a JSON message converter. The `file` part is bound as `MultipartFile`.

Example invocation with curl:

```bash
curl -X POST http://localhost:8080/api/documents/import \
  -F 'metadata={"title":"Sales contract","category":"LEGAL","reference":"HD-2026-001"};type=application/json' \
  -F 'file=@./contract.pdf;type=application/pdf'
```

If the `metadata` part is sent as `text/plain` or lacks an appropriate content type, Spring may fail to find a converter for the DTO and return `415 Unsupported Media Type` or a content conversion error. Inspect each part's headers when debugging.

### 4.1. Describing per-part content types using `encoding`

OpenAPI uses `encoding` inside the Media Type Object to describe how individual properties of a multipart body are encoded. Example:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required:
          - metadata
          - file
        properties:
          metadata:
            $ref: '#/components/schemas/DocumentMetadata'
          file:
            type: string
            format: binary
      encoding:
        metadata:
          contentType: application/json
        file:
          contentType: application/pdf, image/png
```

`encoding.metadata.contentType` explicitly states that the `metadata` part is JSON. `encoding.file.contentType` narrows the media types expected in documentation for the file part. Multiple media types are separated by commas. The server must still validate actual file content and types rather than trusting client-supplied `Content-Type` alone.

A shared metadata schema can be added:

```yaml
components:
  schemas:
    DocumentMetadata:
      type: object
      required:
        - title
        - category
      properties:
        title:
          type: string
        category:
          type: string
          enum: [LEGAL, FINANCE, OTHER]
        reference:
          type: string
```

### 4.2. Declaring `encoding` in Swagger annotations

When you need to adjust the documentation generated by springdoc, you can declare the request body using Swagger Annotations. The example below uses a representative schema for the multipart form:

```java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.media.Content;
import io.swagger.v3.oas.annotations.media.Encoding;
import io.swagger.v3.oas.annotations.media.Schema;

@Operation(
    requestBody = @io.swagger.v3.oas.annotations.parameters.RequestBody(
        required = true,
        content = @Content(
            mediaType = MediaType.MULTIPART_FORM_DATA_VALUE,
            schema = @Schema(implementation = DocumentMultipartSchema.class),
            encoding = {
                @Encoding(
                    name = "metadata",
                    contentType = MediaType.APPLICATION_JSON_VALUE
                ),
                @Encoding(
                    name = "file",
                    contentType = "application/pdf, image/png"
                )
            }
        )
    )
)
@PostMapping(
    path = "/api/documents/import",
    consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
DocumentResponse importDocument(
        @Valid @RequestPart("metadata") DocumentMetadata metadata,
        @RequestPart("file") MultipartFile file) {
    return documentService.importDocument(metadata, file);
}
```

The representative schema can be declared separately to control documentation structure:

```java
public class DocumentMultipartSchema {
    @Schema(description = "Document metadata")
    private DocumentMetadata metadata;

    @Schema(type = "string", format = "binary")
    private MultipartFile file;
}
```

This is OpenAPI metadata; the representative schema class does not have to be the object bound directly by Spring. The controller still receives parts via `@RequestPart` parameters. After adding annotations, always inspect `/v3/api-docs` to ensure the schema and `encoding` are generated properly, as input structures and annotations can affect inference.

## 5. Uploading multiple files

An HTML form can send multiple files via an input with the `multiple` attribute:

```html
<input type="file" name="files" multiple>
```

The client sends each file as a separate part sharing the same name `files`. In Spring MVC, you can receive them as `List<MultipartFile>`:

```java
@PostMapping(
        path = "/api/documents/batch",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
BatchUploadResponse uploadMany(
        @RequestPart("files") List<MultipartFile> files) {
    return documentService.storeAll(files);
}
```

The request can contain multiple parts with the same name:

```text
Content-Disposition: form-data; name="files"; filename="a.pdf"
...
Content-Disposition: form-data; name="files"; filename="b.pdf"
...
Content-Disposition: form-data; name="files"; filename="c.pdf"
...
```

In OpenAPI, an array of files is described as an `array` with `string/binary` items:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required:
          - files
        properties:
          files:
            type: array
            items:
              type: string
              format: binary
```

If you need to annotate this on a schema DTO:

```java
import io.swagger.v3.oas.annotations.media.ArraySchema;
import io.swagger.v3.oas.annotations.media.Schema;

public class BatchUploadSchema {
    @ArraySchema(
        schema = @Schema(type = "string", format = "binary"),
        arraySchema = @Schema(description = "List of files to upload")
    )
    private List<MultipartFile> files;
}
```

Each element in the array corresponds to a part with the same name. In annotations, `@ArraySchema` helps describe the element type and array metadata. Inspect the generated OpenAPI JSON because Swagger Annotations versions can influence how annotations are rendered.

Invoke with curl by repeating the same field name:

```bash
curl -X POST http://localhost:8080/api/documents/batch \
  -F 'files=@./contract-a.pdf;type=application/pdf' \
  -F 'files=@./contract-b.pdf;type=application/pdf' \
  -F 'files=@./contract-c.pdf;type=application/pdf'
```

Do not send three files as a single concatenated filename string. Each file must be passed as its own part matching the name declared by the controller.

## 6. Multiple files alongside regular data fields

A batch endpoint often requires shared fields for the entire upload batch, per-file metadata, or both. A simple example with `folderId`, a note, and a list of files:

```java
@PostMapping(
        path = "/api/folders/{folderId}/documents",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
BatchUploadResponse uploadToFolder(
        @PathVariable UUID folderId,
        @RequestParam("note") String note,
        @RequestPart("files") List<MultipartFile> files) {
    return documentService.storeAll(folderId, note, files);
}
```

The OpenAPI body describes `note` and `files` in the same object:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required: [note, files]
        properties:
          note:
            type: string
          files:
            type: array
            items:
              type: string
              format: binary
```

`folderId` is in the path and is therefore described as a path parameter, not inside the multipart request body. When designing the schema, maintain a clean boundary between path/query parameters and body parts.

If each file needs its own metadata, you can use a JSON part containing a list of metadata alongside a list of files, though you must define a convention for pairing metadata to files—such as by order or a client-generated ID. Multipart does not automatically guarantee pairing between two independent lists.

## 7. Distinguishing `@RequestParam`, `@RequestPart`, and `@ModelAttribute`

These three mechanisms have related but distinct roles in Spring MVC:

| Mechanism | When to use | How it converts |
|---|---|---|
| `@RequestParam` | Simple form fields or file parts fetched by name | Spring binding and type conversion. |
| `@RequestPart` | Specific parts, especially JSON/XML or content needing a message converter | Selects `HttpMessageConverter` based on the part's content type. |
| `@ModelAttribute` | Multiple form fields grouped into a DTO, potentially including `MultipartFile` | Data binding into properties by name. |

Selection examples:

- `title` is a simple string: `@RequestParam("title") String title`.
- `file` is an uploaded file: `@RequestPart("file") MultipartFile file` or `@RequestParam("file") MultipartFile file`.
- `metadata` is a JSON object: `@RequestPart("metadata") DocumentMetadata metadata`.
- Multiple simple form fields and files: `@ModelAttribute DocumentUploadForm form`.

Avoid using `@RequestBody` for a regular JSON DTO when the endpoint actually receives `multipart/form-data`. `@RequestBody` normally reads the entire request body via one message converter; for multipart, use `@RequestPart`, `@RequestParam`, or `@ModelAttribute` as appropriate for each part.

## 8. Spring MVC and Spring WebFlux

Spring MVC is built on the Servlet API and typically uses `MultipartFile`. Spring WebFlux uses a reactive multipart model, typically `FilePart` or `Part`.

WebFlux example:

```java
@PostMapping(
        path = "/api/documents/upload",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
Mono<DocumentResponse> upload(
        @RequestPart("file") FilePart file) {
    return documentService.store(file);
}
```

`FilePart` enables processing content reactively. For large files, consider streaming writes to avoid loading the entire payload into memory. `MultipartFile` belongs to the Servlet MVC stack; do not use it as the default type for WebFlux.

In WebFlux, `@RequestParam` is primarily for query parameters. To read multipart parts, use `@RequestPart` or the corresponding `Part`/`Flux<Part>` mechanism. Do not copy Spring MVC form-binding patterns verbatim into WebFlux without checking the active framework's APIs.

The springdoc starter must also match the web stack: `springdoc-openapi-starter-webmvc-ui` or `springdoc-openapi-starter-webmvc-api` for MVC; `springdoc-openapi-starter-webflux-ui` or `springdoc-openapi-starter-webflux-api` for WebFlux.

## 9. Size limits and file checks

OpenAPI documents describe data types and can document some limits, yet the server must enforce upload limits at runtime. In Spring Boot with Servlet MVC, you can configure per-file and total-request sizes:

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 25MB
```

`max-file-size` limits the size of a single file; `max-request-size` limits the entire multipart request, including all files and other parts. The total request limit must be greater than or equal to the expected total payload plus multipart overhead.

Beyond framework limits, the application should verify:

- Whether the file is empty and the maximum number of files.
- File extension, media type, and actual binary content signature.
- Client-supplied filenames; never use them directly as storage paths.
- Uploader permissions and access rights to the target resource.
- Malware scanning or content inspection per system policy.
- Storage location, retention period, and temporary file cleanup on error.

Client-supplied part `Content-Type` headers cannot be trusted blindly. If business rules accept only PDF or PNG, verify actual content on the server; `encoding.contentType` in OpenAPI only documents the contract and guides clients.

## 10. Validation for multipart requests

Metadata fields can use Bean Validation. For a JSON part, place `@Valid` before `@RequestPart`:

```java
@PostMapping(
        path = "/api/documents/import",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
DocumentResponse importDocument(
        @Valid @RequestPart("metadata") DocumentMetadata metadata,
        @RequestPart("file") MultipartFile file) {

    if (file.isEmpty()) {
        throw new InvalidUploadException("File must not be empty");
    }
    return documentService.importDocument(metadata, file);
}
```

For a form DTO using `@ModelAttribute`, place `@Valid` on the DTO parameter to check fields with validation annotations. Constraints such as `@NotBlank`, `@Size`, or `@Pattern` can describe text fields; file size and file count should be checked with appropriate logic or custom validators.

OpenAPI can express certain constraints in the schema, such as `minItems`, `maxItems`, `minLength`, or `maxLength`. Not every file business rule can be fully represented in the schema. Document additional limits, accepted formats, and potential errors in the operation/responses.

## 11. Verifying OpenAPI docs generated by springdoc

After declaring a multipart endpoint, open `/v3/api-docs` or your configured endpoint and verify:

1. Request body has media type `multipart/form-data`.
2. Property names match the part names accepted by the controller.
3. A single file has schema `type: string`, `format: binary`.
4. Multiple files have schema `type: array` and `items` of `string/binary`.
5. Text fields have accurate types and required/optional states.
6. JSON parts have accurate schemas and `encoding` declares `application/json` when needed.
7. Allowed file content types are appropriately described.

Example desired request body:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        required:
          - metadata
          - files
        properties:
          metadata:
            $ref: '#/components/schemas/DocumentMetadata'
          files:
            type: array
            items:
              type: string
              format: binary
      encoding:
        metadata:
          contentType: application/json
        files:
          contentType: application/pdf, image/png
```

If springdoc generates `application/json` instead of `multipart/form-data`, inspect `consumes` on the mapping and request body annotations. If a file appears as an object with internal fields instead of `string/binary`, declare the schema explicitly with Swagger Annotations and re-check the output.

## 12. Testing upload endpoints

### 12.1. Testing with curl

Single file with text fields:

```bash
curl -X POST http://localhost:8080/api/documents \
  -F 'title=Sales contract' \
  -F 'description=Signed copy' \
  -F 'file=@./contract.pdf;type=application/pdf'
```

JSON metadata with file:

```bash
curl -X POST http://localhost:8080/api/documents/import \
  -F 'metadata={"title":"Contract","category":"LEGAL"};type=application/json' \
  -F 'file=@./contract.pdf;type=application/pdf'
```

Multiple files:

```bash
curl -X POST http://localhost:8080/api/documents/batch \
  -F 'files=@./a.pdf;type=application/pdf' \
  -F 'files=@./b.png;type=image/png'
```

When using `curl -F`, curl automatically generates the boundary and multipart headers. In browsers, when sending `FormData` with `fetch`, do not set the `Content-Type: multipart/form-data` header manually either; let the browser add the boundary accurately.

### 12.2. Testing with MockMvc

Spring MVC Test supports building multipart requests with `MockMultipartFile`:

```java
@SpringBootTest
@AutoConfigureMockMvc
class DocumentUploadTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void uploadsOneFileWithTextFields() throws Exception {
        MockMultipartFile file = new MockMultipartFile(
                "file",
                "contract.pdf",
                MediaType.APPLICATION_PDF_VALUE,
                "sample-pdf-content".getBytes(StandardCharsets.UTF_8)
        );

        mockMvc.perform(multipart("/api/documents")
                        .file(file)
                        .param("title", "Sales contract")
                        .param("description", "Signed copy"))
                .andExpect(status().isOk());
    }
}
```

For JSON metadata, create a multipart part with content type `application/json`:

```java
MockMultipartFile metadata = new MockMultipartFile(
        "metadata",
        "",
        MediaType.APPLICATION_JSON_VALUE,
        "{\"title\":\"Contract\",\"category\":\"LEGAL\"}"
                .getBytes(StandardCharsets.UTF_8)
);

MockMultipartFile file = new MockMultipartFile(
        "file", "contract.pdf", MediaType.APPLICATION_PDF_VALUE,
        "sample-pdf-content".getBytes(StandardCharsets.UTF_8)
);

mockMvc.perform(multipart("/api/documents/import")
                .file(metadata)
                .file(file))
        .andExpect(status().isOk());
```

For multiple files, attach multiple `MockMultipartFile` instances with the same name `files`:

```java
mockMvc.perform(multipart("/api/documents/batch")
                .file(new MockMultipartFile(
                        "files", "a.pdf", MediaType.APPLICATION_PDF_VALUE,
                        new byte[]{1, 2, 3}))
                .file(new MockMultipartFile(
                        "files", "b.pdf", MediaType.APPLICATION_PDF_VALUE,
                        new byte[]{4, 5, 6})))
        .andExpect(status().isOk());
```

These tests illustrate how to construct requests. In real projects, add assertions for file count, filenames, stored contents, bound metadata, and error cases such as missing parts, wrong content types, empty files, or size limit violations.

## 13. Common mistakes

- **Forgetting `consumes = multipart/form-data`**: the mapping may fail to match requests or generate the wrong media type in docs. Declare `consumes` explicitly on upload endpoints.
- **Part name mismatch**: controller expects `@RequestPart("file")` while client sends `document`; Spring cannot locate the required part.
- **Sending JSON metadata as `text/plain`**: message converters cannot convert the part into a DTO. Send `Content-Type: application/json` for the part.
- **Using `@RequestBody` for the entire multipart**: pick `@RequestPart`, `@RequestParam`, or `@ModelAttribute` per part.
- **Describing multiple files as a single string**: use a `string/binary` array and send multiple parts sharing the same name.
- **Setting `Content-Type` manually when sending `FormData`**: omits the boundary; let the browser or HTTP client build the header.
- **Trusting client-supplied `Content-Type` or filenames**: validate file content and sanitize filenames on the server.
- **Missing request size limits**: configure upload limits and handle oversized request errors.
- **Using `MultipartFile` in WebFlux**: use `FilePart`/`Part` per the reactive stack.
- **Checking only Swagger UI**: call endpoints with curl or integration tests and cross-check `/v3/api-docs`.

## 14. Multipart API design workflow

1. **List every part**: name, role, data type, required or optional.
2. **Choose appropriate binding**: `@RequestParam` for simple fields, `@RequestPart` for files/JSON parts, `@ModelAttribute` for form DTOs.
3. **Declare media types**: endpoint uses `multipart/form-data`; individual parts use accurate content types.
4. **Describe the OpenAPI schema**: files as `string/binary`, multiple files as arrays, metadata referencing DTO schemas.
5. **Add the Encoding Object**: set `contentType` for JSON parts and restrict file types where needed.
6. **Enforce limits and validation**: size, count, format, content, and upload permissions.
7. **Verify generated docs**: confirm `requestBody`, properties, `required`, schemas, and encoding.
8. **Test real requests**: use curl, MockMvc/WebTestClient, and real consumers.

## 15. Review checklist

- [ ] Mapping declares `consumes = multipart/form-data`.
- [ ] Client part names match `@RequestPart`, `@RequestParam`, or DTO properties.
- [ ] Single files are described as `type: string`, `format: binary`.
- [ ] Multiple files are described as an array of `string/binary` and sent as multiple parts with the same name.
- [ ] Text fields have accurate schemas and required/optional states.
- [ ] JSON metadata uses an `application/json` part and is bound with `@RequestPart`.
- [ ] `encoding` describes per-part content types accurately when needed.
- [ ] Spring MVC uses `MultipartFile`; WebFlux uses `FilePart`/`Part` appropriately.
- [ ] Per-file and total-request size limits are configured.
- [ ] Uploaded files undergo content, permission, and storage-name validation on the server.
- [ ] `/v3/api-docs` reflects the multipart request body accurately.
- [ ] Integration tests cover single-file, multi-file, metadata, and error cases.
