# Reviewing Description Clarity, Example Accuracy, and Integrator Usability

A syntactically valid OpenAPI document can still be hard to use if operation names are vague, schemas omit constraints, examples do not match real data, or authentication is undocumented. This hands-on exercise establishes a workflow to review documentation generated by springdoc-openapi from Spring Boot controllers, aiming to let an integrating team understand the contract, construct valid requests, and handle responses without guessing API behavior.

We will use an order creation API as an example. The same workflow applies to internal APIs, partner APIs, and documentation groups created with `GroupedOpenApi`.

## 1. Identifying users and documentation scope

Before editing annotations, identify who will read the documentation and what tasks they need to complete. Integrators typically need to know:

- The URL and HTTP method to invoke an operation.
- How to pass path parameters, query parameters, headers, and request bodies.
- Required fields, data types, formats, bounds, and valid values.
- Authentication methods, required permissions, and responses for invalid tokens.
- Success responses, error responses, key headers, and bodyless response cases.
- Copyable examples they can run in an authorized environment.
- API version, server URLs, and deprecated operations.

State clearly which API, environment, and contract version the document describes. A group named `partner` may publish only partner-facing APIs; an `internal` group may contain internal operations. Readers must be able to confirm they are viewing the right document and access scope.

## 2. Reviewing operation descriptions

Each operation should have a short `summary` clearly stating the action and resource; `description` should explain business conditions and behavior callers must know. `operationId` must be unique and stable so client code generators can use it as a function name.

Writing examples:

| Element | Weak description | Helpful description for integrators |
| --- | --- | --- |
| `summary` | `Order API` | `Create an order` |
| `description` | `Create an order` | `Creates an order from items available for sale. Returns the order ID and initial status; the total amount is calculated server-side.` |
| `operationId` | `postApiOrders1` | `createOrder` |

Description does not need to repeat summary verbatim. Add details that affect how callers invoke the endpoint or handle results—such as inventory check rules, line-item limits, status meanings, idempotency, authorization conditions, or retry behavior. Document only guarantees that the implementation actually enforces.

Parameters also need clear descriptions:

- Path parameters: which resource they identify, format, and a valid example.
- Query parameters: filters, sorting syntax, defaults, page limits, and omission behavior.
- Headers: purpose, format, and when required.
- Request body: media type, required fields, bounds, and cross-field rules.

Avoid vague phrases like "ID of the object" when an API has multiple ID types. Specify that `orderId` is the order's UUID, `customerId` is the customer identifier, and whether values are case-sensitive if that affects API calls.

## 3. Reviewing request and response schemas

Schemas must reflect actual DTOs and validation behavior. For every property, verify JSON name, type, `format`, required status, nullability, bounds, enum values, and business meaning. Do not assume a field is required merely because Java uses a primitive type; cross-check both validation and actually accepted payloads.

Example order creation request:

```java
import io.swagger.v3.oas.annotations.media.Schema;
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import jakarta.validation.constraints.Positive;
import java.util.List;

public record CreateOrderRequest(
        @NotBlank
        @Schema(description = "Assigned customer ID", example = "cus_123")
        String customerId,

        @NotEmpty
        @Valid
        @Schema(description = "List of products to order")
        List<OrderLineRequest> lines
) {}

public record OrderLineRequest(
        @NotBlank
        @Schema(description = "Product SKU code", example = "SKU-RED-01")
        String sku,

        @Positive
        @Schema(description = "Quantity must be greater than 0", example = "2", minimum = "1")
        int quantity
) {}
```

`@NotBlank`, `@NotEmpty`, and `@Positive` validate requests only when validation is enabled in the application—for example via `@Valid` at the request binding point. OpenAPI annotations describe schemas; they do not enforce validation themselves. Therefore, compare documentation against DTOs, controllers, and error-handling configuration.

A response can be documented using clearly formatted data types:

```java
import io.swagger.v3.oas.annotations.media.Schema;
import java.math.BigDecimal;
import java.time.OffsetDateTime;
import java.util.UUID;

public enum OrderStatus {
    CREATED, CONFIRMED, CANCELLED
}

public record OrderResponse(
        @Schema(description = "Unique order identifier", example = "7d444840-9dc0-11d1-b245-5ffdce74fad2")
        UUID id,

        @Schema(description = "Current order status", example = "CREATED")
        OrderStatus status,

        @Schema(description = "Server-calculated total amount", example = "125000.00")
        BigDecimal total,

        @Schema(description = "Order creation timestamp in ISO 8601", example = "2026-11-20T10:15:30+07:00")
        OffsetDateTime createdAt
) {}
```

When reviewing schemas, pay special attention to these points:

1. `UUID`, date-times, dates, decimals, and binary data must carry matching formats rather than being left as arbitrary strings when tools can represent them accurately.
2. Enums in documentation must match values the application actually returns and accepts. Do not add "planned" values that are not yet implemented.
3. Optional fields, nullable fields, and fields that may be omitted carry distinct meanings. Document how the server handles each case.
4. Property names in JSON must match actual serialization, including when DTOs use `@JsonProperty` or naming strategies.
5. Shared schemas need stable names and semantics. Prevent two different structures from accidentally sharing one schema solely because they share field names.
6. For collections and pagination, document element structure, ordering, `page`, `size`, `totalElements`, cursors, or continuation tokens according to the real contract.

## 4. Making request and response examples usable

Good examples must be valid JSON, match the schema, and depict a realistic business scenario. Integrators often copy examples to build their first request, so a broken example costs them debugging time even when the endpoint works properly.

Example request:

```json
{
  "customerId": "cus_123",
  "lines": [
    {
      "sku": "SKU-RED-01",
      "quantity": 2
    }
  ]
}
```

Example `201 Created` response:

```json
{
  "id": "7d444840-9dc0-11d1-b245-5ffdce74fad2",
  "status": "CREATED",
  "total": 125000.00,
  "createdAt": "2026-11-20T10:15:30+07:00"
}
```

During review, check every example against these questions:

- Do property names match actual JSON?
- Are data types accurate—for instance `quantity` as integer, `total` as decimal number, and `createdAt` as date-time with offset?
- Are all required fields present? Is any field set to `null` when the schema forbids null?
- Are enum values, string lengths, numeric bounds, and formats valid?
- Does the example response match the status code it is attached to?
- Does sample data accidentally contain real tokens, personal data, or production records?
- Can the example be copied to call the API in the chosen environment without guessing extra fields?

Never use fabricated examples to hide unclear behavior. If totals are calculated server-side, request examples must not tell clients to send `total`. If the server generates `id`, request examples must not expect callers to invent an ID. If the API accepts multiple payload variants, provide separate named examples explaining each variant's purpose.

## 5. Documenting error responses and authentication rules

Listing only `200` or `201` responses is insufficient. Integrators need to know which errors can occur and how to handle them. Cross-check actual responses from controllers, exception handlers, and Spring Security.

Example error DTO:

```java
import io.swagger.v3.oas.annotations.media.Schema;

public record ApiError(
        @Schema(example = "VALIDATION_ERROR")
        String code,

        @Schema(example = "quantity must be greater than 0")
        String message,

        @Schema(description = "Identifier for looking up support logs", example = "req_01JABCXYZ")
        String traceId
) {}
```

A response table for the order creation operation can be reviewed as follows:

| HTTP status | Case | What integrators need to know |
| --- | --- | --- |
| `201` | Order created | Response schema, initial status, and `Location` header if returned by the server. |
| `400` | Malformed request or validation failure | Error structure, offending fields, and how to fix the payload. |
| `401` | Missing or invalid token | How to obtain a token and when re-authentication is required. |
| `403` | Authenticated identity lacks permission | Required permissions or scopes. |
| `409` | State or business rule conflict | Conflict condition and whether the caller can retry after updating data. |

Do not add a status code to OpenAPI merely because it is common. If the API does not return `409`, do not promise `409`. Conversely, if the exception handler actually returns `400` or `422`, documentation must reflect that exact status and error structure. For bodyless responses like `204 No Content`, explicitly state there is no response content.

## 6. Attaching descriptions and examples to controllers with springdoc-openapi

OpenAPI annotations enrich handlers registered by Spring. The example below illustrates an order creation operation; the service layer is assumed to exist in the application.

```java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.media.Content;
import io.swagger.v3.oas.annotations.media.ExampleObject;
import io.swagger.v3.oas.annotations.media.Schema;
import io.swagger.v3.oas.annotations.responses.ApiResponse;
import io.swagger.v3.oas.annotations.responses.ApiResponses;
import io.swagger.v3.oas.annotations.security.SecurityRequirement;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    @Operation(
            operationId = "createOrder",
            summary = "Create an order",
            description = "Creates an order from a list of SKUs and quantities. The server validates input, calculates the total, and returns the initial status.",
            security = @SecurityRequirement(name = "bearerAuth")
    )
    @ApiResponses({
            @ApiResponse(
                    responseCode = "201",
                    description = "Order created successfully",
                    content = @Content(
                            mediaType = "application/json",
                            schema = @Schema(implementation = OrderResponse.class),
                            examples = @ExampleObject(
                                    name = "createdOrder",
                                    summary = "Newly created order",
                                    value = "{\"id\":\"7d444840-9dc0-11d1-b245-5ffdce74fad2\",\"status\":\"CREATED\",\"total\":125000.00,\"createdAt\":\"2026-11-20T10:15:30+07:00\"}"
                            )
                    )
            ),
            @ApiResponse(
                    responseCode = "400",
                    description = "Invalid request",
                    content = @Content(
                            mediaType = "application/json",
                            schema = @Schema(implementation = ApiError.class),
                            examples = @ExampleObject(
                                    value = "{\"code\":\"VALIDATION_ERROR\",\"message\":\"quantity must be greater than 0\",\"traceId\":\"req_01JABCXYZ\"}"
                            )
                    )
            ),
            @ApiResponse(responseCode = "401", description = "Missing or invalid token"),
            @ApiResponse(responseCode = "403", description = "Not authorized to create orders"),
            @ApiResponse(responseCode = "409", description = "Order conflicts with current business state")
    })
    public ResponseEntity<OrderResponse> createOrder(
            @Valid @RequestBody CreateOrderRequest request) {
        OrderResponse created = orderService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }
}
```

Adjust the snippet to match your application's actual responses. If security filters return an error body, add matching schemas and examples for `401`/`403`; if they return no body, keep descriptions without content. If the API returns a `Location` header, document that header when the implementation actually sends it. Annotations do not replace validation, authentication, or exception-handling logic.

Define security schemes in OpenAPI configuration, for example:

```java
import io.swagger.v3.oas.annotations.OpenAPIDefinition;
import io.swagger.v3.oas.annotations.info.Info;
import io.swagger.v3.oas.annotations.security.SecurityScheme;
import io.swagger.v3.oas.annotations.enums.SecuritySchemeType;
import org.springframework.context.annotation.Configuration;

@Configuration
@OpenAPIDefinition(
        info = @Info(
                title = "Orders API",
                version = "v1",
                description = "Order management API for integrating systems"
        )
)
@SecurityScheme(
        name = "bearerAuth",
        type = SecuritySchemeType.HTTP,
        scheme = "bearer",
        bearerFormat = "JWT"
)
public class OpenApiConfiguration {}
```

`@SecurityScheme` declares the authentication method; `@SecurityRequirement` attaches that requirement to an operation or document scope. Verify which operations actually require a token. Do not apply global security if public unauthenticated endpoints exist, unless the contract intentionally requires it.

## 7. Inspecting the generated document, not just reading annotations

Annotations are inputs; the JSON/YAML generated by springdoc is the document tools and integrators actually consume. After starting the application with the right profile, fetch API docs:

```bash
curl -sS http://localhost:8080/v3/api-docs -o openapi.json
curl -sS http://localhost:8080/v3/api-docs.yaml -o openapi.yaml
```

If documentation is grouped, fetch the exact `/v3/api-docs/{group}` URL. Verify JSON/YAML contains:

- Accurate `info.title`, `info.version`, and API scope description.
- Paths and HTTP methods matching running mappings.
- Unique `operationId` values across operations.
- Clear summaries, descriptions, and parameters.
- Request bodies with appropriate media types and schemas.
- Responses with right statuses, content, schemas, and required headers.
- Component schemas with accurate properties, required flags, enums, and formats.
- Security schemes and requirements reflecting real policy.
- Syntactically valid examples matching schemas.

You can run an OpenAPI linter in CI to check structure and conventions. Example with a project-pinned version of Redocly CLI:

```bash
npx @redocly/cli lint openapi.yaml
```

Linters detect structural, reference, or convention issues, but cannot verify by themselves that examples reflect real business data or that endpoints actually return documented statuses. Combine integration tests with contract-based reviews.

## 8. Testing the contract integrators will use

Do not stop at verifying `/v3/api-docs` returns HTTP `200`. Assert that critical operations are present and expected metadata is generated properly. Example with MockMvc, Jackson, and AssertJ:

```java
MvcResult result = mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andReturn();

JsonNode document = objectMapper.readTree(
        result.getResponse().getContentAsString());
JsonNode createOrder = document
        .path("paths")
        .path("/api/orders")
        .path("post");

assertThat(createOrder.path("operationId").asText())
        .isEqualTo("createOrder");
assertThat(createOrder.path("summary").asText())
        .isEqualTo("Create an order");
assertThat(createOrder.path("responses").has("201")).isTrue();
assertThat(createOrder.path("requestBody").isMissingNode()).isFalse();
```

Beyond checking the document, run a round of real API calls in a test environment:

1. Send a valid request based on the example and confirm the response matches the documented status, content type, schema, and values.
2. Omit a required field or send a malformed value; confirm the error matches the status and error schema in OpenAPI.
3. Call without a token and with an under-privileged token; confirm actual `401`/`403` behavior.
4. Send a non-existent ID or conflicting state if supported by the API; confirm status and error content.
5. Verify the server URLs and groups integrators will use; confirm the document does not point to localhost or unreachable environments.

If clients are generated from OpenAPI, generate or compile a client in CI for a representative operation. This catches schemas or operation names that break integration tooling before release.

## 9. Evaluating usability from the integrator's perspective

A reviewer should try completing a realistic workflow using only the documentation. For an orders API, the workflow might involve obtaining a token, creating an order, reading the returned ID, and querying its status. Note every point where you had to ask the API author or guess.

| Integrator step | What the docs must provide | Signs something needs fixing |
| --- | --- | --- |
| Pick environment | Server URL, version, and group scope | Only `localhost` shown, missing environment URLs, or unclear API version. |
| Authenticate | Security scheme, token format, and required scopes/roles | UI has Authorize button but operations lack matching security. |
| Build request | Method, path, media type, parameters, and body example | Missing required fields or example fails to run. |
| Read response | Status, schema, enums, headers, and examples | Actual response differs from schema or omits key fields. |
| Handle errors | Error statuses, error schema, and remediation hints | Only "Bad Request" text with no error structure. |
| Long-term integration | Versioning, deprecation, and compatible changes | Operations renamed or removed without migration info. |

If a reviewer cannot complete this workflow, determine whether the missing information belongs in controller annotations, DTOs/schemas, security configuration, server URLs, or error handling. Fix it at the contract source and regenerate documentation.

## 10. Reviewing groups, versions, and contract changes

With `GroupedOpenApi`, review each group as its own documentation product. Verify group name, path set, packages, security, and server URLs. Do not assume an operation present in the default group also appears in the partner group.

Before releasing a new version:

- Compare the new OpenAPI document against the released baseline.
- Check for removed paths or methods, newly required request fields, removed enum values, altered response schemas, and tightened security.
- Use `deprecated: true` or the corresponding annotation when an operation/field remains supported yet should not be used for new integrations; note alternatives and sunset timelines once agreed.
- Check that `info.version` reflects the contract version per project convention. Do not bump the version solely because a build number changed if the contract stayed unchanged under that convention.
- Keep `operationId` and schema names used by client generators stable unless a clear migration plan exists.

Automated diffs classify compatibility changes, yet context still matters. For instance, adding a response enum value can break generated clients if they assume closed enums; description edits may not break syntax yet still alter business expectations. Evaluate both technical impact and integrator impact.

## 11. Exercise acceptance checklist

Mark as passing only after verifying the generated document and at least one real integration workflow.

| Item | PASS criteria |
| --- | --- |
| Scope | Correct API, group, server URL, and version. |
| Descriptions | Short summary; description covers necessary behavior and constraints. |
| Operations | Accurate paths, methods, `operationId`, and parameters. |
| Schemas | Types, formats, required, nullable, enums, and validation align with implementation. |
| Examples | Request, success response, and error response are valid JSON, match schemas, and use safe sample data. |
| Security | Schemes and requirements match policy; per-operation permissions are documented. |
| Responses | Statuses, bodies, content types, and headers reflect actual behavior. |
| Groups/versions | Groups checked individually; contract changes evaluated. |
| Testing | API docs checked in CI; representative valid and error requests executed. |
| Integrability | Reviewer completes the sample workflow without guessing essential details. |

Record findings in the format `Location → Issue → Integrator impact → Fix → Verification evidence`. For example: `POST /api/orders → missing 400 example → client does not know validation error structure → add ApiError schema and example from exception handler → MockMvc confirms actual response matches OpenAPI`.

## Conclusion

Reviewing OpenAPI documentation requires combining clear descriptions, accurate schemas, runnable examples, and verification of actual behavior. springdoc-openapi generates contracts from Spring Boot controllers, yet final quality depends on annotations, DTOs, security, exception handlers, and testing rigor. When a reviewer can pick the right group, authenticate, send requests, read responses, and handle errors solely from the documentation, the API is much closer to being ready for integrators.
