# Verifying Reactive Documentation with WebTestClient or Equivalent Tools

In a Spring WebFlux application, API testing must verify both reactive runtime behavior when requests run and the OpenAPI documentation generated by springdoc-openapi. A controller can return the right Java Mono or Flux type while the docs describe the wrong schema, media type, or status code. Conversely, OpenAPI JSON can be structurally valid while the actual endpoint returns a body or headers that differ from the contract.

WebTestClient is well suited for sending requests and asserting WebFlux responses without writing a separate HTTP client. You can use it to test controllers, RouterFunctions, OpenAPI JSON/YAML, grouped documents, and Swagger UI config. This lesson covers structuring test layers, writing assertions for schemas and media types, testing reactive streams, and bringing contract verification into CI.

## 1. Two Distinct Testing Goals to Separate

A solid test suite verifies two distinct outputs:

- **Generated documentation:** operations, parameters, request bodies, responses, schemas, security, and media types in OpenAPI.
- **Runtime behavior:** status codes, headers, bodies, and how reactive publishers emit data when clients send requests.

For example, a controller returns Flux<OrderSummary> with application/json. OpenAPI must describe a JSON array with OrderSummary items. Documentation tests check the array schema; runtime tests send a request and confirm the body is indeed a JSON list.

The two test suites complement each other:

| Test Group | Question to Answer |
|---|---|
| OpenAPI document tests | Does springdoc generate the right paths, operations, schemas, responses, and security? |
| Runtime API tests | Does WebFlux return the right status, Content-Type, headers, and body? |
| Streaming tests | Do SSE/NDJSON endpoints emit the right media type, framing, and data? |
| UI configuration tests | Does Swagger UI load the right spec URL and settings? |
| Contract validation | Is the document valid and do all references resolve? |

Do not rely on a single test to conclude the entire contract is sound. Having a 404 response in the spec does not prove the controller actually returns 404; having the controller return 404 does not prove OpenAPI documents that response.

## 2. Why Use WebTestClient?

WebTestClient is built for Spring WebFlux and provides a fluent API similar to WebClient. It supports:

- Sending GET, POST, PUT, PATCH, DELETE, and other HTTP methods.
- Setting paths, query parameters, headers, cookies, and request bodies.
- Asserting statuses, response headers, and bodies.
- Decoding JSON into DTOs or lists.
- Evaluating JSONPath expressions.
- Consuming reactive responses and testing streams.
- Running against a mock WebHandler or connecting to a running server.

WebTestClient can be configured in several ways:

| Client Creation Method | Test Scope |
|---|---|
| bindToController | One or a few selected controllers |
| bindToRouterFunction | An isolated RouterFunction |
| bindToApplicationContext | Web application context and loaded components |
| bindToServer | A running HTTP server |
| Spring Boot test with RANDOM_PORT | Full Spring Boot application via an embedded server |

If the goal is to verify that springdoc scans controllers, RouterFunctions, customizers, groups, and security configuration, prefer integration tests with a full application context. Slice tests are helpful for individual handlers, but may not load the complete springdoc setup.

## 3. Required Dependencies for Testing

In a Spring Boot project, the test starter typically supplies JUnit Jupiter, AssertJ, Mockito, and Spring Test:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

WebFlux applications require the matching runtime dependencies:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webflux-ui</artifactId>
    <version>YOUR_COMPATIBLE_SPRINGDOC_VERSION</version>
</dependency>
~~~

Use a springdoc version compatible with your Spring Boot version. Do not pick an arbitrary version from an example if your project uses a BOM or dedicated dependency management.

If testing endpoints protected by Spring Security, add security test support:

~~~xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

No separate WebTestClient dependency is needed when Spring Boot WebFlux and the test starter already provide the required components per your project setup.

## 4. Integration Testing with the Full Spring Boot Application

To verify documents generated by springdoc in the real application context, start an embedded server on a random port:

~~~java
@SpringBootTest(
    webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT
)
@AutoConfigureWebTestClient
class OpenApiDocumentIntegrationTest {

    @Autowired
    WebTestClient webTestClient;

    @Autowired
    ObjectMapper objectMapper;

    @Test
    void exposesOpenApiDocument() {
        webTestClient.get()
            .uri("/v3/api-docs")
            .exchange()
            .expectStatus().isOk()
            .expectHeader()
            .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
            .expectBody()
            .jsonPath("$.openapi").exists()
            .jsonPath("$.info.title").exists()
            .jsonPath("$.paths").exists();
    }
}
~~~

RANDOM_PORT lets tests send requests to a real server in the test process. This additionally verifies routing, filter chains, and HTTP serialization compared to merely calling controller methods.

If the application needs a database, message broker, or identity provider, use a test profile, containers, or appropriate mock services. Never let tests depend on production data or flaky external services.

Annotation names and WebTestClient auto-configuration may depend on the Spring Boot version. If the project does not create a WebTestClient bean automatically, inspect your test starter version and WebFlux test configuration.

## 5. Checking Basic OpenAPI JSON Metadata

The default endpoint is usually /v3/api-docs. Tests should assert foundational fields:

~~~java
@Test
void exposesBasicOpenApiMetadata() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBody()
        .jsonPath("$.openapi").exists()
        .jsonPath("$.info.title").isNotEmpty()
        .jsonPath("$.info.version").isNotEmpty()
        .jsonPath("$.paths").exists();
}
~~~

Avoid hardcoding the exact OpenAPI version if the project may upgrade springdoc or vary settings across branches. If your team's contract mandates a specific major OpenAPI version, assert it intentionally.

You can verify title, version, description, and server URLs if those metadata fields are committed contracts. If title/version come from environment config, run tests with deterministic test settings for stable results.

## 6. Checking Paths and HTTP Operations

Suppose a controller has this endpoint:

~~~java
@GetMapping("/api/orders/{id}")
public Mono<OrderResponse> getOrder(@PathVariable String id) {
    return orderService.findById(id);
}
~~~

You can verify the path and method in the document:

~~~java
@Test
void documentsGetOrderOperation() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.paths['/api/orders/{id}'].get").exists()
        .jsonPath("$.paths['/api/orders/{id}'].get.operationId")
            .isNotEmpty()
        .jsonPath("$.paths['/api/orders/{id}'].get.responses['200']")
            .exists();
}
~~~

Use bracket notation for paths containing slashes and curly braces. Use string status codes like '200' when querying JSONPath because response keys in JSON are strings.

If operationId is part of a client-generator contract, assert its exact value and uniqueness. If operationIds are auto-generated, renaming a method or mapping could alter client code; consider declaring stable operationIds with @Operation.

## 7. Checking Schemas of Mono Responses

With Mono<OrderResponse>, the JSON response is normally an OrderResponse object. For instance, the docs should include a 200 response and matching schema.

~~~java
@Test
void documentsSingleOrderResponse() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['200'].content['application/json'].schema"
        ).exists();
}
~~~

If the team enforces stable component names, you can check $ref:

~~~java
.jsonPath(
    "$.paths['/api/orders/{id}'].get.responses['200'].content['application/json'].schema.$ref"
).value("#/components/schemas/OrderResponse")
~~~

$ref assertions are suitable only when the project commits to referencing schemas by those component names. springdoc may inline schemas or generate different component names when using generics, wrappers, or custom converters. In those situations, verify schema structure rather than enforcing unstable names.

Also verify components.schemas.OrderResponse to ensure key fields have the right types and required flags.

## 8. Checking Schemas of Flux JSON Arrays

With Flux<OrderSummary> and media type application/json, the documentation typically describes an array:

~~~java
@Test
void documentsFluxAsJsonArray() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath(
            "$.paths['/api/orders'].get.responses['200'].content['application/json'].schema.type"
        ).isEqualTo("array")
        .jsonPath(
            "$.paths['/api/orders'].get.responses['200'].content['application/json'].schema.items"
        ).exists();
}
~~~

This test verifies the overall response shape. If items uses $ref, you can check that reference and the target component schema as well.

Do not check only that the operation exists. An operation may be generated while its response schema is a single object instead of an array. That bug easily breaks client generators.

## 9. Checking Runtime Status and Body for Mono

Runtime tests must verify actual responses:

~~~java
@Test
void returnsOneOrderAsJson() {
    webTestClient.get()
        .uri("/api/orders/{id}", "ORD-1001")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBody(OrderResponse.class)
        .value(order -> {
            assertThat(order.id()).isEqualTo("ORD-1001");
            assertThat(order.status()).isEqualTo("PAID");
        });
}
~~~

The snippet assumes OrderResponse is a record with id and status. If your DTO uses getters, update assertions accordingly.

Checking Content-Type is critical. A body may contain valid JSON while having the wrong header, causing clients to pick the wrong decoder. If an endpoint supports multiple media types, test each required Accept header branch.

## 10. Checking Runtime Flux JSON Arrays

WebTestClient can decode a JSON array response into a list of DTOs:

~~~java
@Test
void returnsOrderListAsJsonArray() {
    webTestClient.get()
        .uri("/api/orders")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBodyList(OrderSummary.class)
        .hasSize(2)
        .contains(
            new OrderSummary("ORD-1001", "PAID"),
            new OrderSummary("ORD-1002", "PENDING")
        );
}
~~~

This example assumes OrderSummary implements equality properly, such as a record. If your DTO lacks equals/hashCode, use consumeWith or field-by-field assertions.

If a list can be large, you do not need to assert every item in the payload in every test. You can check the count, representative fields, and sort order. Test data should be small and deterministic so tests do not depend on database state.

## 11. Checking Bodyless Responses and Mono<Void>

For a delete endpoint returning 204:

~~~java
@Test
void deleteOrderReturnsNoContent() {
    webTestClient.delete()
        .uri("/api/orders/{id}", "ORD-1001")
        .exchange()
        .expectStatus().isNoContent()
        .expectBody().isEmpty();
}
~~~

This test verifies both the status and the empty body. Do not assert only 204, because a buggy response might still include a body due to misconfiguration or faulty implementation.

In OpenAPI, the matching 204 response should have no content. You can verify the document separately:

~~~java
@Test
void documentsDeleteWithoutResponseBody() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath(
            "$.paths['/api/orders/{id}'].delete.responses['204'].description"
        ).exists()
        .jsonPath(
            "$.paths['/api/orders/{id}'].delete.responses['204'].content"
        ).doesNotExist();
}
~~~

If the endpoint can return 404 or 409, verify those responses in the spec and write runtime tests for each branch.

## 12. Checking Mono.empty() and Error Responses

Mono.empty() does not automatically equal 404. If the controller converts an empty publisher into ResponseEntity.notFound(), assert the status:

~~~java
@Test
void missingOrderReturns404() {
    webTestClient.get()
        .uri("/api/orders/{id}", "missing")
        .exchange()
        .expectStatus().isNotFound();
}
~~~

If the API returns an ApiError body, verify Content-Type and fields:

~~~java
@Test
void missingOrderReturnsDocumentedErrorBody() {
    webTestClient.get()
        .uri("/api/orders/{id}", "missing")
        .exchange()
        .expectStatus().isNotFound()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBody()
        .jsonPath("$.code").isEqualTo("ORDER_NOT_FOUND")
        .jsonPath("$.message").isNotEmpty();
}
~~~

Verify all of the following together:

- Runtime tests confirm the controller/advice actually returns 404.
- OpenAPI tests confirm the operation has a 404 response.
- Schema tests confirm the error body is documented with the exact ApiError schema.
- Contract validators verify references and schema structure.

## 13. Checking SSE with WebTestClient

For finite SSE endpoints in tests, you can verify media type and event content:

~~~java
@Test
void streamsOrderEventsAsSse() {
    webTestClient.get()
        .uri("/api/orders/events")
        .accept(MediaType.TEXT_EVENT_STREAM)
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.TEXT_EVENT_STREAM)
        .expectBody()
        .consumeWith(result -> {
            String body = new String(
                result.getResponseBody(),
                StandardCharsets.UTF_8
            );
            assertThat(body).contains("event: order-update");
            assertThat(body).contains("data:");
            assertThat(body).contains("ORD-1001");
        });
}
~~~

So the test finishes, the mock service should emit a finite number of events and complete. For infinite streams, do not use expectBody to wait for the full response. Retrieve the Flux response, check a few events, and cancel the subscription.

Example retrieving the stream response:

~~~java
FluxExchangeResult<String> result = webTestClient.get()
    .uri("/api/orders/events")
    .accept(MediaType.TEXT_EVENT_STREAM)
    .exchange()
    .expectStatus().isOk()
    .returnResult(String.class);

StepVerifier.create(result.getResponseBody())
    .expectNextCount(2)
    .thenCancel()
    .verify(Duration.ofSeconds(5));
~~~

This example verifies emitted data and cancels the subscription with a timeout. Depending on decoders and chunk boundaries, a single SSE event might be split across multiple String elements; if exact event counting is needed, decode SSE frames or use an event-stream-specific client.

Never let infinite stream tests run forever. Always set timeouts and cancel subscriptions.

## 14. Checking NDJSON or Streaming JSON

For NDJSON, tests must verify media type and how each record is separated. Example endpoint returning Flux<OrderEvent>:

~~~java
@Test
void streamsOrdersAsNdjson() {
    webTestClient.get()
        .uri("/api/orders/stream")
        .accept(MediaType.parseMediaType("application/x-ndjson"))
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(
            MediaType.parseMediaType("application/x-ndjson")
        )
        .expectBody(String.class)
        .value(body -> {
            assertThat(body).contains("\"id\":\"ORD-1001\"");
            assertThat(body).contains("\"id\":\"ORD-1002\"");
        });
}
~~~

This test uses a finite publisher. For infinite streams, consume a bounded count and cancel just like SSE.

If clients expect one JSON record per line, verify newline framing rather than just searching for arbitrary JSON substrings. Split the body by newlines, skip blank lines, and parse each line with ObjectMapper.

## 15. Checking OpenAPI YAML

springdoc typically supports the default YAML endpoint /v3/api-docs.yaml. You can verify it:

~~~java
@Test
void exposesOpenApiYaml() {
    webTestClient.get()
        .uri("/v3/api-docs.yaml")
        .exchange()
        .expectStatus().isOk()
        .expectBody(String.class)
        .value(yaml -> {
            assertThat(yaml).contains("openapi:");
            assertThat(yaml).contains("paths:");
            assertThat(yaml).contains("/api/orders:");
        });
}
~~~

This assertion confirms the endpoint returns YAML with basic structure. For deeper validation, parse the YAML using a parser already in your project or save it as an artifact and run an OpenAPI validator.

Do not rely solely on string checks when verifying nested schemas, $ref pointers, or security. String assertions fit smoke tests; parsers/validators fit contract tests.

## 16. Checking Grouped OpenAPI Documents

If using GroupedOpenApi, each group generates a separate document. Example public and internal groups:

~~~java
@Bean
GroupedOpenApi publicApi() {
    return GroupedOpenApi.builder()
        .group("public")
        .pathsToMatch("/api/public/**")
        .build();
}

@Bean
GroupedOpenApi internalApi() {
    return GroupedOpenApi.builder()
        .group("internal")
        .pathsToMatch("/api/internal/**")
        .build();
}
~~~

Document endpoints typically look like:

~~~text
/v3/api-docs/public
/v3/api-docs/internal
~~~

Test each group:

~~~java
@Test
void exposesPublicGroup() {
    webTestClient.get()
        .uri("/v3/api-docs/public")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.paths['/api/public/catalog'].get").exists()
        .jsonPath("$.paths['/api/internal/reports'].get").doesNotExist();
}

@Test
void exposesInternalGroup() {
    webTestClient.get()
        .uri("/v3/api-docs/internal")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.paths['/api/internal/reports'].get").exists();
}
~~~

Group names and paths must match actual configuration. Each group can have its own customizers, security, or components; testing the default document does not substitute for testing groups.

## 17. Checking the Swagger UI Config Endpoint

Swagger UI usually loads its configuration via /v3/api-docs/swagger-config. This endpoint may include document URLs, group lists, OAuth redirect URLs, and UI options.

Smoke test:

~~~java
@Test
void exposesSwaggerUiConfiguration() {
    webTestClient.get()
        .uri("/v3/api-docs/swagger-config")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBody()
        .jsonPath("$.url").exists();
}
~~~

If the application uses multiple groups, the config may use urls instead of a single url. Check the exact structure produced by your springdoc version.

Do not hardcode the entire JSON config when many fields are auto-generated by springdoc and may change between versions. Assert only the fields the application commits to, such as the spec URL or expected group list.

## 18. Checking Swagger UI Assets and Redirects

Default Swagger UI paths typically include /swagger-ui.html and /swagger-ui/index.html. The first URL may redirect to the UI resource page.

You can check the redirect:

~~~java
@Test
void redirectsSwaggerUiEntryPoint() {
    webTestClient.get()
        .uri("/swagger-ui.html")
        .exchange()
        .expectStatus().is3xxRedirection()
        .expectHeader().exists(HttpHeaders.LOCATION);
}
~~~

And check the UI page:

~~~java
@Test
void servesSwaggerUiIndex() {
    webTestClient.get()
        .uri("/swagger-ui/index.html")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.TEXT_HTML);
}
~~~

Paths, redirects, and Content-Type may change when configuring springdoc.swagger-ui.path, context paths, or reverse proxies. If you only need to verify the OpenAPI contract, testing all JavaScript/CSS is unnecessary; browser smoke tests can live in a separate UI pipeline.

## 19. Checking Functional Routes with RouterFunction

Spring WebFlux supports functional endpoints through RouterFunction and HandlerFunction. springdoc can document routes using @RouterOperation or @RouterOperations.

Example route:

~~~java
@Bean
@RouterOperation(
    path = "/api/health",
    method = RequestMethod.GET,
    beanClass = HealthHandler.class,
    beanMethod = "health",
    operation = @Operation(
        operationId = "getHealth",
        summary = "Check service status"
    )
)
RouterFunction<ServerResponse> healthRoutes(HealthHandler handler) {
    return RouterFunctions.route()
        .GET("/api/health", handler::health)
        .build();
}
~~~

Handler:

~~~java
@Component
class HealthHandler {

    Mono<ServerResponse> health(ServerRequest request) {
        return ServerResponse.ok()
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue(Map.of("status", "UP"));
    }
}
~~~

Runtime test:

~~~java
@Test
void functionalHealthRouteReturnsJson() {
    webTestClient.get()
        .uri("/api/health")
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON)
        .expectBody()
        .jsonPath("$.status").isEqualTo("UP");
}
~~~

Documentation test:

~~~java
@Test
void documentsFunctionalHealthRoute() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.paths['/api/health'].get").exists();
}
~~~

Both tests verify different outcomes. If the runtime route works while OpenAPI lacks the path, inspect @RouterOperation, beanClass, beanMethod, and operation metadata. If the docs contain the path while requests return 404, inspect the actual RouterFunction and path mapping.

## 20. Using WebTestClient bindToRouterFunction for Isolated Tests

When you only want to test a single RouterFunction, you can bind WebTestClient directly:

~~~java
@Test
void testsRouterFunctionWithoutStartingServer() {
    RouterFunction<ServerResponse> routes =
        RouterFunctions.route()
            .GET("/api/health", request ->
                ServerResponse.ok()
                    .contentType(MediaType.APPLICATION_JSON)
                    .bodyValue(Map.of("status", "UP"))
            )
            .build();

    WebTestClient client = WebTestClient
        .bindToRouterFunction(routes)
        .build();

    client.get()
        .uri("/api/health")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.status").isEqualTo("UP");
}
~~~

This approach is fast and helpful for standalone route logic. However, it does not verify springdoc scanning the full application context, does not test the complete SecurityFilterChain, and does not verify OpenAPI docs generated from app-wide configuration.

To test documentation of functional routes, use integration tests with an application context and call /v3/api-docs.

## 21. Distinguishing @WebFluxTest from @SpringBootTest

Both annotations serve different test scopes:

| Annotation | Scope | Best Suited For |
|---|---|---|
| @WebFluxTest | Slice focused on WebFlux controllers and selected web components | Testing controller binding, validation, and responses |
| @SpringBootTest | Loads the application context per app configuration | Testing springdoc, groups, customizers, security, and integration |
| WebTestClient.bindToRouterFunction | One specific RouterFunction | Testing isolated functional routes |
| RANDOM_PORT | Real embedded server on a random port | Testing the HTTP stack closer to runtime |

@WebFluxTest typically does not load all business beans or full OpenAPI configuration. You can add needed config with @Import, yet if the goal is verifying documentation generated across the entire application, @SpringBootTest is usually clearer.

Do not spin up a full context for every tiny test. Pick small scopes for fast logic tests, plus focused integration tests verifying the final docs and configuration.

## 22. Checking Response Headers and Content Negotiation

WebFlux can choose representations based on Accept headers and produces. Tests should verify the exact Content-Type:

~~~java
@Test
void returnsJsonWhenClientAcceptsJson() {
    webTestClient.get()
        .uri("/api/orders")
        .accept(MediaType.APPLICATION_JSON)
        .exchange()
        .expectStatus().isOk()
        .expectHeader()
        .contentTypeCompatibleWith(MediaType.APPLICATION_JSON);
}
~~~

If an endpoint supports multiple media types, test each option:

- application/json.
- text/event-stream.
- application/x-ndjson.
- application/pdf or other media types if supported by the endpoint.

Also assert headers such as Cache-Control, ETag, Location, or Retry-After when part of the contract. In OpenAPI, headers should be documented on the corresponding response; at runtime, tests should verify they are actually present.

Do not test only the body. A valid body with the wrong Content-Type or missing header can still break client processing.

## 23. Testing Security for Documentation and APIs

If the OpenAPI document is protected, tests should verify access rules separately:

~~~java
@Test
void deniesAnonymousOpenApiRequest() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isUnauthorized();
}
~~~

If users with the DOCS_READER role may fetch the spec, test with matching credentials:

~~~java
@Test
void allowsDocsReaderToFetchOpenApi() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .headers(headers -> headers.setBasicAuth(
            "docs-reader",
            "test-password"
        ))
        .exchange()
        .expectStatus().isOk();
}
~~~

Runtime APIs should be tested independently with bearer tokens and scopes. You can use Spring Security Test to mock JWT authentication in tests or run integration tests with tokens issued by a test identity provider.

Do not rely on an assertion for /v3/api-docs to conclude /api/** is protected. Documentation and APIs are separate request scopes.

If tests use the jwt() post-processor, note that the helper creates a mock Authentication; it does not verify real JWT signatures, issuers, or signing keys. Those must be covered by dedicated decoder/resource-server tests.

## 24. Checking Schema and Response References

An OpenAPI document may contain many $ref pointers. Tests should verify that components referenced by operations exist:

~~~java
@Test
void exposesSharedErrorSchema() {
    webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .jsonPath("$.components.schemas.ApiError").exists()
        .jsonPath(
            "$.paths['/api/orders/{id}'].get.responses['404']"
        ).exists();
}
~~~

If the 404 response references ApiError, check the schema ref according to the actual spec structure. Not every schema has to use $ref; inline schemas are valid too.

For shared components, verify:

- The component exists.
- $ref points to the right group and name.
- The response has the right content type.
- The schema contains required fields.
- Enums and formats are accurate.
- No component is overwritten unintentionally.

Use an OpenAPI validator to catch broken references and structural errors. JSONPath tests suit specific business assertions; validators suit whole-document checks.

## 25. Using ObjectMapper for Deeper OpenAPI JSON Inspection

When multiple assertions inspect the same document, you can read the body as a String or JsonNode:

~~~java
@Test
void inspectsOpenApiDocumentAsJsonTree() throws Exception {
    EntityExchangeResult<byte[]> result = webTestClient.get()
        .uri("/v3/api-docs")
        .exchange()
        .expectStatus().isOk()
        .expectBody()
        .returnResult();

    JsonNode document = objectMapper.readTree(result.getResponseBody());

    assertThat(document.path("openapi").asText()).startsWith("3.");
    assertThat(document.path("paths")
        .path("/api/orders")
        .path("get")
        .path("responses")
        .path("200")
        .isMissingNode()).isFalse();
}
~~~

This is helpful when checking many branches or walking all components. Using JsonNode avoids long, repetitive JSONPath expressions.

To validate all $ref entries, you can traverse the JSON tree, collect every `$ref` field, and check each JSON Pointer. A dedicated OpenAPI validator is usually more reliable than writing a custom parser for every reference form.

## 26. Validating OpenAPI with a Validator in CI

Besides application tests, you can export OpenAPI JSON as an artifact and run a validator:

~~~bash
curl -fsS http://localhost:8080/v3/api-docs -o build/openapi.json
openapi-generator-cli validate -i build/openapi.json
~~~

Or use an OpenAPI linting tool standardized by your team. Validators can detect:

- Invalid OpenAPI structure.
- Unresolvable $ref pointers.
- Responses missing descriptions.
- Parameters with invalid locations or schemas.
- Referenced security schemes that are undeclared.
- Malformed schema compositions or media types.

Lint rules can also enforce team conventions such as mandatory operationIds, standard error responses, tag naming, and version policies.

Validators alone cannot prove runtime responses match schemas. You still need WebTestClient tests for critical endpoints and can add contract tests comparing real payloads against schemas.

## 27. Saving Snapshots and Reviewing Document Diffs

For critical APIs, save the generated OpenAPI JSON as a build artifact or snapshot. Whenever controllers, DTOs, annotations, customizers, or security configuration change, regenerate the document and review the diff.

Changes to watch closely:

- Removed paths or HTTP methods.
- Changed operationId.
- Changed request parameters or required flags.
- Removed or altered response statuses.
- Schema fields changing type, format, enum, or nullability.
- Changed security requirements.
- Changed media types.
- Renamed components or changed $ref pointers.

Not every diff is a breaking change, but every change should be reviewed in the context of active clients. You can integrate OpenAPI diff tools to classify breaking changes in CI.

## 28. Avoiding Flaky Tests

Common causes of flaky WebFlux/OpenAPI tests:

- Test data depending on a shared database.
- Flux emitting infinite data while the test waits for completion.
- Timeouts too short for application context startup.
- Tests depending on external identity providers or networks.
- Different groups or bean discovery across profiles.
- Swagger UI config varying by environment.
- Assertions relying on non-guaranteed JSON property ordering.
- Assertions relying on unstable auto-generated component names.

Ways to reduce flakiness:

- Use deterministic, isolated test data.
- Use finite publishers in standard body tests.
- For infinite streams, set timeouts and cancel subscriptions.
- Use a test profile and mock external services.
- Assert only contract fields that must remain stable.
- Use @Schema(name = "...") or explicit config when component names are part of the contract.
- Separate UI smoke tests from schema tests when loading all assets is unnecessary.

## 29. Recommended Testing Workflow for a Reactive API Change

When adding or modifying an endpoint:

1. Write unit/slice tests for the handler or controller.
2. Verify status, body, and Content-Type using WebTestClient.
3. Verify Mono, Flux, empty publishers, or error paths as appropriate.
4. Verify OpenAPI JSON contains the path, operation, and response schemas.
5. If the endpoint is a functional route, verify both the runtime route and @RouterOperation metadata.
6. If SSE/NDJSON is used, verify media types and framing.
7. If using grouped docs, inspect the right group.
8. Run an OpenAPI validator/linter.
9. Review spec diffs if the contract is already published.
10. Store test results and OpenAPI artifacts in CI.

You do not need tests for every theoretical combination. Prioritize business branches meaningful to clients and areas of the contract that changed.

## 30. Checklist for Testing Reactive Documentation

- [ ] WebTestClient is properly configured with the WebFlux test context.
- [ ] Integration test calls /v3/api-docs.
- [ ] OpenAPI metadata and paths are published.
- [ ] operationIds are stable if client generators rely on them.
- [ ] Mono responses are documented with the payload's schema.
- [ ] Flux JSON is documented with an array schema.
- [ ] SSE uses text/event-stream.
- [ ] NDJSON uses the agreed media type and framing.
- [ ] Mono<Void> and 204 responses have no body.
- [ ] Mono.empty() is mapped to a status per business rules.
- [ ] Error responses and error schemas match runtime.
- [ ] Status codes, headers, and Content-Type are tested.
- [ ] YAML endpoint and grouped documents are tested if used.
- [ ] Swagger UI config is tested when UI setup is part of deployment.
- [ ] RouterFunction is tested for both runtime and OpenAPI metadata.
- [ ] Documentation security and API security are tested independently.
- [ ] Stream tests have timeouts and cancellation.
- [ ] OpenAPI validator runs in CI.
- [ ] Spec snapshots/diffs are reviewed on contract changes.
