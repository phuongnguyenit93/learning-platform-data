# Spring Data REST and Repository-Generated Endpoints

## 1. How Does Spring Data REST Generate APIs from Repositories?

Spring Data REST automatically publishes Spring Data repositories as REST resources. Instead of writing a controller for every CRUD operation, the application declares a repository interface; Spring Data REST detects the repository and generates the corresponding HTTP endpoints.

For example, the repository:

~~~java
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

can generate a collection resource to read a list, create a product, access an individual product, update, and delete resources. The exact endpoints depend on the exported repository, base path configuration, repository type, and custom annotations.

Springdoc OpenAPI can document these endpoints alongside endpoints declared via Spring MVC controllers. This is important to note: operations can be generated from Spring Data REST handler mappings even when there is no corresponding controller method in the source code.

To document accurately, it is necessary to understand all three layers:

1. **Repository** defines data access capabilities and query methods.
2. **Spring Data REST** determines the resources, URLs, HTTP methods, HAL representation, and export rules.
3. **Springdoc OpenAPI** describes the operations exposed by the application as an OpenAPI document.

This lesson focuses on describing endpoints generated from repositories, customizing resources, and verifying the documentation generated by Springdoc.

## 2. Adding Dependencies and Enabling Spring Data REST

For a Spring Boot application using Spring MVC and Spring Data JPA, dependencies typically look like:

~~~gradle
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    implementation("org.springframework.boot:spring-boot-starter-data-rest")
    implementation("org.springdoc:springdoc-openapi-starter-webmvc-ui:<compatible-version>")

    runtimeOnly("com.mysql:mysql-connector-j")
}
~~~

Spring Data REST provides the repository exporter; the Springdoc starter provides the OpenAPI endpoint and Swagger UI. Choose a Springdoc version compatible with the Spring Boot and Spring Framework line in use. For Spring Boot 3, use the Springdoc 2.x line; Spring Boot 2 projects need to choose the corresponding compatible Springdoc line.

If the application only needs OpenAPI JSON/YAML without Swagger UI, you can choose the API starter instead of the UI starter that matches the web stack.

In Springdoc versions that support the property to enable/disable Spring Data REST, you can declare:

~~~yaml
springdoc:
  enable-data-rest: true
~~~

Check the property and default value for the exact Springdoc version used by the project. If repository endpoints do not appear in the documentation, verify the dependencies, web stack, scan configuration, and integration support of the current version.

## 3. Repositories Exported as Resources

Example domain and repository:

~~~java
@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal price;

    // getters and setters
}
~~~

~~~java
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

If the repository is exported by Spring Data REST, the application can expose a collection resource under a default name derived from the domain type. To control the URL and relation names, use `@RepositoryRestResource`:

~~~java
@RepositoryRestResource(
    path = "products",
    collectionResourceRel = "products",
    itemResourceRel = "product"
)
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

With this configuration, the collection resource has the path `/products`. The item resource is accessed as `/products/{id}`. The collection and item relation names are used in HAL links and embedded representations.

If the application configures a base path:

~~~yaml
spring:
  data:
    rest:
      base-path: /api
~~~

the resources will be located under `/api`, for example `/api/products`. Ensure Springdoc documents the correct base path and clients use the correct URLs.

Do not rely on domain name pluralization rules when writing clients or security rules. If a URL is part of a public contract, set the path explicitly with `@RepositoryRestResource` and verify the runtime path.

## 4. Commonly Generated CRUD Endpoints

For a standard exported repository, Spring Data REST can provide common operations:

| Resource | HTTP method | Purpose |
|---|---|---|
| /api/products | GET | Read collection |
| /api/products | POST | Create a new item |
| /api/products/{id} | GET | Read a single item |
| /api/products/{id} | PUT | Replace an item |
| /api/products/{id} | PATCH | Partially update an item |
| /api/products/{id} | DELETE | Delete an item |

The table above describes common operations; actual endpoints also depend on exported repository methods, exposure configuration, ID type, validation, event handlers, and custom repository behavior.

Spring Data REST may return different statuses and headers depending on the operation, such as `Location` when creating a resource. OpenAPI should reflect the actual responses of the application, including status codes, media types, headers, and bodies.

Springdoc can detect operations from Spring Data REST handler mappings. After starting the application, fetch `/v3/api-docs` to inspect the generated paths and methods. Do not conclude that all HTTP methods in the table are present just because the repository extends `JpaRepository`.

## 5. Limiting Export with @RepositoryRestResource

You can hide an entire repository from the REST API:

~~~java
@RepositoryRestResource(exported = false)
public interface InternalAuditRepository
        extends JpaRepository<AuditRecord, Long> {
}
~~~

When `exported=false`, Spring Data REST does not publish this repository as a REST resource. This is a way to limit the automatically generated HTTP surface.

You can rename the resource using `path` and relations:

~~~java
@RepositoryRestResource(
    path = "catalog-items",
    collectionResourceRel = "catalogItems",
    itemResourceRel = "catalogItem"
)
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

If the resource is already used by clients, changing `path` or relation names can affect the API contract. Treat this as an API change requiring versioning and migration management.

Hiding a repository from Spring Data REST does not mean the data is protected everywhere. The repository can still be used by other services or controllers. Authorization still needs to be enforced in the backend.

## 6. Describing Repositories and Resources with @Description

Spring Data REST provides the `@Description` annotation to describe collection and item resources:

~~~java
@RepositoryRestResource(
    path = "products",
    collectionResourceDescription =
        @Description("List of products in the store"),
    itemResourceDescription =
        @Description("Detailed information of a product")
)
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

These descriptions add metadata for Spring Data REST, especially in hypermedia/profile mechanisms supported by the framework.

Do not assume that every `@Description` automatically becomes the `summary` or `description` of an OpenAPI operation in every Springdoc version. Inspect the generated JSON. If OpenAPI needs more specific content, you can supplement it using `OpenApiCustomizer` or annotation mechanisms supported by your Springdoc version for the corresponding handler.

The goal is to keep resource, operation, and response descriptions consistent. If a collection resource has a business description, the OpenAPI documentation should also explain in what scenarios clients use that resource.

## 7. Exposing Query Methods as Search Endpoints

Spring Data REST can publish repository query methods under the `search` resource. For example:

~~~java
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    List<Product> findByNameContainingIgnoreCase(
        @Param("name") String name
    );
}
~~~

The search endpoint typically has the form:

~~~http
GET /api/products/search/findByNameContainingIgnoreCase?name=keyboard
~~~

Spring Data REST creates a search resource for exported query methods. The method name is usually used as the default path; `@RestResource` allows changing the path and relation:

~~~java
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @RestResource(
        path = "by-name",
        rel = "byName",
        description = @Description("Find products by partial name")
    )
    List<Product> findByNameContainingIgnoreCase(
        @Param("name") String name
    );
}
~~~

The endpoint now has the form:

~~~http
GET /api/products/search/by-name?name=keyboard
~~~

Here the search method path is `by-name` and the query parameter is `name`. `@Param` sets an explicit public parameter name, avoiding reliance on Java parameter names or compiler metadata.

Springdoc needs to describe the path, query parameter, response type, and status of the search operation. After generating the documentation, verify that the parameter name matches `name` and the operation is located under `/search`.

## 8. Hiding Query Methods with @RestResource

A query method may not be allowed to be called directly over REST:

~~~java
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @RestResource(exported = false)
    List<Product> findByInternalStatus(String status);
}
~~~

`exported=false` prevents Spring Data REST from publishing this query method as a search endpoint.

You can change the path or relation of a query method with `@RestResource`:

~~~java
@RestResource(path = "active", rel = "activeProducts")
List<Product> findByActiveTrue();
~~~

When changing exports, inspect both the repository search resource and the OpenAPI document. Operations that are no longer exported should not continue to appear in the documentation. Conversely, an operation appearing in the documentation while returning 404 at runtime indicates that the documentation and handler mapping are out of sync.

Do not use hiding a query method as an authorization mechanism. If a query can still be invoked from another service or endpoint, data access permissions still need to be controlled at the security and business layers.

## 9. Pagination and Sorting of Collection Resources

Spring Data REST supports pagination and sorting for collection resources. Common query parameters:

| Parameter | Meaning | Example |
|---|---|---|
| page | Page index, usually 0-based | page=0 |
| size | Maximum number of items per page | size=20 |
| sort | Property and sort direction | sort=name,asc |

Example:

~~~http
GET /api/products?page=0&size=20&sort=name,asc
~~~

Multiple sort criteria can be passed if the API supports them:

~~~http
GET /api/products?page=0&size=20&sort=category,asc&sort=price,desc
~~~

Collection responses typically include `page` metadata such as `size`, `number`, `totalElements`, and `totalPages`. Clients use this metadata to build page navigation.

Springdoc can describe query parameters and response schemas generated from Spring Data REST. However, you must verify the exact parameter names, default values, size limits, and response types in the OpenAPI JSON. Do not assume all Spring MVC `Pageable` configurations apply identically to Spring Data REST.

If the system enforces a maximum page size, the documentation should clearly state the limit so clients do not send an oversized `size`. The backend must enforce that limit, even if the OpenAPI schema specifies `maximum`.

## 10. HAL Representation and Hypermedia Links

Spring Data REST typically uses HAL (Hypertext Application Language) to represent resources. A collection response may look like:

~~~json
{
  "_embedded": {
    "products": [
      {
        "name": "Mechanical Keyboard",
        "price": 120.00,
        "_links": {
          "self": {
            "href": "https://api.example.com/api/products/42"
          }
        }
      }
    ]
  },
  "_links": {
    "self": {
      "href": "https://api.example.com/api/products?page=0&size=20"
    },
    "search": {
      "href": "https://api.example.com/api/products/search"
    }
  },
  "page": {
    "size": 20,
    "totalElements": 85,
    "totalPages": 5,
    "number": 0
  }
}
~~~

Important parts:

- `_embedded` contains the resources embedded in the collection.
- `_links` contains hypermedia links for clients to discover next actions.
- `page` contains pagination metadata.
- Each item can have its own links such as `self` and links to associations.

HAL helps clients discover the API through link relations instead of hard-coding every URL. When writing documentation, explain the important relations and the media type returned by the endpoint, usually `application/hal+json`.

Do not confuse HAL links with the OpenAPI Link Object. A HAL link is hypermedia data in the response; an OpenAPI Link Object describes relationships between operations in the documentation contract. The two concepts have different purposes and structures.

## 11. HAL Schemas in OpenAPI

A HAL response is not a plain flat DTO. A collection can contain `_embedded`, `_links`, and `page`; an item can contain relation links and business properties.

Springdoc can use Spring HATEOAS support to handle some hypermedia models. In versions that have the corresponding properties, configuration can include:

~~~yaml
springdoc:
  enable-hateoas: true
  enable-data-rest: true
~~~

Verify the properties according to your Springdoc version. If the documentation generates a schema that is too generic, misses `_embedded` contents, or does not represent the item type properly, inspect the OpenAPI JSON and add an appropriate schema/customizer.

A collection schema may need to represent:

- `_embedded` containing the list of resources.
- `_links` containing relations and `href`.
- `page` containing `size`, `number`, `totalElements`, and `totalPages`.
- Item schema describing business fields.
- Media type `application/hal+json`.

Do not force a HAL response to `application/json` if runtime actually returns `application/hal+json`. The media type is part of the contract and affects how clients decode responses.

## 12. Projections and Excerpt Projections

Projections allow Spring Data REST to publish a specific view of an entity. For example:

~~~java
@Projection(
    name = "productSummary",
    types = Product.class
)
public interface ProductSummary {

    Long getId();

    String getName();

    BigDecimal getPrice();
}
~~~

A projection can be used when clients need a compact representation. A repository can declare a default excerpt projection:

~~~java
@RepositoryRestResource(
    path = "products",
    excerptProjection = ProductSummary.class
)
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

Clients can also request a projection via a query parameter if the projection is exported and supported by the endpoint:

~~~http
GET /api/products/42?projection=productSummary
~~~

OpenAPI documentation needs to clarify which representation is returned by default and which projections can be selected. If multiple projections produce different response schemas, check whether Springdoc fully describes each variant.

Do not treat projections as authorization. Hiding a field from a projection does not replace backend permission checks on fields or sensitive data.

## 13. Association Resources and Entity Relationships

Spring Data REST can export associations between entities as resource links. For example, `Product` references `Category`. A product resource can include a relation to `category` in `_links`.

Association operations can be exposed under paths attached to the item, depending on the association type and repository configuration. Clients can follow links to discover related resources instead of constructing URLs manually.

When describing associations:

- State the relation name and business meaning.
- Explain the target URL and media type.
- Describe the request body or URI representation if an operation that updates the association requires it.
- Clearly document required authorization.
- Verify the actual HAL response and OpenAPI schema.

Do not assume every association has the same HTTP method or request body. How relationships are updated also depends on the association type, repository exposure, and Spring Data REST configuration.

## 14. Customizing Resource Names and Base Path

There are two common levels of URL configuration:

**Global Spring Data REST base path:**

~~~yaml
spring:
  data:
    rest:
      base-path: /api
~~~

**Repository-specific path:**

~~~java
@RepositoryRestResource(
    path = "products",
    collectionResourceRel = "products"
)
public interface ProductRepository
        extends JpaRepository<Product, Long> {
}
~~~

Combining both configurations, the collection resource can be accessed at `/api/products`.

If you change the base path or repository path after clients have integrated, this is a contract change. You must update the OpenAPI document, gateway routes, security matchers, CORS policies, and client configurations simultaneously.

You should inspect the root resource after startup. Spring Data REST typically provides discovery links; relations in the root help clients know which collection resources are being exported.

## 15. Customizing OpenAPI for Repository Resources

Springdoc can generate operations from repository handler mappings. If you need to standardize tags or metadata for a path region, you can use `OpenApiCustomizer`.

Example assigning the `Products` tag to operations under `/api/products`:

~~~java
@Bean
OpenApiCustomizer productRepositoryTagCustomizer() {
    return openApi -> {
        openApi.addTagsItem(
            new Tag()
                .name("Products")
                .description("Product resources generated from ProductRepository")
        );

        if (openApi.getPaths() == null) {
            return;
        }

        openApi.getPaths().forEach((path, pathItem) -> {
            if (path.startsWith("/api/products")) {
                pathItem.readOperations()
                    .forEach(operation -> operation.addTagsItem("Products"));
            }
        });
    };
}
~~~

This customizer only modifies the OpenAPI documentation. It does not change URLs, access permissions, or repository behavior.

If the base path or repository path changes, the `startsWith` condition must be updated. With multiple repositories, you can build a mapping between path prefixes and tags to avoid tagging operations incorrectly.

Avoid recreating the entire `Paths` object in a customizer because Springdoc has already generated operations from handler mappings. Only add or adjust the necessary fields to preserve the discovered operations and schemas.

## 16. When Repository Endpoints Do Not Appear in OpenAPI

If Spring Data REST endpoints work at runtime but are missing from `/v3/api-docs`, check in order:

1. The Spring Data REST dependency is on the runtime classpath.
2. The Springdoc starter is compatible with Spring Boot and the web stack.
3. Data REST/HATEOAS integration is enabled according to your version's configuration.
4. The repository is actually exported and does not have `exported=false`.
5. The repository is inside the Spring-managed application context.
6. The base path and repository path match the runtime URL.
7. Query methods are not marked with `@RestResource(exported=false)`.
8. Springdoc path/package filters are not excluding the operations.
9. The OpenAPI document is generated after Spring Data REST handler mappings have been registered.
10. No customizer is removing paths or overwriting the document.

If an operation appears but lacks a schema or description, check media types, HAL models, projections, and generic types. Metadata can be added with `OpenApiCustomizer` after confirming the runtime structure.

Do not create dummy controllers just to make Swagger UI display an operation if the real endpoint is already managed by Spring Data REST. Doing so can create duplicate documentation or cause OpenAPI to describe a non-existent endpoint.

## 17. Securing Repository Endpoints and Documentation

Automatically generated repository endpoints are still real HTTP APIs. Authentication and authorization must be applied according to application policy:

- Limit which repositories or methods are exported.
- Use Spring Security to protect collection and item resources.
- Check object-level permissions when reading, modifying, or deleting.
- Protect query methods that could expose sensitive data.
- Control association endpoints.
- Do not treat hiding an operation from OpenAPI as a security measure.

OpenAPI documentation also needs its own access policy. Users allowed to view Swagger UI do not necessarily have permission to call POST or DELETE. Conversely, repository endpoints can be protected even when the documentation remains public.

Spring Data REST can use the application's security configuration and corresponding authorization mechanisms. Test runtime requests with unauthenticated/unauthorized users, read-only users, and write-privileged users.

## 18. Testing OpenAPI and HAL Responses

After starting the application, test the endpoints:

~~~http
GET /api
GET /api/products
GET /api/products/search
GET /v3/api-docs
~~~

If a different base path is configured, replace the URLs according to the actual configuration.

You can use `MockMvc` to test the collection response:

~~~java
mockMvc.perform(get("/api/products")
        .accept("application/hal+json")
        .param("page", "0")
        .param("size", "20"))
    .andExpect(status().isOk())
    .andExpect(content().contentTypeCompatibleWith("application/hal+json"))
    .andExpect(jsonPath("$._embedded.products").isArray())
    .andExpect(jsonPath("$.page.number").value(0));
~~~

The test above verifies the HAL representation and page metadata. The relation name `products` must match the actual `collectionResourceRel`.

You can test the OpenAPI document:

~~~java
mockMvc.perform(get("/v3/api-docs"))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.paths['/api/products']").exists())
    .andExpect(jsonPath("$.paths['/api/products/search/by-name']").exists());
~~~

The search path must be replaced with the path configured in the repository. In addition to checking path existence, verify HTTP methods, query parameters, response media types, schemas, and security requirements.

## 19. Changes That Can Break Clients

Spring Data REST auto-generates endpoints, but changing repository configuration can still break clients:

| Change | Possible impact |
|---|---|
| Changing @RepositoryRestResource(path) | Collection/item URLs change |
| Changing collectionResourceRel | Relation name in _embedded changes |
| Changing itemResourceRel | Item relation changes |
| Changing @RestResource(path) | Search endpoint changes |
| exported=false | Resource or operation disappears |
| Changing projection/excerptProjection | JSON response changes |
| Changing entity fields or serialization | Schema and payload change |
| Changing base-path | All repository URLs change |
| Changing page size or sort behavior | Results and page navigation change |

Before making changes, save the current OpenAPI document and sample HAL responses. Compare the new document against the old one, identify affected clients, and plan versioning/migration if needed.

Do not rely on repository method names as a stable contract. Public paths should be explicitly declared with annotations and verified with contract tests.

## 20. Principles for Integrating Spring Data REST with Springdoc

When using repository-generated endpoints, apply these principles:

1. Identify which repositories are exported and set explicit paths for public resources.
2. Use `@RepositoryRestResource` to manage collection paths and relation names.
3. Use `@RestResource` to name or hide query methods.
4. Use `@Param` to fix query parameter names.
5. Document pagination, sorting, and search according to runtime URLs.
6. Understand HAL `_embedded`, `_links`, and `page` metadata.
7. Distinguish HAL links from OpenAPI Link Objects.
8. Use projections intentionally and inspect response schemas.
9. Use `OpenApiCustomizer` to add tags/metadata without overwriting the entire `Paths`.
10. Protect repository endpoints with backend authorization.
11. Verify `/v3/api-docs` alongside actual HAL responses.
12. Manage changes to paths, relations, projections, and base paths as API contract changes.

Spring Data REST helps generate REST resources directly from repositories, while Springdoc helps publish the OpenAPI contract for those endpoints. When URLs, relations, HAL representations, and pagination metadata are verified alongside the generated documentation, clients can integrate with the repository API without guessing structures or depending on internal implementation details.
