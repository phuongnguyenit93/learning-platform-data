# Authentication, Authorization, and Live API Call Behavior via MCP

When an MCP client invokes a tool generated by Springdoc from OpenAPI, the application executes a call to the corresponding REST operation. This is an HTTP request with a target, method, path, parameters, headers, and body; the request passes through the web stack and the target API's protection layers. Consequently, MCP security must control both incoming requests to the MCP server and outbound requests generated when a tool runs.

Three separate questions must be answered:

1. Who is allowed to connect to the MCP endpoint and discover tools?
2. Who is allowed to invoke a specific tool and execute the underlying business logic?
3. When a tool calls the REST API over HTTP, which identity and credentials does the target API receive?

A valid Bearer token on the MCP request does not automatically prove that the subsequent REST request carries that token. Similarly, requiring user confirmation for write actions does not replace authentication or authorization. This article traces the live request flow through Spring Security configuration, choosing credential models, per-resource authorization, and verifying side effects in integration tests.

## 1. Three Security Layers in a Single Tool Invocation

A tool invocation through Springdoc can pass through three layers:

~~~text
MCP Client / AI Agent
        |
        | 1. MCP request + MCP client credentials
        v
Spring Security: protects MCP endpoint
        |
        v
Springdoc MCP ToolCallback
        |
        | 2. HTTP request to base-url
        v
Spring Security: protects target REST API
        |
        v
Controller -> Service -> Repository / Database
        |
        v
HTTP response -> Tool result -> MCP Client
~~~

The first layer authenticates and authorizes the client against the MCP server. The second layer authenticates and authorizes the REST request created during tool execution. The third layer checks business permissions on the specific object, such as ensuring a user can only view orders belonging to their tenant or account.

Do not collapse all three layers into a single check. A client authorized to call the MCP server may still lack permission to read a specific order. A tool appearing in the catalog does not imply the caller is allowed to execute it.

## 2. Springdoc MCP Performs Real HTTP Calls

Springdoc scans operations described in OpenAPI and builds `ToolCallback` instances. When an MCP client calls a tool, the callback converts the input into a request for the corresponding operation:

- `operationId` determines the tool name.
- Path parameters are substituted into the URL.
- Query parameters are encoded into the query string.
- Header parameters are placed into HTTP headers per operation metadata.
- The request body becomes the HTTP request body.
- Method and path are taken from the OpenAPI operation.
- The response from the target API is converted into the tool result.

API example:

~~~java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @GetMapping("/{id}")
    @Operation(operationId = "getOrderById")
    public OrderResponse getOrder(@PathVariable UUID id) {
        return orderService.getOrder(id);
    }
}
~~~

The tool may be exposed as `get_order_by_id`. When the agent invokes the tool with `id`, Springdoc issues an HTTP `GET` to the matching path on the configured base URL.

That request traverses HTTP routing, servlet filters or `WebFilter`, Spring Security, controller advice, validation, and related application components. It can produce logs, metrics, traces, database queries, or side effects just like a REST request sent from any other client.

Therefore, do not view a tool callback as a direct Java method call to the controller. In particular, never assume the `SecurityContext` of the MCP request is automatically carried into a new HTTP request to the REST endpoint.

## 3. Distinguishing MCP Endpoints and REST Endpoints

Springdoc's default MCP endpoints include:

| Endpoint | Function |
|---|---|
| `/mcp` | MCP communication over HTTP |
| `/mcp-ui` | MCP Developer Dashboard if enabled |
| `/api/mcp-admin/**` | Dashboard admin API, including listing and executing tools |

Underlying REST endpoints might be `/api/orders/**`, `/api/customers/**`, or other business paths. They are a separate HTTP surface and must have their own protection policy.

Springdoc does not enforce authentication or authorization on MCP endpoints automatically. Without a security layer, clients can access endpoints based on network reachability and current web configuration. Spring AI also describes HTTP MCP transports as authentication-agnostic: the transport defines the protocol, while protecting the endpoints belongs to the application.

Do not protect only `/mcp` while leaving the target API wide open. Conversely, protecting only the REST API while leaving `/mcp` public can leak the capability catalog, dashboard, or other tools lacking complete permission checks.

## 4. OpenAPI Security Metadata Does Not Enforce Security

OpenAPI can describe Bearer authentication so Swagger UI, code generators, and clients know how to call the API:

~~~java
@Configuration
@SecurityScheme(
    name = "bearerAuth",
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT"
)
public class OpenApiSecurityConfiguration {
}
~~~

Apply the scheme to an operation:

~~~java
@GetMapping("/{id}")
@Operation(
    operationId = "getOrderById",
    security = @SecurityRequirement(name = "bearerAuth")
)
public OrderResponse getOrder(@PathVariable UUID id) {
    return orderService.getOrder(id);
}
~~~

The security scheme states that the API requires a Bearer token. It does not issue tokens, verify JWT signatures, or block unauthorized requests. Enforcement must be handled by Spring Security or another security layer.

Do not declare `Authorization` as an ordinary header parameter in OpenAPI. OpenAPI has dedicated Security Schemes for HTTP authentication; use `@SecurityScheme` and `@SecurityRequirement` to describe them.

## 5. Authenticating Incoming Requests to the MCP Server

With HTTP transport, the MCP server is a web endpoint. You can protect it with Spring Security just like other endpoints.

Example application using OAuth2 Resource Server with JWT:

~~~yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://identity.example.com/issuer
~~~

Example `SecurityFilterChain`:

~~~java
@Configuration
@EnableWebSecurity
public class SecurityConfiguration {

    @Bean
    SecurityFilterChain applicationSecurity(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/mcp", "/mcp/**")
                    .hasAuthority("SCOPE_mcp.invoke")
                .requestMatchers("/mcp-ui/**", "/api/mcp-admin/**")
                    .hasRole("MCP_ADMIN")
                .requestMatchers("/api/**")
                    .authenticated()
                .anyRequest()
                    .denyAll()
            )
            .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
            .build();
    }
}
~~~

This is an illustrative authorization setup. Scopes, roles, URLs, and matcher order must align with your identity provider and application structure. If the application defines multiple `SecurityFilterChain` beans, verify `@Order` and `securityMatcher` so MCP requests enter the intended chain.

CSRF note: HTTP MCP uses `POST` requests. If `/mcp` accepts only Bearer tokens in the `Authorization` header and does not authenticate via browser cookies, you can exclude that endpoint specifically from CSRF:

~~~java
.csrf(csrf -> csrf.ignoringRequestMatchers("/mcp", "/mcp/**"))
~~~

Place this configuration in the same `SecurityFilterChain` before `build()`. Do not disable CSRF across the entire application as in simplified snippets. If the dashboard or admin API uses session cookies, keep CSRF active for those browser requests and supply CSRF tokens per Spring Security configuration.

For JWTs, verify issuer, signature, expiration, audience, and scopes suited to the MCP resource. A validly signed token alone does not prove it was issued for the right API.

## 6. Distinguishing 401 and 403

Two common statuses:

| Status | Meaning | Example |
|---|---|---|
| `401 Unauthorized` | Request lacks valid credentials | Missing Bearer token, expired token, or invalid signature |
| `403 Forbidden` | Identity is authenticated but lacks permission | Token lacks `mcp.invoke` or `orders.read` scope |

If an MCP client receives `401` at `/mcp`, check how the client sends credentials to the MCP server. If the MCP request succeeds yet the tool's REST API call receives `401`, check credentials on the downstream request. If the target API returns `403`, check scopes, roles, tenant, and object-level permissions.

Do not turn errors into empty success messages. Tool results must retain enough information for the client to know the call failed, without exposing stack traces, secrets, or internal details.

## 7. MCP Client Credentials and REST API Credentials Are Separate Concerns

Suppose an agent sends:

~~~http
POST /mcp
Authorization: Bearer <mcp-access-token>
Content-Type: application/json
~~~

Spring Security validates the token on this request. Next, Springdoc creates another HTTP request to the target API using `springdoc.ai.mcp.base-url`.

Do not assume the `Authorization` header from the MCP request automatically becomes the `Authorization` header on the new REST request. Springdoc documentation explicitly describes forwarding auth headers from the MCP Developer Dashboard to the underlying API during dashboard execution. That description applies to the dashboard; do not extrapolate it into a guarantee that every MCP client or transport automatically forwards caller credentials to the REST backend.

Test the actual flow in the version you run. If the target API requires a token and the callback sends no credentials, the REST request will be rejected even though the initial MCP request was authenticated.

## 8. Checking base-url and the Downstream Request Path

The `springdoc.ai.mcp.base-url` property defines the base URL used when a tool callback executes an HTTP call. The default is `http://localhost:8080`; if unset, Springdoc infers it from `server.port`.

Example:

~~~yaml
server:
  port: 8080

springdoc:
  ai:
    mcp:
      enabled: true
      base-url: http://localhost:8080
~~~

If the application runs under a `/store` context path, the actual URL may need to be:

~~~yaml
springdoc:
  ai:
    mcp:
      base-url: http://localhost:8080/store
~~~

If the target API lives in another service, `base-url` must point to that service's host and context path. Inside containers, `localhost` refers to the current container itself; if the MCP server and backend API run in separate containers, use the service hostname on the runtime network.

Base URL is the request destination. It does not configure an OAuth client, issue tokens, or replace backend authorization policies.

## 9. Three Downstream Credential Models

When a tool callback must call a protected API, choose an explicit identity model:

| Model | Who Does the Target API See? | Suitable When |
|---|---|---|
| Service identity | The MCP application or a service account | Machine-to-machine tasks with fixed permissions |
| User delegation | The end user interacting with the agent | API permissions must be evaluated per user |
| Native tool/service call | Current principal in the app flow, if security context is properly preserved | Calling the service layer directly instead of HTTP loopback |

Do not pick service identity just to make `401` errors disappear if the business logic requires per-user permissions. Likewise, never forward a user token blindly to another backend with a different audience or scope set.

## 10. Service Identity with Client Credentials

For machine-to-machine tasks, you can issue a dedicated service account for the MCP integration. Tokens are fetched from the authorization server via client credentials and contain only minimal scopes, such as `orders.read` or `orders.create`.

Flow:

~~~text
MCP client
   |
   | token for MCP server
   v
MCP server authenticates caller
   |
   | tool callback needs to call backend
   v
OAuth client obtains service token
   |
   | Service account Bearer token
   v
REST API checks scope and service permissions
~~~

Service identity fits when the target API only needs to know which system is calling. It does not preserve the end user's identity on its own. If the service account has permission to read all orders, restricting `/mcp` to a regular user is not enough to ensure that user can only read their own orders.

Springdoc MCP properties expose `base-url`, endpoints, timeouts, filters, guardrails, and auditing; there is no built-in general property for declaring a client secret or downstream bearer token. Obtaining and attaching service tokens must be handled by a security integration, gateway, or controlled custom execution layer. Do not invent unsupported properties in `application.yml` assuming Springdoc will use them.

## 11. User Delegation and Token Exchange

If the backend must evaluate permissions per end user, propagate user context to the target API through a well-designed mechanism:

- The authorization server supports token exchange or an on-behalf-of flow.
- Downstream tokens are issued for the exact audience of the target API.
- Scopes cover only actions the user is allowed to perform.
- The target API checks tenant, owner, and object permissions just like any other request.

Never send a token intended for the MCP resource to another API if audiences do not match. Never forward session cookies or arbitrary headers to hosts outside the trust boundary.

If your version or execution adapter provides no mechanism to forward identity per request, consider writing a native MCP tool with Spring AI calling the service layer under a controlled security context, or building a custom adapter capable of token exchange. Verify how security context propagates across thread/reactive boundaries before relying on the current principal.

## 12. Never Trust Tool Parameters as an Identity Source

Do not design tools like this:

~~~json
{
  "userId": "user-100",
  "tenantId": "tenant-a",
  "orderId": "order-900"
}
~~~

and then trust `userId` or `tenantId` sent by the agent as the caller's real identity. Tool arguments are client-supplied inputs; they do not prove the caller is authorized to act on behalf of that user or tenant.

Identity should come from an authenticated `Authentication`, validated claims, or context established by a trusted backend. If an API requires a tenant ID, verify that the tenant belongs to the calling identity or service principal.

Agent-provided values such as `customerId`, `accountId`, or `orderId` still require ownership checks. Never use the fact that a tool schema describes a valid ID as a substitute for authorization.

## 13. Request-Level and Method-Level Authorization

Request-level authorization is suited to restricting the endpoint surface:

- Only MCP clients with scope `mcp.invoke` may reach `/mcp`.
- Only MCP administrators may reach the dashboard and admin API.
- Only authenticated callers may reach REST API groups.

Method-level authorization is suited to business permissions:

- Scope `orders.read` is required to read orders.
- Only the owner or staff with the right role may view details.
- Only callers with `orders.cancel` permission may cancel an order.

Spring Security requires enabling method security explicitly:

~~~java
@Configuration
@EnableMethodSecurity
public class MethodSecurityConfiguration {
}
~~~

Example in a service:

~~~java
@Service
public class OrderQueryService {

    @PreAuthorize("hasAuthority('SCOPE_orders.read')")
    public OrderResponse findById(UUID orderId) {
        return orderRepository.findResponseById(orderId);
    }
}
~~~

The Spring Boot Security starter does not enable method-level authorization automatically. When using `@PreAuthorize`, confirm `@EnableMethodSecurity` is present and the method is invoked through a Spring-managed proxy.

## 14. Per-Resource Permission Checks

The `orders.read` scope only answers whether the caller can read order resources in general. It does not answer which specific orders the caller may read.

You can use an authorization bean:

~~~java
@Service
public class OrderService {

    @PreAuthorize("@orderAuthorization.canRead(#orderId, authentication)")
    public OrderResponse getOrder(UUID orderId) {
        return repository.findResponseById(orderId)
            .orElseThrow(OrderNotFoundException::new);
    }
}
~~~

The `orderAuthorization` bean must verify the relationship between the principal and the order: owner, tenant, support role, or sharing policy. The exact same check must apply to direct REST requests and requests originating from MCP tools.

Do not enforce permissions only on controllers while leaving services unprotected. The service layer is the right place to guard business logic invoked from multiple entry points such as REST, native MCP tools, message consumers, or scheduled jobs.

## 15. Never Expose Principal as an Input Parameter

Parameters such as `Principal`, `Authentication`, `HttpServletRequest`, and `@AuthenticationPrincipal` are framework-injected context. They should never become properties filled in by an agent in tool inputs.

Springdoc typically ignores these injectable parameters when generating documentation. If a security parameter appears in OpenAPI, re-check the controller signature and annotations.

Never add a `userId` parameter just to replace `@AuthenticationPrincipal`. When business logic needs the current user, read it from the authenticated security context or pass a trusted context to the service layer.

## 16. Protecting the Dashboard and Admin API Separately

The MCP Developer Dashboard can browse tools, inspect schemas, and execute tools with JSON inputs. The Dashboard REST API typically exposes:

| Method | Endpoint | Function |
|---|---|---|
| `GET` | `/api/mcp-admin/tools` | Lists tools |
| `POST` | `/api/mcp-admin/tools/execute` | Executes a tool by name and arguments |

The dashboard is an administrative surface because users can invoke live APIs. Restrict it to a dedicated role, enable it only when needed, and consider disabling it in production unless operationally required.

Springdoc notes that the dashboard can forward auth headers such as `Authorization` or API keys from the dashboard to the target API call. Use least-privilege test credentials and avoid keeping tokens in browser storage longer than necessary.

Never protect the dashboard merely by hiding links on a page. Enforce server-side authorization for both `/mcp-ui/**` and `/api/mcp-admin/**`.

## 17. Human-in-the-Loop Is Not Authorization

Springdoc classifies tools by HTTP method:

| Default Classification | Methods |
|---|---|
| Safe/read-only | `GET`, `HEAD`, `OPTIONS` |
| Mutating | `POST`, `PUT`, `PATCH`, `DELETE`, and other methods |

When `require-approval-for-mutating-tools` is enabled, a mutating tool returns an approval-required result instead of immediately executing the HTTP request.

Example:

~~~json
{
  "requires_human_approval": true,
  "tool_name": "cancel_order",
  "http_method": "POST",
  "path": "/api/orders/ORD-1001/cancel",
  "arguments": {
    "reason": "Customer request"
  },
  "message": "This mutating operation requires human approval before execution."
}
~~~

The agent should present the request for user review. However, HITL neither authenticates callers nor authorizes actions. Springdoc documentation warns that anyone able to access the MCP endpoint can also complete the approval flow, including via the admin API by sending `approved=true`.

Thus, approval is strictly an impact confirmation step. Spring Security and business permissions must still verify whether the caller is permitted to cancel the order.

## 18. HTTP-Method-Based Safe Classification Is Not Enough

A `GET` endpoint can cause side effects if poorly designed, such as `GET /cache/invalidate`. A `POST` endpoint might only generate a preview report yet be classified as mutating by default.

You can adjust `safe-methods` globally or use `McpToolCustomizer` to override an individual operation:

~~~java
@Bean
McpToolCustomizer classifyOperations() {
    return (context, path, method, operation) -> {
        if (method == PathItem.HttpMethod.GET
                && "/api/cache/invalidate".equals(path)) {
            context.setSafeEndpoint(false);
        }
        return context;
    };
}
~~~

Only mark a `POST` as safe when certain the operation does not mutate business state. This classification is a guardrail for agents; it does not alter HTTP semantics and does not stop callers from sending direct REST requests.

## 19. Tool Input Schemas Do Not Replace REST API Validation

Springdoc converts parameters and request bodies from OpenAPI into input JSON Schemas for tools. Schemas tell MCP clients the data types, required flags, and constraints before invoking.

However, agents can send malformed data, clients may ignore schemas, and users can call REST endpoints directly. The target API must still perform:

- Jackson deserialization.
- Bean Validation with `@Valid`.
- Business rule checks.
- Resource permission checks.
- Current state checks before writing.

Never rely on an LLM to validate amounts, tenants, order statuses, or user permissions. Validation and authorization belong on the server.

## 20. HTTP Request Behavior When a Tool Is Invoked

When a tool executes, the components of the OpenAPI operation govern the request:

| OpenAPI Operation | Actual HTTP Request |
|---|---|
| Path parameter | Substituted into the path template |
| Query parameter | Encoded into the query string |
| Header parameter | Placed into the corresponding header |
| Request body | Serialized into the body matching content type |
| HTTP method | `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, etc. |
| Server/base URL | Determines host and context path |

Example tool input:

~~~json
{
  "id": "ORD-1001",
  "notifyCustomer": true,
  "body": {
    "reason": "Customer requested cancellation"
  }
}
~~~

This can produce a corresponding request:

~~~http
POST /api/orders/ORD-1001/cancel?notifyCustomer=true
Content-Type: application/json
Authorization: Bearer <downstream-token>

{
  "reason": "Customer requested cancellation"
}
~~~

The `Authorization` header in the example appears only if the execution path is configured to attach downstream credentials. Never assume it appears automatically just because the MCP client sent a Bearer token on `/mcp`.

## 21. Responses and Errors from the Target API

The tool callback must handle HTTP outcomes from the target API. Common cases:

- `2xx`: operation completed per response contract.
- `400` or `422`: invalid input or business rule violation.
- `401`: downstream request lacks or has invalid credentials.
- `403`: downstream principal lacks permission.
- `404`: resource does not exist or is hidden under resource-concealment policy.
- `409`: resource state conflict.
- `429`: rate limited.
- `5xx`: target API encountered an error.
- Timeout/connection error: uncertain whether the backend processed the request.

Do not disguise a downstream `401` as an MCP login failure if the two layers use separate credentials. Logs should make clear whether the failure occurred at the MCP transport or during the HTTP call to the target API.

Never return stack traces, SQL, tokens, or sensitive data in tool results. Use a stable error response with error code, safe message, and correlation ID for investigation.

## 22. Timeouts, Retries, and Idempotency

Tool callbacks call APIs over the network and can hit timeouts or dropped connections. An important scenario:

1. The agent invokes create order.
2. The backend persists the order successfully.
3. The response is lost on the network.
4. The MCP client observes a timeout and retries.
5. The backend may create a duplicate second order.

There is no exactly-once guarantee just because a request arrives via MCP. For write operations, consider:

- Business-level idempotency keys.
- Unique constraints or backend deduplication.
- Queryable operation state.
- Bounded timeouts and controlled retry policies.
- Never auto-retrying `POST` unless the operation is known to be idempotent.

If the target API supports `Idempotency-Key`, describe and pass it under an explicit design. Do not let agents invent arbitrary keys and assume the backend always deduplicates.

## 23. Tenant Isolation and Multi-Tenant Data

In multi-tenant systems, access depends on more than roles. Determine the tenant from token claims or a trusted context.

For example:

- The token carries a `tenant_id` claim.
- The service reads the current tenant from the authenticated principal.
- Repository queries always filter by tenant.
- Object-level authorization confirms the resource belongs to that tenant.

Never let an agent pass an arbitrary `tenantId` and use it directly in queries. If a tool needs a tenant selector, the server must verify the user is allowed to access that tenant.

If downstream calls share a service account, the backend sees only the service principal. In that case, use a trusted delegation mechanism to carry verified user/tenant context; never trust a caller-set `X-Tenant-Id` header without signature verification or a trusted source.

## 24. Header Forwarding and Trust Boundaries

Springdoc documentation notes that the dashboard can forward `Authorization` and API keys to underlying API calls. For other MCP clients, explicitly verify what forwarding mechanisms your version and transport provide; never infer forwarding merely because the MCP request carried headers.

If forwarding headers is required:

- Allowlist only headers that are strictly needed.
- Never forward `Cookie`, `Host`, `Content-Length`, or hop-by-hop headers.
- Never forward tokens to another host if audiences do not match.
- Never write raw credentials to logs.
- Verify headers cannot be forged by clients.
- Prefer token exchange over raw token forwarding across multiple resource servers.

Do not make `Authorization` a tool argument or an OpenAPI query parameter. Credentials must travel through authentication mechanisms, never through agent-controlled JSON inputs.

## 25. Protecting Origin and Network Boundaries

HTTP MCP endpoints may be reached from browsers or internal networks. Spring AI notes that HTTP transports do not validate `Origin` by default; applications or reverse proxies should verify `Origin` to prevent DNS rebinding, especially on servers bound only to `localhost`.

Measures to consider:

- TLS at the MCP connection point.
- Client authentication and authorization.
- `Origin` allowlists for browser-accessible endpoints.
- Network ingress and egress restrictions.
- Per-principal or per-client rate limiting.
- Request body size and processing time limits.
- Never letting tool inputs control arbitrary backend URLs.
- Never letting `base-url` be modified from agent-supplied data.

Do not treat `localhost` as a security boundary. A malicious web page can attempt browser requests to services running on `localhost` or private networks if the transport lacks proper protections.

## 26. Auditing and Sensitive Data Redaction

Springdoc writes structured JSON audit events to the logger:

~~~text
org.springdoc.ai.mcp.audit
~~~

When the dashboard is enabled, some events are also held in memory for display. This is not a durable audit store; for long-term retention, ship logs to a centralized system with access controls.

Since Springdoc 3.1.1, audit redaction masks values under secret-like keys such as `authorization`, `password`, `token`, `api-key`, `secret`, and `cookie` by default. Current documentation describes masking across tool arguments, request URL query strings, request bodies, and response bodies.

Configuration:

~~~yaml
springdoc:
  ai:
    mcp:
      audit:
        redact: true
~~~

Keep redaction enabled. It does not replace minimizing sensitive data in payloads; a field holding personal data without a secret-like key name may not be detected. Never place passwords, access tokens, or secrets in descriptions, tool arguments, or responses unnecessarily.

## 27. Testing Each Security Boundary Separately

An integration test suite should distinguish failures at the MCP endpoint from failures at the target REST API:

| Scenario | Expectation |
|---|---|
| No token sent to `/mcp` | `401` |
| Expired token or invalid signature | `401` |
| Valid token lacking `mcp.invoke` | `403` |
| Valid MCP caller, no downstream credentials | Target REST API rejects; test proves two separate layers |
| Downstream service token lacking `orders.read` | Target REST API returns `403` |
| Valid scope but resource belongs to another tenant | Denied per object/tenant policy |
| Caller has sufficient permissions | Tool receives expected response |
| Mutating tool requiring approval | Target API receives no request yet |
| Approved mutating tool | Target API receives exactly one request per test |
| Dashboard accessed without admin role | `403` |
| Audit event contains token in payload | Secret value is masked |

Do not mock `ToolCallback` alone and conclude security works. Boot the application or test server so real requests traverse security filters and API mappings.

## 28. Integration Tests for Live API Call Behavior

An end-to-end test can run a Spring Boot test server on a fixed test port or obtain the actual port and configure `base-url` accordingly. The target API can be the application itself or a separate test service.

Steps:

1. Start the application with MCP enabled.
2. Wait for OpenAPI preloading and MCP server readiness.
3. Connect an MCP test client with test credentials.
4. Call `tools/list` and verify the target tool is present.
5. Call `tools/call` with valid inputs.
6. Verify the target API receives the expected method, path, query, body, and credentials.
7. Verify the response is returned to the MCP client.
8. Call again with a token lacking the required scope and confirm the API rejects it.
9. Inspect the database or event log to confirm side effects occurred the expected number of times.

If using a `localhost` `base-url` with `server.port=0`, do not assume the callback knows the random port automatically. Pass the actual port into test configuration or use an explicitly allocated test port.

## 29. Testing Authorization Propagation

This is the most critical test when the target API needs user identity:

1. Send an MCP request as user A.
2. Invoke a tool reading user A's resource.
3. Confirm the backend receives the principal or delegation context for user A.
4. Request a resource belonging to user B.
5. Confirm the backend denies it even though the tool input has a valid ID.
6. Send a request as user B and confirm distinct permissions apply.

If both user A and user B appear to the backend under a single service account, re-examine delegation policies and tenant context. Never claim per-user authorization works if the backend only sees a service identity.

If identity cannot be propagated safely over HTTP calls, change the design: use a native MCP tool calling the service layer within the same verified security context, or build a dedicated token-exchange adapter. Never work around it by trusting `userId` from arguments.

## 30. Common Errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| MCP client receives 401 | Missing, expired token, or wrong issuer | Check resource server and `Authorization` header |
| MCP client receives 403 | Missing scope/role to enter MCP | Grant appropriate `mcp.invoke` permission |
| Tool appears yet invocations return 401 | Downstream HTTP request lacks credentials | Check separate credentials for the target API |
| Dashboard succeeds yet MCP client fails | Dashboard has separate header forwarding | Test MCP client flow and design propagation explicitly |
| Tool receives 403 at target API | Insufficient scope, role, tenant, or object permission | Inspect which principal the backend actually receives |
| Request hits wrong service | Wrong `base-url`, context path, or DNS | Check URL and network from the MCP process |
| Tool returns 404 | Wrong path parameter or base URL; resource may be hidden | Inspect sent request and resource policy |
| Duplicate data created after timeout | Retried non-idempotent mutation | Use idempotency keys and deduplication |
| Approval enabled yet request still runs | Confused approval with authorization or used admin flow | Protect `/mcp` and `/api/mcp-admin/**` |
| User reads another tenant's data | Trusted `tenantId` from tool input | Read tenant from authenticated identity and check ownership |
| Method security has no effect | Missing `@EnableMethodSecurity` or non-proxied call | Check configuration and service invocation path |
| Token sent to wrong backend | Forwarded credentials without checking audience | Use token exchange or an appropriate service identity |
| Logs leak secrets | Redaction disabled or key name unrecognized | Enable `redact` and minimize sensitive payloads |
| Localhost MCP called unexpectedly from browser | Missing `Origin` validation or network boundary | Apply an `Origin` allowlist and security layer |

When investigating, record the HTTP status of the MCP request and the downstream REST request separately. The two requests may have two different principals, two different tokens, and two different correlation IDs.

## 31. Security Deployment Workflow

Follow these steps in order:

1. Identify the MCP client, transport, resource server, and backend API.
2. Determine whether callers need end-user identity or service identity.
3. Protect `/mcp` with Spring Security and a dedicated scope.
4. Protect the dashboard and admin API with a dedicated role.
5. Protect REST endpoints and service methods with business permissions.
6. Verify token audience, issuer, expiry, and scopes.
7. Configure `base-url` with the right host, port, and context path.
8. Design downstream credentials using a service account, token exchange, or native tool/service calls.
9. Never trust `userId`, `tenantId`, or `role` sent in tool arguments.
10. Keep approval enabled for mutations and treat it as an extra guardrail.
11. Enable audit redaction and ship logs to a controlled system.
12. Add `Origin` validation, TLS, rate limiting, and network policies.
13. Run integration tests covering both MCP requests and live REST requests.
14. Verify side effects, retries, idempotency, and tenant isolation.

Before opening endpoints to external clients, you must be able to answer which principal the target API sees when a tool runs and which policy constrains that principal.

## 32. Takeaways

- Springdoc generates MCP tools from OpenAPI operations and executes them via HTTP calls to the target API.
- MCP endpoints and REST endpoints are two distinct request boundaries.
- OpenAPI Security Schemes only describe security mechanisms; Spring Security enforces authentication and authorization.
- Credentials used to reach `/mcp` are not automatically credentials used for downstream REST requests.
- Springdoc documents header forwarding for the dashboard; do not extrapolate that to automatic forwarding for all MCP clients.
- `base-url` sets the HTTP call target; it does not issue tokens.
- Choose service identity, user delegation, or native service calls per business requirements.
- Never treat `userId` or `tenantId` from tool arguments as a trusted identity.
- Use request-level security for endpoints and method/object-level security for specific data.
- Enable `@EnableMethodSecurity` when using `@PreAuthorize`.
- Mutation approval is not authorization.
- Tool input schemas do not replace Jackson, Bean Validation, or business checks.
- Treat timeouts and retries as scenarios that can repeat side effects; use idempotency for write operations.
- Enable audit redaction and avoid logging raw credentials.
- Protect `Origin`, network boundaries, and MCP endpoints even when listening only on `localhost`.
- Integration tests must verify both MCP requests and live HTTP requests to the target API.

An MCP tool can modify real data because it invokes real REST operations. Proper security requires authenticating clients at the MCP endpoint, determining which credentials downstream requests use, and enforcing business permissions at the target API. Prove all three layers with integration tests using real principals, scopes, tenants, and side effects before exposing tools to agents.
