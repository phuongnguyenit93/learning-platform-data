# Configuring springdoc.api-docs.path and UI paths

Springdoc provides two important groups of paths: the path serving the OpenAPI JSON/YAML specification and the path opening the Swagger UI interface. In a directly accessed application, these URLs usually work right away with the default configuration. When changing paths, adding a context path, or placing the application behind a reverse proxy, you must ensure the browser, Swagger UI, swagger-config, and backend all see a consistent address.

Three path layers typically need to be distinguished:

1. **OpenAPI path:** where JSON/YAML is loaded from, e.g. /v3/api-docs.
2. **Swagger UI path:** the URL users open to access the UI, e.g. /swagger-ui.html.
3. **Context path or proxy prefix:** the application prefix or the public path added by a gateway, e.g. /catalog or /gateway.

Changing one layer does not automatically mean the other two layers change with it. Check the final URL that the browser calls, especially swagger-config and the OpenAPI document.

## 1. Default paths of Springdoc

In common Springdoc 2.x configurations, default URLs typically include:

| Resource | Default path | Purpose |
| --- | --- | --- |
| OpenAPI JSON | /v3/api-docs | OpenAPI specification in JSON format |
| OpenAPI YAML | /v3/api-docs.yaml | OpenAPI specification in YAML format |
| Swagger config | /v3/api-docs/swagger-config | Configuration used by Swagger UI to load documents |
| Swagger UI entry | /swagger-ui.html | Entry URL for opening the UI, usually redirects to UI resources |
| Swagger UI static resources | /swagger-ui/** | HTML, JavaScript, CSS, and UI assets |
| Group OpenAPI | /v3/api-docs/{group} | Specification of a GroupedOpenApi |

Actual paths may vary depending on the Springdoc version, application configuration, and how the reverse proxy forwards requests. The table above is a starting point for inspection, not a substitute for checking the Network tab or the application's endpoint mappings.

## 2. Changing the OpenAPI path with springdoc.api-docs.path

The springdoc.api-docs.path property changes the base path of the OpenAPI endpoint. For example, switching from /v3/api-docs to /openapi:

~~~yaml
springdoc:
  api-docs:
    path: /openapi
~~~

Or using application.properties:

~~~properties
springdoc.api-docs.path=/openapi
~~~

After configuring this, the URLs typically look like:

| Resource | URL |
| --- | --- |
| Default JSON | /openapi |
| YAML | /openapi.yaml |
| Swagger config | /openapi/swagger-config |
| Partner group | /openapi/partner |
| Partner group YAML | /openapi/partner.yaml |

The specific group path depends on the registered group name. If a group is named internal, its document URL will be based on the new base path and that group name.

Changing the path does not change the schemas, operations, tags, or responses inside OpenAPI. It only changes where the documentation is served. Clients, gateways, security matchers, and specification-fetching pipelines need to be updated to the new URL.

## 3. Changing the UI path with springdoc.swagger-ui.path

The springdoc.swagger-ui.path property changes the entry URL that users open to enter Swagger UI:

~~~yaml
springdoc:
  swagger-ui:
    path: /docs
~~~

Or:

~~~properties
springdoc.swagger-ui.path=/docs
~~~

Users access:

~~~text
http://localhost:8080/docs
~~~

The entry path may redirect to the actual Swagger UI page. Static resources are still served via Swagger UI's resource URLs, typically under /swagger-ui/**. Therefore, when changing the entry path, do not assume every UI request moves to /docs/**.

If Spring Security protects Swagger UI, both the new entry path and the static resource path must be updated. If the application runs behind a proxy with a prefix, verify whether the redirect Location preserves the correct public prefix.

## 4. Combining the OpenAPI path and Swagger UI path

Both paths can be changed at the same time:

~~~yaml
springdoc:
  api-docs:
    path: /openapi
  swagger-ui:
    path: /docs
~~~

In a local environment, users can open /docs. Swagger UI loads swagger-config from the path derived from the API docs configuration and then loads the specification at /openapi.

When manually configuring url or config-url in Swagger UI, check whether they override the default URL generated by Springdoc. Do not configure a URL pointing to the old /v3/api-docs after changing api-docs.path to /openapi.

Do not confuse springdoc.swagger-ui.url with springdoc.swagger-ui.path:

| Property | Meaning |
| --- | --- |
| springdoc.swagger-ui.path | URL to open the Swagger UI page |
| springdoc.swagger-ui.url | URL of an OpenAPI document loaded by the UI |
| springdoc.swagger-ui.config-url | URL of swagger-config loaded by the UI |
| springdoc.api-docs.path | Base path where Springdoc serves OpenAPI documents |

Only set url or config-url when you need a dedicated document source, an externally hosted document, or custom UI configuration. For standard setups, letting Springdoc generate swagger-config reduces the risk of the two URLs drifting out of sync.

## 5. Distinguishing Springdoc paths from the application context path

A servlet application can run under a context path, for example:

~~~yaml
server:
  servlet:
    context-path: /catalog

springdoc:
  api-docs:
    path: /openapi
  swagger-ui:
    path: /docs
~~~

In that case, the external URLs of the application typically take the form:

~~~text
http://localhost:8080/catalog/openapi
http://localhost:8080/catalog/openapi.yaml
http://localhost:8080/catalog/docs
~~~

In this configuration, /catalog is the context path of the entire application; /openapi and /docs are paths declared by Springdoc inside that context.

For WebFlux applications, the application base path can be configured with spring.webflux.base-path. Do not use server.servlet.context-path for a pure WebFlux application. Choose the right property for the web stack the application actually runs on.

The context path affects application routes, not just documentation. When adding or changing the context path, update the associated API URLs, redirects, callbacks, security matchers, and proxy configuration.

## 6. Applications behind a reverse proxy with a path prefix

In production, a reverse proxy or API gateway often exposes the application under a prefix, for example:

~~~text
https://api.example.com/gateway/
~~~

The backend may run at http://127.0.0.1:8080 and see only the path rewritten by the proxy. You need to determine whether the proxy is:

- Keeping the /gateway prefix when forwarding requests to the backend; or
- Stripping the /gateway prefix and forwarding requests to internal paths like /docs or /openapi.

These two approaches produce different request URIs at the backend. If misaligned, Springdoc may generate redirects or swagger-config URLs pointing to internal paths, causing the browser to call the wrong endpoint.

A simple proxy contract needs to specify clearly:

| Component | Example |
| --- | --- |
| Public URL | https://api.example.com/gateway |
| Backend origin | http://127.0.0.1:8080 |
| Public prefix | /gateway |
| Internal OpenAPI path | /openapi |
| Internal Swagger UI path | /docs |
| Expected public OpenAPI URL | https://api.example.com/gateway/openapi |
| Expected public Swagger UI URL | https://api.example.com/gateway/docs |

Do not test only the backend using localhost. Open the public URL through the proxy because that is the URL clients and browsers actually use.

## 7. Forwarded headers help the application recognize the public URL

When a proxy terminates TLS or alters host/port/prefix, the backend may only see internal HTTP. The reverse proxy should pass the original details via Forwarded or the appropriate X-Forwarded-* headers, typically including:

- X-Forwarded-Host: the public hostname accessed by the client.
- X-Forwarded-Proto: the public scheme, typically https.
- X-Forwarded-Port: the public port if different from the default port.
- X-Forwarded-Prefix: the public prefix stripped by the proxy before forwarding the request, e.g. /gateway.

Spring Boot can configure how forwarded headers are handled:

~~~yaml
server:
  forward-headers-strategy: framework
~~~

The framework strategy uses Spring's forwarded-header handling mechanism. Depending on the web server and environment, the native strategy may also be suitable. Choose one consistent handling approach and avoid having multiple layers interpret the headers and produce incorrect URLs.

Nginx example when stripping the /gateway prefix before sending requests to the backend:

~~~nginx
location /gateway/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Port $server_port;
    proxy_set_header X-Forwarded-Prefix /gateway;
}
~~~

In the configuration above, the trailing slash on proxy_pass causes Nginx to replace the URI portion matching the location with the specified URI; a request to /gateway/docs is forwarded to the backend under path /docs. X-Forwarded-Prefix informs the application of the public prefix to preserve in generated URLs.

If the proxy keeps the prefix intact and the backend is also configured to serve under that prefix, do not simultaneously instruct the framework to add the prefix again. Clearly designate where the prefix is handled to avoid URLs like /gateway/gateway/docs.

## 8. Only trust forwarded headers from trusted proxies

Forwarded headers can be sent directly by clients if the proxy does not strip or overwrite them. If the application trusts forged headers, redirect URLs or documentation URLs can point to an attacker-controlled host, scheme, or prefix.

At the edge proxy:

1. Overwrite client-sent forwarded headers with values determined by the proxy itself.
2. Do not pass through X-Forwarded-Host or X-Forwarded-Proto provided by the client verbatim.
3. Only allow the backend to receive requests from permitted proxies or networks.
4. Configure a clear trust boundary if multiple proxies are chained.
5. Inspect generated URLs in the real environment rather than relying solely on configured header values.

Do not enable forwarded-header processing indiscriminately when the application is directly reachable from the Internet. Headers should only be trusted when requests pass through a controlled proxy.

## 9. Path rewrite and Swagger UI redirects

A common error is that the entry URL opens but redirects to a path missing the prefix. For example:

~~~text
Public URL:       https://api.example.com/gateway/docs
Redirect Location: https://api.example.com/swagger-ui/index.html
Expected:         https://api.example.com/gateway/swagger-ui/index.html
~~~

The usual cause is that the backend does not recognize the public prefix or the proxy is not forwarding headers properly. Check:

- The Location response header of the /docs request.
- HTML, JavaScript, and CSS requests in the Network tab.
- The swagger-config URL loaded by Swagger UI.
- The OpenAPI document URL inside swagger-config.
- X-Forwarded-Prefix, X-Forwarded-Proto, and X-Forwarded-Host in requests reaching the backend.

If the UI entry redirects properly but swagger-config points to the old /v3/api-docs, check springdoc.api-docs.path and springdoc.swagger-ui.config-url. If the config is correct but static resources return 404, check whether the proxy forwards /swagger-ui/**.

## 10. Configuring custom paths in an application behind a proxy

Example of a Spring MVC application running at backend root while the proxy exposes it under /gateway and strips the prefix before forwarding:

~~~yaml
server:
  port: 8080
  forward-headers-strategy: framework

springdoc:
  api-docs:
    path: /openapi
  swagger-ui:
    path: /docs
~~~

Proxy exposes:

~~~text
https://api.example.com/gateway/docs
https://api.example.com/gateway/openapi
~~~

The backend receives requests under /docs and /openapi, while the forwarded prefix helps the framework build accurate public URLs when generating redirects or absolute links. Actual behavior also depends on whether the proxy forwards headers properly and whether Springdoc/Swagger UI generates relative or absolute URLs in the version in use.

If the application has its own context path, e.g. /catalog, both the context path and proxy prefix must be accounted for. Avoid configuring the same prefix in server.servlet.context-path, spring.webflux.base-path, and proxy rewrite unless they serve distinct intended layers.

## 11. Customizing swagger-config and document URLs

Swagger UI typically loads its configuration from swagger-config. This configuration specifies the OpenAPI document URL, group list, OAuth settings, and related UI options.

If you need to point the UI to a separately hosted document, you can configure springdoc.swagger-ui.url or the springdoc.swagger-ui.urls list as needed. In that case:

- The URL must be reachable from the browser, not just from the backend.
- If the UI and document are on different origins, CORS must be configured on the server serving the document.
- If the document requires authentication, the browser must have a way to send appropriate credentials.
- Do not point the browser to internal hostnames like localhost or Docker network service names.
- If using multiple groups, each URL must have a valid display name and public path.

When changing springdoc.api-docs.path, verify that the auto-generated swagger-config uses the new path. If you have manually overridden config-url or url, update them together so the UI does not keep calling the old endpoint.

## 12. Combining custom paths with Spring Security

When changing paths, security matchers must change too. Example:

~~~java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers(
        "/docs",
        "/swagger-ui/**",
        "/openapi",
        "/openapi.yaml",
        "/openapi/**"
    ).hasRole("API_DOCS")
    .anyRequest().authenticated()
);
~~~

The example above uses Spring Security 6 and internal application paths. If there is a context path, the servlet container usually strips the context path from the path processed by Spring Security matchers; verify according to your web stack and deployment configuration. If the proxy adds a prefix and strips it before forwarding, matchers generally use the internal post-rewrite path.

Do not protect only /docs. The JSON/YAML and swagger-config endpoints can be fetched directly. Also do not forget static assets /swagger-ui/**. When using config-url or group documents at other paths, add those exact URLs to the access policy.

## 13. Verifying URLs after changing configuration

After starting the application, test the internal endpoints:

~~~bash
curl -i http://localhost:8080/docs
curl -i http://localhost:8080/openapi
curl -i http://localhost:8080/openapi.yaml
curl -i http://localhost:8080/openapi/swagger-config
curl -i http://localhost:8080/swagger-ui/index.html
~~~

Then test the public URLs through the reverse proxy:

~~~bash
curl -i https://api.example.com/gateway/docs
curl -i https://api.example.com/gateway/openapi
curl -i https://api.example.com/gateway/openapi.yaml
curl -i https://api.example.com/gateway/openapi/swagger-config
~~~

The URLs in the examples should be replaced with your environment's host, prefix, and paths. Check the response status, Location, Content-Type, and body. For swagger-config, read the document URL that the UI will load; for the UI, open the Network tab to inspect asset and OpenAPI document requests.

Expected results:

| Check | Sign of correctness |
| --- | --- |
| Swagger UI entry | Returns the page or redirects to a URL with the right public prefix |
| OpenAPI JSON | Returns OpenAPI JSON |
| OpenAPI YAML | Returns OpenAPI YAML |
| Swagger config | Document URL points to a public path accessible from the browser |
| Static assets | JavaScript/CSS do not return 404 |
| Group document | Group URL uses the new base path and correct group name |

## 14. Common errors

| Symptom | Possible cause | How to fix |
| --- | --- | --- |
| /openapi returns 404 | Only client or proxy URL was changed, not springdoc.api-docs.path | Configure the property and check the backend endpoint |
| Swagger UI still calls /v3/api-docs | swagger-config or swagger-ui.url is overridden with the old path | Check config-url, url, and swagger-config |
| /docs opens but UI is blank | Static assets or swagger-config are blocked by proxy/security | Check /swagger-ui/** and Network requests |
| Redirect drops /gateway | Forwarded prefix is not sent or handled | Configure X-Forwarded-Prefix and forward-headers-strategy |
| Generated URLs use http instead of https | Backend does not receive X-Forwarded-Proto or does not handle forwarded headers | Configure proxy to overwrite proto and Spring forwarded header strategy |
| URL uses internal hostname | Wrong Host header or X-Forwarded-Host | Have proxy pass public hostname and overwrite client-sent headers |
| URL has /gateway/gateway | Prefix is added at multiple layers | Designate a single place to handle the prefix and remove duplicate config |
| /openapi.yaml returns 404 | Matcher or proxy only allows the base JSON path | Add separate route and security matcher for YAML |
| Group docs fail after path change | Client or UI still uses the old group URL | Update base path and check /openapi/{group} |
| Security blocks UI after path change | Matchers still use default paths | Update matchers for entry, assets, config, and document |
| Swagger UI loads doc from localhost | UI URL is hard-coded or swagger-config generates wrong origin | Use public URLs or proper forwarded headers |

## 15. Pre-deployment checklist

- [ ] Internal and public OpenAPI paths have been identified.
- [ ] Swagger UI entry path and static resource paths have been identified.
- [ ] springdoc.api-docs.path matches the route served by the backend.
- [ ] springdoc.swagger-ui.path matches the URL users open.
- [ ] JSON, YAML, swagger-config, and group URLs have all been tested.
- [ ] Springdoc paths are distinguished from servlet context path or WebFlux base path.
- [ ] Whether the reverse proxy keeps or strips the path prefix has been determined.
- [ ] Proxy overwrites client forwarded headers and sends accurate host/proto/prefix.
- [ ] server.forward-headers-strategy is chosen appropriately for the infrastructure.
- [ ] Redirect Location and URLs in swagger-config preserve the public host, scheme, and prefix.
- [ ] Static assets /swagger-ui/** are forwarded by the proxy.
- [ ] Spring Security matchers are updated for the internal post-rewrite paths.
- [ ] CORS is configured if Swagger UI and the OpenAPI document have different origins.
- [ ] No localhost URLs or internal hostnames appear in browser-visible configuration.
- [ ] Tested directly via the public URL, not just backend localhost.

springdoc.api-docs.path determines where OpenAPI JSON/YAML is served; springdoc.swagger-ui.path determines the URL for opening the UI. Context paths and reverse proxies can add or strip prefixes, so path rewrites, forwarded headers, redirects, swagger-config, and security matchers must stay aligned. Testing all requests through the public URL ensures users can load the UI and the right OpenAPI document after deployment.
