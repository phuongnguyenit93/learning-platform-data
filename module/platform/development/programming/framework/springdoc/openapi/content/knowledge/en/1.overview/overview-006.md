# What Can Be Inferred Automatically vs. What Must Be Added Manually

Springdoc-openapi generates an OpenAPI specification from Spring MVC/WebFlux controllers, Java data types, Spring annotations, Jackson metadata, Bean Validation, and OpenAPI annotations. As a result, many parts of an API can be described without manual duplication: paths, HTTP methods, parameters, request/response types, and part of the schemas.

However, code only expresses part of an API contract. Springdoc cannot automatically understand the full business meaning of a field, why a user is authorized to call an operation, every possible error scenario, realistic data examples, pagination policies, usage limits, or multi-endpoint workflows. Such details must be added using annotations, configuration, or accompanying documentation.

A key principle is to rely on automatic inference for structures verifiable from the implementation, while explicitly adding semantics and guarantees that consumers need to know. A good specification not only reflects current code, but also clearly communicates how clients are permitted and expected to use the API.

## 1. Understanding the Two Information Sources of an OpenAPI Document

An OpenAPI document generated by springdoc typically combines two groups of information:

1. **Information inferred from implementation:** Spring mappings, method signatures, Java types, generic types, DTOs, serialization annotations, and validation.
2. **Explicitly declared information:** business descriptions, examples, error responses, security schemes, security requirements, tags, servers, versioning policies, and conventions that cannot be reliably inferred.

The documentation generation flow can be visualized as:

~~~text
Spring MVC/WebFlux mappings
          |
          v
Controller methods + Java types
          |
          +---- Jackson / Bean Validation metadata
          |
          +---- Swagger/OpenAPI annotations
          |
          +---- Springdoc configuration/customizers
          |
          v
       OpenAPI model
          |
          v
      JSON / YAML
          |
          v
       Swagger UI
~~~

Swagger UI only renders the generated document. If information is wrong or missing in JSON/YAML, changing the Swagger UI display does not fix the contract itself.

## 2. What Springdoc Can Usually Infer

When controllers and dependencies are properly configured, springdoc can typically infer the following structural details:

| Element | Common Inference Source | Notes |
|---|---|---|
| Path | RequestMapping, GetMapping, PostMapping, and other mappings | Can combine prefixes from class and method |
| HTTP method | Spring mapping annotations | Avoid overly dynamic mappings or unintegrated custom routes |
| consumes/produces | Declared mappings and media types | Does not replace per-part encoding descriptions in multipart requests |
| Path parameter | PathVariable and placeholders in paths | Explicit names should be declared |
| Query parameter | RequestParam, parameter type, and name metadata | Inferred name depends on compiler metadata if omitted in annotation |
| Header/cookie parameter | RequestHeader, CookieValue | Explicit name/value should be declared |
| Request body | RequestBody, RequestPart, and DTO types | Multipart requires appropriate schema descriptions |
| Response schema | Return type, generic type, and wrappers | ResponseEntity or reactive wrappers do not reflect all runtime branches |
| DTO properties | Java beans, records, Jackson metadata | JSON names can differ from Java field names |
| Enum values | Enum types | Meaning of each value still needs description |
| Certain constraints | Bean Validation annotations | Cannot express every business rule |
| OpenAPI annotations | Schema, Operation, Parameter, ApiResponse... | These are developer-supplied metadata, not pure inference |

This list describes common capabilities, not a guarantee that every custom structure is recognized identically across all versions. After upgrading Spring Boot, Spring Framework, or springdoc, always inspect the actual document.

## 3. Paths and HTTP Methods Are Usually Inferred from Spring Mappings

Example:

~~~java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping("/{orderId}")
    OrderResponse getOrder(
            @PathVariable("orderId") UUID orderId) {
        // ...
    }

    @PostMapping
    OrderResponse createOrder(
            @RequestBody CreateOrderRequest request) {
        // ...
    }
}
~~~

Springdoc can read the class-level mapping /api/orders, method-level mappings, and HTTP methods to generate the corresponding path operations.

Information that can be inferred:

- GET operation on /api/orders/{orderId}.
- POST operation on /api/orders.
- Path parameter orderId.
- Request body of the POST operation based on the DTO.

Information that must be added:

- Whether this API is meant for end users, staff, or internal systems.
- Which orders GET returns and what visibility rules apply.
- Which initial status POST creates an order in.
- Business conditions under which requests are rejected.
- Whether the operation is idempotent by system design.

Path and method names cannot replace a meaningful summary or description.

## 4. Parameters Can Be Inferred, Yet Public Names Should Stay Stable

Springdoc can read annotations such as PathVariable, RequestParam, RequestHeader, and CookieValue. When an annotation omits an explicit name, the framework may rely on the method parameter name.

Example:

~~~java
@GetMapping("/search")
List<OrderResponse> search(
        @RequestParam(name = "status", required = false) String state,
        @RequestParam(name = "page", defaultValue = "0") int page) {
    // ...
}
~~~

Here the public names are status and page, even though the first Java variable is named state. This avoids depending on source variable renames or compiler metadata.

For public APIs, explicitly declare:

- PathVariable("orderId")
- RequestParam(name = "page")
- RequestHeader(name = "X-Tenant")
- CookieValue(name = "sessionId")

If relying on method parameter names, Java must be compiled with -parameters so names are retained in bytecode. Even with the compiler option enabled, explicit names keep the HTTP contract stable during refactors.

## 5. Request and Response Schemas Are Inferred from Java Types

DTO example:

~~~java
public record CreateOrderRequest(
        String customerCode,
        List<OrderItemRequest> items
) {}

public record OrderResponse(
        UUID id,
        String status,
        Instant createdAt
) {}
~~~

Springdoc can infer object schemas, properties, data types, arrays, and references to nested schemas from Java types.

However, Java types do not explain:

- Which system customerCode belongs to.
- Whether items is allowed to be empty.
- Which valid statuses exist for status and what each means.
- Whether createdAt is in UTC or a business timezone.
- Which fields appear only when the caller has special permissions.

Use Schema and Bean Validation to supply appropriate metadata:

~~~java
@Schema(name = "CreateOrderRequest")
public record CreateOrderRequest(
        @Schema(
                description = "Customer code issued in the system",
                example = "CUS-10025"
        )
        @NotBlank
        String customerCode,

        @Schema(
                description = "Order line items to create",
                minItems = 1
        )
        @NotEmpty
        List<@Valid OrderItemRequest> items
) {}
~~~

Schema describes the contract; validation enforces constraints at runtime. Both are related, yet neither replaces the other.

## 6. Jackson Affects JSON Names and Shape

Java DTOs are serialized to JSON according to Jackson rules. Therefore, schemas generated by springdoc are influenced by supported serialization annotations.

Example:

~~~java
public record CustomerResponse(
        @JsonProperty("customer_code")
        String customerCode,
        String displayName
) {}
~~~

The public JSON property name is customer_code, not customerCode. When a JSON name differs from the Java name, check that the OpenAPI schema reflects the Jackson configuration accurately.

Factors to review:

- JsonProperty and naming strategies.
- JsonIgnore or JsonProperty(access = ...).
- Getters/setters and field visibility.
- Record components.
- Custom serializers/deserializers.
- Globally or module-configured ObjectMapper.

Never infer the JSON contract solely from field names in source code. The OpenAPI document and actual serialized JSON must align.

## 7. Bean Validation Supplies Part of the Constraints

Certain constraints can be reflected in the schema, for example:

| Annotation | Meaning Typically Representable |
|---|---|
| NotNull / NotBlank / NotEmpty | Required or non-empty value |
| Size | Length or element count bounds |
| Min / Max | Numeric bounds |
| DecimalMin / DecimalMax | Decimal numeric bounds |
| Pattern | Regular expression |
| Email | Email format |

Example:

~~~java
public record RegisterCustomerRequest(
        @NotBlank
        @Size(max = 100)
        String fullName,

        @NotBlank
        @Email
        String email,

        @Min(18)
        @Max(120)
        Integer age
) {}
~~~

Springdoc can use constraint metadata to add required, minLength, maxLength, pattern, minimum, or maximum depending on type and version.

Yet rules such as "email must belong to a verified corporate domain", "age must suit the product", or "customer code must belong to the logged-in tenant" cannot be fully inferred from Java types. They must be documented separately and still enforced in the service/domain layer.

## 8. Enum Types Can Generate Value Lists

Java enums usually let springdoc generate a list of allowed values in the schema:

~~~java
public enum OrderStatus {
    DRAFT,
    PENDING,
    PAID,
    CANCELLED
}
~~~

The schema can list the enum values. Yet technical names do not explain the states:

| Value | Business Meaning to Add |
|---|---|
| DRAFT | Order created but not yet submitted for confirmation |
| PENDING | Awaiting processing or payment |
| PAID | Successful payment recorded |
| CANCELLED | Order cancelled according to system rules |

If consumers need to understand transitions, preconditions, or state change possibilities, document them in the Schema description, Operation description, or separate workflow docs. An enum list does not describe a state machine.

## 9. Information You Should Not Expect Springdoc to Infer Automatically

The following details usually require manual additions or dedicated configuration:

| Information | Why It Must Be Added |
|---|---|
| Business name and operation purpose | Method names are merely implementation details |
| Useful summary/description | Mappings do not explain API intent |
| Realistic request/response examples | Java types cannot produce meaningful example data |
| Business error responses | Not all exception branches are visible from method signatures |
| Authentication schemes | Spring Security filter chains do not automatically become OpenAPI security schemes |
| Required permissions/scopes | Authorization rules cannot be fully inferred as consumer contracts |
| Tags and API groups by audience | Packages/classes do not always reflect desired documentation organization |
| Environment-specific server URLs | Local, staging, production, and gateway URLs can differ |
| Rate limits/quotas | Usually reside in gateways or policies outside controllers |
| Idempotency and retry semantics | Cannot be inferred from HTTP methods alone |
| Pagination/sorting conventions | Must explain how clients use the parameters |
| Deprecation and sunset policies | Are API lifecycle decisions |
| Multi-operation workflows | Require describing sequence and business preconditions |
| Data classification | Sensitivity levels cannot be inferred from Java types |

## 10. Summaries and Descriptions Should Reflect Semantics

Method names like create, save, process, or handle do not tell integrators enough.

Example addition:

~~~java
@Operation(
        operationId = "createOrder",
        summary = "Create a new order",
        description = """
                Creates an order from a customer code and a list of line items.
                The system checks customer access rights, current pricing,
                and the validity of each line item before recording the order.
                """
)
@PostMapping
OrderResponse createOrder(
        @Valid @RequestBody CreateOrderRequest request) {
    // ...
}
~~~

Summaries should be short and distinguish operations in the list. Descriptions explain preconditions, effects, and rules clients need to know.

Never put secrets, internal data, or sensitive implementation details in descriptions.

## 11. Request and Response Examples Need Meaningful Data

Schemas only indicate string, integer, or object types. Examples help consumers understand format and context:

~~~java
public record CustomerCodeExample(
        @Schema(
                description = "Customer code",
                example = "CUS-10025",
                minLength = 3,
                maxLength = 20
        )
        String customerCode
) {}
~~~

For responses:

~~~java
@ApiResponse(
        responseCode = "201",
        description = "Order created",
        content = @Content(
                mediaType = "application/json",
                schema = @Schema(implementation = OrderResponse.class),
                examples = @ExampleObject(
                        name = "created-order",
                        value = """
                                {
                                  "id": "b4e7b1e0-72d3-4d75-9b8c-01e5c6c83f15",
                                  "status": "PENDING"
                                }
                                """
                )
        )
)
~~~

Examples must be valid against the schema and must not use real customer data. If a field has format or enum constraints, the example must adhere to them.

## 12. Error Responses Must Be Clearly Documented

From an OrderResponse return type, springdoc can infer the common success response. Yet the implementation may throw exceptions across layers that are handled by ControllerAdvice.

Consumers need to know cases such as:

- 400: invalid request data.
- 401: unauthenticated.
- 403: insufficient permissions.
- 404: resource does not exist or is not visible to the caller.
- 409: state conflict or idempotency key conflict.
- 422: syntactically valid data that violates business rules.
- 429: quota or rate limit exceeded.
- 500: unexpected system error.

Declare appropriate responses:

~~~java
@ApiResponses({
        @ApiResponse(
                responseCode = "201",
                description = "Order created",
                content = @Content(
                        schema = @Schema(implementation = OrderResponse.class)
                )
        ),
        @ApiResponse(
                responseCode = "400",
                description = "Invalid request data",
                content = @Content(
                        schema = @Schema(implementation = ApiError.class)
                )
        ),
        @ApiResponse(
                responseCode = "409",
                description = "Order conflicts with current state",
                content = @Content(
                        schema = @Schema(implementation = ApiError.class)
                )
        )
})
~~~

Documented responses must match the actual exception handlers and status codes. Annotations do not generate error responses or alter runtime behavior on their own.

## 13. Authentication and Authorization Must Be Declared Separately

Spring Security can protect endpoints using JWT, sessions, OAuth2, or custom filters. Springdoc should not be expected to automatically convert the entire runtime security configuration into OpenAPI security schemes.

Example declaring HTTP Bearer:

~~~java
@SecurityScheme(
        name = "bearerAuth",
        type = SecuritySchemeType.HTTP,
        scheme = "bearer",
        bearerFormat = "JWT"
)
~~~

Attach the requirement to an operation or class:

~~~java
@Operation(
        summary = "Get order",
        security = @SecurityRequirement(name = "bearerAuth")
)
~~~

Distinguish:

- SecurityScheme describes the authentication mechanism.
- SecurityRequirement indicates the operation requires that scheme.
- Spring Security enforces actual authentication and authorization.

Declaring a scheme without attaching a requirement can make Swagger UI know how to enter a token without marking the operation as requiring authentication. Conversely, a requirement referencing an undeclared scheme name creates an inconsistent document.

## 14. Tags and Grouping Are Documentation Organization Decisions

Springdoc can use classes/packages or configuration to group operations, yet consumer-friendly grouping is usually a design decision.

Example:

~~~java
@Tag(
        name = "Orders",
        description = "Create, look up, and manage the order lifecycle"
)
@RestController
@RequestMapping("/api/orders")
class OrderController {
    // ...
}
~~~

For large documents, use GroupedOpenApi to create documents by audience or functional domain:

~~~java
@Bean
GroupedOpenApi partnerApi() {
    return GroupedOpenApi.builder()
            .group("partner")
            .pathsToMatch("/api/partner/**")
            .build();
}
~~~

Whether an operation belongs to public, partner, or internal APIs should not rely solely on package names. Clearly define path filters and security policies for each group.

## 15. Server URLs and Deployment Environments

Controller mappings can show relative paths, yet do not necessarily show the URL consumers use in production. The application may run behind an ingress, API gateway, reverse proxy, or context path.

Details to determine:

- Public base URL.
- Context path or API prefix.
- HTTP/HTTPS.
- URLs for sandbox and production.
- Server variables if applicable.

Servers can be declared in OpenAPI metadata:

~~~java
@OpenAPIDefinition(
        servers = {
                @Server(
                        url = "https://api.example.com",
                        description = "Production API"
                ),
                @Server(
                        url = "https://sandbox-api.example.com",
                        description = "Sandbox API"
                )
        }
)
~~~

Never put placeholder URLs into production documents. If URLs vary by environment, use profile-based configuration or customizers and verify the output in each environment.

## 16. Pagination, Sorting, and Filtering Need Explanation

A method taking Pageable or page, size, and sort parameters does not fully explain the API's pagination behavior on its own.

Consumers need to know:

- Whether page index starts at 0 or 1.
- Default page size and maximum page size.
- Which sort fields are supported.
- Multi-field sort syntax and ASC/DESC direction.
- Whether filters combine with AND or OR.
- Whether cursors expire.
- Whether the response includes totalElements, totalPages, or nextCursor.

Use Parameter to describe parameters and Schema to describe pagination responses. If there are shared conventions, add descriptions at the tag level or in API overview docs.

## 17. Other Semantics That Must Be Added

The following details affect how clients use the API yet are usually not inferable from method signatures:

- **Idempotency:** which key clients can use to retry POST, key TTL, and replay behavior.
- **Rate limits:** request limits, time windows, and returned headers.
- **Concurrency:** ETag, If-Match, or version fields used to prevent lost updates.
- **Retries:** which errors are retryable, backoff, and attempt limits.
- **Asynchronous processing:** whether an operation returns a job ID or completes synchronously.
- **Webhooks/callbacks:** callback verification, delivery retries, and event ordering.
- **Deprecation:** sunset dates and replacement endpoints.
- **Data privacy:** which fields are sensitive and whether any are masked.

If these rules matter to consumers, put them in OpenAPI extensions, descriptions, or clearly linked operational docs.

## 18. Adding Module-Level Metadata

Overview information can be declared with OpenAPIDefinition:

~~~java
@OpenAPIDefinition(
        info = @Info(
                title = "Order API",
                version = "1.0.0",
                description = "Order lifecycle management API",
                contact = @Contact(
                        name = "API Support",
                        email = "api-support@example.com"
                ),
                license = @License(
                        name = "Internal Use"
                )
        ),
        externalDocs = @ExternalDocumentation(
                description = "Integration guide",
                url = "https://docs.example.com/order-api"
        )
)
~~~

This is data supplied by the API team. Springdoc cannot reliably infer title, public version, contact, or license from the Maven artifact name alone.

Do not use example emails or URLs in real environments; replace them with organization-approved addresses.

## 19. Using Customizers When Annotations Are Not Enough

When metadata comes from external configuration, or common rules must be applied, you can use OpenApiCustomizer:

~~~java
@Bean
OpenApiCustomizer addCommonDescription() {
    return openApi -> {
        if (openApi.getInfo() != null) {
            openApi.getInfo().setDescription(
                    "API for authorized partner integrations.");
        }
    };
}
~~~

Customizers are well suited for:

- Adding shared extensions.
- Standardizing tag or server metadata.
- Applying common descriptions to the document.
- Adjusting schemas or operations according to system rules.

Do not use customizers to hide mapping bugs or bulk-override metadata in hard-to-trace ways. With group configurations, clarify whether a customizer applies to the default document, individual groups, or all groups.

## 20. Choosing the Right Place to Add Metadata

| Need | Suitable Mechanism |
|---|---|
| Describe overall API, title, version, contact | OpenAPIDefinition / Info |
| Describe a single operation | Operation |
| Describe a single parameter | Parameter |
| Describe a field/schema | Schema |
| Request/response examples | ExampleObject |
| Response statuses and error schemas | ApiResponse / ApiResponses |
| Authentication mechanism | SecurityScheme |
| Operation requiring authentication | SecurityRequirement |
| Group operations | Tag / GroupedOpenApi |
| Adjust according to global rules | OpenApiCustomizer |

Choose the place closest to the scope of the information. Do not put a field's description into the overall API description or repeat the same paragraph on every operation when a schema/component can be reused.

## 21. Example Combining Inference and Manual Additions

The following controller uses Spring mappings and DTOs for structure while adding summary, description, responses, and parameter semantics:

~~~java
@Tag(name = "Orders", description = "Order management")
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @Operation(
            operationId = "getOrder",
            summary = "Look up an order",
            description = "Looks up an order that the caller has permission to view."
    )
    @ApiResponses({
            @ApiResponse(
                    responseCode = "200",
                    description = "Order found",
                    content = @Content(
                            schema = @Schema(implementation = OrderResponse.class)
                    )
            ),
            @ApiResponse(
                    responseCode = "404",
                    description = "Order not found",
                    content = @Content(
                            schema = @Schema(implementation = ApiError.class)
                    )
            )
    })
    @GetMapping("/{orderId}")
    OrderResponse getOrder(
            @Parameter(description = "Order identifier")
            @PathVariable("orderId") UUID orderId) {
        // ...
    }
}
~~~

Springdoc infers the path, method, path parameter, and response type. Annotations add operation semantics, parameter descriptions, and response statuses. The runtime service must still enforce authorization checks and return the corresponding status codes.

## 22. Do Not Confuse Description with Actual Behavior

OpenAPI annotations do not on their own:

- Enable authentication or authorization.
- Create runtime validation rules.
- Add response handlers.
- Change HTTP status codes.
- Enable rate limiting or idempotency.
- Change JSON serialization.
- Create new server endpoints.

For instance, ApiResponse(responseCode = "404") only documents the response. The controller or exception handler must still actually return HTTP 404 when the condition occurs.

Similarly, Schema(requiredMode = REQUIRED) does not replace Bean Validation. If data is mandatory, ensure runtime rejects missing data.

## 23. Inspecting the OpenAPI Document After Generation

Do not stop at opening Swagger UI. Download the JSON:

~~~bash
curl -fS http://localhost:8080/v3/api-docs -o openapi.json
~~~

Inspect paths:

~~~bash
jq '.paths | keys' openapi.json
~~~

Inspect an operation:

~~~bash
jq '.paths["/api/orders/{orderId}"].get' openapi.json
~~~

Inspect component schemas:

~~~bash
jq '.components.schemas' openapi.json
~~~

Inspect security schemes:

~~~bash
jq '.components.securitySchemes' openapi.json
~~~

Compare the output against:

- Actual mappings in controllers.
- JSON serialized by ObjectMapper.
- Actual validation.
- SecurityFilterChain and endpoint permissions.
- Exception handlers and status codes.
- Public URLs behind gateways/proxies.

If these sources contradict each other, the OpenAPI document is not yet a trustworthy contract.

## 24. Automated Testing to Catch Missing Information

You can write an integration test that fetches /v3/api-docs and verifies key parts:

~~~java
@Test
void orderOperationDocumentsExpectedContract() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andExpect(jsonPath(
                    "$.paths['/api/orders/{orderId}'].get.operationId")
                    .value("getOrder"))
            .andExpect(jsonPath(
                    "$.paths['/api/orders/{orderId}'].get.parameters[0].name")
                    .value("orderId"))
            .andExpect(jsonPath(
                    "$.paths['/api/orders/{orderId}'].get.responses.404")
                    .exists());
}
~~~

This test is only a structural check example. In real projects, look up parameters by name and in rather than assuming array order, and also check schemas, security requirements, and response content.

You can store OpenAPI JSON as an artifact in CI, validate it with an OpenAPI linter, and compare it with the previous release to detect breaking changes.

## 25. Decision Process: Automatic or Manual Addition?

For every piece of API information, ask:

1. Can this information be inferred directly from Spring mappings or Java types?
2. Does the metadata accurately reflect the HTTP contract after Jackson, validation, and custom resolvers?
3. Do consumers need to know business semantics that source code does not express?
4. Does the information affect security, errors, retries, versioning, or operations?
5. Can it be declared once at the schema, tag, class, or module level instead of repeated?
6. Is there an integration test confirming the document matches runtime?

If the answers to questions 1 and 2 are yes, prefer automatic inference to avoid duplicating structure. If questions 3 or 4 are yes, add explicit metadata. If question 6 is no, consider adding tests before publishing the API.

## 26. Checklist for Finalizing API Documentation

- [ ] Paths and HTTP methods match Spring mappings.
- [ ] Path/query/header/cookie parameter names match the HTTP protocol.
- [ ] Request and response schemas reflect actual JSON.
- [ ] Jackson annotations and naming strategies have been checked.
- [ ] Bean Validation is reflected and enforced at runtime.
- [ ] Enums have meaning descriptions if value names are not self-explanatory.
- [ ] Operations have helpful summaries and descriptions.
- [ ] Requests/responses have valid examples with no sensitive real data.
- [ ] Key error responses have accurate status codes and schemas.
- [ ] Security schemes and requirements match runtime policy.
- [ ] Tags and GroupedOpenApi reflect audiences/domains.
- [ ] Server URLs match environments and gateways.
- [ ] Pagination, sorting, retries, idempotency, and rate limits are documented where applicable.
- [ ] Deprecation and version policies are published.
- [ ] OpenAPI JSON is checked in CI.
- [ ] Contract has been diffed against the previous release.

## Conclusion

Springdoc-openapi can automatically infer substantial structural information from Spring mappings, controller signatures, Java types, Jackson, and Bean Validation. This capability avoids duplicating paths, methods, parameters, and schemas. Yet the implementation cannot fully explain business meaning, realistic examples, error responses, security policies, environment-specific servers, rate limits, idempotency, or the API lifecycle on its own. Let springdoc infer verifiable structure, supplement semantics with Operation, Parameter, Schema, ApiResponse, SecurityScheme, Tag, and OpenAPI configuration, and verify JSON/YAML against runtime behavior. That is how you produce documentation that stays close to code while remaining clear enough for consumers to integrate safely.
