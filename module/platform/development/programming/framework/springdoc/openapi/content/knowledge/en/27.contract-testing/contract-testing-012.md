# Contract Snapshots and Semantic Diffs Instead of Formatting Diffs Only

When a Spring Boot application changes controllers, DTOs, validation, or security settings, the OpenAPI Description generated by springdoc can change too. You need to know whether the edit merely alters document formatting or changes the contract clients rely on. Plain text diffs of two JSON/YAML files generate heavy noise: key ordering, whitespace, serialization style, or regenerated component names can shift without changing API semantics.

A **contract snapshot** is a captured OpenAPI Description generated from a specific application version and controlled environment. Snapshots are stored as baselines to compare against newer documents. A **semantic diff** analyzes OpenAPI structure and evaluates changes by contract meaning: paths, methods, parameters, schemas, responses, media types, and security. The goal is catching client-impacting edits rather than merely reporting that two files differ byte-for-byte.

Snapshots and semantic diffs complement runtime testing. They detect unexpected contract shifts, yet they do not by themselves prove the server implements the documentation or that all consumers remain compatible.

## 1. What Is a Contract Snapshot?

A contract snapshot is an OpenAPI document captured at a specific point in time and kept as a reference baseline. Snapshots are typically generated from a built application running with a controlled profile and configuration.

Example:

~~~text
api/
  openapi/
    catalog-v1.yaml       # Reviewed and released baseline
build/
  openapi/
    catalog-current.yaml  # Document generated from commit under test
~~~

Baselines can live in Git, an artifact repository, or a contract management system. Storing them in Git lets reviewers inspect contract history alongside code. Storing them as release artifacts preserves exact released contracts. Either way, track which commit, release, API group, and environment produced each snapshot.

A good snapshot includes:

- The complete OpenAPI document, not a Swagger UI screenshot.
- The matching API or release version.
- The documented API group and base path.
- The profile configuration used during generation.
- The commit or build identifier that generated the snapshot.
- Conventions for server URLs, environment variables, and auto-generated metadata.

A snapshot is an API contract description, not a recording of an actual request's runtime response. To verify live payloads, add integration tests or contract tests sending requests to the server.

## 2. Why Not Compare JSON/YAML with Plain Git Diff?

A JSON object is an unordered set of key/value pairs; key order carries no contract meaning. YAML mappings should likewise not be treated as semantically different merely because a serializer reordered lines. Consequently, two equivalent documents can yield massive text diffs.

Common sources of noise:

- Reordered keys inside JSON objects or YAML mappings.
- Different indentation, line breaks, quoting, or scalar formatting.
- Serializer differences for numbers, booleans, or nulls.
- Reordered generated components or schemas.
- Server URLs varying by host, port, or reverse proxy in the build environment.
- Timestamps, build metadata, or dynamic values injected into descriptions/examples.
- Auto-generated component names shifting after package or class refactors.
- Different groups or profiles altering the endpoint set in the document.

Git diff remains useful for reviewing prose, yet it answers "which lines changed?" rather than "can existing clients still call the API under the old contract?"

## 3. Format Canonicalization vs. Semantic Normalization

**Canonicalization** ensures identical structures serialize deterministically. For instance, parsing JSON and sorting object keys before writing to disk reduces key-order diffs.

~~~bash
jq -S . build/openapi.json > build/openapi.canonical.json
~~~

This command sorts keys inside JSON objects. It does not evaluate API compatibility or eliminate semantic changes—it only reduces formatting noise.

Never blindly sort every array. In OpenAPI, array order can affect display or precedence, such as `tags` or `servers` order. Security requirements carry OR semantics across array items, while schemes within a requirement carry AND semantics. Sorting or merging arrays without semantic awareness can alter the document's meaning.

**Semantic normalization** requires an OpenAPI-aware parser to distinguish:

- Unordered map/object keys.
- Arrays whose ordering is preserved by contract or UX.
- References pointing to identical schemas.
- Operations keyed by path and HTTP method.
- Effective security requirements at root and operation levels.
- Request and response schemas evaluated by data direction.

Never strip `description`, `example`, `deprecated`, `security`, or server URLs just to make diffs look cleaner. Those fields matter to consumers, operations, and security. If a specific check ignores certain change types, document that policy explicitly and retain full diffs for reviewers.

## 4. Generating Snapshots from a Deterministic Environment

springdoc usually serves documentation at **/v3/api-docs** or group endpoints. A Gradle plugin can boot Spring Boot, fetch the endpoint, and write the file. Example:

~~~bash
./gradlew clean test generateOpenApiDocs
~~~

To keep snapshots comparable, control:

1. **Spring profile:** use a consistent documentation profile close to production settings.
2. **API group:** generate the exact group being compared; never accidentally compare a public API against an admin API.
3. **Server URL:** use stable values or separate configurations per environment intentionally.
4. **Dynamic values:** never emit timestamps, random IDs, or build-machine data into schemas/examples.
5. **Feature flags:** pin flags affecting endpoints and schemas.
6. **Security metadata:** generate with the intended release security policy.
7. **Dependencies:** pin springdoc and model library versions to avoid unexpected serializer shifts.

When documentation has multiple groups, keep a separate baseline per API group. A change in an admin group should never overwrite the public API baseline.

Never auto-update the baseline whenever CI produces a new file. Baselines should change only after semantic diffs are reviewed and contract edits are approved.

## 5. What Does a Semantic Diff Evaluate?

A semantic diff parses two OpenAPI documents and compares contract elements. Depending on the tool, findings may be categorized as:

- **Breaking:** changes that can break clients conforming to the previous contract.
- **Potential breaking:** insufficient information to decide conclusively, or requires review against consumer usage.
- **Non-breaking:** changes preserving compatibility with the old contract under the tool's rules.
- **Documentation-only:** description, example, or metadata edits not affecting the wire contract.

No single classification fits every organization. For example, adding a response property is usually contract-compatible, yet a strict client generator or deserializer might reject unknown fields. Conversely, a description change may not break parsers while altering business guidance for integrators.

Treat semantic diffs as rule-based analysis rather than absolute verdicts. Read the report, understand consumers, and apply your API's policy.

## 6. Changes That Are Typically Breaking

A change tends to be breaking when a request valid under the old baseline becomes invalid under the new spec, or when a new response can break old clients.

| Element | Change | Why It Can Break |
|---|---|---|
| Path/method | Removing a path or HTTP method | Clients calling the old operation get 404/405 |
| Parameter | Removing a parameter used by clients | Old requests lose part of the contract |
| Required request parameter | Adding a required parameter | Old clients omit the new parameter |
| Request body | Changing body from optional to required | Old bodyless requests become invalid |
| Request schema | Adding a property to `required` | Old clients may not send the new property |
| Request schema | Narrowing enums, min/max, patterns, or length bounds | Previously valid values get rejected |
| Request content | Dropping a supported media type | Old clients send an unaccepted content type |
| Response | Removing a response code or response body schema | Clients lose a documented outcome |
| Response schema | Removing a property or widening types beyond client handling | Clients lose expected fields or receive unexpected types |
| Response enum | Adding a new enum value | Exhaustive client enums may fail on unknown values |
| Security | Adding auth requirements or scopes | Old clients lacking new credentials/scopes get rejected |
| Serialization | Changing parameter `style`, `explode`, or `format` | Old client requests get parsed differently |

Example adding a required request property:

~~~yaml
components:
  schemas:
    CreateOrderRequest:
      type: object
      required:
        - productId
        - quantity
      properties:
        productId:
          type: string
        quantity:
          type: integer
~~~

If the baseline required only `productId` while the revision adds `quantity` to `required`, existing clients sending only `productId` no longer conform to the new contract. The server might still default `quantity` in code, yet the new specification declares it required. Gateways, validators, or SDKs generated from the new schema may reject those requests.

## 7. Usually Compatible Changes That Still Need Review

The following changes are often compatible, depending on how consumers and tooling behave:

| Change | Typical Classification | Why Review Is Still Needed |
|---|---|---|
| Adding a new path/method | Additive | May collide on `operationId` or access control |
| Adding an optional query parameter | Additive | Some gateways or client wrappers enforce custom rules |
| Adding an optional request property | Additive | Verify old/new servers and serializers |
| Adding an optional response property | Usually additive | Strict clients may reject unknown fields |
| Editing `description` | Documentation change | May alter integration guidance or business commitments |
| Adding `example` | Documentation change | Invalid examples can mislead consumers |
| Changing `tags` | Usually wire-compatible | Alters UI grouping and display order |
| Changing `operationId` | Usually HTTP-compatible | May rename methods in generated SDKs |
| Renaming component schema | May preserve wire schema | SDK generators may rename public model types |
| Changing server URL | Schema unchanged | Clients may hit wrong host or environment |
| Removing security requirement | Won't block old clients | Weakens security; requires security review |

A wire-compatible change can still break SDKs, operations docs, deployment flows, or security policies. Distinguish HTTP wire compatibility from generated client surface compatibility.

## 8. Evaluating Request and Response Directions Separately

Schemas involve more than data types; direction matters.

### Request Schemas

Clients send requests. Narrowing the accepted input set tends to be breaking:

- Adding fields to `required`.
- Removing old enum values.
- Adding tighter `minimum`, `maximum`, `minLength`, `maxLength`, or `pattern` constraints.
- Removing previously accepted media types.
- Changing nullable to non-nullable.

Conversely, relaxing constraints or adding optional properties expands valid inputs.

### Response Schemas

Servers return responses. Narrowing possible outputs can stay safe for old clients, whereas widening outputs can expose unhandled values:

- Removing a response property clients read: typically breaking.
- Widening a response type: clients may receive unhandled values.
- Adding enum values or union branches: exhaustive clients may fail.
- Adding optional response properties: usually compatible, though strict clients may break.
- Removing a response schema: clients lose payload guarantees they relied on.

Do not look only at whether a type "widened" or "narrowed." Ask: how does the set of valid requests change, and how does the set of possible server responses change? Both directions can yield opposite compatibility conclusions.

## 9. Security, `operationId`, and Server URLs Are Not Minor Details

### Security

Adding security requirements, OAuth2 scopes, or changing schemes can lock out existing clients. Removing a security requirement rarely breaks old clients, yet it is a security change requiring dedicated review. Never let a "non-breaking" classification mask an endpoint accidentally becoming public.

### `operationId`

`operationId` commonly drives method naming in SDK generation. Changing `operationId` leaves HTTP requests intact yet can break consumer compilation after an SDK upgrade. When publishing SDKs, treat `operationId` as part of your public developer surface.

### Server URLs

Changing `servers` can route clients to a different host, base path, or environment. A semantic diff may flag server URL edits, with impact depending on how clients use `servers` and configure endpoints. Do not strip server URLs from snapshots merely because local differs from production; standardize environments or compare baselines within matching environments.

## 10. Semantic Diffing with `oasdiff`

`oasdiff` is a CLI tool for comparing OpenAPI documents and catching consumer-impacting edits. Its main subcommands serve distinct roles:

| Command | Scope |
|---|---|
| **oasdiff breaking** | Reports only changes likely to break existing clients |
| **oasdiff changelog** | Reports consumer-relevant changes, both breaking and non-breaking |
| **oasdiff diff** | Full diff of API definitions, including documentation-only edits |
| **oasdiff validate** | Checks a document against supported OpenAPI and JSON Schema rules |

Comparing a baseline and revision:

~~~bash
oasdiff breaking api/openapi-baseline.yaml build/openapi.yaml
oasdiff changelog api/openapi-baseline.yaml build/openapi.yaml
oasdiff diff api/openapi-baseline.yaml build/openapi.yaml
~~~

`breaking` suits gating incompatible changes. `changelog` helps reviewers see all consumer-facing changes. `diff` helps when reviewing descriptions and examples too.

To fail CI on `ERR`-level breaking changes:

~~~bash
oasdiff breaking --fail-on ERR api/openapi-baseline.yaml build/openapi.yaml
~~~

You can also configure `WARN` thresholds if your organization wants to block changes needing review. Never promote every `WARN` to a failure without understanding the rules and false positives; conversely, never blanket-ignore `WARN`s just to keep pipelines green.

## 11. Reading Severities and Applying Policy

`oasdiff` classifies findings by severity:

- **ERR:** clear breaking change under the documented contract.
- **WARN:** potentially breaking, requiring additional context.
- **INFO:** noted change not classified as breaking under current rules.

By default, `breaking` focuses on `ERR` and `WARN`. Use **--fail-on ERR** to block only definite breaks, or **--fail-on WARN** to block warnings as well.

Severity reflects tool rules and current configuration, not a substitute for human review. If a recurring `WARN` is verified safe in your architecture, adjust that specific rule's severity via tool config. Record the rationale and owner; never lower thresholds globally just to wave a PR through.

Likewise, if an `INFO` change impacts generated SDKs or security, the API team can still mandate manual review.

## 12. CI Pipeline with Snapshots and Semantic Diffs

A basic pipeline:

~~~bash
# 1. Build, test, and generate OpenAPI from the current app
./gradlew clean test generateOpenApiDocs

# 2. Validate the current document
oasdiff validate build/openapi.json

# 3. Compare against the approved snapshot
oasdiff breaking --fail-on ERR api/openapi-baseline.yaml build/openapi.json

# 4. Print changelog for reviewers
oasdiff changelog api/openapi-baseline.yaml build/openapi.json
~~~

This example uses the Gradle plugin's default JSON filename. If your plugin outputs YAML, update paths to match real output; never rename file extensions to fake formats.

On pull requests, CI should:

1. Generate the document from the commit under test.
2. Validate the document.
3. Diff against the target branch's or latest release's baseline.
4. Save the semantic diff report as an artifact or PR annotation.
5. Block merge when policy catches unapproved breaking changes.
6. Require reviewers to update the baseline alongside intentional contract edits.

Never diff a revision against a snapshot generated from a different profile. If the baseline is the production public API, the revision must generate the public API with matching settings.

## 13. Comparing Directly Against a Git Revision

Some semantic diff tools accept a Git revision for one side of the comparison. With `oasdiff`, for instance:

~~~bash
oasdiff breaking origin/main:api/openapi.yaml build/openapi.yaml
~~~

This is convenient in CI because the baseline comes from the target branch while the revision builds from the current commit. Ensure the file on `origin/main` is a reviewed snapshot rather than an ad-hoc generated file.

When multiple OpenAPI files represent separate APIs, use multi-file diff modes. When a single API splits across multiple referencing files, choose the proper compose/resolve mode instead of treating each file as an independent API.

## 14. When Should a Snapshot Baseline Be Updated?

A baseline represents an approved contract. Never update it simply because a build produced a diff.

Update workflow:

1. Generate the new snapshot from an agreed runtime configuration.
2. Run validation and semantic diff.
3. Read every breaking, warning, and non-breaking finding.
4. Confirm edits reflect API intent.
5. Assess impact on consumers, SDKs, gateways, and integration docs.
6. If breaking, plan versioning, migration, or deprecation.
7. Update the baseline in the same code change after review.
8. Record the release/commit producing the snapshot for traceability.

Never accept a new snapshot just to turn CI green. Updating baselines without understanding diffs defeats contract regression detection.

## 15. Versioning and Breaking Change Policies

When an API uses Semantic Versioning:

| Change Type | Typical Version Bump |
|---|---|
| Approved breaking change | Increment major |
| Compatible feature, new operation, or optional field | Increment minor |
| Description or non-contract metadata edit | Increment patch or docs-only update per policy |

This is an API governance convention, not something OpenAPI enforces automatically. `info.version` is document metadata; bumping the version number does not preserve wire compatibility. Conversely, leaving `info.version` unchanged does not make a breaking edit safe.

Some tools include rules enforcing version bumps on breaking changes. Even with such rules, the API team must review compatibility and consumer upgrade paths.

## 16. Semantic Diffs Do Not Replace Runtime Contract Tests

Semantic diffs compare what two documents advertise. They do not send requests to servers or prove implementations honor OpenAPI.

Examples:

- Documentation types `quantity` as integer while the controller returns a string.
- OpenAPI declares `404` while runtime always returns `200` with an error body.
- Docs require bearer tokens while a route is configured `permitAll`.
- The server rejects a schema-valid request due to a business rule or bug.
- An endpoint exists at runtime yet was omitted from documentation.

Combine verification layers:

| Check | Question Answered |
|---|---|
| OpenAPI validation | Is the document valid per specification rules? |
| Snapshot/semantic diff | Did the contract change compared to the baseline? |
| Provider contract/runtime tests | Does the server handle requests/responses per contract? |
| Consumer-driven contract tests | Does the provider satisfy interactions consumers actually rely on? |
| Integration/security tests | Are auth, authorization, error handling, and middleware accurate? |

OpenAPI semantic diff is a document-level provider contract check. In multi-consumer systems, consumer-driven contract tests supply additional proof for specific interactions each consumer uses.

## 17. Limitations and False Positives to Know

- **Code generation:** changing `operationId` or component names can break generated SDKs even when wire contracts stay identical.
- **Strict deserializers:** adding response fields can break clients configured to reject unknown properties.
- **Gateway policies:** API gateways may validate more strictly than servers, so schema edits affect traffic before reaching controllers.
- **Security:** dropping a security requirement may look client-compatible yet create a security vulnerability.
- **Server URLs:** changing hosts can send consumers to the wrong environment.
- **References:** external `$ref`s or schema compositions can make diff accuracy depend on the tool's resolve and flatten support.
- **Custom extensions:** vendor extensions can drive gateways or generators while being ignored by diff tools unaware of them.
- **Runtime drift:** documents generated from the wrong profile or stale code fail to reflect real endpoints.

When reports warn of incomplete context, inspect source documents, resolve references, and test with real consumers. Never rely blindly on breaking/non-breaking labels alone.

## 18. Example Change Review

Suppose a revision introduces three changes:

1. Added `GET /orders/{id}/events`.
2. Added required property `customerId` to `POST /orders` request.
3. Updated `description` on the `200` response.

Evaluation:

| Change | Expected Classification | Action |
|---|---|---|
| Added `GET /orders/{id}/events` | Additive | Review auth, `operationId`, and responses |
| Added required `customerId` | Breaking | Update clients or design a transition period |
| Updated `description` | Documentation-only | Review prose clarity |

Do not lump all three into a single "has diff" verdict. Semantic diffs focus reviewers on impactful contract changes while full diffs retain prose edits.

## 19. Practical Workflow for API Teams

When modifying controllers or DTOs:

1. Run application tests.
2. Generate OpenAPI from the agreed profile and group.
3. Validate the document.
4. Canonicalize formatting if needed to reduce snapshot noise.
5. Run semantic diff against the released baseline.
6. Classify changes by request, response, security, and generated SDK impact.
7. Run runtime/consumer contract tests for affected operations.
8. Update version and migration guides if needed.
9. Review before updating the baseline.
10. Archive the snapshot and diff report as release artifacts.

Keep snapshots scoped per API group and clearly tagged by release. A baseline lacking clear provenance, profile, or group cannot support reliable comparisons.

## 20. Snapshot and Semantic Diff Checklist

- [ ] Snapshots are generated from a known commit and profile.
- [ ] API group and server URLs match the baseline.
- [ ] Documents are validated before diffing.
- [ ] Format canonicalization is distinguished from semantic comparison.
- [ ] Arrays/fields are not sorted or stripped without semantic awareness.
- [ ] Breaking changes are evaluated separately for request and response directions.
- [ ] Security requirements and server URLs are reviewed explicitly.
- [ ] `operationId`/component names are checked when publishing SDKs.
- [ ] CI diffs revisions against reviewed baselines.
- [ ] `ERR`/`WARN` thresholds follow an explicit policy.
- [ ] Reports are archived for reviewer inspection.
- [ ] Baselines update only after diffs are approved.
- [ ] Runtime/consumer tests cover significant changes.
- [ ] Version bumps and migration plans accompany breaking changes.

## Conclusion

Contract snapshots preserve an approved OpenAPI Description as a baseline. Canonicalization reduces serialization noise, while semantic diffing evaluates changes across paths, methods, parameters, schemas, responses, and security. Plain text diffs cannot establish compatibility, nor should breaking/non-breaking labels be trusted blindly without considering consumers and runtime behavior. In CI, generate docs from a deterministic environment, validate them, run semantic diffs against reviewed baselines, archive reports, and update snapshots only after changes are approved. Pair document checks with provider/consumer contract tests to catch both contract drift and implementation bugs.
