# Distinguishing Build-Exported Contracts from Deployed Application Documentation

Springdoc-openapi can serve the OpenAPI document directly from a running application and can also export the document to a file during a build. Both approaches draw from the same description sources—controllers, models, annotations, and Spring configuration—yet answer two different questions: which contract was verified and released from a controlled build configuration, versus what the endpoint in a deployed environment is exposing right now.

A key point to understand accurately is that Springdoc's export plugin does not independently parse source code at compile time. The plugin starts the Spring Boot application, calls the HTTP endpoint provided by Springdoc, downloads JSON/YAML, and writes it to a file. Because the document is built from the running application context, the profile, properties, beans, groups, customizers, locale, and request headers of that run can all affect the result.

This lesson builds a reproducible OpenAPI export workflow in Maven or Gradle, manages artifacts per release, and compares those artifacts against the deployed application's documentation to detect configuration drift.

## Objectives

After this lesson, you can:

- Distinguish a runtime OpenAPI endpoint from a contract file generated during the build.
- Explain why "build-time export" still launches the application and makes HTTP calls.
- Configure `springdoc-openapi-maven-plugin` and `springdoc-openapi-gradle-plugin`.
- Choose profiles, ports, headers, output paths, and groups for an export run.
- Export JSON or YAML for the default document and each `GroupedOpenApi`.
- Package OpenAPI files as versioned artifacts.
- Verify reproducibility and identify why two export runs differ.
- Compare build artifacts against `/v3/api-docs` on staging/production.
- Distinguish contract changes from deployment-environment differences.
- Integrate export, validation, semantic diff, and runtime verification into CI/CD.

## 1. Two forms of documentation to manage

Springdoc typically generates the OpenAPI document from the Spring application context. You can fetch the document over HTTP while the application is running or download it inside a build task and save it as a file.

### 1.1. Runtime documentation

This is the document served by an active application. Under the default configuration:

~~~text
GET /v3/api-docs
GET /v3/api-docs.yaml
~~~

If groups exist, each group has its own URL:

~~~text
GET /v3/api-docs/public
GET /v3/api-docs/admin
~~~

Runtime documentation reflects the application context and configuration that specific instance is using. For example, a staging instance runs the `staging` profile while a production instance runs the `prod` profile; if the two profiles create different beans or `GroupedOpenApi` beans, the documents may differ.

### 1.2. Artifact exported during the build

The build plugin starts the application using the configuration specified for the task, downloads the OpenAPI document over HTTP, and writes it to the build directory, for example:

~~~text
target/openapi/openapi.json
build/openapi.json
~~~

This file can be:

- Stored alongside build output for inspection.
- Fed into a semantic diff against the previous release.
- Attached as a Maven artifact or stored in an artifact repository.
- Supplied to SDK generators, API portals, or consumer test suites.
- Published as a contract snapshot linked to the commit and application version.

A build artifact is evidence of the document generated by the application instance inside the build. It does not by itself prove that every deployed instance is serving that exact same document.

## 2. How does "build-time export" actually work?

The Springdoc FAQ refers to exporting JSON/YAML during the build as fetching documentation at "compile time". Technically, the export plugin works by running the application and calling the OpenAPI endpoint:

~~~text
Compile / package application
          |
          v
Start Spring Boot application
with a controlled profile and properties
          |
          v
Wait for the application to become ready
          |
          v
GET /v3/api-docs (or a group URL)
          |
          v
Write JSON/YAML to the build directory
          |
          v
Validate and compare the contract
          |
          v
Stop the application
          |
          v
Publish the OpenAPI artifact
~~~

Therefore, the plugin does not merely read annotations at compile time and synthesize the document in an isolated process. Springdoc still generates the document from the application context of the instance launched by the build task. Beans, profiles, properties, customizers, and runtime dependencies can all influence the result.

This is useful because the exported file goes through the exact same documentation-generation mechanism the application uses at runtime. It also means export configuration must be controlled to avoid generating a contract from a profile different from the intended release configuration.

## 3. Factors that make build and runtime documentation differ

| Factor | Impact on OpenAPI document |
|---|---|
| Spring profile | May enable/disable controllers, beans, customizers, or groups |
| Environment properties | Changes `Info`, `servers`, path filters, media types, or docs endpoints |
| `@ConditionalOnProperty` / `@Profile` | Changes which beans participate in the application context |
| `GroupedOpenApi` | Changes the set of paths and operations in each document |
| `OpenAPI` beans/customizers | Changes metadata, security, server URLs, schemas, or operations |
| Request headers | May affect locale, forwarded host/port, or authentication |
| Reverse proxy | May cause inferred server URLs to differ |
| Cache | Document is computed once and reused under default configuration |
| Springdoc/library version | May change how schemas and operations are inferred |
| API docs enabled/security | May render export or runtime endpoints unreachable |

For instance, the build profile may disable connections to a real database so the application can start in CI. That is appropriate if controllers and contracts stay unchanged. If the build profile accidentally drops a controller or a `GroupedOpenApi`, the exported file will not represent the released contract.

Do not use two different profiles without justification and cross-checking tests. If staging/production need different `servers` settings, decide clearly which parts belong to the shared contract and which parts are deployment metadata.

## 4. Configuring runtime documentation endpoints

Core properties:

~~~yaml
springdoc:
  api-docs:
    path: /v3/api-docs
    enabled: true
  writer-with-default-pretty-printer: true
~~~

`springdoc.api-docs.path` changes the JSON endpoint path. `springdoc.api-docs.enabled=false` disables the application's OpenAPI endpoint. If the endpoint is disabled in the production profile, the build plugin can still export an artifact under the `openapi` profile, yet you cannot download the document from production via that endpoint.

Springdoc also supports YAML via the `.yaml` suffix:

~~~text
/v3/api-docs.yaml
~~~

For multiple documents, declare groups with `GroupedOpenApi` or `springdoc.group-configs`. Group names must stay stable because they become part of export URLs and artifact names:

~~~yaml
springdoc:
  group-configs:
    - group: public
      display-name: Public API
      paths-to-match:
        - /api/public/**
    - group: admin
      display-name: Admin API
      paths-to-match:
        - /api/admin/**
~~~

The corresponding documents reside by default at `/v3/api-docs/public` and `/v3/api-docs/admin`.

## 5. Choosing a dedicated profile for export

You can create an `openapi` profile to start the application during the build:

~~~yaml
# application-openapi.yml
spring:
  datasource:
    url: jdbc:h2:mem:openapi

springdoc:
  api-docs:
    enabled: true
~~~

This profile can use a test database, mock services, or replacement dependencies so the application starts in CI. However, do not exclude controllers or alter paths, response schemas, or security metadata merely to make exporting easier.

A helpful rule:

- You may replace external infrastructure if it does not alter the contract.
- Do not change the endpoint set, methods, request/response schemas, or operation metadata relative to release configuration.
- If the contract depends on profiles, export and validate each profile as separate artifacts.
- Record the exact profile and properties used in build metadata or the CI artifact record.

If server URLs vary by environment, use explicit server configuration or controlled forwarded headers. Do not let an internal CI hostname accidentally become the server URL in the published file.

## 6. Exporting OpenAPI with Maven

`springdoc-openapi-maven-plugin` works alongside `spring-boot-maven-plugin`. The Spring Boot Maven plugin starts the application in the `pre-integration-test` phase; the Springdoc plugin calls the endpoint and writes the file in the `integration-test` phase; the application is stopped in the `post-integration-test` phase.

Example configuration in `pom.xml`:

~~~xml
<properties>
    <springdoc.maven-plugin.version>PLUGIN_VERSION</springdoc.maven-plugin.version>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
            <configuration>
                <jvmArguments>
                    -Dspring.application.admin.enabled=true
                </jvmArguments>
                <arguments>
                    <argument>--spring.profiles.active=openapi</argument>
                </arguments>
            </configuration>
            <executions>
                <execution>
                    <id>start-openapi-application</id>
                    <phase>pre-integration-test</phase>
                    <goals>
                        <goal>start</goal>
                    </goals>
                </execution>
                <execution>
                    <id>stop-openapi-application</id>
                    <phase>post-integration-test</phase>
                    <goals>
                        <goal>stop</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>

        <plugin>
            <groupId>org.springdoc</groupId>
            <artifactId>springdoc-openapi-maven-plugin</artifactId>
            <version>${springdoc.maven-plugin.version}</version>
            <executions>
                <execution>
                    <id>export-openapi</id>
                    <phase>integration-test</phase>
                    <goals>
                        <goal>generate</goal>
                    </goals>
                </execution>
            </executions>
            <configuration>
                <apiDocsUrl>
                    http://localhost:8080/v3/api-docs
                </apiDocsUrl>
                <outputDir>
                    ${project.build.directory}/openapi
                </outputDir>
                <outputFileName>openapi.json</outputFileName>
                <attachArtifact>true</attachArtifact>
                <attachArtifactClassifier>openapi</attachArtifactClassifier>
                <failOnError>true</failOnError>
                <timeout>60</timeout>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

Replace `PLUGIN_VERSION` with the plugin version managed in your project. The example uses a placeholder to avoid pinning an outdated plugin version into a project with different Spring Boot/Springdoc versions.

Run:

~~~bash
./mvnw verify
~~~

The default file in the example is written at:

~~~text
target/openapi/openapi.json
~~~

`attachArtifact=true` attaches the file to the Maven artifact with the `openapi` classifier so it can be installed/deployed alongside the binary. If you only need it internally in CI, leave `attachArtifact=false` and upload the file as a separate build artifact.

### 6.1. Common Maven parameters

| Parameter | Meaning |
|---|---|
| `apiDocsUrl` | JSON/YAML URL to fetch |
| `outputDir` | Directory to write the file |
| `outputFileName` | Filename |
| `attachArtifact` | Attaches the OpenAPI file to the Maven artifact |
| `attachArtifactClassifier` | Classifier of the attached file |
| `headers` | HTTP headers sent to the endpoint, e.g., Authorization |
| `timeout` | Connect/read timeout |
| `skip` | Skips the export goal |
| `failOnError` | Fails the build if downloading/writing the document fails |

The plugin defaults to `failOnError=false`. In CI, set `true`; otherwise the job may continue even if the file was not created. Never use `skip=true` in a contract release job.

### 6.2. Sending authentication headers safely

If the documentation endpoint requires authentication, the plugin supports sending headers:

~~~xml
<headers>
    <Authorization>Bearer ${env.OPENAPI_EXPORT_TOKEN}</Authorization>
</headers>
~~~

Never put real tokens in `pom.xml`, committed YAML files, or CI logs. Supply tokens from the CI secret store and grant the export job read access only to the documentation it needs.

### 6.3. Exporting YAML

Change the URL and filename:

~~~xml
<apiDocsUrl>
    http://localhost:8080/v3/api-docs.yaml
</apiDocsUrl>
<outputFileName>openapi.yaml</outputFileName>
~~~

Content is saved in the format returned by the endpoint. If you want readable JSON, enable `springdoc.writer-with-default-pretty-printer=true` in the export profile.

### 6.4. Exporting multiple groups

Each group needs an execution with its own URL and filename:

~~~xml
<executions>
    <execution>
        <id>export-public-api</id>
        <phase>integration-test</phase>
        <goals>
            <goal>generate</goal>
        </goals>
        <configuration>
            <apiDocsUrl>
                http://localhost:8080/v3/api-docs/public
            </apiDocsUrl>
            <outputFileName>openapi-public.json</outputFileName>
            <attachArtifact>true</attachArtifact>
            <attachArtifactClassifier>openapi-public</attachArtifactClassifier>
            <failOnError>true</failOnError>
        </configuration>
    </execution>
    <execution>
        <id>export-admin-api</id>
        <phase>integration-test</phase>
        <goals>
            <goal>generate</goal>
        </goals>
        <configuration>
            <apiDocsUrl>
                http://localhost:8080/v3/api-docs/admin
            </apiDocsUrl>
            <outputFileName>openapi-admin.json</outputFileName>
            <attachArtifact>true</attachArtifact>
            <attachArtifactClassifier>openapi-admin</attachArtifactClassifier>
            <failOnError>true</failOnError>
        </configuration>
    </execution>
</executions>
~~~

If the project uses multiple groups, verify all groups in CI. Exporting the default `/v3/api-docs` alone does not prove the public/admin groups are built properly.

## 7. Exporting OpenAPI with Gradle

Springdoc provides the `org.springdoc.openapi-gradle-plugin` plugin. The plugin requires the application to include the Spring Boot plugin and a Springdoc API dependency so the documentation endpoint is served.

Kotlin DSL example:

~~~kotlin
plugins {
    java
    id("org.springframework.boot") version libs.versions.springBoot.get()
    id("org.springdoc.openapi-gradle-plugin")
}

openApi {
    apiDocsUrl.set("http://localhost:8080/v3/api-docs")
    outputDir.set(layout.buildDirectory.dir("openapi"))
    outputFileName.set("openapi.json")
    waitTimeInSeconds.set(60)

    customBootRun {
        args.set(listOf("--spring.profiles.active=openapi"))
    }
}
~~~

Declare the plugin version in `pluginManagement` or the version catalog per project standards. The plugin provides the task:

~~~bash
./gradlew generateOpenApiDocs
~~~

The default file is written to `build/openapi.json`; the example above changes it to `build/openapi/openapi.json`.

The Gradle plugin launches the application using `bootRun` configuration, downloads the OpenAPI document, and stops the application. `customBootRun` lets you set custom profiles, JVM arguments, system properties, or environment variables for the export run.

### 7.1. Exporting groups with Gradle

`groupedApiMappings` maps each group's URL to a filename:

~~~kotlin
openApi {
    groupedApiMappings.set(
        mapOf(
            "http://localhost:8080/v3/api-docs/public" to
                "openapi-public.json",
            "http://localhost:8080/v3/api-docs/admin" to
                "openapi-admin.json"
        )
    )
}
~~~

When `groupedApiMappings` is configured, single `apiDocsUrl` and `outputFileName` are ignored. Inspect each output file after the task runs.

### 7.2. Exporting YAML and headers

~~~kotlin
openApi {
    apiDocsUrl.set("http://localhost:8080/v3/api-docs.yaml")
    outputDir.set(layout.buildDirectory.dir("openapi"))
    outputFileName.set("openapi.yaml")
    requestHeaders.set(
        mapOf(
            "x-forwarded-host" to "api.example.test",
            "x-forwarded-proto" to "https"
        )
    )
}
~~~

Do not send forwarded headers arbitrarily. Only use them when simulating an exact reverse proxy trusted by the application, and ensure Spring Boot's forwarded-header strategy is configured appropriately.

### 7.3. Build plugin version compatibility

The build plugin only calls an HTTP endpoint, yet the launched application must still use a compatible Spring Boot/Springdoc pair. The current compatibility matrix for Springdoc plugins states:

| Spring Boot | Springdoc |
|---|---|
| 4.x | 3.x |
| 3.x | 2.x |
| 2.x and 1.x | 1.x |

The Maven/Gradle build plugin version is a separate dependency, not the version of the Springdoc runtime starter. Manage and pin both versions. The Maven plugin documentation notes requirements of Maven 3.6.3+ and Java 8+; the Gradle plugin requires Gradle 8.0+ and needs the Spring Boot plugin along with the Java/Kotlin plugin in the build.

## 8. Keeping the export profile close to release configuration

An export profile can swap databases or external integrations so the build does not depend on live services:

~~~yaml
# application-openapi.yml
spring:
  datasource:
    url: jdbc:h2:mem:openapi

springdoc:
  api-docs:
    enabled: true
~~~

There is no need to create a new profile if the default profile already suffices for startup. If a dedicated profile exists, document clearly:

- Which profile is activated during export.
- Which environment variables affect `OpenAPI` beans or customizers.
- Which `@ConditionalOnProperty` and `@Profile` annotations alter controllers/groups.
- Which external services are replaced with mocks.
- Which server URLs are placed into the document.

If API groups, controllers, or OpenAPI configuration depend on profiles, export and validate each profile as separate artifacts. A profile disabling external services can be safe; a profile dropping endpoints or altering schemas produces a different contract.

Do not alter responses or hide operations solely so the build avoids starting an auxiliary system. Replace infrastructure dependencies at the service layer with mock/test adapters while preserving the controller contract intact.

## 9. Managing server URLs, proxies, and caching

OpenAPI `servers` describes the base URLs clients use to call the API. Springdoc can infer server URLs from the current request; if explicit server annotations/configuration exist, declared values are used.

In environments behind a reverse proxy, internal requests may see a different host/port than the public URL. In that case:

- Configure forwarded headers properly in Spring Boot/proxy.
- Trust forwarded headers only from trusted proxies.
- You can send `x-forwarded-host`, `x-forwarded-port`, or `x-forwarded-proto` during export if the plugin needs to simulate a post-proxy request.
- Verify `servers` in both the exported file and the runtime document.

Springdoc caches the OpenAPI document by default. If server URLs must be recomputed per request—such as when the same application is served behind multiple proxies—you can configure:

~~~yaml
springdoc:
  cache:
    disabled: true
~~~

The corresponding property is `springdoc.cache.disabled=true`. Disable caching only when you genuinely need the document to vary per request. If the contract does not depend on request hosts, an explicit `servers` URL generally keeps build artifacts more stable.

Locale can also affect description content. If the application uses `Accept-Language` to produce multilingual documentation, choose an explicit locale for export and record that locale in artifact metadata. Do not let the runner's default locale dictate contract content.

## 10. Making artifacts reproducible

Two exports from the same commit should produce contract-equivalent documents. To achieve that:

1. Pin versions of Spring Boot, Springdoc, Maven/Gradle plugins, and schema-management dependencies.
2. Use the exact same export profile and property set.
3. Keep `GroupedOpenApi`, package/path filters, and customizers stable.
4. Declare `info.version` from a single build version source.
5. Use explicit server URLs if hostnames are not part of the artifact.
6. Control locale and `Accept-Language` if descriptions use i18n.
7. Stabilize output ordering when diff reviews are needed; Springdoc has `springdoc.writer-with-order-by-keys`.
8. Never put timestamps or random data into descriptions, extensions, or schemas.
9. Record commit SHA, application version, profile, and build number externally or alongside artifact metadata.

Pretty-printing helps file review, while deterministic key ordering reduces diffs from property ordering. Neither replaces semantic diffing: changes to a schema, path, security requirement, or server URL still require review.

If the Gradle build plugin marks the task up-to-date, it may skip restarting the application when classpath, application settings, and export configuration are unchanged. Ensure environment properties affecting the document are declared as task inputs or deliberately re-run the task when those values change.

## 11. Checking the artifact after export

Do not treat the mere appearance of a file as sole proof. After export, you must:

- Confirm the file is non-empty and in valid JSON/YAML format.
- Parse the document with an OpenAPI parser or validator.
- Lint project rules for naming, operationId, tags, security, and schemas.
- Inspect `openapi`, `info`, `servers`, `paths`, and `components`.
- Verify all group files were created.
- Compare against the previous release's baseline with a semantic diff.
- Fail the build on fetch errors, parse errors, lint errors, or unapproved breaking changes.

Example quick JSON check:

~~~bash
test -s target/openapi/openapi.json
jq -e '.openapi and .info.title and (.paths | type == "object")' \
  target/openapi/openapi.json
~~~

The `jq` command here only checks foundational fields. It does not replace an OpenAPI validator because it does not fully verify references, schemas, and specification rules.

## 12. Comparing against the deployed application's document

Once the application is deployed, you can retrieve the runtime document if the endpoint is enabled and the caller has permission:

~~~bash
curl --fail --silent --show-error \
  https://staging.example.com/v3/api-docs \
  -o deployed-openapi.json
~~~

If using groups:

~~~bash
curl --fail --silent --show-error \
  https://staging.example.com/v3/api-docs/public \
  -o deployed-openapi-public.json
~~~

If the endpoint requires authentication, use credentials supplied through the CI secret store. Never save bearer tokens in command history, committed files, or artifacts.

Cross-check the build artifact against the runtime document across these areas:

| Area to compare | What to verify |
|---|---|
| `paths` and HTTP methods | No unexpected missing or added operations |
| `operationId` | Stable and unique IDs |
| Parameters/request body | Names, required flags, schemas, and content types match |
| Responses | Status codes, headers, media types, and schemas match |
| `components.schemas` | No missing components or unintended constraint changes |
| `security` | Authentication requirements match |
| `servers` | Base URLs fit the environment |
| Group documents | Public/admin operation sets match group purpose |

Do not diff files as plain text and conclude every difference is contract drift. Key ordering or pretty-printing can differ without altering meaning. Use an OpenAPI-aware semantic diff, then review meaningful changes.

### 12.1. Classifying differences

Some differences belong strictly to deployment metadata:

- Hostname or port in `servers`.
- Context paths added by ingress/gateway.
- Distinct public and internal URLs.

Some differences directly affect the contract:

- Added or removed paths or HTTP methods.
- Changed request parameters, required flags, or schemas.
- Changed response codes or response schemas.
- Removed or altered security requirements.
- Changed `operationId` or tags, which can impact SDKs and API portals.

Do not blindly ignore every difference in `servers`. If the build file is published to an SDK generator, the server URL may also be baked into the client; clearly decide which servers belong to the artifact and which are configured at deployment time.

## 13. When production does not expose /v3/api-docs

Some applications disable documentation endpoints in production with:

~~~yaml
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
~~~

This is a valid deployment choice when contract artifacts are already distributed via an API portal or artifact repository. However, when the runtime endpoint is disabled, the pipeline cannot use it to prove the deployed document matches the build artifact.

In that case:

- Store the OpenAPI artifact linked to the exact deployed image/tag/commit.
- Check the image digest or release metadata to know which binary the instance runs.
- Run smoke tests against critical operations.
- Verify the contract in staging before promoting.
- If live document inspection is needed, expose the endpoint in staging or a secured admin channel, not necessarily publicly in production.

The build artifact shows how the application is described under the export configuration. Runtime smoke tests confirm the deployed application behaves accordingly. These two pieces of evidence complement each other.

## 14. CI pipeline for OpenAPI artifacts

A reference pipeline:

~~~text
Checkout exact commit
        |
        v
Resolve pinned dependencies
        |
        v
Compile and package application
        |
        v
Start application with openapi profile
        |
        v
Fetch default and grouped OpenAPI documents
        |
        v
Stop the build application
        |
        v
Parse and lint each document
        |
        v
Semantic diff against released baseline
        |
        v
Review breaking / security-sensitive changes
        |
        v
Attach or publish versioned OpenAPI artifacts
        |
        v
Deploy same application image to staging
        |
        v
Fetch runtime docs or run runtime smoke tests
        |
        v
Compare runtime and build contract
~~~

In CI:

- Enable `failOnError=true` for the Maven plugin.
- Do not skip the export task in a contract-release job.
- Store the OpenAPI file as a versioned artifact linked to the commit.
- Verify all groups, not just the default document.
- Run a semantic diff before publishing SDKs or API portals.
- Do not promote if staging has unexplained drift.

The Maven plugin notes that when a build fails before the stop phase, the application may remain running. Runners must be cleaned up or processes stopped before the next build so export requests do not hit a stale instance. The Gradle plugin likewise needs a free port and the application must start successfully before timeout.

## 15. Common mistakes

| Symptom | Possible cause | Resolution |
|---|---|---|
| Build passes yet no file exists | `failOnError=false`, goal skipped, or endpoint unreachable | Enable fail-on-error and inspect logs/tasks |
| File misses controllers | Export profile does not create those beans/controllers | Compare profiles and conditions against release config |
| Exported stale old document | An old process occupies the port | Stop process, use dedicated port, and verify startup logs |
| Maven does not stop app after error | `post-integration-test` phase skipped on build failure | Clean up processes in CI before the next job |
| Gradle waits too long | Wrong port/path or app not ready | Check `apiDocsUrl`, increase `waitTimeInSeconds` when needed |
| Group file does not appear | Wrong group name or URL | Check `/v3/api-docs/{group}` and group config |
| Runtime `servers` differs from build | Proxy/forwarded headers or server annotations differ | Standardize `servers` or configure proxy headers |
| Schemas differ across environments | Dependency versions or profile/customizers differ | Pin dependencies and check conditions/properties |
| Production docs unreachable | `springdoc.api-docs.enabled=false` or blocked by Security | Use published artifacts and runtime smoke tests |
| Huge file diff despite unchanged API | JSON key order, formatter, or locale differs | Standardize output and use semantic diffs |
| CI cannot fetch protected endpoint | Missing Authorization header or expired token | Supply secret and pass via plugin header config |
| Artifact contains localhost URL | Exported from server URL inferred during build | Declare proper `servers` or handle server metadata per environment |

## 16. Comprehensive hands-on exercise

Set up a Spring Boot project with public and admin APIs:

1. Create two `GroupedOpenApi` beans named `public` and `admin`.
2. Verify the runtime endpoints `/v3/api-docs/public` and `/v3/api-docs/admin`.
3. Configure the `openapi` profile so the application starts in CI without needing real external services.
4. Use the Maven plugin or Gradle plugin to export both documents into two files.
5. Enable fail-on-error and verify files are non-empty.
6. Parse/lint both files.
7. Store artifacts alongside commit SHA, application version, and profile.
8. Make an intentional change to an `operationId` or response schema to observe the semantic diff.
9. Deploy the exact built image to staging.
10. Fetch the runtime document if the endpoint is permitted.
11. Compare paths, methods, operationIds, schemas, security, and servers.
12. Disable docs endpoints in the production profile, confirm the build artifact still publishes and API smoke tests still run.
13. Trigger a failing export build to verify CI catches the failure and cleans up processes.

### Completion criteria

- [ ] Distinguished runtime OpenAPI documents from build-exported artifacts.
- [ ] Explained how the build plugin launches the application and calls an HTTP endpoint.
- [ ] Exported JSON and YAML using Maven or Gradle.
- [ ] Exported each `GroupedOpenApi` into its own file.
- [ ] Export profile causes no unintended contract changes.
- [ ] Files are parsed/linted and semantically diffed against the baseline.
- [ ] Artifacts include version, commit, and export configuration info.
- [ ] CI fails if documents cannot be downloaded or written.
- [ ] Know how to handle port conflicts and lingering processes after failed builds.
- [ ] Compared build artifacts against runtime documents on staging.
- [ ] Established a workflow when production disables `/v3/api-docs`.
- [ ] Never publish SDKs or API portals from an unreviewed artifact.

## Next steps

After this lesson, combine artifact export with contract testing, backward compatibility, and documentation distribution. An OpenAPI file is only valuable when you know which commit, dependencies, profile, and group produced it; cross-checking it against deployed applications catches misconfiguration or contract drift early before clients hit errors.
