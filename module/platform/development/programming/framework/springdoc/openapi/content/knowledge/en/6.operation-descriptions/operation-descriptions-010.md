# Hiding a Documentation Detail vs. Disabling the Actual Endpoint

In a Spring Boot application, there are times when you want to hide an internal endpoint from Swagger UI, omit a technical parameter from the documentation, or exclude a property from an OpenAPI schema. springdoc-openapi supports these actions so documentation fits its target audience. However, **hiding information from the OpenAPI specification does not change how Spring registers and handles the endpoint**.

A controller marked hidden can still receive HTTP requests. A property hidden in the schema can still appear in the actual JSON. A path excluded from documentation can still be called directly if the application permits it. To restrict access or stop serving an endpoint, configure security or bean/route lifecycle at the application layer.

This lesson explains how to hide operations, parameters, and schemas using annotations or springdoc-openapi configuration, while clearly distinguishing documentation operations from security and disabling endpoints in Spring Boot.

## Objectives

After this lesson, you will be able to:

- Distinguish hiding OpenAPI content from blocking access or disabling endpoint registration.
- Use `@Hidden` and `@Operation(hidden = true)` to hide an operation or controller from documentation.
- Hide parameters or schema properties and understand the impact of that choice on integrators.
- Filter paths or packages from the default document and individual API groups.
- Disable OpenAPI JSON/YAML or Swagger UI per environment.
- Use Spring Security, profiles, or configuration conditions to protect or disable actual endpoints.
- Write tests verifying both generated documentation and HTTP behavior.

## 1. Three Behavioral Layers to Distinguish

When saying an API is "not visible", identify precisely which layer is being changed:

| Layer | Change | Example | Direct HTTP Request |
|---|---|---|---|
| Documentation | Does not emit an operation, parameter, or schema into OpenAPI | `@Hidden`, `@Parameter(hidden = true)` | May still work |
| Access | Application rejects callers who do not meet policy | Spring Security requiring a role or scope | Route still exists; requests may receive 401/403 |
| Endpoint registration | Controller/handler is not registered or mapping is removed | `@ConditionalOnProperty`, profiles, removing mapping | Usually no handler remains and may receive 404/405 |

These three layers can be combined. For example, an admin endpoint can be hidden from public docs, restricted to users with the ADMIN role, and registered only in a specific environment. Each layer serves a distinct purpose and must be configured and tested separately.

Remember: Swagger UI is a viewer for the specification. It is neither an access control gateway for controllers nor the source of truth for which routes are active.

## 2. Hiding an Entire Controller with @Hidden

The `@Hidden` annotation from Swagger Annotations can be placed on a controller so springdoc-openapi excludes that controller's operations from the generated document:

~~~java
import io.swagger.v3.oas.annotations.Hidden;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@Hidden
@RestController
@RequestMapping("/internal/diagnostics")
public class DiagnosticsController {

    @GetMapping
    public DiagnosticStatus status() {
        return diagnosticsService.currentStatus();
    }
}
~~~

In the OpenAPI document, this controller's group of operations will not be added to the path list generated by springdoc. Even so, Spring still detects the controller bean, registers the mapping, and invokes the method when a matching request arrives. Without another protection mechanism, anyone who knows the URL can still call the endpoint.

`@Hidden` is appropriate when a controller serves internal use, operational tooling, or an API not meant for public documentation readers. Before hiding, determine whether the endpoint truly needs to exist in the running environment. If an endpoint should not operate in production, add registration conditions or appropriate safeguards.

## 3. Hiding One Operation with @Hidden or @Operation

If only one method in a controller needs to be hidden, place `@Hidden` on that method:

~~~java
import io.swagger.v3.oas.annotations.Hidden;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ProductController {

    @GetMapping("/api/products")
    public List<ProductResponse> list() {
        return productService.findAll();
    }

    @Hidden
    @GetMapping("/internal/products/reindex")
    public ReindexResult reindex() {
        return productService.reindexSearchIndex();
    }
}
~~~

You can also use the `hidden` attribute of `@Operation`:

~~~java
import io.swagger.v3.oas.annotations.Operation;

@Operation(
    summary = "Rebuild search index",
    hidden = true
)
@PostMapping("/internal/products/reindex")
public ReindexResult reindex() {
    return productService.reindexSearchIndex();
}
~~~

Both approaches achieve the same goal: omitting that operation from the OpenAPI specification. Choose one approach consistently in the project. `@Hidden` is a general annotation usable on classes or methods; `@Operation(hidden = true)` places the hiding intent directly in the operation description.

Do not rely on hiding an operation to conceal a sensitive API assuming outsiders cannot call it. URLs can be discovered from logs, old client code, access history, proxies, earlier docs, or route probing. Access permissions must still be enforced on the server.

## 4. Hiding a Parameter from Documentation

`@Parameter(hidden = true)` excludes a parameter from the OpenAPI description:

~~~java
import io.swagger.v3.oas.annotations.Parameter;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InternalReportController {

    @GetMapping("/internal/reports")
    public ReportResponse getReport(
        @Parameter(hidden = true)
        @RequestHeader("X-Internal-Context") String internalContext
    ) {
        return reportService.getReport(internalContext);
    }
}
~~~

Spring still binds the `X-Internal-Context` header to the method parameter. The hidden annotation only controls how the parameter is described in documentation. If the server still requires that header, clients must learn how to send it via another contract or controlled internal docs. If the header carries authentication credentials, consider modeling it as a security scheme rather than treating it as a normal business parameter.

Hiding a required parameter from public documentation can prevent integrators from calling the API successfully. Only do this when the parameter is genuinely an implementation detail supplied through another channel, or when the endpoint is not intended for that documentation audience. For public APIs, document all parameters clients must supply.

### Distinguishing hidden parameters from security schemes

Do not hide the Authorization header and force clients to guess how to authenticate. Declare `securitySchemes` and `security` so Swagger UI and client generators know the endpoint requires a bearer token, API key, or OAuth2. A security scheme describes the authentication mechanism; Spring Security enforces that mechanism.

## 5. Hiding a Property in a Schema

`@Schema(hidden = true)` can exclude a property from the OpenAPI schema:

~~~java
import io.swagger.v3.oas.annotations.media.Schema;

public record ProductResponse(
    Long id,
    String name,

    @Schema(hidden = true)
    String internalSearchKey
) {}
~~~

The `internalSearchKey` property is not described as a normal property in the schema generated by springdoc. However, this OpenAPI annotation does not control Jackson's JSON serialization. If the record is returned directly and Jackson still serializes that property, the data can appear in the real response even though Swagger UI does not display it.

Therefore, before hiding a property, clarify your intent:

- If the property is still sent over HTTP and clients need to know it exists, document it in the schema.
- If the property is internal-only and must not be sent to clients, use an appropriate response DTO or serialization configuration such as `@JsonIgnore` as required.
- If the property is read-only or write-only, consider `@Schema(accessMode = Schema.AccessMode.READ_ONLY)` or `WRITE_ONLY` instead of hiding it completely.

Example of a server-generated field that is read-only for clients:

~~~java
@Schema(accessMode = Schema.AccessMode.READ_ONLY,
        description = "Server-generated identifier")
private Long id;
~~~

`READ_ONLY` indicates the field appears in responses but must not be sent in requests per the contract. `WRITE_ONLY` expresses the reverse direction. These modes clarify schemas when the same DTO or schema is reused in both directions, though separate request and response DTOs remain easier to control.

### @JsonIgnore vs. @Schema(hidden = true)

| Annotation | Primary Effect | Removes the Route? |
|---|---|---|
| `@Schema(hidden = true)` | Hides the property in the OpenAPI specification | No |
| `@JsonIgnore` | Skips the property according to Jackson serialization/deserialization rules | No |
| `@Schema(accessMode = READ_ONLY)` | Describes a property that appears only on the response side | No |
| `@Hidden` on controller/method | Hides the operation in OpenAPI | No |

Do not use documentation-hiding annotations as a data protection measure. If data must not be sent to clients, control DTOs or serialization and test the actual HTTP body.

## 6. Hiding Schemas or Operation Groups from Documentation

Beyond marking individual controllers, methods, or properties, springdoc-openapi can filter packages and paths. This is useful when an internal API group follows dedicated package or URL conventions.

Example exclusion configuration in `application.yml`:

~~~yaml
springdoc:
  packages-to-exclude:
    - com.example.application.internal
  paths-to-exclude:
    - /internal/**
    - /management/**
~~~

Exclusion properties tell springdoc to omit matching controllers or paths from the generated document. They do not remove Spring beans or unregister request mappings. Endpoints can still operate normally.

Include and exclude filters can be combined:

~~~yaml
springdoc:
  packages-to-scan:
    - com.example.application.api
  paths-to-match:
    - /api/**
  paths-to-exclude:
    - /api/internal/**
~~~

When using filters, inspect the specification after startup because scanning scope depends on package structure, actual mappings, and application configuration. Never assume every path absent from OpenAPI has been disabled.

### Filtering specifically for a GroupedOpenApi

If the application splits docs into public and internal groups, you can configure path scopes for each group:

~~~java
import org.springdoc.core.models.GroupedOpenApi;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ApiGroupsConfiguration {

    @Bean
    GroupedOpenApi publicApi() {
        return GroupedOpenApi.builder()
            .group("public")
            .pathsToMatch("/api/**")
            .pathsToExclude("/api/internal/**")
            .build();
    }

    @Bean
    GroupedOpenApi internalApi() {
        return GroupedOpenApi.builder()
            .group("internal")
            .pathsToMatch("/api/internal/**", "/internal/**")
            .build();
    }
}
~~~

Group specifications are usually accessed at `/v3/api-docs/{group}`, such as `/v3/api-docs/public`. If the internal group is meant only for operations teams, protect that group documentation endpoint itself via Spring Security or environment configuration. Naming a group internal or omitting it from a Swagger UI page does not automatically grant privacy.

The package name `org.springdoc.core.models.GroupedOpenApi` applies to modern springdoc versions; projects on another major version may have different imports or configuration APIs. Use the exact API of your project's dependency.

## 7. Hiding All of OpenAPI or Swagger UI

Sometimes you do not want to expose the specification endpoint or Swagger UI in a given environment, such as production. You can configure:

~~~yaml
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
~~~

`springdoc.api-docs.enabled` controls serving the OpenAPI specification endpoint, typically `/v3/api-docs` and related variants. `springdoc.swagger-ui.enabled` controls Swagger UI. When both are disabled, business endpoints in controllers continue operating.

Configuration can be set per profile:

~~~yaml
# application-dev.yml
springdoc:
  api-docs:
    enabled: true
  swagger-ui:
    enabled: true

---
# application-prod.yml
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
~~~

This example shows the per-environment configuration idea; ensure Spring Boot activates the right profile at deployment time. If documentation is still needed for CI systems or an external developer portal, consider generating and storing the OpenAPI artifact during the build pipeline, then disabling public doc endpoints at runtime.

Disabling Swagger UI does not disable OpenAPI JSON. Disabling OpenAPI JSON also does not disable application endpoints. Verify each URL after changing configuration.

## 8. Securing Real Endpoints with Spring Security

If an endpoint must remain active yet only certain users are allowed to call it, use authentication and authorization. Example of Spring Security requiring the ADMIN role for an admin endpoint group:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfiguration {

    @Bean
    SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/internal/**").hasRole("ADMIN")
                .requestMatchers("/api/**").authenticated()
                .anyRequest().permitAll()
            )
            .httpBasic(Customizer.withDefaults())
            .build();
    }
}
~~~

This is an illustrative example for an app using HTTP Basic; JWT or OAuth2 Resource Server systems must configure the corresponding authentication mechanism. When callers are unauthenticated, the server usually returns `401`; when authenticated without sufficient permissions, the server usually returns `403`. Exact behavior also depends on entry points, access denied handlers, and resource-hiding policies of the application.

Securing an endpoint does not automatically hide the operation from OpenAPI. If public documentation should not list admin endpoints, combine `@Hidden` or path filters with Spring Security. If admin docs need to be provided to authorized users, create a separate documentation group and protect that documentation endpoint.

Do not rely solely on CORS, hidden URLs, obscure path names, or omitting endpoints from Swagger UI to protect an API. CORS is primarily a browser policy; it does not replace server-side authentication and authorization.

## 9. Disabling Real Endpoints via Controller Registration Conditions

If an endpoint must not exist in a certain environment, you can prevent the controller from being created as a Spring bean. A flexible approach is `@ConditionalOnProperty`:

~~~java
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/internal/diagnostics")
@ConditionalOnProperty(
    prefix = "features.internal-diagnostics",
    name = "enabled",
    havingValue = "true"
)
public class DiagnosticsController {

    @GetMapping
    public DiagnosticStatus status() {
        return diagnosticsService.currentStatus();
    }
}
~~~

In default configuration:

~~~yaml
features:
  internal-diagnostics:
    enabled: false
~~~

With this configuration, the controller is only registered when the property equals `true`. By default `matchIfMissing` is `false`, so if the property is omitted the controller is also not registered. When the bean does not exist, the corresponding mapping is not created and requests usually receive `404 Not Found` if no other handler matches that URL. When the property is enabled, the route becomes active again and springdoc can discover it, unless the operation is separately hidden.

This mechanism suits tool endpoints intended only for development or operations environments. Control the property via deployment configuration and avoid enabling sensitive diagnostic endpoints accidentally.

### Using @Profile for environment-specific controllers

Another option is registering the controller only when a specific profile is active:

~~~java
import org.springframework.context.annotation.Profile;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@Profile("internal-tools")
@RestController
@RequestMapping("/internal/tools")
public class InternalToolsController {
    // Endpoints only present under the internal-tools profile.
}
~~~

When the `internal-tools` profile is not active, the controller is not created in the application context. Profiles suit cases tied to an environment; `@ConditionalOnProperty` is more flexible when toggling a feature with an independent configuration flag.

## 10. Choosing an Approach Based on Your Goal

| Need | Appropriate Approach | Does the HTTP Endpoint Still Work? |
|---|---|---|
| Hide an operation from OpenAPI | `@Hidden` or `@Operation(hidden = true)` | Yes |
| Hide a parameter from docs | `@Parameter(hidden = true)` | Yes |
| Hide a property from schema | `@Schema(hidden = true)` | Yes; actual JSON does not change from this annotation alone |
| Exclude path/package from docs | `paths-to-exclude`, `packages-to-exclude` | Yes |
| Disable Swagger UI | `springdoc.swagger-ui.enabled=false` | Yes |
| Disable OpenAPI JSON/YAML endpoint | `springdoc.api-docs.enabled=false` | Yes |
| Allow only authorized users | Spring Security | Yes, though unauthorized requests are rejected |
| Do not register controller per config | `@ConditionalOnProperty` or `@Profile` | No mapping exists when the controller is not registered |
| Remove API completely | Remove mapping/controller and deploy new version | No mapping exists after deployment |

Choose the mechanism based on your objective. If you only need cleaner public docs, annotations or springdoc filters usually suffice. If an endpoint performs sensitive actions, protect it with Spring Security. If an endpoint must not exist in production, control controller registration or remove the route.

## 11. Testing to Prove the Difference

A useful test should verify both outcomes simultaneously:

1. The hidden operation does not appear in the OpenAPI specification.
2. The endpoint still returns a response when only documentation hiding is applied and the request satisfies access conditions.

Example with MockMvc:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class HiddenOperationTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void hiddenOperationIsAbsentFromDocsButRouteStillWorks() throws Exception {
        mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.paths['/internal/diagnostics']").doesNotExist());

        mockMvc.perform(get("/internal/diagnostics"))
            .andExpect(status().isOk());
    }
}
~~~

This test assumes the diagnostics endpoint does not require authentication in the test context and returns success. If Spring Security is enabled, configure appropriate users/authorities or use test security support to verify the real policy.

For controllers conditioned by a property, run a context test with the property disabled and verify the mapping does not exist:

~~~java
@SpringBootTest(properties = "features.internal-diagnostics.enabled=false")
@AutoConfigureMockMvc
class DisabledDiagnosticsControllerTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void disabledControllerHasNoRoute() throws Exception {
        mockMvc.perform(get("/internal/diagnostics"))
            .andExpect(status().isNotFound());
    }
}
~~~

In some systems, fallback routes or security filters can produce a status other than `404`; in that case, inspect the application context and mapping registry to confirm the controller was truly not registered. Tests must also run under the same profile/property configuration as the target environment.

### Pre-release checklist

- [ ] Clearly identified whether the goal is hiding documentation, protecting access, or disabling a route.
- [ ] Hidden operations are absent from OpenAPI JSON of the corresponding group.
- [ ] Hidden parameters and schemas do not deprive integrators of required information.
- [ ] Sensitive data does not appear in actual JSON responses.
- [ ] Sensitive endpoints have appropriate Spring Security policies.
- [ ] Environment-specific controllers are properly conditioned.
- [ ] Swagger UI and OpenAPI endpoints are enabled/disabled appropriately per environment.
- [ ] Tests verify both documentation content and HTTP behavior.

## 12. Common Mistakes

| Symptom | Cause | How to Fix |
|---|---|---|
| Used `@Hidden` yet URL can still be called | Annotation only affects OpenAPI | Add Spring Security or stop registering the controller |
| Endpoint disappears from Swagger UI yet remains in another group | Filter applies only to one document/group | Check each `/v3/api-docs/{group}` endpoint |
| Property hidden in schema yet present in JSON | `@Schema(hidden = true)` does not control Jackson | Use an appropriate DTO or configure serialization |
| Required header hidden, causing clients to fail calls | Documentation lacks necessary info | Publish a valid mechanism or redesign the contract |
| Disabled Swagger UI yet `/v3/api-docs` remains accessible | Only UI was disabled | Also disable `springdoc.api-docs.enabled` if needed |
| Disabled OpenAPI yet controller still works | Business endpoints are independent of doc endpoints | Expected behavior; use security or bean conditions if needed |
| Controller enabled unintentionally | Wrong deployment property or profile | Inspect effective configuration and test startup |

An important rule: never confirm an endpoint is disabled just by looking at Swagger UI. Send an HTTP request or inspect mappings in the application context.

## 13. Practice Exercise

Create a controller with two operations: a public endpoint to list products and an internal endpoint to trigger search index rebuilding. Perform the following:

1. Use `@Hidden` to hide the internal controller or operation from OpenAPI.
2. Verify the public operation still appears in `/v3/api-docs`.
3. Call the internal URL directly to prove the route still works when only documentation is hidden.
4. Add Spring Security so only ADMIN can call the internal endpoint.
5. Verify unauthenticated and unauthorized requests receive appropriate status codes.
6. Switch the internal controller to `@ConditionalOnProperty` and disable the property in production config.
7. Start the application with the property disabled and verify the internal mapping no longer exists.
8. Use `@Parameter(hidden = true)` for a technical parameter and evaluate whether clients still have enough info to call the API.
9. Use `@Schema(hidden = true)` for a test property; compare the OpenAPI schema with the actual JSON.
10. Choose a proper DTO or Jackson annotation if the property must not appear in responses.
