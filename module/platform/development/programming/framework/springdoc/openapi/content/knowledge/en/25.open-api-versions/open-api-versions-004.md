# `nullable` in 3.0 and Representing the `null` Type in 3.1

When describing a JSON property that can accept a `null` value, OpenAPI 3.0 and OpenAPI 3.1 use two different representations. OpenAPI 3.0 adds the **nullable: true** keyword to the Schema Object. OpenAPI 3.1 is based on JSON Schema 2020-12 and therefore represents `null` as a data type in a union type, such as **type: [string, "null"]**, or as an **anyOf** branch.

This difference directly affects schemas generated by springdoc, Swagger UI, validators, code generators, and OpenAPI-reading clients. When upgrading a document from 3.0 to 3.1, you must convert `nullable` schemas rather than simply changing the version number at the top of the file.

## 1. Distinguishing null, omitted properties, and empty values

In JSON, the following three states are not the same:

~~~json
{
  "nickname": null
}
~~~

~~~json
{}
~~~

~~~json
{
  "nickname": ""
}
~~~

- **null:** the property is present and its value is `null`.
- **Omitted:** the object does not contain that property.
- **Empty string:** the property is present and its value is a string of length 0.

An API can assign different business meanings to each state. For example, in a profile update request:

| Payload sent | Possible meaning |
| --- | --- |
| `nickname` omitted | Keep the current nickname |
| `nickname: null` | Clear the nickname |
| `nickname: ""` | Set the nickname to an empty string, or reject via validation |
| `nickname: "An"` | Change the nickname to An |

The schema must accurately reflect the API contract. If the server distinguishes an omitted property from one explicitly sent as `null`, the document must preserve that distinction.

## 2. `nullable` and `required` answer two different questions

A Schema Object can answer two independent questions:

1. Is the property's value allowed to be `null`?
2. Is the property required to appear in the object?

**nullable** in OpenAPI 3.0 or a union with the `null` type in OpenAPI 3.1 answers the first question. The object's **required** array answers the second question.

| Required | Allows null | Meaning |
| --- | --- | --- |
| No | No | Property can be omitted; if present, it must have a value of the right type |
| No | Yes | Property can be omitted or sent as `null` |
| Yes | No | Property must be present and its value cannot be `null` |
| Yes | Yes | Property must be present, but its value can be `null` |

For example, `nickname` is required to be present, yet allowed to be `null`:

~~~json
{
  "nickname": null
}
~~~

If the schema does not include `nickname` in `required`, clients can omit that property. Do not use **nullable: true** as a substitute for removing a property from the `required` list; the two concepts are not equivalent.

## 3. Representing `nullable` in OpenAPI 3.0

OpenAPI 3.0 does not support `null` as a valid value for the `type` keyword. Instead, the Schema Object has a separate `nullable` field.

Example of a `nickname` property that is a string or `null`:

~~~yaml
openapi: 3.0.3
components:
  schemas:
    Customer:
      type: object
      properties:
        nickname:
          type: string
          nullable: true
          maxLength: 80
~~~

The schema above allows:

~~~json
{"nickname": "An"}
~~~

and:

~~~json
{"nickname": null}
~~~

However, it does not allow numbers, booleans, or objects on the `nickname` property.

According to OpenAPI 3.0.3, **nullable: true** only takes effect when **type** is explicitly declared in the same Schema Object. It adds `null` to the value set of that type. Other constraints still apply and may still exclude a `null` value in certain schema structures.

The following example does not reliably express `nullable` because the Schema Object does not declare `type` at the same location:

~~~yaml
nickname:
  nullable: true
  maxLength: 80
~~~

Declare `type` explicitly:

~~~yaml
nickname:
  type: string
  nullable: true
  maxLength: 80
~~~

The default value of `nullable` is `false`. If a property is not allowed to be `null`, there is no need to write `nullable: false` everywhere.

## 4. Limitations of `nullable` in OpenAPI 3.0

OpenAPI 3.0 uses its own Schema Object subset based on an older JSON Schema. You cannot set `type: null` or `type: [string, "null"]` as in modern JSON Schema.

The following examples are invalid under OpenAPI 3.0's type representation:

~~~yaml
# Do not use in OpenAPI 3.0
nickname:
  type: null
~~~

~~~yaml
# Type arrays are not supported in OpenAPI 3.0 Schema Objects
nickname:
  type:
    - string
    - "null"
~~~

Use `type: string` together with `nullable: true`.

Another limitation involves `$ref`. In OpenAPI 3.0, a Reference Object cannot be extended with arbitrary properties. Therefore, you should not write `nullable: true` as a sibling of `$ref` and expect every tool to treat it as a nullable schema:

~~~yaml
# Do not rely on this pattern in OpenAPI 3.0
nickname:
  $ref: '#/components/schemas/Nickname'
  nullable: true
~~~

`nullable` also cannot be used as a way to relax type constraints already imposed inside a schema referenced via `allOf`. A subschema cannot use `allOf` to remove a parent schema's type constraint.

If the referenced definition must be nullable everywhere, you can declare `nullable` right inside that component:

~~~yaml
components:
  schemas:
    Nickname:
      type: string
      nullable: true
~~~

If only one usage site needs to be nullable, consider declaring an inline schema with a concrete `type` and `nullable: true`, or redesigning the components so the nullable scope is explicit. Avoid modifying a shared component if doing so unintentionally allows `null` at all reference sites.

## 5. Representing `null` in OpenAPI 3.1 with union types

OpenAPI 3.1 aligns the Schema Object with JSON Schema Draft 2020-12. The `type` keyword can take an array of types, allowing you to list the regular data type alongside `null`.

Example:

~~~yaml
openapi: 3.1.0
components:
  schemas:
    Customer:
      type: object
      properties:
        nickname:
          type:
            - string
            - "null"
          maxLength: 80
~~~

The `nickname` property accepts a string or `null`. This is a direct, readable conversion from the OpenAPI 3.0 example:

~~~yaml
# OpenAPI 3.0
type: string
nullable: true
~~~

~~~yaml
# OpenAPI 3.1
type:
  - string
  - "null"
~~~

In the `type` array, `"null"` is the JSON Schema data type name, not a string containing the literal text `"null"` in the payload. Valid payloads still use the JSON literal `null`:

~~~json
{"nickname": null}
~~~

If a schema permits only `null` and no other type, OpenAPI 3.1 can use:

~~~yaml
type: "null"
~~~

This case differs from a nullable property, which allows both a regular data type and `null`.

## 6. Representing `null` with `anyOf`

OpenAPI 3.1 can also represent a value as either a referenced type or `null` using `anyOf`:

~~~yaml
components:
  schemas:
    Nickname:
      type: string
      maxLength: 80

    Customer:
      type: object
      properties:
        nickname:
          anyOf:
            - $ref: '#/components/schemas/Nickname'
            - type: "null"
~~~

`anyOf` allows an instance that is valid against at least one subschema. Here, the value must satisfy the `Nickname` schema or be `null`.

This pattern is useful when the primary type is reused via `$ref`. It keeps the `Nickname` component non-nullable elsewhere while allowing one specific property to accept `null`.

`oneOf` can be used in some union models when branches are designed to be mutually exclusive. For a `null` branch paired with a regular object/string type, `anyOf` is usually clearer and well-suited for expressing nullability.

## 7. Nullable enums in OpenAPI 3.1

When using a union type with `enum`, remember that `enum` remains an independent constraint. If you want to allow `null`, the value `null` must be included in the `enum` list.

Example:

~~~yaml
status:
  type:
    - string
    - "null"
  enum:
    - active
    - disabled
    - null
~~~

If `null` is omitted from `enum`, the schema still rejects `null` even though `type` contains `"null"`, because that value is not in the `enum` set.

Another approach is placing `enum` in the `string` branch and using a separate `null` branch:

~~~yaml
status:
  anyOf:
    - type: string
      enum:
        - active
        - disabled
    - type: "null"
~~~

Both approaches can describe the union. When a schema has multiple constraints or uses `$ref`, the `anyOf` approach often makes it clearer which branch permits `null`.

## 8. Distinguishing a nullable array from a nullable array item

An array itself can be nullable, or each element inside the array can be nullable. These are two different structures.

### Array can be null, items are always strings

~~~yaml
tags:
  type:
    - array
    - "null"
  items:
    type: string
~~~

Valid payloads:

~~~json
{"tags": null}
~~~

or:

~~~json
{"tags": ["java", "spring"]}
~~~

### Array must always be an array, but items can be null

~~~yaml
tags:
  type: array
  items:
    type:
      - string
      - "null"
~~~

Valid payload:

~~~json
{"tags": ["java", null, "spring"]}
~~~

### Both array and items can be null

~~~yaml
tags:
  type:
    - array
    - "null"
  items:
    type:
      - string
      - "null"
~~~

Place the union at the right schema level. Placing `"null"` in `items` only allows a `null` element; it does not make the entire array nullable.

## 9. Comparison table: OpenAPI 3.0 vs 3.1

| Topic | OpenAPI 3.0 | OpenAPI 3.1 |
| --- | --- | --- |
| Schema Object foundation | Adapted JSON Schema Draft 05 subset | JSON Schema Draft 2020-12 |
| `null` type inside `type` | Not supported | Supported |
| Representing string or null | `type: string`, `nullable: true` | `type: [string, "null"]` |
| Representing ref or null | Limited; requires dedicated schema design | `anyOf` with `$ref` and a `type: "null"` branch |
| Union types via `type` array | Not supported | Supported |
| `nullable` keyword | Meaningful OpenAPI keyword | No longer the standard approach; use JSON Schema `null` type |
| Validators/code generators | Must support OAS 3.0 | Must support OAS 3.1 and modern JSON Schema |

OpenAPI 3.1 does more than change how `nullable` is written. The Schema Object has many other changes due to alignment with JSON Schema 2020-12. When upgrading, check all schema-processing tools, not just Swagger UI.

## 10. Choosing the OpenAPI version when using springdoc

Springdoc provides the `springdoc.api-docs.version` property to choose OpenAPI 3.0 or 3.1. Example:

~~~yaml
springdoc:
  api-docs:
    version: OPENAPI_3_1
~~~

To generate documents targeting OpenAPI 3.0:

~~~yaml
springdoc:
  api-docs:
    version: OPENAPI_3_0
~~~

Current springdoc configuration documentation lists `openapi_3_1` as the default value; the configuration enum uses `OPENAPI_3_0` and `OPENAPI_3_1`. Check your actual springdoc version because defaults and support capabilities can differ across release lines.

This property selects the OpenAPI dialect generated by springdoc. It does not change Java types, Jackson serialization, or controller validation logic. You should also never manually edit only the `openapi` field in output JSON from `3.0.x` to `3.1.x`; the schemas inside must be converted according to the right rules.

## 11. Verifying the generated version and schemas

After configuring springdoc, fetch the JSON document:

~~~bash
curl -sS http://localhost:8080/v3/api-docs -o openapi.json
~~~

Check the document-level version:

~~~bash
jq -r '.openapi' openapi.json
~~~

If configured for OpenAPI 3.1, the `openapi` field should start with `3.1`. If configured for 3.0, it should start with `3.0`.

Inspect a model's schema:

~~~bash
jq '.components.schemas.Customer' openapi.json
~~~

For OpenAPI 3.0, look for `nullable: true` on the corresponding property. For OpenAPI 3.1, look for `type` containing `"null"` or an `anyOf`/`oneOf` branch containing a `type: "null"` schema.

Do not only check whether Swagger UI can display the page. The UI may render a document while downstream validators or code generators fail to understand certain schema constructs.

## 12. Mapping null from Java models

In Java, reference types such as `String`, `Integer`, `BigDecimal`, or DTOs can hold `null` values. Primitive types such as `int`, `long`, and `boolean` cannot hold `null`.

Example:

~~~java
public record CustomerResponse(
    String id,
    String nickname,
    Integer age
) {}
~~~

At the Java layer, `nickname` and `age` can be `null` unless validation or other logic prevents it. However, whether springdoc generates a nullable schema also depends on the version, annotations, model converters, and configuration in use.

If a contract needs explicit nullability, inspect the generated OpenAPI JSON. Do not infer the schema solely from the fact that a Java field is a reference type.

For primitive types:

~~~java
public record CounterResponse(int count) {}
~~~

`count` cannot be `null` at runtime. If an API needs to represent a nullable `count`, use the wrapper type `Integer` or an appropriate reference type and define validation clearly.

## 13. Bean Validation does not replace nullable descriptions

Bean Validation checks data at runtime. Example:

~~~java
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

public record UpdateCustomerRequest(
    @NotNull
    String customerId,

    String nickname
) {}
~~~

`@NotNull` requires a non-null value when validation runs. `@NotBlank` also rejects `null` as well as empty or whitespace-only strings. If a property is genuinely allowed to be `null`, do not attach a null-forbidding constraint to that property.

However, `required` in OpenAPI refers to whether a property must appear in the object, whereas `@NotNull` checks the value after Jackson binds the request into a Java object. With some DTOs, an omitted field and a field explicitly sent as `null` both become Java `null`. To distinguish the two cases in `PATCH`, design an appropriate request model and deserialization process.

Springdoc can read certain Bean Validation annotations to add constraints to schemas. Inspect the generated document and test actual validation instead of assuming every annotation automatically creates the right `required`, `nullable`, or `PATCH` semantics.

## 14. Jackson can change how null appears in JSON

The schema describes allowed values, while Jackson decides how Java objects are serialized into JSON.

Example:

~~~java
import com.fasterxml.jackson.annotation.JsonInclude;

@JsonInclude(JsonInclude.Include.NON_NULL)
public record CustomerResponse(
    String id,
    String nickname
) {}
~~~

If `nickname` is `null`, Jackson may omit the property completely from the response instead of writing `"nickname": null`. This is the difference between an omitted property and a property with a `null` value.

If the contract requires responses to always include the property with a `null` value, configure serialization accordingly—for example, by not excluding `null` from JSON for that model or property. Conversely, if the contract allows the server to omit `null` properties, the schema and response description must make that handling clear.

For requests, Jackson settings such as `null` handling during deserialization or custom setters can also affect the meaning of submitted values. Therefore, test input JSON, the bound Java object, and the actual response JSON.

## 15. Creating nullable schemas via annotations or customizers

`swagger-core` annotations can supplement schema metadata, but nullable generation depends on the OpenAPI version and the bundled `swagger-core`/springdoc version. An annotation written for OpenAPI 3.0 will not necessarily produce the right union type for OpenAPI 3.1.

When precise control is required:

1. Select the OpenAPI version via `springdoc.api-docs.version`.
2. Declare DTOs and validation according to business semantics.
3. Use annotations or version-appropriate model converters/customizers.
4. Fetch the OpenAPI JSON and verify the output schemas.
5. Run validators and test the actual consumer code generator.

Do not insert `nullable: true` into every schema when the document already declares OpenAPI 3.1. In 3.1, prefer a union with the `null` type or `anyOf`.

If multiple components reference the same schema, determine whether nullability belongs to the component itself or only to the referencing property. Choose the corresponding declaration so you do not alter the contracts of other endpoints.

## 16. Migration strategy from 3.0 to 3.1

When upgrading a document or springdoc system:

1. Inventory schemas using `nullable: true`.
2. Convert `type: string` with `nullable` into `type: [string, "null"]`.
3. For referenced schemas, use `anyOf` containing `$ref` and a `type: "null"` branch if only one site needs to be nullable.
4. Check enums and add `null` where needed.
5. Separately check nullable arrays and nullable array items.
6. Check the `required` list to ensure mandatory presence is not confused with non-null.
7. Run an OpenAPI 3.1 validator and a compatible JSON Schema validator.
8. Test Swagger UI, API client generators, mock servers, and contract tests.
9. Compare actual requests/responses before and after conversion.

A conversion example:

~~~yaml
# Before: OpenAPI 3.0
components:
  schemas:
    Customer:
      type: object
      required:
        - nickname
      properties:
        nickname:
          type: string
          nullable: true
~~~

~~~yaml
# After: OpenAPI 3.1
components:
  schemas:
    Customer:
      type: object
      required:
        - nickname
      properties:
        nickname:
          type:
            - string
            - "null"
~~~

Both schemas preserve the same meaning: `nickname` must be present, yet its value can be a string or `null`.

## 17. Common mistakes

**Using `type: null` in OpenAPI 3.0.** OAS 3.0 does not support `null` as a type. Use a concrete `type` and `nullable: true`.

**Putting `nullable: true` on a schema without `type`.** In OAS 3.0, `nullable` only takes effect when `type` is declared in the same Schema Object.

**Assuming `nullable` means `optional`.** Nullable permits a `null` value; optional means the property can be omitted. Check the `required` list.

**Using the string `"null"` instead of JSON `null`.** JSON `null` values have no quotes. The string `"null"` is a normal string.

**Using `type: [string, "null"]` but forgetting to move the document to OAS 3.1.** Type arrays are invalid in OAS 3.0 Schema Objects.

**Placing `nullable` next to `$ref` in OAS 3.0.** Reference Objects cannot be arbitrarily extended. Put `nullable` inside the component if all reference sites permit `null`, or design a separate inline schema.

**Using `allOf` to relax the type of a referenced schema.** `allOf` combines constraints; a subschema cannot remove a non-null constraint from a parent schema.

**Union type allows `null` but `enum` does not contain `null`.** Enum is a separate constraint. Add `null` to `enum` or split out a `null` branch with `anyOf`.

**Confusing a nullable array with a nullable item.** Place the union at the array level or the `items` level according to the desired payload.

**Swagger UI renders it, but the code generator fails.** Check whether the toolchain supports OpenAPI 3.1 and JSON Schema 2020-12; if not, consider continuing to emit OAS 3.0.

**Schema allows `null`, but the response omits the property.** Check Jackson `JsonInclude` and serialization configuration.

**Using `@NotNull` on a property intended to accept `null`.** The constraint will reject `null` when validation runs. Align validation with the OpenAPI contract.

**Only editing the `openapi` field in JSON.** Migrating from 3.0 to 3.1 requires converting Schema Objects and checking the entire document, not just changing the version string.

## 18. Nullable design checklist

- [ ] Determined whether the API needs to distinguish `null`, omitted properties, and empty strings.
- [ ] Determined whether the property must appear in the object.
- [ ] For OAS 3.0, used an explicit `type` together with `nullable: true`.
- [ ] For OAS 3.1, used a `type` array containing `"null"` or `anyOf`.
- [ ] Avoided `type` arrays in OAS 3.0 documents.
- [ ] Checked whether enums need to include `null`.
- [ ] Distinguished nullable arrays from nullable array items.
- [ ] Handled `$ref` according to OAS 3.0 limits or OAS 3.1 unions.
- [ ] Chosen `springdoc.api-docs.version` based on consumer capabilities.
- [ ] Aligned Java types, Bean Validation, and Jackson serialization.
- [ ] Inspected the generated OpenAPI JSON, not just annotations.
- [ ] Ran validators and contract tests for both requests and responses.

## 19. Conclusion

OpenAPI 3.0 represents `null` values using `nullable: true` on a Schema Object with an explicit `type`. OpenAPI 3.1 uses JSON Schema 2020-12 capabilities to represent `null` as a type in a union or an `anyOf` branch. In both versions, `nullable` remains independent of `required`: a property can be required to appear while still permitted to hold a `null` value. When using springdoc, pick the right document version, inspect the output schemas, and ensure Java models, Bean Validation, Jackson, and consumer tools share the same understanding of the contract.
