# Distinguishing Shared Features from Branch-Specific Features

Springdoc-openapi keeps a common model across branches: reading Spring endpoints, combining Java types and annotations, generating an OpenAPI document, and serving JSON/YAML plus a documentation UI if the app selects the corresponding starter. However, you cannot take dependencies, Java packages, configuration, or capabilities from one branch and assume they apply to all branches. Spring Boot 1/2, 3, and 4 have different generations of Spring Framework, Jakarta APIs, auto-configuration mechanisms, and dependency ecosystems; Springdoc therefore publishes separate compatible lines.

When choosing or upgrading versions, separate two questions: which concepts stay the same and which implementation details are branch-dependent? Concepts like operations, parameters, schemas, responses, security schemes, groups, and OpenAPI JSON/YAML have continuity. Maven artifacts, package imports, module composition, framework integrations, and new features must be checked per release line. This guide places commonalities and differences side by side, then outlines a workflow for choosing dependencies, reading release notes, and verifying real capabilities.

## 1. Distinguishing Shared Concepts from Version-Specific Implementations

A concept can persist across multiple branches while how you enable it changes. For instance, applications still need to describe endpoints with OpenAPI, yet the dependency providing Swagger UI in 1.x has a different name than the corresponding starter in 2.x and 3.x.

| Group | Usually Conceptually Stable | Must Be Checked Per Branch |
|---|---|---|
| API contract | Paths, HTTP methods, parameters, request bodies, responses | Emitted OpenAPI dialect, schema edge cases, and defaults |
| Java metadata | Controllers, DTOs, descriptive annotations | Package imports, Spring APIs, and how annotations are discovered |
| Documentation | OpenAPI JSON/YAML | Starters, endpoint paths, and export methods |
| Interface | UI reading the OpenAPI document | Swagger UI/Scalar starter and UI version |
| Web stack | MVC and reactive are two distinct web models | MVC/WebFlux artifacts and Spring Boot integrations |
| Customization | Extension points exist to modify documents | Packages, interface names, ordering, and customizer scope |
| Integration | Can connect with security, validation, data modules | Which modules are bundled vs. need separate starters |
| New features | Goal of describing APIs remains the same | Which release first introduced a specific capability |

Do not infer that a feature is available just because an annotation with the same name still compiles. Check actual dependencies, branch-matched documentation, and the OpenAPI document generated by the real runtime.

## 2. Three Main Release Lines

Springdoc is currently divided into three lines compatible with Spring Boot generations:

| Springdoc | Corresponding Spring Boot | Scope |
|---|---|---|
| 1.x | Spring Boot 1.x and 2.x | Legacy line; 1.8.0 is the last open-source release for Boot 1/2 |
| 2.x | Spring Boot 3.x | Starter line for Boot 3 |
| 3.x | Spring Boot 4.x | Line for Boot 4 |

This is the most important selection boundary. Do not add springdoc 3.x to a Boot 3 application just because 3.x has a newer version number; likewise, do not use 2.x in a Boot 4 application if the compatibility matrix does not list that pair.

Official documentation maintains separate pages for v1 and v2, while the current branch describes v3. Open the right page before copying dependencies or package imports.

## 3. The Compatibility Matrix Must Be Read by Spring Boot Minor Line

Matrix published by Springdoc at the time of writing:

| Spring Boot | Springdoc line built/tested per documentation |
|---|---|
| 4.1.x | 3.1.x to 3.2.x |
| 4.0.x | 3.0.x |
| 3.5.x | 2.8.x to 2.10.x |
| 3.4.x | 2.7.x to 2.8.x |
| 3.3.x | 2.6.x |
| 3.2.x | 2.3.x to 2.5.x |
| 3.1.x | 2.2.x |
| 3.0.x | 2.0.x to 2.1.x |
| 2.7.x and certain older 2.x lines | 1.6.x and above per minor |

The matrix is a verified compatibility guide, not a promise that all combinations behave identically. When a project upgrades a Spring Boot minor version, re-read the current table and release notes. Do not pick a random Springdoc version within the same major line and assume every Boot minor was tested with it.

## 4. Current Version Milestones to Recognize

According to published documentation and release lists:

- Springdoc 1.8.0 is the final open-source release of the Boot 1/2 line.
- Springdoc 2.10.0 belongs to the Boot 3.5.x line.
- Springdoc 3.2.0 belongs to the Boot 4.1.x line.

These numbers are reference points at the time of writing. In real deployments, check the latest releases page and compatibility matrix; do not keep example versions from this lesson if the project has upgraded its platform.

## 5. Why Not Use One Major Version for All Spring Boot Releases?

Major lines reflect changes in the underlying integration platform. Spring Boot 3 migrated the old Java EE ecosystem to the Jakarta namespace while upgrading Spring Framework and many dependencies. Spring Boot 4 continues raising the platform and base APIs. Springdoc must compile, wire auto-configuration, and be tested against the corresponding APIs.

A dependency can fail immediately at compile time if it references classes or packages no longer in the platform. Others may compile yet fail at startup because auto-configuration, beans, or method signatures changed.

Therefore, select the major line by Spring Boot first, then select the minor/patch by the compatibility matrix and release notes.

## 6. Shared Core Capabilities

Across branches supporting OpenAPI 3, common core capabilities include:

- Analyzing Spring MVC or Spring WebFlux controllers via the corresponding starter.
- Generating paths and operations from request mappings.
- Describing path, query, and header parameters.
- Analyzing request bodies and response types.
- Generating schemas from DTOs, generic types, and annotations.
- Reading Swagger/OpenAPI annotations such as Operation, Parameter, Schema, ApiResponse, Tag, and SecurityScheme.
- Filtering controllers by package or path.
- Creating multiple documents using groups.
- Customizing OpenAPI using customizers.
- Serving OpenAPI JSON and YAML.
- Integrating Swagger UI when selecting a UI starter.

These are shared conceptual capabilities. Specific edge cases, nullable inference rules, newer validation annotations, or integration modules may only be supported starting from a given release. Always verify details against the exact version in use.

## 7. The OpenAPI Concept Is Not Synonymous with the Springdoc Major Version

Three version types are easily confused:

| Version | Meaning |
|---|---|
| Springdoc version | Version of the Spring integration library |
| OpenAPI specification version | Standard version recorded in the document's openapi field |
| Spring Boot version | Application platform version |

For example, an application may use Spring Boot 3.5.x, Springdoc 2.10.x, and an OpenAPI document with its own openapi field. Do not infer the specification version solely from the Springdoc major number.

Open the top of the JSON/YAML file and read the openapi field. If downstream tools only support a specific OpenAPI version, verify both the actual document and configuration support in that exact release.

## 8. Swagger Annotations Are Metadata, Not Springdoc's API

Annotations such as Operation, Schema, Parameter, ApiResponse, and Tag belong to the Swagger/OpenAPI annotations ecosystem, typically imported from `io.swagger.v3.oas.annotations`.

Springdoc uses this metadata to build the document. That is why many business annotations can stay unchanged across Springdoc upgrades, provided the Swagger annotations dependency is compatible and has no version conflicts.

However, Springdoc's own APIs such as GroupedOpenApi, SpringDocUtils, or customizer interfaces may change packages or names across majors. Do not mistake Swagger annotations remaining identical for all internal Springdoc classes keeping the same packages.

## 9. Major Module Changes from v1 to v2

In v1, modules were split into many separate artifacts. Moving to v2, Springdoc renamed modules and consolidated several integrations into starter-common to reduce the number of dependencies to declare.

| v1 Artifact | Corresponding v2 Artifact | Notes |
|---|---|---|
| springdoc-openapi-common | springdoc-openapi-starter-common | Shared foundation |
| springdoc-openapi-webmvc-core | springdoc-openapi-starter-webmvc-api | OpenAPI for Spring MVC |
| springdoc-openapi-webflux-core | springdoc-openapi-starter-webflux-api | OpenAPI for WebFlux |
| springdoc-openapi-ui | springdoc-openapi-starter-webmvc-ui | MVC with Swagger UI |
| springdoc-openapi-webflux-ui | springdoc-openapi-starter-webflux-ui | WebFlux with Swagger UI |
| springdoc-openapi-data-rest | springdoc-openapi-starter-common | Integration merged into common |
| springdoc-openapi-hateoas | springdoc-openapi-starter-common | Integration merged into common |
| springdoc-openapi-kotlin | springdoc-openapi-starter-common | Integration merged into common |
| springdoc-openapi-javadoc | springdoc-openapi-starter-common | Integration merged into common |
| springdoc-openapi-security | springdoc-openapi-starter-common | Integration merged into common |

This table guides v1-to-v2 migration per the migration docs. Do not mechanically add every artifact to a project; pick the starter matching your web stack and UI/API-only needs.

## 10. Several Springdoc Packages Changed from v1 to v2

The v1-to-v2 migration includes important import changes:

| v1 | v2 |
|---|---|
| org.springdoc.core.SpringDocUtils | org.springdoc.core.utils.SpringDocUtils |
| org.springdoc.api.annotations.ParameterObject | org.springdoc.core.annotations.ParameterObject |
| org.springdoc.core.GroupedOpenApi | org.springdoc.core.models.GroupedOpenApi |
| org.springdoc.core.customizers.OpenApiCustomiser | org.springdoc.core.customizers.OpenApiCustomizer |
| org.springdoc.core.Constants | org.springdoc.core.utils.Constants |
| org.springdoc.core.SwaggerUiConfigParameters | org.springdoc.core.properties.SwaggerUiConfigParameters |

Note that OpenApiCustomiser changed spelling from Customiser to Customizer. Changing only the dependency version without updating imports may prevent the project from compiling.

For v3, do not deduce all new packages solely from the v1/v2 table. Check API docs and sources for the exact v3 tag before changing imports.

## 11. Choosing Starters by Web Stack

On branches using the starter layout, pick the right web stack:

| Need | Spring MVC | Spring WebFlux |
|---|---|---|
| OpenAPI document only | springdoc-openapi-starter-webmvc-api | springdoc-openapi-starter-webflux-api |
| OpenAPI and Swagger UI | springdoc-openapi-starter-webmvc-ui | springdoc-openapi-starter-webflux-ui |
| OpenAPI and Scalar | springdoc-openapi-starter-webmvc-scalar | springdoc-openapi-starter-webflux-scalar |

MVC starters integrate with spring-boot-starter-web. WebFlux starters integrate with spring-boot-starter-webflux. Do not add both just to get another UI; the application must have the matching web stack.

Artifact names in the table follow the starter format of current branches. If still on v1, consult v1 docs instead of copying v2/v3 artifact names.

## 12. Distinguishing API-Only from UI Starters

Not every application needs Swagger UI. If you only need the OpenAPI document for CI, code generators, or another developer portal, use the corresponding API-only starter.

Example with Spring MVC on the v3 branch:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-api</artifactId>
    <version>3.2.0</version>
</dependency>
~~~

If Swagger UI is needed:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>3.2.0</version>
</dependency>
~~~

The examples above target Spring Boot 4.1.x on the 3.2.x line. For Boot 3, pick the same starter structure with a compatible 2.x version. For Boot 2, look up v1 artifacts.

API-only still serves the document; it does not pull Swagger UI. Conversely, the UI starter provides both document integration and the interface.

## 13. Dependency Examples for Boot 3 and Boot 4

A Spring Boot 3.5.x application can use Springdoc 2.8.x through 2.10.x per the matrix:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.10.0</version>
</dependency>
~~~

A Spring Boot 4.1.x application can use Springdoc 3.1.x through 3.2.x:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>3.2.0</version>
</dependency>
~~~

Identical artifact names do not mean cross-major binary compatibility. Versions 2.10.0 and 3.2.0 are built for different Spring Boot generations.

## 14. Common Features That Must Be Checked by Module

Some features depend not only on the Springdoc version but also on the starter or framework integration:

| Capability | What to Check |
|---|---|
| Swagger UI | Whether the right MVC/WebFlux UI starter is used |
| Scalar | Whether a Scalar starter and supporting release exist |
| Spring Data REST | Whether integration is merged into common or needs a separate module in older branches |
| Spring HATEOAS | Compatible version and HAL schemas |
| Actuator | Module or auto-configuration supporting the right Boot line |
| Kotlin | Nullability, sealed classes, and compiler metadata |
| Groovy/Javadoc | Whether modules exist in the branch in use |
| Functional endpoints | Whether RouterFunction/functional mapping styles are supported in that release |
| MCP | Available only in supporting 3.x releases, starting from 3.0.3 |
| Spring Framework API versioning | Check the 3.x release and corresponding Spring Framework version |

Do not equate a feature appearing in the current README with it having existed in v1 or every v2 patch.

## 15. New Features Available Only in One Branch

Certain capabilities were added in newer releases:

- MCP integration was added in Springdoc 3.0.3 on the Spring Boot 4 branch.
- Spring Framework API versioning support was added in the 3.x branch in corresponding releases.
- Various improvements to Kotlin nullability, schemas, and serialization were added release by release.
- Scalar integration and security/configuration changes can differ across 3.x milestones.

If a Boot 3 application needs a capability published only in 3.x, you cannot simply upgrade Springdoc 2.x to 3.x while ignoring the Boot major. Evaluate upgrading Spring Boot first or design another supported integration approach.

## 16. MCP as a Classic Example of a Branch-Specific Feature

Springdoc MCP turns OpenAPI operations into MCP tools for AI clients. Release notes record this feature as added in Springdoc 3.0.3.

Therefore:

- Springdoc 1.x has no Springdoc MCP module.
- Springdoc 2.x for Boot 3 has no corresponding MCP starter in that line.
- Springdoc 3.x on Boot 4 has the MCP module starting from supporting releases.

Do not add a 3.x MCP artifact to a Boot 3 app running Springdoc 2.x. If MCP is needed on Boot 3, evaluate native MCP solutions compatible with Spring AI and the app's dependency matrix rather than assuming Springdoc 2.x ships the same module.

## 17. OpenAPI Annotations Have Continuity, While Springdoc APIs Can Change

Swagger v3 annotations such as Operation, Schema, Parameter, ApiResponse, and Tag are usually the metadata controllers carry across branches. They belong to the OpenAPI annotations ecosystem.

Springdoc extension APIs can change:

- Package of GroupedOpenApi.
- Package of SpringDocUtils.
- Names and packages of customizers.
- Artifacts containing auto-configuration.
- How Springdoc integrates with Spring Boot properties.

When upgrading majors, resolve compile errors by package import first. After compiling, verify customizer beans are registered by Spring and the final document applies the changes.

## 18. Shared Properties and New Properties

Many properties keep the same springdoc prefix, for example:

~~~yaml
springdoc:
  api-docs:
    enabled: true
    path: /v3/api-docs
  swagger-ui:
    enabled: true
    path: /swagger-ui.html
  packages-to-scan:
    - com.acme.api
  paths-to-match:
    - /api/**
~~~

However, do not copy an entire application.yml across majors without checking the property reference. A property may be added, change defaults, change types, move to another module, or no longer be supported.

Check the properties page for the right branch and confirm property binding at runtime. Unknown properties do not always raise errors; the app might boot normally while silently ignoring the value.

## 19. How to Choose the Right Documentation Page

Springdoc maintains separate documentation pages:

| Application Line | Documentation to Open |
|---|---|
| Boot 1/2 + Springdoc 1.x | springdoc.org/v1 |
| Boot 3 + Springdoc 2.x | springdoc.org/v2 |
| Boot 4 + Springdoc 3.x | springdoc.org |

Do not use the default landing page for every application. The current page may describe new properties or modules that do not exist in older branches.

When reading a blog post or Stack Overflow example, check the publication date, artifact version, package imports, and Spring Boot version before applying it.

## 20. Maven and Gradle Plugins Also Have Their Own Lifecycles

Springdoc provides plugins to export OpenAPI documents at build time. These plugins differ from runtime starters:

- Runtime starters integrate into the application to generate documents while the app runs.
- Maven/Gradle plugins start the application or invoke appropriate configuration to fetch the document during a build.
- Plugin versions do not necessarily match starter versions.

For example, the Gradle plugin must be configured alongside the Spring Boot plugin per the plugin docs for the release in use. In Gradle plugin v2, task execution and Gradle requirements differ from plugin v1; do not copy old tasks or plugin DSL without reading the migration guide.

If you only need runtime endpoints, adding a build plugin is unnecessary. If you need OpenAPI artifacts in CI, check plugin compatibility, how the app boots, and which profile is needed.

## 21. BOM and Synchronized Version Management

If a project uses multiple Springdoc modules, a BOM helps manage versions consistently when the branch provides one.

Conceptual example:

~~~xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springdoc</groupId>
            <artifactId>springdoc-openapi-bom</artifactId>
            <version>3.2.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
~~~

Modules can then omit repeating versions if the BOM manages those artifacts. Verify that a BOM is published for the right line and the artifacts you need.

Do not mix a v3 BOM with v2 starters or old Springdoc dependencies. Let one dependency management source govern modules of the same line.

## 22. Inspecting the Dependency Tree on Conflicts

When an app uses Springdoc alongside Swagger Core or other libraries, multiple versions of swagger-annotations, swagger-models, or swagger-core may exist.

Maven:

~~~bash
./mvnw dependency:tree
~~~

Gradle:

~~~bash
./gradlew dependencies
~~~

Focus on checking:

- Whether org.springdoc artifacts share the same major line.
- Whether swagger-core, swagger-annotations, and swagger-models are overridden.
- Whether old Springfox remains on the classpath.
- Whether multiple MVC/WebFlux starters appear simultaneously.
- Whether a Swagger UI version is pulled in by another dependency.

A NoSuchMethodError or ClassNotFoundException can come from an inconsistent dependency graph, not necessarily from incorrect controller annotations.

## 23. Migrating from v1 to v2: Migration Checklist

When upgrading from Spring Boot 2/Springdoc 1 to Boot 3/Springdoc 2:

1. Confirm the application has moved to Spring Boot 3 and the Jakarta namespace.
2. Choose Springdoc 2.x matching the Boot 3 minor.
3. Replace v1 artifacts with corresponding starters.
4. Update renamed Springdoc package imports.
5. Check customizer interfaces and bean registration.
6. Check Spring Security, HATEOAS, Data REST, and Actuator integration.
7. Export OpenAPI JSON/YAML.
8. Compare paths, schemas, responses, and security against the baseline.
9. Run HTTP integration tests and OpenAPI validation.

Do not just bump dependencies. This is a migration of both the Spring Boot platform and the Jakarta ecosystem.

## 24. Migrating from v2 to v3: Migration Checklist

When upgrading from Spring Boot 3/Springdoc 2 to Boot 4/Springdoc 3:

1. Upgrade Spring Boot on its own plan and verify Spring Framework compatibility.
2. Choose Springdoc 3.x matching the Boot 4 minor.
3. Verify starter artifacts and MVC/WebFlux/UI/Scalar modules.
4. Check internal Springdoc APIs imported by the application.
5. Check the property reference and new defaults.
6. Read release notes across intermediate versions, especially schema and security changes.
7. If using API versioning, MCP, or new capabilities, confirm minimum release milestones.
8. Export the OpenAPI document under the right profile.
9. Run contract diffs and integration tests.

Do not enable MCP or API versioning in production simply because 3.x supports them; configure security and test your application's actual behavior.

## 25. Do Not Confuse Swagger UI with the OpenAPI Document

OpenAPI is the machine-readable contract. Swagger UI is an interface that renders that contract. The two can be supplied by different starters.

Therefore:

- An API-only starter can generate the document without Swagger UI.
- A UI starter supplies the interface alongside the document.
- Scalar can be used instead of Swagger UI if the starter and release support it.
- Disabling UI does not disable JSON/YAML.
- A different UI version does not necessarily change API schemas, though it can change rendering or request execution.

When a bug only appears in the UI, inspect the JSON document directly before changing the Springdoc version.

## 26. MVC and WebFlux Differ by Application Architecture

Spring MVC handles requests via the servlet stack. WebFlux uses the reactive stack. Springdoc provides separate starters for each.

Do not pick the WebFlux starter just because controllers return Mono or Flux if the app actually runs on the servlet stack, or vice versa. Identify the underlying dependency:

| Web Stack | Typical Spring Boot Dependency | Springdoc Starter |
|---|---|---|
| MVC | spring-boot-starter-web | webmvc-api or webmvc-ui |
| WebFlux | spring-boot-starter-webflux | webflux-api or webflux-ui |

Some functional endpoints are supported, though specific capabilities and API versioning for functional routes depend on the release. Read branch-matched docs and inspect the generated document.

## 27. Validation Support Does Not Mean Every Validator Becomes a Schema

Common annotations like NotNull, NotBlank, Size, Min, Max, DecimalMin, and Pattern can contribute constraints to schemas depending on version and config.

However:

- Custom validators relying on services/databases cannot be fully translated into JSON Schema automatically.
- Newer annotations may only be supported starting in a specific release.
- Jakarta Validation and javax.validation belong to different namespace generations.
- Runtime validation still requires the validation dependency and @Valid or an appropriate activation mechanism.

If upgrading from Boot 2 to Boot 3/4, check javax/jakarta namespaces in DTOs and the validation provider. If schemas lack constraints, inspect the document and dependencies before concluding Springdoc lacks support.

## 28. Parameter Name Discovery as an Example of Platform Changes

Spring Boot 3.2 changed parameter name discovery in certain cases. The Springdoc FAQ instructs enabling the `-parameters` compiler option if parameter names are not generated properly in OpenAPI.

Maven:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
    </configuration>
</plugin>
~~~

This shows that missing query parameter names can stem from compiler metadata rather than a feature removed from Springdoc. When upgrading Spring Boot or the Java compiler, verify parameter names in OpenAPI output.

## 29. Ecosystem Integrations Can Change by Release

Springdoc supports many integrations such as Spring Security, Spring Data REST, Spring HATEOAS, Actuator, Spring Cloud Function, Kotlin, Groovy, and Javadoc. However, packaging can change:

- In v1 there were many separate integration artifacts.
- In v2, several integrations moved into starter-common.
- In v3, starters continue to be organized for Boot 4 with new capabilities added per release.

Not seeing a separate artifact does not mean a feature is gone—it may have been merged into starter-common. Conversely, not seeing a feature mentioned in the README does not mean the current starter automatically enables every integration; check the modules guide.

## 30. Reading Release Notes to Locate Features by Branch

When you need to determine which version introduced a capability:

1. Open GitHub Releases for springdoc-openapi.
2. Select the right tag: v1, v2, or v3.
3. Look under Added, Changed, Fixed, and Security sections.
4. Check the first release introducing the feature.
5. Check subsequent releases for behavior or default changes.
6. Cross-reference that version with the Spring Boot compatibility matrix.
7. Build a small test on that exact dependency before upgrading the main project.

Release notes are crucial for newer features like MCP, API versioning, Kotlin nullability, Scalar integration, or required/default schema changes.

## 31. Verifying Features with a Minimal Project

If unsure whether a feature exists in a version, create a small sample with:

- The same Spring Boot version as the application.
- A single Springdoc starter.
- A minimal controller.
- A DTO with relevant annotations.
- Minimal configuration for the feature under test.

Start the application and check:

~~~bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs \
  -o target/openapi.json
~~~

Then verify:

- Application context starts cleanly.
- Expected auto-configuration beans are registered.
- Documentation endpoints respond.
- JSON/YAML has the expected fields or behavior.
- No related warnings or exceptions appear.

A small sample isolates library compatibility bugs from complex real-application configuration.

## 32. Reading the Document to Verify OpenAPI Version and Features

Open the top of the JSON file:

~~~json
{
  "openapi": "3.1.0",
  "info": {
    "title": "Catalog API",
    "version": "1.0.0"
  },
  "paths": {}
}
~~~

The example above only illustrates structure, not a guarantee that every Springdoc branch emits this exact version. Read the actual value in your application's document.

For specific features, inspect the corresponding section:

- paths to inspect operations.
- components/schemas to inspect models.
- securitySchemes to inspect authentication metadata.
- tags to inspect groups.
- servers to inspect server URLs.
- extensions with the x- prefix to inspect custom metadata.

If a capability cannot be represented in an OpenAPI document, it may belong to the UI, build plugin, or runtime integration rather than the contract schema.

## 33. Quick Decision Matrix When Choosing Versions

| Project Status | Selection Approach |
|---|---|
| Spring Boot 2.x running stably | Compatible Springdoc 1.x line; consider platform upgrade plans since v1 reached end of open-source line |
| Spring Boot 3.0.x | Springdoc 2.0.x–2.1.x |
| Spring Boot 3.2.x | Springdoc 2.3.x–2.5.x |
| Spring Boot 3.5.x | Springdoc 2.8.x–2.10.x |
| Spring Boot 4.0.x | Springdoc 3.0.x |
| Spring Boot 4.1.x | Springdoc 3.1.x–3.2.x |
| Springdoc MCP needed | 3.x branch from supporting release, on Boot 4 |
| OpenAPI JSON/YAML only needed | Choose API-only starter |
| Swagger UI needed | Choose UI starter for MVC/WebFlux |
| Scalar needed | Choose Scalar starter of the right branch |

This matrix is a starting point. Always check the updated compatibility matrix and release notes before locking a version.

## 34. Common Errors When Mixing Branches

| Symptom | Possible Cause | Resolution |
|---|---|---|
| ClassNotFoundException in org.springdoc | Imported from a different major's package | Consult migration guide and update imports |
| NoSuchMethodError in swagger-core | Dependency graph mixes versions | Inspect dependency tree and BOM |
| Auto-configuration does not create API docs | Starter mismatches web stack or Boot line | Choose right MVC/WebFlux and compatibility line |
| Starter artifact not found | Copied v2/v3 artifact names into v1 | Use module docs for the active branch |
| Swagger UI missing while JSON exists | Using API-only starter | Add UI starter if interface is actually needed |
| MCP artifact fails to resolve on Boot 3 | Springdoc MCP belongs to 3.x branch | Use a Boot 3-compatible solution or upgrade platform |
| Query parameter loses name | Compiler does not retain parameter names or different binding | Enable -parameters and check signature |
| Schema differs after patch upgrade | Release changed introspection or dependencies | Read release notes and run contract diff |
| Scalar or UI behavior differs | Starter/UI version changed | Check module docs and release notes |
| Property ignored | Property does not exist in active branch | Check properties reference for the right branch |
| Functional endpoint lacks operation | Release or route style not yet supported as expected | Check support matrix and same-version sample |

## 35. Safe Upgrade Procedure

Proceed in order:

1. Record Spring Boot version, Java version, and web stack.
2. Record all existing Springdoc artifacts.
3. Identify the compatible major line from the official matrix.
4. Choose the right starter and UI/API-only variant.
5. Inspect Springdoc packages imported in source code.
6. Read the migration guide if changing majors.
7. Read release notes from current version to target version.
8. Update dependency management and remove duplicate old dependencies.
9. Compile to detect package/API incompatibilities.
10. Start the application with a realistic profile.
11. Export OpenAPI JSON and YAML.
12. Compare paths, operationIds, parameters, schemas, responses, and security.
13. Run contract tests and an OpenAPI validator.
14. Check UI, reverse proxy, and document groups.
15. Document which features were added, removed, or changed.

Do not conclude a migration is complete just because the Maven/Gradle build succeeds. Documents can change at runtime even when source compiles without error.

## 36. Key Takeaways

- Springdoc has three main lines: 1.x for Boot 1/2, 2.x for Boot 3, and 3.x for Boot 4.
- Choose versions by the Spring Boot minor compatibility matrix, not solely by major or latest version.
- OpenAPI concepts such as operations, parameters, schemas, responses, groups, and security have continuity.
- Artifacts, package imports, module composition, and auto-configuration can change across majors.
- v1 uses legacy artifacts; v2 switched to starter layout and merged several integrations into starter-common.
- v2 introduced package migrations such as GroupedOpenApi, SpringDocUtils, and OpenApiCustomizer.
- v3 targets Boot 4; capabilities like Springdoc MCP appear at specific release milestones.
- MVC, WebFlux, API-only, Swagger UI, and Scalar require starters matching needs.
- Springdoc version is not the OpenAPI specification version; read the openapi field in the document.
- Bean Validation, Jackson, Kotlin, and functional endpoint support must be verified per release.
- Maven/Gradle plugins have separate versions and lifecycles from runtime starters.
- Dependency trees and release notes are essential tools when investigating incompatibilities.
- After upgrading, inspect OpenAPI JSON/YAML and contract diffs, not just compilation.

Shared concepts help developers transfer knowledge across Springdoc branches, while implementation details must still follow the actual version. Start from Spring Boot and the web stack, select a compatible Springdoc major/minor, then verify artifacts, packages, modules, and release-specific features. When upgrading, compare OpenAPI documents before and after to catch contract changes that the compiler cannot warn about.
