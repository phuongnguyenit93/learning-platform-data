# Swagger UI Returns 404 Even Though the Specification Endpoint Still Works

A Spring Boot application may return OpenAPI JSON normally at /v3/api-docs, yet opening /swagger-ui.html results in HTTP 404. This symptom usually means OpenAPI generation is working, while the UI route, Swagger UI static resources, or routing through a proxy has not been registered or routed properly.

The two endpoints serve different purposes:

- /v3/api-docs is the endpoint returning the OpenAPI document generated by springdoc.
- /swagger-ui.html is the Swagger UI entry point. Springdoc usually redirects this entry point to the index.html page inside a WebJar.

Therefore, JSON working does not prove that Swagger UI has been packaged and served. You need to pinpoint which exact request in the UI loading chain returns 404: the initial HTML URL, the index.html page, JavaScript/CSS files, or the swagger-config endpoint.

## 1. Identifying the Exact Symptom

A Swagger UI page load typically involves multiple requests:

1. The browser calls /swagger-ui.html.
2. Springdoc returns a redirect to the UI page, usually /swagger-ui/index.html.
3. The browser loads swagger-ui.css, swagger-ui-bundle.js, and other static resources.
4. Swagger UI calls /v3/api-docs/swagger-config.
5. From the configuration received, the UI loads the OpenAPI document such as /v3/api-docs.

The request sequence can be visualized as follows:

~~~mermaid
sequenceDiagram
    participant B as Browser
    participant S as Spring Boot
    B->>S: GET /swagger-ui.html
    S-->>B: 3xx Location: /swagger-ui/index.html
    B->>S: GET /swagger-ui/index.html
    S-->>B: HTML 200
    B->>S: GET JavaScript/CSS assets
    S-->>B: Assets 200
    B->>S: GET /v3/api-docs/swagger-config
    S-->>B: Config JSON 200
    B->>S: GET /v3/api-docs
    S-->>B: OpenAPI JSON 200
~~~

Asset paths and redirects can change depending on version, custom path, or resource resolver. Get the actual URLs from the `Location` response header and the browser Network tab.

If you only look at the first request in the Network tab, you may miss the request actually causing the error.

| Failing request | Sign | First area to check |
|---|---|---|
| /swagger-ui.html returns 404 immediately | No redirect or response is an application/proxy 404 page | UI starter, enabled/path properties, context path, management port |
| /swagger-ui.html redirects but /swagger-ui/index.html returns 404 | Entry point exists but UI resource cannot be found | WebJar, static resource mapping, dependency packaging |
| index.html returns 200 but JS/CSS return 404 | HTML page loads but UI is blank or broken | Static path pattern, resource locations, reverse proxy prefix |
| HTML and JS/CSS return 200 but swagger-config returns 404 | UI opens but does not know which document to load | configUrl, api-docs.path, custom path |
| swagger-config returns 200 but OpenAPI URL returns 404 | UI runs, document URL in config is wrong | url, urls, group path, context path |
| 3xx to login page | Security entry point redirects the request | Check authentication and the final URL in the redirect chain |
| 401/403 | Request rejected by Spring Security | Authorization rules, authorities, and SecurityFilterChain |
| 404 from gateway while application returns 200 | Proxy/ingress rewrite or public route is wrong | Compare direct request vs request through proxy |
| 500 | Error initializing config or resolving resources | Read server logs and root exception |

HTTP 404 differs from 401 and 403. If the application has a mechanism that intentionally hides endpoints when unauthenticated, a security handler may return 404; in that case check security logs and test with an authorized identity.

## 2. Checking Dependencies First

This is the most common cause when /v3/api-docs works but Swagger UI does not exist: the application only added the API starter, not the UI starter.

Springdoc provides separate starters:

| Web stack | Generates OpenAPI JSON/YAML only | Includes Swagger UI |
|---|---|---|
| Spring MVC | springdoc-openapi-starter-webmvc-api | springdoc-openapi-starter-webmvc-ui |
| Spring WebFlux | springdoc-openapi-starter-webflux-api | springdoc-openapi-starter-webflux-ui |

If the project uses spring-boot-starter-web (Spring MVC), the dependency needed for the UI is:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>${springdoc.version}</version>
</dependency>
~~~

If the project uses spring-boot-starter-webflux, choose:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webflux-ui</artifactId>
    <version>${springdoc.version}</version>
</dependency>
~~~

Define `springdoc.version` in Maven properties or a Gradle version catalog using a release compatible with your Spring Boot version. Common major version matrix:

| Spring Boot | springdoc branch |
|---|---|
| 2.x | 1.x |
| 3.x | 2.x |
| 4.x | 3.x |

Do not choose the MVC starter for a WebFlux application or vice versa. When upgrading a major Spring Boot version, check the springdoc compatibility matrix and migration guide before updating dependencies.

### 2.1. Verifying Actual Dependencies

With Maven:

~~~bash
mvn dependency:tree -Dincludes=org.springdoc:*,org.webjars:*
~~~

With Gradle:

~~~bash
./gradlew dependencyInsight --dependency springdoc-openapi-starter-webmvc-ui --configuration runtimeClasspath
./gradlew dependencyInsight --dependency springdoc-openapi-starter-webflux-ui --configuration runtimeClasspath
~~~

With Maven, you can restrict the dependency tree to runtime scope:

~~~bash
mvn dependency:tree -Dscope=runtime -Dincludes=org.springdoc:*
~~~

Cross-check the dependency tree against the application's web starter type. If you only see springdoc-openapi-starter-webmvc-api or springdoc-openapi-starter-webflux-api, the OpenAPI endpoint can work without Swagger UI. Add the proper UI starter instead of adding a standalone incompatible Swagger UI release.

Declaring the starter in the build file is not enough: the dependency must appear in the running runtime artifact. For an executable JAR, check `BOOT-INF/lib` to confirm the UI starter and WebJar are packaged. If local works but a container returns 404, check whether the image copied the right new JAR and avoid deploying an old artifact by mistake.

If the dependency graph contains both spring-boot-starter-web and spring-boot-starter-webflux, do not infer the web stack from a single dependency. Spring Boot may select Spring MVC when both stacks are present; check startup logs and the condition evaluation report to see which auto-configuration is actually active. Then use the UI starter matching the selected stack and remove unnecessary dependencies if possible.

Do not declare both MVC and WebFlux starters simultaneously just to try fixing 404. Pick the application's actual stack and remove duplicate dependencies or leftover old versions.

## 3. Distinguishing Properties Controlling UI and OpenAPI

Springdoc has independent properties for the specification and the UI:

| Property | Meaning |
|---|---|
| springdoc.api-docs.enabled | Enable/disable the OpenAPI endpoint |
| springdoc.api-docs.path | OpenAPI JSON endpoint path |
| springdoc.swagger-ui.enabled | Enable/disable Swagger UI |
| springdoc.swagger-ui.path | Swagger UI HTML entry path |
| springdoc.swagger-ui.configUrl | Configuration JSON URL loaded by Swagger UI |
| springdoc.swagger-ui.url | URL of a custom OpenAPI document |
| springdoc.swagger-ui.urls | List of OpenAPI documents for the UI group selector |

Basic configuration example:

~~~yaml
springdoc:
  api-docs:
    enabled: true
    path: /v3/api-docs
  swagger-ui:
    enabled: true
    path: /swagger-ui.html
~~~

If `springdoc.swagger-ui.enabled=false` in the active profile, /v3/api-docs can still return 200 while the UI is not registered.

Check both profile configurations and environment variables. For example:

~~~bash
SPRINGDOC_SWAGGER_UI_ENABLED=false
SPRINGDOC_SWAGGER_UI_PATH=/docs/api.html
~~~

Property values can be overridden by application-prod.yml, environment variables, system properties, or command-line arguments. Do not read only application.yml and assume those are the running values.

In particular, compare effective configuration between local and production. The production profile may disable the UI, change a custom path, disable static mappings, or apply a different security chain; a deployment may also be running an old artifact. If you need Actuator env, configprops, or conditions to investigate, only access them in a protected admin environment and never expose these endpoints publicly.

### 3.1. Changing the HTML Path Does Not Change the OpenAPI Path

For example, to place the UI at /docs/api.html while keeping OpenAPI JSON at /v3/api-docs:

~~~yaml
springdoc:
  api-docs:
    path: /v3/api-docs
  swagger-ui:
    path: /docs/api.html
~~~

The URL to open is:

~~~text
http://localhost:8080/docs/api.html
~~~

If you only changed `springdoc.swagger-ui.path` and keep visiting /swagger-ui.html, the old request may rightly return 404 as configured.

Conversely, if you changed `springdoc.api-docs.path`, inspect `swagger-config` to see which URL the UI is configured to load the document from. Do not confuse `configUrl` with the OpenAPI spec URL:

- configUrl points to the Swagger UI configuration JSON.
- url points to the OpenAPI document.

When using an external OpenAPI file or multiple groups, check `url`/`urls` and `urlsPrimaryName` in the UI configuration. Only override `configUrl` when you genuinely want the UI to fetch its configuration from another endpoint.

If you want Swagger UI to read a static OpenAPI file instead of a dynamically generated document, you can place the file on a classpath resource path such as `src/main/resources/static/open-api.json`, then configure `springdoc.swagger-ui.url: /open-api.json`. Here `url` must point to a directly downloadable spec file; `configUrl` still points to the Swagger UI configuration JSON. The two URLs do not replace each other.

## 4. Checking Context Path and Servlet Path

If the application declares a context path:

~~~yaml
server:
  servlet:
    context-path: /catalog
~~~

then URLs must include the context path:

~~~text
http://localhost:8080/catalog/swagger-ui.html
http://localhost:8080/catalog/v3/api-docs
~~~

The Springdoc FAQ also confirms that Swagger UI resides under the application's context path. Therefore, /swagger-ui.html at the server root may 404 while /catalog/v3/api-docs still works.

With WebFlux, check `spring.webflux.base-path` if the application has a base path. With Spring MVC, check `server.servlet.context-path` and `spring.mvc.servlet.path` if a servlet prefix is configured.

Do not add the context path twice. If a reverse proxy already puts a prefix in the public URL and the application also sets a similar context path, check whether the proxy preserves or strips the prefix before forwarding.

## 5. Checking Static Resources and WebJar

Springdoc does not merely return one HTML controller. Swagger UI consists of static files packaged in a WebJar, for example:

- index.html
- swagger-ui-bundle.js
- swagger-ui-standalone-preset.js
- swagger-ui.css
- favicon and supporting resources

Spring Boot serves static resources through `ResourceHttpRequestHandler`. By default, Spring Boot searches for static content in classpath locations such as:

- META-INF/resources
- resources
- static
- public

WebJars are served via the `/webjars/**` path under Spring Boot's default configuration.

Thus, you may encounter a situation where:

- /swagger-ui.html redirects successfully.
- /swagger-ui/index.html returns 404.
- /v3/api-docs still returns JSON normally.

This is a sign to check the static resource handler or the WebJar dependency.

### 5.1. Checking Properties That Alter Resource Mapping

The following properties can alter or disable default mappings:

| Property | Impact |
|---|---|
| spring.mvc.static-path-pattern | Changes the URL pattern used to serve static resources |
| spring.webflux.static-path-pattern | Changes the static resources URL pattern in WebFlux |
| spring.web.resources.static-locations | Replaces the list of searched classpath/filesystem locations |
| spring.web.resources.add-mappings | Disables/enables static resource mappings |
| spring.mvc.webjars-path-pattern | Changes the path pattern for WebJars |
| spring.webflux.webjars-path-pattern | Changes the WebJar path pattern in WebFlux |

For example, the following configuration moves static resources to `/assets/**`:

~~~yaml
spring:
  mvc:
    static-path-pattern: /assets/**
~~~

While Swagger UI needs to load resources at URLs like `/swagger-ui/**` and `/webjars/**`, the `/assets/**` pattern can prevent those URLs from being served. Unless specially required, remove the custom configuration and restore the default `/**` mapping.

If configuring `spring.web.resources.static-locations`, ensure locations containing WebJars and application resources are still searched. This property replaces the default list; do not keep only a single `classpath:/static/` directory and assume resources inside dependency JARs will still be found.

If set:

~~~yaml
spring:
  web:
    resources:
      add-mappings: false
~~~

Spring Boot disables static resource mappings. OpenAPI JSON may still be served by its dedicated controller, but Swagger UI's JavaScript/CSS files will no longer be delivered by the default resource handler.

### 5.2. Checking Custom MVC Configuration

Review the following components if the application has customized the web stack:

- Classes annotated with `@EnableWebMvc`.
- Classes extending `WebMvcConfigurationSupport`.
- `WebMvcConfigurer#addResourceHandlers`.
- Classes annotated with `@EnableWebFlux`.
- Classes extending `WebFluxConfigurationSupport`.
- `WebFluxConfigurer#addResourceHandlers`.
- `ResourceHandlerRegistry`.
- Resource chain configuration or custom `ResourceResolver`.
- `spring.mvc.static-path-pattern` or `spring.webflux.static-path-pattern`.
- `spring.mvc.webjars-path-pattern` or `spring.webflux.webjars-path-pattern`.

`@EnableWebMvc` hands MVC configuration control to the application and causes Spring Boot MVC auto-configuration to back off. Similarly, `@EnableWebFlux` causes WebFlux auto-configuration to back off. If either configuration was added to handle another feature, re-check the resource handlers for Swagger UI.

Do not delete all custom MVC configuration just because Swagger UI returns 404. Identify which handler changed the mapping, then restore the exact static/WebJar resource paths the application needs.

### 5.3. Inspecting Artifact Contents

For Spring MVC packaged as an executable JAR, `src/main/webapp` is not an appropriate location for storing Swagger UI or application static resources; this directory is typically ignored when building a JAR. Spring WebFlux does not use `src/main/webapp`. Prefer classpath locations such as `src/main/resources/static` for application-managed static content; springdoc's Swagger UI is packaged inside the WebJar dependency.

Check whether the application JAR contains the WebJar dependency:

~~~bash
jar tf target/application.jar | findstr /i "swagger-ui webjars"
~~~

Executable JARs typically nest dependencies inside `BOOT-INF/lib`. The command above shows which WebJar is packaged. To inspect its contents, grab the Swagger UI JAR from the dependency cache and run:

~~~bash
jar tf swagger-ui-webjar.jar | findstr /i "META-INF/resources/webjars/swagger-ui index.html"
~~~

If the WebJar is missing from the runtime artifact, go back to the dependency tree and dependency scope. If the WebJar is present yet the URL still returns 404, focus on resource mapping, resolvers, or proxy.

Do not add `webjars-locator-core` as a default fix. First determine the Spring Boot version, springdoc version, WebJar locator currently in use, and runtime environment. Some bugs only appear with a specific combination of versions or application servers; adding an arbitrary locator version can introduce new dependency conflicts.

If the application already has a landing page at the root such as `public/index.html`, check whether Swagger UI's default route collides with the welcome page. You can move the UI to a dedicated path, for example `springdoc.swagger-ui.path=/swagger-ui/api-docs.html`.

The Springdoc FAQ also recommends using a dedicated path when the application already owns root content. Keeping the home page at `/` and the UI at a path like `/docs/swagger-ui.html` keeps the welcome page distinct from the Swagger UI entry point.

## 6. Checking Spring Security

If security policy requires authentication for all requests, Swagger UI and static resources can also be blocked. Distinguish:

- 401: unauthenticated or invalid token.
- 403: authenticated but insufficient permissions.
- 302: redirecting to the login page per form login configuration.
- 404: route/resource does not exist or the application intentionally hides the endpoint.

Example protecting documentation with a dedicated authority:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Bean
SecurityFilterChain applicationSecurity(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(
                            "/swagger-ui.html",
                            "/swagger-ui/**",
                            "/webjars/**",
                            "/v3/api-docs/**"
                    ).hasAuthority("DOCS_READ")
                    .anyRequest().authenticated()
            )
            .build();
}
~~~

The example above uses the `DOCS_READ` authority for all documentation. The application needs an authentication mechanism and must grant the corresponding authority. If using custom paths, add the changed UI and OpenAPI document paths to the matchers. If using a context path, Spring Security normally matches paths inside the application, excluding the context path.

If the application has multiple `SecurityFilterChain` beans, check the `securityMatcher` and order of each chain. A request may be handled by a different chain than the one you just edited. Spring Security applies the first rule that matches the request; appending `permitAll` at the end of the list does not override an earlier matching rule. When the browser loads assets under `/webjars/**`, check the matcher for that path separately.

If documentation is permitted to be public, use `permitAll()` on the exact UI/config/spec URLs inside `authorizeHttpRequests` instead of excluding these requests from the security filter chain via `web.ignoring()`. This preserves Spring Security's security headers. For internal documentation, continue requiring an appropriate authority/role as in the example above.

In development environments these docs URLs may be allowed for testing the UI, but in production an access policy appropriate to the data exposed by the OpenAPI document must be applied. Never disable Spring Security entirely to fix a 404.

## 7. Checking Reverse Proxy and URL Prefix

The application may work properly at http://localhost:8080, yet return 404 through Nginx, ingress, or a load balancer.

Example public URL:

~~~text
https://api.example.com/catalog/swagger-ui.html
~~~

While the proxy forwards the request to the application at:

~~~text
http://application:8080/swagger-ui.html
~~~

If the proxy strips `/catalog` without forwarding prefix information properly, springdoc may generate redirects or resource URLs missing the prefix. The browser then requests `/swagger-ui/index.html` at the host root and receives 404.

Check:

1. Does the proxy preserve or strip the `/catalog` prefix?
2. Does the proxy send an appropriate `X-Forwarded-Prefix` or `Forwarded` header?
3. Has the application enabled forwarded-header support properly for its Spring Boot version?
4. Does the redirect `Location` retain the public host, scheme, and prefix?
5. Do JS/CSS and `swagger-config` requests go through the same proxy route?

With Spring Boot 3.x, you can use Spring Framework forwarded header support:

~~~yaml
server:
  forward-headers-strategy: framework
~~~

With Spring Boot 4.x, forwarded header configuration is reorganized under `server.request.header.forwarded`. Example using the Spring Framework strategy and enabling prefix:

~~~yaml
server:
  request:
    header:
      forwarded:
        strategy: framework
        use-prefix: true
~~~

Choose the strategy suited to your proxy and web server. Only trust forwarded headers from trusted proxies; do not configure the application to trust headers sent by any external client.

At the framework API level, the Servlet stack can use `ForwardedHeaderFilter`, while the reactive stack has `ForwardedHeaderTransformer`. Spring Boot can auto-configure forwarded header handling via properties per major version; avoid manually registering an additional filter/transformer if auto-configuration already handles the same function.

If the proxy does not forward the prefix, fix routing at the proxy or configure a consistent public path. Do not alter `springdoc.swagger-ui.path` to compensate for a proxy that strips prefixes incorrectly.

## 8. Checking When Using the Actuator Management Port

If configured:

~~~yaml
springdoc:
  use-management-port: true

management:
  server:
    port: 9090
  endpoints:
    web:
      exposure:
        include:
          - openapi
          - swagger-ui
~~~

then documentation and UI are exposed under the management base path, for example:

~~~text
http://localhost:9090/actuator/openapi
http://localhost:9090/actuator/swagger-ui
~~~

In this mode, regular path properties such as `springdoc.swagger-ui.path` and `springdoc.api-docs.path` are no longer applied in the usual way. If you keep accessing `/swagger-ui.html` on the application port, you may receive 404 even while the OpenAPI endpoint is still working on the management port.

The management port must be configured separately from the application port to use this exposure mode.

Check `management.server.port`, `management.endpoints.web.base-path`, `management.endpoints.web.exposure.include`, and `springdoc.use-management-port` before changing URLs.

### 8.1. Using Actuator Mappings to Confirm Registered Routes

If the application has Actuator and the operations team has authorized access, `/actuator/mappings` helps identify registered handlers and resource mappings:

~~~text
/actuator/mappings
~~~

Look for mappings related to the Swagger UI entry/welcome route, `swagger-config`, OpenAPI JSON, and the resource handler for UI assets. If the API-docs mapping is present but the UI entry route is absent, check the UI starter and auto-configuration conditions. If the entry route exists but assets are not mapped, check static resource/WebJar configuration.

Do not enable `/actuator/mappings` publicly to investigate. The output can reveal endpoint structure and deployment details; protect the endpoint with network policy and Spring Security.

## 9. Diagnostic Procedure with curl

Run these commands against the same host, port, context path, and authentication that the browser uses.

### 9.1. Confirming the OpenAPI Document

~~~bash
curl -i http://localhost:8080/v3/api-docs
~~~

The expected result is HTTP 200 and JSON containing the `openapi`, `info`, and `paths` fields.

### 9.2. Checking the Swagger UI Entry URL

~~~bash
curl -i http://localhost:8080/swagger-ui.html
~~~

If the route exists, the response is usually a redirect (3xx) to the Swagger UI page. Inspect the `Location` header to see the next URL.

Follow redirects:

~~~bash
curl -i -L http://localhost:8080/swagger-ui.html
~~~

If the final response is 404, identify the last URL in the redirect chain. Do not only look at the status of the first request.

### 9.3. Directly Checking index and WebJar Resources

~~~bash
curl -i http://localhost:8080/swagger-ui/index.html
curl -i http://localhost:8080/webjars/swagger-ui/swagger-ui.css
~~~

Actual WebJar URLs may depend on version and resource resolver. Grab the exact URL from the Network tab or returned HTML to test the exact file the browser is requesting.

### 9.4. Checking swagger-config

~~~bash
curl -i http://localhost:8080/v3/api-docs/swagger-config
~~~

The expected response is the UI configuration JSON. Check fields such as `url`, `urls`, `configUrl`, and `oauth2RedirectUrl` if present. If you changed `springdoc.api-docs.path`, verify whether the URL in the config points to the new document.

### 9.5. Checking the Entire Chain with Header-Only Requests

~~~bash
curl -sS -D - -o /dev/null http://localhost:8080/swagger-ui.html
curl -sS -L -D - -o /dev/null http://localhost:8080/swagger-ui.html
curl -sS -D - -o /dev/null http://localhost:8080/swagger-ui/index.html
curl -sS -D - -o /dev/null http://localhost:8080/v3/api-docs/swagger-config
~~~

Compare status, `Location`, `Content-Type`, and final URL. If using context path `/catalog`, prepend that prefix to each request.

## 10. Checking in Browser DevTools

Open Developer Tools → Network, enable Preserve log and Disable cache, then reload the Swagger UI page.

Filter by Doc, JS, CSS and inspect:

- First request to /swagger-ui.html.
- Redirect chain and Location.
- Request for index.html.
- Requests for .js, .css, favicon.
- Request for /v3/api-docs/swagger-config.
- Request for OpenAPI JSON/YAML.

Cross-check the Status and Initiator columns:

| Observation | Likely conclusion |
|---|---|
| HTML entry 404 | UI route or path/context is wrong |
| HTML entry 302, index 404 | Static/WebJar mapping or proxy prefix is wrong |
| HTML 200, JS/CSS 404 | Resource URL is not being served |
| JS/CSS 200, config 404 | configUrl or API docs path is wrong |
| Config 200, spec 404 | url/urls in config is wrong |
| Requests 401/403 | Security policy |
| Local works, public URL fails | Reverse proxy/ingress/base path |

If the browser receives an HTML login page with status 200 or 302 instead of JSON at `swagger-config`, check authentication redirects. An HTML response is not a valid OpenAPI config.

## 11. Enabling Logs to Identify the Request Handler

In a test environment, you can enable Spring MVC resource handler logs:

~~~yaml
logging:
  level:
    org.springframework.web.servlet.DispatcherServlet: DEBUG
    org.springframework.web.servlet.handler: TRACE
    org.springframework.web.servlet.resource: TRACE
~~~

If the application uses WebFlux, enable logging for the corresponding reactive handler/resource packages:

~~~yaml
logging:
  level:
    org.springframework.web.reactive.DispatcherHandler: DEBUG
    org.springframework.web.reactive.handler: TRACE
    org.springframework.web.reactive.resource: TRACE
~~~

Look for this information:

- Which controller is the request mapped to?
- Is the request mapped to `ResourceHttpRequestHandler`?
- Which classpath locations is the resource handler searching?
- Is the resource resolved from a WebJar?
- Is there a `NoResourceFoundException` or `NoHandlerFoundException`?
- Is the request rejected or redirected by a security filter?

After identifying the issue, turn off TRACE in production if unnecessary because logs can become very verbose.

## 12. MockMvc Regression Test

You should have an integration test confirming that both the OpenAPI endpoint and the Swagger UI entry remain served after upgrading Spring Boot or springdoc.

Example with Spring MVC:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class SwaggerUiAvailabilityTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void openApiDocumentIsAvailable() throws Exception {
        mockMvc.perform(get("/v3/api-docs"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.openapi").exists())
                .andExpect(jsonPath("$.paths").exists());
    }

    @Test
    void swaggerUiEntryRedirectsToItsPage() throws Exception {
        mockMvc.perform(get("/swagger-ui.html"))
                .andExpect(status().is3xxRedirection())
                .andExpect(header().exists("Location"));
    }

    @Test
    void swaggerUiIndexIsAvailable() throws Exception {
        mockMvc.perform(get("/swagger-ui/index.html"))
                .andExpect(status().isOk());
    }

    @Test
    void swaggerUiConfigurationIsAvailable() throws Exception {
        mockMvc.perform(get("/v3/api-docs/swagger-config"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.url").exists());
    }
}
~~~

This example assumes default paths, the MVC UI starter, and no security policy blocking requests in tests. If the application uses a context path, custom UI path, custom `configUrl`, or security, adjust the requests and add appropriate authentication.

`/swagger-ui.html` may redirect to an internal URL that varies by configuration/version; tests should verify that a redirect occurs and the index resource works, rather than hardcoding the entire query string in `Location`.

If docs are protected, add tests for authorized and unauthorized users. The example below assumes security policy returns 401 when a request is unauthenticated; if the application uses form login or intentionally hides routes, adjust assertions to match actual policy:

~~~java
import org.springframework.security.test.context.support.WithMockUser;

@Test
@WithMockUser(authorities = "DOCS_READ")
void apiDocsAreAvailableToDeveloper() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isOk());
}

@Test
void apiDocsAreNotAvailableWithoutAuthentication() throws Exception {
    mockMvc.perform(get("/v3/api-docs"))
            .andExpect(status().isUnauthorized());
}
~~~

Test the entry point, `swagger-config`, assets, and document separately. One permitted request does not prove every URL in the UI loading chain is permitted.

MockMvc tests handlers and resource mappings inside the application context. It does not test reverse proxies, DNS, TLS termination, or ingress routing; add a smoke test via the public URL after deployment.

## 13. Common Errors and Fixes

| Error | Cause | How to fix |
|---|---|---|
| Only springdoc-openapi-starter-webmvc-api present | Starter only generates OpenAPI document | Add springdoc-openapi-starter-webmvc-ui |
| Using MVC UI starter for WebFlux | Starter does not match web stack | Choose springdoc-openapi-starter-webflux-ui |
| Build has UI starter but production still 404 | Old runtime artifact/container image or dependency excluded from runtime | Check runtime dependency tree, BOOT-INF/lib, and deployed image |
| springdoc.swagger-ui.enabled=false | UI disabled in profile or environment | Enable UI where needed and check effective properties |
| Visiting old URL after changing springdoc.swagger-ui.path | UI entry moved to another path | Open the right custom path |
| Ignoring server.servlet.context-path | Missing context prefix | Add context path to the URL |
| spring.mvc.static-path-pattern changed to /assets/** | Swagger UI static resources do not match mapping | Restore /** or redesign static mappings |
| spring.web.resources.add-mappings=false | Static resources disabled | Re-enable if serving Swagger UI is needed |
| @EnableWebMvc or custom resource handler | Boot MVC auto-configuration no longer manages mappings as before | Review resource handlers and WebJar locations |
| Missing WebJar in runtime artifact | Dependency scope/exclusion or wrong starter | Fix dependency and inspect packaged JAR |
| Proxy strips prefix without forwarding prefix | Redirect/resource URLs missing base path | Align proxy route and forwarded-header strategy |
| springdoc.use-management-port=true | UI moved to management port/base path | Open /actuator/swagger-ui on the management port |
| Security blocks static resources | UI/index/config not permitted | Update matchers to match docs policy |
| UI loads but config URL 404 | configUrl or API docs path mismatch | Check swagger-config and related properties |
| src/main/webapp contains resources in JAR-packaged app | Directory contents not packaged as expected | Place resources in classpath static locations or use appropriate WAR |
| Fails only through gateway | Rewrite/strip prefix or forwarded headers mismatch | Compare Location, request path, and headers between public URL and app |
| Mapping missing in Actuator | Auto-configuration did not create route or profile/condition unmet | Check /actuator/mappings and condition report in a protected environment |

## 14. Step-by-Step Troubleshooting Procedure

1. **Confirm the exact URL**: check context path, custom UI path, management port, and proxy prefix.
2. **Confirm the exact dependency**: use the UI starter matching MVC/WebFlux and the Spring Boot major version.
3. **Check effective properties**: `springdoc.swagger-ui.enabled`, `springdoc.swagger-ui.path`, `springdoc.api-docs.path`, and profiles.
4. **Follow redirects**: record the URL in `Location`, do not just look at the status of `/swagger-ui.html`.
5. **Check the index resource**: call `/swagger-ui/index.html` directly.
6. **Check the WebJar**: inspect the dependency tree and JAR contents.
7. **Check static mappings**: `static-path-pattern`, `static-locations`, `add-mappings`, `WebMvcConfigurer`, and `@EnableWebMvc`.
8. **Check security**: distinguish 401/403/302 from an actual 404.
9. **Check config**: fetch `/v3/api-docs/swagger-config`, confirm which OpenAPI URL is pointed to.
10. **Check proxy**: compare localhost and public URL requests, forwarded headers, and prefixes.
11. **Check mapping logs**: determine which handler/resource resolver returns 404.
12. **Add regression tests**: verify OpenAPI, Swagger UI entry, index, and `swagger-config`.

Do not add dependencies or bulk-change resource configurations before identifying which specific request returns 404. Fix the exact layer causing the error, then re-run the entire request chain.

## 15. Review Checklist

- [ ] /v3/api-docs returns HTTP 200.
- [ ] Dependency includes the UI starter matching Spring MVC or WebFlux.
- [ ] springdoc major version is compatible with Spring Boot.
- [ ] `springdoc.swagger-ui.enabled` has an effective value of `true`.
- [ ] UI URL matches `springdoc.swagger-ui.path`.
- [ ] Context path/base path is included in the URL.
- [ ] /swagger-ui.html redirects to a valid URL.
- [ ] /swagger-ui/index.html returns HTTP 200.
- [ ] JavaScript, CSS, and WebJar resources return HTTP 200.
- [ ] /v3/api-docs/swagger-config returns valid JSON.
- [ ] `url` or `urls` points to an accessible OpenAPI document.
- [ ] Static resource mapping is not disabled or moved away from Swagger/WebJar paths.
- [ ] Runtime JAR contains the Swagger UI WebJar dependency.
- [ ] Security rules for UI, WebJars, and docs align with policy.
- [ ] Reverse proxy passes prefix/forwarded headers properly.
- [ ] If using the management port, the UI is opened under the Actuator path.
- [ ] MockMvc test and smoke test via public URL are in place.
