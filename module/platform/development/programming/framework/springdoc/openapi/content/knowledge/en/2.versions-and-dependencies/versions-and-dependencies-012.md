# Choosing the Documentation Guide Matching Your Deployed Version

When using springdoc-openapi, select documentation guides according to your application's actual Spring Boot and springdoc versions. The latest documentation page may describe APIs, starters, packages, or configurations that do not exist in the running release. Following guides from a different major version can lead to incompatible dependencies, nonexistent imports, or unsupported configurations.

The right workflow starts by identifying the resolved dependencies in the build and runtime, then matching them against the official compatibility table. Next, open the matching v1, v2, or v3 documentation branch, check release notes for the exact version, and verify against the OpenAPI document generated by the application.

## 1. Distinguishing Application Versions from Documentation Versions

A Spring Boot project involves multiple related versions:

| Component | Role | Where Typically Defined |
|---|---|---|
| Java/JDK | Compiles and runs the application | Toolchain, compiler config, runtime image |
| Spring Boot | Manages platform and dependencies | Maven parent/BOM or Gradle plugin/platform |
| Spring Framework | MVC, WebFlux, DI, binding, and core APIs | Usually managed by Spring Boot BOM |
| springdoc-openapi | Generates OpenAPI document and integrates Swagger UI | Direct dependency or starter |
| Swagger Core | OpenAPI models and annotations | Transitive dependency from springdoc |
| Jackson | JSON conversion and metadata serialization | Usually managed by Spring Boot |
| OpenAPI Specification | Format version of the generated document | openapi field in JSON/YAML |
| API info.version | API version published by the product team | OpenAPIDefinition or configuration |

Three values are commonly confused:

- Spring Boot version determines the application platform.
- springdoc version determines the library line generating documentation.
- OpenAPI version determines the specification version the JSON/YAML file complies with.

For example, an application can run Spring Boot 3.5, use springdoc 2.10, and generate a document conforming to OpenAPI 3.1. The info.version value might be 2026.11 or 1.4.0 by product convention; it is not the springdoc version.

## 2. Identifying Actual Versions Before Opening Documentation

Do not just look at one version line in pom.xml or build.gradle. Versions can be managed in a parent, BOM, version catalog, plugin, dependency constraint, or changed by dependency resolution.

At a minimum, record:

- Resolved Spring Boot version.
- Resolved springdoc version on runtimeClasspath.
- Java toolchain and JDK running the application.
- Spring MVC or Spring WebFlux.
- Whether the starter includes Swagger UI or only provides OpenAPI API endpoints.
- Additional springdoc modules in use.

With Maven, check Spring Boot and springdoc versions in the dependency tree:

~~~bash
./mvnw dependency:tree -Dincludes=org.springframework.boot,org.springdoc
~~~

To see all dependencies related to Spring and Swagger Core:

~~~bash
./mvnw dependency:tree -Dincludes=org.springframework,org.springdoc,io.swagger.core.v3
~~~

To inspect the POM configuration after parent inheritance, profiles, and properties are applied:

~~~bash
./mvnw help:effective-pom
~~~

With Gradle:

~~~bash
./gradlew dependencyInsight --dependency springdoc-openapi --configuration runtimeClasspath
~~~

Also check Spring Boot:

~~~bash
./gradlew dependencyInsight --dependency spring-boot --configuration runtimeClasspath
~~~

If dependencies are declared via a version catalog, the catalog shows the requested version; dependencyInsight shows the actual version selected by Gradle after resolution.

## 3. Spring Boot and springdoc Compatibility Table

The table below summarizes compatible lines published in Springdoc documentation at the time of writing, 20-11-2026. Open the official table before each upgrade because support ranges and patch versions may change.

| Spring Boot | Published compatible springdoc line |
|---|---|
| 4.1.x | 3.1.x to 3.2.x |
| 4.0.x | 3.0.x |
| 3.5.x | 2.8.x to 2.10.x |
| 3.4.x | 2.7.x to 2.8.x |
| 3.3.x | 2.6.x |
| 3.2.x | 2.3.x to 2.5.x |
| 3.1.x | 2.2.x |
| 3.0.x | 2.0.x to 2.1.x |
| 2.7.x and certain older Boot 1.5.x platforms | 1.6.0 and above per v1 table |
| 2.6.x and certain older Boot 1.5.x platforms | 1.6.0 and above per v1 table |
| 2.5.x | 1.5.9 and above |
| 2.4.x | 1.5.0 and above |
| 2.3.x | 1.4.0 and above |
| 2.2.x | 1.2.1 and above |
| 2.0.x | 1.0.0 and above |

General major rule:

- Spring Boot 2 and older Boot 1 apps belong to the Springdoc v1 line.
- Spring Boot 3 belongs to the Springdoc v2 line.
- Spring Boot 4 belongs to the Springdoc v3 line.

Do not assume every patch version within the same major is equally compatible. The detailed minor-by-minor table above matters when choosing a version for a deployed application.

## 4. Note When the Compatibility Table Does Not Yet List a New Boot Version

At the time of writing, the Spring Boot site lists 4.2.0 as a stable release. However, the Springdoc compatibility table lists Boot 4.1.x and 4.0.x without a 4.2.x row yet.

This is not enough evidence to conclude springdoc 3.2.x has been tested with Boot 4.2.0. Do not extrapolate the 4.1.x range to 4.2.x just because they share the same major.

When encountering a version not yet in the table:

1. Re-check the compatibility matrix page and last-updated date.
2. Look for official release notes or issues confirming support for that version.
3. Check the Spring Framework and Java baselines of the new Spring Boot version.
4. If testing is needed, create a separate test branch and verify startup, OpenAPI JSON, Swagger UI, and integration tests.
5. Clearly mark the combination as experimental if no official confirmation exists.
6. Choose an officially supported combination for production when operational requirements demand confirmed compatibility.

Do not use Snapshot lines as evidence for a stable release. Snapshots can change and do not carry the same compatibility commitment as official releases.

## 5. Choosing the Right Documentation Branch: v1, v2, or v3

Springdoc maintains documentation by major version. Use the page matching the running dependency:

| Library Line | Primary Platform | Documentation to Open |
|---|---|---|
| Springdoc v1 | Legacy Spring Boot 1/2 | https://springdoc.org/v1/ |
| Springdoc v2 | Spring Boot 3 | https://springdoc.org/v2/ |
| Springdoc v3 | Spring Boot 4 | https://springdoc.org/ |

The main documentation page may be updated to describe the current major version. If the application still uses v1 or v2, navigate to the versioned documentation branch rather than copying dependencies or code samples from the latest page.

Documentation types to consult:

- Getting started: starters and minimal configuration.
- Modules: MVC, WebFlux, UI, API-only, and add-ons.
- Migration guide: changes across major versions.
- FAQ: known issues and resolutions per library line.
- Configuration properties: property names, data types, and defaults.
- Release notes: changes in specific patches/minors.
- Javadoc/API reference: packages, classes, and methods for the exact version.

## 6. Examples of Choosing Documentation by Running Version

### Case A: Spring Boot 3.5.x

If the dependency tree shows Spring Boot 3.5.x and springdoc 2.9.x:

1. Choose Springdoc v2 documentation.
2. Use the compatibility table to confirm 2.9.x is in the supported range for Boot 3.5.x.
3. Read starter and configuration sections at https://springdoc.org/v2/.
4. When encountering API differences, open release notes for the exact 2.9.x patch.
5. Do not take imports or v3 migration examples before upgrading to Boot 4.

### Case B: Spring Boot 4.0.x

If the application uses Boot 4.0.x:

1. Choose Springdoc v3 per the compatibility table.
2. Use current documentation at https://springdoc.org/.
3. Check v3 starters and packages.
4. Read the migration guide if source was upgraded from v2.
5. Check Spring Boot 4 platform changes alongside Springdoc changes.

### Case C: Spring Boot 2.7.x

If a legacy application still uses Boot 2.7.x:

1. Choose a compatible Springdoc v1 line.
2. Open https://springdoc.org/v1/.
3. Do not copy v2 or v3 starters into a Boot 2 application.
4. If planning a Boot 3 upgrade, follow a dedicated migration roadmap and verify javax-to-jakarta changes.

## 7. Identifying the Right Web Stack Before Picking Examples

After choosing the right major version, choose the right integration branch:

| Web Stack | Swagger UI Needed | OpenAPI Document Only |
|---|---|---|
| Spring MVC | WebMVC UI starter matching major | Corresponding WebMVC API starter |
| Spring WebFlux | WebFlux UI starter matching major | Corresponding WebFlux API starter |

Example on the v2 line:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.x.y</version>
</dependency>
~~~

This example is for Spring MVC with Swagger UI. For WebFlux, use the WebFlux UI starter. If no UI is needed, select the corresponding API-only starter.

Do not combine WebMVC and WebFlux starters together just to experiment. If the application has both spring-boot-starter-web and spring-boot-starter-webflux, determine which application context type Spring Boot actually selects.

Artifact names and packages can change across major versions. Read the modules and migration sections of the matching branch before copying dependencies.

## 8. Distinguishing Major-Version Documentation from Patch Release Notes

Major-version documentation explains the overall API and architecture of the library line. Patch/minor release notes tell you:

- Which bugs were fixed.
- Which framework or JDK versions gained support.
- Which transitive dependencies were upgraded.
- Which properties or defaults changed.
- Which classes, methods, or packages were added, renamed, or removed.
- Any workarounds or breaking behaviors to watch out for.

For example, if a project uses springdoc 2.8.6, the v2 page is the baseline documentation. When investigating a bug that only appeared from 2.8.5 to 2.8.6, read the changelogs/releases for 2.8.5 and 2.8.6 instead of only re-reading getting started.

Do not treat an old blog post or forum answer as a substitute for official release notes. If you must use a community workaround, verify it on your running version and document its limits.

## 9. Checking Resolved Dependency Versions in Maven

A POM may declare a version via a property:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springdoc</groupId>
        <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
        <version>2.x.y</version>
    </dependency>
</dependencies>
~~~

2.x.y is only a placeholder. Use a specific version confirmed compatible or managed via your organization's BOM/catalog.

Inspect actual resolved dependencies:

~~~bash
./mvnw dependency:tree -Dincludes=org.springdoc
~~~

If the version is overridden by dependencyManagement or profiles, inspect the effective POM:

~~~bash
./mvnw help:effective-pom
~~~

If multiple Springdoc artifacts from different majors appear together, trace which dependency pulls them in and resolve it before relying on single-version documentation.

## 10. Checking Resolved Versions in Gradle

With Gradle, the version declared in build.gradle or libs.versions.toml may differ from the final version due to constraints, platforms, or conflict resolution.

Check:

~~~bash
./gradlew dependencyInsight --dependency springdoc-openapi --configuration runtimeClasspath
~~~

View all runtime dependencies:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
~~~

If the application has multiple source sets or modules, use the configuration matching where the running code resides. For example, testRuntimeClasspath dependencies do not necessarily match runtimeClasspath.

Once you find the resolved version, pick the matching major documentation and read the corresponding release notes.

## 11. Identifying Versions Inside Packaged Artifacts

Your workspace's dependency tree may differ from the artifact running in a container or server.

If the application uses an executable JAR, inspect its contents:

~~~bash
jar tf application.jar
~~~

Look for nested JARs in BOOT-INF/lib, for example:

~~~text
BOOT-INF/lib/springdoc-openapi-starter-webmvc-ui-2.x.y.jar
BOOT-INF/lib/springdoc-openapi-starter-common-2.x.y.jar
~~~

File names give a quick signal of packaged versions. For WAR deployments, container images, or external dependency layers, inspect the actual deployed artifact and runtime classpath.

Do not judge solely from the source POM if production runs an image built from a different commit or lockfile.

## 12. Choosing the Right Docs on Compile Errors

Compile errors usually indicate source code uses a different API than the resolved dependency:

| Symptom | Where to Check |
|---|---|
| Package import does not exist | Compare code packages with Javadoc of the exact major |
| Method not found | Check API signature of the resolved release |
| Starter fails to resolve | Check artifact name and major version |
| Annotations not recognized | Check Swagger Core dependency and annotation package |
| Property config has no effect | Check property reference for the exact version |

For example, a class may have changed packages between v1 and v2. Look up the class in the Javadoc/API reference of the exact version rather than changing imports based on a guide for a different major.

Do not fix errors by randomly adding an older Swagger Core or Springdoc dependency onto the classpath. That can let the build pass while causing linkage errors at runtime.

## 13. Choosing the Right Docs When Errors Only Appear at Runtime

If compilation succeeds yet the app fails at startup or when calling /v3/api-docs:

1. Confirm the resolved Springdoc version on runtimeClasspath.
2. Verify Spring Boot and Spring Framework are within supported ranges.
3. Inspect the dependency tree for mixed major versions or overridden Swagger Core.
4. Read the FAQ and release notes for the matching documentation branch.
5. Inspect auto-configuration logs and class loading errors.
6. Reproduce with a minimal configuration before adding customizers or secondary modules.

Errors like NoSuchMethodError, NoClassDefFoundError, or ClassNotFoundException are usually tied to mismatched APIs/classpaths. Read docs for the exact dependency being loaded, not just the directly declared version.

## 14. Distinguishing OpenAPI Document Versions from springdoc

The default endpoint is usually:

~~~text
/v3/api-docs
~~~

In the returned JSON, the openapi field indicates the specification version:

~~~json
{
  "openapi": "3.1.0",
  "info": {
    "title": "Order API",
    "version": "1.0.0"
  }
}
~~~

This example contains three distinct values:

- 3.1.0 is the OpenAPI Specification version.
- 1.0.0 is the API version published by the product team.
- The springdoc version is the dependency version in the build, not present in either field above.

Do not pick Springdoc v3 docs just because JSON says openapi: 3.1.0. The springdoc major is chosen based on compatibility with Spring Boot and actual dependencies.

## 15. Do Not Use Migration Guides Instead of Daily Configuration Guides

Migration guides are meant for transitions across majors or large API changes. Once an application runs stably on a line:

- Use getting started/configuration of that major for day-to-day setup.
- Use the FAQ to investigate known issues.
- Use release notes when upgrading patches/minors.
- Use the migration guide when changing majors.
- Use Javadoc/API reference when verifying a specific class or method.

Do not apply an entire migration guide to a project that is not migrating. Some changes are only required during platform transitions and can cause unnecessary churn in existing code.

## 16. Cross-Checking Java and Spring Framework Requirements

The Springdoc/Spring Boot compatibility table does not replace Spring Boot's platform requirements.

Before upgrading:

- Check minimum and maximum supported Java versions for Spring Boot.
- Check the Spring Framework version managed by Boot's BOM.
- Check Maven/Gradle versions.
- Check the servlet container or web runtime if deploying a WAR.
- Check whether third-party libraries support the Jakarta namespace or Spring Framework changes.

For instance, Spring Boot 4.x uses Spring Framework 7.x and requires at least Java 17 per system requirements. If an add-on library only supports Spring Framework 6, picking a matrix-matched Springdoc alone is not enough to guarantee full application compatibility.

## 17. Keeping Dependency Management Consistent

In Maven, prefer the Spring Boot parent or dependency management to keep Spring Framework and platform libraries on a unified version set. Manage springdoc in one explicit property or dependencyManagement entry.

In Gradle, use a version catalog, platform/BOM, and dependency constraints per project conventions. Do not declare the same dependency with multiple versions across modules without a unified resolution policy.

Avoid arbitrary overrides of:

- Spring Framework modules.
- Swagger Core.
- Jackson.
- Servlet API or Jakarta API.
- Transitive springdoc modules.

If an override is required for a confirmed bug, document the cause, scope, forced version, and regression test. Do not add an older dependency solely to silence a compile error.

## 18. Checking the Right Documentation for MVC, WebFlux, and UI/API-Only

Having the right major version is still not enough if you open the guide for the wrong stack.

Confirm:

- Whether the app uses Spring MVC or WebFlux.
- Whether Swagger UI is needed or only JSON/YAML.
- Whether Spring Data REST, HATEOAS, security, or other integration modules are used.
- Whether docs endpoints sit behind a context path or reverse proxy.

Within your chosen documentation branch, open the corresponding module section. Do not copy an MVC dependency into a WebFlux app just because the example is at the top of the page.

## 19. Verifying the Generated Document After Picking the Right Docs

After configuring according to version-matched docs, start the application and fetch the document:

~~~bash
curl -fS http://localhost:8080/v3/api-docs -o openapi.json
~~~

Inspect the structure:

~~~bash
jq '{openapi, info, paths: (.paths | keys)}' openapi.json
~~~

If using Swagger UI, verify the UI loads both configuration and the OpenAPI document. If using only an API-only starter, do not expect UI assets to be present.

Also check:

- Paths and HTTP methods.
- Request/response schemas.
- Parameter names and locations.
- Security schemes and requirements.
- Response statuses and media types.
- Grouped documents if configured.
- Server URLs when running behind a gateway.

Even a version-matched guide does not guarantee your app config is right; runtime output is the final verification step.

## 20. Managing Snapshots and Prereleases

Snapshots, milestones, or release candidates fit cases where you need to test features not yet in a stable release or verify compatibility with a new platform.

Before using a prerelease:

1. Clearly state why testing is needed.
2. Read release notes for that exact milestone/RC.
3. Isolate in a test branch or sandbox environment.
4. Do not mix snapshots and stable modules of the same major without guidance.
5. Run build, startup, OpenAPI generation, and integration tests.
6. Record the prerelease version in artifact and deployment metadata.
7. Replace with a stable release once a suitable one is available.

Do not use snapshots as production dependencies just because they are newer. Snapshots can change without maintaining binary or configuration compatibility.

## 21. Complete Version Selection Workflow Example

Suppose dependencyInsight shows:

~~~text
Spring Boot: 3.5.x
Spring Framework: 6.2.x
springdoc-openapi: 2.9.x
Web stack: Spring MVC
UI: enabled
~~~

Workflow:

1. Cross-check Boot 3.5.x against the compatibility table and confirm springdoc 2.9.x is within the published range.
2. Open v2 documentation at https://springdoc.org/v2/.
3. Select the WebMVC UI section since the app uses MVC and needs Swagger UI.
4. Read v2 configuration properties before changing paths or UI behavior.
5. If errors occur, open the v2 FAQ and 2.9.x release notes.
6. After configuring, fetch /v3/api-docs and verify paths, schemas, and security.
7. Archive contract test results alongside the build artifact.

If the application is upgraded to Boot 4, re-evaluate the whole process: move to the springdoc v3 line per the compatibility table, read v3 docs, audit starters/packages, and check Spring Boot migrations.

## 22. Common Mistakes When Choosing Wrong Documentation

| Mistake | Why It Happens | Fix |
|---|---|---|
| Copying v3 dependencies into Boot 3 | Picked the current landing page without checking major | Cross-check Boot version and pick v2 |
| Using v2 examples in Boot 4 | Code sample belongs to Springdoc v2 | Open v3 docs and migration guide |
| Using v1 docs for v2 starters | Older page has different packages/artifacts | Open /v2 and check resolved dependencies |
| Picking latest patch unsupported by Boot minor | Compared majors only | Use the detailed minor compatibility matrix |
| Using Snapshot docs for stable | Confused prerelease with stable | Open release notes and pick matching stable |
| Compiles yet runtime linkage error | Mixed or overridden dependency graph | Inspect runtime dependency tree and classpath |
| Swagger UI missing | Using API-only starter | Pick UI starter if an interface is needed |
| UI loads but document misses operations | Wrong filter, stack, or customizer | Check config and OpenAPI JSON |
| Local works, production fails | Different artifact or dependencies deployed | Inspect deployed JAR/image and runtime classpath |

## 23. Checklist Before Applying Any Guide

- [ ] Identified actual Spring Boot version.
- [ ] Identified actual springdoc version on runtimeClasspath.
- [ ] Checked Java and Spring Framework requirements.
- [ ] Cross-checked the right row in the compatibility matrix.
- [ ] Opened the right v1, v2, or v3 documentation branch.
- [ ] Selected the right MVC/WebFlux and UI/API-only option.
- [ ] Dependency examples use the right artifact and major version.
- [ ] Properties and APIs confirmed in docs for the active version.
- [ ] Release notes read when changing patches/minors.
- [ ] Migration guide used when changing majors.
- [ ] No multiple Springdoc majors or Swagger Core versions mixed.
- [ ] OpenAPI JSON fetched and inspected after changes.
- [ ] Integration/contract tests confirm document and runtime behavior.
- [ ] Production artifact verified to match the tested build.

## 24. Principles for Maintaining Version-Matched Documentation

- Record Spring Boot, Java, and springdoc versions in build/release records.
- Save the dependency tree or SBOM of deployed artifacts.
- Link to versioned documentation in the project's internal guides.
- Do not use the latest page as the sole reference for legacy systems.
- When upgrading versions, check the compatibility matrix first, release notes second, and migration guides if changing majors.
- Update internal code samples after verifying against the real version.
- Mark clearly what is officially supported stable versus newly experimental.
- Re-check documentation when dependencies change via BOM or platform.

## Conclusion

Selecting Springdoc documentation starts from the Spring Boot and springdoc versions resolved at runtime, not from the first search result or the latest version number. Match the minor line in the compatibility matrix, open the right v1, v2, or v3 branch, and then select the matching MVC/WebFlux and UI/API-only sections. When the table does not yet list a new Boot version, do not infer compatibility; look for official confirmation or mark the combination experimental. Finally, inspect the dependency graph, read release notes or migration guides within scope, and verify OpenAPI JSON alongside runtime behavior. This keeps guides, source code, and deployed artifacts aligned on one version of truth.
