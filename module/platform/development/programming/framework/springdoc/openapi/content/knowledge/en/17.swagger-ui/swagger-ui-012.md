# Request Interceptor, Response Interceptor, and Customization Limits

## 1. What problem do interceptors in Swagger UI solve?

Swagger UI lets users read OpenAPI documents and send test requests directly from the browser. In some projects, development teams need to add behavior on the documentation UI side, such as:

- Adding a header identifying requests sent from Swagger UI.
- Attaching an access token provided by a developer portal's login mechanism.
- Recording response status codes to aid diagnostics.
- Standardizing or supplementing information displayed in the API testing UI.
- Performing a common step before Swagger UI dispatches a request or after receiving a response.

Swagger UI provides two JavaScript callbacks for those scenarios:

- **requestInterceptor** receives the request Swagger UI is about to send, allowing it to inspect or modify the request before dispatch.
- **responseInterceptor** receives the response after the request completes at the HTTP layer, allowing it to inspect or modify the response object before the UI consumes it.

These are hooks running in the documentation viewer's browser. They do not alter Spring Boot controllers, do not replace Spring Security, and do not automatically edit the OpenAPI contract generated by Springdoc.

With Springdoc OpenAPI, configuring Swagger UI endpoints and installing interceptor callbacks are two separate tasks. Springdoc properties can configure the UI path or OpenAPI document loading URL; callbacks are JavaScript functions and must be supplied in Swagger UI initialization or via the corresponding UI customization mechanism.

## 2. How does requestInterceptor work?

requestInterceptor is a function receiving the request object prepared for sending by Swagger Client. The function can inspect method, URL, headers, or body, then return the modified request.

For example, adding a header to identify API testing calls:

~~~javascript
const requestInterceptor = (request) => {
  request.headers = request.headers || {};
  request.headers["X-Request-Source"] = "swagger-ui";
  return request;
};
~~~

When the callback is configured in Swagger UI, matching requests carry the extra X-Request-Source header. The backend can use this header for diagnostics or traffic classification if system policy allows.

Never treat a browser-sent header as trustworthy authentication proof. Any HTTP client can manually add the same header. When identity or permissions must be verified, use genuine authentication and authorization mechanisms.

requestInterceptor can also add a header conditionally:

~~~javascript
const requestInterceptor = (request) => {
  request.headers = request.headers || {};

  if (request.method === "GET") {
    request.headers["X-Read-Source"] = "api-docs";
  }

  return request;
};
~~~

Check method letter casing and how the library normalizes requests in your Swagger UI version. If logic depends on the URL, match against explicit origins/paths rather than attaching sensitive headers to every destination.

## 3. Adding interceptors to Swagger UI initialization

Swagger UI accepts configuration through an object passed to SwaggerUIBundle. requestInterceptor and responseInterceptor are JavaScript callbacks inside that configuration object.

Initialization example:

~~~javascript
const ui = SwaggerUIBundle({
  url: "/v3/api-docs",
  dom_id: "#swagger-ui",
  deepLinking: true,

  requestInterceptor: (request) => {
    request.headers = request.headers || {};
    request.headers["X-Request-Source"] = "swagger-ui";
    return request;
  },

  responseInterceptor: (response) => {
    return response;
  }
});

window.ui = ui;
~~~

This is an illustrative configuration snippet to place in the Swagger UI initialization JavaScript. It is not a full index.html file; a real custom page must also load the proper CSS, JavaScript bundle, presets, plugins, and UI settings used by the application.

When integrating with Springdoc, preserve the configuration values provided by the default page or swagger-config. Replacing the entire initialization page can accidentally drop document URLs, OAuth redirects, presets, or other settings.

## 4. Springdoc config and JavaScript callbacks are two different layers

Springdoc can configure the Swagger UI path and document URL via application.yml:

~~~yaml
springdoc:
  swagger-ui:
    path: /docs
    config-url: /v3/api-docs/swagger-config
~~~

In this example:

- path changes the Swagger UI interface path.
- config-url specifies the Swagger UI configuration endpoint.
- swagger-config contains data-shaped configuration supplied by Springdoc to the UI.

These properties cannot declare a JavaScript function on their own. JSON cannot represent a function in a way Swagger UI can invoke as a callback. Therefore, you cannot simply put a requestInterceptor function name as a string in application.yml and expect Swagger UI to execute it.

To install interceptors, the application must supply callbacks inside Swagger UI's initialization JavaScript. Depending on the Springdoc version, you can use a custom index.html page or an extension point to transform the generated page. Check customization mechanics against the exact springdoc-openapi version in use.

Do not confuse springdoc.swagger-ui.path and springdoc.swagger-ui.config-url with requestInterceptor. The first two control where the UI loads the page/configuration; interceptors control Swagger Client behavior in the browser.

## 5. Customizing index.html while preserving default settings

A common way to supply callbacks is using a customized Swagger UI page and passing interceptors into SwaggerUIBundle. When doing so:

1. Identify the Swagger UI page served by Springdoc in the current version.
2. Use the override or transformer mechanism supported by that Springdoc version.
3. Keep the right paths to swagger-ui-bundle.js and stylesheets.
4. Keep URL or configUrl settings to load OpenAPI documents.
5. Add requestInterceptor and responseInterceptor.
6. Verify OAuth redirects, the group selector, deep linking, and Try it out after the change.

Do not copy an index.html from another Swagger UI version and keep it indefinitely without verification. Static assets and initialization structure can change when upgrading springdoc-openapi or swagger-ui.

If you only need to change the title, document paths, or options directly supported by Springdoc, use application properties. Only override the initialization page when JavaScript callbacks or UI behaviors not expressible via config properties are required.

## 6. How does responseInterceptor work?

responseInterceptor receives the response object after Swagger Client receives the HTTP result. The callback can inspect status, headers, or response content, then return the response for Swagger UI to continue processing.

Example logging status codes:

~~~javascript
const responseInterceptor = (response) => {
  if (response.status >= 400) {
    console.info("Swagger UI received an HTTP error", response.status);
  }

  return response;
};
~~~

This callback only logs status codes. It does not change the response sent by the server and does not handle every network error automatically. If the browser receives no HTTP response due to DNS, TLS, CORS, or dropped connections, there may be no response object for the callback to process.

You can read diagnostic headers:

~~~javascript
const responseInterceptor = (response) => {
  const traceId = response.headers?.["x-trace-id"];

  if (traceId) {
    console.info("API trace:", traceId);
  }

  return response;
};
~~~

Header names in the JavaScript object depend on how Swagger Client normalizes headers. Inspect the actual response object in your running version before relying on a specific property spelling.

Never log response bodies containing personal data, tokens, account details, or sensitive business data to the console or analytics systems.

## 7. What happens when modifying the response object?

responseInterceptor can return a modified response. Because Swagger UI continues using that object, altering status, headers, or body can affect what the UI displays.

Example adding a client-side field for debugging:

~~~javascript
const responseInterceptor = (response) => {
  response.swaggerUiObserved = true;
  return response;
};
~~~

The swaggerUiObserved field exists only on the response object in the browser. It is never sent back to the server and does not appear in the original HTTP response.

If modifying the body, understand precisely which response properties Swagger UI reads. Altering the structure can make the displayed response stop reflecting the true payload. For an API testing UI, keep responses unmodified unless there is a clear reason to transform them.

Interceptors should also never be used to hide error statuses or turn error responses into successes. Doing so misleads users about backend behavior.

## 8. Using requestInterceptor to attach access tokens

requestInterceptor can attach application-issued tokens, though Swagger UI's built-in Authorize and OAuth mechanisms should be preferred once the API declares appropriate security schemes.

If a token provider is exposed by the application's login portal, for example:

~~~javascript
const requestInterceptor = (request) => {
  request.headers = request.headers || {};

  const token = window.appAuth?.getAccessToken?.();

  if (token && !request.headers.Authorization) {
    request.headers.Authorization = "Bearer " + token;
  }

  return request;
};
~~~

This example assumes the application already provides window.appAuth and a getAccessToken method. These are not built-in APIs of Swagger UI or Springdoc; the project must integrate its own token provider.

Key principles:

- Never hardcode access tokens or refresh tokens in JavaScript files.
- Never place tokens in URL query strings.
- Never log Authorization headers.
- Never write tokens into vendor extensions or OpenAPI documents.
- Do not overwrite an Authorization value supplied by the user via Authorize unintentionally.
- Send tokens only to trusted API origins.
- Handle token expiration and re-login behavior.

When using OAuth2, configure security schemes and OAuth redirects according to your version's Swagger UI/Springdoc documentation. Interceptors are only a UI request-handling layer and do not replace token issuance, refresh, and revocation workflows.

## 9. Do not attach sensitive headers to every request

A global requestInterceptor may be invoked for many requests initiated by Swagger UI. Depending on loading flow and version, those requests may include fetching documents or invoking operations. Therefore, do not assume the callback runs only for a single API path.

When adding tokens or internal headers, restrict them by origin/path:

~~~javascript
const requestInterceptor = (request) => {
  const target = new URL(request.url, window.location.origin);
  const apiOrigin = "https://api.example.com";

  if (target.origin === apiOrigin &&
      target.pathname.startsWith("/api/")) {
    request.headers = request.headers || {};
    request.headers["X-Request-Source"] = "swagger-ui";
  }

  return request;
};
~~~

This example attaches the header only when the URL matches the selected origin and path. Adjust apiOrigin and the prefix to fit the actual environment. If documentation is fetched from one host while operations call another host, origin scoping prevents sending headers to the wrong target.

Do not attach Authorization to OpenAPI document fetch requests if the documentation endpoint uses a separate access mechanism or different credentials. Separate documentation access policies from business API calling policies.

## 10. CORS when interceptors add request headers

When Swagger UI runs on a different origin from the API, browsers enforce Cross-Origin Resource Sharing (CORS). Adding custom headers in requestInterceptor can trigger an OPTIONS preflight request.

For instance, headers like X-Request-Source or Authorization can cause the browser to send a preflight asking the server whether the method and headers are allowed.

The backend must configure CORS accordingly:

- Allow the Swagger UI page's origin.
- Allow the methods clients need to call.
- Allow request headers such as Authorization, Content-Type, and custom headers.
- If using cookies or credentials, configure allow-credentials and origins per browser rules.
- Expose only response headers JavaScript needs to read, such as X-Trace-Id.

If JavaScript cannot read a response header even though it appears in the network response, check Access-Control-Expose-Headers. If preflight fails, interceptors cannot fix CORS on their own because that policy is enforced by browser and server.

Never combine an allow-origin wildcard with credentials when CORS requires credentials. Configure explicit origins per environment.

## 11. Interceptors are not backend middleware

requestInterceptor and responseInterceptor run only in browsers hosting Swagger UI. They do not execute when:

- A mobile app calls the API.
- Another backend calls the API.
- Users call the API with curl or Postman.
- A frontend application outside Swagger UI sends requests.
- Spring Boot handles direct requests from other clients.

Therefore, never place business logic, permission checks, or mandatory validation solely inside interceptors. Any rule that must hold across all clients must be enforced on the backend.

Similarly, responseInterceptor does not alter responses sent by the backend to other clients. It only alters how Swagger UI receives or processes responses in that browser session.

Interceptors can be used for UI telemetry or debugging headers, yet browser-supplied data must never be treated as a trusted authentication source.

## 12. Limits when handling errors and responses

responseInterceptor is well-suited for observing HTTP responses received by Swagger Client. It does not replace:

- Exception handlers in Spring MVC.
- Standardized backend error responses.
- CORS configuration.
- Client retry policies.
- Authentication and authorization.
- Browser-level network error handling.
- OpenAPI document contract testing.

Some errors occur before an HTTP response exists, such as failed DNS lookup, TLS handshake errors, CORS blocks by the browser, or connection timeouts. Such cases may provide no response object to responseInterceptor.

For HTTP 400, 401, 403, 404, or 500, the server returned a response so the interceptor can observe the status and response fields exposed by Swagger Client. Detailed display still depends on how Swagger UI handles responses and version settings.

Never use responseInterceptor to turn a 401 error into 200 or strip error payloads to make the UI appear successful. Preserve error signals so API testers can evaluate outcomes accurately.

## 13. Example combining both interceptors

The example below adds an identification header to requests and logs only error statuses for responses:

~~~javascript
const ui = SwaggerUIBundle({
  url: "/v3/api-docs",
  dom_id: "#swagger-ui",
  deepLinking: true,

  requestInterceptor: (request) => {
    const target = new URL(request.url, window.location.origin);

    if (target.pathname.startsWith("/api/")) {
      request.headers = request.headers || {};
      request.headers["X-Request-Source"] = "swagger-ui";
    }

    return request;
  },

  responseInterceptor: (response) => {
    if (response.status >= 400) {
      console.info("API returned status", response.status);
    }

    return response;
  }
});

window.ui = ui;
~~~

In this example:

- The request interceptor adds the header only for paths starting with /api/.
- The response interceptor logs error statuses.
- Both callbacks return the input object.
- No tokens or sensitive data are written to the console.

When bringing this into a project, retain default or required options such as presets, plugins, layout, OAuth configuration, and configUrl. The snippet above illustrates callbacks rather than a complete drop-in replacement for every Swagger UI version.

## 14. Common errors when configuring interceptors

| Symptom | Cause to inspect |
|---|---|
| requestInterceptor does not run | Callback not passed to SwaggerUIBundle or custom UI page not used |
| responseInterceptor does not run | Request produced no HTTP response, callback not registered, or call bypassed Swagger Client |
| YAML does not accept function | Data-only Springdoc config cannot represent JavaScript callbacks |
| Header does not reach backend | CORS preflight failed or request restricted by browser |
| Token sent to unexpected host | Interceptor did not restrict origin/path |
| Authorize works yet token is overwritten | Request interceptor overwrote existing Authorization header |
| Swagger UI fails to load docs | Custom index has wrong bundle URL, configUrl, or OpenAPI path |
| Group selector disappears | Custom page omitted swagger-config or needed options |
| Displayed response differs from server payload | responseInterceptor altered body/status or client config transformed response |
| responseInterceptor not triggered on network failure | No HTTP response object exists for the callback |
| Swagger UI works locally yet fails in staging | Origin, CORS, context path, or server URL differs across environments |
| Upgrading Springdoc breaks UI | Custom index page relied on old version resources or init structure |

When investigating, open browser Developer Tools and inspect Console, Network, request URLs, OPTIONS preflights, response headers, and swagger-config content. Confirm the callback was loaded before concluding the bug is on the backend.

## 15. Testing interceptors in the browser

Test layer by layer:

**Checking requests:**

1. Open Swagger UI and pick an operation to test.
2. Execute Try it out.
3. Open the Network tab.
4. Inspect URL, method, and sent headers.
5. Confirm the interceptor modifies only requests within the intended scope.
6. Confirm Authorization is neither overwritten nor sent to another origin.

**Checking responses:**

1. Call an operation returning 2xx.
2. Call an operation returning 4xx or 5xx.
3. Verify responseInterceptor receives the status.
4. Compare displayed response with the response in the Network tab.
5. Confirm body and headers were not altered unintentionally.

**Checking edge cases:**

- Same-origin and cross-origin APIs.
- Succeeding and failing CORS preflights.
- Missing or expired tokens.
- Public endpoints and authenticated endpoints.
- Loading the OpenAPI document and invoking operations.
- Timeouts or dropped connections.
- Swagger UI group selector and OAuth redirect.

Do not check only the console. Cross-check the Network tab because console logs can omit header details, preflights, and actual responses.

## 16. Principles for using requestInterceptor and responseInterceptor

When customizing Swagger UI in a Spring Boot application using Springdoc OpenAPI, follow these principles:

1. Use requestInterceptor for browser-side request adjustments.
2. Use responseInterceptor to observe or transform response objects inside Swagger UI.
3. Place callbacks in Swagger UI initialization JavaScript; never treat YAML/JSON config as a place for functions.
4. Preserve required default configuration when customizing the index page.
5. Scope headers and tokens to trusted origins/paths.
6. Prefer Authorize/OAuth flows for authentication instead of hardcoding tokens.
7. Configure backend CORS whenever interceptors add cross-origin headers.
8. Never use interceptors to replace server-side authorization, validation, or exception handling.
9. Never log tokens, personal data, or sensitive response bodies.
10. Inspect requests/responses in the Network tab after every change.

requestInterceptor and responseInterceptor help tailor the API testing experience in Swagger UI. They run in the browser and affect only requests/responses handled by the documentation UI. When callbacks are configured properly, scoped clearly by origin, and the backend enforces full security, validation, and CORS, development teams can add observability and integration support without distorting the published API contract.
