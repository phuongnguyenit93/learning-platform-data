# Generics, Response Wrappers, and the Risk of Losing Type Information

APIs often use generic data types to reuse structures: a response wrapper may hold a book, an author, or an order; a pagination structure may hold a list of elements of various types; a bulk request may accept a list of different DTOs. In Java, these structures are represented using **generic types**. When springdoc-openapi generates schemas, the library needs to determine the concrete type supplied to the generic parameter to accurately describe the JSON over HTTP.

Problems arise when the concrete type is no longer clearly visible in the method signature or bytecode metadata. Java uses **type erasure** to implement generics, so type parameter information does not exist as a separate runtime type per instance. However, generic signatures declared in class files can still store **Signature** metadata that reflection and analysis tools can read. Therefore, you must distinguish between Java erasing type parameters from runtime objects and generic information in method/class declarations still being readable.

With springdoc-openapi, how return types are declared, how wrapper classes are designed, and how annotations are used can determine whether the generated schema is complete or collapses to **Object**, a raw type, or a structure that does not reflect actual JSON. This lesson covers everything from basic generics to wrapper responses, type erasure, OpenAPI representation, and the specification verification process.

## 1. Generic Types in Java and Their Meaning for APIs

Generics allow a class or method to work with multiple data types while preserving type information at compile time.

~~~java
public class Box<T> {
    private T value;

    public Box(T value) {
        this.value = value;
    }

    public T getValue() {
        return value;
    }
}
~~~

**Box<String>** holds a `String`, while **Box<BookResponse>** holds a `BookResponse`. The same **Box<T>** definition is reused without writing two separate classes.

A response wrapper can declare a type parameter `T`, such as **ApiEnvelope<T>**, so that the `data` property retains the concrete type chosen by each operation. The full definition of this wrapper appears in the response design example below.

Endpoints can return the same outer structure with different inner data types:

~~~java
ApiEnvelope<BookResponse>
ApiEnvelope<AuthorResponse>
ApiEnvelope<List<BookResponse>>
~~~

To clients, these three types share a similar outer JSON structure, but the type of **data** differs. OpenAPI needs to preserve that distinction so consumers know whether `data` holds a book object, an author object, or an array of books.

### Nested Generic Types

Generics can be nested across multiple levels:

~~~java
ApiEnvelope<List<BookResponse>>
ApiEnvelope<PageResponse<BookResponse>>
ApiEnvelope<Map<String, List<BookResponse>>>
~~~

Each level carries meaning for the schema:

- **ApiEnvelope** describes the `success`, `data`, and `error` fields.
- **List** or **PageResponse** describes the collection structure.
- **BookResponse** describes each element.
- **Map<String, ...>** describes an object with dynamic keys and values matching a defined schema.

If one level loses its concrete type, the nested schema beneath it can become a generic object or fail to describe the structure clients need.

## 2. From Generic Methods to OpenAPI Schemas

When a concrete type appears in a method signature, analysis tools can read the generic return type and infer the schema.

~~~java
@RestController
@RequestMapping("/api/books")
public class BookController {

    @GetMapping("/{bookId}")
    public ApiEnvelope<BookResponse> getBook(
        @PathVariable UUID bookId
    ) {
        BookResponse book = findBook(bookId);
        return new ApiEnvelope<>(true, book, null);
    }
}
~~~

The signature **ApiEnvelope<BookResponse>** indicates that the type parameter `T` of **ApiEnvelope<T>** is replaced by **BookResponse** in this operation. springdoc can analyze the generic signature to describe `data` using the `BookResponse` schema.

An abbreviated specification might look similar to:

~~~yaml
paths:
  /api/books/{bookId}:
    get:
      responses:
        "200":
          description: Successfully retrieved book information
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ApiEnvelopeBookResponse"
components:
  schemas:
    ApiEnvelopeBookResponse:
      type: object
      properties:
        success:
          type: boolean
        data:
          $ref: "#/components/schemas/BookResponse"
        error:
          $ref: "#/components/schemas/ApiError"
~~~

The component name in the example is illustrative. The actual name generated by springdoc/swagger-core depends on the version, model converters, and naming configuration. What you need to verify is that the schema for `data` points to `BookResponse`, while the outer envelope fields are preserved.

### Generics in Request Bodies

Generics can also be used for data sent by clients:

~~~java
public record BulkRequest<T>(
    List<T> items,
    boolean validateOnly
) {}

@PostMapping("/bulk")
public ApiEnvelope<BulkResult> createMany(
    @Valid @RequestBody BulkRequest<CreateBookRequest> request
) {
    // ...
    return null;
}
~~~

Here `items` is a list of `CreateBookRequest`. The request body schema needs to describe:

- Object `BulkRequest`.
- Property `items` as an array.
- `items` having elements matching the `CreateBookRequest` schema.
- Property `validateOnly` as a boolean.

If the signature uses only **BulkRequest** without a type argument, the element type of `items` is no longer clear in the method declaration. springdoc may infer only a raw type or generic object, depending on metadata and converters.

## 3. Response Wrappers and ResponseEntity

In Spring Boot, you must distinguish **HTTP transport wrappers** from **application data wrappers**.

**ResponseEntity<T>** is a Spring type used to control HTTP status codes, headers, and the body. It is not necessarily a JSON object serialized into `statusCode`, `headers`, and `body` properties. For a controller returning **ResponseEntity<ApiEnvelope<BookResponse>>**, the application's JSON body is `ApiEnvelope<BookResponse>`.

~~~java
@GetMapping("/{bookId}")
public ResponseEntity<ApiEnvelope<BookResponse>> getBook(
    @PathVariable UUID bookId
) {
    BookResponse book = findBook(bookId);
    ApiEnvelope<BookResponse> body =
        new ApiEnvelope<>(true, book, null);

    return ResponseEntity.ok(body);
}
~~~

springdoc typically treats `ResponseEntity` as a Spring transport wrapper and analyzes the inner body type. The result should describe `ApiEnvelope<BookResponse>`, not a JSON schema for `ResponseEntity` itself.

Conversely, **ApiEnvelope<T>** is an application-defined data wrapper. Whether a controller returns `ApiEnvelope<BookResponse>` directly or places it inside `ResponseEntity`, the envelope properties are part of the real JSON and must appear in the schema.

| Method signature | Meaning for the response body |
|---|---|
| **BookResponse** | JSON is a `BookResponse` |
| **ResponseEntity<BookResponse>** | HTTP status/headers controlled by `ResponseEntity`; body is `BookResponse` |
| **ApiEnvelope<BookResponse>** | JSON body is an envelope with `data` of type `BookResponse` |
| **ResponseEntity<ApiEnvelope<BookResponse>>** | `ResponseEntity` controls HTTP; JSON body is still the envelope |
| **ResponseEntity<ApiEnvelope>** | Envelope loses its concrete type parameter in the signature |

Do not document `ResponseEntity` as a response DTO. Describe the actual body type and use `ResponseEntity` to control HTTP behavior.

## 4. Designing Generic Wrappers with a Stable Structure

A wrapper can hold success data and errors:

~~~java
public record ApiError(
    String code,
    String message
) {}

public class ApiEnvelope<T> {
    private final boolean success;
    private final T data;
    private final ApiError error;

    public ApiEnvelope(boolean success, T data, ApiError error) {
        this.success = success;
        this.data = data;
        this.error = error;
    }

    public boolean isSuccess() {
        return success;
    }

    public T getData() {
        return data;
    }

    public ApiError getError() {
        return error;
    }

    public static <T> ApiEnvelope<T> success(T data) {
        return new ApiEnvelope<>(true, data, null);
    }

    public static <T> ApiEnvelope<T> failure(ApiError error) {
        return new ApiEnvelope<>(false, null, error);
    }
}
~~~

A success response:

~~~json
{
  "success": true,
  "data": {
    "id": "8f4c2c2e-3d3d-4c2b-a3d8-5e3b7b6a1001",
    "title": "Spring in Action"
  },
  "error": null
}
~~~

An error response:

~~~json
{
  "success": false,
  "data": null,
  "error": {
    "code": "BOOK_NOT_FOUND",
    "message": "Book not found"
  }
}
~~~

If the API always returns a wrapper, the schema must describe both the outer structure and the `data` portion. Declaring the response solely as `BookResponse` makes the documentation disagree with the actual JSON because clients also receive `success` and `error`.

### Do Not Turn Every Response into Object

A design that easily causes information loss is:

~~~java
public record ApiEnvelope(
    boolean success,
    Object data,
    ApiError error
) {}
~~~

Using `Object` makes the schema of `data` overly broad. Clients cannot tell when `data` is a `BookResponse`, when it is an `AuthorResponse`, or when it is a collection. When each endpoint has a concrete type, a generic `ApiEnvelope<T>` preserves the type relationship in the method signature and reuses the structure.

If data genuinely has multiple unpredictable shapes, describe the contract using `oneOf`/`anyOf` or a polymorphic model with a discriminator where appropriate. `Object` should only be used when the payload truly has no stable structure and that is accepted in the contract.

## 5. Type Erasure: What Java Keeps and What Java Erases

Java implements generics using **type erasure**. At runtime bytecode level, type parameters are replaced by their bounds; if no bound is declared, the default bound is `Object`. Thus, **ApiEnvelope<BookResponse>** and **ApiEnvelope<AuthorResponse>** share the same runtime class `ApiEnvelope`.

~~~java
ApiEnvelope<String> texts =
    new ApiEnvelope<>(true, "hello", null);

ApiEnvelope<Integer> counts =
    new ApiEnvelope<>(true, 42, null);

System.out.println(texts.getClass() == counts.getClass()); // true
~~~

An instance does not carry a separate runtime class per generic parameter. From `texts.getClass()`, you cannot directly ask whether the instance is an `ApiEnvelope<String>`.

However, you should not conclude that all generic information disappears from `.class` files. The compiler usually records **generic Signature metadata** for class, field, method, and superclass declarations. Java Reflection can read a method's generic signature:

~~~java
Method method = BookController.class.getMethod(
    "getBook",
    UUID.class
);

Type returnType = method.getGenericReturnType();
System.out.println(returnType);
~~~

`getGenericReturnType()` can return a `ParameterizedType` corresponding to `ApiEnvelope<BookResponse>`, whereas `getReturnType()` only returns the runtime class `ApiEnvelope`. This is why springdoc can analyze generic types declared on methods even though Java executes with type erasure.

| Reflection API | Information |
|---|---|
| **Method.getReturnType()** | Erased class type, e.g. `ApiEnvelope` |
| **Method.getGenericReturnType()** | Generic signature if metadata is present, e.g. `ApiEnvelope<BookResponse>` |
| **Field.getType()** | Runtime type of the field after erasure |
| **Field.getGenericType()** | Generic signature of the field if stored |
| **Class.getGenericSuperclass()** | Superclass type along with declared generic arguments |

Therefore, the risk is not solely Java's type erasure. The real risk is declaring API signatures too coarsely, failing to preserve concrete specializations, or making required metadata impossible to determine.

## 6. Declaration Patterns That Lose Type Information

The following cases make it difficult for documentation tools to determine concrete schemas:

### Raw types

~~~java
@GetMapping("/books")
public ApiEnvelope getBooks() {
    // ...
    return null;
}
~~~

The method only declares `ApiEnvelope`, without `T`. The generic parameter has been omitted from the signature. The schema for `data` can become an unspecified object or a generic representation.

### Using Object

~~~java
public ApiEnvelope<Object> getData() {
    // ...
    return null;
}
~~~

The signature has a generic argument, but the concrete type is still `Object`. Metadata gives no indication of the actual payload shape.

### Wildcards that do not identify a concrete type

~~~java
public ApiEnvelope<?> getData() {
    // ...
    return null;
}
~~~

The `?` wildcard indicates some type exists without specifying a concrete DTO. `? extends SomeBase` can provide an upper bound, but the upper bound does not necessarily expose all properties of the concrete runtime type. If the contract has multiple shapes, describe them intentionally using `oneOf` or a discriminator.

### Unspecialized type variables

~~~java
@GetMapping("/data")
public <T> ApiEnvelope<T> getData() {
    // ...
    return null;
}
~~~

The method type variable `T` is not bound to a concrete type in the endpoint signature. springdoc cannot guess the runtime payload from the data the method happens to return.

### Returning generics via an interface or base class without a concrete type

~~~java
public interface ResultProvider<T> {
    ApiEnvelope<T> getResult();
}

public class GenericController<T> {
    public ApiEnvelope<T> getResult() {
        // ...
        return null;
    }
}
~~~

If an endpoint is described from a generic declaration where `T` is not resolved in the concrete controller context, the schema may not resolve as expected. When a controller extends a specialized base class, superclass metadata can provide the information, but you must verify the actual output based on the inheritance hierarchy and library version.

## 7. How to Preserve Concrete Types for Generic Wrappers

The first priority is declaring the concrete type directly in the method signature:

~~~java
@GetMapping("/{bookId}")
public ApiEnvelope<BookResponse> getBook(
    @PathVariable UUID bookId
) {
    return ApiEnvelope.success(findBook(bookId));
}
~~~

If a controller uses a generic superclass, create a specialized controller with a concrete type:

~~~java
public abstract class BaseReadController<T> {
    public abstract ApiEnvelope<T> getOne(UUID id);
}

@RestController
@RequestMapping("/api/books")
public class BookController
        extends BaseReadController<BookResponse> {

    @Override
    @GetMapping("/{bookId}")
    public ApiEnvelope<BookResponse> getOne(
        @PathVariable UUID bookId
    ) {
        return ApiEnvelope.success(findBook(bookId));
    }
}
~~~

Overriding the method with a specialized signature makes the controller contract explicitly show `BookResponse`. If you keep a method with only `T` on a superclass, verify whether springdoc resolves the inherited type in that specific case.

### Using a Concrete Subclass for a Stable Response

If you want a clear schema name for a specific wrapper type, you can create a specialized class:

~~~java
@Schema(
    name = "BookEnvelope",
    description = "Response containing book information"
)
public class BookEnvelope extends ApiEnvelope<BookResponse> {
    public BookEnvelope(
        boolean success,
        BookResponse data,
        ApiError error
    ) {
        super(success, data, error);
    }
}
~~~

The controller can then return `BookEnvelope`. The generic superclass declares `ApiEnvelope<BookResponse>`, so the concrete type is stored in the superclass metadata. This approach is useful when you need a stable component name or want a dedicated response type for documentation.

A concrete subclass must reflect the actual JSON. Do not create a class just to make documentation look nice if the serializer does not produce the corresponding structure.

## 8. Pagination and Collections Inside Generic Wrappers

A custom pagination type can use generics:

~~~java
public record PageResponse<T>(
    List<T> items,
    int page,
    int size,
    long totalElements,
    int totalPages
) {}
~~~

Controller:

~~~java
@GetMapping
public ApiEnvelope<PageResponse<BookResponse>> listBooks(
    @RequestParam(defaultValue = "0") int page,
    @RequestParam(defaultValue = "20") int size
) {
    PageResponse<BookResponse> result = searchBooks(page, size);
    return ApiEnvelope.success(result);
}
~~~

The schema needs to represent each level:

~~~yaml
ApiEnvelope:
  type: object
  properties:
    success:
      type: boolean
    data:
      $ref: "#/components/schemas/PageResponseBookResponse"

PageResponseBookResponse:
  type: object
  properties:
    items:
      type: array
      items:
        $ref: "#/components/schemas/BookResponse"
    page:
      type: integer
    size:
      type: integer
    totalElements:
      type: integer
      format: int64
    totalPages:
      type: integer
~~~

The illustrative component names may differ in actual output. What matters is that `items` points to `BookResponse`, not `Object`.

With Spring Data, `Page<T>` carries pagination metadata and implementation-dependent details. For a stable API contract, many systems convert `Page<T>` into a `PageResponse<T>` DTO with selected public fields. The schema then depends less on Spring Data's internal structure.

## 9. Using @Schema(implementation = ...) in the Right Scope

The annotation **@Schema(implementation = SomeClass.class)** can specify the schema type used in documentation. This is useful when the Java return type is too generic or when you want to explicitly name a concrete DTO.

~~~java
@ApiResponse(
    responseCode = "200",
    description = "Book information",
    content = @Content(
        mediaType = MediaType.APPLICATION_JSON_VALUE,
        schema = @Schema(implementation = BookEnvelope.class)
    )
)
@GetMapping("/{bookId}")
public ResponseEntity<?> getBook(@PathVariable UUID bookId) {
    // Return JSON matching the BookEnvelope structure
    return ResponseEntity.ok(loadBookEnvelope(bookId));
}
~~~

In the example, the documentation uses `BookEnvelope` as the response schema. The `ResponseEntity<?>` signature still does not provide a concrete body type for inference; the annotation supplies the information for documentation. The actual data type must always be compatible with `BookEnvelope`.

`implementation` accepts a class literal, so you cannot write **ApiEnvelope<BookResponse>.class** directly in Java. Java does not allow taking a class literal of a parameterized type. Common alternatives include:

- Declare the concrete generic type in the method signature so springdoc can infer it.
- Create a concrete subclass such as `BookEnvelope` to obtain a class literal and a clear component name.
- Use `@ApiResponse`/`@Content`/`@Schema` to specify a concrete schema when overriding documentation, while ensuring runtime JSON matches that structure.

Do not use **@Schema(implementation = BookResponse.class)** if the actual response is `ApiEnvelope<BookResponse>`. Doing so removes the `success`, `data`, and `error` fields from the published schema.

### When useReturnTypeSchema Is Needed

In some cases where `@ApiResponse` is declared manually, you may need springdoc to use the schema inferred from the return type instead of a default schema from the description. The **useReturnTypeSchema** attribute of `@ApiResponse` can be helpful depending on the `swagger-annotations` version and how the response is declared. Check the Javadoc of the dependency version you are using and verify the JSON output; do not add this attribute mechanically if the schema is already inferred correctly.

## 10. Generic Requests and Responses Should Maintain Consistent Contracts

An API can use generic types in both requests and responses:

~~~java
public record DataRequest<T>(
    T data
) {}

public record DataResponse<T>(
    boolean accepted,
    T result
) {}
~~~

Controller:

~~~java
@PostMapping("/books/validate")
public DataResponse<BookResponse> validateBook(
    @RequestBody DataRequest<CreateBookRequest> request
) {
    // ...
    return null;
}
~~~

The request schema needs `data` conforming to `CreateBookRequest`; the response schema needs `result` conforming to `BookResponse`. You should not reuse a `DataRequest<Object>` or `DataResponse<Object>` schema if the actual endpoint has concrete DTOs.

For APIs with multiple data types, you can use different endpoint specializations. For example:

| Endpoint | Request type | Response type |
|---|---|---|
| POST /api/books | **DataRequest<CreateBookRequest>** | **DataResponse<BookResponse>** |
| POST /api/authors | **DataRequest<CreateAuthorRequest>** | **DataResponse<AuthorResponse>** |
| POST /api/orders | **DataRequest<CreateOrderRequest>** | **DataResponse<OrderResponse>** |

In this way, the wrapper structure is reused while each operation keeps a concrete schema.

## 11. Polymorphism: When a Generic Has Multiple Valid Subtypes

Sometimes `T` is not a fixed type but can be one of several subtypes. For example, a notification could be a book-created event or a book-updated event. In this case, use a base type and describe the subtypes with **oneOf** or **anyOf**, often combined with a discriminator.

~~~java
@Schema(
    name = "BookEvent",
    oneOf = {
        BookCreatedEvent.class,
        BookUpdatedEvent.class
    },
    discriminatorProperty = "eventType"
)
public interface BookEvent {
}

@Schema(name = "BookCreatedEvent")
public record BookCreatedEvent(
    String eventType,
    UUID bookId,
    String title
) implements BookEvent {}

@Schema(name = "BookUpdatedEvent")
public record BookUpdatedEvent(
    String eventType,
    UUID bookId,
    String changedField
) implements BookEvent {}
~~~

If the wrapper is `ApiEnvelope<BookEvent>`, the schema for `data` can reference `BookEvent`, where `oneOf` lists the valid variants. This describes polymorphic payloads much more clearly than using `Object`.

Ensure runtime JSON contains enough information for clients to distinguish subtypes, typically a discriminator property like `eventType`. OpenAPI annotations only describe the contract; Jackson must also be configured to serialize/deserialize the corresponding subtypes.

## 12. Common Pitfalls and How to Fix Them

| Symptom in OpenAPI | Possible cause | Resolution |
|---|---|---|
| `data` has an empty or overly generic object schema | Raw type, `Object`, or unresolved generic | Declare a concrete type in the method signature |
| `data` loses the wrapper structure | Response annotation points only to the inner DTO | Document the envelope or concrete subclass properly |
| Wrapper appears as a schema for Spring `ResponseEntity` | Confusing transport wrapper with JSON body | Check the body type inside `ResponseEntity` |
| Generic superclass is not specialized | Base class still has unresolved `T` in controller context | Override with a concrete type or create a concrete subclass |
| Generic component name is hard to read or changes | Auto-generated name depends on model converters | Use a concrete subclass with `@Schema(name = "...")` |
| Request array only shows items of type `Object` | Generic request body lacks a concrete type argument | Use `BulkRequest<CreateBookRequest>` |
| `@Schema(implementation=BookResponse.class)` drops `data`/`error` | `implementation` replaces the envelope schema with the child DTO | Specify the corresponding wrapper schema |
| `oneOf` schema does not match JSON | Jackson does not serialize the discriminator or subtypes as documented | Align Jackson and OpenAPI configurations |
| Runtime response has a wrapper but documentation does not | Method signature or `@ApiResponse` describes it wrongly | Compare actual JSON against the response schema |

## 13. Inspecting Generic Schemas Generated by springdoc

After starting the application, fetch the spec at **/v3/api-docs** or the YAML endpoint if enabled. For each operation using generics, check:

1. Does the operation have the right status codes and media types?
2. Does the response schema preserve the application's data wrapper?
3. Does the `data` property point to the expected concrete type?
4. If `data` is an array, do `items` have the right element schema?
5. If generics are nested, does each level preserve the right type?
6. Do schema components have unique names and valid `$ref` targets?
7. Does a generic request body show the right accepted element type?
8. Does the runtime JSON payload match the published structure?

You can use `jq` to inspect the response schema:

~~~bash
curl -s http://localhost:8080/v3/api-docs | jq '.paths["/api/books/{bookId}"].get.responses["200"].content["application/json"].schema'
~~~

Then open the referenced component:

~~~bash
curl -s http://localhost:8080/v3/api-docs | jq '.components.schemas'
~~~

If the schema is inlined, inspect the properties directly inside the response schema. If the schema uses `$ref`, verify that the reference path points to an existing component.

### Comparing Schemas with Actual JSON

Call the endpoint with an HTTP client or integration test, capture the actual JSON, and verify:

- Is `success` a boolean?
- Does `data` match the published object/array?
- Does `error` have the right structure and appear in error cases?
- Do DTO properties have the right names after Jackson serialization?
- Do status code and content type match the documented response?

A syntactically valid OpenAPI specification can still have a broken contract if wrappers or generic arguments are lost. You must inspect both the JSON structure and the schema, rather than only verifying that Swagger UI opens.

## 14. Principles for Designing Generic Wrappers

- Use a generic `Wrapper<T>` when the outer structure is shared while the inner data type varies per endpoint.
- Declare concrete type arguments in controller signatures, such as `ApiEnvelope<BookResponse>`.
- For nested generics, preserve every level completely, such as `ApiEnvelope<PageResponse<BookResponse>>`.
- Avoid raw types, `Object`, and unnecessary wildcards at public API boundaries.
- Distinguish Spring's `ResponseEntity` from application-defined JSON wrappers.
- Use concrete subclasses when stable schema names or specialized response types are needed.
- Use `oneOf`/`anyOf` and a discriminator when payloads genuinely have multiple valid subtypes.
- Override schemas with `@Schema(implementation = ...)` only when that type matches runtime JSON.
- Keep request and response DTOs distinct if the two directions have different structures.
- Inspect `/v3/api-docs` alongside actual payloads after every change to generics or wrappers.

## Conclusion

Generics let you reuse wrappers and pagination structures while keeping concrete data types in Java signatures. springdoc-openapi can analyze generic metadata to generate nested schemas when controllers declare clear specializations. Type erasure means runtime instances do not carry distinct classes per type parameter, yet generic Signatures in class and method declarations can still be read by reflection. Raw types, `Object`, wildcards, or unresolved type variables are common causes of schema information loss. Declare concrete types, distinguish `ResponseEntity` from JSON wrappers, use concrete subclasses or appropriately scoped `implementation` annotations when needed, and verify OpenAPI JSON against actual payloads.
