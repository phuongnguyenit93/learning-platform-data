# Documenting a CRUD API with a Complete Success and Error Contract

A CRUD API is only well-documented when integrators know how to create, read, update, and delete resources; as well as knowing what status code each operation can return, what structure the body has, and how errors are represented. Merely writing a summary for the controller or letting Springdoc infer schemas from DTOs is usually not enough for a stable contract.

This hands-on exercise builds a product management API using Spring Boot and springdoc-openapi. We will define the request DTO, response DTO, validation, error model, CRUD controller, exception handler, and OpenAPI annotations. Afterward, we will inspect the generated JSON/YAML, test the endpoints, and write integration tests to ensure the documentation matches actual HTTP behavior.

## 1. Objectives of the exercise

After completing this exercise, an API integrator can:

- Find the operations to create, list, view details, update, and delete products.
- Know the path, HTTP method, query/path parameters, and request body of each operation.
- Know which fields are required, their data types, constraints, and valid examples.
- Know what status code and schema the success response has.
- Know the structure of validation errors, resource-not-found errors, data conflict errors, and system errors.
- Use Swagger UI or an HTTP client to test requests.
- Inspect OpenAPI JSON/YAML and automatically verify the contract in CI.

The example scope is Spring MVC with a REST controller. If the project uses Spring WebFlux, replace the MVC starter with the corresponding WebFlux starter and keep the same contract description principles.

## 2. Product management API context

The API has a Product resource with the following attributes:

| Attribute | Type | Meaning |
|---|---|---|
| id | UUID | Product identifier generated by the server |
| sku | String | Unique product code |
| name | String | Product name |
| description | String | Description, optional |
| price | BigDecimal | Non-negative price |
| category | String | Product category |
| createdAt | Instant | Creation timestamp |
| updatedAt | Instant | Last update timestamp |

Clients must not send id, createdAt, or updatedAt when creating a product. These values are managed by the server.

Operations:

| Method | Path | Function | Success |
|---|---|---|---|
| POST | /api/products | Create a product | 201 Created |
| GET | /api/products | List products | 200 OK |
| GET | /api/products/{id} | View details | 200 OK |
| PUT | /api/products/{id} | Replace product information | 200 OK |
| DELETE | /api/products/{id} | Delete a product | 204 No Content |

Errors are described uniformly:

| Status | Example error code | Case |
|---|---|---|
| 400 | VALIDATION_FAILED | Request is missing fields or violates constraints |
| 404 | PRODUCT_NOT_FOUND | No matching product found |
| 409 | SKU_ALREADY_EXISTS | SKU is already used by another product |
| 500 | INTERNAL_ERROR | Unexpected server error |

Status codes and error codes are part of the contract. Do not return 200 for every case and put error information in the body, as clients will find it difficult to handle correctly according to HTTP semantics.

## 4. Adding Springdoc and validation dependencies

With Spring MVC, the main dependency is typically:

~~~xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>${springdoc.version}</version>
</dependency>
~~~

Add Bean Validation:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
~~~

Choose a springdoc version compatible with your project's Spring Boot version. The Spring Boot 3 branch uses springdoc 2.x; the Spring Boot 4 branch uses springdoc 3.x. Do not choose a version based solely on the latest number while ignoring the compatibility matrix.

Springdoc at runtime reads controllers, DTOs, Jackson metadata, and validation annotations to generate the OpenAPI document. The validation dependency ensures constraints such as @NotBlank, @PositiveOrZero, and @Size are enforced when requests are validated.

## 5. Defining the contract before writing the controller

Before adding annotations, clearly decide:

- Which fields does the create request contain?
- Does update replace the entire resource or only update part of it?
- Is the ID generated by the client or the server?
- Must the SKU be unique?
- Can the price be negative?
- When the resource is not found, return 404 or another response?
- When the SKU is duplicated, return 409 or 400?
- Does delete return 204 with no body or 200 with a confirmation body?

In this exercise, POST creates a new resource and returns 201 along with a Location header. PUT replaces all editable fields. DELETE returns 204 with no response body. These choices will be used consistently across code, documentation, and tests.

## 6. Designing a shared ErrorResponse

Errors should have a stable structure so clients can handle them without parsing free-form text:

~~~java
public class ErrorResponse {

    @Schema(example = "2026-11-20T10:15:30Z")
    private Instant timestamp;

    @Schema(example = "400")
    private int status;

    @Schema(example = "VALIDATION_FAILED")
    private String code;

    @Schema(example = "Request contains invalid fields")
    private String message;

    @Schema(example = "/api/products")
    private String path;

    private List<FieldViolation> fieldErrors;

    // constructors, getters and setters
}
~~~

FieldViolation describes the error on each field:

~~~java
public class FieldViolation {

    @Schema(example = "price")
    private String field;

    @Schema(example = "must be greater than or equal to 0")
    private String message;

    // constructors, getters and setters
}
~~~

Example validation response:

~~~json
{
  "timestamp": "2026-11-20T10:15:30Z",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Request contains invalid fields",
  "path": "/api/products",
  "fieldErrors": [
    {
      "field": "name",
      "message": "must not be blank"
    },
    {
      "field": "price",
      "message": "must be greater than or equal to 0"
    }
  ]
}
~~~

Do not include stack traces, SQL, table names, or sensitive information in ErrorResponse. The message should be safe and sufficiently helpful to the client; technical details are logged internally with a correlation ID if needed.

## 7. Creating the request DTO for the create operation

CreateProductRequest contains only the fields the client is allowed to send:

~~~java
public class CreateProductRequest {

    @NotBlank
    @Size(max = 100)
    @Schema(
        description = "Product name",
        example = "Mechanical Keyboard K8"
    )
    private String name;

    @NotBlank
    @Size(max = 40)
    @Schema(
        description = "Unique SKU code",
        example = "KB-K8-BLK"
    )
    private String sku;

    @Size(max = 2000)
    @Schema(
        description = "Product description",
        example = "75 percent layout mechanical keyboard"
    )
    private String description;

    @NotNull
    @DecimalMin("0.00")
    @Digits(integer = 12, fraction = 2)
    @Schema(
        description = "Selling price, must not be negative",
        example = "129.90"
    )
    private BigDecimal price;

    @NotBlank
    @Size(max = 80)
    @Schema(
        description = "Product category",
        example = "Accessories"
    )
    private String category;

    // constructors, getters and setters
}
~~~

The annotations serve two related but distinct roles:

- Bean Validation checks data at runtime when the controller receives a request with @Valid.
- Swagger annotations add descriptions, examples, and OpenAPI metadata.

Springdoc can infer some constraints from Bean Validation, but open the generated JSON to confirm required, minLength, maxLength, and minimum match expectations.

## 8. Creating the request DTO for the update operation

PUT is used as an operation that replaces the editable fields of the resource:

~~~java
    private String description;

    @NotNull
    @DecimalMin("0.00")
    @Digits(integer = 12, fraction = 2)
    @Schema(description = "Selling price", example = "139.90")
    private BigDecimal price;

    @NotBlank
    @Size(max = 80)
    @Schema(description = "Category", example = "Accessories")
    private String category;

    // constructors, getters and setters
~~~

In this contract, required fields must appear in PUT. If you want to support partial updates, design a separate PATCH operation and clearly document how missing fields, null fields, and new values are handled.

Do not reuse the same DTO for POST, PUT, and response just to reduce the number of classes. A create request should not allow clients to send server-managed IDs or timestamps; a response, on the other hand, needs to expose those fields.

## 10. Creating the response for paginated lists

To keep the contract readable and independent of a specific Page implementation, you can use a dedicated DTO:

~~~java
public class ProductPageResponse {

    private List<ProductResponse> items;

    @Schema(example = "0")
    private int page;

    @Schema(example = "20")
    private int size;

    @Schema(example = "125")
    private long totalElements;

    @Schema(example = "7")
    private int totalPages;

    // constructors, getters and setters

~~~

Query parameters:

- category: filter by category, optional.
- page: 0-based page index, default 0.
- size: number of items per page, default 20.

Using a pagination DTO keeps clients from depending on the internal structure of Spring Data Page.

## 11. Defining domain exceptions

The service can throw exceptions based on business semantics:

~~~java
public class ProductNotFoundException extends RuntimeException {
    public ProductNotFoundException(UUID id) {
        super("Product not found: " + id);
    }
}

public class DuplicateSkuException extends RuntimeException {
    public DuplicateSkuException(String sku) {
        super("SKU already exists: " + sku);
    }
}
~~~

Do not return internal exception messages directly to the client if the message might contain sensitive data. The exception handler will translate them into stable error codes and messages.

## 12. Declaring the service contract

The controller should not contain persistence logic. The service is responsible for business logic:

~~~java
public interface ProductService {

    ProductResponse create(CreateProductRequest request);

    ProductPageResponse findAll(String category, int page, int size);

    ProductResponse findById(UUID id);

    ProductResponse update(UUID id, UpdateProductRequest request);

    void delete(UUID id);
}
~~~

The service implementation must verify:

- SKU is not duplicated when creating.
- The new SKU does not collide with another product when updating.
- The product exists before viewing, updating, or deleting.
- Price and input data are valid.
- Deletion follows business policy.

These rules must be enforced on the server, not merely relied upon through schemas displayed by MCP or Swagger UI.

## 13. Creating the controller and shared tag

Controller:

~~~java
@RestController
@RequestMapping("/api/products")
@Tag(
    name = "Products",
    description = "Create, query, update, and delete products"
)
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }
}
~~~

@Tag groups related operations in Swagger UI. The description should explain the business scope rather than merely repeating the class name.

Each method needs a stable operationId. Java method names can be changed during refactoring, whereas operationId is metadata that code generators and consumers may rely on.

## 14. Documenting the create product operation

POST /api/products returns 201 Created with a ProductResponse body. Common errors include 400 for invalid requests and 409 when the SKU already exists.

~~~java
@PostMapping
@Operation(
    operationId = "createProduct",
    summary = "Create a product",
    description = "Creates a new product. The server automatically generates the ID and creation timestamp."
)
@ApiResponses({
    @ApiResponse(
        responseCode = "201",
        description = "Product created",
        content = @Content(
            mediaType = "application/json",
            schema = @Schema(implementation = ProductResponse.class)
        )
    ),
    @ApiResponse(
        responseCode = "400",
        description = "Invalid request",
        content = @Content(
            mediaType = "application/json",
            schema = @Schema(implementation = ErrorResponse.class)
        )
    ),
    @ApiResponse(
        responseCode = "409",
        description = "SKU already exists",
        content = @Content(
            mediaType = "application/json",
            schema = @Schema(implementation = ErrorResponse.class)
        )
    )
})
public ResponseEntity<ProductResponse> create(
        @Valid
        @org.springframework.web.bind.annotation.RequestBody
        CreateProductRequest request) {

    ProductResponse created = productService.create(request);
    URI location = ServletUriComponentsBuilder
        .fromCurrentRequest()
        .path("/{id}")
        .buildAndExpand(created.getId())
        .toUri();

    return ResponseEntity.created(location).body(created);
}
~~~

Key points to note:

- @Valid triggers Bean Validation on the request DTO.
- 201 indicates a new resource has been created.
- Location points to the URL of the newly created resource.
- Content schema describes the response body.
- ErrorResponse is used consistently for 400 and 409.

## 18. Documenting the delete operation

DELETE /api/products/{id} returns 204 No Content on successful deletion:

~~~java
@DeleteMapping("/{id}")
@Operation(
    operationId = "deleteProduct",
    summary = "Delete a product",

    @ApiResponse(
        responseCode = "204",

        content = @Content

    @ApiResponse(
        responseCode = "404",
        description = "Product not found",
        content = @Content(
            mediaType = "application/json",
            schema = @Schema(implementation = ErrorResponse.class)
~~~

## 20. Creating a ControllerAdvice to map validation errors

Spring MVC throws MethodArgumentNotValidException when the request body fails Bean Validation and the controller uses @Valid.

~~~java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(
            MethodArgumentNotValidException ex,
            HttpServletRequest request) {

        List<FieldViolation> violations = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(error -> new FieldViolation(
                error.getField(),
                error.getDefaultMessage()
            ))
            .toList();

        ErrorResponse body = new ErrorResponse(
            Instant.now(),
            400,
            "VALIDATION_FAILED",
            "Request contains invalid fields",
            request.getRequestURI(),
            violations
        );

        return ResponseEntity.badRequest().body(body);
    }
}
~~~

If the project uses a Java version that does not support Stream.toList(), replace it with Collectors.toList(). The return type and response payload must remain consistent with the ErrorResponse schema.

## 21. Mapping not-found and conflict errors

Add handlers for domain exceptions:

~~~java
@ExceptionHandler(ProductNotFoundException.class)
public ResponseEntity<ErrorResponse> handleNotFound(
        ProductNotFoundException ex,
        HttpServletRequest request) {

    ErrorResponse body = new ErrorResponse(
        Instant.now(),
        404,
        "PRODUCT_NOT_FOUND",
        "Product was not found",
        request.getRequestURI(),
        List.of()
    );

    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
}

@ExceptionHandler(DuplicateSkuException.class)
public ResponseEntity<ErrorResponse> handleDuplicateSku(
        DuplicateSkuException ex,
        HttpServletRequest request) {

    ErrorResponse body = new ErrorResponse(
        Instant.now(),
        409,
        "SKU_ALREADY_EXISTS",
        "SKU is already used by another product",
        request.getRequestURI(),
        List.of()
    );

    return ResponseEntity.status(HttpStatus.CONFLICT).body(body);
}
~~~

Do not return the raw exception message if it contains database details or internal data. Clients need stable error codes rather than implementation-dependent wording.

## 22. Mapping unexpected errors

You can have a fallback handler for unclassified errors:

~~~java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(
        Exception ex,
        HttpServletRequest request) {

    log.error("Unhandled API error at {}", request.getRequestURI(), ex);

    ErrorResponse body = new ErrorResponse(
        Instant.now(),
        500,
        "INTERNAL_ERROR",
        "An unexpected error occurred",
        request.getRequestURI(),
        List.of()
    );

    return ResponseEntity.internalServerError().body(body);
}
~~~

The generic handler must come after specific handlers in exception resolution logic. Internal logs may include stack traces; public responses should not.

## 23. Documenting ErrorResponse in OpenAPI

There are two common approaches:

1. Declare @ApiResponse per operation using the ErrorResponse schema.
2. Use a customizer mechanism or shared response configuration if the organization has a standard convention.

In this exercise, declare them explicitly on each operation so readers immediately see the important statuses. For example, GET /api/products/{id} has 200 and 404; POST has 201, 400, and 409. For 500 errors, use @ApiResponse at the controller level to apply a shared response across the controller's operations; method-level responses still declare specific statuses. If an operation has different 500 error behavior, redeclare it on the method and verify the result after Springdoc merges metadata.

Springdoc can read information from ControllerAdvice to build generic error responses. However, do not rely on the framework automatically adding every error to every operation without inspecting the final JSON. If the contract requires a specific status, document it explicitly and verify it appears on the corresponding operation.

## 24. Configuring API info and security scheme

Global metadata can be declared as:

~~~java
@Configuration
@OpenAPIDefinition(
    info = @Info(
        title = "Product Catalog API",
        version = "1.0.0",
        description = "Product catalog management API"
    )
)
@SecurityScheme(
    name = "bearerAuth",
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT"
)
public class OpenApiConfiguration {
}
~~~

If operations require a Bearer token, apply @SecurityRequirement at the controller or individual operation level:

~~~java
@SecurityRequirement(name = "bearerAuth")
@RestController
@RequestMapping("/api/products")
public class ProductController {
}
~~~

The security scheme only describes authentication in OpenAPI. Spring Security is what actually enforces token validation and permissions. If some operations are public, place security requirements per operation instead of applying them to the entire controller.

## 26. Reviewing the status code and response body contract

Before running the application, review the following table:

| Operation | Success | Errors to document | Error body |
|---|---|---|---|
| POST /api/products | 201 ProductResponse | 400, 409 | ErrorResponse |
| GET /api/products | 200 ProductPageResponse | 500 | ErrorResponse |
| GET /api/products/{id} | 200 ProductResponse | 404 | ErrorResponse |
| PUT /api/products/{id} | 200 ProductResponse | 400, 404, 409 | ErrorResponse |

You do not need to declare every status code that could exist on the network. Choose the responses the API commits to or intentionally handles. If a gateway can return 502 or 504, document it in the gateway documentation or at the API layer if it is part of the public contract.

OpenAPI YAML:

~~~text
http://localhost:8080/v3/api-docs.yaml
~~~

Paths may change if the application uses a context path or configures springdoc.api-docs.path and springdoc.swagger-ui.path.

## 28. Testing CRUD requests with an HTTP client

Create a product:

~~~bash
curl -i -X POST http://localhost:8080/api/products \

~~~

## 29. Testing error cases

Request missing name or having negative price:

~~~bash
curl -i -X POST http://localhost:8080/api/products \
  -H "Content-Type: application/json" \
  -d '{
    "name": "",
    "sku": "KB-BAD",
    "price": -10,
    "category": "Accessories"
  }'
~~~

Expected result: 400 with ErrorResponse and fieldErrors pointing to name or price.

Look up a non-existent ID:

~~~bash
curl -i http://localhost:8080/api/products/00000000-0000-0000-0000-000000000000
~~~

Expected result: 404 with code PRODUCT_NOT_FOUND.

Create two products with the same SKU:

~~~bash
curl -i -X POST http://localhost:8080/api/products \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Duplicate SKU item",
    "sku": "KB-K8-BLK",
    "price": 99.00,
    "category": "Accessories"
  }'
~~~

Expected result: 409 with code SKU_ALREADY_EXISTS if the SKU is already in use.

Compare the actual response against the ErrorResponse schema. If a handler returns a body with a different structure, the documentation and runtime are inconsistent.

## 30. Inspecting OpenAPI JSON with jq

Save the document:

~~~bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs \
  -o target/openapi.json
~~~

Inspect metadata:

~~~bash
jq '{openapi, info, pathCount: (.paths | length)}' target/openapi.json
~~~

List paths:

~~~bash
jq -r '.paths | keys[]' target/openapi.json
~~~

Inspect POST responses:

~~~bash
jq '.paths["/api/products"].post.responses' target/openapi.json
~~~

Inspect GET by ID responses:

~~~bash
jq '.paths["/api/products/{id}"].get.responses' target/openapi.json
~~~

The document must contain status 201 for create, 200 for read/update, 204 for delete, and the published error responses. Check content schemas as well, not only whether the status key exists.

## 31. Checking YAML and Swagger UI

Fetch YAML:

~~~bash
curl --fail --silent --show-error \
  http://localhost:8080/v3/api-docs.yaml \
  -o target/openapi.yaml
~~~

Use a YAML parser or OpenAPI validator to verify the file is valid. Do not rename a JSON file extension to YAML.

In Swagger UI, verify:

- The Products tag is present.
- All five CRUD operations are present.
- The path parameter id has type UUID.
- Query parameters category, page, and size have appropriate descriptions/defaults.
- The request body shows fields and constraints.
- Responses 201/200/204 have the correct schemas.
- Error responses 400/404/409/500 use ErrorResponse.
- Authorize appears if the API defines a security scheme.

Swagger UI is a visual inspection tool; OpenAPI JSON/YAML is the contract artifact processed by validators, code generators, and CI.

## 32. Writing integration tests for the HTTP contract

You can use MockMvc:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class ProductContractTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void createProductReturns201AndLocation() throws Exception {
        mockMvc.perform(post("/api/products")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                    {
                      "name": "Keyboard K8",
                      "sku": "KB-K8-BLK",
                      "price": 129.90,
                      "category": "Accessories"
                    }
                    """))
            .andExpect(status().isCreated())
            .andExpect(header().exists(HttpHeaders.LOCATION))
            .andExpect(jsonPath("$.id").exists())
            .andExpect(jsonPath("$.sku").value("KB-K8-BLK"));
    }

    @Test
    void invalidCreateRequestReturns400() throws Exception {
        mockMvc.perform(post("/api/products")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                    {
                      "name": "",
                      "sku": "KB-BAD",
                      "price": -10,
                      "category": "Accessories"
                    }
                    """))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.code").value("VALIDATION_FAILED"))
            .andExpect(jsonPath("$.fieldErrors").isArray());
    }
}
~~~

These tests verify real HTTP responses through Spring MVC, Jackson, and validation. If the application uses security, add appropriate authentication/authorization tests or configure a test principal.

## 33. Testing the OpenAPI document in integration tests

You can invoke the documentation endpoint from MockMvc:

~~~java
@Test
void openApiContainsCrudOperationsAndErrorResponses() throws Exception {
    MvcResult result = mockMvc.perform(get("/v3/api-docs"))
        .andExpect(status().isOk())
        .andReturn();

    JsonNode document = objectMapper.readTree(
        result.getResponse().getContentAsString()
    );

    JsonNode paths = document.path("paths");

    assertThat(paths.path("/api/products").path("post")
        .path("responses").has("201")).isTrue();

    assertThat(paths.path("/api/products").path("post")
        .path("responses").has("500")).isTrue();

    assertThat(paths.path("/api/products").path("get")
        .path("responses").has("200")).isTrue();

    assertThat(paths.path("/api/products/{id}").path("get")
        .path("responses").has("404")).isTrue();

    assertThat(paths.path("/api/products/{id}").path("delete")
        .path("responses").has("204")).isTrue();
}
~~~

The example uses JsonNode to verify structure instead of searching for strings across the entire document. Add assertions for 400, 409, and the ErrorResponse schema to avoid cases where a status exists but its content is missing.

If the project uses multiple GroupedOpenApi instances, test each group endpoint separately. An operation may exist in the default document while being excluded from the public group by design.

## 34. Distinguishing runtime bugs from documentation bugs

Certain situations require separate checks:

| Symptom | What to check |
|---|---|
| POST returns 400 but OpenAPI does not document 400 | @ApiResponse and validation contract |
| OpenAPI states 201 but code returns 200 | ResponseEntity/status mapping |
| DELETE states 204 but returns a body | Controller response and serialization |
| ErrorResponse schema has a field but JSON omits it | Jackson inclusion or DTO mapping |
| Swagger UI does not show operation while JSON has it | UI has selected the wrong group or filter |
| JSON has operation but request returns 404 | Runtime mapping, context path, or proxy |
| Validation annotation is in source but schema lacks constraint | Dependency, annotation target, or version compatibility |
| 500 response exposes stack trace | Exception handler and error serialization |

Do not tweak annotations merely to make Swagger UI look like the expected result if the HTTP behavior is wrong. Decide the contract first, then fix either the runtime or the documentation so both comply.

## 35. Checking whether success and error responses are consistent

Cross-check three sources:

1. OpenAPI document.
2. HTTP responses from the application.
3. Integration tests.

For example, with POST:

- OpenAPI says 201 and ProductResponse.
- Actual HTTP returns 201, Location, and ProductResponse JSON.
- Tests verify status, header, and key fields.

With validation:

- OpenAPI says 400 and ErrorResponse.
- Actual HTTP returns 400, code VALIDATION_FAILED, and fieldErrors.
- Tests verify status and body structure.

If one of the three sources differs, the contract is incomplete. Fix the source code or the documentation and rerun the tests.

## 36. Integrating OpenAPI validation into CI

A pipeline can:

1. Run unit tests and integration tests.
2. Start the application or use the Maven plugin to export OpenAPI.
3. Save JSON/YAML into the build directory.
4. Parse the document.
5. Run an OpenAPI validator.
6. Compare against a baseline if the API has already been released.
7. Upload the validated artifact.

Example using OpenAPI Generator CLI:

~~~bash
openapi-generator-cli validate -i target/openapi.json
~~~

Or using Redocly CLI:

~~~bash
npx @redocly/cli lint target/openapi.json
~~~

Pin the validator version in CI. An older validator may not understand the OpenAPI version or JSON Schema dialect used by the project.

## 37. Common mistakes when documenting CRUD APIs

| Mistake | Consequence | Fix |
|---|---|---|
| Omitting operationId | Client generators produce unpredictable names | Set a stable operationId for each operation |
| Summary only | Lacks conditions and semantics | Write a short, clear description |
| Using entities as request/response | Exposes internal fields and tightly couples API to database | Use dedicated DTOs |
| Missing @Valid | Constraints do not execute on request body | Add @Valid and the validation dependency |
| Not documenting errors | Clients do not know the schema on failure | Add @ApiResponse for important statuses |
| Returning 200 for create | Loses resource creation semantics | Use 201 and Location |
| DELETE returns body while documented as 204 | Runtime and OpenAPI contradict each other | Choose 204 without body or 200 with schema |
| Error handlers return multiple structures | Clients must parse multiple error formats | Standardize ErrorResponse |
| Invalid @Schema example | Misleading examples | Sync examples with types and validation |
| Checking only Swagger UI | Fails to catch errors in JSON/YAML | Inspect /v3/api-docs endpoint directly |
| Not testing the OpenAPI document | Operations or responses may disappear | Add integration tests for the document |
| Testing only the happy path | 400/404/409 errors remain unverified | Test both success and error paths |

## 38. Exercise completion checklist

Before considering the CRUD API fully documented:

- [ ] Every operation has a stable operationId.
- [ ] Controller has @Tag and an appropriate description.
- [ ] Request DTOs are separated from entities and response DTOs.
- [ ] Validation annotations reflect business rules.
- [ ] OpenAPI schema accurately reflects required, type, format, and constraints.
- [ ] POST returns 201 and Location.
- [ ] GET returns 200 and the correct response schema.
- [ ] PUT clearly documents replacement semantics.
- [ ] DELETE returns 204 without a body if the contract selects No Content.
- [ ] Errors 400, 404, 409, and 500 have a uniform ErrorResponse.
- [ ] ControllerAdvice maps exceptions to the right status codes.
- [ ] Security scheme is documented if the API requires authentication.
- [ ] JSON and YAML endpoints work.
- [ ] Swagger UI displays all operations, parameters, and responses.
- [ ] Integration tests verify both HTTP behavior and the OpenAPI document.
- [ ] CI parses and validates the OpenAPI artifact.

## 39. Key takeaways

- A CRUD contract must describe requests, success responses, and error responses.
- Use separate DTOs for create, update, and response.
- Bean Validation validates data at runtime; springdoc places the corresponding metadata into the schema.
- @Operation describes an operation's purpose; operationId must be stable.
- @ApiResponse describes status, description, media type, and response schema.
- @Parameter clarifies path/query parameters and examples.
- @Schema adds description, example, and constraints to models.
- @RestControllerAdvice standardizes exceptions into ErrorResponse.
- Status codes must match actual HTTP behavior.
- 204 has no response body; 201 typically includes Location when creating a resource.
- Swagger UI is the visual interface; OpenAPI JSON/YAML is the contract artifact.
- Integration tests must verify success payloads, error payloads, and document structure.
- CI should validate OpenAPI and compare against a baseline before release.

A CRUD API only has a reliable contract when the OpenAPI document, HTTP responses, and integration tests describe the exact same behavior. Define the DTOs and error model first, attach clear metadata to each operation, map exceptions to stable status codes, then inspect JSON/YAML and run tests for both success and error paths. When all three sources match, clients can integrate the API without guessing how failed requests behave.
