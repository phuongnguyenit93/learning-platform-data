# @Attribute và tên attribute LDAP trong Spring LDAP ODM

Khi làm việc trực tiếp với JNDI hoặc `LdapTemplate`, ứng dụng thường đọc thuộc tính LDAP bằng tên như `cn`, `sn`, `uid` và `mail`. Với **Object-Directory Mapping (ODM)** của Spring LDAP, các giá trị đó có thể được ánh xạ vào các field của đối tượng Java. Annotation **`@Attribute`** là cầu nối giúp nói rõ *field Java nào đại diện cho attribute LDAP nào*.

Ví dụ, một ứng dụng muốn dùng field `email` trong Java, trong khi schema LDAP dùng tên `mail`. Khai báo `@Attribute(name = "mail")` giúp ODM đọc và ghi giá trị đúng thuộc tính LDAP, thay vì buộc mã nghiệp vụ phải gọi trực tiếp `attrs.get("mail")` ở mọi nơi.

Bài học thuộc chương **ODM** trong module **Spring LDAP**. Phần trọng tâm là ý nghĩa của tên LDAP attribute, cú pháp `@Attribute`, các annotation thường dùng kèm theo, cách Spring LDAP ánh xạ dữ liệu khi đọc/cập nhật entry và những ràng buộc của schema, DN, bảo mật và kiểm thử.

Sau khi học, bạn có thể:

- Giải thích sự khác nhau giữa **tên field Java** và **tên LDAP attribute**.
- Khai báo `@Entry`, `@Id`, `@Attribute(name = "...")` cho một lớp ODM.
- Lựa chọn ánh xạ tường minh khi tên Java và tên LDAP khác nhau.
- Nhận biết thuộc tính đơn trị, đa trị, tùy chọn, nhị phân và giá trị thuộc RDN.
- Phân biệt ánh xạ thuộc tính với việc đặt tên/đổi DN của entry.
- Phòng tránh lỗi thiếu thuộc tính, sai schema, ghi đè dữ liệu và dùng filter/DN không an toàn.

## 1. Vì sao cần ánh xạ tên attribute?

Giả sử LDAP server có entry dạng LDIF:

```ldif
dn: uid=lan,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: lan
cn: Lan Nguyen
sn: Nguyen
givenName: Lan
displayName: Lan Nguyen
mail: lan@example.org
telephoneNumber: +84 28 1234 5678
```

Ứng dụng Java lại muốn model có tên dễ hiểu theo quy ước nội bộ:

```java
class DirectoryUser {
    private String username;
    private String fullName;
    private String surname;
    private String givenName;
    private String displayLabel;
    private String email;
    private String phoneNumber;
}
```

Tên field Java và tên attribute LDAP **không nhất thiết giống nhau**:

| Tên LDAP attribute | Field Java mong muốn | Vì sao nên khai báo tường minh? |
| --- | --- | --- |
| `uid` | `username` | LDAP dùng `uid`; Java dùng tên theo nghiệp vụ |
| `cn` | `fullName` | `cn` không tự đồng nghĩa với `fullName` trong Java |
| `sn` | `surname` | Dễ bị viết nhầm thành `lastName` mà quên tên LDAP |
| `givenName` | `givenName` | Dù trùng tên, khai báo rõ giúp hợp đồng dữ liệu dễ đọc |
| `displayName` | `displayLabel` | Thuộc tính hiển thị không nhất thiết giống `cn` |
| `mail` | `email` | `mail` là tên thuộc tính LDAP phổ biến, không phải `email` |
| `telephoneNumber` | `phoneNumber` | Tên schema dài hơn tên thuộc tính trong model |

Với ODM, thay vì tự viết nhiều lần:

```java
String email = (String) attributes.get("mail").get();
```

ta khai báo:

```java
@Attribute(name = "mail")
private String email;
```

Spring LDAP ODM dùng thông tin ánh xạ để chuyển giữa đối tượng Java và dữ liệu LDAP trong các thao tác ODM tương ứng.

**Điểm cốt lõi:** `@Attribute` là **metadata ánh xạ** trong ứng dụng Java. Nó không tạo attribute mới trên LDAP server, không sửa schema và không đổi tên thuộc tính trên máy chủ.

## 2. Phân biệt field Java, tên LDAP và giá trị dữ liệu

Trước khi viết annotation, hãy tách ba khái niệm:

- **Tên field Java:** `email` trong `DirectoryUser.email`. Tên này được Java compiler và mã ứng dụng sử dụng.
- **Tên attribute LDAP:** `mail`. Đây là tên attribute type được LDAP schema nhận diện.
- **Giá trị attribute:** `lan@example.org`. Đây là dữ liệu của entry, phải tuân thủ cú pháp, cardinality và quyền truy cập.

Ví dụ:

```text
Java:
    email          = "lan@example.org"
    └ tên field      └ giá trị

LDAP:
    mail: lan@example.org
    └ tên attribute  └ giá trị
```

Spring LDAP không tự xác minh một tên do bạn ghi trong `@Attribute` có thực sự tồn tại trong schema của server ở lúc biên dịch Java. Nếu ghi `@Attribute(name = "eMailAddress")` nhưng server chỉ biết `mail`, lớp Java vẫn có thể biên dịch, còn việc đọc/ghi sẽ phụ thuộc cách server xử lý tên attribute không có trong schema.

### LDAP attribute type và quy tắc chữ hoa/chữ thường

Trong LDAP, tên attribute type thường được server xử lý **không phân biệt chữ hoa/chữ thường** trong định danh schema. Chẳng hạn `cn` và `CN` thường cùng chỉ một attribute type. Tuy vậy:

1. Nên dùng **tên chuẩn** như `cn`, `sn`, `uid`, `mail` để code dễ đối chiếu tài liệu/schema.
2. Không suy ra **giá trị attribute** cũng luôn so sánh không phân biệt chữ hoa/chữ thường; điều đó do matching rule và syntax của schema quyết định.
3. Không dùng việc LDAP chấp nhận `CN` để giả định tên field Java `CN` và `cn` là một.
4. Một attribute type có thể có alias hoặc OID; nên dùng tên đã được schema và tổ chức thống nhất.

Ví dụ hai attribute `displayName` và `cn` có thể mang giá trị tương tự, nhưng **không phải một attribute type**. Annotate field bằng `cn` không làm nó tự đọc `displayName`.

## 3. Các annotation ODM liên quan đến `@Attribute`

Trong Spring LDAP, một entity ODM thường có những thành phần sau:

| Annotation | Vai trò | Ví dụ |
| --- | --- | --- |
| `@Entry` | Đánh dấu lớp ánh xạ entry LDAP; mô tả base và object classes theo cấu hình | `@Entry(base = "ou=people", objectClasses = {...})` |
| `@Id` | Ánh xạ DN của entry vào một field kiểu `Name`/`LdapName` | `@Id private Name dn;` |
| `@Attribute` | Ánh xạ một thuộc tính LDAP sang một field của entity | `@Attribute(name = "mail") private String email;` |
| `@DnAttribute` | Liên kết một field với thành phần được dùng trong DN/RDN theo quy tắc ODM | Dùng khi cần đồng bộ thông tin đặt tên |
| `@Transient` | Đánh dấu field không được ánh xạ thành dữ liệu LDAP | Trạng thái tính toán chỉ dùng trong ứng dụng |

Ví dụ ngắn:

```java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
    }
)
public class DirectoryUser {
    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String username;

    @Attribute(name = "cn")
    private String fullName;

    @Attribute(name = "sn")
    private String surname;

    @Attribute(name = "mail")
    private String email;

    public DirectoryUser() {
        // Constructor không đối số để hỗ trợ ODM khởi tạo entity.
    }
}
```

Ở ví dụ này:

- `@Entry` mô tả lớp Java tương ứng với loại entry và vùng base của ODM.
- `@Id` giữ **DN**, không phải giá trị attribute `uid`.
- `@Attribute(name = "uid")` ánh xạ giá trị LDAP `uid` sang field `username`.
- `@Attribute(name = "cn")` ánh xạ `cn` sang `fullName`.
- `@Attribute(name = "mail")` ánh xạ `mail` sang `email`.

Các annotation này giải quyết **những khía cạnh khác nhau** của một entry, nên không được thay `@Id` bằng `@Attribute(name = "uid")` rồi nghĩ rằng đã khai báo DN.

### Lưu ý về `@Entry` và schema

Danh sách `objectClasses` trong `@Entry` cần phù hợp schema server. Ví dụ `inetOrgPerson` là lớp kế thừa từ `organizationalPerson`, `person` và `top` trong hệ schema phổ biến. Tuy nhiên, Spring LDAP **không tự cài đặt schema** chỉ vì entity có annotation.

Với `person`, các thuộc tính như `cn` và `sn` thường là bắt buộc. Khi tạo entry, thiếu thuộc tính bắt buộc hoặc dùng sai object class có thể khiến LDAP server trả lỗi `objectClassViolation`. Việc đọc entry cũng có thể bị ảnh hưởng nếu loại entry không khớp điều kiện ánh xạ của ODM.

## 4. Cú pháp `@Attribute(name = "...")`

Cách dùng phổ biến nhất là chỉ rõ tên attribute LDAP:

```java
@Attribute(name = "cn")
private String fullName;

@Attribute(name = "mail")
private String email;

@Attribute(name = "givenName")
private String firstName;
```

Đây là ánh xạ **tường minh**:

```text
Field Java       @Attribute(name)       Attribute LDAP
fullName   ────> "cn"              ────> cn
email      ────> "mail"            ────> mail
firstName  ────> "givenName"       ────> givenName
```

Nếu field Java và attribute LDAP cùng tên, trong cách ánh xạ ODM thông dụng có thể dùng `@Attribute` mà không khai báo `name` để dùng tên field làm mặc định. Tuy nhiên, để code đào tạo và tích hợp schema rõ ràng, **nên ghi `name` tường minh** ở các thuộc tính nghiệp vụ quan trọng và kiểm tra hợp đồng của phiên bản Spring LDAP đang sử dụng.

Ví dụ chọn cách tường minh:

```java
@Attribute(name = "displayName")
private String displayName;
```

Thay vì chỉ dựa vào quy ước mặc định:

```java
@Attribute
private String displayName;
```

Cách thứ hai có thể phù hợp nhưng đòi hỏi người đọc hiểu quy tắc mặc định. Cách thứ nhất cho biết rõ rằng dữ liệu phải lấy từ attribute type `displayName`.

### Nếu đổi tên field Java thì sao?

Giả sử ban đầu:

```java
@Attribute(name = "mail")
private String email;
```

Sau một đợt refactor, ứng dụng đổi field thành `primaryEmail`:

```java
@Attribute(name = "mail")
private String primaryEmail;
```

Tên attribute LDAP vẫn là **`mail`**. Refactor Java không phải migration LDAP schema, miễn annotation và các đoạn mã liên quan vẫn đúng.

Ngược lại, nếu đổi annotation từ `@Attribute(name = "mail")` thành `@Attribute(name = "primaryEmail")`, ứng dụng sẽ yêu cầu **một attribute LDAP khác**. Đây không phải chỉ đổi tên biến; nếu server không có attribute type tương ứng, việc đọc/ghi có thể sai hoặc thất bại.

## 5. Một entity ODM đầy đủ để minh họa

Ví dụ dưới đây dùng một model chỉ chứa dữ liệu cần cho hồ sơ cơ bản. Nó minh họa rõ các attribute phổ biến và cách field Java không cần trùng tên LDAP:

```java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;
import org.springframework.ldap.odm.annotations.Transient;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top",
        "person",
        "organizationalPerson",
        "inetOrgPerson"
    }
)
public class DirectoryPerson {
    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String username;

    @Attribute(name = "cn")
    private String fullName;

    @Attribute(name = "sn")
    private String familyName;

    @Attribute(name = "givenName")
    private String givenName;

    @Attribute(name = "displayName")
    private String displayLabel;

    @Attribute(name = "mail")
    private String email;

    @Transient
    private boolean selectedInUi;

    public DirectoryPerson() {
    }

    public Name getDn() {
        return dn;
    }

    public void setDn(Name dn) {
        this.dn = dn;
    }

    public String getUsername() {
        return username;
    }

    public void setUsername(String username) {
        this.username = username;
    }

    public String getFullName() {
        return fullName;
    }

    public void setFullName(String fullName) {
        this.fullName = fullName;
    }

    public String getFamilyName() {
        return familyName;
    }

    public void setFamilyName(String familyName) {
        this.familyName = familyName;
    }

    public String getGivenName() {
        return givenName;
    }

    public void setGivenName(String givenName) {
        this.givenName = givenName;
    }

    public String getDisplayLabel() {
        return displayLabel;
    }

    public void setDisplayLabel(String displayLabel) {
        this.displayLabel = displayLabel;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    public boolean isSelectedInUi() {
        return selectedInUi;
    }

    public void setSelectedInUi(boolean selectedInUi) {
        this.selectedInUi = selectedInUi;
    }
}
```

Các field `username`, `fullName`, `familyName`, `displayLabel` và `email` có tên theo **ngữ nghĩa Java**, không phải theo tên schema LDAP.

**`@Transient`** cho `selectedInUi` giúp tránh ánh xạ một trạng thái thuần giao diện người dùng thành thuộc tính LDAP. Không nên lưu thông tin điều khiển UI hoặc cờ xử lý nội bộ vào directory chỉ vì chúng xuất hiện trên entity Java.

### Tại sao `@Id private Name dn` không phải `String username`?

DN là chuỗi RDN có cấu trúc, ví dụ:

```text
uid=lan,ou=people,dc=example,dc=org
```

Trong khi `uid=lan` chỉ là một RDN, `username = "lan"` chỉ là giá trị thuộc tính `uid`. Cùng giá trị `uid=lan` có thể tồn tại trong những OU khác nhau nếu thiết kế directory cho phép; bản thân `uid` không nhất thiết xác định duy nhất entry trên toàn DIT.

`@Id` biểu diễn **DN của entry**, còn `@Attribute(name = "uid")` biểu diễn **giá trị thuộc tính**. Hai giá trị có liên quan trong các entry dùng `uid` làm RDN nhưng không phải cùng một đối tượng dữ liệu.

## 6. Đọc entity ODM: tên annotation quyết định nguồn dữ liệu

Giả sử `LdapContextSource` có cấu hình:

```text
URL:      ldaps://ldap.example.org:636
Base DN:  dc=example,dc=org
User DN:  uid=app-reader,ou=service,dc=example,dc=org
```

Khi đọc một entry, có thể dùng `LdapTemplate` với API ODM:

```java
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public final class DirectoryPersonService {
    private final LdapTemplate ldapTemplate;

    public DirectoryPersonService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public DirectoryPerson findByUsername(String username) {
        Name relativeDn = LdapNameBuilder.newInstance("ou=people")
                .add("uid", username)
                .build();

        return ldapTemplate.findByDn(relativeDn, DirectoryPerson.class);
    }
}
```

Khi tìm `username = "lan"`, DN tương đối là `uid=lan,ou=people`; LDAP server thực tế sẽ được truy cập dưới base `dc=example,dc=org` mà `ContextSource` cung cấp.

Nếu server trả:

```ldif
dn: uid=lan,ou=people,dc=example,dc=org
uid: lan
cn: Lan Nguyen
sn: Nguyen
mail: lan@example.org
```

thì sau khi ánh xạ, đối tượng Java có thể có:

```text
person.getUsername()     → "lan"
person.getFullName()     → "Lan Nguyen"
person.getFamilyName()   → "Nguyen"
person.getEmail()        → "lan@example.org"
```

Những thuộc tính không có trong entry hoặc không được tài khoản bind phép đọc có thể ánh xạ thành `null` hoặc giá trị mặc định tùy kiểu field/cơ chế mapper. Hãy thiết kế lớp Java để xử lý dữ liệu thiếu rõ ràng, không tự mặc định một kết quả thiếu là giá trị đã bị xóa khỏi LDAP.

### Khi nào cần search thay vì tra đúng DN?

Nếu không biết DN đầy đủ, ta có thể dùng LDAP filter để tìm entry trước:

```java
import java.util.List;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.query.LdapQuery;
import org.springframework.ldap.query.LdapQueryBuilder;

public final class DirectoryPersonSearch {
    private final LdapTemplate ldapTemplate;

    public DirectoryPersonSearch(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public List<DirectoryPerson> findByMail(String email) {
        LdapQuery query = LdapQueryBuilder.query()
                .base("ou=people")
                .where("mail").is(email);

        return ldapTemplate.find(query, DirectoryPerson.class);
    }
}
```

**Chú ý hai loại tên khác nhau xuất hiện đồng thời:**

- `.where("mail").is(email)` dùng **tên LDAP attribute** `mail` trong filter.
- `@Attribute(name = "mail") private String email;` dùng cùng tên LDAP để ánh xạ kết quả vào field `email`.

Filter do server xử lý, còn ODM mapping do ứng dụng Java thực hiện. `LdapQueryBuilder` xử lý escaping giá trị filter, tránh lỗi LDAP filter injection khi `email` đến từ input.

### Không tự suy ra khả năng tìm kiếm từ tên field

Câu lệnh sai ý định sau không tự động hiểu `email` là alias của `mail`:

```java
// Sai nếu LDAP schema không khai báo attribute type "email".
LdapQuery query = LdapQueryBuilder.query()
        .base("ou=people")
        .where("email").is(userInput);
```

**`@Attribute(name = "mail")` không đổi tên thuộc tính trong LDAP filter.** Khi xây filter, vẫn dùng tên thật của LDAP schema. ODM chỉ ánh xạ dữ liệu trả về cho Java object.

## 7. Dùng tên LDAP attribute đúng theo schema

LDAP directory server có **schema** để định nghĩa attribute type, object class, matching rule, giá trị bắt buộc/tùy chọn và cú pháp.

| Attribute thường gặp | Ví dụ nội dung | Điều cần nhớ |
| --- | --- | --- |
| `cn` | `Lan Nguyen` | Thường gắn với tên chung (*common name*) |
| `sn` | `Nguyen` | Thường bắt buộc với object class `person` |
| `givenName` | `Lan` | Có thể là thuộc tính tùy chọn |
| `uid` | `lan` | Giá trị có thể dùng làm RDN nếu schema và naming design cho phép |
| `mail` | `lan@example.org` | Tên attribute LDAP phổ biến, không phải `email` |
| `displayName` | `Lan Nguyen` | Tách biệt với `cn`, dù có thể trùng giá trị |
| `telephoneNumber` | `+84 28 1234 5678` | Có thể hỗ trợ nhiều giá trị theo schema |
| `member` | Một hoặc nhiều DN thành viên | Giá trị là DN, cần xử lý cú pháp và tham chiếu |
| `objectClass` | `top`, `person`, ... | Định nghĩa loại entry và các ràng buộc schema |

Ví dụ một entry có thể có `cn=Lan Nguyen` nhưng `displayName=Lan N. (Sales)`. Ánh xạ hai trường riêng:

```java
@Attribute(name = "cn")
private String fullName;

@Attribute(name = "displayName")
private String displayLabel;
```

Sẽ giữ lại sự khác biệt của dữ liệu. Nếu cả hai field đều ánh xạ vào `cn`, ứng dụng có thể vô tình làm mất ý nghĩa của `displayName` trong model và gây nhầm lẫn khi cập nhật.

**Không tự tạo tên attribute** bằng cách đoán từ tên property Java: `fullName`, `primaryEmail` hoặc `teamId` không nhất thiết là attribute type được LDAP server định nghĩa. Khi tích hợp hệ thống thật, phải đối chiếu schema hoặc tài liệu của directory server đang sử dụng.

## 8. Thuộc tính đơn trị và đa trị

LDAP phân biệt **attribute type chỉ cho một giá trị** (*SINGLE-VALUE*) và attribute type có thể chứa nhiều giá trị. Java cũng cần chọn kiểu field phù hợp.

### Thuộc tính đơn trị

Với `mail` là một thuộc tính đang được sử dụng với một giá trị trong ví dụ:

```java
@Attribute(name = "mail")
private String email;
```

ODM có thể ánh xạ một giá trị LDAP về `String`. Tuy nhiên, **kiểu `String` trong Java không làm attribute trở thành SINGLE-VALUE trong schema**. Nếu schema cho phép `mail` đa trị và thực tế server có nhiều giá trị, model đơn trị có thể làm mất thông tin hoặc dẫn đến hành vi phụ thuộc mapper. Cần lựa chọn mô hình theo dữ liệu thật.

### Thuộc tính nhiều giá trị

Một ví dụ thường gặp là entry có nhiều số điện thoại:

```ldif
dn: uid=lan,ou=people,dc=example,dc=org
telephoneNumber: +84 28 1234 5678
telephoneNumber: +84 90 123 4567
```

Trong các phiên bản Spring LDAP ODM có hỗ trợ ánh xạ collection phù hợp, bạn có thể biểu diễn tập giá trị như:

```java
import java.util.Set;

import org.springframework.ldap.odm.annotations.Attribute;

@Attribute(name = "telephoneNumber")
private Set<String> phoneNumbers;
```

Lưu ý:

- Nhiều LDAP attribute được coi là **tập giá trị không có thứ tự**; không dựa vào thứ tự trả về để suy ra “số chính” hay “số phụ”.
- Phải đối chiếu loại collection/array và cơ chế chuyển đổi mà phiên bản ODM đang dùng hỗ trợ.
- Không dùng `Set<String>` để biểu diễn một attribute thực sự là nhị phân hoặc chứa giá trị DN mà chưa kiểm tra yêu cầu chuyển đổi.
- Khi sửa một tập đa trị, cần xác định rõ nghiệp vụ là **thêm một giá trị**, **xóa một giá trị** hay **thay toàn bộ tập**.
- Không giả định việc đặt `null` hoặc một collection rỗng luôn tương ứng cùng một ModifyRequest trên mọi cách cập nhật; hãy kiểm chứng hành vi của API ODM.

### Giá trị nhị phân và thuộc tính đặc biệt

Một số attribute như `jpegPhoto` hoặc chứng chỉ có giá trị nhị phân. Không nên mặc định chúng có thể ánh xạ thành `String`. Các phiên bản Spring LDAP có cơ chế cấu hình kiểu dữ liệu và chuyển đổi cho các tình huống này; cần xem hợp đồng annotation/converter thực tế để chọn `byte[]` hoặc kiểu thích hợp.

Đừng đưa ảnh, chứng chỉ hoặc thuộc tính nhạy cảm vào DTO tìm kiếm thông thường nếu chỉ cần `uid` và `cn`. Điều đó làm tăng băng thông, bộ nhớ và phạm vi dữ liệu truy cập.

## 9. `@Attribute` không thay thế `@Id` hoặc `@DnAttribute`

Một lỗi thiết kế phổ biến là nghĩ rằng sửa field được ánh xạ bằng `@Attribute(name = "uid")` cũng sẽ tự đổi DN của entry.

Giả sử entry đang ở:

```text
DN: uid=lan,ou=people,dc=example,dc=org
uid: lan
```

Java entity có:

```java
@Id
private Name dn;

@Attribute(name = "uid")
private String username;
```

Nếu ứng dụng gán:

```java
person.setUsername("lan.tran");
```

thì nó **chỉ đang thay đổi giá trị field Java**, không phải thao tác rename của LDAP. Khi cập nhật ODM, server có thể từ chối sửa giá trị thuộc RDN, hoặc dữ liệu và DN không khớp với kỳ vọng của ứng dụng. **Không thể suy ra DN tự động đổi thành `uid=lan.tran,...`.**

Để đổi định danh:

```text
uid=lan,ou=people,dc=example,dc=org
        ↓ LDAP Modify DN
uid=lan.tran,ou=people,dc=example,dc=org
```

cần dùng thao tác rename/move thích hợp, ví dụ `LdapTemplate.rename(oldDn, newDn)`, với quyền ACL và hỗ trợ server phù hợp.

### `@DnAttribute` dùng để làm gì?

`@DnAttribute` hỗ trợ liên kết một field với thành phần đặt tên của DN trong cơ chế ODM, khác với `@Attribute` là ánh xạ attribute của entry. Nó hữu ích khi một thuộc tính như `uid` còn tham gia RDN, nhưng cấu hình đúng phụ thuộc vị trí RDN, base DN và mô hình của entity.

Không nên gắn `@DnAttribute` một cách tùy tiện rồi bỏ qua quá trình rename. Thao tác **đổi DN của entry trên server** vẫn cần được thiết kế rõ ràng; logic đặt tên, cập nhật thuộc tính RDN và chuyển OU phải phù hợp schema.

### `@Id` là DN, không phải khóa nghiệp vụ bất biến

DN có thể thay đổi khi entry được rename/move. Nếu hệ thống khác lưu chuỗi DN làm khóa lâu dài, cần tính đến tham chiếu sau rename. Tùy server, có thể có thuộc tính định danh ổn định như `entryUUID` hoặc `objectGUID`, nhưng sự tồn tại, cách đọc và quyền truy cập khác nhau. Không nên giả định LDAP DN là ID bất biến chỉ vì nó được đánh dấu `@Id` trong entity Java.

## 10. Cập nhật ODM: annotation không có nghĩa được phép ghi

Spring LDAP cung cấp các thao tác ODM như `LdapTemplate.update(...)` ở những phiên bản hỗ trợ. Ví dụ:

```java
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public final class DirectoryEmailService {
    private final LdapTemplate ldapTemplate;

    public DirectoryEmailService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public void updateEmail(String username, String newEmail) {
        Name relativeDn = LdapNameBuilder.newInstance("ou=people")
                .add("uid", username)
                .build();

        DirectoryPerson person =
                ldapTemplate.findByDn(relativeDn, DirectoryPerson.class);

        person.setEmail(newEmail);
        ldapTemplate.update(person);
    }
}
```

Việc `person.setEmail(...)` thay đổi Java field, còn `ldapTemplate.update(person)` là lúc Spring LDAP thực hiện thao tác cần thiết lên directory theo ánh xạ ODM.

Tuy nhiên, cần lưu ý:

1. **Schema vẫn quyết định** attribute có được phép trên object class hay không, kiểu dữ liệu và số lượng giá trị.
2. **ACL của server vẫn quyết định** tài khoản bind có được phép sửa `mail` hay không.
3. **Không phải mọi thay đổi field Java đều là một lệnh LDAP Modify riêng**; API ODM có quy tắc cập nhật/so sánh trạng thái của phiên bản thư viện.
4. **Không dùng entity đọc thiếu dữ liệu như một bản ghi đầy đủ để cập nhật một cách mù quáng.** Nếu truy vấn chỉ trả về một số thuộc tính, các field khác có thể trống; việc cập nhật lại entity cần được kiểm chứng để tránh làm mất dữ liệu.
5. Nếu chỉ muốn sửa **một attribute cụ thể**, có thể chọn API sửa thuộc tính tường minh của `LdapTemplate`/`DirContextOperations` thay vì phụ thuộc vào trạng thái của toàn entity.
6. Kết nối phải được bảo vệ bằng LDAPS hoặc StartTLS có xác thực chứng chỉ; mật khẩu và DN tài khoản dịch vụ phải lấy từ cơ chế cấu hình an toàn.

### Khi chỉ cần sửa một thuộc tính

Nếu mục tiêu là thay duy nhất `mail`, một lựa chọn dễ kiểm soát là:

```java
import javax.naming.Name;

import org.springframework.ldap.core.DirContextOperations;
import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

Name dn = LdapNameBuilder.newInstance("ou=people")
        .add("uid", "lan")
        .build();

DirContextOperations entry = ldapTemplate.lookupContext(dn);
entry.setAttributeValue("mail", "lan.new@example.org");
ldapTemplate.modifyAttributes(entry);
```

Cách này dùng tên LDAP attribute **`mail`** trực tiếp, không cần Java field `email`. Chọn ODM hay thao tác tường minh tùy nhu cầu: ODM phù hợp với model thống nhất, còn thao tác theo attribute có thể rõ ràng hơn khi chỉ cập nhật một trường.

**Lưu ý:** Ví dụ sửa trực tiếp trên giả định `ldapTemplate` đã được tạo và context hiện tại có đủ quyền. Mọi thao tác sửa dữ liệu phải được kiểm thử trên directory thử nghiệm trước khi áp dụng vào môi trường thật.

## 11. Projection: yêu cầu trả về những attribute nào?

Khi tìm kiếm LDAP, ứng dụng có thể chỉ yêu cầu các attribute cần thiết:

```java
LdapQuery query = LdapQueryBuilder.query()
        .base("ou=people")
        .attributes("uid", "cn", "mail")
        .where("uid").is("lan");
```

Danh sách trong `.attributes(...)` dùng **tên LDAP attribute**. Nó không dùng tên Java property như `username`, `fullName` hay `email`.

Có hai hợp đồng cần giữ nhất quán:

| Vị trí | Sử dụng tên gì? | Ví dụ |
| --- | --- | --- |
| `@Attribute(name = "...")` | Tên LDAP attribute | `@Attribute(name = "mail")` |
| `LdapQueryBuilder.where(...)` | Tên LDAP attribute | `where("mail")` |
| `LdapQueryBuilder.attributes(...)` | Tên LDAP attribute | `attributes("uid", "mail")` |
| Code Java gọi getter/setter | Tên property/method Java | `person.getEmail()` |
| `@Id` | DN của entry | `Name dn` |

Nếu query chỉ yêu cầu `uid` và `cn`, bạn không nên kỳ vọng `email` (được map từ `mail`) có giá trị, dù server thực tế lưu `mail`. Một DTO thiếu thuộc tính có thể dùng cho **đọc danh sách**, nhưng không nên dùng ngay như entity đầy đủ để thực hiện cập nhật toàn phần.

Ở một số trường hợp, các API ODM có thể tự thêm các thuộc tính phục vụ ánh xạ entry; tuy nhiên, code ứng dụng vẫn cần nêu rõ những trường nghiệp vụ cần đọc. Không dùng `@Attribute` để suy ra mọi truy vấn sẽ luôn lấy toàn bộ thuộc tính.

## 12. Những lỗi thực tế thường gặp

| Hiện tượng | Nguyên nhân thường gặp | Hướng xử lý |
| --- | --- | --- |
| Field `email` luôn rỗng | Dùng `@Attribute(name = "email")` trong khi schema có `mail` | Đổi annotation sang tên attribute thực: `mail` |
| `cn` có dữ liệu nhưng `displayLabel` rỗng | `displayName` khác `cn` và entry thiếu `displayName` | Kiểm tra LDAP entry, schema, quyền và ánh xạ |
| Java compile được nhưng cập nhật LDAP thất bại | Annotation không kiểm tra schema/ACL | Xem mã lỗi server, object classes và quyền ghi |
| Giá trị đa trị chỉ xuất hiện một phần | Field Java dùng kiểu đơn trị | Chọn collection/array phù hợp và xác minh mapping |
| Dùng `.where("email")` không tìm được entry | Filter dùng tên field Java thay vì LDAP attribute | Dùng `.where("mail")` |
| Đổi `username` nhưng DN không đổi | `@Attribute` không tự thực hiện LDAP Modify DN | Thiết kế rename/move và kiểm tra thuộc tính RDN |
| Đổi tên field Java làm mất ánh xạ | Dựa vào tên field mặc định mà không cập nhật mapping | Ghi `name` tường minh và kiểm thử sau refactor |
| Truy vấn trả entity thiếu vài giá trị | Projection, ACL hoặc attribute không tồn tại | Kiểm tra danh sách thuộc tính trả về, quyền và schema |
| Cập nhật entity làm mất dữ liệu không chủ ý | Entity không đầy đủ hoặc logic cập nhật không đúng kỳ vọng | Đọc đủ dữ liệu trước cập nhật hoặc sửa từng attribute có chủ đích |
| Binary attribute bị ép thành `String` sai | Chọn sai kiểu Java hoặc converter | Đối chiếu syntax LDAP và cấu hình ODM/JNDI |
| Tên attribute có chữ hoa khác nhau trong output | LDAP có ngữ nghĩa tên schema riêng, mapper hiển thị có thể khác | Chuẩn hóa tên annotation; không lẫn với case của giá trị |
| Entry không được map vào lớp ODM | `@Entry`, object classes, base hoặc DN không phù hợp | Kiểm tra cấu trúc DIT, base và annotation |

Một số lỗi có vẻ là lỗi mapping nhưng gốc vấn đề lại nằm ở server: schema thay đổi, ACL che thuộc tính, ứng dụng đọc nhầm subtree hoặc kết nối tới replica chưa đồng bộ. Trước khi sửa tên annotation, hãy xác minh **DN thực**, **objectClass**, **attribute type** và **thuộc tính được tài khoản bind nhìn thấy**.

## 13. Kiểm thử ánh xạ `@Attribute`

Để bảo đảm code không âm thầm phụ thuộc vào tên field Java, cần kiểm thử bằng dữ liệu có tên LDAP rõ ràng.

### Bảng kịch bản kiểm thử

| Kiểm thử | Dữ liệu mẫu | Kết quả mong đợi |
| --- | --- | --- |
| Ánh xạ tên khác nhau | LDAP `mail=lan@example.org`, Java field `email` | `person.getEmail()` nhận đúng giá trị |
| Ánh xạ trùng tên | LDAP `givenName=Lan`, field `givenName` | Giá trị giữ nguyên |
| Thuộc tính tùy chọn vắng mặt | Entry không có `displayName` | Java xử lý thiếu giá trị an toàn |
| Thuộc tính đa trị | Hai giá trị `telephoneNumber` | Model đa trị nhận đủ theo hỗ trợ ODM |
| Sửa một thuộc tính | `mail` được cập nhật | DN và các attribute không liên quan được bảo toàn |
| Đổi DN/RDN | `uid=lan` → `uid=lan.tran` | Phải dùng rename; không chỉ setter của entity |
| Tên annotation không hợp lệ | `@Attribute(name="unknownField")` | Phát hiện qua kiểm thử/schema server |
| Projection thiếu thuộc tính | Chỉ request `uid` và `cn` | Không coi `mail` vắng mặt là dữ liệu đã bị xóa |

### Kiểm thử tích hợp trong directory thử nghiệm

Một quy trình kiểm thử có thể là:

1. Chuẩn bị test LDAP server hoặc directory thử nghiệm có schema phù hợp với `inetOrgPerson`.
2. Tạo entry `uid=lan,ou=people,dc=example,dc=org` với `uid`, `cn`, `sn` và `mail` rõ ràng.
3. Dùng `LdapTemplate.findByDn(...)` để đọc entry thành `DirectoryPerson`.
4. Xác nhận `getUsername()`, `getFullName()`, `getFamilyName()` và `getEmail()`.
5. Sửa `email` và cập nhật theo API đã chọn.
6. Đọc lại entry bằng JNDI/`LdapTemplate` để xác nhận **LDAP `mail` thực sự đã đổi**, không chỉ field Java.
7. Kiểm tra rằng DN, `cn` và `sn` không thay đổi ngoài dự kiến.
8. Lặp lại với `displayName` thiếu hoặc tài khoản không có quyền đọc `mail`.

Không cần kết nối LDAP sản xuất để xác minh các nguyên tắc ánh xạ này. Với integration test, nên dùng dữ liệu giả, chứng chỉ TLS phù hợp và tài khoản có quyền giới hạn theo OU thử nghiệm.

### Kiểm thử metadata của annotation

Có thể bổ sung một unit test đơn giản để phát hiện refactor làm mất tên mapping:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;

import java.lang.reflect.Field;

import org.junit.jupiter.api.Test;
import org.springframework.ldap.odm.annotations.Attribute;

class DirectoryPersonMappingTest {
    @Test
    void emailFieldMapsToLdapMailAttribute() throws Exception {
        Field emailField = DirectoryPerson.class.getDeclaredField("email");
        Attribute annotation = emailField.getAnnotation(Attribute.class);

        assertEquals("mail", annotation.name());
    }
}
```

Đoạn test kiểm tra annotation trong Java, **không chứng minh server có schema đúng, ACL cho phép hoặc một lần update sẽ thành công**. Vì vậy, test metadata nên bổ sung cho integration test chứ không thay thế nó.

## 14. Bài thực hành

Giả sử LDAP thử nghiệm lưu entry:

```ldif
dn: uid=mai,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: mai
cn: Mai Tran
sn: Tran
givenName: Mai
displayName: Mai T.
mail: mai@example.org
telephoneNumber: +84 90 000 0001
telephoneNumber: +84 90 000 0002
```

Yêu cầu ứng dụng:

- Field `login` đọc LDAP `uid`.
- Field `name` đọc `cn`.
- Field `surname` đọc `sn`.
- Field `label` đọc `displayName`.
- Field `primaryEmail` đọc `mail`.
- Field `phones` chứa nhiều `telephoneNumber` nếu phiên bản ODM hỗ trợ kiểu collection phù hợp.
- Field `dn` lưu DN của entry, không thay bằng `uid`.

**Bài A – Thiết kế entity.** Tạo lớp Java `DirectoryAccount` có `@Entry`, `@Id` và các `@Attribute(name = "...")` tường minh. Giải thích vì sao tên field `primaryEmail` không thể đem dùng nguyên văn trong `LdapQueryBuilder.where(...)`.

**Bài B – Truy vấn.** Dùng `LdapTemplate` để tìm entry có `uid=mai`. Chỉ yêu cầu những attribute cần thiết, ánh xạ thành entity và in ra tên cùng email. Không in mật khẩu hay các attribute nhạy cảm.

**Bài C – Cập nhật.** Đổi `mail` của tài khoản thử nghiệm thành `mai.new@example.org`. Đọc lại từ server để xác minh giá trị. Kiểm tra DN vẫn là `uid=mai,ou=people,dc=example,dc=org`.

**Bài D – Phân tích sai sót.** Nếu một lập trình viên đổi `@Attribute(name = "mail")` thành `@Attribute(name = "primaryEmail")`, hãy mô tả hậu quả có thể xảy ra khi đọc và ghi, cũng như cách test phát hiện lỗi.

### Câu hỏi tự kiểm tra

**Câu 1.** Trong `@Attribute(name = "mail") private String email;`, chuỗi `mail` có nghĩa gì?

**Đáp án:** Đó là **tên LDAP attribute** mà field `email` được ánh xạ tới; không phải tên field Java và cũng không phải giá trị email.

**Câu 2.** Đổi tên field Java từ `email` sang `primaryEmail`, giữ nguyên `@Attribute(name = "mail")`, có phải đổi schema LDAP không?

**Đáp án:** Không. Tên attribute LDAP vẫn là `mail`; thay đổi chủ yếu thuộc phía model Java và mã ứng dụng liên quan.

**Câu 3.** Nếu đã ánh xạ `@Attribute(name = "mail") private String email;`, có được tìm kiếm bằng `where("email")` không?

**Đáp án:** Không nên, trừ khi `email` thật sự là một LDAP attribute type được server định nghĩa. Filter phải dùng **tên LDAP**, ở đây là `where("mail")`.

**Câu 4.** Vì sao `@Id private Name dn;` khác `@Attribute(name = "uid") private String username;`?

**Đáp án:** `@Id` chứa DN đầy đủ/tương đối theo cơ chế ODM, còn field `username` chứa giá trị `uid`. `uid` có thể nằm trong RDN nhưng không đại diện cho toàn bộ DN.

**Câu 5.** Một attribute có nhiều giá trị nhưng entity dùng `String`. Điều gì cần kiểm tra?

**Đáp án:** Kiểm tra schema, dữ liệu thực tế và khả năng ánh xạ collection/array của ODM. Field đơn trị có thể không biểu diễn đủ toàn bộ giá trị.

**Câu 6.** `@Attribute` có đảm bảo tài khoản bind được phép sửa `mail` không?

**Đáp án:** Không. Annotation chỉ mô tả mapping; ACL, schema và chính sách của LDAP server quyết định có sửa được hay không.

**Câu 7.** Đổi giá trị field `username` từ `mai` thành `mai.tran` có làm entry tự chuyển sang DN mới không?

**Đáp án:** Không. Đổi RDN/DN cần thao tác LDAP Modify DN/rename phù hợp; setter hoặc mapping attribute không tự bảo đảm rename.

## Ghi nhớ

**`@Attribute(name = "...")` ánh xạ field Java đến tên attribute thực trong LDAP schema.** Tên Java được chọn theo nhu cầu ứng dụng, còn tên trong annotation phải theo directory server. `@Attribute` không thay `@Id`, không tự đổi DN, không tạo schema, không cấp quyền truy cập và không sửa cú pháp filter. Khi dùng Spring LDAP ODM, hãy viết tên attribute rõ ràng, đối chiếu schema, xử lý dữ liệu đa trị/thiếu giá trị, giới hạn thuộc tính truy vấn và kiểm thử cả chiều đọc lẫn chiều cập nhật trên LDAP server thử nghiệm.
