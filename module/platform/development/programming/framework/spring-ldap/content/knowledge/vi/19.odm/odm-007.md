# @Transient annotation với dữ liệu dẫn xuất trong Spring LDAP ODM

Khi ứng dụng Java dùng **Spring LDAP** để ánh xạ entry của thư mục LDAP thành entity, không phải mọi thông tin hữu ích cho giao diện hay nghiệp vụ đều cần được lưu vào directory. Ví dụ, nhãn `"Lan Nguyen (lan)"` có thể tạo từ `cn` và `uid`; trạng thái `hasEmail` có thể tính từ `mail`. Nếu các giá trị này chỉ phục vụ hiển thị hoặc xử lý tạm thời, lưu chúng như một thuộc tính LDAP riêng sẽ tạo dữ liệu trùng lặp và có nguy cơ không đồng bộ.

Trong chương **ODM (Object-Directory Mapping)**, annotation `@Transient` cho biết một **field của entity không được ánh xạ thành thuộc tính LDAP**. Bài này trình bày chính xác annotation cần import, cách sử dụng với dữ liệu dẫn xuất, thời điểm tính lại giá trị, quan hệ với `@DnAttribute`, cách kiểm tra khi `LdapTemplate.create/update/findByDn` và các tình huống dễ nhầm với Java/JPA.

## 1. ODM mặc định xử lý field như thế nào?

Spring LDAP ODM cho phép viết một entity Java đại diện cho entry LDAP. Ví dụ:

```ldif
dn: uid=lan,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: lan
cn: Lan Nguyen
sn: Nguyen
mail: lan@example.org
```

Trong ODM, một class được đánh dấu `@Entry` và có field `@Id` sẽ cung cấp metadata để `LdapTemplate` đọc hoặc ghi entry. Theo quy tắc ánh xạ của Spring LDAP, **các field thường được ánh xạ theo tên field**, trừ khi có annotation quy định cách ánh xạ khác.

| Annotation / thành phần | Vai trò |
| --- | --- |
| `@Entry(objectClasses = {...})` | Khai báo class đại diện những object class nào của LDAP. |
| `@Id` trên `javax.naming.Name` | Chỉ DN định danh entry. |
| `@Attribute(name = "cn")` | Ánh xạ field sang thuộc tính LDAP có tên xác định. |
| Field không có `@Attribute` | Thông thường vẫn được ánh xạ sang thuộc tính LDAP **cùng tên với field**. |
| **`@Transient`** | Loại field khỏi ánh xạ thuộc tính LDAP của ODM. |
| `@DnAttribute` | Đọc thành phần của DN vào field; có thể kết hợp với `@Transient`. |

Ví dụ, nếu class có field `displayLabel` và quên đánh dấu `@Transient`, ODM có thể cố đọc/ghi một thuộc tính LDAP tên `displayLabel`. Thuộc tính đó có thể **không tồn tại trong schema**, dẫn đến lỗi khi tạo/cập nhật entry, hoặc vô tình lưu một giá trị dẫn xuất nếu schema cho phép.

### Annotation đúng cần import

```java
import org.springframework.ldap.odm.annotations.Transient;
```

Annotation này có đích là **field** (`@Target(FIELD)`) và tồn tại trong runtime (`@Retention(RUNTIME)`). Nó thuộc **Spring LDAP ODM**, không phải annotation chỉ dành cho JPA, Spring Data Commons hay từ khóa `transient` của Java.

## 2. Dữ liệu dẫn xuất và dữ liệu lưu trữ

**Dữ liệu lưu trữ** là nguồn dữ liệu được directory quản lý, ví dụ `uid`, `cn`, `sn` và `mail`. **Dữ liệu dẫn xuất** là giá trị được tính dựa trên dữ liệu lưu trữ hoặc ngữ cảnh khác.

| Field Java | Nguồn giá trị | Nên lưu LDAP? |
| --- | --- | --- |
| `uid` | Thuộc tính LDAP `uid` | Có, nếu schema và nghiệp vụ sử dụng. |
| `cn` | Thuộc tính LDAP `cn` | Có. |
| `mail` | Thuộc tính LDAP `mail` | Có, nếu có dữ liệu. |
| `displayLabel` | Từ `cn` và `uid` | Thường **không**; đánh dấu `@Transient` nếu là field. |
| `hasEmail` | Từ việc `mail` có giá trị hợp lệ theo quy tắc ứng dụng | Thường **không**; tính từ `mail`. |
| `lastViewedAt` | Thời điểm người dùng xem entry trên UI | Không nên lưu vào LDAP theo cơ chế ODM thông thường. |
| `departmentFromDn` | Thành phần `ou` trong DN, nếu cấu trúc DN có ý nghĩa đó | Có thể dùng `@DnAttribute` kết hợp `@Transient`. |

Quy tắc quan trọng là **xác định nguồn sự thật (source of truth)**. Nếu `displayLabel` luôn tính được từ `cn` và `uid`, không cần một thuộc tính LDAP thứ ba để lưu lại cùng thông tin. Ngược lại, nếu một tên hiển thị được người dùng chỉnh sửa độc lập và phải tồn tại lâu dài, đó có thể là dữ liệu thực sự cần lưu, không còn là dẫn xuất thuần túy.

## 3. Entity ODM dùng @Transient cho field dẫn xuất

Ví dụ sau mô tả người dùng LDAP có nhãn hiển thị và cờ kiểm tra có email. Hai field này tồn tại trong bộ nhớ Java nhưng không được ODM ghi vào directory.

```java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;
import org.springframework.ldap.odm.annotations.Transient;

@Entry(objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
})
public class DirectoryPerson {

    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String uid;

    @Attribute(name = "cn")
    private String cn;

    @Attribute(name = "sn")
    private String sn;

    @Attribute(name = "mail")
    private String mail;

    @Transient
    private String displayLabel;

    @Transient
    private boolean hasEmail;

    // Constructor không tham số để ODM khởi tạo object.
    public DirectoryPerson() {
    }

    public void refreshDerivedFields() {
        String shownName =
                cn == null || cn.trim().isEmpty() ? uid : cn;

        if (shownName == null) {
            displayLabel = null;
        } else if (uid == null || uid.trim().isEmpty()) {
            displayLabel = shownName;
        } else {
            displayLabel = shownName + " (" + uid + ")";
        }

        hasEmail = mail != null && !mail.trim().isEmpty();
    }

    public Name getDn() {
        return dn;
    }

    public void setDn(Name dn) {
        this.dn = dn;
    }

    public String getUid() {
        return uid;
    }

    public void setUid(String uid) {
        this.uid = uid;
    }

    public String getCn() {
        return cn;
    }

    public void setCn(String cn) {
        this.cn = cn;
    }

    public String getSn() {
        return sn;
    }

    public void setSn(String sn) {
        this.sn = sn;
    }

    public String getMail() {
        return mail;
    }

    public void setMail(String mail) {
        this.mail = mail;
    }

    public String getDisplayLabel() {
        return displayLabel;
    }

    public boolean isHasEmail() {
        return hasEmail;
    }
}
```

Với dữ liệu LDIF ở trên, sau khi gọi `refreshDerivedFields()`:

```text
dn           = uid=lan,ou=people       (tương đối với ContextSource base)
uid          = lan                    (từ LDAP)
cn           = Lan Nguyen             (từ LDAP)
sn           = Nguyen                 (từ LDAP)
mail         = lan@example.org        (từ LDAP)
displayLabel = Lan Nguyen (lan)       (tính trong Java, @Transient)
hasEmail     = true                   (tính trong Java, @Transient)
```

Giả sử `ContextSource` đặt base DN `dc=example,dc=org`, field `dn` ở ví dụ là DN tương đối của entry trong phạm vi base đó. Không thêm `dc=example,dc=org` hai lần khi dựng DN truy vấn.

### @Transient có tác dụng ở đâu?

Với entity này:

- `LdapTemplate.findByDn(...)` nạp `uid`, `cn`, `sn`, `mail` và DN theo ODM. ODM **bỏ qua** việc nạp `displayLabel` và `hasEmail` từ LDAP.
- `LdapTemplate.create(person)` không đưa `displayLabel` hay `hasEmail` thành thuộc tính LDAP của entry mới.
- `LdapTemplate.update(person)` không ghi những field đó như thay đổi thuộc tính LDAP.
- `@Transient` **không chạy** `refreshDerivedFields()`, không tạo một biểu thức tính toán và không tự bảo đảm giá trị dẫn xuất luôn mới.

Hai giá trị dẫn xuất chỉ được tính vì **mã Java gọi phương thức** `refreshDerivedFields()`. Nếu không gọi, `displayLabel` sau khi ODM nạp đối tượng thường vẫn là `null`, còn `hasEmail` mang giá trị mặc định `false`, kể cả khi `mail` có dữ liệu.

## 4. Tính dữ liệu sau khi đọc LDAP

Giả sử đã cấu hình `ContextSource` với base `dc=example,dc=org` và inject `LdapTemplate`. Có thể đặt phần tính dẫn xuất trong service hoặc repository wrapper để tầng giao diện không quên gọi nó.

```java
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public class PersonDirectoryService {
    private final LdapTemplate ldapTemplate;

    public PersonDirectoryService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public DirectoryPerson findByUid(String uid) {
        if (uid == null || uid.trim().isEmpty()) {
            throw new IllegalArgumentException("uid không được rỗng");
        }

        Name relativeDn = LdapNameBuilder.newInstance()
                .add("ou", "people")
                .add("uid", uid)
                .build();

        DirectoryPerson person =
                ldapTemplate.findByDn(relativeDn, DirectoryPerson.class);

        person.refreshDerivedFields();
        return person;
    }
}
```

Ở đây `findByDn` dùng mapping ODM của Spring LDAP; không cần tự viết `ContextMapper` cho mỗi thuộc tính. `LdapNameBuilder` giúp escape các ký tự đặc biệt trong giá trị RDN của `uid`.

Nếu ứng dụng dùng `ldapTemplate.find(query, DirectoryPerson.class)` để tìm nhiều entry, cũng cần tính lại trên **mỗi entity** trước khi trả về kết quả:

```java
import java.util.List;
import org.springframework.ldap.query.LdapQuery;
import org.springframework.ldap.query.LdapQueryBuilder;

// Đặt trong một phương thức có sẵn ldapTemplate:
LdapQuery query = LdapQueryBuilder.query()
        .base("ou=people")
        .where("objectClass").is("inetOrgPerson");

List<DirectoryPerson> people =
        ldapTemplate.find(query, DirectoryPerson.class);

people.forEach(DirectoryPerson::refreshDerivedFields);
```

Khi làm việc với dữ liệu nhạy cảm, chỉ trả ra các trường ứng dụng cần, sử dụng quyền đọc LDAP phù hợp và cấu hình TLS ở tầng kết nối. `@Transient` điều khiển **ODM persistence**, không phải quyền truy cập LDAP.

### Vì sao phải tính lại sau khi thay đổi source field?

```java
DirectoryPerson person = service.findByUid("lan");

System.out.println(person.getDisplayLabel());
// Lan Nguyen (lan)

person.setCn("Lan N.");
System.out.println(person.getDisplayLabel());
// Vẫn là Lan Nguyen (lan) nếu chưa tính lại.

person.refreshDerivedFields();
System.out.println(person.getDisplayLabel());
// Lan N. (lan)
```

Tình trạng nhãn bị cũ là vấn đề **đồng bộ giữa các field trong bộ nhớ**, không phải lỗi của LDAP. Vì vậy, khi giữ giá trị dẫn xuất dạng field, ứng dụng phải xác định điểm tính lại: sau khi đọc, sau khi thay đổi input hoặc ngay trước khi xuất DTO.

## 5. Phương án tránh trạng thái cũ: computed getter

Nếu giá trị dễ tính và không cần lưu cache, getter tính trực tiếp thường đơn giản hơn. Ta không cần thêm field `displayLabel` trong entity:

```java
public String getDisplayLabel() {
    String name = cn == null || cn.trim().isEmpty() ? uid : cn;
    if (name == null) {
        return null;
    }
    return uid == null || uid.trim().isEmpty()
            ? name
            : name + " (" + uid + ")";
}
```

Đoạn trên là **phương án thay thế** cho field `@Transient private String displayLabel` và getter tương ứng trong class ví dụ, không phải hai getter cùng tồn tại trong một class. Vì Spring LDAP ODM ánh xạ **field**, computed getter không có backing field để lưu LDAP theo cơ chế mapping mặc định.

| Tiêu chí | Field `@Transient` và phương thức refresh | Computed getter |
| --- | --- | --- |
| Giá trị được giữ trong object | Có, cho tới lần refresh tiếp theo | Tính lại mỗi khi gọi getter |
| Nguy cơ bị cũ khi `cn` đổi | Có nếu quên refresh | Thấp hơn khi chỉ phụ thuộc các field hiện tại |
| Chi phí tính toán | Có thể tính một lần rồi tái sử dụng | Tính mỗi lần đọc |
| Phù hợp với | Dữ liệu tổng hợp phức tạp, tính tại một bước xử lý rõ ràng | Biểu thức đơn giản, nhẹ, xác định được từ entity |

Với dữ liệu dẫn xuất phụ thuộc **môi trường bên ngoài** (ví dụ quyền của người gọi, thời điểm hiện tại, dịch vụ khác), tránh nhét cả ngữ cảnh đó vào entity ODM. Nên dùng **service hoặc DTO** để tính tại nơi có đủ thông tin, vì một getter tính trên entity có thể thiếu ngữ cảnh, tốn chi phí hoặc tạo truy vấn LDAP ngoài ý muốn.

## 6. Cập nhật entity: field dẫn xuất không được persist

Giả sử `DirectoryPerson` đã được nạp thành công, sau đó ứng dụng đổi `mail`:

```java
DirectoryPerson person = service.findByUid("lan");

// Dữ liệu LDAP thật cần cập nhật:
person.setMail("lan.new@example.org");

// Dữ liệu Java dẫn xuất cũng cần cập nhật cho caller:
person.refreshDerivedFields();

// ODM chỉ dùng các field được ánh xạ khi ghi lên LDAP.
ldapTemplate.update(person);
```

Sau `update`, trường `mail` trong LDAP có thể đổi sang `lan.new@example.org` nếu thao tác ghi được phép và thành công. Hai field `displayLabel` và `hasEmail` **không** được ghi thành thuộc tính LDAP dù đang có giá trị trên entity.

Quy tắc này áp dụng cho cả `create` và `update` ở mức ODM, nhưng không có nghĩa mọi thay đổi khác sẽ tự thành công: máy chủ vẫn kiểm tra **schema, ACL, quyền bind, kết nối và trạng thái entry**.

**Một tình huống dễ nhầm:** Nếu chỉ đổi `person.displayLabel` trong bộ nhớ mà không đổi `cn` hoặc `uid`, rồi gọi `ldapTemplate.update(person)`, ứng dụng không thể kỳ vọng LDAP lưu nhãn đó; field đã được loại khỏi mapping theo chủ ý. Muốn lưu một giá trị độc lập, cần thiết kế thuộc tính LDAP phù hợp schema và ánh xạ như một field thực sự được persist.

### Đọc lại để xác minh

Sau khi cập nhật thành công trong môi trường thử nghiệm:

```java
DirContextOperations context = ldapTemplate.lookupContext(person.getDn());

String storedMail = context.getStringAttribute("mail");
String storedCn = context.getStringAttribute("cn");

// Không mong chờ LDAP sinh ra attribute "displayLabel"
// chỉ vì object Java có field @Transient đó.
String storedDisplayLabel = context.getStringAttribute("displayLabel");
```

Đoạn kiểm tra giả định `person`, `ldapTemplate` và kiểu `DirContextOperations` đã có trong scope; cần import `org.springframework.ldap.core.DirContextOperations`. Nếu directory **đã có sẵn** attribute tên `displayLabel` từ thao tác bên ngoài, ODM với `@Transient` không tự xóa attribute đó. Do đó kiểm tra không có attribute chỉ có ý nghĩa khi dữ liệu đầu vào thử nghiệm đã được biết rõ.

## 7. @Transient kết hợp @DnAttribute: giá trị lấy từ DN

Ngoài giá trị tính từ thuộc tính LDAP, một field còn có thể lấy thông tin từ thành phần **Distinguished Name**. Spring LDAP cung cấp `@DnAttribute` để ánh xạ một thành phần DN vào field `String`.

Ví dụ minh họa một field chỉ đọc tên nhánh tổ chức từ DN:

```java
import org.springframework.ldap.odm.annotations.DnAttribute;
import org.springframework.ldap.odm.annotations.Transient;

// Bên trong một entity @Entry:
@DnAttribute(value = "ou")
@Transient
private String organizationalUnit;
```

Ý nghĩa:

- `@DnAttribute(value = "ou")` yêu cầu ODM lấy thành phần `ou` từ DN của entry, khi DN chứa thành phần này.
- `@Transient` ngăn field `organizationalUnit` đồng thời được ánh xạ thành **thuộc tính LDAP tên organizationalUnit**.
- Không cần lưu thêm `organizationalUnit: people` trong entry chỉ để phản ánh `ou=people` đã có ở DN.

Tài liệu Spring LDAP đặc biệt lưu ý rằng `@DnAttribute` **không tự loại** field khỏi mapping thuộc tính LDAP. Nếu muốn field chỉ đại diện thành phần DN, cần đánh dấu `@Transient` như ví dụ.

Hãy thử trên DN có cấu trúc xác định trong môi trường thật, vì vị trí các thành phần DN và cách đặt `@Entry.base` có thể ảnh hưởng phép trích xuất. `@DnAttribute(index = ...)` còn được dùng để **tính DN khi tạo/cập nhật** entity và có thể khiến thao tác thay đổi DN khi giá trị field thay đổi. Chỉ dùng index khi đã thiết kế rõ quy tắc tạo DN; một field chỉ để hiển thị đôi khi không cần tham gia vào quá trình này.

## 8. Phân biệt các loại Transient trong Java

Nhiều framework cùng có annotation tên `Transient`. Chúng không phải các lựa chọn có thể thay thế tùy ý.

| Cách khai báo | Phạm vi áp dụng | Có bảo đảm Spring LDAP ODM bỏ qua field? |
| --- | --- | --- |
| `org.springframework.ldap.odm.annotations.Transient` | **Spring LDAP ODM** | **Có**. |
| `jakarta.persistence.Transient` hoặc `javax.persistence.Transient` | JPA/ORM | Không phải annotation Spring LDAP ODM yêu cầu. |
| `org.springframework.data.annotation.Transient` | Spring Data mapping | Không dùng thay thế cho annotation ODM của Spring LDAP trong ví dụ này. |
| Từ khóa Java `transient` | Java Serialization | Không phải cơ chế khai báo của Spring LDAP ODM; không nên chỉ dựa vào nó. |
| Không có field, chỉ có computed getter | Tính từ các field được ánh xạ | Không có field dẫn xuất để ODM tự persist theo mapping dựa trên field. |

Ví dụ nhập nhầm:

```java
// Sai mục đích nếu muốn loại field khỏi Spring LDAP ODM:
import jakarta.persistence.Transient;

@Transient
private String displayLabel;
```

Trong bài này, cách đúng là:

```java
import org.springframework.ldap.odm.annotations.Transient;

@Transient
private String displayLabel;
```

Khi dự án dùng cả JPA và LDAP ODM, nên đặt entity ở package rõ ràng và rà soát import trong IDE. Với hai annotation có cùng tên, có thể dùng tên đầy đủ tại điểm khai báo để tránh mơ hồ.

## 9. Các lỗi thường gặp và cách phòng tránh

| Triệu chứng | Nguyên nhân có thể | Hướng xử lý |
| --- | --- | --- |
| `create/update` báo LDAP attribute hoặc schema không hợp lệ | Field dẫn xuất chưa đánh dấu `@Transient`, ODM cố ghi tên field như attribute. | Thêm đúng annotation Spring LDAP; kiểm tra schema và các field được ánh xạ. |
| `displayLabel` là `null` sau `findByDn` | `@Transient` ngăn việc đọc mapping, và ứng dụng chưa gọi hàm tính. | Gọi `refreshDerivedFields()` ở service hoặc dùng computed getter. |
| `displayLabel` không đổi khi `cn` đã đổi | Cache dẫn xuất bị cũ. | Refresh sau khi đổi source field hoặc thay bằng computed getter. |
| Giá trị có trong Java nhưng không xuất hiện trong LDAP | Đây có thể là **hành vi đúng** của `@Transient`. | Xác định field có thật sự cần được persist hay không trước khi bỏ annotation. |
| `@Transient` không hoạt động như mong đợi | Import nhầm annotation JPA/Spring Data hoặc dùng sai entity mapping. | Kiểm tra package `org.springframework.ldap.odm.annotations` và phương thức ODM đang gọi. |
| Field lấy từ DN bị ghi như attribute | Chỉ đặt `@DnAttribute` mà không thêm `@Transient`. | Kết hợp hai annotation nếu mục đích là đọc DN mà không persist field. |
| Dẫn xuất sai sau đổi DN hoặc move | Nguồn DN đã thay đổi nhưng dữ liệu hiển thị/cache chưa được tính lại. | Đọc lại entity hoặc cập nhật trạng thái sau thay đổi DN. |
| Field transient rò ra JSON | `@Transient` của ODM không phải cơ chế kiểm soát serialization HTTP. | Dùng DTO hoặc cấu hình JSON serialization riêng; không suy ra dữ liệu sẽ bị ẩn. |

### Tình huống bảo mật

Giả sử ứng dụng tạo field `@Transient boolean isAdmin` dựa trên thông tin nhóm được tra từ server khác. Việc `@Transient` không lưu field xuống LDAP **không tự biến field đó thành một quyết định phân quyền đáng tin cậy**. Quyền truy cập phải được tính từ nguồn được xác thực và đánh giá ở tầng bảo mật tại thời điểm cần thiết. Không dựa vào một cờ cache dẫn xuất có thể bị cũ để cấp quyền.

Tương tự, chú ý dữ liệu LDAP có thể chứa email, số điện thoại, DN nội bộ và các thông tin nhạy cảm khác. Tránh log toàn bộ entity hoặc ghi các field chứa dữ liệu dẫn xuất nhạy cảm ra API mà không kiểm soát.

## 10. Kiểm thử hành vi @Transient

Một phép kiểm thử đầy đủ cần phân biệt **logic tính toán Java** với **tác động lên LDAP**.

### 10.1. Unit test cho phép tính dữ liệu dẫn xuất

Ví dụ JUnit 5 không cần LDAP server:

```java
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;

class DirectoryPersonDerivedTest {

    @Test
    void derivesLabelAndEmailStateFromMappedFields() {
        DirectoryPerson person = new DirectoryPerson();
        person.setUid("lan");
        person.setCn("Lan Nguyen");
        person.setMail("lan@example.org");

        person.refreshDerivedFields();

        assertEquals("Lan Nguyen (lan)", person.getDisplayLabel());
        assertTrue(person.isHasEmail());

        person.setCn("Lan N.");
        person.setMail(null);
        person.refreshDerivedFields();

        assertEquals("Lan N. (lan)", person.getDisplayLabel());
        assertFalse(person.isHasEmail());
    }
}
```

Test trên chứng minh **phép tính trong Java** hoạt động theo quy tắc đã thiết kế. Nó **không kiểm tra** quá trình Spring LDAP ODM lưu field hay bỏ qua field trên server.

### 10.2. Integration test trên directory thử nghiệm

Để xác minh chức năng ODM, dùng LDAP thử nghiệm đã cấu hình schema và quyền ghi phù hợp; không chạy test ghi trên directory sản xuất. Chuẩn bị một entry thử nghiệm có `uid`, `cn`, `sn` và `mail`.

1. Dùng `ldapTemplate.findByDn(testDn, DirectoryPerson.class)` để đọc entry; kiểm tra field có mapping khớp dữ liệu LDAP.
2. Kiểm tra `displayLabel` ban đầu chưa được tính tự động; sau khi gọi `refreshDerivedFields()`, giá trị phải đúng.
3. Đổi `mail` (thuộc tính thật) và tính lại dữ liệu dẫn xuất; gọi `ldapTemplate.update(person)`.
4. Dùng `ldapTemplate.lookupContext(testDn)` để xác minh `mail` đã đổi và các thuộc tính LDAP thiết yếu vẫn còn.
5. Khi entry ban đầu **không có attribute `displayLabel`**, xác minh thao tác update không tạo attribute đó. Không dùng việc không thấy attribute ở một truy vấn thiếu quyền làm bằng chứng duy nhất.
6. Đọc lại entity bằng một lệnh `findByDn` mới; quan sát `displayLabel` cần được tính lại ở ứng dụng, chứng minh nó không phải dữ liệu được ODM lưu.
7. Khôi phục entry thử nghiệm hoặc dọn dữ liệu thử nghiệm đúng quy trình môi trường.

### Ma trận kỳ vọng

| Hành động | Field LDAP `cn/mail` | Field dẫn xuất `displayLabel/hasEmail` |
| --- | --- | --- |
| Đọc bằng ODM | Được map từ entry (nếu server trả về) | Không được map, mang giá trị Java mặc định cho đến khi tự tính. |
| Gọi `refreshDerivedFields()` | Không đổi | Được tính từ field hiện tại. |
| Gọi `ldapTemplate.update(person)` | Có thể ghi thay đổi thật theo mapping | Không được ghi như LDAP attribute. |
| Đọc entity mới sau update | Nhận giá trị hiện tại từ LDAP | Cần tính lại nếu muốn sử dụng. |

Nếu không thể dùng LDAP thử nghiệm, hãy giới hạn kết luận ở unit test phép tính và kiểm tra annotation/source code; **không tuyên bố đã kiểm thử hành vi persist thực tế**.

## 11. Bài tập thực hành

**Yêu cầu:** Ứng dụng hiển thị danh sách người dùng LDAP gồm `uid`, `cn`, `mail`, một nhãn giao diện và trạng thái email có hay không.

1. Tạo class `DirectoryPerson` có `@Entry`, `@Id`, `@Attribute` và đúng hai field `@Transient`.
2. Dùng `LdapTemplate.findByDn` đọc người dùng `uid=lan,ou=people` trong môi trường thử nghiệm.
3. Bỏ lời gọi `refreshDerivedFields()`, quan sát các field dẫn xuất; sau đó thêm lời gọi và so sánh.
4. Đổi `cn` từ `Lan Nguyen` thành `Lan N.` trong bộ nhớ, kiểm tra vì sao nhãn chưa đổi; sửa bằng refresh hoặc computed getter.
5. Cố ý bỏ `@Transient` khỏi `displayLabel` trong bản sao mã thử nghiệm, so sánh metadata ODM: field sẽ được xem là attribute cần ánh xạ và có thể gây lỗi schema khi ghi.
6. Tạo một phương án chỉ sử dụng getter `getDisplayLabel()` thay cho field cached; giải thích ưu và nhược.
7. Nếu có field đọc từ `ou` trong DN, đánh dấu `@DnAttribute` cùng `@Transient` và xác minh giá trị trong môi trường thử nghiệm.

**Câu hỏi tự đánh giá:**

- Vì sao Spring LDAP ODM cần `@Transient` khi entity có field dẫn xuất?
- Annotation `Transient` phải được import từ package nào?
- Vì sao `@Transient` không tự cập nhật `displayLabel` sau khi `cn` thay đổi?
- Tại sao `@DnAttribute` có thể cần kết hợp `@Transient`?
- Java `transient` và JPA `@Transient` có thay thế cho annotation Spring LDAP ODM không?
- Nếu ứng dụng cần ẩn field khỏi JSON response, `@Transient` của ODM có đủ hay không?
- Khi nào nên dùng computed getter, khi nào nên dùng field được cache và đánh dấu `@Transient`?

## 12. Ghi nhớ

- Spring LDAP ODM **ánh xạ field thành LDAP attribute theo mặc định**; `org.springframework.ldap.odm.annotations.Transient` loại field khỏi quá trình lưu/đọc thuộc tính LDAP.
- `@Transient` phù hợp với dữ liệu dẫn xuất, thông tin tạm thời và field chỉ phục vụ ứng dụng.
- Annotation này **không tính toán dữ liệu**, không tự refresh cache, không thay thế cơ chế kiểm soát phân quyền và không quản lý JSON serialization.
- Dùng computed getter cho phép tính đơn giản; với field cached, xác định điểm gọi refresh rõ ràng.
- Khi cần lấy thành phần DN mà không lưu thành attribute, kết hợp `@DnAttribute` và `@Transient` đúng mục đích.
- Kiểm thử phép tính bằng unit test, đồng thời kiểm thử hành vi persist của ODM bằng LDAP thử nghiệm nếu cần xác nhận đầy đủ.
