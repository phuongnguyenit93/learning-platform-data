# Object Directory Mapping (ODM) là gì trong Spring LDAP?

## 1. Bài toán: từ LDAP entry sang đối tượng Java

**Object Directory Mapping (ODM)** là cơ chế ánh xạ dữ liệu của một entry trong thư mục LDAP thành một đối tượng Java, và theo chiều ngược lại, ánh xạ trạng thái đối tượng thành dữ liệu cần ghi xuống LDAP. Trong **Spring LDAP**, ODM giúp lập trình viên làm việc với mô hình có kiểu rõ ràng thay vì phải truy cập từng attribute qua API JNDI hoặc tự viết bộ chuyển đổi cho mọi truy vấn.

Một entry LDAP thông thường có **DN (Distinguished Name)** để định danh vị trí trong cây thư mục, một hoặc nhiều giá trị `objectClass` để xác định schema, và tập các **attribute**. Ví dụ:

```ldif
dn: uid=an,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: an
cn: An Nguyen
sn: Nguyen
mail: an@example.org
```

Nếu một ứng dụng quản lý nhân sự cần hiển thị tên, email và mã người dùng, ta muốn xử lý entry ở dạng:

```java
PersonEntry person = ...;
String username = person.getUid();
String email = person.getEmail();
```

ODM cung cấp cách khai báo rằng `uid` của LDAP tương ứng với property `uid`, `cn` tương ứng với `commonName`, `mail` tương ứng với `email`. Quy tắc này được biểu diễn bằng annotation trên một lớp Java.

Trong module **Spring LDAP**, ODM là một cách tổ chức thao tác entry bên cạnh cách làm thủ công với `LdapTemplate`/`LdapClient`, `DirContextOperations` và `ContextMapper`. Các kiến thức về DN, schema, LDAP filter, xác thực, TLS, pooling và xử lý lỗi vẫn cần thiết: ODM chỉ đảm nhiệm phần ánh xạ đối tượng, không thay thế những cơ chế đó.

## 2. ODM đứng ở đâu trong quá trình truy cập thư mục?

Có thể hình dung hai kiểu xử lý cùng một dữ liệu:

```text
                             LDAP server
                                  │
                           LDAP entry / DN
                                  │
                             LdapTemplate
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
             Không dùng ODM                  Dùng ODM
                    │                           │
         DirContextOperations             ODM mapper
          + ContextMapper                 + annotation
                    │                           │
          Tự đọc từng attribute             PersonEntry
                    └─────────────┬─────────────┘
                                  │
                         Tầng nghiệp vụ Java
```

Khi **không dùng ODM**, ta có thể lấy `DirContextOperations` rồi gọi `getStringAttribute("cn")`, `getStringAttributes(...)` và tự tạo DTO. Khi **dùng ODM**, Spring LDAP đọc thông tin annotation để chuyển đổi các attribute được khai báo thành các trường của một lớp Java.

Mục tiêu thực tế của ODM gồm:

- **Tập trung quy tắc ánh xạ:** tên attribute LDAP được khai báo tại model, giảm việc lặp lại chuỗi `"cn"`, `"mail"` trong nhiều mapper.
- **Làm rõ kiểu dữ liệu:** tầng service làm việc với `PersonEntry` và các property Java.
- **Giảm mã lặp:** có thể dùng các thao tác ODM của `LdapTemplate` để tìm, tạo, cập nhật hoặc xóa entry theo đối tượng.
- **Dễ bảo trì:** thay đổi cách đặt tên property trong Java không bắt buộc thay đổi tên attribute trên LDAP.

ODM **không phải** một bản sao của JPA/Hibernate. LDAP có DN, RDN, schema và attribute đa trị; nó không có mô hình bảng, khóa ngoại và quan hệ như cơ sở dữ liệu quan hệ. Vì vậy, không nên mặc định có lazy loading, join, transaction hay cascade giống ORM.

## 3. Các annotation ODM cơ bản

Những annotation ODM thường dùng nằm trong package `org.springframework.ldap.odm.annotations`.

| Thành phần | Vai trò | Lưu ý |
| --- | --- | --- |
| `@Entry` | Đánh dấu lớp Java là một entry LDAP, khai báo object class và có thể chỉ định base DN | Object class phải phù hợp schema của server |
| `@Id` | Đánh dấu trường chứa DN của entry | Thường dùng kiểu `javax.naming.Name` |
| `@Attribute` | Ánh xạ trường Java với attribute LDAP | Có thể chỉ định `name` để tên Java khác tên LDAP |
| `@DnAttribute` | Tham gia ánh xạ một phần RDN/DN từ property | Phụ thuộc cấu trúc DN; cần hiểu rõ thứ tự và tên RDN |
| `LdapTemplate` | Thực hiện thao tác đọc/ghi thư mục, bao gồm các phương thức hỗ trợ ODM | Vẫn phụ thuộc `ContextSource` và quyền LDAP |

Ba annotation đầu tiên đủ để minh họa một model ODM đơn giản. `@DnAttribute` hữu ích khi muốn gắn property với các thành phần DN, nhưng không phải entry nào cũng cần dùng.

Cần phân biệt ba khái niệm:

1. **DN** xác định vị trí của entry, chẳng hạn `uid=an,ou=people,dc=example,dc=org`.
2. **Attribute** là dữ liệu trong entry, chẳng hạn `cn: An Nguyen`.
3. **Property Java** là trường của đối tượng, chẳng hạn `commonName`.

DN không chỉ là một property chuỗi bất kỳ; nó mang cú pháp và quy tắc phân cấp LDAP. Khi ứng dụng cần ghép DN, nên dùng `LdapNameBuilder` hoặc API xử lý tên của LDAP thay cho nối chuỗi tùy ý.

## 4. Định nghĩa một lớp ODM đầu tiên

Giả sử ứng dụng đã có một `LdapContextSource` kết nối đến máy chủ LDAP và cấu hình base DN là `dc=example,dc=org`. Entry nhân sự nằm dưới `ou=people`. Ta khai báo một lớp Java như sau:

```java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top",
        "person",
        "organizationalPerson",
        "inetOrgPerson"
    }
)
public class PersonEntry {

    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String uid;

    @Attribute(name = "cn")
    private String commonName;

    @Attribute(name = "sn")
    private String surname;

    @Attribute(name = "mail")
    private String email;

    public PersonEntry() {
    }

    public Name getDn() {
        return dn;
    }

    public void setDn(Name dn) {
        this.dn = dn;
    }

    public String getUid() {
        return uid;
    }

    public void setUid(String uid) {
        this.uid = uid;
    }

    public String getCommonName() {
        return commonName;
    }

    public void setCommonName(String commonName) {
        this.commonName = commonName;
    }

    public String getSurname() {
        return surname;
    }

    public void setSurname(String surname) {
        this.surname = surname;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }
}
```

Đặt lớp trên trong file `PersonEntry.java`. Một số điểm cần hiểu rõ:

- `@Entry(base = "ou=people")` mô tả nhánh chứa entry trong phạm vi base DN của `ContextSource`. Không tự thêm lại `dc=example,dc=org` vào giá trị `base` khi đã cấu hình phần đó tại `ContextSource`.
- `objectClasses` mô tả tập object class cho kiểu entry. Theo schema tiêu chuẩn của `inetOrgPerson`, `cn` và `sn` là các attribute cần thiết; việc tạo entry thiếu dữ liệu bắt buộc có thể bị server từ chối.
- `@Id` đặt DN trong trường `dn`. Ở đây dùng `javax.naming.Name` để biểu diễn DN có cấu trúc.
- `@Attribute(name = "cn")` cho phép property `commonName` trong Java lấy dữ liệu từ attribute `cn` trong LDAP.
- `PersonEntry` là model dùng cho giao tiếp thư mục. Khi trả dữ liệu cho API công khai, thường nên chuyển sang DTO riêng để kiểm soát các trường được phơi bày.

Việc ODM ánh xạ thành công còn phụ thuộc loại dữ liệu, quyền đọc, schema LDAP và cách cấu hình bản Spring LDAP đang dùng. Không phải attribute nào cũng được bảo đảm hiện diện trên mọi entry.

## 5. Đọc entry bằng `LdapTemplate` và ODM

Giả sử ứng dụng đã tạo bean `LdapTemplate` từ `ContextSource` hợp lệ. Ta có thể viết service đọc các `PersonEntry` như sau:

```java
import java.util.List;
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import static org.springframework.ldap.query.LdapQueryBuilder.query;

public class PersonDirectory {

    private final LdapTemplate ldapTemplate;

    public PersonDirectory(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public List<PersonEntry> findAllPeople() {
        return ldapTemplate.findAll(PersonEntry.class);
    }

    public PersonEntry findByDn(Name dn) {
        return ldapTemplate.findByDn(dn, PersonEntry.class);
    }

    public List<PersonEntry> findByUid(String uid) {
        return ldapTemplate.find(
                query().base("ou=people").where("uid").is(uid),
                PersonEntry.class);
    }
}
```

Các thao tác này minh họa ba cách truy xuất khác nhau:

- `findAll(PersonEntry.class)` tìm các entry thuộc model, dùng thông tin ánh xạ, trong đó có `@Entry`.
- `findByDn(dn, PersonEntry.class)` truy xuất một entry theo DN được cung cấp và ánh xạ kết quả.
- `find(query, PersonEntry.class)` kết hợp filter LDAP với việc trả về các đối tượng Java đã ánh xạ.

`LdapQueryBuilder` là cách biểu diễn điều kiện tìm kiếm có cấu trúc. Đối với giá trị đến từ người dùng, **tránh tự nối filter** như `"(uid=" + uid + ")"`; giá trị đặc biệt trong LDAP filter cần được escape đúng cách. Khi service chỉ cần tìm một người dùng, nên quy định cách xử lý trường hợp không thấy entry và trường hợp có nhiều entry cùng khớp, thay vì ngầm định rằng mọi truy vấn luôn trả đúng một đối tượng.

**Cách hiểu base DN trong ví dụ:**

```text
ContextSource base: dc=example,dc=org
@Entry base:       ou=people
Entry RDN:         uid=an
--------------------------------------------
DN trên server:    uid=an,ou=people,dc=example,dc=org
```

Khi gọi các API nhận `Name`, cần xác định rõ DN được truyền theo hệ quy chiếu của `ContextSource`. Trong ví dụ này, có thể dùng `uid=an,ou=people` là DN tương đối với base đã cấu hình.

## 6. Tạo mới, cập nhật và xóa entry theo đối tượng

ODM cũng hỗ trợ luồng ghi dữ liệu. Để tạo một người dùng, trước tiên đặt DN và các attribute cần thiết:

```java
import javax.naming.Name;

import org.springframework.ldap.support.LdapNameBuilder;

Name relativeDn = LdapNameBuilder.newInstance("ou=people")
        .add("uid", "an")
        .build();

PersonEntry person = new PersonEntry();
person.setDn(relativeDn);
person.setUid("an");
person.setCommonName("An Nguyen");
person.setSurname("Nguyen");
person.setEmail("an@example.org");

ldapTemplate.create(person);
```

Với `ContextSource` có base DN `dc=example,dc=org`, `relativeDn` biểu diễn entry `uid=an,ou=people` bên dưới base đó. Để thao tác thành công, nhánh `ou=people` phải tồn tại, tài khoản kết nối cần quyền ghi, và dữ liệu phải thỏa schema của server.

Cập nhật một giá trị đã lưu:

```java
PersonEntry person = ldapTemplate.findByDn(
        relativeDn, PersonEntry.class);

person.setEmail("an.nguyen@example.org");
ldapTemplate.update(person);
```

Xóa một entry theo đối tượng:

```java
PersonEntry person = ldapTemplate.findByDn(
        relativeDn, PersonEntry.class);

ldapTemplate.delete(person);
```

Các đoạn mã là những thao tác **độc lập** để minh họa các trường hợp tạo, sửa và xóa; không chạy liên tiếp toàn bộ trên cùng entry trong ứng dụng chỉ để thử nghiệm. Khi cập nhật, cần chú ý các attribute vắng mặt, attribute nhiều giá trị và các trường mà service account được phép thay đổi. Thao tác tạo hoặc cập nhật có thể thất bại vì vi phạm schema, thiếu quyền, xung đột DN hoặc entry không tồn tại.

**Thay đổi DN không giống thay đổi một attribute thông thường.** Ví dụ đổi `uid=an` thành `uid=anh` có thể kéo theo đổi RDN của entry. Cần xem xét thao tác `rename` phù hợp, cập nhật tham chiếu liên quan và quyền của tài khoản LDAP. Không nên mặc định rằng gọi setter trên `uid` rồi `update` sẽ tự di chuyển hoặc đổi tên DN.

## 7. ODM khác gì với `ContextMapper` và `DirContextAdapter`?

Khi sử dụng Spring LDAP, cả ba hướng tiếp cận đều hữu ích, nhưng có phạm vi phù hợp khác nhau.

| Tiêu chí | ODM (`@Entry`, `@Attribute`) | `ContextMapper` với `DirContextOperations` |
| --- | --- | --- |
| Cách định nghĩa ánh xạ | Annotation tập trung trên lớp model | Mã Java đọc, kiểm tra và chuyển đổi từng attribute |
| Dữ liệu trả về | Đối tượng ánh xạ theo model ODM | Bất kỳ DTO/kiểu kết quả do mapper tạo ra |
| Khả năng tùy biến | Thuận tiện khi entry có cấu trúc ổn định, tương thích khả năng ODM | Linh hoạt khi cần quy tắc chuyển đổi phức tạp |
| Tình huống phù hợp | CRUD cho entry có schema rõ ràng | Dữ liệu không đồng nhất, tổng hợp nhiều nguồn, mapping tùy chỉnh |
| Phụ thuộc schema và ACL | Có | Có |

Ví dụ, một entry `inetOrgPerson` có các trường `uid`, `cn`, `sn` và `mail` tương đối ổn định là ứng viên tốt cho ODM. Ngược lại, nếu response cần tổng hợp thông tin từ một entry người dùng, nhiều entry nhóm và một hệ thống phân quyền khác, việc xây dựng DTO ở tầng service bằng truy vấn và mapper riêng có thể minh bạch hơn.

ODM không tự đi theo các liên kết DN để tải đối tượng khác như quan hệ JPA. Với attribute `memberOf` hoặc các nhóm chứa `member`, ứng dụng vẫn phải xem xét schema và truy vấn membership tương ứng.

## 8. Các vấn đề quan trọng khi thiết kế model ODM

### 8.1. Tôn trọng schema và `objectClass`

Một object class quy định những attribute bắt buộc và những attribute được phép sử dụng. Trong ví dụ `inetOrgPerson`, `cn` và `sn` là các attribute quan trọng của schema. Annotating một trường bằng `@Attribute` **không tự sửa schema LDAP**, cũng không đảm bảo server chấp nhận giá trị ghi xuống.

Cần kiểm tra schema thực tế của OpenLDAP, Active Directory hoặc sản phẩm LDAP đang triển khai. Một số hệ thống dùng attribute riêng theo vendor hoặc cấu hình mở rộng, vì vậy không nên xem mọi directory server đều cung cấp cùng tập attribute.

### 8.2. Phân biệt thuộc tính đơn trị và đa trị

LDAP có attribute đơn trị và đa trị. Ví dụ `mail` trong một cấu hình có thể có nhiều giá trị, còn `memberOf` nếu tồn tại thường biểu diễn tập DN. Không lấy một phần tử rồi coi đó là toàn bộ tập dữ liệu. Với attribute nhiều giá trị, sử dụng kiểu collection/array mà phiên bản ODM hỗ trợ, hoặc đọc và chuyển đổi bằng `DirContextOperations` khi cần kiểm soát chặt chẽ hơn.

Thứ tự của các giá trị LDAP thường không phải thứ tự nghiệp vụ. Nếu ứng dụng cần hiển thị cố định, hãy sắp xếp kết quả tại tầng ứng dụng.

### 8.3. Xử lý null và dữ liệu không hợp lệ

Một field `String` có thể không có giá trị khi entry thiếu attribute hoặc giá trị không được trả về do quyền truy cập/cách truy vấn. Tránh gọi các phương thức như `trim()` trên thuộc tính có thể null. Nếu nghiệp vụ cần email bắt buộc, kiểm tra rõ quy tắc ở tầng service và ở quy trình ghi dữ liệu.

Không gộp lỗi mạng, lỗi bind, lỗi phân quyền hoặc schema thành trường hợp `null` thông thường. Spring LDAP chuyển nhiều lỗi JNDI sang exception trong hệ sinh thái Spring; service cần phân biệt lỗi kỹ thuật với tình huống không tìm thấy entry.

### 8.4. Định danh và vòng đời của đối tượng

`@Id` chứa DN, trong khi các field như `uid` hay `cn` là attribute. DN có thể thay đổi do rename hoặc move, vì vậy cần quy tắc định danh rõ ràng ở tầng ứng dụng. Nên coi đối tượng ODM là dữ liệu mô tả trạng thái entry ở thời điểm truy cập; các thay đổi đồng thời trên LDAP có thể khiến bản sao trong bộ nhớ cũ đi.

Nếu nhiều quy trình cùng cập nhật một entry, thiết kế chính sách xử lý xung đột và dùng cơ chế của directory server khi có hỗ trợ. ODM không tự bảo đảm giao dịch nhiều entry hoặc phát hiện mọi cập nhật đồng thời.

### 8.5. An toàn khi kết nối và ghi dữ liệu

Sử dụng `ContextSource` có xác thực phù hợp, TLS/LDAPS và cấu hình tin cậy chứng chỉ đúng môi trường. Giới hạn tài khoản dịch vụ ở quyền đọc/ghi cần thiết cho các nhánh LDAP được phép thao tác. Không map các attribute nhạy cảm như `userPassword` thành dữ liệu sẽ xuất ra API hoặc log.

Nếu ứng dụng xử lý tìm kiếm theo đầu vào người dùng, dùng LDAP query builder hoặc bộ lọc có escape đúng cách. Nếu ứng dụng tạo DN từ tên người dùng, dùng `LdapNameBuilder` để tránh làm sai cú pháp RDN bởi ký tự đặc biệt.

## 9. Quy trình triển khai ODM theo từng bước

Đối với một module sử dụng Spring LDAP, có thể triển khai theo trình tự sau:

1. **Khảo sát schema:** xác định object class, attribute bắt buộc, đơn trị/đa trị, quy ước DN và ACL của entry mục tiêu.
2. **Cấu hình kết nối:** tạo `ContextSource` và `LdapTemplate`, cấu hình base DN, xác thực, TLS và chính sách timeout/pooling theo môi trường.
3. **Khai báo model:** tạo lớp có `@Entry`, `@Id` và các `@Attribute` cần dùng; chỉ ánh xạ những dữ liệu phục vụ nghiệp vụ.
4. **Cài đặt truy vấn:** bắt đầu với `findByDn`/`find` hoặc `findAll` trong phạm vi phù hợp; kiểm tra hành vi khi không tìm thấy entry.
5. **Bổ sung thao tác ghi:** chỉ cho phép `create`, `update` và `delete` ở những luồng đã kiểm tra quyền, DN và schema.
6. **Kiểm thử với LDAP thực hoặc server thử nghiệm:** chuẩn bị dữ liệu trong nhánh riêng, xác minh kết quả đọc/ghi, exception, tìm kiếm và kiểm soát truy cập.

Để kiểm thử một CRUD flow, có thể dùng bộ dữ liệu:

```text
Base:      dc=example,dc=org
Nhánh:     ou=people
Entry DN:  uid=an,ou=people,dc=example,dc=org
ObjectClass:
  top, person, organizationalPerson, inetOrgPerson
Dữ liệu:
  uid=an
  cn=An Nguyen
  sn=Nguyen
  mail=an@example.org
```

Các kiểm tra có ý nghĩa gồm: đọc entry thành `PersonEntry` có đúng `dn` và property; tìm theo `uid` trả đúng kết quả; sửa `mail` rồi đọc lại từ server; thử tạo entry thiếu `sn` để quan sát lỗi schema; thử ghi bằng tài khoản chỉ có quyền đọc để xác minh xử lý lỗi ACL. Thực hiện bài thử trên thư mục thử nghiệm, có dữ liệu và quyền phù hợp.

## 12. Tổng kết

**ODM trong Spring LDAP** là cơ chế biểu diễn entry LDAP bằng đối tượng Java có annotation. `@Entry` mô tả kiểu entry và phạm vi, `@Id` ánh xạ DN, `@Attribute` ánh xạ dữ liệu, còn các API ODM của `LdapTemplate` giúp đọc và ghi entry theo model đã khai báo.

ODM phù hợp với thao tác trên entry có schema rõ ràng và quy tắc ánh xạ tương đối ổn định. Hiểu đúng DN, RDN, schema, attribute đa trị, quyền truy cập và cơ chế tìm kiếm sẽ giúp sử dụng ODM an toàn, đặc biệt khi ứng dụng có chức năng tạo, sửa hoặc xóa dữ liệu thư mục.
