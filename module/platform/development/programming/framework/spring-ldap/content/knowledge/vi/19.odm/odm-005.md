# @DnAttribute và thành phần DN

Trong Spring LDAP, Object-Directory Mapping (ODM) cho phép biểu diễn entry của dịch vụ thư mục LDAP bằng đối tượng Java. Ngoài những thuộc tính thông thường như `cn`, `sn`, `mail`, mỗi entry còn có một **distinguished name (DN)** xác định vị trí của nó trong cây thư mục. Annotation `@DnAttribute` giúp lấy một phần của DN vào trường Java và, khi cấu hình đầy đủ, giúp ODM dựng DN từ các trường đó. Điều này hữu ích khi viết chức năng tạo người dùng, tìm kiếm theo tổ chức và cập nhật vị trí entry qua `LdapTemplate`.

Bài này tập trung vào `org.springframework.ldap.odm.annotations.DnAttribute`, cách phối hợp với `@Entry`, `@Id`, `@Attribute`, `@Transient`, cũng như các giới hạn cần lưu ý khi đổi DN. Phần kết nối LDAP, `ContextSource`, xác thực, TLS, pooling và quyền sửa entry vẫn phải được cấu hình, kiểm thử riêng ở tầng kết nối và máy chủ.

## 1. DN và RDN: phân biệt đường dẫn với thuộc tính

Xét entry LDAP:

```ldif
dn: uid=linh,ou=engineering,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: linh
cn: Linh Nguyen
sn: Nguyen
mail: linh@example.org
```

- **DN**: `uid=linh,ou=engineering,ou=people,dc=example,dc=org` là tên đầy đủ định vị entry trong cây LDAP.
- **RDN (Relative Distinguished Name)**: từng thành phần như `uid=linh`, `ou=engineering` hoặc `dc=org`. RDN gần bên trái nhất (`uid=linh`) xác định entry tương đối với entry cha.
- **Tên thuộc tính trong RDN**: `uid`, `ou`, `dc`; **giá trị** tương ứng là `linh`, `engineering`, `example`, `org`.
- **Attribute của entry**: `cn`, `sn`, `mail` và `uid` là dữ liệu thuộc entry do LDAP trả về; một thành phần DN như `ou=engineering` có thể là RDN của **entry cha**, chứ không nhất thiết là attribute của entry người dùng.

Sơ đồ vị trí entry:

```text
dc=org
└── dc=example
    └── ou=people
        └── ou=engineering
            └── uid=linh          ← entry người dùng
```

**Lưu ý:** DN không phải một khóa chính dạng chuỗi tùy ý. Nó có quy tắc mã hóa ký tự đặc biệt, có thể chứa RDN nhiều giá trị và phụ thuộc base DN mà `ContextSource` sử dụng. Khi phải tạo hoặc so sánh DN, ưu tiên kiểu `javax.naming.Name` / `LdapName` và công cụ dựng DN thay cho nối chuỗi thủ công.

## 2. @DnAttribute ánh xạ gì?

`@DnAttribute` đặt trên **trường `String`** của một lớp ODM. Khi đọc entry, Spring LDAP tìm giá trị tương ứng trong DN để điền vào trường đó. Hai tham số quan trọng:

| Thành phần | Ý nghĩa | Ghi chú |
| --- | --- | --- |
| `value = "uid"` | Tên attribute trong RDN cần lấy | Bắt buộc trong khai báo annotation; có thể viết ngắn `@DnAttribute("uid")`. |
| `index = 1` | Vị trí RDN khi ánh xạ hoặc dựng DN | Bắt đầu từ `0`; mặc định `-1` nghĩa là không chỉ rõ vị trí. |
| `@Id` | Trường chứa DN toàn bộ entry | Kiểu `javax.naming.Name`, không dùng `String`. |
| `@Attribute(name = "cn")` | Ánh xạ một LDAP attribute của chính entry | Khác với lấy giá trị từ DN. |
| `@Transient` | Loại trường khỏi ánh xạ LDAP attribute thông thường | Có thể kết hợp với `@DnAttribute` để chỉ lấy giá trị từ DN. |

Ví dụ chỉ lấy `uid` từ DN:

```java
import org.springframework.ldap.odm.annotations.DnAttribute;

@DnAttribute("uid")
private String uid;
```

Với DN `uid=linh,ou=engineering,ou=people,dc=example,dc=org`, trường `uid` nhận `"linh"` khi Spring LDAP đọc entry. Trường `String` này không thay thế trường `@Id Name dn` lưu DN đầy đủ.

Nếu cần **tự động tạo DN**, hãy chỉ định `index` cho **tất cả** trường gắn `@DnAttribute` trong lớp. Các index chỉ thứ tự các RDN *được tính thêm vào* `@Entry(base=...)`. Với ví dụ có base `ou=people`, thứ tự là:

```text
uid=linh,ou=engineering,ou=people
└─ index=1 ─┘└── index=0 ──┘└ @Entry.base ┘
```

Do cách biểu diễn DN của LDAP, `index=0` ở **gần base nhất**, rồi `index=1` ở bên trái thành phần `index=0`. Với `index` được chỉ định, bộ ánh xạ dùng vị trí RDN đó thay vì dựa vào tên trong `value` để tìm thành phần DN. Vì vậy, chỉ dùng `index` khi cấu trúc DN ổn định và bảo đảm tên RDN ở từng vị trí đúng với mô hình.

> Hai lựa chọn tương ứng với hai nhu cầu: chỉ `@DnAttribute("uid")` đủ để đọc giá trị DN; `@DnAttribute(value = "uid", index = 1)` giúp mô hình còn tính được DN khi kết hợp với các thành phần có chỉ số khác.

## 3. Tạo một entity ODM có hai thành phần DN

Giả sử `ContextSource` đã cấu hình base DN `dc=example,dc=org`. Dưới base này, chúng ta quản lý các entry người dùng thuộc `ou=people` và từng bộ phận `ou=engineering`, `ou=sales`...

```java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.DnAttribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;
import org.springframework.ldap.odm.annotations.Transient;

@Entry(
    objectClasses = { "top", "person", "organizationalPerson", "inetOrgPerson" },
    base = "ou=people"
)
public class PersonEntry {
    @Id
    private Name dn;                           // DN tương đối với base ContextSource

    @DnAttribute(value = "ou", index = 0)
    @Transient
    private String department;                 // ou của entry cha, chỉ lấy từ DN

    @DnAttribute(value = "uid", index = 1)
    private String uid;                        // RDN uid và LDAP attribute uid

    @Attribute(name = "cn")
    private String fullName;

    @Attribute(name = "sn")
    private String surname;

    @Attribute(name = "mail")
    private String email;

    public PersonEntry() {}                    // ODM có thể khởi tạo đối tượng

    public Name getDn() { return dn; }
    public void setDn(Name dn) { this.dn = dn; }

    public String getDepartment() { return department; }
    public void setDepartment(String department) { this.department = department; }

    public String getUid() { return uid; }
    public void setUid(String uid) { this.uid = uid; }

    public String getFullName() { return fullName; }
    public void setFullName(String fullName) { this.fullName = fullName; }

    public String getSurname() { return surname; }
    public void setSurname(String surname) { this.surname = surname; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
}
```

Giải thích từng trường:

1. `@Entry` khai báo các LDAP object class và phần base của entry. `base="ou=people"` được hiểu trong phạm vi base DN của `ContextSource`.
2. `@Id Name dn` chứa **toàn bộ DN** dùng trong thao tác ODM. Khi `dn` không được cung cấp, ODM có thể tính nó từ các trường `@DnAttribute` có `index` hợp lệ.
3. `department` lấy `engineering` từ RDN `ou=engineering`. `@Transient` ngăn ODM ghi trường này như một attribute `department` của entry người dùng.
4. `uid` lấy `linh` từ `uid=linh`. Vì không có `@Transient`, trường này **vẫn được ánh xạ** thành LDAP attribute `uid` theo mặc định.
5. `fullName`, `surname`, `email` lần lượt ánh xạ đến LDAP attributes `cn`, `sn`, `mail`; chúng không tham gia tính DN ở ví dụ này.

Tại sao trường `department` gắn cả `@DnAttribute` và `@Transient`? Spring LDAP **mặc định ánh xạ các trường của entity thành LDAP attributes có cùng tên**, kể cả trường gắn `@DnAttribute`. `@DnAttribute` là phần bổ sung thông tin về DN, **không tự vô hiệu hóa** ánh xạ attribute. Nếu muốn trường chỉ phục vụ DN, hãy dùng thêm `@Transient`.

## 4. Tạo entry và đọc ngược DN qua LdapTemplate

Giả sử có `LdapTemplate ldapTemplate` sử dụng một `ContextSource` với base `dc=example,dc=org`, và entry cha `ou=engineering,ou=people` đã tồn tại. Đoạn dưới minh họa logic nghiệp vụ ở tầng ứng dụng:

```java
import javax.naming.Name;
import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public class PersonDirectoryService {
    private final LdapTemplate ldapTemplate;

    public PersonDirectoryService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public PersonEntry createExample() {
        PersonEntry person = new PersonEntry();
        person.setDepartment("engineering");
        person.setUid("linh");
        person.setFullName("Linh Nguyen");
        person.setSurname("Nguyen");
        person.setEmail("linh@example.org");

        // Chưa gọi setDn: ODM thử tính DN từ index=0, index=1 và @Entry.base.
        ldapTemplate.create(person);
        return person;
    }

    public PersonEntry findExample() {
        Name relativeDn = LdapNameBuilder.newInstance("ou=people")
            .add("ou", "engineering")
            .add("uid", "linh")
            .build();

        return ldapTemplate.findByDn(relativeDn, PersonEntry.class);
    }
}
```

Các bước tính tên mong đợi:

```text
@Entry.base     = ou=people
index=0         = ou=engineering
index=1         = uid=linh

DN tương đối   = uid=linh,ou=engineering,ou=people
ContextSource   = dc=example,dc=org

DN đầy đủ      = uid=linh,ou=engineering,ou=people,dc=example,dc=org
```

`ldapTemplate.create(person)` sẽ dùng `@Id` nếu trường DN được đặt tường minh; khi `dn == null`, ODM thử dựng DN từ `@DnAttribute` và `@Entry.base`. Nếu tạo thành công và tên được tính được, `@Id` của đối tượng cũng được cập nhật. Việc tạo entry còn đòi hỏi schema phù hợp (`cn`, `sn` với `inetOrgPerson`), entry cha có thật và tài khoản kết nối có quyền ghi.

`LdapNameBuilder` tạo `Name` từ cặp tên/giá trị RDN và xử lý escaping, ví dụ username chứa dấu phẩy. Đoạn `add("ou", ...).add("uid", ...)` đặt RDN mới về phía bên trái DN biểu diễn thành chuỗi. Đừng ghép DN bằng `"uid=" + uid + ",ou=..."` khi giá trị đến từ dữ liệu nhập.

### Đọc bằng query

Bạn có thể dùng ODM theo truy vấn có kiểm soát, chẳng hạn tìm người dùng theo `uid`:

```java
import static org.springframework.ldap.query.LdapQueryBuilder.query;

PersonEntry person = ldapTemplate.findOne(
    query().base("ou=people").where("uid").is("linh"),
    PersonEntry.class
);
```

Cần lưu ý: `uid` có thể trùng nhau ở các bộ phận khác nhau, nên `findOne` chỉ phù hợp khi filter đảm bảo duy nhất trong phạm vi tìm kiếm. Nếu không có bảo đảm, dùng `find(..., PersonEntry.class)` và xử lý danh sách kết quả. `@DnAttribute` lấy thành phần từ DN **sau khi** entry được tìm thấy; nó không tự tạo search filter cho LDAP server.

## 5. Đổi trường tham gia DN có thể làm entry đổi vị trí

Trường `uid` và `department` trong ví dụ không chỉ là giá trị hiển thị. Chúng xác định **DN của entry**. Nếu đổi `department` từ `engineering` sang `sales`, tên tính từ annotation sẽ chuyển từ:

```text
uid=linh,ou=engineering,ou=people
                       ↓
uid=linh,ou=sales,ou=people
```

Khi gọi `ldapTemplate.update(person)`, nếu DN mới được tính từ các trường `@DnAttribute` khác với DN hiện có trong `@Id`, Spring LDAP sẽ xử lý như một thao tác **chuyển/đổi tên entry** theo cơ chế ODM thay vì chỉ sửa một thuộc tính bình thường. Tài liệu API của `LdapTemplate.update` mô tả nhánh di chuyển qua thao tác unbind/bind; vì vậy đừng mặc định đây là một phép sửa thuộc tính nguyên tử hay rằng mọi tham chiếu đến DN cũ đều được chuyển theo.

Đoạn mã minh họa **ý định thay đổi vị trí**, chỉ nên chạy trên môi trường thử nghiệm hoặc luồng nghiệp vụ đã xác thực quyền và sự tồn tại của OU đích:

```java
PersonEntry person = personDirectoryService.findExample();

person.setDepartment("sales");    // Đổi một RDN: ou=engineering -> ou=sales
ldapTemplate.update(person);      // Có thể làm thay đổi DN, tùy trạng thái entity
```

Trước khi cho phép đổi `department` hoặc `uid`, cần kiểm tra OU đích tồn tại, người dùng được quyền thực hiện, chính sách schema của máy chủ, khả năng trùng DN, các nhóm hoặc hệ thống khác đang lưu DN cũ và cách khôi phục khi thao tác thất bại. LDAP server có thể áp dụng những giới hạn khác nhau với việc đổi RDN/di chuyển entry; hãy kiểm thử trên máy chủ tương ứng. Khi nghiệp vụ chỉ muốn sửa email, họ tên hoặc thuộc tính khác, hãy tránh thay đổi những trường tham gia tính DN.

## 6. @DnAttribute, @Attribute, @Id và @Transient: chọn đúng

| Tình huống | Cách ánh xạ phù hợp | Lý do |
| --- | --- | --- |
| Cần DN toàn bộ của người dùng | `@Id private Name dn;` | Đại diện định danh đầy đủ để tìm/sửa/xóa entry. |
| Cần lấy `linh` từ `uid=linh` | `@DnAttribute("uid")` trên `String` | Đọc giá trị trực tiếp từ RDN. |
| Cần tạo DN `uid=linh,ou=engineering,ou=people` | `@DnAttribute(value="ou", index=0)` và `@DnAttribute(value="uid", index=1)` | Dựng thứ tự thành phần tương đối với `@Entry.base`. |
| Cần đọc `mail` từ LDAP entry | `@Attribute(name="mail")` | Đây là dữ liệu attribute thông thường. |
| Cần dùng tên phòng ban từ DN, không lưu trường `department` xuống LDAP entry | `@DnAttribute(...)` + `@Transient` | Chỉ tham gia ánh xạ DN, không tạo attribute cùng tên. |
| Cần lấy `cn` đồng thời từ DN và entry (ví dụ entry có RDN `cn=...`) | `@DnAttribute(value="cn", index=...)` + `@Attribute(name="cn")` | RDN và attribute của entry có thể cùng mang tên `cn`; cần biết quy tắc đồng bộ khi đổi. |

Một số ranh giới quan trọng:

- `@DnAttribute` chỉ hỗ trợ trường `String`; nếu cần DN đầy đủ, dùng `@Id Name`.
- Các `index` cần xác định đủ, không mâu thuẫn và phản ánh **đúng cấu trúc DN** nếu muốn ODM tự dựng tên.
- `@Entry.base` thường chứa OU gốc cố định của loại entity; đừng đưa lại phần base này vào các trường `@DnAttribute` nếu không muốn lặp RDN.
- `@Transient` không xóa trường Java, và không ngăn giá trị được lấy từ DN khi đi cùng `@DnAttribute`.
- `@DnAttribute` không làm thay nhiệm vụ kiểm soát kết nối TLS, LDAP filter, quyền đọc/ghi hoặc pooling.

## 7. Các lỗi thường gặp và cách chẩn đoán

| Hiện tượng | Nguyên nhân có thể | Cách kiểm tra |
| --- | --- | --- |
| Entity đọc được nhưng `uid` hoặc `department` sai | `index` không đúng thứ tự DN; có nhiều RDN hoặc cấu trúc DN khác giả định | Log DN **đã ẩn dữ liệu nhạy cảm** và so với `@Entry.base`, vị trí RDN. |
| Tạo entry không tính được DN | Thiếu `@Id`/base hoặc thiếu `index` ở một số `@DnAttribute` | Kiểm tra annotation trên toàn bộ trường tham gia DN; đảm bảo giá trị đầu vào đầy đủ. |
| LDAP nhận một attribute `department` ngoài ý muốn | Trường gắn `@DnAttribute` vẫn được ODM map thành attribute mặc định | Bổ sung `@Transient` nếu chỉ lấy department từ DN. |
| LDAP trả lỗi tên hoặc schema | Cha chưa tồn tại, giá trị RDN không hợp lệ, thiếu attribute bắt buộc hoặc DN đã có | Kiểm tra parent DN, object class, `cn`/`sn`, quyền và trùng tên. |
| Sửa phòng ban gây tác động bất ngờ | Trường dùng để tính DN thay đổi nên ODM thực hiện nhánh chuyển/đổi tên | Đánh giá tác động của di chuyển, tham chiếu DN và quyền trên OU đích. |
| Xử lý không đúng username chứa dấu phẩy hoặc dấu bằng | Tạo DN bằng nối chuỗi thủ công, không escape giá trị | Dựng `Name` bằng `LdapNameBuilder.add(key, value)`. |
| `findOne` không trả đúng một người | `uid` không duy nhất trên toàn nhánh tìm kiếm | Thu hẹp base/search filter hoặc dùng `find` để xử lý nhiều entry. |

### Thực hành tự kiểm tra

1. Với `@Entry(base="ou=people")`, `index=0` là `ou=ops`, `index=1` là `uid=an`, và `ContextSource` có base `dc=example,dc=org`, DN đầy đủ là gì? **Đáp án:** `uid=an,ou=ops,ou=people,dc=example,dc=org`.
2. Vì sao `@DnAttribute("ou")` chưa đủ khi cần tự động tạo DN gồm hai RDN? **Đáp án:** Phải xác định `index` cho tất cả trường `@DnAttribute` dùng tính tên, đồng thời cung cấp base phù hợp.
3. Khi `department` chỉ là tên OU cha, có nên tự động ghi nó thành LDAP attribute của người dùng không? **Đáp án:** Thường không; kết hợp `@DnAttribute` và `@Transient`.
4. Đổi `email` có làm đổi DN trong mô hình này không? **Đáp án:** Không, vì trường `email` không được dùng làm thành phần DN. Đổi `uid` hoặc `department` thì có thể.
5. Tại sao không chèn trực tiếp username vào chuỗi `uid=<giá trị>,ou=people`? **Đáp án:** Giá trị có thể chứa ký tự cần escape; `LdapNameBuilder` tạo RDN đúng quy tắc.
