# @Entry và object classes của domain object trong Spring LDAP ODM

Khi truy cập LDAP bằng JNDI hoặc `LdapTemplate.search(...)`, ứng dụng thường nhận `Attributes` rồi tự chuyển các giá trị `cn`, `sn`, `mail` thành một đối tượng Java. **Object-Directory Mapping (ODM)** của Spring LDAP cho phép khai báo trực tiếp cách một lớp Java tương ứng với entry trong thư mục. Annotation quan trọng nhất là **`@Entry`**, nơi xác định những **LDAP object classes** mà domain object đại diện và, nếu cần, DN gốc cho các entry thuộc loại đó.

Tuy nhiên, `@Entry` không biến một POJO thành entry hợp lệ một cách tự động. Máy chủ LDAP vẫn kiểm tra schema, quan hệ kế thừa object class, attribute `MUST`/`MAY`, syntax, DN và quyền truy cập. Hiểu được ranh giới giữa *Java domain class*, *LDAP objectClass* và *entry thực tế* là nền tảng để dùng ODM đúng.

Bài học thuộc chương **ODM** của **SPRING_LDAP**. Người học sẽ đọc và khai báo `@Entry(objectClasses = ..., base = ...)`, phối hợp với `@Id` và `@Attribute`, xây entity cho `inetOrgPerson`, giải thích các lỗi schema/ánh xạ thường gặp, rồi tạo và tìm entry bằng các API ODM của `LdapTemplate`. Cấu hình `ContextSource`, xác thực, TLS, kết nối và pooling vẫn là trách nhiệm của tầng truy cập LDAP, không phải của annotation trên domain object.

## 1. Ba khái niệm phải tách biệt

| Khái niệm | Bản chất | Ví dụ |
|---|---|---|
| **Java domain class** | Kiểu Java để ứng dụng xử lý dữ liệu | `PersonEntry` |
| **LDAP object class** | Định nghĩa schema mô tả kiểu entry, ràng buộc MUST/MAY và kế thừa | `person`, `organizationalPerson`, `inetOrgPerson` |
| **LDAP entry** | Bản ghi có DN duy nhất và các attribute cụ thể trong DIT | `uid=an,ou=people,dc=example,dc=org` |

Ví dụ một entry đang tồn tại trong LDAP:

~~~ldif
dn: uid=an,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: an
cn: Nguyen Van An
sn: Nguyen
givenName: Van An
mail: an@example.org
~~~

Một ứng dụng có thể đọc entry này vào đối tượng `PersonEntry`. Domain object **không phải** bản thân LDAP server; nó là biểu diễn Java của dữ liệu thư mục.

~~~mermaid
flowchart LR
    A["Java: PersonEntry"] --> B["@Entry: objectClasses + base"]
    A --> C["@Id: DN"]
    A --> D["@Attribute: trường dữ liệu"]
    B --> E["Spring LDAP ObjectDirectoryMapper"]
    C --> E
    D --> E
    E <-->|"find / create / update"| F["LDAP entry trong DIT"]
    G["LDAP schema + ACL"] --> F
~~~

Có hai lớp quy tắc:

1. **ODM mapping** quyết định trường Java nào tương ứng với DN/attribute, và loại entry nào được chọn để ánh xạ.
2. **LDAP server** quyết định thao tác đọc/ghi có được chấp nhận theo schema, ACL, DN và chính sách thực tế hay không.

Một đối tượng Java biên dịch thành công chưa chứng minh được rằng thao tác `ldapTemplate.create(person)` sẽ thành công.

## 2. Annotation @Entry là gì?

Trong Spring LDAP, annotation có tên đầy đủ:

~~~java
org.springframework.ldap.odm.annotations.Entry
~~~

Nó được đặt trên **lớp Java**, không phải trên một trường:

~~~java
import org.springframework.ldap.odm.annotations.Entry;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top",
        "person",
        "organizationalPerson",
        "inetOrgPerson"
    }
)
public class PersonEntry {
    // @Id, @Attribute và những trường Java khác
}
~~~

Hai thành phần chủ yếu:

| Thành phần | Bắt buộc? | Ý nghĩa |
|---|---|---|
| `objectClasses` | **Bắt buộc** đối với `@Entry` | Các object class LDAP mà entity đại diện; là metadata dùng để nhận diện và tạo entry |
| `base` | Tùy chọn | DN gốc cho entity; được dùng khi Spring LDAP tính toán các DN từ thông tin ánh xạ |

**`@Entry` và `@Id` là hai annotation cần có đối với entity do ODM của Spring LDAP quản lý.** Các annotation khác như `@Attribute`, `@DnAttribute` và `@Transient` điều chỉnh cách từng trường được ánh xạ.

Nếu không ghi `base`, giá trị mặc định là chuỗi rỗng, và vị trí của entry vẫn phải được xác định đúng theo API, DN hoặc thông tin đặt tên khác.

### @Entry không khai báo schema mới

`objectClasses = {"inetOrgPerson", ...}` có nghĩa lớp Java đại diện cho entry thuộc những object class đã **được LDAP server nhận diện**. Nó **không** tạo object class mới trên server, không sửa thuộc tính bắt buộc, không làm thay đổi matching rule và không cấp quyền tạo entry.

Nếu server chưa nạp schema tương ứng hoặc entry không đáp ứng yêu cầu của `inetOrgPerson`, thao tác ghi vẫn có thể thất bại.

## 3. Hiểu objectClass, SUP, MUST và MAY trước khi viết @Entry

Một LDAP object class thường có:

- **`NAME`/OID**: tên hoặc định danh của class.
- **`SUP`**: object class cha, thể hiện kế thừa các ràng buộc.
- **`MUST`**: attribute bắt buộc có giá trị.
- **`MAY`**: attribute được phép nhưng không bắt buộc.
- **Kiểu class**: `ABSTRACT`, `STRUCTURAL` hoặc `AUXILIARY`.

Chuỗi kế thừa phổ biến cho entry người dùng:

~~~text
top                            (ABSTRACT)
└── person                      (STRUCTURAL)
    └── organizationalPerson    (STRUCTURAL)
        └── inetOrgPerson       (STRUCTURAL)
~~~

`person` yêu cầu `cn` và `sn`. Vì `inetOrgPerson` là hậu duệ của `person`, một entry `inetOrgPerson` vẫn phải có các attribute bắt buộc kế thừa ấy. Tùy schema, `inetOrgPerson` cho phép những attribute bổ sung như `uid`, `mail`, `givenName`.

**Kế thừa LDAP object class khác với `extends` trong Java.** Ví dụ lớp Java `PersonEntry` không cần kế thừa một lớp Java tên `InetOrgPerson`. Các tên trong `@Entry.objectClasses` là **tên object class của schema LDAP**, không phải tên class Java.

### Vì sao liệt kê cả chuỗi object class?

Với entry minh họa, có thể khai báo:

~~~java
@Entry(
    objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
    },
    base = "ou=people"
)
~~~

Trong ODM, danh sách này có vai trò quan trọng cả khi **tìm/ánh xạ entry** lẫn khi **tạo entry mới**: Spring LDAP dùng metadata để xác định loại entry được quản lý, và khi tạo mới thì các object class được khai báo là những giá trị được dùng cho entry tạo ra.

Vì thế, nếu domain object cần quản lý các thuộc tính thuộc các lớp dẫn xuất, hãy khai báo tập object class phù hợp. Ví dụ chỉ khai báo `person` và `top` không có nghĩa mapper được phép tự thêm mọi object class cần thiết để lưu `mail` hoặc các thuộc tính chỉ được cho phép bởi `inetOrgPerson`.

Không suy luận rằng Spring LDAP sẽ tự truy vấn schema và bổ sung toàn bộ object class còn thiếu vào annotation. **Khớp với entry/schema thực tế** quan trọng hơn việc viết mảng tên theo cảm tính.

### Khi nào được bổ sung auxiliary class?

Một số entry có thể kết hợp chuỗi structural class với **auxiliary class** nhằm cho phép thêm nhóm attribute theo schema bổ sung. Chẳng hạn nhiều directory hỗ trợ các lớp mở rộng riêng cho nghiệp vụ.

Tuy nhiên:

- Không ghép hai **structural class độc lập** chỉ để lấy thêm attribute.
- Chỉ thêm auxiliary class khi schema và content rules của máy chủ cho phép.
- Một class có tên nghe hợp lý nhưng chưa được server cài đặt sẽ gây lỗi schema.
- Không dùng `extensibleObject` như “lối thoát” mặc định để né kiểm tra dữ liệu.

Nếu cần thuộc tính riêng của doanh nghiệp, hãy phối hợp với người quản trị LDAP về schema và object class phù hợp, thay vì thêm ngẫu nhiên vào `objectClasses`.

## 4. base của @Entry nằm trong hệ thống DN nào?

Xét directory:

~~~text
dc=example,dc=org            (base của ContextSource)
└── ou=people                (base của @Entry trong ví dụ)
    ├── uid=an
    └── uid=binh
~~~

Có hai mức base cần phân biệt:

| Cấu hình | Giá trị minh họa | Vai trò |
|---|---|---|
| `ContextSource` base | `dc=example,dc=org` | Phần DIT gốc mà Spring LDAP/JNDI truy cập tương đối |
| `@Entry.base` | `ou=people` | Vị trí gốc dành cho các entry của domain class khi ODM tính toán DN |
| DN đầy đủ của người dùng | `uid=an,ou=people,dc=example,dc=org` | Tên thực của entry trong directory |

Trong tình huống trên, `ou=people` là base **tương đối** với base đã cấu hình ở `ContextSource`. Khi dùng chức năng ODM **tính DN từ các trường `@DnAttribute`**, `@Entry.base` được ghép vào phần DN đã tính theo cơ chế ánh xạ. Không nên tự bổ sung base hai lần.

**Lưu ý về DN được gán tường minh:** nếu trường `@Id` đã chứa một `Name` hợp lệ, phương thức `LdapTemplate.create(...)` sử dụng DN được gán đó. Nếu không cung cấp `@Id`, ODM sẽ thử tính DN từ các trường `@DnAttribute`; khi đó `@Entry.base` là phần nền của DN được tính.

Việc chọn cấp đặt base rất quan trọng: dùng một `@Entry.base` quá rộng có thể khiến query duyệt phạm vi không mong muốn, còn dùng sai base có thể tạo entry tại DN khác dự kiến hoặc gây `noSuchObject`.

## 5. Entity đầy đủ: @Entry, @Id, @Attribute và @Transient

Ví dụ một class Java ánh xạ tài khoản người dùng thuộc `inetOrgPerson`:

~~~java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;
import org.springframework.ldap.odm.annotations.Transient;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
    }
)
public class PersonEntry {

    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String uid;

    @Attribute(name = "cn")
    private String commonName;

    @Attribute(name = "sn")
    private String surname;

    @Attribute(name = "mail")
    private String email;

    @Transient
    private String displayLabel;

    public PersonEntry() {
        // Constructor không tham số cho cơ chế ánh xạ.
    }

    public PersonEntry(
            Name dn, String uid, String commonName,
            String surname, String email) {
        this.dn = dn;
        this.uid = uid;
        this.commonName = commonName;
        this.surname = surname;
        this.email = email;
    }

    public Name getDn() { return dn; }
    public void setDn(Name dn) { this.dn = dn; }

    public String getUid() { return uid; }
    public void setUid(String uid) { this.uid = uid; }

    public String getCommonName() { return commonName; }
    public void setCommonName(String commonName) {
        this.commonName = commonName;
    }

    public String getSurname() { return surname; }
    public void setSurname(String surname) {
        this.surname = surname;
    }

    public String getEmail() { return email; }
    public void setEmail(String email) {
        this.email = email;
    }

    public String getDisplayLabel() { return displayLabel; }
    public void setDisplayLabel(String displayLabel) {
        this.displayLabel = displayLabel;
    }
}
~~~

### Đọc từng annotation

| Annotation | Đối tượng nhận | Điều nó mô tả |
|---|---|---|
| `@Entry` | Lớp `PersonEntry` | Entry thuộc các object class và vùng base đã khai báo |
| `@Id` | Trường `dn` | **Distinguished Name** của entry; phải là kiểu dẫn xuất từ `javax.naming.Name` |
| `@Attribute(name="uid")` | Trường `uid` | Giá trị LDAP attribute `uid` |
| `@Attribute(name="cn")` | Trường `commonName` | Tên Java khác tên LDAP; cần ánh xạ rõ ràng |
| `@Attribute(name="sn")` | Trường `surname` | Giá trị surname, thuộc nhóm bắt buộc của `person` |
| `@Attribute(name="mail")` | Trường `email` | Attribute tùy chọn theo schema đang sử dụng |
| `@Transient` | Trường `displayLabel` | Trường dành cho ứng dụng; ODM bỏ qua khi lưu/đọc LDAP |

Đặc biệt, **`@Id` không đồng nghĩa với giá trị `uid`**. Trường `dn` chứa một tên LDAP đầy đủ trong phạm vi mà API đang sử dụng, chẳng hạn `uid=an,ou=people` tương đối với `ContextSource`. `uid` chỉ là attribute có thể dùng làm thành phần RDN.

**Theo ODM của Spring LDAP, các trường không có `@Transient` có thể được ánh xạ theo tên trường Java mặc định.** Vì vậy đặt tên field `email` mà không ghi `@Attribute(name="mail")` có thể khiến mapper tìm attribute `email` thay vì `mail`. Cần khai báo rõ khi tên Java và tên LDAP khác nhau. Trường phụ chỉ phục vụ giao diện nên đánh dấu `@Transient`.

### @Attribute không hợp thức hóa một attribute bị schema cấm

Nếu bỏ `inetOrgPerson` khỏi cấu hình nhưng vẫn cố lưu `mail` trên một entry mà các object class còn lại không cho phép `mail`, LDAP server có thể từ chối với `objectClassViolation`. Annotation `@Attribute(name="mail")` chỉ nói “trường này tương ứng với attribute mail”; nó không thể thay đổi quy tắc `MAY` hay `MUST` của schema.

## 6. Đưa một entity Java về đúng dữ liệu LDIF

Với `PersonEntry` ở trên, giả sử tạo instance chứa:

~~~text
dn         = uid=an,ou=people            (tương đối với ContextSource base)
uid        = an
commonName = Nguyen Van An
surname    = Nguyen
email      = an@example.org
displayLabel = "An (Engineering)"       (chỉ trong Java)
~~~

Mục tiêu về dữ liệu LDAP là:

~~~ldif
dn: uid=an,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: an
cn: Nguyen Van An
sn: Nguyen
mail: an@example.org
~~~

Trong ví dụ:

- `@Entry.objectClasses` tương ứng nhiều giá trị của LDAP attribute `objectClass`.
- `@Id` tương ứng **DN của entry**, không phải một attribute `dn` thường.
- `@Attribute(name="cn")` ánh xạ `commonName` sang `cn`.
- `@Transient` khiến `displayLabel` **không** xuất hiện thành một LDAP attribute.
- `sn` phải có giá trị hợp lệ để đáp ứng schema `person`.
- Việc `mail` có giá trị hợp cú pháp và được phép lưu vẫn do schema/server kiểm tra.

**Không cần tạo trường Java `objectClass` chỉ để lưu chuỗi các object class** khi đã dùng `@Entry` đúng cách. Nếu ứng dụng thật sự cần đọc/ghi object class như attribute riêng, phải hiểu rõ tác động đến schema và metadata ODM thay vì quản lý hai nguồn giá trị mâu thuẫn.

## 7. Tạo entry bằng ODM của LdapTemplate

Khi class đã có metadata ODM, `LdapTemplate` hỗ trợ phương thức:

~~~java
ldapTemplate.create(person);
~~~

Ví dụ một service tạo người dùng ở parent đã tồn tại:

~~~java
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public final class PersonService {
    private final LdapTemplate ldapTemplate;

    public PersonService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public void createAn() {
        // ContextSource đã có base = dc=example,dc=org.
        Name relativeDn = LdapNameBuilder.newInstance()
                .add("ou", "people")
                .add("uid", "an")
                .build();

        PersonEntry person = new PersonEntry(
                relativeDn,
                "an",
                "Nguyen Van An",
                "Nguyen",
                "an@example.org"
        );

        // ODM lấy thông tin từ @Entry, @Id và @Attribute.
        ldapTemplate.create(person);
    }
}
~~~

Quy trình:

1. Dựng DN bằng `LdapNameBuilder` để xử lý đúng RDN và escape của tên.
2. Gán `@Id` bằng DN tương đối đúng với `ContextSource`, gồm cả `ou=people` trong ví dụ.
3. Gán các trường cần thiết của entity, bao gồm `cn` và `sn`.
4. Spring LDAP dùng metadata `@Entry` và các field mapping để xây yêu cầu tạo entry.
5. LDAP server kiểm tra parent, schema, ACL và DN chưa tồn tại.
6. Nếu server chấp nhận, entry xuất hiện tại DN đã chỉ định.

**Phải tạo container cha trước.** Nếu `ou=people,dc=example,dc=org` chưa tồn tại, việc có `base="ou=people"` trong `@Entry` không khiến ODM tự tạo OU. Cần khởi tạo container bằng thao tác thích hợp, chẳng hạn `LdapTemplate.bind(relativeDn, null, attrs)`, rồi mới tạo người dùng.

### Tạo entry bằng DN tính từ @DnAttribute

Ngoài cách gán `@Id` tường minh, Spring LDAP có `@DnAttribute` để ánh xạ một trường Java với thành phần RDN. Với cách khai báo **DN do ODM tính**, một trường dùng để định danh có thể được viết như sau:

~~~java
import org.springframework.ldap.odm.annotations.DnAttribute;

@DnAttribute(value = "uid", index = 0)
private String uid;
~~~

Ví dụ trên là **một phần của entity**, không phải toàn bộ class. Khi kết hợp với `@Entry(base="ou=people", objectClasses=...)` và `@Id Name dn` để null lúc tạo, ODM có thể tính DN từ các trường `@DnAttribute` được khai báo đúng thứ tự/index, sau đó điền DN đã tính vào trường `@Id` theo hợp đồng của phương thức `create`.

Cần lưu ý:

- `@DnAttribute` ánh xạ thành phần của DN, **không phải`@Id`**; trường `@Id` vẫn phải tồn tại.
- Một trường có `@DnAttribute` **vẫn được ánh xạ sang attribute LDAP theo quy tắc mặc định** trừ khi thêm `@Transient`.
- Khi khai báo `index`, thư viện dùng thứ tự thành phần DN để tính tên; không chọn chỉ số một cách tùy tiện.
- Nếu đổi một trường là thành phần DN rồi gọi `update`, ODM có thể cần thực hiện hành vi đổi tên/di chuyển entry, không chỉ sửa attribute nội dung.
- Với các chuỗi DN nhiều OU, hãy kiểm tra thứ tự RDN và phần base trong test tích hợp; không dựa vào một phép nối chuỗi thủ công.

Trong bài này, mẫu `@Id` tường minh ở mục trên là cách dễ nhìn nhất để hiểu mối quan hệ giữa `@Entry`, DN và LDAP entry.

## 8. Tìm kiếm domain object qua ODM

Nếu mục tiêu chỉ là đọc entry vào Java, không cần tự duyệt `Attributes`. Ví dụ:

~~~java
import java.util.List;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.query.LdapQuery;

import static org.springframework.ldap.query.LdapQueryBuilder.query;

public final class PersonQueries {
    private final LdapTemplate ldapTemplate;

    public PersonQueries(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public List<PersonEntry> findByUid(String uid) {
        LdapQuery q = query()
                .base("ou=people")
                .where("uid").is(uid);

        return ldapTemplate.find(q, PersonEntry.class);
    }
}
~~~

Trong phương thức này:

- `find(..., PersonEntry.class)` yêu cầu ODM trả về các đối tượng theo metadata của `PersonEntry`.
- Điều kiện `uid` được xây bằng query builder, tránh tự nối input thành LDAP filter.
- `@Entry.objectClasses` giúp ODM nhận diện kiểu entry phù hợp; không cần tùy ý map nhóm LDAP thành người dùng.
- `@Attribute` xác định cách đặt dữ liệu trong các trường Java.
- `@Id` được dùng để mang DN của entry đọc được.
- `@Entry.base` và `query().base(...)` cần được hiểu đúng theo contract API. Ví dụ đặt cùng nhánh `ou=people` để diễn đạt phạm vi tìm kiếm; không tự tính tên bằng cách cộng hai chuỗi base.

**Một số API ODM còn gồm** `findByDn(Name, Class)`, `findOne(LdapQuery, Class)`, `findAll(Class)`, `create(Object)`, `update(Object)` và `delete(Object)`. Chữ ký cụ thể cần đối chiếu phiên bản Spring LDAP đang sử dụng.

### Không nhầm objectClasses với filter nghiệp vụ

Một truy vấn `uid=an` có thể thu hẹp kết quả theo UID. Nhưng `uid` **không mặc định duy nhất trên toàn DIT**; hai entry tại những OU khác nhau có thể cùng UID nhưng DN khác. Để chọn đúng account, cần đồng thời xác định phạm vi base/search scope và điều kiện nghiệp vụ.

Nếu chỉ cần kiểm tra một DN cụ thể, `findByDn(...)` hoặc lookup theo DN thường rõ ràng hơn việc search toàn cây.

## 9. Khi @Entry không khớp objectClass thực tế

Giả sử directory có entry:

~~~ldif
dn: uid=mai,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: mai
cn: Tran Thi Mai
sn: Tran
mail: mai@example.org
~~~

Nhưng class Java được đánh dấu:

~~~java
@Entry(objectClasses = {"top", "person"}, base = "ou=people")
public class MinimalPerson {
    // Chỉ ánh xạ các attribute thích hợp với person.
}
~~~

Điều cần phân biệt:

1. **Entry đã tồn tại** có tập `objectClass` riêng và những attribute phù hợp với schema thực tế.
2. `@Entry.objectClasses` cung cấp tiêu chí và metadata để ODM xác định các object classes mà entity đại diện.
3. Tập class quá hẹp có thể khiến một số entry không được ánh xạ như kỳ vọng, nhất là khi cần quản lý attribute thuộc lớp dẫn xuất.
4. Khi **tạo entry mới**, chỉ các object class được khai báo trong entity sẽ được ODM sử dụng; nếu đồng thời muốn lưu `mail` hoặc thuộc tính đặc thù của lớp dẫn xuất, có thể gặp lỗi ràng buộc.
5. Một class Java với mảng `objectClasses` rộng không cấp cho tài khoản quyền đọc các attribute bị ACL hạn chế.

Vì thế, trước khi dùng ODM cho một kiểu entry có sẵn trong doanh nghiệp, hãy **kiểm tra schema và dữ liệu mẫu thực tế**, bao gồm object class phụ, thuộc tính optional, schema mở rộng và cách quản lý operational attributes.

### Có nên tạo một domain class cho mọi objectClass không?

Không nhất thiết. Một domain class nên đại diện cho **một khái niệm nghiệp vụ và tập entry có cấu trúc tương thích**, chứ không phải phản ánh toàn bộ catalog LDAP schema trong Java.

Ví dụ:

| Kiểu domain object | Object class dự kiến | Dữ liệu điển hình |
|---|---|---|
| `PersonEntry` | Chuỗi `top → person → organizationalPerson → inetOrgPerson` | `uid`, `cn`, `sn`, `mail` |
| `OrgUnitEntry` | `top`, `organizationalUnit` | `ou`, `description` |
| `GroupEntry` | `top`, `groupOfNames` | `cn`, `member` |

Ba loại này thường nên có ba model khác nhau. Không khai báo `GroupEntry` sử dụng `inetOrgPerson` chỉ vì cả hai cùng có attribute `cn`.

## 10. Ví dụ thứ hai: @Entry cho container organizationalUnit

Khi cấu trúc dữ liệu cần chứa entry con, domain class cho OU có thể dùng metadata khác với người dùng:

~~~java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;

@Entry(
    base = "",
    objectClasses = {"top", "organizationalUnit"}
)
public class OrgUnitEntry {

    @Id
    private Name dn;

    @Attribute(name = "ou")
    private String name;

    @Attribute(name = "description")
    private String description;

    public OrgUnitEntry() {}

    public OrgUnitEntry(Name dn, String name, String description) {
        this.dn = dn;
        this.name = name;
        this.description = description;
    }

    public Name getDn() { return dn; }
    public String getName() { return name; }
    public String getDescription() { return description; }
}
~~~

Nếu tạo `ou=people` bằng ODM:

~~~java
Name peopleDn = LdapNameBuilder.newInstance()
        .add("ou", "people")
        .build();

OrgUnitEntry people = new OrgUnitEntry(
        peopleDn, "people", "People accounts"
);

ldapTemplate.create(people);
~~~

Sau khi container tồn tại, mới tạo các `PersonEntry` bên dưới nó. Cả hai lời gọi `create(...)` phải được thực hiện bằng tài khoản đủ quyền; **không có bảo đảm một giao dịch gồm hai lần Add sẽ rollback toàn bộ nếu bước sau lỗi**.

Lưu ý: class cho OU là một ví dụ của kiểu entry thường có thể chứa con. **Việc được phép có con vẫn phụ thuộc DIT, schema/content rules, ACL và cấu hình của LDAP server**; annotation `@Entry` không tự quyết định quy tắc cấu trúc của cây.

## 11. Object class và các ràng buộc schema khi ghi

Các lỗi hay gặp khi cấu hình `@Entry` và domain object:

| Hiện tượng | Nguyên nhân có thể | Hướng kiểm tra |
|---|---|---|
| Add người dùng thất bại với `objectClassViolation` | Thiếu object class phù hợp, thiếu `cn`/`sn`, field không được schema cho phép | Đối chiếu `@Entry.objectClasses` và MUST/MAY |
| Add thất bại với `invalidAttributeSyntax` | Giá trị không hợp syntax, ví dụ kiểu Integer, DN, IA5 String | Kiểm tra loại attribute và converter |
| Add thất bại với `noSuchObject` | Parent DN chưa tồn tại hoặc base DN sai | Kiểm tra `@Entry.base`, `@Id` và `ContextSource` base |
| Add thất bại với `entryAlreadyExists` | DN đã được dùng | Xem quy tắc uniqueness/idempotency |
| Add thất bại với `insufficientAccessRights` | Tài khoản bind thiếu quyền | Kiểm tra ACL ở parent và entry |
| Object đọc lên thiếu dữ liệu `mail` | Field Java không ánh xạ đúng attribute hoặc ACL không cho đọc | Kiểm tra `@Attribute(name="mail")` và quyền đọc |
| Mapper chỉ trả một phần entry | Object class metadata không khớp; search base/filter không phù hợp | Đối chiếu `@Entry.objectClasses` và objectClass thực tế |
| Trường Java phụ bị ghi thành attribute lạ | Quên `@Transient` | Đánh dấu trường không bền vững |
| Update vô tình làm thay đổi DN | Thay đổi trường `@DnAttribute` dùng để tính tên | Tách biệt đổi DN và sửa nội dung, kiểm thử kỹ |

Các mã LDAP hữu ích:

| Result code | Tên | Ý nghĩa thường gặp |
|---|---|---|
| **19** | `constraintViolation` | Vi phạm ràng buộc dữ liệu hoặc chính sách server |
| **21** | `invalidAttributeSyntax` | Giá trị không phù hợp cú pháp LDAP attribute |
| **32** | `noSuchObject` | Entry/parent cần dùng không tìm thấy |
| **50** | `insufficientAccessRights` | Không đủ quyền |
| **65** | `objectClassViolation` | Object class, MUST/MAY hoặc tính hợp lệ của entry |
| **68** | `entryAlreadyExists` | DN đích đã tồn tại |

**Không kết luận chỉ từ exception Java** rằng annotation sai; lỗi có thể do server, ACL, DN, schema, dữ liệu hiện có hoặc một converter. Cần thu thập loại lỗi, DN liên quan đã được che dữ liệu nhạy cảm và chẩn đoán phía server nếu có quyền.

## 12. Cập nhật domain object: cần để ý objectClasses và DN

Spring LDAP hỗ trợ `ldapTemplate.update(entity)` đối với entity được ánh xạ. Khi cập nhật:

- Cần đảm bảo class có metadata `@Entry`/`@Id` hợp lệ.
- Những trường Java được ánh xạ phải phù hợp schema và attribute hiện có.
- Các trường `@Transient` không được dùng làm thay đổi dữ liệu LDAP.
- Nếu DN được **tính từ `@DnAttribute`** và các thành phần tên thay đổi, một số quy trình update có thể cần thực hiện **rename/move**; đây là thao tác khác với thay đổi `mail` đơn thuần.
- Update không tự tạo OU cha còn thiếu hoặc thêm object class bất kỳ vào schema của máy chủ.

Một lỗi thiết kế là ánh xạ một entity chỉ với `objectClasses={"top","person"}`, rồi dùng nó để sửa những attribute cần `inetOrgPerson` mà không xem xét schema thực tế. Một lỗi khác là đổi giá trị RDN/UID mà không nhận ra DN và những tham chiếu nhóm dựa trên DN có thể thay đổi theo.

Trong các ứng dụng đồng bộ nhiều hệ thống, hãy tách **khóa định danh nghiệp vụ** khỏi **DN có thể thay đổi**. DN đặc biệt hữu ích để lookup một entry trong DIT, nhưng không phải một khóa bất biến trên mọi lần rename/move.

## 13. Mapping dữ liệu nhiều giá trị và kiểu đặc biệt

Object class xác định attribute được phép, nhưng mapping còn phụ thuộc **kiểu giá trị**. LDAP cho phép attribute đa giá trị, và một số attribute chứa DN hoặc dữ liệu nhị phân.

Ví dụ nhóm dùng `groupOfNames`:

~~~ldif
dn: cn=developers,ou=groups,dc=example,dc=org
objectClass: top
objectClass: groupOfNames
cn: developers
member: uid=an,ou=people,dc=example,dc=org
member: uid=mai,ou=people,dc=example,dc=org
~~~

Không nên ánh xạ `member` thành một chuỗi duy nhất nếu nghiệp vụ cần lưu nhiều DN. Spring LDAP ODM có hỗ trợ các kiểu như `Set<Name>` trong trường hợp thích hợp; ví dụ:

~~~java
@Entry(
    objectClasses = {"top", "groupOfNames"},
    base = "ou=groups"
)
public class GroupEntry {
    @Id
    private Name dn;

    @Attribute(name = "cn")
    private String groupName;

    @Attribute(name = "member")
    private java.util.Set<Name> members;

    // Constructor, getter/setter phù hợp.
}
~~~

Đây là **đoạn định nghĩa minh họa**, không phải class Java đầy đủ. Với `Name`, mapper dùng ngữ nghĩa DN thay vì so sánh chuỗi theo ký tự thuần khi tính toán một số thay đổi. Kiểu được chọn phải phù hợp schema, converter và phiên bản thư viện.

Nếu cần mã hóa/giải mã attribute nhị phân, hãy kiểm tra converter và syntax OID của attribute. Không giả định mọi LDAP attribute đều có thể map an toàn sang `String`.

## 14. @Entry không thay thế validation, authentication và TLS

Ngay cả khi entity có đầy đủ annotation:

- **Validation nghiệp vụ**: kiểm tra độ dài UID theo chính sách, email, trạng thái tài khoản và tính duy nhất theo yêu cầu của ứng dụng.
- **LDAP schema**: máy chủ kiểm tra object class, syntax và attribute bắt buộc/được phép.
- **ACL**: danh tính dùng để bind có quyền tạo/đọc/sửa entry ở DN tương ứng hay không.
- **Authentication**: `create(person)` không phải thao tác xác thực mật khẩu người dùng; LDAP Bind authentication là quy trình khác.
- **Kết nối**: `ContextSource`, LDAPS/StartTLS, chứng chỉ, pooling và timeout quyết định cách ứng dụng truy cập directory.
- **Ghi log an toàn**: không log credential hoặc các attribute nhạy cảm; DN cũng có thể chứa dữ liệu cá nhân.
- **Kiểm thử**: cần LDAP test server có schema và ACL gần thực tế thay vì chỉ kiểm tra POJO có annotation.

Một domain object đôi khi được tái sử dụng cho cả hiển thị và ghi LDAP. Hãy cẩn thận: dữ liệu trả từ API công khai không nên vô tình bao gồm những attribute nhạy cảm mà tài khoản LDAP có quyền đọc. Cân nhắc tách **LDAP entity** và **DTO giao tiếp API** khi có nhiều đối tượng nhận dữ liệu.

### Ví dụ cấu hình sai về bảo mật

Không nên lưu `userPassword` trong một trường Java được tự động serialize vào JSON hoặc log chỉ vì server có attribute đó. `@Entry` không che giấu dữ liệu nhạy cảm; chính sách truy cập, DTO, ACL và quy trình xác thực mới quyết định bảo mật.

Tương tự, không đặt mật khẩu bind LDAP trực tiếp trong annotation/domain class. Thông tin đăng nhập thuộc cấu hình an toàn của `ContextSource` hoặc hệ thống quản lý bí mật.

## 15. Checklist thiết kế @Entry trước khi triển khai

| Câu hỏi | Đáp án cần có |
|---|---|
| Domain object đại diện loại entry gì? | Ví dụ `inetOrgPerson` hay `organizationalUnit` |
| Schema thật của server định nghĩa chuỗi object class thế nào? | Kiểm tra `SUP`, `MUST`, `MAY`, lớp structural/auxiliary |
| Mảng `objectClasses` có phù hợp thuộc tính cần quản lý không? | Không thiếu lớp cần thiết và không thêm class vô cớ |
| `@Entry.base` có phù hợp `ContextSource` base không? | DN tương đối được hiểu rõ, không lặp hay thiếu OU |
| Trường `@Id` có kiểu đúng không? | Kiểu `Name` hoặc dẫn xuất thích hợp |
| RDN sẽ được dựng như thế nào? | `@Id` tường minh hoặc `@DnAttribute` có quy tắc rõ ràng |
| Tên Java khác tên LDAP có `@Attribute` không? | Ví dụ `commonName → cn`, `email → mail` |
| Trường không được ghi có `@Transient` không? | Tránh tạo attribute không hợp schema |
| Có attribute đa trị/nhị phân/DN không? | Chọn kiểu và converter tương ứng |
| Parent DN đã tồn tại và tài khoản có ACL chưa? | Kiểm tra trước khi tạo |
| Dữ liệu đã có những object class bổ sung nào? | Khảo sát entry thật; không giả định mọi người dùng giống hệt |
| Có test các nhánh lỗi không? | Object class sai, thiếu MUST, trùng DN, sai base, thiếu quyền |

### Bài tập 1: đọc một class ODM

Cho đoạn Java:

~~~java
@Entry(
    base = "ou=people",
    objectClasses = {"top", "person", "organizationalPerson", "inetOrgPerson"}
)
public class Employee {
    @Id
    private Name dn;

    @Attribute(name = "cn")
    private String fullName;

    @Attribute(name = "sn")
    private String familyName;

    @Attribute(name = "mail")
    private String email;

    @Transient
    private String screenTitle;
}
~~~

Hãy trả lời:

1. Class Java này ánh xạ với kiểu entry nào?
2. Nếu `ContextSource` base là `dc=example,dc=org`, `@Entry.base` tương ứng nhánh nào?
3. Trường nào chứa DN? Trường nào không được ghi LDAP?
4. Để tạo `uid=an,ou=people,dc=example,dc=org` còn cần attribute nào cho RDN?
5. Nếu bỏ `familyName`/`sn` khi Add, lỗi nào có thể xảy ra?

**Gợi ý đáp án:** Entity đại diện chuỗi structural `person → organizationalPerson → inetOrgPerson` cùng `top`; base là `ou=people,dc=example,dc=org`; `dn` mang tên LDAP và `screenTitle` không lưu. Nếu RDN dùng `uid=an`, cần giá trị `uid: an` phù hợp schema/RDN. Thiếu `sn` vi phạm yêu cầu `MUST` kế thừa từ `person` và có thể bị từ chối với `objectClassViolation (65)`.

### Bài tập 2: chọn objectClasses cho nhóm

Directory có entry nhóm:

~~~ldif
dn: cn=ops,ou=groups,dc=example,dc=org
objectClass: top
objectClass: groupOfNames
cn: ops
member: uid=an,ou=people,dc=example,dc=org
~~~

**Câu hỏi:** Nếu muốn tạo một model Java cho nhóm này, có nên sao chép `@Entry.objectClasses` của `PersonEntry` không?

**Đáp án:** Không. Nhóm đại diện kiểu entry khác, nên sử dụng các object class của schema nhóm (ở đây `top` và `groupOfNames`) và trường `member` thuộc loại nhiều giá trị DN. Cần kiểm tra schema/ACL và điều kiện tối thiểu cho `groupOfNames`, bao gồm ít nhất một thành viên nếu schema yêu cầu.

### Bài tập 3: base và @Id

Cho `ContextSource` base `dc=example,dc=org`, entity `@Entry(base="ou=people")` và cần tạo người dùng `uid=mai` dưới OU này.

**Câu hỏi:** Nếu gán `@Id` tường minh, DN nào nên truyền trong ví dụ ở mục 7? Nếu không gán `@Id`, có thể dựa vào cơ chế nào?

**Đáp án:** DN tương đối chứa cả OU đích: `uid=mai,ou=people`, bởi nó được hiểu so với base của `ContextSource` trong ví dụ. Nếu muốn ODM tính DN, cần khai báo các trường `@DnAttribute` phù hợp với RDN và kết hợp `@Entry.base`; không thể chỉ để `@Id` rỗng mà không có đủ metadata định danh.

### Bài tập 4: chẩn đoán lỗi

Khi gọi `ldapTemplate.create(person)`, server báo `objectClassViolation`. Người viết class khẳng định rằng đã có `@Attribute(name="mail")` nên chắc chắn `mail` hợp lệ.

**Hướng phân tích:** Kiểm tra đủ `@Entry.objectClasses`, chuỗi kế thừa, `cn`/`sn`, DN/RDN, các field tự động map theo tên và `@Transient`. Sau đó đối chiếu schema thực tế. `@Attribute` không cấp phép attribute ngoài schema.

## 16. Câu hỏi tự kiểm tra

**1. `@Entry` là annotation đặt trên class Java hay trên LDAP server?**

Trên class Java, để cung cấp metadata cho ODM. Nó không tự định nghĩa schema trên LDAP server.

**2. Vì sao một `inetOrgPerson` cần `cn` và `sn` dù trong Java chỉ khai báo một class `PersonEntry`?**

Vì object class LDAP kế thừa `person`, mà `person` quy định hai attribute này là bắt buộc. Kế thừa schema độc lập với kế thừa class Java.

**3. `@Id` phải là `String uid` không?**

Không. `@Id` đại diện cho **DN** và phải có kiểu `javax.naming.Name` hoặc kiểu dẫn xuất phù hợp; `uid` là attribute riêng.

**4. `@Entry.base` có tạo entry container nếu chưa tồn tại không?**

Không. Khi tạo tài khoản, parent DN phải tồn tại và tài khoản bind phải đủ quyền.

**5. Tại sao một field không đánh dấu `@Attribute` vẫn có thể bị ODM lưu?**

Vì ODM hỗ trợ ánh xạ mặc định theo tên field Java. Nếu là field không muốn persist, cần dùng `@Transient`.

**6. Có thể dùng `@Entry.objectClasses` để cho phép một attribute bị schema cấm không?**

Không. Annotation chỉ khai báo object classes mà entity đại diện; server vẫn là nơi quyết định hợp lệ dữ liệu.

**7. Khi dùng `@DnAttribute` mà thay giá trị định danh rồi cập nhật, cần đề phòng điều gì?**

DN được tính có thể đổi và kéo theo thao tác rename/move. Cần kiểm thử tác động đến DN, nhóm và các hệ thống tham chiếu.

## Ghi nhớ

**`@Entry` xác định các LDAP object classes mà domain object Java đại diện và vùng base tùy chọn để ODM làm việc với các entry đó.** Cần khai báo `objectClasses` phù hợp **schema thực tế**, bao gồm chuỗi kế thừa cần thiết cho những attribute được ánh xạ; `@Id` lưu DN, `@Attribute` điều chỉnh tên thuộc tính, `@DnAttribute` hỗ trợ thành phần tên và `@Transient` loại bỏ trường không cần persist. Annotation giúp Spring LDAP tạo/đọc/sửa entry qua ODM, nhưng **không thay thế LDAP schema, ACL, kiểm tra DN, bảo mật kết nối hoặc kiểm thử tích hợp**. Hiểu đúng giới hạn này giúp mô hình domain rõ ràng mà không đánh đổi tính hợp lệ và an toàn của dữ liệu thư mục.
