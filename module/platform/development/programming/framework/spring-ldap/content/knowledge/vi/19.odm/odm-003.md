# @Id và DN của đối tượng trong Spring LDAP ODM

Khi viết ứng dụng với ORM như JPA, lập trình viên thường nghĩ tới `@Id` như một khóa chính kiểu `Long` hoặc `UUID`. Trong **Spring LDAP Object-Directory Mapping (ODM)**, ý nghĩa của `@Id` khác: nó đánh dấu trường chứa **Distinguished Name (DN)** của entry LDAP. DN là **tên và vị trí của entry trong cây thư mục**, không phải một số ID do cơ sở dữ liệu quan hệ tự tăng.

Hiểu sai `@Id` có thể dẫn đến lỗi rất khó nhận biết: dùng `uid` thay cho DN, nối lặp suffix `dc=example,dc=org`, tạo entry ở sai OU, vô tình move khi cập nhật hoặc không tìm thấy đối tượng sau rename. Bài học thuộc chương **ODM** của **SPRING_LDAP**, tập trung vào cách khai báo `@Id`, quan hệ giữa `Name`, DN, `@Entry(base=...)` và `@DnAttribute`; đồng thời thực hành đọc/tạo/cập nhật entity bằng `LdapTemplate`, xử lý DN an toàn và kiểm thử với directory lab.

Spring LDAP còn cung cấp `LdapClient`, `ContextSource`, `LdapTemplate` và `DirContextAdapter` cho các cách truy cập LDAP khác nhau. ODM là lớp mapping tiện ích, **không thay thế** schema, filter, ACL, TLS hoặc quy tắc quản trị danh tính trên LDAP server.

## 1. LDAP entry có tên DN và các thuộc tính

Giả sử cây directory:

~~~text
dc=example,dc=org
├── ou=people
│   ├── uid=an
│   ├── uid=binh
│   └── ou=contractors
│       └── uid=chi
├── ou=groups
│   └── cn=developers
└── ou=services
    └── cn=app-reader
~~~

Entry của An:

~~~ldif
dn: uid=an,ou=people,dc=example,dc=org
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: an
cn: Nguyen Van An
sn: Nguyen
mail: an@example.org
~~~

| Thành phần | Ví dụ | Vai trò |
| --- | --- | --- |
| **DN** | `uid=an,ou=people,dc=example,dc=org` | Tên đầy đủ xác định entry trong cây |
| **RDN** | `uid=an` | Thành phần tên phân biệt entry với các sibling |
| **Naming attribute** | `uid` | Loại thuộc tính được dùng trong RDN |
| **Attribute value** | `an` | Giá trị thực tế của `uid` |
| **LDAP object class** | `inetOrgPerson` | Ràng buộc schema về các thuộc tính MUST/MAY |
| **ODM entity** | Java `PersonEntry` | Đối tượng biểu diễn entry sau mapping |

**DN không phải một thuộc tính LDAP bình thường có tên `dn` để mapping như `mail` hay `cn`.** DN là tên entry do giao thức và JNDI quản lý. Một số server có operational attribute liên quan tên entry, nhưng không được đồng nhất chúng với trường `@Id`.

### Ba loại “ID” khác nhau

| Tên gọi | Có thể thay đổi? | Ví dụ |
| --- | --- | --- |
| DN / `@Id` của ODM | **Có** khi rename/move | `uid=an,ou=people,dc=example,dc=org` |
| Giá trị định danh nghiệp vụ | Phụ thuộc chính sách; có thể là UID, employee number | `uid: an`, `employeeNumber: E104` |
| Định danh bất biến do directory cấp | Phụ thuộc server và attribute | `entryUUID`, `objectGUID` |

Spring LDAP **không bảo đảm `@Id` là ID bất biến** chỉ vì nó mang tên annotation `Id`. Nếu ứng dụng cần khóa liên kết bền vững xuyên rename/move, phải thiết kế một khóa bất biến tương ứng và kiểm tra cách server hỗ trợ.

## 2. `@Id` trong Spring LDAP ODM là annotation nào?

Khai báo đúng là:

~~~java
import org.springframework.ldap.odm.annotations.Id;
import javax.naming.Name;

@Id
private Name dn;
~~~

Đây là **`org.springframework.ldap.odm.annotations.Id`**, không phải:

- `jakarta.persistence.Id` hoặc `javax.persistence.Id` của JPA.
- `org.springframework.data.annotation.Id` của Spring Data.
- Một annotation do dự án tự tạo.

Theo Spring LDAP ODM, trường đánh dấu `@Id` phải có kiểu **`javax.naming.Name` hoặc một lớp con thích hợp**, ví dụ `javax.naming.ldap.LdapName`. Không dùng `String`, `Long` hay `UUID` làm trường `@Id`.

~~~java
// ĐÚNG cho Spring LDAP ODM:
@Id
private Name dn;

// SAI cho Spring LDAP ODM:
// @Id private String uid;
// @Id private Long id;
// @jakarta.persistence.Id private Name dn;
~~~

**`Name` là interface Java của JNDI**, còn `LdapName` là triển khai biểu diễn tên LDAP theo cú pháp DN. Dùng kiểu `Name` giúp API thao tác tên theo cấu trúc thay vì ghép chuỗi thô, nhưng **không tự cấp quyền** hoặc xác nhận entry tồn tại trên server.

### Khác biệt quan trọng với JPA

| Spring LDAP ODM `@Id` | JPA `@Id` |
| --- | --- |
| Chứa DN của LDAP entry | Chứa khóa của bản ghi/entity quan hệ |
| Kiểu `Name`/`LdapName` | Thường kiểu số, `UUID` hoặc giá trị khóa khác |
| Mang thông tin vị trí trong DIT | Khóa thường không chứa đường dẫn bảng/nhánh |
| Có thể đổi sau rename/move | Khóa chính thường được giữ ổn định theo thiết kế |
| Không có trình sinh ID tự tăng mặc định | Có thể phối hợp `@GeneratedValue` trong JPA |
| Phải hiểu `ContextSource.base` | Không có khái niệm LDAP search base |

Spring LDAP ODM không tự tạo một DN “duy nhất ngẫu nhiên” chỉ vì trường `@Id` được để `null`. Muốn tự tính DN, cần cấu hình đúng `@DnAttribute` và `@Entry.base` hoặc gán tên tường minh.

## 3. Các annotation kết hợp với `@Id`

| Annotation | Đặt ở đâu? | Chức năng |
| --- | --- | --- |
| **`@Entry`** | Class | Mô tả các LDAP object classes và base phục vụ mapping |
| **`@Id`** | Field kiểu `Name` | Ánh xạ DN của entry |
| **`@Attribute`** | Field | Ánh xạ giá trị thuộc tính LDAP như `cn`, `sn`, `mail` |
| **`@DnAttribute`** | Field `String` | Ánh xạ thành phần RDN/DN; có thể hỗ trợ tính DN tự động |
| **`@Transient`** | Field | Loại field khỏi ánh xạ LDAP attribute |

Các annotation này thuộc package:

~~~java
org.springframework.ldap.odm.annotations
~~~

`@Entry` và `@Id` là hai annotation bắt buộc đối với entity ODM. Khi **tạo entry mới**, Spring LDAP dùng danh sách `objectClasses` khai báo trong `@Entry` để tạo dữ liệu object class; vì vậy cần chọn các class phù hợp schema. Ví dụ với `inetOrgPerson`, nên khai báo chuỗi phù hợp `top`, `person`, `organizationalPerson` và `inetOrgPerson`.

**Cẩn thận với `@DnAttribute`:** chỉ field kiểu `String` được hỗ trợ theo hợp đồng annotation. Nếu muốn Spring tự **tính DN** từ các trường, cần khai báo `index` trên tất cả các trường `@DnAttribute` của entity đó. Nếu chỉ dùng `@DnAttribute(value="uid")` không có index, Spring có thể đọc thành phần DN vào field nhưng không có đầy đủ thông tin để tính DN khi tạo entity.

## 4. Khai báo entity với DN tường minh

Đây là ví dụ phổ biến và dễ kiểm soát khi service **tự quyết định DN**:

~~~java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;
import org.springframework.ldap.odm.annotations.Transient;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
    }
)
public class PersonEntry {

    @Id
    private Name dn;

    @Attribute(name = "uid")
    private String uid;

    @Attribute(name = "cn")
    private String commonName;

    @Attribute(name = "sn")
    private String surname;

    @Attribute(name = "mail")
    private String email;

    @Transient
    private String displayOnlyNote;

    public PersonEntry() {}

    public Name getDn() { return dn; }
    public void setDn(Name dn) { this.dn = dn; }

    public String getUid() { return uid; }
    public void setUid(String uid) { this.uid = uid; }

    public String getCommonName() { return commonName; }
    public void setCommonName(String commonName) {
        this.commonName = commonName;
    }

    public String getSurname() { return surname; }
    public void setSurname(String surname) { this.surname = surname; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }

    public String getDisplayOnlyNote() { return displayOnlyNote; }
    public void setDisplayOnlyNote(String note) {
        this.displayOnlyNote = note;
    }
}
~~~

Lưu ý về đoạn mã:

1. `dn` dùng kiểu `Name` và annotation đúng của **Spring LDAP ODM**.
2. `uid`, `cn`, `sn`, `mail` là **thuộc tính riêng**, không tự đồng nhất với toàn bộ DN.
3. `@Attribute(name="cn")` cho phép tên Java `commonName` khác tên thuộc tính LDAP.
4. `@Transient` ngăn `displayOnlyNote` bị lưu thành attribute trong LDAP; không dùng `@Transient` để che một secret đang bị log ở tầng khác.
5. Class có constructor không tham số và getter/setter để dễ mapping/kiểm thử; ODM thao tác dựa trên mapping field theo cấu hình.
6. `@Entry.base="ou=people"` là base giúp tính DN nếu dùng `@DnAttribute`, nhưng **không có nghĩa Spring sẽ tự thêm `ou=people` vào một DN tường minh đã chứa chính OU đó**. Phải hiểu ngữ cảnh khi xây tên.

Ví dụ này dùng **explicit DN**, chưa cấu hình `@DnAttribute`. Mỗi entity mới cần được gán `dn` trước khi gọi `ldapTemplate.create(entity)`.

## 5. DN tương đối với `ContextSource.base`

Giả sử Spring LDAP kết nối tới:

~~~text
URL:                ldaps://ldap.example.org:636
ContextSource.base: dc=example,dc=org
Bind identity:      cn=app-reader,ou=services,dc=example,dc=org
~~~

Trong đường gọi thông thường của `LdapTemplate`, DN được truyền từ service thường **tương đối với `ContextSource.base`**:

| Giá trị `Name` trong ODM | DN hiệu lực trên LDAP server |
| --- | --- |
| `uid=an,ou=people` | `uid=an,ou=people,dc=example,dc=org` |
| `uid=chi,ou=contractors,ou=people` | `uid=chi,ou=contractors,ou=people,dc=example,dc=org` |
| `cn=developers,ou=groups` | `cn=developers,ou=groups,dc=example,dc=org` |

Không đưa full DN vào API đang kỳ vọng tên tương đối rồi mong nó tự bỏ suffix đã có. Nếu `ContextSource.base` đã là `dc=example,dc=org`, một giá trị `Name` chứa toàn bộ `dc=example,dc=org` có thể gây **lặp suffix**.

### Dùng `LdapNameBuilder` thay vì nối chuỗi

~~~java
import javax.naming.Name;
import org.springframework.ldap.support.LdapNameBuilder;

public final class PersonDns {
    private PersonDns() {}

    public static Name relativeDn(String uid) {
        if (uid == null || uid.isBlank() || uid.length() > 64) {
            throw new IllegalArgumentException("Invalid uid");
        }
        return LdapNameBuilder.newInstance("ou=people")
                .add("uid", uid)
                .build();
    }
}
~~~

Với `uid="an"`:

~~~text
relativeDn("an") -> uid=an,ou=people
full server DN    -> uid=an,ou=people,dc=example,dc=org
~~~

Nếu UID chứa dấu phẩy hoặc ký tự cần escape, builder tạo biểu diễn tên phù hợp thay vì xem chúng như ranh giới RDN mới. Ví dụ `uid="an,dev"` phải được biểu diễn như **một giá trị UID**, không trở thành hai thành phần DN.

**DN escaping khác LDAP filter escaping**. Khi dựng DN, dùng `LdapNameBuilder`. Khi tìm theo UID do người dùng nhập, dùng `LdapQueryBuilder` hoặc filter builder để escape assertion value. Builder giúp cú pháp đúng, nhưng ứng dụng vẫn phải kiểm tra UID nào được phép tạo và OU nào được phép ghi.

## 6. Dùng `@Id` trong các thao tác ODM

Spring LDAP cung cấp các phương thức ODM trực tiếp trên `LdapTemplate`:

| API | Mục đích | Tương tác với `@Id` |
| --- | --- | --- |
| `create(entity)` | Tạo LDAP entry mới | Lấy DN tường minh ở `@Id` hoặc thử tính qua `@DnAttribute` |
| `findByDn(dn, clazz)` | Tìm entry xác định theo DN | Trả entity có `@Id` được ánh xạ |
| `findOne(query, clazz)` | Tìm đúng một entry phù hợp query | Ánh xạ DN của entry tìm được vào `@Id` |
| `find(query, clazz)` | Tìm danh sách entry | Mỗi entity có DN riêng |
| `update(entity)` | Cập nhật entity hiện có | Dùng DN tường minh hoặc DN tính toán để xác định thao tác |
| `delete(entity)` | Xóa entity theo mapping | Cần xác định đúng entry qua DN |
| `findAll(clazz)` | Tìm tất cả entry phù hợp entity type | Chỉ hoạt động trong phạm vi và ACL cho phép |

Lưu ý hai họ phương thức có thể gây nhầm:

~~~java
ldapTemplate.create(person);        // ODM: dùng @Entry, @Id...
ldapTemplate.bind(dirContextOps);   // Tạo entry theo DirContextOperations

ldapTemplate.update(person);        // ODM entity update
ldapTemplate.modifyAttributes(...); // Sửa theo DN/ModificationItem
~~~

Cả hai đường đều có thể sử dụng trong ứng dụng, nhưng không tự động **giống nhau về cách mapping, kiểm tra object class và cách tính DN**.

### Ví dụ tạo, đọc và cập nhật

~~~java
import javax.naming.Name;

import org.springframework.ldap.core.LdapTemplate;
import org.springframework.stereotype.Service;

@Service
public class PersonOdmService {

    private final LdapTemplate ldapTemplate;

    public PersonOdmService(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public PersonEntry createPerson(
            String uid, String commonName, String surname) {

        if (commonName == null || commonName.isBlank()
                || surname == null || surname.isBlank()) {
            throw new IllegalArgumentException("cn and sn required");
        }

        PersonEntry person = new PersonEntry();
        person.setDn(PersonDns.relativeDn(uid));
        person.setUid(uid);
        person.setCommonName(commonName);
        person.setSurname(surname);

        ldapTemplate.create(person);
        return person;
    }

    public PersonEntry findPerson(String uid) {
        Name dn = PersonDns.relativeDn(uid);
        return ldapTemplate.findByDn(dn, PersonEntry.class);
    }

    public void updateEmail(String uid, String email) {
        if (email != null && email.length() > 254) {
            throw new IllegalArgumentException("Email too long");
        }

        PersonEntry person = findPerson(uid);
        person.setEmail(email);
        ldapTemplate.update(person);
    }
}
~~~

**Giả định:** schema trong LDAP lab chấp nhận chuỗi object class của entity và các thuộc tính được khai báo; OU `ou=people` đã có, `ContextSource.base=dc=example,dc=org` và tài khoản thực hiện có quyền thích hợp. Không dùng account quản trị production cho code mẫu.

Điểm cần hiểu:

- `createPerson` **gán DN tường minh vào `@Id`**, đồng thời đặt `uid` như một attribute của entry.
- `findByDn` tra cứu theo DN, không phải search filter `(uid=...)`.
- `updateEmail` đọc entity rồi sửa một attribute; ở thời điểm cập nhật, server vẫn quyết định quyền/schema.
- **Không tự chỉnh `person.setDn(...)` để giả lập rename**, cũng không đổi `uid` tùy tiện khi DN đang dùng `uid` làm RDN. Rename/move là một quy trình riêng cần kiểm tra tham chiếu và ACL.

### Khi DN đã tồn tại thì sao?

Một lệnh `ldapTemplate.create(person)` với DN đã có **không phải upsert**. Thao tác tạo entry có thể thất bại với LDAP result `entryAlreadyExists (68)` và Spring LDAP exception tương ứng `NameAlreadyBoundException`. Không tự chuyển lỗi đó thành `update(...)` nếu nghiệp vụ không cho phép ghi đè entity hiện có.

## 7. Không đồng nhất `@Id` và `@DnAttribute`

Đây là phần thường gây nhầm nhất trong ODM.

- **`@Id`** ánh xạ **toàn bộ DN** của entity vào một trường kiểu `Name`.
- **`@DnAttribute`** ánh xạ **một thành phần giá trị trong DN** vào trường kiểu `String`.
- **`@Entry(base=...)`** cung cấp phần gốc cho việc tính DN khi dùng các `@DnAttribute(index=...)`.

Ví dụ khi đã đọc entry:

~~~text
DN hiệu lực: uid=an,ou=people,dc=example,dc=org
@Entry.base:  ou=people
@Id dn:      uid=an,ou=people
@DnAttribute(value="uid", index=0) uid: an
~~~

Trường `uid` chỉ chứa giá trị `"an"`, không thể thay thế trường `dn` nếu service cần biết cả OU và vị trí entry.

### Quy tắc về index

Theo Spring LDAP, `index` của `@DnAttribute` là **chỉ số 0-based trong phần DN được tính toán**; để tự tính DN, mọi field mang `@DnAttribute` phải có index. Ví dụ DN:

~~~text
uid=an,ou=team-a,ou=people
~~~

khi `@Entry.base="ou=people"`:

| Index | Thành phần tính DN | Field minh họa |
| --- | --- | --- |
| `0` | `ou=team-a` | `teamOu` |
| `1` | `uid=an` | `uid` |

Phần tính DN thường được ghép theo thứ tự index rồi gắn `@Entry.base`. Dễ nhầm index với thứ tự đọc chuỗi DN từ trái qua phải; nên đối chiếu với ví dụ của thư viện và unit/integration test khi entity có nhiều thành phần RDN.

Với một RDN đơn giản dưới `ou=people`, chỉ cần `@DnAttribute(value="uid", index=0)`.
## 8. Để ODM tự tính DN từ `@DnAttribute(index=...)`

Nếu mỗi người nằm trực tiếp dưới `ou=people` và dùng RDN `uid=<giá trị>`, có thể để trường `@Id` ban đầu là `null` và cung cấp một field `@DnAttribute` có index:

~~~java
import javax.naming.Name;

import org.springframework.ldap.odm.annotations.Attribute;
import org.springframework.ldap.odm.annotations.DnAttribute;
import org.springframework.ldap.odm.annotations.Entry;
import org.springframework.ldap.odm.annotations.Id;

@Entry(
    base = "ou=people",
    objectClasses = {
        "top", "person", "organizationalPerson", "inetOrgPerson"
    }
)
public class GeneratedDnPerson {

    @Id
    private Name dn;

    @Attribute(name = "uid")
    @DnAttribute(value = "uid", index = 0)
    private String uid;

    @Attribute(name = "cn")
    private String commonName;

    @Attribute(name = "sn")
    private String surname;

    public GeneratedDnPerson() {}

    public Name getDn() { return dn; }
    public void setDn(Name dn) { this.dn = dn; }

    public String getUid() { return uid; }
    public void setUid(String uid) { this.uid = uid; }

    public String getCommonName() { return commonName; }
    public void setCommonName(String name) { this.commonName = name; }

    public String getSurname() { return surname; }
    public void setSurname(String name) { this.surname = name; }
}
~~~

Lời gọi tạo mới:

~~~java
GeneratedDnPerson person = new GeneratedDnPerson();
person.setUid("an");
person.setCommonName("Nguyen Van An");
person.setSurname("Nguyen");

// Chưa chỉ định DN tường minh.
assert person.getDn() == null;

ldapTemplate.create(person);

// Spring LDAP thử tính DN từ @DnAttribute(index=0)
// và @Entry(base="ou=people"), rồi điền vào @Id.
Name calculatedDn = person.getDn();
// Kỳ vọng tương đối ContextSource.base: uid=an,ou=people
~~~

Trong ví dụ, giả sử `ContextSource.base=dc=example,dc=org`:

~~~text
@DnAttribute(uid) = "an"
    ↓
index 0:  uid=an
    ↓
@Entry.base:  ou=people
    ↓
@Id dn:  uid=an,ou=people
    ↓
ContextSource.base: dc=example,dc=org
    ↓
DN trên server: uid=an,ou=people,dc=example,dc=org
~~~

**Lưu ý:** đây là cơ chế **tính DN theo giá trị đã được cung cấp**, không phải cơ chế sinh UID tự động. Nếu UID trống, không hợp schema hoặc DN đã tồn tại, server vẫn có thể từ chối thao tác. Với nghiệp vụ cần bảo đảm không trùng UID giữa nhiều OU, phải bổ sung chính sách uniqueness theo phạm vi thực tế, không coi annotation tự bảo đảm điều đó.

### `@DnAttribute` không mặc nhiên thay `@Attribute`

Spring LDAP ánh xạ các field entity vào attribute theo quy ước, trừ khi đánh dấu `@Transient`. Một field gắn `@DnAttribute` vẫn có thể được ánh xạ thành một LDAP attribute:

~~~java
@Attribute(name = "uid")
@DnAttribute(value = "uid", index = 0)
private String uid;
~~~

Ngược lại, một trường mô tả **nhánh đường dẫn**, chẳng hạn `ou` của parent, đôi khi chỉ nên lấy từ DN và **không được viết như attribute của chính entry**. Khi đó có thể kết hợp `@DnAttribute` với `@Transient`, nhưng phải chắc cấu trúc DN và schema mong đợi.

Ví dụ ý tưởng với DN chứa thêm một nhánh:

~~~text
uid=an,ou=team-a,ou=people,dc=example,dc=org
~~~

Một entity có thể dùng:

~~~java
@DnAttribute(value = "ou", index = 0)
@Transient
private String teamOu;

@DnAttribute(value = "uid", index = 1)
@Attribute(name = "uid")
private String uid;
~~~

Khi `@Entry.base=ou=people`, index 0 và 1 mô tả những thành phần tên phía trước base đó. **Không sử dụng index tùy đoán** nếu entry có RDN nhiều thành phần hoặc cấu trúc OU không đồng nhất; cần kiểm thử với nhiều DN thật trong môi trường lab.

## 9. Phân biệt rõ `@Id`, `uid` và `employeeNumber`

Xét ba entry:

~~~text
uid=an,ou=employees,dc=example,dc=org
uid=an,ou=contractors,dc=example,dc=org
uid=binh,ou=employees,dc=example,dc=org
~~~

Hai entry đầu có cùng `uid=an` nhưng **DN khác nhau**. Điều này có thể hợp lệ ở cấp directory nếu schema/server không áp uniqueness toàn tổ chức. Do đó:

| Thao tác | Điều được xác định |
| --- | --- |
| `findByDn("uid=an,ou=employees", PersonEntry.class)` | Một entry theo tên cụ thể |
| Search `(uid=an)` dưới `dc=example,dc=org` | Có thể trả nhiều entry thuộc nhiều OU |
| `employeeNumber=E104` | Chỉ là khóa nghiệp vụ nếu có quy tắc đảm bảo duy nhất |
| Đổi DN từ employees sang contractors | Cùng đối tượng có thể đổi vị trí trong DIT |
| Đổi `uid` trên entity | Không đồng nghĩa một lệnh rename hợp lệ trừ khi API và mapping xử lý đúng |

### Không dùng tên field `dn` làm khóa cho mọi hệ thống bên ngoài

Nếu ứng dụng A lưu `dn` vào bảng quan hệ làm foreign key, rồi LDAP rename/move người dùng, liên kết đó có thể không còn truy cập được. Nên phân biệt:

- **Tên định vị LDAP hiện tại:** DN, thích hợp để lookup hoặc sửa entry.
- **ID bất biến giữa các lần rename:** một thuộc tính có hợp đồng bất biến và đọc được theo ACL, ví dụ ID server cấp hoặc ID ứng dụng được bảo đảm.
- **Tên đăng nhập:** UID/email có thể thay đổi; không tự coi nó là khóa bất biến.

Với server có operational attribute như `entryUUID` hay `objectGUID`, phải hiểu kiểu dữ liệu, quyền đọc và semantics riêng. Không tự ép `byte[]` của GUID thành `String`; không tự giả định mọi LDAP server có cùng một operational attribute.

## 10. Cẩn trọng khi cập nhật field tham gia DN

Một entity ánh xạ field `uid` bằng `@DnAttribute(index=0)` có thể gây tác dụng phụ nếu service đổi UID:

~~~java
GeneratedDnPerson person = ldapTemplate.findByDn(
        PersonDns.relativeDn("an"), GeneratedDnPerson.class);

// Ý định nghiệp vụ: đổi username.
person.setUid("an2");

// Nguy cơ: không còn là một cập nhật thuộc tính thông thường.
ldapTemplate.update(person);
~~~

Theo hợp đồng các phiên bản Spring LDAP ODM hiện hành, `update(entity)` có thể so sánh DN ở `@Id` với DN được tính từ các `@DnAttribute`. Khi khác nhau, nó có thể thực hiện quy trình **di chuyển/thay đổi định danh entry**, thay vì chỉ sửa một thuộc tính. Tài liệu API mô tả một số nhánh như **unbind rồi bind**, nên không được coi đây là một lệnh Modify DN nguyên tử và không được mặc định nó bảo toàn mọi thuộc tính ngoài mapping.

| Thay đổi | Điều cần làm rõ |
| --- | --- |
| Đổi `mail` nhưng giữ DN | Thường là cập nhật thuộc tính |
| Đổi `uid` vốn nằm trong RDN | Có thể đòi rename/Modify DN và chính sách old RDN |
| Đổi OU của entry | Đó là move, thay đổi DN chứ không chỉ field |
| Chỉ thay `@Id dn` trong Java | Không tự chứng minh server đã rename |
| Đổi UID trong entity có `@DnAttribute(index=...)` | Có thể kích hoạt logic tính DN và di chuyển khi `update` |
| Xóa entity sau rename bằng DN cũ | Có thể không còn tìm được entry |

**Không tùy tiện dùng `ldapTemplate.update(person)` để đổi tên người dùng.** Một quy trình rename/move cần xác minh DN đích, schema của RDN, quyền sửa ở OU nguồn/đích, chính sách `deleteOldRDN`, nhóm chứa DN thành viên, cache và khả năng lỗi giữa các thao tác.

Nếu nghiệp vụ thực sự cần rename/move, cân nhắc API `LdapTemplate.rename(oldDn, newDn)` với chính sách provider/server thích hợp, hoặc cơ chế chuyên biệt đã được kiểm chứng; sau khi thành công, **đọc lại entity theo DN mới** để có trạng thái mới nhất. Đừng suy luận rằng `@Id` là khóa tự thay đổi tương tự Java bean ID.

### DN thay đổi có thể làm đứt tham chiếu nhóm

Ví dụ một nhóm lưu:

~~~ldif
dn: cn=developers,ou=groups,dc=example,dc=org
objectClass: top
objectClass: groupOfNames
cn: developers
member: uid=an,ou=people,dc=example,dc=org
~~~

Nếu An được rename thành `uid=an2,ou=people,...`, các giá trị `member` lưu **DN cũ** có thể trở nên lỗi thời trừ khi server có plugin/cơ chế referential integrity hoặc ứng dụng cập nhật chúng có kiểm soát. Việc field `@Id` mới được gán trong Java **không đảm bảo** cập nhật tham chiếu ngoài entity đó.

## 11. Không nên tự suy ra DN đầy đủ khi hiển thị hoặc log

Trong nhiều đường gọi Spring LDAP, `@Id` chứa một `Name` **tương đối với base của `ContextSource`**. Nó nên được dùng trong các API Spring LDAP cùng ngữ cảnh thay vì đưa qua nhiều dịch vụ dưới dạng chuỗi không có metadata.

Ví dụ:

~~~text
ContextSource A base = dc=example,dc=org
@Id dn              = uid=an,ou=people
DN hiệu lực         = uid=an,ou=people,dc=example,dc=org

ContextSource B base = ou=people,dc=example,dc=org
@Id dn nếu tương đối = uid=an
~~~

Một chuỗi `"uid=an,ou=people"` thiếu bối cảnh sẽ không cho biết đó là tên đầy đủ trong naming context nào. Khi cần trao đổi tên giữa các hệ thống, hãy quy định representation có chứa base rõ ràng hoặc dùng một ID bất biến và truy xuất DN qua LDAP.

**Không log password và không tự động phơi bày DN** trong API công khai. DN có thể chứa cấu trúc tổ chức, tên OU hoặc định danh người dùng nhạy cảm. Với lỗi nghiệp vụ, trả thông báo vừa đủ và ghi correlation ID để điều tra nội bộ.

### Đọc DN không phải đọc thuộc tính `distinguishedName` bất kỳ

Các LDAP server có thể cung cấp operational hoặc thuộc tính do vendor định nghĩa chứa DN, nhưng không đồng nhất chúng với `@Id`. Đặc biệt, `distinguishedName` trên một server cụ thể không phải phép thay thế di động cho trường `Name dn` của ODM. Khi viết mã đa nhà cung cấp, dùng contract ODM và API DN cho định danh entry.

## 12. Kiểm tra schema và quyền khi tạo entity theo `@Id`

Khi tạo mới, Spring LDAP ODM không làm mọi dữ liệu hợp lệ một cách tự động. Server vẫn cần:

- **Parent DN tồn tại:** ví dụ `ou=people,dc=example,dc=org`.
- **RDN hợp lệ:** attribute `uid` và giá trị không vi phạm cú pháp.
- **Object classes hợp lệ:** chuỗi `top` → `person` → `organizationalPerson` → `inetOrgPerson` theo schema được triển khai.
- **Thuộc tính MUST:** với `person`, `cn` và `sn` phải có giá trị hợp lệ.
- **RDN value hiện diện:** entry phải có giá trị naming attribute phù hợp.
- **Không trùng DN:** server không cho Add hai entry với cùng tên hiệu lực.
- **ACL:** tài khoản service bind phải được phép tạo entry ở OU đích.
- **Kết nối bảo vệ:** LDAPS hoặc StartTLS với hostname/CA được xác minh.
- **Chính sách tổ chức:** không cho request tạo tên tùy ý ngoài OU được cấp quyền.

| Lỗi thường gặp | Mã LDAP điển hình | Nguyên nhân |
| --- | --- | --- |
| DN đã tồn tại | `entryAlreadyExists (68)` | Tạo trùng tên |
| Parent OU không có | `noSuchObject (32)` | DN/base sai hoặc OU chưa tạo |
| Thiếu quyền | `insufficientAccessRights (50)` | ACL không cho bind/create/update |
| Vi phạm object class | `objectClassViolation (65)` | Thiếu MUST hay class sai |
| Giá trị attribute sai syntax | `invalidAttributeSyntax (21)` | Dữ liệu không hợp schema |
| DN không hợp lệ | `invalidDNSyntax (34)` | Tạo DN bằng chuỗi thô/sai escape |
| Bind credential sai | `invalidCredentials (49)` | Tài khoản dịch vụ không xác thực được |
| Timeout sau tạo/sửa | Kết quả chưa rõ | Server có thể đã ghi nhưng response mất |

Các mã là trường hợp điển hình, không phải mọi server đều chọn cùng lỗi nếu đồng thời có nhiều vi phạm. Nếu `create` báo timeout, **không retry mù**: phải xác minh DN đích và định danh chủ thể trước khi tạo lại, vì lần đầu có thể đã thành công.

## 13. Tìm đối tượng: DN chính xác khác filter theo thuộc tính

Có hai trường hợp nghiệp vụ rõ ràng:

**A — Đã biết DN:** tra cứu trực tiếp bằng `findByDn`.

~~~java
Name dn = PersonDns.relativeDn("an");
PersonEntry person = ldapTemplate.findByDn(dn, PersonEntry.class);
~~~

**B — Chỉ biết UID hoặc dữ liệu khác:** tìm bằng query, không tự đoán OU nếu có cấu trúc lồng nhau.

~~~java
import java.util.List;
import javax.naming.directory.SearchControls;
import org.springframework.ldap.query.LdapQuery;
import org.springframework.ldap.query.LdapQueryBuilder;

String uidFromUser = "an";

LdapQuery query = LdapQueryBuilder.query()
        .base("ou=people")
        .searchScope(SearchControls.SUBTREE_SCOPE)
        .where("uid").is(uidFromUser);

List<PersonEntry> people = ldapTemplate.find(query, PersonEntry.class);
~~~

Cách B có thể tìm các entry ở nhiều OU con vì đã khai báo `SUBTREE_SCOPE`. Nếu UID không được bảo đảm duy nhất trong scope, kết quả có thể có nhiều entity; **không lấy phần tử đầu tiên rồi coi đó là người dùng duy nhất**. Kiểm tra query có trả dữ liệu đầy đủ cho ODM mapping và được ACL cho phép.

### Tránh LDAP filter injection

Trong query trên, `.where("uid").is(uidFromUser)` sử dụng builder để escape giá trị filter. Không làm:

~~~java
// SAI: input người dùng có thể thay đổi ý nghĩa của LDAP filter.
String filter = "(uid=" + uidFromUser + ")";
~~~

Escaping của filter (RFC 4515) **khác** escaping của DN (RFC 4514). Việc xây chuỗi DN đúng cú pháp không chứng minh caller có quyền đọc/sửa entry đó; LDAP ACL và chính sách tầng service vẫn phải được kiểm tra.
## 14. ODM không phải một database ORM có transaction thông thường

Một số thói quen từ JPA dễ gây sai khi chuyển sang LDAP:

| Giả định từ ORM | Thực tế khi dùng Spring LDAP ODM |
| --- | --- |
| Để `@Id=null` thì DB tự sinh ID | Chỉ có thể tính DN nếu mapping `@DnAttribute`/base phù hợp |
| Thay đổi entity trong RAM sẽ tự flush | Phải gọi API `create`, `update`, `delete` hoặc thao tác tương ứng |
| `@Id` là khóa bất biến | DN có thể đổi do rename/move |
| Có transaction rollback xuyên nhiều entity | LDAP không tự cung cấp transaction ORM đa entry kiểu JPA |
| Cập nhật UID chỉ sửa một cột | Nếu UID thuộc RDN, có thể là rename entry |
| Field Java luôn bằng một cột đơn trị | LDAP attributes có thể đa trị hoặc kiểu nhị phân |
| Có `@Id` là search tất cả phải duy nhất theo UID | DN uniqueness khác UID uniqueness |
| Query theo thuộc tính luôn biết full DN | Cần giữ context/base và đọc DN từ mapping |

Điều này không làm ODM kém hữu ích. ODM giúp giảm code đọc `Attributes`, chuyển dữ liệu sang POJO và tạo API nhất quán. Nhưng phải giữ đúng mô hình **cây, DN, schema, ACL và thao tác LDAP** khi thiết kế domain.

### Dùng entity với những thay đổi có kiểm soát

Một mô hình hợp lý là chỉ cho phép service sửa những field được chính sách nghiệp vụ sở hữu, chẳng hạn `mail`. Không đưa toàn bộ HTTP request vào entity rồi gọi `ldapTemplate.update(entity)` nếu request có thể chứa `dn`, `uid` hoặc các thuộc tính nhóm.

Nếu client được quyền thay email, trước hết tìm đúng entry theo một DN đã được xác minh, kiểm tra email mới, chỉ sửa field được phép, rồi gọi API cập nhật. Đối với thay đổi liên quan mật khẩu hoặc quyền nhóm, nên dùng đường nghiệp vụ chuyên biệt, không để generic update ghi mọi attribute.

## 15. Unit test: DN builder và metadata entity

Unit test không cần LDAP server có thể kiểm tra tên DN được xây từ UID:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import javax.naming.Name;
import javax.naming.ldap.LdapName;
import org.junit.jupiter.api.Test;
import org.springframework.ldap.odm.annotations.Id;

class PersonDnTest {

    @Test
    void buildsRelativeDn() {
        Name dn = PersonDns.relativeDn("an");

        assertEquals("uid=an,ou=people", dn.toString());
    }

    @Test
    void specialCharacterRemainsOneRdnValue() throws Exception {
        Name dn = PersonDns.relativeDn("an,dev");
        LdapName parsed = new LdapName(dn.toString());

        // RDN cuối theo chỉ số JNDI là RDN ngoài cùng bên trái của DN.
        assertEquals("an,dev",
                parsed.getRdn(parsed.size() - 1).getValue());
    }

    @Test
    void odmIdIsAnnotatedNameField() throws Exception {
        var field = PersonEntry.class.getDeclaredField("dn");

        assertTrue(field.isAnnotationPresent(Id.class));
        assertEquals(Name.class, field.getType());
    }
}
~~~

Unit test trên xác minh cú pháp DN và metadata cơ bản; **không chứng minh ODM mapping đã đọc hoặc ghi được LDAP server**. Với các tình huống Unicode, RDN phức hợp, multi-valued attribute và DN thực tế của directory, cần bổ sung integration test.

### Test service chuẩn bị entity với `@Id` đúng

Sử dụng JUnit 5 và Mockito:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.*;

import org.junit.jupiter.api.Test;
import org.mockito.ArgumentCaptor;
import org.springframework.ldap.core.LdapTemplate;

class PersonOdmServiceTest {

    @Test
    void createPersonSuppliesRelativeDnAndAttributes() {
        LdapTemplate ldapTemplate = mock(LdapTemplate.class);
        PersonOdmService service = new PersonOdmService(ldapTemplate);

        service.createPerson("an", "Nguyen Van An", "Nguyen");

        ArgumentCaptor<PersonEntry> captor =
                ArgumentCaptor.forClass(PersonEntry.class);

        verify(ldapTemplate).create(captor.capture());
        verifyNoMoreInteractions(ldapTemplate);

        PersonEntry entry = captor.getValue();
        assertEquals("uid=an,ou=people", entry.getDn().toString());
        assertEquals("an", entry.getUid());
        assertEquals("Nguyen Van An", entry.getCommonName());
        assertEquals("Nguyen", entry.getSurname());
    }
}
~~~

Test này chỉ kiểm tra **service truyền đúng entity** vào `LdapTemplate.create`. Mockito không thực thi ObjectDirectoryMapper thật, nên nó không thể phát hiện toàn bộ lỗi mapping object class hoặc `@DnAttribute`. Để khẳng định DN tự được tính và field `@Id` được điền đúng, cần test với LDAP server hoặc công cụ mapping thực sự của phiên bản dự án.

## 16. Integration test: lưu và đọc lại `@Id` trên LDAP lab

Chuẩn bị server/OU riêng, chẳng hạn:

OU                  = ou=people
DN của entry test    = uid=lab-003,ou=people,dc=lab,dc=example,dc=org

Tài khoản test có quyền **create/read/delete** chỉ trong OU lab. Kết nối qua LDAPS hoặc StartTLS đã xác minh chứng chỉ, không sử dụng dữ liệu người dùng thật. Nếu dùng embedded server cho unit/integration test, vẫn cần chạy bổ sung trên loại LDAP server sẽ dùng khi vận hành vì schema, quyền và cách xử lý DN có thể khác nhau.

### Kịch bản C — sai base hoặc DN bị lặp suffix

2. Dựng DN đúng là `uid=lab-003,ou=people`.
3. So với một DN được nối cả suffix nhiều lần.
4. Xác minh code ứng dụng từ chối hoặc test phát hiện tên hiệu lực sai; không tự thử tạo entry ngoài OU lab.

### Kịch bản D — rename/move

1. Tạo entry với UID `lab-rename-old` và một ID nghiệp vụ riêng để đối chiếu.
2. Rename bằng cơ chế được phê duyệt, ví dụ `ldapTemplate.rename(oldDn, newDn)`.
3. Đọc theo DN mới, xác nhận đúng **cùng chủ thể** và trường `@Id` phản ánh DN mới.
4. Kiểm tra lookup theo DN cũ không tự thành công dù old RDN value có thể còn là một attribute theo chính sách `deleteOldRDN`.
5. Kiểm tra các DN tham chiếu trong nhóm nếu môi trường lab có thành viên nhóm.
6. Dọn dữ liệu test bằng DN hiện hành, không dùng DN cũ có thể đã không tồn tại.

### Kịch bản E — bảo mật và lỗi

| Kịch bản | Điều cần chứng minh |
| --- | --- |
| Tạo cùng DN hai lần | Lần sau bị từ chối, không tự ghi đè |
| Parent OU không tồn tại | Nhận lỗi có thể phân biệt với create conflict |
| Thiếu `cn` hoặc `sn` | Server áp schema và từ chối entry không hợp lệ |
| Service bind chỉ đọc | Create/update/delete không được phép |
| UID chứa dấu phẩy hoặc ký tự cần escape | DN builder không tạo thêm RDN ngoài ý định |
| Search UID không duy nhất ở nhiều OU | Không coi một UID là một DN duy nhất |
| `@Id` null nhưng thiếu index `@DnAttribute` | Không giả định ODM tính được DN |
| Root DN/source base khác nhau | Không copy `@Id` giữa context sources mà không đổi base |
| Timeout sau create | Không retry mù và làm rõ kết quả chưa xác định |
| Đổi UID đã nằm trong RDN | Phát hiện tác động rename/move, schema và tham chiếu |

### Khung xác nhận DN trong integration test

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;

import javax.naming.Name;
import org.springframework.ldap.core.LdapTemplate;
import org.springframework.ldap.support.LdapNameBuilder;

public class PersonOdmIntegrationVerifier {

    private final LdapTemplate ldapTemplate;

    public PersonOdmIntegrationVerifier(LdapTemplate ldapTemplate) {
        this.ldapTemplate = ldapTemplate;
    }

    public void verifyCreatedPerson(String uid) {
        Name expected = LdapNameBuilder.newInstance("ou=people")
                .add("uid", uid)
                .build();

        PersonEntry loaded =
                ldapTemplate.findByDn(expected, PersonEntry.class);

        assertEquals(expected, loaded.getDn());
        assertEquals(uid, loaded.getUid());
    }
}
~~~

Đây là **helper** dùng trong integration test, không tự tạo server/entry hoặc chạy cleanup. Cần đặt nó vào test có fixture được kiểm soát và xác nhận dependency Spring LDAP/JUnit tương thích. Với nhiều provider, nên kiểm tra cùng một cấu trúc tên trước khi so sánh `Name.equals(...)`; phép so sánh Name của Java không thay thế mọi matching rule DN ở server.

## 17. Bài thực hành: hiểu đúng `@Id` và DN

Giả sử:

~~~text
ContextSource.base = dc=example,dc=org
@Entry.base        = ou=people
Entity mới có UID  = an
~~~

**Câu hỏi**

1. Trường `@Id` của Spring LDAP ODM dùng kiểu Java gì?
2. `@Id` có phải `org.springframework.data.annotation.Id` không?
3. DN hiệu lực trên server của `uid=an,ou=people` là gì?
4. Với entity gán DN tường minh, phải làm gì trước khi gọi `create(...)`?
5. Muốn ODM tự tính DN khi `@Id=null`, cần annotation nào và thuộc tính gì của nó?
6. Field `@DnAttribute` có tự động ngừng mapping thành LDAP attribute không?
7. Nếu hai người cùng có `uid=an` nhưng ở hai OU khác nhau, có nhất thiết trùng DN không?
8. Sau move từ `ou=people` sang `ou=contractors`, có nên coi DN là khóa bất biến của người đó không?
9. Nếu đổi `uid` trên entity có `@DnAttribute(index=0)` rồi gọi `update(...)`, rủi ro là gì?
10. Tại sao test Mockito chỉ `verify(ldapTemplate).create(person)` chưa đủ xác nhận `@Id` mapping đúng?
11. Nếu search theo UID do người dùng nhập, nên dùng DN builder hay LDAP filter builder?
12. Nếu server báo `entryAlreadyExists (68)` khi tạo entity, có nên tự động đổi sang `update(...)` không?

### Đáp án có giải thích

| Câu | Đáp án |
| --- | --- |
| 1 | `javax.naming.Name` hoặc lớp con thích hợp như `LdapName` |
| 2 | Không. Dùng `org.springframework.ldap.odm.annotations.Id` |
| 3 | `uid=an,ou=people,dc=example,dc=org` |
| 4 | Gán DN vào field `@Id`, ví dụ với `LdapNameBuilder` |
| 5 | `@DnAttribute(value="uid", index=0)` và `@Entry(base="ou=people")` cho cấu trúc một RDN |
| 6 | Không. Field `@DnAttribute` vẫn được mapping theo quy ước trừ khi có `@Transient` |
| 7 | Không. DN gồm RDN và toàn bộ parent path; hai OU có thể tạo hai DN khác nhau |
| 8 | Không. DN thay đổi khi rename/move; cần ID ổn định riêng nếu nghiệp vụ yêu cầu |
| 9 | ODM có thể tính DN mới và thực hiện di chuyển/thay thế; không an toàn để coi là sửa attribute đơn giản |
| 10 | Mock không thực thi ODM mapper, schema, ACL hoặc server |
| 11 | Dùng filter builder/`LdapQueryBuilder` cho assertion value trong search; DN builder cho tên entry |
| 12 | Không. Tạo và cập nhật là hai hợp đồng khác nhau, cần xử lý conflict có chủ đích |

### Bài tập code: tìm hai lỗi trong entity

~~~java
@Entry(
    base = "ou=people",
    objectClasses = {"top", "person", "inetOrgPerson"}
)
public class WrongPerson {
    @org.springframework.data.annotation.Id
    private String uid;

    @Attribute(name = "cn")
    private String fullName;
}
~~~

**Gợi ý trả lời:** (1) annotation `@Id` sai package và kiểu field không phải `Name`; (2) thiếu danh sách class đầy đủ phù hợp khi tạo entry `inetOrgPerson` (ví dụ `organizationalPerson`) và thiếu thuộc tính `sn` bắt buộc của `person`. Ngoài ra, entity cần cơ chế xác định DN hợp lệ và các field theo schema.

## 18. Checklist triển khai ODM với DN

- [ ] Dùng chính xác `org.springframework.ldap.odm.annotations.Id` trên một field kiểu `Name`/`LdapName`.
- [ ] Khai báo `@Entry` với object classes phù hợp schema; hiểu `base` dùng để tính DN.
- [ ] Xác định chọn **DN tường minh** hay **DN tự tính từ `@DnAttribute(index)`**; không trộn tùy tiện.
- [ ] Với DN tường minh, dựng tên bằng `LdapNameBuilder`; hiểu nó tương đối với `ContextSource.base`.
- [ ] Với DN tự tính, khai báo index đầy đủ, đúng thứ tự; test với cấu trúc OU/RDN thực tế.
- [ ] Không nhầm `@Id dn` với `uid`, `mail`, employee ID hoặc `@Id` của JPA/Spring Data.
- [ ] Không coi DN là ID bất biến xuyên rename/move; thiết kế ID khác cho liên kết dài hạn nếu cần.
- [ ] Không đổi `uid`/OU nằm trong DN rồi gọi `update` nếu chưa xác minh semantics move của ODM.
- [ ] Kiểm tra schema MUST/MAY, kiểu dữ liệu, RDN value, ACL và parent OU trước khi tạo.
- [ ] Filter từ input dùng query builder để escape; không ghép DN hoặc filter bằng chuỗi thô.
- [ ] Tài khoản service bind chỉ có quyền cần thiết; dùng LDAPS/StartTLS với chứng chỉ hợp lệ.
- [ ] Không phơi bày DN hoặc thuộc tính nội bộ ngoài phạm vi cho phép.
- [ ] Unit test DN builder và metadata; integration test `create/findByDn/update`, DN auto và lỗi.
- [ ] Dọn dữ liệu kiểm thử trong OU lab, không tạo/xóa entry trên production.

## 19. Điểm cần ghi nhớ

- **`@Id` của Spring LDAP ODM biểu diễn DN của entry**, bằng kiểu Java **`javax.naming.Name`**; không phải một khóa số, UID hoặc JPA ID.
- **`@Entry.base`, `@DnAttribute(index)` và `ContextSource.base` là ba lớp thông tin riêng** để tính DN khi ODM được cấu hình tương ứng.
- **`@Id` là tên hiện tại, không tự bất biến.** Rename/move có thể thay DN, dù entry vẫn biểu diễn cùng một chủ thể nghiệp vụ.
- **DN tường minh** cần được gán trước `ldapTemplate.create(entity)`. **DN tự tính** cần `@DnAttribute(index=...)` đúng và giá trị RDN hợp lệ.
- **`findByDn` tra cứu theo tên**, còn `find(query, clazz)` tìm theo thuộc tính; một UID không mặc nhiên duy nhất giữa các OU.
- **Không xem ODM như JPA transaction**: LDAP schema, ACL, connection, rename, bind/update và xử lý xung đột vẫn phải được thiết kế riêng.
- **Kiểm thử cả mapping và server thật** trên directory lab, với đường truyền TLS, quyền tối thiểu và dữ liệu giả, trước khi triển khai sản xuất.
