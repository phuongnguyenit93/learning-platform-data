# Tài nguyên, reflection và thành phần JLine cần đối chiếu khi đóng gói native

Khi biên dịch ứng dụng Spring Shell thành executable bằng GraalVM Native Image, mã Java được phân tích tĩnh ở thời điểm build. Những lớp, phương thức và tài nguyên chỉ được truy cập động lúc chạy có thể không được đưa vào binary nếu thiếu reachability metadata phù hợp.

Với ứng dụng Spring Shell, cần kiểm tra ba nhóm:

- **Tài nguyên:** service descriptor, dữ liệu terminfo, resource bundle, template và file cấu hình được đọc từ classpath.
- **Reflection:** class, constructor, method hoặc field được tìm và gọi bằng tên ở runtime.
- **JLine và terminal provider:** các module đọc input, điều khiển terminal, tải thư viện native và cung cấp khả năng tương tác.

Spring AOT và Spring Shell đã cung cấp một phần hint cho Native Image. Công việc đóng gói là xác định phần nào đã được framework và thư viện đăng ký, phần nào còn thiếu trong đúng phiên bản dependency của ứng dụng, rồi kiểm chứng executable trên môi trường đích.

Bài học dùng Spring Shell 3.3.4 làm mốc tham chiếu. Phiên bản này dựa trên Spring Boot 3.3.6, Spring Framework 6.1.15, yêu cầu JDK 17 và dùng JLine 3.26.3 trong `spring-shell-core`. Nếu ứng dụng dùng bản 3.x khác, hãy kiểm tra lại dependency graph và tài liệu của chính phiên bản đó.

## 1. Vì sao native image cần metadata?

Trên JVM thông thường, class loader có thể tải lớp và tài nguyên khi chương trình chạy. Reflection cũng có thể tìm constructor, method hoặc field dựa trên tên nhận được từ cấu hình. Native Image phân tích từ điểm vào của chương trình ở thời điểm build và chỉ giữ những thành phần mà nó xác định là có thể được sử dụng.

Điều này tạo ra mô hình *closed world*: classpath và tập thành phần có thể truy cập được xác định khi build. Nếu code gọi `Class.forName()` với tên lớp lấy từ file cấu hình, hoặc tải một resource bằng tên được ghép lúc chạy, bộ phân tích có thể không suy ra được thành phần cần giữ.

~~~text
Source code + dependencies
          |
          v
Spring AOT
  - Phân tích bean và cấu hình
  - Sinh source/proxy cần thiết
  - Sinh RuntimeHints
          |
          v
GraalVM Native Image
  - Static reachability analysis
  - Đọc reflection/resource metadata
  - Liên kết native libraries
          |
          v
Platform-specific executable
          |
          v
Runtime
  - Tải resource đã được đóng gói
  - Dùng reflection đã được đăng ký
  - Khởi tạo terminal provider phù hợp
~~~

Khi metadata bị thiếu, ứng dụng có thể vẫn chạy tốt trên JVM nhưng thất bại trong native executable. Các lỗi thường gặp là không tìm thấy resource, `ClassNotFoundException`, lỗi đăng ký reflection, không tìm được provider hoặc không tải được thư viện native.

Không phải mọi ứng dụng Spring Shell đều cần tự viết hint. Spring Framework, Spring Boot và Spring Shell đã đăng ký nhiều trường hợp phổ biến. Chỉ bổ sung metadata sau khi đã kiểm tra hint có sẵn và xác định được truy cập động còn thiếu.

## 2. Spring AOT và hint do Spring Shell cung cấp

Spring Shell 3.3.4 có hướng dẫn native support riêng. Framework sử dụng AOT của Spring Framework và Spring Boot để chuẩn bị application context ở build time. Spring Shell bổ sung GraalVM configuration để khai báo các thành phần cần có trong binary.

Spring Boot AOT có thể sinh:

| Thành phần | Vai trò |
|---|---|
| Java source | Mã khởi tạo bean và cấu hình đã được phân tích ở build time |
| Generated bytecode | Proxy hoặc lớp hỗ trợ được tạo trước |
| Resource hints | Tài nguyên cần được đưa vào executable |
| Reflection hints | Kiểu, constructor, method hoặc field được truy cập động |
| Serialization hints | Kiểu được tuần tự hóa/giải tuần tự hóa |
| Proxy hints | Interface cần tạo dynamic proxy |
| JNI hints | Thành phần Java được native code truy cập |

Các file JSON do AOT sinh được đặt dưới `META-INF/native-image`. Với Gradle, Spring Boot 3.3 ghi nhận output AOT ở `build/generated/aotResources`; với Maven, output thường ở `target/spring-aot/main/resources`. Hãy xem output thực tế của build để biết hint nào đã được sinh.

Spring Shell 3.3.4 cũng khuyến nghị bật GraalVM Reachability Metadata Repository để nhận metadata của thư viện bên thứ ba. Đây là nguồn bổ sung cho những dependency chưa đóng gói đủ hint. Repository không thay thế kiểm thử native của ứng dụng.

## 3. Xác định đúng phiên bản JLine đang được đóng gói

Đừng suy luận thành phần JLine chỉ từ dependency khai báo trực tiếp. Spring Shell kéo theo một nhóm module JLine và có thể thêm terminal provider qua starter hoặc dependency khác.

Với `spring-shell-core` 3.3.4, POM công bố các dependency JLine 3.26.3:

| Artifact | Vai trò |
|---|---|
| `jline-console` | Thành phần console và tích hợp |
| `jline-reader` | Đọc dòng lệnh, chỉnh sửa input và completion |
| `jline-style` | Định dạng, style và nội dung có thuộc tính |
| `jline-terminal` | Abstraction của terminal và screen/output |

Các provider có thể được bổ sung theo cấu hình ứng dụng:

| Provider | Artifact JLine thường gặp | Thành phần liên quan |
|---|---|---|
| Jansi | `jline-terminal-jansi` | Jansi và xử lý ANSI/native theo nền tảng |
| JNA | `jline-terminal-jna` | JNA và truy cập API hệ điều hành |
| JNI | `jline-terminal-jni`, `jline-native` | Thư viện native của JLine |
| FFM | `jline-terminal-ffm` | Foreign Function and Memory API trên JDK 22+ |

Đối với Spring Shell 3.3.x, hãy kiểm tra provider thực tế trong dependency graph. Hỗ trợ provider FFM của Spring Shell bắt đầu từ nhánh 3.4.x và cần JDK 22 trở lên; không thêm cấu hình FFM của 3.4.x vào ứng dụng 3.3.x chạy JDK 17.

Một số phiên bản Spring Shell có starter riêng cho Jansi, JNA hoặc JNI. Starter quyết định provider dependency nào được thêm vào classpath. Nếu ứng dụng không cần terminal provider cụ thể, không thêm tất cả provider theo thói quen.

Ví dụ dùng Gradle để xem dependency runtime:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
~~~

Hoặc lọc các module JLine trong dependency insight:

~~~bash
./gradlew dependencyInsight --dependency jline --configuration runtimeClasspath
~~~

Với Maven:

~~~bash
./mvnw dependency:tree -Dincludes=org.jline
~~~

Ghi lại phiên bản của từng artifact và provider thực sự được chọn. Nếu nhiều phiên bản JLine cùng xuất hiện hoặc provider kéo một phiên bản khác với BOM, xử lý xung đột dependency trước khi điều tra hint.

## 4. Kiểm tra tài nguyên trong classpath

Tài nguyên là file không phải class mà code đọc ở runtime. Với Spring Shell và JLine, các nhóm nên rà soát gồm:

- Service descriptor dùng để phát hiện terminal provider hoặc extension.
- Cơ sở dữ liệu terminfo/capability và dữ liệu terminal mà JLine đọc theo tên.
- Resource bundle dùng cho thông báo hoặc bản địa hóa.
- Template, banner, script mẫu và file cấu hình của ứng dụng.
- File nằm trong `META-INF/native-image` của các dependency, gồm native-image properties và JSON metadata.
- Thư viện native hoặc dữ liệu nền tảng được đóng gói trong JLine provider artifact.

Không phải resource nào cũng cần một hint riêng. GraalVM có thể tự nhận ra một số lời gọi `Class.getResourceAsStream()` khi class và tên resource là hằng số. Truy cập bằng tên được tạo động hoặc qua một thư viện dùng class loader có thể cần metadata.

### 4.1. Service descriptor và provider discovery

JLine có thể tìm terminal provider thông qua cơ chế service loading. Khi đóng gói native, kiểm tra:

1. Provider cần dùng có nằm trong `runtimeClasspath` không?
2. Artifact có chứa service descriptor tương ứng không?
3. Descriptor có còn sau khi đóng gói fat JAR không?
4. Native Image hoặc metadata của artifact đã giữ provider class cần thiết chưa?
5. Provider có thể tải thư viện native tương ứng trên hệ điều hành đích không?

Service descriptor có thể nằm trong `META-INF/services`. Nếu build tool hoặc quá trình tạo fat JAR hợp nhất resource, kiểm tra descriptor không bị ghi đè bởi một dependency khác.

Đừng tự thêm toàn bộ class của mọi provider vào reflection config. Trước hết hãy xác nhận provider discovery là đường đi thực tế và kiểm tra metadata được cung cấp trong đúng JAR.

### 4.2. Resource được tải bằng tên động

Ví dụ ứng dụng tự chọn template theo tên định dạng:

~~~java
public String loadTemplate(String format) throws IOException {
    String resourceName = "templates/report-" + format + ".st";

    try (InputStream input = getClass().getClassLoader()
            .getResourceAsStream(resourceName)) {
        if (input == null) {
            throw new IllegalArgumentException(
                    "Không tìm thấy template: " + resourceName);
        }
        return new String(input.readAllBytes(), StandardCharsets.UTF_8);
    }
}
~~~

Tên resource được ghép lúc runtime, nên AOT có thể không nhận ra tất cả file cần giữ. Có thể đăng ký một pattern hẹp cho thư mục template của ứng dụng.

### 4.3. Đăng ký resource bằng RuntimeHints

Spring Framework cung cấp `RuntimeHintsRegistrar` để khai báo tài nguyên và reflection cần thiết:

~~~java
import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportRuntimeHints;

class ReportRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("templates/report-*.st");
    }
}

@Configuration(proxyBeanMethods = false)
@ImportRuntimeHints(ReportRuntimeHints.class)
class NativeHintsConfiguration {
}
~~~

Pattern trong ví dụ chỉ dành cho template của ứng dụng. Khi đăng ký resource cho thư viện, dùng đúng đường dẫn đã xác minh trong artifact và chỉ thêm pattern cần thiết. Không đăng ký toàn bộ classpath vì binary có thể phình to và chứa nhiều dữ liệu không cần dùng.

Nếu dùng `ResourceBundle`, có thể đăng ký bundle cụ thể qua `hints.resources().registerResourceBundle("com.example.messages")`. Hãy đăng ký base name của bundle và kiểm tra các locale mà ứng dụng thực sự hỗ trợ.

## 5. Kiểm tra reflection và dynamic proxy

Reflection xuất hiện khi ứng dụng tìm lớp hoặc thành phần bằng tên, đọc annotation hoặc gọi constructor/method không được tham chiếu trực tiếp trong mã. Native Image cần biết chính xác phần tử nào phải được giữ.

Trong ứng dụng Spring Shell, các điểm nên kiểm tra:

- Command hoặc plugin do ứng dụng tự nạp bằng `Class.forName()`.
- Converter, formatter hoặc handler được chọn từ cấu hình.
- Extension được tạo bằng tên lớp trong file cấu hình.
- Constructor hoặc method được gọi bằng reflection.
- Field được truy cập động bởi serializer hoặc framework bên thứ ba.
- Proxy interface hoặc kiểu được tạo động.

Spring AOT đã xử lý nhiều trường hợp bean và annotation. Không thêm reflection hint cho toàn bộ command chỉ vì ứng dụng dùng `@ShellComponent`/`@ShellMethod`. Trước tiên kiểm tra generated hints và log build.

### 5.1. Đăng ký kiểu được tạo bằng reflection

Giả sử ứng dụng cho phép cấu hình formatter theo tên lớp:

~~~java
String formatterClass = properties.getFormatterClass();
Class<?> type = Class.forName(formatterClass);
Object formatter = type.getDeclaredConstructor().newInstance();
~~~

Native Image không thể suy ra mọi tên lớp có thể xuất hiện trong file cấu hình. Nếu tập formatter được biết trước, nên thay việc nạp lớp tùy ý bằng registry tĩnh hoặc đăng ký đúng các kiểu cần thiết.

Ví dụ đăng ký một formatter cụ thể:

~~~java
import org.springframework.aot.hint.MemberCategory;

hints.reflection().registerType(
        CsvReportFormatter.class,
        MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
        MemberCategory.INVOKE_PUBLIC_METHODS);
~~~

Đăng ký đúng member category cần thiết. Nếu code cần gọi private method hoặc đọc field qua reflection, chỉ thêm quyền tương ứng sau khi xác định đường truy cập đó thực sự tồn tại.

### 5.2. Ví dụ RuntimeHints cho reflection

Có thể mở rộng registrar ở phần resource:

~~~java
class ReportRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("templates/report-*.st");

        hints.reflection().registerType(
                CsvReportFormatter.class,
                MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                MemberCategory.INVOKE_PUBLIC_METHODS);
    }
}
~~~

Nếu lớp được gọi trực tiếp bằng `new CsvReportFormatter()` và method được gọi trực tiếp bằng mã Java, static analysis thường đã thấy các lời gọi đó; hint reflection có thể không cần. Ví dụ trên dành cho trường hợp thật sự có dynamic lookup.

### 5.3. Dynamic proxy và serialization

Reflection không phải loại metadata duy nhất. Nếu ứng dụng hoặc dependency tạo JDK dynamic proxy, serialize/deserialize kiểu theo tên hoặc gọi native code qua JNI, cần kiểm tra proxy, serialization và JNI hints tương ứng.

Đừng xử lý mọi lỗi native bằng cách mở rộng reflection. Hãy xác định lỗi thuộc nhóm resource, reflection, proxy, serialization hay JNI rồi bổ sung metadata đúng loại.

## 6. JLine: những thành phần cần đối chiếu

JLine có nhiều module. Chỉ một phần được sử dụng trong từng ứng dụng, tùy việc command có tương tác terminal, đọc input, dùng completion, style hoặc terminal provider.

| Thành phần | Nội dung cần kiểm tra khi build native |
|---|---|
| `jline-reader` | Reader, parser, completion và các extension được tải động |
| `jline-console` | Console integration và service/provider discovery |
| `jline-style` | Style, resource hoặc cấu hình được tải theo tên |
| `jline-terminal` | Terminal abstraction, terminfo/capability và service descriptor |
| `jline-terminal-jansi` | Jansi classes, resource và native access cần cho provider |
| `jline-terminal-jna` | JNA reflection, platform classes và native library loading |
| `jline-terminal-jni` | JLine native classes, JNI metadata và thư viện native theo nền tảng |
| `jline-native` | Native library resources và cấu hình khởi tạo lớp liên quan |

JAR của thư viện có thể tự đóng gói file dưới `META-INF/native-image`. GraalVM đọc các cấu hình này khi chúng có mặt trên classpath. Kiểm tra các file `native-image.properties`, `resource-config.json`, `reflect-config.json`, `jni-config.json` hoặc `reachability-metadata.json` trong đúng artifact thay vì sao chép thủ công một cấu hình từ phiên bản JLine khác.

Ví dụ, một artifact provider có thể đóng gói resource config và reflection config riêng. Nếu artifact đã cung cấp hint, không tạo một bản trùng trong ứng dụng trừ khi có một đường truy cập riêng còn thiếu.

## 7. Phân biệt Native Image và native terminal provider

Hai khái niệm có chữ “native” nhưng giải quyết hai vấn đề khác nhau:

| Khái niệm | Ý nghĩa |
|---|---|
| GraalVM Native Image | Biên dịch ứng dụng Java thành executable độc lập với JVM |
| JLine terminal provider | Cách JLine tương tác với terminal và API hệ điều hành |
| JNI/JNA/Jansi library | Thành phần hỗ trợ truy cập native của provider tương ứng |

Một ứng dụng có thể được biên dịch thành native executable nhưng vẫn không mở được terminal nếu provider không được đóng gói hoặc native library không phù hợp hệ điều hành. Ngược lại, một ứng dụng chạy trên JVM có thể dùng JLine native provider mà không cần GraalVM.

Vì vậy, kiểm thử thành công lệnh `nativeCompile` chưa chứng minh tương tác terminal đã hoạt động. Cần chạy binary và kiểm tra provider thực sự khởi tạo được.

## 8. Chọn và kiểm tra terminal provider

Trong Spring Shell 3.3.x, các lựa chọn provider thường gặp là Jansi, JNA và JNI. Chúng có thể cung cấp khả năng tương tác terminal tương tự nhưng khác cách truy cập hệ điều hành và tải thư viện.

Khi chọn provider:

- Chỉ đưa provider cần dùng vào runtime dependency.
- Kiểm tra provider đó có metadata cho phiên bản GraalVM và JLine đang dùng không.
- Xác nhận native library có sẵn cho OS/architecture mục tiêu.
- Kiểm tra quyền tải thư viện và các dependency hệ thống.
- Chạy test trong terminal thật hoặc pseudo-terminal.
- Kiểm tra chế độ không có TTY, nơi ứng dụng có thể cần fallback phù hợp.

Danh sách thư viện được GraalVM công bố là đã kiểm thử có mức hỗ trợ và ngưỡng phiên bản khác nhau. Ví dụ danh sách hiện tại ghi nhận `jline`, `jline-console`, `jline-reader` và `jline-terminal` từ các phiên bản 3.x thấp hơn; trong khi `jline-native` và `jline-terminal-jni` có ngưỡng được liệt kê từ 3.27.1. Spring Shell 3.3.4 dùng JLine 3.26.3, vì vậy không nên mặc định metadata repository đã bao phủ đầy đủ provider JNI của phiên bản đó.

Đây là thông tin tương thích để đối chiếu, không phải khẳng định JNI 3.26.3 chắc chắn thất bại. Hãy kiểm tra metadata đi kèm JAR thực tế, dependency graph, log build và smoke test của ứng dụng. Nếu cần dùng JNI, có thể cân nhắc nâng cấp lên phiên bản Spring Shell/JLine được hỗ trợ tương thích, hoặc bổ sung hint còn thiếu sau khi xác định cụ thể.

## 9. Đọc metadata đi kèm JLine JAR

Có thể kiểm tra nội dung JAR bằng `jar tf`:

~~~bash
jar tf ~/.m2/repository/org/jline/jline-terminal/3.26.3/jline-terminal-3.26.3.jar
~~~

Tìm các đường dẫn liên quan:

~~~text
META-INF/services/
META-INF/native-image/
org/jline/
~~~

Nếu dùng Gradle cache hoặc một thư mục Maven khác, thay đường dẫn bằng vị trí artifact thực tế. Kiểm tra cả provider artifact đã được chọn, ví dụ `jline-terminal-jansi` hoặc `jline-terminal-jni`.

Các câu hỏi khi rà soát:

1. Có service descriptor cho provider cần dùng không?
2. Provider có resource config hoặc reflection config riêng không?
3. Có `native-image.properties` chỉ định runtime initialization hoặc native build arguments không?
4. Resource cấu hình và dữ liệu terminal có được đưa vào executable không?
5. Có thư viện `.so`, `.dll` hoặc `.dylib` theo nền tảng không?
6. Phiên bản GraalVM có hiểu metadata schema và build argument trong JAR đó không?

Không sửa trực tiếp nội dung JAR trong cache dependency. Nếu cần thêm hint, quản lý chúng trong source của ứng dụng hoặc nâng cấp dependency đã sửa metadata.

## 10. Bật Reachability Metadata Repository

Spring Shell 3.3.4 hướng dẫn bật GraalVM Reachability Metadata Repository trong plugin native của Gradle hoặc Maven. Repository cung cấp metadata do cộng đồng duy trì cho một số thư viện bên thứ ba.

Ví dụ phần cấu hình Gradle:

~~~groovy
plugins {
    id 'org.graalvm.buildtools.native' version '0.10.3'
}

graalvmNative {
    metadataRepository {
        enabled = true
    }
}
~~~

Phiên bản plugin trong ví dụ là một mốc cấu hình minh họa. Chọn Native Build Tools version tương thích với Gradle, Spring Boot và GraalVM của dự án. Spring Shell 3.3.4 có tài liệu build native riêng; hãy đối chiếu hướng dẫn đó nếu build tool của ứng dụng khác.

Sau khi cấu hình, có thể build:

~~~bash
./gradlew nativeCompile
~~~

Với Maven dùng Spring Boot parent và native profile:

~~~bash
./mvnw native:compile -Pnative
~~~

Đường dẫn binary thường là `build/native/nativeCompile` với Gradle và `target` với Maven, tùy cấu hình plugin.

Repository giúp lấy metadata cho dependency đã được hỗ trợ. Nếu một artifact hoặc version chưa có metadata phù hợp, build có thể cần hint riêng hoặc nâng cấp dependency.

## 11. Thêm RuntimeHints cho phần còn thiếu

Khi log native build chỉ ra resource hoặc reflection của code ứng dụng bị thiếu, dùng `RuntimeHintsRegistrar` để đăng ký đúng phần tử.

~~~java
import org.springframework.aot.hint.MemberCategory;
import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportRuntimeHints;

class CliRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("com/example/cli/templates/**");
        hints.reflection().registerType(
                CsvReportFormatter.class,
                MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                MemberCategory.INVOKE_PUBLIC_METHODS);
    }
}

@Configuration(proxyBeanMethods = false)
@ImportRuntimeHints(CliRuntimeHints.class)
class NativeHintsConfiguration {
}
~~~

Ví dụ này minh họa resource và reflection của ứng dụng. Với JLine, chỉ thêm hint khi đã xác nhận JAR cụ thể thiếu cấu hình cần thiết. Nếu có thể nâng cấp lên bản JLine đã cung cấp metadata, đó thường là cách duy trì dễ hơn so với tự sao chép toàn bộ cấu hình upstream.

Không dùng cấu hình quá rộng như đăng ký mọi constructor, method và field của tất cả class trong `org.jline`. Cấu hình rộng làm tăng kích thước binary, giảm lợi ích của reachability analysis và có thể che khuất vấn đề thực sự.

## 12. Thu thập metadata bằng tracing agent

Nếu không xác định được code nào truy cập động, có thể chạy ứng dụng trên JVM cùng Native Image tracing agent. Agent ghi lại reflection, resource, proxy, serialization hoặc JNI access quan sát được trong quá trình chạy.

Ví dụ chạy ứng dụng:

~~~bash
java -agentlib:native-image-agent=config-output-dir=build/native/agent-metadata -jar build/libs/inventory-shell.jar
~~~

Trong phiên chạy có agent, thực hiện các kịch bản thực tế:

- Khởi động shell và hiển thị help.
- Chạy command có completion và selector.
- Chạy command đọc template, resource hoặc file cấu hình.
- Kích hoạt formatter, converter hoặc plugin được nạp động.
- Chạy luồng terminal tương tác dùng provider đang chọn.
- Thực hiện các nhánh lỗi và các tính năng ít dùng nhưng vẫn được phát hành.

Sau khi kết thúc, xem metadata được tạo trong thư mục cấu hình. Agent chỉ ghi nhận đường đi đã chạy; tính năng chưa được kích hoạt sẽ không xuất hiện trong kết quả. Vì vậy, metadata do agent sinh không tự chứng minh toàn bộ ứng dụng đã được bao phủ.

Rà soát các file trước khi đưa vào source control:

- Loại bỏ entry không còn cần thiết.
- Giữ metadata đúng với version dependency đang dùng.
- Tránh ghi nhận các lớp test hoặc công cụ phát triển không nằm trong executable production.
- Kiểm tra lại native build sau khi thay đổi metadata.

## 13. Theo dõi lỗi thiếu metadata

Khi native executable chạy lỗi, phân loại thông báo trước khi sửa:

| Dấu hiệu | Nhóm cần kiểm tra |
|---|---|
| Không tìm thấy resource hoặc resource stream trả `null` | Resource hints, đường dẫn resource, service descriptor |
| `MissingReflectionRegistrationError` | Reflection hint cho class/member được truy cập động |
| Không tìm thấy service provider | Service descriptor, provider artifact và classpath |
| `UnsatisfiedLinkError` hoặc không tải được thư viện | JNI/JNA/Jansi artifact, native library và OS/architecture |
| Lỗi khi khởi tạo static field/class | Runtime initialization trong metadata của dependency |
| Terminal mở được nhưng không có màu hoặc capability | Provider, terminfo, `TERM` và khả năng của terminal |
| Lỗi chỉ xảy ra khi chạy script | Non-interactive runner, stdin/stdout và cách command được gọi |

Với GraalVM hỗ trợ exact reachability metadata, có thể bật `--exact-reachability-metadata` trong quá trình chẩn đoán để phát hiện thiếu đăng ký sớm hơn. Một số bản Native Image còn hỗ trợ `-XX:MissingRegistrationReportingMode=Warn` khi chạy. Kiểm tra cờ có tồn tại trong GraalVM version đang dùng trước khi thêm vào pipeline.

Không bắt `Throwable` rồi bỏ qua lỗi thiếu registration. Điều đó có thể khiến native executable tiếp tục chạy với trạng thái không đầy đủ và che mất nguyên nhân.

## 14. Kiểm tra output AOT và native build

Trước khi bổ sung metadata thủ công, kiểm tra output do AOT sinh:

~~~text
Gradle:
  build/generated/aotResources/
  build/generated/aotClasses/

Maven:
  target/spring-aot/main/resources/
  target/spring-aot/main/classes/
~~~

Tìm `META-INF/native-image` và kiểm tra resource/reflection hints. Sau đó xem log native compile để xác định:

- Hint nào được đọc từ dependency JAR.
- Hint nào do Spring AOT sinh.
- Hint nào do ứng dụng đăng ký.
- Resource hoặc reflection access nào vẫn bị báo thiếu.
- Provider nào thực sự được đưa vào binary.

Nếu GraalVM hỗ trợ build report, có thể bật `--emit build-report` để xem các resource và thành phần được đưa vào executable. Dùng báo cáo này để xác minh resource quan trọng đã được đóng gói, không chỉ dựa vào việc build kết thúc thành công.

## 15. Kiểm thử executable trên môi trường đích

Native image là binary gắn với hệ điều hành và kiến trúc mục tiêu. Hãy build và kiểm thử trên môi trường tương ứng hoặc dùng toolchain cross-compilation đã được hỗ trợ.

Ma trận smoke test nên có:

| Kịch bản | Điều cần xác nhận |
|---|---|
| Khởi động executable | Application context khởi tạo thành công |
| `help` và completion | Command metadata và JLine reader hoạt động |
| Command đọc resource | Template, banner và cấu hình có mặt |
| Command dùng formatter/plugin | Reflection hoặc registry hoạt động |
| Interactive terminal | Prompt, input editing, history và signal hoạt động |
| ANSI/style | Màu và thuộc tính hiển thị đúng trong terminal hỗ trợ |
| Terminal hẹp hoặc không có TTY | Ứng dụng có fallback hoặc thông báo phù hợp |
| Non-interactive command | Input/output và exit code đúng |
| Script nhiều command | Các command chạy theo đúng thứ tự và không bị chờ input tương tác |
| Provider JNI/JNA/Jansi | Native library được tải trên OS/architecture đích |
| Lỗi đầu vào | Lỗi được hiển thị và không tạo side effect ngoài dự kiến |

Spring Shell 3.3.x chỉ bật `NonInteractiveShellRunner` mặc định. Nếu muốn kiểm thử REPL, bật `spring.shell.interactive.enabled=true` trong cấu hình phù hợp và chạy binary trong một terminal thật hoặc pseudo-terminal.

Một native binary chạy tốt trong terminal Linux không chứng minh binary Windows hoặc macOS hoạt động. Mỗi nền tảng có terminal provider, native library và quy tắc đóng gói riêng.

## 16. Ví dụ checklist dependency và metadata

Trước khi phát hành, có thể ghi lại bảng đối chiếu:

| Hạng mục | Giá trị cần xác nhận |
|---|---|
| Spring Shell | Phiên bản runtime thực tế |
| Spring Boot / Framework | Phiên bản được BOM quản lý |
| JDK / GraalVM | Phiên bản dùng để AOT và native compile |
| JLine core modules | `jline-reader`, `jline-console`, `jline-style`, `jline-terminal` |
| Terminal provider | Jansi, JNA, JNI hoặc lựa chọn khác |
| Provider native library | Phiên bản và OS/architecture được hỗ trợ |
| Reachability metadata | Metadata từ Spring, dependency JAR và repository |
| App RuntimeHints | Chỉ các resource/reflection thực sự cần |

Không nâng riêng một module JLine lên phiên bản khác chỉ để làm mất lỗi build. Hãy nâng đồng bộ theo BOM hoặc kiểm tra tương thích của cả nhóm module vì API, metadata và native library có thể phụ thuộc lẫn nhau.

## 17. Lỗi thường gặp

| Lỗi | Nguyên nhân | Cách xử lý |
|---|---|---|

| Command/plugin không được tạo | Class được nạp bằng tên runtime | Dùng registry tĩnh hoặc đăng ký reflection cho kiểu cần thiết |
| Bổ sung reflection cho toàn bộ JLine | Chưa phân loại lỗi và chưa kiểm tra hint upstream | Xác định class/member cụ thể, kiểm tra metadata trong JAR |
| Build native thành công nhưng terminal không mở | Provider hoặc native library không có trong binary | Kiểm tra runtime dependency và OS/architecture |

| Chỉ test một terminal | Khác biệt provider/OS chưa được phát hiện | Kiểm thử từng target platform |
| Dùng JLine JNI nhưng metadata repository không khớp version | Version artifact thấp hơn mức được repository kiểm thử | Kiểm tra metadata đi kèm JAR hoặc nâng cấp phiên bản tương thích |
| Copy metadata từ JLine phiên bản khác | Tên lớp, resource và native properties đã đổi | Dùng metadata của đúng dependency version |

| Chỉ chạy `nativeCompile` | Chưa kiểm tra runtime behavior | Chạy binary với terminal thật và các luồng command đại diện |

## 18. Quy trình đóng gói native

1. Chốt phiên bản Spring Shell, Spring Boot, JDK, GraalVM và JLine.
2. Xuất dependency tree để biết chính xác provider và native artifact nào được dùng.
3. Kiểm tra các JAR JLine/provider có `META-INF/native-image`, service descriptor và resource cần thiết.
4. Chạy Spring AOT và xem hint được sinh.
5. Bật GraalVM Reachability Metadata Repository cho dependency được hỗ trợ.
6. Build native image lần đầu và phân loại cảnh báo/lỗi theo resource, reflection, proxy, serialization hoặc JNI.
7. Bổ sung RuntimeHints hẹp cho code ứng dụng hoặc metadata còn thiếu đã xác minh.
8. Nếu cần, dùng tracing agent với các kịch bản runtime đại diện rồi rà soát metadata sinh ra.
9. Build lại executable cho từng OS/architecture mục tiêu.
10. Chạy smoke test interactive, non-interactive, script, resource, reflection và terminal provider.
11. Kiểm tra kích thước binary, dependency native, giấy phép thư viện và quy trình phân phối.

## 19. Tổng kết

Đóng gói Spring Shell thành native executable đòi hỏi kiểm tra những thành phần mà static analysis không thể tự suy ra. Spring AOT và Spring Shell cung cấp nhiều hint, còn GraalVM Reachability Metadata Repository hỗ trợ một số dependency bên thứ ba. Trước khi tự thêm cấu hình, hãy xem generated hints và metadata đi kèm đúng JAR.

Với JLine, kiểm tra các module reader, console, style và terminal cùng provider Jansi/JNA/JNI được chọn. Rà soát service descriptor, terminfo/resource, reflection, native-image properties và native library theo OS/architecture. Spring Shell 3.3.4 dùng JLine 3.26.3 và JDK 17; provider FFM thuộc nhánh Spring Shell 3.4.x trở lên với JDK 22+. Không sao chép cấu hình provider giữa các phiên bản mà chưa đối chiếu.

Build thành công chỉ xác nhận quá trình biên dịch hoàn tất. Chạy executable trong terminal thật, kiểm tra cả interactive và non-interactive command, resource, plugin, completion, history, signal và native provider mới xác nhận gói phân phối hoạt động trên nền tảng mục tiêu.
