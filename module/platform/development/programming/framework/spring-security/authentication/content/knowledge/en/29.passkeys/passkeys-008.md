# Lost device, revoking passkey credentials, and account recovery without creating a weaker path

## 1. Learning objectives and scenario

Passkeys are credentials using **WebAuthn/FIDO2**, where the authenticator holds the private key and the Relying Party (RP, the application) stores the public key along with the credential ID. The user verifies locally on the device via PIN, biometrics, or an appropriate user verification (UV) mechanism. WebAuthn signs a challenge bound to the RP ID/origin, helping defend against many forms of phishing and password reuse.

When a user reports **a lost phone, lost security key, stolen laptop, or lost access to a passkey provider**, the critical questions are not merely "how do they sign back in?" but also:

- Can the credential remaining on the lost device still be used?
- Are there synced copies of the passkey on other devices?
- Which credentials must be revoked at the RP? Does the user have any other independent passkey?
- Are previously issued HTTP sessions, refresh tokens, or API tokens still valid?
- Could the support process accidentally let **email/SMS/helpdesk staff** bypass WebAuthn protection and take over the account?
- How do we verify that recovery returned account control to the rightful owner?

Lesson objectives:

1. Distinguish **device-bound passkeys** and **synced passkeys**, backup flags (`BE`/`BS`), and the RP's limits in identifying individual physical devices.
2. Understand **removing the credential ID/public key binding from an account** at the RP; distinguish it from deleting a passkey on a device and revoking sessions/tokens.
3. Build runbooks for **lost device**, **suspected account compromise**, and **all authenticators lost**.
4. Design **recovery with assurance commensurate with account value**, using backup/enrolled passkeys, protected recovery codes, or controlled identity proofing.
5. Use the right Spring Security WebAuthn APIs (`UserCredentialRepository`, `PublicKeyCredentialUserEntityRepository`, `WebAuthnRegistrationFilter`) and authorize credential add/remove operations.
6. Test credential revocation, anti-helpdesk-takeover, session invalidation, and race conditions across multi-device and multi-node scenarios.

Scope: **Spring Security Servlet/WebAuthn applications**, with concrete API examples using Spring Security 6.5.11 as the baseline; some packages/dependencies differ in Spring Security 7.x. The lesson includes Java 17 and a simulation program compilable with JDK alone. Do not conflate this with **mTLS client certificates**, **OAuth access-token revocation**, or **password reset**.

## 2. WebAuthn model: what does the RP actually store and have authority to revoke?

### 2.1. Registration

When creating a passkey, the browser calls WebAuthn `navigator.credentials.create(...)` with the RP's challenge/creation options. The authenticator generates a key pair scoped to the RP ID. The private key is held by the authenticator/passkey provider; the RP receives the **credential ID, public key, and metadata** verified through the registration ceremony.

```text
User                       Browser / platform              RP backend
   |                              |                              |
   | Request to add passkey       |                              |
   |----------------------------->| POST /webauthn/register/options
   |                              |----------------------------->|
   |                              |<----- challenge, RP ID, ...--|
   | Verify via device unlock     |                              |
   |<---- navigator.credentials.create() ------------------------|
   |                              | POST attestation result      |
   |                              |----------------------------->|
   |                              |         RP checks challenge, |
   |                              |         origin, RP ID, struct|
   |                              |         then saves credential|
   |                              |<------------ 200/4xx --------|
```

Server-side credential records typically include:

| Field | Role | Revocation notes |
| --- | --- | --- |
| `credentialId` | Credential identifier generated by the authenticator | Lookup key to reject/delete a credential; **not** a device serial number |
| `userHandle / user entity ID` | Key linking the credential to the user at the RP | Never use client-sent username/email to redefine the owner |
| `publicKey` (COSE key) | Verifies future assertion signatures | Deleting the record removes the RP's trusted key for accepting that credential |
| `created`, `lastUsed`, user-visible `label` | Credential management/observability | User-entered labels may be inaccurate; never use as proof of ownership |
| `signCount` | Tracks signature counter when meaningful | With syncable credentials, counter may be 0; **do not** infer non-cloning from `counter=0` |
| `backupEligible` (`BE`) | Authenticator reports whether credential can be backed up/synced | Only a signal from the authenticator; does not reveal how many devices hold the passkey |
| `backupState` (`BS`) | Authenticator reports credential is currently backed up | May change over time; does not replace real device state |
| `transports`, AAGUID/metadata if stored | Assists UX/policy choices | Never use labels or transports as a user authentication factor |

**WebAuthn stores per credential, not per physical unit like "Phone A."** A synced passkey can share the exact same credential ID/private key synced across multiple devices by the passkey provider. The RP typically **cannot** look at a credential record and determine how many copies exist.

### 2.2. Sign-in (assertion)

The browser fetches authentication options and calls `navigator.credentials.get(...)`. The authenticator signs the challenge with the passkey's private key. The RP checks the signature against the registered public key while verifying challenge, origin, RP ID, UP/UV flags, and relevant security rules.

```text
RP generates random challenge / expiration
            |
            v
Browser + authenticator verify user, sign challenge
            |
            v
RP looks up credential ID -> public key and owner
            |
            +-- credential missing/revoked -> REJECT
            |
            +-- signature, challenge, origin, RP ID invalid -> REJECT
            |
            +-- valid -> Authentication, then authorization/session
```

If the RP deletes the credential record or marks it revoked and **all nodes** share that trust state, any new assertion using that credential must be rejected. However, **sessions created before credential deletion may remain alive** unless the system actively invalidates sessions. That must be handled separately during a lost-device incident.

## 3. "Lost device" does not always mean "lost all passkeys"

Before picking an action, classify the situation:

| Scenario | Can the passkey still work on another device? | Primary risk | Handling approach |
| --- | --- | --- | --- |
| Lost **physical security key** holding a device-bound passkey | No copy of that exact credential exists; another backup credential may exist | Device stolen and attacker knows PIN/UV, or user lockout | Use backup passkey; revoke credential on lost key, replace key |
| Lost phone with **synced passkey**, provider account still secure | May exist on laptop/another phone signed in to provider | Lost device could still sign in if unlocked; sync-provider account may be targeted | Remotely lock/wipe device via provider; assess compromise; revoke credential at RP if at risk |
| Device completely destroyed, device-bound private key unrecoverable | No, unless an independent passkey exists | Loss of access without necessarily a compromise | Use backup authenticator or policy-compliant recovery |
| Lost access to **passkey provider / cloud sync account** | May be unable to bootstrap new device | Provider recovery flow or attacker taking over provider account | Prefer backup passkey in a different trust domain; assess provider takeover risk |
| Device suspected of malware, or unlock code stolen too | A synced credential may appear across multiple devices | Unknown whether attacker can sign assertions or use active sessions | Suspend/revoke suspect credentials, invalidate sessions, audit account changes |
| User deleted passkey in provider settings | Depends on ecosystem and sync | RP may still have the record while private key is gone | Register a new credential via secure auth, then remove orphaned record |

**Losing a device does not automatically mean the private key was extracted.** Passkeys usually have key protection mechanisms. Yet upon a theft report, policy must account for the attacker abusing an **active logged-in session**, unlocking the device, or exploiting the passkey provider's recovery flow; never assume "completely safe because of biometrics."

### 3.1. Device-bound vs. synced: pros/cons for recovery

- **Device-bound**: the key is tied to the authenticator, such as a non-exportable FIDO security key. Losing the device can mean permanently losing that credential. If **two security keys** were enrolled and stored in two safe places, the remaining key lets you authenticate and replace the lost one.
- **Synced**: the same credential can be protected, encrypted, and synced across the provider ecosystem. The user can regain access to the passkey when signing in to the provider on a new device. This reduces lockouts while introducing trust in the **sync provider's security and account recovery**.
- **Cross-device authentication / hybrid**: lets you use a nearby phone to authenticate a browser on another machine without copying a plaintext private key out of the ecosystem. This is a way to use an authenticator you still control, not a recovery method if all passkeys are lost.

Therefore, "registering 2 passkeys" provides independent backup only when they **do not share a single point of failure**. Two devices syncing the same credential from one provider may still be the exact same WebAuthn credential. For high-value accounts, consider an additional passkey on a **separate authenticator/security key and location** or an independent provider.

### 3.2. `BE`/`BS` flags: understand accurately, do not overreach

WebAuthn Level 3 defines `BE` (backup eligible) and `BS` (current backup state) in authenticator data. They are useful to indicate "syncable" and support device policies. However:

1. `BE=1` does not prove the credential has actually been backed up/copied.
2. `BS=1` does not prove the RP knows which devices hold copies or that the sync source is unconditionally secure.
3. `BE=0` usually hints at device-bound; it does not prove all hardware properties without proper attestation/verification policy.
4. Flags from an old assertion may not reflect the provider ecosystem's current state immediately.
5. When a **synced credential ID** is revoked at the RP, **every copy using that credential** can no longer sign in to that RP. You cannot "delete the credential only on the lost phone" via a server-side action by credential ID.

Never display UI text like "iPhone X was removed from your account" simply because a record with an arbitrary label was deleted; a more accurate message is "The selected passkey has been revoked for this account."

## 4. Threat model: where will an attacker strike?

An account with strong phishing-resistant passkeys can be undermined if recovery is too permissive. Common attack vectors:

1. **Helpdesk social engineering**: attacker knows name/email/employee ID, fakes a lost-phone report, and asks support to reset MFA and enroll the attacker's passkey.
2. **Email takeover**: attacker accesses the mailbox and uses a "forgot passkey" link to bypass WebAuthn requirements.
3. **SIM swap / SMS interception**: uses SMS OTP to replace passkey cryptographic authentication.
4. **Session hijacking**: attacker steals a cookie/session via malware; from an old session, they try adding a passkey or deleting the primary passkey.
5. **Password downgrade**: UI shows "Try another way → password" with an old/weak password still active, breaking phishing-resistant guarantees.
6. **Recovery code theft/replay**: backup codes stored on the same lost machine/drive, too short, lacking brute-force limits, or not single-use.
7. **Cross-tenant credential deletion**: backend accepts a credential ID and deletes it arbitrarily without checking the owner.
8. **Race condition**: concurrent credential add/delete and email/role changes bypass the "must keep one secure authenticator" policy.
9. **Insider recovery abuse**: a support agent can unilaterally approve recovery for others without audit or separation of duties.
10. **Sync-provider compromise**: attacker compromises the passkey management account and bootstraps a new device via the provider's recovery flow.

"Not creating a weaker path" does not mean never helping users who lost all devices; it means **every recovery path is intentionally designed, narrowly scoped, and verified with commensurate evidence**, never turning a lone email code into unrestricted passkey enrollment.

## 5. Prevention: set up recovery *before* a device is lost

### 5.1. Enroll an independent backup authenticator

Right after a user adds their first passkey, the UI should encourage:

- Adding a second passkey on an **independent authenticator** or a hardware security key stored safely, especially for admin/financial accounts.
- Synced passkeys can reduce everyday lockouts, yet for high assurance, maintain a backup separate from the same cloud account.
- Confirming the user actually tested signing in with the backup method (not just seeing a "saved" screen).
- Storing user-understandable details: label, created date, last used, and WebAuthn-reported backup policy; never expose raw credential IDs/public keys as proof of ownership.
- When adding a new passkey: require sufficiently fresh **reauthentication/step-up**, verify permissions on the current account, enforce CSRF, and block enrollment from stolen sessions.

A 30-day-old session created with a legacy password is likely insufficient to attach a new passkey to an account requiring phishing-resistant auth. Distinguish `session.isAuthenticated()` from **the recency and strength of the authentication used**. You can leverage `auth_time`, AAL/acr levels, WebAuthn UV, and application step-up proofs.

### 5.2. Issue recovery codes only when policy permits

Recovery codes are not passkeys, because they are phishable secrets. If a product chooses to offer them:

- Generate with a cryptographic random source; refer to NIST SP 800-63B-4: **saved recovery codes must have at least 64 bits of entropy** within that standard's scope.
- Display once only and encourage **offline storage** separate from the potentially lost device/passkey, such as a sealed printout or independent vault.
- Store only hashed verifiers per policy, never raw codes; single-use tokens with guess limits and time limits.
- Upon successful use, **consume atomically** to prevent two concurrent requests from reusing the same code.
- Never assume a single code suffices to re-grant access for AAL2/AAL3 accounts; follow evidence combinations/re-proofing rules per assurance policy.
- After using or reissuing codes, notify via previously verified contact channels.

**NIST 800-63B-4 at AAL2** specifies concrete recovery combinations, such as two codes from two distinct methods, or one code paired with a bound single-factor authenticator, or repeating prior identity proofing. These are standard-specific requirements in context, not a universal formula for every app. Read the source specification before claiming compliance.

### 5.3. Lock the account when all proof is lost

A system may require users to complete a manual process commensurate with the assurance level before restoring access. **Never build a "magic email link" that automatically grants permission to register a new passkey** just for implementation speed. Without approved recovery evidence, policy may keep the account locked/pending verification, even at the cost of UX friction.

### 5.4. Prepare independent alert channels

Whenever a user adds/removes a passkey, changes recovery addresses, alters MFA policy, or recovers an account, send alerts to **previously verified and stored contact addresses**. Never notify only an email address freshly changed by an attacker within the same recovery flow.

## 6. Runbook when a device is reported lost: three distinct branches

### 6.1. Branch A — another trusted enrolled passkey remains available

```text
User reports lost device
        |
        v
Authenticate with independent enrolled passkey
        |
        v
Recent step-up / account ownership confirmed
        |
        +--> list relevant credential records
        |
        +--> revoke suspect credential(s) at RP
        |
        +--> invalidate suspicious sessions and refresh tokens per policy
        |
        +--> register and test replacement passkey
        |
        +--> notify out-of-band / audit / monitor
```

This is usually the best path because the user still proves control with a previously bound authenticator. When device loss suggests compromise, review transactions/sessions created since the last known-safe use.

### 6.2. Branch B — synced passkey remains on a safe device

The user can sign in from a laptop linked to the same passkey provider. Before using that passkey to handle the incident, distinguish:

- Device was merely dropped/broken and the provider account remains safe: user may sign in to enroll a replacement device.
- Device was **stolen/unlocked/unlock code potentially known**: consider revoking the associated credential at the RP even if the same credential still sits on the laptop, and require enrolling a different credential via trusted verification.
- Provider account shows signs of compromise: recover/secure the provider per provider procedures; the RP must restrict synced credentials from continuing to authenticate if treated as compromised.

If you delete **one synced credential at the RP**, the copy remaining on the laptop with the same credential ID will also be rejected by the RP. Therefore, **ensure an independent authenticator exists** before deleting whenever possible; otherwise route the account into controlled recovery rather than sacrificing security merely to lower ticket volume.

### 6.3. Branch C — all authenticators are lost/inaccessible

This is true **account recovery**, not just "add another passkey." Sample workflow:

1. Receive the recovery request and create a case ID without disclosing account existence to outsiders.
2. Put the request through **risk review**: credential change history, devices, geography, initiation method, account sensitivity, fraud signals.
3. Verify recovery evidence **registered before the incident**, never relying on a newly changed phone number or email.
4. Execute a combination of recovery code + remaining authenticator or identity proofing/manual verification commensurate with the assurance policy; never accept guessable security questions, unverified ID photos sent over chat, or a single helpdesk agent unilaterally clicking "reset MFA."
5. For sensitive accounts, enforce dual approval, an appropriate cooling-off delay, notifications to prior channels, and dispute reporting mechanisms.
6. Once recovery is approved, issue a **limited-privilege recovery session**: allowed only to enroll a new passkey, inspect recent activity, and reset recovery info per policy; **not yet** allowed to withdraw funds, change payout accounts, change admin roles, or export sensitive data.
7. Complete a **normal WebAuthn registration ceremony** to generate a new public/private key pair on an authenticator the user controls. Recovery evidence is **not** a public key or a WebAuthn assertion.
8. Revoke lost/suspect credentials, invalidate at-risk sessions/tokens, and rotate recovery codes as needed.
9. Send out-of-band notifications, write audit events with actor/case/timestamp/method, allow user disputes, and monitor behavior.

**Critical distinction:** a recovery session granted after verification **is not synonymous with a full user session**. The system must lock sensitive endpoints behind a dedicated scope/authority, and grant normal privileges only after the new passkey is successfully registered/authenticated and all defined conditions are met.

## 7. Revoking credentials at the RP: scope and limits

### 7.1. "Revoke" means removing the credential → account binding

Under WebAuthn, the RP typically authenticates by looking up the credential ID to retrieve the public key/owner. Revocation can be implemented by:

- **Deleting** the credential record in `UserCredentialRepository`.
- Or using a `REVOKED/SUSPENDED` status in a dedicated credential management table and customizing the verifier/policy to reject such records; this is a **custom design**, not the default across all Spring repositories.

Verification goal:

```text
credentialId  ──lookup─► credential record (publicKey + userHandle)
       |
       +-- revoked / missing ──► reject assertion
       |
       +-- active ──► verify signature + challenge + RP/origin/UV ...
```

If deleting, ensure **all nodes** performing authentication see the updated state without stale caches keeping the old record alive. If the app uses a per-node in-memory credential registry, deleting on node A does not remove the record on node B. Use shared persistence or reliable invalidation events.

### 7.2. Revoking a credential does NOT automatically affect the following

| Asset | Does RP passkey revocation affect it automatically? | Action needed on suspected compromise |
| --- | --- | --- |
| Private key on lost device | **No**; RP does not control keys inside authenticators | Lock/wipe device or revoke at provider per actual capabilities, alongside blocking the RP credential |
| Same credential synced on other devices | **Yes**, in that the RP will reject it if the credential ID is identical | Clarify this in user guidance; enroll a new independent credential |
| Already-authenticated session cookies | **Not by default** | Invalidate related sessions in the session store/registry and rotate security state |
| OAuth access tokens/refresh tokens | **Not by default** | Invoke AS/RS revocation, short TTLs, denylists/introspection as appropriate |
| Recovery codes / old reset links | **Not by default** | Revoke/reissue codes and invalidate unused recovery tokens |
| Passkeys at other RPs | **No** | Each RP manages its own bindings; coordinate with IdP/SSO where applicable |
| Ability to enroll new credentials | **Not by default** | Gate registration behind recent WebAuthn step-up or verified recovery scope |

When a device is reported lost, **deleting a credential without invalidating active sessions on that device** can let an attacker continue operating. Conversely, invalidating all sessions does not stop a stolen credential from creating a new login. Both steps must be addressed independently.

### 7.3. Removing a credential differs from "deleting the account"

Never delete `PublicKeyCredentialUserEntity` or the user account just to revoke one passkey; multiple credentials may share that user handle. Before deleting, confirm the credential ID belongs to the right user and policy allows it. When an account has only one remaining credential, you may deny self-service deletion until a new passkey is enrolled or valid recovery exists—except in incident-response flows authorized to lock the account.

## 8. Spring Security 6.5: APIs to know for credential management

Spring Security **6.4+** supports WebAuthn on **Servlet**; **6.5.11** includes JDBC persistence and management APIs. Typical structure:

| API (Spring Security 6.5) | Responsibility |
| --- | --- |
| `HttpSecurity.webAuthn(...)` | Configures RP ID, allowed origins, and WebAuthn login/registration |
| `WebAuthnRegistrationFilter` | Handles registration and the removal endpoint per matcher |
| `UserCredentialRepository` | Saves/looks up/deletes `CredentialRecord` by credential ID/user handle |
| `PublicKeyCredentialUserEntityRepository` | Resolves the account's user handle, not a per-passkey store |
| `CredentialRecord` | Credential metadata: ID, user entity ID, public key, created/last used, BE/BS |
| `Bytes` | Byte wrapper for credential ID/user handle, Base64URL helpers |
| `JdbcUserCredentialRepository` | Persists credential records via JDBC in its dedicated schema |
| `JdbcPublicKeyCredentialUserEntityRepository` | Persists user entities via JDBC |
| `CredentialRecordOwnerAuthorizationManager` | Spring Security 6.5.10+ checks that the credential ID belongs to the authenticated user before deletion |

**Notable version detail:** the **6.5.11** `WebAuthnRegistrationFilter` Javadoc states the default deletion request matcher is **`DELETE /webauthn/register/{id}`**, yet **by default all deletion requests are denied** until an appropriate `AuthorizationManager<Bytes>` is configured. Do not see a `DELETE` endpoint mentioned and assume it is already open to users or can safely use `permitAll()`.

`CredentialRecordOwnerAuthorizationManager` was introduced in 6.5.10; do not copy this class into 6.5.0/6.4.x without upgrading. `WebAuthnConfigurer` in the 6.5.11 DSL **does not have** a `deleteCredentialAuthorizationManager(...)` customization method per the Javadoc; to use the built-in deletion filter, locate the version's exact integration point or build a custom management endpoint enforcing owner/CSRF/step-up checks. Never invent non-existent API methods.

### 8.1. Basic Servlet WebAuthn configuration

**Snippet** inside a `@Configuration` class with `HttpSecurity` and Spring Security imports:

```java
@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/error").permitAll()
            .anyRequest().authenticated())
        .webAuthn(webauthn -> webauthn
            .rpId("example.com")
            .allowedOrigins("https://example.com"));
    return http.build();
}
```

This snippet illustrates the WebAuthn DSL and origin/RP ID; it is **not a runnable standalone project**: you need a web app configured with HTTPS, the right public domain, a user identity source, login/registration pages, and compatible dependencies. If you use form login while learning passkey registration, remember that **password login becomes a parallel authentication path**; a high-assurance app cannot claim "passkey-only phishing resistance" while a password fallback remains open to sensitive resources.

WebAuthn challenges and creation/request options must be generated/stored/matched by the framework; never write an endpoint like `login?credentialId=...` treating the ID as a credential. The credential ID is a **public identifier/reference**, not a password.

### 8.2. JDBC persistence for multiple nodes

In Spring Security 6.5:

```java
// Bean snippet in @Configuration, with JdbcOperations injected.
@Bean
JdbcPublicKeyCredentialUserEntityRepository userEntities(
        JdbcOperations jdbc) {
    return new JdbcPublicKeyCredentialUserEntityRepository(jdbc);
}

@Bean
JdbcUserCredentialRepository passkeyCredentials(JdbcOperations jdbc) {
    return new JdbcUserCredentialRepository(jdbc);
}
```

Imports:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.jdbc.core.JdbcOperations;
import org.springframework.security.web.webauthn.management.JdbcPublicKeyCredentialUserEntityRepository;
import org.springframework.security.web.webauthn.management.JdbcUserCredentialRepository;
```

Spring Security docs reference classpath schemas where `JdbcUserCredentialRepository` depends on:

```text
classpath:org/springframework/security/user-credentials-schema.sql
```

In production, deploy dialect-verified schemas/migrations before enabling the JDBC repositories; use shared storage across nodes with transactions, indexes, and cache invalidation plans if caching is used. Never rely on the default in-memory repository for a cluster.

### 8.3. Reading and deleting the right credential in the repository

`UserCredentialRepository` exposes these methods:

```java
CredentialRecord findByCredentialId(Bytes credentialId);
List<CredentialRecord> findByUserId(Bytes userHandle);
void save(CredentialRecord record);
void delete(Bytes credentialId);
```

These are **abbreviated explanatory signatures**, not a custom interface replacing Spring Security. `PublicKeyCredentialUserEntityRepository.findByUsername(String)` returns the RP's user entity, from which you obtain `getId()`. `CredentialRecord.getUserEntityUserId()` is the linking key. Verify equality against the user handle, not merely against a UUID/email label.

Important: repository `delete(id)` **only performs the storage operation**; by itself it does not enforce recent authentication, CSRF, owner authorization, last-credential checks, session invalidation, or user notifications. Calling the repo from an unprotected HTTP controller is a severe vulnerability.

## 9. Java 17 Spring Security example: service checking ownership before deletion

The example below presents a **compilable Spring service class** using exact Spring Security 6.5.11 APIs in a Servlet project that already has `spring-security-web` and WebAuthn dependencies. It performs only a **repository-level ownership check**; the controller must still enforce **recent reauthentication/step-up, CSRF, rate limiting, and recovery permissions**, and a production service needs transactions/atomic conditional deletes to avoid races when concurrent requests modify credential bindings.

File `src/main/java/demo/passkey/PasskeyCredentialManagement.java`:

```java
package demo.passkey;

import java.util.List;

import org.springframework.security.access.AccessDeniedException;
import org.springframework.security.web.webauthn.api.Bytes;
import org.springframework.security.web.webauthn.api.CredentialRecord;
import org.springframework.security.web.webauthn.api.PublicKeyCredentialUserEntity;
import org.springframework.security.web.webauthn.management.PublicKeyCredentialUserEntityRepository;
import org.springframework.security.web.webauthn.management.UserCredentialRepository;

public final class PasskeyCredentialManagement {

    private final PublicKeyCredentialUserEntityRepository users;
    private final UserCredentialRepository credentials;

    public PasskeyCredentialManagement(
            PublicKeyCredentialUserEntityRepository users,
            UserCredentialRepository credentials) {
        this.users = users;
        this.credentials = credentials;
    }

    public List<CredentialRecord> listForAuthenticatedUser(
            String authenticatedUsername) {
        PublicKeyCredentialUserEntity user =
                users.findByUsername(authenticatedUsername);

        if (user == null) {
            throw new AccessDeniedException("Account not available");
        }
        return credentials.findByUserId(user.getId());
    }

    public void removeOwnedCredential(
            String authenticatedUsername, Bytes credentialId) {

        PublicKeyCredentialUserEntity user =
                users.findByUsername(authenticatedUsername);
        if (user == null || credentialId == null) {
            throw new AccessDeniedException("Not allowed");
        }

        CredentialRecord record =
                credentials.findByCredentialId(credentialId);

        if (record == null ||
                !user.getId().equals(record.getUserEntityUserId())) {
            throw new AccessDeniedException("Not allowed");
        }

        // Security policy must be verified BEFORE this call:
        // recent phishing-resistant step-up or verified recovery flow;
        // session/token invalidation if this is a compromise incident;
        // ensure the user is not locked out of their account.
        credentials.delete(credentialId);
    }
}
```

**What the code accomplishes:** looks up the user strictly by the server-provided `authenticatedUsername`, checks ownership via user handle, rejects non-existent/unowned credentials, and only then calls `delete`. To manage this class with Spring DI, declare a `@Bean PasskeyCredentialManagement` or annotate `@Service` per your project conventions; the example uses no static global state.

**What the class intentionally does not assume:** whether the passed username string has completed WebAuthn step-up; it has no request/session context to know. The caller must obtain the username from a Spring Security-verified `Authentication` and enforce the policies listed above. An HTTP endpoint merely calling this class behind `@PreAuthorize("isAuthenticated()")` is **insufficient** for security-critical changes.

**Race condition:** `findByCredentialId` → owner check → `delete` is still two operations. In multi-node/multi-tenant systems, use a transaction and a **conditional delete on credential ID + owner user ID** to prevent TOCTOU; generic repositories do not guarantee a single atomic conditional delete covering ownership verification. Without such guarantees, do not declare this endpoint production-ready.

## 10. Preventing self-lockout and preventing passkey addition by session hijackers

### 10.1. Never delete the last passkey recklessly

There are at least three sound policies depending on the product:

1. **Normal self-service**: allow deleting a credential only if the user has another independent backup authenticator and completed recent step-up. For the last credential, require adding a new passkey first.
2. **Incident response**: when the last credential is suspected compromised, immediately suspend/revoke it and place the account into restricted recovery; never keep a dangerous credential active just so the user can still log in.
3. **Admin break-glass**: requires independent proofing/approval and auditing; never let helpdesk use `permitAll()` or hardcode admin powers into UI.

Counting `credentials.findByUserId(userId).size()` before deletion is only **for display or a preliminary check**. Two concurrent transactions can both observe `size=2` and delete two different credentials, leaving 0. Guaranteeing "at least one credential remains" requires serializable isolation/locking/conditional policies in persistence.

### 10.2. Adding a new passkey is also high-risk

An attacker might possess a session cookie without possessing a passkey. If the application permits **`POST /webauthn/register/options`** and **`POST /webauthn/register`** solely on an old authenticated session, the attacker can enroll a passkey on their own device. Thus registration/options and credential removal require:

- Recent, sufficiently strong reauthentication recorded **server-side** (never trust a client-sent `recent=true` flag).
- Policy-appropriate User Verification (UV); never treat `userPresent` alone as AAL2.
- CSRF protection for state-changing requests, especially when browsers use cookies.
- Ownership checks, rate/count limits, and risk scoring on device/region changes.
- Independent out-of-band notifications to previously registered addresses.
- For restricted recovery sessions: allow enrolling **only one new credential** after proofing, verify real usage, and only then unlock remaining privileges.

A newly registered passkey **does not retroactively prove prior recovery evidence was trustworthy**. If an easily hijacked email link granted registration rights, the attacker's passkey will look completely valid cryptographically.

### 10.3. Replacement sequence when the user still holds a safe passkey

```text
authenticate with known-good passkey
       |
       v
register NEW passkey on trusted authenticator
       |
       v
VERIFY new credential with a real assertion
       |
       v
revoke lost/compromised credential record(s)
       |
       v
invalidate risky sessions and tokens as needed
       |
       v
notify + audit + recovery-code rotation
```

If there are signs **an attacker is actively using the old credential**, reverse the priority: suspend the compromised credential immediately and move the account into a restricted recovery flow. Never delay revocation until an attacker finishes using a session, yet also never open a weak bypass to handle lockouts.

## 11. Session and token lifecycle after passkey revocation

After a valid WebAuthn assertion, Spring Security may create an HTTP session or issue application/OAuth tokens. **The credential verifier and session manager hold separate state.**

A compromise-response playbook typically does the following:

1. Mark/delete the revoked credential in the repository and ensure all auth nodes reject it.
2. Invalidate user sessions on suspect devices; if suspect sessions cannot be isolated or risk is high, invalidate **all sessions** for the user per policy.
3. If using Spring Session/Redis, delete session records in the shared store; do not merely expire a cookie in the current browser.
4. If OAuth refresh/access tokens were issued, invoke proper revocation at the Authorization Server and coordinate with Resource Servers if needed; offline JWTs can remain live until `exp` without a denylist/introspection.
5. Revoke **persistent remember-me tokens**, recovery tokens/codes, and account-change tokens when loss of control is suspected.
6. Consider session rotation/reauthentication on known-good devices; avoid accidentally leaving an attacker on an old session.
7. Audit the credential revocation timestamp, acting principal, policy decision, case ID, count of invalidated sessions, and token revocation outcomes.

An end-to-end guarantee that "the attacker has no remaining access" depends on **WebAuthn, sessions, OAuth tokens, session caches, and RS enforcement together**. A single line of `userCredentialRepository.delete(...)` cannot make that promise alone.

### 11.1. Do not overuse "logout all" for non-compromise incidents

If a user merely physically broke an offline security key without theft, the risk differs from an unlocked stolen phone. Policy may preserve safe sessions after user verification, yet that decision must rest on your threat model and actual behavior—not a vague "lost device" checkbox.

## 12. Standalone Java 17 exercise: credential revocation state machine

To see how **credential revocation differs from session invalidation**, below is a pure Java 17 example (no Spring dependencies). It simulates the defined rules without performing cryptographic WebAuthn verification or using a real session store.

Save as `PasskeyRecoveryModel.java`:

```java
import java.util.LinkedHashSet;
import java.util.Set;

public class PasskeyRecoveryModel {

    static final class Account {
        final Set<String> credentialIds = new LinkedHashSet<>();
        boolean sessionActive = true;
        boolean recoveryApproved = false;

        Account(String... initialIds) {
            for (String id : initialIds) {
                credentialIds.add(id);
            }
        }

        boolean canAuthenticate(String credentialId) {
            return credentialIds.contains(credentialId);
        }

        void revoke(String credentialId) {
            credentialIds.remove(credentialId);
        }

        void invalidateSession() {
            sessionActive = false;
        }

        boolean enrollReplacement(String id) {
            if (!recoveryApproved || id == null || id.isBlank()) {
                return false;
            }
            credentialIds.add(id);
            recoveryApproved = false; // consume restricted recovery approval
            return true;
        }
    }

    public static void main(String[] args) {
        Account alice = new Account("synced-A", "security-key-B");

        System.out.println("before A: " + alice.canAuthenticate("synced-A"));
        alice.revoke("synced-A");
        System.out.println("after A: " + alice.canAuthenticate("synced-A"));
        System.out.println("old session: " + alice.sessionActive);

        alice.invalidateSession();
        System.out.println("session after invalidate: " + alice.sessionActive);

        System.out.println("enroll without proof: "
                + alice.enrollReplacement("replacement-C"));

        // Simulation only: the policy engine approved recovery.
        alice.recoveryApproved = true;
        System.out.println("enroll with proof: "
                + alice.enrollReplacement("replacement-C"));
        System.out.println("new credential: "
                + alice.canAuthenticate("replacement-C"));
        System.out.println("replay approval: "
                + alice.enrollReplacement("attacker-D"));
    }
}
```

Compile/run with JDK 17+:

```bash
javac PasskeyRecoveryModel.java
java PasskeyRecoveryModel
```

**Exact** stdout:

```text
before A: true
after A: false
old session: true
session after invalidate: false
enroll without proof: false
enroll with proof: true
new credential: true
replay approval: false
```

The exercise shows:

- Revoking credential A flips `canAuthenticate("synced-A")` from `true` to `false`.
- The old session **remains `true`** until an independent invalidate action runs.
- Recovery approval is a bounded, consumed capability—not a permanently lingering flag.
- `recoveryApproved=true` in the example is controlled test data; **never** read it from a client query/parameter in a real application.

This example has no WebAuthn signatures, locks/transactions, or expiry/CSRF/identity proofing; use it to study state boundaries, **not** as a template for a production recovery endpoint.

## 13. Designing secure recovery codes and handling race conditions

If your product supports saved recovery codes, a server-side design must guarantee:

| Aspect | Expected contract |
| --- | --- |
| Generation | CSPRNG, entropy matching assurance tier; e.g., minimum 64 bits per NIST saved codes, or higher |
| Storage | Store only salted/keyed verifier hashes; show raw codes once; protect DB backups |
| Verification | Rate-limit per account/IP/risk, generic error messages that do not leak which codes are valid |
| Consumption | **Atomic mark-used/delete** so at most one request wins when the same code is sent concurrently |
| Scope | Never turn a code into a full-privilege session if policy requires additional proof |
| Expiry | Apply appropriate policy to saved/issued codes; do not treat every code as timeless by default |
| Notification | Alert previously registered channels on recovery attempts, successes, and credential changes |
| Rotation | After recovery, issue new codes and revoke old/used ones |
| Audit | Log outcome/risk/case ID, never raw codes or passkey private keys |

**Hypothetical SQL** example for an application-designed recovery code table (PostgreSQL dialect), not a Spring Security schema:

```sql
-- Only one request can win if the code has not been consumed yet.
UPDATE account_recovery_codes
SET used_at = CURRENT_TIMESTAMP
WHERE account_id = :account_id
  AND code_hash = :code_hash
  AND used_at IS NULL
  AND revoked_at IS NULL
RETURNING code_id;
```

When expiration applies, add `expires_at > CURRENT_TIMESTAMP` per schema/policy. Confirm **1 row affected** before treating the code as validly used. Hash lookups and transactions/uniqueness must fit your implementation; never split `SELECT unused` and `UPDATE used` outside a transaction. If relying on a one-time code alone falls below required assurance, **still enforce additional proofs** before allowing enrollment.

### 13.1. Other race conditions to test

- Two concurrent deletes targeting the last two credentials simultaneously.
- A recovery approval used concurrently in two tabs to register two passkeys, one of which is an attacker's.
- One request deleting a credential while another authenticates with it; define consistency boundaries across storage/caches.
- One request changing the recovery email while another initiates recovery; verification contacts must be **snapshotted beforehand** or governed by risk policy.
- A session invalidation event arriving after credential revocation; evaluate the exposure window and propagation delay.

## 14. Support surface (helpdesk) and anti-social-engineering

A support agent often holds internal knowledge yet **cannot prove account ownership merely by viewing a ticket/email**. Workflows must minimize helpdesk privileges and require independent evidence.

### 14.1. Recommended policies

- Helpdesk can **open a case, flag an account as suspected compromised, and request review**; never unilaterally bypass WebAuthn or issue full sessions.
- For high-assurance requirements, enforce at least **separation between requester and approver roles** per risk; optionally add waiting periods or contact via pre-registered channels.
- If the product identity-proofed users at onboarding, recovery may require commensurate **reproofing**; never accept an unverified photo of an ID over chat as proof.
- Permit issuing only a narrow-scoped recovery session; require registering a new WebAuthn passkey and verifying a real assertion before granting sensitive privileges.
- Recovery decisions must record case ID, actor, proof type, timestamps, approvals, and outcome. Protect audit logs against arbitrary edits/deletes.
- Use out-of-band alerts and "this wasn't me" reporting links, especially before/after changing an account's email or phone number.
- Never leak "whether an account exists or which passkeys are enabled" on public endpoints via distinct status codes or latency.

### 14.2. Weak paths to eliminate

```text
BAD: "I lost my passkey"
  -> send a 6-digit SMS to a newly supplied phone
  -> allow full login and add new passkey
```

```text
BAD: "I have a browser session"
  -> change account recovery email
  -> send magic link to that new email
  -> register an attacker's passkey
```

```text
GOOD: lost all authenticators
  -> verified pre-enrolled recovery methods / identity proofing
  -> restricted recovery state + audit + independent notification
  -> normal WebAuthn registration + real assertion
  -> revoke compromised credentials/sessions
  -> restore necessary privileges under risk policy
```

"GOOD" is a generalized model; there is **no** fixed small set of steps sufficient for every AAL/IAL tier. For financial or admin accounts, consult the applicable assurance specifications and legal requirements.

## 15. UX and accurate user messaging

UI states must avoid misleading users:

| Action | Acceptable copy | Do NOT say |
| --- | --- | --- |
| Register passkey | "Passkey has been added to this account." | "Your phone is permanently secure." |
| Revoke credential | "This passkey is no longer accepted to sign in to this account." | "The private key has been deleted from all devices." |
| Invalidate sessions | "Selected sessions have been signed out." | "All OAuth tokens have been revoked" when unverified |
| Lost synced passkey | "If your provider account is still secure, you can restore use on another device." | "Removed on the stolen phone while the laptop keeps using the same passkey." |
| No authenticators left | "Start recovery using your registered recovery methods." | "Just use a new email/SMS to get full access." |
| Recovery approved | "You may register a new sign-in method in this limited recovery session." | "All account actions are unlocked." |
| Sensitive credential add/remove | "This change has been recorded. If this wasn't you, report it." | Displaying raw credential IDs/private keys as proof |

A **Manage passkeys** page should list credential records with label, created/last used, status if policy supports it, and backup warnings based on signals; provide rename/delete buttons protected by CSRF and recent step-up. When a user deletes a **synced credential**, explain that it may stop working **on every device sharing that passkey**.

### 15.1. Helping users who don't understand syncing

Do not force users to understand what the "WebAuthn BE bit" is. Ask situation-based questions: "Do you have another machine using the same passkey provider?", "Do you have a backup security key?", "Could someone else unlock the lost device?". The UI uses plain questions; the backend must still enforce security policies based on evidence, not solely on user claims.

## 16. Security testing: don't just test that Delete returns 200

Below is a test matrix for real applications:

| Test | Condition | Required outcome |
| --- | --- | --- |
| T1. Revoke exact credential | User has A, B; revoke A after step-up | Assertion with A rejected; B still logs in |
| T2. Revoke synced credential | A synced on two devices | Both copies of A rejected by RP; do not frame as single-device-only revocation |
| T3. Revoke wrong owner | Alice sends DELETE with Bob's credential ID | 403/404 per policy, Bob's credential stays active |
| T4. Unauthenticated/CSRF DELETE | Missing session or CSRF token | Rejected, registry unchanged |
| T5. Stale session after revoke | Session created before deleting A | Invalidated if incident policy requires; test old tokens separately |
| T6. Delete last credential | User only has A, no recovery | Self-service blocked/routed to controlled flow, no silent lockout |
| T7. Two concurrent DELETEs | User has A, B; each request deletes one ID | Database policy prevents zero-access state if policy requires |
| T8. Add passkey from stolen session | Old session without recent WebAuthn step-up | New registration denied |
| T9. Email/SMS bypass | Attacker controls only compromised email/SMS | Cannot escalate to full WebAuthn account if policy demands higher |
| T10. Recovery code replay | Same code sent in two requests | Exactly one claim succeeds; never two recovery sessions |
| T11. Recovery code brute force | Repeated wrong attempts from IP/account | Rate limiting/risk escalation without leaking account/code validity |
| T12. Newly changed recovery contact | Attacker changes email then requests recovery | Never uses new contact info to bypass proofing |
| T13. Device-bound lost | A on lost key, B on backup key | Use B to revoke A, register and test C |
| T14. Synced provider compromised | Provider compromised, user still has independent B | Revoke provider credentials, invalidate sessions, test B and re-enroll |
| T15. Multi-node | Revoke A on node 1, login with A on node 2 | Node 2 rejects within defined propagation threshold |
| T16. Session/token cleanup failure | Credential revoke OK, Redis/AS revoke fails | Do not declare full incident resolved; retry/audit/escalate |
| T17. Support impersonation | Operator submits ticket without proof | Cannot self-approve/swap passkey, audited clearly |
| T18. No registered authenticator | User lost all passkeys | Recovery follows assurance policy, never falls back to weak default passwords |
| T19. Passkey label spoofing | User sets label matching another device | Backend uses credential ID/owner, never labels for auth |
| T20. Backup flags | Credential `BE=1`/`BS=1`, `BE=0` | Accurate UX/risk handling; never assume exact copy list |
| T21. WebAuthn origin mismatch | Assertion from wrong origin/RP ID | Rejected, no bypass during recovery |
| T22. Notifications | Recovery success / credential added/deleted | Sent to pre-registered channels, zero secrets/private keys |

**Note on Spring Security tests:** `MockMvc` and `spring-security-test` can verify controller authorization/CSRF/sessions. Proving real WebAuthn ceremonies requires a WebAuthn-capable browser/virtual authenticator and the real backend validator, not just mocking `Authentication`. Testing cross-device, synced providers, and lost devices requires dedicated environments or clearly defined boundary simulations.

### 16.1. Typical end-to-end scenario

```text
Setup:
  Enroll A on phone (synced), B on hardware key (independent).
  Log in with A -> creates RP session S.

Incident:
  Phone reported stolen; assume attacker might use S.
  Safely sign in with B, verify step-up.
  Revoke A in RP repository.
  Invalidate S and risky sessions; revoke tokens per architecture.
  Register C on new device and verify assertion C.

Assertions:
  A -> login rejected.
  B -> login accepted.
  C -> login accepted after persistence.
  S -> no longer usable if incident policy requires invalidation.
  Raw private key -> never appears at RP.
  Credential A on provider -> may still exist locally, yet RP rejects it.
```

For high assurance, also test **recovery without B**: only policy-compliant proofing evidence leads to a restricted recovery session, then credential C; a one-step email must never bypass. Results must produce audits and notifications.

## 17. Operations, incident response, and practical responsibilities

### 17.1. Division of responsibilities

| Role | Responsibility |
| --- | --- |
| RP application | Stores public keys/credential IDs, verifies WebAuthn, revokes bindings, enforces authorization/step-up |
| Session/Identity backend | Tracks sessions, tokens, and active credential state across the entire cluster |
| Passkey provider | Protects/syncs private keys per policy; supports device lock/wipe and provider account recovery |
| User | Reports lost devices, safeguards backup authenticators/codes, verifies security alerts |
| Helpdesk | Handles tickets within narrow permissions, never bypasses proofing |
| Security/Identity team | Risk policies, recovery approvals, audits, alerts, incident containment |
| OAuth AS/RS (if any) | Revokes tokens, verifies active/expiry per contract, never infers from WebAuthn credential deletion |

### 17.2. Minimum audit log

An audit event should capture:

- Stable account ID (not necessarily email), tenant ID if applicable.
- Actor type (self-service, recovery operator, automated risk response).
- Action (`PASSKEY_ADDED`, `PASSKEY_REVOKED`, `RECOVERY_STARTED`, `RECOVERY_APPROVED`, `SESSIONS_INVALIDATED`).
- Timestamp, case/correlation ID, step-up/proofing method, result/reason code.
- Protected credential reference (if logged, consider a hash/pseudonymous ID; raw credential IDs are identifying data better not broadcast).
- Propagation status to authentication nodes/token stores when applicable.

**Never log** raw recovery codes, passwords, WebAuthn private keys (RP doesn't have them), full signed assertions, session cookies, or OAuth tokens. Restrict read access and retention of audit logs per privacy policy.

### 17.3. Remote device-locking methods

The OS/passkey provider may let users lock or wipe a device remotely. This is an **external** step beyond the RP that can reduce credential-usage risk, yet must never replace revoking the credential at the RP during a suspected incident; remote wipe execution may be uncertain (offline device). Conversely, once the RP revokes, the provider may retain local/synced passkeys until deleted locally.

### 17.4. State synchronization in distributed applications

In multi-node environments:

- Use a shared credential registry/persistence with atomic updates/revocations.
- If caching records for authentication, define a maximum cache invalidation lag; prefer failing closed when state is indeterminate.
- Alert when DB writes, session deletions, or token revocations fail or lag in propagating across nodes.
- Test rollbacks, schema migrations, and backup restores: never let an old backup "resurrect" a revoked credential. Tombstones or a revocation ledger can help enforce this.
- Execute credential deletion and "recovery restricted" state transitions inside transactions or explicit state workflows; never confuse partial success with completion.

## 18. Pre-production deployment checklist

1. **Inventory:** RP stores `credentialId → userHandle → publicKey` mappings, created/last-used/BE/BS state as appropriate; users view and manage credentials on a secured page.
2. **Pre-enroll:** encourage enrolling at least two independent methods, such as a backup security key; avoid treating two copies of one synced credential/provider as independent backups.
3. **Step-up:** adding/deleting passkeys and changing recovery settings require sufficiently strong recent authentication, policy-matching UV, CSRF, and owner authorization.
4. **Deletion:** in Spring Security 6.5.11, built-in `DELETE /webauthn/register/{id}` defaults to denied; configure an appropriate authorizer or build a protected custom endpoint. Never use `permitAll()`.
5. **Revoke semantics:** deleted credentials are rejected by the RP on every node; never promise remote deletion from devices or automatic session/token revocation.
6. **Device loss:** maintain runbooks for stolen, broken, device-bound, synced-provider compromise, and lost-all scenarios; define when to suspend immediately vs. letting the user replace via another safe passkey.
7. **Recovery assurance:** use saved codes/issued codes/contacts/identity proofing strictly per policy and risk. Never let password/SMS/email-link paths weaker than the account's protection tier grant full login automatically.
8. **Restricted recovery:** permit registering only a new credential after proofing, consume the approval once, verify a new assertion, and handle remaining credentials per policy.
9. **Session lifecycle:** invalidate suspect sessions, remember-me tokens, and OAuth tokens separately; test the RS/session store.
10. **Concurrency:** conditional deletes, atomic recovery code claims, last-credential handling, and cluster consistency.
11. **Notifications:** alert pre-registered channels on recovery/credential changes, with a mechanism to report unauthorized activity.
12. **Operational security:** separate helpdesk permissions, case approval/audit, anti-enumeration, rate limiting, monitoring, and breach playbooks.
13. **Versioning:** verify dependencies/DSL for your exact Spring Security version: 6.5 uses `spring-security-web` + WebAuthn4J, while 7.x has `spring-security-webauthn`; never copy incompatible configs.
14. **Tests:** include negative tests for owner checks, CSRF, recent step-up, BE/BS, revoked synced credentials, cluster caches, recovery code replay, session invalidation, and fake-helpdesk requests.

Design rule: **revoking a passkey at the RP only ends the right to use that credential ID/public key for new authentications.** Lost-device handling must also protect sessions, tokens, recovery methods, and the right to register new passkeys. An account is only as strong as **the weakest path an attacker can use to recover or replace an authenticator**.
