# formLogin, loginPage, and loginProcessingUrl

## Objectives

A form-based login page usually involves **two independent HTTP requests**: GET to view the form and POST to submit username/password. In Spring Security Servlet, three configuration methods have similar names but distinct responsibilities:

- `formLogin(...)` enables form authentication, wiring up the filter, entry point, manager, and handlers.
- `loginPage("/signin")` specifies **the URL that displays the login page**, usually via GET. When specifying a custom page, you **must create a controller/view** to render HTML.
- `loginProcessingUrl("/auth/login")` specifies **the POST URL where `UsernamePasswordAuthenticationFilter` receives credentials**. Normally the application **does not write a @PostMapping** for this URL.

By default, if form login is enabled without specifying a custom page, Spring Security can generate a page at `GET /login` and process `POST /login`. The path may look the same, but **the HTTP method, handling, and purpose are different**.

This lesson belongs to the **Form Login** group, module *Spring Security - authentication*, using Java 17+, Spring Boot 3.x, and Spring Security 6.x on Servlet. The main example runs with Spring MVC + Thymeleaf + BCrypt. WebFlux, JWT resource servers, and OIDC have different flows; do not apply this MVC form-login config verbatim to them.

After this lesson you will be able to:

1. Distinguish the generated login page, custom login page, and processing endpoint.
2. Trace a request from a protected resource to the login page, then credential submission, session creation, and redirect.
3. Write a `SecurityFilterChain` with distinct `loginPage` and `loginProcessingUrl`, synchronized with the HTML form.
4. Check `username`, `password`, CSRF token, success/failure URLs, saved requests, and logout.
5. Distinguish the login matcher, `securityMatcher` for chain selection, and `requestMatchers` for authorization.
6. Run a complete Java 17+ app and test valid/invalid login with MockMvc.
7. Troubleshoot 403, 404, redirect loops, wrong methods, and logins that succeed without persisting the session.

## 1. Reading the Three APIs by Responsibility

| Configuration | Role | Example request | Handling component |
| --- | --- | --- | --- |
| `formLogin(withDefaults())` | Enables form authentication | Default GET/POST login | Spring Security filters |
| `loginPage("/signin")` | Page that **displays** the form | `GET /signin` | Spring MVC controller + view/template |
| `loginProcessingUrl("/auth/login")` | **Processes** form credentials | `POST /auth/login` | `UsernamePasswordAuthenticationFilter` |
| `usernameParameter("username")` | Username field name | Form field `name="username"` | Filter reads request parameter |
| `passwordParameter("password")` | Password field name | Form field `name="password"` | Filter reads request parameter |
| `failureUrl("/signin?error")` | Page after authentication failure | GET after redirect | AuthenticationFailureHandler + MVC |
| `defaultSuccessUrl("/me", true)` | Fixed target page on success | GET after redirect | AuthenticationSuccessHandler |
| `form.permitAll()` | Grants public access to necessary form login URLs | Login page/processing/failure | Authorization rule, **does not disable CSRF** |

`loginPage` is **not** the password verification endpoint. `loginProcessingUrl` is **not** a template path. `formLogin` does **not replace** UserDetailsService/AuthenticationProvider configuration or authorization rules.

### 1.1. Defaults in Spring Security 6

Basic configuration:

~~~java
@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth ->
            auth.anyRequest().authenticated()
        )
        .formLogin(Customizer.withDefaults())
        .build();
}
~~~

This snippet is a fragment of a class with `@Bean`, `HttpSecurity`, `SecurityFilterChain`, and `Customizer` imports. When form login is enabled with typical defaults:

- `GET /login`: default login page generated by Spring Security.
- `POST /login`: filter processes username/password.
- Wrong credentials: typically redirects to `GET /login?error`.
- After logout: typically redirects to `GET /login?logout`.
- Username parameter: `username`.
- Password parameter: `password`.
- When accessing a protected URL unauthenticated: redirects to the login page.
- On login success: the success handler typically prioritizes the saved request, if present.

Note: once you declare your own `SecurityFilterChain`, **enable `formLogin` explicitly** if you want it; do not assume Spring Boot will always auto-configure every mechanism. A chain with a `securityMatcher` limiting paths may exclude `/login`, so the filter will not expose that endpoint.

### 1.2. Specifying a Custom Page Affects Related Defaults

~~~java
http.formLogin(form -> form
    .loginPage("/signin")
    .permitAll()
);
~~~

When specifying a custom `loginPage`, the generator is no longer responsible for rendering that page: you must provide an MVC route or another mechanism to return HTML. The `FormLoginConfigurer` Javadoc also explains that setting a custom page changes related defaults (processing/failure/logout). To keep the code clear and predictable, the example will **explicitly specify** `loginProcessingUrl`, `failureUrl`, and `logoutSuccessUrl` rather than relying on implicit defaults.

If you want the GET form and POST processing to share a path, you can set both `loginPage("/signin")` and `loginProcessingUrl("/signin")`. However, separating `GET /signin` and `POST /auth/login` clarifies the two responsibilities and makes debugging easier.

## 2. Request Processing Chain During Login

~~~text
Browser -> GET /me (unauthenticated)
          |
          v
FilterChainProxy / AuthorizationFilter
          |
          v
Access to /me denied
          |
          v
ExceptionTranslationFilter -> AuthenticationEntryPoint
          |
          v
302 /signin

Browser -> GET /signin
          |
          v
@Controller @GetMapping("/signin") -> signin.html
          |
          v
200 HTML with POST /auth/login form and CSRF token

Browser -> POST /auth/login
           username=alice&password=...&_csrf=...
          |
          v
CsrfFilter (if enabled) validates token
          |
          v
UsernamePasswordAuthenticationFilter
          |
          v
Unauthenticated UsernamePasswordAuthenticationToken
          |
          v
AuthenticationManager -> AuthenticationProvider
          |
          +-- UserDetailsService loads account
          +-- PasswordEncoder.matches(rawPassword, hash)
          +-- account-status checks
          |
          +-- FAILURE -> failure handler -> 302 /signin?error
          |
          +-- SUCCESS -> SecurityContext + session strategy
                         -> success handler -> 302 /me

Browser -> GET /me + session cookie
          |
          v
SecurityContext restored -> 200 account page
~~~

This is the logical Servlet flow; the exact filter order depends on the chain. `loginProcessingUrl` only controls whether the filter accepts credentials; it does not grant access permissions. CORS/CSRF can block the POST **before the authentication filter even checks the password**.

### 2.1. Role of the GET Page

`GET /signin` only **renders HTML**; it does not verify passwords. An MVC handler typically returns a view name:

~~~java
@Controller
class SigninPage {
    @GetMapping("/signin")
    String signin() {
        return "signin";
    }
}
~~~

This is a code fragment requiring imports and a `signin.html` template. Use `@Controller`, not `@RestController`, if you want the returned string resolved as a view name. Do not place passwords into the view model.

### 2.2. Why Does POST Not Need @PostMapping?

When the filter chain is configured properly:

~~~java
.formLogin(form -> form
    .loginPage("/signin")
    .loginProcessingUrl("/auth/login")
    .permitAll()
)
~~~

then `UsernamePasswordAuthenticationFilter` handles `POST /auth/login`. No `@PostMapping("/auth/login")` is needed in MVC. A POST controller that compares passwords manually and constructs an authenticated token from a username risks bypassing providers, account status checks, session fixation protection, and handlers.

For standard form login, delegate credential handling to Spring Security. Only write a custom filter/provider when requirements genuinely exceed the standard DSL and additional security responsibilities are clearly accounted for.

### 2.3. Sending the Wrong Method or URL

| Request | Is it a standard authentication attempt? | What happens next |
| --- | --- | --- |
| `GET /signin` | No | MVC renders form |
| `POST /auth/login` | Yes, if chain/filter matches | Authenticates or CSRF fails |
| `GET /auth/login` | No | MVC/authorization handles next |
| `POST /signin` | No if processing URL is `/auth/login` | May redirect, 404, or 405 |
| `OPTIONS /auth/login` | No | CORS preflight/rules |
| `POST /api/orders` | No | Business filter/controller |

Do not assume `GET /auth/login` must return 405; when the filter ignores it, authorization may redirect an anonymous user to `/signin` before the request ever reaches Spring MVC.

## 3. loginPage and Page Access Permissions

### 3.1. Why Does a Custom Page Need permitAll?

Misconfiguration:

~~~java
http
    .authorizeHttpRequests(auth ->
        auth.anyRequest().authenticated()
    )
    .formLogin(form ->
        form.loginPage("/signin")
    );
~~~

If `/signin` is subject to the `authenticated` rule, an anonymous GET `/me` redirects to `/signin`, and then GET `/signin` redirects to itself. The browser reports a redirect loop. The configuration should include:

~~~java
http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/signin", "/public").permitAll()
        .anyRequest().authenticated()
    )
    .formLogin(form -> form
        .loginPage("/signin")
        .loginProcessingUrl("/auth/login")
        .permitAll()
    );
~~~

`form.permitAll()` allows access to the necessary form login endpoints, but **does not disable** CSRF, security headers, or authentication filters. `permitAll("/**")` opens up the entire app; never use it to fix a redirect loop.

### 3.2. Open Public CSS/JS Only as Needed

If the page needs `/css/signin.css` or `/images/logo.svg`, you can add `requestMatchers("/css/**", "/images/**").permitAll()`. Do not open `/api/**` or private data just so the login page has styles. `permitAll` differs from `web.ignoring`: security filters can still execute under `permitAll`.

### 3.3. Generated Login Page Is Not a Custom Login Page

With `formLogin(withDefaults())`, Spring Security provides a default form. Once you set `loginPage("/signin")`, a custom page will not appear on its own unless the app has a controller/template. Do not configure a custom page while expecting the generator to serve the custom GET URL for you.

## 4. loginProcessingUrl, Form Fields, and CSRF

### 4.1. Form Action Must Match the Processing URL

With:

~~~java
.loginProcessingUrl("/auth/login")
~~~

Valid HTML requires:

~~~html
<form action="/auth/login" method="post">
    <input type="text" name="username">
    <input type="password" name="password">
    <button type="submit">Sign in</button>
</form>
~~~

The HTML above is **insufficient in a CSRF-enabled environment** and hardcodes the action at the root. In the Thymeleaf example below, `th:action="@{/auth/login}"` is used to include any context path properly while letting the Spring MVC/Thymeleaf integration emit the hidden CSRF input.

If the form POSTs to `/login` while the processing URL is `/auth/login`, the filter will not receive the credentials. Do not change the PasswordEncoder or write a duplicate POST controller to mask the bug; fix the form action URL.

### 4.2. Input Names Are the name Attribute

By default, the filter reads:

~~~text
username=alice
password=demo-pass
~~~

If you customize the DSL:

~~~java
.usernameParameter("loginId")
.passwordParameter("secret")
~~~

then the form must use `name="loginId"` and `name="secret"`. The `id` and `placeholder` attributes are only for HTML/UI and do not change request parameter names. Never log form bodies or put raw passwords in URLs/query strings.

### 4.3. Form Data Is Not JSON

`UsernamePasswordAuthenticationFilter` reads HTTP parameters by default, typically from `application/x-www-form-urlencoded`. If a frontend sends `Content-Type: application/json` with body:

~~~json
{"username":"alice","password":"demo-pass"}
~~~

then having the right processing URL **does not mean the filter parses JSON automatically**. JSON login requires a dedicated authentication converter/filter and response behavior. You cannot enable JSON simply by changing `loginProcessingUrl`.

### 4.4. CSRF Token Protects POST

Spring Security includes `CsrfFilter` to validate tokens on state-changing requests by default. A login POST with a missing or invalid CSRF token can return **403 Forbidden before the password is checked**.

Server-side HTML can use:

~~~html
<form th:action="@{/auth/login}" method="post">
    <input type="text" name="username">
    <input type="password" name="password">
    <button type="submit">Sign in</button>
</form>
~~~

With Thymeleaf + Spring MVC/Security integration, `th:action` uses `RequestDataValueProcessor` to add the hidden CSRF token when a CSRF request is active. If using another template engine, you must render the `CsrfToken` hidden field via a supported mechanism; do not arbitrarily disable CSRF globally.

The CSRF token must match the corresponding flow/request/cookie. A cURL POST sending only username/password can receive 403 even with a valid account and password. When testing in a browser, inspect the hidden token in rendered HTML and the session cookie in DevTools.

## 5. failureUrl, defaultSuccessUrl, and logoutSuccessUrl

### 5.1. Failed Login: Failure URL

~~~java
.failureUrl("/signin?error")
~~~

When the provider rejects credentials, the failure handler can redirect to this URL. The controller renders the signin page again, and the template shows a **generic** message. Do not disclose whether the username exists, whether the account is disabled, or internal status to unauthenticated users; rely on controlled internal auditing.

### 5.2. Successful Login: Saved Request or Fixed Target?

By default, Spring Security typically saves the URL an anonymous user tried to open:

~~~text
GET /orders -> 302 /signin
POST /auth/login -> successful authentication
-> GET /orders (if saved request is valid)
~~~

If you want to **always** go to `/me` for a deterministic example:

~~~java
.defaultSuccessUrl("/me", true)
~~~

The `true` flag forces a redirect to `/me` even if a saved request exists. In real apps, you can keep saved-request behavior or use `defaultSuccessUrl("/me")` without overriding saved requests. Never accept an unvalidated redirect URL from the client, as attackers can exploit open redirects.

### 5.3. Logout Is Separate from Login

Example:

~~~java
.logout(logout -> logout
    .logoutSuccessUrl("/signin?logout")
    .permitAll()
)
~~~

With CSRF enabled, real logouts are typically triggered via **POST /logout** with a CSRF token. Spring Security clears the session/context and redirects to the success URL; a custom login page can display a logout notice based on the query parameter. Do not use a GET logout link and disable CSRF just for navigation convenience.

### 6.2. Complete Java File

Create `src/main/java/com/example/demo/FormLoginDemoApplication.java`:

~~~java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class FormLoginDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(FormLoginDemoApplication.class, args);
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    UserDetailsService users(PasswordEncoder encoder) {
        UserDetails alice = User.withUsername("alice")
            .password(encoder.encode("demo-pass"))
            .roles("USER")
            .build();
        return new InMemoryUserDetailsManager(alice);
    }

    @Bean
    SecurityFilterChain security(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public", "/signin").permitAll()
                .requestMatchers("/admin").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .formLogin(form -> form
                .loginPage("/signin")
                .loginProcessingUrl("/auth/login")
                .failureUrl("/signin?error")
                .defaultSuccessUrl("/me", true)
                .permitAll()
            )
            .logout(logout -> logout
                .logoutSuccessUrl("/signin?logout")
                .permitAll()
            )
            .build();
    }

    @Controller
    static class Pages {
        @GetMapping("/signin")
        String signin() {
            return "signin";
        }

        @GetMapping("/me")
        String me(Authentication authentication, Model model) {
            model.addAttribute("username", authentication.getName());
            return "me";
        }
    }

    @RestController
    static class Resources {
        @GetMapping("/public")
        String open() {
            return "public";
        }

        @GetMapping("/admin")
        String admin() {
            return "admin";
        }
    }
}
~~~

Notable points:

- `formLogin` enables the authentication filter and redirect handlers.
- `loginPage("/signin")` requires a GET controller for the login page.
- `loginProcessingUrl("/auth/login")` is handled by the filter; do not write `@PostMapping("/auth/login")`.
- `failureUrl` and `logoutSuccessUrl` point to the custom page with query flags.
- `defaultSuccessUrl("/me", true)` makes the post-success destination deterministic.
- `form.permitAll()` ensures login-related URLs have public authorization, while `/me` requires authentication and `/admin` requires role ADMIN.
- Spring Security uses BCrypt to hash the demo password; the authentication provider verifies via the encoder rather than plaintext comparison.
- `@Controller` returns template names, while `@RestController` returns response bodies.

Do not use hardcoded passwords or unencrypted HTTP in production; this example is for running on localhost.

### 6.3. signin.html File

Create `src/main/resources/templates/signin.html`:

~~~html
<!DOCTYPE html>
~~~

### 6.5. Running and Observing

In the directory containing `pom.xml`:

~~~bash
./mvnw spring-boot:run
~~~

Windows PowerShell:

~~~powershell
.\mvnw.cmd spring-boot:run
~~~

Use a browser because the browser manages cookies and Thymeleaf renders CSRF:

1. `GET http://localhost:8080/public` → HTTP 200, body `public`.
2. `GET http://localhost:8080/me` while anonymous → redirects to `/signin`.
3. `GET /signin` → HTML page with form POST `/auth/login` and CSRF token.
4. Enter **alice / demo-pass**, submit → login succeeds, redirects to `/me`, page displays **Hello alice**.
5. `GET /admin` while logged in as Alice → HTTP **403** due to missing ROLE_ADMIN.
6. Log out using the button on `/me` → POST `/logout`, redirects to `/signin?logout`.
7. Access `/me` again → must log in again. An incognito browser does not share Alice's session cookie.
8. Try a wrong password → redirects to `/signin?error`; page displays a generic message.

If DevTools shows 200 on the final page after a redirect, inspect the Network waterfall to distinguish the 302 response from the login/filter from the GET 200 of the destination page.

### 7.2. Runnable JUnit 5 File

Create `src/test/java/com/example/demo/FormLoginDemoTest.java`:

~~~java
package com.example.demo;

import jakarta.servlet.http.HttpSession;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.mock.web.MockHttpSession;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.csrf;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest
@AutoConfigureMockMvc
class FormLoginDemoTest {

    @Autowired
    MockMvc mvc;

    @Test
    void publicAndSigninAreAccessible() throws Exception {
        mvc.perform(get("/public"))
            .andExpect(status().isOk())
            .andExpect(content().string("public"));

        mvc.perform(get("/signin"))
            .andExpect(status().isOk())
            .andExpect(view().name("signin"));
    }

    @Test
    void anonymousMustVisitCustomSignin() throws Exception {
        mvc.perform(get("/me"))
            .andExpect(status().is3xxRedirection())
            .andExpect(redirectedUrlPattern("**/signin"));
    }

    @Test
    void correctLoginPersistsSessionButNotAdminRole()
            throws Exception {
        MvcResult login = mvc.perform(
                post("/auth/login")
                    .with(csrf())
                    .param("username", "alice")
                    .param("password", "demo-pass")
            )
            .andExpect(status().is3xxRedirection())
            .andExpect(redirectedUrl("/me"))
            .andReturn();

        HttpSession session = login.getRequest().getSession(false);
        assertNotNull(session);

        MockHttpSession mockSession = (MockHttpSession) session;

        mvc.perform(get("/me").session(mockSession))
            .andExpect(status().isOk())
            .andExpect(view().name("me"))
            .andExpect(model().attribute("username", "alice"));

        mvc.perform(get("/admin").session(mockSession))
            .andExpect(status().isForbidden());
    }

    @Test
    void wrongPasswordRedirectsToFailure() throws Exception {
        mvc.perform(
                post("/auth/login")
                    .with(csrf())
                    .param("username", "alice")
                    .param("password", "wrong")
            )
            .andExpect(status().is3xxRedirection())
            .andExpect(redirectedUrl("/signin?error"));
    }

    @Test
    void missingCsrfIsForbidden() throws Exception {
        mvc.perform(
                post("/auth/login")
                    .param("username", "alice")
                    .param("password", "demo-pass")
            )
            .andExpect(status().isForbidden());
    }
}
~~~

The tests confirm that GET on the custom login page is allowed, anonymous users redirect to the custom page, valid credentials create a session with user role but not admin role, wrong passwords go to the failure page, and missing CSRF is rejected before authentication.

## 8. Saved Request, Form Action, and Login URL Across Multiple SecurityFilterChains

Spring Security has three levels of matchers that are easily confused:

| Matcher | Effect |
| --- | --- |
| `http.securityMatcher("/app/**")` | Does this chain handle the request? |
| `UsernamePasswordAuthenticationFilter` matcher from `loginProcessingUrl` | Does the filter attempt authentication on this URL/method? |
| `authorizeHttpRequests().requestMatchers("/admin").hasRole("ADMIN")` | Can a request that entered the chain access this resource? |

The following configuration is error-prone:

~~~java
http
    .securityMatcher("/app/**")
    .formLogin(form -> form
        .loginPage("/signin")
        .loginProcessingUrl("/auth/login")
    );
~~~

`/signin` and `/auth/login` do not fall under `/app/**`. This chain is not selected, so its login filter **cannot receive `POST /auth/login`**. Adding `permitAll("/auth/login")` inside the chain will not fix chain selection.

How to design it:

- Place the page and processing URLs in the same namespace, such as `/app/signin` and `/app/auth/login`, with unified controller/template paths.
- Or expand the chain's matcher in a controlled way using a `RequestMatcher` that covers the needed URLs, while keeping a catch-all chain to protect everything else.
- With multiple chains, specify `@Order` clearly. Spring Security picks the **first matching `SecurityFilterChain`**, rather than running all chains.

A saved request (`GET /orders` before login) is normally prioritized by the success handler unless you set `defaultSuccessUrl("/me", true)`. When using a custom success handler, validate both the saved request and redirect target to prevent open redirects.

## 9. Common Errors

| Symptom | Cause | How to check/fix |
| --- | --- | --- |
| `GET /signin` 404 | Missing controller or template | Create `@Controller @GetMapping` + `templates/signin.html` |
| GET returns plain text "signin" | Used `@RestController` instead of a view controller | Use `@Controller` |
| Redirect loop `/signin` | Login page protected by authenticated rule | `form.permitAll()` and accurate public rules |
| Form submits without authenticating | Action does not match processing URL | Align `th:action` and `loginProcessingUrl` |
| Form submits POST with wrong method/path | HTML method is GET or stale URL | Check browser Network tab |
| POST login returns 403 | Missing/invalid CSRF | Check token+session; do not blindly disable CSRF |
| Form POSTs JSON and login fails | Standard filter reads form parameters | Use a dedicated JSON converter/filter if needed |
| Changed `usernameParameter` and login fails | Input `name` does not match | Update both template and filter |
| Login succeeds but `/admin` 403 | User lacks ROLE_ADMIN | Debug authorization; do not change password |
| Login succeeds but next request is anonymous | Broken session/cookie/context persistence | Check repository, session policy, success flow |
| Has `JSESSIONID` yet still anonymous | Session does not necessarily hold Authentication | Inspect security context |
| Only `/app/**` prefix is protected | Processing/login URLs are outside the chain | Align chain matcher |
| Root action breaks under `/shop` deploy | Hardcoded `action="/auth/login"` | Use `th:action="@{/auth/login}"` |
| Default page disappeared | Custom `loginPage` replaced generator | Provide a custom GET view |
| Login filter runs twice | Custom filter registered in both container and security chain | Wire it only once |
| Logout succeeds but another tab stays logged in | Other token/session not revoked | Design appropriate logout/revocation |

### 9.1. Ordered Debugging Checklist

1. Use DevTools to inspect **HTTP method**, path, and response Location; do not look only at the final page.
2. Check which chain `FilterChainProxy` selects and whether the form-login filter is in that chain.
3. Verify `GET /signin` returns HTML from MVC, not plain text or a redirect loop.
4. Check that the final rendered form has POST `/auth/login`, `username`/`password` fields, and a hidden CSRF input.
5. If 403 happens before auth, inspect `CsrfFilter`, session/cookies, and CORS.
6. If it reaches the provider, check `UserDetailsService`, `PasswordEncoder`, and account status.
7. If login succeeds but a page refresh loses auth, check the session cookie, SecurityContextRepository, and session creation policy.
8. If authenticated yet getting 403 on admin, inspect authorities.
9. If logout does not clear the session, check the logout flow and token/session store.
10. Never log raw passwords, hashes, session cookies, CSRF tokens, or full Authentication objects.

## 10. Security Guarantees to Maintain

**HTTPS:** a form POST does not protect credentials from network eavesdropping over plain HTTP. Production requires TLS, appropriate Secure/HttpOnly/SameSite cookie flags, and never placing passwords in URLs/query strings.

**CSRF:** form login and logout in cookie-based apps require CSRF protection. Thymeleaf integrated with Spring MVC can auto-generate hidden tokens with `th:action`, but you must verify the rendered HTML in the real environment. `permitAll` does not exempt CSRF.

**Rate limiting and MFA:** `formLogin` does not inherently stop all password spraying or brute-force attacks. Combine multi-dimensional rate limiting, DoS-safe account lockout, MFA/passkeys where appropriate, monitoring, and controlled auditing.

**Do not leak account status:** `/signin?error` should display a generic error without revealing whether a user exists/is disabled/is locked to unauthenticated callers. Never echo raw credentials.

**Session fixation:** standard form login integrates a session authentication strategy. If you write a custom login handler and only call `SecurityContextHolder.setContext`, you risk omitting session fixation protection and Spring Security 6's explicit `saveContext`.

**Stored hash:** use an adaptive `PasswordEncoder` (BCrypt/Argon2id...) in the proper format; never store plaintext. A hash match is only the first step: authorization and account-status checks remain essential.

**XSS:** templates must use `th:text` to escape usernames, never rendering unescaped HTML from query errors or user input. XSS on the login page can leak credentials.

**Token/session revocation:** changing a role or disabling a user in the DB does not automatically destroy all existing authenticated sessions. Define session invalidation and token TTL/revocation policies appropriate to risk.

## 11. Exercises and Answers

**Question 1.** `formLogin` is enabled with defaults. Do `GET /login` and `POST /login` have the same effect?

**Answer:** no. GET displays the generated login page; POST receives credentials through the filter.

**Question 2.** You configured `loginPage("/signin")` without writing a controller/template. Why do anonymous users get 404?

**Answer:** Spring Security does not render HTML for a custom page on behalf of your app; a GET route and view are required.

**Question 3.** The HTML form POSTs to `/login` while `loginProcessingUrl("/auth/login")` is set. Why does login fail even with the right password?

**Answer:** the request hits the wrong processing URL; fix `th:action` instead of changing the provider or writing a custom login controller.

**Question 4.** A POST hits the right URL without CSRF and returns 403. Does that prove the password is wrong?

**Answer:** no. `CsrfFilter` can block the request before the login filter ever runs.

**Question 5.** Does returning `"signin"` from a `@RestController` render `signin.html`?

**Answer:** not with normal string-body return handling; use `@Controller` to return a view name.

**Question 6.** Why should the login page use `permitAll` even if the system requires authentication for most URLs?

**Answer:** anonymous users must be able to view the form and submit credentials. If the login page itself is blocked, a redirect loop can occur. `permitAll` does not open private resources.

**Question 7.** How does `defaultSuccessUrl("/me", true)` affect saved requests?

**Answer:** it forces a redirect to `/me` upon success, even if the user originally tried to access another protected page.

**Question 8.** Does `UsernamePasswordAuthenticationFilter` automatically parse a JSON login body?

**Answer:** no, not in the standard form-parameter implementation; a separate converter/filter is needed.

**Question 9.** `/admin` returns 403 after a successful login; is it related to `loginPage`?

**Answer:** usually no. The user is authenticated but lacks the authority required by the authorization rule.

**Question 10.** `http.securityMatcher("/app/**")` is set, while the login page and processing URL are at root. Does `form.permitAll()` fix chain selection?

**Answer:** no. Login endpoints must belong to the chain containing the authentication filter, or the chain matcher must be redesigned.

**Question 11.** Deployed under context path `/shop`, the form hardcodes action `/auth/login`. Why does the browser send the wrong URL?

**Answer:** a domain-root path omits the `/shop` context path; use `th:action="@{/auth/login}"`.

**Question 12.** Why shouldn't you skip CSRF for login/logout when using session cookies?

**Answer:** browsers automatically send cookies and can be tricked into issuing cross-site state-changing requests. Use tokens properly rather than disabling protection for test convenience.

## 12. Implementation Checklist

- [ ] `formLogin` is enabled in the right `SecurityFilterChain`.
- [ ] `loginPage` has a real GET controller/template and is accessible to anonymous users.
- [ ] `loginProcessingUrl` matches the form POST URL exactly; no redundant POST controller.
- [ ] Form uses POST method, matching parameter names, and a valid CSRF token.
- [ ] `failureUrl`, `logoutSuccessUrl`, and success/saved-request behavior align with the views.
- [ ] No redirect loop caused by requiring authentication on the login page.
- [ ] Did not open `permitAll` for the entire app just to make login work.
- [ ] Admin resources have dedicated authorization; login success does not imply full access.
- [ ] Context path, servlet path, reverse proxy, and static asset paths are tested.
- [ ] Multi-chain `securityMatcher` covers both the login page and processing endpoint; catch-all protection is present.
- [ ] BCrypt/PasswordEncoder matches stored password format; UserDetailsService does not authenticate by itself.
- [ ] HTTPS, rate limiting, MFA, CSRF, session fixation, and cookie policies are designed.
- [ ] Integration tests cover GET login, valid/invalid POST, missing CSRF, role 403, session persistence, and logout.
- [ ] No logging of raw credentials/hashes, CSRF tokens, or session cookies; never construct authenticated tokens blindly from client input.

**Conclusion:** `formLogin` enables form-based authentication; `loginPage` defines **the GET page displaying the form**; `loginProcessingUrl` defines **the POST URL where the filter receives credentials**. These settings must align with MVC views, HTML action/fields, CSRF, success/failure handlers, sessions, and `SecurityFilterChain` rules. Separating these responsibilities clearly allows you to diagnose 404 from a missing view, 403 from CSRF, redirect loops from missing `permitAll`, and authorization 403 after a successful login.
