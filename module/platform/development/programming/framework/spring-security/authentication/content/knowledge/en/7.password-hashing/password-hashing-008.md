# The {id}encodedPassword Format and Encoder Selection During Verification

A Spring Security application may have stored passwords using an older version of bcrypt, then raised the cost or gradually transitioned to a stronger algorithm. At login, the system must know **which algorithm produced the stored hash** in order to invoke the right password verifier. If it merely re-hashed the newly submitted password with the current algorithm and compared two strings, verification could fail — especially with algorithms using random salts.

Spring Security solves algorithm selection with **`DelegatingPasswordEncoder`** and the storage format:

~~~text
{id}encodedPassword
~~~

Here **`{id}`** is the label selecting a configured `PasswordEncoder`, while **`encodedPassword`** is the complete hash string generated by that encoder. When *creating a new hash*, `idForEncode` decides which encoder is used; when *verifying a stored hash*, **the ID read from the hash itself in the database** decides which encoder is invoked. Those two choices **do not have to be the same algorithm**.

This lesson belongs to the **Password Hashing** group of Spring Security Authentication. It focuses on the structure and parsing of the `{id}` prefix, `encode`/`matches` routing, factory and custom map configuration, unrecognized ID errors, legacy data conversion, `upgradeEncoding`, `DaoAuthenticationProvider` integration, testing, and a runnable Java 17 example.

## 1. Reading the {id}encodedPassword String Correctly

Illustrative examples:

~~~text
{bcrypt}$2a$12$.....................................................
{pbkdf2}...corresponding PBKDF2 data...
{scrypt}...corresponding scrypt data...
{argon2}...corresponding Argon2 data...
~~~

The `{` and `}` characters enclose the encoder ID label. Do not confuse them with `$2a$`, `$2b$`, cost, and salt **inside the bcrypt format**; those belong to the `encodedPassword` part and serve their own roles.

| Component | Example | What Is It Responsible For? |
|---|---|---|
| ID prefix | `{bcrypt}` | Selects the encoder registered under key `"bcrypt"` |
| Encoded part | `$2a$12$...` | Bcrypt hash with algorithm/cost/salt metadata in bcrypt's format |
| `idForEncode` | `"bcrypt"` | Selects the encoder for creating **new hashes** |
| `idToPasswordEncoder` map | `"bcrypt" → BCryptPasswordEncoder` | Only registered IDs can be selected during verification |
| `matches(raw, stored)` | `matches("guess", "{bcrypt}$2a$...")` | Extracts ID, picks delegate, verifies candidate password |

For example, given `{bcrypt}$2a$12$...`, Spring extracts ID `bcrypt`, finds the bcrypt encoder in the map, **strips the `{bcrypt}` part**, and passes `$2a$12$...` to `BCryptPasswordEncoder.matches(...)`. Bcrypt uses the salt and cost embedded in the hash to verify the newly submitted raw password.

### 1.1. The Prefix Is Not a Secret

`{bcrypt}` is not a password, salt, pepper, encryption key, or user identifier. It is **metadata** telling the program how to read the hash. Exposing the algorithm name does not break a sound password-hashing design; systems should never rely on hiding the algorithm as a security measure.

In the database, you should normally store the **entire string** `{id}encodedPassword` in the `password_hash` column; never strip the prefix when saving `encode` output. Salt/cost are managed by each encoder in its own format, so no manual splitting is needed when storing bcrypt.

### 1.2. Where Must the Prefix Be Located?

Under the default `DelegatingPasswordEncoder` configuration, the first character must be `{` and a closing `}` for the ID must be found. For instance:

~~~text
{bcrypt}$2a$12$...   -> id = "bcrypt"
$2a$12$...           -> id = null (no prefix)
 bcrypt}$2a$12$...   -> id = null (missing opening brace)
{unknown}...         -> id = "unknown" though no encoder may exist
{}...                -> id = "" (does not default to bcrypt)
~~~

Do not assume "seeing `$2a$` in the hash means the framework automatically picks bcrypt". **`DelegatingPasswordEncoder` selects by `{id}`**, rather than guessing algorithms from payload contents by trying every encoder. Some constructors allow customizing delimiters, yet the `{id}...` format is standard and should be applied consistently across application versions.

## 2. Two Independent Paths: encode and matches

### 2.1. Encode — Creating a New Password Hash

~~~text
rawPassword
    |
    v
DelegatingPasswordEncoder.encode(rawPassword)
    |
    +--> idForEncode = "bcrypt"
    +--> map["bcrypt"] = BCryptPasswordEncoder
    +--> bcrypt.encode(rawPassword)
    |
    v
"{bcrypt}" + bcryptEncodedPassword
~~~

Example:

~~~java
String raw = "Example!Pass123";
String stored = encoder.encode(raw);
~~~

This is a **code fragment**, assuming `encoder` is a `DelegatingPasswordEncoder` or suitable `PasswordEncoder`. If `idForEncode="bcrypt"`, the output normally starts with `{bcrypt}`. The remainder uses a random salt and is **not deterministic** across `encode` calls.

### 2.2. Matches — Checking Candidate Password Against Stored Hash

~~~text
rawPassword submitted at login
                       |
storedHash from DB ----+--> DelegatingPasswordEncoder.matches(raw, stored)
                                  |
                                  +--> Read id from storedHash
                                  +--> Look up encoder by id in map
                                  +--> Strip {id} from storedHash
                                  +--> delegate.matches(raw, encodedPart)
                                  |
                                  v
                              true / false
~~~

If a row stores `{pbkdf2}...` and the map has `pbkdf2`, Spring uses PBKDF2 to verify, **even when `idForEncode` for new hashes is `bcrypt`**. That is why an application can allow accounts created across multiple algorithm generations to log in validly.

The `PasswordEncoder` contract:

~~~java
public interface PasswordEncoder {
    String encode(CharSequence rawPassword);
    boolean matches(CharSequence rawPassword, String encodedPassword);
    default boolean upgradeEncoding(String encodedPassword) {
        return false;
    }
}
~~~

This is an **abbreviated API signature**, not a file to create yourself. `matches` does not decrypt the hash to recover the original raw password. The encoder uses the candidate raw password, salt, and stored parameters to compute/verify per the exact algorithm.

### 2.3. Why Not Re-encode and Call equals?

Wrong:

~~~java
boolean valid = encoder.encode(submittedPassword).equals(storedHash);
~~~

Right:

~~~java
boolean valid = encoder.matches(submittedPassword, storedHash);
~~~

With per-hash salted bcrypt/scrypt/Argon2/PBKDF2, `encode` generates a new string; two identical passwords do not yield identical hashes. Moreover, when legacy algorithms exist, current `encode` may use a **new algorithm** while stored hashes must be checked with an **old one**.

## 3. Creating DelegatingPasswordEncoder via Factory vs. Custom Map

### 3.1. Factory with Default Mappings

Spring Security provides:

~~~java
PasswordEncoder encoder =
        PasswordEncoderFactories.createDelegatingPasswordEncoder();
~~~

In Spring Security 6.x, the factory typically selects **bcrypt as the ID for new hashes** and includes compatibility mappings to read several older formats alongside bcrypt and newer algorithms. Specific mappings/versions can change across library releases; if a project needs to pin an approved set of algorithms, **check the API for your project's version and define an explicit map**.

Examples of IDs that have appeared in Spring Security versions:

| Illustrative ID | Encoder family | Notes |
|---|---|---|
| `bcrypt` | BCryptPasswordEncoder | Usually `idForEncode` of the Spring Security 6 factory |
| `pbkdf2` | Pbkdf2PasswordEncoder per pinned mapping | Parameters may depend on version |
| `pbkdf2@SpringSecurity_v5_8` | PBKDF2 config with version in ID | IDs can include `@`, not just letters |
| `scrypt` | SCryptPasswordEncoder | Multiple parameter generations mapped |
| `scrypt@SpringSecurity_v5_8` | Updated SCrypt parameter set | Enables verifying historical hashes |
| `argon2@SpringSecurity_v5_8` | Argon2PasswordEncoder per config version | May require extra crypto dependencies |
| `noop` | NoOpPasswordEncoder | **Does not hash or protect passwords**; only for controlled compatibility/tests/migration |
| `MD5`, `SHA-256`, or older labels | Legacy encoders | Never use to create new passwords in production |

**Security point:** having a decoder to *read historical hashes* differs from permitting it to *write new hashes*. With the factory, new passwords use `idForEncode`; however, factory support for legacy/noop is not an endorsement to use those algorithms. If your organization strictly bans plaintext/legacy formats, configure a controlled map or phase them out via migration and apply appropriate security policies.

### 3.2. Custom Map: Explicit Allowlist

`DelegatingPasswordEncoder` has the constructor:

~~~java
DelegatingPasswordEncoder(
        String idForEncode,
        Map<String, PasswordEncoder> idToPasswordEncoder)
~~~

Example inside a configuration class:

~~~java
Map<String, PasswordEncoder> supported = Map.of(
        "bcrypt", new BCryptPasswordEncoder(12),
        "bcrypt10", new BCryptPasswordEncoder(10));

PasswordEncoder encoder =
        new DelegatingPasswordEncoder("bcrypt", supported);
~~~

This Java snippet is **illustrative inside a file with declared imports**, not a standalone runnable program. With this map:

- `encode` creates new hashes prefixed `{bcrypt}`, using BCrypt cost 12.
- `matches` with `{bcrypt}...` uses the cost-12 encoder (bcrypt reads the actual cost from the stored hash itself).
- `matches` with `{bcrypt10}...` uses the encoder for the legacy alias.
- `{argon2}...` or `{noop}...` **are not accepted** because those IDs are absent from the map.
- The `"bcrypt10"` ID is an application-chosen label, not a mandatory factory built-in.

This is how you **restrict the readable encoder set** to migration needs. Ensure a mapping exists for `idForEncode`; invalid configurations fail fast rather than allowing unverifiable hashes to be saved.

### 3.3. Keep ID Semantics Immutable

If `"bcrypt"` previously pointed to bcrypt and you accidentally reassign `"bcrypt"` to another decoder, all `{bcrypt}` hashes may stop verifying. **An ID is a storage contract**, not merely a temporary alias for a Java class.

When an algorithm has multiple parameter profiles not self-described in the hash, use versioned IDs such as `pbkdf2@2026` instead of reassigning `pbkdf2` to a new config and breaking old hashes. ID naming must remain consistent across all nodes sharing a database; never relabel a row unless the underlying hash payload matches that algorithm.

## 4. Selecting an Encoder During Verification: Step-by-Step and ID Errors

Consider calling:

~~~java
boolean valid = delegating.matches(raw, storedPasswordHash);
~~~

The logical flow inside `DelegatingPasswordEncoder` is:

1. Extract `id` from the start of `storedPasswordHash` using the configured delimiters.
2. Look up the `PasswordEncoder` with key equal to `id` in the map.
3. If a delegate is found, take the **encoded portion** after the prefix and call `delegate.matches(raw, encodedPart)`.
4. If the delegate returns `true`, the candidate password matches the stored hash; if `false`, it does not.
5. If there is no ID or no mapping for that ID, by default it routes to **`UnmappedIdPasswordEncoder`** and throws **`IllegalArgumentException`**. This indicates a format/configuration error, not an ordinary "wrong password" answer.
6. Applications can configure a fallback via `setDefaultPasswordEncoderForMatches`, though doing so requires security review because it alters the semantics of missing/unrecognized IDs.

### 4.1. Concrete Cases

| `storedPasswordHash` | Extracted ID | If map supports only `bcrypt` and `bcrypt10` |
|---|---|---|
| `{bcrypt}$2a$12$...` | `bcrypt` | Invokes BCryptPasswordEncoder with encoded part |
| `{bcrypt10}$2a$10$...` | `bcrypt10` | Invokes legacy alias encoder |
| `$2a$10$...` | `null` | Throws `IllegalArgumentException` by default |
| `{foo}whatever` | `foo` | Throws `IllegalArgumentException` by default |
| `{noop}plain` | `noop` | Throws by default if map removed `noop` |
| `{bcrypt}not-a-bcrypt-hash` | `bcrypt` | Bcrypt delegate may return `false` or handle format error per implementation |
| `{bcrypt}...` with wrong raw password | `bcrypt` | `matches` returns `false` when encoded hash is valid |

Distinguish **password mismatch**, **corrupted hash**, **missing ID**, and **unsupported ID**. Do not hastily collapse everything into "wrong username" in server metrics, nor return raw stack traces or algorithms/hashes to the client.

### 4.2. Why Does "There is no PasswordEncoder mapped for the id null" Appear?

A database that stored bcrypt hashes before adopting delegating usually looks like:

~~~text
$2a$10$... (unprefixed bcrypt hash)
~~~

After switching to `DelegatingPasswordEncoder`, the program expects `{id}...`. Since the string begins with `$` rather than `{`, the extracted ID is `null`; by default it throws `IllegalArgumentException`.

**It is not that bcrypt hashes suddenly stopped being valid.** The issue is that the routing layer does not yet know which encoder owns the hash. Once you have proven that legacy rows are genuinely bcrypt, you can run a migration that **only prepends the matching prefix**:

~~~text
Before: $2a$10$<valid encoded bcrypt>
After : {bcrypt}$2a$10$<valid encoded bcrypt>
~~~

This is an **illustrative format**, not a valid hash to copy straight into a DB. In real migrations, preserve every byte of the encoded part; never rewrite salt, cost, or hash. Back up data, inventory legacy algorithms, test `matches` with known test credentials, and ensure the migration is idempotent.

### 4.3. What Risks Does Fallback Carry?

There is a method:

~~~java
delegating.setDefaultPasswordEncoderForMatches(fallbackEncoder);
~~~

It is invoked when no encoder is found for the ID. One critical API detail: **the fallback receives the entire original encoded string, including `{unknown}` if present**, rather than stripping the unrecognized prefix automatically. Therefore, if you must handle unprefixed legacy hashes, the fallback must know the exact allowed format, reject unrecognized prefixes, and never default to NoOp for arbitrary inputs.

A dangerous configuration:

~~~java
delegating.setDefaultPasswordEncoderForMatches(
        NoOpPasswordEncoder.getInstance());
~~~

That is an **anti-pattern**, never for production use. It risks turning ID-less values into plaintext comparisons or causing unexpected authentication behavior. If a transitional fallback is unavoidable, restrict it to a **verified legacy format** and remove it after migration; directly prefixing known-format hashes is usually cleaner and safer.

### 4.4. Note on Web-Layer Errors

`IllegalArgumentException` from an unmapped ID is not a `BadCredentialsException`. Inside `DaoAuthenticationProvider`, certain runtime configuration errors may not be translated into a standard 401 login error and may instead flow through different exception handling. Never rely on guessed HTTP behavior; test the exact exception type and mapping in your application version, log server incidents with a correlation ID, and return safe responses without exposing hashes or schemas.

## 5. Complete Java 17 Example: Multiple IDs, Proper Delegate, Migration, and Upgrade

This example uses **Spring Security Crypto/Core 6.3.8** and Gradle, requiring no Spring Boot or web server. The goal is seeing the difference between the **encoder creating new hashes** and the **encoder verifying historical hashes** via deterministic stdout lines independent of random salts.

We choose:

- `idForEncode = "bcrypt"` with cost-12 encoder.
- A second encoder with custom ID `"bcrypt10"`, representing historical hashes created with bcrypt cost 10.
- No `noop` or weak algorithm mapped in the test map.
- One raw password to generate both the new hash and the old hash. Never print real passwords or hashes to the console.

### 5.1. Project Structure

~~~text
delegating-password-demo/
├── settings.gradle
├── build.gradle
└── src/main/java/example/DelegatingPasswordDemo.java
~~~

`settings.gradle`:

~~~groovy
rootProject.name = 'delegating-password-demo'
~~~

`build.gradle`:

~~~groovy
plugins {
    id 'java'
    id 'application'
}

group = 'example'
version = '1.0'

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.springframework.security:spring-security-crypto:6.3.8'
    implementation 'org.springframework.security:spring-security-core:6.3.8'
}

application {
    mainClass = 'example.DelegatingPasswordDemo'
}
~~~

In real Spring Boot projects, versions are normally managed by Boot's dependency management. The example pins versions for API reference, requiring JDK 17+ and a compatible Gradle; the program runs no HTTP endpoints.

### 5.2. Complete Java File

Create `src/main/java/example/DelegatingPasswordDemo.java`:

~~~java
package example;

import java.util.Map;

import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.DelegatingPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

public final class DelegatingPasswordDemo {

    public static void main(String[] args) {
        String raw = "Example!Pass123";

        BCryptPasswordEncoder bcrypt12 =
                new BCryptPasswordEncoder(12);
        BCryptPasswordEncoder bcrypt10 =
                new BCryptPasswordEncoder(10);

        Map<String, PasswordEncoder> known = Map.of(
                "bcrypt", bcrypt12,
                "bcrypt10", bcrypt10);

        DelegatingPasswordEncoder delegating =
                new DelegatingPasswordEncoder("bcrypt", known);

        // New encode: idForEncode="bcrypt" => {bcrypt} + hash.
        String fresh = delegating.encode(raw);
        System.out.println("new prefix -> "
                + fresh.startsWith("{bcrypt}"));
        System.out.println("new correct -> "
                + delegating.matches(raw, fresh));
        System.out.println("new wrong -> "
                + delegating.matches("wrong-password", fresh));

        // Legacy hash generated separately, then tagged with a registered ID.
        String oldBcrypt = bcrypt10.encode(raw);
        String taggedLegacy = "{bcrypt10}" + oldBcrypt;

        System.out.println("legacy correct -> "
                + delegating.matches(raw, taggedLegacy));
        System.out.println("legacy needs upgrade -> "
                + delegating.upgradeEncoding(taggedLegacy));
        System.out.println("new needs upgrade -> "
                + delegating.upgradeEncoding(fresh));

        // No ID: does not guess from "$2a$..." by default.
        try {
            delegating.matches(raw, oldBcrypt);
            System.out.println("missing id -> unexpectedly accepted");
        } catch (IllegalArgumentException ex) {
            System.out.println("missing id -> "
                    + ex.getClass().getSimpleName());
        }

        // Unknown ID: no encoder in map.
        try {
            delegating.matches(raw, "{other}" + oldBcrypt);
            System.out.println("unknown id -> unexpectedly accepted");
        } catch (IllegalArgumentException ex) {
            System.out.println("unknown id -> "
                    + ex.getClass().getSimpleName());
        }

        // Spring Security 6.3 factory also uses {bcrypt} for new hashes.
        PasswordEncoder factory =
                PasswordEncoderFactories.createDelegatingPasswordEncoder();
        String factoryHash = factory.encode(raw);
        System.out.println("factory prefix -> "
                + factoryHash.startsWith("{bcrypt}"));
        System.out.println("factory verifies -> "
                + factory.matches(raw, factoryHash));
    }
}
~~~

The code uses a map with **two IDs** and one `DelegatingPasswordEncoder`. `"bcrypt10"` is a label we chose for the demo: it does not require a different bcrypt hash prefix; following `}` is the full bcrypt string. In both branches, bcrypt reads the actual cost from the encoded hash.

Do not test by comparing `fresh.equals(delegating.encode(raw))`, because two `encode` calls use random salts and yield no fixed string. The stdout lines test true/false semantics rather than printing hashes.

### 5.3. Run Command and Result

If a compatible Gradle Wrapper has been generated:

~~~bash
./gradlew run
~~~

If there is no wrapper yet but Gradle is installed, use `gradle run`. On Windows PowerShell with the wrapper, the command is typically `.\gradlew.bat run`.

Counting only the program's `System.out.println` lines:

~~~text
new prefix -> true
new correct -> true
new wrong -> false
legacy correct -> true
legacy needs upgrade -> true
new needs upgrade -> false
missing id -> IllegalArgumentException
unknown id -> IllegalArgumentException
factory prefix -> true
factory verifies -> true
~~~

Explanation:

1. `delegating.encode(raw)` uses `idForEncode="bcrypt"` and prepends `{bcrypt}`.
2. `matches(raw, fresh)` looks up `bcrypt` in the map and verifies true; wrong passwords return false.
3. `taggedLegacy` carries `{bcrypt10}`. Even though new hashes use `bcrypt`, old hashes still verify via the delegate labeled `bcrypt10`.
4. `upgradeEncoding(taggedLegacy)` returns true because the old ID differs from `idForEncode`, even though the raw password is still valid.
5. `upgradeEncoding(fresh)` returns false for a cost-12 bcrypt hash checked by a cost-12 bcrypt encoder. This matches expected behavior for the demo's implementation.
6. Unprefixed hashes and `{other}`-prefixed hashes are both unmapped, so `matches` throws `IllegalArgumentException` by default rather than merely returning false.
7. The default factory in Spring Security 6.3 generates new hashes with `{bcrypt}` and verifies them itself.

**Limitations of the example:** it does not connect `UserDetailsService` or handle HTTP, sessions, registration, databases, MFA, or password-hash update flows. Its focus is **hash format and routing to the right encoder**.

### 5.4. Variants to Test Comprehension

**Variant A:** change `"bcrypt10"` in the map to `"old-bcrypt"` without changing `taggedLegacy`'s prefix. `legacy correct` no longer verifies and instead throws `IllegalArgumentException` by default, because the stored ID and map ID do not match.

**Variant B:** change `idForEncode` to `"bcrypt10"` in the constructor. New hashes receive `{bcrypt10}`, even though the map still has cost-12 bcrypt. This demonstrates that **having a stronger encoder in the map does not automatically dictate the write algorithm**.

**Variant C:** add a mapping for another algorithm and create a hash with the matching ID; if the encoded part is valid, `matches` can verify it without changing `idForEncode`. Pick supported, version-appropriate algorithms during testing rather than randomly attaching another algorithm's ID to a bcrypt hash.

## 6. Integrating with DaoAuthenticationProvider in Spring Boot

In username/password login, `UserDetailsService` fetches `UserDetails` from the database, while `DaoAuthenticationProvider` calls `PasswordEncoder.matches(raw, storedHash)` to verify.

~~~text
HTTP login request
   |
   v
Authentication filter
   |
   v
DaoAuthenticationProvider
   +--> UserDetailsService.loadUserByUsername(username)
   |       -> UserDetails.password = "{bcrypt}..."
   |
   +--> delegatingPasswordEncoder.matches(raw, stored)
           +--> read id = "bcrypt"
           +--> map lookup for bcrypt
           +--> BCryptPasswordEncoder.matches(raw, encodedPart)
   |
   v
Authentication succeeds / AuthenticationException
~~~

Example beans in a Spring Boot app with Spring Security 6.3.x:

~~~java
@Configuration
class PasswordSecurityConfig {

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    AuthenticationProvider daoProvider(
            UserDetailsService userDetailsService,
            PasswordEncoder passwordEncoder) {
        DaoAuthenticationProvider provider =
                new DaoAuthenticationProvider();
        provider.setUserDetailsService(userDetailsService);
        provider.setPasswordEncoder(passwordEncoder);
        return provider;
    }
}
~~~

This is a **configuration snippet** in a Spring Boot 3.x app, not a standalone Java file. It requires imports for annotations, beans, classes, and a real `UserDetailsService`. Some newer versions of `DaoAuthenticationProvider` change recommended constructor usage; check JavaDocs for your deployed version.

`UserDetailsService` must return the **exact stored hash string**, including `{id}` when the DB uses delegating. Never strip the prefix before returning `UserDetails`, because the delegating encoder needs to see the prefix to pick the delegate.

### 6.1. Registration: Obtain Hash from the Encoder Bean Itself

~~~java
String encoded = passwordEncoder.encode(request.rawPassword());
account.setPasswordHash(encoded);
repository.save(account);
~~~

This is an **integration snippet**, assuming request/bean/repository and validation policies exist. You must store `encoded` intact, restrict DB access, and never return `passwordHash` over APIs. If the encoder bean is delegating, the ID-prefixed format must be preserved across ORM/DAO/backups/migrations.

### 6.2. Login: Do Not Hardcode Fixed Bcrypt

An anti-pattern:

~~~java
new BCryptPasswordEncoder().matches(raw, user.getPassword());
~~~

If `user.getPassword()` is `{bcrypt}$2a$...`, the value is not a raw plain bcrypt format so `BCryptPasswordEncoder` may reject it. With a DB also containing `{pbkdf2}...`, you obviously cannot use bcrypt for every row. Instead, use the **same delegating policy** in the verification flow so the encoder is selected by stored ID.

### 6.3. Do Not Confuse Encoder ID with accountId

The `{bcrypt}` ID only states the hashing algorithm, not the identity of the user logging in. `UserDetailsService`/the repository and login namespace identify the account, while the password encoder verifies that account's credentials. If login selects the wrong account due to duplicate usernames or wrong tenant scope, using the right encoder will not fix the identity bug.

## 7. Migrating Legacy Data: When to Only Add ID vs. When to Rehash?

### 7.1. Add ID Only When the Hash Algorithm Is Positively Verified

If you know for certain that a column previously stored **plain bcrypt hashes**, a migration can prepend `{bcrypt}` to the **intact hash**. This is a **metadata format change**; it needs no raw password and does not change the password the user must enter.

~~~text
OLD: $2a$10$...  (verified bcrypt)
NEW: {bcrypt}$2a$10$...
~~~

Notes:

- Apply only to rows **without a prefix** that genuinely match the bcrypt format.
- Never prepend `{bcrypt}` to SHA-256, Base64, plaintext, or already-prefixed hashes.
- Never prepend multiple times; migrations must be idempotent.
- Ensure the database column is wide enough to avoid truncating prefixes or entire hashes.
- Test against confirmed fixture/test credentials and measure login success rates before/after.
- If the DB holds multiple formats, group rows by data source and run dedicated adapters/migrations per group; **never assume every unprefixed row is bcrypt**.

### 7.2. Rehashing Replaces the Encoded Password, Not Just the Prefix

Suppose account A uses `{bcrypt10}...` while the new policy uses `{bcrypt}...`. At login:

1. `matches(rawPassword, storedHash)` uses the encoder for the old hash's ID.
2. If matched, evaluate `upgradeEncoding(storedHash)` per policy.
3. If an upgrade is needed, call `encode(rawPassword)` **using the write encoder**, obtaining a new hash with the new prefix.
4. Write the new hash to the DB inside a transaction with concurrency control.
5. Subsequent logins read the new ID and verify with the new encoder.

Never call `encode(storedHash)` to "upgrade" from an old hash. A one-way hash contains no plaintext to swap algorithms that way; doing so hashes the **hash string**, breaking the original password.

### 7.3. upgradeEncoding on DelegatingPasswordEncoder

`DelegatingPasswordEncoder.upgradeEncoding(storedHash)` can return true when the **stored ID differs from the current encode ID**, or when the active delegate sees its own hash parameters are outdated. With `BCryptPasswordEncoder`, a cost lower than the target config is one reason an upgrade may be needed.

However, this is a **signal**, not a DB write operation. Illustrative safe rehash rule:

~~~java
if (encoder.matches(rawPassword, storedHash)
        && encoder.upgradeEncoding(storedHash)) {
    String replacement = encoder.encode(rawPassword);
    // Write replacement via transaction/CAS or optimistic locking.
}
~~~

This snippet assumes variables are initialized and illustrates flow only. **Never rehash before `matches` succeeds.** If login and password reset run concurrently, a stale login request could overwrite the new password; use conditional updates like `WHERE id=? AND password_hash=?` or a version column.

### 7.4. Rolling Deploys and Multi-Node Mappings

When some nodes already write hashes with a new ID while older nodes do not yet recognize that ID, users can log in on new nodes and fail on old nodes. Safe rollouts typically follow this order:

1. Deploy the ability to **read** the new ID to every node.
2. Confirm both new and old nodes can `matches` both old and new hashes.
3. Switch `idForEncode` to **write new hashes**.
4. Monitor hash format error rates, upgrade rates, and login outcomes.
5. Remove legacy mappings only after data is rehashed/reset and no longer depends on them.

Coordinate across all services sharing the account database: other mobile/backend apps, batch workers, admin UIs, and login portals may all need to read the new hash format. Plan rollback handling in case an older node fails to read new hashes.

### 7.5. Real Data May Need Stronger Security Than "Automatic Compatibility"

If a system previously stored `{noop}plainPassword` or fast unsalted hashes, keeping weak encoders in the map indefinitely to preserve logins perpetuates risk. You may need forced password resets, disabling legacy logins, security notifications, incident reviews, or proactive migrations. **Compatibility is not a reason to let new passwords keep using weak encoders.**

## 8. Database Storage and Data Constraints

An illustrative PostgreSQL table:

~~~sql
CREATE TABLE account_credentials (
    account_id    UUID PRIMARY KEY,
    password_hash TEXT NOT NULL,
    changed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
~~~

A `TEXT` column prevents hash truncation when algorithms/prefixes change; a properly sized `varchar` works too if required by the system. **Never** place a unique constraint on `password_hash`: two users can pick the same password while random salts yield different hashes; never use hashes as identifiers or to detect duplicate passwords across users.

Never run SQL `LOWER(password_hash)`, `TRIM(password_hash)`, or alter case in the encoded data: hashes/IDs have strict semantics and hashes are **case-sensitive**. Stripping `{`, `}` or mis-escaping during CSV/JSON exports can corrupt encoder routing.

A sensible migration audit might track:

~~~text
Total credential rows
Rows tagged with {bcrypt}
Rows tagged with legacy IDs
Rows missing an ID
Rows with IDs outside the allowlist
Rows that are null/empty/schema-mismatched
Rows rehashed per deployment release
~~~

Never record raw encoded hashes or raw passwords in dashboards, logs, or migration reports. Only store **counts**, approved ID categories, and operational event codes sufficient for troubleshooting. Hashes remain sensitive data vulnerable to offline attacks if leaked.

## 9. Security Boundary: IDs May Be Read, Never Trusted Unconditionally

The `{id}` prefix resides in stored data. Every ID must be resolved through an **allowlisted map**. Never design code like:

~~~java
String className = userSuppliedId;
Class<?> encoderType = Class.forName(className);
// Creating an arbitrary encoder decided by the client.
~~~

This is an **anti-pattern**, not a standalone runnable program. Hash-routing IDs must never select arbitrary Java classes, execute code, or dynamically instantiate algorithms outside an allowlist.

Never read the encoder ID directly from a login request to decide which algorithm verifies the raw password. The legitimate ID is metadata on the **stored hash for that account**; attackers must never write `password_hash` or alter IDs directly. Still, if an attacker can modify the DB, they can compromise credentials in many ways; input validation and write authorization on account credentials must remain guarded.

### 9.1. Do Not Use {noop} in Production Data

`{noop}password` means the encoded part **equals the plaintext password** when the map permits NoOp. It exists strictly for testing/special compatibility, not as a password protection algorithm. If real `{noop}` rows exist in the DB, that is a plaintext storage exposure to resolve via incident/migration policy, not left mapped forever because "login still works".

### 9.2. Do Not Use Secret Homemade Algorithms Instead of Strong Password Hashes

Sometimes people consider creating a `{custom}` ID with a homemade algorithm. Custom cryptographic schemes risk offline attacks, weak entropy, insufficient salt/cost, and non-standard migrations. Prefer vetted password KDFs such as Argon2id, scrypt, bcrypt, or PBKDF2 with approved parameters, depending on system/compliance needs.

**Pepper** is a secret managed separately from the database, distinct from `{id}` and salt. If adding pepper, establish explicit key management and versioning; an encoder ID can help select the verification profile, yet never put plaintext pepper inside the ID, hash, code, or logs.

### 9.3. Encoding Is Not Encryption

The `{bcrypt}` prefix has nothing to do with Base64 decoding to recover passwords. `PasswordEncoder.matches` verifies candidates; it does not decrypt plaintext. If a system must recover an API secret to send to a third party, that is a separate **authenticated encryption** and key management problem. Storing user passwords with reversible encryption just to "read them back if forgotten" violates password storage goals.

## 10. Error Handling, Operational Observability, and Common Scenarios

### 10.1. Quick Diagnostic Table

| Symptom | Likely Cause | How to Handle |
|---|---|---|
| `There is no PasswordEncoder mapped for the id "null"` | Old hash lacks `{id}` | Inventory formats; prepend **accurate algorithm prefix** or migrate |
| ID is `bcrypt` yet `matches` always false | Wrong raw password, truncated hash, or wrong encoder/data format | Use test fixtures and verify hashes are not mutated/trimmed |
| `{unknown}...` triggers `IllegalArgumentException` | ID absent from map | Check migration/compatibility; never open a permissive fallback |
| `{bcrypt}{bcrypt}$2a$...` fails verification | Prefix prepended twice | Make migrations idempotent; repair corrupted data safely |
| New `{bcrypt}` hashes fail on old nodes | Old nodes lack the mapping/version | Deploy read compatibility before switching writes |
| Login fails right after password reset | Reset used a different encoder without prefix | Share one policy for writing/reading encoded passwords |
| `NoOpPasswordEncoder` logs users in with plaintext | Weak/legacy config | Stop writing weak hashes; execute resets and migrations |
| `upgradeEncoding` always true for legacy ID | ID differs from `idForEncode` | Upgrade after valid login; never rehash unverified raw input |
| `encode(raw)` equals DB hash returns false | Random salt / different mapping | Use `matches(raw,stored)` |
| `UserDetails` password hash becomes null after login | Credential erasure mutates shared object | Separate principal from cache; do not disable erasure blindly |
| Unmapped ID exception returns 500 stack trace | Config errors not distinguished from bad credentials | Log safely; handle operational errors and unify public responses |
| Changed bcrypt cost yet new/stored hashes differ | Hash embeds its own cost; config changed | Check `upgradeEncoding` and cost-upgrade roadmap |

### 10.2. Logging Rules

Never log raw passwords, hashes, reset tokens, or full `Authentication` objects on errors. You may log an **internal error code** such as `PASSWORD_HASH_ID_UNMAPPED`, a request correlation ID, application version, and normalized/allowlisted ID (if policy permits), avoiding dumping arbitrary DB strings containing sensitive data.

If an unrecognized ID suddenly appears after a deploy, it may signal a migration bug, schema corruption, or version skew across nodes. Never silently let login succeed; fail closed and raise actionable alerts.

### 10.3. Nonexistent Account Differs from Unreadable Hash ID

`UserDetailsService.loadUserByUsername` may throw `UsernameNotFoundException` when an account does not exist. `DaoAuthenticationProvider` usually masks nonexistent-user errors as `BadCredentialsException`. Yet when an account exists and its hash has an unmapped ID, that is a **credential format/configuration issue**, not "account does not exist".

In public responses, keep messages uniform to avoid leaking account existence; in internal observability, separate root causes so operations teams do not "fix" a config bug by mistakenly resetting everyone's passwords.

## 11. Complete Test Suite for Encoder Routing

Test across at least three layers: **encoder unit tests**, **`UserDetailsService`/`DaoAuthenticationProvider` integration tests**, and **migration/rolling-deploy tests** on realistic fixtures.

| Scenario | What Must Be Proven |
|---|---|
| `encode(raw)` with current ID | Returns `{idForEncode}...` and `matches(raw, encoded) == true` |
| Different raw password | `matches` returns `false` against a valid hash |
| Hash with mapped legacy ID | Legacy delegate is chosen; valid password still verifies |
| Hash with unmapped ID | Throws `IllegalArgumentException` by default |
| Unprefixed hash | Does not guess an encoder unless a fallback is configured |
| Prefix not at start / missing `}` | Never accepted as a valid hash |
| Truncated bcrypt payload in DB | Does not falsely authenticate; raises schema/data alert |
| Same raw encoded twice | Both verify via `matches`; never compare two hashes with `equals` |
| `upgradeEncoding` on legacy ID | Upgrade signal aligns with `idForEncode` |
| `upgradeEncoding` on fresh hash | Does not request upgrade when current policy is satisfied |
| Rehash after valid `matches` | New hash uses current algorithm and still verifies old password |
| Concurrent rehash and reset | Does not overwrite the newly changed password |
| Registration and password reset | Share the same encoded format/prefix from encoder bean |
| Two nodes reading the same DB | Share the same ID allowlist with no version skew |
| Old node in rolling deploy | Can read new ID before switching to write new hashes |
| Factory's legacy `noop` mapping | Never creates new plaintext or retains it long-term in prod |
| DB with multiple legacy hash types | Migration classifies cohorts cleanly without mislabeling prefixes |
| Hash with crafted spoofed ID | Never picks an encoder outside allowlist; never issues auth token |
| HTTP login with malformed hash | Leaks no hash, SQL schema, or stack trace in response |
| Cached `UserDetails` | Does not corrupt encoded part when credentials are erased after login |

### 11.1. Self-Review Questions

**Question 1.** What is `{bcrypt}` in `{bcrypt}$2a$12$...` used for?  
**Answer:** It selects the `PasswordEncoder` by ID; the remainder is the encoded bcrypt hash containing algorithm/cost/salt metadata in bcrypt format.

**Question 2.** Does `idForEncode="bcrypt"` force all old passwords to use bcrypt at login?  
**Answer:** No. `matches` picks the delegate based on the **ID in the stored hash**; `idForEncode` only determines the algorithm for **writing new hashes**.

**Question 3.** Why does a legacy `$2a$...` bcrypt hash cause a null ID error?  
**Answer:** Because `{id}` is missing at the start. `DelegatingPasswordEncoder` does not infer bcrypt from the `$2a$` prefix by default.

**Question 4.** Can you prepend `{bcrypt}` to a SHA-256 string to "convert it to bcrypt"?  
**Answer:** No. The prefix only selects the decoder; it does not transform the underlying data.

**Question 5.** When is prepending a prefix without plaintext passwords valid?  
**Answer:** When you have **positively verified** each legacy hash belongs to that exact algorithm and only lacks ID metadata. The encoded part must remain intact.

**Question 6.** When must you rehash?  
**Answer:** After the candidate password succeeds in `matches` and policy requires an upgrade; call `encode(raw)` with the new encoder and update the DB safely.

**Question 7.** Does `setDefaultPasswordEncoderForMatches` strip unknown prefixes before calling the fallback?  
**Answer:** No. The fallback receives the entire original encoded string, including any unrecognized prefix, so it must be designed carefully.

**Question 8.** Is `{noop}` a good way to temporarily bypass null ID errors?  
**Answer:** No. It compares plaintext and risks keeping weak credentials; migrate explicitly based on inventoried formats instead.

**Question 9.** Why can an older node fail logins after a newer node changes `idForEncode`?  
**Answer:** The older node lacks a decoder mapping for the new ID in the DB. Deploy read capability before write capability.

## 12. Pre-Production Checklist

- [ ] Choose the algorithm/password KDF for **new** hashes, set `idForEncode` accurately, and benchmark work factor.
- [ ] Inventory all hash IDs/formats currently in the database, including unprefixed rows and legacy IDs.
- [ ] Ensure the ID → `PasswordEncoder` map is controlled, versioned, and uniform across nodes.
- [ ] Store the full `{id}encodedPassword` without stripping prefix, salt, or cost; pick a sufficiently wide column.
- [ ] Registration, password change/reset, and login use the **same encoder policy**.
- [ ] For `matches`, the ID comes from the stored hash, never from the client request.
- [ ] Missing/unrecognized IDs must not default to plaintext or reflexively fall back to NoOp.
- [ ] If migrating unprefixed hashes, prepend IDs **only after confirming the exact algorithm**.
- [ ] When upgrading, verify raw input first, use `upgradeEncoding`, and enforce CAS/optimistic locking against reset overwrites.
- [ ] Deploy new decoders to all nodes before switching `idForEncode` for new writes.
- [ ] Test old/new IDs, unmapped IDs, malformed hashes, bcrypt costs, and concurrent updates.
- [ ] Never store new `{noop}` plaintext or keep weak legacy decoders alive longer than needed.
- [ ] Never expose raw passwords/hashes/exception internals in responses or logs.
- [ ] Verify `DaoAuthenticationProvider` actually uses the chosen encoder bean and `UserDetailsService` returns the exact stored hash.
- [ ] Monitor unmapped ID errors, rehash rates, login success/failure, and rolling-deploy anomalies.

**Remember:** `{id}encodedPassword` is the **storage format contract** enabling Spring Security to **read multiple generations of hashes with matching encoders**, whereas `idForEncode` specifies the **algorithm for new writes**. Keeping those two decisions separate, alongside safe migrations and controlled maps, is the foundation for updating password-hashing policies without locking users out of their accounts.
