# encode, matches, and upgradeEncoding in Spring Security PasswordEncoder

> **Context:** Spring Security – authentication, **Password Hashing** group. This lesson clarifies the three `PasswordEncoder` methods `encode`, `matches`, and `upgradeEncoding`, how they are used across the account lifecycle, BCrypt/`DelegatingPasswordEncoder` mechanics, and how to safely upgrade hashes after a successful authentication using `DaoAuthenticationProvider` together with `UserDetailsPasswordService`. Examples target Java 17+ and Spring Boot Servlet.

## 1. Three Methods Serving Three Different Questions

Plaintext passwords should not be stored in the database. The server stores a **password hash** generated by a dedicated algorithm with a salt and work factor, such as BCrypt. When a user logs in, the system must verify the client-provided password against this hash without being able to "decrypt" the hash back into the original password.

The three methods of `PasswordEncoder` correspond to three moments in time:

| Method | Question | When |
| --- | --- | --- |
| `encode(raw)` | How do we create a new hash to store under the current policy? | Creating/changing/resetting a password; rehashing after valid authentication |
| `matches(raw, encoded)` | Does the password just provided by the caller match the stored hash? | During authentication |
| `upgradeEncoding(encoded)` | Does the stored hash need to be regenerated with the current algorithm/cost? | Evaluating migration after obtaining the correct password |

Diagram:

```text
REGISTRATION / PASSWORD CHANGE
    new raw password
         |
         v
    PasswordEncoder.encode(...)
         |
         v
    hash stored in account repository

LOGIN
    raw password from client + hash from DB
         |
         v
    PasswordEncoder.matches(...)
       |                |
     FALSE             TRUE
       |                |
    Reject        Other authentication checks
                        |
                   All succeeded?
                     |        |
                    No       Yes
                     |        |
                  Reject      v
                        upgradeEncoding(stored)?
                            |           |
                          false       true
                            |           |
                         keep hash   encode(verified raw)
                                        |
                                        v
                                 write new hash safely
```

**Never generate a new hash from an incorrect password**, because that could turn an attacker's failed login attempt into a password change on the victim's account.

## 2. Exact API Contract

The `org.springframework.security.crypto.password.PasswordEncoder` interface has these primary methods:

```java
String encode(CharSequence rawPassword);

boolean matches(CharSequence rawPassword, String encodedPassword);

default boolean upgradeEncoding(String encodedPassword) {
    return false;
}
```

This is a **condensed API shape for explanation**, not a file you need to define yourself. In some versions, the API also declares nullability annotations; follow the contract of the version you use.

- `encode` takes a new plaintext password and returns a storable **encoded string**.
- `matches` takes **plaintext first, stored hash second**; a valid result is a boolean.
- `upgradeEncoding` only takes the hash, **not the plaintext**, so it cannot verify credentials or rehash by itself.
- The default implementation of `upgradeEncoding` on the interface returns `false`; specific encoders may override it.
- `upgradeEncoding=false` does not mean every hash is sufficiently secure against all standards. It only expresses the upgrade policy of the encoder currently in use.
- When a hash is malformed or its id is unsupported, implementations may return false or throw an exception; do not treat every anomalous input as an ordinary failed login without proper handling.

The name `matches` means checking for a match, **not** directly comparing two plaintext strings. PasswordEncoder also handles the salt/format/hash work factor according to its algorithm.

## 3. encode: Creating a Password Hash to Store

BCrypt is a common example of password hashing with salt and cost. If choosing strength 12:

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

PasswordEncoder encoder = new BCryptPasswordEncoder(12);
String storedHash = encoder.encode("correct-horse");
```

This is a **code snippet used inside a method** of an application with the Spring Security Crypto dependency; not a standalone Java program with `main`.

An actual BCrypt hash looks similar to:

```text
$2a$12$[generated salt and hash portion]
```

The bracketed portion is only for describing the shape, **not a valid BCrypt hash**. Do not use it as a real encoded password in a demo. The parameter `12` is the cost recorded inside the hash; it is not the password length or the number of salt characters.

### Why Does Hashing Twice Usually Produce Different Results?

With a random salt, even for identical plaintext, two `encode` calls usually produce different outputs:

```java
String h1 = encoder.encode("correct-horse");
String h2 = encoder.encode("correct-horse");

System.out.println(h1.equals(h2)); // usually false
System.out.println(encoder.matches("correct-horse", h1)); // true
System.out.println(encoder.matches("correct-horse", h2)); // true
```

The two `matches` lines are predictable outcomes when the encoder and hashes are valid. The `equals` line is "usually false" because of the random salt; do not write an absolute assertion claiming two random salts can **never** collide.

For this reason, the following approach is **wrong**:

```java
// WRONG: BCrypt re-encoding usually produces a different salt.
boolean accepted =
        encoder.encode(presentedPassword).equals(storedHash);
```

`presentedPassword` and `storedHash` here are illustrative variables. To check whether a raw password matches an old hash, always use `matches`.

### Do Not Confuse Password Hashing with Plain Digests

Plain `SHA-256(password)` or `MD5(password)` is very fast and unsuitable as a modern password storage mechanism. Purpose-built password hashing uses a salt and tunable computational cost, helping slow down offline password guessing if the hash store is leaked. Storing hashes properly still needs to be paired with HTTPS, rate limiting, MFA, DB protection, backups, logs, and compromised-credential handling procedures.

## 4. matches: Verifying the Password Is Not Enough to Conclude Login Succeeded

`matches` takes:

1. `rawPassword` – the password string presented by the caller over the authentication channel.
2. `encodedPassword` – the hash loaded by the server from a trusted identity source.

Example:

```java
String stored = encoder.encode("s3cret");

System.out.println(encoder.matches("s3cret", stored)); // true
System.out.println(encoder.matches("wrong", stored));  // false
```

The snippet above is a code fragment assuming an already initialized `encoder` variable, not a standalone runnable Java file.

### The Two Parameters Are Not Interchangeable

`matches(storedHash, rawPassword)` is not a valid equivalent to `matches(rawPassword, storedHash)`. The hash must be in the second parameter so the encoder can identify the format, salt, and cost.

Do not manually extract the salt and rehash using a homemade formula. With BCrypt, the encoder object takes the stored hash string and performs the appropriate verification.

### matches=true Does Not Mean Login Is Permitted

Spring Security still must check other conditions, such as `UserDetails.isEnabled()`, `isAccountNonLocked()`, `isAccountNonExpired()`, `isCredentialsNonExpired()`, or other authentication policies.

```text
UserDetailsService -> UserDetails(passwordHash, status, authorities)
                              |
                              v
                    DaoAuthenticationProvider
                      |          |
                      |          +-- PasswordEncoder.matches
                      +-- Account status checks
                              |
                              v
                  Authentication succeeds if valid
```

A locked account may have the right password, yet `DaoAuthenticationProvider` still refuses to issue an authenticated token. Do not use `matches=true` alone to grant access or bypass account status.

If using standard form login/HTTP Basic, let `AuthenticationManager`/`DaoAuthenticationProvider` call `matches` rather than writing a custom `/login` controller that calls `matches` and mints a trusted `Authentication` yourself. Custom code easily bypasses multiple safeguards built into the framework.

## 5. upgradeEncoding: Detecting When Rehashing Is Needed

`upgradeEncoding(storedHash)` only inspects the old hash and the encoder's current policy. It returns `true` when the implementation determines the hash should be regenerated under the new policy. It **does not perform rehashing, does not update the database, and does not verify the password**.

With BCrypt, one concrete criterion is cost: when the stored BCrypt cost is lower than the current `BCryptPasswordEncoder` strength, `upgradeEncoding` returns `true`.

Example:

```java
PasswordEncoder previous = new BCryptPasswordEncoder(8);
PasswordEncoder current = new BCryptPasswordEncoder(12);

String oldHash = previous.encode("s3cret");

System.out.println(current.matches("s3cret", oldHash)); // true
System.out.println(current.upgradeEncoding(oldHash));   // true

String newHash = current.encode("s3cret");

System.out.println(current.matches("s3cret", newHash)); // true
System.out.println(current.upgradeEncoding(newHash));   // false
```

This is a **code snippet used inside a method** with appropriate imports. Even though `current` uses cost 12, it still reads the cost/salt metadata inside the cost-8 BCrypt hash to verify the credential. After rehashing with cost 12, the check no longer requests an upgrade because the cost meets the current policy.

### Cost Is Non-Linear

BCrypt's work factor grows exponentially. Going from cost 8 to 12 does not just add four operations; it makes the workload significantly larger. Therefore, higher costs can increase login latency and CPU load. Choose cost based on benchmarks and performance budgets, not by picking the maximum value intuitively.

### If upgradeEncoding Is Not Overridden

If a custom `PasswordEncoder` only implements `encode` and `matches`, the default `upgradeEncoding` returns false. This does not prove the custom encoder has a proper migration strategy. You must actively design and test how legacy hashes are detected.

### Why Must We Wait for Valid Authentication?

Suppose user An has hash H1. An attacker sends password `wrong`, the application sees H1 needs an upgrade, and then runs `encode("wrong")` and updates the DB. The attacker has replaced An's password with one they know **without ever authenticating successfully**. That is a severe privilege compromise bug. A `upgradeEncoding=true` signal **must never permit** an update when `matches` or another authentication step fails.

## 6. Three-Method Matrix by Use Case

| Use Case | `encode` | `matches` | `upgradeEncoding` |
| --- | --- | --- | --- |
| User registration | Hash new password | No old hash needed | Not needed since new policy is already used |
| Correct login | Used when lazy rehashing is needed | **Yes** | Evaluates existing hash |
| Incorrect login | Must not persist wrong password | **Yes**, returns mismatch | Does not trigger migration |
| Password change | Hash new password | May verify old password | No need to rehash old password before changing |
| Password reset via valid token | Hash new password | Old raw password may be absent | No need to rehash old hash |
| Increasing BCrypt cost | Rehash upon successful authentication | Still verifies old hash | Evaluates old cost lower than current cost |
| Algorithm transition | Create hash with new algorithm | Converter/delegating verifies permitted old hash | Detects id/cost needing change |
| JWT bearer request | No internal plaintext password | Typically unused | Do not attempt upgrade on every bearer request |

With JWT, OIDC, and SSO, the application may never receive the user's plaintext password. Never attempt to "migrate" hashes merely by inspecting token claims. If a user needs to change their password, that belongs to the password-managing identity service or a separate verification flow.

## 7. DelegatingPasswordEncoder and the {id} Format

Long-lived systems may contain multiple generations of password hashes. `DelegatingPasswordEncoder` identifies the algorithm based on a prefix at the start of the stored hash:

```text
{id}encodedPassword

Shape examples:
{bcrypt}$2a$12$...               (prefixed BCrypt hash)
{pbkdf2}...                      (prefixed PBKDF2 hash)
{scrypt}...                      (prefixed SCrypt hash)
```

Strings with ellipses are **format descriptions only**, not valid hashes. `idForEncode` is the id used to create new hashes; `matches` uses the id present in the stored hash to pick the corresponding encoder.

### Default Factory

```java
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

PasswordEncoder encoder =
        PasswordEncoderFactories.createDelegatingPasswordEncoder();

String encoded = encoder.encode("correct-horse");

System.out.println(encoded.startsWith("{bcrypt}")); // true with default factory
System.out.println(encoder.matches("correct-horse", encoded)); // true
```

This is a **code snippet run inside a method**, not a standalone application. Per current Spring Security documentation, the default factory uses `bcrypt` as the id for encoding; the list of compatible encoders may vary by version and configuration.

### Creating a Delegating Encoder with Controlled Cost

```java
import java.util.Map;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.DelegatingPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

PasswordEncoder current = new DelegatingPasswordEncoder(
        "bcrypt",
        Map.of("bcrypt", new BCryptPasswordEncoder(12)));
```

This example **only** permits the `bcrypt` id; it does not automatically support all legacy algorithms. In a real system, include required legacy encoders in the mapping during a controlled migration phase with an explicit deprecation date. Never permit `NoOpPasswordEncoder` or plaintext fallbacks just so old data "can log in".

### upgradeEncoding with Delegating

If a hash has an `{id}` different from the current `idForEncode`, the delegating encoder can mark it as needing an upgrade. If the id already matches, it can ask the child encoder whether the work factor/format needs updating. Therefore, migration can encompass both **algorithm changes** and **cost increases within the same algorithm**.

Pay special attention to old BCrypt hashes lacking a prefix like `$2a$10$...`. When switching to a delegating decoder expecting `{id}`, unprefixed stored values can fail because the id is undetermined. Design a migration that adds the prefix based on verified hash formats, or a strictly scoped legacy fallback with a scheduled removal deadline. Never treat unprefixed strings as plaintext passwords.

### Never Automatically Re-encode Existing Hashes in the DB

You cannot take a BCrypt hash and call `encode(oldHash)` to produce a "new password hash" compatible with the old plaintext. Doing so hashes the **hash string**, causing the real password to stop matching. Proper migration rehashes the **verified raw password** at login, or a new password during a reset flow.

## 8. DaoAuthenticationProvider Connects PasswordEncoder with UserDetailsPasswordService

In Spring Security Servlet username/password authentication, `DaoAuthenticationProvider` uses `UserDetailsService` to load the user, then `PasswordEncoder` to verify the password and authentication conditions. On the success path, it can call `upgradeEncoding`; if needed and a `UserDetailsPasswordService` is present, the provider generates a new hash from the verified plaintext password and invokes the writer:

```java
UserDetails updatePassword(UserDetails user, String newPassword);
```

This is the **abbreviated signature** of `UserDetailsPasswordService`. The parameter name `newPassword` in the contract means the **password already encoded by PasswordEncoder**, not plaintext. Implementations must update the user store for the right account and return a `UserDetails` reflecting the change.

### Why PasswordEncoder Alone Is Not Enough

There are three separate responsibilities:

- `UserDetailsService`: reads `UserDetails`, hash, and user status.
- `PasswordEncoder`: creates hashes, compares them, and determines needed upgrades.
- `UserDetailsPasswordService`: **persists** the new hash to the account store.

`upgradeEncoding` does not run SQL, write files, or update accounts by itself. If you configure `BCryptPasswordEncoder(12)` without supplying a writer, the system may keep using stored cost-8 hashes indefinitely even though authentication succeeds.

### Protecting Passwords After Authentication

`ProviderManager` has a mechanism to erase credentials from `Authentication` upon completion. Do not try to retrieve the raw password from the principal or session to rehash after login; by then the credential may already have been erased by design. The provider has a valid hook before sensitive data is discarded.

If `UserDetailsService` caches the same mutable instance containing the hash, credential erasure can mutate cached data. Review how `UserDetails` copying and invalidation strategies work. Do not broadly disable credential erasure just to fix a cache bug.

## 9. Runnable Java 17+ Example: Upgrading BCrypt 08 to 12

This example uses Spring Boot Servlet, Spring MVC/Web, and Spring Security. Create a project from Spring Initializr with **Spring Web** and **Spring Security**, Java 17+, and a supported Spring Boot version compatible with the APIs. If using Spring Boot 4, the corresponding Maven starters may be `spring-boot-starter-webmvc` and `spring-boot-starter-security`.

The demo creates user `an` with BCrypt cost 8 to simulate an old hash. The current encoder uses cost 12. An incorrect login **does not** alter the hash. A valid login causes `DaoAuthenticationProvider` to invoke `UserDetailsPasswordService` and persist a cost-12 hash in the in-memory store.

Create **`src/main/java/com/example/passworddemo/PasswordUpgradeApplication.java`**:

```java
package com.example.passworddemo;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.BadCredentialsException;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class PasswordUpgradeApplication {

    public static void main(String[] args) {
        SpringApplication.run(PasswordUpgradeApplication.class, args);
    }

    @Bean
    CommandLineRunner verifyUpgrade(
            InMemoryUserDetailsManager accounts,
            PasswordEncoder currentEncoder,
            AuthenticationManager manager) {

        return args -> {
            String before =
                    accounts.loadUserByUsername("an").getPassword();

            System.out.println("cost-before=" + before.substring(4, 6));
            System.out.println("upgrade-before="
                    + currentEncoder.upgradeEncoding(before));

            try {
                manager.authenticate(
                        UsernamePasswordAuthenticationToken.unauthenticated(
                                "an", "wrong"));
            } catch (BadCredentialsException ex) {
                System.out.println("wrong-password=REJECTED");
            }

            String afterFailure =
                    accounts.loadUserByUsername("an").getPassword();
            System.out.println("unchanged-after-failure="
                    + before.equals(afterFailure));

            Authentication success = manager.authenticate(
                    UsernamePasswordAuthenticationToken.unauthenticated(
                            "an", "demo-password"));

            String afterSuccess =
                    accounts.loadUserByUsername("an").getPassword();
            System.out.println("authenticated="
                    + success.isAuthenticated());
            System.out.println("cost-after="
                    + afterSuccess.substring(4, 6));
            System.out.println("upgrade-after="
                    + currentEncoder.upgradeEncoding(afterSuccess));
            System.out.println("matches-after="
                    + currentEncoder.matches(
                            "demo-password", afterSuccess));
        };
    }
}

@Configuration(proxyBeanMethods = false)
class PasswordSecurityConfig {

    @Bean
    PasswordEncoder currentPasswordEncoder() {
        return new BCryptPasswordEncoder(12);
    }

    @Bean
    InMemoryUserDetailsManager accounts() {
        PasswordEncoder old = new BCryptPasswordEncoder(8);
        UserDetails account = User.withUsername("an")
                .password(old.encode("demo-password"))
                .authorities("ROLE_USER")
                .build();
        return new InMemoryUserDetailsManager(account);
    }

    @Bean
    AuthenticationManager authenticationManager(
            InMemoryUserDetailsManager accounts,
            PasswordEncoder currentPasswordEncoder) {

        DaoAuthenticationProvider provider =
                new DaoAuthenticationProvider(accounts);
        provider.setPasswordEncoder(currentPasswordEncoder);

        // With a writer, the provider can persist the upgraded hash.
        provider.setUserDetailsPasswordService(accounts);

        return new ProviderManager(provider);
    }

    @Bean
    SecurityFilterChain filterChain(
            HttpSecurity http,
            AuthenticationManager manager) throws Exception {

        return http
                .authenticationManager(manager)
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/public/ping").permitAll()
                        .anyRequest().authenticated())
                .httpBasic(Customizer.withDefaults())
                .build();
    }
}

@RestController
class PasswordDemoController {

    @GetMapping("/public/ping")
    String ping() {
        return "pong";
    }

    @GetMapping("/me")
    String me(Authentication authentication) {
        return "principal=" + authentication.getName();
    }
}
```

### Code Analysis

**Old user:** `accounts()` uses `new BCryptPasswordEncoder(8)` to create the legacy hash. In production, **never create new hashes with a low cost** just to upgrade them; this is test data.

**New encoder:** `currentPasswordEncoder()` uses cost 12. The BCrypt hash carries cost/salt metadata so the new encoder can verify the cost-8 hash and flag it for upgrade.

**Dao provider:** `provider.setPasswordEncoder(currentPasswordEncoder)` uses the current encoder for verification. `provider.setUserDetailsPasswordService(accounts)` enables updating the hash. `InMemoryUserDetailsManager` implements both `UserDetailsService` and `UserDetailsPasswordService`, suitable for demos but not persistent storage.

**Manager:** `ProviderManager` is configured on `HttpSecurity`, allowing the HTTP Basic filter to use the chosen provider. `CommandLineRunner` calls the manager directly to print upgrade results before the learner tests HTTP.

**Failure check:** after password `wrong`, the hash from the store is compared again with the old value and must remain unchanged.

**Success check:** after password `demo-password`, the new hash cost is 12, `upgradeEncoding` returns false, and the password still matches. On subsequent logins, no unnecessary rehashing happens per request once the hash satisfies policy.

### How to Run and stdout

From the Maven project root with wrapper:

```bash

```

Or with Gradle wrapper:

```bash
./gradlew bootRun
```

On Windows PowerShell use `.\mvnw.cmd spring-boot:run` or `.\gradlew.bat bootRun`. Do not run with plain `javac` without the Spring Boot/Security classpath.

At startup, the lines printed by `CommandLineRunner` (excluding Spring Boot logs) are expected to be:

```text

wrong-password=REJECTED
unchanged-after-failure=true
authenticated=true

```

Next, test HTTP Basic:

The two successful lines return bodies:


**Note:** the program uses an in-memory store. After restart, the account reverts to the cost-8 hash from initialization data; production databases need a persistent writer implementation.

## 10. Writing UserDetailsPasswordService for a Business Store or JPA

In production, rehashing must write to the account/identity table under a **consistent contract**:

```text
trusted account + newEncodedPassword
    |
    v
UserDetailsPasswordService.updatePassword(...)
    |
    +-- identify account by trusted ID
    +-- check hash/version is still the authenticated one
    +-- update password_hash with newEncodedPassword
    +-- appropriate audit/transaction
    |
    v
return UserDetails with new hash
```

The writer receives the **encoded password supplied by the provider**, and must not call `encode` again.

A design fragment (requires corresponding domain/repository classes and imports; **not a standalone Java file**):

```java
@Service
class PersistentPasswordUpgradeService
        implements UserDetailsPasswordService {

    private final AccountRepository repository;

    PersistentPasswordUpgradeService(AccountRepository repository) {
        this.repository = repository;
    }

    @Override
    @Transactional
    public UserDetails updatePassword(
            UserDetails user, String newEncodedPassword) {

        DomainUserDetails principal = (DomainUserDetails) user;
        Account account = repository.findById(principal.accountId())
                .orElseThrow();

        if (!account.getPasswordHash().equals(user.getPassword())) {
            throw new IllegalStateException(
                    "Password was changed concurrently");
        }

        account.setPasswordHash(newEncodedPassword);
        return principal.withEncodedPassword(newEncodedPassword);
    }
}
```

The hash check in code only expresses **intent** and is not sufficient to prevent DB race conditions. In real deployments, row locking/optimistic versioning or compare-and-swap in a properly isolated transaction is needed. Never rely on an unguarded read-then-write statement for safety.

### Race Condition with Password Reset

The following can happen:

1. Login request L reads old hash H1 and verifies the old password.
2. Reset request R writes a new password as H2.
3. L wants to upgrade H1 to H3 using the old password.
4. If L overwrites H2, the old password may become accepted again, breaking the reset.

A conditional update can take the form:

```sql
UPDATE accounts
SET password_hash = :new_encoded_hash,
    version = version + 1
WHERE id = :account_id
  AND password_hash = :old_encoded_hash;
```

This is illustrative SQL; transaction handling and parameters depend on the DB engine. Check the affected row count: if 0, the source hash changed and the conflict must be handled rather than blindly overwriting. If the password hash lives on a versioned JPA entity, design optimistic locking and appropriate conflict handling.

### Do Not Double-Encode

Wrong:

```java
// WRONG: newEncodedPassword is already a hash created by the provider.
account.setPasswordHash(encoder.encode(newEncodedPassword));
```

Doing so hashes the **hash itself**, causing the raw password to stop matching. Only call `encode(rawNewPassword)` when you genuinely have a new plaintext password from a valid registration/change/reset flow.

## 11. Multi-Version and Multi-Algorithm Migrations

When an organization raises BCrypt cost or migrates from legacy hashes to a new format, it must answer:

- Are old hashes still permitted for verification?
- How is each stored hash's format/id identified?
- Which encoder will produce new hashes?
- When do users supply a validly verified raw password?
- Is there a safe writer that prevents overwriting concurrent resets?
- What percentage of accounts have migrated so far?
- How are users who have not logged in for months handled?

**Rehash on successful login** is a common strategy: after valid authentication, if the old hash is flagged for upgrade, re-encode the raw password with the new policy and persist it. The advantage is not forcing users to change passwords immediately; the limitation is that inactive accounts retain old hashes.

**Verified password reset** is appropriate when the old algorithm is no longer allowed or accounts have not supplied raw passwords for a long time. Users pick a new password and the server encodes it with the current policy, without needing to know the old plaintext.

### Do Not Turn Migration into a Dangerous Fallback

Especially avoid:

- Accepting raw passwords because an id prefix is missing.
- Adding `NoOpPasswordEncoder` as a default production fallback path.
- Calling `encode(oldHash)` and saving it — that is a hash of a hash.
- Writing a custom `matches` accepting both raw passwords and hashes via arbitrary string comparison.
- Swallowing encoder exceptions and treating them as successful logins or granting roles.
- Logging raw passwords, password hashes, or Basic Authorization headers.

If storage contains unprefixed hashes, classify actual formats, test thoroughly, and create a prefix migration or strictly scoped legacy decoder. Never infer formats from a couple of characters and permit arbitrary unknown algorithms.

## 12. Performance, Safety, and Upgrade Timing

BCrypt cost grows exponentially. Increasing cost from 8 to 12 can make every `matches` or `encode` call noticeably more CPU-intensive. If every HTTP Basic request must verify a password, the impact can be much higher than occasional session logins. Benchmark on real hardware:

- Average and p95/p99 authentication latency.
- CPU usage under many concurrent login requests.
- Resistance to request floods and hash verification capacity.
- Daily count of accounts remaining with legacy hashes to rehash.
- Staged rollout by cohort, monitoring user errors and database writes.
- A kill switch to pause upgrades if the service becomes overloaded.

Choose an algorithm/cost aligned with security standards and current hardware, not the highest possible setting just because it is configurable.

BCrypt also has an algorithmic limit on input bytes processed; for long passwords and Unicode, carefully design validation/normalization policies. Never silently truncate passwords before hashing, which would make distinct passwords equivalent. Consider other algorithms such as Argon2 depending on system requirements and operational capabilities.

## 13. Common Mistakes

| Mistake | Why It Is Wrong | Fix |
| --- | --- | --- |
| Storing plaintext passwords | Secrets leak if DB/backups are exposed | `encode` with a secure encoder |
| Plain fast `SHA-256(password)` hash | Far easier to brute-force offline than dedicated password hashing | Appropriate BCrypt/Argon2/scrypt |
| Comparing `encode(raw).equals(stored)` | Salt usually makes strings differ | `matches(raw, stored)` |
| Swapping `matches` parameters | Raw and stored hash have different types/roles | Raw first, encoded second |
| Granting access on `matches=true` alone | Bypasses account status and authorization | Let provider/security chain decide |
| Calling `upgradeEncoding` to check a password | It does not accept a raw password | Call `matches` first |
| Assuming `upgradeEncoding=true` already updated DB | It only returns a boolean | Writer/`UserDetailsPasswordService` |
| Rehashing a wrong submitted password | Can unauthorizedly overwrite credentials | Only after valid authentication |
| Using a writer without transactions/concurrency guards | Overwrites password resets | Version/compare-and-swap |
| Double-encoding `newEncodedPassword` | Password stops matching | Save new encoded hash directly |
| Switching to delegating and forgetting `{id}` | Old hashes fail to be recognized | Controlled format migration |
| Plaintext fallback for unknown ids | Creates an authentication bypass path | Reject unsupported inputs |
| Disabling credential erasure to make cache work | Credentials linger longer in memory | Fix UserDetails copying/caching |
| Expecting JWT to auto-rehash passwords | Tokens do not carry raw passwords | Valid password login or reset |
| Not benchmarking cost | Increases CPU and DoS risk | Benchmark and enforce load limits |
| Logging passwords/hashes | Leaks sensitive material | Log minimal status and policy version |

## 14. Recommended Test Matrix

**Testing encode and matches:**

1. A newly encoded hash must match the correct raw password.
2. Different passwords must not match.
3. Two BCrypt encodings of the same raw password can differ due to salt; do not write tests comparing literal hash strings.
4. Malformed hashes or unsupported ids must be handled according to policy.
5. Long and Unicode passwords must be tested against product policy.

**Testing upgradeEncoding:**

1. Stored cost 8 with encoder cost 12 → `true`.
2. Stored cost 12 with encoder cost 12 → `false`.
3. A custom encoder that does not override it may always return `false`.
4. Old and new delegating ids are handled according to the mapping.
5. Calling `upgradeEncoding` alone does not write to the DB.

**Testing provider/writer:**

1. Wrong password **does not update** the hash.
2. Correct login with an old hash calls the writer once per policy.
3. Subsequent correct login after upgrade does not unnecessarily update the hash again.
4. The upgraded hash still matches the raw password.
5. A writer failure must not report "upgrade succeeded".
6. Concurrent password resets are not overwritten by login migration.
7. Sessions/caches/replicas do not continue using stale hashes after update.
8. Verify HTTP 401/403 and individual account status conditions.

### Java Test Snippet

```java
PasswordEncoder oldEncoder = new BCryptPasswordEncoder(8);
PasswordEncoder newEncoder = new BCryptPasswordEncoder(12);

String oldHash = oldEncoder.encode("demo");
boolean valid = newEncoder.matches("demo", oldHash);
boolean invalid = newEncoder.matches("wrong", oldHash);
boolean needsUpgrade = newEncoder.upgradeEncoding(oldHash);

String newHash = newEncoder.encode("demo");
boolean noFurtherUpgrade = !newEncoder.upgradeEncoding(newHash);

System.out.println(valid);
System.out.println(invalid);
System.out.println(needsUpgrade);
System.out.println(noFurtherUpgrade);
```

This is an **in-method code snippet** with appropriate imports, not a standalone class with `main`. Output:

```text
true
false
true
true
```

Booleans are verifiable outputs; actual hashes are non-deterministic due to salt.

## 15. Real-World Scenarios: How Should You Decide?

### Locked Account with Correct Password

`matches` may return true if called directly, but the provider must reject login when the account is locked. Do not upgrade the password hash during a login rejected by security policy.

### User Changes Password

Password changes use `encode(rawNewPassword)` and persist the new hash after verifying authorization to perform the action. There is no need to upgrade the old hash when replacing it with a new password hashed under the current policy.

### SSO/OIDC Login

If the application does not own the user's password, do not simulate `PasswordEncoder` on an ID token. The Identity Provider is responsible for hashing/storing their passwords.

### Changing Encoder Configuration

Do not merely change the bean's strength and assume all old hashes will be rewritten. Check the `upgradeEncoding` implementation, supply a writer, track migration rates, and have a plan for accounts that have not logged back in.

### Multiple Instances and Database Replicas

One instance may read an old hash from a replica while another instance has already updated the new hash. You need a consistency/cache/replica propagation policy, especially when rehashing and password resets happen concurrently. The writer must prevent lost updates.

## 16. Self-Check Questions

**Question 1.** Can two calls to `encode("abc")` with BCrypt produce different strings?  
**Answer:** Yes, because of the random salt. Both can still match the same password.

**Question 2.** Why is `encoder.encode(raw).equals(stored)` wrong?  
**Answer:** Salt makes the new encoding usually differ; you must use `matches(raw, stored)`.

**Question 3.** Does `upgradeEncoding(oldHash) == true` mean the password is correct?  
**Answer:** No. It only inspects the hash and the encoder policy.

**Question 4.** After `upgradeEncoding=true`, does the database already have the new hash?  
**Answer:** Not yet. A rehash flow with a valid raw password and a writer persisting the new hash is required.

**Question 5.** Can a BCrypt hash stored at cost 8 be verified by a cost-12 encoder?  
**Answer:** Yes, if it is a valid BCrypt hash; the cost is stored inside the hash.

**Question 6.** May the provider rehash a wrong password and save it?  
**Answer:** No. That would become a flaw allowing an attacker to replace the user's credentials.

**Question 7.** What does `UserDetailsPasswordService.updatePassword` receive?  
**Answer:** It receives an **encoded** password, not raw plaintext.

**Question 8.** When replacing a password in a reset request, do we still need to upgrade the old hash?  
**Answer:** No, because the new password is already encoded using the current policy.

**Question 9.** Why can switching to delegating cause unprefixed BCrypt hashes to stop matching?  
**Answer:** Because the decoder selects by `{id}`; hashes without an id need migration or a controlled legacy mapping.

**Question 10.** How do we prevent an old hash upgrade from overwriting a new password reset?  
**Answer:** Conditional updates checking the old hash/version alongside appropriate transactions/optimistic locking.

**Question 11.** Why not pick the highest possible BCrypt cost?  
**Answer:** Because it increases latency, CPU usage, and bottleneck/DoS risk; you must benchmark on real infrastructure.

**Question 12.** Does `upgradeEncoding=false` mean the hash is completely secure?  
**Answer:** No. It only reflects the current encoder's decision and does not replace periodic security reviews.

## Conclusion

The three methods of `PasswordEncoder` are not interchangeable:

- **`encode`** creates a new hash to store.
- **`matches`** verifies a presented password against a stored hash.
- **`upgradeEncoding`** only evaluates whether the stored hash should be replaced with a new hash.

In Spring Security, `DaoAuthenticationProvider` is where credentials are checked in the username/password flow; to automatically rehash after successful authentication, configure `UserDetailsPasswordService` to persist updated hashes safely against concurrent password resets. Changing BCrypt cost or the algorithm without designing the writer and handling legacy data is not enough to ensure migration.

**Key takeaway:** *`matches` answers whether the password matches; `upgradeEncoding` answers whether the hash is outdated; `encode` creates a new hash. Only a valid authentication flow and a safe writer may persist an upgraded hash.*
