# Success Events and Authentication Failure Event Groups

## 1. Lesson objectives

In Spring Security, password login, bearer token validation, or calling an `AuthenticationManager` can result in an **authentication success event** or an **authentication failure event**. Spring application events help record audit logs, track bad passwords, detect anomalies, and monitor authentication backend outages without forcing every controller to implement its own logging.

Core concepts:

- `AuthenticationSuccessEvent`: reflects a successful authentication when an `AuthenticationEventPublisher` is used.
- `AbstractAuthenticationFailureEvent`: base class for failure events such as invalid credentials, disabled/locked/expired accounts, or backend errors.
- `DefaultAuthenticationEventPublisher`: maps `AuthenticationException` to event classes and publishes them through Spring's `ApplicationEventPublisher`.
- `@EventListener`: how to listen for events inside the Spring container.

**Important distinction:** an HTTP `200` does not equal a new login; an HTTP `401` does not guarantee a failure event; and a `403` due to insufficient permissions is an **authorization denial**, not an authentication error.

Events provide information for observability and auditing; **they do not automatically block attacks, grant permissions, or guarantee durable storage**. Mandatory controls such as rate limiting, account lockout, MFA, and authorization must be placed on the appropriate enforcement path.

## 2. Event publishing architecture

~~~text
Browser / API client
       |
       v
Authentication filter
       |
       v
AuthenticationManager (usually ProviderManager)
       |
       +--> AuthenticationProvider A
       +--> AuthenticationProvider B ...
       |
       +-- successful Authentication
       |        |
       |        v
       |   AuthenticationEventPublisher
       |        |
       |   AuthenticationSuccessEvent
       |
       +-- final AuthenticationException
                |
                v
          DefaultAuthenticationEventPublisher
                |
          AbstractAuthenticationFailureEvent subclass
                |
                v
         Spring ApplicationEventPublisher
                |
         @EventListener / ApplicationListener
                |
         Audit / metrics / detection
~~~

An `AuthenticationProvider` verifies credentials or tokens and returns a valid `Authentication`, `null` if it does not handle that token type, or throws an `AuthenticationException`. `ProviderManager` coordinates providers to reach the **final outcome**. Do not assume an error from provider A necessarily publishes a failure event if provider B subsequently authenticates successfully.

Per the Spring Security 6.x API, `ProviderManager` delegates events to a configured `AuthenticationEventPublisher`; if you construct a manager manually without setting a publisher, you may not receive events. With a parent manager, avoid letting both parent and child publish, which leads to duplicate metrics.

Filter handlers (`AuthenticationSuccessHandler`, `AuthenticationFailureHandler`) control the HTTP redirect/status after login, which is **different** from the application-event publisher. Listeners can even run in flows that do not use Servlet.

## 3. Authentication success events

`AuthenticationSuccessEvent` belongs to package `org.springframework.security.authentication.event` and exposes the authentication object via `getAuthentication()`.

Example **application-defined** audit schema, not a payload automatically generated by Spring:

~~~json
{
  "eventId": "evt-s01",
  "outcome": "SUCCESS",
  "eventType": "AuthenticationSuccessEvent",
  "principalRef": "usr-1042",
  "mechanism": "PASSWORD",
  "occurredAt": "2026-11-06T09:00:00Z",
  "correlationId": "req-a42"
}
~~~

A success event states that **AuthenticationManager accepted the authentication from a provider**. It does not on its own prove that:

- The browser created a new HTTP session cookie.
- The user just typed a password at the moment of the event; a resource server might only be validating an access token.
- MFA has completed or high assurance was achieved, if the flow only passed the password phase.
- The account holds all roles, or the next request is permitted to view all resources.
- This is a unique user login; stateless APIs may authenticate tokens on every request.

In statistics, explicitly record the **authentication mechanism, source, and semantics**. If a dashboard aims to count *human interactive logins*, do not count every JWT bearer token success as a user login.

### `InteractiveAuthenticationSuccessEvent`

Spring Security has the `InteractiveAuthenticationSuccessEvent` class representing successful interactive authentication in certain web flows. It **does not extend `AuthenticationSuccessEvent`**, because the API is designed to avoid sending duplicate `AuthenticationSuccessEvent` notifications to a listener of that class. If you want to count browser-login completions, verify the exact filter/flow and handle both event types according to your measurement goal rather than blindly summing them.

## 4. Failure event inheritance hierarchy

In Spring Security 6.x, listen to `AbstractAuthenticationFailureEvent` to receive subclasses.

~~~text
AbstractAuthenticationEvent
|
+-- AuthenticationSuccessEvent
+-- InteractiveAuthenticationSuccessEvent
|
+-- AbstractAuthenticationFailureEvent
    |
    +-- AuthenticationFailureBadCredentialsEvent
    +-- AuthenticationFailureDisabledEvent
    +-- AuthenticationFailureLockedEvent
    +-- AuthenticationFailureExpiredEvent
    +-- AuthenticationFailureCredentialsExpiredEvent
    +-- AuthenticationFailureProviderNotFoundEvent
    +-- AuthenticationFailureServiceExceptionEvent
    +-- AuthenticationFailureProxyUntrustedEvent
    +-- Custom failure events ...
~~~

Failure events inherit `getAuthentication()` and provide `getException()`. On failure, `Authentication` represents the **authentication attempt**, not a verified principal; it may contain an unauthenticated username or sensitive data in credentials/details. Never log the raw object.

`AbstractAuthenticationFailureEvent` is the API to use in new code. Very old documentation may mention `AuthenticationFailureEvent`; avoid relying on names from another version's docs without checking actual imports/classes.

## 5. Default mapping: which exception produces which event?

In Spring Security 6.5 documentation, `DefaultAuthenticationEventPublisher` has the following default mappings:

| Thrown exception | Event | Interpretation |
|---|---|---|
| `BadCredentialsException` | `AuthenticationFailureBadCredentialsEvent` | Invalid credentials. |
| `UsernameNotFoundException` | `AuthenticationFailureBadCredentialsEvent` | User lookup failed, grouped into bad credentials. |
| `InvalidBearerTokenException` | `AuthenticationFailureBadCredentialsEvent` | Invalid bearer token when the flow goes through the corresponding publisher. |
| `DisabledException` | `AuthenticationFailureDisabledEvent` | Account disabled. |
| `LockedException` | `AuthenticationFailureLockedEvent` | Account locked. |
| `AccountExpiredException` | `AuthenticationFailureExpiredEvent` | Account expired. |
| `CredentialsExpiredException` | `AuthenticationFailureCredentialsExpiredEvent` | Credentials expired. |
| `ProviderNotFoundException` | `AuthenticationFailureProviderNotFoundEvent` | No provider supports the `Authentication` type. |
| `AuthenticationServiceException` | `AuthenticationFailureServiceExceptionEvent` | Internal authentication/service error. |

`AuthenticationFailureProxyUntrustedEvent` is also a valid class related to untrusted CAS proxy scenarios; **do not claim it appears by default in every application**.

Easy-to-miss point: the publisher uses **exact exception-class matching**. If a custom exception extends `BadCredentialsException`, it **does not automatically inherit the parent class's mapping**. You must configure `setAdditionalExceptionMappings(...)` or a fallback failure event, and then test it.

Additionally, not every failure at a filter originates from an `AuthenticationManager` with a publisher: requests missing a token, header parsing errors rejected before the manager, or custom filters handling requests directly may not emit these events.

## 6. Standardizing error categories for monitoring and response

| Internal category | Event | Usage |
|---|---|---|
| `SUCCESS` | `AuthenticationSuccessEvent` | Track successful logins/token checks by mechanism. |
| `INVALID_CREDENTIALS` | `AuthenticationFailureBadCredentialsEvent` | Signal for credential guessing/invalid token. |
| `ACCOUNT_DISABLED` | `AuthenticationFailureDisabledEvent` | Attempt to access a disabled account. |
| `ACCOUNT_LOCKED` | `AuthenticationFailureLockedEvent` | Attempt on an already locked account. |
| `ACCOUNT_EXPIRED` | `AuthenticationFailureExpiredEvent` | Account validity expired. |
| `CREDENTIALS_EXPIRED` | `AuthenticationFailureCredentialsExpiredEvent` | Credentials need rotation or re-enrollment. |
| `NO_AUTH_PROVIDER` | `AuthenticationFailureProviderNotFoundEvent` | Misconfigured AuthenticationProvider/filter chain. |
| `AUTH_SYSTEM_ERROR` | `AuthenticationFailureServiceExceptionEvent` | Outage of DB/LDAP/IdP/verifier. |
| `PROXY_NOT_TRUSTED` | `AuthenticationFailureProxyUntrustedEvent` | Specific CAS/trust configuration issue. |
| `CUSTOM_POLICY_FAILURE` | Application custom event. | Tenant/device/risk/assurance per custom policy. |

This is a **system-defined taxonomy**, independent of Spring class names. The goal is to distinguish **password guessing** from **misconfiguration or backend outages**, so alerts fire accurately and accounts are not accidentally locked because a service lost connectivity.

An `AuthenticationFailureLockedEvent` also **does not prove** that the current request just caused the account to be locked. It may simply be emitted when a user tries to log in to an account that was already locked earlier.

## 7. Configuring the publisher in Spring Security

Spring Boot 3.x / Spring Security 6.x example:

~~~java
package example.security;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationEventPublisher;
import org.springframework.security.authentication.DefaultAuthenticationEventPublisher;

@Configuration
public class AuthenticationEventConfiguration {
    @Bean
    AuthenticationEventPublisher authenticationEventPublisher(
            ApplicationEventPublisher publisher) {
        return new DefaultAuthenticationEventPublisher(publisher);
    }
}
~~~

`DefaultAuthenticationEventPublisher` converts authentication outcomes into Spring application events when the manager uses this publisher. **Check existing beans** before declaring a new bean: some Spring Boot/Spring Security setups already provide a publisher or custom manager. Do not create two beans for the same purpose and assume the framework will automatically pick the right one or deduplicate them.

If the project constructs `ProviderManager` manually outside the framework:

~~~java
// Integration snippet, not standalone Java:
ProviderManager manager = new ProviderManager(providerA, providerB);
manager.setAuthenticationEventPublisher(authenticationEventPublisher);
~~~

`providerA`/`providerB` must be real `AuthenticationProvider` instances, and `authenticationEventPublisher` must be wired to the Spring application context. Do not simply create `new DefaultAuthenticationEventPublisher()` without supplying `ApplicationEventPublisher` and expect listeners to receive events.

**Correct configuration is proven by testing through the real authentication flow**, not merely by checking that a bean exists.

## 8. Listening with `@EventListener`

You can handle both success and failure in a single component:

~~~java
package example.security;

import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;
import org.springframework.security.authentication.event.AuthenticationSuccessEvent;
import org.springframework.security.authentication.event.AbstractAuthenticationFailureEvent;
import org.springframework.security.authentication.event.AuthenticationFailureBadCredentialsEvent;
import org.springframework.security.authentication.event.AuthenticationFailureDisabledEvent;
import org.springframework.security.authentication.event.AuthenticationFailureLockedEvent;
import org.springframework.security.authentication.event.AuthenticationFailureServiceExceptionEvent;

@Component
public class AuthenticationEventObserver {

    @EventListener
    public void onSuccess(AuthenticationSuccessEvent event) {
        String mechanism =
                event.getAuthentication().getClass().getSimpleName();
        safeAudit("SUCCESS", mechanism);
    }

    @EventListener
    public void onFailure(AbstractAuthenticationFailureEvent event) {
        String category;
        if (event instanceof AuthenticationFailureBadCredentialsEvent) {
            category = "INVALID_CREDENTIALS";
        } else if (event instanceof AuthenticationFailureDisabledEvent) {
            category = "ACCOUNT_DISABLED";
        } else if (event instanceof AuthenticationFailureLockedEvent) {
            category = "ACCOUNT_LOCKED";
        } else if (event instanceof AuthenticationFailureServiceExceptionEvent) {
            category = "AUTH_SYSTEM_ERROR";
        } else {
            category = "OTHER_AUTH_FAILURE";
        }
        safeAudit(category,
                event.getException().getClass().getSimpleName());
    }

    private void safeAudit(String category, String source) {
        // Controlled audit/metrics integration in the application.
        // Do not log full Authentication, credentials, tokens, or PII.
    }
}
~~~

This is an **integration snippet**, not standalone executable Java: the `safeAudit` method is currently an illustrative no-op; the project must connect it to a reliable audit sink and enforce policies. Using `AbstractAuthenticationFailureEvent` receives all failure subclasses. You can further classify `AuthenticationFailureCredentialsExpiredEvent`, `AuthenticationFailureExpiredEvent`, and `AuthenticationFailureProviderNotFoundEvent` if a full taxonomy is needed.

If one listener subscribes to `AbstractAuthenticationFailureEvent` and another listener subscribes to a subclass, the same event will be delivered to both listeners. If you want **one audit record per outcome**, unify coordination in a single handler or use explicit eventId/deduplication.

## 9. Customizing exception mapping per application

Suppose a policy blocks credentials from an untrusted device. To avoid lumping it together with bad passwords, create a dedicated exception:

~~~java
package example.security;

import org.springframework.security.core.AuthenticationException;

public final class DevicePolicyException extends AuthenticationException {
    public DevicePolicyException(String message) {
        super(message);
    }
}
~~~

Create a custom event extending the abstract base class:

~~~java
package example.security;

import org.springframework.security.authentication.event.AbstractAuthenticationFailureEvent;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.AuthenticationException;

public final class AuthenticationFailureDevicePolicyEvent
        extends AbstractAuthenticationFailureEvent {
    public AuthenticationFailureDevicePolicyEvent(
            Authentication authentication, AuthenticationException exception) {
        super(authentication, exception);
    }
}
~~~

Then use **one configured publisher bean**, instead of creating a second publisher:

~~~java
@Bean
AuthenticationEventPublisher authenticationEventPublisher(
        ApplicationEventPublisher publisher) {
    DefaultAuthenticationEventPublisher result =
            new DefaultAuthenticationEventPublisher(publisher);
    result.setAdditionalExceptionMappings(
        java.util.Map.of(
            DevicePolicyException.class,
            AuthenticationFailureDevicePolicyEvent.class
        )
    );
    return result;
}
~~~

The bean imports were shown in section 7; this example **replaces** the basic bean version and requires placing the public classes in their own files. `setAdditionalExceptionMappings(Map)` extends the default mappings rather than erasing all existing mappings.

Spring also provides `setDefaultAuthenticationFailureEvent(...)` for unmapped `AuthenticationException` types; use a **concrete event subclass** with a matching `(Authentication, AuthenticationException)` constructor and test it. Do not pass an abstract class merely because its name sounds all-encompassing.

**Specifically:** a subclass of `BadCredentialsException` must declare its own mapping if you want to guarantee event emission. Never rely on coincidental exception names or infer classification from HTTP status codes.

## 10. Auth success events differ from success handlers and HTTP responses

| Component | Responsibility |
|---|---|
| `AuthenticationSuccessEvent` | Announces a successful authentication outcome from the event publisher. |
| `AuthenticationSuccessHandler` | Redirects/writes HTTP response after browser authentication filter success. |
| `AuthenticationFailureHandler` | Returns errors/redirects/flash messages after filter login failure. |
| `AuthenticationEntryPoint` | Initiates authentication / responds to unauthenticated requests. |
| `AccessDeniedHandler` | Handles authenticated requests lacking permissions, usually `403`. |
| `AuthorizationManager` | Decides access permissions for a specific request/action. |
| `LogoutSuccessEvent` | Signals successful logout in the appropriate flow. |

A `GET /reports` request returning `200` because of a previously authenticated session **does not emit a new login success event** merely because the HTTP outcome succeeded. Conversely, an authenticated login can fail at session creation/redirect or subsequent authorization; event lifecycles and HTTP lifecycles are distinct.

A request with a valid bearer token that lacks `ROLE_ADMIN` may result in `403` from `AuthorizationManager`/method security, **not `AuthenticationFailureBadCredentialsEvent`**. If you need to monitor authorization failures, emit telemetry at the appropriate authorization point, categorized separately from invalid credentials.

## 11. Special scenarios by authentication mechanism

### Form login / `DaoAuthenticationProvider`

Password login via `AuthenticationManager` can publish success/failure if a publisher is configured. `UsernameNotFoundException` and `BadCredentialsException` are mapped by the publisher to bad-credentials events. Never disclose whether a username exists in public responses.

### LDAP / Active Directory

A failed LDAP bind can be caused by a wrong password or an unreachable directory; the provider must use proper exception semantics. **An LDAP outage error should not become a password-guessing event**. Create separate metrics for backend health and authentication failures.

### Resource Server JWT

A JWT token with an invalid issuer/audience/signature/expiry can produce `InvalidBearerTokenException` in certain processing paths; when this exception passes through `DefaultAuthenticationEventPublisher`, it maps to a bad-credentials event. However, a request **missing the token header** may be rejected by the entry point before any manager event occurs. Test against real `oauth2ResourceServer().jwt()`.

### OIDC/SAML SSO

OIDC/SAML authentication has specialized callback and provider flows. An authentication success after a callback does not prove the user just entered a password in the app or completed step-up MFA. Never rely on a listener in place of verifying assertion/token signatures, issuer, audience, and expiration.

### API key / custom filter

A custom `OncePerRequestFilter` that parses headers and sets `SecurityContextHolder` directly without calling `AuthenticationManager` may not emit these Spring authentication events. If auditing is required, structure it through a provider/manager path or publish events under a dedicated deduplicated contract.

### Multi-step MFA

Password-phase success does not mean the session has reached `MFA_COMPLETE`. Track factor verification with dedicated events from a trusted verifier: factor type, challenge ID, `verifiedAt`, purpose, assurance, and consumed/revoked status. Never grant `ROLE_ADMIN` merely because a listener observed password success.

## 12. Distinguishing bad passwords, locked, disabled, expired, and system errors

**Bad credentials – `AuthenticationFailureBadCredentialsEvent`:** used when credentials/tokens are invalid; may also reflect failed user lookup. Do not assume from the event class alone that the user exists or that a password failed cryptographically.

**Account locked – `AuthenticationFailureLockedEvent`:** indicates the provider observed a locked state. It does not mean **this request just locked the account**; the lockout may stem from an earlier policy action.

**Account disabled – `AuthenticationFailureDisabledEvent`:** useful for offboarding/security incidents. However, old sessions/JWTs may still exist if the authorization layer does not check account status, so the event does not replace online state enforcement.

**Account expired – `AuthenticationFailureExpiredEvent`:** the account has passed its active validity period per policy; distinct from password expiration.

**Credentials expired – `AuthenticationFailureCredentialsExpiredEvent`:** credentials such as a password are treated as expired and may require a secure credential update flow.

**Provider not found – `AuthenticationFailureProviderNotFoundEvent`:** usually signals misconfiguration of `AuthenticationProvider`/filter chain or custom authentication token types, not a user's wrong password.

**Service exception – `AuthenticationFailureServiceExceptionEvent`:** signals an internal error in the verifier/repository/LDAP/IdP. Do not turn this into incrementing bad-password counters and locking accounts en masse when the backend is down. External responses must still remain safe and avoid leaking topology.

These causes require separate response policies; generally keep **public login messages non-revealing regarding account existence**, even while internal audits store detailed categories under restricted access.

## 13. Account enumeration and the difference between audit and response

Attackers can probe emails in a login form to enumerate accounts. If the UI returns:

~~~text
unknown user -> "Email does not exist"
bad password -> "Wrong password"
disabled     -> "Your account was disabled by HR"
~~~

then differences in message, status, redirect, or timing can leak account state. A public response can use:

~~~json
{"message":"Invalid credentials."}
~~~

In internal audits, where justified, you can still distinguish `INVALID_CREDENTIALS`, `DISABLED_ACCOUNT`, and `SYSTEM_ERROR` to aid investigations. Do not expose exception classes, account status, username-found flags, or failed-attempt counts in public responses if doing so creates a side channel.

Timing and quotas must also be controlled: an existing identifier under cooldown behaving differently from a non-existent identifier can leak a signal. Apply anti-enumeration policies across response handlers, rate limiters, and recovery flows; **an event listener does not solve this problem by itself**.

## 14. Event payloads can contain credentials: log using an allowlist

An `Authentication` inside an event may contain `principal`, `credentials`, `details`, authorities, request metadata, or tokens. `AuthenticationException` may contain sensitive causes/messages. Never log the raw event:

~~~java
// Example to avoid:
logger.info("Authentication={}", event.getAuthentication());
logger.error("Failure {}", event.getException());
~~~

A safe audit record should include only **selected fields**:

~~~json
{
  "schemaVersion": 1,
  "eventId": "evt-f28",
  "outcome": "FAILURE",
  "category": "INVALID_CREDENTIALS",
  "mechanism": "PASSWORD",
  "occurredAt": "2026-11-06T09:05:00Z",
  "subjectRef": "pseudonymous-ref",
  "application": "employee-portal",
  "requestId": "req-190"
}
~~~

This is a **recommended schema**, not built-in fields. `subjectRef` on failure **does not mean a verified identity**; it may simply be an arbitrary client-supplied identifier. If attempts must be correlated, use HMAC/pseudonymization and appropriate retention.

Do not log: passwords, OTP/TOTP codes, bearer/API keys, refresh tokens, session cookies, raw Authorization headers, request bodies, query strings containing secrets, full Authentication objects, or unsanitized exception stack traces.

Client IP or user-agent should only be collected from trusted sources with a clear privacy justification. Behind a reverse proxy, `X-Forwarded-For` can be spoofed if the edge does not strip/rewrite it. Spring event listeners do not always have an HTTP request context; do not assume `RequestContextHolder` always works.

`event.getTimestamp()` is the timestamp of the Spring application event, not automatically the moment a specific MFA factor was verified or an authorization decision committed.

## 15. Listeners should be lightweight, idempotent, and never alter login outcomes

Spring `ApplicationEventPublisher` dispatches **in-process events**; listeners normally run synchronously on the request thread by default. `@Async` or a custom multicaster can change execution behavior, but **does not turn events into a durable queue**.

Best practices:

1. Classify outcome/category quickly.
2. Send sanitized envelopes to an audit sink, queue, or metrics with load bounds.
3. Handle duplicates and ensure correlation when multiple AuthenticationManagers/listeners exist.
4. Never make slow network calls inside a synchronous listener without timeouts/backpressure.
5. Define the policy when the audit sink fails: retry, buffer, alert, degrade, or fail closed for operations that strictly require auditing.
6. Never let exceptions from a listener unexpectedly alter authentication outcomes.
7. Use a durable outbox/queue and idempotent consumers if guarantees against audit loss on process crash are required.

**Do not rely on event listeners as the sole protection mechanism** for rate limiting, account lockout, MFA, or permission checks. Listeners may not fire on custom authentication paths, may receive duplicates from parent/child managers, or may be interrupted during process crashes.

### "One login" event differs from "one request"

With stateless APIs, the same JWT can be re-authenticated across hundreds of requests. Counting every `AuthenticationSuccessEvent` as a login inflates metrics. Split metrics into `PASSWORD_LOGIN_SUCCESS`, `OIDC_CALLBACK_SUCCESS`, `BEARER_TOKEN_ACCEPTED`, or an equivalent mechanism-based taxonomy.

## 16. Rate limiting, lockout, and alerting

Failure events useful to monitor:

- Multiple `INVALID_CREDENTIALS` for one identifier across different sources.
- Multiple identifiers failing from a single IP/network.
- Unusual spikes in invalid bearer tokens by client/application.
- Attempts on disabled accounts after offboarding.
- `NO_AUTH_PROVIDER` spikes after a deployment.
- `AUTH_SYSTEM_ERROR` spikes due to database/LDAP/IdP outages.

However, a multi-node system must not merely count events in one JVM's `ConcurrentHashMap` and use that to lock accounts. Rate limiting needs a shared store/atomic counters and enforcement before or inside the authentication flow.

Quota dimensions commonly considered:

| Dimension | Purpose | Risk |
|---|---|---|
| Normalized identifier | Limit guessing against one account. | Must apply to both existing and non-existing identifiers to prevent enumeration. |
| IP/network | Limit single-source floods. | NAT, proxy trust, botnet/IP rotation. |
| Client/tenant | Limit abuse per integration. | Avoid letting an attacker lock out an entire tenant. |
| Device/risk signal | Behavioral analysis. | Device cookies are not standalone proof. |
| Global auth backend | Protect DB/LDAP/IdP. | Outages must not be counted as bad passwords. |

Locking accounts after repeated failures risks DoS if an attacker deliberately spams a victim. Policies require limits, challenges, recovery, and auditing—not simply "receive 5 failure events and permanently disable."

## 17. Standalone Java 17: simulating the taxonomy

The following example uses only the **JDK 17 Standard Library**, without Spring. It simulates the **audit category normalization** step from outcome/exception names. The program **does not** authenticate users, publish Spring events, or replace listener implementations; real applications must use event instances/subclasses.

~~~java
public class AuthenticationEventClassifierDemo {
    static String classify(String event, String exceptionType) {
        if ("AuthenticationSuccessEvent".equals(event)) {
            return "SUCCESS";
        }
        if (!"AbstractAuthenticationFailureEvent".equals(event)) {
            return "NOT_AUTH_RESULT";
        }
        return switch (exceptionType) {
            case "BadCredentialsException",
                 "UsernameNotFoundException",
                 "InvalidBearerTokenException" -> "INVALID_CREDENTIALS";
            case "DisabledException" -> "ACCOUNT_DISABLED";
            case "LockedException" -> "ACCOUNT_LOCKED";
            case "AccountExpiredException" -> "ACCOUNT_EXPIRED";
            case "CredentialsExpiredException" -> "CREDENTIALS_EXPIRED";
            case "ProviderNotFoundException" -> "NO_AUTH_PROVIDER";
            case "AuthenticationServiceException" -> "AUTH_SYSTEM_ERROR";
            default -> "UNMAPPED_FAILURE";
        };
    }

    static void show(String label, String event, String exception) {
        System.out.println(label + ": " + classify(event, exception));
    }

    public static void main(String[] args) {
        String fail = "AbstractAuthenticationFailureEvent";
        show("login", "AuthenticationSuccessEvent", "");
        show("bad password", fail, "BadCredentialsException");
        show("unknown username", fail, "UsernameNotFoundException");
        show("bad bearer", fail, "InvalidBearerTokenException");
        show("disabled", fail, "DisabledException");
        show("locked", fail, "LockedException");
        show("expired account", fail, "AccountExpiredException");
        show("expired credentials", fail, "CredentialsExpiredException");
        show("no provider", fail, "ProviderNotFoundException");
        show("backend error", fail, "AuthenticationServiceException");
        show("custom", fail, "MyCustomException");
        show("access denied", "AccessDeniedEvent", "");
    }
}
~~~

Save the file `AuthenticationEventClassifierDemo.java` and run:

~~~bash
javac AuthenticationEventClassifierDemo.java
java AuthenticationEventClassifierDemo
~~~

**Exact stdout:**

~~~text
login: SUCCESS
bad password: INVALID_CREDENTIALS
unknown username: INVALID_CREDENTIALS
bad bearer: INVALID_CREDENTIALS
disabled: ACCOUNT_DISABLED
locked: ACCOUNT_LOCKED
expired account: ACCOUNT_EXPIRED
expired credentials: CREDENTIALS_EXPIRED
no provider: NO_AUTH_PROVIDER
backend error: AUTH_SYSTEM_ERROR
custom: UNMAPPED_FAILURE
access denied: NOT_AUTH_RESULT
~~~

Key takeaway: non-existent users and bad passwords are grouped together, internal service outages are separated from guessing, and access denied sits outside the authentication result hierarchy. For custom exceptions, the app must configure publisher mappings/fallbacks **before** listeners receive events to classify.

## 18. Real-world application scenarios

### A. Login with correct password

~~~text
POST /login
  -> DaoAuthenticationProvider authenticates
  -> ProviderManager returns Authentication
  -> AuthenticationSuccessEvent
  -> audit SUCCESS / mechanism PASSWORD
  -> filter success handler redirects or returns response
~~~

If a TOTP step follows, this is not automatically an MFA-complete result. Emit a separate event from the factor verifier.

### B. Probing a non-existent email

~~~text
User lookup returns UsernameNotFoundException
  -> publisher maps it to AuthenticationFailureBadCredentialsEvent
  -> audit INVALID_CREDENTIALS
  -> public response uses generic message
~~~

Never leak email existence via HTTP body, status, or timing.

### C. Account already locked

~~~text
Provider detects LockedException
  -> AuthenticationFailureLockedEvent
  -> internal audit ACCOUNT_LOCKED
  -> policy decides recovery/unlock
~~~

Do not treat the event as proof that this exact request just incremented the failed-attempt counter past the lock threshold.

### D. LDAP/IdP backend outage

~~~text
Provider throws AuthenticationServiceException
  -> AuthenticationFailureServiceExceptionEvent
  -> alert AUTH_SYSTEM_ERROR
  -> authentication fails closed
~~~

Never treat an outage as password guessing, and never fail open just because the backend temporarily errored.

### E. Valid API bearer JWT lacking permissions

~~~text
JWT signature/issuer/audience/exp validated
  -> authenticated principal exists
  -> authorization checks missing PAYMENT_APPROVE
  -> request denied (typically 403)
~~~

This is an authorization denial, **not** an `AuthenticationFailureBadCredentialsEvent`.

## 19. Testing by layer

| Test case | Expected |
|---|---|
| Correct password through manager with publisher. | Exactly one success event for the logical attempt. |
| Wrong password. | `AuthenticationFailureBadCredentialsEvent`. |
| Non-existent username. | Bad-credentials mapping and generic anti-enumeration response. |
| Disabled account. | `AuthenticationFailureDisabledEvent`. |
| Locked account. | `AuthenticationFailureLockedEvent`. |
| Expired account. | `AuthenticationFailureExpiredEvent`. |
| Expired credentials. | `AuthenticationFailureCredentialsExpiredEvent`. |
| No AuthenticationProvider. | `AuthenticationFailureProviderNotFoundEvent`. |
| Provider throws AuthenticationServiceException. | `AuthenticationFailureServiceExceptionEvent`; do not increment bad-password counter. |
| Invalid bearer token through publisher. | `InvalidBearerTokenException` mapped per actual flow. |
| No token sent to API. | Do not assume an event is emitted; verify entry point/filter. |
| Valid token lacking permissions. | Authorization denial, not counted as an auth failure. |
| Custom exception subclass of bad credentials. | Not auto-mapped unless exact mapping or fallback is declared. |
| Mapped custom exception. | Receives the expected custom event. |
| Listeners for superclass and subclass. | No double-counted audit records. |
| Parent/child AuthenticationManagers both publishing. | No duplicate counts after fixing configuration. |
| Stateless JWT sending 100 requests. | Do not infer 100 human logins. |
| Temporary audit sink failure. | Behavior meets SLA without leaking credentials or bypassing security. |
| Listener logging Authentication object. | Log canary test detects and blocks password/token leaks. |
| User enumeration. | Public status/body/redirect reveals no account state. |
| Multiple app instances. | Aggregation/rate limiting stays accurate without relying on listener memory. |

Test with `MockMvc` on the form login path, provider tests for exception mappings, context tests for `@EventListener`, JWT/OIDC/LDAP integration tests if used by the app, and privacy tests inspecting logs. A test checking "login returns 302 to dashboard" is **insufficient** to prove the event taxonomy works.

## 20. Implementation checklist and summary

- [ ] Identify AuthenticationManagers, Providers, and the publisher for every filter chain.
- [ ] Ensure `DefaultAuthenticationEventPublisher` is configured properly, avoiding overlapping beans.
- [ ] Listen for `AuthenticationSuccessEvent` and `AbstractAuthenticationFailureEvent`.
- [ ] Classify BadCredentials, UsernameNotFound, InvalidBearerToken, Disabled, Locked, AccountExpired, CredentialsExpired, ProviderNotFound, and AuthenticationService appropriately.
- [ ] Ensure custom exceptions have exact mappings or a concrete fallback event class.
- [ ] Do not confuse interactive logins, per-request token validation, MFA success, and authorization denials.
- [ ] Never log raw Authentication objects, credentials, bearer tokens, or sensitive exception messages.
- [ ] Keep public responses free from account enumeration.
- [ ] Prevent service errors from being treated as bad passwords causing mass lockouts.
- [ ] Keep listeners limited to audit/observability; place mandatory protections on the enforcement path.
- [ ] Define policies for duplicate handling, timeouts, backpressure, and audit durability.
- [ ] Use shared state/atomic counters for rate limiters across multiple instances.
- [ ] Maintain integration tests for every authentication mechanism actually in use.
- [ ] Enforce retention, access controls, source trust, and correlation IDs on audit data.

**Conclusion:** `AuthenticationSuccessEvent` describes an accepted result from an authentication flow, while subclasses of `AbstractAuthenticationFailureEvent` separate invalid credentials, disabled/locked/expired accounts, provider misconfigurations, and backend service errors. `DefaultAuthenticationEventPublisher` determines mapping **by exact exception class**, and Spring listeners can normalize them into safe audits/metrics. Ensure the publisher is actually wired, events are not double-counted, sensitive data is never logged, and authentication events are never confused with session lifecycles or authorization failures.
