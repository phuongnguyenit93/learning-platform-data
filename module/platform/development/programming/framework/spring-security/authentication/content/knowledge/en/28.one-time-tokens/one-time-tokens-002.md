# Distinguishing Server-Issued OTT from TOTP or HOTP

## 1. Context and Learning Objectives

In authentication systems, the phrase **one-time** is used for several different mechanisms. Spring Security provides the **One-Time Token Login (OTT)** feature for signing in with a token **issued by the server** and delivered to the user, for example via email in a magic link. Meanwhile, **HOTP** and **TOTP** are two algorithms for generating **One-Time Passwords (OTP)**: the device and the server share a secret key and compute short codes based on a counter or time.

Both groups aim to reduce the reusability of login codes, yet **their configurations cannot be substituted for one another**. `HttpSecurity.oneTimeTokenLogin(...)` does not mean Spring Security has implemented verification of six-digit codes from an authenticator app.

After this lesson, you can:

- Explain the issuer, delivery method, lifecycle, state, and single-use principle of **OTT**.
- Write the formulas, describe the **HOTP (RFC 4226)** and **TOTP (RFC 6238)** standards, and understand why both require secret key enrollment.
- Set up **Spring Security OTT** with `oneTimeTokenLogin`, `OneTimeTokenGenerationSuccessHandler`, `OneTimeTokenService`, token generation/submission endpoints, and account authentication.
- Distinguish **passwordless magic links**, **OTP codes in authenticator apps**, **OTP codes sent via SMS/email**, **password reset/recovery tokens**, and **Bearer access tokens**.
- Evaluate replay, brute force, time/counter synchronization, secret protection, rate limiting, URL leakage, mail scanners, phishing, and MFA requirements.
- Test single-use consumption of OTT and use a **Java 17+** program to verify HOTP/TOTP against RFC test vectors.

**Scope:** Spring Security Servlet/Spring MVC, focusing on Spring Security 6.4–6.5 and 7.x versions; HOTP/TOTP at the standalone algorithm level, without implying the framework provides end-to-end TOTP forms out of the box.

## 2. The Most Important Comparison Table

| Criterion | Server-Issued OTT | HOTP | TOTP |
| --- | --- | --- | --- |
| Full name | One-Time Token | HMAC-Based One-Time Password | Time-Based One-Time Password |
| Who generates the value submitted for verification? | **The server**, via `OneTimeTokenService` | Usually **authenticator/client** using a shared secret | Usually **authenticator/client** using a shared secret |
| Inputs to generate the value | Random token/opaque identifier bound to account and expiry | `K` (secret) and `C` (counter) | `K` and time-step `T` |
| Prerequisites | Needs a verified contact channel; no prior authenticator setup required | Enrollment/sharing of secret and counter synchronization | Enrollment/sharing of secret and time synchronization |
| How the user receives it | Link/email/SMS/out-of-band channel sent by the server | Authenticator/hardware OTP | Authenticator/hardware OTP |
| Typical code format | Long string, URL token/magic link | 6–8 digits (commonly used) | 6–8 digits (commonly used) |
| Lifetime | Expiry specified by the server, e.g. a few minutes | Based on **event counter**, does not auto-expire by wall clock | Based on **time window**, typically 30 seconds |
| Preventing reuse | **Atomically** delete/mark consumed on the server | Increment counter after verification, reject old counters | Track used time-steps to block reuse within the same window |
| Server state | Token→account/expiry/used, cache/DB | Secret and next accepted counter | Secret, clock skew policy, and replay state |
| Built-in support in Spring Security | **`oneTimeTokenLogin` since 6.4** | Not a feature of `oneTimeTokenLogin` | Not a feature of `oneTimeTokenLogin` |
| Common use cases | Passwordless login, magic link | Hardware token/event counter | Codes in authenticator apps, typically as an MFA step |

**Conclusion:** the core criterion is not "whether it has six digits", but **how the token is generated and verified**. An OTT can also be designed as a short code sent by the server via SMS, but if the receiving side merely looks up a code stored on the server, **it is not RFC-compliant HOTP/TOTP**.

## 3. Easily Confused Terms

### OTT in Spring Security

`OTT` here is a random credential generated by the server on request and linked to a username and expiration. The application sends the token to the recipient via a designated channel; the user submits the token back to the login endpoint. The server checks the token, **consumes** it, and establishes an `Authentication` session.

Example (illustrative string only):

```text
Application -> user's email:
https://login.example.org/login/ott?token=8a3ddab3-...-random

User clicks link -> browser goes to submit/confirm page.
Browser sends token to OTT processing endpoint.
Server verifies token is unexpired/unused -> signs in -> token becomes invalid.
```

The **single-use** property comes from server-managed state and the consume operation, not from an HMAC formula based on the current second. Submitting the same token a second time must fail.

### OTP Is a Family of Authentication Codes, Not TOTP by Default

`OTP` is a broad concept. Different systems may call a server-issued random SMS code an "OTP". Therefore:

- **OTP sent via SMS/email** may be a random code stored in a DB, i.e. a **server-issued code** model architecturally close to OTT.
- **HOTP** must be computed from a shared secret and counter per RFC 4226.
- **TOTP** must be computed from a shared secret and time-step per RFC 6238.
- **Recovery code** is a single-use backup code, usually pre-generated and stored/matched securely on the server. It is not automatically TOTP/HOTP.
- **Password reset token** verifies permission to reset a password and should not be used as a general login session unless the product intentionally permits it.
- **Bearer access token** (JWT/opaque) is also called a token, but is typically reused across many requests until expiration/revocation; it is **not automatically an OTT**.

### Passwordless and MFA Are Two Different Questions

**Passwordless** means signing in without a traditional password at that step. An OTT magic link to email can create a session by proving control over the mailbox.

**MFA** requires multiple authentication factors from distinct categories per policy (knowledge, possession, inherence, etc.) and depends on whether the factors are independent. TOTP is often used **after a password**, but a TOTP input field alone does not prove the application implements MFA. Similarly, email-sent OTT does not automatically become a "second factor" if the entire session relies on the same uncontrolled mailbox.

## 4. OTT Flow: Server Issuance, Delivery, and Consumption

Spring Security Servlet provides the `oneTimeTokenLogin(...)` DSL starting in **6.4**. The mechanism has two stages:

```text
Browser                      Spring Security                    Delivery
  |                                |                               |
  | POST /ott/generate             |                               |
  | username=linh                  |                               |
  |------------------------------->| GenerateOneTimeTokenFilter    |
  |                                | -> OneTimeTokenService.generate
  |                                |    (username, expiresAt)      |
  |                                | -> handler receives OneTimeToken
  |                                |------------------------------>| Email/SMS
  |<-------------------------------| generic response              |
  |                                |                               |
  | User receives magic link/token                                 |
  | GET /login/ott?token=...       |                               |
  |------------------------------->| Default submit page           |
  | POST token to login processor  |                               |
  |------------------------------->| OneTimeTokenAuthenticationFilter
  |                                | -> AuthenticationProvider     |
  |                                | -> OneTimeTokenService.consume
  |                                | -> user lookup/authorities    |
  |<-------------------------------| session/login or error        |
  |                                |                               |
  | Resend old token               |                               |
  |------------------------------->| consume fails                 |
  |<-------------------------------| not authenticated twice       |
```

Key points to understand:

1. **Issuance (`generate`)**: accepts account info and TTL, creates an unpredictable token, and stores verification/consumption capability on the server. In the default in-memory implementation, the value is randomly generated; there is no HMAC key shared with an authenticator app.
2. **Token delivery**: Spring Security does not know which email or phone number belongs to a user; a `OneTimeTokenGenerationSuccessHandler` is needed to send to a verified channel. Do not return the token in a public response to the requester.
3. **Token submission**: the user enters it or uses a link leading to the submit page. The browser sends the token to the authentication filter.
4. **Consumption (`consume`)**: a valid token is accepted **only once**, even if two requests arrive concurrently. The server-side implementation must guarantee atomicity in multi-instance deployments.
5. **Login**: after consumption, the authentication provider loads `UserDetails`/authorities as appropriate; authorization remains a separate step.
6. **Expiration**: no reuse is allowed past TTL; cleanup of expired token data must be managed.
7. **Invalid requests**: unknown, already-used, expired, or revoked tokens must fail. Do not tell outsiders whether a username exists.

Specifically, by default Spring Security uses `POST /ott/generate` to request a token and the `GET /login/ott` submit page; `loginProcessingUrl` can be customized. Check the actual API to determine the POST URL and parameters when replacing the form. Path shapes are merely HTTP configuration, not what defines the OTT algorithm.

## 5. Spring Security Components to Recognize

| Component | Role |
| --- | --- |
| `HttpSecurity.oneTimeTokenLogin(...)` | Enables the OTT login path in the Servlet `SecurityFilterChain` |
| `GenerateOneTimeTokenFilter` | Receives token generation requests |
| `OneTimeTokenGenerationSuccessHandler` | Sends the token via email/SMS or a trusted channel after creation |
| `OneTimeTokenService` | `generate(GenerateOneTimeTokenRequest)` and `consume(OneTimeTokenAuthenticationToken)` |
| `OneTimeToken` | Holds `tokenValue`, `username`, `expiresAt` |
| `OneTimeTokenAuthenticationFilter` | Receives the token submitted by the user at the login endpoint |
| `OneTimeTokenAuthenticationProvider` | Authenticates the pre-auth token and looks up the user, working with the service |
| `DefaultOneTimeTokenSubmitPageGeneratingFilter` | Generates the default OTT submit page when the corresponding feature is enabled |
| `InMemoryOneTimeTokenService` | Stores tokens in single-instance memory, suitable for demos/tests |
| `JdbcOneTimeTokenService` | A persistent option provided by Spring Security for DB-backed deployments |
| `UserDetailsService` | Loads the account/authorities of the logged-in user |

**Distinguishing easily confused names:** `OneTimeTokenAuthenticationToken` is the `Authentication` implementation object used in the pipeline; it is not an OAuth Bearer token for HTTP headers. `OneTimeToken` is the object representing the secret value with account info and expiry.

### Safety Warning on Account Status

In some current Spring Security lines, `OneTimeTokenAuthenticationProvider` **does not check by default** all states like `disabled`, `locked`, or `accountExpired`. Check the Javadoc for your version and configure `AccountStatusUserDetailsChecker` on the provider if product policy requires rejecting disabled accounts. Merely creating `UserDetails` with `enabled(false)` is not enough to assume every OTT version blocks it automatically.

## 6. Spring Boot 3.4+/Spring Security 6.4+ Example (Servlet, Java 17)

The following example illustrates **an OTT login path**, without TOTP. To avoid encouraging public token returns, the example uses email delivery and only uses a verified email directory. The `example.org` addresses are mock data; real applications must provide SMTP and real user records.

### 6.2. SecurityFilterChain and User Lookup

File `src/main/java/example/ott/OttSecurityConfig.java`:

```java
package example.ott;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

import static org.springframework.security.config.Customizer.withDefaults;

@Configuration
public class OttSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/", "/login", "/login/ott",
                                 "/ott/generate", "/ott/sent")
                    .permitAll()
                .requestMatchers("/me").authenticated()
                .anyRequest().denyAll()
            )
            // Do not enable formLogin/httpBasic for this passwordless demo.
            .oneTimeTokenLogin(withDefaults());

        return http.build();
    }

    @Bean
    UserDetailsService userDetailsService() {
        UserDetails user = User.withUsername("demo")
            // Demo: no password login is enabled in the filter chain.
            .password("{noop}unusable-for-real-login")
            .authorities("ROLE_USER")
            .build();
        return new InMemoryUserDetailsManager(user);
    }
}
```

Above, the `UserDetails` password is not used to verify OTT and the `formLogin`/`httpBasic` paths are not enabled. **Do not carry this `{noop}` password into a production application**, especially if password login is later enabled on another chain. Real systems must use an account repository, account status, and business roles. OTT login is accepted only when a valid account is loaded per the provider's verified policy.

### 6.4. Handler Sending the Magic Link via Email

File `src/main/java/example/ott/EmailOttSuccessHandler.java`:

```java
package example.ott;

import java.io.IOException;
import java.util.Optional;

import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.mail.SimpleMailMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.stereotype.Component;
import org.springframework.web.util.UriComponentsBuilder;

import org.springframework.security.authentication.ott.OneTimeToken;
import org.springframework.security.web.authentication.ott.OneTimeTokenGenerationSuccessHandler;
import org.springframework.security.web.authentication.ott.RedirectOneTimeTokenGenerationSuccessHandler;

@Component
public class EmailOttSuccessHandler
        implements OneTimeTokenGenerationSuccessHandler {

    private final JavaMailSender mail;
    private final VerifiedEmailDirectory directory;
    private final String baseUrl;

    public EmailOttSuccessHandler(
            JavaMailSender mail,
            VerifiedEmailDirectory directory,
            @Value("${app.public-base-url}") String baseUrl) {
        this.mail = mail;
        this.directory = directory;
        this.baseUrl = baseUrl;
    }

    @Override
    public void handle(
            HttpServletRequest request,
            HttpServletResponse response,
            OneTimeToken oneTimeToken)
            throws IOException, ServletException {

        Optional<String> destination =
            directory.findVerifiedEmail(oneTimeToken.getUsername());

        if (destination.isPresent()) {
            String link = UriComponentsBuilder.fromUriString(baseUrl)
                .path("/login/ott")
                .queryParam("token", oneTimeToken.getTokenValue())
                .build().encode().toUriString();

            SimpleMailMessage message = new SimpleMailMessage();
            message.setTo(destination.get());
            message.setSubject("One-time login link");
            message.setText("Single-use only, expires after the configured duration: "
                    + link);

            mail.send(message);
        }

        // Uniform response for usernames with or without a verified email.
        new RedirectOneTimeTokenGenerationSuccessHandler("/ott/sent")
            .handle(request, response, oneTimeToken);
    }
}
```

Marking the handler with `@Component` lets the DSL pick up the `OneTimeTokenGenerationSuccessHandler`. Spring Security only provides the token delivery hook; it **does not automatically know** which email is trusted for a user. This handler uses a static `PUBLIC_BASE_URL` to prevent login links from being poisoned by host headers. Without valid SMTP, email will not be sent and the demo cannot complete sign-in.

**Important warning:** SMTP error handling in production needs anti-user-enumeration policies, bounded retries, security telemetry, and the same public message for both existing and non-existing users. An email failure must never expose the token to the requester. Emails can be forwarded and URLs can appear in browser history; implement cookies/sessions, referrer policy, log redaction, TLS, and one-time consumption carefully.

## 7. OTT Token Storage: In-Memory, JDBC, TTL, Atomicity

### InMemoryOneTimeTokenService

Spring Security provides `InMemoryOneTimeTokenService` by default when no application-provided service exists. Per Spring Security 6.5 Javadoc, this service uses a `ConcurrentHashMap` and random UUID token values; `generate` returns a `OneTimeToken`, and `consume` returns the token object when valid or `null` when unusable.

Because it stores in process RAM:

- Restarting the application loses pending tokens.
- Two instances A/B have separate memory and do not share tokens automatically.
- Do not use it as distributed OTT storage in production while expecting a token from A to be consumed on B.
- TTL does not mean a background task immediately purges every record; check the cleanup policy of the specific version.

### JdbcOneTimeTokenService and Durable Storage

For multi-instance production environments, consider `JdbcOneTimeTokenService` and a shared DataSource (or equivalent custom service) to hold token state. Check the framework-supported DB schema, index/cleanup requirements, transactions, row locking, and behavior under two concurrent requests. Do not design your own `SELECT` followed by `DELETE` in two independent transactions: this can cause **double consume**.

Core principle:

```text
Is there an unexpired and unused token?
       |
       +-- no  -> authentication fails
       |
       `-- yes -> mark consumed or delete atomically
                    |
                    `-- exactly one request wins -> login
```

With a custom store, consider storing an **appropriately protected hash/digest** instead of the raw token if the lookup model allows, limit TTL, and bind the token to its purpose, username, and requesting session where applicable. This is a custom service design recommendation; **do not assume** Spring's default `JdbcOneTimeTokenService` applies a specific hash model without inspecting its implementation.

## 8. HOTP per RFC 4226: Shared Secret and Counter

**HOTP** is an algorithm that generates codes from:

- `K`: secret key shared at enrollment; must be kept confidential on both authenticator and server.
- `C`: counter (non-negative 64-bit integer) representing the next event/state.
- `HMAC-SHA1(K, C)`: MAC of the counter represented as 8 big-endian bytes.
- **Dynamic truncation**: extracts 31 bits from the HMAC at a determined offset, then takes modulo `10^digits`.

Notation:

```text
HOTP(K, C) = DynamicTruncate(HMAC-SHA1(K, C)) mod 10^Digits
```

Example with the same secret where different counters produce different codes:

```text
Counter 0 -> 755224
Counter 1 -> 287082
Counter 2 -> 359152
```

These are **RFC 4226 test vectors** for `K = ASCII("12345678901234567890")` and 6 digits. Do not use that public key in production.

### How Is HOTP Verified?

```text
Authenticator holds K, counter_client
       |
       | HOTP(K, counter_client) -> code entered by user
       v
Server holds K, counter_server
       |
       | Search in [counter_server, counter_server + lookAhead]
       |
       +-- match at C* -> update counter_server = C* + 1 (atomic)
       |                -> accept once
       `-- no match    -> reject, rate limit
```

Common mistake: only matching secret/counter without **incrementing the counter after acceptance**. An HOTP code could then be reused multiple times, violating replay protection. The look-ahead window must be small enough to limit brute-force risk. If the device and server fall out of sync, a controlled resynchronization mechanism with additional verification is required.

HOTP does not auto-expire every 30 seconds; **the counter is the moving factor**. A code can remain valid if the server has not advanced the counter and policy does not limit code age.

## 9. TOTP per RFC 6238: HOTP with Time-Step

**TOTP** builds on HOTP, replacing the event counter with a time-based counter:

```text
T = floor((UnixTimeSeconds - T0) / X)
TOTP(K, now) = HOTP(K, T)
```

Where:
- `K` is still the enrolled shared secret.
- `T0` is typically Unix epoch `0`.
- `X` is typically **30 seconds**; both sides must agree on the time-step.
- `Digits` is typically **6** or **8**; both sides must agree on length and HMAC algorithm.
- RFC 6238 supports HMAC-SHA1, SHA256, and SHA512; most common compatible authenticators use SHA1 per provisioning config.

For example, at UTC timestamp 59 seconds with `X=30`, we get `T=1`. With the RFC 6238 test secret and 8-digit SHA1, the code is **94287082**.

### Enrollment Is a Mandatory Step

Typical flow:

```text
Authenticated account with strong method and re-auth
           |
           v
Server generates sufficiently strong random secret K
           |
           v
Authenticator app receives K via protected QR/provisioning
           |
           v
Server stores encrypted secret K and metadata (digits, period, algorithm)
           |
           v
User proves possession of K with a valid TOTP code
           |
           v
Mark TOTP factor as enrolled
```

A common provisioning URI format:

```text
otpauth://totp/Example:linh?secret=JBSWY3DPEHPK3PXP&issuer=Example&algorithm=SHA1&digits=6&period=30
```

`JBSWY3DPEHPK3PXP` is only a **public demo secret** with no security value. In production, do not put real secrets into logs, analytics, URLs leaked by browsers, public QR codes, or documentation. The QR/URI must be treated as a **secret equivalent to the user's code-generation privilege**. Store the secret encrypted with a separate management key, restricting which people/processes can decrypt it.

### TOTP Verification Is More Than Comparing the Current Time's Code

Servers typically allow a small clock-skew window, e.g., time-steps `T-1`, `T`, `T+1` depending on risk. You need to:
- Synchronize clocks via NTP; configure `Clock` using UTC Unix epoch, independent of UI time zones.
- Compare valid codes per policy and rate limit, with temporary lockouts/backoff on failed guesses.
- **Record the last accepted time-step** per account/factor and block reuse of that exact time-step (especially under concurrent requests).
- Do not allow an unbounded skew window to compensate for bad clocks; the wider the window, the higher the guessing probability.
- Prevent distributed replay using atomic updates/a shared database across multiple instances.

Saying "the code changes every 30 seconds" **is not enough** to guarantee one-time use: if the same TOTP code is submitted twice within the same time-step and the server does not track used state, both can be accepted. This is a major difference from server-side OTT `consume`.

## 10. Plain JDK Java 17: Demonstrating HOTP and TOTP per RFC

The following program **runs standalone**, needing neither Spring nor external libraries. It implements HMAC-SHA1, dynamic truncation, 8-byte big-endian counters, and zero padding. The example restricts digits to 6 or 8 to avoid `10^digits` overflow in `int`.

Create file `HmacOtpDemo.java`:

```java
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.util.Locale;

import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class HmacOtpDemo {

    static String hotp(byte[] secret, long counter, int digits) throws Exception {
        if (secret == null || secret.length == 0 || counter < 0
                || (digits != 6 && digits != 8)) {
            throw new IllegalArgumentException("Invalid HOTP parameters");
        }

        byte[] counterBytes = ByteBuffer.allocate(Long.BYTES)
            .putLong(counter)
            .array(); // ByteBuffer defaults to BIG_ENDIAN.

        Mac mac = Mac.getInstance("HmacSHA1");
        mac.init(new SecretKeySpec(secret, "HmacSHA1"));
        byte[] hash = mac.doFinal(counterBytes);

        int offset = hash[hash.length - 1] & 0x0f;
        int binary =
              ((hash[offset]     & 0x7f) << 24)
            | ((hash[offset + 1] & 0xff) << 16)
            | ((hash[offset + 2] & 0xff) << 8)
            |  (hash[offset + 3] & 0xff);

        int modulus = (digits == 6) ? 1_000_000 : 100_000_000;
        int code = binary % modulus;
        return String.format(Locale.ROOT, "%0" + digits + "d", code);
    }

    static String totp(
            byte[] secret, long unixSeconds, long periodSeconds, int digits)
            throws Exception {
        if (periodSeconds <= 0 || unixSeconds < 0) {
            throw new IllegalArgumentException("Invalid time or period");
        }
        long timeCounter = unixSeconds / periodSeconds; // T0 = 0.
        return hotp(secret, timeCounter, digits);
    }

    public static void main(String[] args) throws Exception {
        byte[] testSecret =
            "12345678901234567890".getBytes(StandardCharsets.US_ASCII);

        System.out.println("HOTP counter=0: " + hotp(testSecret, 0, 6));
        System.out.println("HOTP counter=1: " + hotp(testSecret, 1, 6));
        System.out.println("TOTP time=59: " + totp(testSecret, 59, 30, 8));
        System.out.println(
            "TOTP time=1111111109: "
            + totp(testSecret, 1_111_111_109L, 30, 8)
        );
    }
}
```

Run command with JDK 17+:

```bash
javac HmacOtpDemo.java
java HmacOtpDemo
```

**Exact stdout per RFC 4226/6238:**

```text
HOTP counter=0: 755224
HOTP counter=1: 287082
TOTP time=59: 94287082
TOTP time=1111111109: 07081804
```

Explanation:
- `ByteBuffer` packs the counter into 8 bytes; never HMAC the decimal string `"0"` or `"59"`.
- `Mac` computes HMAC-SHA1; dynamic truncation derives the offset from the low 4 bits of the last byte and produces an **unsigned 31-bit** integer.
- `modulus` and `String.format` preserve the required digit count, including leading zeros like `07081804`.
- For TOTP, we use `unixSeconds / periodSeconds` when `T0=0`. With `59 / 30`, the time-step is `1`.
- `HmacSHA1` in this example was chosen to match **RFC test vectors**, not because all TOTP devices only support SHA1.
- Do not use this program as-is for a production login service: it **only generates codes**, without secure secret storage, enrollment, constant-time comparison, replay prevention, rate limiting, or account status checks.

### Why Does This Example Have No Spring Security OTT API?

This is the RFC **HOTP/TOTP algorithm**; it does not call `OneTimeTokenService`. Conversely, the OTT example in section 6 creates and consumes tokens with Spring Security without knowing `K`, `C`, or a time-step. The goal is to separate the two mechanisms clearly, rather than grafting HOTP codes into `OneTimeTokenGenerationSuccessHandler` and calling it an official TOTP implementation.

## 11. Comparing Verification and Anti-Replay Through Scenarios

### Scenario A — User Receives OTT via Email

1. Linh requests a magic link from the application.
2. The server issues `tokenA`, bound to Linh, expiring in a few minutes.
3. The link is sent to the verified mailbox.
4. Linh clicks the link and submits `tokenA`. The server **consumes** it and signs her in.
5. Linh reopens the old URL: rejected because `tokenA` has been consumed.
6. If an attacker intercepts the link and uses it **before** Linh, the token is still a bearer credential that can be hijacked. Single-use does not protect against prior use by an attacker.

### Scenario B — Authenticator Generates TOTP

1. Linh enrolls secret `K` with her account.
2. The authenticator at time `T` generates code `123456` (example, not a predicted demo value).
3. The server computes and compares codes at allowed time-steps.
4. On successful verification, the server records `T` as used.
5. Resubmitting `123456` within the old time-step must be rejected per anti-replay policy.
6. When entering a new time-step, the app generates a new code and the user does not have to wait for email.

Subtlety: if a TOTP implementation only computes current `T` and compares the code **without tracking used steps**, one code can succeed multiple times within the same 30 seconds. Being **time-based** does not replace the **one-time acceptance** requirement.

### Scenario C — HOTP on a Hardware Device

1. A hardware token has secret `K` and initial device counter `C=8`.
2. The user presses the button; the device generates HOTP for `C=8` and increments its counter.
3. The server holds the next expected counter `Cserver=8`; after verifying the code at 8, it updates to 9.
4. Pressing the device button multiple times without using the code can cause the client counter to run ahead of the server.
5. The server needs a look-ahead window or policy-controlled resynchronization; do not use TOTP's time-window to fix an HOTP counter.

## 12. Choosing the Right Technology for the Goal

| Goal | Recommendation |
| --- | --- |
| Passwordless login via email to a user with a verified mailbox | OTT/magic link with a server-issued token |
| User already signed in with password and needs an extra factor in an authenticator | TOTP if policy permits OTP; consider WebAuthn/passkeys for stronger phishing resistance |
| Device/hardware key generating codes per button press without relying on a clock | HOTP |
| Sending short codes via SMS/email when users have not installed an app | Server-issued and server-verified codes; **do not call them TOTP/HOTP** if they do not follow the RFCs |
| Approving sensitive transactions/actions | Factors bound to the transaction/request origin, re-auth, and anti-phishing policies; do not assume standalone OTT/TOTP suffices |
| Multi-node system needing tokens not to be used twice | Shared token store with atomic consume; for OTP, store replay/counter state centrally |
| Want strong protection against phishing and AitM | WebAuthn/FIDO2/passkey with origin binding, compared to phishable OTT/TOTP |

Never decide solely by digit count or the feeling that "every token is the same". Start from **what the user possesses, what information the server trusts, what mechanism prevents replay, and whether enrollment is required**.

## 13. Security Risks and Concrete Mitigations

### For OTT / Magic Links

- **Token secrecy:** a URL containing an OTT is a credential. Do not write raw URLs/query tokens into access logs, analytics, APM, chat, or error reporting systems.
- **TLS:** deliver over HTTPS; never use HTTP outside isolated local environments.
- **Issuance:** limit token creation per account/IP/device, prevent email flooding/SMS abuse, and use generic responses against username enumeration.
- **Deliver to the right person:** email/phone addresses must already be verified; do not accept a new address from an unauthenticated request to prevent account takeover.
- **Single-use:** `consume` must be atomic; never allow two requests with the same token to succeed.
- **Expiry:** reasonably short TTL; do not assume a new token invalidates old ones by default—define and test the service's policy.
- **Mail link scanner/prefetch:** link-checking bots may automatically **GET** the URL. Design GET to only open the confirmation/submit page; do not auto-convert GET into an authenticated session if prefetch protection is needed.
- **Session binding:** evaluate login CSRF, session fixation, session rotation after login, and opening the link in a different browser; prevent a link from signing a victim into an attacker's account.
- **Logging:** log only request IDs and sufficient failure reasons, never log the token.
- **User status:** account lock/disable or email changes must be enforced on OTT login per policy, rather than relying only on issued token data.
- **Recovery:** a compromised mailbox may mean a compromised account; require independent recovery checks and risk detection.

### For HOTP/TOTP

- **Secret K:** generated with a CSPRNG, length/algorithm per policy, protected at rest, in backups, and in transit; if K leaks, an attacker generates the exact same codes as the authenticator.
- **Enrollment:** require re-auth to add/remove/reset an authenticator; verify a code before enabling and alert the user when factor configuration changes.
- **Rate limit:** a 6-digit code has only about one million possibilities before considering the acceptance window; limit guess attempts and block distributed brute force.
- **Clock/counter:** TOTP requires time sync and drift limits; HOTP requires atomic counter updates and bounded resync.
- **Replay:** track the last accepted step/counter; do not rely solely on "the code has expired".
- **Phishing:** OTP codes can be phished and replayed in real time; OTP is not inherently phishing-resistant.
- **Backup/recovery:** recovery codes must be issued separately, stored securely, each consumed once, and factor resets must go through a trusted process.

### Shared Policy Needs for Both Groups

Do not let user input select someone else's `username` to **bypass** email/secret verification. Endpoint permissions after login still depend on `Authentication`/authorization. Locking or revoking a login method is a separate action from invalidating existing sessions.

## 14. Testing and QA by Mechanism

| Test Case | OTT | HOTP/TOTP |
| --- | --- | --- |
| Valid value generation | `OneTimeTokenService.generate` | RFC test vectors / HMAC algorithm |
| Who receives the generated value? | **Verified** contact address | Secret enrolled on the right device |
| Reuse same value | Second `consume` must fail | Accepted counter/time-step must be rejected |
| Expiration | TTL/token expiry | TOTP time-window expires; HOTP uses counter, no default 30-second TTL |
| Two concurrent requests | Exactly one consume wins | Replay state/counter must update atomically |
| Non-existent user | External response reveals nothing | No valid secret/enrollment exists |
| Locked/disabled user | Check account status/provider | Check account status before verifying/completing login |
| Rate limit | Block generate spam and consume brute force | Block brute force per user/IP/device/time window |
| Time skew | Mainly depends on server expiry | TOTP must test bounded drift |
| Counter skew | Not applicable | HOTP look-ahead/resynchronization |
| DB/node failure | Verify shared token store, expiry, consistency | Verify secret, last accepted step/counter are durably stored |
| Secret or mailbox change | Revoke old tokens/verify new email per policy | Revoke/re-enroll secret and apply proper invalidation |

**OTT integration tests** must observe the HTTP flow, CSRF, email delivery (mail test server), cookies/sessions, and first login vs. second attempt. **HOTP/TOTP unit tests** must use RFC vectors and failure paths; then integration-test MFA behavior and account recovery. A JUnit test calling only an HMAC helper does not prove the system prevents phishing, blocks replay, or enforces MFA correctly.

## 15. API Differences Across Spring Security Versions

| Version | Status/Implementation Direction |
| --- | --- |
| **Before 6.4** | No `oneTimeTokenLogin` DSL as shown in this lesson; magic links require custom flows or upgrading |
| **6.4** | Added OTT Login support, `OneTimeTokenService`, handlers, and related filters |
| **6.5** | Expanded OTT generation request customization; use `GenerateOneTimeTokenRequestResolver` in Servlet |
| **7.x** | OTT still exists; check the exact version's Javadoc because URL config methods and account status/MFA may change across minors; do not mix up Servlet and Reactive APIs |
| **Reactive/WebFlux** | Has dedicated reactive components like `ReactiveOneTimeTokenService` and `ServerOneTimeTokenGenerationSuccessHandler`; do not plug Servlet `OneTimeTokenAuthenticationFilter` directly into `SecurityWebFilterChain` |

In Spring Security 6.5, an example changing the default 5-minute TTL to 10 minutes using a bean **inserted into** a configuration class (with appropriate imports for the Servlet `web.authentication.ott` package):

```java
@Bean
GenerateOneTimeTokenRequestResolver generateOneTimeTokenRequestResolver() {
    DefaultGenerateOneTimeTokenRequestResolver delegate =
        new DefaultGenerateOneTimeTokenRequestResolver();

    return request -> {
        GenerateOneTimeTokenRequest original = delegate.resolve(request);
        return new GenerateOneTimeTokenRequest(
            original.getUsername(), Duration.ofMinutes(10)
        );
    };
}
```

This code uses `GenerateOneTimeTokenRequest` in `org.springframework.security.authentication.ott`, and `GenerateOneTimeTokenRequestResolver`/`DefaultGenerateOneTimeTokenRequestResolver` in `org.springframework.security.web.authentication.ott`; matching imports plus `java.time.Duration` are required. **This is a configuration snippet**, not a standalone Java file; version 6.4 may not provide this customization hook.

In 6.5, Servlet docs also use the URL configuration name **`generateTokenUrl(...)`**, whereas some 7.x Javadoc/docs use **`tokenGeneratingUrl(...)`**. Apply only the method matching the version in your project's dependency tree. URL config method renames do not turn OTT into TOTP or HOTP algorithms.

## 16. Self-Check Questions

**Question 1:** A user enters `123456` received via server SMS. Is that enough evidence to conclude it is TOTP?

**Answer:** No. You must know whether the code was **computed from K and a time-step** or is simply a random server-stored code for lookup. Having six digits and a 30-second TTL does not prove TOTP.

**Question 2:** Can a TOTP code be reused within the same 30 seconds?

**Answer:** If the verifier only checks HMAC/time-window without remembering the **accepted step**, the same code can be accepted again. Secure designs must explicitly prevent replay.

**Question 3:** Is a single-use magic link definitely MFA?

**Answer:** No. It can be **passwordless single-factor** relying on mailbox access. Calling it MFA requires identifying independent factors verified per policy.

**Question 4:** Does Spring `oneTimeTokenLogin()` read a Base32 seed from Google Authenticator?

**Answer:** No. The DSL configures **server-issued OTT**. For TOTP, you need enrollment, secret generation/storage, an RFC 6238 verifier, a replay store, rate limiting, and integration into the proper authentication flow (or a dedicated IdP/MFA solution).

**Question 5:** Once an OTT token is successfully `consume`d, must it be deleted from the DB?

**Answer:** What is mandatory is that it **cannot be authenticated with again**. Deleting or marking it used in an atomic operation are corresponding design approaches; physical storage details depend on the `OneTimeTokenService` implementation.

**Question 6:** Both HOTP and TOTP include "one-time" in their names, so can the server omit replay state?

**Answer:** No. HOTP must advance the next counter; TOTP must block reusing an already-accepted step. A short code matching the formula is not enough to achieve one-time acceptance at the verification layer.

## 17. Summary

OTT, HOTP, and TOTP can all help users authenticate with short-lived or single-use values, yet they **differ in generation source, required state, delivery method, and verification method**:

- **OTT (Spring Security 6.4+):** the server generates, stores, and delivers the token out-of-band, then **consumes it once**. Suitable for magic links/passwordless login; must protect email delivery, TLS, token store, account status, CSRF, and sessions.
- **HOTP (RFC 4226):** both authenticator and server hold `K` and use **counter C**; the server increments the counter on success and supports controlled resync.
- **TOTP (RFC 6238):** both hold `K` and use **time-step T**; the server allows small clock skew and must prevent replay within the active window.

Never choose a solution by the UI label "OTP/OTT". Identify the goal (passwordless, MFA, recovery), risk level, what the user possesses, secret-protection capability, replay-prevention requirements, and multi-instance architecture, then select the right tool.
