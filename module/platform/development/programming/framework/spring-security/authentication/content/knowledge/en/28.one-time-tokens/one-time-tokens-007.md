# Expiration, Single-Use Consumption, and Concurrent Request Handling of One-Time Tokens

## 1. Why Is a "One-Time" Token a State Problem, Not Just a Random String?

A **one-time token (OTT)** is a secret permitted to produce a successful authentication/action outcome **once**, within a defined **time window** and **purpose**. Typical examples: login magic links, email verification links, password reset tokens, or approvals for sensitive actions.

Three conditions must be checked **together**:

1. **Valid source and purpose:** the token was created by an authorized system and bound to the right account/action/tenant.
2. **Unexpired:** the server's evaluation time is still **before** `expiresAt`.
3. **Unconsumed:** no other request has already won the right to use the token.

Satisfying only two of the three allows the system to accept a wrong-purpose, expired, or replayed token.

### Security Invariants

- **At-most-once acceptance:** for a given token, at any time, **at most one request** may transition it from unused to used successfully.
- **Expiry enforced:** the token must not be usable when `now >= expiresAt`; scheduled deletion of expired rows is only cleanup and **cannot replace expiry checks at consumption time**.
- **Purpose binding:** a password reset token must not work for login; an email verification token must not change a password.
- **No silent privilege escalation:** a valid token does not bypass account status, tenant, or action-condition checks.
- **Fail closed:** if token state cannot be verified due to DB/service failure, never accept by default.
- **Atomicity across concurrent requests:** never produce two successes because requests read the same `unused` value.

**Terminology note:** "one-time" refers to **an issued token**; it does not automatically guarantee an account has only one active token at a time. A "single latest link per user" policy is an additional requirement that must be designed explicitly.

## 2. Distinguishing OTT, OTP, TOTP/HOTP, and Authorization Codes

| Concept | How Created and Used | What Must Be Guaranteed |
| --- | --- | --- |
| **OTT** (one-time token, magic link) | Server issues a high-entropy random string and tracks state/mapping to consume | TTL, purpose, atomic consumption, anti-replay |
| **OTP delivered via SMS/email** | Short code issued by the server for a single verification | Short TTL, attempt limits, anti-brute-force, atomic consumption |
| **TOTP** | Time-based code from a shared secret and algorithm | Prevent replay within the time window if policy requires single-use; attempt limits |
| **HOTP** | Code from a secret and counter | Atomic counter update; anti-replay and counter-drift handling |
| **OAuth2 authorization code** | Authorization Server issues a code exchanged once for tokens | Client/redirect URI/PKCE binding and discarding code after valid exchange |
| **CSRF token** | Value protecting a transaction or form | Dedicated lifecycle rules; do not assume every CSRF token is a single-use OTT |

In **Spring Security 6.4+**, `oneTimeTokenLogin()` supports **server-issued OTT**. Do not equate it with TOTP/HOTP generated by authenticator apps, or with JWT access tokens reusable across multiple requests until `exp`.

## 3. State Machine and Expiration Boundary

A token moves through business states:

```text
                     issue(secure random, account, purpose, TTL)
                                      |
                                      v
                                ISSUED/UNUSED
                                  /       \
                      valid consume      now >= expiresAt
                                |                |
                                v                v
                           CONSUMED           EXPIRED
                                |
                           replay -> DENY

   REVOKED: admin/user changes password, cancels request, issues new token
             per policy -> DENY even if TTL remains.
```

At the DB level you can store `consumed_at` and `revoked_at`, or use a status column. You do not have to actively flip rows to `EXPIRED`; once past the deadline, the consumption query must reject it even if the DB still shows `unused`. Cleanup jobs can delete old rows later.

### Time Boundary Rule

Given `issuedAt = 10:00:00Z` and `expiresAt = 10:05:00Z`:

| Evaluation Timestamp | Accepted If Token Is Still UNUSED? |
| --- | --- |
| `10:04:59.999Z` | Yes, if purpose matches and atomic claim succeeds |
| `10:05:00.000Z` | **No** |
| `10:05:00.001Z` | **No** |

The right condition is `now.isBefore(expiresAt)` in Java, or `expires_at > now` in SQL. Do not use `now <= expiresAt` when the exact expiration instant must be rejected.

**Clocks:** store timestamps as `Instant`/UTC; multi-machine systems must synchronize clocks. With a centralized DB, consider evaluating against the DB clock to avoid node clock skew. In PostgreSQL, `CURRENT_TIMESTAMP` is the transaction start time; if a transaction waits long on a lock, checking with `clock_timestamp()` at evaluation time may be needed to avoid accepting based on a stale timestamp. Never trust client-supplied timestamps to decide validity.

**TTL is an upper limit, not a delivery-speed guarantee:** users receiving delayed mail may find the link already expired. Never "auto-extend old tokens"; provide a rate-limited way to request a fresh token.

## 4. Classic Race Condition: Check Then Update

Unsafe code:

```java
// WRONG PSEUDOCODE: two separate calls do not form an atomic operation.
var token = repository.findByHash(hash);
if (token != null && !token.isUsed() && token.getExpiresAt().isAfter(now)) {
    createLoginSession(token.getAccountId()); // side effect
    repository.markUsed(hash);
}
```

An interleaved execution can occur:

```text
Time           Request A                         Request B
  1            read token: unused
  2                                              read token: unused
  3            expiry check: pass
  4                                              expiry check: pass
  5            create session A
  6                                              create session B
  7            mark used
  8                                              mark used

=> Two successes even though only one row ends up with used=true.
```

Variants that **are still insufficient**:

- Using `synchronized` on a controller in **one JVM**: does not lock other instances.
- Reading the row and then calling `deleteById`: two requests can both read successfully before deletion; a return value from the read step does not prove you won.
- Wrapping `SELECT` then `UPDATE` in `@Transactional` without proper locking/conditional update: depending on isolation level, both can still read the same state.
- Checking cache `containsKey` followed by `remove` in two separate calls: still check-then-act.
- Using Redis `GET` then `DEL`: two non-atomic network commands; you need an atomic command/transaction/script checking conditions and expiry in one step.

**Right approach:** check unused/unexpired/purpose conditions and **claim the right to consume as a linearizable operation** (*linearizable claim*) on the shared data store. Only the request confirmed by the store as "claim succeeded" may proceed.

## 5. Data Design to Prevent Replay

A token model can include:

| Field | Meaning |
| --- | --- |
| `token_hash` | Hash of the secret token; unique/indexed; avoid storing raw tokens unnecessarily |
| `account_id` | Owning account or intended subject |
| `purpose` | `MAGIC_LOGIN`, `RESET_PASSWORD`, `VERIFY_EMAIL`, ... |
| `created_at` | Issuance timestamp |
| `expires_at` | Validity cutoff, stored in UTC |
| `consumed_at` | Null when unused, timestamp when claimed |
| `revoked_at` | Null when unrevoked |
| `tenant_id` / `challenge_id` | Partitioning and business binding if needed |
| `attempt_count` / audit metadata | Supports rate limiting and investigation without recording raw secrets |

**Illustrative PostgreSQL DDL** (not Spring Security's automatic schema):

```sql
CREATE TABLE app_one_time_tokens (
    token_hash CHAR(64) PRIMARY KEY,
    account_id VARCHAR(100) NOT NULL,
    purpose VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    consumed_at TIMESTAMPTZ,
    revoked_at TIMESTAMPTZ,
    CHECK (expires_at > created_at)
);

CREATE INDEX idx_ott_account_purpose
    ON app_one_time_tokens (account_id, purpose);
```

**Token generation:** use `SecureRandom` to generate at least 128 bits of entropy, typically 256 bits, then encode with Base64URL. A 32-byte random token has a search space far too large for direct brute force when kept secret properly. For **high-entropy tokens**, storing the SHA-256 of the raw value can be reasonable; for **6–8 digit OTPs**, plain SHA-256 offers poor protection if the DB leaks because the search space is tiny—consider server-secret HMAC, keyed lookup and rate limiting, or an appropriate verification design.

**Never use** `java.util.Random`, timestamps, predictable custom UUIDs, emails, or DB sequence numbers as secret tokens. Random UUID v4 has meaningful entropy, yet you must ensure it is genuinely securely generated v4 and fits policy; raw 32 bytes from `SecureRandom` is a clearer example.

In HTTP requests, never put raw tokens into logs, traces, query metrics, or exception messages; send tokens only over the intended channel and preserve exact purpose.

## 6. PostgreSQL: Consuming via a Single Conditional UPDATE

A safe transaction can use an **atomic claim** statement:

```sql
-- PostgreSQL: run inside the business transaction.
UPDATE app_one_time_tokens
SET consumed_at = clock_timestamp()
WHERE token_hash = :token_hash
  AND purpose = :purpose
  AND consumed_at IS NULL
  AND revoked_at IS NULL
  AND expires_at > clock_timestamp()
RETURNING account_id;
```

Explanation:

- The request computes `token_hash` from the received raw token; `:purpose` comes from **endpoint/server policy**, never letting the client widen the purpose.
- The database locks and updates the row matching the predicate. If request A wins, request B cannot update the same row because `consumed_at IS NULL` no longer holds once A commits.
- **One row returned** means the token was claimed successfully; **zero rows** means not found/expired/used/revoked/wrong purpose.
- `clock_timestamp()` is PostgreSQL's current time when evaluated, rather than `CURRENT_TIMESTAMP` frozen at the start of a long transaction. The written `consumed_at` and the expiry comparison may differ infinitesimally because it is evaluated twice; systems needing a single strictly identical instant can compute the timestamp once or after acquiring the lock and reuse it consistently.
- Ensure an index on `token_hash`. `RETURNING` is **PostgreSQL** syntax and does not apply verbatim to all RDBMSs.

When updating a password:

```text
BEGIN TRANSACTION
    claim token via UPDATE ... WHERE unused + unexpired
    if 0 rows -> reject and ROLLBACK (or exit with no changes)
    if 1 row  -> check account, password policy, account state
              -> UPDATE users SET password_hash = ...
              -> invalidate sessions/recovery links per policy
COMMIT
```

**Claiming the token and updating business data belong in the same DB transaction** whenever both actions must succeed or roll back together. Never send emails, call external APIs, or create sessions in another service inside a transaction and claim end-to-end "exactly once": external side effects can succeed while the DB rolls back, or vice versa. For external work, use a **transactional outbox + idempotency key**, explicit business state, and safe retries.

### When Multiple Operations Are Genuinely Required

Some flows must inspect the account, MFA state, token purpose, password-change rules, etc. after locking. Choose among:

- A single `UPDATE ... WHERE ... RETURNING` placing every feasible predicate into one statement;
- `SELECT ... FOR UPDATE` then checking/writing **in the same transaction** without releasing the lock early;
- Conditional write using version/CAS/optimistic locking, verifying the updated row count.

Above all, never execute side effects **before** knowing the claim succeeded.

## 7. Redis, MongoDB, and Multiple Instances

If tokens live in Redis:

- For tokens stored with a TTL where you only need to consume the existing value, `GETDEL key` (on supported Redis versions) atomically gets and deletes. Key expiration is enforced by the Redis server.
- If you must atomically check `purpose`, account state, or multiple keys before deleting, use a properly designed Lua script or transaction. Never do separate `GET` then `DEL`.
- If you need to roll back a token when a DB operation fails, Redis and the DB are **two separate transaction systems**. Design sagas/idempotency or co-locate coupled state in the same DB; never treat `GETDEL` as a transaction covering the DB.
- Pick appropriate TTLs, secure Redis credentials/TLS, and consider failover/replication consistency; if strict anti-replay is required, test behavior during primary failover.

In MongoDB, `findOneAndUpdate` with a filter `used=false` and `expiresAt > now` atomically claims one document; a TTL index only handles cleanup and does not replace checking expiry at claim time.

**Storing in a JVM `ConcurrentHashMap`** suffices to demonstrate atomicity within one process, yet **does not** guarantee single-use across 2 pods/instances of the same service. In distributed deployments, the store and transaction must be shared and consistent.

## 8. Runnable Java 17 Example: One Token, 12 Competing Requests, Exactly One Winner

The snippet below uses only Java SE 17, needing no Spring or server; copy it into **`OneTimeTokenDemo.java`** and run to observe replay/concurrency/expiry/purpose. The code generates raw tokens via `SecureRandom`, stores **SHA-256 hashes** in a `ConcurrentHashMap`, and consumes via per-key atomic `compute`.

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicReference;

public class OneTimeTokenDemo {
    record TokenRecord(String subject, String purpose, Instant expiresAt) {}

    // Mutable clock ONLY for testing expiration boundary; do not use
    // this MutableClock in production.
    static final class MutableClock extends Clock {
        private volatile Instant current;

        MutableClock(Instant current) {
            this.current = Objects.requireNonNull(current);
        }

        @Override public ZoneId getZone() { return ZoneOffset.UTC; }
        @Override public Clock withZone(ZoneId zone) {
            return Clock.fixed(current, zone);
        }
        @Override public Instant instant() { return current; }

        void advance(Duration duration) {
            current = current.plus(duration);
        }
    }

    static final class TokenStore {
        private final ConcurrentHashMap<String, TokenRecord> records =
                new ConcurrentHashMap<>();
        private final SecureRandom random = new SecureRandom();
        private final Clock clock;

        TokenStore(Clock clock) {
            this.clock = Objects.requireNonNull(clock);
        }

        String issue(String subject, String purpose, Duration lifetime) {
            if (subject == null || subject.isBlank()
                    || purpose == null || purpose.isBlank()
                    || lifetime == null
                    || lifetime.isZero() || lifetime.isNegative()) {
                throw new IllegalArgumentException("Invalid token request");
            }

            byte[] secret = new byte[32];
            random.nextBytes(secret);
            String raw = Base64.getUrlEncoder().withoutPadding()
                    .encodeToString(secret);

            TokenRecord item = new TokenRecord(
                    subject, purpose, clock.instant().plus(lifetime));
            if (records.putIfAbsent(digest(raw), item) != null) {
                throw new IllegalStateException("Random token collision");
            }
            return raw;
        }

        Optional<String> consume(String raw, String requiredPurpose) {
            if (raw == null || raw.isBlank()
                    || requiredPurpose == null || requiredPurpose.isBlank()) {
                return Optional.empty();
            }

            AtomicReference<TokenRecord> accepted = new AtomicReference<>();

            // compute() serializes updates for a single key in CHM.
            records.compute(digest(raw), (hash, stored) -> {
                if (stored == null) {
                    return null;
                }
                if (!clock.instant().isBefore(stored.expiresAt())) {
                    return null; // expired -> remove
                }
                if (!stored.purpose().equals(requiredPurpose)) {
                    return stored; // wrong purpose: do not consume token
                }

                accepted.set(stored);
                return null; // right purpose/unexpired -> remove atomically
            });

            TokenRecord result = accepted.get();
            return result == null
                    ? Optional.empty()
                    : Optional.of(result.subject());
        }

        private static String digest(String raw) {
            try {
                byte[] hash = MessageDigest.getInstance("SHA-256")
                        .digest(raw.getBytes(StandardCharsets.UTF_8));
                return HexFormat.of().formatHex(hash);
            } catch (NoSuchAlgorithmException ex) {
                throw new IllegalStateException(ex);
            }
        }
    }

    public static void main(String[] args) throws Exception {
        MutableClock clock =
                new MutableClock(Instant.parse("2026-01-01T00:00:00Z"));
        TokenStore store = new TokenStore(clock);
        String token = store.issue(
                "alice", "magic-login", Duration.ofMinutes(5));

        int workers = 12;
        ExecutorService executor = Executors.newFixedThreadPool(workers);
        CountDownLatch gate = new CountDownLatch(1);
        List<Future<Boolean>> attempts = new ArrayList<>();

        for (int i = 0; i < workers; i++) {
            attempts.add(executor.submit(() -> {
                gate.await();
                return store.consume(token, "magic-login").isPresent();
            }));
        }

        gate.countDown();
        int accepted = 0;
        for (Future<Boolean> future : attempts) {
            if (future.get()) {
                accepted++;
            }
        }
        executor.shutdown();

        System.out.println("simultaneousAccepted=" + accepted);
        System.out.println("replayAccepted="
                + store.consume(token, "magic-login").isPresent());

        String purposeToken =
                store.issue("bob", "reset-password", Duration.ofMinutes(2));
        System.out.println("wrongPurposeAccepted="
                + store.consume(purposeToken, "verify-email").isPresent());
        System.out.println("correctPurposeSubject="
                + store.consume(purposeToken, "reset-password")
                        .orElse("none"));

        String expiring =
                store.issue("carol", "magic-login", Duration.ofSeconds(30));
        clock.advance(Duration.ofSeconds(30));
        System.out.println("atExpirationAccepted="
                + store.consume(expiring, "magic-login").isPresent());
    }
}
```

Run:

```bash
javac OneTimeTokenDemo.java
java OneTimeTokenDemo
```

**Deterministic stdout:**

```text
simultaneousAccepted=1
replayAccepted=false
wrongPurposeAccepted=false
correctPurposeSubject=bob
atExpirationAccepted=false
```

### Why Is the Example Race-Free?

- `ConcurrentHashMap.compute(hash, remapping)` serializes updates on **one key** in the process, never splitting the check and deletion.
- The first call seeing a valid entry sets `accepted` for that exact invocation and returns `null`, removing the entry inside the atomic operation.
- Later requests see `stored == null` and thus return `Optional.empty()`; no second request can read the valid entry before the mutation completes.
- `AtomicReference` safely passes the **current compute call's** result out of the lambda. Each call has its own instance, never sharing results across requests.
- When expired, the entry is removed without setting `accepted`. On wrong purpose, the entry is **not consumed**, so its owner can still use it with the right purpose before expiry.
- `CountDownLatch` starts 12 tasks competing at nearly the same instant; thread scheduling decides *who* wins, **not** how many win: always at most one.
- `MutableClock` lets us test the exact `now == expiresAt` boundary without `Thread.sleep(...)` (sleep tests are often flaky).

### Limitations of the Example

- This is an **in-memory single-JVM demo**, not distributed repository code or a production token store.
- "Consume" only returns the subject, **without creating an HTTP session, checking account status, or committing a business action**.
- The demo lacks token-request rate limiting, batch record cleanup, account revocation, auditing, email sending, or database row TTLs.
- For a "one active token per account" constraint, you need an index/generation policy beyond the token-hash map.
- `SHA-256` is reasonable here only because the token has 256 random bits; **do not copy this hash design verbatim for a few-digit OTP**.
- If targeting WebFlux, `ConcurrentHashMap.compute` is very brief and I/O-free; DB/network queries must use async drivers or proper schedulers, never running blocking JDBC on the event loop.

## 9. Connecting to Spring Security One-Time Token Login

Spring Security **6.4 and above** supports `oneTimeTokenLogin()`. With Servlet (Spring MVC):

```java
// Config snippet inside a @Configuration class in Spring MVC:
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/ott/sent").permitAll()
                    .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults())
            .oneTimeTokenLogin(Customizer.withDefaults())
            .build();
}
```

Key imports for this snippet:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
```

This is a **configuration snippet**, not a standalone Java app. It needs a real Spring Boot app, user store, and a bean delivering tokens/magic links over a user-verified channel. Spring Security does not automatically know each account's email/SMS, so a `OneTimeTokenGenerationSuccessHandler` must be configured or registered per official guidance.

### APIs to Know

| API | Role |
| --- | --- |
| `OneTimeTokenService` | Interface to generate and consume one-time tokens |
| `generate(GenerateOneTimeTokenRequest)` | Generates and persists a new token bound to user/expiration |
| `consume(OneTimeTokenAuthenticationToken)` | Claims a presented token; returns `OneTimeToken` if valid, `null` otherwise |
| `OneTimeToken.getTokenValue()` | Raw secret to deliver to the user via a protected channel |
| `OneTimeToken.getUsername()` | User identity linked to the token |
| `OneTimeToken.getExpiresAt()` | Expiration timestamp |
| `OneTimeTokenAuthenticationProvider` | Uses the service to consume tokens and authenticates per policy/provider |
| `OneTimeTokenAuthenticationFilter` | Receives tokens and processes sign-in in Servlet |
| `InMemoryOneTimeTokenService` | Default implementation suitable for demos/single node |
| `JdbcOneTimeTokenService` | Persistent implementation over JDBC, suitable to consider for multi-instance environments |

**Spring Security 6.5 defaults:** token lifetime can be configured via `GenerateOneTimeTokenRequestResolver`; documentation illustrates a default of **5 minutes** and lets you customize `expiresIn`. This is a feature-specific default, not a rule that all application tokens must use a 5-minute TTL.

Interface signature:

```java
// API signature excerpt, not a standalone Java file:
public interface OneTimeTokenService {
    OneTimeToken generate(GenerateOneTimeTokenRequest request);
    @Nullable
    OneTimeToken consume(OneTimeTokenAuthenticationToken authenticationToken);
}
```

`@Nullable` here highlights that **invalid/expired/already-used** cases have no token to authenticate. Never call `getUsername()` on the result of `consume` without checking for null.

### Replacing In-Memory Storage with JDBC

`JdbcOneTimeTokenService` accepts `JdbcOperations`:

```java
@Bean
OneTimeTokenService oneTimeTokenService(JdbcOperations jdbcOperations) {
    return new JdbcOneTimeTokenService(jdbcOperations);
}
```

Imports: `org.springframework.security.authentication.ott.OneTimeTokenService`, `org.springframework.security.authentication.ott.JdbcOneTimeTokenService`, `org.springframework.jdbc.core.JdbcOperations`. This example requires the official SQL schema at classpath `org/springframework/security/core/ott/jdbc/one-time-tokens-schema.sql`; **do not use** the `app_one_time_tokens` table from section 5 and pretend the default JDBC implementation can read it.

**Review points for real deployments:** verify the transactions/consume logic of your implementation and exact Spring Security version under concurrent load, especially with your database engine, isolation level, and multiple instances. Run integration tests proving only one token claim succeeds. Replace the default implementation when you need purpose/account-state binding, auditing, or custom revocation policies.

### Changing TTL in Spring Security 6.5

The 6.5 docs illustrate `DefaultGenerateOneTimeTokenRequestResolver`:

```java
// Config snippet, requires matching Spring Security 6.5.
@Bean
GenerateOneTimeTokenRequestResolver generateOneTimeTokenRequestResolver() {
    var delegate = new DefaultGenerateOneTimeTokenRequestResolver();
    return request -> {
        var generated = delegate.resolve(request);
        return new GenerateOneTimeTokenRequest(
                generated.getUsername(), Duration.ofMinutes(10));
    };
}
```

Imports are in `org.springframework.security.web.authentication.ott` for the resolver, `org.springframework.security.authentication.ott.GenerateOneTimeTokenRequest` for the request, plus `java.time.Duration`. This illustrates the **TTL-setting mechanism**; choosing 10 minutes should stem from risk analysis, email delivery latency, and UX requirements.

### Servlet and WebFlux Differ

In **Spring WebFlux**, the DSL also has `oneTimeTokenLogin()`, yet the service contract is `ReactiveOneTimeTokenService`: `generate(...)` and `consume(...)` return `Mono<OneTimeToken>`; invalid tokens return an empty publisher. The default implementation is `InMemoryReactiveOneTimeTokenService`. The filter chain uses `ServerHttpSecurity` and `SecurityWebFilterChain`, not `HttpSecurity`.

Whether the app is Servlet or reactive, **atomic consume remains the persistence layer's responsibility**. `Mono` or `@Transactional` does not automatically turn a `SELECT` followed by `DELETE` into an atomic operation across nodes.

## 10. When Many Requests Arrive Concurrently: Understanding "Once" Precisely

Three distinct concepts:

- **At-most-once acceptance:** at most one request may claim the token; the minimum property required for OTT.
- **At-least-once processing:** the client retries until it receives confirmation; a non-idempotent system may execute the task repeatedly.
- **Exactly-once effect:** the business effect appears exactly once where observed. This is stronger and harder, especially across multiple systems.

Example: request A claims the token and updates the password, yet the client connection drops before returning HTTP 200. The client retries with the old token and is rejected. That **does not mean** the first password reset failed; proper UX and state tracking are needed without leaking sensitive data.

If request A claims a token inside a DB transaction and errors before commit, transaction rollback returns the token to unused state. A subsequent request B/retry can win. The final outcome can still be correct when operation and consume share a transaction. However, if the system already sent an email or called a downstream API before rolling back, that side effect may have already happened and repeat. When "once" is needed across external systems, use an **outbox, event IDs, and idempotent consumers**, not just a `used` flag.

### What Is a Linearization Point?

The linearization point is the moment the system decides **precisely which request wins**. In the Java demo it is `ConcurrentHashMap.compute(...)` on a single key; in a DB it is `UPDATE ... WHERE ... RETURNING` or an equivalent transaction/lock; in Redis it can be `GETDEL` or a properly designed atomic script.

All losing requests must never create sessions, change passwords, or grant permissions; nor should they reveal which request won or account details if that aids enumeration.

## 11. Two Concurrent Requests to Issue a New Token

Besides races during **consumption**, there are races during **issuance**:

```text
T1: User clicks "Resend link" -> creates token A
T2: User quickly clicks again -> creates token B
Email B arrives first, Email A arrives later.
User clicks A: should it work or not?
```

Policy options:

1. **Allow multiple independent active tokens:** A and B are both valid until expiry, each consumable once. Easy to implement; reduces "delayed link invalidated" issues but increases the count of active secrets.
2. **Latest-wins:** issuing B revokes A for the same account + purpose. Must execute revoke-old + insert-new atomically, or use a generation/version checked at consume time.
3. **One outstanding token per account/purpose:** a unique constraint or row-level transaction prevents two requests from creating two active rows. Must define whether retries/resends send the same secret or issue a new one.
4. **Single-flight requests:** rate-limit/coalesce closely spaced requests to reduce email/SMS spam; be careful not to resend raw tokens if only hashes are stored without a safe design.

**Latest-wins does not replace single-use.** Even when only token B remains active, two concurrent requests using B still require atomic consumption.

If storing a version, consumption must check the **account's current version inside the same transaction or under clear consistency rules**. Never check the version once at the start of a request and apply side effects after the version has changed.

## 12. Magic Links: Preventing Bots, Link Scanners, and Token-Consuming GETs

Email security scanners, preview bots, chat apps, or browsers may **open links before the user** to check safety. If `GET /login?token=...` **consumes immediately**, the token gets burned by a bot and the real user sees "link already used".

A safer flow:

1. Email contains a link to a confirmation page over HTTPS.
2. `GET` only renders the appropriate page/form, **creating no session and consuming nothing**.
3. The user actively clicks "Continue/Sign in"; `POST` sends the token in the body alongside CSRF/state protections per flow.
4. Backend performs **atomic consume**, checks account status, and only then completes authentication/action.
5. Navigate the user to a URL free of raw tokens, avoiding storing tokens in history, Referer, logs, or analytics.

Note: moving the token into `POST` does not solve everything. If the initial link had the secret in the query URL, the secret can still appear in browser history, email services, or reverse proxy logs. Apply `Referrer-Policy`, sanitize the URL quickly, restrict third-party scripts, avoid placing tokens in fragments/JavaScript without understanding trust boundaries, and mitigate clickjacking/phishing.

**Do not make it easy for scanners to submit POSTs** where high security is required; consider human confirmation steps, session/nonce-bound challenges, anti-automation defenses, and purpose-based policies. Never rely on `User-Agent` to detect bots.

## 13. Account Status and Business Actions

A password-reset token may be sent while an account is active; by the time the user clicks the link, the account may have been:

- locked/disabled;
- deleted or moved to another tenant;
- updated with a new primary email address;
- forced by an admin to re-authenticate/MFA;
- updated via another password-reset method;
- stripped of all recovery tokens via revocation.

Therefore **a valid token must not mean "allowed to do everything"**. At consumption time, verify current account conditions and purpose. Policies may revoke tokens immediately when a password changes or an account is disabled; implementation must be consistent and tested.

**Sensitive scenarios:** a magic login token can create an account session, yet the session afterward must still enforce session fixation protection, secure cookies, timeouts, and MFA/step-up when business rules require it. Never grant admin privileges merely for holding an emailed link.

**Login versus password reset:**

- For magic login, the side effect may be creating an authenticated session in Servlet/WebFlux. Atomic consume happens before reporting login success; if session creation fails, the app needs UX to request a new token.
- For password reset, put the password hash update and token claim in the **same DB transaction** when possible; after commit, invalidate sessions/refresh tokens per policy.
- For email verification, updating the verified flag can be idempotent, yet the token still needs single-use policy to prevent privilege-transfer or misdirected email-change flows.
- For payments/approvals, never rely on an OTT as a complete transaction protocol; require authorization and idempotent business operations.

## 14. Common Security and Implementation Bugs

**1. Expired tokens still work.** Only a cron job deletes tokens, with no `expiresAt > now` predicate during consume. Fix on the verification/DB update path; cleanup is not a trust boundary.

**2. Token replayed and both requests succeed.** Reading `used=false` then writing `used=true` separately. Fix with atomic claims, affected-row checks, and concurrency tests.

**3. Using `synchronized` yet still racing in Kubernetes.** Mutexes apply only within a single JVM. Use shared DB/Redis state and appropriate transactions/atomic operations.

**4. Using `get` then `remove` on a `ConcurrentHashMap`.** That is non-atomic check-then-act. Use `remove(key, expectedValue)` safely where applicable or per-key `compute`.

**5. Trusting the client's clock.** Clients can alter their clocks. Use a server-injected `Clock` or DB clock; test boundaries and clock skew.

**6. Wrong-purpose token reuse.** Hashes are accepted on every endpoint because `purpose` is not stored. Bind tokens to action, account, tenant, and policy in the claim step.

**7. Token consumed, yet logs/emails still hold raw secrets.** People with log access can inspect sensitive data, especially when logs stream to multiple systems. Redact raw tokens from URLs/headers/bodies and audit via irreversible IDs/hashes.

**8. A 6-digit OTP stored with unkeyed SHA-256.** If the DB leaks, an attacker can brute-force all one million codes offline. Use keyed hashes/server secrets, short TTLs, and attempt limits; never treat "hashed" as equivalent to brute-force resistance.

**9. Request claims the token and then the action fails.** Token is gone without completing the business task; or the action succeeded yet the DB rolled back. Design shared transactions where possible, and outbox/idempotency when external services are involved.

**10. Link gets hit by a scanner beforehand.** GET executes consume. Switch to GET rendering the page and POST confirming; evaluate automation defenses and URL leaks.

**11. Admin locks account yet old tokens still sign in.** Account status or session revocation is not checked after consume. Enforce policies at usage time.

**12. Repeated token requests on one email arrive out of order.** No clear latest-wins/multi-active policy. Define the policy and store version/generation if needed.

**13. Returning account details on every token submission.** Distinct responses for "user does not exist", "token expired", and "token already used" leak data. Use appropriate notices and separate auditing while preserving UX.

**14. Unbounded retries on DB/introspection errors.** Uncontrolled retries cause load spikes and races; never fail-open. Use bounded retries, timeouts, circuit breakers, and idempotent semantics.

**15. Only sequential unit tests.** Testing 1st request succeeds and 2nd fails is insufficient under concurrency. Use barriers/concurrent load and assert results **against the shared data store**.

**16. Deleting the token from the DB before committing external side effects.** Leads to "token consumed yet action lost" or "executed twice" on retry. Design outbox/transactions and business compensation.

## 15. Essential OTT Test Suite

| Test Case | Input | Expected |
| --- | --- | --- |
| Valid first use | Token matching owner/purpose, before `expiresAt` | Succeeds once |
| Replay | Already-consumed token | Rejected, side effect does not re-run |
| Time boundary | `now == expiresAt` | Rejected |
| Just before boundary | `now < expiresAt` by a tiny margin | Accepted if atomic claim succeeds |
| Expired still in DB | Cleanup cron has not run yet | Rejected |
| Wrong purpose | Password reset token sent to email verification | Rejected, not consumed for the valid purpose |
| Invalid/unknown token | String absent from store | Safely rejected |
| Disabled account | Unexpired token for locked account | Rejected per policy |
| Concurrent in one JVM | 12–100 requests with same token | Winning requests **at most 1**; with valid token and healthy store: exactly 1 |
| Concurrent across instances | Requests distributed across multiple pods | At most 1 wins on shared store |
| Race with expiry | Token expires while waiting on a lock | Rejected past expiry per chosen time definition |
| Race with revocation | Admin revokes near consumption time | Consistent ordering/transaction rules |
| DB rollback | Consume succeeds in txn but business logic fails | No half-committed side effects; retry behavior matches policy |
| Two new issuance requests | A/B created concurrently | Matches latest-wins or multi-active policy |
| Email scanner GET | Link opened without confirmation | Does not consume token on GET |
| Expired record deletion | Cleanup runs alongside consume | Never causes two successes or unhandled exceptions |
| Issuance/guessing abuse | High frequency, brute force | Rate limit, generic response, telemetry, no account leaks |

### Proper Load Testing

- Use a barrier (such as `CountDownLatch`) to fire many requests near-simultaneously.
- Do not inspect only HTTP responses: verify DB `consumed_at`, count of created sessions/actions, and audit rows.
- Run tests repeatedly, including across **two instances** sharing a DB, under production isolation levels and simulated network delays.
- Test failures between steps: after claim and before business update; before commit; after commit and before sending response.
- Never accept a test that only checks "the DB ended up with `used=true`"; assert **successful side effect count equals one**.

## 16. Monitoring and Operations

Track actionable metrics without recording secrets:

- Token issuance requests per account/IP/tenant per window, and email/SMS failure rates.
- Rates of successful consume, invalid, expired, and already-used (details in secure audit only).
- Latency from issue to consume and percentage of tokens expiring unused; use this to tune TTLs.
- Unusual retries/concurrency on an anonymized hash/token ID.
- Post-claim rollbacks, DB lock wait timeouts/deadlocks, Redis failovers, and email scanner incidents.
- Rate of users requesting fresh tokens; alert on brute-force campaigns or email flooding.

You do not need raw tokens in audit logs to detect replay: record a dedicated short ID/hash or keyed truncated token fingerprint with a separate tracking key and retention policy after a privacy review. **Never log raw tokens or full verifier values**. Pseudonymize emails/usernames as well when sufficient for operations.

A log showing only HTTP status codes does not prove tokens are unleaked: audit the full pipeline from **ingress to APM, frontend monitoring, backups, and DLQs**. Security reviews should include automated log-redaction tests using a synthetic canary token, never a real user's token.

## 17. Pre-Deployment Decision Checklist

1. Do tokens have strong entropy, secure delivery channels, and zero exposure in logs/analytics?
2. Does every token carry an explicit **purpose**, account/tenant, and server-side expiration?
3. Is the expiry boundary strictly `now < expiresAt` with synchronized UTC clocks?
4. Is consumption a **single atomic/transactional operation** even across multiple pods?
5. Are successful claim and business action inside the same transaction when needed?
6. When calling external systems, are outbox/idempotent consumers and retry handling in place?
7. Is the multi-token-per-user policy latest-wins or multi-active, and are issue/revoke races handled?
8. Can GET on an email/magic link accidentally consume when crawlers/link scanners hit it?
9. Do account locks, password changes, or privilege revocations invalidate unused tokens?
10. Do error responses prevent username/token enumeration while still letting users request a new valid link?
11. Have concurrency tests run against a real shared store, including failure injection, expiry boundaries, and rollbacks?
12. With Spring Security `oneTimeTokenLogin()`, do service persistence and TTL satisfy your **exact framework version's** requirements?
