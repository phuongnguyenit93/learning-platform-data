# RelyingPartyRegistration, Metadata, and Trust Information in SAML 2.0

In **Spring Security SAML 2.0 Login**, the application acts as the **Service Provider (SP)**, while the federated login system is the **Identity Provider (IdP)**. In Spring Security terminology, the two sides are also called the **Relying Party (RP)** and **Asserting Party (AP)**, respectively. To trust a SAML outcome, the application must know *which SP it is, which IdP it is working with, where to send/receive messages, and which public key to use for signature verification*. Spring Security represents this configuration primarily through **`RelyingPartyRegistration`**.

**RelyingPartyRegistration is neither a login session nor a user.** It is the configuration of **one SP–IdP pair**. A system can hold multiple registrations when supporting multiple IdPs, tenants, or environments, yet each SAML authentication must be matched against the **exact** trusted registration.

This lesson progresses from configuration structure, two-sided metadata, keys and trust boundaries, to a Spring Security Servlet example, key rollover operations, and testing.

## 1. Four Concepts to Keep Separate

| Concept | Owner / Content | Role |
| --- | --- | --- |
| **RelyingPartyRegistration** | Spring Security configuration for one RP–AP pair, identified by `registrationId` | Defines the expected values when sending and receiving SAML |
| **IdP metadata** (AP metadata) | IdP publishes `EntityDescriptor / IDPSSODescriptor` | Tells the SP the issuer/entityID, SSO endpoint, bindings, signing verification certificates, and protocol options |
| **SP metadata** (RP metadata) | SP publishes `EntityDescriptor / SPSSODescriptor` | Tells the IdP the SP entityID, ACS endpoint, and signing/decryption certificates if used |
| **SAML Response/Assertion** | Generated by the IdP on **each login** | Contains the authentication outcome, NameID/attributes/conditions, and signature for the SP to verify |

The two kinds of metadata are **configuration information** enabling the two parties to know each other; SAML Response/Assertion is **per-login runtime data**. Never confuse importing metadata with having authenticated a user.

Configuration exchange and login diagram:

~~~text
TRUST ESTABLISHMENT PHASE
IdP metadata --------------------------> SP RelyingPartyRegistration
SP metadata (entityID, ACS, key, ...) --> IdP application config

SSO PHASE
Browser --> SP /saml2/authenticate/corp
             |
             v
        AuthnRequest --> IdP SSO endpoint
                           |
                        User login
                           |
               SAML Response/Assertion
                           |
Browser -------- POST ----> SP /login/saml2/sso/corp
                           |
              Resolve registration "corp"
              Validate signature, issuer, destination,
              audience, time, and other conditions
                           |
                    Authentication
                           |
               Account mapping/authorization
~~~

**Trust does not emerge automatically from XML.** A metadata XML file can describe keys and endpoints, but the application should accept it only after verifying a trustworthy **metadata source and key distribution process**.

## 2. What Does a Registration Represent?

Important properties of a `RelyingPartyRegistration`:

| Property or Group | Belongs To | Meaning |
| --- | --- | --- |
| `registrationId` | Spring application | Internal name to select configuration, e.g., `corp`; **not** a SAML entityID |
| `entityId` | SP | SP issuer/entityID recognized by the IdP; may be a URI, not necessarily a browsable URL |
| `assertionConsumerServiceLocation` | SP | ACS address where the browser POSTs the SAML Response |
| `assertionConsumerServiceBinding` | SP | Binding used for ACS, typically HTTP-POST |
| `signingX509Credentials` | SP | Private key and certificate used by SP to sign SAML requests when needed |
| `decryptionX509Credentials` | SP | Private key/certificate used to decrypt encrypted assertions/nameIDs/attributes |
| `assertingPartyMetadata().getEntityId()` | IdP | Expected IdP EntityID/Issuer in SAML |
| `singleSignOnServiceLocation` | IdP | SSO endpoint receiving AuthnRequest |
| `singleSignOnServiceBinding` | IdP | How AuthnRequest is sent, such as HTTP-Redirect or HTTP-POST |
| `verificationX509Credentials` | IdP | Trusted public certificates to verify IdP signatures |
| `wantAuthnRequestsSigned` | IdP | IdP preference/requirement for signed requests, coordinated with SP signing keys |

Method names can differ across versions: in Spring Security **6.4+**, the **`assertingPartyMetadata`** and **`getAssertingPartyMetadata`** APIs appear in recent documentation; older APIs named **`assertingPartyDetails`** / **`getAssertingPartyDetails`** are deprecated. Use the API matching your actual dependency version; do not mix 6.x and 7.x examples.

**Three easily confused identifiers**:

~~~text
registrationId  = corp
SP entityId     = https://app.example.org/saml2/service-provider-metadata/corp
IdP entityId    = https://login.example.org/saml/idp
~~~

- `corp` is only a lookup key in the Spring repository.
- SP entityID is the **application** identifier accepted by the IdP as the relying party/audience.
- IdP entityID is the **issuer** identifier against which the SP validates responses.
- Login/metadata/ACS URLs may contain `corp`, but sharing a substring does not make these properties the same thing.

A registration only describes **expected** values. At runtime, the SAML provider must still verify signatures and assertion conditions before granting a login session.

## 3. What Does IdP Metadata Contain and How Does the SP Use It?

SAML metadata is XML conforming to the SAML 2.0 Metadata specification. For an IdP, the relevant section typically looks like:

~~~xml
<md:EntityDescriptor
    xmlns:md="urn:oasis:names:tc:SAML:2.0:metadata"
    entityID="https://login.example.org/saml/idp">
    <md:IDPSSODescriptor
        protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
        <md:SingleSignOnService
            Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect"
            Location="https://login.example.org/saml/sso"/>
    </md:IDPSSODescriptor>
</md:EntityDescriptor>
~~~

This is an **XML snippet for identifying fields** and intentionally omits `KeyDescriptor`, so it is **not sufficient as a production trust configuration**. Real metadata usually contains `KeyDescriptor use="signing"` with certificates or key info, and may include `SingleLogoutService`, `validUntil`, `cacheDuration`, a signature on the metadata itself, and multiple entities inside an `EntitiesDescriptor`.

When importing, inspect the actual values:

1. **IdP `entityID`:** must match the response/assertion issuer under validation rules.
2. **`SingleSignOnService` and binding:** the SP sends AuthnRequest to the matching endpoint. A wrong URL or binding breaks login before any response is received.
3. **Signing `KeyDescriptor`:** forms the basis for verifying SAML Response/Assertion signatures. Keys must come from an approved source, not merely because an XML file declares them.
4. **Metadata expiry/signature:** when `validUntil`, metadata signatures, or update workflows exist, you need a strategy for handling expiration and validating metadata.
5. **Multiple IdP entities:** pick the exact entity for the registration; never accidentally wire another IdP's keys and endpoints.

From metadata, Spring Security can construct **`AssertingPartyMetadata`** inside the registration. It may also retain extended OpenSAML attributes depending on import method and version.

**Important distinction between two signature types:** a **metadata XML** signature proves the metadata document comes from a trusted source when checked with a trusted key; a **SAML Response/Assertion** signature proves the login message was created by the holder of the corresponding signing key and was not altered. The two steps use different keys, scopes, and timing. Checking one does not replace checking the other.

## 4. What Is SP Metadata Used For?

The IdP needs to know the SP's identity and where to send the SAML Response. SP metadata typically contains:

- `EntityDescriptor entityID="..."`: the SP entityID itself.
- `SPSSODescriptor`: the SP's SSO capability details.
- `AssertionConsumerService`: the ACS address + binding (usually POST).
- `KeyDescriptor use="signing"`: the SP's public certificate so the IdP can verify signed AuthnRequests/LogoutRequests.
- `KeyDescriptor use="encryption"`: the SP's public certificate if the IdP must encrypt assertions for the SP.
- Some profiles include single logout endpoints, NameID formats, and other declared attributes.

Simplified XML schema:

~~~xml
<md:EntityDescriptor
    xmlns:md="urn:oasis:names:tc:SAML:2.0:metadata"
    entityID="https://app.example.org/saml2/service-provider-metadata/corp">
    <md:SPSSODescriptor
        protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
        <md:AssertionConsumerService
            Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
            Location="https://app.example.org/login/saml2/sso/corp"
            index="0"/>
    </md:SPSSODescriptor>
</md:EntityDescriptor>
~~~

This too is only a **structural recognition snippet**, not the complete metadata generated by Spring. When deploying, use the endpoint generated by Spring Security and **inspect the actual exported document**.

### SP Metadata Is Not IdP Metadata

- Load **IdP metadata** to configure the SP side.
- Export **SP metadata** to register the SP at the IdP.
- Do not pass SP metadata into `RelyingPartyRegistrations.fromMetadataLocation(...)` expecting Spring to treat it as an IdP.
- Do not take the IdP website's TLS certificate as the SAML signature verification certificate unless the IdP officially publishes that exact key for SAML signing.

SAML metadata is a **configuration/public-key descriptor**, not a secret store; however, endpoint, entity, and certificate details still require accurate change management, auditing, environment, and tenant isolation.

## 5. Configuration Example Using IdP Metadata

This example targets **Spring Security Servlet** with Spring Boot + Java 17. You need a real IdP and verified metadata; URLs and entities in this lesson belong to the `example.org` domain and are not live services.

Gradle Groovy dependencies:

~~~groovy
repositories {
    mavenCentral()
    maven { url "https://build.shibboleth.net/maven/releases" }
}

dependencies {
    implementation "org.springframework.boot:spring-boot-starter-web"
    implementation "org.springframework.boot:spring-boot-starter-security"
    implementation "org.springframework.security:spring-security-saml2-service-provider"
}
~~~

Use your project's Spring Boot/BOM dependency management to keep Spring Security and OpenSAML aligned. The Shibboleth repository may be needed for OpenSAML dependencies; follow your organization's current repository settings rather than manually adding mismatched versions.

Place **verified IdP metadata** at classpath location `saml/corp-idp-metadata.xml`. Java configuration:

~~~java
package demo.saml;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.saml2.provider.service.registration.InMemoryRelyingPartyRegistrationRepository;
import org.springframework.security.saml2.provider.service.registration.RelyingPartyRegistration;
import org.springframework.security.saml2.provider.service.registration.RelyingPartyRegistrationRepository;
import org.springframework.security.saml2.provider.service.registration.RelyingPartyRegistrations;
import org.springframework.security.web.SecurityFilterChain;

@Configuration(proxyBeanMethods = false)
public class SamlSecurityConfig {

    @Bean
    RelyingPartyRegistrationRepository relyingPartyRegistrations() {
        RelyingPartyRegistration registration = RelyingPartyRegistrations
                .fromMetadataLocation("classpath:saml/corp-idp-metadata.xml")
                .registrationId("corp")
                .entityId("https://app.example.org/saml2/service-provider-metadata/corp")
                .assertionConsumerServiceLocation(
                        "https://app.example.org/login/saml2/sso/corp")
                .build();

        return new InMemoryRelyingPartyRegistrationRepository(registration);
    }

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {
        return http
                .authorizeHttpRequests(authorize -> authorize
                        .anyRequest().authenticated())
                .saml2Login(Customizer.withDefaults())
                .saml2Metadata(Customizer.withDefaults())
                .build();
    }
}
~~~

**This is a configuration class for a Spring Boot Servlet application**; it cannot be run standalone with just `javac`. You need a Spring Boot main class, the IdP metadata resource, network connectivity, and reciprocal registration at the IdP. The program will not fabricate an IdP or real accounts.

What was configured:

- Loads **AP/IdP** details (issuer, SSO endpoint, verification certificate, ...) from approved metadata.
- Creates a registration named `corp`.
- Pins **SP entityID and ACS** to match what the IdP registered for the application.
- Stores the registration in `RelyingPartyRegistrationRepository` for SAML filters to look up.
- Enables SAML login and the SP metadata publishing endpoint via the `saml2Login` and `saml2Metadata` DSLs.

If the IdP requires **signed AuthnRequests**, the SP must have real signing credentials (private key + certificate) and the IdP must know the SP's public certificate. The minimal snippet above **does not supply a signing private key**. When IdP metadata requires signing without matching credentials, requests can fail; never disable the signing requirement just to bypass configuration errors.

If your environment uses **Spring Boot property auto-configuration**, you can configure `spring.security.saml2.relyingparty.registration.*` properties instead of defining a repository bean. Pick a **single primary configuration source** and verify which `RelyingPartyRegistrationRepository` bean is actually active.

## 6. Manual Configuration Example Without XML Metadata

When an IdP provides its issuer, SSO URL, and public signing certificate through a separate administrative channel, you can build the registration manually using the builder. Code snippet for **Spring Security 6.4+**:

~~~java
X509Certificate idpSigningCertificate = ...; // load from an approved source
Saml2X509Credential idpVerification =
        Saml2X509Credential.verification(idpSigningCertificate);

RelyingPartyRegistration registration = RelyingPartyRegistration
        .withRegistrationId("corp")
        .entityId("https://app.example.org/saml2/service-provider-metadata/corp")
        .assertionConsumerServiceLocation(
                "https://app.example.org/login/saml2/sso/corp")
        .assertingPartyMetadata(party -> party
                .entityId("https://login.example.org/saml/idp")
                .singleSignOnServiceLocation(
                        "https://login.example.org/saml/sso")
                .wantAuthnRequestsSigned(false)
                .verificationX509Credentials(
                        credentials -> credentials.add(idpVerification)))
        .build();
~~~

This is a **configuration snippet, not a standalone program**: `idpSigningCertificate` must be loaded from a real PEM/certificate via Java's certificate parsing API; the ellipsis represents an input provided by infrastructure, not data magically synthesized by the app. Required imports:

~~~java
import java.security.cert.X509Certificate;

import org.springframework.security.saml2.core.Saml2X509Credential;
import org.springframework.security.saml2.provider.service.registration.RelyingPartyRegistration;
~~~

`wantAuthnRequestsSigned(false)` is appropriate only when **the IdP permits unsigned AuthnRequests and federation policy accepts it**. It does **not** mean skipping Response/Assertion signature verification. If the IdP requires signed requests, configure the SP's `signingX509Credentials` and register the corresponding certificate at the IdP.

When working exclusively with Spring Security **6.3**, the `assertingPartyMetadata` API may not exist yet; use the builder/API appropriate for your running version. Newer Spring Security releases replaced the older `assertingPartyDetails` API with the metadata API, so always verify code snippets from other releases before copying.

### Spring Boot Configuration via YAML

The following example shows **Spring Boot 3.x** declaring issuer, SSO URL, and IdP certificate directly:

~~~yaml
spring:
  security:
    saml2:
      relyingparty:
        registration:
          corp:
            entity-id: "https://app.example.org/saml2/service-provider-metadata/corp"
            acs:
              location: "https://app.example.org/login/saml2/sso/corp"
            assertingparty:
              entity-id: "https://login.example.org/saml/idp"
              singlesignon:
                url: "https://login.example.org/saml/sso"
                sign-request: false
              verification:
                credentials:
                  - certificate-location: "classpath:saml/idp-signing.crt"
~~~

Property names/aliases may change between **Spring Boot 3.x** and **4.x**; check `Saml2RelyingPartyProperties` for your exact version. Unlike the Java example that parses metadata, the YAML above declares **individual fields**, so the certificate path must point to the IdP's real public certificate.

The Java and YAML examples are **two alternative ways to teach configuration**; do not declare the same registration from both sources simultaneously without understanding override precedence.

## 7. Default URIs and Their Relationship to registrationId

In Spring Security Servlet SAML login:

| Common URI | Who Calls It | Function |
| --- | --- | --- |
| `/saml2/authenticate/{registrationId}` | Browser / SP-initiated SSO | SP generates AuthnRequest for the selected registration |
| `/login/saml2/sso/{registrationId}` | Browser POST from IdP | ACS, receives SAMLResponse |
| `/login/saml2/sso/` | Browser POST from IdP | An ACS option supported depending on configuration/registration resolution capability |
| `/saml2/metadata` | IdP admin / integration | Publishes SP metadata |
| `/saml2/metadata/{registrationId}` | IdP admin / integration | Metadata for a specific registration |
| `/saml2/service-provider-metadata/{registrationId}` | IdP admin / integration | Per-registration metadata path, compatible convention |
| `/logout/saml2/sso` | SAML Single Logout | Active only when SLO is properly configured and supported |

Spring resolves these common placeholders:

- `{registrationId}`: the registration name, e.g., `corp`.
- `{baseUrl}`: scheme, host, and port of the application in the request context.
- `{baseScheme}`, `{baseHost}`, `{basePort}`: individual base URL components.

Important default values:

~~~text
SP entityId:
  {baseUrl}/saml2/service-provider-metadata/{registrationId}

SP Assertion Consumer Service Location:
  {baseUrl}/login/saml2/sso/{registrationId}
~~~

When deployed at `https://app.example.org` with registrationId `corp`, these typically become:

~~~text
https://app.example.org/saml2/service-provider-metadata/corp
https://app.example.org/login/saml2/sso/corp
~~~

Exact formatting depends on mappings and deployment setup. **EntityID does not need to be a reachable URL**; if you use a specific URI as entityID, the IdP must be configured with the exact match. **The ACS URL, however, must point to an endpoint capable of receiving POST requests.**

### Reverse Proxies and Forwarded Headers

If Internet traffic passes through an ingress/gateway and reaches Spring Boot over internal HTTP, `{baseUrl}` may resolve to `http://127.0.0.1:8080` or an internal hostname instead of the public URL. Then SP metadata, AuthnRequest issuer, or ACS can be wrong and rejected by the IdP.

Mitigation steps:

1. Configure the correct scheme/host/public port on the ingress and use Spring/container trusted forwarded-header handling.
2. **Only trust forwarded headers from controlled proxies**; the proxy must strip client-supplied headers from outside.
3. Where appropriate, configure **absolute entityID and ACS** as in the examples instead of relying on inferred baseUrl.
4. Fetch SP metadata from the **actual public URL** and cross-check issuer/ACS against the IdP configuration.

Never disable SAML Destination/Audience checks to "fix" host or scheme errors. Fix routing configuration and metadata values first.

## 8. What Exactly Is Trusted: Keys, Issuer, Endpoints, and Conditions?

A secure SP–IdP relationship relies on multiple layers, not just a single certificate.

| Check | Where Trusted Data Comes From | Risk If Skipped |
| --- | --- | --- |
| **IdP issuer** | Approved `assertingPartyMetadata.entityId` | Accepting assertions from a different issuer |
| **Response/Assertion signature** | Trusted IdP `verificationX509Credentials` | Accepting forged or tampered responses |
| **SP audience / entityID** | `RelyingPartyRegistration.entityId` | Reusing an assertion issued for a different SP |
| **Destination / Recipient** | Configured ACS/public URL | Delivering a response to the wrong destination |
| **Validity window** | Assertion Conditions and SubjectConfirmation | Reusing expired or not-yet-valid assertions |
| **InResponseTo / state** | Generated AuthnRequest and matching state | Accepting a response not tied to the login session when required by profile |
| **Decryption when encrypted** | SP `decryptionX509Credentials` | Unable to read encrypted payloads, or misconfigured keys |
| **Local account and permissions** | Application user store / mapping policy | Linking the wrong user or granting excessive privileges |

Spring Security's SAML authentication provider performs many of these SAML checks. However, operational responsibility still includes **configuring the exact expected values, never replacing validators with loose logic, and never trusting an XML response merely because it contains a NameID**.

A dangerous failure case:

~~~text
Trusted IdP: https://login.company-a.example/saml
SAML Issuer: https://login.attacker.example/saml
Self-asserted Response NameID: alice@company-a.example
~~~

If a request is not verified against the **right IdP issuer, key, and registration**, NameID is just an untrusted external string. Never use NameID/email to look up an account before SAML authentication completes.

### Role of Saml2X509Credential

Spring Security represents SAML certificates/keys with `Saml2X509Credential` for distinct purposes:

- **VERIFICATION (IdP):** SP holds the IdP's **public certificate** to verify SAML Response/Assertion signatures.
- **SIGNING (SP):** SP holds a **private key + certificate** to sign AuthnRequests or logout requests when required by profile.
- **DECRYPTION (SP):** SP holds a **private key + certificate** to decrypt assertions/attributes/NameIDs if the IdP encrypts them.
- **ENCRYPTION (IdP):** depends on profile and encryption needs for messages sent from SP to IdP; never assume every public certificate serves the same purpose.

**Never use the SP's keypair as the IdP's verification key.** These belong to opposite sides of the trust relationship. Nor is a SAML signing verification certificate automatically the TLS certificate of the IdP's HTTPS site; keep their purposes distinct.

## 9. Trust Bootstrap: Fetching Metadata over HTTPS Is Not the Whole Trust Story

A common pattern is:

~~~java
RelyingPartyRegistrations
        .fromMetadataLocation("https://login.example.org/metadata")
        .registrationId("corp")
        .build();
~~~

The API supports loading metadata from HTTPS, classpath, and file. With HTTPS, understand the sequence:

1. The application connects to the given URL over TLS, relying on the environment's CA truststore.
2. Metadata is parsed into IdP details; the SAML certificate may reside **inside the metadata**.
3. That IdP signing certificate becomes an input to SAML message verification configuration.

This establishes an **important trust boundary**: the metadata endpoint must be an approved source with integrity protection. If an attacker controls the metadata URL contents and the application ingests unverified keys, they can trick the SP into trusting an unauthorized IdP/key.

Appropriate safeguards per organization:

- **Reviewed classpath/file:** update IdP metadata via code review, verify fingerprints/certificates, and deploy through releases.
- **Pinned HTTPS endpoint:** restrict hosts/redirects, enforce TLS and trusted DNS/network paths, control who can edit the URL; never take a metadata URL directly from a user request.
- **Signed metadata:** if signed metadata distribution is standardized, **verify the metadata signature against an externally provisioned trust anchor**, never using a verification key embedded inside the untrusted XML itself.
- **Audit changes:** record changes to entityID, ACS/SSO URLs, certificates, validUntil, algorithms, and approvers.

**Distinguish two facts:** successfully downloading a file and parsing valid XML does not prove the metadata is approved by the organization. This is a trust problem at configuration ingestion time.

### Metadata Verification APIs in Supported Versions

Recent Spring Security documentation introduces `AssertingPartyMetadataRepository` and `OpenSaml5AssertingPartyMetadataRepository` to work directly with IdP metadata, including expiration-based refresh. When building the repository via `withMetadataLocation(...)`, you must provide **metadata verification credentials** if you want to verify **metadata signatures**. Documentation explicitly notes that omitting credentials skips metadata signature validation.

This mechanism is **distinct** from the IdP `verificationX509Credentials` in `RelyingPartyRegistration` used to verify SAML Responses. When writing code, distinguish the certificate signing **metadata** from the certificate signing **messages**, even if an organization manages both under the same PKI.

APIs vary by version (e.g., OpenSAML 5 support in Spring Security 6.4+/7.x). Do not copy newer version snippets into a 6.3 project if those packages/classes do not exist; consult the Javadoc for your running version.

## 10. Publishing SP Metadata with Spring Security

In `SecurityFilterChain`, to expose XML metadata to the IdP, add:

~~~java
http
    .saml2Login(Customizer.withDefaults())
    .saml2Metadata(Customizer.withDefaults());
~~~

This is a **DSL snippet** inside `HttpSecurity` configuration, not a standalone executable snippet. It enables default metadata endpoints, typically:

~~~text
GET /saml2/metadata
GET /saml2/metadata/corp
GET /saml2/service-provider-metadata/corp
~~~

You can customize the endpoint, for example:

~~~java
http.saml2Metadata(metadata -> metadata
        .metadataUrl("/internal/saml/metadata"));
~~~

If you change the path, clarify the exact public metadata URL the IdP will fetch and update the registration on the IdP. Changing the **metadata endpoint path** does not necessarily mean changing the **SP entityID**; both fields may match by convention yet serve separate roles.

How to test:

~~~bash
curl -fsS https://app.example.org/saml2/metadata/corp
~~~

The expected output is **SP XML metadata** if the endpoint is active and policy permits; this lesson does not assume fixed stdout. Validate the XML with an appropriate parser and check:

- `EntityDescriptor@entityID` matches the SP entityID.
- `AssertionConsumerService@Location` matches the public ACS.
- Signing and/or encryption public certificates appear when the SP has registered corresponding credentials.
- HTTP scheme/host/path are not corrupted by proxies.
- The IdP has imported the matching metadata version.

With multiple registrations, if you want aggregated metadata output, the repository must support **iteration** (e.g., `InMemoryRelyingPartyRegistrationRepository`) as required by the resolver API. A repository offering only `findByRegistrationId` can serve SSO yet fall short for features that iterate all registrations.

## 11. Multiple IdPs/Tenants: Selecting the Right Registration

An application may integrate multiple IdPs:

~~~text
corp        -> Corporate employees IdP
partners    -> Partners IdP
contractors -> Contractors IdP
~~~

In Spring Security, `RelyingPartyRegistrationRepository` stores and looks up each configuration by `registrationId`. Java example (snippet):

~~~java
RelyingPartyRegistration corp = RelyingPartyRegistrations
        .fromMetadataLocation("classpath:saml/corp-idp.xml")
        .registrationId("corp")
        .build();

RelyingPartyRegistration partners = RelyingPartyRegistrations
        .fromMetadataLocation("classpath:saml/partners-idp.xml")
        .registrationId("partners")
        .build();

RelyingPartyRegistrationRepository repository =
        new InMemoryRelyingPartyRegistrationRepository(
                corp, partners);
~~~

Real configuration must provide the **SP entityID/ACS** matching what each IdP registered. Different IdPs may share an SP entityID/ACS in some topologies or differ per tenant; confirm with each IdP.

Key areas to control:

1. **Login route:** whether the user chooses `/saml2/authenticate/corp` or `/saml2/authenticate/partners`.
2. **Registration resolver:** upon receiving a response, Spring must determine the exact applicable configuration (from authentication request state, request path, or IdP issuer depending on framework capabilities). Never pick an arbitrary registration from a client parameter while skipping issuer/audience checks.
3. **Tenant isolation:** if `alice` at `corp` and `alice` at `partners` are two distinct people, local account mapping must not rely on bare NameID.
4. **Key isolation:** each IdP has its own verification certificates; never merge all certificates into one shared trust set accepted for every tenant.
5. **Policy isolation:** permissions on the target system may differ per tenant. Never grant roles from a SAML `admin` attribute when that issuer lacks authority to grant that role.

An internal identity key can be based on **(registrationId, issuer, stable subject identifier)**, provided the IdP supplies a stable NameID/subject identifier with disciplined reassignment policies. If a tenant migrates IdPs or rotates certificates, the migration/identity-linking procedure must be explicit; never auto-merge accounts merely on matching emails.

## 12. Metadata Refresh and Certificate Rotation

Metadata and certificates do not last forever. An IdP may rotate its signing certificate, SSO URL, entityID, or AuthnRequest policy. The SP may also rotate its signing/decryption keypair.

### IdP Verification Certificate Rollover

A safe plan typically follows these steps:

1. Receive notification or detect new metadata from a trusted source.
2. Verify the **metadata source**, approver, and new certificate.
3. If the IdP supports an overlap period, temporarily trust **both old and new certificates** strictly scoped to that IdP.
4. Observe valid SAML signatures using the new key and verify SSO outcomes.
5. After the transition window, remove the old certificate in a controlled manner.

Do not overwrite the old key immediately if the IdP is still signing responses with it during rollover; doing so breaks logins. Conversely, do not retain revoked or out-of-policy old certificates indefinitely.

### SP Signing/Decryption Certificate Rollover

- For **signing**, publish the SP's new public certificate so the IdP knows the new key before the SP starts signing with the new private key.
- For **decryption**, if the IdP still encrypts to the old public certificate, the SP must retain the old private key during the transition window under strict access controls.
- Private keys must reside in a secret manager/keystore or appropriate HSM/KMS infrastructure; never commit PEM private keys to Git or embed them in metadata.
- After rotation, export updated SP metadata and confirm the IdP has synchronized.

### Metadata Does Not Auto-Refresh Merely Because the URL Is HTTPS

If `RelyingPartyRegistrations.fromMetadataLocation(...)` is invoked **once at bean startup**, the registration is constructed at that moment. Never assume it re-downloads metadata on every request.

Update strategies:

- Explicitly redeploy when updating classpath metadata.
- Use a repository/caching strategy capable of refreshing based on expiration policies.
- Use `AssertingPartyMetadataRepository` support with a resolver implementing expiry logic and metadata signature verification if supported by your Spring Security version.
- Design metadata synchronization with authentication, caching, refresh intervals, rollback, and failure observability.

Interpret `validUntil`/`cacheDuration` according to metadata semantics, and never equate them with **X.509 certificate validity** or **SAML Assertion lifetime**. These are three separate lifecycles.

## 13. Java 17 Mini Lab: Checking Registration Identifiers

This is a **standalone Java program for learning configuration invariant checks**. It **does not parse XML, verify signatures, or authenticate SAML**, and must never replace Spring Security/OpenSAML in production.

File **SamlRegistrationCheck.java**:

~~~java
import java.util.Map;

public class SamlRegistrationCheck {

    record Registration(String spEntityId, String acs, String idpEntityId) {}

    static String check(Map<String, Registration> registrations,
                        String registrationId,
                        String issuer,
                        String audience,
                        String destination) {
        Registration expected = registrations.get(registrationId);
        if (expected == null) {
            return "REJECT: registration";
        }
        if (!expected.idpEntityId().equals(issuer)) {
            return "REJECT: issuer";
        }
        if (!expected.spEntityId().equals(audience)) {
            return "REJECT: audience";
        }
        if (!expected.acs().equals(destination)) {
            return "REJECT: destination";
        }
        return "MATCHED CONFIG ONLY";
    }

    public static void main(String[] args) {
        String sp = "https://app.example.org/sp";
        String acs = "https://app.example.org/login/saml2/sso/corp";
        String idp = "https://login.example.org/idp";

        Map<String, Registration> registrations =
                Map.of("corp", new Registration(sp, acs, idp));

        System.out.println(check(registrations, "corp", idp, sp, acs));
        System.out.println(check(registrations, "corp", "other", sp, acs));
        System.out.println(check(registrations, "corp", idp, "other", acs));
        System.out.println(check(registrations, "corp", idp, sp, "other"));
        System.out.println(check(registrations, "unknown", idp, sp, acs));
    }
}
~~~

Run on Java 17 or later:

~~~bash
javac SamlRegistrationCheck.java
java SamlRegistrationCheck
~~~

Exact stdout:

~~~text
MATCHED CONFIG ONLY
REJECT: issuer
REJECT: audience
REJECT: destination
REJECT: registration
~~~

Takeaway: even before considering user identity, configuration must establish **which IdP the issuer belongs to, which SP the audience belongs to, which ACS receives the response, and which registration is selected**. Printing `MATCHED CONFIG ONLY` only means the four example strings matched expectations; it **in no way proves a SAML Response is trustworthy**. Spring Security/OpenSAML performs extensive validations across digital signatures, SAML Conditions, SubjectConfirmation, request correlation, and timestamps — never skip those steps.

## 14. Common Integration Errors and Diagnostics

| Symptom | Common Cause | Check and Fix |
| --- | --- | --- |
| Does not redirect to IdP | Missing registration, wrong registrationId, missing/wrong SSO URL | Check `/saml2/authenticate/corp` and SSO endpoint in metadata |
| ACS returns error / route mismatch | IdP POSTs to a different URL, wrong context path/proxy | Compare `AssertionConsumerService@Location` in SP metadata with IdP console |
| `Issuer` mismatch | Confused IdP entityID with SSO URL or another registration | Check response issuer and `assertingPartyMetadata.entityId` |
| Invalid `Audience` | IdP issued assertion for a different SP entityID | Compare SP `entityId` with the IdP's "Audience/Entity ID" setting |
| Signature verification failed | IdP signing certificate differs from actual; key rollover out of sync | Confirm trust source, active certificate, and signing algorithm |
| AuthnRequest rejected by IdP | IdP requires signing while SP lacks signing credentials; different binding/endpoint | Check metadata signing requirement, SP key configuration, and binding |
| Unable to decrypt assertion | Missing/wrong SP decryption private key, IdP using old public key | Check SP metadata encryption certificate and key lifecycle |
| SP metadata shows `http://localhost` | Wrong Forwarded headers / public baseUrl | Fix ingress config, trusted proxy settings, or use absolute URIs |
| SSO succeeds but tenant accounts collide | Mapped solely by NameID/email without checking issuer/tenant | Use an IdP-namespaced identity key and controlled mapping |
| Updated metadata has no effect | Registration built once at startup without refresh | Use a verified refresh/restart workflow |
| Metadata XML loads but login is insecure | Metadata trust bootstrap unchecked, blindly accepting certificates | Pin source, review changes, verify metadata signature/trust anchor when available |
| Intermittent SSO failures near rollover | Both sides switched keys at different times | Support key overlap and monitor active certificate usage |

### Notes on 401/403 Errors and Access Rights

When SAML authentication finishes, Spring creates `Saml2Authentication` and a principal implementing `Saml2AuthenticatedPrincipal`. `Authentication.getName()` typically reflects the provider-mapped NameID. That **does not mean** the account is granted every internal role.

A response from a trusted IdP can result in **successful login followed by 403** on a resource because the user lacks the required authority. Never "fix" this by disabling signature/audience validation or stripping authorization. Inspect identity linking and role mapping in the post-authentication step.

## 15. Pre-Deployment Integration Test Checklist

Test at least these scenario groups:

| Test | Expected Result |
| --- | --- |
| IdP metadata from verified source, matching entityID and certificate | Registration loads properly and exports valid SP metadata |
| Wrong metadata URL, malformed XML, or unapproved certificate change | Fails clearly; never continues trusting unverified values |
| Valid login from `corp` IdP | Accepted under matching registration, issuer, audience, and ACS |
| SAML Response with invalid signature or different IdP key | Authentication rejected |
| Assertion Audience/Recipient/Destination differs from SP | Rejected |
| Expired assertion or NotBefore in the future | Rejected |
| Response issued for tenant A sent to tenant B | Rejected or denied B's accounts/roles |
| IdP requires signed AuthnRequest | SP signs with the signing key registered at the IdP |
| IdP encrypts assertion | SP decrypts using its authorized private key |
| IdP signing key rollover during overlap window | Approved keys work; old key retired on schedule |
| Reverse proxy rewrites host/scheme | Metadata and ACS still advertise approved public addresses |
| Duplicate NameID/email across tenants | Two accounts are not automatically merged |
| Accessing role-protected resource | Access depends on internal mapping, not NameID text |
| A registration is removed/disabled | No longer selected or trusted for responses |

For Spring projects, run **integration tests against a real IdP or a protocol-faithful test IdP**, dedicated test certificates, and HTTP tests exercising the filter chain. Unit tests on builders/repositories only verify configuration; they **do not replace** testing digital signatures, replay protection, state correlation, and TLS/metadata trust.

When investigating issues, log correlation ID, registrationId, the failing validation step, and metadata version. Avoid logging raw SAMLResponses, assertions containing personal data, private keys, or passwords. Never expose certificate private keys in metadata endpoints.

## 16. Design and Operational Rules

Before integrating an IdP, finalize a configuration specification document:

1. **Who are the RP and AP?** Which entityID pairs are trusted, and what is the internal registrationId?
2. **Where does metadata come from?** HTTPS endpoint, signed file, or document delivered via admin channel? Who approves and updates it?
3. **Which endpoints are public?** IdP SSO URL, SP ACS, SP metadata, and logout if used.
4. **What role does each key play?** IdP public signing certificate for verification; SP signing/decryption keypairs under secret management; metadata-signature trust if used.
5. **What are the validation rules?** Signature, issuer, audience, destination, timestamps, correlation, replay, and algorithms must follow the profile.
6. **How are users linked?** Which NameID/subject is stable, and are issuer/tenant, account lifecycle, and permissions accounted for?
7. **How is it operated?** When the IdP rotates keys/endpoints or the SP changes ACS/entityID, who updates first and how long is the overlap window?

Core mindset: **`RelyingPartyRegistration` is the technical and trust contract between an SP and an IdP**. Metadata helps describe this contract, while validating a SAML Response must use trusted information to verify signatures and conditions. Only afterward does the application link NameID/attributes to an account and decide access rights.
