# Challenges, expiration, and verifying operation context in Passkeys

In WebAuthn/Passkeys, the server (Relying Party, **RP**) sends a **random challenge** to the browser before credential registration or authentication. The authenticator holds the private key to produce the WebAuthn result, yet the server can only accept that result after verifying it matches **the exact pending challenge**, **the right ceremony type**, **the right website/RP**, **the right session and identity**, and, when needed, **the exact business operation**.

An assertion with a valid signature **does not automatically authorize arbitrary requests**. The challenge prevents replaying old proof; expiration bounds the usage window; and context prevents proof from login A from being reused for registration B or approving transaction C.

This lesson focuses on: how to generate/store challenges, server-enforced TTLs, atomic consumption against replay, verifying WebAuthn ceremonies and origin/RP ID, binding challenges to sessions/accounts/operations, and applying this with Spring Security Servlet. The Java 17+ code below illustrates the **challenge management layer**, not a complete WebAuthn signature verifier.

## 1. Distinguishing registration, authentication, and step-up

Two core ceremonies in WebAuthn:

| Purpose | Browser API | `ClientDataJSON.type` | Result |
| --- | --- | --- | --- |
| **Passkey registration** | `navigator.credentials.create()` | `webauthn.create` | New credential and public key for the RP to store for the account |
| **Passkey authentication** | `navigator.credentials.get()` | `webauthn.get` | Signed assertion for the RP to verify against the registered public key |

**Step-up** (re-authentication before a sensitive action) typically uses the `webauthn.get` ceremony, yet differs from login in **application context**: a session/account already exists, there is a specific operation, and the result must be used solely for that purpose.

A generalized login flow:

~~~text
Browser                 RP / Spring Security             Authenticator
   |                           |                              |
   |-- POST options ---------->|                              |
   |                           | Generate fresh challenge     |
   |                           | Save pending state + TTL     |
   |<-- publicKey options -----|                              |
   |-- navigator.credentials.get(options) ------------------->|
   |                           |                      UP / UV |
   |<------------------------ Signed assertion ---------------|
   |-- POST assertion -------->|                              |
   |                           | Consume pending challenge    |
   |                           | Match type, origin, RP ID    |
   |                           | Credential + signature       |
   |                           | Account + authorization      |
   |<-- authenticated / error -|                              |
~~~

The browser has no authority to decide that the user is authenticated. Only the server can verify the credential, challenge, and policy before creating an `Authentication`.

## 2. What is a challenge?

A challenge is **an unpredictable random byte sequence** generated by the RP for a single ceremony. It is sent inside:

- `PublicKeyCredentialCreationOptions.challenge` for registration.
- `PublicKeyCredentialRequestOptions.challenge` for authentication.

The authenticator signs data that includes the hash of `clientDataJSON`, which contains the challenge. For an authentication assertion, the signed payload is:

~~~text
authenticatorData || SHA-256(clientDataJSON)
~~~

Example of a `clientDataJSON` generated by the browser:

~~~json
{
  "type": "webauthn.get",
  "challenge": "<base64url-of-issued-challenge>",
  "origin": "https://login.example.org",
  "crossOrigin": false
}
~~~

The server must **verify that the returned challenge matches the issued challenge still in pending state**. A signature on an old assertion may still be mathematically valid, yet invalid for a new challenge.

A challenge is **not a secret**: the browser sees it; the RP's job is to prevent prediction and reuse. Never embed plaintext passwords, OTP codes, emails, or transaction amounts inside the challenge.

### Generating challenges in Java 17+

Example Java class using the standard library:

~~~java
import java.security.SecureRandom;
import java.util.Base64;

public final class WebAuthnChallengeGenerator {
    private static final SecureRandom RANDOM = new SecureRandom();

    public static String generate() {
        byte[] challenge = new byte[32];
        RANDOM.nextBytes(challenge);
        return Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(challenge);
    }
}
~~~

32 bytes = 256 bits of entropy from a cryptographic random source, unpadded base64url-encoded into **43 characters**. This is a strong practical choice; it is not a mandatory byte length for every implementation. Each invocation must produce a fresh challenge. The code above only generates challenges; it does not persist pending state or verify any assertions.

Broken approaches:

~~~text
challenge = username
challenge = currentTimeMillis()
challenge = "register" + accountId
challenge = fixed hash(username)
challenge = a hardcoded string reused across all requests
challenge = client-supplied value echoed by the RP
~~~

Timestamps and usernames are predictable. Hashing predictable data adds zero entropy. Use `SecureRandom`; never use `Math.random()` or a sequential ID as a challenge.

## 3. Every challenge needs server-side pending state

Storing a challenge string in the browser alone is insufficient. The RP should store a temporary record describing **which request is awaiting a response**.

Illustrative record:

~~~yaml
challengeDigest: "server-stored-challenge-verifier"
ceremony: AUTHENTICATE
flowId: "flow-87"
sessionRef: "anonymous-session-42"
accountRef: null
tenantRef: "tenant-a"
rpId: "login.example.org"
expectedOrigin: "https://login.example.org"
userVerification: required
operationRef: null
createdAt: "2026-11-06T08:00:00Z"
expiresAt: "2026-11-06T08:02:00Z"
status: PENDING
~~~

This is an **application-designed schema**, not standard WebAuthn JSON. The server may store the entire options object or a record with sufficient fields for comparison. `accountRef` may be empty if the user is logging in with a discoverable credential without entering a username first.

| Field | Role |
| --- | --- |
| Challenge or corresponding digest | Match the challenge returned by the browser |
| Ceremony type | Prevent `webauthn.create` from being accepted as `webauthn.get` |
| Session/flow reference | Reject results from another browser/flow |
| Account/tenant reference | Bind the exact user to registration or step-up |
| Expected RP ID / origin | Prevent wrong website or wrong credential scope |
| Expected credential IDs, if any | Restrict permitted credentials in a username-first flow |
| User verification requirement | Prevent downgrading from `required` to `preferred` |
| Operation reference | Bind step-up to the requested action |
| ExpiresAt + status | TTL, replay protection, audit |
| Correlation/rate-limit key | Throttling and diagnostics |

This state must be server-managed; the client must never alter `accountRef`, `ceremony`, or `expiresAt`. In multi-node environments, use a session store, Redis, or a database with proper semantics—never rely on a `static Map` living in a single JVM.

## 4. Expiration: browser timeout is not server expiration

Request options may include:

~~~json
{
  "challenge": "<challenge-base64url>",
  "timeout": 120000,
  "rpId": "login.example.org",
  "allowCredentials": [],
  "userVerification": "required"
}
~~~

`timeout` is in **milliseconds** and serves as a hint to the browser regarding ceremony duration. It is not a server-side rule that automatically rejects responses received after 120 seconds.

**The server must store and enforce its own expiration**, for example:

~~~text
issuedAt:  2026-11-06T08:00:00Z
expiresAt: 2026-11-06T08:02:00Z
accept iff now < expiresAt
~~~

| Receipt time | TTL verdict |
| --- | --- |
| 08:00:30Z | Valid, proceed to WebAuthn verification |
| 08:01:59Z | Valid |
| 08:02:00Z | Expired per `now >= expiresAt` |
| 08:03:00Z | Expired even if browser still submits assertion |
| 08:00:30Z but session logged out | Rejected due to session binding |

A 120-second TTL is an **illustrative value**; the WebAuthn spec recommends challenges remain valid for a window commensurate with the ceremony timeout. Actual duration must balance replay exposure against user/device UX.

Distinguish between:

- **Browser timeout:** controls UX wait time; clients may abort early or behave differently across devices.
- **Server challenge TTL:** limits how long the server honors the pending state.
- **Session expiration:** may expire before the challenge; an invalidated session must never be resurrected via a pending assertion.
- **Step-up grant TTL:** permission to apply re-verification to a sensitive action has its own lifespan, typically short and single-use.

Use `Instant` or a server-side UTC clock—never trust client-supplied timestamps; check the boundary with `now.isBefore(expiresAt)`. Confusing seconds with milliseconds can make challenges live 1,000 times longer than intended.

## 5. Preventing replay with atomic consume

A valid challenge must have **single-use semantics**. Suppose a browser or network sends two concurrent requests carrying the same assertion:

~~~text
Request A                Shared store                Request B
    |                         |                          |
    |--- consume(challenge) ->|                          |
    |                         | Atomic read + delete     |
    |<--- pending state ------|                          |
    |                         |<-- consume(challenge) ---|
    |                         |--- missing ------------->|
    |                         |               B is rejected
    v
A proceeds to verify signature/contexts
~~~

If the server executes `GET`, verifies the signature, and only then runs `DELETE` without a transaction/lock, two requests can both see the challenge as unused. TTL **does not** prevent replay within the window while the challenge is still valid.

In production:

- Redis can use `GETDEL` or Lua/transactions to atomically fetch-and-delete.
- Databases can use a conditional update on `status=PENDING` / version checks inside a transaction.
- A challenge repository must prove identical semantics across multiple nodes, not just in single-threaded unit tests.

A conservative option: **consume on attempt receipt**, even if context or signature checks subsequently fail, requiring a fresh challenge on retry. This trivially blocks replay, though UX/DoS and session/CSRF/rate-limit protections should be weighed. Never keep a challenge valid indefinitely after verification failures.

**Atomic consume does not prove the user is logged in.** It only confirms a pending challenge was used at most once; cryptographic and policy checks must still follow.

## 6. Verifying exact WebAuthn context

The server does not merely compare challenges. Invariants to verify when an authentication assertion arrives:

| Invariant | Source | How to check |
| --- | --- | --- |
| `clientDataJSON.type` | Browser data | `webauthn.get` for authentication, `webauthn.create` for registration |
| `clientDataJSON.challenge` | Browser data | Must match the pending challenge on the RP |
| `clientDataJSON.origin` | Browser data | Match allowed origins list, exact scheme/host/port |
| `crossOrigin` / `topOrigin` | Browser data | Match RP policy for iframes or related origins |
| `authenticatorData.rpIdHash` | Authenticator data | SHA-256 of expected RP ID |
| `flags.UP` | Authenticator data | Check user presence per WebAuthn assertion verification |
| `flags.UV` | Authenticator data | Mandatory when policy requires `userVerification=required` |
| `credentialId` | Credential store | Credential registered for the appropriate RP/account |
| `signature` | Assertion | Verify with credential's public key over `authData || SHA-256(clientDataJSON)` |
| `userHandle` | Response / credential record | Must match account binding when present/required |
| `signCount` | Authenticator data / record | Handle clone-risk signals per WebAuthn |

### RP ID and Origin are distinct

Example:

~~~text
RP ID = example.org
Allowed Origin = https://login.example.org
~~~

RP ID is the domain scoping the credential (no scheme/port). Origin contains scheme, hostname, and port if any. The values **need not be identical strings**, yet must satisfy WebAuthn RP ID rules and the RP's origin allowlist.

Do not arbitrarily configure broad wildcard origins. If the app only runs at `https://login.example.org`, an exact origin allowlist is easiest to audit. Never disable origin/`rpIdHash` validation to fix reverse-proxy errors; fix the public host and trusted forwarded headers.

### User presence and User verification

- **UP:** the authenticator confirmed a user presence gesture.
- **UV:** the authenticator performed local user verification (PIN, biometric, or equivalent).

`userVerification=preferred` **does not guarantee UV**. When business rules require strong verification, set `required` and verify the UV flag. `UV=true` does not prove biometrics were used, since a PIN also satisfies it.

### Signature counter does not replace challenge

Credentials synced across devices may report `signCount=0` or fail to increment under the legacy single-device model. A low/non-incrementing counter can be a risk signal depending on the credential—**not** a reason to drop challenge TTLs or allow replay. Handle clone risk using backup eligibility/state flags and appropriate policy.

## 7. Binding to the exact session and account

In **userless login**, the challenge may bind to an anonymous session or login flow ID; the account is resolved only after verifying the credential.

In **username-first login**, the server already knows the candidate username and can provide `allowCredentials` scoped to that account. The username remains merely a flow-selection input, not proof of login.

In **registration**, the user must typically **already be authenticated** before creating a passkey. The challenge must bind to the session, account, and permission to enroll a new credential. A client request passing `accountId=admin` must never write a new passkey to admin if the session belongs to another account.

Examples:

~~~text
LOGIN:
  ceremony=LOGIN, sessionRef=anonymous-12
  accountRef=unknown, operationRef=none

REGISTER:
  ceremony=REGISTER, sessionRef=logged-in-93
  accountRef=user:lan, operationRef=REGISTER_FOR_user:lan

STEP_UP:
  ceremony=STEP_UP, sessionRef=logged-in-93
  accountRef=user:lan, operationRef=CHANGE_EMAIL_request-57
~~~

A response for a `REGISTER` challenge submitted to `LOGIN` must be rejected even with the same RP/origin. A response for session A submitted with session B's cookie must also fail—a matching challenge value alone does not validate the flow.

Scenarios to handle:

- Session cookies require proper `Secure`/`HttpOnly`/`SameSite` flags, sent over HTTPS.
- On logout, account switch, or session fixation rotation, old pending states must be invalidated per policy.
- Two concurrent tabs must have separate challenge/flow IDs or a clear "new options supersede old options" policy.
- Never use a global `lastChallenge` variable shared across users.
- Rate-limit pending challenges per session/IP/account, and clean up expired state by TTL.

Per Spring Security docs, endpoints creating WebAuthn options use **POST with a CSRF token** because issuing a challenge mutates server-side state. Never treat options POSTs as read-only GETs callable freely from other sites.

## 8. Registration: preserving the rightful credential owner

Registering a passkey changes an account's sign-in methods, creating account-takeover risk if account binding is flawed.

Recommended flow:

1. Authenticate the current account; require step-up/re-auth if credential management policy demands it.
2. Server generates a challenge and `PublicKeyCredentialCreationOptions` for that account.
3. Save `accountRef`, `sessionRef`, RP ID, allowed origin, required UV, and expiry in pending state.
4. Browser calls `navigator.credentials.create({publicKey: options})`.
5. Server consumes the exact challenge, verifies `type=webauthn.create`, origin, `rpIdHash`, flags, attestation policy, and credential data.
6. Only when all conditions pass, write public key/credential ID **to the exact account in the pending state**.
7. Audit credential addition; support listing and revoking passkeys.

`user.id` in options must be determined by the RP from the server's account record, not from an arbitrary client request parameter. `excludeCredentials` helps prevent duplicate credential enrollment, yet uniqueness enforcement is still required on the server.

Never reuse the same challenge for registration and login; they serve two ceremonies with different types.

## 9. Login: account-first and discoverable credentials

An authentication flow can be:

- **Account-first:** user enters username, server looks up registered credential IDs and sends an appropriate `allowCredentials`.
- **Discoverable passkey:** browser/authenticator selects a passkey even without a username; `allowCredentials` may be empty, and credential ID/`userHandle` are used to look up the account **after** verifying the assertion.

On completion, verify:

1. Challenge is unexpired, matches the pending flow, and is unused.
2. Type, origin, RP ID, and flags/UV match.
3. Credential ID exists, public key matches, and signature is valid.
4. Account bound to the credential is allowed to log in; `userHandle` is consistent when needed.
5. For account-first flows, the credential cannot "jump" to a different account.
6. Only then create `Authentication`, establish the session, and enforce authorization separately.

Never read a user from a client-supplied field while skipping public-key verification. Raw username, email, or `userHandle` are not cryptographic proof.

## 10. Step-up: challenge must bind to the exact sensitive operation

Scenario: `user:lan` is logged in and wants to transfer funds from wallet A to wallet B. The app prompts for a passkey again to authorize the action.

~~~text
Actor: user:lan
Operation ID: transfer-42
Version: 3
From: wallet-A
To: wallet-B
Amount: 5000000
Currency: VND
~~~

A WebAuthn assertion valid for a `LOGIN` challenge must not be accepted as approval for `TRANSFER`. Step-up requires two layers:

1. **WebAuthn context:** challenge, type, origin, RP ID, credential, signature, UV.
2. **Application context:** user/session, tenant, operation ID, version, recipient, amount/currency, execution permissions, TTL, and single-use grant.

Example pending state:

~~~yaml
ceremony: STEP_UP
sessionRef: "session-user-lan-2"
accountRef: "user:lan"
operationRef: "transfer-42"
operationVersion: 3
canonicalPayloadDigest: "server-side-content-hash"
requireUserVerification: true
expiresAt: "2026-11-06T08:02:00Z"
status: PENDING
~~~

When the assertion is valid, the server **does not execute the operation immediately**. It must load the operation from a trusted source, confirm payload/version/recipient/amount have not changed, verify the account and permissions remain valid, check limit policies, and then atomically consume the step-up grant for **that exact operation** with transaction/idempotency guarantees.

**Important limitation:** Standard WebAuthn signs `authenticatorData || SHA-256(clientDataJSON)`, containing the challenge and origin. It **does not natively sign a trusted display of the transfer amount or recipient**. Storing a transaction hash in pending state prevents reusing re-authentication for another transaction or a server-altered payload; it **does not prove the authenticator displayed the transaction details to the user and the user approved those exact details**. If a product needs "transaction signing" or WYSIWYS trusted approval, design a dedicated content-confirmation mechanism rather than marketing standard passkey login as transaction signing.

Never build challenges by concatenating `"transfer:" + amount + recipient`: that is predictable, lacks entropy, and carries no authorization binding. Always generate a random challenge and bind it to the canonical operation stored on the server.

## 11. Java 17+: simulating challenge TTL and binding

The **ChallengeContextDemo.java** program below is a standalone console app. It simulates a server challenge store scoped by ceremony, session, operation, and TTL. It **does not implement a WebAuthn cryptographic verifier**, does not parse assertions, and does not authenticate accounts.

~~~java
import java.security.SecureRandom;
import java.time.Duration;
import java.time.Instant;
import java.util.Base64;
import java.util.HashMap;
import java.util.Map;

public class ChallengeContextDemo {
    enum Ceremony { REGISTER, LOGIN, STEP_UP }

    record Pending(Ceremony ceremony, String sessionId,
                   String operationKey, Instant expiresAt) {}

    static final SecureRandom RANDOM = new SecureRandom();
    static final Duration TTL = Duration.ofMinutes(2);

    private final Map<String, Pending> outstanding = new HashMap<>();

    public synchronized String issue(
            Ceremony ceremony, String sessionId,
            String operationKey, Instant now) {

        String challenge;
        do {
            byte[] bytes = new byte[32];
            RANDOM.nextBytes(bytes);
            challenge = Base64.getUrlEncoder()
                    .withoutPadding().encodeToString(bytes);
        } while (outstanding.containsKey(challenge));

        outstanding.put(challenge,
                new Pending(ceremony, sessionId, operationKey,
                        now.plus(TTL)));
        return challenge;
    }

    public synchronized boolean consume(
            String challenge, Ceremony ceremony, String sessionId,
            String operationKey, Instant now) {

        // Atomically remove: even a failed attempt must not allow reuse.
        Pending pending = outstanding.remove(challenge);
        return pending != null
                && now.isBefore(pending.expiresAt())
                && pending.ceremony() == ceremony
                && pending.sessionId().equals(sessionId)
                && pending.operationKey().equals(operationKey);
    }

    public static void main(String[] args) {
        ChallengeContextDemo store = new ChallengeContextDemo();
        Instant now = Instant.parse("2026-11-06T08:00:00Z");

        String login = store.issue(Ceremony.LOGIN, "session-A", "-", now);
        System.out.println("Challenge chars = " + login.length());
        System.out.println("Correct context = "
                + store.consume(login, Ceremony.LOGIN,
                        "session-A", "-", now.plusSeconds(30)));
        System.out.println("Replay rejected = "
                + store.consume(login, Ceremony.LOGIN,
                        "session-A", "-", now.plusSeconds(31)));

        String wrongSession = store.issue(
                Ceremony.LOGIN, "session-A", "-", now);
        System.out.println("Wrong session = "
                + store.consume(wrongSession, Ceremony.LOGIN,
                        "session-B", "-", now.plusSeconds(10)));

        String expired = store.issue(
                Ceremony.LOGIN, "session-A", "-", now);
        System.out.println("Expired = "
                + store.consume(expired, Ceremony.LOGIN,
                        "session-A", "-", now.plusSeconds(120)));

        String wrongType = store.issue(
                Ceremony.REGISTER, "session-A", "-", now);
        System.out.println("Wrong ceremony = "
                + store.consume(wrongType, Ceremony.LOGIN,
                        "session-A", "-", now.plusSeconds(20)));

        String stepUp = store.issue(
                Ceremony.STEP_UP, "session-A", "transfer-42-v3", now);
        System.out.println("Wrong operation = "
                + store.consume(stepUp, Ceremony.STEP_UP,
                        "session-A", "transfer-99-v3", now.plusSeconds(30)));
    }
}
~~~

Compile and run:

~~~bash
javac ChallengeContextDemo.java
java ChallengeContextDemo
~~~

Exact stdout:

~~~text
Challenge chars = 43
Correct context = true
Replay rejected = false
Wrong session = false
Expired = false
Wrong ceremony = false
Wrong operation = false
~~~

Explanation:

- A 32-byte unpadded base64url challenge is exactly 43 characters; the demo avoids printing the concrete secret.
- The first valid `consume` returns `true`, while the second returns `false` since the state was removed.
- Wrong session, wrong ceremony, or wrong operation returns `false`.
- After exactly 120 seconds, `now.isBefore(expiresAt)` returns `false` per the expiration rule.

`synchronized` only protects the map within one JVM. Multi-node apps need Redis/database **atomic consume** and real TTLs. This program does not verify accounts, RP ID, origin, user verification, credential public keys, or signatures. Never create an `Authentication` in a real app solely because `consume=true`.

## 12. Spring Security passkey support

In the Spring Security 7.x Servlet line, the `spring-security-webauthn` module provides passkey registration and authentication flows. Use Spring Boot dependency management or the Spring Security BOM instead of mixing versions manually.

Gradle Groovy:

~~~groovy
dependencies {
    implementation "org.springframework.boot:spring-boot-starter-web"
    implementation "org.springframework.boot:spring-boot-starter-security"
    implementation "org.springframework.security:spring-security-webauthn"
}
~~~

Example **configuration class inside a Spring Boot Servlet application**:

~~~java
package demo.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration(proxyBeanMethods = false)
public class PasskeySecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {

        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/login", "/error").permitAll()
                .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults())
            .webAuthn(webAuthn -> webAuthn
                .rpId("login.example.org")
                .allowedOrigins("https://login.example.org"));

        return http.build();
    }
}
~~~

This snippet **cannot run standalone via `javac`**. It requires a Spring Boot main class, real HTTPS, user/credential repositories, and appropriate frontend/login pages. Replace `rpId` and `allowedOrigins` with approved public hostnames. Verify the exact API and behavior of the Spring Security version your project uses.

Per Spring Security 7.x docs, common default endpoints:

| Endpoint | Meaning |
| --- | --- |
| `POST /webauthn/register/options` | Generates challenge/creation options for the logged-in user |
| `POST /webauthn/register` | Receives credential registration response |
| `POST /webauthn/authenticate/options` | Generates challenge/request options for login |
| `POST /login/webauthn` | Receives and verifies authentication assertion |

The options POSTs use CSRF tokens per Spring Security documentation because pending challenge state is mutated. Never replace them with unprotected GETs.

Spring Security uses `PublicKeyCredentialCreationOptionsRepository` to store creation options between the two requests; 7.x docs state it defaults to **HttpSession** and supports custom repositories. `PublicKeyCredentialUserEntityRepository` and `UserCredentialRepository` persist user entities and credential public keys; they are not synonymous with a TTL-enforcing challenge store. For authentication options or customization, consult your exact version's API before replacing default components.

**Do not write your own signature verifier based on a few JSON strings.** WebAuthn libraries implement detailed rules for CBOR/`authenticatorData`/`clientDataJSON`/public keys, flags, algorithms, origins, and counters. If you need extra operation binding, integrate it at the application boundary after the passkey verifier succeeds—never disable default validations.

## 13. How does the browser handle challenges?

The client receives JSON options, converts the challenge from base64url into a byte array, and invokes the browser WebAuthn API:

~~~javascript
// Illustrative snippet, requires csrfToken from the login page.
const r = await fetch("/webauthn/authenticate/options", {
    method: "POST",
    headers: { "X-CSRF-TOKEN": csrfToken }
});
if (!r.ok) throw new Error("Cannot start passkey ceremony");
const options = await r.json();

function decodeBase64url(value) {
    const s = value.replace(/-/g, "+").replace(/_/g, "/");
    const padded = s.padEnd(Math.ceil(s.length / 4) * 4, "=");
    return Uint8Array.from(atob(padded), c => c.charCodeAt(0));
}

options.challenge = decodeBase64url(options.challenge);
options.allowCredentials = (options.allowCredentials || []).map(x => ({
    ...x,
    id: decodeBase64url(x.id)
}));

const credential = await navigator.credentials.get({
    publicKey: options
});
// Serialize binary fields (rawId, authenticatorData,
// clientDataJSON, signature, userHandle) to base64url and POST
// to /login/webauthn in the format the server expects.
~~~

This is a **client code snippet**, omitting full serialization and error/cancellation UX handling. The browser has no authority to generate challenges on behalf of the server. A returned `credential.id` alone is not enough to prove an account; the RP must still verify the assertion's signature and context.

## 14. Common bugs and diagnostic guide

| Symptom or error | Cause | Resolution |
| --- | --- | --- |
| Replaying an assertion within TTL still succeeds | Challenge reused, non-atomic consume | Atomic take/delete, retry with a fresh challenge |
| Browser timed out yet server still accepts | Relying only on `options.timeout` | Enforce server-side `expiresAt` |
| Challenge created on one node fails completion on another | Session/store not shared across nodes | Shared store or controlled sticky sessions |
| Login A accepted for registration B | Ceremony/`clientDataJSON.type` not checked | Bind state to type and verify |
| Registered under wrong user | Trusted client-supplied `accountId` | Bind current authenticated account in pending state |
| Another user consumes session A's challenge | State not bound to flow/session | Bind `sessionRef` and protect cookies/CSRF |
| Valid passkey rejected on origin | Wrong public host/reverse proxy | Fix `allowedOrigins`, trusted forwarded headers |
| Disabling origin validation to "fix" login | Loses website boundary | Never disable; fix configuration |
| `UserVerification=preferred` treated as mandatory MFA | UV flag not checked | Use `required` and verify UV flag |
| Valid credential ID treated as sufficient | Signature not verified | Verify using registered public key |
| `SignCount=0` treated as replay | Syncable passkeys have different semantics | Risk-based handling; challenge stays single-use |
| Step-up for action A works on action B | Operation/version not bound | Operation-scoped one-time grant |
| Changing amount after step-up still executes | Canonical operation not revalidated | Check payload digest/version and transaction policy |
| Opening multiple tabs breaks flow | Single `latestChallenge` overwrites previous | Bounded multiple pending flows or explicit cancel UX |
| Pending challenges grow without bound | Missing TTL/quota | Expire, clean up, and rate-limit |
| Redis connection lost | State cannot be verified | Fail closed and require generating a new challenge |

Some HTTP errors may look identical (such as 401 for an invalid credential). In operational logs, distinguish **challenge_missing**, **challenge_expired**, **context_mismatch**, **origin_mismatch**, **signature_invalid**, and **account_disabled** using internal reason codes, without returning details that let attackers probe credentials/accounts. Never log sensitive raw assertions or session tokens.

## 15. Mandatory context-based test cases

| Test | Expected result |
| --- | --- |
| Random challenge with sufficient entropy, fresh per ceremony | Unpredictable value, distinct from previous requests |
| Valid challenge within TTL | Passes state layer to continue WebAuthn verification |
| Challenge expired at exact boundary `now == expiresAt` | Rejected |
| Replay same challenge | Second attempt rejected |
| Two concurrent requests with the same challenge | At most one consume succeeds |
| `REGISTER` challenge submitted to `LOGIN` | Rejected on type/ceremony |
| Session A's challenge submitted with session B's cookie | Rejected |
| Origin outside allowlist | Rejected |
| `rpIdHash` differs from expected RP ID | Rejected |
| Invalid signature despite valid challenge | Rejected |
| UV required but UV flag false | Rejected |
| Missing credential ID or belonging to another account | Rejected |
| Inconsistent `userHandle`/credential mapping | Rejected |
| User disabled mid-ceremony | Rejected |
| Register passkey after logout | Rejected |
| Different step-up operation ID/version/amount | Rejected |
| Step-up grant reused for a second transaction | Rejected |
| Browser cancels and retries | Fresh challenge; old state not reused |
| Key store/Redis disconnected | No `Authentication` granted |
| Login across multiple nodes and two tabs | Sessions/challenges never bleed across |
| CSRF attack on options endpoint | Blocked per Spring Security policy |

Write **unit tests** for the challenge store with a controllable `Clock`; **integration tests** of the verifier library using real credentials/test authenticators to validate signatures/origins/flags; **end-to-end tests** over HTTPS and browsers; and **business tests** for transaction binding and idempotency. The Java model in section 11 only verifies TTL/context, not full WebAuthn.

## 16. Implementation checklist and conclusion

1. Does the server use CSPRNG to generate a **fresh, high-entropy challenge** for each ceremony?
2. Is pending state server-owned, with an enforced TTL and atomic single-use consume?
3. Are ceremony type, session, account, tenant, credential options, and UV policy stored and verified?
4. Are `type`, `challenge`, `origin`, `crossOrigin`/`topOrigin`, `rpIdHash`, UP/UV, signature, credential ownership, and counter verified per spec?
5. Does registration protect the current account and CSRF, never trusting client `accountId`?
6. Does login handle account-first/discoverable credentials without trusting usernames prior to verification?
7. Is step-up bound to the exact operation version/payload and restricted to single use?
8. Do you avoid claiming passkeys "signed the amount/recipient" solely because the challenge is server-bound?
9. Have load balancer/session store, time synchronization, cleanup, and quotas been tested?
10. Do all state/signature/account failures **fail closed**, never creating a fallback principal?

**Conclusion:** A secure passkey ceremony does not end at "having a signature." The RP must verify **the signature and all WebAuthn invariants**, while confirming the challenge is **unexpired, unused, and issued for the exact session and purpose**. When approving sensitive actions, the application must bind the verification result back to the **exact server-managed operation**, enforce authorization, and prevent replay at both the challenge and business layers.
