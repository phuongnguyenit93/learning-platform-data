# Why Never Compare Two encode Results to Verify the Same Password

## Goal and Short Answer

In Spring Security, **you must never check whether two passwords match by calling `PasswordEncoder.encode(...)` on each value and comparing the two encoded strings**. With widely used secure password encoders such as `BCryptPasswordEncoder`, each `encode` call typically generates a **new random salt**. Consequently, **the same raw password can produce different hash strings**.

The right way to verify a password on login is:

~~~java
boolean valid = passwordEncoder.matches(
    rawPasswordFromLogin,
    storedEncodedPassword
);
~~~

`matches(raw, encoded)` takes the **raw password just submitted by the user** and the **complete stored hash string**. The encoder reads the required salt/parameters from the stored value, executes the appropriate verification, and returns `true` or `false`. It **does not decrypt** the original password, nor simply call `encode(raw)` with a fresh salt and run `equals`.

This lesson belongs to the **Password Hashing** group in the *Spring Security - authentication* module, targeting Java 17+, Spring Boot 3.x, and Spring Security 6.x. It focuses on understanding the root cause, writing proper registration/login code, testing, handling hash formats, and diagnosing common bugs.

After this lesson, you should be able to answer:

1. Why can two calls to `encode("same-password")` return two different strings?
2. How do salt, work factor, and stored string format relate to this behavior?
3. Why can `matches(raw, stored)` verify when hashes generated by `encode` are randomized?
4. In Spring Security, when do you call `encode`, when do you call `matches`, and when do you call neither directly?
5. If an old hash used a different cost or algorithm, can string comparison alone conclude the password is wrong?
6. How do you write tests without creating flaky tests or bypassing authentication?

## 1. Common Mistake: Comparing Two encode Calls

Suppose a user registers with password `spring-2026!`. The application hashes the password and stores it in the database. At login, a developer writes:

~~~java
// WRONG: encode() usually generates a new salt on each call.
String hashWhenRegistered = passwordEncoder.encode("spring-2026!");
String hashAtLogin = passwordEncoder.encode("spring-2026!");

boolean same = hashWhenRegistered.equals(hashAtLogin);
~~~

With `BCryptPasswordEncoder` using secure randomness, `same` is **almost always `false`** even though both inputs are accurately `spring-2026!`.

The reason is not "bcrypt computed wrong", "the password changed", or "Spring Security is unstable". This is the **intended property** of a password-hashing function with random salts.

Broken into three steps:

~~~text
At registration:
  raw = "spring-2026!"
  salt_A = random()
  storedHash = PasswordHash(raw, salt_A, cost)

At login — WRONG way:
  submittedRaw = "spring-2026!"
  salt_B = random()
  candidateHash = PasswordHash(submittedRaw, salt_B, cost)

Because salt_A usually differs from salt_B,
storedHash and candidateHash usually differ,
even when raw == submittedRaw.
~~~

The **RIGHT way** is keeping `storedHash` and calling:

~~~java
boolean same = passwordEncoder.matches(
    "spring-2026!",
    hashWhenRegistered
);
~~~

`matches` uses the metadata from the **stored hash**, without picking a new random salt to perform the comparison. When the password is right and the hash/encoder formats match, the result is `true`.

### 1.1. Proof by Table

| Raw password | Operation | Salt used | Hash comparison result |
| --- | --- | --- | --- |
| `P` | `encode(P)` 1st time | Random `S1` | Hash `H1` |
| `P` | `encode(P)` 2nd time | Random `S2` | Hash `H2`, usually different from `H1` |
| `P` + `H1` | `matches(P,H1)` | Reads `S1` back from stored hash | `true` |
| `Q` (wrong) + `H1` | `matches(Q,H1)` | Reads `S1` back from stored hash | `false` |

**There is no contradiction:** randomness occurs when **creating a new hash**; when **verifying an existing hash**, the parameters from creation were stored so the algorithm can verify.

## 2. Why Does Password Hashing Use Salt?

**Salt** is random data fed into the password-hashing process. With bcrypt, the standard salt is 16 bytes and that metadata is encoded as part of the hash string. When calling `BCryptPasswordEncoder.encode(...)`, the encoder normally generates a fresh cryptographic salt automatically; you do not need to create a separate column or manually prepend salt to raw passwords to integrate with Spring Security.

Suppose two users pick the same password:

~~~text
Alice: password = "same-password", salt = A
Bob:   password = "same-password", salt = B

Alice storedHash = Hash("same-password", A, cost)
Bob   storedHash = Hash("same-password", B, cost)

A != B  =>  the two storedHashes usually differ
~~~

### 2.1. What Benefits Does Salt Bring?

- **Reduces duplicate-password recognition:** looking at two different hash strings alone does not let you conclude two users have different passwords.
- **Defeats precomputed hash tables (rainbow tables):** a shared lookup table for an unsalted algorithm is no longer directly useful; attackers must compute per salt.
- **Reduces attack-work sharing across accounts:** cracking one hash generally cannot directly reuse one precomputed entry across all hashes with other salts.
- **Allows independent password changes and fresh hashes:** each reset/change re-hashes with a fresh salt.

Salt **does not need to be secret**. Storing salt alongside the hash is normal. Pepper is an optional secret managed on the server/HSM and must not be confused with salt.

### 2.2. What Salt Does NOT Solve

- Salt does not make weak passwords like `123456` strong. An attacker who steals a DB with hashes and salts can still guess passwords **offline**, though they must perform the work for each hash.
- Salt does not replace **work factor**. A fast single-round hash like `SHA-256(password + salt)` is still unsuitable for production password storage.
- Salt does not prevent **online guessing** against HTTP login endpoints: you need rate limiting, MFA/passkeys, monitoring, password policies, and controlled error messages.
- Salt must not be a fixed username/email or a constant in source code. Use a password-hashing implementation generating salts via a cryptographic RNG.

Never disable salt to "make hashes deterministic and easy to compare". Doing so strips an essential safeguard merely to avoid calling the right API.

## 3. Relationship Between Salt, Cost, and the Encoded Value

A bcrypt-style password hash is not merely a simple digest. It normally stores all information required for verification:

~~~text
$2a$12$xxxxxxxxxxxxxxxxxxxxxxYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY
 │  │  │                     │
 │  │  │                     └─ hashing result portion
 │  │  └─ salt representation portion
 │  └─ cost / log rounds
 └─ bcrypt version
~~~

**This is a structural diagram**, not a valid hash to copy into an application. Standard bcrypt strings are 60 ASCII characters long. Variants `$2a$`, `$2b$`, `$2y$` may appear depending on version and configuration. In bcrypt, the 16-byte salt is encoded in 22 characters, and the hash result in 31 characters.

### 3.1. Why Store the Complete Encoded Password?

When a user logs in, the encoder needs to know:

1. Which algorithm or variant was used.
2. The salt attached to the **stored** record.
3. The work factor/cost used during earlier hash creation.
4. The expected hash value to verify against.

If you store only part of the hash, strip prefixes, or alter salt/cost, `matches` can return `false` or reject the format as invalid. If you store plaintext or a custom SHA-256 hash, your storage logic becomes incompatible with `BCryptPasswordEncoder`.

For example, a new cost-12 bcrypt hash starts like `$2a$12$...`; an old cost-10 hash starts like `$2a$10$...`. The two values **cannot be compared directly as strings to tell if passwords match**, even if the salt were unchanged. The encoder must run verification using the stored hash's parameters.

### 3.2. How Does Work Factor Affect encode and matches?

`BCryptPasswordEncoder(12)` sets the cost for **new hashes** created by `encode`. Higher cost makes every hash/verify call more expensive; in bcrypt work scales by log rounds, nearly doubling per +1 cost, while actual duration depends on the hardware.

`matches(raw, storedHash)` verifies the stored hash using the **cost embedded in `storedHash`**. Hence, an encoder configured to generate cost-12 hashes can still verify an earlier cost-10 hash.

Work factor **is not the primary reason** two `encode` calls for the same password differ under the same config; the direct cause is the random salt. Work factor makes password guessing harder and more resource-intensive.

## 4. PasswordEncoder API: encode and matches Have Different Contracts

Spring Security defines the primary interface:

~~~java
public interface PasswordEncoder {

    String encode(CharSequence rawPassword);

    boolean matches(
        CharSequence rawPassword,
        String encodedPassword
    );

    default boolean upgradeEncoding(String encodedPassword) {
        return false;
    }
}
~~~

This is an **abbreviated API signature for learning**, not a source file to create. `PasswordEncoder` supports multiple implementations such as bcrypt, Argon2, scrypt, PBKDF2, or delegating encoders.

| Method | Input | Returns | When Used? |
| --- | --- | --- | --- |
| `encode(raw)` | Raw password | New encoded string; secure algorithms normally create a fresh salt | When creating accounts, changing/resetting passwords, rehashing |
| `matches(raw, encoded)` | Newly submitted raw password + stored hash | Verification boolean | When checking password on login |
| `upgradeEncoding(encoded)` | Stored hash | Boolean suggesting whether encoding should be upgraded | After successful authentication, inside a proper migration mechanism |

**Argument order in `matches` is critical:** `matches(rawPassword, encodedPasswordFromStorage)`. The first argument **is not the hash**, and the second **is not the raw password**.

### 4.1. matches Does Not Decrypt the Hash

Because password hashing is a one-way function, `matches` never tries to recover the old password from the hash. It uses the newly provided raw password together with the stored salt/cost/format to perform verification. Conceptually for bcrypt:

~~~text
matches(submittedRaw, storedHash):
    read version, cost, and salt from storedHash
    run bcrypt algorithm on submittedRaw using those parameters
    compare result against storedHash
    return true/false
~~~

This is a **logical description**, not Spring Security's internal source code, and you should never implement the underlying comparison/cryptography yourself. Let the vetted implementation execute verification, including format handling and safe comparison.

### 4.2. Three Comparisons Very Easy to Mix Up

~~~java
String stored = encoder.encode(raw);

// WRONG: re-encoding generates a new salt.
boolean a = stored.equals(encoder.encode(raw));

// WRONG: two independently generated hashes are not a password check.
boolean b = encoder.encode(raw).equals(encoder.encode(raw));

// RIGHT: raw password + stored hash.
boolean c = encoder.matches(raw, stored);
~~~

With randomized encoders like bcrypt, `a` and `b` are almost always `false`; `c` is `true` if the input truly matches and the format is valid. Never use `a` or `b` as authentication logic. Another implementation might be deterministic, yet **the `PasswordEncoder` contract does not guarantee two `encode` calls produce identical strings**, so code relying on `equals` is broken by design and non-portable across encoders.

### 4.3. Swapped Arguments Are Also a Bug

~~~java
// WRONG: passing stored hash in the raw position and raw in the encoded position.
boolean wrongOrder = encoder.matches(storedHash, inputPassword);
~~~

This can produce `false` or invalid-hash-format warnings depending on implementation. Right:

~~~java
boolean correctOrder = encoder.matches(inputPassword, storedHash);
~~~

`storedHash` is the string loaded directly from the database/trusted storage; never a string sent by the client. Never let the client pick the hash to verify or the cost/algorithm ID.

## 5. Runnable Java 17+ Example: Observing Two Different encodes and Valid matches

This example uses **Spring Boot 3.x + Spring Security 6.x**, Java 17+, running as a CLI (with no HTTP server) to focus on password hashing. It creates no database accounts, prints no passwords/hashes to the console, and does not authenticate a user in an HTTP system.

### 5.1. Creating a Maven Project

On Spring Initializr choose:

- Build: **Maven**.
- Java: **17 or 21**.
- Spring Boot: **3.x**.
- Group `com.example`, artifact `password-compare`.
- Dependency: **Spring Security** (`spring-boot-starter-security`). `Spring Web` is not needed.

Create the file:

~~~text
src/main/java/com/example/demo/PasswordCompareApplication.java
~~~

And ensure the package is `com.example.demo`.

### 5.2. Complete Code

~~~java
package com.example.demo;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@SpringBootApplication
public class PasswordCompareApplication {

    public static void main(String[] args) {
        SpringApplication.run(PasswordCompareApplication.class, args);
    }

    @Bean
    CommandLineRunner comparePasswords() {
        return args -> {
            String raw = "demo-only-Strong!2026";
            PasswordEncoder encoder = new BCryptPasswordEncoder(10);

            String storedHash = encoder.encode(raw);
            String anotherHash = encoder.encode(raw);

            // Two encodes generate independent random salts.
            boolean equalEncodedStrings =
                storedHash.equals(anotherHash);

            // Verify each hash against the original raw password.
            boolean storedMatches =
                encoder.matches(raw, storedHash);
            boolean anotherMatches =
                encoder.matches(raw, anotherHash);

            // Wrong password does not match storedHash.
            boolean wrongPasswordMatches =
                encoder.matches("definitely-wrong", storedHash);

            // Wrong approach: hash again then compare strings.
            boolean wrongComparison =
                encoder.encode(raw).equals(storedHash);

            System.out.println("sameRawDifferentHashes="
                + !equalEncodedStrings);
            System.out.println("storedMatches=" + storedMatches);
            System.out.println("anotherMatches=" + anotherMatches);
            System.out.println("wrongPasswordMatches="
                + wrongPasswordMatches);
            System.out.println("wrongComparison="
                + wrongComparison);
        };
    }
}
~~~

### 5.3. Running the Program

In the directory containing `pom.xml`:

~~~bash
./mvnw spring-boot:run
~~~

On Windows PowerShell use `.\mvnw.cmd spring-boot:run`. Typical lines **printed by the program** are:

~~~text
sameRawDifferentHashes=true
storedMatches=true
anotherMatches=true
wrongPasswordMatches=false
wrongComparison=false
~~~

**Accurate note:** `sameRawDifferentHashes=true` and `wrongComparison=false` reflect the overwhelming probabilistic behavior of random salts, **not a theorem that two hashes can never collide**. If the exact same 128-bit salt were generated again (astronomically improbable) with identical parameters, two outputs could match. In practice this virtually never happens with a cryptographic RNG. `storedMatches=true`, `anotherMatches=true`, and `wrongPasswordMatches=false` reflect deterministic verification expectations on validly generated values.

The point of this lesson is not forcing distinct strings by manually appending timestamps or UUIDs; what matters is that **`matches` works regardless of which salt the encoder picked**.

### 5.4. Recommended Experiments

1. Run the application several times and see `matches` remain true. If you temporarily print hashes for learning, the two hashes differ and show the cost prefix; **do this only on a test machine, never log production hashes**.
2. Change `new BCryptPasswordEncoder(10)` to `new BCryptPasswordEncoder(12)` and observe logical results stay unchanged while runtime may increase.
3. Change `raw` to a string with Unicode characters, whitespace, and Vietnamese diacritics; verify `matches` with the exact raw input, without auto-trimming/lowercasing.
4. Pass a wrong password to `matches` and confirm `false`.
5. Read each line of code and identify which lines generate a new salt and which lines only verify an existing hash.

## 6. Proper Business Example: Registration and Login with a Database

### 6.1. At Registration, Encode Once and Store the Entire Hash

Correct flow:

~~~text
POST /register (username, rawPassword)
        |
        +--> validate input, policy, and account creation permissions
        +--> passwordEncoder.encode(rawPassword)
        +--> save full encodedPassword to DB
        +--> do not store rawPassword
~~~

An example of **illustrative code, not a standalone program**:

~~~java
public void register(String username, String rawPassword) {
    if (accountRepository.existsByUsername(username)) {
        throw new IllegalArgumentException("Account unavailable");
    }

    String hash = passwordEncoder.encode(rawPassword);

    accountRepository.save(new Account(username, hash));
}
~~~

The example assumes `accountRepository`, `Account`, and `passwordEncoder` are already defined domain components. Real applications need transactions, unique constraints/race handling, registration controls, password policies, and input protection. Never include hashes in API responses or logs. Password hashes can live in a `password_hash` or `password_encoded` column wide enough for the **complete format**.

### 6.2. At Login, Fetch the Old Hash and Call matches

~~~text
POST /login (username, submittedRawPassword)
        |
        +--> look up account by username
        +--> fetch storedHash from DB
        +--> passwordEncoder.matches(submittedRawPassword, storedHash)
        |         |
        |         +--> false: reject credentials
        |         +--> true: proceed to status/MFA/next policy checks
        |
        +--> return valid authentication per framework
~~~

Example **domain-layer illustrative code**:

~~~java
Account account = accountRepository.findByUsername(username)
    .orElseThrow(() -> new AuthenticationFailureException());

boolean passwordValid = passwordEncoder.matches(
    rawPasswordFromRequest,
    account.passwordHash()
);

if (!passwordValid) {
    throw new AuthenticationFailureException();
}
~~~

`Account` and `AuthenticationFailureException` here are **hypothetical domain types**, not Spring Security classes of those names. The snippet illustrates password verification only; when building real authentication, use `AuthenticationManager`/`AuthenticationProvider` and handle account flags, sessions, MFA, and other concerns. Never copy this domain snippet straight into a controller to replace the whole authentication mechanism.

### 6.3. With Standard Spring Security, the Provider Performs the Check

Common configuration:

~~~java
@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);
}
~~~

This is a **Spring configuration snippet with proper imports**, not a complete file. With `DaoAuthenticationProvider`, the typical sequence is:

~~~text
UsernamePasswordAuthenticationToken (unauthenticated)
        |
        v
AuthenticationManager
        |
        v
DaoAuthenticationProvider
        |
        +--> UserDetailsService.loadUserByUsername(username)
        |       -> UserDetails.getPassword(): storedHash
        |
        +--> PasswordEncoder.matches(rawCredentials, storedHash)
        |
        +--> account status and additional checks
        |
        v
Authentication succeeds or AuthenticationException
~~~

Therefore, when using Spring Security form login/HTTP Basic properly, **you usually do not need to write `matches` yourself inside a controller**. Just ensure `UserDetailsService` supplies properly formatted hashes, `PasswordEncoder` matches the config, and the provider actually uses them. Never call `encode` before passing raw passwords into `AuthenticationManager`: the provider expects original credentials to verify against the stored hash.

## 7. What If You Need to Compare Two Raw Passwords?

There are two distinct scenarios:

**Scenario A — login / password change:** you have a new raw password and an old **stored hash**. Use `matches(raw, storedHash)` to verify. That is Spring Security's secure flow.

**Scenario B — user fills "New password" and "Confirm new password" in one form:** these are two **raw values in the same request**. You can compare them during validation **before encoding**, then encode and store **once** if valid.

~~~java
// Inside registration/password-change form validation.
// Both strings are raw passwords from the same request.
if (!newPassword.equals(confirmNewPassword)) {
    throw new IllegalArgumentException(
        "Password confirmation does not match"
    );
}

String newHash = passwordEncoder.encode(newPassword);
// Save newHash; do not store the two raw inputs.
~~~

This snippet **is only a fragment**, requiring other application variables and services. The goal is avoiding:

~~~java
// WRONG: do not hash two fields and compare them.
boolean confirmed = passwordEncoder.encode(newPassword)
    .equals(passwordEncoder.encode(confirmNewPassword));
~~~

With bcrypt, two equal fields still produce different hashes. In form validation, using `String.equals` on two raw values in the same request is a different problem from verifying a raw password against a stored hash. Still, never log or retain raw fields long, and enforce Unicode/password policy rules consistently.

## 8. Do Not Confuse Deterministic Hashing with Secure Password Storage

General-purpose hashes like SHA-256 without salt are deterministic:

~~~text
SHA-256(P)  -> digest X
SHA-256(P)  -> digest X  (same input)
~~~

Seeing this property, a developer might think **two hash outputs must be equal for passwords to match**. That reasoning does not apply to **adaptive password encoding with random salts**.

### 8.1. Why Not Drop Salt for a Deterministic Hash?

Because it lets attackers reuse one computation across many accounts and easily spot users sharing identical passwords. Single-round SHA-256 is also far too fast for password storage. Convenience of calling `equals` is never a valid reason to adopt a weak mechanism.

### 8.2. Why Not "Extract the Salt and Call encode" to Make Them Equal?

The library already provides `matches` under the proper contract; manually parsing hashes and regenerating with extracted salt/cost invites encoding, compatibility, timing, or versioning bugs. `encode` is normally designed to generate **new** hashes with random salts, not as a public API to reproduce old hashes from caller-supplied parameters.

### 8.3. If Two Hashes Differ, Does That Prove the Passwords Differ?

No. Different salts, costs, or algorithms make hashes differ even when the raw password is identical.

If two hashes happen to be identical, does that prove two accounts share the same password? With the same hash type/format and salt it could be a hint, yet you should never build security or business logic on cross-account hash string comparisons. Design verification around each account's identity and stored hash, without inferring or sharing credentials across accounts.

## 9. Differences Between BCryptPasswordEncoder and DelegatingPasswordEncoder

### 9.1. Plain Bcrypt

An encoded bcrypt string looks like:

~~~text
$2a$12$... (standard bcrypt string)
~~~

Usage:

~~~java
PasswordEncoder encoder = new BCryptPasswordEncoder(12);
String stored = encoder.encode("example");
boolean ok = encoder.matches("example", stored);
~~~

Although the format includes salt/cost, it does **not** carry Spring's delegating `{bcrypt}` prefix.

### 9.2. DelegatingPasswordEncoder Includes the {id} Prefix

`PasswordEncoderFactories.createDelegatingPasswordEncoder()` typically selects bcrypt for new hashes, adding the algorithm prefix:

~~~text
{bcrypt}$2a$10$... (illustrative shape)
~~~

When `matches` is invoked on a delegating encoder, it reads `{id}` and picks the matching encoder. Example:

~~~java
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

PasswordEncoder delegate =
    PasswordEncoderFactories.createDelegatingPasswordEncoder();

String stored = delegate.encode("demo-only");
boolean ok = delegate.matches("demo-only", stored);
~~~

This is a **fragment inside a Java method**, not a full class. The expected result `ok` is `true`. Do not strip `{bcrypt}` when saving if the encoder uses the delegating format.

### 9.3. A Misleading Error

If the DB stores plain bcrypt strings `$2a$...` yet the program abruptly switches to default `DelegatingPasswordEncoder`, `matches` can fail reporting no encoder mapped for ID `null`, **which is not a business-level wrong password**.

Conversely, if the DB stores `{bcrypt}$2a$...`, calling `BCryptPasswordEncoder.matches(raw, storedWithId)` directly also fails plain bcrypt's expected input format. During migration, classify formats and configure a compatible encoder rather than manually altering hash contents. Never use a plaintext-accepting fallback to "quietly fix" production errors.

The same password can have multiple different stored hashes due to:

- Different salts.
- Different work factors.
- Different algorithms/`{id}`s.
- Different encoder/format versions.

That is yet another reason **never to use `storedHashA.equals(storedHashB)` as proof of whether two passwords match or differ**.

## 10. Does Changing Work Factor or Algorithm Break Old Password Logins?

Not necessarily, if the encoder is configured to support old formats. With bcrypt, cost is recorded inside the hash; an encoder configured to generate cost-12 hashes can still read and verify cost-10 hashes.

~~~java
BCryptPasswordEncoder oldEncoder = new BCryptPasswordEncoder(10);
BCryptPasswordEncoder newEncoder = new BCryptPasswordEncoder(12);

String hashAtCost10 = oldEncoder.encode("same-raw");

// Use the old hash without re-encoding before matches.
boolean stillValid =
    newEncoder.matches("same-raw", hashAtCost10);

// Should we upgrade encoding when a valid raw password is present?
boolean needsUpgrade = newEncoder.upgradeEncoding(hashAtCost10);
~~~

The code above is a **fragment**, not a standalone program. With compatible 6.x bcrypt, `stillValid` is `true` and `needsUpgrade` is `true`. That **does not mean** changing the encoder bean automatically upgrades every hash in the database. Old hashes can only be properly rehashed when the application receives a valid raw password during an authentication/reset flow.

### 10.1. Rehash on Successful Login

A sensible upgrade flow:

1. Receive raw password over a secure channel.
2. Verify with `matches(raw, storedHash)` first.
3. If valid, check `upgradeEncoding(storedHash)`.
4. If needed, use the **verified raw password itself** to generate a new hash via `encode(raw)` (new salt/cost).
5. Save the new hash through a transactional password-management layer guarded against races with other password changes.
6. Clear/avoid retaining the raw password longer than necessary; audit metadata without logging secrets.

If using `DaoAuthenticationProvider`, `UserDetailsPasswordService` is the integration point for updating hashes after authentication when supported by the provider:

~~~java
// In config where these variables already exist:
// users: UserDetailsService
// encoder: PasswordEncoder
// passwordUpdates: UserDetailsPasswordService
DaoAuthenticationProvider provider =
    new DaoAuthenticationProvider(users);

provider.setPasswordEncoder(encoder);
provider.setUserDetailsPasswordService(passwordUpdates);
~~~

This is an **illustrative configuration snippet**, not a standalone file. `UserDetailsPasswordService.updatePassword(UserDetails user, String newPassword)` receives the **already encoded** value to store and returns the updated `UserDetails`. The provider can invoke it when an encoding upgrade is needed. Applications must implement persistence properly; never assume Spring Security writes to the DB just because the `PasswordEncoder` bean changed cost.

### 10.2. What Should Be Stored in the Database?

Store **one complete encoded string** in a column wide enough for the current format and future upgrades. Never split the hash into parts and compare only the digest, nor overwrite an old hash with `encode(storedHash)` — doing so hashes the **old hash string as a new password**, breaking authentication for the original raw password.

Especially wrong:

~~~java
// WRONG: re-hashing the hash instead of the raw password.
String broken = passwordEncoder.encode(existingStoredHash);
accountRepository.updatePasswordHash(userId, broken);
~~~

If no raw password is available in a valid flow, let old hashes continue verifying via a compatible encoder or require users to reset their passwords per policy.

## 11. Common Errors and Diagnosis

| Symptom | Possible Cause | How to Check/Fix |
| --- | --- | --- |
| Same raw password yields two different `encode` outputs | Random salt generated each time | **Normal**; use `matches` |
| Registration works, login always fails | Login uses `encode(raw).equals(stored)` | Switch to `matches(raw, stored)` |
| `matches` always false against DB hash | Truncated stored hash, wrong format/encoder, altered raw input, or truly wrong password | Check column length and format; preserve full encoded value |
| `matches` called with swapped arguments | Passing hash as raw and raw as encoded | Use `matches(submittedRaw, storedHash)` |
| Using `new BCryptPasswordEncoder(12)` while DB holds `{bcrypt}...` | Plain encoder cannot read delegating prefix | Pick matching encoder or controlled migration |
| Delegating encoder hits ID `null` | DB holds unprefixed raw hashes | Classify/migrate formats; never default to plaintext fallback |
| Raising cost slows logins | Each verification costs more work | Benchmark, capacity plan, rate limit |
| Old hashes still verify after raising cost | Cost is embedded in hash; encoder supports verifying old format | Expected; check `upgradeEncoding` |
| Two matching confirm-password fields fail check | Hashing both fields separately then calling `equals` | Compare the two **raw fields** in the same request before encoding |
| Two accounts have different hashes, assumed different passwords | Different salts; raw passwords may match | Never infer password equality/inequality from hash comparisons |
| Logging hashes to debug | Increases exposure of verification data | Never log raw/encoded passwords, tokens, or pepper |
| Login does not invoke expected bean's `matches` | Different provider/manager is active | Trace filter chain, `AuthenticationProvider`, and encoder bean |

### 11.1. Check Three Independent Layers

When errors occur, inspect in order:

**Data layer:** does the user record exist, does `password_hash` hold the entire encoded value without trimming/truncation/re-encoding on read/write, and is the `{id}` prefix accurate?

**Algorithm layer:** is the `PasswordEncoder` bean in the provider compatible with the stored format? Are `matches(raw, stored)` arguments in the right order? Was the raw password processed differently between registration and login (trim, lowercase, Unicode normalization)?

**Authentication layer:** is `DaoAuthenticationProvider` selected for the current token? Does `UserDetailsService` return the right user and hash? Is the account disabled/locked/expired? Succeeding authentication followed by rejected authorization is a separate layer.

Never edit hashes manually in production or log passwords to debug. Reproduce on test data with test passwords, snapshot dependency/version info, and add regression tests.

## 12. Proper Testing to Avoid False Tests

### 12.1. Tests Must Not Depend on Two encodes Being Strictly Different

A poor JUnit test:

~~~java
// WRONG FOR TESTING PURPOSE:
assertNotEquals(
    encoder.encode(raw),
    encoder.encode(raw)
);
~~~

Random salts make this almost always pass, yet there is no **absolute guarantee** two salts can never collide. What matters is the accuracy of `matches`, not proving mathematical uniqueness of every random draw.

Better test:

~~~java
String stored = encoder.encode(raw);

assertTrue(encoder.matches(raw, stored));
assertFalse(encoder.matches("wrong", stored));
~~~

This is a **JUnit 5 fragment** inside a test with `encoder`/`raw` declared and `Assertions.assertTrue/assertFalse` imported. It tests the actual authentication contract.

### 12.2. Complete Test with JUnit 5

In a project with the `spring-boot-starter-test` dependency, the following test runs when placed in the right package and filename:

**`src/test/java/com/example/demo/PasswordEncoderContractTest.java`**:

~~~java
package com.example.demo;

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

class PasswordEncoderContractTest {

    private final PasswordEncoder encoder =
        new BCryptPasswordEncoder(10);

    @Test
    void correctPasswordMatchesStoredHash() {
        String storedHash = encoder.encode("demo-only-Strong!2026");

        assertTrue(
            encoder.matches("demo-only-Strong!2026", storedHash)
        );
        assertFalse(
            encoder.matches("definitely-wrong", storedHash)
        );
    }

    @Test
    void twoIndependentHashesCanValidateSameRawPassword() {
        String raw = "demo-only-Strong!2026";

        String first = encoder.encode(raw);
        String second = encoder.encode(raw);

        assertTrue(encoder.matches(raw, first));
        assertTrue(encoder.matches(raw, second));
    }
}
~~~

Run:

~~~bash
./mvnw test
~~~

Windows PowerShell: `.\mvnw.cmd test`. The test deliberately **does not assert `first != second`**; the invariant to preserve across algorithm changes is that both stored values verify the raw password properly.

### 12.3. Login Integration Tests

An encoder unit test alone does not prove the entire login flow works. With Spring Security, also test:

- Registering an account and confirming the database stores an encoded value, never plaintext.
- Logging in with the right password → authentication succeeds.
- Logging in with a wrong password → fails.
- Disabled/locked account → never authenticates even when `matches` is true.
- Nonexistent username → safe login response without account enumeration leaks.
- Delegating/legacy formatted hash → provider invokes the right encoder.
- Changing password → new hash has a new salt and old raw password is rejected.
- Raising cost → old hashes still verify, new hashes satisfy target parameters.
- Concurrent login/password-change → old rehash never overwrites the newly changed credential.

Never "test login" by manually constructing an authenticated token from a username and placing it into `SecurityContextHolder`: that skips the exact verification step under test.

## 13. Security Perspective: Why Not Optimize with Deterministic Hashes?

The goal of password hashing is not creating a stable identifier for a password to make comparisons convenient. The goal is **limiting damage if the hash store is stolen**. Unique salts and suitable work factors raise the attacker's cost of **offline** password guessing.

If you switch to unsalted single-round MD5/SHA-1/SHA-256 just so two `encode` calls match, you trade away security for string-equality convenience. With proper password hashing, the simpler and safer way is **using the `matches` API**.

### 13.1. Work Factor Does Not Replace Online Guessing Defenses

Even with high-cost bcrypt/Argon2id, attackers can still probe logins over HTTP. Defense in depth is required:

1. Multi-signal rate limiting (account, trusted IP behind reverse proxy, device/risk).
2. Anti-password spraying (one password tried across many accounts).
3. MFA/passkeys where appropriate; prefer phishing-resistant methods.
4. Never reveal username existence via error messages or timing.
5. TLS for password submission; never log raw passwords, hashes, Authorization headers, or cookies.
6. Monitor latency and concurrency so high cost does not cause CPU denial of service.
7. Password policies blocking very weak, breached, and reused passwords.

### 13.2. Raw Passwords, Unicode, and Whitespace

`matches` uses the exact password string provided. If registration runs `trim()` while login keeps it intact, or one side runs `toLowerCase()`, passwords can fail to match even when users type what they chose. Define normalization policy **only if truly needed**, apply it uniformly, and never silently alter user-chosen passwords.

With bcrypt, many implementations process at most 72 input bytes; that is **bytes**, not 72 Unicode characters. Passphrases with Vietnamese diacritics or emojis can exceed byte count faster than character count. Applications need a consistent length policy without silent truncation, or an algorithm/design suited for long passphrases per security guidance.

### 13.3. Pepper Does Not Change the matches Rule

If your organization uses a pepper (additional secret outside the DB), encapsulate it inside a component/encoder with explicit design and secret governance. Never randomly prepend pepper at registration while forgetting it at login, or store the secret in the database/hash. The system rule remains verifying a **raw password** against a **stored encoded credential** through a component with the right contract, never comparing two randomized `encode` calls.

## 14. Questions and Answers

**Question 1.** Two calls to `encoder.encode("P")` return two different strings. Is this a Spring Security bug?

**Answer:** no. For bcrypt and encoders using random salts, this is intended behavior. Two different salts produce two different stored hashes.

**Question 2.** If two hashes differ, can we conclude the two raw passwords differ?

**Answer:** no. They could be the same raw password encoded with different salts or costs.

**Question 3.** Why can `encoder.matches("P", storedHash)` return true even though `encoder.encode("P").equals(storedHash)` is false?

**Answer:** `matches` uses the parameters/salt of the stored hash to verify, whereas `encode` normally creates a fresh salt.

**Question 4.** An account has a stored hash, and login receives a raw password from the client. In what order do you pass arguments to `matches`?

**Answer:** `matches(rawFromClient, storedHashFromDatabase)`.

**Question 5.** A user enters identical "newPassword" and "confirmPassword" values in a form. Should you call `encode` twice to compare the fields?

**Answer:** no. Those are two raw fields in the same request; compare them in validation, then encode **one** raw password to store.

**Question 6.** An old cost-10 hash is checked with `BCryptPasswordEncoder(12)`. Must it fail?

**Answer:** no. Bcrypt stores cost inside the stored hash and can verify old values. `upgradeEncoding` helps determine when to rehash under new parameters.

**Question 7.** An app uses `DelegatingPasswordEncoder` while the DB stores `$2a$...` without `{bcrypt}`. What problem can occur?

**Answer:** the default delegating encoder may fail to find an algorithm ID to pick an encoder and throw an error. You need a plan to identify old formats and migrate properly.

**Question 8.** Does changing the encoder configuration to cost 12 automatically replace all cost-10 hashes in the DB?

**Answer:** no. A valid raw password is needed to rehash during an authentication/reset flow and save it under concurrency control.

**Question 9.** Two `UserDetails` have different password hashes. Should you use `getPassword().equals(...)` to find users sharing passwords?

**Answer:** no. Salts can differ even for identical raw passwords; moreover, hunting for users sharing passwords via cross-account hash comparisons is not something to do.

**Question 10.** Why not drop salt and switch to deterministic SHA-256 so hashes can be compared with `equals`?

**Answer:** because that drastically weakens resistance to offline cracking if the DB is leaked. Using adaptive password hashing and `matches` aligns with security goals.

## 15. Practical Coding Checklist

- [ ] During registration or password change/reset, call `passwordEncoder.encode(raw)` and store the **entire** encoded string.
- [ ] When checking a password, call `passwordEncoder.matches(submittedRaw, storedHash)`.
- [ ] Never call `encode(submittedRaw).equals(storedHash)` and never call `encode` twice to confirm a password.
- [ ] Never manually strip/reassemble or improperly normalize salt, cost, prefix, or version of a stored hash.
- [ ] If using `DelegatingPasswordEncoder`, preserve the `{id}encodedPassword` format and migrate legacy hashes under control.
- [ ] Test encoders with true/false `matches` assertions rather than asserting two encodes must always differ.
- [ ] Account creation code and login providers use compatible encoders; passwords in the DB are never raw plaintext.
- [ ] When raising cost/changing algorithms, use `upgradeEncoding` and rehash with a valid raw password; never re-hash an old hash as raw input.
- [ ] Test disabled/locked accounts, nonexistent usernames, wrong passwords, and post-authentication authorization.
- [ ] Never log raw passwords/hashes; protect transport with HTTPS, rate-limit logins, and monitor brute-force attempts.
- [ ] Handle whitespace, Unicode, password length, and storage policies consistently.
- [ ] When changing encoders/versions, check stored hash formats, runtime performance, and rollback/migration safety.

**Conclusion:** two `encode` calls can produce **two different values for the same password**, because secure password hashing uses random salts and embeds specific parameters in the encoded value. Comparing a newly encoded hash string against a stored hash is the wrong check. In Spring Security, **`encode(raw)` is for storing**, and **`matches(raw, storedHash)` is for verifying** — that is the right contract regardless of whether a new hash differs from an old hash string.
