# Pepper, Secret Stores, and Planning Server-Side Secret Rotation

## 1. Why Understand Pepper When Upgrading Password Protection?

When a user creates an account, the application should store a **password verifier** produced by a one-way adaptive password hashing algorithm such as **Argon2id, scrypt, bcrypt, or PBKDF2 with suitable parameters**, rather than storing plaintext passwords. A verifier normally consists of a **random salt** and key-derived output from the password. The salt enables future verification and **does not need to be kept secret**.

If an attacker obtains the accounts table containing salts and password hashes, they can still run **offline password guessing**: taking each candidate password, running the same algorithm, and comparing outputs. Weak passwords can still be guessed, even though an adaptive hashing function makes each attempt more resource-intensive.

A **pepper** is an **additional server-side secret** used during creation or verification of a password verifier but **not stored alongside the password hash table**. When properly designed, an attacker who **only obtains the database** lacks the pepper and cannot test candidate passwords using the same verification pipeline as the application. This is an added defense layer; it **does not replace salts, adaptive hashing algorithms, strong passwords, rate limiting, or MFA**.

In the **Spring Security - authentication** module, this topic sits in **Password Upgrades** because adding a pepper, rotating a pepper, or changing password hashing algorithms directly impacts the ability to authenticate **all existing accounts**. Changing a single configuration variable is not a complete migration.

**Learning objectives:** understand the threat model, design secret storage, organize versions/key IDs, distinguish **routine rotation** from **compromised-pepper incident response**, illustrate with runnable Java 17 code, and integrate at the proper `PasswordEncoder`/`DaoAuthenticationProvider` boundary.

## 2. How Do Salt, Pepper, Password Hash, and KMS Keys Differ?

| Component | Must be secret? | Scope | Appropriate location | Purpose |
| --- | --- | --- | --- | --- |
| **Raw password** | Yes | Per user | User-supplied; exists only transiently in request flow | Proves credential ownership. |
| **Salt** | No | Usually a fresh random value per verifier creation | Stored alongside password hash in the database | Prevents identical hashes for identical passwords and defeats precomputed tables. |
| **Password hash/KDF output** | Sensitive authentication data though not a secret key | Per credential | Account store with access controls | Enables password verification; must resist offline guessing. |
| **Pepper / pepper key** | **Yes** | May be shared across many accounts under a key version | Vault/KMS/HSM outside the database; least-privilege access | Increases protection if **only** a database dump leaks. |
| **Key ID/version** | No | Per verifier indicating key version | Metadata beside hash or inside verifier format | Selects the right old/new key during verification and rotation. |
| **Algorithm parameters** | No | Per profile/version | Inside hash format or metadata | Selects the right KDF, salt, and iterations/memory/work factor to verify old hashes. |

**Point to remember:** a random salt **is not a pepper**. A salt stored in the database is not a "leaked pepper"; that design is completely normal. Conversely, a pepper stored beside hashes in the same database or backup **no longer provides an independent security boundary** against someone who obtained both.

A pepper is typically a high-entropy secret key generated by a cryptographic random generator, not a memorable word like `"MyCompany2026"`. Nor is it an admin password, JWT signing key, session cookie encryption key, or API token: **separate keys by purpose** so one compromise does not cascade across every other function.

### A More Accurate Threat Model

Suppose an application uses a modern salted KDF plus a separate pepper:

- **Database-only leak, vault/KMS still safe:** pepper can hinder or prevent offline password checking from DB data, provided the design **does not also store an unpeppered verifier that an attacker can use**.
- **Pepper-only leak, no database:** an attacker may not immediately verify user hashes, yet this must be treated as a secret-compromise incident and assessed for impact, because the database might leak separately in the future or may have leaked earlier.
- **Both database and pepper leaked:** pepper's advantage against offline guessing is lost; remaining protection depends on the KDF, parameters, and password quality.
- **Attacker controls an application process authorized to call KMS:** can invoke HMAC/verify operations through the app or steal data prior to the KDF. Pepper cannot guarantee safety when the entire app runtime layer is compromised.
- **Vault/KMS unavailable:** a fail-closed design may temporarily block logins. Pepper introduces an **availability dependency** that requires operational planning.

Never claim "with a pepper, a database leak does not matter". Salts, dedicated keys, KDFs, rate limiting, monitoring, database hardening, IAM permissions, and incident response processes remain essential.

## 3. Two Pepper Strategies: Pre-KDF and Post-KDF

The OWASP Password Storage Cheat Sheet describes two strategy classes: **pre-hashing pepper** and **post-hashing pepper**. Where the secret is combined affects storage format, compatibility, performance, and key rotation.

### 3.1. Pre-Hashing Pepper: Mixing the Secret Before the KDF

An illustrative design:

```text
raw password
     |
     +-----> HMAC(pepper_key, domain_separator || raw_password)
                      |
                      v
          keyed fixed-length input
                      |
        random salt --+--> Argon2id / scrypt / PBKDF2
                              |
                              v
                    stored KDF verifier
                    + salt + KDF profile + key ID
```

Advantage: without the pepper, an attacker cannot compute the right KDF input for a candidate password. Using standard HMAC with key-purpose domain separation avoids ad-hoc `pepper + password` string concatenation with ambiguous encoding.

**Algorithm caveats:** with bcrypt, byte-length input limits and how HMAC output is encoded can introduce truncation, NUL-byte, or encoding pitfalls. Do not hand-roll `bcrypt(pepper + rawPassword)` and assume it is a standard secure design. If integrating manually, use a carefully designed, reviewed, and tested construction; consider a library that supports the mechanism properly.

**Never store the pre-hash HMAC output** outside the database if it acts as an equivalent password substitute. If leaked, it becomes a new secret sufficient to test against the verifier.

### 3.2. Post-Hashing Pepper: Protecting KDF Output with HMAC

Another model:

```text
raw password + random salt
            |
            v
   Adaptive KDF (e.g., PBKDF2-HMAC-SHA256)
            |
            v
   derived password verifier (transient in memory)
            |
            +---- HMAC(pepper_key, context || salt || derived)
                              |
                              v
                  MAC tag + salt + KDF profile + key ID
                              |
                              v
                          Database

      Pepper key in vault/KMS/HSM, not in DB.
      Derived value MUST NOT be stored as a separate verifier.
```

On the next login, the application reads the salt, KDF profile, and key ID, retrieves or invokes the permitted pepper, recomputes the KDF with the user-supplied password, and computes HMAC to compare the tag with the stored value.

**Biggest post-hashing trap:** if the database stores **both** the raw `KDF(password,salt)` **and** `HMAC(pepper, KDF(...))`, an attacker with only the database can run password guessing directly against the unpeppered KDF. Pepper then fails its goal of protecting against a *database-only compromise*. In this post-hash model, store **salt, params, key ID, MAC tag**; never store the raw KDF output as a standalone password verifier.

Nor should fast HMAC directly on the raw password replace the KDF entirely. Peppered HMAC is an **added layer**, whereas the adaptive password hash provides the guessing cost.

### 3.3. Which Style to Choose?

| Criterion | Pre-hash pepper | Post-hash HMAC |
| --- | --- | --- |
| Secret combination point | Before KDF | After KDF |
| Stored parts | KDF output with salt/params/key ID | MAC tag with salt/params/key ID; **no unpeppered verifier retained** |
| KMS/HSM support | Can run HMAC on password before KDF | Can run HMAC on derived value after KDF |
| Rotating pepper without raw password | Generally cannot validly convert verifier | **Cannot** if only MAC tag is kept without unpeppered output |
| Integration risks | Encoding/KDF input length limits, HMAC choice | Accidentally storing unpeppered KDF output, tag formatting, key ID |
| Shared requirements | Suitable KDF, dedicated key, versioned format, reset/migration | Suitable KDF, dedicated key, versioned format, reset/migration |

Both forms have variants. **Choose one fixed combination scheme, publish its version, and test end-to-end**, rather than trying multiple arbitrary pepper concatenations per password at login.

## 4. What Metadata Does a Password Verifier Need?

If designing a pepper mechanism yourself, a record might carry fields like:

```text
user_id         = 42
password_format = "v1"
kdf_algorithm   = "PBKDF2WithHmacSHA256"
kdf_iterations  = 600000
salt_b64        = "..."
pepper_key_id   = "password-pepper-v1"
mac_tag_b64     = "..."
updated_at      = "..."
version         = 17
```

This is solely an **illustrative schema**. Values `salt`, `iterations`, `format`, and `pepper_key_id` are **not secrets**; knowing them must never let an attacker compute the verifier without the pepper. The tag string is sensitive authentication data and must stay out of URLs/logs.

A simple format for the Java example in section 8 is:

```text
v1$k1$600000$<salt-base64url>$<hmac-tag-base64url>
```

It has **5 components**: version, logical key ID, KDF iterations, salt, and HMAC tag. IDs here are illustrative; production should use organization-managed version IDs/key references without embedding secrets in names. The example fixes the algorithm and lengths under `v1`; if changing the KDF, HMAC type, concatenation layout, or encoding, create a **new format version** instead of silently redefining `v1`.

Never let user-modifiable metadata force the server to run huge `iterations` or decode arbitrary formats. **Parse strictly, bound lengths, and validate algorithm/format against an allowlist** before running the KDF. Malformed formats and invalid key IDs must fail safely.

### Key ID Is Not Key Material

`pepper_key_id="k1"` stored beside the hash means "use the key identified as `k1` in the secret store". It **must never** be the pepper value itself, a KMS API key, a vault password, or ciphertext accidentally embedding the raw pepper.

The design can separate two version axes:

- **Password format/KDF version:** algorithm, rounds, salt length, tag structure.
- **Pepper key version:** KMS/HSM secret used to compute the tag.

Separating these two dimensions allows increasing work factors and rotating peppers at different times, making migrations and rollbacks easier to control.

## 5. Where to Place the Pepper: Vault, KMS, HSM, and Access Controls

### 5.1. Options and Trade-Offs

| Pepper storage approach | Assessment |
| --- | --- |
| Hard-coded in Java source / committed `application.yml` | **Unsuitable**: secret leaks easily via Git, artifacts, logs, backups. |
| Stored in the same `users` table or database backup | **Fails** the goal of separating the secret from the DB. |
| Deployment-injected environment variable | Usable in some architectures, but requires securing CI/CD, process environments, crash dumps, and rotation; not as strong natively as vault/HSM. |
| Secrets manager / vault | Keeps secrets outside the DB, supports IAM, auditing, versioning, rotation; app still needs to govern how secrets enter RAM. |
| HSM/KMS supporting HMAC on non-exportable keys | Keeps key material inside hardware/service boundaries while letting the app invoke MACs. Evaluate latency, quotas, cost, and call permissions. |
| Secret "encrypted" with a key stored in the same repo/config | Just moves the secret; an attacker with both pieces decrypts it. |

**Preference:** separate the pepper's administrative domain from the user/password store, use **workload identity/service roles** for least-privilege access rather than long-lived API tokens, audit access, and maintain secure key backup/recovery procedures.

Never assume every product branded `KMS` provides **HMAC-SHA256 with non-exportable keys**. APIs, algorithms, request quotas, and key policies vary by provider. If KMS only encrypts/decrypts a secret to hand raw bytes to the app, **the pepper still resides in app RAM** temporarily and can leak if the process is compromised. Claims that "keys never leave the HSM" hold true only when the keyed operation executes inside that boundary.

### 5.2. Separating Access Permissions

An IAM layout might look like:

- **Production authentication service:** allowed only to run MAC/verify with permitted key IDs; uses the active key for new verifiers.
- **Admin/rotation service:** allowed to create new versions, adjust active/retired states, and schedule transitions under approval workflows.
- **Migration job:** holds only permissions required to update hashes after verified passwords/resets, not blanket access to raw secrets.
- **Database service:** reads/writes password verifiers per app permissions, with **zero permission to export peppers**.
- **Observability/analytics:** reads only IDs/versions, error counts, and sanitized metrics; never keys or raw passwords.

The principles are **least privilege** and **separation of duties**. Never grant `admin` permissions to the app just to fetch the pepper on logins.

### 5.3. Availability Dependencies

If the vault/KMS loses connectivity or an old version is disabled unexpectedly, accounts still using that key may fail to log in. Therefore you need:

- Old keys remain verifiable during the **bounded transition window** of routine rotation.
- Manage KMS quotas, HMAC call throughput, and latency against authentication traffic.
- Monitor for missing keys, access denied, timeouts, version errors, and login failure rates.
- Define fail-closed behavior: **never skip HMAC, never fall back to unpeppered hashes, never switch to NoOp**.
- Separate customer messaging from operational errors: KMS outages should be observed/handled as **authentication infrastructure unavailable**, rather than blaming "wrong password" internally.
- Maintain disaster recovery for **non-compromised** keys. Backups must be protected and restore-tested; never store an easily accessible raw key backup next to the database.

Never cache peppers indefinitely just to mask KMS errors. If the architecture allows short-lived key caching, enforce a threat model, bounded TTL, rotation invalidation, and memory protection. With non-exportable HSM keys, cache handles/connections/authorizations rather than exporting raw keys.

## 6. Routine Pepper Rotation Plan (No Evidence of Compromise)

Routine rotation may stem from secret lifecycle policy, infrastructure moves, or blast-radius reduction against future compromise. It differs sharply from responding to a known compromise.

### 6.1. Lifecycle States of a Key

```text
CREATED  -> ACTIVE_FOR_WRITE  -> VERIFY_ONLY  -> RETIRED/REVOKED
               |                     |
               |                     +--> accept legacy hashes only during
               |                          controlled migration window
               |
               +--> hashes new registrations/password changes
```

States should be managed in the key management system. Never keep an unbounded list of keys with no retirement schedule. `ACTIVE_FOR_WRITE` must be **one explicit version**, not "whichever key has the newest timestamp" guessed independently by each instance.

### 6.2. Safe Rollout Steps

1. **Inventory:** count records by key ID and password format; identify dormant accounts, reset mechanisms, and accountable owners.
2. **Prepare K2:** generate a new random key in vault/HSM, apply IAM and auditing, and test key usage in staging.
3. **Deploy dual-read (both K1 and K2):** all active authentication nodes must recognize the new version **before** any node begins writing K2 hashes.
4. **Switch write mode:** set K2 as active-for-write. New accounts and password changes/resets use K2. K1 becomes verify-only.
5. **Lazy migration on valid login:** when receiving a valid password for a K1 record, recompute the verifier under K2 and persist with transactions/optimistic locking.
6. **Track and handle non-logging-in accounts:** measure remaining K1 hashes and require password changes/resets or run an appropriate user outreach campaign; never retain K1 indefinitely.
7. **Check multi-instance and rollback behavior:** older nodes must read K2 or be prevented from writing K2 until rollout completes; test rollbacks and inspect active writers.
8. **Retire/revoke K1 when eligible:** set explicit cutover timing, policy for unmigrated accounts, and verify backups/restores; then revoke K1 verification rights.
9. **Post-migration audit:** counts moved to K2, accounts needing reset, error rates, KMS latency, and confirming no secrets leaked into logs.

**Never equate "rotating the active key" with "every record is rehashed".** Switching to K2 in the vault does not alter existing K1 HMAC tags.

### 6.3. Why Can't You Rotate Peppers Offline Without Knowing Passwords?

In the post-hash model of section 3.2, the database holds **only the old MAC tag, salt, and metadata**—not the underlying KDF output. You cannot derive `newTag` from `oldTag` alone while keeping verification against the original password working, because HMAC generally lacks such a key-homomorphic conversion.

The same holds for pre-hash peppers: the KDF output already depends on the old pepper. Creating a verifier under K2 by design requires the **right raw password** during login/password change, or executing a reset.

Some systems store an unpeppered KDF output separately to "re-MAC offline". Computationally that works, yet it **simultaneously hands a DB-only attacker an unpeppered KDF verifier** for password guessing. That defeats the chosen threat model unless you designed and separately evaluated a different scheme.

### 6.4. Database Updates Must Guard Against Concurrent Overwrites

The sequence "log in with K1 → rehash with K2 → UPDATE password" can collide with a **password change/reset** on another device. If the UPDATE is unconditional, an older login can overwrite the hash created for the new password.

Conceptual SQL pattern:

```sql
UPDATE user_credentials
SET password_verifier = :new_verifier,
    version = version + 1
WHERE user_id = :user_id
  AND version = :version_read
  AND password_verifier = :old_verifier;
```

This is an **illustrative SQL snippet**, not a full schema. Treat migration as successful only when the affected row count matches expectations; on conflict, re-read state and never force an overwrite. Also avoid rehashing when the account is locked or other authentication checks fail.

## 7. When a Pepper Is Compromised: Incident Response, Not Routine Rotation

This is far more severe than routine rotation.

Suppose evidence shows key K1 was accessed without authorization, leaked into logs or a repository, or a workload with HMAC permissions was compromised. **Never assume merely switching the active key to K2 protects existing passwords tagged with K1.**

### 7.1. Actions to Consider

1. **Containment:** restrict access, disable compromised accounts/infrastructure, preserve forensic evidence, and scope key exposure; do not hastily delete investigation logs.
2. **Scope impact:** how many accounts used K1, which versions, whether databases/hashes or backups also leaked, and how long exposure lasted.
3. **Create an independent K2:** in a cleaned, controlled administrative domain, auditing IAM and secret-delivery mechanisms.
4. **Assess offline guessing risk:** if the attacker has both K1 and the DB, pepper protection on that data is gone. The KDF and weak passwords become the remaining defense.
5. **Force password changes/resets for affected accounts** according to severity and incident policy; OWASP notes you cannot safely swap the pepper for all users without their passwords.
6. **Terminate K1 usage** per the incident response plan; avoid leaving verify-only enabled for months waiting for users to log in if doing so prolongs exposure.
7. **Revoke sessions/tokens as needed**, harden login/reset flows, check MFA, and monitor for credential stuffing/account takeover.
8. **Notify and remediate** per legal requirements, internal procedures, and user obligations; scrub leaked secrets from pipelines/logs/backups as feasible.
9. **Never promise full recovery from rehashing alone:** if an attacker already knows or cracked a password, tagging that **same password** under K2 does not stop it from being abused elsewhere.

**Operational rule:** routine rotation can use a time-boxed dual K1-read / K2-write window. **A compromised pepper** demands incident assessment and typically forced resets, key revocation, and rapidly closing the K1 acceptance window—not passively waiting months for logins.

### 7.2. What If the Pepper Is Lost Without Being Leaked?

If a required key is destroyed with **no backup or valid access path**, verifiers tied to that key become **unverifiable** even when users enter the right password. This is a **key-recovery failure**, not a wrong-password error. Remedies are valid key recovery or secure password resets—never bypassing HMAC.

Account recovery must prevent attackers from exploiting KMS failures to take over accounts—for example, never accept unverified emails or allow resets keyed on untrusted client input.

## 8. Standalone Java 17 Example: KDF + HMAC Pepper + Versioned Rotation

This example **requires no Spring Boot or libraries outside JDK 17**. It demonstrates how a *post-hashing pepper* works and rotates keys **when there is no evidence of compromise**. The program:

- Uses `PBKDF2WithHmacSHA256` with a random 16-byte salt and 600,000 iterations for illustration.
- Uses `HmacSHA256` with a 256-bit key to compute tags.
- Stores in the password verifier only: **format, key ID, iteration count, salt, and HMAC tag**. **Never stores the unpeppered derived key**.
- KeyRing generates K1/K2 at runtime to simulate a secret store. **Production must persist/retrieve keys via vault/KMS/HSM**; keys generated fresh per demo run cannot read verifiers from prior runs.
- Uses `MessageDigest.isEqual` for binary tag comparison; never uses `String.equals` on secret tags.
- Simulates keeping K1 valid for verification while K2 is active-for-write, then retiring K1 post-migration.

**Note:** this is an **educational algorithmic demonstration**, not an audited password storage library for production deployment. It fixes format `v1` and omits real KMS integration, databases, DoS defenses, auditing, bounds on all inputs, and reset flows.

### 8.1. File `PepperRotationDemo.java`

```java
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Arrays;
import java.util.Base64;
import java.util.HashMap;
import java.util.Map;

import javax.crypto.KeyGenerator;
import javax.crypto.Mac;
import javax.crypto.SecretKey;
import javax.crypto.SecretKeyFactory;
import javax.crypto.spec.PBEKeySpec;

public final class PepperRotationDemo {

    private static final int ROUNDS = 600_000;
    private static final int SALT_BYTES = 16;
    private static final int KEY_BITS = 256;
    private static final int TAG_BYTES = 32;
    private static final String FORMAT = "v1";

    private static final SecureRandom RANDOM = new SecureRandom();
    private static final Base64.Encoder ENCODER =
            Base64.getUrlEncoder().withoutPadding();
    private static final Base64.Decoder DECODER =
            Base64.getUrlDecoder();

    // Simulates a vault: holds only key ID -> SecretKey in demo RAM.
    // Never use an in-memory Map of raw keys as a production secret store.
    static final class KeyRing {
        private final Map<String, SecretKey> byId = new HashMap<>();
        private String activeId;

        void add(String id, SecretKey key) {
            if (byId.containsKey(id)) {
                throw new IllegalArgumentException("Duplicate key ID");
            }
            byId.put(id, key);
        }

        void activate(String id) {
            if (!byId.containsKey(id)) {
                throw new IllegalArgumentException("Unknown active key ID");
            }
            activeId = id;
        }

        String activeId() {
            return activeId;
        }

        SecretKey key(String id) {
            return byId.get(id);
        }

        void retire(String id) {
            if (id.equals(activeId)) {
                throw new IllegalStateException("Cannot retire active key");
            }
            byId.remove(id);
        }
    }

    static final class PasswordVerifier {
        private final KeyRing keys;

        PasswordVerifier(KeyRing keys) {
            this.keys = keys;
        }

        String encode(char[] password) throws GeneralSecurityException {
            byte[] salt = new byte[SALT_BYTES];
            RANDOM.nextBytes(salt);

            String keyId = keys.activeId();
            SecretKey key = keys.key(keyId);
            if (key == null) {
                throw new IllegalStateException("Active pepper unavailable");
            }

            byte[] derived = pbkdf2(password, salt);
            byte[] tag;
            try {
                tag = hmac(key, salt, derived);
            } finally {
                Arrays.fill(derived, (byte) 0);
            }

            return FORMAT + "$" + keyId + "$" + ROUNDS + "$"
                    + ENCODER.encodeToString(salt) + "$"
                    + ENCODER.encodeToString(tag);
        }

        boolean matches(char[] password, String stored)
                throws GeneralSecurityException {

            if (password == null || stored == null) {
                return false;
            }

            String[] parts = stored.split("\\$", -1);
            if (parts.length != 5 || !FORMAT.equals(parts[0])
                    || !Integer.toString(ROUNDS).equals(parts[2])) {
                return false;
            }

            // Missing key must never allow bypassing the pepper.
            // Production should distinguish outages from wrong passwords in audits.
            SecretKey key = keys.key(parts[1]);
            if (key == null) {
                return false;
            }

            byte[] salt;
            byte[] expectedTag;
            try {
                salt = DECODER.decode(parts[3]);
                expectedTag = DECODER.decode(parts[4]);
            } catch (IllegalArgumentException invalidFormat) {
                return false;
            }

            if (salt.length != SALT_BYTES
                    || expectedTag.length != TAG_BYTES) {
                return false;
            }

            byte[] derived = pbkdf2(password, salt);
            try {
                byte[] actualTag = hmac(key, salt, derived);
                return MessageDigest.isEqual(expectedTag, actualTag);
            } finally {
                Arrays.fill(derived, (byte) 0);
            }
        }

        boolean needsRehash(String stored) {
            if (stored == null) {
                return false;
            }
            String[] parts = stored.split("\\$", -1);
            return parts.length == 5
                    && FORMAT.equals(parts[0])
                    && !keys.activeId().equals(parts[1]);
        }

        private static byte[] pbkdf2(char[] password, byte[] salt)
                throws GeneralSecurityException {

            PBEKeySpec spec =
                    new PBEKeySpec(password, salt, ROUNDS, KEY_BITS);
            try {
                SecretKeyFactory factory =
                        SecretKeyFactory.getInstance(
                                "PBKDF2WithHmacSHA256");
                return factory.generateSecret(spec).getEncoded();
            } finally {
                spec.clearPassword();
            }
        }

        private static byte[] hmac(
                SecretKey pepper, byte[] salt, byte[] derived)
                throws GeneralSecurityException {

            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(pepper);

            // Domain separation: this HMAC key is dedicated strictly to
            // v1 password verifiers.
            mac.update("pwd-verifier:v1".getBytes(
                    StandardCharsets.UTF_8));
            mac.update((byte) 0);
            mac.update(salt);
            mac.update(derived);
            return mac.doFinal();
        }
    }

    private static SecretKey randomPepper()
            throws GeneralSecurityException {
        KeyGenerator generator =
                KeyGenerator.getInstance("HmacSHA256");
        generator.init(256);
        return generator.generateKey();
    }

    public static void main(String[] args) throws Exception {
        KeyRing keys = new KeyRing();
        keys.add("k1", randomPepper());
        keys.activate("k1");

        PasswordVerifier verifier = new PasswordVerifier(keys);
        char[] password = "DemoPass123!".toCharArray();
        char[] wrong = "wrong-password".toCharArray();

        try {
            // Record created under K1.
            String oldRecord = verifier.encode(password);
            String[] oldFields = oldRecord.split("\\$", -1);

            System.out.println("record.version=" + oldFields[0]);
            System.out.println("record.kid=" + oldFields[1]);
            System.out.println("record.containsRaw="
                    + oldRecord.contains("DemoPass123!"));
            System.out.println("k1.correct="
                    + verifier.matches(password, oldRecord));
            System.out.println("k1.wrong="
                    + verifier.matches(wrong, oldRecord));

            // ROUTINE rotation: K2 writes new records, K1 only reads old ones.
            keys.add("k2", randomPepper());
            keys.activate("k2");

            System.out.println("rotation.oldWorks="
                    + verifier.matches(password, oldRecord));
            System.out.println("rotation.needsRehash="
                    + verifier.needsRehash(oldRecord));

            // Raw password is only available at login/reset time.
            // In a real DB: UPDATE the record with version/compare-and-set.
            String newRecord = verifier.encode(password);
            System.out.println("new.kid="
                    + newRecord.split("\\$", -1)[1]);
            System.out.println("new.correct="
                    + verifier.matches(password, newRecord));

            // Retire K1 only when no users still need K1 records
            // or a matching account-reset strategy is in place.
            keys.retire("k1");

            System.out.println("retired.oldUnavailable="
                    + !verifier.matches(password, oldRecord));
            System.out.println("retired.newWorks="
                    + verifier.matches(password, newRecord));
        } finally {
            Arrays.fill(password, '\0');
            Arrays.fill(wrong, '\0');
        }
    }
}
```

```text
new.correct=true
retired.oldUnavailable=true
retired.newWorks=true
```

The program **does not print the pepper, salt, derived key, or HMAC tag**. Because hashes/tags involve randomness, concrete values vary; printed lines reflect **stable invariants** of the process. 600,000 iterations may feel slow on some machines; that is computational work factor, not a hang.

### 8.3. Reading the Output in Order

**`record.version=v1` and `record.kid=k1`:** metadata specifies the algorithm/format and key ID used; the record **does not contain the key itself**.

**`record.containsRaw=false`:** the stored string does not contain the demo password. Note that "contains no raw string" **is not enough to prove security**; the design must also include an adaptive KDF, salt, separated pepper, and cryptographic testing.

**`k1.correct=true` / `k1.wrong=false`:** the exact password, salt, KDF parameters, and K1 are required to reproduce the MAC tag.

**`rotation.oldWorks=true`:** after K2 is activated for **writes**, K1 remains in the key ring **for reads**. This enables zero-downtime transitions, not indefinite extensions during compromises.

**`rotation.needsRehash=true`:** the record uses a different ID than the active key. It signals **eligibility to transition after valid authentication**, without mutating the DB itself.

**`new.kid=k2`:** passing the right raw password creates a new verifier under K2. Because of the fresh salt, the tag is also fresh.

**`retired.oldUnavailable=true`:** once K1 is removed, old records can no longer authenticate. In production, this is an outage for unmigrated accounts—never silently report "wrong password" to users or bypass pepper as a "quick fix".

**`retired.newWorks=true`:** records already migrated to K2 keep authenticating after K1 is retired.

### 8.4. Demo Limitations

- `KeyRing` only simulates a vault inside a single process. Restarting the program generates **new K1/K2 keys** unable to read records from a previous run. Production must preserve **the exact key material per version** across deploys, regions, and instances until controlled retirement.
- `KeyGenerator` creates random keys via JCA; this **does not prove** keys live in an HSM or use FIPS-certified modules.
- `PasswordVerifier.matches` returns `false` when a key is absent. Real applications should distinguish **key unavailable/access denied** from **password mismatch** for alerts and SLOs, while keeping external messages safe and **never skipping verification**.
- The example hardcodes PBKDF2-HMAC-SHA256/600,000 rounds and format `v1`. Supporting multiple KDFs/cost profiles requires a tested, strictly bounded parser/version registry.
- `MessageDigest.isEqual` works well for comparing length-checked binary tags. Overall security also depends on parsing, error handling, KMS behavior, response timing, account lookup, and throttling.
- Zeroing `char[]` and `derived` best-effort in Java shortens secret lifetime, yet **offers no guarantee that every copy in the JVM/GC was wiped**.
- Never test by taking an existing tag and running HMAC again under K2: that is **not equivalent** to a verifier generated from the original password.

## 9. Integrating with Spring Security: Who Owns Which Responsibility?

`DaoAuthenticationProvider` uses `UserDetailsService` to load `UserDetails` and calls `PasswordEncoder.matches(rawPassword, encodedPassword)`. Therefore, when a system uses a pepper, versioned pepper logic should be encapsulated inside a **tested `PasswordEncoder` implementation** or an adapter backed by a dedicated KMS service.

```text
HTTP login filter
        |
        v
AuthenticationManager / ProviderManager
        |
        v
DaoAuthenticationProvider
        |
        +--> UserDetailsService.loadUserByUsername()
        |      -> load password_verifier (format, KDF, key ID, salt, tag)
        |      -> load account status, authorities
        |
        +--> PasswordEncoder.matches(raw, stored)
        |      -> parse format / key ID
        |      -> PBKDF2/Argon2id/... per profile
        |      -> HMAC with matching-version pepper via vault/KMS
        |      -> constant-time tag comparison
        |
        +--> Account-state checks / optional password upgrade
        |
        v
Authenticated Authentication (when all conditions pass)
        |
        v
SecurityContext managed by web filter
```

**Never** place pepper logic in a controller and then manually build `UsernamePasswordAuthenticationToken.authenticated(...)` from client data. Doing so risks bypassing locked/disabled/expired account checks, brute-force defenses, and authority mapping.

### 9.1. Signature of a `PasswordEncoder` Adapter

An **illustrative structural example**, not a standalone class since `PepperVerifierService` and `KeyProvider` are project-defined:

```java
public final class PepperAwarePasswordEncoder implements PasswordEncoder {

    private final PepperVerifierService service;

    public PepperAwarePasswordEncoder(PepperVerifierService service) {
        this.service = service;
    }

    @Override
    public String encode(CharSequence rawPassword) {
        return service.encodeUsingActiveVersion(rawPassword);
    }

    @Override
    public boolean matches(CharSequence rawPassword, String stored) {
        return service.verifyUsingRecordedKeyId(rawPassword, stored);
    }

    @Override
    public boolean upgradeEncoding(String stored) {
        return service.isOlderThanActivePolicy(stored);
    }
}
```

The adapter must handle cleanly:

- **Encode:** use the active-for-write key supplied by a trusted system, **never** chosen by the client.
- **Matches:** use the stored key ID/profile, accepting only an allowlisted set of versions; verify-only keys must have clear expiration policies.
- **UpgradeEncoding:** flag when key ID, KDF cost, or legacy format needs transitioning; this is **not a DB update operation**.
- **Vault/KMS failures:** throw/record appropriate operational errors; never return `true`, never fall back to an unpeppered KDF, and never leak keys in exception messages.
- **Cryptographic design:** never let callers pick algorithms or iteration counts per request; only accept approved profiles.

### 9.2. Wiring `DaoAuthenticationProvider` and the Upgrade Service

An **illustrative wiring snippet**, requiring application beans:

```java
DaoAuthenticationProvider provider =
        new DaoAuthenticationProvider(userDetailsService);

provider.setPasswordEncoder(pepperAwarePasswordEncoder);
provider.setUserDetailsPasswordService(userDetailsPasswordService);
```

In Spring Security 6.5, `DaoAuthenticationProvider` supports `setUserDetailsPasswordService` to update verifiers after successful authentication when the encoder signals an upgrade. `UserDetailsPasswordService.updatePassword(user, newPassword)` receives the **encoded value** in the new format, not plaintext. `UserDetailsService` still reads from the account store and returns the password verifier with metadata, rather than arbitrarily computing hashes outside transactions.

Crucial when KMS sits on the login path:

1. Never block too many worker threads with slow KMS calls lacking concurrency limits or timeouts.
2. Never log raw passwords or peppers when exceptions happen inside the provider.
3. Never let a database key ID trigger arbitrary secret lookups outside the app's allowlist/permissions.
4. If passwords are encoded under multiple `{id}` schemes, `DelegatingPasswordEncoder` can choose the **password format/KDF algorithm**, while the pepper-aware encoder handles the **key ID** inside. Keep these two ID layers distinct.
5. Never silently accept `{noop}` or an insecure legacy formatter just to patch migration bugs. Legacy hash support must be bounded and monitored.

### 9.3. The `PasswordEncoder` Contract Does Not Solve Vault/Key Lifecycle Automatically

Spring Security does not invent a pepper, HSM key, rotation schedule, or recovery plan simply because a `PasswordEncoder` bean exists. Those remain application and infrastructure design responsibilities.

A `Pbkdf2PasswordEncoder` accepting an extra `secret` argument does not automatically give you a **versioned pepper management system**. Changing that secret without managing old verifiers can reject every user stored under the old secret. If choosing that extension, understand exactly how it mixes the secret, what format is stored, and how key-ID lookups work before deploying.

Likewise, using `DelegatingPasswordEncoder` with `{bcrypt}` does not mean hashes are peppered: the ID merely selects the registered encoder. Swapping the `bcrypt` mapping to an incompatible mechanism can break existing passwords. Reserve distinct IDs/versions for new profiles and keep legacy decoders for the migration period.

## 10. Plan for Upgrading a System Currently Holding Unpeppered Hashes

Many applications already store Spring Security `{bcrypt}...` or PBKDF2 hashes. Adding a pepper is a **format/verification change**, not just a minor configuration tweak.

### 10.1. Account Groups to Manage

| Existing data | How to verify during transition | How to upgrade |
| --- | --- | --- |
| Valid unpeppered BCrypt/PBKDF2/Argon2id hash | Legacy decoder by stored ID | After valid password, encode into peppered verifier + new version. |
| K1-peppered verifier | Key K1 verify-only (if uncompromised), K1 format | After valid password/reset, rehash with K2. |
| K2-peppered verifier | K2 is active | No change needed just because K1 exists in the key ring. |
| Legacy plaintext/`{noop}` | Evaluate and isolate separately; never permit by default | Prioritize incident review, reset, and move to a proper KDF. |
| Unknown format / missing key ID | Fail closed, monitor, and repair data under control | Never loop infinitely across all keys/encoders until one returns true. |

**Never treat adding a prefix as adding a pepper.** `{peppered-v1}{bcrypt}...` does not magically become an HMAC verifier. Every ID must map to its actual implementation and matching generated data.

### 10.2. Rollout Steps

1. **Classify legacy data** using non-sensitive sample shapes and counts by ID/profile, avoiding bulk hash dumps into logs.
2. **Choose the threat model** (DB-only compromise, HSM requirements, KMS quotas, recovery plan, and key-loss handling).
3. **Freeze legacy decoders**, build the new versioned password encoder, and test golden vectors on both paths.
4. **Deploy dual-read first:** every node reads both old and new formats before switching writes, preventing older nodes from rejecting new records.
5. **Switch new writes:** registrations, resets, and password changes emit the new peppered format.
6. **Opportunistic upgrades:** on successful login when policy permits, rehash raw passwords into the new format using `UserDetailsPasswordService` and compare-and-set.
7. **Handle inactive accounts:** proactively require password changes/resets per schedule; never leave legacy decoders enabled forever.
8. **Observe and audit:** metrics by version, upgrade rate, vault errors, KDF latency, memory/CPU, and authentication failure rates.
9. **Shorten the legacy window** based on risk; define criteria for retiring legacy IDs/keys.
10. **Rehearse rollback/DR:** confirm key versions survive pod replacements, region failovers, database restores, KMS account changes, and rolling deploys.

If raising the **work factor** alongside adding a pepper, metadata must capture both changes. Never mutate the KDF parameters of an existing ID in the registry, or old hashes will stop verifying.

### 10.3. Handling Forgotten Passwords and Non-Logging-In Accounts

Because a properly created verifier is **one-way**, the system cannot "decrypt" passwords to add a pepper. Accounts that do not log in during rotation require:

- Routing through recovery/reset flows with appropriate identity verification.
- Time-limited reset tokens with replay and abuse defenses.
- Never treating unverified emails or predictable tokens as proof of account ownership.
- Never emailing new passwords in plaintext.
- Creating post-reset verifiers with the active key and current KDF policy.
- Defining handling for users who do not respond before old-key retirement, such as forcing a reset on next access.

An organization must never keep an old suspected-compromised pepper alive indefinitely just to avoid inconveniencing users.

## 11. Testing and Acceptance Criteria

### 11.1. Functional and Security Test Matrix

| Test | Input / setup | Expected |
| --- | --- | --- |
| **Right password** | Valid password and key ID present | Verifies cleanly without leaking verifier. |
| **Wrong password** | Wrong password, valid key | Verification fails; no `Authentication` granted. |
| **Unique salt** | Create verifier twice for same password/key | Stored verifiers differ due to random salt. |
| **DB-only leak** | Only metadata and tag exist in DB | No unpeppered KDF output available for direct offline guessing. |
| **Version mismatch** | Unsupported format or KDF profile | Controlled rejection; never falls back to insecure default. |
| **K1 verify-only** | New writes use K2, K1 record still valid | K1 verifies during policy-defined transition window. |
| **Rehash after correct login** | K1 record, right raw password | Record transitions to K2 while preserving account and authorities. |
| **No rehash after wrong login** | K1 record, wrong password | Password verifier is not mutated. |
| **K1 retired** | Unmigrated old record | Never bypasses pepper; triggers clear recovery/failure flow. |
| **KMS unavailable** | Denied permission or timeout using key | Fail-closed, observability, and proper operational response. |
| **Concurrent reset vs. upgrade** | Stale login concurrent with password change | Compare-and-set prevents old rehash from overwriting new password. |
| **Rolling deployment** | Old/new nodes serving same users | Every node reads emitted formats or rollout is gated properly. |
| **Restore from backup** | Restored database still needs key version | Can verify or follows an explicit DR/reset plan. |
| **Compromise drill** | K1 flagged as leaked | Blocks K1 writes, triggers resets, containment, revocation review. |

### 11.2. Data-Level Invariants to Verify

- Raw passwords **never** appear in user tables, JSON responses, logs, or traces.
- Peppers/key bytes **never** appear in the database or backups holding password verifiers.
- The database **never** stores an unpeppered KDF verifier usable for offline candidate guessing if post-HMAC architecture is chosen.
- Every record carries sufficient metadata to select algorithm and key version deterministically.
- Never accept formats with arbitrary fields that can induce unbounded CPU work or out-of-allowlist secret lookups.
- Password migration runs only after valid verification and persists with proper transactions/versioning.
- Once the transition window closes, legacy keys/IDs are genuinely removed from the verification path.
- On key provider failure, the system never degrades to NoOp, unpeppered bcrypt, or default passwords.

### 11.3. Testing Spring Security at the Right Scope

`@WithMockUser` helps test authorization, yet **never proves `PepperAwarePasswordEncoder.matches` executed**. To test the real login path:

1. Seed users with K1/K2-peppered verifiers in an isolated store.
2. Wire `DaoAuthenticationProvider` with the real encoder adapter or a contract-faithful fake KMS.
3. Call `AuthenticationManager.authenticate(...)` with right username/password; assert authenticated token, principal, and expected authorities.
4. Call with wrong password; assert rejection.
5. Make KMS fail or deny access; assert fail-closed behavior and zero key leakage.
6. Configure `UserDetailsPasswordService` in upgrade tests; verify the hash is rewritten with the active key after valid login.
7. Test account statuses: locked/disabled accounts must not log in just because the HMAC tag matched.
8. For HTTP tests, run through the real filter chain with matching Basic/form login and TLS/session/CSRF policies.

Use synthetic test fixtures; never copy production peppers or real passwords into source code, test fixtures, CI logs, or documentation.

## 12. Operational Observability Without Leaking Secrets

The system needs to track rotation progress without turning logs into a second secret store.

**Useful metrics:**

- Verifier counts by **format/KDF version/pepper key ID** (key ID only).
- Daily rate of password rehashes from K1 to K2.
- Count of accounts still relying on verify-only keys ahead of retirement.
- Failed KMS/HSM requests by timeout, denied, key disabled, rate limit.
- `p50/p95/p99` latency of KDF and keyed MAC, CPU usage, and concurrency.
- Aggregate login failure rates distinguishing HSM outages from bad passwords.
- Timestamp of the last backup/restore, reset, and key-retirement drill.

**Never log:** raw passwords, derived keys, pepper bytes, full verifiers/hashes, key material returned from vault, login request bodies, HTTP `Authorization` headers, reset tokens, or secrets-manager API credentials.

**Privileged auditing:** who created/activated/disabled keys, which workloads accessed keys, when access was denied, who approved rotations, and when K1 was retired. Enforce tamper-resistant logging and synchronized clocks.

**High-priority alerts:** key access from unexpected workloads/regions, unusual IAM changes, secrets leaked into CI/logs, spikes in K1 usage after K2 write cutover, surges of concurrent login failures due to KMS, or DB writes using legacy formats banned by policy.

## 13. Common Mistakes

1. **"Pepper is the same as salt."** No: salts normally live in the DB per verifier; peppers are secrets managed outside the DB.
2. **"With a pepper, slow password hashing is unnecessary."** Wrong: fast HMAC does not replace Argon2id/scrypt/bcrypt/PBKDF2.
3. **"Putting the pepper in an adjacent DB column is enough."** Offers no independent boundary against a DB dump.
4. **"Keeping the pepper in Git Base64-encoded."** Base64 is encoding, not secret protection.
5. **"Hard-coding the pepper in `application.yml` and labeling it secret."** If bundled with repo/artifact/backups, the secret leaks alongside the app.
6. **"Storing both KDF output and HMAC tag for easy rotation."** In post-HMAC designs, the unpeppered KDF output lets DB-only attackers guess offline, defeating the pepper.
7. **"Changing the KMS active key switches all users automatically."** Existing hashes stay tied to K1 until regenerated.
8. **"We can re-MAC K1 tags into K2 tags without raw passwords."** Not possible in tag-only post-HMAC structures.
9. **"K1 leaked, so let's keep K1 verify-only and wait for organic logins."** Leaves exposure open far too long; run incident response/resets per scope.
10. **"Rotating the pepper revokes already-guessed passwords."** No: compromised/guessed passwords can still be abused; credentials must be changed/reset.
11. **"Peppers don't need versions."** Without key IDs, rotation and recovery degrade into uncontrolled multi-key trial loops.
12. **"The key ID is the key."** The ID is merely a public label; key material must be protected separately.
13. **"Calling KMS guarantees the key never enters app RAM."** Only true if KMS/HSM performs the keyed operation without returning raw key bytes.
14. **"The app needs KMS admin rights for logins."** Overbroad permissions expand blast radius; use minimal IAM.
15. **"If KMS fails, allow unpeppered logins."** Bypassing protection is an unauthorized security downgrade.
16. **"Every KMS error means the user typed the wrong password."** Masks operational outages; separate internal telemetry from safe external responses.
17. **"Reusing one secret for JWTs, cookies, and pepper for convenience."** Cross-purpose key reuse widens compromises and violates domain separation.
18. **"Updating hashes post-login needs no concurrency control."** Can overwrite concurrent password changes or resets.
19. **"Swapping the `{bcrypt}` mapping to a new pepper without versioning."** Causes existing hashes to decode wrongly.
20. **"All users log in often enough that resets aren't needed."** Dormant accounts block retiring K1; plan a clear path.
21. **"Reading iteration counts from requests or unvalidated metadata."** Attackers can trigger DoS with extreme values.
22. **"Using `char[]` in Java wipes all passwords from the JVM."** Copies may linger in logs, request buffers, or immutable strings.
23. **"One passing test proves the architecture is secure."** Must test data invariants, KMS outages, rotation, multi-node rollouts, rollbacks, and compromises.
24. **"Pepper solves rate limiting and MFA."** No: online guessing and account takeover defenses are separate responsibilities.
25. **"Counting K2 accounts is enough without knowing how many K1 remain."** You cannot decide when it is safe to retire K1 without legacy inventory.
26. **"Incident password reset means emailing a new password."** Never send raw passwords; use short-lived token reset flows with identity verification.
27. **"Routine pepper rotation forces immediate resets everywhere."** For uncompromised old keys, timed transition on valid login works; during **compromise**, stricter forced resets apply.
28. **"Higher KDF rounds are always better without benchmarking."** Password verification consumes resources; balance security, latency, and DoS resilience.

## 14. Self-Check Questions

**Question 1.** How do salt and pepper differ? Must salts be stored in KMS?

**Answer:** A salt is per-verifier random data that can be public and stored beside the hash in the DB. A pepper is a server-side secret kept separately in vault/KMS/HSM. Salts do not need to be stored in KMS.

**Question 2.** An attacker steals the entire DB without stealing the pepper. Can they still run offline attacks against password hashes?

**Answer:** If the pepper is designed properly and the DB **holds no unpeppered verifier**, the attacker cannot reproduce verification from DB data alone. Overall protection still depends on the threat model, combination design, and whether the attacker can compromise the app or KMS layers.

**Question 3.** Why is storing both PBKDF2 output and the HMAC tag in the DB a trap in post-hash peppering?

**Answer:** The salted PBKDF2 output acts as a standalone verifier for testing candidate passwords, allowing a DB thief to run offline guessing without the pepper. Never store unpeppered KDF outputs if preventing DB-only guessing is your goal.

**Question 4.** Key K1 holds old hashes and you want new hashes to use K2. Is changing `activeKeyId` enough to migrate?

**Answer:** No. That only changes new writes. K1 hashes must be regenerated when valid raw passwords appear (successful login/reset) and updated safely in the DB; inactive accounts need a separate path.

**Question 5.** Why not compute a K2 tag directly via `HMAC(K2, K1-tag)`?

**Answer:** That produces a different value not equivalent to generating a v1 verifier from password and salt. `K1-tag` lacks the information needed to reconstruct the original KDF output.

**Question 6.** If K1 leaked alongside a DB dump, can you just generate K2 and skip password resets?

**Answer:** That should not be considered sufficient. K1 + DB already gave attackers a window to guess old passwords; assess the incident, rotate keys, review sessions, and require resets for affected accounts per policy.

**Question 7.** Does `pepper_key_id` need to be hidden like the pepper itself?

**Answer:** No. The key ID is metadata for version selection; avoid embedding key material or credentials in the ID, and knowing the key name must not help an attacker compute verifiers.

**Question 8.** When KMS loses connectivity, should you switch to checking hashes without pepper to keep logins working?

**Answer:** No. Fail closed and handle the operational outage via timeouts, alerts, and recovery. Falling back breaks the security boundary.

**Question 9.** Does `PasswordEncoder.upgradeEncoding` returning true mean the pepper in the DB was already rotated?

**Answer:** No. It only signals that an upgrade is needed; the application/provider must perform the actual update—for example via `UserDetailsPasswordService` after valid authentication with concurrency controls.

**Question 10.** Why not apply the pepper inside `UserDetailsService` and issue `Authentication` yourself?

**Answer:** `UserDetailsService` is an account-reading contract, while `PasswordEncoder`/`DaoAuthenticationProvider` verify credentials and account status. Bypassing the provider risks skipping locked/disabled checks and token management.

**Question 11.** Why maintain separate key versions and password format versions?

**Answer:** Key version selects the secret, whereas format version specifies KDF/HMAC/salt/encoding. Separating them allows planned changes to one piece without misinterpreting old hashes under new parameters.

**Question 12.** What good is an HSM if the app can still call MAC on every login?

**Answer:** An HSM prevents raw key extraction, reducing key theft from DBs, source code, or app memory. Workloads authorized to call MAC can still be abused if compromised, so IAM, rate/quota limits, auditing, app-layer hardening, and incident response remain vital.

### Architecture Decision Checklist

- [ ] Defined threat model: DB-only, app compromise, key compromise, and acceptable risk level.
- [ ] Password hashing algorithm uses unique salts, benchmarked work factor, and versioned metadata.
- [ ] Pepper model stores no unpeppered verifier usable by a DB-only attacker for guessing.
- [ ] Pepper is randomly generated, kept **outside the database**, and managed by vault/KMS/HSM under least-privilege IAM.
- [ ] Every record has a **key ID** and there is one explicit **active-for-write ID**.
- [ ] Time-bounded legacy verification path and retirement plan exist; old keys are not kept forever.
- [ ] Migration runs after valid passwords, with a reset path for inactive accounts.
- [ ] Compare-and-set/optimistic locking prevents overwriting post-reset passwords.
- [ ] **Fail-closed** handling for KMS unavailability, with metrics/alerts and DR.
- [ ] Emergency plan for pepper compromise: containment, inventory, revocation/resets, and session handling.
- [ ] Integration tests via Spring Security providers plus rolling-deploy/multi-region tests.
- [ ] Never log raw passwords, key material, or full verifiers; audit key-usage permissions.
- [ ] Reviewed HMAC key usage: dedicated key purpose, domain separation, and no JWT/session key reuse.

**Conclusion:** A pepper is **an additional server-side secret** strengthening password verifiers when **only database data leaks**. Security comes from the full architecture: adaptive KDF + unique salts + pepper separated from the DB + vault/KMS/HSM governance + versioned formats + planned rotation. **Routine rotation** can follow "K2 writes new, K1 verifies for a bounded window, migrate on valid login"; a **compromised pepper** demands incident response—usually requiring password resets and early K1 revocation—never merely renaming the active key and assuming old credentials are safe.
