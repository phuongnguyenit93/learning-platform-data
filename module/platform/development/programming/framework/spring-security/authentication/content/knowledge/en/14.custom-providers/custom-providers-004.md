# Verifying Evidence Against a Trusted Identity Source in a Custom AuthenticationProvider

> **Goal:** When writing a custom **AuthenticationProvider** for Spring Security, you must verify client-supplied evidence against a **trusted, server-managed identity source**, and only then construct an **authenticated Authentication**. A client claiming a username, user ID, role, or seemingly valid token is **not enough** to establish who the caller is.

## 1. What Are “Evidence” and a “Trusted Identity Source”?

**Authentication evidence (credential)** is the data provided by the party attempting to log in to prove ownership or control of an identity. Depending on the mechanism, this can be a password, API key, signed assertion, access token, client certificate, or OTP code.

A **trusted identity source** is where the server has an authoritative basis to know the subject's identity and status: a server-administered account table, a hashed password store, protected LDAP/AD, an IdP, a signature-verification key store, a certificate management system, or an internal authentication service with a secure contract and connection. Being “trusted” requires controlling **provenance, integrity, update mechanisms, access control, freshness, and revocation status**. A client-sent JSON payload, a self-asserted **X-User-Id** header, or a Base64-decoded payload does not automatically become a trusted source.

For example: a client sends **alice / demo-pass**. The server looks up the **alice** account record in its managed store, retrieves the **password hash** and account status, and runs **PasswordEncoder.matches(raw, storedHash)**. Only when the match succeeds and the account is allowed to operate does the provider create the principal and authorities **from server-side data**. If the client also sends **ROLE_ADMIN**, the provider must ignore that self-asserted role.

### What Gets Verified?

| Question | If checked properly | If skipped |
| --- | --- | --- |
| Which identity does this evidence belong to? | Lookup or verification binds the evidence to a subject with a stable identifier | An attacker can claim to be another subject |
| Is the evidence technically valid? | Matches hash, signature, certificate, or appropriate authentication protocol | Accepts unverified data |
| Who issued the evidence? | Trusts only issuers, servers, directories, or keys in the trust configuration | Trusts tokens generated by anyone |
| Is the evidence intended for this application? | Checks audience, intended purpose, and context per token type | Accepts tokens issued for a different service |
| Is the evidence still valid? | Checks expiration, not-before, revocation, and subject status | Accepts expired credentials or locked accounts |
| What permissions does the subject have? | Retrieves roles/permissions from an authoritative source | Privilege escalation via client-submitted fields |
| Is the trusted source reachable? | Fails authentication safely and reports the incident properly | Fails open or uses unverified data |

**Authentication** (establishing “who”) and **authorization** (deciding “what they may do”) are two separate steps. The provider must produce a trusted identity for authorization steps to use; never treat proving identity as permission to access every resource.

## 2. Mechanism in Spring Security: filter → manager → provider

~~~text
HTTP request
  |
  | Username/password, token, or appropriate credential
  v
Authentication filter
  |
  | Creates an Authentication requesting verification
  | (normally isAuthenticated=false)
  v
AuthenticationManager / ProviderManager
  |
  | Selects AuthenticationProvider via supports(...)
  v
Custom AuthenticationProvider
  |
  +--> Checks token type and evidence format
  |
  +--> Queries server-controlled identity source
  |       +--> source error/untrusted --> fail safely
  |
  +--> Verifies evidence against trusted data
  |       +--> mismatch / locked account --> AuthenticationException
  |
  +--> Retrieves verified subject and authorities from trusted source
  |
  +--> Returns authenticated Authentication
  v
SecurityContext / Security filter chain
  |
  v
Authorization: checks endpoint ROLE_/authority rules
~~~

In Spring Security Servlet:

- **Authentication** holds principal, credentials, authorities, details, and authentication status. On input, these fields may be constructed by the client or filter, so they are untrusted.
- **AuthenticationProvider.supports(Class<?>)** determines which Authentication type a provider can handle. It does **not** mean the credentials are valid.
- **AuthenticationProvider.authenticate(Authentication)** performs the verification. On success, it returns an authenticated Authentication, normally carrying a verified principal and authorities; on failure, it throws an appropriate **AuthenticationException**; when the provider does not handle that token type, it may return null so the manager can try another provider.
- **ProviderManager** can coordinate multiple providers. Never configure a “fallback” provider that accepts all credentials when the primary provider fails, as that opens an authentication bypass.
- **SecurityContextHolder** holds the Authentication placed into context by the filter or application code after successful authentication. Putting an Authentication marked as authenticated into the context without verifying evidence is a severe security bug.

**Critical invariant:** only the branch that passes valid verification creates an Authentication with **isAuthenticated() == true**. The identity and roles placed into the Authentication must come from a trusted source, never copied from request authorities.

### Distinguishing Provider Outcomes

| Outcome | Meaning | How to handle |
| --- | --- | --- |
| Returns an authenticated Authentication | Evidence is valid, identity is allowed to log in | Proceed to authorization |
| Throws **BadCredentialsException** | Wrong password/credential or identity cannot be confirmed; external responses typically use a generic message | Reject login, monitor failed attempts |
| Throws **DisabledException** or **LockedException** | Account status prohibits login, if the contract allows distinguishing internally | Reject; avoid leaking username existence to the client |
| Throws **AuthenticationServiceException** | Cannot verify with the trusted source due to a system failure | Fail safely, log incident, and handle service error |
| Returns **null** | Provider does not decide on this token | Manager may try another provider |
| **ProviderNotFoundException** | No provider supports the token | Check manager/provider configuration and token type |

Never catch every exception and return “login succeeded”; nor should you turn a directory connection failure into “wrong password” in internal logs. **The HTTP response** depends on the filter and **AuthenticationEntryPoint**: for example, default HTTP Basic may return 401 even for an AuthenticationServiceException. If the application wants to return 503 when the identity store is disrupted, configure the entry point and API contract explicitly rather than assuming exceptions automatically become 503.

## 3. Complete Example: Custom Provider Checking Passwords Against a Trusted Directory

The example uses **Java 17+, Spring Boot 3.x, Spring Security 6.x, Spring MVC (Servlet)**. Create the application from Spring Initializr with dependencies **Spring Web**, **Spring Security**, and **Spring Boot Starter Test** to run the tests. The sample code uses package **com.example.demo**; save each public class/record/interface in a matching filename under **src/main/java/com/example/demo/**. The **DemoApplication** class is generated by Initializr.

To focus on how evidence is verified, we use **HTTP Basic** as the transport for receiving username/password and passing them to **AuthenticationManager**. In production, **HTTPS** must be used for all requests carrying passwords; localhost HTTP below is strictly for practice. The written provider can serve other username/password intake mechanisms as long as the filter creates the right token type.

**Example design:** a server-side **TrustedIdentitySource** stores records containing subject ID, username, BCrypt hash, active flag, and authorities. The client only knows username/password. The custom provider matches the evidence and retrieves authorities from the trusted record.

### 3.1. Identity Record Model

File **TrustedIdentity.java**:

~~~java
package com.example.demo;

import java.util.Set;

public record TrustedIdentity(
        String subjectId,
        String username,
        String passwordHash,
        boolean active,
        Set<String> authorities) {
}
~~~

**subjectId** is a stable internal key. **username** may change according to policy; do not use username as an immutable key across all data relationships. **passwordHash** is the server-stored hash result, not a client-sent value. **authorities** must be supplied by the trusted source, e.g., **ROLE_READER**. Mark **active=true** only when the account state is allowed to authenticate.

Define the lookup contract in **TrustedIdentitySource.java**:

~~~java
package com.example.demo;

import java.util.Optional;

public interface TrustedIdentitySource {
    Optional<TrustedIdentity> findByUsername(String username);
}
~~~

The interface name emphasizes the boundary of responsibility: the provider asks an authoritative identity source; the source may use a database, directory, or adapter to an internal service. **Optional.empty()** represents user not found. Source access errors must never be disguised as a valid record.

### 3.2. Server-Managed Demo Data Source

File **InMemoryTrustedIdentitySource.java**:

~~~java
package com.example.demo;

import java.util.Map;
import java.util.Optional;
import java.util.Set;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

@Component
public class InMemoryTrustedIdentitySource
        implements TrustedIdentitySource {

    private final Map<String, TrustedIdentity> identities;

    public InMemoryTrustedIdentitySource(
            PasswordEncoder encoder,
            @Value("${demo.user.password}") String demoPassword) {

        TrustedIdentity alice = new TrustedIdentity(
                "user-1001",
                "alice",
                encoder.encode(demoPassword),
                true,
                Set.of("ROLE_READER"));

        identities = Map.of("alice", alice);
    }

    @Override
    public Optional<TrustedIdentity> findByUsername(String username) {
        return Optional.ofNullable(identities.get(username));
    }
}
~~~

**InMemoryTrustedIdentitySource** is merely a simulation of a server-managed source so the lesson requires no database or LDAP. In a real application, records come from a protected data store that controls who can create/modify accounts, status, and permissions. Do not use a demo password environment variable as a real account storage system; in a database, store the **hash**, never plaintext passwords.

**Trust boundary note:** **username** used as the lookup key is an untrusted input, whereas **the returned record** is the authoritative source containing subject, hash, and authorities. Never turn an **authorities** field from the client's body/header into roles merely because the source returned a user with that username.

### 3.3. Principal Containing Only Verified Identity

File **VerifiedPrincipal.java**:

~~~java
package com.example.demo;

import java.security.Principal;

public record VerifiedPrincipal(
        String subjectId, String username) implements Principal {

    @Override
    public String getName() {
        return username;
    }
}
~~~

The principal holds no plaintext password, hash, API key, or unnecessary internal fields. By implementing **Principal**, it provides the name used by **Authentication.getName()**; subjectId lets the application reference a stable identity.

### 3.4. Writing the Verification AuthenticationProvider

File **TrustedPasswordAuthenticationProvider.java**:

~~~java
package com.example.demo;

import java.util.Optional;
import org.springframework.security.authentication.AuthenticationServiceException;
import org.springframework.security.authentication.BadCredentialsException;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.authentication.AuthenticationProvider;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.AuthenticationException;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

@Component
public class TrustedPasswordAuthenticationProvider
        implements AuthenticationProvider {

    private final TrustedIdentitySource identities;
    private final PasswordEncoder encoder;

    public TrustedPasswordAuthenticationProvider(
            TrustedIdentitySource identities,
            PasswordEncoder encoder) {
        this.identities = identities;
        this.encoder = encoder;
    }

    @Override
    public Authentication authenticate(Authentication request)
            throws AuthenticationException {

        // Accept only username/password tokens; do not trust other token types.
        if (!(request instanceof UsernamePasswordAuthenticationToken)) {
            return null;
        }

        String username = request.getName();
        Object credential = request.getCredentials();

        if (username == null
                || username.isBlank()
                || username.length() > 128
                || !(credential instanceof String rawPassword)
                || rawPassword.isBlank()) {
            throw new BadCredentialsException("Invalid credentials");
        }

        // This data must come from a server-controlled source.
        Optional<TrustedIdentity> found;
        try {
            found = identities.findByUsername(username);
        } catch (RuntimeException ex) {
            // Identity source failure is not valid login proof.
            throw new AuthenticationServiceException(
                    "Trusted identity source unavailable", ex);
        }

        if (found.isEmpty()) {
            throw new BadCredentialsException("Invalid credentials");
        }

        TrustedIdentity identity = found.get();

        if (!identity.active()
                || !encoder.matches(rawPassword, identity.passwordHash())) {
            throw new BadCredentialsException("Invalid credentials");
        }

        // Use authorities only from the verified record; ignore roles in input.
        var authorities = identity.authorities().stream()
                .map(SimpleGrantedAuthority::new)
                .toList();

        var verified = UsernamePasswordAuthenticationToken.authenticated(
                new VerifiedPrincipal(
                        identity.subjectId(), identity.username()),
                null,
                authorities);

        verified.setDetails(request.getDetails());
        return verified;
    }

    @Override
    public boolean supports(Class<?> tokenType) {
        return UsernamePasswordAuthenticationToken.class
                .isAssignableFrom(tokenType);
    }
}
~~~

**Explanation in exact security order:**

1. **supports(...)** and the token type check in **authenticate(...)** confirm the provider is handling the designed evidence type. This is not yet identity authentication.
2. Check that username/password are structurally valid before touching the external source. Username length limits are an example to prevent abnormal input; actual policy must align with the username management system.
3. **identities.findByUsername(...)** queries the authoritative server-side source. If the source is unavailable, throw **AuthenticationServiceException** to fail closed. Never skip verification.
4. User not found, disabled account, or password mismatch are all rejected via **BadCredentialsException** with a generic message. Real applications must watch for timing differences that could leak account status; a reasonable dummy check and rate limiting can be applied after load evaluation.
5. **encoder.matches(rawPassword, identity.passwordHash())** compares the client-entered password against the **BCrypt hash** stored by the source. Never compare a plaintext password directly with a hash string.
6. **authorities** are built from **identity.authorities()**. The provider does not copy **request.getAuthorities()** and does not trust client-supplied roles.
7. Only after every step passes verification does the provider create **UsernamePasswordAuthenticationToken.authenticated(...)** and attach **VerifiedPrincipal** with **null** credentials. This avoids keeping passwords in the post-authentication object.

**Why return null when the token type is unsupported?** Under the AuthenticationProvider contract, a provider can let the manager try another provider. In a multi-mechanism system, carefully control the next provider. In particular, a provider that accepted a username/password token and found invalid credentials must **throw AuthenticationException**, never arbitrarily return null just so a weaker provider can accept it.

**Limitations of the snippet:** When a username is not found it rejects early, so timing differences relative to BCrypt must be evaluated for real deployment. The example also lacks rate limiting, lockout, auditing, and connection timeouts since it does not use a remote directory; these are protective layers to add in real environments.

### 3.5. Registering the Provider in SecurityFilterChain

File **SecurityConfig.java**:

~~~java
package com.example.demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            TrustedPasswordAuthenticationProvider provider)
            throws Exception {
        return http
                .authenticationProvider(provider)
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/api/admin").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .httpBasic(Customizer.withDefaults())
                .formLogin(AbstractHttpConfigurer::disable)
                .build();
    }
}
~~~

**http.authenticationProvider(provider)** registers the provider into the AuthenticationManager used by the security chain. **httpBasic(...)** adds the filter that converts the Basic header into a **UsernamePasswordAuthenticationToken** for the manager to pass to the provider. **hasRole("ADMIN")** checks for **ROLE_ADMIN**; the sample user only has **ROLE_READER**, so calling the admin API must return **403** even with a valid password. The configuration does not disable CSRF; state-changing HTTP methods still need CSRF evaluation, especially when clients are browsers.

**Do not** use a configuration that creates default accounts, never assign **ROLE_ADMIN** arbitrarily, and never construct an authenticated **Authentication** inside a controller from unverified input.

### 3.6. API Confirming Principal and Authorities

File **ProfileController.java**:

~~~java
package com.example.demo;

import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ProfileController {

    public record Profile(String subjectId, String username) {}

    @GetMapping("/api/me")
    public Profile me(Authentication authentication) {
        VerifiedPrincipal user =
                (VerifiedPrincipal) authentication.getPrincipal();

        return new Profile(user.subjectId(), user.username());
    }

    @GetMapping("/api/admin")
    public String admin() {
        return "admin ok";
    }
}
~~~

In the example, every request to **/api/me** must already be authenticated, so **getPrincipal()** is the VerifiedPrincipal created by the provider. When multiple login mechanisms exist in one application, do not assume every principal always has the same type; adapters/controllers should handle valid types by design.

### 3.7. Starting Up and Testing with curl

In **src/main/resources/application.properties**:

~~~properties
server.port=8080
demo.user.password=${DEMO_USER_PASSWORD}
~~~

On Linux/macOS:

~~~bash
export DEMO_USER_PASSWORD=demo-pass
./mvnw spring-boot:run
~~~

On Windows PowerShell:

~~~powershell
$env:DEMO_USER_PASSWORD = "demo-pass"
.\mvnw.cmd spring-boot:run
~~~

The commands below use the dummy password **demo-pass** and HTTP on **localhost** for demonstration. In real environments, use HTTPS, protect environment variables/secrets, and keep real passwords out of shell history or process lists; you can use non-echoing password prompts in client tools.

Valid request:

~~~bash
curl -i -u alice:demo-pass http://localhost:8080/api/me
~~~

Expected **200 OK** with JSON content:

~~~json
{
  "subjectId": "user-1001",
  "username": "alice"
}
~~~

Wrong password:

~~~bash
curl -i -u alice:wrong http://localhost:8080/api/me
~~~

Expected **401 Unauthorized** (HTTP Basic prompts for re-authentication). A nonexistent username must also fail authentication, for example:

~~~bash
curl -i -u unknown:demo-pass http://localhost:8080/api/me
~~~

Expected **401 Unauthorized**, with no trusted principal produced. Although the status code is the same, execution time between a nonexistent username and a wrong password can differ in the example; this is why enumeration testing and additional controls are needed before production.

Valid credentials without admin role:

~~~bash
curl -i -u alice:demo-pass http://localhost:8080/api/admin
~~~

Expected **403 Forbidden**. This is the core difference between *authenticated identity* and *authorized to perform the operation*. HTTP Basic may also return **WWW-Authenticate** on 401; this header is a protocol feature, not a sign that a token was verified.

### 3.8. Testing the Provider Independently with JUnit

If the project has **spring-boot-starter-test**, add file **src/test/java/com/example/demo/TrustedPasswordAuthenticationProviderTest.java**:

~~~java
package com.example.demo;

import static org.junit.jupiter.api.Assertions.*;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.authentication.BadCredentialsException;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.authority.SimpleGrantedAuthority;

@SpringBootTest(properties = "demo.user.password=demo-pass")
class TrustedPasswordAuthenticationProviderTest {

    @Autowired
    TrustedPasswordAuthenticationProvider provider;

    @Test
    void validEvidenceCreatesTrustedPrincipal() {
        var request = UsernamePasswordAuthenticationToken.unauthenticated(
                "alice", "demo-pass");

        var result = provider.authenticate(request);

        assertNotNull(result);
        assertTrue(result.isAuthenticated());
        assertEquals("alice", result.getName());
        assertEquals("user-1001",
                ((VerifiedPrincipal) result.getPrincipal()).subjectId());
        assertNull(result.getCredentials());
        assertTrue(result.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("ROLE_READER")));
    }

    @Test
    void invalidPasswordIsRejected() {
        var request = UsernamePasswordAuthenticationToken.unauthenticated(
                "alice", "wrong");

        assertThrows(BadCredentialsException.class,
                () -> provider.authenticate(request));
    }

    @Test
    void missingUserIsRejected() {
        var request = UsernamePasswordAuthenticationToken.unauthenticated(
                "unknown", "demo-pass");

        assertThrows(BadCredentialsException.class,
                () -> provider.authenticate(request));
    }

    @Test
    void ClientCannotChooseTheirOwnRole() {
        var forged = new UsernamePasswordAuthenticationToken(
                "alice",
                "demo-pass",
                List.of(new SimpleGrantedAuthority("ROLE_ADMIN")));

        var result = provider.authenticate(forged);

        assertNotNull(result);
        assertTrue(result.getAuthorities().stream()
                .noneMatch(a -> a.getAuthority().equals("ROLE_ADMIN")));
        assertTrue(result.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("ROLE_READER")));
    }
}
~~~

Run:

~~~bash
./mvnw test
~~~

PowerShell uses **.\mvnw.cmd test**. The last test constructs a request token already carrying a forged **ROLE_ADMIN** authority. The provider still retrieves authorities from the trusted source so the result only has **ROLE_READER**. This directly tests against trusting caller-asserted authority data. This test verifies the provider itself; in the real request flow, the filter must construct the right input token type and never let clients dictate the Authentication object.

If you have a test setup with **MockMvc** and **spring-security-test**, add end-to-end HTTP tests: valid credentials → 200, wrong credentials → 401, valid credentials missing role → 403, source error → never 200.

## 4. Replacing Demo Data with a Real Identity Source

How verification works depends on the type of **evidence**; a simple string comparison function is not enough.

| Evidence | Trusted source | Correct verification | Pitfalls to avoid |
| --- | --- | --- | --- |
| **Username/password** | Account records/LDAP with controlled access | For server-stored hashes: **PasswordEncoder.matches**; for LDAP use the proper directory auth mechanism | Comparing plaintext or trusting a client-sent “passwordValid” flag |
| **API key** | Server-issued key store managing subjects, scopes, and status | Safe lookup, value/hash comparison per design, expiration/revocation checks | Logging keys, putting keys in URLs; treating key ID as the secret key |
| **JWT access token** | Authoritative issuer, trusted signing keys/trust configuration | Verify signature, allowed algorithms, issuer, audience, timestamps, usage scope, and revocation policy when needed | Only Base64-decoding payload, skipping signature check, or accepting unwanted alg |
| **OIDC ID token** | Trusted OpenID Provider | Verify ID-token-specific conditions per flow, client, and nonce where applicable | Using an ID token arbitrarily as an API access token |
| **SAML assertion** | Identity Provider with established trust | Verify signature, issuer, audience, timestamps, recipient, and replay per profile | Taking NameID from unverified XML |
| **mTLS client certificate** | Trusted CA chain and server-managed identity mapping | TLS verifies cert; map SAN/subject per policy, check cert status when needed | Trusting self-asserted certificate headers from the Internet |
| **OTP / verification code** | Server-issued and securely stored secret/challenge | Validity window, bound to exact user and transaction, anti-replay, attempt limits | Accepting an OTP unbound to subject or allowing reuse |

For JWT/OIDC/SAML, prefer Spring Security's **standard library components and configuration** or dedicated middleware. Writing custom signature-verification and cryptographic code easily introduces vulnerabilities. For LDAP, usually use **LdapAuthenticationProvider** and configure LDAPS/StartTLS properly instead of rewriting bind logic. A custom provider is appropriate when the evidence protocol, identity source, or verification rules genuinely differ from built-in providers.

### 4.1. Trust Boundary Example with JWT

A JWT consists of three dot-separated parts, and the payload can be **decoded** by anyone to read claims. Example claims:

~~~json
{
  "sub": "user-1001",
  "iss": "https://idp.example.com",
  "aud": "my-api",
  "role": "ADMIN",
  "exp": 1900000000
}
~~~

Those values become trusted data **only after** the server verifies the signature with the right key, algorithm policy, issuer, audience, timestamps, and related conditions. Never grant ADMIN merely because the payload contains a **role** field. You also need a trusted authority-mapping rule and must evaluate whether that issuer is permitted to grant that role.

A JWT may be signed with a valid key yet issued for a **different service**; without checking **audience**, the API can accept tokens not meant for it. A JWKS key fetched from a client-specified URL is also not a trust anchor; the server must control valid issuer/JWKS URLs via verified configuration.

### 4.2. Trust Boundary Example with a Remote Source

When **TrustedIdentitySource** calls an identity system over HTTP/gRPC:

1. Authenticate the **exact source endpoint** with TLS/certificates; if needed, use mTLS or machine-to-machine credentials to authenticate the caller.
2. Set connect and response timeouts; limit retries, especially never retry indefinitely on a single login request.
3. Verify the response contract: subject ID, active/locked, version, authorities, and issuer cannot merely be pass-through client data.
4. Connection loss, 5xx errors, or unverifiable responses must **fail closed**. No “fallback accept” or reading roles from the request to proceed.
5. Distinguish **invalid credentials** from **identity service unavailable** in telemetry; public responses should not leak secrets or system topology.
6. Cached data can cause stale roles/permissions; decide TTL, revocation/disable handling, and consistency based on risk. Never cache raw passwords or reusable tokens.

A trusted source does not mean it is always available. Monitor latency, rejection rates, source error rates, timeouts, password attempt volume, and lockout/recovery policies. A rejection caused by a network error must not be miscounted as a wrong-password strike if the system enforces lockout by failure count.

## 5. Non-Negotiable Security Constraints

### 5.1. Protecting Secrets in Transit and at Rest

- Use **HTTPS/TLS** with valid certificates for client → server and connections to directories/IdPs. Base64 in HTTP Basic does not encrypt passwords.
- Store only password hashes using an appropriate algorithm (BCrypt, Argon2id, or a security-approved option); use an encoder to match. Never do a single plain SHA-256 hash and treat it as strong enough password hashing.
- Never log **Authorization**, raw passwords, access tokens, API keys, secret hashes, or sensitive data in exceptions, traces, and audit events.
- Apply rate limiting, monitor credential stuffing, and enforce appropriate lockout policies; avoid letting BCrypt workload become a denial-of-service vector.
- Remove credentials from Authentication after verification; if using ProviderManager, understand **eraseCredentialsAfterAuthentication** and avoid sharing mutable credentials with caches.

### 5.2. Preventing User Enumeration and Timing Oracles

Do not return different external messages like **“Username does not exist”** vs. **“Wrong password”** if that helps attackers guess accounts. Return a unified code/message for invalid credentials and disallowed account states if policy requires. However, unifying messages alone is **not enough**: lookup and hashing timing differences can still leak status. Evaluate dummy hashing/constant-work where reasonable, combine with rate limiting, and avoid opening an uncontrolled expensive hash computation on every request.

### 5.3. Avoiding Provider-Chain Vulnerabilities

If multiple providers support **UsernamePasswordAuthenticationToken**, the manager may try subsequent ones depending on results, exception types, and configuration. Ensure no weaker provider accepts evidence that a secure provider already rejected. When mechanisms truly differ, use a **separate Authentication token type** with exact supports and avoid unintended parent AuthenticationManager setups.

A provider must never succeed merely because the request already has **isAuthenticated=true** or a valid-looking principal name; the request token is untrusted input. The example in section 3 still checks credentials even when a forged request already carries authorities.

### 5.4. Do Not Ignore Revocation Status

A valid password does not automatically mean an account is still allowed to log in. Check **active/locked/expired** status, password expiration policy if applicable, active permissions, and credential revocation status. For short-lived tokens, balance revocation checks against query cost; for long-lived sessions, evaluate refreshing authorities or invalidating when an account is locked.

### 5.5. Do Not Mix Authentication and Authorization

The provider verifies who is calling; **AuthorizationFilter** or method security decides what they are permitted to invoke. Returned roles must bind to the verified subject. Never escalate privileges based on a request parameter such as **isAdmin=true**. Never grant all authorities to every user “just to make the endpoint work”.

### 5.6. Keep Audits Useful Without Leaking Secrets

Log an event with request/correlation ID, authentication mechanism, outcome code, timestamp, and normalized account identifier or internal ID per privacy policy. Never log passwords or tokens. Separate metrics for **invalid credentials**, **account disabled**, and **source unavailable** for diagnostics; avoid exposing those internal states to clients where user enumeration is a risk.

## 6. How to Verify a Custom AuthenticationProvider Before Production

Use the following checklist to review trust boundaries and provider behavior:

| Scenario | What must the provider do? |
| --- | --- |
| Valid evidence, source has active account | Create principal and authorities from the trusted source |
| Wrong password or user does not exist | Reject, never return an authenticated Authentication |
| Disabled/locked account | Reject, grant no authorities |
| Source timeout/malformed response | Fail closed, report internal service error; no fallback accept |
| Client self-attaches ROLE_ADMIN | Ignore self-asserted role; return only source-granted authorities |
| Provider receives another token type | Do not accept by mistake; accurate supports |
| Badly signed token or wrong issuer/audience | Reject; never trust decoded payload |
| Expired or revoked credential | Reject; verify freshness per evidence type |
| User logged in but lacks API permission | Authentication may succeed, authorization returns 403 |
| Permissions changed or account locked in source | Active sessions/caches obey designed update/revocation policy |
| Multiple providers present | No fallback path bypassing verification |
| Logging and monitoring enabled | No secrets logged; real failure types distinguishable for investigation |

A high-quality test checks the **result from AuthenticationManager and SecurityFilterChain**, not just calling a password comparison helper directly. Test invalid evidence, source errors, role changes, revocation, connection closures, and credential stuffing detection within system scope.

## 7. Common Mistakes

**Mistake 1 — Trusting a client-sent role field.** A client sending **{"username":"alice","role":"ADMIN"}** does not prove ADMIN rights. Fix by building authorities only from a server source or a fully verified token.

**Mistake 2 — Matching passwords with String.equals against a stored hash.** Plaintext passwords do not equal hashes. Use **PasswordEncoder.matches** with a properly managed hash setup.

**Mistake 3 — Auto-creating a new user when the user is not found.** Login verifies an existing identity; it is not registration. Registration must have separate requirements and controls.

**Mistake 4 — Allowing access when the identity source errors.** That is **fail open** behavior, turning a remote outage into a vulnerability. The right behavior is to return a temporary failure and investigate.

**Mistake 5 — Confusing JWT decoding with JWT verification.** Anyone can create a valid Base64 payload; you must verify the signature and critical claims using a trusted library with server-configured issuer/audience.

**Mistake 6 — Checking only the password without checking active/locked.** Correct credentials for a disabled account must still be rejected per policy.

**Mistake 7 — Calling setAuthenticated(true) on the request-submitted Authentication.** Only create an authenticated object after evidence is valid; do not flip state with a simple setter call.

**Mistake 8 — Treating every AuthenticationException as “wrong password”.** Source disconnection and invalid credentials have different root causes. Ensure appropriate logging/metrics and responses without leaking internals.

**Mistake 9 — Overly broad provider supports or loose fallback.** A token might be accepted by another provider out of context. Define token types and provider lists precisely; test ordering and fallback conditions.

## 8. Self-Check Questions

**1. Why must roles never be taken from the request and returned in Authentication?** Because client-asserted roles are untrusted data. Roles must come from an authoritative source and bind to the verified identity.

**2. What can an AuthenticationProvider do when passed an unsupported token type?** **supports(...)** returns false; if invoked directly with an incompatible token, **authenticate(...)** may return null so the manager can consider another provider.

**3. What if the identity store times out, even though the submitted password looks right?** It cannot be verified, so it must fail safely. Never guess “correct” from user-submitted strings; handle the service outage.

**4. Is using BCrypt alone enough to have a trusted identity source?** No. BCrypt only helps match a password against a hash. You also need trust in the hash data, update workflow, account status, roles, source protection, and data transport.

**5. Is it expected for a valid login to receive 403 on GET /api/admin?** Yes. The user was authenticated, but was not granted **ROLE_ADMIN**. That is an authorization denial, not an authentication failure.

**6. A JWT payload lists a trusted issuer and role ADMIN; can it be trusted immediately?** No. You must verify the signature with a trusted configured key, issuer, audience, validity window, token policy, and authority mapping.
