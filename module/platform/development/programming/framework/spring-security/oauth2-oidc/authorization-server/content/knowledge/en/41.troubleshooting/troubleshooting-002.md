# invalid_grant: Expired Code, Reuse, Wrong PKCE, or Refresh Token

invalid_grant indicates that the authorization grant or credential used to exchange for a token is no longer valid in the request context. With Spring Authorization Server, the error typically relates to an expired or already-used authorization code, a code that does not match the client or redirect URI, an incorrect PKCE verifier, or a refresh token that has expired, been revoked, or been replaced after rotation. Each case has a different cause even though the OAuth response may look identical.

Do not diagnose from the HTTP status alone. Read the error field in the OAuth response, correlate the request ID with server-side logs, and check the stored authorization state. invalid_grant is usually returned from the token endpoint with HTTP 400, though a proxy or gateway can alter the response. Always confirm the request reached the right Authorization Server and the right endpoint before drawing conclusions.

## 1. Distinguishing the Three Errors

| OAuth Error | Meaning | Layer to Check First |
|---|---|---|
| invalid_client | The Authorization Server could not authenticate the client using the registered method | Client ID, secret or credential, authentication method, RegisteredClientRepository |
| unauthorized_client | The client was identified, but is not permitted to use the requested grant type or action | AuthorizationGrantType and client authorization policy |
| invalid_grant | The authorization grant or credential used to exchange for a token is invalid, expired, revoked, already used, or does not match the context | Authorization code, refresh token, redirect URI, PKCE, storage state |

Examples:

- Client sends the wrong client secret: usually invalid_client.
- Client authenticates successfully, but is not registered for the client_credentials grant type: unauthorized_client or the corresponding grant error depending on provider and version.
- Client sends an expired or already-redeemed authorization code: invalid_grant.

Other errors can appear in the same flow. invalid_request usually indicates missing or malformed parameters; unsupported_grant_type indicates the server does not support the submitted grant type; invalid_scope indicates the requested scope is invalid or not granted to the client. Do not rewrite these errors into one of the three above just to simplify logs or responses.

## 2. Gathering Safe Evidence Before Fixing

For each error, record enough metadata to reproduce and trace:

- UTC timestamp, server-generated request ID, and trace ID.
- Endpoint, HTTP method, grant_type, and expected client authentication method.
- Client alias or internal reference ID.
- HTTP status, OAuth error code, and success/failure outcome.
- Application version, request-handling instance, and environment.
- For an authorization code or refresh token, record state such as present, valid, consumed, or revoked; do not log the token value.

Do not log Authorization headers, client secrets, client assertions, authorization codes, refresh tokens, access tokens, ID tokens, code_verifier, cookies, or full request bodies. Do not put these values into exception messages, MDC, trace attributes, or CI reports. If you need to correlate an authorization across multiple logs, use the request ID and a dedicated pseudonymous reference ID.

First confirm the request reached the correct Authorization Server token endpoint. Check DNS, TLS, reverse proxy, path mapping, and issuer if the client calls across multiple environments. A response generated by an API gateway does not prove Spring Authorization Server returned invalid_grant. If the response is OAuth JSON, read the error and match the request ID on the server.

## 3. Diagnosing an Expired or Already-Used Authorization Code

An authorization code has a short lifetime and can only be exchanged once. Spring Authorization Server stores the code with the authorization; the provider checks that the code is still valid before issuing tokens. If the client sends an expired code, a code missing from OAuth2AuthorizationService, or a code already marked invalidated after a prior exchange, the token endpoint usually returns invalid_grant.

Check TokenSettings.authorizationCodeTimeToLive to understand the active code lifetime. Compare the issuance time with the token request arrival time in UTC. A client slow to process the callback, a user reopening an old page, or a network retry can cause the code to expire or already be used. Do not extend the code lifetime just to hide a callback issue; check callback latency and client retry behavior first.

Common causes:

- The client exchanges the code after the authorization code has expired.
- The callback is processed twice because the user refreshes the page or the application retries the POST.
- One exchange request succeeds, but the response is lost; the client resends the same code because it does not know the first attempt succeeded.
- The code was issued on a different node or environment than where the token request is being processed.
- Authorization data was deleted, uncommitted, or not shared across instances.

A sequential replay test must prove that the first attempt succeeds and the second fails:

~~~java
@Test
void rejectsAuthorizationCodeReplay() throws Exception {
    String code = authorizeAndExtractCode(
            "browser-client", validRedirectUri, validChallenge, "S256");

    redeemCode(code, validVerifier)
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.access_token").exists());

    redeemCode(code, validVerifier)
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.error").value("invalid_grant"))
            .andExpect(jsonPath("$.access_token").doesNotExist());
}
~~~

Each test run must generate a fresh code. Do not reuse the same code across multiple negative tests because results can be affected by an earlier test having consumed the code.

Concurrent replay is a separate case. If two requests send the same code nearly simultaneously, the store must ensure only one request consumes the code successfully. For JDBC or custom repositories, test with two threads or two independent HTTP clients, synchronize the request timing, and verify exactly one response succeeds. Checking and marking the code as used must be atomic; checking state in memory and updating later can create a race condition.

## 4. Diagnosing a Wrong or Mismatched PKCE Verifier

For clients requiring PKCE, the authorization request stores code_challenge and code_challenge_method alongside the authorization code. When exchanging the code, the client must send the matching code_verifier. If the verifier is missing, wrong, malformed, or does not produce the stored challenge, the server must not issue tokens and usually returns invalid_grant.

For the S256 method, the challenge is computed as BASE64URL-NOPAD(SHA256(ASCII(code_verifier))). Check the following:

- Did the client keep the exact verifier generated before redirecting the user to the authorization endpoint?
- Did the callback retrieve the verifier from the right session or transaction that initiated the authorization request?
- Did the client send code_verifier in the form body of the token request?
- Is the verifier between 43 and 128 characters long using only the character set allowed by RFC 7636?
- Was the challenge generated with SHA-256 and URL-safe Base64 without padding, rather than standard Base64?
- Does code_challenge_method match S256 from the initial authorization request?

RFC 7636 test vector that can be used to verify the challenge calculation function:

~~~text
code_verifier:
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

code_challenge_method:
S256

code_challenge:
E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
~~~

Corresponding Java function:

~~~java
static String s256Challenge(String verifier) throws Exception {
    byte[] digest = MessageDigest.getInstance("SHA-256")
            .digest(verifier.getBytes(StandardCharsets.US_ASCII));
    return Base64.getUrlEncoder()
            .withoutPadding()
            .encodeToString(digest);
}
~~~

If enforcing an S256-only policy, reject code_challenge_method=plain and omitted methods (RFC 7636 defaults to plain). However, when an authorization code has already been issued with a valid challenge and the token request sends a non-matching verifier, the error should be investigated as invalid_grant. Do not change the PKCE policy or disable requireProofKey to make the request succeed.

A negative test should generate a fresh code with a valid verifier, then send a different verifier of valid length:

~~~java
redeemCode(code, "wrong-verifier-value-0123456789-ABCDEFGHIJKLM")
        .andExpect(status().isBadRequest())
        .andExpect(jsonPath("$.error").value("invalid_grant"))
        .andExpect(jsonPath("$.access_token").doesNotExist());
~~~

Do not log the verifier, challenge, or authorization code in test logs. Log only the request ID, test case, endpoint, and error code.

## 5. Checking Client Binding and Authorization Code Redirect URI

An authorization code is bound to the RegisteredClient that initiated the authorization. The token request must be authenticated as that exact client. If a code belonging to browser-client is sent with another client's credentials, the server must reject the code exchange. Check client_id and the client authentication method on the token request, then compare with the client ID bound to the stored authorization. Do not use RegisteredClient.id (the internal record key) in place of the protocol client_id.

redirect_uri is also part of the authorization transaction. If the client sent redirect_uri in the authorization request, the token request must send the exact same URI. The comparison must preserve path, port, scheme, and significant components; do not normalize two different URIs into one. Do not change the redirect URI configuration to a wildcard to fix invalid_grant.

A typical test for a mismatched redirect URI:

~~~java
@Test
void rejectsAuthorizationCodeWithDifferentRedirectUri() throws Exception {
    // authorizeAndExtractCode creates a code with the registered redirect URI.
    String code = authorizeAndExtractCode(
            "browser-client",
            "https://client.example/callback",
            validChallenge,
            "S256");

    mockMvc.perform(post("/oauth2/token")
                    .with(httpBasic("browser-client", "test-secret"))
                    .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                    .param("grant_type", "authorization_code")
                    .param("code", code)
                    .param("redirect_uri", "https://attacker.example/callback")
                    .param("code_verifier", validVerifier))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.error").value("invalid_grant"))
            .andExpect(jsonPath("$.access_token").doesNotExist());
}
~~~

The helper in the example must complete login and consent as required by the application. Each test must create its own code so a redirect URI error is not confused with an already-redeemed code error.

## 6. Diagnosing invalid_grant for Refresh Tokens

A refresh token can be rejected when it does not exist, is expired, is revoked, belongs to another client, has been replaced, or violates the rotation policy. Check the following:

- Is the client sending the refresh token the same client that originally received it?
- Is the token still valid and has the authorization not been revoked?
- Has the refresh token expired according to TokenSettings.refreshTokenTimeToLive?
- If reuseRefreshTokens(false) is configured, does the client store and use the new refresh token after each refresh?
- Is a concurrent request or retry reusing the old refresh token after rotation succeeded?
- Do multiple server instances share OAuth2AuthorizationService and update state consistently?

When rotation is enabled, a successful refresh response may contain a new refresh token. The client must atomically replace the old token in its store. If the application fails to persist the new token yet retries sending the old token, the next attempt can receive invalid_grant. Check client-side retry policies and write ordering.

Do not assume all refresh tokens are rotated by default. Behavior depends on TokenSettings and version configuration. Check the reuseRefreshTokens value and write tests matching the deployed policy. Example rotation configuration:

~~~java
TokenSettings tokenSettings = TokenSettings.builder()
        .reuseRefreshTokens(false)
        .refreshTokenTimeToLive(Duration.ofDays(30))
        .build();
~~~

After a successful refresh, the client must persist the new refresh token before deleting the old one. A test should confirm that the new token works and the old token cannot be reused:

~~~java
RefreshTokenResponse rotated = refresh(initialRefreshToken);

refresh(rotated.refreshToken())
        .andExpect(status().isOk());

refresh(initialRefreshToken)
        .andExpect(status().isBadRequest())
        .andExpect(jsonPath("$.error").value("invalid_grant"));
~~~

RefreshTokenResponse and the refresh helper in the example are test fixtures, not built-in Spring Authorization Server types. Map the token endpoint JSON response into a helper matching your project's test harness.

## 7. Checking Storage Data and Multiple Instances

Spring Authorization Server uses RegisteredClientRepository to look up clients and OAuth2AuthorizationService to store authorization and token state. If one node issues a code and another node cannot find it, check whether both nodes use the same database, schema, tenant, serializer, and repository configuration.

With JDBC or custom repositories, verify transaction commits, token state updates, expiration timestamps, and marking the code as invalidated. When concurrent requests redeem the same code or refresh the same token, consumption must be atomic. A pattern that reads state, checks it, and writes back without locking or concurrency control can allow two requests to pass the check simultaneously.

Verify system time across nodes using NTP. Clock skew can cause a token to be treated as not yet valid or already expired. Compare issuance and verification timestamps in UTC; do not infer from log display timezones.

## 8. Placing Logs and Breakpoints in the Right Spots

To pinpoint the failure, trace processing points in order:

- Client authentication filter/provider: identifies the client and verifies the credential method.
- Token endpoint filter/converter: reads grant_type and converts the request into the corresponding authentication.
- Grant authentication provider: validates the authorization code, refresh token, scope, and grant conditions.
- RegisteredClientRepository: looks up client configuration and grant types.
- OAuth2AuthorizationService: finds the authorization, reads token state, and persists updates.
- OAuth2TokenGenerator: observe only the result and token type, do not print token values.

You may increase log levels for the relevant packages temporarily in test environments, but do not enable broad TRACE logging in production without inspecting emitted data. Prefer logging event name, client alias, grant type, request ID, and OAuth error code. When using a debugger, do not expand or copy secrets, codes, tokens, verifiers, or full OAuth2Authorization objects into screenshots or reports.

Do not return internal exceptions, SQL, table names, stack traces, or secret encoder details to the client. Client-facing error_description should be brief and must not reveal whether a specific client exists. Detailed diagnostics belong in access-controlled internal logs.

## 9. Quick Decision Table

| Observation | Likely Cause | Next Check |
|---|---|---|
| Previously valid code, but request arrives late | Authorization code expired | TokenSettings.authorizationCodeTimeToLive, callback latency, and UTC clock |
| First code exchange succeeds, second fails | Normal one-time-use behavior | Check retries or callback processed twice |
| Fresh code still returns invalid_grant | Client binding, redirect URI, or PKCE mismatch | Compare stored authorization data and token request parameters |
| Client believes verifier is right, server rejects | Wrong verifier stored, wrong session, or wrong challenge calculation | Check verifier creation/storage flow and S256 test vector |
| Refresh token suddenly returns invalid_grant after refresh | Token rotation or revocation | Check reuseRefreshTokens, new token persistence, and retries |
| Only one node returns invalid_grant | Inconsistent storage, cache, or config across nodes | Compare repository, database, serializer, and clock |
| HTTP 400 without OAuth error JSON | Gateway or proxy generated the response | Check response headers, access logs, and request ID at each layer |

## 10. Checklist Before Closing the Incident

- [ ] Confirmed the request reached the right token endpoint and which OAuth error code the response contains.
- [ ] Confirmed client authentication succeeded before investigating the authorization grant.
- [ ] Authorization code or refresh token is still valid and not unexpectedly consumed or revoked.
- [ ] Redirect URI, client binding, and PKCE verifier match the original authorization.
- [ ] Token rotation, retries, and client-side state updates have been verified.
- [ ] Instances share the same repository and have synchronized system clocks.
- [ ] Logs contain no secrets, authorization codes, tokens, verifiers, or personal data.

If the actual response is invalid_client or unauthorized_client, return to checking client authentication or grant permissions before analyzing the grant. When the error is invalid_grant, focus on authorization lifecycle and context. Preserving security checks while remediating ensures the root cause is fixed without weakening the OAuth 2.0/OIDC flow.
