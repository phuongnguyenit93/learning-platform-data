# Protecting `state`, Callbacks, and Code Data in the Browser

> **Chapter: Authorization Code and PKCE.** Part of the **SPRING_SECURITY_OAUTH2_OIDC_AUTHORIZATION_SERVER** module: learning how to design, configure, secure, test, and operate an OAuth 2.0/OpenID Connect Authorization Server with Spring Security and Spring Authorization Server in Spring Boot. The focus is on **preserving the exact login transaction**, **preventing misuse of authorization codes**, and **minimizing data leakage through the browser**.

## 1. The Problem: The Browser Is a Transit Channel, Not Long-Term Secret Storage

In the Authorization Code Flow, the OAuth2/OIDC Client redirects the browser to the Authorization Server. After login and consent, the Authorization Server redirects the browser back to the **Client's redirect URI**, typically with `code` and `state` in the query string. The Client uses `code` to call the token endpoint over the back-channel. Because browsers have browsing history, extensions, scripts, `Referer` headers, and intermediate proxies/logs, having the code appear in callback URLs creates a distinct attack surface.

Running example throughout:

- **Authorization Server / OpenID Provider:** `https://login.example.vn`, fixed issuer `https://login.example.vn`.
- **Confidential web client (Relying Party):** `portal-web` at `https://portal.example.vn`, backed by Spring Boot.
- **Registered callback:** `https://portal.example.vn/login/oauth2/code/portal`.
- **Resource Server:** `https://api.example.vn`, accepting access tokens issued by the Authorization Server.
- **Flow:** Authorization Code + **PKCE S256**, `state` against callback CSRF/transaction mix-ups, and a separate `nonce` when using OIDC.

| Value | Where Generated and Stored? | Travels Through Browser? | Security Purpose |
|---|---|---|---|
| `state` | Randomly generated by Client, linked to browser transaction/session | **Yes**: authorization request and callback | Correlates response with transaction started by the same Client; prevents login CSRF and transaction mix-ups |
| `code_verifier` | Randomly generated by Client and kept in isolated transaction state | **Must not appear in URL**; in SPAs kept in temporary browser memory/storage | Secret proving the party exchanging the code initiated the PKCE transaction |
| `code_challenge` | Derived from `code_verifier`, typically S256 | **Yes**: authorization request | Binds the issued code to the matching `code_verifier` |
| `code` | Issued by Authorization Server after auth/consent | **Yes**: callback URL in standard Authorization Code Flow | Single-use credential for client token exchange; must be short-lived and bound to client/redirect/PKCE |
| `nonce` (OIDC) | Generated by Client and stored with transaction | **Yes** in authorization request; appears in ID Token for RP verification | Binds the ID Token to the login transaction when nonce is used |
| Client secret / private key | Confidential client or authorized secret manager | **No** | Authenticates confidential client at the token endpoint |
| Access/refresh token | Issued by Authorization Server at token endpoint | **Does not travel in URLs in Authorization Code Flow**; SPAs may receive tokens in browser from token endpoint | Calls APIs or refreshes tokens; protect according to application type |

**Division of responsibilities:**

- **Client/RP** generates, stores, and verifies `state`, retains `code_verifier`, handles callbacks, exchanges codes, and validates ID Tokens when using OIDC.
- **Authorization Server** checks `client_id`/`redirect_uri`, binds PKCE to the authorization code, issues short-lived codes, and rejects invalid, expired, or reused codes.
- **Browser** follows redirects and carries authorization responses back to the Client. It is not a trusted secret vault; never place client secrets, refresh tokens, or `code_verifier` in URLs.
- **Resource Server** validates access tokens, issuer, audience, scopes, and API policies. It does not use `state` or authorization codes to authorize requests.

## 2. Full Flow: Three Values Protecting Three Different Boundaries

```mermaid
sequenceDiagram
    autonumber
    participant B as Browser
    participant C as OAuth2/OIDC Client (RP)
    participant AS as Authorization Server (OP)
    participant API as Resource Server

    B->>C: GET /private
    C->>C: Creates transaction: state, verifier, nonce, redirect URI, issuer
    C->>C: challenge=BASE64URL(SHA256(verifier))
    C-->>B: 302 to /oauth2/authorize?state&code_challenge&nonce...
    B->>AS: Authorization request over HTTPS
    AS->>AS: Validates client_id, redirect_uri, scope, PKCE
    AS->>B: Login and consent if needed
    AS->>AS: Issues short-lived code bound to client + redirect + challenge
    AS-->>B: 302 Location: https://portal.example.vn/login/oauth2/code/portal?code=...&state=...
    B->>C: GET callback?code=...&state=...
    C->>C: Matches state with stored transaction, consumes once
    C->>C: Verifies issuer/transaction; retrieves matching code_verifier
    C->>AS: POST /oauth2/token<br/>code + redirect_uri + code_verifier + client authentication
    AS->>AS: Validates code, client, redirect URI, PKCE; invalidates code
    AS-->>C: Token response over HTTPS (OIDC may include id_token)
    C->>C: If OIDC: validates id_token and nonce
    C-->>B: 303/302 to clean page without code/state
    B->>C: GET /private
    C->>API: Authorization: Bearer ACCESS_TOKEN
    API-->>C: Resource if token/permissions valid
```

Using `state` **does not replace** PKCE and vice versa:

| Risk | Primary Control | Complementary Control |
|---|---|---|
| Attacker forces browser to call callback with code from another session (login CSRF / code injection) | Random, session-bound, single-use `state` | PKCE and nonce/issuer checks where applicable |
| Authorization code leaked via URL and redeemed for tokens | PKCE S256 + client authentication if confidential | Single-use code, short TTL, exact redirect binding, leak minimization |
| Code from another Authorization Server sent to wrong token endpoint (mix-up) | Bind issuer/AS to transaction; verify issuer response when supported | Per-AS redirect URIs or RFC 9207 mechanism |
| Old ID Token / token from another transaction replayed | Verify signature/`iss`/`aud`/`exp`/`nonce` | Session/transaction binding |
| Code/state recorded in history, Referer, or logs | Dedicated callback, no third-party assets, no-referrer/no-store, early redirect to clean URL | PKCE, single-use, monitoring and redaction |

Per RFC 9700 (OAuth 2.0 Security Best Current Practice), Clients must protect against CSRF. When PKCE is properly implemented and verified as supported by the AS, or with OIDC nonce properly used, the spec notes those mechanisms can contribute to CSRF protection; **keeping `state` bound to the session and single-use remains a solid, easily observable and testable choice**, especially for Clients serving multiple issuers.

## 3. `state`: Preventing CSRF and Restoring the Right Transaction

### 3.1. Properties of a Secure `state`

A sound `state` value must be:

1. **Unpredictable:** generated by a cryptographic RNG such as `SecureRandom` with sufficient entropy (e.g., 32 random bytes).
2. **Independent per transaction:** two tabs or two clicks on "Sign in" receive two distinct values.
3. **Bound to the initiating browser/session:** the Client stores the transaction record under a session or server-side state it controls; never treat the callback's `state` as self-authenticating proof.
4. **Short-lived and single-use:** invalidate the transaction after processing the response; replaying a code or state must never start a new session.
5. **An opaque reference carrying no private data:** never copy emails, access tokens, `code_verifier`, arbitrary URLs, or PII into a `state` displayed in URLs.
6. **Applied to both success and error responses:** an `error=access_denied&state=...` callback also needs correlation to the right request.

Java example generating a random `state` value:

```java
import java.security.SecureRandom;
import java.util.Base64;

final class OAuthStateGenerator {
    private static final SecureRandom RANDOM = new SecureRandom();

    static String createState() {
        byte[] random = new byte[32];    // 256-bit entropy
        RANDOM.nextBytes(random);
        return Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(random);
    }
}
```

This snippet only **generates `state`**; it is not an OAuth2 Client implementation. You must store `state` in a trusted transaction record and compare it against the response. In apps using `oauth2Login()`, Spring Security already manages authorization requests/`state`; **do not write an extra custom callback controller** just to use the snippet above.

### 3.2. What Should Be Stored in the Transaction?

Illustrative data model stored on the **client backend** (pseudocode, not a Spring API):

```text
AuthTransaction {
  state:            "STATE_RANDOM_256_BITS"
  expectedIssuer:   "https://login.example.vn"
  clientId:         "portal-web"
  redirectUri:      "https://portal.example.vn/login/oauth2/code/portal"
  codeVerifier:     "RANDOM_PKCE_VERIFIER"
  nonce:            "RANDOM_OIDC_NONCE"
  browserSessionId: "SERVER_MANAGED_SESSION_REFERENCE"
  returnPath:       "/orders"           # Validated internal path only
  createdAt:        2026-11-16T10:00:00Z
  expiresAt:        2026-11-16T10:05:00Z
  consumed:         false
}
```

When the callback arrives, the Client must find **the exact transaction initiated by that browser**, match `state`, enforce expiry, and consume it **atomically**. Backends can store this in the session or a TTL-bounded transaction store; for multiple tabs/IdPs, a session-scoped `state → transaction` map with eviction and max-entry limits can be used. Never let a user guess a state to retrieve someone else's transaction.

**Processing algorithm (pseudocode):**

```text
on GET callback:
    reject if request has both code and error or misses required fields
    transaction = lookupPendingTransactionForCurrentBrowser(response.state)
    reject if not found, expired, wrong session, or wrong client/issuer
    atomically consume transaction once validated
    if response.error:
        handle OIDC/OAuth2 error per transaction; do not exchange code
    if response.code:
        send code, transaction.redirectUri, and transaction.codeVerifier
        over HTTPS back-channel to the stored issuer's token endpoint
    only after token/ID Token validation succeeds:
        create/update client session
        redirect browser to validated internal returnPath
```

A callback endpoint invoked with an invalid `state` must **reject**, never "restart and treat as valid". When `state` is wrong, never try exchanging the code "just to see if it works". Never render raw technical errors, `state`, or `code` values verbatim on an error page.

### 3.3. Multiple Tabs, Session Stores, and Lifecycle

- Some session-based `AuthorizationRequestRepository` implementations may not support unlimited parallel authorization requests; **test multi-tab flows** before claiming full support. If needed, design a repository storing multiple transactions keyed by `state` with TTL and size limits.
- Across multiple pods, callbacks may land on a different instance. Use a shared session store (or proper session routing) so the right authorization request/`code_verifier` can be read.
- Session cookies must use `Secure`, `HttpOnly`, and `SameSite` tested across top-level redirects; misconfigured scheme/domain/path or proxy forwarded headers will drop the session and trigger `invalid_state`.
- Never switch Spring Security `oauth2Login` to `SessionCreationPolicy.STATELESS` without building an equivalent mechanism to persist authorization requests.
- `state` is a value **that can appear in URLs**. Even though random, do not treat it like an absolute secret password. Minimize exposure of transaction data in `Referer`/logs.
- When a user presses "Back" and revisits an old callback, the already-consumed transaction must be **rejected**; display a friendly error or allow starting a fresh login flow.

## 4. PKCE S256: Proving Who May Exchange the Authorization Code

PKCE (Proof Key for Code Exchange, RFC 7636) prevents intercepted codes from being exchanged for tokens by another party. The Client generates `code_verifier`, computes `code_challenge`, and sends the challenge **before** the Authorization Server issues the code. When exchanging the code, the Client must send the **original verifier**; the AS verifies by recomputing the challenge.

With `S256`:

```text
code_verifier  = random string, 43–128 chars from RFC 7636 character set
code_challenge = BASE64URL_NO_PADDING(SHA256(ASCII(code_verifier)))
code_challenge_method = S256
```

**Never use `plain` if the system supports S256.** Never use predictable strings like timestamps, user IDs, or session IDs as the verifier. Never hardcode a single app-wide verifier or put the verifier in the authorization request URL.

### 4.1. Generating PKCE in Java

This Java 17+ example is independent of Spring libraries (for tests or clients implementing the protocol manually; in Spring Security apps, let OAuth2 Client manage it):

```java
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;

record PkcePair(String verifier, String challenge) {}

final class PkceGenerator {
    private static final SecureRandom RANDOM = new SecureRandom();

    static PkcePair newPair() throws GeneralSecurityException {
        byte[] random = new byte[32];
        RANDOM.nextBytes(random);

        String verifier = Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(random);

        byte[] digest = MessageDigest.getInstance("SHA-256")
                .digest(verifier.getBytes(StandardCharsets.US_ASCII));

        String challenge = Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(digest);

        return new PkcePair(verifier, challenge);
    }
}
```

32 bytes of entropy produce a **43-character** unpadded Base64URL verifier, meeting PKCE length rules. The SHA-256 digest is 32 bytes, yielding a **43-character** Base64URL challenge. Send only `challenge` to the authorization endpoint; keep `verifier` in the Client's transaction data and send it in the **POST token request**. In an SPA, keep the verifier in protected origin-scoped memory/ephemeral state and clear it after use; XSS can still read browser-stored data, so enforce CSP and avoid third-party scripts.

### 4.2. Three Distinct PKCE Checks

1. **At the AS authorization endpoint:** require `code_challenge` and `code_challenge_method=S256` per client policy, validate format, and store the challenge bound to the code about to be issued.
2. **At the AS token endpoint:** `code_verifier` must be present and reproduce the bound challenge. Missing/invalid verifier ⇒ reject, typically `invalid_grant`.
3. **At the Client:** the verifier used to exchange the code must be the one saved **for that exact `state`/transaction**, never taken from callback params, a browser-editable cookie, or freshly generated at token exchange.

PKCE does not render a leaked code harmless. If an attacker captures both the code and verifier via XSS, storage, or logs, the risk remains. Therefore, pair PKCE with HTTPS, XSS defenses, minimal verifier retention, short code TTLs, and single-use codes.

## 5. Callbacks: Exact Redirect URI and Safe Response Handling

### 5.1. Redirect URI Belongs to the Client, Not the Authorization Server

In our example, the callback is:

```text
https://portal.example.vn/login/oauth2/code/portal
```

This path is handled by **Spring Security OAuth2 Login on the Client**. It is **not** `/oauth2/token` on the AS and not an arbitrary UI page loading third-party assets. In standard Authorization Code Flow, the AS redirects the browser to the callback:

```http
HTTP/1.1 302 Found
Location: https://portal.example.vn/login/oauth2/code/portal?code=AUTH_CODE&state=STATE_RANDOM
Cache-Control: no-store
```

Values in this example are placeholders. In a real session, the AS also checks the client, authenticates the user, handles consent (if needed), and enforces other bindings before issuing the code.

Per RFC 9700, the AS must **compare the redirect URI against registered URIs using exact string matching**, except for the defined native-app loopback port exception. Never use prefix matching, wildcards, custom domain suffixes, or allow nested redirect parameters.

| Registered URI | Request URI | Outcome |
|---|---|---|
| `https://portal.example.vn/login/oauth2/code/portal` | Identical string | Valid |
| Same as above | `https://portal.example.vn/login/oauth2/code/portal/` | Mismatch due to trailing `/` |
| Same as above | `http://portal.example.vn/login/oauth2/code/portal` | Mismatch due to different scheme |
| Same as above | `https://portal.example.vn.evil.test/login/oauth2/code/portal` | Mismatch due to different host |
| Same as above | `https://portal.example.vn/login/oauth2/code/portal?next=https://evil.test` | Mismatch unless that exact query is registered |

The AS must **never redirect responses** to an invalid or unverified redirect URI. Even on malformed requests, never redirect error responses to an attacker-supplied URI. Authorization error responses sent to a **verified URI** must also carry `state`, which the Client validates per protocol contract.

### 5.2. Client Processes Callbacks in Controlled Order

At the callback, the Client must:

1. Read `code` **or** `error` along with `state`; reject conflicting or duplicate parameters that could cause parser/validator discrepancies.
2. Restore the original authorization request from **the same browser's** session/transaction store and match `state`, issuer, and registration ID/redirect URI.
3. Guard against **authorization server mix-up** if the Client supports multiple issuers (see Section 5.3).
4. When the response carries `code`, exchange it at **the token endpoint bound to the original request**; never read a token URL from callback query parameters.
5. Only after token/ID Token validation succeeds should you create/update the Client session and redirect to a **same-origin/allowlisted** destination page.
6. Never render a callback page containing analytics, tracking pixels, or external scripts while the URL still holds `code`/`state`; never log raw URLs.

`redirect_uri`, `client_id`, `code_challenge`, and issuer must all remain bound to the **original authorization request**. PKCE and client authentication only verify the transaction when preserved and used properly; assembling a token request from callback query params breaks trust boundaries.

### 5.3. Mix-Up Protection with Multiple Identity Providers

A Client may allow login with multiple OPs. If a callback from OP A is mistakenly processed as coming from OP B, the Client might send the code to the wrong token endpoint, leaking the code or confusing identity (authorization server mix-up).

Per RFC 9700/RFC 9207, one mitigation is using the `iss` parameter in the authorization response when supported by the OP, verifying an **exact** match with the issuer stored for that transaction. With OIDC, issuer guarantees in the ID Token/response apply per spec; another defense is registering **a distinct redirect URI per Authorization Server**.

Never infer a trusted issuer solely from an `iss` sent by the browser and dynamically pick that token endpoint. The **source of truth** must be configuration/transaction state created up front by the Client. Test behavior for your Spring Security version and `iss` authorization response support, as not all deployments handle RFC 9207 automatically.

## 6. Minimizing Code and State Leakage via the Browser

### 6.1. Where Can a Code Leak?

| Channel | Scenario | Mitigation |
|---|---|---|
| **Referer/Referrer** | Callback renders a page with images/fonts/scripts from external domains or user clicks an external link; URL with `code`/`state` leaks in `Referer` | `Referrer-Policy: no-referrer`, avoid third-party assets on callback, redirect to a clean URL early |
| **Browser history** | `callback?code=...&state=...` stays in browser history | Backend processes immediately and redirects to a parameter-free URL; SPA calls `history.replaceState(...)` right after reading `state`/`code` |
| **Reverse proxy/access logs** | NGINX/Ingress/APM logs full callback query string | Disable logging sensitive query strings; redact `code`, `state`, `session_state` if present, and `id_token`/tokens if they appear |
| **Error pages and exceptions** | Stack traces/HTML display full request URL or raw params | Return generic errors + correlation ID; log only error category, flow type, and client ID when appropriate |
| **Third-party JS, analytics, tag managers** | Scripts read `window.location.href` or `location.search` | Never embed unvetted scripts on callbacks; strict CSP with only essential assets |
| **Browser extensions, XSS** | Unauthorized scripts read data on Client's origin | Prevent XSS, enforce CSP, review dependencies, protect session cookies; prefer BFF when appropriate |
| **Copied/screenshotted URLs** | User pastes callback URL into a support ticket or chat | Redirect to a clean URL upon completion; instruct users/staff to redact `code`/`state` when debugging |
| **Tokens in URLs** | App redirects `?access_token=...` after exchange | Never put access/refresh/ID Tokens in URLs; use server-side sessions or safe storage |

**Never treat an authorization code as harmless just because it is "single-use".** It can be stolen **before** the Client redeems it. PKCE and client authentication reduce abuse potential, yet the application must still avoid broadcasting the code.

### 6.2. Fast Callback Processing and Clean Redirects

For a **server-side web client**, ideally Spring Security's filter intercepts the callback, validates `state`, runs the backend token exchange, establishes the session, and redirects to a target page free of `code`/`state`. Do not make the callback a React/Thymeleaf view full of trackers and navigation links while the query string remains intact.

Recommended response headers when sensitive parameters are present:

```http
Cache-Control: no-store
Referrer-Policy: no-referrer
Content-Security-Policy: default-src 'none'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'
X-Content-Type-Options: nosniff
```

This CSP is a strict template for a minimal callback page. If the callback simply returns `302`/`303`, there may be no HTML body for CSP to govern, yet **omitting query logs** and setting `Cache-Control: no-store` and `Referrer-Policy: no-referrer` still help. Test actual responses through CDNs/proxies; `no-store` cannot "erase" data already written to logs or history.

For an SPA that must handle callbacks in JavaScript, process and strip the URL **before** loading analytics or third-party bundles:

```javascript
// Minimal illustration for SPA callback; still requires a standard OAuth2/OIDC library.
const params = new URLSearchParams(window.location.search);
const code = params.get("code");
const state = params.get("state");
const error = params.get("error");

// Read values first, then immediately strip query from address bar/current history.
// Never log or send code/state to analytics.
window.history.replaceState(
  window.history.state,
  "",
  window.location.pathname
);

// Next step: invoke transaction/state check, PKCE,
// and token exchange designed for public browser clients.
// Do not trust code/state merely because the URL contained them.
```

This snippet **only illustrates stripping the URL**, not a complete secure OAuth2 Client. If the callback uses other non-sensitive query parameters, retain only allowlisted ones; never preserve the entire query string blindly. Calling `replaceState` does not stop XSS or browser extensions that already read the URL beforehand.

### 6.3. Should You Switch `response_mode` to `form_post`?

Some OPs/clients support `response_mode=form_post`, delivering the authorization response to the callback via an HTML form POST rather than URL query parameters. RFC 9700 mentions this as an option to reduce browser history and `Referer` leakage.

However:

- **Both sides must support** that response mode; never append `response_mode=form_post` assuming Spring Security OAuth2 Login accepts POST by default.
- Cross-site POSTs interact differently with `SameSite=Lax` session cookies and CSRF filters; test thoroughly and configure the callback explicitly.
- Form POST only **mitigates one leakage channel**; it does not replace `state`, PKCE, issuer, redirect URI, TTL, or client authentication checks.

For a Spring MVC web client using the default callback, Authorization Code + PKCE over a **top-level GET redirect** remains secure when the callback executes swiftly, URLs are unlogged, and the code is tightly bound.

## 7. Exchanging the Code at the Token Endpoint and Preventing Replay

The token request must travel over HTTPS using `application/x-www-form-urlencoded` and include `code_verifier` alongside the code and redirect URI. Example confidential client request:

```http
POST /oauth2/token HTTP/1.1
Host: login.example.vn
Content-Type: application/x-www-form-urlencoded
Authorization: Basic REDACTED_CLIENT_CREDENTIALS

grant_type=authorization_code&code=AUTH_CODE&redirect_uri=https%3A%2F%2Fportal.example.vn%2Flogin%2Foauth2%2Fcode%2Fportal&code_verifier=ORIGINAL_PKCE_VERIFIER
```

This request is an **illustrative template**; encoded credentials/secrets are non-functional placeholders. `Authorization: Basic ...` applies when the client registers `client_secret_basic`; a **public client** using `ClientAuthenticationMethod.NONE` does not send a confidential client secret, though it must carry `client_id` as required by the protocol/implementation.

The server checks:

1. The code exists, is unexpired, and has not been used or revoked.
2. The code is bound to **the exact `RegisteredClient`** performing the exchange and the `redirect_uri` used in the authorization request.
3. `code_verifier` matches the `code_challenge` bound to the code under `S256`.
4. Client authentication is valid if confidential; grant/scopes/consent comply with policy.
5. After a successful exchange, the code **cannot be reused**; a second exchange attempt must be rejected, typically with `invalid_grant`.

**Never send codes via GET to the token endpoint**, embed codes in access tokens, or return access tokens in query strings. The token response typically carries `access_token`, optionally `refresh_token`, and (in OIDC) `id_token`; store tokens in the appropriate Client tier. For debugging, log `invalid_grant` and correlation IDs rather than full request bodies or `Authorization` headers.

Per RFC 6749/RFC 9700, an authorization code must be invalidated upon first use. When code reuse is detected, the server should consider revoking tokens previously issued from that code per policy to limit replay; verify exact behavior in your Spring Authorization Server deployment.

## 8. Configuring Spring Authorization Server to Enforce PKCE and Exact Callbacks

Below is an illustrative bean on the **Authorization Server side**, registering a confidential web client `portal-web`. APIs correspond to Spring Authorization Server 1.x; use compatible Spring Boot / Spring Security / Spring Authorization Server versions in your project.

```java
import java.time.Duration;

import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.oauth2.core.AuthorizationGrantType;
import org.springframework.security.oauth2.core.ClientAuthenticationMethod;
import org.springframework.security.oauth2.core.oidc.OidcScopes;
import org.springframework.security.oauth2.server.authorization.client.RegisteredClient;
import org.springframework.security.oauth2.server.authorization.client.InMemoryRegisteredClientRepository;
import org.springframework.security.oauth2.server.authorization.client.RegisteredClientRepository;
import org.springframework.security.oauth2.server.authorization.settings.ClientSettings;
import org.springframework.security.oauth2.server.authorization.settings.TokenSettings;

@Bean
RegisteredClientRepository registeredClientRepository(
        PasswordEncoder passwordEncoder,
        @Value("${PORTAL_CLIENT_SECRET}") String rawSecret) {

    RegisteredClient portal = RegisteredClient
            .withId("registration-portal-web")
            .clientId("portal-web")
            .clientSecret(passwordEncoder.encode(rawSecret))
            .clientAuthenticationMethod(
                    ClientAuthenticationMethod.CLIENT_SECRET_BASIC)
            .authorizationGrantType(AuthorizationGrantType.AUTHORIZATION_CODE)
            .redirectUri(
                    "https://portal.example.vn/login/oauth2/code/portal")
            .scope(OidcScopes.OPENID)
            .scope(OidcScopes.PROFILE)
            .clientSettings(ClientSettings.builder()
                    .requireProofKey(true)
                    .requireAuthorizationConsent(true)
                    .build())
            .tokenSettings(TokenSettings.builder()
                    .authorizationCodeTimeToLive(Duration.ofMinutes(3))
                    .build())
            .build();

    return new InMemoryRegisteredClientRepository(portal);
}
```

**Explanation of choices:**

- `requireProofKey(true)` requires the client to use PKCE for the Authorization Code Flow. **Public clients** must definitely use PKCE; this confidential client example also enables it to strengthen defense against code injection/interception.
- `redirectUri(...)` is **the Client-side callback path**, not the token endpoint. Declare only valid public URIs with exact matching.
- `authorizationCodeTimeToLive(Duration.ofMinutes(3))` limits code lifetime; 3 minutes is an **example policy**, not a mandatory rule.
- `passwordEncoder.encode(rawSecret)` stores a **hash** of the client secret on the Authorization Server; the plaintext secret lives in the Client's secret store. Never hardcode secrets in source code.
- `requireAuthorizationConsent(true)` enforces consent per policy; it **does not replace** `state` or PKCE.
- `InMemoryRegisteredClientRepository` is only for demos/tests; production needs a durable registry and authorization service enforcing single-use codes across instances.

You must also provide a `PasswordEncoder` bean, `SecurityFilterChain` for AS endpoints and user login, `AuthorizationServerSettings.issuer(...)`, `OAuth2AuthorizationService`/consent service, and signing/`JWKSource` if issuing JWT/OIDC tokens. Do not treat the demo snippet above as a complete Authorization Server.

### 8.1. How Do Public Clients Differ?

When registering an SPA or native app, switch the authentication method to `ClientAuthenticationMethod.NONE`, omit `clientSecret`, and require PKCE. The redirect URI must match the app type (an exact registered HTTPS origin/callback; native apps have specific loopback rules). Keeping verifiers/tokens in a browser gives a different risk profile than a confidential backend client; see Section 10.

### 8.2. Storing Codes in `OAuth2AuthorizationService`

Spring Authorization Server uses `OAuth2AuthorizationService` to manage authorization codes and authorization state, with in-memory or JDBC implementations. Across multiple pods, you need a **shared, consistent data store** so a code issued by pod A can be redeemed once validly by pod B; never maintain isolated per-pod in-memory code stores. Design storage and transactions robustly so two concurrent token exchanges cannot both redeem the same code.

Never build custom `/oauth2/authorize` or `/oauth2/token` controllers merely to tweak callbacks: configure the built-in endpoints/filters/providers and write security tests covering PKCE, client binding, and replay.

## 9. Spring Security OAuth2 Client: Keeping `state` and Verifier on the RP Side

On the **Spring Boot Client application** at `https://portal.example.vn`, configure OIDC as follows:

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          portal:
            provider: company-idp
            client-id: portal-web
            client-secret: ${PORTAL_CLIENT_SECRET}
            client-authentication-method: client_secret_basic
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope:
              - openid
              - profile
        provider:
          company-idp:
            issuer-uri: https://login.example.vn

server:
  servlet:
    session:
      cookie:
        secure: true
        http-only: true
        same-site: lax
```

In this example:

- `/oauth2/authorization/portal` initiates OAuth2 login on the Client, distinct from `/oauth2/authorize` on the AS.
- `/login/oauth2/code/portal` is the default callback handled by Spring Security OAuth2 Login.
- `issuer-uri` fetches OP metadata via discovery and verifies the OIDC issuer; the token endpoint is never taken from callback parameters.
- The session cookie preserves authorization request correlation data. `SameSite=Lax` generally fits top-level GET callbacks, though you must **test it in practice** through your reverse proxy and target browsers.
- Never put real secrets in `application.yml`. `PORTAL_CLIENT_SECRET` comes from a secret store or environment variable.

### 9.1. Explicitly Requiring PKCE for a Confidential Spring Security Client

In Spring Security OAuth2 Client, public client mode can automatically enable PKCE per configuration. If the Authorization Server enforces PKCE for a **confidential client**, verify the outgoing request and configure the resolver to add PKCE explicitly if your Spring version does not enable it automatically:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web.DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestCustomizers;
import org.springframework.security.web.SecurityFilterChain;

@Configuration(proxyBeanMethods = false)
class PortalLoginSecurityConfig {

    @Bean
    SecurityFilterChain portalSecurityFilterChain(
            HttpSecurity http,
            ClientRegistrationRepository clients) throws Exception {

        DefaultOAuth2AuthorizationRequestResolver resolver =
                new DefaultOAuth2AuthorizationRequestResolver(
                        clients, "/oauth2/authorization");

        resolver.setAuthorizationRequestCustomizer(
                OAuth2AuthorizationRequestCustomizers.withPkce());

        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/public/**").permitAll()
                .anyRequest().authenticated())
            .oauth2Login(oauth -> oauth
                .authorizationEndpoint(endpoint ->
                    endpoint.authorizationRequestResolver(resolver)));

        return http.build();
    }
}
```

`OAuth2AuthorizationRequestCustomizers.withPkce()` adds `code_challenge` and `code_challenge_method` to the authorization request and stores `code_verifier` in the **authorization request attributes** for token exchange. That verifier will not stay safe if the application customizes the repository and drops those attributes.

By default, Spring Security provides `HttpSessionOAuth2AuthorizationRequestRepository` to persist `OAuth2AuthorizationRequest` across the redirect and callback, enabling lookup of the original request and `state` validation. In multi-tab/multi-pod systems or distributed session stores, test concurrent flows instead of assuming a single request cache handles every case out of the box.

### 9.2. When Do You Need a Custom `AuthorizationRequestRepository`?

Customize only when there is a clear requirement such as parallel tabs, special cookie policies, or a distributed session store. The core contract includes:

```java
void saveAuthorizationRequest(
        OAuth2AuthorizationRequest request,
        HttpServletRequest httpRequest,
        HttpServletResponse httpResponse);

OAuth2AuthorizationRequest loadAuthorizationRequest(
        HttpServletRequest httpRequest);

OAuth2AuthorizationRequest removeAuthorizationRequest(
        HttpServletRequest httpRequest,
        HttpServletResponse httpResponse);
```

These are **abbreviated learning signatures**; consult the interface and nullability annotations for your exact version. A custom implementation must preserve **intact `state`, redirect URI, nonce, PKCE verifier, and issuer/provider bindings**, TTLs, and consumption rules. Never switch to an unsigned cookie holding the verifier; if cookies are used, encrypt/authenticate them with secure cookie policies preventing replay and tampering.

Never write a `@GetMapping("/login/oauth2/code/portal")` controller to "read the code" when `oauth2Login()` is configured: callbacks are handled by `OAuth2LoginAuthenticationFilter`. A homemade handler easily skips `state` matching, token exchange, or ID Token validation.

## 10. BFF vs. SPA: Where Do Codes and Tokens Live?

| Architecture | Where Callback/Code Is Handled | Where `code_verifier` Lives | Where Tokens Are Received/Held | Security Notes |
|---|---|---|---|---|
| **Confidential web client / Backend for Frontend (BFF)** | Client's Spring Boot server | Server-side session / authorization request store | Backend / authorized-client store; browser gets session cookie | Limits JS token access; still protect CSRF/cookies/sessions |
| **Pure browser public SPA** | JS on the SPA origin | Ephemeral browser transaction state | Browser receives access token from token endpoint; store per threat model | No reliable client secret; requires PKCE, XSS prevention, and leak controls |
| **Native public app** | Redirects via OS browser to app-link/loopback | Temporarily stored in the app | App uses tokens per platform | Per RFC 8252, use external user-agent, registered callback, and PKCE |

When architecturally feasible, a **BFF** shrinks the surface where JavaScript can read tokens. Still, you must guard cookies, CSRF, session fixation, and backend endpoints; a BFF does not eliminate all risks.

For a public SPA client, also:

1. Use a vetted OAuth2/OIDC library supporting `state`, PKCE S256, `nonce`, discovery, issuer validation, and callback cleanup.
2. Restrict third-party scripts and XSS via CSP, escaping, and dependency reviews; never treat long-lived tokens in `localStorage` as a "safe default".
3. Ensure token endpoint CORS allows only required origins per AS config; CORS **never replaces** redirect URI, `state`/PKCE, or Authorization Server policy controls.
4. Use token storage and renewal strategies suited to standards, browser constraints, and risk policies; shorten token lifetimes where appropriate.
5. Never assume calling `replaceState` to clear query strings stops malicious scripts that executed before that line.

## 11. Security Testing: State, Callbacks, Codes, and PKCE

A thorough test suite needs **Client, Authorization Server, browser/session, and token endpoint** coverage—not just a unit test of a state generator. Use test accounts/credentials in test environments and never write real codes/verifiers/tokens into test logs.

| Scenario | How to Test | Expected Outcome |
|---|---|---|
| Standard happy path | Authorization Code + PKCE S256 login with valid `state` | Client checks `state`, exchanges code once, valid tokens; final URL clean |
| Missing `state` in callback | Strip `state` parameter | Client rejects; does not call token endpoint |
| Tampered `state` | Modify one character of `state` | Client rejects; creates no login session |
| `state` from another browser | Copy callback URL into another browser without an open flow | Client rejects due to missing bound transaction |
| Replayed callback | Reopen the same callback URL after processing | Creates no new session and does not re-exchange code |
| Multiple tabs | Open two concurrent login requests with different states | Pairs match cleanly or fail explicitly without mixing state/verifiers |
| Missing PKCE | Omit `code_challenge` when `RegisteredClient` requires it | Authorization Server rejects authorization request |
| Wrong `code_verifier` | Exchange code with a different verifier | Token endpoint rejects, typically `invalid_grant` |
| Redeeming code twice | Resend already-used code to token endpoint | Second attempt rejected; review revocation policy on replay |
| Expired code | Wait past code TTL before exchanging | Token endpoint rejects |
| Altered redirect URI | Add trailing `/`, change scheme/host/port | AS rejects bad URI; never redirects code externally |
| Wrong `redirect_uri` at exchange | Supply callback differing from URI used at code issuance | Token endpoint rejects |
| Open redirect attempt | Send `next=https://evil.test` or lookalike domain | Never uses arbitrary URI to forward codes |
| Multi-issuer mix-up | Try using callback from issuer A for transaction B | Client rejects or separates callbacks per AS |
| `Referer` leak | Callback includes external image/link in test env | Never sends full sensitive URL to external origin; ideally zero external assets |
| Browser history | Complete login and inspect URL/history | Final page has no code/state; processed callback cannot be replayed |
| Access logs | Inspect proxy/APM logs using dummy callback code | No raw `code`/`state`/token/verifier logged |
| Error from AS | `error=access_denied&state=...` with valid/invalid state | Valid: show safe error; invalid: reject callback |
| Lost session | Clear cookies then hit callback | Does not exchange code; guides user to restart flow |
| Reverse proxy issue | Request via public HTTPS host, callback routed to another pod | URI, cookies, session, and `state` stay consistent |
| Wrong OIDC `nonce` | ID Token carries nonce differing from transaction | RP rejects ID Token |
| SPA script reading URL | Monitor network and third-party loads on callback | URL stripped early; no sensitive data exfiltrated |

### 11.1. Three Priority Integration Tests

**Test A — Callback CSRF:** Have browser 1 generate state `S1`, browser 2 generate state `S2`. Submit browser 2's callback carrying its code and state `S2` into browser 1. The Client must **not** bind browser 2's account to browser 1; never skip `state` checks just because the code happens to be valid on the server.

**Test B — PKCE Mismatch:** Create an authorization request with `code_challenge=BASE64URL(SHA256(V1))`, obtain a code, and exchange it using `code_verifier=V2`. It must be rejected; attempting to redeem an already-succeeded code must fail even with the right `V1`.

**Test C — Browser Code Leakage:** Inspect a callback carrying `code` and `state` via a browser/test proxy. Confirm no requests go to third-party origins while that URL is present, reverse proxy/observability logs are redacted, and the client moves the browser to a clean URL once handled.

### 11.2. Common Spring Integration Errors

| Symptom | Causes to Check | Fix |
|---|---|---|
| `invalid_state` or `authorization_request_not_found` | Lost cookie/session, multi-tab, session store/TTL, callback hitting wrong instance | Inspect `HttpSessionOAuth2AuthorizationRequestRepository`, `SameSite`/HTTPS, and session routing |
| `invalid_redirect_uri` | `{baseUrl}` mismatch due to proxy, trailing slash, http/https, or registration ID | Compare exact callback in request, `RegisteredClient`, and `ClientRegistration` |
| `invalid_grant` on code exchange | Wrong/lost verifier, expired/used code, redirect URI or client mismatch | Check transaction binding, PKCE S256, code TTL, and single-use semantics |
| `invalid_client` | Wrong confidential client secret or mismatched auth method | Check client authentication; keep secrets out of logs |
| PKCE missing on authorization request | Confidential client did not enable PKCE on resolver or config overridden | Enable `withPkce()` properly; inspect code challenge outside browser |
| Browser still shows `code` after login | Callback renders content page / SPA has not stripped URL | Use server-side callback filter + redirect; or clean up early in SPA |
| OAuth2 callback returns 404/405 | Custom handler conflicts with filter, mismatched callback path/HTTP method | Use default callback or align `redirectionEndpoint` and redirect URI |
| Callback does not return to original page | Lost saved request/return path or buggy custom success handler | Persist validated internal return path; avoid open redirects |
| Valid code, OIDC login fails | ID Token `iss`/`aud`/`nonce` mismatch | Check discovery, issuer, and OIDC transaction |
| Works on one pod, fails on multiple pods | Authorization service or session store lives in RAM only | Use shared persistence/sessions and atomic consumption |

## 12. Operational Checklist Before Launching Authorization Code Flow

- [ ] Every authorization request has a random, browser/transaction-bound, TTL-limited, single-use `state`.
- [ ] Client puts no sensitive data in `state` and never trusts a callback `state` lacking a server-side transaction.
- [ ] PKCE `S256` is enabled and verified at both authorization and token endpoints; `code_verifier` never appears in URLs or logs.
- [ ] Authorization Server performs **exact redirect URI** matching with no wildcards or open redirects.
- [ ] Authorization codes are short-lived, bound to client/redirect/PKCE, single-use, and replay-resistant.
- [ ] Client reads issuer/token endpoints from trusted configuration and applies mix-up defenses when using multiple ASs.
- [ ] Callback loads no third-party scripts/analytics while URL carries `code`/`state`; sets `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
- [ ] Post-callback destination URL is clean; browser history and reverse proxy logs do not retain sensitive values beyond policy.
- [ ] Confidential clients keep secrets/tokens server-side; public SPAs do not pretend to hold secrets and enforce XSS/PKCE/storage policies.
- [ ] Session cookies set `Secure`, `HttpOnly`, and appropriate `SameSite`; CSRF protections remain intact for state-changing forms/endpoints.
- [ ] Multi-tab, multi-pod, expired sessions, replayed callbacks, mix-up, and PKCE mismatch all have integration tests.
- [ ] Raw authorization codes, access tokens, refresh tokens, ID Tokens, client secrets, verifiers, and full callback URLs are never written to logs or tickets.
- [ ] TLS is enforced, `invalid_grant`/`invalid_state`/`invalid_redirect_uri` error rates are monitored, and a data-leakage response procedure exists.

**Self-Check Questions**

1. Why cannot `state` and `code_verifier` fully replace each other?
2. When a callback carries a valid `code` but `state` does not match the session, how should the Client respond?
3. Why is `code_challenge` sent to the AS while `code_verifier` appears only during code exchange?
4. Are redirect URIs `https://portal.example.vn/callback` and `https://portal.example.vn/callback/` equivalent during matching?
5. With PKCE enabled, is it safe to embed Google Analytics directly on the callback page while the URL still contains `code`?
6. If a Client supports multiple issuers, why must the selected issuer be saved with the transaction?
7. Which steps does Spring Security's `HttpSessionOAuth2AuthorizationRequestRepository` hold data for? What happens if the session is lost?
8. Why cannot an already-used authorization code be exchanged again even if the same client sends the right verifier?
