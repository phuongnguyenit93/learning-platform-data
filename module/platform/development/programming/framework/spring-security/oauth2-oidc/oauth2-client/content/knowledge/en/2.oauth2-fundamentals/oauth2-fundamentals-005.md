# 2.5. Authorization Code Grant and Code Exchange Steps

## 1. What Problem Does the Authorization Code Grant Solve?

Suppose a web application written in Spring Boot needs to let users log in through an Identity Provider (IdP) and then call an API on the user's behalf. The application should not ask users to enter their IdP password into a form managed by the application itself. Instead, the browser redirects the user to the IdP, the IdP authenticates the user, and redirects them back to the application with a short-lived **authorization code**. The application uses this code to request tokens over a direct connection to the authorization server.

This approach is OAuth 2.0's **Authorization Code Grant**. The key point is separating two channels:

- **Front channel:** browser redirection flow; carries the authorization request and subsequently the authorization code.
- **Back channel:** HTTP connection from the OAuth client to the Authorization Server's token endpoint; used to exchange the code for tokens. In a typical web server architecture, this connection does not pass through browser JavaScript.

OAuth 2.0 primarily solves **resource access authorization**. When adding OpenID Connect (OIDC), the application uses the same Authorization Code Flow for **login/identity authentication**; the token response additionally includes an ID Token and identity verification rules. The two concepts are related but not synonymous: the access token serves APIs, whereas the ID Token describes the authentication event for the client.

The example throughout this lesson uses:

- Spring Boot application: `https://app.example.com`
- Authorization Server / OIDC Provider: `https://id.example.com`
- Client registration ID in Spring Security: `demo`
- Registered callback: `https://app.example.com/login/oauth2/code/demo`

These domain names are illustrative. In real deployments, replace them with the endpoints and client registration issued by your provider.

## 2. Roles and Data Appearing in the Flow

| Component | Role |
|---|---|
| **Resource Owner** | User who grants the application access to the requested scope of data. |
| **User Agent** | Browser that navigates to the IdP's login/consent page and returns to the application. |
| **OAuth Client / Relying Party** | Spring Boot application that builds the authorization request, receives the code, exchanges it for tokens, and manages the login session. |
| **Authorization Server (AS) / OpenID Provider (OP)** | Authenticates the user, decides on permission approval, issues the code and tokens; if OIDC is supported, issues the ID Token. |
| **Resource Server** | API that validates the access token and returns resources according to granted permissions. |

Important values to distinguish:

| Value | Where Is It Generated? | What Is It Used For? |
|---|---|---|
| `client_id` | Client registration config at the AS | Identifies the application requesting authorization. Not a secret. |
| `client_secret` | Issued by the AS for a *confidential client*, if required by the client authentication method | Proves the client's identity at the token endpoint; kept server-side only. |
| `redirect_uri` | Sent by the client in the authorization request; pre-registered with the AS | Address to which the AS returns the browser after processing the request. |
| `scope` | Requested by the client; AS decides the granted scope | E.g., `openid profile email` for OIDC or system API scopes. |
| `state` | Randomly generated by the client per request | Matches the callback with the initial request; helps prevent CSRF and injected responses. |
| `code` | Issued by the AS after the authorization request is approved | Short-lived, single-use value exchanged for tokens. |
| `code_verifier` | Randomly generated by the client when using PKCE | Temporary secret proving the party exchanging the code is the one that initiated the request. |
| `code_challenge` | Derived from `code_verifier` | Sent to the authorization endpoint and bound to the code by the AS. |
| `nonce` | Generated by the client when using an OIDC nonce | Binds the ID Token to the corresponding authentication request, mitigating replay. |
| `access_token` | Issued by the AS at the token endpoint | Allows calling APIs within the granted scopes/permissions and validity period. |
| `id_token` | Issued by the OpenID Provider in OIDC | Informs the client about the authentication event and logged-in subject. |
| `refresh_token` | May be issued by the AS depending on policy | Requests a new access token under conditions defined by the AS. |

**An authorization code is not an access token.** The client does not use `code` to call APIs, does not read the code as proof of login, and does not hand the code over to another client.

## 3. Overview of the Authorization Code Flow

~~~mermaid
sequenceDiagram
    autonumber
    actor U as User / Browser
    participant C as Spring Security OAuth Client
    participant AS as Authorization Server / OIDC Provider
    participant API as Resource Server

    U->>C: GET /private
    C-->>U: 302 to /oauth2/authorization/demo
    U->>C: GET /oauth2/authorization/demo
    C-->>U: 302 to authorization endpoint (state, PKCE, scope...)
    U->>AS: GET /authorize?response_type=code&...
    AS->>U: Login and/or access consent
    AS-->>U: 302 redirect_uri?code=...&state=...
    U->>C: GET /login/oauth2/code/demo?code=...&state=...
    Note over C: Validate state and stored authorization request
    C->>AS: POST /token (code, redirect_uri, client auth, code_verifier)
    AS-->>C: access_token (+ id_token, refresh_token if applicable)
    Note over C: Validate ID Token if OIDC
    C-->>U: Create login session; redirect to requested page
    C->>API: Authorization: Bearer access_token
    API-->>C: Data per granted permissions
    C-->>U: Application content
~~~

The diagram illustrates a Spring Boot web application whose backend holds tokens. When the user already has a session at the IdP, the password entry step may be skipped; when required consent has not yet been granted, the IdP may show a consent screen. Those screens do not change how the authorization code is exchanged.

### Step 1 — Client Initiates the Authorization Request

The user opens a path requiring login. Spring Security determines that authentication via OAuth 2.0/OIDC is needed and initiates an authorization request.

Example request sent to the AS after URL-encoding parameters:

~~~http
GET /authorize?response_type=code
    &client_id=spring-web-client
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fdemo
    &scope=openid%20profile%20email
    &state=RANDOM_STATE
    &code_challenge=BASE64URL_SHA256_OF_VERIFIER
    &code_challenge_method=S256
    &nonce=RANDOM_NONCE HTTP/1.1
Host: id.example.com
~~~

This is wrapped across multiple lines for readability; in practice, the request URL is a single valid line.

Meaning of the parameters:

- `response_type=code` informs the server that the client wants to receive an **authorization code**, not requesting an access token directly in the callback URL.
- `client_id` identifies the application registered at the IdP.
- `redirect_uri` must match a URI accepted by the AS for that client; this is the address receiving the callback.
- `scope` specifies the requested permissions. The presence of `openid` shifts the request into an OIDC context.
- `state` is a random value stored with the initial request for comparison on callback.
- `code_challenge` and `code_challenge_method=S256` form the first part of the PKCE mechanism.
- `nonce` is used when the client requests and validates a nonce in the ID Token.

At this step, the client **does not yet have an authorization code or access token**. At the same time, the client must persist initial request details (such as `state`, `redirect_uri`, PKCE data, and required parameters) for use upon callback.

### Step 2 — Authorization Server Authenticates and Obtains Consent

The browser arrives at the authorization endpoint managed by the IdP. Here, the AS may perform the following:

1. Validate `client_id`, `redirect_uri`, `response_type`, `scope`, and supported parameters.
2. Authenticate the user or reuse an existing SSO session.
3. Prompt for consent if policy requires user approval of permissions.
4. If the request is valid and approved, issue a code bound to the client, redirect URI, and associated constraints (including PKCE if requested).

Passwords, MFA, or user login methods happen at the IdP. The Spring Boot application never receives the user's IdP password during this process.

### Step 3 — Browser Receives Callback Containing `code` and `state`

After approval, the AS returns an HTTP redirect:

~~~http
HTTP/1.1 302 Found
Location: https://app.example.com/login/oauth2/code/demo?code=AUTH_CODE_ABC&state=RANDOM_STATE
~~~

The browser then calls the callback on the application:

~~~http
GET /login/oauth2/code/demo?code=AUTH_CODE_ABC&state=RANDOM_STATE HTTP/1.1
Host: app.example.com
~~~

The application must match `state` against the value saved for that specific initiated request. If `state` does not match, the initial request data is missing, or the callback arrives in the wrong context, the client must abort the flow and not use the code to call the token endpoint.

If the user denies access, the AS typically redirects back to the callback with an error parameter instead of `code`, for example:

~~~http
HTTP/1.1 302 Found
Location: https://app.example.com/login/oauth2/code/demo?error=access_denied&state=RANDOM_STATE
~~~

Error paths are a normal part of the protocol and must be handled into an appropriate user experience, avoiding exposing tokens, internal codes, or stack traces to the user.

### Step 4 — Backend Exchanges Code for Tokens at the Token Endpoint

After verifying the callback, the OAuth client sends an HTTP POST directly to the token endpoint. For a *confidential client* using `client_secret_basic`, the request looks like:

~~~http
POST /token HTTP/1.1
Host: id.example.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic BASE64_CLIENT_ID_COLON_CLIENT_SECRET

grant_type=authorization_code&code=AUTH_CODE_ABC&redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fdemo&code_verifier=ORIGINAL_HIGH_ENTROPY_VERIFIER
~~~

Field explanations:

- `grant_type=authorization_code` specifies the grant type being used.
- `code` is the code just received from the callback.
- `redirect_uri` must be consistent with the value used in the authorization request when the protocol requires resending it; a mismatch invalidates the request.
- `Authorization: Basic ...` illustrates how the client authenticates to the AS. The Basic part contains Base64-encoded client credentials, **not encryption**; therefore TLS must be used and this value must never be logged.
- `code_verifier` is the original PKCE string, sent only at the token endpoint. The AS recomputes the challenge and compares it with the challenge bound to the code.

The exact parameter set depends on client registration. A *public client* without a trustworthy secret does not send `client_secret_basic`; it typically identifies `client_id` per AS rules and **must rely on PKCE** to bind the code. Some clients use `private_key_jwt` or another authentication method instead of a shared secret.

The AS performs core validations: whether the code exists, is still valid, has not been used, belongs to the right client, matches the redirect URI, has a valid verifier if PKCE was used, and whether the client authenticated properly per its registered method. If any check fails, the AS returns an error and issues no tokens.

### Step 5 — Client Receives the Token Response

A successful OIDC response may look like:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Pragma: no-cache

{
  "access_token": "ACCESS_TOKEN_VALUE",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "openid profile email",
  "id_token": "SIGNED_ID_TOKEN_VALUE",
  "refresh_token": "OPTIONAL_REFRESH_TOKEN_VALUE"
}
~~~

`access_token` is for calling APIs; `id_token` appears when this is an appropriate OIDC response; `refresh_token` depends on configuration, scopes, policies, and the AS's decision, so **never assume it is always present**. The JSON above only illustrates common fields; actual values, lifetimes, and token formats are determined by the AS.

With OIDC, the client must validate the ID Token according to protocol requirements, including signature or corresponding verification mechanism, issuer (`iss`), audience (`aud`), validity period (`exp`), and `nonce` when a nonce request was used. The client also handles other constraints such as `azp` or signing algorithms if required by the scenario. Spring Security provides components that handle token processing and OIDC validation in the standard login flow.

**Merely having a token does not mean having a logged-in browser session.** The application still needs to establish an authentication/session context in a way that fits its architecture. In a web app using `oauth2Login()`, Spring Security can create an `Authentication` and store it in the `SecurityContext` and HTTP session.

### Step 6 — Calling APIs with the Access Token

When needing to access a resource server, the backend uses the access token:

~~~http
GET /v1/profile HTTP/1.1
Host: api.example.com
Authorization: Bearer ACCESS_TOKEN_VALUE
~~~

The resource server validates the access token per the system's mechanism (e.g., JWT verification or introspection), then enforces audience, scopes, and authorization policies. **A resource server does not accept an ID Token in place of an access token.**

In OIDC, the client can obtain identity information from the ID Token and/or UserInfo Endpoint according to provider rules. Do not treat arbitrary claims in any token as suitable proof for authorizing API calls: rely on tokens and policies intended for the respective resource server.

## 4. Understanding PKCE, `state`, and `nonce` Correctly

These three mechanisms often appear together, yet protect different links in the chain.

### 4.1. PKCE Binds the Authorization Code to the Initiator

**Proof Key for Code Exchange (PKCE)** reduces the risk of someone intercepting an authorization code and exchanging it for tokens themselves. The client randomly generates a strong `code_verifier` and derives:

~~~text
code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))
code_challenge_method = S256
~~~

The client sends `code_challenge` to the authorization endpoint, while keeping `code_verifier` to itself until code exchange. The AS stores the binding between the challenge and the code; upon receiving the token request, the AS compares the hash of the verifier. An attacker holding only the code without a valid verifier cannot exchange it for tokens.

Binding flow example:

~~~text
Client:
  code_verifier  = secret random string for one request
  code_challenge = BASE64URL(SHA256(code_verifier))

Authorization request -> AS:
  code_challenge + code_challenge_method=S256

Callback <- AS:
  code

Token request -> AS:
  code + code_verifier

AS:
  BASE64URL(SHA256(code_verifier)) == stored code_challenge?
  True  -> may proceed with remaining checks and issue tokens
  False -> reject code exchange
~~~

Prefer `S256`; never use a fixed verifier or reuse one verifier across all requests. The client must associate the verifier with the exact authorization transaction and protect it from leaking. PKCE is especially essential for public clients and is also a useful defense layer for confidential clients. Client secret authentication and PKCE serve different purposes; both can be used together.

### 4.2. `state` Links the Callback to the Initial Session/Request

`state` is an unpredictable value that the client generates and stores before redirecting the user to the IdP. When the callback returns, the client compares the received value with the corresponding stored value.

For example: an attacker tries to send a link `/login/oauth2/code/demo?code=ATTACKER_CODE&state=...` to a victim's browser. Checking `state` enables the client to reject a code not bound to a request initiated by the victim's own browser/session. This mitigates CSRF and login flow confusion.

`state` must be generated uniquely per request and stored/correlated securely. Never replace it with a fixed string. **PKCE does not fully replace the role of `state` in all scenarios**, and `state` does not prove that the token endpoint caller holds the verifier like PKCE does.

### 4.3. `nonce` Binds the ID Token to the OIDC Request

In OIDC, the client can send a `nonce` when initiating the request. If a nonce is present in the request, the OP must bind the corresponding nonce into the ID Token per OIDC rules, and the client must validate the value in the ID Token. This helps detect an ID Token that is replayed or bound to a different authentication request.

`nonce` serves **ID Token** verification, whereas `state` serves **authorization response** correlation and PKCE serves **token exchange**. These functions should not be swapped.

| Mechanism | Value Sent in Authorization Request | Value Matched Later | Direct Goal |
|---|---|---|---|
| `state` | `state` | `state` in callback | Callback belongs to the exact initial request. |
| **PKCE** | `code_challenge` and `S256` | `code_verifier` in token request | Party exchanging the code holds the verifier used at initiation. |
| **OIDC nonce** | `nonce` if used | `nonce` claim in ID Token | ID Token belongs to the exact OIDC request. |

## 5. Constraints to Remember When Exchanging an Authorization Code

A valid code is not a "use-as-many-times-as-you-want ticket." The Authorization Server must enforce the following constraints:

1. **Short lifetime:** authorization codes expire quickly; expired codes cannot be exchanged for tokens.
2. **Single-use:** after a successful exchange, a code cannot be exchanged again. If an already-used code is resubmitted, the AS rejects it; handling of related issued tokens follows the AS's security policy.
3. **Bound to client:** a code issued to one client cannot be exchanged by another client.
4. **Redirect URI constraint:** the token request must satisfy redirect URI matching rules against the authorization request/registration.
5. **PKCE constraint:** if the code was issued via a PKCE request, the verifier must match successfully.
6. **Secure transport:** authorization, callback, and token exchange must comply with the deployment environment's TLS requirements; HTTP exceptions on loopback/localhost for development should only follow provider-allowed policy.
7. **Clear error handling:** client authentication failures, expired codes, reused codes, or wrong verifiers must abort login session creation.

In particular, **because the code travels in the callback URL**, it can leak via browser history, proxy logs, or monitoring tools if configured carelessly. Therefore PKCE, short lifetimes, single-use enforcement, HTTPS, and policies against logging secrets all matter. Do not place codes, tokens, or client secrets in redirect URLs outside the necessary flow.

## 6. Authorization Code Grant in Spring Security OAuth 2.0 Client

In Servlet applications based on Spring Boot and Spring Security, `oauth2Login()` provides the OAuth 2.0/OIDC login flow. Developers typically configure client registrations and protected endpoints; Spring Security handles authorization requests, callbacks, code exchange, and establishing the login context.

### 6.1. Declaring Dependencies

Gradle example in a Spring Boot project:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.boot:spring-boot-starter-oauth2-client'
}
~~~

This example uses a Servlet web application; with WebFlux, configuration and processing components follow the corresponding reactive model.

### 6.2. Declaring Client Registration and Provider

Example `application.yml`:

~~~yaml
spring:
  security:
    oauth2:
      client:
        registration:
          demo:
            provider: demo-provider
            client-id: ${OIDC_CLIENT_ID}
            client-secret: ${OIDC_CLIENT_SECRET}
            client-authentication-method: client_secret_basic
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope:
              - openid
              - profile
              - email
        provider:
          demo-provider:
            issuer-uri: https://id.example.com
~~~

You must pre-register the client `spring-web-client` (or the actual client ID) at the IdP and configure the corresponding callback. The example uses OIDC discovery via `issuer-uri`; the actual provider must serve valid discovery metadata at the declared issuer. Environment variables `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` hold the provisioned values. Never put real secrets into source code or public examples.

Field meanings:

- `registration.demo` identifies the configuration; `demo` also appears in Spring Security's default URLs.
- `provider: demo-provider` links the registration to the provider details.
- `authorization-grant-type: authorization_code` selects the Authorization Code Grant.
- `client-authentication-method: client_secret_basic` specifies how the client authenticates at the token endpoint in this confidential client example.
- `redirect-uri` points to `oauth2Login()`'s default callback and uses Spring-supported placeholders.
- `scope: openid` makes this an OIDC login; `profile` and `email` request additional claims supported by the provider, without guaranteeing every claim is always present.
- `issuer-uri` enables discovery of authorization, token, UserInfo, JWKS endpoints, and related metadata when the provider supports the standard.

For the real application at `https://app.example.com`, the callback value after expanding placeholders is:

~~~text
https://app.example.com/login/oauth2/code/demo
~~~

This URI must be allowed in the client configuration at the IdP. When running locally on port 8080, the callback is typically `http://localhost:8080/login/oauth2/code/demo`; only use HTTP in development when permitted by the provider.

### 6.3. Enabling OAuth 2.0/OIDC Login

A common Spring Security configuration:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/", "/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .oauth2Login(Customizer.withDefaults());

        return http.build();
    }
}
~~~

When an unauthenticated user accesses `/private`, Spring Security sends them into the login flow. Login can also be started directly via:

~~~http
GET /oauth2/authorization/demo HTTP/1.1
Host: app.example.com
~~~

This path is Spring Security's default **authorization request initiation endpoint**, not an endpoint on the IdP. Spring builds a valid request and redirects the browser to the AS.

The default callback is:

~~~text
/login/oauth2/code/{registrationId}
~~~

When `registrationId = demo`, the callback becomes `/login/oauth2/code/demo`. In the standard flow, developers **do not need to write a custom controller** to read `code` and POST to the token endpoint.

If you want the browser redirected to a specific page after login, use an appropriate success handler or saved request mechanism; do not replace the security callback with an ad-hoc endpoint manually reading `code`.

### 6.4. What Does Spring Security Handle?

| Component / Concept | Role in the Authorization Code Flow |
|---|---|
| `ClientRegistration` / `ClientRegistrationRepository` | Supplies `client_id`, grant type, scopes, redirect URI, and provider configuration. |
| `OAuth2AuthorizationRequestRedirectFilter` | Receives initiation requests, builds authorization requests, persists correlation state, and redirects to the AS. |
| `AuthorizationRequestRepository` | Stores the authorization request between redirecting to the IdP and receiving the callback; in web apps, typically tied to the HTTP session. |
| `OAuth2LoginAuthenticationFilter` | Processes the default callback and uses the stored authorization request to execute the authentication workflow. |
| Token response client / authentication provider components | Sends the authorization code along with required parameters to the token endpoint, receives tokens, and processes the result. |
| Spring Security OIDC support | Processes the ID Token, validates OIDC claims, and creates the corresponding principal when the `openid` scope is present. |
| `OAuth2AuthorizedClient` and its storage | Represents the association between a client registration, principal, and issued tokens for subsequent API requests. |
| `SecurityContext` / login session | Maintains authenticated user state in the web application according to the configured session strategy. |

Note: exact API names and detailed configuration options may vary across Spring Security version lines; the Authorization Code Grant protocol workflow remains based on the same steps.

### 6.5. Example: Reading the Logged-In User's Identity

In an OIDC scenario, a controller can receive the principal created by Spring Security:

~~~java
import java.util.Map;
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.core.oidc.user.OidcUser;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ProfileController {

    @GetMapping("/me")
    public Map<String, String> me(@AuthenticationPrincipal OidcUser user) {
        return Map.of("subject", user.getSubject());
    }
}
~~~

In this example, `subject` comes from OIDC information that went through the authentication pipeline. Avoid displaying access tokens, refresh tokens, or ID Tokens on a page merely to verify login.

If the application only uses plain OAuth 2.0 without requesting `openid`, the principal and user-info loading mechanism may differ; do not blindly cast to `OidcUser`.

### 6.6. PKCE in Spring Security Configuration

For public clients, `client-secret` is not a secret that can be kept safe, and `client-authentication-method` is typically `none`; PKCE is an essential component to address. Modern Spring Security versions support PKCE when generating authorization requests, including public client scenarios. For confidential clients, PKCE can be explicitly enabled to add further protection to the code exchange.

An illustrative configuration for the Servlet flow attaches a PKCE customizer to the resolver:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web.DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestCustomizers;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class PkceSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            ClientRegistrationRepository registrations) throws Exception {

        var resolver = new DefaultOAuth2AuthorizationRequestResolver(
                registrations, "/oauth2/authorization");
        resolver.setAuthorizationRequestCustomizer(
                OAuth2AuthorizationRequestCustomizers.withPkce());

        http
            .authorizeHttpRequests(authorize -> authorize
                .anyRequest().authenticated()
            )
            .oauth2Login(oauth -> oauth
                .authorizationEndpoint(endpoint -> endpoint
                    .authorizationRequestResolver(resolver)));

        return http.build();
    }
}
~~~

This is an **alternative** to the `SecurityFilterChain` bean in section 6.3—do not add both identical beans to the same project. Check the API of your Spring Security version and the provider's PKCE requirements. The resolver must persist the required data so that after the callback, the token request sends the matching `code_verifier`. Never generate a new verifier at code-exchange time.

### 6.7. Login Session and API Access Token Are Two Separate States

After OAuth login, users can continue accessing protected pages via the application's session cookie. When the backend needs to call an API on the user's behalf, it uses the corresponding `OAuth2AuthorizedClient` to retrieve the access token. The session cookie is **not** an access token for the resource server.

Therefore, distinguish:

- `oauth2Login()` focuses on authenticating the user with the web app and establishing the principal.
- `oauth2Client()`, `OAuth2AuthorizedClientManager`, and authorized-client mechanisms support acquiring, managing, and using tokens for APIs. They can be combined with the login flow, yet do not mean triggering a new login request on every API call.
- The Resource Server independently validates the access token. A client cannot use "already logged in successfully" to bypass token checks at the API.

This is especially important in applications that both serve a web UI and call multiple downstream APIs.

## 7. Two Common Variants

### 7.1. Confidential Client: Spring Boot Backend Holds the Secret

For applications with a trusted backend, the client is typically registered as confidential. The server holds the secret in secure configuration or a secret management system; the browser only participates in redirects. During token exchange, the backend authenticates to the AS using the registered method.

Corresponding flow:

~~~text
Browser ── redirect ──> IdP
Browser <── code via redirect ── IdP
Browser ── callback(code, state) ──> Spring Boot
Spring Boot ── POST /token + client auth + PKCE ──> IdP
Spring Boot <── tokens ── IdP
~~~

Secrets must not appear in JavaScript, HTML, responses sent to the browser, URLs, or logs.

### 7.2. Public Client: No Durable Secret

Native applications or SPAs running in an environment unable to protect a client secret are treated as public clients. They can still use the Authorization Code Grant, but must apply appropriate PKCE and platform-specific protections.

Example main fields of the token request could be:

~~~http
POST /token HTTP/1.1
Host: id.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&client_id=public-client&code=AUTH_CODE_ABC&redirect_uri=REGISTERED_REDIRECT_URI&code_verifier=ORIGINAL_VERIFIER
~~~

Do not copy a server's `client-secret` configuration into an SPA. Token storage, callback handling, CORS, and session management for public clients require dedicated design; the Spring Boot server examples in this lesson represent the web backend case.

## 8. Plain OAuth 2.0 vs. OIDC Code Flow

The same redirect and token exchange pattern can serve two goals:

| Aspect | OAuth 2.0 Authorization Code Grant | OIDC Authorization Code Flow |
|---|---|---|
| Primary purpose | Grant permission to access resources | Authenticate user identity, while optionally requesting API permissions |
| Typical scopes | Resource/API-dependent, e.g., `read:orders` | Includes `openid`, optionally `profile`, `email` |
| Token endpoint result | Typically has an access token; refresh token per policy | Has access token and ID Token; refresh token per policy |
| Identity proof for client | OAuth 2.0 does not itself define an ID Token | ID Token has claims, signature, and validation rules per OIDC |
| Principal after Spring Security login | Depends on provider and user info processing config | Typically `OidcUser` in the `oauth2Login()` flow |

For example: an application wanting to fetch an order list needs an access token permitted to read orders; an ID Token does not replace that API scope. Conversely, merely receiving an access token from an OAuth provider does not automatically guarantee the client has a standard OIDC login process. If the goal is federated identity login, configure an OIDC provider and the `openid` scope.

## 9. Common Errors and How to Isolate Them

| Symptom | Possible Cause | Where to Check |
|---|---|---|
| IdP reports `invalid_redirect_uri` or rejects authorization request | Callback not registered, or mismatched scheme/host/port/path | Client registration at IdP and `redirect-uri` in Spring |
| Callback returns but reports `invalid_state` or authorization request not found | Lost session/cookie, mismatched state, overlapping requests, misconfigured proxy/callback | Session, cookies, `SameSite` config, actual URL, and authorization request repository |
| Token endpoint returns `invalid_grant` | Code expired, already used, belongs to wrong client/redirect URI, or wrong PKCE verifier | Sequence of callback → token request, processing time, code binding, and verifier |
| Token endpoint returns `invalid_client` | Wrong Client ID/secret or wrong client authentication method | Registration in IdP, `client-authentication-method`, secret |
| Token endpoint reports error related to `code_verifier` | Missing verifier, regenerated verifier, or challenge and verifier do not match | Where PKCE is generated and where the original request is stored |
| OAuth login succeeds but no ID Token is received | Request is not OIDC, missing `openid`, or provider does not support OIDC | Scopes, provider metadata, token response |
| ID Token is rejected | Wrong issuer/audience, signature, validity time, or nonce | Issuer config, system clock, JWKS, and claims |
| Token obtained but API returns `403 Forbidden` | Token lacks scope/permissions or API enforces a deny policy | Granted scopes, audience, and resource server policies |
| API returns `401 Unauthorized` | Token invalid, expired, wrong token type sent, or missing Bearer header | Authorization header, validity and lifetime of access token |
| Behind reverse proxy, callback has wrong `http`/`https` | App sees internal scheme/host, forwarded headers not trusted/configured | Proxy, forwarded headers config, and `{baseUrl}` when Spring builds redirect URI |

OAuth error codes must be read alongside actual response context. For instance, `invalid_grant` can stem from several different causes; do not immediately assume only code expiration.

### Observing the Flow During Development

You can diagnose along the event sequence:

1. Confirm the browser visits `/oauth2/authorization/demo` and is redirected to the authorization endpoint.
2. Check that the request sent to the AS has `response_type=code`, the right `client_id`, `redirect_uri`, scopes, and PKCE parameters if enabled.
3. Check that the callback reaches `/login/oauth2/code/demo` and the client still retains the original request info to validate `state`.
4. If the callback is valid but login fails, inspect the backend token exchange error (error code, HTTP status, and provider config), without printing full codes or tokens.
5. If login succeeded but API calls fail, check the access token, scope/audience, resource server config, and user permissions separately from OIDC login.

In browser DevTools, you normally see the front-channel redirect steps. With this backend pattern, the POST to the token endpoint occurs **between Spring Boot and the AS**, so it does not appear as a JavaScript request from the web page. Do not manually reproduce the code exchange by sending the code from the browser to the token endpoint when the system uses Spring Security as a confidential client.

## 10. Security Principles When Implementing

A secure Authorization Code Grant implementation must maintain the following principles:

- Use HTTPS in real environments; register exact redirect URIs and restrict arbitrarily controllable URIs.
- Generate random `state` per transaction and verify it at the callback; protect sessions/cookies storing correlation data.
- Use PKCE `S256` and store the verifier per authorization request; especially for public clients.
- Never put client secrets into browsers or mobile apps; choose a client authentication method matching the client type.
- Never reuse an authorization code, store a code as an access token, or attempt to ignore `invalid_grant` errors.
- Never print access tokens, refresh tokens, ID Tokens, client secrets, or authorization codes to logs in real environments; also control proxy/access logs and monitoring tools.
- Validate ID Tokens per OIDC when authenticating users; use an access token with the right audience and scopes to call resource servers.
- Keep issuer, redirect URI, and provider metadata configuration consistent when running behind a load balancer/reverse proxy.
- Apply standard CSRF protection for state-changing operations in the application; OAuth `state` does not replace CSRF protection across all HTTP endpoints.
- Use the framework's token/authorized-client management mechanisms suited to session, expiration, and refresh needs; do not arbitrarily store tokens in URLs or `localStorage` when a server architecture can hold them more securely.

## 11. Self-Check with a Scenario

An application sends an authorization request containing `state=S1` and `code_challenge=C1`. After the user logs in, the browser arrives at the callback with `code=K1&state=S1`.

**Can the application immediately treat the user as logged in?** Not yet. The client must match `state` against the saved request, exchange `K1` at the token endpoint with the right details (including the `code_verifier` matching `C1` and client authentication if needed), process the response, validate the ID Token if OIDC, and only then establish the login context.

**What if someone else obtains `K1` without the verifier?** With PKCE properly enforced by the AS, that party cannot prove possession of the verifier and therefore cannot exchange the code for tokens using `K1` alone.

**What if the callback has `state=S2` instead of `S1`?** The client must reject the callback because it does not match the initiated request, even if the code looks valid.

**What if the application resends `K1` after it has already been successfully exchanged?** The AS must reject the reused code. An application cannot use a single authorization code to obtain tokens indefinitely; token lifetimes and refresh tokens are a separate concern.

**What if an API rejects the access token even though OIDC login succeeded?** Check the audience, scopes, token validity, and API policies. Successful login proves the user was authenticated to the client; it does not automatically grant access to every resource.

## 12. Remembering the Code Exchange Flow

The Authorization Code Grant progresses through **authorization request → user authentication/consent → callback with code and state → callback validation → backend token request → response validation → using tokens for their proper purpose**.

In Spring Security OAuth 2.0/OIDC Client, the endpoints to remember are:

| URL / Endpoint | Owner | Purpose |
|---|---|---|
| `/oauth2/authorization/{registrationId}` | Spring Security client | Initiates the authorization request and redirects to the IdP. |
| Authorization endpoint, e.g., `https://id.example.com/authorize` | IdP / AS | Receives authorization request; authenticates/consents; issues code via redirect. |
| `/login/oauth2/code/{registrationId}` | Spring Security client | Receives callback, correlates request, proceeds to exchange code for tokens. |
| Token endpoint, e.g., `https://id.example.com/token` | IdP / AS | Validates code, client authentication, and PKCE; issues tokens. |
| UserInfo endpoint, if supported by OIDC provider and used by client | OpenID Provider | Provides claims about the user per OIDC mechanism. |
| Protected API endpoint | Resource Server | Receives access token, checks permissions, and returns data. |

A short way to remember: **the browser transports the code; the client exchanges the code; the AS issues tokens; the API validates the access token; the OIDC client validates the ID Token for login.** Each role has a distinct responsibility, and `state`, PKCE, client authentication, and OIDC validation make the entire flow trustworthy.
