# 26.6. Binding Tenant with `state`, Callback, and Principal

## Lesson Objectives

In a **multi-tenant Spring Security OAuth 2.0 / OpenID Connect (OIDC) Client**, logging in successfully at the OpenID Provider is not enough to grant a user access to the selected tenant.

Suppose a user opens `/t/acme/login`. If after the callback the application reads the tenant from a query parameter or a shared `selectedTenant` session attribute, the browser can alter that value or two login tabs can overwrite each other. As a result, the user could be bound to the wrong tenant even though OAuth2 Login just succeeded.

The core principle is to establish a binding that the browser cannot tamper with:

**Initial tenant → Authorization Request with `state` → verified callback → issuer + subject → membership → tenant-scoped principal/session → tenant-aware authorization on every API.**

After this lesson, you will be able to:

1. Distinguish tenant routing hint, canonical tenant ID, client registration, and issuer.
2. Bind the tenant to the `state` generated by Spring Security when initiating the Authorization Code flow.
3. Use a server-side pending login store keyed by `state` with TTL, session binding, and one-time consumption.
4. Verify tenant, registration, and expected issuer on callback without bypassing default OAuth2/OIDC checks.
5. Identify mix-up, login CSRF, state replay, tenant hopping, and account confusion.
6. Build identity around `iss` + `sub` after ID token verification and check membership within the tenant.
7. Avoid two-tab login races and session ID rotation issues.
8. Distinguish OP-issued tenant claims from application tenant roles/permissions.
9. Design tenant context for sessions/principals without letting tenant A's permissions carry over to B.
10. Organize Resolvers/Success Handlers with Spring MVC and understand the corresponding Reactive/WebFlux counterparts.
11. Verify tenant isolation across services/databases, token caches, API authorization, and logout.
12. Write tests for mismatches, replay, concurrent flows, and users lacking tenant membership.

## 1. Context: Multi-Tenant SaaS Portal

Suppose Portal has three tenants:

~~~text
Acme
Globex
Contoso
~~~

The same Spring Boot application serves:

~~~text
https://portal.example.com/t/acme
https://portal.example.com/t/globex
https://portal.example.com/t/contoso
~~~

Each tenant may use its own OP or share one OP. Tenants have separate users, memberships, roles, and business data.

Example trusted configuration:

| Tenant ID | Slug | Registration ID | Expected issuer |
|---|---|---|---|
| 42 | `acme` | `acme-oidc` | `https://id.acme.example/oidc` |
| 51 | `globex` | `globex-oidc` | `https://sso.globex.example` |
| 88 | `contoso` | `shared-oidc` | `https://login.corp.example` |

A registration ID is the local key for `ClientRegistration`. Issuer is the configured and verified AS/OP identity. Tenant ID is the internal organizational identity, which does not necessarily match any claim in the ID token.

### 1.1. Target Login Flow

~~~mermaid
sequenceDiagram
    autonumber
    actor User as User
    participant Browser
    participant Portal as Spring Security Portal
    participant Store as Pending login store
    participant OP as OpenID Provider
    participant Members as Membership service
    User->>Browser: Open /t/acme/login
    Browser->>Portal: Select tenant Acme
    Portal->>Portal: Resolve tenant, allowlist registration/issuer
    Portal->>Portal: Generate Authorization Request with state
    Portal->>Store: Save state → expected Acme/registration/issuer
    Portal-->>Browser: 302 to OP
    Browser->>OP: Authorization Request
    OP-->>Browser: Callback code + state
    Browser->>Portal: /login/oauth2/code/acme-oidc
    Portal->>Portal: Spring verifies state, token, and OIDC
    Portal->>Store: Consume pending binding by state
    Store-->>Portal: Expected Acme/registration/issuer
    Portal->>Members: Check (Acme, iss, sub)
    Members-->>Portal: Membership ACTIVE
    Portal->>Portal: Create tenant-scoped context
    Portal-->>Browser: Redirect to /t/acme
~~~

If `state` is missing, the issuer is wrong, the registration differs, or membership is invalid, the system must **reject**. Never read the tenant from callback query params to recover from errors.

### 1.2. Rules Before and After Login

Before OP authentication:

~~~text
Tenant selection = request routing hint
Identity = unauthenticated
Membership = not yet granted
~~~

After the OIDC token is verified and the membership check succeeds:

~~~text
TenantId = 42
Issuer = https://id.acme.example/oidc
Subject = user-123
LocalUserId = user-92817
Registration = acme-oidc
Membership = ACTIVE
TenantAuthorities = [ORDER_VIEWER]
~~~

Even at this stage, APIs must still verify permissions on individual resources rather than relying solely on a one-time login success.

## 2. Trust Boundaries

| Data | Comes from | Can it be trusted directly? |
|---|---|---|
| Tenant slug in path | Browser | No, must look up in directory |
| Host or subdomain | HTTP request/proxy | No, unless host and forwarded headers are controlled |
| Canonical tenant ID | Server-side directory | Can serve as the tenant's identity |
| `registrationId` | OAuth client configuration | Trusted when chosen from allowlist |
| `state` | Generated by Spring OAuth2 Client | Correlation key; must be matched server-side |
| Callback query `code`/`state` | Browser forwarded from OP | Only used after protocol validation |
| ID token `iss`/`sub` | OP | Only used after OIDC signature/issuer/audience validation |
| Membership | Application directory/ACL | Basis for granting tenant permissions |
| `tid`/`org` claims | OP | Only used if semantics are defined and verified |
| Active tenant context | Application after authorization | Trusted only when protected from client mutation |

### 2.1. Tenant Selection Is Not Authorization

Any browser can enter:

~~~text
https://portal.example.com/t/globex/login
~~~

That merely asks the system to start login for Globex. It does not prove the user is authorized to read Globex's orders.

### 2.2. OIDC Authentication Does Not Auto-Grant Membership

A shared OP can authenticate both Acme and Globex employees. Alice is a valid user at the OP but may belong only to Acme.

If Alice selects Globex, the OP can still return a valid ID token for Alice. Portal must still verify **whether Alice has membership in Globex**.

### 2.3. Tenant Claim Does Not Always Match SaaS Tenant

An ID token may carry `tid` representing the identity system's tenant, not Portal's internal tenant ID.

Never use that claim directly as SaaS data access permission unless there is an explicit contract and mapping.

## 3. `TenantDirectory`: Source of Approved Mappings

A `TenantDirectory` is responsible for:

- Resolving canonical tenant ID from slug or domain.
- Verifying the tenant is `ACTIVE`.
- Specifying the `registrationId` values permitted for the tenant.
- Mapping registration to the approved issuer.
- Managing config versions when issuer/registration changes.
- Providing tenant-specific login policies and appropriate return paths.

### 3.1. Illustrative Interface

~~~java
public interface TenantDirectory {

    PendingTenantLogin beginLogin(
            String tenantSlug,
            String registrationId);
}
~~~

The method must validate both inputs and never treat them as access rights. In practice, it can take a canonical tenant ID resolved by the router instead of a slug.

### 3.2. Never Use User-Supplied Issuer URLs

Dangerous pattern:

~~~text
/login?issuer=https://untrusted.example.net
~~~

If the backend creates a `ClientRegistration` and runs discovery against any URL, risks include SSRF and logging in through an unapproved OP.

The browser should only be allowed to select a tenant/registration **within the server's allowlist**.

### 3.3. One Tenant May Be Allowed Multiple OPs

For example:

~~~text
Acme:
  acme-oidc
  shared-corporate-oidc
~~~

Each OP has its own policy. The same tenant can have multiple login methods, but membership checks must still identify the user from the corresponding issuer/subject.

### 3.4. One OP May Be Shared Across Multiple Tenants

For example:

~~~text
Acme -> shared-oidc
Globex -> shared-oidc
Issuer -> https://login.corp.example
~~~

In this case, **both `registrationId` and issuer are identical** across the two flows. Therefore, storing the selected tenant keyed by `state` and checking membership are mandatory.

## 4. Role of OAuth `state`

OAuth2 Client builds an Authorization Request with an unpredictable random `state`, stores it in `OAuth2AuthorizationRequestRepository`, and redirects the browser to the Authorization Server.

Example flow initiation:

~~~http
GET /oauth2/authorization/acme-oidc?tenant=acme HTTP/1.1
Host: portal.example.com
~~~

Callback:

~~~http
GET /login/oauth2/code/acme-oidc?code=CODE&state=STATE_A HTTP/1.1
Host: portal.example.com
~~~

Spring Security matches `state` against the saved Authorization Request before completing login.

### 4.1. Never Use Tenant Slug as `state`

Wrong:

~~~text
state=acme
~~~

That `state` is predictable and cannot distinguish two requests for the same tenant. It is not a secure correlation key.

Right: use a random value generated by the framework/secure generator:

~~~text
state=RANDOM_OPAQUE_VALUE
~~~

with a server-side mapping:

~~~text
state=RANDOM_OPAQUE_VALUE
  -> tenantId=42
  -> registrationId=acme-oidc
  -> expectedIssuer=https://id.acme.example/oidc
  -> startedAt=...
~~~

### 4.2. Never Trust Tenant in the Callback

The callback could contain a forged query param:

~~~text
/login/oauth2/code/acme-oidc?code=...&state=...&tenant=globex
~~~

The application must never take `tenant=globex` as the real tenant. The tenant was bound when the flow started and is retrieved from the server-side state store.

### 4.3. Self-Contained `state` Has Extra Requirements

If you want to embed the tenant inside the `state` payload instead of a server-side store, you must ensure:

- Integrity/authentication of the payload.
- Sufficient entropy.
- Timestamp/TTL.
- Replay protection.
- Browser/session binding.
- No sensitive data exposure.
- Key rotation.

Simply Base64-encoding JSON provides neither integrity nor confidentiality.

## 5. `PendingTenantLogin`: Transaction Context

You can store an immutable object:

~~~java
import java.time.Instant;

public record PendingTenantLogin(
        String tenantId,
        String registrationId,
        String expectedIssuer,
        Instant startedAt,
        String returnPath) {
}
~~~

Explanation:

| Field | Meaning |
|---|---|
| `tenantId` | Canonical tenant ID resolved by the server |
| `registrationId` | Allowlisted `ClientRegistration` |
| `expectedIssuer` | Issuer configured/trusted at login start |
| `startedAt` | TTL evaluation |
| `returnPath` | Safe internal post-login path |

Never store:

~~~text
client_secret
raw access_token
refresh_token
id_token
authorization_code
raw user password
full OIDC claim set
~~~

The pending binding holds only the data needed to control the transaction, not a token store.

### 5.1. Binding to Configuration at Start Time

If an admin changes Acme's issuer while a user is logging in, a callback from the old issuer must not silently be processed as the new issuer.

You can also store a configuration version and reject pending flows when security-sensitive policies change.

### 5.2. Return Path Must Be Validated

Example valid path:

~~~text
/t/acme/orders
~~~

Never put `https://attacker.example.net` into the return path just because the browser sent a `returnUrl` parameter.

## 6. Storing Pending State on the Server

A simple interface:

~~~java
import jakarta.servlet.http.HttpServletRequest;
import java.util.Optional;

public interface PendingTenantLoginStore {

    void save(
            HttpServletRequest request,
            String state,
            PendingTenantLogin pending);

    Optional<PendingTenantLogin> consume(
            HttpServletRequest request,
            String state);
}
~~~

`save` is called before redirecting to the OP. `consume` is called after the callback has been verified by Spring Security.

### 6.1. Store Invariants

- Each `state` maps to only one pending transaction.
- Tenant/registration/issuer cannot be modified once saved.
- `state` belongs to the browser/session that initiated the flow.
- Records have a short TTL and an entry cap.
- `consume` must be single-use and atomic across multiple nodes.
- A second callback with the same `state` must fail.
- Never look up another session's `state` to "recover" a flow.
- Never log raw `state`, session IDs, or credentials.

### 6.2. Session-Backed Map

Instead of:

~~~text
HttpSession:
  selectedTenant=globex
~~~

store:

~~~text
HttpSession:
  pendingTenantLogins:
    state-A -> acme
    state-B -> globex
~~~

Two requests will not alter the tenant bound to each other's `state`.

### 6.3. Redis/Database Store

If using shared storage across multiple nodes, `consume` must have **atomic read-and-delete** semantics (a transaction, Redis Lua script, or equivalent primitive).

A separate `GET` followed by `DEL` can let two concurrent callbacks both consume the binding.

### 6.4. TTL

Callback wait times are typically short and depend on the OP experience. Pending data must be deleted on expiration, logout, or failure.

A TTL that is too short breaks legitimate flows; too long increases retention and `state` replay risk if the implementation has bugs.

## 7. Two Concurrent Login Tabs

Example:

~~~text
Tab A starts Acme login -> state-A
Tab B starts Globex login -> state-B
~~~

If the app has only one session variable:

~~~text
Tab A: selectedTenant=acme
Tab B: selectedTenant=globex
Tab A callback -> reads globex (wrong)
~~~

A state-indexed map prevents mixing tenants across the two transactions:

~~~text
state-A -> acme
state-B -> globex
~~~

### 7.1. Also Check `AuthorizationRequestRepository`

Some default implementations of `HttpSessionOAuth2AuthorizationRequestRepository` store only one Authorization Request in the session at a time. Two flows in the same session can cause the earlier flow to lose `state` correlation.

**Adding a pending tenant map does not automatically make the default repository support concurrent OAuth logins.**

If your product requires multiple simultaneous login tabs, you need a custom `AuthorizationRequestRepository<OAuth2AuthorizationRequest>` storing multiple pending requests keyed by `state`, with TTL, an upper bound, and one-time removal.

### 7.2. Never Drop `state` Checks to Fix Multi-Tab Issues

If a callback no longer has a matching Authorization Request, reject it and ask the user to restart. Never accept a code merely because the callback endpoint matches.

### 7.3. Entry Count Must Be Bounded

A browser could try initiating thousands of login flows. The pending state store must limit entries per session and purge expired entries to prevent resource exhaustion.

## 8. Session Fixation and Session ID Rotation

Spring Security may rotate the session ID after authentication to mitigate session fixation.

A custom store using a Redis key:

~~~text
pending:{raw-session-id}:{state}
~~~

can break if the session ID rotates before the application consumes the pending binding and the key is not migrated.

### 8.1. Do Not Blindly Depend on the Session ID String

You can store the pending map inside session attributes that get migrated by the active strategy, or use a controlled session-bound stable handle.

Verify the actual ordering of the OAuth2 Login filter, session fixation strategy, and custom success handling.

### 8.2. Session Expires Before Callback

If the session/correlation is lost, the callback must fail closed. Never look up a `state` globally and attach the user to a different session.

### 8.3. Session Cookie

When using cookie-backed sessions, configure `Secure`, `HttpOnly`, and `SameSite` appropriately for the OAuth redirect flow. Never disable these protections just to make the callback work.

## 9. Callback Verification Order

Reference order:

1. Spring Security locates the Authorization Request matching `state`.
2. Verifies flow/callback and exchanges the authorization code at the matching registration's token endpoint.
3. Validates OIDC ID token: signature, issuer, audience, timestamps, and nonce where applicable.
4. Produces an `OAuth2AuthenticationToken` carrying the actual registration ID.
5. Application consumes the pending tenant binding saved under `state`.
6. Compares expected registration with the `Authentication`.
7. Compares expected issuer with the validated ID token issuer.
8. Reads the verified subject.
9. Checks membership in the canonical tenant.
10. Only then grants active tenant context/authorities per policy.
11. Redirects to a path belonging to the verified tenant.
12. Continues checking tenant and ownership on every API request.

Custom tenant checks are an **additional layer**, never a replacement for the framework's `state`/PKCE/nonce/ID token validation.

### 9.1. Registration Check

`OAuth2AuthenticationToken` provides:

~~~java
oauth.getAuthorizedClientRegistrationId();
~~~

This value must match the `registrationId` bound in the pending record.

### 9.2. Issuer Check

`OidcUser` holds the ID token verified by the OP. The issuer from that token must match the issuer chosen and trusted by the tenant/registration.

### 9.3. Membership Check

A valid user at the OP who does not belong to the selected tenant **must not be granted access to that tenant**.

If the SaaS supports just-in-time provisioning, it must follow an approved policy; never assume "login succeeded means create member".

## 10. Custom Authorization Request Resolver in Spring MVC

One integration approach is **wrapping the standard resolver** to obtain the framework-generated `state`, then saving the tenant binding.

### 10.1. Resolver Wrapper

~~~java
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.security.oauth2.client.web
        .OAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.core.endpoint
        .OAuth2AuthorizationRequest;

public final class TenantBoundAuthorizationRequestResolver
        implements OAuth2AuthorizationRequestResolver {

    private static final String BASE_PATH =
            "/oauth2/authorization/";

    private final OAuth2AuthorizationRequestResolver delegate;
    private final TenantDirectory tenantDirectory;
    private final PendingTenantLoginStore store;

    public TenantBoundAuthorizationRequestResolver(
            OAuth2AuthorizationRequestResolver delegate,
            TenantDirectory tenantDirectory,
            PendingTenantLoginStore store) {
        this.delegate = delegate;
        this.tenantDirectory = tenantDirectory;
        this.store = store;
    }

    @Override
    public OAuth2AuthorizationRequest resolve(
            HttpServletRequest request) {

        OAuth2AuthorizationRequest authorization =
                delegate.resolve(request);

        if (authorization == null) {
            return null;
        }

        String registrationId =
                registrationFromPath(request.getServletPath());

        return bind(request, registrationId, authorization);
    }

    @Override
    public OAuth2AuthorizationRequest resolve(
            HttpServletRequest request,
            String registrationId) {

        OAuth2AuthorizationRequest authorization =
                delegate.resolve(request, registrationId);

        if (authorization == null) {
            return null;
        }

        return bind(request, registrationId, authorization);
    }

    private OAuth2AuthorizationRequest bind(
            HttpServletRequest request,
            String registrationId,
            OAuth2AuthorizationRequest authorization) {

        String tenantSlug = request.getParameter("tenant");

        PendingTenantLogin pending =
                tenantDirectory.beginLogin(
                        tenantSlug, registrationId);

        store.save(
                request,
                authorization.getState(),
                pending);

        return authorization;
    }

    private String registrationFromPath(String path) {
        if (path == null || !path.startsWith(BASE_PATH)) {
            throw new IllegalArgumentException(
                    "Unknown OAuth authorization route");
        }

        String registrationId =
                path.substring(BASE_PATH.length());

        if (registrationId.isBlank()
                || registrationId.contains("/")) {
            throw new IllegalArgumentException(
                    "Invalid registration route");
        }

        return registrationId;
    }
}
~~~

This snippet assumes the OAuth login initiation path is literally `/oauth2/authorization/{registrationId}` and the servlet path has no special rewrites. If the deployment uses a custom base URI/context path, adapt how `registrationId` is extracted to match actual routing.

### 10.2. Why Delegate?

Spring Security's `DefaultOAuth2AuthorizationRequestResolver` knows how to build the Authorization Request with the right registration, `state`, redirect URI, scopes, and PKCE/nonce per flow.

The wrapper only binds the tenant to `state`; **never overwrite `state`** with the tenant slug.

### 10.3. Example Starting Login

~~~text
GET /oauth2/authorization/acme-oidc?tenant=acme
~~~

`tenant=acme` is still untrusted input. `TenantDirectory.beginLogin(...)` must verify that this registration is allowlisted for the canonical tenant Acme.

## 11. Configuring the Resolver in `SecurityFilterChain`

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders
        .HttpSecurity;
import org.springframework.security.oauth2.client.registration
        .ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web
        .DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class TenantSecurityConfiguration {

    @Bean
    SecurityFilterChain tenantSecurityFilterChain(
            HttpSecurity http,
            ClientRegistrationRepository registrations,
            TenantDirectory directory,
            PendingTenantLoginStore store,
            TenantLoginSuccessHandler successHandler)
            throws Exception {

        var delegate =
                new DefaultOAuth2AuthorizationRequestResolver(
                        registrations, "/oauth2/authorization");

        var tenantResolver =
                new TenantBoundAuthorizationRequestResolver(
                        delegate, directory, store);

        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers(
                                "/", "/t/*/login", "/error")
                        .permitAll()
                        .anyRequest().authenticated())
                .oauth2Login(oauth2 -> oauth2
                        .authorizationEndpoint(endpoint -> endpoint
                                .authorizationRequestResolver(
                                        tenantResolver))
                        .successHandler(successHandler))
                .oauth2Client(Customizer.withDefaults())
                .build();
    }
}
~~~

The `TenantDirectory`, `PendingTenantLoginStore`, and `TenantLoginSuccessHandler` beans are **custom components** that must be implemented in the application; Spring Security does not provide them out of the box.

This example is for Servlet OAuth2 Login. You do not need to write a new HTTP callback handler to exchange the code yourself, because Spring Security's filter already executes the flow.

## 12. Membership Service and Tenant Identity

After verifying the ID token, map the identity to a local user/tenant membership.

~~~java
public record TenantIdentity(
        String tenantId,
        String issuer,
        String subject,
        String registrationId,
        String localUserId) {
}

public interface TenantMembershipService {

    TenantIdentity requireActiveMembership(
            String tenantId,
            String issuer,
            String subject,
            String registrationId);
}
~~~

A production implementation should:

- Use the verified `issuer` + `subject` as the external identity key.
- Verify the registration/issuer is permitted for the tenant.
- Look up verified account links.
- Verify the tenant is active.
- Verify the membership is active.
- Apply roles/permissions scoped to the tenant.
- Deny if the user has no membership.
- Never auto-create accounts by matching email unless permitted by an explicit provisioning policy.

### 12.1. `iss` + `sub`

One OP may issue `sub=user-123`, and another OP may also issue `sub=user-123`.

These two subjects are **not assumed to be the same user**. The issuer must be included.

### 12.2. Email Does Not Replace Membership

An email claim can change or be unverified. Even a verified email does not by itself prove permission to access a SaaS tenant's data.

## 13. Illustrative Success Handler

One way to verify the tenant **after Spring Security finishes OAuth2/OIDC authentication** is a custom success handler.

~~~java
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import org.springframework.security.core.Authentication;
import org.springframework.security.oauth2.client.authentication
        .OAuth2AuthenticationToken;
import org.springframework.security.oauth2.core.oidc.user.OidcUser;
import org.springframework.security.web.authentication
        .AuthenticationSuccessHandler;
import org.springframework.security.web.authentication.logout
        .SecurityContextLogoutHandler;

public final class TenantLoginSuccessHandler
        implements AuthenticationSuccessHandler {

    private final PendingTenantLoginStore store;
    private final TenantMembershipService memberships;

    public TenantLoginSuccessHandler(
            PendingTenantLoginStore store,
            TenantMembershipService memberships) {
        this.store = store;
        this.memberships = memberships;
    }

    @Override
    public void onAuthenticationSuccess(
            HttpServletRequest request,
            HttpServletResponse response,
            Authentication authentication)
            throws IOException, ServletException {

        try {
            if (!(authentication
                    instanceof OAuth2AuthenticationToken oauth)) {
                throw new IllegalStateException(
                        "OAuth2 authentication required");
            }

            PendingTenantLogin expected = store
                    .consume(
                            request,
                            request.getParameter("state"))
                    .orElseThrow(() ->
                            new IllegalStateException(
                                    "Pending tenant login missing"));

            if (!expected.registrationId().equals(
                    oauth.getAuthorizedClientRegistrationId())) {
                throw new IllegalStateException(
                        "Registration mismatch");
            }

            if (!(oauth.getPrincipal() instanceof OidcUser user)) {
                throw new IllegalStateException(
                        "OIDC principal required");
            }

            String issuer =
                    user.getIdToken().getIssuer().toString();
            String subject =
                    user.getIdToken().getSubject();

            if (!expected.expectedIssuer().equals(issuer)) {
                throw new IllegalStateException(
                        "Issuer mismatch");
            }

            TenantIdentity identity =
                    memberships.requireActiveMembership(
                            expected.tenantId(),
                            issuer,
                            subject,
                            expected.registrationId());

            request.getSession().setAttribute(
                    "VERIFIED_TENANT_IDENTITY", identity);

            // Production: redirect ONLY to a validated path
            // belonging to identity.tenantId(), then return.
            response.sendRedirect(
                    request.getContextPath() + "/t/"
                            + identity.tenantId() + "/home");

        } catch (RuntimeException failure) {
            // Fail closed; ensure local auth/session is removed.
            new SecurityContextLogoutHandler()
                    .logout(request, response, authentication);
            response.sendError(
                    HttpServletResponse.SC_FORBIDDEN,
                    "Tenant login is not permitted");
        }
    }
}
~~~

### 13.1. Limitations of This Example

This is an **illustrative skeleton**. The redirect assumes the route contains the canonical tenant ID. For routes using slugs or vanity domains, use a trusted server-side path resolver and properly encode path segments rather than concatenating unvalidated input.

More importantly: the success handler runs after Spring Security's authentication step, at which point `SecurityContext`/authorized clients **may already have been saved**. When the tenant check fails, you must clean up any created state, including authorized clients in `OAuth2AuthorizedClientService` if stored outside the session.

In systems requiring tenant verification to complete **before saving `Authentication`**, integrate verification into the appropriate authentication pipeline/strategy while preserving all standard OAuth2/OIDC checks. Do not treat the illustrative success handler alone as production-complete.

### 13.2. Never Call Success Logic Before Framework State Checks

The handler must only be invoked by Spring Security's completed OAuth2 Login flow. It is not a standalone endpoint that accepts an arbitrary `state` and grants tenant context.

### 13.3. Do Not Automatically Follow a Saved Request from Another Tenant

If the pre-login request was `/t/globex/orders` while the pending login was bound to Acme, redirecting to the saved request can cause confusion. Validate the redirect's tenant or send to a fixed path belonging to the verified tenant.

## 14. Binding the Principal After Login

An application principal or context may include:

~~~text
localUserId
issuer
subject
registrationId
activeTenantId
membershipId
tenantAuthorities
authenticatedAt
~~~

However, **a session attribute by itself is not an authorization decision**.

### 14.1. Tenant-Scoped Authorities

A user might be:

~~~text
Alice:
  Acme -> ORDER_ADMIN
  Globex -> ORDER_VIEWER
~~~

Acme's `ORDER_ADMIN` must never be usable for admin operations in Globex.

### 14.2. Membership Changes After Login

An admin may revoke Alice's Acme membership while her session is still active.

Depending on policy, recheck membership per request, use versioning, cache invalidation, or session invalidation. Never treat an old claim in an ID token as an immutable right until token expiry.

### 14.3. Principal Identity vs. Tenant Context

Global identity (issuer, subject, local user) differs from the active tenant. A user may belong to multiple tenants; each request still requires a controlled active tenant.

### 14.4. Authorized Client Storage

If a custom token store key relies only on a `sub` that collides across issuers or an unnamespaced registration/username, tokens can be attached to the wrong principal.

Ensure storage keys distinguish registration, trusted principal, and tenant/issuer when required by the architecture.

## 15. One Issuer Serving Multiple Tenants

Example:

~~~text
Acme: shared-oidc
Globex: shared-oidc
Issuer: https://login.corp.example
~~~

User Alice authenticates successfully at the OP, but is only an Acme member.

If Alice tries:

~~~text
/oauth2/authorization/shared-oidc?tenant=globex
~~~

the OP can still issue a valid ID token.

**Comparing issuer and registration alone cannot detect that Alice does not belong to Globex.** State-bound pending tenant binding and membership checks are mandatory.

### 15.1. `login_hint` and `domain_hint` Are Hints

Some OPs accept hints to choose a login form or organization. Never treat these hints as a SaaS membership decision.

### 15.2. Tenant Claims from the OP

If the OP emits `organizations` or `roles`, use them only under an agreed profile after validating issuer, audience, timestamps, and permissions. Never copy claims straight into internal ACLs without a policy mapping.

## 16. Multiple OPs and Authorization Server Mix-Up

When Acme and Globex have different issuers, there is a risk the app confuses one OP's response with another OP's flow.

Example to prevent:

~~~text
Start Acme login
  -> Callback from Globex
  -> App processes it as Acme because it only reads the tenant URL
~~~

Mitigations:

- Spring Security's `state` correlation.
- Registration binding via `state`.
- Issuer binding via `state`.
- Token endpoint taken from the trusted `ClientRegistration`.
- ID token issuer/audience/signature/nonce validation.
- Callback path/redirect URI matching the registration.
- Authorization response issuer validation when supported by profile/framework.
- Never accept token endpoints or issuers from the callback.

### 16.1. Callback Path Alone Is Not Proof

`/login/oauth2/code/acme-oidc` is a route, not cryptographic proof of the issuer.

It must be combined with `state` correlation and token validation.

### 16.2. Never Disable Issuer Validation

On an issuer mismatch, fix the registration/metadata/flow. Never turn off `iss` validation just to make multi-tenant login "work".

## 17. Login CSRF, Replay, and PKCE/Nonce

### 17.1. Login CSRF

If the application accepts a callback that does not match a request initiated by that browser, a user can be logged into the wrong account or tenant.

Spring Security uses `state` to correlate the OAuth2 Authorization Request. Tenant binding ensures the tenant also cannot be swapped mid-flight.

### 17.2. Replay

A `state` may be consumed only once:

~~~text
First callback state-A -> consume -> valid
Second callback state-A -> missing -> reject
~~~

The Authorization Code is also single-use at the AS, yet the application's store should still enforce one-time semantics.

### 17.3. PKCE

PKCE protects the Authorization Code with a code verifier/challenge. Each authorization transaction must have its own verifier when PKCE is enabled.

### 17.4. Nonce

OIDC nonce binds the ID token to the authentication request when applicable. Never share one global nonce across all tenants or browser sessions.

### 17.5. OAuth `state` Does Not Replace Application CSRF Protection

A POST `/tenant/switch` or `/account/link` using a cookie session still requires CSRF protection per web app design. `state` only handles OAuth flow correlation.

## 18. Post-Callback Redirects and Open Redirects

If the app lets users pick a return path, never accept arbitrary URLs:

~~~text
returnTo=https://attacker.example.net
returnTo=//attacker.example.net
~~~

Validate that only internal paths belonging to the verified tenant are allowed:

~~~text
/t/acme/home
/t/acme/orders
~~~

### 18.1. Avoid Cross-Tenant Saved Requests

If the user chose Acme while a saved request points to Globex, reject or redirect to Acme's home page. Never treat a redirect path as allowed simply because login succeeded.

### 18.2. Path Normalization

Check URL encoding, protocol-relative URLs, backslashes, and dot segments with a proper parser. Never rely solely on `startsWith("/t/acme")`, which could accept unintended prefixes like `/t/acme-evil`.

### 18.3. Return Path Does Not Decide the Tenant

The tenant was already verified from pending state and membership. The return path only navigates within that tenant's scope.

## 19. Switching Tenants After Login

A user may belong to both Acme and Globex and want to switch the active tenant.

This is an **in-application authorization operation**, not an OIDC flow callback.

Example flow:

~~~text
POST /tenant/switch
  targetTenant = Globex
  -> CSRF validation if cookie session
  -> Check authenticated identity
  -> Check Globex membership
  -> Recalculate tenant roles
  -> Update active tenant context
  -> Invalidate stale tenant caches if needed
  -> Redirect to Globex path
~~~

### 19.1. Do Not Just Change the URL

If Alice is in Acme and navigates to `/t/globex/orders`, the app must never automatically set the tenant context to Globex and grant permissions.

### 19.2. When Tenants Use Different OPs

Policy may require a new Authorization Code/OIDC Login with the target tenant's OP. Never use OP A's tokens/cookies for OP B.

### 19.3. When Sharing an OP and the Identity Is a Member of Both

Switching without re-login can be allowed if policy permits and membership is verified. Even then, roles, caches, and downstream tokens must be bound to the active tenant.

## 20. Tenant-Aware Authorization in Services and Databases

A valid callback cannot compensate for a data query missing a tenant filter.

Example request:

~~~http
GET /t/acme/orders/123
~~~

The service must ensure:

~~~text
requested tenant = Acme
authenticated tenant = Acme
order.tenant = Acme
user has ORDER_VIEWER permission in Acme
~~~

### 20.1. Tenant-Scoped Repository

~~~java
import java.util.Optional;

public interface TenantOrderRepository {

    Optional<OrderEntity> findByTenantIdAndId(
            String tenantId,
            String orderId);
}
~~~

The `tenantId` passed in must come from the trusted authorization context, never from a modifiable request body.

### 20.2. Ownership Checks

Even when an order belongs to Acme, a user might only be permitted to view orders they created. Tenant isolation and object-level authorization are two separate layers.

### 20.3. Cache Keys Must Include Tenant

Wrong:

~~~text
orders-list:alice
~~~

If Alice belongs to two tenants, the cache can return the wrong tenant's data.

Key appropriately by tenant/principal/resource:

~~~text
orders-list:tenant-42:user-92817
orders-list:tenant-51:user-92817
~~~

## 21. Token and Authorized Client Isolation

`OAuth2AuthorizedClient` binds to a registration and principal. In a multi-tenant system, ensure principal names and storage namespaces cannot collide across issuers/tenants.

### 21.1. Avoid Cache Keys Missing Issuer

If two OPs both issue `sub=12345`, caching tokens by `sub` alone can mix credentials.

You may need to use an internal user ID or a `issuer + subject + tenant` namespace for custom storage.

### 21.2. Token with the Right Audience

Acme's access token must never be sent automatically to Globex's Resource Server. The API must verify issuer, audience, scope, and tenant-related authorization per contract.

### 21.3. A Refresh Token Does Not Prove Membership

A successful token refresh only shows the AS issued a new access token. It does not prove the user still belongs to the tenant after an admin revoked membership.

### 21.4. Logout/User Change

If authorized clients reside in a service store outside the session, logout does not automatically remove every record. Clean up and revoke per policy so Bob's new session never uses Alice's token.

## 22. Dynamic Registration Configuration and Issuer Rotation

A large SaaS may create registrations from a tenant config database. Guard against:

- Tenants entering uncontrolled discovery URLs.
- SSRF via metadata/JWKS/Token endpoints.
- Issuer being edited between authorization and callback.
- Client secrets leaking from configs/logs.
- `ClientRegistration` cache mixing tenants.
- Callback routes running against mismatched config versions.

### 22.1. Configuration Version Binding

The pending transaction can store:

~~~text
tenantId
registrationId
expectedIssuer
registrationConfigVersion
startedAt
~~~

If the issuer changes while the user is at the OP, apply an explicit policy—typically failing closed and asking the user to log in again rather than silently switching an old flow to the new issuer.

### 22.2. Trusted Provisioning

Issuer/client registrations should be created via an admin workflow with vetting, HTTPS, discovery endpoint allowlists, client credential protection, and auditing.

## 23. WebFlux/Reactive

The tenant-binding principles stay the same when running Spring WebFlux. The corresponding APIs differ from Servlet:

| Servlet | WebFlux |
|---|---|
| `OAuth2AuthorizationRequestResolver` | `ServerOAuth2AuthorizationRequestResolver` |
| `OAuth2AuthorizationRequestRepository` | `ServerAuthorizationRequestRepository<OAuth2AuthorizationRequest>` |
| `HttpServletRequest` / HttpSession | `ServerWebExchange` / WebSession |
| `AuthenticationSuccessHandler` | `ServerAuthenticationSuccessHandler` |
| `ClientRegistrationRepository` | `ReactiveClientRegistrationRepository` |
| `SecurityContextHolder` | `ReactiveSecurityContextHolder` |

### 23.1. Reactive Flow

~~~text
ServerOAuth2AuthorizationRequestResolver
  -> Mono<OAuth2AuthorizationRequest>
  -> bind tenant context with state in WebSession/store
  -> redirect

OIDC callback
  -> state and token validation
  -> consume pending tenant binding
  -> reactive membership check
  -> tenant-scoped context or reject
~~~

### 23.2. Never Use `.block()` or Manual `.subscribe()`

A reactive membership lookup should be composed via `flatMap`; never call blocking DB queries on the event loop and never manually subscribe in ways that drop error/security context.

### 23.3. Reactive `SecurityContext`

WebFlux uses Reactor Context for `Authentication`. Do not assume Servlet-style `ThreadLocal` `SecurityContextHolder` is valid across reactive operators.

### 23.4. Concurrent Tabs and `WebSession`

You still need a state-indexed pending store, atomic consumption, and compatibility with `AuthorizationRequestRepository` if multi-tab login is a requirement.

## 24. Multi-Domain Tenants and Cookie Isolation

With subdomains:

~~~text
acme.portal.example.com
globex.portal.example.com
~~~

evaluate cookie domains and session boundaries.

### 24.1. Host-Only Cookies

If strong isolation between tenants is needed, consider host-only cookies instead of a broad domain cookie shared across all subdomains.

### 24.2. Trusted Reverse Proxy

Never trust `Host` or `X-Forwarded-Host` from the Internet to select a tenant. Forwarded headers must come from a trusted reverse proxy, and the app must enforce allowed hosts.

### 24.3. `SameSite`

OAuth redirects require the session/correlation cookie to survive when the browser returns. Pick a `SameSite` policy suited to the flow and browser behavior while preserving `Secure`/`HttpOnly` and CSRF protection.

## 25. Testing Tenant Binding

### 25.1. Unit Tests for `TenantDirectory`

| Scenario | Expectation |
|---|---|
| Acme + `acme-oidc` | Returns canonical tenant Acme and approved issuer |
| Acme + `globex-oidc` | Rejects when disallowed |
| Disabled tenant | Rejects |
| Nonexistent tenant slug | Rejects |
| Browser sends another issuer URL | Ignores that URL |
| Tenant alias | Resolves canonical ID consistently |

### 25.2. State Mapping Tests

~~~text
Start Acme -> state-A -> Acme
Start Globex -> state-B -> Globex

consume(state-A) -> Acme
consume(state-B) -> Globex
consume(state-A) a 2nd time -> reject
consume(expired state-C) -> reject
consume(state-D) from another session -> reject
~~~

### 25.3. Callback Tests

- Valid `state`, matching registration, matching issuer, active membership: allow.
- Registration mismatch: reject.
- Issuer mismatch: reject.
- Subject is not a tenant member: reject.
- Missing/expired/replayed `state`: reject.
- User's membership revoked before callback: reject.
- OAuth2-only principal appearing in a mandatory OIDC flow: reject.
- Saved request pointing to external host or another tenant: reject.

### 25.4. Concurrent Login Tests

- Start two login flows in one browser/session.
- Return callbacks in reverse order.
- `state-A` remains Acme, `state-B` remains Globex.
- Authorization Request repository can hold two requests if required.
- Session ID rotation does not lose the binding before consumption.
- Logout/session timeout clears pending data.

### 25.5. Post-Login Authorization

An authenticated user who is an Acme member must still be denied when calling:

~~~text
GET /t/globex/orders/123
~~~

if they lack Globex permissions. Use service/API integration tests, not just callback tests.

### 25.6. Testing with Mock Tokens

Use MockMvc, mock OIDC metadata/token endpoints, or a test OP. Never use production tokens, and never log authorization codes, refresh tokens, or session cookies.

## 26. Troubleshooting

| Symptom | Possible cause | Fix |
|---|---|---|
| Acme login ends up in Globex | Shared `selectedTenant` used | State-indexed binding |
| Two tabs cause one callback to fail | Repository retains only one Authorization Request | Multi-request repository if needed |
| State mismatch | Lost cookie/session, request overwritten | Session/`SameSite`/repository |
| Pending binding missing | TTL too short, session rotation, premature consumption | Store lifecycle |
| Issuer mismatch | Registration/provider mix-up | Check expected issuer and ID token |
| Valid OP user enters wrong tenant | Missing membership check | Tenant authorization |
| `sub` collides across two OPs | Using subject alone | Use `iss` + `sub` |
| Redirects to another tenant | Unvalidated saved request/`returnPath` | Tenant-bound redirect |
| State reuse | Non-atomic consume | One-time store |
| Acme token used in Globex | Wrong principal/tenant cache key | Authorized client isolation |
| Admin revokes membership yet access remains | Stale session/role cache | Recheck/invalidate |
| WebFlux cannot find `Authentication` | `ThreadLocal` or broken Reactor chain | Reactive security context |
| Session cookie leaks across subdomains | Broad cookie domain | Isolation policy |
| Dynamic issuer altered by attacker | Untrusted discovery URL | Server allowlist/admin approval |

## 27. Common Misconceptions

**"A tenant slug in the URL is proof of access rights."** No. It is a routing hint.

**"Successful OIDC Login means the user belongs to the selected tenant."** No. Membership must be verified.

**"Because `state` exists, tenant binding is unnecessary."** `state` protects OAuth correlation; the app still needs to tie `state` to the tenant and check membership.

**"`state` can equal the tenant ID."** No. `state` needs entropy, uniqueness, and replay protection.

**"Reading the tenant at callback is the same as at initiation."** No. The callback passes through the browser; the tenant must come from the saved pending context.

**"A single `selectedTenant` session attribute covers all cases."** Not when multiple tabs and login transactions run concurrently.

**"A state map automatically solves concurrent OAuth logins."** Not if `AuthorizationRequestRepository` does not support multiple requests.

**"Matching issuer + registration is enough."** Not when multiple tenants share one issuer/registration.

**"`sub` is globally unique."** No. Subject belongs to the issuer's namespace.

**"Because the ID token has `tid`, membership checks can be skipped."** Not by default; semantics/policy must be verified.

**"Setting the tenant once in the session keeps the database safe forever."** No. APIs still require tenant/ownership authorization.

**"PKCE and nonce replace `state`/tenant binding."** No; each mechanism addresses a distinct risk.

**"Local logout automatically revokes tokens at the OP."** No. AS revocation is a separate operation.

## 28. Practical Scenarios

### A. Alice Picks a Tenant She Does Not Belong To

Alice is an Acme member and selects Globex with a shared OP.

**Handling:** OIDC authentication may succeed, but Globex membership is missing so access is denied.

### B. Two Login Tabs

Tab A is Acme, Tab B is Globex.

**Handling:** pending map keyed by `state`, not a shared `selectedTenant` variable; if concurrent OAuth flows are required, the repository must also support multiple states.

### C. Callback Alters the Tenant Query Param

`state-A` belongs to Acme, callback carries `tenant=globex`.

**Handling:** ignore the `tenant` query param and use `state-A`'s pending binding.

### D. Same Issuer for Two Tenants

Issuer/registration do not distinguish Acme and Globex.

**Handling:** tenant state binding and membership checks are mandatory.

### E. Admin Changes Issuer Mid-Flow

The flow started with issuer A, but config switched to B.

**Handling:** compare bound issuer/version; typically fail closed and require re-login.

### F. Session ID Rotation

The pending store keys by raw session ID and the callback cannot find the entry after authentication.

**Handling:** design session migration or a stable browser-bound handle—never skip `state` verification.

### G. User Revoked After Login

Alice validly logs into Acme, then her membership is revoked.

**Handling:** block subsequent requests via recheck/invalidation; refreshing an access token does not restore membership.

### H. Saved Request Targeting Another Tenant

Pending login is Acme, but post-login redirect points to Globex.

**Handling:** validate internal return paths and check tenant authorization before redirecting or serving data.

## 29. Self-Check Questions

**1. Does a tenant slug from the URL prove membership?**

No. You must resolve the canonical tenant and verify the user after authentication.

**2. Why bind the tenant to `state`?**

So the callback stays tied to the tenant selected when the Authorization Request was initiated.

**3. Can `state` be `"acme"`?**

No. `state` must be random, unpredictable, and unique per transaction.

**4. Is a `tenant` query parameter in the callback trustworthy?**

No. Use server-side `state` binding.

**5. Why is a single `selectedTenant` session attribute insufficient for two tabs?**

The second tab can overwrite the first tab's choice.

**6. What if the state store supports multiple tabs, but the OAuth request repository stores only one request?**

One flow can still fail `state` validation. You need a repository supporting concurrency if that is a requirement.

**7. Does a callback with a valid OIDC ID token grant tenant permissions?**

Not yet. You need issuer, registration, and membership verification.

**8. Why use `iss` + `sub`?**

Subject is not unique across issuers.

**9. When two tenants share the same issuer and registration, what extra checks are needed?**

State-bound tenant and membership.

**10. Is `tid` in the ID token automatically the internal tenant ID?**

Not by default; it depends on semantics and mapping.

**11. Why must pending state be consumed only once?**

To prevent replay and updating tenant context from an already-used transaction.

**12. How does session ID rotation affect things?**

It can prevent a pending store keyed by the old session ID from finding the record.

**13. Are tenant checks still needed in APIs/databases after the callback?**

Yes. Tenant-aware authorization and ownership checks are required.

**14. Can a user with two memberships switch tenants?**

Yes, per policy, through an operation verifying permission for the target tenant—not just changing the URL.

**15. Does Portal logout automatically revoke tokens at the OP?**

No.

**16. Should WebFlux use Servlet's `ThreadLocal` `SecurityContext`?**

No; use Reactor Context and the appropriate reactive APIs.

**17. If `state` is missing while the ID token issuer is valid, should login succeed?**

No. Missing transaction correlation must be rejected.

**18. Can a post-login redirect go to another tenant just because the user is logged in?**

No. You must check tenant-bound return paths and authorization.

## Key Takeaways

- **The initial tenant is a routing hint, not an access right.** Canonical tenant mapping and membership checks are required after OIDC identity is verified.
- **Bind tenant, registration, and issuer to a pending transaction keyed by Spring Security's `state`**; `state` must be opaque, with TTL, session binding, and one-time consumption.
- **Never trust tenant from callback query params, `Host` headers, or email claims.** Read the tenant from the state-bound server store.
- **Verify registration, issuer, and `iss` + `sub`**, then verify membership in the exact tenant before granting permissions.
- **Multi-tab flows and session ID rotation must be designed upfront**; never use a single shared `selectedTenant` variable across login flows.
- **Preserve the framework's `state`, PKCE, nonce, and ID token validation**—never disable checks to handle mix-ups.
- **A tenant-scoped principal does not replace per-API/resource authorization.** Databases, caches, and downstream calls must still enforce tenant and ownership boundaries.
- **Tenant switching, account linking, logout, and revocation are separate workflows.** Never carry one tenant's roles/tokens into another tenant.
- **Missing pending state, issuer/registration mismatches, or invalid memberships must fail closed**, never defaulting to a tenant from browser-supplied data.
