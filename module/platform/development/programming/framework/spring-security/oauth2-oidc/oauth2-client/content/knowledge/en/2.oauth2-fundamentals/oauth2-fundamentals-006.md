# 2.6. PKCE: Code Verifier, Code Challenge, and the S256 Method

## 1. What Problem Does PKCE Solve?

**Proof Key for Code Exchange (PKCE, pronounced "pixy")** is an extension to the OAuth 2.0 Authorization Code Flow, defined in RFC 7636. PKCE binds the **authorization code** received via redirect to a random secret generated by the OAuth 2.0 Client before starting login. As a result, someone who obtains the authorization code without the corresponding secret cannot use that code to exchange for tokens.

During an OAuth 2.0/OIDC login, the application (Client) sends the browser to the Authorization Server. After the user authenticates and consents to grant permissions, the Authorization Server returns an authorization code via a redirect URL. This segment passes through the **front channel** (browser, operating system, redirects), so there is a risk the code leaks via a redirect-intercepting app, misconfigured redirect, malicious extension, or compromised intermediary.

If knowing the authorization code alone were enough to exchange for tokens, an attacker could race to use the code before the legitimate Client. PKCE adds a requirement:

- When **sending the authorization request**, the Client declares a derived value called the **code challenge**.
- When **exchanging the code for tokens**, the Client must present the secret **code verifier** used to generate the challenge.
- The Authorization Server verifies whether the verifier matches the challenge bound to the authorization code. If it does not match, token issuance is rejected.

PKCE was originally especially important for **public clients** (mobile apps, desktop apps, SPAs), because these applications cannot securely keep a <code>client_secret</code> long-term. Today, PKCE should be used with the Authorization Code Flow even for **confidential clients** like server-side Spring Boot applications, when supported by the Authorization Server. PKCE adds a protection layer for the authorization code; it does not replace client authentication mechanisms for confidential clients.

> **Key takeaway:** An attacker who possesses the authorization code and knows the code challenge still cannot reverse-engineer a sufficiently random code verifier from an S256 challenge to exchange for tokens.

## 2. Three Core Components

| Component | Where Is It Generated? | Which Channel Does It Travel? | Meaning |
|---|---|---|---|
| <code>code_verifier</code> | Client, for **each** start of the Authorization Code Flow | Sent only in the request to the **token endpoint** over HTTPS | Random secret string proving ownership of the original request |
| <code>code_challenge</code> | Client, derived from the verifier | Sent to the **authorization endpoint** with the code request | Commitment value stored/associated with the authorization code by the Authorization Server |
| <code>code_challenge_method</code> | Chosen by the Client, typically <code>S256</code> | Sent to the **authorization endpoint** | Tells the server the transformation from verifier to challenge |

### 2.1. Code Verifier

Per RFC 7636, <code>code_verifier</code> must be **43–128 characters** long, from the *unreserved* character set:

~~~text
A-Z a-z 0-9 - . _ ~
~~~

The verifier needs enough entropy to be unpredictable; the recommended approach is generating **32 random bytes from a cryptographically secure pseudorandom number generator (CSPRNG)**, then Base64URL-encoding without padding. Thirty-two bytes equals 256 bits of random data and typically yields a **43-character** string. Never use current time, incrementing numbers, UUIDs generated from weak entropy sources, usernames, passwords, or configuration constants as a verifier.

The verifier is **different for every authorization request**. If the user logs in again or opens a new login attempt, the Client must generate a new verifier.

### 2.2. Code Challenge

With the S256 method, the challenge is computed as:

~~~text
code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))
~~~

Where:

1. Represent the verifier as ASCII bytes. All valid verifier characters lie in ASCII.
2. Compute the **SHA-256** of those bytes, obtaining a **32-byte digest**.
3. Encode the digest using **URL-safe Base64**, omitting padding characters <code>=</code>. The S256 result is typically **43 characters** long.

SHA-256 is a hash function, **not reversible encryption**. Base64URL is only a URL-parameter-safe byte representation, not a security mechanism. Security comes from a strong random verifier and exposing only the challenge on the front channel.

Common calculation mistakes include hashing a hex string instead of digest bytes, using standard Base64 with <code>+</code>, <code>/</code>, or <code>=</code>, double-encoding, and confusing <code>SHA-256</code> with the protocol method name <code>S256</code>.

### 2.3. `S256` and `plain` Methods

RFC 7636 also defines <code>plain</code>, where <code>code_challenge = code_verifier</code>. This directly exposes the verifier in the authorization request and fails to protect against scenarios where an attacker observes the authorization request as well. Therefore, **prefer S256**; do not automatically downgrade to `plain` when the server returns an error. If an identity provider does not support S256, review compatibility and server configuration.

## 3. Authorization Code + PKCE Flow End-to-End

Suppose a Spring Boot web application is the OAuth 2.0 Client, the Authorization Server is the login system, and the user's browser redirects between the two parties.

~~~mermaid
sequenceDiagram
    autonumber
    participant U as User
    participant B as Browser
    participant C as Spring Security Client
    participant A as Authorization Server
    U->>B: Chooses to log in
    B->>C: GET /oauth2/authorization/demo
    C->>C: Generates random verifier, challenge = S256(verifier)
    C->>C: Stores verifier bound to authorization request/state
    C-->>B: 302 to authorization endpoint
    B->>A: GET /authorize?code_challenge=...&code_challenge_method=S256
    A->>U: Authenticates, requests consent (if needed)
    A->>A: Binds challenge/method to authorization code
    A-->>B: 302 to redirect_uri?code=...&state=...
    B->>C: GET /login/oauth2/code/demo?code=...&state=...
    C->>C: Validates state, finds matching verifier
    C->>A: POST /token with code and code_verifier
    A->>A: Computes S256(verifier), matches against stored challenge
    alt Valid verifier
        A-->>C: Access token (and ID token if OIDC)
        C-->>B: Creates application login session
    else Invalid verifier
        A-->>C: Token error, typically invalid_grant
    end
~~~

Concrete steps:

**Step 1 — Generate the verifier/challenge pair.** The Client generates a new verifier, computes the challenge with S256, and keeps the verifier safe until the code exchange. For a server-side Spring Boot application, authorization request state is typically kept in the server-side HTTP session.

**Step 2 — Send the authorization request.** The browser receives only the challenge and method name, never the verifier via URL:

~~~http
GET /authorize?response_type=code
    &client_id=demo-public-client
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fdemo
    &scope=openid%20profile
    &state=opaque-random-state
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256 HTTP/1.1
Host: idp.example.com
~~~

The HTTP example above is wrapped for readability; when actually sent, the parameters sit on a single properly percent-encoded URL. The illustrative challenge value is taken from RFC 7636's test vector.

**Step 3 — Authorization Server binds PKCE to the code.** The server stores the challenge and method associated with that authorization code issuance; the code is also bound to the Client and redirect URI. After the user authenticates, the server redirects back to the Client with <code>code</code> and <code>state</code>.

**Step 4 — Validate the callback.** The Client verifies <code>state</code> matches the initiation, retrieves the corresponding verifier, and exchanges the code. Never read the verifier from a user-supplied query string on the callback.

**Step 5 — Exchange the code for tokens via the back channel.** For a public client, a typical request is:

~~~http
POST /token HTTP/1.1
Host: idp.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=AUTHORIZATION_CODE&
redirect_uri=https%3A%2F%2Fapp.example.com%2Flogin%2Foauth2%2Fcode%2Fdemo&
client_id=demo-public-client&
code_verifier=ORIGINAL_CODE_VERIFIER
~~~

Line breaks in the body here are for presentation only; the actual request must be properly form-encoded. The token request must use HTTPS. For a confidential client, **Client authentication** per the registered method (e.g., HTTP Basic with client secret) is also included; PKCE still runs alongside it.

**Step 6 — Server verification.** With S256, the server recomputes SHA-256/Base64URL from the verifier in the token request and compares it with the challenge bound to the code. If the verifier is missing, wrong, or the server cannot find matching PKCE data, the token request is rejected. Authorization codes are typically short-lived and single-use.

### What Happens If the Authorization Code Is Stolen?

| Scenario | What Does the Attacker Have? | Expected Outcome |
|---|---|---|
| Code exposed via redirect | Has <code>code</code>, knows <code>code_challenge</code>, does **not** have verifier | Cannot exchange for tokens due to missing proof |
| Attacker guesses the verifier | Sees S256 challenge | Infeasible if verifier has 256 bits of entropy and is properly generated |
| Attacker also compromises the verifier or Client session | Has both code and valid verifier | PKCE is no longer enough; must protect session, runtime environment, and transport channels |
| Client reuses a verifier across multiple logins | One verifier used for multiple codes | Expands blast radius if verifier leaks; must generate a fresh one every time |

## 4. Generating and Verifying PKCE Yourself in Java

In a normal Spring Security application, the framework can generate and pass PKCE automatically. The Java snippet below helps clarify the S256 algorithm and is useful when testing interoperability with an Authorization Server.

~~~java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;

public final class PkceUtil {
    private static final SecureRandom RANDOM = new SecureRandom();

    private PkceUtil() {
    }

    public static PkcePair newPair() {
        byte[] randomBytes = new byte[32]; // 256 bits
        RANDOM.nextBytes(randomBytes);

        String verifier = Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(randomBytes);

        return new PkcePair(verifier, toS256Challenge(verifier));
    }

    public static String toS256Challenge(String verifier) {
        if (verifier == null || !verifier.matches("[A-Za-z0-9._~-]{43,128}")) {
            throw new IllegalArgumentException("Invalid PKCE code_verifier");
        }

        try {
            byte[] digest = MessageDigest.getInstance("SHA-256")
                    .digest(verifier.getBytes(StandardCharsets.US_ASCII));

            return Base64.getUrlEncoder()
                    .withoutPadding()
                    .encodeToString(digest);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("SHA-256 is unavailable", e);
        }
    }

    public record PkcePair(String verifier, String challenge) {
    }
}
~~~

Key choices in the example:

- <code>SecureRandom</code> provides random bytes suitable for cryptographic purposes.
- <code>Base64.getUrlEncoder().withoutPadding()</code> produces a URL-safe string and strips trailing <code>=</code> signs.
- <code>StandardCharsets.US_ASCII</code> corresponds exactly to the expression in RFC 7636.
- The verifier is always the **original string**, not the digest; the Base64URL-encoded digest is the challenge.
- Never log the verifier and never reuse a <code>PkcePair</code> across login attempts.

### 4.1. Standard RFC 7636 Test Vector

RFC 7636 provides an example that can be used to verify the S256 function:

~~~text
code_verifier:
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

code_challenge (S256):
E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
~~~

Manual verification example:

~~~java
String verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk";
String expected = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM";

if (!expected.equals(PkceUtil.toS256Challenge(verifier))) {
    throw new AssertionError("S256 result does not match RFC 7636");
}
~~~

If the result differs from the test vector, check the order **ASCII → SHA-256 byte digest → Base64URL without padding**. Do not apply extra URL encoding before hashing.

## 5. PKCE in Spring Security OAuth 2.0 Client

Spring Security OAuth2 Client is responsible for building the authorization request, persisting request state across redirects, receiving the callback, and sending the token request. When PKCE is configured properly, the application does not need to store the verifier manually in a controller or manually build <code>/token</code> requests.

### 5.1. Minimal Configuration for OAuth2 Login/OIDC

Example using Spring Boot 3 and Spring Security 6 with a **public client** registered at the Authorization Server:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.boot:spring-boot-starter-oauth2-client'
}
~~~

~~~yaml
spring:
  security:
    oauth2:
      client:
        registration:
          demo:
            provider: demo
            client-id: demo-public-client
            client-authentication-method: none
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope:
              - openid
              - profile
        provider:
          demo:
            issuer-uri: https://idp.example.com
~~~

This is a configuration example: replace <code>issuer-uri</code>, <code>client-id</code>, and the redirect URI according to your actual provider; the Authorization Server must serve valid OIDC discovery metadata at the configured issuer. On the server, register the exact redirect URI matching the application. <code>openid</code> in the scope indicates an OIDC flow; if only OAuth 2.0 is needed, scopes depend on the API and do not necessarily include <code>openid</code>.

With basic security configuration:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error").permitAll()
                .anyRequest().authenticated())
            .oauth2Login(Customizer.withDefaults());

        return http.build();
    }
}
~~~

Users start the flow at the default path:

~~~text
GET /oauth2/authorization/demo
~~~

In modern Spring Security versions that support PKCE, <code>DefaultOAuth2AuthorizationRequestResolver</code> automatically applies PKCE when the Client is a public client with <code>client-authentication-method: none</code> and Authorization Code Flow. When the callback returns to <code>/login/oauth2/code/demo</code>, Spring Security looks up the saved authorization request, uses the verifier to exchange tokens, and establishes authentication for the application.

**Do not infer that PKCE is working solely because login succeeds.** When integrating a specific version/framework, verify that the actual authorization request includes <code>code_challenge</code> and <code>code_challenge_method=S256</code>, and that the token request includes the verifier. Do not log secret values while checking.

### 5.2. Enforcing PKCE via an Authorization Request Customizer

For a **confidential client** (which has a client secret) or when you want to actively require PKCE, you can configure <code>OAuth2AuthorizationRequestCustomizers.withPkce()</code> on the resolver:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web.DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestCustomizers;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            ClientRegistrationRepository registrations) throws Exception {

        var resolver = new DefaultOAuth2AuthorizationRequestResolver(
                registrations, "/oauth2/authorization");
        resolver.setAuthorizationRequestCustomizer(
                OAuth2AuthorizationRequestCustomizers.withPkce());

        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error").permitAll()
                .anyRequest().authenticated())
            .oauth2Login(oauth2 -> oauth2
                .authorizationEndpoint(endpoint -> endpoint
                    .authorizationRequestResolver(resolver)));

        return http.build();
    }
}
~~~

This is an **alternative configuration** to <code>SecurityConfig</code> in section 5.1; do not define both identical filter chain beans at the same time. Depending on the Spring Security version, extension APIs may differ; this example uses Spring Security 6 APIs.

The customizer performs two parts that must go together: adding <code>code_challenge</code> and <code>code_challenge_method</code> to the authorization request sent to the Authorization Server, while storing <code>code_verifier</code> inside the internal authorization request's attributes for the token exchange after callback. **Manually adding only the challenge to the URL** without saving the verifier will cause the token exchange step to fail.

For a confidential client, still configure the Client authentication method such as <code>client_secret_basic</code> or another mechanism required by the Authorization Server. Never place the client secret in JavaScript or URLs. Configure secrets via a secret store/environment variables appropriate to the infrastructure.

### 5.3. Why Is Persisting the Authorization Request Important?

The authorization request and token request are separated by a browser round trip. In between, the Client must remember the verifier of the **exact** initiating request. Spring Security uses <code>AuthorizationRequestRepository</code> to hold this state; the default for OAuth2 Login is <code>HttpSessionOAuth2AuthorizationRequestRepository</code>.

When using a custom repository (for example, cookie-based or Redis-based), preserve all fields Spring Security uses to complete the flow, including <code>state</code> and **the attribute holding the verifier** of <code>OAuth2AuthorizationRequest</code>. Keeping only <code>redirectUri</code>, <code>state</code>, and additional parameters is usually insufficient. If the verifier is lost or overwritten between login attempts, the Authorization Server may return <code>invalid_grant</code>.

With multiple concurrent login tabs, distinguish authorization requests by <code>state</code> or an equivalent mechanism, avoiding using tab A's verifier to exchange a code from tab B. Do not persist verifiers long-term in a database when only temporary login-session storage is needed; clear single-use state when finished.

## 6. Distinguishing PKCE from `state`, `nonce`, and Client Secret

PKCE often appears alongside several other protection mechanisms in OAuth 2.0/OIDC, but they serve different roles.

| Mechanism | Verification Point | Primary Purpose |
|---|---|---|
| <code>state</code> | Client validates upon receiving authorization response | Binds the callback to the original request, preventing session mix-up and CSRF in the login flow |
| **PKCE** (<code>code_verifier</code>/<code>code_challenge</code>) | Authorization Server validates at token endpoint | Ensures only the Client holding the verifier can exchange the issued authorization code |
| OIDC <code>nonce</code> | OIDC Client validates inside ID token | Binds the ID token to the authentication request, mitigating token replay/injection |
| <code>client_secret</code> or private-key client authentication | Authorization Server authenticates Client at token endpoint | Proves the identity of a **confidential client** |
| HTTPS/TLS | When transmitting requests, callbacks, and tokens | Prevents eavesdropping/tampering on the wire |

A single OIDC Authorization Code Flow run can simultaneously have <code>state</code>, <code>nonce</code>, PKCE, and client authentication. Do not use PKCE to completely replace <code>state</code>, and do not confuse OIDC <code>nonce</code> with a PKCE verifier. Nor does PKCE guarantee an access token is used properly after issuance; tokens still require protection per application policy.

## 7. Common Integration Errors

| Symptom | Causes to Check | How to Handle |
|---|---|---|
| Authorization request lacks <code>code_challenge</code> | PKCE not enabled; Client config not recognized as public; custom resolver skipped customizer | Inspect registration/resolver config and outbound authorization endpoint request |
| <code>code_challenge_method=plain</code> or method missing | Client/server config mismatch; manually built request is wrong | Use <code>S256</code>, confirm the Authorization Server supports and requires this method |
| Token endpoint returns <code>invalid_grant</code> | Wrong/lost verifier, expired/used code, wrong redirect URI, or wrong Client | Check <code>state</code> correlation, authorization request storage, single-use code, and matching URI |
| Token endpoint returns <code>invalid_client</code> | Client authentication rejected | Check public/confidential registration and Client authentication method; do not immediately blame PKCE |
| Failures when running multiple login tabs | Verifier or authorization request from previous attempt was overwritten | Store requests independently and look up by state |
| S256 calculation differs from test vector | Hashed wrong input, non-URL-safe Base64, padding, or extra encoding | Use ASCII bytes, SHA-256, and unpadded Base64URL in the exact order |
| PKCE works locally but fails behind reverse proxy | Callback/base URL differs from registered URI, session/cookie not preserved | Check forwarded headers config, redirect URI, session affinity, or shared session store |
| Login fails after customizing <code>AuthorizationRequestRepository</code> | Repository dropped the attribute containing the verifier | Preserve the complete authorization request needed by the token processor |

### Inspecting the Flow Without Exposing the Verifier

When diagnosing errors in a development environment:

1. Confirm the authorization request includes <code>response_type=code</code>, <code>code_challenge</code>, and <code>code_challenge_method=S256</code>.
2. Confirm the request to the token endpoint includes the <code>code_verifier</code> **parameter**, without writing its value to logs, APM, metrics, or screenshots.
3. Confirm the token request corresponds to the right authorization request via state/session and redirect URI.
4. Verify the client registration at the Authorization Server requires/permits PKCE S256 and the client authentication method matching the app type.
5. Verify the code has not been used previously and check lifetimes of the session, cookie, and authorization request.

Never disable PKCE, downgrade to `plain`, skip `state` checks, or accept arbitrary redirect URIs just to bypass integration errors.

## 8. Secure Design for Real-World Deployment

**Generate randomness properly.** Each flow initiation creates an independent verifier from a CSPRNG; 32 random bytes encoded as unpadded Base64URL is an easy choice to implement correctly. Never reuse a fixed verifier per account, device, or login session.

**Keep the verifier out of the front channel.** Only the challenge travels in the authorization URL. The verifier must never appear in URLs, callback query parameters, local logs, analytics, or error pages. For a server-side Spring Boot Client, keep the verifier inside the authorization request stored securely on the server via session or an equivalent store.

**Use S256 and HTTPS.** The authorization endpoint, production callback, and token endpoint must all be configured with proper HTTPS. If a provider does not support S256, treat it as a compatibility/security issue rather than silently dropping PKCE.

**Bind and clean up state.** State and verifier must belong to the same authorization attempt. Upon success, failure, expiration, or cancellation, clear temporary state per application policy. An authorization code is a single-use value and must not be retried.

**Do not drop other controls.** PKCE prevents using an intercepted code without the verifier; it does not stop XSS, session hijacking, access token/refresh token theft, overly broad redirect URI configs, or a compromised Authorization Server. With OIDC, the Client must still validate the ID token for the right issuer, audience, validity window, and library-required conditions.

## 9. Scenario Questions and Practice Exercise

**Scenario A.** A mobile app sends <code>code_challenge_method=S256</code>, but in the token request sends the challenge as <code>code_verifier</code>. Will the server issue tokens?

**Answer:** No. The server computes S256 of the string sent as the verifier and gets a result that does not equal the stored challenge. The token request must contain the **original verifier**, not the challenge.

**Scenario B.** A Spring Boot application has a <code>client_secret</code>, so the dev team wants to drop PKCE. Is that reasonable?

**Answer:** The client secret authenticates the server-side application; PKCE binds the authorization code to the flow initiation. The two mechanisms mitigate different risks. Keep using S256 when supported by the Authorization Server.

**Scenario C.** A login in tab A generates verifier A; tab B generates verifier B. Tab A's callback uses verifier B. What happens?

**Answer:** The challenge bound to tab A's code was computed from verifier A. Using verifier B results in a mismatch and the token request is rejected. Look up the exact authorization request by state and isolate state across attempts.

**Recommended practice:** Generate a PKCE pair with <code>PkceUtil.newPair()</code> and verify that the verifier is 43 characters long and contains only valid characters. Use the RFC 7636 test vector to verify <code>toS256Challenge</code>. In a Spring Security OAuth2 Login application using a PKCE-capable Authorization Server, observe that the authorization request contains an S256 challenge, complete login, and confirm the token exchange uses the verifier without exposing the verifier in browser URLs. Finally, try clearing authorization request state in a test environment to observe why the token exchange fails.

## 10. Key Takeaways

- PKCE extends the **Authorization Code Flow** with a single-use random secret on the Client side.
- **Verifier** is kept secret until the token request; **challenge** is sent in the authorization request.
- **S256 = Base64URL(SHA-256(ASCII(verifier)))**, without padding. The protocol parameter method name is <code>S256</code>.
- In Spring Security, configure the OAuth2 Client appropriately and use an authorization request resolver/customizer so the framework retains the verifier and sends it during code exchange.
- PKCE protects the authorization code; <code>state</code>, OIDC <code>nonce</code>, client authentication, HTTPS, and session security still have their own responsibilities.
