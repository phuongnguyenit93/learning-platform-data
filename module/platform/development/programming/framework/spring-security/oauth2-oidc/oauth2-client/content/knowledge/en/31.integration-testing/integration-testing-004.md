# 31.4. Testing Consent Denial, Invalid State, and Duplicate Callbacks

## Lesson Objectives

In **Spring Security OAuth 2.0 / OpenID Connect (OIDC) Client**, a login flow does not consist solely of the happy path "user consents → receives authorization code → exchanges token → creates session." In real environments, a user may **deny consent**, the browser may return with a **wrong or missing `state`**, and a callback may be **sent twice** due to page refresh, client retries, proxies, stale tabs, or intentional replay.

These three scenarios deserve integration testing because they sit at the **boundary between the Authorization Server, browser, session, Spring Security OAuth2 Login filter, and authorized-client storage**.

For example:

~~~text
GET /oauth2/authorization/company
    -> 302 to OP with state=S1

Case A:
    GET /login/oauth2/code/company?error=access_denied&state=S1

Case B:
    GET /login/oauth2/code/company?code=C1&state=WRONG

Case C:
    GET /login/oauth2/code/company?code=C1&state=S1
    GET /login/oauth2/code/company?code=C1&state=S1
~~~

Not every case is expected to return the exact same HTTP status; the HTTP response depends on custom failure handlers and the `AuthenticationEntryPoint`. The critical invariants are:

- **Never create an unintended successful Authentication.**
- **Never use an authorization code/token from another transaction.**
- **Never skip state checks to "fix" callback failures.**
- **Never exchange the same authorization code twice in a standard transaction.**
- **Never retain or expose the wrong token/authorized client after a failure.**
- **Never accept a callback belonging to a different session.**

After this lesson, you will be able to:

1. Distinguish consent denial at the OP from API `403 Forbidden` and token-endpoint `invalid_grant`.
2. Simulate `error=access_denied` + valid `state` via MockMvc.
3. Extract the real `state` generated by Spring Security from the authorization redirect instead of hardcoding it.
4. Preserve `MockHttpSession` across login initiation and callback requests.
5. Test missing, wrong, expired, cross-session, and tampered `state` values.
6. Understand the role of `OAuth2AuthorizationRequestRepository` in callback correlation.
7. Test duplicate callbacks after either a successful or failed attempt.
8. Observe token endpoint invocation counts using a fake OpenID Provider/Authorization Server.
9. Construct a fake OIDC ID token/JWKS/nonce for happy-path integration tests when needed.
10. Verify the absence of Authentication and authorized-client persistence after failed callbacks.
11. Distinguish authorization-response errors from network errors and token response errors.
12. Write positive/negative tests for multi-session, multi-tab, and account-switching flows.
13. Avoid false positives caused by `oidcLogin()` or directly mocking `SecurityContext`.
14. Know what MockMvc can verify and the limitations of MockMvc without a real browser/OP.
15. Build repeatable, isolated tests with no dependency on a production AS and no credential leakage.

## 1. Three Error Branches That Must Be Distinguished

Starting from an Authorization Code + OIDC flow:

~~~mermaid
flowchart TD
    A["Portal creates Authorization Request and state"] --> B["Browser goes to Authorization Server"]
    B --> C{"Outcome at OP"}
    C -->|"User denies consent"| D["Callback error=access_denied + state"]
    C -->|"User approves"| E["Callback code + state"]
    D --> F["Spring OAuth2 Login failure"]
    E --> G{"Does state match saved request?"}
    G -->|"No"| H["Reject callback"]
    G -->|"Yes"| I["Exchange code at token endpoint"]
    I --> J{"Code/token valid?"}
    J -->|"No"| K["Authorization failure"]
    J -->|"Yes"| L["OIDC validation + Authentication"]
    L --> M["Authorized client/session saved"]
    M --> N["Callback resent"]
    N --> O["No pending request left / code already used"]
~~~

### 1.1. Consent Denial

The user or policy at the Authorization Server does not grant authorization. The AS typically redirects back to the client with an OAuth error response:

~~~http
GET /login/oauth2/code/company?error=access_denied&state=S1
~~~

There is no successful authorization code to exchange for tokens.

### 1.2. Invalid `state`

The browser sends a code, but `state` does not match the Authorization Request saved by the client:

~~~http
GET /login/oauth2/code/company?code=C1&state=OTHER
~~~

Spring Security must not use this response to create an Authentication.

### 1.3. Duplicate Callback

A callback has already been processed and is then sent again:

~~~text
Callback #1: code=C1, state=S1
Callback #2: code=C1, state=S1
~~~

After the successful callback, the pending Authorization Request has been consumed. The authorization code must also be single-use at the AS. The second callback must **not complete a new authorization**.

### 1.4. Do Not Collapse the Three Error Types into One Cause

| Scenario | Source of Issue | Key Check |
|---|---|---|
| `access_denied` | AS/OP did not grant authorization | Error response, state, failure flow |
| State mismatch | Correlation between browser request and callback failed | AuthorizationRequestRepository |
| Callback replay | Transaction/code was already processed | One-time request/code, token call count |
| `invalid_grant` at token endpoint | AS rejected code exchange or refresh | Token exchange failure |
| Wrong ID token issuer/nonce | OIDC validation | RP token validation |
| API `403` | Resource Server/domain authorization | Scope/role/owner/tenant |

A user denying consent **does not mean the Orders API rejected the access token**; the client may not even have received any access token yet.

## 2. Relevant Spring Security Components

| Component | Responsibility in the Flow |
|---|---|
| `ClientRegistrationRepository` | Configures OAuth client, AS endpoints, redirect URI |
| `DefaultOAuth2AuthorizationRequestResolver` | Creates Authorization Request, state, OIDC parameters |
| `OAuth2AuthorizationRequestRedirectFilter` | Handles `/oauth2/authorization/{registrationId}` and redirects |
| `OAuth2AuthorizationRequestRepository` | Stores pending callback request, typically in HttpSession |
| `OAuth2LoginAuthenticationFilter` | Processes callbacks at `/login/oauth2/code/*` |
| `AuthenticationManager` and OAuth2/OIDC providers | Token exchange, OIDC token validation, user authentication |
| `OAuth2AuthorizedClientRepository` / `Service` | Persists authorized client upon success |
| `AuthenticationSuccessHandler` | Redirects/handles login success |
| `AuthenticationFailureHandler` | Redirects/handles login failure |
| `SecurityContextRepository` | Manages SecurityContext/session per configuration |

### 2.1. Each Authorization Request Has Its Own State

When the browser calls:

~~~text
/oauth2/authorization/company
~~~

the resolver constructs a request that may contain:

~~~text
client_id=portal-test-client
response_type=code
scope=openid
redirect_uri=http://localhost/login/oauth2/code/company
state=S1
nonce=N1
~~~

Spring Security saves the request before redirecting so it can correlate the callback.

### 2.2. Callback Must Use the Same Session

With `HttpSessionOAuth2AuthorizationRequestRepository`, pending authorization data is bound to the HTTP session.

If you start the flow in session A and send the callback from session B, the callback has no matching pending request.

### 2.3. `state` Does Not Replace CSRF Tokens on All POSTs

OAuth state correlates the authorization response and mitigates login CSRF. It does not replace CSRF protection for Portal state-changing POST requests using a session cookie.

### 2.4. OIDC Also Has Nonce and Token Validation

Even when state is valid, a successful OIDC callback still requires the ID token to pass signature, issuer, audience, time, and nonce verification where applicable. This lesson focuses on **the three error branches**, while happy-path tests must satisfy those OIDC requirements.

## 3. Choosing the Test Level

### 3.1. Pure Unit Tests

You can call `OAuth2AuthorizationRequestRepository` directly to test load/remove semantics.

Well suited for custom repositories, TTL, one-time consumption, and concurrent states.

### 3.2. MockMvc Integration Tests

Runs the Servlet filter chain, initiates the flow, extracts the redirect state, and sends the callback with the same session.

Well suited for testing:

- `access_denied`.
- Wrong state/missing state.
- Failure handler.
- No session Authentication created.
- One-time callback handling.

### 3.3. MockMvc + Fake Authorization Server

Adds tests for the HTTP token endpoint, JWKS/ID token, and a successful callback followed by replay.

Well suited for verifying:

- Code exchange happens only once.
- ID token validation.
- Authorized client is persisted.
- Duplicate callbacks do not exchange the token a second time.

### 3.4. Browser/E2E

Real browsers also involve cookies, SameSite, reverse proxies, external origins, navigation, and user consent UI. MockMvc does not fully simulate these factors on its own.

### 3.5. Choosing the Right Tool for Each Question

| Question | Test Level |
|---|---|
| Does access_denied trigger login failure? | MockMvc |
| Is a callback with wrong state rejected? | MockMvc |
| Is state single-use? | MockMvc/repository test |
| Is a code exchanged for tokens only once? | MockMvc + fake AS |
| Does the OP issue a valid ID token and create the principal? | MockMvc + JWKS/ID token test |
| Do SameSite cookies work on a real browser? | Browser/E2E |
| Does the real AS display the consent screen properly? | Staging E2E per policy |
| Does the API reject wrong-audience tokens? | Separate Resource Server test |

### 4.1. No Real AS Needed for Error-Only Tests

If a test only sends `error=access_denied` or a wrong `state`, Spring Security must reject it **before calling the token endpoint**.

You can use a fake registration with Authorization/Token/JWKS URIs under `example.test` without running an actual server, provided configuration does not trigger network discovery at startup.

### 4.2. Never Send Production Credentials to a Fake AS

Client ID, client secret, code, ID token, and access token all use synthetic data.

### 4.3. Internet-Independent Tests

Every negative integration test should run without connectivity to a production OP or the Internet.

## 5. Setting Up a Test ClientRegistration

A fake OIDC registration:

~~~java
import org.springframework.security.oauth2.client.registration.ClientRegistration;
import org.springframework.security.oauth2.core.AuthorizationGrantType;
import org.springframework.security.oauth2.core.ClientAuthenticationMethod;

public final class OAuthTestRegistrations {

    private OAuthTestRegistrations() {}

    public static ClientRegistration company() {
        return ClientRegistration
                .withRegistrationId("company")
                .clientId("portal-test-client")
                .clientSecret("test-only-secret")
                .clientAuthenticationMethod(
                        ClientAuthenticationMethod.CLIENT_SECRET_BASIC)
                .authorizationGrantType(
                        AuthorizationGrantType.AUTHORIZATION_CODE)
                .authorizationUri(
                        "https://op.example.test/authorize")
                .tokenUri(
                        "https://op.example.test/token")
                .jwkSetUri(
                        "https://op.example.test/jwks")
                .issuerUri(
                        "https://op.example.test")
                .redirectUri(
                        "{baseUrl}/login/oauth2/code/{registrationId}")
                .scope("openid", "profile")
                .clientName("Company Test OP")
                .build();
    }
}
~~~

### 5.1. Why Not Use `issuer-uri` Discovery from a Real OP?

The test aims to verify client callback handling, not network discovery or an external provider's availability.

Using the builder with fake endpoints sets up the registration without calling OP metadata.

### 5.2. OIDC Scope

Because the registration uses `openid`, any happy path (if present) must supply a valid ID token, not just access token JSON.

### 5.3. Redirect Template

`{baseUrl}/login/oauth2/code/{registrationId}` is the standard default callback for Spring Security OAuth2 Login.

In tests, `baseUrl` may be `http://localhost` created by `MockHttpServletRequest`. The actual callback path must match the registration.

### 5.4. Never Reuse Registrations from Other Producers/Tests

Each test case should have a well-defined registration ID and its own fake OP to avoid leaking state/authorized clients across tests.

## 6. Configuring SecurityFilterChain for Negative Integration Tests

You can use a **test-only** custom failure handler to turn OAuth2 error codes into clear assertions.

### 6.1. Why a Custom Failure Handler?

Default login failure behavior usually redirects the browser to `/login?error`. The response may be 302 rather than 401.

If a test only asserts 302, it is hard to tell whether the failure was `access_denied`, a wrong `state`, or a different exception.

The test handler below returns 401 and a header containing a **normalized error code**, without logging raw tokens or untrusted error descriptions.

### 6.2. Illustrative Configuration

~~~java
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.core.OAuth2AuthenticationException;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class CallbackTestSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {

        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/", "/error", "/login")
                        .permitAll()
                        .anyRequest().authenticated())
                .oauth2Login(oauth2 -> oauth2
                        .failureHandler((request, response, exception) -> {
                            String code =
                                    "authentication_failed";

                            if (exception
                                    instanceof OAuth2AuthenticationException e) {
                                code = e.getError().getErrorCode();
                            }

                            // Strictly for test assertions.
                            response.setHeader(
                                    "X-Test-OAuth-Error", code);
                            response.setStatus(
                                    HttpServletResponse.SC_UNAUTHORIZED);
                        }))
                .build();
    }
}
~~~

### 6.3. How to Use It in Tests

Use `@SpringBootTest` + `@AutoConfigureMockMvc` and load this configuration in the test context alongside a `ClientRegistrationRepository` containing the fake registration.

Never import the test-only failure handler into production. A production application should use a safe redirect/flash message with a correlation ID rather than exposing internal error details to the browser.

### 6.4. Never Trust `error_description` from the Callback

`error_description` on an HTTP callback is browser-traversed input. Never render the raw value in HTML/logs without sanitization, and never use it to make role or redirect URL decisions.

## 7. Complete Test Context for Error Callbacks

A test configuration does not need the entire application:

~~~java
import org.springframework.boot.SpringBootConfiguration;
import org.springframework.boot.autoconfigure.EnableAutoConfiguration;
import org.springframework.context.annotation.Bean;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.registration.InMemoryClientRegistrationRepository;
import org.springframework.security.oauth2.core.OAuth2AuthenticationException;
import org.springframework.security.web.SecurityFilterChain;

import jakarta.servlet.http.HttpServletResponse;

@SpringBootConfiguration
@EnableAutoConfiguration
public class OAuthErrorTestApplication {

    @Bean
    ClientRegistrationRepository clientRegistrations() {
        return new InMemoryClientRegistrationRepository(
                OAuthTestRegistrations.company());
    }

    @Bean
    SecurityFilterChain testSecurity(HttpSecurity http)
            throws Exception {

        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/", "/login", "/error")
                        .permitAll()
                        .anyRequest().authenticated())
                .oauth2Login(oauth2 -> oauth2
                        .failureHandler((request, response, exception) -> {
                            String code =
                                    "authentication_failed";

                            if (exception
                                    instanceof OAuth2AuthenticationException e) {
                                code = e.getError().getErrorCode();
                            }

                            response.setHeader(
                                    "X-Test-OAuth-Error", code);
                            response.setStatus(
                                    HttpServletResponse.SC_UNAUTHORIZED);
                        }))
                .build();
    }
}
~~~

Adjust class/package names per your project; you can place the test configuration as a nested static class in test sources. Illustrative classes like `OAuthTestRegistrations` must reside in test sources or be imported.

### 7.1. Why Is No Controller Needed for the Authorization Endpoint?

`OAuth2AuthorizationRequestRedirectFilter` intercepts `/oauth2/authorization/company` before MVC controllers and issues the redirect.

### 7.2. Why Is No Controller Needed for the Callback?

`OAuth2LoginAuthenticationFilter` handles `/login/oauth2/code/company` via the filter chain.

### 7.3. Do Not Skip Spring Security Filters

Use `@AutoConfigureMockMvc` with filters enabled. If building MockMvc manually via `MockMvcBuilders`, apply `springSecurity()`/the proper chain.

### 7.4. Narrow or Broad Context?

If your application has complex security configuration, this test can use a test-specific configuration to isolate error behavior. Additionally, maintain another set of integration tests loading actual production config to ensure system wiring matches expectations.

## 8. Starting the Authorization Flow and Capturing the Real State

**Do not hardcode `state=S1` in integration tests** when using the real resolver/repository. Capture the state Spring Security just generated.

### 8.1. `beginLogin()` Helper

~~~java
import org.springframework.mock.web.MockHttpSession;
import org.springframework.test.web.servlet.MvcResult;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.web.util.UriComponentsBuilder;

import static org.springframework.test.web.servlet.request
        .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.status;

record LoginAttempt(
        MockHttpSession session,
        String state,
        String nonce,
        String authorizationRedirect) {
}

LoginAttempt beginLogin(MockMvc mvc) throws Exception {
    MvcResult result = mvc.perform(
                    get("/oauth2/authorization/company"))
            .andExpect(status().is3xxRedirection())
            .andReturn();

    String redirect = result.getResponse().getRedirectedUrl();

    var query = UriComponentsBuilder
            .fromUriString(redirect)
            .build()
            .getQueryParams();

    String state = query.getFirst("state");
    String nonce = query.getFirst("nonce");

    MockHttpSession session =
            (MockHttpSession) result.getRequest().getSession(false);

    org.assertj.core.api.Assertions.assertThat(state)
            .isNotBlank();
    org.assertj.core.api.Assertions.assertThat(session)
            .isNotNull();

    return new LoginAttempt(
            session, state, nonce, redirect);
}
~~~

### 8.2. Why Preserve `MockHttpSession`?

The default Authorization Request repository is session-backed. If the callback uses a fresh session, you are only testing "authorization request not found," not fully testing the case where the user denies consent with a **valid state**.

### 8.3. `nonce` for Happy-Path OIDC Tests

If scope includes `openid`, the authorization redirect typically includes a nonce depending on configuration. When the fake OP issues an ID token in a positive test, the nonce claim must match the value the OP saw in the authorization request.

### 8.4. Redirect URI Is Data Worth Observing

Besides state, you can assert:

~~~text
response_type=code
client_id=portal-test-client
redirect_uri=...
scope contains openid
state is non-blank
~~~

A state mismatch test is meaningful when a real Authorization Request was actually created from the right registration and stored in the same session.

### 8.5. Use a Query Parser Instead of Regex

State may contain characters needing URL encoding. Use a proper URI parser or decoder instead of slicing strings with fixed-offset `substring`.

## 9. Test A — Consent Denied with Valid State

A user clicks "Deny" on the consent screen or the AS decides not to grant authorization. The AS returns an error response:

~~~http
GET /login/oauth2/code/company?error=access_denied&state=STATE
~~~

### 9.1. Testing with MockMvc

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request
        .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.status;

@SpringBootTest(classes = OAuthErrorTestApplication.class)
@AutoConfigureMockMvc
class ConsentDenialIntegrationTest {

    @Autowired
    MockMvc mvc;

    @Test
    void userDenyingConsentFailsWithoutLogin()
            throws Exception {

        LoginAttempt pending = beginLogin(mvc);

        mvc.perform(get("/login/oauth2/code/company")
                        .session(pending.session())
                        .param("error", "access_denied")
                        .param("state", pending.state()))
                .andExpect(status().isUnauthorized())
                .andExpect(header().string(
                        "X-Test-OAuth-Error", "access_denied"));
    }
}
~~~

Place the `beginLogin(...)` helper and `LoginAttempt` record from the previous section into the test class or an appropriate test utility.

### 9.2. Why Assert the `access_denied` Code?

The AS returns an error code per the OAuth authorization response spec. Spring Security treats the callback as an authentication failure with no successful authorization code to exchange for tokens.

### 9.3. Do Not Insist HTTP Status Must Always Be 401

The example's test-only handler chose to return 401. In production, the default or a custom failure handler might return 302 to a login page with a message, or another response per UX.

**Assert the status matching the handler your application actually configures.**

### 9.4. Do Not Treat User Refusal as an "Unexpected" Application Exception

This is a normal business branch: the user or AS has the right to deny consent. The UI should offer a way to go back or retry with different permissions without causing an infinite redirect loop.

## 10. Testing Consent Denial Creates No Authenticated Session

After denial, the browser may still retain the HttpSession that held the prior pending Authorization Request. What matters is ensuring **no successful user Authentication is created**.

### 10.1. Accessing a Protected Resource After Failure

~~~java
LoginAttempt pending = beginLogin(mvc);

mvc.perform(get("/login/oauth2/code/company")
                .session(pending.session())
                .param("error", "access_denied")
                .param("state", pending.state()))
        .andExpect(status().isUnauthorized());

mvc.perform(get("/private")
                .session(pending.session()))
        .andExpect(status().is3xxRedirection());
~~~

The example assumes `/private` is protected with `authenticated()` and the test's browser entry point redirects to login. If your test chain returns 401 instead of redirecting, adjust the assertion per policy.

### 10.2. Session Still Existing Does Not Mean Login Succeeded

The fact that `MockHttpSession` has not been invalidated does not prove an Authentication exists. A session may exist to hold saved requests, CSRF tokens, or error attributes.

### 10.3. Never Save `OidcUser` into the Session on Denial

Never invoke custom success logic when a callback carries an error response. Failure handlers must never create a new `OAuth2AuthorizedClient`.

### 10.4. Checking the Authorized Client Store

If the application uses `OAuth2AuthorizedClientService`, you can assert:

~~~java
OAuth2AuthorizedClient client =
        authorizedClientService.loadAuthorizedClient(
                "company", "alice");

assertThat(client).isNull();
~~~

This is meaningful only if the test setup uses **the exact service/repository where the production flow stores tokens** and `alice` is the expected principal key. With a session repository, inspect the corresponding session store instead of mistakenly checking an in-memory service not wired into the filter.

## 11. Testing Consent Denial Never Calls the Token Endpoint

When the callback contains `error=access_denied`, **there is no successful authorization code** to send to the token endpoint.

In tests with a fake AS, set up a counter:

~~~java
AtomicInteger tokenEndpointCalls =
        new AtomicInteger();
~~~

After the denied callback:

~~~java
assertThat(tokenEndpointCalls.get()).isZero();
~~~

### 11.1. Never Test Against a Real Token Endpoint

Use a fake HTTP server and count requests to `/token`; never send production client secrets or tokens.

### 11.2. Why Check the Request Count?

A serious bug could still attempt a code exchange despite an error authorization response. Negative tests should catch unintended token endpoint calls.

### 11.3. Fake OP Must Distinguish Endpoints

~~~text
/authorize  -> redirect created by client; browser doesn't actually hit fake OP
/token      -> fake server counts token requests
/jwks       -> fake server returns public keys for OIDC happy path
/userinfo   -> only if the flow uses UserInfo
~~~

For denial tests, inspecting the authorization redirect and sending the callback directly is usually enough; there is no need to implement a real consent UI.

## 12. Consent Denial Differs from Missing Scope

Two cases that are often confused:

### 12.1. Consent Refusal

~~~text
Authorization endpoint response:
  error=access_denied
  state=S1
~~~

No successful authorization result exists.

### 12.2. Token with Fewer Scopes Than Expected

The AS may return a successful token response with scopes trimmed per policy (depending on profile). The client/API must then check granted scopes before performing actions.

### 12.3. API Returns 403

If the Portal already holds an access token but the Orders API denies `orders.write`, that is resource authorization, **not a consent denial callback**.

### 12.4. `access_denied` Can Have Multiple Causes

An AS may return `access_denied` because the user declined, policy blocked the client, admin consent has not been granted, or other reasons. The client should not definitively claim "the user clicked Deny" without trustworthy information.

## 13. Test B — Invalid State

Start a valid flow:

~~~text
Browser -> /oauth2/authorization/company
  -> state = S1
  -> session holds pending Authorization Request S1
~~~

Then the callback is tampered with:

~~~http
GET /login/oauth2/code/company?code=C1&state=ATTACKER_STATE
~~~

### 13.1. Testing with MockMvc

~~~java
@Test
void rejectsCallbackWithWrongState() throws Exception {
    LoginAttempt pending = beginLogin(mvc);

    mvc.perform(get("/login/oauth2/code/company")
                    .session(pending.session())
                    .param("code", "fake-code")
                    .param("state", "totally-wrong-state"))
            .andExpect(status().isUnauthorized())
            .andExpect(header().exists("X-Test-OAuth-Error"));
}
~~~

### 13.2. Why Not Hardcode a Single Error Code?

Depending on Spring Security version and execution branch, a mismatched callback state may surface as an OAuth2 authentication error such as `authorization_request_not_found` or another code.

The invariants to test are:

- Does not succeed.
- Zero token endpoint exchanges.
- No new authorized client.
- No Authentication created from the callback.

If a product contract demands an exact error code, assert that code only after pinning the version/config and verifying the error mapping.

### 13.3. State Mismatch Must Be Caught Before Token Exchange

Crucially, never send `fake-code` to the configured token endpoint when no matching pending Authorization Request exists.

### 13.4. Do Not Trust the Redirect URI Path Alone

`/login/oauth2/code/company` handles routing, not proof that the browser initiated a valid request. State correlation is an essential layer of protection.

## 14. Invalid State May Not Delete the Valid Pending Request

With a session-backed request repository, a callback with a wrong state typically **cannot find a matching request**.

That does not mean every implementation automatically removes the pending request with state S1.

### 14.1. Understand Repository Behavior

A repository might:

- Keep S1 because the incoming state did not match.
- Remove S1 via custom failure cleanup.
- Enforce a TTL and cap on pending requests.
- Support one or multiple concurrent requests depending on implementation.

Do not write tests assuming state mismatch always consumes the original request.

### 14.2. What If S1 Is Still Pending?

A subsequent valid S1 callback may resume the flow depending on the state store/session/AS code validity.

That is why it is important to test **the policy for handling bad callbacks**, rather than merely checking a single HTTP 401 response.

### 14.3. Avoid Creating an Overly Wide Replay Window

Pending requests need short TTLs and proper cleanup. A bad callback must never cause state to be retained indefinitely or leak into another user/session.

### 14.4. Never "Fall Back" to Another State in the Session

If state is not found, never pick the latest pending request or a registration with the same client ID and continue. That breaks correlation and can introduce login CSRF/mix-up vulnerabilities.

## 15. Testing Missing, Empty, or Duplicated State Query Parameters

Besides a wrong state, a callback might arrive as:

~~~text
?code=C1
?code=C1&state=
?code=C1&state=S1&state=S2
~~~

### 15.1. Missing State

~~~java
@Test
void rejectsCallbackWithoutState() throws Exception {
    LoginAttempt pending = beginLogin(mvc);

    mvc.perform(get("/login/oauth2/code/company")
                    .session(pending.session())
                    .param("code", "fake-code"))
            .andExpect(status().isUnauthorized());
}
~~~

### 15.2. Empty State

~~~java
mvc.perform(get("/login/oauth2/code/company")
                .session(pending.session())
                .param("code", "fake-code")
                .param("state", ""))
        .andExpect(status().isUnauthorized());
~~~

### 15.3. Duplicated State Parameters

~~~java
mvc.perform(get("/login/oauth2/code/company")
                .session(pending.session())
                .param("code", "fake-code")
                .param("state", pending.state(), "different-state"))
        .andExpect(status().isUnauthorized());
~~~

Exact parsing behavior for duplicated HTTP parameters depends on the framework/container/version; this test input captures the application's policy. **Never tolerate parameter ambiguity** where security filters and business logic interpret state differently.

### 15.4. Encoding Edge Cases

You can test state containing URL encoding, whitespace, UTF-8, or oversized inputs if the app uses custom parsing/proxies. Never use a homemade regex to decide whether a state is valid before Spring Security correlates the authorization request.

## 16. Test C — Callback from a Different Session

An attacker may try to use session A's callback inside session B.

~~~text
Session A:
  pending state=S1

Session B:
  no request S1

Callback on B:
  code=C1, state=S1
~~~

### 16.1. Test

~~~java
import org.springframework.mock.web.MockHttpSession;

@Test
void rejectsCallbackFromDifferentSession() throws Exception {
    LoginAttempt pending = beginLogin(mvc);

    MockHttpSession anotherSession =
            new MockHttpSession();

    mvc.perform(get("/login/oauth2/code/company")
                    .session(anotherSession)
                    .param("code", "fake-code")
                    .param("state", pending.state()))
            .andExpect(status().isUnauthorized());
}
~~~

### 16.2. Why Test This Case?

State is not merely a random string; it must also be bound to the pending Authorization Request of the exact browser/session.

### 16.3. Never Search All Sessions by State

When session B's callback has no request S1, the backend must never scan all sessions for that state and create an Authentication on B.

### 16.4. Cookies and SameSite

MockMvc can simulate sessions, but does not fully simulate browser cookie policies. Verify Secure/HttpOnly/SameSite/forwarded headers in browser/E2E tests when required.

## 17. Test D — Duplicate Callback After Consent Denial

Even an error callback can be resent by a browser.

~~~text
Begin:
  pending state = S1

Callback #1:
  error=access_denied&state=S1

Callback #2:
  error=access_denied&state=S1
~~~

### 17.1. Expectations

- The first attempt fails due to `access_denied`.
- The second attempt must not "reopen" the transaction.
- No tokens exchanged.
- No Authentication or authorized client created.

### 17.2. Example

~~~java
@Test
void repeatedDenialDoesNotCreateLogin()
        throws Exception {

    LoginAttempt pending = beginLogin(mvc);

    mvc.perform(get("/login/oauth2/code/company")
                    .session(pending.session())
                    .param("error", "access_denied")
                    .param("state", pending.state()))
            .andExpect(status().isUnauthorized());

    mvc.perform(get("/login/oauth2/code/company")
                    .session(pending.session())
                    .param("error", "access_denied")
                    .param("state", pending.state()))
            .andExpect(status().isUnauthorized())
            .andExpect(header().exists("X-Test-OAuth-Error"));
}
~~~

### 17.3. The Second Error Code May Differ

The first attempt reports `access_denied`; the second may report a missing authorization request because S1 was already removed. Tests should not insist on `access_denied` for both attempts unless that is a specific contract.

### 17.4. Limitation of This Test

It tests duplicate **failure callbacks**. To prove a **successful** callback is not processed twice and the token endpoint is called only once, you need the happy-path integration setup in the following sections.

## 18. Why Does a Successful Callback Need a Fake OP?

A callback:

~~~text
code=C1&state=S1
~~~

with a valid state causes Spring Security to exchange the code at the token endpoint. If `token-uri` is `https://op.example.test/token` without a fake server, the test will fail with a network error and **never reach the happy path**.

### 18.1. Do Not Fake Success with `oidcLogin()`

`oidcLogin()` only sets a mock OIDC principal on the MockMvc request; it does not run:

- The OAuth2 Login callback filter.
- State correlation.
- Authorization code token exchange.
- ID token verification.
- Authorized-client persistence.

Using it to test callback replay produces a **false positive**.

### 18.2. Do Not Bypass AuthenticationManager

If you mock `AuthenticationManager` to always return a successful Authentication without running the OIDC validator, you may test part of the filter wiring, yet you do not prove ID token validation. Clearly document the scope if choosing that mock level.

### 18.3. Minimum Fake OP Support

~~~text
GET /jwks
  -> public RSA JWK

POST /token
  -> JSON access_token + id_token signed with test private key

GET /userinfo
  -> only if the OIDC flow is configured to require UserInfo
~~~

No fake consent UI is required; MockMvc can submit the browser callback directly.

## 19. Fake Authorization Server and Request Counting

You can use WireMock or MockWebServer. Example structure of a fake OP with a test HTTP server:

~~~text
Fake OP:
  issuer = http://127.0.0.1:<dynamic-port>
  authorization endpoint = issuer + /authorize
  token endpoint = issuer + /token
  JWKS = issuer + /jwks

Test shared state:
  tokenCalls: AtomicInteger
  expectedCode: "code-first"
  expectedNonce: captured from Authorization Request
  idToken: JWT signed RS256 by test key
~~~

### 19.1. Valid Token Response

~~~json
{
  "access_token": "test-access-A1",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "openid",
  "id_token": "SIGNED_TEST_ID_TOKEN"
}
~~~

For Spring Security OIDC Client to accept the response, `id_token` must be a validly signed test JWT whose claims satisfy client registration and nonce checks.

### 19.2. Each Test Should Have Isolated Server State

Never share an unreset/unisolated `tokenCalls` counter or static mock response across tests running in parallel.

### 19.3. Authorization Endpoint Need Not Receive HTTP in MockMvc

Spring Security generates the redirect URL; MockMvc does not automatically follow redirects to the fake OP. The test reads the redirect, extracts `state`/`nonce`, and sends a synthetic callback as if the browser returned.

### 19.4. Dynamic Port

The fake server should bind port 0 (random) and construct `ClientRegistration` with the resulting URL to prevent port collisions between test runs.

### 19.5. Never Point Fake Issuer/JWKS at a Production OP

This is a test identity provider using an ephemeral private key and HTTP localhost. Production requires separate HTTPS/trust policies.

## 20. Building an ID Token Signed with a Test RSA Key

For an OIDC happy path, access token JSON **is not enough**; Spring Security requires a valid ID token.

You can use Nimbus JOSE JWT (usually a transitive dependency of Spring Security OAuth2 JOSE).

### 20.1. Generating an RSA Key

~~~java
import com.nimbusds.jose.jwk.RSAKey;
import com.nimbusds.jose.jwk.gen.RSAKeyGenerator;

RSAKey testRsaKey = new RSAKeyGenerator(2048)
        .keyID("test-key-1")
        .generate();
~~~

### 20.2. Public JWKS

~~~java
import com.nimbusds.jose.jwk.JWKSet;

String jwksJson =
        new JWKSet(testRsaKey.toPublicJWK())
                .toString();
~~~

Fake OP `GET /jwks` returns JSON with the public RSA key; never serve the private key via JWKS.

### 20.3. Signing the ID Token

~~~java
import java.time.Instant;
import java.util.Date;

import com.nimbusds.jose.JWSAlgorithm;
import com.nimbusds.jose.JWSHeader;
import com.nimbusds.jose.crypto.RSASSASigner;
import com.nimbusds.jwt.JWTClaimsSet;
import com.nimbusds.jwt.SignedJWT;

static String signIdToken(
        RSAKey key,
        String issuer,
        String clientId,
        String nonce) throws Exception {

    Instant now = Instant.now();

    JWTClaimsSet claims = new JWTClaimsSet.Builder()
            .issuer(issuer)
            .subject("alice-123")
            .audience(clientId)
            .issueTime(Date.from(now))
            .expirationTime(Date.from(now.plusSeconds(600)))
            .claim("nonce", nonce)
            .build();

    JWSHeader header = new JWSHeader.Builder(
            JWSAlgorithm.RS256)
            .keyID(key.getKeyID())
            .build();

    SignedJWT jwt = new SignedJWT(header, claims);
    jwt.sign(new RSASSASigner(key.toPrivateKey()));

    return jwt.serialize();
}
~~~

### 20.4. Nonce Must Match the Browser-Observed Request

Depending on implementation, Spring Security may send a transformed/hashed nonce in the authorization redirect. When the fake OP builds the ID token, **echo the exact nonce value the OP received in the authorization request**, rather than inventing a different random nonce.

### 20.5. Issuer and Audience

- `iss`: must match the ClientRegistration's expected issuer.
- `aud`: must contain the test RP's client ID.
- `exp` and `iat`: valid per clock and policy.
- `sub`: present and matches profile.
- `nonce`: matches the authentication transaction when required.

### 20.6. UserInfo

If the registration only requests `openid` and configures no UserInfo endpoint, the happy path can avoid an extra HTTP UserInfo call. If UserInfo is required, the fake server must return contract-compliant claims, including a `sub` matching the ID token per OIDC rules.

### 20.7. Do Not Use Test JWTs to Claim Real OP Compatibility

A valid signature from a test key only proves Spring Security can verify a test ID token against a test JWKS. It does not replace verifying production issuer/keys/metadata configuration.

## 21. Orchestrating the Fake Server: HTTP Token Endpoint

A test double may receive requests like:

~~~http
POST /token HTTP/1.1
Host: 127.0.0.1:<port>
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <test-client-credentials>

grant_type=authorization_code&code=code-first&redirect_uri=...
~~~

On the first request with a valid code, return access token/ID token. On a second request with the same code, return an error:

~~~http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"invalid_grant"}
~~~

### 21.1. Counter

~~~java
AtomicInteger tokenEndpointCalls = new AtomicInteger();

int call = tokenEndpointCalls.incrementAndGet();
~~~

### 21.2. Code Must Be Single-Use

The fake AS should track code redemption state:

~~~text
code-first -> unused
First POST  -> used, return token response
Second POST -> invalid_grant
~~~

### 21.3. Why Should the Fake AS Guard Against Code Replay?

Suppose a client bug causes the token endpoint to be called a second time. If the fake AS returns tokens on every request, tests might fail to catch improper code redemption.

### 21.4. Checking Client Authentication

For a confidential client using `client_secret_basic`, the fake endpoint can check the Authorization Basic header. Never log the raw client secret or header in test output.

### 21.5. Token Response Must Not Return an ID Token for the Wrong Audience

If the ID token targets another client, the happy-path callback will fail OIDC validation. Establish a valid fixture first before testing replay so you don't confuse root causes.

## 22. Test E — Successful Callback Processed Only Once

Once the fake OP/JWKS are configured properly, the test proceeds:

1. Start the Authorization Request.
2. Extract state and nonce.
3. Fake OP prepares a valid ID token with that nonce.
4. Send callback `code=code-first`, `state=S1`.
5. Assert authentication success and/or redirect per success handler.
6. Read `MockHttpSession` after success.
7. Resend **the same code and state**.
8. Assert the second callback is rejected.
9. Assert the token endpoint saw **only one** code redemption.
10. Assert the authorized client was neither recreated nor altered by the replay.

### 22.1. Test Skeleton

~~~java
@Test
void successfulCallbackIsNotProcessedTwice()
        throws Exception {

    LoginAttempt pending = beginLogin(mvc);

    // Fake OP prepares an id_token signed with test key,
    // right issuer/audience, and nonce = pending.nonce().
    fakeOp.prepareSuccessfulCode(
            "code-first",
            pending.nonce(),
            "alice-123");

    MvcResult first = mvc.perform(
                    get("/login/oauth2/code/company")
                            .session(pending.session())
                            .param("code", "code-first")
                            .param("state", pending.state()))
            .andExpect(status().is3xxRedirection())
            .andReturn();

    assertThat(fakeOp.tokenCalls()).isEqualTo(1);

    MockHttpSession activeSession =
            (MockHttpSession) first.getRequest()
                    .getSession(false);

    mvc.perform(
                    get("/login/oauth2/code/company")
                            .session(activeSession)
                            .param("code", "code-first")
                            .param("state", pending.state()))
            .andExpect(status().isUnauthorized());

    assertThat(fakeOp.tokenCalls()).isEqualTo(1);
}
~~~

`fakeOp.prepareSuccessfulCode(...)` and `fakeOp.tokenCalls()` are **application-implemented test harness APIs**, not built-in Spring Security classes. They are described in Sections 19–21.

### 22.2. Why Capture the Session After Success?

Spring Security may rotate the session ID for session-fixation protection and store the SecurityContext in the updated session.

In MockMvc, keep the exact session state for the replay request; never spin up a separate session and mistake it for testing a duplicate callback from the same browser.

### 22.3. A Success Redirect Alone Is Not Enough

A 302 can be either a success redirect or a failure redirect depending on handlers. In positive tests, assert the Location/success marker or authenticated user/session per your specific configuration.

If your test failure handler returns 401, a successful callback redirects 302 by default; you should still add a positive assertion to rule out false positives from another redirect.

### 22.4. The Counter Is Direct Proof

If replay is blocked **before token exchange**, the fake AS receives only one request at the token endpoint.

### 22.5. What If the Counter Becomes Two?

Either the pending Authorization Request was not consumed properly, or the test setup created a second transaction. Distinguish client correlation bugs from fake AS behavior.

### 22.6. Token Response on Second Attempt

If a bug lets token exchange happen twice, the fake AS must return `invalid_grant` on the second attempt. Even then, the callback must not create a new Authentication.

## 23. After Replay, the Authorized Client Must Remain Unchanged

Duplicate callbacks are not just an HTTP status issue; they can affect authorized-client storage.

### 23.1. Checking the Store

With `OAuth2AuthorizedClientService` and the matching principal key:

~~~java
OAuth2AuthorizedClient beforeReplay =
        service.loadAuthorizedClient(
                "company", "alice-123");

assertThat(beforeReplay).isNotNull();

performDuplicateCallback();

OAuth2AuthorizedClient afterReplay =
        service.loadAuthorizedClient(
                "company", "alice-123");

assertThat(afterReplay.getAccessToken().getTokenValue())
        .isEqualTo(
                beforeReplay.getAccessToken().getTokenValue());
~~~

`performDuplicateCallback()` is only an illustrative helper; the test must use the proper session/callback as shown in Section 22.

### 23.2. Stored in Session or Service?

If the app uses `HttpSessionOAuth2AuthorizedClientRepository`, inspect where it actually persists tokens. Never assert against an `InMemoryOAuth2AuthorizedClientService` that the filter doesn't use and conclude no token was saved.

### 23.3. Do Not Unintentionally Wipe an Authenticated Session on Bad Replay

An invalid duplicate callback after login may invoke the failure handler. Define your policy clearly: keep the existing authenticated session or log out for safety.

Do not assume the failure handler for the second callback automatically preserves the first login; that is an application design choice to implement and test explicitly.

### 23.4. Prevent Login Sessions from Being Swapped to Another Identity

If a replay or mix-up callback produces a different Authentication, that is a security bug. Tests should verify principal `iss` + `sub` before and after per policy.

## 24. Code Replay and State Replay Are Two Independent Defenses

### 24.1. State Correlation

The client must hold an Authorization Request matching the incoming state/session.

### 24.2. Single-Use Authorization Code

The Authorization Server must never exchange an authorization code for tokens more than once.

### 24.3. When State Is Missing

The client should reject **before the token endpoint**. Thus, single-use codes do not substitute for state validation.

### 24.4. When State Is Improperly Reused

If a custom repository allows reusing state/pending transactions, AS single-use codes still mitigate risk, yet client logic remains broken.

### 24.5. Second Callback with a Different Code but Old State

An attacker may try:

~~~text
First:  code=C1, state=S1
Second: code=C2, state=S1
~~~

Even though code C2 is fresh, pending request S1 was already consumed after the first callback. The client must disallow the second response using the stale state.

## 25. Test F — Wrong-State Callback Performs Zero Token Exchanges

You need a fake OP token counter to prove this behavior.

~~~java
@Test
void invalidStateNeverReachesTokenEndpoint()
        throws Exception {

    LoginAttempt pending = beginLogin(mvc);

    int before = fakeOp.tokenCalls();

    mvc.perform(
                    get("/login/oauth2/code/company")
                            .session(pending.session())
                            .param("code", "code-first")
                            .param("state", "wrong-state"))
            .andExpect(status().isUnauthorized());

    assertThat(fakeOp.tokenCalls()).isEqualTo(before);
}
~~~

### 25.1. Why Not Assert Only 401?

A broken implementation might send the code to the token endpoint and fail afterward. The final status would still be 401, yet the secret/code crossed the wrong boundary.

### 25.2. No Real Code Needed to Test Wrong State

Because state must be rejected before token exchange, the code can be any dummy fixture and the fake server count remains zero.

### 25.3. Wrong Registration and State

You can also send the response to another registration's callback path:

~~~text
Begin /oauth2/authorization/company
Callback /login/oauth2/code/other-client?code=C1&state=S1
~~~

Depending on the Spring Security implementation, the registration is determined from the stored Authorization Request rather than just the URL suffix. Tests should confirm the callback/mapping policy **prevents mix-up** and never calls an unintended token endpoint/provider.

### 25.4. Do Not Infer Mix-Up Protection from the Callback Path Alone

State and OIDC issuer/audience/nonce validation remain necessary checks. When supporting multiple Authorization Servers, AS issuer identification is also needed if supported by the protocol/profile/framework.

## 26. Testing Multiple Tabs and Pending Requests

A browser might open two tabs:

~~~text
Tab A: GET /oauth2/authorization/company -> state=A
Tab B: GET /oauth2/authorization/partner -> state=B
~~~

### 26.1. Default Repository Behavior

`HttpSessionOAuth2AuthorizationRequestRepository` in some versions/implementations keeps a single pending Authorization Request per session. Flow B may overwrite flow A.

Do not mistake this behavior for a state mismatch security bug when two tabs race.

### 26.2. If the Product Requires Concurrent Login Tabs

Use a custom `OAuth2AuthorizationRequestRepository` supporting multiple pending states, TTL, bounded entry count, one-time removal, and session binding.

### 26.3. Tests to Write

- Start A and B in the same session.
- Receive callback B before A.
- Which callback is allowed per policy?
- Is the remaining pending state misused?
- Is an Authentication ever created for the wrong issuer/tenant?
- Never consume the same state twice.

### 26.4. Do Not "Fix" This by Disabling State Validation

If flow A loses correlation, the user should restart login A. Never accept a mismatched callback simply because the browser has a live session.

## 27. State Replay and Tenant Binding

In SaaS, an authorization transaction may also carry:

~~~text
state=S1
tenant=acme
registration=company
expectedIssuer=https://op.example.test
returnPath=/t/acme/home
~~~

### 27.1. Right Tenant on Callback

Never read the tenant from callback query parameters. It must be bound to the pending state in the server-side store.

### 27.2. Duplicate Callbacks Must Not Create a New Tenant Context

Once state S1 is consumed, a callback replay must never switch the active tenant to Acme or create extra local user memberships.

### 27.3. Cross-Tenant Mix-Up Tests

- Start Acme flow, callback with state from Globex.
- Start Company registration, callback with a different issuer.
- Start with Acme returnPath, callback tries to redirect to Globex.
- User is authenticated yet not a member of the selected tenant.

### 27.4. Never Use Email as a Global Identity

Two issuers may share a `sub` or email. Identity keys should be based on issuer+subject, and the application must still verify tenant membership.

## 28. Failure Handlers Need Clear Policies

Failure states can happen while a user is unauthenticated, or when an already-logged-in user tries to link another provider.

### 28.1. Safe Error Page

Show just enough information:

~~~text
Could not complete sign-in or authorization.
Please try again or contact an administrator.
~~~

Never print raw `state`, authorization codes, ID tokens, refresh tokens, or stack traces to the browser.

### 28.2. Never Redirect to a URL Taken from the Callback

If a callback contains `returnTo=https://attacker.example`, never use that parameter to redirect after an error.

### 28.3. Distinguish Voluntary Denial from Security Incidents

`access_denied` may be normal user refusal, not necessarily a security alert. Repeated state mismatches/replays may warrant logging/alerting per policy.

### 28.4. Logging

You can log:

~~~text
correlationId=...
registrationId=company
category=OAUTH_LOGIN_FAILURE
errorCode=access_denied
statePresent=true
sessionBoundRequestFound=true
~~~

Avoid logging raw codes/states/session cookies. Restrict log access and apply appropriate retention.

### 28.5. Existing Session After Failure

If a user was already logged in before starting another OAuth2 authorization flow, the failure handler may keep or clear the existing session depending on security/account-linking policy.

Include an "already authenticated user" test case if the application supports account linking or re-login, not only anonymous starts.

## 31. Misconceptions to Avoid

**"If the user denies consent, the API returns 403."**

Not necessarily. This is an OAuth authorization response error at the callback; the API may not have received any request.

**"Consent denied always means the user actively clicked Deny."**

No. AS policy can also produce `access_denied`.

**"If you have a code, you can exchange it for tokens even with the wrong state."**

No. You must correlate the callback with the pending Authorization Request first.

**"On wrong state, the default repository definitely deletes the old request."**

Do not assume this; check your version/implementation and cleanup policy.

**"For duplicate callbacks, returning HTTP 401 is enough."**

Insufficient. Verify the token endpoint is not called a second time and no new authorized client is created.

**"The authorization code is single-use at the AS, so the client doesn't need to consume state."**

No. Those are two independent layers of defense.

**"`oidcLogin()` tests OIDC callbacks."**

No. This helper mocks a post-login principal.

**"A fake OP returning an access token is enough for OIDC Login."**

No. OIDC scope `openid` requires a valid ID token per profile.

**"Because the callback path contains the registration ID, issuer verification isn't needed."**

No. State correlation and OIDC validation are both required.

**"Two tabs in the same session must always succeed on the default repository."**

Not necessarily; understand how your implementation stores multiple pending requests.

**"The failure handler should log the entire query for debugging."**

No. The query contains sensitive authorization codes and state.

**"MockMvc can verify SameSite just like a real browser."**

Not completely. Cookie/browser behavior requires E2E tests.

## 32. Practice Scenarios

### A. User Denies Consent

Browser starts flow S1 and the OP returns `access_denied`.

**Test:** same session, matching state, verify login failure and zero token endpoint calls.

### B. Callback Has Tampered State

Browser has pending S1, callback sends S2.

**Test:** reject before token exchange; create no Authentication.

### C. Callback Missing State

Redirect returning from the OP contains only `code=C1`.

**Test:** reject; do not fall back to the latest pending request.

### D. Callback via Different Session

Started in session A, callback arrives on session B.

**Test:** reject; never look up session A's state to authenticate B.

### E. User Reloads a Successful Callback

First callback C1/S1 creates an OIDC principal. Reload the same URL.

**Test:** second callback fails; token endpoint called only once; no new authorized client created.

### F. AS Token Endpoint Receives Same Code Twice

Fake AS returns tokens on the first attempt and `invalid_grant` on the second.

**Test:** single-use code; client replay must not succeed.

### G. Duplicate Callback While User Is Already Logged In

Alice already has a session, tries logging into Partner, then gets denied or replays.

**Test:** verify policy on keeping/clearing Alice's session without switching to the wrong principal.

### H. Multi-Tab Login

Tabs A and B have separate states in the same session.

**Test:** per repository policy; never drop state validation to "fix" the race.

### I. Tenant Tampered in Callback

Started in tenant Acme, browser edits query `tenant=Globex`.

**Test:** never take tenant from the callback; membership/context follows the pending state.

### J. Fake ID Token with Wrong Nonce

Valid state, token endpoint returns a signed ID token with a different nonce.

**Test:** OIDC validation rejects it; no successful login created.

## 33. Self-Check Questions

**1. Is `access_denied` on a callback an error from the API Resource Server?**

No. It is an error response from the OAuth Authorization Server when authorization is not granted.

**2. If consent is denied, does the client get a successful authorization code to exchange for tokens?**

No.

**3. Why must tests use the real state generated by the authorization redirect?**

To test Spring Security's correlation with a real pending Authorization Request, not just a hardcoded string.

**4. Why preserve `MockHttpSession` between start and callback?**

The Authorization Request is typically stored per browser/session.

**5. When state is wrong, what should you assert besides HTTP status?**

Zero token endpoint calls, and no new Authentication or authorized client.

**6. Does a wrong state always delete the valid pending request S1?**

Not by default; it depends on the repository/cleanup policy.

**7. If a callback arrives from a different session with the right state, should login succeed?**

No, because that session did not initiate the pending request.

**8. What must a duplicate callback after success NOT do?**

Must not reprocess the transaction or exchange the authorization code again.

**9. Why use a fake AS token counter?**

To prove a duplicate callback does not send the code to the token endpoint a second time.

**10. What must the AS verify for an authorization code?**

The code must be bound to the client/redirect and single-use per OAuth policy.

**11. What does an OIDC happy-path mock need besides an access token?**

A valid ID token, JWKS public key, valid issuer/audience/time, and matching nonce where applicable.

**12. Does `oidcLogin()` test real state/nonce/PKCE callbacks?**

No.

**13. Does consent denial always return HTTP 401 at the Portal?**

No. Status is decided by the failure handler; it may be a 302 redirect.

**14. Is UserInfo guaranteed to be called on every OIDC login?**

No. It depends on scope/provider/config.

**15. Should a fake OP use a production client secret?**

No.

**16. When two-tab login hits a state error, should you disable state validation?**

No. Review repository/concurrent pending request policies instead.

**17. Can a replay callback clear an earlier logged-in session?**

Possibly, depending on the failure handler; test the keep/clear session policy when already authenticated.

**18. Should raw authorization codes/states be logged for debugging?**

No. Log safe metadata/correlation IDs instead of credentials.

**19. Why check the authorized client store after failure?**

To ensure no new tokens or wrong principals were stored by a failed callback.

**20. Does MockMvc completely test real browser SameSite cookies?**

No. Use browser/E2E tests when policies depend on cookie/redirect behavior.

## Key Takeaways

- **Consent refusal (`error=access_denied`), state mismatch, and callback replay are three distinct failure paths** in OAuth2/OIDC Login that require dedicated tests.
- **Initiate the authorization flow with Spring Security and capture the real state from the redirect**, preserving `MockHttpSession` so callback tests reflect real correlation.
- **Denied consent yields no authorization code, triggers zero token endpoint calls, and creates no new login**; exact HTTP status/redirect depends on the failure handler.
- **Wrong, missing, or cross-session state must be rejected before token exchange.** Never fall back to another pending request.
- **Duplicate callbacks must never succeed a second time**; verify both token endpoint call counts and authorized client persistence.
- **Client-side state correlation and AS-side single-use authorization codes are two independent defenses.** Never drop state just because the AS prevents code reuse.
- **`oidcLogin()` only mocks a post-login principal**, and does not test callbacks, consent errors, state, PKCE/nonce, or real ID token validation.
- **Happy-path OIDC integration requires a fake AS issuing an ID token signed with a test key, JWKS, and matching nonce**; standalone access token JSON is not enough.
- **Failure handlers, session cleanup, multi-tab handling, tenant binding, and account switching each have distinct policies**; never let failed callbacks swap Authentication or tenants unintentionally.
- **Never use a production OP or real tokens in tests**, never log raw codes/states/secrets, and present only sanitized error details to the browser.
