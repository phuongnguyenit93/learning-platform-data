# Choosing a Compatible JDK, Spring Boot, and Spring Security Version Set

When **bootstrapping and configuring a Spring Security OAuth 2.0/OIDC Resource Server**, choosing the right **JDK + Spring Boot + Spring Security** combination determines whether the application can build, start up, verify Bearer tokens, and be safely maintained. Picking each version independently easily causes binary conflicts, security configuration errors, or issues that only surface in production.

**The most important rule:** choose a supported **Spring Boot** version, choose a **JDK within the Java range supported by that Boot version**, and let **Spring Boot dependency management/BOM** select the corresponding Spring Framework and Spring Security versions. Do not manually pair Security 7.x with a Boot 3.x project, or pick a Gradle version that cannot run on the actual JDK.

This lesson walks through reading compatibility matrices, choosing a release line, configuring Maven/Gradle projects, inspecting the classpath, and troubleshooting common issues in an OAuth2 Resource Server.

## 1. Why Can't You Just Pick Three Version Numbers?

Suppose a development team wants to use:

~~~text
JDK:             21
Spring Boot:     4.1.2
Spring Security: 6.5.11
~~~

JDK 21 may satisfy the Java baseline of Boot 4.1.2, but **Security 6.5.11** belongs to the generation managed by Boot 3.5.x, whereas Boot 4.1.2 manages **Security 7.1.2**. Forcing certain modules back to 6.5.x can make Spring Framework, the Security Filter Chain, and the OAuth2 modules incompatible.

Even with the right JDK and Spring combination, the build can still fail if the **Gradle Wrapper** is too old or the Spring Cloud release train does not match.

Therefore, multiple layers must be verified:

| Layer | What to verify | Common mismatch |
|---|---|---|
| **JDK** | Minimum Java, Java range published by Boot, compiler/toolchain, production JVM | Builds with Java 21 but runtime only has Java 17 |
| **Spring Boot** | Release line, patches, lifecycle, BOM, and auto-configuration | Using an old Boot version past the desired patch support policy |
| **Spring Framework** | Major/minor managed by Boot | Forcing Spring Framework 6.x into Boot 4.x |
| **Spring Security** | Major/minor managed by Boot; modules from the same generation | Core/Web 7.x but OAuth2 Resource Server 6.x |
| **Build tool** | Maven/Gradle, wrapper, Boot plugin, and Java support | Gradle 7.6 with Spring Boot 4.1 |
| **HTTP runtime** | Servlet/MVC or WebFlux, container, and Jakarta API | Library using javax.servlet in a Jakarta runtime |
| **OAuth/OIDC** | JWT/opaque token, JOSE, issuer, audience, scope, Security DSL | Missing JwtDecoder or JOSE module |
| **Ecosystem** | Spring Cloud, Data, Gateway, test libraries, monitoring agents | External starter pulling a dependency from the wrong generation |

**Successful compilation** is not enough to conclude that the application **runs correctly and securely**. After selecting the version set, the Resource Server still needs to verify access tokens, reject invalid tokens, and enforce endpoint/resource authorization.

## 2. Relationship Between JDK, Spring Boot, Spring Framework, and Spring Security

- **JDK** provides the compiler tools, Java APIs, and JVM to run the application. The compiler and runtime versions must match the generated bytecode/artifacts.
- **Spring Framework** provides the DI container, HTTP stack, core data infrastructure, and APIs used by Spring modules.
- **Spring Security** provides authentication, authorization, filter chains, OAuth2 Resource Server, JWT verification, opaque-token introspection, and other security features.
- **Spring Boot** selects consistent dependency versions, and provides starters, build plugins, and auto-configuration.

~~~mermaid
flowchart TD
    A[Technical and operational requirements] --> B[Choose Spring Boot release line]
    B --> C[Choose valid JDK]
    B --> D[Spring Boot BOM / Dependency Management]
    D --> E[Spring Framework]
    D --> F[Spring Security]
    D --> G[JOSE, JSON, and related libraries]
    C --> H[Maven/Gradle Wrapper and CI]
    E --> I[OAuth2 Resource Server]
    F --> I
    G --> I
~~~

**BOM (Bill of Materials)** is a set of metadata used to manage dependency versions. When using **spring-boot-starter-parent** or importing **spring-boot-dependencies** properly, Maven can automatically resolve versions for dependencies managed by Boot. Gradle has an equivalent mechanism via **platform()** or the dependency management plugin.

For example, when using the Spring Boot parent/BOM:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security-oauth2-resource-server</artifactId>
</dependency>
~~~

Omitting the version on the dependency above is **intentional**, because the corresponding Boot 4.x release manages the version for the starter and its transitive dependencies.

## 3. Reference Version Matrix

According to the official **System Requirements** and **Managed Dependency Coordinates** pages, for the releases verified on **November 15, 2026**:

| Spring Boot | Boot-managed Spring Framework | Boot-managed Spring Security | Published Java range | Orientation |
|---|---|---|---|---|
| **4.1.2** | **7.0.10** | **7.1.2** | **Java 17–27** | Boot 4 generation, uses new starters |
| **3.5.16** | **6.2.19** | **6.5.11** | **Java 17–25** | Boot 3 generation, uses corresponding starters |

This is a **version snapshot of specific patches**. Other patches in the same branch may manage newer patches of Framework/Security. Nor should this snapshot be treated as permanently the latest: before creating a project or deploying, always re-read the documentation for the finalized release.

### 3.1. Two Easy-to-Control Option Sets

**Option A — New Project:**

~~~text
JDK                  21 LTS
Spring Boot          4.1.2
Spring Framework     7.0.10, managed by Boot
Spring Security      7.1.2, managed by Boot
HTTP stack           Spring MVC / Servlet
Resource Server      Spring Boot 4 security-oauth2-resource-server starter
~~~

This is a reasonable illustrative set when libraries and infrastructure are ready for Spring Boot 4. Choosing Java 21 instead of the highest supported JDK often helps stick to a familiar LTS milestone; you still need to check which JDK your organization standardizes on.

**Option B — Staying on the Boot 3.5 Ecosystem:**

~~~text
JDK                  21 LTS
Spring Boot          3.5.16
Spring Framework     6.2.19, managed by Boot
Spring Security      6.5.11, managed by Boot
HTTP stack           Spring MVC / Servlet
Resource Server      Spring Boot 3 oauth2-resource-server starter
~~~

This option is suitable for understanding an existing project running on Boot 3.5. In production, you should check the **3.5.x support lifecycle** and patching requirements before deciding to stay on this branch.

### 3.2. Do Not Confuse Minimum Java Version with Compatibility Range

Spring Boot **4.1.2** and **3.5.16** both require **at least Java 17**, but their upper Java limits differ in the documentation for their respective releases. That means:

- **JDK 11** does not meet the baseline of either version.
- **JDK 17 or 21** falls within the published Java range of both versions in the table.
- **JDK 25** falls within the published range of Boot 3.5.16 and 4.1.2, but you must also check support in your build tools and plugins.
- **JDK 27** falls within the range published by Boot 4.1.2; you cannot assume Boot 3.5.16 supports JDK 27.

Boot's Java range **does not automatically guarantee** that Gradle, Maven plugins, bytecode enhancers, annotation processors, IDEs, or CI images already support that JDK. Nor should you run production on a Java version not supported by your operations/policy standards just because the application starts up.

## 4. Maven and Gradle Have Their Own Matrices

The documentation specifies build tool requirements for the noted patches:

| Build tool | **Boot 4.1.2** | **Boot 3.5.16** |
|---|---|---|
| **Maven** | **3.6.3 or later** | **3.6.3 or later** |
| **Gradle** | **8.x from 8.14** or **9.x** | **7.x from 7.6.4** or **8.x from 8.4** |

For example:

- **Boot 4.1.2 + Gradle 7.6**: outside the build tool range published by Spring Boot 4.1.
- **Boot 3.5.16 + Gradle 8.4**: meets Boot 3.5's Gradle constraint; still check the JVM running Gradle.
- **Boot 4.1.2 + JDK 25 + Gradle 8.14**: full support cannot be concluded from the Boot table alone; cross-check the Java compatibility of Gradle/the Gradle daemon itself.
- **Boot 4.1.2 + Maven 3.9.x + JDK 21**: a common Maven setup, provided project plugins are also compatible.

You should commit the **Maven Wrapper** or **Gradle Wrapper** to the repository so developer machines, CI, and production builds use the same tool version. Avoid relying on arbitrary Maven/Gradle versions installed on each machine.

If using Gradle, distinguish between:

1. **The JDK running the Gradle daemon**.
2. **The Java toolchain used for compilation**.
3. **The JVM running the packaged application**.

These may not be the same JDK and have different compatibility requirements.

Helpful documentation: [Gradle Compatibility Matrix](https://docs.gradle.org/current/userguide/compatibility.html).

## 5. Why Should Boot Manage Spring Security?

Spring Security is not just a single dependency. A JWT Resource Server can simultaneously use:

~~~text
spring-security-core
spring-security-config
spring-security-web
spring-security-oauth2-core
spring-security-oauth2-resource-server
spring-security-oauth2-jose
~~~

Spring Boot provides dependency management so these modules and Spring Framework align. Avoid manually specifying mismatched versions such as:

~~~text
spring-boot-starter-webmvc             4.1.2
spring-security-core                   7.1.2
spring-security-web                    6.5.11  <-- generation mismatch
spring-security-oauth2-resource-server 7.1.2
~~~

The result can be **NoSuchMethodError**, **NoClassDefFoundError**, failures creating SecurityFilterChain, or errors that only occur when processing Bearer tokens. Maven/Gradle have their own resolution rules; a passing build is not proof that all modules belong to the same generation.

You should only override a Security dependency outside the BOM when there is a clear reason, confirmed compatibility, and testing—such as needing a specific patch before an appropriate Boot release arrives. For day-to-day maintenance, **upgrading the Spring Boot patch version** is usually much easier to sustain.

### 5.1. How Do Spring Security 6 and 7 Differ?

- **Spring Security 6.x** is the generation typically paired with Spring Framework 6 and Spring Boot 3.x.
- **Spring Security 7.x** is the generation typically paired with Spring Framework 7 and Spring Boot 4.x.
- Upgrading **6 → 7** is a **major migration**; read the [Spring Security Migration Guide](https://docs.spring.io/spring-security/reference/migration/) to prepare API/configuration changes, framework updates, and Jackson integration.
- If code still uses legacy APIs like **WebSecurityConfigurerAdapter** or depends on legacy OAuth2 modules, plan the migration to **SecurityFilterChain** and the modern Resource Server model.

Do not simply change the version of one artifact in a project to "try Security 7" while staying on Boot 3.

## 6. Spring Boot 4 Renames Several Starters

This is an immediate practical difference when bootstrapping a project:

| Feature | **Spring Boot 3.5.x** | **Spring Boot 4.x** |
|---|---|---|
| Servlet / Spring MVC | **spring-boot-starter-web** | **spring-boot-starter-webmvc** |
| OAuth2 Resource Server | **spring-boot-starter-oauth2-resource-server** | **spring-boot-starter-security-oauth2-resource-server** |
| OAuth2/OIDC Client | **spring-boot-starter-oauth2-client** | **spring-boot-starter-security-oauth2-client** |
| OAuth2 Authorization Server | **spring-boot-starter-oauth2-authorization-server** | **spring-boot-starter-security-oauth2-authorization-server** |

Boot 4 documentation notes that the old starter names still appear in the catalog but are **deprecated** in favor of the new names. For new Boot 4 projects, use the new starters from the start. For Boot 3.5, use the starter names of the 3.5 branch; do not apply Boot 4's new names to Boot 3.

Be careful to distinguish three roles:

- **Resource Server**: an API that receives and verifies Bearer access tokens and enforces authorization.
- **OAuth2/OIDC Client**: an application that performs user login or requests tokens to call APIs.
- **Authorization Server/OpenID Provider**: issues tokens, serves issuer metadata, JWKS, introspection, and related endpoints.

An API that only needs to verify JWTs typically **does not need** the OAuth2 Client starter or Authorization Server starter.

Source: [Spring Boot Build Systems — starter catalog](https://docs.spring.io/spring-boot/reference/using/build-systems.html).

## 7. Sample Spring Boot 4.1.2 + JDK 21 + Maven Project

Suppose we create an **Orders API** using Spring MVC and JWT access tokens issued by an external Authorization Server.

### 7.1. Choosing Initial Settings

On [Spring Initializr](https://start.spring.io/) or configured manually:

| Property | Example value |
|---|---|
| Project | Maven |
| Language | Java |
| Spring Boot | **4.1.2** |
| Java | **21** |
| Packaging | Jar |
| Web | Spring MVC |
| Authentication | OAuth2 Resource Server |
| Token | JWT signed by a trusted issuer |

### 7.2. pom.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>4.1.2</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>orders-resource-server</artifactId>
    <version>0.0.1-SNAPSHOT</version>
    <name>orders-resource-server</name>

    <properties>
        <java.version>21</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-webmvc</artifactId>
        </dependency>

        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-security-oauth2-resource-server</artifactId>
        </dependency>

        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

Key points:

1. **Parent Boot 4.1.2** defines dependency management for Spring Framework, Security, and related libraries.
2. **java.version 21** specifies the project's Java level. You must still prepare JDK 21 for the build and a compatible JVM at runtime.
3. **webmvc** fits Servlet applications. If choosing WebFlux, you must use the WebFlux starter and configure reactive security.
4. The **security-oauth2-resource-server** starter provides the required dependencies for the Boot 4 branch; do not manually pin the Spring Security version.
5. The project **does not issue access tokens itself**. Issuer and audience come from a trusted identity system configuration.

### 7.3. application.yml

~~~yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/shop
          audiences:
            - orders-api
~~~

The issuer/audience values here are purely illustrative. In a real environment, **issuer-uri** must match the access token's **iss** claim, and **audiences** must match the intended audience issued for the API. The Resource Server verifies JWTs using issuer/JWKS or trusted keys; only use a token for authorization after it has been verified.

### 7.4. SecurityFilterChain for Servlet

~~~java
package com.example.orders;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/api/public/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/orders/**")
                    .hasAuthority("SCOPE_orders.read")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(Customizer.withDefaults())
            );

        return http.build();
    }
}
~~~

This snippet illustrates the Security DSL for Spring Security 7.x. **SCOPE_orders.read** requires the access token to have the **orders.read** scope via the scope-to-GrantedAuthority mapping mechanism. You still need to check owner/tenant permissions per order; a scope alone does not prove a user may read every order.

Concerns such as CSRF, session management, 401/403 responses, whether clients use cookies or bearer headers, and CORS must be designed for the specific architecture. A project that starts up does not mean its security policy is complete.

For applications not yet upgraded to Boot 4, use **JDK 21 + Boot 3.5.16** and Boot 3 starter names.

Relevant excerpt of **pom.xml**:

    <artifactId>spring-boot-starter-parent</artifactId>

This is an excerpt, not a complete Maven POM file. Parent Boot 3.5.16 manages Security **6.5.11** per the dependency coordinates at the time noted above.

Spring Security 6.x can also use **SecurityFilterChain** and the modern OAuth2 Resource Server APIs. What you should not do is add Spring Security 7.1.x to just one module to get a new feature while the rest of the project remains on Boot 3.5.x.

### When to Choose Boot 3.5 Instead of Boot 4?

An existing project on Boot 3.5 may need to stay there while:

- Spring Cloud, Gateway, JPA libraries, or specialized adapters have not yet been upgraded.
- The team has not finished testing major changes or the Jackson/Jakarta migrations.
- The system operates under strict SLAs and requires a multi-phase rollout plan.

However, **never use "it's running fine" as an excuse to skip maintenance**. Always check the release line's support schedule and security patches. For new projects, prefer a stable, supported platform that meets your organization's constraints.

## 9. Using Gradle: Java Toolchain and BOM

Example Groovy **build.gradle** for **Boot 4.1.2**, using a Gradle Wrapper that satisfies Boot 4.1 requirements:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '4.1.2'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

dependencies {
    implementation platform('org.springframework.boot:spring-boot-dependencies:4.1.2')
    testImplementation platform('org.springframework.boot:spring-boot-dependencies:4.1.2')

    implementation 'org.springframework.boot:spring-boot-starter-webmvc'
    implementation 'org.springframework.boot:spring-boot-starter-security-oauth2-resource-server'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
~~~

In this example:

- **org.springframework.boot plugin** and **spring-boot-dependencies BOM** both use 4.1.2; they must be upgraded together.
- **platform()** is how Gradle attaches dependency constraints to the relevant configurations.
- **Java 21 toolchain** selects the compile JDK, provided that JDK is available locally or supplied by a toolchain resolver.
- No separate version needs to be specified for Security modules.
- You must check the Gradle wrapper and the Java version running the Gradle daemon, because **toolchain** does not change the JDK running Gradle itself.

In a real multi-module project, you can use a version catalog or convention plugin to avoid repeating versions between the plugin and BOM.

When using the **io.spring.dependency-management** plugin, you can let the Spring Boot plugin coordinate BOM management instead of calling **platform()**; pick one documented approach and avoid introducing conflicting constraints.

## 10. Checking the Build JDK and Runtime JDK

### 10.1. Compiling for Java 21 Does Not Mean Java 17 Can Run It

An application compiled to Java 21 bytecode typically requires a compatible Java 21 or newer runtime. If deployed into an image with only Java 17, you may encounter:

~~~text
java.lang.UnsupportedClassVersionError:
class file version 65.0; runtime only recognizes up to 61.0
~~~

Class file version **65** corresponds to Java 21; **61** corresponds to Java 17.

Example container model:

~~~dockerfile
# Illustrates stages, not a complete Dockerfile.
FROM eclipse-temurin:21-jdk AS builder
# Copy source, run Maven/Gradle Wrapper, and build the JAR.

FROM eclipse-temurin:21-jre
# Copy JAR from the builder stage and run.
~~~

Verify the actual images in CI and production. Pin image tags/digests according to policy and manage JDK patches regularly. Having a different JDK on developer machines than in containers easily causes build discrepancies.

### 10.2. Checking Versions Directly

Common commands:

~~~bash
java -version
javac -version
mvn -version

# With Maven Wrapper on macOS/Linux:
./mvnw -version

# With Gradle Wrapper on macOS/Linux:
./gradlew -version
~~~

On Windows PowerShell:

~~~powershell
java -version
javac -version
.\mvnw.cmd -version
.\gradlew.bat -version
~~~

The Maven/Gradle wrapper commands show **the Java version running the build tool**. For Gradle toolchains, also check the Java compiler configuration and the selected JDK. With Maven, if multiple JDKs are needed on the same machine, check Maven Toolchains and the compiler release setting.

Note that **JAVA_HOME**, PATH configuration, IDE project SDK, CI runners, and Docker images may point to different JDKs. When diagnosing errors, confirm each actual environment.

## 11. Inspecting the Dependency Tree to Detect Conflicts

Even when your code does not specify a Security version, a third-party library may pull in transitive dependencies or constraints that cause a different version to be selected.

### 11.1. Maven

On Linux/macOS:

~~~bash
./mvnw dependency:tree -Dincludes=org.springframework.security:*
~~~

On Windows PowerShell:

~~~powershell
.\mvnw.cmd dependency:tree "-Dincludes=org.springframework.security:*"
~~~

You can also view the effective POM and dependencyManagement:

~~~bash
./mvnw help:effective-pom
~~~

In the output, focus on the Spring Security dependencies actually resolved. With Boot 4.1.2, Security modules are normally on the **7.1.2** line; with Boot 3.5.16, **6.5.11**. Read the **resolved version**, not just what a transitive dependency requested.

### 11.2. Gradle

~~~bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight \
  --configuration runtimeClasspath \
  --dependency spring-security-oauth2-resource-server
~~~

Windows equivalent:

~~~powershell
.\gradlew.bat dependencies --configuration runtimeClasspath
.\gradlew.bat dependencyInsight --configuration runtimeClasspath --dependency spring-security-oauth2-resource-server
~~~

**runtimeClasspath** shows the dependency set the application will load at runtime. **dependencyInsight** tells you why the final version was chosen—whether by BOM, conflict resolution, or constraints. If needed, inspect related Spring Security modules to find any mis-pinned versions.

### 11.3. Signs Worth Investigating

- **spring-security-core** and **spring-security-web** resolve to two different major versions.
- **spring-framework** or the Servlet API is overridden outside Boot's set.
- A Spring Cloud starter belongs to a release train that does not support the current Boot version.
- **spring-security-oauth2-resource-server** is present, but **spring-security-oauth2-jose** is missing in a self-managed JWT setup.
- Spring Security 7.x appears in a Boot 3.x project without the corresponding migration/dependency set.
- A third-party module pins Nimbus JOSE/Jackson too tightly, causing conflicts.

Do not resolve conflicts by individually bumping every dependency to its latest version. Find the source of the version, compare against the compatibility matrix, and make controlled changes.

## 12. JWT vs. Opaque Token Affects Configuration, Not JDK Choice

After picking the version set, the Resource Server must also know **which access token format** it uses:

| Criterion | JWT access token | Opaque access token |
|---|---|---|
| How token is verified | JWT signature/JWKS and validators | Token introspection against Authorization Server |
| Spring Security component | **JwtDecoder** | **OpaqueTokenIntrospector** |
| Primary configuration | **resourceserver.jwt** | **resourceserver.opaquetoken** |
| Reads permissions from | Verified JWT claims | Trusted introspection response |
| Issuer dependency | Can fetch public keys via HTTPS/JWKS | Typically requires introspection endpoint and client credentials |

JWT example:

~~~yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/shop
          audiences:
            - orders-api
~~~

Conceptual opaque-token config example:

~~~yaml
spring:
  security:
    oauth2:
      resourceserver:
        opaquetoken:
          introspection-uri: https://login.example.com/oauth2/introspect
          client-id: read-from-secret-manager
          client-secret: read-from-secret-manager
~~~

This is only an illustration of property structure; never hardcode real client secrets in source control. Use environment variables or a controlled secret manager.

If **not using a Spring Boot starter**, JWT configuration requires the appropriate modules such as **spring-security-oauth2-resource-server** and **spring-security-oauth2-jose**. Regardless of choosing JWT or opaque tokens, the Resource Server must still validate **issuer/audience where appropriate, token validity, and business permissions**; an OIDC ID Token used for client login does not automatically serve as an API access token.

## 13. Servlet and WebFlux Use Different Security Configurations

There are two common HTTP stack branches:

| Characteristic | Spring MVC / Servlet | Spring WebFlux / Reactive |
|---|---|---|
| Web mechanism | Servlet filter chain | Reactive WebFilter chain |
| Security bean | **SecurityFilterChain** | **SecurityWebFilterChain** |
| Builder | **HttpSecurity** | **ServerHttpSecurity** |
| JWT decoder | **JwtDecoder** | **ReactiveJwtDecoder** |
| Boot starter | **webmvc** (Boot 4) / **web** (Boot 3) | **webflux** |

**Servlet** example:

~~~java
@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(Customizer.withDefaults()))
        .build();
}
~~~

**Reactive** example:

~~~java
@Bean
SecurityWebFilterChain security(ServerHttpSecurity http) {
    return http
        .authorizeExchange(auth -> auth
            .anyExchange().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(Customizer.withDefaults()))
        .build();
}
~~~

These are two distinct paths. Do not mix both configurations into the same application just to test code snippets from the internet. When choosing versions and starters, determine the HTTP stack based on your application architecture.

## 14. Migration: Java 8/11, Boot 2.x, Security 5.x to Boot 3/4

A legacy application might currently use:

~~~text
Java 8 or 11
Spring Boot 2.x
Spring Framework 5.x
Spring Security 5.x
javax.servlet.*
WebSecurityConfigurerAdapter
~~~

Upgrading to Boot 3.x/4.x typically involves handling multiple changes simultaneously.

### 14.1. Upgrading the Java Baseline

Boot 3 and Boot 4 require Java 17 or later. You must upgrade the development JDK, CI, build tools, container runtime, and agents/plugins. If planning to use JDK 21, ensure the compiler release and runtime match.

### 14.2. Migrating from javax to jakarta

For example:

~~~java
// Legacy generation application:
import javax.servlet.http.HttpServletRequest;

// Application using Jakarta Servlet:
import jakarta.servlet.http.HttpServletRequest;
~~~

This is an ecosystem-wide API shift: Servlet containers, validation, JPA, and third-party integrations may also need upgrading. Spring Boot 4.x has higher servlet/container requirements than the 3.x branch; read the System Requirements for your target version.

### 14.3. Updating Security Configuration Style

The modern configuration style uses a **SecurityFilterChain** bean and the lambda DSL. Older tutorials based on **WebSecurityConfigurerAdapter**, legacy APIs, or legacy OAuth2 modules are not suitable to copy directly into Security 6/7.

### 14.4. When Upgrading Boot 3 → 4

In addition to Spring Security 7, review:

- Starters renamed/split into modules in Boot 4.
- Spring Framework 7 and changed APIs.
- Jackson 2 → Jackson 3 migration in relevant components.
- Matching Jakarta Servlet container versions.
- Spring Cloud release train, Spring Data, database drivers, and test libraries.
- Default behavior changes in security, error responses, serialization, and observability.

**A sound roadmap** is to resolve dependencies and deprecated APIs on your current version, review migration guides, perform major upgrades in a controlled manner, and test every execution path. Avoid merely changing the version in `pom.xml` and assuming the entire application is compatible.

## 15. Common Errors When Choosing the Wrong Version Set

### 15.1. Java Runtime Older Than Bytecode

~~~text
UnsupportedClassVersionError: ... class file version 65.0 ...
~~~

The application was built for Java 21, but the JVM only supports Java 17. Check **java -version** of the runtime, Maven/Gradle toolchain, and Docker image. Do not try to fix this by randomly changing Spring Security versions.

### 15.2. Gradle Plugin Requires a Newer Version

~~~text
Spring Boot plugin requires Gradle ... or later
~~~

The Gradle wrapper is too old for the Boot plugin. Upgrade the wrapper to a version within Boot's published range, and verify that Gradle supports the JDK in use.

### 15.3. NoSuchMethodError or NoClassDefFoundError

This can appear when Spring Framework/Security major versions are mixed, an external library brings in an older API, or a module is resolved outside the BOM. Analyze the dependency tree/insight to inspect **resolved versions**; do not treat this as a JWT bug before verifying the classpath.

### 15.4. Missing JwtDecoder

~~~text
No qualifying bean of type JwtDecoder ...
~~~

This may happen due to a missing JOSE dependency, incomplete issuer/JWKS configuration, or a custom bean disabling auto-configuration. Confirm the project is a JWT Resource Server using the right starter for its branch and proper properties.

### 15.5. Token Returns 401 Even Though the App Starts

A JWT returning 401 can be caused by a wrong **iss**, an **aud** not meant for the API, an expired **exp**, unreachable JWKS, an invalid signature, or an unaccepted algorithm. This is usually a **trust/token configuration** issue, not automatically a sign that the JDK/Boot/Security version set is wrong.

### 15.6. Valid Token Returns 403

The user is authenticated but lacks a scope/authority such as **SCOPE_orders.read**, or violates a tenant/ownership policy. Do not fix this by disabling authorization. Choosing the right version set gets Security running, while **authorization policies** still must be defined by the application.

### 15.7. New Starter Name Does Not Exist in Older Boot

**spring-boot-starter-security-oauth2-resource-server** is the starter name targeting Boot 4. Using this name with Boot 3.5 will not allow Maven to find the corresponding starter. When targeting Boot 3, use **spring-boot-starter-oauth2-resource-server**.

### 15.8. Everything Builds Locally, Fails in Production

CI may run a different JDK than the container. In addition, there are proxies, TLS, trust stores, DNS, issuer metadata, and certificates. Document exact versions/build artifacts and verify the real environment rather than confirming only on a laptop.

## 16. Decision Workflow for a New Project

~~~mermaid
flowchart TD
    A[Define API role and infrastructure constraints] --> B[Choose a supported Spring Boot branch]
    B --> C{Is target JDK in supported range?}
    C -->|No| D[Change JDK or Boot branch]
    C -->|Yes| E[Choose matching Maven/Gradle Wrapper]
    E --> F[Initialize project with branch-appropriate starter]
    F --> G[Let BOM manage Security/Framework]
    G --> H[Verify dependency graph and Java runtime]
    H --> I[Configure issuer, audience, JWT/opaque]
    I --> J[Verify authentication and authorization paths]
~~~

Step-by-step workflow:

1. **Specify the role**: Is this a Resource Server verifying JWT/opaque tokens, or also an OIDC Client or Authorization Server?
2. **Finalize the HTTP stack**: Spring MVC/Servlet or WebFlux/reactive?
3. **List JDK constraints**: Production Java runtime, base image, CI, IDE, build tools, and team policy.
4. **Choose Boot release**: Prefer a stable, supported release fitting the environment; check its lifecycle and integrated libraries.
5. **Use the Boot BOM**: Avoid mixing Spring Security majors or adding separately versioned dependencies.
6. **Pick the release-appropriate starter**: Boot 3 uses the old starter names, Boot 4 uses the new group.
7. **Lock the build tool**: Commit the Wrapper and configure the Java toolchain/compilation target.
8. **Cross-check the dependency graph**: Security, Framework, JOSE/Jackson, Spring Cloud.
9. **Configure the Resource Server**: issuer/JWKS or introspection; validate audience and authorization.
10. **Run required integration tests** before deployment and whenever applying patch/major updates.

A quick decision table:

| Scenario | Recommended choice |
|---|---|
| New project, Java 21, libraries ready for Boot 4 | Consider Boot 4.1.x + Security 7.1.x managed by BOM |
| Existing project on Boot 3.5 needing security updates within the same release line | Use the appropriate 3.5 patch, keeping Security 6.5.x managed by BOM |
| Project on Java 11 | Must upgrade JDK for Boot 3/4; do not keep Java 11 and force a new Boot version |
| Project on Gradle 7.x | Upgrade wrapper if selecting Boot 4.1; verify Gradle's Java support |
| Project using Spring Cloud | Look up the release train compatible with the selected Boot version |
| Project with an individually pinned Spring Security dependency | Check why it is pinned and inspect the dependency tree; prefer aligning with the BOM |

## 17. Minimum Checks After Project Creation

Once a real project is created and built, you should verify:

| Test scenario | Expected outcome |
|---|---|
| Build project with target JDK/toolchain | Build succeeds; no classpath conflicts |
| Start up in real runtime/container | No bytecode, dependency, or security startup errors |
| Call private API without token | Typically **401 Unauthorized** |
| JWT with bad signature, wrong issuer/audience, or expired | Rejected, typically **401** |
| Valid JWT lacking permissions | Blocked, typically **403** |
| JWT with action permission but not record owner | Blocked per owner/tenant policy |
| Change Boot patch within chosen release line | Dependencies re-resolve; relevant tests still pass |
| Upgrade Boot/Security major version | Migration guide applied and all security paths re-tested |

These steps do not replace secure coding and secrets management, but they catch common issues caused by bad version combinations or misconfigured Resource Servers.

## Conclusion

**Spring Boot is the anchor of the version set.** Choose an appropriate Boot release, use a **JDK** within the supported range of Boot and your build tools, and let the BOM manage **Spring Framework/Spring Security**. For the examples verified on November 15, 2026, **Boot 4.1.2** manages **Security 7.1.2**; **Boot 3.5.16** manages **Security 6.5.11**. Both require **Java 17** or higher, but their supported Java/Gradle ranges and starter names differ.

After creating the project, verify the wrapper, runtime JDK, resolved dependencies, issuer/audience, and API authorization policies. Choosing the right JDK–Boot–Security combination is the **foundational prerequisite** for a Resource Server to verify tokens accurately; protecting data still requires separately designed and tested authorization policies.
