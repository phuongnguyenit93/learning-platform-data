# Do Not Trust Headers Forwarded by a Gateway or Proxy Unless the Source Is Protected

When a Spring Security Resource Server application runs behind a load balancer, ingress controller, API gateway, or reverse proxy, the request the application receives can differ from the request the client originally sent. The proxy may terminate TLS, change host/port, rewrite paths, and change the remote address. To inform the application of the original public details, proxies commonly add headers such as **Forwarded**, **X-Forwarded-For**, **X-Forwarded-Host**, **X-Forwarded-Proto**, **X-Forwarded-Port**, or **X-Forwarded-Prefix**.

These headers are useful for generating redirects, building absolute URLs, recording the client IP, and restoring the public request URI. Yet they are still **HTTP headers**. If a client can send values itself and the proxy forwards them intact, an attacker can make the application trust a forged host, scheme, IP, or path.

The safety principle is: **only trust forwarded metadata overwritten or generated by a proxy inside the system's trust boundary, over a backend connection that only the proxy is allowed to use**. Spring Framework can read and apply these headers, but `ForwardedHeaderFilter` or `ForwardedHeaderTransformer` itself does not verify who sent them.

This lesson covers the trust boundary between client, proxy, and Resource Server; how to configure proxies to strip/overwrite incoming headers; how to restrict connection sources; support in Spring Boot, Servlet, and WebFlux; risks when misusing host/proto/client IP/path; and how to test through a real ingress.

## 1. What Are Forwarded Headers?

When a request passes through a proxy, the backend server usually only sees the connection from the proxy. Example:

~~~text
Client
  |
  | HTTPS https://api.example.com/orders
  v
Load balancer / API gateway
  |
  | HTTP http://orders-service:8080/orders
  v
Spring Resource Server
~~~

The backend application sees the load balancer as the remote peer, the scheme may be HTTP, and the host may be an internal hostname. The proxy can forward the original metadata using headers.

Two common families:

| Header | Meaning |
|---|---|
| **Forwarded** | Standardized header per RFC 7239, which may contain `for`, `by`, `host`, `proto` |
| **X-Forwarded-For** | Client address and/or proxy chain per deployment convention |
| **X-Forwarded-Host** | Original public host |
| **X-Forwarded-Proto** | Original scheme, typically `http` or `https` |
| **X-Forwarded-Port** | Original public port |
| **X-Forwarded-Prefix** | Public path prefix when the proxy rewrites paths |
| **X-Forwarded-Ssl** | A legacy convention representing TLS status |

RFC 7239 example:

~~~http
Forwarded: for=192.0.2.60;proto=https;host=api.example.com
~~~

X-Forwarded example:

~~~http
X-Forwarded-For: 192.0.2.60
X-Forwarded-Host: api.example.com
X-Forwarded-Proto: https
X-Forwarded-Port: 443
~~~

These headers help the application reconstruct the request from the client's perspective. They do not by themselves prove that the IP address or host recorded in them is genuine.

### 1.1. Headers Can Come from the Client

A client can send directly:

~~~http
GET /api/orders HTTP/1.1
Host: api.example.com
Forwarded: for=127.0.0.1;proto=https;host=admin.internal
X-Forwarded-For: 127.0.0.1
X-Forwarded-Host: admin.internal
X-Forwarded-Proto: https
X-Forwarded-Port: 443
X-Forwarded-Prefix: /admin
~~~

If the gateway simply forwards these headers, the backend application may misinterpret:

- The client IP as `127.0.0.1`.
- The public host as `admin.internal`.
- The original request as using HTTPS.
- The public path as having the `/admin` prefix.

An attacker does not need to compromise the gateway. It is enough for the gateway to fail to strip or overwrite client-sent headers to inject forged data into the system.

### 1.2. Multiple Proxies Form a Chain

A system may have:

~~~text
Client -> CDN -> Load balancer -> Ingress -> Application
~~~

Each proxy may append or update forwarded metadata. The IP chain may contain multiple entries. Never assume the first or last entry is always the real client; you must understand exactly which proxies are trusted and which proxy appends which entry.

RFC 7239 warns that `Forwarded` contents can be modified by every node along the path to the server, including the client. A trusted proxy list only helps identify hops controlled by the system; entries prior to the trusted proxy may still be untrusted.

## 2. Where Must the Trust Boundary Lie?

A secure architecture can be illustrated as:

~~~mermaid
flowchart LR
    C[Internet client<br/>untrusted headers] --> E[Edge proxy<br/>strips and overwrites headers]
    E -->|TLS/mTLS + network allowlist| A[Application ingress]
    A --> S[Spring Resource Server]
    S --> V[SecurityContext and authorization]
~~~

The edge proxy is the first point under the organization's control. Here, the system must:

1. Receive requests from clients.
2. Strip client-sent forwarded headers.
3. Validate `Host`/public domain against an allowed list.
4. Generate forwarded metadata from the actual connection and proxy configuration.
5. Forward the request to the backend over a protected connection path.

The backend must only accept traffic from the trusted proxy. If an attacker can call the application's port directly, they can bypass the edge and send forged forwarded headers straight to the app.

### 2.1. Using a Private Subnet Alone Is Not Enough

Placing the application server in a private subnet reduces exposure, but you must verify:

- Security groups/firewalls only allow ingress from the gateway.
- Kubernetes `NetworkPolicy` or service mesh policies restrict sources.
- No unintended `NodePort`/host port is published directly.
- Internal load balancers are not open to untrusted workloads.
- The backend has no secondary public route.
- Network access between services is segmented.

Another workload in the same VPC or cluster can still send requests if network policies permit it. The trust boundary must be defined by explicit source identity/network policies.

### 2.2. Securing the Proxy-to-Backend Connection

If the environment requires high protection, use TLS or mutual TLS between the proxy and the application:

- TLS protects confidentiality/integrity in transit.
- mTLS lets the application authenticate the proxy's certificate.
- Network ACLs/security groups restrict connection sources.
- Certificate rotation and trust stores must be managed.

Plain TLS only encrypts the connection. If the backend accepts TLS connections from any reachable client, that does not prove the client is an authorized proxy. mTLS or network identity binds the source.

### 2.3. Forwarded Headers Are Not User Identity

Headers such as:

~~~http
X-Authenticated-User: alice
X-Tenant-ID: tenant-a
X-User-Roles: ADMIN
~~~

do not automatically become an `Authentication`. If an application uses them for identity, there must be a separate trust contract:

- The edge strips same-named headers sent by the client.
- The proxy authenticates the user using a trusted mechanism.
- The assertion is signed or protected by mTLS/a trust boundary.
- The backend verifies the source and integrity of the assertion.
- Claims are checked for issuer, audience, expiry, and permissions.
- Proxy assertions are not mixed with unrelated Bearer tokens.

With an OAuth2 Resource Server, let Spring Security verify the access token by issuer/audience and derive the principal from the verified token/introspection. Forwarded headers only describe request/proxy context.

## 3. Stripping and Overwriting Forwarded Headers at the Edge

This is the most critical step. **Do not strip only `Forwarded` or only `X-Forwarded-For`.** Spring and web servers can read both header families.

Spring Framework recommends that proxies at the trust boundary reset both:

- The standard **Forwarded** header.
- The **X-Forwarded-*** headers.

If the system uses other headers such as `X-Real-IP`, `X-Original-Host`, `X-Original-URL`, or `X-Authenticated-User`, identify and control them under the same principle.

### 3.1. Nginx Example with a Fixed Public Hostname

Illustrative example for an edge proxy terminating TLS on host `api.example.com` and forwarding to an internal backend:

~~~nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://orders-service:8080;

        # Use the public host configured for this virtual host.
        proxy_set_header Host api.example.com;

        # Strip the standard Forwarded header sent by the client.
        proxy_set_header Forwarded "";

        # Overwrite all X-Forwarded metadata from the client.
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Host api.example.com;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-Port 443;

        # Only send prefix if the deployment actually has a public prefix.
        proxy_set_header X-Forwarded-Prefix "";
    }
}
~~~

This is an example for one host and one edge proxy. Adjust it for your actual TLS, upstream, and routing configuration.

Key points:

- **Forwarded** is cleared so the backend never receives a forged chain from the client.
- **X-Forwarded-For** is overwritten from the peer address observed by the edge.
- `Host` is set to the configured virtual host, not taken from an arbitrary value.
- Proto/port reflect the public listener.
- Prefix is only set when the proxy actually rewrites paths.

### 3.2. Be Careful with `X-Forwarded-For` and `proxy_add_x_forwarded_for`

A common configuration:

~~~nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
~~~

This variable appends the current peer address to the existing `X-Forwarded-For` chain. If the edge does not strip the incoming header first, a client can prepend a fake IP at the start of the chain.

For example, the client sends:

~~~http
X-Forwarded-For: 127.0.0.1
~~~

The edge appends the real client address:

~~~http
X-Forwarded-For: 127.0.0.1, 198.51.100.25
~~~

If the application takes the first element as the client IP, it trusts the forged value.

At the first edge point, it is usually best to **reinitialize the chain from the peer address actually observed by the proxy**. If a trusted load balancer sits in front of the edge, the proxy's real-IP config must trust only that load balancer's source addresses before using the restored address.

Do not use `$proxy_add_x_forwarded_for` as an automatically safe setting across all topologies.

### 3.3. When There Are Multiple Managed Proxies

Example:

~~~text
Client -> CDN -> Load balancer -> Nginx -> Application
~~~

A design can:

1. Have the CDN strip client-sent forwarded headers and generate fresh metadata.
2. Have the load balancer trust only allowlisted CDN sources, then update the chain per policy.
3. Have Nginx trust only the identified load balancer.
4. Have the application accept traffic only from Nginx or an authenticated ingress.
5. Have the backend parse the chain according to the configured list of trusted proxies/hops.

If keeping the full proxy chain is unnecessary, you can normalize it to a single edge-verified client IP and forward only that value. Keeping less metadata generally reduces parsing bugs and leaks of internal topology.

## 4. `Host` Header and `X-Forwarded-Host`

`Host` affects how the application constructs absolute URLs, redirects, self-referencing links, and certain authentication flows.

For example, an attacker sends:

~~~http
GET /password/reset HTTP/1.1
Host: attacker.example
X-Forwarded-Host: attacker.example
X-Forwarded-Proto: https
~~~

If the application builds a password reset link using the host it trusts from the request, the email may contain:

~~~text
https://attacker.example/reset?token=...
~~~

This can lead to host-header poisoning, password-reset link poisoning, or redirects to an unintended domain.

### 4.1. Host Must Be Allowlisted

At the edge:

- Declare `server_name`/virtual hosts explicitly.
- Reject invalid or unconfigured hosts.
- For a fixed public domain, overwrite `Host`/`X-Forwarded-Host` with that domain.
- For custom domains, map domains via a verified tenant/domain registry.
- Never use an arbitrary `Host` header to build a tenant or issuer URL.

In the application, sensitive URLs such as OAuth redirect URIs, callback URIs, and password reset base URLs should come from registered configuration or a controlled public origin.

### 4.2. Host Is Not Tenant Authorization

If a system selects a tenant by hostname, the hostname is only routing input. After the access token is verified, you must check that issuer, audience, and tenant claim match the selected tenant.

~~~text
Allowlisted Host -> route tenant-a
Verified Token -> tenant_id=tenant-b

=> reject request
~~~

Never let a valid hostname allow a token from another tenant to be accepted.

## 5. `X-Forwarded-Proto` and Scheme

When TLS terminates at a proxy, the proxy-to-application connection may be HTTP. If the application inspects only the socket, it will think the original request used HTTP.

The proxy may send:

~~~http
X-Forwarded-Proto: https
~~~

The application uses this value to build public URLs, redirects, and determine secure requests.

If an attacker can spoof proto, they can make the application:

- Generate fake HTTPS or insecure HTTP URLs.
- Redirect using the wrong scheme.
- Direct callback/redirect URIs to an unintended domain/scheme.
- Mislead logic relying on `request.isSecure()`.
- Misconfigure cookies or scheme-dependent security decisions.

### 5.1. Do Not Use Forwarded Proto to Replace TLS Policy

TLS must terminate at a trusted proxy or the application server. Forwarded proto is only metadata describing the external connection; it does not encrypt the backend connection and does not enable TLS by itself.

If the edge receives HTTPS while the backend uses HTTP, protect the backend segment with an appropriate network boundary or TLS/mTLS. If the backend is directly reachable, an attacker can send `X-Forwarded-Proto: https` even when the actual connection is HTTP.

### 5.2. Redirects and Cookies

An incorrect scheme/host can affect:

- Post-login/logout redirects.
- Absolute `Location` headers.
- Cookie `Secure` flags when the framework relies on request scheme.
- Links rendered in HTML/JSON.
- OIDC/OAuth callback URLs built from request context.

For cookies and OAuth redirects, use a fixed configured public base URL whenever possible. If request-derived URLs are required, only use them after forwarded metadata has been established by a trusted proxy.

## 6. `X-Forwarded-For` and Client Address

`X-Forwarded-For` is commonly used for:

- Access logs.
- Rate limiting.
- Abuse detection.
- IP allowlists.
- Geolocation or fraud signals.
- Audit trails.

If the IP is taken from a client-supplied header, an attacker can spoof the address and evade policies.

### 6.1. Do Not Blindly Pick the First Element

Example:

~~~http
X-Forwarded-For: 203.0.113.10, 10.0.0.12, 10.0.0.18
~~~

The chain can represent the client and proxies, yet exact semantics depend on how each proxy appends or resets the header.

There is no universal rule that the first or last element is always the client IP. You must:

1. Identify the actual peer socket connecting to the application.
2. Maintain a list of trusted proxy ranges/hops.
3. Traverse the chain from the server side toward the client according to trust policy.
4. Skip hops belonging to trusted proxies.
5. Stop at the first address outside the trusted set using a proper parser/implementation.
6. Never trust entries appearing before the first untrusted proxy.

Avoid manually splitting the string by commas and picking index 0. IPv6, whitespace, quoted values, and multiple header lines can break hand-rolled parsers.

### 6.2. Client IP Is Not Identity

Even when `X-Forwarded-For` is handled properly, IP is still only a network signal. It does not prove who the user is.

Never use client IP to replace OAuth2 Authentication. An IP allowlist can be an additional control layer, yet the access token must still be verified.

### 6.3. Log Peer and Client Addresses Separately

For incident investigation, you can log:

- Direct peer address connecting to the application.
- Client address derived from the trusted proxy chain.
- Proxy identity/source.
- Request ID/correlation ID.
- Authentication result and policy decision.

Explicitly distinguish which field is the peer and which is the derived client IP. Never log an address taken from an unverified header as the "real client IP".

## 7. `X-Forwarded-Prefix` and Path Rewriting

A proxy may expose:

~~~text
https://api.example.com/public/orders/42
~~~

while forwarding to the backend:

~~~text
http://orders-service:8080/orders/42
~~~

The proxy may send:

~~~http
X-Forwarded-Prefix: /public
~~~

Spring Framework can use this prefix to restore the public context path and construct appropriate URLs.

If an attacker controls the prefix, they can affect links, redirects, route reconstruction, or certain path-matching logic.

### 7.1. Prefix Must Be Set by the Proxy

- Strip client-sent prefixes.
- Write only the prefix configured for the route.
- Never append arbitrary prefixes from queries or headers.
- Test path normalization and encoded paths.
- Keep path rewrites aligned between gateway and application.

### 7.2. Path Rewrites Can Create Authorization Discrepancies

Suppose the gateway exposes:

~~~text
/api/admin/users
~~~

but rewrites to the backend:

~~~text
/users
~~~

If a filter or security matcher sees the public path while the controller sees the backend path, determine exactly which layer enforces authorization and which path the policy inspects.

Never let the gateway strip a protected prefix such as `/admin` while the backend route is treated as a public endpoint. Test both external URLs and post-rewrite backend paths.

## 8. Spring Framework: `ForwardedHeaderFilter` and `ForwardedHeaderTransformer`

Spring Framework supports two different components depending on the server stack.

| Component | Stack | Role |
|---|---|---|
| **ForwardedHeaderFilter** | Servlet / Spring MVC | Wraps Servlet request/response and applies forwarded metadata |
| **ForwardedHeaderTransformer** | Reactive / WebFlux | Adapts `ServerHttpRequest` before `ServerWebExchange` is created |

They can update scheme, host, port, remote address, or path-related metadata depending on the headers and implementation, while also removing forwarded headers from the request view so downstream layers do not reuse them.

**They do not authenticate the proxy.** If a client sends forged headers and the edge does not strip them, the filter/transformer can apply that forged data.

### 8.1. Servlet: `ForwardedHeaderFilter`

`ForwardedHeaderFilter` is a Servlet Filter in the `spring-web` module. It wraps the request so downstream components see a request adjusted according to `Forwarded`/`X-Forwarded` headers.

Spring Framework requires the filter to be ordered early enough so other components such as `RequestContextFilter` see the adjusted request. When registering manually via `FilterRegistrationBean` or `web.xml`, pay attention to appropriate dispatcher types such as `REQUEST`, `ASYNC`, and `ERROR` per framework documentation.

In **removeOnly** mode, the filter only removes forwarded headers without applying their values. This mode is useful when an application does not want to trust any forwarded metadata.

### 8.2. WebFlux: `ForwardedHeaderTransformer`

WebFlux uses `ForwardedHeaderTransformer`. The transformer is applied before `ServerWebExchange` is created, so the reactive request has an updated view of scheme/host/port/path.

You can declare the transformer via Spring Framework configuration or use Spring Boot configuration. The transformer also supports **removeOnly**, meaning it strips headers without using them to alter the request.

Do not register both the transformer and another container mechanism handling forwarded headers without clearly understanding their ordering and semantics. Avoid double application, which can lead to inconsistent host/path/remote address changes.

### 8.3. Header Selection by Spring Framework Version

Spring Framework supports both RFC 7239 `Forwarded` and the `X-Forwarded` family. In newer releases, explicitly configure the header type your deployment actually uses rather than relying on legacy behavior that automatically reads both.

If your proxy sends `X-Forwarded-*`, select the corresponding mode. If your proxy sends `Forwarded`, configure the standard header. Whichever type you choose, the edge must still strip both header families from external traffic because another layer might read the other family.

## 9. Spring Boot: `server.forward-headers-strategy`

Spring Boot provides:

~~~yaml
server:
  forward-headers-strategy: FRAMEWORK
~~~

Options:

| Value | Behavior |
|---|---|
| **NONE** | Ignore forwarded headers |
| **NATIVE** | Use the web server/container's forwarded-headers support |
| **FRAMEWORK** | Use Spring Framework's `ForwardedHeaderFilter` or `ForwardedHeaderTransformer` |

Configuration example:

~~~yaml
server:
  forward-headers-strategy: FRAMEWORK
~~~

### 9.1. When to Use `NONE`

Use `NONE` when:

- The application is not behind a proxy.
- Restoring public request metadata is not needed.
- The system lacks a protected forwarded-header trust contract.
- You want to avoid the application applying untrusted headers.

If a proxy terminates TLS and the application needs to generate redirects/public URLs, `NONE` can cause the application to see the internal scheme/host. In that case, configure proper proxy trust before enabling forwarded handling.

### 9.2. When to Use `NATIVE`

`NATIVE` uses the embedded server/container's capability. For example, Tomcat has `RemoteIpValve`; Jetty has `ForwardedRequestCustomizer`. Each container has its own way of configuring trusted proxies.

Do not assume every container has the same defaults or parses proxy chains identically. Read the documentation for the exact server running and trust only controlled source ranges.

### 9.3. When to Use `FRAMEWORK`

`FRAMEWORK` uses Spring Framework:

- Servlet: `ForwardedHeaderFilter`.
- Reactive: `ForwardedHeaderTransformer`.

This option is useful when you want consistent forwarded metadata handling at the framework layer. However, it does not replace edge configuration, network ACLs, or proxy authentication.

### 9.4. Defaults May Depend on the Environment

Spring Boot may set different default strategies depending on the deployment environment. In current documentation, supported cloud platforms may default to `NATIVE`, whereas other environments default to `NONE`.

Do not rely on defaults. Explicitly declare the strategy in deployment configuration and verify behavior on the actual container.

## 10. Tomcat and Trusted Proxy Configuration

If using Tomcat, `RemoteIpValve` can interpret forwarded headers and update the remote address/scheme. Spring Boot allows configuring header names and internal proxy patterns.

Illustrative example:

~~~yaml
server:
  forward-headers-strategy: NATIVE
  tomcat:
    remoteip:
      internal-proxies: "10\\.20\\.0\\.\\d{1,3}"
~~~

The regex above is only an example for a specific internal address range. Replace it with the actual addresses/CIDRs of controlled proxies.

Never configure trust-all-proxies in production. Never set `internal-proxies` to empty to accept all sources. If the container trusts an overly broad proxy range, an unrelated workload can spoof forwarded metadata.

### 10.1. Network Policies Are Still Required

Tomcat's trusted proxy regex is one control layer when interpreting remote IPs. It does not replace firewalls/security groups or mTLS.

The backend should only accept connections from permitted proxies. If an unblocked direct call path exists, ensure the container does not apply forwarded headers to requests from untrusted sources.

## 11. Forwarded Headers and Spring Security Resource Server

Spring Security verifies Bearer tokens based on credentials and trust configuration. Forwarded headers do not alter JWT contents themselves, yet they can influence the request context the application uses in other decisions.

### 11.1. Do Not Use `X-Forwarded-Host` to Pick an Arbitrary Issuer

Issuer/JWKS URIs must come from trusted configuration or a governed tenant registry.

Do not do:

~~~java
String issuer = request.getHeader("X-Forwarded-Host");
ReactiveJwtDecoder decoder =
    ReactiveJwtDecoders.fromIssuerLocation(issuer);
~~~

This turns a request header into a trust-endpoint source and can cause SSRF or verify tokens against an attacker-chosen issuer.

If host is used to route tenants, only map allowlisted hosts to tenant config; after the token is verified, confirm issuer, audience, and tenant claims match the route.

### 11.2. Do Not Use Forwarded Client IP Instead of Authentication

`X-Forwarded-For` can support rate limiting or risk signals after the trust chain is established. It does not replace:

- JWT signature validation.
- Issuer/audience validation.
- Opaque token introspection.
- Scope/role authorization.
- Tenant/owner checks.

Never grant admin privileges or bypass authentication simply because the client IP falls within an IP range, unless it is an independently designed and controlled supplementary policy.

### 11.3. Forwarded Scheme Affects Redirects and OAuth/OIDC Flows

If Spring Security or an OAuth2 client builds a redirect URI from the request, an incorrect scheme/host can produce a mismatched callback URL or send users to an unintended domain.

OAuth2 redirect URIs should be registered exactly at the Authorization Server. Never let an arbitrary forwarded `Host` alter a registered redirect URI.

With a reverse proxy, verify:

- The public scheme is HTTPS.
- The public host/port is right.
- Redirect `Location` uses the right domain.
- Callback URI matches client registration.
- Internal HTTP does not cause cookies/redirects to be created wrongly.
- No direct backend route bypasses proxy policy.

### 11.4. DPoP `htu` Also Depends on Public URI

A DPoP proof contains `htm` and `htu`. `htu` reflects the public target URI called by the client, whereas the backend may see an internal host/scheme/path after proxy rewrites.

If the application compares `htu` against the internal request URI, valid proofs can be rejected. If the application trusts forged forwarded headers, an attacker can manipulate the URI the server uses to verify the proof.

Reconstruct the public URI from source-authenticated proxy metadata, then apply URI normalization per RFC 3986 and DPoP policy. This is why the forwarded-headers trust boundary directly affects token-bound request validation.

## 12. Gateway Identity Headers and Delegation Models

Some gateways authenticate tokens before the application and then add headers:

~~~http
X-Authenticated-User: alice
X-Authenticated-Tenant: tenant-a
X-Authenticated-Scopes: orders.read
~~~

There are two distinct models:

**Model A — The application verifies the access token itself.** The gateway forwards `Authorization: Bearer`; Spring Security Resource Server verifies the token. Identity headers from the gateway are unnecessary for authentication.

**Model B — The gateway verifies the token and issues an assertion to the backend.** The backend trusts the gateway as an internal identity provider. In this model, the assertion must be protected by a verifiable mechanism, such as a signed token with issuer/audience/expiry, or mTLS combined with network policies and an explicit header contract.

Do not blur the two models ambiguously. If the backend trusts `X-Authenticated-User` while still accepting direct requests from the Internet, an attacker can forge the identity header.

### 12.1. If Using a Signed Gateway Assertion

An internal assertion may carry:

~~~json
{
  "iss": "https://gateway.internal.example",
  "aud": ["orders-service"],
  "sub": "alice",
  "tenant_id": "tenant-a",
  "scope": "orders.read",
  "iat": 1893452400,
  "exp": 1893452460
}
~~~

The backend must verify the signature, issuer, audience, `exp`, key lifecycle, and policy. Never treat a plain-text header as an authoritative assertion just because it is named `X-Authenticated-User`.

### 12.2. Do Not Forward the `Authorization` Header Unboundedly

The gateway needs a clear policy on preserving, stripping, or replacing `Authorization`. If the backend needs the original token, forward the right token to the right service. If the backend needs a gateway assertion, do not accidentally allow two conflicting identity sources.

## 13. Trust Configuration by Deployment Type

| Deployment | Source Controls | Forwarded Handling |
|---|---|---|
| Direct public app, no proxy | Client is the direct peer | `NONE` or ignore forwarded headers |
| Single reverse proxy in private subnet | Only proxy can connect to app; strip/overwrite at edge | `NATIVE` or `FRAMEWORK` |
| CDN + load balancer + ingress | Allowlist each hop, normalize chain at edge | Trust chain per proxy |
| Kubernetes ingress | `NetworkPolicy` and ingress-only service exposure | Choose `NATIVE`/`FRAMEWORK`, test ingress |
| Service mesh | mTLS workload identity and policies | Only use metadata from trusted sidecar/gateway |
| Multi-tenant custom domains | Domain registry and host allowlist | Controlled host mapping, verify tenant claim |

No single Spring Boot configuration fits every topology. Trusted proxy ranges, edge sanitization, and backend connection paths determine safety.

## 14. Testing the Forwarded-Header Trust Boundary

Controller unit tests can check logic using request scheme/host, yet they do not prove the proxy stripped client-sent headers. Multi-layer testing is required.

### 14.1. Testing Directly Against the Application

Send requests with forged headers:

~~~http
Forwarded: for=127.0.0.1;host=attacker.example;proto=https
X-Forwarded-For: 127.0.0.1
X-Forwarded-Host: attacker.example
X-Forwarded-Proto: https
X-Forwarded-Port: 443
X-Forwarded-Prefix: /admin
~~~

If the application has no trusted proxy or uses `removeOnly`/`NONE`, these headers must not change the public origin/remote address trusted by the application.

If the application is designed to only accept requests from a proxy, direct access tests must be denied by network policy at the infrastructure layer.

### 14.2. Testing Through a Real Edge Proxy

An integration test should:

1. Send a request from a test client to the public ingress.
2. Include forged `Forwarded` and all `X-Forwarded-*` headers.
3. Verify the proxy strips/overwrites them.
4. Verify the backend sees the configured public scheme/host/path.
5. Verify the client IP is derived from the trusted chain.
6. Verify forwarded headers are not echoed verbatim into responses.
7. Call the backend directly from an unauthorized source and verify it is blocked.

This is the most important test for the trust boundary. `MockMvc` or `WebTestClient` bound directly to the application does not simulate the ingress's network source identity.

### 14.3. Testing `Host` and Redirects

- Valid host produces the right public URL.
- Unknown host is rejected.
- Forged `X-Forwarded-Host` does not alter reset URLs.
- HTTPS redirects use the right domain.
- OAuth callbacks do not change based on client-sent headers.
- Cookie `Secure` and `Domain` attributes match deployment.

### 14.4. Testing Client IP and Rate Limiting

- Client sends forged `X-Forwarded-For`.
- Edge resets incoming values.
- Trusted proxy chain is parsed properly.
- Multiple proxies do not cause selecting the wrong IP.
- Direct backend access is blocked.
- Rate limits cannot be bypassed by changing headers.

### 14.5. Testing Path Prefix and DPoP

- Proxy rewrites the public path properly.
- Forged `X-Forwarded-Prefix` is stripped.
- Public URL is reconstructed properly after rewrite.
- DPoP `htu` is compared against the source-verified public URI.
- Path mismatches are rejected.
- No admin route is exposed due to path normalization differences.

## 15. Observability and Auditing

Forwarded metadata is useful for operations, yet observed data must be distinguished from trusted data.

You should log:

- Direct peer address.
- Derived client address after trusted-proxy parsing.
- Logical proxy/ingress identity.
- Normalized host/scheme.
- Request ID.
- Tenant verified from the principal.
- Authentication/authorization result.

Never log raw `Authorization` tokens. Avoid storing the full proxy chain if unnecessary, as RFC 7239 notes this data can expose network topology and private information.

Never put arbitrary forwarded hosts, arbitrary client IPs, or raw headers into unbounded-cardinality metric labels.

## 16. Anti-Patterns to Avoid

**Trusting `Forwarded` because it is an RFC standard header.** RFC 7239 defines the format, not sender authentication.

**Stripping `Forwarded` while keeping `X-Forwarded-*`.** Another library may read the remaining header family.

**Stripping only `X-Forwarded-For`.** `X-Forwarded-Host`/`Proto`/`Port`/`Prefix` can still be spoofed.

**Using `$proxy_add_x_forwarded_for` at the edge without resetting input.** Clients can inject fake addresses at the head of the chain.

**Leaving the application backend directly reachable from the Internet.** Attackers can bypass the edge and send forged headers directly.

**Trusting every proxy in a private subnet.** A private address does not by itself prove a workload is an authorized proxy.

**Using `X-Forwarded-Host` to build issuer/JWKS URLs.** Can open SSRF and arbitrary trust endpoints.

**Using `X-Forwarded-For` as user identity.** IP does not replace `Authentication`.

**Using plain-text `X-Authenticated-User` as the principal.** A header without a signature/trust contract can be forged.

**Enabling `FRAMEWORK` and assuming Spring authenticates the proxy.** The filter/transformer only applies metadata; the trusted source must be protected at the edge/network.

**Configuring `NATIVE` without checking the container's trusted proxies.** The container may accept forwarded values from an overly broad range of sources.

**Trusting arbitrary `X-Forwarded-Prefix`.** Can corrupt public paths and authorization/routing.

**Trusting forwarded proto to claim the backend connection is encrypted.** TLS termination and backend transport are two separate connections.

**Testing only with `MockMvc`.** Does not prove edge header stripping or network ACLs work.

**Not testing direct backend access.** The trust boundary may be bypassable.

## 17. Safe Deployment Process

**Step 1 — Diagram the proxy chain.** Record client, CDN, load balancer, ingress, service mesh, and application.

**Step 2 — Define the source of truth for each field.** Client IP, public host, scheme, port, and path prefix must each have a clear source.

**Step 3 — Strip incoming headers at the edge.** Clear `Forwarded` and all `X-Forwarded-*` before generating new values. Handle any relevant vendor-specific headers too.

**Step 4 — Allowlist hosts/domains.** Never use client-sent `Host` to build tenants or arbitrary absolute URLs.

**Step 5 — Overwrite metadata.** Emit `Forwarded` or `X-Forwarded` per a consistent contract; avoid preserving client-controlled chains.

**Step 6 — Lock down the backend path.** Only permitted proxies may connect; use firewalls/network policies and TLS/mTLS where appropriate.

**Step 7 — Configure Spring Boot explicitly.** Choose `NONE`, `NATIVE`, or `FRAMEWORK` based on topology and container.

**Step 8 — Restrict trusted proxy ranges.** Never trust all proxies; properly configure Tomcat/Jetty/Reactor Netty or ingress behavior.

**Step 9 — Keep Authentication independent.** Verify JWT/opaque tokens, issuer, audience, scope, and tenant from trusted sources.

**Step 10 — Verify URLs/redirects.** Test public origin, OAuth callbacks, cookies, DPoP `htu`, and path rewrites.

**Step 11 — Test spoofing through ingress.** Send forged `Forwarded` and `X-Forwarded-*`; confirm the edge overwrites them.

**Step 12 — Test bypasses and operations.** Block direct backend access, log peer/client IPs separately, and monitor proxy configuration changes.

## 18. Self-Check Questions

**1. Are `Forwarded` and `X-Forwarded-*` inherently trustworthy because proxies use them?**

No. Clients can also send those headers. Proxies at the trust boundary must strip/overwrite incoming values.

**2. Is it necessary to strip both `Forwarded` and `X-Forwarded-*`?**

Yes. One component may read one standard while another reads the other.

**3. Does `ForwardedHeaderFilter` authenticate the proxy?**

No. It applies forwarded metadata to the Servlet request and removes the headers from the request view.

**4. Which stack is `ForwardedHeaderTransformer` used for?**

The WebFlux/reactive stack; it adapts `ServerHttpRequest` before `ServerWebExchange` is created.

**5. Does Spring Boot `FRAMEWORK` replace edge sanitization?**

No. The proxy must still strip client-sent data and the backend must only accept traffic from permitted proxy sources.

**6. Should an issuer URL be taken from `X-Forwarded-Host`?**

No. Issuer/JWKS must come from trusted configuration or a tenant registry.

**7. Should the first element of `X-Forwarded-For` always be taken as the client IP?**

Not by default. The chain must be parsed according to the configured trusted proxy chain.

**8. Why is direct backend access dangerous?**

Attackers can bypass the edge and send forged forwarded headers directly.

**9. How do `NATIVE` and `FRAMEWORK` differ?**

`NATIVE` uses the web server/container's support; `FRAMEWORK` uses `ForwardedHeaderFilter` or `ForwardedHeaderTransformer`.

**10. Does `Forwarded proto=https` prove the backend connection uses TLS?**

No. It only describes the public scheme observed by the proxy.

**11. Can DPoP `htu` be affected by forwarded headers?**

Yes. The Resource Server must reconstruct a trustworthy public URI to compare against the proof's `htu`.

**12. Does a `MockMvc` test prove the proxy strips forged headers?**

No. You need integration tests through the real ingress/proxy and checks for direct backend access.

## Conclusion

Forwarded headers help Spring applications understand the public request after passing through a proxy, yet **they are only trustworthy when the sender source is identified and protected**. Clients can send `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, and `X-Forwarded-Prefix` themselves. If an edge proxy forwards them unmodified, an attacker can spoof client IP, host, scheme, or path.

Protection must start at the trust boundary: strip/overwrite both header families, validate the host, generate metadata from the actual connection, and allow only managed proxies to connect to the backend. Where needed, use network ACLs and mTLS to authenticate proxies. In Spring Boot, explicitly choose `NONE`, `NATIVE`, or `FRAMEWORK`; `ForwardedHeaderFilter` and `ForwardedHeaderTransformer` only process request metadata and do not verify the source.

With Spring Security Resource Server, never use forwarded headers as identity, issuer, or authorization claims. Verify access tokens independently, check audience/tenant, and use the safely reconstructed public URI for redirects or DPoP. **A deployment can only be considered secure when ingress tests prove forged headers are stripped and the backend cannot be called bypassing the proxy.**
