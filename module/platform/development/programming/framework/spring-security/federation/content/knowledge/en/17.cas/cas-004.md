# The `service` Parameter and Registering Applications Permitted to Use CAS

## Learning Objectives

After this lesson, you will be able to:

1. Explain the roles of **CAS Server**, **CAS Client/Service**, **Service Ticket (ST)**, **Ticket-Granting Ticket (TGT)**, and **Service Registry** in Central Authentication Service.
2. Explain why the **`service`** parameter appears in `/login`, `/serviceValidate`, and `/p3/serviceValidate` and why **the service URL when validating a ticket must correspond to the service URL for which the ticket was issued**.
3. Distinguish between **CAS service identifier** (the specific callback URL) and **Registered Service `serviceId`** (the pattern/rule used to decide which applications are permitted to use CAS).
4. Author a safe Apereo CAS Registered Service definition restricting HTTPS/callback, avoiding overly broad regular expressions, configuring access strategy, and controlling attribute release.
5. Integrate a consistent callback URL with **Spring Security CAS** using `ServiceProperties`, `CasAuthenticationEntryPoint`, `CasAuthenticationFilter`, and `CasAuthenticationProvider`; understand the role of `Cas20ServiceTicketValidator`.
6. Diagnose `INVALID_SERVICE`, `INVALID_TICKET`, wrong URLs behind a reverse proxy, scheme/host/path/query mismatches, lost tickets, replay, and unregistered services.
7. Apply **deny by default**, onboard partners with approval, disable services when no longer trusted, test multiple environments/tenants, and keep Service Tickets out of logs and unnecessary browser history.
8. Run a **standalone Java 17+** program to observe `service` URL encoding and an exact-matching policy; clearly understand that regex demos do not replace the CAS Server.

## 1. What Problem Does CAS Solve?

**CAS – Central Authentication Service** provides Single Sign-On (SSO) across multiple applications. A user already logged in to CAS can access a permitted **Service** without re-entering their password per SSO policy.

Core entities:

| Entity | Example | Responsibility |
| --- | --- | --- |
| **CAS Server** | `https://sso.example.org/cas` | Authenticates users, manages TGT/SSO session, issues and validates service tickets, evaluates Service Registry |
| **CAS Client / Service** | Portal `https://portal.example.org` | Redirects browser to CAS, receives ST at callback, and calls CAS ticket validation |
| **Service URL** | `https://portal.example.org/login/cas` | URL receiving the ST, bound upon ticket issuance and used during validation |
| **Service Registry** | CAS Server's `RegisteredService` list | Allows only approved apps/URLs to use CAS and enforces policies |
| **Service Ticket (ST)** | `ST-...` | Short-lived, opaque, single-use credential confirming the user for the corresponding service |
| **Ticket-Granting Ticket (TGT)** | Managed by CAS after login | Allows CAS to issue new STs within the SSO session per policy |
| **Ticket-Granting Cookie (TGC)** | Cookie on the CAS domain | Enables the browser to reference the CAS SSO session; not a callback service URL |

A service is not trusted by default merely because it points to `https://` or because the browser already holds a CAS SSO cookie. The CAS Server must verify **allowed applications/targets** before issuing a ticket and during verification. This service-registry layer prevents CAS from becoming an open SSO portal issuing tickets to arbitrary stranger-chosen addresses.

### 1.1. Distinguishing the CAS Protocol from SAML2/OIDC

- The native CAS protocol typically passes **`service` and `ticket`** via redirect, after which the application calls `/serviceValidate` or an equivalent endpoint to verify the ticket.
- SAML2 uses **`AuthnRequest`, `SAMLResponse`, Assertions, ACS, EntityID, and XML Signatures**. `RelyingPartyRegistrationRepository` is a Spring Security SAML2 concept, **not** the CAS Service Registry.
- OIDC uses `client_id`, `redirect_uri`, authorization codes, ID tokens, and its own checks.
- A CAS Server can support SAML/OIDC as well depending on modules, but **the native CAS protocol's `service`** cannot be equated with OIDC's `redirect_uri` or SAML's `AssertionConsumerServiceURL`.

This lesson focuses on the **CAS protocol and permitting an application to use CAS**, using a Spring Security Servlet application as the example.

## 2. Login Flow: Why Does the `service` Parameter Matter?

Suppose the browser accesses `/reports` on `portal.example.org` without an app session yet.

```mermaid
sequenceDiagram
    actor U as User
    participant B as Browser
    participant APP as Spring Security CAS Client
    participant CAS as CAS Server
    participant REG as CAS Service Registry
    U->>B: Open /reports
    B->>APP: GET /reports (anonymous)
    APP-->>B: 302 /cas/login?service=URL_ENCODED_CALLBACK
    B->>CAS: GET /cas/login?service=...
    CAS->>REG: Is this service callback allowed?
    alt Service unregistered/prohibited
        REG-->>CAS: Deny
        CAS-->>B: Service unauthorized; do not issue ticket
    else Service permitted
        REG-->>CAS: Allowed
        CAS->>U: Prompt login or use SSO session
        U->>CAS: Complete authentication
        CAS->>CAS: Issue short-lived ST for requested service
        CAS-->>B: 302 https://portal.example.org/login/cas?ticket=ST-...
        B->>APP: GET /login/cas?ticket=ST-...
        APP->>CAS: GET /cas/serviceValidate?service=...&ticket=ST-...
        CAS->>CAS: Verify ST unexpired, unused, exact service
        CAS-->>APP: XML authenticationSuccess or failure
        APP->>APP: Bind Authentication + authorities/session
        APP-->>B: Redirect to /reports
    end
```

**Protocol characteristics:**

1. The SP/Client sends `/cas/login` the `service` parameter specifying the callback URL to which CAS will redirect the browser.
2. CAS checks this URL against the **Service Registry**, applies `RegisteredService` policies, and proceeds only for permitted service types.
3. After authentication, CAS redirects the browser to the **service URL** with `ticket` (usually in the query string).
4. The service receives `ticket` and contacts CAS `/serviceValidate` **directly over HTTPS**, passing the **exact matching service identifier** bound to the ticket.
5. CAS verifies **ticket–service binding**, validity, and one-time use. A success response includes user/attributes within policy limits.
6. The application **maps** the user to a local account/permissions and creates a session; CAS authentication success **does not automatically grant `ROLE_ADMIN`**.

Never equate the browser seeing `ticket=ST-...` with successful authentication. **The ticket must be validated by the CAS Server**, for the exact service, while still valid.

### 2.1. Three Different URLs That Must Never Be Mixed Up

| URL | Correct Role | Example |
| --- | --- | --- |
| **CAS login URL** | Where the browser goes to log in | `https://sso.example.org/cas/login` |
| **Service callback URL** | Where CAS redirects with `ticket` | `https://portal.example.org/login/cas` |
| **CAS validation URL** | Where the app calls server-to-server to validate the ticket | `https://sso.example.org/cas/serviceValidate` |

Mistakenly setting `service=https://sso.example.org/cas/serviceValidate` tells CAS to treat the CAS Server endpoint as the service callback rather than the application portal. Setting `service=https://portal.example.org/reports` when the Spring filter only handles `/login/cas` also breaks ticket reception, unless the integration intentionally supports that path.

## 3. The `service` Parameter in the CAS Protocol

### 3.1. `/login?service=...`

The CAS Protocol Specification defines `service` (case-sensitive parameter name) as the **identifier of the application** being requested. It is typically an HTTPS URL to which the browser will be redirected after login.

Example:

```http
GET /cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas HTTP/1.1
Host: sso.example.org
```

URL-decoding the **parameter value** yields:

```text
service = https://portal.example.org/login/cas
```

**Implications:**

- The callback URL must belong to CAS's **allowed Service Registry**.
- CAS can enforce access, MFA, SSO, attribute release, expiration, and service-specific authentication policies.
- CAS must never treat an arbitrary browser-supplied `service` as an open redirect.
- If `service` is omitted, CAS may handle login/SSO session without issuing a ticket for a specific application depending on protocol/deployment; never assume omitting `service` names a default application.

### 3.2. `/serviceValidate?service=...&ticket=...`

A client receiving an ST at the callback calls:

```http
GET /cas/serviceValidate?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&ticket=ST-EXAMPLE HTTP/1.1
Host: sso.example.org
```

**Two required parameters** for `/serviceValidate` under CAS 2.0:

- **`service`:** identifier of the callback URL for which the ticket was issued.
- **`ticket`:** the ST just issued by CAS to the browser.

CAS verifies that the ticket matches the service, is unexpired, unused, and satisfies other conditions. **An ST cannot be used for a different service.** If two URLs differ only in hostname/path/port/query and CAS treats them as different service identifiers, validation may be rejected.

**Service Tickets are single-use.** Per the specification, an ST is invalidated after **one validation attempt**, whether it succeeds or fails. Never design “retry validation with the exact same ST” as a normal recovery strategy once a request that CAS may have processed has been sent. When re-login is needed, start a new flow and obtain a new ticket.

### 3.3. Other CAS Endpoints

| Endpoint | Function | Key Point |
| --- | --- | --- |
| `/login` | Requests SSO/login, issues ST for `service` | Service Registry must filter allowed services |
| `/validate` | CAS 1.0, returns simple response | Differs in semantics/scope from CAS 2.0 |
| `/serviceValidate` | CAS 2.0 ST validation, XML response | `service` + `ticket` required |
| `/p3/serviceValidate` | Common CAS 3.0 endpoint with attributes | Verify CAS Server support/config; still enforces ticket/service |
| `/proxyValidate` | Validates proxy tickets per CAS protocol | Adds proxy chain policies |
| `/logout` | Supports CAS logout/SSO | Does not guarantee all app sessions are revoked |

Do not hard-code an endpoint from an old guide without checking the deployed server/version. Many modern CAS Servers still support CAS2/CAS3, but policies and API response options may differ.

### 3.4. `renew`, `gateway`, and Extension Flags

- **`renew=true`:** requires primary authentication rather than accepting an existing SSO session as defined by CAS. Clients can set `ServiceProperties.setSendRenew(true)` for especially sensitive areas.
- **`gateway=true`:** enables non-interactive SSO probing; if no suitable session exists, CAS may return to the service without issuing an ST. The client must handle “no ticket” per protocol.
- **`gateway` and `renew`:** the specification notes incompatible/undefined cases; never combine both flags and assume safe behavior.
- **`warn`:** some CAS protocol versions/deployments show a warning before transferring authentication; check your actual profile and contract.
- **`pgtUrl`:** when using CAS proxying, the callback URL requesting a Proxy-Granting Ticket is a separate configuration scope requiring HTTPS and distinct trust. Never confuse `pgtUrl` with the ST login `service`.

**Never enable `renew` as a workaround for a wrong service URL or broken ticket validation.** `renew` changes freshness requirements for authentication; it does not make an unregistered URL valid.

## 4. What Are Registered Service and Service Registry?

The **CAS Service Registry** is the configuration store on the CAS Server describing which applications are **permitted** to participate in SSO. A `RegisteredService` record is not just a URL; it can contain:

- `id`: unique numeric ID of the registry record, not a user ID or ST.
- `name`: display/identifying name of the application.
- `serviceId`: identifier pattern or literal used to **match the requested service URL**.
- `evaluationOrder`: priority when multiple service definitions could match.
- `accessStrategy`: enables or disables the service, SSO policy, and constraints.
- Attribute release policies: releases only permitted attributes per application.
- Authentication/MFA/consent/expiration/renew/SSO policies depending on CAS version/modules.
- Metadata about owner, logo, information/privacy URLs, descriptions, and lifecycle management.
- Policies for proxying, high-risk logins, or extensions when enabled.

**Important:** `service` is the **value requested by the client in the CAS flow**. `serviceId` is the **server-side rule evaluating whether that service is permitted**. They need not be identical strings: for example, a `serviceId` regex may allow a group of callback URLs, while each ST remains bound to a **specific service URL**.

### 4.1. Comparing the Two Values

```text
Client requests:
  service = https://portal.example.org/login/cas

CAS Registry:
  name      = "Portal Production"
  serviceId = ^https://portal[.]example[.]org/login/cas$

CAS decision:
  serviceId matches service?  YES
  service enabled/allowed?    YES
  issue ST for service?       YES, subject to authentication/policy
```

If a client requests:

```text
service = https://attacker.example.net/callback
```

Portal's strict registry pattern **does not match**, and CAS must **reject using this service**, issuing no ST to the attacker endpoint.

### 4.2. Why Not Register an Overly Broad `serviceId`?

**Dangerous** examples:

```text
^https?://.*
^https://.*
.*example.*
^https://portal.example.org.*
```

These patterns can open up unexpected applications or hostnames. An unescaped `.` in regex matches **any character**. `^https://portal.example.org.*` can match hostnames like `portalXexampleYorg.evil.net` or uncontrolled callback paths.

**Rule:** by default, register the **exact scheme + host + port (if any) + callback path**, without using wildcards just to reduce file count. If variable queries/paths are truly required, perform separate canonicalization, callback routing, and threat-model analysis.

## 5. Matching Strategies: Full Regex, Partial Regex, Literal

Apereo CAS supports service identifier matching strategies depending on version:

| Strategy | How It Matches | When Appropriate? | Risks |
| --- | --- | --- | --- |
| **Full regex** | Matches against the entire `service`, implicitly adding anchor semantics | Tightly constrained callback patterns | Unescaped `.`, `.*`, or regex groups |
| **Partial regex** | Accepts a substring match | Only when genuinely needed and reviewed | Easy for attacker URLs containing a valid substring |
| **Literal** | Matches a fixed string directly (config may control case sensitivity) | A single fixed callback | Requires understanding client canonicalization/port/query |
| **Custom matching** | Custom CAS deployment policy | Complex multi-tenant contracts | Needs testing for URL parsing, normalization, SSRF, and allowlisting |

Apereo CAS documentation on Full Regex states it **matches the entire service identifier**. Even when the engine implicitly anchors, writing `^` and `$` explicitly in example configs prevents readers from mistaking it for substring regex.

**Do not treat Java `Pattern.matches(...)` as an exact simulation of every CAS matching strategy**, since CAS may apply normalization/transformation steps or version-specific rules. Use unit/integration tests against the real CAS runtime to conclude.

### 5.1. A JSON Registered Service for a Fixed Production Callback

Assuming the CAS Server has enabled the **JSON Service Registry** module compatible with the deployed version.

Example file `PortalProduction-10001.json` in the managed registry directory:

```json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "name": "Portal Production",
  "description": "CAS login for production portal",
  "id": 10001,
  "evaluationOrder": 10,
  "serviceId": "^https://portal[.]example[.]org/login/cas$",
  "matchingStrategy": {
    "@class": "org.apereo.cas.services.FullRegexRegisteredServiceMatchingStrategy"
  },
  "accessStrategy": {
    "@class": "org.apereo.cas.services.DefaultRegisteredServiceAccessStrategy",
    "enabled": true,
    "ssoEnabled": true
  }
}
```

**Field-by-field explanation:**

- `@class` declares the Registered Service subtype for Apereo CAS's JSON registry.
- `id` is a **unique number** in the registry. Never reuse the same numeric ID across two files.
- `name` and `description` are for administration, not the technical identifier used to issue STs.
- `serviceId` permits **only one callback URL**: Portal's HTTPS origin and `/login/cas` path.
- `[.]` instead of `\.` avoids double-escaping backslashes in JSON; both represent a literal dot in regex.
- `evaluationOrder` sets definition evaluation order; avoid overlapping service patterns causing unpredictable matches.
- `matchingStrategy` explicitly specifies full regex; class names and schemas can vary by CAS release, so verify against your pinned CAS Server version.
- `accessStrategy.enabled=true` allows use when other policies are satisfied; `ssoEnabled=true` permits SSO sessions per policy. Even when enabled, it **does not grant admin privileges inside Portal**.
- If attribute release is needed, add specific approved policies; **never release all directory attributes by default**.

**This is a CAS server configuration file**, not the Spring Boot client's `application.yml`. A CAS Client has no authority to add JSON service definitions onto the server at login time.

### 5.2. Enabling the JSON Registry for the Chosen CAS Server

Module typically required in the **CAS server overlay** (artifact/version managed via CAS BOM):

```groovy
dependencies {
    implementation "org.apereo.cas:cas-server-support-json-service-registry"
}
```

In `application.yml` **on the CAS Server side**:

```yaml
cas:
  service-registry:
    json:
      location: "file:/etc/cas/services"
```

The path is illustrative: the directory must be properly mounted/deployed for the CAS process. The JSON registry may watch files and reload depending on config/version, but **does not guarantee automatic multi-node synchronization**. In a cluster, every CAS node must receive identical definitions; verify revisions/digests and run negative tests.

Property names and modular dependencies can change across CAS upgrades. Always check version-pinned documentation; `development` docs reflect unreleased code and do not guarantee identical settings across environments.

### 5.3. Suspending an Application: Disabling Service Access

One way to temporarily stop accepting a service in the registry is via its access strategy:

```json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "name": "Portal Production",
  "id": 10001,
  "serviceId": "^https://portal[.]example[.]org/login/cas$",
  "accessStrategy": {
    "@class": "org.apereo.cas.services.DefaultRegisteredServiceAccessStrategy",
    "enabled": false
  }
}
```

Under baseline CAS policy, `enabled=false` rejects the service similarly to an unregistered service. However, this state **does not automatically delete already-logged-in Portal application sessions**, API keys, or other refresh tokens. You need an independent plan to revoke sessions/grants.

**Do not confuse `ssoEnabled=false` with `enabled=false`:** `ssoEnabled=false` can force primary authentication on every entry to the service while still **allowing the service to use CAS**. To **suspend an application**, disable service access or remove the definition and verify every CAS node.

### 5.4. Do Not Use a Catch-All Regex Across Services for “Convenience”

Each application/environment should have a managed record, or a narrow policy with explicit choices. Never use:

```json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "name": "All Web Apps - UNSAFE",
  "id": 999999,
  "serviceId": "^https://.*"
}
```

This is an **intentional anti-pattern**: any HTTPS URL matches, enabling the CAS server to redirect browsers/tickets to attacker-owned endpoints. Never deploy this example.

## 6. The Service URL Must Be Consistent Across Login, Callback, and Validation

Suppose the Spring Security CAS Client is configured with:

```text
ServiceProperties.service =
  https://portal.example.org/login/cas

CasAuthenticationFilter.filterProcessesUrl =
  /login/cas

CAS Server RegisteredService.serviceId =
  ^https://portal[.]example[.]org/login/cas$
```

When login begins, `CasAuthenticationEntryPoint` redirects the browser to CAS `/login?service=...`. Once CAS issues an ST, the browser returns to `https://portal.example.org/login/cas?ticket=ST-...`. The filter intercepts the ticket; the provider/ticket validator calls CAS `/serviceValidate` using the corresponding **`ServiceProperties.service`**.

Verify consistency in three places:

1. **The `service` URL sent to CAS `/login`.**
2. **The callback URL to which CAS redirects and that the Spring filter actually handles.**
3. **The `service` URL sent when the app calls CAS ticket validation.**

If they differ, never “fix” it by disabling service matching on CAS. Fix URL generation, proxy/callback routing, and configuration consistently.

### 6.1. Small Differences That Cause Big Failures

| Login `service` | Validate `service` / Callback | Expected Result |
| --- | --- | --- |
| `https://portal.example.org/login/cas` | Same URL | May succeed if service is registered and ST is valid |
| `http://portal.example.org/login/cas` | `https://portal.example.org/login/cas` | Likely mismatch; HTTP should not be used in production |
| `https://portal.example.org/login/cas` | `https://portal.example.org/app/login/cas` | Different path |
| `https://portal.example.org/login/cas` | `https://portal.example.org:8443/login/cas` | Different explicit port |
| `https://portal.example.org/login/cas` | `https://portal.internal:8080/login/cas` | Public vs. private hostname mismatch, proxy misconfiguration |
| `https://portal.example.org/login/cas` | `https://portal.example.org/login/cas/` | Trailing slash mismatch |
| `https://portal.example.org/login/cas` | `https://portal.example.org/login/cas?next=/admin` | Extra query can alter the service identifier |
| `https://portal.example.org/login/cas` | `https://portal.example.org/login/cas?ticket=ST-...` | **Never** treat the ticket query as part of the base validation service |

CAS and client libraries may normalize certain URLs depending on version/service matching strategy; **never rely on undocumented normalization**. In tests, log the exact service string sent to `/login` and `/serviceValidate`, along with the match outcome.

### 6.2. Reverse Proxies and HTTPS Termination

A Spring Boot application running internally:

```text
Browser -> https://portal.example.org/login/cas
Ingress -> http://portal-app:8080/login/cas
```

If the app builds `service` from `HttpServletRequest` without understanding external scheme/host (or trusts arbitrary `X-Forwarded-*` headers sent by browsers), it may emit:

```text
http://portal-app:8080/login/cas
```

The approved CAS registry allows only `https://portal.example.org/login/cas`, so it rejects the request.

Remediation:

- Prefer configuring a **static/canonical public HTTPS service URL** for single-callback applications.
- If relying on forwarded headers, **trust only a controlled reverse proxy**; never allow clients to send arbitrary `X-Forwarded-Host` values and turn them into the service URL.
- Audit `Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`, context path, servlet mapping, load balancer rewrites, and header spoofing.
- The actual callback must reside on the filter-monitored path. **Never use a user-supplied dynamic redirect target as the service URL**.
- If a proxy serves multiple hosts/tenants, use a per-tenant/per-host allowlist and security review; never concatenate strings from HTTP `Host` blindly.

### 6.3. URL Encoding: Encode Only the Parameter Value

In the CAS login query, `service` is a **URL value**, so it must be percent-encoded when embedded inside another URL:

```text
Service URL:
  https://portal.example.org/login/cas

Put in query:
  https://sso.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
```

Do not URL-encode the **entire** CAS login URL into a string without `?service=...`. Do not double URL-decode, mishandle `+`/`%2F`, or append `&ticket=...` to the canonical service.

## 7. Standalone Java 17+: Simulating Exact Service Policy and Encoding

This snippet **runs on JDK 17+** without Spring or CAS. It demonstrates an exact-match regex policy and URL encoding of the `service` parameter. **It does not issue tickets, validate the CAS protocol, or create sessions**. The CAS server must still be the authority deciding real service access.

**File `CasServicePolicyDemo.java`:**

```java
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.util.regex.Pattern;

public final class CasServicePolicyDemo {
    private static final String CANONICAL_SERVICE =
            "https://portal.example.org/login/cas";

    // Java regex matches the full URL. CAS has its own matching strategies.
    private static final Pattern ALLOWED = Pattern.compile(
            "^https://portal[.]example[.]org/login/cas$");

    static boolean isAllowed(String service) {
        return service != null
                && ALLOWED.matcher(service).matches();
    }

    public static void main(String[] args) {
        String loginUrl = "https://sso.example.org/cas/login?service="
                + URLEncoder.encode(
                        CANONICAL_SERVICE, StandardCharsets.UTF_8);

        System.out.println("CAS login: " + loginUrl);
        System.out.println("Canonical allowed: "
                + isAllowed(CANONICAL_SERVICE));
        System.out.println("HTTP allowed: "
                + isAllowed("http://portal.example.org/login/cas"));
        System.out.println("Attacker subdomain allowed: "
                + isAllowed("https://portal.example.org.evil.test/login/cas"));
        System.out.println("Different path allowed: "
                + isAllowed("https://portal.example.org/admin"));
        System.out.println("Extra query allowed: "
                + isAllowed(CANONICAL_SERVICE + "?next=/admin"));
        System.out.println("Unknown service allowed: "
                + isAllowed("https://unknown.example.org/login/cas"));
        System.out.println("Trust established by demo: false");
    }
}
```

Compile and run:

```bash
javac CasServicePolicyDemo.java
java CasServicePolicyDemo
```

**Exact stdout:**

```text
CAS login: https://sso.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
Canonical allowed: true
HTTP allowed: false
Attacker subdomain allowed: false
Different path allowed: false
Extra query allowed: false
Unknown service allowed: false
Trust established by demo: false
```

**Explanation:**

- `URLEncoder.encode(service, UTF_8)` formats the callback string as a syntactically valid query value. That is not a trust check.
- `Pattern.matcher(...).matches()` requires matching the full URL, constraining the callback path in the fixture.
- `[.]` matches a literal dot; using an unescaped `.` in regex allows many unintended hostnames to match erroneously.
- `portal.example.org.evil.test` is rejected instead of accepted merely for sharing a prefix with an approved host.
- `?next=/admin` is rejected under the demo's **strict callback** policy because the service URL no longer equals the canonical identifier.
- **Never use this program in place of a real Service Registry**; CAS matching strategies, normalization, service access policies, authentication, and ticket validation reside on the CAS Server.
- Never assume an exact regex protects the entire application: the Spring Security client must still call CAS `/serviceValidate`, validate tickets, and enforce role-based access properly.

### 7.1. Why Not Try “Decoding Until It Matches”?

A URL can be percent-encoded in multiple forms, carry default ports, trailing dots in hostnames, case differences, slashes, or differing query order. Having an application repeatedly decode until an allowed regex matches creates **canonicalization ambiguity** and bypass risks.

In a real architecture:

1. **The SP defines an approved canonical URL** for the public HTTPS callback.
2. The CAS Server uses a **well-understood matching strategy** tested against bypasses.
3. Never let the browser modify the service URL or supply an arbitrary redirect target.
4. The CAS Client sends the **exact matching service identifier** to both `/login` and `/serviceValidate`.
5. If multiple callbacks are needed, register a specific set of URLs using narrow definitions/regexes covered by tests.

## 8. Spring Security CAS Client: Service-Related Components

In Spring Security Servlet CAS integration:

| Bean/Class | Role |
| --- | --- |
| `ServiceProperties` | Holds the canonical service URL; includes `sendRenew` and other options |
| `CasAuthenticationEntryPoint` | Redirects browser to CAS `/login` with configured `service` |
| `CasAuthenticationFilter` | Listens on the callback path, usually `/login/cas`; extracts `ticket` from request |
| `CasAuthenticationProvider` | Uses a ticket validator to authenticate the ST and build Spring `Authentication` |
| `Cas20ServiceTicketValidator` | CAS client library calling CAS server `/serviceValidate` over HTTPS |
| `UserDetailsService` / `AuthenticationUserDetailsService` | After CAS validation, maps the authenticated user to application authorities |
| `SecurityContextRepository`/session | Stores Spring authentication after login per web policy |
| CAS Server `RegisteredService` | **Separate configuration on the CAS Server**, deciding which Service URLs may use SSO |

**Consistency point:** `ServiceProperties.service` must correspond to the URL monitored by `CasAuthenticationFilter`. If the filter listens on `/login/cas` while the service URL is `/cas-callback` without matching mapping/canonical behavior, the user may receive an ST that no filter validates.

### 8.1. Dependencies in a Spring Boot 3 / Spring Security 6 Project

Example `build.gradle` snippet in a Spring Boot project that already declares the Spring Boot plugin and BOM:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.security:spring-security-cas'

    // The CAS Client library must be Jakarta Servlet compatible when using
    // integrations with servlet filters on Spring Boot 3.
    implementation 'org.apereo.cas.client:cas-client-core'
}
```

This is an **illustrative dependencies snippet**, not a complete build script. Choose a **CAS Client version and artifact whose API is compatible** with your Spring Security version; verify transitive dependencies, Jakarta Servlet/`javax.servlet` alignment, and security advisories. Do not blindly add both Spring Security's `CasAuthenticationFilter` and servlet filters from CAS Client without understanding ordering and double-authentication effects.

### 8.2. Bean Configuring Service URL and Entry Point

File `src/main/java/com/example/cas/CasConfig.java` (Spring configuration excerpt):

```java
package com.example.cas;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;

@Configuration
public class CasConfig {

    public static final String SERVICE_URL =
            "https://portal.example.org/login/cas";
    public static final String CAS_BASE =
            "https://sso.example.org/cas";

    @Bean
    ServiceProperties serviceProperties() {
        ServiceProperties properties = new ServiceProperties();
        properties.setService(SERVICE_URL);
        properties.setSendRenew(false);
        return properties;
    }

    @Bean
    CasAuthenticationEntryPoint casEntryPoint(
            ServiceProperties serviceProperties) {
        CasAuthenticationEntryPoint entry = new CasAuthenticationEntryPoint();
        entry.setLoginUrl(CAS_BASE + "/login");
        entry.setServiceProperties(serviceProperties);
        return entry;
    }
}
```

Explanation:

- `SERVICE_URL` must be permitted by the CAS Server in its **Service Registry**.
- `CAS_BASE` uses HTTPS with a valid TLS certificate; never accept redirects/callbacks to a browser-chosen CAS Server.
- `setSendRenew(false)` uses SSO sessions per policy. If business logic requires primary authentication, consider `true` and matching server config; never use `renew` to bypass the registry.
- This configuration **does not automatically register the service on the CAS Server**; a CAS administrator must still create the Registered Service.
- Across multiple environments/tenants, load canonical configuration from an approved allowlist/config store rather than assembling URLs from arbitrary `Host` headers.

### 8.3. `AuthenticationProvider` and Filter Chain (Integration Pattern)

File `src/main/java/com/example/cas/CasSecurityConfiguration.java`:

```java
package com.example.cas;

import org.apereo.cas.client.validation.Cas20ServiceTicketValidator;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.authentication.CasAuthenticationProvider;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;
import org.springframework.security.cas.web.CasAuthenticationFilter;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UserDetailsByNameServiceWrapper;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class CasSecurityConfiguration {

    @Bean
    CasAuthenticationProvider casAuthenticationProvider(
            ServiceProperties serviceProperties,
            UserDetailsService applicationUsers) {
        CasAuthenticationProvider provider = new CasAuthenticationProvider();
        provider.setKey("portal-cas-auth-provider");
        provider.setServiceProperties(serviceProperties);
        provider.setTicketValidator(new Cas20ServiceTicketValidator(
                CasConfig.CAS_BASE));
        provider.setAuthenticationUserDetailsService(
                new UserDetailsByNameServiceWrapper<>(applicationUsers));
        return provider;
    }

    @Bean
    AuthenticationManager casAuthenticationManager(
            CasAuthenticationProvider provider) {
        return new ProviderManager(provider);
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            CasAuthenticationEntryPoint entry,
            AuthenticationManager casAuthenticationManager,
            ServiceProperties serviceProperties) throws Exception {
        CasAuthenticationFilter filter = new CasAuthenticationFilter();
        filter.setFilterProcessesUrl("/login/cas");
        filter.setServiceProperties(serviceProperties);
        filter.setAuthenticationManager(casAuthenticationManager);

        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error").permitAll()
                .anyRequest().authenticated());
        http.exceptionHandling(errors -> errors.authenticationEntryPoint(entry));
        http.addFilterAt(filter, CasAuthenticationFilter.class);
        return http.build();
    }
}
```

**Scope and prerequisites:**

- This sample requires a **real** application `UserDetailsService` (DB/IAM/local repository) to load authorities for the CAS-authenticated user. Never auto-grant `ROLE_ADMIN` merely because a username/group string contains “admin”.
- Requires a real CAS Server, trusted HTTPS, a Service Registry permitting `https://portal.example.org/login/cas`, and compatible Java/Spring/CAS Client modules/versions.
- The filter is instantiated inside `SecurityFilterChain` rather than exposed as a standalone servlet `Filter` bean to prevent Spring Boot from accidentally auto-registering it a second time.
- `CasAuthenticationFilter` monitors only `/login/cas`; `ServiceProperties.service` holds the full public callback URL. `ProviderManager` delegates the ticket to `CasAuthenticationProvider`; the validator uses `CAS_BASE`.
- The sample assumes **stateful browser login via Service Ticket** and does not yet handle proxy tickets, gateway, logout/SLO, or multi-app stateless caches. Those flows have separate configs, policies, and tests.
- You must add `UserDetailsService`, controllers, and packaging/Gradle versions to run end-to-end. This is an **integration excerpt**, not standalone Java compiled directly with `javac`.
- Depending on minor version, check the CAS module APIs and filter defaults in the documentation of your exact Spring Security release before applying to production.

### 8.4. After Ticket Validation: Application Permissions Are Separate

CAS returns the authenticated user principal (and attributes per policy). Spring Security can load authorities via `UserDetailsService` or an approved mapping. **CAS Server permitting an application to log in does not mean that user has admin privileges in the application.**

For example, user `alice` may log in to Portal via CAS with only `ROLE_USER`; `GET /admin` must still return 403 if she lacks permission. Never derive authorities from `serviceId` names or unapproved groups.

## 9. CAS Service Registry: Onboarding and Offboarding Procedures

### 9.1. Safe Onboarding

Registering a service on the CAS Server is a **trust-relationship change**. The process should include:

1. **Business owner** confirms the application is authorized to use CAS, plus environment/tenant/support contacts.
2. **Technical owner** supplies the canonical HTTPS callback URL and confirms the Spring Security filter path, reverse proxy/ingress routes, and cookie/session strategy.
3. **Security/IAM** verifies domain ownership by the organization/partner, TLS certificates, absence of open redirects on the callback, and non-overbroad service matching rules.
4. Define minimal **attribute release**, stable user ID mapping, and application-side roles/permissions.
5. Assign a unique numeric `id` and `name`; set `serviceId` to cover the exact callback and an appropriate `evaluationOrder` if overlaps could exist.
6. Test `/cas/login?service=...` with the allowed URL, blocked URLs, lookalike/attacker domains, exact `serviceValidate`, and wrong-service validation.
7. Review and publish the JSON registry or DB service registry per policy; verify all CAS nodes update.
8. Monitor logins, `INVALID_SERVICE`, `INVALID_TICKET`, request timing, and certificate/endpoint changes before go-live.

**Never let customers self-register an arbitrary redirect URL as a production CAS service via a public form.** A control plane with RBAC, review, auditing, and emergency disable is required.

### 9.2. Modifying or Suspending a Service

If an application changes its callback from `/login/cas` to `/auth/cas/callback`:

- Update the client's `ServiceProperties.service`.
- Update the actual filter callback path.
- Update the CAS Registered Service `serviceId` (and evaluation/access policy).
- Coordinate the release; in-flight tickets bound to the old service may fail validation against the new URL.
- Test the new login flow and run negative tests against the retired old URL.

If an application must be suspended:

- Set `accessStrategy.enabled=false` or remove the registration, depending on CAS version/policy.
- Verify every CAS Server node has stopped issuing/validating new STs for that service per policy.
- Revoke/deny previously issued **app sessions**; disabling the CAS service **does not automatically clear Spring `SecurityContext`** in browsers.
- Audit API keys, stateless clients, proxy tickets/grants, and local role assignments if any exist.
- Use partner communication channels to announce timing, rollback milestones, and affected scope.

### 9.3. Planned Rollout vs. Emergency Incident

**Planned service change:** coordinate URL migration with preparation time, test the new callback, and handle in-flight tickets. Never open a wildcard callback just to support both simultaneously.

**Emergency compromise:** if a partner callback/domain is compromised, block the service immediately, audit tickets/sessions/attribute exposure, and halt privilege issuance. Never leave a service active with a broad regex to avoid downtime. Investigate evidence and re-enable only after approval.

## 10. Multiple CAS Services, Tenants, or Environments

### 10.1. Production and Staging Must Be Separated

| Environment | Service URL | Registered Service ID |
| --- | --- | --- |
| Production | `https://portal.example.org/login/cas` | `10001` |
| Staging | `https://staging.portal.example.org/login/cas` | `10002` |
| Development | `https://dev.portal.example.org/login/cas` | `10003` if CAS environment allows |

Do not use a single `serviceId` like `^https://.*portal.*` to cover both prod and dev. If dev is compromised, an overly broad policy can let production CAS issue tickets to dev callbacks or lookalike spoofed hosts. A test environment can use a separate CAS Server and separate policies.

### 10.2. Multi-Tenant Callbacks

For a multi-tenant application, two common options:

- **One shared canonical callback** `https://portal.example.org/login/cas`. The tenant is determined by server-side state/session or an approved principal/tenant mapping, **never** from a user-modifiable `?tenant=...`.
- **Per-tenant callbacks** `https://portal.example.org/tenants/alpha/login/cas` and `.../beta/...`. Each URL requires corresponding routing/filter + CAS Registered Service allowlist entries, verified against cross-tenant access.

Never build `service=https://portal.example.org/login/cas?tenant=<user-input>` to “pass the tenant through CAS” and trust the returned value. If state must be carried, use an opaque mechanism with integrity/binding protection, validate tenant mapping after authentication, and never turn `service` into an open redirect target.

### 10.3. A CAS Ticket Is Not a Multi-Tenant Authorization Grant

Successful CAS validation only confirms an identity under the CAS protocol. The application must still evaluate user/tenant account state, locally approved entitlements, and resource access; **never** let a user with Tenant A's CAS SSO session view Tenant B's data by altering a query/path.

### 10.4. Separating Ticket Types

| Ticket | Purpose | What Must Not Be Inferred |
| --- | --- | --- |
| **ST – Service Ticket** | Validated once for a specific service | Not a token reused across arbitrary URLs |
| **TGT – Ticket Granting Ticket** | CAS server-side SSO grant | Not data a client can use directly as an ST |
| **PT – Proxy Ticket** | Authorizes calls from a proxy-authorized service | Not automatically accepted by `/serviceValidate` for STs |
| **PGT – Proxy Granting Ticket** | Supports CAS proxy delegation | Never use an arbitrary `pgtUrl`; requires trust/HTTPS and proxy chain policy |
| **App `HttpSession`** | Maintains Spring Security `Authentication` after login | Does not automatically invalidate when CAS Service Registry changes |

If the application only needs browser SSO, **stick to the Service Ticket flow**, without enabling proxy ticket acceptance or stateless caching unless backed by a dedicated use case and threat model.

## 11. Preventing Open Redirects, Service Spoofing, and Ticket Leakage

### 11.1. Open Redirects at the CAS Server or Service Callback

If the CAS Server redirects users to an **unfiltered service URL**, it can become an open redirect and issue tickets to attacker-controlled endpoints. Thus the Service Registry is a **critical allowlist layer**.

However, risk also exists at the application's own callback:

```text
https://portal.example.org/login/cas?next=https://attacker.example/
```

If the application blindly redirects after login to `next` without validating origin/route, an attacker can send the browser to a rogue site; ticket/session details may also leak depending on the flow. Ensure:

- Fixed canonical callback; never use external URLs as the service identifier.
- Post-login redirect uses a **verified saved request and internal-relative path** or allowlisted targets.
- Strip `ticket` from the browser's displayed URL as early as possible per framework flow; never copy the ticket into external/analytics URLs.
- Never leak tickets, CAS TGC, or session cookies into broad logs or Referer headers to third-party assets.
- Enforce HTTPS, security headers/proper `Referrer-Policy`, and audit links/resources on callbacks.
- A redirect target like `https://trusted.example.evil.test` does **not** become safe simply because it starts with `https://trusted.example`.

### 11.2. Ticket Replay and Service Binding

An ST is typically issued **for one specific service** and **validated once**. If an attacker intercepts an ST, the risk remains severe: they may attempt to redeem it at the corresponding callback/service before the legitimate client does. Therefore keep STs out of browser history/logs/3rd-party resources and validate **over HTTPS** immediately upon receipt.

The CAS Server must reject:
- Already-used STs.
- Expired STs.
- An ST bound to `service=A` when validation provides `service=B`.
- Non-existent tickets or wrong ticket types for the endpoint.
- Unregistered, disabled, or access-policy-violating services.

**Never implement ticket validation with a regex** like `ticket.startsWith("ST-")`. Ticket format is not proof of login; the validator must call the CAS Server (or use a valid library mechanism) and verify the response.

### 11.3. Preventing Session Fixation and Role Escalation

After CAS authentication, the app needs Spring Security session management and authorization:

- Rotate the session ID upon successful authentication per anti-fixation policy.
- Never read username/roles directly from `service` or `ticket` query params.
- Never auto-grant `ROLE_ADMIN` because a CAS account belongs to a group named “Admins” when that group is not allowlisted.
- Maintain CSRF protection for app actions; the CAS ticket callback does not replace application-wide CSRF policy.
- Configure session TTL/Single Logout separately; CAS TGC logout does not guarantee all app `HttpSession` instances are deleted.
- Enforce tenant/resource permissions in server-side service methods, not merely by hiding UI links.

## 12. Diagnosing Service and Ticket Failures

### 12.1. Symptom Table

| Symptom | Fault Layer | Possible Cause | Remediation |
| --- | --- | --- | --- |
| `INVALID_SERVICE` / unauthorized service | CAS registry | Unregistered, wrong `serviceId` regex, disabled, evaluation conflicts | Compare exact `service` string and effective registry across all nodes |
| CAS login succeeds then returns to URL with no filter | Callback | `ServiceProperties.service` differs from filter path | Align service URL and `CasAuthenticationFilter` callback |
| CAS redirects to HTTP/internal host | Reverse proxy | Building service URL from internal request or wrong forwarded headers | Use canonical public HTTPS URL, configure trusted proxies properly |
| `INVALID_TICKET` on very first attempt | Ticket validation | ST expired, wrong service, validator calls wrong CAS, ticket already processed | Trace timing, `service`, and sanitized server logs |
| `INVALID_TICKET` on browser refresh | Ticket replay | ST already validated/consumed | Never retry ST; start a new login flow |
| Login works in prod, fails in staging | Registry/URLs | Staging callback unregistered or regex matches only prod | Register staging separately per policy |
| Query string difference causes validation failure | Service binding | Added query or differing normalization between login and validate | Fix service URL, compare exact bytes/strings after decoding |
| Callback receives ticket yet app stays anonymous | Spring filter/session | Filter chain skips path, `SecurityContext` not persisted | Check filter order, session cookie, auth manager |
| CAS returns user but app returns 403 | Authorization | User lacks local permission/role | Check app permissions; never broaden `serviceId` regex |
| One CAS node permits, another rejects | Registry cluster | JSON service definitions out of sync / stale cache | Sync config/revision, verify every CAS node |
| Setting `accessStrategy.enabled=false` still lets user into app | Existing app session | App `HttpSession` remains authenticated | Revoke sessions, enforce app-level denial |
| `renew=true` does not fix `INVALID_SERVICE` | Misunderstanding `renew` | `renew` forces reauthentication, does not allowlist URLs | Fix registered service/callback |
| CAS validation call fails TLS | Networking/trust | CAS cert untrusted, proxy/MITM, wrong endpoint | Fix TLS truststore, hostname validation; never disable TLS checks |
| Service login allowed but attributes empty | Attribute release | CAS policy does not release group/email to app | Inspect registered service attribute release; never assume all claims |
| Browser loops after CAS | Session/cookie/filter | Session fixation/rewrite, wrong callback, app session not saved | Check auth success and `SecurityContext` on follow-up request |
| Client grabs ST from query without calling validation | App logic | Treating ticket format as authenticated | Use proper CAS client ticket validator |

### 12.2. Ordered Debugging Procedure

1. Identify the **CAS Server base URL**, client public callback URL, and actual filter path.
2. Inspect the **URL-decoded `service` value** at `/login` and `/serviceValidate` via controlled logs; never log verbatim STs.
3. Check `serviceId` matching strategy, `enabled`, evaluation order, and registered service revision across every CAS node.
4. Verify the browser received the redirect with `ticket` at the **exact callback** and Spring `CasAuthenticationFilter` processed it.
5. Verify the CAS validation request used the right service/cert/TLS endpoint, ticket type, and timestamp.
6. Check replay/timeout: was the ticket already validated or sent a second time?
7. If CAS validation succeeded, inspect user details, authorities, app session, cookies, and authorization separately.
8. Check proxy/canonicalization if the URL changed across host/scheme/port/context path.
9. If the error occurs on only one node, check registry consistency, LB, caching, and build version.

**Safe logging:** you may record the numeric registration ID, public callback hostname/path, match result, CAS error category, app-generated correlation ID, timestamps, and node/version. **Never record raw STs, TGCs, passwords, proxy-granting tickets, or session cookies.**

## 13. Test Matrix for Service Registry

### 13.1. Unit Tests for URL Policy

| Requested `service` | Strict Portal `serviceId` | Result |
| --- | --- | --- |
| `https://portal.example.org/login/cas` | Exact callback | **ALLOW** if enabled |
| `http://portal.example.org/login/cas` | Wrong scheme | **DENY** |
| `https://portal.example.org.evil.test/login/cas` | Wrong hostname | **DENY** |
| `https://portal.example.org/admin` | Wrong path | **DENY** |
| `https://portal.example.org/login/cas/` | Extra trailing slash | **DENY** under strict pattern |
| `https://portal.example.org/login/cas?next=/admin` | Extra query | **DENY** under strict pattern |
| `https://staging.portal.example.org/login/cas` | Different environment | **DENY** unless staging has its own entry |
| `https://attacker.example.net/callback` | Unregistered | **DENY** |
| URL with unusual encoded host/path | Must parse/canonicalize per tested policy | **DENY** when inexact/ambiguous |
| Exact URL but `enabled=false` | Service disabled | **DENY** |

### 13.2. CAS Server and Spring Client Integration Tests

- CAS login with permitted `service` → issues ST and redirects to exact callback.
- CAS login with unregistered `service` → **does not issue ST for the service**.
- ST issued for `service=A` validated with `service=B` → authentication **FAILS**.
- ST already validated once → second attempt **FAILS**.
- Expired ST → **FAILS**.
- CAS validation succeeds but app user is disabled → authentication/authorization **FAILS** per local policy.
- CAS validation succeeds but user lacks `ROLE_ADMIN` → accessing admin endpoint returns **403**.
- Reverse proxy changes scheme/host/port → client still uses canonical public service URL and callback receives ST.
- JSON registry updated across cluster → CAS nodes have identical effective definitions.
- Disable Portal service → CAS stops issuing new STs; existing app sessions are handled separately.
- Planned callback migration → old/new allowed only within the policy window; no wildcard opened.
- Service URL containing `?redirect=https://attacker.example` is outside allowlist; app callback also does not open-redirect.
- Attribute release includes only approved fields, without exposing unnecessary directory data.

### 13.3. Using a Test CAS Server and Real Client Tests

Example request **solely to observe redirects** in a test environment—never put real tickets on the command line or public logs:

```bash
curl -I 'https://sso.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas'
```

The response may be a login page/SSO redirect, service error, or cookie depending on policy; **there is no single fixed stdout**. Never probe unfamiliar service URLs on production CAS without authorization; use staging fixtures and approved test users.

For `/serviceValidate`, the request requires a **valid freshly issued ST**, so never put a “copy-paste curl with a production ticket” into docs or chat. In test automation, mint a fresh ticket per test, redact tokens in output, and assert both `authenticationSuccess` and `authenticationFailure`.

### 13.4. Testing Policy on Both CAS and Client

Tests on both sides complement each other:

- **CAS Server tests:** `serviceId` matching, `accessStrategy`, ticket–service binding, and certificate/SSO policies.
- **Spring Security client tests:** callback filter intercepts the exact path, `ServiceProperties.service` is accurate, ticket validator genuinely calls CAS, and user authorities and app sessions are right.
- **Security integration tests:** ticket replay, mixed service IDs, open redirects, attribute release, tenant isolation, and admin permissions.

Never just run a single browser “login succeeded once” check and conclude the service registry is secure.

## 14. Onboarding/Offboarding and Operational Procedures

### 14.1. Onboarding a New CAS Service

- Verify owner/tenant/environment and callback domain.
- Require a canonical HTTPS `service` and confirm the service endpoint is genuinely handled by the Spring CAS filter.
- Assign a unique numeric `id`; record `name`, `evaluationOrder`, and narrow `serviceId`.
- Review attribute release, access strategy, SSO/MFA/renew policy, and role mapping.
- Test regex against both positive and negative cases, especially hostname suffixes and path/query.
- Publish the registry over a protected channel, synchronizing all CAS nodes.
- Test login, validation, one-time tickets, redirect paths, and error UX.
- Activate only after business + IAM/security approval; record audit/revision and rollback plan.

### 14.2. When a Partner or Callback Changes

- Never assume `https://portal.example.org/new` is the same service as the old URL.
- Align the new callback across client and CAS registry, checking all proxies/ingress.
- Assess in-flight STs issued for the old service, existing app sessions, and saved redirect links.
- Maintain a controlled transition window if planned; never open `^https://portal.example.org/.*` unnecessarily.
- Monitor `INVALID_SERVICE`/`INVALID_TICKET` across every cluster node.

### 14.3. Emergency Suspend

- Disable the service or remove it from the registry on all CAS nodes.
- If the domain/callback was compromised, address URL/ticket exposure and app sessions created during the exposure window.
- Revoke related proxy tickets/grants, app sessions, local admin permissions, and API credentials per threat assessment.
- Never declare the system safe merely because CAS stopped issuing new STs; existing app sessions may continue operating.
- Verify with negative tests: service rejected, direct callback does not log in automatically, and accounts with old sessions cannot access resources against policy.

### 14.4. Managing Changes Across a CAS Server Cluster

The JSON service registry may auto-watch/reload depending on deployment/version, but **files must be consistent across all instances**. Require versions/digests, coordinated deployment, per-node CAS acknowledgments, emergency kill switches, and stale-config alerts. Never edit a file only on node A and assume the load balancer always routes to A.

## 15. Important Misconceptions

| Statement | True/False | Reason |
| --- | --- | --- |
| “`service` is the CAS Server URL.” | **False** | `service` is the application's callback identifier; CAS login/validation URLs are different endpoints |
| “`serviceId` must always equal the literal `service` string.” | **False** | It can be a regex or literal matching the service URL |
| “Register `serviceId=^https://.*` to onboard apps easily.” | **Dangerous** | Virtually any HTTPS URL becomes a permitted service |
| “HTTPS alone allows any app to use CAS.” | **False** | Requires Service Registry allowlist and access policies |
| “An ST can be validated multiple times if login hasn't finished.” | **False** | ST is single-use; replay/retry after validation must be rejected |
| “An ST issued for A can be sent to `/serviceValidate` with B.” | **False** | CAS verifies which service owns the ticket |
| “`renew` fixes `INVALID_SERVICE`.” | **False** | Renew controls primary authentication requirements, not the allowlist |
| “Disabling `ssoEnabled` suspends the service.” | **False** | Disabling SSO still allows login via primary authentication |
| “Removing the JSON registry record logs out all Portal users.” | **False** | App sessions exist independently of the CAS registry |
| “Building the service URL from the `Host` header is always safe.” | **False** | Clients can spoof Host/forwarded headers if proxy trust is misconfigured |
| “Regex `portal.example.org.*` only matches the portal host.” | **False** | Unescaped dots and suffix regex allow other hosts to match |
| “Having `ticket=ST-...` means the app knows the user.” | **False** | Must validate with the CAS server before establishing `Authentication` |
| “CAS permitting a service gives the user admin rights in the app.” | **False** | CAS authentication is separate from local authorization |
| “CAS Service Registry is the same as SAML `RelyingPartyRegistrationRepository`.” | **False** | Two different registries for different protocols/sides, though both manage trust |

## 16. Production Checklist

### CAS Server Side

- [ ] Only approved registered services exist; no wildcards covering all HTTPS domains.
- [ ] Every service has a unique numeric `id`, owner, environment, audit trail, and clear access strategy.
- [ ] `serviceId` strictly matches scheme/host/port/path; tested for percent encoding, queries, Unicode/IDN, and regex metacharacters.
- [ ] `enabled`, `ssoEnabled`, attribute release, and proxy/MFA/renew match the contract.
- [ ] CAS Server uses proper HTTPS/TLS, ticket lifetimes, and one-time policy.
- [ ] JSON/DB registry is synchronized across all CAS nodes with revision/digest monitoring and safe rollback.
- [ ] Procedures exist to disable/retire CAS services and notify partners.
- [ ] No public endpoint or unauthorized admin can register new services.

### Spring Security CAS Client Side

- [ ] `ServiceProperties.service` is the public canonical HTTPS callback URL.
- [ ] `CasAuthenticationFilter` actually monitors the corresponding callback path.
- [ ] `CasAuthenticationEntryPoint` points to the trusted CAS login endpoint.
- [ ] CAS ticket validator uses HTTPS with proper truststore/hostname verification for the CAS Server.
- [ ] `service` at `/login` and `/serviceValidate` is consistent with the ticket and registry.
- [ ] ST is validated via CAS Server, never accepted solely due to `ST-` format or query presence.
- [ ] ST is never reused once validation is attempted; login retries start a new transaction.

- [ ] Disable/remove the service on every CAS node and verify direct login/validation are rejected.
- [ ] Revoke related app sessions/roles/keys per policy; CAS logout alone is insufficient.
- [ ] Account for in-flight STs/proxy tickets and plan cutover impact.
- [ ] Maintain audit logs, owner notifications, retention records, and post-cutover negative tests.

## 17. Self-Check Questions

**1. What is `service` in `/cas/login` used for?**

It is the identifier (usually a URL) of the application the browser wants to access. CAS verifies the service is allowed via the Service Registry and uses that URL as the target to return the ticket after login.

**2. How must `service` in `/serviceValidate` relate to `/login`?**

It must correspond to the service for which the ST was issued; passing a different URL can cause `INVALID_TICKET`/service mismatch. An ST can only be used for the matching service and one validation attempt.

**3. What is `serviceId` in a Registered Service?**

It is the identifier/rule (typically a regex or literal depending on matching strategy) that the CAS Server uses to match `service` in requests and decide whether the service is permitted.

**4. Why is `serviceId=^https://.*` dangerous?**

It permits an overly broad range of HTTPS URLs, potentially including attacker-controlled callbacks, weakening the service allowlist and increasing the risk of unintended ticket issuance/redirects.

**5. Why is `portal.example.org.*` insufficient as a hostname check?**

In regex, `.` matches any character and `.*` matches any suffix or path. You must escape literal dots and constrain the entire URL/path with anchors or literal matching.

**6. When should `renew=true` be used?**

When policy requires fresh primary authentication rather than relying solely on an SSO session. It does not make an unregistered service acceptable to CAS.

**7. Why must an ST in the callback not be used as user authentication immediately upon receipt?**

Because the ST could be forged, expired, already used, or issued for another service. The client must call the CAS validation endpoint over HTTPS and establish a session only after a valid `authenticationSuccess`.

**8. How does `ServiceProperties.service` differ from `CasAuthenticationFilter.filterProcessesUrl`?**

`ServiceProperties.service` is the full public URL for CAS to issue/validate tickets; `filterProcessesUrl` is the path the application monitors for ticket callbacks. Both settings must align.

**9. The CAS Service Registry entry was disabled, yet a user is still using Portal. Why?**

A previously created Spring Security session may remain authenticated. Blocking new CAS logins in the registry does not automatically erase the app's `HttpSession`/authorization.

**10. Should production and staging callbacks share `serviceId=^https://.*portal.*`?**

No. Use separate definitions or an extremely narrow approved allowlist so test environments or spoofed hosts cannot benefit from production SSO.

**11. If the browser returns to `/login/cas?ticket=ST-...`, should validation be called with `service` including the `ticket` query?**

Do not do that yourself. Use the canonical service URL for which the ST was issued per the integration, and let the CAS client library handle the `ticket` parameter/validation.

**12. When encountering `INVALID_SERVICE`, what is the first check to perform?**

Compare the `service` string sent by the client in `/login` against the effective registry `serviceId`/matching strategy and `accessStrategy` on the CAS Server, then check the public HTTPS host/scheme/path/port and multi-node configuration.

## Key Takeaway

**CAS `service` is the application's specific callback URL/identifier.** The CAS Server must check it against **Registered Service `serviceId`** in the Service Registry; arbitrary URLs must never be allowed. CAS issues an ST for that service; the Spring Security client receives the ST and validates it using the **exact matching service identifier**. STs are single-use.

**Formula to remember:**

**CAS login + `service=canonical callback` → registry allowlist → CAS issues ST → browser returns to callback with `ticket` → client calls `/serviceValidate` with ST and canonical service → CAS verifies → Spring Authentication + app authorization.**

Four essential boundaries:

1. **Registry allowlist differs from ticket validation:** an allowed URL does not prove every ticket is valid.
2. **Service identity differs from app permission:** CAS SSO success does not grant arbitrary admin/tenant privileges.
3. **Public URL must be consistent:** scheme/host/port/path/query/encoding across login, callback, and validation are part of security.
4. **Disabling the registry differs from revoking app sessions:** you must address access strategy, sessions/grants, and cluster consistency together.
