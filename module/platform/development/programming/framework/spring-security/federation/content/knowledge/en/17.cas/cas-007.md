# User Attributes Released by CAS and Attribute Release Policies

In **Apereo CAS (Central Authentication Service)**, successful authentication does not mean every piece of data in LDAP, Active Directory, JDBC, SCIM, or profile stores is sent to the application. CAS knows the authenticated **principal**, can retrieve numerous **principal attributes**, and uses each **registered service's attribute release policy** to decide exactly which attribute names and values are allowed to appear in the ticket validation response.

This is the foundation of **data minimization** and separation of duties: CAS verifies identity, while the application receives only information approved for business needs. If misconfigured, an app that only needs a display name might accidentally receive employee IDs, admin groups, home addresses, sensitive HR data, or even credentials/proxy tickets. If configured too restrictively, the app reports “CAS login succeeded but email/role is missing.”

This lesson belongs to the **CAS Fundamentals** group and explains the entire attribute lifecycle: **source → principal resolution → registered service selection → attribute release → consent/filters → CAS ticket validation response → Spring Security CAS client → internal authorization**. Content is based on **Apereo CAS 7.3.x** documentation and Spring Security CAS documentation, including properly structured service registry JSON examples, standalone Java 17 with deterministic stdout, security tests, and a runbook.

> Scope: the CAS **protocol** (tickets, `/p3/serviceValidate`, `<cas:attributes>`) is the focus. If the same CAS server also emits SAML2 Assertions or OIDC ID Tokens, formats and protocol-specific policies may differ; **never assume every CAS protocol attribute release policy automatically equals OIDC scopes/claims or SAML `AttributeStatement`**.

## 1. Core Concepts: User, Principal, Attributes, and Service

| Concept | Meaning | Illustrative Example |
| --- | --- | --- |
| **Credentials** | Proof presented by the user to a CAS authentication handler | Password/FIDO2 key/certificate per enabled mechanism |
| **Authentication** | Result of CAS successfully authenticating via handler and policy | Login via LDAP + MFA |
| **Principal** | Identity authenticated by CAS; has an `id` and resolved attribute set | Principal ID = `employee-123` |
| **Principal attributes** | User fields supplied by CAS/attribute repositories | `displayName`, `mail`, `eduPersonAffiliation` |
| **Authentication attributes** | Metadata about the authentication event, not necessarily HR data | Timestamp, authentication handler, authentication method |
| **Registered service** | Application permitted by CAS to use SSO | `https://portal.example.com/login/cas` |
| **Attribute release policy** | Rules governing data permitted to be returned **for a specific service** | Release only `displayName` and `mail` |
| **Attribute value filter** | Constrains attribute **values** after allowing the attribute name | Only groups matching a namespace/contract condition |
| **Attribute consent** | Step asking the user to decide on disclosing attributes per policy | Consent screen before releasing info to the application |
| **Ticket validation** | SP sends Service Ticket to CAS to verify ticket bound to service | `/p3/serviceValidate` |

Example of a fully resolved CAS principal:

~~~text
principalId = employee-123

resolved principal attributes:
  displayName       = ["Nguyen An"]
  mail              = ["an@example.org"]
  eduPersonAffiliation = ["employee", "faculty"]
  department        = ["Finance"]
  groups            = ["PortalReaders", "HR-Admins"]
  employeeSalary    = ["sensitive-value"]
~~~

A standard reporting application only needs display name and email address:

~~~text
serviceId = https://portal.example.com/login/cas

released principal attributes:
  displayName = ["Nguyen An"]
  mail        = ["an@example.org"]

NOT RELEASED:
  department
  groups
  employeeSalary
~~~

**Never conclude from an attribute existing in LDAP that CAS sent it out.** Nor should you conclude from an attribute **being present on the principal** that a service **is permitted to receive it**. These are two separate steps.

## 2. Two Separate Steps: Attribute Resolution and Attribute Release

According to Apereo CAS documentation, attributes pass through two stages:

1. **Attribute Resolution:** CAS creates/resolves the principal during or after authentication using `PrincipalResolver` and data sources such as LDAP, JDBC, REST, SCIM, Grouper, Entra ID, or other attribute repositories. Retrieved fields **do not automatically** mean external release.
2. **Attribute Release:** CAS locates the exact **registered service** matching the request, loads the policy for that service, selects permitted attributes, applies configured filters/consent/defaults, and builds the validation response for the application.

~~~mermaid
flowchart LR
    A[Authentication handler] --> B[Principal / PrincipalResolver]
    B --> R[LDAP/JDBC/SCIM/REST attribute repositories]
    R --> B
    B --> C[Resolved attributes]
    C --> D[Registered service lookup]
    D --> E[Attribute release policy]
    E --> F[Value filters / defaults / consent]
    F --> G[CAS validation response]
    G --> H[Spring Security CAS client]
    H --> I[Local account and authorization]
~~~

In operations, a registered service can also select specific attribute repositories, or a policy can trigger dynamic resolution. Thus presenting “resolve then release” is a **responsibility model**, not a claim that the framework can never query an attribute source during release.

### Example of a “Missing `mail`” Error

- LDAP has the `mail` attribute.
- CAS authentication succeeds with the right principal ID.
- However, `PrincipalResolver` did not enable the attribute repository or mapping is misconfigured: **`mail` was not resolved**.
- Or `mail` was resolved, but the registered service policy **does not include `mail` in the allowlist**.
- Or it was allowed, yet a **filter stripped the value**, consent was denied, or the response used an endpoint/protocol that does not emit attributes as the application expected.
- Or CAS returned `mail`, but the **CAS client parser/mapper** could not read it so the Spring app cannot see it.

The causes reside at different layers; identify the failing layer before changing service permissions.

## 3. CAS Protocol Transmits Attributes After Service Ticket Verification

Common flow:

~~~mermaid
sequenceDiagram
    participant U as Browser
    participant S as Portal / Spring CAS Client
    participant CAS as Apereo CAS
    participant Repo as Principal attribute repository
    U->>S: GET /reports
    S-->>U: Redirect to CAS /login?service=...
    U->>CAS: Log in (or use CAS TGC session)
    CAS->>Repo: Resolve principal attributes when applicable
    Repo-->>CAS: displayName, mail, groups, ...
    CAS->>CAS: Service registration and attribute release policy
    CAS-->>U: Redirect to service with ST-... ticket
    U->>S: GET /login/cas?ticket=ST-...
    S->>CAS: /p3/serviceValidate?ticket=...&service=...
    CAS->>CAS: Validate ticket + service + release policy
    CAS-->>S: CAS XML authenticationSuccess + permitted attributes
    S->>S: Create Authentication, local roles, and session
~~~

Key facts:

- **Service Ticket (`ST-...`)** is bound to a specific **service URL** and is normally single-use; the service must send the exact `service` when validating.
- **`<cas:user>`** is the primary user identifier in authentication success; **`<cas:attributes>`** is optional supplementary data.
- CAS protocol **3.0** and `/p3/serviceValidate` are typically used when the app needs attributes in XML. Depending on version/protocol, other validation endpoints may support partial structures; check your specific CAS server/client.
- CAS ticket validation must still run over **HTTPS to a trusted CAS** and verify ticket/service. Never accept a `user` query param or JSON attributes from the browser to create a session.

Example server-generated CAS3 validation response (illustrative only, not a real ticket):

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>employee-123</cas:user>
    <cas:attributes>
      <cas:displayName>Nguyen An</cas:displayName>
      <cas:mail>an@example.org</cas:mail>
      <cas:affiliation>employee</cas:affiliation>
      <cas:affiliation>faculty</cas:affiliation>
    </cas:attributes>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Two `<cas:affiliation>` elements show that **an attribute can be multi-valued**. The client must understand data types, multi-valued behavior, and null/empty handling. Never arbitrarily take the first value and infer a role when multiple values conflict.

**XML security:** use the official CAS client validator/parser to process responses, avoiding custom parsers with unsafe XML entity/DTD settings. When debugging, never write full CAS responses containing personal data to production logs.

## 4. Registered Service Is the Release Policy Boundary

One CAS server typically serves multiple applications:

~~~text
CAS: https://sso.example.org/cas

Payroll Portal:
  service = https://payroll.example.org/login/cas
  needs employeeId, displayName

Reports Portal:
  service = https://reports.example.org/login/cas
  needs displayName, mail, affiliation

Public Helpdesk:
  service = https://help.example.org/login/cas
  needs displayName or a pseudonymous ID

HR Admin:
  service = https://hr.example.org/login/cas
  may also need department, subject to approval
~~~

Each service must be registered with its own policy. **Just because HR Admin is approved to see `department` does not mean Reports Portal gets to see it.** A user having the same `principalId` across services does not entitle those services to receive all the same attributes.

A registered service also holds `serviceId`, the pattern matching the application URL. Write tight regexes: HTTPS scheme, exact hostname, exact callback path—never a broad `^https://.*` across production apps.

Never read a browser-supplied `service` query parameter and release attributes under a default “trusted” policy. CAS must locate the registered service in its registry; the SP must configure a fixed service URL matching the public host.

## 5. First Policy to Know: `ReturnAllowedAttributeReleasePolicy`

This is an **allowlist** policy: it returns only **attributes explicitly declared as permitted** for the service. In Apereo CAS 7.3.x, example JSON service registry structure:

Create `reports-1001.json` in the CAS-managed registry directory:

~~~json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "serviceId": "^https://reports[.]example[.]org/login/cas$",
  "name": "Reports Portal",
  "id": 1001,
  "description": "CAS protocol application for reporting",
  "attributeReleasePolicy": {
    "@class": "org.apereo.cas.services.ReturnAllowedAttributeReleasePolicy",
    "allowedAttributes": [
      "java.util.ArrayList",
      [
        "displayName",
        "mail",
        "eduPersonAffiliation"
      ]
    ]
  }
}
~~~

**Explanation:**

- `@class: CasRegisteredService`: CAS registered service type.
- `serviceId`: regex identifying the service URL; use `[.]` instead of a plain dot so it does not accidentally match any character.
- `name`/`id`: service identifiers; `id` must be unique in the registry.
- `attributeReleasePolicy`: object specifying release rules.
- `ReturnAllowedAttributeReleasePolicy`: allows only the names in `allowedAttributes`; **it does not magically fabricate non-existent fields**.
- `["java.util.ArrayList", [...]]` is **CAS/Jackson JSON type metadata**, appearing in official CAS 7.3.x examples. Do not replace it with a plain JSON array if your registry version requires that type metadata.

Prerequisites to run this example: the server has the JSON service registry module installed, a matching CAS overlay/version, configured directory location, and resolved principal attributes. **Simply creating a JSON file on disk does not make CAS load it** if the registry is disabled or not reloaded.

**Security note:** allowlisting is preferred for production because it **fails closed on new attributes**. If LDAP suddenly adds `employeeSalary`, the policy above **will not automatically release it**.

### Registry Configuration Mechanics

In CAS 7.3.x, the JSON registry is enabled via the `cas-server-support-json-service-registry` module and property:

~~~properties
cas.service-registry.json.location=file:/etc/cas/services
~~~

This is an **illustrative path**, depending on CAS overlay deployment and file permissions. Configuration settings must follow exact version docs; create JSON files in a dedicated folder and deploy/reload via CI/CD or a configured watcher mechanism. If a CAS cluster has multiple nodes, synchronize registry definitions/caches across all nodes so every node releases attributes under the same policy.

**Never manage sensitive policies by manually editing registry files directly on one production node** without review/versioning; rollback and audit trails for policy changes must be recorded.

## 6. Absent on Principal vs. Not Released Are Two Distinct Events

With `ReturnAllowed`:

~~~text
Allowed by policy: [displayName, mail, eduPersonAffiliation]

User A resolved:
  displayName = ["Nguyen An"]
  mail        = ["an@example.org"]
  department  = ["Finance"]

Release:
  displayName = ["Nguyen An"]
  mail        = ["an@example.org"]
  eduPersonAffiliation = absent (not resolved)
  department           = absent (not allowed)
~~~

Both `eduPersonAffiliation` and `department` are absent from the response, for different reasons:

- `eduPersonAffiliation`: present in the allowlist, but the repository/handler did not resolve it for user A.
- `department`: resolved, but CAS did not release it to Reports Portal.

“Adding `mail` to the allowlist” does not fix missing `mail` if the attribute repository does not know how to fetch `mail`. Conversely, “enabling release of all attributes” is the wrong fix when you only want to add `mail`.

CAS also allows dynamic resolution via an attribute definition store depending on policy; before enabling, verify data source rules, performance, cache/TTL, and access controls. Never open arbitrary Groovy scripts or REST callbacks to pull data from untrusted sources.

## 7. Renaming Attributes with `ReturnMappedAttributeReleasePolicy`

Not every application uses LDAP field names. For instance, the source system has `eduPersonAffiliation` while the app expects `affiliation`; the source has `mail` while the app expects `email`. You can use a policy to **map/rename when releasing to a service** without **renaming the underlying field in LDAP**.

Another CAS service example:

~~~json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "serviceId": "^https://payroll[.]example[.]org/login/cas$",
  "name": "Payroll Portal",
  "id": 1002,
  "attributeReleasePolicy": {
    "@class": "org.apereo.cas.services.ReturnMappedAttributeReleasePolicy",
    "allowedAttributes": {
      "@class": "java.util.TreeMap",
      "employeeNumber": "employeeId",
      "displayName": "fullName",
      "mail": "email"
    }
  }
}
~~~

How to read it: **key** is the resolved source attribute name, and **value** is the attribute name the application receives. Example:

~~~text
Resolved by CAS:
  employeeNumber = ["E-102"]
  displayName    = ["Nguyen An"]
  mail           = ["an@example.org"]

Released to Payroll:
  employeeId = ["E-102"]
  fullName   = ["Nguyen An"]
  email      = ["an@example.org"]
~~~

**Renaming does not elevate the trustworthiness of a value.** If the source `employeeNumber` can be edited by users or is not guaranteed unique, renaming it `employeeId` does not make it an immutable identifier. The application must maintain a contract on the field's source, format, and lifecycle.

An important distinction: mapping applies **per registered service**; it does not alter principal attributes for other applications. For example, Reports Portal can keep receiving `mail` while Payroll Portal receives `email`.

CAS also has `ReturnMultiMapped` to map one source to multiple names when genuinely needed, but **duplicating data** widens exposure and risks claim precedence confusion. Avoid it unless the app has an explicit requirement.

## 8. `DenyAll` and `ReturnAll`: Two Extremes Used Deliberately

CAS 7.3.x includes several policies. Four are easy to recognize:

| Policy | Meaning | Assessment |
| --- | --- | --- |
| `DenyAllAttributeReleasePolicy` | **Releases no principal attributes** to the application; also blocks default bundle if applicable | Suitable for services needing only principal ID |
| `ReturnAllowedAttributeReleasePolicy` | Releases exact attribute names in the allowlist | **Recommended default choice for least privilege** |
| `ReturnMappedAttributeReleasePolicy` | Allows and renames fields per service | When service contract differs from internal schema |
| `ReturnAllAttributeReleasePolicy` | Releases all resolved principal attributes; supports excluded fields | Risk of data over-exposure; requires careful review, usually unsuitable for public/third-party services |

### `DenyAll` Example

~~~json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "serviceId": "^https://help[.]example[.]org/login/cas$",
  "name": "Helpdesk Minimal",
  "id": 1003,
  "attributeReleasePolicy": {
    "@class": "org.apereo.cas.services.DenyAllAttributeReleasePolicy"
  }
}
~~~

**`DenyAll` does not mean “CAS withholds the `<cas:user>` identifier”**: it targets additional released **principal attributes**; a CAS protocol `authenticationSuccess` still provides the principal ID to the client. If an organization wants an anonymous/pseudonymous identifier per service, a dedicated **principal ID attribute/transformer** mechanism is required—do not assume `DenyAll` generates pseudonyms automatically.

### `ReturnAll` Illustrative Example, Not Recommended for Production

~~~json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "serviceId": "^https://lab[.]example[.]org/login/cas$",
  "name": "Isolated Attribute Lab",
  "id": 1099,
  "attributeReleasePolicy": {
    "@class": "org.apereo.cas.services.ReturnAllAttributeReleasePolicy",
    "excludedAttributes": [
      "java.util.LinkedHashSet",
      ["employeeSalary", "nationalId"]
    ]
  }
}
~~~

In a lab it can be convenient for inspecting data, but whenever a new attribute appears in the source, `ReturnAll` can automatically send it to the service. **Exclusion lists are less durable than allowlists**. Never use `ReturnAll + excludedAttributes` as the default for HR data or external partners.

## 9. Default Attribute Bundle: The “Allowlist Yet Extra Fields Appear” Trap

CAS has a **default attributes to release** mechanism, for example the property:

~~~properties
cas.authn.attribute-repository.core.default-attributes-to-release=displayName
~~~

In principle, the default bundle is shared across services and can **combine** with attributes permitted by each service's policy. Thus a local policy permitting only `mail` may still release `displayName` due to the global default. This is by design, though it can surprise teams controlling data exposure.

CAS provides `excludeDefaultAttributes` on release policies to opt out of the default bundle where appropriate; verify exact usage and serialization for your version and policy class.

Extended service JSON example (configuration illustration):

~~~json
{
  "@class": "org.apereo.cas.services.CasRegisteredService",
  "serviceId": "^https://minimal[.]example[.]org/login/cas$",
  "name": "Minimal Service",
  "id": 1010,
  "attributeReleasePolicy": {
    "@class": "org.apereo.cas.services.ReturnAllowedAttributeReleasePolicy",
    "excludeDefaultAttributes": true,
    "allowedAttributes": [
      "java.util.ArrayList",
      ["mail"]
    ]
  }
}
~~~

**When QA-testing policies, examine both global and per-service configuration**. Never look solely at `reports-1001.json` and claim the app can never receive unlisted fields if a global default bundle or protocol-specific behavior exists. The test target is the **actual response after ticket validation**.

## 10. Principal Attributes vs. Authentication Attributes

CAS distinguishes:

- **Principal attributes:** person/account data such as `displayName`, `mail`, `department`, `groupMembership`.
- **Authentication attributes:** describe the authentication event, handler/method, timestamp, and auxiliary metadata. These can risk exposing topology, authentication methods, or internal audit details.

CAS provides separate properties governing **authentication/protocol attribute release**; in CAS 7.3.x docs:

~~~properties
cas.authn.authentication-attribute-release.enabled=true
# List of fields that must never be released:
# cas.authn.authentication-attribute-release.never-release=...
# Exclusive list permitted for release:
# cas.authn.authentication-attribute-release.only-release=...
~~~

The comments are guidance, not advice to leave all defaults enabled. When an application needs to know MFA freshness or authentication method, define an explicit claim/protocol contract instead of releasing all metadata for the app to “inspect on its own.”

Related release-policy flags also include:

- `authorizedToReleaseAuthenticationAttributes`: permits releasing authentication/protocol metadata per policy.
- `principalIdAttribute`: places the CAS principal identifier into a named attribute when genuinely needed.
- `canonicalizationMode`: transforms value casing; use care because user IDs/codes can be case-sensitive.
- `excludeDefaultAttributes`: excludes the default bundle for a policy.

**Do not confuse `principalIdAttribute` with replacing `<cas:user>` with a new username.** Putting an ID into a named attribute requires assessing identifier-exposure risk; for data-minimized services, avoid releasing the same global ID across unrelated contexts unless needed.

## 11. Avoid Releasing Passwords and Proxy Granting Tickets as Attributes

Two release policy properties warrant special attention because they are **highly sensitive**:

- `authorizedToReleaseCredentialPassword`: allows releasing the user's credential/password as an attribute in specific cases.
- `authorizedToReleaseProxyGrantingTicket`: allows releasing the Proxy Granting Ticket ID under CAS mechanisms.

CAS documentation warns **against enabling these** without fully understanding their impact. For ordinary services, the rule is:

~~~text
credentialPassword release -> NO
proxyGrantingTicket release -> NO

Allow only genuinely required identity/attribute fields
after security review and a clear contract.
~~~

**A Proxy Granting Ticket is not “an ordinary HR attribute”**. It enables proxy ticketing mechanisms capable of accessing services on the user's behalf within an authorized proxy chain. If an application is not implementing standard CAS proxy authentication, never enable PGT release to “fix a missing attribute error.”

Likewise, credentials/passwords must be treated as secrets. Never write them to service ticket XML, logs, metrics, or support emails. The entire reason an application uses CAS SSO is **so it does not have to receive users' passwords**.

## 12. Attribute Value Filters: Allowing a Field Name Does Not Mean Allowing Every Value

A `groups` field might contain:

~~~text
groupMembership:
  ["PortalReaders", "HR-Admins", "Finance-Payroll", "Confidential-Board"]
~~~

Reports Portal only needs to know the `PortalReaders` group to render reporting features. Allowlisting **the field name `groupMembership`** does not mean all group values should be disclosed.

CAS supports **attribute value filters** attached to release policies to prune values. Exact class names and serialization details depend on filter type and version; this lesson uses **policy pseudocode** to illustrate the principle:

~~~text
filterForReports("groupMembership", values):
    return values matching exactly ["PortalReaders"]

input:
  groupMembership = [
    "PortalReaders",
    "HR-Admins",
    "Finance-Payroll"
  ]

released:
  groupMembership = ["PortalReaders"]
~~~

**Do not copy pseudocode as an existing CAS class name.** In implementation, choose a policy/filter supported by CAS 7.3.x and verify type/value matching, case sensitivity, regex anchoring, and multi-valued lists. Never use a regex like `.*Admin.*` to grab all admin-related groups and infer elevated privileges.

Data filtering in CAS and authorization at the SP are **two independent layers**: CAS may release only approved groups, yet the SP must still determine whether the user holds a valid local role or tenant membership.

## 13. Consent Does Not Replace an Attribute Release Policy

Apereo CAS includes an **Attribute Consent** module that can show a screen informing the user which fields are about to be shared with a service and letting them approve or deny per policy.

Key distinctions:

- **Release policy:** decides which attributes a service is **permitted** to receive in principle.
- **Consent policy:** decides when the user is prompted and agrees to release eligible attributes.
- **Attribute repository:** supplies source values, not a permission-approval tool.
- **Service business contract:** establishes legitimate purpose, data minimization, and processing accountability.

A user clicking approve **must not** let a service bypass the release allowlist; conversely, simply having an allowlist **does not automatically** satisfy consent/privacy obligations when the data-processing context requires them.

CAS supports service-level consent policies and corresponding modules with fields such as `excludedAttributes`, `includeOnlyAttributes`, `excludedServices`, and `status` in releases with this feature. **Never copy properties from `development` docs into a CAS 7.3.x deployment** without verifying them against your running release's docs/Javadoc.

**Operations:** when policies change, users may need to be re-prompted per consent lifecycle; audit logs should record only policy ID, service, timestamp, and consent status, avoiding storing full copies of sensitive data unnecessarily.

## 14. Attribute Sources from LDAP/AD/JDBC/REST and Resolution Risks

CAS can retrieve principal attributes from one or more sources:

| Source | Example | Concerns |
| --- | --- | --- |
| LDAP/Active Directory | `mail`, `displayName`, `memberOf` | Nested groups, case/canonicalization, bind account privileges, caching |
| JDBC | Employee ID, active status | SQL injection in custom queries, stale records, connection limits |
| REST/SCIM | Department, HR status, external ID | TLS/authn, rate limits, retries/timeouts, and data contract |
| Microsoft Entra ID / SaaS | User profile/roles | Issuer/source boundaries, schema drift, token/API scopes |
| Grouper/group repository | Group memberships | Nested roles, multi-valued attributes, and tenant scoping |
| Groovy/custom resolver | Derived attributes | Sandboxing, code review, never execute scripts from user input |

**Finding the right source does not guarantee releasing correctly**: CAS can merge attributes from multiple repositories, and the same key may hold multiple values. Establish deterministic rules for precedence, schema, and transformations so data from different tenants/identity domains is never accidentally mixed.

When a registered service has its own `principalAttributesRepository`, policy can activate a specific source once the service is identified. This helps curb unnecessary data retrieval, but config and cache/TTL must be guarded against cross-user or cross-service data leakage.

### Privacy by Design

For a service that only needs a display name:

~~~text
Need:
  displayName

Do not retrieve or release unless justified:
  homeAddress
  dateOfBirth
  nationalId
  salary
  managerNotes
  securityQuestions
  password
~~~

If the server still needs to resolve certain fields for internal policy, the release policy must still restrict data sent to the service. **Never make the SP responsible for discarding excess data** after CAS already sent it; avoiding transmission from the start is better.

## 15. Flow of Ticket Validation and Attribute Release in CAS Protocol 3

Suppose the valid service URL is:

~~~text
https://reports.example.org/login/cas
~~~

The browser receives `ST-...` and the SP submits it for validation (illustrative only, do not use real tickets):

~~~http
GET /cas/p3/serviceValidate?service=https%3A%2F%2Freports.example.org%2Flogin%2Fcas&ticket=ST-EXAMPLE HTTP/1.1
Host: sso.example.org
Accept: application/xml
~~~

CAS checks that the Service Ticket belongs to the **exact service URL** and is unused/unexpired per policy. If valid, CAS builds the validation response with `<cas:user>` and permitted attributes. If invalid, the response signals an authentication/ticket validation failure with no principal for the app to trust.

**Never mint Service Tickets yourself or pull STs from logs as production test data.** They are short-lived, single-use credentials tied to login sessions. Passing tickets in URLs requires HTTPS protection and preventing full URLs from reflecting into analytics/referrers/logs; strip the ticket from the URL after callback and establish the application session.

### Multi-Valued Attributes in CAS 3.0 Responses

One field can be represented by multiple XML elements with the same name:

~~~xml
<cas:attributes xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:affiliation>employee</cas:affiliation>
  <cas:affiliation>faculty</cas:affiliation>
  <cas:displayName>Nguyen An</cas:displayName>
</cas:attributes>
~~~

The CAS client parser may return a list or a single value depending on type/config; the application must check the **actual runtime type** instead of blindly casting every field to `String`. For a multi-valued field like `groups`, never call `String.valueOf(value)` and split on commas, since group names may contain delimiters.

## 16. Where Does the Spring Security CAS Client Read Attributes?

Spring Security has a dedicated CAS module with these components:

- `CasAuthenticationFilter`: handles the login callback/ticket sent back by CAS.
- `ServiceProperties`: defines the service URL for which the ticket was issued; must match during validation.
- `CasAuthenticationEntryPoint`: redirects the browser to CAS login.
- `CasAuthenticationProvider`: invokes the ticket validator, determines authentication, and loads local user/authorities.
- `CasAuthenticationToken`: successful `Authentication`, holding the CAS `Assertion`.
- `AuthenticationUserDetailsService<CasAssertionAuthenticationToken>`: where the app loads user/roles after CAS verification.
- Apereo CAS client `Cas30ServiceTicketValidator` (in versions supporting CAS 3.0 responses) to retrieve additional attributes.

**Do not confuse with `oauth2Login()` and `saml2Login()`**: Spring Security CAS client uses CAS-protocol ticket validation. If the CAS server also emits OIDC/SAML2, the app must use OAuth2 Login or SAML2 Login accordingly rather than mixing all three protocol parsers.

In Spring Security docs, `CasAuthenticationProvider` can use `UserDetailsService` to load local authorities after CAS validates the ticket; local passwords are normally not used by the CAS provider to authenticate the user. This is the right place to check user status and per-role/per-tenant policies.

### Example Reading Verified Attributes in a Spring Controller

The snippet below is a **class in a Spring project**, and will not compile/run standalone via `javac` without Spring Security CAS:

~~~java
import java.util.List;
import java.util.Map;

import org.springframework.security.core.Authentication;
import org.springframework.security.cas.authentication.CasAuthenticationToken;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
class CasProfileController {

    @GetMapping("/cas/profile-summary")
    Map<String, Object> summary(Authentication authentication) {
        if (!(authentication instanceof CasAuthenticationToken cas)) {
            throw new IllegalStateException("CAS login required");
        }

        Map<String, Object> released =
                cas.getAssertion().getPrincipal().getAttributes();

        // Return only the subset approved by the application;
        // never return raw released directly via a public API.
        return Map.of(
                "principal", cas.getName(),
                "attributeNames", List.copyOf(released.keySet()));
    }
}
~~~

**Warning:** using `attributeNames` is illustrative only; even field names can be sensitive in some environments. Production should return a minimal local view model rather than exposing raw CAS attributes. The return type of `Assertion.getPrincipal().getAttributes()`/CAS client depends on library version; verify imports and APIs against your resolved version. If the app does not use CAS Authentication, the cast is invalid; never use this class for OIDC/SAML.

### Ticket Validator and CAS Protocol Version

Spring Security CAS docs show `Cas20ServiceTicketValidator` for basic flows needing mainly user identity. When the app needs CAS3 attributes, use an Apereo CAS client library version containing `Cas30ServiceTicketValidator` or the validator matching the enabled server protocol. **Do not assume Cas20 always parses every CAS3 attribute extension by configuration**.

Provider/filter config must specify the exact CAS base URL and service URL, preventing SSRF or clients contacting untrusted CAS hosts over unprotected HTTP. Never roll your own `RestTemplate` call to `/p3/serviceValidate` while skipping ticket/service checks when a CAS client library already provides a standard validator.

## 17. From CAS Attributes to Spring Security Authorities

A `groupMembership` attribute in the CAS response can serve as **input** to mapping, but **is not itself an authority**.

Example:

~~~text
CAS released to Reports Portal:
  principalId = employee-123
  groupMembership = ["PortalReaders", "HR-Admins"]

App local identity:
  (trustedCasServer, employee-123) -> localUser u-702
  localUser u-702 is ACTIVE
  tenantMembership = reports-tenant
  authorities = ["ROLE_REPORT_VIEWER"]

Decision:
  HR-Admins from CAS != automatic ROLE_ADMIN in Reports Portal
~~~

**Granting `ROLE_ADMIN` directly from any group containing “Admin” is an anti-pattern.** When CAS groups are needed, establish a mapping policy:

| Source | Exact Group Value | Internal Authority |
| --- | --- | --- |
| Trusted CAS registry | `PortalReaders` | `ROLE_REPORT_VIEWER` |
| Trusted CAS registry | `PortalEditors` | `ROLE_REPORT_EDITOR` if locally approved |
| Trusted CAS registry | `HR-Admins` | **Do not map automatically** in Reports Portal |
| Unknown CAS / proxy chain | Any group | **Grant no privileges** |

Some deployments also factor in the upstream authentication handler identity or service registration, but **never trust a browser-sent field** as an authorization source. The application must verify local active/locked account status, memberships, service scope, and object-level authorization. After login, permissions may change; sessions/caches need TTLs and revocation mechanisms.

**A CAS release policy does not replace endpoint authorization.** It restricts **what data the app sees**, not whether the user can open `/admin` or read Tenant C's data. Access control still lives in Spring Security and the business layer.

## 18. Standalone Java 17: Simulating Allowlist, Mapping, DenyAll, and Role Policy

The program below models **already-resolved CAS principal attributes** and a subset of release policy logic. Its purpose is to verify:

1. Only attributes in the allowlist are released.
2. `mail` can be renamed to `email` per service.
3. Different services have different allowlists.
4. Unregistered or `DenyAll` services receive **no principal attributes**.
5. `employeeSalary` is withheld because it is not allowed.
6. The `HR-Admins` group does not automatically grant an admin role in the application.

**This is pure Java, not a CAS server; it does not validate Service Tickets or implement real release policies.** The `ServicePolicy` record name is defined by this exercise, not a CAS API.

Create `CasAttributeReleaseDemo.java`:

~~~java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeSet;

public class CasAttributeReleaseDemo {

    record ServicePolicy(
            Set<String> allowed,
            Map<String, String> renamed) {}

    static Map<String, List<String>> release(
            Map<String, List<String>> resolved,
            ServicePolicy policy) {

        Map<String, List<String>> output = new LinkedHashMap<>();
        for (var item : resolved.entrySet()) {
            String sourceName = item.getKey();
            if (policy.allowed().contains(sourceName)) {
                String targetName =
                        policy.renamed().getOrDefault(sourceName, sourceName);
                output.put(targetName, List.copyOf(item.getValue()));
            }
        }
        return output;
    }

    static Set<String> localRoles(Map<String, List<String>> released) {
        Set<String> result = new TreeSet<>();
        List<String> groups =
                released.getOrDefault("groupMembership", List.of());

        // Map only the enterprise-approved group.
        if (groups.contains("PortalReaders")) {
            result.add("ROLE_REPORT_VIEWER");
        }
        return result;
    }

    public static void main(String[] args) {
        Map<String, List<String>> resolved = new LinkedHashMap<>();
        resolved.put("displayName", List.of("Nguyen An"));
        resolved.put("mail", List.of("an@example.org"));
        resolved.put("groupMembership",
                List.of("PortalReaders", "HR-Admins"));
        resolved.put("employeeSalary", List.of("sensitive"));

        ServicePolicy reports = new ServicePolicy(
                Set.of("displayName", "mail"),
                Map.of("mail", "email"));

        ServicePolicy hr = new ServicePolicy(
                Set.of("displayName", "mail", "groupMembership"),
                Map.of("mail", "email"));

        ServicePolicy denyAll =
                new ServicePolicy(Set.of(), Map.of());

        Map<String, List<String>> releasedReports =
                release(resolved, reports);
        Map<String, List<String>> releasedHr =
                release(resolved, hr);

        System.out.println("Reports: " + releasedReports);
        System.out.println("HR: " + releasedHr);
        System.out.println("Deny all: " + release(resolved, denyAll));
        System.out.println("Salary released: "
                + releasedHr.containsKey("employeeSalary"));
        System.out.println("Local roles: " + localRoles(releasedHr));
        System.out.println("External admin became admin: "
                + localRoles(releasedHr).contains("ROLE_ADMIN"));

        Map<String, List<String>> noMail =
                new LinkedHashMap<>(resolved);
        noMail.remove("mail");
        System.out.println("Mail missing: " + release(noMail, reports));
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac CasAttributeReleaseDemo.java
java CasAttributeReleaseDemo
~~~

**Exact stdout:**

~~~text
Reports: {displayName=[Nguyen An], email=[an@example.org]}
HR: {displayName=[Nguyen An], email=[an@example.org], groupMembership=[PortalReaders, HR-Admins]}
Deny all: {}
Salary released: false
Local roles: [ROLE_REPORT_VIEWER]
External admin became admin: false
Mail missing: {displayName=[Nguyen An]}
~~~

**Interpreting the output:**

- `Reports` does not see groups or salary because it allows only `displayName` and `mail`.
- `HR` can see `groupMembership` in the example, yet **cannot see salary**.
- `Deny all` releases no principal attributes; the demo does not model `<cas:user>`.
- `Salary released: false` shows the allowlist does not leak new sensitive source fields.
- `Local roles: [ROLE_REPORT_VIEWER]` applies the exact approved group rule.
- `External admin became admin: false` shows group names do not automatically grant privileges.
- `Mail missing` illustrates that an allowed attribute **that was not resolved** remains absent.

**Demo limitations:** it has no CAS tickets, `serviceId` regex matching, default attributes, consent, real attribute value filters, proxy authentication, credential release, caching, HTTP, or CAS XML. In real systems, use Apereo CAS `RegisteredServiceAttributeReleasePolicy`/Service Registry and a CAS client ticket validator—never use this demo to process production assertions.

## 19. Attribute Release Test Matrix

An end-to-end test must genuinely mint a Service Ticket via a test CAS server and validate it, not just parse JSON.

| Test | Config / Condition | Expectation |
| --- | --- | --- |
| Valid service | Reports Portal registered | CAS allows login and ticket validation for exact service |
| Unknown service | Unregistered URL | Does not release attributes / denies service per policy |
| Allowlist | `displayName`, `mail` | Only approved fields + defaults if configured |
| Missing source attribute | `mail` not resolved | `mail` absent even though allowed |
| New source attribute | LDAP adds `employeeSalary` | Absent from `ReturnAllowed` response |
| `ReturnMapped` | `mail -> email` | CAS returns `email` name per contract |
| `DenyAll` | Helpdesk service | No principal attributes, including default bundle per policy |
| `ReturnAll` lab | Isolated in staging | Verifies field exclusions, but not used broadly in production |
| Global default bundle | CAS sets `displayName` globally | Verify whether service receives bundle or drops via `excludeDefaultAttributes` |
| Value filter | `groups` contains sensitive values | Only policy-permitted values released |
| Consent rejected | User declines sharing | CAS honors consent flow; app receives no declined data |
| Multi-valued attribute | `affiliation` has employee/faculty | Client reads full list without data loss |
| Wrong service URL | Ticket issued for app A, validated as B | CAS rejects |
| Replayed ticket | Validate ST a second time | No login created from reused ticket |
| Bad CAS TLS | Invalid server certificate | Client refuses connection, creates no `Authentication` |
| Group role spoof | CAS group `HR-Admins` at Reports | Does not auto-grant `ROLE_ADMIN` |
| Disabled local user | CAS auth succeeds but user locked at SP | SP denies/terminates session per policy |
| Tenant boundary | App A user accesses Tenant B data | 403 despite successful CAS login |
| Stale cache | LDAP changes group, CAS cache holds old value | Configured TTL/revocation policy takes effect |
| Cluster registry | CAS nodes A/B read different registries | Drift detected and fixed; inconsistent policy rejected |
| OIDC/SAML service | CAS emits non-CAS3 protocol | Verify protocol-specific claim mapping separately |

**PASS must be based on verified responses from CAS**, not merely on the JSON file “looking right.” Also test the browser login flow with a real service URL and local authorities in Spring Security.

### Limited `curl` Verification Example

After a **test service ticket** is actually issued by CAS, you can call the CAS validation endpoint:

~~~bash
curl --fail-with-body \
  --get "https://sso.example.org/cas/p3/serviceValidate" \
  --data-urlencode "service=https://reports.example.org/login/cas" \
  --data-urlencode "ticket=ST-FROM-TEST-SERVER"
~~~

`ST-FROM-TEST-SERVER` is a placeholder only; the example command **cannot produce a real `authenticationSuccess`** without a valid ST. Tickets are short-lived secrets—avoid logging command history/tickets. In production, prefer credential-protecting client tests over running manual `curl` against real tickets.

If the response contains `<cas:authenticationFailure>`, check the reason code and safe logs; never treat an absent `<cas:attributes>` element as sole proof that the policy is broken. Even when validation succeeds, inspect the principal ID and permitted attributes.

## 20. Safe Rollout Process for the CAS Team

1. **Gather per-service requirements:** field names, purpose, sensitivity, owner, and retention.
2. **Verify attribute sources:** LDAP/JDBC/REST, types, multi-value behavior, normalization, and stability.
3. **Choose principal ID:** durable user identifier, avoiding easily recycled usernames/emails when long-lived links are needed.
4. **Register exact service URL:** public HTTPS, tightly anchored `serviceId` regex, and unique numeric ID.
5. **Start with `ReturnAllowed`:** use `ReturnMapped` only when schema field renaming is needed.
6. **Inspect the default bundle:** exclude global fields inappropriate for the service.
7. **Apply value filters** only when business policy requires them, preventing role/group leakage.
8. **Evaluate consent** where legal/privacy rules apply, never turning consent into an allowlist bypass.
9. **Keep password/PGT release disabled** unless strictly reviewed and approved.
10. **Deploy via managed registry:** versioning/CI, review, rollback, and CAS cluster synchronization.
11. **Verify `/p3/serviceValidate`:** ST bound to exact service and XML contains exact fields.
12. **Verify Spring CAS client:** validator supports CAS3, multi-value parsing, local authorities, and sessions.
13. **Negative tests:** unknown service, new attribute, wrong ST, disabled user, admin group spoofing.
14. **Protect logs:** never print raw tickets, CAS XML, PII, passwords, or proxy tickets.
15. **Monitor drift:** attribute schemas/LDAP groups, contracts, and consent state post-deployment.

**Operational rule:** when an application asks to add `employeeNumber`, the CAS administrator must ask **“what does the app use it for, can a pseudonymous ID be used instead, who approved it, and what is the retention?”** rather than blindly changing the policy and closing the ticket.

## 21. Common Errors and Fixes

| Symptom | Likely Cause | Fix |
| --- | --- | --- |
| CAS login OK yet `mail` missing | `mail` not resolved or not allowed | Check attribute repo, then service release policy |
| CAS has `mail` yet SP sees only `email` | `ReturnMapped` renames field | Align data contract between CAS and client |
| SP expects `email` yet receives `mail` | Mapping not enabled | Use `ReturnMapped` or adjust client mapper |
| Service receives attribute outside allowlist | Global default bundle or protocol-specific rule | Check `excludeDefaultAttributes`, defaults, and validation response |
| CAS returns principal ID but no attributes | `DenyAll` or policy omits fields | Check registered service release policy; do not assume ticket failure |
| User has group list yet different roles | Spring app maps roles per local policy | Check local `UserDetailsService`/authority mapping |
| `HR-Admins` group appears in public portal | `ReturnAll`/broad rule or missing filter | Narrow allowlist and value filtering |
| Ticket fails validation | Wrong service URL, expired/replayed ST, wrong CAS HTTPS | Check exact `service` param and CAS ticket validation |
| Only CAS node B releases extra field | Registry/cache out of sync across nodes | Sync service registry and restart/reload properly |
| Consent declined yet field still sent | Consent config/status/flow misconfigured | Check CAS consent module, policy, and tests |
| New role does not take effect immediately | Cached principal/attributes or stale SP session | Define TTL, refresh, or revoke sessions |
| XML parser sees no attributes | Client uses CAS2 validator/different response parser | Check CAS3 validator and API version |
| New email merges wrong local user | App uses email alone as identifier | Use durable CAS principal ID / identity link |
| CAS accidentally releases credential/PGT | Sensitive flags enabled by mistake | Disable immediately and handle as severe credential exposure |
| Groovy/REST policy unstable | External outage, timeout, script change | Pin source, review sandbox/timeouts, and audit |
| CAS 7.3 config copied from `development` fails | Serialization/schema/module changes | Follow docs for exact deployed version |

**Never fix one missing attribute by enabling `ReturnAll` for every service**. Diagnose along the pipeline: resolution → service match → release → filter/defaults/consent → protocol response → CAS client → local authorization.

## 22. Differences Across CAS Protocol, SAML2, and OIDC When CAS Is a Broker

Apereo CAS can offer multiple protocols, and the same principal repository can serve multiple integrations. However, data delivery differs:

| Protocol | Where Data Arrives | Limits to Watch |
| --- | --- | --- |
| **CAS Protocol 3.0** | `<cas:attributes>` in ticket validation response | Service ticket, CAS service registry/policy |
| **SAML 2.0** | `<saml:AttributeStatement>` in Assertion | Metadata, issuer/audience, NameID, SAML-specific attribute release |
| **OIDC** | ID Token claims and/or UserInfo | Issuer/client ID, scopes/claims, OIDC protocol policies |
| **CAS Proxy** | Proxy ticket/PGT per CAS protocol | Authorized proxy services/chains only; never release credentials arbitrarily |

If a Spring app uses `oauth2Login` with CAS as an OIDC OP, configure `ClientRegistration`, verify `iss`/`aud`, and read `OidcUser`; **do not use CAS protocol's `CasAuthenticationToken`**. If using `saml2Login` with CAS as a SAML IdP, check Assertion attributes per SAML profile. **Never mix user attributes from all three protocols as if they carried identical semantics/guarantees**.

Choosing between CAS protocol and OIDC/SAML2 should follow integration requirements and CAS/client capabilities; CAS brokering an upstream provider does not automatically entitle applications to receive all upstream PII.

## 23. Quick Q&A — Staying Within Scope

**Q:** CAS authentication succeeded—why doesn't the SP see the email address?

**A:** `mail` may not be resolved, may be blocked by release policy/filter/consent, renamed to `email`, or the client may not be reading CAS3 attributes. Check each layer.

**Q:** Does `DenyAllAttributeReleasePolicy` stop CAS from knowing who the user is?

**A:** No. It prevents releasing extra principal attributes to the service; CAS still authenticates the principal and CAS protocol `authenticationSuccess` normally includes `<cas:user>`.

**Q:** Why is `ReturnAllowed` safer than `ReturnAll`?

**A:** When a new sensitive field is added to the repository, `ReturnAllowed` will not release it unless explicitly approved. `ReturnAll` risks exposing it in responses.

**Q:** Can `groupMembership=HR-Admins` be mapped to `ROLE_ADMIN` directly in Spring?

**A:** Only when an approved policy exists for that exact service/tenant alongside local authorization conditions. Never infer solely from a group name.

**Q:** Does consent let an app view extra fields not in the allowlist?

**A:** Consent is a layer governing sharing of eligible attributes; it is not permission to bypass the registered-service release policy.

**Q:** Does `ReturnMapped` renaming `mail` to `email` make the email address more verified?

**A:** No. Renaming only changes the schema. Trustworthiness and stability depend on the attribute source and operational contract.

**Q:** Must credential password release be enabled for an SP to use CAS login?

**A:** No. CAS SSO uses Service Tickets, not sending passwords to the SP. Never enable that extremely sensitive flag.

**Q:** Is the Java 17 demo in this lesson a production CAS configuration?

**A:** No. It illustrates allowlist/mapping logic; it does not validate tickets or run a real CAS server or service registry.

## 24. Final QA Checklist

- [ ] Service URL is registered with a tightly anchored regex and uses HTTPS.
- [ ] Each service has a dedicated owner/ID and an approved release contract.
- [ ] Attribute sources, resolvers, and field names are verified.
- [ ] Resolved attributes are not confused with released attributes.
- [ ] `ReturnAllowed`/`ReturnMapped` chosen appropriately, avoiding broad `ReturnAll`.
- [ ] Default attribute bundle and `excludeDefaultAttributes` verified.
- [ ] Principal ID and named attributes handled separately.
- [ ] Credential passwords or PGTs are never released to services without explicit need.
- [ ] Attribute value filtering ensures groups/values stay within contract.
- [ ] Consent adheres to policy without bypassing the allowlist.
- [ ] CAS3 `/p3/serviceValidate` returns exact user/attributes and fails on invalid tickets.
- [ ] CAS client parses multi-valued attributes accurately.
- [ ] Spring Security uses local users/roles and checks tenant/object authorization.
- [ ] Accounts are never merged on unverified email or mutable display names.
- [ ] No out-of-allowlist group automatically grants `ROLE_ADMIN`.
- [ ] JSON registry and attribute caches are synchronized across the CAS cluster.
- [ ] Positive and negative tests executed with real test service tickets.
- [ ] Raw tickets, raw CAS responses, PII, passwords, and proxy tickets are never logged.
- [ ] Rollback and audit processes exist when adding or revoking attributes.
- [ ] Compatibility verified across exact CAS / Apereo Client / Spring Security versions.
