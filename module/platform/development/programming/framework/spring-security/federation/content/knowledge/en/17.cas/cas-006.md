# Distinguishing CAS Protocol from SAML 2.0 Web Browser SSO in Spring Security

## 1. Problem Statement and Learning Objectives

Both the **CAS Protocol** and **SAML 2.0 Web Browser Single Sign-On (Web Browser SSO)** let a user log in across multiple applications without re-entering credentials at each one. Consequently, they are often loosely described as “redirect to an SSO system and come back.” That description holds at the user-experience level, but **is wrong when used to design, code, and verify security**.

In the **CAS Protocol**, the browser typically delivers a short-lived **Service Ticket (ST)** to the application; the application uses a **direct connection to the CAS Server** to verify the ST. In **SAML 2.0 Web Browser SSO**, the browser typically carries a **`SAMLResponse` containing a SAML Assertion** back to the Assertion Consumer Service (ACS); the Service Provider (SP) uses **configured trust/keys/metadata** to verify the signature, issuer, audience, subject, conditions, and response constraints. SAML also has an **Artifact binding** that uses an extra back-channel, but that should not be taken as the default definition of Web Browser SSO.

This lesson belongs to **Spring Security - federation → CAS Fundamentals**, covering **“Distinguishing CAS protocol from SAML2 Web Browser SSO.”** Content targets Java 17+, Spring Boot 3.x, and Spring Security 6.x/7.x **Servlet/MVC**, noting API changes across versions.

After this lesson, you will be able to:

1. Draw accurate CAS login and SAML Web Browser SSO flows, pinpointing data carried through the **browser** and server-side verification steps.
2. Distinguish CAS `Service Ticket (ST)`, `Ticket-Granting Ticket (TGT)`, and `Ticket-Granting Cookie (TGC)` from SAML `AuthnRequest`, `Response`, and `Assertion`.
3. Explain why CAS needs `/serviceValidate` and why a SAML SP needs **X.509 verification credentials and XML signature validation**.
4. Compare CAS `service` with SAML `entityID`, `ACS`, `AudienceRestriction`, `Destination`, and `InResponseTo`.
5. Distinguish CAS `renew`/`gateway` from SAML `ForceAuthn`/`IsPassive` without claiming they are absolute equivalents.
6. Recognize CAS proxy tickets and SAML IdP proxying as **distinct mechanisms**.
7. Integrate using the corresponding Spring Security modules/classes; never feed a CAS Service Ticket into `Saml2WebSsoAuthenticationFilter` or a `SAMLResponse` into `CasAuthenticationFilter`.
8. Compare logout, cookies, session lifetimes, SSO reuse, error handling, app authorization, and brokered migration strategies.
9. Practice with a Java 17 simulation of **service-bound, one-time ticket** rules, properly testing ST behavior without pretending to build a real CAS Server.
10. Build a QA checklist when an organization migrates from the CAS Protocol to SAML 2.0 or operates both protocols in parallel.

**Scope:** covers the **CAS Protocol** implemented by Apereo CAS and the **SAML 2.0 Web Browser SSO Profile** per OASIS. An **Apereo CAS Server** product can support **multiple protocols** (CAS, SAML 2, OIDC, OAuth2, etc.), but the product being named “CAS” **does not turn all of its endpoints into the CAS Protocol**.

## 2. Lock Down Terminology Before Diving into Flows

| Term | CAS Protocol | SAML 2.0 Web Browser SSO |
| --- | --- | --- |
| Central system | **CAS Server** | **Identity Provider (IdP)** / Asserting Party |
| Application needing login | **CAS client / service** | **Service Provider (SP)** / Relying Party |
| Initial request | Redirect `/login?service=...` | SAML `AuthnRequest` sent to IdP SSO endpoint or IdP-initiated per profile |
| Data returned via browser | `ticket=ST-...` (opaque Service Ticket) | `SAMLResponse` (Base64-encoded SAML XML; usually HTTP POST) |
| Primary verification | CAS client sends ST and `service` to CAS validation endpoint | SP verifies SAML Response/Assertion against metadata and trusted signing certificate |
| Identity result | `cas:user` and attributes if version/endpoint supports | `NameID`, `Subject`, `AttributeStatement` |
| Central SSO session | **TGT** on CAS Server, **TGC** on browser | IdP session/cookie; SAML standard defines no direct TGT/TGC names |
| Application session | `HttpSession`/`SecurityContext` per client | `HttpSession`/`SecurityContext` per SP |
| Key endpoint | `/serviceValidate`, `/p3/serviceValidate` | `AssertionConsumerService (ACS)` |
| Trust model | CAS endpoint, TLS server validation, service allow-list, ST validation | SAML metadata/entityID, IdP signing keys, XML signature and assertion conditions |
| Federated logout | CAS logout + SLO implemented/supported per client and server | SAML Single Logout Profile and `LogoutRequest`/`LogoutResponse` messages |
| Replayable bearer unit? | ST must be **one-time** | SAML Response/Assertion must also block replay via request/session/time/ID per policy |

**Note:** “CAS” can also be used as the name of **an identity platform** supporting SAML/OIDC. This table compares **protocols**, not grading every Apereo CAS software release.

## 3. What Is the CAS Protocol?

CAS (**Central Authentication Service**) is a **ticket-based** centralized authentication model. An application wanting to log a user in redirects the browser to the CAS Server with an application-identifying URL called the **service URL**.

Typically:
1. The client redirects the browser to `https://cas.example.org/cas/login?service=...`.
2. CAS checks for an existing centralized login session; if needed, it authenticates the user.
3. CAS issues a **Service Ticket** dedicated to the registered service.
4. The browser returns to the service callback carrying `ticket=ST-...`.
5. **The application backend** calls `https://cas.example.org/cas/serviceValidate?service=...&ticket=...` over HTTPS.
6. The CAS Server verifies the ST, matching service, expiration, and single use, returning an identity result or error.
7. The application creates a local session and enforces its own authorization.

### CAS Login Sequence

~~~mermaid
sequenceDiagram
    participant B as Browser
    participant APP as Spring Security CAS client
    participant CAS as CAS Server
    B->>APP: GET /private
    APP-->>B: 302 /cas/login?service=https://app.example.org/login/cas
    B->>CAS: GET /cas/login?service=...
    CAS->>CAS: Check TGC/TGT or authenticate user
    CAS-->>B: 302 https://app.example.org/login/cas?ticket=ST-...
    B->>APP: GET /login/cas?ticket=ST-...
    APP->>CAS: Backend HTTPS /cas/serviceValidate?service=...&ticket=ST-...
    CAS->>CAS: Validate ST matches service, unused, unexpired
    alt Ticket valid
        CAS-->>APP: XML authenticationSuccess + user
        APP->>APP: Map principal and permissions, create SecurityContext
        APP-->>B: App session + redirect to resource
    else Ticket invalid
        CAS-->>APP: XML authenticationFailure
        APP-->>B: Handle login failure, grant no Authentication
    end
~~~

The key point is that **the browser does not self-report that the user is CAS-authenticated**. It merely transports the **ST**. The application must call the CAS Server and trust **only a validation result coming from a valid CAS Server**. A string looking like `ST-123` in the URL is not a logged-in user.

## 4. Service Ticket, TGT, and TGC Are Not the Same Artifact

### 4.1 Ticket-Granting Ticket (TGT)

- A TGT represents the centralized login session on the CAS Server.
- CAS manages TGTs per session policies, lifetime, activity, and logout.
- A TGT lets CAS issue new Service Tickets for other services when conditions allow.
- **Never pass a TGT to an application so it can call `serviceValidate`**.

### 4.2 Ticket-Granting Cookie (TGC)

- The browser receives/holds a CAS cookie used to reference the TGT session.
- CAS reads the TGC when the user visits the CAS login endpoint.
- The TGC belongs to the **CAS domain**, not the application's `HttpSession` cookie.
- Deleting the application's `JSESSIONID` does not automatically delete the CAS Server's TGC.
- An existing cookie does not guarantee the TGT is still valid (it may be revoked server-side).

### 4.3 Service Ticket (ST)

- An ST is an **opaque string**, commonly prefixed in examples with `ST-`.
- CAS issues an ST **for one specific service URL**.
- Under CAS Protocol 2.0, an ST is valid for **only one verification attempt**; after a validation attempt, whether it succeeds or fails, CAS must invalidate the ST.
- STs must have short lifetimes to reduce the window for theft and abuse.
- An ST is **not a JWT and not a SAML Assertion**; the application cannot Base64-decode an ST into a user.
- Reading an ST from a browser URL does not prove who the user is. The app must send the ST back to CAS to verify.

### Three Distinct Lifecycles

| Artifact | Where Involved | Can Remain When User Logs Out Locally? |
| --- | --- | --- |
| CAS TGT/TGC | CAS Server/browser on CAS domain | **Yes**; depends on centralized logout |
| CAS Service Ticket | One login transaction to one service | Normally already consumed during validation |
| SP/CAS client HttpSession | Logged-in application | No if local logout invalidated it |

Never treat an ST as a long-lived API access token. It is **unsuitable** for attaching in a Bearer header across all application requests.

## 5. CAS Endpoints and Validation Results by Version

Common endpoints:

| Endpoint | Purpose | Note |
| --- | --- | --- |
| `/cas/login` | CAS authenticates, issues ST; accepts `service` parameter | CAS context path may be configured other than `/cas` |
| `/cas/logout` | Ends CAS SSO session per policy | Does not mean all app local sessions are destroyed |
| `/cas/validate` | CAS Protocol 1.0, simple text response | Do not use as default for attribute-rich CAS 3 |
| `/cas/serviceValidate` | CAS 2.0 XML service-ticket validation | `service` + `ticket` contract |
| `/cas/p3/serviceValidate` | CAS 3.0 validation and user attributes | Do not assume all attributes are present by default |
| `/cas/proxyValidate` | Validates service/proxy tickets per profile | Separate proxy trust/chain rules |
| `/cas/p3/proxyValidate` | Proxy validation with CAS 3 attributes | Requires proper proxy configuration |
| `/cas/proxy` | Issues Proxy Ticket from PGT and `targetService` | Not SAML IdP proxying |

These paths are **CAS protocol endpoints**. An Apereo CAS server may also expose SAML 2.0 endpoints under other path names; inspect the service registry and protocol configuration of each endpoint rather than guessing from the hostname.

### 5.1 Valid `serviceValidate` Example

Server-side request (illustrative; ticket and service values are dummy):

~~~http
GET /cas/serviceValidate?ticket=ST-demo-one-time&service=https%3A%2F%2Fapp.example.org%2Flogin%2Fcas HTTP/1.1
Host: cas.example.org
~~~

CAS XML success:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>opaque-user-42</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

CAS 3.0 with `/p3/serviceValidate` may also return:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>opaque-user-42</cas:user>
    <cas:attributes>
      <cas:department>finance</cas:department>
      <cas:employeeType>staff</cas:employeeType>
    </cas:attributes>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

These snippets are **structural examples**, not responses from a live CAS instance. `cas:user` and attributes must be processed according to **identity mapping/authorization** policy—never auto-grant admin rights from an arbitrary string. Trust the response only if the backend genuinely called a trusted CAS endpoint over HTTPS, verified TLS, and CAS validated the ST.

### 5.2 CAS XML Failure

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationFailure code="INVALID_SERVICE">
    Ticket was issued for a different service
  </cas:authenticationFailure>
</cas:serviceResponse>
~~~

Common codes in CAS 2.x:
- `INVALID_REQUEST`: missing required parameter.
- `INVALID_TICKET`: invalid, expired, already-used ticket, or failed renew policy.
- `INVALID_SERVICE`: ticket was issued for a different service.
- `INTERNAL_ERROR`: internal error during validation.

**These are CAS error codes**, not SAML `StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:Responder"`. A CAS ticket validation failure can still arrive over an ordinary HTTP response; never treat a plain HTTP 200 as successful authentication.

## 6. Why Is the CAS `service` URL a Security Control?

In CAS, the `service` parameter identifies the **target service** to which CAS is permitted to return an ST. During validation, the application must pass the **exact same service URL** corresponding to the issued ST.

Example:

~~~text
Issued ST for:
  https://app.example.org/login/cas

App validates with:
  https://app.example.org/login/cas

=> Valid if ticket and other conditions match.

App validates with:
  http://internal-service:8080/login/cas

=> May fail with INVALID_SERVICE even though both URLs reach the same system behind a proxy.
~~~

Problems typically occur when:
- Public HTTPS is downgraded to internal HTTP by a reverse proxy.
- Host/port/path or context path differs between entry point and validator config.
- Trailing slashes or query parameter differences break CAS service comparison.
- The service URL is not registered/allow-listed on the CAS Server.
- The application reads `service` unchecked from user queries, creating open redirects or ticket leakage.

**Never fix this by making CAS accept uncontrolled wildcard services.** Use a public canonical service URL, register services via an allow-list, configure forwarded headers only from trusted proxies, and test the exact flow.

CAS's service URL **designates one specific callback/service**, and is not equivalent to all of SAML's `Audience`/`Recipient`/`ACS`/`Issuer` elements (which separate into distinct constraints).

## 7. What Is SAML 2.0 Web Browser SSO?

SAML (**Security Assertion Markup Language**) 2.0 standardized by OASIS comprises:
- **Assertions**: verified statements about subject, conditions, and attributes.
- **Protocols**: request/response messages such as `AuthnRequest` and `Response`.
- **Bindings**: how SAML is transported over HTTP, such as **HTTP-Redirect**, **HTTP-POST**, and **HTTP-Artifact**.
- **Profiles**: how protocols + bindings combine for a use case, such as the **Web Browser SSO Profile**.

In standard **SP-initiated Web Browser SSO**:
1. The browser accesses the Spring Security SP application.
2. The SP builds an `AuthnRequest` with ID, issuer, destination, and appropriate ACS/ProtocolBinding constraints.
3. The browser delivers `AuthnRequest` to the IdP SSO endpoint, usually via Redirect.
4. The IdP authenticates the user or reuses an SSO session per policy, creating a SAML Response containing an Assertion.
5. The browser **HTTP POSTs** the `SAMLResponse` form field back to the SP's ACS.
6. The SP parses, verifies the signature and SAML conditions, checks correlation, and creates an `Authentication`.

**Key distinction from CAS:** the SP normally **does not call a CAS-style `/serviceValidate` with an opaque ST**. In SAML HTTP-POST, authentication evidence is inside the **Response/Assertion**, which the SP verifies itself using trust/certs rather than querying a fixed IdP ticket validation endpoint like CAS. **Artifact binding** is a SAML variant requiring back-channel `ArtifactResolve`, but it is a **different protocol/binding** and does not turn a SAML Artifact into a CAS Service Ticket.

### SAML SP-Initiated Flow

~~~mermaid
sequenceDiagram
    participant B as Browser
    participant SP as Spring Security SAML SP
    participant IDP as SAML IdP
    B->>SP: GET /private
    SP->>SP: Create AuthnRequest with ID, Issuer, ACS
    SP-->>B: 302 to IdP SSO with SAMLRequest
    B->>IDP: GET SingleSignOnService
    IDP->>IDP: Authenticate user / use IdP SSO session per policy
    IDP-->>B: HTML form with SAMLResponse (+ RelayState)
    B->>SP: POST /login/saml2/sso/corp
    SP->>SP: Verify XML Signature, Issuer, Audience, Time, Subject, InResponseTo
    alt SAML valid
        SP->>SP: Create Saml2Authentication / SecurityContext
        SP-->>B: HttpSession + redirect protected route
    else SAML invalid
        SP-->>B: Authentication failure, create no new session
    end
~~~

With **IdP-initiated Web Browser SSO**, the IdP may emit a Response without the SP having created an `AuthnRequest` beforehand. You must explicitly decide **whether unsolicited responses are allowed** per framework/profile/trust policy—never disable all `InResponseTo` checks casually during migration.

## 8. Structure of `AuthnRequest`, `Response`, and `Assertion`

### 8.1 `AuthnRequest`

Abbreviated example:

~~~xml
<samlp:AuthnRequest
    xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
    xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
    ID="_req-001"
    Version="2.0"
    IssueInstant="2026-11-07T03:00:00Z"
    Destination="https://idp.example.org/saml/sso"
    AssertionConsumerServiceURL="https://app.example.org/login/saml2/sso/corp">
  <saml:Issuer>https://app.example.org/saml/metadata</saml:Issuer>
</samlp:AuthnRequest>
~~~

This is **illustrative unsigned XML** without proper metadata/certs/trust; do not send to production. `AuthnRequest@ID` lets the SP correlate the Response with the issued request, unlike a CAS ST.

### 8.2 `Response` and `Assertion`

Abbreviated structure to identify parts:

~~~xml
<samlp:Response
    xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
    xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
    ID="_resp-001"
    InResponseTo="_req-001"
    Version="2.0"
    IssueInstant="2026-11-07T03:00:05Z"
    Destination="https://app.example.org/login/saml2/sso/corp">
  <saml:Issuer>https://idp.example.org/issuer</saml:Issuer>
  <samlp:Status>
    <samlp:StatusCode
        Value="urn:oasis:names:tc:SAML:2.0:status:Success"/>
  </samlp:Status>
  <saml:Assertion Version="2.0" ID="_assert-001"
                  IssueInstant="2026-11-07T03:00:05Z">
    <saml:Issuer>https://idp.example.org/issuer</saml:Issuer>
    <saml:Subject>
      <saml:NameID>opaque-user-42</saml:NameID>
    </saml:Subject>
  </saml:Assertion>
</samlp:Response>
~~~

**This example is intentionally minimal** to show element names; it **lacks an XML Signature**, `Conditions`, `AudienceRestriction`, `SubjectConfirmation`, and complete fields, so it is **not an acceptable SAML Response**. A compliant SP must never create a session from this XML merely because `StatusCode=Success`.

In a real SAML Response, you must evaluate:
- Signature on the Response and/or Assertion per SP profile/policy;
- IdP issuer and trusted verification certificate;
- `AudienceRestriction` matching the exact SP entity ID;
- `Destination` and `SubjectConfirmationData` `Recipient` matching the ACS;
- `NotBefore`, `NotOnOrAfter`, `IssueInstant`, and clock skew;
- `InResponseTo` matching `AuthnRequest` for SP-initiated flows;
- `Subject`/`NameID`, authentication statements, and replay prevention;
- Decryption if the IdP sends an `EncryptedAssertion`;
- App-local account/permission policy after authentication.

**Never parse XML with XPath yourself and extract `NameID` as the user** before verification. Use the OpenSAML/Spring Security provider.

## 9. Comparing CAS and SAML 2.0 Flows at Each HTTP Hop

| Question | CAS Protocol | SAML 2.0 Web Browser SSO |
| --- | --- | --- |
| How does the browser go to the central system? | Redirect `/login?service=...` | Redirect/POST `SAMLRequest` carrying `AuthnRequest` (SP-initiated) |
| What does the central system return to the browser? | Redirect to service URL with `ticket=ST-...` | `SAMLResponse` in an HTTP-POST form; other bindings if supported by profile |
| What HTTP method does the app usually receive at callback? | **GET** service callback with `ticket` query | **POST** ACS with `SAMLResponse` form field |
| Is the data arriving via browser enough to authenticate? | No; needs CAS backend validation | No; needs XML signature + SAML condition validation |
| Does the app perform server-to-server validation by default? | Yes: CAS `/serviceValidate` | Not in the CAS ST manner, except profiles/bindings like Artifact resolution |
| Where does identity proof usually live? | XML validation response from CAS Server | SAML Assertion inside Response from IdP |
| What enforces single use? | CAS Server **consumes ST** on validation | SP checks IDs/correlation/conditions/replay policy |
| Primary trust source | Fixed CAS URL, HTTPS/TLS, ST+service, CAS policy | Metadata/entity IDs, trusted signing cert, XML Signature, conditions |
| When is local session issued? | After ticket validation passes | After SAML response/assertion validation passes |
| What if the browser only returns with `ticket`? | That is a CAS-style callback | Not a `SAMLResponse` |
| What if the browser POSTs `SAMLResponse`? | Not CAS `serviceValidate` | That is SAML ACS input |
| Does the app directly see the central IdP/CAS session? | No | No |

**Summary:** A CAS ST is typically a **lookup token verified online by the CAS Server**; a SAML Assertion is a **structured, signed message that the SP must verify itself based on trust**. This is a mechanistic difference, not merely a parameter name change in the URL.

## 10. Trust Boundary: “Trusting the CAS Server” vs. “Trusting a SAML Signing Key”

### 10.1 CAS Protocol: Trust Based on Ticket Validation

The CAS client must:
1. Send the ST and exact service URL to the **configured** CAS Server.
2. Use HTTPS and verify the TLS certificate and hostname of the CAS endpoint.
3. Parse the XML validation response safely; never accept data from a browser-specified CAS endpoint.
4. Create a principal only if the result is `cas:authenticationSuccess` from the trusted CAS Server.
5. Never ignore `INVALID_TICKET`/`INVALID_SERVICE` or accept stale STs.
6. Verify proxy chains when using Proxy Tickets, along with client/service authorization.
7. Map users/roles per internal policy, never granting privileges from arbitrary attribute strings.

In pure CAS Protocol, **an ST does not carry an XML signature** and the app does not “verify an ST signature offline”; proof is obtained by **asking the trusted CAS Server to validate the ticket over a trusted channel**.

### 10.2 SAML 2.0: Trust Based on Issuer + Signature + Conditions

The SAML SP must:
1. Have a **`RelyingPartyRegistration`** for the right IdP/entity ID.
2. Trust the IdP's public signing X.509 certificates via approved metadata/channels.
3. Verify the Response/Assertion signature per profile-compatible settings.
4. Check `Issuer`, `AudienceRestriction`, `Destination`/`Recipient`, timestamps, `SubjectConfirmation`, and correlation.
5. Never trust a certificate embedded inside the Response unless independently tied to the IdP registration/trust.
6. Decrypt encrypted assertions using the SP's private key when the IdP encrypts.
7. Never “fix” login by disabling signature, audience, time, or recipient checks.

**HTTPS is still required** to protect the browser and metadata endpoints. However, the IdP web server's TLS certificate **is not automatically the SAML Assertion signing certificate**. A working `https://idp.example.org` URL does not prove any `SAMLResponse` claiming that issuer is valid.

### 10.3 Both Produce a Local Session After Login

Both CAS and SAML can end in a **Spring Security `Authentication`/`SecurityContext`/`HttpSession`**. Once the application session exists, it **does not re-query CAS or the IdP on every request**. Privilege revocation, account locking, and logout require separate mechanisms aligned with risk.

## 11. CAS `service` Compared to SAML Identifiers

| CAS | Closest SAML Purpose Equivalent | Why It Is Not a 1:1 Mapping |
| --- | --- | --- |
| `service=https://app.../login/cas` | SP ACS URL, Recipient/Destination | CAS typically uses one service URL to issue and validate STs; SAML separates receiving endpoint, recipient, and conditions |
| CAS service allow-list | IdP config for SP entity ID, ACS allow-list | One manages service URLs; the other manages SAML registrations/metadata |
| CAS username/user attributes | `NameID`/`AttributeStatement` | Identifiers, formats, qualifiers, and semantics can differ |
| CAS ST | SAML Response/Assertion | ST is an opaque one-time credential; Assertion is XML with signatures/conditions |
| CAS TGT/TGC | IdP SSO session/cookie | Similar user experience lifecycle, different protocol structures |
| CAS `renew` | SAML `ForceAuthn` | Similar reauthentication intent, different obligations/conditions/mechanisms |
| CAS `gateway` | SAML `IsPassive` | Same non-interactive goal, different failure/response semantics |
| CAS PGT/PT | SAML proxying/artifact (superficially similar ideas) | **Not interchangeable**; different protocols, issuers/trust, and message lifecycles |

**Never look for a setting that “directly turns an ST into an Assertion”** by renaming query parameters. Switching protocols requires a **broker/adapter** that completes full validation on one side and mints a fresh message under the other protocol.

## 12. CAS `renew`/`gateway` and SAML `ForceAuthn`/`IsPassive`

The CAS Protocol has two commonly used login parameters:

### `renew`

~~~text
https://cas.example.org/cas/login?service=...&renew=true
~~~

`renew` requests a fresh login based on **primary credentials** per the CAS spec rather than benefiting from an existing SSO session. On ticket validation, `renew=true` can ensure the ST was issued after authentication meeting CAS's freshness condition.

### `gateway`

~~~text
https://cas.example.org/cas/login?service=...&gateway=true
~~~

`gateway` asks CAS **not to prompt the user interactively for credentials**. If non-interactive authentication is not possible, CAS may return the browser to the service **without a ticket** so the app knows there is no silent SSO.

In SAML 2.0:
- `AuthnRequest ForceAuthn="true"`: asks the IdP to authenticate directly rather than relying solely on a prior security context, per SAML Core.
- `AuthnRequest IsPassive="true"`: requires processing without the IdP/user agent visibly taking control of the UI; if unable, the IdP returns an appropriate error such as `NoPassive`.

| Product Intent | CAS | SAML |
| --- | --- | --- |
| Standard SSO login | Omit `renew`/`gateway` | `ForceAuthn=false`, `IsPassive=false` or omitted |
| Check user non-interactively | `gateway=true` | `IsPassive=true` |
| Force fresh authentication | `renew=true` | `ForceAuthn=true` |
| No session for silent login | CAS redirects to service **without a ticket** | SAML responder may return `NoPassive` error in Response |
| Combine both renew and gateway | CAS spec leaves semantics unclear when combined; avoid | SAML defines rules when both `ForceAuthn` and `IsPassive` are true; must not break passive requirement |

**Do not treat the two flag pairs as absolute equivalents**:
- CAS `renew` references primary credentials; SAML `ForceAuthn` does not by default mandate password re-entry or MFA.
- CAS `gateway` typically produces a **ticketless callback** when impossible; SAML `IsPassive` typically produces an **error status in the SAML Response**.
- Any migration must test actual IdP/CAS policies rather than renaming flags and claiming identical assurance levels.

## 13. CAS Proxy Tickets Differ from SAML Proxying

The CAS Protocol includes **proxy authentication** when service A must call service B on the user's behalf:
1. Service A validates the ST and can request a **Proxy-Granting Ticket (PGT)** via a `pgtUrl` callback.
2. The CAS Server sends PGT details to the trusted callback; A correlates `pgtIou` with the validation result.
3. A uses the PGT to request a **Proxy Ticket (PT)** for `targetService` B.
4. B calls `/proxyValidate` with the PT, target service, and checks the **proxy chain/policy**.
5. App B enforces appropriate authorization for the principal and intermediate proxies.

In SAML:
- There may be **IdP proxying** via `Scoping`/`ProxyCount`/`IDPList` and specific profiles/conditions.
- There is **SAML Artifact binding** to pass a reference via the browser and resolve it over a back-channel.
- There are `SubjectConfirmation`, audiences, and other delegation extensions/profiles.

These mechanisms **are not CAS PGT/PT**. Never feed a CAS Proxy Ticket into SAML `ArtifactResolve`, and never use a SAML Artifact as a CAS ST. If a system must support multi-hop delegation through a broker, build explicit trust/claim mapping, validate the exact protocol on both sides, and preserve audit provenance.

## 14. Does a CAS Server Support SAML, and What Does That Mean?

Apereo CAS Server is a **server product** capable of supporting multiple protocols. One deployment can let:
- Legacy App A log in with CAS Protocol: `/cas/login?service=...`.
- App B log in with SAML 2.0: `AuthnRequest → SAMLResponse`.
- App C log in with OpenID Connect: `/authorize → code → token endpoint`.

All may share the same identity backend or SSO policy, yet **each client's authentication/trust path is distinct**.

For example, you cannot conclude:
> “The server is called CAS, so the SAML client just needs to call `/serviceValidate`.”

False: `/serviceValidate` is CAS Protocol. A SAML SP needs IdP `entityID`, `SingleSignOnService`, signing certificates/metadata, ACS, and SAML validation.

Conversely, a SAML IdP sitting behind a broker does not directly issue CAS STs to a legacy app unless the broker/server acts as a CAS Server toward the legacy client.

## 15. Spring Security CAS: Relevant Components

Spring Security has a CAS integration module via `spring-security-cas`. Per documentation, the key classes are:

| Component | Responsibility |
| --- | --- |
| `ServiceProperties` | Configures service callback URL and `sendRenew` |
| `CasAuthenticationEntryPoint` | Redirects unauthenticated browser to CAS `/login?service=...` |
| `CasAuthenticationFilter` | Receives `ticket` at callback (usually `/login/cas`) |
| `CasAuthenticationProvider` | Validates CAS ticket via validator and creates `Authentication` |
| `Cas20ServiceTicketValidator` | Client library validating ST via CAS 2.0 `/serviceValidate` |
| `Cas20ProxyTicketValidator` | Supports proxy tickets when required and permitted by policy |
| `AuthenticationUserDetailsService` | Maps CAS principal to authorities in Spring |
| `CasAuthenticationToken` | `Authentication` created by Spring after successful CAS validation |
| `ServiceAuthenticationDetailsSource` | When service URL must be determined dynamically per request |

### Standard CAS Wiring Conditions

In Spring Security documentation, traditional XML config examples show:

~~~xml
<bean id="serviceProperties" class="org.springframework.security.cas.ServiceProperties">
  <property name="service"
            value="https://app.example.org/login/cas"/>
  <property name="sendRenew" value="false"/>
</bean>

<bean id="casEntryPoint"
      class="org.springframework.security.cas.web.CasAuthenticationEntryPoint">
  <property name="loginUrl" value="https://cas.example.org/cas/login"/>
  <property name="serviceProperties" ref="serviceProperties"/>
</bean>

<bean id="casFilter"
      class="org.springframework.security.cas.web.CasAuthenticationFilter">
  <property name="authenticationManager" ref="authenticationManager"/>
</bean>
~~~

**This is an illustrative configuration excerpt, not a complete Spring `ApplicationContext` XML**: `authenticationManager`, provider, ticket validator, `UserDetailsService`, filter chain, and namespaces still need declaration. Real beans must be wired into the exact Spring Security filter chain. Spring's CAS docs contain historical XML namespace examples written for older Spring Security versions—**never copy old config structures verbatim into Boot 3.x/7.x projects without checking versions**.

### Java Snippet Configuring `ServiceProperties`

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.cas.ServiceProperties;

@Configuration
public class CasServicePropertiesConfig {

    @Bean
    ServiceProperties serviceProperties() {
        ServiceProperties properties = new ServiceProperties();
        properties.setService("https://app.example.org/login/cas");
        properties.setSendRenew(false);
        return properties;
    }
}
~~~

This class **has valid Java syntax** but is only **a single configuration bean**, not a complete CAS login app: it lacks the CAS entry point/filter/provider/ticket validator/user details, `spring-security-cas` dependency, Java Servlet app `main`, and a real CAS Server. There is no fixed stdout. If using a Spring Security version with changed packages/APIs, check the exact Javadoc.

**Note:** do not set `sendRenew(true)` just to “increase security” and think every request is re-authenticated. `renew` can repeatedly prompt users for credentials and must be properly supported by the CAS Server/validator; step-up also requires dedicated MFA/account policies.

## 16. Spring Security SAML2: Completely Different Components

In modern Spring Security, SAML 2.0 integration uses the module:

~~~groovy
implementation 'org.springframework.security:spring-security-saml2-service-provider'
~~~

With Spring Boot 3.x and matching plugin/dependency management, Java Servlet code:

~~~java
package com.example.federation;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SamlWebSsoConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/", "/public/**", "/error").permitAll()
                        .anyRequest().authenticated())
                .saml2Login(Customizer.withDefaults())
                .build();
    }
}
~~~

Example `application.yml` with vetted IdP metadata:

~~~yaml
spring:
  security:
    saml2:
      relyingparty:
        registration:
          corp:
            assertingparty:
              metadata-uri: "classpath:saml/idp-metadata.xml"
~~~

**Prerequisites:** a Spring Boot Servlet app, Spring Web/Security/SAML2 dependencies, real IdP metadata (`entityId`, SSO endpoint, verification cert), and SP metadata/ACS registered at the IdP. The Java config above **does not run standalone via `javac`** and has no fixed stdout. Some Boot/Spring Security releases use different `metadata-uri`/namespace properties; verify against your active release.

Spring Security components:

| SAML Component | Role |
| --- | --- |
| `RelyingPartyRegistrationRepository` | Holds SP details, IdP metadata, certs, ACS |
| `Saml2WebSsoAuthenticationRequestFilter` | Builds and sends `AuthnRequest` |
| `Saml2AuthenticationRequestResolver` | Prepares `AuthnRequest` and binding/destination |
| `Saml2WebSsoAuthenticationFilter` | Receives `SAMLResponse` at ACS |
| `OpenSaml4AuthenticationProvider` / `OpenSaml5AuthenticationProvider` | Parses, validates, and authenticates SAML, depending on version/stack |
| `Saml2Authentication` | SP-verified SAML login result |
| `Saml2AuthenticatedPrincipal` | Principal/attributes from SAML per Spring API |
| `Saml2X509Credential.verification` | Trusted IdP public X.509 cert used to verify signatures |

Spring Security 6.x includes OpenSAML 4-based versions, while newer releases support/target OpenSAML 5; Spring Security 7.x uses corresponding classes. **Never rename everything to `OpenSaml5` when the dependency is absent**, and never place `CasAuthenticationProvider` inside the SAML chain.

### Different Spring Security Endpoints

| CAS Client | SAML SP |
| --- | --- |
| `/login/cas?ticket=...` (CAS callback pattern) | `/login/saml2/sso/{registrationId}` (SAML ACS pattern) |
| CAS entry point redirects `/cas/login?service=...` | `/saml2/authenticate/{registrationId}` creates SAML `AuthnRequest` |
| Validator calls CAS `/serviceValidate` | Spring provider verifies `SAMLResponse` and assertion |
| `ServiceProperties.service` | `RelyingPartyRegistration.entityId` / `assertionConsumerServiceLocation` |
| CAS user + attributes | SAML `NameID` + attributes |

**Never configure both filters to intercept the same callback URL** unless you intentionally build a proper dispatcher/routing flow. When coexisting, use separate URLs and an explicit mechanism-selection policy.

repositories {

## 18. XML Signatures and HTTPS: Why Neither Can Be Dropped

### CAS Protocol

An ST is carried by the browser via query string, and then the app uses **backend HTTPS** to reach the CAS Server for validation. Critical trust checks include:
- The app never calls validation against an arbitrary browser-supplied host.
- The CAS Server's TLS certificate and hostname are properly verified.
- The ST matches the service, is unused, and is unexpired.
- The CAS service registry permits the app to receive STs.
- The XML response is parsed safely without unintended redirects to another host.
- Proxy flows are trusted under separate policy.

A CAS ST **does not need its own signature**, because the server maintains ST state and the app queries the trusted CAS Server directly.

### SAML Web Browser SSO

`SAMLResponse` travels over the browser front-channel. The browser is an **untrusted transport**. The SP must verify:
- XML Signature with safe ID/reference/canonicalization handling, preventing signature wrapping.
- The IdP's signing certificate belongs to approved metadata/trust.
- Issuer, audience, recipient, destination, temporal conditions, and subject confirmation.
- Request correlation and replay prevention, if SP-initiated.
- Decryption if the assertion is encrypted, using the exact SP private key.

SAML can use HTTP-Redirect binding with query `SigAlg`/`Signature` on `AuthnRequest` or HTTP-POST with XML Signature, depending on flow/config. **Never equate a CAS ST directly with a SAML XML Signature**: one relies on ticket state + validation, the other on message signatures + conditions.

**TLS is still mandatory in SAML** for browser/metadata endpoints. It protects transport, but **never replaces** assertion signatures.

## 19. Post-Login Authorization: Neither Automatically Grants Business Permissions

CAS can return:
- `cas:user`;
- CAS 3.0 `cas:attributes`, such as department, group, affiliation.

SAML can return:
- `NameID`;
- `AttributeStatement`, `AuthnStatement`;
- `AuthnContext` when emitted by the IdP per profile.

Even so:
1. The SP/app must map identities using stable keys scoped by tenant/issuer.
2. Never use an unverified email as a global account ID.
3. Never auto-grant `ROLE_ADMIN` merely because a response includes `group=admins` from a partner not authorized to grant that role.
4. Permissions can change **after the Spring Security session was created**; `Authentication.getAuthorities()` can become stale.
5. For sensitive actions, verify account enabled/locked status and current permissions under app authorization policy.
6. Successful SSO authentication never proves authorization to view every resource.

**A CAS username and a SAML `NameID` are not guaranteed to be the same identifier** during migration. The IdP may issue an opaque persistent `NameID`, a transient `NameID`, or another identifier; establish an account mapping plan rather than equating strings that look alike.

## 20. CAS Logout Differs from SAML Single Logout

### 20.1 CAS Logout

CAS Server `/logout` can destroy the CAS SSO session/TGT and related cookies per policy. CAS also supports **Single Logout notifications** to participating clients when supported and configured on both server and client. However:
- App local sessions are not automatically erased just because the CAS TGT is gone.
- If an application does not process CAS SLO messages, its local session can persist.
- A user logging out locally at the app while CAS TGC remains can immediately SSO again.
- Format/delivery of CAS SLO messages depends on version and profile, and does not default to SAML 2.0 `LogoutRequest`.

### 20.2 SAML Single Logout

SAML 2.0 defines the **Single Logout Profile** with `LogoutRequest` and `LogoutResponse`. SP-initiated/IdP-initiated SLO requires `SingleLogoutService` metadata, signing keys, trust/validation, and session correlation. The browser may participate via front-channel chains; other bindings may exist if supported.

**Never call a CAS logout URL as a SAML `SingleLogoutService`** when the CAS Server is exposing a CAS protocol endpoint. Likewise, never POST a SAML `LogoutRequest` to CAS Protocol `/cas/logout` expecting SAML 2.0 XML handling.

### 20.3 Logout Across All Devices?

Neither protocol by itself guarantees that **every session across every device, every application, OAuth/JWT tokens, WebSockets, and non-participating systems** is revoked. Separate session registries, token revocation, events, IdP policies, and monitoring are required.

## 21. Session Lifetimes and SSO Reuse

Suppose a user logs into App A via CAS at 09:00:
- The ST is consumed, while App A's HTTP session may persist.
- CAS TGT/TGC may persist, allowing a new ST when the user visits App B.
- If the account is locked on the CAS Server at 10:00, App A's SP/local session **is not necessarily invalidated**.

With SAML 2.0:
- The Assertion is verified at login and creates the SP's `HttpSession`.
- The IdP session may persist to issue a new `SAMLResponse` for App B.
- The assertion's `NotOnOrAfter` **does not automatically mean the SP session expires at the same time**, unless policy/app explicitly enforces that.
- Locking the IdP account does not guarantee active SP sessions are terminated immediately without SLO/authorization revocation.

**Therefore:** before migrating, define consistent policies for account disablement, permission changes, session idle/absolute TTL, global logout, and active session revocation across both protocols. Changing the callback protocol alone never solves stale sessions.

## 22. Standalone Java 17: Simulating Service-Bound and One-Time CAS STs

The program below illustrates **a signature rule of the CAS Protocol**: an ST issued by the server for one service URL is valid only for a time window and is consumed after **one validation attempt**, even when the presented service is wrong. The code **does not** mint real CAS tickets, implement CAS login/HTTPS, verify XML, or act as a production server.

File `CasTicketLifecycleDemo.java`:

~~~java
import java.time.Instant;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public final class CasTicketLifecycleDemo {

    record Ticket(String service, String subject, Instant expiresAt) {
    }

    static final class TicketStore {
        private final Map<String, Ticket> tickets =
                new ConcurrentHashMap<>();

        void issue(String opaqueTicket, String service,
                   String subject, Instant expiresAt) {
            tickets.put(opaqueTicket, new Ticket(
                    service, subject, expiresAt));
        }

        String validate(String opaqueTicket, String presentedService,
                        Instant now) {
            // Consumes on first validation attempt, including invalid service.
            Ticket ticket = tickets.remove(opaqueTicket);
            if (ticket == null) {
                return "DENY";
            }
            if (!ticket.expiresAt().isAfter(now)) {
                return "DENY";
            }
            if (!ticket.service().equals(presentedService)) {
                return "DENY";
            }
            return "ALLOW:" + ticket.subject();
        }
    }

    public static void main(String[] args) {
        Instant now = Instant.parse("2026-11-07T03:00:00Z");
        String callback = "https://app.example.org/login/cas";
        String wrongCallback = "https://evil.example.org/login/cas";
        TicketStore server = new TicketStore();

        server.issue("ST-demo-01", callback, "user-42",
                now.plusSeconds(60));
        System.out.println("Correct service: " +
                server.validate("ST-demo-01", callback, now));
        System.out.println("Replay: " +
                server.validate("ST-demo-01", callback, now));

        server.issue("ST-demo-02", callback, "user-42",
                now.plusSeconds(60));
        System.out.println("Wrong service: " +
                server.validate("ST-demo-02", wrongCallback, now));
        System.out.println("Retry after wrong service: " +
                server.validate("ST-demo-02", callback, now));

        server.issue("ST-demo-03", callback, "user-42",
                now.minusSeconds(1));
        System.out.println("Expired: " +
                server.validate("ST-demo-03", callback, now));
    }
}
~~~

Run with Java 17+:

~~~bash
javac CasTicketLifecycleDemo.java
java CasTicketLifecycleDemo
~~~

**Exact** stdout:

~~~text
Correct service: ALLOW:user-42
Replay: DENY
Wrong service: DENY
Retry after wrong service: DENY
Expired: DENY
~~~

Explanation:
1. The first ST was issued for the matching service and unexpired, so validation succeeds.
2. The second use is rejected because the ST was already consumed.
3. The next ST is presented for a **different service**, so it fails.
4. Even when retried with the exact service, that ST was invalidated after the first validation attempt.
5. An expired ST is rejected.

**Security limitations of the demo:** `ST-demo-01` is a predictable dummy string; real CAS must mint cryptographically random tickets with policy-driven TTL, storage/concurrency/replication, service allow-lists, and a trusted HTTPS validation endpoint. `ConcurrentHashMap.remove` simulates single-use consumption within one JVM, insufficient as a distributed production ticket store. Never copy this code as security middleware or a CAS Server.

### Comparison with SAML

An equivalent SAML program **must not** merely take a `SAMLResponse` string and call `validate(ticket, service)`. It requires **XML Signature, IdP certificate trust, issuer, audience, subject, recipient, validity, replay, `InResponseTo`**, and safe parsing. In Spring Security, let the SAML/OpenSAML provider handle those steps.

## 23. Observing CAS and SAML Yourself via Browser/Network Traces

### CAS Protocol

1. Browser has no app session and visits `/private`.
2. Network shows a redirect to **CAS login** with the `service` parameter.
3. After CAS login, browser returns to the callback with query `ticket=ST-...`.
4. In the browser you **will not see** the backend HTTPS `/serviceValidate` call if it is server-to-server; inspect authorized CAS client server logs/traces.
5. App creates a session if validation passes.
6. `INVALID_SERVICE` usually relates to public callback/service mismatch; `INVALID_TICKET` can indicate expired/replayed/wrong ticket.
7. Never record raw tickets in analytics, public logs, screenshots, or widely shared HAR files.

### SAML 2.0 Web Browser SSO

1. Browser visits `/private`; SP initiates SAML login.
2. Redirect carries `SAMLRequest` (Redirect binding) or a form POST carries the request.
3. After authentication, IdP returns an HTML form with `SAMLResponse` and optionally `RelayState`.
4. Browser HTTP POSTs to ACS `/login/saml2/sso/corp`.
5. Spring provider verifies SAML signature, issuer, audience, subject/time, and correlation.
6. App creates a session if checks pass; a provider failure does not mean the IdP sent a non-Success status.
7. Never copy raw SAML Assertions, `NameID`, or cookies into shared logs.

**Core DevTools difference:** a `GET callback with ticket` is not a `POST ACS with SAMLResponse`. However, systems can have custom bindings or proxy rewrites, so identify via **message format + protocol contract**, not HTTP method alone.

## 24. CAS and SAML Errors: Never Equate Error Codes

| Symptom | Protocol / Fault Layer | How to Investigate |
| --- | --- | --- |
| `cas:authenticationFailure code="INVALID_TICKET"` | CAS validation | Expired/used ST, wrong ticket, renew policy |
| `cas:authenticationFailure code="INVALID_SERVICE"` | CAS validation | `service` mismatch, reverse proxy, service registry |
| CAS server `UNAUTHORIZED_SERVICE` | CAS policy/registry | App/callback not authorized by CAS |
| CAS XML response parse failure | CAS client/backend | HTTP/TLS, XML parser, wrong endpoint |
| CAS `403` after login | Application authorization | Session/roles/resource permissions |
| SAML `StatusCode=Responder` | IdP reports protocol failure | IdP policy, status subcode if present |
| SAML `NoPassive` | IdP cannot satisfy `IsPassive` | IdP session, requested passive policy |
| Spring SAML invalid signature | SAML SP validation | IdP signing cert, metadata, payload tampering |
| Spring SAML audience mismatch | SAML SP validation | SP entity ID and IdP audience config |
| SAML Response expired | SAML SP validation | `NotBefore`/`NotOnOrAfter`/clock skew |
| SAML `InResponseTo` mismatch | SAML SP correlation | Saved `AuthnRequest`/session/cookie |
| HTTP 403 at ACS | HTTP/filter/CSRF or validation | Inspect exact host/filter/server logs; do not infer IdP status |
| Login succeeds yet route returns 403 | App authorization | Account enabled, role mapping, tenant ACL |
| Immediate SSO again after local logout | CAS or SAML | CAS TGC/IdP SSO session still alive |

CAS `INVALID_TICKET` **is not equivalent** to SAML `AuthnFailed`; one is an ST validation failure, the other is an IdP protocol status. A SAML Response with `Success` can still be rejected by the SP due to local signature/audience checks; CAS can return HTTP 200 while the XML contains `authenticationFailure`.

## 25. Migration Strategy from CAS Client to SAML 2.0 SP

### 25.1 Start from Contracts, Not Config Files

Before switching:
1. Inventory all CAS services using `/login?service=...`, `/login/cas` callbacks, service registry entries, `renew`/`gateway`, and CAS SLO.
2. Determine how the app derives **username/attributes/authorities** from CAS validation and which authority sources are trusted.
3. Check whether the app uses CAS proxy tickets/PGTs to call downstream services. **This is a major transition point**.
4. Define app session handling, timeouts, logout, account lock/role changes, and audit requirements.
5. Select a SAML IdP capable of required SSO/metadata/signing/encryption/`NameID`/Attributes.
6. Register SP entity ID, ACS, SLO URL (if needed), and trust certificates.
7. Define the **CAS username → SAML `NameID`/stable external ID** mapping; never link accounts via unverified email.
8. Determine whether IdP-initiated login must be supported and assess unsolicited-response risks.
9. Plan cutover, backout, test accounts, and log redaction.

### 25.2 Functional Configuration Mapping

| Currently with CAS | After Migration to SAML |
| --- | --- |
| CAS server login URL | IdP `SingleSignOnService` metadata endpoint |
| `ServiceProperties.service` | SP `entityId` + ACS `assertionConsumerServiceLocation` |
| `CasAuthenticationEntryPoint` | SAML `Saml2WebSsoAuthenticationRequestFilter` / EntryPoint |
| `CasAuthenticationFilter` | `Saml2WebSsoAuthenticationFilter` |
| `CasAuthenticationProvider` + `TicketValidator` | OpenSAML authentication provider / SAML validation |
| CAS ST in query | `SAMLResponse` XML via ACS |
| CAS user/attributes | SAML `NameID`/`AttributeStatement` |
| CAS `renew` | SAML `ForceAuthn` (test semantics) |
| CAS `gateway` | SAML `IsPassive` (no 1:1 response mapping) |
| CAS SLO | SAML Single Logout (requires dedicated metadata/profile) |
| CAS proxy tickets | Requires new delegation/downstream trust design; no direct mapping |

### 25.3 Option A: Full Application Cutover to SAML

- Remove the CAS entry point/filter/provider from protected routes and use `.saml2Login()`.
- Replace the service callback with the SP ACS and register metadata with the IdP.
- Configure trusted IdP signing credentials and SP signing/decryption credentials as needed.
- Ensure proper SAML attributes/`NameID` mapping and local authorization.
- Test login, invalid signatures, audience, time checks, logout, reverse proxy, and account disablement.
- If legacy CAS interaction with downstream services was used, build a new solution rather than passing STs/PTs through the SAML channel.

### 25.4 Option B: Running CAS and SAML in Parallel

- Dedicate separate endpoints: CAS `/login/cas`, SAML `/login/saml2/sso/{registrationId}`.
- Configure Spring Security filter chains/request matchers properly to avoid filter collisions.
- Clearly track which protocol/IdP authenticated the user; map consistently to a verified internal account ID.
- Test sessions, logout, and permissions for the same user across both methods to prevent account takeover.
- Support tenant- or service-based cutover/rollback, logging metrics segmented by protocol and failure type.
- Never enable an “accept responses from any IdP” mode just to ease coexistence.

### 25.5 Option C: Using a Broker Keeping CAS for Legacy Apps and Issuing SAML to New Apps

The broker/server verifies the **inbound protocol** and issues the **outbound protocol** under separate trust:
- Legacy CAS clients still obtain STs and validate at the CAS endpoint.
- New SAML clients receive Assertions issued by a SAML IdP/broker.
- The broker manages identity mapping, assurance, sessions, and logout coverage.
- SAML apps trust **the broker's signing certificate and issuer**, never trusting upstream CAS TGT/STs directly.
- If the broker validates tickets from an upstream CAS, it must protect backend TLS and service binding like any CAS client.
- Never accept an ST string from the browser and mint Assertions for any client without validation and audience agreement.

### 25.6 Data and Account Identity Strategy

CAS `cas:user=alice` and SAML `NameID=alice` look identical but can belong to **two different identity namespaces**. Better practices:
- Key internal accounts on a governed immutable ID, mapped per issuer/tenant.
- Enforce a verified account-linking workflow instead of auto-merging by email.
- Use only approved SAML groups/roles; never let another scope grant admin access.
- Active permission revocations/updates must still take effect for existing sessions even as the protocol changes.

## 26. CAS and SAML Test Matrix During Transition

| Test | Expected CAS | Expected SAML |
| --- | --- | --- |
| User has no central session | CAS login form or matching policy | IdP login or matching policy |
| User already has central session | CAS uses TGC/TGT, issues ST if allowed | IdP SSO session, emits Response if allowed |
| Browser callback | `ticket=ST-...` | `SAMLResponse` |
| Backend validation | Calls CAS `serviceValidate` | OpenSAML verifies XML Signature/conditions |
| Ticket/Response replay | ST fails on second validation | SP blocks replay of response/assertion/request |
| Callback URL changes | `INVALID_SERVICE` or service policy | Destination/Recipient/ACS mismatch |
| Wrong trust source | CAS TLS/endpoint mismatch | IdP signature/issuer/metadata mismatch |
| Account lacks permission | App authorization deny | App authorization deny |
| Renew/force reauth | CAS `renew` policy | SAML `ForceAuthn` + IdP policy |
| Silent login without session | CAS `gateway` returns without ST | SAML `IsPassive` may return `NoPassive` |
| Local logout | Clears SP/CAS client session; TGC may remain | Clears SP session; IdP session may remain |
| Federated logout | CAS SLO when server/client support | SAML `LogoutRequest`/`LogoutResponse` when supported |
| Multi-node | Shared session/ticket server, client state | Shared request repository/session + metadata/cert |
| Disabled user | CAS policy + live app state | SAML IdP policy + live app state |

**In real environments:** test both HTTP traces and server logs on each side using authorized negative scenarios. Never send production user STs or `SAMLResponse`s to a test service for debugging.

## 27. Procedure for Reading Logs and Pinpointing Root Cause

### CAS Case: Browser Has an ST, Yet App Reports Login Failed

1. Check that the browser actually sent `GET /login/cas?ticket=...` to the app.
2. Verify whether the CAS client called the right CAS Server `/serviceValidate` over backend HTTPS.
3. Compare the `service` used to request the ST with the `service` used to validate it. Public HTTPS/scheme/host/path must match.
4. Check whether the ticket was already validated earlier by a proxy or retry; STs are single-use.
5. Inspect the CAS validation XML, distinguishing `authenticationSuccess` from `authenticationFailure`.
6. If validation succeeded yet the app returned 403, inspect authorities and business account policies instead of blaming CAS.
7. Redact tickets/cookies/usernames before sharing HAR files or logs.

### SAML Case: Browser POSTs Response, Yet App Login Failed

1. Check whether the ACS endpoint and `SAMLResponse` POST reached the SP.
2. Inspect provider logs: parsing, signature verification, trusted IdP certificate, and issuer.
3. Compare `Destination`/`Recipient`/`Audience`/`EntityID` and public URLs behind proxies.
4. Check `NotBefore`/`NotOnOrAfter`, NTP/clock skew, `InResponseTo`, and session cookies.
5. Check whether the assertion is encrypted and whether the SP decryption key matches.
6. If the IdP sent a non-Success Status, record **IdP-reported status**; if status was Success yet signature failed, record **SP verification failure**.
7. If `Authentication` succeeded yet the route returned 403, investigate application authorization.

### Classifying by Failure Point

~~~mermaid
flowchart TD
    A[SSO login failed] --> B{Callback carries ticket or SAMLResponse?}
    B -- ticket --> C[CAS client]
    C --> D{Backend /serviceValidate succeeded?}
    D -- No --> E[CAS ticket/service/TLS validation]
    D -- Yes --> F[Spring principal mapping and app authorization]
    B -- SAMLResponse --> G[SAML SP]
    G --> H{XML/Signature/Conditions verified?}
    H -- No --> I[SP SAML trust/metadata/clock/correlation]
    H -- Yes --> J[Spring principal mapping and app authorization]
    B -- No callback --> K[Browser/proxy/CAS-or-IdP endpoint/network]
~~~

This diagram is solely for triage and has no authority to establish `Authentication` from an unverified query or XML value.

## 28. Misconceptions to Avoid

1. **“CAS and SAML both redirect, so they share the same security controls.”** False. CAS ST validation and SAML Signatures/Conditions are two different mechanisms.
2. **“A CAS Service Ticket can be decoded to get the user.”** False. An ST is opaque; the CAS backend verifies it and returns the user.
3. **“One ST can be reused repeatedly to log in.”** False for CAS Protocol STs: one-time validation attempt.
4. **“A SAML Assertion is just a longer ST.”** False. An Assertion is an XML statement with issuer, subject, conditions, and signature.
5. **“HTTPS is enough to accept a `SAMLResponse`.”** False. The browser transports the XML, so signature/trust/conditions must be verified.
6. **“SAML must call `/serviceValidate` like CAS.”** False for HTTP-POST Browser SSO. Artifact binding has its own back-channel, not a CAS endpoint.
7. **“CAS `renew` is identical to SAML `ForceAuthn`.”** Similar only in intent; semantics and policies differ.
8. **“CAS `gateway` = SAML `NoPassive` status.”** CAS may return without a ticket; SAML returns a protocol error status.
9. **“Apereo CAS Server supports SAML, so the CAS Protocol is SAML.”** False: one product, multiple protocols.
10. **“The Spring CAS client is enough to handle SAML 2.0.”** False: different modules and protocol handlers.
11. **“Once SAML is signed, audience checks aren't needed.”** False: a signed assertion may have been issued for a different SP.
12. **“CAS validation success or SAML Response Success means the user has `ADMIN` rights.”** False: authorization is a separate app step.
13. **“CAS `/logout` or SAML SLO automatically erases all JWTs and devices.”** Not guaranteed.
14. **“Just changing the CAS callback URL to ACS completes the migration.”** False: trust, identity mapping, logout, proxying, and testing also remain.
15. **“HTTP 200 from CAS/IdP means login succeeded.”** False: inspect the actual response and SP/app validation.
16. **“An ST in a browser URL is safe to log.”** False: it is a short-lived credential exploitable before consumption.
17. **“Matching text between SAML `NameID` and CAS user means the same account.”** Not guaranteed; requires namespace/issuer/tenant mapping.
18. **“Changing permissions at CAS/IdP updates all `HttpSession`s automatically.”** False: sessions may hold a stale snapshot of authorities.

## 29. Self-Check Exercises with Answers

**Q1.** The browser returns to `/login/cas?ticket=ST-123`. Can the application create a session as soon as it sees `ST-`?

**Answer:** No. The backend must validate the ST with the trusted CAS Server and exact service URL, and check success/failure before creating an `Authentication`.

**Q2.** A CAS client validates an ST with the wrong service URL and gets `INVALID_SERVICE`. Should retrying that old ST with the right service URL succeed?

**Answer:** No. Per spec, a CAS ST is invalidated after a single validation attempt, even if it fails.

**Q3.** How do CAS TGT and TGC differ?

**Answer:** TGT is the CAS Server-side ticket/SSO session; TGC is the browser cookie referencing that centralized session. Both differ from a single-use per-service ST.

**Q4.** The IdP returns a `SAMLResponse` with `StatusCode=Success` and `NameID=admin`, but the XML Signature is invalid. Should the SP create an `Authentication`?

**Answer:** No. Status/`NameID` never replace signature, trust, and condition validation.

**Q5.** At which endpoint can CAS return user attributes?

**Answer:** CAS 3.0 typically uses `/p3/serviceValidate` to return CAS attributes, depending on server/registration policy. Never assume CAS 1.0 `/validate` provides metadata attributes.

**Q6.** Is `AudienceRestriction` in SAML close to CAS's “service-bound” idea?

**Answer:** It shares the goal of restricting the intended recipient, but **is not a 1:1 mapping**. SAML also uses `Issuer`, `Recipient`, `Destination`, ACS, `SubjectConfirmation`, request correlation, and signatures.

**Q7.** Do CAS `renew=true` and SAML `ForceAuthn=true` both guarantee MFA?

**Answer:** No. They request fresh authentication per each protocol's semantics, while MFA/assurance require dedicated policies and evidence.

**Q8.** Browsers GET the app with a CAS ST, whereas SAML Browser SSO typically POSTs to the ACS. Can you determine the protocol from HTTP method alone?

**Answer:** Method is a useful clue, but inspect **payload/form/contract**; custom bindings and configs exist. CAS may support other transports depending on version, and SAML has multiple bindings.

**Q9.** An app using `spring-security-cas` wants to accept SAML 2.0 from an IdP. Can it just swap `Cas20ServiceTicketValidator` for an XML parser class?

**Answer:** No. It needs the SAML SP module/provider, `RelyingPartyRegistration`, metadata, signature/condition validation, and the corresponding ACS.

**Q10.** CAS backend validation encounters a TLS hostname mismatch. Should `trustAllCertificates()` be used to make login work?

**Answer:** No. Fix the public CAS endpoint, truststore/TLS cert, and network configuration rather than disabling server certificate validation.

**Q11.** An IdP issues a validly signed Assertion whose `AudienceRestriction` targets SP B, and App A still wants to accept it. Is that allowed?

**Answer:** No. The Assertion is intended for another party; the SP must reject it even though the signature is valid.

**Q12.** A CAS Server acts as a broker supporting SAML 2.0 and the CAS Protocol. A legacy app wants CAS while a new app wants SAML. Must all apps call the same protocol endpoint?

**Answer:** No. One platform can host multiple protocol modules; each app registers its own CAS service or SAML SP, trust, and callback.

**Q13.** After local logout, the user immediately SSOs back into both the CAS app and the SAML app. What is the likely reason?

**Answer:** The CAS TGC/TGT or IdP session still exists; only the app's local `HttpSession` was deleted. Federated logout/session revocation is required if policy demands it.

**Q14.** With CAS `gateway=true` and no session, the broker sends the browser back without an ST. Should the app create an anonymous authenticated principal?

**Answer:** No. There is no validation success; the app stays anonymous/unauthenticated and chooses another login UX per policy.

**Q15.** A CAS app uses a Proxy Ticket to call service B. After migrating to SAML, can the PT be placed into `SAMLRequest` as an artifact?

**Answer:** No. CAS PTs and SAML Artifacts differ in protocol, structure, trust, and lifecycle. Delegation/broker/backend authentication must be redesigned.

**Q16.** When a user's role changes from ADMIN to READ, can you simply replace CAS login with SAML and consider stale permissions solved?

**Answer:** No. Both create a Spring Security session caching authorities at login; the app needs live authorization, refresh/revocation, or session invalidation per requirements.

## 30. Pre-Deployment or Migration Checklist

- [ ] Identified the **exact protocol** the application uses: CAS tickets or SAML 2.0 Web Browser SSO.
- [ ] CAS client has a fixed CAS Server URL, valid HTTPS/TLS trust, canonical service URL, and allow-list.
- [ ] CAS Service Tickets are validated backend-side for the exact service with TTL and one-time semantics.
- [ ] CAS 2/3 endpoints (`/serviceValidate`, `/p3/serviceValidate`) are chosen to match attribute needs.
- [ ] If CAS uses proxy tickets, `pgtUrl` callback, proxy chain policies, and dedicated tests are in place.
- [ ] SAML SP has accurate IdP metadata/entity ID, trusted signing certificates, SSO endpoint, and ACS.
- [ ] `SAMLResponse`/Assertion is verified by Spring/OpenSAML for signature, issuer, audience, recipient, time, subject, and correlation/replay.
- [ ] Never confuse SAML Artifacts with CAS STs, or CAS `renew`/`gateway` with SAML `ForceAuthn`/`IsPassive`.
- [ ] Spring Security uses the matching module and filter: CAS or SAML SP, never sharing one callback.
- [ ] Public URL/forwarded headers/reverse proxies align with CAS `service` or SAML `Destination`/ACS.
- [ ] Account identity mapping uses issuer/tenant/immutable ID, not bare username/email.
- [ ] Authorization checks live permissions when needed; SSO does not auto-sync role changes.
- [ ] Session idle/absolute TTL, CAS TGT/TGC or IdP SSO session, and local logout are clearly separated.
- [ ] Federated logout is tested; never promise all devices/tokens are logged out without a mechanism.
- [ ] Tested callback replay, wrong service, invalid signature, wrong audience, expired assertion, and lost sessions.
- [ ] Logs and telemetry exclude CAS STs, TGCs, `SAMLResponse`s, real `NameID`s, private keys, and session cookies.
- [ ] Multi-node Spring Session/`RequestRepository` supports callbacks and anti-replay.
- [ ] Migration, parallel-run, rollback, and protocol-specific error triage plans exist.

## 31. Core Conclusion

**CAS Protocol**: the browser receives a single-use **Service Ticket** for a service; the application backend **calls the CAS Server to validate the ticket**. **SAML 2.0 Web Browser SSO**: the browser carries a **`SAMLResponse`/Assertion**; the SP **verifies the signature and SAML conditions** against partner metadata and trust. Both can produce a Spring Security `Authentication`/session and a similar SSO experience, yet their **evidence, trust boundaries, APIs, error handling, metadata, lifecycles, and migration paths differ**.

Never implement by “renaming ticket to `SAMLResponse`”; identify the right protocol and let the proper security provider/validator handle it. With brokered federation, each hop must validate the **incoming protocol's inputs** and mint a **new** credential according to the outgoing protocol's contract.
