# Service Binding, Expiration, and Usage Limits of Service Tickets

**Module:** Spring Security – federation  
**Parent topic:** CAS Fundamentals  
**Scope:** Central Authentication Service (CAS) Protocol 2.0/3.0, Service Ticket (ST), Spring Security 6.x, Spring Boot 3.x, Java 17+.

## 1. Summary of Service Ticket Nature

In the **Central Authentication Service (CAS)** protocol, a **Service Ticket (ST)** is an **opaque, random, short-lived login credential bound to exactly one service**. The CAS Server issues an ST after authenticating a user or accepting a valid Single Sign-On (SSO) session. The browser carries the ST to the **service/CAS client** application; the application sends the ST back to the CAS Server for verification before creating an `Authentication` and its own application session.

An ST has **three mandatory limits you must understand**:

1. **Service binding:** The ticket is valid only for the **service identifier** for which the CAS Server issued it; a ticket issued for application A cannot be used to authenticate against application B.
2. **Expiration:** An unverified ticket remains valid only for a very short window. Once expired, validation must fail, even if the user still holds an SSO session at CAS.
3. **One-time validation:** Under the CAS specification, an ST may be attempted for verification **only once**; whether that attempt succeeds or fails, CAS must invalidate the ticket, so any subsequent attempts fail.

**Consequence:** An ST is **not** a token for repeated API calls, not an SP login cookie, and cannot be re-verified every time the user loads a page. The CAS client verifies the ST **once at the callback**, then maintains the **`SecurityContext`/`HttpSession`** and enforces business authorization as usual.

Example:

~~~text
ST-X issued for https://portal.example.org/login/cas
  +-- first validation, exact service, unexpired -> SUCCESS
  +-- second validation, even with exact service -> FAIL

ST-Y issued for https://reports.example.org/login/cas
  +-- used at portal.example.org -> SERVICE MISMATCH
  +-- cannot be taken back to reports to retry same ST after validation attempt

ST-Z never validated, but past expiration
  +-- first validation -> EXPIRED/FAIL
~~~

The second scenario is especially important: **trying the wrong service can ruin the ticket**, rather than being a harmless “check where the ticket belongs” step.

## 2. Components in the CAS Single Sign-On Flow

| Component | Function | Data Held |
| --- | --- | --- |
| **Browser** | Navigates between service and CAS Server | CAS TGC cookie, SP session cookie, ST in callback URL |
| **CAS Server** | Centralized authentication, ticket issuance and validation | TGT/TGC association, ST registry, service registry, ticket policies |
| **Service/CAS Client** | Application needing user login | Fixed Service URL, ticket validator, local session, business permissions |
| **Ticket-Granting Ticket (TGT)** | CAS-side SSO session, allowing CAS to issue multiple STs after login | Lifetime independent of ST |
| **Ticket-Granting Cookie (TGC)** | Browser cookie used to look up TGT state at CAS | Neither an ST nor the service's HttpSession |
| **Service Ticket (ST)** | Single-use proof for a service to verify login | Random, service-bound, short-lived |
| **Local HttpSession** | Maintains `Authentication` at the service itself after ST is validated | `SecurityContext`, local policy/lifetime |

One browser can log in to **portal** and **reports** through CAS using the same TGT; each service receives **a new ST dedicated to its own service**, then maintains **its own HTTP session**.

**TGT lives longer than ST in normal flows.** A TGT can allow CAS to issue additional STs without re-prompting for login credentials; that does not “renew” an already-consumed ST. If an ST fails due to expiration or misuse, the client normally must **restart the CAS login cycle to obtain a new ST**, and cannot revive the old ticket.

## 3. ST Issuance and ST Verification Flow

Diagram of one **SP-initiated CAS login**:

~~~text
Browser                   Service A (Spring)                CAS Server
   |                               |                           |
   | GET /private                  |                           |
   |------------------------------>| no Authentication         |
   |<------------------------------| 302 to CAS /login         |
   |                               | service=A/login/cas       |
   | GET /cas/login?service=A      |-------------------------->|
   |                               |                           | authenticate
   |                               |                           | or reuse TGT
   |<----------------------------------------------------------|
   | 302 Location: A/login/cas?ticket=ST-XYZ                    |
   | GET /login/cas?ticket=...   |                           |
   |------------------------------>| receive ticket            |
   |                               | GET /p3/serviceValidate   |
   |                               | ticket=ST-XYZ&service=A   |
   |                               |-------------------------->|
   |                               |                           | verify:
   |                               |                           | exact service
   |                               |                           | unexpired
   |                               |                           | unused
   |                               |                           | consume ST
   |                               |<--------------------------|
   |                               | cas:authenticationSuccess |
   |                               | create Authentication     |
   |                               | save SP HttpSession       |
   |<------------------------------| redirect to resource      |
   | GET /private + SP cookie      |                           |
   |------------------------------>| use SecurityContext       |
   |<------------------------------| authorized page           |
~~~

**The CAS protocol does not require the browser to know the server-to-server validation outcome.** The browser receives only the redirect/login result and the service's session cookie. Nor is the browser trusted to report “ticket valid” on behalf of the CAS Server.

### 3.1. CAS Login Receives the `service` Parameter

Suppose the approved service callback is:

~~~text
https://portal.example.org/login/cas
~~~

The application sends the browser to:

~~~http
GET /cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas HTTP/1.1
Host: sso.example.org
~~~

**`service`** is the identifier of the **exact callback application**, URL-encoded inside the query parameter. The CAS Server needs a **service registry/allowlist** permitting this URL; never accept arbitrary service URLs to avoid issuing tickets to malicious sites or open redirects.

After CAS authenticates successfully, typical response:

~~~http
HTTP/1.1 302 Found
Location: https://portal.example.org/login/cas?ticket=ST-opaque-example
~~~

**`ST-opaque-example`** is illustrative only; real tickets must be sufficiently random/unpredictable. The CAS protocol specifies STs carry the **`ST-`** prefix, but clients **must not parse structure after the prefix to decide identity or permissions**.

### 3.2. Service Validates via Back-Channel

The service receives the **`ticket`** query parameter at **`/login/cas`**, and then the application server itself calls the CAS validation endpoint:

~~~http
GET /cas/p3/serviceValidate?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&ticket=ST-opaque-example HTTP/1.1
Host: sso.example.org
~~~

Related endpoints:

- **`/validate`:** CAS 1.0 version, simple response format.
- **`/serviceValidate`:** CAS 2.0, XML response.
- **`/p3/serviceValidate`:** CAS 3.0, often able to return attributes alongside principal information.
- **`/proxyValidate` / `/p3/proxyValidate`:** for proxy ticket scenarios, requiring dedicated proxy verification rules.

**Never treat HTTP status = 200 as proof of successful authentication.** CAS typically returns an XML **`cas:authenticationSuccess`** or **`cas:authenticationFailure`** in the body; the application must parse/validate the response per schema and policy. Use a trusted CAS client validator instead of string-matching XML yourself or assuming success.

### 3.3. CAS 2.0/3.0 Response Examples

Success, illustrative XML:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>employee-847</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Failure, illustrative XML:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationFailure code="INVALID_TICKET">
    Service ticket invalid or already used
  </cas:authenticationFailure>
</cas:serviceResponse>
~~~

Errors may use **`INVALID_TICKET`**, **`INVALID_REQUEST`**, or other codes depending on scenario/deployment version. Do not hardcode an assumption that every service mismatch returns the exact same error code. Always inspect **`authenticationFailure`**, handle it safely, and start a new login cycle when appropriate.

## 4. Service Binding: ST Bound to Exact Service Identifier

According to the CAS Protocol Specification, **an ST is valid only for the service identifier provided when issuing the ticket via `/login`**. The `service` in the **`/serviceValidate`** request must match the service used to issue the ticket.

For example, CAS receives:

~~~text
/login?service=https://portal.example.org/login/cas
~~~

CAS issues **`ST-A`** and records that `ST-A` belongs to **`https://portal.example.org/login/cas`**. Thereafter:

| `service` Value at `ST-A` Validation | Conclusion |
| --- | --- |
| https://portal.example.org/login/cas | Exact service; still must pass expiry and one-time check |
| https://reports.example.org/login/cas | Wrong service → reject |
| http://portal.example.org/login/cas | Not the registered HTTPS service → never assume equal |
| https://portal.example.org/login/cas/ | Different path/trailing slash; check canonicalization |
| https://portal.example.org/another/cas | Different callback → reject |
| Client-supplied URL outside service registry | Must never be used as a trust decision source |

**Note on canonicalization:** CAS servers/versions may have their own matching/normalization rules; never claim every difference in slash/port/encoding produces the exact same error code. Safe policy is a **stable, configured, strictly consistent service URL** across `/login`, callback, `/serviceValidate`, and the service registry.

### 4.1. Why Isn't the Service Embedded in the Ticket?

An ST is an **opaque string**. CAS stores the ticket → principal/service/conditions mapping in its server-side ticket registry. The specification advises **against embedding the service identifier inside the ticket itself**. Therefore:

- Do not decode the ST to extract URL, username, roles, or expiration.
- Never design a custom client that only checks an ST prefix or UUID and treats the ticket as valid.
- Even if a ticket is stolen, sending it to CAS validation with the wrong service prevents it from acting as a valid credential for another service.
- Still, **service binding does not stop an attacker racing to redeem a ticket at the right service** if leaked before the legitimate client consumes it; hence HTTPS, redirect control, and ticket-leakage defenses remain essential.

### 4.2. Service URLs with Query Strings

Some services have a fixed query in the service identifier or route under a context path. For instance, one deployment uses:

~~~text
https://portal.example.org/app/login/cas
~~~

instead of:

~~~text
https://portal.example.org/login/cas
~~~

That must be reflected **consistently** in client configuration and the service registry. If a service has a fixed query, all **`&`**, **`?`**, and **`=`** characters in the nested URL must be properly URL-encoded when sent to CAS. Avoid taking the entire current URL with **`?ticket=ST-...`** appended as the validation `service`, because when CAS issued the ticket the original service **did not contain `ticket`**.

**Never construct `service` from browser-controlled `Host`, `X-Forwarded-Host`, or `X-Forwarded-Proto` values**. When the app sits behind a reverse proxy, trust headers only from configured/trusted proxies; best of all, use a server-side public canonical service URL whenever the contract allows.

## 5. Single-Use ST: Even Failed Validation Consumes the Ticket

The CAS specification mandates: **A Service Ticket is valid for only one validation attempt; whether validation succeeds or not, CAS must invalidate the ticket**.

This is the point learners most often misunderstand.

~~~text
CAS issues ST-001 for service A
       |
       +--- attempt 1: validate ST-001 with service B
       |                  |
       |                  +--> FAIL: wrong service
       |                  +--> ST-001 invalidated/consumed
       |
       +--- attempt 2: validate ST-001 with service A
                          |
                          +--> FAIL: used/unknown ticket
~~~

If the CAS client retries validation with the same ticket after a **network timeout**, there is a hazard: the CAS server may already have consumed the ticket and returned a response that was lost in transit. Retries cannot be assumed idempotent and usually fail.

**Proper handling:** Distinguish connection/timeout errors from `authenticationFailure` results, with an appropriate retry policy that **does not reuse STs**. Whenever unsure whether a ticket was already used, initiate a **new CAS login flow to obtain a fresh ST** instead of resending the old ST.

### 5.1. Replay Attacks and Race Conditions

An attacker may try submitting the same ST twice nearly simultaneously. If the ticket registry lets both requests “see it unused” and both succeed, the system violates single-use and increases replay risk.

Server-side safeguards required:

1. Generate STs with strong randomness so they are unpredictable.
2. Bind each ST to a service and expiration.
3. On validation, **fetch/consume state atomically** in the shared ticket registry.
4. Regardless of outcome, never allow the ticket a second successful validation.
5. Across multiple CAS nodes, the registry/cache/DB must coordinate consistently; never use a per-node local map if traffic can shift between nodes.

A service application cannot turn a used ticket back into “unused” by clearing cookies. **One-time enforcement lives on the CAS Server**; the client is responsible for not retrying or forwarding tickets against policy.

## 6. Service Ticket Expiration: Very Short, Independent of TGT and App Sessions

An ST must expire quickly to shrink the replay/leakage window. The CAS Protocol Specification **recommends** that unvalidated ST lifetimes be **no longer than five minutes**; this is a **recommended upper bound**, not a fixed TTL across every CAS deployment.

In **documented Apereo CAS Server 8.0.x** configuration, example properties are:

~~~properties
# CAS SERVER configuration example, NOT CAS CLIENT configuration:
cas.ticket.st.number-of-uses=1
cas.ticket.st.time-to-kill-in-seconds=PT10S
~~~

- **`number-of-uses=1`:** limits how many validation attempts may use an ST, matching the single-use principle.
- **`time-to-kill-in-seconds=PT10S`:** expresses a 10-second duration as shown in documented Apereo CAS 8.0.x default configuration.
- **`PT10S`:** duration in **`java.time.Duration`** syntax, not a UTC timestamp.
- Property names and defaults may vary by **CAS Server version**, per-service expiration policies, or overrides; **verify actual runtime behavior** rather than assuming every CAS uses 10 seconds.

If policy requires 20 seconds for an application due to real-world latency, CAS admins must assess URL exposure and replay risk before changing it. **Never increase it to hours to mask slow callbacks**.

### 6.1. Illustrative Timeline

~~~text
10:00:00  CAS issues ST-A for service A
10:00:02  service A validates first time, exact service -> SUCCESS
10:00:03  validate ST-A again -> FAIL (single-use)

10:01:00  CAS issues ST-B
10:01:10  service A validates ST-B with 10s TTL -> EXPIRED/FAIL
           (assuming exclusive boundary under this model)
~~~

Do not treat this simulated timestamp as an exact assertion about a real CAS Server's scheduler or clock skew; some policies use idle time or different expiration modes.

### 6.2. Comparison with TGT/TGC

| Mechanism | Purpose | Lifetime / Limits |
| --- | --- | --- |
| **Service Ticket (ST)** | Proves CAS login for one specific service | Short-lived, **service-bound, one validation attempt** |
| **Ticket-Granting Ticket (TGT)** | Maintains CAS-side SSO and issues additional STs | Separate policy, usually longer than ST, with idle/hard timeouts |
| **Ticket-Granting Cookie (TGC)** | Browser reference to CAS/TGT session | CAS cookie, not an ST |
| **SP HttpSession/SecurityContext** | Maintains logged-in state at the app after ST verification | Local idle/absolute timeout; does not expire automatically when ST expires |
| **Proxy Ticket (PT)** | Accesses a backend service in an approved proxy flow | Service-bound, single-use, but must be validated via proper proxy endpoint/policy |
| **Proxy-Granting Ticket (PGT)** | Allows a proxy service to request PTs | Distinct from ST; has its own lifecycle, permissions, and proxy controls |

A user can have a TGT valid for an hour, an ST that expired after seconds, and yet remain logged in at the SP via a valid `HttpSession`. This is normal when local policy permits it.

## 7. HTTP Example: Client Must Use the Exact Service During Validation

Assume configuration:

~~~text
CAS base URL = https://sso.example.org/cas
Service URL  = https://portal.example.org/login/cas
Validation   = https://sso.example.org/cas/p3/serviceValidate
~~~

Step one: the service redirects the browser to CAS with the encoded `service`:

~~~http
HTTP/1.1 302 Found
Location: https://sso.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
~~~

Step two: the browser returns:

~~~http
GET /login/cas?ticket=ST-example-one-time HTTP/1.1
Host: portal.example.org
~~~

Step three: portal's **server-to-server** validator:

~~~http
GET /cas/p3/serviceValidate?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&ticket=ST-example-one-time HTTP/1.1
Host: sso.example.org
~~~

Step four: CAS returns `cas:authenticationSuccess` or `cas:authenticationFailure`. Only after valid success does the service create a local `Authentication` and session.

**Never perform step three via browser JavaScript**, to avoid exposing trust/token design and mistakenly assuming client responses can grant access. A browser-side fetch to CAS also runs into CORS/cookie/header issues and does not replace a trusted server-side ticket validator.

### 7.1. Never Use `curl` to “Check If an Active Login Ticket Is Still Alive”

Because an ST is single-use, if a developer copies a ticket from the browser and runs `curl` to validate it first, CAS consumes it; when the Spring filter validates the ticket at the callback, it will fail. To test the endpoint directly, **mint a separate fresh ST for that test**, never using an ST that an app/browser flow needs.

Command structure example (ticket is a placeholder only—**do not run verbatim against real CAS**):

~~~bash
curl --get   --data-urlencode "service=https://portal.example.org/login/cas"   --data-urlencode "ticket=ST-TEST-FROM-ISOLATED-FLOW"   "https://sso.example.org/cas/p3/serviceValidate"
~~~

Use only in a **test environment with a real CAS** and a dedicated ST, protecting stdout/history/traces. The command does not mint tickets and guarantees no success output when the placeholder ticket does not exist.

## 8. Spring Security CAS: Responsible Components

Spring Security provides the **`spring-security-cas`** module for the **CAS Protocol**, distinct from **`spring-security-saml2-service-provider`** (for SAML2).

| Component | Role |
| --- | --- |
| **CasAuthenticationEntryPoint** | Sends unauthenticated browser to CAS `/login` with the `service` parameter |
| **ServiceProperties** | Holds the canonical **`service` URL**, `sendRenew`, and ticket/service parameter names |
| **CasAuthenticationFilter** | Monitors the callback, defaulting to **`/login/cas`**, and extracts **`ticket`** |
| **CasServiceTicketAuthenticationToken** | Temporary authentication request carrying the opaque ticket |
| **AuthenticationManager/ProviderManager** | Routes the token to a CAS-capable provider |
| **CasAuthenticationProvider** | Invokes **`TicketValidator`**, builds `CasAuthenticationToken` after CAS verifies successfully |
| **Cas20ServiceTicketValidator** | CAS client library validating ST via CAS Server `/serviceValidate` over back-channel |
| **UserDetailsService** | Loads local authorities/account status after CAS verifies the subject |
| **SecurityContextRepository/HttpSession** | Stores application `Authentication` for subsequent requests |
| **CAS service registry** | Determines which service URLs may receive STs; managed by the CAS Server |

**Core point:** **`ServiceProperties.getService()`** must represent the exact callback URL handled by the filter and **must match the service identifier used when the CAS Server issued the ticket**. With the default **`/login/cas`** callback, never configure the service URL pointing only to root **`/`** or to a different route.

**Never write an `Authentication` with `authenticated=true` merely upon seeing a `ticket` query param with prefix `ST-`**. The ticket is only an unverified credential; `CasAuthenticationProvider`/`TicketValidator` must complete validation.

## 9. Spring Boot 3.x, Java 17+ Configuration Example for CAS Service Tickets

This sample illustrates **Java DSL** instead of CAS docs' legacy XML configurations. It configures the **CAS Protocol**, not `saml2Login()` and not `OAuth2Login()`.

Prerequisites to run end-to-end: a **real CAS Server over HTTPS**, service URL properly registered in the CAS service registry, valid truststore, JDK 17+, and a Spring Boot 3.x project with Spring Security 6.x. The **`example.org`** domains are illustrative only; do not assume the code itself provides a CAS Server.

### 9.1. Maven Dependencies

In the dependencies section of `pom.xml` with a compatible Spring Boot parent/BOM:

~~~xml
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-cas</artifactId>
  </dependency>
</dependencies>
~~~

**`spring-security-cas`** integrates CAS client validation (including classes in **`org.apereo.cas.client.validation`** in compatible versions). Use the version from your Spring Security/Boot BOM; check the dependency tree and add **`cas-client-core`** per version guidance if the transitive dependency is absent. Avoid confusing it with **`spring-security-saml2-service-provider`**.

### 9.2. `application.yml`

**`src/main/resources/application.yml`**

~~~yaml
app:
  cas:
    server-base-url: https://sso.example.org/cas
    login-url: https://sso.example.org/cas/login
    service-url: https://portal.example.org/login/cas

server:
  servlet:
    session:
      timeout: 30m
~~~

**Service URL** is a fixed public HTTPS callback. It must be added to the CAS service registry. When running on localhost, the service URL above will not route back to localhost: you need a test CAS server, a test HTTPS domain, and matching updates on both the CAS Server and the service.

**A 30-minute SP session is completely different from a 10-second ST TTL.** The timeout setting here controls only the Servlet session, not the ST lifetime.

### 9.4. `SecurityFilterChain` and CAS Beans

**`src/main/java/com/example/cas/CasSecurityConfig.java`**

~~~java
package com.example.cas;

import org.apereo.cas.client.validation.Cas20ServiceTicketValidator;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.authentication.CasAuthenticationProvider;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;
import org.springframework.security.cas.web.CasAuthenticationFilter;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;
import org.springframework.security.web.context.HttpSessionSecurityContextRepository;
import org.springframework.security.web.context.SecurityContextRepository;
import org.springframework.security.web.authentication.session.ChangeSessionIdAuthenticationStrategy;

@Configuration
public class CasSecurityConfig {

    @Bean
    ServiceProperties serviceProperties(
            @Value("${app.cas.service-url}") String serviceUrl) {
        ServiceProperties props = new ServiceProperties();
        props.setService(serviceUrl);
        props.setSendRenew(false);
        return props;
    }

    @Bean
    CasAuthenticationEntryPoint casEntryPoint(
            ServiceProperties serviceProperties,
            @Value("${app.cas.login-url}") String loginUrl) {
        CasAuthenticationEntryPoint point =
            new CasAuthenticationEntryPoint();
        point.setLoginUrl(loginUrl);
        point.setServiceProperties(serviceProperties);
        return point;
    }

    @Bean
    CasAuthenticationProvider casProvider(
            ServiceProperties serviceProperties,
            @Value("${app.cas.server-base-url}") String serverBaseUrl) {

        CasAuthenticationProvider provider =
            new CasAuthenticationProvider();
        provider.setServiceProperties(serviceProperties);
        provider.setTicketValidator(
            new Cas20ServiceTicketValidator(serverBaseUrl));

        // Grant test permissions only to demo user.
        // Production: replace with DB/LDAP UserDetailsService lookup
        // and allow only enabled accounts per internal policy.
        provider.setUserDetailsService(name -> {
            if (!"demo".equals(name)) {
                throw new org.springframework.security.core.userdetails
                    .UsernameNotFoundException("Local user not enabled");
            }
            return User.withUsername(name)
                .password("{noop}unused-by-cas")
                .roles("USER")
                .build();
        });
        provider.setKey("portal-cas-provider-v1");
        return provider;
    }

    @Bean
    SecurityFilterChain webSecurity(
            HttpSecurity http,
            ServiceProperties serviceProperties,
            CasAuthenticationEntryPoint entryPoint,
            CasAuthenticationProvider casProvider)
            throws Exception {

        SecurityContextRepository contextRepository =
            new HttpSessionSecurityContextRepository();

        CasAuthenticationFilter casFilter =
            new CasAuthenticationFilter();
        casFilter.setFilterProcessesUrl("/login/cas");
        casFilter.setServiceProperties(serviceProperties);
        casFilter.setAuthenticationManager(
            new ProviderManager(casProvider));
        casFilter.setSecurityContextRepository(contextRepository);
        casFilter.setSessionAuthenticationStrategy(
            new ChangeSessionIdAuthenticationStrategy());

        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error").permitAll()
                .anyRequest().authenticated())
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint(entryPoint))
            .securityContext(ctx -> ctx
                .securityContextRepository(contextRepository))
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED))
            .addFilterAt(
                casFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}
~~~

**Explanation:**

- **`ServiceProperties`** keeps the service URL consistent. **`CasAuthenticationEntryPoint`** includes that value in the `service` parameter when sending the browser to CAS login.
- **`CasAuthenticationFilter`** handles **`/login/cas`**, reads the ticket, and uses `ProviderManager`/`CasAuthenticationProvider` to validate it.
- **`Cas20ServiceTicketValidator`** sends requests to the CAS Server over HTTPS; the application never derives permissions from the ticket text itself.
- **`HttpSessionSecurityContextRepository`** is configured on both the filter and security chain so Spring Security 6 persists/restores `Authentication` after the callback.
- **`ChangeSessionIdAuthenticationStrategy`** provides session fixation protection for session-based login flows.
- **Demo `UserDetailsService`** grants `ROLE_USER` only to subject **`demo`**; other usernames are rejected at local lookup even if CAS verifies them. The password string is merely a `UserDetails` field, **not used for CAS authentication**. Production must use a local account registry/DB and role policy rather than auto-creating users with elevated privileges.
- Use **`addFilterAt`** inside `SecurityFilterChain`; **never register `CasAuthenticationFilter` separately as a servlet filter outside the Spring Security chain**, to avoid double execution unintentionally consuming the ST.
- **This is a stateful CAS browser pattern**. Never add custom logic to re-validate STs on every API request or call the same ST twice.
- If the project also uses form login/Bearer/OIDC, design filter chains and entry points with explicit matchers; avoid custom filters intercepting the callback or consuming the ticket before the CAS filter.

**Deployment prerequisites:** Spring Security 6.5 supports the CAS classes above; if using another version, verify APIs/packages of your actual version before copying. With a real CAS Server, configure TLS trust, service registry, network timeouts, error handling, local roles, and session/logout policies.

### 9.5. Controller Observed After ST Verification

**`src/main/java/com/example/cas/CasController.java`**

~~~java
package com.example.cas;

import java.security.Principal;
import java.util.Map;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class CasController {

    @GetMapping("/")
    public String home() {
        return "CAS service ticket demo";
    }

    @GetMapping("/me")
    public Map<String, String> currentUser(Principal principal) {
        return Map.of(
            "principal", principal.getName(),
            "authentication", "session");
    }
}
~~~

**`/me`** in the example is protected by `anyRequest().authenticated()`. When the browser is unauthenticated, CAS login begins; after ST validation, the browser uses the SP session cookie and **does not need to pass an ST on every request**.

## 10. Runnable Java 17: Simulating Service Binding, TTL, and Single-Use

The following program **runs standalone on JDK 17**, without Spring. It simulates three key CAS conditions in memory:

- Each ticket carries a **service identifier** bound at issuance.
- A ticket remains valid only **before `issuedAt + TTL`**.
- The first validation attempt **atomically consumes** the ticket **before returning a result**; even a wrong service or expired ticket cannot be reused.

This is a learning model, **not a CAS Server**. The code does not generate random STs, authenticate accounts, handle HTTPS, service registries, proxy tickets, TLS, distributed ticket registries, or browser-spoofing defenses. Production must use a real CAS Server and client validator.

**File: `ServiceTicketPolicyDemo.java`**

~~~java
import java.time.Duration;
import java.time.Instant;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public final class ServiceTicketPolicyDemo {

    enum Result {
        VALID, SERVICE_MISMATCH, EXPIRED, USED_OR_UNKNOWN
    }

    record Ticket(String service, Instant issuedAt) { }

    private final Map<String, Ticket> tickets =
        new ConcurrentHashMap<>();
    private final Duration lifetime = Duration.ofSeconds(10);

    void issue(String opaqueValue, String service, Instant issuedAt) {
        tickets.put(opaqueValue, new Ticket(service, issuedAt));
    }

    Result validate(String opaqueValue, String service, Instant now) {
        if (opaqueValue == null || service == null) {
            return Result.USED_OR_UNKNOWN;
        }

        // remove is atomic in ConcurrentHashMap.
        // A real attempt consumes the ticket, even on wrong service.
        Ticket ticket = tickets.remove(opaqueValue);
        if (ticket == null) {
            return Result.USED_OR_UNKNOWN;
        }
        if (!ticket.service().equals(service)) {
            return Result.SERVICE_MISMATCH;
        }
        if (!now.isBefore(ticket.issuedAt().plus(lifetime))) {
            return Result.EXPIRED;
        }
        return Result.VALID;
    }

    public static void main(String[] args) {
        ServiceTicketPolicyDemo cas = new ServiceTicketPolicyDemo();
        Instant t0 = Instant.parse("2026-11-07T00:00:00Z");
        String portal = "https://portal.example.org/login/cas";
        String reports = "https://reports.example.org/login/cas";

        cas.issue("ST-A", portal, t0);
        System.out.println("wrongService=" + cas.validate(
            "ST-A", reports, t0.plusSeconds(1)));
        System.out.println("afterWrongService=" + cas.validate(
            "ST-A", portal, t0.plusSeconds(2)));

        cas.issue("ST-B", portal, t0);
        System.out.println("expiredAtLimit=" + cas.validate(
            "ST-B", portal, t0.plusSeconds(10)));
        System.out.println("retryExpired=" + cas.validate(
            "ST-B", portal, t0.plusSeconds(11)));

        cas.issue("ST-C", portal, t0);
        System.out.println("firstValid=" + cas.validate(
            "ST-C", portal, t0.plusSeconds(2)));
        System.out.println("replay=" + cas.validate(
            "ST-C", portal, t0.plusSeconds(3)));

        cas.issue("ST-D", reports, t0);
        System.out.println("otherServiceOwnTicket=" + cas.validate(
            "ST-D", reports, t0.plusSeconds(4)));
    }
}
~~~

Compile/run:

~~~bash
javac ServiceTicketPolicyDemo.java
java ServiceTicketPolicyDemo
~~~

**Exact stdout:**

~~~text
wrongService=SERVICE_MISMATCH
afterWrongService=USED_OR_UNKNOWN
expiredAtLimit=EXPIRED
retryExpired=USED_OR_UNKNOWN
firstValid=VALID
replay=USED_OR_UNKNOWN
otherServiceOwnTicket=VALID
~~~

**Explaining the output:**

1. `ST-A` was issued for portal but validated with reports → **`SERVICE_MISMATCH`**; because it was consumed, retrying portal → **`USED_OR_UNKNOWN`**.
2. `ST-B` validated right at **`issuedAt+10s`**, which the model treats as an exclusive TTL boundary → **`EXPIRED`**. The next attempt fails as already used.
3. `ST-C` was validated by portal within its lifetime → **`VALID`**; replaying the same ticket → **`USED_OR_UNKNOWN`**.
4. `ST-D` was issued specifically for reports and used at reports → **`VALID`**.

The code uses **`ConcurrentHashMap.remove(key)`** to guarantee each key returns an object to at most one thread. For a multi-node ticket server, an in-JVM map is **insufficient**; you need a distributed ticket registry/cache with proper atomic consumption and expiration.

**Never use simulation outcomes to predict exact real CAS error codes**. A real CAS Server may return XML with different error codes depending on validation failure; clients must rely on the protocol and standard exceptions.

## 11. When ST Expires, ST Is Already Used, and TGT Is Still Alive

Three cases that can look alike as “CAS login fail” but have different causes:

### 11.1. ST Expires Before the Service Validates It

For instance, the browser leaves the CAS login page and loads the callback slowly, a reverse proxy stalls, a service node is overloaded, or the network hiccups. The ticket was never validated and exceeded its TTL.

**Remediation:** restart CAS login to obtain a new ST, reduce latency, and verify reasonable TTL policies. Never extend ST TTL indefinitely or skip server-side validation.

### 11.2. ST Was Already Consumed

Possible causes:

- Browser refresh or back/forward to an old URL containing **`?ticket=ST-...`**.
- Filter or middleware attempting to validate the ST twice.
- Admin using `curl` to validate before the app handles the callback.
- Two parallel requests hitting nodes carrying the same ticket.
- A validation attempt hit a network timeout after CAS already consumed it.
- Custom client code processing the callback across multiple filter chains.

**Remediation:** identify the caller performing the **first validation**, never retry the same ticket; after successful login, redirect the browser to a URL **without the ticket** so refreshes hit the SP session rather than the ST.

### 11.3. TGT Is Still Valid Though ST Failed

CAS can issue a new ST when the browser returns to `/login` thanks to the **Ticket-Granting Cookie** still pointing to an active TGT. The user may experience a quick redirect cycle without re-entering a password. That is **SSO working normally**, not the old ST being reused.

If policy requires the user to actually re-authenticate, CAS offers the **`renew`** parameter; in Spring Security **`ServiceProperties.sendRenew`** can require **`renew=true`** at login and validation. Verify that the CAS Server enforces the policy and auth freshness conditions; never confuse `renew` with automatic MFA.

## 12. Real-World Service URL Mismatch Cases

### 12.1. Reverse Proxy: External HTTPS, Internal HTTP

Environment:

~~~text
Browser -> https://portal.example.org/login/cas
Proxy   -> http://portal-app:8080/login/cas
~~~

If CAS issued the ticket for the public HTTPS URL while the client sends **`http://portal-app:8080/login/cas`** to CAS validation, it altered the service identifier. Never fix this by letting the CAS registry trust arbitrary internal **`http://`** URLs or disabling binding.

**Fix:** configure a fixed, consistent service URL of **`https://portal.example.org/login/cas`**; protect forwarded headers, trust only proxies inside the trust boundary, and check the CAS Server registered service.

### 12.2. Trailing Slash or Context Path

The app runs under **`/portal`**, but `ServiceProperties` configures **`https://portal.example.org/login/cas`** instead of **`https://portal.example.org/portal/login/cas`**. CAS issues the ticket for one URL while the callback listener sits at another.

Verify **`context-path`, `filterProcessesUrl`, service URL, proxy rewrites**, and the CAS service registration. Test with real redirects rather than guessing solely from `application.yml`.

### 12.3. Query Parameters and the `ticket` Parameter

Some CAS clients have a dynamic service URL containing query parameters. When CAS redirects back, the **`ticket`** parameter is appended. The client must never send the entire callback URL including `ticket` back as the `service` value unless a protocol-specific contract explicitly requires that structure.

**Best approach for learners:** start with a **fixed, query-free callback service URL** such as **`/login/cas`**; after login completes, use `SavedRequest` or controlled state to return to the original resource.

### 12.4. Wrong CAS Server / Domain / Tenant

A CAS ticket issued by **`sso.company.example`** must never be sent to a partner's CAS server for validation. In multi-CAS/multi-tenant deployments, choose the server and service registry from **trusted configuration**, never reading the issuer/base URL from browser query params.

A ticket sharing the same `ST-` prefix does not reveal which CAS server issued it; the service must validate against the **exact trusted CAS server** based on the initiated flow.

## 13. ST in the URL: Risks and Mitigations

CAS browser redirects typically carry the ST in a **query parameter**, so the ticket may appear in:

- proxy/application access logs;
- browser history;
- analytics/monitoring if full URLs are recorded;
- `Referer` headers when the callback page loads third-party resources;
- bug reports/screenshots and tickets pasted into chat;
- tracing tools storing raw URLs/queries.

**Being short-lived/single-use does not make ticket exposure harmless.** In the window before the first validation, anyone holding the ST and able to reach the matching service can race to redeem it before the client.

Recommendations:

1. **HTTPS for browser→service and service→CAS**; verify CA/truststore, hostname verification, and timeouts.
2. After successful CAS validation, **redirect the browser to a URL without the ticket**; never leave the ticket in SPA routes or downstream referrers.
3. Restrict caching: callback responses must not be shared-cached; enforce appropriate **`Cache-Control`/`Referrer-Policy`**.
4. Disable/sanitize logging of the **`ticket`** query string across reverse proxies, APMs, exception trackers, access logs, and analytics.
5. Never append the ticket to cross-domain redirect URLs; the CAS service registry must enforce an allowlist.
6. Never use the ticket as a business account key, API key, session token, or cookie.
7. Maintain **one-time atomic validation** and short TTLs on the CAS Server.
8. Never forward the ticket to another backend and rely on service binding instead of validation.
9. Monitor mismatches/replays while logging only **controlled hashes/correlation IDs**, never storing raw STs.
10. Constrain local `Authentication`/authorization privileges and enforce account disablement/revocation independently of STs.

## 14. Service Ticket vs. Proxy Ticket, TGT, and Bearer Access Tokens

| Credential | Issued By | Intended For | Reusable? |
| --- | --- | --- | --- |
| **CAS ST** | CAS Server | One specific service | **One validation attempt**, short lifetime |
| **CAS PT** | CAS Server via proxy flow | A target service across a verified proxy chain | Typically **one validation attempt** with proxy rules |
| **CAS PGT** | CAS Server issued to an eligible proxy service | Requesting multiple PTs later | Can request multiple PTs; lifecycle differs from ST |
| **CAS TGT/TGC** | CAS Server/browser session | Maintaining CAS SSO and issuing ST/PT per policy | Many transactions within its own lifetime |
| **OAuth2 access token** | Authorization Server | API/resource scopes and audiences | Completely different rules; usually multi-request bearer token until expiration |
| **SP HttpSession cookie** | Service/Servlet | Logged-in state at the application | Multiple requests, per session policy |

**Never use an ST in place of an OAuth2 access token to call APIs.** CAS uses STs as proof to establish a login session via validation. If backend-to-backend proxy authentication is required, design a **CAS proxy flow** with PGT/PT or use an architecturally appropriate token mechanism rather than reusing STs.

**An ST is not a SAML Assertion.** The CAS Protocol has its own endpoints/responses; an Apereo CAS Server may also support SAML/OIDC as additional protocols, but CAS Service Tickets are not replaced by XML `SAMLResponse` merely because the same CAS Server product provides them.

## 15. Mandatory Test Cases

### 15.1. Ticket Verification Matrix

Assume a test CAS server issues STs for **`https://portal.example.org/login/cas`**, configured with a 10-second TTL and `one-use=1`.

| Case | First Validation | Expectation | Second Attempt? |
| --- | --- | --- | --- |
| Fresh ticket, exact service, within TTL | portal, +2 seconds | **SUCCESS** | FAIL because already used |
| Fresh ticket, wrong service | reports, +2 seconds | **FAIL service mismatch** | FAIL even when retried with portal |
| Fresh ticket, exact service, past TTL | portal, +11 seconds | **FAIL expired** | FAIL |
| Fresh ticket, exact service at +10s boundary | portal, +10 seconds | Per actual expiration/boundary policy; do not allow past expiry | Must not be reused |
| ST absent from ticket registry | portal | **FAIL invalid/unknown** | FAIL |
| Already successfully validated ticket | portal second time | **FAIL replay** | Must not create a new login |
| CAS `/serviceValidate` times out after receiving ST | Unclear if consumed | Do not assume same ST can be retried | Start a new login per flow |
| Ticket belongs to portal, validated with `http` instead of `https` | `http://portal...` | **Must not count as public HTTPS service** | Do not relax policy |
| Ticket belongs to portal with `/app` context | Missing `/app` in validation service | **FAIL service mismatch or config error** | Use fresh ST after fixing |
| Fresh ticket, exact service, CAS returns failure XML | `authenticationFailure` body | **Do not create Authentication** | Do not reuse |
| CAS user logged in but local account disabled | CAS ST valid | **Do not grant business access** | Local policy still denies |
| Service URL is an open redirect | CAS registry | **Block unapproved service** | Do not issue ticket to external URL |
| Fresh ticket, exact service, two parallel requests | CAS registry | At most **one** validation succeeds | Remaining request fails |
| Partner service ST sent to company app | Wrong service/issuer config | **Must not grant company session** | Do not transfer trust |

**To properly test service mismatch**, obtain a real ST for service A from the test CAS server, then send a validation request for service B with that ST. Never use a previously validated ticket or arbitrary XML; that only tests `used/unknown` rather than verifying service binding.

### 15.2. Spring Security / Browser Tests

1. Open a private page unauthenticated → observe redirect with the **exact canonical `service` URL**.
2. Complete CAS login → callback **`/login/cas?ticket=ST-...`** runs the filter once.
3. Spring `CasAuthenticationProvider` calls CAS's exact **`/serviceValidate`** with the service URL excluding the ticket.
4. CAS returns success → local `UserDetailsService` is invoked, `SecurityContext` is stored in `HttpSession`.
5. Reload the page after stripping `ticket` from the URL → remains authenticated via session cookie, no extra ST validation.
6. Copy the ticket to another browser after consumption → cannot establish a new session.
7. Stop the CAS Server after user login: local sessions may continue working per policy; new logins must fail safely.
8. Alter public host/port/path via proxy → validation fails service URL check; fix config properly rather than loosening registry bounds.
9. Network timeout during validation → never unconditionally retry ST; check failure handler and redirect loops.
10. Clear/delete SP cookie and revisit `/private` while CAS TGT remains → can obtain a new ST without re-entering password.
11. Send a ticket to an endpoint other than the callback → not mistakenly processed by the filter or turned into an identity.
12. Valid CAS ticket but invalid local role/tenant → HTTP 403/deny per business policy.
13. Audit access logs/APM/browser history to ensure no raw ST leaks after login.
14. With multiple CAS Server nodes, verify consistent ticket registry and atomic consumption under load balancing.

## 16. Common Troubleshooting

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| **`INVALID_TICKET`** right at callback | Expired ticket, already validated, client double-call, CAS registry miss | Check issuance/validation timestamps, validate once, inspect cluster and ticket-redacted logs |
| **Ticket valid at CAS but app login fails** | Local `UserDetailsService` disabled/missing account; provider config | Separate CAS validation success from local account status; fail closed |
| **Service mismatch** | Differing HTTP/HTTPS, host, port, context path, slash, or query | Compare canonical service URL across login/validation/registry; inspect proxy |
| **HTTP 200 from validate yet user stays anonymous** | Response contains `authenticationFailure`, client checked only status | Parse CAS response properly; inspect auth success/failure |
| **Browser refresh on callback fails** | ST already consumed; refresh resends old ticket | Redirect to a clean URL after login; never revalidate |
| **Login loop** | Wrong callback/filter, lost session, inconsistent CAS URL/service | Inspect `SecurityFilterChain`, cookies, session repository, allowed URLs |
| **User forced to log in again despite live CAS TGT** | Callback ticket error or local session not persisted | Check ST validation and `SecurityContextRepository` |
| **CAS reports unregistered service** | Service registry lacks URL or matcher is too strict | Register exact public HTTPS service URL per policy |
| **CAS issues ST but proxy delays until expiration** | Short TTL, load balancer/network delay | Reduce latency, tune TTL per risk policy; never extend indefinitely |
| **HTTPS validation fails** | Invalid certificate/hostname/truststore | Configure TLS properly; never disable certificate validation |
| **Both CAS nodes accept the ST** | Non-shared/non-atomic ticket registry | Fix ticket registry; audit cluster/invalidation |
| **Multiple filters consume the same ST** | CAS filter registered outside Spring chain or duplicated | Install only one callback filter; check filter ordering |
| **Used ST still accepted by app cache** | Custom cache violates single-use policy | Never cache ST validation to permit replay; store only SP session `Authentication` |
| **CAS Server SSO logs out yet SP still allows access** | SP `HttpSession` is independent; no logout/revocation integration | Design CAS Single Logout / local session policy separately |
| **`renew=true` rejected** | ST issued from old SSO TGT instead of direct credentials | Verify CAS login `renew` and validator `renew` policy |
| **Inconsistent service URL in multi-tenant setup** | Using client request host arbitrarily as issuer/service | Server-side per-tenant allowlist, canonical URLs; never blindly trust `Host` header |

### Useful Diagnostic Order

~~~text
1. Are both CAS Server and service running valid HTTPS?
2. Does CAS service registry allow the exact public URL?
3. Does /login receive the properly URL-encoded service?
4. Does CAS issue a fresh ST and does browser reach exact /login/cas?
5. Does CasAuthenticationFilter run only once?
6. Does TicketValidator send the exact service URL and CAS Server?
7. Is the ST unexpired and never previously validated?
8. Does CAS XML report authenticationSuccess or authenticationFailure?
9. Does local UserDetailsService accept the user?
10. Does SecurityContextRepository persist the application session?
11. Does resource-level authorization permit the operation?
~~~

In dev, you can enable Spring Security logging at an appropriate level, but always **mask the `ticket` query** in access logs/APM; never print raw STs to debug files or public error messages.

## 17. Self-Check Exercises

**Q1:** An ST was issued for portal, but service B accidentally validated it first; will portal's subsequent validation of that ST succeed?  
**Answer:** No. CAS must invalidate the ST after **one validation attempt**, even if the first attempt fails.

**Q2:** A 10-second ST TTL expired, but the TGT at CAS still has 2 hours left. Must the user re-enter their password to get a new ST?  
**Answer:** Not necessarily. The browser may still have a valid CAS TGC/TGT, so CAS issues a new ST via a quick login round-trip. The old ST does not come back to life.

**Q3:** A service receives HTTP 200 on `/serviceValidate`—can it immediately set `authenticated=true`?  
**Answer:** No. The CAS response may contain **`cas:authenticationFailure`**; the validator must verify protocol content and local account/role policy.

**Q4:** Should the same ticket be retried after a CAS validation timeout?  
**Answer:** Never retry by default. CAS may already have consumed the ST; start a fresh CAS login to get a new ST and diagnose the network.

**Q5:** Why does `serviceProperties.service` point to **`https://portal.example.org/login/cas`**, not **`https://portal.example.org/`**?  
**Answer:** Because `/login/cas` is the callback handled by `CasAuthenticationFilter`, and CAS binds the ST to that service identifier. Omitting the callback path causes mismatches.

**Q6:** If the user remains authenticated after 30 minutes even though the ST expired in the first minute, is CAS broken?  
**Answer:** No. The ST is verified once; afterward the application uses **`HttpSession`/`SecurityContext`** under its local session policy.

**Q7:** Can an ST be used repeatedly to call backend APIs like an OAuth2 Bearer token?  
**Answer:** No. An ST is a single-use CAS ticket for service login; API delegation requires another mechanism such as CAS PT/PGT or appropriate tokens.

**Q8:** Why not open the service registry to all of `https://*` to fix service mismatches?  
**Answer:** Because tickets could then be redirected/issued to unapproved applications; the service registry is part of the trust boundary.

## 18. Production Security Checklist

- [ ] **`service` URL** is fixed, public HTTPS, and allowlisted in the CAS Server registry.
- [ ] The `service` value used at CAS **`/login`** and **`/serviceValidate`** is consistent and excludes generated `ticket` parameters.
- [ ] CAS Server enforces ST binding **to only the one service** it was issued for, never validating across other services.
- [ ] ST is **single-use** even when validation fails, with atomic consumption across the cluster.
- [ ] ST TTL is short and configured per server version/risk; never treat the CAS Protocol's 5-minute recommendation as a fixed default.
- [ ] TGT/TGC and SP `HttpSession` have independent lifecycles; never use an ST as a session cookie or access token.
- [ ] CAS Server and service validation use HTTPS with real TLS/truststores, never disabling certificate validation.
- [ ] CAS service registry avoids overly broad matchers or client-controlled redirect URLs.
- [ ] **`CasAuthenticationFilter`**, **`CasAuthenticationProvider`**, **`ServiceProperties`**, and **`TicketValidator`** are configured exactly once in `SecurityFilterChain`.
- [ ] Spring Security 6 persists `Authentication` via **`SecurityContextRepository`/`HttpSession`** rather than re-validating STs on later requests.
- [ ] Local accounts/roles/tenant/resource grants are checked after CAS validation; deny when an account is disabled.
- [ ] Browser is redirected to a URL without ST after login; logs/APM/referrers do not expose raw tickets.
- [ ] Never retry STs after timeout/validation failure; start a new flow when needed.
- [ ] Proxy/Forwarded headers are trusted only from approved reverse proxies; canonical scheme/host/path are accurate.
- [ ] Multi-CAS/tenant setups choose the CAS server and service URL from trusted configuration, never from untrusted queries.
- [ ] Negative tests cover wrong service, expired ST, already-used ST, race conditions, URL mismatch, `renew`, HTTP 200 containing failure, network timeout, and disabled local account.
- [ ] Monitor **invalid/expired/mismatch/replay** rates without logging raw STs or exposing user data.

**Final Takeaway:** CAS **Service Ticket = opaque + service-bound + short-lived + single validation attempt**. An ST is used solely for one service to verify a login result at the CAS Server. After successful validation, Spring Security creates and stores **`Authentication`** in the application session; an already-consumed ST **must never be reused** or transferred to another service.
