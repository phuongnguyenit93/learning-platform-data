# Ticket Granting Ticket, Ticket Granting Cookie, and Service Ticket in CAS

**Central Authentication Service (CAS)** is a Single Sign-On (SSO) protocol and architecture between a **CAS Server** and multiple **applications integrated with a CAS Client**. To understand how CAS actually works, it is necessary to distinguish three artifacts often loosely called “tickets”:

- **Ticket Granting Ticket (TGT):** a longer-lived SSO session created by the **CAS Server** after a user authenticates; it can be used to **issue multiple Service Tickets** for permitted services while it remains valid.
- **Ticket Granting Cookie (TGC):** a cookie **belonging to the CAS Server** that the browser sends back when returning to CAS; the cookie ties to a TGT or server-side SSO state, allowing CAS to recognize a prior authentication. In modern Apereo CAS versions, the cookie value may be **signed and encrypted**; you should not assume the cookie contains a readable TGT ID.
- **Service Ticket (ST):** a **short-lived, single-use ticket bound to one specific service**. CAS delivers the ST via the browser to the service's callback URL; the **service-side CAS Client** calls the CAS Server to validate the ST and then creates its own application session.

**Upfront conclusion:** **A TGT is not an ST; a TGC is not a TGT; an ST is not a JWT or an application session cookie.** A user may have one active TGT/TGC and be issued many different STs for multiple applications, but each ST is intended for one service only and must be verified before the service grants access.

This lesson belongs to **Spring Security – federation → CAS Fundamentals**, explaining accurate terminology, CAS login/SSO/validation/logout flows, trust boundaries, Spring Security configuration, a standalone Java 17 simulation, real-world failure modes, and a production checklist.

## 1. Who Holds What in a CAS Session?

Suppose an organization runs a **CAS Server** at `https://sso.example.test/cas` and two applications:

- **Portal A:** `https://portal.example.test/login/cas`
- **HRM B:** `https://hrm.example.test/login/cas`

The browser interacts with all three websites, but **each website has its own cookie scope**.

| Component | Where Managed | Role |
| --- | --- | --- |
| Authenticated identity | CAS Server/ticket registry | Subject, timestamp, and authentication context |
| TGT | CAS Server (ticket registry) | Basis for issuing new STs for the same SSO context |
| TGC | CAS cookie in browser | Proof enabling CAS to locate/restore the SSO session |
| ST for Portal | Issued by CAS Server; carried by browser to Portal | Ticket for Portal to ask CAS to confirm the right user |
| ST for HRM | Issued by CAS Server; carried by browser to HRM | Separate ticket, valid only for HRM |
| Portal session | Portal/Spring Security | Maintains SecurityContext after the ST has been verified |
| HRM session | HRM/Spring Security | Separate session, does not share Portal's cookie |
| Roles/permissions | Each application per policy | Authorization after authentication |

**CAS is not the manager of every individual application's session.** Apereo CAS emphasizes that CAS maintains the SSO session via TGT/TGC, while application sessions are each application's own responsibility. SSO and session management are related but **have independent lifecycles**.

~~~text
                     Browser
                        |
               CAS cookie: TGC
                        |
                        v
             +---------------------+
             |    CAS Server       |
             |  TGT in registry    |
             |  issues ST per svc  |
             +---------------------+
                 |             |
              ST-A           ST-B
                 |             |
                 v             v
          +-----------+   +-----------+
          | Portal A  |   | HRM B     |
          | Session A |   | Session B |
          +-----------+   +-----------+
~~~

**The browser only sends the TGC to the CAS domain/path** per cookie rules. Portal and HRM **must not accept a TGT/TGC as direct proof of login**; they must obtain an ST issued for themselves and verify that ST with CAS.

## 2. What Is a TGT? The Nature of a CAS SSO Session

A **Ticket Granting Ticket** is an opaque ticket with sufficient randomness created by the CAS Server after a successful authentication event. It binds to the authentication, subject, timing policies, and server state to determine whether issuing new STs is permitted.

Key characteristics under the CAS protocol:

1. **Reusable to issue multiple STs** for registered and permitted services, as long as the TGT policy remains valid.
2. **Not a one-time ticket** like an ST.
3. **Has an expiry policy:** a TGT can expire by idle timeout, maximum time-to-live, or other version/deployment policies.
4. **Must be invalidated upon CAS logout** per the applied logout flow.
5. **Not a token for a service to verify directly by parsing the string**; service authentication occurs through ST validation and trust in the CAS Server.
6. **Not self-describing:** a TGT is not necessarily a JWT; never infer identity/roles from the prefix or contents of a TGT string.

An illustrative TGT looks like `TGT-9fa5...`. **Do not rely on prefix/length as a security check**; every ticket ID must be generated and verified by the real implementation. TGTs may be stored in an in-memory registry, Redis, Hazelcast, JDBC, or another CAS-supported backend; the actual choice depends on version, topology, and HA requirements.

### Why Does a TGT Exist?

If there were only STs and users had to enter their password every time they switched applications, it would no longer be true SSO. The TGT holds the **authenticated state at CAS**, allowing CAS to issue new STs for permitted services without prompting for credentials every time.

A TGT does not automatically guarantee every application will accept the user: each service still has its own registration requirements, audience/service policy, and authorization.

## 3. What Is a TGC? The Cookie Leading Back to the TGT

A **Ticket Granting Cookie** is an HTTP(S) cookie issued by the CAS Server after establishing an SSO session. When the browser is later redirected back to CAS, it sends this cookie according to cookie scope.

Conceptual HTTP response example:

~~~http
HTTP/1.1 302 Found
Location: https://portal.example.test/login/cas?ticket=ST-example-1
Set-Cookie: TGC=opaque-protected-cookie; Path=/cas; Secure; HttpOnly; SameSite=Lax
~~~

This is an **illustrative example**, not a mandatory header for every CAS version: cookie name, value, SameSite, path, expiry, and protection techniques are configured by CAS. The ST code in the URL is dummy data. Never expose real cookies/tickets in documentation or logs.

**Why can't TGC be equated with TGT?**

- **TGT:** server-side ticket state/object at the CAS Server or ticket registry.
- **TGC:** mechanism the browser presents to prove access to the corresponding CAS session.
- Some specifications or implementations may embed a TGT ID as part of the cookie value, but many modern deployments protect the cookie with signing/encryption and/or device bindings.
- The cookie may still exist in the browser while the **server-side TGT has expired**; in that case the cookie is insufficient for SSO.
- The TGT may still exist in the registry while the **browser lost/did not send the TGC**; CAS will not automatically recognize the user and may require re-authentication.

**Security:** the TGC is a cookie carrying capability to access the SSO session; protect it like a credential. Use HTTPS, `Secure`, `HttpOnly`, tight path/domain, a `SameSite` policy compatible with CAS flows, and environment-appropriate XSS/CSRF and cookie-theft defenses. Never write TGC values to production logs or send them to child applications.

### TGC and Application Cookies Are Different

After the ST is validated, a browser visiting Portal may receive Portal's **`JSESSIONID`**. That cookie is not a TGC. Portal cannot use it to issue an ST for HRM; nor does CAS use Portal's `JSESSIONID` as a basis for issuing new STs.

## 4. What Is an ST? A Short-Lived Ticket for Exactly One Service

A **Service Ticket** is an opaque bearer ticket issued by CAS for **one specified `service`**. The browser is redirected to the service with the `ticket` query parameter; the service calls the CAS Server over a back channel to verify it.

According to the CAS protocol specification:

- An ST is **valid only for the service identifier bound to it** when CAS issued it.
- An ST is **valid for only one verification attempt**; after one validation attempt, whether it fails or succeeds, the ticket must be invalidated to prevent replay.
- An unused ST must also **expire after an appropriate interval**; there is no single ST lifetime mandated across all CAS deployments.
- Services should use **HTTPS** and prevent ST leakage via URLs, access logs, browser history, Referrer headers, and analytics.
- A valid ST **does not replace application authorization**, nor is it a long-lived API access token.

A name like `ST-1856339-random` is illustrative only. Never accept an ST simply because the string starts with `ST-`; you must call the CAS validator using the proper protocol and exact service.

### An ST Is Not a JWT Verified Offline

A CAS ST is typically just a ticket string. A service should not Base64-decode an ST to look up a subject or verify a signature itself like a JWT. The source of truth is the **CAS Server validation endpoint**, called via a secure HTTP client, returning an authentication success or failure response.

## 5. Comparison Table: TGT – TGC – ST – Local Session

| Property | TGT | TGC | ST | SP Local Session |
| --- | --- | --- | --- | --- |
| Who creates it? | CAS Server | CAS Server via Set-Cookie | CAS Server | Service application |
| Where does it live? | CAS ticket registry | Browser cookie sent to CAS | Browser redirect then CAS validator | SP session store/cookie |
| Purpose | Maintains SSO at CAS | Links browser to TGT | Proves login for one service | Maintains login at SP |
| Can issue STs? | Yes, while valid and permitted | Does not issue directly; helps CAS find TGT | No | No under CAS protocol |
| Bound to one service? | No | No, belongs to CAS session | **Yes** | Belongs to that app |
| Single-use? | No | Cookie sent on multiple requests while valid | **One validation attempt** | Per session policy |
| Used by SP as credential? | Not directly | No | **Yes, via CAS validation** | Session cookie/local context |
| How does it expire? | TGT expiry policy | Browser cookie policy and CAS server state | ST expiry policy/validation consumption | SP session expiry policy |
| Logout | CAS destroys/expires TGT | CAS clears/invalidates cookie | ST unusable after validation | SP logout handler invalidates |
| Main risk | TGT theft/ticket registry compromise | Cookie theft/fixation | Replay/leakage/service confusion | Session hijack/stale authorization |

**Easy to remember:** **TGT = CAS-side SSO session; TGC = browser link to that session; ST = one-time ticket per service; local session = post-validation application session.**

## 6. First-Time Login Flow Without a TGC

A user who has never logged in to CAS on this browser accesses `/private` on Portal.

~~~text
Browser             Portal (CAS Client)             CAS Server
   |                        |                           |
   | GET /private           |                           |
   |----------------------->|                           |
   | 302 to CAS /login?service=Portal callback          |
   |<-----------------------|                           |
   | GET /cas/login?service=... (no TGC yet)            |
   |--------------------------------------------------->|
   |                  CAS displays login form           |
   |<---------------------------------------------------|
   | POST credentials -> CAS                            |
   |--------------------------------------------------->|
   |                 CAS verifies credentials/MFA       |
   |                 CAS creates TGT in ticket registry |
   | Set-Cookie TGC + 302 to Portal?ticket=ST-A         |
   |<---------------------------------------------------|
   | GET /login/cas?ticket=ST-A                         |
   |----------------------->|                           |
   |                        | GET /serviceValidate      |
   |                        |  service=Portal&ticket=ST-A|
   |                        |-------------------------->|
   |                        |  success + principal      |
   |                        |<--------------------------|
   |                        | create local session/roles|
   |<-----------------------| 302/200 app content       |
~~~

**Looking clearly at the pieces:**

1. **Portal** requires authentication and redirects to CAS with its `service` identifier.
2. **CAS** sees no valid TGC/TGT, so it requests credentials.
3. After successful authentication, CAS creates a **TGT**, sets the **TGC** in CAS's cookie, and issues **ST-A** exclusively for Portal.
4. The browser carries only **ST-A** to Portal, not the TGT.
5. **Portal backend** validates ST-A with CAS using the exact registered `service` value.
6. CAS returns user information if the ST is valid; ST-A is consumed.
7. Portal creates its **own session** and performs authorization.

**Which part holds the password?** CAS or an upstream authentication provider. The Portal CAS Client does not need to collect the user's password to validate a CAS ST.

## 7. SSO Flow to a Second Application While TGC/TGT Is Valid

Now the user opens HRM; the Portal session is not directly involved.

~~~text
Browser         HRM (CAS Client)             CAS Server
   |                   |                         |
   | GET /hr           |                         |
   |------------------>|                         |
   | 302 CAS login?service=HRM                   |
   |<------------------|                         |
   | GET CAS /login, with TGC                    |
   |-------------------------------------------->|
   |                CAS checks TGC -> valid TGT  |
   |                CAS checks HRM svc permitted |
   | Set/refresh cookie per policy               |
   | 302 HRM callback?ticket=ST-B                |
   |<--------------------------------------------|
   | GET HRM /login/cas?ticket=ST-B              |
   |------------------>|                         |
   |                   | /serviceValidate ST-B   |
   |                   |------------------------>|
   |                   | success + user attrs    |
   |                   |<------------------------|
   |                   | create HRM local session|
   |<------------------|                         |
~~~

Result:

- One **TGT** can serve as the source for CAS to mint distinct **ST-A, ST-B, ST-C** tickets across visits.
- **ST-A and ST-B are not interchangeable**: ST-A was issued for Portal, ST-B for HRM.
- **TGC** is sent to the CAS domain, never directly to HRM.
- HRM does not have to trust that Portal is logged in; HRM validates **ST-B** itself with CAS.
- Portal and HRM maintain **separate sessions/application authorization** and do not automatically share CSRF tokens, roles, or cookies.
- If CAS policy requires fresh login, `renew=true` can make CAS require primary credentials even while the TGT is active.

**SSO goal:** the user enters credentials once at CAS and is issued a separate ST to open each service, when service policy allows.

## 8. How `/login?service`, `/serviceValidate`, and `/p3/serviceValidate` Work

Common CAS protocol URIs:

| Endpoint | Purpose |
| --- | --- |
| `/cas/login` | CAS requests/verifies credentials or uses a valid TGC/TGT to issue an ST |
| `/cas/validate` | CAS 1.0 style validation (simple plain-text result), minimal information |
| `/cas/serviceValidate` | CAS 2.0 service ticket validation, XML |
| `/cas/p3/serviceValidate` | CAS 3.x service validation, XML and extended attributes per profile |
| `/cas/proxyValidate`, `/cas/p3/proxyValidate` | Validation with proxy ticket support when configured |
| `/cas/proxy` | Issues proxy ticket from PGT and targetService, when profile allows |
| `/cas/logout` | Ends the CAS SSO session within practical scope |

**Do not treat example endpoints as version guarantees:** Applications may use a context path other than `/cas`; CAS 2.0/3.0 validation and proxy capabilities depend on server, client library, and configuration.

### Browser Request to CAS

~~~http
GET /cas/login?service=https%3A%2F%2Fportal.example.test%2Flogin%2Fcas HTTP/1.1
Host: sso.example.test
~~~

CAS uses `service` as the identifier of the application to which the ST will be bound, but **must verify that the service is in the allowed list**. Accepting an arbitrary `service` URL from the browser can lead to open redirects, abuse of CAS as an IdP for unapproved apps, or ticket leakage.

### CAS Redirects Back to the Exact Service

~~~http
HTTP/1.1 302 Found
Location: https://portal.example.test/login/cas?ticket=ST-example-123
~~~

The browser sends a request to the Portal callback, where the CAS Client extracts `ticket`. Do not keep passing `ticket` as a query parameter through unrelated pages or redirects.

### Portal Validates the Ticket via Back Channel

~~~http
GET /cas/serviceValidate?service=https%3A%2F%2Fportal.example.test%2Flogin%2Fcas&ticket=ST-example-123 HTTP/1.1
Host: sso.example.test
~~~

This is a **server-to-server request** from Portal to CAS, not Portal simply looking at the `ticket` query param and logging the user in. The HTTPS connection to CAS must be authenticated, with hostname/certificate verification and reasonable timeouts. The `service` passed during validation must match the identifier the ST was issued for (per CAS matching rules/policy), including scheme/host/path as applicable.

## 9. Validation Responses: Success and Failure

CAS 2.0 XML success example:

~~~xml
<cas:serviceResponse
    xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>alice</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Failure example:

~~~xml
<cas:serviceResponse
    xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationFailure code="INVALID_TICKET">
    Ticket is invalid or already consumed
  </cas:authenticationFailure>
</cas:serviceResponse>
~~~

These messages are **illustrative samples**, not real output from a live CAS Server. CAS 3.x may include `cas:attributes` in the response according to attribute release policy.

**Only after `authenticationSuccess` is verified per protocol** does the CAS Client proceed to create `Authentication` and a local session. An HTTP 200 status from `serviceValidate` **is not enough**; you must check protocol success/failure, exact XML namespace, ticket, service, and transport trust.

Note that `cas:user` is a principal string from CAS. When an application has multiple CAS servers/tenants or identity brokers, do not use a bare username alone as a global identifier; bind it to the CAS instance/issuer/trust context and internal mapping. Attributes/roles from CAS still require the application's mapping policy.

## 10. One-Time ST: Why Can't It Be Reused After Validation?

The CAS protocol requires an ST to be valid for **only one validation attempt**, even if that attempt fails.

~~~text
CAS issues ST-1 for Portal

Attempt 1:
  Portal -> CAS /serviceValidate(ST-1, service=Portal)
  CAS -> success
  ST-1 -> consumed

Attempt 2:
  Portal -> CAS /serviceValidate(ST-1, service=Portal)
  CAS -> INVALID_TICKET

If Attempt 1 uses wrong service:
  HRM -> CAS /serviceValidate(ST-1, service=HRM)
  CAS -> failure
  ST-1 -> consumed; Portal must not be allowed to reuse it
~~~

**Reason:** reduces the chance of reusing a ticket captured via eavesdropping or taken from browser history/logs. However, an ST is still a bearer credential **before validation**, so leaking an ST within its validity window remains a risk.

**Do not do this:** when CAS returns `INVALID_TICKET`, have the application resend the same ST 5 times to “retry”. An earlier validation attempt may already have consumed the ST; retrying must start a new authentication flow or use proper CAS client error handling, never legitimize replay.

### If Validation Times Out

It is hard to tell whether CAS never received the request or already consumed the ST and the response was lost. Because the ST is one-time, retrying that ticket may fail. The application should **fail closed** on the unauthenticated request and redirect the user to start a new SSO flow, while logging a safe correlation ID and reason. Do not create a session just because “the ticket seemed to exist”.

## 11. TGT and ST Have Different Lifetimes

An organization might configure:

- TGT with an 8-hour hard timeout and 2-hour idle timeout.
- ST expiring after a very short period if not validated.
- Local Portal session timeout of 30 minutes.
- Local HRM session timeout of 20 minutes.

**The numbers above are illustrative only**, not mandatory CAS defaults.

| Scenario | Possible Outcome |
| --- | --- |
| TGT still valid, Portal local session expired | Browser redirects to CAS; valid TGC/TGT can issue a new ST, re-login is near-instant |
| ST unvalidated and expired | CAS rejects ST; must restart flow |
| TGT expired, browser still holds TGC | CAS will not auto-issue ST; new authentication required |
| Portal local session valid, TGT just expired | Portal may continue serving requests until Portal's session/policy blocks, unless logout/revocation is integrated |
| ST consumed, TGT still active | That ST is invalid; a new ST can be issued for another login while TGT remains valid |
| Browser clears TGC, TGT remains in registry | CAS cannot rely on the old browser to identify the session; new login may be required |
| CAS `/logout` destroys TGT and TGC | Next CAS visit usually requires fresh login; local SP sessions depend on SLO implementation |

Apereo CAS supports multiple expiration policies for TGTs: idle/default/hard timeout, max time to live, or per-service/per-principal policies depending on release. STs have their own expiration policy. **Do not pick one uniform lifetime for TGT, ST, TGC, and application sessions.**

### Long-Term SSO / Remember Me

Some CAS configurations allow keeping an SSO session longer than the browser session. In that case, the TGC may be a persistent cookie with a lifetime matching the long-term TGT policy. This is a **risk-controlled feature**; do not assume every TGC is a session cookie or an indefinite remember-me cookie.

## 12. How Do `renew=true` and `gateway=true` Change the Flow?

The CAS protocol includes optional parameters:

| Parameter | Effect | Watch Out For |
| --- | --- | --- |
| `renew=true` | Instructs CAS **not to rely solely on an existing SSO session**, requiring primary credentials per protocol/policy | Does not automatically mean every request has MFA or high assurance |
| `gateway=true` | Queries CAS **non-interactively**: if an SSO session exists, issue ST; otherwise return to service without a ticket | Application must handle the no-ST case |
| Both renew and gateway | Incompatible per CAS spec | Do not enable simultaneously as normal behavior |

Example requesting fresh authentication:

~~~text
GET https://sso.example.test/cas/login
    ?service=https%3A%2F%2Fportal.example.test%2Flogin%2Fcas
    &renew=true
~~~

**Do not interpret `renew` simply as deleting all of a user's TGTs.** It requests fresh authentication for the service per profile. Whether a new TGT is issued or how SSO state changes depends on CAS policy.

In Spring Security CAS, `ServiceProperties.sendRenew` expresses the intent to require fresh authentication. If the system needs MFA step-up, you must enforce a **strong authentication policy and assurance check** at CAS, not just turn on `renew` and assume MFA is covered.

## 13. Logout: Destroying TGT/TGC vs. Destroying Local App Sessions

There are three distinct operations:

1. **Logout at Portal:** Portal destroys its own `HttpSession`/SecurityContext. If TGC/TGT remain valid, the next visit to Portal may SSO again without a password.
2. **Logout at CAS:** CAS destroys/expires the TGT and clears the TGC appropriately; subsequent ST issuances cannot use that session. However, Portal/HRM may **still retain local sessions**.
3. **CAS Single Logout (SLO):** CAS attempts to send notifications to participating services so they destroy their local sessions. This requires CAS clients configured to process notifications and accurate session mapping.

~~~text
Before:
  TGT active, TGC active
  Portal session active
  HRM session active

Portal-only logout:
  TGT active, TGC active
  Portal session invalid
  HRM session active

CAS logout, no SLO to apps:
  TGT invalid, TGC invalid
  Portal session may still be active
  HRM session may still be active

CAS logout + successful SLO at both SPs:
  TGT invalid, TGC invalid
  Portal session invalid
  HRM session invalid
~~~

**CAS is not a global session database for every application.** Apereo CAS explicitly notes that an SLO message is a **notification**; the application/CAS client must receive it and invalidate its own session. Never promise “logged out from all devices” simply because CAS `/logout` returned 200 or the browser no longer has a TGC.

### Multiple Devices and Browsers

Each browser may hold a different TGC or CAS session. CAS SLO for one TGT/session does not prove that every other device of the same username has logged out. To revoke all sessions when an account is locked, you need CAS server session management combined with per-app session/token revocation mechanisms and clear policy.

## 14. An ST Is Not a Credential for Repeated API Calls

An ST is issued for a specific callback and **is consumed after validation**. Therefore:

- Do not send the same ST in `Authorization: Bearer ST-...` across multiple API requests.
- Do not use an ST to prove user identity across multiple different backend services.
- Do not store an ST as a long-lived session token.
- Do not let an API re-validate an ST that the frontend already validated.
- Do not pass an ST as a redirect parameter across multiple applications; that breaks service binding or leaks a bearer secret.

**Correct web model:** the ST is verified **once** by the CAS client, and the service creates a local session (or its own policy-governed token) for subsequent requests.

**Proxying model:** CAS has **Proxy Granting Ticket (PGT)** and **Proxy Ticket (PT)** for use cases delegating one service to access a back-end service on the user's behalf, with proxy validation/proxy chain policies. PGT/PT are **a separate mechanism from standard STs**, requiring explicit configuration—never enable accept-any-proxy blindly.

If a modern API system uses OAuth2/OIDC, use protocols with proper access tokens, audiences, and resource-server validation; CAS STs do not substitute for JWT/OAuth access tokens.

## 15. Distinguishing ST, PGT, PT, and Login Ticket (LT)

| Type | Abbreviation | What Is It Used For? |
| --- | --- | --- |
| **Ticket Granting Ticket** | TGT | CAS SSO session, basis for issuing STs |
| **Ticket Granting Cookie** | TGC | Browser cookie linking to the TGT session |
| **Service Ticket** | ST | Proof for one specific service, validated once |
| **Proxy Granting Ticket** | PGT | Authorization basis allowing a service to request proxy tickets for backends |
| **Proxy Ticket** | PT | Ticket for a target service in a proxy flow, checks proxy chain if applicable |
| **Login Ticket** | LT | One-time token in the login form of some CAS implementations to prevent form/credential replay attempts |

**PGT differs from TGT:** PGT serves delegated/proxy access, not the browser SSO cookie. **PT differs from ST:** PT is bound to a target/proxy flow and requires chain verification, and is not broadly accepted like an ST across all services.

Not every CAS deployment enables proxying. If app A does not need to call backend B on behalf of the user, **do not enable proxy ticket validation** or set `acceptAnyProxy=true` just to avoid errors.

## 16. Service Registry and Service Identifier: Boundary Against ST Misuse

A ticket is meaningless unless bound to the **service identifier** to which CAS granted access.

Suppose:

- ST-A was issued for `https://portal.example.test/login/cas`.
- ST-B was issued for `https://hrm.example.test/login/cas`.

CAS validation must match the **exact service**:

~~~text
validate(ST-A, Portal service URL) => may SUCCEED
validate(ST-A, HRM service URL)    => FAILURE
validate(ST-B, Portal service URL) => FAILURE
validate(ST-B, HRM service URL)    => may SUCCEED
~~~

Outcomes also depend on whether the ticket was already consumed, expiry, and authentication policy.

The **CAS Service Registry** governs which services may participate in SSO, potentially including URL matching, attribute release, proxy policy, MFA/authentication context, access strategy, and logout callbacks. Never permit an open URL unconditionally just because it starts with `https://`.

### Reverse Proxies Causing Service Mismatch

An application runs internally at `http://portal:8080/login/cas` but externally at `https://portal.example.test/login/cas`. If Spring `ServiceProperties.service` declares the public URL while the CAS client uses the internal HTTP URL during validation, CAS may reject the ST due to `service` mismatch.

Check:

1. `service` when redirecting to `/cas/login`.
2. `service` when CAS issues the ST.
3. `service` when the backend calls `/serviceValidate`.
4. The callback URL watched by `CasAuthenticationFilter`.
5. Reverse proxy HTTPS/Host/forwarded-header trust and context path.

**Do not fix this by** broadening the Service Registry to a regex matching all URLs or disabling service matching.

## 17. Cookie Security: How Dangerous Is a Stolen TGC?

The TGC is a powerful SSO session access capability; if an attacker steals a valid cookie, they can try to use it to ask CAS to issue new STs for services permitted by that session, depending on additional protections such as device binding/MFA/step-up.

Principles:

- **HTTPS mandatory** in real environments, protecting TLS on CAS and all service URLs.
- `Secure`: browser sends cookie only over HTTPS.
- `HttpOnly`: reduces JavaScript access to the cookie; **does not completely eliminate XSS/session abuse**.
- `SameSite`: design to fit CAS browser redirects/POSTs/cross-site navigation; test across modern browsers.
- `Path` and `Domain`: restrict scope; do not share the TGC across all subdomains unnecessarily.
- **Cryptographic protection**: modern Apereo CAS releases have TGC signing/encryption mechanisms; keys must be consistent across the cluster and managed via a secret manager.
- **Rotate** cookie signing/encryption keys through a controlled process, understanding the impact of invalidating user sessions.
- **Logout/invalidation**: do not only clear the browser cookie—invalidate the TGT server-side when revocation is needed.
- **Rate limit/anomaly detection**: monitor abnormal ST issuance rates and IP/user-agent/device changes where policy applies.
- **Never log secrets**: never write TGC, TGT, ST, or login credentials to access logs, APM traces, or telemetry.

**A TGC is not an OIDC JWT access token** that can be sent to APIs. A newer CAS system might use JWT/JWE to represent the protected cookie, but that is a TGC implementation detail and does not turn the CAS protocol into OAuth2.

## 18. ST in the Query String: Reducing Leakage Risk

The CAS protocol passes the ST via the `ticket` query parameter on redirect. This can accidentally expose secrets through:

- Browser history or copying/pasting the full URL.
- Reverse proxy and web server access logs.
- Referer headers sent to third-party resources if the app navigates before stripping the ticket.
- Analytics scripts, error trackers, and APM instrumentation.
- Screenshots, incident tickets, and centralized log tracing.

**Practical measures:**

1. Use `HTTPS` for CAS and service callbacks.
2. Have the CAS Client validate the ST **immediately at the callback**, without forwarding the ticket deep into business controllers.
3. After successful validation, redirect the user to a **clean URL without `ticket`**.
4. Enable an appropriate `Referrer-Policy` and avoid loading third-party resources before the ticket is consumed and the URL is cleaned.
5. Configure reverse proxy/access logs to **mask the `ticket` query parameter** instead of storing raw URLs.
6. Never capture/log/write STs to the browser console, metrics labels, or exception messages.
7. Enforce short expiration, one-time validation, and replay protection at CAS.
8. Perform backend authorization based on the verified session/authentication, not on the ST string.

**Never think:** “STs are very short-lived so logging them is fine”. It remains a valid bearer credential during its window before consumption.

## 19. TGT Registry, CAS Cluster, and Multi-Node Operation

In a multi-node deployment, CAS nodes must agree on ticket state:

~~~text
                      Load Balancer
                       /        \
                   CAS node 1   CAS node 2
                       \        /
                 Shared Ticket Registry
                  + TGT session state
                  + ST issue/consume state
                  + expiration/revocation
                       |
                Consistent TGC crypto keys
~~~

If node 1 creates a TGT/ST but node 2 cannot see the ticket, the browser may be forced to log in again or ST validation may fail intermittently. If the registry does not guarantee **atomic consume** of the ST, the same ST could be validated twice in a race condition, violating one-time semantics.

### What Must Be Synchronized

- Ticket registry backend and how tickets are stored/expired/deserialized.
- TGT expiration policies, clocks, and synchronization.
- Truly atomic ST invalidation/one-time consume.
- TGC signing/encryption keys, cookie name/path/domain, and key rotation.
- Service Registry: every node has the same allowed services list and rules.
- CAS authentication policies, MFA/renew/gateway behavior, and attribute release.
- Logout notifications, session mapping, and log correlation.

**Do not** use independent in-memory ticket registries across production CAS nodes behind a load balancer without sticky routing and appropriate system design; even sticky sessions have failure modes when a node goes down. Choose a shared registry supported by that CAS release and test real failover/consistency.

## 20. Spring Security CAS: Core Classes and Responsibilities

**Spring Security supports CAS through its dedicated CAS integration module**, not `saml2Login` or `oauth2Login` configuration.

| Component | Responsibility |
| --- | --- |
| `CasAuthenticationEntryPoint` | Redirects browser to CAS `/login` with the service URL |
| `ServiceProperties` | Configures the application service callback URL and `sendRenew` when required |
| `CasAuthenticationFilter` | Receives `ticket` at the callback, delegates to `AuthenticationManager` |
| `CasAuthenticationProvider` | Validates the ticket and builds Spring `Authentication` |
| `Cas20ServiceTicketValidator` | CAS client validator calling `/serviceValidate` |
| `UserDetailsService` / `AuthenticationUserDetailsService` | Maps the CAS-authenticated principal to local account/authorities |
| `SecurityContext` / local session | Holds the application's authentication after the ST is consumed |
| `SingleSignOutFilter` / listener (CAS client) | Processes CAS logout notifications if SLO is properly integrated |
| `CasAuthenticationToken` or `CasServiceTicketAuthenticationToken` | CAS auth-related token classes depending on Spring Security version |

**Key point from Spring Security documentation:** by default `CasAuthenticationFilter` handles the `/login/cas` callback; `ServiceProperties.service` must represent that exact URL. A service URL mismatch causes ticket validation to fail even when TGC/TGT are valid.

Spring Security 6.x/7.x introduced class/token changes and can integrate with different Apereo Java CAS Client versions. Do not copy old Spring Security 4/5 code into 6/7 without checking Javadoc/BOM, especially token classes, caches, constructors, and namespaces.

### Do Not Confuse Security Modes

- **CAS integration:** receives and validates an opaque **Service Ticket** via the CAS validation endpoint.
- **SAML 2.0 integration:** receives `SAMLResponse`, verifies XML signatures, assertions, and metadata.
- **OIDC integration:** receives an ID Token with `iss/sub` alongside the OAuth2 authorization code flow.

One identity broker may offer all three protocols, but **each protocol has its own client library**. TGT/TGC belong to the CAS model; do not equate them with SAML assertions or OIDC refresh tokens.

## 21. Component-Level Spring Security CAS Configuration

This example shows **Spring Security CAS Java components** under the Servlet model using classes documented in Spring Security. This is **not a Spring Boot starter enabled by a single `spring.security.cas.enabled` property**, nor is it a standalone Java program.

~~~java
// Code snippet belonging to a Spring application @Configuration,
// requiring matching spring-security-cas + apereo CAS client dependencies,
// proper imports, AuthenticationManager, UserDetailsService,
// and SecurityFilterChain for the version in use.

@Bean
ServiceProperties casServiceProperties() {
    ServiceProperties service = new ServiceProperties();
    service.setService("https://portal.example.test/login/cas");
    service.setSendRenew(false);
    return service;
}

@Bean
CasAuthenticationEntryPoint casEntryPoint(ServiceProperties service) {
    CasAuthenticationEntryPoint entry = new CasAuthenticationEntryPoint();
    entry.setLoginUrl("https://sso.example.test/cas/login");
    entry.setServiceProperties(service);
    return entry;
}

@Bean
TicketValidator casTicketValidator() {
    // Portal-side validator that calls CAS Server to validate the ST.
    return new Cas20ServiceTicketValidator(
        "https://sso.example.test/cas");
}

@Bean
CasAuthenticationProvider casProvider(
        ServiceProperties service,
        TicketValidator validator,
        AuthenticationUserDetailsService<CasAssertionAuthenticationToken>
                userDetails) {
    CasAuthenticationProvider provider = new CasAuthenticationProvider();
    provider.setServiceProperties(service);
    provider.setTicketValidator(validator);
    provider.setAuthenticationUserDetailsService(userDetails);
    provider.setKey("portal-cas-provider-v1");
    return provider;
}
~~~

**Note:** This sample is **Java pseudo-integration** to illustrate the beans and their relationships. The generic type of `AuthenticationUserDetailsService`, the `CasAssertionAuthenticationToken` package, and Spring APIs can vary between 6.5 and 7.x branches; adapt and compile against your **actual BOM Javadoc**. Do not copy verbatim as a complete class; you still need the CAS filter, `AuthenticationManager`, `SecurityFilterChain`, actual CAS `UserDetails` loader, SLO filter/registration, and exception/error handling.

**Architectural invariants:**

1. `ServiceProperties.service` matches the public callback `https://portal.example.test/login/cas` in the CAS Service Registry.
2. `CasAuthenticationEntryPoint` sends the browser to the CAS login endpoint with the exact service.
3. `CasAuthenticationFilter` receives the **ST** and hands it to the provider for verification; it never accepts TGC/TGT as authentication.
4. `CasAuthenticationProvider` uses `TicketValidator` to query the CAS Server over HTTPS; it never trusts the `ticket` query string on its own.
5. After CAS authentication, the app retrieves local account/authorities from a trusted policy source.

**Safety note:** Some older samples use `{noop}` passwords or accept-any-proxy for illustration—never copy those into production. If proxy authentication is not needed, use an appropriate service ticket validator and keep proxying disabled.

## 22. Configuring URLs, Reverse Proxies, Sessions, and Authorities in Spring

Example URLs that must stay consistent:

~~~text
CAS login URL:
  https://sso.example.test/cas/login

CAS validation base URL:
  https://sso.example.test/cas

Portal public callback service:
  https://portal.example.test/login/cas

Spring CAS filter processing path:
  /login/cas

CAS Service Registry:
  service = https://portal.example.test/login/cas
~~~

Implementation steps:

1. Register Portal in the **CAS Service Registry** with the exact service URL, HTTPS, and access policy.
2. In Spring, configure `CasAuthenticationEntryPoint` using the CAS login URL.
3. Set `ServiceProperties.service` to the **public callback URL** corresponding to the filter.
4. `CasAuthenticationFilter` receives the `ticket` query param and the provider validates the ST with the CAS validator.
5. Local user details/authority mapping must not blindly grant `ROLE_ADMIN` from arbitrary CAS attributes.
6. Spring session management configures timeout, fixation protection, CSRF, and logout handlers.
7. Trust proxy headers only from a trusted reverse proxy; never trust `Host`/`X-Forwarded-Host` from the public internet.
8. Test requesting an ST for Portal, validating with the exact URL, clean redirect, and subsequent access via local session.

**It is not mandatory to establish an HTTP session before redirecting to CAS** for CAS to issue a TGT; CAS manages its own SSO session. However, a Spring Web app typically uses a local session after ST validation.

### Role and Tenant Mapping

Suppose CAS returns `cas:user=alice` with a `groups` attribute. The Spring provider can use `UserDetailsService` to load local accounts/roles. Do not treat username `alice` from CAS A and `alice` from CAS B as the same person in an application trusting multiple CAS contexts. Store the identity link with the **CAS server/issuer context** and appropriate subject, then verify tenant membership, object-level permissions, and account status.

## 23. Standalone Java 17: Simulating TGT, TGC, and ST

To demonstrate the lifecycle without depending on a real CAS Server, the program below simulates:

- One TGT able to issue multiple STs.
- A TGC pointing to an active TGT session.
- STs bound to the exact service, consumed after the **first validation attempt**, even on wrong service.
- Logout preventing the TGT from issuing further STs.
- Ticket IDs are sample strings for deterministic stdout, **with no cryptographic randomness**.

Create **`CasTicketLifecycleDemo.java`**:

~~~java
import java.util.HashMap;
import java.util.Map;

public class CasTicketLifecycleDemo {

    record ServiceTicket(String owner, String service) {}

    static final class MiniCas {
        private final Map<String, ServiceTicket> tickets =
                new HashMap<>();
        private boolean tgtActive = true;
        private final String tgtId = "TGT-demo";
        private int counter;

        String tgcValue() {
            // This only models a cookie pointing to a TGT, not
            // the TGC signing/encryption technique of real Apereo CAS.
            return tgtId;
        }

        boolean hasSsoSession(String tgc) {
            return tgtActive && tgtId.equals(tgc);
        }

        String issue(String tgc, String service) {
            if (!hasSsoSession(tgc)) {
                return "DENIED_NO_TGT";
            }
            String ticket = "ST-" + (++counter);
            tickets.put(ticket,
                    new ServiceTicket("alice", service));
            return ticket;
        }

        String validate(String ticket, String service) {
            // remove() before checking service: a validation attempt
            // consumes the ticket even when returning failure.
            ServiceTicket found = tickets.remove(ticket);
            if (found == null) {
                return "INVALID_CONSUMED";
            }
            if (!found.service().equals(service)) {
                return "INVALID_SERVICE";
            }
            return "VALID user=" + found.owner();
        }

        void logout() {
            tgtActive = false;
        }
    }

    public static void main(String[] args) {
        MiniCas cas = new MiniCas();
        String cookie = cas.tgcValue();

        System.out.println("TGC maps to active TGT: "
                + cas.hasSsoSession(cookie));

        String ticketA = cas.issue(cookie, "PORTAL");
        System.out.println("Issue Portal: " + ticketA);
        System.out.println("Validate Portal: "
                + cas.validate(ticketA, "PORTAL"));
        System.out.println("Replay Portal: "
                + cas.validate(ticketA, "PORTAL"));

        String ticketB = cas.issue(cookie, "HRM");
        System.out.println("Issue HRM: " + ticketB);
        System.out.println("Wrong service validation: "
                + cas.validate(ticketB, "PORTAL"));
        System.out.println("Retry HRM: "
                + cas.validate(ticketB, "HRM"));

        String ticketC = cas.issue(cookie, "HRM");
        System.out.println("New ticket for HRM: " + ticketC);
        cas.logout();

        System.out.println("TGC after CAS logout: "
                + cas.hasSsoSession(cookie));
        System.out.println("Issue after logout: "
                + cas.issue(cookie, "PORTAL"));
    }
}
~~~

Compile and run with **JDK 17+**:

~~~bash
javac CasTicketLifecycleDemo.java
java CasTicketLifecycleDemo
~~~

**Exact stdout:**

~~~text
TGC maps to active TGT: true
Issue Portal: ST-1
Validate Portal: VALID user=alice
Replay Portal: INVALID_CONSUMED
Issue HRM: ST-2
Wrong service validation: INVALID_SERVICE
Retry HRM: INVALID_CONSUMED
New ticket for HRM: ST-3
TGC after CAS logout: false
Issue after logout: DENIED_NO_TGT
~~~

**Interpretation:**

- A sample TGC locates an active TGT.
- The TGT issues `ST-1` and `ST-2` for different services.
- `ST-1` validates once for Portal and cannot be replayed.
- `ST-2` was tried with the wrong Portal service, so it was consumed; HRM cannot validate it afterward.
- CAS can issue a new `ST-3` for HRM while the TGT remains active.
- After CAS logout, the TGC no longer points to a valid TGT and CAS issues no new STs.

**Very important model limitations:** No cryptography, entropy, real expiry, secure cookies, networking, CAS Service Registry, concurrent atomic validation, CAS XML responses, or app sessions. `ST-3` remains unconsumed in the map after logout because the demo only illustrates **blocking new ST issuance**, not full graph invalidation; in production CAS must enforce proper expiration/revocation and logout policies. **Do not use `MiniCas` as a real CAS server.**

## 24. Does Destroying a TGT Immediately Erase Local Sessions?

Not by default. Once Portal has validated the ST and established a session, subsequent requests typically use the **Portal session**; CAS may not be called again on each request.

Example:

~~~text
09:00 CAS creates TGT, TGC
09:01 CAS issues ST-A; Portal validates and creates 60-minute session
09:10 CAS TGT expires/logs out
09:11 Portal local session still exists if no SLO received
09:30 Portal may still serve requests per policy
10:01 Portal session expires -> redirects to CAS
       CAS has no TGT left -> fresh login
~~~

These are **hypothetical timings**, not mandatory behavior for every configuration. If the system has CAS Single Logout and the SP destroys its session upon receiving a notification, Portal can end the session sooner. If APIs also issue their own tokens, their revocation must be evaluated independently.

**Therefore CAS is not a component that “checks TGT on every request” by default** in every SP. For sensitive services, you need local session TTLs, step-up/renew, server-side authorization, and consistent logout/revocation policies.

## 25. Common Failure Scenarios

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| After Portal login, HRM still asks for password | TGC not sent, TGT expired, `renew` enabled, or wrong cookie scope | Check cookie/TGT policy, renew, SameSite, browser flow |
| CAS keeps prompting for credentials after redirect | Cookie encryption/signing keys mismatch across nodes or unsynchronized TGT registry | Check node keys, ticket registry, load balancing |
| Portal receives `INVALID_TICKET` on first attempt | ST expired/consumed, validated earlier, timeout/retry, or ticket leak | Trace flow/correlation, avoid retrying ST |
| ST-A from Portal works at HRM | Critical bug in service binding/validator | Check CAS Service Registry, strict service validation |
| CAS `/login` redirects to unexpected URL | Overly broad Service Registry or open redirect | Permit only registered/approved services |
| Spring `CasAuthenticationFilter` ignores ticket | Callback path does not match `filterProcessesUrl` | Compare `ServiceProperties.service` and filter URL |
| CAS validation `INVALID_SERVICE` | Service URL differs due to proxy/host/path | Compare URL at issuance and validation |
| HTTP 200 from `/serviceValidate` yet login fails | XML response is `authenticationFailure` | Parse protocol status, not just HTTP code |
| CAS TGC present but TGT does not exist | Registry expiry, logout, or cluster mismatch | Handle reauthentication safely |
| CAS logout yet Portal stays logged in | Portal local session not destroyed, SLO not handled | Configure CAS client SLO and session registry |
| Browser retains Portal session after CAS TGT expiry | Independent app session timeout | Define clear session lifecycle |
| ST appears in nginx/access logs | Logging full URL/query parameters | Redact `ticket`, limit logging and retention |
| CAS certificate rotation causes validation timeout | Stale HTTPS truststore, TLS handshake failure | Update CA/trust properly; never disable cert checks |
| Service unexpectedly grants `ROLE_ADMIN` | Mapping attributes directly to authorities | Allowlist local roles, check account/tenant |
| Client tries sending ST as API Bearer token | Mistaking one-time ticket for access token | Use local session or appropriate API token scheme |
| Cluster occasionally allows validating an ST twice | Ticket registry lacks atomic consume | Check consistency/atomicity and race testing |
| `gateway=true` returns without ST | No CAS SSO session exists | Handle anonymous/interactive login per policy |
| `renew=true` does not trigger MFA automatically | `renew` requires primary credentials, does not imply full MFA | Check CAS MFA policy and assurance |

**Never fix issues by** disabling TLS validation, accepting arbitrary `service` URLs, setting an excessively long ST TTL, enabling unconditional proxying, or allowing login when CAS validation fails.

## 27. Layered Diagnostics: Browser, CAS, Service, and Backend

### A. Browser

- Is there a TGC cookie in the cookie jar for the CAS origin?
- Is the cookie sent to CAS `/login` per path/domain/SameSite/Secure?
- Is the user on a different browser/device? Cookie stores are separate.
- When CAS redirects back to the service, are `ticket` and the exact callback URL present?
- Is the browser stuck in a redirect loop between Portal and CAS?

**Never copy raw cookies or STs into support tickets.** Use redacted network timelines and correlation IDs.

### B. CAS Server

- Did initial authentication succeed?
- Is the TGT active/expired/revoked in the ticket registry?
- Does the TGC have consistent cryptographic configuration across CAS nodes?
- Does the Service Registry allow Portal/HRM and the exact URL?
- Which service was the ST issued for, and at what timestamp?
- Did an earlier ST validation attempt already consume the ticket?
- Did CAS `/logout` trigger SLO and did apps receive notifications?

### C. Spring Security/CAS Client

- Does the `/login/cas` callback match `ServiceProperties.service`?
- Is the CAS validation base URL pointing to the right endpoint with a valid HTTPS truststore?
- Are `CasAuthenticationFilter` and `CasAuthenticationProvider` wired into the right `SecurityFilterChain`/`AuthenticationManager`?
- Was the CAS validation response `authenticationSuccess` or `authenticationFailure`?
- Were local `Authentication`/`SecurityContext` stored properly after validation?
- Was local account mapping/roles rejected after CAS success?

### D. Infrastructure

- Does the reverse proxy pass scheme/host/path accurately and restrict spoofed forwarded headers?
- Does the ticket registry have shared state and atomic consumption?
- Do CAS nodes use synchronized cookie encryption/signing keys?
- Are cache/clock drift or browser cookie policies causing discrepancies?
- Do logs mask `ticket` and cookies?
- During an outage, does the client fail closed and avoid infinite redirect loops?

## 28. Production Operations: Lifetimes, Monitoring, and Auditing

**Recommended metrics** (custom-defined per system, not necessarily built-in by default):

- `cas_tgt_active_sessions`: count of active TGTs.
- `cas_tgt_expired_total`: count of expired TGTs, distinguishing logout vs. timeout.
- `cas_st_issued_total`: count of STs issued per service (without including ticket strings).
- `cas_st_validation_success_total`: successful validations.
- `cas_st_validation_failure_total`: failures by reason (expired, consumed, service mismatch).
- `cas_sso_login_latency`: time spent traversing CAS and returning to the SP.
- `cas_tgc_cookie_validation_failure_total`: cookie cryptography/format errors.
- `cas_slo_notification_failed_total`: CAS Single Logout delivery failures.
- `cas_ticket_registry_latency`: registry issue/consume latency.
- `cas_local_session_revocation_delay`: delay updating SP sessions upon logout.

These metrics **must not contain ST/TGT/TGC values**, high-cardinality NameID/username/email labels, or exposed personal data.

### What Should Be Audited

1. Changes to the service registry and URL matching regexes.
2. Changes to ST/TGT/TGC lifetime policies.
3. Cookie encryption/signing key rotation.
4. Ticket registry backend or clustering changes.
5. CAS client service URL/validator/truststore changes.
6. Unusual spikes in `INVALID_TICKET` or `INVALID_SERVICE`.
7. CAS logout/SLO propagation and stale local session incidents.
8. Changes to CAS principal-to-local-account/role mappings.
9. Whether any device/browser retains a session after a revocation request.
10. Security test results and rollback readiness.

**Do not extend TGT lifetime indefinitely** just to reduce password prompts; weigh shared-device threats, idle risk, MFA policy, privileged administration, and session revocation.

## 29. Self-Check Questions

**1. How many times can a TGT be used?**  
It can be used to issue **multiple STs** while valid and permitted by policy. It is not a one-time token.

**2. Can an ST be validated twice if the first attempt fails?**  
Under the CAS protocol, **no**: a single validation attempt consumes the ST even if the result is a failure.

**3. Is the TGC Portal's session cookie?**  
No. The TGC is a cookie set by the CAS Server to link the browser to the CAS-side SSO session; Portal has its own session cookie.

**4. Can an ST issued for Portal be used to log in to HRM?**  
No. An ST must match the service identifier for which CAS issued it.

**5. Why doesn't Portal need to hold the TGT to log the user in?**  
Portal only needs a **CAS-verified ST**; afterward Portal creates its own local session and authorization.

**6. If the CAS TGT expires before the Portal session expires, does Portal force an immediate logout?**  
Not by default. That requires SLO/revocation integration or local session policy.

**7. Why doesn't a browser navigating to HRM need to re-enter its password?**  
The browser sends the TGC to CAS; CAS locates the valid TGT and issues a new ST for HRM when service policy allows.

**8. Can you infer the user from `ST-` or decode an ST like a JWT?**  
No. An ST is an opaque string; you must call the proper CAS validation endpoint.

**9. Does `renew=true` guarantee MFA?**  
No. It requires primary authentication rather than reusing SSO alone; MFA requires dedicated policy/assurance.

**10. How do TGT and TGC differ when the browser deletes cookies?**  
The TGT may still exist in the CAS registry, but the browser no longer holds the session proof so it will not SSO automatically.

**11. Why must Spring's `ServiceProperties.service` match the callback?**  
Because CAS validates the ST in the context of the exact service; any difference in scheme/host/path can cause rejection.

**12. Does CAS logout delete every app's local session?**  
Not guaranteed. CAS may send SLO notifications; each application must receive and execute invalidation.

**13. Is an ST suitable as a long-lived bearer token for microservices?**  
No. It is scoped to one service and single-use; use an appropriate access token/session scheme instead.

**14. Are PGT and PT needed when only logging into Portal?**  
Usually no. PGT/PT serve proxy authentication and require separate configuration/validation.

**15. Does a TGC contain a plain-text TGT ID?**  
Never assume so. Modern Apereo CAS releases typically protect the cookie with signing/encryption and may add other session bindings.

## 30. Implementation Checklist

- [ ] Distinguish **TGT/TGC/ST/local session**; never merge them into a single token.
- [ ] Protect the CAS Server with HTTPS and a strict Service Registry per service.
- [ ] Give TGTs an appropriate expiration policy; keep STs short-lived with one-time validation.
- [ ] Configure TGC with `Secure`, `HttpOnly`, tight cookie scope, appropriate `SameSite`, and cryptographic protection.
- [ ] Share a valid ticket registry and consistent cookie crypto keys across CAS nodes.
- [ ] Ensure the ticket registry performs **atomic consume** on ST validation, preventing race-condition replay.
- [ ] Match `service` between CAS issuance/validation and the registered public callback URL.
- [ ] Have Spring `CasAuthenticationFilter` receive the ST at callback and provider validate with CAS server using proper TLS trust.
- [ ] Never authenticate solely on seeing a `ticket` query string or HTTP 200 from the validator.
- [ ] When an ST is invalid/expired/consumed, do not create a session; initiate a controlled new flow.
- [ ] After validation, clean the ST from the browser URL and mask logs/referrers.
- [ ] Never send TGT/TGC to SPs, and never use STs for repeated API calls.
- [ ] Use `renew` and `gateway` per protocol; never enable both simultaneously.
- [ ] On CAS logout, evaluate SLO requirements and verify local session invalidation across apps.
- [ ] Do not treat CAS TGT expiry as local session expiry; design separate lifetimes.
- [ ] Never accept arbitrary PGT/PT or `acceptAnyProxy` when proxying is not needed.
- [ ] Map principal/attributes to local account/authorities per policy, never auto-admin.
- [ ] Test wrong service, ST replay, ST timeout, TGT expiration, cookie loss, and SLO failure.
- [ ] Maintain plans for secret protection, registry auditing, and multi-device login limits.
- [ ] Cross-check CAS Server, CAS Client, and Spring Security versions before deployment.

## 31. Conclusion

A **TGT** is the CAS-side SSO session ticket; a **TGC** is the browser cookie presented when returning to CAS; an **ST** is a short-lived, single-use verification ticket dedicated to one application. One valid TGT can issue multiple distinct STs to deliver a single sign-on experience. Each service must still **validate its exact ST with the CAS Server**, then establish its own local session and enforce authorization.

Always keep four security boundaries in mind: **TGC belongs only to CAS**, **ST belongs only to the exact service**, **TGT is not an app session**, and **ST validation does not replace authorization**. These distinctions explain most common CAS issues: SSO prompting for passwords again, ST `INVALID_TICKET`, `INVALID_SERVICE`, logout not propagating to applications, or mistaking an ST for an API bearer token.
