# Login Redirect Flow and Ticket Verification Over Server-to-Server Connection

> **Module:** Spring Security – federation · **Parent topic:** CAS Fundamentals. This lesson explains the Single Sign-On flow of **Central Authentication Service (CAS)**: the browser is redirected to the CAS server to authenticate, receives a **service ticket (ST)** upon returning to the application, and the **application server** verifies the ST with CAS over HTTPS before creating a login session. The focus is on trust boundaries, one-time ticket semantics, `service` accuracy, and Spring Security integration.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Explain the roles of the **browser**, **CAS server**, **Service Provider/application (service)**, **CAS client**, and **Spring Security** in a single login.
2. Distinguish **Ticket-Granting Ticket (TGT)**, **ticket-granting cookie (TGC)**, **Service Ticket (ST)**, **Login Ticket (LT)**, and **Proxy Ticket (PT)**; know which ticket appears in the application URL.
3. Present the exact flow: resource request → HTTP 302 to `/cas/login?service=...` → CAS authentication → 302 to `service?ticket=ST-...` → application calls `/serviceValidate` server-to-server → create local security context/session.
4. Distinguish verifying an ST with a **trusted CAS server over HTTPS** from merely seeing a `ticket` parameter sent by the browser.
5. Grasp that `service` **must match the service for which the ticket was issued**, the ticket is **single-use**, has a short lifetime, and failures must **fail closed**.
6. Read `cas:serviceResponse` XML with `cas:authenticationSuccess/cas:user` or `cas:authenticationFailure`, including the real CAS XML namespace.
7. Distinguish CAS 1.0 `/validate`, CAS 2.0 `/serviceValidate`, CAS 3.0 `/p3/serviceValidate`, `/proxyValidate`, and CAS SAML 1.1 `/samlValidate`; do not confuse them with SAML2 Web SSO.
8. Understand `CasAuthenticationEntryPoint`, `CasAuthenticationFilter`, `CasAuthenticationProvider`, `ServiceProperties`, and `Cas20ServiceTicketValidator` in Spring Security.
9. Run a Java 17 example simulating the service-ticket lifecycle with deterministic stdout; also examine a JDK 17 program performing HTTPS validation and safe XML parsing.
10. Identify risks of open redirects, ticket replay, service mismatch, ticket leakage via URL/logs/Referer, TLS failures, CAS outages, user mapping, and authorization.
11. Plan tests for valid/invalid tickets, wrong service, timeouts, CA trust, multi-tenant setups, and local session fixation.

**Target audience:** Java Servlet and Spring Boot/Spring Security applications using the **traditional CAS protocol**. A CAS server may also support SAML2/OIDC as separate protocols. **A CAS service ticket is not a SAML2 Assertion or an OAuth2 access token.**

## 2. Overview: Why Are Two Connection Legs Required?

The Orders Portal application needs employee login. Rather than accepting passwords, Portal delegates authentication to the CAS server. However, the browser can alter any query parameter it sends to Portal, so **an ST arriving via the browser is not sufficient to prove identity**.

~~~text
             BROWSER / FRONT CHANNEL              SERVER / BACK CHANNEL

[Browser]   [Orders Portal / CAS client]          [CAS server]
    |                  |                                 |
    | GET /orders      |                                 |
    |----------------->|                                 |
    |    no local Authentication yet                     |
    |<-- 302 ----------|                                 |
    |    Location: https://cas.example/cas/login         |
    |             ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    |--------------------------------------------------->|
    |                                                   | authenticate user
    |                                                   | create TGT/TGC
    |<------------------ 302 redirect ------------------|
    |    Location: https://portal.example/login/cas?ticket=ST-123
    |----------------->|                                 |
    |                  |-- HTTPS GET /cas/serviceValidate -->|
    |                  |   service=https://portal.example/login/cas
    |                  |   ticket=ST-123                  |
    |                  |<-- CAS XML Success / Failure ----|
    |                  |                                 |
    |                  | verify validation result        |
    |                  | load local account + authorities |
    |                  | create SecurityContext/session  |
    |<-- 302 clean URL-|                                 |
    | GET /orders      |                                 |
    |----------------->|                                 |
    |<-- 200 ----------|                                 |
~~~

Two distinct legs:

- **Front channel (browser):** redirects to CAS and returns to the service URL with an ST. The browser sees `ticket`, but is not the party that verifies it.
- **Back channel (server-to-server):** the application uses a `TicketValidator` to contact the **configured, trusted CAS server** and ask whether the ticket is valid **for that exact service**. Only user information from a valid validation result is used to log the user in.

When handling the callback, **never** write:

~~~java
// WRONG: ticket is browser input, not a verified username.
String user = request.getParameter("ticket");
session.setAttribute("user", user);
~~~

An `ST-...` string only has meaning after the CAS server authenticates it and returns a result over a trusted channel.

## 3. Glossary of Easily Confused “Tickets”

| Artifact | Who Creates and Holds It? | Purpose | Should Portal Treat It as a User ID? |
| --- | --- | --- | --- |
| **TGT** | Managed by CAS server; browser usually holds a TGC referencing the TGT. | Maintains the SSO session at CAS, allowing new ST requests without re-entering a password. | **No**. |
| **TGC** | Cookie issued by CAS server to browser on the CAS domain. | Browser presents the CAS cookie to identify the TGT/SSO session. | **No**. Portal has no permission to read CAS domain cookies. |
| **ST** | Issued by CAS server for an exact `service`. | Temporary proof for **one service** to call CAS and verify. | **Do not** use as local user ID/session ID. |
| **LT** | May be issued by CAS server for the login form. | Single-submission protection for submitting CAS login credentials. | Neither an ST nor a Portal session cookie. |
| **PT** | Issued by CAS server for a proxy per profile. | Downstream service verifies proxy ticket per policy. | Do not accept on an ST-only endpoint. |
| **PGT / PGTIOU** | Exchanged between CAS server and proxy service via a dedicated mechanism. | Enables a service to request PTs when performing proxying. | Not needed for basic web login flows. |
| **JSESSIONID** | Portal's Servlet container (or session store). | Maintains Portal's **own** session after ST verification. | Not a CAS ST/TGT. |

**TGT vs. ST:** One user can hold **one CAS SSO session** while receiving **many different STs** when entering multiple applications. STs are used once to establish application sessions; a live TGT/TGC allows requesting new STs.

**LT vs. ST:** If you see `LT-...` on a CAS login form, that is typically a login ticket for submitting credentials to CAS, **not** an ST that Portal is allowed to pass to `/serviceValidate`.

**Do not store STs long-term:** A verified ST should be consumed by CAS. The application uses the established `Authentication` and local session per policy, without “renewing” or replaying the ST on subsequent business requests.

## 4. Step 1 — User Requests a Protected Page

Suppose Portal receives:

~~~text
GET https://portal.example/orders
Cookie: JSESSIONID=... (no valid Authentication yet)
~~~

Spring Security inspects the request. If the resource requires authentication and the user lacks an `Authentication`, `ExceptionTranslationFilter` invokes `AuthenticationEntryPoint`. In a CAS integration, `CasAuthenticationEntryPoint` builds the CAS login URL along with a configured `service`.

Example:

~~~http
HTTP/1.1 302 Found
Location: https://cas.example/cas/login?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
Cache-Control: no-store
~~~

**Reading the URL:** The browser goes to `https://cas.example/cas/login`. `service` is Portal's callback URL, specifically:

~~~text
https://portal.example/login/cas
~~~

It is **not** the page the user wanted to view (`/orders`), unless the CAS client intentionally processes tickets at that URL. After verification, Portal can use Spring Security's `SavedRequest` to return to `/orders`.

### 4.1. Safety Rules for `service`

- The CAS server should maintain a **service registry/allowlist** of application URLs allowed to use CAS; never issue tickets to an arbitrary attacker-controlled service URL.
- The application uses a **public canonical HTTPS service URL** from trusted configuration: scheme, host, port, context path, path, and query (if any).
- The value used when calling `/serviceValidate` must match the service for which CAS issued the ticket, per server/registration matching rules.
- Never read `service` from the browser's `request.getParameter("service")` and send it for validation; doing so widens the trust boundary and risks open redirects or tenant confusion.
- Behind a reverse proxy/load balancer, ensure the external HTTPS URL is not replaced with `http://internal-node:8080/login/cas`.
- In multi-tenant setups, each service/registration requires a canonical URL and clear mapping policy; never pick a tenant from untrusted parameters.

**Remember:** Even though both the CAS URL and Portal URL contain `/login`, they are **two different hosts and two different endpoints**.

## 5. Step 2 — CAS Authenticates the User and Issues an ST

When the browser arrives at `/cas/login?service=...`:

1. CAS checks whether a ticket-granting cookie is already present; if a valid TGT/SSO session exists, CAS may skip asking for a password.
2. If no session exists, CAS prompts the user for credentials or uses the configured login mechanism (MFA, directory, external IdP, etc.).
3. The CAS server decides whether authentication succeeds and whether the service is permitted to participate in federation.
4. When eligible, CAS creates **an opaque ST** dedicated to the specified service.
5. CAS sends an HTTP redirect back to the application callback with `ticket`.

Example:

~~~http
HTTP/1.1 302 Found
Location: https://portal.example/login/cas?ticket=ST-4e8c9a
Cache-Control: no-store
~~~

The browser then requests:

~~~http
GET /login/cas?ticket=ST-4e8c9a HTTP/1.1
Host: portal.example
Cookie: JSESSIONID=...
~~~

The ticket may start with `ST-`, but **never verify validity by regex, prefix, or length**. Any string can be labeled `ST-`; only the trusted CAS server determines whether it was issued and has not been consumed or expired.

### 5.1. An ST Is an Opaque Credential

- Do not decode an ST into a username, role, or email.
- Do not use an ST as an account key or long-lived permission cache key.
- Do not log verbatim STs in access logs, APM traces, exception messages, or `Referer` headers.
- Do not forward an ST to another API as a bearer token.
- Do not use tenant A's ST to log into tenant B.
- Do not let a failed ST validation trigger creating a “temporary session” with default privileges.

### 5.2. Ticket Lifetime and One-Time Semantics

The CAS protocol specifies that an ST:

1. **Is valid only for the service** designated when CAS issued it.
2. **Is valid for only one verification attempt**; CAS must invalidate the ticket after a validation attempt, **regardless of whether validation succeeds or fails**.
3. Should expire quickly if not verified.

Therefore, if Portal calls CAS validation with the **wrong service**, the ticket may already have been consumed; correcting the service and **retrying the exact same ticket** is not a safe recovery plan. The user must start a new CAS login flow to obtain a new ST.

If the connection times out after sending the request, the application cannot know whether CAS already consumed the ST; never assume the ticket is still valid and never grant `Authentication` on your own.

## 6. Step 3 — Callback Receives the ST, Not Yet Authenticated

`CasAuthenticationFilter` listens on the callback URL, typically `/login/cas` by default. When the browser presents the ST via the `ticket` parameter, the filter creates an **authentication request** containing the ST credential and hands it to `AuthenticationManager` / `CasAuthenticationProvider`.

~~~text
GET /login/cas?ticket=ST-4e8c9a
         |
         v
CasAuthenticationFilter
  -> CasServiceTicketAuthenticationToken (unauthenticated)
         |
         v
AuthenticationManager / ProviderManager
         |
         v
CasAuthenticationProvider
  -> TicketValidator (server-to-server)
         |
         v
CAS /serviceValidate
         |
         v
Validated Assertion + CAS username
         |
         v
Load local UserDetails / GrantedAuthority
         |
         v
CasAuthenticationToken (authenticated)
         |
         v
SecurityContextRepository + local session
~~~

**In Spring Security 6.3**, the token name used in Javadoc is `CasServiceTicketAuthenticationToken`. When reading older documentation, you may encounter descriptions/XML snippets from prior versions; cross-check the API source against your active dependency tree.

Note: **The browser does not call `/serviceValidate` directly to log in to Portal**. If JavaScript/the browser were allowed to validate and send a username back to the server, an attacker could alter the username or forge the response. Verification must happen on the Portal server side, over a Portal-controlled HTTPS connection to CAS.

## 7. Step 4 — Portal Calls CAS to Validate the Ticket Over Back Channel

### 7.1. CAS 2.0 Endpoint

~~~text
GET https://cas.example/cas/serviceValidate
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    &ticket=ST-4e8c9a
~~~

Two required parameters:

| Parameter | Who Supplies It? | Key Check |
| --- | --- | --- |
| `service` | **Portal server from trusted configuration**. | Must match the exact service for which CAS issued the ST. |
| `ticket` | Brought back by the browser, but **trusted only after CAS validation**. | ST matches service, unused, unexpired according to CAS. |

The `renew=true` parameter is used only when the service requires re-authentication with primary credentials rather than relying on an SSO session. If used at login, it must also be used at validation per the contract; otherwise security expectations can break.

**This connection differs from the earlier HTTP redirect:** the CAS server does not communicate the username by having the browser call Portal with a self-asserted confirmation string; **Portal actively connects to CAS** and checks the result from a fixed configured endpoint.

### 7.2. CAS Returns Success XML

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationSuccess>
        <cas:user>alice</cas:user>
    </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Key points to grasp:

- XML namespace is **`http://www.yale.edu/tp/cas`**, not a SAML2 namespace.
- `cas:user` is the username/subject reported by CAS for a **valid ST**.
- CAS 3.0 can add `cas:attributes` when using `/p3/serviceValidate` with attribute release configured. Do not assume every CAS 2.0 deployment returns the same set of attributes.
- Success at CAS establishes only **authentication identity**; order read permissions, tenants, and local accounts are Portal's responsibility.
- Usernames are not necessarily globally unique/stable across multiple CAS realms; with multi-CAS setups, bind a trusted issuer/source to the link key.

CAS 3.0 example with attributes:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationSuccess>
        <cas:user>alice</cas:user>
        <cas:attributes>
            <cas:displayName>Alice</cas:displayName>
            <cas:email>alice@example.org</cas:email>
            <cas:affiliation>staff</cas:affiliation>
        </cas:attributes>
    </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

`email` or `affiliation` is IdP-asserted data; never turn `affiliation=admin` into `ROLE_ADMIN` automatically without an explicit trust/policy mapping.

### 7.3. CAS Returns Failure XML

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationFailure code="INVALID_TICKET">
        Ticket not recognized
    </cas:authenticationFailure>
</cas:serviceResponse>
~~~

Common failure codes in the CAS protocol:

| Failure Code | Typical Meaning | Handling at SP |
| --- | --- | --- |
| `INVALID_TICKET` | ST does not exist, already used, or expired. | Do not authenticate; start a new flow if the user chooses. |
| `INVALID_SERVICE` | Validation service does not match or service is not accepted by CAS. | Fix canonical service URL/registration; do not relax whitelist. |
| `INVALID_REQUEST` | Missing parameters or invalid request. | Fix client/protocol configuration. |
| `UNAUTHORIZED_SERVICE_PROXY` | Proxy grant not permitted in the relevant configuration. | Do not switch to proxy mode arbitrarily. |
| `INTERNAL_ERROR` | CAS server encountered an internal error. | Fail closed, log error category, alert/investigate. |

Never store a ticket validation failure as an “anonymous session with USER role” to salvage UX. Return an intelligible error without leaking raw tickets or raw CAS XML to the browser.

### 7.4. CAS Protocol Versions

| CAS Endpoint | Protocol | Response | When Used |
| --- | --- | --- | --- |
| `/validate` | CAS 1.0 | Plaintext `yes\\nusername\\n` or `no\\n`. | Legacy compatibility only; no XML attributes. |
| `/serviceValidate` | CAS 2.0 | CAS XML success/failure. | Validates **service tickets**; does not accept proxy tickets as valid. |
| `/p3/serviceValidate` | CAS 3.0 | CAS XML possibly including `attributes` or other supported formats. | When IdP-released attributes are needed. |
| `/proxyValidate` | CAS 2.0/3.0 | Validates ST or PT per profile. | Only when the application genuinely supports proxying. |
| `/proxy` | CAS 2.0/3.0 | Issues proxy ticket given a valid PGT. | Not needed for direct browser SSO. |
| `/samlValidate` | CAS extension using SAML 1.1 | SAML 1.1 response via POST. | Entirely distinct from Spring `saml2Login` SAML2 Web SSO. |

**Do not upgrade to `/proxyValidate` to “fix” a rejected ST**. When allowing PTs, verify the proxy chain and `CasProxyDecider` rules; never enable `AcceptAnyCasProxy` blindly in sensitive environments.

## 8. Step 5 — Portal Creates Local Authentication and Session

When CAS returns success and `TicketValidator` verifies the result:

1. `CasAuthenticationProvider` receives the username and assertion/attributes from the CAS client.
2. The application looks up `UserDetails` or an approved identity link.
3. Computes `GrantedAuthority` based on **internal permissions** and trusted sources.
4. Creates an authenticated `CasAuthenticationToken`.
5. `CasAuthenticationFilter` saves `SecurityContext` via repository/session per configuration, applying session fixation protection.
6. Redirects away from the callback URL containing the ticket to a clean page (usually the original saved request).
7. Subsequent business requests use the local `JSESSIONID` session, **never calling CAS again with the consumed ST**.
8. The backend still checks permissions/tenant/resource ownership on every action.

~~~text
CAS returns: authenticated CAS username = alice
       |
       v
(local account link CAS source, username) -> local_user_id=104
       |
       v
Local account ACTIVE?
  no -> deny/approval
 yes -> local permissions {APP_ORDER_READ}
       |
       v
GET /orders/123
  require APP_ORDER_READ
  AND localUser.tenant == order.tenant
       |
       v
Allow / Deny
~~~

CAS authenticating an identity **does not by itself prove `alice` has ADMIN privileges** at Portal. Never assign high roles by default to every CAS principal or grant privileges merely because an account name has a trusted-looking prefix.

### 8.1. Local Session Differs from CAS SSO Session

After the ST is verified, Portal keeps its own session. CAS still holds TGT/TGC; therefore:

- Local Portal logout does not automatically destroy CAS's TGT.
- CAS logout can send SLO notifications to services if implemented, but that is a separate flow.
- A revoked Portal session must be blocked even while the CAS session still exists.
- The user may immediately SSO again if they visit a protected page while the CAS TGT remains alive.

## 9. Three Most Important Failure Modes

### 9.1. Reused Ticket — Replay

~~~text
CAS issues ST-123 for https://portal.example/login/cas
Portal attempt 1: serviceValidate(ST-123, exact service) -> Success alice
Portal attempt 2: serviceValidate(ST-123, exact service) -> INVALID_TICKET
~~~

**One-time** semantics belong to the CAS protocol. Never “cache” a success response so the same ticket can be reused like a bearer token. If auth is needed across multiple APIs, use an application-issued session/access token with its own mechanism and lifecycle.

### 9.2. Wrong Service — Service Mismatch

~~~text
CAS issued ticket for:
  https://portal.example/login/cas

Portal mistakenly validates with:
  http://portal-internal:8080/login/cas
~~~

The result may be `INVALID_SERVICE` or validation failure. In clusters behind a reverse proxy, configure a **public service URL** so both redirect and back-channel use the exact same value. Never “fix” this by disabling service checks at CAS or creating an unbounded whitelist.

### 9.3. CAS Unresponsive — Timeout/HTTPS Failure

If Portal calls CAS and encounters a timeout, untrusted TLS certificate, or HTTP 5xx:

- No trusted `authenticationSuccess` → **do not create `Authentication`**.
- CAS may already have consumed the ST even though Portal received no response; do not loop indefinitely retrying the same ST.
- Record an error metric and instruct the user to try logging in again from the beginning once the system recovers.
- Set connect/read timeouts and response size limits; avoid exhausting all servlet threads when CAS is slow.
- Never fall back to `request.getParameter("username")` or an unproven prior identity in the session.

## 10. Networking, TLS, and Service URL Configuration

### 10.1. HTTPS Rules

- `CAS /login`: browser goes to the official, administratively trusted HTTPS URL.
- `CAS /serviceValidate`: Portal server connects over HTTPS, verifying the certificate chain and hostname using an appropriate trust store.
- `Portal service`: public HTTPS callback matching the CAS registration.
- Do not disable certificate checks with `TrustAll`, `HostnameVerifier(alwaysTrue)`, or CAS client flags skipping `SSLValidation`.
- If using mTLS/internal CA, register the CA certificate in the proper trust store; **never skip TLS verification** to bypass errors.
- Never read the CAS validation URL from a query parameter or ticket contents; doing so creates SSRF/identity-switching vulnerabilities.

### 10.2. A Correct Illustrative URL Set

~~~text
CAS base URL:
  https://cas.example/cas

CAS login:
  https://cas.example/cas/login

CAS CAS2 validation:
  https://cas.example/cas/serviceValidate

Portal canonical service URL:
  https://portal.example/login/cas

Browser redirect:
  https://cas.example/cas/login
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas

Server validation:
  https://cas.example/cas/serviceValidate
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    &ticket=ST-4e8c9a
~~~

All URLs above are examples using the `.example` domain, not live endpoints. In deployment, register the real Portal service on CAS and supply valid certificates/CAs.

### 10.3. Protecting the Ticket in the URL

Even though an ST is short-lived and single-use, it remains a sensitive credential before validation:

- HTTPS from CAS to Portal.
- `Referrer-Policy: no-referrer` or a strict policy on callbacks/responses containing a ticket.
- Do not load third-party assets or run analytics scripts on the callback URL while `ticket` is still present.
- After validation, redirect to a page **without the ticket**.
- Configure ingress/access logs not to store the ticket query parameter or to mask tokens properly.
- `Cache-Control: no-store` for sensitive callbacks/statuses.
- Never put tickets in emails, third-party redirect queries, metrics labels, or exception messages.
- Do not pass the ticket via `window.location` to an HTML page manipulable by the user.

**Caution:** Browsers retain navigation history/referrers; “single-use” narrows the abuse window but does not replace credential-exposure controls.

## 11. Standalone Java 17: Simulating Service-Bound Tickets and One-Time Consumption

The following example is a **completely offline program** with no real CAS server. It simulates the mandatory rules: a ticket is bound to the exact service and consumed **even when validation fails**. Use it to understand the sequence; **never use a simulation as a production authenticator**.

### 11.1. File `CasTicketLifecycleDemo.java`

~~~java
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

public class CasTicketLifecycleDemo {

    private static final String PORTAL =
        "https://portal.example/login/cas";
    private static final String OTHER =
        "https://other.example/login/cas";

    record Ticket(String service, String username) { }

    private final Map<String, Ticket> issued = new HashMap<>();
    private final Set<String> consumed = new HashSet<>();

    void issue(String ticket, String service, String username) {
        issued.put(ticket, new Ticket(service, username));
    }

    String validate(String ticket, String presentedService) {
        Ticket expected = issued.get(ticket);
        if (expected == null || !consumed.add(ticket)) {
            return "INVALID_TICKET";
        }

        // Ticket is consumed immediately on the validation attempt.
        if (!expected.service().equals(presentedService)) {
            return "INVALID_SERVICE";
        }
        return "SUCCESS:" + expected.username();
    }

    public static void main(String[] args) {
        CasTicketLifecycleDemo cas = new CasTicketLifecycleDemo();
        cas.issue("ST-A", PORTAL, "alice");
        cas.issue("ST-B", PORTAL, "bob");

        System.out.println("first=" +
            cas.validate("ST-A", PORTAL));
        System.out.println("replay=" +
            cas.validate("ST-A", PORTAL));
        System.out.println("wrongService=" +
            cas.validate("ST-B", OTHER));
        System.out.println("afterWrongService=" +
            cas.validate("ST-B", PORTAL));
        System.out.println("unknown=" +
            cas.validate("ST-NOT-ISSUED", PORTAL));
    }
}
~~~

### 11.2. Run and Stdout

~~~bash
javac --release 17 CasTicketLifecycleDemo.java
java CasTicketLifecycleDemo
~~~

**Exact stdout:**

~~~text
first=SUCCESS:alice
replay=INVALID_TICKET
wrongService=INVALID_SERVICE
afterWrongService=INVALID_TICKET
unknown=INVALID_TICKET
~~~

Explanation:

- `ST-A` on first attempt with exact service returns user alice.
- Next attempt with `ST-A` is no longer valid.
- `ST-B` was issued for Portal but validated with OTHER → wrong service.
- `ST-B` still cannot validate successfully after that failure, because the protocol consumed the ticket.
- An unissued ST is rejected.

**Limitations:** the simulation stores state in a `HashMap` with no cryptography, user database, TGC/TGT, ticket expiration, or HTTP. It offers no defense against a real attacker. The program only demonstrates **the rules** for designing a test suite.

## 12. Java 17 Server-to-Server: Calling `/serviceValidate` and Safely Parsing CAS XML

In production, prefer a **CAS client library / Spring Security CAS** instead of building your own parser and validator. The sample below uses **pure JDK 17** to illustrate the exact point where the HTTPS call occurs and the minimum XML checks. It accepts only **fixed configured CAS validation URL and service URL**, never reading those two URLs from the browser.

### 12.1. File `CasServiceValidateClient.java`

~~~java
import java.io.ByteArrayInputStream;
import java.io.InputStream;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;

import javax.xml.XMLConstants;
import javax.xml.parsers.DocumentBuilderFactory;

import org.w3c.dom.Document;
import org.w3c.dom.Element;
import org.w3c.dom.Node;
import org.w3c.dom.NodeList;

public final class CasServiceValidateClient {

    // Example: replace with ADMIN-configured HTTPS URL.
    private static final String VALIDATION_ENDPOINT =
        "https://cas.example/cas/serviceValidate";
    private static final String SERVICE =
        "https://portal.example/login/cas";
    private static final String CAS_NS =
        "http://www.yale.edu/tp/cas";

    private CasServiceValidateClient() {
    }

    public static String verifyServiceTicket(String ticket)
            throws Exception {

        if (ticket == null || ticket.isBlank()
                || ticket.length() > 512
                || ticket.chars().anyMatch(Character::isISOControl)) {
            throw new IllegalArgumentException("Invalid ticket input");
        }

        // CAS URL and service are trusted constants; only ticket
        // comes from the browser and must be verified via CAS HTTPS.
        String query = "service=" +
            URLEncoder.encode(SERVICE, StandardCharsets.UTF_8)
            + "&ticket=" +
            URLEncoder.encode(ticket, StandardCharsets.UTF_8);

        URI uri = URI.create(VALIDATION_ENDPOINT + "?" + query);
        if (!"https".equalsIgnoreCase(uri.getScheme())) {
            throw new SecurityException("CAS must use HTTPS");
        }

        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))
            .followRedirects(HttpClient.Redirect.NEVER)
            .build();

        HttpRequest request = HttpRequest.newBuilder(uri)
            .timeout(Duration.ofSeconds(5))
            .header("Accept", "application/xml")
            .GET()
            .build();

        HttpResponse<InputStream> response = client.send(
            request, HttpResponse.BodyHandlers.ofInputStream());

        // Bound response reading; do not allocate unbounded memory for XML.
        try (InputStream body = response.body()) {
            if (response.statusCode() != 200) {
                throw new SecurityException(
                    "CAS validation HTTP status not 200");
            }

            byte[] xml = body.readNBytes(65_537);
            if (xml.length > 65_536) {
                throw new SecurityException("CAS XML too large");
            }

            return parseSuccess(xml);
        }
    }

    private static String parseSuccess(byte[] xml) throws Exception {
        DocumentBuilderFactory factory =
            DocumentBuilderFactory.newInstance();
        factory.setNamespaceAware(true);
        factory.setXIncludeAware(false);
        factory.setExpandEntityReferences(false);
        factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
        factory.setFeature(
            "http://apache.org/xml/features/disallow-doctype-decl",
            true);
        factory.setFeature(
            "http://xml.org/sax/features/external-general-entities",
            false);
        factory.setFeature(
            "http://xml.org/sax/features/external-parameter-entities",
            false);
        factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");

        Document document = factory.newDocumentBuilder().parse(
            new ByteArrayInputStream(xml));
        Element root = document.getDocumentElement();
        if (!CAS_NS.equals(root.getNamespaceURI())
                || !"serviceResponse".equals(root.getLocalName())) {
            throw new SecurityException("Not CAS serviceResponse");
        }

        Element success = directChild(root, "authenticationSuccess");
        Element failure = directChild(root, "authenticationFailure");
        if ((success == null) == (failure == null)) {
            throw new SecurityException("Ambiguous CAS response");
        }
        if (failure != null) {
            // Do not expose raw XML details or ticket to browser/logs.
            throw new SecurityException("CAS rejected service ticket");
        }

        Element user = directChild(success, "user");
        if (user == null || user.getTextContent().isBlank()) {
            throw new SecurityException("CAS response without user");
        }
        return user.getTextContent().trim();
    }

    private static Element directChild(Element parent, String name) {
        Element found = null;
        NodeList nodes = parent.getChildNodes();
        for (int i = 0; i < nodes.getLength(); i++) {
            Node node = nodes.item(i);
            if (node instanceof Element element
                    && CAS_NS.equals(element.getNamespaceURI())
                    && name.equals(element.getLocalName())) {
                if (found != null) {
                    throw new SecurityException("Duplicate CAS element");
                }
                found = element;
            }
        }
        return found;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            System.err.println(
                "Usage: java CasServiceValidateClient <service-ticket>");
            System.exit(2);
        }
        String user = verifyServiceTicket(args[0]);
        System.out.println("validatedUser=" + user);
    }
}
~~~

### 12.2. Running

~~~bash
javac --release 17 CasServiceValidateClient.java
java CasServiceValidateClient ST-REAL-TICKET
~~~

Because the example uses non-existent hosts `cas.example` and `portal.example`, the command only succeeds **when replacing both constants with a real test CAS environment and providing an unused ST**. Valid stdout depends on the username returned by CAS, e.g., `validatedUser=alice`; there is no fixed stdout when CAS/TLS/ticket are not provided.

**What the code does:**

- Fixed HTTPS validation endpoint, disables redirect following, and enforces connect/request timeouts.
- `service` is URL-encoded and immutable relative to browser input.
- Ticket is sent only to the CAS validation endpoint, never trusting ticket content directly.
- Bounds body size and checks HTTP status.
- Parses the CAS namespace, disallows DTD/external entities to mitigate XXE, and accepts **one** success or failure element.
- Returns the username from `cas:authenticationSuccess` only when the response passes minimum checks.

**What the code does NOT do on its own:**

- Not a complete production CAS client: lacks version negotiation, login redirect, Spring session/authentication, proxy chains, SLO, and extended response schemas.
- Does not itself check whether the ST matches the service from XML data; the **CAS server** checks this via `serviceValidate`. That requires trusting the right CAS server and TLS certificate/hostname.
- Does not provision local users/permissions or harden all HTTP ingress/headers.
- Does not replace a CAS client with hardened timeouts, telemetry, schema handling, and security updates.
- Does not accept “having a username equals admin”; authorization must be separated.

### 12.3. Do Not Trust an XML Response Based Only on HTTP Status 200

A CAS server can return **HTTP 200 containing `authenticationFailure`**. Thus status 200 only means the HTTP request completed, **not that login succeeded**. You must parse the CAS XML and accept only `authenticationSuccess` with the right namespace/format. If you get HTTP 302 to a login page, error HTML, malformed XML, TLS error, or missing user → do not grant `Authentication`.

### 12.4. Proper Retry Handling for One-Time Tickets

If a ticket entered a `serviceValidate` request but the response was lost, you cannot be sure whether CAS already consumed the ST. For browser logins, the straightforward option is to ask the user to **initiate a fresh CAS login** and receive a new ST. Never cache a username received over an untrusted connection to let subsequent requests pass without verification.

## 13. Spring Security CAS: Classes and Configuration Flow

Spring Security CAS documentation describes the following components:

| Component | Role |
| --- | --- |
| `ServiceProperties` | Holds the `service` URL (Portal callback) and renew policy. |
| `CasAuthenticationEntryPoint` | Redirects browser to `/cas/login?service=...`. |
| `CasAuthenticationFilter` | Receives `ticket` at `/login/cas` callback, creates unauthenticated token. |
| `CasServiceTicketAuthenticationToken` | Carries the ST to `AuthenticationManager`/Provider. |
| `CasAuthenticationProvider` | Calls `TicketValidator`, loads user/authorities, produces authenticated token. |
| `Cas20ServiceTicketValidator` | CAS client calling CAS `/serviceValidate` over HTTPS, parses XML. |
| `UserDetailsService` | Loads local user, status, and application-approved permissions. |
| `CasAuthenticationToken` | Completed `Authentication` from CAS validation and local authorities. |
| `SecurityContextRepository` | Saves `Authentication` in local session after success. |
| `LogoutFilter` / CAS Single Sign Out filters | Local logout/SLO is a separate concern and does not happen automatically just from logging in via CAS. |

**Spring Security CAS is not `.saml2Login()`.** If the CAS server issues SAML2 Web SSO, that is a different integration; select the matching protocol and dependencies.

### 13.1. Dependency Package

For Spring Boot 3.3.x (Spring Security 6.3.x), include the module:

dependencies {

    implementation 'org.springframework.boot:spring-boot-starter-security'

### 14.4. CasSecurityConfig.java

`src/main/java/com/example/casdemo/CasSecurityConfig.java`:

~~~java
package com.example.casdemo;

import java.util.List;
import java.util.Map;

import org.apereo.cas.client.validation.Cas20ServiceTicketValidator;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.authentication.CasAuthenticationProvider;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;
import org.springframework.security.cas.web.CasAuthenticationFilter;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.context.HttpSessionSecurityContextRepository;

@Configuration
public class CasSecurityConfig {

    @Bean
    ServiceProperties serviceProperties(
            @Value("${app.cas.service-url}") String serviceUrl) {
        if (!serviceUrl.startsWith("https://")
                || !serviceUrl.endsWith("/login/cas")) {
            throw new IllegalArgumentException(
                "CAS service must be canonical HTTPS /login/cas");
        }
        ServiceProperties properties = new ServiceProperties();
        properties.setService(serviceUrl);
        properties.setSendRenew(false);
        return properties;
    }

    @Bean
    CasAuthenticationEntryPoint casEntryPoint(
            ServiceProperties properties,
            @Value("${app.cas.login-url}") String loginUrl) {
        if (!loginUrl.startsWith("https://")) {
            throw new IllegalArgumentException("CAS login requires HTTPS");
        }
        CasAuthenticationEntryPoint entryPoint =
            new CasAuthenticationEntryPoint();
        entryPoint.setLoginUrl(loginUrl);
        entryPoint.setServiceProperties(properties);
        return entryPoint;
    }

    @Bean
    UserDetailsService localUsers() {
        // Fixed demo allowlist. Production: database,
        // account status, tenant mapping, and approval.
        UserDetails alice = User.withUsername("alice")
            .password("{noop}not-used-for-cas")
            .authorities("APP_ORDER_READ")
            .build();

        Map<String, UserDetails> allowed =
            Map.of("alice", alice);

        return username -> {
            UserDetails found = allowed.get(username);
            if (found == null) {
                throw new UsernameNotFoundException(
                    "CAS subject not linked to local account");
            }
            return found;
        };
    }

    @Bean
    CasAuthenticationProvider casProvider(
            ServiceProperties properties,
            UserDetailsService localUsers,
            @Value("${app.cas.base-url}") String baseUrl) {

        if (!baseUrl.startsWith("https://")) {
            throw new IllegalArgumentException("CAS requires HTTPS");
        }

        CasAuthenticationProvider provider =
            new CasAuthenticationProvider();
        provider.setServiceProperties(properties);
        provider.setTicketValidator(
            new Cas20ServiceTicketValidator(baseUrl));
        provider.setUserDetailsService(localUsers);

        // CAS provider-local identity, not a private key.
        provider.setKey("orders-portal-cas-provider");
        return provider;
    }

    @Bean
    AuthenticationManager casAuthenticationManager(
            CasAuthenticationProvider provider) {
        return new ProviderManager(List.of(provider));
    }

    @Bean
    CasAuthenticationFilter casAuthenticationFilter(
            AuthenticationManager casAuthenticationManager,
            ServiceProperties properties) {

        CasAuthenticationFilter filter =
            new CasAuthenticationFilter();
        filter.setAuthenticationManager(casAuthenticationManager);
        filter.setServiceProperties(properties);
        filter.setFilterProcessesUrl("/login/cas");

        // Spring Security 6.x: store SecurityContext
        // after CAS auth into the session per policy.
        filter.setSecurityContextRepository(
            new HttpSessionSecurityContextRepository());
        return filter;
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            CasAuthenticationEntryPoint entryPoint,
            CasAuthenticationFilter casFilter) throws Exception {

        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/error").permitAll()
                .anyRequest().authenticated()
            )
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint(entryPoint)
            )
            .addFilterAt(casFilter, CasAuthenticationFilter.class)
            .build();
    }
}
~~~

**How each bean works together:**

1. `ServiceProperties` holds a fixed service URL. This value is used for redirecting to CAS and for validation; it never changes based on browser `service` query params.
2. `CasAuthenticationEntryPoint` is invoked by Spring Security when a protected page requires `Authentication`. It redirects the browser to `CAS_LOGIN_URL`.
3. `CasAuthenticationFilter` handles `/login/cas` and extracts `ticket`. This callback must match the path in `CAS_SERVICE_URL`.
4. `CasAuthenticationProvider` creates CAS authentication once `Cas20ServiceTicketValidator` verifies the ST over HTTPS to `CAS_SERVER_BASE_URL + /serviceValidate`.
5. `localUsers` restricts which users may access Portal after CAS login. It **does not use a local password to verify CAS**, and grants only `APP_ORDER_READ` to `alice` in the demo.
6. `ProviderManager` wraps the CAS provider. `HttpSessionSecurityContextRepository` lets the Servlet session persist `Authentication` after the filter succeeds.
7. `.exceptionHandling(...authenticationEntryPoint(...))` ensures unauthenticated requests redirect to CAS.
8. `.addFilterAt(..., CasAuthenticationFilter.class)` places the CAS filter at Spring Security's dedicated slot.
9. The configuration does not yet include **multi-tenant identity mapping** or CAS SLO. If Portal serves multiple CAS servers, separate realm/issuer and policy instead of matching bare usernames.
10. `password("{noop}not-used-for-cas")` is dummy data for local `UserDetails`; the example **does not** recommend using `{noop}` passwords for production local login accounts. The CAS provider does not use that password for CAS authentication.

**Never do this:** replace `Cas20ServiceTicketValidator` with a validator that always returns “success” to bypass CAS errors. That turns any browser-supplied ST into a valid login.

## 15. CAS `renew`, `gateway`, and Proxying: Know Them to Avoid Breaking the Flow

### 15.1. Renew

`renew=true` at CAS `/login` tells CAS to bypass the SSO session and perform primary authentication again per profile. At `/serviceValidate`, the same option restricts acceptance to tickets issued from the user presenting primary credentials rather than only reusing an existing SSO session.

Do not enable `renew` on only one side and assume step-up has been enforced. When using MFA/step-up, understand the actual CAS server policy and test with users who already hold a TGT.

### 15.2. Gateway

`gateway=true` at `/login` allows **non-disruptive** login probing. If the browser has no SSO session, CAS can return to `service` **without a ticket**. This is a valid outcome in gateway mode, **not an empty ST allowed to count as authenticated**.

Gateway and renew have opposite meanings; never send both and rely on undefined behavior. A gateway-enabled CAS client must handle ticketless callbacks and prevent infinite redirect loops.

### 15.3. Proxying

For applications calling other services on a user's behalf, CAS supports PGT/PT and `/proxyValidate`. Proxy flows have their own trust chain; never “open” proxying just to accept more tickets. When accepting PTs, validate the proxy list against policy and accept only trusted proxies; never enable `acceptAnyProxy` by default in sensitive environments.

This lesson **focuses solely on direct service-ticket login**; proxying is an additional scope.

### 15.4. CAS SLO

CAS `/logout` ends the CAS session; the CAS server can notify services to destroy local sessions when Single Sign Out is supported. SLO configuration uses dedicated filters/session mapping and must be tested across multiple nodes.

**Do not confuse** CAS Single Sign Out with SAML2 `LogoutRequest` and `LogoutResponse`. Message types, cookies, tickets, and validators differ. Local Portal logout does not guarantee destroying the CAS TGT.

## 16. When Multiple CAS Servers or Multiple Tenants Exist

A federated application may connect to:

~~~text
CAS realm A:
  CAS base URL = https://cas-a.partner.example/cas
  service URL = https://portal.example/a/login/cas
  tenant = A

CAS realm B:
  CAS base URL = https://cas-b.partner.example/cas
  service URL = https://portal.example/b/login/cas
  tenant = B
~~~

If both CAS servers return username `alice`, never assume they represent the same person or the same local account.

Reference link key:

~~~text
ExternalIdentityKey =
    (approved_cas_realm_id,
     canonical_service_scope,
     validated_cas_username)
~~~

- `approved_cas_realm_id` comes from trusted CAS server configuration, **never from the ticket query**.
- `canonical_service_scope` is the registered service; a single CAS server may issue STs across different service scopes.
- `validated_cas_username` comes strictly from a successful validation result on the exact CAS endpoint.
- Local tenant and permissions are mapped via approved/trusted identity sources, never defaulted from username.
- If the service URL changes during host/reverse-proxy migration, perform a tested migration; never simply swap a URL and accept old tickets.
- If using dynamic routing, lock the realm/service mapping **before redirecting**, never allowing the browser callback to choose a different CAS server.

**Mix-up attack example:** the browser sends `ticket=ST-A-...&casServer=https://attacker.example`. If Portal calls a client-specified validation URL, the attacker returns `authenticationSuccess` XML containing an admin username, and the application grants improper privileges. Proper configuration **never** trusts an arbitrary server URL from the HTTP request.

## 17. Error States That Must Be Separated

| Error / Context | Symptom | Safe Handling |
| --- | --- | --- |
| No ST on callback | CAS gateway without SSO or malformed request. | Do not authenticate; handle gateway explicitly if enabled. |
| Replayed ST | CAS returns `INVALID_TICKET`. | Do not reuse; initiate a fresh CAS login. |
| Service mismatch | CAS returns `INVALID_SERVICE`/validation failure. | Fix canonical service URL and service registry. |
| CAS server timeout | Portal has no CAS validation result. | Fail closed; let user retry a fresh flow. |
| Wrong TLS trust/hostname | `SSLHandshakeException`/HTTPS failure. | Fix trust store/certificate; never disable validation. |
| CAS HTTP 200 with XML failure | HTTP succeeds, auth fails. | Do not create `Authentication`. |
| CAS HTTP 302/HTML login page | Wrong validation URL or proxy rule. | Do not follow redirects as success; inspect endpoint. |
| Invalid XML/DOCTYPE/XXE | Parser rejects payload. | Log error category and block; never fall back to request username. |
| CAS user has no local link | CAS auth succeeds but Portal is unprovisioned. | Deny/require approval; never auto-grant admin role. |
| ST leaked in access logs | Risk of capture before Portal consumes it. | Mask query, HTTPS, No-Referrer, clean redirect. |
| Reverse proxy alters host/scheme | Service sends different URL than registered on CAS. | Use canonical HTTPS service URL; configure trusted forwarded headers. |
| Callback lands on Node 2 | `SavedRequest` session differs from Node 1. | Session replication/sticky session/shared store per architecture. |
| CAS running but service registry lacks Portal | CAS blocks service or refuses ST. | Register exact service/tenant; never use allow-all regex. |
| Reused username | Local link points to wrong user. | Identity lifecycle policy, immutable ID/approved mapping if CAS supports. |
| Immediate SSO after local logout | CAS TGT/TGC still active. | Separate local logout from CAS logout/SLO, clarify UX. |

### 18.1. Definition of “Pass” for the Test Suite

- Network evidence that the **Portal server** called the right CAS host/service.
- ST accepted by CAS at most once, with no caching of auth results by ST for replay.
- No `Authentication` on CAS XML failure, network error, invalid XML, or service mismatch.
- Local account and permissions loaded from a trusted source, never trusting username/roles from HTTP queries.
- Browser ends on a clean URL; tickets are never logged.
- Multi-tenant tests do not switch CAS realm/service/identity context via browser-supplied parameters.
- Local logout, CAS logout, session timeout, and SLO are described and tested separately.

**Example limitations:** Offline Java in Section 11 **only simulates** ticket policy; HTTPS Java in Section 12 illustrates wire validation; the Spring project in Section 14 requires a real CAS server. Never treat simulation output as proof that production SSO is secure.

## 19. Self-Assessment Questions

**1. Why can't Portal just see `ticket=ST-...` and log the user in?**  
Because the browser controls query parameters. Portal must verify with a trusted CAS server over a back-channel connection.

**2. What is `service` used for?**  
Binding the ticket to the exact application/callback authorized by CAS, preventing an ST issued for elsewhere from being used at Portal.

**3. Can a ticket validated with the wrong service be resent with the right service?**  
Do not expect it to work; the CAS protocol specifies an ST is good for one validation attempt, even on failure.

**4. CAS returns HTTP 200—can you trust that the user is authenticated?**  
No. You must read `cas:authenticationSuccess` and the user data in valid XML.

**5. How does a TGT differ from an ST?**  
TGT/TGC maintain the SSO session at CAS; an ST is used once for one service for Portal to verify.

**6. In Spring Security, which class creates the redirect to CAS?**  
`CasAuthenticationEntryPoint`, using `ServiceProperties` to determine the service URL.

**7. Which class validates the ticket?**  
`CasAuthenticationProvider` invokes a `TicketValidator`, such as `Cas20ServiceTicketValidator`, connecting to CAS over HTTPS.

**8. Does CAS success automatically grant permission to read all orders?**  
No. Local accounts, tenants, and resource authorization are the application's responsibility.

**9. How does `renew=true` differ from `gateway=true`?**  
Renew requires fresh primary credentials; gateway is non-disruptive and can return without a ticket.

**10. During a CAS outage, should an ST be accepted because it “looks like the right pattern”?**  
No. Without successful validation, never grant `Authentication`.

**11. Should `spring-security-saml2-service-provider` be used for CAS service tickets?**  
No. The CAS ticket protocol uses different flows, validators, and dependencies than SAML2 Web SSO.

**12. Why do proxies/reverse proxies often cause `INVALID_SERVICE`?**  
The application sends an internal callback URL or a scheme/port/path differing from the URL CAS used to issue the ST.

**13. How is the ST used for subsequent requests after successful validation?**  
Normally the ST is not used again; Spring stores the authenticated `SecurityContext` in the local session and uses a session cookie.

**14. Does a CAS server issuing username `alice` in two realms prove it is the same person?**  
No; an explicit realm/source scope and approved account linking are required.

## 20. Production Checklist

- [ ] CAS server login URL, validation endpoint, and service URL are all governed HTTPS URLs.
- [ ] CAS service registry allowlists only valid services/callbacks, without uncontrolled wildcards.
- [ ] Canonical service URL is **identical** between the redirect and `/serviceValidate`.
- [ ] `CasAuthenticationFilter` handles the exact callback path without bypassing the provider.
- [ ] `CasAuthenticationProvider` calls a real `TicketValidator`, never faking success.
- [ ] Never trust `ticket`/`service`/`username`/`casServer` sent by the browser before validation.
- [ ] Never cache STs as bearer tokens or blindly retry them after validation/timeout.
- [ ] Parser validates the exact CAS XML namespace and blocks XXE/invalid responses.
- [ ] CAS TLS certificate/hostname are verified; internal trust stores are properly configured.
- [ ] Network connect/read timeouts, response size limits, and backoff/alerts for CAS outages are in place.
- [ ] Never log or leak STs in `Referer` URLs, metrics labels, analytics, or access logs.
- [ ] Callback redirects to a clean URL after success, without loading third-party resources before cleanup.
- [ ] Local user active state and authorities come from trusted sources, with tenant isolation enforced.
- [ ] Session fixation protection, `Secure`/`HttpOnly`/`SameSite` cookies, CSRF, and session timeouts are tested.
- [ ] CAS TGT/TGC are distinguished from local sessions, with a clear CAS Single Sign Out policy.
- [ ] If using proxy tickets, enforce proxy list validation and a dedicated trust policy.
- [ ] With multiple CAS realms/tenants, store source realm and service scope alongside username.
- [ ] Execute tests C01–C32 or equivalent in staging against a real CAS server.
- [ ] Keep Spring Security/CAS client updated with security patches and align APIs by version.
- [ ] Never use the hand-written snippet in Section 12 in place of a tested/hardened CAS client in production.

## Key Takeaway

> **A redirect carrying a ticket to Portal is only the credential handoff step. Portal must use a server-to-server HTTPS channel to call CAS and verify that the ticket matches the service, is unused, and is unexpired.** Only when CAS returns a verified authentication success result does the application map to a local account, establish a session, and grant appropriate permissions. **STs are single-use; `service` is a security binding; the browser is never the source of identity proof.**
