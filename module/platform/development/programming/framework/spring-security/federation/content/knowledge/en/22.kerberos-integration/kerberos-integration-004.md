# KerberosServiceAuthenticationProvider and Verifying Service Tickets

> **Topic:** Spring Security – federation. **Group:** Kerberos Integration. This Knowledge lesson explains how Spring Security processes HTTP SPNEGO/Negotiate with `KerberosServiceAuthenticationProvider`, using `KerberosTicketValidator` and a **service keytab** to verify a Kerberos **Service Ticket**, then loading `UserDetails` and `GrantedAuthorities` to establish an application session. The guide focuses on Java 17+, Servlet applications, and Windows Active Directory or a compatible Kerberos KDC. Integration examples target Spring Security Kerberos **2.2.x with Spring Security 6.x**; for Spring Security 7.x you must use the matching module/dependency coordinates without mixing the two version lines.

## 1. Objectives and Scope

After this lesson, learners can:

1. Distinguish `KerberosServiceAuthenticationProvider` from `KerberosAuthenticationProvider`; identify which is the **server verifying a service ticket** and which is the **client sending username/password via a Kerberos client**.
2. Describe the path from the browser receiving HTTP `401 WWW-Authenticate: Negotiate`, requesting a ticket from the **KDC**, and sending `Authorization: Negotiate ...`, to `SpnegoAuthenticationProcessingFilter` and `KerberosServiceAuthenticationProvider`.
3. Explain the relationship between **SPN** (Service Principal Name), **keytab**, **realm**, **KDC**, **TGT**, **TGS-REP**, **service ticket**, **authenticator**, **GSS-API/JAAS**, and **SecurityContext**.
4. Configure `SunJaasKerberosTicketValidator` with the **exact service principal and keytab**, instead of taking a password/ticket from an HTTP client and trusting it directly.
5. Understand that the provider receives only the **username** after ticket validation; `UserDetailsService`/internal authorization services must determine the account, tenant, disabled status, and authorities.
6. Protect the program against wrong SPNs, mismatched keytab/KVNO/etypes, expired tickets, clock skew, replay, forged tokens, unwanted NTLM fallback, unauthorized principals, session fixation, and data scope violations.
7. Transparently configure Spring `SecurityFilterChain`, `SpnegoEntryPoint`, `SpnegoAuthenticationProcessingFilter`, `KerberosServiceAuthenticationProvider`, and the session repository.
8. Read network traces accurately, run `klist`/`kvno`/`curl --negotiate` in test environments, and inspect keytabs **without logging tickets or private service keys**.
9. Distinguish **web login via SPNEGO** from **API Kerberos delegation** and other mechanisms such as CAS, SAML, and OIDC.
10. Write an integration plan and a positive/negative QA matrix verifiable in a real domain/lab.

**Core principle:** A user is authenticated **only after the server proves it can properly process the Kerberos service token with the key of a trusted SPN and receives a KDC-certified identity**. Never build an `Authentication` merely from seeing an `Authorization: Negotiate ...` string, a username string, or a token prefix.

## 2. From TGT to Service Ticket: Two Steps Not to Confuse

Kerberos has three primary actors:

| Actor | Role |
| --- | --- |
| **Client** | Browser/process running under a user's identity, holding suitable credentials/TGT |
| **KDC** | Key Distribution Center, typically comprising the Authentication Service (AS) and Ticket-Granting Service (TGS), provided by Active Directory or a Kerberos realm |
| **Service** | Spring application with a service principal like `HTTP/web.example.org@EXAMPLE.ORG` and its corresponding private key in a keytab |

Types of evidence:

- **TGT (Ticket-Granting Ticket):** issued after the user authenticates with the AS/KDC; lets the client request service tickets from the TGS without re-entering a password for each service.
- **Service Ticket / TGS ticket:** issued by the TGS for **one specific service principal**. The sensitive part of the ticket is protected with the service's key, not a user password known to the application.
- **Authenticator:** authentication data generated by the client alongside the ticket in `AP-REQ`, using the session key/timestamp proof to prove possession of the session key and prevent replay per policy.
- **SPNEGO token:** the negotiation mechanism layer inside HTTP `Negotiate` that can carry a Kerberos AP-REQ and exchange GSS tokens; the token is not a username JSON or bearer JWT.
- **Keytab:** file holding service keys/KVNO/etypes used by the app server to accept Kerberos tickets. This is a **privileged secret**, never served over HTTP, baked into public Docker images, or committed to repositories.

### 2.1. When the KDC Appears

```text
User workstation/browser          KDC                    Spring Service
      |                             |                            |
      |-- AS-REQ (if TGT needed) -->|                            |
      |<-- AS-REP / TGT ------------|                            |
      |                             |                            |
      |-- TGS-REQ for HTTP/web ---->|                            |
      |<-- TGS-REP / Service Ticket-|                            |
      |                             |                            |
      |    HTTP GET /secure         |                            |
      |--------------------------------------------------------->|
      |<--- 401 WWW-Authenticate: Negotiate ---------------------|
      |    Authorization: Negotiate <base64 SPNEGO/GSS token>    |
      |--------------------------------------------------------->|
      |                        Spring SPNEGO filter               |
      |                        Provider + JAAS/GSS acceptor       |
      |                        decrypt/check token via keytab    |
      |<--- 200 / session cookie if authorized ------------------|
```

In practice, the client may already have cached the ticket for the SPN before the request or wait for the challenge first; network ordering can vary. **The KDC does not necessarily get called each time the Spring server verifies a request**: the acceptor can use its **service keytab** and GSS/Kerberos rules locally; never interpret the absence of KDC traffic as "verification was skipped".

A client might lack a TGT, lack permission to obtain a TGS ticket, or not use browser integrated authentication, in which case no valid Negotiate ticket is sent. The server should return the defined challenge/fallback rather than accepting a plain username.

### 2.2. Service Principal Name Example

For the website `https://web.example.org/secure`, the SPN is typically:

```text
HTTP/web.example.org@EXAMPLE.ORG
```

- `HTTP` is the standard service class for HTTP Negotiate/Kerberos, not the `http://` protocol scheme.
- `web.example.org` must match the **public hostname** the client actually uses to construct the Kerberos target name, accounting for environment DNS/canonicalization.
- `EXAMPLE.ORG` is the Kerberos realm; in AD this usually aligns with the domain, though mapping rules/cross-realm trusts may exist.
- **HTTP SPNs do not directly include the `/secure` path or HTTP port** in typical builds. Do not invent `HTTP/web.example.org:8443` unless your client/KDC/mechanism is explicitly configured for that SPN format.
- `HTTP/web.example.org@EXAMPLE.ORG` differs from `HTTP/web-internal@EXAMPLE.ORG`. If the browser visits the public alias while the service only has a keytab for the backend host, validation can fail.
- With multiple aliases, register/verify the exact SPN owner/target key; **never** let one service arbitrarily claim every SPN.

**The SPN registered on the directory account and the keytab holding that account's key must stay consistent.** In Active Directory, duplicate SPNs or SPNs attached to the wrong account break ticket issuance/decryption; inspect SPNs with domain admin tools and manage them through change tickets.

## 3. What Does KerberosServiceAuthenticationProvider Actually Do?

`KerberosServiceAuthenticationProvider` resides in:

```text
org.springframework.security.kerberos.authentication
    .KerberosServiceAuthenticationProvider
```

It is a Spring `AuthenticationProvider` belonging to the Kerberos extension module. Per its official Javadoc, it:

1. Receives a `KerberosServiceRequestToken` containing a **Kerberos service ticket or SPNEGO token** from the authentication manager.
2. Delegates to `KerberosTicketValidator` to check the token contents using JAAS/GSS compatible with the JDK/OS.
3. If the ticket can be validly accepted for the service, obtains the **principal name** from the `KerberosTicketValidation` result.
4. Uses `UserDetailsService` to look up the local user and `GrantedAuthorities` because Kerberos ticket validation **does not provide application roles/permissions**.
5. May run `additionalAuthenticationChecks` per policy/provider customization.
6. Returns the authenticated `Authentication` (or throws `AuthenticationException` if unacceptable/invalid); Spring can persist it into `SecurityContext`/session according to the filter/repository.

**The provider is not an HTTP Filter**: it does not read `Authorization` headers itself, does not generate `WWW-Authenticate` challenges, and does not register URL endpoints. Those responsibilities belong to `SpnegoEntryPoint` and `SpnegoAuthenticationProcessingFilter`.

### 3.1. Layer Diagram

```text
HTTP Request from browser
     |
     v
SpnegoAuthenticationProcessingFilter
  reads Authorization: Negotiate <token>
  Base64-decodes per SPNEGO handling
  creates KerberosServiceRequestToken
     |
     v
AuthenticationManager / ProviderManager
     |
     v
KerberosServiceAuthenticationProvider
     |
     +-- KerberosTicketValidator
     |     SunJaasKerberosTicketValidator
     |       servicePrincipal = HTTP/web.example.org@EXAMPLE.ORG
     |       keyTabLocation   = file:/run/secrets/http-service.keytab
     |       JAAS + GSS acceptSecContext()
     |       => authenticated Kerberos principal
     |
     +-- UserDetailsService
     |       local account lookup
     |       account status + GrantedAuthorities
     |
     v
Authenticated KerberosServiceRequestToken
     |
     v
SecurityContextRepository + SessionAuthenticationStrategy
     |
     v
Authorization rules and application data access
```

Underneath, JDK `java.security.jgss`/JAAS performs the Kerberos cryptographic validation. Never write a custom `Base64.decode(token)` to read a username at the start of the byte array instead of using the provider.

### 3.2. Comparison with KerberosAuthenticationProvider

| Property | `KerberosServiceAuthenticationProvider` | `KerberosAuthenticationProvider` |
| --- | --- | --- |
| Role | **Service acceptor** verifying incoming tickets/SPNEGO | **Kerberos client** authenticating username/password via `KerberosClient` |
| Input | `KerberosServiceRequestToken` | Username/password authentication request per API |
| Core component | `KerberosTicketValidator` | `KerberosClient`, such as `SunJaasKerberosClient` |
| Service secret | Keytab/SPN to decrypt/accept tickets | Client credentials per flow |
| Common usage | Browser Integrated Windows Authentication HTTP Negotiate | Form/credential-based authentication against a Kerberos backend |
| Output | Kerberos principal + local UserDetails authorities | Principal + authorities per service user mapping |
| Emits HTTP challenge? | No; filter/entry point handles that | No; web chain/controller decides flow |

**Do not swap the service provider for the username/password provider just because both contain the word "Kerberos".** This lesson focuses on **service ticket verification**, requiring `KerberosServiceAuthenticationProvider` + `KerberosTicketValidator`.

## 4. SpnegoAuthenticationProcessingFilter, SpnegoEntryPoint, and HTTP Boundaries

### 4.1. Challenge Response

When a user GETs a protected URL without authentication, `SpnegoEntryPoint` typically emits:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Negotiate
```

Only a browser with integrated authentication support and matching allowlist policy looks up Kerberos credentials/tickets and retries:

```http
GET /secure HTTP/1.1
Host: web.example.org
Authorization: Negotiate YIIB...example-base64...
```

The `YIIB...` string is only a placeholder. Real tokens contain sensitive protocol data and must not appear in documentation or logs. The header **is not** valid proof until the token has been accepted by the provider/JAAS.

### 4.2. The Filter Does Not Inspect Tickets Itself

`SpnegoAuthenticationProcessingFilter` reads the Negotiate Authorization header, constructs `KerberosServiceRequestToken`, and calls `AuthenticationManager`. It does not decide identity or groups itself. In Spring Security Kerberos 2.2.x, notable filter options include:

- `setAuthenticationManager(...)`: must be configured with a manager containing the service provider.
- `setSecurityContextRepository(...)`: persists the context after successful authentication; Javadoc 2.2 notes that by default it **does not save SecurityContext**.
- `setSessionAuthenticationStrategy(...)`: invoked on new authentication success; can enforce session fixation protection.
- `setSkipIfAlreadyAuthenticated(...)`: defaults to `true`, skipping negotiate when the request is already authenticated via an app session; relates to permission changes and reauthentication policy.
- `setStopFilterChainOnSuccessfulAuthentication(...)`: defaults to `false`, allowing the request to continue through remaining filters after success.
- `setFailureHandler(...)`: handles errors safely; avoid logging raw tokens or causing infinite login loops.

Do not attach the Filter to **both the Spring Security chain and Servlet Filter auto-registration**, causing the same request to process the Negotiate header twice. For custom filters, instantiate inside the chain configuration or disable auto-registration as Boot permits.

### 4.3. SPNEGO Is a Negotiation Mechanism; Not Every `Negotiate` Is Guaranteed to Be Kerberos

SPNEGO can negotiate mechanisms depending on client/KDC/policy. In AD environments, browser setups sometimes fall back to NTLM. **Do not assume every header prefixed with `Negotiate` holds a valid Kerberos AP-REQ**, and never silently accept NTLM if policy permits only Kerberos. Verify the negotiated mechanism at the JAAS/GSS/provider layer and domain security rules; enable auditing if unexpected NTLM fallback occurs.

When a browser lacks a TGT or the site is outside Integrated Authentication policy, the browser may prompt for login, try another scheme, or omit the token. Never work around this with `permitAll("/secure/**")` or skipping verification to quiet UI errors.

## 5. KerberosTicketValidator, JAAS, and Keytabs

### 5.1. Interface Decoupling the Provider from Validation Logic

`KerberosTicketValidator` is the abstraction used by the provider to verify tokens. The common implementation on Oracle/OpenJDK is `SunJaasKerberosTicketValidator`, in package:

```java
org.springframework.security.kerberos.authentication.sun
    .SunJaasKerberosTicketValidator
```

Some other JDK environments have their own GSS/Kerberos implementations; do not treat the SunJaas implementation as universal across all runtimes. Check JDK vendor, system properties, and the compatible native Kerberos/GSS provider.

Per Spring Kerberos Javadoc, key settings include:

| Property | Meaning | Guidance |
| --- | --- | --- |
| `setServicePrincipal(String)` | SPN the app accepts | `HTTP/web.example.org@EXAMPLE.ORG`, matching keytab |
| `setKeyTabLocation(Resource)` | Source file holding service keys | Prefer `file:/run/secrets/http-service.keytab`, never bake into image |
| `setDebug(boolean)` | JAAS/Kerberos debugging | `false` in production; enable only temporarily in staging |
| `setRefreshKrb5Config(boolean)` | Reloads `krb5.conf` before login per implementation | Do not change runtime keytab/realm policy untested |
| `setHoldOnToGSSContext(boolean)` | Retains GSS security context for follow-up GSS ops | Disposed by default; change only with an explicit use case |
| `setMultiTier(boolean)` | Multi-tier/Kerberos delegation mode | Leave off for basic web authentication |
| `setRealmName(String)` | Application realm name when needed | Never mix client/tenant realms arbitrarily |

**A keytab file is a secret.** Do not commit `.keytab`, upload it to Sheets, log its bytes, or serve it as a static resource. Spring's `classpath:` Resource may fail to act as a file path for JAAS on some runtimes; docs suggest `file:` paths for real deployments protected via OS/k8s Secret mounts.

### 5.2. Why Must the Exact Key Be Present?

The KDC encrypts the service-bound portion of the ticket using the target principal's key. The service needs the matching key to decrypt/verify and recover the client principal via the Kerberos AP exchange. If operators configure:

```text
Expected SPN: HTTP/web.example.org@EXAMPLE.ORG
Keytab only:  HTTP/legacy.example.org@EXAMPLE.ORG
```

then tickets issued for `HTTP/web.example.org` cannot be accepted, even if the user holds a valid TGT and the KDC is healthy. Similarly, an older keytab whose **KVNO** no longer matches after a service account password change, or an incompatible encryption type, causes decryption to fail.

**Do not "fix" this by using an arbitrary domain controller keytab or a user's key.** The service must use a least-privilege managed identity restricted to the exact public SPN.

### 5.3. KVNO, Encryption Type, and Rotation

- **KVNO** (Key Version Number) selects the matching key version between a Kerberos ticket and keytab. When the service principal key changes, the KDC issues tickets with the new KVNO.
- **Encryption types (etypes)** across ticket, keytab, JDK, and KDC must align; modern policy favors AES and retires weak etypes per organizational security standards.
- **Rotation** requires coordinating the KDC/AD service account, new keytab, old ticket lifetimes, multi-node rollouts, replay caches, and acceptable key versions. Never swap a keytab on one node before knowing which key version clients will receive tickets under.
- After rotation, test both new tickets and in-flight old tickets per policy. Never retain a compromised key in a keytab "for extra overlap".
- Never grant domain admin privileges to an HTTP service account; a keytab holds secrets capable of impersonating the service within that principal's scope.

**When a new keytab fails to make SPNEGO work**, inspect the SPN owner, KVNO, etype, realm, file permissions, and JAAS validator cache/restart rather than disabling encryption verification.

## 6. Spring Security Kerberos 6.x/7.x: Correct Version Dependencies

Because the Kerberos extension changed Maven coordinates when targeting Spring Security 7.x, pick **one single version line**:

| Platform | Kerberos Maven Module | Notes |
| --- | --- | --- |
| Spring Boot 3.x, Spring Security 6.5.x | `org.springframework.security.kerberos:spring-security-kerberos-core:2.2.0` and `org.springframework.security.kerberos:spring-security-kerberos-web:2.2.0` | Extension 2.2.0 line, Jakarta Servlet, Java 17+ |
| Spring Security 7.1.x / Spring Framework 7.x | `org.springframework.security:spring-security-kerberos-core` and `org.springframework.security:spring-security-kerberos-web` matching 7.1.x | Group coordinates changed; use compatible Boot/framework/BOM |

## 7. Lab: Preparing KDC, SPN, Keytab, and HTTPS

Sample environment:

```text
Kerberos realm:          EXAMPLE.ORG
KDC/AD Domain Controller: kdc.example.org
Public web host:         web.example.org
Service principal:       HTTP/web.example.org@EXAMPLE.ORG
Keytab path on Spring:   /run/secrets/http-web.keytab
App HTTPS URL:           https://web.example.org/secure
Backend app:             http://spring-backend:8080
```

Prerequisites:

1. A domain admin/Kerberos operator creates or confirms the service account and **registers the SPN exactly once** for the public FQDN.
2. A keytab is delivered via a secure secret mechanism containing the right principal, KVNO, and etypes. The service process has **read** permission while regular users do not.
3. The KDC/AD realm and DNS are reachable from the client; the browser has an Integrated Authentication policy for `web.example.org`.
4. The Linux/Windows Spring JVM has Kerberos configuration (`krb5.conf` or OS config), DNS/KDC reachability, and clock sync/NTP.
5. Browser→web host uses valid HTTPS; the proxy does not alter `Authorization: Negotiate`/`WWW-Authenticate`, unless the proxy intentionally acts as the Kerberos acceptor itself.
6. The KDC and Spring host share synchronized timezone/UTC clocks; ticket replay cache and principal mapping follow security policy.
7. The test environment has user `alice@EXAMPLE.ORG` **provisioned** in the Kerberos realm along with a matching internal user/role mapping.

### 7.1. Inspecting Keytab Configuration Safely

On Linux MIT Kerberos, with authorized access on the host **holding the keytab**:

```bash
klist -k -t -e /run/secrets/http-web.keytab
```

This lists the keytab's principals/KVNOs/etypes; **it does not print key bytes**. Still, principal names are operational metadata that can be sensitive, so do not paste full output into public tickets. Commands may vary on Windows/Heimdal; check installed tools.

Use domain admin tooling to check SPNs in AD (e.g., on Windows):

```powershell
setspn -Q HTTP/web.example.org
setspn -X
```

- `-Q` checks which account an SPN points to.
- `-X` searches for duplicate SPNs within the tool's permissions/scope.
- Do not run `setspn -A`/`-S` from a README to modify a production directory without change approval.
- **Do not export passwords/keytabs into logs** or send them to web browsers for testing.

To check TGS tickets from a client machine that already holds a TGT:

```bash
klist
kvno HTTP/web.example.org@EXAMPLE.ORG
klist
```

These commands are meaningful only inside a configured Kerberos realm; `kvno` requires an active account and valid ticket issuance. No fixed stdout is provided since KDC/DNS/realm/OS differ. Running `kinit -k` with a keytab on a service host is a sensitive service-account test only for authorized operators following policy; **it is not required for browser SPNEGO login to work**.

### 7.2. What Must the Reverse Proxy Do?

When HTTPS terminates at ingress/LB:

```text
Browser HTTPS web.example.org:443
      |
      | Authorization: Negotiate <token>
      v
Ingress / Reverse Proxy
      |
      | forwarded header, Host and target path preserved
      v
Spring Security / SpnegoAuthenticationProcessingFilter
      |
      | JAAS validates AP-REQ for HTTP/web.example.org
      v
Authentication + app SecurityContext
```

- The browser requests a service ticket for the **public host `web.example.org`**, not the container name `spring-backend`.
- Spring's keytab must contain the key for that public SPN.
- Ingress must **preserve** `Authorization: Negotiate` and pass `401 WWW-Authenticate: Negotiate` back to the browser.
- Never let a reverse proxy run a different authentication mechanism and forward an unprotected `X-Remote-User` to the app; if the proxy is the acceptor, switch cleanly to trusted preauthentication over a private network channel.
- The browser HTTPS/TLS server certificate differs from the Kerberos service keytab; both require protection yet serve separate functions.
- Never trust client-supplied `X-Forwarded-Host` headers to dynamically select an SPN or grant access to another tenant.
- If using hostname aliases/CNAMEs, verify how browsers canonicalize SPNs and how the KDC maps them; never change DNS alone expecting an old keytab to match automatically.

## 8. Spring Boot 3.x + Kerberos 2.2.x Configuration Example

### 8.1. `application.yml` File

```yaml
server:
  port: 8080
  forward-headers-strategy: framework
  servlet:
    session:
      cookie:
        secure: true
        http-only: true
        same-site: lax

app:
  kerberos:
    service-principal: "HTTP/web.example.org@EXAMPLE.ORG"
    keytab: "/run/secrets/http-web.keytab"
```

This example assumes placement behind a trusted HTTPS ingress. `forward-headers-strategy` is safe only if the proxy strips client-supplied forwarded headers and re-sets them accurately. On plain HTTP localhost without a proxy, `secure=true` cookies might not be sent; use staging HTTPS rather than disabling production TLS. Never put keytab bytes or KDC passwords in YAML.

### 8.2. SecurityFilterChain, Ticket Validator, and Provider

File `src/main/java/com/example/kerberos/KerberosSecurityConfig.java`:

```java
package com.example.kerberos;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.FileSystemResource;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.kerberos.authentication.KerberosServiceAuthenticationProvider;
import org.springframework.security.kerberos.authentication.sun.SunJaasKerberosTicketValidator;
import org.springframework.security.kerberos.web.authentication.SpnegoAuthenticationProcessingFilter;
import org.springframework.security.kerberos.web.authentication.SpnegoEntryPoint;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.session.ChangeSessionIdAuthenticationStrategy;
import org.springframework.security.web.authentication.www.BasicAuthenticationFilter;
import org.springframework.security.web.context.HttpSessionSecurityContextRepository;
import org.springframework.security.web.context.SecurityContextRepository;

@Configuration
public class KerberosSecurityConfig {

    @Bean
    SunJaasKerberosTicketValidator kerberosTicketValidator(
            @Value("${app.kerberos.service-principal}") String spn,
            @Value("${app.kerberos.keytab}") String keytabPath) {

        SunJaasKerberosTicketValidator validator =
            new SunJaasKerberosTicketValidator();
        validator.setServicePrincipal(spn);
        validator.setKeyTabLocation(new FileSystemResource(keytabPath));
        validator.setDebug(false);
        return validator;
    }

    @Bean
    UserDetailsService users() {
        // LAB ONLY: username verified by the Kerberos acceptor.
        // Real production uses directory/internal account+tenant policy.
        return new InMemoryUserDetailsManager(
            User.withUsername("alice@EXAMPLE.ORG")
                .password("{noop}not-used-for-spnego")
                .roles("REPORT_READER")
                .build());
    }

    @Bean
    KerberosServiceAuthenticationProvider serviceProvider(
            SunJaasKerberosTicketValidator validator,
            UserDetailsService users) {

        KerberosServiceAuthenticationProvider provider =
            new KerberosServiceAuthenticationProvider();
        provider.setTicketValidator(validator);
        provider.setUserDetailsService(users);
        return provider;
    }

    @Bean
    SecurityContextRepository securityContextRepository() {
        return new HttpSessionSecurityContextRepository();
    }

    @Bean
    SecurityFilterChain webSecurity(
            HttpSecurity http,
            KerberosServiceAuthenticationProvider provider,
            SecurityContextRepository contextRepository)
            throws Exception {

        SpnegoAuthenticationProcessingFilter spnegoFilter =
            new SpnegoAuthenticationProcessingFilter();

        spnegoFilter.setAuthenticationManager(
            new ProviderManager(provider));

        // In Spring Security 6, custom filters must specify
        // where to save context; by default the Spnego filter does not save.
        spnegoFilter.setSecurityContextRepository(contextRepository);
        spnegoFilter.setSessionAuthenticationStrategy(
            new ChangeSessionIdAuthenticationStrategy());
        spnegoFilter.setSkipIfAlreadyAuthenticated(true);

        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error").permitAll()
                .requestMatchers("/secure", "/secure/**")
                    .hasRole("REPORT_READER")
                .anyRequest().authenticated())
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint(new SpnegoEntryPoint()))
            .securityContext(context -> context
                .securityContextRepository(contextRepository))
            .authenticationProvider(provider)
            .logout(logout -> logout
                .logoutUrl("/logout")
                .invalidateHttpSession(true)
                .clearAuthentication(true));

        // Do not declare a @Bean for Spnego Filter outside the chain:
        // avoids Boot auto-registering an extra Servlet Filter.
        http.addFilterBefore(
            spnegoFilter, BasicAuthenticationFilter.class);
        return http.build();
    }
}
```

**What does this configuration mean?**

- `SunJaasKerberosTicketValidator` uses the app's keytab+SPN to accept incoming Kerberos service tokens via JAAS/GSS, never treating the `Authorization` header as an API key.
- `KerberosServiceAuthenticationProvider` receives the validated principal from the validator and uses `UserDetailsService` to look up the user/authorities. If a Kerberos user lacks a local account, **do not grant default roles to all domain users**.
- `ProviderManager(provider)` ensures the SPNEGO filter calls the service provider; `http.authenticationProvider(provider)` also registers it with the Spring chain for compatible authentication paths.
- `SpnegoEntryPoint` emits the Negotiate challenge. If a form/LDAP fallback is needed, build a separate design with explicit failover policy; this example **illustrates Negotiate only**.
- `securityContextRepository` is shared between the SPNEGO filter and `HttpSecurity` for consistent persistence.
- `ChangeSessionIdAuthenticationStrategy` reduces session fixation risk upon new authentication. Real configs can add concurrent-session controls and logout/revocation as needed.
- `setSkipIfAlreadyAuthenticated(true)` avoids re-processing tickets once the local app session is authenticated. **This does not mean the KDC must be called on every request**, and it makes stale authorities a risk requiring a dedicated refresh/revocation policy.
- `hasRole("REPORT_READER")` requires local authority `ROLE_REPORT_READER`. It is not a built-in role carried by the Kerberos ticket; the lab `UserDetailsService` assigns it.
- Do not disable CSRF globally to accommodate Negotiate; cookie/session-authenticated POST actions still need proper CSRF protection.
- A TLS terminator may sit in front, yet the JVM must be provisioned with the keytab for the **public SPN**; never configure the principal for a backend hostname users never access.
- All imports belong to Spring Security Servlet/Jakarta-compatible 6.x and Kerberos extension 2.2.x. If targeting Spring Security 7.x, use 7.x module coordinates and APIs and run matching compile/integration tests.

**Important note:** In-memory user `alice@EXAMPLE.ORG` is strictly a fixture. Real Kerberos principal strings may carry casing/realm formatting exactly as returned by the GSS provider; measure in a test environment, normalize via controlled mapping, and look up accounts by immutable directory ID when appropriate. Never rely on `String.toLowerCase()` or stripping `@REALM` indiscriminately to merge accounts across domains/tenants.

## 9. Browser Integrated Authentication and Testing from a Client with a TGT

A domain-joined browser can use Kerberos automatically if:

- The target site belongs to the Integrated Authentication zone/allowlist (org-configured Chrome/Edge/Firefox policy).
- The user already holds a TGT or can acquire valid credentials.
- DNS/SPN/realm mappings match.
- The HTTP 401 Negotiate challenge reaches the browser.
- The client network can reach the KDC to request a ticket (or already caches a valid ticket).
- The TLS endpoint is trusted by the browser without hostname redirects unexpectedly switching the SPN.

### 9.1. Observing the Handshake

Use DevTools Network in a **test environment**, but **never copy `Authorization: Negotiate ...`** or session cookies into tickets/logs. Normal trace:

```text
1. GET https://web.example.org/secure
   => HTTP 401
      WWW-Authenticate: Negotiate

2. GET https://web.example.org/secure
   Authorization: Negotiate [redacted]
   => HTTP 200 if user has ROLE_REPORT_READER
      or 403 if Kerberos is valid but app permissions are insufficient.
```

Note that multi-step GSS negotiation can involve several header/status exchanges; the round-trip count is not fixed. If a final 401 occurs, distinguish among: browser didn't send a ticket, token was rejected, keytab mismatch, user details lookup failure, or authenticated session wasn't saved.

### 9.2. Command-Line Tools with a Valid Ticket

On a Linux/macOS host with Kerberos/curl SPNEGO support and a **test user's** TGT:

```bash
klist
curl --negotiate -u : -i https://web.example.org/secure
```

- `--negotiate` instructs curl to use GSS Negotiate.
- `-u :` triggers HTTP auth negotiation in many curl builds without sending an actual password.
- Never pass `-k`/`--insecure`, which disables TLS verification of the web host.
- Check `curl -V` for GSS-API/SSPI support; not all builds include Kerberos.
- `klist`/`kvno` reflect only the client's ticket cache/realm; they do not replace verifying the keytab and validator on the JVM service.
- Target a valid test realm/host; never run against unapproved production endpoints.

**Never print raw Negotiate tokens via `curl -v` into public logs.** If detailed tracing is needed, restrict it to a test environment with redaction and record only status, request ID, and verified principal.

## 10. Standalone Java 17: Separating Ticket Verification from Authorization

This example **does not verify a real Kerberos ticket**; that must be handled by JAAS/GSS and `KerberosTicketValidator`. It simulates only the **policy layer after cryptographic verification succeeds** to show that a user with a valid Kerberos principal must still be verified as an **active account in the right realm with the right application permissions**.

Create `KerberosServiceDecisionDemo.java`:

```java
import java.util.Map;
import java.util.Set;

public final class KerberosServiceDecisionDemo {

    record VerifiedIdentity(
        String clientPrincipal,
        String acceptedServicePrincipal,
        boolean ticketValidated
    ) { }

    record Account(boolean active, Set<String> roles) { }

    private static final String EXPECTED_SERVICE =
        "HTTP/web.example.org@EXAMPLE.ORG";
    private static final String EXPECTED_REALM =
        "EXAMPLE.ORG";

    private static final Map<String, Account> ACCOUNTS = Map.of(
        "alice@EXAMPLE.ORG",
        new Account(true, Set.of("REPORT_READER")),
        "bob@EXAMPLE.ORG",
        new Account(true, Set.of("EMPLOYEE")),
        "disabled@EXAMPLE.ORG",
        new Account(false, Set.of("REPORT_READER"))
    );

    static String decision(VerifiedIdentity identity) {
        if (identity == null || !identity.ticketValidated()) {
            return "DENY_UNVERIFIED";
        }

        if (!EXPECTED_SERVICE.equals(
                identity.acceptedServicePrincipal())) {
            return "DENY_SERVICE";
        }

        String client = identity.clientPrincipal();
        if (client == null
                || !client.endsWith("@" + EXPECTED_REALM)) {
            return "DENY_REALM";
        }

        Account account = ACCOUNTS.get(client);
        if (account == null || !account.active()) {
            return "DENY_ACCOUNT";
        }

        if (!account.roles().contains("REPORT_READER")) {
            return "DENY_ROLE";
        }

        return "ALLOW";
    }

    public static void main(String[] args) {
        System.out.println("valid=" + decision(
            new VerifiedIdentity(
                "alice@EXAMPLE.ORG", EXPECTED_SERVICE, true)));

        System.out.println("unverified=" + decision(
            new VerifiedIdentity(
                "alice@EXAMPLE.ORG", EXPECTED_SERVICE, false)));

        System.out.println("wrongService=" + decision(
            new VerifiedIdentity(
                "alice@EXAMPLE.ORG",
                "HTTP/other.example.org@EXAMPLE.ORG", true)));

        System.out.println("wrongRealm=" + decision(
            new VerifiedIdentity(
                "alice@EVIL.EXAMPLE", EXPECTED_SERVICE, true)));

        System.out.println("missingAccount=" + decision(
            new VerifiedIdentity(
                "charlie@EXAMPLE.ORG", EXPECTED_SERVICE, true)));

        System.out.println("disabled=" + decision(
            new VerifiedIdentity(
                "disabled@EXAMPLE.ORG", EXPECTED_SERVICE, true)));

        System.out.println("insufficientRole=" + decision(
            new VerifiedIdentity(
                "bob@EXAMPLE.ORG", EXPECTED_SERVICE, true)));
    }
}
```

Compile/run with **JDK 17+**, no Spring required:

```bash
javac --release 17 KerberosServiceDecisionDemo.java
java KerberosServiceDecisionDemo
```

**Deterministic** stdout:

```text
valid=ALLOW
unverified=DENY_UNVERIFIED
wrongService=DENY_SERVICE
wrongRealm=DENY_REALM
missingAccount=DENY_ACCOUNT
disabled=DENY_ACCOUNT
insufficientRole=DENY_ROLE
```

Explanation:

1. `valid=ALLOW` succeeds only because **all** conditions hold: verified ticket, right service, right realm, active account, and matching role.
2. `unverified=DENY_UNVERIFIED`: having a username without Kerberos verification grants no access.
3. `wrongService=DENY_SERVICE`: a ticket issued for another service is invalid for this application.
4. `wrongRealm=DENY_REALM`: source realm is outside allowed policy.
5. `missingAccount=DENY_ACCOUNT`: existing in the domain does not automatically provision an app account/role.
6. `disabled=DENY_ACCOUNT`: a locked user must be blocked even with an otherwise valid ticket.
7. `insufficientRole=DENY_ROLE`: successful Kerberos authentication alone is insufficient to read reports.

**Absolute limitation:** `VerifiedIdentity.ticketValidated` is a **simulated boolean used only in this console demo**. In a real application, a boolean from a browser/query/header **proves nothing** about Kerberos; evidence must originate from the provider/validator after a successful GSS accept. Never use this demo class as a production token verifier or authorization engine.

### 10.1. Extensions for Production UserDetailsService

In production, `UserDetailsService.loadUserByUsername(kerberosPrincipal)` should:

- Accept only usernames **validated by the Kerberos provider**, never from arbitrary request headers.
- Map principal+realm via a trusted source; with AD, consider linking to immutable SID/objectGUID/enterprise identity ID rather than string comparison alone.
- Reject DISABLED/DELETED accounts, and enforce per-tenant memberships/entitlements.
- Load least-privilege authorities from a backend permission store; never grant `ROLE_ADMIN` to all domain users.
- Never merge principals sharing the name `alice` across different realms like `EXAMPLE.ORG`/`PARTNER.ORG`.
- Define a cache/revocation SLA: if a user is revoked in the directory, existing app sessions could hold stale roles unless invalidated/rechecked.
- Never look up users by unverified email aliases or auto-provision uninvited users.
- Audit the verified source principal, local account ID, tenant, policy decision, and timestamp without logging Kerberos tokens.

## 11. A Valid Service Ticket Still Does Not Guarantee Access

Separate two questions:

**Authentication:** Did the service verify an `AP-REQ` carrying a valid ticket for `HTTP/web.example.org@EXAMPLE.ORG`, within its validity window, from a trusted KDC/realm, resolving to principal `alice@EXAMPLE.ORG`?

**Authorization:** Does local account `alice` hold `ROLE_REPORT_READER`, membership in tenant `org-red`, permission to view report ID 123, and compliance with internal policies?

Do not conflate these checks. A Kerberos ticket is typically **not an entitlement database**. Microsoft AD PAC/group data may be present depending on the environment, yet this simple provider uses `UserDetailsService` to load permissions; never treat arbitrary PACs or group IDs from untrusted sources as application roles.

### 11.1. Tenant Partitioning Example

One realm `EXAMPLE.ORG` can authenticate employees of both `tenant-red` and `tenant-blue`. A service ticket only proves who the KDC authenticated to the service, **not** that the user may read every tenant's data.

```text
Verified Kerberos principal = alice@EXAMPLE.ORG
Mapped local account       = acct-42
Tenant memberships:
    tenant-red -> REPORT_READER (ACTIVE)
    tenant-blue -> NONE

GET /t/tenant-red/reports/123  -> allow if report belongs to red
GET /t/tenant-blue/reports/987 -> deny
```

Enforce tenant checks at the service/repository/data layer, not just `anyRequest().authenticated()`. A valid Kerberos principal reading the wrong tenant is still a cross-tenant authorization defect.

## 12. Service Ticket Validation Is Not ID Token / SAML Assertion Verification

| Federation System | Evidence Presented to App | Primary Verification Mechanism | Identity / Permission Data |
| --- | --- | --- | --- |
| **Kerberos SPNEGO** | `Authorization: Negotiate` carrying GSS token/AP-REQ | GSS/JAAS acceptor + service principal keytab/Kerberos protocol | Client principal; app loads UserDetails/GrantedAuthorities |
| **CAS** | Opaque `ticket=ST-...` via browser callback | Backend calls CAS `/serviceValidate` with exact `service` | CAS principal/attributes, app maps roles |
| **SAML2** | XML `SAMLResponse`/Assertion | XML signature, issuer, audience, recipient, conditions, replay | NameID/attributes, app maps identity/rights |
| **OIDC** | JWT ID Token after authorization code flow | JWT signature, issuer, audience, nonce/state, expiry | `iss+sub`/claims, app maps identity/rights |
| **OAuth2 Resource Server** | Bearer access token (JWT/opaque) | Decoder/introspection, issuer, resource audience/scope | Scope/claims, app authorization |

Never send a Kerberos service ticket as `Authorization: Bearer` to a JWT API, and never feed a CAS ST or SAMLResponse into `KerberosTicketValidator`. All mechanisms produce a Spring `Authentication` in the end, yet each has distinct trust boundaries.

## 13. Replay, Time, and GSS Security Context

### 13.1. Why Clock Synchronization Matters

Kerberos relies on timestamps and ticket validity windows, typically tolerating limited clock skew across client/server/KDC. If the server clock drifts too far, tickets/authenticators are rejected even when SPN/keytab match. Use managed NTP/domain time sync; **never widen clock skew tolerances arbitrarily** or roll back system time to "make tests pass".

Failure cases:

- Ticket is before `starttime` or past `endtime`.
- Authenticator timestamp exceeds allowable clock skew.
- KDC/client/service clock/timezone drift from faulty NTP; handle consistently in UTC.
- Authenticator replay within the permitted window; the replay cache must catch duplicates per RFC 4120.

### 13.2. Replay Cache Is Not HttpSession

RFC 4120 requires servers to maintain a **replay cache** unless the application protocol provides equivalent protection under standard conditions. Across multiple nodes sharing an SPN/keytab, replay protection must be evaluated carefully: the RFC warns about multiple servers sharing a service principal **without sharing a replay cache**, unless other application protections eliminate the risk.

**Do not confuse:**

- Kerberos authenticator replay cache ≠ Spring `HttpSession`.
- `SpnegoAuthenticationProcessingFilter.setSkipIfAlreadyAuthenticated(true)` ≠ replay protection.
- TLS connection ≠ guarantee that a Negotiate token cannot be replayed to another server.
- A custom authentication result cache ≠ `GSSContext.acceptSecContext` and Kerberos replay policies.

Verify which replay cache your actual implementation/JVM/realm uses, its scope, and how HA handles it; **never assume every JDK/cluster shares a single cache by default**. If a replay cache is infeasible, perform an RFC-aligned security review rather than setting `disableReplayCache=true` to silence errors.

### 13.3. GSSContext and Multi-Step Negotiation

JDK `GSSContext.acceptSecContext` can require multiple token exchanges, emit output tokens back to the initiator, and report `isEstablished()` only once the context completes. Spring's validator handles this per library/configuration; **never alter HTTP logic to assume every Negotiate handshake consists of strictly one token**. With mutual authentication or GSS delegated credentials, deliberately manage/dispose contexts and protect delegated credentials.

`SunJaasKerberosTicketValidator.setHoldOnToGSSContext(true)` makes sense only if the application performs post-authentication GSS operations. Never retain contexts globally when only principal/roles are needed; holding unneeded secret/session handles increases resource usage and exposure.

## 14. Permissions and Safety Policies for Keytabs

A keytab is a **service-account secret**, not a harmless config file. At minimum:

1. Mount via a secrets system; never embed in JARs/Git/public Docker images.
2. Set file ownership to the service process identity with restricted read permissions; containers access only the keytab they need.
3. Avoid service accounts with domain admin rights, interactive login, or unnecessary broad privileges.
4. Protect build pipelines, filesystem backups, crash dumps, and diagnostic outputs from capturing keytabs.
5. Rotate per policy or suspected exposure; coordinate SPN/KVNO/etypes and rollout across all nodes.
6. If a keytab leaks, an attacker can impersonate the **service acceptor** within that key's scope; treat it as a security incident, rotate keys, review tickets/traffic, and do not merely delete the file on one node.
7. Audit file access/permission changes without logging keytab contents.
8. Never place a keytab on the `classpath:` of a fat JAR in production when a clean file secret mount is available; JAAS/JVM often requires a real filesystem path.
9. On the KDC/AD, audit the service account, assigned SPNs, encryption policy, and out-of-band password changes.
10. In multi-tenant SaaS, never share one keytab across realm/tenant boundaries without evaluating trust, SPNs, and authorization.

**HTTPS remains essential** even though Kerberos provides authentication: HTTP Negotiate tokens, response/payload data, cookies, and post-login requests must be protected in transit. Kerberos does not automatically enforce CSP/CSRF/Secure/HttpOnly for the application.

## 15. Integration QA Matrix for KerberosServiceAuthenticationProvider

Negative cases require a **test KDC/realm or validly issued token fixtures** when testing SPN/time/role rules, distinguishing validation errors from garbage input. Never flip one byte in a token and conclude "wrong realm" — flipping a byte breaks the signature/protocol before realm checks run.

| Test Case | Input / Setup | Expected Outcome |
| --- | --- | --- |
| **Happy path** | Domain client has TGT, browser gets ST for right SPN, right service keytab, active user+role | SPNEGO login succeeds, `/secure` allowed |
| Missing Authorization header | Browser has not negotiated yet | `401 WWW-Authenticate: Negotiate` |
| Basic header instead of Negotiate | Browser sends `Authorization: Basic` on SPNEGO-only chain | Not treated as Kerberos login |
| `Negotiate` header with garbage Base64 | No valid GSS token | Rejected, no Authentication created |
| Token with attacker-claimed username | No service ticket | Rejected |
| **SPN mismatch** | Ticket for `HTTP/other.example.org`, web app keytab | Rejected by service acceptor |
| **Wrong keytab** | File holds key for a different principal | JAAS/GSS failure; rejected |
| **Wrong KVNO** | KDC issues ticket with new KVNO, keytab still old | Decryption/validation fails |
| **Unsupported etype** | KDC/client/keytab and JDK disagree on encryption types | Fails; fix policy/keys rather than enabling weak DES/RC4 |
| **Unreadable keytab** | Process lacks file permissions/secret mount | Startup/validation fails, no insecure fallback |
| **Duplicate SPN in AD** | Two directory accounts claim the same HTTP SPN | TGS request/validation fails; fix directory registration |
| **Wrong DNS alias** | Browser uses web alias, KDC ticket SPN mismatches | Fails; fix DNS/SPN mapping |
| **Clock skew** | JVM clock out of sync with KDC/client | Rejected per Kerberos clock policy |
| Expired ticket | TGS ticket expired | Rejected; client needs a fresh valid ticket |
| Ticket/authenticator replay | Resubmitted token while replay cache/policy active | Rejected per GSS/Kerberos policy |
| NTLM fallback | Client fails to get Kerberos and tries NTLM | Rejected if app policy permits Kerberos only |
| Valid principal, missing local account | GSS succeeds yet `UserDetailsService` finds no user | Login/access denied |
| Disabled user | Valid ticket yet internal account locked/disabled | Rejected per local account policy |
| User lacks `REPORT_READER` | Kerberos succeeds, active user has another role | 403, cannot view `/secure` |
| Wrong tenant | Kerberos user Red requests Blue data | Denied by membership/resource policy |
| Browser not in Integrated Auth allowlist | Does not auto-send SPNEGO | Defined 401/fallback, no bypass |
| Ingress strips `Authorization` | Request reaches app without Negotiate header | Unauthenticated; fix proxy forwarding |
| Ingress strips `WWW-Authenticate` | Browser never gets challenge | Does not auto-send ticket; fix proxy |
| Untrusted web TLS certificate | Browser HTTPS fails | Never bypass TLS or use `curl -k` in production |
| GSS established yet app session not saved | Filter lacks repository or cookie/session store broken | Prompts per request/loops; fix persistence |
| Session fixation | Client holds pre-login session ID | Session ID rotated/protected upon new auth |
| App session active after user revoked | Authorities cached in session | Revocation policy blocks within SLA |
| Two pods with different keytabs | One pod has wrong KVNO/SPN | Intermittent login failures; sync secrets and versions |

| Untrusted Kerberos realm | Token from realm outside trust policy | Rejected, never auto-mapped by short username |
| KDC unavailable after ST issued | Existing ticket still valid, service holds keytab | May still accept token via GSS; never equate KDC outage with skipping validation |
| KDC unavailable when fetching ticket | Client lacks cached valid ST/TGT | Login fails/uses fallback policy, no fake session |
| Compromised keytab | Security incident | Rotate service keys, revoke sessions/credentials per risk; never keep old trust |

**PASS criteria:** Not just HTTP 200. Confirm `Authentication.getName()` came from the verified ticket, mapped to the right local account and authorities; protected resources follow policy; negative cases **never** produce an authenticated session. Some client-side errors simply result in no token being sent while the server awaits a challenge; a failure handler event is not required for every case.

### 15.1. Testing Software with a Fake KerberosTicketValidator?

You can unit-test the **provider → UserDetailsService wiring** using a fake `KerberosTicketValidator` returning a simulated principal in an isolated test, yet **this does not prove GSS/Kerberos cryptographic validation**. For integration/security acceptance, use a Kerberos test realm/KDC with real keytab/token generation; otherwise you only verify code wiring and mocked authorization.

Never store production ticket fixtures in unit tests, CI logs, or Google Sheets. Tickets carry lifetimes/identities and can be abused while valid.

### 16.1. Diagnosing Like a Decision Tree

```text

  |
  +-- No --> DNS/TLS/redirect/proxy.
  |
  +-- Yes: received 401 WWW-Authenticate: Negotiate?
       |
       +-- No --> SecurityFilterChain/SpnegoEntryPoint/proxy.
       |
       +-- Yes: sent Authorization: Negotiate token?
             |
             +-- No --> browser policy/TGT/SPN/KDC.
             |
             +-- Yes: SPNEGO filter invoked?
                   |
                   +-- No --> filter chain/order/proxy header.
                   |
                   +-- Yes: KerberosTicketValidator accepted cleanly?
                         |
                         +-- No --> SPN/keytab/KVNO/etype/time/GSS.
                         |
                         +-- Yes: UserDetailsService mapped account?
                               |
                               +-- No --> identity/realm/disabled state.
                               |
                               +-- Yes: SecurityContext persisted?
                                     |
                                     +-- No --> repository/session/cookie.
                                     |
                                     +-- Yes: Resource/tenant authorization passed?
                                           |

                                           |

```

**Stop at the first layer that actually fails.** A trace showing `KRB_AP_ERR_MODIFIED` is not fixed by adding the user to local `UserDetailsService`; the provider has not passed cryptographic validation. Conversely, a Kerberos-authenticated user getting 403 for missing permissions does not mean you should edit the keytab to "solve 403".

## 17. Advanced Topics: Delegation, Multiple Backends, and Multi-Realm Apps

### 17.1. Verifying Tickets Differs from Calling Downstream Services as the User

The `KerberosServiceAuthenticationProvider` shown here is an **acceptor** for incoming SPNEGO. It **does not automatically supply delegated credentials** for service A to call B. If the app needs:

```text
Browser/user -> Spring App A -> SQL/HTTP Service B
```

then you must design Kerberos **constrained delegation** or an appropriate identity/token exchange mechanism, managing `GSSContext` and delegated credentials. Spring Kerberos includes `KerberosRestTemplate` and multi-tier support, yet never set `setMultiTier(true)` just because a backend endpoint returned 401. Delegation grants user impersonation power, requiring strict target-service limits, KDC policy, and auditing.

### 17.2. Cross-Realm Trust

An SPN in `EXAMPLE.ORG` can authenticate users from another realm via configured Kerberos trust. The application must still map the principal **together with its verified realm**, account status, and memberships; never strip `@PARTNER.ORG` and turn it into `alice@EXAMPLE.ORG`. KDC trust policy does not automatically grant tenant/app permissions.

### 17.3. Web App Sessions and Ticket Lifetime

Kerberos service tickets expire, yet the Spring web app can hold an authenticated user in `HttpSession`. Ticket expiration **does not immediately invalidate** the local session, depending on session policy. For sensitive applications:

- Define idle/absolute session lifetimes and revocation controls.
- Consider reauthentication for high-risk actions.
- Protect cookies with `Secure`/`HttpOnly`/`SameSite` and CSRF defenses.
- Never store raw service tickets in the session just to "recheck later".
- Never treat client-side `klist` as the source of truth for terminating backend sessions.
- When a user is disabled or group memberships change, trigger event-driven revocation/rechecks within SLA instead of waiting for Kerberos tickets to expire.

### 17.4. Do Not Roll Your Own Kerberos/SPNEGO Protocol Implementation

JDK `java.security.jgss` has a complex token acceptance API; a GSS context can span multiple rounds and emit response tokens for the client. Use the Spring Kerberos module/JDK JAAS GSS or a vetted Kerberos client library. Never Base64-decode and parse ASN.1 yourself, skip clock-skew/replay checks, or pull KDC passwords out of `application.properties`.

## 18. Production Checklist for Ticket Validator and Provider

- [ ] `KerberosServiceAuthenticationProvider` is actually wired to `SpnegoAuthenticationProcessingFilter` via `ProviderManager`; not confused with `KerberosAuthenticationProvider`.
- [ ] `SunJaasKerberosTicketValidator` (or JDK-appropriate provider) uses the managed **SPN + keytab** matching the service ticket issued by the KDC for the public web host.
- [ ] Keytab holds the exact principal/KVNO/etypes and is readable only by the service process; absent from repos/images/logs/HTTP.
- [ ] SPN owner in AD/KDC is accurate and unique; DNS aliases/public FQDNs verified on client machines.
- [ ] Kerberos realm/krb5.conf/KDC discovery/time sync/NTP and cross-realm trust configured cleanly.
- [ ] HTTP 401 challenge `WWW-Authenticate: Negotiate` reaches the browser; `Authorization: Negotiate` is preserved by ingress.
- [ ] Browser Integrated Authentication/SSPI/GSS policy tested with real users in the lab.
- [ ] Raw usernames, `X-Remote-User`, and NTLM fallback are never accepted as Kerberos authentication without a trust contract.
- [ ] Provider validates tickets via GSS/JAAS with clock-skew/expiry/replay protection, failing closed on forged/wrong-SPN/wrong-etype tokens.
- [ ] `UserDetailsService` loads local user/roles post-authentication; disabled accounts, tenant memberships, and object authorization are enforced.
- [ ] `SecurityContextRepository` and `SessionAuthenticationStrategy` configured; session fixation and logout/revocation tested.
- [ ] Session/TGT/service ticket lifetimes separated; the app does not assume an earlier verified AP-REQ keeps stale session authorities valid forever.
- [ ] TLS HTTPS uses the right certificate for the public host; cookies/CSRF/CSP configured; Kerberos keytabs are not conflated with TLS private keys.
- [ ] KRB5/JAAS debug logging does not dump raw tokens, keytabs, or passwords in production logs; redaction and retention enforced.
- [ ] Multi-pod deployments share SPN/keytabs by design; replay caches/risks assessed per RFC 4120 rather than assuming individual nodes are safe in isolation.
- [ ] Keytab rotation/KVNO/etype changes have a runbook and pre/post-cutover integration tests; compromised secrets are never kept.
- [ ] Spring Security 6.x uses Kerberos 2.2.x group `org.springframework.security.kerberos`, while Security 7.x uses the corresponding `org.springframework.security` group.
- [ ] Tests cover normal Negotiate, wrong/missing SPN, wrong keytab, clock skew, revoked users, 403 authorization, session persistence, and reverse proxies.
- [ ] Monitoring tracks categories: missing token, GSS validation failure, missing local account, insufficient role, session save failure, and node/realm/SPN changes.
- [ ] Incident response runbook links KDC administrators, application owners, and ingress owners while keeping logs redacted.
- [ ] Delegation/multi-tier or storing delegated credentials is not enabled when the business requirement is solely web SSO.

**Conclusion:** `KerberosServiceAuthenticationProvider` serves as the **bridge from Kerberos service-ticket verification to Spring Authentication**. The filter reads the SPNEGO token from HTTP, the provider invokes `KerberosTicketValidator` and JAAS/GSS to verify the ticket using the **matching SPN's keytab**, and `UserDetailsService` resolves the local account/GrantedAuthorities; only then does Spring Security establish the SecurityContext/session and enforce application authorization. **Verifying a Kerberos ticket ≠ granting business permissions**, and an HTTP header labeled "Negotiate" ≠ a verified ticket. A system is secure only when SPN, keytab, KDC, time, replay, browser/proxy, session, and tenant authorization are all tested at their respective layers.
