# CAS Server, CAS Service, and the Browser in Centralized Login

> **Topic:** Spring Security – federation · **Group:** CAS Fundamentals. This document explains the **Central Authentication Service (CAS)** architecture under the ticket-based SSO protocol: the **CAS Server** authenticates users and issues tickets, the **CAS service** (the protected application, e.g., a Spring Security web app) validates tickets and manages its own application session, and the **browser** only transports redirects and domain-scoped cookies. This lesson focuses on the traditional CAS protocol (CAS 2.0/3.0 with tickets and validation), without conflating it with SAML 2.0, OAuth 2.0, or OpenID Connect even though an Apereo CAS Server deployment may support multiple protocols. Standalone Java snippets require **JDK 17+**; Spring configuration requires compatible versions/dependencies.

## 1. The Centralized Login Problem

An enterprise has two applications:

- `https://portal.example.org` — employee portal.
- `https://reports.example.org` — internal reporting.

If both verify passwords independently, users must log in twice, and each application must handle passwords, MFA, account lockout, and authentication policies. With CAS:

1. Both portal and reports redirect the browser to **a single CAS Server** such as `https://sso.example.org/cas` when authentication is required.
2. The CAS Server verifies the user against LDAP/AD, a database, MFA, or configured authentication handlers.
3. The CAS Server returns a **Service Ticket (ST)** intended **exclusively for the requesting application**.
4. The application calls the CAS Server over a **server-to-server backchannel** to **validate the ST**, receives the identity/attributes, and then creates a **local session**.
5. When the user accesses the second application, CAS recognizes the SSO session via the **Ticket-Granting Cookie (TGC)** and can issue a **new ST for the second application** without requiring the user to enter their password again.

**Result:** identity authentication is centralized, but **each CAS service remains responsible for its own authorization, session lifecycle, and business security**. Centralized login does not automatically cause two applications to share a single `HttpSession`.

### Learning Objectives

After this lesson, you will be able to:

1. Clearly state the responsibilities of the CAS Server, CAS service, and browser.
2. Distinguish between `TGT`, `TGC`, `ST`, and the application's `JSESSIONID`/`SESSION` session.
3. Explain the sequence of redirects, initial login, ST issuance, backchannel validation, and second login without re-entering a password.
4. Know the purpose of `/login`, `/serviceValidate`, `/p3/serviceValidate`, `/logout`, and the `service`, `ticket`, `renew`, and `gateway` parameters.
5. Explain why an ST is bound to one service and must be **consumed once**, even when validation fails under the CAS protocol.
6. Identify Spring Security CAS client components: `ServiceProperties`, `CasAuthenticationEntryPoint`, `CasAuthenticationFilter`, `CasAuthenticationProvider`, and `TicketValidator`.
7. Analyze the threat model: service URL allowlist, ticket leakage/replay, backchannel TLS, session fixation, login CSRF/session confusion, and SLO.
8. Practice with a Java 17 simulation and build safe integration tests.

## 2. Three Actors and Responsibility Boundaries

| Actor | Primary Responsibilities | What Does It See? | What Should It Not Do? |
| --- | --- | --- | --- |
| **CAS Server** | Centralized login, authentication policy, TGT/TGC, ST issuance/validation, service registry | User credentials **only at CAS login**, CAS session/ticket registry, service ID | Issue STs for an arbitrary unapproved service URL, or allow one ST to authenticate at multiple services |
| **CAS service / CAS client** | Protect resources, redirect to CAS, receive ST, backchannel validate, create local SecurityContext/session, authorization | The ST intended for it, identity and attributes returned by CAS after validation | Trust an ST solely because it has the `ST-...` format; use TGC instead of ST; collect passwords at the application |
| **Browser** | Carry requests, redirects, domain-scoped cookies, receive URL with ST and forward it to the callback | CAS TGC cookie in the CAS origin cookie jar; local app cookie per service origin; ticket URL | Validate tickets itself, create server-side principals itself, or send TGC as a ticket to other applications |

### 2.1. CAS Server

The CAS Server is the **issuer and verifier** of authentication tickets. It needs:

- Authentication handlers/policy: password, WebAuthn, MFA, delegated authentication… depending on deployment.
- Ticket registry: stores and controls ticket lifecycle, timeout, replay, and SSO state; in a cluster, a shared/consistent backend is required.
- Registered service registry: list of applications permitted to use SSO, callback URLs/regexes, released attributes, and per-service policies.
- Web endpoints: login, ticket validation, logout, and proxy functions when configured.
- TLS, cookie protection, auditing, rate limiting, and abuse/availability controls.

The CAS Server **does not unilaterally decide** which reports a user may read inside an application. It verifies identity and may return certain attributes; the app must enforce domain authorization.

### 2.2. CAS Service

In CAS terminology, a **service** refers both to the CASified application and to the **callback URL passed in the `service` parameter**. These two concepts are related but not completely identical:

- The portal application has multiple protected routes such as `/dashboard`, `/orders`, and `/profile`.
- A stable CAS service URL to receive STs, for example `https://portal.example.org/login/cas`.
- When initiating authentication, the application sends the browser to CAS `/login?service=...`, where `service` has the value of the **ticket-receiving URL**.
- When validating the ST, the application must send the **exact same service URL identifier** for which the ticket was issued; do not use an arbitrary user-provided host or an untrusted `X-Forwarded-Host`.

**Do not assume a “CAS service” must be a backend microservice.** It can be a servlet web application, a Spring MVC app, or another system with a CAS client. “Service” is the **CAS ticket-consuming** side.

### 2.3. The Browser

The browser is the **frontchannel transport** for redirects:

```text
GET /dashboard on Portal
   |
   +--> 302 Location: https://sso.example.org/cas/login?service=...
   |
   +--> Browser displays CAS login if no SSO yet
   |
   +--> CAS 302 Location: https://portal.example.org/login/cas?ticket=ST-...
   |
   +--> Browser sends callback request to Portal
```

The browser **does not call `/serviceValidate` to verify identity** in the standard flow. The CAS service backend makes an HTTPS request to the CAS validation endpoint; this is a critical trust boundary.

## 3. Distinguishing TGT, TGC, ST, and Application Sessions

| Artifact | Where Managed/Stored | Purpose | How Long Does It Live? | Who Uses It to Authenticate? |
| --- | --- | --- | --- | --- |
| **TGT — Ticket Granting Ticket** | CAS Server/ticket registry; tied to SSO context | Foundation of the SSO session, allowing issuance of multiple STs within its validity period | Per CAS SSO/session policy | CAS Server |
| **TGC — Ticket Granting Cookie** | Browser cookie jar for the CAS domain; references/represents the SSO TGT depending on implementation | Allows CAS to recognize the SSO session when the browser returns to `/login` | Per CAS cookie/session policy | Browser sends to CAS Server |
| **ST — Service Ticket** | Issued and managed by CAS Server; browser passes ST in URL to service | Short-lived proof intended for **a single service URL** | Very short; single-use | CAS service sends back to CAS Server for validation |
| **Local session cookie** | Browser cookie jar for the application origin, e.g., `JSESSIONID`/`SESSION` | Reads the authenticated session of Portal/Reports after ST validation | Per-application session policy | Individual application |
| **SecurityContext / Authentication** | Spring Security service backend, optionally tied to local HttpSession | Holds the accepted principal/authorities | Per local session | Spring Security and business authorization |

### 3.1. Are TGT and TGC the Same Thing?

No. The TGT is the **entity/session grant at CAS**, whereas the TGC is the **cookie the browser sends to CAS** so CAS can locate/restore that SSO grant. Some CAS documentation loosely describes “TGT stored in TGC cookie”; do not infer that this cookie is a raw TGT that business applications can verify on their own. Cookie format, cryptography, and cookie name/attributes depend on the CAS version/deployment.

**Only the CAS Server should receive and interpret the CAS TGC**. Portal does not read the TGC as a “login ticket” in place of an ST; the browser normally does not send cookies belonging to `sso.example.org` to `portal.example.org` because of different domains/scopes.

### 3.2. ST Is a Service-Bound Credential

The CAS protocol defines an ST as:

- An opaque string, typically starting with `ST-`; do not decode its contents yourself to extract a username.
- Having sufficient entropy so it cannot be guessed by brute force.
- Valid only for the **service identifier** requested when issuing the ticket.
- Valid only for **one validation attempt**; after that attempt, whether it succeeds or fails, it must be invalidated.
- Expiring quickly if unvalidated. The CAS protocol **recommends** a maximum of around **5 minutes** for an unvalidated ST, which does not mean every CAS deployment must use exactly 5 minutes.
- Not containing a password; however, it is a **short-lived bearer credential** at risk of abuse if leaked before validation.

Do not resend an already-used ST to access subsequent APIs. The service must establish its own local authenticated session after CAS validates the ST successfully.

### 3.3. Two Separate Local Sessions

For example, the browser holds:

```text
TGC  (domain sso.example.org)       -> CAS SSO context
JSESSIONID (portal.example.org)     -> Portal local session
JSESSIONID (reports.example.org)    -> Reports local session
```

If Portal is already logged in but Reports does not yet have a local session, Reports still needs an **ST intended for Reports**. Because the CAS TGC is still valid, CAS can issue an ST for Reports without the user re-entering their password.

Deleting the Portal session **does not automatically delete** the TGT at CAS and does not automatically invalidate the Reports session. This is a common source of confusion when talking about “centralized logout”.

## 4. First-Time CAS Login Flow — Step by Step

Assume public URLs:

```text
CAS Server:    https://sso.example.org/cas
Portal callback: https://portal.example.org/login/cas
Protected page:  https://portal.example.org/dashboard
```

These are **illustrative** addresses to understand the protocol, not a live system.

### Step 1. User requests a protected resource

```http
GET /dashboard HTTP/1.1
Host: portal.example.org
```

Portal does not yet have an authenticated `SecurityContext`. Spring Security routes the flow to the CAS entry point instead of handling passwords at Portal.

### Step 2. Portal instructs the browser to go to CAS

The CAS client produces a redirect:

```http
HTTP/1.1 302 Found
Location: https://sso.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
```

The `service` parameter specifies the **URL where Portal will receive the ticket**, not necessarily the protected page `/dashboard`. Spring Security can save the originally requested page in a local `RequestCache` and return the user to `/dashboard` **after** the ticket is validated and the local session is created.

**Do not confuse the original target URL with the service identifier.** Typically `ServiceProperties.getService()` configures a specific callback URL, such as `https://portal.example.org/login/cas`, and the CAS Server has this URL registered.

### Step 3. Browser opens CAS login

The browser sends a request to `sso.example.org`. If there is no valid TGC yet, CAS displays a login form/MFA per policy. Credentials are submitted **to the CAS Server**, not to Portal.

When the user authenticates successfully, CAS creates a TGT/SSO state and sends the TGC cookie (exact name/structure varies by deployment). The cookie requires appropriate `Secure`, `HttpOnly`, `SameSite`, TTL/path/domain policies and HTTPS. Do not attach the TGC to a redirect URL like an ST.

### Step 4. CAS checks the service registry and issues an ST

CAS checks whether `service=https://portal.example.org/login/cas` is in the list of approved services. When allowed, CAS issues an ST specifically for this Portal callback.

The browser receives:

```http
HTTP/1.1 302 Found
Location: https://portal.example.org/login/cas?ticket=ST-demo-portal-001
```

`ST-demo-portal-001` is a **placeholder value for the diagram**, not a real secure ticket. Real tickets must be generated by the CAS Server with sufficient entropy and an appropriate timeout. A redirect containing a ticket is not yet an authenticated session at Portal; the app must not trust the user until validation succeeds.

### Step 5. Browser returns the ST to Portal

The browser performs:

```http
GET /login/cas?ticket=ST-demo-portal-001 HTTP/1.1
Host: portal.example.org
```

The CAS client (e.g., Spring Security `CasAuthenticationFilter`) receives the `ticket` parameter at the configured callback and creates an authentication request for the provider.

### Step 6. Portal backend verifies the ST via backchannel

The Portal server calls the CAS Server over HTTPS:

```http
GET /cas/serviceValidate?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&ticket=ST-demo-portal-001 HTTP/1.1
Host: sso.example.org
```

This is a **request from the Portal backend to CAS**, not the browser calling the `/serviceValidate` URL directly to obtain a username. The backend must verify CAS's TLS certificate/hostname, handle timeouts, and parse XML safely.

If the ticket is valid and the service matches, CAS returns a success XML response, for example:

```xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>alice</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
```

This is a **simple CAS 2.0 XML response example**, not a SAML Assertion. CAS 3.0 can return attributes via `/p3/serviceValidate` or appropriate extensions/elements. If the ticket is invalid, the XML response contains `authenticationFailure`, and Portal must reject the login.

### Step 7. Portal creates an application session

After `TicketValidator` returns a trusted result, `CasAuthenticationProvider` can create a `CasAuthenticationToken` and map user details/authorities per application policy. Spring Security stores `Authentication` in the security context and maintains the local session via `HttpSession` or an appropriate mechanism.

Finally, the browser can be redirected to `/dashboard` with no `ticket` remaining in the URL.

**Key point:** CAS authenticated “alice”, but Portal must still decide whether alice is authorized to view `/dashboard` and which tenant data she can access. Do not grant `ROLE_ADMIN` solely because CAS returned an existing username.

## 5. SSO Across a Second Application

The user is already logged in to Portal and still has a TGC at CAS. Then they open Reports:

```text
Browser         Reports service             CAS Server             Portal
   |                   |                         |                    |
   | GET /reports      |                         |                    |
   |------------------>|                         |                    |
   |                   | local session? NO       |                    |
   |<------------------| 302 /cas/login?service=Reports callback       |
   |-------------------------------------------->|                    |
   |                   |              Browser sends CAS TGC           |
   |                   |              CAS TGT is still valid          |
   |<--------------------------------------------| 302 to Reports     |
   |                 ticket=ST-Reports-002       |                    |
   |------------------>|                         |                    |
   |                   | GET /serviceValidate     |                    |
   |                   |------------------------>|                    |
   |                   |<------------------------| cas:user=alice     |
   |<------------------| Reports local session    |                    |
   |                   |                         |                    |
   |  Portal still has its own local session      |                    |
```

Key takeaways:

- **CAS TGT/TGC can be reused**, but each CAS service still receives **its own ST**.
- Portal's ST is **not** accepted for Reports.
- Reports must validate with its own `service`.
- Reports' local session is separate from Portal's local session.
- The user does not enter their password a second time **if** the CAS SSO state is still valid and policy permits it. `renew=true` or step-up/MFA policy may require re-authentication.

### 5.1. What If the CAS SSO Cookie Has Expired?

The browser returns to CAS `/login` without a valid TGC, so CAS may require logging in again. Even if Portal still has a local session, on first access to Reports the user may have to re-authenticate with CAS. This is why **SSO session timeout** and **local application session timeout** must be observed separately.

### 5.2. What If Reports Already Has a Local Session?

Once Reports has a valid `Authentication` in its local session, it normally **does not need to issue a new ST** for every HTTP request. CAS is not an authority queried on every API request to Reports: Spring Security uses the local security context for subsequent requests.

## 6. CAS Protocol Endpoints and Parameters

| Endpoint | Purpose | Typical Caller |
| --- | --- | --- |
| `/cas/login` | Login page; authenticates user or uses SSO TGC; issues ST for an allowed service | Browser |
| `/cas/logout` | Ends CAS SSO session per policy; may coordinate Single Logout | Browser, via logout workflow |
| `/cas/validate` | CAS 1.0 ticket validation, typically plain text `yes/no` | CAS service backend |
| `/cas/serviceValidate` | CAS 2.0 ST validation, XML response | CAS service backend |
| `/cas/p3/serviceValidate` | CAS 3.0 attribute-capable ST validation | CAS service backend |
| `/cas/proxyValidate` or `/cas/p3/proxyValidate` | ST/PT validation with proxy support | CAS service backend |
| `/cas/proxy` | Issues proxy ticket using PGT, for delegated backend service scenarios | Trusted CAS service |

**Note:** The `/cas` prefix is an assumed context path in examples; a real CAS Server may run at root or another path. Do not confuse `/login/cas` on **Portal** with `/cas/login` on the **CAS Server**.

### 6.1. `service`

`service` is the URI identifying the application/callback receiving the ticket, URL-encoded in the query string:

```text
service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
```

It is used both when CAS issues the ST and when the service validates the ST. Therefore differences such as:

- HTTP vs HTTPS
- internal hostname vs public hostname
- port
- context path or trailing slash
- query parameters defined/encoded by the service

can cause validation to fail. Do not “fix” this by disabling service binding checks. Configure a canonical public URL and trusted reverse proxy headers, using the exact same URL during issuance and validation.

### 6.2. `ticket`

`ticket` is an opaque bearer credential from CAS. A service must not trust the `ST-` prefix as proof of authentication. It must validate against the real CAS Server, verify the service, and process it once.

A ticket is **not a session cookie**: after successful validation, the app creates a local session; the browser does not have to send the ticket on every request.

### 6.3. `renew=true`

In the CAS protocol, `renew=true` requires authentication based on **primary credentials** rather than relying solely on an existing CAS SSO session. When a service configures `sendRenew=true` in Spring Security `ServiceProperties`, an application can require the user to log in again with CAS for sensitive policies.

**Do not assume `renew` implies MFA or guarantees a specific password check**: CAS authentication flows can involve multiple methods, so check CAS's assurance-level rules. The validator must enforce `renew` appropriately if the service requires step-up/reauth.

### 6.4. `gateway=true`

`gateway=true` is typically used when a service wants to know whether the browser **already has an SSO session** without forcing a login form to be displayed. If there is no suitable SSO session, CAS may redirect back to the service **without a ticket** per the protocol; the service must handle the anonymous/gateway response branch.

Do not turn “no ticket on gateway callback” into an authenticated user. Nor does it replace `renew=true`; the two parameters solve different problems.

### 6.5. CAS Attributes and Authorization

CAS 3.0/extensions can return attributes in XML:

```xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>alice</cas:user>
    <cas:attributes>
      <cas:department>engineering</cas:department>
      <cas:affiliation>staff</cas:affiliation>
      <cas:affiliation>reviewer</cas:affiliation>
    </cas:attributes>
  </cas:authenticationSuccess>
</cas:serviceResponse>
```

A CAS service must only use attributes **after the response from the trusted CAS validation endpoint has been verified and safely parsed**. Mapping to local roles must enforce an allowlist, tenant boundaries, and least privilege; never take data from query parameters, `ticket`, or browser forms and treat it as CAS attributes.

## 7. Why Must Ticket Validation Be Server-to-Server?

Suppose the browser sends:

```text
https://portal.example.org/login/cas?ticket=ST-fake
```

If Portal only checks `ticket.startsWith("ST-")` and creates a session, an attacker can supply a forged ticket. Therefore, the ST and service URL must be sent to the trusted CAS Server to obtain the validation result.

A standard flow:

```text
Untrusted browser query "ticket"
       |
       v
CAS service callback/filter
       |
       v
TicketValidator (server-to-server HTTPS)
       |
       v
Trusted CAS server /serviceValidate
       |
       v
Valid only if:
  - ticket exists, is not expired/already used
  - was issued for the exact service
  - is not rejected due to renew/policy
       |
       v
CAS returns authenticated principal / attributes
       |
       v
Spring Security creates local Authentication + session
```

### 7.1. CAS Is Not “Validating a JWT in the Browser”

In the traditional CAS protocol, an ST is an **opaque reference ticket**, not a JWT containing claims whose signature the frontend verifies. The Spring Security CAS client has a dedicated module for the CAS protocol; do not put an ST into `Authorization: Bearer` as a long-lived access token to call arbitrary microservices.

### 7.2. CAS HTTPS Must Be Verified

The backend service connects to the CAS validation endpoint over HTTPS, verifies the server certificate and hostname, uses an appropriate trust store, and enforces timeouts and network egress policy. Do not disable TLS hostname verification or use a trust-all certificate setup to work around validation errors.

If the CAS validation service is unreachable, the service must **fail closed**, not simulate CAS success based on the ticket query value.

### 7.3. Parsing the CAS Response

`/serviceValidate` returns XML containing `authenticationSuccess` or `authenticationFailure`. Use a maintained CAS client/`TicketValidator`; if writing a custom parser, restrict DTD/external entities/XXE, entity expansion, and response size, and do not read the username element when `authenticationFailure` is present. Response data is untrusted unless it comes from the authentic CAS origin over TLS.

An arbitrary response POSTed by a browser containing an XML snippet for “alice” **is not a CAS validation result**.

## 8. Security Boundaries in the Redirect Path

### 8.1. Service Allowlist on the CAS Server

The CAS Server must maintain a **service registry** restricting which applications are permitted to use SSO. Do not accept a `service` with an arbitrary hostname or an overly broad regex such as a wildcard for all URLs. If the registry is left open, an attacker can cause CAS to issue an ST/redirect to a site they control, leaking identity or causing credential/ticket leakage or abuse.

For each registered service, control:

- Scheme: prefer mandatory HTTPS.
- Approved public host/domain.
- Callback path and query structure, without overly broad matching.
- Application ownership/onboarding process.
- Attribute release, MFA/renew requirements, logout policy, and protocol version.
- Regex semantics (if used) must be anchored, escaped, and reviewed.

### 8.2. Tickets in the Query String Are Sensitive

CAS service tickets normally appear in redirect URLs, making them susceptible to:

- Being recorded in reverse-proxy/access logs or browser history.
- Being sent to third-party analytics/referrer headers if the application renders external content before removing the ticket from the URL.
- Copy/paste or screenshots during debugging.
- Replay within the window before the first validation.

Defenses:

1. End-to-end HTTPS for CAS and services.
2. Shorten ST lifetime and consume on **a single validation attempt**.
3. Redirect immediately to a clean URL after validation/local session creation.
4. `Referrer-Policy: no-referrer`, avoiding analytics/tracking scripts on the callback.
5. Restrict logging raw `ticket`, `service` query strings, and cookies in access logs, traces/APM/WAF.
6. Never send STs over email/chat/support tickets; use an internally generated correlation ID when debugging.

**Do not misunderstand:** once an ST is consumed, replay is normally rejected, but exposure **before** validation remains dangerous. “Single use” reduces the attack window; it does not eliminate the need to protect the ticket.

### 8.3. Login CSRF / Session Swapping

Service-bound STs and one-time semantics are important, but they **do not by themselves prove that the current browser intentionally initiated login**. If a flow allows injecting an attacker's ST into a victim's browser and establishing a session without checking context, there is a risk of login CSRF/session confusion.

Depending on the system, ensure:

- Bind initiation intent to the local browser session, avoiding arbitrary callbacks logging into another account via an injected ticket.
- Verify the callback URL and expected service, plus state if the CAS client/application intentionally adds transaction context (do not call it standard CAS `RelayState` or `state` if the protocol does not define it).
- Rotate the session ID after login to prevent session fixation.
- For account linking/switching users, require an intentional identity-verification flow rather than accepting an ST triggered by an external page to link accounts.
- Use a standard CAS client and integration tests on a real browser instead of writing a custom GET ticket controller that accepts tickets directly.

Do not invent a query “state” parameter not supported by the CAS Server and assume it is a built-in protocol feature.

### 8.4. Service Authorization

The CAS Server confirms the username/attributes. The service must map permissions itself:

```text
cas:user = alice (validated)
   |
   +--> application account lookup by IdP/tenant namespace
   +--> active? allowed organization?
   +--> role/authorities from approved policy
   +--> object-level authorization per HTTP request
```

Do not assume every CAS-authenticated principal is an admin. If integrating multiple CAS servers or multiple tenants, the same username alone is not sufficient as an identifier; use a trusted issuer/CAS provider namespace and tenant context.

## 9. Spring Security CAS Integration: Core Components

Spring Security supports CAS via the **`spring-security-cas`** module (distinct from `spring-security-saml2-service-provider`). The integration framework centers on using an `AuthenticationEntryPoint` to send the browser to CAS and an `AuthenticationProvider` to validate the ticket.

| Component | Role |
| --- | --- |
| `ServiceProperties` | Holds the service callback URL and options such as `sendRenew`; this URL must match the filter/certificate/routing |
| `CasAuthenticationEntryPoint` | When an anonymous user accesses a protected resource, redirects the browser to CAS `/login` with `service` |
| `CasAuthenticationFilter` | Receives the ST at `/login/cas` (common default) and creates an authentication request for the manager |
| `CasAuthenticationProvider` | Invokes `TicketValidator` and maps the CAS result into a `CasAuthenticationToken` |
| `Cas20ServiceTicketValidator` | CAS client validator that calls CAS 2.0 `/serviceValidate` over HTTPS |
| `AuthenticationUserDetailsService` | Resolves user/authorities in the application after CAS validates the ticket |
| `SecurityContextRepository`/`HttpSession` | Stores the service's local authentication context |
| `RequestCache` / saved request | Returns the browser to the original protected URL after successful login, if configured by the app |
| `LogoutFilter` and CAS logout integration | Invalidates the local session; can link CAS logout/SLO via a separate flow |

### 9.1. Separate CAS Dependency Is Required

Example Maven dependencies (fragment in a Spring Boot 3.x application):

```xml
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-cas</artifactId>
  </dependency>
</dependencies>
```

This is a `pom.xml` fragment, not a standalone copy-paste build. To run a project, you need a Spring Boot parent/BOM, application code, compatible transitive CAS client dependencies, a real or test CAS Server, and full configuration. Check your release because Spring CAS documentation includes some legacy XML/namespace examples (referencing CAS Server 3.x): **the protocol concepts remain valid, but do not copy old XML config verbatim into Spring Boot 3/Security 6 and assume Jakarta Servlet compatibility**.

### 9.2. `ServiceProperties` Bean: Canonical URL Is Required

Source-level Spring bean example:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.cas.ServiceProperties;

@Configuration
public class CasServicePropertiesConfig {

    @Bean
    ServiceProperties casServiceProperties() {
        ServiceProperties properties = new ServiceProperties();
        properties.setService("https://portal.example.org/login/cas");
        properties.setSendRenew(false);
        return properties;
    }
}
```

Key points:

- `service` is the callback URL listened to by `CasAuthenticationFilter`, not the CAS Server login URL.
- `sendRenew=false` means an existing CAS SSO session is allowed per policy; `true` requires reauthentication per CAS semantics.
- If the browser starts login with callback `https://portal.example.org/login/cas` but validates the ST with `http://portal-internal:8080/login/cas`, CAS may reject it even for a valid ticket due to service mismatch.
- The file is a Spring `@Configuration`, has no `main` method, and does not yet configure CAS login end-to-end.

### 9.3. CAS Login Entry Point: Who Redirects the Browser?

Example fragment, using the bean above:

```java
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;

CasAuthenticationEntryPoint entryPoint =
        new CasAuthenticationEntryPoint();
entryPoint.setLoginUrl("https://sso.example.org/cas/login");
entryPoint.setServiceProperties(casServiceProperties);
```

`casServiceProperties` in the fragment is a previously configured `ServiceProperties` variable. The entry point navigates the browser from the service to CAS; **it does not validate the ST**. Ticket validation is performed by the filter/provider at the callback.

In route protection configuration, the entry point must be registered in `exceptionHandling(...).authenticationEntryPoint(...)` of the appropriate `SecurityFilterChain`.

### 9.4. Ticket Validator and Provider

The CAS client provides `org.apereo.cas.client.validation.Cas20ServiceTicketValidator`. Example fragment:

```java
import org.apereo.cas.client.validation.Cas20ServiceTicketValidator;

Cas20ServiceTicketValidator ticketValidator =
        new Cas20ServiceTicketValidator(
                "https://sso.example.org/cas");
```

This is only the **validator object**; the application must wire it into `CasAuthenticationProvider` along with `ServiceProperties`, an authentication user details mapper, and an appropriate provider key, then register it with `AuthenticationManager`. A `CasAuthenticationFilter` instance is configured to handle `/login/cas` and invoke that manager.

For CAS 3.0 attributes, choose the validator/parser matching the API version and CAS Server endpoint; **do not assume the default CAS 2.0 validator returns all attributes**.

### 9.6. `SecurityFilterChain` Configuration Skeleton

Fragment illustrating structure, **not a full standalone project**:

```java
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;
import org.springframework.security.cas.web.CasAuthenticationFilter;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

// Assumes CasAuthenticationEntryPoint entryPoint and
// CasAuthenticationFilter casFilter are configured with AuthenticationManager
// along with CasAuthenticationProvider/TicketValidator/ServiceProperties.
SecurityFilterChain chain = http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/public/**").permitAll()
        .anyRequest().authenticated())
    .exceptionHandling(ex -> ex.authenticationEntryPoint(entryPoint))
    .addFilterBefore(casFilter, UsernamePasswordAuthenticationFilter.class)
    .build();
```

The fragment only shows entry point + filter placement. **Must not be deployed as a standalone statement**: it requires Spring configuration's `HttpSecurity` bean, CAS provider/manager wiring, proper filter chain/order, and compatible library versions. When manually wiring `CasAuthenticationFilter`, always test that the `/login/cas` callback is actually intercepted by the filter to avoid 404s or redirect loops.

A CAS client app is not by default equivalent to a SAML2 SP: `saml2Login()` expects a `SAMLResponse`, whereas `CasAuthenticationFilter` expects a `ticket`; they are not interchangeable.

## 11. Pure Java 17: Simulating CAS, Two Services, and One-Time Tickets

The following program includes a **simulated CAS Server** with TGC→TGT user mapping, a registry of two service URLs, and one-time STs. When validation uses the wrong `service`, the ticket is still consumed according to CAS protocol rules. Then a new ST for Portal is successfully validated; Reports receives a different ST thanks to the existing SSO TGC.

**Security limitations:** This is **not a real CAS Server** and does not use Spring Security. `"TGC-demo"` and `ST-1` have no entropy; there is no TLS, no cookie signing, no password/MFA, no authorization, no browser networking, and no XML parser. Its purpose is to demonstrate state transitions and trust boundaries, **not for use in production**.

Create `CentralCasDemo.java`:

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Set;

public class CentralCasDemo {

    record ServiceTicket(String value, String serviceUrl, String username) {}

    static final class CasServer {
        private final Set<String> allowedServices;
        private final Map<String, String> ssoUsersByCookie = new HashMap<>();
        private final Map<String, ServiceTicket> tickets = new HashMap<>();
        private int nextId = 1;

        CasServer(Set<String> allowedServices) {
            this.allowedServices = Set.copyOf(allowedServices);
        }

        void login(String tgc, String username) {
            ssoUsersByCookie.put(tgc, username);
        }

        String issue(String tgc, String serviceUrl) {
            String user = ssoUsersByCookie.get(tgc);
            if (user == null || !allowedServices.contains(serviceUrl)) {
                return null;
            }
            String id = "ST-" + nextId++;
            tickets.put(id, new ServiceTicket(id, serviceUrl, user));
            return id;
        }

        String validate(String ticketId, String serviceUrl) {
            // Consume on ANY validation attempt, success or failure.
            ServiceTicket ticket = tickets.remove(ticketId);
            if (ticket == null || !ticket.serviceUrl().equals(serviceUrl)) {
                return null;
            }
            return ticket.username();
        }

        void logout(String tgc) {
            ssoUsersByCookie.remove(tgc);
        }
    }

    public static void main(String[] args) {
        String portal = "https://portal.example.org/login/cas";
        String reports = "https://reports.example.org/login/cas";

        CasServer cas = new CasServer(Set.of(portal, reports));
        cas.login("TGC-demo", "alice");

        String first = cas.issue("TGC-demo", portal);
        System.out.println("First ticket: " + first);
        System.out.println("Wrong service accepted: "
                + (cas.validate(first, reports) != null));
        System.out.println("Replay after failed validation: "
                + (cas.validate(first, portal) != null));

        String second = cas.issue("TGC-demo", portal);
        System.out.println("Portal principal: "
                + cas.validate(second, portal));

        String third = cas.issue("TGC-demo", reports);
        System.out.println("Reports principal via SSO: "
                + cas.validate(third, reports));
        System.out.println("Reports ticket replay: "
                + (cas.validate(third, reports) != null));

        System.out.println("Unknown service ticket: "
                + cas.issue("TGC-demo", "https://evil.example/login/cas"));

        cas.logout("TGC-demo");
        System.out.println("Ticket after CAS logout: "
                + cas.issue("TGC-demo", reports));
    }
}
```

Compile/run:

```bash
javac CentralCasDemo.java
java CentralCasDemo
```

**Exact** stdout:

```text
First ticket: ST-1
Wrong service accepted: false
Replay after failed validation: false
Portal principal: alice
Reports principal via SSO: alice
Reports ticket replay: false
Unknown service ticket: null
Ticket after CAS logout: null
```

### 11.1. Reading the Output

- The simulated CAS only issues a ticket when the user's TGC has a logged-in state and `serviceUrl` is registered.
- `ST-1` was issued for Portal, mistakenly sent to Reports for validation → rejected, and the ST was also consumed; retrying with Portal afterward still fails.
- Portal issues a second ST, validates with the matching service → principal `alice`.
- Reports receives a new ST without CAS requiring the user to log in again; this is TGC/TGT-based SSO.
- A consumed Reports ST cannot be reused.
- Unregistered services are not issued an ST.
- After CAS logs out the TGC, no new STs are issued unless the browser re-authenticates.

### 11.2. What the Program Does Not Prove

- No HTTP 302 redirects, cookie scope, or real network backchannel.
- `Map` lives in a single JVM, unsuitable for a multi-node/clustered CAS Server.
- TGC/username are accepted directly in `login` without password verification; production uses CAS authentication handlers.
- STs use an incrementing counter and are predictable; production requires secure random/entropy and expiration.
- No XML responses, TLS certificate validation, ticket signatures/trust, issuer namespaces, or authorization.
- Portal/Reports sessions are not fully modeled; in a real application, they are only created **after validation succeeds**.

Use this demo to observe issue/validate/consume rules; then use an **Apereo CAS test server + Spring Security CAS client** to test the protocol end-to-end.

## 12. Logout and SSO Sessions: Three Different Outcomes

### 12.1. Local Logout at Portal

When the user sends `POST /logout` at Portal (with a CSRF token), Portal deletes the local authenticated session. However:

- The CAS TGC/TGT may still be valid.
- The Reports local session may still be valid.
- If Portal redirects the user back to CAS login, CAS may perform SSO immediately and issue a new ST.

Therefore **local logout ≠ global logout**.

### 12.2. CAS Logout

When the browser visits CAS `/logout` in a valid flow, CAS destroys the SSO TGT/TGC per policy. However, existing local sessions at Portal/Reports **do not automatically disappear** just because the CAS SSO session ended, unless the applications integrate Single Logout/session invalidation.

### 12.3. Single Logout (SLO) When Supported

The CAS Server can send notifications to registered CAS services requesting invalidation of the corresponding local sessions. This requires configuring the CAS service registry, session mapping, and client-side support according to version/protocol.

**Do not promise:** CAS SLO always succeeds in destroying every local session. Service downtime, browser/network failures, backend callback rejections, or apps without SLO enabled can occur. The UX must distinguish between the CAS SSO session being cleared and each service's local session being invalidated.

**CSRF:** browser user-initiated logout is a state-changing operation requiring CSRF protection in the app. SLO notifications from the CAS Server require their own verification/protection mechanism; do not disable CSRF across the entire application to accept server-to-service notifications without ensuring trust.

### 12.4. Session Fixation and Lifecycle

After successful CAS ticket validation, Spring Security should rotate the session ID per session-fixation policy, safely bind `Authentication` to the current session, and enforce timeouts. Never reuse a URL containing an ST as a session identifier, and never store ST credentials to authenticate future requests.

## 13. CAS vs. SAML/OIDC: Same Goal, Different Protocols

CAS, SAML2, and OIDC can all serve **SSO**, but their messages/callbacks differ:

| Criterion | CAS Protocol | SAML 2.0 Web SSO | OIDC Authorization Code |
| --- | --- | --- | --- |
| Artifact sent to application | Opaque **ST** in `ticket` query | `SAMLResponse` containing XML Assertion (usually POST) | Authorization `code` (and state) |
| Client validation | Backend calls CAS `/serviceValidate` | SP verifies signature/protocol/conditions of SAML assertion; metadata/keys from IdP | Relying Party exchanges code at token endpoint, verifies ID Token |
| Browser SSO state | CAS TGC/TGT | IdP browser session cookie | OIDC provider browser session cookie |
| Client binding | ST issued for exact service URL | Audience/Recipient/Destination/InResponseTo… | client_id, redirect_uri, nonce/state, PKCE… |
| Spring Security module/DSL | `spring-security-cas` / CAS filter+provider | `spring-security-saml2-service-provider` / `saml2Login()` | `oauth2Login()` |
| Principal | CAS validation response + local account mapping | SAML authenticated principal | OIDC user / OAuth2 authentication principal |

**Do not use a SAML ACS filter to read a CAS `ticket`**. A CAS Server such as Apereo may support SAML/OIDC as extensions, but when an application uses the native CAS protocol, use the CAS client/validator rather than interpreting tickets as SAML Assertions.

## 14. Operating CAS Server and Services Across Multiple Nodes

### 14.1. CAS Server Cluster

The CAS Server can run multiple instances behind a load balancer. For SSO and one-time STs, you need:

- A ticket registry with appropriate consistency, ensuring an ST issued on node A can be validated on node B and consumed atomically.
- Consistent TGT/TGC crypto configuration/keys and session policies.
- Canonical public CAS Server login/validation URLs, shared trust store, and consistent policies.
- TTL, eviction, HA/failover, clock synchronization, rate limiting, and auditing.
- Prevention of replay succeeding across two nodes when two validation requests arrive concurrently.
- A uniform service registry; do not let node A permit a new service while node B rejects it.

Sticky sessions can assist some deployments, but **cannot substitute** for a shared/atomic ticket registry when failover/scaling requires it.

### 14.2. Service Cluster

Portal may run across pods A/B:

- CAS redirects the browser to public `https://portal.example.org/login/cas`, never `http://pod-a:8080`.
- Callbacks arriving at POD B require `ServiceProperties` configured identically to the callback used when CAS issued the ST.
- After ST validation, if the authenticated session is stored locally on POD B, subsequent requests hitting POD A require a shared `HttpSession` or appropriate session affinity.
- `SecurityContext` and local sessions are separate concerns from CAS TGT/ST.
- Do not let two pods write/override the service URL from untrusted internal request headers.
- If the CAS validation endpoint has an outage, fail closed; never “cache validated STs” as a bypass for new logins.

### 14.3. Reverse Proxies and URL Canonicalization

Common mismatches:

```text
Browser sees: https://portal.example.org/login/cas
Spring app sees internally: http://localhost:8080/login/cas
CAS ST issued for: https://portal.example.org/login/cas
CAS validation request uses: http://localhost:8080/login/cas
=> INVALID_SERVICE
```

The fix is to configure a **fixed public service URL** and trusted proxy/forwarded headers or a safe URL builder, rather than letting the validator accept arbitrary URLs.

### 15.1. Happy Path

1. Open a fresh browser profile with no TGC or Portal/Reports sessions.
2. Access Portal `/dashboard` → redirect to CAS login.

## 16. Diagnosing Common Issues

| Symptom | Possible Cause | Proper Check |
| --- | --- | --- |
| Portal loops continuously redirecting to CAS | Callback not intercepted by filter, ST validation fails, session not saved | `CasAuthenticationFilter` matcher, `ServiceProperties` URL, CAS response code |
| CAS returns `INVALID_SERVICE` | Service URL unregistered or issue/validate mismatch | Exact public URL and CAS service registry |
| ST fails on first attempt after redirect | Wrong validation URL/TLS, ST expired, proxy rewrite | Backend-to-CAS HTTPS, ticket TTL, service string |
| Reused ST sees `INVALID_TICKET` | ST is one-time, already validated or consumed by a failed attempt | Do not retry old ticket; start a new CAS flow |
| Logged in to CAS but Reports still prompts for password | TGC not sent, expired, `renew`, or CAS policy | Cookie attributes, SSO policy, reauth config |
| Portal local session persists after CAS logout | No SLO/session notification | Distinguish CAS TGT and local Portal session |
| Reports login succeeds but roles are missing | Reports `UserDetails`/authorities mapping differs from Portal | Application authorization mappings |
| CAS cookie appears in Portal request | Cookie domain configured too broadly | Cookie domain/scope, secure attributes |
| External `https` becomes `http` in service URL behind proxy | Incorrect forwarded headers or `ServiceProperties` | Canonical public service URL |
| Validation returns 200 but user is not authenticated | Response contains `authenticationFailure` or parser/mapper rejects | Controlled result contents; do not only check HTTP status |
| CAS Server node A issues ST, node B cannot validate | Local/unsynchronized ticket registry | Distributed ticket registry, atomic consume |
| Login on Portal pod A, pod B prompts again | App local session not shared | Spring Session/shared `HttpSession` or affinity |
| CAS endpoint unreachable | Network firewall/TLS trust/timeout | CAS URL, TLS certificate/hostname, health |
| Registered service still redirects browser to unexpected destination | Overly broad service regex/open redirect config | Registry allowlist, callback ownership |
| Logs contain `ticket=ST-...` | Access log/tracing captures query string | Redact ticket query, redirect to clean URL |

### 16.1. Safe Logging

Example audit event:

```json
{
  "event": "cas_ticket_validation",
  "service": "portal",
  "result": "DENIED",
  "reason_code": "INVALID_SERVICE",
  "request_id": "req-742",
  "node": "portal-pod-b"
}
```

This is an **illustrative** event containing no ticket. In practice, log only the allowlisted service ID, fixed reason code, node, and correlation ID. Never log raw `ticket`, TGC, session cookies, passwords, full validation URL queries, or CAS XML containing PII. Track invalid/expired/service mismatch rates, CAS latency, and session creation success rates.

## 17. Production Checklist

- [ ] CAS Server URL/IdP origin is governed and TLS-verified; do not trust arbitrary CAS URLs from the browser.
- [ ] Registered service registry only permits HTTPS callback URLs of approved applications, with no abusable wildcards.
- [ ] `ServiceProperties.service` **matches** the URL CAS uses to issue STs and the callback `CasAuthenticationFilter` listens on.
- [ ] The browser must never self-verify tickets; the backend `TicketValidator` calls CAS `/serviceValidate` over HTTPS.
- [ ] STs are bound to one service, one-time use, and short TTL; replay and wrong-service attempts fail closed.
- [ ] CAS TGT/TGC SSO state is distinct from each app's local `HttpSession`/`SecurityContext`.
- [ ] After authentication, rotate local session ID and apply authorization by least privilege/tenant.
- [ ] CAS validation results are parsed by a maintained client with hardened XML parsing and used only on success.
- [ ] `renew` and `gateway` have accurate semantics; never treat gateway no-ticket as a successful login.
- [ ] STs are stripped from URLs after validation and excluded from logs/referrer/APM/analytics.
- [ ] CAS/app cookies have `Secure`, `HttpOnly`, and `SameSite`/Domain/Path matching the topology.
- [ ] Multi-node CAS uses a shared/atomic ticket registry; app clusters have a session strategy.
- [ ] App local logout and CAS global logout/SLO are communicated accurately, without assuming all services log out synchronously.
- [ ] Tests cover CAS one-time tickets, issuer/trust/service binding, replay, expiration, wrong callback, invalid XML, and TLS failure.
- [ ] Never configure a SAML2 filter to process CAS STs or use STs as OAuth bearer tokens.
- [ ] Dashboards support root-cause investigation via event codes without storing credential tickets.
- [ ] Two-service test verified: log in once via CAS and each service receives its own ST with a separate local session.

## 18. Review Questions with Answers

**1. How do the CAS Server and CAS service differ?**  
The CAS Server authenticates users and manages SSO/tickets; the CAS service is the protected application that redirects/validates tickets and then creates its own local session and enforces authorization.

**2. Does the browser directly validate the ST?**  
No. The browser follows redirects and carries the ST to the service callback; the service backend calls the CAS validation endpoint.

**3. Are TGT and TGC the same as an ST?**  
No. TGT/TGC maintain the CAS SSO session; each service is issued a separate short-lived, one-time, service-bound ST.

**4. After Portal logs in, can Reports use Portal's ST?**  
No. Reports must request a new ST for the exact Reports service URL. Thanks to a valid TGC, the user may not need to enter their password a second time.

**5. If ST validation fails with the wrong service and is then retried with the right service, is it valid?**  
No under the CAS protocol: an ST is valid for only one **validation attempt**, regardless of outcome.

**6. Does CAS authentication success automatically grant an admin role across all applications?**  
No. Each app has its own authorization mapping/tenant policy after ticket validation.

**7. When `/serviceValidate` returns HTTP 200, is login guaranteed to have succeeded?**  
No. The CAS response may contain `authenticationFailure`; the client must parse/evaluate the protocol result.

**8. Is `service` in CAS always the initial URL the user wanted to open?**  
No. It is usually a fixed callback URL such as `/login/cas`; the app retains the original URL in `RequestCache` to redirect after login.

**9. Why are `SameSite` and cookie domain important?**  
Browsers only send cookies according to scope/policy; CAS TGC lives at the CAS origin and local sessions live at each service origin. Misconfigured cookies prevent SSO from recognizing the session or leak credentials.

**10. Does local logout at Portal log out Reports and the CAS Server?**  
Not by default. The CAS TGT and Reports local session may remain active; SLO requires separate configuration and testing.

**11. Why must `ticket` in the URL be protected even though it is one-time?**  
It is a valid bearer credential before the first validation attempt; logs/referrer/history can expose it and create a race window.

**12. When should `renew=true` be used?**  
When a service needs re-authentication with primary credentials per CAS policy instead of accepting an existing SSO session, such as for a sensitive operation. It does not by itself guarantee MFA unless CAS policy requires it.

**13. Does `gateway=true` mean “bypass authentication”?**  
No. It attempts to detect SSO without showing a login form; if no ticket is returned, the service must treat the request as anonymous.

**14. Why can a wrong `ServiceProperties` URL cause a login loop?**  
CAS issues an ST for URL A while the service validates with URL B, so CAS rejects the ST and the client repeats the redirect.

**15. How are CAS and SAML similar, and how do they differ?**  
Both can serve SSO, but the CAS protocol uses STs and backchannel validation, whereas SAML Web SSO uses signed `SAMLResponse`/Assertions and SAML-specific conditions. Spring provides different modules/filters for each.

**Summary:** The CAS Server is responsible for **centralized authentication and ticket issuance**, the browser is the **redirect/transport channel for TGC and ST**, and the CAS service **calls the CAS backchannel to validate the ST, create a local session, and enforce authorization**. TGT/TGC lets the user log in once, but **each service receives its own short-lived, single-use ST**. Safe deployment requires an allowlisted HTTPS service registry, a consistent service URL, TLS validation, protection against ticket leakage/replay, and separating the CAS SSO session from application sessions; centralized logout must be designed and tested rather than assumed.
