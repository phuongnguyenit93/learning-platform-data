# CAS `renew`, `gateway`, and Their Impact on Login Experience

> **Topic:** Spring Security – federation. **Group:** CAS Fundamentals. This lesson explains the two CAS protocol parameters **`renew`** and **`gateway`**, their impact on users, Service Ticket validation, Spring Security integration, and secure UX design for SSO, re-authentication, and optional login.

## 1. Objectives and Quick Summary

After this lesson, you will be able to:

1. Distinguish the CAS Server, CAS Client, TGT, TGC, Service Ticket, and the application's `HttpSession`.
2. Explain **`renew=true`**: bypasses an existing SSO session and requires primary authentication.
3. Explain **`gateway=true`**: does not prompt for credentials; may return a ticket when SSO/non-interactive authentication exists, or **returns to the service without a ticket when no SSO exists**.
4. Know why **`renew` and `gateway` are incompatible** and must never be sent simultaneously.
5. Understand the difference between `renew` on **CAS `/login`** and `renew` on **CAS `/serviceValidate`**.
6. Use **`ServiceProperties.setSendRenew(true)`** properly in Spring Security CAS Client; understand that it does not automatically step up an already-authenticated local session.
7. Design gateway optional-login so no redirect loops occur, no data leaks, and users are not forced to log in on public pages.
8. Validate STs with the exact service and only once, managing TLS, cookies, logout, account switching, CSRF, and tenants.
9. Run standalone Java 17 examples, distinguishing simulations from real CAS integration.

**Core idea:** **`renew` = force fresh authentication**, **`gateway` = probe SSO without prompting for credentials**, and **normal = allow SSO as usual**.

## 2. CAS Native Protocol Context

CAS is a ticket-based SSO protocol comprising a CAS Server and CAS client applications. The browser goes through CAS to authenticate, receives a bounded ticket back to the application, and the application calls CAS over a server-to-server HTTPS channel to verify the ticket.

| Name | Full Name | Where Stored | Purpose |
|---|---|---|---|
| CAS Server | Central Authentication Service | Authentication system | Verifies credentials, issues STs, manages SSO sessions |
| CAS Client | CAS-aware Service Provider | Java/Spring application | Redirects to CAS, receives ST, and validates it |
| TGT | Ticket Granting Ticket | CAS Server | SSO session used to issue multiple STs |
| TGC | Ticket Granting Cookie | Browser, CAS domain | Helps CAS recognize the TGT |
| ST | Service Ticket | Issued by CAS, carried by browser to service | Ticket for one service and one validation |
| `service` | Service identifier/URL | Client and CAS registered service | Binds ST to the exact callback |
| Local session | `HttpSession` + `SecurityContext` | Spring application | Holds `Authentication` after ST validation |

Common native CAS endpoints:
- **`/login`:** prompts for or accepts primary authentication; accepts `service`, `renew`, `gateway` parameters.
- **`/logout`:** ends the CAS SSO session; may coordinate SLO if CAS/clients support it.
- **`/validate`:** CAS 1.0 validation, returns `yes`/`no`.
- **`/serviceValidate`:** CAS 2.0 validation, returns XML username/attributes per version.
- **`/p3/serviceValidate`:** CAS 3.0, can return additional attributes.
- **`/proxyValidate`:** for scenarios accepting proxy tickets per profile.

**Do not confuse:** a TGT is not Spring's `HttpSession` ID. An ST is a single-use ticket, not an access token reusable across APIs. A TGC is a CAS-domain cookie; applications must never treat a TGC as a Principal.

## 3. Normal CAS Login: Why Don't Users Have to Log In Repeatedly?

Assume:
- CAS Server login: `https://cas.example.org/cas/login`
- Portal protected page: `https://portal.example.org/dashboard`
- Registered CAS service/callback: `https://portal.example.org/login/cas`

### 3.1. Browser Has No SSO Yet

~~~text
Browser               Spring CAS Client                CAS Server
  |                          |                             |
  | GET /dashboard           |                             |
  +------------------------->|  no local Authentication    |
  |<-------- 302 CAS --------+                             |
  +------------------------------------------------------->|
  | /cas/login?service=ENCODED_CALLBACK                    |
  |                                                        |
  |<------------------------ CAS login form ---------------+
  | submit credentials ----------------------------------->|
  |                                                        | verify credentials,
  |                                                        | create TGT/TGC
  |<----------- callback?ticket=ST-... --------------------+
  +------------------------->|                             |
  |                          | /serviceValidate?ticket=... |
  |                          +---------------------------->|
  |                          |<---- validation success ----+
  |                          | create Authentication/HttpSession
  |<-------- dashboard ------+                             |
~~~

At the callback step, Spring must never trust any ticket string merely because it starts with `ST`. The ST must be verified by the CAS Server, for the exact service URL, and unused.

### 3.2. Browser Already Has TGC/TGT

~~~text
Browser -> /dashboard with no local session
        -> CAS /login?service=...
        -> browser sends existing TGC
        -> CAS locates valid TGT
        -> CAS may issue ST without re-prompting for credentials
        -> client validates ST, creates local session
~~~

This is the benefit of **Single Sign-On**. Depending on authentication policy, CAS may still show an advisory/consent/MFA page; never assume every existing TGT is completely silent.

## 4. `renew=true`: Requiring Re-Authentication

The CAS Protocol 2.0/3.0 specification states: when a request to CAS **`/login`** carries the **`renew`** parameter, CAS must bypass any existing SSO session and require the user to perform primary authentication, even when the browser already holds a TGC/TGT.

Illustrative example:

~~~text
https://cas.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&renew=true
~~~

| Pre-Login State | Without `renew` | With `renew` |
|---|---|---|
| No CAS SSO yet | CAS prompts for login | CAS requires primary authentication |
| Valid CAS SSO exists | May receive ST via SSO | Must perform primary authentication for the new flow |
| Local `HttpSession` active in Spring | Spring may skip calling CAS | **May also skip calling CAS** if app does not actively step up |

### 4.1. Does `renew` Force Re-Entering a Password?

Do not equate **primary authentication** with a specific password screen across every CAS deployment. CAS may use WebAuthn, Kerberos, delegated authentication, or another organization-approved flow. `renew` requires **not relying solely on an old SSO session**, without itself specifying which authentication method the user completed.

### 4.2. Is `renew` MFA?

**No.** `renew` does not automatically guarantee:
- That an MFA method was completed.
- High-assurance / phishing-resistant authentication.
- That all old sessions were logged out.
- That the user confirmed a specific transaction.
- That the new authentication belongs to the same subject as the old local session.

To enforce MFA step-up, the application needs matching CAS Server policy/context/assurance and application-side freshness checks. Never authorize a payment merely because the URL had `renew=true`.

### 4.3. Does `renew` Terminate the TGT?

`renew` is not CAS logout. The CAS TGT may remain active/managed by the CAS Server per policy; other applications may continue holding local sessions. If the goal is ending SSO, use CAS `/logout` and configured SLO, not `renew`.

## 5. `renew` in Two Different Places: Login and Validation

This is the most critical security aspect.

### 5.1. At CAS `/login`

The `renew` parameter instructs CAS to issue an ST only after primary authentication:

~~~text
GET /cas/login?service=ENCODED_SERVICE&renew=true
~~~

### 5.2. At CAS `/serviceValidate`

Once the app receives the ST at the callback, the validator must check that the ticket satisfies the primary-authentication requirement if business logic mandates it:

~~~text
GET /cas/serviceValidate?service=ENCODED_SERVICE&ticket=ST-EXAMPLE&renew=true
~~~

The CAS Protocol specifies: when validation includes `renew`, CAS returns success only if the ticket was issued from **presenting primary credentials**. An ST issued solely from a normal SSO session must be rejected when validated with `renew`.

Success XML example:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>user123</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Failure XML example:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationFailure code="INVALID_TICKET">
    Invalid ticket or authentication requirement
  </cas:authenticationFailure>
</cas:serviceResponse>
~~~

These are illustrative CAS 2.0 response fragments, not usable real STs.

### 5.3. Why Not Only Add `renew` to the Login Redirect?

If the application adds `renew` only to the login URL while the callback receives an ST issued during a normal flow, there is no proof the new ticket satisfies the policy. **You must validate with `renew`** so the CAS Server re-checks the ticket's origin. Never rely on a browser query flag to verify freshness.

### 5.4. What If `renew` Is Enabled Only at Validation?

An ST issued via normal SSO will not qualify. If the app redirects to normal CAS and then validates with `renew`, the user can loop on errors endlessly. Both steps must align modes within the same authentication journey.

## 6. `gateway=true`: Optional SSO Without a Login Prompt

When CAS **`/login`** receives `gateway`, CAS does not ask the user to enter credentials in the gateway flow.

- If an SSO session already exists, or CAS can authenticate non-interactively per policy, CAS **may** return to the service with an ST.
- If no SSO exists and non-interactive authentication is not possible, CAS **must** return to the service **without a ticket**.

Example:

~~~text
https://cas.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Fcas%2Foptional&gateway=true
~~~

### 6.1. SSO Session Exists

~~~text
Browser -> Portal /welcome
        -> CAS gateway=true
        -> CAS locates valid TGT
        -> may issue ST without prompting for credentials
        -> Portal validates ST and displays logged-in content
~~~

CAS may interject an advisory page; never promise every gateway response is visually silent. The key guarantee is that credentials are not mandatory in a gateway flow.

### 6.2. No SSO Session Exists

~~~text
Browser -> Portal /welcome
        -> CAS gateway=true
        -> no TGT and no non-interactive authentication
        -> CAS redirects back to service WITHOUT a ticket
        -> Portal renders guest (anonymous) mode
~~~

**No ticket is not an authentication error.** It is a protocol-defined outcome suited for public/optional-login pages. Never create a Spring `Authentication` or `GrantedAuthority` without a verified ticket.

### 6.3. Gateway Must Not Guard Private Routes

Gateway can return anonymous. Therefore never use it to enforce mandatory login on `/account`, `/admin`, or `/payments`. When a user needs a private resource, the application must send them through **normal login** or an appropriate flow after they choose to proceed.

## 7. Why Do `renew` and `gateway` Conflict?

`renew` mandates primary authentication; `gateway` forbids prompting for credentials. The CAS Protocol calls the two parameters **incompatible**, and their combined behavior is **undefined**. The specification recommends servers may ignore `gateway` when `renew` is set, but applications must never depend on that precedence.

| `renew` | `gateway` | Meaning |
|---|---|---|
| No | No | Normal login |
| Yes | No | Bypass SSO, require primary authentication |
| No | Yes | Check SSO without prompting for credentials |
| Yes | Yes | **Invalid intent, undefined behavior** |

Avoid URLs such as:

~~~text
/cas/login?service=ENCODED_SERVICE&renew=true&gateway=true
~~~

A custom login builder should use an enum **`NORMAL`**, **`RENEW`**, **`GATEWAY`** rather than two independent booleans. When an app has multiple filters or proxies, check that no global filter automatically appends `renew` to a `gateway` request.

## 8. Experience Matrix by Mode and TGT State

Table assumes no special custom CAS policies:

| Mode | Valid TGT Exists? | Primary Behavior | Ticket Returned to Service? | UX |
|---|---|---|---|---|
| Normal | No | Shows login challenge | After user succeeds | Interactive login |
| Normal | Yes | May SSO from TGT | Usually yes | Seamless transition |
| Renew | No | Primary auth | After user succeeds | Fresh login |
| Renew | Yes | Bypasses SSO, primary auth | After user succeeds | Re-prompted |
| Gateway | No | Returns to service without ticket | **No** | Remains anonymous |
| Gateway | Yes | May issue ST without prompting | Possibly yes | Optional login |
| Gateway | No TGT, but passive auth valid | May authenticate non-interactively | Possibly yes | No login prompt |
| Renew + Gateway | Any | Undefined | Unpredictable | Never configure |

**An ST being issued does not guarantee Spring authentication succeeds:** the client must still validate the ST, verify exact service, and confirm the user passes local policy.

## 9. Impact on Login Experience

### 9.1. Normal Mode Delivers Convenient SSO

Normal mode fits dashboards, work tools, and everyday access. Users already logged in via SSO on one app typically enter the next app without re-entering credentials. Good UX, though timeouts, sessions, logout, permissions, and sensitive actions still need separate management.

### 9.2. `renew` Increases Assurance but Adds Friction

`renew` fits situations requiring fresh primary authentication. However:
- Overusing it causes user fatigue.
- Users easily think “remember login” is broken.
- The CAS Server and auth infrastructure take extra load.
- If primary auth has multiple steps, the journey lengthens.
- If the app does not explain why, users suspect a security glitch.
- It does not automatically guarantee MFA or account matching.

Display a clear notice: **“To perform this sensitive action, please verify your identity again.”**

### 9.3. `gateway` Keeps Public Pages Unblocked

`gateway` suits portals with a public landing page that want personalization if the user already has SSO:
- Users with a TGT see personalized content after validation.
- Users without a TGT continue viewing public content.
- Provide an explicit Sign In button.
- No credential prompt appears merely from visiting the public landing page.
- Requires one-shot state and loop prevention.
- When the browser blocks CAS cookies, no-ticket falls back cleanly to normal anonymous mode.

## 10. Preventing `gateway` Redirect Loops

Common bug scenario:

~~~text
/welcome -> CAS gateway
        -> /welcome with no ticket
        -> Spring still sees anonymous
        -> redirects to CAS gateway again
        -> /welcome with no ticket
        -> ...
~~~

Design solutions:

1. Run gateway only once per browser/session context or within a TTL-bounded window.
2. Record a server-side **`gatewayAttempted`** marker or short-lived integrity-protected state.
3. When CAS returns without a ticket, the callback must permit anonymous access and render the public page.
4. Never treat no-ticket as an error that causes `ExceptionTranslationFilter` to trigger another login redirect.
5. Let the user explicitly click **Log In** to initiate **normal login**.
6. After the TTL expires or an explicit action occurs, gateway may be tried again rather than permanently locking the user anonymous.
7. Once the app already has a local `Authentication`, do not re-trigger gateway.
8. Ensure the state works across multiple nodes, proxies, and session stores.

Never treat a browser-modifiable `gatewayAttempted` query parameter as a `SecurityContext`; it is strictly a navigation signal, not identity proof.

### 10.1. Why Not Apply `gateway` Across the Entire Application?

If `/private` requires authentication and gateway returns no ticket, Spring will re-invoke the entry point automatically. Keep a dedicated public callback and clear policy: protected routes require normal/`renew` when requested by the user.

## 11. Spring Security CAS: Core APIs

Spring Security provides the **`spring-security-cas`** module for Servlet apps, separate from `oauth2Login`/`saml2Login`.

| Class | Purpose |
|---|---|
| `ServiceProperties` | `service` URL, `sendRenew`, ticket/service parameter names |
| `CasAuthenticationEntryPoint` | Redirects browser to CAS Server login |
| `CasAuthenticationFilter` | Receives `ticket` at callback, typically `/login/cas` |
| `CasAuthenticationProvider` | Validates ticket, builds `Authentication` |
| `Cas20ServiceTicketValidator` | Calls CAS Server's `/serviceValidate` |
| `CasAuthenticationToken` | `Authentication` after successful validation |
| `SecurityContextHolder` | Stores/reads current `Authentication` |
| `SecurityFilterChain` | Authorization rules, EntryPoint selection, and filters |

In Spring Security, **`ServiceProperties.setSendRenew(true)`** sends `renew` to **both the CAS login URL and the CAS validation URL** per Javadoc. By default `sendRenew=false` to support normal SSO.

There is no symmetric **`ServiceProperties.setGateway(true)`** setting. Gateway is handled by the Apereo Java CAS Client authentication filter in gateway mode or a custom optional-login flow. When integrating CAS client filters with Spring, ensure exactly one filter chain owns ticket extraction and callback handling; an ST cannot validate successfully twice.

### 11.1. Java Spring Bean Example for a Service with `renew`

File **`CasRenewBeans.java`**:

~~~java
package com.example.cas;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.cas.ServiceProperties;
import org.springframework.security.cas.web.CasAuthenticationEntryPoint;

@Configuration
public class CasRenewBeans {

    @Bean
    ServiceProperties serviceProperties() {
        ServiceProperties properties = new ServiceProperties();
        properties.setService(
                "https://portal.example.org/login/cas");
        properties.setSendRenew(true);
        return properties;
    }

    @Bean
    CasAuthenticationEntryPoint casEntryPoint(
            ServiceProperties properties) {
        CasAuthenticationEntryPoint entryPoint =
                new CasAuthenticationEntryPoint();
        entryPoint.setLoginUrl(
                "https://cas.example.org/cas/login");
        entryPoint.setServiceProperties(properties);
        return entryPoint;
    }
}
~~~

This is a **Java class with valid imports, not a standalone runnable CAS app**. You must add `CasAuthenticationFilter`, `CasAuthenticationProvider`, `TicketValidator`, `AuthenticationManager`, `SecurityFilterChain`, `UserDetailsService`, a CAS registered service, and a real CAS Server.

Configuring only two beans is insufficient to accept tickets or serve the application. Enabling `sendRenew=true` site-wide forces users to re-authenticate on every CAS login flow; consider designing targeted step-up for sensitive routes.

### 11.2. Maven Dependencies

Fragment inside a Spring Boot project with a parent/BOM:

~~~xml
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
~~~

## 12. Standalone Java 17 – Simulating Behavior

The program below **compiles and runs with `javac`/`java`**, without Spring or a CAS Server. It simulates normal/`renew`/`gateway` assuming no trust-auth or advanced policies.

File **`CasModesDemo.java`**:

~~~java
public class CasModesDemo {

    enum Mode { NORMAL, RENEW, GATEWAY }

    static String decide(Mode mode, boolean hasSso) {
        return switch (mode) {
            case NORMAL -> hasSso
                    ? "ST_FROM_SSO" : "SHOW_LOGIN";
            case RENEW -> "REQUIRE_PRIMARY_AUTH";
            case GATEWAY -> hasSso
                    ? "MAY_RETURN_ST"
                    : "RETURN_NO_TICKET";
        };
    }

    public static void main(String[] args) {
        System.out.println("normal/noSSO=" +
                decide(Mode.NORMAL, false));
        System.out.println("normal/SSO=" +
                decide(Mode.NORMAL, true));
        System.out.println("renew/noSSO=" +
                decide(Mode.RENEW, false));
        System.out.println("renew/SSO=" +
                decide(Mode.RENEW, true));
        System.out.println("gateway/noSSO=" +
                decide(Mode.GATEWAY, false));
        System.out.println("gateway/SSO=" +
                decide(Mode.GATEWAY, true));
    }
}
~~~

Run:

~~~bash
javac CasModesDemo.java
java CasModesDemo
~~~

Exact stdout:

~~~text
normal/noSSO=SHOW_LOGIN
normal/SSO=ST_FROM_SSO
renew/noSSO=REQUIRE_PRIMARY_AUTH
renew/SSO=REQUIRE_PRIMARY_AUTH
gateway/noSSO=RETURN_NO_TICKET
gateway/SSO=MAY_RETURN_ST
~~~

**Explanation:** `renew` requires primary authentication even when a TGT exists. `gateway` with no TGT and no silent auth returns without a ticket. With a TGT, `gateway` may issue an ST. This program **does not actually mint/validate STs**, test cryptography or networking, or model CAS advisory pages.

## 13. Standalone Java 17 – Building URLs Without Mixing Modes

File **`CasLoginUrlDemo.java`**:

~~~java
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public class CasLoginUrlDemo {

    enum Mode { NORMAL, RENEW, GATEWAY }

    private static final String LOGIN =
            "https://cas.example.org/cas/login";
    private static final String SERVICE =
            "https://portal.example.org/login/cas";

    static String build(Mode mode) {
        String service = URLEncoder.encode(
                SERVICE, StandardCharsets.UTF_8);

        String suffix = switch (mode) {
            case NORMAL -> "";
            case RENEW -> "&renew=true";
            case GATEWAY -> "&gateway=true";
        };

        return LOGIN + "?service=" + service + suffix;
    }

    public static void main(String[] args) {
        System.out.println(build(Mode.NORMAL));
        System.out.println(build(Mode.RENEW));
        System.out.println(build(Mode.GATEWAY));
    }
}
~~~

Run:

~~~bash
javac CasLoginUrlDemo.java
java CasLoginUrlDemo
~~~

Exact stdout:

~~~text
https://cas.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas
https://cas.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&renew=true
https://cas.example.org/cas/login?service=https%3A%2F%2Fportal.example.org%2Flogin%2Fcas&gateway=true
~~~

The enum permits only one mode per request. The fixed callback URL is URL-encoded with `URLEncoder` rather than reading an untrusted service URL from the HTTP request. The example only constructs strings; it does not guarantee the CAS Service Registry permits it and does not validate STs.

## 14. Step-Up for Sensitive Operations with a Local Spring Session

A common design mistake: the user already has a Spring local `Authentication`, yet a payment route requires recent re-authentication. A developer sets only `sendRenew=true` on the CAS entry point and assumes Spring will automatically call CAS on every route access.

In practice, while the local session stays authenticated, the CAS entry point **will not run**. You must build a freshness workflow:

~~~text
Logged-in user -> POST /payment/confirm-intent (+ CSRF)
                     |
                     v
              check permissions and business intent
                     |
                     +-- freshness met -> proceed with processing
                     |
                     +-- not met -> save pending action server-side with TTL
                                        |
                                        v
                                   redirect CAS renew
                                        |
                                        v
                                   receive ST, validate renew=true
                                        |
                                        v
                                   verify subject matches original user
                                        |
                                        v
                                   record time-bounded freshness evidence
                                        |
                                        v
                                   require final confirmation POST
~~~

Never execute a money transfer merely because a **GET callback** arrived with a ticket. Always re-check CSRF, intent, resource state, business authorization, and identity after reauth. If the user switches accounts during the CAS `renew` flow, **never attach the new account's freshness to the old account**.

Freshness must be stored server-side (timestamp, principal, CAS service, assurance policy/version), never read from a browser-editable query parameter.

## 15. Ticket Validation: Exact Service URL and One-Time ST

The CAS Protocol specifies:
- An ST is valid only for the service for which CAS issued the ticket.
- An ST may be used for **only one validation attempt**.
- An ST must never be reused once consumed.
- CAS should enforce a short expiration window for unused STs.
- The client must send `ticket`/`service` to the CAS validation endpoint over HTTPS.

Example:

~~~text
CAS login issued ST for:
  https://portal.example.org/login/cas

CAS validation must send service:
  https://portal.example.org/login/cas

CAS validation must send ticket:
  ST-EXAMPLE-ONE-TIME

CAS validation adds renew=true:
  only when required by policy
~~~

If a reverse proxy generates an internal `http` URL instead of public HTTPS, wrong port, extra trailing slash, or altered query values, validation can fail with service mismatch. Never disable service matching to work around proxy errors; configure the exact canonical HTTPS callback and trusted forwarded headers.

### 15.1. Protecting the ST While It Is in the URL

The browser may receive a redirect:

~~~text
https://portal.example.org/login/cas?ticket=ST-...
~~~

An ST is a short-lived bearer credential. Never log raw queries at ingress or analytics, never leak via `Referer`, and never share ticket URLs. After validation, redirect the user to a clean URL, and never retry the same ST after one validation attempt.

### 15.2. CAS Server Must Constrain Registered Services

The CAS Specification recommends filtering service URLs via the service management tool and permitting only HTTPS. Never take arbitrary `service` or `returnUrl` parameters from the user and pass them directly to CAS `/login`, as that risks open redirects, service confusion, and ticket leakage.

## 16. Gateway and Cookies/Browsers

Gateway may return no-ticket when:
- No TGC/TGT exists.
- The TGT has expired.
- The browser withholds the CAS cookie due to `SameSite`, `Secure`, privacy restrictions, or embedded contexts.
- The CAS Server cannot authenticate non-interactively.
- Proxy/iframe flows are blocked by browser policy.

Never conclude for certain that the user logged out or the account does not exist. Conclude only that **the current request did not establish a new CAS-authenticated identity**.

In SPAs or multi-node apps, anti-loop gateway state must fit session/cookie policies and load balancers. Never use a client-editable guest cookie to grant privileges; the `gatewayAttempted` marker serves UX only, not as a security credential.

## 17. Local Logout and CAS Logout Are Two Different Things

| Action | CAS TGT/TGC | Local Spring `HttpSession` |
|---|---|---|
| Normal SSO login | Used/continued | Created if ticket valid |
| `renew` | Does not necessarily delete TGT | App processes callback and freshness |
| `gateway` | Does not necessarily alter TGT | Creates auth if ST valid, else anonymous |
| Local Spring logout | CAS TGT usually remains | Invalidated |
| CAS `/logout` | CAS SSO terminated | Depends on SLO client support |
| CAS Single Logout | CAS may notify services | Participating SPs may clear sessions |

A user logging out locally and immediately logging back in via normal SSO **is not necessarily a bug**. The TGT still exists. `renew` can force fresh authentication, yet is not a federation-wide logout command. `gateway` may silently log the user back in if the TGT remains valid.

## 19. Testing Negative Cases and Security

| Case | Scenario | Expectation |
|---|---|---|
| N1 | `renew=true` and `gateway=true` in same request | Client must never construct the undefined combination |
| N2 | ST from normal SSO validated with `renew=true` | CAS rejects |
| N3 | Ticket reused | CAS rejects |
| N4 | ST issued for service A, validated at service B | CAS rejects |
| N5 | Gateway no-ticket yet app grants `Authentication` | Blocked; fails security test |
| N6 | No-ticket callback redirects to gateway endlessly | Test catches loop |
| N7 | Untrusted ticket validator TLS cert | Fails safely; never disables TLS |
| N8 | `service` URL taken from un-allowlisted query | Rejected |
| N9 | Spring local session authorized yet step-up TTL expired | Forces `renew` flow per policy |
| N10 | `renew` returns different user than original session | Aborts sensitive action |

| N12 | CAS TGC cookie blocked by browser | Gateway no-ticket, anonymous UX |
| N13 | Multi-tenant service URL with wrong issuer/tenant | Denies access in other tenant |
| N14 | User completed `renew` without MFA | Does not claim MFA achieved |
| N15 | Proxy alters HTTP/HTTPS hostname | Fix service URL / canonical routing |
| N16 | ST appears in analytics/access logs | Security/privacy defect |

| N18 | CAS logout yet another SP lacks SLO | Never claims all sessions cleared |

Integration tests must run against a CAS Server/test harness that mints and validates real STs. The two Java demos above verify only logic, not tickets, networking, or TLS.

## 20. Troubleshooting

| Symptom | Cause | What to Check |
|---|---|---|
| `renew` enabled yet enters app immediately | Local `SecurityContext` already active | Design explicit reauth flow, not just EntryPoint |
| CAS login `renew` succeeds yet validation fails | `renew` mismatch or ticket not from primary auth | Check login URL and validation request |
| Gateway receives no ticket | No TGT or browser withholds TGC | Anonymous is a valid result |
| Gateway redirects endlessly | Marker not saved, or callback is protected | Public callback, one-shot state, and TTL |
| Gateway displays login form | `gateway` not sent or CAS policy overrides | Check redirect chain and CAS configuration |
| Normal always prompts for password | TGT expired, cookie issue, or `renew` enabled | Check TGC/session/queries |
| Immediately SSOs again after logout | CAS TGT still alive | Distinguish local logout from CAS logout/SLO |
| `INVALID_TICKET` | Ticket reused, wrong service, `renew` validation mismatch | Check exact service, one-time use, mode |
| 404 `/login/cas` | Callback not monitored by CAS filter | Check `ServiceProperties` and filter URL |
| CAS validation TLS failure | Wrong truststore/CA/SAN | Fix TLS; never bypass certificate checks |
| User switches account after `renew` | Principal differs from original user | Abort transaction |
| Wrong roles after CAS login | `UserDetailsService`/`GrantedAuthority` mapping | Check business authorization separately |
| Gateway behaves differently across browsers | `SameSite`/third-party cookie restrictions | Test real browsers and anonymous fallback |
| CAS client breaks after version upgrade | Spring Security / CAS client dependency mismatch | Pin BOM and run integration tests |

## 21. Logging and Metrics

Distinguish these events:
- `cas_normal_redirect`, `cas_renew_redirect`, `cas_gateway_redirect`.
- `cas_gateway_no_ticket`: **do not count as an authentication failure**.
- `cas_gateway_ticket_validated`, `cas_renew_ticket_validated`.
- `cas_ticket_validation_failed` by reason.
- `cas_redirect_loop_prevented`, `cas_service_mismatch`.
- `cas_stepup_subject_mismatch`, `cas_timeout`.

Never log STs, TGTs, TGCs, passwords, session cookies, raw query strings containing tickets, or responses with PII. For correlation, use internal IDs and a proper privacy policy.

## 22. Implementation Checklist

- [ ] `NORMAL`/`RENEW`/`GATEWAY` modes clearly defined; never send both `renew` and `gateway`.
- [ ] Service URL is server-controlled HTTPS and registered at CAS.
- [ ] ST is validated once only, for the exact service, over HTTPS.
- [ ] When `renew` is required, both login and validation carry `renew=true`.
- [ ] Spring `ServiceProperties.setSendRenew(true)` is used only where appropriate.
- [ ] Never assume a global `renew` EntryPoint automatically steps up an active local `Authentication`.
- [ ] Freshness evidence enforces TTL, subject match, business authorization, and CSRF.
- [ ] `renew` is never treated by default as MFA.
- [ ] Gateway no-ticket renders an anonymous public page without looping.
- [ ] Manual normal login still works after a gateway no-ticket outcome.
- [ ] Cookies/browsers/ingress proxies tested across multiple browsers.
- [ ] Never trust arbitrary client-supplied `service`/`returnUrl` or forwarded headers.
- [ ] Never grant roles without a verified ticket.
- [ ] Local logout is never confused with CAS logout/SLO.
- [ ] No ST exposure in logs, referrers, or analytics.
- [ ] Positive and negative tests verified against real CAS.
- [ ] Versions pinned for CAS Server, Apereo Java CAS Client, and Spring Security CAS.

## 23. Review Questions

1. **What is `renew` used for?** Bypasses an old SSO session and requires primary authentication.
2. **What is `gateway` used for?** Probes SSO without prompting for credentials; without SSO, returns without a ticket.
3. **Is gateway returning without a ticket an error?** No.
4. **Does `renew` mean MFA?** No; separate assurance policies/evidence are required.
5. **Does `renew` log out the TGT?** Not by default.
6. **Can `renew` and `gateway` both be true?** No; protocol behavior is undefined.
7. **Why must `renew` be sent during validation?** To verify the ST was issued from primary authentication.
8. **Which Spring CAS API sends `renew` in both places?** `ServiceProperties.setSendRenew(true)`.
9. **If a local Spring `Authentication` already exists, does `renew` run automatically?** No; explicit reauth is required when policy demands it.
10. **How do TGT and ST differ?** TGT manages SSO; ST is a one-time ticket for a service.
11. **Does CAS gateway no-ticket make the user authenticated?** No.
12. **How do you prevent gateway loops?** One-shot/TTL marker and a public callback.
13. **When a TGT exists, how do normal and `renew` differ?** Normal can SSO; `renew` requires fresh primary auth.
14. **When no TGT exists, how do normal and `gateway` differ?** Normal prompts for credentials; `gateway` returns with no ticket.
15. **Can an ST be reused?** No; one validation attempt only.
16. **Can the service URL come from a user query param?** No, unless allowlisted.
17. **Can a user immediately SSO again after local logout?** Yes, if the CAS TGT remains valid.
18. **What if `renew` returns a different account?** Never attach freshness to the old user.
19. **What does `CasAuthenticationFilter` do?** Receives the ST at the callback and triggers authentication.
20. **Can `gateway` be used to protect `/admin`?** No; private routes require mandatory authentication.

**Summary:** In CAS, **`renew=true`** requires primary authentication instead of an existing SSO session and must be paired with **`renew=true` during ticket validation** when policy mandates fresh authentication. **`gateway=true`** enables credential-free SSO probing, returning to the service **without a ticket** when no session or silent auth exists. The two parameters **must never be combined**. In Spring Security, `ServiceProperties.setSendRenew(true)` supports `renew` at both login and validation; `gateway` requires an optional-login flow with a public callback, one-shot state, and proper anonymous handling. Never sacrifice ticket validation, exact service URLs, TLS, CSRF, or business authorization for faster UX.
