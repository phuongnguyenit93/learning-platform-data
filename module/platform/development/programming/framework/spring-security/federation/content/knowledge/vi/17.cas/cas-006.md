# Phân biệt CAS Protocol với SAML 2.0 Web Browser SSO trong Spring Security

## 1. Bài toán và mục tiêu học tập

Cả **CAS Protocol** và **SAML 2.0 Web Browser Single Sign-On (Web Browser SSO)** đều giúp một người dùng đăng nhập vào nhiều ứng dụng mà không phải nhập lại thông tin ở từng ứng dụng. Vì thế chúng thường bị mô tả chung chung là “redirect sang hệ thống SSO rồi quay về”. Mô tả đó đúng ở mức trải nghiệm, nhưng **sai nếu dùng để thiết kế, code và kiểm tra bảo mật**.

Trong **CAS Protocol**, browser thường đưa một **Service Ticket (ST)** ngắn hạn đến ứng dụng; ứng dụng dùng **kết nối trực tiếp tới CAS Server** để xác minh ST. Trong **SAML 2.0 Web Browser SSO**, browser thường mang **SAMLResponse chứa SAML Assertion** về Assertion Consumer Service (ACS); Service Provider (SP) dùng **trust/key/metadata đã cấu hình** để kiểm tra chữ ký, issuer, audience, subject, conditions và các ràng buộc của response. SAML cũng có **Artifact binding** dùng thêm back-channel, nhưng không nên lấy nó làm định nghĩa mặc định của Web Browser SSO.

Bài học thuộc **Spring Security - federation → Nền tảng CAS**, chủ đề **“Phân biệt CAS protocol với SAML2 Web Browser SSO”**. Nội dung hướng đến Java 17+, Spring Boot 3.x, Spring Security 6.x/7.x **Servlet/MVC**, với lưu ý API thay đổi theo phiên bản.

Sau bài, bạn có thể:

1. Vẽ đúng luồng CAS login và SAML Web Browser SSO, chỉ rõ dữ liệu đi qua **browser** và bước server xác minh.
2. Phân biệt CAS `Service Ticket (ST)`, `Ticket-Granting Ticket (TGT)`, `Ticket-Granting Cookie (TGC)` với SAML `AuthnRequest`, `Response` và `Assertion`.
3. Giải thích lý do CAS cần `/serviceValidate` và lý do SAML SP cần **X.509 verification credentials và XML signature validation**.
4. So sánh CAS `service` với SAML `entityID`, `ACS`, `AudienceRestriction`, `Destination` và `InResponseTo`.
5. Phân biệt CAS `renew/gateway` với SAML `ForceAuthn/IsPassive` mà không khẳng định chúng tương đương tuyệt đối.
6. Nhận diện CAS proxy tickets và SAML IdP proxying là **các cơ chế khác nhau**.
7. Biết cách tích hợp bằng các module/lớp Spring Security tương ứng; không đưa CAS Service Ticket vào `Saml2WebSsoAuthenticationFilter` hoặc SAMLResponse vào `CasAuthenticationFilter`.
8. So sánh logout, cookie, thời hạn phiên, tái sử dụng SSO, xử lý lỗi, quyền ứng dụng và cách migration có broker.
9. Thực hành Java 17 mô phỏng quy tắc **service-bound, one-time ticket**, kiểm thử đúng hành vi ST mà không giả vờ xây CAS Server thực.
10. Lập checklist QA khi một tổ chức chuyển từ CAS Protocol sang SAML 2.0 hoặc vận hành hai giao thức song song.

**Phạm vi:** nói về **CAS Protocol** do Apereo CAS triển khai và **SAML 2.0 Web Browser SSO Profile** theo OASIS. Một sản phẩm **Apereo CAS Server** có thể hỗ trợ **nhiều giao thức** (CAS, SAML 2, OIDC, OAuth2...), nhưng việc sản phẩm mang tên “CAS” **không biến mọi endpoint của nó thành CAS Protocol**.

## 2. Chốt thuật ngữ trước khi đi vào luồng

| Thuật ngữ | CAS Protocol | SAML 2.0 Web Browser SSO |
| --- | --- | --- |
| Hệ thống tập trung | **CAS Server** | **Identity Provider (IdP)** / Asserting Party |
| Ứng dụng cần đăng nhập | **CAS client / service** | **Service Provider (SP)** / Relying Party |
| Yêu cầu khởi đầu | Redirect `/login?service=...` | SAML `AuthnRequest` gửi tới IdP SSO endpoint hoặc IdP-initiated theo profile |
| Dữ liệu về qua browser | `ticket=ST-...` (opaque Service Ticket) | `SAMLResponse` (Base64 của SAML XML; thường HTTP POST) |
| Kiểm chứng chính | CAS client gửi ST và `service` đến CAS validation endpoint | SP xác minh SAML Response/Assertion với metadata và signing certificate tin cậy |
| Kết quả định danh | `cas:user` và thuộc tính nếu phiên bản/endpoint có | `NameID`, `Subject`, `AttributeStatement` |
| Phiên SSO trung tâm | **TGT** phía CAS Server, **TGC** phía browser | Phiên/cookie của IdP; chuẩn SAML không đặt tên tương đương TGT/TGC |
| Phiên ứng dụng | `HttpSession/SecurityContext` tùy client | `HttpSession/SecurityContext` tùy SP |
| Điểm kết thúc quan trọng | `/serviceValidate`, `/p3/serviceValidate` | `AssertionConsumerService (ACS)` |
| Mô hình trust | CAS endpoint, TLS server validation, service allow-list, ST validation | SAML metadata/entityID, IdP signing keys, XML signature và assertion conditions |
| Logout liên kết | CAS logout + SLO triển khai/hỗ trợ tùy client và server | SAML Single Logout Profile và message `LogoutRequest/LogoutResponse` |
| Đơn vị bearer có thể replay? | ST phải **one-time** | SAML Response/Assertion cũng phải chống replay bằng request/session/time/ID theo policy |

**Lưu ý:** “CAS” cũng có thể được dùng như tên **một nền tảng danh tính** tích hợp SAML/OIDC. Bảng này so **giao thức**, không chấm điểm mọi phiên bản/phần mềm Apereo CAS.

## 3. CAS Protocol là gì?

CAS (**Central Authentication Service**) là mô hình xác thực tập trung dựa trên **ticket**. Một ứng dụng muốn đăng nhập người dùng chuyển browser tới CAS Server với URL định danh ứng dụng gọi là **service URL**.

Thông thường:
1. Client chuyển browser tới `https://cas.example.org/cas/login?service=...`.
2. CAS kiểm tra phiên đăng nhập tập trung hiện có; nếu cần, xác thực người dùng.
3. CAS phát **Service Ticket** dành riêng cho service đã đăng ký.
4. Browser quay về service callback mang `ticket=ST-...`.
5. **Backend ứng dụng** gọi `https://cas.example.org/cas/serviceValidate?service=...&ticket=...` bằng HTTPS.
6. CAS Server kiểm tra ST, service tương ứng, thời hạn, một lần sử dụng và trả kết quả định danh hoặc lỗi.
7. Ứng dụng tạo phiên local và áp dụng authorization riêng.

### CAS login sequence

~~~mermaid
sequenceDiagram
    participant B as Browser
    participant APP as Spring Security CAS client
    participant CAS as CAS Server
    B->>APP: GET /private
    APP-->>B: 302 /cas/login?service=https://app.example.org/login/cas
    B->>CAS: GET /cas/login?service=...
    CAS->>CAS: Kiểm tra TGC/TGT hoặc xác thực người dùng
    CAS-->>B: 302 https://app.example.org/login/cas?ticket=ST-...
    B->>APP: GET /login/cas?ticket=ST-...
    APP->>CAS: Backend HTTPS /cas/serviceValidate?service=...&ticket=ST-...
    CAS->>CAS: Validate ST đúng service, chưa dùng, chưa hết hạn
    alt Ticket hợp lệ
        CAS-->>APP: XML authenticationSuccess + user
        APP->>APP: Ánh xạ principal và quyền, tạo SecurityContext
        APP-->>B: App session + redirect tài nguyên
    else Ticket không hợp lệ
        CAS-->>APP: XML authenticationFailure
        APP-->>B: Xử lý login failure, không cấp Authentication
    end
~~~

Điểm quan trọng là **browser không tự báo user đã được CAS xác thực**. Nó chỉ chuyển **ST**. Bên ứng dụng phải gọi CAS Server và tin **kết quả validation đến từ CAS Server hợp lệ**. Một chuỗi trông giống `ST-123` trong URL không phải một user đã đăng nhập.

## 4. Service Ticket, TGT và TGC không phải một loại

### 4.1 Ticket-Granting Ticket (TGT)

- TGT biểu diễn phiên đăng nhập tập trung tại CAS Server.
- CAS quản lý TGT theo session chính sách, thời gian sống, hoạt động và logout.
- TGT cho phép CAS phát các Service Ticket mới cho dịch vụ khác nếu điều kiện cho phép.
- **Không đưa TGT về ứng dụng để nó gọi serviceValidate**.

### 4.2 Ticket-Granting Cookie (TGC)

- Browser nhận/giữ cookie CAS dùng để tham chiếu phiên TGT.
- CAS đọc TGC khi người dùng đi đến CAS login endpoint.
- TGC thuộc **domain CAS**, không phải cookie HttpSession của ứng dụng.
- Xóa `JSESSIONID` của ứng dụng không tự xóa TGC của CAS Server.
- Một cookie còn tồn tại không bảo đảm TGT vẫn hiệu lực (server-side có thể revoke).

### 4.3 Service Ticket (ST)

- ST là một **chuỗi opaque** thường có tiền tố minh họa `ST-`.
- CAS phát ST **cho một service URL cụ thể**.
- Theo CAS Protocol 2.0, ST chỉ hợp lệ **một lần thử xác minh**; sau lần validation, dù thành công hay thất bại, CAS phải vô hiệu hóa ST.
- ST phải có thời hạn ngắn để giảm khả năng bị lộ rồi sử dụng.
- ST **không phải JWT và không phải SAML Assertion**; ứng dụng không thể Base64-decode ST thành user.
- Đọc được ST trong browser URL không chứng minh user là ai. App phải gửi ST về CAS để xác minh.

### Ba vòng đời khác nhau

| Đối tượng | Nơi liên quan | Có thể còn khi user logout local? |
| --- | --- | --- |
| CAS TGT/TGC | CAS Server/browser trên domain CAS | **Có**; tùy logout trung tâm |
| CAS Service Ticket | Một giao dịch đăng nhập tới một service | Thường đã bị consume khi validation |
| SP/CAS client HttpSession | Ứng dụng đã đăng nhập | Không nếu logout local đã invalidated |

Không coi ST là token truy cập API dài hạn. Nó **không thích hợp** để gắn trong header Bearer cho mọi request ứng dụng.

## 5. CAS endpoint và kết quả validation theo phiên bản

Các endpoint phổ biến:

| Endpoint | Mục đích | Lưu ý |
| --- | --- | --- |
| `/cas/login` | CAS xác thực, cấp ST; nhận tham số `service` | CAS context path có thể cấu hình khác `/cas` |
| `/cas/logout` | Kết thúc CAS SSO session theo policy | Không đồng nghĩa mọi app local session bị hủy |
| `/cas/validate` | CAS Protocol 1.0, text response đơn giản | Không dùng làm mặc định cho attribute-rich CAS 3 |
| `/cas/serviceValidate` | CAS 2.0 XML service-ticket validation | Hợp đồng `service` + `ticket` |
| `/cas/p3/serviceValidate` | CAS 3.0 validation và user attributes | Không tự mặc định có mọi attribute |
| `/cas/proxyValidate` | Kiểm tra service/proxy ticket theo profile | Proxy trust/chain riêng |
| `/cas/p3/proxyValidate` | Proxy validation có CAS 3 attributes | Cần cấu hình proxy đúng |
| `/cas/proxy` | Phát Proxy Ticket dựa trên PGT, targetService | Không phải SAML IdP proxy |

Các path là **endpoint CAS protocol**. Một server Apereo CAS cũng có thể xuất SAML 2.0 endpoints với tên path khác; phải xem cấu hình service registry và protocol của từng endpoint, không đoán theo hostname.

### 5.1 Ví dụ serviceValidate hợp lệ

Server-side request (để minh họa; giá trị ticket và service không có thật):

~~~http
GET /cas/serviceValidate?ticket=ST-demo-one-time&service=https%3A%2F%2Fapp.example.org%2Flogin%2Fcas HTTP/1.1
Host: cas.example.org
~~~

CAS XML success:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>opaque-user-42</cas:user>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

CAS 3.0 với `/p3/serviceValidate` có thể trả thêm:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationSuccess>
    <cas:user>opaque-user-42</cas:user>
    <cas:attributes>
      <cas:department>finance</cas:department>
      <cas:employeeType>staff</cas:employeeType>
    </cas:attributes>
  </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Các đoạn là **ví dụ cấu trúc**, không phải response từ CAS đang hoạt động. `cas:user` hoặc attributes cần được dùng theo chính sách **identity mapping/authorization**, không tự động gán quyền quản trị từ string bất kỳ. Chỉ tin response nếu backend thực sự gọi endpoint CAS đáng tin qua HTTPS, verify TLS, và CAS đã validation ST.

### 5.2 CAS XML failure

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
  <cas:authenticationFailure code="INVALID_SERVICE">
    Ticket was issued for a different service
  </cas:authenticationFailure>
</cas:serviceResponse>
~~~

Các code phổ biến trong CAS 2.x:
- `INVALID_REQUEST`: thiếu tham số bắt buộc.
- `INVALID_TICKET`: ticket sai, hết hạn, đã dùng hoặc không đáp ứng renew policy.
- `INVALID_SERVICE`: ticket được cấp cho service khác.
- `INTERNAL_ERROR`: lỗi nội bộ khi validation.

**Đây là CAS error codes**, không phải SAML `StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:Responder"`. CAS ticket validation failure có thể đi qua HTTP response bình thường; không lấy một HTTP 200 đơn thuần làm xác thực thành công.

## 6. Vì sao CAS service URL là một yếu tố bảo mật?

Trong CAS, tham số `service` cho biết **dịch vụ đích** mà CAS được phép trả ST về. Khi validation, ứng dụng phải gửi **cùng service URL** tương ứng với ST đã phát.

Ví dụ:

~~~text
Đã cấp ST cho:
  https://app.example.org/login/cas

App validate bằng:
  https://app.example.org/login/cas

=> Hợp lệ nếu ticket và điều kiện khác đúng.

App validate bằng:
  http://internal-service:8080/login/cas

=> Có thể INVALID_SERVICE dù hai URL trỏ tới cùng hệ thống qua proxy.
~~~

Vấn đề thường xảy ra khi:
- Public HTTPS bị reverse proxy chuyển thành HTTP nội bộ.
- Host/port/path hoặc context path khác giữa cấu hình entry point và validator.
- Có dấu slash/query parameter khác khiến CAS service comparison không khớp.
- Service URL chưa được đăng ký/allow-list ở CAS Server.
- Ứng dụng tự lấy `service` từ query user rồi gửi không kiểm soát, tạo open redirect hoặc ticket leakage.

**Không sửa bằng cách cho CAS chấp nhận mọi service wildcard không kiểm soát.** Dùng public canonical service URL, đăng ký service theo allow-list, thiết lập forwarded headers chỉ từ proxy đáng tin và kiểm thử đúng flow.

Service URL của CAS là **chỉ định một callback/service cụ thể**, không tương đương với mọi yếu tố SAML `Audience/Recipient/ACS/Issuer` (chúng tách thành nhiều ràng buộc).

## 7. SAML 2.0 Web Browser SSO là gì?

SAML (**Security Assertion Markup Language**) 2.0 do OASIS chuẩn hóa gồm:
- **Assertions**: phát biểu đã xác thực về subject, conditions và attributes.
- **Protocols**: thông điệp yêu cầu/phản hồi như `AuthnRequest` và `Response`.
- **Bindings**: cách vận chuyển SAML qua HTTP, chẳng hạn **HTTP-Redirect**, **HTTP-POST** và **HTTP-Artifact**.
- **Profiles**: quy định cách kết hợp protocol + binding để giải quyết tình huống, ví dụ **Web Browser SSO Profile**.

Trong phổ biến **SP-initiated Web Browser SSO**:
1. Browser truy cập ứng dụng Spring Security SP.
2. SP tạo `AuthnRequest` với ID, issuer, destination và ràng buộc ACS/ProtocolBinding thích hợp.
3. Browser chuyển AuthnRequest sang IdP SSO endpoint, thường bằng Redirect.
4. IdP xác thực user hoặc tái sử dụng SSO session theo chính sách, tạo SAML Response chứa Assertion.
5. Browser **HTTP POST** form field `SAMLResponse` về ACS của SP.
6. SP parse, xác minh chữ ký và các điều kiện SAML, xử lý correlation rồi tạo Authentication.

**Điểm phân biệt với CAS:** SP thường **không gọi CAS-style /serviceValidate với một ST opaque**. Trong SAML HTTP-POST, dữ liệu xác thực nằm trong **Response/Assertion** mà SP phải xác minh theo trust/cert; không gọi một điểm ticket validation cố định của IdP như CAS. **Artifact binding** là biến thể SAML cần back-channel ArtifactResolve, nhưng là **giao thức/binding khác**, không biến SAML Artifact thành CAS Service Ticket.

### SAML SP-initiated flow

~~~mermaid
sequenceDiagram
    participant B as Browser
    participant SP as Spring Security SAML SP
    participant IDP as SAML IdP
    B->>SP: GET /private
    SP->>SP: Tạo AuthnRequest với ID, Issuer, ACS
    SP-->>B: 302 tới IdP SSO với SAMLRequest
    B->>IDP: GET SingleSignOnService
    IDP->>IDP: Xác thực user / dùng IdP SSO session theo policy
    IDP-->>B: HTML form chứa SAMLResponse (+ RelayState)
    B->>SP: POST /login/saml2/sso/corp
    SP->>SP: Verify XML Signature, Issuer, Audience, Time, Subject, InResponseTo
    alt SAML hợp lệ
        SP->>SP: Tạo Saml2Authentication / SecurityContext
        SP-->>B: HttpSession + redirect protected route
    else SAML không hợp lệ
        SP-->>B: Authentication failure, không tạo session mới
    end
~~~

Với **IdP-initiated Web Browser SSO**, IdP có thể phát Response mà SP không tạo AuthnRequest trước đó. Cần quyết định **có cho phép unsolicited response hay không** theo framework/profile/trust policy, không tự tắt mọi kiểm tra `InResponseTo` để phục vụ migration.

## 8. Cấu trúc AuthnRequest, Response và Assertion

### 8.1 AuthnRequest

Ví dụ rút gọn:

~~~xml
<samlp:AuthnRequest
    xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
    xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
    ID="_req-001"
    Version="2.0"
    IssueInstant="2026-11-07T03:00:00Z"
    Destination="https://idp.example.org/saml/sso"
    AssertionConsumerServiceURL="https://app.example.org/login/saml2/sso/corp">
  <saml:Issuer>https://app.example.org/saml/metadata</saml:Issuer>
</samlp:AuthnRequest>
~~~

Đây là **XML minh họa chưa ký**, chưa có metadata/cert/trust phù hợp, không gửi production. `AuthnRequest@ID` dùng để SP liên hệ Response với request đã phát, khác với CAS ST.

### 8.2 Response và Assertion

Cấu trúc rút gọn để nhận diện các phần:

~~~xml
<samlp:Response
    xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
    xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
    ID="_resp-001"
    InResponseTo="_req-001"
    Version="2.0"
    IssueInstant="2026-11-07T03:00:05Z"
    Destination="https://app.example.org/login/saml2/sso/corp">
  <saml:Issuer>https://idp.example.org/issuer</saml:Issuer>
  <samlp:Status>
    <samlp:StatusCode
        Value="urn:oasis:names:tc:SAML:2.0:status:Success"/>
  </samlp:Status>
  <saml:Assertion Version="2.0" ID="_assert-001"
                  IssueInstant="2026-11-07T03:00:05Z">
    <saml:Issuer>https://idp.example.org/issuer</saml:Issuer>
    <saml:Subject>
      <saml:NameID>opaque-user-42</saml:NameID>
    </saml:Subject>
  </saml:Assertion>
</samlp:Response>
~~~

**Ví dụ này cố ý tối giản** để thấy tên các phần tử; **không có XML Signature**, Conditions, AudienceRestriction, SubjectConfirmation và các yếu tố đầy đủ, nên **không phải SAML Response được chấp nhận**. Một SP đúng chuẩn không được tạo phiên từ XML này chỉ vì `StatusCode=Success`.

Trong SAML Response thật, cần đánh giá:
- Chữ ký Response và/hoặc Assertion theo profile/chính sách của SP;
- IdP issuer và verification certificate tin cậy;
- `AudienceRestriction` cho đúng SP entity ID;
- `Destination` và SubjectConfirmationData `Recipient` đúng ACS;
- `NotBefore`, `NotOnOrAfter`, IssueInstant, clock skew;
- `InResponseTo` khớp AuthnRequest đối với SP-initiated flow;
- Subject/NameID, authentication statements, replay prevention;
- Decryption nếu IdP gửi `EncryptedAssertion`;
- App-local account/permission policy sau xác thực.

**Đừng tự parse XML bằng XPath rồi lấy NameID làm user** trước khi verification. Dùng provider OpenSAML/Spring Security.

## 9. So sánh luồng CAS với SAML 2.0 ở từng HTTP hop

| Câu hỏi | CAS Protocol | SAML 2.0 Web Browser SSO |
| --- | --- | --- |
| Browser tới hệ thống tập trung bằng gì? | Redirect `/login?service=...` | Redirect/POST `SAMLRequest` chứa AuthnRequest (SP-initiated) |
| Hệ thống tập trung trả về browser cái gì? | Redirect URL service kèm `ticket=ST-...` | SAMLResponse ở HTTP-POST form; binding khác nếu profile hỗ trợ |
| App nhận callback qua method gì thường gặp? | **GET** service callback với query `ticket` | **POST** ACS với form field `SAMLResponse` |
| Dữ liệu về qua browser có đủ để xác thực chưa? | Chưa; cần CAS backend validation | Chưa; cần XML signature + SAML condition validation |
| App có server-to-server validation mặc định? | Có: CAS `/serviceValidate` | Không theo cách CAS ST, trừ profile/binding như Artifact có resolution |
| Bằng chứng danh tính thường ở đâu? | XML validation response từ CAS Server | SAML Assertion trong Response từ IdP |
| Một lần sử dụng ràng buộc bởi gì? | CAS Server **consume ST** ở validation | SP kiểm tra IDs/correlation/conditions/replay policy |
| Trust source chủ yếu | CAS URL cố định, HTTPS/TLS, ST+service, CAS policy | Metadata/entity IDs, trusted signing cert, XML Signature, conditions |
| Phát phiên local khi nào? | Sau khi ticket validation pass | Sau khi SAML response/assertion validation pass |
| Nếu browser chỉ quay về với `ticket`? | Đây là CAS-style callback | Không phải SAMLResponse |
| Nếu browser POST `SAMLResponse`? | Không phải CAS `serviceValidate` | Đây là SAML ACS input |
| App nhìn thấy session central IdP/CAS trực tiếp? | Không | Không |

**Tóm tắt:** CAS ST thường là **thẻ tra cứu được CAS Server xác minh online**; SAML Assertion là **thông điệp có cấu trúc và chữ ký cần SP tự xác minh dựa trên trust**. Đây là khác biệt cơ chế, không chỉ khác tên trường trong URL.

## 10. Trust boundary: “tin CAS Server” khác “tin SAML signing key”

### 10.1 CAS Protocol: trust dựa trên ticket validation

CAS client phải:
1. Gửi ST và service URL đúng tới CAS Server **đã cấu hình**.
2. Dùng HTTPS và kiểm tra TLS certificate/hostname của CAS endpoint.
3. Parse XML validation response an toàn; không nhận dữ liệu từ endpoint CAS do browser chỉ định.
4. Chỉ tạo principal nếu kết quả là `cas:authenticationSuccess` từ CAS Server tin cậy.
5. Không bỏ qua `INVALID_TICKET/INVALID_SERVICE`, không chấp nhận ST cũ.
6. Kiểm tra proxy chain khi dùng Proxy Ticket và authorization cho client/service.
7. Ánh xạ user/roles theo policy nội bộ, không cấp quyền vì bất kỳ attribute string nào.

Ở CAS Protocol thuần, **ST không cần tự mang chữ ký XML** và ứng dụng cũng không “verify ST signature offline”; bằng chứng nhận được bằng **CAS Server kiểm tra ticket qua kênh đáng tin**.

### 10.2 SAML 2.0: trust dựa trên issuer + signature + conditions

SAML SP phải:
1. Có **RelyingPartyRegistration** cho đúng IdP/entity ID.
2. Tin các public signing X.509 certificates của IdP qua metadata/kênh đã được duyệt.
3. Xác minh chữ ký của Response/Assertion theo thiết lập tương thích profile.
4. Kiểm tra `Issuer`, `AudienceRestriction`, `Destination/Recipient`, thời gian, SubjectConfirmation và correlation.
5. Không tin certificate nằm trong Response nếu chưa gắn với IdP registration/trust độc lập.
6. Kiểm tra encrypted assertions bằng SP private key khi IdP mã hóa.
7. Không tự “fix” login bằng cách tắt signature/audience/time/recipient checks.

**HTTPS vẫn cần thiết** để bảo vệ browser và metadata endpoints. Nhưng TLS certificate của IdP web server **không tự là chứng thư SAML ký Assertion**. Một URL `https://idp.example.org` hoạt động không chứng minh bất kỳ SAMLResponse tự khai issuer đó là hợp lệ.

### 10.3 Đều có session local sau login

Cả CAS và SAML có thể cùng kết thúc ở một **Spring Security Authentication/SecurityContext/HttpSession**. Khi session ứng dụng còn, nó **không tự hỏi lại CAS hoặc IdP mỗi request**. Việc thu hồi quyền, khóa tài khoản và logout cần cơ chế riêng theo rủi ro.

## 11. “service” của CAS so với các định danh SAML

| CAS | SAML gần tương ứng về mục đích | Vì sao không phải mapping 1:1? |
| --- | --- | --- |
| `service=https://app.../login/cas` | SP ACS URL, Recipient/Destination | CAS thường dùng một service URL để cấp và validate ST; SAML tách endpoint nhận, recipient và conditions |
| CAS service allow-list | IdP cấu hình SP entity ID, ACS allow-list | Một bên quản lý service URLs, bên kia quản lý SAML registration/metadata |
| CAS username/user attributes | NameID/AttributeStatement | Identifiers, formats, qualifiers và semantics có thể khác |
| CAS ST | SAML Response/Assertion | ST là opaque one-time credential, Assertion là XML với chữ ký/conditions |
| CAS TGT/TGC | IdP SSO session/cookie | Vòng đời cùng loại trải nghiệm nhưng không cùng cấu trúc protocol |
| CAS renew | SAML ForceAuthn | Gần ý định reauthentication nhưng nghĩa vụ/điều kiện/cơ chế khác |
| CAS gateway | SAML IsPassive | Cùng nhu cầu ít tương tác nhưng failure/response khác |
| CAS PGT/PT | SAML proxying/artifact (khái niệm có vẻ gần) | **Không trao đổi được**; khác protocol, issuer/trust và message lifecycle |

**Đừng tìm một cấu hình “chuyển thẳng” ST thành Assertion** bằng cách đổi tên query parameter. Đó là đổi giao thức, cần một điểm **broker/adapter** thực thi đầy đủ validation của một bên rồi tạo thông điệp mới theo giao thức bên kia.

## 12. CAS renew/gateway và SAML ForceAuthn/IsPassive

CAS Protocol có hai tham số được dùng phổ biến trong login:

### renew

~~~text
https://cas.example.org/cas/login?service=...&renew=true
~~~

`renew` yêu cầu login mới dựa trên **primary credentials** theo CAS spec thay vì chỉ hưởng phiên SSO hiện tại. Với ticket validation, có thể dùng `renew=true` để bảo đảm ST được phát sau xác thực theo điều kiện mà CAS đòi hỏi.

### gateway

~~~text
https://cas.example.org/cas/login?service=...&gateway=true
~~~

`gateway` yêu cầu CAS **không đòi người dùng nhập credential tương tác**. Nếu không thể xác thực không tương tác, CAS có thể chuyển browser về service **không kèm ticket** để app biết không có SSO im lặng.

Trong SAML 2.0:
- `AuthnRequest ForceAuthn="true"`: yêu cầu IdP xác thực trực tiếp thay vì chỉ dựa trên security context trước đó, theo SAML Core.
- `AuthnRequest IsPassive="true"`: yêu cầu xử lý không cần IdP/user agent visibly take control of UI; nếu không thể, IdP trả lỗi phù hợp, ví dụ `NoPassive`.

| Ý định sản phẩm | CAS | SAML |
| --- | --- | --- |
| Login SSO thông thường | Không gửi renew/gateway | ForceAuthn=false, IsPassive=false hoặc vắng |
| Muốn kiểm tra người dùng không tương tác | `gateway=true` | `IsPassive=true` |
| Muốn xác thực mới | `renew=true` | `ForceAuthn=true` |
| Không có session cho silent login | CAS redirect về service **không có ticket** | SAML responder có thể trả lỗi `NoPassive` trong Response |
| Vừa ép renew vừa gateway | CAS spec không định nghĩa nghĩa rõ khi dùng chung; tránh | SAML đặt quy tắc khi ForceAuthn và IsPassive cùng true; không được phá yêu cầu passive |

**Không coi hai bộ cờ là tương đương tuyệt đối**:
- CAS renew có khái niệm primary credentials; SAML ForceAuthn không mặc định bắt người dùng nhập lại password hay dùng MFA.
- CAS gateway thường có **callback không kèm ST** khi không thể; SAML IsPassive thường có **SAML Response status lỗi**.
- Một ứng dụng migration phải test IdP/CAS policy thực tế, không thay tên cờ rồi khẳng định cùng mức assurance.

## 13. CAS proxy tickets khác SAML proxying

CAS Protocol có cơ chế **proxy authentication** khi service A cần gọi service B nhân danh người dùng:
1. Service A xác minh ST và có thể yêu cầu **Proxy-Granting Ticket (PGT)** qua `pgtUrl` callback.
2. CAS Server gửi thông tin PGT về callback đáng tin; A liên hệ `pgtIou` với kết quả validation.
3. A dùng PGT xin **Proxy Ticket (PT)** cho `targetService` B.
4. B gọi endpoint `/proxyValidate` với PT, target service, và kiểm tra **proxy chain/policy**.
5. App B áp dụng authorization phù hợp đối với principal và các proxy trung gian.

Trong SAML:
- Có thể có **IdP proxying** theo `Scoping/ProxyCount/IDPList` và các profile/điều kiện riêng.
- Có **SAML Artifact binding** để chuyển reference qua browser và resolve qua back-channel.
- Có `SubjectConfirmation`, audience, delegation extensions/profile khác.

Các cơ chế này **không phải CAS PGT/PT**. Không đưa một Proxy Ticket CAS vào SAML ArtifactResolve; không dùng SAML Artifact làm CAS ST. Nếu hệ thống phải hỗ trợ delegation/hop qua broker, xây trust/claim mapping rõ, validate đúng protocol ở cả hai phía và giữ audit provenance.

## 14. CAS Server có hỗ trợ SAML không, và điều đó có ý nghĩa gì?

Apereo CAS Server là **sản phẩm server** có thể hỗ trợ nhiều protocol. Một deployment có thể cho:
- Ứng dụng legacy A login bằng CAS Protocol: `/cas/login?service=...`.
- Ứng dụng B login bằng SAML 2.0: `AuthnRequest → SAMLResponse`.
- Ứng dụng C login bằng OpenID Connect: `/authorize → code → token endpoint`.

Tất cả có thể dùng cùng identity backend hoặc SSO policy, nhưng **đường xác thực/trust của từng client khác nhau**.

Ví dụ, không thể kết luận:
> “Server tên CAS nên SAML client chỉ cần gọi /serviceValidate”.

Không đúng: `/serviceValidate` là CAS Protocol. SAML SP cần cấu hình IdP entityID, SingleSignOnService, signing certificates/metadata, ACS và validation của SAML.

Ngược lại, một SAML IdP phía sau broker không trực tiếp cấp CAS ST cho app legacy trừ khi broker/server thực hiện chức năng CAS Server ở phía client legacy.

## 15. Spring Security CAS: thành phần liên quan

Spring Security có module tích hợp CAS qua `spring-security-cas`. Theo tài liệu, những lớp quan trọng là:

| Thành phần | Trách nhiệm |
| --- | --- |
| `ServiceProperties` | Cấu hình service callback URL và `sendRenew` |
| `CasAuthenticationEntryPoint` | Redirect unauthenticated browser đến CAS `/login?service=...` |
| `CasAuthenticationFilter` | Nhận `ticket` ở callback (thường `/login/cas`) |
| `CasAuthenticationProvider` | Xác minh CAS ticket qua validator rồi tạo Authentication |
| `Cas20ServiceTicketValidator` | Client library xác minh ST qua CAS 2.0 `/serviceValidate` |
| `Cas20ProxyTicketValidator` | Hỗ trợ proxy tickets khi có yêu cầu và policy |
| `AuthenticationUserDetailsService` | Ánh xạ CAS principal sang authorities trong Spring |
| `CasAuthenticationToken` | Authentication được Spring tạo sau khi CAS validation thành công |
| `ServiceAuthenticationDetailsSource` | Trường hợp cần xác định service URL động theo request |

### Điều kiện kết nối CAS chuẩn

Trong tài liệu Spring Security, mẫu cấu hình XML truyền thống thể hiện:

~~~xml
<bean id="serviceProperties" class="org.springframework.security.cas.ServiceProperties">
  <property name="service"
            value="https://app.example.org/login/cas"/>
  <property name="sendRenew" value="false"/>
</bean>

<bean id="casEntryPoint"
      class="org.springframework.security.cas.web.CasAuthenticationEntryPoint">
  <property name="loginUrl" value="https://cas.example.org/cas/login"/>
  <property name="serviceProperties" ref="serviceProperties"/>
</bean>

<bean id="casFilter"
      class="org.springframework.security.cas.web.CasAuthenticationFilter">
  <property name="authenticationManager" ref="authenticationManager"/>
</bean>
~~~

**Đây là một trích đoạn cấu hình minh họa, không phải XML Spring ApplicationContext hoàn chỉnh**: `authenticationManager`, provider, ticket validator, UserDetailsService, filter chain và namespaces còn cần khai báo. Các bean thực phải được wiring vào đúng Spring Security filter chain. Tài liệu CAS của Spring có ví dụ namespace XML được viết từ lịch sử Spring Security cũ, **không copy nguyên cấu trúc config vào dự án Boot 3.x/7.x mà không kiểm tra phiên bản**.

### Mảnh Java cấu hình ServiceProperties

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.cas.ServiceProperties;

@Configuration
public class CasServicePropertiesConfig {

    @Bean
    ServiceProperties serviceProperties() {
        ServiceProperties properties = new ServiceProperties();
        properties.setService("https://app.example.org/login/cas");
        properties.setSendRenew(false);
        return properties;
    }
}
~~~

Lớp này **có cú pháp Java hoàn chỉnh** nhưng chỉ là **một bean cấu hình**, không phải một CAS login app hoàn chỉnh: còn thiếu CAS entry point/filter/provider/ticket validator/user details, dependency `spring-security-cas`, Java Servlet app main và CAS Server thật. Không có stdout cố định. Nếu dùng Spring Security version có package/API đổi, phải kiểm tra Javadoc chính xác.

**Lưu ý:** đừng đặt `sendRenew(true)` chỉ để “tăng bảo mật” rồi nghĩ mọi request đã xác thực lại. `renew` có thể khiến user liên tục được yêu cầu credential và phải được CAS Server/validator hỗ trợ đúng; với step-up còn cần MFA/account policy riêng.

## 16. Spring Security SAML2: thành phần hoàn toàn khác

Trong Spring Security hiện đại, tích hợp SAML 2.0 dùng module:

~~~groovy
implementation 'org.springframework.security:spring-security-saml2-service-provider'
~~~

Với Spring Boot 3.x và plugin/dependency management phù hợp, code Java Servlet:

~~~java
package com.example.federation;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SamlWebSsoConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/", "/public/**", "/error").permitAll()
                        .anyRequest().authenticated())
                .saml2Login(Customizer.withDefaults())
                .build();
    }
}
~~~

Ví dụ `application.yml` với metadata IdP đã được thẩm định:

~~~yaml
spring:
  security:
    saml2:
      relyingparty:
        registration:
          corp:
            assertingparty:
              metadata-uri: "classpath:saml/idp-metadata.xml"
~~~

**Điều kiện:** có Spring Boot Servlet app, dependencies Spring Web/Security/SAML2, IdP metadata thực (entityId, SSO endpoint, verification cert) và SP metadata/ACS đã đăng ký tại IdP. Java config trên **không chạy độc lập bằng javac** và không có stdout cố định. Một số bản Boot/Spring Security có properties metadata-uri/namespace khác; đối chiếu release đang dùng.

Các thành phần Spring Security:

| Thành phần SAML | Vai trò |
| --- | --- |
| `RelyingPartyRegistrationRepository` | Giữ thông tin SP, IdP metadata, cert, ACS |
| `Saml2WebSsoAuthenticationRequestFilter` | Tạo và gửi AuthnRequest |
| `Saml2AuthenticationRequestResolver` | Chuẩn bị AuthnRequest và binding/đường gửi |
| `Saml2WebSsoAuthenticationFilter` | Nhận `SAMLResponse` ở ACS |
| `OpenSaml4AuthenticationProvider / OpenSaml5AuthenticationProvider` | Parse, validate và xác thực SAML, tùy version/stack |
| `Saml2Authentication` | Kết quả đăng nhập SAML đã được SP xác thực |
| `Saml2AuthenticatedPrincipal` | Principal/attributes từ SAML theo API Spring |
| `Saml2X509Credential.verification` | Public X.509 cert tin cậy của IdP dùng để verify chữ ký |

Spring Security 6.x có phiên bản dựa OpenSAML 4, các phiên bản mới hỗ trợ/định hướng OpenSAML 5; Spring Security 7.x dùng lớp tương ứng. **Đừng thay tất cả tên thành OpenSaml5 khi dependency không có**, và đừng đưa `CasAuthenticationProvider` vào chain SAML.

### Spring Security endpoint khác nhau

| CAS client | SAML SP |
| --- | --- |
| `/login/cas?ticket=...` (mẫu callback CAS) | `/login/saml2/sso/{registrationId}` (mẫu ACS SAML) |
| CAS entry point redirect `/cas/login?service=...` | `/saml2/authenticate/{registrationId}` tạo SAML AuthnRequest |
| Validator gọi CAS `/serviceValidate` | Spring provider kiểm tra `SAMLResponse` và assertion |
| `ServiceProperties.service` | `RelyingPartyRegistration.entityId / assertionConsumerServiceLocation` |
| CAS user + attributes | SAML NameID + attributes |

**Không cấu hình cả hai filter bắt cùng URL callback** trừ khi bạn chủ động xây một dispatcher/flow routing đúng. Nếu coexist, dùng URL tách biệt và policy chọn mechanism rõ.

## 18. Chữ ký XML và HTTPS: vì sao không thể bỏ một trong hai?

### CAS Protocol

Một ST được browser mang qua query, rồi app dùng **HTTPS backend** đến CAS Server để validation. Trust quan trọng gồm:
- App không gọi validation tới host tùy ý từ browser.
- TLS certificate và hostname CAS Server được kiểm tra đúng.
- ST đúng service, chưa dùng và còn hạn.
- CAS service registry cho phép app nhận ST.
- Response XML được parse an toàn, không bị redirect sai tới host khác.
- Proxy flow được tin cậy theo chính sách riêng.

CAS ST **không cần tự có chữ ký**, bởi vì server giữ trạng thái ST và app hỏi trực tiếp CAS Server đáng tin.

### SAML Web Browser SSO

SAMLResponse đi qua browser front-channel. Browser là **khâu vận chuyển không đáng tin**. SP cần xác minh:
- XML Signature theo ID/reference/canonicalization an toàn, chống signature wrapping.
- Certificate ký của IdP thuộc metadata/trust được phê duyệt.
- Issuer, audience, recipient, destination, temporal conditions, subject confirmation.
- Tương quan request và chống replay, nếu SP initiated.
- Decryption nếu assertion được mã hóa, đúng private key SP.

SAML có thể sử dụng HTTP-Redirect binding với chữ ký query `SigAlg/Signature` cho AuthnRequest hoặc HTTP-POST với XML Signature, tùy flow/config. **Không được so sánh trực tiếp CAS ST với SAML XML Signature**: một bên dùng ticket state+validation, bên kia dùng message signature/conditions.

**TLS ở SAML vẫn phải dùng** cho browser/metadata endpoints. Nó bảo vệ đường truyền nhưng **không thay** chữ ký assertion.

## 19. Authorization sau login: cả hai không tự cấp quyền nghiệp vụ

CAS có thể trả:
- `cas:user`;
- CAS 3.0 `cas:attributes`, ví dụ department, group, affiliation.

SAML có thể trả:
- `NameID`;
- `AttributeStatement`, `AuthnStatement`;
- `AuthnContext` khi IdP phát theo profile.

Dù vậy:
1. SP/app phải ánh xạ identity theo khóa ổn định và đúng tenant/issuer.
2. Đừng dùng email chưa được xác minh làm account ID toàn cục.
3. Đừng tự cấp `ROLE_ADMIN` chỉ vì response có `group=admins` từ một đối tác không được ủy quyền cấp quyền đó.
4. Quyền có thể thay đổi **sau khi phiên Spring Security đã tạo**; `Authentication.getAuthorities()` có thể stale.
5. Với hành động nhạy cảm, kiểm tra account enabled/locked và permission hiện hành theo app authorization policy.
6. SSO authentication thành công không tự chứng minh đủ quyền xem mọi tài nguyên.

**CAS username và SAML NameID không phải một định danh chắc chắn giống nhau** khi migration. IdP có thể dùng opaque persistent NameID, transient NameID hoặc định danh khác; cần kế hoạch account mapping, không đồng nhất chuỗi vì trông giống.

## 20. CAS logout khác SAML Single Logout

### 20.1 CAS logout

CAS Server `/logout` có thể hủy CAS SSO session/TGT và cookie liên quan theo policy. CAS cũng có khả năng **Single Logout notifications** tới những client đã tham gia nếu server/client hỗ trợ và cấu hình tương ứng. Nhưng:
- App local session không tự bị xóa chỉ vì CAS TGT không còn.
- Nếu ứng dụng không xử lý CAS SLO message, phiên local có thể tiếp tục.
- Người dùng logout cục bộ tại app nhưng CAS TGC còn có thể SSO lại ngay.
- Định dạng/cách gửi CAS SLO messages tùy phiên bản và profile, không áp dụng SAML 2.0 `LogoutRequest` mặc định.

### 20.2 SAML Single Logout

SAML 2.0 định nghĩa **Single Logout Profile** với `LogoutRequest` và `LogoutResponse`. SP-initiated/IdP-initiated SLO cần metadata `SingleLogoutService`, signing keys, trust/validation và session correlation. Browser có thể tham gia chuỗi front-channel; đôi khi có các binding khác nếu được hỗ trợ.

**Không gọi CAS logout URL như SAML SingleLogoutService** nếu CAS Server đang expose endpoint CAS protocol. Tương tự, không POST SAML LogoutRequest vào CAS Protocol `/cas/logout` rồi mong nó xử lý theo XML SAML 2.0.

### 20.3 Logout khỏi mọi thiết bị?

Không giao thức nào tự đảm bảo **mọi phiên trên mọi thiết bị, mọi ứng dụng, OAuth/JWT token, WebSocket và các hệ thống không tham gia** đều bị thu hồi. Cần session registry, token revocation, event, IdP policy và hệ thống giám sát riêng.

## 21. Thời hạn phiên và tái sử dụng SSO

Giả sử user đăng nhập ứng dụng A bằng CAS lúc 09:00:
- ST đã consume, nhưng HTTP session ứng dụng A có thể còn.
- TGT/TGC CAS có thể còn, cho phép ST mới khi user tới app B.
- Nếu account bị khóa ở CAS Server lúc 10:00, SP/local session của A **chưa chắc bị invalidated**.

Với SAML 2.0:
- Assertion được kiểm tra tại login và tạo HttpSession của SP.
- IdP session có thể còn để cấp SAMLResponse mới cho app B.
- `NotOnOrAfter` của assertion **không tự đồng nghĩa session SP hết hạn cùng lúc**, trừ khi policy/app xử lý như vậy.
- Khóa account IdP không bảo đảm các SP đang có session bị hủy ngay nếu không có SLO/authorization revocation.

**Do đó:** trước khi migrate, cần định nghĩa cùng một chính sách về account disable, permission changes, session idle/absolute TTL, global logout và active session revocation ở cả hai giao thức. Đổi callback protocol không tự giải quyết stale sessions.

## 22. Java 17 độc lập: mô phỏng tính service-bound và one-time của CAS ST

Chương trình dưới đây minh họa **một quy tắc đặc trưng của CAS Protocol**: ST do server cấp cho một service URL, chỉ hợp lệ trong một khoảng thời gian và bị tiêu thụ sau **một lần thử validation**, kể cả khi service truyền vào sai. Phần mềm **không** tạo CAS ticket thật, không triển khai CAS login/HTTPS, không xác minh XML và không phải một server production.

Tệp `CasTicketLifecycleDemo.java`:

~~~java
import java.time.Instant;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public final class CasTicketLifecycleDemo {

    record Ticket(String service, String subject, Instant expiresAt) {
    }

    static final class TicketStore {
        private final Map<String, Ticket> tickets =
                new ConcurrentHashMap<>();

        void issue(String opaqueTicket, String service,
                   String subject, Instant expiresAt) {
            tickets.put(opaqueTicket, new Ticket(
                    service, subject, expiresAt));
        }

        String validate(String opaqueTicket, String presentedService,
                        Instant now) {
            // Consumes on first validation attempt, including invalid service.
            Ticket ticket = tickets.remove(opaqueTicket);
            if (ticket == null) {
                return "DENY";
            }
            if (!ticket.expiresAt().isAfter(now)) {
                return "DENY";
            }
            if (!ticket.service().equals(presentedService)) {
                return "DENY";
            }
            return "ALLOW:" + ticket.subject();
        }
    }

    public static void main(String[] args) {
        Instant now = Instant.parse("2026-11-07T03:00:00Z");
        String callback = "https://app.example.org/login/cas";
        String wrongCallback = "https://evil.example.org/login/cas";
        TicketStore server = new TicketStore();

        server.issue("ST-demo-01", callback, "user-42",
                now.plusSeconds(60));
        System.out.println("Correct service: " +
                server.validate("ST-demo-01", callback, now));
        System.out.println("Replay: " +
                server.validate("ST-demo-01", callback, now));

        server.issue("ST-demo-02", callback, "user-42",
                now.plusSeconds(60));
        System.out.println("Wrong service: " +
                server.validate("ST-demo-02", wrongCallback, now));
        System.out.println("Retry after wrong service: " +
                server.validate("ST-demo-02", callback, now));

        server.issue("ST-demo-03", callback, "user-42",
                now.minusSeconds(1));
        System.out.println("Expired: " +
                server.validate("ST-demo-03", callback, now));
    }
}
~~~

Chạy với Java 17+:

~~~bash
javac CasTicketLifecycleDemo.java
java CasTicketLifecycleDemo
~~~

Stdout **chính xác**:

~~~text
Correct service: ALLOW:user-42
Replay: DENY
Wrong service: DENY
Retry after wrong service: DENY
Expired: DENY
~~~

Giải thích:
1. ST đầu được cấp cho đúng service, còn hạn nên validation thành công.
2. Lần dùng thứ hai bị từ chối vì ST đã bị consume.
3. ST tiếp theo được trình lên cho **service khác** nên fail.
4. Dù retry bằng đúng service, ST đó đã bị vô hiệu hóa sau lần validation đầu.
5. ST hết hạn bị từ chối.

**Giới hạn bảo mật của demo:** ST tên `ST-demo-01` là chuỗi giả dễ đoán; CAS thật phải phát ticket ngẫu nhiên an toàn, TTL theo policy, storage/concurrency/replication, service allow-list và một validation endpoint HTTPS tin cậy. `ConcurrentHashMap.remove` mô phỏng consume một lần trong JVM; không đủ làm ticket store phân tán production. Không nên copy code này làm security middleware hoặc CAS Server.

### Đối chiếu với SAML

Một chương trình SAML tương đương **không** nên chỉ lấy chuỗi `SAMLResponse` và gọi `validate(ticket, service)`. Nó cần **XML Signature, IdP certificate trust, issuer, audience, subject, recipient, validity, replay, InResponseTo** và parse an toàn. Trong Spring Security, để provider SAML/OpenSAML xử lý những bước đó.

## 23. Tự quan sát CAS và SAML bằng browser/network trace

### CAS Protocol

1. Browser chưa có phiên app, vào `/private`.
2. Network có redirect tới **CAS login** với tham số `service`.
3. Sau CAS login, browser quay về callback với query `ticket=ST-...`.
4. Trong browser **không thấy** backend HTTPS `/serviceValidate` nếu call đó là server-to-server; kiểm tra server logs/tracing CAS client theo quyền.
5. App tạo session nếu validation pass.
6. Sự cố `INVALID_SERVICE` thường liên quan public callback/service mismatch; `INVALID_TICKET` có thể là expired/replayed/wrong ticket.
7. Không ghi raw ticket trong analytics, public logs, screenshot hay HAR gửi rộng rãi.

### SAML 2.0 Web Browser SSO

1. Browser vào `/private`, SP bắt đầu SAML login.
2. Redirect có `SAMLRequest` (Redirect binding) hoặc form POST mang request.
3. IdP sau xác thực trả HTML form với `SAMLResponse` và có thể `RelayState`.
4. Browser HTTP POST đến ACS `/login/saml2/sso/corp`.
5. Spring provider xác minh SAML signature, issuer, audience, subject/time và correlation.
6. App tạo session nếu pass; lỗi provider không đồng nghĩa IdP đã gửi status không-Success.
7. Không sao chép raw SAML Assertion/NameID/cookies vào log chia sẻ.

**Điểm khác cốt lõi trong DevTools:** một `GET callback có ticket` không phải `POST ACS có SAMLResponse`. Tuy nhiên các hệ thống có custom bindings/rewrite proxy nên cần xác định bằng **format message + protocol contract**, không chỉ HTTP method.

## 24. Các lỗi CAS và SAML: không đồng nhất mã

| Dấu hiệu | Protocol/lớp lỗi | Cách điều tra |
| --- | --- | --- |
| `cas:authenticationFailure code="INVALID_TICKET"` | CAS validation | ST hết hạn/đã dùng, ticket sai, renew policy |
| `cas:authenticationFailure code="INVALID_SERVICE"` | CAS validation | `service` mismatch, reverse proxy, service registry |
| CAS server `UNAUTHORIZED_SERVICE` | CAS policy/registry | App/callback chưa được CAS cấp quyền |
| CAS XML response parse fail | CAS client/backend | HTTP/TLS, XML parser, endpoint sai |
| CAS `403` sau đăng nhập | Application authorization | Session/roles/resource permissions |
| SAML `StatusCode=Responder` | IdP reports protocol failure | IdP policy, status subcode nếu có |
| SAML `NoPassive` | IdP không đáp ứng IsPassive | IdP session, requested passive policy |
| Spring SAML invalid signature | SAML SP validation | IdP signing cert, metadata, payload tampering |
| Spring SAML audience mismatch | SAML SP validation | SP entity ID và IdP audience config |
| SAML Response expired | SAML SP validation | NotBefore/NotOnOrAfter/clock skew |
| SAML InResponseTo mismatch | SAML SP correlation | Saved AuthnRequest/session/cookie |
| HTTP 403 ở ACS | HTTP/filter/CSRF hoặc validation | Xem đúng host/filter/server logs, không tự suy IdP status |
| Login success nhưng route 403 | App authorization | Account enabled, role mapping, tenant ACL |
| Logout local xong SSO lại | CAS hoặc SAML | CAS TGC/IdP SSO session còn |

CAS `INVALID_TICKET` **không tương đương** SAML `AuthnFailed`; một bên là lỗi ST validation, bên kia là một loại IdP protocol status. Một SAML Response có `Success` vẫn có thể bị SP từ chối vì local signature/audience check; CAS có thể HTTP 200 nhưng XML chứa authenticationFailure.

## 25. Chiến lược migration từ CAS client sang SAML 2.0 SP

### 25.1 Bắt đầu từ hợp đồng, không từ file cấu hình

Trước khi chuyển:
1. Liệt kê mọi CAS services đang sử dụng `/login?service=...`, callback `/login/cas`, service registry, renew/gateway và CAS SLO.
2. Xác định cách app lấy **username/attributes/authorities** từ CAS validation, nguồn quyền nào đang tin.
3. Kiểm tra ứng dụng có dùng CAS proxy tickets/PGT để gọi downstream không. **Đây là điểm chuyển đổi lớn**.
4. Xác định phiên ứng dụng, timeout, logout, account lock/role changes và audit requirements.
5. Chọn SAML IdP có khả năng SSO/metadata/signing/encryption/NameID/Attributes đáp ứng.
6. Đăng ký SP entity ID, ACS, SLO URL nếu cần và trust certificates.
7. Định nghĩa mapping **CAS username → SAML NameID/stable external ID**; không nối account bằng email chưa được xác minh.
8. Xác định IdP-initiated login có cần hỗ trợ và rủi ro unsolicited response.
9. Xác định cutover, backout, test accounts và log redaction.

### 25.2 Mapping cấu hình chức năng

| Hiện tại với CAS | Sau migration sang SAML |
| --- | --- |
| CAS server login URL | IdP `SingleSignOnService` metadata endpoint |
| `ServiceProperties.service` | SP `entityId` + ACS `assertionConsumerServiceLocation` |
| `CasAuthenticationEntryPoint` | SAML `Saml2WebSsoAuthenticationRequestFilter` / EntryPoint |
| `CasAuthenticationFilter` | `Saml2WebSsoAuthenticationFilter` |
| `CasAuthenticationProvider` + TicketValidator | OpenSAML authentication provider / SAML validation |
| CAS ST trong query | SAMLResponse XML qua ACS |
| CAS user/attributes | SAML NameID/AttributeStatement |
| CAS renew | SAML ForceAuthn (kiểm thử semantics) |
| CAS gateway | SAML IsPassive (không mapping response 1:1) |
| CAS SLO | SAML Single Logout (yêu cầu metadata/profile riêng) |
| CAS proxy tickets | Cần thiết kế delegation/downstream trust mới, không tự map |

### 25.3 Phương án A: ứng dụng chuyển hẳn sang SAML

- Bỏ đường CAS entry point/filter/provider trên vùng request được bảo vệ, dùng `.saml2Login()`.
- Thay service callback bằng SP ACS, đăng ký metadata với IdP.
- Cấu hình trusted IdP signing credentials và SP signing/decryption credentials khi cần.
- Đảm bảo SAML attributes/NameID mapping và local authorization.
- Test cả login, invalid signature, audience, time, logout, reverse proxy, account disable.
- Nếu cần tương tác CAS cũ với downstream, phải xây giải pháp mới, không đem ST/PT qua SAML channel.

### 25.4 Phương án B: chạy CAS và SAML song song

- Dành endpoints riêng: CAS `/login/cas`, SAML `/login/saml2/sso/{registrationId}`.
- Dùng Spring Security filter chains/request matchers đúng, tránh filter collisions.
- Cho biết rõ user đang được xác thực qua protocol/IdP nào; ánh xạ chung vào account ID nội bộ đã xác minh.
- Kiểm thử session, logout và quyền cùng một user từ hai phương thức, tránh account takeover.
- Có cutover/rollback theo tenant hoặc dịch vụ, log metrics phân biệt protocol và lỗi.
- Không bật cơ chế “chấp nhận response từ mọi IdP” để tiện coexist.

### 25.5 Phương án C: dùng broker giữ CAS cho app cũ, phát SAML cho app mới

Broker/server xác minh **giao thức inbound** và phát **giao thức outbound** theo trust riêng:
- Client CAS legacy vẫn lấy ST và validate ở CAS endpoint.
- Client SAML mới nhận Assertion do một SAML IdP/broker phát.
- Broker quản lý mapping identity, assurance, session và logout coverage.
- App SAML tin **signing certificate và issuer của broker**, không tự tin upstream CAS TGT/ST.
- Nếu broker kiểm tra ticket từ CAS upstream, phải bảo vệ backend TLS và service-binding như mọi CAS client.
- Không nhận một string ST từ browser rồi tạo Assertion cho mọi client mà không validation/thỏa thuận audience.

### 25.6 Chiến lược dữ liệu và account identity

CAS `cas:user=alice` và SAML `NameID=alice` trông giống nhau nhưng có thể là **hai identity namespaces** khác nhau. Tốt hơn:
- Khoá tài khoản nội bộ dựa trên immutable ID được quản trị, mapping theo issuer/tenant.
- Có quy trình link account cần xác minh, không “ghép theo email” tự động.
- Những group/role SAML phát ra được phê duyệt, không dùng khác scope để cấp admin.
- Revoke/cập nhật quyền hiện hành vẫn có hiệu lực với phiên cũ dù protocol đã đổi.

## 26. Ma trận kiểm thử CAS và SAML khi chuyển đổi

| Test | CAS kỳ vọng | SAML kỳ vọng |
| --- | --- | --- |
| User chưa có phiên trung tâm | CAS login form hoặc policy tương ứng | IdP login hoặc policy tương ứng |
| User đã có phiên trung tâm | CAS dùng TGC/TGT, cấp ST nếu được phép | IdP SSO session, phát Response nếu được phép |
| Browser callback | `ticket=ST-...` | `SAMLResponse` |
| Backend validation | Gọi CAS serviceValidate | OpenSAML kiểm tra XML Signature/conditions |
| Ticket/Response replay | ST không validate lần hai | SP chống replay response/assertion/request |
| Callback URL thay đổi | `INVALID_SERVICE` hoặc service policy | Destination/Recipient/ACS mismatch |
| Trust sai nguồn | CAS TLS/endpoint mismatch | IdP signature/issuer/metadata mismatch |
| Tài khoản thiếu quyền | App authorization deny | App authorization deny |
| Renew/force reauth | CAS renew policy | SAML ForceAuthn + IdP policy |
| Silent login không có phiên | CAS gateway trả về không có ST | SAML IsPassive có thể trả NoPassive |
| Logout local | Xóa SP/CAS client session, TGC có thể còn | Xóa SP session, IdP session có thể còn |
| Logout federation | CAS SLO khi server/client hỗ trợ | SAML LogoutRequest/LogoutResponse khi hỗ trợ |
| Multi-node | Shared session/ticket server, client state | Shared request repository/session + metadata/cert |
| User bị disable | CAS policy + app live state | SAML IdP policy + app live state |

**Với môi trường thật:** test cả HTTP traces và server logs ở từng bên, có kịch bản tiêu cực được ủy quyền. Không tự gửi ST/SAMLResponse của người dùng sản xuất tới dịch vụ test để debug.

## 27. Quy trình đọc logs và tìm nguyên nhân đúng

### CAS case: browser có ST nhưng app báo login failed

1. Kiểm tra browser thực sự có `GET /login/cas?ticket=...` đến app.
2. Kiểm tra CAS client gọi đúng CAS Server `/serviceValidate` qua backend HTTPS không.
3. So `service` client dùng để xin ST và validate. Public HTTPS/scheme/host/path phải nhất quán.
4. Kiểm tra ticket có bị validate trước đó bởi proxy/retry không; ST là one-time.
5. Đọc CAS validation XML, phân biệt `authenticationSuccess` và `authenticationFailure`.
6. Nếu validation success mà app 403, xem authorities và business account policy, không tiếp tục đổ lỗi CAS.
7. Redact ticket/cookie/username khi chia sẻ HAR/log.

### SAML case: browser POST Response nhưng app login failed

1. Kiểm tra ACS endpoint và `SAMLResponse` POST có đến SP không.
2. Xem provider logs: parse, verification signature, trusted IdP certificate, issuer.
3. Đối chiếu Destination/Recipient/Audience/EntityID, public URL qua proxy.
4. Kiểm tra NotBefore/NotOnOrAfter, NTP/clock skew, InResponseTo và session cookies.
5. Xem assertion có encrypted không và SP decryption key đúng không.
6. Nếu IdP gửi Status không-Success, ghi **IdP-reported status**; nếu status Success nhưng signature fail, ghi **SP verification failure**.
7. Nếu Authentication thành công nhưng route 403, chuyển sang app authorization.

### Phân loại theo nơi thất bại

~~~mermaid
flowchart TD
    A[SSO login failed] --> B{Callback mang ticket hay SAMLResponse?}
    B -- ticket --> C[CAS client]
    C --> D{Backend /serviceValidate thành công?}
    D -- Không --> E[CAS ticket/service/TLS validation]
    D -- Có --> F[Spring principal mapping và app authorization]
    B -- SAMLResponse --> G[SAML SP]
    G --> H{XML/Signature/Conditions được verify?}
    H -- Không --> I[SP SAML trust/metadata/clock/correlation]
    H -- Có --> J[Spring principal mapping và app authorization]
    B -- Không có callback --> K[Browser/proxy/CAS-or-IdP endpoint/network]
~~~

Sơ đồ chỉ phục vụ triage, không có quyền tự quyết định `Authentication` từ một giá trị query/XML chưa xác minh.

## 28. Những ngộ nhận cần tránh

1. **“CAS và SAML đều redirect nên cùng security controls.”** Sai. CAS ST validation và SAML Signature/Conditions là hai cơ chế khác nhau.
2. **“CAS Service Ticket có thể decode để lấy user.”** Sai. ST là opaque, backend CAS xác minh và trả user.
3. **“Một ST có thể dùng đi dùng lại để login.”** Sai với CAS Protocol ST: one-time validation attempt.
4. **“SAML Assertion là ST dài hơn.”** Sai. Assertion là phát biểu XML có issuer, subject, conditions và signature.
5. **“HTTPS đủ để nhận SAMLResponse.”** Sai. Browser vận chuyển XML cần chữ ký/trust/conditions được verify.
6. **“SAML phải gọi /serviceValidate như CAS.”** Sai với HTTP-POST Browser SSO. Artifact binding có back-channel riêng nhưng không phải CAS endpoint.
7. **“CAS renew chính là SAML ForceAuthn.”** Chỉ gần mục đích; semantics và policy khác.
8. **“CAS gateway = SAML NoPassive status.”** CAS có thể trả về không có ticket; SAML có status lỗi protocol.
9. **“Apereo CAS Server hỗ trợ SAML nên CAS Protocol đã là SAML.”** Sai: một sản phẩm, nhiều protocol.
10. **“Spring CAS client đủ để xử lý SAML 2.0.”** Sai: module/protocol handlers khác nhau.
11. **“SAML ký rồi không cần check audience.”** Sai: signed assertion có thể dành cho SP khác.
12. **“CAS validation success hoặc SAML Response Success nghĩa là user có quyền ADMIN.”** Sai: authorization là bước app riêng.
13. **“CAS logout /logout hay SAML SLO tự xóa mọi JWT/thiết bị.”** Không có bảo đảm.
14. **“Chỉ thay URL callback CAS thành ACS là migration hoàn thành.”** Sai: còn trust, identity mapping, logout, proxy, testing.
15. **“HTTP 200 từ CAS/IdP nghĩa là login thành công.”** Sai: phải xem response cụ thể và SP/app validation.
16. **“ST trong browser URL an toàn để ghi log.”** Sai: đây là credential ngắn hạn, có thể bị lợi dụng trước khi consume.
17. **“SAML NameID và CAS user trùng text là cùng account.”** Không chắc; cần namespace/issuer/tenant mapping.
18. **“Đổi quyền ở CAS/IdP là mọi HttpSession tự cập nhật.”** Sai: session có thể giữ snapshot quyền cũ.

## 29. Bài tập tự kiểm tra có đáp án

**Câu 1.** Browser quay về `/login/cas?ticket=ST-123`. Ứng dụng có thể tạo session ngay khi thấy `ST-` không?

**Đáp án:** không. Backend phải validate ST với CAS Server đáng tin và đúng service URL; kiểm tra success/failure rồi mới tạo Authentication.

**Câu 2.** CAS client validate một ST bằng service URL sai và nhận `INVALID_SERVICE`. Sau đó retry ST cũ với service URL đúng có nên thành công không?

**Đáp án:** không. CAS ST theo spec bị invalidated sau một lần validation attempt, kể cả thất bại.

**Câu 3.** CAS TGT và TGC khác nhau thế nào?

**Đáp án:** TGT là ticket/SSO session phía CAS Server; TGC là cookie browser tham chiếu phiên tập trung. Chúng khác ST dùng một lần cho service.

**Câu 4.** IdP trả SAMLResponse chứa `StatusCode=Success` và `NameID=admin`, nhưng XML Signature sai. SP có được tạo Authentication không?

**Đáp án:** không. Status/NameID không thay validation chữ ký, trust và conditions.

**Câu 5.** CAS có thể trả user attributes ở endpoint nào?

**Đáp án:** CAS 3.0 thường dùng `/p3/serviceValidate` để nhận CAS attributes, tùy server/registration policy. Không mặc định `/validate` CAS 1.0 có metadata attributes.

**Câu 6.** `AudienceRestriction` trong SAML gần ý tưởng “service-bound” của CAS không?

**Đáp án:** có liên hệ mục tiêu giới hạn bên nhận, nhưng **không mapping 1:1**. SAML còn Issuer, Recipient, Destination, ACS, subject confirmation, request correlation và signature.

**Câu 7.** CAS renew=true và SAML ForceAuthn=true đều đảm bảo MFA không?

**Đáp án:** không. Chúng yêu cầu hình thức xác thực mới theo semantics từng protocol, còn MFA/assurance phải có chính sách và bằng chứng riêng.

**Câu 8.** Browser GET đến app với CAS ST, còn SAML Browser SSO thường POST tới ACS. Có thể kết luận protocol chỉ bằng HTTP method không?

**Đáp án:** method là dấu hiệu hữu ích, nhưng cần kiểm tra **payload/form/contract**; có custom bindings/config. CAS có thể hỗ trợ cách vận chuyển khác theo version, SAML có nhiều bindings.

**Câu 9.** Một ứng dụng đã dùng `spring-security-cas` muốn nhận SAML 2.0 từ IdP. Có thể chỉ đổi `Cas20ServiceTicketValidator` thành một class XML parser không?

**Đáp án:** không. Cần SAML SP module/provider, RelyingPartyRegistration, metadata, signature/conditions validation và ACS tương ứng.

**Câu 10.** CAS backend validation bị TLS hostname mismatch. Có nên `trustAllCertificates()` để login chạy?

**Đáp án:** không. Cần sửa public CAS endpoint, truststore/TLS cert và network config, không bỏ server certificate validation.

**Câu 11.** IdP phát Assertion đúng chữ ký nhưng `AudienceRestriction` dành cho SP B, app A vẫn muốn nhận. Có được không?

**Đáp án:** không. Assertion dành cho bên khác; SP phải từ chối dù chữ ký đúng.

**Câu 12.** Cas Server là broker hỗ trợ SAML 2.0 và CAS Protocol. App legacy muốn dùng CAS, app mới muốn dùng SAML. Có cần tất cả app gọi cùng protocol endpoint không?

**Đáp án:** không. Một platform có nhiều protocol modules; mỗi app đăng ký đúng CAS service hoặc SAML SP, trust và callback riêng.

**Câu 13.** Sau local logout, user lập tức SSO trở lại cả CAS app và SAML app. Lý do có thể là gì?

**Đáp án:** CAS TGC/TGT hoặc IdP session còn tồn tại; local HttpSession chỉ bị xóa tại app. Cần federation logout/session revocation riêng nếu chính sách yêu cầu.

**Câu 14.** CAS `gateway=true` không có session, broker chuyển browser về không có ST. Có nên tự tạo anonymous authenticated principal không?

**Đáp án:** không. Không có validation success; app giữ anonymous/unauthenticated và chọn UX login khác theo policy.

**Câu 15.** CAS app dùng Proxy Ticket gọi service B. Sau migration sang SAML, có thể đặt PT vào `SAMLRequest` như artifact không?

**Đáp án:** không. CAS PT và SAML Artifact khác protocol, cấu trúc, trust và lifecycle. Cần redesign delegation/broker/backend authentication.

**Câu 16.** Khi user đổi quyền từ ADMIN thành READ, có thể chỉ thay CAS login bằng SAML và xem vấn đề quyền stale đã được giải quyết không?

**Đáp án:** không. Cả hai có thể tạo Spring Security session lưu authorities khi login; app cần live authorization, refresh/revoke hoặc session invalidation theo requirement.

## 30. Checklist trước khi triển khai hoặc chuyển đổi

- [ ] Đã xác định **đúng protocol** mà ứng dụng đang dùng: CAS ticket hay SAML 2.0 Web Browser SSO.
- [ ] CAS client có CAS Server URL cố định, HTTPS/TLS trust đúng, service URL chuẩn và allow-list.
- [ ] CAS Service Ticket được validate backend, đúng service, có TTL và one-time semantics.
- [ ] CAS 2/3 endpoint (`/serviceValidate`, `/p3/serviceValidate`) được dùng đúng nhu cầu attributes.
- [ ] Nếu CAS dùng proxy tickets, có PGT callback/proxy chain policy và bài test riêng.
- [ ] SAML SP có IdP metadata/entity ID, trusted signing certificates, SSO endpoint và ACS đúng.
- [ ] SAMLResponse/Assertion được Spring/OpenSAML kiểm tra signature, issuer, audience, recipient, time, subject và correlation/replay.
- [ ] Không nhầm SAML Artifact với CAS ST, CAS `renew/gateway` với SAML `ForceAuthn/IsPassive`.
- [ ] Spring Security dùng đúng module và filter: CAS hay SAML SP, không nhận chung callback.
- [ ] Public URL/forwarded headers/reverse proxy phù hợp với CAS service hoặc SAML Destination/ACS.
- [ ] Account identity mapping theo issuer/tenant/immutable ID, không chỉ username/email.
- [ ] Authorization kiểm tra quyền hiện hành khi cần; SSO không tự đồng bộ role change.
- [ ] Session idle/absolute TTL, CAS TGT/TGC hoặc IdP SSO session và local logout được phân biệt.
- [ ] Federation logout được kiểm thử, không hứa mọi thiết bị/token bị logout nếu chưa có cơ chế.
- [ ] Test callback replay, wrong service, invalid signature, wrong audience, expired assertion, lost session.
- [ ] Log và telemetry không chứa CAS ST, TGC, SAMLResponse, NameID thật, private key hoặc session cookies.
- [ ] Multi-node Spring Session/RequestRepository tương thích callback và anti-replay.
- [ ] Có kế hoạch migration, parallel-run, rollback và phân loại lỗi theo protocol.

## 31. Kết luận cốt lõi

**CAS Protocol**: browser nhận **Service Ticket** dùng một lần cho service; backend ứng dụng **gọi CAS Server để validate ticket**. **SAML 2.0 Web Browser SSO**: browser mang **SAMLResponse/Assertion**; SP **xác minh chữ ký và các điều kiện SAML** theo metadata và trust đối tác. Hai bên đều có thể tạo Spring Security Authentication/session và cho trải nghiệm SSO giống nhau, nhưng **bằng chứng, trust boundary, API, error handling, metadata, lifecycle và phương án migration khác nhau**.

Đừng triển khai bằng cách “đổi tên ticket thành SAMLResponse”; hãy xác định giao thức đúng và để đúng security provider/validator xử lý. Với federation qua broker, mỗi hop cần kiểm tra **đầu vào của protocol đó** rồi phát credential **mới** theo hợp đồng giao thức đầu ra.
