# Creating Your First `SecurityWebFilterChain` with `ServerHttpSecurity`

## Lesson objectives

After this lesson, you can create a **Spring WebFlux** security configuration in Java, understand the `ServerHttpSecurity → SecurityWebFilterChain → WebFilter` flow, allow a public endpoint, require authentication for a personal endpoint, restrict an admin endpoint by role, run the application, and verify the results via HTTP and automated tests.

**Scope:** configuring **a single** first `SecurityWebFilterChain` for WebFlux, using HTTP Basic and in-memory accounts for learning. This is not yet a lesson on implementing OAuth2, JWT, database login, or multiple security chains; those topics are only noted where boundaries need to be recognized. The Java examples below target Spring Boot 3.x, Spring Security 6.x, Java 17 or higher, and Gradle. For newer versions, check the corresponding documentation if APIs have changed.

## 1. Three concepts to grasp before writing code

- **`ServerHttpSecurity`:** the HTTP security configuration builder/DSL for **Spring WebFlux**. You declare which paths can be accessed, how authentication works, HTTP security headers, CSRF, login, etc. It is the object that helps *construct* the chain, not the filter that handles each request itself.
- **`SecurityWebFilterChain`:** the result of `http.build()`. It describes a set of security `WebFilter`s and the matcher applied to requests. Spring Security places this chain into `WebFilterChainProxy` so actual WebFlux requests are protected.
- **`@EnableWebFluxSecurity`:** enables Spring Security integration with WebFlux via Java configuration. When Spring Boot auto-configuration already enables WebFlux Security, this annotation sometimes does not need to be declared manually; in this first lesson we use it explicitly to recognize its role.

Simplified flow:

```text
HTTP client
    |
    v
Spring WebFlux (ServerWebExchange)
    |
    v
Spring Security WebFilterChainProxy
    |
    +--> Selected SecurityWebFilterChain
    |       |
    |       +--> WebFilter authenticating caller
    |       +--> WebFilter checking permissions
    |       +--> other mechanisms (headers, CSRF, ...)
    |
    v
@RestController / RouterFunction
    |
    v
Mono / Flux -> HTTP response
```

Important distinction: in **Servlet/MVC** applications, `HttpSecurity` and `SecurityFilterChain` are commonly used. In **WebFlux**, use `ServerHttpSecurity` and `SecurityWebFilterChain`. Do not mix the two API pairs because they integrate into two different pipelines.

## 2. Preparing a proper WebFlux project

Create a project via [Spring Initializr](https://start.spring.io/) with Java 17+ (or Java 21), Gradle, Spring Boot 3.x, and the dependencies:

- **Spring Reactive Web** (`spring-boot-starter-webflux`): provides the server, router/controller, and Reactor.
- **Spring Security** (`spring-boot-starter-security`): provides Spring Security and web security components.
- **Spring Boot Starter Test** (`spring-boot-starter-test`): for writing JUnit and `WebTestClient` tests.
- **Spring Security Test** (`spring-security-test`): security support when writing tests.

In the `build.gradle` generated by Initializr, the corresponding dependencies section can be written as:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-webflux'
    implementation 'org.springframework.boot:spring-boot-starter-security'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.security:spring-security-test'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}
```

This is a **Gradle configuration snippet**, not a complete standalone `build.gradle`. Keep the Spring Boot plugin, dependency management, repositories, and Java toolchain generated by Initializr. Do not add `spring-boot-starter-web` to the demo: when both MVC and WebFlux starters are present, Spring Boot 3.x usually picks **Servlet/MVC** as the default server type, even if the project has Reactor or `WebClient`. The demo's goal is for inbound requests to run on WebFlux.

Use the shared package `demo.security.webflux` and organize:


## 3. Defining the security policy before configuring

In this example, we have three APIs supporting HTTP GET only:

| HTTP endpoint | Who is allowed? | Expectation |
|---|---|---|
| `GET /public` | Everyone, including unauthenticated guests | Return `public` |
| `GET /profile` | Authenticated users | Return `hello <username>` |
| `GET /admin` | Users with role `ADMIN` | Return `admin` |
| Any other request | Disallowed by the demo policy | Reject immediately at the security layer |

Two learning accounts are declared in memory:

| Username | Password *for demo only* | Role |
|---|---|---|
| `reader` | `reader-pass` | `USER` |
| `admin` | `admin-pass` | `ADMIN` |

Spring Security normally converts `.roles("ADMIN")` into granted authority `ROLE_ADMIN`. Thus `hasRole("ADMIN")` requires that authority; **do not** write `hasRole("ROLE_ADMIN")` when using the default convention. Authentication answers "who is calling?", authorization answers "what is that caller allowed to do?"; the two steps must not be conflated.

Place specific rules **before** the default rule for all requests. We use `anyExchange().denyAll()` so we do not accidentally expose endpoints when adding new controllers. In a real application, you will also need to consider CORS preflight, health checks, static assets, and required HTTP methods; do not grant them unintended access.

## 4. Writing the complete Java application

### 4.1. Entry point

Create `src/main/java/demo/security/webflux/DemoApplication.java`:

```java
package demo.security.webflux;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

The `@SpringBootApplication` annotation enables component scanning in the package and its subpackages. Because all three classes share the same package, Spring finds `SecurityConfig` and `DemoController` at startup.

### 4.2. Creating `SecurityWebFilterChain` from `ServerHttpSecurity`

Create `src/main/java/demo/security/webflux/SecurityConfig.java`:

```java
package demo.security.webflux;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.core.userdetails.MapReactiveUserDetailsService;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration
@EnableWebFluxSecurity
public class SecurityConfig {

    @Bean
    public SecurityWebFilterChain securityWebFilterChain(ServerHttpSecurity http) {
        return http
            .authorizeExchange(exchanges -> exchanges
                .pathMatchers(HttpMethod.GET, "/public").permitAll()
                .pathMatchers(HttpMethod.GET, "/profile").authenticated()
                .pathMatchers(HttpMethod.GET, "/admin").hasRole("ADMIN")
                .anyExchange().denyAll()
            )
            .httpBasic(Customizer.withDefaults())
            .formLogin(form -> form.disable())
            .build();
    }

    @Bean
    public MapReactiveUserDetailsService userDetailsService() {
        PasswordEncoder encoder =
            PasswordEncoderFactories.createDelegatingPasswordEncoder();

        UserDetails reader = User.withUsername("reader")
            .password(encoder.encode("reader-pass"))
            .roles("USER")
            .build();

        UserDetails admin = User.withUsername("admin")
            .password(encoder.encode("admin-pass"))
            .roles("ADMIN")
            .build();

        return new MapReactiveUserDetailsService(reader, admin);
    }
}
```

This is a **standalone Java class within the Spring Boot project with dependencies from Section 2**. Meaning of the key lines:

1. **`@Configuration`**: marks the class as declaring beans.
2. **`@EnableWebFluxSecurity`**: enables WebFlux security infrastructure.
3. **`@Bean SecurityWebFilterChain securityWebFilterChain(ServerHttpSecurity http)`**: Spring provides the `ServerHttpSecurity` builder; the method configures the policy and returns the bean containing the chain.
4. **`authorizeExchange(...)`**: enters the HTTP authorization DSL on `ServerWebExchange`. This is the WebFlux DSL, distinct from Servlet's `authorizeHttpRequests(...)`.
5. **`pathMatchers(HttpMethod.GET, "/public").permitAll()`**: allows the exact GET method and `/public` path through permission checks. It still passes through the security chain, including related filters.
6. **`pathMatchers(... "/profile").authenticated()`**: requires an authenticated `Authentication`.
7. **`pathMatchers(... "/admin").hasRole("ADMIN")`**: requires `ROLE_ADMIN`.
8. **`anyExchange().denyAll()`**: requests matching no earlier rule are denied. This is the finite fallback of the policy.
9. **`httpBasic(Customizer.withDefaults())`**: enables HTTP Basic authentication so clients send the `Authorization: Basic ...` header. Real accounts/passwords must be transmitted over HTTPS; Base64 in HTTP Basic **does not encrypt secrets**.
10. **`formLogin(form -> form.disable())`**: disables HTML form login because the demo uses Basic with a JSON/text API; default form login is not needed here.
11. **`build()`**: finishes the DSL and builds `SecurityWebFilterChain`. No need to manually instantiate `WebFilterChainProxy` or a `Servlet Filter`.
12. **`MapReactiveUserDetailsService`**: reactive account lookup store for the exercise. `PasswordEncoderFactories.createDelegatingPasswordEncoder()` stores a hash string prefixed with the encoder identifier (e.g., `{bcrypt}`); it does not store the plaintext password directly in `UserDetails`.

Note: demo passwords still appear in source so the hands-on lab can run, even though values are hashed when building `UserDetails`. Do not bring these accounts/passwords into real environments. Production requires proper identity sources and credential management.

### 4.3. Creating three endpoints to observe the policy

Create `src/main/java/demo/security/webflux/DemoController.java`:

```java
package demo.security.webflux;

import org.springframework.security.core.context.ReactiveSecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Mono;

@RestController
public class DemoController {

    @GetMapping("/public")
    public Mono<String> publicEndpoint() {
        return Mono.just("public");
    }

    @GetMapping("/profile")
    public Mono<String> profile() {
        return ReactiveSecurityContextHolder.getContext()
            .map(context -> context.getAuthentication().getName())
            .map(name -> "hello " + name);
    }

    @GetMapping("/admin")
    public Mono<String> adminEndpoint() {
        return Mono.just("admin");
    }
}
```

These are **three reactive handlers**, returning `Mono` so WebFlux manages subscription and completes the response. In `/profile`, `ReactiveSecurityContextHolder` accesses `SecurityContext` from the subscription's **Reactor Context**. Do not use `SecurityContextHolder.getContext()`, which by default relies on `ThreadLocal`, to guess the principal inside a reactive pipeline. If you call a context-reading method where no security context exists, the `Mono` can complete empty; this example requires authentication at the security chain before entering the handler.

The three classes `DemoApplication`, `SecurityConfig`, and `DemoController`, combined with the Initializr project and dependencies above, form the complete sample application.

## 5. Running and self-verifying via HTTP

From the root directory of the project created by Initializr:

```bash
./gradlew bootRun
```

In Windows PowerShell/cmd use:

```powershell
.\gradlew.bat bootRun
```

Once the application is listening on the default port `8080`, open another terminal and send the requests below (on Windows use `curl.exe` to avoid PowerShell aliases):

```bash
curl -i http://localhost:8080/public
curl -i http://localhost:8080/profile
curl -i -u reader:reader-pass http://localhost:8080/profile
curl -i -u reader:reader-pass http://localhost:8080/admin
curl -i -u admin:admin-pass http://localhost:8080/admin
```

**Expected** HTTP results in order:

| Request | HTTP status | Body on success |
|---|---:|---|
| `GET /public` without credentials | `200` | `public` |
| `GET /profile` without credentials | `401` | No specific body required |
| `GET /profile` with `reader` | `200` | `hello reader` |
| `GET /admin` with `reader` | `403` | No specific body required |
| `GET /admin` with `admin` | `200` | `admin` |

Do not predict every line of `curl -i` verbatim: `WWW-Authenticate` headers, error bodies, and response timestamps/metadata depend on version and configuration. `401 Unauthorized` means the client needs valid authentication; `403 Forbidden` for `reader` on `/admin` means **authenticated** but lacking `ROLE_ADMIN`.

A `GET /does-not-exist` request without an allow rule will not be forwarded to a controller to return 404 like a public route. It is blocked by `anyExchange().denyAll()`; the exact status may differ depending on whether authentication is present and error handling configuration. When building APIs, you must deliberately decide whether unauthenticated callers should see 404 or be blocked at the security gate.

**Reading error responses properly:** do not conclude `SecurityWebFilterChain` is not running just because a request returns 401; that is usually a sign that Basic authentication is working. Conversely, a 200 response from `/public` **does not prove** private routes are protected; you must test unauthenticated, under-privileged, and properly privileged cases.

## 6. How to read `ServerHttpSecurity` as a policy

The core structure can be viewed concisely as:

```java
@Bean
SecurityWebFilterChain chain(ServerHttpSecurity http) {
    return http
        .authorizeExchange(spec -> spec
            .pathMatchers("/open/**").permitAll()
            .pathMatchers("/staff/**").hasRole("STAFF")
            .anyExchange().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
}
```

*The snippet above only illustrates the DSL inside a `@Configuration` class, not a standalone runnable file; do not use it simultaneously with the demo `SecurityWebFilterChain` bean in Section 4 without designing multiple chains.* Points to distinguish:

### 6.1. Matchers and rule order

- `pathMatchers("/open/**")` checks path and authorization when requests enter the chain. The `/open/**` pattern differs from `/open` depending on the matcher; do not assume a pattern covers all path variants without testing.
- `pathMatchers(HttpMethod.GET, "/public")` in the demo restricts the HTTP method as well; POST to the same path **is not automatically permitted**.
- Rules are evaluated in **declaration order**. Place specific rules before `anyExchange()`. An overly broad `permitAll()` at the top can prevent stricter rules below from ever being reached.
- `authenticated()` requires an authenticated identity; `permitAll()` makes it public; `denyAll()` blocks it; `hasRole("STAFF")` requires granted authority `ROLE_STAFF`; `hasAuthority("SCOPE_read")` checks that exact authority.

### 6.2. Whole-chain scope vs permissions within a chain

In this single-chain lesson, `http.securityMatcher(...)` is not called, so the chain applies to the default request scope. If an application has multiple `SecurityWebFilterChain`s, `securityMatcher(ServerWebExchangeMatcher)` selects **which requests belong to the chain**, while `authorizeExchange(...).pathMatchers(...)` applies **authorization rules inside the selected chain**. Bean order/`@Order` must be set deliberately along with a strategy for requests outside the matchers; do not think two chains merge their filters together.

Conceptual example (not code to add to the demo):

```text
Chain A: matches only /api/** -> bearer token authentication
Chain B: matches remaining requests -> configuration for web UI
        |
        v
Each request selects the matching chain; chain A's policy
does not automatically merge with chain B's policy.
```

### 6.3. Should you instantiate `ServerHttpSecurity` with `new`?

No. The `@Bean` method receives the builder as a parameter so the framework provides and manages configuration. You use the DSL and return the built bean. Do not return `ServerHttpSecurity` itself instead of `SecurityWebFilterChain`; do not construct `SecurityWebFilterChain` by directly stuffing a Servlet `Filter` into it.

### 6.4. Why declare a bean when Spring Security already has defaults?

A minimal WebFlux configuration can protect endpoints and enable default authentication mechanisms when no custom chain exists. However, to have a custom policy for `/public`, `/profile`, and `/admin`, you declare a `SecurityWebFilterChain` bean. Once you provide this bean, you must state the required rules explicitly; do not rely on an assumption that the previous auto-configured chain's rules will always be merged into your bean.

## 7. Distinguishing authentication, authorization, and Reactor Context

When sending `curl -u reader:reader-pass ...`, the client builds an HTTP Basic Authorization header from username/password. The security filter parses the header, uses the authentication mechanism and `ReactiveUserDetailsService` to look up reader's `UserDetails`, checks the password, and stores `Authentication` in the security context appropriate for the reactive request.

For `/profile`, authorization lets it through because the caller is authenticated. The controller gains access to the Reactor Context to retrieve the name. For `/admin`, that user is authenticated but only has `ROLE_USER`; `hasRole("ADMIN")` is not satisfied, so `403` is returned.

```text
GET /admin + Basic reader
  -> authentication: reader, authorities = [ROLE_USER]
  -> authorization: requires ROLE_ADMIN
  -> DENIED -> 403

GET /admin + Basic admin
  -> authentication: admin, authorities = [ROLE_ADMIN]
  -> authorization: has ROLE_ADMIN
  -> ALLOWED -> controller -> "admin"
```

**Reactor Context** differs from a global variable or `ThreadLocal`. A reactive publisher can hop between threads, yet context must stay tied to the **subscription**. Therefore, inside a WebFlux application, to access the principal you should normally use `ReactiveSecurityContextHolder`, Spring-supported injection, or the authentication/`Principal` object provided by the framework. Do not call `subscribe()` manually to detach HTTP processing work because it easily breaks context propagation and error handling. Avoid `.block()` on the event loop.

## 8. Automated security chain testing with `WebTestClient`

Manual testing helps observation, but automated tests protect the policy when endpoints are added later. Use the class below in `src/test/java/demo/security/webflux/SecurityFlowTests.java`:

```java
package demo.security.webflux;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.reactive.AutoConfigureWebTestClient;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.reactive.server.WebTestClient;

import static org.springframework.boot.test.context.SpringBootTest.WebEnvironment.RANDOM_PORT;

@SpringBootTest(webEnvironment = RANDOM_PORT)
@AutoConfigureWebTestClient
class SecurityFlowTests {

    @Autowired
    WebTestClient client;

    @Test
    void publicEndpointWorksWithoutLogin() {
        client.get().uri("/public")
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("public");
    }

    @Test
    void profileWithoutLoginReturns401() {
        client.get().uri("/profile")
            .exchange()
            .expectStatus().isUnauthorized();
    }

    @Test
    void readerCanReadOwnProfile() {
        client.get().uri("/profile")
            .headers(headers -> headers.setBasicAuth("reader", "reader-pass"))
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("hello reader");
    }

    @Test
    void readerCannotEnterAdminArea() {
        client.get().uri("/admin")
            .headers(headers -> headers.setBasicAuth("reader", "reader-pass"))
            .exchange()
            .expectStatus().isForbidden();
    }

    @Test
    void adminCanEnterAdminArea() {
        client.get().uri("/admin")
            .headers(headers -> headers.setBasicAuth("admin", "admin-pass"))
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("admin");
    }
}
```

Run:

```bash
./gradlew test
```

Or on Windows:

```powershell
.\gradlew.bat test
```

In a Spring Boot 3.x environment with the test dependencies from Section 2, these tests boot the application on a random port, use `WebTestClient` to send real HTTP to the test web server, and verify both the chain and controller. **Expectation:** 5 tests pass. Do not expect fixed Gradle stdout lines because Gradle/JUnit print task names, timings, and statuses differently across versions. When a test fails, check logs, security beans, roles, and web application type; do not edit expected HTTP statuses just to make tests green.

When you only need to verify security at the mock WebFlux test client level (without opening a server), you can use `WebTestClient.bindToApplicationContext(context).apply(springSecurity())` with `spring-security-test`; matchers and mock principals are managed via the test DSL. This lesson chooses testing over a random port to make real HTTP verification straightforward and avoid mistaking controller unit tests for complete endpoint protection.

## 9. CSRF, sessions, CORS, and defaults to respect

### 9.1. CSRF does not disappear just because you use WebFlux

Spring Security WebFlux **enables CSRF by default**. State-changing requests like POST/PUT/PATCH/DELETE typically require a CSRF token under the active policy. The demo only implements GET, so it does not encounter form submissions. If you add browser form login, sessions/cookies, or POST APIs, you must design tokens and tests properly. Do not mechanically add `csrf(csrf -> csrf.disable())` when requests automatically send cookies/sessions. A bearer-token API not using cookies may have a different threat model, but disabling CSRF must be based on verifying the actual authentication mechanism.

### 9.2. HTTP Basic does not replace HTTPS or session management

HTTP Basic sends credentials on every request in a header; only accept it over HTTPS in real environments. Enabling HTTP Basic **does not automatically make a system stateless**. WebFlux still has `WebSession` and `ServerSecurityContextRepository` for scenarios needing security context persistence. If designing a stateless REST API, configure the token/context/session strategy explicitly and verify it rather than inferring from the word "reactive".

### 9.3. CORS preflight differs from GET permissions

Browsers send `OPTIONS` preflight requests in certain CORS situations. Because the demo uses `anyExchange().denyAll()`, preflights not yet permitted or handled separately may be blocked. In real applications, CORS must be configured for trusted client origins and processed before authentication checks when needed. Avoid `permitAll()` on all methods/URLs just to "make CORS work", as that over-grants permissions.

### 9.4. Error statuses and login flows

With HTTP Basic and form login disabled, unauthenticated requests to routes requiring authentication usually receive `401` with an HTTP Basic challenge; logged-in users lacking roles receive `403`. Switching to `formLogin`, OAuth2 login, or a custom authentication entry point can change the experience to redirects or JSON errors. In tests, tie expected statuses to the actual configuration.

## 10. From the first chain to a real application

When adding features, expand with deliberate individual decisions:

- **Adding endpoints:** define appropriate rules before `anyExchange()`; specify HTTP method, roles/authorities, and 401/403/200 test cases. Do not change `anyExchange()` to `permitAll()` to "get it running temporarily".
- **Using roles and permissions differently:** `hasRole("ADMIN")` checks `ROLE_ADMIN`, whereas `hasAuthority("SCOPE_orders.read")` checks that exact authority string; map clearly from identity/JWT to granted authorities.
- **Using a database:** replace `MapReactiveUserDetailsService` with a real account source, managing hashes and credentials. `ReactiveUserDetailsService` must not block the event loop; do not wrap blocking JDBC in `Mono.just(...)` and treat it as non-blocking.
- **Switching to JWT Resource Server:** replace HTTP Basic and the demo user store with appropriate resource server security configuration, declaring issuer/JWK/audience/claims and authority rules. Do not leave two global chains both matching all requests without `securityMatcher`/`@Order`.
- **Method protection:** WebFlux has `@EnableReactiveMethodSecurity` for methods returning reactive publishers and using Reactor Context; it complements rather than completely replaces HTTP authorization.
- **Adding health/static paths:** identify which requests truly need to be public and which resources are internal-only; also consider firewalls/proxies/API gateways to avoid relying on path names that may differ in practice.

Focus on protecting **inbound requests to the running application**. A Spring MVC application can use `WebClient` to call other systems while inbound security remains Servlet. Once the right starter/server stack is chosen, configuration code and tests must stay consistent with that stack.

## 11. Common issues, causes, and how to check

| Symptom | Cause to consider | How to verify or fix |
|---|---|---|
| Imported `HttpSecurity`/`SecurityFilterChain` and reactive APIs refuse to configure | Confusing Servlet stack with WebFlux | Use `ServerHttpSecurity`, `SecurityWebFilterChain`, `@EnableWebFluxSecurity` |
| `/public` returns `401` | Forgot `permitAll` or matcher has wrong method/path | Check exact path and `authorizeExchange` order |
| `/admin` returns `403` for `reader` | Role `USER`, lacks `ROLE_ADMIN` | Check authorities; this is the expected demo result |
| `/admin` still returns `403` for an identity expected to have ADMIN | Actual authority is not `ROLE_ADMIN`, wrong mapper, or wrong Basic credentials | Print/log authorities in a safe test area; check `roles` and `hasRole` |
| Every request redirects to a login page | Form login or another entry point is enabled | Verify the right demo chain and `formLogin(form -> form.disable())` |
| POST fails even though GET works | Fallback `denyAll`, CSRF, or method policy | Identify exact cause of 403 and rules; do not unconditionally disable CSRF |
| Test gets 200 while production gets 401 | Test did not apply Spring Security to WebTestClient/mocks or did not test real server | Run integration tests with security chain and 401/403 cases |
| Startup warns about two security chains/matchers | Added multiple beans or framework config differs from assumption | Audit `SecurityWebFilterChain` beans and chain selection priority |
| Sees `Mono` yet requests still hang | Service code makes blocking calls or `.block()` | Check threads used, choose non-blocking adapters, or isolate blocking work |
| Login credentials exposed over HTTP | Using Basic on unencrypted connection | Use TLS/HTTPS and production credential solutions |

**Common mindset mistake:** "Now that `@Bean SecurityWebFilterChain` exists, all endpoints have the right permissions." A bean only contains the rules you defined; misplaced matchers/roles/chains can still expose or block APIs by mistake. Therefore, test all three states: unauthenticated caller, under-privileged user, and authorized user.

## 12. Hands-on exercises

**Exercise 1.** Add a `GET /reports` endpoint restricted to `USER` and `ADMIN`. Before coding, decide which role helper to use and add tests for both accounts. To permit two roles, you can use `hasAnyRole("USER", "ADMIN")`; place the rule before `anyExchange().denyAll()`.

**Exercise 2.** Change the `/profile` rule to `hasRole("USER")` and call it using the demo's `admin` (who only has `ROLE_ADMIN`). Why does `403` occur? Because `authenticated()` verifies identity, whereas `hasRole("USER")` checks that exact permission; the ADMIN role does not automatically include USER. To inherit permissions, you must design a role hierarchy or grant appropriate authorities.

**Exercise 3.** Send a POST to `/public` (which only has GET). Making `GET /public` public **does not permit POST**. Identify whether the request is blocked by matcher/fallback and/or CSRF depending on configuration; do not expect a route to handle POST if no handler is declared.

**Exercise 4.** Why is `SecurityContextHolder.getContext()` not the default choice for retrieving the principal inside a `Mono` in WebFlux?

**Answer:** Reactive Security holds context in the Reactor subscription, which may resume on a different thread. `SecurityContextHolder` relies on `ThreadLocal` by default, so it is not a reliable way to access a reactive request's context; use `ReactiveSecurityContextHolder` or appropriate injection APIs.

**Exercise 5.** What changes if you call `.anyExchange().permitAll()` at the end?

**Answer:** Endpoints outside the three specific rules will be accessible; this is a major policy change and can accidentally expose APIs added in the future. The demo uses `denyAll()` to require explicit declarations.
