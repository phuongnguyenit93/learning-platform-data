# Storing API Keys Securely, Scoping Permissions, and Key Rotation — Spring Security Reactive

> **Module:** Spring Security - reactive  
> **Topic:** Advanced Authentication  
> **Objective:** Generate API keys with sufficient entropy, avoid storing plaintext in the verification system, restrict scope/tenant/expiry, build `AuthenticationWebFilter` + `ReactiveAuthenticationManager` for WebFlux, issue/rotate/revoke safely, test failure paths, and operate without leaking secrets.

## 1. Scenario and Trust Boundaries

A partner backend needs to call `GET /partner/reports` on a Spring WebFlux application. It has no browser login, should not borrow a user's password, and can send an API key in an HTTPS header:

~~~http
GET /partner/reports HTTP/1.1
Host: api.example.com
X-API-Key: ak_<key-id>.<secret>
Accept: application/json
~~~

From the server's perspective, an API key is a **bearer credential**: anyone holding the valid secret string can call the API within the granted scope. It does not prove the client is running on a specific machine, provides no MFA/consent, and does not bind itself to a particular user or request.

A sound design must ensure:
- Credentials have at least 256-bit entropy generated by a CSPRNG, never customer-chosen passwords.
- Each key has a **public ID** for metadata lookup and a **secret** distributed exactly once.
- The database table stores only an HMAC fingerprint/hash of the key, never recoverable plaintext.
- Every request verifies the key ID, fingerprint, validity window, revocation status, and scopes.
- Permissions are enforced at both the HTTP layer and the domain/tenant/owner layer, not merely by possessing a key.
- A zero-downtime rotation workflow and immediate revocation upon suspected exposure exist.
- Redaction is applied at proxies, application logs, APM, backups, error reports, and test logs.
- If the DB or KMS is unavailable, **fail closed**—never restore Authentication from untrusted stale data.

## 2. Threat Model and Controls

| Threat | Impact | Defense |
| --- | --- | --- |
| Database leaks plaintext keys | Attacker uses all keys | Never store plaintext; one-way HMAC fingerprint |
| Logs contain `X-API-Key` | Log readers impersonate clients | Header redaction + secret scanning |
| Key embedded in SPA/mobile | Users can extract it | BFF or OAuth2; never issue static keys to public clients |
| Weak/predictable key | Brute force | `SecureRandom` and ≥32 random bytes |
| Non-expiring key | Leaked credentials persist indefinitely | Expiry, rotation policy, and revocation |
| Single key has all permissions | Excessive access beyond need | Least-privilege scopes/tenant/owner |
| Key status cached too long | Revoked keys remain usable | Invalidation or TTL ≤ revocation SLA |
| Database/KMS outage | Verification bypassed temporarily | Fail closed, timeouts, metrics |
| Public key ID guessed | Probing many IDs | Key ID is not secret; HMAC, rate limits, generic errors |
| Pepper leaked | Weakens DB defense layer | KMS, key versioning, and reissue plan |
| Key used across tenants | BOLA/IDOR | Query tenant from verified principal, never from input |
| Retry/gateway logs secret | Leaked via request dumps | Sanitize and enforce controls at every hop |

**An API key is not an encryption key.** The key proves authorization to call an API; the server's HMAC algorithm uses a separate secret called a **pepper**, and the two roles must never be conflated or stored together in the same DB.

## 3. Format: Public Key ID and 256-Bit Secret

Illustrative format:

~~~text
ak_<kid16>.<secret43>
kid16:     12 random bytes -> unpadded Base64URL -> 16 chars
secret43:  32 random bytes -> unpadded Base64URL -> 43 chars
~~~

Dummy example **for tests only**:

~~~text
ak_k7Xb2Pq9Wm4Ns8Ta.AQIDBAUGBwgJCgsMDQ4PEBESExQVFhcYGRobHB0eHyA
~~~

The public string above is **not a production secret**. For real keys, Java's `SecureRandom` generates 32 fresh random secret bytes; 32 good random bytes correspond to roughly \(2^{256}\) possibilities. Never use timestamps, emails, sequential numbers, `java.util.Random`, improperly assembled UUIDs, or user-chosen passwords for the secret portion.

**Public ID** enables querying the record, precise revocation, and distinguishing rotations in audit logs. It grants no authority on its own. The prefix is purely formatting; never use an `ak_prod` prefix to treat a token as coming from production prior to verification.

Accept only a single canonical encoding. Validate length, Base64URL charset, and exact decoded byte count; do not arbitrarily trim whitespace or accept multiple representations of the same key. Because secrets are issued once, losing a key means **reissuing**, never building a "view secret again" API.

## 4. One-Way Storage with HMAC-SHA256

After generating the full key, the server computes:

~~~text
digest = HMAC_SHA256(
    server_pepper_v1,
    ASCII("api-key:v1:" + kid + ":" + secret)
)
~~~

Store **kid, 32-byte digest, pepper_version, owner/tenant, scopes, validFrom, expiresAt, revokedAt**. Never store the secret or full key.

On each request: parse the key → look up the DB by kid → fetch the matching pepper version from the secret manager → recompute HMAC → use `MessageDigest.isEqual` on the two fixed-size digests → check status/time/scopes.

**Why HMAC?** With a random 256-bit secret, plain SHA-256 is already hard to brute-force; a server-held pepper kept separate from the DB adds defense in depth if only the DB is read. A pepper does not make a weak key strong. Never use fast HMAC for user-chosen passwords; passwords require slow KDFs such as Argon2id/PBKDF2/bcrypt per threat model and must not run blocking CPU work on the Netty event loop.

**Why not reversible encryption?** The application only needs to match credentials, not recover plaintext. Encryption at rest / DB encryption remains useful for protecting metadata and backups, but does not replace storing a fingerprint.

**No full-HTTP constant-time guarantee:** `MessageDigest.isEqual` improves over naive byte-by-byte comparison, yet DB hits/misses and metadata paths still vary in timing; pair it with generic errors, rate limits, and monitoring. Never call `String.equals` directly on a plaintext key and log the result alongside the input string.

## 5. Key Lifecycle

~~~mermaid
flowchart TD
    A["Authorized admin/owner requests key"] --> B["Generate kid + secret via CSPRNG"]
    B --> C["HMAC fingerprint with pepper version"]
    C --> D["Insert digest/scopes/tenant/time/audit"]
    D --> E["Display full key once over secure TLS channel"]
    E --> F["ACTIVE"]
    F --> G{"Normal rotation?"}
    G -->|"Yes"| H["Issue new key, bounded overlap"]
    H --> I["Client deploys new secret, verify usage"]
    I --> J["Revoke old key"]
    G -->|"Compromised"| K["Revoke immediately, no overlap"]
    F --> L["ExpiresAt or revokedAt -> 401"]
    J --> M["Retain audit metadata per policy"]
    K --> M
    L --> M
~~~

Required states: issued, `valid_from` active, active, pending replacement, revoked, expired. Do not "soft-disable" in the UI while forgetting API enforcement. Never return detailed status to unauthenticated callers, as that can disclose whether a key ID exists.

**Normal rotation:** issue a new key with a different ID and secret, let the client switch during a bounded overlap window, then revoke the old key; both keys are audited separately. **Emergency rotation:** if a key is leaked, revoke it immediately and issue a new key—never wait for the client to finish deploying while an attacker continues using the compromised key.

## 6. Realistic Database Schema

PostgreSQL example for an R2DBC-backed system:

~~~sql
CREATE TABLE api_keys (
    kid                 VARCHAR(32) PRIMARY KEY,
    owner_id            UUID NOT NULL,
    tenant_id           UUID NOT NULL,
    credential_digest   BYTEA NOT NULL,
    digest_version      SMALLINT NOT NULL,
    pepper_version      SMALLINT NOT NULL,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_from          TIMESTAMPTZ NOT NULL,
    expires_at          TIMESTAMPTZ NOT NULL,
    revoked_at          TIMESTAMPTZ,
    last_used_at        TIMESTAMPTZ,
    rotation_group_id   UUID NOT NULL,
    created_by          UUID NOT NULL,
    CONSTRAINT ck_digest_length CHECK (
        octet_length(credential_digest) = 32),
    CONSTRAINT ck_valid_interval CHECK (expires_at > valid_from)
);

CREATE TABLE api_key_scopes (
    kid                 VARCHAR(32) NOT NULL
        REFERENCES api_keys(kid) ON DELETE CASCADE,
    scope               VARCHAR(120) NOT NULL,
    PRIMARY KEY (kid, scope)
);

CREATE INDEX idx_key_owner
    ON api_keys(owner_id, tenant_id, revoked_at, expires_at);
~~~

There is no `raw_key`, `secret`, or `plaintext_api_key`. `kid` is unique to locate the record; `digest` is strictly for verification, never a foreign key or log field. You may add `status`, label, `replaced_by`, policy version, quota, or a last-four masked indicator per contract.

**Database permissions:** the runtime application only needs read access to verification columns; admin/revocation endpoints need separate privileges; backups and logs must be encrypted and audited. With R2DBC, `findByKid` returns `Mono<ApiKeyRecord>`, avoiding blocking JDBC on the Reactor event loop. Tenant queries in the domain layer must use prepared/parameterized statements, never string concatenation from paths.

## 7. Scoping Permissions Before and After Authentication

A key can be issued as:

| Integration | Tenant | Scopes | Lifetime |
| --- | --- | --- | --- |
| Reporting worker | tenant-A | `reports.read` | 30 days |
| Export worker | tenant-A | `reports.read`, `reports.export` | 7 days |
| Billing worker | tenant-B | `invoices.read` | 14 days |

The HTTP layer allows `GET /partner/reports` only with `SCOPE_reports.read` and `POST /partner/reports` only with `SCOPE_reports.write`. The domain layer then verifies that the record belongs to `tenantId` from the **verified principal**. Never trust a tenant in `X-Tenant-Id` or `?tenant=...` to grant access without matching it against the verified identity.

An HMAC match alone does not grant access. The owner/tenant may be suspended, scopes may have changed, the resource may be deleted, or dual approval may be required. For sensitive data, object-level authorization must live in the service near persistence, not solely in route matchers.

## 8. Authentication Design in WebFlux

~~~mermaid
sequenceDiagram
    participant C as Client
    participant F as AuthenticationWebFilter
    participant M as ReactiveAuthenticationManager
    participant R as ApiKeyStore
    participant H as Handler
    C->>F: X-API-Key ak_kid.secret
    F->>F: ServerAuthenticationConverter parse header count/size
    F->>M: Unauthenticated credential
    M->>M: Canonical parse, HMAC-SHA256
    M->>R: findByKid(kid)
    R-->>M: digest, scopes, tenant, expiry, revoke
    M->>M: Digest compare + validFrom/expiry/revokedAt
    alt invalid
        M-->>F: BadCredentialsException
        F-->>C: 401 generic
    else valid
        M-->>F: Authenticated principal, SCOPE_...
        F->>H: Reactor SecurityContext
        H-->>C: Authorized response
    end
~~~

Spring Security Reactive uses `AuthenticationWebFilter`, `ServerAuthenticationConverter`, `ReactiveAuthenticationManager`, and `SecurityWebFilterChain`. Never use Servlet `OncePerRequestFilter` or ThreadLocal `SecurityContextHolder` in Reactor code and expect authentication to survive thread switches.

**Fail closed:** missing/malformed/wrong/revoked/expired key → 401; valid key lacking scope → 403; DB/KMS unavailable → no successful Authentication (HTTP 5xx per error policy). Never write `onErrorResume(ex -> Mono.just(previousPrincipal))` to preserve uptime.

## 10. KeyCrypto.java: Canonical Parsing and HMAC Fingerprint

File `src/main/java/demo/keys/KeyCrypto.java`:

~~~java
package demo.keys;

import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.util.Base64;
import java.util.regex.Matcher;
import java.util.regex.Pattern;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import org.springframework.security.authentication.BadCredentialsException;

record KeyParts(String kid, String secret) {
    // Prevent toString from accidentally printing the raw key.
    @Override public String toString() {
        return "KeyParts[kid=" + kid + ",secret=<redacted>]";
    }
}

public final class KeyCrypto {
    private static final Pattern FORMAT = Pattern.compile(
        "^ak_([A-Za-z0-9_-]{16})\\.([A-Za-z0-9_-]{43})$");

    private final byte[] pepper;

    public KeyCrypto(String encodedPepper) {
        byte[] decoded;
        try {
            decoded = Base64.getDecoder().decode(encodedPepper);
        } catch (IllegalArgumentException exception) {
            throw new IllegalStateException(
                "HMAC pepper must be valid Base64", exception);
        }
        if (decoded.length != 32) {
            throw new IllegalStateException(
                "HMAC pepper must have exactly 32 bytes");
        }
        this.pepper = decoded.clone();
    }

    static KeyParts parse(String raw) {
        if (raw == null || raw.length() > 96) {
            throw invalid();
        }
        Matcher m = FORMAT.matcher(raw);
        if (!m.matches()) {
            throw invalid();
        }
        String secret = m.group(2);
        byte[] decoded;
        try {
            decoded = Base64.getUrlDecoder().decode(secret);
        } catch (IllegalArgumentException ex) {
            throw invalid();
        }
        if (decoded.length != 32) {
            throw invalid();
        }
        String canonical = Base64.getUrlEncoder()
            .withoutPadding().encodeToString(decoded);
        if (!canonical.equals(secret)) {
            throw invalid();
        }
        return new KeyParts(m.group(1), secret);
    }

    byte[] fingerprint(KeyParts parts) {
        String message = "api-key:v1:" + parts.kid()
            + ":" + parts.secret();
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(pepper, "HmacSHA256"));
            return mac.doFinal(
                message.getBytes(StandardCharsets.US_ASCII));
        } catch (GeneralSecurityException ex) {
            throw new IllegalStateException("HMAC unavailable", ex);
        }
    }

    static BadCredentialsException invalid() {
        return new BadCredentialsException("Invalid API key");
    }
}
~~~

**Explanation:**
- 12-byte public ID → 16 chars; 32-byte secret → 43 chars unpadded Base64URL.
- `parse` does not auto-trim and validates length plus canonical encoding so two different strings cannot represent the same entropy.
- `Mac` is instantiated per verification rather than sharing a non-thread-safe instance.
- The HMAC message includes a domain separator + `kid` so the same digest cannot accidentally be reused for another purpose.
- Never log raw `KeyParts`, request headers, or pepper. Java Strings cannot be reliably zeroized; restrict memory dumps/APM and secret scope.
- In production, the pepper is fetched from KMS per the record's `pepper_version`; the lab only has v1.

## 11. KeyStore.java: In-Memory Metadata, Expiry, and Revocation

File `src/main/java/demo/keys/KeyStore.java`:

~~~java
package demo.keys;

import java.time.Instant;
import java.util.Arrays;
import java.util.Objects;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import reactor.core.publisher.Mono;

record KeyRecord(
        String kid,
        String ownerId,
        String tenantId,
        byte[] digest,
        Set<String> scopes,
        Instant validFrom,
        Instant expiresAt,
        Instant revokedAt) {

    KeyRecord {
        Objects.requireNonNull(kid);
        Objects.requireNonNull(ownerId);
        Objects.requireNonNull(tenantId);
        Objects.requireNonNull(digest);
        Objects.requireNonNull(scopes);
        Objects.requireNonNull(validFrom);
        Objects.requireNonNull(expiresAt);
        if (digest.length != 32 || !expiresAt.isAfter(validFrom)) {
            throw new IllegalArgumentException("Invalid key metadata");
        }
        digest = Arrays.copyOf(digest, digest.length);
        scopes = Set.copyOf(scopes);
    }

    @Override public byte[] digest() {
        return Arrays.copyOf(digest, digest.length);
    }

    KeyRecord revoked(Instant at) {
        return new KeyRecord(kid, ownerId, tenantId,
            digest, scopes, validFrom, expiresAt, at);
    }
}

public final class KeyStore {
    private final ConcurrentHashMap<String, KeyRecord> rows =
        new ConcurrentHashMap<>();

    public Mono<KeyRecord> findByKid(String kid) {
        return Mono.defer(() -> Mono.justOrEmpty(rows.get(kid)));
    }

    public void put(KeyRecord record) {
        rows.put(record.kid(), record);
    }

    public void revoke(String kid) {
        rows.computeIfPresent(kid,
            (id, prior) -> prior.revoked(Instant.now()));
    }

    public void clear() {
        rows.clear();
    }
}
~~~

`KeyRecord` defensively clones `digest` to prevent external array mutation and copies scopes into an immutable set. In production, use a DB/R2DBC queried by `kid`, never storing full keys. `ConcurrentHashMap` lacks persistence, cross-node coherence, auditing, or multi-table atomic transactions—replace it before real deployment.

## 12. KeyAuthManager.java: Verifying Digest, Status, and Granting Scopes

File `src/main/java/demo/keys/KeyAuthManager.java`:

~~~java
package demo.keys;

import java.security.MessageDigest;
import java.security.Principal;
import java.time.Instant;
import java.util.List;
import org.springframework.security.authentication.ReactiveAuthenticationManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import reactor.core.publisher.Mono;

record KeyPrincipal(String kid, String ownerId, String tenantId)
        implements Principal {
    @Override public String getName() {
        return ownerId;
    }
}

public final class KeyAuthManager implements ReactiveAuthenticationManager {

    private static final byte[] DUMMY_DIGEST = new byte[32];

    private final KeyStore store;
    private final KeyCrypto crypto;

    public KeyAuthManager(KeyStore store, KeyCrypto crypto) {
        this.store = store;
        this.crypto = crypto;
    }

    @Override
    public Mono<Authentication> authenticate(Authentication input) {
        if (!(input.getCredentials() instanceof String raw)) {
            return Mono.error(KeyCrypto.invalid());
        }

        return Mono.defer(() -> {
            KeyParts parts = KeyCrypto.parse(raw);
            byte[] candidate = crypto.fingerprint(parts);

            return store.findByKid(parts.kid())
                .switchIfEmpty(Mono.defer(() -> {
                    // Constant-time HTTP is not guaranteed:
                    // DB hit/miss may still exhibit timing differences.
                    MessageDigest.isEqual(DUMMY_DIGEST, candidate);
                    return Mono.error(KeyCrypto.invalid());
                }))
                .flatMap(record -> {
                    boolean matched = MessageDigest.isEqual(
                        record.digest(), candidate);
                    Instant now = Instant.now();
                    if (!matched
                            || record.revokedAt() != null
                            || now.isBefore(record.validFrom())
                            || !now.isBefore(record.expiresAt())) {
                        return Mono.error(KeyCrypto.invalid());
                    }

                    List<GrantedAuthority> granted =
                        record.scopes().stream()
                            .map(scope -> (GrantedAuthority)
                                new SimpleGrantedAuthority(
                                    "SCOPE_" + scope))
                            .toList();

                    KeyPrincipal principal = new KeyPrincipal(
                        record.kid(),
                        record.ownerId(),
                        record.tenantId());

                    return Mono.just((Authentication)
                        UsernamePasswordAuthenticationToken.authenticated(
                            principal, null, granted));
                });
        });
    }
}
~~~

**Security guarantees:** HMAC/digest is verified before issuing Authentication; invalid keys and unknown `kid`s both return the same `BadCredentialsException`. Authorities are granted strictly from **server-stored** metadata, never from client headers or bodies. A successful Authentication carries no raw secret in credentials, and the principal holds only public key ID, owner, and tenant.

In the lab this is a fast in-memory operation. Production DBs must be non-blocking or properly scheduled, never calling `block()` or manually calling `subscribe()`. If the DB/KMS genuinely fails, `Mono.error` keeps the request unauthenticated; never fall back to a cached stale principal.

## 13. KeySecurityConfig.java: AuthenticationWebFilter in WebFlux

File `src/main/java/demo/keys/KeySecurityConfig.java`:

~~~java
package demo.keys;

import java.time.Instant;
import java.util.List;
import java.util.Set;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.security.authentication.BadCredentialsException;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.config.web.server.SecurityWebFiltersOrder;
import org.springframework.security.web.server.SecurityWebFilterChain;
import org.springframework.security.web.server.authentication.AuthenticationWebFilter;
import org.springframework.security.web.server.authentication.HttpStatusServerEntryPoint;
import org.springframework.security.web.server.authentication.ServerAuthenticationEntryPointFailureHandler;
import org.springframework.security.web.server.context.NoOpServerSecurityContextRepository;
import org.springframework.security.web.server.util.matcher.PathPatternParserServerWebExchangeMatcher;
import reactor.core.publisher.Mono;

@Configuration
@EnableWebFluxSecurity
public class KeySecurityConfig {

    @Bean
    KeyCrypto crypto(@Value("${lab.pepper-base64}") String pepper) {
        return new KeyCrypto(pepper);
    }

    @Bean
    KeyStore store(
            KeyCrypto crypto,
            @Value("${lab.bootstrap-key:}") String bootstrap) {
        KeyStore store = new KeyStore();
        if (!bootstrap.isBlank()) {
            KeyParts parts = KeyCrypto.parse(bootstrap);
            Instant now = Instant.now();
            store.put(new KeyRecord(
                parts.kid(), "demo-partner", "demo-tenant",
                crypto.fingerprint(parts), Set.of("reports.read"),
                now.minusSeconds(1), now.plusSeconds(86400), null));
        }
        return store;
    }

    @Bean
    KeyAuthManager manager(KeyStore store, KeyCrypto crypto) {
        return new KeyAuthManager(store, crypto);
    }

    @Bean
    SecurityWebFilterChain chain(
            ServerHttpSecurity http, KeyAuthManager manager) {

        var entry = new HttpStatusServerEntryPoint(
            HttpStatus.UNAUTHORIZED);

        var filter = new AuthenticationWebFilter(manager);
        filter.setSecurityContextRepository(
            NoOpServerSecurityContextRepository.getInstance());
        filter.setRequiresAuthenticationMatcher(
            new PathPatternParserServerWebExchangeMatcher("/partner/**"));
        filter.setAuthenticationFailureHandler(
            new ServerAuthenticationEntryPointFailureHandler(entry));

        filter.setServerAuthenticationConverter(exchange -> {
            List<String> values =
                exchange.getRequest().getHeaders().get("X-API-Key");
            if (values == null || values.isEmpty()) {
                return Mono.empty();
            }
            if (values.size() != 1
                    || values.get(0) == null
                    || values.get(0).length() > 96) {
                return Mono.error(
                    new BadCredentialsException("Invalid API key"));
            }
            return Mono.just(
                UsernamePasswordAuthenticationToken.unauthenticated(
                    "api-key", values.get(0)));
        });

        return http
            .securityContextRepository(
                NoOpServerSecurityContextRepository.getInstance())
            .authorizeExchange(ex -> ex
                .pathMatchers(HttpMethod.GET, "/public/health")
                    .permitAll()
                .pathMatchers(HttpMethod.GET, "/partner/reports")
                    .hasAuthority("SCOPE_reports.read")
                .pathMatchers(HttpMethod.POST, "/partner/reports")
                    .hasAuthority("SCOPE_reports.write")
                .anyExchange().denyAll())
            .exceptionHandling(ex ->
                ex.authenticationEntryPoint(entry))
            .addFilterAt(filter, SecurityWebFiltersOrder.AUTHENTICATION)
            .httpBasic(ServerHttpSecurity.HttpBasicSpec::disable)
            .formLogin(ServerHttpSecurity.FormLoginSpec::disable)
            .requestCache(ServerHttpSecurity.RequestCacheSpec::disable)
            .csrf(ServerHttpSecurity.CsrfSpec::disable)
            .build();
    }
}
~~~

**Why this setup?** `AuthenticationWebFilter` runs its converter only on `/partner/**`; an `X-API-Key` header produces an **unauthenticated** token, and the manager verifies it and returns an authenticated principal. `authorizeExchange` checks permissions by method and path. `HttpStatusServerEntryPoint` returns a generic 401 for unauthenticated requests or wrong keys without prompting for HTTP Basic credentials. `NoOpServerSecurityContextRepository` avoids saving Authentication into cookies/sessions.

**Do not auto-trim the key**, and do not read keys from URLs/queries or cookies. If another application uses multiple authentication mechanisms, use `securityMatcher` and `@Order` to separate `SecurityWebFilterChain`s cleanly; never allow a cookie session to authenticate routes where CSRF is disabled.

CSRF is disabled in this example because it is **strictly header-only server-to-server authentication**, where browsers do not auto-send API keys like cookies. If you allow API keys in auto-sent cookies, you must design CSRF protection. CORS does not replace auth/CSRF; an SPA embedding a key in JavaScript is insecure because the key can easily be extracted.

## 15. KeyGenerator.java: CSPRNG and One-Time Local Key Issuance

File `src/main/java/demo/keys/KeyGenerator.java`:

~~~java
package demo.keys;

import java.security.SecureRandom;
import java.util.Base64;

public final class KeyGenerator {
    private static final SecureRandom RANDOM = new SecureRandom();

    private static String url(byte[] value) {
        return Base64.getUrlEncoder()
            .withoutPadding().encodeToString(value);
    }

    public static void main(String[] args) {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                "Choose --key or --pepper");
        }

        if ("--key".equals(args[0])) {
            byte[] id = new byte[12];
            byte[] secret = new byte[32];
            RANDOM.nextBytes(id);
            RANDOM.nextBytes(secret);
            System.out.println("ak_" + url(id) + "." + url(secret));
            return;
        }

        if ("--pepper".equals(args[0])) {
            byte[] pepper = new byte[32];
            RANDOM.nextBytes(pepper);
            System.out.println(
                Base64.getEncoder().encodeToString(pepper));
            return;
        }

        throw new IllegalArgumentException("Unknown option");
    }
}
~~~

This CLI intentionally **prints keys/peppers to stdout** because it is strictly for local learning in a private terminal. Production issuance must deliver secrets over a protected admin channel and display them only once, never printing them to CI/build logs. Production peppers should be generated and managed in a secret vault/KMS, never reusing an API key as a pepper.

## 18. Issuing API Keys as an Administrative Action

The lab does not expose a public key-issuance endpoint because copying it carelessly creates vulnerabilities. A production admin API should:
1. Require strong admin/workload authentication with risk-appropriate MFA/approval.
2. Determine owner/tenant from the admin principal, never trusting self-declared request user fields.
3. Allow only scopes from an admin-grantable allowlist with a maximum TTL.
4. Generate `kid`/secret with a CSPRNG server-side, compute HMAC with KMS pepper, and store digest+metadata.
5. Persist scopes and audit records in a single transaction; handle unique `kid` collisions and idempotency.
6. Return the full key **once** over TLS with `Cache-Control: no-store`; never send it via email, tickets, or analytics.
7. Subsequent reads expose only `kid`, masked suffix, scopes, created/expires timestamps, status, and `lastUsed`.
8. Support revocation by `kid`, always checking owner/tenant authorization and auditing the actor.
9. Cap active keys per client/tenant and enforce risk-based default expirations.
10. If the client loses a key before saving it to a vault, there is no "recover plaintext"; revoke and reissue.

Example **showing response structure only** on initial creation:

~~~json
{
  "keyId": "k7Xb2Pq9Wm4Ns8Ta",
  "apiKey": "<one-time-value-from-secure-issuance>",
  "scopes": ["reports.read"],
  "expiresAt": "2027-01-01T00:00:00Z"
}
~~~

Never return `apiKey` again afterward. For key rotation, the two keys have distinct `kid`s but may share a rotation group or owner for auditing.

## 19. Zero-Downtime Rotation Workflow

Suppose key A expires on day T:
- **T−7 days:** system notifies the owner and reviews the current client and scopes.
- **T−2 days:** issue new key B with least-privilege permissions, same tenant, and its own expiry; A and B are temporarily both active.
- **T−1 day:** partner updates B in their secret vault/deployment and verifies B works.
- **Before T:** observe usage by public `kid` and error rates to ensure B is genuinely serving traffic.
- **T:** revoke A, invalidate caches, and verify A→401, B→200 in an authorized environment.
- **After T:** audit and purge any plaintext copies from deployment logs (if any) per procedure, retaining metadata per retention policy.

This is a **bounded-overlap** process, not an excuse to keep old keys indefinitely. Never overwrite A's digest in the same row to turn it into B, as auditing and caching could conflate two distinct keys' usage.

**Emergency rotation:** when A is suspected compromised, revoke A **immediately** and issue B securely; never extend overlap just because a client asks for more time. Temporarily block endpoints or follow an approved break-glass plan if necessary. Afterward, trace by `kid`/time/IP/traces (without viewing raw tokens), inspect accessed data, and notify stakeholders.

## 20. Pepper Rotation and the No-Plaintext Constraint

If the DB stores only:

~~~text
fingerprint_v1 = HMAC(pepper_v1, "api-key:v1:"+kid+":"+secret)
~~~

then you cannot directly compute:

~~~text
fingerprint_v2 = HMAC(pepper_v2, "api-key:v1:"+kid+":"+secret)
~~~

from `fingerprint_v1` **without knowing the secret**. Therefore, pepper rotation must be designed as follows:
- Store `pepper_version` in the DB record.
- New key issuance always uses the current pepper version.
- During transition, the server retains the old pepper **solely to verify old keys** inside KMS with strict permissions.
- Migrate by **issuing new keys** and retiring old ones, or via a carefully vetted re-fingerprinting mechanism when a valid key is presented after thorough transaction, race, and revocation analysis.
- Once no active records depend on the old pepper, retire the old pepper per policy.
- If a pepper is compromised, treat it as an incident and reissue affected keys rather than relying on long-term dual verification.

Never share a single pepper across multiple systems or unrelated cryptographic purposes. Versioning must go hand in hand with auditing, KMS ACLs, disaster recovery, and rollback planning.

## 21. Caching, Revocation, and Multiple Instances

With an in-memory store, revocation takes effect immediately within the same process. Production runs multiple instances and may cache metadata; a revoked key can remain usable on another instance until its cache is invalidated.

| Approach | Performance | Revocation |
| --- | --- | --- |
| R2DBC DB read per request | Higher I/O cost | Sees committed DB state per consistency model |
| Short positive-TTL cache | Fast | Stale up to TTL/cache anomalies |
| Pub/sub invalidation + TTL fallback | Fast | Must test lost messages/restarts/network partitions |
| Infinite cache | Very fast | **Incompatible** with revocation SLAs |
| DB down → fall back indefinitely to cached principal | Appears resilient | **Fails open** under strict trust models |

Define your **revocation SLA** before choosing a cache strategy: payment APIs may require strict immediate revocation, whereas low-sensitivity read APIs may tolerate a few seconds per policy. Never generalize that "a 5-minute TTL is always safe".

A request that already passed auth prior to revocation may still be executing; when revocation must halt long-running jobs, domain services need checkpoints, revalidation, or cancellation at business boundaries. No single `UPDATE` statement automatically rolls back already completed side effects.

## 22. Protecting Secrets Across Logs, Network, and Clients

- Enforce HTTPS outside localhost; never disable certificate validation.
- Pass API keys in headers, **never** in URL queries, redirect `Location` headers, or JSON errors.
- Mask `X-API-Key` across gateways, app logs, wiretap, APM, traces, screenshots, and support bundles.
- Never embed secrets in frontend JavaScript, mobile bundles, Git, Dockerfiles, commit messages, Slack/email, or issue trackers.
- Issue separate keys per environment/client/tenant; never reuse prod keys in staging.
- Apply rate limits per `kid`/owner/tenant for valid keys, and IP/WAF/concurrency limits for unknown keys.
- Check header size before parsing; reject multiple header values or ambiguous formats.
- If using IP allowlists behind proxies, trust forwarded IPs only from trusted proxies.
- Run secret scanning in repos and CI with automated revoke/rotate runbooks on Git leaks.
- Consider mTLS or request signing + nonce/timestamp for anti-replay use cases; ordinary API keys do not stop replay once plaintext is leaked.

**CORS is not authentication:** if a JavaScript SPA sends `X-API-Key` cross-origin, the browser may send a preflight, but a CORS allowlist **does not stop** attackers from extracting a key already embedded in JS. Use OAuth2 Authorization Code + PKCE or a server-side BFF for public/browser clients.

## 23. 401/403 Matrix and Errors That Must Not Leak

| Scenario | Result | Meaning |
| --- | --- | --- |
| Missing header on protected endpoint | 401 | Unauthenticated |
| Malformed key / oversized / multiple headers | 401 | No valid credential |
| Unknown kid | 401 | No matching auth record found |
| Wrong secret | 401 | HMAC mismatch |
| Revoked / expired / not-before | 401 | Credential no longer or not yet valid |
| Valid key, missing write scope | 403 | Authentication succeeded, authorization failed |
| Valid key, `reports.read` matching tenant | 200 | Allowed into controller |
| Valid key, wrong object owner/tenant | 403/404 per API policy | Domain authorization |
| Database/KMS cannot verify | Fail closed, typically 5xx | No authenticated principal issued |
| Key rotated/revoked while cache is stale | Potential vulnerability | Needs revocation SLA/invalidation |

Use a **generic status/body** for 401 credential errors; never return "this key ID exists but was revoked" to unauthenticated callers. Internal logging can classify reasons with a dedicated enum, while strictly omitting full keys, digests, or peppers.

## 24. Incidents and Diagnostics

| Symptom | Likely Cause | Resolution |
| --- | --- | --- |
| All requests return 401 after deploy | Wrong pepper/version or DB metadata mismatch | Check KMS config/digest version |
| Newly issued key gets 401 | Canonical format mismatch or `validFrom` skew | Check Base64URL and clocks/NTP |
| Revoked key still returns 200 | Stale cache or replica lag | Invalidate cache, shorten TTL, verify DB read |
| Read-only partner succeeds on POST | Broken authz scope rule | Check `hasAuthority` and unit tests |
| Tenant-A reads Tenant-B data | Missing ownership check | Filter by tenant in service/DB |
| HMAC always fails | Encoding/pepper mismatch in code | Verify versioning, US_ASCII/UTF-8, canonical format |
| Spike of 401s on one kid | Key leaked/probed/bad secret update | Rate limit, notify owner, audit |
| Key lost and admin wants to view it | Database holds only fingerprint | Revoke and issue a new key |
| API key works in both staging and prod | Secret reused against policy | Enforce per-environment issuance |
| DB outage produces 200 | Fail-open fallback | Remove fallback, test repository errors |
| Client gets 403 after rotation | New key missing required scope | Approve scope changes/contracts |
| API key leaked in support logs | Masking omitted some hop | Scrub logs, revoke, run incident response |

Debug in order: header presence/length → canonical parsing → `kid` lookup → fingerprint version/HMAC → revoked/time checks → scopes → domain tenant → cache/invalidation → HTTP status. Never fix a 401 by disabling authentication or granting wildcard scopes.

## 25. Practice Exercises

**A. High entropy:** Generate 1000 keys with `KeyGenerator` in a lab; inspect format, length, and ID uniqueness (without treating small-sample non-collision as mathematical proof). Never log secrets in CI.

**B. Fingerprint only:** Store only the HMAC digest and metadata; verify zero raw secrets remain in DB/test snapshots and no "show key" endpoint exists.

**C. Invalid authentication:** Use `WebTestClient` to test missing, wrong, malformed, and duplicate keys. Status and body must not reveal whether `kid` exists.

**D. Scope:** Verify GET `reports.read`=200 and POST without `reports.write`=403; then issue a test key with `reports.write` and confirm POST succeeds.

**E. Expiry/revocation:** Create revoked, expired, and not-yet-valid records. Prove no Authentication succeeds even when the HMAC matches.

**F. Rotation overlap:** Issue A and B for the same owner/tenant, confirm both work during overlap, then revoke A and confirm A→401 and B→200.

**G. Emergency revoke:** Simulate key A exposure; revoke immediately with no overlap and verify logs/traces contain no raw secret.

**H. Pepper rotation:** Add pepper versions v1/v2 and migrate via key reissue; explain why old fingerprints cannot be rehashed without knowing the secret.

**I. Domain authorization:** Have a Tenant-A key attempt to query Tenant-B's report; the service must block it despite `reports.read`.

**J. Cache outage:** Simulate DB timeouts, stale caches, dropped invalidation messages, and recently revoked keys; measure revocation SLA and confirm fail-closed behavior.

**K. Resource boundaries:** Compare API keys with OAuth2 Client Credentials, mTLS, and BFF/OIDC to choose appropriately for public vs confidential clients.

**L. Secret scanning:** Place a dummy test key in a lab file, configure a detector, and practice the automated revoke/rotate runbook on a Git leak. Never test with real credentials.
