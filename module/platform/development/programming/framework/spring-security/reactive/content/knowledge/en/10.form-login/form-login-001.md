# Protected Resource Access Flow, Redirects, and Login

## Lesson Objectives

In a **Spring Security Reactive (Spring WebFlux)** application using **form login**, an unauthenticated user typically does not receive the content of a protected page immediately. Instead, Spring Security initiates a **browser-based login flow**: redirecting to the login page, authenticating the form data, storing the authentication state appropriately for WebFlux, and then returning the user to the requested resource if the request was remembered.

After this lesson, you will be able to:

1. Describe the exact sequence of requests/responses from an unauthenticated `GET /private` to `GET /login`, `POST /login`, and back to `/private`.
2. Distinguish **authentication** (who the user is) from **authorization** (what that user is allowed to access).
3. Distinguish **302 redirect**, **401 authentication required**, **403 insufficient permissions**, and **403 CSRF**.
4. Understand the roles of `SecurityWebFilterChain`, `AuthenticationWebFilter`, `ReactiveAuthenticationManager`, `ReactiveUserDetailsService`, `ExceptionTranslationWebFilter`, authentication entry point, success/failure handlers, and request cache.
5. Explain why **session cookies, CSRF tokens, and saved requests** must be kept consistent across browser requests.
6. Write a Java 17+ WebFlux application with default form login, two users with different roles, public endpoints, and protected endpoints.
7. Verify the flow using a browser and `WebTestClient`; avoid pitfalls such as redirect loops, lost sessions, POST login missing CSRF, or exposing the wrong endpoints.

This lesson belongs to the **Form Login** section. Examples target Spring Boot 3.x, Spring Security 6.x, Reactor, and Java 17 or higher. Version-specific APIs/behaviors should be cross-checked against the Spring Security version in use. The examples use in-memory usernames/passwords **for learning only**; do not use sample credentials or that storage mechanism in production.

## 1. Problem Statement: An Unauthenticated User Opens a Protected Page

Suppose a website has four paths:

| Endpoint | Policy | Expected Result |
|---|---|---|
| `GET /` | Public | Home page `home` |
| `GET /public` | Public | `public` content |
| `GET /private` | Must be authenticated | Only logged-in users can view private content |
| `GET /admin` | Must have role `ADMIN` | Only admins can view |
| `GET /login` | Public, generated by Spring Security in the demo | HTML page with a username/password form |
| `POST /login` | Form authentication processing endpoint, not a business controller | Verify credentials, create login state, redirect |
| Other URLs | Denied per demo policy | Not automatically public |

For an unauthenticated guest, a `GET /private` request **must not pass through to the controller**. Depending on the authentication mechanism configuration, Spring Security may return `401`, `302`, or handle it differently. Specifically in **browser form login** of this demo, the typical result is **302 Found**, with header `Location: /login`.

The browser interprets `302` as an instruction to send a **new request** to the URL in `Location`. It is not the server "replacing the original request with login" within the same HTTP request. The two requests have different URLs and a continuing cookie/session chain.

## 2. The Complete Journey: Protected Request → Login → Back to Resource

### 2.1. Timeline Diagram

```text
Browser               Spring Security WebFlux             Controller / App
  |                             |                                  |
  |--- GET /private ----------->|                                  |
  |                             | unauthenticated                  |
  |                             | save request (if cache enabled)  |
  |<-- 302 Location: /login ----|                                  |
  |     (may Set-Cookie)        |                                  |
  |                             |                                  |
  |--- GET /login ------------->|                                  |
  |     Cookie: SESSION=...     |                                  |
  |<-- 200 HTML login form -----|                                  |
  |     (form has CSRF token)   |                                  |
  |                             |                                  |
  |--- POST /login ------------>|                                  |
  |     username/password       |                                  |
  |     CSRF token              |                                  |
  |     Cookie: SESSION=...     |                                  |
  |                             | verify CSRF                      |
  |                             | authenticate credentials         |
  |                             | store appropriate Authentication |
  |                             | look up saved request            |
  |<-- 302 Location: /private --|                                  |
  |     (session ID may change) |                                  |
  |                             |                                  |
  |--- GET /private ----------->|                                  |
  |     Current session cookie  |                                  |
  |                             | look up SecurityContext          |
  |                             | pass authorization               |
  |                             |--------------------------------->|
  |                             |                          handle /private
  |<----------------------------+-------- 200 hello viewer --------|
```

This is the **happy path** when the request is saved in the session, the user enters the right password, the CSRF token is valid, the session/cookie is sent back by the browser, and the success handler uses the default request cache. There is no guarantee that all headers or cookie values are strictly identical across every version. If there is no saved request, the default success handler typically redirects to `/` instead of `/private`.

### 2.2. Step 1: GET Resource While Not Logged In

`GET /private` enters WebFlux's `WebFilter`s and passes through Spring Security's `WebFilterChainProxy` and `SecurityWebFilterChain`. The rule:

```java
.pathMatchers(HttpMethod.GET, "/private").authenticated()
```

requires an authenticated `Authentication`. If none exists yet, authorization cannot let the request proceed to the controller.

In a form login configuration, the **authentication entry point** mechanism initiates the login interaction. A familiar WebFlux implementation is `RedirectServerAuthenticationEntryPoint`: instead of writing HTML directly at `/private`, it returns a redirect to `/login`.

In some flows, `ServerRequestCache` saves the original URI/request so the success handler can return to it after login. Spring Security WebFlux provides `WebSessionServerRequestCache`, `NoOpServerRequestCache`, and other options. With default form login/session, a WebSession-based request cache is typically used. **A saved request is not an arbitrary copy of the entire body**; do not assume a POST upload can be safely replayed after login. Be especially careful with state-changing actions, large requests, and sensitive parameters.

### 2.3. Step 2: Browser Receives the Redirect

Typical HTTP response:

```http
HTTP/1.1 302 Found
Location: /login
Set-Cookie: SESSION=...; Path=/; HttpOnly; ...
```

This is a **response shape example**, not verbatim headers sent by every server. The cookie may already exist from earlier, be set on another request, or belong to a different session configuration; do not hardcode the session ID and do not assume cookie names/flags are always fixed without checking the environment.

Upon receiving `Location: /login`, the browser opens another GET request. If there is a matching cookie for the domain/path/SameSite/Secure attributes, the browser sends that cookie. Using a client that does not retain cookies (for example, invoking separate `curl` commands without a cookie jar) easily causes the request cache and login state to be lost.

### 2.4. Step 3: GET Login Page

With `formLogin(Customizer.withDefaults())`, Spring Security WebFlux can provide a **default login page**: an HTML form with `username`, `password`, and a CSRF token field for POST.

Descriptive form structure example:

```html
<form method="post" action="/login">
  <input type="text" name="username" autocomplete="username">
  <input type="password" name="password" autocomplete="current-password">
  <!-- Spring Security / view engine adds a valid CSRF token -->
  <button type="submit">Sign in</button>
</form>
```

This is a **structural illustration** and does not include the actual CSRF field; **do not copy this abbreviated form directly into production**. When using Spring Security's generated login page, the page supplies the token per framework integration. If you write a custom login page, you must render the real token for the exact session; do not take a fake token or static value from examples.

### 2.5. Step 4: Browser Sends POST /login

The form typically sends content type `application/x-www-form-urlencoded` with the fields:

```text
username=viewer
password=viewer-pass
_csrf=<CSRF token value issued by the server for the session>
```

The string `<CSRF token value issued by the server for the session>` in the illustration **is not a usable value**. The browser builds the request from the form; passwords must be transmitted over **HTTPS** in a real application.

In Spring Security WebFlux, the login filter (typically part of the `AuthenticationWebFilter` mechanism for form login) extracts credentials from the request and calls `ReactiveAuthenticationManager`. The manager checks the user via `ReactiveUserDetailsService` or another identity provider, and verifies the password with `PasswordEncoder` matching the hash format.

**Key point:** `POST /login` is handled by the security filter. You **do not need** to write a `@PostMapping("/login")` controller for the default mechanism; writing a controller there by mistake can break or conflict with login processing.

### 2.6. Step 5: Successful Login

Once credentials are valid, security creates an authenticated `Authentication` with authorities and places it into the reactive context. Depending on configuration, a `ServerSecurityContextRepository` such as `WebSessionServerSecurityContextRepository` stores the state via `WebSession` so subsequent requests with the session cookie can be identified as logged in.

Do not deduce that just because "reactive" is in the name, default form login is **stateless**. Traditional browser form login requires enough state to handle sessions, request caching, and logout. Reactor Context serves context **within a single request's subscription**, whereas WebSession/security context repository helps **the next request** restore the appropriate authentication.

A success handler such as `RedirectServerAuthenticationSuccessHandler` checks the saved request. If there is an appropriate `/private` request and session continuity, it usually sends the browser back to `/private`; if there was no prior request, the default usually goes to `/`.

### 2.7. Step 6: Browser Requests the Resource Again

The browser sends a **second request to `/private`** with the current session cookie. Spring Security restores the `Authentication`, authorization checks `authenticated()`, and the new request proceeds to the controller.

The controller returns private content, such as `hello viewer`. Login success **does not automatically grant every permission**: if viewer subsequently opens `/admin` while only having `ROLE_USER`, the `hasRole("ADMIN")` rule can reject it with `403 Forbidden`.

## 3. Distinguishing Easily Confused HTTP Statuses

| Scenario | Typical Behavior in Form Login Demo | Meaning |
|---|---|---|
| Guest opens `GET /private` | `302 Location: /login` | Initiates interactive authentication |
| Guest opens `GET /login` | `200` with HTML form | Public login page |
| `POST /login` valid credentials and CSRF | `302` to saved request or `/` | Login succeeded; browser performs next GET |
| `POST /login` wrong username/password, valid CSRF | `302 Location: /login?error` | Authentication failed |
| `POST /login` missing/invalid CSRF | `403` per default CSRF protection | Request rejected before valid login |
| Logged-in viewer opens `GET /admin` | `403` | Has identity but lacks ADMIN role |
| Logged-in admin opens `GET /admin` | `200` | Valid authentication + authorization |
| API client chooses HTTP Basic instead of form | Typically `401` with challenge | Different response mechanism due to entry point |

The exact HTTP status depends on the authentication entry point, success/failure handlers, request cache, content negotiation, and customizations. Do not equate "not logged in" with "logged in but lacking permissions", and do not equate `403 CSRF` with `403 missing role`.

### 3.1. Why Not Always Return 401?

`401` fits many APIs/tokens/HTTP Basic: the client receives a challenge and sends credentials. With **browser form login**, the expected experience is redirecting the browser to an HTML page for user input. Therefore `302 /login` typically appears.

If you enable **both** form login and HTTP Basic, the chosen entry point may depend on configuration and request type. To give the demo a cleanly verifiable flow, we **disable HTTP Basic** and explicitly enable form login.

## 4. Participating Spring Security Reactive Components

| Component | Responsibility in the Journey |
|---|---|
| `WebFilterChainProxy` | Selects the security chain applied to the WebFlux request |
| `SecurityWebFilterChain` | Contains filters for authentication, authorization, CSRF, context, redirects, logout, etc. per configuration |
| `ServerHttpSecurity` | Builder creating the chain; here using `authorizeExchange` and `formLogin` |
| `AuthorizationWebFilter` | Enforces policies like `authenticated()`, `hasRole(...)`, etc. |
| `ExceptionTranslationWebFilter` | Converts eligible authn/authz errors within its scope into HTTP responses via entry point/denied handler |
| `RedirectServerAuthenticationEntryPoint` | Performs redirect to the login page when interactive authentication is needed |
| `ServerRequestCache` | Remembers the appropriate request/URI to return to after login |
| `AuthenticationWebFilter` | Reads form credentials, requests authentication, handles success/failure via the corresponding handlers |
| `ReactiveAuthenticationManager` | Verifies credentials; may rely on a user store or another system |
| `ReactiveUserDetailsService` | Looks up users in the reactive model |
| `PasswordEncoder` | Compares entered raw password against stored hash using `matches` |
| `ServerSecurityContextRepository` | Saves/restores security context across requests, typically tied to WebSession in form login flows |
| `ReactiveSecurityContextHolder` | Reads security context inside a reactive request's subscription |
| `CsrfWebFilter` | Protects unsafe methods such as POST login and POST logout |
| `RedirectServerAuthenticationSuccessHandler` | Redirects after successful login, considering saved requests |
| `ServerAuthenticationFailureHandler` | Decides the response when credentials are invalid |

This is a **responsibility map**, not a claim that filters always appear in the table's order. The actual order is managed by Spring Security; adding custom security filters requires understanding `SecurityWebFiltersOrder`. Do not use **Servlet**'s `HttpSecurity`, `SecurityFilterChain`, `ExceptionTranslationFilter`, or `HttpSessionRequestCache` to configure inbound WebFlux: they belong to a different stack.

## 5. Building a Java 17+ WebFlux Application with Default Form Login

### 5.2. `FormFlowApplication.java`

This class starts the application and scans components in the `demo.formflow` package.

### 5.3. `WebSecurityConfig.java`

```java
package demo.formflow;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.core.userdetails.MapReactiveUserDetailsService;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration
@EnableWebFluxSecurity
public class WebSecurityConfig {

    @Bean
    public SecurityWebFilterChain springSecurityFilterChain(
            ServerHttpSecurity http) {

        return http
            .authorizeExchange(exchanges -> exchanges
                .pathMatchers(HttpMethod.GET, "/", "/public").permitAll()
                .pathMatchers("/login").permitAll()
                .pathMatchers(HttpMethod.GET, "/private").authenticated()
                .pathMatchers(HttpMethod.GET, "/admin").hasRole("ADMIN")
                .anyExchange().denyAll())
            .formLogin(Customizer.withDefaults())
            .httpBasic(basic -> basic.disable())
            .build();
    }

    @Bean
    public MapReactiveUserDetailsService userDetailsService() {
        PasswordEncoder encoder =
            PasswordEncoderFactories.createDelegatingPasswordEncoder();

        UserDetails viewer = User.withUsername("viewer")
            .password(encoder.encode("viewer-pass"))
            .roles("USER")
            .build();

        UserDetails admin = User.withUsername("admin")
            .password(encoder.encode("admin-pass"))
            .roles("ADMIN")
            .build();

        return new MapReactiveUserDetailsService(viewer, admin);
    }
}
```

**Explanation of key decisions:**

1. `@EnableWebFluxSecurity` enables Spring Security integration with WebFlux; Spring Boot provides auto-configuration, but the explicit annotation makes the stack being studied clear.
2. `SecurityWebFilterChain` from `ServerHttpSecurity` is the WebFlux chain type, different from `SecurityFilterChain` from `HttpSecurity` in Servlet.
3. `GET /` and `GET /public` are public to provide a starting page and a default landing page.
4. `/login` is permitted publicly; blocking the login page itself can cause the browser to redirect in a loop without ever reaching the form.
5. `GET /private` requires `authenticated()`, while `GET /admin` requires `ROLE_ADMIN`.
6. `anyExchange().denyAll()` blocks any request not matching the demo policy, avoiding accidentally exposing new endpoints. In production, explicitly design rules for static assets, healthchecks, CORS, and actual HTTP methods used.
7. `formLogin(Customizer.withDefaults())` instructs Spring Security to use the default form login configuration; the example neither builds custom HTML nor writes a custom POST handler.
8. `httpBasic(basic -> basic.disable())` prevents the HTTP Basic entry point from interfering with the browser-dedicated redirect flow.
9. `PasswordEncoderFactories.createDelegatingPasswordEncoder()` produces a hash with an algorithm prefix, typically using BCrypt as the default encoding choice per Spring Security configuration. The two hardcoded passwords in the source are **exercise data**, not production secrets.
10. `MapReactiveUserDetailsService` allows Spring Security to look up users in the reactive model. For production, integrate a real account store, password reset management, password hashing cost, MFA, and auditing.

**Note on roles:** `.roles("ADMIN")` assigns the `ROLE_ADMIN` authority. `.hasRole("ADMIN")` checks that authority; do not write `hasRole("ROLE_ADMIN")` under the default convention. The admin in the example only has the ADMIN role, and does not automatically have USER unless declared or a role hierarchy is configured.

**CSRF has not been disabled**. This is an important part of form login and browser POSTs. Do not add `csrf(csrf -> csrf.disable())` to the configuration just to make login "work".

### 5.4. `PagesController.java`

```java
package demo.formflow;

import org.springframework.security.core.context.ReactiveSecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Mono;

@RestController
public class PagesController {

    @GetMapping("/")
    public Mono<String> home() {
        return Mono.just("home");
    }

    @GetMapping("/public")
    public Mono<String> publicPage() {
        return Mono.just("public");
    }

    @GetMapping("/private")
    public Mono<String> privatePage() {
        return ReactiveSecurityContextHolder.getContext()
            .map(context -> context.getAuthentication().getName())
            .map(name -> "hello " + name);
    }

    @GetMapping("/admin")
    public Mono<String> adminPage() {
        return Mono.just("admin");
    }
}
```

`@RestController` returns simple text bodies for easy observation in a browser. In a real web application, pages usually render HTML templates; **the security flow does not depend on whether the controller returns HTML or plain text**. `ReactiveSecurityContextHolder` reads authentication from the subscription's **Reactor Context**, not relying on Servlet's ThreadLocal.

When someone opens `/private` while unauthenticated, the controller **is not successfully invoked before the login step**. Once logged in, the controller returns `hello viewer` or `hello admin` depending on the principal. Being able to read the username in the controller does not mean all of the user's data has access control enforced: with real data, resource permissions must be checked in the service/repository.

## 6. Testing the Journey in a Browser

From the project directory containing the Gradle wrapper:

```bash
./gradlew bootRun
```

On Windows:

```powershell
.\gradlew.bat bootRun
```

Use a regular browser with a fresh/unauthenticated session and perform:

1. Open `http://localhost:8080/public`. Expect body `public` without logging in.
2. Open `http://localhost:8080/private`. The browser receives 302 to `/login` and displays the form.
3. Enter username `viewer`, password `viewer-pass`, and submit. The browser sends a POST containing the session cookie and the CSRF token generated by the login page.
4. Login succeeds. If the `/private` request was retained by the saved request cache, the browser is redirected back to `/private` and displays `hello viewer`.
5. Open `http://localhost:8080/admin` in the same browser session. Expect `403` denial because viewer does not have role ADMIN.
6. Open a new private/incognito window and log in as `admin` / `admin-pass`. After login, `/admin` allows access and returns `admin`.

**Why use two separate sessions/windows?** A browser already logged in as viewer usually sends that session cookie across all tabs of the same origin. Opening a new tab does not necessarily give you a different identity; to test admin, log out or use another profile/browser session.

### 6.1. Direct Login Differs from Accessing a Protected Page First

If you open `/login` directly and log in without a prior saved request, the default success handler usually sends you to `/`. That is the expected result for the default configuration, not evidence of a lost request cache. To test returning to `/private`, **you must start from `/private` while unauthenticated**.

### 6.2. Verifying Redirects with curl

You can inspect headers without a browser:

```bash
curl -i http://localhost:8080/private
```

If there is no authentication cookie and no interference from HTTP Basic/custom entry point, look for HTTP `302` and the `Location` header pointing to `/login`. To track cookies across multiple curl requests, use a cookie jar:

```bash
curl -i -c cookies.txt -b cookies.txt http://localhost:8080/private
curl -i -c cookies.txt -b cookies.txt http://localhost:8080/login
```

This syntax illustrates the cookie jar mechanism. To POST the form with curl, you also need to extract a **valid CSRF token for that exact session**, send the proper URL-encoded form fields, and reuse the cookie jar; do not pass real passwords on the terminal/shell history. For learning the end-to-end flow, a browser is usually more intuitive and less error-prone than copying tokens manually.

Do not use `curl -L` right away when you want to observe the 302 steps; it automatically follows redirects, making it easy to miss the status and `Location` of each hop.

## 7. Automated Spring Security WebFlux Testing

Tests should verify **the state at each step**, not just check which string a controller returns. Here we use `WebTestClient` in a **mock WebFlux application context**, applying Spring Security test support. This approach lets us send a CSRF token in tests without manually parsing HTML while still passing through the security filters.

Create `src/test/java/demo/formflow/FormFlowSecurityTests.java`:

```java
package demo.formflow;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.ApplicationContext;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.test.web.reactive.server.WebTestClient;
import org.springframework.web.reactive.function.BodyInserters;

import static org.springframework.security.test.web.reactive.server
    .SecurityMockServerConfigurers.csrf;
import static org.springframework.security.test.web.reactive.server
    .SecurityMockServerConfigurers.mockUser;
import static org.springframework.security.test.web.reactive.server
    .SecurityMockServerConfigurers.springSecurity;

@SpringBootTest
class FormFlowSecurityTests {

    @Autowired
    ApplicationContext context;

    private WebTestClient client;

    @BeforeEach
    void setup() {
        client = WebTestClient.bindToApplicationContext(context)
            .apply(springSecurity())
            .configureClient()
            .build();
    }

    @Test
    void publicResourceDoesNotRequireLogin() {
        client.get().uri("/public")
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("public");
    }

    @Test
    void unauthenticatedPrivateRequestRedirectsToLogin() {
        client.get().uri("/private")
            .exchange()
            .expectStatus().is3xxRedirection()
            .expectHeader().valueEquals(HttpHeaders.LOCATION, "/login");
    }

    @Test
    void defaultLoginPageIsAccessible() {
        client.get().uri("/login")
            .exchange()
            .expectStatus().isOk();
    }

    @Test
    void loginWithoutCsrfIsRejected() {
        client.post().uri("/login")
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)
            .body(BodyInserters.fromFormData(
                "username", "viewer").with("password", "viewer-pass"))
            .exchange()
            .expectStatus().isForbidden();
    }

    @Test
    void validLoginWithCsrfRedirects() {
        client.mutateWith(csrf())
            .post().uri("/login")
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)
            .body(BodyInserters.fromFormData(
                "username", "viewer").with("password", "viewer-pass"))
            .exchange()
            .expectStatus().is3xxRedirection()
            .expectHeader().valueEquals(HttpHeaders.LOCATION, "/");
    }

    @Test
    void invalidPasswordRedirectsBackWithError() {
        client.mutateWith(csrf())
            .post().uri("/login")
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)
            .body(BodyInserters.fromFormData(
                "username", "viewer").with("password", "wrong"))
            .exchange()
            .expectStatus().is3xxRedirection()
            .expectHeader().valueEquals(
                HttpHeaders.LOCATION, "/login?error");
    }

    @Test
    void userRoleIsNotAdminRole() {
        client.mutateWith(mockUser("viewer").roles("USER"))
            .get().uri("/admin")
            .exchange()
            .expectStatus().isForbidden();
    }

    @Test
    void adminRoleCanAccessAdminEndpoint() {
        client.mutateWith(mockUser("admin").roles("ADMIN"))
            .get().uri("/admin")
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("admin");
    }
}
```

**Note on static imports in Java:** The syntax `import static org.springframework.security.test.web.reactive.server` wrapped onto `.SecurityMockServerConfigurers...;` in the snippet above is a Java import declaration wrapped at the dot; whitespace remains lexically valid. You can type it on a single line in your IDE. The needed symbols are `SecurityMockServerConfigurers.csrf`, `mockUser`, and `springSecurity` from `spring-security-test`.

**Why use `bindToApplicationContext(...).apply(springSecurity())`?** When using a WebTestClient mock server directly from the application context, you must integrate Spring Security WebFilters into the client setup; if you bind only the controller, authorization can be bypassed in tests. `mutateWith(csrf())` uses security test infrastructure to send a valid token for the login POST. The two `mockUser` tests check **authorization** with a mocked principal; they **do not** test password hashing. Only the two login POST tests go through form credential verification.

**Meaning of the `/` redirect test:** `validLoginWithCsrfRedirects` does not start with `GET /private`, so by default there is no saved request in that request's session. Expecting `/` is appropriate. To verify saved-request end-to-end, the test must retain cookies/session across hops or run controlled browser automation; do not send two independent requests and guess why it did not return to `/private`.

Run:

```bash
./gradlew test
```

Windows:

```powershell
.\gradlew.bat test
```

Expect **8 passing tests** in a Spring Boot 3.x project with the dependencies and configuration shown above. This is the expected outcome, **not a claim that Gradle was actually executed**. If library versions or test adapters differ on redirect URLs, inspect the actual headers and adjust assertions based on the **confirmed policy**, rather than changing expected statuses merely to make tests green.

### 7.1. Testing the Request Cache Separately

To genuinely verify redirecting back to `/private`, write or run an integration flow keeping the same session:

```text
1. GET /private (unauthenticated)
   assert 302 + Location /login
   capture session cookie, if server returns Set-Cookie

2. GET /login with that cookie
   assert 200 and extract CSRF token from HTML
   remember new session cookie if any

3. POST /login with:
   Current cookie
   username=viewer
   password=viewer-pass
   _csrf=<actual token extracted from the form>
   assert 302 + Location /private

4. GET /private with post-login session cookie
   assert 200, body "hello viewer"
```

This is a **test scenario**, not token-mocking code. Changing the session ID after login or distributing sessions across multiple servers may require the test to update its cookie jar. What matters is that every request in the flow uses the exact session/token data per the application's mechanism.

### 7.2. Test Suite to Expand in Production

For a real policy, add these cases:

- Invalid credentials, disabled/locked user, expired session.
- Logged-in viewer cannot view admin data, even when calling the URL directly.
- Successful login with no saved request -> valid landing page.
- Successful login with saved request -> right URL, safe query string policy.
- Public login URL and required static resources can load; no redirect loop.
- Missing/invalid CSRF -> POST rejected; POST with valid token/session -> proceeds to authentication.
- Logout POST with valid CSRF and cookie, after which protected resources require logging in again.
- Session renewal/session fixation protection, `Secure`, `HttpOnly`, `SameSite` cookie attributes appropriate for production.
- Policy disallowing redirects to attacker-supplied domains (open redirect).
- Client receives an appropriate error when the login service or user store fails, without leaking credential details.

## 8. Saved Request, RequestCache, and Post-Login Redirect

### 8.1. What Is a Saved Request?

When an unauthenticated user opens `/private`, Spring Security can store the request information needed to return after login in `ServerRequestCache`. The form login success handler looks up the cache to pick the redirect target. For WebFlux, the relevant class is `org.springframework.security.web.server.savedrequest.WebSessionServerRequestCache`.

Do not confuse it with Servlet's `HttpSessionRequestCache` or `SavedRequestAwareAuthenticationSuccessHandler`: class names/contracts differ by stack. Not every request should be saved (such as uploads or state-changing POSTs); an appropriate caching strategy must be evaluated per version and application policy.

### 8.2. Why Does It Sometimes Redirect to `/`?

There are several valid reasons:

1. The user opened `/login` directly without a preceding protected request.
2. The browser did not send back the session cookie used when the saved request was recorded.
3. The saved request expired, was cleared, or was overwritten because the user opened multiple protected pages.
4. The request cache is disabled, or the application configured a success handler to always go to a fixed page.
5. The app runs multiple instances without properly shared/routed session state.
6. The original URL was blocked by the redirect/matcher policy, so the handler did not choose it.

If you always want to go to a fixed page (for example, a dashboard), you can configure a suitable `ServerAuthenticationSuccessHandler`, keeping in mind that it will ignore or alter the experience of returning to the saved request. This is a **UX and security decision**, not fixing every case with a hardcoded URL string.

### 8.3. Avoiding Open Redirects

Never trust a client-supplied `next`/`returnUrl` parameter without verification. For example, `/login?next=https://attacker.invalid/collect` must not be used directly as `Location` after login. If parameter-based redirects are supported, allow only internal paths/allowlisted origins, normalize paths, avoid protocol-relative URLs (`//host`), and validate encoding and canonicalization. A framework-managed saved request cache is usually safer than passing uncontrolled next URLs yourself.

### 8.4. Session Is Not Reactor Context

`WebSession` stores state across **HTTP requests** via a session repository/cookie mechanism. `ReactiveSecurityContextHolder` retrieves the security context inside the **reactive subscriber** handling a request. When a new request arrives, security filters must restore authentication from a trusted source and attach it to the current subscription. Therefore, "copying Reactor Context into ThreadLocal" cannot replace session handling.

## 9. Form Login, CSRF, and Cookies: Three Interlinked Elements

### 9.1. Why Does POST /login Require CSRF?

CSRF does not only protect state-changing operations inside the app: **login CSRF** can also force a browser to log into an attacker-controlled account, leading to data storage consequences, identity confusion, and privacy issues. Spring Security WebFlux enables CSRF protection by default for unsafe requests, including POST login.

When rendering the form, the security framework/view engine must supply a token for the exact session. The user submits the POST with cookie and token, and `CsrfWebFilter` verifies it. When the token is wrong/missing, the request is blocked. **Do not** disable CSRF merely to avoid providing a token for the form.

If writing a custom Thymeleaf view, the form should use Spring Security integration to populate the token automatically:

```html
<form th:action="@{/login}" method="post">
  <label>
    Username
    <input type="text" name="username" autocomplete="username">
  </label>
  <label>
    Password
    <input type="password" name="password" autocomplete="current-password">
  </label>
  <button type="submit">Log in</button>
</form>
```

This is a **Thymeleaf template fragment** in an application that has added Thymeleaf dependencies/view resolver and properly integrated CSRF configuration. It is not a standalone plain HTML file that is already sufficiently protected. Thymeleaf can automatically insert the CSRF hidden field when `th:action` and Spring Security integration are active; always verify the rendered HTML and actual POST in the running version.

### 9.2. Role of the Session Cookie

The browser receives a cookie identifying a server-managed session and can send it back on requests within the same origin/scope. This cookie **must not contain a plaintext password**. Flags like `Secure` (HTTPS), `HttpOnly`, `SameSite`, domain/path scope, and lifetime must be configured to fit the threat model. `SameSite` reduces certain CSRF risks but **does not replace CSRF tokens** on forms that could be attacked.

When testing behind a proxy/reverse proxy, pay attention to TLS termination and forwarded headers to avoid cookies missing the Secure flag or redirect URLs being built with the wrong scheme/host. Trust forwarded headers only from trusted proxies.

### 9.3. Session Fixation and Successful Login

The system must protect against **session fixation**: an attacker fixes a session ID and tricks the user into logging in to hijack the session. Session ID renewal/invalidation/migration on authentication, logout handlers, and the security context repository must be evaluated per policy/version. Do not assume the session ID stays unchanged before and after login; browsers and WebTestClient must follow cookies returned by the server at each step.

### 9.4. Logout POST Requires CSRF

In Spring Security WebFlux, the default logout flow typically handles **POST /logout**; because this is a state-changing request, CSRF protection applies. Users can visit a logout confirmation page via GET, then submit a POST from a form carrying the token. Do not turn `GET /logout` into a logout action solely for convenience unless the risk of forced logout has been clearly assessed. After a successful logout, verify that a new request to `/private` no longer carries the old authentication.

## 10. Customizing Form Login: Endpoint Boundaries

In a real application, you may want a branded HTML form instead of the generated login page. Concept:

```java
// Configuration snippet inside the ServerHttpSecurity DSL.
// Do not add simultaneously with the default formLogin in the main example.
.formLogin(form -> form.loginPage("/signin"))
```

When changing the login page URL yourself, you are responsible for **serving GET /signin** (controller and template/static page), permitting that URL publicly, and keeping the login processing URL/CSRF consistent. The login page URL and the URL receiving POST login **can be two different endpoints**. Do not assume changing `loginPage("/signin")` will automatically create a controller or template.

Key customizations to know:

- **Login page**: GET URL where users view the form.
- **Authentication converter**: reads username/password from the form or your chosen format per Spring Security's mechanism.
- **ReactiveAuthenticationManager**: decides whether credentials are valid.
- **Success handler**: decides the post-login redirect, considering saved requests or a fixed route.
- **Failure handler**: typically redirects back to the login page with an error indicator.
- **Authentication entry point**: decides the response when a guest opens a protected page while unauthenticated.
- **Security context repository**: saves/restores context across requests.
- **Request cache**: saves the original request if returning to it is needed.
- **Access-denied handler**: responds when an authenticated user lacks permissions.

**Do not configure by Servlet API names just because the lesson targets browsers.** In WebFlux, use components in the `org.springframework.security.web.server...` package and `ServerHttpSecurity`. Verify exact method names for your version before copying a customization snippet from a Servlet tutorial.

### 10.1. Preventing Redirect Loops with Custom Pages

If you have the rule:

```java
.authorizeExchange(exchanges -> exchanges
    .anyExchange().authenticated())
.formLogin(form -> form.loginPage("/signin"))
```

but do not permit `GET /signin` publicly, users may be redirected to a page they still need to log in to access. In the main example, `pathMatchers("/login").permitAll()` solves the corresponding problem. When adding CSS, JS, logos, or locale routes for a custom form, permit **precisely the static assets** the login page needs, avoiding overly broad `permitAll()` rules that expose APIs.

### 10.2. Do Not Read Username/Password from Query Strings

Form login should be submitted via **POST** in a URL-encoded body and over HTTPS. Do not construct links like `/login?username=...&password=...`: URLs can appear in browser history, reverse proxy logs, analytics, and referrers. Passwords must also not be stored in localStorage, written to logs, or echoed back to the client after login.

### 10.3. Authorization Is Still Required After Login

A user may pass authentication yet lack permission for the original resource. For instance, a USER user accesses `/admin` while unauthenticated: initially they may be redirected to the login page, log in successfully as viewer, yet the returning request to `/admin` must still be denied with `403`. This is the right result, not a redirect bug. **The success handler does not replace authorization.**

## 11. Distinguishing WebFlux Form Login from Other Mechanisms

| Mechanism | Where Are Credentials? | Typical Unauthenticated Response | State Retention |
|---|---|---|---|
| WebFlux Form Login | POST HTML form + CSRF | `302` redirect to login page | Typically based on WebSession/security context repository |
| HTTP Basic | `Authorization: Basic ...` on each request | `401` with Basic challenge | Do not assume stateless merely from enabling Basic |
| OAuth2/OIDC Login | Browser redirects between app and identity provider | Redirect to authorization endpoint | Uses state/nonce and protocol-specific session/correlation |
| JWT Bearer Resource Server | `Authorization: Bearer token` | `401` with challenge per configuration | Typically token-based, though each app must be evaluated |

Do not conflate a "login page" with an OAuth2 authorization flow or a JWT login REST API. This lesson covers only **username/password form login** via Spring Security Reactive.

A Spring MVC application may use `WebClient` to call other services while its inbound security remains **Servlet**. Distinguish based on the web application type handling inbound requests and security configuration, not on whether the Reactor library is present.

## 12. How to Debug When the Browser Does Not Return to the Expected Page

### 12.1. Build a Request-by-Request Observation Table

When debugging, open Developer Tools → Network in the browser and observe:

| Hop | Check | Abnormal Signs |
|---|---|---|
| GET protected | `302`, `Location` to login URL, cookie/session | Unexpected 401 or redirect URL with wrong host |
| GET login | `200`, form has right action/method, CSRF token | Repeated 302, missing form, static CSS 403 |
| POST login | Form body has username/password, CSRF token; session cookie | 403 CSRF, 302 ?error, or 4xx/5xx |
| Post-login redirect | `Location` saved request or landing page | Goes to / due to lost cookie/saved request, open redirect |
| GET protected after login | Current cookie; status 200 or 403 per role | 302 back to /login despite just logging in |
| POST logout | Cookie/token; logout succeeds | 403 due to missing CSRF, new request still authenticated |

Do not enable logging of full request bodies/headers containing credentials. When debugging is needed, use request IDs, URL paths stripped of sensitive query parameters, statuses, exception types, and safely handled session correlation IDs; do not print verbatim session IDs/tokens.

### 12.2. Specific Causes and Fixes

**A. Infinite 302 /login loop**

- Your login page is also blocked by an `authenticated()` rule.
- Proxy path/context-path rewriting causes redirects to a URL with no controller.
- The session cookie is not sent over the right HTTPS/domain/path.
- A custom entry point redirects to the wrong URL; permit the login page and inspect proxy headers.

**B. GET /login returns 404**

- Configured `formLogin(form -> form.loginPage(...))` without creating a controller/template for the custom URL.
- Running the MVC/Servlet stack instead of WebFlux while thinking it is reactive.
- Disabled form login or created a custom security chain that does not match the URL.
- URL has a different context path/routing than the client expects.

**C. POST /login returns 403**

- Missing CSRF token or token does not match the current session.
- Session cookie was not sent back; token was generated from another session.
- Form action/HTTP method/content-type does not match what the security filter expects.
- A security rule or custom filter rejected the request before authentication. Check the response and safe logs before concluding the password is wrong.

**D. POST /login redirects to ?error**

- Wrong username/password, user disabled/locked/expired per policy, or authentication manager is not reading the right account store.
- Password hash stored in the wrong format/encoder, or user store does not provide the right username.
- CSRF was valid but credential verification failed; do not change the status to 403 if the real reason is authentication failure.

**E. Login succeeds but goes to / instead of /private**

- The user opened the login page directly without going through a protected request.
- Cookies/session were not preserved across GET protected, GET login, and POST login.
- Request cache is disabled, overwritten, or the success handler uses a fixed redirect.
- Multiple browser tabs/windows caused the last saved request to change.
- Session expired or a multi-instance app does not share sessions properly.

**F. Login succeeds but /admin still returns 403**

- Authentication is valid, but role/authority is insufficient: viewer only has `ROLE_USER`.
- Wrong role mapper or using `hasRole("ROLE_ADMIN")` instead of `hasRole("ADMIN")` per convention.
- Do not fix by making the admin area `permitAll`; grant valid authorities or deny per policy.

**G. After login it 302 redirects to /login again**

- Security context was not saved/restored between the two requests.
- Browser did not send the session cookie, or the cookie was blocked by the browser due to Secure/SameSite/domain.
- Application has multiple inconsistently configured session repositories/proxies.
- A custom auth success handler wrote the response without letting the framework finish saving the context.
- Session ID changed, but the HTTP client kept using the old cookie.

**H. JavaScript client calling an API receives login HTML instead of JSON**

- Your client is calling an endpoint governed by the browser website's security policy.
- If it is a machine-to-machine API, consider a separate chain/entry point to return appropriate 401/403, token-based auth, and CSRF threat model; do not assume HTML redirects are right for every client.
- Design `securityMatcher` and the order of multiple `SecurityWebFilterChain`s when serving both browser UI and APIs; do not add two arbitrary catch-all chains.

## 13. Questions and Exercises with Answers

### Exercise 1 — Predict the Requests

A fresh browser opens `GET /private` and receives `302 /login`. It then opens `GET /login` and successfully POSTs. Why does the browser make another GET to `/private`?

**Answer:** The success handler uses the request cache to determine the URI requested prior to authentication and returns a new redirect. The browser executes a new GET request to that URL and sends the current session cookie. It is not the original `GET /private` request silently resuming from where it was paused.

### Exercise 2 — Valid Login but 403

Viewer logs in successfully with `ROLE_USER`. When the browser is redirected to `/admin`, the server returns 403. Is there an authentication error?

**Answer:** Not necessarily. Successful authentication means identity was verified; `hasRole("ADMIN")` requires `ROLE_ADMIN`. Viewer lacks permission, so 403 is the right response.

### Exercise 3 — Login Missing CSRF

The form POST sends the right username/password without a CSRF token, and the server returns 403. Should you add `csrf(csrf -> csrf.disable())` to make login work?

**Answer:** No. Protecting login from CSRF is a security requirement for browser forms. Ensure the login page supplies the token from the right session, the form submits it with POST, and the browser keeps the cookie. Only change CSRF policy when the threat model has been thoroughly evaluated with appropriate mitigations.

### Exercise 4 — Accessing /login Directly

If a user opens `GET /login` directly and logs in successfully, why do they usually land on `/` instead of `/private`?

**Answer:** Because there was no prior saved request from a protected resource. The success handler uses the default landing page, which is `/` in the example.

### Exercise 5 — Can curl Verify Redirects Without Logging In?

**Answer:** Yes. `curl -i` shows the 302 status and Location. However, to test a successful login and returning to the previous page, the client must manage session cookies and CSRF tokens across multiple requests; a standalone POST is not enough.

### Exercise 6 — Why Not Create @PostMapping("/login")?

**Answer:** Spring Security form login has a security filter that handles POST login per configuration. A custom controller is only needed when you are intentionally designing a different flow; writing a duplicate endpoint makes it very easy to misroute processing and bypass protections.

### Exercise 7 — Can Authentication Be Stored in ThreadLocal After Login?

**Answer:** In WebFlux, the standard way to access identity within a reactive request is `ReactiveSecurityContextHolder`/Reactor Context. Authentication across requests involves `ServerSecurityContextRepository`/session; ThreadLocal cannot replace them when Reactor switches threads.

### Exercise 8 — Browser Redirects to a Client-Supplied Domain

A custom success handler reads `returnUrl` from the query string without validation and returns `Location` to that domain after login. What is the risk?

**Answer:** Open redirect: an attacker abuses a trusted website to send users to a spoofed site, potentially enabling phishing or further attack chains. Only allow canonicalized and validated internal destinations/allowlists; avoid trusting client input verbatim.

### Exercise 9 — Still Able to Access /private After Logout

A browser logs out, then reopens `/private` and sees the content without logging in. What should be checked?

**Answer:** Whether logout actually cleared/stopped restoring the security context, whether cookies/sessions are handled properly, whether a browser cache/service worker is showing stale content, and whether the server is mistakenly permitting the endpoint by policy. For sensitive pages, control cache headers appropriately rather than drawing conclusions solely from the displayed page.

## 14. Pre-Production Design Checklist

- [ ] The actual inbound stack is Spring WebFlux; use `ServerHttpSecurity`/`SecurityWebFilterChain`, not Servlet by mistake.
- [ ] Public endpoints (`/login`, required assets) are explicit; protected routes have authn/authz-based policies.
- [ ] Form POST uses the right URL, username/password fields, method, and encoding.
- [ ] CSRF protection is enabled for POST login/logout and browser state-changing operations.
- [ ] Session cookies have `Secure`, `HttpOnly`, `SameSite`, domain/path/expiry suited for HTTPS/reverse proxies.
- [ ] Session fixation protection and appropriate timeout/logout/revocation plans are in place.
- [ ] Passwords are hashed via `PasswordEncoder`, never stored or logged in plaintext.
- [ ] Login includes rate limiting, credential stuffing defenses, MFA where appropriate, and error messages that avoid revealing account existence.
- [ ] Success handler and request cache have tested behavior: right saved request, safe redirect URLs, no open redirects.
- [ ] Failures return appropriate notices; users lacking roles receive 403 and are never auto-granted permissions.
- [ ] Session IDs, CSRF tokens, raw passwords, and Authorization headers are never written to logs.
- [ ] Browser testing covers the happy path, wrong password, invalid CSRF, session timeout, and logout.
- [ ] API clients are tested separately with an appropriate entry point if the app also serves REST/SPA.
- [ ] Request/response statuses and redirect chains are observable enough for diagnostics without leaking sensitive data.
- [ ] In-memory accounts and example passwords are not used in production.

## 15. Flow Summary to Remember

```text
GET /private (not logged in)
  -> AuthorizationWebFilter requires authenticated()
  -> authentication entry point for browser
  -> RequestCache may store the /private URI in WebSession
  <- 302 Location: /login

GET /login + cookie
  <- 200 HTML form with valid CSRF token

POST /login + username/password + CSRF + cookie
  -> CSRF validation
  -> AuthenticationWebFilter
  -> ReactiveAuthenticationManager + ReactiveUserDetailsService
  -> PasswordEncoder.matches(rawPassword, storedHash)

If invalid:
  <- 302 /login?error (default form login failure handler)

If valid:
  -> Authenticated Authentication + authorities
  -> ServerSecurityContextRepository stores appropriate context/session
  -> RedirectServerAuthenticationSuccessHandler looks up saved request
  <- 302 /private (if saved request exists) or / (otherwise)

GET /private + current session cookie
  -> SecurityContext is restored for the reactive request
  -> authorization authenticated() permits
  -> controller returns "hello viewer"

GET /admin + viewer session
  -> role lacks ROLE_ADMIN
  <- 403 Forbidden
```

**Three core takeaways:** (1) the redirect to login and the post-login redirect are distinct HTTP responses; (2) saved request/session/cookie allow the journey to span multiple requests, but do not replace CSRF; (3) successful login only verifies identity, while access to each resource is still decided by authorization.
