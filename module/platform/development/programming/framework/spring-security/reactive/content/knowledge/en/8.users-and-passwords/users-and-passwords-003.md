# Loading Users from a Reactive Database with R2DBC in Spring Security WebFlux

## Learning Objectives

After this lesson, you can:

1. Explain how **R2DBC**, `ConnectionFactory`, `DatabaseClient`, and Spring Data R2DBC connect relational databases in WebFlux applications.
2. Implement `ReactiveUserDetailsService.findByUsername(String)` returning `Mono<UserDetails>` from an account and authority list in the database.
3. Understand how `UserDetailsRepositoryReactiveAuthenticationManager` verifies hashed passwords and account status, then passes the identity into the WebFlux security chain.
4. Write parameterized queries, avoid blocking and SQL injection, and distinguish `Mono.empty()`, authentication failures, and database errors.
5. Test 200/401/403, nonexistent usernames, wrong passwords, disabled accounts, and roles using H2 R2DBC + `WebTestClient`.
6. Identify what changes when moving from demo H2 to production PostgreSQL: migrations, connection pooling, secrets, indexes, transactions, and access control.

> This exercise targets Java 17+, Spring Boot 3.x, and Spring Security WebFlux/reactive. In Servlet/MVC, `UserDetailsService` and synchronous JDBC/JPA follow a different design; do not place those blocking calls directly onto the WebFlux event loop.

## 1. Why Load Users with R2DBC?

In Spring Security WebFlux, every HTTP request flows through `SecurityWebFilterChain` and Project Reactor publishers. When Basic Auth sends a username/password, the authenticator must read the account, password hash, and permissions, then check the credentials. If blocking JDBC/JPA runs on the Reactor Netty event loop, threads serving many requests get tied up waiting on I/O.

**R2DBC (Reactive Relational Database Connectivity)** defines relational database access via Reactive Streams with drivers supporting reactive I/O. It does not solve password hashing, roles, transactions, or authorization on its own; those responsibilities still belong to Spring Security and application design.

| Component | Role | Typical Output |
| --- | --- | --- |
| `ConnectionFactory` | Manages how R2DBC connections are created instead of JDBC `DataSource` | Connection infrastructure |
| `DatabaseClient` | Executes SQL, binds parameters, maps result rows | `Mono<AccountRow>`, `Flux<GrantedAuthority>` |
| `ReactiveCrudRepository` | Spring Data R2DBC high-level repository API | `Mono<Account>` |
| `ReactiveUserDetailsService` | Contract for looking up accounts by username for Spring Security | `Mono<UserDetails>` |
| `UserDetailsRepositoryReactiveAuthenticationManager` | Uses the service to load users, check hashes and status | `Mono<Authentication>` |
| `SecurityWebFilterChain` | HTTP authentication/authorization rules | Permits or rejects requests |

HTTP Basic authentication flow diagram:

```text
GET /admin/report + HTTP Basic credentials
            |
            v
SecurityWebFilterChain
            |
            v
ReactiveAuthenticationManager
            |
            +--> ReactiveUserDetailsService.findByUsername(username)
            |                |
            |                v
            |          DatabaseClient + R2DBC
            |                |
            |                +--> SELECT account       -> Mono<AccountRow>
            |                +--> SELECT authorities   -> Flux<GrantedAuthority>
            |                +--> map/flatMap          -> Mono<UserDetails>
            |
            +--> PasswordEncoder.matches(rawPassword, storedHash)
            +--> Check enabled / account status
            |
            v
Authentication + Reactor SecurityContext
            |
            v
Authorization: /admin/** requires ROLE_ADMIN
            |
            +--> Authorized: controller
            +--> Unauthenticated: 401 (HTTP Basic)
            +--> Authenticated, missing role: 403
```

This is a conceptual model. Requests without credentials, `permitAll()` endpoints, or other token mechanisms do not necessarily go through all of these account query steps.

## 2. Designing Account and Authority Tables

The example uses two tables to separate users from permissions:

**`src/main/resources/schema.sql`** — for H2 in this lab:

```sql
CREATE TABLE IF NOT EXISTS app_users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(120) NOT NULL UNIQUE,
    password_hash VARCHAR(150) NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE IF NOT EXISTS app_user_authorities (
    user_id BIGINT NOT NULL,
    authority VARCHAR(100) NOT NULL,
    PRIMARY KEY (user_id, authority),
    CONSTRAINT fk_user_authority
        FOREIGN KEY (user_id) REFERENCES app_users(id)
        ON DELETE CASCADE
);
```

**Schema significance:**

- `username UNIQUE` ensures at most one account is matched. Real systems must align Unicode normalization and case sensitivity across registration logic, queries, and database collation.
- `password_hash` holds the string produced by `PasswordEncoder`, such as `{bcrypt}$2a$...`. The ellipsis only illustrates the format; it is not a usable valid hash. Never store plaintext or single-round SHA-256 and treat it as secure password hashing.
- `enabled=false` causes the account to be rejected at login when the manager checks status.
- `authority` stores the full name such as `ROLE_ADMIN` or `ROLE_READER`. `hasRole("ADMIN")` requires the `ROLE_ADMIN` authority; do not accidentally store `ADMIN` without prefix mapping.
- The composite primary key prevents duplicate authorities; the foreign key prevents orphaned permissions. Only privileged administrative workflows should modify the role assignment table.
- One user can have multiple authorities, so account lookup uses `Mono` while authority lookup uses `Flux`.

This is a demo schema. Production PostgreSQL requires versioned migrations, least-privilege DB permissions, and audit controls; never enable automatic demo table creation against databases holding real data.

```yaml
spring:
  application:
    name: r2dbc-security-demo
  r2dbc:
    url: "r2dbc:h2:mem:///securitydb?options=DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE"
```

## 4. Querying Accounts and Roles with DatabaseClient

Spring Boot auto-configures `ConnectionFactory` and `DatabaseClient` when dependencies and URLs match. We write the SQL repository directly to observe the `Mono`/`Flux` mechanics. Another project may use `ReactiveCrudRepository` if entity mapping fits.

**`src/main/java/example/r2dbcauth/SqlAccountRepository.java`**:

```java
package example.r2dbcauth;

import org.springframework.r2dbc.core.DatabaseClient;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.stereotype.Repository;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@Repository
public class SqlAccountRepository {

    private final DatabaseClient database;

    public SqlAccountRepository(DatabaseClient database) {
        this.database = database;
    }

    public Mono<AccountRow> findByUsername(String username) {
        return database.sql("""
                    SELECT id, username, password_hash, enabled
                      FROM app_users
                     WHERE username = :username
                    """)
                .bind("username", username)
                .map((row, metadata) -> new AccountRow(
                        row.get("id", Long.class),
                        row.get("username", String.class),
                        row.get("password_hash", String.class),
                        Boolean.TRUE.equals(row.get("enabled", Boolean.class))
                ))
                .one();
    }

    public Flux<GrantedAuthority> findAuthorities(long userId) {
        return database.sql("""
                    SELECT authority
                      FROM app_user_authorities
                     WHERE user_id = :userId
                     ORDER BY authority
                    """)
                .bind("userId", userId)
                .map((row, metadata) ->
                        (GrantedAuthority) new SimpleGrantedAuthority(
                                row.get("authority", String.class)))
                .all();
    }

    public record AccountRow(
            long id,
            String username,
            String passwordHash,
            boolean enabled
    ) {}
}
```

**Analysis:**

1. `sql(...).bind("username", username)` uses **parameter binding**; never concatenate `username` into the SQL string. This prevents SQL injection through input values.
2. `.map((row, metadata) -> ...)` converts each row into a Java record. Key columns carry `NOT NULL` constraints in the schema.
3. `.one()` represents at most one account. If no row is found, it completes as `Mono.empty()`; if SQL fails, it emits `onError`.
4. `.all()` returns `Flux<GrantedAuthority>`, which may be empty or contain multiple permissions.
5. There is no `block()` or `subscribe()`. Operations execute later within a framework-managed subscription.

For clarity in learning, the repository uses two SQL queries instead of a JOIN; under heavy load, measure latency and optimize into a JOIN if needed, preserving the zero-role case and avoiding duplicate authorities. Between the two queries, the role table could change; if a consistent snapshot is required, consider reactive transactions or an appropriate versioning mechanism.

## 5. Implementing ReactiveUserDetailsService from the Database

Spring Security WebFlux uses the interface:

```java
Mono<UserDetails> findByUsername(String username);
```

**`src/main/java/example/r2dbcauth/DatabaseReactiveUserDetailsService.java`**:

```java
package example.r2dbcauth;

import org.springframework.security.core.userdetails.ReactiveUserDetailsService;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class DatabaseReactiveUserDetailsService
        implements ReactiveUserDetailsService {

    private final SqlAccountRepository repository;

    public DatabaseReactiveUserDetailsService(
            SqlAccountRepository repository) {
        this.repository = repository;
    }

    @Override
    public Mono<UserDetails> findByUsername(String username) {
        return repository.findByUsername(username)
                .flatMap(account ->
                        repository.findAuthorities(account.id())
                                .collectList()
                                .map(authorities -> User
                                        .withUsername(account.username())
                                        .password(account.passwordHash())
                                        .disabled(!account.enabled())
                                        .authorities(authorities)
                                        .build()));
    }
}
```

Because `findByUsername` may not find an account, we keep `Mono.empty()`: `flatMap` does not run, and the manager treats authentication as failed per contract. If an account is found, `flatMap` chains the authority query using `account.id()`. `collectList()` turns `Flux<GrantedAuthority>` into a list of authorities; the number of roles per account is usually bounded, making this aggregation appropriate.

`User.withUsername(...).password(...).disabled(...).authorities(...).build()` constructs `UserDetails` with the hash and status. Do not compare raw passwords here. Any R2DBC errors from the repository remain publisher errors; **do not indiscriminately use `onErrorResume(e -> Mono.empty())`**, because that turns database outages into "user not found".

An account with zero roles can still authenticate if its password and status are valid; it will fail `hasRole("ADMIN")`. If policy requires every account to have at least one role, enforce that during business logic/provisioning rather than auto-granting ADMIN to "patch" data.

### Distinguishing Three Signals from the Service

| Case | Publisher | Meaning |
| --- | --- | --- |
| Account exists | `Mono.just(UserDetails)` after queries complete | Manager has data to verify credentials |
| Account does not exist | `Mono.empty()` | No matching user |
| SQL timeout/connection error | `Mono.error(...)` | Data infrastructure failed; needs different handling/monitoring |

`ReactiveUserDetailsService` is a **data loader**, not an authentication manager. Even if SQL returns a user, the raw password may be wrong, the account may be disabled, or roles may be insufficient.

## 6. Wiring into SecurityWebFilterChain and Controller

**`src/main/java/example/r2dbcauth/SecurityConfiguration.java`**:

```java
package example.r2dbcauth;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.authentication.ReactiveAuthenticationManager;
import org.springframework.security.authentication.UserDetailsRepositoryReactiveAuthenticationManager;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.core.userdetails.ReactiveUserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration(proxyBeanMethods = false)
@EnableWebFluxSecurity
public class SecurityConfiguration {

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    ReactiveAuthenticationManager authenticationManager(
            ReactiveUserDetailsService userService,
            PasswordEncoder encoder) {
        var manager =
                new UserDetailsRepositoryReactiveAuthenticationManager(
                        userService);
        manager.setPasswordEncoder(encoder);
        return manager;
    }

    @Bean
    SecurityWebFilterChain securityWebFilterChain(
            ServerHttpSecurity http,
            ReactiveAuthenticationManager manager) {
        return http
                .authorizeExchange(exchanges -> exchanges
                        .pathMatchers(HttpMethod.GET, "/public/ping")
                            .permitAll()
                        .pathMatchers("/admin/**")
                            .hasRole("ADMIN")
                        .anyExchange().authenticated())
                .httpBasic(basic ->
                        basic.authenticationManager(manager))
                .formLogin(form -> form.disable())
                .build();
    }
}
```

**`src/main/java/example/r2dbcauth/DemoController.java`**:

```java
package example.r2dbcauth;

import org.springframework.security.core.context.ReactiveSecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Mono;

@RestController
public class DemoController {

    @GetMapping("/public/ping")
    public Mono<String> ping() {
        return Mono.just("pong");
    }

    @GetMapping("/me")
    public Mono<String> me() {
        return ReactiveSecurityContextHolder.getContext()
                .map(ctx ->
                        "hello " + ctx.getAuthentication().getName());
    }

    @GetMapping("/admin/report")
    public Mono<String> report() {
        return Mono.just("admin report");
    }
}
```

**Why configure it this way?**

- `UserDetailsRepositoryReactiveAuthenticationManager` uses the `ReactiveUserDetailsService` we created to look up users. It accepts `PasswordEncoder` to check the raw password against the stored hash; password encoding does not live in the controller.
- `PasswordEncoderFactories.createDelegatingPasswordEncoder()` creates an encoder with an algorithm id. Hashes generated in the test example typically start with `{bcrypt}`.
- HTTP Basic is explicitly enabled, and form login is disabled because the demo has no web login UI. **CSRF is not disabled by default**; the controller only uses GET. Real APIs with POST/PUT/DELETE must evaluate CSRF based on the credential mechanism.
- `/public/ping` allows anonymous GET; `/admin/**` requires `ROLE_ADMIN` via `hasRole("ADMIN")`; other requests require authentication.
- `ReactiveSecurityContextHolder` reads the context per reactive subscription, without assuming authentication data sits in a Servlet thread-local.
- HTTP Basic carries raw username/password on every request as Base64; production must use HTTPS, brute-force controls, and proper auditing. Base64 **does not provide cryptographic security**.

### 401 and 403 Represent Different Failures

| Request or Data | Typical Result in Demo | Cause |
| --- | --- | --- |
| Anonymous to `/me` | 401 | Unauthenticated |
| Nonexistent username | 401 | Lookup found no user |
| Wrong password | 401 | Encoder did not match |
| `enabled=false` even with right password | 401 | Account rejected |
| User with `ROLE_READER` calling `/admin/report` | 403 | Authenticated, lacks role |
| User with `ROLE_ADMIN` calling `/admin/report` | 200 | Sufficient permissions |
| R2DBC database error | Corresponding server/handler error | **Infrastructure error**, not treated as wrong password |

Do not leak sensitive information in client errors, such as "account exists but password is wrong", because that enables username enumeration. Internal logs should record error categories/correlation IDs, avoiding Authorization headers, passwords, or hashes.

## 7. Integration Testing with H2 R2DBC and WebTestClient

Tests generate hashes via `PasswordEncoder`, insert accounts/roles via `DatabaseClient`, and then send HTTP requests. There is no need to commit real password hashes to the repository. Use local fixtures only; never reuse test credentials in real environments.

**`src/test/java/example/r2dbcauth/R2dbcSecurityHttpTest.java`**:

```java
package example.r2dbcauth;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.reactive.AutoConfigureWebTestClient;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.r2dbc.core.DatabaseClient;
import org.springframework.security.core.userdetails.ReactiveUserDetailsService;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.test.web.reactive.server.WebTestClient;
import reactor.core.publisher.Mono;
import reactor.test.StepVerifier;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureWebTestClient
class R2dbcSecurityHttpTest {

    @Autowired DatabaseClient database;
    @Autowired PasswordEncoder encoder;
    @Autowired ReactiveUserDetailsService userService;
    @Autowired WebTestClient client;

    @BeforeEach
    void seedUsers() {
        Mono<Void> seed = database.sql("DELETE FROM app_user_authorities")
                .then()
                .then(database.sql("DELETE FROM app_users").then())
                .then(insertUser("admin", "admin-test-pass", true))
                .then(insertUser("reader", "reader-test-pass", true))
                .then(insertUser("disabled", "disabled-test-pass", false))
                .then(insertAuthority("admin", "ROLE_ADMIN"))
                .then(insertAuthority("reader", "ROLE_READER"));

        StepVerifier.create(seed).verifyComplete();
    }

    private Mono<Void> insertUser(
            String username, String password, boolean enabled) {
        return database.sql("""
                    INSERT INTO app_users
                        (username, password_hash, enabled)
                    VALUES (:username, :hash, :enabled)
                    """)
                .bind("username", username)
                .bind("hash", encoder.encode(password))
                .bind("enabled", enabled)
                .fetch()
                .rowsUpdated()
                .then();
    }

    private Mono<Void> insertAuthority(String username, String authority) {
        return database.sql("""
                    INSERT INTO app_user_authorities (user_id, authority)
                    SELECT id, :authority
                      FROM app_users
                     WHERE username = :username
                    """)
                .bind("authority", authority)
                .bind("username", username)
                .fetch()
                .rowsUpdated()
                .then();
    }

    @Test
    void unknownUsernameProducesEmptyMono() {
        StepVerifier.create(userService.findByUsername("nobody"))
                .verifyComplete();
    }

    @Test
    void publicEndpointIsAccessible() {
        client.get().uri("/public/ping").exchange()
                .expectStatus().isOk()
                .expectBody(String.class).isEqualTo("pong");
    }

    @Test
    void anonymousCannotAccessProtectedEndpoint() {
        client.get().uri("/me").exchange()
                .expectStatus().isUnauthorized();
    }

    @Test
    void wrongPasswordReturnsUnauthorized() {
        client.get().uri("/me")
                .headers(h -> h.setBasicAuth("admin", "wrong"))
                .exchange()
                .expectStatus().isUnauthorized();
    }

    @Test
    void readerCanReadPrincipal() {
        client.get().uri("/me")
                .headers(h -> h.setBasicAuth("reader", "reader-test-pass"))
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class).isEqualTo("hello reader");
    }

    @Test
    void readerCannotReadAdminReport() {
        client.get().uri("/admin/report")
                .headers(h -> h.setBasicAuth("reader", "reader-test-pass"))
                .exchange()
                .expectStatus().isForbidden();
    }

    @Test
    void adminCanReadAdminReport() {
        client.get().uri("/admin/report")
                .headers(h -> h.setBasicAuth("admin", "admin-test-pass"))
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class).isEqualTo("admin report");
    }

    @Test
    void disabledAccountCannotAuthenticate() {
        client.get().uri("/me")
                .headers(h -> h.setBasicAuth("disabled", "disabled-test-pass"))
                .exchange()
                .expectStatus().isUnauthorized();
    }
}
```

## 8. From Demo H2 to Production PostgreSQL

Add the PostgreSQL R2DBC driver via Boot project dependencies:

```groovy
runtimeOnly 'org.postgresql:r2dbc-postgresql'
```

**`src/main/resources/application-prod.yml`** (placeholders, no real secrets):

```yaml
spring:
  r2dbc:
    url: "${DB_R2DBC_URL}"
    username: "${DB_USERNAME}"
    password: "${DB_PASSWORD}"
  sql:
    init:
      mode: never
```

`DB_R2DBC_URL` must have a format like `r2dbc:postgresql://db-host:5432/appdb` and be supplied from deployment/secret management. Do not use a JDBC URL to configure an R2DBC `ConnectionFactory`. Differences between H2 and PostgreSQL include DDL syntax, collation, generated key behavior, and column types; schemas must be migrated in a controlled manner.

Required steps when going to production:

1. **Migrations:** run Flyway/Liquibase or a versioned schema workflow through a managed environment; never leave `spring.sql.init.mode=always` enabled on real data.
2. **Least privilege:** the database user used to read login details should have minimal privileges. Creating users, changing passwords, and granting/revoking roles belong to separate authorized services/workflows.
3. **Indexes:** `username UNIQUE` provides an index for account lookup; consider adding an index on `user_id` in authorities based on query plans and load.
4. **Pooling and timeouts:** non-blocking WebFlux can still overload a DB. Limit connection pool size, request timeouts, and concurrency, and monitor p95/p99 login latency.
5. **TLS and secrets:** configure proper TLS to the database, restrict network access, and never print password hashes/raw passwords. Manage rotation and auditing.
6. **Database errors:** SQL timeouts/connection failures must never turn into user-not-found; preserve error signals for telemetry/appropriate handlers.
7. **Consistency:** create user + roles inside one reactive transaction when atomicity is needed, using `R2dbcTransactionManager`/`TransactionalOperator` or `@Transactional` on reactive Spring-proxied methods. Never use `JpaTransactionManager` for R2DBC flows.
8. **Normalization:** verify username case sensitivity/Unicode and unique constraints on the real database; do not assume H2 and PostgreSQL share identical collations.

## 9. Common Mistakes and Security Pitfalls

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Using blocking JDBC in reactive filters/controllers | Blocks event loop, reduces throughput | Use an R2DBC driver or isolate blocking with load evaluation |
| Calling `findByUsername(...).block()` during requests | May be forbidden by Reactor on non-blocking threads | Return publishers, chain with `flatMap`/`map` |
| Calling `subscribe()` manually inside services | Detaches from request lifecycle, loses error/context handling | Let Spring Security subscribe |
| Concatenating username directly into SQL | SQL injection | Use `bind("username", username)` |
| Using `map` when the function returns `Mono` | Produces `Mono<Mono<T>>` | Use `flatMap` |
| Swallowing database errors as `Mono.empty()` | DB failures get mistaken for wrong username | Preserve infrastructure errors, classify/log/monitor safely |
| Storing raw passwords or fast SHA hashes | Easy to leak/guess passwords | Use a proper password encoder and work factor |
| Hash missing `{bcrypt}` prefix with delegating encoder | Fails to authenticate with expected algorithm | Migrate hashes explicitly; do not enable `{noop}` casually |
| DB stores `ADMIN` while policy expects `ROLE_ADMIN` | User can log in but always gets 403 | Standardize authority formats |
| Failing to map `enabled` | Disabled accounts can still log in | Configure `UserDetails.disabled(...)` and test |
| Using `SELECT *` / logging entire accounts | Widens exposure of sensitive data | SELECT only needed columns, redact logs |
| Caching UserDetails without invalidation | Stale roles/passwords/disabled state after changes | Use TTL/invalidation/revalidation per risk |
| Retrying queries infinitely on DB errors | Amplifies pool/DB incidents | Bounded retries only for appropriate transient errors |
| Exposing an endpoint granting ADMIN to seed data | Creates a privilege escalation path | Provision outside public APIs with auditing and permissions |

### Password Verification and Performance

Password encoders like BCrypt intentionally require significant CPU cost. `UserDetailsRepositoryReactiveAuthenticationManager` supports a scheduler for password verification work; measure load and tune an appropriate work factor rather than running heavy CPU hashing directly on the Reactor Netty event loop. `DelegatingPasswordEncoder` can help upgrade algorithms/hashes per policy. Wrong passwords, disabled accounts, and nonexistent usernames may all return 401 in HTTP Basic, but should be categorized properly for control logic and operations without exposing account enumeration.

### Dynamic Roles and Permissions

The `UserDetails` object is created from a data snapshot at lookup time. When a role is revoked later, previously issued authentications are not automatically invalidated across every session/token/cache mechanism. Design TTLs, invalidation, or direct permission evaluation from a trusted source per business requirements. `hasRole("ADMIN")` only checks the route's role; it does not replace owner-based query filtering for individual records.

## 10. Extension Exercises

1. Add `account_locked` to the table and map it to `UserDetails.accountNonLocked`; write a test proving a valid password on a locked account still gets 401.
2. Use `ReactiveCrudRepository` instead of `DatabaseClient` to look up `Mono<Account>`; compare SQL transparency, mapping, and query count for reading authorities.
3. Create a user with zero authorities and prove `/me` can return 200 while `/admin/report` returns 403.
4. Simulate DB unavailability: verify the repository emits an error instead of returning `Mono.empty()`; build metrics without passwords/hashes.
5. Create an account + authorities inside a reactive transaction. Deliberately insert a duplicate username and verify rollback.
6. Switch the demo to PostgreSQL R2DBC, run migrations, and measure login latency under concurrent requests.
7. Test revoking the ADMIN role after a user has logged in under HTTP Basic, sessions, and caching; identify where permissions must be refreshed.

**Key takeaway:** R2DBC loads user/permission data as publishers; `ReactiveUserDetailsService` turns them into `Mono<UserDetails>`; `ReactiveAuthenticationManager` verifies passwords and status; `SecurityWebFilterChain` checks permissions. Preserving reactiveness, SQL parameter binding, strong password hashing, and tests distinguishing 401/403 forms the foundation for correct and secure database-backed authentication.
