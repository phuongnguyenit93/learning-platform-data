# Configuring formLogin and the Default Login Page in Spring Security WebFlux

## Objectives

This lesson helps you understand:

1. `ServerHttpSecurity.formLogin(...)` enables an HTML form-based login flow for **WebFlux**, different from the Servlet `HttpSecurity.formLogin(...)` mechanism.
2. The default login page is generated by Spring Security at `GET /login`, while `POST /login` is handled by a Spring Security WebFilter for authentication.
3. How username/password, CSRF tokens, `ReactiveAuthenticationManager`, `WebSession`, and `SecurityContext` work together.
4. How to configure `SecurityWebFilterChain` using Java 17+ without writing a custom controller to handle passwords.
5. How to test the default page, redirects, valid/invalid credentials, CSRF, and authorization with `WebTestClient`.
6. How to replace the default page with a custom Thymeleaf page while preserving CSRF requirements and secure session management.

> Scope: Spring Boot 3.x, Spring Security 6.x, Java 17+, and **Spring WebFlux reactive**. `SecurityFilterChain`, `UsernamePasswordAuthenticationFilter`, and `HttpSecurity` commonly appear in Servlet/MVC documentation; the examples here use `SecurityWebFilterChain`, `ServerHttpSecurity`, and reactive WebFilters.

## 1. What Is formLogin?

Form login allows users to open an HTML page, enter a username/password, and submit via HTTP POST. Spring Security receives the credentials, verifies them, creates an `Authentication`, and manages login state and redirects. Business controllers receive the authenticated request without having to check passwords themselves.

In Spring Security WebFlux, form login consists of:

- **Login page**: HTML generated by the framework by default, or custom HTML provided by the application.
- **Authentication WebFilter**: processes form POSTs at the configured path.
- **ReactiveAuthenticationManager**: authenticates the credentials.
- **ReactiveUserDetailsService/PasswordEncoder**: loads the user and verifies the hash when using username/password authentication.
- **Security context persistence**: saves/restores authentication per the chosen session or repository.
- **Authorization**: decides whether the logged-in user is allowed to access the requested URL.
- **CSRF protection**: protects state-changing requests, including login and logout.

Do not confuse "opening the login page" with "logging in successfully". GET on the login page is typically open to anonymous users, whereas POST login creates or updates the Authentication.

| Mechanism | Client-Side Information | Suitable For | Notes |
| --- | --- | --- | --- |
| Form login | Form-encoded body with username/password and CSRF token; afterwards browser sends session cookie | Web apps with browser UI | Usually **stateful**, must handle session and CSRF |
| HTTP Basic | `Authorization: Basic ...` header on requests | API clients or simple examples | Base64 is not encryption; requires HTTPS |
| JWT resource server | Bearer token header | Token-based APIs/SPAs | Does not imply auto-generating login HTML |
| OIDC/OAuth2 login | Redirect to identity provider | SSO, centralized login | Involves state/nonce/callback and IdP policies |

You can combine multiple mechanisms, though anonymous request behavior may depend on the entry point, `Accept` header, and security chain selection. The demo below **disables HTTP Basic** so the browser uses form login exclusively.

## 2. How Does the Default Login Page Work?

When configuring:

```java
.formLogin(Customizer.withDefaults())
```

without calling `loginPage(...)`, Spring Security WebFlux generates a default login page.

| HTTP | Path | Behavior with Default Configuration |
| --- | --- | --- |
| GET | `/login` | Returns HTML containing username/password fields and the login form |
| POST | `/login` | Filter receives the form and invokes the authentication manager |
| GET | `/login?error` | Displays the login page in an error state after authentication failure |
| GET | `/logout` | May display a default logout confirmation page |
| POST | `/logout` | Processes logout when valid CSRF is present |

**Do not write `@PostMapping("/login")` to verify passwords** when using default form login; the authentication filter already handles that URL. You do not need to create `login.html` or `@GetMapping("/login")` while still using the framework-generated page.

The default form submits at least these parameters:

- `username`: the user's name, unless the credential conversion mechanism is customized.
- `password`: the password entered by the user.
- `_csrf`: a valid CSRF token for the current session/request.

The following HTML snippet only **explains the structure** and is not a working form while the CSRF value is still a placeholder:

```html
<form action="/login" method="post">
  <label for="username">Username</label>
  <input id="username" name="username" autocomplete="username">

  <label for="password">Password</label>
  <input id="password" name="password" type="password"
         autocomplete="current-password">

  <input type="hidden" name="_csrf" value="SERVER_GENERATED_TOKEN">
  <button type="submit">Log in</button>
</form>
```

The `/login` path is the **default path**, not a requirement that every application use this exact URL: calling `loginPage("/signin")` changes the behavior. The value `SERVER_GENERATED_TOKEN` must not be hardcoded into real code; it must be issued and validated by Spring Security.

### Which Filters Does a Request Pass Through?

```text
Browser: GET /private (not logged in)
             |
             v
SecurityWebFilterChain: authorization requires authenticated()
             |
             v
Authentication entry point -> HTTP redirect /login
             |
             v
Browser: GET /login -> receives form page + CSRF token
             |
             v
Browser: POST /login (username, password, _csrf)
             |
             +--> CsrfWebFilter verifies token
             |
             +--> Form login AuthenticationWebFilter
             |        |
             |        v
             |     ReactiveAuthenticationManager
             |        |
             |        +--> Verify user/password, account status
             |        |
             |        +--> Success -> Authentication
             |
             +--> SecurityContext written to repository/session
             |
             +--> Success handler -> redirect to target page
             |
             +--> If failed -> failure handler -> /login?error
```

This is a **conceptual** diagram. Any filter can terminate early, so a POST missing CSRF is usually rejected **before** checking the password. If the app enables multiple chains, a request only passes through the chain selected by matcher/order. The successful redirect target is decided by the success handler/request cache; no single fixed URL is guaranteed across all configurations.

### Why Must State Be Kept Across Sessions?

Form login usually serves browsers: if the server did not maintain state, users would have to re-send their password on every request. Spring Security WebFlux can use `WebSessionServerSecurityContextRepository` by default to store `SecurityContext`; the session cookie lets the browser associate subsequent requests with the session. WebSession in WebFlux typically uses a cookie named `SESSION` (configurable), not `JSESSIONID` by default like Servlet.

**WebSession differs from Reactor Context**:

| Concept | Scope | Role |
| --- | --- | --- |
| `WebSession` | Across multiple HTTP requests carrying the matching cookie | Stores server-side state |
| `ServerSecurityContextRepository` | Saves/restores security context per configured mechanism | Preserves Authentication across requests |
| `Reactor Context` | Within the current subscription | Propagates SecurityContext along the WebFlux pipeline |
| `PasswordEncoder` | During credential verification | Matches raw password against stored hash |

Never store raw passwords in sessions, local storage, or logs. Never build your own session using global variables or `ThreadLocal` when working reactively.

### 3.3. SecurityWebFilterChain and Demo Users

**`src/main/java/example/formlogin/SecurityConfiguration.java`**:

```java
package example.formlogin;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.MapReactiveUserDetailsService;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration(proxyBeanMethods = false)
@EnableWebFluxSecurity
public class SecurityConfiguration {

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    MapReactiveUserDetailsService users(PasswordEncoder encoder) {
        UserDetails learner = User.withUsername("learner")
                .password(encoder.encode("local-learner-pass"))
                .roles("USER")
                .build();

        UserDetails admin = User.withUsername("admin")
                .password(encoder.encode("local-admin-pass"))
                .roles("ADMIN")
                .build();

        return new MapReactiveUserDetailsService(learner, admin);
    }

    @Bean
    SecurityWebFilterChain securityWebFilterChain(ServerHttpSecurity http) {
        return http
                .authorizeExchange(exchanges -> exchanges
                        .pathMatchers("/", "/favicon.ico").permitAll()
                        .pathMatchers("/admin").hasRole("ADMIN")
                        .anyExchange().authenticated()
                )
                .formLogin(Customizer.withDefaults())
                .httpBasic(basic -> basic.disable())
                .logout(Customizer.withDefaults())
                .build();
    }
}
```

Explanation:

1. `@EnableWebFluxSecurity` together with the `SecurityWebFilterChain` bean creates a **reactive** security configuration. Do not use Servlet's `HttpSecurity`.
2. `pathMatchers("/", "/favicon.ico").permitAll()` opens the home page; `/admin` requires `ROLE_ADMIN`; all other URLs require authentication. The default login page filter can serve `GET /login` before authorization blocks it.
3. `formLogin(Customizer.withDefaults())` enables the generated login page and form authentication. Since `loginPage(...)` is not specified, no custom template is required yet.
4. `httpBasic(basic -> basic.disable())` disables only HTTP Basic so the demo stays consistent for browsers. It does not disable authorization, session, or CSRF protections.
5. `logout(Customizer.withDefaults())` enables logout handling. Do not turn logout into a state-changing GET.
6. `PasswordEncoderFactories.createDelegatingPasswordEncoder()` produces hashes with an algorithm prefix, typically `{bcrypt}`. Do not use `User.withDefaultPasswordEncoder()` for production passwords.
7. The two accounts have hardcoded sample passwords for **local practice/testing**. Real applications use a secure user/secret store, appropriate hashing, account management, and rate limiting.
8. There is no `.csrf(csrf -> csrf.disable())`: **CSRF remains enabled by default**, which is especially necessary for browser session-based login.

### 3.4. Demo Controller

**`src/main/java/example/formlogin/ExampleController.java`**:

```java
package example.formlogin;

import org.springframework.security.core.context.ReactiveSecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Mono;

@RestController
public class ExampleController {

    @GetMapping("/")
    public Mono<String> home() {
        return Mono.just("Home is public");
    }

    @GetMapping("/private")
    public Mono<String> privatePage() {
        return ReactiveSecurityContextHolder.getContext()
                .map(ctx -> "Hello " + ctx.getAuthentication().getName());
    }

    @GetMapping("/admin")
    public Mono<String> adminPage() {
        return Mono.just("Admin only");
    }
}
```

The controller has neither `@GetMapping("/login")` nor `@PostMapping("/login")`, because WebFlux security filters manage the default page and form. `ReactiveSecurityContextHolder` retrieves the principal from the request's Reactor Context; do not read `SecurityContextHolder.getContext()` synchronously as in Servlet.

## 4. HTTP Statuses to Distinguish

| Scenario | Typical Outcome in Demo | Key Takeaway |
| --- | --- | --- |
| GET `/login` | 200 and HTML | Page generated by Spring Security |
| GET `/private` unauthenticated | 3xx to `/login` | Entry point requests form login |
| POST `/login` without CSRF | Typically 403 | CSRF filter blocks before checking password |
| POST `/login` with CSRF, wrong password | 3xx to `/login?error` | Authentication failure handler |
| POST `/login` with CSRF, valid password | 3xx to success handler target | Authenticated and session/context established |
| GET `/admin` as logged-in learner | Typically 403 | Authenticated, lacks ADMIN role |
| GET `/admin` as logged-in admin | 200 and `Admin only` | Has `ROLE_ADMIN` |
| Valid POST `/logout` | Redirect/logout completed | Session/security context handled per configuration |

**Form login uses redirects to ask the browser to log in; do not expect HTTP 401 for every anonymous browser request** as when using HTTP Basic alone. The HTTP status/Location can vary with custom entry points, handlers, request caches, or matchers; verify the application's actual behavior.

### "Logged In Successfully" Differs from "Authorized to Access"

Authentication answers **who the user is**. Authorization checks what the user is allowed to do. `roles("USER")` creates authority `ROLE_USER`; `roles("ADMIN")` creates `ROLE_ADMIN`. Spring Security `hasRole("ADMIN")` looks for authority `ROLE_ADMIN`. A USER user can log in successfully and still receive 403 on `/admin`.

### Saving and Restoring Sessions

In default form login, Spring Security WebFlux typically uses `WebSessionServerSecurityContextRepository` to store Authentication. The browser sends the session cookie on subsequent requests; Spring Security loads the context into the processing pipeline when needed. In multi-instance deployments, if each instance keeps WebSession in local memory without sharing, a later request may hit another instance and be treated as anonymous. You must design a shared session store (such as Spring Session with an appropriate backend) or managed routing; do not assume WebFlux has no session just because it is reactive.

## 5. CSRF: An Essential Part of Using Forms

CSRF protects state-changing actions when browsers automatically attach the user's cookies. If a malicious website tricks a victim's browser into sending a POST to your site, login cookies may still be sent; a CSRF token proves the request uses data issued by the server for that session.

Spring Security WebFlux **enables CSRF by default**, using `CsrfWebFilter`. When using WebSession, the expected token is typically held by `WebSessionServerCsrfTokenRepository`. Since Spring Security 6.x, `XorServerCsrfTokenRequestAttributeHandler` may mask the output token to mitigate BREACH risks; do not attempt custom token matching when the framework already provides a handler.

Standard steps:

1. GET `/login` to receive the form and associated cookie/session.
2. Spring Security issues a CSRF token for the form.
3. Browser POSTs `username`, `password`, and `_csrf` with the matching cookie.
4. The CSRF filter validates the token before the authentication filter processes credentials.
5. If the token is invalid/missing, the response can be 403 even when the password is right.
6. Logout via POST also requires a token. Do not turn `GET /logout` into an automatic logout action without proper design and risk assessment.

**Common mistake:** using curl to POST username/password without first GETting the page and keeping the cookie/token, then concluding the password is wrong because the server returned 403. That is a CSRF error, unlike wrong-password authentication (which usually redirects to `/login?error` when CSRF is valid).

For a frontend SPA using cookies and a cross-origin API, properly align CORS, SameSite cookies, and the CSRF repository. CORS restricts cross-origin JavaScript from reading responses; **it does not replace CSRF**. Do not disable CSRF globally just to make test requests pass.

## 6. Testing with WebTestClient and spring-security-test

Spring Security Test provides `springSecurity()` to integrate security filters into `WebTestClient`, along with `csrf()` to send valid tokens in tests. The example below verifies the distinction between **CSRF**, **authentication**, and **authorization**, without pretending that a mock user proves the entire login flow.

**`src/test/java/example/formlogin/FormLoginWebTest.java`**:

```java
package example.formlogin;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.ApplicationContext;
import org.springframework.http.MediaType;
import org.springframework.test.web.reactive.server.WebTestClient;
import org.springframework.web.reactive.function.BodyInserters;

import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.springframework.security.test.web.reactive.server.SecurityMockServerConfigurers.csrf;
import static org.springframework.security.test.web.reactive.server.SecurityMockServerConfigurers.mockUser;
import static org.springframework.security.test.web.reactive.server.SecurityMockServerConfigurers.springSecurity;

@SpringBootTest
class FormLoginWebTest {

    @Autowired
    ApplicationContext context;

    private WebTestClient client;

    @BeforeEach
    void setUp() {
        client = WebTestClient.bindToApplicationContext(context)
                .apply(springSecurity())
                .configureClient()
                .build();
    }

    @Test
    void defaultLoginPageIsAvailable() {
        client.get().uri("/login")
                .accept(MediaType.TEXT_HTML)
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class)
                .value(html -> assertTrue(html.contains("username")));
    }

    @Test
    void protectedPageRedirectsToLogin() {
        client.get().uri("/private")
                .accept(MediaType.TEXT_HTML)
                .exchange()
                .expectStatus().is3xxRedirection()
                .expectHeader().valueMatches("Location", ".*login.*");
    }

    @Test
    void loginWithoutCsrfIsForbidden() {
        client.post().uri("/login")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .body(BodyInserters.fromFormData("username", "learner")
                        .with("password", "local-learner-pass"))
                .exchange()
                .expectStatus().isForbidden();
    }

    @Test
    void wrongPasswordRedirectsToErrorPage() {
        client.mutateWith(csrf())
                .post().uri("/login")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .body(BodyInserters.fromFormData("username", "learner")
                        .with("password", "wrong-password"))
                .exchange()
                .expectStatus().is3xxRedirection()
                .expectHeader().valueMatches(
                        "Location", ".*login\\?error.*");
    }

    @Test
    void correctPasswordProducesSuccessRedirect() {
        client.mutateWith(csrf())
                .post().uri("/login")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .body(BodyInserters.fromFormData("username", "learner")
                        .with("password", "local-learner-pass"))
                .exchange()
                .expectStatus().is3xxRedirection();
    }

    @Test
    void authenticatedUserWithoutAdminRoleIsForbidden() {
        client.mutateWith(mockUser("learner").roles("USER"))
                .get().uri("/admin")
                .exchange()
                .expectStatus().isForbidden();
    }
}
```

Run command:

```bash
./gradlew test --tests example.formlogin.FormLoginWebTest
```

Windows:

```powershell
.\gradlew.bat test --tests example.formlogin.FormLoginWebTest
```

**Expected:** six PASSing tests once the project has the files and dependencies properly placed. This is the expected outcome from the sample code, **not a log of an executed test run**.

Limitations to distinguish:

- `bindToApplicationContext(context)` sets up a mock server attached to the Spring ApplicationContext and security filters; it does not necessarily open a real network port.
- `mutateWith(csrf())` supplies a valid test token; the wrong-password test therefore evaluates **authentication**, without mistaking it for a CSRF failure.
- `mockUser(...)` simulates authentication to test **authorization**; it does not prove a user logged in via the form.
- The success test only verifies the redirect after POST; it does not prove the browser retains the session cookie across multiple requests.
- To test real end-to-end sessions, execute POST login with a real token/cookie, capture `Set-Cookie`, and send that cookie when GETting `/private`. Use a browser/HTTP client with a cookie jar or additional integration tests.

## 7. Replacing the Default Login Page with Thymeleaf

In real products, you may want a custom UI: logo, password recovery link, keyboard support, accessibility, and localized error messages. **Calling `loginPage("/signin")` only configures the path; it does not generate your HTML.**

Per `ServerHttpSecurity.FormLoginSpec.loginPage(String)` in Spring Security WebFlux 6.x:

- When a custom page is configured, the default login/logout pages are no longer auto-generated as before.
- The application must serve GET for that page, e.g., `GET /signin`.
- When authentication fails, the page with `?error` must be rendered, e.g., `GET /signin?error`.
- By default, form authentication POSTs to the new URL itself, here `POST /signin`.

### 7.1. Additional Dependency

Add to dependencies:

```groovy
implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
```

### 7.2. Replacing the SecurityWebFilterChain Bean

**Replace** the security chain method in section 3 with the version below. Keep the main class and the user/password encoder beans. Do not create a second chain matching all requests without an explicit matcher/order:

```java
@Bean
SecurityWebFilterChain securityWebFilterChain(ServerHttpSecurity http) {
    return http
            .authorizeExchange(exchanges -> exchanges
                    .pathMatchers("/", "/signin", "/css/**").permitAll()
                    .pathMatchers("/admin").hasRole("ADMIN")
                    .anyExchange().authenticated()
            )
            .formLogin(form -> form.loginPage("/signin"))
            .httpBasic(basic -> basic.disable())
            .logout(Customizer.withDefaults())
            .build();
}
```

Even though GET on the login page is public, the Authorization rules for `/private` and `/admin` continue working as before. If the template uses local CSS/images/scripts, ensure the required static resources are accessible anonymously without accidentally exposing APIs.

### 7.3. Custom Page and CSRF Token

Use `@Controller` (not `@RestController`) to return a Thymeleaf view. The CSRF filter can expose `Mono<CsrfToken>` via `ServerWebExchange`; let Spring WebFlux subscribe and supply the token value to the template.

**`src/main/java/example/formlogin/SignInPageController.java`**:

```java
package example.formlogin;

import org.springframework.security.web.server.csrf.CsrfToken;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.reactive.result.view.Rendering;
import reactor.core.publisher.Mono;

@Controller
public class SignInPageController {

    @GetMapping("/signin")
    public Mono<Rendering> signin(ServerWebExchange exchange) {
        Mono<CsrfToken> csrf =
                exchange.getAttribute(CsrfToken.class.getName());

        return csrf.map(token -> Rendering.view("signin")
                .modelAttribute("_csrf", token)
                .modelAttribute("hasError",
                        exchange.getRequest().getQueryParams()
                                .containsKey("error"))
                .build());
    }
}
```

With CSRF enabled in this chain, the attribute is expected to exist. If you customize the CSRF repository/request handler, verify how the token is exposed. Never replace it with a static token string or call `block()` inside the controller.

**`src/main/resources/templates/signin.html`**:

```html
<!doctype html>
<html lang="en" xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <title>Log in</title>
</head>
<body>
<main>
    <h1>Log in</h1>
    <p th:if="${hasError}">
        Login failed. Please check your credentials.
    </p>

    <form method="post" th:action="@{/signin}">
        <label for="username">Username</label>
        <input id="username" name="username" type="text"
               autocomplete="username" required>

        <label for="password">Password</label>
        <input id="password" name="password" type="password"
               autocomplete="current-password" required>

        <input type="hidden"
               th:name="${_csrf.parameterName}"
               th:value="${_csrf.token}">

        <button type="submit">Log in</button>
    </form>
</main>
</body>
</html>
```

Spring/Thymeleaf also integrates `CsrfRequestDataValueProcessor` to inject the token into unsafe-method forms when using `th:action`. If your template engine already auto-generates the hidden CSRF input, **do not try to add another duplicate input with the same name**: keep one clean token injection path and inspect the actual rendered HTML. The code above demonstrates exposing the token via the model; when using auto-insertion, you can omit the manual hidden input. Never send CSRF tokens in URLs without compelling reason and leakage risk evaluation.

### 7.4. Custom vs. Default Flow

| Item | Default | Custom `/signin` |
| --- | --- | --- |
| HTML page | Filter auto-generates GET `/login` | Application must render GET `/signin` |
| Submit | POST `/login` | POST `/signin` per `loginPage("/signin")` |
| Authentication error | `/login?error` | `/signin?error` must be handled by the view |
| CSRF | Default form includes it built-in | Controller/template must integrate token properly |
| Password mechanism | Authentication manager | Still the manager; controller does not compare passwords |
| Default logout page | Can be generated by framework | With custom login, proactively design logout UI |
| URL protection | `authorizeExchange` | Still `authorizeExchange` |
| Post-login redirect | Success handler | Success handler can be customized |

If you need GET `/signin` while POSTing to a different URL, configure `requiresAuthenticationMatcher(...)` and the handlers properly, updating the `form action` at the same time. Do not change only the HTML `action` and expect the filter to receive requests at the new path.

### 7.5. Navigating on Login Success/Failure

`ServerHttpSecurity.FormLoginSpec` allows attaching `authenticationSuccessHandler(...)` and `authenticationFailureHandler(...)`; exact configuration details depend on the version. Example illustrating a success handler redirecting to a fixed page:

```java
.formLogin(form -> form
        .authenticationSuccessHandler(
                new RedirectServerAuthenticationSuccessHandler("/dashboard"))
)
```

When using the snippet above, import `RedirectServerAuthenticationSuccessHandler` from `org.springframework.security.web.server.authentication` and create the `/dashboard` endpoint. This is a **configuration snippet**, not a standalone Java class. If the app has a request cache/saved request, a custom success handler may alter how users return to the URL they originally opened. Never accept arbitrary redirect URLs from request parameters without an allowlist/checks to prevent open redirects.

## 8. Common Errors and Root-Cause Analysis

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| GET `/login` returns 404 | Form login disabled, `loginPage` changed, or another chain selected | Inspect `SecurityWebFilterChain` beans and active login URL |
| GET `/private` does not redirect to login | HTTP Basic/custom entry point, Accept header, or different matcher | Check HTTP Basic/form login and request headers |
| POST login returns 403 despite right password | Missing/wrong CSRF, token and session cookie mismatch | Open login page to get real token, keep cookie; do not disable CSRF |
| Wrong password redirects to `?error` | Form-login failure handler working normally | Verify user source and encoder; do not log raw password |
| Login succeeds then another GET is still anonymous | Browser dropped cookie, unshared session store, wrong SameSite/HTTPS/proxy | Check session cookie, redirects, proxy, and persistence |
| User can log in but cannot enter `/admin` | Missing `ROLE_ADMIN` | Inspect `hasRole` rules and authorities |
| Custom login redirect loop | Login page route also requires authenticated | Permit `/signin` and required resources |
| Custom POST receives 404 | Form action differs from `loginPage`/matcher | Align POST URI with Security form authentication |
| Template lacks CSRF input | CSRF Mono not added to model/view | Inspect rendered HTML and use Thymeleaf CSRF integration |
| App has two chains with overlapping matchers | Higher-priority chain intercepts request | Define `@Order` and `securityMatcher(...)` clearly |
| Passwords/secrets appear in HAR/traces | Overly verbose logging | Redact; never log passwords/tokens/session cookies |
| Using Servlet `SecurityContextHolder` | Does not reflect Reactor Context on thread switches | Use `ReactiveSecurityContextHolder` |
| Tests use `mockUser` and conclude login works | Only tests authorization, skips password/CSRF/redirect | Add form POST tests with `csrf()` and password |
| Using `.csrf(csrf -> csrf.disable())` to fix login | Can open vulnerabilities with browser cookies | Keep CSRF, fix token/session properly |

### Safe Practices

- Transmit credentials only over **HTTPS**; apply `Secure`, `HttpOnly`, `SameSite` to cookies per client model, and verify forwarded header handling from trusted proxies.
- Passwords must be stored using a dedicated hashing function with a work factor, such as BCrypt/Argon2 per policy; never store plaintext, never use fast single hashes or `{noop}` in production.
- Configure session timeouts, limit concurrent sessions when needed, and invalidate sessions on logout and after critical account changes.
- Rate-limit login attempts, monitor security failures, and avoid revealing whether an account exists through error messages.
- For multi-instance systems, design a shared WebSession store or appropriate session affinity.
- Test successful login, failed login, CSRF, missing roles, logout, and session expiration. Real browser tests complement mock WebTestClient tests.

## 9. Reinforcement Exercises

1. Run the app and observe how GET `/private` transitions to GET `/login`; record status and `Location` in DevTools.
2. Compare POST `/login` without CSRF against POST with CSRF but a wrong password. Explain why one returns 403 while the other redirects to `/login?error`.
3. Add a `/reports` page requiring `ROLE_ADMIN` and test with learner/admin. Distinguish successful authentication from successful authorization.
4. Use `loginPage("/signin")`, add the Thymeleaf controller, and verify both `GET /signin?error` and `POST /signin` work.
5. Create a success handler redirecting to `/dashboard`, then compare with saved-request behavior when opening a protected URL before logging in.
6. Write an end-to-end test preserving the same session cookie across POST login and GET `/private`, then log out and prove the next request requires login.
7. Replace `MapReactiveUserDetailsService` with a service reading users from a reactive database; prove changing the user source does not require writing a custom POST controller.
8. Test running behind a reverse proxy with TLS and SameSite cookies; verify no redirect loops, no password leaks, and no lost CSRF tokens.

**Remember:** In WebFlux, `formLogin(Customizer.withDefaults())` creates the default login form, Spring Security processes POST credentials via filters, and protects them with CSRF. Customizing the UI only changes presentation, not responsibility for authentication/passwords/sessions/authorization. Maintain a consistent reactive flow with security tests and never hardcode sensitive data.
