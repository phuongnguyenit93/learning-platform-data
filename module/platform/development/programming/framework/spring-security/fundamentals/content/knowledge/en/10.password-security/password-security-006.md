# Do Not Compare Two Encode Outputs to Verify the Same Password

> **Parent topic:** Passwords · **Context:** Spring Security for Servlet/Spring MVC, Java 17+, Spring Boot 3.5.x, and Spring Security 6.5.x. This lesson clarifies why `passwordEncoder.encode(raw).equals(storedHash)` is the wrong verification approach, how BCrypt's random salt works, the proper use of `PasswordEncoder.matches(rawPassword, encodedPassword)`, and how to store and load passwords in real applications. Java examples include a console program, a complete Spring Boot application, and JUnit/MockMvc tests. Reported results are expectations based on the source code; run Gradle in the project to verify in practice.

## 1. The Problem in One Minute

Suppose Alice registers with the password `Example!123`. The backend stores a hash:

~~~text
raw password  --[PasswordEncoder.encode]-->  storedHash
"Example!123"                               "$2a$10$..." 
~~~

A day later Alice logs in with the **same password**. Someone writes:

~~~java
// WRONG: do not verify a password by comparing two encode results.
String newlyEncoded = passwordEncoder.encode(passwordFromLogin);
boolean loginAllowed = newlyEncoded.equals(hashFromDatabase);
~~~

With `BCryptPasswordEncoder`, this code **usually returns false even when the password is completely right**, because the two `encode` calls use different random salts.

The right way:

~~~java
// RIGHT: first argument is the raw password the user just entered;
// second argument is the encoded password/hash ALREADY STORED in the database.
boolean loginAllowed = passwordEncoder.matches(
    passwordFromLogin,
    hashFromDatabase
);
~~~

**Rules to memorize:**

- **Registration or password change:** call `encode(rawPassword)` **once to create a new hash**, then store the hash.
- **Login:** load the **stored hash**, and call `matches(rawPasswordFromLogin, storedHash)`.
- **Never re-encode and compare two hash strings**.
- **Never decrypt a hash** to recover the original password. Standard password hashes are designed to be one-way.

This lesson does not say `String.equals` is always wrong in Java. `equals` is perfectly fine for comparing ordinary strings; what is wrong here is **applying it to compare two independent hashes** from a randomly salted password hashing algorithm.

## 2. Distinguishing Raw Password, Encoded Password, Salt, and Hash

| Term | Meaning | Illustrative Example | Should It Be Stored? |
| --- | --- | --- | --- |
| **Raw password** | The password entered by the user | `Example!123` | **Never store plaintext**; exists briefly during authentication flow |
| **Salt** | Random data varying per hash/account | Random bytes generated by the encoder | Embedded in the hash string or stored alongside; does not need secrecy like a password |
| **Password hash / encoded password** | Output of a password storage algorithm with salt and work factor | `$2a$10$...` | **Stored** in the password column |
| **Work factor / cost** | Computational cost level to slow password guessing | BCrypt cost `10`, `12`... | Typically included in the hash format |
| **Pepper** | Shared secret, if security policy adds one | System-managed secret | Never stored alongside the database password hash |
| **PasswordEncoder** | Spring Security API for encode/matches/upgrade | `BCryptPasswordEncoder`, `DelegatingPasswordEncoder` | Configures the proper algorithm; not stored as an object in the DB |

A **salt is not a secret password**. Even if an attacker knows the salt, they must still guess passwords through the costly password hashing algorithm. Salt prevents the same password across accounts from producing identical hashes and degrades shared precomputed tables.

**A pepper differs from a salt**: a pepper is a private secret that, if used, must stay outside the database in a secret manager/HSM by design. This lesson uses standard BCrypt without inventing an ad-hoc pepper or custom password encryption.

### 2.1. Why Does BCrypt Usually Produce Two Different Strings?

With BCrypt:

~~~text
Registration:
  raw = "Example!123"
  salt = S1 (random)
  encoded1 = bcrypt(raw, S1, cost)

Second encode call:
  raw = "Example!123"
  salt = S2 (random)
  encoded2 = bcrypt(raw, S2, cost)

In practice: S1 != S2 is nearly certain
=> encoded1 != encoded2 is nearly certain.
~~~

A BCrypt hash typically encodes metadata such as algorithm version, cost, salt, and verification digest into one string. Example **shape**:

~~~text
$2a$10$.....................................................
|  |  |
|  |  +-- cost (work factor per BCrypt convention)
|  +----- BCrypt version variant
+-------- format identifier
~~~

The sample line above **is not a valid BCrypt hash to copy into a database**; it merely illustrates the parts. A BCrypt string without a `{bcrypt}` prefix is typically **60 characters** long, while `DelegatingPasswordEncoder` prepends `{bcrypt}`. Never slice the string at fixed offsets yourself to verify passwords; use `PasswordEncoder`.

Two encoded strings differing **does not prove two raw passwords differ**. Conversely, two encoded strings matching is not the definition of a login mechanism either. A random salt collision has a minuscule probability rather than being a mathematically forbidden impossibility: never write tests asserting “two encodes must strictly always differ.”

### 2.2. Purpose of Cost

BCrypt is a tunable-cost password hashing algorithm. Higher cost makes testing many candidate passwords more resource-intensive, while also consuming more server CPU per login. Choose cost via benchmarks on your infrastructure, login load, attack-resistance targets, and active security guidance.

**Do not generate `new SecureRandom()` yourself on every login to hash with a new salt for string comparison.** `BCryptPasswordEncoder.matches(...)` handles the salt stored inside the encoded hash. Also never lower cost or switch to a fast hash just because tests run slowly.

## 3. `PasswordEncoder` Defines the Exact Contract

Core contract of `org.springframework.security.crypto.password.PasswordEncoder`:

~~~java
// Simplified interface signature for explanation, not a standalone Java file.
String encode(CharSequence rawPassword);
boolean matches(CharSequence rawPassword, String encodedPassword);
boolean upgradeEncoding(String encodedPassword);
~~~

In Spring Security:

- `encode(raw)` creates an encoded password under the current encoder for storage.
- `matches(raw, encoded)` checks whether the **raw password** matches a **previously generated encoded password** using the encoder's own logic.
- `upgradeEncoding(encoded)` signals whether the current hash **should be updated** per encoder policy; calling it does not modify the database automatically.

The key call:

~~~java
boolean correct = encoder.matches(
    passwordSubmittedNow, // RAW from login request
    storedHash            // ENCODED from trusted account source
);
~~~

**Never swap the arguments.** Writing `encoder.matches(storedHash, rawPassword)` asks the encoder to treat the hash as plaintext and the raw password as the encoded format; the result will be wrong or throw a format error depending on the encoder.

### 3.1. What Happens Inside BCrypt's matches?

Conceptually:

~~~text
matches(rawPassword, storedEncodedPassword)
   |
   +--> Read salt/cost/version from storedEncodedPassword
   |
   +--> Compute verification of rawPassword with stored parameters
   |
   +--> Compare against stored hash result
   |
   +--> true or false
~~~

You **never** extract the salt, invoke the BCrypt hash function, and run `String.equals` yourself; the library handles that and the exact format details. Never use reversible encryption and decrypt passwords to authenticate logins.

### 3.2. Why Is `encode(raw).equals(encoded)` Not Equivalent to `matches(raw, encoded)`?

Both may look like “comparing hashes,” yet they differ fundamentally:

| Expression | Salt Used | Meaning | Suitable for Auth? |
| --- | --- | --- | --- |
| `encode(raw)` | Fresh salt generated by encoder | Create a new hash to store | Yes, at **registration/password change** |
| `encode(raw).equals(storedHash)` | New salt vs. old salt | Compare two independent hashes | **No** |
| `matches(raw, storedHash)` | Required parameters extracted from storedHash | Verify password against stored hash | **Yes** |
| `matches(otherRaw, storedHash)` | Parameters from storedHash | Check wrong password | Returns false for non-matching credentials |
| `storedHash.equals(raw)` | No password hashing used | Compare plaintext to hash | **No** |
| `encode(encode(raw))` | Second hash pass | Hash of a hash string | **No**, neither login nor standard storage |

Some **deterministic** encoders might yield identical strings for the same input; that does not make “encode then equals” a valid contract for password verification. Systems should use **`PasswordEncoder.matches`** and secure password hashing rather than relying on whether an implementation is randomized or deterministic.

## 4. Runnable Java 17 Program to Observe Behavior

Create `PasswordHashLab.java` in a project that already includes `spring-security-crypto` via the Spring Security starter or standalone dependency.

~~~java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

public class PasswordHashLab {

    public static void main(String[] args) {
        PasswordEncoder encoder = new BCryptPasswordEncoder(10);

        String raw = "Example!123";
        String hashAtRegistration = encoder.encode(raw);

        // Create another hash of the same raw password strictly for illustration.
        String anotherHash = encoder.encode(raw);

        // Right: check the same raw password against the hash stored at registration.
        boolean validLogin = encoder.matches(
            raw, hashAtRegistration
        );
        boolean wrongLogin = encoder.matches(
            "WrongPassword", hashAtRegistration
        );

        // Both independent hashes can verify the same raw password.
        boolean firstHashMatches = encoder.matches(
            raw, hashAtRegistration
        );
        boolean secondHashMatches = encoder.matches(
            raw, anotherHash
        );

        // Never print hashes/passwords in production logs.
        System.out.println("validLogin=" + validLogin);
        System.out.println("wrongLogin=" + wrongLogin);
        System.out.println(
            "bothHashesVerify=" + (firstHashMatches && secondHashMatches)
        );
    }
}
~~~

Expected logical output:

~~~text
validLogin=true
wrongLogin=false
bothHashesVerify=true
~~~

**The stdout above contains no hashes**, because hashes vary with random salts. It also intentionally **omits** printing `hashAtRegistration.equals(anotherHash)` as a fixed assertion: with BCrypt it is almost always false, yet probability should not be turned into a hard logic invariant.

### 4.2. Runnable Counterexample with Broken Logic

~~~java
PasswordEncoder encoder = new BCryptPasswordEncoder();

String stored = encoder.encode("Example!123");
String submitted = "Example!123";

// WRONG: a new salt is generated on every encode call.
boolean accepted = encoder.encode(submitted).equals(stored);
~~~

`accepted` is **nearly always false** even when the password is right. Never fix this by storing plaintext, disabling salts, or forcing one static salt for every user. Simply change it to:

~~~java
boolean accepted = encoder.matches(submitted, stored);
~~~

This is a change **in how verification is performed**, without altering the hashing algorithm or stored records. If existing records already use valid BCrypt formatting, you do not need to “rehash all users” to fix the comparison.

## 5. Applying This Across Three Flows: Registration, Login, and Password Change

### 5.1. Account Registration

~~~text
POST /registration
   |
   +--> Validate username/password policy
   +--> Check username uniqueness/tenant
   |
   v
   passwordEncoder.encode(rawPassword)
   |
   v
   Account(passwordHash=encoded)
   |
   v
   Store encoded password in database
~~~

Example snippet:

~~~java
public void register(String username, String rawPassword) {
    if (accountRepository.existsByUsername(username)) {
        throw new DuplicateAccountException();
    }

    String storedHash = passwordEncoder.encode(rawPassword);
    accountRepository.insert(username, storedHash);
}
~~~

This is **Java-like pseudocode**, since `AccountRepository` and `DuplicateAccountException` are application-defined types; it is not a standalone compilable file. Real apps need DB unique constraints to handle concurrent registration races, password policies, input size limits, and log redaction for credentials.

**Calling `encode` here is right**, because we need a fresh hash to store. The salt and cost live directly in the stored string.

### 5.2. Login

~~~text
POST /login
  username + rawPassword
           |
           v
    AuthenticationManager
           |
           v
    DaoAuthenticationProvider
           |
           +--> UserDetailsService.loadUserByUsername(username)
           |       |
           |       +--> Read storedHash and account flags
           |
           +--> PasswordEncoder.matches(rawPassword, storedHash)
           |
           +--> Check enabled/locked/expired
           |
           v
    Authentication succeeds or AuthenticationException
~~~

**Spring Security already implements this flow.** When using `DaoAuthenticationProvider`, do not write a custom login controller that loads `UserDetails`, calls `encode()`, and runs `equals`. The provider handles credential verification, while filters and managers coordinate authentication requests.

On a protected endpoint, `.authenticated()` checks authentication state; `.hasRole()` and domain-layer policies enforce authorization. A passing `matches` check does not grant a user every permission.

### 5.3. Password Change

A controlled flow:

1. Identify the current user via framework-verified `Authentication`.
2. Depending on sensitivity, require recent authentication/MFA before changing the password.
3. If the current password is required, verify `matches(currentRawPassword, storedHash)`.
4. Enforce password policy and breached-password checks per system capabilities.
5. Call **`encode(newRawPassword)`** to generate a new hash and save atomically.
6. Apply revocation policies for old sessions/tokens and notify of the change.

~~~java
// Snippet in a service, requiring userId from a trusted Authentication.
if (!encoder.matches(currentRawPassword, account.getPasswordHash())) {
    throw new InvalidCredentialsException();
}

String newStoredHash = encoder.encode(newRawPassword);
account.setPasswordHash(newStoredHash);
accountRepository.save(account);
~~~

`InvalidCredentialsException`, the entity, and the repository are application types; this snippet illustrates order of operations. **Do not check `encode(newRawPassword).equals(oldHash)` to detect password reuse**; if policy forbids reusing the current password, call:

~~~java
boolean newPasswordSameAsOld =
    encoder.matches(newRawPassword, oldStoredHash);
~~~

However, enforcing a history of the last N passwords requires checking against a list of **previously stored hashes**, never storing raw passwords or comparing new `encode` calls. Reuse policies, recovery flows, and revocation should be designed to match your threat model.

## 6. An End-to-End Spring Boot 3.5 / Spring Security 6.5 Demo App

The next example provides all classes needed to run a demo with an **in-memory account store**. The demo includes:

- `RegistrationService` calling `encode` during initial account creation.
- `AccountUserDetailsService` loading only the stored hash without re-encoding.
- `DaoAuthenticationProvider` wired with `PasswordEncoder` to use `matches`.
- `SecurityFilterChain` enabling HTTP Basic; `/me` requires an authenticated user.
- `PasswordComparisonTest` verifying right/wrong passwords via both encoder and MockMvc.

**There is no public HTTP registration endpoint**: sample accounts are seeded via `CommandLineRunner` on startup. That keeps focus on storing and verifying passwords instead of turning the lesson into a guide that exposes an unthrottled, unverified registration endpoint.

### 6.3. AccountStore.java

~~~java
package com.example.passwordcheck;

import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;

import org.springframework.stereotype.Repository;

@Repository
public class AccountStore {

    public record Account(String username, String passwordHash) {}

    private final ConcurrentMap<String, Account> accounts =
        new ConcurrentHashMap<>();

    public boolean insertIfAbsent(Account account) {
        return accounts.putIfAbsent(
            account.username(), account
        ) == null;
    }

    public Optional<Account> findByUsername(String username) {
        return Optional.ofNullable(accounts.get(username));
    }
}
~~~

`AccountStore` holds **only encoded passwords** in memory. `ConcurrentMap` and `putIfAbsent` handle concurrent duplicate-username creation in the demo, though it is not a production database. When replacing with PostgreSQL/MySQL, add unique constraints, transactions, and queries scoped by account ID/tenant.

### 6.4. RegistrationService.java

~~~java
package com.example.passwordcheck;

import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
public class RegistrationService {

    private final AccountStore store;
    private final PasswordEncoder encoder;

    public RegistrationService(
            AccountStore store, PasswordEncoder encoder) {
        this.store = store;
        this.encoder = encoder;
    }

    public void register(String username, String rawPassword) {
        if (username == null || username.isBlank()
                || rawPassword == null || rawPassword.isBlank()) {
            throw new IllegalArgumentException(
                "Invalid account registration input"
            );
        }

        String encodedPassword = encoder.encode(rawPassword);

        boolean inserted = store.insertIfAbsent(
            new AccountStore.Account(username, encodedPassword)
        );

        if (!inserted) {
            throw new IllegalArgumentException(
                "Username already exists"
            );
        }
    }
}
~~~

**What is right here:** `encode(rawPassword)` is called to generate a hash **when saving the account**, not on every user lookup. Production also requires password policies, breached-password screening, input length limits, DB username uniqueness checks, abuse controls, and responses that avoid user enumeration.

### 6.5. AccountUserDetailsService.java

~~~java
package com.example.passwordcheck;

import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

@Service
public class AccountUserDetailsService
        implements UserDetailsService {

    private final AccountStore store;

    public AccountUserDetailsService(AccountStore store) {
        this.store = store;
    }

    @Override
    public UserDetails loadUserByUsername(String username) {
        AccountStore.Account account =
            store.findByUsername(username)
                .orElseThrow(() ->
                    new UsernameNotFoundException(
                        "Invalid credentials"
                    )
                );

        return User.withUsername(account.username())
            .password(account.passwordHash())
            .roles("USER")
            .build();
    }
}
~~~

**Important:** `.password(account.passwordHash())` simply sets the loaded hash on `UserDetails`. If you wrote `.password(encoder.encode(account.passwordHash()))`, you would create a **hash of a hash**; the original raw password would fail to match when checked by the provider.

`loadUserByUsername` **does not receive the raw password** and is not responsible for verifying passwords. Account flags `enabled`, `locked`, `accountExpired`, and `credentialsExpired` use `User` builder defaults in the demo; in a real database they must be mapped from trusted columns.

### 6.6. SecurityConfig.java

~~~java
package com.example.passwordcheck;

import org.springframework.boot.CommandLineRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.ProviderManager;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(10);
    }

    @Bean
    AuthenticationManager authenticationManager(
            UserDetailsService userDetailsService,
            PasswordEncoder passwordEncoder) {

        DaoAuthenticationProvider provider =
            new DaoAuthenticationProvider(userDetailsService);

        provider.setPasswordEncoder(passwordEncoder);
        return new ProviderManager(provider);
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            AuthenticationManager authenticationManager)
            throws Exception {

        http
            .authenticationManager(authenticationManager)
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/public").permitAll()
                .requestMatchers(HttpMethod.GET, "/me").authenticated()
                .anyRequest().denyAll()
            )
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            );

        return http.build();
    }

    @Bean
    CommandLineRunner seedDemoUser(RegistrationService registration) {
        return args -> registration.register(
            "alice", "a1ice-Secret!"
        );
    }
}
~~~

**Reading the flow:**

1. The `PasswordEncoder` bean uses BCrypt cost `10` for the demo; production must benchmark and pick a cost/algorithm per current policy.
2. The `AuthenticationManager` bean wraps a `DaoAuthenticationProvider` configured with both `UserDetailsService` and `PasswordEncoder`. In Spring Security 6.5, `new DaoAuthenticationProvider(userDetailsService)` matches the API.
3. When `/me` receives a Basic header, `BasicAuthenticationFilter` passes the token to the manager/provider. The provider loads the hash from the service and runs **`matches(raw, storedHash)`**—never `encode(raw).equals(...)`.
4. `STATELESS` avoids restoring `SecurityContext` from `HttpSession` on subsequent requests. That fits the Basic demo, though it is not required for `PasswordEncoder`.
5. `seedDemoUser` invokes the registration flow on startup and stores a randomly salted hash. Each restart generates a different hash, yet the same password still logs in.
6. `anyRequest().denyAll()` blocks any unmatched URL/method. The app exposes no public endpoint to change passwords or create users.
7. HTTP Basic transmits passwords in Base64; **HTTPS** is mandatory when deploying outside localhost.

### 6.7. DemoController.java

~~~java
package com.example.passwordcheck;

import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class DemoController {

    @GetMapping("/public")
    public String publicEndpoint() {
        return "public";

~~~

The controller **never reads hashes, never calls encode/matches**, and does not need to know the BCrypt cost. Authentication was already verified by the provider via the filter. Never return the full `UserDetails`, `Authentication`, or hash in a response.

## 7. JUnit and MockMvc: Verifying What Actually Matters

Create `src/test/java/com/example/passwordcheck/PasswordComparisonTest.java`:

~~~java
package com.example.passwordcheck;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.test.web.servlet.MockMvc;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class PasswordComparisonTest {

    @Autowired PasswordEncoder encoder;
    @Autowired AccountStore accounts;
    @Autowired MockMvc mvc;

    @Test
    void storedPasswordHashIsNotPlaintext() {
        String hash = accounts.findByUsername("alice")
            .orElseThrow()
            .passwordHash();

        assertNotEquals("a1ice-Secret!", hash);
        assertTrue(encoder.matches("a1ice-Secret!", hash));
        assertFalse(encoder.matches("wrong", hash));
    }

    @Test
    void twoIndependentEncodesBothVerifySameRawPassword() {
        String hashOne = encoder.encode("same-password");
        String hashTwo = encoder.encode("same-password");

        assertTrue(encoder.matches("same-password", hashOne));
        assertTrue(encoder.matches("same-password", hashTwo));

        // Do not assertNotEquals(hashOne, hashTwo):
        // random salt makes them nearly always differ,
        // but the contract does not promise an absolute invariant.
    }

    @Test
    void storedHashMustBePassedAsSecondParameter() {
        String stored = encoder.encode("correct");

        assertTrue(encoder.matches("correct", stored));
        assertFalse(encoder.matches("incorrect", stored));
    }

    @Test
    void correctPasswordAuthenticatesThroughBasicFilter()
            throws Exception {
        mvc.perform(get("/me")
                .with(httpBasic("alice", "a1ice-Secret!")))
            .andExpect(status().isOk())
            .andExpect(content().string("user:alice"));
    }

    @Test
    void wrongPasswordAndMissingCredentialAreRejected()
            throws Exception {
        mvc.perform(get("/me")
                .with(httpBasic("alice", "wrong")))
            .andExpect(status().isUnauthorized());

        mvc.perform(get("/me"))
            .andExpect(status().isUnauthorized());
    }

    @Test
    void publicEndpointStillWorksWithoutLogin()
            throws Exception {
        mvc.perform(get("/public"))
            .andExpect(status().isOk())
            .andExpect(content().string("public"));
    }
}
~~~

gradlew.bat test
~~~

**Why are the tests written this way?**

- `storedPasswordHashIsNotPlaintext` proves registration saved a hash, and valid vs. invalid passwords are distinguished via `matches`.
- `twoIndependentEncodesBothVerifySameRawPassword` focuses on the **key contract**: both hashes can verify the same raw password. It **avoids a brittle assertion** claiming two random salts can never collide.
- `storedHashMustBePassedAsSecondParameter` guards argument order.
- `correctPasswordAuthenticatesThroughBasicFilter` and the 401 tests exercise the HTTP Basic filter, `AuthenticationManager`, and `DaoAuthenticationProvider`, rather than bypassing them with a mock authenticated principal.
- The public endpoint proves access rules work independently of password matching.

**Gradle has not been executed inside this document**; the results table is expected behavior derived from the code. If your project uses another version, review dependencies, imports, and behavior against that actual Spring Security release.

### 7.1. Common Bad Tests

~~~java
// Weak/misdirected test:
assertEquals(
    encoder.encode("password123"),
    encoder.encode("password123")
);
~~~

With BCrypt, that test nearly always fails. Never fix the test by locking down the salt to force two hashes to match. Tests should instead do:

~~~java
String saved = encoder.encode("password123");
assertTrue(encoder.matches("password123", saved));
assertFalse(encoder.matches("different", saved));
~~~

Or when testing a registration service, read the **actual stored hash from the test store**, then verify the raw password with `matches`. Never call the registration service and compare the stored result against an expected hash generated by a separate `encode` call.

### 7.2. Avoiding Fragile Tests from Work Factors

A high BCrypt work factor can slow down tests with many accounts or logins. For pure unit tests not exercising the BCrypt implementation itself, you may use a fake/in-memory encoder **only in tests**; however, integration tests for real login must keep the encoder mechanism aligned with production and cover end-to-end cases.

Never switch to `NoOpPasswordEncoder` in production to speed up tests; if tests need optimization, separate unit tests from crypto integration tests and ensure test profiles never leak into live configs.

## 8. `DelegatingPasswordEncoder`: The `{bcrypt}` Prefix and Configuration Pitfalls

Spring Security commonly uses `DelegatingPasswordEncoder` to manage multiple password hashing formats and support gradual upgrades. Creating the encoder:

~~~java
PasswordEncoder encoder =
    PasswordEncoderFactories.createDelegatingPasswordEncoder();
~~~

This snippet uses imports `org.springframework.security.crypto.factory.PasswordEncoderFactories` and `PasswordEncoder`.

Default `encode(raw)` typically outputs strings of the form:

~~~text
{bcrypt}$2a$10$...
~~~

The line above is an **illustrative shape**, not a valid hash. The `{bcrypt}` prefix identifies the algorithm used for the remainder, letting `matches(raw, stored)` pick the right encoder.

### 8.1. Comparing Three Formats

| Stored Value | Matching Encoder | Notes |
| --- | --- | --- |
| `$2a$10$...` | Plain `BCryptPasswordEncoder` | BCrypt hash **without a prefix id** |
| `{bcrypt}$2a$10$...` | `DelegatingPasswordEncoder` with `bcrypt` id mapped | Has prefix for encoder routing |
| `{pbkdf2}...` or `{scrypt}...` | Delegating with corresponding encoder/version | Requires exact format/parameters per version |

**You cannot take two hashes with different prefixes and compare them with `String.equals`** to verify a user. When a system uses `DelegatingPasswordEncoder`, always pass the **raw password and the full stored string** into `matches`.

### 8.2. Error: “There is no PasswordEncoder mapped for the id null”

When using `DelegatingPasswordEncoder`, the database may still hold legacy BCrypt hashes like `$2a$...` **without `{bcrypt}`**. Without a default encoder for null/unmapped ids, `matches` throws `IllegalArgumentException` instead of returning false:

~~~text
There is no PasswordEncoder mapped for the id "null"
~~~

The cause is **not** “wrong password,” but a **mismatch between the stored format and the configured encoder**. The proper fix is inspecting actual formats, identifying the legacy algorithm, and executing a documented migration or prefixing plan.

For example, once you have verified for certain a column holds plain BCrypt hashes, prepending `{bcrypt}` to those hashes **requires neither raw passwords nor changing any BCrypt bits**; nonetheless, guard against mixed data, back up, use transactions, audit, and test before migrating. Never blindly prepend prefixes to hashes of unknown origin.

### 8.3. Do Not Use `NoOpPasswordEncoder` as a Production Solution

Some legacy examples use `{noop}` to represent plaintext, which is **not** safe password storage in production. Using NoOp merely to “make login work” can leave the server storing plaintext passwords or accepting insecure mechanisms.

When migrating away from old passwords, define a clear strategy per format: identify the algorithm id, allow `matches` against existing hashes during transition, then upgrade to the new encoder upon successful user authentication or force password resets.

### 8.4. `upgradeEncoding` and `UserDetailsPasswordService`

Password hashes can be upgraded after a user logs in successfully:

~~~text
User submits raw password
       |
       v
PasswordEncoder.matches(raw, storedHash) -> true
       |
       v
PasswordEncoder.upgradeEncoding(storedHash)
       |
       +--> false: keep using old hash
       |
       +--> true:
               |
               v
           encode(raw) per new policy
               |
               v
           UserDetailsPasswordService.updatePassword(...)
               |
               v
           Safely write new hash to database
~~~

This is a **conceptual diagram**, not an automatic database rewrite triggered merely because a `PasswordEncoder` bean exists. In the DAO flow, Spring Security supports `UserDetailsPasswordService` when provided/configured alongside an upgrade mechanism. Your application must still implement persistence updates, transactions, concurrency guards against other password changes, and cache invalidation if needed.

**Never “upgrade” by calling `encode(storedHash)`**: that creates a hash of a hash and breaks verification for the original raw password.

## 9. Common Mistakes Seen in Code Reviews

### 9.1. Encoding Twice During Login

~~~java
// Wrong.
String storedHash = repository.findByUsername(username)
    .orElseThrow()
    .passwordHash();

String hashFromInput = encoder.encode(passwordFromLogin);
if (hashFromInput.equals(storedHash)) {
    // login
}
~~~

With BCrypt, this fails because the two encode calls generate independent salts. Use `matches(passwordFromLogin, storedHash)` or let `AuthenticationManager`/`DaoAuthenticationProvider` handle it.

### 9.2. Re-Encoding the Hash When Loading the User

~~~java
// Wrong in UserDetailsService: account.passwordHash() is already encoded.
return User.withUsername(account.username())
    .password(encoder.encode(account.passwordHash()))
    .roles("USER")
    .build();
~~~

During login the provider compares the raw password against a **hash of a hash**, causing every password to be rejected. Fix it to:

~~~java
return User.withUsername(account.username())
    .password(account.passwordHash())
    .roles("USER")
    .build();
~~~

### 9.3. Comparing Raw Password Directly with Stored Hash

~~~java
// Wrong.
boolean matches = rawPassword.equals(storedHash);
~~~

A password hash is not plaintext. If this code ever succeeds, data is likely stored in plaintext, which is a security defect requiring remediation.

### 9.4. Swapping Argument Order

~~~java
// Wrong.
encoder.matches(storedHash, rawPassword);

// Right.
encoder.matches(rawPassword, storedHash);
~~~

Avoid naming both hashes and plaintexts `password`. Use `rawPassword`, `storedHash`, and `encodedPassword` to prevent mix-ups.

### 9.5. Generating a New Salt During Verification

~~~java
// Wrong by design if picking a new random salt yourself to match a hash.
String salt = generateNewSalt();
String newHash = hashWithSalt(rawPassword, salt);
boolean valid = newHash.equals(storedHash);
~~~

Instead of rolling custom hashing/salt logic, use `PasswordEncoder.matches`. If your app needs a specialized algorithm/format, rely on vetted cryptographic libraries and tested contracts rather than writing security-critical primitives yourself.

### 9.6. Using the Hash Itself as a “Verified Password”

~~~java
// Wrong: client sends the raw stored hash to log in.
// Server treats the hash as a bearer token instead of requiring the raw password.
if (requestPassword.equals(account.passwordHash())) {
    return allow();
}
~~~

If the stored hash leaks, an attacker can log in without knowing the raw password. **A password hash is not a credential for clients to present in standard login protocols.** Avoid “pass the hash” designs.

### 9.7. Switching Encoders Without Migrating Data

Previously using plain BCrypt, today switching the bean to Delegating. Old hashes lack `{bcrypt}`, so `matches` throws an id null error. Plan migrations and test against realistic hash datasets.

### 9.8. Hardcoding Wrong-Version Password Hashes in Migrations

Hashes generated under another encoder or parameter set may fail verification under the current encoder. Validate format, algorithm, cost, and version with non-sensitive sample data. Never paste real account hashes into issue trackers or public docs.

### 9.9. Assuming Visually Identical Strings Are the Same Unicode Password

Some Unicode inputs have different code point representations that look identical. Java String equality and hashing operate on bytes determined by the application's encoding/normalization policy. Changing Unicode normalization, case mapping, or whitespace trimming between **registration** and **login** can make visually identical inputs stop matching.

Keep password input policies consistent, and avoid blindly calling `trim()` or `toLowerCase()` on passwords; unlike usernames, passwords should generally preserve exact user input. If applying normalization, design and document it upfront and test both Unicode and long passwords.

### 9.10. Using `equalsIgnoreCase` for Passwords

Standard passwords are case-sensitive. Never use `equalsIgnoreCase`, `toLowerCase`, `trim`, or strip characters to “improve login success rate.” That alters the user's chosen secret.

### 9.11. Logging Raw Passwords and Encoded Hashes

~~~java
// Do not do this in production:
log.info("login password={}", rawPassword);
log.info("stored password hash={}", storedHash);
~~~

Hashes are not plaintext, yet they remain sensitive data enabling offline attacks if leaked. Never write raw passwords, password hashes, Authorization headers, or cookie/session tokens to application logs, traces, analytics, or responses.

### 9.12. Testing Two Encoded Strings with assertEquals

~~~java
// Misdirected for a salted encoder.
assertEquals(encoder.encode("abc"), encoder.encode("abc"));
~~~

The right way to test is **`matches("abc", hash)`**, then verifying a wrong password returns false. Never force BCrypt to use a fixed salt in production just to make a test pass.

## 10. Login Latency: Do Not Rip Out Hashing to Optimize Prematurely

Password hashing is slow by design. When a server handles heavy login traffic, balance **cost/throughput** and attack controls:

- Benchmark BCrypt cost on production-equivalent CPUs and instance configurations.
- Apply per-account and per-source rate limits while avoiding easily abused self-DoS lockouts.
- Deploy credential-stuffing/password-spraying detection, failed-login audits, and MFA where needed.
- Set sensible input bounds against resource exhaustion while still supporting long passphrases per policy.
- Design responses that avoid leaking username existence via distinct messages or timing.
- Never replace BCrypt with `NoOpPasswordEncoder`, MD5/SHA-1, or single-pass SHA-256 just to speed up logins.

### 10.1. BCrypt and Very Long Passwords

Traditional BCrypt has an input boundary around **72 bytes** depending on the implementation. With Unicode passwords, UTF-8 byte count does not necessarily equal Java character count. When setting a long-password policy, verify your running encoder/version behavior and the risk of two distinct inputs colliding due to length truncation.

Never silently truncate passwords to 72 characters or naively pre-hash with SHA-256 without careful design; such changes can break login compatibility across versions or introduce vulnerabilities. Choose a documented storage scheme and input policy, test Unicode/long passwords, and give users clear guidance.

### 10.2. Timing and User Enumeration

An authentication flow for a nonexistent username can take a different path than a wrong password. Spring Security/`DaoAuthenticationProvider` includes mitigations against user enumeration in certain cases, yet applications must still evaluate timing, responses, rate limits, and logging. Never return “this account exists but the password is wrong” on public endpoints unless explicitly intended by policy.

## 11. Troubleshooting Table

| Symptom | Common Cause | Correct Check |
| --- | --- | --- |
| Right password gets 401 | Code calls `encode(raw).equals(stored)` | Switch to `matches(raw, stored)` |
| New hash differs from old hash | Random salt | Normal behavior; both can match the same raw password |
| `matches` returns false for all users | Service re-encodes stored hash | Load only the original hash from DB |
| `There is no PasswordEncoder mapped for id "null"` | Delegating used with hashes lacking `{id}` | Identify format and migrate/configure proper encoder |
| `matches` throws format error | Corrupted hash or unsupported algorithm id | Check migration, data integrity, and compatibility |
| Slow logins | High BCrypt/Argon2 work factor, overloaded CPU | Benchmark and tune capacity/rate limiting; do not disable hashing |
| Login succeeds but /admin returns 403 | Authentication succeeded; missing ROLE_ADMIN | Check authorization/`GrantedAuthority` separately |
| Old sessions still work after password reset | Sessions/tokens not revoked | Implement session/refresh-token revocation policy |
| User still logs in with old password on another node | Cache/replication/store out of sync | Check cache invalidation, DB transactions, IdP |
| Visually identical Unicode password fails login | Mismatched input conversion/normalization | Align policy and test code points/bytes |
| Cannot log in after changing encoder | Different hash prefix/parameters | Use proper Delegating/migration strategy |
| Hash appears in API response | Serializing full UserDetails/Authentication | Return explicit DTOs; never expose hashes |

**401 Unauthorized** typically relates to authentication, while **403 Forbidden** typically indicates insufficient permissions or rejection by a filter such as CSRF. With form login, failure may return a 302 redirect. Never treat every 403 as a `PasswordEncoder` bug.

## 12. Code Review Checklist

When reviewing a PR containing password-related code, ask:

1. Is `encode(rawPassword)` called only when **creating/migrating/changing hashes**, never on every login for an `equals` check?
2. Does `matches` receive **raw as the first parameter** and **stored encoded hash as the second parameter**?
3. Is the hash persisted once encoded without being re-encoded when `UserDetailsService` loads it?
4. Do all accounts follow the same `{bcrypt}`/raw-BCrypt convention expected by the configured encoder?
5. Are there unit/integration tests for valid passwords, wrong passwords, and invalid/missing credentials?
6. Do tests check passwords from the actual account store instead of synthesizing an “expected” hash via another `encode` call?
7. Does anything roll custom salts/hashes, truncate inputs, lowercase, trim, or alter Unicode passwords?
8. Are PasswordEncoder cost/parameters measured in a realistic environment and tuned appropriately?
9. Are password hashes or raw tokens ever logged, returned in JSON, dumped in exceptions, or emitted in metrics?
10. Do registration and password-change flows have uniqueness checks, validation, rate limiting, password policies, and proper recovery?
11. When changing hash algorithms, are migration/upgrading and `UserDetailsPasswordService` wired if needed?
12. On password reset, are sessions, tokens, and remember-me tokens revoked per policy?
13. Does the system handle malformed stored hashes or unmapped ids safely without failing open?
14. Do variable names like `rawPassword` and `storedHash` help prevent argument swaps?
15. Does the backend let Spring Security providers verify credentials instead of constructing authenticated tokens directly from client input?

A small `String.equals` bug at login can lock out an entire user base. Reviewing both **data direction** and **hash lifecycle** matters far more than merely checking method names.

## 13. Self-Check Exercises

**Question 1.** A user registers password `Example!123`; BCrypt produces hash X. At login, calling BCrypt encode again produces hash Y different from X. Does that mean the user typed the wrong password?

**Answer:** No. Random salting causes two encode calls to produce different hashes even for identical raw passwords. You must check `matches("Example!123", X)`.

**Question 2.** Which line verifies a password properly?

~~~java
// A
encoder.encode(raw).equals(storedHash);

// B
encoder.matches(raw, storedHash);

// C
encoder.matches(storedHash, raw);

// D
raw.equals(storedHash);
~~~

**Answer:** **B**.

**Question 3.** An account has a stored BCrypt hash; do we need to decode it to recover the real password?

**Answer:** No, and standard password hashing is one-way. Use `matches` to verify the candidate raw password.

**Question 4.** Should `UserDetailsService.loadUserByUsername` encode the password hash one more time?

**Answer:** No. It must return the existing stored hash along with authorities and account status. The provider is responsible for verifying credentials.

**Question 5.** Why do two users who both set `Example!123` still get different `storedHash` values?

**Answer:** Each account/encode call gets its own random salt, preventing identical hash fingerprints.

**Question 6.** Should we fix the salt across all accounts so two `encode()` calls produce the same string and tests pass?

**Answer:** No. Doing so defeats the purpose of salts; fix the tests and login logic to use `matches`.

**Question 7.** When changing password from `old` to `new`, at which step is `encode` called?

**Answer:** Verify the old password with `matches(oldRaw, oldStoredHash)` if policy requires it; hash `newRaw` with `encode(newRaw)` and save.

**Question 8.** To forbid users from reusing old passwords, should we compare two encoded strings with `equals`?

**Answer:** No. Use `matches(newRaw, oldStoredHash)` against the old hash; if checking history, test against each historical stored hash per policy.

**Question 9.** What does `There is no PasswordEncoder mapped for the id "null"` usually indicate?

**Answer:** `DelegatingPasswordEncoder` cannot recognize a stored hash id/format, such as a missing `{bcrypt}` prefix. Do not assume it means wrong password; inspect configuration and migration.

**Question 10.** Should raw passwords be stored in the DB alongside hashes in case the encoder changes later?

**Answer:** No. Store proper encoded hashes and use migration/reset strategies when changing algorithms—never keep plaintext.

**Question 11.** What effect does BCrypt cost have?

**Answer:** It controls computational cost for encode/matches, making brute-force harder while increasing server load; benchmark and plan capacity.

**Question 12.** If a unit test asserts `encoder.encode("abc") == encoder.encode("abc")`, how should it be fixed?

**Answer:** Generate one hash with `encode`, then assert `matches("abc", hash)` is true and `matches("wrong", hash)` is false.

**Question 13.** Does `matches` succeeding mean the user is allowed to access `/admin`?

**Answer:** No. Authentication and authorization are separate; roles, authorities, ownership, and account status still apply.

**Question 14.** Should all passwords be converted to lowercase or trimmed before `matches`?

**Answer:** Not arbitrarily. Doing so alters chosen secrets and causes inconsistent behavior. Follow an explicitly designed and consistently tested policy.

**Question 15.** Is leaking a password hash completely harmless because it cannot be decrypted?

**Answer:** No. Hashing prevents storing plaintext, yet attackers can attempt offline guessing. Strong algorithms, salts, costs, DB protection, rate limiting, and incident response remain necessary.
