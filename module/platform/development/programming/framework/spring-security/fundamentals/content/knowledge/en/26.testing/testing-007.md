# Testing Valid Login, Invalid Credentials, and Unusable Accounts

> **Scope:** testing username/password authentication with **Spring Boot 3.x, Spring Security 6.x, Spring MVC (Servlet), Java 17+**. This lab uses form login and `MockMvc` to distinguish three outcome groups: **successful login**, **invalid credentials**, and **existing accounts that are not permitted to be used** (such as disabled, locked, or expired). Supporting scenarios cover accessing protected resources, CSRF, sessions, and insufficient permissions. The examples fully integrate `spring-security-test`; do not treat HTTP 401 as the default outcome for **form login**.

## 1. Objectives and scenario matrix

Login testing is not just checking which HTTP status `POST /login` returns. A solid authentication suite must prove: **valid credentials establish the right authenticated identity**, whereas invalid credentials or unusable accounts **cannot create an authenticated context**. You must also verify redirect targets and post-login access rights.

| Scenario | Authentication evidence | Account state | Expected outcome with form login |
| --- | --- | --- | --- |
| Valid login | Username exists, password matches | Enabled, unlocked, non-expired | Redirects to `/home`; `authenticated()` with matching username/role |
| Wrong password | Username exists, wrong password | Active | Redirects to `/login?error`; `unauthenticated()` |
| Non-existent username | Username absent from store | N/A | Redirects to `/login?error`; `unauthenticated()` |
| Missing username or password | Missing or empty credentials | Unknown | Authentication fails; no authenticated identity |
| Disabled account | Password matches | `enabled=false` | Fails; no valid login session issued |
| Locked account | Password matches | `accountNonLocked=false` | Fails; no authenticated identity issued |
| Expired account | Password matches | `accountNonExpired=false` | Fails; account cannot be used |
| Expired credentials | Password matches | `credentialsNonExpired=false` | Fails; requires credential change/re-issuance flow per design |
| Valid account lacking role | Login succeeds | Active | Authenticated, yet request to `/admin` returns **403** |
| Login POST missing CSRF | Credentials may be valid | Active | **403 from CSRF protection** before authentication completes |

**Distinguish two concepts:** *authentication failure* means rejecting credentials or the account; *authorization failure* happens after authentication succeeds when the caller lacks permission for an action. Thus a test returning 403 on `/admin` does not prove login failed.

**Common HTTP pitfall:** In the **form login** example, both valid and invalid logins can return **302 Found** because results are delivered via redirects. Success goes to `/home`; failure goes to `/login?error`. With **HTTP Basic**, credential failures normally return **401** and `WWW-Authenticate`. Write assertions matching the configured mechanism instead of forcing every login failure to be 401.

## 2. Spring Security's form login processing flow

```text
Browser
  |
  | GET /login
  v
Login page generated by Spring Security
  |
  | POST /login + username/password + CSRF
  v
CsrfFilter
  |-- missing/invalid CSRF --> typically 403 (password not checked yet)
  |
  v
UsernamePasswordAuthenticationFilter
  |
  | creates unauthenticated UsernamePasswordAuthenticationToken
  v
AuthenticationManager (typically ProviderManager)
  |
  v
DaoAuthenticationProvider
  |-- UserDetailsService loads UserDetails
  |-- checks account status flags
  |-- PasswordEncoder matches password/hash
  |-- checks credential status
  |
  +------ success -------------------- failure --------+
  |                                                    |
  v                                                    v
Valid Authentication                          AuthenticationException
  |                                                    |
  v                                                    v
SecurityContext is populated                  SecurityContext is cleared
and saved per login mechanism                   AuthenticationFailureHandler
  |                                                    |
  v                                                    v
AuthenticationSuccessHandler                     Redirect /login?error
  |
  v
Redirect /home
  |
  v
GET /home with authenticated session -> 200
```

Role of each component:

- `UserDetailsService`: returns `UserDetails` from the account store. The example uses `InMemoryUserDetailsManager`; production can swap in database/LDAP or an appropriate adapter.
- `PasswordEncoder`: calls `matches(rawPassword, storedHash)` to verify passwords. The example uses `BCryptPasswordEncoder`; never store plaintext passwords in production data stores.
- `DaoAuthenticationProvider`: standard mechanism checking username/password and `UserDetails` status flags. No custom provider is needed merely to enforce enabled/locked/expired states.
- `UsernamePasswordAuthenticationFilter`: handles login requests, builds the input token, and delegates to the manager.
- `AuthenticationSuccessHandler`/`AuthenticationFailureHandler`: decides redirects or response format after authentication.
- `SecurityContext`: holds the accepted `Authentication`. In session-based form login, the context persists across requests via Spring Security's repository mechanism.
- `AuthorizationFilter`: enforces URL permissions after authentication; `/admin` requiring `ROLE_ADMIN` rejects a caller with `ROLE_USER`.

A test checking only `response.status == 302` is weak: **both branches can return 302**. Add `redirectedUrl` and security result matchers. A test calling `get("/home").with(user("alice"))` also does not prove passwords were checked: `user(...)` injects a mock identity directly into the request.

## 3. Preparing the demo application

### 3.1. Dependencies

Use a Spring Boot 3.x project with Java 17+ and the Spring Boot Gradle plugin configured. Add to the `dependencies` block in `build.gradle`:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.security:spring-security-test'
}
```

This is a **dependencies block**, not a full Gradle file. `spring-boot-starter-test` provides JUnit Jupiter, AssertJ/Hamcrest, and MockMvc; `spring-security-test` provides `formLogin()`, `authenticated()`, `unauthenticated()`, and security test helpers. No external server needs to be started to use `MockMvc`.

### 3.2. Creating the application and account states

Create **`src/main/java/demo/DemoApplication.java`** as follows:

```java
package demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@Configuration
class SecurityConfig {

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    UserDetailsService userDetailsService(PasswordEncoder encoder) {
        return new InMemoryUserDetailsManager(
                User.withUsername("active")
                        .password(encoder.encode("active-pass"))
                        .roles("USER")
                        .build(),

                User.withUsername("admin")
                        .password(encoder.encode("admin-pass"))
                        .roles("ADMIN")
                        .build(),

                User.withUsername("disabled")
                        .password(encoder.encode("disabled-pass"))
                        .roles("USER")
                        .disabled(true)
                        .build(),

                User.withUsername("locked")
                        .password(encoder.encode("locked-pass"))
                        .roles("USER")
                        .accountLocked(true)
                        .build(),

                User.withUsername("expired")
                        .password(encoder.encode("expired-pass"))
                        .roles("USER")
                        .accountExpired(true)
                        .build(),

                User.withUsername("credential-old")
                        .password(encoder.encode("credential-old-pass"))
                        .roles("USER")
                        .credentialsExpired(true)
                        .build()
        );
    }

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/public").permitAll()
                        .requestMatchers("/admin").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .formLogin(form -> form
                        .defaultSuccessUrl("/home", true)
                        .failureUrl("/login?error")
                        .permitAll())
                .build();
    }
}

@RestController
class DemoController {

    @GetMapping("/public")
    String publicPage() {
        return "public";
    }

    @GetMapping("/home")
    String home(Authentication authentication) {
        return "Xin chao " + authentication.getName();
    }

    @GetMapping("/admin")
    String adminPage() {
        return "admin-only";
    }
}
```

**This is a complete Java file.** The filename matches the `public DemoApplication` class; `SecurityConfig` and `DemoController` are package-private top-level classes in package `demo`. `@SpringBootApplication` scans this package and registers the beans automatically.

Accounts used in the example:

| Username | Demo password | Important status flag | Can log in? |
| --- | --- | --- | --- |
| `active` | `active-pass` | Meets default conditions | Yes, role `USER` |
| `admin` | `admin-pass` | Meets default conditions | Yes, role `ADMIN` |
| `disabled` | `disabled-pass` | `isEnabled() == false` | No |
| `locked` | `locked-pass` | `isAccountNonLocked() == false` | No |
| `expired` | `expired-pass` | `isAccountNonExpired() == false` | No |
| `credential-old` | `credential-old-pass` | `isCredentialsNonExpired() == false` | No |

`User.withUsername(...)` builds `UserDetails` for the demo. Builder setters `disabled(true)`, `accountLocked(true)`, `accountExpired(true)`, and `credentialsExpired(true)` represent **denied** states. Pay attention to the positive/non-negated naming on the interface: `isAccountNonLocked() == true` means the account **is not locked**; `isCredentialsNonExpired() == true` means credentials **have not expired**.

In the configuration:

- `.requestMatchers("/public").permitAll()` exposes one open endpoint for comparison.
- `.requestMatchers("/admin").hasRole("ADMIN")` requires `ROLE_ADMIN`; user `active` only holds `ROLE_USER`.
- `.anyRequest().authenticated()` requires authentication for other endpoints like `/home`.
- `.formLogin(...)` enables form login and the default login page. Because `loginPage(...)` is not called, Spring Security generates `GET /login` automatically. If you define a custom login page later, you must serve it yourself.
- `.defaultSuccessUrl("/home", true)` ensures successful login always redirects to `/home` in the example, even if a saved request existed earlier.
- `.failureUrl("/login?error")` gives every login failure the same public redirect target. This choice helps avoid leaking "username exists but is locked."
- `.permitAll()` lets unauthenticated users reach the login endpoints. There is no need to put password validation inside a controller.
- There is no `csrf.disable()`. Form login submits via POST, so CSRF stays enabled; tests must send a valid token.

**Example safety:** hardcoded accounts and passwords are for localhost/lab use only. In production, never store raw passwords in code, never expose hashes via APIs, use HTTPS, and back accounts with a real store plus lockout/rate-limiting policies.

## 4. Writing integration tests with MockMvc

Create **`src/test/java/demo/FormLoginFlowTest.java`**:

```java
package demo;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.mock.web.MockHttpSession;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.hamcrest.Matchers.containsString;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.springframework.security.test.web.servlet.request
        .SecurityMockMvcRequestBuilders.formLogin;
import static org.springframework.security.test.web.servlet.response
        .SecurityMockMvcResultMatchers.authenticated;
import static org.springframework.security.test.web.servlet.response
        .SecurityMockMvcResultMatchers.unauthenticated;
import static org.springframework.test.web.servlet.request
        .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request
        .MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.redirectedUrl;
import static org.springframework.test.web.servlet.result
        .MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class FormLoginFlowTest {

    @Autowired
    MockMvc mvc;

    @Autowired
    UserDetailsService userDetailsService;

    @Test
    void publicPageDoesNotRequireLogin() throws Exception {
        mvc.perform(get("/public"))
                .andExpect(status().isOk())
                .andExpect(content().string("public"));
    }

    @Test
    void anonymousVisitorIsRedirectedToLoginPage() throws Exception {
        mvc.perform(get("/home"))
                .andExpect(status().is3xxRedirection())
                .andExpect(header().string(
                        "Location", containsString("/login")));
    }

    @Test
    void correctLoginCreatesAuthenticatedSession() throws Exception {
        MvcResult login = mvc.perform(formLogin()
                        .user("active")
                        .password("active-pass"))
                .andExpect(status().isFound())
                .andExpect(redirectedUrl("/home"))
                .andExpect(authenticated()
                        .withUsername("active")
                        .withRoles("USER"))
                .andReturn();

        MockHttpSession session =
                (MockHttpSession) login.getRequest().getSession(false);
        assertNotNull(session);

        mvc.perform(get("/home").session(session))
                .andExpect(status().isOk())
                .andExpect(content().string("Xin chao active"));
    }

    @Test
    void wrongPasswordFailsAuthentication() throws Exception {
        mvc.perform(formLogin()
                        .user("active")
                        .password("wrong-password"))
                .andExpect(status().isFound())
                .andExpect(redirectedUrl("/login?error"))
                .andExpect(unauthenticated());
    }

    @Test
    void unknownUsernameHasSamePublicFailureOutcome() throws Exception {
        mvc.perform(formLogin()
                        .user("missing-user")
                        .password("some-password"))
                .andExpect(status().isFound())
                .andExpect(redirectedUrl("/login?error"))
                .andExpect(unauthenticated());
    }

    @Test
    void emptyCredentialsFailAuthentication() throws Exception {
        mvc.perform(formLogin()
                        .user("")
                        .password(""))
                .andExpect(status().isFound())
                .andExpect(redirectedUrl("/login?error"))
                .andExpect(unauthenticated());
    }

    @ParameterizedTest
    @CsvSource({
            "disabled, disabled-pass",
            "locked, locked-pass",
            "expired, expired-pass",
            "credential-old, credential-old-pass"
    })
    void unusableAccountCannotLogIn(
            String username, String correctPassword) throws Exception {

        mvc.perform(formLogin()
                        .user(username)
                        .password(correctPassword))
                .andExpect(status().isFound())
                .andExpect(redirectedUrl("/login?error"))
                .andExpect(unauthenticated());
    }

    @Test
    void accountStateFlagsAreConfiguredAsExpected() {
        assertFalse(userDetailsService
                .loadUserByUsername("disabled").isEnabled());

        assertFalse(userDetailsService
                .loadUserByUsername("locked").isAccountNonLocked());

        assertFalse(userDetailsService
                .loadUserByUsername("expired").isAccountNonExpired());

        assertFalse(userDetailsService
                .loadUserByUsername("credential-old")
                .isCredentialsNonExpired());
    }

    @Test
    void loggedInUserStillCannotAccessAdminOnlyUrl()
            throws Exception {

        MvcResult login = mvc.perform(formLogin()
                        .user("active")
                        .password("active-pass"))
                .andExpect(authenticated()
                        .withUsername("active"))
                .andReturn();

        MockHttpSession session =
                (MockHttpSession) login.getRequest().getSession(false);
        assertNotNull(session);

        mvc.perform(get("/admin").session(session))
                .andExpect(status().isForbidden());
    }

    @Test
    void adminCanAccessAdminOnlyUrlAfterLogin()
            throws Exception {

        MvcResult login = mvc.perform(formLogin()
                        .user("admin")
                        .password("admin-pass"))
                .andExpect(authenticated()
                        .withUsername("admin")
                        .withRoles("ADMIN"))
                .andReturn();

        MockHttpSession session =
                (MockHttpSession) login.getRequest().getSession(false);
        assertNotNull(session);

        mvc.perform(get("/admin").session(session))
                .andExpect(status().isOk())
                .andExpect(content().string("admin-only"));
    }

    @Test
    void postLoginWithoutCsrfIsRejectedBeforePasswordCheck()
            throws Exception {

        mvc.perform(post("/login")
                        .param("username", "active")
                        .param("password", "active-pass"))
                .andExpect(status().isForbidden())
                .andExpect(unauthenticated());
    }
}
```

**This is a complete test class** in the `demo` package using JUnit Jupiter and Spring Security Test. It uses `@SpringBootTest` to start the example's real context and `@AutoConfigureMockMvc` to configure `MockMvc` with Spring Security filters. No network server is invoked; requests/responses are simulated inside the JVM via Spring MVC Test.

To run in the project directory:

```bash
./gradlew test
```

On Windows:

```powershell
.\gradlew.bat test
```

When running a single class in Gradle:

```bash
./gradlew test --tests demo.FormLoginFlowTest
```

**Expected result:** all test methods pass when the application code and dependencies match the example setup. Do not assert exact total test-count output from an unexecuted environment; `@ParameterizedTest` creates multiple invocations and Gradle/JUnit versions may report counts differently. For real failures, read the specific test's stack trace to locate mismatches across redirects, principals, sessions, or CSRF.

## 5. Reading the three main test groups closely

### 5.1. Valid login: looking beyond status 302

Test `correctLoginCreatesAuthenticatedSession` builds four layers of evidence:

1. `formLogin().user("active").password("active-pass")` simulates submitting `POST /login` with default `username/password` parameters **and a valid CSRF token**.
2. `status().isFound()` and `redirectedUrl("/home")` prove the success handler redirects to the intended target.
3. `authenticated().withUsername("active").withRoles("USER")` proves the authentication result has the right identity/authority. `withRoles("USER")` checks the `ROLE_USER` convention.
4. Grabbing `MockHttpSession` from the login request and sending `GET /home` with that same session proves the **subsequent request** reads the stored `SecurityContext`. The response returns exactly `Xin chao active`.

If you assert only 302, the test misses regressions that redirect to the failure URL. If you only call `get("/home").with(user("active"))`, that **simulates an already-authenticated user** and skips the password encoder and account-status checks. Only `formLogin()` traverses the login flow inside the example's `SecurityFilterChain`.

Note that `@WithMockUser` and `user(...)` are useful for testing authorization/controllers elsewhere, yet **are insufficient** to prove credentials were actually verified through `AuthenticationManager`.

### 5.2. Wrong password or unknown username

Test `wrongPasswordFailsAuthentication` uses a valid username with a bad password; `unknownUsernameHasSamePublicFailureOutcome` uses a missing username. Both must:

- Go to `/login?error`, rather than being mistaken for success just because they return 302.
- Satisfy `unauthenticated()` with no authenticated principal.
- Not create `ROLE_USER` privileges or a usable login session.

Depending on provider/configuration, `UsernameNotFoundException` may be masked as `BadCredentialsException` to limit account enumeration. **Do not require "the response must state the user does not exist"** on a public API. In black-box tests, response equivalence is observed via redirect/status and authentication outcome; in production, also review body/message/headers, rate limits, and response timing if user enumeration matters.

**A wrong username is not a missing permission:** bad credentials stop authentication; missing permissions happen after an identity is accepted.

### 5.3. Unusable accounts: disabled, locked, and expired

Test `unusableAccountCannotLogIn` supplies the **correct password** for each account whose state is disallowed. Using the right password is intentional and critical: the test must prove the account state itself blocks login, unmasked by a wrong-password error.

| `UserDetails` flag | Valid meaning when `true` | Builder denial example |
| --- | --- | --- |
| `isEnabled()` | Account is enabled for use | `disabled(true)` |
| `isAccountNonLocked()` | Account is not locked | `accountLocked(true)` |
| `isAccountNonExpired()` | Account has not expired | `accountExpired(true)` |
| `isCredentialsNonExpired()` | Credentials have not expired | `credentialsExpired(true)` |

Corresponding errors in standard providers typically belong to `DisabledException`, `LockedException`, `AccountExpiredException`, and `CredentialsExpiredException`, all subclasses of `AuthenticationException`. The order of checking account vs credential flags can vary by provider; never rely on internal exception names to build overly specific client messages.

Test `accountStateFlagsAreConfiguredAsExpected` inspects `UserDetails` directly to ensure the demo accounts **genuinely carry invalid states**. Yet that test alone **is not enough**: if the authentication mechanism ignored status flags, the data test would still pass while login broke. Thus you need both **state-configuration** tests and **login-rejection** tests.

The `disabled`/`locked` flags in the example are static states built via `UserDetails`. They **do not automatically implement lockout after N failed password attempts**. If real requirements call for lockout, attempt counters, cooldowns, or admin unlock, that is a separate operational mechanism needing storage/services, race-condition protection, and additional tests.

## 6. Distinguishing login failure, authorization failure, and CSRF failure

### Login failure: redirect to `/login?error`

In form login, `AuthenticationFailureHandler` runs after authentication fails; `SecurityContext` is cleared appropriately, and the browser is redirected back to the login page. Because the example configures `failureUrl("/login?error")`, both bad passwords and disabled/locked/expired accounts produce the same redirect path.

**Do not define "login failure always returns 401"**: that is common for HTTP Basic/Bearer APIs, not inherent to form login. Nor should you define "any 302 redirect means success"; always assert destination and security context.

### Login succeeded yet lacking permission: 403

Test `loggedInUserStillCannotAccessAdminOnlyUrl` logs in as `active`, grabs the session, and calls `GET /admin`. Because the account only has `ROLE_USER`, Spring Security rejects the request—normally with 403. This proves **authorization**, without contradicting that login succeeded.

Test `adminCanAccessAdminOnlyUrlAfterLogin` is the positive control: the same endpoint with `ROLE_ADMIN` returns 200 and body `admin-only`. Without a positive control, a 403 test could pass simply because a misconfiguration blocks the endpoint for everyone.

### POST missing CSRF: 403 before password check

Spring Security's CSRF protection applies by default to non-"safe" HTTP methods in Servlet apps; form login submits via POST and needs a valid token. The `formLogin()` helper from `spring-security-test` **automatically generates a valid CSRF token**, so valid/invalid login tests reach authentication instead of stopping at CSRF.

Test `postLoginWithoutCsrfIsRejectedBeforePasswordCheck` intentionally uses:

```java
mvc.perform(post("/login")
        .param("username", "active")
        .param("password", "active-pass"))
    .andExpect(status().isForbidden())
    .andExpect(unauthenticated());
```

This is a **test fragment belonging to the class in section 4**, not a standalone Java file. It demonstrates a 403 coming from CSRF, **not proving the password was rejected**. For manual POSTs in MockMvc:

```java
mvc.perform(post("/login")
        .with(csrf())
        .param("username", "active")
        .param("password", "active-pass"));
```

This snippet requires static import `SecurityMockMvcRequestPostProcessors.csrf`, plus `MockMvc` and result assertions in test context. Never disable `csrf` just to make login tests pass; send a valid token like a browser or use the helper. When browsers load the default `GET /login` page, Spring Security renders the form with CSRF support; for custom login pages, developers must supply the form token properly.

## 7. Testing mistakes that easily lead to wrong conclusions

| Mistake | Why it is dangerous | How to check / improve |
| --- | --- | --- |
| Asserting only `status=302` | Both success and failure redirect | Assert both `redirectedUrl` and `authenticated()/unauthenticated()` |
| Using `@WithMockUser` to prove passwords work | Mock user attaches to request without running password auth | Use `formLogin()` or real HTTP requests through filters |
| Testing wrong password on a disabled user and claiming disabled was tested | Fails to separate password errors from account state | Use the **correct password** for disabled accounts |
| Omitting CSRF on `POST /login` | Tests can hit 403 before the authentication filter runs | Use `formLogin()` or `.with(csrf())` |
| Setting `.csrf(csrf -> csrf.disable())` in tests when production enables CSRF | Tests no longer reflect the real security chain | Keep real config or state scope clearly if using a special test setup |
| Asserting redirect without testing the session afterward | Can miss bugs persisting `SecurityContext` | Reuse `MockHttpSession` and call a login-protected endpoint |
| Testing disabled only with `isEnabled() == false` | Data is right yet provider might still ignore the flag | Also test a rejected login request |
| Lacking a positive control | 403/redirect might stem from config blocking everyone | Test an active account/matching role succeeding |
| Sharing sessions across tests | Failing test may inherit a user from an earlier test | Create an independent session per test |
| Hardcoding detailed "account is locked" messages on the login page | Easily leaks username existence/status | Use a generic public message and log internal reasons safely |
| Mocking all of `UserDetailsService` in integration tests | Skips real account-state/encoder wiring | Test end-to-end through real beans; mock only needed dependencies |
| Storing plaintext passwords in production stores | Security risk and skips real hashing | Use `PasswordEncoder` and stored hashes |
| Treating GET `/login` returning 200 as login proof | Login page renders for anonymous callers | Submit the form POST and assert `Authentication` afterward |

For readability, name tests after **behavior**: `correctLoginCreatesAuthenticatedSession`, `wrongPasswordFailsAuthentication`, `unusableAccountCannotLogIn`. Avoid names like `test1`, `test2`, or packing unrelated conditions into one test so failures remain easy to diagnose.

## 8. Separating unit tests and integration tests

### Which logic suits unit tests?

If you write a custom `UserDetailsService` or a service enforcing account lockout policies, you can unit-test these conditions without HTTP:

- Existing user: returns `UserDetails` with the right username, authorities, and hash.
- Disabled user: `isEnabled()==false`.
- Locked user: `isAccountNonLocked()==false`.
- Expired account/credentials: `isAccountNonExpired()` and `isCredentialsNonExpired()` flags.
- If there is a "lock after N wrong attempts" policy: test counting, lock threshold, reset on successful login, lock expiration, and concurrent requests; none of these come built into `InMemoryUserDetailsManager`.
- If writing a custom `AuthenticationProvider`: test `supports`, valid/invalid credentials, status checks, and `null`/exception contract; verify raw passwords/tokens never appear in results.

Unit tests pinpoint internal logic quickly. They **do not** replace `formLogin()` tests through `SecurityFilterChain`, since bugs in provider registration, CSRF, failure handlers, or session storage appear only during integration.

### What are MockMvc integration tests suited for?

`@SpringBootTest + @AutoConfigureMockMvc` in the example starts the application context and security filters without opening a real server port. It works well for checking:

1. Login POST with right/wrong credentials and account flags.
2. Redirects to the right URLs on success and failure.
3. Authentication results and sessions usable on subsequent requests.
4. Protected URLs: anonymous redirected to login; authenticated user lacking role gets 403.
5. Proper handling of form login CSRF tokens.

When you need to verify HTTP `Set-Cookie`, reverse proxies, HTTPS, real browsers, `SameSite`, or session clustering, add HTTP/browser/infrastructure tests accordingly. `MockMvc` does not verify deployment config, TLS, or all browser nuances by itself.

### Testing against user enumeration

Both non-existent usernames and wrong passwords should return a **consistent public message** by design. The tests in this lesson compare statuses/redirects and authentication state. When hardening for production, consider testing response bodies, error codes, headers, log sanitization, rate limits, and response-timing effects. You do not need to pad every code path to an exact millisecond count; assess real risk and avoid exposing account status through public errors.

## 9. If the application uses HTTP Basic or API tokens

This lab chose **form login** so learners see the difference between success and failure redirects. If an app uses HTTP Basic for REST APIs, configuration and assertions must change accordingly. With HTTP Basic, you can write requests like:

```java
// Snippet for a MockMvc test with httpBasic() enabled:
mvc.perform(get("/home")
        .with(httpBasic("active", "active-pass")))
    .andExpect(status().isOk());

mvc.perform(get("/home")
        .with(httpBasic("active", "wrong-password")))
    .andExpect(status().isUnauthorized());
```

This requires static imports `SecurityMockMvcRequestPostProcessors.httpBasic`, `MockMvcRequestBuilders.get`, and `MockMvcResultMatchers.status`. It **does not belong to the form-login app in section 3**: to run as shown, `SecurityFilterChain` must enable `httpBasic(...)` and configure matching handlers.

Likewise, Bearer JWT typically checks token signature/expiration and claims rather than comparing passwords per request. For WebFlux, use `WebTestClient` and reactive security test support. Regardless of mechanism, test structure must still separate the three cases: **valid credentials + usable account**, **invalid credentials**, and **unusable account**, while also testing post-authentication access control.

## 10. Security and real-world production notes

1. **Do not leak sensitive data:** authentication failure logs can record reason codes, correlation IDs, timestamps, and sanitized identifiers, but never raw passwords, Authorization headers, bearer tokens, or session IDs.
2. **Intentional public messaging:** `/login?error` keeps a uniform message across bad username, bad password, and disabled/locked/expired; account-support workflows can share specifics only after verifying identity via an appropriate channel.
3. **Do not treat every failure as a wrong password:** data-store errors or LDAP timeouts are system failures; handle them per contract and monitor separately instead of silently turning them into "invalid password."
4. **Lockout does not exist just because an account can be marked locked:** real apps need brute-force defenses, rate limiting, credential-stuffing detection, cooldowns, and audited unlock workflows.
5. **Form login and sessions:** check session fixation protection, session timeouts, logout, remember-me, and `SecurityContext` persistence. Avoid implicit test dependencies on stale sessions; log in cleanly per test.
6. **CSRF:** POST-based form login requires valid CSRF. With cookies and browsers, never disable CSRF without justification; distinguish CSRF 403 from authorization 403.
7. **PasswordEncoder:** use BCrypt/PBKDF2/scrypt/Argon2 per system policy; test fixtures should hash passwords with `PasswordEncoder`. Never use `{noop}` as a model for production behavior.
8. **MFA/passkeys/OIDC:** passing password verification is only one stage when multi-factor flows are required; tests must cover intermediate pending states and final completion. Never assume username/password suffices for every system.
9. **Test data:** never use production passwords or real user data; seed deterministic fixtures, isolate each test, and clean up mutated state clearly.
10. **Production-like security configuration:** with multiple `SecurityFilterChain`s or `securityMatcher`s, tests must confirm requests hit the intended chain. A `@WithMockUser` in a test cannot replace evidence that authentication filters/providers are properly configured.

## 11. Practice exercises

1. If you only have `mvc.perform(formLogin(...)).andExpect(status().isFound())`, why can't you conclude login succeeded?
2. When user `active` sends a wrong password, which matchers prove failure better than a lone status assertion?
3. Why must the `disabled` case use the **correct** password to test account status?
4. What does `UserDetails.isAccountNonLocked() == false` mean? Compare it with builder `accountLocked(true)`.
5. If a login request has valid username/password yet misses the CSRF token, why does 403 not mean the password was rejected?
6. After successful login, how in `MockMvc` do you verify a follow-up `GET /home` receives the identity from the session?
7. Why can't `@WithMockUser(username="active")` prove BCrypt/password checking works?
8. Why can user `active` still receive 403 when accessing `/admin`, and how does that differ from `AuthenticationException`?
9. How do you detect a "disabled login denied" test passing only because the system blocks **every** account? Which positive control is needed?
10. If you truly want to lock a user after five consecutive failures, does putting `.accountLocked(true)` in test data test that policy? Which additional scenarios are needed?
11. If switching to HTTP Basic, how do status and redirect assertions change across the three main cases?
12. What extra checks are needed if login involves CAPTCHA, MFA, or an external identity service?

**Solutions guide:** (1) both success and failure return 302; (2) `redirectedUrl("/login?error")` + `unauthenticated()`; (3) isolates the account-status cause; (4) `false` means the account is locked; (5) error occurs in `CsrfFilter`; (6) grab `MockHttpSession` from login and reuse it; (7) mock user bypasses password verification; (8) authentication succeeded, authorization lacked role; (9) a valid-login + resource-access test returning 200; (10) need counting logic, locking, unlocking, timestamps, and concurrency tests; (11) Basic typically returns 200 on valid requests, 401 on invalid credentials/unusable accounts, with no failure redirect; (12) design tests matching each additional step of the authentication flow.
