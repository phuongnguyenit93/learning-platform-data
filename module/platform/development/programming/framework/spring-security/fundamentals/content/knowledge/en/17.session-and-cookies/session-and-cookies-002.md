# Session ID, Session Cookie, and Server-Side Stored Data

When a web application needs to remember a logged-in user or keep a shopping cart across multiple HTTP requests, the server can create a **session** and issue a **Session ID** to the browser. The browser typically sends this ID back via a **session cookie**, while the data associated with the session is managed on the server. This is the foundation for understanding session-based login in Servlet applications and Spring Security.

After this lesson, you should be able to clearly distinguish Session ID, cookie, and session data; describe the lifecycle of a session; use `HttpSession` in Servlets; and recognize risks such as session hijacking, session fixation, CSRF, and cookie misconfiguration.

## 1. Three Commonly Confused Concepts

| Component | Where does it live? | Function | Example |
|---|---|---|---|
| **Session ID** | An identifier value issued by the server; usually appears in a browser cookie | Helps the server look up the corresponding session; must be unpredictable and carry no business meaning | `JSESSIONID=R8eK2p...` |
| **Session cookie** | Stored by the browser per cookie rules and sent on matching requests | The usual transport mechanism for passing the Session ID between browser and server | `Cookie: JSESSIONID=R8eK2p...` |
| **Session data** | Stored or managed on the server side: memory, distributed session store... | Holds state tied to a session | `userId`, shopping cart, `SecurityContext` when an appropriate mechanism is enabled |

**Key point:** A typical `JSESSIONID` cookie **only contains the ID**, not the entire user object, password, authorities, or shopping cart. The server uses the received ID to look up session state. A cookie *can* hold data or tokens under other designs, so you must not conclude that every cookie is a Session ID.

A Session ID is **not** a user ID: one user can have multiple sessions across multiple browsers or devices; a session can also exist before logging in. The Session ID is merely a lookup key and does not by itself prove that the user has successfully authenticated.

## 2. Why Do We Need Sessions if HTTP Does Not Store State?

HTTP processes each request independently. Looking solely at isolated requests, the server does not automatically know that two requests came from the same usage session. The session mechanism adds that link:

1. When state needs to be stored, the application or servlet container creates a session with an unpredictable ID.
2. The server stores data for that session and sends a cookie carrying the ID to the browser, usually via the `Set-Cookie` header.
3. The browser stores the cookie and automatically sends `Cookie` on subsequent requests that satisfy domain, path, HTTPS, and SameSite conditions.
4. The server receives the ID, looks up the still-valid session, and reads or updates data in the session.
5. The session can expire due to inactivity, be invalidated upon logout, or have its ID rotated during certain security operations.

Illustrative HTTP example after a successful login:

```http
HTTP/1.1 302 Found
Location: /profile
Set-Cookie: JSESSIONID=demoR8eK2p; Path=/; Secure; HttpOnly; SameSite=Lax
```

Subsequent request sending the matching cookie:

```http
GET /profile HTTP/1.1
Host: app.example.test
Cookie: JSESSIONID=demoR8eK2p
```

The value `demoR8eK2p` is for illustration only; a real ID must be generated by the system with sufficiently strong randomness. The `Set-Cookie` header contains attributes such as `Path`, `Secure`, `HttpOnly`, and `SameSite`; the request `Cookie` header sends only name–value pairs. A cookie might also not appear yet if an endpoint does not need to create a session.

With standard Servlet containers, the default cookie name is usually `JSESSIONID`. This name **can be configured differently**; for example, an application using Spring Session may use the `SESSION` cookie. Therefore, do not write business logic that hardcodes a specific cookie name if the system allows changing it.

## 3. How Is Data Actually Stored and Looked Up?

You can picture the server-side session store as follows:

```text
Browser A
  Cookie: JSESSIONID=S-A
                         Server / session store
                         S-A -> { userId: "u42", cartCount: 3 }
                         S-B -> { userId: "u99", cartCount: 1 }
Browser B
  Cookie: JSESSIONID=S-B
```

Browser A does not receive the `{ userId, cartCount }` object just because the server stores that object; it only carries the key `S-A`. If session `S-A` is deleted or expires, resending the old ID will not recover the old data.

The following standalone Java 17 example merely **simulates the lookup** to clarify the boundary between the cookie and the data store. It does not replace `HttpSession` or the servlet container's secure Session ID generator.

File `SessionLookupDemo.java`:

```java
import java.util.HashMap;
import java.util.Map;

public class SessionLookupDemo {
    public static void main(String[] args) {
        Map<String, Map<String, String>> serverSessions = new HashMap<>();
        String demoSessionId = "demo-123";
        serverSessions.put(
                demoSessionId,
                Map.of("userId", "u42", "cartCount", "3")
        );

        String cookieHeader = "JSESSIONID=" + demoSessionId;
        String receivedId = cookieHeader.substring("JSESSIONID=".length());
        Map<String, String> state = serverSessions.get(receivedId);

        System.out.println("Cookie: " + cookieHeader);
        System.out.println("userId on server: " + state.get("userId"));
        System.out.println("cartCount on server: " + state.get("cartCount"));
        System.out.println("Does Cookie contain userId? " + cookieHeader.contains("userId"));
    }
}
```

Run with JDK 17 or higher:

```bash
javac SessionLookupDemo.java
java SessionLookupDemo
```

Exact output:

```text
Cookie: JSESSIONID=demo-123
userId on server: u42
cartCount on server: 3
Does Cookie contain userId? false
```

The program uses a fixed ID so the output is easy to verify. A real application **must not** use `demo-123`, sequential IDs, or predictable data as a Session ID; the servlet container manages ID generation and control.

## 4. `HttpSession` in a Servlet Application

In the Servlet API, `jakarta.servlet.http.HttpSession` is the interface for manipulating session data. With Spring Boot 3 and Spring MVC, Servlet packages use `jakarta.servlet.*`, not the legacy `javax.servlet.*`.

Important operations:

| Call | Meaning |
|---|---|
| `request.getSession()` | Gets the existing session or **creates a new session** if none exists |
| `request.getSession(false)` | Gets only the existing session; returns `null` if no valid session exists |
| `session.getId()` | Gets the current Session ID |
| `session.setAttribute(name, value)` | Writes server-side session data |
| `session.getAttribute(name)` | Reads session data |
| `session.removeAttribute(name)` | Removes an attribute from the session |
| `session.invalidate()` | Invalidates the current session; the old ID can no longer look up that session |
| `session.setMaxInactiveInterval(seconds)` | Sets the maximum inactive interval before the session expires |

Example Servlet controller using a session to count visits. This code is meant for a **Spring Boot Web MVC project with Servlet/Spring Web dependencies**, not a standalone Java program:

```java
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class VisitController {
    @GetMapping("/visits")
    public String visits(HttpServletRequest request) {
        HttpSession session = request.getSession();
        Integer previous = (Integer) session.getAttribute("visits");
        int current = previous == null ? 1 : previous + 1;
        session.setAttribute("visits", current);
        return "Session visits: " + current;
    }
}
```

If the same browser calls `/visits` twice, sending back the valid cookie while the session has not expired, the responses are `Session visits: 1` and `Session visits: 2`, respectively. Another browser with a different session will have its own counter. This example illustrates storing state; the read–increment–write operation is **not safe under concurrent requests**, so do not use this naive counter pattern for data requiring consistency in production.

If you only need to check whether a session already exists, use `request.getSession(false)` to avoid accidentally creating a session on every request:

```java
HttpSession session = request.getSession(false);
if (session == null) {
    // No valid session yet: handle per endpoint requirements.
}
```

Do not store raw passwords, long-lived secrets, or overly large objects in the session. Session data consumes memory/storage capacity; in a multi-instance cluster, keeping sessions only in one instance's RAM can cause requests routed to another instance to miss the state. You can use a session-sharing mechanism like Spring Session backed by an appropriate store, or a load-balancing architecture designed for stateful sessions.

## 5. How Does Spring Security Use Sessions to Maintain Login?

In a **Spring Security Servlet** application using stateful authentication, a successful authentication result is typically represented by an `Authentication` inside a `SecurityContext`. Depending on the `SecurityContextRepository` configuration, the context can be stored in `HttpSession` (for example, `HttpSessionSecurityContextRepository`, using the `SPRING_SECURITY_CONTEXT` attribute). Subsequent matching requests can read the context back from the session to know the user is authenticated.

Conceptual processing flow:

1. The user authenticates through the mechanism configured by the application, such as form login.
2. Spring Security establishes a valid `Authentication` and the appropriate login mechanism persists the security state when needed.
3. The browser sends the Session ID in a cookie on subsequent requests.
4. The security filter uses the configured repository to obtain the `SecurityContext`, then applies authorization rules.
5. Upon logout or when the session is no longer valid, the old session's context is no longer used to authenticate new requests.

**Not every Spring Security application stores login in `HttpSession`.** APIs using Bearer tokens and a stateless policy can authenticate each request from the token without reading an HTTP session's `SecurityContext`. Even in a stateful application, calling `getSession()` only creates a session; that action **does not log the user in** on its own.

Basic configuration example for Spring Security 6 on Servlet (inside a Spring Boot application, with imports):

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {
    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/visits").permitAll()
                        .anyRequest().authenticated())
                .formLogin(Customizer.withDefaults())
                .sessionManagement(session -> session
                        .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED))
                .build();
    }
}
```

`IF_REQUIRED` allows Spring Security to create a session when the security mechanism needs one; it is also the typical policy for session-based applications. The example configuration does not disable CSRF. Understand the session creation policies:

- `ALWAYS`: Spring Security proactively creates a session.
- `IF_REQUIRED`: creates one only when needed.
- `NEVER`: Spring Security does not create a new session, though it may use an existing one.
- `STATELESS`: Spring Security neither creates nor uses `HttpSession` to obtain `SecurityContext`; other application code can still explicitly call Servlet APIs to create a session, so do not interpret it as guaranteeing the entire system never has a session.

Spring Security 6 uses configurable mechanisms to save `SecurityContext`; if you write a custom login flow and manually set `Authentication` in `SecurityContextHolder`, placing it only into the thread-local does not guarantee the login is retained on the next request. You must save the context via the appropriate `SecurityContextRepository` or use the framework's built-in authentication mechanisms.

## 6. Cookie Attributes Determine Scope and Protection Level

| Attribute | Meaning and usage |
|---|---|
| `HttpOnly` | Regular JavaScript cannot read the cookie via `document.cookie`; reduces the chance of stealing the ID via XSS, though it does not stop XSS from sending requests on the user's behalf |
| `Secure` | The browser only sends the cookie over HTTPS connections (localhost exceptions/details vary by browser); should be enabled in HTTPS deployments |
| `SameSite=Lax` | Reduces sending cookies on certain cross-site requests; usually suitable for many typical web applications |
| `SameSite=Strict` | Stronger cross-site restriction, which can affect redirect flows and login UX |
| `SameSite=None` | Allows sending in appropriate cross-site contexts; modern browsers require pairing it with `Secure` |
| `Path`, `Domain` | Restricts which URL paths/hosts receive the cookie; avoid broadening scope unnecessarily |
| `Max-Age` / `Expires` | Controls how long the browser keeps the cookie; not synonymous with how long the server session remains valid |

Example Spring Boot configuration for the servlet container's session cookie, applied when the application is served over HTTPS:

```properties
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=lax
server.servlet.session.timeout=30m
```

`server.servlet.session.timeout` is the server-side session inactivity timeout (enforcement can depend on the container), whereas `cookie.max-age` if configured is the browser-side cookie retention policy. They are **two separate lifecycles**: if the browser has a cookie but the server has removed the session, the request is still not treated as logged in. Likewise, deleting the cookie from the browser does not immediately delete the session record on the server at that moment.

`Secure` in an HTTPS environment is very important; if enabled when testing over plain HTTP, the browser may refuse to send the cookie, causing requests to keep creating new sessions. When running behind a reverse proxy/ingress, HTTPS and forwarded headers must be configured properly per the infrastructure so the server knows the connection scheme. Never blindly trust any `X-Forwarded-*` headers from untrusted sources.

## 7. Session Lifecycle: Creation, ID Rotation, Expiration, and Logout

**Session creation:** On the first request requiring a session, the container generates an ID and the initial session data may be empty. Do not assume that simply visiting a website always produces a `JSESSIONID` cookie.

**Rotating Session ID on login:** Session fixation occurs when an attacker tricks a victim into using a Session ID already known to the attacker and then waits for the victim to log in. A crucial safeguard is **changing the Session ID upon successful authentication**. In modern Spring Security Servlet, `changeSessionId` is the protection mechanism typically applied by default when available; this method rotates the current session's ID while usually preserving session attributes. Do not build an ad-hoc ID rotation flow when the framework already provides it.

**Inactivity expiration:** Sessions typically have an idle timeout. Once expired, the old ID can no longer look up the previous state. The server may create another session if the next request needs one, meaning the browser may receive a new ID cookie. This is distinct from explicit logout and distinct from the cookie's retention duration.

**Logout:** In session-based applications, proper logout must clear authentication state and invalidate the session per the applicable policy; with Spring Security form login, the default logout handler typically invalidates `HttpSession`. At the same time, the browser cookie can be cleared by configuration to reduce confusion. Clearing the cookie on the client side alone is not enough to guarantee the session has been revoked on the server if the old ID was previously stolen.

**Multiple tabs or multiple devices:** Tabs sharing the same browser profile normally share cookies within the same scope and thus share the session; two devices or separate profiles usually have different Session IDs. Logging out of one session does not automatically revoke all other sessions for the same account unless the application implements such a mechanism.

## 8. Security Risks and Rules to Remember

1. **Session hijacking:** Anyone holding a still-valid Session ID can impersonate the session under the right conditions. Always use HTTPS, prevent leaking IDs in logs/URLs, set `HttpOnly`, `Secure`, an appropriate `SameSite` policy, and protect the application from XSS. Never treat a Session ID as public data.
2. **Session fixation:** Change the ID after login; never accept a fixed client-chosen ID and treat it as an authenticated session.
3. **CSRF:** With cookie-based authentication, the browser can automatically attach cookies to requests. `HttpOnly` **does not prevent CSRF**, and `SameSite` does not replace all defenses. Keep appropriate CSRF protection for state-changing operations; Spring Security Servlet enables CSRF by default unless configured otherwise.
4. **Authorization:** The existence of a session only proves a session exists, not that the user has permission. Access rights must be determined from trusted authentication state and checked on each resource.
5. **Session data:** Store the minimum necessary, avoid storing unnecessary credentials/secrets; account for concurrent updates, serialization, and timeouts, especially in distributed setups.
6. **CORS / cross-origin cookies:** If the frontend calls an API on a different origin, sending cookies also depends on request `credentials`, CORS responses, and cookie policies. Do not carelessly open credentialed CORS to all origins.

Watch out for the fallacy **"having `JSESSIONID` means logged in"**: an anonymous request can still have a session to hold a shopping cart or CSRF state. Checking only the Session ID is not checking `Authentication`.

## 9. How to Observe with Developer Tools

On a Servlet application you have permission to test, you can verify the exact mechanics without reading secret data:

1. Open **Network** and visit an endpoint known to create a session, such as `/visits` in the example above. Check the `Set-Cookie` response header. If the header does not appear, verify whether the endpoint actually creates a session or if a valid session already existed.
2. Under **Application / Storage → Cookies**, inspect name, domain, path, `Secure`, `HttpOnly`, `SameSite`, and expiration; do not share the real ID value in screenshots or logs.
3. Send the next request from the same browser profile; in Network, observe the `Cookie` request header. If the cookie is right and the server session is still valid, `/visits` will increment the visit count.
4. Open a private window or clear the corresponding cookie; the new request normally starts a different session when the endpoint needs one. Test logout/expiration to observe that the old ID no longer grants the authenticated state.
5. In multi-instance environments, test instance-switching scenarios and verify that the shared session store or routing strategy meets the design.

To inspect cookies from the command line in a test environment with an appropriate real URL, `curl -c cookies.txt` saves cookies from the response and `curl -b cookies.txt` sends them back. Use the appropriate endpoint and scheme (HTTP/HTTPS), and note that `Secure` cookies are only sent over HTTPS. The cookie file may contain an active Session ID, so protect it and delete it after testing.

## 10. Quick Comprehension Check

- Browser has `JSESSIONID`, but does not send it in the request due to `Path`, `SameSite`, or `Secure`: the server will not receive the ID via cookie on that request, so it cannot use it to look up the session via that channel.
- Browser sends the right ID, but the session on the server has expired: the cookie cannot restore the old session.
- Two requests send the same ID while the session is still alive: in principle they point to the same session; concurrent update issues still need to be handled.
- Changing the Session ID after login helps prevent fixation; this is different from assigning a new user ID.
- A stateless API authenticating with Bearer tokens is not synonymous with `JSESSIONID` cookie-based login; you must read the active authentication configuration.

**Remember:** `Session ID` is the lookup key, **the session cookie is the transport vehicle for the key**, and **session data lives and is managed on the server**. Spring Security only considers a user authenticated when the security mechanism restores or verifies a valid `Authentication`, not simply because the browser holds a session cookie.
