# Do Not Log Passwords, Return Them in Responses, or Publish Them in Test Data

## 1. The Problem: Passwords Can Leak in Seemingly Harmless Places

A Spring Boot application can store passwords properly with BCrypt and still leak passwords when a developer turns on debug logging, prints a request object, returns a full `User` entity from an API, or commits test fixtures containing real credentials. In many systems, logs and test artifacts are shipped to services accessible to far more people than the production database. Protecting the `password_hash` table is therefore only part of protecting credentials.

Suppose a login endpoint accepts a username and password. A developer might accidentally write:

~~~java
// ANTI-PATTERN: never include this in deployed code.
log.debug("Login input: {}", loginRequest);
log.info("Credentials: {}", authentication);
return ResponseEntity.ok(userEntity);
~~~

The issue is not merely whether a log statement contains the word “password”:

- **`loginRequest.toString()`** generated by a Java record, Lombok, or an IDE can print every field, including the password.
- **`Authentication`** may hold credentials, principal, or details; depending on the implementation, stringifying it can expose sensitive data.
- **`UserEntity`** often contains `passwordHash`, personal data, and JPA relationships; Jackson can serialize public getters.
- An exception, HTTP debugging filter, or APM plugin may capture request bodies and headers even when the Controller logs nothing.
- Test or CI reports can print command-line arguments, environment variables, HTTP exchanges, failure diffs, screenshots, HAR files, or fixtures containing passwords.

**Core principle:** raw passwords, password hashes, reset tokens, access/refresh tokens, API keys, session cookies, and verification codes are **secrets or sensitive credentials**. Send or store them only where strictly needed for authentication within their proper lifecycle; never let them leak into **logs, public HTTP responses, shared source/test fixtures, or downloadable build artifacts**.

This lesson belongs to **Spring Security – Fundamentals → Passwords**. Examples use **Java 17+, Spring Boot 3.x, Spring Security 6.x, Spring MVC/Servlet, SLF4J, and MockMvc**. The text clearly distinguishes runnable project code from illustrative snippets. Neither real passwords nor fixed sample passwords are used in source code or `curl` commands.

### After This Lesson, You Can

1. Identify password leak surfaces across Controllers, filters, services, logging configs, proxies, APMs, and CI.
2. Explain why **password hashes must still never be treated as public data**.
3. Design allowlisted response DTOs instead of returning raw `Authentication`, `UserDetails`, or entities.
4. Log authentication events using **event type, outcome, and safe request IDs** without logging raw credentials.
5. Avoid pitfalls of `toString`, Java records, Lombok `@Data`, `exception.getMessage()`, and HTTP request/response body logging.
6. Build a Spring Boot example receiving demo credentials from runtime configuration so source contains no real passwords or static fixtures.

8. Recognize the limits of testing, and also audit reverse proxies, central logging, tracing, CI reports, and test-data exports.
9. Design secret scanning, credential rotation workflows, and incident response when a credential leak is discovered.
10. Understand that credential protection spans the full path from receiving a request to purging test data.

## 2. Data Classification: What May Be Stored or Emitted Where?

| Data | Purpose | Log? | Return in Response? | Commit to Repo? |
| --- | --- | --- | --- | --- |
| Raw password | Prove the user knows the secret | **No** | **No** | **No** |
| Encoded password/BCrypt hash | Provider verifies candidate passwords | **No** | **No** | Avoid real hashes; tests use ephemerally generated values only |
| Password reset token | Verify a password reset request | **No** | Never echo in a way that leaks the token | **No** |
| OTP/MFA recovery code | Complete a secondary verification step | **No** | Deliver only via controlled channels and protocols | **No** |
| Access token/refresh token | Access proof or token renewal | **No** | Only on issuance endpoints per protocol; never echo arbitrarily | **No** |
| Session cookie/session ID | Bind an authenticated session | **No** | Issued via secure HTTP cookie mechanisms, never embedded casually in JSON | **No** |
| Username or email | Look up account identity | Restricted, per personal-data policy | Conditionally | Never use real user data |
| Internal user ID | Distinguish users/authorization | Conditionally; not a secret, yet may be personal data | Only when the client needs it | Synthetic IDs permitted when unlinked from real people |
| Server-generated Request ID | Incident investigation and log correlation | Normally yes | May be included per API contract | Yes, if free of secrets |
| Event category: auth.failure | Security activity analysis | **Recommended** | May be a public error code if appropriate | Yes |
| HTTP status 200/401/403 | Observe request outcomes | **Recommended** | Per protocol | Yes |
| Exception details/stack trace | Internal troubleshooting | Controlled, with redaction | **No** on public APIs | Never store artifacts containing secrets |

The “never return in response” entries refer to **public APIs or responses not designed to issue credentials**. For example, a token-based login protocol **intentionally issues an access token** after authentication; that is an explicit security contract backed by TLS, scopes, expiration, and proper client storage. Never conclude “every response carrying a token is wrong”; what is wrong is **accidentally echoing secrets into other APIs, logs, or public test output**.

### 2.1. Password Hashes Remain Sensitive

BCrypt/Argon2/PBKDF2 hashes are not plaintext and must never serve as raw passwords in normal logins. Yet if hashes leak, attackers can attempt offline password guessing, exploit weak passwords, or correlate breaches across services. Therefore:

- Databases must restrict read access to the `password_hash` column.
- Backups must be encrypted with strict download/view controls.
- Never print hashes just to “see whether the encoder worked.”
- Never return hashes in DTOs, GraphQL schemas, debug endpoints, or routine admin exports.
- Never push hashes onto event buses, queues, or caches just for frontend convenience.
- To test encoding logic, test `matches` and format/algorithm IDs rather than printing full hashes to the console.

### 2.2. Do Not Treat Base64 or Reversible Encoding as Redaction

HTTP Basic uses `Base64(username:password)`. Base64 decodes directly. Logging the full `Authorization: Basic` header is equivalent to logging reusable credentials. Logging a JWT/Bearer token while masking only the first few characters may still fail to protect it if the remaining portion stays usable or leaks claims.

**Redaction** means removing or replacing sensitive values before they reach logs or responses—not merely encoding them into another representation.

## 3. Spring Security Flow and Potential Leak Points

~~~text
Client submits credentials
       |
       v
Servlet container / reverse proxy
       |     Risk: access logs capturing full URL/query, headers
       v
FilterChainProxy / authentication filter
       |     Risk: request/response dumps, Authorization, body
       v
AuthenticationManager / AuthenticationProvider
       |     Risk: debugging credentials, exception details
       v
UserDetailsService / PasswordEncoder / database
       |     Risk: logging SQL params, hashes, entity.toString
       v
Authentication / SecurityContext
       |     Risk: serializing principal, details, tokens
       v
Controller / business service
       |     Risk: responses returning entities, broad DTOs
       v
HTTP response / API gateway / frontend
       |     Risk: error bodies, browser console, HAR
       v
Monitoring, APM, logging collector, CI/test artifacts
             Risk: copying data across multiple stores
~~~

In Spring Security, **`UserDetailsService`** supplies `UserDetails`, which can include the password hash for `DaoAuthenticationProvider`. **`PasswordEncoder.matches(raw, storedHash)`** verifies credentials. After authentication, **`Authentication`** holds identity/authority data, and the framework includes credential-erasure mechanisms. Even so, you must never assume every copy of a raw password or hash vanishes from every layer.

Do not rely on **`Authentication.toString()` “usually hiding credentials”** as a safety guarantee: custom principals, details, or custom implementations may still carry sensitive data, and framework upgrades can change formatted output.

### 3.1. Key Boundaries

1. **Request boundary:** Receive the password to verify it; never register it as data for logging or analytics.
2. **Authentication boundary:** Use credentials only where needed; providers should not pass raw passwords into business Controllers.
3. **Response boundary:** Emit only allowlisted DTOs; never serialize framework objects.
4. **Observability boundary:** Log only fields vetted and classified as safe.
5. **Test/build boundary:** Use ephemeral credentials in tests, keeping them out of stdout, reports, screenshots, and public fixture libraries.

## 4. Logging Properly: Useful Events Without Secrets

A system still needs to log **authentication successes/failures, denied access, suspected brute force, role changes, and infrastructure errors** to detect incidents. “Never log passwords” does not mean disabling security logging.

### 4.1. Dangerous Logging Patterns

~~~java
// ANTI-PATTERN: all statements below must be avoided.
log.debug("login request={}", loginRequest);
log.info("password={}", rawPassword);
log.warn("authentication={}", authentication);
log.error("failed: {}", exception.getMessage());
log.trace("request headers={}", headers);
log.debug("saved user={}", userEntity);
~~~

Even if code does not explicitly write a password literal, a `toString()`, exception message, or header map can contain secrets. Never let a logging framework decide which fields are safe on your behalf.

### 4.2. Allowlist-Based Logging

Instead, construct events with fixed, policy-approved fields:

~~~java
// Example inside a service using SLF4J.
private static final Logger log =
    LoggerFactory.getLogger(LoginAudit.class);

void loginRejected() {
    log.warn("event=authentication_failed outcome=rejected");
}

void accessGranted() {
    log.info("event=protected_resource_access outcome=success");
}
~~~

This is a **snippet**, not a standalone Java file; it requires the `LoginAudit` class and `org.slf4j.Logger`/`LoggerFactory` imports. The key rule is **never passing raw passwords, hashes, request DTOs, or tokens into logger placeholders**.

Real systems can add a **server-generated correlation ID**, route template, and policy outcome. Request IDs may flow through tracing, but never echo an arbitrary client-supplied ID without length/character validation, which risks log injection or breaking structured logs.

### 4.3. Choosing Events and Log Levels

| Event | Suggested Level | Safe Field Examples |
| --- | --- | --- |
| Successful login | INFO or audit pipeline | `event=auth.success`, `result=allow`, `requestId` |
| Failed login | WARN/audit depending on volume | `event=auth.failure`, `result=deny`, generic category |
| Missing role | WARN/audit | `event=authz.denied`, permission code |
| Password changed | INFO/audit | `event=credential.rotated`, `outcome=success` |
| Reset token requested | INFO/audit with rate limiting | `event=recovery.requested`, `outcome=accepted` |
| DB account lookup error | ERROR | `event=identity_store.failure`, error category, correlation ID |
| Unusual login spike | Metric/alert | failure counts per time window |

These are **suggestions**, not mandatory fixed levels. On high-traffic systems experiencing credential stuffing, logging WARN on every failed attempt can flood storage and drive up costs. Use aggregation, appropriate sampling, and dedicated audits to detect brute force without causing logging-induced DoS.

### 4.4. Allowlists Beat String Blacklists

A regex-only solution that “masks keys named `password`” misses many secrets:

- Fields named `pwd`, `passcode`, `oldSecret`, `confirmation`, or nested JSON properties.
- Headers such as `Authorization`, `Proxy-Authorization`, `Cookie`, `X-API-Key`, or `Set-Cookie`.
- Tokens embedded in URL queries, paths, exceptions, attributes, or unlabeled request bodies.
- Logging libraries stringifying objects before field masking runs.
- Stack traces containing file paths, request parameters, or values in exception messages.
- Unrelated fields into which an attacker deliberately places a password value.

**Primary rule:** build log events strictly from allowlisted fields emitted by business logic. Collector-side redaction is a fallback safety net, never the sole control.

## 5. Pitfalls in Spring Boot, Java, and Logging Frameworks

### 5.1. Java Records Auto-Generate toString

A Java record carrying a password field auto-generates a `toString` that prints that field. For example:

~~~java
record ChangePasswordRequest(
    String currentPassword,
    String newPassword
) {}
~~~

This is an **illustrative type**, not something to log. Calling `log.info("{}", request)` prints both fields. Java records do not hide sensitive data automatically.

Fix: **never log the request object**. If you truly need a custom `toString`, return masked markers only—and remember that **a safe `toString` does not replace safe JSON serialization**.

### 5.2. Lombok @Data and @ToString

Lombok can generate `toString`, `equals`, and accessors. If a request or entity class holds a password while using `@Data` or unguarded `@ToString`, other developers can easily log the entire object.

You can add `@ToString.Exclude` on sensitive fields as a secondary safeguard, yet the stronger rule is **never logging raw DTOs**, never returning entities, and never relying on a single annotation to keep secrets out of Jackson, logs, serialization, and tracing.

### 5.3. UserDetails, Authentication, and Principal

`DaoAuthenticationProvider` needs `UserDetails` containing the encoded password for verification. Spring Security tries to limit credential retention in certain `Authentication` types via **`CredentialsContainer` / `ProviderManager`**. Still:

- Custom principals may carry sensitive fields.
- Cached `UserDetails` may retain password hashes.
- `Authentication.details` can contain IPs, session metadata, or custom data.
- JWT/OIDC `Authentication` objects can reference claims and tokens.
- Custom `toString` or serializers can expose unexpected properties.

Therefore never write:

~~~java
@GetMapping("/me")
Authentication unsafe(Authentication authentication) {
    return authentication;
}
~~~

This is an **anti-pattern**. Never return `SecurityContext`, `UserDetails`, or `UserEntity` for “quick debugging.”

### 5.4. Logging HTTP Bodies and Headers

In Spring MVC, developers may add `CommonsRequestLoggingFilter`, `OncePerRequestFilter`, `ContentCachingRequestWrapper`, or interceptors to log requests/responses. For endpoints handling passwords, any configuration logging **payloads**, **`Authorization`**, **`Cookie`**, or query strings demands extreme caution.

Do not enable `includePayload`/`includeHeaders` application-wide, and never dump raw header maps into logs. For HTTP observability, prefer **method, route template, status, duration, and request ID**. Avoid query parameters for sensitive flows so tokens or reset links never land in URLs.

Reverse proxies and server access logs often record the **request target** including path and query; avoid passing secrets in query strings by API design.

### 5.5. Spring Security DEBUG/TRACE

`DEBUG` logging can be invaluable for inspecting filter chains, authentication providers, and authorization rules. However, exact log levels, messages, and third-party libraries vary across versions and configurations, so **never assume `TRACE` is safe when production traffic carries real credentials**.

When investigating an incident:

1. Use an isolated test environment and synthetic accounts.
2. Restrict log scope, level, duration, and read permissions.
3. Never dump request bodies, raw headers, passwords, or hashes.
4. Audit logging at gateways, servlet containers, APMs, and collectors.
5. Disable debug configs once investigation concludes and check log retention.

### 5.6. APM, Actuator, and Tracing

Spring Boot Actuator can record HTTP exchanges if configured and enabled. Depending on configuration, collectors may capture URIs, headers, principals, or session metadata. Third-party APM/tracing agents may also capture bodies, exceptions, or attributes automatically.

**Having no log statements in your Controller does not guarantee the system logs nothing.** Audit actual configurations across proxies, service meshes, servlet filters, Actuator HTTP exchanges, OpenTelemetry instrumentation, error reporting, and central logging.

### 5.7. Exceptions and Validation Errors

Validation layers may include a **`rejectedValue`** or field value inside an exception. If a global handler returns `exception.getMessage()` or raw binding errors verbatim, passwords can surface in HTTP error JSON.

Example to avoid:

~~~java
// ANTI-PATTERN: may expose exception details.
return ResponseEntity.badRequest()
    .body(Map.of("message", exception.getMessage()));
~~~

Return error responses with **static, context-appropriate codes/messages**, routing detailed diagnostics only to classified, redacted internal channels.

## 6. HTTP Responses: Emit Only Allowlisted Fields

### 6.1. Designing a Response DTO

An endpoint reporting login status may only need:

~~~java
record IdentityStatus(boolean authenticated) {}

@GetMapping("/me")
IdentityStatus currentIdentity() {
    return new IdentityStatus(true);
}
~~~

This snippet sits inside a `@RestController` protected by Spring Security. It needs no password, hash, email, or token to tell the frontend the request is authenticated.

A safe response in this lesson:

~~~json
{
  "authenticated": true
}
~~~

If the frontend genuinely needs a username, display name, or roles, decide each field explicitly per API contract, caller permissions, and data minimization. Never let Jackson auto-discover fields from an entity or framework object.

### 6.2. Do Not Hide Passwords in Seemingly Safe Fields

Common leak vectors:

- Echoing the login request JSON back for debugging.
- Returning `passwordHash` in `/me`, `/users/{id}`, GraphQL, or admin exports.
- Returning exception messages containing a rejected password.
- Returning reset codes/tokens in responses of endpoints not meant to issue secrets.
- Placing credentials in a `Location` header or redirect query string.
- Putting secrets in `X-Debug-*`, `Server-Timing`, or custom headers.
- Writing `ResponseEntity.ok(loginRequest)` or `ResponseEntity.ok(userEntity)` out of convenience.

Jackson annotations like `@JsonProperty(access = WRITE_ONLY)` can reduce the risk of accidental serialization, yet **they are only a secondary safeguard**: request DTOs can still be printed by `toString`, AOP, tracing, other mappers, or other JSON libraries. The primary defense is a **dedicated response DTO containing only allowlisted fields**.

### 6.3. AuthenticationEntryPoint and 401 Errors

With HTTP Basic, when credentials are missing or wrong, `AuthenticationEntryPoint` generates HTTP 401. Choose a generic public error body without echoing the client-submitted username or password.

Expected example:

~~~http
HTTP/1.1 401 Unauthorized
Content-Type: application/json
WWW-Authenticate: Basic realm="lesson"
Cache-Control: no-store

{"error":"authentication_required"}
~~~

Never use `exception.toString()` as the response body. In form login flows, use a consistent `FailureHandler`/redirect. When an authenticated user lacks permissions, that is an authorization failure—typically HTTP 403; never turn every 403 into a 401.

### 6.4. Caching, CORS, and Browsers

Personal details in `/me` or auth responses need proper caching headers; sensitive APIs typically return **`Cache-Control: no-store`**. CORS does not protect credentials if you allow untrusted origins or accidentally return sensitive data; explicitly lock down allowed origins and credentials policies.

Never put passwords in URLs, because URLs land in browser history, access logs, proxies, referrers, and analytics. Use HTTPS, send credentials in request bodies or appropriate headers per protocol, and protect browser consoles and storage too.

## 7. Runnable Spring Boot 3.x Example Without Hardcoded Passwords

This example uses Spring Boot Security with HTTP Basic. **The demo password comes from runtime configuration**, rather than putting a password literal in source code, committed property files, or `curl` commands.

The app keeps only an encoded password in `InMemoryUserDetailsManager`; the Controller returns a minimal DTO, logs one fixed event, and error handlers return static JSON. This demonstrates controls at the **application layer**; proxies, APMs, and CI must still be configured separately.

### 7.1. Project Setup and Dependencies

Create a **Java 17+, Spring Boot 3.x, Spring MVC/Servlet, Gradle Groovy DSL** project via Spring Initializr with the Gradle Wrapper. In the **`dependencies`** block of `build.gradle`:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.security:spring-security-test'
}
~~~

This is **only the dependencies section in a Boot project with plugin/BOM configured**, not a standalone `build.gradle`. `spring-security-test` provides the `httpBasic()` MockMvc request post-processor used in the tests below.

### 7.2. Complete Java Source

Create **src/main/java/com/example/credential/SafeCredentialApplication.java**:

~~~java
package com.example.credential;

import java.nio.charset.StandardCharsets;

import jakarta.servlet.http.HttpServletResponse;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpMethod;
import org.springframework.http.MediaType;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.AuthenticationEntryPoint;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class SafeCredentialApplication {

    public static void main(String[] args) {
        SpringApplication.run(SafeCredentialApplication.class, args);
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    UserDetailsService users(PasswordEncoder encoder, Environment env) {
        // Spring Boot maps DEMO_AUTH_PASSWORD to demo.auth.password.
        String password = env.getRequiredProperty("demo.auth.password");

        if (password.isBlank()) {
            throw new IllegalStateException(
                "Missing local demo credential");
        }

        return new InMemoryUserDetailsManager(
            User.withUsername("demo-user")
                .password(encoder.encode(password))
                .roles("USER")
                .build()
        );
    }

    @Bean
    AuthenticationEntryPoint genericEntryPoint() {
        return (request, response, failure) -> {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            response.setContentType(MediaType.APPLICATION_JSON_VALUE);
            response.setCharacterEncoding(StandardCharsets.UTF_8.name());
            response.setHeader(
                HttpHeaders.WWW_AUTHENTICATE, "Basic realm=\"lesson\"");
            response.setHeader(HttpHeaders.CACHE_CONTROL, "no-store");
            response.getWriter()
                .write("{\"error\":\"authentication_required\"}");
        };
    }

    @Bean
    SecurityFilterChain security(
            HttpSecurity http, AuthenticationEntryPoint genericEntryPoint)
            throws Exception {

        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/public").permitAll()
                .requestMatchers(HttpMethod.GET, "/me").authenticated()
                .requestMatchers(HttpMethod.GET, "/admin")
                    .hasRole("ADMIN")
                .anyRequest().denyAll()
            )
            .httpBasic(basic -> basic
                .authenticationEntryPoint(genericEntryPoint)
            )
            .exceptionHandling(errors -> errors
                .authenticationEntryPoint(genericEntryPoint)
                .accessDeniedHandler((request, response, failure) -> {
                    response.setStatus(
                        HttpServletResponse.SC_FORBIDDEN);
                    response.setContentType(
                        MediaType.APPLICATION_JSON_VALUE);
                    response.setCharacterEncoding(
                        StandardCharsets.UTF_8.name());
                    response.setHeader(
                        HttpHeaders.CACHE_CONTROL, "no-store");
                    response.getWriter()
                        .write("{\"error\":\"access_denied\"}");
                })
            )
            .formLogin(form -> form.disable())
            .build();
    }
}

@RestController
class SafeIdentityController {

    private static final Logger log =
        LoggerFactory.getLogger(SafeIdentityController.class);

    @GetMapping("/public")
    String publicEndpoint() {
        return "public OK";
    }

    @GetMapping("/me")
    IdentityStatus identity() {
        log.info("event=identity_view outcome=success");
        return new IdentityStatus(true);
    }

    @GetMapping("/admin")
    String adminEndpoint() {
        return "admin OK";
    }
}

record IdentityStatus(boolean authenticated) {}
~~~

This is **a complete Java file inside the created Spring Boot project**. Public class `SafeCredentialApplication` matches the filename; the Controller and record are package-private in the same package. The `PasswordEncoder` bean uses BCrypt; the `UserDetailsService` bean hashes the demo password before storing it in the in-memory store.

**There is no password literal in the Java file or `build.gradle`.** The password comes from runtime property `demo.auth.password`, which Spring Boot can bind from environment variable `DEMO_AUTH_PASSWORD`. If that configuration property is missing, the app fails fast rather than silently falling back to a default password.

### 7.3. Why Do Responses Leak No Secrets?

- `GET /me` returns `IdentityStatus(true)`, never `Authentication`, `UserDetails`, `PasswordEncoder`, or `UserEntity`.
- No getter on the response DTO exposes a raw password or hash.
- On login failure, the entry point returns a static error code instead of `failure.getMessage()`.
- When a user has the right password but lacks `ADMIN`, the handler returns static `access_denied` JSON.
- The logger emits only `event=identity_view outcome=success`, with no user, password, hash, request payload, or headers.

**Limitation:** This is application-code protection in the example. If a reverse proxy, servlet access log, or APM is configured to capture `Authorization`, headers, or bodies, secrets can still leak outside the Controller. Enforce logging policies end-to-end.

### 7.4. Running with Runtime-Supplied Credentials

Locally, supply a temporary demo password via **`DEMO_AUTH_PASSWORD`** in the process environment. Never place the value in committed `application.properties`, Gradle arguments, terminal command lines, URLs, or READMEs.

Example in **Bash** for an isolated lab session:

~~~bash
read -r -s -p "Temporary demo password: " DEMO_AUTH_PASSWORD
printf "\n"
export DEMO_AUTH_PASSWORD
./gradlew bootRun
unset DEMO_AUTH_PASSWORD
~~~

`read -s` suppresses terminal echo while typing. The environment variable still lives in the shell and app process during execution; this is a **demo** approach, not a substitute for a production Secret Manager. Stop the server after testing.

On **Windows PowerShell 5.1+**, you can read without echoing:

~~~powershell
$secure = Read-Host "Temporary demo password" -AsSecureString
$pointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try {
    $env:DEMO_AUTH_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($pointer)
    .\gradlew.bat bootRun
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($pointer)
    Remove-Item Env:DEMO_AUTH_PASSWORD -ErrorAction SilentlyContinue
}
~~~

Converting `SecureString` into a temporary environment variable means the raw password resides in process memory. Never use real data; production should use a secret store/identity provider per architecture and restrict reads of environment/process dumps. Clearing an environment variable cannot guarantee every Java `String` copy has been wiped from the JVM heap.

### 7.5. Calling curl Without Putting Passwords in Command History

With the server running on `localhost:8080`:

~~~bash
curl -i http://localhost:8080/public
curl -i http://localhost:8080/me
curl -i -u demo-user http://localhost:8080/me
curl -i -u demo-user http://localhost:8080/admin
~~~

**`curl -u demo-user`** prompts interactively for the password in the terminal when you omit the colon and password. On Windows PowerShell you may need **`curl.exe`** since `curl` is an alias. Avoid `curl -u user:password` because shell history and process listings can record the credential verbatim.

HTTP Basic encodes credentials as Base64 and **does not encrypt content**. Over real networks, require HTTPS/TLS and appropriate controls. Never reuse demo passwords on any real system.

### 7.6. Expected Results

| Request | Expected HTTP Status | Body |
| --- | --- | --- |
| `GET /public` anonymous | **200** | `public OK` |
| `GET /me` anonymous | **401** | `{"error":"authentication_required"}` |
| `GET /me` demo-user right password | **200** | `{"authenticated":true}` |
| `GET /me` demo-user wrong password | **401** | `{"error":"authentication_required"}` |
| `GET /admin` demo-user right password | **403** | `{"error":"access_denied"}` |

In the demo, `demo-user` holds only `ROLE_USER`. Therefore `/admin`, which requires `ROLE_ADMIN`, returns 403 even after password verification. If a client sends invalid credentials to `/public`, `BasicAuthenticationFilter` may also attempt authentication and return 401 before `permitAll` is reached.

This table shows **results inferred from the code**, not output captured from a live server during authoring. Actual HTTP behavior can change when adding filters, exception handlers, or proxies.

## 8. MockMvc Testing: Generating Credentials in RAM Without Committing Them

Good tests do not need to commit fixed test passwords, pass credentials via shell arguments, or print hashes to the console. With JUnit, you can **generate a temporary string via UUID at runtime**; it represents no real account and exists solely within the test context.

To test the app from section 7, create **src/test/java/com/example/credential/SafeCredentialApplicationTest.java**:

~~~java
package com.example.credential;

import java.util.UUID;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.system.CapturedOutput;
import org.springframework.boot.test.system.OutputCaptureExtension;
import org.springframework.http.HttpHeaders;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.springframework.security.test.web.servlet.request
    .SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@ExtendWith(OutputCaptureExtension.class)
class SafeCredentialApplicationTest {

    // Generated at runtime: no static secret in the repository.
    private static final String EPHEMERAL =
        UUID.randomUUID().toString();

    @DynamicPropertySource
    static void supplyCredential(DynamicPropertyRegistry registry) {
        registry.add("demo.auth.password", () -> EPHEMERAL);
    }

    @Autowired MockMvc mvc;
    @Autowired UserDetailsService users;

    @Test
    void successResponseAndCapturedLogContainNoPassword(
            CapturedOutput output) throws Exception {

        String encoded = users.loadUserByUsername("demo-user")
            .getPassword();

        MvcResult result = mvc.perform(get("/me")
                .with(httpBasic("demo-user", EPHEMERAL)))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.authenticated").value(true))
            .andReturn();

        String body = result.getResponse().getContentAsString();

        assertEquals("{\"authenticated\":true}", body);
        assertFalse(body.contains(EPHEMERAL));
        assertFalse(body.contains(encoded));
        assertFalse(output.getAll().contains(EPHEMERAL));
        assertFalse(output.getAll().contains(encoded));
    }

    @Test
    void failureResponseIsGenericAndDoesNotEchoInput(
            CapturedOutput output) throws Exception {

        String wrongPassword = UUID.randomUUID().toString();

        MvcResult result = mvc.perform(get("/me")
                .with(httpBasic("demo-user", wrongPassword)))
            .andExpect(status().isUnauthorized())
            .andReturn();

        String body = result.getResponse().getContentAsString();

        assertEquals("{\"error\":\"authentication_required\"}", body);
        assertEquals("Basic realm=\"lesson\"",
            result.getResponse()
                .getHeader(HttpHeaders.WWW_AUTHENTICATE));
        assertFalse(body.contains(wrongPassword));
        assertFalse(output.getAll().contains(wrongPassword));
    }

    @Test
    void authorizationFailureDoesNotLeakSecret(
            CapturedOutput output) throws Exception {

        MvcResult result = mvc.perform(get("/admin")
                .with(httpBasic("demo-user", EPHEMERAL)))
            .andExpect(status().isForbidden())
            .andReturn();

        String body = result.getResponse().getContentAsString();

        assertEquals("{\"error\":\"access_denied\"}", body);
        assertFalse(body.contains(EPHEMERAL));
        assertFalse(output.getAll().contains(EPHEMERAL));
    }
}
~~~

### 8.1. Running the Tests

~~~bash
./gradlew test
~~~

PowerShell: **.\gradlew.bat test**.

The test uses **`@DynamicPropertySource`** to supply `demo.auth.password` before Spring initializes `UserDetailsService` in the test context, eliminating any need for a developer environment variable. MockMvc uses `SecurityMockMvcRequestPostProcessors.httpBasic` to build the header, and `OutputCaptureExtension` captures logs/stdout/stderr observed during the test run.

### 8.2. Why Not Hardcode a Password in Tests?

`EPHEMERAL` is generated by `UUID.randomUUID` at runtime. The test injects that string into the app property and uses it for HTTP Basic calls. The repository holds only credential-generation logic—no static test passwords and no production secrets.

This **reduces the risk of exposing public test credentials**, rather than serving as a full production password generator; UUIDs suffice for in-memory test verification. When tests need real secrets such as third-party API keys or integration tokens, use a **secret manager or CI secret binding** instead of hardcoding into test fixtures.

### 8.3. What Do These Tests Prove?

- `GET /me` with valid credentials returns a DTO containing only `authenticated=true`.
- The response body contains neither the test raw password nor the encoded password from `UserDetails`.
- The wrong-password branch returns 401 and a generic body without echoing input.
- The authenticated-but-unauthorized branch returns 403 and a generic body.
- Logs captured by `OutputCaptureExtension` during these test requests contain neither the test raw password nor the stored hash.

### 8.4. What Have These Tests Not Proven?

**Very important:** output capture inspects only logs captured within the test process scope. It does not observe:

- Raw access logs of a reverse proxy or API gateway.
- Servlet container logs outside the test process.
- Telemetry recorded by production APM agents or log collectors.
- Tracing spans or baggage exported externally.
- Browser consoles, HAR captures, screenshots, or screen recordings.
- Git history and CI logs from other builds.
- Any logging path not triggered by those three test requests.

Nor does it prove the password was wiped from the JVM heap or absent from copies held temporarily for authentication. **A green test proves only the bounded paths exercised, not an absolute guarantee of secrecy.**

### 8.5. Avoid Assertions That Leak Secrets on Failure

An assertion comparing a raw password against a response body in a way that prints both expected and actual values can dump the secret into JUnit failure reports if the test fails. In our example, we use boolean `assertFalse(body.contains(EPHEMERAL))` and avoid embedding `EPHEMERAL` in assertion failure messages.

With snapshot-diff test tools, never snapshot requests containing raw passwords or full `Authorization` headers. Never attach failure screenshots of unmasked password forms.

## 9. Test Fixtures, Seed Data, and Public Artifacts

### 9.1. Why Must “Just a Test Password” Still Be Handled Carefully?

A fixed sample password committed publicly often gets copied into staging or production out of convenience. Some teams even reuse test credentials for real database connections, E2E accounts, or integration services—at which point it is no longer harmless data.

Distinguish tiers:

- **Pure unit tests:** use data generated inside the test, touching no real accounts.
- **Local integration tests:** use isolated DBs/containers, seeding users with ephemerally generated passwords.
- **Staging end-to-end tests:** use dedicated least-privilege accounts with secrets injected from CI/secret managers, rotated and torn down.
- **Production smoke tests:** use authorized identity mechanisms, keeping credentials out of test reports and screenshots.

Demo usernames, fake user IDs, and role names may appear in test data. Usable raw passwords, API keys, access tokens, and reset tokens must be treated as secrets—even in staging.

### 9.2. Avoid Often-Overlooked Test Surfaces

| Surface | Risk | Mitigation |
| --- | --- | --- |
| `src/test/resources/*.json` | Committed password literals | Generate credentials at test setup or use safe secret fixtures |
| `application-test.properties` | Hardcoded DB/API passwords | CI secret injection or ephemeral Testcontainers credentials |
| Postman collections/environments | Exported with tokens/passwords | Separate secret variables; inspect exports |
| JUnit failure reports | Assertion diffs printing sensitive values | Keep secrets out of expected/actual/messages |
| MockMvc `print()` / `andDo(print())` | Prints request headers/bodies | Never print real auth requests or mask beforehand |
| RestAssured logging | Logs full request/response | Disable or redact credentials |
| WireMock request journal | Stores `Authorization`/bodies | Bound recorded data and retention |
| Testcontainers logs | DB/container output with credentials | Avoid dumping env/config/command secrets |
| CI console | Command-line args, `echo`, `set -x` | Use secret bindings, masking, and suppress echo |
| E2E screenshots/videos | Password fields or UI tokens | Mask inputs; avoid capturing screens showing secrets |
| HAR/network recordings | `Authorization`/cookies/bodies | Sanitize or never export |
| Coverage/test artifacts | Embedded captured output | Scan reports before publishing |
| Shared sample YAML/`.env` | Passwords pushed to Git | Ignore secret files; provide key-only example files |

### 9.3. Do Not Rely on `.gitignore` for Already-Committed Files

Once Git has tracked a secret, adding it to `.gitignore` **does not remove copies from repository history or old clones**. Treat the credential as compromised: revoke or rotate it first, then address history and artifacts according to policy, permissions, and collaborator impact.

Never force-push shared repository history without a coordinated process; rewriting history disrupts existing clones and open PRs. **Rotation and revocation come first whenever a usable secret leaks**, not merely deleting a line of source code.

## 10. Infrastructure Logging and Observability

### 10.1. Reverse Proxies and Ingress

Reverse proxies often log request paths/queries, response statuses, latencies, client IPs, and user agents. If a system mistakenly sends reset tokens or passwords in query parameters, access logs can preserve them long-term even if the Java app logs nothing.

At API gateways, disable body logging on login, reset, and token endpoints. Avoid collecting `Authorization`, `Cookie`, `Set-Cookie`, and custom auth headers. Audit retention policies, log read permissions, and third-party log forwarding.

### 10.2. OpenTelemetry, Tracing, and MDC

Tracing helps follow requests end-to-end, yet **span attributes, baggage, and MDC** are also stored and replicated. Never put passwords, raw tokens, full `Authorization` headers, or request bodies into attributes. Record only approved metadata such as route template, status, and server-generated `traceId`.

For `userId`, `sessionId`, IP, or email, enforce dedicated personal-data policies and access controls. Never treat `userId` as “non-sensitive” just because it is not a password.

### 10.3. Centralized Logs and Backups

Once a secret enters a log stream, it can propagate through local buffers, collectors, message queues, search indices, archives, and backups. Deleting logs on one host never erases all copies.

Design in layers:

1. **Prevent before writing:** allowlist fields in the app and minimize body/header logging.
2. **Redact at ingestion:** add gateway/collector rules as a backstop for slips.
3. **Restrict read access:** lock down dashboards, search queries, and exports.
4. **Bound retention:** keep logs only as long as investigations/compliance require.
5. **Alert on secret detection:** detect credential patterns while tuning false positives.
6. **Incident plan:** rotate, revoke, and trace where leaked logs traveled or were downloaded.

### 10.4. Should You Hash Usernames or Passwords for Logging?

**Never directly hash a password and log that hash** as a correlation ID. Leaked hashes enable offline guessing. For usernames/emails, if cross-event correlation is genuinely needed, use a controlled internal identifier or policy-designed pseudonymization—avoid naive `SHA-256(email)` since dictionary attacks easily reverse common emails.

For anonymous failed-login events, event type, request ID, bounded client risk signals, and counters often suffice for investigation. Any sensitive details belong in a separate, restricted audit store.

## 11. Redaction vs. Data Minimization

| Strategy | Meaning | Risk If Used Alone |
| --- | --- | --- |
| **Data minimization** | Never create, retain, or transmit secrets unnecessarily | Can miss existing logging paths |
| **Allowlist fields** | Emit only vetted safe fields in logs/responses | Requires schema discipline and review on new fields |
| **Redaction/masking** | Strip or mask secrets before writing | Regexes miss nested structures or new formats |
| **Encryption at rest** | Protects stored logs and databases | Anyone authorized to decrypt still sees the secret |
| **Access control** | Restricts who can view logs/artifacts | Does not undo secret collection |
| **Retention/rotation** | Shrinks exposure window | Does not prevent immediate leakage upon write |
| **Secret scanning** | Detects secrets in source/artifacts | Cannot guarantee catching every credential format |

Combine multiple layers in practice. For example, **returning a hash-free DTO from the Controller** is far safer than returning an entity and hoping a serializer hides `passwordHash`; adding Jackson write-only/redaction acts as a backup guard against future edits.

## 12. Dangerous Code Patterns and Safer Replacements

### 12.1. Logging the Entire Request Object

**Wrong:**

~~~java
log.info("password change request={}", changePasswordRequest);
~~~

**Better:**

~~~java
log.info("event=password_change_requested");
~~~

If correlation is needed, include a validated server-generated `traceId`. Never log raw `currentPassword` or `newPassword` on either success or failure.

### 12.2. Returning UserDetails or UserEntity

**Wrong:**

~~~java
@GetMapping("/account")
Object account(Authentication authentication) {
    return authentication.getPrincipal();
}
~~~

**Better:**

~~~java
record AccountView(boolean authenticated) {}

@GetMapping("/account")
AccountView account() {
    return new AccountView(true);
}
~~~

These snippets belong inside a `@RestController` with proper imports, not standalone files. The safer version never pulls passwords or hashes from `Authentication`.

### 12.3. Embedding Raw Input in Errors

**Wrong:**

~~~java
throw new IllegalArgumentException(
    "Rejected password value=" + rawPassword);
~~~

**Better:**

~~~java
throw new IllegalArgumentException(
    "Password did not satisfy the configured policy");
~~~

Real applications should use standard validation/error codes ensuring messages never echo input values. Remember frameworks often log exceptions along with their messages automatically.

### 12.4. Overly Broad Logging Filters

**Dangerous:** adding a filter that logs full headers + bodies for every URL to debug. Even if the Controller logs nothing, the filter runs earlier and records raw passwords on `/login`, `/change-password`, or `Authorization` headers.

**Fix:** disable body/header capture on sensitive routes and favor allowlisted method/route/status/duration records. For request-logging filters offering `includePayload`/`includeHeaders`, evaluate impact before enabling and never assume defaults stay identical across versions.

### 12.5. Reusing Fixed Tutorial Passwords on Staging

**Process mistake:** entering a password from a README/demo into a staging account with real privileges and never rotating it.

**Right approach:** provision dedicated test accounts with passwords from a secret manager, tight scope/TTL, no exports, and automated teardown/rotation. Public test code should only describe **how to generate** credentials, never contain a reusable credential.

## 13. Pull Request Review and CI Process

Any PR touching login or password handling should be reviewed against these questions:

1. Does any request DTO carry a password, confirmation, or OTP? Could `toString`/AOP log it?
2. Does any filter or interceptor enable request/response body logging?
3. Does any new logging config turn on `TRACE`, `includeHeaders`/`includePayload`, or serialize `Authentication`?
4. Does any endpoint return `UserDetails`, `Authentication`, `Jwt`, `OidcUser`, or an entity containing a hash?
5. Does any global exception handler return `exception.getMessage()` or `rejectedValue`?
6. Are there real secrets/credentials in source, test fixtures, YAML, JSON, SQL seeds, Postman exports, or docs?
7. Do tests include `andDo(print())`, debug captures, snapshot diffs, or failure messages containing raw secrets?
8. Do E2E screenshots, browser HARs, or pipeline artifacts capture tokens or cookies?
9. Do CI command lines or environment dumps print credentials to the console?
10. Where are logs/metrics/traces shipped? Are access controls and retention enforced?
11. If a leak is detected, is there an immediate rotate/revoke and prevention workflow?
12. Are response contracts and audit logs tested for login success, failure, and 403 paths?

### 13.1. Secret Scanning

Run secret scanning in CI and pre-commit hooks appropriate for your repo to catch API keys, tokens, private keys, and configured passwords. It is very helpful yet cannot catch every password, especially short strings under non-obvious field names.

Therefore combine:

- Static analysis flagging sensitive logging and raw entity returns.
- Code reviews on authentication, error handling, and serialization paths.
- Tests asserting HTTP contracts and log output.
- Checks on uploaded build artifacts.
- Audits of APM, proxy, and log-collector configs.

Never commit a real secret as a public “test case” just to see if the scanner catches it. Use non-functional synthetic patterns or test tooling in an isolated, access-controlled environment.

### 13.2. CI Masking Is Not a Standalone Defense

CI secret masking can be bypassed by string transformations (Base64, URL encoding), split strings, JSON formatting, or external tools. Never deliberately echo a secret expecting CI to mask it. Users authorized to view pipelines, download artifacts, or export logs may still access unmasked values in some systems.

### 13.3. Inspect Test Reports Before Publishing

Before sharing test reports, screenshots, sample logs, or READMEs externally, check:

- Any HTTP `Authorization`/`Cookie`/`Set-Cookie` headers?
- Any stack traces containing `rejectedValue` or raw request bodies?
- Any encoded password hashes or reset tokens?
- Any database connection strings with credentials?
- Any credentials in images, videos, HAR files, or attachments?
- Any still-valid tokens from the test environment itself?
- Any real personal IDs beyond what sharing requires?

If real data appears, handle it via security incident procedures and share only a genuinely cleaned version—never merely rename a file to “sanitized.”

## 14. When a Password or Token Is Found in Logs or a Repository

Distinguish **preventing recurrence** from **remediating exposed data**.

1. **Assess whether the secret is still usable:** raw password, refresh token, API key, private key, or reset code? Identify the source and blast radius.
2. **Revoke/rotate:** for still-valid credentials, prioritize revoking or rotating the password, key, or token through authorized procedures. If a password may be reused elsewhere, advise the user to change it.
3. **Trace propagation:** app logs, proxies, collectors, SIEM, APM, CI, build artifacts, Git history, external exports.
4. **Restrict access and retention:** halt further spread and apply retention/deletion per legal and access-control obligations.
5. **Fix the emission source:** remove object logging, introduce response DTOs, update filters/serializers—never rely solely on post-log regexes.
6. **Add regression tests:** use ephemeral test secrets to verify safe bodies and logs, and scan artifacts.
7. **Audit and notify:** follow organizational incident response, legal obligations, and incident classification.

**Deleting a log line or commit does not restore the secrecy of an exposed credential.** Especially for raw passwords and access tokens, account for copies in log aggregators, backups, and old clones. Never rewrite shared Git history unilaterally without a coordinated workflow.

If only **password hashes** leaked, never dismiss it as harmless; evaluate algorithm/cost, data access scope, offline cracking feasibility, weak/reused password risk, and appropriate mitigations.

## 15. Common Misconceptions

**“I only log requests at DEBUG, and production runs INFO, so it’s safe.”** Not reliable. Engineers may enable DEBUG during troubleshooting, another service may have a different log level, or staging data with real traffic may already have been captured. Fix the root cause and lock down configuration.

**“Authentication.toString masks credentials automatically, so logging Authentication is safe.”** Avoid doing this. Principals, details, and custom objects can still expose sensitive data.

**“BCrypt hashes aren’t passwords, so sharing them for debugging is fine.”** False. Hashes are sensitive credential data valuable for offline guessing if leaked.

**“Putting @JsonIgnore on the password field is enough.”** Insufficient. It does not protect other serializers, logs, `toString`, tracing, caches, or other fields.

**“Tests use fake passwords, so printing them in CI doesn’t matter.”** Not always true; fixtures get reused or tests touch real staging accounts. Never log secrets; generate or inject credentials via protected mechanisms.

**“My Controller has no log statements, so passwords cannot enter logs.”** False. Proxies, filters, APMs, request-logging middleware, exceptions, and containers can all capture data.

**“Renaming the key `password` to `p` bypasses the scanner.”** That hides a defect without reducing risk.

**“Secrets in environment variables are 100% safe.”** No. Environments can leak via process inspection, crash dumps, or diagnostics if permissions or tooling slip. They reduce source-commit risk when used properly, while production requires proper secret management.

**“A test proving the response omits the password proves the password was erased from the JVM.”** False. Tests verify only the observed output channels, not memory lifecycle across the heap.

**“Logging nothing at all is good security auditing.”** No. Structured, safe security event logging is essential—just keep secrets out of logs.

## 16. Practice Exercises and Questions

### 16.1. Exercise A — Audit Credential Exposure in a DTO

An API returns `UserEntity` containing `passwordHash` and `phone`. Refactor the response into a DTO carrying only fields the UI is authorized to view. Write a MockMvc test verifying the response omits `passwordHash` and sensitive fields. Never use a real password as a fixture.

### 16.2. Exercise B — Failed Login Auditing

Define an `auth.failure` event with request ID, outcome, and internal reason category. Include only allowlisted metadata, keeping usernames, passwords, and tokens out of default logs. Try enabling `DEBUG` in a test environment and inspect what filters and exceptions log.

### 16.3. Exercise C — Inspecting CI Artifacts

Run a pipeline on **synthetic data in an access-controlled environment**. Inspect JUnit XML, build console logs, screenshots, HTTP recordings, and log collectors to confirm zero passwords or tokens appear. When a test generates an ephemeral credential, confirm output never prints that value.

### 16.4. Questions and Answers

**Question 1.** Why can logging `loginRequest` via `toString` be dangerous?  
**Answer:** The request may contain the raw password; Java record or Lombok `toString` implementations can print that field.

**Question 2.** Should a BCrypt hash be returned by `/me`?  
**Answer:** No. Hashes are sensitive credential data and serve no purpose in identifying the user to the UI.

**Question 3.** Why must HTTP Basic `Authorization` headers never be logged?  
**Answer:** Base64 decodes directly back into the username and password.

**Question 4.** If the Controller logs nothing, can a proxy still leak the password?  
**Answer:** Yes, especially when header/body logging is enabled or secrets appear in URLs.

**Question 5.** Should `ResponseEntity.ok(authentication)` be used for debugging?  
**Answer:** No. Framework objects can hold principals, credentials, details, and tokens.

**Question 6.** What does `PasswordEncoder` use to compare passwords?  
**Answer:** `PasswordEncoder.matches(rawPassword, storedHash)` within the proper authentication mechanism; there is no need to send hashes to clients.

**Question 7.** Why do tests generate passwords with `UUID.randomUUID`?  
**Answer:** To avoid committing a static test credential; tests only need an ephemeral credential to verify behavior.

**Question 8.** Does `OutputCaptureExtension` inspect every proxy and APM log?  
**Answer:** No. It observes only logs, stdout, and stderr captured inside the test process scope.

**Question 9.** Why is `assertFalse(body.contains(secret))` better than `assertEquals(secret, body)`?  
**Answer:** It prevents printing the secret inside expected/actual failure diffs if a test fails.

**Question 10.** If a credential was already committed, is adding `.gitignore` enough?  
**Answer:** No. The credential remains in Git history and clones; rotate/revoke it and address copies.

**Question 11.** Does `403 Access Denied` mean the password was wrong?  
**Answer:** No. An authenticated request may simply lack a required role or business permission.

**Question 12.** Is masking fields named `password` with a regex sufficient?  
**Answer:** No. Secrets appear in headers, nested objects, exceptions, tokens, or differently named keys; use allowlists.

**Question 13.** Should raw passwords be placed in URLs for easier `curl` testing?  
**Answer:** No. URLs end up in history, logs, referrers, APMs, and analytics.

**Question 14.** Should authentication successes and failures be logged?  
**Answer:** Yes, with sensible auditing and monitoring using only minimal allowlisted metadata and zero credentials.

**Question 15.** If tests pass and responses contain no secrets, can you declare production leak-free?  
**Answer:** No. You must audit filters, proxies, CI, APMs, error handlers, log settings, and real runtime paths.

## 17. Final Pre-Deployment Checklist

- [ ] Never hardcode usable raw passwords, API keys, or tokens into source, examples, fixtures, YAML, or Postman exports.
- [ ] Never log full request DTOs, `Authentication`, `UserDetails`, `UserEntity`, `Jwt`/`OidcUser`, or password hashes.
- [ ] Never log `Authorization`, `Cookie`, `Set-Cookie`, tokens/reset links, or credentials from queries/bodies.
- [ ] Audit Java record/Lombok `toString` and AOP interception on classes carrying sensitive fields.
- [ ] Use allowlisted response DTOs; never serialize entities or framework objects.
- [ ] Return context-appropriate error codes/messages without echoing input, exceptions, or `rejectedValue`.
- [ ] Ensure `UserDetailsService`/providers use encoded passwords and Controllers never expose hashes.
- [ ] Enforce TLS, limit caching, protect sessions/tokens, and lock down CORS settings.
- [ ] Audit logging settings across reverse proxies, API gateways, Actuator, APM, tracing, and error reporting.
- [ ] Generate test credentials at runtime or fetch them from a least-privilege secret manager.
- [ ] Ensure MockMvc/RestAssured/test reports never print sensitive `Authorization` headers or bodies on failure.
- [ ] Inspect CI artifacts, screenshots, HAR captures, log archives, and exports before sharing.
- [ ] Pair secret scanning with code reviews and tests; never rely on regex masking alone.
- [ ] Maintain rotation/revocation procedures for leaked secrets along with retention/backup governance.
- [ ] Log enough metadata to detect attacks without over-collecting sensitive data.
