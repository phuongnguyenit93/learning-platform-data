# BCrypt, PBKDF2, SCrypt, and Argon2: How to Choose a Password Storage Algorithm

When building registration or login with Spring Security, a critical security decision is **how to store passwords**. User passwords can be weak, reused, or exposed through a database breach. A good password hash does not make a weak password strong, but it can make **offline password guessing from a stolen database** dramatically more expensive in time, memory, and money.

Under the **Passwords** topic, four common options are **BCrypt**, **PBKDF2**, **SCrypt/scrypt**, and **Argon2**, especially **Argon2id**. All four can be used through Spring Security's **PasswordEncoder** contract, yet they differ in how they raise computational cost, RAM requirements, compatibility, compliance support, and implementation limits.

This lesson presents the **algorithm-selection level**: understanding goals, selection criteria, parameter comparisons, pros/cons, Spring Security configuration, safe migration from legacy hashes, and testing. No custom cryptography implementation is required. The Java 17/Spring Boot 3.3.6 example at the end uses standard library components and contains no real passwords.

## 1. Start from the Threat Model: What Does a Password Hash Protect Against?

Suppose an account table is leaked:

~~~text
user_id | username | password
--------+----------+---------------------
101     | alice    | spring123
102     | bob      | Welcome2024!
~~~

If stored in plaintext, the attacker immediately has the passwords. If stored as fast SHA-256(password), an attacker can test huge password dictionaries offline, compare hashes, and recover matches. **Fast hashes are suited for data integrity checks, not directly for storing passwords.**

The goal of **password hashing** is to turn each password guess into an intentionally costly computation.

~~~mermaid
flowchart LR
    R["Raw password from registration/password change"] --> E["Password hashing: salt + cost parameters"]
    E --> H["Stored encoded hash (with required metadata)"]
    L["Raw password at login"] --> M["PasswordEncoder.matches(raw, stored)"]
    H --> M
    M --> D{"Match?"}
    D -- "Yes" --> A["Continue account checks / authentication"]
    D -- "No" --> F["Reject authentication"]
~~~

Several algorithm-independent principles:

1. **Never store raw passwords**, never log passwords, and never return password hashes over an API.
2. **Each password needs a random, practically unique salt**, generated by a good encoder and stored with the hash in its format.
3. **The work factor** must be expensive enough to deter offline guessing, yet not so costly that the login endpoint exhausts its own CPU/RAM.
4. **Input password strength** still matters: length, breached-password checks, MFA, rate limiting, and credential-stuffing detection.
5. **HTTPS is mandatory** when transmitting credentials outside local environments; database hashing does not replace TLS.
6. **Protecting databases, secrets, backups, audits, and access permissions** remains essential. Hashing does not replace those controls.

What hashing protects particularly well against is **an attacker holding a dump of hashes and guessing offline**. It does not stop an attacker logging in through the API using a valid stolen password. Online threats require rate limiting, MFA, alerting, and other authentication controls.

## 2. Distinguishing Hashing, Encryption, Salt, and Pepper

| Term | Purpose | Used for Password Storage? |
| --- | --- | --- |
| **Fast hash** (plain SHA-256) | Turns input into a digest quickly, with no design to slow password guessing. | **Do not use directly** for passwords. |
| **Password hashing / password KDF** | Intentionally slow; uses salt and cost parameters; verified via matches(). | **Yes**: bcrypt, PBKDF2, scrypt, Argon2id. |
| **Encryption** (AES, etc.) | Encrypted data can be decrypted with a key; suited when plaintext must be recovered. | Usually **not chosen** for storing user authentication passwords. |
| **Salt** | Random value unique per hash, defeating precomputation and identical hashes. | **Required in good designs**; does not need to be kept secret. |
| **Pepper** | Application/system-level secret added to hashing/verification, stored **outside the database**. | Can add defense-in-depth if managed properly; does not replace salt. |
| **Work factor** | Configures computational work; for memory-hard functions, also RAM cost. | Chosen after reviewing threat model and benchmarks. |

**Salt and pepper are different:**

- A salt is randomly generated by the encoder per password and **does not need to be a secret**; it typically lives inside the encoded hash string.
- A pepper is a **shared or scoped secret** kept in a secret manager/HSM or separate location from the database.
- If a pepper leaks, you need a rotation plan; because plaintext passwords are not available, many rotation approaches require password resets or waiting to rehash on user login.
- Never invent a hardcoded “pepper” in source or commit it to a repository and assume you added a security layer.
- Never concatenate raw passwords with a pepper using ad-hoc string concatenation and call it a secure protocol; if a pepper is needed, use a reviewed design/HMAC and proper secret management.

Salts also ensure two accounts choosing the **same password** still yield different stored hashes under random salt generation. Never write tests expecting an encoded hash to equal a fixed string: encoders normally use randomness.

## 3. High-Level Comparison of the Four Options

| Criterion | BCrypt | PBKDF2 | SCrypt (scrypt) | Argon2id |
| --- | --- | --- | --- | --- |
| Primary mechanism | Blowfish-based password hashing with tunable CPU cost. | Iterated HMAC/PRF over many rounds. | KDF designed to consume substantial RAM to hinder parallel cracking hardware. | **Memory-hard** password hashing balancing practical attack classes. |
| Key work factor | **cost** (log2), e.g., 10, 12. | **iteration count** and HMAC (SHA-256, SHA-512...). | **N**, **r**, **p**, and key/salt lengths. | **m** (memory), **t** (passes), **p** (parallelism), salt/hash lengths. |
| RAM usage | Generally not memory-hard like scrypt/Argon2. | Typically low RAM; primarily CPU cost. | **Memory-hard**. | **Memory-hard**, more flexible tuning. |
| Best-fit context | Legacy systems already on bcrypt; broad support; simple deployment if input limits are managed. | When an ecosystem requires a **FIPS-validated implementation** or specific standards compliance. | When Argon2id is unavailable but the runtime supports scrypt and has sufficient RAM. | **Preferred candidate for new designs** when runtime and memory budget allow. |
| Caveats | **72-byte input limit** in traditional bcrypt; requires policy/compatibility handling. | Easy to raise iterations, but not memory-hard like Argon2id/scrypt. | High RAM parameters can cause DoS if concurrency is unbounded. | Needs compatible runtime/provider; RAM cost and concurrency must be measured; Spring Security implementation uses Bouncy Castle. |
| Spring Security PasswordEncoder? | BCryptPasswordEncoder | Pbkdf2PasswordEncoder | SCryptPasswordEncoder | Argon2PasswordEncoder |

This is a **decision table**, not an absolute ranking for every system. Each option can provide solid protection given proper parameters, safe libraries, proper salts, and sound operations. A PBKDF2 system with FIPS requirements differs from a new service with ample RAM for Argon2id.

**Argon2 is an algorithm family:** there are Argon2d, Argon2i, and **Argon2id**. For application password storage, practical guidance generally recommends **Argon2id** because it combines resistance to side-channel attacks and specialized cracking hardware. Do not pick Argon2d just because you saw the name Argon2 in a document.

## 4. BCrypt: Broad Compatibility, CPU-Based Work Factor

BCrypt is a long-standing popular choice for password hashing. It combines a salt with computational cost tuned via a cost parameter. A bcrypt hash typically carries metadata such as version, cost, salt, and hash, e.g. **structure**:

~~~text
$2a$12$[salt-and-hash-data]
~~~

This is only structural notation, **not a valid hash to copy into a database**. Prefixes like 2a/2b/2y depend on the implementation and support. You do not need to parse it manually to check passwords: use **BCryptPasswordEncoder.matches(raw, stored)**.

### 4.1. Work Factor and Verification Time

BCrypt uses an exponential **cost** parameter: raising cost from 10 to 11 roughly doubles the algorithmic work rather than simply adding one loop. Actual wall-clock time depends on CPU, library version, load, and environment.

~~~java
// Java snippet used in a project with Spring Security Crypto.
PasswordEncoder bcrypt = new BCryptPasswordEncoder(12);

String encoded = bcrypt.encode("example-password");
boolean valid = bcrypt.matches("example-password", encoded);
~~~

In this code **valid will be true**, while **encoded changes every run** due to the random salt. Never place a fixed hash result into expected output.

Per the OWASP Password Storage Cheat Sheet referenced for this lesson, legacy bcrypt should use a **cost of at least 10**, then be benchmarked and tuned to system capacity. That is a reference baseline, not a reason for every service to lock in one cost forever.

### 4.2. Warning: 72 Bytes, Not 72 Characters

Traditional BCrypt only evaluates the **first 72 bytes of password input**. With UTF-8 Unicode, 72 bytes can be fewer than 72 characters. If an implementation or system silently truncates at this boundary, two passwords sharing the same first 72 bytes can be treated as equivalent.

You should:

- Verify the input-limit behavior of your **actual running implementation** and its String-to-byte conversion.
- Define a clear password length policy without silently truncating passwords so distinct inputs match.
- Prefer Argon2id/PBKDF2/scrypt with proper input handling when long passphrases must be supported.
- If migrating an existing bcrypt database, inspect the legacy implementation's policy and test passwords containing Vietnamese/emoji/Unicode; never “fix” it with an unreviewed fast pre-hash before bcrypt.

Also avoid accidentally applying **trim()** or toLowerCase() to passwords: passwords are character-sensitive by application contract; if Unicode normalization is used, design it consistently and never change it abruptly during upgrades.

### 4.3. When to Choose bcrypt?

- Many bcrypt hashes already exist in an active system and verification compatibility must be preserved.
- Libraries, runtimes, and integrated systems already support it well.
- You want to raise the cost on new hashes while incrementally upgrading older hashes.
- Operational constraints make an immediate move to Argon2id difficult, with a clear plan to review cost and input limits.

**Do not choose bcrypt simply because Spring Security once used it as the default encoder for new hashes.** Library defaults, modern security requirements, and operational budgets are three separate considerations.

## 5. PBKDF2: Iterated HMAC KDF, Advantageous for Certain Compliance Needs

**PBKDF2** (Password-Based Key Derivation Function 2) is standardized and widely supported. Key parameters include:

- **HMAC/PRF**: e.g., HMAC-SHA-256.
- **Iteration count**: increasing iterations raises computational cost.
- **Salt**: random and unique per hash.
- **Derived key length** and storage format.
- Some implementations may add a separate secret/pepper.

PBKDF2 relies primarily on **CPU**, rather than being memory-hard in the sense of Argon2id and scrypt. That can be a relative disadvantage against adversaries with hash-optimized hardware, yet advantageous in environments requiring validated HMAC/cryptographic modules.

### 5.1. When Is PBKDF2 an Appropriate Choice?

When a system has **FIPS-140 requirements**, PBKDF2-HMAC-SHA-256 can be a pragmatic option when used with a **validated implementation and cryptographic module** in an approved configuration.

**Using PBKDF2 does not automatically make an application FIPS compliant.** You must verify the provider/JCE, module version, operating mode, key policies, and all remaining compliance requirements.

Per the OWASP Password Storage Cheat Sheet referenced for this lesson: for **PBKDF2-HMAC-SHA-256**, the reference baseline is **600,000 iterations or more**. That is practical guidance subject to change over time; always verify at production deployment time.

### 5.2. Spring Security: Watch Factory Defaults

~~~java
PasswordEncoder pbkdf2 =
    Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8();
~~~

In Spring Security 6.3, the **defaultsForSpringSecurity_v5_8()** factory uses a 16-byte salt, roughly **310,000 iterations**, HMAC-SHA-256, and a 256-bit derived key. This is **lower** than the 600,000-iteration OWASP recommendation noted above.

That **does not make the API broken**, but it means **you must not treat a framework version's factory default as an up-to-date security baseline for every environment**.

An explicit configuration applying 600,000 iterations:

~~~java
PasswordEncoder pbkdf2 =
    new Pbkdf2PasswordEncoder(
        "", 16, 600_000,
        Pbkdf2PasswordEncoder.SecretKeyFactoryAlgorithm.PBKDF2WithHmacSHA256
    );
~~~

The parameters in order are **additional secret** (left empty in the example), **salt length in bytes**, **iterations**, and **SecretKeyFactory algorithm**. If using a real additional secret, back it with a secret manager and rotation plan; never use a literal constant in source.

### 5.3. PBKDF2 Hashes Are Not Necessarily Interoperable

Two hashes both labeled PBKDF2 that use different HMACs, salt lengths, iteration counts, or output lengths/encodings **cannot automatically be verified** by the same PasswordEncoder configuration.

When migrating, store version/parameter identifiers and keep the old encoder able to verify before transitioning to the new encoder. With DelegatingPasswordEncoder formatting, each parameter set should have a distinct id.

## 6. SCrypt/scrypt: Memory-Hard to Raise Offline Guessing Costs

**scrypt** intentionally requires substantial RAM in addition to CPU to make password guessing costlier on parallel-optimized hardware. In Spring Security, use **SCryptPasswordEncoder**.

Common parameters:

| Parameter | Meaning | Example |
| --- | --- | --- |
| **N** (cpuCost) | Work cost parameter, typically a power of 2. | 2^16 or 2^17. |
| **r** (memoryCost in Spring API) | Block size; affects RAM footprint and cost. | 8. |
| **p** (parallelization) | Parallelization/work factor. | 1 or higher per benchmark target. |
| **saltLength** | Random salt length. | 16 bytes. |
| **keyLength** | Derived key length. | 32 bytes. |

Core scrypt RAM usage is commonly estimated at roughly **128 × N × r bytes** (excluding implementation, JVM, and other overhead). With N=65,536 and r=8, the core working memory is around **64 MiB per operation**. With N=131,072 and r=8, it is around **128 MiB per operation**. Therefore, you must measure concurrent login volume, not just single-request duration.

### 6.1. Spring Security Factory and Recommended Parameters

~~~java
PasswordEncoder scryptDemo =
    SCryptPasswordEncoder.defaultsForSpringSecurity_v5_8();
~~~

The v5_8 factory in Spring Security 6.3 uses values like **N=2^16, r=8, p=1, 32-byte key, 16-byte salt**. It is reasonable for **learning the API** and comparing behavior, but lower than **N=2^17, r=8, p=1**, which OWASP cites as a recommended level when Argon2id is unavailable.

An illustrative configuration with stronger parameters:

~~~java
PasswordEncoder scrypt =
    new SCryptPasswordEncoder(
        1 << 17, // N = 131072
        8,       // r
        1,       // p
        32,      // key length, bytes
        16       // salt length, bytes
    );
~~~

This configuration has significant RAM cost and **should not be pushed straight to production without load testing**. Especially in memory-constrained containers, concurrent verifications can trigger memory pressure or OOM. OWASP parameters are a starting point for evaluation, not a mandate that “every request must allocate this exact MiB count” for every system.

### 6.2. When to Choose scrypt?

- Argon2id cannot be used, but an up-to-date, vetted scrypt library is available.
- Sufficient RAM and quota exist to afford memory-hard costs at login.
- You want to avoid relying purely on CPU iterations like PBKDF2.
- You have plans to bound concurrency, timeouts, rate limits, and test memory usage.

If a platform has specific compliance rules, verify whether scrypt is permitted under that policy. Never swap PBKDF2 for scrypt when a FIPS-validated module is mandatory without review.

## 7. Argon2: Prefer Argon2id for New Password Storage When Suitable

**Argon2** is the algorithm family selected as winner of the Password Hashing Competition. Three variants are commonly discussed:

- **Argon2d**: data-dependent memory access; not a safe default in environments exposed to side-channel risks.
- **Argon2i**: focuses on resisting certain side-channels via data-independent memory access.
- **Argon2id**: hybrid of both approaches; **the widely recommended choice for application password hashing**.

Parameters:

| Symbol | Meaning | Effect When Increased |
| --- | --- | --- |
| **m** | Memory size (typically in KiB per API/format). | Increases RAM usage; raises cost for both attacker and server. |
| **t** | Number of passes/iterations. | Increases computational work, typically increasing latency. |
| **p** | Parallelism/lanes. | Changes execution pattern and resource usage; not simply “multiplying RAM by p.” |
| **saltLength** | Per-password random salt. | Helps prevent precomputation and practical hash collisions. |
| **hashLength** | Stored output length. | Does not directly replace the role of m/t/p. |

**Argon2id does not automatically tune every setup.** Choosing m/t/p requires assessing CPU, RAM, concurrent logins, container deployment, and the performance gap between defender and attacker.

### 7.1. OWASP vs. RFC 9106: Two Different Reference Tiers

The OWASP Password Storage Cheat Sheet proposes Argon2id with a reference baseline of **m=19 MiB (19,456 KiB), t=2, p=1**. This is a practical baseline applicable to many applications if benchmarks fit.

**RFC 9106** provides stronger profiles for memory-rich conditions: for example **64 MiB, t=3, p=4**, or an option using **2 GiB** of RAM with RFC parameters. You cannot conclude “OWASP is wrong” or “RFC demands 2 GiB in every web app”; they serve different contexts and cost targets.

For a service handling hundreds of concurrent login requests, 2 GiB per request may be operationally infeasible. Pick an **appropriate baseline + tuning and load testing**, then raise it as infrastructure allows. For sensitive workloads, consider adding multi-factor authentication and login throttling.

### 7.2. Argon2PasswordEncoder in Spring Security

~~~java
PasswordEncoder argon2Default =
    Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
~~~

In the Spring Security 6.3.x line, this factory uses a 16-byte salt, 32-byte hash, **p=1, m=2^14 KiB (16 MiB), t=2**. **16 MiB** of memory is below the **19 MiB** OWASP baseline above, so production systems should not rely on a factory name to assume it matches every current recommendation.

Explicit configuration near the OWASP baseline:

~~~java
PasswordEncoder argon2id =
    new Argon2PasswordEncoder(
        16,       // saltLength: bytes
        32,       // hashLength: bytes
        1,        // parallelism
        19 * 1024,// memory: KiB = 19456
        2         // iterations
    );
~~~

This snippet belongs to **Spring Security Crypto**. The **Argon2PasswordEncoder** implementation uses **Bouncy Castle** and requires that dependency on the runtime classpath. The Maven example in the hands-on section declares that library explicitly.

### 7.3. What Must Be Measured When Choosing Argon2id

- Actual **memory cost** per encode/matches call in the Java implementation.
- **p95/p99 latency** under dozens of concurrent login requests, not just a single isolated hash.
- CPU, GC, heap, native memory, and RSS/container OOM risk.
- Under autoscaling, total RAM/CPU and the risk of an attacker triggering many concurrent verifications.
- Can legacy hashes with old parameters still be verified after upgrades?
- Do code or Bouncy Castle dependency updates alter output or performance?

Spring Security uses Bouncy Castle in Argon2PasswordEncoder; optimizations and parallelism can differ from native C implementations. Therefore **benchmark the actual Java implementation**, rather than using benchmarks from another language library to predict server latency.

## 8. Selection Table for Common Scenarios

| Scenario | Practical Direction | Why |
| --- | --- | --- |
| New app with available RAM and no special compliance constraints | **Argon2id** with benchmarked m/t/p starting from current recommendations. | Memory-hard, modern design, flexible cost tuning. |
| Cannot deploy Argon2id but need memory-hard | **scrypt** with policy-aligned N/r/p, guarding RAM/concurrency. | Raises memory cost for offline guessing. |
| Need cryptographic modules compliant with FIPS/regulatory interop | **PBKDF2-HMAC-SHA-256** via validated provider, sufficiently high iterations. | Standards support and compliant ecosystem. |
| Existing system with millions of bcrypt hashes | **Keep verifying bcrypt**, raise cost gradually or rehash to a new algorithm on login. | No plaintext available for bulk migration; avoids breaking user logins. |
| Constrained RAM but sufficient CPU, with FIPS need | **PBKDF2** with tuned work factor and compensating controls. | Primarily CPU cost, easier to balance RAM than memory-hard functions. |
| High concurrent logins in memory-limited containers | Choose via **real load benchmarks**, enforce rate limits and scaling; avoid extreme `m`. | Overly high settings can turn into self-inflicted DoS. |
| Legacy MD5/SHA1/noop hashes | **Plan migration/reset**; verify legacy only within controlled scope if forced and stop creating new hashes in that format. | Fast/unhashed formats do not adequately protect passwords. |

A quick summary that does not replace a security review:

~~~text
FIPS requirement and suitable provider?
  Yes -> PBKDF2-HMAC-SHA-256 with current iteration count and validated module.
  No ->
    Can use Argon2id and RAM budget allows?
      Yes -> Argon2id, benchmark m/t/p.
      No ->
        Can use scrypt and sufficient RAM?
          Yes -> scrypt, benchmark N/r/p.
          No -> Consider bcrypt/PBKDF2 per constraints, input policy,
                   upgrade plan, and compensating controls.
Existing old stored hashes?
  Yes -> keep ability to verify old formats + upgrade safely by version.
~~~

Decision trees are only a rough guide: organizational standards, library support, long passwords, capacity/traffic, threat models, and security budgets can shift the choice.

## 9. PasswordEncoder in Spring Security

Spring Security defines the contract:

~~~java
// Simplified API signature, not a standalone Java file.
public interface PasswordEncoder {
    String encode(CharSequence rawPassword);
    boolean matches(CharSequence rawPassword, String encodedPassword);
    default boolean upgradeEncoding(String encodedPassword) {
        return false;
    }
}
~~~

Meaning:

- **encode(raw)** is used at registration or password change; normally creates a fresh salt.
- **matches(raw, stored)** checks the entered password against the stored hash—**never use raw.equals(stored)**.
- **upgradeEncoding(stored)** indicates whether a hash should be updated per the encoder's cost/algorithm policy; exact behavior depends on the implementation. It does not update the database automatically.

Never call `encode(raw)` a second time and compare strings with `stored`: because of the random salt, two valid hashes normally differ. Call **matches**.

### 9.1. Key Classes to Remember

~~~java
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.Pbkdf2PasswordEncoder;
import org.springframework.security.crypto.scrypt.SCryptPasswordEncoder;
import org.springframework.security.crypto.argon2.Argon2PasswordEncoder;
import org.springframework.security.crypto.password.DelegatingPasswordEncoder;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
~~~

There is no reason to write custom MD5/SHA-256 implementations for password storage. Fast hashes may appear in some factories for legacy support, **which does not mean they are safe for issuing new hashes**.

### 9.2. DelegatingPasswordEncoder Enables Multiple Algorithms to Coexist

When transitioning gradually from bcrypt to Argon2id, a system usually does not know every user's raw password to rehash immediately. **DelegatingPasswordEncoder** stores an external identifier alongside the stored hash:

~~~text
{bcrypt}$2a$10$...
{pbkdf2-600k}...
{scrypt-v1}$...
{argon2id-m19456-t2-p1}$argon2id$v=19$m=19456,t=2,p=1$...
~~~

Strings containing **...** are format illustrations, **not real hashes**. The **{id}** prefix lets the router choose the right PasswordEncoder for matches; the remainder is encoded data per implementation, carrying its own salt/cost metadata.

Example:

~~~java
PasswordEncoder encoder =
    PasswordEncoderFactories.createDelegatingPasswordEncoder();

String stored = encoder.encode("a-demo-pass");
// Usually starts with "{bcrypt}" with the default factory on 6.x.
boolean ok = encoder.matches("a-demo-pass", stored);
~~~

**The default factory** provides compatibility with certain legacy ids/formats. That does not mean every algorithm in the mapping should be used to **create new hashes**; the id used for encoding can differ from ids accepted to verify legacy hashes.

Never configure a fallback such as NoOpPasswordEncoder for unknown ids in production. When a hash lacks an id or carries an unrecognized id, the system must have a **clear migration strategy** rather than treating the stored value as plaintext.

### 9.3. Why Not Just Swap the PasswordEncoder Bean and Deploy?

Suppose the DB stores:

~~~text
username: alice
password_hash: $2a$12$...
~~~

If the bean was previously BCryptPasswordEncoder and you swap it to Argon2PasswordEncoder without storing algorithm ids, subsequent logins will fail because the new encoder does not understand the old format. A safer path is to **attach ids** and keep support for old hashes:

~~~text
Before: raw bcrypt format, e.g. $2a$12$...
Normalized: {bcrypt}$2a$12$...
After valid login: can upgrade to {argon2id-...}...
~~~

Note: bulk-prepending a prefix to legacy hashes is only permitted when you **know for certain** the existing data is bcrypt in the expected format. Never prepend {bcrypt} to arbitrary DB strings merely because they “look like hashes.” Inventory and sample-test first.

### 10.3. HashingPolicy.java

~~~java
package com.example.hashchoice;

import java.util.LinkedHashMap;
import java.util.Map;

import org.springframework.security.crypto.argon2.Argon2PasswordEncoder;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.DelegatingPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.crypto.password.Pbkdf2PasswordEncoder;
import org.springframework.security.crypto.scrypt.SCryptPasswordEncoder;

public final class HashingPolicy {

    private HashingPolicy() {
    }

    public static Map<String, PasswordEncoder> algorithms() {
        Map<String, PasswordEncoder> encoders = new LinkedHashMap<>();

        encoders.put("bcrypt",
            new BCryptPasswordEncoder(10));

        encoders.put("pbkdf2-sha256-600k",
            new Pbkdf2PasswordEncoder(
                "", 16, 600_000,
                Pbkdf2PasswordEncoder.SecretKeyFactoryAlgorithm
                    .PBKDF2WithHmacSHA256));

        // N=2^16 for the lab; do not treat this as a production minimum.
        encoders.put("scrypt-demo-n65536",
            SCryptPasswordEncoder.defaultsForSpringSecurity_v5_8());

        encoders.put("argon2id-m19456-t2-p1",
            new Argon2PasswordEncoder(
                16, 32, 1, 19 * 1024, 2));

        return encoders;
    }

    public static PasswordEncoder delegating() {
        return new DelegatingPasswordEncoder(
            "argon2id-m19456-t2-p1", algorithms());
    }
}
~~~

**Why choose these four configurations?**

- **bcrypt cost 10**: convenient for lab/legacy and meets the OWASP reference minimum; production must benchmark and pick a higher cost when needed.
- **PBKDF2-HMAC-SHA-256 600,000 iterations**: demonstrates explicit parameter selection instead of blindly relying on the 310,000-iteration factory.
- **scrypt N=2^16, r=8, p=1**: lowers lab RAM usage; this level **does not meet the OWASP N=2^17/r=8/p=1 baseline** noted earlier. For production, raise parameters after load testing or choose Argon2id.
- **Argon2id m=19 MiB, t=2, p=1**: matches the OWASP baseline used in this lesson; still requires Java/Bouncy Castle and real concurrency benchmarking.
- **DelegatingPasswordEncoder** creates new hashes with id `argon2id-m19456-t2-p1`, while still verifying hashes prefixed with `{bcrypt}`, `{pbkdf2-sha256-600k}`, `{scrypt-demo-n65536}`, or `{argon2id-m19456-t2-p1}` when needed.

Ids are intentionally distinct to avoid confusing **the same algorithm with different parameters**. Do not use a generic `{pbkdf2}` id for hashes created under different configurations and expect every provider to guess iterations; use clear version/parameter ids.

## 11. JUnit Suite Testing Four Encoders and Migration

Create **src/test/java/com/example/hashchoice/HashingPolicyTests.java**:

~~~java
package com.example.hashchoice;

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class HashingPolicyTests {

    private static final String RAW = "a-safe-demo-passphrase";

    @Test
    void eachAlgorithmMatchesCorrectAndRejectsWrongPassword() {
        HashingPolicy.algorithms().forEach((name, encoder) -> {
            String encoded = encoder.encode(RAW);

            assertThat(encoded)
                .describedAs(name)
                .isNotBlank()
                .isNotEqualTo(RAW);

            assertThat(encoder.matches(RAW, encoded))
                .describedAs(name + " correct")
                .isTrue();

            assertThat(encoder.matches("wrong", encoded))
                .describedAs(name + " wrong")
                .isFalse();
        });
    }

    @Test
    void saltingProducesDifferentEncodedValues() {
        PasswordEncoder bcrypt = new BCryptPasswordEncoder(10);

        String first = bcrypt.encode(RAW);
        String second = bcrypt.encode(RAW);

        assertThat(first).isNotEqualTo(second);
        assertThat(bcrypt.matches(RAW, first)).isTrue();
        assertThat(bcrypt.matches(RAW, second)).isTrue();
    }

    @Test
    void newHashesUseArgon2idPolicyId() {
        PasswordEncoder encoder = HashingPolicy.delegating();

        String encoded = encoder.encode(RAW);

        assertThat(encoded)
            .startsWith("{argon2id-m19456-t2-p1}");
        assertThat(encoder.matches(RAW, encoded)).isTrue();
        assertThat(encoder.matches("wrong", encoded)).isFalse();
    }

    @Test
    void oldBcryptHashRemainsVerifiable() {
        String oldStored = "{bcrypt}"
            + new BCryptPasswordEncoder(10).encode(RAW);

        PasswordEncoder mixed = HashingPolicy.delegating();

        assertThat(mixed.matches(RAW, oldStored)).isTrue();
        assertThat(mixed.upgradeEncoding(oldStored)).isTrue();
    }

    @Test
    void oldPbkdf2HashRemainsVerifiableWithMatchingParams() {
        PasswordEncoder old = HashingPolicy.algorithms()
            .get("pbkdf2-sha256-600k");
        String stored = "{pbkdf2-sha256-600k}" + old.encode(RAW);

        PasswordEncoder mixed = HashingPolicy.delegating();

        assertThat(mixed.matches(RAW, stored)).isTrue();
    }

    @Test
    void unknownAlgorithmIdIsRejectedNotReadAsPlaintext() {
        PasswordEncoder mixed = HashingPolicy.delegating();

        assertThatThrownBy(() ->
            mixed.matches(RAW, "{unknown-algorithm}anything")
        ).isInstanceOf(IllegalArgumentException.class);
    }
}
~~~

These are **six JUnit test methods**. A single test can exercise multiple algorithms in a loop; coverage correctness should not be judged merely by counting test annotations. With BCrypt/scrypt/Argon2id, **do not enforce a 100 ms timeout** or fixed duration; the slowness is intentional. The code is provided to run, not as a report of execution on a learner's machine.

Testing distinct salts has an infinitesimally small theoretical collision probability, yet for sufficiently long random salts this is a reasonable practical expectation. It does not prove entropy generation is sound across every OS; inspect the implementation/RNG per system requirements when deep assurance is required.

### 11.1. What Has This Test Suite Not Proven?

- It does not measure offline cracking resistance on real GPUs or ASICs.
- It does not test login/password-change throughput under heavy load.
- It does not verify FIPS compliance.
- It does not guarantee container RAM limits hold when 50 or 500 requests arrive concurrently.
- It does not test breached-password checks, MFA, account lockout, rate limiting, or authorization.
- It does not prove legacy frameworks saved every bcrypt hash in a compatible format.

**Testing algorithms is necessary, but it does not replace benchmarking and security reviews.**

## 12. Rehashing and Upgrading Legacy Password Hashes Safely

A real system might have an account table like:

~~~text
username | password_hash
---------+--------------------------------------
alice    | {bcrypt}$2a$12$...
bob      | {pbkdf2-sha256-600k}...
carol    | {argon2id-m19456-t2-p1}$argon2id$...
~~~

Values containing ellipses are **illustrative**, not usable directly for password verification. The point is that **hashes carry ids to route to the right encoder**.

### 12.1. Opportunistic Rehashing on Login

A proper sequence:

1. The user submits username and password over an HTTPS-protected channel.
2. The authentication service loads the user and their **current stored hash**.
3. Use `DelegatingPasswordEncoder.matches(raw, stored)` with mappings covering legacy hashes.
4. Check account state and other authentication policies before issuing a session/token.
5. If login succeeds **and** `encoder.upgradeEncoding(stored)` indicates an upgrade is needed, call `encoder.encode(raw)` under the **current target id**.
6. Persist the new hash using a **concurrency-safe update**, such as `UPDATE ... WHERE user_id=? AND password_hash=?`, to avoid overwriting a concurrent password change.
7. Never return raw passwords/hashes in logs or responses, and clear credential data from unnecessary holders.
8. Once coverage is sufficient and planned, retire verification support for deprecated legacy algorithms.

With Spring Security, you can integrate **UserDetailsPasswordService.updatePassword(...)** with `DaoAuthenticationProvider` per your version's API, while verifying how the framework triggers rehashing and handles data updates. **PasswordEncoder.upgradeEncoding is only a signal; it does not update the database automatically.**

### 12.2. Why Not Rehash All Accounts with a Batch SQL Script?

You do not have the raw passwords to compute valid Argon2id hashes from old bcrypt hashes. **Argon2id(bcryptHash) is not equivalent to Argon2id(rawPassword)**; ad-hoc hash layering alters the login protocol and carries legacy design risks. Never turn an old hash into a “new password” or store double-hashes without an audited design.

Practical paths:

- Rehash **when users log in validly**.
- For inactive accounts that no longer log in, enforce a **password reset** over a secure channel if retiring legacy support is mandatory.
- If legacy hashes are dangerously weak, proactive resets and a limited support window may be necessary.
- Track metrics (without passwords/hashes) by algorithm id to see how many accounts remain un-upgraded.
- Plan rollbacks: older application instances may not understand new hash ids, so deploy in compatible rollout stages.

### 12.3. Never Enable a Plaintext Fallback for Unknown Ids

If a hash lacks a prefix or has an id absent from the map, **do not treat it like {noop}**. Never add a NoOp default matching encoder just to “stop login errors.”

Inventory real records, group them by schema/trusted origin, and write tested migrations. For raw bcrypt hashes with clear structural markers, you may normalize prefixes after verifying format validity; ambiguous strings require targeted handling or forced resets.

### 12.4. Changing Parameters Is Also a Policy Upgrade

You can stay on Argon2id while raising memory from 19 MiB to 32/64 MiB. That requires appropriate ids/metadata and `upgradeEncoding` logic; **you do not necessarily have to switch algorithm families**. For PBKDF2, changing iterations or HMAC also requires versioning. For bcrypt, cost is embedded in the encoded hash and the encoder can detect some cases needing an upgrade.

New hashes should follow current policy while old hashes remain verifiable during the allowed transition period. Never break logins by swapping a bean without validation.

## 13. Practical Benchmarking Before Choosing Cost

No single cost value fits every CPU or container. Choose by measuring instead of guessing:

1. **Establish your security baseline** from organizational policy, OWASP/NIST/RFC, and compliance rules.
2. **Measure encode and matches** on the target hardware/runtime, using the exact JDK and provider version.
3. **Warm up the JVM/JIT** before measuring. Avoid using the first encode call to represent p95/p99.
4. **Measure many samples** and examine percentiles, not just averages; never print raw passwords or hashes in benchmark logs.
5. **Measure concurrency**, especially for scrypt/Argon2id: 20 concurrent requests × 64–128 MiB can cause heavy memory pressure.
6. **Review full API latency** (database lookup, network/IdP, encoder, session) to allocate a hashing budget.
7. **Verify rate limits/queues/circuit breaking** so attackers cannot open floods of expensive password checks.
8. **Check registration/reset costs**, not just login. Encoding also consumes CPU/RAM and can be abused on unprotected endpoints.
9. **Monitor production systems** and review periodically; adjust cost as hardware, traffic, or threat models shift.
10. **Roll out versioned migrations**, never changing everything at once without rollback support.

Simple observation snippet (not a substitute for JMH benchmarks):

~~~java
// Illustrative snippet inside a method that has a PasswordEncoder.
String stored = encoder.encode("a-safe-demo-passphrase");

long started = System.nanoTime();
boolean matched = encoder.matches(
    "a-safe-demo-passphrase", stored);
long elapsed = System.nanoTime() - started;

System.out.println("matched=" + matched);
System.out.println("elapsedMs=" + elapsed / 1_000_000);
~~~

**matched=true**, while **elapsedMs has no fixed expected value**. Every machine, JVM, and load level will vary. Never use a single request's duration to deduce an attacker's offline cost; GPU/ASIC hardware and attacker parallelism differ fundamentally from a Java server.

### 13.1. Why Isn’t Slower Always Better?

If m/t/p are too high:

- Users experience sluggish logins and password resets.
- CPU or RAM spikes can cause timeouts, GC pauses, OOM crashes, and higher infrastructure bills.
- A credential-stuffing wave can turn into a **denial of service** saturating the server.
- Container autoscaling may not react fast enough to demand spikes.
- Across heterogeneous nodes, differing libraries/providers can yield uneven latencies.

**The goal is not maximizing slowness**, but raising offline guessing costs within acceptable latency, resource, and availability limits alongside online attack defenses.

## 14. Input Handling: Length, Unicode, Normalization, and Secret Management

### 14.1. Password Length

- Do not impose overly short maximum lengths merely because of a legacy DB schema or UI form.
- For bcrypt, pay special attention to the **72-byte** input limit.
- Distinguish UTF-8 bytes from Java String characters; Vietnamese diacritics and emoji can take multiple bytes.
- If supporting long passphrases, set a generous limit that still protects against gigantic DoS payloads.
- Never truncate passwords with `substring()` before hashing.
- Never change trim/case-folding/normalization behavior between registration and login.

### 14.2. Unicode and Normalization

Suppose a user registers using a string with Vietnamese diacritics in combining Unicode form, then logs in with the visually identical precomposed form. If the application lacks consistent normalization rules, the password may fail to match.

Do not normalize in one path while forgetting another; decide deliberately based on UX, identity standards, security policy, and backward compatibility. Changing normalization can break verification for existing passwords. If migration is needed, plan and test it explicitly rather than silently probing multiple variants without review.

### 14.3. Pepper and Secret Management

A pepper can reduce the impact of an attack that compromises only the database without **compromising the secret manager**. However, a pepper also makes verification depend on another secret and requires:

- Management via KMS/HSM/secret store with least-privilege access.
- A defined HMAC or vetted construction—never ad-hoc string mixing without audit.
- A rotation plan, secret versioning, and breach response if the pepper leaks.
- Backup/restore and disaster recovery preserving verification capability.
- Never printing peppers, raw passwords, or hashes in logs, metrics, or traces.

Not every application must use a pepper. **Strong passwords + proper password hashing + MFA + rate limiting + database security** usually form a far more important foundation than adding an unvetted pepper scheme.

## 15. Common Mistakes and How to Fix Them

| Mistake | Why It Is Risky | Correct Practice |
| --- | --- | --- |
| Storing plaintext passwords | Reading the database immediately exposes credentials. | Use an appropriate password hashing encoder. |
| Storing SHA-256(password) without cost/salt | Enables high-speed offline guessing. | Argon2id, scrypt, bcrypt, or PBKDF2 with proper parameters. |
| Using one shared salt across all users | Identical passwords produce identical results, losing per-user salt benefits. | Fresh random salt per encode call. |
| Testing BCryptPasswordEncoder by comparing two encode() calls | Random salts make the new hash differ from the old hash. | Call matches(raw, stored). |
| Picking cost from defaults without benchmarking | No visibility into baseline compliance, latency, or memory impact. | Check current guidance and measure in a realistic environment. |
| Using 310k PBKDF2 iterations and calling it the current OWASP baseline | Confusing framework defaults with external guidance. | Review the 600k HMAC-SHA-256 baseline noted and tune per policy. |
| Using scrypt N=2^16 from factory thinking it meets OWASP N=2^17 | Falls below a specific reference tier. | Distinguish demo/defaults from production targets. |
| Using Argon2 factory 16 MiB assuming it is 19 MiB | Wrong actual memory parameter. | Configure explicitly, measure, and document m/t/p. |
| Cranking m/t/p extremely high for “maximum security” | Logins cause DoS or RAM exhaustion. | Benchmark concurrency and enforce quotas/rate limits. |
| Using bcrypt for long passphrases without checking 72 bytes | Risk of silent input truncation depending on bcrypt behavior. | Clear input policy or choose a suitable algorithm. |
| Falling back unknown hash ids to noop | Stored values could be compared as plaintext. | Fail closed, inventory/migrate, or trigger password resets. |
| Dropping old hash verification immediately on new policy rollout | Locks out existing users. | Use DelegatingPasswordEncoder and phased migration. |
| Printing raw passwords/hashes to console for debugging | Leaks credentials into logs and telemetry. | Log only algorithm ids/counters, never secrets. |
| Rehashing before credentials are verified | Attackers could trigger invalid changes. | Rehash only after successful authentication. |
| Hashing passwords on the frontend and treating that hash as the secret | The hash becomes a replayable password equivalent. | Use TLS, proper authentication protocols, and backend password hashing. |
| Using PBKDF2 and claiming FIPS compliance | Algorithm choice alone does not equal a validated module/mode. | Verify provider, boundary, and compliance requirements. |
| Turning off rate limiting because slow hashing is enabled | Offline and online are different threat scenarios. | Keep rate limits, MFA, and credential-stuffing defenses. |

Another Spring Security pitfall: if `UserDetails#getPassword()` returns a raw password or a hash incompatible with the `PasswordEncoder` bean, `DaoAuthenticationProvider` will reject logins; **never fix this with `NoOpPasswordEncoder`**. Identify the exact hash format and encoder configuration.

## 16. Spring MVC, WebFlux, and Where Password Hashing Lives

In Spring MVC with username/password:

~~~text
HTTP request -> Servlet authentication filter
             -> AuthenticationManager / DaoAuthenticationProvider
             -> UserDetailsService.loadUserByUsername
             -> PasswordEncoder.matches(raw, stored)
             -> Authentication / SecurityContext
~~~

In WebFlux:

~~~text
HTTP request -> SecurityWebFilterChain
             -> ReactiveAuthenticationManager
             -> ReactiveUserDetailsService.findByUsername
             -> PasswordEncoder.matches(raw, stored) on a managed thread
             -> Authentication / Reactor Context
~~~

**PasswordEncoder remains a synchronous contract** even when invoked in a reactive pipeline. BCrypt/PBKDF2/scrypt/Argon2id are CPU-intensive and can consume substantial RAM. Never assume `Mono` magically turns hashing work into nonblocking I/O.

If writing a custom reactive authentication manager, take care never to block the event loop and manage schedulers and concurrency explicitly. With Spring Security's built-in mechanisms, verify the implementation for your exact version and measure real latency rather than sprinkling `.block()` in WebFlux Controllers or WebFilters.

Once again: **UserDetailsService and ReactiveUserDetailsService only look up users**, `PasswordEncoder` verifies hashes, and `AuthenticationManager`/providers determine authentication outcomes. Authorization such as `hasRole`, scopes, or object ownership is a separate step; a valid password alone never grants access to every API.

## 17. Self-Check Exercises

1. **Fast hashes:** Why is SHA-256(password) without salt or work factor a poor choice for an account database?
2. **Salt:** If two users pick the same password and `encode()` properly uses random salts, why do their hashes normally differ?
3. **Pepper:** How does a pepper differ from a salt in secrecy and storage location? How should a leak be handled?
4. **BCrypt:** How do cost 12 and cost 10 differ in computational work? Why is the 72-**byte** limit significant for Unicode passwords?
5. **PBKDF2:** Does FIPS compliance make any `PBKDF2PasswordEncoder` automatically compliant? What factors must be checked?
6. **SCrypt:** With N=65,536 and r=8, roughly how many MiB does `128×N×r` yield? Why do concurrent requests make RAM planning critical?
7. **Argon2id:** Distinguish m/t/p. Why does increasing `p` not simply multiply RAM `m` by `p`?
8. **Defaults:** Spring Security's Argon2 v5_8 factory uses 16 MiB, whereas OWASP cites 19 MiB. How would you choose production parameters?
9. **Migration:** The DB stores raw-format bcrypt hashes and the new encoder is Argon2id. Why can swapping the bean directly break logins?
10. **Delegating:** Which encoder verifies a hash prefixed with `{bcrypt}`? Which id do new hashes carry if `idForEncode` is `argon2id-m19456-t2-p1`?
11. **Rehashing:** May an account be rehashed before verifying the raw password? How do you avoid overwriting a concurrent password change?
12. **Rate limiting:** Why doesn't a strong memory-hard hash stop credential stuffing against the API?
13. **Load testing:** Design a test of 10/50/100 concurrent logins with your chosen m/t/p. Monitor CPU, RSS, GC, p95, p99, and error rates.
14. **Distinction:** Does password hashing replace encryption for data that must be decrypted for reuse? Why not?
15. **Auditing:** If a hash table is discovered leaked, what must you do beyond changing the hash algorithm? Hint: incident response, resets, MFA, audits, session/token revocation, and access controls.
16. **Versions:** Why should new projects use actively supported Spring Boot/Spring Security/Bouncy Castle versions rather than copying exact pins from an older lab?

### Algorithm Selection Checklist

- **Argon2id** is usually the preferred choice for new systems when RAM/runtime budgets allow and no conflicting compliance constraint applies.
- **scrypt** is an alternative memory-hard option when Argon2id cannot be used; verify N/r/p and concurrent memory usage.
- **PBKDF2-HMAC-SHA-256** suits many standards/FIPS requirements when paired with a **validated implementation**, enough iterations, and proper provider management.
- **bcrypt** remains useful for legacy/compatibility; verify cost, the 72-byte limit, and migration plans.
- **Unique random salt** per hash; pepper is an optional additional secret, not a salt replacement.
- **Never use fast digests or plaintext** for password storage.
- **Spring Security defaults do not automatically match current OWASP recommendations**; compare exact parameters.
- **Benchmark CPU/RAM/latency under load**; avoid self-inflicted DoS from excessive cost.
- **DelegatingPasswordEncoder** uses ids to verify multiple hash types; rehash only after valid logins.
- **Never fall back unknown algorithm ids to NoOp**, and never log raw passwords or hashes.
- **HTTPS, MFA, rate limits, credential lifecycle, and security patches** remain essential.

## Conclusion

**BCrypt, PBKDF2, SCrypt, and Argon2id can all protect passwords when configured properly, yet no single parameter set fits every system.** Choosing an algorithm requires weighing offline cracking resistance, RAM/CPU budgets, password characteristics, FIPS/compliance needs, legacy hash compatibility, and operational behavior under load. For new applications, Argon2id is the top candidate when conditions permit; systems requiring validated cryptographic modules may pick PBKDF2; legacy bcrypt setups should retain verification and upgrade in a controlled manner. In Spring Security, **PasswordEncoder** handles encode/matches and **DelegatingPasswordEncoder** supports multi-format migration, yet **true security depends on parameters, measurements, secret handling, and real authentication workflows**—not just which class you imported.
