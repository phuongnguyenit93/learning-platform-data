# Building a Test Matrix by Resource, Action, and User Group

> **Context:** Spring Security — fundamentals / Testing. This lesson shows how to turn an access policy into an **authorization test matrix** across three axes—**resource × action × user group**—and then use Spring Security Test and MockMvc to prove both allowed and denied cases. Examples use Java 17+, Spring Boot 3.5.0, Spring Security 6.x, and the Servlet stack.

## 1. The problem: a single "login succeeded" test is not enough

Suppose an application has private documents and administrative reports. Two logged-in users can both open `/api/documents/101`, but should the second user be allowed to view document 101, rename it, or delete it? Can an administrator from **another tenant** cross the tenant boundary? If an API returns `403` after data has already been modified, a test that only checks the status code can **miss a security bug**.

Three core questions:

1. **Resource:** which object is being protected — a document, report, record, attachment, order, project, list, or export?
2. **Action:** is it reading, creating, updating, deleting, sharing, approving, downloading, exporting, or administering?
3. **User group (subject group):** anonymous, owner, same-tenant colleague, editor, auditor, admin, service account, or a user from another tenant? These groups must reflect **identity + attributes + relationship to the object**, not just role names.

An *authorization test matrix* specifies **the inputs, expected policy decision, and required evidence** at each intersection. It uncovers BOLA/IDOR (reading or modifying another user's object), role/scope bugs, cross-tenant access, and overlooked paths.

**Authentication ≠ authorization.** Spring Security verifies who the user is; the application's policy must still decide what they are allowed to do with a specific resource. `.authenticated()` protects the route, but it does not know on its own who owns document 101.

## 2. Turning business requirements into testable rules

Consider a demo API for managing documents and reports with three initial documents:

| Resource | Tenant | Owner | Illustrative content |
|---|---|---|---|
| Document `101` | `east` | `alice` | `Alice plan` |
| Document `202` | `east` | `bob` | `Bob budget` |
| Document `303` | `west` | `mallory` | `West plan` |

Principals authenticated by the server with trusted tenant/role assignments:

| Caller | Tenant | Role | Relationship to test |
|---|---|---|---|
| Anonymous | — | — | No valid identity yet |
| `alice` | `east` | `USER` | Owner of 101 |
| `bob` | `east` | `USER` | Owner of 202; does not own 101 |
| `carol` | `east` | `EDITOR` | Allowed to update documents in the tenant; not allowed to delete others' documents |
| `audrey` | `east` | `AUDITOR` | Allowed to read documents/reports in the tenant; not allowed to update/delete |
| `admin` | `east` | `ADMIN` | Administrator within the east tenant |
| `mallory` | `west` | `ADMIN` | Administrator of the west tenant; **no** access to east |

**Exercise rules** (an illustrative policy, not a default policy generated by Spring Security):

- **Document READ:** same tenant **and** (is owner **or** has role `EDITOR`, `AUDITOR`, or `ADMIN`).
- **Document UPDATE:** same tenant **and** (is owner **or** has role `EDITOR` or `ADMIN`).
- **Document DELETE:** same tenant **and** (is owner **or** has role `ADMIN`).
- **Report READ:** has role `AUDITOR` or `ADMIN`; summary statistics belong only to the tenant the server verifies for the caller.
- **Anonymous:** must not call protected APIs.
- **Document not found / document in another tenant:** return `404` in the demo; a caller in the same tenant without READ permission also receives `404` to reduce object enumeration. For UPDATE/DELETE in the same tenant with insufficient permission, the demo returns `403`; this choice can reveal existence within the tenant and must be changed if a hiding policy requires 404 for every action.

The policy can be expressed in pseudocode:

~~~text
canReadDocument(user, doc) =
    sameTenant(user, doc) AND
    (isOwner(user, doc) OR hasAnyRole(user, EDITOR, AUDITOR, ADMIN))

canUpdateDocument(user, doc) =
    sameTenant(user, doc) AND
    (isOwner(user, doc) OR hasAnyRole(user, EDITOR, ADMIN))

canDeleteDocument(user, doc) =
    sameTenant(user, doc) AND
    (isOwner(user, doc) OR hasRole(user, ADMIN))

canReadReport(user) =
    hasAnyRole(user, AUDITOR, ADMIN)
    // The report only contains data for the server-verified tenant.
~~~

The `sameTenant` condition applies **even to ADMIN**. Admin privilege does not automatically cross every tenant. Explicitly distinguishing between role and ownership avoids tests where "ADMIN can do everything" ends up validating an authorization flaw.

## 3. Designing the matrix along three axes

A matrix is not a simple role table. A complete test suite can be modeled as:

~~~text
Case = {
  resourceType, resourceIdOrScope,
  action, httpMethod, route,
  actor, role, tenant, relationToResource,
  input, expectedStatus, expectedBody, expectedSideEffects
}
~~~

The most important sample matrix for document 101:

| Caller / relationship | GET 101 (READ) | PATCH 101 (UPDATE) | DELETE 101 (DELETE) |
|---|---|---|---|
| Anonymous | 401 | 401* | 401* |
| Alice — owner, east | 200 | 200 | 204 |
| Bob — non-owner USER, east | 404 | 403 | 403 |
| Carol — EDITOR, east | 200 | 200 | 403 |
| Audrey — AUDITOR, east | 200 | 403 | 403 |
| Admin — ADMIN, east | 200 | 200 | 204 |
| Mallory — ADMIN, west | 404 | 404 | 404 |

`* `For PATCH/DELETE, tests must supply a valid CSRF token when isolating **authentication/authorization** results. Without a CSRF token, Spring Security can return `403` before evaluating the caller. The demo keeps default CSRF protection enabled and uses `with(csrf())` in MockMvc so CSRF is not conflated with authorization.

Adding a second resource axis, `GET /api/reports/summary`:

| User group | Expected | Required data |
|---|---|---|
| Anonymous | 401 | Return no statistics |
| Alice / Bob (`USER`) | 403 | Return no statistics |
| Carol (`EDITOR`) | 403 | Return no statistics |
| Audrey (`AUDITOR`, east) | 200 | Count **only** east documents |
| Admin (`ADMIN`, east) | 200 | Count **only** east documents |
| Mallory (`ADMIN`, west) | 200 | Count **only** west documents |

Boundary cases that should accompany this:

- Non-existent document ID, e.g. 999: must be `404`, not turning into `403` or 500.
- Cross-tenant admin: `GET/PATCH/DELETE /api/documents/101` by Mallory is always blocked, even though Mallory has `ROLE_ADMIN`.
- POST/PATCH/DELETE without a CSRF token: must be rejected in the demo model even when the caller is the owner.
- Rejected UPDATE: **title remains unchanged** in the data store after the request.
- Rejected DELETE: the document still exists.
- Report must not include records from another tenant even when the HTTP status is 200.
- Two principals with the same USER role who own different documents must produce opposite results. Testing only a single `USER` account creates a high risk of missing object-level authorization bugs.

For maintainability, each case should have a **stable ID** (for example AUTH-DOC-READ-007), a link to the policy clause, and traceability to an automated test.

## 4. Separating expected outcomes from the implementation

When writing a matrix, determine expected outcomes from the **approved rules** before running the code. Do not take the current returned status as the expected value: a `200` vulnerability could get stamped "test passed" if expected outcomes are generated from a buggy system.

Each case needs four layers of assertions:

1. **HTTP status:** 200/204 when allowed; 401/403/404 per contract when denied.
2. **Response data:** data belongs to the right subject/tenant; does not leak title, owner, or secrets of unauthorized objects; restricts sensitive fields.
3. **State change:** allowed actions actually modify data; denied actions do not alter the database, storage, cache, or emitted messages.
4. **Boundary behavior:** routes, methods, tenants, IDs, nested IDs, roles/scopes, and request variants must be authorized under the same policy.

Example:

~~~text
Test ID: AUTH-DOC-UPDATE-BOB-101
Actor: bob (tenant=east, role=USER)
Resource: document/101 (owner=alice, tenant=east)
Action: UPDATE; PATCH /api/documents/101
Request: {"title":"Unauthorized overwrite"}
Expected: HTTP 403
Invariant: title of document 101 remains "Alice plan"
Rationale: Bob does not own 101 and does not have EDITOR/ADMIN
~~~

**A 403 response is not enough to prove there is no security flaw.** If a service writes to the DB first and only then throws an exception, the status may look right while the data has already been modified. Always verify side effects especially for DELETE, ownership transfer, payments, approvals, permission grants, sending emails, and emitting events.

### 5.3. SecurityConfig.java

~~~java
package com.example.matrix;

import jakarta.servlet.DispatcherType;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .dispatcherTypeMatchers(
                    DispatcherType.ERROR, DispatcherType.FORWARD).permitAll()
                .requestMatchers("/api/**").authenticated()
                .anyRequest().denyAll()
            )
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS));

        // Keep default CSRF protection for PATCH/DELETE.
        return http.build();
    }

    @Bean
    UserDetailsService users() {
        return new InMemoryUserDetailsManager(
            user("alice", "USER"),
            user("bob", "USER"),
            user("carol", "EDITOR"),
            user("audrey", "AUDITOR"),
            user("admin", "ADMIN"),
            user("mallory", "ADMIN")
        );
    }

    private static org.springframework.security.core.userdetails.UserDetails
            user(String name, String role) {
        return User.withUsername(name)
            .password("{noop}pw")
            .roles(role)
            .build();
    }
}
~~~

**The configuration only handles authentication at the route level.** `/api/**` requires login, but says nothing about which user can read document 101. Role data from `InMemoryUserDetailsManager` is server-owned; the `ADMIN` role is interpreted within the **tenant scope** enforced by the policy service.

CSRF remains enabled by default. For state-changing requests, valid tests use `with(csrf())`. If a PATCH test missing CSRF returns `403`, you cannot conclude the UPDATE policy was tested: `CsrfFilter` may have rejected the request earlier.

### 5.4. DocumentService.java

The demo service defines the policy in one testable place and returns data only after access is decided. `tenant` is assigned by the server from the sample identity map, not read from `X-Tenant` or client-supplied JSON.

~~~java
package com.example.matrix;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

import org.springframework.http.HttpStatus;
import org.springframework.security.authentication.AnonymousAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

@Service
public class DocumentService {

    private static final Map<String, String> USER_TENANTS = Map.of(
        "alice", "east",
        "bob", "east",
        "carol", "east",
        "audrey", "east",
        "admin", "east",
        "mallory", "west"
    );

    private final Map<Long, Document> documents = new ConcurrentHashMap<>();

    public DocumentService() {
        resetDemo();
    }

    // Fixture data; tests run sequentially by default.
    public void resetDemo() {
        documents.clear();
        documents.put(101L,
            new Document(101L, "east", "alice", "Alice plan"));
        documents.put(202L,
            new Document(202L, "east", "bob", "Bob budget"));
        documents.put(303L,
            new Document(303L, "west", "mallory", "West plan"));
    }

    public DocumentView read(long id, Authentication auth) {
        Document doc = withinTenant(id, auth);
        boolean owner = doc.owner().equals(auth.getName());

        if (!owner && !has(auth, "EDITOR")
                && !has(auth, "AUDITOR") && !has(auth, "ADMIN")) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND);
        }
        return view(doc);
    }

    public DocumentView rename(
            long id, String newTitle, Authentication auth) {
        Document doc = withinTenant(id, auth);
        boolean owner = doc.owner().equals(auth.getName());

        if (!owner && !has(auth, "EDITOR") && !has(auth, "ADMIN")) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN);
        }
        if (newTitle == null || newTitle.isBlank()) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST);
        }

        Document updated = new Document(
            doc.id(), doc.tenant(), doc.owner(), newTitle);
        documents.put(id, updated);
        return view(updated);
    }

    public void delete(long id, Authentication auth) {
        Document doc = withinTenant(id, auth);
        boolean owner = doc.owner().equals(auth.getName());

        if (!owner && !has(auth, "ADMIN")) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN);
        }
        documents.remove(id);
    }

    public ReportView report(Authentication auth) {
        if (!has(auth, "AUDITOR") && !has(auth, "ADMIN")) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN);
        }
        String tenant = tenantOf(auth);
        long count = documents.values().stream()
            .filter(doc -> doc.tenant().equals(tenant))
            .count();

        return new ReportView(tenant, count);
    }

    private Document withinTenant(long id, Authentication auth) {
        String trustedTenant = tenantOf(auth);
        Document doc = documents.get(id);
        if (doc == null || !doc.tenant().equals(trustedTenant)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND);
        }
        return doc;
    }

    private static String tenantOf(Authentication auth) {
        if (auth == null || auth instanceof AnonymousAuthenticationToken
                || !auth.isAuthenticated()) {
            throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
        }

        String tenant = USER_TENANTS.get(auth.getName());
        if (tenant == null) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN);
        }
        return tenant;
    }

    private static boolean has(Authentication auth, String role) {
        return auth != null && auth.getAuthorities().stream()
            .anyMatch(a -> a.getAuthority().equals("ROLE_" + role));
    }

    private static DocumentView view(Document doc) {
        return new DocumentView(doc.id(), doc.title());
    }

    private record Document(long id, String tenant,
                            String owner, String title) {}

    public record DocumentView(long id, String title) {}

    public record ReportView(String tenant, long documentCount) {}
}
~~~

**Security boundaries demonstrated:**

- `withinTenant(...)` runs before any READ/UPDATE/DELETE; the ADMIN role does not bypass tenant isolation.
- `read(...)` returns the document only to the owner or an authorized read role; non-owners without read permission receive 404.
- `rename(...)` and `delete(...)` check permissions **before writing**. Same-tenant callers lacking UPDATE/DELETE permission receive 403.
- `report(...)` both checks the role and filters statistics by tenant. Checking the role while forgetting to filter by tenant is still a bug.
- The controller returns `DocumentView` containing only ID/title, rather than serializing the full internal object. Production requires DTOs that restrict fields according to policy and prevent leaks through serialization.
- `resetDemo()` only supports the lesson's test fixture; do not expose an HTTP endpoint allowing users to reset data.

**Intentional limitations:** An in-memory Map lacks transactionality, locking, data isolation, and durability of a database. In a real system, use queries/mutations constrained by `tenant_id`, owner, sharing permissions, and action; test concurrency, TOCTOU, and transactions. The example uses a Map to highlight each branch of the matrix without depending on an external DB.

### 5.5. DocumentController.java

~~~java
package com.example.matrix;

import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PatchMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/documents")
public class DocumentController {

    private final DocumentService service;

    public DocumentController(DocumentService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public DocumentService.DocumentView read(
            @PathVariable long id, Authentication authentication) {
        return service.read(id, authentication);
    }

    @PatchMapping(
        path = "/{id}",
        consumes = MediaType.APPLICATION_JSON_VALUE
    )
    public DocumentService.DocumentView rename(
            @PathVariable long id,
            @RequestBody RenameRequest request,
            Authentication authentication) {
        return service.rename(id, request.title(), authentication);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(
            @PathVariable long id, Authentication authentication) {
        service.delete(id, authentication);
    }

    public record RenameRequest(String title) {}
}
~~~

**Do not pass `tenant`, `owner`, or `role` from the request into the service for authorization decisions.** The controller receives the `Authentication` verified by Spring Security. `PATCH` only allows updating the title; the client has no path in the DTO to alter the owner or tenant.

package com.example.matrix;

import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.GetMapping;

    private final DocumentService service;

    public ReportController(DocumentService service) {

    }

~~~

Reports are separated into **a second resource type** so the test matrix covers more than just documents. The report's `tenant` is verified on the server. There is no `?tenant=west` parameter letting callers pick another tenant's data.

## 6. Automating the entire matrix with MockMvc and JUnit 5

Create `src/test/java/com/example/matrix/AuthorizationMatrixTest.java`:

~~~java
package com.example.matrix;

import java.util.stream.Stream;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.Arguments;
import org.junit.jupiter.params.provider.MethodSource;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.request.MockHttpServletRequestBuilder;

import static org.springframework.security.test.web.servlet.request
    .SecurityMockMvcRequestPostProcessors.csrf;
import static org.springframework.security.test.web.servlet.request
    .SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.delete;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.patch;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class AuthorizationMatrixTest {

    @Autowired
    MockMvc mvc;

    @Autowired
    DocumentService documents;

    @BeforeEach
    void freshFixture() {
        documents.resetDemo();
    }

    static Stream<Arguments> cases() {
        return Stream.of(
            // Document READ: anonymous / owner / same-tenant / role / cross-tenant
            Arguments.of("R01 anonymous GET 101",
                null, "GET", "/api/documents/101", 401),
            Arguments.of("R02 Alice owner GET 101",
                "alice", "GET", "/api/documents/101", 200),
            Arguments.of("R03 Bob non-owner GET 101",
                "bob", "GET", "/api/documents/101", 404),
            Arguments.of("R04 Carol editor GET 101",
                "carol", "GET", "/api/documents/101", 200),
            Arguments.of("R05 Audrey auditor GET 101",
                "audrey", "GET", "/api/documents/101", 200),
            Arguments.of("R06 East admin GET 101",
                "admin", "GET", "/api/documents/101", 200),
            Arguments.of("R07 West admin GET 101",
                "mallory", "GET", "/api/documents/101", 404),
            Arguments.of("R08 Bob owner GET 202",
                "bob", "GET", "/api/documents/202", 200),
            Arguments.of("R09 Alice GET missing ID",
                "alice", "GET", "/api/documents/999", 404),

            // Document UPDATE: valid csrf() isolates authorization.
            Arguments.of("U01 anonymous PATCH 101",
                null, "PATCH", "/api/documents/101", 401),
            Arguments.of("U02 Alice owner PATCH 101",
                "alice", "PATCH", "/api/documents/101", 200),
            Arguments.of("U03 Bob non-owner PATCH 101",
                "bob", "PATCH", "/api/documents/101", 403),
            Arguments.of("U04 Carol editor PATCH 101",
                "carol", "PATCH", "/api/documents/101", 200),
            Arguments.of("U05 Audrey auditor PATCH 101",
                "audrey", "PATCH", "/api/documents/101", 403),
            Arguments.of("U06 East admin PATCH 101",
                "admin", "PATCH", "/api/documents/101", 200),
            Arguments.of("U07 West admin PATCH 101",
                "mallory", "PATCH", "/api/documents/101", 404),

            // Document DELETE: same resource, different policy.
            Arguments.of("D01 anonymous DELETE 101",
                null, "DELETE", "/api/documents/101", 401),
            Arguments.of("D02 Alice owner DELETE 101",
                "alice", "DELETE", "/api/documents/101", 204),
            Arguments.of("D03 Bob non-owner DELETE 101",
                "bob", "DELETE", "/api/documents/101", 403),
            Arguments.of("D04 Carol editor DELETE 101",
                "carol", "DELETE", "/api/documents/101", 403),
            Arguments.of("D05 Audrey auditor DELETE 101",
                "audrey", "DELETE", "/api/documents/101", 403),
            Arguments.of("D06 East admin DELETE 101",
                "admin", "DELETE", "/api/documents/101", 204),
            Arguments.of("D07 West admin DELETE 101",
                "mallory", "DELETE", "/api/documents/101", 404),

            // Report READ: second resource type.
            Arguments.of("P01 anonymous REPORT",
                null, "GET", "/api/reports/summary", 401),
            Arguments.of("P02 Alice user REPORT",
                "alice", "GET", "/api/reports/summary", 403),
            Arguments.of("P03 Carol editor REPORT",
                "carol", "GET", "/api/reports/summary", 403),
            Arguments.of("P04 Audrey auditor REPORT",
                "audrey", "GET", "/api/reports/summary", 200),
            Arguments.of("P05 East admin REPORT",
                "admin", "GET", "/api/reports/summary", 200),
            Arguments.of("P06 West admin REPORT",
                "mallory", "GET", "/api/reports/summary", 200)
        );
    }

    @ParameterizedTest(name = "{index}: {0}")
    @MethodSource("cases")
    void authorizationMatrix(
            String caseName, String username, String method,
            String path, int expectedStatus) throws Exception {

        MockHttpServletRequestBuilder request = switch (method) {
            case "GET" -> get(path);
            case "PATCH" -> patch(path)
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"title\":\"Revised\"}")
                .with(csrf());
            case "DELETE" -> delete(path).with(csrf());
            default -> throw new IllegalArgumentException(
                "Unsupported method: " + method);
        };

        if (username != null) {
            request.with(httpBasic(username, "pw"));
        }
        mvc.perform(request)
            .andExpect(status().is(expectedStatus));
    }

    @Test
    void rejectedPatchMustNotChangeData() throws Exception {
        mvc.perform(patch("/api/documents/101")
                .with(httpBasic("bob", "pw"))
                .with(csrf())
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"title\":\"Overwritten by Bob\"}"))
            .andExpect(status().isForbidden());

        mvc.perform(get("/api/documents/101")
                .with(httpBasic("alice", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.title").value("Alice plan"));
    }

    @Test
    void crossTenantAdminCannotDeleteOrReadDocument() throws Exception {
        mvc.perform(delete("/api/documents/101")
                .with(httpBasic("mallory", "pw"))
                .with(csrf()))
            .andExpect(status().isNotFound());

        mvc.perform(get("/api/documents/101")
                .with(httpBasic("alice", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.title").value("Alice plan"));
    }

    @Test
    void allowedEditorPatchChangesState() throws Exception {
        mvc.perform(patch("/api/documents/101")
                .with(httpBasic("carol", "pw"))
                .with(csrf())
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"title\":\"Approved edit\"}"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.title").value("Approved edit"));

        mvc.perform(get("/api/documents/101")
                .with(httpBasic("alice", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.title").value("Approved edit"));
    }

    @Test
    void reportIsLimitedToAuthenticatedTenant() throws Exception {
        mvc.perform(get("/api/reports/summary")
                .with(httpBasic("audrey", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.tenant").value("east"))
            .andExpect(jsonPath("$.documentCount").value(2));

        mvc.perform(get("/api/reports/summary")
                .with(httpBasic("mallory", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.tenant").value("west"))
            .andExpect(jsonPath("$.documentCount").value(1));
    }

    @Test
    void missingCsrfCannotMutateEvenOwnersDocument() throws Exception {
        mvc.perform(patch("/api/documents/101")
                .with(httpBasic("alice", "pw"))
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"title\":\"No CSRF token\"}"))
            .andExpect(status().isForbidden());

        mvc.perform(get("/api/documents/101")
                .with(httpBasic("alice", "pw")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.title").value("Alice plan"));
    }

~~~

### Why is this test organization helpful?

- `@SpringBootTest` and `@AutoConfigureMockMvc` run the **real Spring Security filter chain** in the Spring test context (without opening a TCP port). Requests go through HTTP mapping, authentication, CSRF, service policy, and serialization.
- `httpBasic(username, "pw")` creates credentials for a real fixture principal; it does not assume that swapping roles in a unit test always simulates HTTP Basic accurately.
- `@ParameterizedTest` turns 29 case rows into independent tests with clear names and expected statuses. Each row is a **resource + action + subject** intersection.
- `@BeforeEach` resets the fixture before each run, preventing a DELETE in one case from affecting another case. Do not enable parallel test execution for this singleton fixture; real systems should use database isolation/transactions or independent fixtures to run in parallel.
- `with(csrf())` on PATCH/DELETE **does not disable** CSRF protection; it simulates a client sending a valid token so authorization can be tested. A separate test intentionally omits the token.
- Three mutation tests also verify the **state invariant**: denied requests do not modify/delete data; valid requests update data as expected.
- The report test verifies `east=2` and `west=1`. If the logic returned a total of `3` for every admin, the test catches the tenant scope leak even though both statuses are 200.

In the code, `403` on `PATCH` for Bob and `404` on `GET` for Bob are defined by policy, not an automatic difference from the HTTP method. If the contract requires hiding document existence for UPDATE/DELETE as well, change the policy to 404 for insufficient same-tenant permission and update the expected matrix accordingly.

## 8. Achieving broad coverage without combinatorial explosion

If there are 20 resource types, 6 actions, 10 subject groups, 3 tenant relations, and 4 resource states, the Cartesian product reaches thousands of cases. Not every combination is meaningful or requires a separate HTTP integration test.

Design around **risk and policy boundaries**:

1. **Mandatory for every sensitive resource/action:** READ, UPDATE, DELETE, EXPORT, SHARE, APPROVE, file download; prioritize private data, financial data, and administrative privileges.
2. **Every policy branch must have one allowed case and one denied case.** For example: owner, editor, auditor, admin, and cross-tenant branches.
3. **Cross-user and cross-tenant must have opposing cases:** Alice can read doc101 while Bob cannot; East admin can read doc101 while West admin cannot.
4. **Authentication failure, anonymous, invalid credentials:** use 401 according to the API scheme; distinguish from 403 due to missing permissions after authentication.
5. **Non-existent resources, locked/archived states, soft-deleted:** ensure no data leaks and no unintended operations are allowed.
6. **For mutations, assert post-request state:** denied permissions must simultaneously avoid writing to DB, emitting events, sending notifications, or saving files.
7. **Test alternative entry points:** list, search, export APIs, GraphQL queries, nested endpoints, file downloads, background jobs/service accounts; do not test only the primary endpoint.

Testing can be layered:

| Layer | What to test? | Strengths / limitations |
|---|---|---|
| Policy unit test | `canRead/canWrite` truth table, role-owner-tenant combinations, branch coverage | Very fast; does not prove the security filter or HTTP mapping is enabled |
| MVC/security integration | HTTP status, authentication, CSRF, routes, service policy | Catches misconfigured filters, rule ordering, mappings, responses |
| DB integration | Queries with tenant/owner predicates, affected UPDATE/DELETE row counts, real side effects | Catches repository/transaction bypasses; heavier setup |
| E2E | Browser/client, cookies/sessions, headers, reverse proxy, multiple accounts | Verifies real journeys; slow and more brittle |
| Security review/manual | IDOR/BOLA, token replay, endpoints outside the matrix, privilege escalation | Helps uncover paths/attributes omitted from the test plan |

**Coverage should be measured by policy branches and API surface**, not just line coverage percentage. 100% line coverage of `DocumentController` can still miss Bob reading Alice's document. The best test specifies a **concrete object, caller, and expected behavior**.

## 9. Building a matrix from requirements via a repeatable process

### Step 1 — Inventory resources and actions

From OpenAPI specs, controllers, use cases, and the data model, identify all entry points. For example:

~~~text
Document:
  READ    GET    /api/documents/{id}
  UPDATE  PATCH  /api/documents/{id}
  DELETE  DELETE /api/documents/{id}

Report:
  READ    GET    /api/reports/summary
~~~

Later add CREATE, list/search, bulk, export, file, share/ownership transfer, and any admin routes if the product has them. Do not limit tests to three common routes when the real API exposes other endpoints.

### Step 2 — Lock down subject groups and object relationships

For role-based and ownership-based authorization, listing only `USER/ADMIN` is not enough. Record additional attributes:

~~~text
actor = alice
authn = authenticated
role = USER
tenant = east
relationship(document 101) = OWNER
relationship(document 202) = SAME_TENANT_NON_OWNER
relationship(document 303) = OTHER_TENANT
~~~

An actor can be the owner of one object and a non-owner of another. The "owner" group is a **relationship** built from the fixture, not a static role attached permanently to the user.

### Step 3 — Write the policy decision table before test code

Assign `ALLOW` / `DENY` from business requirements; then map to HTTP status and body/state invariants. For example:

~~~text
sameTenant? no  -> deny, 404
sameTenant? yes
    READ:   owner || EDITOR || AUDITOR || ADMIN
    UPDATE: owner || EDITOR || ADMIN
    DELETE: owner || ADMIN
Report READ: AUDITOR || ADMIN (tenant-scoped)
~~~

The choice of `401`, `403`, or `404` must be consistent with the authentication scheme, resource-hiding policy, and API contract. Do not default every DENY to `403`.

### Step 4 — Standardize fixtures and authentication method

Every test needs to know which document belongs to which user/tenant and which account holds which role. Avoid tests relying on random records or production data. Fixtures must include **at least two principals with the same role but different ownership**, plus a high-privilege principal from another tenant.

For JWT/OIDC, verify issuer, audience, expiry, scope, and verified tenant mapping; do not craft fake tokens and assume production accepts the same thing. For the Basic demo, `httpBasic` is the way to send credentials into the real filter chain.

### Step 5 — Generate tests from matrix data

Use `@MethodSource`, `@CsvSource`, or an appropriate test factory. When there are many cases, the data table can live in a code-reviewed YAML/JSON fixture or a test DSL, provided the **policy decision source** stays independent of production code.

Be careful: generating expected outcomes from the same `canRead(...)` function under test creates a **circular oracle**; if the policy has a bug, the test agrees with the bug. Expected outcomes must come from the approved decision table.

### Step 6 — Execute, observe, and update the matrix under control

Link test IDs to rules or requirements; when the policy changes, update the policy documentation first, assess impacted cases, and then update the implementation/tests. If a test is wrongly rejected due to CSRF, identify the true root cause instead of loosening permissions arbitrarily.

## 10. Common pitfalls when testing authorization

1. **Using only `@WithMockUser(roles="ADMIN")` for every test.** It skips credential authentication and easily masks group/tenant mapping bugs. Combine unit policy tests using mock principals with integration tests using the real authentication scheme.
2. **Testing `200` for the owner without testing a non-owner.** BOLA only surfaces when changing the **object ID** while keeping the same principal.
3. **Asserting only `status().isForbidden()`.** For mutations, verify DB/cache/events did not change. In the demo, the test re-reads the title after a rejected PATCH.
4. **Omitting CSRF for unsafe methods in tests.** A 403 result may come from `CsrfFilter` rather than `AuthorizationManager`. Use `with(csrf())` to test permissions and test missing/invalid CSRF separately.
5. **Assuming "global admin" when not in the policy.** If admins only manage their own tenant, cross-tenant ADMIN must be denied.
6. **Trusting `tenantId`, `ownerId`, or `role` sent by the client.** Test forged headers/bodies; the server must derive them from verified identity/claims and server policy.
7. **Lacking a fixture with two users sharing the same role.** Pure role tests will never catch ownership bugs.
8. **Securing detail endpoints while forgetting list/search/export.** Unfiltered queries can leak an entire tenant via lists, counts, pagination, or caches.
9. **Testing only the expected route and method.** Different HTTP methods, nested objects, bulk IDs, or legacy endpoints can also open bypass paths.
10. **Running tests with shared mutable state in parallel.** A DELETE case affects a READ case; tests become flaky/non-deterministic. Use isolated fixtures or transaction rollbacks for DB tests.
11. **Checking only 404 for cross-tenant without checking the response body.** Error messages containing title/owner or metadata can leak data.
12. **Confusing method security with HTTP request security.** `@PreAuthorize` typically requires `@EnableMethodSecurity`; `MockMvc` tests do not automatically prove every service invocation via jobs/events is also secure.
13. **Automatically substituting `hasRole("USER")` for an ownership check.** Users with the same role must still be distinguished by object and action.
14. **Treating `401 Unauthorized` as "missing role".** 401 is about authentication/challenges; insufficient permissions for an authenticated user are usually 403 or 404 depending on policy.

## 11. Criteria for a high-value test matrix

An adequate test matrix should be able to answer:

- Is there an inventory of sensitive resources/actions, including bulk/export/file and alternative paths?
- Does every policy branch have **at least one allowed and one denied case**?
- Have same-role different-owner, same-owner different-action, cross-tenant admin, anonymous, and non-existent resource cases been tested?
- Does each case specify expected status, allowed/disallowed response data, and state invariants?
- Are CSRF, authentication, role, object ownership, tenant, and business state tested separately?
- Are fixtures deterministic and isolated? Are inputs/expected outcomes derived from an independent policy?
- For denied requests, is there proof that no data was written and no side effects were emitted?
- For allowed requests, is it verified that the result is accurate and **only** within the permitted scope?
- When the policy changes, can you tell which matrix rows must be updated?

**Target capability:** you can take any Spring Security endpoint, identify its resources, actions, user groups, and object relationships; write an allow/deny matrix before running code; automate it with MockMvc/parameterized tests; and catch BOLA, role escalation, cross-tenant access, CSRF confusion, and unauthorized mutations.
