# HttpSession, Cookies, and the Relationship Between Browser and Server

**Scope:** HTTP and Jakarta Servlet fundamentals in web applications running on a Servlet container (for example, Apache Tomcat 10.1). This lesson explains session mechanics; it does not yet assume users are logged in or using Spring Security.

## 1. Why Do We Need Cookies and Sessions?

HTTP operates on a **request → response** model. A request by itself has no memory of the previous request: the server receives the path, method, headers, and body, and sends a response. Therefore, when the browser calls <code>GET /cart</code> a second time, the HTTP protocol itself does not indicate that both calls came from the same browser.

An application that wants to remember a shopping cart, preferences, or login state needs a mechanism to link requests together. Two components usually work together:

- **Cookie**: a name/value pair stored by the browser according to domain, path, and expiration rules. The server can ask the browser to store a cookie via the <code>Set-Cookie</code> header; the browser sends matching cookies in the <code>Cookie</code> header of subsequent requests.
- **HttpSession**: a server-side session object managed by the Servlet container, holding attributes keyed by a session identifier (session ID). The container typically uses a cookie named <code>JSESSIONID</code> to recognize which session a request belongs to.

**Core distinction:** <code>JSESSIONID</code> is usually just an unpredictable identifier in the browser; the actual <code>HttpSession</code> data, such as <code>cart</code> or <code>viewCount</code>, lives on the server. Cookies can serve many other purposes, and not every cookie holds only a session ID.

| Aspect | HTTP Cookie | HttpSession in Servlet |
| --- | --- | --- |
| Where does it live? | In the browser's cookie store, sent back according to matching rules | Managed by the container on the server |
| Who creates/manages it? | Server sends <code>Set-Cookie</code>; browser decides storage/sending per policy | Application creates/retrieves via <code>HttpServletRequest</code>; container manages ID/lifecycle |
| Data sent over the network | Cookie name and value sent on matching requests | Normally only the session ID travels via cookie; attributes are not sent automatically |
| Lifetime | Governed by <code>Max-Age</code>/<code>Expires</code> or browser session cookie policy | Governed by inactivity timeout, invalidation, and container configuration |
| Sharing scope | By domain/path and cookie policies | By web application and configured session storage mechanism |

## 2. Practical Flow Between Browser and Server

Suppose a Servlet application runs at <code>https://app.example</code> and needs to remember a shopping cart:

~~~text
Browser                                Servlet container / application
    |  GET /cart (no JSESSIONID yet)           |
    |----------------------------------------->|
    |                            getSession() creates HttpSession S1
    |                            stores cart in S1
    |  200 OK + Set-Cookie: JSESSIONID=abc...  |
    |<-----------------------------------------|
    |  Store cookie per Path/Domain/policy     |
    |                                          |
    |  GET /cart + Cookie: JSESSIONID=abc...   |
    |----------------------------------------->|
    |                            look up session ID -> S1
    |                            read/update cart in S1
    |  200 OK + cart contents                  |
    |<-----------------------------------------|
~~~

Abbreviated headers for illustration (real IDs are generated by the container and normally differ per session):

~~~http
GET /cart HTTP/1.1
Host: app.example

HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=opaque-session-id; Path=/; HttpOnly; Secure; SameSite=Lax
Content-Type: text/html;charset=UTF-8
~~~

On the next request, the browser automatically adds the header as long as the cookie is eligible to be sent:

~~~http
GET /cart HTTP/1.1
Host: app.example
Cookie: JSESSIONID=opaque-session-id
~~~

<code>Secure</code> and <code>SameSite=Lax</code> in the example are **illustrative settings**, not a guarantee that the container emits those exact attributes by default. They must be checked and configured for your actual container/infrastructure.

Note these common situations:

- **Two tabs in the same browser profile** normally share the cookie store for the same scope and thus share one HttpSession; opening another tab does not automatically create a new session.
- **A different browser or a private window** normally has a separate cookie store and therefore receives a different session ID.
- **Deleting cookies** removes the browser's ability to present the old ID; it does not immediately destroy the session object still sitting on the server.
- **An expired or invalidated session** means the old ID no longer maps to a valid HttpSession; the next time the application calls <code>getSession()</code>, it may create a new session.
- **No cookie** does not mean no session exists: a session may have just been created before the client received/sent the ID, or the application may have configured another tracking strategy.

## 3. Rules Governing How Cookies Are Stored and Sent

The <code>Set-Cookie</code> response header creates or updates a cookie. The <code>Cookie</code> request header carries only eligible name/value pairs; attributes like <code>HttpOnly</code> do not appear in the <code>Cookie</code> header.

| Attribute | Effect and things to remember |
| --- | --- |
| <code>Path</code> | Restricts which request paths receive the cookie; a wrong path can make the server “lose the session”. |
| <code>Domain</code> | Controls host scope; omitting it normally creates a host-only cookie for the issuing host. Do not widen the domain casually. |
| <code>Secure</code> | Sends the cookie only over secure connections per browser policy; enable for session cookies in production over HTTPS. |
| <code>HttpOnly</code> | Prevents JavaScript from reading the cookie via <code>document.cookie</code>, though the browser **still sends it automatically** on matching HTTP requests. |
| <code>SameSite=Strict</code> | Restricts sending the cookie in cross-site contexts; suitable when cross-site navigation does not need to carry the session. |
| <code>SameSite=Lax</code> | Allows certain safe top-level navigations per browser rules; often balances user experience and CSRF defense. |
| <code>SameSite=None</code> | Allows cookies in supported cross-site contexts; modern browsers typically require <code>Secure</code>, and third-party cookie blocking policies may still apply. |
| <code>Max-Age</code>/<code>Expires</code> | Controls browser-side expiration. Not identical to the server-side HttpSession timeout. |

A cookie without <code>Max-Age</code>/<code>Expires</code> is a browser *session cookie*; actual deletion timing depends on the browser and session-restore features. Nor does a long-lived cookie keep an HttpSession alive once the server has expired the session.

To protect data, **do not put passwords, sensitive session attributes, or plaintext personal data into cookies**. For a cookie holding a session ID, anyone obtaining a still-valid ID may be able to impersonate the session (session hijacking). HTTPS, proper cookie management, and XSS prevention help reduce this risk.

## 4. HttpSession Lifecycle and Servlet API

Servlets use <code>HttpServletRequest</code> to access the session:

| Call | Meaning |
| --- | --- |
| <code>request.getSession()</code> or <code>getSession(true)</code> | Returns the current session; creates one if none exists. |
| <code>request.getSession(false)</code> | Returns an active valid session, or <code>null</code>; never creates a new one. Use when only checking state. |
| <code>session.getId()</code> | Reads the session ID; never expose the ID in public logs, URLs, or production response bodies. |
| <code>session.isNew()</code> | Indicates the client has not yet joined the session as seen by the container; typically <code>true</code> on the request that created the session. |
| <code>session.setAttribute(name, value)</code> | Stores an object by key in the server-side session. |
| <code>session.getAttribute(name)</code> | Reads an object; returns <code>null</code> if absent. |
| <code>session.removeAttribute(name)</code> | Removes an attribute. |
| <code>session.setMaxInactiveInterval(seconds)</code> | Sets the inactivity threshold in seconds for the session; <code>0</code> or negative means no automatic timeout per Servlet API rules (consider container config). |
| <code>session.invalidate()</code> | Invalidates the session, making its attributes unusable via that session. Does not automatically guarantee browser cookies are deleted. |
| <code>request.changeSessionId()</code> | Rotates the ID of an existing session, useful after authentication to mitigate session fixation without creating a new HttpSession. |

A session can end due to <code>invalidate()</code>, inactivity timeout, or container changes/operations. <code>getMaxInactiveInterval()</code> returns the configured seconds, not the remaining seconds. Each request touching the session is tracked by the container per Servlet's last-accessed-time rules; do not treat it as an absolute countdown from login time.

Attributes are server-side Java objects and **are not automatically synced to the browser**. Nor does HttpSession automatically lock every operation on those objects: two concurrent requests from two tabs can update the same counter/cart and cause a race condition. For important data, use appropriate concurrency-safe update designs rather than assuming one request per session at a time.

## 5. Runnable Servlet Example: Same Cookie, Same Counter

Example using **Java 17+, Maven, Jakarta Servlet 6.0, and Tomcat 10.1**. This is a standalone demo app with no Spring Boot required. File structure:

~~~text
session-demo/
├── pom.xml
└── src/main/java/com/example/session/CounterServlet.java
~~~

Create <code>pom.xml</code>:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>session-demo</artifactId>
    <version>1.0.0</version>
    <packaging>war</packaging>
    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <dependencies>
        <dependency>
            <groupId>jakarta.servlet</groupId>
            <artifactId>jakarta.servlet-api</artifactId>
            <version>6.0.0</version>
            <scope>provided</scope>
        </dependency>
    </dependencies>
    <build>
        <finalName>session-demo</finalName>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-war-plugin</artifactId>
                <version>3.4.0</version>
            </plugin>
        </plugins>
    </build>
</project>
~~~

Create <code>src/main/java/com/example/session/CounterServlet.java</code>:

~~~java
package com.example.session;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import java.io.IOException;

@WebServlet("/counter")
public class CounterServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest request,
                         HttpServletResponse response) throws IOException {
        HttpSession session = request.getSession(); // Create if it does not exist yet.
        Integer oldCount = (Integer) session.getAttribute("viewCount");
        int count = (oldCount == null) ? 1 : oldCount + 1;
        session.setAttribute("viewCount", count);
        session.setMaxInactiveInterval(15 * 60);

        response.setContentType("text/plain;charset=UTF-8");
        response.getWriter().println("count=" + count);
        response.getWriter().println("new=" + session.isNew());
    }

    @Override
    protected void doPost(HttpServletRequest request,
                          HttpServletResponse response) throws IOException {
        HttpSession existing = request.getSession(false);
        if (existing != null) {
            existing.invalidate();
        }
        response.setStatus(HttpServletResponse.SC_NO_CONTENT);
    }
}
~~~

Explanation: <code>GET /counter</code> retrieves/creates a session and increments the <code>viewCount</code> attribute. <code>POST /counter</code> invalidates the current session if present, returning HTTP 204. This is a session lifecycle demo, **not a complete authenticated logout endpoint**. The counter update is intentionally simple: two parallel requests can suffer a lost update; do not use this read–increment–write pattern for critical counts.

Run in the project directory:

~~~bash
mvn clean package
~~~

Copy <code>target/session-demo.war</code> into Tomcat 10.1's <code>webapps</code> directory and start Tomcat. The application is deployed at context path <code>/session-demo</code>. In a shell with <code>curl</code>:

~~~bash
# 1st call: save server's Set-Cookie into a cookie jar.
curl -i -c cookies.txt http://localhost:8080/session-demo/counter

# 2nd call: send back the same cookie jar.
curl -i -b cookies.txt -c cookies.txt http://localhost:8080/session-demo/counter

# Invalidate HttpSession; then try GET with the old cookie.
curl -i -X POST -b cookies.txt http://localhost:8080/session-demo/counter
curl -i -b cookies.txt -c cookies.txt http://localhost:8080/session-demo/counter
~~~

Expected **body output when called sequentially**:

~~~text
1st GET:
count=1
new=true

2nd GET with same cookie:
count=2
new=false

POST:
HTTP 204, no body

GET after invalidate:
count=1
new=true
~~~

The <code>Set-Cookie</code> header, session ID, and other HTTP headers/ordering depend on Tomcat and your environment. If you omit <code>-b cookies.txt</code> between calls, curl does not automatically “remember” cookies like a browser, so the server may create a new session and the counter resets to 1. If deployed at another context path, adjust the URL accordingly.

## 6. How Do Session Cookies, Authentication, and Spring Security Relate?

**HttpSession is not synonymous with being logged in.** A Servlet can create a session to store a guest's unauthenticated cart. Conversely, a system can authenticate every request using a token without relying on HttpSession to hold login state.

When a Servlet application uses Spring Security in a session-based model, the security filter chain processes requests before the servlet/controller. After successful login, authentication details can be stored as a <code>SecurityContext</code> associated with the session depending on configuration. On subsequent requests, the cookie carrying the session ID lets the system look up the session and restore the security context via the configured mechanism. Do not assume every Spring Security app creates sessions: configurations like <code>SessionCreationPolicy.STATELESS</code> avoid using HttpSession to store SecurityContext across requests.

Distinguish three things in a system:

1. **Session ID** is the session lookup key; it must be unpredictable and protected like a secret.
2. **Authentication state** states which identity the current request is authenticated as; it may be tied to a session or a token.
3. **Authorization** checks whether the user has permission to perform a specific action; merely having a valid cookie is not enough to grant access.

Upon login, rotate the existing session ID to defend against **session fixation** (an attacker trying to force a victim to use an ID the attacker already knows). Servlets support <code>request.changeSessionId()</code>; Spring Security has configurable session fixation protection strategies. Upon logout, appropriately clear authentication/session state, handle cookies if needed, and prevent reuse of the old session. Clearing only the UI or a JavaScript variable does not invalidate the server-side HttpSession.

## 7. Session and Cookie Security in Practice

- **HTTPS + Secure:** use session cookies only over HTTPS in production. Configure <code>Secure</code> on cookies to match client-side TLS; behind a reverse proxy, verify the app receives accurate scheme information via trusted proxy header mechanisms.
- **HttpOnly:** restricts JavaScript from reading the session cookie, closing one XSS avenue for stealing the ID. It **does not stop XSS from making requests on the user's behalf** and is not a substitute for XSS defenses.
- **SameSite and CSRF:** browsers automatically attach cookies to matching requests, so another website can try to make the browser send state-changing requests using the victim's session. <code>SameSite</code> mitigates some risks, yet cookie-based apps still need proper CSRF protection, such as CSRF tokens for state-changing actions and never mutating state on GET.
- **Timeout and logout:** configure an appropriate inactivity timeout; call <code>invalidate()</code> on logout; avoid putting sensitive/large objects in the session unnecessarily. An unexpired cookie can point to an already expired session.
- **Do not leak session IDs:** never put IDs in logs, analytics, URLs, browser history, or error reports. A stolen ID can be used for session hijacking until it expires or is revoked.
- **Minimal cookie scope:** restrict Domain/Path as appropriate; never widen cookies to untrusted subdomains. If cross-site cookies are needed, understand <code>SameSite=None; Secure</code> and browser third-party cookie policies.

An easily confused distinction: **Same-Origin Policy, CORS, and SameSite are different layers**. CORS primarily controls whether JavaScript on another origin can read a response; it does not automatically block all form submissions or all credentialed requests. SameSite operates on the *site* context; two different origins are not necessarily two different sites.

For a frontend app calling a cross-origin API with <code>fetch</code>, browsers normally do not send cross-origin cookies unless the appropriate option is specified, for example:

~~~javascript
fetch("https://api.example.com/profile", {
  credentials: "include"
});
~~~

The server must also configure CORS credentials with explicitly allowed origins (never use wildcard <code>*</code> for credentialed responses); the cookie must still pass Domain/Path/SameSite/Secure checks and browser policies. <code>credentials: "include"</code> does not bypass those cookie restrictions.

## 8. Without Cookies: URL Rewriting and Its Limitations

Servlets support alternative session-tracking schemes, including **URL rewriting**: the session ID can be appended to URLs when needed (for example, a <code>;jsessionid=...</code> segment depending on the container). If an application needs to generate URLs capable of carrying a session ID under this mechanism, use <code>response.encodeURL(...)</code> or <code>encodeRedirectURL(...)</code> instead of concatenating the ID manually.

However, session IDs in URLs can leak via browser history, logs, bookmarks, shared links, or navigation flows. For security-sensitive web applications, secure cookies are normally preferred, and tracking can be configured to use cookies only. URL rewriting should be understood as a Servlet capability, not a default workaround for browsers blocking cookies.

## 9. Operations: Session Expiration, Multiple Servers, and Concurrent Requests

**Server-side timeout is not cookie expiration.** If the inactivity timeout is 15 minutes, the container can evict the HttpSession after that threshold; the old cookie may still remain in the browser. A request sending the old ID only tells the server which ID was requested, not that the session is still valid. You can use <code>request.isRequestedSessionIdValid()</code> to check whether the client-supplied session ID is still valid in the request context; calling <code>getSession()</code> after the old session expires may create a new session.

**Multiple instances:** if an application runs behind a load balancer while session data lives only in instance A's RAM, the next request routed to B may not find the session. You need an operational strategy such as session affinity (sticky sessions), centralized/shared session storage, or stateless design as required. Survival across restarts and replication depend on container/configuration; do not assume HttpSession is a durable data store by default.

**Concurrent requests:** a single browser can send multiple concurrent requests using the same JSESSIONID. The session object does not guarantee thread-safety for every attribute updated across multiple threads. In real applications, protect shared updates and prefer storing business data requiring consistency in a database or appropriate storage service.

## 10. Troubleshooting with Browser DevTools and curl

If an application “loses login” or “gets a new session on every refresh”, check in order:

1. In **Network**, does the first response contain <code>Set-Cookie</code>? Was a session actually created (did the app call <code>getSession()</code>)?
2. In **Application/Storage → Cookies**, was the cookie accepted by the browser? Check blocked-cookie warnings and Domain, Path, SameSite, Secure, and expiry attributes.
3. In the next request's **Request Headers**, is <code>Cookie: JSESSIONID=...</code> present? Verify matching host, path, protocol, browser profile, and credentials options.
4. If the cookie was sent, is the session ID valid? Check timeouts, <code>invalidate()</code>, ID rotation after login, container restarts, and multi-instance routing.
5. If the session exists but state is wrong, check for accidental new session creation via <code>getSession()</code>, overwritten attributes, mismatched attribute keys, or concurrent updates.

| Symptom | Causes worth checking |
| --- | --- |
| Every request has <code>new=true</code> | Cookie not stored/sent; curl missing <code>-b</code>; wrong Domain/Path/SameSite/Secure; client blocking cookies. |
| Cookie is present but cart is lost | Session expired/invalidated; request hit another instance without session state; attribute overwritten. |
| Two tabs see the same cart | Same profile and cookie scope sharing a session; this is normally expected behavior. |
| Deleting cookie leaves session on server | Browser only discarded client-side identifier; server cleans up via timeout or invalidation flow. |
| Logged out but old requests still have access | Authentication/session not invalidated or token still valid; inspect logout flow and auth policy. |
| Cross-origin API does not receive cookie | Missing credentials flag, misconfigured CORS, or cookie ineligible under browser policies. |

## 11. Knowledge Self-Check

**Scenario A:** The browser sends <code>Cookie: JSESSIONID=X</code>, but the server already timed out session X. Will the browser automatically restore the old cart from the cookie? **No.** Cookies usually hold only the ID, not the cart attribute; the server must create a new session or retrieve business data from persistent storage if the application is designed to do so.

**Scenario B:** Two tabs send requests incrementing <code>viewCount</code> simultaneously. Is the result guaranteed to increase by exactly 2? **No.** Both requests can read the same old value and overwrite each other if the application does not control concurrency.

**Scenario C:** Does enabling <code>HttpOnly</code> on a cookie completely eliminate CSRF? **No.** HttpOnly restricts JavaScript from reading the cookie value, while the browser still automatically attaches the cookie to eligible requests; proper CSRF policies, SameSite, and safe handling of state-changing operations are still needed.

**Key takeaway:** HTTP requests are protocol-independent; cookies let the browser carry information across requests; HttpSession lets the Servlet container link an ID to server-side state. Protecting session IDs and properly managing session lifecycles are foundational before learning Spring Security's login/authorization mechanisms.
