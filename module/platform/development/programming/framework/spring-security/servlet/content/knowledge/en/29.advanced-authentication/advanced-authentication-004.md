# Passkeys with WebAuthn: Credential Registration and Login

**Context:** Spring Security for **Servlet/Spring MVC**, Java 17+, Spring Boot 3.x, and a Spring Security version with the corresponding WebAuthn/passkey module. This guide covers everything from public-key credential principles to the **registration** and **authentication** flows, backend data to persist, mandatory security checks, `SecurityFilterChain` integration, JavaScript examples, and testing. Custom endpoint names in examples are always explicitly marked so they are not confused with default paths of a specific Spring Security release.

## 1. What Are Passkeys and WebAuthn Based On?

A **Passkey** is a credential based on an asymmetric key pair. During registration, the authenticator generates a **private key** protected on the device or within a passkey manager ecosystem, and sends the **public key** to the Relying Party (RP, i.e., the application). During login, the authenticator signs a fresh challenge issued by the server; the server uses the stored public key to verify the signature. The private key **is never sent to Spring Security**, and the backend does not have to store reusable passkey secrets.

**WebAuthn (Web Authentication API)** is the standard browser interface with two primary operations:

- `navigator.credentials.create({ publicKey: ... })`: requests creating a credential and returns the public key/attestation data for registration.
- `navigator.credentials.get({ publicKey: ... })`: requests an assertion signed by an existing credential for authentication.

WebAuthn belongs to the **FIDO2** ecosystem alongside CTAP for communication between the device/browser and authenticator (USB, NFC, BLE, platform authenticator, passkey manager). Spring MVC **does not implement CTAP**; the server issues WebAuthn options, verifies responses, and manages accounts/sessions.

### 1.1 How Does It Differ from Passwords and OTPs?

| Factor | Password | OTP/TOTP | Passkey/WebAuthn |
| --- | --- | --- | --- |
| Login proof | Secret known by the user. | Temporary code or shared secret. | Valid signature from a private key bound to the RP ID. |
| Server stores | Password hash. | OTP verification data. | Credential ID + public key + account mapping. |
| Phishing susceptibility | Can be entered into a fake site. | OTP can be relayed. | Bound to RP ID/origin, much stronger phishing resistance. |
| Experience | User types password. | Reads/enters code. | Device prompt, PIN/biometrics/security key per authenticator. |
| Recovery needed | Yes. | Yes. | Yes, especially if all devices/passkeys are lost. |

**Biometrics never leave for the server.** Face ID, fingerprint, or PIN only unlocks the authenticator and satisfies local user verification on the device. The backend receives a signature and **User Presence (UP)** / **User Verification (UV)** flags—not face images or fingerprint templates.

Passkeys may be **synced across multiple devices** or **bound to a hardware authenticator**; not every passkey is hardware-bound. Therefore, device policies, attestation, and sign counters must be chosen based on real risk.

## 2. Terminology and Trust Boundaries

| Term | Meaning |
| --- | --- |
| **Relying Party (RP)** | The application registering/verifying credentials, e.g., Spring MVC Portal. |
| **RP ID** | Logical domain of the credential, such as `example.com` or `localhost`; does **not** include scheme, port, or path. |
| **Origin** | Scheme + host + port of the page calling WebAuthn, e.g., `https://login.example.com` or `http://localhost:8080`. |
| **Authenticator** | The component holding the private key, creating credentials, and signing assertions. |
| **User handle** | Stable bytes representing the account at the RP; avoid using mutable emails as immutable IDs. |
| **Credential ID** | Credential identifier; used by the backend to look up the registered public key. |
| **Challenge** | Random byte sequence generated by the backend for one registration/login; has TTL and must prevent replay. |
| **Public key** | Public key from registration, stored on the backend to verify signatures. |
| **Attestation** | Optional information about authenticator provenance/policy during registration. |
| **Assertion** | Authentication result containing authenticator data, client data, and signature. |
| **Discoverable credential** | Credential that an authenticator can locate by RP ID, enabling username-less login. |

### RP ID Differs from Origin

For example, a user visits `https://login.example.com`. The RP ID can be `example.com` if it satisfies domain validity rules, while the page’s **origin** remains `https://login.example.com`. The server must configure both a **fixed RP ID** and an **exact origin allowlist**. WebAuthn includes the hash of the RP ID in authenticator data; `clientDataJSON` contains the origin, and the server must verify both.

- `rpId: "example.com"` is a domain name, **not** `"https://example.com:443"`.
- `origin: "https://login.example.com"` includes the scheme; non-default ports (if any) are part of the origin.
- Never use an arbitrary RP ID like `"com"` or a domain outside your site’s scope.
- `localhost` with `http://localhost:8080` is commonly a secure-context exception for **development**. Production should use real HTTPS and a managed domain.
- Changing the RP ID after issuance can make old credentials unusable on the new domain; plan domains/RP IDs upfront.

**Never take RP ID and allowed origins from the client’s request JSON.** They are trusted backend configuration. A request with a plausible-looking `Origin` header is not proof by itself; the WebAuthn verifier must validate `origin` inside the response’s client data.

## 3. What Must Be Stored for a Credential?

Recommended storage model per credential:

| Field | Data Type | Purpose |
| --- | --- | --- |
| `account_id` | Internal User ID | Links to the verified account. |
| `user_handle` | Stable bytes | Links WebAuthn user entity to the account, enabling username-less login. |
| `credential_id` | Bytes / Base64url, **unique** | Finds the credential from an assertion. |
| `public_key` | COSE public key or library-supported format | Verifies login signatures. |
| `algorithm` | COSE algorithm | Selects the verifier matching the registered algorithm. |
| `signature_count` | Non-negative integer | Monitors cloning signals when the authenticator maintains meaningful counters. |
| `backup_eligibility / backup_state` | BE/BS flags, if present | Observes whether backup/sync capabilities apply. |
| `transports` | internal, usb, nfc, ble, hybrid… | Hint for browser UX; not authorization evidence. |
| `status` | active/revoked | Blocks deactivated credentials. |
| `created_at / last_used_at / label` | Metadata | Manages the passkey list and auditing. |

**Private keys, PINs, fingerprints, and face templates** do not belong in the backend database. Credential IDs/public keys are not password-like secrets, yet user handles, credential IDs, and attestation metadata can still identify users and require protection and retention policies.

Challenges must be stored temporarily in a challenge repository/cache (with TTL, operation type, and binding). Credentials can coexist across multiple devices; an account can own **multiple passkeys**. Use a unique constraint on credential ID rather than relying solely on JavaScript `excludeCredentials` to prevent duplicates.

## 4. Registering a Passkey: The Registration Flow

Typically, a user is already logged in via password/MFA, OIDC, or a secure bootstrap mechanism before adding a passkey. Registration grants **a new way to log in** to the account, so CSRF protection and authorization/re-authentication checks based on risk are mandatory.

```text
User             Browser                  Spring Servlet RP            Authenticator
 |  Add passkey     |                             |                           |
 |----------------->| POST registration options   |                           |
 |                  |---------------------------->|                           |
 |                  |  challenge + rp + user + options                         |
 |                  |<----------------------------|                           |
 |                  | navigator.credentials.create({publicKey})                |
 |                  |-------------------------------------------------------->|
 |                  |           create keypair, require PIN/UV if needed      |
 |                  |<--------------------------------------------------------|
 |                  | credentialId + clientDataJSON + attestationObject       |
 |                  | POST registration verify    |                           |
 |                  |---------------------------->|                           |
 |                  | verify challenge/origin/RP/flags, persist public key    |
 |                  |<----------------------------|                           |
 |  Passkey added   |                             |                           |
```

This is a **protocol diagram**. In the JavaScript section below, `/passkeys/registration/options` and `/passkeys/registration/verify` are **illustrative application-implemented APIs**, not a promise of default endpoints in a Spring Security release.

### 4.1 Generating Creation Options on the Backend

The backend generates a **fresh challenge from a CSPRNG** (e.g., 32 random bytes) and stores a pending challenge bound to the account/session/`REGISTRATION` flow with a short expiration. Return configuration equivalent to the following JSON to the browser:

```json
{
  "challenge": "<fresh-base64url-challenge>",
  "rp": { "id": "localhost", "name": "Passkey Demo" },
  "user": {
    "id": "<stable-base64url-user-handle>",
    "name": "alice@example.test",
    "displayName": "Alice"
  },
  "pubKeyCredParams": [
    { "type": "public-key", "alg": -7 },
    { "type": "public-key", "alg": -257 }
  ],
  "authenticatorSelection": {
    "residentKey": "required",
    "userVerification": "required"
  },
  "attestation": "none",
  "timeout": 60000,
  "excludeCredentials": []
}
```

Values inside `<...>` are **descriptive data-format placeholders** and cannot be sent directly to a browser as a valid challenge.

- `challenge`: Base64url string representing **random bytes**, different per attempt, never derived solely from timestamps or usernames.
- `rp.id`: backend-configured RP ID; `rp.name` is display-only.
- `user.id`: stable opaque **byte identifier**, distinct from username/email; `name` and `displayName` are display fields.
- `pubKeyCredParams`: list of COSE algorithms supported by the backend; `-7` is typically ES256, `-257` is RS256.
- `residentKey: "required"` requests a **discoverable credential** for username-less passkey login. If used only as a second factor, `preferred` can be considered based on UX and policy.
- `userVerification: "required"` requires local user verification; it does not mean the backend receives biometrics.
- `attestation: "none"` suits many consumer apps that do not need device-model identification. Attestation is managed separately if an organization has hardware/enterprise policies.
- `excludeCredentials` hints to the authenticator to avoid recreating known credentials; the backend must still enforce uniqueness.
- `timeout` is a browser hint; the server must enforce its own TTL and one-time use.

### 4.2 Authenticator Creates the Credential

The browser calls `navigator.credentials.create` and receives a `PublicKeyCredential` object. Key fields:

- `credential.id` or `rawId`: credential identifier.
- `response.clientDataJSON`: JSON containing `type = "webauthn.create"`, `challenge`, `origin`, and contextual properties.
- `response.attestationObject`: CBOR containing authenticator data (including public key/credential ID during registration) and attestation statement.
- `response.getTransports()`: hint of supported device transports, if the API is available.
- `getClientExtensionResults()`: extension results if used.

The browser does not expose the private key to JavaScript. The passkey manager decides where the credential is stored and whether it syncs.

### 4.3 Server Verifies Registration Before Persisting

A trustworthy WebAuthn server verifier must:

1. Locate the pending registration challenge and verify **matching session + account + purpose**, unexpired, and unused.
2. Parse `clientDataJSON`; check `type="webauthn.create"`, challenge **matches original bytes**, `origin` is allowed, and any applicable cross-origin/top-origin rules.
3. Parse CBOR attestation and authenticator data: check `rpIdHash == SHA-256(rpId)`, **UP** flag, **UV** flag when policy requires it, attested credential data structure, and an allowed key algorithm.
4. If policy requires attestation trust, verify the chain/metadata/attestation statement per standard; when using `attestation:"none"`, **do not** assume the device belongs to a specific trusted model.
5. Extract the verified credential ID and public key, **bind to the server-side authenticated account**, and verify the credential ID does not belong to another account.
6. Mark the challenge used atomically and persist inside a safe transaction; return success only after DB confirmation, and audit the event.

The server must never trust a `user.id`/`accountId` sent by the client in the verify body to pick an account; integrity must rely on the verified session, challenge binding, and credential data.

## 5. Logging In with a Passkey: The Authentication Flow

Login must use a **fresh challenge** and an **assertion signature** rather than trusting a credential ID alone.

```text
Browser                   Spring Servlet RP                Authenticator
  |  POST login options          |                                |
  |----------------------------->|                                |
  |  challenge + rpId + UV policy|                                |
  |<-----------------------------|                                |
  | navigator.credentials.get({publicKey})                         |
  |--------------------------------------------------------------->|
  |                        Choose passkey, user presence/verification |
  |<---------------------------------------------------------------|
  |  credentialId + authenticatorData + clientDataJSON + signature |
  | POST login verify            |                                |
  |----------------------------->|                                |
  | verify challenge/origin/rp/signature/account mapping          |
  | create Spring Authentication/session if valid                 |
  |<-----------------------------|                                |
  | GET /me + session cookie     |                                |
  |----------------------------->|                                |
```

### 5.1 Username-First vs. Username-Less Login

**Username-first:** frontend asks for username/email; backend looks up registered credential IDs for the account and returns `allowCredentials`. After the assertion, the backend must verify the credential actually belongs to the chosen account.

**Username-less (discoverable):** backend returns options without `allowCredentials`; the authenticator/browser can offer passkeys matching the RP ID. The backend looks up the account by **credential ID** after verification and checks `userHandle` if present. Never pick the account from a client-supplied username in the verify request.

Example login request options:

```json
{
  "challenge": "<fresh-base64url-challenge>",
  "rpId": "localhost",
  "userVerification": "required",
  "timeout": 60000
}
```

With username-first, the backend can add:

```json
{
  "allowCredentials": [
    {
      "type": "public-key",
      "id": "<registered-credential-id-base64url>",
      "transports": ["internal", "hybrid"]
    }
  ]
}
```

Credential IDs are not login secrets, yet you should avoid needlessly exposing credential lists and account status; consider anti-user-enumeration and rate limiting.

### 5.2 What Does a Browser Assertion Contain?

The response from `navigator.credentials.get` includes:

- `id`/`rawId`: credential identifier for the backend to look up the public key.
- `response.clientDataJSON`: `type="webauthn.get"`, challenge, origin, and context.
- `response.authenticatorData`: `rpIdHash`, UP/UV, `signCount`, and flags.
- `response.signature`: authenticator signature over **`authenticatorData || SHA-256(clientDataJSON)`**.
- `response.userHandle`: may be null in some flows; if present, verify mapping.

**A matching Credential ID is not enough to log in**: it can be public information. The server must verify the signature using the **public key registered for that credential ID** and all challenge/RP/origin/flag bindings.

### 5.3 Server Verifies the Assertion

1. Load the pending login challenge: unexpired, matching flow/session/attempt, and unused.
2. Check `clientDataJSON.type = "webauthn.get"`, challenge byte match, origin in allowlist; handle cross-origin per policy.
3. Check `rpIdHash` equals SHA-256(configured RP ID).
4. Check **UP** flag and **UV** flag if policy requires it. Asking the browser for UV does not guarantee the authenticator performed it unless the server checks the flag.
5. Find the active credential by credential ID, verify it is not revoked, matches the account, and `userHandle` matches if present.
6. Verify the signature with the stored public key/algorithm and exact signed bytes.
7. Handle `signCount` and BE/BS backup flags per risk policy. Synced passkeys may report counter 0 or non-monotonic counters; do not assume every 0 counter is a clone.
8. Consume the challenge once, update last-used/counter, and complete **Spring Security Authentication/SecurityContext/session** using the proper framework handler/mechanism.

A controller returning JSON `{"authenticated":true}` without creating/saving a `SecurityContext` **is not a real login**. Session fixation protection, security context persistence, and authorization rules must operate after verification.

## 6. Integrating into Spring Security Servlet

Modern Spring Security versions include a module supporting **WebAuthn/passkeys** via the `HttpSecurity.webAuthn(...)` DSL. **Verify version/module before applying**: an older Spring Security project may not have `webAuthn`; default endpoints, repository interfaces, and UI differ by release. Avoid inventing “default” endpoint names without checking the actual library.

### 6.1 Configuring Spring Boot with the WebAuthn DSL

With a BOM managing a Spring Security version that includes the WebAuthn module, Gradle dependencies can include:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.security:spring-security-webauthn'
}
```

**`src/main/java/com/example/passkey/SecurityConfig.java`**

```java
package com.example.passkey;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/login", "/assets/**").permitAll()
                .anyRequest().authenticated()
            )
            .formLogin(Customizer.withDefaults())
            .webAuthn(webAuthn -> webAuthn
                .rpId("localhost")
                .rpName("Passkey Demo")
                .allowedOrigins("http://localhost:8080")
            );

        return http.build();
    }
}
```

**`src/main/java/com/example/passkey/PasskeyDemoApplication.java`**

```java
package com.example.passkey;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class PasskeyDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(PasskeyDemoApplication.class, args);
    }
}
```

**Explanation and runnable scope:** this configuration targets a release supporting the WebAuthn DSL and is **not** a plain Java program compiled with raw `javac`. Create a Spring Boot/Spring MVC project from Spring Initializr with Java 17+, install the compatible WebAuthn module, Gradle wrapper, and matching user/repository/UI configuration. If Spring cannot find `webAuthn` at compile time, check the **version/module** before changing business logic. Run with `./gradlew bootRun` (Windows: `.\gradlew.bat bootRun`) once framework/registration UI components are in place.

In the example, `formLogin` can serve as a **bootstrap login** so a user who has proven account ownership can register a passkey; a production app may choose another bootstrap mechanism. `webAuthn` lets Spring manage the module flow, but you still must design a **durable credential repository, account mapping, revocation, authorization, session management, and recovery**. Never infer that adding this snippet alone provides a production schema, complete passkey management pages, or custom endpoints.

**Development:** `rpId("localhost")` and `allowedOrigins("http://localhost:8080")` apply only when the browser invokes WebAuthn from this localhost origin. **Production:** use the RP ID and allowed origins of your real HTTPS website, avoiding wildcards and uncontrolled origins. If HTML is served from a frontend origin different from the backend API, determine browser origin, cookies/CSRF/CORS, and RP ID architecture upfront.

**Security defaults:** keep CSRF protection for state-changing endpoints backed by session cookies. Never call `csrf.disable()` just because test registration/login returns 403. When a Spring Security module defines its own endpoints and CSRF integration, the frontend must follow the **actual contract** of that release.

### 6.2 When Implementing Endpoints Yourself with Another WebAuthn Library

If not using Spring’s WebAuthn DSL or needing custom workflows, choose a **maintained and tested server-side WebAuthn verifier library**, integrating:

- `/passkeys/registration/options` — only for verified accounts authorized to add credentials.
- `/passkeys/registration/verify` — verify WebAuthn registration, persist credential with transaction/unique constraint.
- `/passkeys/login/options` — generate challenge, return request options for login.
- `/passkeys/login/verify` — verify assertion, create Spring `Authentication`, save `SecurityContext` and secure session.

These are **custom route names** for this lesson, not framework Java APIs. Use an appropriate `AuthenticationProvider`/filter or authentication success handler and `SecurityContextRepository` so login persists properly across the lifecycle. **Never write CBOR/COSE parsers and signature verification algorithms from scratch** for production.

## 7. JavaScript: Converting Binary Correctly Before Calling WebAuthn

WebAuthn uses `ArrayBuffer`/`Uint8Array` for challenges, user handles, credential IDs, and responses. JSON transports binary data via **Base64url**. Never pass a Base64url string into `new TextEncoder().encode(...)` as the challenge: that produces bytes of the **encoded string**, not the original challenge bytes.

### 7.1 Base64url ↔ Binary Helpers

```javascript
function decodeBase64url(input) {
  const base64 = input.replace(/-/g, "+").replace(/_/g, "/");
  const padded = base64.padEnd(Math.ceil(base64.length / 4) * 4, "=");
  const raw = atob(padded);
  return Uint8Array.from(raw, ch => ch.charCodeAt(0));
}

function encodeBase64url(buffer) {
  const bytes = new Uint8Array(buffer);
  let binary = "";
  for (const byte of bytes) binary += String.fromCharCode(byte);

  return btoa(binary)
    .replace(/\+/g, "-")
    .replace(/\//g, "_")
    .replace(/=+$/g, "");
}

function requireWebAuthn() {
  if (!window.PublicKeyCredential || !navigator.credentials) {
    throw new Error("WebAuthn is not available in this context");
  }
}
```

`decodeBase64url` accepts a valid Base64url string and returns exact bytes. `encodeBase64url` works on response `ArrayBuffer`s. Newer browsers may support `PublicKeyCredential.parseCreationOptionsFromJSON`, `parseRequestOptionsFromJSON`, and `credential.toJSON()` to reduce conversion boilerplate, though target browser support should be checked.

### 7.2 POST JSON Helper with CSRF Token

This example contract assumes the frontend shares an origin with the Spring Servlet app and already has a valid CSRF token supplied by the server via HTML/endpoint. Header/token names must match the application’s repository/request handler.

```javascript
async function postJson(url, payload, csrfToken) {
  const response = await fetch(url, {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-TOKEN": csrfToken
    },
    body: JSON.stringify(payload)
  });

  if (!response.ok) {
    throw new Error("HTTP " + response.status + " at " + url);
  }
  return response.json();
}
```

The example above does not generate `csrfToken`; the token must be issued by the server and sent by the browser per active Spring Security policy. Never hardcode a fake/static token or disable CSRF to bypass 403.

### 7.3 Passkey Registration Client

```javascript
async function registerPasskey(csrfToken) {
  requireWebAuthn();

  // Custom application endpoints, not Spring default endpoints.
  const options = await postJson(
    "/passkeys/registration/options", {}, csrfToken
  );

  const publicKey = {
    ...options,
    challenge: decodeBase64url(options.challenge),
    user: {
      ...options.user,
      id: decodeBase64url(options.user.id)
    },
    excludeCredentials: (options.excludeCredentials ?? []).map(c => ({
      ...c,
      id: decodeBase64url(c.id)
    }))
  };

  const credential = await navigator.credentials.create({ publicKey });
  if (!credential || credential.type !== "public-key") {
    throw new Error("No credential created");
  }

  const response = credential.response;
  const payload = {
    id: credential.id,
    rawId: encodeBase64url(credential.rawId),
    type: credential.type,
    response: {
      clientDataJSON: encodeBase64url(response.clientDataJSON),
      attestationObject: encodeBase64url(response.attestationObject),
      transports: typeof response.getTransports === "function"
        ? response.getTransports() : []
    },
    clientExtensionResults: credential.getClientExtensionResults()
  };

  return postJson(
    "/passkeys/registration/verify", payload, csrfToken
  );
}
```

**Success condition:** the server verified it, saved it to the DB, linked it to the right account, and returned a success response. The user confirming PIN/fingerprint **is not enough** to report “registration complete” if the backend has not persisted it. Browsers may throw `NotAllowedError` when the user cancels the prompt or times out, and `NotSupportedError` when the authenticator/policy is unsupported.

### 7.4 Passkey Login Client

```javascript
async function loginWithPasskey(csrfToken) {
  requireWebAuthn();

  const options = await postJson(
    "/passkeys/login/options", {}, csrfToken
  );

  const publicKey = {
    ...options,
    challenge: decodeBase64url(options.challenge),
    allowCredentials: options.allowCredentials?.map(c => ({
      ...c,
      id: decodeBase64url(c.id)
    }))
  };

  const credential = await navigator.credentials.get({ publicKey });
  if (!credential || credential.type !== "public-key") {
    throw new Error("No assertion received");
  }

  const response = credential.response;
  const payload = {
    id: credential.id,
    rawId: encodeBase64url(credential.rawId),
    type: credential.type,
    response: {
      authenticatorData: encodeBase64url(response.authenticatorData),
      clientDataJSON: encodeBase64url(response.clientDataJSON),
      signature: encodeBase64url(response.signature),
      userHandle: response.userHandle
        ? encodeBase64url(response.userHandle) : null
    },
    clientExtensionResults: credential.getClientExtensionResults()
  };

  return postJson("/passkeys/login/verify", payload, csrfToken);
}
```

If `options.allowCredentials` is absent, the browser can choose a **discoverable credential** matching the RP ID; if present, it usually selects from the specified credential set. The backend must perform signature/account-mapping verification, then create `Authentication` and the session. This JS code is a **client-only sketch**—backend endpoints must be implemented per contract; it cannot run standalone with only Spring MVC static files.

## 8. Standalone Java 17 Example: Generating a Random Challenge

Only the following challenge-generation snippet is **Java SE**, compiling with JDK 17 without Spring. It demonstrates **SecureRandom** and Base64url, not a WebAuthn verifier.

**`WebAuthnChallengeDemo.java`**

```java
import java.security.SecureRandom;
import java.util.Base64;

public final class WebAuthnChallengeDemo {

    public static void main(String[] args) {
        byte[] challenge = new byte[32];
        new SecureRandom().nextBytes(challenge);

        String base64url = Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(challenge);

        System.out.println("bytes=" + challenge.length);
        System.out.println("base64urlLength=" + base64url.length());
        System.out.println("containsPadding=" + base64url.contains("="));
    }
}
```

Compile and run:

```bash
javac WebAuthnChallengeDemo.java
java WebAuthnChallengeDemo
```

**Exact** stdout (without printing the random challenge value):

```text
bytes=32
base64urlLength=43
containsPadding=false
```

32 bytes = 256 bits, encoded to 43 unpadded Base64url characters. The challenge value **must differ across attempts**, be stored with TTL/flow/binding, and be single-use. Never use usernames, timestamps, or predictable UUIDs as the sole challenge source.

## 9. Backend Pseudocode and Where a WebAuthn Library Is Needed

This is **pseudocode**, not an actual Java API. Methods like `verifier.verify...` represent a tested WebAuthn verifier library; do not copy directly as production code.

```text
createRegistrationOptions(authenticatedUser, session):
    requireUserCanAddPasskey(authenticatedUser)
    challenge = secureRandomBytes(32)
    savePending(
        kind=REGISTRATION, account=authenticatedUser.id,
        session=session.id, expiresInMinutes=3, oneTime=true
    )
    return creationOptions(challenge, rpId, stableUserHandle, policy)

finishRegistration(authenticatedUser, response, session):
    pending = atomicallyConsumePending(REGISTRATION, session)
    requirePendingMatchesAccountAndNotExpired(pending, authenticatedUser)
    result = verifier.verifyRegistration(
        response, expectedChallenge=pending.challenge,
        expectedOrigins=trustedOrigins, expectedRpId=rpId,
        userVerificationPolicy=policy
    )
    requireCredentialIdUnique(result.credentialId)
    savePublicKeyCredentialInTransaction(
        account=authenticatedUser.id, credential=result
    )
    audit("passkey-added")

createLoginOptions(session, optionalAccount):
    challenge = secureRandomBytes(32)
    savePending(LOGIN, session=session.id, expiresInMinutes=3)
    return requestOptions(challenge, rpId, accountCredentialsIfAny)

finishLogin(response, session):
    pending = atomicallyConsumePending(LOGIN, session)
    requireNotExpired(pending)
    stored = findActiveCredential(response.rawId)
    requireExists(stored)
    verified = verifier.verifyAssertion(
        response, stored.publicKey, stored.algorithm,
        expectedChallenge=pending.challenge,
        expectedOrigins=trustedOrigins, expectedRpId=rpId,
        requireUserVerification=true
    )
    requireVerified(verified)
    requireUserHandleMatchesAccountIfPresent(verified, stored)
    updateCounterBackupFlagsAndLastUsedSafely()
    completeSpringAuthenticationAndSession(stored.account)
    audit("passkey-login")
```

Atomicity of challenge consumption and data persistence must be designed consistently across transactions/caches. Test two competing requests with the same challenge: **only one** may succeed. Never rely on disabling the submit button in the frontend to prevent replay.

### 9.1 Mandatory Server-Side Verification Table

| Condition | Registration | Authentication |
| --- | --- | --- |
| Pending challenge matches flow, TTL, one-time | Yes | Yes |
| `clientDataJSON.type` | `webauthn.create` | `webauthn.get` |
| `clientDataJSON.challenge`, origin | Match | Match |
| `rpIdHash` from authenticator data | Match RP ID | Match RP ID |
| UP/UV per policy | Check | Check |
| Attestation/credential public key | Parse and verify before saving | Use stored public key |
| Assertion signature | Not an assertion flow | **Mandatory verify** |
| Credential ID/account | Unique, bound to current account | Trusted mapping lookup, active/not revoked |
| User handle | Bind user entity | Match if present |
| Sign counter/backup flags | Store initially | Evaluate and update |
| Spring Security session | Require sufficiently privileged session when registering | Establish after verified login |

**Never self-authenticate by reading Base64 `clientDataJSON` and only comparing the challenge:** you must verify the entire origin/RP hash/flags and signature over the exact bytes and algorithm. A standard library prevents mistakes in CBOR/COSE parsing, DER/raw signature encoding, and state checks.

## 10. Design Choices and Real-World Risks

### 10.1 Single-Factor Passkey or MFA?

**Passwordless:** the user logs in with a passkey only, so set `userVerification:"required"` aligned with the auth model and verify the UV flag on the backend. Some authenticators/platform browsers have UX limitations; provide a sufficiently strong fallback.

**MFA/step-up:** a passkey can serve as one factor in a multi-step flow. Do not assume adding WebAuthn automatically satisfies every MFA policy; understand whether the authenticator provides UV, how the session is bound, and which factors/assurance the organization requires.

### 10.2 Passkey Syncing and Sign Counters

Some passkeys sync across multiple devices; counters may be 0 or fail to increment like traditional hardware keys. `signCount` and BE/BS flags should be used as **risk signals matched to authenticator characteristics**, not rigid conditions that break valid passkeys. Do not drop monitoring completely if production enforces anti-cloning policies.

### 10.3 Attestation

`attestation:"none"` is common for consumer UX and privacy. An enterprise application requiring managed-only devices can use attestation trust validation/approved hardware; that is an **additional evidence-backed policy**, not something automatically obtained when given a public key. Never trust client-sent AAGUIDs or model strings without proper verification.

### 10.4 Account Recovery and Revocation

- Allow users to register multiple passkeys to avoid a single point of failure.
- Provide UI to view, name, and **revoke** passkeys, requiring an authenticated/step-up session and a CSRF token.
- If all devices are lost, recovery must be sufficiently strong, with cooldowns/auditing/anti-abuse matching risk. Weak recovery negates phishing resistance.
- Locked/deleted accounts must disable associated credentials; update mappings/backup policies.
- WebAuthn login does not prove every subsequent request; keep session timeouts, logout, session fixation protection, and backend authorization.

### 10.5 CSRF, XSS, and Web Sessions

In a Servlet app authenticated with session cookies, browsers automatically attach cookies. **Registering a new credential** is a highly sensitive action requiring CSRF protection; if an attacker forces a victim to register the attacker’s passkey, account takeover occurs. Login also needs protection against **login CSRF** and proper challenge/session binding. Never disable `csrf()` just because the passkey flow uses public-key cryptography.

WebAuthn reduces phishing on spoofed domains via RP ID/origin binding, but **does not fix XSS on the real origin**, authorization bugs, session theft, or weak recovery. Use HTTPS, CSP/escaping, `Secure`/`HttpOnly`/`SameSite` cookies, CSRF, and complete server-side authorization.

## 11. Common Errors and Real Root Causes

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `navigator.credentials` missing | Insecure context, unsupported browser/platform. | Use HTTPS or trusted localhost dev; check support. |
| `SecurityError` creating/getting credential | Wrong RP ID domain, disallowed origin, restricted iframe/policy context. | Verify exact RP ID and allowed origins, plus iframe policy if used. |
| `NotAllowedError` at prompt | User canceled, timed out, UV unmet, or no authenticator. | UX fallback, never treat as success; inspect options and capabilities. |
| Backend reports challenge mismatch | Stale/wrong-flow challenge, Base64url encoded incorrectly. | Decode to bytes before WebAuthn; store challenge one-time, compare original. |
| Browser registration succeeds but not saved | Server attestation/origin/RP/UV check failed, DB unique or transaction error. | Debug verifier safely, never remove security checks. |
| `InvalidStateError` on registration | Credential already exists / `excludeCredentials`. | Show passkey management UI, handle duplicates properly. |
| Assertion cannot find credential | Not persisted, storage reset, different RP ID, or wrong mapping. | Check credentialId/DB and consistent RP ID. |
| Assertion signature invalid | Wrong public key/alg, altered bytes, forged response. | Use standard verifier library, never roll custom crypto. |
| Login verify OK but subsequent requests return 302/401 | `Authentication` not created/saved in `SecurityContext`, invalid session cookie. | Integrate authentication success/session persistence, inspect cookies. |
| Registration POST returns 403 | Missing/invalid CSRF token or insufficient user permissions. | Separate CSRF error from WebAuthn, do not disable CSRF. |
| Synced passkey fails when counter does not increase | Backend assumes every authenticator counter increments. | Handle counter/BE/BS per appropriate policy. |
| Passkey “lost” after host/domain change | Credential bound to previous RP ID. | Plan domains/RP/migration/recovery. |
| User authenticated but sees wrong account | Backend trusts client-supplied username instead of credential/userHandle mapping. | Look up verified credential, match account and authorization. |

## 12. End-to-End Testing Scenarios

**Success flow:**

1. Bootstrap login with a trusted method, call registration options; receive a fresh challenge each time.
2. Browser calls `navigator.credentials.create`, user verifies locally. Backend verifies and persists credential/public key to the current account.
3. Log out, start login options with a different challenge. Browser calls `navigator.credentials.get` and receives an assertion.
4. Server verifies challenge/origin/RP/UP/UV/signature and creates a Spring session. Call protected endpoint `/me` and observe the right account.
5. Register a second passkey, revoke the first passkey, and verify the revoked credential can no longer log in.

**Flows that must be rejected:**

- Resubmit an old assertion with an already-used challenge; must be rejected (anti-replay).
- Use a registration response to verify login or a different attempt’s challenge; must be rejected.
- Alter origin/RP ID or modify signature/clientData/authenticatorData bytes; must be rejected.
- UV unmet when required by policy; must be rejected.
- Valid credential ID belonging to another account; must not grant the wrong session.
- Unauthenticated request calling registration for another user; must be rejected.
- Send two competing verify requests with the same credential/challenge; only one transaction succeeds.
- User lacks resource permission after login; backend must still return 403 for unauthorized endpoints.

**How to observe:** DevTools → Network to confirm options contain challenge, RP ID, `userVerification`, and valid JSON/Base64url fields; after login inspect `Set-Cookie`/session and `/me` requests. When debugging, redact credential IDs, cookies, account identifiers, and sensitive responses before sharing logs/HARs. `curl` can test the HTTP contract, but **cannot generate a valid WebAuthn assertion** without the corresponding authenticator/private key.

## 13. Implementation Checklist

- Fixed RP ID matching the domain; exact allowlist for allowed origins, HTTPS in production.
- Registration only for verified accounts; CSRF, credential-add authorization, and step-up if needed.
- Challenge from `SecureRandom`/CSPRNG, TTL, one-time, flow/session/account binding.
- Frontend converts Base64url ↔ bytes properly, handles prompt cancellation/fallback.
- Backend uses a tested WebAuthn verifier library: type, challenge, origin, RP hash, UP/UV, public key, COSE algorithm, and signature.
- Durable credential repository with unique ID/account mapping, revocation status, counter/backup flags, and auditing.
- Authentication creates secure `SecurityContext`/session; authorization still enforced at service/controller layers.
- Recovery, multiple passkeys, session/logout design, and device/sync/attestation policies aligned with requirements.
- Verify the exact WebAuthn DSL/module/endpoints of the **running Spring Security release**; never treat custom example APIs as built-in framework endpoints.

**Key takeaway:** **Registration** creates a credential on the authenticator and stores the **public key, credential ID, and account mapping** after server verification. **Authentication** uses the private key to sign a **fresh challenge**; the backend verifies the signature along with challenge/origin/RP/UP/UV and creates a Spring Security session. A passkey’s strength comes from **RP ID binding, accurate server-side verification, replay protection, and a secure credential lifecycle**—not just a “Log in with passkey” button.
