# Choosing Compatible Versions Between Java, Spring Boot, and Spring Security (Servlet)

When initializing a **Spring MVC / Servlet** application, choosing versions is not just a matter of picking the latest release of each library and combining them. Java determines the compilation and runtime environment; Spring Boot provides a compatibility-tested set of dependencies; Spring Security must belong to the version family supported by that Spring Boot and Spring Framework release. Making the right choice requires checking **the JDK, Spring Boot version, Spring Security, build tool, and Servlet API**.

This guide focuses on **how to choose, configure, and verify** a version set for a Servlet application, with Maven or Gradle, along with a runnable and testable Spring Boot 3.x demonstration project. Version numbers in the examples are **specific illustrative baselines**, and should not be taken as the latest version or still within support windows at the time of reading.

## 1. Understanding Version Layers and What Manages What

```text
JDK running the build (java/javac; Maven or Gradle daemon)
        |
        +--> Java language level / bytecode target
        |
Spring Boot version (parent / plugin + dependency management)
        |
        +--> Spring Framework (Spring MVC, core, context...)
        +--> Spring Security (core, config, web...)
        +--> Servlet container / Jakarta APIs (Tomcat/Jetty/...)
        +--> other infrastructure libraries
        |
spring-boot-starter-web + spring-boot-starter-security
        |
Spring MVC Servlet application
        |
Actual JRE/JDK on the server or container at runtime
```

- **Java / JDK:** used to compile source code, run Maven/Gradle, and run the application. There are at least three parameters to distinguish: the JDK used for the build process, the generated bytecode level, and the JRE/JDK of the deployment environment.
- **Spring Boot:** manages a set of versions tested together via dependency management (Maven parent/BOM or the equivalent mechanism in Gradle). Boot auto-configures Spring MVC, the Servlet container, and Security based on present starters/beans.
- **Spring Framework:** the foundational library of a Spring application; Spring MVC uses the Servlet API. Spring Framework has corresponding Java and Jakarta requirements.
- **Spring Security:** provides authentication, authorization, the Servlet security filter chain, and OAuth2 integrations if the corresponding starter is selected. It must be compatible with Spring Framework and Boot; Security modules such as `spring-security-web`, `spring-security-config`, and `spring-security-core` should be version-aligned with one another.
- **Servlet container:** the actual HTTP runtime environment (typically embedded Tomcat in `spring-boot-starter-web`). The `javax.servlet.*` and `jakarta.servlet.*` APIs belong to different generations; a sufficiently new Java version does not resolve this package incompatibility.
- **Build tool:** Maven or Gradle and Boot's plugin have their own version requirements. The JDK used by the IDE may differ from the JDK running the Gradle daemon/Maven.

**Selection principle:** choose a *supported Spring Boot line suited to your deployment target*, check the Java and build tool requirements for that specific Boot release, and then **let Boot manage Spring Security versions** unless there is an officially documented reason to override the entire dependency group.

## 2. Generation Matrix: Use to Identify Boundaries, Not as a Substitute for Release Notes

| Application Family | Minimum Java at Generation Level | Spring Framework / Security Family | Servlet Namespace | Meaning at Initialization |
|---|---|---|---|---|
| Spring Boot **2.7.x** | Java 8 | Spring Framework 5.x / Spring Security 5.x | `javax.servlet.*` | Legacy line; may be encountered during maintenance, do not apply Security 6/7 configurations verbatim |
| Spring Boot **3.x** | Java 17 | Spring Framework 6.x / Spring Security 6.x | `jakarta.servlet.*` | Choose Servlet starters and Security 6 generation security APIs |
| Spring Boot **4.x** | Java 17 | Spring Framework 7.x / Spring Security 7.x | `jakarta.servlet.*` | Check the migration guide and starter/API names for 4.x itself; do not assume 3.x code runs unchanged |

This table describes **major version groups**. It does not claim that every newer Java version is supported on every Spring Boot *minor/patch* release. Especially when using a newly released JDK, the JVM version, Gradle/Maven, bytecode instrumentation, and third-party dependencies must all support it together. The table also does not claim that legacy lines are still maintained by the vendor or receive security patches.

Three differences to keep in mind:

1. **Spring Security 6+ requires Java 17+**, even if your business code only uses Java 8 syntax.
2. **Spring Boot 3 switched to Jakarta EE:** import `jakarta.servlet.*` instead of `javax.servlet.*`; the WAR/Servlet container environment must also be compatible. JDK 21 still does not turn a `javax.servlet.Filter` library into a `jakarta.servlet.Filter`.
3. **Spring Security changes APIs across major versions:** for example, Security 6 uses `SecurityFilterChain` and the lambda DSL; do not copy configurations extending `WebSecurityConfigurerAdapter` from legacy Security 5 projects (that adapter no longer exists in Security 6).

Within the same Boot 3.x family, you still must look up the **exact minor/patch version** to know which Spring Security version is managed, the build tool requirements, and the JDK support level. Do not assume things like “any Boot 3.3 ↔ any Security 6.3” when preparing a release.

## 3. How to Make Version Decisions for a New Project

### Step 1 — Lock Down the JDK at Build and Runtime

Determine which JDKs are permitted in the production environment. For a Boot 3.x project, **JDK 17 or 21** is an easy-to-test illustrative choice; if you want a newer Java version, verify that the specific Boot release and build tool declare support for it. Do not equate “a JDK that can run the application” with “officially supported by libraries, frameworks, and plugins”.

Check on your development/CI machine:

```bash
java -version
javac -version
mvn -version
```

If using Gradle, also check `gradle -version` or `./gradlew --version` (on Windows use `gradlew.bat --version`). The output must actually be inspected: these commands **do not have fixed stdout** because it varies by machine and JDK build. Observe the JDK used by Maven/Gradle rather than only looking at the Java SDK selected in your IDE.

### Step 2 — Choose an Appropriately Supported Boot Version

Use a **released stable version that is still supported under your project's policy**. When finalizing, verify in the official documentation for the **exact chosen Boot version**:

- *System Requirements*: minimum Java, tested/supported Java, and Maven/Gradle requirements.
- *Dependency Versions / managed dependencies*: the Spring Framework, Spring Security, Tomcat, and other module versions managed by Boot.
- *Release Notes / Migration Guide*: changes to APIs, starter names, packages, behavior, and deprecations when changing major/minor versions.
- Support and security patch information: distinguish between *community support*, commercial support, release previews, and stable releases.

Commonly used references: [Spring Initializr](https://start.spring.io/), [Spring Boot Reference](https://docs.spring.io/spring-boot/reference/), [Spring Security Reference](https://docs.spring.io/spring-security/reference/). Initializr helps generate a project with a valid combination of choices; release notes and the dependency tree determine the **actual resolved versions**.

### Step 3 — Choose the Right Starters for **Servlet**

In the Spring Boot 3.x family, initialize with:

- `spring-boot-starter-web`: Spring MVC + Servlet stack.
- `spring-boot-starter-security`: integrates Security into the Servlet filter chain.
- If building a Resource Server accepting bearer tokens: add `spring-boot-starter-oauth2-resource-server`, still letting Boot manage versions.
- If building an OAuth2/OIDC Client: add the appropriate OAuth2 Client starter, without mixing in Security modules from a different major version directly.

**Note for the Boot 4.x line:** check the starters recommended by the Boot 4.x documentation (for example, Web MVC starter names or dependency groupings may differ from Boot 3); do not mechanically copy Boot 3.x build files.

Do not add `spring-boot-starter-webflux` just to make reactive HTTP calls with `WebClient` and then assume the application secures HTTP with WebFlux. When the server is still MVC Servlet, the right configuration is `HttpSecurity` + `SecurityFilterChain`.

### Step 4 — Let Boot Decide the Spring Security Version

Maven's parent/BOM and Gradle's dependency management plugin perform *version alignment*: Spring/Security/Tomcat modules must be compatible with each other. Do not declare “latest” individually for `spring-security-web` or `spring-security-core`.

**Key takeaway:** a starter is a bundle of dependencies, **not** an independent Spring Security version. For example, with the same `spring-boot-starter-security` declaration, two different Spring Boot releases may pull in two different Spring Security versions according to their respective managed dependency tables. To know the actual version, inspect the *resolved dependency tree*, not just `pom.xml` or `build.gradle`.

## 4. Maven: Single Source of Version Management

This is an **illustrative configuration with pinned versions** for Spring Boot **3.3.5 + Java 21**; use it to learn how to align dependencies in the Boot 3.x family. When starting a new project, replace the illustrative Boot baseline with a currently supported stable release after reading the system requirements/migration guide, and re-test.

Create `pom.xml` at the project root:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.5</version>
        <relativePath/>
    </parent>

    <groupId>example</groupId>
    <artifactId>servlet-security-compat</artifactId>
    <version>1.0.0</version>

    <properties>
        <java.version>21</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-security</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>org.springframework.security</groupId>
            <artifactId>spring-security-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

Explanation:

- The Boot parent manages the versions of the starters and `spring-security-test`; do not write `<version>` on those four dependencies.
- Setting `java.version` to 21 requires a compatible build JDK. An application compiled targeting Java 21 cannot run on Java 17.
- `spring-boot-maven-plugin` must match the Boot line; the parent manages the plugin to avoid using a plugin version that differs from the project.
- Starter Test provides JUnit and Boot testing support; `spring-security-test` provides principal simulation utilities such as `@WithMockUser`.

If the project uses an internal corporate parent instead of the Boot parent, you can import the `spring-boot-dependencies` BOM inside `dependencyManagement`. **Importing a dependency BOM** only manages dependencies; it does not automatically manage all Maven plugins like the starter parent does, so you must verify plugin/compiler/test configuration yourself. Avoid using multiple BOMs simultaneously with unclear override ordering.

### Checking What Maven Actually Resolves

```bash
mvn -version
mvn dependency:tree -Dincludes=org.springframework.security
mvn dependency:tree -Dincludes=org.springframework
mvn help:effective-pom
```

Look for artifacts such as `spring-security-web`, `spring-security-config`, and `spring-security-core`. They must form a consistent version set managed by Boot (not every artifact will necessarily appear if unused); also check Spring Framework and the servlet container. Tree output varies depending on the dependency set and repositories, so do not assume a single static output.

## 5. Gradle: Boot Plugin, Toolchain, and Dependency Alignment

In **a separate Gradle project**, equivalent to the Maven example above, a `build.gradle` using the **Groovy DSL** can look like:

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.5'
    id 'io.spring.dependency-management' version '1.1.6'
}

group = 'example'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.security:spring-security-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
```

This Gradle example illustrates how the Boot plugin and dependency-management plugin manage transitive versions. Choose a **Gradle Wrapper** compatible with the Boot/Gradle plugin and the JDK used to run Gradle; do not assume every Gradle 8.x or every Gradle 9.x release is supported by a fixed Boot version. With Boot 3.3.5 and JDK 21, Gradle 8.5 is a suitable illustrative baseline; when upgrading Boot/JDK, re-check the release notes.

Another strategy is Gradle's native BOM/platform support; when using it, keep only **one clearly understood alignment strategy** instead of randomly mixing forced versions, strict constraints, and BOMs. In a multi-module build, avoid letting individual modules choose different major versions of Spring Security.

Inspect resolved dependencies:

```bash
./gradlew --version
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency spring-security-web --configuration runtimeClasspath
./gradlew dependencyInsight --dependency spring-core --configuration runtimeClasspath
```

On Windows, replace `./gradlew` with `gradlew.bat`. These commands assume the project already has a Gradle Wrapper generated; if you use Maven, only run the Maven command set in section 4. `dependencyInsight` shows **which version was selected and why** (constraint, platform, dependency conflict), which is more informative than looking at a single `implementation` line.

## 6. Concrete Verification Application on the Servlet Stack

Use **either of the two build configurations** in section 4 or 5, together with the Java source directory below. Goal: Spring Boot starts with Servlet Security; public requests are permitted, and private requests are blocked if unauthenticated. The entire example is tailored for Java 21 and Boot 3.3.5 pinned above.

Create `src/main/java/example/compat/CompatApplication.java`:

```java
package example.compat;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class CompatApplication {

    public static void main(String[] args) {
        SpringApplication.run(CompatApplication.class, args);
    }

    @GetMapping("/public")
    public String publicEndpoint() {
        return "public OK";
    }

    @GetMapping("/private")
    public String privateEndpoint() {
        return "private OK";
    }
}
```

Create `src/main/java/example/compat/ServletSecurityConfig.java`:

```java
package example.compat;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class ServletSecurityConfig {

    @Bean
    SecurityFilterChain webSecurity(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public").permitAll()
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults())
            .build();
    }
}
```

Because this runs Spring MVC **Servlet**, the configuration uses `HttpSecurity` and `SecurityFilterChain`. Do not use WebFlux's `ServerHttpSecurity`/`SecurityWebFilterChain`.

- `/public` is permitted without logging in.
- `/private` requires an authenticated user; because HTTP Basic is enabled, unauthenticated requests typically return `401 Unauthorized`.
- With this demo configuration and no custom user management bean, Spring Boot may create a default development user and log a generated password. **Do not rely on that default account in real deployments**; replace it with an appropriate identity provider or authentication configuration.
- The example configuration does not disable default CSRF protection. For state-changing HTTP methods, design CSRF handling to match how clients send credentials rather than disabling it indiscriminately. The two GET endpoints are solely for a version smoke test.

### Testing Spring Security During the Build

Create `src/test/java/example/compat/CompatApplicationTest.java`:

```java
package example.compat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.test.context.support.WithMockUser;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class CompatApplicationTest {

    @Autowired
    MockMvc mvc;

    @Test
    void publicEndpointWorksWithoutLogin() throws Exception {
        mvc.perform(get("/public"))
            .andExpect(status().isOk())
            .andExpect(content().string("public OK"));
    }

    @Test
    void privateEndpointRequiresAuthentication() throws Exception {
        mvc.perform(get("/private"))
            .andExpect(status().isUnauthorized());
    }

    @Test
    @WithMockUser(username = "student")
    void privateEndpointWorksWhenAuthenticated() throws Exception {
        mvc.perform(get("/private"))
            .andExpect(status().isOk())
            .andExpect(content().string("private OK"));
    }
}
```

Run with **Maven**:

```bash
mvn test
mvn spring-boot:run
```

Or with **Gradle** (with Wrapper):

```bash
./gradlew test
./gradlew bootRun
```

The `test` commands run the three assertions above; the expected test outcome is **3 tests PASS** if the project, JDK, dependencies, and environment are correct. There is no fixed Maven/Gradle stdout because dependency downloads and log levels vary. Once the application is running, you can use another terminal:

```bash
curl -i http://localhost:8080/public
curl -i http://localhost:8080/private
```

The expected logical results are `GET /public → HTTP 200` with body `public OK` and `GET /private → HTTP 401` when no credentials are sent. In practice, headers, timestamps, cookies, and logging may vary; if you change the authentication configuration or port, the results will also change. The test suite is more reliable than merely looking for the “Started” message in the logs.

**Significance of the demo:** it shows Boot, MVC, Spring Security, and test infrastructure working together under one version set. It does **not** prove that every external dependency, every JVM version, or every production environment is compatible.

## 7. Java Compiler Target Differing from the Runtime JDK

Suppose the build machine uses JDK 21, but you want to produce library classfiles that run on Java 17. Using a standalone Java program `VersionProbe.java`:

```java
public class VersionProbe {
    public static void main(String[] args) {
        System.out.println("Bytecode target verified");
    }
}
```

On **JDK 21**, run:

```bash
javac --release 17 VersionProbe.java
java VersionProbe
javap -verbose VersionProbe
```

The command `java VersionProbe` prints exactly:

```text
Bytecode target verified
```

Near the top of the `javap -verbose` output, the class file has `major version: 61`, corresponding to Java 17. This illustrates the **bytecode target**; it does not turn a Boot application requiring Java 17 into one supporting Java 8. If you compile targeting Java 21 (class file major 65) and run it with JRE 17, the JVM will reject it because the classfile is too new, typically throwing `UnsupportedClassVersionError`.

In the Maven example, `<java.version>21</java.version>` combined with the Boot parent configuration controls the application's Java level. With Gradle, `java.toolchain` selects the Java 21 compiler; when you need a lower target, you must configure `options.release` and **verify that dependent libraries also support the target**. Changing `sourceCompatibility` while still compiling against newer JDK APIs is not a substitute for `--release`.

To handle cases where the JVM differs across local, CI, IDE, and Docker, explicitly record the build JDK, Gradle daemon, Java target, and runtime JRE base image in the build pipeline. An application that runs fine in an IDE can still fail when a container uses an older JRE.

## 8. Common Version Errors

| Symptom | Possible Cause | How to Check/Fix |
|---|---|---|
| `UnsupportedClassVersionError` | Compiled bytecode is newer than the actual runtime JRE | Read the major version, check `java -version` in the runtime/container; choose a compatible JRE or rebuild with the right target |
| Maven/Gradle reports `invalid source release: 21` or cannot find toolchain | Actual build uses an older JDK or lacks JDK 21 | Compare `javac -version`, `mvn -version`, `gradlew --version`, toolchain/JAVA_HOME |
| `NoClassDefFoundError`, `NoSuchMethodError` for Spring Security classes | Mixing mismatched Security modules or version skew with Spring Framework | Print the resolved dependency tree, find overrides/exclusions/forced versions; return to a unified Boot BOM |
| `javax.servlet.*` / `jakarta.servlet.*` errors | Library or servlet container belongs to a different Servlet API generation | With Boot 3+, use compatible Jakarta dependencies; upgrade related adapters/libraries instead of changing imports alone and ignoring dependencies |
| `WebSecurityConfigurerAdapter` not found | Configuration code from Security 5 uses an API removed in Security 6 | Rewrite using a `SecurityFilterChain` bean and current APIs |
| `No qualifying bean of type SecurityFilterChain` or routes not protected as expected | Servlet chain not created properly, wrong WebFlux configuration, or conditions changed | Check web stack, actual beans, starters, matchers/order, and startup logs |
| `BeanCreationException` on startup with a manually forced newer Security dependency | Version override causes API mismatch between Boot/Framework/Security | Remove override, inspect effective POM or Gradle dependencyInsight, cross-check release notes |
| Getting `401`/`403` after upgrading even though build succeeds | Configuration defaults, matchers, filter order, CSRF, or authority mapping changed | Write security integration tests, inspect responses and the Security filter chain, read the migration guide |
| Gradle/Maven plugin error before compilation | Build tool/plugin version incompatible with JDK or Boot | Check Boot's System Requirements, Gradle compatibility matrix, and Maven version |
| Local build succeeds but CI or container fails | JDK/toolchain, OS, dependency cache, repository, or runtime image differs | Print versions across all environments, use wrappers and pinned image versions, run a clean controlled build |

Some errors in the table have multiple causes. **Start with evidence**: the first meaningful stack trace, actual resolved versions, and how `SecurityFilterChain` is constructed, before deciding whether to upgrade or downgrade a version.

## 9. Boundaries Specific to Spring Security Servlet

### Servlet Namespace When Upgrading from Boot 2 to Boot 3

In legacy Servlet code, you may encounter:

```java
import javax.servlet.Filter;
import javax.servlet.http.HttpServletRequest;
```

In a corresponding Jakarta-based application, you need:

```java
import jakarta.servlet.Filter;
import jakarta.servlet.http.HttpServletRequest;
```

However, **changing imports is not enough**. Every servlet filter, supporting library, security integration, and servlet container must be compatible with the same generation. With Boot 3, starter-managed embedded Tomcat helps prevent many manual mistakes; when deploying a WAR to an external application server, verify that the server supports the appropriate Jakarta Servlet API.

### Distinguishing Security Versions from Security Chain Types

**Servlet:**

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
}
```

**WebFlux is a different architecture**, using `ServerHttpSecurity` and `SecurityWebFilterChain`. Do not switch to reactive configuration simply because you are upgrading the JDK or Spring Security. The Servlet snippet above is an **illustrative bean fragment**; imports and `@Configuration` are shown in the runnable example in section 6.

### OAuth2 Dependencies Do Not Independently Determine Java/Boot

If a Servlet API needs to validate bearer tokens, add the Resource Server starter **from the same Boot family**. If a website needs OIDC login, add the corresponding OAuth2 Client starter. Do not use the presence of an OAuth2 dependency to manually bump a single Security module to another major version; Security Core/Web/Config/OAuth2 must belong to the same Boot compatibility layer.

## 10. Controlled Upgrade Process

1. **Record the baseline:** local/CI/container JDK, Maven/Gradle wrapper, Spring Boot, resolved Spring Security, servlet container, list of critical integrations, and test status.
2. **Identify the target:** pick a stable Boot release based on support window and Java/Jakarta/Servlet requirements; read the migration guide before a major upgrade. Prefer security patches on a supported line before choosing a major upgrade when appropriate.
3. **Upgrade the management anchor:** update the **Boot parent/plugin/BOM version** and corresponding JDK/toolchain. Avoid upgrading `spring-security-web`/`spring-security-config`/`spring-security-core` in isolation.
4. **Re-resolve all dependencies:** inspect `mvn dependency:tree` or `gradlew dependencies` and `dependencyInsight`. Look for duplicate/forced versions, exclusions, dependency shading, and libraries still using `javax.servlet`.
5. **Fix incompatible APIs:** security configuration DSL, servlet namespace, filter adapters, and third-party dependencies. Use only the migration guide for the exact target version.
6. **Run multi-layer tests:** build/compile, unit tests, Servlet integration tests with MockMvc, `401`/`403`/CSRF/login/logout flows, public endpoints, authorization policies, and OAuth2 if applicable.
7. **Verify the release environment:** runtime JDK in the image, TLS/certs, reverse proxy, session, servlet container, external integrations, and CI/CD. Record versions and outcomes in internal release notes.

**Do not treat a “green build” as proof of completion:** dependencies that are valid at compile time can still alter security defaults or runtime behavior. For security features, specifically test unauthorized access cases (*negative tests*).

### Pre-Finalization Checklist

- [ ] Recorded build JDK, Java target, and production JRE; they are compatible with both Boot requirements and bytecode.
- [ ] Selected **one specific Spring Boot version** based on official documentation and support lifecycle.
- [ ] Spring Framework, Spring Security, and the Servlet container resolve from a unified BOM/parent/plugin without ungrounded version overrides.
- [ ] Servlet project uses the MVC starter and the right-generation `HttpSecurity`/`SecurityFilterChain`.
- [ ] Checked `javax.servlet` / `jakarta.servlet` when doing a major upgrade or integrating legacy libraries.
- [ ] Maven/Gradle wrapper, plugins, CI, and base image support the corresponding JDK.
- [ ] Integration tests prove public endpoints are accessible, private endpoints are properly blocked, and business permissions are not bypassed.
- [ ] Read the release notes/migration guide and inspected the dependency tree after resolution.

## 11. Self-Check Knowledge Questions

**Question 1.** A project uses Spring Boot 3.x and Java 21; can you arbitrarily add `spring-security-web:5.x` because you are familiar with its class APIs?  
**Answer:** No. Spring Security 5.x belongs to a different Spring Framework/Servlet generation; you should follow the versions managed by Boot 3.x and migrate the security configuration.

**Question 2.** `build.gradle` specifies no version on `spring-boot-starter-security`. How do you find out which Spring Security version is actually running?  
**Answer:** Inspect the resolved `runtimeClasspath` using `dependencies`/`dependencyInsight`; the managed version comes from Boot/dependency management configuration, not by guessing from the starter name.

**Question 3.** JDK 21 builds successfully, but a Java 17 container throws `UnsupportedClassVersionError`. What should you check?  
**Answer:** The classfile target and the runtime JRE. If the build produces Java 21 classfiles (major 65), Java 17 cannot run them; choose a matching runtime or build with a compatible target if all dependencies allow it.

**Question 4.** Is changing `javax.servlet.Filter` to `jakarta.servlet.Filter` enough to upgrade a Servlet application from Boot 2 to Boot 3?  
**Answer:** Not yet. You must check whether integrations, libraries, the servlet container, and security APIs are compatible with Jakarta/newer Spring, and then re-run tests.

**Question 5.** If you want to upgrade Spring Security for a patch, should you arbitrarily change one Security module in the POM or upgrade to a supported Boot patch first?  
**Answer:** Prefer evaluating a supported Boot patch first, checking the managed Security version and relevant advisories; if an intentional override is needed, follow official guidance and test the entire dependency group.

**Conclusion:** **Compatible JDK + a unified managed Spring Boot family + right-generation Security/Servlet + verified build/runtime** are the conditions for choosing versions safely. The exact answer for a specific release always comes from *System Requirements*, *managed dependencies*, release notes, and the project's own dependency tree, confirmed by Servlet security testing.
