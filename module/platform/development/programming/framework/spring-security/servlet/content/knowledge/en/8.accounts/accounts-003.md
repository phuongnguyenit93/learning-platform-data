# JdbcUserDetailsManager: Account Schema, Authorities, and Queries

In **Spring Security for Servlet applications**, `JdbcUserDetailsManager` lets you manage accounts and authorities in a **relational database via JDBC** instead of keeping users in memory. It serves both as a `UserDetailsService` for authentication to load users and as a `UserDetailsManager` providing operations to create, update, delete accounts, and change passwords under the API contract.

The focus of this lesson is three things that must align: **data structure** (columns, tables, constraints), **the SQL statements** Spring Security uses, and **the meaning of authority data** after querying. We then build a Spring Boot demo application, test authentication states, and analyze common pitfalls when renaming tables/columns, storing passwords, or updating accounts.

> Scope: Spring Boot 3.x, Spring Security 6.x, Java 17+, Spring MVC/Servlet, JDBC `DataSource`. Exact APIs and DDL templates may vary by version/DBMS; verify the library version and actual migrations before production deployment.

## 1. Where Does JdbcUserDetailsManager Sit in the Authentication Flow?

Clearly separate **loading accounts** from **verifying login credentials**:

~~~text
HTTP Basic / form login / Servlet login mechanism
             |
             v
Authentication filter
             |
             v
AuthenticationManager
             |
             v
DaoAuthenticationProvider
    |                     |
    | loadUserByUsername  | passwordEncoder.matches(...)
    v                     v
JdbcUserDetailsManager   PasswordEncoder
    |
    v
DataSource -> JDBC SQL
    |
    +--> users        : username, password, enabled
    +--> authorities  : username, authority
    |
    v
UserDetails (username, password hash, enabled, authorities)
             |
             v
Authentication succeeded
             |
             v
SecurityContext -> SecurityContextHolder for the current request
             |
             v
AuthorizationFilter / method security applies authorization rules
~~~

Distinct responsibilities:

- `JdbcUserDetailsManager` uses SQL to **read/write user information**. It **does not compare HTTP requests with passwords itself**.
- `DaoAuthenticationProvider` uses `UserDetailsService` to load the user and `PasswordEncoder` to verify credentials submitted by the user.
- After successful authentication, `Authentication` contains the principal and authorities; authorization components use them to decide access.
- `SecurityContextHolder` stores the context currently being processed, not the account store.
- `DataSource` supplies JDBC connections; `JdbcTemplate` and SQL reside in the manager's data access layer.
- `JdbcUserDetailsManager` is **not an ORM/JPA repository**; it does not require `@Entity` entities or `JpaRepository`.

Important point: Spring Security **does not treat having a row in the users table as sufficient to log in**. The authentication mechanism still must verify the password or valid credentials, the enabled status, and other security conditions.

## 2. Two Default Tables: users and authorities

Spring Security's common minimal JDBC schema has **two tables**:

| Table | Column | Role |
| --- | --- | --- |
| `users` | `username` | User identifier key, usually the primary key |
| `users` | `password` | **One-way hashed/encoded password** per `PasswordEncoder`, never plaintext |
| `users` | `enabled` | Whether the user is allowed to authenticate based on enabled status |
| `authorities` | `username` | References the user owning the authority |
| `authorities` | `authority` | A permission/role/scope as a string |

The relationship is **one user has many authorities**:

~~~text
users
+-----------+---------------------------------+---------+
| username  | password                        | enabled |
+-----------+---------------------------------+---------+
| alice     | <bcrypt-hash>                   | true    |
| bob       | <bcrypt-hash>                   | false   |
+-----------+---------------------------------+---------+
        1
        |
        | 1:N (by username)
        v
authorities
+-----------+--------------+
| username  | authority    |
+-----------+--------------+
| alice     | ROLE_USER    |
| alice     | REPORT_READ  |
| bob       | ROLE_USER    |
+-----------+--------------+
~~~

The `<bcrypt-hash>` string in the table above is only a descriptive placeholder, **not a value that can be used to log in**. Actual values are generated by the correspondingly configured encoder.

### Illustrative DDL Runnable on H2

The following `src/main/resources/schema.sql` file matches `JdbcUserDetailsManager`'s default SQL for reading users and authorities. It uses standard H2 `VARCHAR` types; in applications with a case-insensitive username policy, you must additionally design appropriate normalization/collation.

~~~sql
CREATE TABLE users (
    username VARCHAR(50) NOT NULL PRIMARY KEY,
    password VARCHAR(500) NOT NULL,
    enabled BOOLEAN NOT NULL
);

CREATE TABLE authorities (
    username VARCHAR(50) NOT NULL,
    authority VARCHAR(100) NOT NULL,
    CONSTRAINT fk_authorities_user
        FOREIGN KEY (username) REFERENCES users(username),
    CONSTRAINT uq_username_authority
        UNIQUE (username, authority)
);
~~~

Constraints with security and data significance:

1. **Primary key `users.username`**: prevents duplicate records under the DB's username comparison rules.
2. **Foreign key `authorities.username`**: prevents orphan authorities assigned to nonexistent users.
3. **Unique `(username, authority)`**: prevents storing the same authority multiple times for one user.
4. **NOT NULL `password` and `enabled`**: prevents records missing essential data.
5. **Sufficient password column length**: BCrypt, Argon2, or `{id}hash`-formatted strings can be longer than plaintext passwords. Choose column length according to the encoder used.

Spring Security's built-in schema is typically located at resource `org/springframework/security/core/userdetails/jdbc/users.ddl`; a specific schema file may use `varchar_ignorecase` on certain test DBs and include additional group tables. **Do not apply DDL written for one database verbatim to PostgreSQL, MySQL, or SQL Server without checking that database's data types and syntax.** In real projects, use versioned migrations with Flyway/Liquibase rather than re-running CREATE TABLE at server startup.

### Illustrative Records and Authorities

One user can have multiple rows in `authorities`:

~~~sql
-- Illustrates AUTHORITIES data only; the account must exist first.
INSERT INTO authorities (username, authority)
VALUES ('alice', 'ROLE_USER');

INSERT INTO authorities (username, authority)
VALUES ('alice', 'REPORT_READ');
~~~

These examples only run when a row `users.username = 'alice'` already exists. Never insert plaintext passwords into `users`. Also never create users with a BCrypt hash copied from an example and treat it as a securely managed password: use a real encoder, manage secrets through an appropriate channel, and never commit production credentials to the repository.

## 3. The Most Important Default SELECT Queries

When a provider calls `loadUserByUsername("alice")`, the processing flow typically needs to **load the user record** and **the set of authorities**.

The default user query logically is:

~~~sql
SELECT username, password, enabled
FROM users
WHERE username = ?;
~~~

The `?` mark is a **JDBC parameter**, bound with the input username. Never concatenate usernames directly into SQL strings to build queries.

The default authority query logically is:

~~~sql
SELECT username, authority
FROM authorities
WHERE username = ?;
~~~

The query content in `JdbcDaoImpl`'s default implementation essentially follows the structure above. Actual SQL executed in an application depends on any overridden query setters and enabled group features.

If the queries above return for user `alice`:

~~~text
users:
alice | <encoded-password> | true

authorities:
alice | ROLE_USER
alice | REPORT_READ
~~~

Then a loaded `UserDetails` contains username `alice`, encoded password, `enabled=true`, and two `GrantedAuthority` objects. It **does not yet** prove the caller's submitted password is correct; the provider compares authentication credentials.

### Significance of Column Positions

A custom `usersByUsernameQuery` needs to return **three columns in the exact order**: username, password, enabled. An `authoritiesByUsernameQuery` needs to return **two columns in the exact order**: username, authority. Even though SQL aliases/renames are possible, it is best to keep column names clear and test the mapping, because row structure and column reading must be compatible with `JdbcDaoImpl` in the version in use.

**Do not use `SELECT *`** for core queries. When the schema adds columns such as `email`, `created_at`, or `tenant_id`, `SELECT *` can shift column order and break data mapping.

### "Account Not Found" Is Not the Same as "Wrong Password"

If `usersByUsernameQuery` returns no rows, `UserDetailsService` may throw `UsernameNotFoundException`. A provider typically turns authentication errors into a generic response to limit exposing whether an account exists. If the record exists but the password is wrong, verification also fails. Do not build a login API returning "username exists but password is wrong" with distinct messages that make account enumeration easy.

### Enabled and Other Status Flags

By default, the schema has `enabled`. Flags such as `accountNonLocked`, `accountNonExpired`, and `credentialsNonExpired` exist on the `UserDetails` contract, but **have no corresponding columns in the two default tables**. If the product needs account locking, credential expiration, MFA, or custom business statuses, you must design custom schema and logic or customize `UserDetailsService`, rather than assuming default `JdbcUserDetailsManager` manages all those states automatically.

## 4. ROLE_USER, Authorities, and Authorization Rules

Spring Security does not mandate that every authority be a role. Each row of `authorities.authority` is a string `GrantedAuthority` value:

| Stored in DB | Check method | Result under default rules |
| --- | --- | --- |
| `ROLE_USER` | `hasRole("USER")` | Matches |
| `ROLE_ADMIN` | `hasRole("ADMIN")` | Matches |
| `REPORT_READ` | `hasAuthority("REPORT_READ")` | Matches |
| `ADMIN` | `hasRole("ADMIN")` | **Does not match** unless the role prefix is reconfigured |

By default, `hasRole("ADMIN")` checks for authority `ROLE_ADMIN`. When creating a user:

~~~java
UserDetails user = User.withUsername("alice")
        .password(passwordEncoder.encode("password-from-secure-source"))
        .roles("USER")
        .build();
~~~

`roles("USER")` automatically creates authority `ROLE_USER`. Conversely:

~~~java
UserDetails user = User.withUsername("alice")
        .password(passwordEncoder.encode("password-from-secure-source"))
        .authorities("ROLE_USER", "REPORT_READ")
        .build();
~~~

`authorities(...)` stores the exact strings passed. The two snippets above are **fragments belonging to a Spring Security project**, with variables/types already imported/provided; never use these example string literals as production passwords. Pick a consistent authority naming convention and test end-to-end from DB to `hasRole/hasAuthority`.

Authorities from JDBC can be used in filter security or method security. `JdbcUserDetailsManager` only provides stored authorities; it does not automatically know which report a user may view if no authorization policy has been declared.

## 5. Account Administration APIs of JdbcUserDetailsManager

This class implements common `UserDetailsManager` behaviors:

| API | Effect | Notes |
| --- | --- | --- |
| `loadUserByUsername(username)` | Loads user and authorities | Used for authentication; may throw `UsernameNotFoundException` |
| `userExists(username)` | Checks if a matching user record exists | For admin operations; do not expose result directly on public login |
| `createUser(user)` | Creates user record and authorities | Password must already be properly encoded; requires admin privileges |
| `updateUser(user)` | Updates default attributes and user authorities | Must avoid accidentally overwriting password hash or losing authorities |
| `deleteUser(username)` | Deletes user data managed by the manager | Consider FKs, active login sessions, and related business data |
| `changePassword(oldPassword, newPassword)` | Changes user password per manager contract | Depends on how current user is identified and configured verification; does not replace a secure reset flow |

"Administration" here refers to the interface's technical function; **it does not mean the API automatically ensures the HTTP caller has admin privileges**. If you expose an endpoint calling `createUser(...)`, you must configure authorization at the web/method layer and validate inputs. JDBC data access is also subject to the DB connection account's privileges.

### Safely Creating a User in Java

Example fragment inside a permission-controlled service:

~~~java
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.provisioning.JdbcUserDetailsManager;

UserDetails account = User.withUsername("reporter")
        .password(passwordEncoder.encode(rawPassword))
        .authorities("ROLE_USER", "REPORT_READ")
        .build();

if (!jdbcUserDetailsManager.userExists("reporter")) {
    jdbcUserDetailsManager.createUser(account);
}
~~~

Here `passwordEncoder`, `rawPassword`, and `jdbcUserDetailsManager` are objects/values from the application; this is a **fragment**, not a self-running Java file. Never log `rawPassword`. The check-then-create pattern can suffer a **race condition** if two concurrent requests create the same username, so you must also rely on the DB's unique constraint and handle duplicate-key exceptions properly. Avoid treating `userExists(...)` as the sole duplicate-prevention mechanism.

### Updating and Changing Passwords: Two Operations Not to Equate

`updateUser(...)` normally updates columns managed by the manager, including password/authorities taken from the passed `UserDetails`. If code builds an update object from a form without a valid password hash, it risks writing an invalid value into the DB. When updating only profile fields (e.g., email), it is usually better to use a separate profile service/repository rather than rewriting the entire security user.

For `changePassword(...)`, check the contract of your specific version and the manager's authentication manager configuration: do not assume calling this method alone establishes all password-change rules. A real password-change workflow must verify the current user, verify the old password if required, encode the new password, validate password policy, protect against CSRF with cookie-based auth, and consider invalidating other sessions/tokens. Those behaviors are **application policies**, not all automatically handled by the manager implementation.

## 6. Password Encoding and PasswordEncoder

Data stored in `users.password` must be compatible with the `PasswordEncoder` used by the authentication provider. A common encoder is `BCryptPasswordEncoder`:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
~~~

When creating an account, **encode before saving**:

~~~java
String encoded = passwordEncoder.encode(rawPassword);
userManager.createUser(User.withUsername(username)
        .password(encoded)
        .roles("USER")
        .build());
~~~

This is a fragment using variables from the application. Spring Security will use `passwordEncoder.matches(rawPassword, encodedPassword)` during verification. BCrypt generates a random salt, so encoding the same password twice produces different strings; **never compare two hash strings with equals to authenticate**. Also never re-hash an already stored hash before saving, as that makes the real password fail to authenticate.

### Direct BCrypt vs DelegatingPasswordEncoder

Two common storage styles:

- With a `new BCryptPasswordEncoder()` bean: the `password` column stores a BCrypt string like `$2a$...`, without needing the `{bcrypt}` prefix for this encoder itself to verify it.
- With `DelegatingPasswordEncoder` (e.g., from `PasswordEncoderFactories.createDelegatingPasswordEncoder()`): stored strings usually carry an algorithm identifier prefix like `{bcrypt}$2a$...` so the system selects the matching encoder.

**Do not mix the two formats without proper configuration.** If you use `BCryptPasswordEncoder` directly and store a string containing `{bcrypt}`, it may fail to match because the prefix is not a pure BCrypt hash. Conversely, a default delegating encoder may require the prefix to know which algorithm to check.

Regardless of algorithm, never store plaintext passwords, never use fast unsalted hashes for passwords, and never hardcode real passwords in Java or config files. Real products need proper password rotation, account recovery, and secret management mechanisms.

### 7.4. JdbcUserDetailsManager, Encoder, and Security Chain Beans

Create `src/main/java/com/example/security/JdbcSecurityConfig.java`:

~~~java
package com.example.security;

import javax.sql.DataSource;

import org.springframework.boot.CommandLineRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.JdbcUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class JdbcSecurityConfig {

    @Bean
    JdbcUserDetailsManager jdbcUserDetailsManager(DataSource dataSource) {
        return new JdbcUserDetailsManager(dataSource);
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            JdbcUserDetailsManager users,
            PasswordEncoder encoder) throws Exception {

        DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
        provider.setUserDetailsService(users);
        provider.setPasswordEncoder(encoder);

        http.authenticationProvider(provider)
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public").permitAll()
                .requestMatchers("/reports").hasAuthority("REPORT_READ")
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults());

        return http.build();
    }

    @Bean
    CommandLineRunner seedDemoUser(
            JdbcUserDetailsManager users, PasswordEncoder encoder) {

        return args -> {
            String initialPassword = System.getenv("DEMO_INITIAL_PASSWORD");
            if (initialPassword == null || initialPassword.isBlank()) {
                return; // Do not auto-generate an account with a default password.
            }

            if (!users.userExists("alice")) {
                users.createUser(User.withUsername("alice")
                    .password(encoder.encode(initialPassword))
                    .authorities("ROLE_USER", "REPORT_READ")
                    .build());
            }
        };
    }
}
~~~

**Version note:** For example, `DaoAuthenticationProvider()` and `setUserDetailsService(...)` use APIs from the Spring Security 6.x line; in some newer versions these constructors/setters may be marked deprecated or replaced by a constructor accepting `UserDetailsService`. When upgrading, choose the API appropriate for the version locked in your project. The key point is that the provider uses **the same manager and the same PasswordEncoder** to authenticate.

The `DEMO_INITIAL_PASSWORD` environment variable is only for initializing a **demo user in development**. In production, do not use a shared bootstrap password, do not leave secrets in shell history, and do not silently create admin accounts. For real applications, you need a controlled provisioning or migration process, logging that never leaks credentials, and secret rotation.

## 8. Standalone Java 17 Program: Understanding How Accounts and Authorities Join

If you do not yet have Spring Boot/H2, you can run a simulation with **plain JDK 17**. It does not run SQL queries and **does not implement JdbcUserDetailsManager**; the goal is to show why each user needs one user row yet can have multiple authority rows, and why "user not found" differs from a disabled user.

Save `UserAuthorityRowsDemo.java`:

~~~java
import java.util.List;

public class UserAuthorityRowsDemo {
    record UserRow(String username, String passwordHash, boolean enabled) {}
    record AuthorityRow(String username, String authority) {}

    public static void main(String[] args) {
        List<UserRow> users = List.of(
            new UserRow("alice", "encoded-A", true),
            new UserRow("bob", "encoded-B", false)
        );
        List<AuthorityRow> grants = List.of(
            new AuthorityRow("alice", "ROLE_USER"),
            new AuthorityRow("alice", "REPORT_READ"),
            new AuthorityRow("bob", "ROLE_USER")
        );

        for (String name : List.of("alice", "bob", "ghost")) {
            var user = users.stream()
                    .filter(row -> row.username().equals(name))
                    .findFirst();

            if (user.isEmpty()) {
                System.out.println(name + " -> not found");
                continue;
            }

            List<String> authorities = grants.stream()
                    .filter(row -> row.username().equals(name))
                    .map(AuthorityRow::authority)
                    .sorted()
                    .toList();

            System.out.println(name + " enabled=" + user.get().enabled()
                    + " authorities=" + authorities);
        }
    }
}
~~~

Compile and run:

~~~bash
javac UserAuthorityRowsDemo.java
java UserAuthorityRowsDemo
~~~

Exact stdout:

~~~text
alice enabled=true authorities=[REPORT_READ, ROLE_USER]
bob enabled=false authorities=[ROLE_USER]
ghost -> not found
~~~

The strings `encoded-A` / `encoded-B` are only dummy simulation data. They **are not valid password hashes** and must never be used in real tables. In a JDBC system, the manager loads the exact user/authorities from SQL, while the provider verifies the encoded password and enabled status.

## 9. Customizing Queries When Using an Existing Enterprise Schema

Not every company names its tables `users` and `authorities`. Suppose you have:

~~~text
app_account: login_name, password_hash, active, display_name
app_grant:   login_name, permission_code
~~~

Instead of changing the entire database, you can configure the **read** queries:

~~~java
JdbcUserDetailsManager manager = new JdbcUserDetailsManager(dataSource);

manager.setUsersByUsernameQuery(
    "SELECT login_name, password_hash, active " +
    "FROM app_account WHERE login_name = ?");

manager.setAuthoritiesByUsernameQuery(
    "SELECT login_name, permission_code " +
    "FROM app_grant WHERE login_name = ?");
~~~

This is a **fragment** with a `dataSource` variable supplied by the application. Note:

- The first query must return three columns with the semantics **username, encoded password, enabled**.
- The second query must return pairs of **username, authority**.
- Use `?` to pass the username via JDBC; never concatenate strings from input.
- If usernames carry a tenant ID, design the key and explicit tenant filtering carefully. The default `loadUserByUsername(String)` contract only receives a username; you cannot assume it is safe to infer the tenant from an arbitrary ThreadLocal variable.
- Using JOINs to query authorities across multiple tables is fine as long as the right column structure is returned and duplicates/authorities are handled per policy.
- Ensure indexes exist for username lookups and authority joins.

**Important warning:** The two setters above only change the **read path**. If the application also calls `createUser(...)`, `updateUser(...)`, `deleteUser(...)`, or `userExists(...)`, those operations have their own SQL statements and may still target the default `users` / `authorities` tables. You must configure **the full set of write/check queries** on `JdbcUserDetailsManager` for your custom schema, or use a custom read-only `UserDetailsService` paired with a dedicated user administration service. Do not change just the two SELECTs and assume all CRUD moved to the enterprise tables.

### When Should You Write a Custom UserDetailsService?

Choose `JdbcUserDetailsManager` when user + authority management fits closely with the default schema, SQL rules are simple, and you want the standard admin APIs. Consider implementing a custom `UserDetailsService` when:

- Account data already uses a large or multi-tenant schema.
- Authorities are derived from groups, hierarchies, organizational units, or dynamic policies.
- Usernames have multiple identifiers/aliases, or login must check status beyond enabled.
- The account lifecycle requires mandatory auditing, soft delete, lockout, MFA, domain events, or complex transaction rules.
- Users are synced from LDAP, IdP, SSO, OAuth2, or an identity mechanism outside the database.

A custom `UserDetailsService` usually only needs to load a valid user and construct `UserDetails`. Verification is still performed by the provider; if multiple authentication mechanisms are needed, design providers/managers properly instead of checking passwords manually in controllers.

## 10. Group Authorities: groups, group_members, and group_authorities

In addition to authorities assigned directly to a username, the JDBC schema provided by Spring Security also supports **group-based authorities** in certain configurations. Group tables typically have these roles:

| Table | Main data | Relationship |
| --- | --- | --- |
| `groups` | Group ID, group name | One group has many members |
| `group_members` | Group and member's username | Assigns a user to a group |
| `group_authorities` | Group and granted authority | Members can inherit the group's authorities |

Support for loading group authorities sits in the JDBC mechanism behind options like `setEnableGroups(true)`. **Do not assume group authorities are enabled by default just because a `groups` table exists.** When enabling groups, check the version/schema, group authority queries, and how group authorities merge with direct authorities. Verify member update/delete rules alongside transactions and foreign keys; missing cleanup can leave orphaned mappings.

Group-based authorities do not solve every role-hierarchy or tenant-permission problem. When the permission model is complex, define explicit policies rather than forcing every relationship into a single `authorities` table.

## 11. Transactions, Data Locks, and Race Conditions

A `createUser(...)` operation may have to write **the user first, then authorities**. `updateUser(...)` may have to update the user and replace the authority set. When an error occurs mid-way, consistency depends on transactions, how the manager is called, and DB configuration:

- Execute account provisioning/update/deletion within a controlled **service transaction**.
- Ensure proper foreign keys, unique indexes, and on-delete policies; do not rely solely on checks in Java.
- If two requests concurrently create the same username, one may fail on the unique constraint; handle the error deliberately without turning it into a sensitive message for the client.
- When updating authorities, consider auditing and concurrency (optimistic locking or an appropriate isolation level) if business rules require it.
- When deleting a user, business links such as orders, audit history, and login sessions need dedicated policies; never automatically cascade-delete critical business data just to match the security schema.

**Transactions do not automatically solve every security issue.** For instance, a user is disabled in the DB yet still holds a valid signed JWT with embedded authorities; `JdbcUserDetailsManager` only takes effect if the authentication/authorization flow actually reloads user status from the DB or has a revocation-check mechanism.

### Caching UserDetails

An authentication provider can use `UserCache` or an application-layer cache. If users/authorities are cached, DB changes might not be reflected immediately on the next request. You need an invalidation policy and cache TTL, especially when locking accounts or revoking authorities. Do not assume every request runs both SQL SELECTs; the authentication and caching flow determines query frequency.

## 12. Integration Testing JDBC Accounts and Authorities

For the Spring Boot application in Section 7, `spring-security-test` lets you send real Basic credentials to the filters and provider, rather than only mocking a principal with `@WithMockUser`. A sample test:

~~~java
package com.example.security;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.JdbcUserDetailsManager;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class JdbcAuthenticationTest {

    @Autowired MockMvc mvc;
    @Autowired JdbcUserDetailsManager users;
    @Autowired PasswordEncoder passwords;

    @BeforeEach
    void setUp() {
        if (!users.userExists("reader")) {
            users.createUser(User.withUsername("reader")
                .password(passwords.encode("reader-test-pass"))
                .authorities("ROLE_USER")
                .build());
        }
        if (!users.userExists("reporter")) {
            users.createUser(User.withUsername("reporter")
                .password(passwords.encode("reporter-test-pass"))
                .authorities("ROLE_USER", "REPORT_READ")
                .build());
        }
    }

    @Test
    void anonymousAndWrongPasswordAreRejected() throws Exception {
        mvc.perform(get("/reports"))
            .andExpect(status().isUnauthorized());

        mvc.perform(get("/reports")
                .with(httpBasic("reporter", "wrong")))
            .andExpect(status().isUnauthorized());
    }

    @Test
    void authenticationDoesNotGrantEveryAuthority() throws Exception {
        mvc.perform(get("/reports")
                .with(httpBasic("reader", "reader-test-pass")))
            .andExpect(status().isForbidden());

        mvc.perform(get("/reports")
                .with(httpBasic("reporter", "reporter-test-pass")))
            .andExpect(status().isOk())
            .andExpect(content().string("reports"));
    }
}
~~~

This is a **test using dummy passwords scoped strictly to tests**, not production secrets. If the schema in `schema.sql` has not been initialized, or the test class cannot see the right application configuration, the test will fail due to missing DB/beans. The expected HTTP statuses apply to the exact HTTP Basic, controller, and authority configuration shown; custom entry points or authorization rules may change statuses.

`@WithMockUser` tests are useful when you only want to test authorization, but **do not verify** real JDBC SQL, `PasswordEncoder`, and `DaoAuthenticationProvider`. To learn `JdbcUserDetailsManager`, you need at least one integration test going through the database as shown above.

### Testing Other Cases

- Nonexistent user: `loadUserByUsername(...)` fails, login returns a generic message.
- Existing user with `enabled=false`: authentication is not granted.
- Incompatible password hash/encoder: user is still loaded, but verification fails.
- User has `ROLE_USER` while endpoint requires `ROLE_ADMIN`: typically 403 if already authenticated.
- User has multiple authorities: all must be loaded accurately, avoiding lost authorities from JOINs or mapping bugs.
- Duplicate username/authority: DB unique constraint takes effect.
- Authority changes in DB: check impact of cache/session/token and update policy.
- Custom SQL: verify column order, username parameter, soft delete, tenant, and case sensitivity.

## 13. Common Configuration Errors

| Symptom | Common Cause | How to Check/Fix |
| --- | --- | --- |
| SQL reports table `users` or `authorities` does not exist | Schema not run, wrong DataSource/schema search path | Check migrations, JDBC URL, DB user, and schema name |
| User created successfully, yet login fails | Password stored in wrong format or encoder mismatch | Check PasswordEncoder config, `encode/matches` workflow |
| User `alice` cannot access hasRole("USER") endpoint | DB stores `USER` instead of `ROLE_USER` | Standardize authority strings and check rules |
| Has `roles("ADMIN")` yet user still gets 403 | Another chain/rule selected, or token/session holds old authorities | Verify selected chain, actual authorities, cache |
| `loadUserByUsername` reports not found | Username case mismatch, wrong SQL, or wrong datasource | Check WHERE, collation, normalization, and bind parameter |
| Updating user corrupts password | `updateUser(...)` overwrote with invalid password | Do not use manager to arbitrarily change profile fields; check hash |
| Changed two SELECTs yet CRUD throws errors | Write/check SQL still targets old tables | Configure all SQL statements or separate admin service |
| User receives too many/too few authorities | JOIN query, group config, duplicate permissions, wrong tenant filter | Test full authority set, indexes, and constraints |
| Concurrent account creation occasionally fails with unique error | Race between `userExists` and `createUser` | Rely on unique constraint and transaction/exception handling |
| PasswordEncoder reports no encoder for id | Using delegating encoder while hash lacks/has wrong prefix | Unify storage format and encoder |
| User disabled yet old JWT still calls API | Resource Server does not reload user per request | Design revocation/expiry and status check policy |
| MockMvc test with WithMockUser PASSES, real run FAILS | Mock user bypasses JDBC/password verification | Add integration test with `httpBasic` or real login |

### Protecting Queries and Data

`JdbcUserDetailsManager` uses parameterized SQL for default lookups. With custom SQL, keep safe parameter binding and never build dynamic SQL from input. Restrict the DB account's permissions (only read/write necessary tables), enable TLS for DB connections when appropriate, protect backups, and audit privilege-changing operations. Do not return distinct messages that let attackers enumerate usernames, and never log passwords, hashes, tokens, or full credentials.

### Performance and Indexes

Authentication may require at least one user lookup and one authorities lookup. With many users, indexes on `users.username` and `authorities.username` reduce cost. Custom queries with complex JOINs must have appropriate indexes and execution plans. Avoid carelessly caching passwords/authorities without a revocation strategy.

## 14. Self-Check Exercises

**Exercise 1.** The `users` table has `alice` with enabled=true, and `authorities` has `ROLE_USER`. An endpoint is protected by `hasAuthority("ROLE_USER")`. What must happen before Alice is allowed into the endpoint?

**Answer:** The provider must load the user, verify the valid password/credentials and required status flags, and produce a successful `Authentication`. Then authorization checks the `ROLE_USER` authority. Simply having user data in the DB is not enough to authenticate.

**Exercise 2.** Why does `hasRole("ADMIN")` not match authority `ADMIN` in the DB by default?

**Answer:** By default, `hasRole("ADMIN")` expects authority `ROLE_ADMIN`. You can store `ROLE_ADMIN` or use `hasAuthority("ADMIN")` if the project policy intentionally defines a permission named `ADMIN`.

**Exercise 3.** A company renames table `users` to `app_account`, and column `password` to `password_hash`. Is updating only `setUsersByUsernameQuery(...)` enough to call `createUser(...)`?

**Answer:** Not yet. You must also adjust the SQL for creating/updating/deleting/checking users and authorities accordingly or use a dedicated administration service. Custom SELECT SQL only affects the read path.

**Exercise 4.** Calling `passwordEncoder.encode("secret")` a second time produces a different hash than the first call. Is the encoder broken?

**Answer:** No. Encoders like BCrypt use a salt, so different hashes can all be valid for the same password. Verify with `matches(raw, storedHash)`, not by comparing a new hash against the old hash with equals.

**Exercise 5.** If `UserDetailsManager.userExists("bob")` returns false before `createUser("bob")`, is a duplicate-username error guaranteed not to happen?

**Answer:** No. Two concurrent tasks can both observe false and then both insert. A unique/primary key constraint in the database is a mandatory line of defense; the application should handle duplicate errors safely.

**Exercise 6.** A test using `@WithMockUser(roles = "ADMIN")` succeeds. Does that prove BCrypt/JDBC users/authorities are configured correctly?

**Answer:** No. Mock users skip password verification and real DB user loading. You need an integration test with Basic/form login going through `DaoAuthenticationProvider` and `JdbcUserDetailsManager`.

**Exercise 7.** A user has `REPORT_READ` removed in the DB, yet requests carrying an old JWT bearer token still have `REPORT_READ`. Did `JdbcUserDetailsManager` fail to remove the permission?

**Answer:** Not necessarily. The JWT may embed previously issued authorities and the request does not reload from the DB. You need token expiry/revocation policies or dynamic authority loading per system requirements; DB authorities and token claims are two distinct scopes.

## 15. Practical Deployment Checklist

- Identify which **DataSource**, schema, and migrations the JDBC manager uses; avoid pointing at the wrong environment.
- Ensure default columns `username/password/enabled` and `username/authority` match the SQL; when customizing, configure both **read and write** queries completely.
- Have primary keys, foreign keys, unique constraints, indexes, and clear case-sensitivity/tenant rules.
- Use a secure `PasswordEncoder` consistent with hashes stored in the DB; never keep plaintext/credentials in logs.
- Understand authority strings: `roles(...)` creates `ROLE_...`; `hasRole(...)` and `hasAuthority(...)` have different semantics.
- Distinguish loading `UserDetails`, verifying credentials at the provider, and checking permissions at the authorization layer.
- Only expose account administration operations after enforcing authorization, validation, auditing, and transactions.
- Test nonexistent usernames, wrong passwords, disabled users, sufficient/insufficient authorities, custom SQL, concurrent creates/updates, and caching.
- When identity/permission management grows complex (SSO, MFA, tenants, workflows), consider a custom `UserDetailsService`/domain service rather than stretching the default schema.

**Takeaway:** `JdbcUserDetailsManager` provides a bridge from **accounts and authorities in SQL** to the `UserDetails` Spring Security uses for authentication, while also supporting a set of user management APIs. Its correctness depends on **table schema, SQL queries, PasswordEncoder, authority interpretation, and the authentication mechanism** all staying aligned.
