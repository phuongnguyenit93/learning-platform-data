# Investigating Unexpected 401, 403, and 302 Redirects

**Module:** Spring Security – Servlet  
**Parent Topic:** Diagnostics

## 1. Understand the Right Question Before Changing Configuration

In Spring Security Servlet, three HTTP outcomes frequently confuse learners:

- **401 Unauthorized**: the request requires authentication, but valid credentials were not provided or the authentication mechanism demands a retry. Although HTTP names it "Unauthorized", the practical meaning of 401 is usually **unauthenticated**.
- **403 Forbidden**: the request was refused. This may happen because an authenticated user lacks an authority, because a **CSRF token** is missing/invalid, because of a `denyAll` policy, because of CORS, or because of another permission check. **Not every 403 is caused by a missing role**.
- **302 Found**: redirects to another URL via the `Location` header. In a web app using `formLogin()`, unauthenticated requests are typically redirected to `/login`. However, 302 can also be a **post-login redirect, post-logout redirect, redirect to a saved request**, or one generated by the application or a reverse proxy.

An effective investigation does not begin with "how do I turn off security to stop the error", but with the question:

> **Which security chain did the actual request enter, which mechanism authenticated it, at which filter or authorization rule was it blocked, and which component produced the response?**

The exact same endpoint can return 401, 403, or 302 depending on:

1. **HTTP method**: GET or POST; does POST require CSRF?
2. **Actual path**: `/api/orders`, `/web/orders`, context path, servlet path, trailing slash, and forward/error dispatch.
3. **Selected SecurityFilterChain**: HTTP Basic, OAuth2 Resource Server, form login, or a fallback chain.
4. **Caller state**: anonymous, valid session, valid bearer token, wrong credentials, or authenticated account lacking permissions.
5. **Authorities and policy**: `ROLE_ADMIN`, `SCOPE_orders.read`, `hasAuthority`, `hasRole`, `denyAll`, method security, or resource-level permission checks.
6. **CSRF/CORS policy**: browser auto-sending cookies, JSON requests, OPTIONS preflight, and CSRF tokens.
7. **Entry point, error handler, reverse proxy, or controller**: who decided 401, 403, or 302?

This guide walks through tracing each layer, accompanied by a **Java 17 / Spring Boot 3.3.5 / Spring Security 6** project to verify real behavior via MockMvc.

## 2. Quick-Lookup Table: Which Symptom Suggests Which Cause?

| Outcome | Common Clues | What to Check First |
| --- | --- | --- |
| 401 + `WWW-Authenticate: Basic ...` | API uses HTTP Basic; missing or wrong Basic credentials | Right chain? `Authorization` header? `UserDetailsService`/`PasswordEncoder`? |
| 401 + `WWW-Authenticate: Bearer ...` | Resource Server rejects the bearer token | Token, issuer, audience, signature/introspection, `exp`, resource server config |
| 403 after login | Missing role/scope/permission or blocking policy | Actual authorities, `hasRole`/`hasAuthority`, matcher order, object-level permission |
| 403 on POST while GET on same path works | Likely missing/invalid CSRF token | `CsrfFilter`, hidden form field, cookie/session, `csrf()` in security test |
| 403 even as admin | `denyAll`, wrong filter chain, role prefix, object/tenant rule, CSRF | Selected rule, security matcher, HTTP method, context |
| 302 to `/login` | Form login demands authentication instead of API 401 | `formLogin()`, entry point, chain, session |
| 302 to another page after login | Saved request / success handler / `defaultSuccessUrl` | `Location`, request cache, success handler, session |
| Infinite 302 loop | Login/session/cookie/host/proxy/redirect URI mismatch | `Set-Cookie`, `Location`, HTTPS, forwarded headers, `SameSite`/`Domain`/`Path` |
| 200 returning login HTML instead of JSON | Client followed redirects automatically, hiding initial 302 | Network redirect chain, `Content-Type`, `Location` |
| 403 on OPTIONS preflight | Policy/security/CORS mishandling preflight | `Origin`, `Access-Control-Request-Method`, CORS config, chain |

**Remember:** this table lists **hypotheses to test**, not absolute rules for every application. With `@ControllerAdvice`, custom `AuthenticationEntryPoint`, gateways, or multiple chains, the same failure can be mapped to a different status code.

## 3. Request Flow in Spring Security Servlet

An HTTP request typically flows through:

~~~text
Client / browser
    |
    v
Reverse proxy / load balancer / ingress (if present)
    |
    v
Servlet container
    |
    v
DelegatingFilterProxy("springSecurityFilterChain")
    |
    v
FilterChainProxy
    |--- selects the FIRST SecurityFilterChain matching the request
    |
    v
Filters of the selected chain
    |--- SecurityContextHolderFilter / context repository
    |--- CsrfFilter (if applicable)
    |--- authentication filters (Basic, Bearer, formLogin...)
    |--- AnonymousAuthenticationFilter
    |--- ExceptionTranslationFilter
    |--- AuthorizationFilter
    |
    v
DispatcherServlet
    |--- Controller
    |--- Service / @PreAuthorize
    |--- Exception handlers
    v
Response: 200 / 302 / 401 / 403 / ...
~~~

This diagram illustrates **the roles of filter groups**, not an immutable exact ordering across every version or configuration. Actual present components and their order depend on the constructed `SecurityFilterChain`.

### 3.1. Authentication and Authorization Are Not One Step

- **Authentication** verifies the principal: password, session, Basic header, bearer token, OIDC login...
- **Authorization** decides whether the authenticated principal may perform the request, based on authorities and policy.
- **`SecurityContextHolder`** holds the current `Authentication` while executing on that thread.
- **`AuthenticationEntryPoint`** initiates authentication when needed: it may return 401 or redirect 302.
- **`AccessDeniedHandler`** handles an access denial: normally returns 403; can be customized.
- **`ExceptionTranslationFilter`** translates certain `AuthenticationException` and `AccessDeniedException` instances into entry-point or access-denied behavior. However, **the CSRF filter can handle `AccessDeniedException` with its own handler**, so do not assume every 403 originates from `ExceptionTranslationFilter`.

### 3.2. Mechanics of 401, 403, and 302 by Caller State

~~~text
Request reaches protected endpoint
    |
    +-- No valid authentication yet
    |      |
    |      +-- Chain uses HTTP Basic ---> 401 + Basic challenge
    |      +-- Chain uses bearer -------> 401 + Bearer challenge
    |      +-- Chain uses form login ---> 302 Location: /login
    |      +-- Custom entry point ------> per configuration
    |
    +-- Authenticated, but lacking permission
    |      |
    |      +-- Authorization denies ----> usually 403
    |
    +-- POST missing/invalid CSRF token
    |      |
    |      +-- CsrfFilter denies -------> usually 403
    |
    +-- Authenticated, authorized, valid request
           |
           +-- Controller handles ------> 200/201/204/302/4xx/5xx per app
~~~

**Important:** the branches do not represent a rigid check sequence; CSRF can block a POST **before** authorization checks roles. An anonymous POST missing CSRF can return 403 even when an anonymous GET would return 302/401.

## 4. When Is 401 Returned?

### 4.1. HTTP Basic

With a chain using `httpBasic()`, a credential-less request to a protected endpoint may receive:

~~~http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Realm"
~~~

The client must send a properly formatted `Authorization: Basic ...` header. Spring Security processes credentials via `AuthenticationManager` and the appropriate provider. Common causes:

- Missing `Authorization` header.
- Non-existent username, wrong password, or encoder mismatch with stored hash format.
- Request entered the Basic chain instead of the form-login chain.
- Proxy/gateway stripped the `Authorization` header.
- Custom `AuthenticationEntryPoint` altered the response.

**Do not fix by setting `permitAll()` on every endpoint** just to eliminate 401; determine why authentication did not succeed.

### 4.2. Bearer / JWT / Opaque Token

With `oauth2ResourceServer().jwt()` or `.opaqueToken()`, a token may be rejected due to:

- Missing or malformed `Authorization: Bearer ...` header.
- Expired JWT, invalid signature, unsupported algorithm, or mismatched issuer.
- Token not targeting the expected audience/resource, if an audience validator/policy is configured.
- JWK endpoint / issuer metadata unreachable, or introspection endpoint failing to respond properly.
- Opaque introspection returned `active:false`, or the resource server lacks valid credentials to introspect.

An illustrative response:

~~~http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"
~~~

Not every 401 includes `invalid_token`; challenge details depend on the error and handler. **Never write raw tokens, client secrets, or sensitive data into debug logs**.

### 4.3. Why Does 401 Sometimes Become 302?

If a request enters a **form-login chain**, `LoginUrlAuthenticationEntryPoint` typically redirects to `/login` instead of returning a Basic/Bearer challenge. This is sensible behavior for web browsers, yet violates API client expectations.

An API call `GET /api/profile` via `fetch()` receiving `200 text/html` containing the login page is usually the result of **a 302 followed automatically by the client**. When debugging, inspect the initial request and redirect chain, not just the final response.

If one application serves both web login and REST APIs, design **separate `SecurityFilterChain`/`AuthenticationEntryPoint` configurations** per path group or specify entry points deliberately via `RequestMatcher`.

## 5. When Is 403 Returned?

### 5.1. Authenticated but Insufficient Authority

Example endpoint:

~~~java
// Illustrative snippet inside HttpSecurity DSL:
.requestMatchers("/admin/**").hasRole("ADMIN")
~~~

With the default prefix, `hasRole("ADMIN")` checks for authority **`ROLE_ADMIN`**. If the authentication only holds `ROLE_USER`, the request is denied.

| Rule | Required Authority (Default) |
| --- | --- |
| `hasRole("ADMIN")` | `ROLE_ADMIN` |
| `hasAuthority("ROLE_ADMIN")` | `ROLE_ADMIN` |
| `hasAuthority("SCOPE_reports.read")` | `SCOPE_reports.read` |
| `hasAnyRole("EDITOR", "ADMIN")` | At least one of `ROLE_EDITOR`, `ROLE_ADMIN` |

Common mistakes include calling `hasRole("ROLE_ADMIN")` while the default `ROLE_` prefix is active, or treating `SCOPE_profile` as an admin role. Check the authorities **actually present inside `Authentication`**, rather than guessing from usernames or IdP claims.

**Even when the role is present**, method security `@PreAuthorize`, domain permissions, ownership/tenant checks, or a `denyAll` policy can still deny access. Check the service layer whenever URL rules look right.

### 5.2. 403 Due to CSRF

In Spring Security Servlet, for web apps using sessions/cookies or credential types sent automatically by browsers, CSRF protection is essential.

Example request missing token:

~~~http
POST /web/notes HTTP/1.1
Cookie: JSESSIONID=...
Content-Type: application/x-www-form-urlencoded

text=hello
~~~

When CSRF is enabled and the request requires a token, `CsrfFilter` typically returns **403** even if the session is valid and the user holds the required role.

A valid request can include a hidden `_csrf` field with name/value rendered by the server:

~~~html
<form method="post" action="/web/notes">
    <input name="text" value="hello">
    <input type="hidden" name="_csrf" value="server-provided-value">
    <button type="submit">Save</button>
</form>
~~~

The value above is **illustrative only**; never hard-code tokens or invent fake strings. With Spring MVC/Thymeleaf, the server can expose `_csrf.parameterName` and `_csrf.token` on the request, or automatically insert the token via `RequestDataValueProcessor` depending on form rendering.

To prove a 403 is caused by **role** in a MockMvc POST test, supply a valid `csrf()` and test a user lacking authority. If you forget the token, a 403 test can **pass for the wrong reason**.

### 5.3. DenyAll or Wrong SecurityFilterChain

With multiple chains:

~~~text
@Order(1): /api/admin/**       -> ADMIN rule
@Order(2): /api/**             -> API rule
@Order(3): catch-all           -> WEB / denyAll rule
~~~

Spring Security picks the **first matching SecurityFilterChain**. Rules on later chains are not evaluated once an earlier chain matches.

- `http.securityMatcher(...)`: selects the scope of the **chain**.
- `authorizeHttpRequests().requestMatchers(...)`: selects **permission rules inside the chain**.
- `anyRequest().denyAll()`: blocks requests entering the chain that matched no allow rule.
- A catch-all chain without `securityMatcher`: protects remaining URLs.

An admin user can get 403 not because the account lacks a role, but because the request entered a **different** chain or hit `denyAll` before the intended allow rule.

### 5.4. CSRF and CORS Are Not the Same Thing

A browser making a cross-origin request may send a preflight `OPTIONS`. If CORS is misconfigured, the browser may block the request or the server/proxy may return 401/403 on preflight. Do not confuse this with CSRF:

- **CORS** controls how browsers may permit and read certain cross-origin requests. It is not a token authentication mechanism.
- **CSRF** protects state-changing operations against browsers being tricked into sending credentials automatically.
- **401/403 preflight** can happen before the main request is ever sent; inspect `OPTIONS`, `Origin`, `Access-Control-Request-Method`, and `Access-Control-Allow-*` separately.
- **Do not** combine `Access-Control-Allow-Origin: *` with credentialed CORS as a cure-all.
- For SPAs using cookies, analyze **CORS, CSRF, SameSite, and session** together; stateless bearer APIs have a different threat model.

## 6. When Is 302 Expected, and When Is 302 Wrong?

### 6.1. Anonymous Request to Web Form Login

Browser sends:

~~~http
GET /web/home HTTP/1.1
Host: localhost:8080
~~~

If `/web/home` requires authentication and the chain uses `formLogin()`, the typical result is:

~~~http
HTTP/1.1 302 Found
Location: http://localhost:8080/login
~~~

`Location` is the redirect target. This is normal form-login flow behavior, not evidence that the endpoint became public.

### 6.2. Redirect After Login

After a valid POST `/login`, Spring Security may:

- Redirect to the initial **saved request** that triggered login.
- Redirect to `defaultSuccessUrl` or a URL chosen by `AuthenticationSuccessHandler`.
- Redirect to an application-configured target URL.

If a test expects `/dashboard` but actually lands on `/orders/42`, the request cache may have saved the original URL. `defaultSuccessUrl("/dashboard", true)` forces the default target in that configuration, whereas without forcing it, the saved request can take precedence.

**Never check only status 302; assert the `Location` header along with session/request-cache context**. A redirect response with the right status but wrong target is still a functional bug.

### 6.3. Login Redirect Loop

Scenario:

~~~text
GET /web/home
 -> 302 /login
GET /login
 -> 302 /login
GET /login
 -> 302 /login
 ...
~~~

Possible causes:

1. `/login` is **not `permitAll`**, or lies outside the chain containing `formLogin`/the default login page filter.
2. Session cookies are not retained due to **`Domain`, `Path`, `Secure`, `SameSite`, HTTPS/HTTP, or proxy settings**.
3. After successful login, `SecurityContext` is not saved/restored as expected.
4. A reverse proxy rewrites host/scheme inconsistently, bouncing between HTTP and HTTPS.
5. OAuth2/OIDC redirect URI, callback path, `state`, or session mismatch.
6. A custom handler/controller redirects to login even when authenticated.
7. The browser automatically follows redirects, hiding the first step in final logs.

Inspect **every 302 response**, `Location`, and `Set-Cookie` (keeping secrets redacted), not just the final URL in the address bar.

### 6.4. Redirects Not Coming from Spring Security

A `302` can also come from:

- A controller returning `redirect:/...`.
- The servlet container rewriting URLs or protecting sessions per its own config.
- A gateway/ingress/CDN redirecting HTTP to HTTPS, adding slashes, or changing hostnames.
- Another SSO library (CAS, SAML2, OAuth2 Login).
- An application exception handler or post-form-submit redirect.

Always identify **which layer generated the response**. Use a safe correlation ID to match gateway, application, and test access logs.

## 7. Building a Runnable Diagnostic Project: Java 17 + Spring Boot 3.3.5

The example uses **two SecurityFilterChains** so outcomes can be distinguished by behavior:

- **API chain** `/api/**` uses HTTP Basic: anonymous typically **401**, valid user+permission **200**, user lacking permission **403**.
- **Web/fallback chain** handles remaining paths with form login: anonymous to `/web/home` typically **302 /login**, user lacking `ROLE_ADMIN` on `/web/admin` **403**.
- **POST** in both groups still requires **CSRF** by default in this demo; HTTP Basic credentials can be auto-sent by browsers, so do not disable CSRF merely because of the word "API".
- **Catch-all `denyAll`** blocks undeclared URLs; a real `/shadow` controller exists yet cannot be accessed.
- Spring Security Test / MockMvc verifies both status codes and selected response headers.

This is a diagnostic model to **separate root causes**; production needs appropriate providers, session strategies, CSRF policies, and resource authorization.

### 7.4. src/main/java/demo/SecurityConfiguration.java

~~~java
package demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfiguration {

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    UserDetailsService testUsers(PasswordEncoder encoder) {
        // Fixed users/passwords for local demo only.
        return new InMemoryUserDetailsManager(
            User.withUsername("reader")
                .password(encoder.encode("demo-only"))
                .authorities("DOC_READ").build(),
            User.withUsername("writer")
                .password(encoder.encode("demo-only"))
                .authorities("DOC_WRITE").build(),
            User.withUsername("editor")
                .password(encoder.encode("demo-only"))
                .roles("EDITOR").build(),
            User.withUsername("admin")
                .password(encoder.encode("demo-only"))
                .roles("ADMIN").build()
        );
    }

    // API evaluated first: Basic challenge when unauthenticated.
    @Bean
    @Order(1)
    SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/api/public")
                    .permitAll()
                .requestMatchers(HttpMethod.GET, "/api/documents")
                    .hasAuthority("DOC_READ")
                .requestMatchers(HttpMethod.POST, "/api/documents")
                    .hasAuthority("DOC_WRITE")
                .anyRequest().denyAll()
            )
            .httpBasic(Customizer.withDefaults());

        // Keep default CSRF: Basic credentials may be sent automatically by browsers.
        return http.build();
    }

    // No securityMatcher restriction: acts as both web chain and catch-all.
    @Bean
    @Order(2)
    SecurityFilterChain webAndFallback(HttpSecurity http)
            throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/error", "/login")
                    .permitAll()
                .requestMatchers(HttpMethod.GET, "/web/home")
                    .authenticated()
                .requestMatchers(HttpMethod.GET, "/web/admin")
                    .hasRole("ADMIN")
                .requestMatchers(HttpMethod.POST, "/web/notes")
                    .hasRole("EDITOR")
                .anyRequest().denyAll()
            )
            .formLogin(form -> form
                .defaultSuccessUrl("/web/home", true)
            )
            .logout(Customizer.withDefaults());

        // Do not disable CSRF: form login, form POST, and logout all require a token.
        return http.build();
    }
}
~~~

**Explanation:**

1. `apiChain` has `securityMatcher("/api/**")`, so GET `/api/documents` is handled by the Basic entry point. Unauthenticated requests usually return **401**, not a redirect to the login form.
2. `webAndFallback` declares no specific `securityMatcher`, so it covers all requests **that did not match the API chain**. Anonymous GET `/web/home` usually returns **302** to `/login`.
3. `@Order(1)` precedes `@Order(2)`: order decides chain selection; `anyRequest` only decides rules **inside the selected chain**.
4. `hasRole("ADMIN")` requires `ROLE_ADMIN`, whereas `hasAuthority("DOC_READ")` requires exact `DOC_READ`.
5. `anyRequest().denyAll()` is a fail-closed policy: new routes or methods do not become public automatically.
6. `formLogin` generates the default login page; `defaultSuccessUrl("/web/home", true)` forces the post-login target instead of using a saved request. A real system might want to preserve saved-request behavior, so weigh that before forcing a target.
7. The `demo-only` password is in source strictly for learning. **Never use hard-coded users or HTTP Basic without TLS in production**.
8. The code keeps default CSRF protection on both chains. Do not assume every Basic API must share the exact same policy: the actual threat model determines that.

**Expectation:** anonymous API 401, authorized 200, authenticated lacking permission 403, anonymous web 302. These are **code-expected outcomes**, not live execution logs captured during authoring.

## 8. MockMvc: Testing Causes Rather Than Just Status Codes

### 8.1. src/test/java/demo/StatusDemoTests.java

~~~java
package demo;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpHeaders;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.test.web.servlet.MockMvc;

import static org.hamcrest.Matchers.containsString;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.csrf;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.user;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class StatusDemoTests {

    @Autowired
    MockMvc mvc;

    @Test
    void publicApiReturns200() throws Exception {
        mvc.perform(get("/api/public"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.message").value("api-public"));
    }

    @Test
    void apiWithoutCredentialsReturns401BasicChallenge()
~~~

### 8.2. Important Testing Notes

- **`.with(user(...))`** attaches a synthetic authentication onto a **specific MockMvc request**. It tests authorization but **does not exercise the password encoder or real HTTP Basic authentication**.
- **`.with(httpBasic(...))`** builds a Basic header to test the API chain's real authentication path. The wrong-password test confirms at least one rejection branch.
- **`.with(csrf())`** generates a valid test CSRF token; use it when isolating POST authorization from missing-token failures.
- **`status().isFound()`** verifies 302, and **`header().string("Location", ...)`** checks the redirect target URL. Asserting 302 alone is not enough.
- **`header().string("WWW-Authenticate", ...)`** confirms the API receives a Basic challenge, distinguishing it from a form-login redirect.
- **`/shadow`** has a real controller yet must be blocked by the catch-all `denyAll`. This test catches the risk of deleting the fallback chain.
- **`/api/unlisted`** has no controller yet matches the API chain; testing with an authenticated user yields 403 from `denyAll` **before MVC checks whether a route exists**.
- **`@SpringBootTest` + `@AutoConfigureMockMvc`** loads the `ApplicationContext` and Spring Security filters. With `MockMvcBuilders.standaloneSetup` if you forget `springSecurity()`, tests can skip security and give misleading results.
- Never use `@AutoConfigureMockMvc(addFilters = false)` when the goal is testing security filters.

## 9. Practical Step-by-Step Investigation Method

### Step 1 — Capture the Initial Request/Response

Do not start with a final browser screenshot. Record **secret-free** facts:

| Field | Example |
| --- | --- |
| Method + path | `GET /api/documents` |
| Scheme/host | `https://api.example.test` |
| Initial response | `401 Unauthorized` |
| `WWW-Authenticate` | `Basic realm="Realm"` |
| `Location` if redirected | `/login` or `https://...` |
| Were credentials sent? | Yes/no, **do not record values** |
| Was a session cookie present? | Yes/no, **do not record ID** |
| CSRF (for POST) | Present/missing/invalid, **never log token** |
| Content-Type / Accept | `application/json` / `text/html` |
| Correlation ID | Safe ID linking gateway and application |

Also check whether **the request used the right HTTP method**. GET and POST on the same URL can hit different rules, and POST involves CSRF.

### Step 2 — Check the Right SecurityFilterChain

With multiple chains, list `securityMatcher` and `@Order` and find the **first matching** chain for the request. Only then inspect `requestMatchers` inside `authorizeHttpRequests` of that chain.

If a chain only matches `/api/**`, then `anyRequest().authenticated()` or `denyAll()` inside it **does not** protect `/web/**`. A separate chain or catch-all is needed. If a `formLogin` chain has too narrow a matcher, `/login` or the OAuth2 callback may fall outside the login filter's scope.

To inspect chains via logs in a test environment, you can use a configuration **strictly for temporary debugging**:

~~~yaml
logging:
  level:
    org.springframework.security: DEBUG
    org.springframework.security.web.FilterChainProxy: TRACE
~~~

Log levels vary across Spring Security versions; never rely solely on one fixed log line to draw conclusions. **Never enable broad TRACE in production**, and configure masking for `Authorization`, session cookies, tokens, and PII across all loggers and gateways.

### Step 3 — Determine Anonymous vs. Authenticated

For a blocked request, ask:

- Was `Authentication` constructed from credentials/token/session?
- If so, what are the `principal` and **authority names**? You may log authority names in test environments with dummy data, never real credentials/tokens.
- Does the user have `ROLE_ADMIN` or just `ADMIN`? `SCOPE_reports.read` or just `ROLE_USER`?
- Are multiple authentication mechanisms (session + Basic + bearer) in the same chain causing the wrong authentication type to be selected?
- If login succeeded yet the next request is anonymous again: was `SecurityContext` saved to the session, and was the cookie sent back?

When troubleshooting 401, confirm the provider was actually invoked. For bearer tokens, inspect validator/introspector errors via safe instrumentation; for Basic, inspect `AuthenticationManager`/providers without logging passwords.

### Step 4 — Distinguish 403 from CSRF vs. 403 from Authorization

Test the matrix:

| Authentication | CSRF Token | Required Permission | POST Expectation |
| --- | --- | --- | --- |
| Logged in, permitted | **Missing** | Sufficient | 403 from CSRF may fire before authorization. |
| Logged in, unpermitted | Valid | Missing | 403 from authorization. |
| Logged in, permitted | Valid | Sufficient | Reaches controller; typically 200/201/302 per app. |
| Anonymous | Missing | None | May be 403 from CSRF before entry point is invoked. |
| Anonymous | Valid | None | May be 401/302 depending on entry point and chain. |

**Do not disable CSRF just to make a test green**. For session/cookie web apps, render/send a valid token and verify login/logout flows refresh tokens as needed. For stateless bearer APIs, a different CSRF policy may apply based on a validated threat model.

### Step 5 — Find the Redirect Origin and Inspect Session State

For 302, check:

1. Check the **`Location` header of the first response** and every subsequent hop.
2. Identify whether the redirect came from a Spring Security entry point, authentication success/failure handler, controller, OAuth2 flow, or gateway.
3. For a login redirect loop, verify whether the session cookie was **set via `Set-Cookie` and sent back**; record only presence and safe attributes.
4. Check **HTTPS, Host, `X-Forwarded-Proto`, context path, cookie `Secure`/`SameSite`/`Domain`/`Path`**, reverse proxies, and callback URLs.
5. Verify saved request / target URL logic: original request, success handler, `defaultSuccessUrl(..., true)`, or custom handler.
6. For OAuth2/OIDC, safely check `redirect_uri`, `state`, callback route, and session; never share real codes/tokens.

### Step 6 — Check Controller and Gateway Layers

If Spring Security allows the request through yet the response is still 403/302:

- **Method security** `@PreAuthorize` or domain permissions may deny at the service layer.
- The controller may return `ResponseEntity.status(FORBIDDEN)`, `redirect:/...`, or throw an exception handled by `@ControllerAdvice`.
- A downstream backend may return 401/403 which the gateway forwards or remaps.
- An error dispatch to `/error` or `FORWARD` to a view may be blocked by another chain.
- A reverse proxy may generate HTTPS redirects itself or block CORS.
- A resource server may enforce **audience, tenant, and per-object permissions** even when a token is valid.

To tell them apart, compare **MockMvc against the app** with requests **through the gateway** for both valid and invalid cases. If the two outcomes differ, investigate the proxy/infrastructure boundary without turning off application security.

## 10. Tricky Case: Failures During ERROR/FORWARD Dispatch

Servlets can perform internal dispatches:

~~~text
REQUEST /api/orders
    -> Controller throws exception
    -> ERROR dispatch /error
    -> security matcher/chain re-evaluated depending on filter dispatcher mapping
    -> /error denied
    -> final response differs from expected 500/404
~~~

So if a controller actually threw an error yet the client receives 403 or a 302 to login, check the dispatcher type and `/error` path. In some applications, `DispatcherType.ERROR` or `DispatcherType.FORWARD` must be explicitly permitted:

~~~java
// Illustrative snippet inside authorizeHttpRequests:
.dispatcherTypeMatchers(
    jakarta.servlet.DispatcherType.ERROR
).permitAll()
~~~

This snippet is **not a standalone Java file** and is not automatically required in every configuration. Permitting error dispatches must be evaluated so sensitive endpoints are not exposed. Never fix a mysterious 403 with `anyRequest().permitAll()` across the entire app.

## 11. When an API Returns Login HTML via 302: Choosing the Entry Point

A JSON API should normally return **401** with an appropriate challenge/response for unauthenticated calls rather than an HTML login redirect. A session-based web app should normally redirect users to login. With both URL groups, there are two design options:

- **Separate `SecurityFilterChain` per path** (as in the example): `/api/**` uses Basic/Bearer and `/web/**` uses form login.
- **One chain with request-specific `AuthenticationEntryPoint`**: use `exceptionHandling(...)` and explicit matchers to select API vs. web entry points when architecture mandates a shared chain.

Diagram:

~~~text
GET /api/profile  -> API chain -> 401 (if anonymous)
GET /web/profile  -> WEB chain -> 302 /login (if anonymous)
GET /web/profile  -> WEB chain -> 200 (if authenticated)
GET /api/profile  -> API chain -> 403 (if authenticated but lacking permission)
~~~

**Do not rely solely on the `Accept: application/json` header** to guess the client if the app has distinct API URLs. Browsers can send varying `Accept` headers; entry-point selection should be a **tested contract**, not accidentally coupled to content negotiation. If multiple authentication mechanisms coexist in one chain, verify the ordering of `exceptionHandling().defaultAuthenticationEntryPointFor(...)` and matchers under the current API.

If the API uses bearer tokens, changing only the entry point is insufficient: ensure the bearer filter/validator is properly configured and does not accidentally accept session cookies as API authentication.

## 12. Testing Session, Login, and Logout Without Weakening Security

### 12.1. Case: GET Login Works but POST Login Returns 403

This is usually **login CSRF**:

- GET `/login` renders the form with a CSRF token.
- POST `/login` submits username/password and a valid CSRF token.
- If the token is missing/wrong or the session changed, `CsrfFilter` returns 403 before checking the password.

Do not delete `csrf()` or blindly add `permitAll` thinking it is fixed. `permitAll` **does not disable CSRF checks**.

### 12.2. Login Returns 302 Success, Yet the Next GET Redirects 302 to /login

Check:

- Did the browser store the issued session cookie?
- Does the cookie have `Secure` while the next page uses HTTP?
- Do cookie `Domain` or `Path` mismatch?
- Did the hostname change between `localhost`, IP, proxy hostname, or subdomain?
- Does the session survive across multiple requests/nodes in the server or load balancer?
- Did `SecurityContextRepository`, `SessionCreationPolicy`, session fixation protection, or a custom filter alter context persistence?
- Is `SameSite` compatible with cross-site OAuth2 redirect/session cookie flows?
- Did login actually succeed, or did it hit a failure handler that also returns 302?

Never rely on status 302 alone to conclude authentication succeeded. Inspect **`Location` of POST `/login`**, the session, and the subsequent authenticated request.

### 12.3. Logout 302 Differs from Successful Logout

Spring Security logout normally uses **POST `/logout` with CSRF** when CSRF is enabled. A GET `/logout` may merely display a confirmation page. Post-logout may 302 to `/login?logout` or a configured URL.

Proper tests must verify HTTP method, token, and that the user is cleared—not merely a redirect. Old session cookies and tokens may be invalidated, so submitting a form retained from the prior session can return 403.

## 13. Testing Commonly Misleading Assumptions

| False Assumption | Why It Is Dangerous | How to Verify |
| --- | --- | --- |
| “401 always means missing user role.” | 401 is normally an authentication challenge, not an authorization denial. | Check entry point, challenge, and whether a valid `Authentication` exists. |
| “403 always means missing `ROLE_ADMIN`.” | Could be CSRF, `denyAll`, CORS, method security, or tenant checks. | Add valid CSRF for POST; check policy and dispatcher chain. |
| “302 is a security error.” | With form login, redirecting to login is expected behavior. | Inspect `Location` and chain. |
| “200 HTML login means the API granted access.” | The HTTP client may have followed 302 automatically. | Inspect redirect history and `Content-Type`. |
| “With `permitAll`, POST needs no CSRF.” | The CSRF filter operates independently of URL authorization. | Test POST with and without `csrf()`. |
| “Granting `ROLE_ADMIN` passes everywhere.” | Wrong matcher, `denyAll`, or resource/tenant policies still block. | Inspect first matching chain + actual authorities + object permissions. |
| “`anyRequest().authenticated()` inside `/api/**` is enough.” | Does not protect URLs outside that chain's scope. | Test a controller mapped outside `/api` with a catch-all deny. |
| “Every path without a controller must return 404.” | Security can return 401/403 before MVC routing runs. | Test undeclared paths with valid auth; compare handler mapping. |
| “`@WithMockUser` proves password/login works.” | It injects a fake `Authentication`, bypassing the password provider. | Add Basic/formLogin integration tests using real test-fixture credentials. |
| “Disabling filters makes HTTP tests pass cleanly.” | False green because security is gone. | Keep filters enabled in MockMvc and assert denied cases. |
| “CORS `*` fixes all 403s.” | Does not fix roles/CSRF/tokens; can create invalid credentialed CORS config. | Separate preflight, response headers, browser console, and server behavior. |
| “Keeping the same hostname is enough; sessions always survive.” | Proxy scheme, cookie attributes, or server store may be wrong. | Trace each redirect, cookie metadata, and session lifecycle. |

## 14. Debugging by HTTP Status — 15 Steps

1. Record **method, full URL, initial status, `Location`/`WWW-Authenticate`**, without recording secrets.
2. Disable automatic redirect following in test tools to observe the **first 302**.
3. Confirm hostname, scheme, context path, servlet path, HTTP method, and dispatcher type.
4. Find the **first `SecurityFilterChain` matching** the request and its `@Order`.
5. Check whether the chain uses `formLogin`, `httpBasic`, `oauth2ResourceServer`, or a custom provider.
6. Inspect the `AuthenticationEntryPoint` mechanism; verify whether 401 or 302 matches endpoint policy.
7. Confirm whether `Authentication` exists and authenticated properly; do not infer from form usernames.
8. Compare actual authorities `ROLE_`, `SCOPE_`, and `hasAuthority` / `hasRole`.
9. Check the order of `requestMatchers` and `anyRequest()` inside the chain.
10. For POST/PUT/PATCH/DELETE, check **CSRF token/session** before blaming roles.
11. For CORS, separate **OPTIONS preflight** from business requests.
12. If authorization passes, check method security, domain policy, controller, advice, downstream, and error dispatches.
13. For 302 loops, trace every `Location`, `Set-Cookie` attributes, proxy headers, and session continuity.
14. Write a **negative test + positive test** in MockMvc for the exact failure observed, including status and expected headers/body.
15. Modify policy only after finding root cause; verify regressions and never loosen `permitAll` globally.

## 15. Production and Security Checklist

- [ ] HTTP Basic/bearer/form login are cleanly separated by path and chain/entry point.
- [ ] Every protected endpoint matches **at least one `SecurityFilterChain`**; an appropriate catch-all exists.
- [ ] HTTP status and headers follow the API/browser contract; 302s are not masked by auto-following clients.
- [ ] Never log tokens, Basic passwords, session cookies, CSRF tokens, or full sensitive request headers.
- [ ] Tests cover anonymous, authenticated without role, with role, invalid token, invalid CSRF, and redirect targets.
- [ ] CSRF is disabled only where the threat model genuinely allows; session/cookie web apps remain protected.
- [ ] CORS configures origins/methods/headers/credentials properly and does not replace authentication.
- [ ] API bearer tokens validate issuer/audience/lifetime/introspection per provider; self-asserted claims are rejected.
- [ ] Session cookies have proper `Secure`/`HttpOnly`/`SameSite`/`Domain`/`Path` attributes over real HTTPS.
- [ ] Proxy forwarded headers/host/scheme are trusted in a controlled manner; client-supplied headers are not trusted.
- [ ] `/login`, `/logout`, OAuth2 callbacks, `/error`, and internal dispatches reside in the proper chains.
- [ ] Authorization does not rely on URLs alone; resource/tenant/ownership checks run where required.
- [ ] Tests assert status **and** headers: `Location`, `WWW-Authenticate`, response content type.
- [ ] Safe correlation IDs link gateway/app traces without leaking identity or credentials.
- [ ] Newly added endpoints deny by default until policy and tests are intentionally added.

## 16. Self-Check

**Question 1.** Why can the same GET `/api/documents` return 401 when anonymous yet 403 when logged in as another user?

**Answer:** 401 is typically an authentication challenge because valid credentials were not provided; 403 is an authorization denial because the user authenticated yet lacks `DOC_READ`.

**Question 2.** Why can POST `/api/documents` with a user holding `DOC_WRITE` still return 403?

**Answer:** Because the CSRF filter still requires a token in the demo configuration. If CSRF is missing, the request is blocked before permission rules take effect. In MockMvc, add `csrf()` to isolate the role check.

**Question 3.** Why does anonymous GET `/web/home` return 302 instead of 401?

**Answer:** The request entered the web/form-login chain; `LoginUrlAuthenticationEntryPoint` redirects the browser to `/login`. The API Basic chain uses a different entry point.

**Question 4.** Why does the browser report 200 HTML when JavaScript expected JSON?

**Answer:** The API request may have received a 302 to login and `fetch` followed the redirect automatically. Inspect redirect history and `Content-Type` of the final response.

**Question 5.** The user has `ROLE_ADMIN` yet still gets 403; what do you investigate first?

**Answer:** Confirm the active `SecurityFilterChain`, `securityMatcher`, and first matching rule; check actual authorities, `denyAll`, method security, ownership, CSRF, and dispatcher type.

**Question 6.** Does a 302 after POST login prove login succeeded?

**Answer:** No. Both login success and failure handlers, or another controller, can redirect. Inspect `Location`, session, and the next protected request.

**Question 7.** Why must a valid CSRF token be sent when testing a missing-role 403 on POST?

**Answer:** Because without the token, `CsrfFilter` can block the request first and the test will still return 403 even if the authorization rule is completely broken.

**Question 8.** If `/api/unlisted` has no controller yet returns 403, does that mean MVC has that route?

**Answer:** No. The security chain matches the path and `denyAll` can block before controller lookup occurs. 403 and 404 reflect different processing layers.

**Question 9.** Why should CORS preflight errors not be fixed with `permitAll` on every endpoint?

**Answer:** Because CORS/preflight and main-request authorization are two separate concerns. Broadly relaxing authorization creates unauthorized access risk without necessarily fixing CORS.

**Question 10.** What is the first thing to inspect when debugging a redirect loop?

**Answer:** The first 302 response, the `Location` chain, and session cookie attributes step by step, then identify the chain/entry point and proxy/callback behavior.

---

**Conclusion:** Investigating **401, 403, and 302** in Spring Security Servlet is a matter of **identifying which layer produced the response**. 401 usually relates to an authentication challenge; 403 can stem from authorization, CSRF, or another policy; 302 is typically form-login/success-handler navigation yet may also come from a controller or gateway. Always start with the initial request and headers, locate the right `SecurityFilterChain`, verify authentication/authorities/CSRF, trace redirects and sessions, and then write positive and negative MockMvc tests to prove root cause before changing configuration.
