# ASYNC Dispatch, OncePerRequestFilter, and Avoiding Wrong Policy Re-Execution in Spring Security Servlet

> **Scope:** Servlet 3.1+, Spring MVC, Spring Security 6.x, and Spring Boot 3.x (Java 17+). This lesson distinguishes an **asynchronous request** from an **ASYNC dispatch**, explains the real behavior of `OncePerRequestFilter`, how to register dispatcher types, handling `SecurityContext` across threads, and how to prevent operations meant to run once from repeating. Runnable code is structured in a Spring Boot project; remaining fragments are explicitly marked as illustrative.

## 1. Problem: "One HTTP Request" Can Traverse the Filter Chain Multiple Times

In the synchronous Servlet model, an HTTP request is typically processed on one container thread:

~~~text
Client
  |
  v
Servlet container
  -> DispatcherType.REQUEST
  -> Servlet filters / Spring Security FilterChainProxy
  -> DispatcherServlet / Controller
  -> HTTP response
~~~

With Spring MVC async, a controller can return `Callable<T>`, `DeferredResult<T>`, or an equivalent type to **release the initial servlet thread** while the result is not yet ready. Once the result arrives, the container performs an **ASYNC dispatch** to continue response processing:

~~~text
Client sends GET /api/async
          |
          v
[Servlet thread A]
  DispatcherType.REQUEST
  -> Servlet filters
  -> Spring Security filters
  -> DispatcherServlet
  -> Controller returns Callable/DeferredResult
  -> request.startAsync() / suspend
          |
          | thread A can be released
          v
[Worker thread B]
  Callable or work producing the result
  (not by default a Servlet filter dispatch)
          |
          | result ready
          v
[Servlet thread C]
  DispatcherType.ASYNC
  -> filters mapped for ASYNC
  -> Spring Security FilterChainProxy if registered for ASYNC
  -> DispatcherServlet completes response
          |
          v
Client receives JSON/HTML
~~~

**The same logical HTTP request can pass through the filter chain multiple times.** A subsequent pass has `DispatcherType.ASYNC`, not a brand-new HTTP request sent by the browser. If you write a custom filter performing side effects (sending audit events, writing to a database, charging fees, updating quotas) every time it executes without understanding dispatches, you can create duplicate actions.

Conversely, if a filter must set up **MDC logging context** or a `ThreadLocal` on each servlet thread, skipping the ASYNC dispatch can cause context to be missing during response completion. The question is not "re-run or not?" in the abstract, but **which policy is allowed to run on which dispatcher type and thread?**

## 2. Request, Dispatch, Thread, and Business Work Are Not the Same Concept

| Concept | Example | Reminder |
| --- | --- | --- |
| HTTP request | A single client call `GET /api/async`. | One request may undergo multiple dispatches. |
| `DispatcherType.REQUEST` | Initial pass when the container receives the client request. | Standard entry point. |
| `DispatcherType.ASYNC` | Container pass re-dispatching the request after async processing. | Does not necessarily use the original thread. |
| Worker thread | `Callable.call()`, executor task, or application callback. | **Not automatically** a Servlet filter dispatch. |
| `DispatcherType.ERROR` | Error dispatch generated by the container. | May re-invoke filters if registered and permitted. |
| `DispatcherType.FORWARD` / `INCLUDE` | Internal Servlet forward/include. | Depends on dispatcher mapping, not an extra client request. |
| SecurityContext | `Authentication` applied to the thread/request per Spring Security rules. | ThreadLocal does not automatically propagate to other threads. |
| Idempotency | Way to guarantee business work is not processed twice. | Cannot be replaced by a filter flag in every system. |

For example, there may be **one** HTTP request, **two** servlet dispatches, and **one or more** worker tasks. Never use `Thread.currentThread().getId()` as a request ID: one request can switch threads, while one thread processes many requests over time.

If you need request correlation, use a request ID generated by a trusted server/gateway, storing it as a request attribute or inside a managed context propagation mechanism. When handling async requests, distinguish:
- **"run once for REQUEST dispatch"**;
- **"run once for each participating servlet dispatch"**;
- **"run once as a durable business operation"**.

These three requirements are not equivalent.

## 3. Does OncePerRequestFilter Truly Run Only Once?

`org.springframework.web.filter.OncePerRequestFilter` is an abstract base class in **Spring Web**, and many Spring Security filters follow a similar model.

An implementation typically overrides:

~~~java
@Override
protected void doFilterInternal(
        HttpServletRequest request,
        HttpServletResponse response,
        FilterChain filterChain)
        throws ServletException, IOException {

    // Filter logic ...
    filterChain.doFilter(request, response);
}
~~~

This is a fragment without complete imports/class. `OncePerRequestFilter` uses an **"already filtered" marker request attribute** to avoid re-running logic when a filter is encountered multiple times within **the same dispatch or a nested branch**. It is not a distributed idempotency store, persists no durable state, and must not be rigidly interpreted as "exactly once across the entire lifetime of the HTTP request".

### 3.1. How Is the Marker Set and Removed?

Abbreviated description:

~~~text
Filter receives request
  |
  +--> if dispatcher type should be skipped -> call only filterChain.doFilter
  |
  +--> if "already filtered" marker exists:
  |       -> do not re-run doFilterInternal in the normal branch
  |
  +--> if no marker yet:
          -> set marker request attribute
          -> call doFilterInternal(...)
          -> in finally: remove marker
~~~

**Crucial point:** When the `REQUEST` pass finishes by initiating async, the filter has usually completed its `finally` block and **removed the marker**. If the container re-dispatches with `ASYNC` and the filter is permitted on that dispatcher, `doFilterInternal` **can run once more** on that same request. This is intentional behavior, not a framework bug.

Markers are keyed by filter name to avoid duplicating a filter in one chain; if you register the same logic as **two distinct filter instances**, or run a filter both outside and inside the Spring Security chain, inspect naming/registration to avoid unintended effects.

### 3.2. shouldNotFilterAsyncDispatch()

`OncePerRequestFilter` provides the hook:

~~~java
@Override
protected boolean shouldNotFilterAsyncDispatch() {
    return true;
}
~~~

- **`true`**: skips `ASYNC dispatch` for `doFilterInternal`; this is the **default behavior** of `OncePerRequestFilter`.
- **`false`**: allows `doFilterInternal` logic to run on **ASYNC dispatch**, provided the filter mapping actually applies to that dispatcher.
- Overriding to `false` does **not** make the filter run on the `Callable.call()` thread; it only affects a Servlet filter invocation during ASYNC dispatch.
- If multiple independent ASYNC dispatches occur, `doFilterInternal` may run in each pass, not strictly once.

If you only want to inspect/transform the incoming request once, usually keep the default `true`. If you need to establish logging context on **the container thread completing the response**, you can return `false` and ensure the logic is designed to be **dispatch-aware**.

### 3.3. shouldNotFilterErrorDispatch()

~~~java
@Override
protected boolean shouldNotFilterErrorDispatch() {
    return true;
}
~~~

By default, `OncePerRequestFilter` skips `ERROR dispatch`. Change to `false` if the filter itself must participate in error-dispatch handling/context setup, while accounting for nested errors, `doFilterNestedErrorDispatch`, and the fact that the response may already be committed.

Never blindly flip both hooks to `false` just because "I want the filter to always run". Authentication, authorization, tracing, logging, and auditing filters have **different dispatcher policies**.

### 3.4. shouldNotFilter(HttpServletRequest)

A filter can also override `shouldNotFilter(request)` to skip specific paths or conditions:

~~~java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    return request.getRequestURI().startsWith("/assets/");
}
~~~

This is an illustrative fragment, and path-prefix matching with `startsWith` is unsuitable for all security requirements. If skipping a sensitive endpoint, use a matcher with clear semantics and test encoded/normalized paths; **never use custom skips to bypass authorization rules**.

## 4. Two Configuration Layers: Servlet Dispatcher Mapping and OncePerRequestFilter Hooks

A filter only gets a chance to run on ASYNC dispatch when **both conditions** are met:

1. **Servlet container side:** the filter registration is mapped for `DispatcherType.ASYNC`; filters/servlets support async per required configuration.
2. **Implementation side:** the filter does not actively skip `ASYNC` via `shouldNotFilterAsyncDispatch()`/custom logic.

If the filter runs inside Spring Security, a third condition is needed:

3. **Spring Security's `DelegatingFilterProxy` / `FilterChainProxy`** is registered for `ASYNC`, and the appropriate security chain is selected on that pass.

~~~text
ASYNC dispatch
  |
  +--> Servlet filter mapping includes ASYNC?
  |        No -> filter is not invoked
  |
  +--> Spring Security proxy mapping includes ASYNC?
  |        No -> SecurityFilterChain is not invoked on this pass
  |
  +--> Custom filter is inside the matching chain?
  |        No -> filter is not invoked
  |
  +--> shouldNotFilterAsyncDispatch() == true?
  |        Yes -> doFilterInternal does not run
  |
  +--> All conditions permit:
           doFilterInternal runs on ASYNC dispatch
~~~

**Overriding the hook alone is not enough.** Conversely, merely adding `ASYNC` to the dispatcher mapping does not force every `OncePerRequestFilter` to re-run, because some filters choose to skip it.

### 4.1. Spring Boot dispatcher-types

In a Spring Boot Servlet application, you can control the dispatcher types of the **Spring Security filter registration** via configuration:

~~~yaml
spring:
  security:
    filter:
      dispatcher-types: request,async,error
~~~

This form shows Spring Security's `DelegatingFilterProxy` can be invoked on the corresponding dispatches. Always verify the **effective configuration** on your Spring Boot version, custom servlet registrations, and web container; never infer from YAML alone that every filter runs on ASYNC. When registering a standalone custom filter directly with the Servlet container, configure dispatcher types on **that specific registration**.

### 4.2. Async Support and IllegalStateException

If any filter/servlet registration along the path lacks async support, calling `startAsync()` can fail with an error like `IllegalStateException`. Check Servlet API `isAsyncSupported()`, `asyncSupported=true` on registrations, and container support.

`OncePerRequestFilter` does not call `startAsync()` itself and does not enable async support for the entire filter chain automatically.

### 4.3. Avoiding Double Registration of the Same Filter

If you declare a filter as a `@Component` or `@Bean` **and** insert it into `HttpSecurity.addFilterBefore(...)`, Spring Boot may register it as a **standalone Servlet filter** while Spring Security also invokes it **inside `FilterChainProxy`**. This easily causes misdiagnosis, unexpected ordering, or duplicate runs across dispatches.

There are two clear patterns:

- Instantiate a **new object, not a Servlet filter bean**, and add it **only** to `SecurityFilterChain` via `http.addFilterBefore(new MyFilter(), SomeSecurityFilter.class)`. The complete example in section 7 uses this approach.
- If the filter must be a Spring bean, use `FilterRegistrationBean` with `setEnabled(false)` to disable Servlet auto-registration, then add the bean to the security chain. Test the exact registration on your Boot version.

Never combine `@WebFilter`/`@Component` and `addFilterBefore` without knowing how many actual filter registrations exist. And never rely on the "already filtered" marker as a band-aid for double registration.

## 5. Three Processing Policies to Keep Separate

### 5.1. Run Only on the Initial REQUEST Pass

Examples: reading normalized request metadata, generating a request identifier, recording a "request accepted for processing" event, or setting a state flag.

The simplest approach is usually keeping the defaults `shouldNotFilterAsyncDispatch() == true` and `shouldNotFilterErrorDispatch() == true`. If the filter still participates in other dispatchers, check explicitly:

~~~java
if (request.getDispatcherType() == DispatcherType.REQUEST) {
    // Run only on REQUEST pass; do not treat async completion as a new request.
}
~~~

Still, **never place non-repeatable business operations** (money transfers, provisioning, sending emails) inside a filter just because you want "once". It does not guard against client retries, failover, or distributed execution; use transactions, unique constraints, idempotency keys, and outboxes tailored to the problem.

### 5.2. Run on Each Participating Servlet Dispatch/Thread

Example: adding `traceId` to MDC on the thread handling `REQUEST`, and **re-establishing** MDC when the container runs `ASYNC` on another thread. For this kind of filter:

- override `shouldNotFilterAsyncDispatch()` to return `false`;
- set MDC **before** `filterChain.doFilter`;
- clear/restore MDC in `finally` to avoid leaking context to the next request on a pooled thread;
- store the generated trace ID in a request attribute once, rather than generating a new ID on every dispatch;
- if the `Callable`'s worker thread needs MDC, propagate context to the worker **via a dedicated mechanism**, rather than inferring it from the ASYNC filter.

MDC is a `ThreadLocal` in common logging frameworks, so having `traceId` on servlet thread A does not guarantee `traceId` automatically appears on worker thread B.

### 5.3. Business Exactly-Once Across All Dispatches/Retries

For example, a payment `POST /payments` can suffer client retries, gateway retries, or multiple business task executions. A Servlet request attribute only stops certain duplicates **within the same request object**; it **cannot** guarantee exactly-once when a new HTTP request arrives, the process restarts, or another worker picks up the job. You need:
- an idempotency key scoped by principal/tenant/operation;
- persisting result state under a unique constraint or transaction;
- deterministically rejecting/memoizing duplicate requests;
- transactions/outbox and idempotent consumers when publishing messages;
- tests for retries, timeouts, async double completion, and crash/recovery.

**Never treat `OncePerRequestFilter` as a promise of business exactly-once semantics.**

## 6. SecurityContext Across Asynchronous Processing

### 6.1. SecurityContextHolder Usually Uses ThreadLocal

`SecurityContextHolder` normally stores context per thread. During the initial `REQUEST`, the Spring Security filter chain authenticates the caller and places `Authentication` in context for downstream code. When an executor runs work on another thread, **do not assume that context appears automatically**.

~~~text
Thread A (REQUEST):
  SecurityContextHolder -> alice
          |
          +--> submit task
                     |
                     v
Thread B (pool worker):
  SecurityContextHolder -> ? (depends on propagation mechanism)
~~~

Calling `SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)` is not a general fix for thread pools: reused threads have independent lifecycles and risk carrying the wrong context if not cleaned up properly.

### 6.2. Spring MVC Callable

Spring Security integrates with Spring MVC async `Callable` through mechanisms such as `WebAsyncManagerIntegrationFilter`. It can transfer the initial request's `SecurityContext` for the `Callable` execution window and clean up afterward. Thus, with standard Spring Security web integration, code inside `Callable` can read the caller's `Authentication`.

Do not extrapolate this into "every kind of async task gets context":
- Spring MVC `Callable` has dedicated framework integration.
- `DeferredResult` can be completed by an application-supplied thread/event; such manually spawned work is not covered identically by default.
- `@Async`, custom executors, `CompletableFuture`, scheduled jobs, and queue consumers generally require explicit context propagation when justified by security requirements.
- On the `ASYNC dispatch` running on another container thread, Spring Security must be registered and restore/manage security context appropriately; never assume Spring Security ran if dispatcher mappings do not match.

### 6.3. DelegatingSecurityContextExecutor for Self-Managed Tasks

Spring Security provides `DelegatingSecurityContextExecutor`, `DelegatingSecurityContextRunnable`, and related wrappers to execute work with a controlled propagated context.

Conceptual fragment:

~~~java
Executor wrapped = new DelegatingSecurityContextExecutor(delegateExecutor);
wrapped.execute(() -> {
    Authentication current =
        SecurityContextHolder.getContext().getAuthentication();
    // Use identity only when the task genuinely belongs to an authenticated request.
});
~~~

This is a **fragment** requiring imports and an application-defined `delegateExecutor` variable. With the constructor taking a delegate executor, the wrapper can capture the current context at task submission and clean up context per lifecycle. Never propagate user info unintentionally to long-running jobs, and never store `SecurityContext` in static fields.

**Propagation does not replace authorization.** A worker holding principal `alice` must still check permissions when accessing resources; domain and tenant data must never be trusted merely because ThreadLocal has an authentication.

### 6.4. Authentication and MDC Are Two Different Contexts

`WebAsyncManagerIntegrationFilter` supports **Spring SecurityContext** for `Callable`, yet it does not automatically guarantee MDC logging correlation across arbitrary libraries. If MDC is needed on the worker thread, use a `TaskDecorator`, wrapped executor, or appropriate observability context propagation with post-task cleanup.

Do not set MDC on thread A expecting `shouldNotFilterAsyncDispatch(false)` to enter thread B while `Callable.call()` runs. The ASYNC filter runs on a **Servlet dispatch**—typically the response-completing thread—not where background work executes.

## 7. Complete Example: Spring Boot 3 + Java 17

The example builds an endpoint protected by HTTP Basic, returning a `Callable` for Spring MVC async handling. `AsyncTraceFilter` is registered **only inside SecurityFilterChain**, participating in both `REQUEST` and `ASYNC` dispatches to populate MDC on each servlet thread. It **does not** run business logic again on re-entry.

We will count:
- visits through `REQUEST` and `ASYNC`;
- an `initialWork` marker set only during `REQUEST` and only once per request;
- a trace ID preserved across dispatches.

These counters are **for testing/illustration only**, not a production idempotency mechanism.

### 7.4. AsyncTraceFilter: Re-Running on ASYNC Without Repeating REQUEST Policy

**`src/main/java/com/example/asyncfilter/AsyncTraceFilter.java`:**

~~~java
package com.example.asyncfilter;

import java.io.IOException;
import java.util.UUID;

import jakarta.servlet.DispatcherType;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.slf4j.MDC;
import org.springframework.web.filter.OncePerRequestFilter;

public final class AsyncTraceFilter extends OncePerRequestFilter {

    static final String TRACE_ID =
        AsyncTraceFilter.class.getName() + ".traceId";

    static final String REQUEST_VISITS =
        AsyncTraceFilter.class.getName() + ".requestVisits";

    static final String ASYNC_VISITS =
        AsyncTraceFilter.class.getName() + ".asyncVisits";

    static final String INITIAL_MARKER =
        AsyncTraceFilter.class.getName() + ".initialOnly";

    @Override
    protected boolean shouldNotFilterAsyncDispatch() {
        // Allow doFilterInternal to run during ASYNC dispatch.
        return false;
    }

    @Override
    protected boolean shouldNotFilterErrorDispatch() {
        // ERROR dispatch has its own policy; this example skips it.
        return true;
    }

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain)
            throws ServletException, IOException {

        String traceId = (String) request.getAttribute(TRACE_ID);
        if (traceId == null) {
            traceId = UUID.randomUUID().toString();
            request.setAttribute(TRACE_ID, traceId);
        }

        DispatcherType dispatch = request.getDispatcherType();

        if (dispatch == DispatcherType.REQUEST) {
            increment(request, REQUEST_VISITS);

            // Policy for the initial REQUEST pass only.
            // Marker is illustrative only; does NOT guarantee business exactly-once.
            if (request.getAttribute(INITIAL_MARKER) == null) {
                request.setAttribute(INITIAL_MARKER, Boolean.TRUE);
            }
        } else if (dispatch == DispatcherType.ASYNC) {
            // On the ASYNC pass, do only dispatch-safe work.
            increment(request, ASYNC_VISITS);
        }

        // MDC is thread-bound; must set/cleanup on EVERY dispatch.
        String priorTrace = MDC.get("traceId");
        MDC.put("traceId", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            if (priorTrace == null) {
                MDC.remove("traceId");
            } else {
                MDC.put("traceId", priorTrace);
            }
        }
    }

    private static void increment(
            HttpServletRequest request, String attribute) {

        Integer before = (Integer) request.getAttribute(attribute);
        request.setAttribute(attribute,
            before == null ? 1 : before + 1);
    }
}
~~~

**Detailed explanation:**

1. `shouldNotFilterAsyncDispatch() == false` is a **deliberate choice** because the filter's goal is populating MDC on every servlet dispatch.
2. `TRACE_ID` is generated once and kept in request attributes, so both dispatches of the same request share the ID. If correlating with a gateway, accept an external request ID only when the gateway is controlled/sanitized; never trust unverified input headers.
3. `INITIAL_MARKER` is set only when `DispatcherType.REQUEST`. When the filter sees `ASYNC`, it **does not re-run** the initial-only action.
4. `REQUEST_VISITS` and `ASYNC_VISITS` counters help tests observe **how many times the filter actually ran**. They are not used as application state.
5. MDC is restored/cleared in `finally`, avoiding polluting thread pools. If the servlet thread already held a valid prior trace context, the example preserves that old value after the filter instead of blindly wiping context managed by an outer layer.
6. Real systems may have nested dispatches/error conditions, multiple filter instances, or separate chains; tests must cover the product's **actual registrations**.
7. This filter **does not create Authentication** and **cannot bypass AuthorizationFilter**; security responsibility remains with the chain.

Never use request attributes as durable business keys: when a client sends a new HTTP request or the system restarts, markers are gone. "Already handled the request" at this layer is completely different from "recorded the bank transfer in the database exactly once".

### 7.5. SecurityConfig: Registering the Filter Only Inside SecurityFilterChain

**`src/main/java/com/example/asyncfilter/SecurityConfig.java`:**

~~~java
package com.example.asyncfilter;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.access.intercept.AuthorizationFilter;

@Configuration
public class SecurityConfig {

    @Bean
    UserDetailsService userDetailsService() {
        // Exercise only; fixed passwords are unsuitable for production.
        return new InMemoryUserDetailsManager(
            User.withUsername("alice")
                .password("{noop}demo-pass")
                .roles("USER")
                .build());
    }

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {

        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/async").authenticated()
                .anyRequest().denyAll())
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .addFilterBefore(
                new AsyncTraceFilter(),
                AuthorizationFilter.class)
            .build();
    }
}
~~~

**Notes on ordering and registration:**

- `AsyncTraceFilter` is instantiated with `new` **inside the security chain**, not as a `@Bean`/`@Component`. Therefore Spring Boot does not auto-register it as a **second Servlet filter**.
- `addFilterBefore(..., AuthorizationFilter.class)` fixes the custom filter's position relative to a known security filter. Preceding filters can still reject/short-circuit requests; never treat whether the custom filter logged as the sole proof that SecurityFilterChain ran.
- `httpBasic()` authenticates username/password for the exercise. Production apps should use an IdP/password encoder and transport matching the threat model; HTTP Basic must run over HTTPS.
- All other endpoints hit `denyAll()`, avoiding accidentally leaving side paths without rules.
- `STATELESS` does not mean "every thread automatically gets SecurityContext". It describes the chain's session/security context policy; async context still needs dedicated handling.
- The example only has a GET endpoint so CSRF is not disabled. If adding POST/PUT/DELETE, evaluate CSRF whenever browser clients use cookies/Basic credentials.
- Spring Security has its own filters with distinct async/error policies. **Never conclude** that because a custom filter has `shouldNotFilterAsyncDispatch(false)`, all authentication or authorization checks always re-run the exact same number of times.

In the demo, `{noop}demo-pass` keeps password entry simple for the exercise. **Never use `{noop}` and hardcoded passwords in production**; replace with a proper encoder, vault/IdP, and HTTPS.

### 7.6. Controller: Callable Running on a Worker Thread

**`src/main/java/com/example/asyncfilter/AsyncController.java`:**

~~~java
package com.example.asyncfilter;

import java.security.Principal;
import java.util.Map;
import java.util.concurrent.Callable;

import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class AsyncController {

    @GetMapping("/api/async")
    public Callable<Map<String, String>> async(Principal principal) {

        // Read principal on the initial REQUEST thread.
        String requestUser = principal.getName();

        // Spring MVC executes the Callable via the async executor.
        return () -> {
            Authentication current = SecurityContextHolder
                .getContext().getAuthentication();

            // With standard Spring Security MVC integration,
            // the Callable's context is transferred appropriately.
            String workerUser = current == null
                ? "missing" : current.getName();

            return Map.of(
                "requestUser", requestUser,
                "workerUser", workerUser,
                "result", "done");
        };
    }
}
~~~

This controller does not call `startAsync()` directly because Spring MVC manages async handling when returning `Callable`. Do not use `Thread.sleep` to prove async behavior: Spring MVC already selects the async processing path from the return type.

`workerUser` verifies `SecurityContext` is present inside the **Callable** via Spring Security MVC integration. This **does not say** MDC from the initial filter was also propagated to the worker. If MDC is needed inside Callable, add appropriate context propagation/tracing.

A typical JSON response with valid Basic credentials:

~~~json
{
  "requestUser": "alice",
  "workerUser": "alice",
  "result": "done"
}
~~~

JSON property positions may differ; tests verify values, not key order.

## 8. Testing Async Dispatch with MockMvc

Spring MVC `MockMvc` can verify **async start** and **the second dispatch** via `asyncDispatch`. Distinguish tests calling only `mvc.perform(get(...))` from tests awaiting completion and re-dispatching; stopping after the first step typically does not observe the final JSON response.

**`src/test/java/com/example/asyncfilter/AsyncFilterTest.java`:**

~~~java
package com.example.asyncfilter;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.springframework.security.test.web.servlet.request
    .SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.asyncDispatch;
import static org.springframework.test.web.servlet.request
    .MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.request;
import static org.springframework.test.web.servlet.result
    .MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class AsyncFilterTest {

    @Autowired
    MockMvc mvc;

    @Test
    void unauthenticatedRequestIsRejected() throws Exception {
        mvc.perform(get("/api/async"))
            .andExpect(status().isUnauthorized());
    }

    @Test
    void asyncDispatchReentersTraceFilterWithoutRepeatingInitialPolicy()
            throws Exception {

        MvcResult started = mvc.perform(
                get("/api/async")
                    .with(httpBasic("alice", "demo-pass")))
            .andExpect(request().asyncStarted())
            .andExpect(request().attribute(
                AsyncTraceFilter.REQUEST_VISITS, 1))
            .andReturn();

        mvc.perform(asyncDispatch(started))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.requestUser").value("alice"))
            .andExpect(jsonPath("$.workerUser").value("alice"))
            .andExpect(jsonPath("$.result").value("done"))
            .andExpect(request().attribute(
                AsyncTraceFilter.REQUEST_VISITS, 1))
            .andExpect(request().attribute(
                AsyncTraceFilter.ASYNC_VISITS, 1))
            .andExpect(request().attribute(
                AsyncTraceFilter.INITIAL_MARKER, true));
    }
}
~~~

Test meaning:

- `request().asyncStarted()` indicates Spring MVC entered async processing rather than returning a synchronous response.
- `asyncDispatch(started)` simulates the container re-dispatch after the `Callable` produces its result.
- `REQUEST_VISITS=1` and `ASYNC_VISITS=1` are expectations **of this demo config** where the security filter chain actually participates in ASYNC and the custom filter overrides its skip flag. They are not universal guarantees across every container/proxy/custom registration.
- `INITIAL_MARKER=true` confirms the initial-only marker stayed intact and was not cleared/repeated on ASYNC.
- `workerUser=alice` demonstrates Spring Security MVC `Callable` context integration, **not** automatic verification of all `@Async`, `DeferredResult`, or queue tasks.

If `ASYNC_VISITS` remains empty even though the async controller succeeds, inspect the dispatcher mapping of the **MockMvc filter registration**, Spring Security filter chain, `shouldNotFilterAsyncDispatch`, and test environment. Never "fix" the test by manually forcing an ASYNC visits request attribute—that hides registration bugs.

## 9. Do Not Arbitrarily Allow ASYNC Dispatch to Bypass Authorization

Some developers see an error status during the ASYNC pass and try configuring:

~~~java
// Illustrative FRAGMENT, not a default recommendation:
authorize.requestMatchers("/api/**").authenticated();
authorize.dispatcherTypeMatchers(DispatcherType.ASYNC).permitAll();
~~~

The snippet above is **not a complete chain**; matcher order and builder usage must match your API/version. The core question is: should ASYNC dispatch receive different authorization because the initial request was already checked, or are you accidentally bypassing a policy that needs enforcement during the dispatch phase?

Things to verify:

1. Did the initial request pass required authentication/authorization?
2. Which paths can trigger asynchronous dispatch, and could the response expose data without authorization?
3. Does the security filter registration apply to `ASYNC` and is context preservation working properly?
4. Are there multiple `SecurityFilterChain`s by path/dispatcher? Does the ASYNC pass still match the intended chain?
5. Do custom filters rely on session, ThreadLocal, or request bodies valid only during initial REQUEST?

**Never add `permitAll` for all ASYNC just to make tests pass** without explaining the trust boundary. Dispatcher-type authorization rules can make sense in a specific architecture, yet you must have tests proving initial authorization, context, and endpoint responses cannot be bypassed.

### Must Authentication and Authorization Always Run Twice?

There is no single answer true for every app. Security filters have distinct policies; `FilterChainProxy` can be invoked on multiple dispatches and certain filters skip async/error. Some authorization layers may re-evaluate the path on the subsequent pass; some authentication mechanisms rely on the saved/restored context.

**Good policy:** avoid putting authorization decisions in custom logging filters; configure authorization in Spring Security, separate rules by dispatcher/path only when truly needed, and test the full `REQUEST -> worker -> ASYNC` lifecycle on your deployment version.

## 10. ERROR Dispatch and Nested Dispatches

Async tasks can throw exceptions, time out, or be cancelled. Spring MVC and the Servlet container have different error-handling/dispatch mechanics; a filter may encounter `DispatcherType.ERROR` or errors may be handled inside MVC depending on the error source.

- `OncePerRequestFilter.shouldNotFilterErrorDispatch()` defaults to `true`: custom filters normally **do not re-run `doFilterInternal`** on error dispatches.
- If overridden to `false`, ensure the filter is mapped for `ERROR` in the container, avoid side effects, and watch for **nested ERROR dispatches**.
- Some containers can perform a nested error dispatch within the chain before the previous invocation's marker is removed. `OncePerRequestFilter` has `doFilterNestedErrorDispatch` for this case; do not assume it behaves identically to an independent pass.
- The response may already be committed or an error response may already be generated by a proxy/container before Spring MVC; custom filters are not the right place to arbitrarily "reset" responses.
- Avoid logging duplicate business audit events on error dispatches; record operational failures separately via filtered logs/metrics.

For example, if a `Callable` throws an exception, the request might route to an MVC exception handler without going through a separate container error dispatch. Observe the **actual dispatcher type** rather than guessing from HTTP 500.

## 11. Differences Among DeferredResult, CompletableFuture, and @Async

| Work Style | Thread Running Business Logic | SecurityContext Propagation | ASYNC Dispatch? |
| --- | --- | --- | --- |
| Spring MVC `Callable` | Executor managed by MVC. | Spring Security MVC integration supports Callable. | Usually yes upon completion. |
| Spring MVC `DeferredResult` | App decides which thread/callback completes the result. | Do not assume context propagates to the producer thread; use proper wrappers. | Usually yes when result is set. |
| Controller returning `CompletableFuture` | Executor/callback depends on how the future is created. | Not automatically propagated by OncePerRequestFilter. | MVC may use async processing depending on return value handler. |
| `@Async` on a service | Spring's TaskExecutor. | Requires explicit propagation design if task needs caller context. | Not automatically a Servlet dispatch if outside request lifecycle. |
| Queue consumer/scheduled task | Independent worker. | No end-user security context by default. | No HTTP Servlet dispatch unless results attach to a request via dedicated mechanisms. |

Never use `InheritableThreadLocal` as a universal fix for thread pools; it can carry stale context to subsequent tasks. Never keep `HttpServletRequest` for use long after the request finishes: lifecycle/attributes are not guaranteed for long-running background jobs. Pass immutable actor IDs or correlation IDs, propagating security context only with clear semantics and exact cleanup.

### Illustrative DeferredResult (Fragment)

~~~java
@GetMapping("/api/deferred")
public DeferredResult<String> deferred(Principal principal) {
    DeferredResult<String> result = new DeferredResult<>();

    String stableUser = principal.getName();
    trustedExecutor.execute(() -> {
        // The request's SecurityContextHolder is not automatically present here.
        result.setResult("hello " + stableUser);
    });

    return result;
}
~~~

The fragment requires an injected `trustedExecutor`, `DeferredResult`/`Principal` imports, and proper timeout/error handling. It **deliberately captures** an authenticated string before switching threads, avoiding `SecurityContextHolder` inside the task. For operations requiring fresh permissions, the service must still check the appropriate policy.

## 12. Diagnosing Common Async/Filter Bugs

| Symptom | Causes to Check | Resolution |
| --- | --- | --- |
| Filter runs twice for one HTTP request | Both REQUEST and ASYNC dispatches occurred; or double registration. | Log dispatcher type and filter identity; compare security chain vs servlet registrations. |
| `shouldNotFilterAsyncDispatch(false)` yet ASYNC never triggers | Filter registration lacks `DispatcherType.ASYNC`, security proxy unmapped for ASYNC, or no real async dispatch. | Check dispatcher mapping, `asyncDispatch`, and filter selection. |
| Audit event written twice | Side-effect logic sits in a filter running on both REQUEST and ASYNC. | Move side effects to service/outbox; if request-start only, guard on REQUEST. |
| MDC trace vanishes during response completion | MDC was only set on the REQUEST thread. | Re-establish MDC on ASYNC dispatch; clear/restore in finally. |
| MDC vanishes inside `Callable.call()` | Worker thread does not run Servlet filters. | Use TaskDecorator/wrapped executor; do not confuse with SecurityContext propagation. |
| SecurityContext missing in custom executor | ThreadLocal does not cross threads automatically. | Use `DelegatingSecurityContextExecutor` or explicit actor propagation with cleanup. |
| `Callable` runs yet MockMvc HTTP response is unfinished | `asyncDispatch(result)` was not called. | Write two-step test; verify `asyncStarted` and final response. |
| Starting async throws IllegalStateException | A filter/servlet registration lacks async support. | Check `asyncSupported` on registrations and container. |
| Custom filter runs inconsistently | Different SecurityChain matchers, filter ordering, or short-circuits. | Check request matchers, dispatches, order, and registrations. |
| ASYNC dispatch returns 403/401 differently from REQUEST | SecurityContext/registration/authorization rules differ across dispatches. | Test true lifecycle and verify config instead of enabling blanket permitAll. |
| ERROR creates unexpected extra logs/audits | Filter is mapped for ERROR and does not skip. | Design `shouldNotFilterErrorDispatch`/nested error policy. |
| Filter is `@Component` and `addFilterBefore` | Double registration or unexpected order. | Register in one place only; disable Servlet registration if using a bean. |
| Request ID differs between REQUEST and ASYNC | Generating a new ID per thread/dispatch. | Store one stable ID in request attributes/trusted gateway context. |
| Wrong user info across concurrent async tasks | Context leaked in ThreadLocal/thread pool. | Wrapper cleanup; avoid static contexts or ad-hoc inheritable thread locals. |
| POST processed twice despite REQUEST-only filter | Client/gateway retry or message redelivery. | Idempotency keys, unique constraints, transactions/outbox. |

### Ordered Debugging Checklist

1. Grab a sanitized request ID to correlate logs across REQUEST, worker, and ASYNC.
2. Log dispatcher type (`request.getDispatcherType()`), filter name, and thread name in test environments—never log tokens/cookies.
3. Confirm the controller returns `Callable`/`DeferredResult` and the request truly goes async.
4. Inspect Servlet registrations for REQUEST/ASYNC/ERROR; for Spring Security, inspect `DelegatingFilterProxy` and `FilterChainProxy`.
5. Check `shouldNotFilterAsyncDispatch`/`shouldNotFilterErrorDispatch` of every **involved** filter, not only your custom filter.
6. Check whether the filter is registered in two places.
7. Verify `SecurityContext` in the worker thread and the Servlet async dispatch **separately**.
8. For side effects, classify whether they belong to "request once", "dispatch each", or "business exactly-once", then place them at the right layer.
9. Write two-phase MockMvc tests plus real Servlet container integration tests when issues depend on registration.
10. Never change authorization to `permitAll` or disable CSRF just to mask async bugs.

## 13. Self-Check Questions

1. **Does an ASYNC dispatch mean a new HTTP request from the client?** No. It is normally the container continuing processing of the same request after async work finishes.
2. **Can `OncePerRequestFilter` invoke `doFilterInternal` twice during one logical HTTP request?** Yes, when the filter participates in both REQUEST and ASYNC dispatches and configuration does not skip ASYNC.
3. **What is the default of `shouldNotFilterAsyncDispatch()`?** `true`: skip ASYNC dispatch.
4. **If overridden to return `false`, is the filter guaranteed to run on ASYNC?** Not yet. Servlet/security proxy registrations must map that dispatcher type and the filter must belong to the invoked chain.
5. **Does the "already filtered" marker guarantee exactly-once payment processing?** No. The marker is transient per-request state and does not prevent retries, partitions, or other workers.
6. **How do you avoid logging an initial-only audit event twice?** Run it on REQUEST dispatch and skip on ASYNC; for critical business actions, use durable idempotency/outbox.
7. **Does MDC on the initial Servlet thread automatically enter a Callable worker?** Do not assume so; dedicated observability context propagation is required.
8. **How does Spring Security handle a Callable's `SecurityContext`?** It integrates with Spring MVC `Callable` via components like WebAsyncManagerIntegrationFilter; do not generalize that to arbitrary executors/DeferredResult.
9. **Does an `@Async` service create an ASYNC Servlet dispatch?** Not by itself. `@Async` is a task-execution mechanism; Servlet async dispatch depends on the request/return-value lifecycle.
10. **Why avoid `@Component` combined with `addFilterBefore`?** It can create two registrations with different ordering/dispatcher types, causing duplicate runs or unpredictable behavior.
11. **Is ERROR dispatch identical to ASYNC dispatch?** No. ERROR has its own purpose and `shouldNotFilterErrorDispatch` hook, and can be nested.
12. **Why must `DispatcherType.ASYNC permitAll` be scrutinized carefully?** It can alter the authorization policy of the response-completion phase; you must prove the initial request is protected and no bypass is introduced.
13. **If a filter needs MDC on both REQUEST and ASYNC, what should you do?** Enable ASYNC handling for the filter/registration, set MDC on each dispatch, and restore/clear in `finally`.
14. **When do you need an idempotency key instead of a request attribute?** When business requirements must prevent duplicates across HTTP requests, retries, or distributed processing.
15. **In MockMvc, why must you call `asyncDispatch(MvcResult)`?** To simulate the container re-dispatch and inspect the final response along with filters running on ASYNC.
16. **If a `Callable` reads Authentication properly yet a `CompletableFuture` sees no SecurityContext, is that a contradiction?** No; different async models have different context propagation mechanisms.

## 14. Practice Exercises with Guided Solutions

**Exercise 1 — Run only on initial REQUEST:** Create `InitialRequestFilter extends OncePerRequestFilter` keeping the default async/error hooks. Inside `doFilterInternal`, record a marker; verify with `MockMvc asyncDispatch` that the marker remains on the request and the filter does not run again. **Guidance:** distinguish the custom marker created by your filter from the internal "already filtered" marker removed in `finally`.

**Exercise 2 — Attach correlation ID on every Servlet dispatch:** Apply `AsyncTraceFilter` from section 7. Observe `REQUEST_VISITS` and `ASYNC_VISITS` across the two test steps. **Guidance:** generate a new trace ID only when the request attribute is absent; MDC must be set and restored in `try/finally` on each dispatch.

**Exercise 3 — Deliberately provoke a bug:** Put an unguarded `auditRepository.save(...)` inside `doFilterInternal` with the async hook returning `false`. **Guidance:** observe that it can run again on ASYNC; fix with a REQUEST-only policy for request-start auditing, or move critical business logic into an idempotent service/outbox.

**Exercise 4 — DeferredResult:** Build a `DeferredResult` completed from a custom executor and inspect `SecurityContextHolder`. **Guidance:** do not extrapolate from Callable results; use the right wrapper/decorator or pass a verified actor ID.

**Exercise 5 — Double registration:** Annotate `AsyncTraceFilter` with `@Component` while still adding `addFilterBefore`, then inspect registrations/logs. **Guidance:** remove one registration rather than hiding the bug by incrementing markers or tweaking filter order arbitrarily.

**Exercise 6 — Security testing:** Verify unauthenticated `GET /api/async` returns 401 while authenticated requests run the `Callable` and return final 200; experiment with changing dispatcher registrations to observe effects. **Guidance:** never use `permitAll` on ASYNC as an automatic fix; inspect lifecycle and context.

**Remember:** `OncePerRequestFilter` prevents duplicate execution **within the dispatch scope it controls**, while Servlet async can create a **new ASYNC dispatch** on a different thread. Never equate *one HTTP request* with *one filter invocation*, *one thread*, or *one business operation*. Configure dispatcher mappings accurately, decide ASYNC/ERROR hooks explicitly per filter, propagate `SecurityContext` and MDC with the right mechanisms, and protect business operations with true idempotency whenever needed.
