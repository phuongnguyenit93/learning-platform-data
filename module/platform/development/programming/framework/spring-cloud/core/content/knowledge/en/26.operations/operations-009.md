# Limiting Load from Discovery, Health Checks, and Configuration Refresh

> **Chapter:** Operations  
> **Module:** SPRING_CLOUD_CORE

In a Spring Cloud system, service discovery, health checks, and configuration refresh help applications adapt to changes in a distributed system. However, these mechanisms themselves generate extra traffic toward registries, instances, and downstream dependencies. As replica counts grow, check intervals shrink, or configuration changes broadcast simultaneously, background work can escalate rapidly and overload the system right during an incident.

This lesson focuses on **limiting load generated by discovery, health checks, and refresh**. We will look at reducing registry queries, caching in the right place, designing lightweight probes, avoiding cascading restarts, batching refreshes, and monitoring operational signals. Examples fall within Spring Cloud Commons, Spring Cloud LoadBalancer, Spring Cloud Context, and Spring Boot Actuator in the **SPRING_CLOUD_CORE** module.

## 1. Viewing Operational Load as Part of System Load

A single business request can entail several auxiliary activities:

- Clients need an instance list to pick a target.
- Discovery health indicators query the registry to check discovery health.
- LoadBalancer health-check suppliers probe each instance on a schedule.
- Kubernetes or orchestration platforms call liveness/readiness probes.
- A configuration change triggers rebinding or bean re-instantiation.
- Spring Cloud Bus distributes refresh events across many replicas.

If each activity runs on only one instance, the cost may be small. When multiplied by replica count, service count, target instance count, and frequency, background operations can accumulate into substantial load.

### 1.1. Three Primary Load Sources

| Source | Work Generated | Consequence When Frequency or Scope Is Too High |
| --- | --- | --- |
| Discovery | Querying service/instance lists, updating registry, refreshing caches | Registry burns CPU/network; clients pull huge lists or stale data |
| Health checks | Platform probes, health indicators, LoadBalancer checking each instance | Background traffic rises, dependencies get polled repeatedly, multiple instances marked unhealthy together |
| Configuration refresh | Rebinding `ConfigurationProperties`, clearing `RefreshScope` caches, recreating clients/pools, publishing Bus events | Bursty initialization load, connection spikes to databases/APIs, broker backlogs |

### 1.2. Relationship Diagram

~~~mermaid
flowchart TB
    A["Multiple application replicas"]
    A --> B["DiscoveryClient / LoadBalancer"]
    A --> C["Health indicators and probes"]
    A --> D["Configuration refresh"]
    B --> E["Service registry"]
    C --> E
    C --> F["Service instances"]
    D --> G["Config source / Spring Cloud Bus"]
    D --> H["Bean and connection pool re-initialization"]
    E --> I["Control-plane load"]
    F --> J["Background request load"]
    G --> K["Event and broker load"]
    H --> L["Dependency initialization load"]
~~~

Crucially, never treat requests to health endpoints or the registry as free. They consume threads, connections, CPU, and network bandwidth just like business requests.

## 2. Quantifying Load Before Changing Configuration

Simple calculations help identify configurations capable of causing bursts.

### 2.1. Health Probe Frequency

If there are `N` replicas and each replica is probed every `T` seconds, the approximate probe rate is:

`Q_probe ≈ N / T`

For example, 60 replicas probed every 10 seconds produce roughly 6 requests/second to the probe endpoint. That is merely traffic to the application endpoint; if the endpoint calls discovery, a database, and several APIs, downstream load scales accordingly.

### 2.2. Per-Service-Instance Health Checks

With a group of independent clients, if each client checks `M` instances every `T` seconds, the estimated check rate is:

`Q_instance-check ≈ N_clients × M / T`

For example, 20 clients checking 10 instances every 30 seconds create roughly 6.7 checks/second. This is a planning estimate; actual counts depend on suppliers, caching, number of service IDs, and scheduler implementation.

### 2.3. Load from Simultaneous Refresh

If `R` replicas refresh at once and each replica must recreate `B` expensive beans, total initializations in one wave can reach:

`W_refresh ≈ R × B`

If those beans create HTTP connection pools, database pools, TLS contexts, or broker subscriptions, a refresh wave can cause a connection burst. Splitting refreshes into small batches reduces concurrent initializations.

These formulas do not replace benchmarking. Use them for initial sizing, then measure real traffic in a production-like environment.

## 3. Limiting Discovery Queries

Spring Cloud Commons provides the `DiscoveryClient` abstraction to fetch service and instance lists. Actual cost depends on the provider, how the provider caches data, the number of registered services, and the number of clients querying discovery.

### 3.1. Avoid Calling getServices Too Frequently

`DiscoveryClientHealthIndicator` can call `DiscoveryClient.getServices()` by default to check discovery. In systems with many services, this operation may retrieve and assemble a large list on every health check.

Switch to a lighter probe:

~~~yaml
spring:
  cloud:
    discovery:
      client:
        health-indicator:
          enabled: true
          use-services-query: false
~~~

When `use-services-query` is `false`, the health indicator uses `DiscoveryClient.probe()` instead of querying the entire service catalog. This is helpful when you only need to confirm the discovery client is functional without downloading every service name on each probe.

If the health indicator does not provide actionable operational signals, disable it:

~~~yaml
spring:
  cloud:
    discovery:
      client:
        health-indicator:
          enabled: false
~~~

Disable it only after confirming other signals detect registry failures. Never remove a health indicator merely to make a dashboard look greener.

### 3.2. Avoid Duplicate Discovery Checks

Spring Cloud Commons can aggregate multiple `DiscoveryHealthIndicator` beans through `DiscoveryCompositeHealthContributor`. Providers may also supply their own health indicators. If several indicators query the same registry or call the same API, a single health aggregation can trigger redundant requests.

Review:

- `DiscoveryClientHealthIndicator`.
- `DiscoveryCompositeHealthContributor`.
- Health indicators provided by Eureka, Consul, or other providers.
- Application custom health indicators.
- LoadBalancer health checks and platform probes.

Keep only checks answering distinct operational questions. To disable the composite indicator if needed:

~~~yaml
spring:
  cloud:
    discovery:
      client:
        composite-indicator:
          enabled: false
~~~

This is an application health design choice, not a mandatory default for every system.

### 3.3. LoadBalancer Instance List Caching

Spring Cloud LoadBalancer caches instance lists. Without Caffeine on the classpath, the starter uses a default cache; when Caffeine is present, the Caffeine implementation is used.

Illustrative configuration:

~~~yaml
spring:
  cloud:
    loadbalancer:
      cache:
        enabled: true
        ttl: 35s
        capacity: 256
~~~

In current Spring Cloud configuration, the default LoadBalancer cache TTL is 35 seconds and initial capacity is 256. Appropriate values depend on instance churn rate, number of service IDs, and list freshness requirements.

Caching reduces repeated discovery queries, at the trade-off that clients may continue seeing stale instance lists until the cache expires or refreshes. Balance carefully:

- Longer TTL: fewer registry queries, slower visibility into instance changes.
- Shorter TTL: faster updates, higher list-fetch frequency.
- Capacity too low: cache thrashes with constant evictions when calling many service IDs.
- Capacity too high: wastes memory for little gain when actual service ID count is small.

If a discovery provider like Eureka already caches instance lists, consider disabling LoadBalancer caching to avoid double caching:

~~~yaml
spring:
  cloud:
    loadbalancer:
      cache:
        enabled: false
~~~

Do not blindly stack two caching layers. Decide which layer owns freshness, TTL, and invalidation.

### 3.4. Do Not Overlap Cache and Health-Check Suppliers

`HealthCheckServiceInstanceListSupplier` has its own cache based on Reactor Flux replay. When using this supplier, do not automatically wrap it inside `CachingServiceInstanceListSupplier` without understanding ordering and cache behavior.

In custom configurations, supplier ordering also matters: network-fetching instance suppliers belong before cache/health-check suppliers, and request-filtering suppliers belong after the appropriate instance-fetching/updating layer.

Verify custom supplier setups against your active Spring Cloud version. Do not chain multiple suppliers merely because each offers a useful feature.

## 4. Using LoadBalancer Health Checks in the Right Scenarios

Spring Cloud LoadBalancer provides `HealthCheckServiceInstanceListSupplier` to periodically check instances returned by a delegate supplier. It filters and returns healthy instances; if no instances are healthy, it can fall back to returning the retrieved list to avoid leaving the list completely empty.

This means the health-check supplier is not a strict fail-closed mechanism: when every instance fails checks, the original list may still be returned. Pair it with timeouts, retries/circuit breakers, and accurate registry status; never rely on this supplier alone to guarantee requests never reach unhealthy instances.

### 4.1. When Should It Be Used?

The health-check supplier is especially useful with `SimpleDiscoveryClient` using statically configured instance lists, or when a provider lacks sufficiently trustworthy health status.

With real registries like Eureka/Consul, service discovery usually already provides instance health via its own mechanisms. Adding scheduled health checks from every client in that case creates duplicate traffic without adding much selection quality.

Before enabling, answer:

1. Does the registry already return instance health status?
2. Is that status fresh enough for routing requirements?
3. Do instances expose a lightweight, stable health endpoint?
4. How many clients and target instances exist?
5. Must every client probe the same instances individually, or can they trust the registry?

### 4.2. Tuning Intervals and Paths

If scheduled health checks are genuinely needed, configure appropriate intervals and endpoints:

~~~yaml
spring:
  cloud:
    loadbalancer:
      configurations: health-check
      health-check:
        initial-delay: 10s
        interval: 45s
        path:
          default: /actuator/health
~~~

`initial-delay` prevents launching all probes the instant applications boot. `interval` controls time between cycles. The default path is `/actuator/health` unless configured otherwise; you can configure paths per service ID when services have custom health endpoints.

A health endpoint polled by LoadBalancer must:

- Respond quickly with a reasonable timeout.
- Not query the entire service registry.
- Not invoke long downstream chains merely to report instance state.
- Cause no transactions or side effects.
- Have clear semantics: liveness, readiness, or a routing-focused check.

Never use a heavy health endpoint as a per-instance probe called by many clients.

### 4.3. Refetching Instance Lists and Repeating Health Checks

When a delegate does not emit updated instance lists even after registry changes, you can instruct the health-check supplier to refetch:

~~~yaml
spring:
  cloud:
    loadbalancer:
      health-check:
        refetch-instances: true
        refetch-instances-interval: 45s
        repeat-health-check: false
~~~

`refetch-instances` defaults to `false`. When refetch is enabled, each new instance list fetch can also trigger health checks. Therefore, `repeat-health-check: false` avoids running an unnecessary redundant health-check cycle when refetch already triggers checks.

Do not enable refetch just to force faster registry updates when the delegate already emits updated lists on its own. First measure delegate freshness and identify where caching resides.

### 4.4. Avoid Unnecessary Dual Caching Layers

When using `HealthCheckServiceInstanceListSupplier`, it maintains its own cache. Running `CachingServiceInstanceListSupplier` concurrently can increase staleness delay or make freshness harder to diagnose.

Spring Cloud recommends placing the health-check supplier directly after the network-fetching supplier and before other filtering suppliers. When writing custom configurations, preserve this order and pick a single appropriate cache/health-check mechanism.

## 5. Designing Health Checks Without Cascading Failures

Health checks signal to orchestrators and clients whether an application can serve traffic. If a health check is overly sensitive or depends on too many external systems, a localized issue can turn into a restart storm.

### 5.1. Separating Liveness and Readiness

- **Liveness** answers whether the process is alive and able to continue running.
- **Readiness** answers whether the instance should receive new traffic right now.
- **Startup probe** gives the application sufficient startup time before liveness is enforced.

Do not include database, discovery server, or external API health checks in liveness. If an external dependency fails temporarily, Kubernetes could restart all Pods; mass restarts surge load onto the very dependency already failing.

Readiness may include select external dependencies if business logic genuinely cannot serve when those dependencies fail. Choose carefully: if every replica switches to `NOT_READY` when a shared dependency blips, the entire service can drop out of traffic and struggle to recover.

### 5.2. Do Not Include Every Health Indicator in Readiness

Spring Boot creates liveness and readiness health groups by default in Kubernetes environments. Other health indicators are not added to the readiness group automatically.

To add a specific indicator, declare it explicitly:

~~~yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include:
            - readinessState
            - catalogDependency
~~~

Add `catalogDependency` only if it is genuinely required to accept new requests. Never wildcard-include all indicators into readiness.

### 5.3. Tuning Probe Intervals and Thresholds

Example Kubernetes configuration:

~~~yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
~~~

These values are examples only. Base them on startup time, health contributor execution time, application timeouts, and recovery behavior. If probes run too frequently, background traffic grows; if thresholds are too low, a brief CPU spike can unnecessarily pull or restart Pods.

For slow-starting applications, use a startup probe so liveness does not kick in prematurely. Ensure probes target the main server port when verifying the primary web server can accept requests; a separate management port can stay healthy while the serving port fails.

## 6. Refreshing Configuration Without Causing a Refresh Storm

Spring Cloud Context supports updating the `Environment`, rebinding `@ConfigurationProperties`, and refreshing `@RefreshScope` beans. While useful, if every replica refreshes simultaneously, they may concurrently recreate HTTP clients, connection pools, caches, or subscriptions.

### 6.1. Understanding the Cost of Each Refresh Mode

When an `EnvironmentChangeEvent` occurs, Spring Cloud can:

- Rebind `@ConfigurationProperties` beans.
- Update logger levels if corresponding properties changed.
- Refresh beans in `RefreshScope` when an appropriate context refresh runs.

Rebinding `@ConfigurationProperties` usually updates fields on existing beans. Concurrent readers may observe an intermediate state between resetting and applying new values.

`@RefreshScope` uses lazy proxies and caches target beans. On refresh, the cache clears; the next invocation recreates the target bean. This fits beans needing a consistent view across refreshes, though recreating targets still carries initialization cost.

### 6.2. Scope Only Necessary Beans with RefreshScope

Do not annotate every bean in the application with `@RefreshScope`. Select only beans that truly must be recreated when configuration changes, such as clients holding endpoints or credentials that may change.

Example:

~~~java
import org.springframework.cloud.context.config.annotation.RefreshScope;
import org.springframework.stereotype.Component;

@Component
@RefreshScope
public class CatalogRemoteClient {

    private final CatalogClientProperties properties;

    public CatalogRemoteClient(CatalogClientProperties properties) {
        this.properties = properties;
    }

    public String currentBaseUrl() {
        return properties.getBaseUrl();
    }
}
~~~

This example illustrates bean lifecycle; in real applications, a client may own connection pools or transports that must be closed properly when the old target is replaced.

Notes:

- Placing `@RefreshScope` on a `@Configuration` class does not automatically put every bean declared in that class into refresh scope.
- Beans using constructor binding, including `@ConfigurationProperties` Java records, cannot refresh through this mechanism.
- `HikariDataSource` is in Spring Cloud's default non-refreshable list; do not assume its connection pool can be safely recreated via refresh.
- If a bean needs read consistency across refreshes, prefer refresh scope over directly rebinding mutable fields.
- Context refresh is not supported for Spring AOT transformations and native images; verify version-specific properties.

### 6.3. Do Not Refresh Merely on a Polling Loop

Spring Cloud Config Client does not poll the `Environment` by default. Spring Cloud documentation advises against frequent polling to detect changes in scaled-out applications. When updating many instances, use Spring Cloud Bus to broadcast change events instead of having every replica continuously poll Config Server.

Polling every few seconds across hundreds of replicas increases Config Server load and can trigger simultaneous refreshes when multiple clients observe a change together.

If polling is required for specific reasons, add jitter, backoff, caching, concurrency limits, and trigger refresh only when the configuration fingerprint actually changes. Never trigger repeated refreshes when values are unchanged.

In deployment pipelines, coalesce multiple property edits into a single refresh once the configuration release is finalized. Use locking or a queue so only one refresh runs per service/environment at a time; enforce a cooldown between waves and deduplicate events with identical fingerprints. This prevents rapid consecutive commits or operator actions from triggering back-to-back bean re-initializations.

## 7. Splitting Refreshes with Spring Cloud Bus

Spring Cloud Bus distributes refresh events via a broker to application instances. `/actuator/busrefresh` clears `RefreshScope` caches and rebinds `@ConfigurationProperties` on receiving instances.

### 7.1. Broadcasting Can Cause Bursts

Sending a refresh event to an entire running service causes every receiving instance to start rebinding or recreating beans almost simultaneously. When every instance reopens pools or connections to the same dependency, load can spike sharply.

A large refresh must account for:

- Service replica count.
- Number of refresh-scoped beans.
- Number of connection pools or HTTP clients recreated.
- Connection limits on databases/APIs/brokers.
- Initialization and readiness time per replica.
- Throughput and backlog capacity of the Bus broker.

### 7.2. Targeting a Single Instance or Group

Spring Cloud Bus allows specifying a destination in the path. Example targeting one instance:

~~~bash
curl -X POST   http://localhost:8080/actuator/busrefresh/catalog-service:8081
~~~

Or targeting all instances of a service:

~~~bash
curl -X POST   http://localhost:8080/actuator/busrefresh/catalog-service:**
~~~

Destinations match against the Bus service ID. Ensure each instance has a unique ID; default IDs are constructed from application name and appropriate instance/port metadata. Configure `spring.cloud.bus.id` when explicit identity control is needed.

Targeting a single instance allows a canary refresh first. After verifying success, proceed in small batches before refreshing the rest. Unless simultaneous change is required, avoid broadcasting across all replicas at once.

### 7.3. Batched Refresh Workflow

A safe workflow:

1. Identify changed properties and the affected services/instances.
2. Confirm which beans will rebind or refresh.
3. Target one canary instance.
4. Check `/actuator/health`, `/actuator/configprops`, and dependency metrics.
5. Wait for the instance to stabilize and pools to normalize.
6. Refresh the next small batch.
7. Watch broker lag, initialization errors, and connection counts.
8. Halt batching if error rates or dependency load cross thresholds.
9. Continue until the entire fleet runs the new configuration.
10. Verify configuration version/fingerprint across all replicas.

With 100 replicas, you might start with one canary, then batches of 5–10 replicas, tuning to dependency capacity. This is an example strategy, not a Spring Cloud default.

### 7.4. Refresh Does Not Replace Rollouts

Some changes do not fit runtime refresh: bean structure changes, library upgrades, non-rebindable config types, or connection/resource changes needing full context recreation.

When changes significantly impact lifecycle or compatibility, use a rolling deployment with appropriate surge/unavailable limits. Never force-refresh configuration the application cannot safely recreate.

## 8. Reference Operational Configuration Set

The following example shows reducing discovery queries while retaining LoadBalancer caching:

~~~yaml
spring:
  cloud:
    discovery:
      client:
        health-indicator:
          enabled: true
          use-services-query: false
    loadbalancer:
      cache:
        enabled: true
        ttl: 35s
        capacity: 256

management:
  endpoints:
    web:
      exposure:
        include:
          - health
          - refresh
          - busrefresh
          - configprops
~~~

`refresh` and `busrefresh` alter runtime state and trigger bean re-initialization. Expose them only on management networks, require operator authentication/authorization, audit every invocation, and never expose them publicly.

If the application uses a real registry that already supplies instance status, do not enable an extra scheduled health-check supplier without good reason. If using `SimpleDiscoveryClient` and needing per-instance checks, configure health checks separately:

~~~yaml
spring:
  cloud:
    loadbalancer:
      configurations: health-check
      health-check:
        initial-delay: 10s
        interval: 45s
        path:
          default: /actuator/health
~~~

These are two configuration patterns tailored to different needs. Enabling both is not necessary. Inspect your provider's caching and health suppliers before adding probe schedules.

## 9. Observing Whether Load Limiting Is Effective

You cannot judge solely from endpoints returning UP. Monitor control-plane load and its impact on dependencies.

### 9.1. Discovery and LoadBalancer

Monitor:

- `DiscoveryClient` call counts, latency, and error rates.
- Number of services/instances returned per query.
- Cache hit/miss ratios if metrics are exposed by the implementation.
- Delay from instance registration/deregistration until clients see the change.
- Number of requests where LoadBalancer fails to pick an instance.

Spring Cloud LoadBalancer can enable Micrometer statistics:

~~~yaml
spring:
  cloud:
    loadbalancer:
      stats:
        micrometer:
          enabled: true
~~~

When a suitable `MeterRegistry` is present, LoadBalancer records `loadbalancer.requests.active`, `loadbalancer.requests.success`, `loadbalancer.requests.failed`, and `loadbalancer.requests.discard`. These meters help pinpoint instance selection errors, failed requests, and load per service instance. Verify exact metric/tag names against your version and observability backend.

### 9.2. Health Checks

Monitor:

- Request rate to liveness/readiness endpoints.
- Health endpoint processing latency.
- Rate at which health contributors call the registry or downstream services.
- Timeouts, probe failures, and Pod restart counts.
- Instances evicted from LoadBalancer lists.
- Divergence between application health and external dependency health.

If the health endpoint spikes in latency when the database slows down, check whether an indicator performs synchronous queries or waits on overly long timeouts.

### 9.3. Configuration Refresh

Monitor:

- Refresh event counts by service and instance.
- Refresh/rebind processing duration.
- Beans recreated and initialization errors.
- Database/HTTP connection counts before, during, and after refresh.
- Broker queue depth/consumer lag when using Bus.
- Time from event emission until all instances converge on the new configuration.
- `RefreshScopeHealthIndicator` if enabled.

Never create metric tags containing raw property values, tokens, user IDs, or high-cardinality random IDs. Use service name, environment, result, and bounded labels.

## 10. Load Testing Background Mechanisms

Test these three load categories separately rather than running only a business-request benchmark.

### 10.1. Discovery Load Test

Create a scenario with production-like replica counts and service IDs. Measure:

- Registry requests per second.
- `getServices`/`getInstances` latency.
- Registry CPU and memory.
- Difference with caching enabled vs. disabled.
- Visibility lag for newly added or removed instances.

Test both scale-out and scale-in to see whether cache TTLs delay instance list updates beyond acceptable limits.

### 10.2. Health-Check Load Test

Gradually increase client and instance counts. Confirm health-check intervals produce the expected traffic, health endpoints maintain stable latency, and health indicators do not repeatedly query the same dependency.

Simulate slow or failing dependencies to test whether probes trigger retry/restart storms. Never test solely when all dependencies are healthy.

### 10.3. Refresh Burst Test

Refresh a group of replicas simultaneously and observe:

- New connections opened to databases or APIs.
- Bean and pool initialization duration.
- Errors during refresh.
- Whether readiness drops while target beans recreate.
- Whether the broker builds a backlog when many refresh events fire.

Then compare full broadcast against batched refresh. Choose batch sizes based on real load and recovery capacity rather than replica count alone.

## 11. Common Operational Troubleshooting

| Symptom | Possible Cause | Remediation |
| --- | --- | --- |
| Registry CPU spikes on probes | Discovery health indicator calls `getServices` too often | Use lighter probe with `use-services-query=false`; review probe cadence |
| Clients frequently hit registry | LoadBalancer cache disabled or TTL too low | Measure freshness, tune TTL, and check provider cache |
| New instances appear slowly | Stacked caches or overly long TTL | Identify cache layers, drop one layer, or adjust TTL per requirements |
| Health checks generate heavy traffic | Many clients polling all instances | Enable health-check supplier only when needed; increase interval or trust registry |
| All Pods restart when DB fails | Liveness depends on database health | Decouple liveness from external dependencies; use selective readiness |
| Readiness flips DOWN fleet-wide | Shared indicator failed or timed out | Inspect shared dependency, thresholds, and readiness policy |
| DB connections spike after refresh | Many replicas recreate clients/pools simultaneously | Refresh in batches, minimize refreshable beans, and cap pools |
| Bus broker backlog grows | Refresh broadcasts too frequent or consumers slow | Reduce frequency, target by destination, and inspect consumers |
| Refresh succeeds yet value unchanged | Bean not in `RefreshScope` or property not rebound | Inspect `configprops`, lifecycle, and how bean reads config |
| Bean fails after refresh | Invalid new value or external initialization failed | Validate pre-rollout, canary first, and maintain rollback plan |
| Health endpoint is slow | Indicator calls multiple dependencies sequentially | Reduce indicators, set timeouts, and separate deep checks from frequent probes |

## 12. End-to-End Operational Workflow

When preparing to scale a service or apply wide configuration changes:

1. Measure baseline request rates to registry, health endpoints, broker, and dependencies.
2. Estimate discovery/health-check/refresh rates from replica counts and intervals.
3. Determine whether the provider already caches instance lists.
4. Pick one clear caching layer and set TTLs per freshness requirements.
5. Disable `DiscoveryClientHealthIndicator` `use-services-query` if full service lists are unnecessary.
6. Enable LoadBalancer health-check suppliers only when the registry lacks adequate health state.
7. Keep liveness free of external dependencies and choose readiness indicators deliberately.
8. Identify which beans need refresh versus stability or rolling restarts.
9. Choose canary and batch sizes for refresh; avoid fleet-wide broadcasts if dependencies have connection limits.
10. Monitor metrics, logs, broker lag, and health states after each batch.
11. Stop rollout when error rates, latency, or connection counts cross thresholds.
12. Confirm all replicas converged on the configuration and instance lists updated.

**Key takeaways:** Discovery requires intentional caching; health checks must stay lightweight without redundant polling; refreshes must be scoped tightly and rolled out in batches. Rely on health status already provided by your registry before adding client-side health checks, keep liveness independent of external dependencies, and use Spring Cloud Bus destinations to steer batched refreshes. Measure background load alongside business load to maintain stability as your **SPRING_CLOUD_CORE** system scales.
