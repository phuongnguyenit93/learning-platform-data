# Stripping Spoofed Identity Headers and Trusting Only Verified Proxies

## 1. Why Do Identity Headers Become a Vulnerability in an API Gateway?

In a microservices architecture, **Spring Cloud Gateway** serves as the entry point handling route predicates, filter chains, path/header transformations, service discovery, authentication, rate limiting, circuit breakers, retries, TLS, and request observability. The Gateway typically sits between clients and backends that are **not directly exposed to the Internet**. If a backend trusts an arbitrary header sent by a client, the Gateway's central position can be abused to **escalate privileges or impersonate users**.

Suppose an order service has flawed logic:

~~~java
// COUNTEREXAMPLE; never use for production authorization.
@GetMapping("/orders")
public Object listOrders(@RequestHeader("X-User-Id") String userId) {
    return orderService.findByOwner(userId);
}
~~~

An unauthorized client can simply send:

~~~http
GET /api/orders HTTP/1.1
Host: api.example.test
X-User-Id: administrator
X-Role: admin
X-Tenant-Id: finance
X-Forwarded-For: 10.0.0.9
~~~

If the Gateway **forwards those headers verbatim** and the backend treats them as authentication proof, the client has chosen their own identity and tenant. Similarly, if an admin route permits internal IPs and the Gateway trusts a self-declared `X-Forwarded-For`, an attacker can attempt to bypass the IP allowlist.

The topic **"Stripping Spoofed Identity Headers and Trusting Only Verified Proxies"** belongs to the **Security Hardening** chapter of the **SPRING_CLOUD_GATEWAY** module. This lesson focuses on the **trust boundary across client → edge/reverse proxy → Gateway → backend**, rather than treating adding a header via `AddRequestHeader` as an authentication mechanism.

After this lesson, you will be able to:

1. Classify **client-controlled**, **proxy metadata**, **verified identity**, and **hop-by-hop** headers.
2. Strip spoofed identity headers using `RemoveRequestHeader` or an early `WebFilter`.
3. Configure JWT authentication with Spring Security WebFlux and authorize by scope/role.
4. Generate internal headers strictly from a **verified principal/claims**, provided the backend can verify the Gateway.
5. Determine trusted sources for `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, and proxy hop counts.
6. Avoid `trustAll()`, misconfigured `trusted-proxies`, or directly trusting client-supplied IPs.
7. Execute the lab and test matrix against identity spoofing, duplicate headers, direct backend access, and IP spoofing.

> **Core rule:** *Verified identity must originate from an authentication mechanism and a controlled channel, never from any header a client can set themselves.* Even Gateway-generated internal headers **provide no security by themselves** if the backend can be called directly or another component can impersonate the Gateway.

## 2. Distinguishing Four Header Categories

| Category | Examples | Who can supply them? | Default trust level |
| --- | --- | --- | --- |
| Ordinary request headers | `Accept`, `User-Agent`, `X-Request-Id` | Client/proxy | **Untrusted** for security decisions |
| Identity/authorization assertion headers | `X-User-Id`, `X-Role`, `X-Tenant-Id`, `X-Authenticated-User` | Spoofable by client | **Do not trust** unless regenerated by edge/Gateway from a verified source |
| Forwarding/proxy metadata | `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` | Client or reverse proxy | Trust **only after** verifying proxy hops and rewrite policy |
| Hop-by-hop/transport | `Connection`, `Transfer-Encoding`, `Keep-Alive`, `TE` | Multiple HTTP layers | Never forward arbitrarily; use proper transport filters |

Key criteria:

- `Authorization: Bearer ...` is a **client-sent credential**, not a verified identity assertion. Only after checking signature/issuer/audience/expiry/scopes do you have a trusted principal.
- `Cookie: SESSION=...` is also a client-sent string; session validity, CSRF, and cookie constraints must be checked before use.
- `X-User-Id` or `X-Tenant-Id` has no built-in HTTP cryptographic signature standard. Renaming it to `X-Trusted-User` **does not** make it any more trustworthy.
- `X-Forwarded-For` is proxy-chain metadata, **not an authentication certificate**, and must not be used as a role or tenant.
- `Host`/`Forwarded: host=...`/`X-Forwarded-Host` can influence route selection and absolute URLs; validate before using them for redirects/callbacks.
- A header may appear with **multiple values**, altered casing, underscores, or comma-joining by intermediaries. Policy must account for duplicates and normalization.

### 2.1. Example of a Flawed Decision

~~~java
// Wrong: caller picks their own role via HTTP request.
String role = exchange.getRequest()
        .getHeaders().getFirst("X-Role");
if ("admin".equals(role)) {
    // Allow admin endpoint
}
~~~

Merely sending `X-Role: admin` lets the client enter the privileged branch. Even if a route predicate has `Header=X-Role,^admin$`, that is still only a **routing condition**, not authentication.

### 2.2. A Sound Decision in Principle

~~~text
Authorization: Bearer <access token>
         ↓
Spring Security Resource Server
  - verify signature or introspection
  - issuer, expiry/not-before
  - audience, application scope/role
         ↓
Authentication / SecurityContext
         ↓
Gateway forwards only permitted, verified info
         ↓
Backend verifies token or trusted channel and resource permissions
~~~

Even if a JWT carries a `tenant_id` claim, it may only be used once the **token is valid**, the claim comes from a trusted issuer, and the backend/application verifies the principal actually has access to that tenant.

## 3. Trust Boundary Diagram

~~~mermaid
flowchart LR
    U["Internet client<br/>any header can be spoofed"] --> E["Edge / Ingress<br/>HTTPS + Host allowlist<br/>strip sensitive headers"]
    E -->|"Private network / TLS"| G["Spring Cloud Gateway<br/>Security authn/authz<br/>route + scrub"]
    G -->|"mTLS / private network"| B["Backend microservice<br/>verify token / trusted identity"]
    U -. "Must not access directly" .-> G
    U -. "Must not access directly" .-> B
~~~

Three distinct responsibilities:

1. **Edge** restricts ingress paths, validates upstream proxies/CDNs (if any), normalizes Host/forwarded metadata, and strips client-supplied identity headers.
2. **Gateway** authenticates requests, selects routes, continues scrubbing/overwriting sensitive headers, and forwards only necessary data downstream to the backend.
3. **Backend** verifies tokens or trusts an **authenticated Gateway–backend channel**, then checks resource access permissions. It never relies on a header simply because its name sounds trustworthy.

### 3.1. The Dangerous Path

~~~text
Client
  X-User-Id: admin
  X-Forwarded-For: 10.0.0.8
       ↓
Public Gateway (passes through all headers)
       ↓
Backend: "X-User-Id=admin, internal IP → allowed"
       ↓
Impersonation / unauthorized access to others' data
~~~

### 3.2. The Intended Path

~~~text
Client: X-User-Id=admin, Authorization: Bearer <client-token>
       ↓
Trusted ingress removes X-User-Id
       ↓
Gateway scrubs again, Spring Security validates token
       ↓
Does not forward self-declared "admin"
       ↓
Gateway sends properly audience-scoped access token or verified metadata
over a private/mTLS channel per contract with backend
       ↓
Backend verifies and checks resource ownership
~~~

In the strongest approach, the backend **independently verifies an appropriate JWT/token**. If an internal header must be used instead of a token, you need **network ACLs/mTLS service identity, zero direct access, verification that the header originates solely from Gateway**, and ideally signing/timestamps to prevent spoofing/replay.

## 4. A Trust Boundary Cannot Be Built from a Single Setting

| Layer | Goal | How to protect |
| --- | --- | --- |
| Public DNS/Ingress | Only allowed public routes | Host allowlist, HTTPS/TLS, WAF/size limits, never expose management |
| Network Gateway | No path bypassing reverse proxy | Firewall, Kubernetes NetworkPolicy, private Service, service mesh policy |
| Forwarded-header normalization | IP/scheme/host metadata has provenance | Strip inbound untrusted values, regenerate at trusted edge |
| HTTP Gateway header policy | Never pass spoofed claims | `RemoveRequestHeader` or pre-processing `WebFilter`, then set validated claims |
| Identity authentication | Know who is calling | Spring Security JWT/opaque token/mTLS, issuer/audience/scope |
| Authorization | Know what they may do | Method/path rules + backend resource ownership |
| Gateway→backend | Only Gateway may call backend | mTLS workload identity, ACLs, private endpoints, token audience |
| Observability | Detect spoofing, policy bypass | Redacted decision logs, alerts, negative tests |

**Never pin everything on a `Header=X-Trusted-IP` predicate.** An HTTP header cannot tell you who actually sent it. Verifying origin starts with **controlled connections and proxies**.

### 4.1. Scenarios with a CDN or Multiple Proxies

~~~text
Client → CDN → WAF/Load Balancer → Ingress → Gateway → Backend
~~~

This involves **multiple hops**. If the CDN receives a client-spoofed `X-Forwarded-For` and fails to reset it, the downstream chain starts with a fake address. If Ingress only appends, a service reading the "first IP" treats the fake address as the client. Check:

- Do the CDN and WAF authenticate each other via connection/IP/certificate or private link?
- Does the first component touching untrusted clients **strip/overwrite** old headers or only append?
- Do subsequent proxies verify the IP/certificate of the preceding hop?
- Can the Gateway be reached directly outside this chain?
- Can the backend be reached via another Service/port bypassing the Gateway?

Only after answering these questions should you configure **how many trusted hops** exist and which part of the forwarded chain to read.

## 5. Sanitizing Headers at the Edge Before Gateway

The safest place to stop spoofed data is the **first proxy receiving requests from untrusted sources**. The edge must know which network paths/certs are trusted, then strip or overwrite headers that only infrastructure may emit.

### 5.1. Illustrative NGINX Pattern for a Trusted Ingress

~~~nginx
# SKETCH FOR LAB/REVIEW ONLY. ACLs, logging, DNS, and default server
# rules still need to be completed separately.
upstream gateway_private {
    server 10.20.30.20:8080;
}

server {
    listen 443 ssl;
    server_name api.example.test;

    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;

    location / {
        # Strip identity headers self-declared by public clients.
        proxy_set_header X-User-Id "";
        proxy_set_header X-Role "";
        proxy_set_header X-Tenant-Id "";
        proxy_set_header X-Authenticated-User "";
        proxy_set_header X-Verified-Subject "";
        proxy_set_header X-Verified-Tenant "";

        # Single-hop edge: instead of trusting inbound XFF chain,
        # record the peer IP NGINX directly accepted the connection from.
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header Forwarded "";

        proxy_set_header Host $host;
        proxy_pass http://gateway_private;
    }
}
~~~

In NGINX, `proxy_set_header Header-Name ""` drops the header on the upstream request; however, this example is **not yet a complete production configuration**. You also need a default server **rejecting Hosts outside the allowlist**, TLS certs/keys, timeouts, size limits, access controls, proper upstream configuration, and network blocks against direct Gateway access.

**If NGINX sits behind a CDN:** `$remote_addr` is the CDN/direct peer address, **not the end-user IP by default**. To recover the end-user IP, verify the request genuinely came from the trusted CDN (IP/CIDR/mTLS/private link), apply proper real-IP handling, scrub the XFF chain at the right boundary, and only then build metadata for Gateway. Never blindly switch to `$http_x_forwarded_for` from any arbitrary request.

### 5.2. Why Appending Without Stripping Is Usually Dangerous

Client sends:

~~~http
X-Forwarded-For: 10.0.0.8
~~~

Proxy appends `198.51.100.77` and Gateway receives:

~~~http
X-Forwarded-For: 10.0.0.8, 198.51.100.77
~~~

If an application picks the **leftmost address** without verifying the trusted proxy chain, it can mistake `10.0.0.8` for an internal client IP. The `maxTrustedIndex` mechanism discussed later bounds how many hops to read from the right; **nevertheless, direct connections to Gateway must still be blocked**—configuring an IP resolver alone is not enough.

### 5.3. Preventing Network Bypasses

A Gateway should receive public requests solely through a controlled path. Network configurations to inspect:

- **VM/bare metal:** firewall allows only edge/load balancer addresses to reach the Gateway listener; separate admin ports are never public.
- **Kubernetes:** Gateway application Service may be internal `ClusterIP`, yet **ClusterIP does not block other Pods**; add ingress NetworkPolicies, service mesh identities, and appropriate RBAC.
- **Cloud Load Balancer:** security groups/firewalls on the Gateway listener allow only approved L7 proxies.
- **Backend:** ingress rules allow only Gateway workload identities/service accounts; unauthenticated APIs must not be reachable directly via another Service/NodePort.
- **IPv4/IPv6:** verify both families; a firewall locking down only IPv4 may still expose an IPv6 listener.
- **NAT/sidecars/port-forward:** verify auxiliary paths do not bypass edge WAF/auth.

**Never treat an IP allowlist as user identity authentication.** IPs can change, and shared NATs/proxies serve many principals; tokens/mTLS identities serve a different purpose.

## 6. Stripping Spoofed Headers via Gateway Filter Configuration

Spring Cloud Gateway Server WebFlux includes `RemoveRequestHeader` and `SetRequestHeader`. Both intercept requests **before forwarding downstream** once a Gateway route matches.

### 6.1. WebFlux Gateway 5.x — Default Routes Do Not Forward Identity Headers

Example configuration when the **backend verifies the access token itself**, requiring no new identity headers from Gateway:

~~~yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          default-filters:
            - RemoveRequestHeader=X-User-Id
            - RemoveRequestHeader=X-Role
            - RemoveRequestHeader=X-Tenant-Id
            - RemoveRequestHeader=X-Authenticated-User
            - RemoveRequestHeader=X-Verified-Subject
            - RemoveRequestHeader=X-Verified-Tenant
          routes:
            - id: orders-api
              uri: http://127.0.0.1:9091
              predicates:
                - Path=/api/orders/**
~~~

Here, `default-filters` applies to **Gateway Server routes** and does not automatically strip headers on non-Gateway endpoints (such as local controllers or separate Actuator handlers). Every listed header is removed before the Netty HTTP client sends the request downstream.

**Important:** The configuration above assumes the backend has **its own authentication mechanism**. It neither generates `X-Verified-Subject` from a principal nor verifies JWTs on its own. If a backend currently relies on legacy identity headers, plan a protocol migration before deleting them to avoid breaking functionality; never leave client headers in place as a shortcut.

### 6.2. WebFlux Gateway 4.2/4.3 — Legacy Namespace

On Gateway WebFlux 4.x lines using the shorter prefix:

~~~yaml
spring:
  cloud:
    gateway:
      default-filters:
        - RemoveRequestHeader=X-User-Id
        - RemoveRequestHeader=X-Role
        - RemoveRequestHeader=X-Tenant-Id
        - RemoveRequestHeader=X-Authenticated-User
        - RemoveRequestHeader=X-Verified-Subject
        - RemoveRequestHeader=X-Verified-Tenant
      routes:
        - id: orders-api
          uri: http://127.0.0.1:9091
          predicates:
            - Path=/api/orders/**
~~~

Do not mix 4.x `spring.cloud.gateway.default-filters` with 5.x `spring.cloud.gateway.server.webflux.default-filters` assuming both take effect. Use a **Spring Boot–compatible Spring Cloud BOM** and verify actual runtime route/filter definitions. Starter artifact names also changed across Gateway generations.

### 6.3. Removing Headers on a Single Route Only

~~~yaml
filters:
  - RemoveRequestHeader=X-User-Id
  - RemoveRequestHeader=X-Role
  - RemoveRequestHeader=X-Tenant-Id
~~~

Place inside a specific route when the policy applies only to that downstream. However, identity spoofing is a **gateway-wide** concern, so in production you generally want a **deny-by-default** policy across all public routes so a newly added route never forgets the filter.

### 6.4. `RemoveRequestHeader` vs `SetRequestHeader`

| Filter | Behavior | Suitable for |
| --- | --- | --- |
| `RemoveRequestHeader=X-User-Id` | Deletes all values for that header name | Preventing any client value from reaching the backend |
| `SetRequestHeader=X-Route-Label,orders` | Overwrites instead of appending all values of the name | Static internal technical headers, never user identity |
| `AddRequestHeader=X-Route-Label,orders` | Appends a value | Only when a header is allowed to be multi-valued |

**Never configure `SetRequestHeader=X-User-Id,admin` and treat it as authentication.** A static string does not represent a principal. Passing identity requires reading from a verified context, or forwarding an appropriate token for the backend to verify.

### 6.5. Route Filters Do Not Replace Ingress Scrubbing

`RemoveRequestHeader` runs inside the Gateway route chain. If a request is handled by a **local controller**, another WebFilter, or a custom handler outside Gateway routes, that policy may not execute. Moreover, a WebFilter or Security component could inspect a header **before** the route filter deletes it.

**Layered protection:** strip at trusted edge, strip early in a `WebFilter` if protecting all WebFlux handlers, and enforce downstream header policy on Gateway routes. Combine multiple layers only after checking execution order, avoiding having a later filter accidentally strip an identity **regenerated from a valid principal**.

## 7. Early WebFilter: Stripping Headers Across All WebFlux Handlers

When Gateway Server WebFlux also hosts controllers, custom endpoints, or multiple route sources, a **WebFlux `WebFilter`** can remove spoofed headers **before routing and before filters that read identity**.

Java example:

~~~java
package demo.gateway.security;

import java.util.List;

import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.http.server.reactive.ServerHttpRequest;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebFilter;
import org.springframework.web.server.WebFilterChain;

import reactor.core.publisher.Mono;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public final class UntrustedIdentityHeadersWebFilter
        implements WebFilter {

    private static final List<String> UNTRUSTED = List.of(
            "X-User-Id",
            "X-Role",
            "X-Tenant-Id",
            "X-Authenticated-User",
            "X-Verified-Subject",
            "X-Verified-Tenant");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange,
                             WebFilterChain chain) {

        ServerHttpRequest sanitized =
                exchange.getRequest().mutate()
                        .headers(headers -> {
                            for (String name : UNTRUSTED) {
                                headers.remove(name);
                            }
                        })
                        .build();

        return chain.filter(exchange.mutate()
                .request(sanitized)
                .build());
    }
}
~~~

Explanation:

1. `@Order(Ordered.HIGHEST_PRECEDENCE)` requests early execution in the **WebFilter chain**; review ordering relative to other components, especially any custom WebFilters.
2. `ServerHttpRequest.mutate()` creates a request decorator with modified headers without mutating the original request object in place.
3. `HttpHeaders.remove(name)` matches header names case-insensitively per HTTP semantics; still test how proxies normalize underscores or duplicate names.
4. The filter leaves `Authorization` and `Cookie` untouched: Spring Security still needs to read legitimate credentials; stripping credentials from public requests without an alternative auth model would fail all APIs with 401.
5. The filter also **does not remove `Forwarded` or `X-Forwarded-*`**: they follow separate trust policies and network topologies, covered later.

**This is a scrubbing layer, not an identity-issuing layer.** If Spring Security is unconfigured, the backend still must not grant access merely because a header was stripped. If the Gateway is not Spring WebFlux (but **Server Web MVC**), this Java snippet cannot be used verbatim; you need a `jakarta.servlet.Filter`/`OncePerRequestFilter` or equivalent MVC mechanism.

### 7.1. Why Not Delete Every Header Starting with `X-`?

There is no rule that every custom header is untrusted and must be deleted. Headers like `X-Correlation-Id` or headers emitted by an internal proxy may have valid contracts. Conversely, headers without an `X-` prefix like `Forwarded` or `Authorization` are **highly sensitive**.

Maintain a **list of privilege-bearing headers** governed by a versioned security policy. If you need format control on IDs, normalize/generate them at edge/Gateway and avoid logging untrusted raw values.

## 8. JWT Authentication and Authorization with Spring Security WebFlux

Headers have been scrubbed, yet **an unauthenticated client must still be blocked** on protected APIs. Spring Security Resource Server supports JWT/opaque access tokens with WebFlux; for JWTs, verify signature, `iss` (issuer), `exp`, `nbf`, and the application's `aud` (audience) policy.

### 8.1. Dependencies and Issuer Configuration

With a compatible Spring Boot/Spring Cloud BOM and Gateway WebFlux:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>
</dependency>
~~~

Configuration example:

~~~yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.example.test/realms/platform
~~~

`idp.example.test` is strictly a **documentation placeholder**, not a real IdP. In running environments, replace it with a valid issuer offering trusted metadata/JWKs and TLS. Spring Security can validate JWTs using the issuer config, but **expected audience checks must be configured explicitly** when an application requires a specific audience; never assume a valid signature alone is enough.

### 8.2. SecurityWebFilterChain Authorizing Before Routing

~~~java
package demo.gateway.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration(proxyBeanMethods = false)
public class GatewaySecurityConfiguration {

    @Bean
    SecurityWebFilterChain security(ServerHttpSecurity http) {
        return http
                .authorizeExchange(exchanges -> exchanges
                        .pathMatchers(HttpMethod.GET, "/api/orders/**")
                        .hasAuthority("SCOPE_orders.read")
                        .pathMatchers(HttpMethod.POST, "/api/orders/**")
                        .hasAuthority("SCOPE_orders.write")
                        .anyExchange().denyAll())
                .oauth2ResourceServer(oauth2 -> oauth2
                        .jwt(Customizer.withDefaults()))
                .build();
    }
}
~~~

All undeclared APIs in this example are denied, including Actuator if routed through the same Security chain. **In production**, govern Actuator via a separate management context/port and dedicated authorization; readiness probes or CORS preflight must be designed explicitly instead of opening `anyExchange().permitAll()`.

For bearer-only APIs that do not use browser cookies, evaluate appropriate CSRF settings. **Never disable CSRF mechanically** if session/cookie authentication is still active. POSTs may require CSRF tokens under default Security policies, so the lab below focuses on GET.

### 8.3. Verifying Audience Alongside Issuer: Explicit Validator Example

A token with a valid signature that was issued for **a different application** must not automatically work against the Gateway. Spring Security WebFlux example with `ReactiveJwtDecoder`:

~~~java
package demo.gateway.security;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.oauth2.core.OAuth2Error;
import org.springframework.security.oauth2.core.DelegatingOAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidatorResult;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.jwt.JwtValidators;
import org.springframework.security.oauth2.jwt.NimbusReactiveJwtDecoder;
import org.springframework.security.oauth2.jwt.ReactiveJwtDecoder;

@Configuration(proxyBeanMethods = false)
public class GatewayJwtDecoderConfiguration {

    @Bean
    ReactiveJwtDecoder jwtDecoder(
            @Value("${demo.security.jwk-set-uri}") String jwkSetUri,
            @Value("${demo.security.issuer}") String issuer,
            @Value("${demo.security.audience}") String audience) {

        NimbusReactiveJwtDecoder decoder =
                NimbusReactiveJwtDecoder
                        .withJwkSetUri(jwkSetUri)
                        .build();

        OAuth2TokenValidator<Jwt> standard =
                JwtValidators.createDefaultWithIssuer(issuer);

        OAuth2TokenValidator<Jwt> audienceCheck = jwt ->
                jwt.getAudience().contains(audience)
                        ? OAuth2TokenValidatorResult.success()
                        : OAuth2TokenValidatorResult.failure(
                                new OAuth2Error(
                                        "invalid_token",
                                        "Required audience missing",
                                        null));

        decoder.setJwtValidator(
                new DelegatingOAuth2TokenValidator<>(
                        standard, audienceCheck));
        return decoder;
    }
}
~~~

And custom properties backing `@Value`:

~~~yaml
demo:
  security:
    issuer: https://idp.example.test/realms/platform
    audience: api-gateway
    jwk-set-uri: https://idp.example.test/realms/platform/protocol/openid-connect/certs
~~~

**Do not copy placeholder JWK URLs as production endpoints.** The JWK location depends on your IdP. `JwtValidators.createDefaultWithIssuer` provides default checks plus issuer validation; `audienceCheck` accepts only tokens whose `aud` includes the expected audience. Also review algorithms/key sizes, key rotation, scopes, token revocation, claim sources, clock skew, and IdP policies commensurate with risk.

When declaring a custom `ReactiveJwtDecoder` bean, you are **replacing/overriding the related decoder auto-configuration**. Test invalid signatures, wrong issuers, wrong audiences, expired, not-before, and missing scopes. Do not register two conflicting decoder beans for unclear token types and expect Spring to guess right.

### 8.4. A Principal from a JWT Is Not Yet Resource-Level Permission

A JWT containing:

~~~json
{
  "sub": "user-123",
  "aud": ["api-gateway"],
  "scope": "orders.read",
  "tenant_id": "tenant-42"
}
~~~

Once the token is verified, Gateway can allow `GET /api/orders/**` based on `SCOPE_orders.read`. However, the backend must still verify **whether `user-123` has permission to view that specific order**, and whether `tenant_id` matches the resource. An API-level scope **does not imply permission to read every order in every tenant**.

## 9. When Identity Must Be Forwarded to the Backend: Pick a Safe Contract

**Preferred:** Backend verifies an access token **scoped to the backend's audience**, or a new token obtained via token exchange/client credentials/delegation under policy. Only emit an internal header generated by Gateway from the principal when the backend has a trusted channel and a very strict contract.

| Approach | Advantage | Risk / requirements |
| --- | --- | --- |
| Backend verifies audience-matched token directly | Does not rely on plain headers | Manage IdP/JWKS, audience, scopes, retries/revocation |
| Gateway token exchange for backend | Isolates audience/scope, bounds delegation | Token exchange policy, credentials, caching, and TLS |
| Gateway emits `X-Verified-Subject` post-auth | Easy integration with legacy backends | **Safe only with mTLS/ACLs + no direct access + anti-spoof checks** |
| Gateway forwards client `X-User-Id` verbatim | Zero security advantage | **Never use** |

### 9.1. Do Not Use `SetRequestHeader` with a Static User ID

~~~yaml
# Semantically broken for security: does not establish a principal identity.
filters:
  - SetRequestHeader=X-Verified-Subject,admin
~~~

This merely sets a constant string. Another variant like `AddRequestHeader=X-Verified-Subject,{userId}` from a URI template is also wrong: clients can control path variables. Identity must originate from a **validated security context**, never from caller-chosen paths/queries/headers.

### 9.2. Example Identity Bridge Scoped to One Gateway Route

An application can use a `GlobalFilter` to extract `JwtAuthenticationToken` from Reactive SecurityContext and attach a header after `UntrustedIdentityHeadersWebFilter` (section 7) has stripped spoofed headers. The lab example below applies only to route ID `orders-protected`:

~~~java
package demo.gateway.security;

import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.cloud.gateway.route.Route;
import org.springframework.core.Ordered;
import org.springframework.http.HttpStatus;
import org.springframework.http.server.reactive.ServerHttpRequest;
import org.springframework.security.core.context.ReactiveSecurityContextHolder;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;

import reactor.core.publisher.Mono;

import static org.springframework.cloud.gateway.support.ServerWebExchangeUtils.GATEWAY_ROUTE_ATTR;

@Component
public final class VerifiedIdentityBridgeFilter
        implements GlobalFilter, Ordered {

    @Override
    public int getOrder() {
        // Lab example: verify actual ordering against route filters.
        return 10_000;
    }

    @Override
    public Mono<Void> filter(ServerWebExchange exchange,
                             GatewayFilterChain chain) {

        Route route = exchange.getAttribute(GATEWAY_ROUTE_ATTR);
        if (route == null ||
                !"orders-protected".equals(route.getId())) {
            return chain.filter(exchange);
        }

        return ReactiveSecurityContextHolder.getContext()
                .map(ctx -> ctx.getAuthentication())
                .ofType(JwtAuthenticationToken.class)
                .filter(auth -> auth.isAuthenticated())
                .flatMap(auth -> Mono.justOrEmpty(
                        auth.getToken().getSubject()))
                .filter(subject -> subject.matches(
                        "[A-Za-z0-9._:@-]{1,128}"))
                // Place fallback BEFORE flatMap returning Mono<Void>:
                // Mono<Void> normally completes without emitting onNext.
                .defaultIfEmpty("")
                .flatMap(subject -> {
                    if (subject.isEmpty()) {
                        return reject(exchange);
                    }

                    ServerHttpRequest sanitized =
                            exchange.getRequest().mutate()
                                    .headers(headers -> {
                                        headers.remove(
                                                "X-Verified-Subject");
                                        headers.set(
                                                "X-Verified-Subject",
                                                subject);
                                    }).build();

                    return chain.filter(exchange.mutate()
                            .request(sanitized).build());
                });
    }

    private Mono<Void> reject(ServerWebExchange exchange) {
        exchange.getResponse()
                .setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();
    }
}
~~~

**Security meaning of this example:**

1. It **never** reads `X-User-Id` from the request.
2. An earlier `WebFilter` strips caller-supplied identity headers.
3. On route `orders-protected`, a `GlobalFilter` accepts only a `JwtAuthenticationToken` after Spring Security has verified the JWT.
4. `X-Verified-Subject` is removed again and **set exclusively** from the valid `sub` claim.
5. If no valid principal exists or the claim violates formatting rules, the request is rejected.
6. The backend must still accept requests only from the Gateway service identity and enforce resource authorization.

**Limitations:** This is an **illustrative** bridge, not a complete production identity protocol. The `sub` regex only constrains characters safely for an HTTP header, not authentication. The header is unsigned and can be forged on any unlocked backend path. Filter order `10_000` was chosen for the lab; **verify actual execution order between GlobalFilters and GatewayFilters/NettyRoutingFilter on your exact version**. Never place a `RemoveRequestHeader=X-Verified-Subject` running **after** this bridge, or it will wipe the verified header. Do not build backend authorization solely on plain headers when direct token verification is possible.

### 9.3. Avoid "Strip and Re-Add from Client Data"

A broken pattern:

~~~java
// COUNTEREXAMPLE: header name changed, yet the data source did not!
String user = exchange.getRequest().getHeaders()
        .getFirst("X-User-Id");
ServerHttpRequest request = exchange.getRequest().mutate()
        .headers(h -> {
            h.remove("X-User-Id");
            h.set("X-Verified-Subject", user);
        }).build();
~~~

The source of `user` is still client input. Renaming a header does not upgrade trust. Likewise, never read `jwt.getClaimAsString("role")` to grant privileges unless the issuer and claim conform to a verified trust policy.

### 9.4. Internal Headers Must Never Leak Back in Responses

When backends/Gateways log or return data, avoid reflecting `X-Verified-Subject` and `X-Verified-Tenant` back to clients outside contract. If a backend accidentally echoes all request headers into JSON responses, attackers can harvest internal identifiers. For debugging, use synthetic markers only in test environments, and remove them before production.

## 10. Forwarded and X-Forwarded-*: Metadata Trusted Only When the Proxy Is Trusted

Common header group:

~~~http
Forwarded: for=198.51.100.20;proto=https;host=api.example.test
X-Forwarded-For: 198.51.100.20, 10.20.30.5
X-Forwarded-Proto: https
X-Forwarded-Host: api.example.test
X-Forwarded-Port: 443
X-Forwarded-Prefix: /edge
~~~

`Forwarded` follows RFC 7239, while `X-Forwarded-*` are widespread conventions. They help backends reconstruct client address, scheme, original Host, and prefix when Gateway sits behind a reverse proxy. Yet they are **just bytes in an HTTP request** until their origin is verified.

### 10.1. Two Completely Distinct Questions

1. **Who is permitted to set forwarding metadata?** Only an edge/proxy verified by network path/cert, after stripping client-supplied values.
2. **How does Gateway interpret metadata?** Via `trusted-proxies`, Spring forwarding strategy, or `RemoteAddressResolver` depending on version and request path.

Configuring the second **cannot substitute for** the first. Even a tight `trusted-proxies` regex can be bypassed if clients connect directly to Gateway or ingress fails to scrub inbound headers.

### 10.2. WebFlux Gateway 5.x — trusted-proxies

Spring Cloud Gateway Server WebFlux 5.x documentation describes `spring.cloud.gateway.server.webflux.trusted-proxies` as a **Java regular expression** identifying trusted proxies appearing in `Forwarded` or `X-Forwarded` metadata. This is **not CIDR notation**.

Example restricting to two fixed proxy addresses in a lab network:

~~~yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          trusted-proxies: '^10[.]20[.]30[.](5|6)$'
          x-forwarded:
            for-enabled: true
            host-enabled: true
            proto-enabled: true
            for-append: false
            host-append: false
            proto-append: false
~~~

Explanation:

- Pattern `^10[.]20[.]30[.](5|6)$` is an **illustrative allowlist** for `10.20.30.5` and `10.20.30.6`, not a universal config for all environments.
- `trusted-proxies` governs Gateway WebFlux's **`Forwarded`/`XForwarded` HttpHeadersFilters** when preparing downstream headers.
- `for-append: false`, `host-append: false`, and `proto-append: false` instruct Gateway's mechanism **not to append** to existing values for those features, but **do not automatically delete every spoofed header before route matching or Spring Security**.
- To preserve a full proxy chain for auditing, the entire chain must be verified; do not enable appending just to collect more addresses.
- For Host/Proto, ingress must validate real hostnames and schemes; never let browsers declare external values that backends turn into redirects.

**Warning:** Never put `.*` or `^.*$` into `trusted-proxies` just "to make headers work." That is trust-all by regex; patterns must match a reviewed operational allowlist, while the network blocks unapproved sources. Verify the exact address format Gateway feeds into the regex (IPv4/IPv6, ports/quotes) via integration tests.

### 10.3. WebFlux Gateway 4.x and Server Web MVC

Some Gateway 4.x lines use:

~~~yaml
spring:
  cloud:
    gateway:
      trusted-proxies: '^10[.]20[.]30[.](5|6)$'
      x-forwarded:
        for-append: false
~~~

This is the **legacy prefix syntax**; check the configuration metadata of your exact 4.x release before applying. Gateway Server Web MVC has its corresponding namespace:

~~~yaml
spring:
  cloud:
    gateway:
      server:
        webmvc:
          trusted-proxies: '^10[.]20[.]30[.](5|6)$'
~~~

**Web MVC and WebFlux do not share filter code APIs**: Web MVC runs on Servlet/WebMvc.fn, while the Java `WebFilter`, `ServerWebExchange`, and `GlobalFilter` examples in this lesson target WebFlux. Proxy trust principles remain identical, but properties and filter lifecycles must match the stack.

### 10.4. Do Not Confuse Gateway HttpHeadersFilters with Spring Forwarding Strategy

Spring Boot has `server.forward-headers-strategy` (typically `NONE`, `NATIVE`, or `FRAMEWORK` depending on environment/version). It controls how the web server or Spring Framework processes forwarded headers on the **inbound request side**, affecting the scheme/host/port handlers observe.

Meanwhile, Gateway's `Forwarded`/`XForwarded` **HttpHeadersFilters** act when constructing **downstream requests**. They operate at different layers; configuring one does not automatically lock down the other.

If enabling `server.forward-headers-strategy: framework` or Reactor Netty proxy support:

1. Confirm the edge strips/cleans forwarded headers.
2. Block clients from reaching the Gateway listener directly.
3. Verify URI/scheme/Host post-transform before route predicates, OAuth2 redirects, and absolute URL generation.
4. Check that stripping/appending outbound headers aligns with the trust boundary.

Never enable an inbound forwarding transformer on an Internet-facing listener while trusting client-supplied forwarded inputs. In deployments without a trusted reverse proxy, the safest choice is usually not using forwarded metadata for security decisions.

## 11. X-Forwarded-For and Two Easily Confused IP Resolvers

### 11.1. Standard `RemoteAddr`

Route predicate:

~~~yaml
predicates:
  - RemoteAddr=10.20.30.0/24
~~~

by default inspects the **remote socket peer address** of the request received by Gateway. Behind an ingress, that address is usually the **ingress IP**, not the Internet end-user.

If the network permits only trusted ingress to reach Gateway, checking the remote socket peer helps restrict proxy connections. However, it **does not authenticate end-user identity**.

### 11.2. `XForwardedRemoteAddressResolver.trustAll()` Is a Spoofing Risk

Gateway WebFlux offers an XFF-based resolver:

~~~java
XForwardedRemoteAddressResolver.trustAll()
~~~

Per Gateway documentation, this picks the first address in `X-Forwarded-For`, which a client can forge. Given:

~~~http
X-Forwarded-For: 10.0.0.8, 198.51.100.20
~~~

a caller can supply `10.0.0.8` and trick the resolver into treating it as the client IP. **Never use `trustAll()` for IP allowlists or security decisions on untrusted traffic.**

### 11.3. `maxTrustedIndex(n)` Reads the Chain from the Right

Example XFF chain:

~~~http
X-Forwarded-For: 192.0.2.10, 198.51.100.20, 10.20.30.5
~~~

Gateway documentation describes:

| `maxTrustedIndex` | Selected address from example | Meaning |
| ---: | --- | --- |
| `1` | `10.20.30.5` | Last element, closest to Gateway in XFF |
| `2` | `198.51.100.20` | Two positions back from the right |
| `3` | `192.0.2.10` | Leftmost element in this chain |
| `>3` | `192.0.2.10` per current behavior | Exceeding element count adds no further verification |

`maxTrustedIndex(0)` is invalid. More importantly: **matching topology with n is not an option to "pick the IP I want to see."** The value n must equal the exact number of **controlled** proxy hops after the edge strips inbound client headers.

When spoofed client IPs sit on the left, picking too large an n still selects a forged IP. If Gateway is accessed directly without traversing the expected hops, all assumptions break.

### 11.4. Java RouteLocator Example with a Bounded Resolver

~~~java
package demo.gateway.routing;

import org.springframework.cloud.gateway.route.RouteLocator;
import org.springframework.cloud.gateway.route.builder.RouteLocatorBuilder;
import org.springframework.cloud.gateway.support.ipresolver.XForwardedRemoteAddressResolver;
import org.springframework.cloud.gateway.support.ipresolver.RemoteAddressResolver;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class ExampleRemoteAddrRoutes {

    @Bean
    RouteLocator exampleRoutes(RouteLocatorBuilder builder) {
        RemoteAddressResolver resolver =
                XForwardedRemoteAddressResolver.maxTrustedIndex(1);

        return builder.routes()
                .route("ip-observation-lab",
                        r -> r.remoteAddr(resolver, "198.51.100.0/24")
                                .uri("http://127.0.0.1:9091"))
                .build();
    }
}
~~~

**This is an IP-matching lab, not a fully secured admin endpoint.** The code lacks a Path predicate so it is very broad; if testing alongside other routes, attach explicit Path/method predicates and verify ordering. Never deploy this snippet to production verbatim, and never rely on IPs to replace Spring Security. The example matches `198.51.100.0/24` in XFF **only when the network/proxy guarantees XFF provenance**.

### 11.5. `XForwardedRemoteAddr` Predicate Does Not Prove Trust by Itself

Some Gateway Server WebFlux releases also provide an `XForwardedRemoteAddr` route predicate using `X-Forwarded-For` data. If the header source is untrusted, CIDR matching can still rely on a spoofed IP. Check version behavior and ensure only verified proxies can set metadata; when the goal is authorization, prefer verified principals/tokens over IPs/headers.

### 11.6. Real Client IPs Are Not Always Determinable

Because of NAT, CDNs, VPNs, mobile carriers, HTTP proxies, and IPv6:

- One IP can represent thousands of users.
- One user can change IPs between requests.
- Some networks expose only an upstream proxy address, never the end-user address.
- Rate limiters keyed by IP can cause false positives/negatives if the trust chain is misunderstood.

Therefore, use IPs for **telemetry/auxiliary quotas** and network boundaries, never as a replacement for a principal. For account/tenant quotas, use verified identity.

## 12. Host, Proto, HTTP Headers, and TLS Also Sit Inside the Trust Boundary

### 12.1. `X-Forwarded-Host` Can Cause Open Redirects

Suppose an app constructs an email confirmation URL:

~~~java
// COUNTEREXAMPLE: never use an unverified Host
// to build account/reset-password links.
String host = request.getHeaders()
        .getFirst("X-Forwarded-Host");
String resetUrl = "https://" + host + "/reset?token=...";
~~~

If a client can set `X-Forwarded-Host: attacker.example.test`, the app may email reset links pointing to the attacker's domain (**host-header injection**). For sensitive links, use a **fixed public base URL from approved config**; if dynamic hosts are necessary, validate against an allowlist after edge canonicalization.

### 12.2. `X-Forwarded-Proto` Does Not Prove TLS

A request arriving at Gateway over HTTP does not become HTTPS just because the client sends:

~~~http
X-Forwarded-Proto: https
~~~

To ensure the public leg is protected, you need **TLS termination at a trusted edge**, properly configured HSTS, and network access controls. If SSL/TLS terminates at the edge and runs HTTP to Gateway, the internal hop still needs network segregation/mTLS per threat model.

### 12.3. `PreserveHostHeader` Does Not Prove a Valid Host

Gateway Server has a `PreserveHostHeader` filter that forwards the client's Host header to the backend. It satisfies virtual host requirements, **not validation** that Host belongs to an allowed domain.

When backends use Host to select tenants or build callback URLs:

- Enforce Host allowlists at public ingress/`server_name`/TLS.
- Treat the `Host` route predicate as **routing**, not authentication.
- Block paths bypassing ingress.
- If the original host is needed, read from a canonical source post-trusted-proxy validation.
- Test duplicate Hosts, HTTP/2 `:authority`, casing, ports, and unusual hostnames per HTTP server behavior.

### 12.4. Hop-by-Hop Headers and HTTP Request Smuggling

Headers like `Connection`, `Transfer-Encoding`, and `Keep-Alive` must not be proxied blindly. Gateway WebFlux includes **`RemoveHopByHop` HttpHeadersFilter**, with documentation listing default header names stripped from downstream requests.

Do not alter the hop-by-hop allowlist to "preserve all headers" without a standard HTTP rationale and testing. Disagreements on `Content-Length`/`Transfer-Encoding` across edge, Gateway, and backend can cause request desynchronization/smuggling; keep Netty/HTTP server patches updated and configurations aligned. This is **distinct** from JWT identity, yet part of the same safe reverse proxy boundary.

### 12.5. Backends Must Verify the Gateway, Not Just the Header

If a backend relies on `X-Verified-Subject`, minimum requirements are:

1. No direct Internet/NodePort/LoadBalancer route to the backend.
2. Only the Gateway workload identity can connect (mTLS or appropriate network and service identity controls).
3. `X-Verified-Subject` is generated solely from a verified auth context, never from client requests.
4. Backend verifies requests genuinely arrive over the authorized channel; never trust any inbound packet carrying the header.
5. Backend still enforces resource-level authorization and tenant ownership.

**An mTLS channel authenticates the Gateway workload, not the end user.** The backend still needs a dedicated delegation/token/verified-claims model for end-user identity.

### 13.2. Standalone Echo Backend

Create a Spring Boot WebFlux application on `9091` (e.g., Spring Boot 3.x with `spring-boot-starter-webflux`):

~~~java
package demo.orders;

import java.util.LinkedHashMap;
import java.util.Map;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.http.server.reactive.ServerHttpRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class OrdersBackendApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrdersBackendApplication.class, args);
    }
}

@RestController
class OrdersEchoController {

    @GetMapping("/api/orders/{id}")
    Map<String, Object> echo(
            @PathVariable String id,
            ServerHttpRequest request) {

        Map<String, Object> body = new LinkedHashMap<>();
        body.put("backend", "orders-echo");
        body.put("orderId", id);
        body.put("userIdFromClient",
                request.getHeaders().getFirst("X-User-Id"));
        body.put("roleFromClient",
                request.getHeaders().getFirst("X-Role"));
        body.put("tenantFromClient",
                request.getHeaders().getFirst("X-Tenant-Id"));
        body.put("verifiedSubject",
                request.getHeaders().getFirst(
                        "X-Verified-Subject"));
        body.put("forwardedFor",
                request.getHeaders().getFirst(
                        "X-Forwarded-For"));
        body.put("authorizationPresent",
                request.getHeaders().containsKey(
                        "Authorization"));
        return body;
    }
}
~~~

~~~yaml
# Backend application.yml

  port: 9091
~~~

**Lab warning:** The echo controller returns request header metadata in the response body solely for **local lab observation**, not as a production pattern. Never expose an echo endpoint publicly, never echo tokens/cookies, and never use the returned `verifiedSubject` as an authorization mechanism. If exposed on the Internet, outsiders could call it directly with forged headers and break the security model.

### 13.4. Testing Spoofing Without a Valid Token

~~~bash
curl -i "http://127.0.0.1:8080/api/orders/42" \
  -H "X-User-Id: admin" \
  -H "X-Role: admin" \
  -H "X-Verified-Subject: admin" \
  -H "X-Tenant-Id: privileged"
~~~

With a `SecurityWebFilterChain` requiring `SCOPE_orders.read` on GET `/api/orders/**`, this request must be **rejected before proxying** (typically 401 unauthenticated). The backend must see zero new requests.

If the backend still returns 200, verify whether Security config is active, check other routes/handlers, test profiles, auto-configuration, and how route filters are wired.

### 13.5. Testing Valid JWT Alongside Spoofed Headers

Obtain a token **issued by a test IdP** with matching issuer/audience, scope `orders.read`, and a properly formatted `sub`. Never fabricate a literal token string and call it valid.

~~~bash
# ACCESS_TOKEN loaded into environment per safe lab workflow.
# Never print tokens into logs/tickets.
curl -i "http://127.0.0.1:8080/api/orders/42" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-User-Id: admin" \
  -H "X-Role: admin" \
  -H "X-Tenant-Id: privileged" \
  -H "X-Verified-Subject: attacker"
~~~

Once the JWT is verified and route `orders-protected` matches, the expected echo backend body looks like:

~~~json
{
  "backend": "orders-echo",
  "orderId": "42",
  "userIdFromClient": null,
  "roleFromClient": null,
  "tenantFromClient": null,
  "verifiedSubject": "user-123",
  "authorizationPresent": true
}
~~~

`user-123` is only an **illustrative value** corresponding to the test JWT's `sub`. `verifiedSubject` must come from the verified token, **never from `attacker`**. `authorizationPresent` may differ depending on Gateway token-forwarding policy; if the backend must not receive client tokens, implement intentional **token exchange or bearer token stripping/swapping** and update the assertion.

Forwarding headers (like `forwardedFor`) may be preserved or added by the HTTP client/Gateway depending on configuration. **Do not mark them trusted merely because they appear in echo output**; test the trust boundary per section 14.

### 13.6. Comparing Direct Calls to the Backend

In the lab, you can call directly:

~~~bash
curl -i "http://127.0.0.1:9091/api/orders/42" \
  -H "X-Verified-Subject: attacker"
~~~

The echo backend will observe `attacker` because **the request bypassed the Gateway**. This demonstrates why backends **cannot rely solely on plain headers**. In production, direct paths must be blocked by firewalls/NetworkPolicies/mTLS, or backends must verify bearer/internal tokens themselves.

When building service-to-service identity with mTLS, the backend should trust only senders presenting Gateway's valid workload certificate. Never grant every Pod in the cluster access to the backend merely because the Service type is `ClusterIP`.

### 13.7. Never Conclude from HTTP Status Alone

A request may return:

| Status | Possible reasons |
| --- | --- |
| 200 | Valid JWT, policy allowed, backend succeeded; or another insecure route handled the request |
| 401 | Unauthenticated, invalid signature/issuer/audience/expiry, or bridge lacked principal |
| 403 | Valid JWT missing scope/role, or backend denied |
| 404/405 | Route method/path predicate missed, or different handler |
| 429 | Rate limiter throttled client |
| 502/503 | Backend/transport/LB/mTLS failure |

For header spoofing tests, simultaneously verify **status + route ID + backend request count + downstream header values**. Only then do you have proof no request crossed the boundary.

## 14. Anti-Spoofing Tests Must Cover "Denied" Cases Too

### 14.1. Security Acceptance Matrix

| ID | Scenario | Expectation |
| --- | --- | --- |
| S01 | No Authorization, sends `X-User-Id: admin` | Gateway grants no access; backend receives zero requests |
| S02 | Invalid token signature, spoofed valid identity headers | 401, not forwarded |
| S03 | Valid signature, wrong issuer | Rejected, not forwarded |
| S04 | Valid issuer, wrong `aud` | Rejected if audience validator is enabled |
| S05 | Unexpired token missing `orders.read` | 403 per policy, not forwarded |
| S06 | Valid token with right scope, no identity headers | Correct route; backend receives proper principal/token |
| S07 | Token for `user-123` with `X-User-Id: admin` | Backend never sees `admin` |
| S08 | Token for `user-123` with `X-Verified-Subject: attacker` | Backend sees only `user-123` if identity bridge is enabled |
| S09 | Repeated multi-value `X-Verified-Subject` | Zero client values retained downstream |
| S10 | Renamed header `x-user-id`/`X-USER-ID` | Also stripped per HTTP semantics |
| S11 | Underscore/mixed normalization header variants | Edge/Gateway enforces policy; no alias bypass |
| S12 | Client sends `X-Forwarded-For: 10.0.0.8` | Spoofed IP never treated as trusted client identity |
| S13 | Client hits Gateway directly instead of Ingress | Network boundary rejects bypass path in production |
| S14 | Trusted Ingress sends reset forwarding metadata | Gateway resolves client peer/trusted chain accurately |
| S15 | `maxTrustedIndex` exceeds hop count | Tests catch misconfig/untrusted IP selection |
| S16 | Backend called directly with `X-Verified-Subject: admin` | Production blocks via network/mTLS or backend ignores plain header |
| S17 | Host outside allowlist or spoofed `X-Forwarded-Host` | Generates no redirects/privileged domains from fake values |
| S18 | Public TLS valid, yet Gateway→backend lacks authentication | Policy test forbids missing mTLS/ACL when required |
| S19 | New route omits identity header filters | Global/edge policy still scrubs; regression fails if omitted |
| S20 | Actuator/public debug echo endpoint exposes headers | Diagnostics/PII unexposed, separately governed |
| S21 | Same request carries valid `Authorization` plus spoofed tenant header | Tenant derived from IdP/authorization, not header |
| S22 | Fallback route matches request rejected by primary route | Never bypasses scope/auth or downstream header policy |
| S23 | Expired/not-yet-valid JWT or revoked key | Decoder/IdP validation rejects per policy |
| S24 | No trusted proxy, yet HTTP request contains `Forwarded` | Client-declared host/proto/for never treated as verified |

The matrix mixes **positive, negative, and topology tests**. Several cases require results from network policy or TLS/mTLS integration tests rather than HTTP header unit tests alone.

### 14.2. Unit Test for `UntrustedIdentityHeadersWebFilter`

JUnit 5 + Spring Test example:

~~~java
package demo.gateway.security;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicReference;

import org.junit.jupiter.api.Test;
import org.springframework.mock.http.server.reactive.MockServerHttpRequest;
import org.springframework.mock.web.server.MockServerWebExchange;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebFilterChain;

import reactor.core.publisher.Mono;

import static org.assertj.core.api.Assertions.assertThat;

class UntrustedIdentityHeadersWebFilterTest {

    @Test
    void stripsSpoofedIdentityButKeepsBearerForSecurity() {
        var exchange = MockServerWebExchange.from(
                MockServerHttpRequest
                        .get("/api/orders/42")
                        .header("X-User-Id", "admin")
                        .header("x-role", "admin")
                        .header("X-Tenant-Id", "privileged")
                        .header("X-Verified-Subject", "attacker")
                        .header("Authorization",
                                "Bearer LAB_FAKE_TOKEN"));

        AtomicReference<ServerWebExchange> seen =
                new AtomicReference<>();
        WebFilterChain chain = next -> {
            seen.set(next);
            return Mono.empty();
        };

        new UntrustedIdentityHeadersWebFilter()
                .filter(exchange, chain)
                .block(Duration.ofSeconds(2));

        assertThat(seen.get()).isNotNull();
        var headers = seen.get().getRequest().getHeaders();

        assertThat(headers.containsKey("X-User-Id"))
                .isFalse();
        assertThat(headers.containsKey("X-Role"))
                .isFalse();
        assertThat(headers.containsKey("X-Tenant-Id"))
                .isFalse();
        assertThat(headers.containsKey("X-Verified-Subject"))
                .isFalse();
        assertThat(headers.getFirst("Authorization"))
                .isEqualTo("Bearer LAB_FAKE_TOKEN");
    }
}
~~~

The `block(...)` call here lives **solely inside the JUnit unit test**, never in a production WebFlux request pipeline. The test uses a synthetic bearer string to verify the scrub layer **does not remove credentials ahead of Spring Security**; it **does not validate JWT signatures**.

This unit test verifies the header sanitizer **directly**. It does not test security, filter ordering, Gateway route selection, or Netty outbound headers. Run integration tests through a real HTTP server as well.

### 14.3. Integration Test with Gateway and Backend Stub

With `@SpringBootTest(webEnvironment=RANDOM_PORT)`, `WebTestClient`, and MockWebServer/WireMock, point the backend `uri` to a dynamic port instead of fixed port 9091:

~~~yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: orders-protected
              uri: http://127.0.0.1:${test.backend.port}
              predicates:
                - Path=/api/orders/**
                - Method=GET
~~~

In test setup, use `@DynamicPropertySource` to inject `test.backend.port` from the stub and generate **test JWTs signed with a test key** (or mock SecurityContext in dedicated *mock-web* tests). Never try stuffing `SecurityMockServerConfigurers.mockJwt()` into an HTTP client hitting a real server assuming the server receives mock authentication: the client-side mock JWT helper operates on the **test context**, and does not mint a real signed bearer token for a remote HTTP listener.

Core assertions:

~~~text
Client sends valid token, X-User-Id=admin
    ↓
Gateway Security validates JWT
    ↓
Gateway WebFilter strips X-User-Id
    ↓
Gateway filter sets X-Verified-Subject=user-123 (if bridge enabled)
    ↓
MockWebServer recorded request:
    X-User-Id: ABSENT
    X-Verified-Subject: user-123
    Authorization: per tested token-forwarding policy
~~~

For forged tokens or tokens missing scopes, MockWebServer **must receive zero new requests**. Use counts and `RecordedRequest` to catch requests accidentally slipping through a fallback route or another bean.

### 14.4. Testing Duplicates/Casing/Aliases

~~~bash
# Only in test environments with a valid token.
curl -i "http://127.0.0.1:8080/api/orders/42" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-User-Id: admin" \
  -H "x-user-id: another-user" \
  -H "X-Verified-Subject: attacker" \
  -H "X-Verified-Subject: second-attacker"
~~~

Clients/proxies may merge duplicate headers or reject before Gateway receives them. Therefore tests must inspect **actual downstream data** and HTTP server behavior rather than assuming all headers arrive intact. For single-valued identity headers, the policy should **wipe inbound values and emit a single value from the principal**.

Variants like `X_User_Id` and `X-User-Id` are occasionally converted/normalized by intermediaries. Never assume they are automatically treated identically under HTTP standards; enforce a policy to **reject/strip non-standard forms** at the edge and test on the exact proxy you deploy.

### 14.5. Testing Topology, Not Just HTTP Payloads

Two distinct checks:

- From the **Internet/public subnet**, attempt direct connections to the Gateway application port/backend port: must be denied by firewall/NetworkPolicy, not merely HTTP 401/403.
- From the **trusted edge subnet**, requests traverse ingress and TLS properly; Gateway observes the configured remote socket address and sanitized Forwarded/XFF headers.

A 401 response at Gateway **does not prove** bypass paths are closed: attackers can still probe other endpoints, parser bugs, or gaps in Security matchers. Network isolation is an independent defense layer.

## 15. Locking Down the Backend with Kubernetes NetworkPolicy and Service Identity

Suppose Gateway runs in namespace `platform-edge` and the backend runs in `platform-apps`. A sample ingress NetworkPolicy allowing only selected Gateway Pods to reach backend port 9091:

~~~yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-backend-from-gateway
  namespace: platform-apps
spec:
  podSelector:
    matchLabels:
      app: orders-backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: platform-edge
          podSelector:
            matchLabels:
              app: api-gateway
      ports:
        - protocol: TCP
          port: 9091
~~~

Explanation:

- The top-level `podSelector` selects the **protected backend Pods**.
- `from.namespaceSelector` and `from.podSelector` in the same entry restrict access to **Gateway Pods in the permitted namespace**.
- `Ingress` policy prevents other Pods from reaching the chosen port **when the CNI actually enforces NetworkPolicies**.
- NetworkPolicy is L3/L4 isolation, **not end-user authentication**; labels can be misassigned if RBAC/deployment permissions are loose.
- If Gateway calls the backend on other ports or via a service mesh sidecar, inspect every real path.

**Do not copy policies verbatim:** namespaces/labels/ports are illustrative only. Test both allowed and blocked paths after deployment. NetworkPolicy does not protect a listener if a NodePort/LoadBalancer or `hostNetwork` bypasses policy depending on CNI/infrastructure.

### 15.1. Adding mTLS Between Gateway and Backend

NetworkPolicy narrows sources, yet a compromised Pod or misapplied label/ServiceAccount may still need **workload identity** protection. Service-mesh mTLS or direct client/server certificates can:

- Authenticate the Gateway workload via client certificate.
- Authenticate the target backend and prevent man-in-the-middle attacks.
- Encrypt traffic between the two services.
- Bind calling rights to service identity, namespace, or policy.

Nevertheless, **mTLS does not carry end-user principals automatically**. If the backend authorizes by `user-123`, you still need tokens/delegation/verified-header protocols. Also verify certificate rotation, SPIFFE/SVID, or CA/truststore mechanics for your platform.

### 15.2. Never Let Dynamic Routes Proxy Back into the Control Plane

If an admin API can create arbitrary routes, an under-privileged actor may try setting `uri` to:

~~~text
http://127.0.0.1:9090/actuator/...
http://169.254.169.254/...
http://internal-admin-service/...
~~~

This is an SSRF/open proxy risk. If the Gateway can reach internal admin endpoints, a public route can turn into a bypass around the trust boundary.

Therefore, a dynamic route control plane needs:

1. Authentication/RBAC/approval for route creation/update/deletion.
2. Scheme/host/port allowlists plus DNS resolution/redirect checks.
3. Blocks on loopback, link-local, metadata endpoints, and management listeners unless explicitly allowlisted.
4. Audits of revisions, route IDs, operators, and rollbacks.
5. Negative tests for forbidden host/IP URLs, including DNS rebinding/races.

Trusting only verified proxies **does not stop SSRF** if insufficiently privileged clients/admins can alter route `uri`s.

## 16. Rate Limiting, Retries, and Observability Must Use Valid Identity Sources

### 16.1. KeyResolver Must Never Pull Tenant/User from Spoofed Headers

A broken approach:

~~~java
// COUNTEREXAMPLE: caller picks their own key and can rotate keys to evade quotas.
return exchange -> Mono.justOrEmpty(
        exchange.getRequest().getHeaders()
                .getFirst("X-User-Id"));
~~~

If rate limits key off client-supplied `X-User-Id`, attackers can change the header on every request to spawn fresh quota buckets. Likewise, if limiters rely on untrusted `X-Forwarded-For`, attackers can send fake addresses to bypass limits.

### 16.2. Using the Authenticated Principal as the Quota Key

With JWT Resource Server:

~~~java
package demo.gateway.security;

import org.springframework.cloud.gateway.filter.ratelimit.KeyResolver;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;

import reactor.core.publisher.Mono;

@Configuration(proxyBeanMethods = false)
public class RateLimitIdentityConfiguration {

    @Bean
    KeyResolver verifiedUserKeyResolver() {
        return exchange -> exchange.getPrincipal()
                .ofType(JwtAuthenticationToken.class)
                .map(JwtAuthenticationToken::getName)
                .switchIfEmpty(Mono.just("unauthenticated"));
    }
}
~~~

On routes protected by `SecurityWebFilterChain`, the key comes from the verified JWT principal. The `"unauthenticated"` fallback is a **shared bucket for requests lacking a principal if a route genuinely permits them to reach the limiter**, never permission to skip authentication. On sensitive APIs, let Security **reject anonymous calls upfront**; avoid falling back to `X-User-Id`.

If per-tenant quotas are needed, derive the key from a **verified and authorized tenant claim**, not a `tenantId` query/header. Bound bucket key lengths, charsets, and cardinality; never place raw JWTs inside Redis keys or metrics.

### 16.3. Avoid Leaks During Retries, Circuit Breakers, and Fallbacks

A retry filter can resend the same request multiple times. Before permitting retries, verify:

- The JWT/token remains valid and carries the right audience for downstream attempts.
- Internal headers are generated **exactly once** or overwritten, never appended as duplicate claims.
- When a circuit breaker invokes a fallback handler, the fallback **does not bypass Security** or read identity from untrusted headers.
- For POST/PUT/PATCH with side effects, retries require idempotency keys/transaction policies.
- When a backend fails, responses never echo Authorization/Cookie/forwarded metadata in error messages.

Route selection and filter chains have pre/post ordering; if a filter added after `VerifiedIdentityBridgeFilter` can touch `X-Verified-Subject`, verify **actual ordering** with downstream request captures.

### 16.4. Auditing and Alerting Without Raw PII

Signals worth recording:

| Signal | Purpose |
| --- | --- |
| Public edge receives forbidden inbound identity headers | Detect spoofing attempts or unmigrated clients |
| Auth 401 by route class | Track missing/invalid tokens and credential misuse |
| AuthZ 403 by route class | Detect missing role/scope/tenant permissions |
| Requests reaching Gateway from non-trusted-proxy IPs | Detect bypass paths or misconfigured LBs |
| Count of requests with duplicate identity headers | Detect header pollution/casing conflicts |
| Mismatched forwarded Host/Proto vs trusted ingress | Detect host/scheme spoofing |
| Backend rejects service identity/token | Detect bypasses, mTLS failures, or broken delegation |
| Route revisions and `trusted-proxies` changes | Audit control plane and trust configuration |

Never log raw bearer tokens, cookies, spoofed `X-User-Id` values, full queries with secrets, or client IPs where disallowed. Audit events should carry an **edge-generated/normalized correlation ID**, route ID, violation type, status, and verified source hop under an approved retention policy.

Meter labels must use bounded-cardinality categories. Never create a separate meter per token, user, or IP due to high cardinality and data leakage.

### 16.5. CORS Does Not Stop curl or Service-to-Service Clients

Setting:

~~~http
Access-Control-Allow-Origin: https://portal.example.test
~~~

enforces browser CORS rules only when the client is a browser. It **does not stop curl** from sending `X-User-Id: admin`, nor does it protect directly reachable backends. Never treat a CORS allowlist as anti-spoofing or authentication; JWT/mTLS/network policies remain mandatory.

## 17. Misconceptions to Catch in Code Reviews

**A — "Headers starting with X-Verified are trustworthy."**

False. Header names are plain HTTP data; any connected client can send the exact same name. Trust only authenticated sources and protected network paths.

**B — "Having a Gateway RemoveRequestHeader filter makes other controllers safe too."**

Not by default. Gateway filters run for **selected routes**; local controllers, Actuator, and WebFilters have different lifecycles. To cover the whole WebFlux app, add an early `WebFilter` and edge scrubbing.

**C — "Setting `trusted-proxies: '.*'` trusts every legitimate proxy."**

In regex terms, that is overly broad trust-all. Never use it on public paths; restrict the pattern to approved sources and test on topologies with verified proxies.

**D — "`XForwardedRemoteAddressResolver.trustAll()` picks the most accurate first IP."**

No. The first address can be forged by the client. Use `maxTrustedIndex` matching your chain and ensure ingress strips/overwrites untrusted data.

**E — "`maxTrustedIndex(2)` means two hops are automatically safe."**

Not automatically. It is valid only when those two hops are verified and clients cannot connect directly or inject unscrubbed XFF entries.

**F — "Gateway already verified the JWT, so the backend can trust X-User-Id."**

Not if the backend still has direct access paths, or if the header wasn't regenerated from a verified principal. Only properly audience-scoped tokens or mTLS service identity + verified metadata establish a trusted contract.

**G — "`Host=admin.example.test` grants admin privileges."**

False. Host is a route predicate/virtual-hosting signal; clients can spoof it if ingress does not restrict it. Separate authentication and authorization are required.

**H — "TLS at the public edge protects every hop."**

No. Gateway→backend still faces sniffing/spoofing/bypass risks on internal networks; enforce mTLS, security groups, or NetworkPolicies per threat model.

**I — "Just deleting X-Forwarded-For at Gateway fixes everything."**

No. Deleting valid metadata without regenerating it deprives backends of needed IP/proto context. Design the policy at the **trusted ingress**, verify every hop, and forward only genuinely required fields.

**J — "The backend returned 200 after adding an auth header, so security works."**

No. You need negative tests with forged identities, wrong issuers/audiences/scopes, duplicate headers, and direct backend access. A 200 response only shows one request succeeded.

## 18. Troubleshooting When Headers Are Spoofed or Stripped by Mistake

| Symptom | Likely cause | Check step |
| --- | --- | --- |
| Backend still sees `X-User-Id: admin` | Scrub WebFilter didn't run, different route filter, or bypassed Gateway | Handler mapping, filter ordering, recorded backend request |
| `X-Verified-Subject` becomes `attacker` | Client header passed through or bridge read client header | Trace claim source, check WebFilter/GlobalFilter |
| Two values for `X-Verified-Subject` | Used `AddRequestHeader`/multiple writers | Use remove+set from principal, check order |
| Backend misses verified subject despite valid JWT | Filter order, route ID != `orders-protected`, or removed after bridge | Route ID, GlobalFilter order, downstream capture |
| Gateway returns 401 for valid JWT | Wrong issuer/JWKS, expired/not-before, audience validator, no auth context | Redacted Security logs, test-env token claims |
| Gateway returns 403 | Missing `SCOPE_orders.read` or different Security matcher | Check authorities and role/scope mapping |
| JWT has scope, yet backend returns 403 | Backend resource-level policy/tenant ownership | Backend authorization logs; never bypass checks |
| Direct backend access succeeds | Service exposed or NetworkPolicy unenforced | Ports/Services/Ingress, security groups, mTLS |
| Changing XFF changes rate limiter key | Limiter uses untrusted XFF/header | Switch to authenticated principal/trusted resolver |
| `RemoteAddr` shows only ingress IP | That is the remote TCP peer, not end-user IP | Topology, resolver, trust chain |
| `maxTrustedIndex` picks a spoofed IP | Hop count wrong or edge failed to scrub | Captured chain and real network source |
| `trusted-proxies` regex fails to match | Bad escaping/IPv6/port/casing or wrong namespace | Configuration metadata, effective properties |
| Backend receives client `X-Forwarded-Host` | Edge appended/forwarded without overwriting | Ingress config, spoofed Host tests |
| OAuth redirect points to HTTP while public uses HTTPS | Forwarded proto mishandled | TLS termination, forwarded strategy, allowed public base URL |
| OAuth redirect points to unknown domain | Trusted untrusted X-Forwarded-Host/Host | Canonical host allowlist, edge reset |
| Enabling RemoveRequestHeader makes backend always 401 | Backend previously relied on spoofed header or token stripped wrongly | Migration contract, token audience, backend AuthZ |
| CORS preflight returns 403 | OPTIONS and Security/CORS policy misaligned | Preflight policy, actual GET tests; never open auth blindly |
| HTTP 502 after enabling mTLS | Wrong cert, truststore, SNI, or client identity | TLS handshake diagnostics, SAN/issuer/rotation |
| New route bypasses global identity policy | Used route-only filters or unguarded fallback | Default filters/WebFilter, route inventory, tests |
| Management Actuator leaks route info | Endpoint publicly exposed | Management port/NetworkPolicy/RBAC |

### 18.1. Investigating a Suspected Spoofed Request

1. **Identify real connection source** to Gateway: was the socket peer an approved ingress?
2. **Inspect ingress scrubbing**: which headers were stripped/overwritten, and does the trusted proxy chain have the right hop count?
3. **Verify authentication**: token signature, issuer/audience, expiry, and granted authorities.
4. **Inspect WebFilters**: were client identity headers stripped before other handlers?
5. **Check Gateway route ID and filter order**: did the request hit the right route and did the bridge execute?
6. **Inspect downstream recordings**: which headers did the backend receive, and were there duplicates?
7. **Inspect the backend channel**: is direct access blocked, and is the mTLS principal right?
8. **Verify resource authorization**: does the user/tenant actually own the object?
9. **Check versions**: WebFlux 4.x/5.x, Servlet/Web MVC, Spring Security, ingress/controller versions.
10. **Re-run negative tests** after fixing and record the revision for rollback.

Never remove authentication, delete NetworkPolicies, or set `trusted-proxies: '.*'` just "to make tests pass." Doing so turns a misconfiguration into a vulnerability.

### 18.2. Incident Runbook When Identity Spoofing Is Suspected

1. Block suspected public/direct access paths to Gateway/backend using a rollback-capable policy.
2. Pause routes or features relying on plain headers while preserving logs/audit evidence per procedure.
3. Inspect logs and backend access traces to identify every request using spoofed headers rather than guessing from one sample.
4. If tokens/credentials may be exposed, rotate/revoke them per IdP playbook.
5. Fix edge scrubbing, Gateway WebFilters/filters, trusted proxy settings, and backend auth contracts.
6. Audit all replicas/route definition sources and side paths like NodePorts, port-forwards, and sidecars.
7. Run the negative suite from **Internet, trusted ingress, and internal network**; verify mTLS/NetworkPolicy.
8. Monitor auth failures, suspicious forwarding metadata, route changes, and downstream violations post-rollout.

Never paste raw JWTs/cookies or personal data into unapproved tickets/chats. Report impact strictly from evidence, separating weak configuration from confirmed exploitation.

## 19. Pre-Production Security Hardening Checklist

### 19.1. Edge and Network

- [ ] Only **approved public ingress/edge** can connect to the Gateway application listener.
- [ ] Backend accepts requests solely from Gateway workload/service identity, with zero direct Internet/NodePort/LoadBalancer bypasses.
- [ ] Firewalls/security groups/NetworkPolicies cover both IPv4 and IPv6.
- [ ] Public edge TLS has valid certificates, hostname validation, and rotation.
- [ ] Gateway→backend uses mTLS/TLS and service authorization where required by threat model.
- [ ] Gateway Actuator write endpoints are unexposed; management listener sits on an isolated network with RBAC.
- [ ] Sidecars, port-forwards, debugging Services, and NAT paths audited.

### 19.2. Headers and Proxy Trust

- [ ] Edge strips inbound `X-User-Id`, `X-Role`, `X-Tenant-Id`, `X-Authenticated-User`, and organization-defined identity claims.
- [ ] Policy covers alternate/legacy identity header names, including case variants, duplicates, and underscore variants.
- [ ] All Gateway Server routes strip disallowed headers before downstream forwarding.
- [ ] If the app hosts WebFlux controllers outside routes, a `WebFilter` or equivalent protects every handler.
- [ ] No downstream route filter accidentally appends or strips verified identities incorrectly.
- [ ] `Forwarded` and `X-Forwarded-*` are created/canonicalized strictly by trusted edge; raw client values never trusted.
- [ ] `trusted-proxies` is tightly scoped, never `.*`, and uses the right Gateway WebFlux/Web MVC namespace.
- [ ] `x-forwarded.*-append` matches design, verified by inspecting actual downstream headers.
- [ ] If using `maxTrustedIndex(n)`, n matches verified hop count; `trustAll()` never used for untrusted clients.
- [ ] `RemoteAddr` and `XForwardedRemoteAddr` never mistaken for authentication/roles.
- [ ] `Host`/`X-Forwarded-Host`/`X-Forwarded-Proto` validated before generating redirects, callback URLs, or tenant routing.

### 19.3. Identity and Authorization

- [ ] Spring Security Resource Server validates signatures/keys, issuer, expiry/not-before, audience, and token policy.
- [ ] Scopes/roles mapped solely from validated authentication context, never client headers.
- [ ] Zero overly broad `permitAll()` or fallback routes outside policy.
- [ ] Gateway never emits `X-Verified-Subject` from client-controlled paths/queries/headers.
- [ ] When forwarding internal headers, backend verifies Gateway workload identity/channel and rejects direct calls.
- [ ] Backend-audience tokens or token exchange preferred when delegated authorization is needed.
- [ ] Backend always checks resource ownership/tenant permissions on real data.
- [ ] RateLimiter/KeyResolver uses authenticated principals or verified IP sources.
- [ ] CSRF/cookies/sessions and CORS match client types; CORS never treated as authentication.

### 19.4. Testing and Operations

- [ ] Positive tests with valid scoped tokens and negative tests for missing/wrong issuer/audience/scope.
- [ ] Tests for `X-User-Id: admin`, `X-Role: admin`, duplicated `X-Verified-Subject`, and case-insensitive header names.
- [ ] Backend stub confirms **client headers vanish** and verified claims (if enabled) match the subject.
- [ ] Network bypass tests from public subnet directly to Gateway/backend confirmed blocked.
- [ ] XFF spoofing tests run through real Ingress alongside trusted proxy chain tests.
- [ ] Tests confirm spoofed `X-Forwarded-Host`/Proto cause no open redirects or wrong-origin URLs.
- [ ] Tests confirm fallback/dynamic routes never bypass security/filter policies.
- [ ] Security event auditing by route class and alerts on proxy-trust drift.
- [ ] Raw Authorization/Cookies/PII or full forwarded chains never logged into metric labels.
- [ ] Rollback revisions/approvals required for edits to `trusted-proxies`, filters, and destination URIs.
- [ ] Re-verified after every Gateway BOM, Spring Security, Ingress/CDN, or network topology change.

## 21. Self-Check Questions

**1. Why is stripping `X-User-Id` at the Gateway still insufficient to secure the backend?**

Because the backend might be called directly via another path, or another Gateway handler/filter might read the header before it is stripped. You need edge scrubbing, network/mTLS trust, authentication, and backend authorization.

**2. Does `SetRequestHeader=X-Verified-Subject,admin` create a verified identity?**

No. It merely sets a constant string. Identity must come from an authenticated token/session or trusted identity mechanism.

**3. Is `spring.cloud.gateway.server.webflux.trusted-proxies` a CIDR firewall?**

No. Per Gateway docs, it is a **Java regex** governing `Forwarded`/`XForwarded` header filters. Firewalls/NetworkPolicies are separate mechanisms and cannot be replaced by this regex.

**4. Why shouldn't you pick the leftmost address in `X-Forwarded-For`?**

Because clients can prepend their own first address if the trusted edge fails to reset it. `trustAll()` risks spoofing; verify hops/chains and use an appropriate resolver.

**5. Why can `maxTrustedIndex(2)` also be wrong?**

Because 2 is safe only if the topology genuinely has those exact trusted hops and no bypass paths. When the chain has fewer elements or carries unscrubbed client entries, it picks the wrong IP.

**6. How do `WebFilter` and `GatewayFilter` differ for this purpose?**

`WebFilter` is a broader pre-handler WebFlux filter capable of sanitizing inbound requests even for controllers; `GatewayFilter` belongs to the **selected route** chain and controls per-route downstream requests.

**7. Why verify `aud` even when a JWT signature is valid?**

Because the token could have been issued for a different service. Audience binds whether the token is intended for the target application/backend.

**8. What value should a rate limiter use to identify a user?**

An authenticated principal or verified tenant key; never client-supplied `X-User-Id` or unverified XFF.

**9. Does mTLS between Gateway and backend automatically authorize users to read every order?**

No. mTLS authenticates the service workload, whereas end-user permissions require token/claims verification and resource-level authorization.

**10. Does a request with an admin Host returning HTTP 200 prove the trust boundary is sound?**

No. You must inspect which route actually matched, JWT/scope/tenant policies, downstream headers, trusted ingress, and backend bypass resistance.

**Remember:** In Spring Cloud Gateway, **never treat client-supplied `X-User-Id`, `X-Role`, `X-Tenant-Id`, or `X-Forwarded-For` as proof of identity or authority**. Strip dangerous headers at the **trusted edge** and inside the Gateway, validate JWTs/sessions with issuer/audience/scope checks, and emit internal metadata solely from a **verified principal** over a protected Gateway→backend channel. `trusted-proxies` and `maxTrustedIndex` are meaningful only across a **verified proxy chain with no bypass paths**. Success means negative tests prove every spoofed header is stripped, backends cannot be called directly, and resource permissions remain enforced—not merely seeing one valid request return HTTP 200.
