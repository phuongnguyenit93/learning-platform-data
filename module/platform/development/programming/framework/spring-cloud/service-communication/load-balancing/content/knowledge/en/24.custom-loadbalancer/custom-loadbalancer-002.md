# Writing a ServiceInstanceListSupplier for a Custom Instance Source

When using Spring Cloud LoadBalancer, the `ServiceInstance` list is typically fetched from a `DiscoveryClient` (Eureka, Consul, Kubernetes, or a compatible discovery mechanism). However, some systems use a **custom instance list source**: an internal topology management API, data generated by a control plane, a specialized inventory service, or a dynamic list provided by a system without `DiscoveryClient` integration.

Instead of writing an entirely new load-balancing algorithm, you can implement **`ServiceInstanceListSupplier`** to transform data from your custom source into a `List<ServiceInstance>`. Spring Cloud LoadBalancer still handles **picking an instance** from that list (for example, Round Robin), while RestClient, WebClient, or OpenFeign continues calling by **service ID**.

This lesson belongs to the **Customizing LoadBalancer** chapter of the **SPRING_CLOUD_SERVICE_COMMUNICATION_LOAD_BALANCING** module. The goal is to understand the `ServiceInstanceListSupplier` contract, write a supplier that fetches instances over HTTP, register it in a per-service-ID context, enforce data quality, and handle caching/health checks, timeouts, retries, and observability. Examples use Java 17+, compatible Spring Boot/Spring Cloud versions, and an HTTP source **independent of LoadBalancer**.

> **Boundary of responsibility:** `ServiceInstanceListSupplier` provides the **candidate set**, and does not itself decide which single instance is chosen for a request. If you only want to replace Round Robin with another selection policy, consider customizing `ReactorServiceInstanceLoadBalancer` rather than placing single-instance selection logic inside the supplier.

## 1. When Do You Need a Custom ServiceInstanceListSupplier?

A custom source might be:

- An internally built management API storing replicas currently permitted to receive traffic.
- A service deployment control plane without a `DiscoveryClient` adapter.
- An endpoint returning topology by environment, cluster, region, or version.
- An instance list normalized from multiple inventory systems.
- A source containing extra attributes such as `zone`, `weight`, and `version` without existing Spring Cloud Discovery integration.

**No custom supplier is needed** if a suitable `DiscoveryClient` already exists and you only want to filter instances by zone, health, request hint, or weight: Spring Cloud provides built-in suppliers/decorators for those purposes. Avoid creating a secondary data source if your current registry is already a trusted source of truth.

### An Architectural Question

If a system has hundreds of services, a custom `DiscoveryClient` may be better when you want all Spring Cloud Discovery consumers to use the new source. A **custom `ServiceInstanceListSupplier`** is a better fit when only specific **LoadBalancer clients** need custom topology, or when you want to scope changes strictly to a given service ID.

| Criterion | Custom DiscoveryClient | Custom ServiceInstanceListSupplier |
|---|---|---|
| Scope | General integration into the discovery abstraction | Serves candidate provisioning for LoadBalancer |
| Reusability in other components | Usable by many DiscoveryClient consumers | Primarily inside the LoadBalancer supplier chain |
| Per-service-ID scoping | Via discovery logic or configuration | Easy with `@LoadBalancerClient(name=...)` |
| Data source | Custom registry or discovery system | Registry, API, snapshot, or aggregator |
| Does it make Round Robin decisions? | No | No |

## 2. Processing Flow from Custom Source to HTTP Client

~~~mermaid
flowchart LR
    S["Topology API / custom instance source"] --> F["Custom ServiceInstanceListSupplier"]
    F --> C["Optional cache / health / zone / weight decorators"]
    C --> LB["RoundRobinLoadBalancer or another policy"]
    LB --> I["Select ServiceInstance"]
    I --> HTTP["RestClient / WebClient / OpenFeign"]
    HTTP --> B["Actual instance host:port"]

    Caller["Caller requests http://catalog-service/..."] --> LB
~~~

The relationship can be summarized as:

1. The caller creates an HTTP request with the logical URL `http://catalog-service/api/items/42`.
2. Spring Cloud LoadBalancer receives the service ID `catalog-service`.
3. The supplier returns the **candidate list** for that ID.
4. The instance selection policy picks a valid element.
5. The HTTP client connects to the real host/port of the chosen instance.
6. The response or exception is returned to the caller; the supplier does not replace HTTP client status/timeout handling.

**One HTTP request does not necessarily trigger a new network query to the topology API:** that depends on caching, refresh behavior, and supplier implementation. Without caching, a supplier making an HTTP call on every selection can become a bottleneck.

## 3. Core Contract of ServiceInstanceListSupplier

The interface resides in package:

~~~java
org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier
~~~

Two methods to understand:

~~~java
String getServiceId();

Flux<List<ServiceInstance>> get();
~~~

The API also includes a method accepting request context such as `get(Request request)` for suppliers whose logic depends on the request. This lesson builds a **request-independent** supplier, so implementing `get()` and `getServiceId()` per the current interface is sufficient.

**The key detail is the return type `Flux<List<ServiceInstance>>`, not `Flux<ServiceInstance>`.**

~~~text
Correct: onNext([A, B, C])      -> one candidate list snapshot
Wrong:   onNext(A), onNext(B)   -> individual elements
~~~

A subscription may emit one list and complete; another supplier may emit multiple lists as the topology source changes. For our hands-on example, **each subscription emits one snapshot and completes**.

| Value/signal | Meaning to understand |
|---|---|
| `Flux.just(List.of(A, B))` | Two candidates available |
| `Flux.just(List.of())` | Valid snapshot with zero candidates |
| `Flux.error(ex)` | Failed to fetch or validate snapshot |
| `Flux.empty()` | Publisher completed **without emitting any snapshot** |
| `Flux.never()` | Emits nothing and never completes; can hang selection |

Do not arbitrarily replace `Flux.just(List.of())` with `Flux.empty()`: "having an empty snapshot" and "having no snapshot" are not identical signals to all consumers.

### What Does ServiceInstance Contain?

At a minimum, a `ServiceInstance` carries these essential details:

- `getServiceId()`: logical name, must match `catalog-service`.
- `getInstanceId()`: stable identifier within the contract scope.
- `getHost()` and `getPort()`: where HTTP requests are sent.
- `isSecure()` / `getUri()`: protocol and URL information.
- `getMetadata()`: metadata map such as zone, weight, version.

You can use `DefaultServiceInstance` to map data instead of writing a full custom `ServiceInstance` implementation.

  "instances": [

      "id": "catalog-a",

      "port": 18081,
      "secure": false,

      "secure": false,
      "zone": "zone-b",

    }

This is an **illustrative JSON contract**, not a standard Eureka/Kubernetes format. The team operating the custom topology API is responsible for access control, data freshness, and instance status semantics.

In the lab:

| Component | Address | Role |
|---|---|---|
| Topology API | `127.0.0.1:18100` | Provides list snapshots |

**Use loopback HTTP only for the lab.** In production, the registry source must be authenticated, encrypted, and authorized, and instance addresses must be validated by an independent policy; never take URIs directly from user input to establish connections.

### Decoupling the Source Abstraction from the HTTP Client

~~~java
package demo.lbconfig;

import reactor.core.publisher.Mono;

@FunctionalInterface
public interface InstanceDirectory {
    Mono<DirectorySnapshot> find(String serviceId);
}
~~~

Benefit of this small interface: the supplier does not need to know whether data comes from HTTP, a database, or a mock; it only needs a `Mono<DirectorySnapshot>`. Unit tests can supply a fake `InstanceDirectory` without starting a web server.

## 7. Calling the Custom Source with a **Non**-Load-Balanced WebClient

A design mistake that easily causes a loop is creating the WebClient for the topology API from a `@LoadBalanced WebClient.Builder`, while LoadBalancer itself relies on the supplier to resolve the topology API target.

~~~mermaid
flowchart TD
    A["Caller needs catalog-service"] --> B["LoadBalancer selects instance"]
    B --> C["Custom supplier calls topology API"]
    C --> D{"Does topology API also go through the same LoadBalancer?"}
    D -->|Yes, misconfigured| E["Risk of recursive lookup with no data to choose from"]
    D -->|No, uses direct client| F["Read list and return ServiceInstance"]
    F --> B
~~~

Use a **direct** WebClient with a fixed, trusted base URL for the control plane:

~~~java
package demo.lbconfig;

import java.time.Duration;

import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

public final class HttpInstanceDirectory implements InstanceDirectory {

    private final WebClient webClient;

    public HttpInstanceDirectory(WebClient webClient) {
        this.webClient = webClient;
    }

    @Override
    public Mono<DirectorySnapshot> find(String serviceId) {
        return webClient.get()
            .uri("/api/v1/services/{id}/instances", serviceId)
            .retrieve()
            .bodyToMono(DirectorySnapshot.class)
            .switchIfEmpty(Mono.error(
                new IllegalStateException("Empty topology response")
            ))
            .timeout(Duration.ofSeconds(2));
    }
}
~~~

This mechanism returns a publisher and does not block threads with `block()`. Nor does it retry indefinitely when the topology API fails. In production, configure appropriate connection pools, connect timeouts, TLS identity, client authentication, response size limits, and deadlines.

**Avoid writing:**

~~~java
// Do not do this inside get() of a reactive supplier:
DirectorySnapshot snapshot = directory.find(serviceId).block();
~~~

Calling `block()` inside a reactive pipeline can stall the event loop or cause deadlocks. Use Reactor operators to map the list rather than switching to blocking just because data normalization feels more convenient.

## 8. Writing the Supplier to Map Custom Instances to ServiceInstance

Implement `CatalogDirectorySupplier` in the same `demo.lbconfig` package:

~~~java
package demo.lbconfig;

import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Objects;
import java.util.Set;

import org.springframework.cloud.client.DefaultServiceInstance;
import org.springframework.cloud.client.ServiceInstance;
import org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier;

import reactor.core.publisher.Flux;

public final class CatalogDirectorySupplier
        implements ServiceInstanceListSupplier {

    public static final String SERVICE_ID = "catalog-service";

    private final InstanceDirectory directory;

    public CatalogDirectorySupplier(InstanceDirectory directory) {
        this.directory = Objects.requireNonNull(directory);
    }

    @Override
    public String getServiceId() {
        return SERVICE_ID;
    }

    @Override
    public Flux<List<ServiceInstance>> get() {
        return Flux.defer(() ->
            directory.find(SERVICE_ID)
                .map(this::validateAndConvert)
                .flux()
        );
    }

    private List<ServiceInstance> validateAndConvert(
            DirectorySnapshot snapshot) {

        if (snapshot == null
                || !SERVICE_ID.equals(snapshot.serviceId())
                || snapshot.instances() == null) {
            throw new IllegalArgumentException(
                "Invalid catalog-service snapshot");
        }

        Set<String> seenIds = new HashSet<>();
        List<ServiceInstance> result = new ArrayList<>();

        for (DirectoryNode node : snapshot.instances()) {
            if (!allowedInLab(node)) {
                // In production, record a safe metric/audit event here.
                continue;
            }

            if (!seenIds.add(node.id())) {
                throw new IllegalArgumentException(
                    "Duplicate instance ID in snapshot");
            }

            DefaultServiceInstance instance = new DefaultServiceInstance(
                node.id(),
                SERVICE_ID,
                node.host(),
                node.port(),
                node.secure()
            );

            instance.getMetadata().put("zone", node.zone());
            instance.getMetadata().put(
                "weight", Integer.toString(node.weight())
            );

            result.add(instance);
        }

        return List.copyOf(result);
    }

    private static boolean allowedInLab(DirectoryNode node) {
        return node != null
            && node.id() != null
            && !node.id().isBlank()
            && "127.0.0.1".equals(node.host())
            && (node.port() == 18081 || node.port() == 18082)
            && !node.secure()
            && node.zone() != null
            && Set.of("zone-a", "zone-b").contains(node.zone())
            && node.weight() >= 1
            && node.weight() <= 100;
    }
}
~~~

### Why Choose This Implementation Style?

- `getServiceId()` returns the exact service ID that LoadBalancer will request.
- `get()` returns `Flux<List<ServiceInstance>>`, emitting **one snapshot** per successful subscription.
- `Flux.defer(...)` creates a fresh lookup stream on each subscription rather than reusing fixed data captured at bean initialization.
- `validateAndConvert(...)` verifies the snapshot matches the right service ID, the list is non-null, disallowed nodes are dropped, and duplicate IDs are rejected.
- `DefaultServiceInstance` provides a ready-made `ServiceInstance` implementation, avoiding reimplementing `getUri()`, `getHost()`, `getPort()`, etc.
- `List.copyOf(result)` returns an unmodifiable list at the collection level; do not mutate `DefaultServiceInstance` metadata after publishing the snapshot.
- When both backends are excluded, the result is an **empty list** rather than attempting to connect to an out-of-policy host.

**This allowlist policy is strictly for the lab**: loopback host, ports 18081/18082, and HTTP. Production must replace it with source identity verification, trust policy, endpoint/network egress rules, and proper TLS/mTLS instead of hardcoding localhost.

### Cases That Must Not Be Masked

If the source returns `serviceId=payment-service` instead of `catalog-service`, the code emits an error. If the snapshot is malformed or has duplicate IDs, the code emits an error rather than picking arbitrarily. However, if the source returns a **valid empty array**, the supplier emits `List.of()` so LoadBalancer knows there are no candidates.

**A registry outage is different from "healthy registry with zero instances."** `Flux.error(...)` from the directory should not be turned into an empty list without metrics/alerts, as the two cases require different operational responses.

## 9. Registering the Supplier in the Per-Service-ID LoadBalancer Context

Spring Cloud supports service-specific configuration via `@LoadBalancerClient`. Create the configuration class in package `demo.lbconfig`, **outside the default component scan scope** of the caller application in package `demo.caller`.

~~~java
package demo.lbconfig;

import org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.client.WebClient;

@Configuration(proxyBeanMethods = false)
public class CatalogLoadBalancerConfiguration {

    @Bean
    ServiceInstanceListSupplier catalogInstanceSupplier() {
        // Dedicated control-plane client, NOT @LoadBalanced.
        WebClient plainDirectoryClient = WebClient.builder()
            .baseUrl("http://127.0.0.1:18100")
            .build();

        InstanceDirectory directory =
            new HttpInstanceDirectory(plainDirectoryClient);

        return new CatalogDirectorySupplier(directory);
    }
}
~~~

**Important:** the URL `127.0.0.1:18100` is the fixed endpoint of the topology API in the **lab**. In production, load the URL from trusted configuration, use HTTPS/TLS with identity verification, dedicated credentials, and appropriate circuit breakers/timeouts. Never let arbitrary user input decide the source URL.

Bind the configuration to the right service:

~~~java
package demo.caller;

import demo.lbconfig.CatalogLoadBalancerConfiguration;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.loadbalancer.annotation.LoadBalancerClient;

@SpringBootApplication
@LoadBalancerClient(
    name = "catalog-service",
    configuration = CatalogLoadBalancerConfiguration.class
)
public class OrderApplication {

    public static void main(String[] args) {
        SpringApplication.run(OrderApplication.class, args);
    }
}
~~~

When caller code requests `catalog-service`, the corresponding LoadBalancer context uses the `ServiceInstanceListSupplier` bean provided by this configuration class.

### Notes on Component Scanning

A `@Configuration` registered into the shared application context can cause the same supplier to be applied more broadly than intended. Therefore you should:

- Place `CatalogLoadBalancerConfiguration` outside the package tree scanned by `@SpringBootApplication`.
- Or, following Spring Cloud guidance, omit `@Configuration` if your registration approach supports it.
- Verify that the target service ID actually uses the custom supplier while other service IDs retain their default suppliers.
- Avoid creating multiple `ServiceInstanceListSupplier` beans with ambiguous precedence inside the same LoadBalancer child context.

Exact bean/context creation capabilities depend on the release train; the code above uses the standard `@LoadBalancerClient` configuration pattern.

## 10. Creating a RestClient Caller That Calls by Service ID

Once the supplier is registered, business code does not need to know whether discovery comes from Eureka or a topology API:

~~~java
package demo.caller;

import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.cloud.client.loadbalancer.LoadBalanced;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;

@Configuration(proxyBeanMethods = false)
class CatalogHttpClientConfiguration {

    @Bean
    @LoadBalanced
    RestClient.Builder loadBalancedRestClientBuilder() {
        return RestClient.builder();
    }

    @Bean
    RestClient catalogRestClient(
        @Qualifier("loadBalancedRestClientBuilder")
        RestClient.Builder builder
    ) {
        return builder.baseUrl("http://catalog-service").build();
    }
}
~~~

Create an illustrative endpoint:

~~~java
package demo.caller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.client.RestClient;

@RestController
class CatalogCallerController {

    private final RestClient catalogRestClient;

    CatalogCallerController(RestClient catalogRestClient) {
        this.catalogRestClient = catalogRestClient;
    }

    @GetMapping("/demo/whoami")
    String whoami() {
        return catalogRestClient.get()
            .uri("/api/whoami")
            .retrieve()
            .body(String.class);
    }
}
~~~

The logical request `GET http://catalog-service/api/whoami` passes through Spring Cloud LoadBalancer. The supplier returns A/B; LoadBalancer picks an instance and RestClient sends the request to `127.0.0.1:18081` or `127.0.0.1:18082`.

**Do not create `RestClient.create("http://catalog-service")` directly** expecting the custom supplier to be used: that client does not receive `@LoadBalanced` integration.

### WebClient and OpenFeign Can Also Use the Same Supplier

For WebClient, create a `@LoadBalanced WebClient.Builder` and a client with base URL `http://catalog-service`. For OpenFeign, use `@FeignClient(name = "catalog-service")` with compatible Spring Cloud LoadBalancer integration.

~~~java
@FeignClient(name = "catalog-service")
interface CatalogFeignClient {

    @GetMapping("/api/whoami")
    String whoami();
}
~~~

The Feign example requires `spring-cloud-starter-openfeign` and `@EnableFeignClients` when used; this is an **alternative** to the RestClient demo, not a requirement to enable both. All three clients can obtain candidates from the supplier for that service ID when integration is properly configured.

## 12. Setting Up the Independent Topology API

Another Spring Boot application serves the JSON snapshot. You can copy the `DirectorySnapshot` and `DirectoryNode` DTOs (with identical JSON structure) into this module or use a shared, explicitly versioned API contract.

~~~java
package demo.directory;

import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

record DirectoryNode(
    String id, String host, int port,
    boolean secure, String zone, int weight
) {}

record DirectorySnapshot(
    String serviceId, List<DirectoryNode> instances
) {}

@RestController
@RequestMapping("/api/v1/services")
class LabDirectoryController {

    @GetMapping("/{serviceId}/instances")
    DirectorySnapshot instances(@PathVariable String serviceId) {
        if (!"catalog-service".equals(serviceId)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND);
        }

        return new DirectorySnapshot(
            serviceId,
            List.of(
                new DirectoryNode(
                    "catalog-a", "127.0.0.1", 18081,
                    false, "zone-a", 50
                ),
                new DirectoryNode(
                    "catalog-b", "127.0.0.1", 18082,
                    false, "zone-b", 50
                )
            )
        );
    }
}
~~~

Assuming the topology backend is built into `topology-directory.jar` with `@SpringBootApplication`:

~~~bash
java -jar topology-directory.jar --server.port=18100
~~~

Verify the endpoint:

~~~bash
curl -i http://127.0.0.1:18100/api/v1/services/catalog-service/instances
~~~

**Do not host the topology API behind the very `catalog-service` it is resolving** if that creates a circular dependency or prevents discovery recovery. In the lab, the topology API uses a fixed local address separate from the backend instance list.

## 13. Verifying Requests Are Distributed per the Snapshot

After starting:

1. Two backends on 18081/18082.
2. Topology API on 18100.
3. Caller `OrderApplication` on 18090 (via `--server.port=18090` or `application.yml`).
4. Custom supplier bound via `@LoadBalancerClient(name = "catalog-service", ...)`.

Send multiple calls:

~~~bash
for i in $(seq 1 12); do
  curl -s http://127.0.0.1:18090/demo/whoami
  echo
done
~~~

Expected: responses show `instanceId=catalog-a` and `instanceId=catalog-b` while the list is stable and Round Robin is active.

This demonstrates behavior, **not a guarantee that every run alternates A/B strictly turn by turn**: multiple callers, retries, list updates, or other policies can influence the sequence.

### Changing the Topology

Modify the topology API response to return only A, then test again. Because the baseline supplier does not cache, new subscriptions receive the updated snapshot. If caching is enabled, you must wait for cache refresh or use an appropriate invalidation mechanism.

Try adding a node on port 18083 or an unfamiliar host to the snapshot: `allowedInLab(...)` will exclude it. If all nodes are invalid, the supplier returns an empty list; the caller must handle the case where no instance can be selected.

## 14. Custom Source Failures: No Instances vs. Failed Fetch

Three situations must be distinguished:

| Situation | Signal in demo supplier | Meaning |
|---|---|---|
| API returns valid snapshot with A/B | `Flux.just(List.of(A,B))` equivalent | Candidates available |
| API returns valid snapshot with `instances=[]` | `Flux.just(List.of())` equivalent | No candidates |
| API times out, returns 5xx, or invalid JSON | `Flux.error(exception)` | Unable to fetch/verify source |

Example of **what not to do**:

~~~java
@Override
public Flux<List<ServiceInstance>> get() {
    return directory.find(SERVICE_ID)
        .map(this::validateAndConvert)
        .onErrorReturn(List.of())    // Do not mask all source errors as 0 instances
        .flux();
}
~~~

Why? A topology API outage could be misreported as "no healthy backends." During incident triage, these two cases require different alerts and remediation steps.

### Fail Closed or Retain the Last Snapshot?

In some systems, when the topology API fails, a **last-known-good snapshot** may be used briefly if policy permits. However, this is an **availability and security trade-off**, not a default fallback:

- There must be a TTL and maximum snapshot age.
- Instances may have been revoked or had permissions changed; stale data poses risks.
- If no valid snapshot remains or it has expired, fail closed.
- When fallback occurs, metrics/alerts must distinguish "using stale" from "fresh."
- Never take an unvalidated list and "try calling anyway" when data is untrusted.

For sources carrying authorization to connect, combine network egress/TLS identity controls so revocation does not depend solely on cache TTL.

## 15. Caching: Avoiding a Topology API Call per HTTP Request

The current supplier can hit the HTTP source every time LoadBalancer needs a snapshot. In high-throughput systems, this increases:

- Instance selection latency before the actual HTTP request is sent.
- Request volume against the topology API.
- Risk of the topology API becoming a hot dependency or single point of failure.
- Connection count and memory/CPU usage for control-plane lookups.

Spring Cloud LoadBalancer provides `CachingServiceInstanceListSupplier`. One pattern is **wrapping the network-fetching supplier with a cache before placing request-dependent filters**.

~~~text
CustomDirectorySupplier (queries external source)
    -> CachingServiceInstanceListSupplier (optional)
    -> Zone/Hint/Version filtering (optional)
    -> LoadBalancer selects instance
~~~

Illustrative example of wrapping a delegate with a `cacheManager` properly configured for LoadBalancer:

~~~java
import org.springframework.cache.CacheManager;
import org.springframework.cloud.loadbalancer.core.CachingServiceInstanceListSupplier;
import org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier;

// Inside the supplier configuration method:
ServiceInstanceListSupplier source =
    new CatalogDirectorySupplier(directory);

ServiceInstanceListSupplier cached =
    new CachingServiceInstanceListSupplier(source, cacheManager);
~~~

This is an **illustrative replacement** for the non-cached supplier registration in section 9, not a second automatically registered bean. A `CacheManager` compatible with LoadBalancer caching must exist in the context, and you should check constructors/APIs for your project's Spring Cloud release train.

Commonly used cache properties:

~~~yaml
spring:
  cloud:
    loadbalancer:
      cache:
        enabled: true
        ttl: 20s
        capacity: 256
~~~

The 20-second/256 values are illustrative. `capacity` in LoadBalancer configuration is **initial capacity**, not a guarantee of "at most 256 entries stored." If a custom Caffeine specification is used, that spec can override global TTL/capacity settings per current documentation.

**Mandatory note:** if your custom source SDK already caches the list internally, adding LoadBalancer caching can cause **double caching**. Each layer increases staleness duration; clarify which layer owns refresh and when revoked targets are blocked.

Do not use `ServiceInstanceListSupplier.builder().withDiscoveryClient().withCaching()` if your goal is reading from a **custom source** without a DiscoveryClient: `withDiscoveryClient()` builds a discovery-backed pipeline and will not know about `HttpInstanceDirectory` from this lesson.

## 16. Health Checks and Other Filters

This lesson only changed the **candidate source**. If you also need health checks, zone preference, weighted routing, request hints, or API versioning, design the supplier chain accordingly.

| Layer | Effect | What to verify |
|---|---|---|
| Custom source supplier | Fetches A/B list from topology API | Trust, schema, timeout, freshness |
| Cache | Reduces source queries | TTL, staleness/revocation |
| Health-check supplier | Assesses instance availability | Probe endpoint, interval, fallback |
| Zone preference | Prefers instances in the same zone | `zone` metadata supplied by trusted source |
| Weighted supplier | Influences selection ratio by weight | Do not trust unvalidated weight values |
| Request hint/version filter | Filters based on request context | Do not treat raw unchecked input as routing authorization |

Spring Cloud advises placing `CachingServiceInstanceListSupplier` or `HealthCheckServiceInstanceListSupplier` **immediately after the network-fetching supplier**, before other filtering suppliers; avoid accidentally stacking both caching and health-check in ways that create overlapping cache layers. For any concrete chain, verify constructors and delegate ordering against your release train.

**Filters do not activate automatically just because a snapshot contains metadata.** For example, putting `weight=50` into `DefaultServiceInstance.getMetadata()` **does not automatically turn Round Robin into weighted routing**; weights take effect only when `WeightedServiceInstanceListSupplier` or another policy is configured and consumes that metadata.

Health checks are not authentication either: a rogue instance can return HTTP 200. Securing the topology source, TLS identity, and egress policies must remain independent of health checks.

## 17. When Should You Customize a Request-Aware Supplier?

In this example, every request to `catalog-service` uses the same candidate list. Some systems want to filter by:

- Caller zone or tenant routing policy.
- Permitted API version/header.
- Canary cohort computed at an authenticated boundary.
- Request hint from a trusted source.

Spring Cloud provides `ServiceInstanceListSupplier.get(Request request)` for suppliers that require request context. However, **never take a raw header from the client and translate it directly into a host/port**; authorization, validation, and consistency with the supplier chain are required.

If you only need zone or weight constraints, evaluate built-in suppliers such as `ZonePreferenceServiceInstanceListSupplier` and `WeightedServiceInstanceListSupplier` first. Write a new request-aware supplier only when semantics differ clearly and fail-closed tests cover invalid request metadata.

### Do Not Put Instance Selection Inside get()

An anti-pattern:

~~~java
// Wrong responsibility: returns only a single random instance in every snapshot.
return directory.find(SERVICE_ID)
    .map(snapshot -> List.of(
        pickRandomInstance(snapshot.instances())
    ))
    .flux();
~~~

This strips candidates away from health/zone/weight layers and forces Round Robin to operate on an unintentionally narrowed list. If you need a specialized single-instance selection policy, customize the LoadBalancer policy rather than silently picking inside the source.

## 18. Timeouts, Retries, and Load Limits for Topology Lookups

An HTTP call to the topology API is a **control-plane lookup**. It needs its own bounds and should not share a business operation's deadline without accounting for total budget.

~~~mermaid
sequenceDiagram
    participant C as Caller
    participant LB as LoadBalancer
    participant S as Custom Supplier
    participant API as Topology API
    participant I as catalog instance

    C->>LB: GET catalog-service/api/whoami
    LB->>S: get()
    S->>API: GET /instances (separate deadline)
    API-->>S: A/B or error/timeout
    S-->>LB: Snapshot or error
    LB-->>C: Selected instance / error
    C->>I: Actual HTTP request if selected
    I-->>C: HTTP response
~~~

**Total elapsed time** can include topology lookup, acquiring a connection from the pool, connecting to the backend, waiting for the response, and retries. If the caller sets a 2-second deadline and topology lookup already consumed 1.8 seconds, the subsequent HTTP request should not wait another 3 seconds before even considering a retry.

A sound lookup policy needs:

1. Connect/response timeouts on the topology API's HTTP client.
2. Concurrency caps and an appropriate connection pool to protect the source.
3. Caching or snapshot refresh instead of hitting the hot registry on every request.
4. **Very limited** lookup retries when safe, with backoff and an overall deadline.
5. Clear separation between topology API outages, backend 503s, and zero-instance states.
6. A circuit breaker/limit if the source suffers prolonged failures.
7. Ensuring the lookup never uses the very `@LoadBalanced` client that depends on its snapshot.

If many callers miss the cache simultaneously, a **thundering herd** can hit the topology API. Choose caching/single-flight refresh or a push/watch mechanism with backpressure suited to your design.

## 19. Testing the Supplier Independently of the HTTP Stack

Because `InstanceDirectory` was extracted as an interface, tests can easily supply fake data.

~~~java
package demo.lbconfig;

import java.util.List;

import org.junit.jupiter.api.Test;
import reactor.core.publisher.Mono;
import reactor.test.StepVerifier;

import static org.assertj.core.api.Assertions.assertThat;

class CatalogDirectorySupplierTest {

    @Test
    void keepsOnlyAllowedInstances() {
        InstanceDirectory fake = serviceId -> Mono.just(
            new DirectorySnapshot(
                serviceId,
                List.of(
                    new DirectoryNode(
                        "catalog-a", "127.0.0.1", 18081,
                        false, "zone-a", 50
                    ),
                    new DirectoryNode(
                        "not-allowed", "127.0.0.1", 18083,
                        false, "zone-b", 10
                    )
                )
            )
        );

        var supplier = new CatalogDirectorySupplier(fake);

        StepVerifier.create(supplier.get().next())
            .assertNext(instances -> {
                assertThat(instances).hasSize(1);
                assertThat(instances.get(0).getInstanceId())
                    .isEqualTo("catalog-a");
                assertThat(instances.get(0).getServiceId())
                    .isEqualTo("catalog-service");
            })
            .verifyComplete();
    }
}
~~~

This is an illustrative test snippet, **not executed in STEP 4** under the current workflow. In later QA/build stages, you can add:

| Test case | Expected behavior |
|---|---|
| Valid A/B snapshot | Emits a list containing two instances |
| Empty snapshot | Emits an empty list |
| Snapshot with different serviceId | Error; never selects wrong host |
| Snapshot with invalid port | Excluded per policy |
| Snapshot with duplicate instanceId | Error; never selects conflicting data |
| Directory HTTP 401/403 | Source error, no blind fallback |
| Directory HTTP 500 | Error or last-good snapshot per explicit policy |
| Directory timeout | Bounded timeout error |
| JSON parse/schema failure | Error; decode metric |
| A/B changes over time | Non-cached supplier picks up new snapshot |
| Cache TTL not expired | May still return prior snapshot |
| All instances filtered out | No request sent to out-of-policy target |
| Same supplier bean name across contexts | Only target service ID is overridden |

## 20. Integration Testing: Proving the Client Uses the Custom Supplier

A passing `get()` unit test is **not enough** to prove LoadBalancer uses the right supplier.

In an integration test or lab:

1. Start the topology API on 18100 returning A/B.
2. Start backends A/B on 18081/18082.
3. Start the caller with `@LoadBalancerClient` for `catalog-service`.
4. Send multiple GET requests to `/demo/whoami`.
5. Observe that backends A/B received real requests, rather than relying only on mock outputs.
6. Update the snapshot to contain only A; verify new requests go solely to A after refresh/cache expiry.
7. Add an invalid record; verify no HTTP request is sent to an out-of-policy port.
8. Make the topology API return 503; verify the error is classified as **source unavailable**.
9. Slow down the topology API; observe lookup latency and total deadline behavior.
10. Verify another service ID still uses its own/default configuration as expected.

### Two Kinds of Logs to Distinguish

~~~text
supplier: serviceId=catalog-service candidates=2 source=topology-api
loadbalancer: serviceId=catalog-service selected=catalog-b
http-client: destination=catalog-b status=200 duration=35ms
~~~

These lines show a **target log format**, not verbatim logs emitted automatically by the framework. Avoid overusing high-cardinality event logs or logging raw metadata/credentials from the topology API.

## 21. Observing and Operating a Custom Source

A custom supplier sits on the critical path of every remote call. Measure:

| Metric / log field | Purpose |
|---|---|
| `serviceId` | Identify which candidate set is being fetched |
| Source endpoint label | Distinguish control plane from data plane |
| Lookup latency p50/p95/p99 | Detect slow topology API responses |
| Lookup success/error/timeout | Isolate source outages |
| Snapshot age / cache hit | Measure data freshness |
| Candidate count before/after validation | Spot malformed data or abnormal shifts |
| Rejected instance count/reason | Protect routing and auditing |
| Duplicate ID / schema error | Detect conflicting data sources |
| Selected instance | Compare load-balancing distribution |
| No-instance count | Distinguish valid empty snapshots |
| Downstream connect/read timeout | Separate backend faults from source faults |
| Retry attempts and deadline remaining | Prevent retry storms |
| Source circuit breaker state | Know when the control plane is isolated |

Do not put arbitrary `instanceId` values or unbounded long URLs into high-cardinality metric labels. When logging host/port, ensure sensitive topology details are not exposed to public systems.

For tracing, you can correlate three spans/operations: **list lookup**, **instance selection**, and **actual HTTP request**. An instance selection failure can happen **before any HTTP request reaches the backend**, so dashboards counting only HTTP 5xx will miss that failure mode.

## 22. Common Mistakes

1. Returning `Flux<ServiceInstance>` instead of `Flux<List<ServiceInstance>>`.
2. Returning `Flux.empty()` when the snapshot is valid but has zero candidates.
3. Calling `block()` inside a reactive supplier, stalling the event loop.
4. Using a `@LoadBalanced` client to call the topology API itself, creating a circular dependency.
5. Creating a new HTTP client on every `get()` call, losing connection pool reuse.
6. Registering custom config inside shared component scanning, affecting unintended service IDs.
7. Calling `ServiceInstanceListSupplier.builder().withDiscoveryClient()` assuming it automatically reads from a custom directory.
8. Returning only one element in the supplier because you only want one instance picked, bypassing selection algorithms.
9. Failing to validate service ID, host, port, scheme, duplicate IDs, and metadata.
10. Treating `weight/zone` metadata as proof of identity or assuming it activates weighting automatically.
11. Converting all topology API errors into an empty list without alerting.
12. Falling back indefinitely to an expired last-known-good snapshot.
13. Calling the topology API on every request at high QPS without caching or concurrency caps.
14. Stacking caching and health-check layers carelessly, increasing convergence delay.
15. Assuming the LoadBalancer cache and HTTP connection pool are the same thing.
16. Only unit-testing the supplier without proving `@LoadBalancerClient` activated it.
17. Failing to distinguish source errors, no-instance states, connect timeouts, and backend HTTP 503s.
18. Lacking network egress/TLS identity controls when using a topology source editable by multiple parties.
19. Overlooking that retries can pick a different instance, exposing stateful session/idempotency issues.
20. Lacking metrics for rejected instance counts, snapshot age, and lookup latency.

## 23. Pre-Deployment Checklist

- Have you established the **source of truth** for the instance set and who is authorized to update it?
- Does the custom supplier return the right `serviceId`, `Flux<List<ServiceInstance>>`, and valid snapshots?
- Does the source have a suitable reactive API or non-blocking client?
- Is the control-plane HTTP client **independent of the LoadBalancer** that relies on it?
- Are timeouts, pooling, concurrency, and retry budgets bounded for source lookups?
- Do you validate schema, host/port/scheme, instance IDs, zone/weight, and duplicate IDs?
- When no instances remain, does it fail closed per policy?
- When the source fails, do you distinguish errors from valid empty snapshots?
- If caching is used, have you defined TTL, refresh, stale caps, and revocation behavior?
- Is the supplier registered for the **exact service ID** and outside shared component scanning?
- Do RestClient/WebClient/OpenFeign callers actually use LoadBalancer integration?
- Are health, zone, weight, and hints/version combined in the right order with the right semantics?
- Do integration tests cover A/B topology changes, source outages, and invalid records?
- Are lookup latency, rejected candidates, and selected instances observable?
- In production, do registry/metadata have TLS, RBAC, and network egress controls?

## 24. Conclusion

**`ServiceInstanceListSupplier` is the right extension point when Spring Cloud LoadBalancer must fetch `ServiceInstance` entries from a custom source.** The custom supplier is responsible for **fetching, converting, validating, and emitting the candidate list**; LoadBalancer continues selecting instances according to policy, and the HTTP client executes requests by service ID. The `CatalogDirectorySupplier` example shows how to return a `Flux<List<ServiceInstance>>` from an independent topology API and use `@LoadBalancerClient` to scope configuration strictly to `catalog-service`.

For reliable operations, do not stop at "the returned list looks right": ensure a **trusted source, validated data, non-blocking lookups, bounded cache staleness, properly ordered health/filters, budgeted timeouts/retries, and thorough observability**. Once those conditions are verified, RestClient, WebClient, and OpenFeign can keep communicating by service name without needing to know whether replica lists come from Eureka, Kubernetes, or a custom control plane.
