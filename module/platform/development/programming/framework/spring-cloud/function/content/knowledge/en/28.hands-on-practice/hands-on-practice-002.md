# Converting JSON to POJO with a Custom Converter

## 1. Practice Problem

In **Spring Cloud Function** (`SPRING_CLOUD_FUNCTION`), `Supplier`, `Function`, and `Consumer` beans hold business logic that can be looked up via `FunctionCatalog` and reused across HTTP, event-driven systems, or serverless environments. A key feature of the framework is **message conversion**: adapters can receive JSON or byte arrays, while the business function still operates on typed Java objects.

In most cases, the default JSON converter is sufficient. Suppose, however, that a partner system sends orders using a **legacy JSON contract**:

~~~json
{
  "order_id": "O-201",
  "amount_vnd": 1500000,
  "source_code": "PARTNER-A"
}
~~~

In Java, we want to use an immutable POJO with camelCase property names:

~~~java
public record OrderRequest(
        String orderId,
        long amountVnd,
        String sourceCode) {
}
~~~

In addition, the system must explicitly recognize the partner's media type:

~~~http
Content-Type: application/vnd.textlab.order+json
~~~

We should not modify every `Function` to read a `Map<String,Object>`, manually remap JSON keys, and cast types. Instead, we will create a **custom Spring Messaging `MessageConverter`** that handles only this payload type, converting `snake_case` JSON into `OrderRequest` before the business function runs.

~~~text
Message<byte[]>
  contentType = application/vnd.textlab.order+json
  payload = {"order_id":"O-201","amount_vnd":1500000,...}
            |
            v
 VendorOrderJsonConverter
  - check MIME
  - check target class
  - enforce size limit
  - Jackson snake_case / strict JSON
            |
            v
 OrderRequest("O-201",1500000,"PARTNER-A")
            |
            v
 Function<OrderRequest, ClassificationResult>
            |
            v
 ClassificationResult("O-201","PRIORITY")
            |
            v
 Adapter outputs data according to its own contract
~~~

**After this lesson, you will be able to:**

1. Distinguish `contentType` from the **target Java argument type**.
2. Write an `AbstractMessageConverter` capable of converting `byte[]`/`String` into a Java record.
3. Register the converter as a `@Bean` for Spring Cloud Function to use.
4. Directly verify `fromMessage` and `toMessage` along with wrong MIME, malformed JSON, and missing-field cases.
5. Test a `Message<byte[]>` passing through `FunctionCatalog` into `Function<OrderRequest,ClassificationResult>`.
6. Understand what belongs to the converter, what belongs to business logic, and what still needs to be tested at the HTTP or Spring Cloud Stream adapter layer.

> **Scope:** This lesson conducts the lab via JUnit/Spring context and does not require a real broker, web server, or serverless deployment. The Java, Maven, and YAML files below are **instructional content for learners**, not files directly generated by a worker.

## 2. When Do You Need a Custom Converter?

Before writing code, identify the problem accurately:

| Situation | Appropriate Approach |
| --- | --- |
| Standard JSON, `orderId` field matches POJO | The default JSON converter is usually sufficient |
| JSON uses different names for only a few fields | Consider `@JsonProperty` or a Jackson naming strategy |
| A partner uses a distinct JSON format and rules | A custom `MessageConverter` bound to a dedicated media type may make sense |
| Non-JSON data such as CSV, Avro, or custom binary | A converter for that specific media type or an appropriate schema system |
| Input is not a `Message`, but a plain Java value | `ConversionService` or dedicated conversion logic can participate |
| Deciding whether to accept or reject an order | That is **business logic**, not the converter's responsibility |

Spring Cloud Function uses two primary mechanisms: `MessageConverter` for Spring `Message` payloads, while `ConversionService` can handle certain **non-Message** inputs. The custom converter in this lesson is **not** meant to replace all of Spring's conversion mechanisms.

### 2.1. Two Pieces of Information Required for Conversion

Suppose a message is sent into the catalog:

~~~text
contentType = application/vnd.textlab.order+json
target Java type = OrderRequest
~~~

- **`contentType`** specifies how to interpret the bytes: the message's data format.
- **`target Java type`** comes from the signature `Function<OrderRequest, ClassificationResult>`: the object to construct.

Relying solely on `contentType` is **not enough** to pick an arbitrary class to deserialize. Conversely, looking only at `OrderRequest` while ignoring the media type may cause partner data to be read under the wrong rules.

### 2.2. Why Use a Dedicated Media Type?

The lab uses:

~~~text
application/vnd.textlab.order+json
~~~

The `+json` suffix indicates that this is a JSON variant with its own structure. We separate it from `application/json` so that the custom converter **does not hijack every JSON message** in the application.

Custom converters are added to Spring Cloud Function's converter list and **take precedence before built-in converters**. Therefore, a converter that accepts `application/json` too broadly can accidentally alter the behavior of other functions. Restricting by both **MIME and target class** reduces unintended side effects.

## 5. Writing the POJOs and Business Rules

### 5.1. Record OrderRequest

Create `OrderRequest.java`:

~~~java
package com.example.vendorjson;

public record OrderRequest(
        String orderId,
        long amountVnd,
        String sourceCode) {
}
~~~

A Java record is an immutable POJO with a constructor, accessors `orderId()`, `amountVnd()`, `sourceCode()`, and auto-generated `equals/hashCode/toString`. The converter will be responsible for mapping:

| Partner JSON | Java record |
| --- | --- |
| `order_id` | `orderId` |
| `amount_vnd` | `amountVnd` |
| `source_code` | `sourceCode` |

### 5.2. Record ClassificationResult

Create `ClassificationResult.java`:

~~~java
package com.example.vendorjson;

public record ClassificationResult(
        String id,
        String category) {
}
~~~

The result uses two fields: `id` and `category`. This is a business DTO; the converter can serialize it to JSON on output when the media type matches.

### 5.3. Business Policy Independent of JSON

Create `OrderPolicy.java`:

~~~java
package com.example.vendorjson;

public final class OrderPolicy {

    private OrderPolicy() {
    }

    public static ClassificationResult classify(OrderRequest order) {
        if (order == null) {
            throw new IllegalArgumentException("order must not be null");
        }
        if (order.orderId() == null || order.orderId().isBlank()) {
            throw new IllegalArgumentException("orderId is required");
        }
        if (order.sourceCode() == null || order.sourceCode().isBlank()) {
            throw new IllegalArgumentException("sourceCode is required");
        }
        if (order.amountVnd() < 0) {
            throw new IllegalArgumentException("amountVnd must be >= 0");
        }

        return new ClassificationResult(
                order.orderId(),
                order.amountVnd() >= 1_000_000L
                        ? "PRIORITY"
                        : "STANDARD");
    }
}
~~~

Here, **the converter only changes the data representation**. Business rule checks (negative order amount, blank ID, empty source, priority threshold) live in `OrderPolicy`. As a result, the same `OrderPolicy.classify` can be reused with an `OrderRequest` created from default JSON, vendor JSON, direct calls, or other adapters.

## 6. Writing a Custom Converter Using AbstractMessageConverter

Create `VendorOrderJsonConverter.java`:

~~~java
package com.example.vendorjson;

import java.nio.charset.StandardCharsets;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.PropertyNamingStrategies;

import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.converter.AbstractMessageConverter;
import org.springframework.messaging.converter.MessageConversionException;
import org.springframework.util.MimeType;

public final class VendorOrderJsonConverter
        extends AbstractMessageConverter {

    public static final MimeType VENDOR_JSON =
            new MimeType("application", "vnd.textlab.order+json");

    private static final int MAX_PAYLOAD_BYTES = 16 * 1024;

    private final ObjectMapper mapper;

    public VendorOrderJsonConverter() {
        super(VENDOR_JSON);

        // Accept only the exact registered media type.
        setStrictContentTypeMatch(true);

        // toMessage prefers returning payload as byte[].
        setSerializedPayloadClass(byte[].class);

        this.mapper = new ObjectMapper()
                .setPropertyNamingStrategy(
                        PropertyNamingStrategies.SNAKE_CASE)
                .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
                .enable(DeserializationFeature.FAIL_ON_MISSING_CREATOR_PROPERTIES)
                .enable(DeserializationFeature.FAIL_ON_NULL_CREATOR_PROPERTIES)
                .enable(DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES);
    }

    @Override
    protected boolean supports(Class<?> clazz) {
        return OrderRequest.class.equals(clazz)
                || ClassificationResult.class.equals(clazz);
    }

    @Override
    protected Object convertFromInternal(
            Message<?> message,
            Class<?> targetClass,
            Object conversionHint) {

        Object payload = message.getPayload();
        byte[] bytes;

        if (payload instanceof byte[] data) {
            bytes = data;
        } else if (payload instanceof String text) {
            bytes = text.getBytes(StandardCharsets.UTF_8);
        } else {
            // Unrecognized representation: let another converter try.
            return null;
        }

        if (bytes.length > MAX_PAYLOAD_BYTES) {
            throw new MessageConversionException(
                    message, "Vendor JSON exceeds 16 KiB");
        }

        try {
            return mapper.readValue(bytes, targetClass);
        } catch (JsonProcessingException ex) {
            throw new MessageConversionException(
                    message, "Invalid vendor order JSON", ex);
        }
    }

    @Override
    protected Object convertToInternal(
            Object payload,
            MessageHeaders headers,
            Object conversionHint) {

        if (!supports(payload.getClass())) {
            return null;
        }

        try {
            byte[] bytes = mapper.writeValueAsBytes(payload);
            if (bytes.length > MAX_PAYLOAD_BYTES) {
                throw new MessageConversionException(
                        "Serialized vendor JSON exceeds 16 KiB");
            }
            return bytes;
        } catch (JsonProcessingException ex) {
            throw new MessageConversionException(
                    "Cannot serialize vendor JSON", ex);
        }
    }
}
~~~

### 6.1. Why Extend AbstractMessageConverter?

`org.springframework.messaging.converter.AbstractMessageConverter` already provides the boilerplate of `MessageConverter`, such as:

- Recognizing supported MIME types.
- Checking whether the target class belongs to the supported set.
- Calling `convertFromInternal` to create an object from a message.
- Calling `convertToInternal` when creating a message from an object.

We only declare **the media type, the set of classes, and the conversion logic**. This way, the converter does not need to implement every public method of the `MessageConverter` interface manually.

### 6.2. Why Does supports Only Accept Two Classes?

~~~java
return OrderRequest.class.equals(clazz)
        || ClassificationResult.class.equals(clazz);
~~~

This is an **allowlist of POJO types** that the converter knows how to process. It avoids accepting arbitrary `Object`, `Map`, or `List` types and deserializing them indiscriminately. When adding another DTO, expand this intentionally with corresponding tests.

The `supports` method is part of converter selection, **not** business validation. A message converted into `OrderRequest` can still contain a negative `amountVnd`, which must be handled by `OrderPolicy`.

### 6.3. What Does Strict MIME Matching Do?

~~~java
setStrictContentTypeMatch(true);
~~~

When a message has no `contentType`, this converter **does not claim it** solely because the target class is `OrderRequest`. For ordinary `application/json` media types, the custom converter should not steal the turn from the default JSON converter.

A custom converter is placed at the **front of Spring Cloud Function's priority list**, so it is only safe when it rejects everything outside its contract. When a converter returns `null` for an unsupported payload or type, the framework can fall back to another converter.

### 6.4. Bidirectional Conversion

| Method | Input | Result |
| --- | --- | --- |
| `fromMessage(message, OrderRequest.class)` | Message with `byte[]` or `String` JSON and matching MIME | `OrderRequest` |
| `fromMessage(message, ClassificationResult.class)` | Message with result JSON | `ClassificationResult` |
| `toMessage(orderRequest, headers)` | POJO + MIME header | Message with `byte[]` snake_case JSON payload |
| `toMessage(classificationResult, headers)` | Result DTO + MIME header | Message with `byte[]` JSON payload |

Especially in messaging, `toMessage` should produce a **wire payload** such as `byte[]`, rather than returning a raw Java object reference that cannot be transmitted across a broker.

### 6.5. Jackson Configuration: Why Strict?

The converter uses:

- `PropertyNamingStrategies.SNAKE_CASE`: `orderId` ↔ `order_id`.
- `FAIL_ON_UNKNOWN_PROPERTIES`: does not silently ignore unknown fields.
- `FAIL_ON_MISSING_CREATOR_PROPERTIES`: rejects missing required constructor parameters.
- `FAIL_ON_NULL_CREATOR_PROPERTIES`: rejects JSON `null` for creator parameters.
- `FAIL_ON_NULL_FOR_PRIMITIVES`: prevents `amount_vnd: null` from silently coercing to `0L`.

This is the **lab policy**. In an application that needs schema evolution compatibility, certain extra fields may be allowed; however, that must be decided deliberately and tested with versioning. Placing these strict options on the **converter's own ObjectMapper** avoids altering JSON mapping across the entire application.

### 6.6. The 16 KiB Limit

`MAX_PAYLOAD_BYTES` is an illustrative limit to prevent oversized payloads on the custom JSON path. In production, you also need payload size controls at the gateway/broker, limits on nested JSON elements and depth, resource budgets, and logging/retention policies. A custom converter **cannot** protect the entire application with a single `bytes.length` check.

## 7. Registering the Converter and Function in Spring

Create `ConverterFunctions.java`:

~~~java
package com.example.vendorjson;

import java.util.function.Function;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.messaging.converter.MessageConverter;

@Configuration(proxyBeanMethods = false)
public class ConverterFunctions {

    @Bean
    public MessageConverter vendorOrderJsonConverter() {
        return new VendorOrderJsonConverter();
    }

    @Bean
    public Function<OrderRequest, ClassificationResult> classifyOrder() {
        return OrderPolicy::classify;
    }
}
~~~

Registering them this way carries **two distinct meanings**:

1. `vendorOrderJsonConverter` is a **MessageConverter bean**, not a business function to invoke via `FunctionCatalog.lookup("vendorOrderJsonConverter")`.
2. `classifyOrder` is a **functional bean**. It only accepts an `OrderRequest`; it does not parse JSON itself or read `MessageHeaders`.

Spring Cloud Function collects user-defined converters and places them ahead of built-in converters. When the catalog needs to convert a message to `OrderRequest`, the custom converter gets to handle it if **both the media type and the target class** match.

## 9. Testing MessageConverter Directly

Create `VendorOrderJsonConverterTest.java`:

~~~java
package com.example.vendorjson;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertInstanceOf;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertThrows;

import java.nio.charset.StandardCharsets;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

import org.junit.jupiter.api.Test;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.converter.MessageConversionException;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.util.MimeTypeUtils;

class VendorOrderJsonConverterTest {

    private final VendorOrderJsonConverter converter =
            new VendorOrderJsonConverter();

    private static final String VALID_JSON = """
            {
              "order_id": "O-201",
              "amount_vnd": 1500000,
              "source_code": "PARTNER-A"
            }
            """;

    private Message<byte[]> vendorMessage(String json) {
        return MessageBuilder
                .withPayload(json.getBytes(StandardCharsets.UTF_8))
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        VendorOrderJsonConverter.VENDOR_JSON)
                .build();
    }

    @Test
    void parsesSnakeCaseJsonIntoRecord() {
        Object result = converter.fromMessage(
                vendorMessage(VALID_JSON), OrderRequest.class);

        assertInstanceOf(OrderRequest.class, result);
        assertEquals(
                new OrderRequest("O-201", 1_500_000L, "PARTNER-A"),
                result);
    }

    @Test
    void alsoAcceptsStringPayloadForVendorMime() {
        Message<String> input = MessageBuilder
                .withPayload(VALID_JSON)
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        VendorOrderJsonConverter.VENDOR_JSON)
                .build();

        assertEquals(
                new OrderRequest("O-201", 1_500_000L, "PARTNER-A"),
                converter.fromMessage(input, OrderRequest.class));
    }

    @Test
    void doesNotHijackOrdinaryJsonOrOtherTargetClasses() {
        var input = MessageBuilder
                .withPayload(VALID_JSON.getBytes(StandardCharsets.UTF_8))
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        MimeTypeUtils.APPLICATION_JSON)
                .build();

        assertNull(converter.fromMessage(input, OrderRequest.class));
        assertNull(converter.fromMessage(
                vendorMessage(VALID_JSON), String.class));
    }

    @Test
    void requiresExplicitVendorContentType() {
        var missingType = MessageBuilder
                .withPayload(VALID_JSON.getBytes(StandardCharsets.UTF_8))
                .build();

        assertNull(converter.fromMessage(
                missingType, OrderRequest.class));
    }

    @Test
    void rejectsMalformedAndIncompleteJson() {
        assertThrows(MessageConversionException.class,
                () -> converter.fromMessage(
                        vendorMessage("{bad-json"),
                        OrderRequest.class));

        assertThrows(MessageConversionException.class,
                () -> converter.fromMessage(
                        vendorMessage("""
                            {"order_id":"O-204","source_code":"P"}
                            """),
                        OrderRequest.class));
    }

    @Test
    void rejectsNullPrimitiveAndUnknownProperty() {
        assertThrows(MessageConversionException.class,
                () -> converter.fromMessage(
                        vendorMessage("""
                            {"order_id":"O-205","amount_vnd":null,
                             "source_code":"P"}
                            """),
                        OrderRequest.class));

        assertThrows(MessageConversionException.class,
                () -> converter.fromMessage(
                        vendorMessage("""
                            {"order_id":"O-205","amount_vnd":10,
                             "source_code":"P","unexpected":true}
                            """),
                        OrderRequest.class));
    }

    @Test
    void serializesRecordBackToSnakeCaseJson() throws Exception {
        var headers = vendorMessage(VALID_JSON).getHeaders();
        Message<?> result = converter.toMessage(
                new OrderRequest("O-206", 500_000L, "PARTNER-Z"),
                headers);

        assertNotNull(result);
        byte[] bytes = assertInstanceOf(byte[].class, result.getPayload());
        JsonNode json = new ObjectMapper().readTree(bytes);

        assertEquals("O-206", json.get("order_id").asText());
        assertEquals(500_000L, json.get("amount_vnd").asLong());
        assertEquals("PARTNER-Z", json.get("source_code").asText());
    }

    @Test
    void enforcesPayloadSizeLimit() {
        String oversized = "x".repeat(17 * 1024);

        assertThrows(MessageConversionException.class,
                () -> converter.fromMessage(
                        vendorMessage(oversized),
                        OrderRequest.class));
    }
}
~~~

The tests at this step confirm:

- The converter works with `Message<byte[]>` and `Message<String>`.
- Standard `application/json` MIME is **not mistakenly intercepted by the custom converter**.
- For an unsupported target class, the converter returns `null` so other converters can be tried.
- Malformed JSON, missing fields, null primitives, and unknown fields are rejected per the lab's policy.
- `toMessage` produces `snake_case` JSON as `byte[]`.

**Error testing note:** At the **direct converter invocation** level, we check `MessageConversionException`. When going through a **chain of multiple converters** managed by Spring Cloud Function, the framework may try subsequent converters or wrap exceptions differently depending on the version; do not assume every error above will preserve the exact exception class at the HTTP/broker layer.

## 10. Testing the Converter via FunctionCatalog

This is the most important step: `FunctionCatalog` must use the converter to transform `Message<byte[]>` into `OrderRequest` **before** invoking `Function<OrderRequest, ClassificationResult>`.

Create `ConverterFunctionCatalogTest.java`:

~~~java
package com.example.vendorjson;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;

import java.nio.charset.StandardCharsets;
import java.util.function.Function;

import com.fasterxml.jackson.databind.ObjectMapper;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.cloud.function.context.FunctionCatalog;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.converter.MessageConverter;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.beans.factory.annotation.Qualifier;

@SpringBootTest(
        classes = ConverterLabApplication.class,
        webEnvironment = SpringBootTest.WebEnvironment.NONE)
class ConverterFunctionCatalogTest {

    @Autowired
    private FunctionCatalog catalog;

    @Autowired
    @Qualifier("vendorOrderJsonConverter")
    private MessageConverter vendorConverter;

    @Test
    void customConverterBeanIsRegistered() {
        assertNotNull(vendorConverter);
    }

    @Test
    void catalogConvertsMessageBeforeCallingBusinessFunction()
            throws Exception {

        String body = """
                {
                  "order_id": "O-301",
                  "amount_vnd": 1700000,
                  "source_code": "PARTNER-A"
                }
                """;

        Message<byte[]> incoming = MessageBuilder
                .withPayload(body.getBytes(StandardCharsets.UTF_8))
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        VendorOrderJsonConverter.VENDOR_JSON)
                .build();

        // Look up the SCF wrapper, NOT the raw Java Function bean.
        Function<Object, Object> function =
                catalog.lookup("classifyOrder");
        assertNotNull(function);

        Object rawResult = function.apply(incoming);
        ClassificationResult decision = decodeResult(rawResult);

        assertEquals(
                new ClassificationResult("O-301", "PRIORITY"),
                decision);
    }

    private ClassificationResult decodeResult(Object raw)
            throws Exception {

        Object payload = raw instanceof Message<?> message
                ? message.getPayload()
                : raw;

        if (payload instanceof ClassificationResult decision) {
            return decision;
        }

        // Some adapters/wrappers return serialized data.
        ObjectMapper mapper = new ObjectMapper();
        if (payload instanceof byte[] bytes) {
            return mapper.readValue(bytes, ClassificationResult.class);
        }
        if (payload instanceof String text) {
            return mapper.readValue(text, ClassificationResult.class);
        }

        throw new AssertionError(
                "Unexpected function output type: "
                        + payload.getClass().getName());
    }
}
~~~

This test does not enforce a single output wrapper shape: depending on the invocation path and version, a catalog function may return a **POJO**, a **Message containing a POJO**, or serialized output. However, the test always checks the **final business value**; if the input is not converted to `OrderRequest`, calling the Java bean will not match its signature and the test will fail.

### 10.1. Why Does lookup Use Function<Object,Object>?

In this example, we want to **explicitly pass a `Message<byte[]>`** into the wrapper, even though the underlying bean has signature:

~~~java
Function<OrderRequest, ClassificationResult>
~~~

`FunctionCatalog.lookup("classifyOrder")` returns a function *instrumented* by Spring Cloud Function to handle conversion. The `Function<Object,Object>` generic on the **test variable** simply lets us pass a raw value into the wrapper; it **does not change the original bean's signature**.

Do not manually convert `Message<byte[]>` into `OrderRequest` before invoking the function, as that would bypass the converter under test.

### 10.2. Comparison Test with Default JSON

If you change the input media type to `application/json` and send camelCase JSON:

~~~json
{
  "orderId": "O-302",
  "amountVnd": 500000,
  "sourceCode": "DIRECT"
}
~~~

then the **default JSON converter** can convert the payload to `OrderRequest`. The custom converter should not intervene because it only supports `application/vnd.textlab.order+json`.

Add a separate integration test in your project:

1. Send a `Message<byte[]>` carrying camelCase JSON and header `application/json`.
2. Call `lookup("classifyOrder")` and invoke the function.
3. Verify the result `ClassificationResult("O-302","STANDARD")`.

This test demonstrates that the application can accept **two JSON contracts** on the same functional bean without duplicating business logic. If the outcome differs from expectations, inspect type information, Jackson configuration, and which converter is actually selected.

## 12. When Extending to Spring Cloud Stream

Spring Cloud Stream uses bindings to connect functional beans to broker destinations. To turn this lab into a messaging consumer/processor, you need to:

1. Add the Spring Cloud Stream dependency and an appropriate binder, such as Kafka or RabbitMQ.
2. Provide a running broker and configure connection settings.
3. Specify `spring.cloud.function.definition=classifyOrder`.
4. Attach the **exact vendor media type** to the input binding.

Example **illustrative extension** configuration, which cannot be used with the current `pom.xml` without adding Stream/binder:

~~~yaml
spring:
  cloud:
    function:
      definition: classifyOrder
    stream:
      bindings:
        classifyOrder-in-0:
          destination: partner.orders.received
          group: order-classifier
          content-type: application/vnd.textlab.order+json
        classifyOrder-out-0:
          destination: partner.orders.classified
          content-type: application/json
~~~

Here:

| Binding | Direction | Media Type | Java Type |
| --- | --- | --- | --- |
| `classifyOrder-in-0` | Input | `application/vnd.textlab.order+json` | `OrderRequest` |
| `classifyOrder-out-0` | Output | `application/json` | `ClassificationResult` |

Input passes through the custom converter because it follows the vendor JSON contract. Output uses standard JSON as specified by the output binding. **The custom converter does not necessarily have to serialize the output**; this lesson still implements `convertToInternal` to demonstrate both directions and to support applications that need to send back the vendor format.

### 12.1. Where Does Content Type Come From?

In Spring Cloud Stream, the typical precedence order is:

1. **The `contentType` header on the message itself** has the highest priority.
2. If the header is absent, **the binding's `content-type` configuration**.
3. If neither is present, **the framework default**, typically `application/json`.

Therefore, when receiving data from a partner, check what header the producer sends. If the producer intentionally sends `application/json` while the payload follows the vendor schema, an input binding configured with the vendor MIME may **not override the header**; the custom converter may not be selected.

**Do not confuse binding names with destinations.** `classifyOrder-in-0` is the binding identifier inside the application; `partner.orders.received` is the destination on the binder.

### 12.2. Testing the Real Adapter

After adding a binder, write integration tests with the **Spring Cloud Stream Test Binder** or a test broker:

- Emit `snake_case` JSON `byte[]` to `classifyOrder-in-0`.
- Attach the proper `contentType` header.
- Read output from `classifyOrder-out-0`.
- Verify that business data is classified and output JSON matches expectations.
- Test malformed JSON cases: verify retry/DLQ and acknowledgment behavior at the binder rather than inferring it from unit test exceptions.

A custom converter **does not control** retries, offset commits, partitioning, or delivery guarantees. Those properties reside in Spring Cloud Stream/the binder and the application's operational design.

## 13. When Extending to HTTP or Serverless

With the **Spring Cloud Function web adapter**, an HTTP request carries a `Content-Type` header and a body; the adapter can construct a Spring `Message` and use catalog conversion. However, **Spring MVC/WebFlux also have their own converters** for certain request types. Consequently, having `MessageConverter` properly registered in SCF **does not guarantee** every HTTP call path will pass through this converter.

Before publishing an endpoint:

- Add the web adapter and a compatible Spring Boot web runtime.
- Send requests with `Content-Type: application/vnd.textlab.order+json`.
- Test response status, headers, body, and actual converter selection over HTTP.
- Do not treat `FunctionCatalog` tests as full proof of HTTP content negotiation and error handling.

Similarly, for AWS Lambda, Azure Functions, or Google Cloud Functions: events may be wrapped into messages or use provider-specific event structures. **`OrderPolicy` and `Function<OrderRequest,ClassificationResult>`** remain reusable, while bringing a custom media type into a trigger requires adapter-specific configuration and testing.

## 14. Converter, Function, and Validation: Separation of Responsibilities

A maintainable design has three independent layers:

| Layer | Responsibility | What It Should Not Do |
| --- | --- | --- |
| Custom converter | Recognize media type, deserialize/serialize, enforce schema and payload size | Decide "which order is PRIORITY" |
| Functional bean | Execute business rules on typed POJOs | Read raw `byte[]` and re-parse JSON inside every function |
| Adapter (HTTP/Stream/serverless) | Provide transport, content type, routing, error mapping | Embed classification rules deep inside controllers/broker callbacks |

Clear example:

~~~java
// Input may come from default JSON, vendor JSON, or a unit test.
Function<OrderRequest, ClassificationResult> function =
        OrderPolicy::classify;

var request = new OrderRequest(
        "O-501", 1_250_000L, "DIRECT");

ClassificationResult result = function.apply(request);
// ClassificationResult("O-501", "PRIORITY")
~~~

The converter is not involved when the input is already an `OrderRequest`. This keeps both the Function and unit tests decoupled from data conversion.

### 14.1. Why Not Pass Map<String,Object> to the Function?

If the bean declares `Function<Map<String,Object>,ClassificationResult>`:

- `amount_vnd` might arrive as `Integer`, `Long`, `BigDecimal`, or `String` depending on mapper/config.
- Every bean must know the partner's `snake_case` field names.
- Manual casting across multiple places is prone to runtime errors.
- Adding support for another source forces business code to change.

`OrderRequest` separates the external wire structure from the business model; the compiler checks accessors and generics directly in source code.

### 14.2. Should a Custom Converter Be Used for Every JSON Format?

**Not by default.** If only a few field names differ, you can use `@JsonProperty` on the DTO, `PropertyNamingStrategies.SNAKE_CASE` in a dedicated mapper, or adapter-specific schema mapping. A custom converter fits when you need rules **scoped to a media type**, an independent legacy format, or explicitly controlled decoding.

If a custom converter broadly accepts `application/json` for any `Object`, it can "swallow" payloads meant for other functions because user-declared converters take precedence over built-in ones. That is one reason this lesson designs a **dedicated MIME + target class allowlist**.

## 15. Generic Types and Nested Data

The converter demonstrated here handles **a single `OrderRequest` record per conversion**, because `supports` only accepts specific classes. If the actual input is:

~~~java
List<OrderRequest>
~~~

or:

~~~java
Envelope<OrderRequest>
~~~

then `Class<?> targetClass` **does not carry full generic information** such as the element type `OrderRequest` inside the List, due to **type erasure** on the JVM. When extending:

- Inspect `conversionHint` and generic metadata provided by the framework.
- Use Jackson `JavaType`/`TypeReference` to deserialize typed lists or wrappers.
- Update `supports` intentionally and add tests for both valid and invalid schemas.
- Do not open `supports(Object.class)` just to avoid managing generics.

A Jackson 2 example for reading a list when parsing manually:

~~~java
import com.fasterxml.jackson.core.type.TypeReference;

// Use a mapper configured with the appropriate naming strategy.
List<OrderRequest> orders = mapper.readValue(
        jsonBytes,
        new TypeReference<List<OrderRequest>>() {});
~~~

This is an extension pattern, not a snippet to copy verbatim into the single-`OrderRequest` converter. To add real batch processing, build a new converter or evolve the design in a controlled way.

## 16. Security and Untrusted Input Controls

JSON arriving from HTTP or a broker is **external data**, not an instruction telling the framework to instantiate an arbitrary class. When a header includes something like `application/json;type=...`, Spring Cloud Function requires an allowlist of permitted classes in `META-INF/deserializable.types` in certain dynamic-typing mechanisms to prevent instantiating arbitrary classes from untrusted sources.

In this lab, **dynamic target classes from headers are not used**: the signature `Function<OrderRequest,ClassificationResult>` specifies the target type in Java code, and the converter accepts only two known DTOs.

Minimum production checklist:

1. **Do not enable default typing / polymorphic deserialization arbitrarily** on external JSON.
2. Restrict which classes the converter handles instead of deserializing `Object` unchecked.
3. Enforce message size and JSON complexity limits across multiple layers.
4. Validate missing/null/unknown fields and schema versioning.
5. Do not log raw JSON containing personal information, tokens, or secrets in exception logs.
6. Do not treat `MessageConverter` as an authentication/authorization mechanism.
7. Define adapter-specific retry, DLQ, or error response policies.
8. Keep Jackson/Spring dependencies updated on supported release branches.

A `MessageConversionException` may hold a reference to the failed message; when logging in production, avoid accidentally exposing sensitive payloads.

## 17. Common Errors and Diagnostics

| Symptom | Possible Cause | What to Check |
| --- | --- | --- |
| Custom converter is never invoked | Bean not registered or MIME mismatch | Check `@Bean MessageConverter` and `contentType` |
| JSON deserializes as `Map` instead of `OrderRequest` | Target type inferred too broadly; raw `Function`/`Object` used | Declare `Function<OrderRequest,...>` |
| `fromMessage` returns null | Unsupported MIME, target class, or payload type | Check `supports` and `setStrictContentTypeMatch` |
| `amount_vnd: null` becomes 0 | Jackson primitive coercion is not strict | Enable `FAIL_ON_NULL_FOR_PRIMITIVES` and test |
| JSON missing `source_code` still passes | Creator property checks not enabled | Check `FAIL_ON_MISSING_CREATOR_PROPERTIES` |
| System sends camelCase while converter expects snake_case | Different schema/media type | Attach the right MIME; separate default and vendor converters |
| Invalid business data still reaches function | Converter allowed bad schema or validation is missing | Separate strict deserialization from business validation |
| `ClassCastException` inside Function | Wrapper failed to convert to declared type | Test `Message<byte[]>` via catalog; check contentType/converter |
| Catalog test passes, HTTP still fails | Web adapter uses its own mapping/converters | Write an HTTP integration test; check content negotiation |
| Catalog test passes, Kafka receives no message | Missing binder/destination or wrong headers | Check Stream bindings and the real broker |
| Converter affects other JSON functions | `supports` or MIME is too broad | Use a dedicated media type and explicit class allowlist |
| Nested generic JSON becomes `Map` | Generic type lost in `Class<?>` | Use `TypeReference`/`JavaType` and add tests |
| Conversion error wrapped as another exception | Composite converter/wrapper/adapter error handling | Test converter directly and test adapter integration |
| Heap spikes on large messages | No payload size, depth, or concurrency limits | Enforce multi-layer size limits and monitor |

### 17.1. Recommended Debugging Order

1. Test `OrderPolicy.classify` alone with constructed Java DTOs.
2. Test `VendorOrderJsonConverter.fromMessage` with the exact vendor MIME.
3. Test that the converter rejects messages with wrong MIME/target.
4. Test `toMessage` returning `snake_case` JSON `byte[]`.
5. Verify the Spring context contains the `vendorOrderJsonConverter` bean.
6. Look up `classifyOrder` via `FunctionCatalog`.
7. Send `Message<byte[]>` through the wrapper and assert the final output.
8. Only then test HTTP or a broker, where additional conversion and error-handling layers exist.

## 19. Completion Criteria

| Criterion | Evidence |
| --- | --- |
| Typed POJOs | `OrderRequest` and `ClassificationResult` have no framework dependency |
| Business Function | `Function<OrderRequest, ClassificationResult>` registered via `@Bean` |
| Custom converter | Extends `AbstractMessageConverter` with an explicit vendor media type |
| Input conversion | JSON `order_id/amount_vnd/source_code` converts into the Java record |
| Output conversion | `toMessage` emits JSON `byte[]` |
| Does not hijack default converter | `application/json` messages are not intercepted by the custom converter |
| Error handling | Tests cover malformed JSON, missing/null fields, unknown fields, and size limits |
| Spring integration | `FunctionCatalog.lookup("classifyOrder")` and `apply(Message<byte[]>)` work |
| Limitations understood | Catalog tests do not replace HTTP/broker/serverless integration tests |
| Security | No dynamic class loading; class allowlist and size limit enforced |

**Summary:** A custom converter should handle **data formatting**, while the functional bean handles **business logic**. `FunctionCatalog` bridges the two layers using input type metadata and message `contentType`. With this design, the same `Function<OrderRequest,ClassificationResult>` can be deployed across multiple adapters without copying JSON parsing logic into every execution path.

## 20. Self-Check Questions

**Question 1.** Why is `application/vnd.textlab.order+json` alone not enough for Spring Cloud Function to know it must construct `OrderRequest`?

**Answer:** Content type only describes the format. The target type also comes from the function signature or conversion metadata—in this case `Function<OrderRequest,...>`.

**Question 2.** Why does the custom converter only `supports` `OrderRequest` and `ClassificationResult` instead of any `Object`?

**Answer:** To avoid interfering with converters for other DTOs and to prevent deserializing unpermitted types.

**Question 3.** What problem can placing a custom converter at the head of the chain cause?

**Answer:** If its MIME matching and `supports` check are too broad, the converter can hijack messages intended for other functions before the default converter is tried. You must constrain the acceptance criteria.

**Question 4.** How does `FAIL_ON_NULL_FOR_PRIMITIVES` help with `long amountVnd`?

**Answer:** It prevents JSON `null` from silently coercing to the primitive default `0L`, which would distort business meaning.

**Question 5.** Why does a passing `OrderPolicy.classify(new OrderRequest(...))` test not prove the custom converter works?

**Answer:** That test bypasses JSON, MIME, `MessageConverter`, and the catalog wrapper. You need to test `fromMessage` and `FunctionCatalog` with `Message<byte[]>`.

**Question 6.** When deploying with Spring Cloud Stream, how do the `contentType` header and binding `content-type` configuration take precedence?

**Answer:** The message header usually takes precedence over the binding configuration, followed by the framework default. If a producer sends the wrong header, the custom converter might not be selected even when the binding is configured properly.

**Question 7.** Should the converter publish malformed JSON messages directly to a Kafka DLQ?

**Answer:** You should not couple the converter to Kafka. It should surface the conversion error; the adapter/binder decides retry, DLQ, acknowledgment, and telemetry behavior.

**Question 8.** When you need `List<OrderRequest>`, why is passing `OrderRequest.class` or `List.class` alone insufficient?

**Answer:** Generic element types can be erased at runtime. You must provide `TypeReference`/`JavaType` or suitable metadata so the JSON mapper knows the element type.
