# Restricting HTTP Methods with `spring.cloud.function.http` in Spring Cloud Function

## 1. Why Restrict HTTP Methods?

In **Spring Cloud Function (SCF)**, business logic is declared as Java beans (`Supplier<O>`, `Function<I, O>`, and `Consumer<I>`) and registered in `FunctionCatalog`. The same logic can be invoked via HTTP, Spring Cloud Stream events, or serverless runtimes. The HTTP adapter is responsible for passing data into the function and representing the result as an HTTP response.

When `spring-cloud-starter-function-web` is enabled, SCF provides default rules by function type:

- `Supplier` typically uses `GET /{supplier}`.
- `Function` typically uses `POST`/`PUT /{function}`, or `GET /{function}/{item}`.
- `Consumer` can use `POST`/`PUT`/`DELETE /{consumer}`.

These mappings are convenient for prototypes, yet they may not fit an **HTTP API with a strict contract**. For example, you may want to:

1. Allow only `GET` for a status-reading function.
2. Allow only `POST` for a quote-creation operation.
3. Allow only `PUT` for a data-replacement operation.
4. Allow only `DELETE` for a deletion request.

Instead of allowing the same function to be called across multiple default HTTP methods, SCF supports **method-specific function mapping**:

```properties
spring.cloud.function.http.GET=status
spring.cloud.function.http.POST=quote
spring.cloud.function.http.PUT=replaceStock
spring.cloud.function.http.DELETE=deleteById
```

This is the core topic of this lesson: **restricting which functions/compositions the HTTP adapter maps for each method**, while distinguishing HTTP route restrictions from security and business semantics.

### Learning Objectives

After this lesson, you will be able to:

- Explain the structure of `spring.cloud.function.http.<METHOD>` properties and how they differ from `spring.cloud.function.definition`.
- Assign GET/POST/PUT/DELETE to appropriate functional beans, including compositions.
- Use `;` to list multiple functions for the same method and `|` to compose functions.
- Predict URLs, request bodies, response bodies, and statuses by `Supplier`/`Function`/`Consumer` type.
- Test both permitted methods and unmapped methods without confusing `404` with `405`.
- Understand why restricting methods **does not automatically guarantee idempotency, authorization, or durable persistence**.

## 2. Default HTTP Rules Before Custom Configuration

Per SCF's official **Standalone Web Applications** documentation:

| HTTP method | Default path | Matching bean | Request | Typical success status |
| --- | --- | --- | --- | --- |
| GET | `/{supplier}` | `Supplier<O>` | No body needed | 200 OK, data generated by Supplier |
| POST | `/{function}` | `Function<I,O>` | Text/JSON body | 200 OK, result of applying function |
| PUT | `/{function}` | `Function<I,O>` | Text/JSON body | 200 OK |
| GET | `/{function}/{item}` | `Function<I,O>` | One value in the path | 200 OK |
| POST | `/{consumer}` | `Consumer<I>` | Text/JSON body | 202 Accepted |
| PUT | `/{consumer}` | `Consumer<I>` | Text/JSON body | 202 Accepted |
| DELETE | `/{consumer}` | `Consumer<I>` | Data per adapter contract | 204 No Content |

This table describes **what the adapter can handle by default**, not a requirement that every application expose all of them. The function must also exist in `FunctionCatalog`, the name/path must resolve, and the request must use an appropriate media type.

**Common pitfall:** having a valid HTTP method **does not mean business code honors that method's semantics**. For example, Java's `Function.apply()` can update a database regardless of whether the client sends POST or PUT. SCF does not enforce PUT idempotency automatically.

### One vs. Multiple Functions

When there is only **one** functional bean in the catalog, the name in the URL can be omitted, e.g., `POST /`. When there are multiple beans, URLs typically include the function name. `spring.cloud.function.definition` can select a default function/composition at root, which is a **different mechanism** from the per-HTTP-method mapping in this lesson.

## 3. Syntax of `spring.cloud.function.http.<METHOD>`

Configuration has the form:

```properties
spring.cloud.function.http.GET=foo;bar;normalize|uppercase
spring.cloud.function.http.POST=quote
spring.cloud.function.http.PUT=replaceStock
spring.cloud.function.http.DELETE=deleteById
```

SCF documentation refers to this as **CRUD REST with Spring Cloud Function**. Each property's value is a function name or a list of functions/compositions allowed to map to **the method named in the key**.

### 3.1. Meaning of the Key

- `spring.cloud.function.http.GET`: selects functions/compositions mapped when requests use GET.
- `spring.cloud.function.http.POST`: list mapped for POST.
- `spring.cloud.function.http.PUT`: list mapped for PUT.
- `spring.cloud.function.http.DELETE`: list mapped for DELETE.

Method names in the examples are **uppercase**, matching the official documentation syntax. Do not assume less common HTTP methods such as PATCH, HEAD, or OPTIONS behave identically across every SCF version; if needed, check the active web module or build a controller/router.

### 3.2. Meaning of the Value String

| Value | Listed items | Meaning |
| --- | ---: | --- |
| `quote` | 1 | Selects one function |
| `quote;reverse` | 2 | Selects two independent functions |
| `normalize\|uppercase` | 1 | Selects one composition running `normalize` then `uppercase` |
| `normalize\|uppercase;quote` | 2 | One composition and one function |
| `status;uppercase;normalize\|uppercase` | 3 | Two independent functions and one composition |

In this table:

- **Semicolons** (`;`) list items mapped to that method.
- **Pipes** (`|`) compose functions **from left to right** within a single item.
- **Commas** (`,`) are typically convenient when calling compositions in URLs, e.g., `/normalize,uppercase`.

These delimiters are **configuration syntax**, not a user authorization mechanism.

### 3.3. Example from Official Documentation

SCF documentation gives the example:

```properties
spring.cloud.function.http.GET=uppercase;reverse;foo|bar
spring.cloud.function.http.POST=reverse
spring.cloud.function.http.DELETE=deleteById
```

Here `reverse` is permitted in the lists for **both GET and POST**; each method has its own mapping. `foo|bar` is a composition mapped to GET. If `foo` and `bar` have incompatible types or do not match GET's input source, the configuration can exist yet fail when called; **the method name alone does not make a function valid for business logic**.

## 4. Complete Example for Practice

We will build an application with multiple functional beans and then use per-method properties to **expose only the intended operations**.

### 4.1. Dependencies

The Spring Boot project needs a compatible Spring Cloud dependencies BOM. For an SCF HTTP adapter on Spring MVC:

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-function-web</artifactId>
</dependency>
```

Do not mix incompatible versions of Spring Boot, Spring Cloud Function, and Reactor. If the application intentionally uses WebFlux, select the web adapter matching the release train and run tests on the actual runtime.

### 4.2. Java Beans

Create `src/main/java/demo/MethodMappingApplication.java` (Java 17+):

```java
package demo;

import java.math.BigDecimal;
import java.util.Locale;
import java.util.function.Consumer;
import java.util.function.Function;
import java.util.function.Supplier;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class MethodMappingApplication {

    public static void main(String[] args) {
        SpringApplication.run(MethodMappingApplication.class, args);
    }

    // Read-only status; suitable for GET.
    @Bean
    public Supplier<ServiceStatus> status() {
        return () -> new ServiceStatus("READY", "SCF-DEMO");
    }

    // Single String-input Function, callable via GET /uppercase/{item}.
    @Bean
    public Function<String, String> uppercase() {
        return text -> text.toUpperCase(Locale.ROOT);
    }

    // Step in the POST normalize|uppercase pipeline.
    @Bean
    public Function<String, String> normalize() {
        return String::trim;
    }

    // POST: accepts JSON and returns JSON.
    @Bean
    public Function<QuoteRequest, QuoteResponse> quote() {
        return request -> {
            if (request == null || request.sku() == null
                    || request.sku().isBlank()
                    || request.quantity() <= 0) {
                throw new IllegalArgumentException(
                        "Invalid quote request");
            }

            BigDecimal unitPrice = new BigDecimal("120000");
            BigDecimal total = unitPrice.multiply(
                    BigDecimal.valueOf(request.quantity()));

            return new QuoteResponse(
                    request.sku(), request.quantity(), total);
        };
    }

    // PUT: illustrates the result of a stock replacement request.
    // This is simulated, NOT written to a database.
    @Bean
    public Function<StockChange, StockReceipt> replaceStock() {
        return request -> {
            if (request == null || request.sku() == null
                    || request.sku().isBlank()
                    || request.quantity() < 0) {
                throw new IllegalArgumentException(
                        "Invalid stock replacement");
            }

            return new StockReceipt(
                    request.sku(), request.quantity(), "SIMULATED");
        };
    }

    // DELETE: Consumer processes a command, does NOT delete any record itself.
    @Bean
    public Consumer<String> deleteById() {
        return sku -> System.out.println(
                "Simulated delete request for SKU: " + sku);
    }

    // Bean present in catalog, not intended for HTTP exposure.
    @Bean
    public Function<String, String> internalEcho() {
        return input -> "[internal] " + input;
    }

    public record ServiceStatus(String state, String service) {}
    public record QuoteRequest(String sku, int quantity) {}
    public record QuoteResponse(
            String sku, int quantity, BigDecimal totalPrice) {}
    public record StockChange(String sku, int quantity) {}
    public record StockReceipt(
            String sku, int quantity, String result) {}
}
```

The application defines **seven** functional beans. The code uses no `HttpServletRequest`, `@PostMapping`, or `@DeleteMapping`—that is the transport independence SCF aims for. The `internalEcho` bean illustrates internal logic that must not be exposed accidentally.

**Note:** `replaceStock` returns `SIMULATED` and mutates no data. `deleteById` only logs to stdout and deletes no resource. Function names and HTTP methods do not create durability, transactions, or CRUD semantics by themselves.

### 4.3. Configuring HTTP Methods

In `src/main/resources/application.properties`:

```properties
spring.cloud.function.http.GET=status;uppercase
spring.cloud.function.http.POST=normalize|uppercase;quote
spring.cloud.function.http.PUT=replaceStock
spring.cloud.function.http.DELETE=deleteById
```

These are four separate lists:

1. GET: Supplier `status` and Function `uppercase`.
2. POST: composition `normalize|uppercase` and Function `quote`.
3. PUT: Function `replaceStock`.
4. DELETE: Consumer `deleteById`.

**Do not** set `spring.cloud.function.definition` in this example so root/fallback/function filtering are not mixed with method-specific mappings. Once each mechanism is understood individually, combine them and write integration tests for their actual interaction.

Run:

```bash
mvn spring-boot:run
```

The `curl` commands below use Bash syntax. In Windows PowerShell, use `curl.exe` and adjust line continuations. The server is assumed to run at `http://localhost:8080`.

## 5. Permitted Endpoint Matrix by HTTP Method

Based on section 4's configuration, build an expectation table:

| Method | URL | Function/composition | Input | Typical success result |
| --- | --- | --- | --- | --- |
| GET | `/status` | `status` | No body | 200 + status JSON |
| GET | `/uppercase/hello` | `uppercase` | Path item `hello` | 200 + `HELLO` |
| POST | `/normalize,uppercase` | `normalize\|uppercase` | Text in body | 200 + trimmed/uppercased string |
| POST | `/quote` | `quote` | JSON DTO | 200 + quote JSON |
| PUT | `/replaceStock` | `replaceStock` | JSON DTO | 200 + simulated result |
| DELETE | `/deleteById` | `deleteById` | `text/plain` body | 204, no response body |

**Do not assume:** `POST /uppercase` is automatically mapped just because `uppercase` appears under GET. POST in this example lists only the **composition** `normalize|uppercase` and `quote`. Likewise, `PUT /quote` and `POST /internalEcho` are not in the intended lists.

**Detail note:** GET for a Function uses `/{function}/{item}`; it does not automatically bind a JSON DTO from query strings. When complex DTO input is needed, use a POST/PUT body and set `Content-Type` explicitly.

## 6. Practicing GET: Supplier and Function with Path Item

### 6.1. `GET /status`

```bash
curl -i 'http://localhost:8080/status' \
  -H 'Accept: application/json'
```

Typical response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"state":"READY","service":"SCF-DEMO"}
```

A Supplier takes no business input from the request body. Per HTTP semantics, GET should be designed as a read operation that does not alter server state aside from ancillary side effects like logging.

### 6.2. `GET /uppercase/{item}`

```bash
curl -i 'http://localhost:8080/uppercase/hello' \
  -H 'Accept: text/plain'
```

Expected response body:

```text
HELLO
```

The input `hello` comes from the **path item**, not a `POST` body. If the value contains spaces or special characters, percent-encode the path segment properly, e.g., `hello%20world`. Arbitrary or complex data should go in the body of an appropriate method.

### 6.3. Non-Equivalent Requests

```bash
# Uses GET, but missing an item for the Function.
curl -i 'http://localhost:8080/uppercase'

# Same name uppercase, but POST is not in the method mapping.
curl -i -X POST 'http://localhost:8080/uppercase' \
  -H 'Content-Type: text/plain' --data 'hello'
```

These two requests can fail for **different reasons**: one lacks the path-input form, while the other is not selected for POST. `404 Not Found` or `405 Method Not Allowed` may vary depending on the adapter, fallback routes, and web runtime. Do not guess the root cause from status codes alone.

## 7. Practicing POST: Single Function and Composition

### 7.1. `POST /quote` with JSON

```bash
curl -i -X POST 'http://localhost:8080/quote' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  --data '{"sku":"BOOK-001","quantity":2}'
```

Expected business response:

```json
{
  "sku": "BOOK-001",
  "quantity": 2,
  "totalPrice": 240000
}
```

Typical success HTTP status is `200 OK`. Because this is `Function<QuoteRequest, QuoteResponse>`, the adapter uses a JSON converter to deserialize the body into the input DTO and serialize the result back to JSON.

### 7.2. `POST /normalize,uppercase` with Plain Text

```bash
curl -i -X POST 'http://localhost:8080/normalize,uppercase' \
  -H 'Content-Type: text/plain' \
  -H 'Accept: text/plain' \
  --data '  hello  '
```

Composition pipeline:

```text
"  hello  "
    |
normalize -> "hello"
    |
uppercase -> "HELLO"
    |
response  -> "HELLO"
```

The pipe in `normalize|uppercase` inside the config file denotes **composition order**, while the comma in `/normalize,uppercase` represents the **same composition**. POST accepts only the items listed in `spring.cloud.function.http.POST`.

### 7.3. Testing Disallowed POST Calls

```bash
# reverse is not listed under POST.
curl -i -X POST 'http://localhost:8080/reverse' \
  -H 'Content-Type: text/plain' --data 'hello'

# Different composition not in the POST list.
curl -i -X POST 'http://localhost:8080/uppercase,normalize' \
  -H 'Content-Type: text/plain' --data '  hello  '

# Internal bean not in any method list.
curl -i -X POST 'http://localhost:8080/internalEcho' \
  -H 'Content-Type: text/plain' --data 'hello'
```

These requests **are outside the intended mappings**. If any of them still invokes a function, inspect effective properties, root/fallback settings, routing headers, custom controllers, and your runtime version rather than assuming method restrictions took effect.

## 8. Practicing PUT: Mapping Does Not Create Idempotency

Configuration:

```properties
spring.cloud.function.http.PUT=replaceStock
```

Call:

```bash
curl -i -X PUT 'http://localhost:8080/replaceStock' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  --data '{"sku":"BOOK-001","quantity":50}'
```

Illustrative response:

```json
{
  "sku": "BOOK-001",
  "quantity": 50,
  "result": "SIMULATED"
}
```

In HTTP semantics, PUT is expected to be **idempotent**: sending the same request multiple times should have the same intended effect as sending it once. However, method-mapping properties only choose routes; they **do not inspect** what `replaceStock.apply()` does. If code writes to a database, emits events, or charges money, the application must implement its own retry/idempotency guarantees.

In this example, the function writes no data; it merely simulates a response to illustrate method and DTO handling. If you need an API replacing resources by ID, URLs like `PUT /stocks/{sku}`, validation, `ETag`, or `If-Match` may require a dedicated Spring MVC/WebFlux controller or router.

## 9. Practicing DELETE: Consumer and 204 Response

Configuration:

```properties
spring.cloud.function.http.DELETE=deleteById
```

Send a simple body:

```bash
curl -i -X DELETE 'http://localhost:8080/deleteById' \
  -H 'Content-Type: text/plain' \
  --data 'BOOK-001'
```

For `Consumer<String> deleteById`, under the default mapping table the SCF HTTP adapter typically returns:

```http
HTTP/1.1 204 No Content
```

**`204 No Content` has no response body.** Do not try to parse JSON from this response. More importantly, our sample bean only logs; `204` **does not prove** an item was deleted from a database or a transaction committed.

For real REST APIs, sending DELETE with a **request body** warrants caution: clients, proxies, and gateways can handle DELETE bodies differently. If you want `DELETE /stocks/{sku}` with a resource ID in the path, use a controller/router with `@PathVariable` and delegate business logic to a functional bean.

### Consumer Is Not Like Function

A `Function<I,O>` produces a return value, whereas `Consumer<I>` has signature `void accept(I input)`. Hence the HTTP adapter uses different default statuses: Function typically returns `200`, Consumer POST/PUT typically returns `202`, and DELETE typically returns `204`. **Assigning a Consumer to DELETE does not automatically turn the function into a CRUD repository.**

## 10. Distinguishing Method Mapping from Function Filtering

Both mechanisms look similar in delimiter syntax, yet answer two different questions.

| Configuration | Question answered | Example |
| --- | --- | --- |
| `spring.cloud.function.definition` | Which function/composition is default or exposed? | `foo;bar` |
| `spring.cloud.function.http.POST` | Which functions/compositions are mapped **specifically for POST**? | `foo;normalize\|uppercase` |
| `spring.cloud.function.web.path` | Which **URL prefix** does the HTTP adapter use? | `/api/functions` |
| `spring.cloud.function.http.ignored-headers` | Which HTTP headers are excluded from header propagation? | `X-Internal-Token` |

**Note:** `spring.cloud.function.http.ignored-headers` shares the `spring.cloud.function.http` prefix, yet **is not an HTTP method**. Do not list it alongside GET/POST/PUT/DELETE mappings.

### 10.1. A Single Composition Without `;` Is Valid

```properties
spring.cloud.function.http.POST=normalize|uppercase
```

This line lists **one composition** for POST. To also add `quote`, separate with a semicolon:

```properties
spring.cloud.function.http.POST=normalize|uppercase;quote
```

### 10.2. Do Not Infer Root Mapping

`spring.cloud.function.definition=normalize|uppercase` can designate a **default composition at root**. By contrast, `spring.cloud.function.http.POST=normalize|uppercase;quote` is a **per-method list**, not an instruction for POST root to auto-pick the first entry.

In multi-bean applications, use named URLs for method-specific mappings. If you need per-method root mappings, test your running SCF version's behavior or configure an explicit HTTP controller/router.

### 10.3. When Combining Both Configurations

An application can combine these properties, but be careful: `spring.cloud.function.definition` is also used for **fallback/function filtering** and by other adapters such as Spring Cloud Stream. Do not assume setting method-specific mappings disables all root/fallback behavior or header-based routing. When combining them, test your exact web adapter/version and every published HTTP route.

## 11. Configuring the HTTP Prefix and Deployment Environments

### 11.1. `spring.cloud.function.web.path`

To place endpoints under `/api/functions`, add:

```properties
spring.cloud.function.web.path=/api/functions
spring.cloud.function.http.GET=status;uppercase
spring.cloud.function.http.POST=normalize|uppercase;quote
spring.cloud.function.http.PUT=replaceStock
spring.cloud.function.http.DELETE=deleteById
```

Expected URLs:

```text
GET    /api/functions/status
GET    /api/functions/uppercase/hello
POST   /api/functions/normalize,uppercase
POST   /api/functions/quote
PUT    /api/functions/replaceStock
DELETE /api/functions/deleteById
```

`web.path` only changes the **base path**, without changing per-method lists or function Java types.

If `server.servlet.context-path=/backend` is set in Spring MVC, client-facing URLs may start with `/backend/api/functions`. When an API gateway rewrites paths, check both the **public URL** and the **actual backend URL** to avoid double-prefixing.

### 11.2. `application.yml`

Equivalent representation:

```yaml
spring:
  cloud:
    function:
      web:
        path: /api/functions
      http:
        GET: "status;uppercase"
        POST: "normalize|uppercase;quote"
        PUT: "replaceStock"
        DELETE: "deleteById"
```

Each entry is a **string**. Do not turn the POST value into a YAML list without testing the binder; SCF documentation specifies definition strings using `;` and `|`.

### 11.3. Environment Variables and Command Line

In Bash you can set:

```bash
export SPRING_CLOUD_FUNCTION_HTTP_GET='status;uppercase'
export SPRING_CLOUD_FUNCTION_HTTP_POST='normalize|uppercase;quote'
export SPRING_CLOUD_FUNCTION_HTTP_PUT='replaceStock'
export SPRING_CLOUD_FUNCTION_HTTP_DELETE='deleteById'
mvn spring-boot:run
```

Or pass properties when launching the artifact:

```bash
java -jar app.jar \
  '--spring.cloud.function.http.GET=status;uppercase' \
  '--spring.cloud.function.http.POST=normalize|uppercase;quote' \
  '--spring.cloud.function.http.PUT=replaceStock' \
  '--spring.cloud.function.http.DELETE=deleteById'
```

`app.jar` is an illustrative filename. In shells, `;` separates commands and `|` creates pipes, so **quote the entire argument**. With environment variables, Spring Boot applies relaxed binding; verify effective properties via tests rather than assuming every casing variant behaves identically across versions.

## 12. What Happens When Calling the Wrong HTTP Method?

There are two cases:

1. **Wrong method on a registered URL**: the HTTP layer may return `405 Method Not Allowed`.
2. **No matching URL/route found**, e.g., an unexposed composition: it may return `404 Not Found`.

In SCF, handler mapping, function filtering, root/fallback, web path, and exact version can all affect the status code. **Never promise** that every unlisted request produces strictly 404 or 405. What must be proven is that **the function does not execute via a forbidden method or route**.

Cases to test:

```bash
# quote is listed for POST, not PUT.
curl -i -X PUT 'http://localhost:8080/quote' \
  -H 'Content-Type: application/json' \
  --data '{"sku":"BOOK-001","quantity":2}'

# replaceStock is listed for PUT, not POST.
curl -i -X POST 'http://localhost:8080/replaceStock' \
  -H 'Content-Type: application/json' \
  --data '{"sku":"BOOK-001","quantity":50}'

# deleteById is listed for DELETE, not POST.
curl -i -X POST 'http://localhost:8080/deleteById' \
  -H 'Content-Type: text/plain' --data 'BOOK-001'

# An internal bean not included in any method list.
curl -i -X POST 'http://localhost:8080/internalEcho' \
  -H 'Content-Type: text/plain' --data 'hello'
```

If any of these requests still execute, hunt down **another route or misconfiguration**. Specifically, never infer from an HTTP error body alone whether a side effect occurred; for writes/deletes, verify logs, test doubles, or database state in tests.

## 13. HTTP Methods Do Not Enforce REST Semantics

Naming properties `POST`, `PUT`, and `DELETE` routes by method, yet **does not turn a function into a full REST controller**.

| HTTP semantics | API design expectation | What SCF method mapping does |
| --- | --- | --- |
| GET | Read data without changing state (safe) | Selects function for GET; does not verify code lacks side effects |
| POST | Process/create per API contract | Calls function mapped for POST |
| PUT | Replace idempotently | Calls function mapped for PUT; does not create idempotency |
| DELETE | Delete or request deletion of a resource | Selects Consumer/function for DELETE; does not delete from database |
| OPTIONS/HEAD | Endpoint, protocol, or HTTP behavior metadata | Depends on web handlers; do not assume all are configured by the same property |
| PATCH | Partial update | Verify SCF adapter support or use an appropriate controller/router |

If an API needs `201 Created`, `409 Conflict`, `ETag`, `If-Match`, resource-path authorization, and custom JSON error payloads, keep business logic in functional beans while using Spring MVC/WebFlux as the HTTP boundary.

### Idempotency and Retries

Suppose `PUT /replaceStock` is sent twice by a client after a timeout. The GET/POST/PUT properties do not prevent double processing, provide an **idempotency key**, or guarantee transaction commits. Design the proper domain layer, test with your database/broker, and handle retries explicitly.

### Authorization Is Separate

Method-specific mapping is **not** an authorization rule. It does not prove a user is permitted to call `DELETE /deleteById`, nor does it guard beans invoked through other controllers, `FunctionCatalog`, or event adapters. In production, enforce authentication, authorization, routing-header controls, and payload limits in Spring Security/API gateways.

## 14. Security When `functionRouter` and Routing Headers Are Present

SCF also includes `functionRouter`, allowing target selection via application properties or message headers in supported configurations. SCF documentation notes that the web adapter can copy HTTP headers into Spring `MessageHeaders`, including routing headers like `spring.cloud.function.definition` when supplied.

Distinguish clearly:

- **Method mapping:** `spring.cloud.function.http.POST=quote` selects which functions the HTTP adapter maps for POST.
- **Message routing:** `functionRouter` can choose a target function inside a message.
- **Authorization:** Spring Security or the gateway decides **who** may call which route.

When external requests reach a dynamic router, enforce an explicit target allowlist, strip or trust only permitted routing headers, and test requests attempting to invoke an internal function. **Never treat HTTP method property lists as an access-control system.**

| `GET /status` | Status 200, JSON with `state=READY` |
| `GET /uppercase/hello` | Status 200, body `HELLO` |
| `POST /normalize,uppercase` | Status 200, body `HELLO` |
| `POST /quote` | Status 200, JSON with `totalPrice=240000` |
| `PUT /replaceStock` | Status 200, accurate simulated result |
| `DELETE /deleteById` | Status 204, empty response body; console logs simulated command |
| `PUT /quote` | Does not execute `quote` via PUT |
| `POST /replaceStock` | Does not execute `replaceStock` via POST |
| `POST /deleteById` | Does not execute `deleteById` via POST |
| `POST /internalEcho` | Does not execute internal bean over HTTP |

For disallowed-method requests, **record the actual status** instead of hardcoding `404` or `405` in advance. When side effects exist, use spies/mocks or test fixtures to verify the forbidden function **did not run**.

### 15.3. Why Real HTTP Tests Are Needed?

Calling directly:

```java
String result = uppercase().apply("hello");
```

only proves Java logic returns `HELLO`; **it does not prove POST is restricted or GET is mapped**. You need integration tests via `MockMvc` (MVC), `WebTestClient` (WebFlux), or an HTTP client matching your runtime, including testing through an API gateway if one exists.

## 16. Common Errors and Resolutions

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| `POST /quote` fails to run | Method config not active or wrong bean name | Check `spring.cloud.function.http.POST` and catalog |
| `POST /uppercase` fails to run | POST only exposes `normalize\|uppercase`, not standalone `uppercase` | Call `/normalize,uppercase` or add `uppercase` if standalone export is desired |
| `GET /uppercase` fails | Function GET requires a path item | Call `GET /uppercase/{item}` |
| DELETE has no response body | Adapter returns `204 No Content` | Do not parse JSON body on 204 |
| DELETE with body is blocked by gateway | Gateway/client handles DELETE bodies differently than expected | Design a dedicated controller/resource path |
| Repeated PUT calls duplicate side effects | Code is not idempotent | Design business logic, retries, and idempotency |
| Property has no effect | Overridden by env/profile/CLI or typo in property key | Inspect effective property sources |
| `normalize\|uppercase;quote` splits in shell | Pipe/semicolon unquoted | Quote the entire argument |
| `404` or `405` differs from expectation | Spring web adapter routing or another handler behaves differently | Inspect endpoint mappings, logs, and runtime |
| Composition still callable via unexpected method | Fallback definition, header router, or custom controller exists | Test actual routes, control routing, and enforce security |
| Wrong `Content-Type` | JSON body sent as plain text or vice versa | Send matching `application/json` / `text/plain` |
| API requires `201`, `409`, `PATCH` | SCF web adapter is too minimal for the HTTP contract | Use an MVC/WebFlux controller/router calling the function |

### Diagnostic Workflow

1. Confirm functional beans are registered in `FunctionCatalog` with the right names and input/output types.
2. Read the **effective values** of `spring.cloud.function.http.GET`, `POST`, `PUT`, and `DELETE`.
3. Check whether `spring.cloud.function.definition`, `web.path`, custom controllers, or gateway rewrites affect routes.
4. Match method + path + `Content-Type` + `Accept`.
5. Call both allowed and disallowed cases with `curl -i`.
6. Check side effects and logs to confirm disallowed methods trigger no business logic.
7. Enforce security/authorization independently of route filtering.
