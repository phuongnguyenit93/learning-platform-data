# Declaring Binder Configuration Names and Assigning Binders to Bindings

Spring Cloud Stream uses Binders to connect application bindings to messaging systems such as Apache Kafka, RabbitMQ, or Apache Pulsar. An application may need to read from Kafka and write to RabbitMQ, send events to two different Kafka clusters, or connect to two independent RabbitMQ brokers. In such cases, you need to declare each binder configuration with its own name and assign the right binder to each binding.

There are three naming concepts to distinguish:

- **Binder type**: the binder implementation type, such as `kafka`, `rabbit`, or `pulsar`. The type is registered by the binder library on the classpath.
- **Binder configuration name**: the name of a specific connection configuration assigned by the application, such as `ordersKafka`, `auditKafka`, or `rabbitCommands`.
- **Binding name**: the input/output endpoint name generated by Spring Cloud Stream from a function, such as `routeOrder-in-0` and `routeOrder-out-0`.

One binder type can have multiple distinct connection configurations. For example, `ordersKafka` and `auditKafka` both have `type: kafka`, but each points to a different Kafka cluster. The `binder` property on a binding takes a **configuration name**, not a destination, topic name, or type name if the configuration has been explicitly named.

## 1. Binder type and Binder configuration name

Each binder library provides a `META-INF/spring.binders` file. This file maps a type identifier key to the configuration class that creates the Binder. For example, the RabbitMQ library registers type `rabbit`, the Kafka library registers type `kafka`; a custom binder must also register its type.

When there is only one binder implementation on the classpath, Spring Cloud Stream can select that binder automatically. When there are multiple binder implementations, the application must explicitly specify which binder serves each binding or set a default binder.

In a multi-broker configuration, one type can be declared multiple times with different configuration names:

| Binder configuration name | Binder type | Broker |
|---|---|---|
| `ordersKafka` | `kafka` | Kafka cluster handling orders |
| `auditKafka` | `kafka` | Kafka cluster storing audit logs |
| `commandsRabbit` | `rabbit` | RabbitMQ cluster sending commands |
| `eventsPulsar` | `pulsar` | Pulsar service for events |

The configuration name is managed by the application. The type must match the type registered by the binder implementation. You should declare `type` explicitly, especially when the configuration name differs from the type.

## 2. Selecting a global binder with defaultBinder

If most bindings share the same binder, you can set a default binder:

~~~yaml
spring:
  cloud:
    stream:
      default-binder: kafka
~~~

Then, bindings that do not declare a `binder` property will use the default binder if that binder is configured and eligible as a default candidate.

You can override it at the binding level:

~~~yaml
spring:
  cloud:
    stream:
      default-binder: kafka
      bindings:
        orders-in-0:
          destination: orders.created
        alerts-out-0:
          destination: operations.alerts
          binder: rabbit
~~~

In this example, `orders-in-0` uses the default binder `kafka`; `alerts-out-0` uses the binder `rabbit`. This approach works well when there is one primary messaging system and only a few flows require another broker.

If multiple binders can act as default and there is no clear choice, binding initialization may be ambiguous. Do not rely on dependency order or YAML key order to select a binder. Set `default-binder` or assign a binder to each binding.

## 3. Assigning a dedicated binder to each binding

The general binding property has the form:

~~~text
spring.cloud.stream.bindings.<bindingName>.binder
~~~

For example, a function reads orders from Kafka and then sends a command to RabbitMQ:

~~~java
@Bean
Function<OrderCreated, ShippingCommand> routeOrder() {
    return event -> new ShippingCommand(
        event.orderId(),
        event.destination()
    );
}
~~~

The function has two default bindings:

- `routeOrder-in-0`: input.
- `routeOrder-out-0`: output.

Configuration:

~~~yaml
spring:
  cloud:
    function:
      definition: routeOrder
    stream:
      bindings:
        routeOrder-in-0:
          destination: orders.created
          group: shipping-service
          binder: kafka
        routeOrder-out-0:
          destination: shipping.commands
          binder: rabbit
~~~

The input binding reads from the `orders.created` topic using the Kafka binder. The output binding publishes to the `shipping.commands` exchange/destination using the Rabbit binder. The function does not need to know broker details; it processes the Java data types passed in by the framework.

Each binding has one selected binder. A consumer binding can read from multiple destinations depending on the binder's capabilities, but the destinations of the same binding still belong to one binder configuration. If you need to receive data from multiple independent systems, create appropriate bindings/processors rather than trying to assign multiple binders to a single binding.

## 4. Declaring named binders in YAML

When separate configuration per broker is needed, use the branch:

~~~text
spring.cloud.stream.binders.<configurationName>
~~~

Important properties:

| Property | Meaning | Default |
|---|---|---|
| `type` | Binder implementation type, e.g., `kafka`, `rabbit`, `pulsar` | Same as configuration name if omitted |
| `environment` | Group of Spring Boot properties dedicated to that binder instance | Empty |
| `inherit-environment` | Whether to inherit the application's environment | `true` |
| `default-candidate` | Whether the configuration is considered as a default binder or only used when explicitly referenced | `true` |

Example declaring two brokers:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        ordersKafka:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${ORDERS_KAFKA_BROKERS:localhost:9092}
        commandsRabbit:
          type: rabbit
          environment:
            spring:
              rabbitmq:
                host: ${COMMANDS_RABBIT_HOST:localhost}
                port: ${COMMANDS_RABBIT_PORT:5672}
                username: ${COMMANDS_RABBIT_USERNAME:guest}
                password: ${COMMANDS_RABBIT_PASSWORD:guest}
~~~

In this example:

- `ordersKafka` is the configuration name; `kafka` is the type.
- `commandsRabbit` is the configuration name; `rabbit` is the type.
- `environment` holds the Spring Boot properties that the binder instance uses to connect.
- Environment values are supplied via environment variables or a secret store at deployment time.

Do not use `ordersKafka` as the type just because it is the configuration name. If the type does not match a binder implementation on the classpath, the framework cannot create the corresponding binder.

## 5. Assigning named binders to bindings

After declaring named binders, assign the configuration name to the appropriate binding:

~~~yaml
spring:
  cloud:
    function:
      definition: routeOrder
    stream:
      bindings:
        routeOrder-in-0:
          destination: orders.created
          group: shipping-service
          binder: ordersKafka
        routeOrder-out-0:
          destination: shipping.commands
          binder: commandsRabbit
      binders:
        ordersKafka:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${ORDERS_KAFKA_BROKERS:localhost:9092}
        commandsRabbit:
          type: rabbit
          environment:
            spring:
              rabbitmq:
                host: ${COMMANDS_RABBIT_HOST:localhost}
                port: ${COMMANDS_RABBIT_PORT:5672}
                username: ${COMMANDS_RABBIT_USERNAME:guest}
                password: ${COMMANDS_RABBIT_PASSWORD:guest}
~~~

This is a complete example for a processor reading from Kafka and writing to RabbitMQ. The `binder` property takes `ordersKafka` and `commandsRabbit`, not `kafka` or `rabbit`, because the application is referencing two named configurations.

If multiple functions are used in the same application, declare the active functions in `spring.cloud.function.definition` and set `binder` on each generated binding. Do not guess binding names from destination names; use the function name plus the `-in-0`, `-out-0`, or corresponding index suffix.

## 6. Connecting two brokers of the same type

Named binders are not just for two different middleware types. They also allow an application to connect to multiple brokers of the same type with separate addresses and credentials.

For example, a function reads audit events from a primary Kafka cluster and writes a copy to an archive Kafka cluster:

~~~java
@Bean
Function<AuditEvent, AuditArchiveRecord> archiveAudit() {
    return event -> new AuditArchiveRecord(
        event.eventId(),
        event.occurredAt(),
        event.action()
    );
}
~~~

~~~yaml
spring:
  cloud:
    function:
      definition: archiveAudit
    stream:
      bindings:
        archiveAudit-in-0:
          destination: audit.events
          group: audit-archiver
          binder: kafkaPrimary
        archiveAudit-out-0:
          destination: audit.archive
          binder: kafkaArchive
      binders:
        kafkaPrimary:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${KAFKA_PRIMARY_BROKERS}
        kafkaArchive:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${KAFKA_ARCHIVE_BROKERS}
~~~

Both configurations have `type: kafka`, but `kafkaPrimary` and `kafkaArchive` have separate environments. The input binding uses the primary cluster; the output binding uses the archive cluster. This pattern also applies to two RabbitMQ brokers or two Pulsar services with separate binder instances.

If you use a shared root property such as `spring.kafka.bootstrap-servers` across multiple binder instances, check whether they accidentally share the same address. With named binders, place connection properties inside each binder's `environment` to clearly specify the target broker.

## 7. Isolating the environment with inheritEnvironment

By default, a binder configuration inherits the application's environment (`inherit-environment: true`). When configuring `environment`, the binder receives its own properties; if you need complete isolation from the application environment, set:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        isolatedKafka:
          type: kafka
          inherit-environment: false
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${ISOLATED_KAFKA_BROKERS}
~~~

When environment inheritance is disabled, the binder context does not receive configuration properties from the application context by default. Therefore, all required properties must be included in `environment`, including connection settings, security settings, and dependent Spring Boot properties. Do not enable isolation without knowing clearly which properties are currently being inherited.

`environment` is a dedicated Spring Boot environment for the binder; it can contain any valid Spring Boot property, not just broker connection properties. You can activate a dedicated profile using `spring.profiles.active` in the binder's environment:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        securedRabbit:
          type: rabbit
          environment:
            spring:
              profiles:
                active: rabbit-production
~~~

The profile is activated inside that binder's environment. Ensure the corresponding profile configuration file and secrets are present at runtime.

## 8. Distinguishing defaultCandidate and defaultBinder

These two properties solve two different problems:

- `default-binder` specifies the default binder that bindings without a declared binder will use.
- `default-candidate` determines whether a binder configuration is considered as a default candidate or only used when directly referenced by a binding.

For example, a binder created solely for an audit flow:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        auditArchive:
          type: kafka
          default-candidate: false
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${AUDIT_ARCHIVE_BROKERS}
      bindings:
        audit-out-0:
          destination: audit.archive
          binder: auditArchive
~~~

`auditArchive` can still be used because the binding references that name directly, but it will not be chosen as the default binder. This is useful when a framework or part of the application adds a binder configuration without wanting to alter the default selection of other bindings.

If a binding has no `binder` and no default binder is available, the framework may fail to determine a binder to create the binding. Ensure every binding is explicitly assigned or has a valid default binder.

## 9. Explicit configuration replaces the default binder mechanism

When named binder configurations are declared in `spring.cloud.stream.binders`, Spring Cloud Stream switches to explicit binder configuration and does not run the automatic default binder creation process as before. Therefore, all binders needed by the application must be fully declared in the configuration.

For example, if the application uses Kafka and RabbitMQ via named configurations, declare both:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        kafkaOrders:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${KAFKA_BROKERS}
        rabbitEvents:
          type: rabbit
          environment:
            spring:
              rabbitmq:
                host: ${RABBIT_HOST}
      bindings:
        orders-in-0:
          destination: orders.created
          binder: kafkaOrders
        events-out-0:
          destination: domain.events
          binder: rabbitEvents
~~~

Do not declare a single named binder and assume other binders on the classpath will still be created automatically by the default mechanism. If the application needs one default configured binder and other configured binders only referenced explicitly, design `defaultCandidate` and explicit binding assignments carefully, then verify the actual binder list at startup.

## 10. Configuring binder-specific properties

Common binding properties reside under:

~~~text
spring.cloud.stream.bindings.<bindingName>
~~~

For example, `destination`, `group`, `content-type`, and `binder` are placed here. Middleware-specific extended properties reside under the prefix for each binder type:

| Binder type | Extended property prefix |
|---|---|
| Kafka | `spring.cloud.stream.kafka.bindings.<bindingName>` |
| RabbitMQ | `spring.cloud.stream.rabbit.bindings.<bindingName>` |
| Pulsar | `spring.cloud.stream.pulsar.bindings.<bindingName>` |

Example:

~~~yaml
spring:
  cloud:
    stream:
      bindings:
        orders-in-0:
          destination: orders.created
          group: order-processor
          binder: ordersKafka
      kafka:
        bindings:
          orders-in-0:
            consumer:
              ack-mode: RECORD
~~~

Extended prefixes remain based on the binder implementation, while `binder` on the binding selects the named configuration. When multiple instances of the same type need different extended properties, check whether that property is supported at the binder environment level or at the binding level; do not mistakenly put Kafka settings under Rabbit or Pulsar.

## 11. A binding does not automatically create a cross-broker transaction

For example, a function reading from Kafka and publishing to RabbitMQ is simply a processing pipeline connecting two brokers. Each binding using its own binder does not create a shared distributed transaction between Kafka and RabbitMQ.

The following scenario can occur:

1. The consumer reads a record from Kafka.
2. The function processes it and publishes a message to RabbitMQ.
3. RabbitMQ has received the message.
4. The application fails before the Kafka offset is committed.
5. Kafka redelivers the record and the function may publish a duplicate to RabbitMQ.

Or publishing to RabbitMQ fails after the Kafka consumer has advanced its offset if the application/ack strategy is misconfigured. Design retries, publisher confirms, consumer acknowledgements, idempotency keys, outbox, or reconciliation processes according to business requirements. Do not claim exactly-once semantics just because each binding is assigned its own binder.

## 12. Boundary between regular Kafka Binder and Kafka Streams Binder

An application can use both the regular Kafka Binder and the Kafka Streams Binder in the same Spring Cloud Stream application if they serve separate functions/processors. However, do not mix both binder types within the same function or consumer.

The Kafka Streams binder family also has specific types such as `kstream`, `ktable`, and `globalktable`. In an application that genuinely runs multiple processors across multiple Kafka clusters or combines the regular Kafka Binder with the Kafka Streams Binder, you must declare the appropriate type for each named binder and assign each binding to the right configuration name.

This example illustrates a specialized scenario:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        kafkaMessages:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${KAFKA_MESSAGES_BROKERS}
        kafkaTopology:
          type: kstream
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    streams:
                      binder:
                        brokers: ${KAFKA_STREAMS_BROKERS}
~~~

Only use the `kstream` configuration when the Kafka Streams binder dependency is present and the function has a matching Kafka Streams signature. Do not set type `kstream` for a regular `Function<String, String>`.

## 13. Dependencies and binder discovery

Declaring a binder configuration does not automatically add the binder library to the classpath. The application must have the corresponding dependency:

- Kafka Binder to use type `kafka`.
- RabbitMQ Binder to use type `rabbit`.
- Pulsar Binder to use type `pulsar`.
- Kafka Streams Binder to use Kafka Streams family types such as `kstream`.

If a binder type is not registered on the classpath, the framework cannot instantiate the binder from YAML alone. For custom binders, the library must provide `META-INF/spring.binders` metadata and configuration to create the Binder bean according to the Binder SPI.

When an application has multiple binder dependencies, verify version compatibility across Spring Cloud Stream and each binder. Use appropriate dependency management/BOM to avoid mixing incompatible binder versions.

## 14. Securing configuration per broker

Each named binder may have its own credentials, TLS settings, and network endpoints. Do not commit passwords, tokens, private keys, or JAAS secrets into YAML:

~~~yaml
spring:
  cloud:
    stream:
      binders:
        securedKafka:
          type: kafka
          environment:
            spring:
              cloud:
                stream:
                  kafka:
                    binder:
                      brokers: ${SECURED_KAFKA_BROKERS}
                      configuration:
                        security.protocol: SASL_SSL
                        sasl.mechanism: PLAIN
                        sasl.jaas.config: ${SECURED_KAFKA_JAAS}
~~~

This example illustrates where to configure Kafka client properties; actual values must follow the cluster's authentication mechanism and be supplied via a secret manager or protected environment variables. For RabbitMQ and Pulsar, place credentials/TLS in the corresponding named binder's `environment`.

If using `inherit-environment: false`, include all required properties in the binder's dedicated environment. Inspect startup logs to ensure no secrets or full connection strings containing credentials are printed.

## 15. Testing multi-binder configurations

Both binder selection and message delivery behavior should be tested:

1. Start the application with all required binder dependencies.
2. Verify each named binder has a valid type and connects to the right broker.
3. Check GET `/actuator/bindings` or binding logs to confirm binding names, destinations, and binder assignments.
4. Publish a message to the input broker and verify the function receives the expected payload.
5. Verify the output appears on the exact broker/destination assigned to the output binding.
6. Test the same binder type with two different brokers and verify messages are not routed to the wrong cluster.
7. Test `default-binder` together with binding-level overrides.
8. Test `default-candidate: false` to ensure the binder is only used when explicitly referenced.
9. Test `inherit-environment: false` and verify the binder still has complete connection configuration.
10. Verify error behavior when a binder dependency is missing, the type is wrong, the configuration name is wrong, or the broker endpoint is missing.
11. Test timeouts, disconnections, retries, and duplicates when forwarding between two brokers.

The Test Binder can verify function logic and message contracts, but it does not replace integration tests against each real broker. For applications connecting to Kafka and RabbitMQ, a test environment with both brokers is needed; for multiple Kafka clusters, verify each binding uses the right cluster with isolated test data.

## 16. Common errors when declaring multiple binders

| Symptom | Possible cause | Resolution |
|---|---|---|
| Binder type not found | Missing binder dependency or wrong type | Check the classpath and keys in `META-INF/spring.binders` |
| Binder configuration not found | Binding uses type instead of configuration name | Use the exact name defined under `spring.cloud.stream.binders` |
| Binding uses the wrong broker | Missing `binder` or incorrect default binder | Explicitly assign the configuration name to the binding |
| Two Kafka bindings connect to the same cluster | Both inherit a root configuration or environments are not separated | Configure separate brokers inside each named binder environment |
| Application does not create default binder | Explicit binder config enabled without declaring all needed binders | Declare all required binders under `binders` |
| Default binder is ambiguous | Multiple default candidates or no default set | Set `default-binder` and adjust `default-candidate` |
| Binder cannot read profile configuration | Profile set in application context instead of binder environment | Set `spring.profiles.active` inside the binder's environment |
| Isolated binder lacks credentials | `inherit-environment: false` without transferring required properties | Add endpoints, auth, TLS, and dependent properties |
| Output does not reach target broker | Wrong binding name or destination/binder assignment | Check actual bindings and initialization logs |
| Duplicates after forwarding failure | No shared transaction between the two brokers | Use idempotency, controlled retries, and outbox/reconciliation |

## 17. Pre-deployment checklist

- [ ] Distinguished binder type, binder configuration name, and binding name.
- [ ] Added dependencies for every binder type used.
- [ ] Each named binder has the correct `type` matching the binder implementation.
- [ ] Each binding is assigned the right configuration name or has a clear default binder.
- [ ] Brokers of the same type have separate named configurations and environments.
- [ ] Understood `inherit-environment` and `default-candidate`.
- [ ] When using explicit binder configuration, declared all required binders completely.
- [ ] Binder-specific properties are placed under the correct middleware prefix.
- [ ] Endpoints and credentials are passed via environment/secret store.
- [ ] Tested each binding against the right broker and destination.
- [ ] Evaluated retries, duplicates, and atomicity when forwarding across different broker types.
- [ ] Verified binder versions are compatible with the version of Spring Cloud Stream in use.

Named binder configuration enables a single application to connect to multiple middleware systems or multiple brokers of the same type. Declare a configuration name for each connection, set `type` according to the binder implementation, configure the dedicated broker in `environment`, and assign that name to `spring.cloud.stream.bindings.<bindingName>.binder`. Use `default-binder` for default flows and `default-candidate` to control which configurations can be selected by default. Proper binder assignment routes bindings to the right broker; it does not automatically create cross-broker transactions, so retries and idempotency must be designed for forwarding flows.
