# Headers, Keys, or Metadata Disappearing Across the Broker

In Spring Cloud Stream, a message may pass through `Supplier`, `Function`, `Consumer`, and one or more Kafka, RabbitMQ, or Pulsar binders. A common bug is that the payload arrives intact, yet `correlationId`, tenant ID, the Kafka key, or topic/partition/offset info does not appear in the target service. This symptom does not necessarily mean the broker "lost" data. The value may not have been attached to the right field, may have been filtered during header mapping, replaced when building a new `Message`, failed deserialization, or belonged to transport metadata that exists only for a single record consumption.

This lesson explains how to distinguish **payload**, **application headers**, **record keys**, and **transport metadata**; isolate losses hop-by-hop; resolve issues in Kafka/RabbitMQ; and write end-to-end tests. Sample configurations illustrate the message-channel Kafka binder under the Spring Cloud Stream functional model; Kafka Streams Binder, RabbitMQ, and Pulsar require APIs suited to each transport.

## 1. Identify the Symptom Before Changing Configuration

| Symptom | Priority Hypothesis | First Place to Check |
|---|---|---|
| Consumer reads payload but lacks `correlationId` | Producer omitted header, mapper filtered it, or function did not forward it | Headers on Spring `Message` before send and raw headers on broker |
| Kafka record has value but key is `null` | ID put only in payload/regular header, never set as Kafka record key | `ProducerRecord.key()` or Kafka console consumer printing keys |
| Kafka input has key, output topic has no key | Function built a new message without copying key or producer key config ignores it | `KafkaHeaders.RECEIVED_KEY` at input, `KafkaHeaders.MESSAGE_KEY` at output |
| Header exists on broker but arrives as `byte[]` or fails to decode | Producer and consumer use different header mappers/encodings | Raw header bytes, `KafkaHeaderMapper`, trusted packages |
| `id` or `timestamp` changes at every service | These are Spring `Message` metadata, not durable business event IDs | Compare with a custom-defined `eventId` |
| Original topic/partition/offset missing after republish | Receive metadata from old record does not become metadata of new record | Add explicit lineage fields if business needs them |
| RabbitMQ lacks expected routing key/`x-death` | AMQP routing/properties and DLX/republish semantics differ from Kafka | RabbitMQ Management UI or AMQP `MessageProperties` |
| Header present in regular consumer but missing in batch/reactive flow | Input type or transformation did not preserve metadata | `Message<?>`, batch metadata, explicit copying |
| Headers break after version upgrade | Header mapping/type conversion or binding config changed | Version-matched reference docs, resolved dependencies, regression tests |

Distinguish **absent**, **present under a different name**, **present with a different type**, **not exposed by function signature**, and **intentionally not forwarded**. Each case requires a different fix.

## 2. Four Information Layers That Must Not Be Equated

Consider an order event:

~~~text
Business event:
  payload: {"orderId":"O-501","status":"PAID"}
  eventId: EV-501
  correlationId: trace-business-501

Kafka record:
  topic: orders.events
  partition: 2
  offset: 1839
  key: O-501
  value: bytes of the business event
  headers: ["correlationId" => bytes, "eventId" => bytes, ...]

Spring Message at consumer:
  payload: OrderEvent or String
  headers:
    correlationId
    eventId
    kafka_receivedMessageKey / KafkaHeaders.RECEIVED_KEY
    kafka_receivedTopic / KafkaHeaders.RECEIVED_TOPIC
    kafka_receivedPartitionId / KafkaHeaders.RECEIVED_PARTITION
    kafka_offset / KafkaHeaders.OFFSET
    ...
~~~

These fields come from different sources:

1. **Payload** carries business data. It is serialized/deserialized based on content type and client configuration.
2. **Application headers** are metadata actively sent by the application: `correlationId`, `tenantId`, `eventId`, `schemaVersion`. When the binder supports them and mappers allow them, they are written to broker metadata.
3. **Record key** is a dedicated routing component of a Kafka record (`key` is distinct from `value` and `headers`). Kafka Streams likewise treats key/value as primary record components. RabbitMQ has no direct Kafka record key equivalent; instead it has routing keys and properties.
4. **Transport/receive metadata** describes a specific transmission or receipt: topic, partition, offset, timestamp, RabbitMQ delivery tag, routing key, or Pulsar message ID. Many of these fields are generated by the client/broker and can differ completely on the next hop.

Do not use Spring's `id` header as a durable business identifier. `MessageHeaders.ID` is framework-generated and is not mapped by the Kafka binder as a user record header; it can change whenever a message is rebuilt. For deduplication, use an explicitly managed `eventId`.

## 3. Hop-by-Hop Isolation Diagram

~~~mermaid
flowchart TD
    A[Producer builds Spring Message] --> B[Output Function / StreamBridge]
    B --> C[Binder outbound header mapper]
    C --> D[(Broker record: key, headers, value)]
    D --> E[Binder inbound header mapper]
    E --> F[Consumer / Input Function]
    F --> G[Function builds new Message]
    G --> H[Output binder and next broker]
    C -. Header present before C but lost after D .-> I[Check headerPatterns / mapper / serialization]
    E -. Present on D but missing at F .-> J[Check inbound mapper / types / native decoding]
    G -. Present at F but lost at H .-> K[Check key and header forwarding]
~~~

The most effective diagnostic method is verifying data at **every boundary**:

1. Before producer calls `send`: which headers does the Spring `Message` have?
2. After binder serializes: what key, native headers, and value appear on the broker record?
3. Immediately after consumer receives: which fields and types exist in `MessageHeaders`?
4. After `Function` processing: does the outgoing `Message` preserve the needed business metadata?
5. After the second publish: does the target broker hold the expected key/headers?

If the raw broker record already contains the headers, stop fixing the producer. If the raw broker record lacks headers, tweaking consumer mapping cannot recreate information that was never sent. Do not rely solely on payload logs: payload logs do not prove record keys or native headers exist.

## 4. A Kafka Record Key Is Not an Arbitrary Header

A Kafka message is a record consisting of **key, value, and headers**. Putting `orderId` inside the payload or in a `businessKey` header does not automatically make the Kafka producer use that value as the record key.

The Spring Cloud Stream Kafka binder supports two common ways:

- Set `KafkaHeaders.MESSAGE_KEY` on the outgoing Spring `Message`.
- Configure producer `messageKeyExpression` to derive the key from the payload or a header.

Example creating a message with a real Kafka key:

~~~java
import java.util.function.Supplier;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

@Configuration
class OrderProducer {

    @Bean
    Supplier<Message<String>> publishOrder() {
        return () -> MessageBuilder
                .withPayload("{\"orderId\":\"O-501\",\"status\":\"PAID\"}")
                .setHeader(KafkaHeaders.MESSAGE_KEY, "O-501")
                .setHeader("eventId", "EV-501")
                .setHeader("correlationId", "trace-business-501")
                .setHeader("tenantId", "tenant-a")
                .build();
    }
}
~~~

This is a structural example; do not deploy this `Supplier` as a production source because the poller would repeatedly emit the same `eventId`. In real applications, derive event IDs/records from input data and set an appropriate cadence. The key takeaway is that `KafkaHeaders.MESSAGE_KEY` controls the **Kafka record key**, rather than creating an arbitrary native header.

Binding configuration:

~~~yaml
spring:
  cloud:
    function:
      definition: publishOrder
    stream:
      bindings:
        publishOrder-out-0:
          destination: orders.events
~~~

To use a custom header instead of `KafkaHeaders.MESSAGE_KEY`:

~~~yaml
spring:
  cloud:
    stream:
      kafka:
        bindings:
          publishOrder-out-0:
            producer:
              messageKeyExpression: "headers['businessKey']"
~~~

With this configuration, the producer must attach `businessKey` to the outgoing message. Do not confuse the Kafka binder's `messageKeyExpression` with the generic Spring Cloud Stream producer's `partitionKeyExpression`: one selects the **Kafka record key**, while the other drives the framework's partitioning mechanism. In systems requiring ordering by business key, inspect the actual key on the broker and how partitions are chosen.

## 5. Reading Keys and Receive Metadata at the Input

For Kafka consumers, choose the `Consumer<Message<T>>` signature when you need to inspect headers:

~~~java
import java.util.function.Consumer;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.Message;

@Configuration
class OrderDiagnostics {

    @Bean
    Consumer<Message<String>> inspectOrder() {
        return message -> {
            var headers = message.getHeaders();

            Object key = headers.get(KafkaHeaders.RECEIVED_KEY);
            Object topic = headers.get(KafkaHeaders.RECEIVED_TOPIC);
            Object partition = headers.get(KafkaHeaders.RECEIVED_PARTITION);
            Object offset = headers.get(KafkaHeaders.OFFSET);
            Object correlationId = headers.get("correlationId");

            System.out.printf(
                    "key=%s topic=%s partition=%s offset=%s correlation=%s%n",
                    key, topic, partition, offset, correlationId);
        };
    }
}
~~~

In Spring for Apache Kafka, `KafkaHeaders.RECEIVED_KEY` holds the key of the **just-received record**. It is not the outgoing `KafkaHeaders.MESSAGE_KEY`; to republish with the same key, explicitly copy that key to the outgoing message or configure the producer appropriately.

If a Kafka record has a `null` key, the received-key header may **not exist at all**. Do not check for missing headers by assuming every message contains `KafkaHeaders.RECEIVED_KEY`.

`RECEIVED_TOPIC`, `RECEIVED_PARTITION`, and `OFFSET` describe the current record. If the message is published to a new topic, the new offset and partition are decided by Kafka, not copied from the original offset.

When using `Consumer<String>`, the function receives only the payload and has no headers argument to inspect. Never conclude the binder lost headers simply because the function signature does not expose `MessageHeaders`.

## 6. Forwarding Keys and Headers Through a Function

A common bug is a Function accepting `Message<String>` yet returning a plain `String` or building a new `Message` without copying important fields. The fact that the framework may automatically forward some headers along certain paths is **not a contract** guaranteeing all keys and broker-specific metadata survive across two publishes.

Example of intentional forwarding:

~~~java
import java.util.Locale;
import java.util.function.Function;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

@Configuration
class OrderRelayConfiguration {

    @Bean
    Function<Message<String>, Message<String>> orderRelay() {
        return incoming -> {
            var output = MessageBuilder.withPayload(
                    incoming.getPayload().trim().toUpperCase(Locale.ROOT));

            Object correlationId = incoming.getHeaders().get("correlationId");
            if (correlationId != null) {
                output.setHeader("correlationId", correlationId);
            }

            Object eventId = incoming.getHeaders().get("eventId");
            if (eventId != null) {
                output.setHeader("eventId", eventId);
            }

            Object key = incoming.getHeaders().get(KafkaHeaders.RECEIVED_KEY);
            if (key != null) {
                output.setHeader(KafkaHeaders.MESSAGE_KEY, key);
            }

            return output.build();
        };
    }
}
~~~

Binding:

~~~yaml
spring:
  cloud:
    function:
      definition: orderRelay
    stream:
      bindings:
        orderRelay-in-0:
          destination: orders.events
          group: order-relay
        orderRelay-out-0:
          destination: orders.normalized
~~~

This is a **Kafka → Kafka** example. It forwards `correlationId`, `eventId`, and the business key without blindly copying all inbound headers. Blind copying can leak `kafka_received*` fields, acknowledgment handles, or error metadata meant strictly for the consumer into another producer.

If you want to record origin lineage, create dedicated application headers such as `sourceTopic` or `sourcePartition`; do not reuse system headers that the binder interprets differently:

~~~java
Object topic = incoming.getHeaders().get(KafkaHeaders.RECEIVED_TOPIC);
if (topic != null) {
    output.setHeader("sourceTopic", topic.toString());
}
~~~

When pipelines span multiple hops, decide consistently whether to track `originalTopic`, `originalPartition`, `originalOffset`, or `lastHopTopic`. These are **application lineage metadata**, not substitutes for the record metadata Kafka provides at the consumer.

## 7. Check Kafka `headerPatterns` Before Blaming the Broker

The Kafka binder maps Spring `MessageHeaders` to Kafka native `Headers` according to the producer `headerPatterns` setting. The Kafka binder reference specifies the default as `*`, excluding `id` and `timestamp`, two framework headers not mapped as user headers.

Example of a configuration prone to dropping headers:

~~~yaml
spring:
  cloud:
    stream:
      kafka:
        bindings:
          orderRelay-out-0:
            producer:
              headerPatterns: "eventId"
~~~

Here `correlationId` and `tenantId` are absent from the allowed patterns, so you cannot expect them to appear as native Kafka headers on the output topic.

Fix per contract:

~~~yaml
spring:
  cloud:
    stream:
      kafka:
        bindings:
          orderRelay-out-0:
            producer:
              headerPatterns: "eventId,correlationId,tenantId,contentType"
~~~

Include only the application headers genuinely needed over the transport in the allowlist. `headerPatterns` takes comma-separated patterns supporting leading/trailing `*` and negation with `!`; **the first matching pattern wins**. Put negations first when excluding sensitive headers.

Note that the Kafka key cannot be fixed by adding `KafkaHeaders.MESSAGE_KEY` to native header patterns. The key is a dedicated `ProducerRecord` field; inspect how the Kafka binder sets the record key.

## 8. Find Custom `KafkaHeaderMapper` Beans That Silently Drop Headers

An application may define a bean named `kafkaBinderHeaderMapper` to customize header mapping. When this bean replaces the default mapper and its implementation does not handle `fromHeaders` or `toHeaders` completely, headers disappear even though the producer attached them.

Anti-pattern example:

~~~java
// Do not use: this mapper drops every header.
@Bean
KafkaHeaderMapper kafkaBinderHeaderMapper() {
    return new KafkaHeaderMapper() {
        @Override
        public void fromHeaders(MessageHeaders source, Headers target) {
            // Do nothing.
        }

        @Override
        public void toHeaders(Headers source, Map<String, Object> target) {
            // Do nothing.
        }
    };
}
~~~

This case is described directly in **Kafka Binder Tips, Tricks and Recipes** under "Adding custom header mapper in Kafka." When headers are missing, check whether a custom mapper bean exists and whether it serializes/deserializes both outbound and inbound directions properly.

Prefer the default mapper when headers only contain common types like `String`/`byte[]`. If a custom mapper is required, test both directions, handle `null` and explicit charsets, restrict the allowed header list, and verify no sensitive data leaks.

Do not add a custom mapper solely because an `id` field did not cross the broker. Use clear application header names like `eventId` or `correlationId` to avoid colliding with Spring `MessageHeaders.ID`'s internal semantics.

## 9. Header Exists but Has the Wrong Type or Is Blocked from Deserialization

Kafka native headers store **byte arrays**. Spring Kafka uses `KafkaHeaderMapper` to map between Java types and bytes. `String` headers may be encoded as UTF-8/raw bytes or as JSON depending on the mapper/version; a consumer written in another language may see bytes without understanding the type wrapper.

Example:

~~~text
Spring producer:
  correlationId: String("abc-123")
Kafka native record:
  correlationId: byte[]
Another consumer:
  must decode UTF-8 or the agreed format
~~~

Some mappers emit metadata headers describing types. If the receiving side uses a different mapper, headers may arrive as `byte[]`, `NonTrustedHeaderType`, or fail to map as expected. `JsonKafkaHeaderMapper` deserializes only a default set of trusted packages; do not configure `addTrustedPackages("*")` just to "fix missing headers" in environments handling untrusted data.

Safe solutions:

- For data shared across multiple services or languages, standardize a simple header contract: UTF-8 `String` or schema-defined `byte[]`.
- Align header mappers, encodings, charsets, and header names across client versions.
- If custom Java classes must be deserialized, allowlist only the exact trusted packages and review security implications.
- Never place complex objects like `Authentication`, `HttpServletRequest`, or transaction contexts directly into broker headers.
- Distinguish a value "not being created" from "bytes existing but failing type decoding."

Spring Kafka's `Message Headers` documentation describes configuring raw-mapped headers and trusted packages. When diagnosing a specific version, consult the Spring Kafka reference aligned with your Spring Cloud BOM.

## 10. `headerMode`, Native Encoding, and `contentType`

Spring Cloud Stream provides the `headerMode` binding property with options such as `headers` (broker native headers), `embeddedHeaders` (embedding headers in the payload for transports needing embedded support), and `none` (no embedding). The default depends on the binder.

Example:

~~~yaml
spring:
  cloud:
    stream:
      bindings:
        orderRelay-in-0:
          consumer:
            headerMode: headers
        orderRelay-out-0:
          producer:
            headerMode: headers
~~~

This illustrates configuration when the binder and version support native headers. Modern Kafka and RabbitMQ support native headers; do not enable `embeddedHeaders` based on advice from older Kafka versions without verifying the actual protocol.

Two other properties to distinguish:

- `producer.useNativeEncoding: true`: delegates **value** serialization to the broker client serializer; payload conversion via binding `contentType` no longer runs in the default way.
- `consumer.useNativeDecoding: true`: delegates value decoding to the broker client deserializer; it must match the producer serializer.

When native encoding/decoding is used, `embeddedHeaders` embedding may be ignored according to the binding properties reference. That **does not mean all native broker headers vanish**; inspect the specific binder mapper. A wrong `contentType` typically causes **payload** conversion failures, distinct from a `null` Kafka record key or a header filtered by patterns.

If messages pass to a consumer not using Spring Cloud Stream, enabling embedded headers that the partner does not understand alters the payload bytes and breaks their parser. Agree on the wire format across all parties.

## 11. Functional Model and Reactive Pipelines Can Alter Metadata

With this function:

~~~java
Function<String, String> upperCase() {
    return value -> value.toUpperCase(Locale.ROOT);
}
~~~

The function sees only the `String` payload and has no way to read or modify headers directly. When correlation IDs or keys must be forwarded, prefer `Function<Message<String>, Message<String>>` as shown in section 6.

Especially in reactive functions `Function<Flux<Message<T>>, Flux<Message<R>>>`, responsibility for building the output `Message` and forwarding headers lies with the reactive code. Do not assume each record automatically keeps keys/metadata if the pipeline uses `map(Message::getPayload)` and builds new messages from the transformed payload.

Illustrative example:

~~~java
@Bean
Function<Flux<Message<String>>, Flux<Message<String>>> reactiveRelay() {
    return flux -> flux.map(incoming -> {
        var builder = MessageBuilder.withPayload(
                incoming.getPayload().toUpperCase(Locale.ROOT));

        Object correlation = incoming.getHeaders().get("correlationId");
        if (correlation != null) {
            builder.setHeader("correlationId", correlation);
        }

        Object key = incoming.getHeaders().get(KafkaHeaders.RECEIVED_KEY);
        if (key != null) {
            builder.setHeader(KafkaHeaders.MESSAGE_KEY, key);
        }
        return builder.build();
    });
}
~~~

This example requires importing `reactor.core.publisher.Flux` and the corresponding Spring Messaging/Spring Kafka classes. With dedicated reactive binders, consult binder documentation because acknowledgment and message propagation can differ from message-channel binders.

**With batch consumers**, do not assume every record is represented by a flat `MessageHeaders`. Some binders wrap payload lists inside `Message<List<?>>` and provide per-element metadata in a dedicated structure. For instance, the Rabbit binder places a list of header maps under `AmqpInboundChannelAdapter.CONSOLIDATED_HEADERS`; the map index corresponds to the payload element index. When headers appear "missing" in batch mode, check consolidated metadata before changing mappers or producers.

## 12. RabbitMQ: AMQP Properties and Routing Keys Differ from Kafka Keys

RabbitMQ transport has these concepts:

- **Exchange** receives messages from producers.
- **Routing key** paired with exchange/binding rules lets the broker select target queues.
- **MessageProperties** and application headers hold `contentType`, `messageId`, `correlationId`, and custom fields.
- **Delivery tag**, consumer tag, and received exchange/routing key are per-delivery metadata.

RabbitMQ has no `ProducerRecord.key` field like Kafka. If routing by customer ID is required, choose a routing key suited to the exchange type or place the business key in an application header/payload per contract. Never set `KafkaHeaders.MESSAGE_KEY` on RabbitMQ expecting it to become an AMQP routing key.

The Rabbit binder supports `headerPatterns` on both input and output, usually defaulting to `['*']` per the binder reference:

~~~yaml
spring:
  cloud:
    stream:
      rabbit:
        bindings:
          audit-in-0:
            consumer:
              headerPatterns: "eventId,correlationId,tenantId,contentType"
          audit-out-0:
            producer:
              headerPatterns: "eventId,correlationId,tenantId,contentType"
~~~

If you narrow the allowlist and omit `correlationId`, the application cannot expect that header to pass through the mapper. Named AMQP properties may also be handled specially by the mapper; not every property is merely a key in the user headers map.

Spring Integration AMQP header mapping also has default rules excluding certain `x-*` headers, specifically to avoid forwarding broker/system metadata by mistake. If you need to preserve a specially prefixed header, check version-specific mapper rules; do not wildcard everything just to copy `x-death` or receive metadata onto a brand-new message.

## 13. RabbitMQ DLQ and Broker-Generated Metadata

When RabbitMQ dead-letters a message, the broker can append `x-death` containing details about the dead-lettering event. When an application republishes to a DLQ via a recoverer, error headers and source headers can differ from the broker's native dead-letter mechanism.

Therefore, do not assume:

- Every message in the DLQ has an identically structured `x-death`.
- `x-death` always survives intact after an intermediate service consumes and republishes via `RabbitTemplate` or `StreamBridge`.
- `deliveryTag` or received routing key is a durable ID for deduplication.
- An `eventId` application header appears automatically if the producer never created it.

If the business needs DLQ traceability, store application `eventId`/`correlationId`, standardize an error metadata schema, and test both **broker DLX** and **application republish** paths separately. Do not stuff huge stack traces into arbitrary headers; RabbitMQ enforces frame/header size limits and the binder truncates certain error details.

## 14. Kafka Streams Binder: Key Is Record Data Inside the Topology

In Kafka Streams, `KStream<K,V>` represents key/value pairs rather than payload plus `MessageHeaders` as in the message-channel binder model. Example:

~~~java
@Bean
Function<KStream<String, String>, KStream<String, String>> normalize() {
    return input -> input.mapValues(value -> value.trim().toUpperCase());
}
~~~

Here `mapValues` preserves the record key in the DSL, whereas `selectKey` or `map` can change the key according to application logic. After `groupBy`, `repartition`, aggregation, join, or materialization, check the actual output key/record semantics: Kafka Streams may create repartition/changelog topics and new records.

Kafka Streams supports native record headers, yet not every API exposes or propagates them like a message-channel `Message<T>`. Some stateful operations produce aggregated records rather than carrying input metadata verbatim. If `eventId` or lineage must survive windows/aggregations, model it explicitly in the aggregate schema or use an appropriate Processor API/header enricher; do not assume the source's Kafka `OFFSET` exists on the aggregate output.

Inspect key serdes, repartition topics, topology output keys, and consumer deserializers whenever a key appears to "disappear" after a join or aggregation. A key serde error can look like a missing key when the consumer is actually decoding it wrongly or failing to read the value.

## 15. Pulsar: Message Keys and Properties Need Explicit Mapping

Apache Pulsar has its own message metadata: `partition_key`/key, key/value `properties`, `messageId`, `publishTime`, `producerName`, `sequenceId`, and others. These values do not automatically map to Kafka `KafkaHeaders.MESSAGE_KEY` or RabbitMQ routing keys.

When using a Pulsar binder or Spring for Apache Pulsar:

1. Check whether the binder maps Spring application headers into Pulsar `properties`.
2. Check how the binder sets Pulsar message key/partition key.
3. Determine whether the receiver reads a `Message` wrapper, raw Pulsar message, or bare payload.
4. Check schema/serialization and metadata conversion.
5. Do not look up `KafkaHeaders.RECEIVED_KEY` expecting to find a Pulsar message key.
6. Distinguish Pulsar-assigned `messageId` from business-assigned `eventId`.

Cross-broker contracts should favor explicitly named, stably formatted business fields. When bridging Kafka → Pulsar, map keys and properties explicitly in the translation layer; do not expect Spring to carry every transport metadata field automatically across two protocols.

## 16. Tracing Headers and Security Headers Are Not the Same

Micrometer Tracing/OpenTelemetry libraries can inject `traceparent`, `tracestate`, baggage, or observability metadata into messages when instrumentation is enabled. If tracing context disappears:

- Verify both producer and consumer have matching tracing instrumentation versions.
- Verify the header mapper does not filter trace headers.
- Verify functions creating new messages preserve propagation context across async/reactive boundaries.
- Distinguish `traceId`, `spanId`, `correlationId`, and `eventId` because they serve different purposes.

Do not turn `traceId` into a business key just to restore ordering. Trace IDs can change across requests/hops and are not deduplication IDs.

Likewise, never blindly copy headers like `Authorization`, session cookies, internal tokens, security principals, or PII onto a broker. A header "not passing through" may be an **intentional security safeguard**, not a bug. Ensure header allowlists obey privacy, multi-tenant authorization, and data-governance policies.

## 17. Observing Real Kafka Records on the Broker

Using a Kafka CLI tool compatible with your broker/client version:

~~~bash
kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic orders.events \
  --from-beginning \
  --property print.key=true \
  --property print.headers=true \
  --property print.partition=true \
  --property print.offset=true
~~~

Do not run `--from-beginning` unbounded on high-volume production topics. Use a test topic with unique message IDs or set consumer timeouts/max-messages flags in your tool.

Read all three parts carefully:

- **Key:** prints `null` if written without a key; it does not auto-extract `orderId` from JSON.
- **Headers:** native key/value metadata on the record; in CLI output, some binary bytes are not human-readable text.
- **Topic/partition/offset:** shows where the record is stored, not original application headers.

With a Java consumer in an integration test, inspect `ConsumerRecord<K,V>`:

~~~java
ConsumerRecord<String, String> record = ...; // Read from test topic.

String key = record.key();
String value = record.value();

Header header = record.headers().lastHeader("correlationId");
String correlationId = header == null
        ? null
        : new String(header.value(), StandardCharsets.UTF_8);

System.out.printf(
        "topic=%s partition=%d offset=%d key=%s correlation=%s value=%s%n",
        record.topic(),
        record.partition(),
        record.offset(),
        key,
        correlationId,
        value);
~~~

This snippet uses `org.apache.kafka.clients.consumer.ConsumerRecord`, `org.apache.kafka.common.header.Header`, and `java.nio.charset.StandardCharsets`. UTF-8 decoding is valid when the contract defines this header as a raw UTF-8 string; if the mapper uses JSON bytes or another format, decode per the actual contract.

This check is decisive: if `record.headers()` contains `correlationId` while `Consumer<Message<String>>` lacks it, focus on the inbound mapper/converter; if the broker record already lacks it, check message construction and the outbound mapper.

## 18. Successful-Send Metadata Is Not Received-Record Metadata

The Kafka binder provides the producer property `recordMetadataChannel`. When configured, a successful send emits a message to that channel with header `KafkaHeaders.RECORD_METADATA` containing the `RecordMetadata` returned by the Kafka producer, such as the partition and offset where the record was written.

~~~yaml
spring:
  cloud:
    stream:
      kafka:
        bindings:
          orderRelay-out-0:
            producer:
              recordMetadataChannel: producerResults
~~~

`producerResults` must be an existing `MessageChannel` bean. This metadata is for observing send outcomes; it does not automatically become a business header on the downstream consumer topic. A newly produced record gets fresh producer/consumer metadata, even while keeping the same `eventId`.

Do not log full serialized payloads merely to observe offsets. Use topic, partition, offset, event ID, masked/hashed keys where needed, and send timestamps for diagnosis; avoid storing personal data in monitoring systems.

## 19. Test Binder Does Not Validate On-the-Wire Headers

Spring Integration Test Binder runs inside the JVM and is well suited for testing function logic and `MessageHeaders` usage. However, it does **not** exercise Kafka record header mapping, AMQP `MessageProperties`, Pulsar keys, serialization, or real brokering.

Tests should cover two layers:

**Logic layer with Test Binder:**

~~~java
var input = MessageBuilder.withPayload(" paid ")
        .setHeader("eventId", "EV-501")
        .setHeader("correlationId", "trace-business-501")
        .build();

var relay = new OrderRelayConfiguration().orderRelay();
Message<String> output = relay.apply(input);

assertThat(output.getPayload()).isEqualTo("PAID");
assertThat(output.getHeaders().get("eventId")).isEqualTo("EV-501");
assertThat(output.getHeaders().get("correlationId"))
        .isEqualTo("trace-business-501");
~~~

This test verifies that the function forwards application headers; it does not prove the producer sets the right Kafka record key because the sample input lacks `KafkaHeaders.RECEIVED_KEY`.

**Integration layer with real Kafka/Rabbit/Pulsar:**

1. Producer sends the defined event ID, correlation ID, business key, and content type.
2. Read the raw record directly from the broker to verify key, value, and native headers.
3. Run the consumer via the real binder and inspect inbound `MessageHeaders`.
4. Run the Function/relay and inspect the raw output record.
5. Verify the producer output key and application headers match the contract.
6. Repeat with `null` keys, missing optional headers, Unicode headers, and byte headers.
7. Test different serializers, custom header mappers, and restrictive `headerPatterns`.
8. Test retry/DLQ paths, republishes, and version migrations if applicable.

For RabbitMQ, use a dedicated test queue and inspect AMQP properties/routing keys via client or management APIs; for Pulsar, read native Pulsar Message metadata. Never claim header portability without corresponding cross-binder integration tests.

## 20. Evidence-Based Troubleshooting Procedure

When handling a "headers lost" ticket, follow this runbook:

1. **Establish identifiers:** broker, topic/exchange, consumer group/queue/subscription, `eventId`, timestamp, and service versions.
2. **Define the expected field:** header name, Java type, wire format, who creates it, and which hops must preserve it. For keys, state explicitly whether it is a Kafka record key, RabbitMQ routing key, or Pulsar key.
3. **Check the producer:** immediately before `send`, are `MessageHeaders` populated as expected? Is the key set per binder rules?
4. **Read raw broker data:** verify key/native headers/value with CLI tools or a test client.
5. **Check binder outbound:** `headerPatterns`, `headerMode`, `messageKeyExpression`, `useNativeEncoding`, and custom mappers.
6. **Check binder inbound:** header mapper, trusted packages, charset, `useNativeDecoding`, and batch semantics.
7. **Check function signature:** `Consumer<T>` or `Consumer<Message<T>>`? Does the function build a new message, or does a reactive pipeline drop context?
8. **Check downstream output:** are application keys/headers set explicitly without carrying stale receive metadata?
9. **Check DLQ/retries:** did the message pass through a recoverer/republisher that altered headers?
10. **Write a regression test:** reproduce the bug with a real binder and lock down the contract against future upgrades.

Avoid "fixes" that copy all `MessageHeaders` blindly or allow deserializing every package. Those shortcuts can leak authentication tokens or sensitive metadata, break downstream transports, and hide the real root cause.

## 21. Quick Diagnostic Table

| If You See... | Check... | Priority Fix |
|---|---|---|
| Kafka key is `null` | `ProducerRecord.key`, `KafkaHeaders.MESSAGE_KEY`, `messageKeyExpression` | Set the key on the right field and confirm on the broker |
| Key exists on input, missing on output | `KafkaHeaders.RECEIVED_KEY` and outgoing message | Copy to `KafkaHeaders.MESSAGE_KEY` or set producer expression |
| Only `correlationId` is missing | Producer/consumer `headerPatterns` | Add to allowlist after reviewing security contract |
| All custom headers missing | `kafkaBinderHeaderMapper` bean, `headerMode` | Use default mapper or fix bidirectional mapping |
| `id` or `timestamp` changes | Spring `MessageHeaders` lifecycle | Use business `eventId`/`createdAt` |
| Header is `byte[]` instead of `String` | Wire encoding and mapper | Align charset/JSON/raw header contract |
| Header becomes `NonTrustedHeaderType` | JSON header mapper trusted packages | Trust only required packages or use String/bytes |
| Original Kafka offset lost after relay | New records receive new offsets | Record lineage intentionally in an application header |
| RabbitMQ routing key not preserved | AMQP routing semantics | Set routing key per binder/protocol, not Kafka key |
| `x-death` differs across DLQ messages | Native DLX vs application republish differ | Check DLQ path and preserve `eventId` |
| Trace context lost across reactive pipeline | Message creation and instrumentation | Propagate context with proper tracing mechanisms |
| Test Binder PASSES but production drops headers | Tests did not cross a real broker | Add raw-record integration tests |

## 22. Prevention Checklist

- Distinguish payload, application headers, record keys, and transport metadata.
- Use clear application header names such as `eventId`, `correlationId`, and `tenantId`.
- Never use framework `id`/`timestamp` as durable business IDs.
- Set Kafka record keys via `KafkaHeaders.MESSAGE_KEY` or `messageKeyExpression`.
- Read `KafkaHeaders.RECEIVED_KEY` when inspecting inbound keyed records.
- Use `Message<T>` whenever a function must read or copy application headers.
- Never blindly copy received metadata or security credentials to the next broker.
- Check `headerPatterns` and custom header mappers in both directions.
- Align wire encoding, charset, content type, and trusted package policies.
- Distinguish `headerMode` from native encoding/decoding and payload conversion.
- For RabbitMQ, define AMQP routing keys/properties and DLQ behavior explicitly.
- For Pulsar, verify keys/properties/messageId using Pulsar binder/client APIs.
- For Kafka Streams, verify topology key/value, repartition, and output semantics.
- Inspect raw broker records and Spring `MessageHeaders` for the same event ID.
- Maintain real-broker integration tests for keys, custom headers, null/bytes, and DLQs.
- Record exact versions of Spring Boot, Spring Cloud Stream, binders, and Spring Kafka/AMQP/Pulsar.

## Summary

When headers, keys, or metadata "disappear" across a broker, the first question is not "is the broker broken?" but **which layer does that value belong to, who creates it, at which boundary is it present, and is it allowed across the next boundary?** In Kafka, the key is a dedicated record field; `KafkaHeaders.MESSAGE_KEY` sets the outbound key while `KafkaHeaders.RECEIVED_KEY` exposes the inbound key. Custom headers depend on mappers and `headerPatterns`. In RabbitMQ and Pulsar, routing keys, properties, and message IDs carry different semantics and must be mapped intentionally. Under the Spring Cloud Stream functional model, inspect inbound `Message<T>`, outbound message creation, and raw broker records to pinpoint the exact place where data was lost.
