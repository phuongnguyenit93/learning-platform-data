# Securing Actuator and Binding Control Operations

Spring Cloud Stream can expose binding details via Spring Boot Actuator and allow operators to stop, start, pause, or resume a binding. These endpoints are useful when troubleshooting, yet they also reveal broker connection configuration and can alter running message flows. Therefore, you must control endpoint exposure, read permissions, and state-changing permissions simultaneously.

In an event-driven application, an unauthorized request to `/actuator/bindings` can expose topic names, consumer groups, retry configurations, broker addresses, or authentication details. An unauthorized POST request can even stop a consumer, cause backlogs to grow, halt order processing, or change message delivery timing. This lesson covers deploying Actuator with restricted access, securing binding control operations, and testing access permissions.

## 1. What Do Actuator and the Bindings Endpoint Provide?

Spring Boot Actuator provides administrative and observability endpoints for applications. Spring Cloud Stream adds the `bindings` endpoint to inspect current bindings and control the lifecycle of each binding.

When web and Actuator dependencies are present, Spring Cloud Stream can expose the following routes:

| HTTP method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/actuator/bindings` | List bindings |
| `GET` | `/actuator/bindings/{bindingName}` | View the state of a binding |
| `POST` | `/actuator/bindings/{bindingName}` | Change binding state using JSON |

For example, a binding name for the `processOrder` function could be `processOrder-in-0`. This is the binding name generated by Spring Cloud Stream from the function definition; it is not necessarily identical to the topic or queue name on the broker.

This endpoint can return information such as:

- Binding name and destination.
- Whether the binding is input or output.
- Consumer group.
- The binder in use.
- Current lifecycle state.
- Certain extended consumer/producer binder properties.

Detailed information helps diagnose issues, but can also reveal how the system connects to Kafka, RabbitMQ, or Pulsar. Treat GET requests as operations that require protection as well.

## 2. Adding Dependencies and Exposing Only Necessary Endpoints

Actuator and web are optional dependencies for Spring Cloud Stream. The application must include Actuator and a web stack such as Spring MVC or WebFlux:

~~~kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
    implementation("org.springframework.boot:spring-boot-starter-web")
    implementation("org.springframework.boot:spring-boot-starter-security")
    implementation("org.springframework.boot:spring-boot-starter-oauth2-resource-server")
    testImplementation("org.springframework.security:spring-security-test")
}
~~~

If the application uses WebFlux, replace `spring-boot-starter-web` with `spring-boot-starter-webflux` and choose the Spring Security configuration matching the reactive stack. Do not add both web stacks simultaneously just to enable Actuator.

By default, Spring Boot exposes only `health` over HTTP. To enable the bindings endpoint, add `bindings` to the exposure list:

~~~yaml
management:
  endpoints:
    web:
      exposure:
        include: "health,info,bindings"
~~~

This list exposes only the three selected endpoints. Avoid using `include: "*"` in production applications because it can expose additional endpoints containing configuration, logs, beans, heap dumps, or other administrative operations.

There are three conditions to distinguish:

1. **Endpoint exists:** dependencies and auto-configuration have registered the endpoint.
2. **Access permitted:** Actuator access settings allow the corresponding operation.
3. **Exposed:** the endpoint is published over HTTP or JMX.

Being exposed does not mean authenticated or authorized. Spring Security must still control who can read and who can send POST requests.

## 3. Restricting Actuator Access

On Spring Boot versions supporting endpoint access properties, you can default to deny and re-enable only the endpoints needed:

~~~yaml
management:
  endpoints:
    access:
      default: none
    web:
      exposure:
        include: "health,info,bindings"
  endpoint:
    health:
      access: read-only
    info:
      access: read-only
    bindings:
      access: unrestricted
~~~

Here:

- `management.endpoints.access.default: none` closes default access to endpoints.
- `health` and `info` are read-only.
- `bindings` requires access for both GET and POST because this endpoint includes state-control operations.
- The `exposure.include` list still determines which endpoints are published over HTTP.

`unrestricted` here refers to Actuator operation access, not allowing unauthenticated users. Pair it with Spring Security and network policies. If your Spring Boot version does not yet support endpoint access properties, use the exposure and Spring Security mechanisms appropriate for that version.

## 4. Separating the Management Port from the Business API Port

One way to reduce the attack surface is running management endpoints on a separate port:

~~~yaml
management:
  server:
    port: 9001
  endpoints:
    web:
      exposure:
        include: "health,info,bindings"
~~~

This example moves Actuator to port `9001`, while business APIs continue using the main application port. In production environments, allow only management networks, monitoring systems, or operations workloads to reach this port.

You can bind to a specific address using `management.server.address` if the infrastructure has a dedicated management interface. The address value must suit your container, VM, or Kubernetes networking; do not copy `127.0.0.1` into production if management systems need to connect from another host.

A separate port does not replace authentication. If a firewall or service mesh is misconfigured, the endpoint can still be reached. Combine:

- Private network or management subnet.
- Firewall/security group/network policy allowing only management sources.
- TLS for management connections.
- Authentication and authorization in Spring Security.
- Auditing for every state-changing operation.

## 5. Controlling Binding State Over HTTP

Spring Cloud Stream accepts JSON with a `state` field at the binding's endpoint:

~~~bash
curl --request POST \
  --url https://stream-admin.internal:9001/actuator/bindings/processOrder-in-0 \
  --header "Authorization: Bearer <access-token>" \
  --header "Content-Type: application/json" \
  --data '{"state":"STOPPED"}'
~~~

The states documented by binding visualization/control are:

| State | Operational Meaning |
|---|---|
| `STOPPED` | Stop the binding |
| `STARTED` | Start the binding |
| `PAUSED` | Pause the binding if supported by the binder |
| `RESUMED` | Resume a paused binding if supported by the binder |

You can send `STARTED`, `PAUSED`, or `RESUMED` by changing the value in JSON. `STOPPED` and `STARTED` are lifecycle operations; `PAUSED` and `RESUMED` depend on binder capabilities and the underlying broker technology.

As of Spring Cloud Stream 5.1, current documentation notes that Kafka and Solace support `PAUSED`/`RESUMED` states. Do not assume RabbitMQ or Pulsar share the same semantics just because the endpoint accepts the same JSON. Check your binder version and application logs before adding pause/resume operations to a runbook.

Stopping an input binding causes the consumer to stop receiving messages and can build up backlog. Stopping an output binding can make the message publishing path unavailable. Before taking action, verify the exact binding name, input/output direction, traffic impact, and recovery procedure.

## 6. Distinguishing Binding State from Application State

Controlling a binding is not equivalent to stopping the entire Spring Boot application. An application can have multiple input/output bindings; stopping one binding affects only that binding.

~~~text
Spring Cloud Stream application
          |
          +-- orders-in-0  ---> Kafka topic orders.events
          |
          +-- orders-out-0 ---> Kafka topic orders.processed
          |
          +-- audit-out-0  ---> RabbitMQ exchange audit.events
~~~

If only `orders-in-0` is stopped, other bindings can continue operating. However, functions depending on that input will stop receiving new data from the stopped binding.

Lifecycle operations are also not permanent deployment configuration changes. When the application restarts, bindings are recreated according to the application's configuration and lifecycle policy. Do not use binding control POSTs as a way to permanently alter `autoStartup`, destination, group, or binder in configuration.

## 7. Separating Read and Control Permissions

Permissions should be split by responsibility:

| Principal | Permissions |
|---|---|
| Monitoring service | Read health and required metrics |
| Actuator viewer | Read permitted Actuator information |
| Stream operator | Read bindings and perform pause/resume/stop/start per procedure |
| Application user | Call business APIs; does not automatically hold binding admin rights |

An access token with scope `stream:read` can be used to read state. Scope `stream:control` should be granted only to humans or workloads permitted to alter state. Never share a single broad-privilege token across dashboards, business apps, and automation.

If using roles instead of OAuth2 scopes, keep the same principle: read permissions and control permissions must be distinct. Do not rely on obscure endpoint names or an alternate port as a substitute for authorization.

## 8. Configuring Spring Security for Actuator

The example below uses the Spring Boot 3.x Servlet stack and OAuth2 Resource Server with JWT bearer tokens. Scopes are mapped to authorities prefixed with `SCOPE_`.

Binding POST requests require `SCOPE_stream:control`; binding GET requests require `SCOPE_stream:read`; other Actuator endpoints require `SCOPE_actuator:read`.

~~~java
import org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.util.matcher.AndRequestMatcher;
import org.springframework.security.web.util.matcher.RequestMatcher;

@Configuration
@EnableMethodSecurity
class ManagementSecurityConfiguration {

    @Bean
    @Order(1)
    SecurityFilterChain actuatorSecurity(HttpSecurity http) throws Exception {
        RequestMatcher bindingPost = new AndRequestMatcher(
                EndpointRequest.to("bindings"),
                request -> HttpMethod.POST.matches(request.getMethod()));

        return http
                .securityMatcher(EndpointRequest.toAnyEndpoint())
                .authorizeHttpRequests(authorize -> authorize
                        .requestMatchers(bindingPost)
                            .hasAuthority("SCOPE_stream:control")
                        .requestMatchers(EndpointRequest.to("bindings"))
                            .hasAuthority("SCOPE_stream:read")
                        .anyRequest()
                            .hasAuthority("SCOPE_actuator:read"))
                .oauth2ResourceServer(oauth2 ->
                        oauth2.jwt(Customizer.withDefaults()))
                .sessionManagement(session -> session
                        .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                // Suitable only for stateless management APIs using bearer tokens.
                .csrf(AbstractHttpConfigurer::disable)
                .build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain applicationSecurity(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(authorize -> authorize
                        .anyRequest().authenticated())
                .oauth2ResourceServer(oauth2 ->
                        oauth2.jwt(Customizer.withDefaults()))
                .build();
    }
}
~~~

Key points to note:

- `EndpointRequest.toAnyEndpoint()` scopes the first chain to Actuator endpoints.
- The POST matcher for `bindings` is placed before the general `bindings` matcher.
- `stream:control` applies only to state-changing requests.
- `stream:read` permits binding GET requests.
- The second chain protects the remaining application routes.
- `@Order(1)` ensures the management chain is evaluated before the application chain.

When defining a custom `SecurityFilterChain`, Spring Boot no longer applies automatic Actuator security configuration as it does when no custom chain exists. Therefore, you must configure both Actuator and business APIs completely. If the application already has a custom security chain, integrate the matchers into the existing chain ordering rather than creating conflicting configurations.

The example above targets bearer tokens that do not rely on cookies or HTTP sessions. Because the Actuator chain is stateless and authenticates with `Authorization: Bearer`, CSRF is disabled in that specific chain. If endpoints are accessed via browser sessions, cookies, or automatic browser Basic authentication, keep CSRF protection enabled and require valid CSRF tokens on POSTs. Never disable CSRF application-wide just to make a curl command work.

`EndpointRequest` imports vary across Spring Boot generations. The snippet uses the Spring Boot 3.x package; verify the exact API matching the Spring Boot BOM used by your application.

## 9. Allowing Only Approved Binding Names

Even authorized operators should be restricted to an approved list of controllable bindings. A typo in a name can stop the wrong stream; automation accepting arbitrary binding names can affect out-of-scope flows.

The list can be managed in configuration:

~~~yaml
stream:
  operations:
    controllable-bindings:
      - processOrder-in-0
      - enrichOrder-in-0
~~~

Before executing a command:

1. Verify the binding name is in the allowlist.
2. Verify the binding exists and is in the expected state.
3. Verify the operation is valid for the binder and input/output direction.
4. Require an operational reason or incident ID.
5. Record caller, binding, previous state, new state, and outcome.

Do not allow clients to pass wildcards like `*` or assemble binding names from untrusted data. For multi-binding operations, execute each binding under control and record individual results; do not assume one POST is atomic across the entire application.

## 10. Controlling Bindings via Java API

Since Spring Cloud Stream 3.1, applications can inject `BindingsLifecycleController` to query and modify the lifecycle of individual bindings. This API is useful when integrating operations into an internal management service.

Example operations:

~~~java
BindingsLifecycleController controller =
        applicationContext.getBean(BindingsLifecycleController.class);

var bindingState = controller.queryState("processOrder-in-0");

controller.stop("processOrder-in-0");
controller.start("processOrder-in-0");
controller.pause("processOrder-in-0");
controller.resume("processOrder-in-0");
~~~

Pause/resume operations still depend on binder support. `BindingsLifecycleController` is an API inside the same application context; Spring Security protecting HTTP endpoints does not automatically guard direct Java calls.

If wrapping this API in a management service, enable method security and enforce permissions at the service layer:

~~~java
import java.util.Set;

import org.springframework.cloud.stream.binding.BindingsLifecycleController;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;

@Service
class BindingOperations {

    private static final Set<String> ALLOWED_BINDINGS =
            Set.of("processOrder-in-0", "enrichOrder-in-0");

    private final BindingsLifecycleController lifecycle;

    BindingOperations(BindingsLifecycleController lifecycle) {
        this.lifecycle = lifecycle;
    }

    @PreAuthorize("hasAuthority('SCOPE_stream:control')")
    public void stop(String bindingName) {
        requireAllowed(bindingName);
        lifecycle.stop(bindingName);
    }

    @PreAuthorize("hasAuthority('SCOPE_stream:control')")
    public void start(String bindingName) {
        requireAllowed(bindingName);
        lifecycle.start(bindingName);
    }

    private void requireAllowed(String bindingName) {
        if (!ALLOWED_BINDINGS.contains(bindingName)) {
            throw new IllegalArgumentException(
                    "Binding is not approved for runtime control");
        }
    }
}
~~~

For `@PreAuthorize` to work, enable method security with `@EnableMethodSecurity` in configuration. If the service is invoked through an internal controller, that endpoint must also be secured. Never expose a new controller wrapper while forgetting to apply authentication, authorization, and auditing.

## 11. Auditing Control Operations

Changing binding lifecycle state is an operational action, not just a routine HTTP request. Each state change should record:

| Audit Field | Example |
|---|---|
| Timestamp | UTC timestamp |
| Principal | Subject or service account |
| Action | `STOPPED`, `STARTED`, `PAUSED`, `RESUMED` |
| Binding | `processOrder-in-0` |
| Previous state | `RUNNING` |
| New state | `STOPPED` |
| Reason | Incident or change ticket |
| Request ID | Correlation ID |
| Result | Success or exception |

Never write bearer tokens, passwords, SASL JAAS strings, or full binder configuration payloads into audit logs. Audit records need enough detail for traceability without copying secrets into a log system with broader access scope.

Audit events can be sent to a centralized management system or stored in an audit store with dedicated retention and read permissions. If using Spring Boot's `AuditEventRepository`, define where it persists, retention periods, and access controls; simply having the `auditevents` endpoint does not create a durable audit store.

## 12. Preventing Credential Leakage via GET bindings

The bindings endpoint can expose extended binder properties. Some Kafka configurations contain `sasl.jaas.config`; TLS configurations may also contain keystore/truststore paths or passwords. Thus, GET access itself is sensitive.

Spring Cloud Stream recommends providing a `SanitizingFunction` to mask values such as `sasl.jaas.config`. Example:

~~~java
import java.util.Locale;
import java.util.Set;

import org.springframework.boot.actuate.endpoint.SanitizingFunction;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ActuatorDataSanitization {

    private static final Set<String> SENSITIVE_KEYS = Set.of(
            "sasl.jaas.config",
            "ssl.keystore.password",
            "ssl.truststore.password",
            "ssl.key.password");

    @Bean
    SanitizingFunction bindingSecretsSanitizer() {
        return data -> {
            String key = data.getKey().toLowerCase(Locale.ROOT);
            return SENSITIVE_KEYS.contains(key)
                    ? data.withValue("******")
                    : data;
        };
    }
}
~~~

**Do not assume `SanitizingFunction` is guaranteed to apply to every version of `/actuator/bindings`.** Reports exist for Spring Boot 3.2.4 and Spring Cloud 2023.0.1 where `sasl.jaas.config` appeared in responses and the sanitization function was not invoked by the bindings endpoint. Spring Cloud Stream documentation shows sanitizer configuration examples, yet actual behavior must be verified against your exact version and application payload.

Therefore:

- Do not expose `bindings` publicly just because `SanitizingFunction` is declared.
- Use a secret manager or environment injection to manage credentials rather than hardcoding them in source.
- Inspect actual GET responses in integration tests to confirm every sensitive key is masked.
- If the endpoint still returns secret data, do not grant broad GET access; consider a custom management endpoint returning only needed fields or stripping sensitive fields in a version-appropriate way.
- Never paste full `/actuator/bindings` responses into public logs or tickets.

## 13. Protecting Management Endpoints at the Network Layer

Spring Security is the application protection layer; network policy reduces the sources able to reach the endpoint:

~~~text
Operator / Monitoring
        |
        v
Private management network
        |
        v
Firewall / Network Policy
        |
        v
Management port 9001
        |
        v
Spring Security
        |
        v
/actuator/bindings
~~~

In Kubernetes, use a NetworkPolicy allowing only operations namespaces or service accounts to reach the management port. On VMs or cloud networks, use matching security groups/firewalls. If management endpoints sit behind an ingress or gateway, the gateway configuration must never bypass application authentication.

CORS does not replace authorization. Allowing only a single browser origin does not block curl, other services, or non-browser clients. Similarly, an obscure URL or uncommon port is not an authentication mechanism.

## 14. Testing Authorization with MockMvc

Tests must verify both read access and state-changing access. The example below assumes the Actuator chain uses JWT bearer tokens and CSRF is disabled only in that stateless management chain:

~~~java
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.jwt;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.test.web.servlet.MockMvc;

@SpringBootTest
@AutoConfigureMockMvc
class BindingActuatorSecurityTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void readerCanInspectBindings() throws Exception {
        mockMvc.perform(get("/actuator/bindings")
                .with(jwt().authorities(
                        new SimpleGrantedAuthority("SCOPE_stream:read"))))
                .andExpect(status().isOk());
    }

    @Test
    void readerCannotStopBinding() throws Exception {
        mockMvc.perform(post("/actuator/bindings/processOrder-in-0")
                .with(jwt().authorities(
                        new SimpleGrantedAuthority("SCOPE_stream:read")))
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"state\":\"STOPPED\"}"))
                .andExpect(status().isForbidden());
    }

    @Test
    void operatorCanRequestBindingControl() throws Exception {
        mockMvc.perform(post("/actuator/bindings/processOrder-in-0")
                .with(jwt().authorities(
                        new SimpleGrantedAuthority("SCOPE_stream:control")))
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"state\":\"STOPPED\"}"))
                .andExpect(status().isOk());
    }
}
~~~

The last test requires a real `processOrder-in-0` binding in the test context along with an appropriate binder. If the binding does not exist, the result may be an error unrelated to authorization; thus create a clear test binding before asserting status codes.

Beyond these three tests, verify:

- Requests without a token are rejected.
- Tokens with scope `stream:read` cannot POST.
- Tokens with scope `stream:control` can control only bindings in the allowlist.
- POST requests with invalid states are rejected.
- Non-existent binding names do not affect other bindings.
- GET responses do not contain credentials.
- The endpoint remains unreachable from networks outside the management network.

If using browser sessions, add tests confirming POST without a CSRF token is rejected and POST with a valid CSRF token is processed.

## 15. Safe Operational Procedure When Stopping a Binding

Before stopping a binding:

1. Confirm the binding name and destination from an authorized GET.
2. Inspect the consumer group, partition assignments, or related queue/subscription.
3. Confirm the impact on backlog, SLA, and dependent functions.
4. Record the incident/change ID and reason.
5. Execute the operation using a token with the control scope.
6. Re-read the state to confirm the binding changed.
7. Monitor backlog and processing errors while stopped.
8. Start or resume following the approved runbook.
9. Confirm consumers resume receiving messages and backlog decreases.
10. Close the incident after verifying business outcomes.

Do not stop bindings in bulk based merely on a name pattern. When maintaining an entire consumer group, specify the stopping sequence, how in-flight messages are handled, and the restart procedure to avoid traffic spikes on the broker.

## 16. Common Errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| `/actuator/bindings` returns 404 | Missing Actuator/web dependency or `bindings` not exposed | Check dependencies and `management.endpoints.web.exposure.include` |
| GET works but POST returns 403 | Missing control permission or CSRF token | Check scope/role and management chain CSRF policy |
| Spring Security present but Actuator not protected as expected | Custom `SecurityFilterChain` backs off Boot auto-security | Create separate chains for Actuator and the remaining API |
| `PAUSED` has no effect | Binder or broker technology does not support pause/resume | Check binder version and use supported lifecycle operations |
| Binding stopped but backlog grows | Consumer is not receiving messages while stopped | Monitor lag/queue depth and plan resume |
| GET bindings exposes sensitive config | Response contains unsanitized extended binder properties | Restrict GET permissions, test response, and mask per version |
| Operator controls wrong binding | Missing allowlist or name check | Enforce allowlist and verify destination before changing |
| Business API accidentally left open | Custom security chain handles only Actuator, missing main chain | Add a chain protecting all non-Actuator requests |
| Audit lacks detail | Logging only HTTP status or generic messages | Record principal, binding, old/new state, reason, and request ID |

## 17. Pre-Production Checklist

- Expose only `health`, `info`, and genuinely needed endpoints.
- Do not use wildcard exposure without strong justification and tight controls.
- Configure Actuator access explicitly; open `bindings` only for required operations.
- Use a management port/private network and firewall/network policy.
- Protect Actuator with authentication and authorization.
- Separate binding read permissions from POST control permissions.
- Grant control scopes only to approved operators or automation.
- Keep CSRF enabled for browser sessions/cookies; disable only in appropriate stateless bearer chains.
- Protect remaining application routes whenever a custom `SecurityFilterChain` is defined.
- Restrict controllable binding names with an allowlist.
- Verify how your binder supports `STOPPED`, `STARTED`, `PAUSED`, and `RESUMED`.
- Verify bindings responses contain no credentials or secrets.
- Do not assume `SanitizingFunction` already masks data on the bindings endpoint.
- Audit all state-changing operations.
- Maintain runbooks for stopping, restarting, and monitoring backlog.
- Include tests for 401, 403, operator privileges, invalid bindings, and secret leakage.

Actuator enables observing bindings and controlling message flow lifecycles, yet the `bindings` endpoint can reveal broker settings and accept commands that alter consumer/producer behavior. Expose only necessary endpoints, place them in a management network, authenticate every request, separate read permissions from control permissions, restrict allowed bindings, and audit every operation. In particular, inspect real responses to verify credentials are never exposed; never treat declaring a sanitizer as proof that the endpoint masks all sensitive data.
