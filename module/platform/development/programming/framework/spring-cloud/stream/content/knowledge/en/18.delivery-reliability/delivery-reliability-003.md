# Inbox Tables, Unique Constraints, and Duplicate Message Control

Brokers in event-driven systems typically deliver messages under an at-least-once model. If a consumer finishes processing but stops before acknowledging the message or committing the offset, the broker can redeliver that message. Retries, rebalances, reconnects, and DLQ replays can also cause the same event to appear multiple times.

An **inbox** table records events that a logical consumer has already processed. A unique constraint on the event identifier prevents multiple instances of the same consumer from applying the same data change twice. When the inbox record and the business change are committed in the same database transaction, redeliveries can be safely detected.

An inbox does not turn a broker into an exactly-once delivery system. It provides idempotency for effects inside the same data transaction while helping the application recover when the broker redelivers a message.

## 1. Why Must Consumers Tolerate Duplicate Messages?

A common processing flow consists of receiving a message, updating the database, and then confirming to the broker:

~~~text
Broker
  |
  v
Consumer receives event
  |
  v
Update database
  |
  v
Commit transaction
  |
  v
Ack message / commit offset
~~~

Suppose the database commits successfully, but the process stops before acknowledgement or offset commit completes. The broker does not know the business operation finished, so it may redeliver the event. The consumer receives it a second time, and without an idempotency check, it could add inventory again, create a second invoice, or send a duplicate email.

Common sources of redelivery/duplicates include:

- The consumer finishes processing but loses connection before acking.
- A Kafka consumer undergoes a rebalance before processing or offset commit finishes.
- RabbitMQ redelivers unacknowledged messages after a consumer closes.
- Pulsar redelivers unacknowledged messages or after a negative acknowledgement/ack timeout.
- The producer resends after a timeout without knowing whether the broker received the previous attempt.
- A DLQ is replayed or data is reloaded from a backup.

Therefore, "sent once" and "business effect processed once" are two distinct concepts. The consumer must recognize the same event across all redeliveries.

## 2. Distinguishing Event ID, Message ID, and Deduplication Key

Do not use an internal framework message object ID as a business identifier. A message may be repackaged or recreated during a retry, whereas the business event remains a single event.

| Identifier | Scope | Suitable as an inbox key? |
|---|---|---|
| Event ID | A business event generated by the producer | Yes, if stable across retries/replays |
| Source + Event ID | An event within a producer's namespace | Yes, suitable when multiple producers might collide on IDs |
| Spring MessageHeaders.ID | A message object instance in Spring Messaging | Should not be used as a business ID |
| Kafka offset | Record position within a topic-partition | Identifies position only in that log; not a shared event ID |
| Rabbit delivery tag | A delivery on a channel | Not stable across redeliveries |
| Pulsar message ID | Message position by broker/topic | Useful for broker diagnostics, but cross-system contracts should have their own event ID |
| Correlation ID | Group of events in a workflow | No; multiple distinct events share the same correlation ID |

The producer should generate the event ID once when creating the event and keep that same ID across all republish attempts. If an ID is only unique within a producer's scope, use the `(source, eventId)` pair as the key. For example, `orders-service + evt-1001`.

Do not generate a new event ID on each retry of the same outbox record. If the ID changes, the consumer treats each send as a new event and cannot deduplicate it.

## 3. Inbox Table Model

A basic inbox table stores the logical consumer, event source, event ID, and processing timestamp:

~~~sql
CREATE TABLE consumer_inbox (
    consumer_name VARCHAR(120) NOT NULL,
    source        VARCHAR(200) NOT NULL,
    event_id      VARCHAR(200) NOT NULL,
    payload_hash  CHAR(64) NOT NULL,
    received_at   TIMESTAMP WITH TIME ZONE NOT NULL,
    processed_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (consumer_name, source, event_id)
);
~~~

The composite primary key ensures a logical consumer records each event once within a source namespace. `payload_hash` helps detect cases where a producer reuses the same event ID while sending different content. `received_at` and `processed_at` support investigation, latency measurement, and retention policies.

In the short-transaction model presented in this lesson, the inbox row is committed in the same transaction as the business change. If the business logic fails and the transaction rolls back, the inbox row rolls back as well. Thus, the existence of an inbox row means the database effect committed successfully.

The consumer name must represent a **logical role**, not a machine name or instance ID:

- Replicas of `inventory-projection` share the same `consumer_name`.
- A notification-sending consumer uses a separate `notification-dispatcher`.
- An analytics consumer uses a separate `sales-analytics`.

If all services shared a single consumer name, one service could mark an event as processed and cause other services to skip it. If each replica used a different name, every instance could process the same event once.

## 4. Creating an Event Envelope with a Stable Identifier

Example event envelope carrying `source` and `eventId`:

~~~java
import java.math.BigDecimal;
import java.time.Instant;

public record EventEnvelope<T>(
    String eventId,
    String source,
    String eventType,
    Instant occurredAt,
    T data
) {}

public record OrderPlaced(
    String orderId,
    BigDecimal total,
    String currency
) {}
~~~

The producer generates the event ID when the business event is formed:

~~~java
import java.time.Instant;
import java.util.UUID;

public EventEnvelope<OrderPlaced> createOrderEvent(Order order) {
    return new EventEnvelope<>(
        UUID.randomUUID().toString(),
        "orders-service",
        "OrderPlaced",
        Instant.now(),
        new OrderPlaced(
            order.publicId(),
            order.total(),
            order.currency()
        )
    );
}
~~~

The example above is called only once for a new event. If the application uses a transactional outbox, persist the envelope in the same business transaction. The relay reads that exact record and publishes with the same `eventId` and payload on retries.

If an event is regenerated from a previously received command, ensure command idempotency or persist the generated event ID. Simply calling a random UUID each time a request arrives creates a new event when the client resends the same command.

## 5. Integrating the Inbox with a Spring Cloud Stream Consumer

Spring Cloud Stream can receive the envelope via a `Consumer` bean. The consumer delegates work to a service with its own transaction:

~~~java
import java.util.function.Consumer;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class OrderConsumers {

    @Bean
    Consumer<EventEnvelope<OrderPlaced>> orderPlacedConsumer(
            OrderInboxService inboxService) {
        return inboxService::handle;
    }
}
~~~

Binding configuration:

~~~yaml
spring:
  cloud:
    function:
      definition: orderPlacedConsumer

    stream:
      bindings:
        orderPlacedConsumer-in-0:
          destination: orders.placed
          group: inventory-projection
          content-type: application/json
~~~

Every replica of the inventory role uses the same group and the same consumer name in the inbox table. If another logical consumer needs to receive the event independently, it has its own group and its own inbox namespace.

Because the event ID lives in the envelope contract, the service can read it without depending on headers generated by the binder or Spring Messaging. If a system places the event ID in a header, ensure that header is propagated through the binder and validate its presence before processing. Do not use `MessageHeaders.ID` as a substitute for the business event ID.

## 6. Writing the Inbox and Business Change in the Same Transaction

The most important rule is that **inserting the inbox row and updating business data must be in the same database transaction**. Do not commit the inbox first and process business logic in a separate transaction, because the process could stop between the two steps: the next delivery would see the inbox entry and skip the event even though the business effect never happened.

The following example uses PostgreSQL `ON CONFLICT DO NOTHING` syntax. This is an atomic insert; for other databases, use the equivalent upsert/insert-ignore syntax.

~~~java
import java.util.Objects;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderInboxService {

    private static final String CONSUMER = "inventory-projection";

    private final JdbcTemplate jdbc;
    private final OrderRepository orders;
    private final PayloadFingerprint fingerprint;

    public OrderInboxService(
            JdbcTemplate jdbc,
            OrderRepository orders,
            PayloadFingerprint fingerprint) {
        this.jdbc = jdbc;
        this.orders = orders;
        this.fingerprint = fingerprint;
    }

    @Transactional
    public void handle(EventEnvelope<OrderPlaced> event) {
        String hash = fingerprint.sha256(event.data());

        int inserted = jdbc.update("""
            INSERT INTO consumer_inbox (
                consumer_name, source, event_id, payload_hash,
                received_at, processed_at
            )
            VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP)
            ON CONFLICT (consumer_name, source, event_id) DO NOTHING
            """,
            CONSUMER,
            event.source(),
            event.eventId(),
            hash
        );

        if (inserted == 0) {
            String previousHash = jdbc.queryForObject("""
                SELECT payload_hash
                FROM consumer_inbox
                WHERE consumer_name = ?
                  AND source = ?
                  AND event_id = ?
                """,
                String.class,
                CONSUMER,
                event.source(),
                event.eventId()
            );

            if (!Objects.equals(previousHash, hash)) {
                throw new EventIdentityConflictException(
                    "Same source/eventId arrived with a different payload"
                );
            }

            // Event was already processed earlier: do not repeat the inventory change.
            return;
        }

        // Business change is in the same transaction as the inbox insert.
        orders.applyPlacedEvent(event.data());
    }
}
~~~

`PayloadFingerprint` is an application adapter that produces a SHA-256 digest from a canonicalized payload representation:

~~~java
public interface PayloadFingerprint {
    String sha256(Object payload);
}
~~~

In implementation, use canonical serialization or deterministic normalization rules so the same payload always produces the same hash. Do not directly hash JSON whose field order or number formatting varies randomly across serializations.

Example exception when the same event ID arrives with different content:

~~~java
public class EventIdentityConflictException extends RuntimeException {
    public EventIdentityConflictException(String message) {
        super(message);
    }
}
~~~

If `inserted == 1`, the new event is recorded and business processing proceeds. If `inserted == 0`, the key already exists. Matching hashes indicate a redelivery/replay of the same content; the service skips the side effect. Differing hashes indicate the producer reused an event ID for a different payload or there is a contract error; alert and quarantine rather than treating it as a normal duplicate.

Put `EventIdentityConflictException` in its own Java file in the same package. Types like `OrderRepository`, `OrderPlaced`, `EventEnvelope`, and `PayloadFingerprint` are also separately defined application components.

## 7. Why Use a Unique Constraint Instead of SELECT Then INSERT?

A seemingly simple approach is:

1. SELECT to check if the event ID already exists.
2. If not present, INSERT.
3. Execute business logic.

This approach has a race condition when two instances receive the same event nearly simultaneously:

~~~text
Instance A                    Instance B
    |                             |
    | SELECT -> not found         |
    |                             | SELECT -> not found
    | INSERT                      |
    |                             | INSERT
    |                             |
    v                             v
Both may execute the side effect
~~~

A unique constraint in the database is the final arbiter. It guarantees only one transaction can create the `(consumer_name, source, event_id)` key. With PostgreSQL, `INSERT ... ON CONFLICT DO NOTHING` handles contention cleanly without catching unique violation errors as normal control flow.

When using a different database:

- Choose an insert-ignore/upsert syntax with atomic semantics.
- Or use an insert mechanism with controlled duplicate-error handling compatible with your transaction manager and driver.
- Do not assume a SELECT before INSERT protects against concurrent execution across multiple instances.
- Verify isolation levels, unique indexes, and how the database handles concurrent transactions.

Do not catch a constraint error and keep using a transaction if the database or JPA provider has already marked the transaction rollback-only. Use an atomic upsert statement or an appropriate transaction/savepoint mechanism.

## 8. What Happens in Failure Windows?

The table below describes how the inbox coordinates with transactions and broker acknowledgements:

| Failure timing | Database state | When the broker redelivers |
|---|---|---|
| Before inserting into inbox | No inbox row, no side effect | Consumer processes it as a new event |
| After insert but before business update, transaction rolls back | Inbox insert rolls back | Consumer reprocesses from the beginning |
| After business update but before database commit, transaction rolls back | Both inbox and business update roll back | Consumer reprocesses from the beginning |
| After database commit but before broker ack/offset commit | Inbox and business update committed | Unique key detects duplicate, skips side effect |
| After broker ack/offset commit | Inbox and business update committed | No redelivery needed in normal flow |

For this table to hold, the inbox and business operations must genuinely share the same database transaction manager, and broker acknowledgement must complete only after the handler/transaction succeeds per the configured binder semantics. There is no automatic distributed transaction between database and broker merely from using `@Transactional`.

Check your binder's ack/commit mode and test real failure windows. With Kafka, observe offset commits and redelivery after killing the consumer. With RabbitMQ, observe acknowledgements and redelivery. With Pulsar, verify subscription acknowledgements and redelivery. Do not claim end-to-end exactly-once from an inbox table alone.

## 9. Consumer Identity and Deduplication Scope

The inbox key must reflect the logical unit of work. The same event may need to be processed independently by multiple consumers:

~~~text
Event evt-1001
      |
      +---- inventory-projection / evt-1001
      |
      +---- notification-dispatcher / evt-1001
      |
      +---- sales-analytics / evt-1001
~~~

Each consumer has its own inbox key. As a result, inventory finishing processing does not cause notification to skip the event.

Keep `consumer_name` stable when deploying a new version if it is still the same logical job and must continue deduplicating. If you change the consumer name, the database treats it as a new consumer; old events may be reprocessed. This can be useful when intentionally building a new read model, provided you use a dedicated target table/schema or have a clear replay and side-effect plan.

Do not include pod name, hostname, process ID, or instance ID in the consumer name. Those values change during scaling/restarts and give each instance an isolated deduplication scope, defeating shared idempotency across replicas.

## 10. Same Event ID with Different Payload Is a Contract Error

A single event ID must never represent two different payloads. If the same `source` and `eventId` appear with a different hash, the causes may include:

- The producer generated an unstable event ID or reused an ID.
- Two producers share the same source despite not sharing a namespace.
- A relay/outbox payload was mutated after the event had already been published.
- Data was altered in transit or a producer violated the contract.

Do not ignore this case as a normal duplicate. Record a dedicated metric, preserve traces of both the original and new events per security policy, and investigate the producer. Do not overwrite the old payload hash to "fix" the inbox, as that hides an identity violation.

Hashing is only an additional consistency check. It does not replace schema validation, signatures, or source authentication mechanisms when the system has high security requirements.

## 11. Side Effects Outside the Database Need Separate Mechanisms

An inbox transaction only protects effects inside the same database transaction. If the consumer calls a payment API, sends an email, or publishes a new event, a database rollback cannot undo an external action that already succeeded.

Dangerous example:

~~~text
BEGIN DB TRANSACTION
  INSERT inbox
  CALL payment API  ---> API already charged successfully
  UPDATE order
  DB COMMIT fails
ROLLBACK
~~~

The broker redelivers the event. Because the inbox insert rolled back, the consumer calls the payment API again. The customer could be charged twice.

Approaches to handle this:

- **Target-service idempotency key:** send a stable key such as `consumerName:source:eventId`; the target API must store and deduplicate that key.
- **Transactional outbox:** write the outbound command/event to an outbox in the same transaction as the inbox and business change; a relay sends it after commit.
- **Stateful workflow/saga:** store step-by-step state, retry, and reconcile when the API result is indeterminate.
- **Inbox state machine:** for long-running work, store received, processing, completed states, attempt count, and a lease so another worker can recover.

Avoid holding a database transaction open while waiting on a slow API whenever possible. For long-running tasks, use a state machine with leases and target-service idempotency. Mark completion only after obtaining a verifiable outcome.

## 12. Separating Inbox and Outbox for Bidirectional Event Flows

Inbox records received events; outbox records events or commands to emit. When a consumer processes an incoming event and needs to emit a downstream event, it can write the inbox row, domain update, and outbox row in the same transaction:

~~~text
Single database transaction
  |
  +-- INSERT consumer_inbox
  |
  +-- UPDATE orders
  |
  +-- INSERT outbox_events
          |
          v
       COMMIT
          |
          v
    Outbox relay publish
          |
          v
        Broker
~~~

If the transaction rolls back, the inbox, domain change, and outbox all roll back. If commit succeeds but the relay has not sent yet, the outbox remains ready to send later. If the relay sends the message but crashes before marking it sent, it may publish again; the downstream consumer still needs inbox/idempotency.

Inbox and outbox address two opposite directions of the same integration boundary. They do not eliminate all duplicates; they turn duplicates into safe, recoverable operations.

## 13. Long-Running Processing: States, Leases, and Recovery

For short work that finishes within a single database transaction, inserting into the inbox and updating business state in the same transaction is simplest. For long-running work, do not keep a transaction open for the entire duration. An extended inbox table can be used:

| Field | Purpose |
|---|---|
| `consumer_name, source, event_id` | Unique key |
| `status` | RECEIVED, PROCESSING, COMPLETED, or FAILED |
| `attempt_count` | Number of worker attempts |
| `lease_owner` | Worker currently holding processing ownership |
| `lease_until` | Timestamp when the lease expires |
| `last_error_code` | Most recent error code |
| `received_at, updated_at` | Lifecycle tracking |

Workers claim records atomically, picking only unprocessed records or records whose lease has expired. After claiming, the worker executes the step with an idempotency key. On success, it transitions status to COMPLETED; on failure, it increments attempts and schedules a retry.

Leases must be renewed for long tasks and bounded by an expiration so a dead worker does not hold the lock forever. However, an expired lease can allow two workers to execute concurrently if the old worker is still running. Therefore, fencing tokens or idempotency keys at the target side effect are still required; a lease alone does not guarantee mutual exclusion.

Do not mark COMPLETED immediately upon receiving the message. If the worker stops before the side effect, redeliveries would see it marked complete and skip the work. State transitions must follow verifiable completion boundaries.

## 14. Inbox Retention and Replay

The inbox must be retained long enough to cover the window during which events can be redelivered or replayed:

- Kafka topic retention and the window during which offsets can be reset.
- RabbitMQ messages held in queues/DLQs or republished from archives.
- Pulsar subscription backlog and retention permitting re-reads.
- Operational replays from object storage, backups, or old outboxes.

If an inbox record is deleted before an old event can reappear, the consumer will treat that event as new and run the side effect again. Retention must therefore align with replay policies, DLQ retention, backup windows, and business requirements.

You can time-partition the table or clean up data in batches, while ensuring the unique key remains valid across the deduplication window. If you need longer retention with smaller storage, move records to historical storage or keep compact/tombstone records containing only the key and hash.

Do not delete inbox records on an arbitrary TTL just because the table grows large. Define the minimum retention period, measure storage, plan archiving, and test replay after cleanup.

## 15. Testing Idempotency and Concurrency

Key tests:

| Scenario | Expected outcome |
|---|---|
| Send the same event twice sequentially | Database side effect occurs only once |
| Two instances receive the same event concurrently | Unique key allows only one transaction to execute the side effect |
| Error before commit | Both inbox and business change roll back |
| DB commit succeeds but broker ack fails | Redelivery is detected as a duplicate |
| Same event ID with different payload | Raises event identity conflict, does not silently ignore |
| Different consumer receives the same event | That consumer still processes it due to its own namespace |
| Replay after deployment | Same consumer name preserves deduplication |
| Replay after inbox cleanup | Verify retention policy prevents unwanted duplicate side effects |
| External API succeeds then consumer crashes | Idempotency key at target API prevents double execution |

Example unit/integration test for duplicates:

~~~java
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.verify;

import org.junit.jupiter.api.Test;

class OrderInboxServiceTest {

    @Test
    void duplicateEventDoesNotApplyOrderTwice() {
        EventEnvelope<OrderPlaced> event = sampleEvent("evt-1001");

        inboxService.handle(event);
        inboxService.handle(event);

        verify(orderRepository, times(1))
            .applyPlacedEvent(event.data());
    }
}
~~~

That test requires a real database or Testcontainers to verify the unique constraint and transaction. A plain mocked repository cannot prove the atomicity of `INSERT ... ON CONFLICT`.

For concurrency tests, send the same event to two concurrent transactions/instances and confirm only one business update occurs. For failure-window tests, stop the consumer after database commit but before broker ack, then verify redelivery does not create a second side effect.

## 16. Observing the Inbox in Production

Track metrics with bounded cardinality:

- Count of new inbox inserts per consumer.
- Count of skipped duplicates.
- Count of event identity conflicts.
- Count of transaction rollbacks during event processing.
- Count of records stuck in PROCESSING beyond lease expiration (if using a state machine).
- Age of incomplete inbox records.
- Retry counts and redelivery counts.
- Table size, growth rate, and cleanup duration.

Structured logs should include `consumer_name`, `source`, `event_id`, `event_type`, outcome `NEW/ DUPLICATE/CONFLICT`, and correlation ID if present. Do not use event ID as a metric label because its cardinality is effectively unbounded. Do not log full payloads or sensitive data unless needed for investigation.

Alert when duplicates spike abnormally, identity conflicts appear, inbox backlog or expired PROCESSING leases grow, or cleanup falls behind the write rate.

## 17. Hands-On Workflow and Completion Criteria

Complete the exercise with an inventory-updating consumer:

1. Define an event envelope containing `source`, `eventId`, and `OrderPlaced` payload.
2. Create an inbox table with primary key `(consumer_name, source, event_id)`.
3. Write a Spring Cloud Stream consumer receiving the envelope.
4. Use a single transaction to insert the inbox row and update inventory.
5. Send the same event twice; verify inventory changes only once.
6. Run two instances in the same consumer group and send the same event concurrently; verify the unique constraint protects the side effect.
7. Simulate a database rollback; verify the inbox record is not committed.
8. Simulate a successful database commit followed by a failed broker ack/offset commit; verify the redelivery is skipped.
9. Send the same event ID with a different payload; verify an identity conflict alert is raised.
10. Add another logical consumer and verify it has its own inbox namespace.
11. Try sending an email or calling an external API; add an idempotency key or outbox.
12. Define retention and the replay window before cleaning up the inbox.

You are done when you can explain why a message may be delivered multiple times; design a stable unique key; execute the inbox insert and side effect in the same transaction; prevent race conditions across replicas; and distinguish database effects protected by the inbox from external side effects requiring dedicated idempotency/outbox handling.
