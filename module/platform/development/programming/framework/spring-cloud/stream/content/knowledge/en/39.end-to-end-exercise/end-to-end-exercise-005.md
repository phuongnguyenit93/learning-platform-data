# Idempotent Consumer with Inbox Pattern and Unique Constraints

A Spring Cloud Stream consumer can receive the same event multiple times. A producer may resend when it fails to receive a publish confirmation; a broker may redeliver an unacknowledged message; Kafka may re-read a record after a consumer finishes processing but crashes before committing its offset; Pulsar may redeliver after an acknowledgment timeout. Retries and replays can also reintroduce an old event hours or days later.

If every delivery deducts money, increments inventory, or creates a new order, duplicates corrupt business data. Consumers must handle redeliveries safely: the same event may arrive multiple times, yet its business effect is applied only once within that consumer's scope.

The Inbox pattern combines a table storing received event identities with a database unique constraint. The consumer records the event marker and updates business data in the same transaction. The unique constraint serves as the final arbiter when two deliveries of the same event arrive concurrently.

## 1. Why Can Brokers Redeliver Messages?

Messaging systems typically favor redelivery when uncertain whether a consumer completed processing. This yields at-least-once semantics: a message may be delivered one or more times until completion is confirmed via the broker's acknowledgment mechanism.

Common scenarios:

- Producer publishes successfully but loses connection before receiving confirmation, so it resends.
- RabbitMQ consumer finishes partial work, then the channel closes before the broker receives the ACK.
- Kafka consumer updates the database, then the process dies before committing the offset.
- Pulsar consumer fails to ACK before the acknowledgment timeout or disconnects.
- An operator manually replays messages for data recovery or backfilling a time window.
- Retry topics, dead-letter recovery, or redrives re-inject old events into the processing pipeline.

Example failure window:

~~~mermaid
sequenceDiagram
    participant B as Broker
    participant C as Consumer
    participant D as Database
    B->>C: Event E-101
    C->>D: Update order and commit
    Note over C,B: Process dies before ACK / offset commit
    B->>C: Redeliver E-101
    C->>D: Update order again?
~~~

The database committed, yet the broker does not know it. From the broker's perspective, the event remains unacknowledged; redelivery is expected behavior. The consumer must recognize that the event was already applied and finish the redelivery without repeating side effects.

## 2. What Does the Inbox Pattern Solve?

An inbox is a table in the consumer's database storing identifiers of events successfully processed by a logical consumer. An inbox row typically represents a consumer-event pair:

    (consumer_name, producer_id, event_id)

When a message arrives, the consumer attempts to insert this key into the inbox. A unique constraint ensures only one transaction can insert the same key. If the insert succeeds, the transaction proceeds to update business data. If the key already exists, the event was processed previously and the current delivery can complete as a duplicate.

~~~mermaid
flowchart TD
    A["Receive event"] --> B["Start DB transaction"]
    B --> C["INSERT inbox with unique key"]
    C --> D{"One row inserted?"}
    D -- No --> E["Already processed: skip duplicate"]
    D -- Yes --> F["Update business state"]
    F --> G["Commit transaction"]
    E --> H["Handler returns normally"]
    G --> H
    H --> I["Binder/broker acknowledges per configuration"]
~~~

Crucially, the inbox insert and business update must commit or roll back together. If the inbox insert commits separately and the process dies before updating business data, subsequent deliveries get marked as duplicates even though the business change never happened. If the business update commits separately and the inbox insert fails, redelivery can repeat the side effect.

## 3. Designing Stable Event Identities

Consumers need an event identity that stays stable across every retry, redelivery, and replay. Use an event ID generated by the producer and preserved on resends.

An envelope might look like:

~~~json
{
  "id": "7c83c4f2-3e0f-4d7c-9b8e-4d6c6c2c0101",
  "source": "order-service",
  "type": "com.example.order.created.v1",
  "subject": "orders/ORD-1001",
  "time": "2026-11-24T08:30:00Z",
  "data": {
    "orderId": "ORD-1001",
    "customerId": "CUS-42",
    "amount": 125.50
  }
}
~~~

In this example, `id` is the event identifier, `source` is the producer identity, and `type` describes the contract. With CloudEvents, `(source, id)` can serve as the identity per the producer's contract. The database example below uses `UUID` for `event_id`; if your contract uses arbitrary string IDs, change `event_id` to `VARCHAR` and store the exact string.

Never generate a new UUID inside the consumer on every delivery; doing so gives each redelivery a different key and prevents the inbox from detecting duplicates. Also avoid using timestamps or raw business payloads as IDs if uniqueness is not guaranteed.

### 3.1. Choosing the Unique Key Scope

Event IDs are not always globally unique across an entire platform. Choose the key scope according to the contract:

| Scenario | Recommended key |
|---|---|
| Event ID globally unique across platform | `(consumer_name, event_id)` |
| Event ID unique only per producer | `(consumer_name, producer_id, event_id)` |
| Event ID unique only per tenant | `(consumer_name, tenant_id, producer_id, event_id)` |
| Multiple logical consumers need the same event | Each consumer has its own `consumer_name` |

`consumer_name` is the stable name of the logical handler, such as `orders-projection` or `billing-ledger`. Do not embed deployment versions like `orders-projection-v2` if v2 simply replaces v1 and must inherit deduplication history. Changing `consumer_name` creates a new inbox namespace, allowing the same events to be applied again.

If two independent consumers both need to process the same event, each consumer gets its own key. Never share a single inbox table keyed only by `event_id` and accidentally block the second consumer.

## 4. Creating the Inbox Table with a Unique Constraint

The example below uses PostgreSQL:

~~~sql
CREATE TABLE consumer_inbox (
    consumer_name  VARCHAR(120) NOT NULL,
    producer_id    VARCHAR(160) NOT NULL,
    event_id       UUID NOT NULL,
    event_type     VARCHAR(240) NOT NULL,
    payload_hash   BYTEA,
    received_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    processed_at   TIMESTAMPTZ,
    CONSTRAINT pk_consumer_inbox
        PRIMARY KEY (consumer_name, producer_id, event_id)
);
~~~

The primary key simultaneously enforces a unique constraint across the three columns. The database guarantees uniqueness even when multiple threads, Pods, or consumers process events concurrently.

If IDs are only unique per tenant, add `tenant_id` to both the table and the primary key, and include `tenant_id` in insert statements. Do not add tenant checks solely in application code while omitting it from the database unique constraint.

Column meanings:

- `consumer_name`: logical consumer owning the execution.
- `producer_id`: producer identity namespace.
- `event_id`: stable ID generated by the producer.
- `event_type`: aids investigation and per-contract metrics.
- `payload_hash`: optional, detects producers reusing the same ID for different payloads.
- `received_at`: timestamp when the transaction wrote the inbox row.
- `processed_at`: timestamp when the business update completed, updated before transaction commit.

For synchronous single-transaction processing, the inbox row becomes visible only after commit. `processed_at` is updated after the business update and before commit; a transaction rollback removes both the inbox row and business changes. If you need separate start and completion timestamps, use the asynchronous state machine pattern discussed later.

Do not store full payloads inside the inbox unless there is a clear audit/replay need. Storing IDs and metadata is usually enough for deduplication; payloads may contain personal data or cause rapid table bloat.

## 5. Unique Constraints as the Guard Against Race Conditions

A common flawed implementation:

~~~java
if (!inboxRepository.existsById(eventId)) {
    orderService.apply(event);
    inboxRepository.save(new InboxEntry(eventId));
}
~~~

Two consumers can both execute `existsById` before either inserts. Both see the entry missing, and both apply the business update. This is a classic check-then-act race condition.

An application-level distributed lock is also error-prone if locks expire, processes die, or instances fail to share a single lock service. A database unique constraint provides atomic arbitration right where business data is written.

Rules:

1. Let the database attempt to insert the inbox key.
2. Only the transaction whose insert succeeds executes the business update.
3. Duplicate transactions must not execute side effects.
4. If the business update fails, roll back the inbox insert as well.

The unique constraint must live in a database shared across all consumer instances. A `HashSet` or local cache only deduplicates within a single JVM; it fails across restarts, scale-outs, or multiple Pods.

## 6. Insert-if-Absent with PostgreSQL

PostgreSQL supports `ON CONFLICT DO NOTHING`. The statement returns the number of inserted rows:

~~~sql
INSERT INTO consumer_inbox (
    consumer_name,
    producer_id,
    event_id,
    event_type,
    payload_hash
)
VALUES (
    :consumerName,
    :producerId,
    :eventId,
    :eventType,
    :payloadHash
)
ON CONFLICT (consumer_name, producer_id, event_id)
DO NOTHING;
~~~

- Result `1`: this transaction claimed the event key and may proceed with the business update.
- Result `0`: the key already exists; the event has already been recorded by this logical consumer's inbox.

When two concurrent transactions insert the same key, PostgreSQL checks the unique index and arbitrates the conflict. The losing transaction waits for the winning transaction's outcome; once the winner commits, the loser's statement inserts zero rows.

Do not use `ON CONFLICT DO UPDATE` to blindly overwrite payloads or timestamps. A duplicate carrying a different payload may signal a serious producer bug; overwriting hides that evidence.

## 7. Integrating with Spring Cloud Stream and JdbcTemplate

The following example illustrates an imperative consumer receiving `OrderCreated`, using `JdbcTemplate` to claim the event in the inbox, and updating an orders projection table. Assume the inbox and business tables live in the same database under the same transaction manager.

~~~java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.UUID;

public record OrderCreated(
    String producerId,
    UUID eventId,
    String orderId,
    String customerId,
    BigDecimal amount,
    Instant occurredAt
) {}
~~~

Transactional service:

~~~java
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderCreatedHandler {

    private static final String CONSUMER = "orders-projection";

    private final JdbcTemplate jdbc;

    public OrderCreatedHandler(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public boolean handle(OrderCreated event) {
        int inserted = jdbc.update("""
            INSERT INTO consumer_inbox (
                consumer_name,
                producer_id,
                event_id,
                event_type
            )
            VALUES (?, ?, ?, ?)
            ON CONFLICT (consumer_name, producer_id, event_id)
            DO NOTHING
            """,
            CONSUMER,
            event.producerId(),
            event.eventId(),
            "OrderCreated"
        );

        if (inserted == 0) {
            return false; // Duplicate: business update does not run again.
        }

        jdbc.update("""
            INSERT INTO order_projection (
                order_id, customer_id, amount, created_at
            )
            VALUES (?, ?, ?, ?)
            """,
            event.orderId(),
            event.customerId(),
            event.amount(),
            event.occurredAt()
        );

        jdbc.update("""
            UPDATE consumer_inbox
            SET processed_at = clock_timestamp()
            WHERE consumer_name = ?
              AND producer_id = ?
              AND event_id = ?
            """,
            CONSUMER,
            event.producerId(),
            event.eventId()
        );

        return true;
    }
}
~~~

Spring Cloud Stream function invoking the service:

~~~java
import java.util.function.Consumer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class OrderConsumerConfiguration {

    @Bean
    Consumer<OrderCreated> orderCreated(OrderCreatedHandler handler) {
        return event -> handler.handle(event);
    }
}
~~~

Example binding configuration:

~~~yaml
spring:
  cloud:
    function:
      definition: orderCreated
    stream:
      bindings:
        orderCreated-in-0:
          destination: orders.created
          group: orders-projection
~~~

The service transaction completes before `handler.handle` returns. If an exception escapes the handler, the transaction rolls back and the framework/binder applies the configured error handling, retry, or dead-letter policy. When the handler returns normally for a duplicate, the binder can acknowledge that delivery according to its acknowledgment semantics.

### 7.1. Why Does the Transactional Service Live in a Separate Bean?

Spring typically applies `@Transactional` via proxies. Calling a transactional method from another method on the same object (self-invocation) bypasses the proxy and fails to open a transaction as expected.

Placing the transaction on a separate service bean injected into the function bean ensures calls pass through the proxy. Verify that the proper transaction manager is selected and that JDBC/JPA share the same `DataSource`.

### 7.2. Conditions for True Atomicity in the Example

The inbox insert and business update are atomic only when:

- They share the same database transaction.
- They use the same transaction manager and connection resource.
- Neither step performs a manual commit in between.
- Neither uses `REQUIRES_NEW` in a way that splits the transaction.
- No external API outside the database is called under the assumption that it rolls back with the JDBC transaction.

If the inbox resides in database A while business state resides in database B, a local transaction on A does not protect B. In that case, you need an explicit distributed transaction or a saga/outbox/inbox design aligned with service boundaries.

## 8. What Happens When the Business Update Fails?

Suppose the inbox insert succeeds, then `INSERT INTO order_projection` violates a constraint:

1. An exception escapes the service.
2. The transaction rolls back.
3. The newly inserted inbox row also rolls back.
4. A subsequent retry can insert the inbox row and re-attempt the business update.

This is the most critical property of a shared-transaction inbox. If code catches the exception and returns normally, Spring may commit the inbox row even though the business update failed. Never swallow business or database exceptions if the message needs to be retried.

Anti-pattern to avoid:

~~~java
@Transactional
public void handle(OrderCreated event) {
    claimInbox(event);
    try {
        updateProjection(event);
    } catch (RuntimeException ex) {
        log.error("Projection failed", ex);
        // Returning normally may commit the inbox and lose the retry opportunity.
    }
}
~~~

Let the exception propagate or mark the transaction rollback-only per an explicit policy. Only route messages to a DLQ when the failure is non-retryable per policy; DLQ routing should be an observable decision made by the error handler/binder.

By default, Spring rolls back transactions on unchecked exceptions or `Error`. If a business method throws a checked exception that must also roll back both the inbox and business update, configure `rollbackFor` on `@Transactional` or translate the exception per application conventions.

## 9. Distinguishing Valid Duplicates from Misused Event IDs

If the same `(consumer_name, producer_id, event_id)` reappears with identical content, it is normally a safe duplicate to skip.

If the same key appears with a different payload, the producer may have:

- Reused an event ID for a new event.
- Resent an edited event instead of keeping it immutable.
- Suffered a serialization bug or misrouted data.
- Allowed two producers to share an ID namespace against contract.

Never silently treat every conflict as a benign duplicate. You can store a SHA-256 hash of the canonicalized payload or critical fields, then compare on conflict. If the hash differs, emit a dedicated metric/error and route to an investigation or quarantine workflow.

Hashing is meaningful only if canonicalization is deterministic. JSON field ordering or formatting can differ while carrying identical data; hashing raw bytes would produce mismatches. If comparing logical content, canonicalize according to the schema/contract before hashing.

## 10. Unique Constraints for Business Invariants

The inbox guarantees the same event is not applied twice by a logical consumer. A business invariant may still require its own unique constraint.

For example, ensuring each payment provider transaction is recorded only once:

~~~sql
CREATE TABLE payment_ledger (
    id BIGSERIAL PRIMARY KEY,
    provider_name VARCHAR(80) NOT NULL,
    provider_transaction_id VARCHAR(180) NOT NULL,
    order_id VARCHAR(100) NOT NULL,
    amount NUMERIC(19, 4) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_payment_provider_transaction
        UNIQUE (provider_name, provider_transaction_id)
);
~~~

The inbox protects event delivery identity; the ledger unique constraint protects the business rule. Both layers complement each other:

- Two different event IDs might reference the same provider transaction; the ledger constraint prevents double recording.
- The same event ID is redelivered; the inbox constraint stops the handler from re-running.
- Two Pods process two distinct events sharing the same order/payment key; the business constraint still guards data integrity.

Do not replace a business constraint with an inbox. Conversely, do not make a unique constraint overly broad so it blocks valid business actions, such as multiple distinct payment attempts for one order.

## 11. Handling Unique Constraint Errors by Database

The `ON CONFLICT DO NOTHING` SQL in earlier examples uses PostgreSQL syntax. Other engines have their own syntax and semantics:

| Database | Common implementation | What to verify |
|---|---|---|
| PostgreSQL | `INSERT ... ON CONFLICT DO NOTHING` | Conflict target must match the intended unique constraint |
| MySQL | `INSERT IGNORE` or `INSERT ... ON DUPLICATE KEY` | `IGNORE` can mask other errors; affected row count depends on configuration |
| SQL Server | Insert with unique violation handling or appropriate locking | Avoid assuming `MERGE` is always safe under all concurrency patterns |
| Oracle | Insert and catch specific constraint violations | Transaction/error handling must preserve atomicity |

When calling JPA `save()` and catching `DataIntegrityViolationException`, the transaction may already be marked rollback-only. Do not catch the exception and continue updating business tables inside the same transaction assuming it will still commit.

Prefer database-native insert-if-absent/upsert primitives. If using unique violations for control flow, design savepoints/transaction boundaries carefully and test against the exact production database engine. Do not test solely on H2 and assume PostgreSQL or MySQL shares identical semantics.

## 12. Never Rely Solely on `SELECT` Before `INSERT`

The following query is unsafe across multiple instances:

~~~sql
SELECT 1
FROM consumer_inbox
WHERE consumer_name = 'orders-projection'
  AND producer_id = 'order-service'
  AND event_id = '7c83c4f2-3e0f-4d7c-9b8e-4d6c6c2c0101';
~~~

A "no rows found" result is only true at the instant of the query. Another transaction can insert immediately afterward. `SELECT` followed by `INSERT` does not establish uniqueness.

`SELECT` remains useful for reading metadata of already-processed events, such as verifying a payload hash. However, the decision to claim an event must rest on a write protected by a unique constraint, or a proven locking/isolation strategy on the target database.

## 13. Inbox for Synchronous vs. Asynchronous Processing

### 13.1. Synchronous Within a Single Transaction

This is the simplest form:

1. Receive the event.
2. Insert into inbox.
3. Update business tables.
4. Commit a single transaction.
5. Handler returns so the binder acknowledges the message per configuration.

Appropriate when business processing is short enough to keep database transaction lifetimes reasonable. Never hold a database transaction open while waiting on slow external APIs.

### 13.2. Asynchronous with Inbox State Tracking

For long-running processing, separate ingestion from execution:

~~~sql
CREATE TABLE inbox_work (
    consumer_name VARCHAR(120) NOT NULL,
    producer_id VARCHAR(160) NOT NULL,
    event_id UUID NOT NULL,
    status VARCHAR(20) NOT NULL,
    attempt_count INTEGER NOT NULL DEFAULT 0,
    available_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_until TIMESTAMPTZ,
    last_error TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    processed_at TIMESTAMPTZ,
    PRIMARY KEY (consumer_name, producer_id, event_id),
    CHECK (status IN ('PENDING', 'PROCESSING', 'PROCESSED', 'FAILED'))
);
~~~

The consumer transaction inserts `PENDING` and commits; the broker message can be acknowledged once the work row is durably stored. A separate worker claims tasks using locking/leases, processes them, and marks `PROCESSED`.

This design additionally requires:

- Atomic work claiming so two workers never process the same row simultaneously.
- Lease/lock expiration to recover if a worker crashes.
- Attempt count, retry schedule, and retry limits.
- Rules for transitioning to `FAILED` or forwarding to a DLQ.
- Metrics for `PENDING` age and expired `PROCESSING` leases.
- Idempotency for external side effects.

Never leave rows stuck permanently in `PROCESSING` if a worker crashes. Leases must expire with a reclaim process. Also never mark `PROCESSED` before external side effects reach a completion boundary.

## 14. Combining Inbox and Outbox

The inbox prevents incoming events from being applied multiple times. If the consumer also needs to publish an output event, an outbox protects that step:

~~~mermaid
flowchart TD
    A["Receive input event"] --> B["DB transaction"]
    B --> C["Insert inbox unique key"]
    C --> D["Update business state"]
    D --> E["Insert outbox event"]
    E --> F["Commit"]
    F --> G["Outbox relay"]
    G --> H["Publish to broker"]
    H --> I["Mark outbox as sent"]
~~~

The inbox insert, business update, and outbox insert execute inside the same database transaction. If the transaction rolls back, all three roll back. The relay reads the outbox and publishes after commit; if the relay crashes after publishing but before marking `sent`, it may republish. Therefore, downstream consumers still need inbox/idempotency.

Example outbox table:

~~~sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,
    aggregate_id VARCHAR(120) NOT NULL,
    event_type VARCHAR(240) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    published_at TIMESTAMPTZ
);
~~~

Do not label an outbox relay as end-to-end exactly-once. The outbox guarantees the event is persisted with the business transaction and can be republished; duplicates at the broker boundary must still be handled.

## 15. External APIs and Side Effects Outside the Database Transaction

A JDBC transaction cannot roll back a sent email, a completed HTTP request, or a payment charge accepted by a provider.

Pattern to avoid:

~~~java
@Transactional
public void handle(PaymentRequested event) {
    claimInbox(event);
    paymentGateway.charge(event.paymentId(), event.amount());
    paymentRepository.markPaid(event.paymentId());
}
~~~

If the gateway charges successfully and then the database transaction rolls back, a retry could charge again. Rolling back the inbox cannot undo an external charge.

Safer options:

- Pass a stable idempotency key to the external API if supported by the provider.
- Write a command/outbox row inside the transaction, then let a worker invoke the API with the idempotency key.
- Persist workflow state and reconcile with the provider when timeouts leave outcomes uncertain.
- Use sagas/compensations when workflows span multiple services.

Never generate a new idempotency key on every retry. The key must stay constant for the same business operation.

## 16. Inbox Retention and Replay

The inbox only blocks duplicates while the corresponding row exists. If rows are purged too early, older events replayed later will be treated as brand new.

Retention must account for:

- Broker retention and how long messages can stay in queues/topics.
- Retry topics, delayed retries, and DLQ retention.
- The window during which operators can redrive messages.
- Backfills, disaster recovery, and replays from archives.
- How long producers might resend older events.
- Data retention and privacy regulations.

For example, if events can be replayed within 30 days, do not delete inbox rows after 7 days unless another deduplication archive exists. You can partition the table by time, archive older keys, or maintain compacted dedupe keys, provided cleanup preserves the required deduplication window.

Never purge the inbox purely to save disk space without evaluating replay windows. When intentional replay is required—such as rebuilding a projection—use a new logical consumer identity/version and an isolated target database/output per plan. Changing `consumer_name` alters deduplication semantics and is not a harmless operation.

## 17. Inbox and Processing Order

The inbox solves duplicates, not event ordering. Two distinct events for the same aggregate can still be processed concurrently or out of order if broker partitions/queues and concurrency permit it.

If business invariants require ordering:

- Use a consistent aggregate key as the Kafka key or appropriate routing key.
- Verify partition/queue ordering semantics and consumer concurrency.
- Persist aggregate version or sequence numbers.
- Apply an event only when it matches the next valid version; detect gaps and retry/reconcile.
- Add a unique constraint on `(aggregate_id, aggregate_version)` if each version may only be applied once.

Example:

~~~sql
ALTER TABLE order_projection
ADD COLUMN last_event_version BIGINT NOT NULL DEFAULT 0;

CREATE UNIQUE INDEX uq_order_event_version
ON applied_order_event (order_id, event_version);
~~~

When receiving a version less than or equal to the already applied version, the consumer can identify a duplicate or stale event. When receiving a skipped version, do not mark the event processed and skip the gap; wait for the missing event or route to a repair workflow.

## 18. Inbox Across Multiple Consumers and Multiple Bindings

A Spring Cloud Stream application can host multiple functions and bindings. Each logical consumer needs its own namespace:

~~~text
orders-projection + order-service + event-101
billing-ledger    + order-service + event-101
shipping-planner  + order-service + event-101
~~~

All three rows are valid because the three consumers have distinct responsibilities. If `(producer_id, event_id)` alone were the table's primary key, the first consumer to process would block the other two. That is why `consumer_name` is normally part of the unique key.

If a single function has multiple input bindings updating the same projection, base consumer identity on the logical business handler rather than arbitrary bean or binding names. Identity must remain stable across function renames and deployments.

## 19. Testing Duplicates and Concurrency

Testing only by sending the same message twice sequentially is insufficient. Race conditions typically surface only when two instances try to claim the same event nearly simultaneously.

### 19.1. Mandatory Test Scenarios

| Scenario | How to test | Expected outcome |
|---|---|---|
| Sequential duplicate | Send the same event ID twice | Business update runs only once |
| Concurrent duplicate | Two threads/Pods process the same ID | One transaction inserts inbox; only one business update runs |
| Rollback after inbox insert | Trigger failure in business update | Both inbox and business state roll back |
| Crash after DB commit before ACK | Kill consumer at test point | Redelivery recognized by inbox; no repeat update |
| Two independent consumers | Same event reaches two logical consumers | Each consumer processes once |
| Same ID, different payload | Send same key with modified content | Conflict detected; never silently overwritten |
| Colliding IDs across producers | Two producers emit same event ID | Producer namespaces stay isolated |
| Replay past retention | Redrive old event | Behavior matches retention policy |
| External API timeout | Provider may have executed request | Retry keeps same idempotency key and reconciles |
| Out-of-order event | Send version 12 before version 11 | Gap is not marked complete or skipped |

### 19.2. Concurrency Testing Against a Real Database

For PostgreSQL, use Testcontainers to run the exact engine and a version close to production. Spawn two transactions inserting the same inbox key and coordinate with a latch so they execute concurrently. Verify:

- Total inbox rows for the key equals one.
- Total business mutations equal one.
- The losing transaction observes a duplicate outcome after the winner commits.
- If the winner rolls back, the other transaction can claim and process the event.

Do not rely solely on mocked repositories because mocks do not simulate unique indexes, lock waits, isolation levels, or transaction rollbacks.

## 20. Example Service Test for Duplicate Delivery

Conceptual integration test using the database configured in the Spring test context:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.UUID;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;

@SpringBootTest
class OrderCreatedHandlerIT {

    @Autowired
    OrderCreatedHandler handler;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void duplicateEventChangesProjectionOnlyOnce() {
        UUID eventId = UUID.randomUUID();
        OrderCreated event = new OrderCreated(
            "order-service",
            eventId,
            "ORD-9001",
            "CUS-9001",
            new BigDecimal("125.50"),
            Instant.parse("2026-11-24T08:30:00Z")
        );

        boolean first = handler.handle(event);
        boolean second = handler.handle(event);

        assertThat(first).isTrue();
        assertThat(second).isFalse();

        Integer inboxRows = jdbc.queryForObject("""
            SELECT COUNT(*)
            FROM consumer_inbox
            WHERE consumer_name = 'orders-projection'
              AND producer_id = 'order-service'
              AND event_id = ?
            """, Integer.class, eventId);

        Integer projectionRows = jdbc.queryForObject("""
            SELECT COUNT(*)
            FROM order_projection
            WHERE order_id = 'ORD-9001'
            """, Integer.class);

        assertThat(inboxRows).isEqualTo(1);
        assertThat(projectionRows).isEqualTo(1);
    }
}
~~~

The test above demonstrates sequential duplicates. Concurrency tests should run two transactions on two threads with the same event using a latch/barrier to maximize contention, then assert row counts and business effects. Also test transaction rollback to prove the inbox does not commit independently.

If a test method is annotated with `@Transactional`, note that the outer test transaction can alter commit and visibility behavior. To test real transaction boundaries, call the service through its Spring proxy in independent transactions and verify state after each call completes.

## 21. Observing the Inbox in Production

The inbox prevents duplicates, yet metrics are still essential to catch producer or broker anomalies:

- Total new events claimed.
- Duplicates skipped.
- Duplicate rate by producer, event type, and binding.
- Unique conflict rate and lock wait duration.
- Transaction rollbacks and business update failures.
- Age of `PENDING`/`PROCESSING` rows if using async workers.
- Count of events with matching IDs but mismatched payload hashes.
- Table storage size, growth rate, and cleanup duration.
- End-to-end processing time from receipt to commit.

Never attach `eventId` or `orderId` as metric labels because cardinality grows unboundedly. Record event IDs in structured logs or traces under appropriate data protection policies; keep metric labels low-cardinality such as consumer, producer, and event type.

A sudden spike in duplicate rate may indicate:

- Excessive producer retries due to confirmation timeouts.
- Frequent consumer restarts or rebalances.
- Repeated ACK/commit failures.
- Operator replays or redrives.
- A producer bug emitting the same event repeatedly.

Skipped duplicates are not always errors, but abnormal spikes warrant investigation.

## 22. Common Design Pitfalls

| Mistake | Consequence | Fix |
|---|---|---|
| Using only `existsById` before insert | Two consumers both pass the check | Claim using an insert guarded by a unique constraint |
| Inbox and business update in separate transactions | Event marked processed while business update fails to commit | Use the same database transaction |
| Generating a new event ID on retry | Each delivery looks like a brand new event | Producer must keep IDs stable |
| Changing inbox identity across releases | Rollbacks or new deployments reprocess all history | Keep logical `consumer_name` stable |
| Omitting `consumer_name` from key with multiple handlers | One consumer blocks another | Namespace by logical consumer |
| Catching all exceptions and returning normally | Binder ACKs the failed event | Propagate errors or roll back the transaction |
| Catching unique violations and continuing in a rollback-only transaction | Business update fails to commit or errors at commit | Use database-appropriate insert-if-absent/upsert |
| Deduplicating only in JVM cache | Duplicates occur after restart or on another Pod | Unique constraint in a shared database |
| Purging inbox too early | Replaying old events repeats side effects | Retention longer than replay/retry windows |
| Calling external APIs inside DB transaction | External side effect does not roll back | Outbox, provider idempotency keys, and reconciliation |
| Treating inbox as system-wide exactly-once | Duplicates still happen at broker or downstream boundaries | Inbox per consumer and outbox at producer boundaries |
| Hashing raw JSON to compare content | Field order/formatting differences cause false mismatches | Canonicalize per schema or hash semantic fields |

## 23. Step-by-Step Guide to Implementing an Inbox Consumer

1. Identify a stable event identity from the producer contract.
2. Choose a logical consumer name and uniqueness scope.
3. Create the inbox table with a primary key or unique constraint.
4. Determine which business updates must share the same database transaction.
5. Implement insert-if-absent using the database's native primitive.
6. Execute business updates only when the insert claim succeeds.
7. Let business exceptions propagate so the transaction rolls back and the binder applies retries.
8. If emitting output events, write to an outbox in the same transaction.
9. Make external side effects idempotent or back them with workflows/reconciliation.
10. Define retention based on broker retention, retries, DLQ, and replay windows.
11. Test sequential duplicates, concurrent duplicates, rollbacks, and crashes before ACK.
12. Monitor duplicate rates, transaction failures, lock waits, and inbox growth.

## 24. Design and Operations Checklist

- [ ] Producer generates a stable event ID and preserves it across retries.
- [ ] Identity includes producer/tenant namespaces if event IDs are not globally unique.
- [ ] Logical `consumer_name` stays stable across deployments and refactors.
- [ ] Inbox has a primary key/unique constraint in a shared database.
- [ ] Inbox insert and business update execute in the same transaction.
- [ ] Insert-if-absent is atomic; never relies purely on `SELECT` then `INSERT`.
- [ ] Duplicates never re-execute business side effects.
- [ ] Critical business invariants have their own dedicated unique constraints.
- [ ] Business exceptions are not swallowed and do not falsely commit the inbox.
- [ ] External APIs use idempotency keys or appropriate outbox/workflow patterns.
- [ ] Payload ID conflicts are detected when the same key carries different content.
- [ ] Retention exceeds retry, DLQ redrive, replay, and recovery windows.
- [ ] Concurrency tests run against a production-equivalent database engine.
- [ ] Crash tests verify recovery after DB commit but before broker ACK/offset commit.
- [ ] Dashboards monitor duplicate rates, transaction failures, and inbox storage.
- [ ] Inbox cleanup is planned and does not break replay guarantees.

## 25. Key Principles to Remember

An inbox does not prevent brokers from redelivering messages. An inbox ensures the consumer recognizes an already-applied event and safely ignores repeat deliveries. A unique constraint provides safe arbitration across concurrent transactions, while a shared transaction guarantees the inbox marker and business state succeed or fail together.

In Spring Cloud Stream, handlers should return normally once the business transaction completes or once a delivery is confirmed as a valid duplicate. When a transaction fails, let errors reach the binder's error handling so the message can be retried or routed to a DLQ per policy. When a consumer produces output or calls external systems, protect those boundaries with an outbox, idempotency keys, and reconciliation.
