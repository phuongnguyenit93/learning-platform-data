# Configuring application.yml and Running an End-to-End Flow

A Spring Cloud Stream application is typically configured in three parts: choosing the business function to run, mapping input/output bindings to destinations, and declaring the binder to connect to the broker. When these three parts align, a message sent to an input destination flows through your application's `Supplier`, `Function`, or `Consumer` according to the declared function type.

The hands-on exercise below uses Kafka to run a complete flow: sending strings to the `greetings` topic, processing them with a `Function<String, String>`, and reading the uppercased results from the `greetings-uppercase` topic. The function and binding model stays the same when switching to RabbitMQ or Pulsar; connection settings and some binder-dependent semantics will change.

## 1. Preparing the Project and Broker

Before configuring, you need:

- Java 17 or later and Maven or the Maven Wrapper.
- A runnable Spring Boot application.
- Apache Kafka running and reachable at `localhost:9092`.
- Kafka command-line tools to create topics, send, and read messages.

If creating a new project with Spring Initializr, pick a Spring Boot version compatible with the Spring Cloud release train you plan to use. Spring Cloud Stream and the binder should have their versions managed by the Spring Cloud BOM corresponding to that Spring Boot version; do not manually mix versions from different release trains.

With Maven, add dependency management and the Kafka binder. Example relevant section in `pom.xml`:

~~~xml
<properties>
    <java.version>17</java.version>
    <spring-cloud.version>YOUR_COMPATIBLE_SPRING_CLOUD_VERSION</spring-cloud.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-stream-kafka</artifactId>
    </dependency>
</dependencies>
~~~

Replace `YOUR_COMPATIBLE_SPRING_CLOUD_VERSION` with a compatible release train version from the Spring Cloud compatibility table. If the project was already generated by Spring Initializr with the corresponding dependency management, keep the existing BOM configuration and just add the binder.

The Kafka broker must be ready before running the application. This exercise assumes the broker is at `localhost:9092`; if running the application inside a container, `localhost` may point to the application container itself. In that case, use a hostname the container can resolve to the broker.

## 2. Writing a Message-Processing Function

Create a `Function` bean named `uppercase`. The function takes an input string and returns the uppercased string:

~~~java
import java.util.Locale;
import java.util.function.Function;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class StreamUppercaseApplication {

    public static void main(String[] args) {
        SpringApplication.run(StreamUppercaseApplication.class, args);
    }

    @Bean
    Function<String, String> uppercase() {
        return message -> message.toUpperCase(Locale.ROOT);
    }
}
~~~

Spring Cloud Stream detects the function bean and creates bindings based on the bean name and parameter position:

| Bean name | Binding | Role |
|---|---|---|
| `uppercase` | `uppercase-in-0` | Receives input messages |
| `uppercase` | `uppercase-out-0` | Emits output results |

The `-in-0` suffix indicates the first input, and `-out-0` indicates the first output. If a function has multiple inputs or outputs, the index increments from 0 in parameter order. These binding names are logical names inside the application; destinations are configured separately.

## 3. Configuring application.yml

Create the file `src/main/resources/application.yml`:

~~~yaml
spring:
  application:
    name: stream-uppercase

  cloud:
    function:
      definition: uppercase

    stream:
      bindings:
        uppercase-in-0:
          destination: greetings
          group: uppercase-service
          content-type: text/plain

        uppercase-out-0:
          destination: greetings-uppercase
          content-type: text/plain

      kafka:
        binder:
          brokers: ${KAFKA_BROKERS:localhost:9092}
~~~

Reading the configuration section by section:

- `spring.application.name` sets the Spring Boot application name, useful for logs and observability.
- `spring.cloud.function.definition` selects the function bean that Spring Cloud Stream activates. The value must match the bean name, here `uppercase`.
- `uppercase-in-0.destination` maps the input binding to the `greetings` topic.
- `uppercase-in-0.group` sets a stable consumer group. Instances using the same group share consumption work according to Kafka's mechanism.
- `uppercase-in-0.content-type` declares the input content type as plain text.
- `uppercase-out-0.destination` maps the output binding to the `greetings-uppercase` topic.
- `uppercase-out-0.content-type` declares the output content type.
- `spring.cloud.stream.kafka.binder.brokers` specifies the Kafka broker address. The placeholder allows reading the address from the `KAFKA_BROKERS` environment variable, using `localhost:9092` as the default.

In this configuration, `greetings` and `greetings-uppercase` are destination names on Kafka. Bindings let code reference inputs and outputs by function name, while the binder moves messages between bindings and the broker.

You can split configurations by profile, such as `application-local.yml`, `application-staging.yml`, and `application-prod.yml`. Connection details, credentials, and TLS settings should be supplied via environment variables or a secret manager. Do not commit broker passwords to the repository.

## 4. Creating Topics and Starting the Application

Create the two topics before running:

~~~bash
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic greetings --partitions 3 --replication-factor 1
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic greetings-uppercase --partitions 3 --replication-factor 1
~~~

If using Kafka on Windows, the scripts are typically in `bin\windows` with a `.bat` extension, for example `kafka-topics.bat`. Depending on the Kafka distribution, actual paths may vary.

Start the application from the directory containing `pom.xml`:

~~~bash
./mvnw spring-boot:run
~~~

On Windows, use the Maven Wrapper:

~~~powershell
.\mvnw.cmd spring-boot:run
~~~

Watch the logs to confirm the application started and the Kafka binder connected and created or assigned a consumer for the input binding. If the application reports connection errors, check that the broker is running, the bootstrap address is reachable from the application process, and the port is open.

You should start the application before sending messages on the first run. That way, the new consumer group can receive messages sent during the exercise without depending on offset positions left over from a previous run.

## 5. Sending Messages and Verifying Results

Open a second terminal and run a producer to send messages to the input topic:

~~~bash
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic greetings
~~~

Enter lines one by one, for example:

~~~text
hello spring cloud stream
order-created
Kafka binder is connected
~~~

Each line is sent as a Kafka record. Open a third terminal and read the output topic:

~~~bash
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic greetings-uppercase --from-beginning
~~~

Expected output:

~~~text
HELLO SPRING CLOUD STREAM
ORDER-CREATED
KAFKA BINDER IS CONNECTED
~~~

When a record arrives on `greetings`, the Kafka binder converts the payload into a message for the `uppercase-in-0` input binding. The `uppercase` function processes the payload and returns the result. The `uppercase-out-0` output binding sends the result to the `greetings-uppercase` topic; the console consumer reads those records.

You can inspect both topics with the corresponding `kafka-console-consumer` commands. Reading the input topic shows the original strings; reading the output topic shows the uppercased strings. This verifies both sides of the flow.

## 6. Trying Supplier and Consumer Function Types

After the `Function` flow runs successfully, you can try the other two function types to see how bindings are created.

### Supplier Emitting Messages

`Supplier` takes no input; the framework invokes the function to retrieve data and emits it to the output binding:

~~~java
import java.util.function.Supplier;

@Bean
Supplier<String> heartbeat() {
    return () -> "stream-is-alive";
}
~~~

The default output binding is `heartbeat-out-0`. You can map this binding to another destination:

~~~yaml
spring:
  cloud:
    function:
      definition: heartbeat
    stream:
      bindings:
        heartbeat-out-0:
          destination: heartbeat-events
          content-type: text/plain
~~~

A `Supplier` is normally invoked by a poller. You can adjust the polling interval with Spring Integration poller configuration, such as `spring.integration.poller.fixed-delay`. Make sure the `Supplier` does not unintentionally repeat a non-idempotent action on each invocation.

### Consumer Receiving and Processing Messages

`Consumer` only has an input and emits no output binding:

~~~java
import java.util.function.Consumer;

@Bean
Consumer<String> logGreeting() {
    return message -> System.out.println("Received: " + message);
}
~~~

The default input binding is `logGreeting-in-0`. Example configuration:

~~~yaml
spring:
  cloud:
    function:
      definition: logGreeting
    stream:
      bindings:
        logGreeting-in-0:
          destination: greetings
          group: greeting-logger
          content-type: text/plain
~~~

The `Supplier` and `Consumer` examples are alternative configurations for the `Function` exercise. If you put multiple function beans in the same application, explicitly declare which functions are activated. You can use a semicolon to activate multiple independent functions, such as `uppercase;logGreeting`; use `|` to compose functions with compatible types into a single pipeline, such as `normalize|uppercase`.

## 7. Using Another Binder

The functional model and most of the `spring.cloud.stream.bindings` configuration can remain unchanged when switching middleware. Replace the binder dependency and the corresponding connection configuration.

| Broker | Dependency | Commonly used connection properties | Destination |
|---|---|---|---|
| Kafka | `org.springframework.cloud:spring-cloud-starter-stream-kafka` | `spring.cloud.stream.kafka.binder.brokers` | Topic |
| RabbitMQ | `org.springframework.cloud:spring-cloud-starter-stream-rabbit` | `spring.rabbitmq.host`, `port`, `username`, `password` | Exchange and queue |
| Pulsar | `org.springframework.pulsar:spring-pulsar-spring-cloud-stream-binder` | `spring.pulsar.client.service-url` | Topic and subscription |

Example RabbitMQ connection section:

~~~yaml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: guest
    password: guest
~~~

The Rabbit binder maps destinations to exchanges; for a consumer with a group, the binder creates a queue bound to the exchange so instances in the same group share messages. In production, use dedicated accounts and restrict permissions rather than keeping default credentials.

Example Pulsar connection section:

~~~yaml
spring:
  pulsar:
    client:
      service-url: pulsar://localhost:6650
~~~

The Pulsar binder maps destinations to topics and uses subscriptions to manage consumers. Choose a subscription type suited to load-sharing or broadcasting data to multiple consumer groups. Pulsar retry, dead-letter, and schema configurations have their own properties; do not copy Kafka or RabbitMQ extended properties verbatim.

If an application has multiple binders on the classpath, explicitly configure the binder for each binding using the declared binder name. When only one binder is present, the framework can usually auto-select it. Sharing the same destination name does not mean the semantics of topics, exchanges, queues, and subscriptions are identical.

## 8. Reading Errors and Fixing Common Misconfigurations

| Symptom | Cause to check | How to resolve |
|---|---|---|
| Application starts, but the function receives no messages | `spring.cloud.function.definition` does not match the bean name or binding is wrong | Compare the bean name, `-in-0`, and destination in YAML |
| Broker reports connection refused | Wrong hostname/port, broker not running, or container cannot reach the address | Check the broker address from the exact environment running the application |
| Messages arrive at input, but no output appears | Function throws an exception, output binding is wrong, or broker rejects writes | Read the stack trace, check the output binding name and destination write permissions |
| Payload is converted incorrectly | `content-type` does not match the sent format | Use `text/plain` for strings or configure JSON matching the payload |
| Consumer does not re-read old data | The group already has committed offsets | Understand the current offset position; use a fresh test group when independent verification is needed |
| Cannot create topic or queue | Broker disallows auto-provisioning or account lacks permissions | Provision destinations via infrastructure processes and grant appropriate permissions |
| Application has multiple binders and fails to determine which binder to use | Multiple binders present without specifying the binder on bindings | Declare the corresponding binder for each binding |

When inspecting a Kafka consumer group, use the following command to view status and lag:

~~~bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group uppercase-service
~~~

This command lets you observe assigned partitions, committed offsets, log-end offsets, and lag. When running multiple instances, watch the partition count and active consumer count to understand parallelism.

## 9. Testing Before Integrating with a Real Broker

Running manually against Kafka helps confirm real connectivity, but terminal actions should not be your only automated check. You can add:

- Unit tests for the function, checking regular strings, empty strings, and Unicode characters.
- Test binder tests with `spring-cloud-stream-test-binder` to send messages to `InputDestination` and receive results from `OutputDestination` without a real broker.
- Integration tests with real Kafka or Testcontainers to verify broker URLs, topics, groups, serialization, partitions, and offsets.
- Failure tests when the broker disconnects, the function throws an exception, or the output destination is unavailable.

The test binder is useful for verifying application-level wiring and message processing. It does not prove that broker configuration, partitioning, rebalancing, transactions, or DLQs work properly. Broker-dependent behaviors must be verified with integration tests.

## 10. Things to Keep When Moving to Deployment Environments

Before promoting the application to staging or production:

- Move broker URLs, credentials, TLS, and environment-specific values out of source code.
- Use stable consumer groups to preserve consumption progress across restarts.
- Create topics, exchanges, queues, partitions, retention, and subscriptions via managed infrastructure configuration.
- Set timeouts, retries, and DLQs according to business processing times; design idempotent consumers to tolerate redelivered messages.
- Monitor throughput, processing latency, consumer lag, connection errors, and DLQ message counts.
- Test shutdown, restart, and multi-instance scaling to confirm in-flight messages complete or are safely redelivered.

A single successful send to the broker does not by itself prove the business operation was processed exactly once. Producer, broker, consumer, and database side effects each have their own delivery boundaries. Clearly define when acknowledgements or offsets are committed, how data is persisted durably, and how consumers handle duplicates.

## 11. Complete Hands-On Exercise and Completion Criteria

Follow this order:

1. Create a Spring Boot project and add the Kafka binder along with a compatible Spring Cloud BOM.
2. Write a `Function<String, String>` bean named `uppercase`.
3. Declare `spring.cloud.function.definition`, the two bindings `uppercase-in-0` and `uppercase-out-0`, both destinations, and content types in `application.yml`.
4. Start Kafka, create the two topics, and run the application.
5. Send at least three messages to the `greetings` topic; confirm that the `greetings-uppercase` topic receives the exact three uppercased results.
6. Start a second instance with the same consumer group; observe how Kafka distributes partitions when enough partitions exist.
7. Change the group in a test environment and observe the creation of an independent consumer group.
8. Run unit tests, test binder tests, and broker integration tests.

You have completed the exercise when you can accurately trace a message's path from producer, input destination, input binding, function, output binding, to output destination; know where each component is configured; and diagnose connection errors, wrong bindings, wrong content types, or consumer group issues.
