# Preserving Log, Tracing, and Authentication Context

A synchronous call through Spring Cloud CircuitBreaker typically starts while processing an incoming HTTP request, then calls a dependent service such as Inventory or Payment. Throughout this flow, the application must retain information to answer three questions: which request is being processed, which services the call has traversed, and under which identity the call is being made.

Those three groups of information are commonly referred to as context:

- **Logging context:** correlation ID, request ID, and MDC fields that link log entries belonging to the same request.
- **Tracing context:** trace ID, span ID, and parent-child span relationships to follow the request path across services.
- **Authentication context:** `Authentication`, `SecurityContext`, and OAuth2 credentials needed by the target service to verify whether the caller is authorized to perform the operation.

When execution stays synchronous on the same thread, `ThreadLocal`-based mechanisms such as MDC and `SecurityContextHolder` usually remain available. However, a thread-pool bulkhead, executor, or asynchronous boundary can shift work onto another thread. In that case, context does not follow automatically unless the application configures an appropriate context propagation mechanism.

This lesson explains how to preserve all three context groups during synchronous calls with Spring Cloud CircuitBreaker and Resilience4j, how to forward correlation IDs to dependent services, how to let Micrometer Tracing create spans and propagate trace context, and how to forward authentication details in a controlled manner.

## 1. What Context Does a Request Carry?

Suppose a user calls an API to check stock availability. The Order API calls Inventory through a Circuit Breaker. When Inventory returns an error, Order may execute a fallback. An operator needs to find all logs for the request, inspect the span calling Inventory, and know whether the request ran under a user identity or a service identity.

| Context Type | Example | Purpose |
| --- | --- | --- |
| Correlation ID | `X-Correlation-ID: req-7f2a` | Find logs belonging to the same request across multiple services. |
| Trace context | `traceparent`, trace ID, span ID | Inspect parent-child relationships between operations in a distributed trace. |
| Authentication | JWT, OAuth2 access token, service identity | Identify the caller and permissions the target service must verify. |
| Business context | Order ID, tenant ID, transaction ID | Support business-level diagnostics when the data is permitted to be recorded. |

Not all information belongs in logs or HTTP headers. Access tokens, refresh tokens, passwords, session cookies, and sensitive personal data must never be logged. Tenant IDs or transaction IDs must also be checked against your system's data policies.

Correlation ID and trace ID serve related purposes, yet do not replace each other. A correlation ID is typically generated by the application or gateway to correlate logs at the business level. A trace ID belongs to the tracing model, carrying spans and timing relationships between operations. A single request may carry both.

## 2. Synchronous Flow and Thread Boundaries

A basic synchronous call can be represented as follows:

~~~text
HTTP request
    |
    v
Servlet filter
  - resolve correlation ID
  - populate SecurityContext
  - create trace/span for request
    |
    v
Controller / Service
    |
    v
Spring Cloud CircuitBreaker
    |
    v
RestClient
    |
    v
Inventory service
~~~

If every step runs on the same thread, `ThreadLocal`-backed MDC and `SecurityContextHolder` can be read by downstream steps. Micrometer Tracing maintains the current span in the execution context and integrates with instrumented HTTP clients to create child spans and propagate trace context to the target service.

However, you must check which bulkhead and executor are in use:

- **No thread-pool bulkhead:** the synchronous call usually runs on the current thread.
- **Semaphore bulkhead:** limits concurrent calls while executing the supplier on the calling thread.
- **Thread-pool bulkhead:** dispatches work to a thread from the pool. MDC, `SecurityContext`, and other `ThreadLocal` values are not copied automatically to that thread unless context propagation is configured.
- **Executor or asynchronous task:** faces the same issue whenever work shifts to another thread.

Therefore, never rely solely on the word "synchronous" in a method signature to conclude that context is guaranteed to be preserved. Verify explicitly whether the execution path switches threads.

## 3. Setting Up Correlation ID and MDC

MDC (Mapped Diagnostic Context) allows attaching fields to logs emitted on the current thread. With SLF4J, you can use `MDC.put`, `MDC.get`, and `MDC.remove`.

A servlet filter can read the correlation ID from the request, validate its format, and store it in MDC for the duration of request processing:

~~~java
package com.example.order.logging;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.UUID;
import java.util.regex.Pattern;

@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

    private static final String HEADER = "X-Correlation-ID";
    private static final String MDC_KEY = "correlationId";
    private static final Pattern SAFE_ID =
        Pattern.compile("[A-Za-z0-9._-]{1,64}");

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {

        String incomingId = request.getHeader(HEADER);
        String correlationId = incomingId != null
                && SAFE_ID.matcher(incomingId).matches()
            ? incomingId
            : UUID.randomUUID().toString();

        String previousValue = MDC.get(MDC_KEY);
        MDC.put(MDC_KEY, correlationId);
        response.setHeader(HEADER, correlationId);

        try {
            filterChain.doFilter(request, response);
        } finally {
            if (previousValue == null) {
                MDC.remove(MDC_KEY);
            } else {
                MDC.put(MDC_KEY, previousValue);
            }
        }
    }
}
~~~

The filter accepts only IDs matching permitted characters and length. This prevents arbitrary strings containing newline characters from entering logs. If your system has a trusted gateway generating correlation IDs, explicitly restrict which gateway is allowed to supply that value.

The `finally` block is critical. Servlet containers reuse threads across requests. If you do not clear or restore MDC, the next request may log entries under the previous request's correlation ID.

You can include the correlation ID and trace ID in the log pattern inside `application.yml`:

~~~yaml
logging:
  pattern:
    level: "%5p [corr:%X{correlationId:-}] [trace:%X{traceId:-} span:%X{spanId:-}]"
~~~

When Micrometer Tracing integrates with logging, trace ID and span ID fields are typically populated into MDC automatically. If tracing is not enabled yet, the trace section remains empty while the correlation ID continues working independently.

## 4. Propagating Correlation ID Through RestClient

MDC exists only within the current thread's context. For the Inventory service to receive the correlation ID, the caller must place it into an outbound HTTP request header.

With Spring Boot, use the Spring-managed `RestClient.Builder` to keep automatic observation and tracing integrations intact. You can attach a `ClientHttpRequestInterceptor` to forward the correlation ID:

~~~java
package com.example.order.inventory;

import org.slf4j.MDC;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;

@Configuration
public class InventoryClientConfiguration {

    @Bean
    RestClient inventoryRestClient(
            RestClient.Builder builder) {

        return builder
            .baseUrl("http://localhost:8081")
            .requestInterceptor((request, body, execution) -> {
                String correlationId = MDC.get("correlationId");

                if (correlationId != null) {
                    request.getHeaders().set(
                        "X-Correlation-ID",
                        correlationId
                    );
                }

                return execution.execute(request, body);
            })
            .build();
    }
}
~~~

The Inventory service can use a similar filter to store the correlation ID in its own MDC. Then logs from both Order and Inventory can be searched under the same ID.

Do not generate a new correlation ID at every tier if the goal is to link a single request. If an incoming request lacks a valid ID, the entry tier generates one and downstream tiers forward it unchanged. If you need to distinguish individual retry attempts, add a separate attempt number rather than replacing the original correlation ID.

## 5. Propagating Trace Context with Micrometer Tracing

Tracing captures the relationship between operations within a request. For example:

- The first span represents the incoming request to Order.
- The next span represents the HTTP call from Order to Inventory.
- Inventory creates a server span for the incoming request.
- If Inventory calls another service, that call creates another child span.

With Spring Boot, Micrometer Observation and Micrometer Tracing integrate with the server and HTTP clients to create spans and propagate trace context over HTTP. With W3C Trace Context, the `traceparent` header carries the details required for the target service to continue the same trace.

Common dependencies in a Spring Boot 3 application include Actuator, a tracing bridge, and a corresponding exporter. For example, with OpenTelemetry:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-tracing-bridge-otel</artifactId>
    </dependency>

    <dependency>
        <groupId>io.opentelemetry</groupId>
        <artifactId>opentelemetry-exporter-otlp</artifactId>
    </dependency>
</dependencies>
~~~

Use Spring Boot dependency management to select compatible versions. Depending on your system, you can choose the Brave bridge instead of OpenTelemetry; do not add multiple tracing bridges to the same application simultaneously unless you have a specialized architecture.

Configure sampling and the exporter endpoint per environment. Example sampling probability configuration:

~~~yaml
management:
  tracing:
    sampling:
      probability: 1.0
~~~

A value of `1.0` is convenient in a lab because every request is sampled. In high-traffic production environments, choose a sampling rate suited to your cost and observability goals.

When building the HTTP client, inject the `RestClient.Builder` provided by Spring Boot and call `build()`. That builder is preconfigured with Observation instrumentation in supported Spring Boot versions. Creating a client manually via `RestClient.create()` or a standalone builder can bypass the instrumentation configured by the application.

Do not manually copy the trace ID into a custom header or hand-craft `traceparent` when using an instrumented HTTP client. Instrumentation automatically creates the client span and injects properly formatted trace context. Manual copying can break parent-child span relationships or produce inconsistent traces.

## 6. Preserving Authentication Details

Authentication context indicates who is making the request. In a Spring Security application, `SecurityContextHolder` holds the active `SecurityContext`. With default servlet application configuration, the context is usually stored in a `ThreadLocal`.

When a synchronous call continues on the same thread, code can read `Authentication` from `SecurityContextHolder`. However, having `Authentication` in the caller does not mean the HTTP client automatically sends credentials to the dependent service.

Explicitly decide which identity the target service should see:

1. **Forwarding user identity (token relay):** the target service receives the user's access token and performs its own authentication and authorization based on that token.
2. **Service identity:** the caller obtains its own access token via client credentials or workload identity; the target service sees the caller as a service account.
3. **No authentication at the target service:** only applicable when architecture and network boundaries allow it; never assume an internal network is inherently trusted.

### 6.1. Intentional Token Relay

If the caller is an OAuth2 Resource Server and Inventory is permitted to accept the user's access token directly, you can read the authenticated JWT and forward it:

~~~java
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;

Authentication authentication =
    SecurityContextHolder.getContext().getAuthentication();

if (authentication instanceof JwtAuthenticationToken jwtAuthentication) {
    String accessToken = jwtAuthentication.getToken().getTokenValue();
    request.getHeaders().setBearerAuth(accessToken);
}
~~~

This is an example of conditional token relay, not a rule to apply to every call. Only forward a token when:

- Inventory is a valid audience for the token.
- The scopes or authorities inside the token suffice for the intended operation.
- Security policy permits the Order service to relay the user's identity.
- The token remains valid for the duration of the call.

If the token is scoped solely to the Order API, Inventory may reject it. In that case, the caller must obtain an appropriate token for Inventory or use a service identity.

### 6.2. Service-to-Service OAuth2

When Inventory needs to authenticate Order as a service, use an OAuth2 Client with client credentials or a workload token issuance mechanism. The application acquires a token from the authorization server using the corresponding client registration, then attaches the access token to outbound requests.

Never hand-craft JWTs, sign tokens with arbitrary secrets, or reuse a user access token as a service identity when the architecture calls for a service identity. Also never log tokens for debugging.

### 6.3. Do Not Blindly Forward All Headers

Never copy every header from an inbound request to an outbound request. Some headers apply only to the preceding hop, may contain sensitive data, or are untrusted by the target service.

Allowlist the headers to forward, for example:

- `X-Correlation-ID` for log correlation.
- `traceparent` and `tracestate` managed by tracing instrumentation.
- `Authorization` only when token relay or a service token is explicitly intended.
- Controlled business headers such as tenant or locale if required by the target API.

Session cookies, `Set-Cookie`, `Host`, `Content-Length`, hop-by-hop headers, and other internal headers should not be forwarded arbitrarily.

## 7. Combining Circuit Breaker with the HTTP Client

The Circuit Breaker wraps the synchronous call. The HTTP client handles sending the chosen correlation ID, tracing headers, and authentication credentials.

Example of a simple gateway:

~~~java
package com.example.order.inventory;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.cloud.client.circuitbreaker.CircuitBreakerFactory;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;

@Service
public class InventoryGateway {

    private static final Logger log =
        LoggerFactory.getLogger(InventoryGateway.class);

    private final CircuitBreakerFactory<?, ?> circuitBreakerFactory;
    private final RestClient inventoryRestClient;

    public InventoryGateway(
            CircuitBreakerFactory<?, ?> circuitBreakerFactory,
            RestClient inventoryRestClient) {
        this.circuitBreakerFactory = circuitBreakerFactory;
        this.inventoryRestClient = inventoryRestClient;
    }

    public InventoryResponse getInventory(String sku) {
        String correlationId = MDC.get("correlationId");

        return circuitBreakerFactory.create("inventory").run(
            () -> {
                log.info(
                    "Calling Inventory for sku={}, correlationId={}",
                    sku,
                    correlationId
                );

                return inventoryRestClient.get()
                    .uri("/inventory/{sku}", sku)
                    .retrieve()
                    .body(InventoryResponse.class);
            },
            error -> {
                log.warn(
                    "Inventory call failed for sku={}, correlationId={}",
                    sku,
                    correlationId,
                    error
                );

                return InventoryResponse.unavailable(sku);
            }
        );
    }
}
~~~

This snippet illustrates logging and fallback handling. `RestClient` is configured separately to forward the correlation ID and use tracing instrumentation. If token relay or a service token is needed, the HTTP client configuration must add the chosen authentication mechanism.

The fallback may run in a different execution context depending on the bulkhead integration and provider version. If the fallback needs to read MDC or `SecurityContext`, verify that context has been propagated to the fallback's executing thread. A safer pattern is passing non-sensitive values the fallback genuinely needs as explicit parameters rather than relying on `ThreadLocal`.

## 8. When a Thread-Pool Bulkhead Loses Context

A thread-pool bulkhead isolates calls using a dedicated pool. While useful for bounding resources allocated to a dependency, it can lose MDC and `SecurityContext` if context propagation is not configured.

For example, a request starts on thread `http-nio-8080-exec-4`, then the supplier runs on thread `inventory-bulkhead-2`. The new thread does not automatically inherit `ThreadLocal` values from the request-handling thread.

| Context | Same Thread | Shifted to Thread Pool |
| --- | --- | --- |
| MDC | Readable if not cleared yet | Not available automatically |
| Correlation ID in MDC | Readable | Needs propagation or re-initialization |
| Trace context | Held in current execution context | Needs context propagation or proper instrumentation |
| `SecurityContextHolder` | Usually present under default `ThreadLocal` strategy | Not available automatically |
| HTTP headers already attached to request | Sent with request | Still sent if the request was already built with those headers |

There are three common approaches:

- Use a semaphore bulkhead if you want concurrency limiting while keeping supplier execution on the calling thread, and if the application's load profile suits it.
- Configure context propagation for the executor or thread-pool bulkhead. Micrometer Context Propagation can transfer registered values via `ThreadLocalAccessor`; Spring provides `ContextPropagatingTaskDecorator` for compatible task executors.
- For `SecurityContext`, use Spring Security's executor or task wrappers such as `DelegatingSecurityContextExecutor` when the executor is application-managed. If Resilience4j creates its own thread pool, use the context propagator hook supported by your integration version or pass the needed identity explicitly.

Do not enable `MODE_INHERITABLETHREADLOCAL` as a blanket fix for thread pools. Pooled threads are reused; inherited context may not reflect the current request and risks leaking a previous identity. Always ensure context is cleaned up after every task.

In Spring Cloud CircuitBreaker with Resilience4j, verify the application's actual bulkhead configuration. Depending on version and configuration, you can select semaphore bulkhead as the default using:

~~~yaml
spring:
  cloud:
    circuitbreaker:
      resilience4j:
        enableSemaphoreDefaultBulkhead: true
~~~

Confirm that this property is supported in your Spring Cloud version. Choosing a semaphore does not replace timeout limits; timeouts and bulkheads still need to be designed individually around the dependency's load profile.

## 9. Propagating Context Across Retries and Fallbacks

Retries can generate multiple calls to the same dependency. The original request's correlation ID should remain unchanged across attempts so the entire processing sequence can be traced. You can add an attempt number to distinguish individual attempts:

~~~java
for (int attempt = 1; attempt <= maxAttempts; attempt++) {
    log.info(
        "Inventory attempt={}, correlationId={}",
        attempt,
        MDC.get("correlationId")
    );

    // Execute the call according to the retry policy
}
~~~

This snippet illustrates logging attempts; in production applications, use Resilience4j `Retry` or a standardized retry mechanism with bounded attempts, backoff, and jitter.

Tracing instrumentation may create a span per HTTP attempt depending on how retry and the HTTP client are configured. Never reuse a span ID by setting headers manually. Let the tracing library manage spans and relationships across attempts.

The fallback must retain the minimum information required for logging and producing a valid business outcome. If the fallback executes on another thread, do not assume the original request's MDC and `SecurityContext` are still present. Pass the correlation ID or business identifiers as parameters if the fallback needs them. Do not pass access tokens into a fallback unless the fallback genuinely calls another service and has its own token issuance mechanism.

## 10. Verifying Context Propagation in Practice

You can test using a request with an explicit correlation ID:

~~~bash
curl -H "X-Correlation-ID: lab-order-001" \
     "http://localhost:8080/orders/123/inventory"
~~~

If the API requires a JWT, send a test access token with valid audience and scopes:

~~~bash
curl -H "X-Correlation-ID: lab-order-001" \
     -H "Authorization: Bearer <access-token>" \
     "http://localhost:8080/orders/123/inventory"
~~~

Never use production tokens in examples or logs. Replace token placeholders with test tokens issued by your authorization server for the target API.

Verify the following checkpoints:

1. Logs at Order's request-receiving layer contain correlation ID `lab-order-001`.
2. Logs at the gateway calling Inventory contain the same correlation ID.
3. Logs at Inventory contain the same correlation ID if the header was forwarded.
4. The trace backend displays Order's server span, the client span calling Inventory, and Inventory's server span within the same trace.
5. Inventory receives the designed identity type: an intentionally relayed user token or Order's service token.
6. When the Circuit Breaker is `OPEN` and the supplier does not run, the fallback still logs using the propagated context or explicit parameters.
7. When thread-pool bulkhead is enabled, repeat the checks above to confirm context propagation still works.
8. After a request finishes, the thread serving the next request must not reuse the previous request's correlation ID or `SecurityContext`.

To verify MDC cleanup, send two consecutive requests with two different correlation IDs and compare the logs. Each request must appear only with its own ID. If the first ID appears in logs for the second request, filter or task cleanup is incomplete.

## 11. Common Issues

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Caller logs show correlation ID but provider logs do not | Outbound client does not send `X-Correlation-ID` | Add a request interceptor and a provider-side filter |
| Provider logs show a different ID from caller | A layer generated a new ID or a gateway overwrote the header | Designate a single origin for ID generation and standardize forwarding rules |
| Trace splits into two separate traces | HTTP client is not instrumented or trace header was overwritten | Use the Spring Boot-managed builder and let the tracing library inject context |
| Trace ID missing from logs | Micrometer Tracing not enabled or log pattern lacks MDC fields | Check tracing bridge, exporter, and logging pattern |
| `SecurityContext` is empty inside supplier | Supplier runs on a different thread pool | Configure Security context propagation or use an appropriate execution model |
| Inventory returns 401 or 403 | Invalid token, wrong audience, or missing scope | Inspect resource server configuration and token permissions |
| Fallback lacks correlation ID | Fallback runs on another thread or after context cleanup | Pass correlation ID explicitly or configure propagation |
| Subsequent request reuses wrong correlation ID | MDC not cleared in `finally` | Restore or clear MDC after every request and task |
| Logs accidentally contain tokens | Logging full request headers or `Authentication` | Strip `Authorization`, `Cookie`, and secrets from logs |

## 12. Design Principles

- Generate or validate the correlation ID at the request ingress boundary, then propagate it consistently across services.
- Use MDC for log fields bound to the current thread and always clean up context after each request or task.
- Use Micrometer Tracing with instrumented HTTP clients to propagate trace context.
- Never manually forge or overwrite `traceparent` when a tracing library manages propagation.
- Relay access tokens only when audience, scopes, and policy match the target service.
- Use a dedicated service identity when a call requires workload identity rather than user identity.
- Never log tokens, session cookies, passwords, or secrets.
- Determine whether a bulkhead switches threads; configure context propagation on executors when needed.
- Do not rely on `InheritableThreadLocal` to share context across thread pools.
- Test the supplier, fallback, retries, and subsequent requests to catch lost or leaked context.

When making synchronous calls through Spring Cloud CircuitBreaker, preserving context keeps logs correlatable, traces accurate end-to-end, and dependent services receiving the right identity. This depends on the actual execution path: same-thread execution can retain `ThreadLocal` values, whereas thread pools require explicit context propagation. Combining MDC, Micrometer Tracing, Spring Security, and properly configured HTTP clients keeps error diagnostics and access control consistent across service layers.
