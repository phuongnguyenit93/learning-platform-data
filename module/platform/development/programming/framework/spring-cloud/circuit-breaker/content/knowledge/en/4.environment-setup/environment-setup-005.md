# Setting Up a Caller Application and a Fault-Injectable Service

To observe a Circuit Breaker in action, you need a calling service (caller) and a dependent service (provider). The caller sends HTTP requests to the provider. The provider has modes to respond normally, respond slowly, or return errors based on request parameters. By actively controlling failure scenarios, you can observe how Spring Cloud CircuitBreaker combined with Resilience4j records outcomes, opens the circuit, returns fallbacks, and permits probe calls when the service recovers.

This lesson sets up a small practice environment consisting of two independently running Spring Boot applications:

- **inventory-service:** a service providing inventory information, running on port 8081. The service can return normal data, delay responses, or return HTTP 503.
- **circuit-breaker-client:** an application calling inventory-service, running on port 8080. The application uses Spring Cloud CircuitBreaker with Resilience4j to protect calls to Inventory.

This environment focuses on synchronous HTTP calls so learners can easily trace requests and responses. Reactive, timeout, and bulkhead examples can be added later once the basic flow is understood.

## 1. Preparing Tools and Versions

Install the following tools on your development machine:

- A JDK compatible with the chosen Spring Boot version.
- Maven or Maven Wrapper generated by Spring Initializr.
- A Java-capable IDE such as IntelliJ IDEA, Eclipse, or Visual Studio Code.
- An HTTP request tool such as curl, Postman, or the built-in HTTP Client in your IDE.

Both applications need to run simultaneously, so verify that ports 8080 and 8081 are not already in use by another program.

When creating the projects, select compatible Spring Boot and Spring Cloud versions according to the official Spring Cloud compatibility matrix. Do not pick two versions independently by intuition: a Spring Cloud release train is designed to work with specific Spring Boot lines. If your project already has a parent POM or dependency management provided by your organization, use the exact standardized versions in the project.

You can create two independent Maven projects using Spring Initializr:

| Property | inventory-service | circuit-breaker-client |
| --- | --- | --- |
| Project | Maven | Maven |
| Language | Java | Java |
| Packaging | Jar | Jar |
| Main dependencies | Spring Web | Spring Web, Spring Boot Actuator |
| Additional dependencies | Optional | Spring Cloud CircuitBreaker Resilience4j |
| Practice port | 8081 | 8080 |

Name the packages clearly, such as `com.example.inventory` for the provider and `com.example.client` for the caller. The two applications are separate processes and do not share memory or an HTTP port.

## 3. Creating an Inventory Service That Can Deliberately Inject Faults

The provider needs a stable endpoint returning inventory data, along with two test parameters:

- `fail=true`: returns HTTP 503 to simulate a failing dependent service.
- `delayMs=3000`: delays the response by 3 seconds to simulate a slow call.

Omitting parameters or passing `fail=false&delayMs=0` produces a normal response. Capping the maximum delay in the example prevents accidentally hanging the process for too long.

### 3.1. Response DTO

Create `InventoryResponse.java` in package `com.example.inventory`:

~~~java
package com.example.inventory;

public record InventoryResponse(
    String sku,
    int available,
    String status
) {
}
~~~

The DTO contains the SKU code, available stock quantity, and status. The provider returns `OK` when processing succeeds.

### 3.2. Controller Simulating Errors and Latency

Create `InventoryController.java`:

~~~java
package com.example.inventory;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

@RestController
@RequestMapping("/inventory")
public class InventoryController {

    private static final Logger log = LoggerFactory.getLogger(InventoryController.class);

    @GetMapping("/{sku}")
    public InventoryResponse getInventory(
            @PathVariable String sku,
            @RequestParam(defaultValue = "false") boolean fail,
            @RequestParam(defaultValue = "0") long delayMs) {

        long safeDelay = Math.min(Math.max(delayMs, 0), 15_000);
        log.info("Inventory request sku={} fail={} delayMs={}", sku, fail, safeDelay);

        if (safeDelay > 0) {
            try {
                Thread.sleep(safeDelay);
            } catch (InterruptedException exception) {
                Thread.currentThread().interrupt();
                throw new ResponseStatusException(
                    HttpStatus.SERVICE_UNAVAILABLE,
                    "Inventory request interrupted",
                    exception
                );
            }
        }

        if (fail) {
            throw new ResponseStatusException(
                HttpStatus.SERVICE_UNAVAILABLE,
                "Simulated inventory failure"
            );
        }

        return new InventoryResponse(sku, 25, "OK");
    }
}
~~~

The `fail` parameter simulates an error only after waiting for the requested delay. This lets you test HTTP errors alone, slow calls alone, or a combination of both. In a real application, fault-control endpoints like this should never be publicly exposed; this is strictly a local testing tool.

### 3.3. Configuring the Provider Port

In `inventory-service/src/main/resources/application.yml`:

~~~yaml
server:
  port: 8081
~~~

The startup class can be generated by Spring Initializr:

~~~java
package com.example.inventory;

    public static void main(String[] args) {
        SpringApplication.run(InventoryApplication.class, args);
    }

~~~

At this point, inventory-service can run independently and accept requests from an HTTP tool.

## 4. Creating the Caller Application and Adding Resilience4j

The caller is a Spring Boot application sending requests to Inventory. It needs Spring Web to provide an endpoint for the tester, Spring Boot Actuator for application observability, and Spring Cloud CircuitBreaker Resilience4j to wrap remote calls.

### 4.1. Declaring Maven Dependencies

In `circuit-breaker-client/pom.xml`, the project needs a Spring Boot parent matching the environment and a compatible Spring Cloud BOM. Example Spring Cloud version management section:

~~~xml
<properties>
    <java.version>17</java.version>
    <spring-cloud.version>SPRING_CLOUD_COMPATIBLE_RELEASE_TRAIN</spring-cloud.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
~~~

Replace `SPRING_CLOUD_COMPATIBLE_RELEASE_TRAIN` with a release train compatible with your project's Spring Boot version. In an actual POM, `properties` and `dependencyManagement` are placed inside the `project` element.

Declare the caller's dependencies:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
    </dependency>
</dependencies>
~~~

For the provider, the minimal dependency is `spring-boot-starter-web`. There is no need to add Resilience4j to the provider because in this exercise, the Circuit Breaker sits on the calling application's side.

Spring Cloud CircuitBreaker provides an abstraction so caller code does not have to interact directly with each provider's API. Resilience4j is the provider used in this lesson. The BOM lets Maven select synchronized Spring Cloud versions instead of declaring a separate version for each starter.

### 4.2. Configuring Inventory Address and Circuit Breaker

In `circuit-breaker-client/src/main/resources/application.yml`:

~~~yaml
server:
  port: 8080

inventory:
  base-url: http://localhost:8081

resilience4j:
  circuitbreaker:
    instances:
      inventory:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 10
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 2
        automaticTransitionFromOpenToHalfOpenEnabled: true

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
~~~

This configuration uses a window of the latest 10 calls and requires at least 5 samples before calculating rates. When the failure rate reaches 50% or the slow-call rate reaches 50%, the Circuit Breaker can transition to OPEN. Calls lasting 2 seconds or longer are counted as slow. After 10 seconds in OPEN, the circuit automatically transitions to HALF_OPEN and permits up to two probe calls.

These numbers are for a lab environment only. In production, choose thresholds based on normal traffic and dependency latency. `slowCallDurationThreshold` only marks a call as slow for rate calculation; it does not cancel the call or replace timeout configuration. Configure timeouts on the HTTP client or TimeLimiter when you want to bound actual wait time.

### 4.3. Initializing the HTTP Client

The example uses `RestClient`, a synchronous API available in Spring Framework 6.1 and later. Spring Boot provides `RestClient.Builder` to create the client:

~~~java
package com.example.client;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;

@Configuration
public class InventoryClientConfiguration {

    @Bean
    RestClient inventoryRestClient(
            RestClient.Builder builder,
            @Value("${inventory.base-url}") String baseUrl) {
        return builder
            .baseUrl(baseUrl)
            .build();
    }
}
~~~

If the project uses an older Spring Framework without `RestClient`, you can substitute `RestTemplate` or upgrade to a compatible version. Make sure Spring Boot and Spring Cloud versions are chosen from the same compatibility matrix.

### 4.4. Declaring the DTO in the Caller

Create `InventoryResponse.java` in package `com.example.client`:

~~~java
package com.example.client;

public record InventoryResponse(
    String sku,
    int available,
    String status
) {
    public static InventoryResponse unavailable(String sku) {
        return new InventoryResponse(sku, 0, "UNAVAILABLE");
    }
}
~~~

The fallback returns status `UNAVAILABLE` so the caller can distinguish fallback results from real inventory data. In a business application, clearly define the API contract: the fallback result could be a degraded response, cached data, or a controlled HTTP error, depending on feature requirements.

### 4.5. Wrapping the Call with a Circuit Breaker

Create `InventoryGateway.java`:

~~~java
package com.example.client;

import org.springframework.cloud.client.circuitbreaker.CircuitBreakerFactory;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;

@Service
public class InventoryGateway {

    private final CircuitBreakerFactory<?, ?> circuitBreakerFactory;
    private final RestClient inventoryRestClient;

    public InventoryGateway(
            CircuitBreakerFactory<?, ?> circuitBreakerFactory,
            RestClient inventoryRestClient) {
        this.circuitBreakerFactory = circuitBreakerFactory;
        this.inventoryRestClient = inventoryRestClient;
    }

    public InventoryResponse getInventory(
            String sku,
            boolean fail,
            long delayMs) {

        return circuitBreakerFactory.create("inventory").run(
            () -> inventoryRestClient.get()
                .uri(uriBuilder -> uriBuilder
                    .path("/inventory/{sku}")
                    .queryParam("fail", fail)
                    .queryParam("delayMs", delayMs)
                    .build(sku))
                .retrieve()
                .body(InventoryResponse.class),
            error -> InventoryResponse.unavailable(sku)
        );
    }
}
~~~

The name `inventory` in `create("inventory")` must match the instance name in application.yml. When the provider returns HTTP 503, `RestClient` throws an exception and the Circuit Breaker records a failed outcome. When the circuit is OPEN or the call fails, the fallback function returns a DTO with status `UNAVAILABLE`.

In this example, the fallback returns a normal DTO so the caller endpoint can still return HTTP 200. This is a simple choice for observing results. For a real API, design responses and HTTP statuses to fit the business contract, avoiding letting clients mistake fallback data for confirmed inventory data.

### 4.6. Exposing a Test Endpoint

Create `InventoryController.java` in the caller:

~~~java
package com.example.client;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InventoryController {

    private final InventoryGateway inventoryGateway;

    public InventoryController(InventoryGateway inventoryGateway) {
        this.inventoryGateway = inventoryGateway;
    }

    @GetMapping("/check/{sku}")
    public InventoryResponse check(
            @PathVariable String sku,
            @RequestParam(defaultValue = "false") boolean fail,
            @RequestParam(defaultValue = "0") long delayMs) {
        return inventoryGateway.getInventory(sku, fail, delayMs);
    }
}
~~~

The startup class `ClientApplication` is created similarly to `InventoryApplication`, in package `com.example.client`.

The request flow is now:

~~~text
HTTP client
    |
    v
circuit-breaker-client :8080
    |
    v
CircuitBreaker "inventory"
    |
    +---- CLOSED / HALF_OPEN: allow call
    |             |
    |             v
    |       RestClient
    |             |
    |             v
    |       inventory-service :8081
    |
    +---- OPEN: reject call
                  |
                  v
               fallback
~~~

## 5. Starting Both Applications

Open two separate terminals in the project directory.

In the first terminal, run the provider:

~~~powershell
cd inventory-service
.\mvnw.cmd spring-boot:run
~~~

In the second terminal, run the caller:

~~~powershell
cd circuit-breaker-client
.\mvnw.cmd spring-boot:run
~~~

If using a pre-installed Maven instead of Maven Wrapper, you can run `mvn spring-boot:run`. Start the provider first so the caller can connect immediately when receiving requests. Once both applications are ready, check the health endpoint if Actuator is enabled or send a direct test request to Inventory.

If running from an IDE, create two separate Run Configurations and ensure each application uses the proper working directory. Do not start both applications on the same port.

## 6. Testing the Provider Independently First

Before testing the Circuit Breaker, call the provider directly to confirm the mock endpoint works properly.

Normal response:

~~~bash
curl "http://localhost:8081/inventory/ABC-001"
~~~

The provider returns data similar to:

~~~json
{
  "sku": "ABC-001",
  "available": 25,
  "status": "OK"
}
~~~

Simulate HTTP 503 error:

~~~bash
curl -i "http://localhost:8081/inventory/ABC-001?fail=true"
~~~

Simulate a 3-second slow response:

~~~bash
curl -i "http://localhost:8081/inventory/ABC-001?delayMs=3000"
~~~

If direct requests do not yield expected results, resolve the provider issue first. When the provider is not running or the URL is wrong, the caller can also receive connection errors; connection errors are still a scenario you can use to observe the Circuit Breaker, though they are harder to distinguish from errors produced by the mock endpoint.

## 7. Sending Requests Through the Caller

Once both applications are running, send a request to the caller:

~~~bash
curl "http://localhost:8080/check/ABC-001"
~~~

The caller invokes Inventory and returns successful data.

Simulate an error:

~~~bash
curl "http://localhost:8080/check/ABC-001?fail=true"
~~~

The caller receives HTTP 503 from the provider. The fallback returns a result with status `UNAVAILABLE`. If only one request has failed, the Circuit Breaker usually remains CLOSED because `minimumNumberOfCalls` has not been reached to evaluate the rate.

Simulate a slow call:

~~~bash
curl "http://localhost:8080/check/ABC-001?delayMs=3000"
~~~

The request takes about 3 seconds at the provider. With the lab configuration, this duration exceeds `slowCallDurationThreshold: 2s` and is recorded as a slow call. A single slow call is not enough to open the circuit if the minimum sample count and required slow-call rate have not been met.

## 8. Generating Enough Samples to Observe the Circuit Breaker Opening

The lab configuration requires a minimum of 5 calls and a 50% error threshold. To create a clear scenario, send at least 5 failing requests through the caller. In PowerShell:

~~~powershell
1..5 | ForEach-Object {
    curl.exe -s "http://localhost:8080/check/ABC-001?fail=true"
}
~~~

Or send repeated requests in Postman. Once enough samples are collected, the failure rate reaches 100%, exceeding the 50% threshold, and the Circuit Breaker transitions to OPEN.

Send additional failing or normal requests through the caller while the Circuit Breaker is OPEN. The caller continues returning the `UNAVAILABLE` fallback, while the provider receives no new requests from the Circuit Breaker while the circuit is open. You can check the inventory-service logs to verify that circuit-broken requests do not continue reaching the provider controller.

After `waitDurationInOpenState: 10s` elapses, the Circuit Breaker transitions to HALF_OPEN due to the automatic transition configuration. Send two successful requests:

~~~powershell
1..2 | ForEach-Object {
    curl.exe -s "http://localhost:8080/check/ABC-001?fail=false"
}
~~~

Two successful probe calls allow the Circuit Breaker to return to CLOSED. If probe calls continue failing or exceed the slow-call threshold, the circuit can return to OPEN.

To test the slow-call condition, send multiple requests with `delayMs=3000`. Once the minimum sample count is met and the slow-call rate exceeds the threshold, the Circuit Breaker can also open the circuit even though the final requests return successfully. Wait for the state to return to CLOSED before running another independent test scenario, or restart the caller to reset the instance to its initial state in the lab environment.

## 9. Observing State and Metrics

The caller has Spring Boot Actuator added and exposes the health, info, and metrics endpoints. You can check health:

~~~bash
curl "http://localhost:8080/actuator/health"
~~~

Depending on provider configuration and integration version, Resilience4j can provide metrics such as successful, failed, and rejected call counts, failure rate, and slow-call rate. Inspect the metrics published by the application:

~~~bash
curl "http://localhost:8080/actuator/metrics"
~~~

The `/actuator/metrics` endpoint returns a list of available metric names. You can query a specific metric by replacing `{metric-name}` with a returned name:

~~~bash
curl "http://localhost:8080/actuator/metrics/{metric-name}"
~~~

Metric names and tags depend on the Resilience4j version, Micrometer, and Actuator configuration. If expected metrics do not appear, check dependencies, endpoint exposure, tag configuration, and provider metrics integration. Do not assume that merely adding Actuator makes every Circuit Breaker metric appear automatically in every version.

In shared environments, expose only the necessary management and metrics endpoints. Do not open Actuator widely to public networks without proper authentication and access control.

## 10. Common Errors During Environment Setup

| Symptom | Common Cause | How to Check |
| --- | --- | --- |
| Caller fails to start | Incompatible Spring Boot and Spring Cloud versions or Maven cannot resolve dependencies | Check BOM, release train, and Maven logs |
| Caller reports connection refused | Provider is not running, wrong port, or wrong `inventory.base-url` | Call port 8081 directly and check application.yml |
| Request returns 404 | Wrong mapping or wrong path | Check `/inventory/{sku}` on provider and `/check/{sku}` on caller |
| Sending `fail=true` does not open the Circuit Breaker | Insufficient samples, errors not recorded, or threshold not exceeded | Check `minimumNumberOfCalls`, exceptions, and request count |
| Sending slow requests does not open the circuit | Insufficient sample count or slow-call rate has not reached threshold | Check `slowCallDurationThreshold`, `slowCallRateThreshold`, and actual duration |
| Fallback does not run as expected | Incompatible fallback signature or return type, or request does not go through the right Circuit Breaker | Check the `run` block, instance name, and exception logs |
| Metrics not visible | Actuator not enabled, endpoint not exposed, or Micrometer integration missing | Check dependencies and metric list |
| Port already in use | Another application occupies 8080 or 8081 | Stop the old process or change ports in sync with base URL |

A common configuration mistake is using different instance names between Java code and application.yml. For example, code calls `create("inventory")` while YAML declares `instances.inventoryService`. In that case, the expected configuration may not apply to the running instance. Keep the name consistent from end to end.

Another issue is confusing slow calls with timeouts. A slow-call threshold only marks calls that took a long time to complete. If you need to abort a request after a specific limit, configure a timeout on the HTTP client or TimeLimiter. The two mechanisms can work together, but they solve two different objectives.

## 11. Preparing for Subsequent Practice Exercises

Once the environment is working, you can use these two applications to practice the upcoming topics:

- Adjust `slidingWindowSize`, `minimumNumberOfCalls`, and `failureRateThreshold`, then observe when the Circuit Breaker opens the circuit.
- Compare COUNT_BASED and TIME_BASED by varying request sending cadence.
- Test CLOSED, OPEN, and HALF_OPEN using deliberate sequences of failures and successes.
- Modify the fallback to distinguish cached data, degraded results, and business errors.
- Add timeout and bulkhead to observe how wait time and concurrent calls are bounded.
- Create a WebFlux version with WebClient and ReactiveCircuitBreakerFactory to practice reactive flows.

Before moving to the next lesson, confirm that the provider runs on port 8081, the caller runs on port 8080, normal requests return inventory data, `fail=true` requests produce a 503 error, and requests with `delayMs` produce observable latency. Once these scenarios are reproducible, you have a stable environment to observe how Circuit Breaker protects the calling application when a dependency is slow or unavailable.
