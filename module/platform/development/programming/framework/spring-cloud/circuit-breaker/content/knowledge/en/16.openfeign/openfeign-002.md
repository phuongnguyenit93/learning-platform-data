# Naming Rules by Client, Method, and Signature

When integrating Spring Cloud OpenFeign with CircuitBreaker, each call in a Feign client needs to be associated with a stable circuit breaker identifier. That identifier determines which policy the call uses, under what name metrics are recorded, and how it binds to a Resilience4j configuration instance. If you only use the service name without considering the client interface and method, multiple calls may unintentionally share a single breaker. If you generate names from per-request data, the application can produce too many breakers and metrics.

To design naming intentionally, distinguish three levels: **client** identifies the group of Feign calls, **method** identifies the operation being called, and **method signature** distinguishes methods with the same name that accept different parameters. Spring Cloud OpenFeign allows customizing the circuit breaker name via `CircuitBreakerNameResolver`, synchronizing generated names with configuration and runtime observability.

## 1. Three Kinds of Names to Distinguish

In an application with multiple Feign clients, a name can appear in several places with different meanings:

| Component | Example | Role |
|---|---|---|
| `@FeignClient(name = ...)` | `inventory-service` | Name of the target service that the Feign client calls, typically used with service discovery or load balancing |
| `contextId` | `inventoryReadClient` | Identifier for the Feign client's dedicated configuration context in the application, useful when multiple clients call the same service but need different configurations |
| Circuit breaker ID | `inventoryserviceInventoryClientfindBySkuString` | Policy identifier protecting a client method or a selected group of calls |

`name` is not automatically unique for every method. `contextId` is also not the circuit breaker name by default in every version. The circuit breaker ID is generated by the OpenFeign integration mechanism and can be customized via a resolver. Do not conflate these three concepts when configuring.

Example of two clients calling the same inventory service with different purposes and configurations:

```java
@FeignClient(
        name = "inventory-service",
        contextId = "inventoryReadClient")
public interface InventoryReadClient {
    // Read-only inventory APIs.
}

@FeignClient(
        name = "inventory-service",
        contextId = "inventoryAdminClient")
public interface InventoryAdminClient {
    // Inventory administration APIs.
}
```

Both clients share the same `name` to call the same service, but have different `contextId` values so Spring Cloud OpenFeign creates separate configuration contexts. If both need different circuit breaker policies, the breaker name must distinguish the two call groups. A resolver can use the target interface type together with the method to generate distinct IDs.

## 2. Enabling CircuitBreaker Integration for OpenFeign

Spring Cloud OpenFeign can integrate Spring Cloud CircuitBreaker to wrap Feign calls. Enable this feature with the property:

```yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true
```

When enabled and a compatible CircuitBreaker implementation is on the classpath, the Feign builder uses the circuit breaker integration mechanism for supported methods. With Resilience4j, the application typically adds the Spring Cloud CircuitBreaker Resilience4j starter and manages versions via a Spring Cloud release train compatible with Spring Boot.

If `spring.cloud.openfeign.circuitbreaker.enabled` is not enabled, placing `@FeignClient` or declaring `fallback` does not prove that calls are wrapped by a circuit breaker. Verify the effective configuration, dependencies, and runtime metrics.

## 3. Breaker Names Bound to Client Methods

A Feign interface typically declares multiple methods. For example:

```java
@FeignClient(name = "inventory-service", contextId = "inventoryClient")
public interface InventoryClient {

    @GetMapping("/inventory/{sku}")
    InventoryView findBySku(@PathVariable("sku") String sku);

    @GetMapping("/inventory/{sku}/availability")
    AvailabilityView checkAvailability(@PathVariable("sku") String sku);

    @PostMapping("/inventory/reservations")
    ReservationView reserve(@RequestBody ReservationRequest request);
}
```

This client has three methods with different purposes and failure characteristics. Calls to read inventory, check availability, and create a reservation may need different timeouts, fallbacks, or failure thresholds. If all methods share the same breaker ID, failures in one operation can affect the others.

A common naming rule combines the client identifier with the method name. When overloads must be distinguished, append the method parameter types to the name. For example:

| Client | Method | Parameter | ID Meaning |
|---|---|---|---|
| `InventoryClient` | `findBySku` | `String` | Read inventory by SKU |
| `InventoryClient` | `checkAvailability` | `String` | Check availability |
| `InventoryClient` | `reserve` | `ReservationRequest` | Create reservation |
| `PricingClient` | `findBySku` | `String` | Fetch price; separated from the same-named operation in InventoryClient |

The exact name depends on the resolver and the Spring Cloud OpenFeign version. Inspect the actually generated identifier or explicitly provide a resolver, rather than hardcoding an unverified default format for the version in use.

## 4. Role of CircuitBreakerNameResolver

Spring Cloud OpenFeign provides `CircuitBreakerNameResolver` to customize how breaker names are generated. The resolver receives information about the Feign client name, target, and Java `Method`, and returns the ID used for the circuit breaker.

The following example builds the ID from the client name, target interface, method, and parameter types:

```java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.stream.Collectors;

import feign.Target;
import org.springframework.cloud.openfeign.CircuitBreakerNameResolver;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class FeignCircuitBreakerNamingConfiguration {

    @Bean
    CircuitBreakerNameResolver circuitBreakerNameResolver() {
        return (feignClientName, target, method) -> {
            String parameterTypes = Arrays.stream(method.getParameterTypes())
                    .map(Class::getSimpleName)
                    .collect(Collectors.joining(""));

            String rawName = feignClientName
                    + target.type().getSimpleName()
                    + method.getName()
                    + parameterTypes;

            return rawName.replaceAll("[^A-Za-z0-9]", "");
        };
    }
}
```

The resolver above uses:

- `feignClientName`: the client name passed by OpenFeign to the resolver.
- `target.type()`: the target Feign interface, distinguishing different client interfaces.
- `method.getName()`: the Java operation name.
- `method.getParameterTypes()`: the parameter types in the method signature, distinguishing overloads.

For `InventoryClient.findBySku(String sku)` with client name `inventory-service`, the normalized ID will look like `inventoryserviceInventoryClientfindBySkuString`. Another method or another interface will get its own ID.

This is an illustrative rule. In a real application, confirm that the resolver is loaded by Spring for the right Feign clients and verify the runtime names. If the client name can vary across environments, consider using `contextId` or an explicit mapping when the resolver API and version provide enough information. Do not assume `contextId` is always passed as `feignClientName`; the resolver receives the exact arguments defined in the current version's API.

## 5. Why Method Signatures Matter

Using only `method.getName()` may be insufficient when an interface has overloaded methods. For example:

```java
public interface ReportClient {
    @GetMapping("/reports/by-id")
    ReportView find(@RequestParam("id") String id);

    @GetMapping("/reports/by-code")
    ReportView find(@RequestParam("code") Long code);
}
```

Both methods share the Java name `find`, but their parameters are `String` and `Long`, respectively. If the resolver only concatenates client name and method name, both may produce the same ID. They would then share the same breaker and the same sliding window even though they call two different endpoints.

Including parameter types in the ID distinguishes them:

```text
reportclientReportClientfindString
reportclientReportClientfindLong
```

In Java, an overload signature is determined by the method name and parameter type list; return type alone does not create a distinct overload. Therefore, the resolver should rely on `getParameterTypes()` when overloads need to be distinguished.

### Limitations of Simple Parameter Types

`Class.getSimpleName()` is readable, but it may not be unique if two types from different packages share the same simple name. For large projects or complex inherited interfaces, you can use normalized fully qualified names:

```java
String parameterTypes = Arrays.stream(method.getParameterTypes())
        .map(Class::getName)
        .collect(Collectors.joining(""));
```

Then strip dots, `$`, square brackets, and non-alphanumeric characters if you want an alphanumeric-only ID. Pay attention to array types, primitives, and nested classes so the normalized name remains stable and does not cause unintended collisions.

Java generic types undergo type erasure. `List<String>` and `List<Long>` both have the raw parameter type `List.class`; `getParameterTypes()` does not distinguish generic arguments. If the design involves complex inherited generic contracts that need distinct names, use an explicit ID mapping or inspect `getGenericParameterTypes()` alongside the resolved target method. Avoid relying on Java parameter names, as parameter names may not be preserved in bytecode unless compiler parameter metadata is enabled.

## 6. Separating Policies by Client and Method

Not every method needs its own breaker. Choose the granularity based on whether methods share the same dependency, failure characteristics, SLA, and recovery behavior.

| Naming Approach | When Appropriate | Impact |
|---|---|---|
| One breaker per client | Methods share the same dependency and similar failure policies | Easy to manage, but failures in one method can affect others |
| One breaker per method | Methods have different SLAs, timeouts, or fallbacks | Better isolation, requires managing more instances |
| One breaker per method signature | Overloads have different semantics or backends | Prevents ID collisions between overloads |
| One breaker per operation group | Multiple methods can share one business policy | Reduces instance count, requires clear group mapping |

For example, `findBySku` and `checkAvailability` both read inventory data and may share a breaker if they hit the same backend with the same policy. The `reserve` method writes data and has idempotency requirements, so it may need a separate policy. Do not split breakers just because methods have different names if they genuinely share the same failure boundary and protection goal.

When sharing a breaker, a high-traffic method can dominate the sliding window and open the breaker for the remaining methods. When split, each breaker has fewer samples and may take longer to reach `minimumNumberOfCalls`. Balance both isolation and statistical quality.

## 7. Alphanumeric ID Configuration and Version Compatibility

Recent versions of Spring Cloud OpenFeign support normalizing circuit breaker IDs to alphanumeric characters. The property controlling this behavior is:

```yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true
        alphanumeric-ids:
          enabled: true
```

Normalization makes IDs compatible with configuration and metric systems that restrict characters. Generated names may differ from formats used in older versions. When upgrading the Spring Cloud release train, check the version documentation and runtime IDs before renaming instances in Resilience4j configuration.

If you use a custom `CircuitBreakerNameResolver`, decide explicitly whether the resolver normalizes names itself and test its interaction with the alphanumeric ID option in the running version. Do not assume a custom resolver is always transformed the same way as the default resolver.

Changing the naming rule can cause the application to create new breaker instances instead of using the configured ones. When that happens, old configuration may no longer apply, metrics split across different name series, and dashboards/alerts fail to find the instance. Update the resolver, `resilience4j.circuitbreaker.instances` configuration, and dashboards in the same plan.

## 8. Synchronizing IDs with Resilience4j Configuration

Resilience4j uses the breaker ID as the key under `resilience4j.circuitbreaker.instances`. The ID in configuration must match the resolver output exactly.

With the resolver above, suppose the runtime ID of `InventoryClient.findBySku(String)` is `inventoryserviceInventoryClientfindBySkuString`. The configuration can be declared as:

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventoryserviceInventoryClientfindBySkuString:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        slowCallDurationThreshold: 800ms
        slowCallRateThreshold: 60
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
```

If the ID in YAML does not match, the instance may receive the default configuration instead of the intended policy, depending on factory setup and integration version. Therefore, log the actual ID at startup or observe it via metrics and cross-check against the configuration.

To reduce risks from long names or signature-driven changes, you can use an explicit mapping inside the resolver:

```java
@Bean
CircuitBreakerNameResolver circuitBreakerNameResolver() {
    return (clientName, target, method) -> {
        String clientType = target.type().getSimpleName();
        String operation = clientType + "_" + method.getName();

        if (clientType.equals("InventoryClient")
                && method.getName().equals("findBySku")) {
            return "inventoryRead";
        }
        if (clientType.equals("InventoryClient")
                && method.getName().equals("reserve")) {
            return "inventoryReserve";
        }
        return (clientName + "_" + operation)
                .replaceAll("[^A-Za-z0-9]", "");
    };
}
```

Explicit mapping keeps names short and stable across certain refactorings. However, you must update the mapping when a method is renamed or moved to another interface; otherwise, the resolver may fall back to a rule that the configuration did not anticipate. Projects should have tests verifying names for critical methods.

## 9. Fallback Belongs to the Feign Client, Not the Breaker Name

OpenFeign supports `fallback` and `fallbackFactory` to provide an alternative result when a call fails under the integration mechanism. Fallback is not part of the breaker name, though it is configured on the same `@FeignClient`.

Example using `fallbackFactory` to record the cause:

```java
@FeignClient(
        name = "inventory-service",
        contextId = "inventoryClient",
        fallbackFactory = InventoryFallbackFactory.class)
public interface InventoryClient {

    @GetMapping("/inventory/{sku}")
    InventoryView findBySku(@PathVariable("sku") String sku);
}
```

```java
import org.springframework.cloud.openfeign.FallbackFactory;
import org.springframework.stereotype.Component;

@Component
public class InventoryFallbackFactory implements FallbackFactory<InventoryClient> {

    @Override
    public InventoryClient create(Throwable cause) {
        return sku -> {
            // Record the cause and return a state without confirmed data.
            return InventoryView.unavailable(sku);
        };
    }
}
```

The fallback factory receives the failure cause so the application can classify timeouts, connection errors, or breaker rejections. In practice, log the cause in a structured way and return an appropriate business state. Do not return quantity 0 if the application could not read inventory; `UNAVAILABLE` is different from `OUT_OF_STOCK`.

A Feign fallback should also not call back into the same client or the same failing dependency. If the fallback keeps calling the same service, the application can create a failure loop and increase load. If using a cache, clearly represent stale data and its update timestamp.

## 10. Common Naming Mistakes

| Symptom | Cause | Resolution |
|---|---|---|
| Multiple methods unintentionally share one breaker | Resolver only uses client name or insufficiently distinct method name | Add target type and method signature or explicit mapping |
| Two clients calling the same service share an ID | Relies only on service name, ignoring interface/client context | Use target type or client-specific rules |
| YAML does not apply desired thresholds | ID in `instances` differs from what the resolver returns | Check runtime name and synchronize exactly |
| Overloads share metrics | Resolver only appends `method.getName()` | Include parameter types in the ID |
| Breaker name changes after version upgrade | Default rule / alphanumeric ID behavior changed | Check release train, resolver, and metrics after upgrading |
| High metric cardinality | Breaker name contains SKU, user ID, or request data | Use only static client/method metadata |
| Hard to distinguish two clients with the same `name` | Using service name as the sole identifier | Set distinct `contextId` and use target interface in resolver when appropriate |
| Fallback runs without clear cause | Using static fallback and ignoring cause | Use `FallbackFactory` to log/record metrics by error type |

Do not include runtime parameter values such as `sku`, `orderId`, user ID, or actual URL paths in the circuit breaker ID. An ID is a long-lived policy identifier, not a per-call key. Using dynamic data will cause the number of breakers to grow uncontrollably, consuming memory and creating very high metric cardinality.

## 11. Testing Naming Rules

Breaker names should be tested as part of the configuration contract. You can write unit tests directly for the resolver or integration tests through the Feign client.

Cases to verify:

1. Two differently named methods in the same client produce different IDs when separate policies are needed.
2. Two overloads with the same name but different parameter types produce different IDs.
3. Two client interfaces calling the same service name remain distinct when policies must be separated.
4. Methods inherited from a parent interface are named stably based on the actual target type and method.
5. Methods with primitive, array, nested class, or different-package parameter types do not cause unintended collisions.
6. The name returned by the resolver matches the alphanumeric rules of the version in use.
7. Names in YAML `resilience4j.circuitbreaker.instances` match the runtime IDs exactly.
8. Fallback or fallbackFactory is invoked when the breaker opens or the Feign call fails per policy.
9. No breaker name contains dynamic request data.

A simple unit test for a pure ID-generation function can verify that two different signatures return two different names. For actual integration, confirm the ID via Resilience4j logs or metrics when calling the Feign client. Testing `@FeignClient` annotations by reflection alone does not prove the resolver is used at runtime.

## 12. Workflow for Designing Names for a Feign Client

When adding a Feign client to a Spring Cloud CircuitBreaker system, follow this sequence:

1. Set `name` to the target service or service discovery name.
2. Set a distinct `contextId` when multiple Feign clients call the same service but need separate configuration contexts.
3. List methods and group operations that share the same failure boundary, timeouts, and fallback.
4. Decide whether to use one breaker for the whole client, per method, or per method signature.
5. Enable `spring.cloud.openfeign.circuitbreaker.enabled` and add a compatible starter.
6. Use `CircuitBreakerNameResolver` if the default format does not meet requirements or if overloads/clients must be distinguished.
7. Keep IDs stable, relying solely on static client, target, and method metadata.
8. Synchronize IDs with `resilience4j.circuitbreaker.instances` and dashboards/alerts.
9. Write tests verifying the generated names, applied configuration, and fallback behavior.
10. When upgrading Spring Cloud, check changes to the resolver and alphanumeric IDs before deploying.

Naming rules by client, method, and signature ensure each Feign operation receives the right protection policy. `name` identifies the target service, `contextId` separates client configuration contexts, and `CircuitBreakerNameResolver` determines the breaker ID. Combining the target interface with the method signature prevents collisions between operations while keeping names stable so Resilience4j configuration, metrics, and alerts always reference the same instance.
