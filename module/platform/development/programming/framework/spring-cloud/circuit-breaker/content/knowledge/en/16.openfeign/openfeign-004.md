# Mapping Generated Names to Resilience4j Configuration Keys

When Circuit Breaker is enabled for Spring Cloud OpenFeign, each Feign client method call can be protected by its own Circuit Breaker. Spring Cloud generates an identifier name for the Circuit Breaker from the client and invoked method information. Resilience4j, in turn, looks up configuration by instance name under `resilience4j.circuitbreaker.instances`. Therefore, if the generated name and the configuration key do not match, calls may run with the default configuration instead of the thresholds the development team intended.

In the **SPRING_CLOUD_CIRCUIT_BREAKER** module, mapping this name accurately enables configuring CLOSED, OPEN, HALF_OPEN, sliding windows, timeouts, and fallbacks per dependency. You need to understand where names come from, how characters are normalized, how Spring Cloud versions affect naming, and how to verify the actual name at runtime.

## 1. Where Does the Circuit Breaker Name Come From?

When Circuit Breaker is enabled for OpenFeign, Spring Cloud OpenFeign uses the Spring Cloud CircuitBreaker integration to wrap Feign methods. Each call is bound to an identifier so the factory can create the corresponding Circuit Breaker.

Factors typically involved in name generation:

- The Feign client name passed into the name resolution mechanism.
- The method invoked on the client interface.
- The default name resolution rule or a custom `CircuitBreakerNameResolver`.
- ID normalization rules, such as stripping non-alphanumeric characters in certain versions/configurations.

Example:

~~~java
@FeignClient(name = "inventory")
public interface InventoryClient {
    @GetMapping("/items/{sku}")
    Inventory getInventory(@PathVariable("sku") String sku);

    @GetMapping("/items/{sku}/availability")
    Availability getAvailability(@PathVariable("sku") String sku);
}
~~~

The client has two methods. If the naming resolver generates IDs from the client name and method name pair, the two calls will have two different Circuit Breaker names. This allows setting separate thresholds for reading inventory and checking availability if the two operations differ in traffic or latency.

The generated name is the Circuit Breaker's identifier key. It does not necessarily match the service name in the registry, the Java bean name, or the HTTP URL.

## 2. Enabling Circuit Breaker for OpenFeign

In Spring Boot configuration, enable OpenFeign's Circuit Breaker support:

~~~yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true
~~~

The application also needs the Spring Cloud CircuitBreaker integration dependency with the Resilience4j implementation and OpenFeign dependencies compatible with the release train in use. The Spring Boot, Spring Cloud, and Resilience4j versions must be compatible with each other.

Once enabled, Feign calls are wrapped by a Circuit Breaker. The specific instance name depends on the active naming resolver. Therefore, determine the actual name before writing keys in Resilience4j YAML.

## 3. ID Normalization Rules and Version Differences

Spring Cloud OpenFeign supports an alphanumeric ID option. Depending on the version and configuration, names generated by the default rule may be normalized by removing non-alphanumeric characters. For example, underscores or separators in the name may no longer appear in the final ID.

Related property:

~~~yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true
        alphanumeric-ids:
          enabled: true
~~~

When using the default resolver, check the documentation for your specific Spring Cloud release train to learn the naming rule and default value of `alphanumeric-ids.enabled`. Do not copy configuration keys from an example for another version and assume the result will be identical.

Example illustrating normalization differences:

| Name Before Normalization | After Removing Separators |
| --- | --- |
| `inventory_getInventory` | `inventorygetInventory` |
| `catalog_findBySku` | `catalogfindBySku` |
| `payment_createOrder` | `paymentcreateOrder` |

The table above illustrates separator removal; the actual name also depends on the resolver and version. Use the name generated at runtime as the basis for the Resilience4j key.

## 4. Generating Stable Names with CircuitBreakerNameResolver

If you want to control the name and avoid depending on default rule changes across versions, provide a `CircuitBreakerNameResolver` bean. The resolver receives the Feign client name, target, and method, and returns the desired ID.

Example choosing the `<client>_<method>` convention:

~~~java
import feign.Target;
import java.lang.reflect.Method;
import org.springframework.cloud.openfeign.CircuitBreakerNameResolver;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class FeignCircuitBreakerConfiguration {
    @Bean
    CircuitBreakerNameResolver circuitBreakerNameResolver() {
        return (feignClientName, target, method) ->
                feignClientName + "_" + method.getName();
    }
}
~~~

With a client named `inventory` and method `getInventory`, the resolver above generates `inventory_getInventory`. If the method is `getAvailability`, the name will be `inventory_getAvailability`.

When using a custom resolver, the key in Resilience4j must match the exact string the resolver returns. If the resolver adds prefixes, suffixes, or uses the interface name instead of the client name, the YAML keys must also reflect that convention.

Do not have multiple `CircuitBreakerNameResolver` beans competing in the same context. If multiple Feign clients need different policies, a single resolver can branch on client name or target information to generate consistent IDs.

## 5. Mapping IDs to Resilience4j Instances

Suppose the resolver returns:

- `inventory_getInventory` for the inventory read method.
- `inventory_getAvailability` for the availability check method.

We declare the two corresponding instances:

~~~yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory_getInventory:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        slowCallDurationThreshold: 1500ms
        slowCallRateThreshold: 60
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
      inventory_getAvailability:
        slidingWindowType: TIME_BASED
        slidingWindowSize: 10
        minimumNumberOfCalls: 15
        failureRateThreshold: 40
        slowCallDurationThreshold: 800ms
        slowCallRateThreshold: 50
        waitDurationInOpenState: 15s
        permittedNumberOfCallsInHalfOpenState: 2
~~~

In the example:

- The inventory lookup call uses a window of the last 20 results and a 50% failure threshold.
- The availability check call uses a 10-second window and a 40% failure threshold.
- Each instance has its own OPEN duration and HALF_OPEN probe call count.

These values are only meant to illustrate name mapping. Choose thresholds based on the measured traffic and latency of each operation.

If the actual ID was normalized to `inventorygetInventory`, but YAML only declares `inventory_getInventory`, Resilience4j will not find the instance under the expected name. In that case, the configuration may not apply to that call and the application will use default configuration or fallback configuration depending on how it is set up.

## 6. Using Shared Configs and Per-Instance Overrides

Multiple Feign methods can share a common base policy. You can declare `configs` and reference them via `baseConfig`:

~~~yaml
resilience4j:
  circuitbreaker:
    configs:
      feign-read-default:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 60
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
    instances:
      inventory_getInventory:
        baseConfig: feign-read-default
      inventory_getAvailability:
        baseConfig: feign-read-default
        slowCallDurationThreshold: 800ms
        failureRateThreshold: 40
~~~

Both instances share the same base policy. The availability check instance overrides the slow call duration threshold and failure rate threshold because that operation requires faster responses.

The name `feign-read-default` is an application-chosen config name; it is not the Circuit Breaker ID generated by OpenFeign. Only the keys under `instances` need to match the ID returned by the resolver.

## 7. Separating Configuration per Feign Client

When an application has multiple Feign clients, avoid confusing the service name with per-method IDs:

~~~java
@FeignClient(name = "inventory")
public interface InventoryClient {
    @GetMapping("/items/{sku}")
    Inventory getInventory(@PathVariable("sku") String sku);
}

@FeignClient(name = "payment")
public interface PaymentClient {
    @PostMapping("/payments")
    PaymentResult createPayment(@RequestBody PaymentRequest request);
}
~~~

With the resolver `feignClientName + "_" + method.getName()`, illustrative names would be `inventory_getInventory` and `payment_createPayment`. Declare the corresponding instances:

~~~yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory_getInventory:
        slidingWindowSize: 20
        failureRateThreshold: 50
      payment_createPayment:
        slidingWindowSize: 10
        failureRateThreshold: 30
        waitDurationInOpenState: 30s
~~~

Payments may need different thresholds and OPEN durations than inventory reads. For write operations like payments, combine an idempotency key and reconciliation process; a Circuit Breaker does not determine on its own whether a transaction was processed when a request times out.

## 8. Verifying the Actual Name at Runtime

When configuration does not take effect as expected, verify the ID in this order:

1. Check that `spring.cloud.openfeign.circuitbreaker.enabled` is enabled in the active profile.
2. Determine whether a custom `CircuitBreakerNameResolver` bean is present.
3. Log the `feignClientName`, method name, and string returned by the resolver in a development environment.
4. Check the `alphanumeric-ids.enabled` option and the rules of the Spring Cloud version in use.
5. Compare the runtime ID against the `resilience4j.circuitbreaker.instances.<id>` key.
6. Check corresponding metrics or Actuator endpoints if the application has enabled and secured those endpoints.

You can add logging inside the resolver to inspect the result:

~~~java
@Bean
CircuitBreakerNameResolver circuitBreakerNameResolver() {
    return (feignClientName, target, method) -> {
        String circuitBreakerId =
                feignClientName + "_" + method.getName();
        log.debug(
                "OpenFeign Circuit Breaker ID: client={}, method={}, id={}",
                feignClientName,
                method.getName(),
                circuitBreakerId);
        return circuitBreakerId;
    };
}
~~~

In the example, `log` is the configuration class logger. Log only the necessary identifiers and method names; do not log request payloads, tokens, or sensitive data. Once the ID is confirmed, lower the log level appropriately for deployment environments.

Resilience4j metrics typically attach the instance name in the `name` tag. If Micrometer and metrics endpoints are enabled, use that tag to cross-check against YAML keys. Specific Actuator endpoints depend on dependencies, exposure configuration, and Spring Boot version.

## 9. Distinguishing Client Name, contextId, and Circuit Breaker ID

The following three concepts are related but should not be treated as identical:

| Value | Purpose |
| --- | --- |
| `@FeignClient(name = "inventory")` | Service/client identifier used in Feign configuration and routing |
| `contextId` | Identifier for a Feign client's dedicated configuration context, useful when multiple clients share a service name but need different configurations |
| Circuit Breaker ID | Name generated by the resolver for a call and used to look up the Resilience4j instance |

If `contextId` is declared, do not assume the Circuit Breaker ID will use `name` or `contextId` in all versions. The resolver receives the `feignClientName` parameter passed by Spring Cloud OpenFeign; log that value to know the exact input used in the current application.

Separating these values avoids common mistakes: configuring `instances.inventory` while the resolver actually returns `inventory_getInventory`, or mistakenly using `contextId` as the key even though the resolver does not generate names from it.

## 10. Common Mapping Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Using the Feign client name as the instance key for all methods | Key does not match per-method ID | Use the exact ID returned by the active resolver |
| Ignoring alphanumeric normalization | Underscores or separators differ between ID and YAML | Check the version and `alphanumeric-ids.enabled` |
| Copying keys from examples of another release train | IDs may change under default rules | Log the ID or use a stable custom resolver |
| Renaming a method without updating YAML keys | Calls no longer reference the old instance | Update configuration together with the Feign interface |
| Confusing `contextId` with Circuit Breaker ID | Configuration placed under the wrong key | Inspect the value the resolver receives and returns |
| Multiple resolvers with unclear ordering | Generated name is hard to predict | Register only one resolver with a clear convention |
| Defining only `configs` without a referencing instance | Calls do not use the desired config | Declare `instances.<generated-id>.baseConfig` |
| Not checking runtime metrics | Misconfiguration goes unnoticed | Cross-check the instance name tag and resolver logs |

## 11. Workflow for Mapping Names for a New Feign Client

When adding a new Feign client or method, follow these steps:

1. Enable Circuit Breaker for OpenFeign in the application configuration.
2. Identify the active default naming resolver or register a custom resolver.
3. List the client names and methods that need protection.
4. Determine the generated ID string for each method, including any normalization step.
5. Declare `resilience4j.circuitbreaker.instances` with keys matching those IDs.
6. Use `baseConfig` if multiple instances share a policy, overriding only parameters that differ.
7. Test successful calls, HTTP errors, timeouts, and the OPEN state; inspect metrics to confirm the right instance is used.
8. When renaming a client, method, or resolver, update the configuration keys and re-verify at runtime.

Accurately mapping generated names to Resilience4j configuration keys ensures every OpenFeign method receives the intended Circuit Breaker policy. Using a stable resolver, understanding alphanumeric rules, and verifying IDs through logs or metrics prevents silent misconfigurations and lets operations teams tune sliding windows, failure thresholds, and recovery times per dependency call.
