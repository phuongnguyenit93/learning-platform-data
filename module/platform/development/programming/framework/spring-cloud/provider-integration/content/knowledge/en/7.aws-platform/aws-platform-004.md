# AWS CLI Profiles, AWS IAM Identity Center, and Local Development

## 1. Context and Objectives

A Spring Boot application integrating Amazon S3, Amazon SQS, or AWS Secrets Manager is typically developed on a personal machine, tested in a dedicated environment, and deployed with an IAM role on AWS. On a developer machine, the application must know **which AWS identity it is using**, **which account it belongs to**, **which region it targets**, and **which permissions have been granted**. Handling these values by copying access keys into `application.yml` dramatically increases the risk of leaking secrets and accidentally accessing production.

In the **AWS Platform** chapter of the **SPRING_CLOUD_PROVIDER_INTEGRATION** module, this lesson guides local development for Spring Boot applications using AWS managed services. It is also part of a broader objective: learning how to configure identity and permissions, access storage/messaging/data, protect secrets, perform integration testing, and compare equivalent mechanisms on Azure and Google Cloud.

The focus is on three components:

- **AWS CLI profile:** a named configuration that selects the account, credential source, region, and settings when running AWS CLI commands or SDK applications.
- **AWS IAM Identity Center:** a platform that grants AWS access to users and groups; supports centralized sign-in to obtain temporary credentials for development.
- **AWS SDK for Java v2 / AWSpring:** the application layer that reads profiles and credentials through the provider chain, then exercises real IAM permissions when calling S3, SQS, STS, and other AWS services.

After this lesson, you will be able to set up local profiles with AWS CLI v2; sign in to IAM Identity Center; inspect the principal and region; run Spring Boot with a dev profile; handle expired tokens, environment credential conflicts, and missing SDK SSO module errors; and structure tests without depending on production accounts.

> **Scope:** Examples focus on AWS CLI **v2** and AWS SDK for Java **v2**, commonly used with Spring Cloud AWS 3.x across compatible Spring Boot version sets. Commands, properties, and token lifecycle details may vary by release; for real deployments, consult documentation for your chosen versions. URLs, account IDs, permission sets, buckets, and queues below are all illustrative values.

## 2. From Human User to AWS Resource Access

Distinguish five concepts that are often conflated:

| Concept | Example | Meaning |
| --- | --- | --- |
| Organization user | `developer@example.com` | Human signing in through an identity system; not an access key |
| AWS IAM Identity Center | Company's central sign-in portal | Authenticates users and authorizes access to assigned AWS accounts/permission sets |
| Permission set | `DeveloperReadOnly` | Permission bundle Identity Center uses to provision an appropriate IAM role in the target account |
| AWS CLI profile | `dev-sandbox` | Local configuration pointing to account, permission set, SSO session, region, and credential source |
| Temporary AWS credentials | Access key ID + secret access key + expiring session token | Material the SDK uses to sign requests to AWS APIs |

A **profile is not an IAM principal**. A profile only tells the CLI/SDK how to obtain credentials, choose an account/permissions, and pick a region. The actual principal seen by AWS is usually a session of an IAM role in the target account. What permissions that role session holds depends on policies, resource policies, SCPs, permission boundaries, KMS policies, and other conditions.

For example, the same person might be granted by Identity Center:

- `dev-sandbox` → test account, permission set allowing S3 uploads and SQS sends.
- `prod-readonly` → production account, permission set allowing read/observe operations only.

Profile names are chosen by the developer; a profile name **does not create an IAM policy**. The organization must assign account access and permission sets before a developer can sign in and use them.

~~~mermaid
flowchart TD
    U["Developer"] --> I["IAM Identity Center / organization"]
    I --> A["Assigned account"]
    A --> P["Permission set"]
    U --> C["AWS CLI v2: aws sso login"]
    C --> T["SSO session and local token cache"]
    T --> D["CLI / SDK Java v2"]
    P -. "Grants permissions via account role" .-> R["Temporary AWS credentials"]
    D --> R
    R --> API["S3 / SQS / STS / Secrets Manager"]
    API --> IAM["AWS checks IAM and resource policy"]
~~~

The diagram illustrates the conceptual flow. When the SDK uses an SSO profile, it can use the SSO token generated by the CLI to obtain temporary AWS credentials; refresh behavior depends on the profile type, SDK, and whether the session remains valid.

## 3. Where Are AWS CLI Profiles Stored?

The AWS CLI and AWS SDK typically look for shared configuration in the `.aws` directory of the current OS user account:

| Operating system | Typical directory | Files |
| --- | --- | --- |
| Linux/macOS | `~/.aws/` | `config`, `credentials` |
| Windows | `C:\Users\<user>\.aws\` | `config`, `credentials` |

Paths can be overridden using the `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` environment variables. These overrides are helpful when running tests or containers, but pointing to the wrong path prevents the CLI/SDK from seeing created profiles.

### 3.1. The `config` File

The `~/.aws/config` file usually holds region, output format, and access configuration such as SSO sessions or assume-role settings:

~~~ini
[profile dev-sandbox]
region = ap-southeast-1
output = json

[profile prod-readonly]
region = ap-southeast-1
output = json
~~~

Profile names are declared as `[profile <name>]` in `config`; the default profile is written as `[default]`.

A profile containing only `region` does **not necessarily provide credentials**. It can pair with a credential source from environment variables or another provider, whereas using Identity Center requires full SSO configuration.

### 3.2. The `credentials` File

The `~/.aws/credentials` file is primarily for credential entries stored under a profile name, using sections like `[dev-sandbox]` instead of `[profile dev-sandbox]`. In traditional setups, contents may include an access key ID and secret key. With temporary credentials, a session token is also included.

You do not need and **should not** copy access keys into `credentials` when your project already uses IAM Identity Center. Modern SSO profiles are configured in `config`; the CLI/SDK retrieves temporary credentials via the SSO session and cache.

Never commit `config`/`credentials` files containing sensitive information into a repository, paste them into tickets, or copy the SSO cache into a Docker image. Cached tokens are also sensitive material requiring protection, even though they are not static secret keys.

### 3.3. Inspecting the Profile List

After installing **AWS CLI v2**, you can check:

~~~bash
aws --version
aws configure list-profiles
aws configure list --profile dev-sandbox
aws configure get region --profile dev-sandbox
~~~

`aws configure list --profile ...` displays configuration values and their sources, though in some setups output may expose partial credential info. Run only in controlled terminals and avoid pasting raw output into public issues or chats.

Reading configuration commands **does not guarantee** the profile is logged into Identity Center or has permission to access services.

## 4. What Role Does IAM Identity Center Play in Local Development?

**AWS IAM Identity Center** (formerly AWS Single Sign-On, often abbreviated SSO) integrates with an organization's identity provider, manages users/groups, and assigns AWS account access via permission sets.

An administrator typically provides a developer with:

1. The **Start URL or issuer URL** of the IAM Identity Center instance, depending on the AWS CLI capabilities in use.
2. The **Identity Center region** (the region of the IAM Identity Center/OIDC service), which can **differ** from the S3/SQS region accessed by the application.
3. The list of assigned **AWS accounts**.
4. The corresponding **Permission set** in each account, e.g. `DeveloperReadOnly` or `DeveloperSandbox`.
5. Sign-in, MFA, and session duration guidelines under organizational policy.

Administrators control permissions. Developers cannot arbitrarily pick an unauthorized permission set or grant themselves permissions by editing a profile file.

### 4.1. Distinguishing Three Commonly Confused Values

| Value | Example | What is it used for? |
| --- | --- | --- |
| `sso_region` | `us-east-1` | Connecting to IAM Identity Center/OIDC sign-in APIs |
| `sso_account_id` | `111122223333` | The AWS account where role credentials will be issued |
| `region` in profile | `ap-southeast-1` | Default region when calling AWS services such as S3/SQS |

`sso_region` does not have to match `region`. Choosing the wrong `sso_region` breaks SSO authentication/endpoints; choosing the wrong `region` makes API calls look for queues, buckets, or tables in the wrong region. Both must be verified independently.

### 4.2. Permission Sets and IAM Roles

A permission set is a configuration managed by IAM Identity Center. When assigning a permission set to a user/group in an AWS account, IAM Identity Center provisions a managed IAM role inside that account. After sign-in, the CLI/SDK obtains **temporary role credentials** based on the chosen account and permission set.

For example, someone holding `DeveloperReadOnly` in production cannot send SQS messages if the policy only allows reads. A successful SSO login does not imply `sqs:SendMessage` is authorized.

## 5. Setting Up an SSO Profile with AWS CLI v2

### 5.1. Prerequisites Before Configuration

You need AWS CLI v2 installed, the IAM Identity Center URL, the IAM Identity Center region, and account/permission set assignments. Your browser/device login may require MFA. Never create long-lived access keys as a workaround for organizational sign-in.

Typical setup command:

~~~bash
aws configure sso --profile dev-sandbox
~~~

The wizard may prompt for an SSO session name, Start URL or issuer URL, SSO region, scope, account, role/permission set, default AWS region, and output format. Select the **sandbox** account carefully before accepting. With newer CLI versions, the wizard usually creates a `[sso-session ...]` section and links it to the profile.

Example configuration generated or reviewed in `~/.aws/config`:

~~~ini
[sso-session team-sso]
sso_start_url = https://example.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access

[profile dev-sandbox]
sso_session = team-sso
sso_account_id = 111122223333
sso_role_name = DeveloperSandbox
region = ap-southeast-1
output = json
~~~

This is an **illustrative example**: the domain, account ID, and permission set name do not represent a real account. `sso_role_name` must match the permission actually granted by Identity Center; it is not something you can arbitrarily edit to gain privileges.

You can add a read-only production profile as well:

~~~ini
[profile prod-readonly]
sso_session = team-sso
sso_account_id = 444455556666
sso_role_name = DeveloperReadOnly
region = ap-southeast-1
output = json
~~~

Both profiles reference the same `sso-session` if they share the same SSO instance, yet point to **different AWS accounts or permission sets**. Verify exact permissions before use; a self-chosen name like `prod-readonly` is not a security control. IAM policies and provisioned permissions determine write/delete capabilities.

### 5.2. Signing In to IAM Identity Center

~~~bash
aws sso login --profile dev-sandbox
~~~

The AWS CLI opens or guides the login flow. After successful authentication, the CLI stores the necessary tokens in the local cache for working with the profile. Depending on version and session state, the login command may reuse a still-valid session.

Next, verify your identity:

~~~bash
aws sts get-caller-identity --profile dev-sandbox
~~~

The response includes `UserId`, `Account`, and `Arn`. Match `Account` against the assigned sandbox account and `Arn` against the expected principal/role. Never trust the profile name alone.

**Note:** `sts get-caller-identity` confirms the real principal, but it does not prove S3/SQS or KMS permissions. Only testing operations on specific test resources validates the permissions and policies for those actions.

### 5.3. Signing Out and Session Expiration

~~~bash
aws sso logout
~~~

The logout command clears cached SSO credentials/tokens according to the CLI's supported scope; do not assume logout always affects only one profile. Review your active workflow if you use multiple SSO sessions.

When a session or token expires, CLI commands may prompt you to re-run `aws sso login --profile dev-sandbox`. Token, cache, and credential refresh capabilities depend on **SSO session configuration** and tool versions. The SDK refreshing temporary AWS role credentials does not mean the human user stays logged in forever.

Never resolve an expired token by temporarily copying access keys into source code. Sign in again and check the system clock, connectivity to Identity Center, and account/permission set assignments.

## 6. Selecting a Profile When Using the AWS CLI

There are two common ways: per command or via environment variables.

### 6.1. Specifying Per Command

~~~bash
aws sts get-caller-identity --profile dev-sandbox
aws s3 ls --profile dev-sandbox --region ap-southeast-1
~~~

Adding `--profile` makes clear which profile is used for **that specific CLI command**. For example, `aws s3 ls` also requires the role to hold appropriate read/list permissions; if denied, inspect IAM and policies rather than assuming SSO login failed.

A good habit is verifying the account with STS before any write, delete, resource creation, or policy change.

### 6.2. Setting a Default Profile for the Current Terminal

Linux/macOS with Bash:

~~~bash
export AWS_PROFILE=dev-sandbox
export AWS_REGION=ap-southeast-1

aws sts get-caller-identity
~~~

Windows PowerShell:

~~~powershell
$env:AWS_PROFILE = "dev-sandbox"
$env:AWS_REGION = "ap-southeast-1"

aws sts get-caller-identity
~~~

These settings apply to the **current shell process and its child processes**. An IDE, Gradle daemon, separate terminal, or container may inherit a different environment. In particular, if an IDE was launched before environment variables were set, applications started from the IDE might not see the new values.

For AWS SDK for Java v2, `AWS_PROFILE` selects a profile from shared configuration when the provider chain reaches the profile provider. **It does not necessarily override credentials from Java system properties or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`**, which are normally checked before profiles. Therefore, verify the application's actual runtime identity rather than assuming `AWS_PROFILE` always controls all credentials.

### 6.3. Do Not Make Production the Default Profile

If you frequently switch between dev and prod, do not put production write permissions into the `default` profile. Use clearly named, least-privilege profiles, and ensure resource-mutating scripts run only after confirming the target account and region.

Commands like `aws configure list-profiles` and `aws sts get-caller-identity --profile ...` help verify context switches; however, stronger guardrails remain IAM policies, read-only roles, sandbox accounts, and environment-scoped permissions.

## 7. How Does AWS SDK for Java v2 Use SSO Profiles?

Spring Cloud AWS 3.x typically uses **AWS SDK for Java v2** underneath. The SDK can read shared configuration files created by the AWS CLI and use SSO profiles to obtain temporary credentials. The SDK does not "log in on your behalf" via a browser the way a developer interacts with `aws sso login`; it generally requires an already-logged-in SSO session or an SDK-supported refresh mechanism.

### 7.1. ProfileCredentialsProvider

If you want to invoke the SDK with a specific profile:

~~~java
import software.amazon.awssdk.auth.credentials.ProfileCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;

public final class S3DevClientFactory {
    public static S3Client create() {
        return S3Client.builder()
                .credentialsProvider(
                        ProfileCredentialsProvider.create("dev-sandbox"))
                .region(Region.AP_SOUTHEAST_1)
                .build();
    }
}
~~~

`ProfileCredentialsProvider` processes profile settings and can delegate to other providers depending on profile type (SSO, assume role, credential process, etc.). It **does not grant IAM permissions**. The snippet hard-codes the `dev-sandbox` profile, so it is only appropriate when you intentionally lock a client to a dev environment; **never hard-code this profile in shared deployable code**.

In production, you generally do not want clients depending on a developer's local profile file; let workload identity/roles and the default provider chain handle credentials.

### 7.2. DefaultCredentialsProvider and AWS_PROFILE

When an application does not configure a custom credential provider, AWS SDK v2 uses the default chain in this order:

1. Java system properties containing AWS access key/secret.
2. Environment variables containing AWS access key/secret.
3. Web identity token and role ARN.
4. Shared AWS profile.
5. Container credentials (e.g., ECS task role).
6. EC2 instance profile via IMDS.

Consequently, in a local environment **without** credentials from higher-priority sources, `AWS_PROFILE=dev-sandbox` steers the chain to the SSO profile. Yet if an ECS container carries static environment keys, the SDK can pick those keys ahead of the task role. That is why long-lived keys should be kept out of runtime environments.

Example of an SDK client using the default chain:

~~~java
import software.amazon.awssdk.services.s3.S3Client;

try (S3Client s3 = S3Client.create()) {
    // May use credentials from AWS_PROFILE if no higher-priority source exists
    // and region is resolved by the region provider chain.
}
~~~

The client also needs a region. With AWS SDK for Java v2, the typical region chain checks the `aws.region` system property, `AWS_REGION`, the region in the shared profile, and then EC2 metadata. If the builder or AWSpring already set the region explicitly, the region chain will not govern that client's region.

### 7.3. Required SDK Modules for SSO Profiles

In Java v2 applications, SSO profiles may require the **`sso`** and **`ssooidc`** SDK modules on the runtime classpath, depending on integration and release. Some setups also assume the **`sts`** module when profiles require assume-role/STS. If the SDK reports it cannot load SSO credentials or is missing an implementation, check the BOM version and resolved dependencies.

Illustrative Maven declaration:

~~~xml
<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>sso</artifactId>
    </dependency>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>ssooidc</artifactId>
    </dependency>
</dependencies>
~~~

The example assumes SDK versions are already managed by the project's **BOM/dependency management**. Otherwise, import the proper SDK BOM or declare an approved consistent version. Do not put mismatched versions across SDK modules just to silence compile errors. If calling other APIs directly, add the corresponding modules (e.g., `s3`, `sqs`, `sts`).

**Distinguishing three errors**:

| Message or symptom | Primary issue layer | First check |
| --- | --- | --- |
| CLI asks to run `aws sso login` | Local SSO session/token | Profile session, login state, token cache |
| Java reports missing SSO provider/module | Runtime dependencies | `sso`/`ssooidc` and resolved SDK versions |
| Java receives `AccessDenied` from S3/SQS | IAM/resource policies | Principal/role, action, ARN, KMS, and account |

### 7.4. AWSpring and Spring Boot

In a Spring Boot application using AWSpring, you can keep application code independent of local profile names. For instance, once the S3 starter is configured:

~~~java
import org.springframework.stereotype.Service;
import software.amazon.awssdk.services.s3.S3Client;

@Service
public class DocumentMetadataReader {
    private final S3Client s3;

    public DocumentMetadataReader(S3Client s3) {
        this.s3 = s3;
    }

    public long size(String bucket, String key) {
        return s3.headObject(req -> req
                .bucket(bucket)
                .key(key))
            .contentLength();
    }
}
~~~

The snippet assumes an `S3Client` bean configured by AWSpring or custom Spring configuration. Locally, supply `AWS_PROFILE=dev-sandbox` and a region; on ECS/EKS/EC2, supply the workload's role. Check whether your AWSpring configuration overrides default credentials or region handling.

Example configuration specifying only region and bucket name:

~~~yaml
spring:
  cloud:
    aws:
      region:
        static: ${AWS_REGION}

app:
  storage:
    bucket: ${APP_DOCUMENT_BUCKET}
~~~

`APP_DOCUMENT_BUCKET` must point to the **right environment's** bucket. The YAML snippet contains no access keys or session tokens; local runs supply identity via an SSO profile, production via a role. If a build defines a custom client bean with `.credentialsProvider(...)`, that custom configuration may bypass the SDK's default profile selection.

## 8. Hands-On: Running Spring Boot Locally with SSO

Suppose a **Document Service** receives requests to upload receipts to S3 and then sends an event to SQS. The team provides a sandbox AWS account and a dedicated permission set for development; the application uses Spring Boot + AWSpring.

### Step 1: Prepare the Dev Profile

~~~bash
aws configure sso --profile dev-sandbox
aws sso login --profile dev-sandbox
aws sts get-caller-identity --profile dev-sandbox
~~~

Match STS's `Account` field against the sandbox account assigned by your organization. If the account is wrong, **stop any write operations** and inspect profile/session/credential overrides.

### Step 2: Verify the Region Separately

~~~bash
aws configure get region --profile dev-sandbox
~~~

If resources reside in Singapore, the example's default region is `ap-southeast-1`. The S3/SQS region and the SSO login region can differ; do not automatically assume `sso_region` is the AWS service region.

### Step 3: Open a Terminal with the Right Profile and Region

Bash:

~~~bash
export AWS_PROFILE=dev-sandbox
export AWS_REGION=ap-southeast-1
export APP_DOCUMENT_BUCKET=example-dev-documents
export APP_EVENTS_QUEUE=example-dev-events
~~~

PowerShell:

~~~powershell
$env:AWS_PROFILE = "dev-sandbox"
$env:AWS_REGION = "ap-southeast-1"
$env:APP_DOCUMENT_BUCKET = "example-dev-documents"
$env:APP_EVENTS_QUEUE = "example-dev-events"
~~~

The bucket/queue names above are placeholders; replace them with **already provisioned** sandbox resources, and do not recreate resources using production scripts. If the system expects a queue URL rather than a queue name, supply the exact format required by the API/SDK.

### Step 4: Run the Application via IDE or Build Tool

Start the application from **the same terminal** where the environment variables were exported, or configure your IDE Run Configuration with `AWS_PROFILE`, `AWS_REGION`, and resource name variables. If the IDE was launched from the GUI and does not inherit terminal environment variables, set the variables in the run configuration.

The application needs the AWSpring starters and SDK SSO modules compatible with your version. A successful `aws sso login` does not guarantee the JVM picks up the profile; the JVM might have a different `HOME`, a different `AWS_CONFIG_FILE`, or lack the needed SDK modules.

### Step 5: Test Against Constrained Resources

With a dev role granted read access to the sandbox bucket, you can run a **low-impact** command to check, for example:

~~~bash
aws s3 ls s3://example-dev-documents --profile dev-sandbox --region ap-southeast-1
~~~

This command requires the resource to exist and appropriate permissions to be present. If the account allows `s3:PutObject` without `s3:ListBucket`, `aws s3 ls` will be denied even though uploading a specific object succeeds. Test the exact operation to draw accurate permission conclusions.

For operations with side effects such as `PutObject` or `SendMessage`, use dedicated test bucket prefixes/sandbox queues, fake data, and proper idempotency. Never use real customer data locally.

## 9. Troubleshooting Common Issues

### 9.1. Login Succeeds, Yet the JVM Still Reports Missing Credentials

Check in order:

1. Are the CLI and Java application running under the same OS user, sharing the same `~/.aws/config`, SSO cache, and `HOME`?
2. Is the JVM picking up the right `AWS_PROFILE` or `aws.profile`; is a custom `ProfileCredentialsProvider`/`DefaultCredentialsProvider` being used?
3. Are `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` or Java system properties overriding the profile?
4. Are SDK v2 `sso`/`ssooidc` on the runtime classpath with consistent SDK versions?
5. Is the SSO session still valid, is the user assigned to the account/permission set, and is the token cache readable?

Never print credential environment variables to the console to debug; confirm only **presence/absence** and configuration source to avoid exposing sensitive data.

### 9.2. SSO Session Expired or Token Cannot Refresh

Symptoms include messages about an invalid or expired SSO token, inability to fetch role credentials, or Identity Center call failures. Re-run:

~~~bash
aws sso login --profile dev-sandbox
aws sts get-caller-identity --profile dev-sandbox
~~~

If it still fails, check the SSO session URL/region, network connectivity, MFA, and account/permission set access. Check system clock accuracy if seeing token/signature errors; never copy token caches across machines.

### 9.3. Right Profile Selected, Wrong Account Accessed

A profile may be named `dev-sandbox`, yet the SDK uses higher-priority environment credentials, or the profile was edited to point to another account. In Java applications, `DefaultCredentialsProvider` follows its own source precedence; the CLI `--profile` flag does not change the provider logic configured for the JVM.

**How to verify:** call `GetCallerIdentity` using the application's actual client/credentials before running mutating operations. If you need a quick check in a local Java utility, build an `StsClient` with `DefaultCredentialsProvider`:

~~~java
import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.sts.StsClient;

public class LocalIdentityCheck {
    public static void main(String[] args) {
        try (StsClient sts = StsClient.builder()
                .credentialsProvider(DefaultCredentialsProvider.create())
                .region(Region.AP_SOUTHEAST_1)
                .build()) {
            var caller = sts.getCallerIdentity();
            System.out.println("AWS Account: " + caller.account());
            System.out.println("Principal ARN: " + caller.arn());
        }
    }
}
~~~

Note that the utility needs `software.amazon.awssdk:sts` on the classpath. ARNs and account IDs may also be internal information, so keep output out of public channels. `GetCallerIdentity` proves the active identity, not directly which child provider in the chain supplied the credentials.

### 9.4. `AccessDenied` Even After STS Confirms the Right Account

Having the right account **does not guarantee** the permission set allows a specific operation. Check:

- The permission set assigned to the account and user/group.
- The IAM policy provisioned from the permission set.
- The bucket/object, queue, or secret ARN and requested action.
- Resource policies, KMS key policies, organization SCPs, permission boundaries, and condition policies.
- The target resource's region or endpoint.

When calling S3 `PutObject` with SSE-KMS, bucket permissions might be fine while KMS policy/permissions are insufficient. Never fix this by granting broad permissions like `AdministratorAccess`; identify the exact denied API and ARN.

### 9.5. Wrong Region or Resource Not Found

Check the Java SDK region precedence: region set directly on builder/AWSpring; then `aws.region`, `AWS_REGION`, region in the shared profile, and EC2 metadata. In the CLI, command flags like `--region` override the profile region.

For example, the SSO profile specifies `region = ap-southeast-1`, while the IDE sets `AWS_REGION=us-east-1`. The Java client uses the environment region unless overridden at a higher precedence; an SQS queue in Singapore may appear missing or unreachable.

### 9.6. Container or IDE Cannot See Host Profile Files

Docker containers have their own filesystem and environment; `~/.aws` on the host does not appear inside a container automatically. When local containers are needed:

- Mount only the required config/cache files **read-only** in controlled development environments.
- Set the profile/region for the container process.
- Avoid baking credentials, tokens, or the entire `.aws` directory into images.
- Consider using a secure credential endpoint or organization-supported dev identity mechanism instead of distributing secrets.
- Never reuse this local mount pattern for ECS/EKS production; production should use workload roles.

Protect filesystem permissions on the SSO cache directory on both host and container. The cache is sensitive credential material; keep it out of images, artifacts, and CI logs.

## 10. Local Development Differs from CI and Production

IAM Identity Center is built for **interactive human sign-in**. A production application or CI pipeline should not require a human to open a browser and enter MFA on every startup.

| Environment | Typical identity mechanism | What to ensure |
| --- | --- | --- |
| Developer laptop | AWS CLI v2 + IAM Identity Center profile | Sandbox account, least privilege, clear login/refresh |
| Local integration tests | SDK client with LocalStack endpoint and fake credentials, or dedicated test env | Never hit real AWS unintentionally |
| CI outside AWS | OIDC federation/STS assume role, temporary credentials | Trust policy restricted to repo/branch/job, test resources |
| ECS/Fargate | ECS **task role** | Distinguish task role from task execution role |
| EKS | IRSA or EKS Pod Identity depending on architecture | Never inject static credentials into pods |
| EC2 | Instance profile | Appropriate IMDS and role permissions |

Environment transition architecture example:

~~~mermaid
flowchart TD
    CODE["Same Spring Boot code"] --> LOCAL["Local"]
    CODE --> TEST["Integration test"]
    CODE --> PROD["AWS workload"]
    LOCAL --> SSO["AWS_PROFILE -> SSO profile"]
    TEST --> LS["LocalStack + test credentials"]
    PROD --> IAM["ECS/EKS/EC2 role -> temporary credentials"]
    SSO --> API["AWS SDK Java v2"]
    LS --> API
    IAM --> API
    API --> AWS["S3 / SQS / Secrets Manager"]
~~~

The diagram highlights **the same business code** receiving identities from different environments. The goal is zero `if (prod) useHardcodedKey()` branches in the application.

### 10.1. Environment-Specific Spring Boot Configuration

A shared configuration may contain only resource identifiers and region:

~~~yaml
spring:
  cloud:
    aws:
      region:
        static: ${AWS_REGION}

app:
  aws:
    bucket: ${APP_DOCUMENT_BUCKET}
    queue: ${APP_EVENTS_QUEUE}
~~~

These variables can be injected by the IDE, pipeline, or deployment manifest. Locally, `AWS_PROFILE` picks the SSO profile; in production, avoid setting `AWS_PROFILE` to developer configs. If custom AWSpring credential beans exist, verify they remain compatible with workload roles and the default provider chain.

### 10.2. LocalStack Testing Without SSO

In an integration test using an emulator, configure **endpoint override**, **fixed region**, and **fake credentials** on the SDK client strictly within test scope. For example:

~~~java
import java.net.URI;
import software.amazon.awssdk.auth.credentials.AwsBasicCredentials;
import software.amazon.awssdk.auth.credentials.StaticCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.S3Configuration;

public final class LocalTestS3 {
    public static S3Client client(URI localEndpoint) {
        return S3Client.builder()
                .endpointOverride(localEndpoint)
                .region(Region.US_EAST_1)
                .credentialsProvider(StaticCredentialsProvider.create(
                        AwsBasicCredentials.create("test", "test")))
                .serviceConfiguration(S3Configuration.builder()
                        .pathStyleAccessEnabled(true)
                        .build())
                .build();
    }
}
~~~

These are strictly fake credentials for local emulation; never apply them at runtime against real AWS. LocalStack verifies SDK wiring, serialization, and basic operations, yet **cannot prove** IAM roles, Identity Center, KMS, and all production behaviors are right. Follow up with a smoke test on a restricted testing AWS account.

## 11. Security When Using Profiles and SSO

### 11.1. Least Privilege for Developers

Sandbox accounts should isolate resources, restrict regions/quotas, and grant only the operations required for the work. If a developer only needs to read S3 metadata, do not grant bucket deletion; if they need to send messages to a test queue, grant `sqs:SendMessage` only on that test queue's ARN.

Remember that S3 object and bucket permissions differ: for instance, `s3:PutObject` generally applies to object ARNs, while `s3:ListBucket` applies to bucket ARNs. An application can upload successfully while `aws s3 ls` is denied for lacking list permission.

### 11.2. Protecting Local Configuration

- Use MFA and organizational security controls when signing in to Identity Center.
- Restrict `~/.aws` and SSO token cache permissions to the owning user; never share caches across developers.
- Never commit access keys, tokens, caches, sensitive configs, STS logs, or diagnostic outputs containing internal details.
- Never store long-lived access keys in `application.yml`, committed `.env` files, Dockerfiles, image layers, or test fixtures.
- Use separate profiles for dev and read-only prod; always verify the AWS account before mutating commands.
- When a token/credential leak is suspected, follow your organization's incident procedure and revoke/sign out sessions using available controls.

### 11.3. Guardrails for Write Operations

Across both applications and the CLI, before calling `PutObject`, `DeleteMessage`, updating secrets, or modifying resources, enforce automated checks:

1. The actual principal from STS must belong to a dev/test account allowlist.
2. The region must belong to the environment's permitted regions.
3. Resource IDs/ARNs must follow test-environment naming prefixes/tags.
4. Destructive or policy-changing operations must require elevated privileges and clear auditing.
5. Never use real customer data in local experiments.

**Profile names are only conventions**, not substitutes for server-side and IAM guardrails. A profile named `sandbox` can still be edited to point at production.

## 12. Connections to Azure and Google Cloud

In multi-cloud design, the core requirement is the same: applications need an environment-appropriate identity and permissions on specific resources. However, sign-in workflows, token caching, default credential lookup, and location models differ.

| Need | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Interactive developer sign-in | AWS CLI v2 + IAM Identity Center profile | Azure CLI or suitable developer identity tooling | Google Cloud CLI and corresponding ADC/local auth |
| SDK default credential lookup | `DefaultCredentialsProvider` and shared AWS profiles | Credential chain mechanisms such as `DefaultAzureCredential` | Application Default Credentials (ADC) |
| Workload permissions | IAM task/instance/service role or web identity | Managed Identity and RBAC/resource access | Service account and IAM/workload identity |
| Resource location | AWS region, service endpoint/ARN | Resource endpoint, subscription, region | Project ID, location, and service endpoint |

Do not copy the AWS SDK provider chain order verbatim onto Azure or GCP. For example, `AWS_PROFILE` controls shared AWS profiles, not generic settings for Google Cloud Storage or Azure Blob Storage. For multi-cloud adapters, business code can define shared interfaces while keeping identity, permissions, and client configuration tailored to each provider.

## 13. Guided Practice Exercises

### Exercise 1. Create Two Profiles and Verify Identity

**Assumption:** your organization has granted Identity Center access to both a test account and a read-only prod account.

1. Use `aws configure sso --profile dev-sandbox` to set up the dev profile.
2. Sign in with `aws sso login --profile dev-sandbox`.
3. Run `aws sts get-caller-identity --profile dev-sandbox` and inspect the account ID/ARN.
4. Create `prod-readonly` for the production account with a read-only permission set.
5. Explain how to prevent the application from accidentally writing to production if a profile is misconfigured.

**Expected outcome:** clearly distinguish successful login, selected account, granted permission set, and AWS resource region.

### Exercise 2. Analyze Credential Precedence

Consider a local machine with:

~~~text
AWS_PROFILE=dev-sandbox
AWS_REGION=ap-southeast-1

AWS_ACCESS_KEY_ID=<old-credential>
AWS_SECRET_ACCESS_KEY=<old-credential>
~~~

The Java application uses `DefaultCredentialsProvider` yet S3 calls are denied. Explain why running `aws sso login` does not necessarily fix the error. Propose steps to confirm the credential source and account, and remove the old keys from the environment without printing secrets.

**Hint:** the SDK can pick up environment credentials before reaching the shared profile. Verify the client's identity, inspect env/system properties, then use the right SSO profile. Avoid writing new keys into the application to "override" the error.

### Exercise 3. Debug Differences Between CLI and Spring Boot

The CLI works:

~~~bash
aws sts get-caller-identity --profile dev-sandbox
~~~

Yet Spring Boot launched from the IDE cannot obtain S3 credentials. Build a checklist covering: IDE environment, `AWS_PROFILE`, user home, shared config path, SSO cache, SDK `sso`/`ssooidc` modules, AWSpring beans, client region, and IAM errors.

Explain why testing the CLI again and testing Java inside **the same process environment** are two different checks.

### Exercise 4. Design a Local–CI–Production Workflow

A team builds a Spring Boot service that uploads documents to S3 and publishes SQS events. Design:

- Local developers using Identity Center with a sandbox profile.
- CI using OIDC/STS temporary credentials and a test account, without needing a browser.
- Production ECS using a task role and configured region, without developer profiles.
- Unit tests using fake adapters; integration tests emulating S3/SQS with test credentials; smoke tests using a dedicated IAM role.

Identify which identity/account, region, bucket/queue, IAM actions, and KMS conditions each environment must check. Describe how the application should refuse to start if a test environment points to the production account.

### Exercise 5. Reasoning Questions

1. Does a successful `aws sso login --profile dev-sandbox` prove the Java application will load credentials from `dev-sandbox`? **No**; the provider chain has higher-priority sources and custom bean configurations.
2. Does `sso_region=us-east-1` force `region=us-east-1`? **No**; sign-in region and service region are independent.
3. If `GetCallerIdentity` returns the sandbox account yet SQS `SendMessage` gets `AccessDenied`, what should be checked? **Permission set/IAM, queue policy, action, ARN, region, KMS, and policy conditions**.
4. Should `~/.aws/sso/cache` be copied into a CI Docker image to avoid login? **No**; CI should use workload federation/temporary roles with restricted permissions.
5. When a local token expires, should static access keys be added to `application.yml`? **No**; re-authenticate with Identity Center or resolve the session/provider issue properly.

## 14. Summary

An **AWS CLI profile** configures how credentials, account/role, and region are located; **IAM Identity Center** is the organizational mechanism for human sign-in and account access via permission sets; **AWS SDK for Java v2 and AWSpring** use the resolved credentials when Spring Boot calls AWS services. Successful sign-in and a well-named profile are not enough: verify the STS principal, region, policies, and target resources.

The recommended model for local development is **AWS CLI v2 + IAM Identity Center + sandbox profile + temporary credentials**; CI and production should use dedicated roles/workload identities. This design provides a safe foundation for upcoming lessons on storage, messaging, data, secrets, and integration testing on AWS, while supporting comparison with Azure and Google Cloud identity patterns.
