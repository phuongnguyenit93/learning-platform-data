# Limiting metric label cardinality and observability data costs

## 1. Context and objectives

In the **SPRING_CLOUD_PROVIDER_INTEGRATION** module, we practice integrating Spring Boot with managed services from **AWS, Azure, and Google Cloud** using the corresponding Spring Cloud libraries and SDKs. Once metrics, logs, and traces flow into an observability platform, a common problem emerges after real traffic arrives: time-series counts and data volume grow faster than expected, driving up storage, ingestion, and query costs.

For example, a developer adds a `customerId` tag to the `http.server.requests` metric to view per-customer latency. In test environments with only a few customers, dashboards run fine. In production with 80,000 customers, each customer spawns distinct time series across method, URI, status, and instance. If the metric also publishes histogram buckets, series counts can reach millions or more.

This lesson explains how to limit cardinality and control observability data costs when Spring Boot ships telemetry to Prometheus, Amazon CloudWatch, Azure Monitor, or Google Cloud Monitoring.

After this lesson, you will be able to:

- Distinguish metric name, label, dimension, time series, and sample.
- Estimate time-series count from label combinations and histogram buckets.
- Design label sets with bounded, stable values.
- Use Micrometer `MeterFilter` to drop or cap meters/tags.
- Control cardinality across Prometheus, CloudWatch, Azure Monitor, and Google Cloud Monitoring.
- Route the right data to metrics, logs, and traces.
- Reduce costs using aggregation, sampling, retention, filtering, and batching.
- Establish a cardinality budget and verify it before production rollout.

## 2. What is cardinality?

In a metrics system, **cardinality** is the number of distinct values a label can take, or the number of distinct time series generated by combinations of labels.

A metric typically consists of:

- **Metric name:** the quantity being measured, e.g., `http.server.requests`.
- **Label/tag/dimension:** an attribute used for grouping, e.g., `method`, `status`, `provider`.
- **Time series:** one metric name paired with a specific set of label values.
- **Sample:** a single value recorded at a point in time for a time series.

Example:

~~~text
http_server_requests_seconds_count{
  method="GET",
  uri="/documents",
  status="200",
  instance="api-1"
}
~~~

If `method` has 4 values, `uri` has 20 values, `status` has 5 values, and `instance` has 6 values, the maximum number of combinations is:

\[
4 \times 20 \times 5 \times 6 = 12,000
\]

This is a theoretical upper bound. The actual active time-series count depends on which combinations actually emit data.

**Cardinality is not sample count.** A single time series scraped every 15 seconds for a day generates 5,760 samples, yet its cardinality remains one time series. High cardinality increases the number of series to track; high scrape frequency increases sample/ingestion volume over the same period.

## 3. Why does high cardinality cause problems?

Every time series carries metadata, index entries, state, and stored samples. As series count grows:

- Prometheus needs more RAM and disk to hold head series, indexes, and chunks.
- Metric backends must manage more streams, potentially increasing ingestion and retention bills.
- Dashboards and queries scan more series, slowing down or timing out.
- Alert rules evaluate more alert instances, creating noise and heavier evaluation load.
- Collectors/exporters consume more CPU, memory, and network bandwidth.
- A minor code change can silently create tens of thousands of new series that are easy to miss during review.

Examples of high-cardinality tags:

| Tag | Why it is dangerous | Where it should live |
|---|---|---|
| `user_id` / `customer_id` | Every user can become a distinct value | Access-controlled logs/traces |
| `request_id` | Nearly every request has its own ID | Logs and traces |
| `trace_id` / `span_id` | Virtually unique per trace/span | Trace backend/log correlation |
| `order_id` / `job_id` | Grows unbounded with business volume | Logs/traces |
| `file_name` / `object_key` | Can take millions of values | Logs/traces |
| Full `url` | Paths/queries may contain IDs and parameters | Use route templates |
| `exception_message` | Free-form text that changes continuously | Redacted logs |
| `pod_uid` | Every Pod recreation gets a new UID | Resource metadata; weigh instance labels |

Not every multi-valued dimension is wrong. Some systems genuinely require breakdowns by region or queue. What matters is understanding the multiplicative cost of label combinations, keeping value sets bounded, and adding a dimension only to answer a concrete operational question.

## 4. Calculating time series before adding a tag

For a metric with independent labels, you can estimate:

\[
N_{series} \approx \prod_{i=1}^{n} C_i
\]

Here `C_i` is the expected cardinality of the *i*-th label. This formula is a simple upper bound; unobserved combinations keep the actual series count lower.

Example dependency metric:

| Label | Expected cardinality |
|---|---:|
| `provider`: `aws`, `azure`, `gcp` | 3 |
| `service`: `s3`, `blob`, `pubsub`, `rds`, `sqs` | 5 |
| `operation`: `upload`, `download`, `read`, `write`, `send`, `receive`, `ack`, `query` | 8 |
| `outcome`: `success`, `error`, `timeout` | 3 |
| `region`: 4 deployment regions | 4 |
| **Maximum combinations** | **1,440** |

If this same metric is a classic histogram with 10 finite bucket boundaries, each label set can produce 13 series: 11 bucket series (10 buckets + `+Inf`), plus `_sum` and `_count`.

\[
1,440 \times 13 = 18,720 \text{ time series}
\]

If you add `customer_id` with 10,000 values:

\[
18,720 \times 10,000 = 187,200,000 \text{ time series}
\]

This shows how one seemingly helpful tag can trigger explosive cost growth. Histograms produce many more series than Counters or Gauges with the same label set; native histograms use a different storage model, so do not mechanically apply the classic bucket multiplier to every backend.

### 4.1. Cardinality budget

Before adding a tag, document:

- Metric name and meter type.
- Planned labels.
- Maximum values per label.
- Number of instances/regions/clusters.
- Bucket count if it is a histogram.
- Estimated time-series count.
- The operational question this dimension answers.
- Metric owner and review cadence.

A team might set an internal budget, for instance: at most 500 series per business metric per environment, and at most 5,000 histogram series per service. These are illustrative internal budgets, not default limits of Prometheus or cloud providers.

## 5. Choosing labels with bounded value sets

Good labels describe stable attributes with small value sets:

- `provider`: `aws`, `azure`, `gcp`.
- `operation`: `upload`, `download`, `send_message`, `receive_message`.
- `outcome`: `success`, `error`, `timeout`.
- `error_type`: `throttled`, `timeout`, `authorization`, `not_found`, `server`, `other`.
- `environment`: `dev`, `staging`, `production`.
- `region`: a known list of deployment regions.

Bad labels contain identifiers or free-form text:

- `customer_id=tenant-93821`.
- `request_id=8d9...`.
- `path=/documents/849201/download`.
- `exception_message=Connection reset by peer at 10:15:...`.

To break down HTTP metrics by endpoint, use a route template such as `/documents/{documentId}` instead of the concrete URL `/documents/849201`. To break down errors by exception, normalize into a bounded enum such as `timeout`, `permission_denied`, or `other`.

### 5.1. Normalizing input values

Never pass raw request or SDK data directly into metric tags. Map inputs to a bounded set:

~~~java
public enum Operation {
    UPLOAD,
    DOWNLOAD,
    SEND_MESSAGE,
    RECEIVE_MESSAGE,
    OTHER
}

public static Operation normalizeOperation(String raw) {
    if (raw == null) {
        return Operation.OTHER;
    }

    return switch (raw) {
        case "upload", "put_object" -> Operation.UPLOAD;
        case "download", "get_object" -> Operation.DOWNLOAD;
        case "send", "send_message" -> Operation.SEND_MESSAGE;
        case "receive", "receive_message" -> Operation.RECEIVE_MESSAGE;
        default -> Operation.OTHER;
    };
}
~~~

Metric tags use the enum name or a stable string mapping. Raw values can be written to logs when investigation requires them, after screening for sensitive data.

### 5.2. Never use URLs or resource IDs as labels

For HTTP server metrics, rely on URI templates provided by the framework. Avoid tagging full URLs, query strings, or unnormalized paths. For cloud storage, tag `container` or `bucket` only when the list is small and comparison is genuinely needed; never tag object keys.

For queues, `destination` can be reasonable if the set of queues/topics is fixed. If destinations include tenant names or dynamic queue names, map them to queue categories such as `document-jobs`, `billing-events`, or `other`.

## 6. Micrometer: limiting meters and tags

Micrometer lets you filter meters before a registry records them. `MeterFilter` serves as a useful guardrail to block unwanted meters or cap tag values.

### 6.1. Capping meter count and tag values

Example:

~~~java
import io.micrometer.core.instrument.config.MeterFilter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MetricsCardinalityConfiguration {

    @Bean
    MeterFilter limitCloudMetricTags() {
        return MeterFilter.maximumAllowableTags(
                "cloud.dependency",
                "operation",
                20,
                MeterFilter.deny());
    }

    @Bean
    MeterFilter limitTotalMeters() {
        return MeterFilter.maximumAllowableMetrics(500);
    }
}
~~~

`maximumAllowableTags` caps the number of distinct values for a tag key across meters matching the prefix. Once exceeded, new meters are rejected according to the passed fallback filter—in this example, `MeterFilter.deny()`.

`maximumAllowableMetrics` caps the total number of meter IDs accepted by the registry. This is a last-resort guardrail, not a substitute for good label design. Once hit, new metrics may be dropped silently unless monitored, so test and alert when filters begin rejecting meters.

Note: a global `MeterFilter` applied at the registry level can affect multiple backends in the same application. If you only want to restrict CloudWatch or a specific registry, attach the filter to that target registry using your Micrometer/Spring Boot version's configuration mechanism.

### 6.2. Blocking unnecessary metrics

You can use an allow-list:

~~~java
import io.micrometer.core.instrument.config.MeterFilter;
import java.util.Set;
import org.springframework.context.annotation.Bean;

@Bean
MeterFilter applicationMetricAllowList() {
    Set<String> allowed = Set.of(
            "http.server.requests",
            "jvm.memory.used",
            "jvm.gc.pause",
            "cloud.dependency.duration",
            "cloud.dependency.errors",
            "messaging.process.duration");

    return MeterFilter.denyUnless(
            id -> allowed.contains(id.getName()));
}
~~~

An allow-list must be derived from meters actually registered by the application. When enabled, meters omitted from the list will not appear in the filtered registry. Test in local/staging profiles before rolling out to production so you do not accidentally suppress critical SLO or health metrics.

### 6.3. Setting common tags carefully

Common tags attach stable metadata to all meters:

~~~java
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.boot.actuate.autoconfigure.metrics.MeterRegistryCustomizer;
import org.springframework.context.annotation.Bean;

@Bean
MeterRegistryCustomizer<MeterRegistry> commonTags() {
    return registry -> registry.config().commonTags(
            "application", "provider-integration",
            "environment", "production");
}
~~~

Never add instance UUIDs, request IDs, or deployment timestamps as common tags. In Kubernetes, evaluate Pod/instance labels carefully: they help debugging yet increase series churn whenever Pods are recreated frequently.

## 7. Prometheus: time series, histograms, and scrape volume

Prometheus stores metrics as time series where every combination of metric name and label set forms a series. Cardinality rises when:

- New labels are added.
- An existing label acquires many new values.
- Instances/pods/endpoints churn continuously.
- Histograms combine many buckets with many label combinations.

### 7.1. Classic histograms

With a classic histogram, each label set creates bucket counters plus `_sum` and `_count`. For example, 8 bucket boundaries produce 11 series per label set: 9 buckets (8 buckets + `+Inf`), 1 sum, and 1 count.

If 2,000 label sets exist, that single histogram metric generates around 22,000 series.

Do not add buckets solely for finer percentile resolution. Choose buckets aligned with meaningful SLO/latency boundaries, such as 50 ms, 100 ms, 250 ms, 500 ms, 1 s, and 2 s.

### 7.2. Scrape interval and sample volume

Scrape interval does not change the active series count, but it directly drives sample volume:

\[
SamplesPerDay = ActiveSeries \times \frac{86,400}{ScrapeIntervalSeconds}
\]

For example, 10,000 active series scraped every 15 seconds:

\[
10,000 \times \frac{86,400}{15}=57,600,000
\]

The system ingests roughly 57.6 million samples per day if every series appears in every scrape. Shortening the scrape interval improves resolution and spike detection, while raising ingestion, storage, and query costs.

### 7.3. Relabeling is only a secondary safeguard

Prometheus can apply metric relabeling to drop metrics or labels prior to ingestion. Example dropping a debug metric:

~~~yaml
scrape_configs:
  - job_name: provider-integration
    static_configs:
      - targets: ["provider-integration:8080"]
    metrics_path: /actuator/prometheus
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: "debug_.*"
        action: drop
~~~

Relabeling reduces stored series in Prometheus, yet the exporter still builds and serves the data before it is dropped. Therefore, preventing high cardinality inside the application with Micrometer and normalized labels remains the primary control.

## 8. CloudWatch: dimensions create custom metrics

In Amazon CloudWatch, a custom metric is identified by namespace, metric name, and the combination of dimensions. Each combination of dimension values can be billed as a separate custom metric.

Example:

~~~text
Namespace: ProviderIntegration
MetricName: CloudDependencyLatency
Dimensions:
  Provider = aws
  Service = s3
  Operation = get_object
  Environment = production
~~~

Adding a `CustomerId` dimension with thousands of values sends thousands of distinct metric identities to CloudWatch. A single new dimension multiplies custom metric counts by the product of all remaining dimensions.

### 8.1. Rules for CloudWatch

- Scope namespaces by service/domain, e.g., `ProviderIntegration`.
- Add only small-cardinality dimensions necessary for dashboards/alerts.
- Never place request ID, trace ID, user ID, object key, or exception message in dimensions.
- Apply metric filters/allow-lists in the Micrometer registry.
- Choose export step and resolution to fit operational needs.
- Review custom metric counts and spend in Cost Explorer/CloudWatch usage.

CloudWatch supports standard-resolution and high-resolution custom metrics; high-resolution metrics can increase cost and not every metric needs per-second granularity. Do not enable high resolution on every meter just because it is available.

### 8.2. Metric math is no substitute for dimension design

Metric math and dashboards can aggregate across metrics, but they do not reduce the number of custom metrics already published. To cut costs, reduce dimension combinations at the application or exporter level.

## 9. Azure Monitor: metric dimensions and custom telemetry

Azure Monitor has platform metrics and custom metrics. Platform metrics are emitted by Azure resources; custom metrics are sent by applications or agents. With Application Insights, custom metrics and telemetry dimensions can also raise ingestion volume and queryable time-series counts.

### 9.1. Choosing useful dimensions

Example custom metric:

~~~text
Metric: cloud_dependency_duration
Dimensions:
  cloud.provider = azure
  cloud.service = blob
  operation = upload
  outcome = success
  cloud.region = southeastasia
~~~

These dimensions support grouping by provider, operation, and outcome. Avoid adding `documentId`, `tenantId`, or `blobName`.

### 9.2. Limits and separating metrics from logs

- Use metric dimensions for bounded trend breakdowns.
- Write request IDs, correlation IDs, and resource paths to structured logs/traces per policy.
- With Application Insights, control custom dimensions and sampling to avoid unexpected ingestion volume.
- Verify dimension/cardinality limits for your specific metric type and workspace; Azure Monitor platform metrics, custom metrics, and Application Insights do not share identical semantics or pricing models.
- Do not assume all custom dimensions are stored or displayed identically across Metrics Explorer and Logs.

Azure Monitor pricing depends on data type, region, ingestion, retention, export, and commitment tier. Check actual workspace/resource pricing before finalizing sampling and retention.

## 10. Google Cloud Monitoring: metric labels and monitored resources

Cloud Monitoring identifies a time series by metric type, monitored resource, and label values. Thus, combinations of metric labels plus resource labels directly drive active series counts.

Example metric:

~~~text
custom.googleapis.com/cloud/dependency/duration
Resource:
  service_name = provider-integration
  location = asia-southeast1
Metric labels:
  provider = azure
  operation = upload
  outcome = success
~~~

### 10.1. Designing labels

- Use standard resource labels to describe service, location, and workload.
- Use metric labels for `provider`, `operation`, `outcome`, or `error_class` with small value sets.
- Never place request ID, trace ID, user ID, tenant ID, or object key in metric labels.
- Avoid creating new metric descriptors per business object.
- Monitor active time series and ingestion volume per metric type.

Google Cloud Monitoring enforces limits on labels/descriptors and prices by metric type, samples/time series, and product. Check current limits and pricing docs; never treat one project's quota as a universal default across environments.

### 10.2. Aggregating before export

If the application needs per-tenant visibility, consider aggregating at the business layer:

- Count total requests by plan/tier instead of tenant ID.
- Measure p95 latency by service/operation rather than per customer.
- Record select request details in sampled, access-controlled logs/traces.
- Create per-tenant metrics only when backed by a clear product requirement, bounded tenant count, and cost review.

## 11. Metrics, logs, and traces serve different roles

Do not cram every attribute into metric labels. Pick the telemetry signal matching the question:

| Question | Telemetry type | Example fields |
|---|---|---|
| How many uploads failed in the last 5 minutes? | Metric | `operation`, `outcome`, `provider` |
| Which customer's upload failed? | Structured log | `correlation_id`, `job_id`, tenant per policy |
| Which services did a request pass through? | Trace | `trace_id`, `span_id`, `service`, `dependency` |
| Which request ID did an S3 call return? | Log/trace | `provider_request_id` |
| What is the p95 latency of Blob uploads? | Histogram metric | `provider`, `service`, `operation` |
| How many times did a specific message retry? | Log/trace/event | `message_id`, `delivery_attempt` |

Logs can store unique IDs for investigation, yet still incur ingestion, indexing, storage, and query costs. Traces can hold many spans and attributes; sampling curbs volume while keeping representative traces. Metrics rely on stable dimensions for fast aggregation.

**Never move a high-cardinality tag from metrics to logs without evaluating privacy, retention, and indexing cost.** Choose appropriate storage and access policies.

## 12. Reducing metrics cost

Common techniques:

1. **Lower label cardinality:** eliminate IDs and raw strings; normalize to enums.
2. **Reduce meter count:** publish only meters tied to clear operational questions.
3. **Reduce histogram buckets:** choose SLO-aligned buckets instead of dense grids.
4. **Aggregate:** aggregate by service/operation prior to export.
5. **Sample or downsample:** apply where supported while understanding precision trade-offs.
6. **Tune export/scrape intervals:** pick appropriate resolution.
7. **Shorten detailed retention:** keep long-term history in aggregated form when suitable.
8. **Retire stale meters:** stop publishing metrics no longer used by dashboards or alerts.

Do not blindly slash sampling or scrape intervals. Metrics backing SLOs, alerts, or rapid incident detection need sufficient resolution to spot issues.

## 13. Reducing logs cost

Log costs are typically driven by:

- Bytes ingested.
- Events per second.
- Retention and archiving.
- Indexing, analytics, and queries.
- Cross-workspace or cross-region exports.
- Log verbosity and stack trace size.

Ways to reduce:

- Use INFO for normal events and WARN/ERROR for anomalies; avoid leaving DEBUG/HTTP wire logging on permanently.
- Never log full request/response bodies.
- Cap stack traces and exception messages.
- Sample successful access logs if platform and audit policies allow; retain error logs and security events per policy.
- Remove duplicate fields and unnecessary payloads.
- Set retention by log class: security/audit, application, debug.
- Use structured JSON without duplicating the same information in both message text and fields.

Never sample or drop security/audit logs when compliance requires full retention. Separate debugging logs from audit/compliance logs.

## 14. Reducing traces cost

Trace volume typically depends on:

- Request/operation count.
- Spans per trace.
- Sampling probability.
- Attributes/events per span.
- Exception/stack trace size.
- Retention and query load.

For example, a single request traversing API, storage, queue producer, worker, database, and HTTP dependencies can generate 8–15 spans. At 100,000 requests/hour and 100% sampling, span volume can hit millions per hour.

Techniques:

- Use parent-based sampling to keep traces consistent end-to-end.
- Sample high-volume successful traffic at a lower rate while keeping errors/high-latency traces via tail sampling if supported by your collector/backend.
- Do not create spans for every line of code or trivial getter.
- Cap span attributes and events.
- Never attach large payloads or PII to spans.
- Use metrics to track all traffic; use traces to investigate representative samples.

Tail sampling requires sufficient collector memory and wait windows to assemble a trace's spans before deciding. Misconfiguration can drop spans or split traces.

## 15. Budgets and review process for new metrics

Before merging a new metric, reviewers can ask for this checklist:

| Item | Question to answer |
|---|---|
| Purpose | Which operational question does this metric answer? |
| Name/type | Counter, Gauge, Timer, or DistributionSummary? |
| Labels | Which labels are strictly necessary? |
| Cardinality | Maximum values for each label? |
| Series estimate | How many series do label combinations and histogram buckets produce? |
| Scope | Per instance, service, cluster, or region? |
| Backend | Prometheus, CloudWatch, Azure Monitor, or Cloud Monitoring? |
| Cost | Impact on ingestion, custom metrics, retention, and queries? |
| Owner | Who owns remediation if cardinality spikes? |
| Lifecycle | When will the metric be retired or its schema updated? |

Do not arbitrarily rename metrics or labels once dashboards and alerts depend on them. Changing a label key creates a brand-new set of time series and can break existing dashboards.

## 16. Monitoring cardinality in production

### 16.1. Prometheus

Prometheus exposes internal metrics tracking series count and TSDB usage, such as:

- `prometheus_tsdb_head_series`: number of series in the head block.
- `prometheus_tsdb_head_samples_appended_total`: samples appended.
- `prometheus_tsdb_head_series_created_total`: newly created series.
- `scrape_samples_post_metric_relabeling`: post-relabeling sample count per target.

Exact metric names can vary by version/build and deployment; inspect Prometheus's `/metrics` endpoint before building dashboards.

### 16.2. Cloud providers

- **CloudWatch:** monitor custom metrics/dimensions, usage, and spend per namespace/account.
- **Azure Monitor:** monitor ingestion, custom metrics, workspace usage, and retention.
- **Google Cloud Monitoring:** monitor active time series, metric descriptors, samples, and usage.

Set alerts when cardinality or ingestion jumps sharply against baseline—such as doubling within a day. Thresholds should fit service traffic and deployment cadence; avoid applying one fixed threshold across all services.

## 17. Testing and enforcing cardinality in Spring Boot

You can test meter counts and tag values using `SimpleMeterRegistry`:

~~~java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.config.MeterFilter;
import io.micrometer.core.instrument.simple.SimpleMeterRegistry;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class MetricCardinalityTest {
    @Test
    void deniesNewOperationValuesAfterLimit() {
        SimpleMeterRegistry registry = new SimpleMeterRegistry();
        registry.config().meterFilter(
                MeterFilter.maximumAllowableTags(
                        "cloud.dependency",
                        "operation",
                        2,
                        MeterFilter.deny()));

        Counter.builder("cloud.dependency.calls")
                .tag("operation", "upload")
                .register(registry)
                .increment();

        Counter.builder("cloud.dependency.calls")
                .tag("operation", "download")
                .register(registry)
                .increment();

        Counter.builder("cloud.dependency.calls")
                .tag("operation", "dynamic-operation-123")
                .register(registry)
                .increment();

        assertEquals(2, registry.getMeters().size());
        assertEquals(
                0,
                registry.find("cloud.dependency.calls")
                        .tag("operation", "dynamic-operation-123")
                        .counters()
                        .size());
    }
}
~~~

This test illustrates capping operation values at two. In real projects, also test that:

- Raw URLs normalize to route templates.
- Customer/request/object IDs never appear in metric tags.
- Error types accept only bounded enums.
- Histogram bucket counts stay within budget.
- `MeterFilter` does not block critical SLO or health metrics.
- Exported metrics at `/actuator/prometheus` contain no tags outside the allow-list.

Note: filter tests only prove the registry drops excess meters. They do not prove CloudWatch/Azure/Google billing dropped; verify backend usage after deployment.

## 18. Troubleshooting

| Symptom | Possible cause | Fix |
|---|---|---|
| Prometheus RAM climbs rapidly | Many series or dynamic label values | Run cardinality analysis, remove IDs, normalize routes |
| Histograms create too many series | Too many buckets combined with many labels | Cut buckets, reduce labels, or split metrics |
| Dashboard queries run slowly | Queries return hundreds of thousands of series | Drop dimensions, pre-aggregate, and narrow time range |
| CloudWatch custom metric bill spikes | High-cardinality dimension added | Remove dimension, use `MeterFilter`, check metric identity |
| Azure Monitor ingestion rises | High custom metrics/logs or changing dimensions | Check workspace usage, sampling, and field schema |
| Google Monitoring active time series climb | Many metric/resource label combinations | Standardize labels and pre-aggregate |
| New meter does not appear | `MeterFilter` denied it or allow-list lacks the name | Inspect active filters and registry |
| Metrics vanish after setting limits | `MeterFilter` rejects new tag values | Find the cardinality-driving label and map to bounded values |
| High series churn despite modest cardinality | Pod/instance IDs change constantly | Control resource labels and reduce churn |
| High log costs | DEBUG logging, full bodies, or huge stack traces | Reduce verbosity, cap payloads and retention |
| High trace backend ingestion | High sampling, excessive spans/attributes | Tune sampling, span boundaries, and tail sampling |
| Relabeling does not reduce app memory | Dropping happens after scraping | Block meters/tags inside the application |

## 19. Hands-on exercises and self-check questions

**Scenario A — `customerId` tag:** A `document.preview.duration` metric has `provider`, `operation`, `outcome`, and `customerId`. Calculate series count with 3 providers, 8 operations, 3 outcomes, and 20,000 customers. Propose replacing `customerId` with plan/tier groups or moving details to logs.

**Scenario B — Histograms:** An HTTP metric has 12 bucket boundaries, 5 route templates, 4 methods, 5 status classes, and 6 instances. Estimate classic histogram series count and propose trimming buckets/labels.

**Scenario C — CloudWatch bill:** After adding an `objectKey` dimension, custom metrics surge. Explain metric identity by namespace/name/dimensions and redesign the dimension set.

**Scenario D — Azure Monitor:** Workspace ingestion rises after adding custom properties and logging request/response bodies. Distinguish metric dimensions from log custom dimensions and propose suitable sampling/retention policies.

**Scenario E — Google Cloud Monitoring:** A custom metric uses labels `region`, `tenant`, `orderId`, and `operation`. Calculate the upper bound, identify which labels to drop, and propose pre-export aggregation.

**Scenario F — Micrometer:** Add `MeterFilter.maximumAllowableTags` for a dependency metric, write a unit test proving the third tag value is denied, and verify `/actuator/prometheus`.

**Scenario G — Telemetry cost:** A service's metrics, logs, and traces double in cost. Identify why you need to inspect active time series, samples/day, bytes ingested, spans/request, sampling rate, and retention to pinpoint the driver.

### Self-check questions

1. **What is the cardinality of a time series?** Each unique combination of metric name and label values defines a distinct series.
2. **How does cardinality differ from sample count?** Cardinality is the number of series; sample count is the number of data points recorded over time.
3. **Why is `customerId` unsuitable as a metric label?** Its value count grows with customers and multiplies across every other label.
4. **How do classic histograms multiply series?** Each label set creates bucket series plus `_sum` and `_count`.
5. **What is Micrometer `MeterFilter` used for?** Dropping meters, capping total meters, or capping tag value counts.
6. **What determines CloudWatch custom metric identity?** Namespace, metric name, and the combination of dimensions.
7. **Do Azure Monitor platform metrics and custom metrics share identical semantics?** No; limits and pricing depend on data type and resource.
8. **What defines a Google Cloud Monitoring time series?** Metric type, monitored resource, and label values.
9. **Can request IDs be moved from metrics to logs?** Yes, when needed for investigation and guarded by privacy, indexing, and retention controls.
10. **Does scrape interval increase active series?** Not directly; it increases sample/ingestion volume over time.
11. **Does relabeling replace in-application cardinality controls?** No; it drops after scraping, so the exporter still builds the data.
12. **What are the three observability cost pillars to watch?** Metrics ingestion/time series, log bytes/retention/queries, and trace spans/sampling/retention.

## 20. Summary

Cardinality grows whenever a metric adds labels or a label takes too many values. Series count can be estimated as the product of label cardinalities; classic histograms multiply that further by buckets, sum, and count. Always design bounded labels before instrumenting and review every new dimension.

In Spring Boot, use Micrometer `MeterFilter` to cap meters/tags, normalize operations and error types, and keep request/customer/object IDs in controlled logs and traces. Prometheus requires managing series, buckets, and scrape volume; CloudWatch bills custom metrics per namespace/name/dimensions; Azure Monitor distinguishes platform/custom metrics and log ingestion; Google Cloud Monitoring tracks metric labels alongside monitored resource labels.

Observability costs come from more than metrics alone. Logs depend on ingested bytes, indexing, and retention; traces depend on span count, attributes, and sampling. Combine cardinality budgets, aggregation, sampling, retention, dashboard hygiene, and pre-release testing to keep telemetry actionable while controlling spend.
