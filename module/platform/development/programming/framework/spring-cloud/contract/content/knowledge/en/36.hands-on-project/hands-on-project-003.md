# Writing JSON Contracts with Dynamic Fields and Matchers

An order-creation API typically receives request data that varies per call—such as customer ID, client request ID, and item quantity—while returning producer-generated values such as order ID and creation timestamp. If a contract hardcodes every value to a single literal JSON sample, the stub only matches one exact request. Conversely, if matchers are too broad, tests can accept payloads with wrong types or missing fields.

**Spring Cloud Contract** lets you declare both **sample values** and **matching rules** for each side of the interaction. With the Groovy DSL, you can specify distinct consumer and producer values directly inside the body using `$()` or `value(...)`, or separate rules into `bodyMatchers`. With the YAML DSL, you declare sample data in the body and rules in the `matchers` section. From the same contract, Contract Verifier generates producer tests and the plugin packages stubs for the consumer to use via Stub Runner.

This lesson belongs to the **Hands-On Project** chapter in the **SPRING_CLOUD_CONTRACT** learning path: learning contract testing between producer and consumer with Groovy/YAML DSL, generating producer tests, publishing stubs, using Stub Runner, and integrating CI to catch breaking API changes. Its direct focus is **Writing JSON contracts with dynamic fields and matchers**.

After completing this lab, you will be able to distinguish consumer and producer values, write JSON contracts with dynamic UUIDs, order codes, timestamps, and correlation IDs, apply regex/type/date/array matchers, write equivalent contracts in Groovy and YAML, inspect generated tests and stub mappings, and connect producer verification with consumer Stub Runner tests.

## 1. Scenario: Checkout Creating an Order

**Order Service** exposes an order-creation API. **Checkout Service** sends:

```http
POST /api/orders
Content-Type: application/json
Accept: application/json

{
  "customerId": "CUS-000042",
  "clientRequestId": "A1B2C3D4E5F60708",
  "items": [
    {
      "sku": "SKU-42",
      "quantity": 2,
      "unitPrice": 62500
    }
  ]
}
```

Order Service validates the payload, generates an order ID, records the timestamp, and returns:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/ORD-100042

{
  "orderId": "ORD-100042",
  "clientRequestId": "A1B2C3D4E5F60708",
  "status": "CREATED",
  "createdAt": "2026-11-24T09:00:00Z",
  "totalAmount": 125000,
  "items": [
    {
      "sku": "SKU-42",
      "quantity": 2,
      "unitPrice": 62500
    }
  ]
}
```

| Field | Source | What needs to be verified |
|---|---|---|
| customerId | Sent by Checkout | Customer ID format |
| clientRequestId | Generated by Checkout | Valid ID format and echoed back accurately |
| items | Sent by Checkout | Array, SKU, quantity, and unitPrice types |
| orderId | Generated by Order Service | ORD prefix and length |
| createdAt | Generated by Order Service | ISO-8601 timestamp |
| status | Producer business logic | Value CREATED |
| totalAmount | Computed by Order Service | Numeric type and business value |
| Location | Returned by Order Service | Resource path of the new order |

The contract must allow the consumer to send different valid IDs while still giving the generated producer test a concrete, reproducible request.

## 2. Understanding the Consumer and Producer Sides

Spring Cloud Contract produces two outputs from a contract:

- **Consumer side:** the stub called by the consumer. The stub needs a flexible request matcher and a predictable sample response.
- **Producer side:** the generated test calling the real producer implementation. The test needs a concrete request and verifies the real response using matchers.

| Contract section | consumer(...) | producer(...) |
|---|---|---|
| Request body/header/path | Value or matcher used when the stub receives a request | Concrete value sent by the generated test to the producer |
| Response body/header | Concrete value returned by the stub to the consumer | Value or matcher used by the generated test to verify the real response |

### 2.1. Request: Consumer Sends Varying Values, Producer Test Sends a Fixed Sample

```groovy
customerId: $(
    consumer(regex('CUS-[0-9]{6}')),
    producer('CUS-000042')
)
```

Result:

- The stub accepts IDs such as CUS-000042 or CUS-654321.
- The generated producer test sends a concrete request with CUS-000042.

The producer test does not send the regex as a literal string; the regex is the rule the stub uses to match consumer requests.

### 2.2. Response: Stub Returns a Fixed Sample, Producer Test Verifies Dynamic Values

```groovy
orderId: $(
    consumer('ORD-100042'),
    producer(regex('ORD-[0-9]{6}'))
)
```

Result:

- The stub returns a fixed orderId ORD-100042 so consumer tests stay deterministic.
- The generated producer test accepts a real response whose orderId matches ORD-[0-9]{6}.

This lets the producer generate IDs freely without forcing a UUID or ID generator to return one hardcoded value in tests.

### 2.3. Rule of Thumb

- **Request:** consumer matcher, producer sample.
- **Response:** consumer sample, producer matcher.

If you invert the two sides, you can end up with a test request that cannot be sent or a stub response without a concrete value to return. Always inspect generated tests and mappings after writing a dynamic contract.

## 3. Groovy DSL: Order Creation Contract with Dynamic Fields

Create the file:

```text
src/test/resources/contracts/checkout/create_order_201.groovy
```

Contents:

```groovy
import org.springframework.cloud.contract.spec.Contract

Contract.make {
    name 'checkout_create_order_201'
    description 'Checkout creates an order with dynamic request IDs and producer-generated response ID'

    request {
        method POST()
        url '/api/orders'

        headers {
            contentType(applicationJson())
            accept(applicationJson())
        }

        body(
            customerId: $(
                consumer(regex('CUS-[0-9]{6}')),
                producer('CUS-000042')
            ),
            clientRequestId: $(
                consumer(regex('[A-F0-9]{16}')),
                producer('A1B2C3D4E5F60708')
            ),
            items: [
                [
                    sku: 'SKU-42',
                    quantity: 2,
                    unitPrice: 62500
                ]
            ]
        )

        bodyMatchers {
            jsonPath('$.items', byType {
                minOccurrence(1)
                maxOccurrence(5)
            })
        }
    }

    response {
        status CREATED()

        headers {
            contentType(applicationJson())
            header(
                'Location',
                $(
                    consumer('/api/orders/ORD-100042'),
                    producer(regex('/api/orders/ORD-[0-9]{6}'))
                )
            )
        }

        body(
            orderId: $(
                consumer('ORD-100042'),
                producer(regex('ORD-[0-9]{6}'))
            ),
            clientRequestId: fromRequest().body('$.clientRequestId'),
            status: 'CREATED',
            createdAt: $(
                consumer('2026-11-24T09:00:00Z'),
                producer(anyIso8601WithOffset())
            ),
            totalAmount: 125000,
            items: [
                [
                    sku: 'SKU-42',
                    quantity: 2,
                    unitPrice: 62500
                ]
            ]
        )

        bodyMatchers {
            jsonPath('$.totalAmount', byType())
            jsonPath('$.items', byType {
                minOccurrence(1)
                maxOccurrence(5)
            })
        }
    }
}
```

This is a Groovy DSL example for learning dynamic values and matchers. Confirm the exact helper methods against your version of Spring Cloud Contract.

### 3.1. Analyzing the Request

customerId has two values:

- The consumer stub matcher accepts CUS- followed by six digits.
- The generated producer test sends CUS-000042.

clientRequestId behaves similarly:

- The consumer can send different 16-character hex IDs.
- The producer test sends A1B2C3D4E5F60708.
- The stub is not locked to a single correlation ID.

items has one sample element. bodyMatchers enforces an array size between 1 and 5 elements. The sample body must still include the items field; matchers do not synthesize missing fields or payloads.

### 3.2. Analyzing the Response

orderId:

- The stub returns ORD-100042.
- The generated producer test verifies the real response matches ORD-[0-9]{6}.

createdAt:

- The stub returns a fixed timestamp so consumer tests remain reproducible.
- The producer test accepts an ISO-8601 timestamp with an offset.
- anyIso8601WithOffset() is a predefined regex helper in Spring Cloud Contract.

totalAmount is type-checked via byType(). The sample body uses the number 125000, so the producer response must return a JSON number, not the string "125000".

Location also uses a dynamic response: the stub returns a concrete URL, and the producer test verifies the real URL against the pattern.

### 3.3. Echoing a Value from Request to Response

The following line requires the response to echo the clientRequestId received in the request:

```groovy
clientRequestId: fromRequest().body('$.clientRequestId')
```

Groovy's fromRequest() can reference URL, path, query parameters, headers, and body via JSONPath. In YAML, you can use a Handlebars helper such as {{{ jsonpath this '$.clientRequestId' }}} in the response body. Response templating must be supported by the WireMock version and corresponding transformer.

## 4. YAML DSL: Sample Body and JSONPath Matchers

YAML does not directly use Groovy's $() syntax. In YAML, you declare **sample values in the body** and place rules in the matchers section.

Create an illustrative YAML alternative for the contract above:

```text
src/test/resources/contracts/checkout/create_order_201.yml
```

```yaml
name: checkout_create_order_201_yaml
description: Checkout creates an order with JSON matchers

request:
  method: POST
  url: /api/orders
  headers:
    Content-Type: application/json
    Accept: application/json
  body:
    customerId: CUS-000042
    clientRequestId: A1B2C3D4E5F60708
    items:
      - sku: SKU-42
        quantity: 2
        unitPrice: 62500
  matchers:
    body:
      - path: $.customerId
        type: by_regex
        value: 'CUS-[0-9]{6}'
        regexType: as_string
      - path: $.clientRequestId
        type: by_regex
        value: '[A-F0-9]{16}'
        regexType: as_string
      - path: $.items
        type: by_type
        minOccurrence: 1
        maxOccurrence: 5

response:
  status: 201
  headers:
    Content-Type: application/json
  body:
    orderId: ORD-100042
    clientRequestId: A1B2C3D4E5F60708
    status: CREATED
    createdAt: '2026-11-24T09:00:00Z'
    totalAmount: 125000
    items:
      - sku: SKU-42
        quantity: 2
        unitPrice: 62500
  matchers:
    body:
      - path: $.orderId
        type: by_regex
        value: 'ORD-[0-9]{6}'
        regexType: as_string
      - path: $.createdAt
        type: by_timestamp
      - path: $.totalAmount
        type: by_type
      - path: $.items
        type: by_type
        minOccurrence: 1
        maxOccurrence: 5
```

This is an **alternative YAML syntax** for the same idea; do not place both Groovy and YAML contracts for the same scenario in the same source directory. Doing so can generate duplicate contracts, duplicate tests, or duplicate stub mappings.

### 4.1. request.matchers Used for Stub Requests

In the YAML above:

- The sample body has customerId CUS-000042.
- The $.customerId matcher requires consumer requests to match CUS-[0-9]{6}.
- The sample body has a concrete clientRequestId.
- The matcher lets consumers send other 16-character hex IDs.
- items must have an element count within the bounds.

The generated producer test still uses the sample body from the contract to call the producer. request.matchers lets the stub accept varying valid requests.

### 4.2. response.matchers Used for Producer Verification

The response body in YAML provides the sample returned by the stub to the consumer. response.matchers describes how the generated producer test verifies the real response:

- orderId must match the pattern.
- createdAt must be a valid ISO timestamp.
- totalAmount must remain a number.
- items must be a collection within the specified bounds.

**Every JSONPath in matchers must reference an element that exists in the body.** If you write a $.orderId matcher without orderId in the body, the contract is missing the required sample data.

### 4.3. YAML Matchers Are Not a General-Purpose JSON Schema Validator

Spring Cloud Contract YAML matchers rely on JSONPath and supported matcher types. They do not replace full JSON Schema/OpenAPI validation or domain business validation.

If you need to verify that totalAmount equals the sum of quantity times unitPrice, or enforce cross-field invariants, add producer integration/service tests. Contracts should protect the properties consumers genuinely depend on.

## 5. How Are bodyMatchers and Dynamic Values Different?

Groovy DSL supports two ways to describe dynamic sections:

1. Placing side-specific values directly inside the body using value(...) or $().
2. Declaring a sample body and adding JSONPath matchers in bodyMatchers.

| Style | Best suited when | Example |
|---|---|---|
| `$(consumer(...), producer(...))` | Both sides need different values | Stub returns fixed ID, producer test accepts regex |
| bodyMatchers | You want to separate sample data from rules | Timestamps, types, array sizes |
| byType() | Checking JSON types | String, number, boolean, collection |
| byRegex(...) | Checking patterns | UUID, order code, email |
| byDate/byTimestamp/byTime | Checking temporal formats | Date, ISO datetime, time |
| byEquality() | Exact match against sample value | Status or enum |
| byNull() | Checking null fields | Fields allowed to be null |

### 5.1. bodyMatchers in Request and Response

| Location | Purpose | Used by |
|---|---|---|
| request.bodyMatchers | Conditions for stub to accept a JSON request | Consumer-side stub |
| response.bodyMatchers | Verifying the producer's real response | Generated producer test |
| outputMessage.bodyMatchers | Verifying the message body emitted by producer | Generated producer messaging test |

Groovy example:

```groovy
bodyMatchers {
    jsonPath('$.orderId', byRegex('ORD-[0-9]{6}').asString())
    jsonPath('$.createdAt', byTimestamp())
    jsonPath('$.totalAmount', byType())
}
```

Place matchers in the right section. A matcher in request does not automatically validate the response.

## 6. Choosing Matchers Based on JSON Data

### 6.1. Regex for Strings

```groovy
bodyMatchers {
    jsonPath('$.orderId', byRegex('ORD-[0-9]{6}').asString())
    jsonPath('$.customer.email', byRegex('[^@]+@[^@]+\\.[^@]+').asString())
}
```

YAML:

```yaml
matchers:
  body:
    - path: $.orderId
      type: by_regex
      value: 'ORD-[0-9]{6}'
      regexType: as_string
```

Regex matches the **entire value**, not just a substring. Thus ORD-[0-9]{6} matches ORD-100042 but not prefix-ORD-100042-suffix. Spring Cloud Contract uses semantics equivalent to Pattern.matches().

When a regex is used to auto-generate counterpart values, be mindful of regex-to-string library limitations; avoid relying on ^/$ when auto-generation is needed. Whenever possible, supply a concrete value for the side that needs a sample.

### 6.2. Regex and JSON Types

YAML regexType supports types such as:

| regexType | Type |
|---|---|
| as_string | String |
| as_integer | Integer |
| as_long | Long |
| as_double | Double |
| as_float | Float |
| as_short | Short |
| as_boolean | Boolean |

Groovy:

```groovy
bodyMatchers {
    jsonPath('$.quantity', byRegex('[1-9][0-9]*').asInteger())
    jsonPath('$.unitPrice', byRegex('[0-9]+').asInteger())
    jsonPath('$.active', byRegex('true|false').asBooleanType())
}
```

JSON number and JSON string are two distinct types:

```json
{"quantity": 2}
```

```json
{"quantity": "2"}
```

If the consumer deserializes into an integer, the contract must not treat these two payloads as equivalent.

### 6.3. Temporal Matchers

Groovy:

```groovy
bodyMatchers {
    jsonPath('$.createdDate', byDate())
    jsonPath('$.createdAt', byTimestamp())
    jsonPath('$.deliveryTime', byTime())
}
```

YAML:

```yaml
matchers:
  body:
    - path: $.createdDate
      type: by_date
    - path: $.createdAt
      type: by_timestamp
    - path: $.deliveryTime
      type: by_time
```

- by_date: date-formatted value.
- by_timestamp: date and time.
- by_time: time of day.

Format matchers do not verify business timezone rules or ordering between two temporal fields. If createdAt must precede expiresAt, add a dedicated business assertion.

### 6.4. Type and Array-Size Matchers

Groovy:

```groovy
bodyMatchers {
    jsonPath('$.status', byType())
    jsonPath('$.totalAmount', byType())
    jsonPath('$.items', byType {
        minOccurrence(1)
        maxOccurrence(5)
    })
}
```

YAML:

```yaml
matchers:
  body:
    - path: $.status
      type: by_type
    - path: $.totalAmount
      type: by_type
    - path: $.items
      type: by_type
      minOccurrence: 1
      maxOccurrence: 5
```

byType() compares the runtime type against the type in the sample body. For collections, minOccurrence/maxOccurrence bound element counts per matcher semantics. If you need an exact count of two elements, set both min and max to 2, or use equality when the array must have fixed contents.

### 6.5. Equality and Null

Groovy:

```groovy
bodyMatchers {
    jsonPath('$.status', byEquality())
    jsonPath('$.optionalNote', byNull())
}
```

YAML:

```yaml
matchers:
  body:
    - path: $.status
      type: by_equality
    - path: $.optionalNote
      type: by_null
      value: null
```

An absent field and a field with value null are two different states. Do not treat them as equivalent if the consumer distinguishes between them.

## 7. Arrays and Nested JSON

Example response:

```json
{
  "orderId": "ORD-100042",
  "customer": {
    "id": "CUS-000042",
    "tier": "GOLD"
  },
  "items": [
    {
      "sku": "SKU-42",
      "quantity": 2,
      "unitPrice": 62500
    },
    {
      "sku": "SKU-99",
      "quantity": 1,
      "unitPrice": 20000
    }
  ]
}
```

Common JSONPaths:

| JSONPath | Meaning |
|---|---|
| $.orderId | Order ID |
| $.customer.id | Nested customer ID |
| $.customer.tier | Customer tier |
| $.items | Entire array |
| $.items[0].sku | SKU of first element |
| $.items[*].sku | SKUs of elements |
| $.items[*].quantity | Quantities of elements |

Groovy matchers:

```groovy
bodyMatchers {
    jsonPath('$.customer.id', byRegex('CUS-[0-9]{6}').asString())
    jsonPath('$.customer.tier', byEquality())
    jsonPath('$.items', byType {
        minOccurrence(1)
        maxOccurrence(10)
    })
    jsonPath('$.items[0].quantity', byRegex('[1-9][0-9]*').asInteger())
}
```

The $.items[0].quantity matcher protects the first element. If you want to constrain every element, verify JSONPath wildcard semantics and generated assertions with your plugin version; do not assume a matcher at [0] applies to the entire array.

## 8. Predefined Regex Helpers

Spring Cloud Contract provides helpers so you do not have to write every pattern manually:

| Helper | Meaning |
|---|---|
| anyUuid() | UUID |
| anyInteger() | Integer |
| anyPositiveInt() | Positive integer |
| anyNumber() | Numeric value |
| anyDouble() | Floating-point number |
| anyBoolean()/aBoolean() | Boolean |
| anyEmail() | Email address |
| anyUrl()/anyHttpsUrl() | URL |
| anyIpAddress() | IP address |
| anyHostname() | Hostname |
| anyDate() | Date |
| anyDateTime() | Date and time |
| anyTime() | Time |
| anyIso8601WithOffset() | ISO-8601 with offset |
| anyNonBlankString() | Non-blank string |
| anyNonEmptyString() | Non-empty string |
| anyOf('A', 'B') | One of the given values |

Example:

```groovy
body(
    id: $(anyUuid()),
    quantity: $(anyPositiveInt()),
    email: $(anyEmail()),
    active: $(anyBoolean()),
    createdAt: $(anyIso8601WithOffset())
)
```

Choose a helper that reflects the API's semantics. If quantity must be greater than 0, anyInteger() is too broad because it includes 0 and negative numbers; anyPositiveInt() is more accurate.

## 9. Optional Fields and Null

Groovy DSL supports optional(...) in framework-defined positions.

Example request with an optional email:

```groovy
body(
    customerId: 'CUS-000042',
    email: $(
        consumer(optional(regex(email()))),
        producer('buyer@example.test')
    )
)
```

The consumer-side stub can accept requests without email or with a valid email; the generated producer test uses the concrete email value.

Do not sprinkle optional() everywhere arbitrarily. Spring Cloud Contract documentation restricts optional parameters to supported sides of a contract, such as the stub side of a request and the test side of a response. Check your version before expanding its use.

The following three payloads are distinct:

```json
{"email": "buyer@example.test"}
```

```json
{"email": null}
```

```json
{}
```

They represent a populated field, a null field, and an omitted field, respectively. byNull() is not the same as an optional field.

## 10. Headers and Query Parameters Can Also Be Dynamic

Groovy request header:

```groovy
headers {
    header(
        'X-Correlation-Id',
        $(
            consumer(regex('[A-F0-9]{16}')),
            producer('A1B2C3D4E5F60708')
        )
    )
    contentType(applicationJson())
}
```

YAML header matcher:

```yaml
request:
  method: POST
  url: /api/orders
  headers:
    Content-Type: application/json
    X-Correlation-Id: A1B2C3D4E5F60708
  matchers:
    headers:
      - key: X-Correlation-Id
        regex: '[A-F0-9]{16}'
```

For the Location response header, you can use dynamic values in Groovy as shown in Section 3. In YAML, use header matchers per the supported DSL structure. Do not put body matchers inside matchers.headers or confuse header names with JSONPaths.

## 11. Referencing the Request in the Response

Groovy DSL provides fromRequest():

```groovy
response {
    status CREATED()
    headers {
        contentType(applicationJson())
    }
    body(
        orderId: 'ORD-100042',
        clientRequestId: fromRequest().body('$.clientRequestId'),
        customerId: fromRequest().body('$.customerId')
    )
}
```

YAML can use Handlebars helpers:

```yaml
response:
  status: 201
  headers:
    Content-Type: application/json
  body:
    orderId: ORD-100042
    clientRequestId: "{{{ jsonpath this '$.clientRequestId' }}}"
    customerId: "{{{ jsonpath this '$.customerId' }}}"
```

Templated responses rely on WireMock's response transformer and Handlebars. Verify your WireMock version and transformer support in your Spring Cloud Contract release train. If dynamic request echoing is unnecessary, fixed sample values are simpler.

## 12. Producer Implementation and Fixture

Illustrative controller:

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderApplicationService orderService;

    public OrderController(OrderApplicationService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<OrderResponse> create(
            @RequestBody CreateOrderRequest request) {
        OrderResponse response = orderService.create(request);

        return ResponseEntity
            .created(URI.create("/api/orders/" + response.orderId()))
            .body(response);
    }
}
```

Service implementing the business flow:

```java
@Service
public class OrderApplicationService {

    private final OrderRepository repository;
    private final Clock clock;
    private final OrderIdGenerator idGenerator;

    public OrderApplicationService(
            OrderRepository repository,
            Clock clock,
            OrderIdGenerator idGenerator) {
        this.repository = repository;
        this.clock = clock;
        this.idGenerator = idGenerator;
    }

    public OrderResponse create(CreateOrderRequest request) {
        validate(request);

        String orderId = idGenerator.nextOrderId();
        Instant createdAt = clock.instant();

        Order order = Order.create(
            orderId,
            request.customerId(),
            request.items(),
            createdAt
        );

        repository.save(order);

        return OrderResponse.from(order, request.clientRequestId());
    }
}
```

Classes such as CreateOrderRequest, OrderResponse, Order, OrderRepository, OrderIdGenerator, and validate are illustrative pieces for the project to implement. This is not a complete pre-built application.

### 12.1. Stable Producer Fixture

The generated producer test sends the concrete request from producer(...). The base test can prepare the database:

```java
@SpringBootTest
@AutoConfigureMockMvc
public abstract class OrderContractTestBase {

    @Autowired
    MockMvc mockMvc;

    @Autowired
    OrderContractFixture fixture;

    @BeforeEach
    void prepare() {
        fixture.reset();
        RestAssuredMockMvc.mockMvc(mockMvc);
    }
}
```

For an order-creation contract, the fixture should reset data between tests, avoid any production database, seed customer CUS-000042 if the endpoint requires it, configure Clock/ID generators appropriately if deterministic values are needed, and avoid mocking OrderApplicationService when the goal is verifying order-creation logic. Only fake external boundaries outside the contract scope.

This is a fragment; you need a parent/BOM and compatible Spring Boot/Cloud/Contract versions. Generated test sources normally appear under target/generated-test-sources/contracts/ per Maven plugin configuration. Your test runner must actually execute those classes.

Run:

```bash

```

generateTests only generates source files; verify walks the lifecycle to compile and run tests when plugin and test runner are configured correctly. Generated files existing on disk is not proof that the producer passed.

## 13. Inspecting Generated Producer Tests and Stub Mappings

After building, the generated test reads similarly to this pseudocode:

```java
// Illustrative pseudocode, not verbatim generated source.
given()
    .contentType("application/json")
    .body("""
        {
          "customerId": "CUS-000042",
          "clientRequestId": "A1B2C3D4E5F60708",
          "items": [
            {"sku":"SKU-42","quantity":2,"unitPrice":62500}
          ]
        }
        """)
.when()
    .post("/api/orders")
.then()
    .statusCode(201)
    .body("orderId", matchesPattern("ORD-[0-9]{6}"))
    .body("status", equalTo("CREATED"))
    .body("totalAmount", instanceOf(Number.class));
```

Actual generated source depends on Contract Verifier, DSL, test framework, and version. Confirm that the request sends the producer sample, response matchers use regex/type, status and headers are asserted, consumer-relied JSON fields are protected, and the generated test extends the right base class and is executed without skipping.

### 13.1. Stub Response

The consumer-side stub must return a predictable sample JSON:

```json
{
  "orderId": "ORD-100042",
  "clientRequestId": "A1B2C3D4E5F60708",
  "status": "CREATED",
  "createdAt": "2026-11-24T09:00:00Z",
  "totalAmount": 125000
}
```

The request mapping must accept dynamic customerId/clientRequestId values according to the matchers. Never hand-edit generated mappings under target/; fix the contract DSL and regenerate.

### 13.2. Testing Two Requests Against the Same Stub

Request A:

```json
{
  "customerId": "CUS-000042",
  "clientRequestId": "A1B2C3D4E5F60708",
  "items": [{"sku":"SKU-42","quantity":2,"unitPrice":62500}]
}
```

Request B:

```json
{
  "customerId": "CUS-654321",
  "clientRequestId": "ABCDEF0123456789",
  "items": [{"sku":"SKU-42","quantity":2,"unitPrice":62500}]
}
```

Both should match the stub if they satisfy the request matchers. The stub returns a deterministic sample response, letting Checkout test post-order logic without knowing which real ID or timestamp Order Service generates.

## 14. Consumer Test with Stub Runner

The consumer resolves the exact version of the stubs artifact. Example:

```java
@SpringBootTest
@AutoConfigureStubRunner(
    ids = "com.example:order-service:1.4.0:stubs:8085",
    stubsMode = StubRunnerProperties.StubsMode.LOCAL
)
class CheckoutOrderClientTest {
    // Inject real OrderClient and verify request/response.
}
```

This is an illustrative configuration; you need imports, the Stub Runner test dependency, base URL wiring, and an installed/published artifact. 8085 is the HTTP stub server port in the example notation.

Consumer tests should verify that the client sends POST /api/orders with proper Content-Type and Accept headers, JSON requests carry validly formatted IDs, the client handles 201 Created, deserializes orderId/status/createdAt/totalAmount with proper types, and handles Location if used.

Stub Runner does not execute the real Order Service implementation. Producer verification and consumer Stub Runner tests complement each other.

## 15. Error Contracts to Protect Validation

YAML example for an invalid quantity:

```yaml
name: checkout_create_order_invalid_quantity_400
request:
  method: POST
  url: /api/orders
  headers:
    Content-Type: application/json
  body:
    customerId: CUS-000042
    clientRequestId: A1B2C3D4E5F60708
    items:
      - sku: SKU-42
        quantity: 0
        unitPrice: 62500
response:
  status: 400
  headers:
    Content-Type: application/json
  body:
    code: INVALID_QUANTITY
  matchers:
    body:
      - path: $.code
        type: by_equality
```

This contract needs its own file, and the producer implementation must return the matching status and error body. If your API policy uses 422, use that status instead of forcing every validation error to 400.

If Checkout depends on code, assert that field; checking only HTTP status 400 can miss incompatible error schemas.

## 16. Common Pitfalls When Writing Dynamic JSON Contracts

| Mistake | Consequence | Fix |
|---|---|---|
| Swapping consumer and producer | Test request or stub response uses wrong value | Apply the matrix in Section 2 |
| Unnecessary regex on both sides | Hard to reproduce or missing sample | Supply a concrete value to the side needing a sample |
| Writing a JSON number as a string | Wrong type matcher / deserializer behavior | Preserve exact JSON types |
| Matcher path does not exist | Contract lacks the referenced element | Add the body field or fix the JSONPath |
| Overly broad regex such as .* | Accepts invalid payloads | Constrain prefix, length, and character set |
| Overly narrow regex | Valid requests fail to match stub | Align with real API format |
| Confusing by_type with business validation | Checks type only | Add equality or business tests |
| Treating by_timestamp as timezone validation | Misses timezone rules | Add business assertions |
| Array missing min/max | Unbounded element count | Set occurrence bounds |
| Using $() syntax in YAML | YAML does not evaluate Groovy expressions | Use matchers |
| Duplicate Groovy/YAML for same scenario | Duplicate generated tests/stubs | Pick one source per scenario |
| Putting request matcher in response | Validates the wrong side | Place in the right request/response block |
| Using fromRequest() in YAML | YAML lacks Groovy methods | Use Handlebars |
| Never inspecting generated mappings | Stub matches too broadly or serves wrong body | Inspect actual mappings |
| Running only Stub Runner tests | Producer is unverified | Run Contract Verifier |
| Running only producer tests | Unknown how consumer handles stubs | Run Stub Runner tests |

### 16.1. Regex Matches the Whole Value

Spring Cloud Contract uses Pattern.matches() semantics for regex matching. ORD-[0-9]{6} checks the entire string; it does not search for a substring inside a larger string.

- ORD-100042: matches.
- prefix-ORD-100042: does not match.
- ORD-100042-suffix: does not match.

Regex checks format; it does not verify that an ID exists or that the caller is authorized to access it.

## 17. Mutation Testing to Prove Matchers Work

Intentionally mutate the implementation on an experimental branch:

| Mutation | What the test must catch |
|---|---|
| Change orderId to BAD-42 | Regex ORD-[0-9]{6} fails |
| Change createdAt to yesterday | Timestamp matcher fails |
| Change totalAmount from number to string | Type matcher catches it |
| Change items to empty array | minOccurrence: 1 fails |
| Change status to PENDING | Equality matcher for CREATED fails |
| Omit Location | Header assertion fails |

Workflow:

1. Run the baseline and confirm producer tests PASS.
2. Mutate one field in the implementation.
3. Re-run the specific generated test.
4. Confirm the failure occurs on the expected matcher.
5. Restore the implementation.
6. Re-run and confirm PASS.

If a mutation does not break the test, inspect generated assertions, base class, test mode, and runner reports. Parsing a contract cleanly does not prove matchers are enforced.

## 20. Matcher Troubleshooting Table

| Symptom | Possible cause | How to investigate |
|---|---|---|
| Stub only accepts CUS-000042 | Request matcher not generated or misplaced | Inspect mapping and request.matchers |
| Generated test sends literal regex text | Regex placed on the wrong side | Request producer side must be a sample |
| Stub response returns literal regex text | Response consumer side lacks a sample | Use consumer('...') |
| Producer test fails on random ID | Assertion uses equality | Check response producer(regex(...)) |
| createdAt fails to match | Format/timezone differs from pattern | Use byTimestamp or an appropriate regex |
| totalAmount fails to match | Number serialized as String | Check DTO/Jackson and regexType |
| YAML matcher has no effect | Wrong or missing path | Check body and JSONPath |
| Array accepts wrong element count | Missing min/max or wrong path | Inspect generated matcher |
| Response echoes wrong ID | Request reference template not processed | Check fromRequest/Handlebars |
| Stub Runner returns 404 | Request does not match mapping | Check method/path/header/body matchers |
| Producer test does not run | Plugin/test runner/lifecycle issue | Check generated sources and reports |
| Groovy regex parse error | Quotes/escaping or DSL version | Read stack trace and check version |
| YAML parses but generation fails | Key/type outside DSL spec | Check YAML schema |
| Matcher is too broad | Regex does not constrain format | Restrict prefix/length/type |
| Duplicate matcher | Both dynamic body value and bodyMatcher used | Pick one clear mechanism per field |

## 22. Self-Check Questions

1. **Why do we need dynamic fields?** So stubs remain reusable when IDs, timestamps, or request values vary.
2. **Which side does consumer(...) represent?** Values/behavior on the consumer stub side.
3. **Which side does producer(...) represent?** Values/behavior in generated producer verification.
4. **Why does a request use consumer(regex(...))?** So the stub accepts multiple valid requests.
5. **Why does a request use producer('CUS-000042')?** So the generated producer test sends a concrete request.
6. **Why does a response use consumer('ORD-100042')?** So the stub returns a fixed sample response.
7. **Why does a response use producer(regex(...))?** So the producer test checks the real response against a pattern.
8. **How does Groovy DSL declare dynamic body values?** Using value(...) or $().
9. **Where does YAML DSL declare matchers?** Under the matchers section.
10. **What does by_regex do?** Checks that a JSON value matches a regex.
11. **Why is regexType: as_integer needed?** To preserve integer semantics instead of treating the value as a string.
12. **What does by_type verify?** Runtime data type compared to the sample body.
13. **What are minOccurrence/maxOccurrence used for?** Bounding collection element counts.
14. **When is by_timestamp used?** When a field holds a timestamp.
15. **How does by_null differ from optional?** Null means a field has a null value; optional can allow a field to be absent in DSL-supported positions.
16. **Why must a matcher path point to a field in the body?** Matchers do not create payload elements.
17. **What is fromRequest() used for?** Referencing request fields inside a Groovy DSL response.
18. **How does YAML reference the request body?** Using a Handlebars helper such as {{{ jsonpath this '$.field' }}}.
19. **Does a regex matcher search for substrings?** Do not assume so; semantics match the entire value.
20. **Why shouldn't you use .* for every field?** It makes matchers too permissive and lets breaking changes slip through.
21. **How do producer tests differ from Stub Runner tests?** One verifies the real producer; the other tests the consumer against stubs.
22. **Does a stub need a fixed response sample?** Usually yes, so consumer tests are reproducible.
23. **Why must JSON numbers and JSON strings be distinguished?** They are distinct data types.
24. **What does mutation testing prove?** That matchers catch specific breaking changes in the implementation.
25. **When should you use Groovy dynamic values vs. YAML matchers?** Groovy is convenient when both sides need different values inline in the body; YAML works well when separating sample bodies from JSONPath constraints.

## Conclusion

A well-crafted JSON contract defines **sample data the consumer can rely on**, **flexible request matchers**, and **strict producer assertions**. Groovy DSL lets you place side-specific values inline using `$(consumer(...), producer(...))`; YAML DSL pairs a sample body with JSONPath-based matchers. Picking the right side for each value prevents stubs from locking onto a single request's IDs or timestamps while still testing the producer via generated tests.

In this lab, customerId and clientRequestId are matched by format; orderId and createdAt are producer-generated; totalAmount preserves its numeric type; items enforces element bounds; and clientRequestId can be echoed from the request. Combining **Contract Verifier**, **Stub Runner**, generated test inspection, mutation checks, and **CI gates** enables teams to catch breaking JSON changes early while keeping stubs flexible and reusable.
