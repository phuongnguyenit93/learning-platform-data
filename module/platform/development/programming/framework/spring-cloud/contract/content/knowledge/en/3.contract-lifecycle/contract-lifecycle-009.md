# Evidence Required Before Declaring Compatibility

## Lesson Objectives

In the contract lifecycle between a **producer** (API/message provider) and a **consumer** (API/message caller), declaring **“the new version is compatible”** directly impacts deployment decisions across multiple teams. A passing build or a runnable set of stubs is not enough to make that claim.

**Spring Cloud Contract** helps turn HTTP or message behaviors specified in **Groovy/YAML DSL** into automatable checks: generating tests to verify the producer, creating stubs, using **Stub Runner** so consumers can test interactions, and running these steps in CI. However, a compatibility claim is only trustworthy when **the checks are properly linked to the contracts, source code, builds, artifacts, and actual consumer set**.

After this lesson, you will be able to:

- Formulate a compatibility claim with a clearly defined verification scope.
- Distinguish evidence from contracts, producer tests, stubs, consumer tests, and supplemental integration tests.
- Build a traceability chain from contract version to build and CI results.
- Evaluate a version matrix when two services are not deployed simultaneously.
- Design release gates and an evidence record before announcing an API/message change as safe for consumers.

## 1. First, State Clearly “Compatible with Whom, at Which Version?”

Avoid vague announcements:

> “Order API version 2 is backward compatible.”

A verifiable statement must be much more specific:

> “Order API producer version 2.4.0, built from commit P2, still satisfies the HTTP contracts that consumer Checkout 1.9.0 depends on, within the declared scenarios and verified by CI using stubs from the same build.”

The second statement answers critical questions:

| Question | Information to record |
| --- | --- |
| **Which producer?** | Service name, build, commit, version, or image digest |
| **Which consumer?** | Consumer name, version, branch, or tested commit |
| **Which integration surface?** | Endpoints, HTTP methods, schemas, error codes, events/messages |
| **Which contracts?** | Contract file or set at a specific revision |
| **Where is the evidence from?** | Traceable test runs and artifacts |
| **What are the scope limits?** | Covered scenarios, untested versions, open risks |

In a multi-service system, “compatibility” is a **relationship between versions within a scope**, not an absolute property of a producer. A new producer version might be compatible with Checkout yet incompatible with Reporting if the two consumers rely on different fields or error codes.

### Distinguishing two directions of compatibility

- **Old consumer → New producer:** the new producer must continue handling requests and returning behaviors expected by existing consumers. This is typically critical when upgrading the producer first.
- **New consumer → Old producer:** the new consumer must continue working against an un-upgraded producer. This direction is especially important when deploying consumers first or during rolling deployments.

Proving one direction does not automatically prove the other. Use **deployment order**, rollback capability, and coexistence windows to decide which combinations must be verified.

## 2. The Evidence Chain from Commitment to Release Version

An auditable workflow must construct the following chain of links:

~~~mermaid
flowchart TD
    A["Groovy/YAML Contracts<br/>specific revision"] --> B["Tests generated by Spring Cloud Contract"]
    A --> C["Stubs/mappings generated from same contracts"]
    B --> D["Tested against producer build P"]
    C --> E["Stub artifact with coordinates/version"]
    D --> F{"Producer tests PASS?"}
    F -->|Yes| G["Allow publishing verified artifact"]
    F -->|No| X["Stop: insufficient evidence"]
    E --> H["Consumer tests with exact stub version"]
    G --> I["Release record"]
    H --> J{"Consumer tests PASS?"}
    J -->|Yes| I
    J -->|No| X
    I --> K["Evaluate scope, version matrix, and risks"]
    K --> L["Decision to declare compatibility"]
~~~

This is a **reference workflow**, not a pre-built pipeline provided out of the box by Spring Cloud Contract. Project teams must connect these steps using appropriate build configuration, artifact registries, CI, and release policies.

An evidence record should cover at least these groups:

| Evidence group | What must be verified | What this evidence **does not** prove |
| --- | --- | --- |
| **Agreed contracts** | Which requests/responses or messages are committed, who depends on them, which revision was tested | That any undescribed behavior is compatible |
| **Producer-side tests** | Tests generated from contracts pass against the producer build slated for release | That all production network, security, and data configs work |
| **Traceable stubs** | Stubs were generated/packaged from the exact verified contract and build, with version coordinates | That current consumers succeed against those stubs |
| **Consumer tests** | Corresponding consumers pass against the right stub version via Stub Runner or equivalent | That the real producer exhibits properties stubs do not simulate |
| **Deployment matrix** | Version pairs that must coexist are verified or controlled | That every historical version is safe |
| **Related operational conditions** | Remaining risks around auth, gateway, broker, event ordering, timeouts, etc., have separate evidence if impactful | That contract tests alone replace system/performance testing |

Crucial condition: **all evidence must point to one identifiable version**, or provide a clear explanation of the relationship between versions. A producer PASS report from yesterday's commit does not automatically apply to a new image built from today's commit.

## 3. Evidence #1: Contracts Accurately Describe Consumer Needs

Spring Cloud Contract verifies what is **declared**. Therefore, even before running tests, you need evidence that the contract set genuinely reflects integration needs.

A contract review should answer:

1. Which consumer uses this endpoint or message, and when?
2. Which method, path, parameters, headers, body, and HTTP status are mandatory?
3. Which data fields does the consumer read and use for decisions?
4. Which error cases or special states does the consumer handle?
5. Which values must be fixed, and which only need to satisfy a type/format?
6. Are there specific compatibility rules, such as tolerating extra fields or keeping enums unchanged?

Suppose consumer Checkout reads order status. Here is an **illustrative YAML DSL** contract, not a built-in default Spring Cloud Contract API:

~~~yaml
description: "Consumer can read paid order status"
name: get_paid_order
request:
  method: GET
  url: /api/orders/ORD-1001
  headers:
    Accept: application/json
response:
  status: 200
  headers:
    Content-Type: application/json
  body:
    id: ORD-1001
    status: PAID
~~~

The missing-order case also needs a separate contract if Checkout branches on errors:

~~~yaml
description: "Non-existent order returns a stable error code"
name: get_missing_order
request:
  method: GET
  url: /api/orders/ORD-9999
  headers:
    Accept: application/json
response:
  status: 404
  headers:
    Content-Type: application/json
  body:
    code: ORDER_NOT_FOUND
~~~

What to verify in review: Checkout uses **status = PAID** to display payment completion, and uses **404 + code = ORDER_NOT_FOUND** to handle missing orders. The contract does not need to constrain which Java classes, database, or cache the producer uses.

If the consumer also branches on CANCELLED, REFUNDED, or requires another field, the two contracts above are **insufficient** to declare compatibility for that entire behavior. A high count of passing tests cannot make up for omitted scenarios.

**Evidence to retain:** contract revision, reviewed diff, list of applicable consumers/scenarios, and schema assumptions or unknown-value handling rules.

## 4. Evidence #2: Real Producer Satisfies the Contracts

From Groovy/YAML contracts, **Spring Cloud Contract Verifier** generates producer-side tests. In the producer pipeline, run these tests against the source code and test configuration of **the build about to be released**.

For example, to run the `GET /api/orders/ORD-1001` test, the producer must have the right data state: in the test fixture, `ORD-1001` has status `PAID`. The contract for `ORD-9999` must ensure that record does not exist in the test context. Such data may be managed by a test base class, boundary mocks, database seeds, or fixtures; the contract does not dictate fixture implementation.

Passing tests are evidence that **the producer in the test environment produced responses matching the contracts**. To make the statement auditable, the report should be tied to:

- Producer commit or image digest.
- Revision of the contract set used to generate tests.
- Tool configuration version and test suite executed, if relevant to reproducibility.
- PASS/FAIL results; names of any skipped tests and reasons for skipping.
- Execution timestamp and link to the CI job/test report artifact.

For instance, a valid claim is “test `get_paid_order` PASSED on producer commit `abc123` in build 527”. Claiming “producer is compatible with all consumers” requires additional evidence from specific consumers.

**Never treat the following as a full PASS:** merely compiling successfully, generating tests without running them, skipping tests, fixtures replying directly with a stub while bypassing HTTP logic under test, or a PASS report from a different commit.

## 5. Evidence #3: Stubs Originate from the Right Contract and Build

Spring Cloud Contract generates mappings/stubs from contracts; stub artifacts can be packaged and published to an artifact repository for consumers to use via **Stub Runner**.

For a Maven/Gradle project, the following coordinates **illustrate** a stub artifact:

~~~text
groupId:    com.example
artifactId: order-service
version:    2.4.0
classifier: stubs
~~~

The consumer must know **which stub build** it tested against, not merely that the test started a stub server. To preserve the chain of evidence, the pipeline should prove:

1. Stubs were generated from the verified contract revision.
2. The build producing the stubs is tied to a specific producer version.
3. Post-test artifacts carry immutable identifiers (coordinates, version, and ideally checksum/digest).
4. Consumer tests fetch that exact artifact, avoiding silent drift to an unknown newer build during testing.

Some setups use dynamic versions like `latest` or plus (`+`) to explore stubs during development. For pre-release evidence, **pin the verified version** so re-running the same test is reproducible. Also distinguish a **successfully published** stub from a **consumer-tested** stub: these are two distinct milestones.

If the producer updates a contract without regenerating/publishing stubs, consumers may keep PASSing against the old stub. That state **does not prove** the new producer is compatible.

## 6. Evidence #4: Current Consumers Pass Against the Pinned Stub

Stub Runner helps consumers start or access published stubs to test HTTP calls without running the real producer inside the same test.

**Illustrative** configuration example for a test using a specific version (depending on your project's dependency versions and repository config):

~~~java
@SpringBootTest
@AutoConfigureStubRunner(
    ids = "com.example:order-service:2.4.0:stubs:8080",
    stubsMode = StubRunnerProperties.StubsMode.REMOTE
)
class CheckoutContractIntegrationTest {
    // Test sends request to stub server and verifies
    // consumer logic handling PAID status or ORDER_NOT_FOUND error.
}
~~~

For this example to work in a real project, configure appropriate repository URLs and dependencies, and point the consumer's HTTP client URL to the test-managed stub server. The Java snippet above is **not a complete runnable test**; it illustrates the principle of pinning artifact versions.

A consumer test is valuable when it actually calls the application's client/adapter and verifies **behavior the consumer cares about**. For example:

| Scenario | Evidence from consumer test |
| --- | --- |
| Receives 200 with status PAID | Checkout recognizes the order as paid and prevents duplicate payment |
| Receives 404 with code ORDER_NOT_FOUND | Checkout displays or handles missing order properly |
| Receives extra optional field if contract permits | Consumer parser does not fail on unknown fields |
| Producer introduces a new enum value | Consumer handles it safely or required version upgrade is tested |

If a test only checks “HTTP 200” without verifying how Checkout logic uses `status`, a PASS does not prove consumer functionality is compatible.

Conversely, a consumer passing against a stub also **does not prove** production connectivity to the real producer will succeed over TLS, gateways, authentication, rate limits, load balancers, or real data. Test those layers additionally when deployment risk demands it.

## 7. Evidence #5: Version Matrix Matching Deployment Order

In a microservices architecture, producers and consumers are rarely replaced at the exact same instant. Therefore, you must verify **version pairs that may coexist**, including transition windows and rollbacks.

Suppose:

- P1 is the currently running producer; P2 is the new producer.
- C1 is the currently running consumer; C2 is the new consumer.
- P2 adds field `paymentState` while **retaining** `status` to serve C1.
- C2 reads `paymentState`, while falling back to `status` if needed when talking to P1.

Illustrative verification matrix:

| Deployment pair | Why it must be tested | Outcome to mark “supported” |
| --- | --- | --- |
| C1 ↔ P1 | Baseline state before upgrade | Verified baseline tests |
| **C1 ↔ P2** | Producer upgrades first | C1 still works with P2 behavior |
| **C2 ↔ P1** | Consumer upgrades first or producer rolls back | C2 handles P1 contract |
| C2 ↔ P2 | Target state after both upgrade | C2 properly handles P2 behavior |

Never mark a cell PASS just because other cells PASSED. If deployment plans never allow C2 to run against P1 and rollback mechanics also exclude that pair, you may mark that cell **unsupported** with explicit deployment constraints. This is a versioning decision that must be documented publicly.

For contract-breaking changes, a typical transition strategy is:

1. Producer adds new behavior while retaining old behavior during the transition window.
2. Producer tests and publishes stubs for behavior still used by older consumers.
3. New consumers are tested against the producer versions they may encounter.
4. Only after confirming no consumer depends on old behavior is removal considered under versioning/deprecation policy.

Adding a field is not automatically compatible: a consumer using a strict deserializer might reject unknown fields. Likewise, a new enum value can break a consumer even though the JSON type remains string. Test evidence must reflect these distinctions.

## 8. For Asynchronous Messages, What Evidence Is Needed?

Spring Cloud Contract also supports **message-based** contracts. Here, the integration boundary is the emitted/received message, not an HTTP status code.

Example payload of a business event:

~~~json
{
  "eventType": "ORDER_PAID",
  "orderId": "ORD-1001",
  "occurredAt": "2026-11-24T04:00:00Z"
}
~~~

This is illustrative data for discussing evidence, not complete message contract DSL syntax. Real contracts must describe the trigger scenario, message type, headers/destination if they are part of the committed interface, payload, and data rules used by the consumer.

For the `ORDER_PAID` event, cross-check:

- **Producer:** contract-generated tests verify the emitted message has `eventType`, `orderId`, and valid timestamp format.
- **Stub/message test:** consumer receives the contract-compliant sample message and tests state update logic or required idempotency.
- **Schema compatibility:** field names, types, enum values, tolerance for new or missing fields, and event versioning policies are checked.
- **Operational integration:** if the consumer relies on ordering, retries, duplicate delivery, dead-letter queues, or delivery guarantees, verify those properties with appropriate broker/infrastructure tests or operational evidence.

**A contract-matching payload alone does not prove the broker always delivers in order or exactly once.** Operational guarantees must be evaluated at the layer capable of verifying them.

## 9. Using CI as an Evidence Gate

A reference CI pipeline can be organized as follows:

~~~mermaid
sequenceDiagram
    participant R as Contracts/Repository
    participant P as Producer CI
    participant A as Artifact Registry
    participant C as Consumer CI
    participant G as Release Gate
    R->>P: Pin contract revision
    P->>P: Generate and run producer tests
    alt Producer tests fail
        P-->>G: BLOCK, report discrepancy
    else Producer tests pass
        P->>A: Publish pinned stub version
        A->>C: Consumer tests use that stub
        C->>C: Run integration scenarios
        C-->>G: Report PASS/FAIL + version
        G->>G: Check matrix and open risks
    end
~~~

In an organization, pipelines may span multiple repositories; triggering consumer CI from new artifacts, awaiting results, and aggregating evidence are responsibilities of the CI/CD process.

Example **pipeline pseudocode**, not runnable verbatim Jenkins/GitHub Actions syntax:

~~~yaml
producer_pipeline:
  contract_revision: "contracts@c12abc"
  source_revision: "producer@p34def"
  steps:
    - generate_contract_tests
    - run_producer_contract_tests
    - publish_versioned_stubs_if_tests_pass
  outputs:
    - producer_test_report
    - stub_artifact_coordinates
    - stub_checksum

consumer_pipeline:
  source_revision: "checkout@a56bcd"
  stub_version: "com.example:order-service:2.4.0:stubs"
  steps:
    - fetch_exact_stub_version
    - run_stub_runner_integration_tests
  outputs:
    - consumer_test_report

release_gate:
  require:
    - producer_contract_tests_pass
    - stub_matches_verified_build
    - required_consumers_pass_with_exact_stub
    - required_version_pairs_approved
    - open_breaking_changes_resolved_or_explicitly_accepted
~~~

Release gates must **fail closed** on mandatory requirements: missing reports, FAILing consumer tests, missing artifacts, or mismatched versions must never default to PASS. If a consumer is granted an exception, the exception must specify the approver, reason, scope, expiration, and risk mitigations.

### What should be pinned in CI?

| Component | How to attach evidence |
| --- | --- |
| Producer source | Commit SHA and build ID/image digest |
| Contracts | Commit/revision or checksum of contract set |
| Generated tests | Build logs and list of executed tests |
| Stubs | Artifact coordinates, version, and checksum |
| Consumer source | Consumer commit and version |
| Consumer test run | Job URL/ID, result, stub version used |
| Release decision | List of supported version pairs, scope, and exceptions |

Everything does not have to live in one physical file. It can reside in CI metadata linked via a release record, provided an auditor can **retrieve the exact data at decision time**.

## 10. Example Pre-Release Evidence Record

Suppose the Order API team prepares to deploy 2.4.0, while Checkout runs 1.9.0. A release record can be stored as JSON like this:

~~~json
{
  "producer": {
    "service": "order-service",
    "version": "2.4.0",
    "commit": "p34def",
    "buildId": "527"
  },
  "contracts": {
    "revision": "c12abc",
    "coveredScenarios": [
      "get_paid_order",
      "get_missing_order"
    ]
  },
  "producerVerification": {
    "result": "PASS",
    "ciRun": "producer-ci/527"
  },
  "stub": {
    "coordinates": "com.example:order-service:2.4.0:stubs",
    "checksum": "artifact-sha256-recorded-by-ci"
  },
  "consumerVerification": [
    {
      "service": "checkout",
      "version": "1.9.0",
      "result": "PASS",
      "ciRun": "checkout-ci/814",
      "stubVersion": "2.4.0"
    }
  ],
  "compatibilityClaim": {
    "supportedPair": "checkout 1.9.0 -> order-service 2.4.0",
    "scope": "GET order: paid and not-found scenarios",
    "unverified": [
      "Checkout flows not included in these contracts",
      "Production gateway and network conditions"
    ]
  }
}
~~~

**Note:** this is a **team-designed record template**, not a file generated by default by Spring Cloud Contract. The commit IDs, job IDs, and checksum here are hypothetical. In real systems, checksums must be authentic artifact hashes, not descriptive strings as shown in the example.

This record is clear enough to support claims about **the two listed GET scenarios** for the Checkout 1.9.0 / Order API 2.4.0 pair. It is not sufficient to declare that the entire API, every consumer, or every business flow is compatible.

## 11. Misleading "Evidence" Signals

| Signal that looks sufficient | Why it falls short | How to fix |
| --- | --- | --- |
| Producer build SUCCESS | Contract tests might not have run | Record executed test report and PASS status |
| Contract tests PASS without commit info | Unclear whether tests ran on release build or another | Bind test run to immutable commit/build |
| Consumer tests PASS with latest stub | Re-running may resolve a different artifact | Pin artifact/version/checksum |
| New stub published | No proof consumers can handle it | Run real consumer tests with matching stub |
| Producer and consumer both PASS at different revisions | Both may be verifying inconsistent contracts | Cross-check revisions, stub source, and builds |
| One consumer PASSES | Another consumer may use different fields or error codes | Enumerate each supported consumer |
| Tests with stub PASS | Stubs do not simulate real infrastructure and live data | Add integration/e2e/operational tests when needed |
| JSON changed while schema stays valid | Consumers may depend on field names, enums, or semantics | Check contracts against business behavior |
| Tests lack meaningful assertions | Test runs yet fails to catch real consumer bugs | Verify how consumer interprets responses |

An especially dangerous failure mode is **stub drift**: the real producer changed behavior, yet consumer CI still uses an old stub artifact and keeps PASSing. Enforcing provenance and version alignment across contracts, producers, and stubs reduces this risk.

## 12. Release Decision: PASS, Scoped, or BLOCK?

Recommended decision guide:

| Situation | Decision to make |
| --- | --- |
| Contracts reviewed; producer tests PASS; stubs match build; required consumers PASS; deployment pairs checked | Can declare **compatible within verified scope** |
| Producer tests PASS yet no consumer tests ran with new stub | **Insufficient evidence** for that consumer; await results or record explicit exception |
| Consumer tests PASS yet producer contract tests FAIL | **BLOCK** producer release for failing its commitment |
| Contracts modified after tests ran | Old tests are stale for the new revision; **re-run** affected steps |
| Producer adds new enum and consumer fails to handle it | **Incompatible** with that consumer; fix consumer, adjust rollout, or version interface |
| Functional tests PASS yet gateway/auth changes remain untested | Declare compatibility only within contract scope; add integration evidence before rollout if real traffic is affected |

“Safe to declare” still does not equate to an absolute zero-bug guarantee. Announcements should state **versions, scenarios, consumers, test results, and known limitations**.

### When an urgent release is needed despite missing evidence

If process allows accepting risk, explicitly document:

1. Which evidence is missing and why.
2. Affected producer–consumer pair.
3. Approver and deadline to complete missing verification.
4. Post-deployment monitoring, rollout-halt criteria, and rollback plan.

Never flip a FAIL/UNKNOWN status to PASS just to meet a release deadline. Exception decisions must be **clearly separated from full compatibility verification**.

## 13. Scenario Exercises

**Scenario A — Build and stub come from different sources.**

Order API producer 2.4.0 is built from commit P2 and passes contract tests. Consumer Checkout passes against stub 2.3.0. A team member proposes announcing “Checkout is compatible with Order API 2.4.0”.

- What evidence already exists?
- What evidence is missing?
- What must change in CI for the conclusion to be reproducible?

**Hint:** The producer proved the tested build satisfies its contracts, yet the consumer has not been verified against the corresponding **2.4.0 stub**. You must publish/identify the exact stub from the verified build, re-run consumer tests with that stub, and cross-check contract revisions.

**Scenario B — Potentially breaking change.**

P2 removes `status` and returns only `paymentState`. New producer tests PASS, while consumer tests against stub P2 FAIL because Checkout 1.9.0 still reads `status`.

- Can P2 be called “backward compatible” with Checkout 1.9.0?
- Propose at least one rollout strategy avoiding downtime.

**Hint:** Compatibility cannot be declared for a failing pair. Keep `status` alongside `paymentState` during a transition window, or upgrade Checkout first to read both fields before retiring the old field per agreed process.

**Scenario C — Event contract PASSES yet consumer loses/corrupts data.**

The `ORDER_PAID` payload is valid, yet the broker delivers duplicate events causing the consumer to credit funds twice.

- What did the contract test prove?
- What additional verification or commitment is needed?

**Hint:** The contract test proved the message shape/content for the declared scenario; it did not test duplicate delivery conditions. The consumer needs an idempotency strategy and tests matching the real system's delivery guarantees.

## 14. Checklist Before Declaring Compatibility

- [ ] Claim explicitly states producer–consumer version pair and verified behavior scope.
- [ ] Groovy/YAML contract set reflects behaviors consumers truly depend on, including critical error branches.
- [ ] Contract revision is traceable and has not been altered after tests without re-running.
- [ ] Producer-side generated tests **actually ran and PASSED** against the release build/commit.
- [ ] Stubs were generated and published from the exact verified contract/build, with a pinned version.
- [ ] Consumer tests use the exact stub version and verify application logic, not just context startup.
- [ ] Version pairs required for rollout and rollback are identified, verified, or intentionally excluded.
- [ ] Schema, enum, HTTP status, header, and semantic changes are evaluated for breaking risk.
- [ ] Remaining auth/gateway/broker/timeout/production risks are addressed with appropriate evidence when needed.
- [ ] CI reports, artifact sources, scope, limitations, and exceptions are linked in the release record.
- [ ] If mandatory evidence is missing, the release gate reports BLOCK/UNKNOWN or records a transparent exception.

**Core takeaway:** In Spring Cloud Contract, producer tests, stubs, and consumer tests form an **evidence chain**, not three disconnected checkboxes. Only declare compatibility when the claim traces directly back to **specific contracts, a specific build, specific stubs, specific consumers, and specific test results**. The announced scope must be equal to or narrower than what was actually verified.
