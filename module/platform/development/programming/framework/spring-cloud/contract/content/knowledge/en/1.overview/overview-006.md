# How Do Contracts, Generated Tests, and Stubs Relate to Each Other?

In a multi-service architecture, a **producer** (provider) implements an API or emits messages, while a **consumer** (caller/subscriber) depends on that behavior. If the producer changes a path, status code, JSON structure, or event content without the consumer knowing, the system can fail even though each service still passes its own unit tests.

**Spring Cloud Contract** addresses this by using a single contract definition as input for two complementary activities:

1. **Generating producer-side tests** to check the contract against the providing application's real behavior.
2. **Generating stubs** so the consumer can test interactions against a simulated version of producer behavior, typically launched via **Stub Runner**.

Both outputs originate from the contract, yet they run on different sides and answer different questions. Understanding this relationship is the foundation before learning Groovy/YAML DSL, Contract Verifier, WireMock, Stub Runner, and CI integration.

## 1. Three Concepts, Three Responsibilities

| Component | Nature | Who Uses It and Purpose | What Is **Not** Guaranteed by That Component Alone |
| --- | --- | --- | --- |
| **Contract** | Specification of an expected interaction: HTTP request/response or message input/output; written in Groovy or YAML DSL. | Producer and consumer agree on behavior meaningful to the consumer. | Having a contract file alone does not prove the current program implements it correctly. |
| **Generated producer test** | Test code generated by Spring Cloud Contract Verifier from the contract. | Runs against the producer implementation to detect mismatched behavior. | Does not test every behavior outside the scenarios described in the contract. |
| **Stub** | Simulation of HTTP responses or messaging behavior generated from the contract. For HTTP, typically WireMock mappings. | Consumer runs tests without needing a live running producer implementation. | A stub is not the real producer application and does not itself prove the producer implemented things correctly. |

**Stub Runner** is not a fourth artifact type: it is the tool that **locates, downloads, and runs packaged stubs** so consumer tests can call into them. Consumer-side tests are usually written by the consumer team; Spring Cloud Contract does not automatically generate all of the consumer's business tests from the contract alone.

## 2. One Contract Drives Two Verification Branches

~~~mermaid
flowchart TD
    C["Groovy / YAML Contract"] --> T["Generate producer-side tests"]
    C --> S["Generate stubs from the same contract"]
    T --> P["Run tests against producer implementation"]
    P --> G{"Producer tests pass?"}
    G -->|No| F["CI fails, fix code or revisit contract"]
    G -->|Yes| A["Allow publishing stubs artifact"]
    S --> A
    A --> R["Stub Runner downloads and starts stub"]
    R --> U["Consumer runs tests over HTTP / messaging"]
~~~

The flow above represents **the CI process you should set up**: only publish a trusted stub version after producer tests for the corresponding contract have passed. The tool can still generate stub files during a build even before verification completes; **restricting publication until tests pass is a pipeline configuration responsibility**.

You can read the diagram through three questions:

- **What was agreed upon?** → Read the contract.
- **Does the producer actually implement what was agreed upon?** → Run generated tests on the producer.
- **Does the consumer handle that behavior properly?** → Run consumer tests against stubs provided by Stub Runner.

These are two complementary checks, not two duplicates of the same test.

## 3. Running Example: Reading Order Status

Suppose **Order Service** is the producer and **Billing Service** is the consumer. Billing needs to call:

~~~http
GET /api/orders/42
~~~

The behavior both teams agree on is:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":42,"status":"PAID"}
~~~

A minimal HTTP contract in **Groovy DSL** can live in the producer's contracts directory, for example at `src/test/resources/contracts/orders/get_paid_order.groovy`:

~~~groovy
import org.springframework.cloud.contract.spec.Contract

Contract.make {
    description 'Returns paid order 42'

    request {
        method 'GET'
        url '/api/orders/42'
    }

    response {
        status 200
        headers {
            contentType(applicationJson())
        }
        body(
            id: 42,
            status: 'PAID'
        )
    }
}
~~~

This specification states that upon receiving **GET /api/orders/42**, the producer must return **200** with a JSON body containing **id = 42** and **status = PAID**. It does not by itself define the entire orders API, non-existent IDs, or other statuses. Those important scenarios need their own contracts or appropriate conditional variants.

Spring Cloud Contract also supports writing contracts in **YAML DSL**. Choosing Groovy or YAML affects how rules are authored and expressed, not the core meaning: from the specification, the tool produces artifacts to verify the producer and simulate for the consumer. In a real project, each DSL's syntax and capabilities must match the Spring Cloud Contract version in use.

### 3.1. Branch A — Generated Tests Protect the Producer

When integrating the Spring Cloud Contract plugin into the producer build, Contract Verifier reads contract files and generates tests during the appropriate Maven/Gradle phase. For the example above, the generated test has a meaning close to the **illustrative** snippet below (exact code depends on test mode, base test configuration, and version):

~~~java
// Illustrates the assertions that the generated test will perform.
given()
    .get("/api/orders/42")
.then()
    .statusCode(200)
    .contentType("application/json")
    .body("id", equalTo(42))
    .body("status", equalTo("PAID"));
~~~

This test must execute **against the real producer at the interface layer configured for testing**, such as an HTTP server, MockMvc, or WebTestClient. The producer team must configure the test base class, Spring context, and required data so the endpoint can produce the described response. Never edit the generated test file directly, as the next generation pass will overwrite it.

If producer code renames `status` to `state` while the contract still requires `status`, the test step must fail. Likewise, changing `200` to `204`, altering the path, or dropping a required field will cause the corresponding tests to fail as long as they remain in the tested contract set.

**Key takeaway:** generated tests compare the contract against the producer's **real implementation**. They do not exercise the consumer's HTTP client calls and do not use stubs to impersonate the producer during this verification step.

### 3.2. Branch B — Stubs Help the Consumer Test Independently

From the same contract, the build can generate a **WireMock** mapping for HTTP. A simplified view of that mapping looks like this:

~~~json
{
  "request": {
    "method": "GET",
    "url": "/api/orders/42"
  },
  "response": {
    "status": 200,
    "headers": {
      "Content-Type": "application/json"
    },
    "jsonBody": {
      "id": 42,
      "status": "PAID"
    }
  }
}
~~~

This is an **illustration of stub semantics**, not a guarantee that the tool-generated JSON file has the exact same property names, formatting, or structure. When a request matches the method and path, WireMock returns the corresponding response. The consumer can test its HTTP client code, data mapping, status handling, and business flow without starting Order Service.

Typically, the producer packages mappings and stub resources into an artifact with the **stubs** classifier (for example, Maven coordinates `com.example:order-service:1.2.3:stubs`), then installs it into the local repo or publishes it to a shared artifact repository. **The stub artifact must carry the verified producer/contract version**, so teams can trace the exact set of expectations.

In Billing Service's tests, **Spring Cloud Contract Stub Runner** can retrieve that artifact and run an HTTP stub server on a specified port:

~~~java
// Illustrative configuration in a consumer test.
@SpringBootTest(properties = "order.api.base-url=http://localhost:8089")
@AutoConfigureStubRunner(
    ids = "com.example:order-service:1.2.3:stubs:8089",
    stubsMode = StubRunnerProperties.StubsMode.LOCAL
)
class BillingOrderClientTest {
    @Autowired
    OrderClient orderClient;

    @Test
    void docDuocTrangThaiDonHangDaThanhToan() {
        OrderDto order = orderClient.getOrder(42L);

        assertThat(order.getStatus()).isEqualTo("PAID");
    }
}
~~~

The example assumes the consumer already has `OrderClient`, `OrderDto`, test dependencies, and the `order.api.base-url` property pointing the client to the stub. **LOCAL** requires the stubs artifact to already be present in the local Maven repository; in CI, many teams switch to fetching artifacts from a remote repository with appropriate Stub Runner settings. Artifact name, version, and port must match the test environment.

**Who writes consumer tests?** The Billing team writes or maintains tests asserting that their client and business flow interpret the response properly. Stub Runner only provides a simulated service matching the contract; it does not know all of Billing's business requirements to auto-generate those assertions.

## 4. Why Are Both Producer Tests and Stubs Needed?

Consider the following three scenarios:

| Situation | Producer Test from Contract | Consumer Test via Stub | Meaning |
| --- | --- | --- | --- |
| Producer accidentally renames `status` to `state`, old contract still exists. | **Fails** because actual response no longer matches. | May **still pass** with the old stub having `status`. | Producer-side CI gate catches the contract breach; looking only at consumer tests is not enough. |
| Consumer writes a buggy parser, e.g., reading `paymentStatus` instead of `status`. | May **pass** because producer implements it properly. | **Fails** when receiving the stub containing `status`. | Stub catches the integration bug in consumer code. |
| Both sides agree to update the contract and implement the same change. | Passes with new contract if producer implements it properly. | Passes with new stub if consumer handles it properly. | Both sides align on the new version, yet older running consumers still need consideration. |

A stub generated from a contract **does not by itself become proof** that the producer obeys the contract. If the producer has not run or passed its generated tests, the stub reflects only what was **declared**, which may differ from reality. Conversely, the producer passing tests does not mean every consumer uses the output correctly.

The relationship between the components can be remembered as a chain:

> **Contract is the commitment → generated tests verify the commitment on the producer → stubs replay the commitment for the consumer → consumer tests verify how the commitment is used.**

## 5. What Happens When a Contract Changes?

Suppose Billing reads the `status` field. The producer wants to rename it to `state`. There are two easily confused possibilities:

**Case 1 — Producer changes code while keeping the existing contract:** generated producer tests catch the discrepancy and block the build if the pipeline requires green tests before release.

**Case 2 — Producer simultaneously edits or deletes the old contract so only the new field remains:** tests generated from the new contract can still pass. **That does not prove backward compatibility** for a Billing deployment still reading the old field. To catch breaking changes, teams must preserve and run active contracts for supported consumers alongside versioning policies, transition windows, or legacy API support.

This leads to three principles when changing an API:

1. **Review impact with consumers before changing a contract**: method, path, HTTP status, headers, required fields, data types, formats, and error behavior.
2. **Maintain contracts still relied upon by consumers**: a change can be valid for a new consumer while breaking an older consumer. Tests only protect what remains specified and executed.
3. **Publish artifacts with controlled versions**: consumer tests should target the stub version corresponding to the producer the system will integrate with. In CI, account for artifact updates and traceability, avoiding blind reliance on "latest."

Adding an optional JSON field generally causes less impact than deleting or renaming a required field, yet **compatibility always depends on the contract and how the consumer actually parses responses**. A consumer using a strict parser can still break when the producer adds a field.

## 6. Where Each Piece Fits in CI/CD

A sound workflow can be organized as follows:

1. **Propose or update the contract**: producer and consumer agree on the interaction. Contracts live alongside producer code or in a dedicated contracts repo with a clear sync workflow.
2. **Generate and run producer tests**: the Contract Verifier plugin creates tests; the build executes them against the producer application and prepared test data. If they fail, fix the implementation or renegotiate the specification.
3. **Build and publish stubs**: after passing the test gate, publish the stubs artifact with a specific version to the artifact repository.
4. **Run consumer tests**: Stub Runner fetches the artifact, starts the stub, and the consumer's HTTP client / business-flow tests call the stub address.
5. **Manage changes and releases**: CI marks builds failed when relevant tests fail; responsible teams decide whether to preserve compatibility, introduce a new API version, or coordinate consumer upgrades.

| Pipeline Stage | Primary Input | Outcome to Observe |
| --- | --- | --- |
| Producer build | Contract files + producer code + test config | Generated producer tests **PASS/FAIL** |
| Publish stubs | Contracts + passing build result | `stubs` artifact with the right version |
| Consumer build | Consumer code + stubs artifact + consumer tests | Consumer tests with Stub Runner **PASS/FAIL** |
| Deeper integration checks | Real services, real data, and real infrastructure | Checks issues not covered by contract tests/stubs |

Note: testing via stubs catches API expectation drift early and reduces reliance on shared service environments. It **does not completely replace** integration tests or end-to-end tests for authentication, networking, deployment config, real data, or unspecified behaviors.

## 7. Do Message Contracts Follow the Same Idea?

**Yes, in principle.** Beyond HTTP request/response, Spring Cloud Contract can also specify a triggering input and the producer's **output message** (destination, headers, payload, etc.). In that setup:

- **Generated producer tests** verify the producer's actual message-emitting behavior according to the contract and messaging test configuration.
- **Messaging stubs** help the consumer test message-receiving/processing flows through supported message broker/test binding integrations.
- **Stub Runner** and messaging integrations bring stub definitions into the test environment, though messages cannot be treated like a standard WireMock HTTP response.

Example: when order creation completes, the producer must emit an `OrderCreated` event with `orderId` and `eventType`. The contract describes this expectation; producer tests check emission; the consumer uses simulated messages to verify event handling. Verifying the real broker, transactions, and production operational behavior still requires other appropriate tests.

## 8. Common Misconceptions

**"Having contracts guarantees API compatibility."** No. A contract is only a specification; generated tests must run against the producer and active contracts must be maintained. An API can also break compatibility in scenarios not covered by contracts.

**"A stub is a miniature producer, so green consumer tests mean the real implementation definitely passes."** No. A stub only answers according to configured interactions. A stub can pass even when the real producer has drifted from the contract, especially if producer verification is skipped or the stub is stale.

**"Spring Cloud Contract generates the consumer's business tests too."** Usually no. The tool generates producer verification tests and stubs; the consumer must still assert how its own client/application handles received responses or messages.

**"A single contract for HTTP 200 covers the whole API."** Not enough if consumers also depend on 400, 404, 409, 500, timeouts, varying values, or messaging flows. Contracts should capture high-value, high-compatibility-risk behaviors, combined with other testing layers.

**"Just updating the contract to match new code fixes the build failure."** That can break the API for existing consumers. Identify who still depends on the contract and establish a migration strategy before accepting the change.

## 9. Short Hands-On Exercise to Test the Relationship

Using the Order Service and Billing Service example, practice the following sequence on a project already configured with Spring Cloud Contract:

1. Write a GET order contract returning JSON with `id` and `status`; generate tests and stubs via the build plugin.
2. Implement the endpoint matching the contract; run producer tests and confirm they pass.
3. Publish the stubs artifact from the passing build; in Billing, configure Stub Runner and write a test confirming it reads status `PAID`.
4. Change only producer code from `status` to `state`, **keeping the contract unchanged**, then re-run generated producer tests: expect **FAIL**.
5. Revert the producer, then modify consumer code to read `state`: expect consumer tests against the old stub to **FAIL**.
6. Discuss how to evolve the contract for a new version while protecting old consumers, then put both test suites into CI.

The desired outcome is not just two green tests. More importantly, you should be able to explain **which test fails when which side is wrong**, where stubs come from, why producer verification must run before publishing stubs, and why deleting old contracts can blind you to breaking changes.

## 10. Knowledge Self-Check

- When generated producer tests fail while consumer tests against the stub still pass, what possibilities should you check first? Hint: compare the real implementation, the active contract, and the stub version.
- If the consumer receives a response matching the template yet processes it wrongly, which test layer should catch it? Hint: assertions in consumer tests.
- Is Stub Runner responsible for proving that the real producer works properly? Why or why not?
- If both producer tests and consumer tests against a new contract pass, what must you check before claiming the upgrade is compatible with existing consumers?

**Connecting the ideas:** The contract describes expected behavior, generated tests check that behavior against the producer, and stubs reproduce that behavior for independent consumer testing. Spring Cloud Contract's strength comes from maintaining **a single specification source**, running **the right tests on each side**, and controlling **contract versions** in continuous integration.
