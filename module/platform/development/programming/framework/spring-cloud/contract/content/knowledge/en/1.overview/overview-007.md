# Verification Flow for a Change from Producer to Consumer

## 1. Why Is End-to-End Verification Across the Boundary Needed?

In a microservices architecture, a small change in an API-providing service can break a service consuming that API. For example, **Inventory Service** (producer) returns stock information to **Checkout Service** (consumer). The producer renames a JSON field from **available** to **inStock** because the new name feels clearer. The endpoint still returns HTTP 200 and the producer's build can stay green, yet the consumer may misread the stock status and reject a valid order.

**Spring Cloud Contract (SCC)** helps express communication behavior as an executable *contract*: which requests should be accepted, which responses must be returned, or which messages must be emitted. From a contract, the system can:

- **Generate tests for the producer** to verify that the real implementation does what was promised.
- **Generate stubs** so the consumer can test integration against a version of the expected behavior without running the real producer.
- **Integrate both checks into CI** to block incompatible changes before release.

This topic focuses on **the path of a change**: from the intent to modify an API, keeping or updating the contract, producer verification, building and distributing stubs, running consumer tests, through to the deployment decision. The same mindset applies to both HTTP contracts and messaging contracts.

### Learning Outcomes

After this lesson, you can explain:

1. How the producer and consumer verify **different assertions** on opposite sides of the contract.
2. At which stage a breaking change is caught if only code changes, or if both code and contract change.
3. Why passing producer tests **are not enough** to conclude existing consumers remain compatible.
4. How to combine contracts, generated tests, stub artifacts, Stub Runner, and CI quality gates into a single workflow.
5. How to roll out risky API changes using an expand first, migrate second, then contract strategy.

## 2. Participating Components

| Component | Role | Question It Answers |
|---|---|---|
| **Producer** | Exposes an HTTP endpoint or emits messages. | Does the new implementation continue to satisfy the commitment? |
| **Consumer** | Calls the endpoint or processes messages. | Does my client/handler work with the expected behavior? |
| **Contract (Groovy/YAML DSL)** | Describes requests, responses, headers, body, status, or input/output messages. | What behavior do both sides agree on? |
| **Generated producer test** | Test generated by SCC from the contract and run against real producer code. | Does producer code match the contract? |
| **Stub artifact** | Stubs generated from contracts, usually packaged as a JAR with classifier **stubs**. | Where can the consumer test the committed behavior? |
| **Stub Runner** | Downloads stubs, starts an HTTP stub server, or integrates with the appropriate messaging mechanism. | Do consumer tests have a stable simulated environment? |
| **CI/CD** | Builds, runs tests, distributes candidate stubs, and aggregates results. | Has the change passed the verification gates for release? |

A contract does not automatically test the entire system. It only protects **the behaviors that have been described and actually executed in tests**. A stub is a behavioral simulation based on the contract, not a full producer instance with a real database, business state, and downstream dependencies.

## 3. Verification Flow Map

~~~mermaid
flowchart TD
    A["Producer proposes API/message change"] --> B["Identify affected consumers and contracts"]
    B --> C["Keep or update contract"]
    C --> D["SCC generates tests for producer"]
    D --> E{"Generated tests + related tests pass?"}
    E -- "No" --> F["Fix implementation or invalid contract; block change"]
    E -- "Yes" --> G["Package and provide candidate stub"]
    G --> H["Consumer runs tests with Stub Runner using exact candidate version"]
    H --> I{"Consumer tests pass?"}
    I -- "No" --> J["Preserve compatibility, add transition phase, or coordinate consumers"]
    I -- "Yes" --> K["Evaluate remaining required checks and allow release"]
    F --> C
    J --> C
~~~

There are **two complementary layers of evidence**:

- **Producer verification:** the current implementation satisfies the contract under test. If code changes while the old contract stays intact, generated tests are usually the first place that catches breaking the committed behavior.
- **Consumer verification:** actual consumer code can use the stub generated from the candidate producer version's contract. If the producer modifies **both code and contract** to reflect a new interface, producer tests may stay green; consumer tests running with the **new stub** are what have a chance to detect that old clients do not understand the new interface.

The key requirement is that the consumer must be tested against the **exact artifact of the candidate version**. A test suite passing because it still pulls an old stub from cache or uses a prior release does not prove the new change is safe.

## 4. Running Example: Renaming a Response Field

Suppose Checkout Service calls:

~~~http
GET /api/inventory/SKU-123 HTTP/1.1
Accept: application/json
~~~

The current producer version returns:

~~~http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "sku": "SKU-123",
  "available": true,
  "quantity": 12
}
~~~

Checkout relies on **available = true** to allow customers to place orders. The Inventory team wants to change it to:

~~~json
{
  "sku": "SKU-123",
  "inStock": true,
  "quantity": 12
}
~~~

This is a **potentially breaking** change for consumers reading the **available** field. The fact that the response is still valid JSON and status is still 200 does not guarantee compatibility. In a Java DTO with a primitive **boolean available** field, data missing that field can even deserialize to **false**, making the bug manifest as a wrong business decision.

Before editing code, identify which consumers use this field, which consumer versions remain active, and which contracts check it. From here, two scenarios are especially important.

## 5. Step A — Define the Contract for Current Behavior

In a producer project integrated with Spring Cloud Contract, an HTTP contract typically lives under **src/test/resources/contracts/**. For example, **inventory/shouldReturnInventory.groovy**:

~~~groovy
import org.springframework.cloud.contract.spec.Contract

Contract.make {
    description 'Return inventory for Checkout Service'

    request {
        method GET()
        url '/api/inventory/SKU-123'
    }

    response {
        status OK()
        headers {
            contentType(applicationJson())
        }
        body(
            sku: 'SKU-123',
            available: true,
            quantity: 12
        )
    }
}
~~~

This contract expresses: when receiving a GET request to that specific path, the producer must return 200 with JSON containing the fields and values the verification cares about. It is one concrete behavioral example; a real product typically needs additional contracts or matchers for other scenarios such as non-existent SKUs, out-of-stock, unauthorized access, or dynamic data.

If the project chooses **YAML DSL**, the same behavior can be expressed in a YAML contract file:

~~~yaml
description: Return inventory for Checkout Service
request:
  method: GET
  url: /api/inventory/SKU-123
response:
  status: 200
  headers:
    Content-Type: application/json
  body:
    sku: SKU-123
    available: true
    quantity: 12
~~~

**Choose one format for each specific contract**, avoiding maintaining two equivalent Groovy/YAML files unintentionally. Matcher syntax and plugin configuration can vary by DSL and SCC version; keep them aligned with the Spring Cloud Contract version your project uses.

Details to lock down when writing a contract:

- Which **path, method, query params, headers, and request body** the consumer actually sends.
- Which **status, headers, and response body** the consumer depends on.
- Which values are **fixed examples**, and which need matchers or dynamic conditions.
- Which fields are required vs. optional; business semantics of the data, not just JSON types.
- Which error cases or edge cases can alter consumer behavior.

## 6. Step B — Generate and Run Producer-Side Tests

With **spring-cloud-contract-maven-plugin** or the corresponding Gradle plugin configured, SCC reads the contracts and generates tests to verify the producer. Depending on configuration, tests can use MockMvc, WebTestClient, or live HTTP; the project must configure a test base class/context for generated tests to invoke the real application and prepare test data.

Example Maven workflow on a developer machine:

~~~bash
# Run in a producer project configured with Spring Cloud Contract.
./mvnw clean verify

# Once producer tests pass, install the artifact and stubs into local Maven
# to test the consumer flow on the developer machine.
./mvnw install
~~~

Exact commands and generated file locations depend on build configuration. With Maven, you can inspect generated tests under **target/generated-test-sources/contracts/** and the stub artifact with the **stubs** classifier in the packaging output. In CI, the local install step is replaced by supplying the candidate stub via an artifact repository or pipeline workspace.

Suppose a developer changes the controller to return only **inStock** while **keeping the contract** requiring **available**. When SCC-generated tests run against the real producer, the response expectation is no longer met and the producer pipeline fails. This is an early stop: the code change broke an existing commitment.

Alternatively, the developer changes **both the controller and the contract** to **inStock**. Now producer tests can pass, because the code matches the **new** contract. That result does not answer the question: "Can an older deployed version of Checkout still read the response?" You must proceed to the consumer step.

> **Distinction:** Generated producer tests check **the producer against the current contract**; they do not automatically compare a new contract against all old contracts or all deployed consumers.

## 7. Step C — Package and Distribute the Candidate Stub

From HTTP contracts, SCC generates the corresponding stubs (typically WireMock-based). The artifact is commonly published in the Maven ecosystem as a JAR with the **stubs** classifier. An illustrative coordinate:

~~~text
groupId     = com.example
artifactId  = inventory-service
version     = 1.3.0-rc1
classifier  = stubs
~~~

This is the **stub of candidate producer** 1.3.0-rc1, not the stub of an already released production build. Common workflow:

1. Producer CI runs generated contract tests and related tests.
2. If successful, CI packages stubs from **the exact commit under test**.
3. The candidate stub is installed into the local repository within the same job, shared via pipeline artifacts, or published to a staging repository with appropriate access controls.
4. The consumer verification job fetches **that exact version/commit** and runs tests.
5. Only after all required quality gates pass is the producer permitted to promote or release.

Distinguish between **publishing an artifact for testing** and **releasing a stable version for users**. Candidate stubs may be pushed to a testing repository so teams can verify ahead of time; that does not mean the producer has been deployed to production.

When evaluating a specific change, **pin the candidate version** rather than using uncontrolled latest-version selectors like **+**. If Stub Runner accidentally fetches an old artifact, tests can produce a false green.

## 8. Step D — Consumer Testing with Stub Runner

The consumer does not need to start a live Inventory Service to test its HTTP client. **Spring Cloud Contract Stub Runner** can download the stub artifact and spin up a simulated HTTP server returning responses per the contract.

Checkout-side test example, assuming the consumer already has **InventoryClient** using Spring **RestClient** along with a Java DTO:

~~~java
// Illustrative consumer-side code: this class is used in production.
public record InventoryStock(String sku, boolean available, int quantity) {
}
~~~

~~~java
import org.springframework.web.client.RestClient;

public class InventoryClient {
    private final RestClient http;

    public InventoryClient(RestClient http) {
        this.http = http;
    }

    public InventoryStock findBySku(String sku) {
        return http.get()
                .uri("/api/inventory/{sku}", sku)
                .retrieve()
                .body(InventoryStock.class);
    }
}
~~~

Consumer integration test using **that exact InventoryClient**:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.cloud.contract.stubrunner.spring.AutoConfigureStubRunner;
import org.springframework.cloud.contract.stubrunner.spring.StubRunnerProperties;
import org.springframework.web.client.RestClient;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
@AutoConfigureStubRunner(
        ids = "com.example:inventory-service:1.3.0-rc1:stubs:8081",
        stubsMode = StubRunnerProperties.StubsMode.LOCAL
)
class InventoryClientContractTest {

    @Test
    void checkoutCanReadAvailabilityFromCandidateStub() {
        InventoryClient client =
                new InventoryClient(RestClient.create("http://localhost:8081"));

        InventoryStock stock = client.findBySku("SKU-123");

        assertThat(stock).isNotNull();
        assertThat(stock.sku()).isEqualTo("SKU-123");
        assertThat(stock.available()).isTrue();
    }
}
~~~

**Configuration breakdown:**

- The string **com.example:inventory-service:1.3.0-rc1:stubs:8081** specifies group, artifact, version, classifier, and HTTP stub port.
- **LOCAL** requires the artifact to already exist in local Maven; run the producer stub installation step before executing tests. Cross-environment CI typically uses **REMOTE** and configures an artifact repository to retrieve candidate stubs.
- Port **8081** is fixed so the example is easy to follow. In larger suites, let Stub Runner allocate ports dynamically and look up URLs via **StubFinder** to avoid port collisions.
- The test exercises the consumer's real HTTP client class. Simply firing a manual request at the stub and comparing raw JSON only proves the stub works, not that the consumer's deserialization and usage logic works properly.
- The example relies on Spring Framework's **RestClient**; on older versions, the consumer might use RestTemplate, WebClient, or whichever client the application uses. Choose compatible Spring Boot / Spring Cloud Contract versions and declare the Stub Runner test dependency.

With the **new** stub containing only **inStock**, the old consumer still looks for **available**. The test fails because the DTO does not receive the expected value. If the test still passes, check first whether it genuinely loaded stub **1.3.0-rc1** and whether the stub data reflects the new contract.

**Limitation:** Stub Runner verifies compatibility between the consumer and **the requests/responses described by the stub**. It does not replace integration tests with a live producer, databases, authentication, timeouts, performance, or scenarios not described in contracts.

## 9. What Outcomes Can the Same Change Produce?

| Change in Producer | Generated Producer Test | Consumer Test with Candidate Stub | Assessment |
|---|---|---|---|
| Edit code only, rename **available** to **inStock**; contract unchanged | **Red** because response no longer matches contract | Not even needed to catch this mismatch | Block change, fix code, or plan a contract change |
| Edit both code and contract to return only **inStock** | Can be **green** | **Red** if consumer still expects **available** and tests cover that behavior | Change breaks compatibility with current consumer |
| Keep **available**, add **inStock** during transition period | Must satisfy all maintained contracts | Both old and new consumers can be **green** | Safer evolution path, still verify assumptions about extra fields |
| Migrate consumer to read **inStock**, then delete **available** too early | Can be **green** against new contract | Upgraded consumer is green; un-upgraded old version can turn red | Only remove old field once active consumers are confirmed ready |

**Adding a field** is usually compatible with JSON clients that ignore unknown fields, though not always: a consumer configured with strict deserialization or exact structural checks can still fail. Safe decisions must be grounded in how consumers actually read data and which versions are running.

## 10. Safe Change Pattern: Expand → Migrate → Contract

To rename **available** to **inStock** without disruption, roll out in three phases:

**Phase 1 — Expand:** The producer returns both fields with consistent semantics. Keep the contract checking **available** and add a check for the new **inStock** field. Run producer tests and consumer tests against the expanded version's stub.

~~~json
{
  "sku": "SKU-123",
  "available": true,
  "inStock": true,
  "quantity": 12
}
~~~

**Phase 2 — Migrate:** Consumers update their clients to read **inStock** and deploy in the proper order. During this period, keep testing both un-upgraded and upgraded consumers against the corresponding stubs; use telemetry or deployed version metadata to determine who still depends on the old field.

**Phase 3 — Contract:** Only when no supported consumer depends on **available** anymore does the producer remove the old field and update contracts. Removal may require a new API version or an explicit deprecation policy depending on system commitments.

This pattern applies similarly to renaming endpoints, changing data types, changing error codes, adding required fields to requests, or renaming message fields. For required **request** fields, the producer must also support old clients not yet sending the new field during the transition period.

## 11. Integrating into CI/CD: The Quality Gates You Actually Need

A practical pipeline usually has at least three logical stages:

| Stage | Input | Passing Condition | Action on Failure |
|---|---|---|---|
| **Producer verification** | Producer code + candidate commit contracts | Generated contract tests and related tests pass | Block producer merge/release; report failure on PR |
| **Candidate stub handoff** | Contracts verified by producer | Stub artifact packaged with exact version/commit and retrievable by consumer | Block consumer step; fix packaging/artifact repo, do not treat as passing |
| **Consumer compatibility gate** | Supported consumer + exact candidate stub | Tests calling real client/handler and asserting dependent behavior all pass | Block rollout, renegotiate contract, or apply phased migration |

Illustrative job ordering independent of a specific CI system:

~~~text
Producer PR/commit
  └─ build + generated contract tests + producer tests
       └─ package candidate stub (group:artifact:version:stubs)
            └─ supply artifact to consumer CI
                 └─ run consumer contract/integration tests with candidate version
                      ├─ FAIL → mark change incompatible
                      └─ PASS → proceed to remaining gates and release workflow
~~~

Three operational notes:

1. **Link version/commit:** Log the artifact coordinate and commit SHA in both pipelines; the consumer job must receive the exact newly built stub. Avoid uncontrolled dynamic versions or stale caches.
2. **Define the set of consumers to test:** If there are multiple consumers, one passing consumer test does not represent all of them. Run a matrix of supported consumers/versions or a centralized compatibility pipeline.
3. **Release decision authority:** A contract failure does not necessarily mean the producer must keep an old API forever; it indicates that migration/versioning or release coordination is needed. CI policy must clearly state when breaking changes may be accepted.

If consumer tests only run **after the producer has gone to production**, this mechanism mostly detects incidents late. Its greatest value comes from testing the candidate artifact **before** deployment decisions.

## 12. How Does the Flow Change When Communicating via Messages?

With events or messages, the producer does not return a direct HTTP response. A contract can describe a triggering condition and an **outputMessage**, including destination, headers, and payload; on the consumer side, it can describe the input message to process.

For example, Inventory Service emits an event:

~~~json
{
  "eventType": "InventoryChanged",
  "sku": "SKU-123",
  "available": true
}
~~~

If the producer changes **available** to **inStock**, verification still spans both sides:

- **Producer:** Generated tests verify that the real application emits messages with the right payload/headers/destination per the contract, using the configured messaging environment/test base.
- **Consumer:** Tests trigger or receive messages from the appropriate stub/messaging support, pass them through the consumer's **real handler**, and verify the processing outcome.

Unlike HTTP, messaging tests require attention to the broker/test binder, destination/topic, keys, headers, serialization, schemas, ordering, and retry mechanisms. Do not treat auto-generated stub JSON as proof that every broker mechanism works properly. SCC supports message contracts, while triggering and integration specifics depend on the messaging stack your project uses.

For messages broadcast to multiple independent consumers, retaining old fields long enough is often especially important because the producer does not control when all consumers upgrade.

## 13. Common Implementation Pitfalls and Troubleshooting

| Symptom | Possibilities to Check | Resolution |
|---|---|---|
| Producer tests green even though code clearly changed response | Contract was edited alongside code; matchers too broad; contract omits key field | Inspect generated tests and contract expectations; add cases reflecting consumer needs |
| No generated tests found | Plugin not configured/bound to build lifecycle, contracts in wrong directory, wrong test base config | Check test generation logs, source sets, plugin config, and test runner |
| Consumer tests green against an old stub | Wrong coordinates/version, **+** resolved wrong version, stale artifact cache | Pin version/commit, log loaded stub, inspect artifact contents |
| Stub Runner fails to download stub | **stubs** JAR not packaged/installed/published or LOCAL/REMOTE mode mismatch | Check artifact coordinates, local repository, remote repository, and access permissions |
| Consumer test only compares JSON body and passes | Not calling real client/handler, not asserting downstream dependent data | Exercise real consumer code and assert business semantics |
| Tests green locally, red in CI | Different Spring/Java versions, fixed-port collision, different test data or artifacts | Align dependencies, isolate ports, pin artifacts and test environment |
| Both sides green yet production still fails | Contract does not describe the failing scenario, real network/security/broker config or real data differs | Add contracts for missing behavior and keep appropriate integration/E2E/observability checks |

When a failure occurs, trace in order: **which contract is in use → which generated producer test ran → which stub was published → which version Stub Runner actually loaded → which consumer code/test executed**. This chain separates behavioral bugs, build config errors, and artifact publishing mistakes.

## 14. Hands-On Exercise: Tracing a Breaking Change

Prepare two sample applications: **inventory-service** (producer) exposing a GET inventory endpoint and **checkout-service** (consumer) with a client reading stock status. Configure the SCC plugin on the producer and Stub Runner in consumer tests.

**Round 1 — Lock Down the Baseline Contract**

1. Write a GET contract for SKU-123 with **available: true**.
2. Run the build to generate producer tests; confirm tests pass and stubs are built.
3. Have the consumer use the baseline stub; assert that the client reads **available = true**.

**Round 2 — Catch Code Drift**

1. Change only the producer implementation to return **inStock**.
2. Keep the contract unchanged and re-run generated producer tests.
3. Observe the red test and compare the expected field with the actual body.

**Round 3 — Catch Cross-Service Drift**

1. Update the contract to return only **inStock**, matching the producer code.
2. Run producer tests until green, and package the stub with a **new candidate version**.
3. Run the old consumer's tests against the **candidate stub**, without reusing the v1 stub.
4. Observe the consumer assertion failing even though producer tests pass.

**Round 4 — Compatible Migration**

1. Update the producer to return both **available** and **inStock**.
2. Verify both the contract serving the old consumer and the contract for the new consumer.
3. Upgrade the consumer to read **inStock**, testing both old and new versions during the support window.
4. Only propose removing **available** once supported consumers no longer depend on it.

**Evidence to collect:** producer test report; name/path of generated tests; version and checksum/commit of the **stubs** JAR; Stub Runner logs confirming the candidate stub; consumer test results before and after fixes. From this evidence, pinpoint exactly at which step the change was blocked and why.

## 15. Checklist Before Merging a Contract Change

- [ ] Identified affected endpoint/topic, active consumers, and desired compatibility level.
- [ ] Contract reflects genuine consumer requirements, including fields, status codes, headers, and key error cases.
- [ ] Generated producer tests run against **candidate code** and pass.
- [ ] Stubs are packaged from **the same contract/commit**, with a clearly identifiable version.
- [ ] Stub Runner loads **the exact candidate artifact**; no accidental reuse of old versions.
- [ ] Consumer tests execute the **real client or handler** and verify business outcomes.
- [ ] Supported consumers/versions have been verified or have a clear migration plan.
- [ ] CI blocks release when compatibility gates fail; logs trace contract, commit, and stub.
- [ ] Risks outside contract scope (real data, auth, networking, broker, timeouts) have appropriate checks.

## 16. Self-Check Questions

**1. Why can producer tests still pass after renaming a field that a consumer uses?**

Because the producer may have updated the contract alongside the implementation. Producer tests prove the code matches the **new contract**; they do not directly test old clients. Consumer tests must run against the candidate stub and assert behavior relying on that field.

**2. Why is a consumer test using a previous stub version insufficient to verify a new PR?**

Because the previous stub version does not contain the changed behavior. The test can pass simply because the simulated producer still returns old data. CI must point to the artifact built from the candidate commit.

**3. Can we drop integration tests because we already have Spring Cloud Contract?**

No. Contract tests are useful for documented communication behavior; real systems also involve persistence, security, networking, brokers, configuration, runtime failures, and uncontracted scenarios.

**4. When can an old field be removed from a response?**

When versioning/deprecation policy permits and you have confirmed that supported consumers no longer depend on that field—typically after a transition period returning both old and new fields.

---

**Key takeaway:** The complete chain of evidence is **producer change → contract → generated producer test → candidate stub → Stub Runner → consumer test → CI decision gate**. Each leg answers a different question; reliable verification is only achieved when artifacts and versions are linked seamlessly across the entire chain.
