# SNAPSHOT Versions, Caching, and Stub Freshness

## 1. Why Does Stub Version Determine the Value of Contract Testing?

**Spring Cloud Contract (SCC)** helps producers and consumers agree on HTTP or messaging behavior via the **Groovy/YAML DSL**. The tool generates **generated producer tests** to verify the real providing implementation, while generating **stubs** for consumers to test clients/handlers via **Stub Runner**. In CI, both sides must use **the same contract revision** to catch incompatible API changes.

A dangerous scenario:

- 09:00 — Inventory Service publishes `1.4.0-SNAPSHOT`, returning JSON with `available`.
- 09:30 — Producer changes contract/code to return JSON with `inStock`, then republishes `1.4.0-SNAPSHOT`.
- 09:35 — Checkout Service runs Stub Runner yet consumes the stale stub cached from 09:00.
- Checkout's test stays green because code still reads `available`. The pipeline fails to catch the breaking change in the 09:30 candidate.

Both builds shared the same **logical version `1.4.0-SNAPSHOT`**, yet they did not share the same **artifact bytes**. Hence stub freshness is part of **test correctness**, not merely a download-speed optimization.

This lesson belongs to the **Contract and Artifact Repositories** chapter and focuses on **SNAPSHOT versions, caching, and stub freshness**: Maven snapshot metadata, timestamped builds, layered caches, Stub Runner LOCAL/REMOTE, candidate artifact strategies, and CI gates.

### Learning objectives

After this lesson, you can:

1. Distinguish **releases**, **SNAPSHOT logical versions**, and **timestamped SNAPSHOTs**.
2. Explain `maven-metadata.xml`, snapshot repositories, update policies, and local/remote caches.
3. Identify caching layers across **Maven**, **Gradle**, **artifact repository proxies**, **Stub Runner**, and **WireMock**.
4. Configure Stub Runner LOCAL/REMOTE appropriately for the context.
5. Use `mvn -U` or `gradle --refresh-dependencies` within their real scope without treating them as magic bullets.
6. Verify loaded stubs correspond to the intended producer commit, classifier, and contract revision.
7. Design CI using **immutable candidate versions** or snapshots pinned by timestamp/digest.
8. Diagnose stale stubs, wrong repositories, missing artifacts, false green tests, and multi-pipeline publish races.

## 2. Four Distinct Assets Often Lumped Together as “Contract”

| Component | Example | Role |
|---|---|---|
| **Contract source** | `get-stock.groovy` or `get-stock.yml` | Defines HTTP/message behavior |
| **Generated producer tests** | Java tests generated by Contract Verifier | Verifies **real producer code** |
| **Generated stub mappings** | WireMock JSON, response files | Simulates contract requests/responses |
| **Stubs artifact** | `inventory-service-1.4.0-SNAPSHOT-stubs.jar` | Delivers stubs to consumers via a repository |

~~~mermaid
flowchart TD
    A["Producer commit A code + contract"] --> B["SCC generated producer tests"]
    A --> C["SCC generated stub mappings"]
    B --> D{"Producer tests pass?"}
    D -- "No" --> X["Block release"]
    D -- "Yes" --> E["Candidate stubs artifact"]
    C --> E
    E --> F["Maven artifact repository"]
    F --> G["Stub Runner resolves and loads"]
    G --> H["WireMock HTTP server"]
    H --> I["Real consumer client"]
    I --> J{"Compatible?"}
    J -- "No" --> X
    J -- "Yes" --> K["Proceed to CI/release gates"]
~~~

If producer tests ran against contract B while the consumer fetched the artifact from contract A, both sides **are no longer testing the same change**. CI must therefore prove the chain **producer commit → contract → generated test → stubs JAR → Stub Runner → consumer test**.

## 3. What Are Stub Artifact Coordinates?

A stub bundle can be published under Maven coordinates:

~~~text
groupId:     com.example
artifactId:  inventory-service
version:     1.4.0-SNAPSHOT
classifier:  stubs
type:        jar
~~~

An ID string in Stub Runner is typically written as:

~~~text
com.example:inventory-service:1.4.0-SNAPSHOT:stubs:18081
~~~

| Component | Meaning | If used wrongly |
|---|---|---|
| `groupId` | Organization namespace | May download wrong producer |
| `artifactId` | Producer artifact name | Downloads wrong service |
| `version` | Contract/stub version | Uses stale API code or wrong PR |
| `classifier=stubs` | JAR containing mappings/fixtures | Confused with application JAR |
| `type=jar` | Artifact format | Cannot unpack/read |
| `port=18081` | Stub Runner HTTP port | Consumer calls wrong server |

The `group:artifact:version:classifier` coordinates identify a **logical artifact**. With a mutable SNAPSHOT, that information does not necessarily pinpoint **unique bytes**.

## 4. How Do Releases and SNAPSHOTs Differ?

### 4.1. Release

~~~text
com.example:inventory-service:1.4.0:stubs
~~~

A repository should enforce an **immutable release** policy: the same coordinates cannot be redeployed with different contents. Many repository managers can block overwrites; however, immutability is a **policy that must be configured and verified**, not an automatic guarantee in every repository.

### 4.2. SNAPSHOT

~~~text
com.example:inventory-service:1.4.0-SNAPSHOT:stubs
~~~

A SNAPSHOT is typically an in-development version that can be published repeatedly. For example:

~~~text
1.4.0-SNAPSHOT publish A -> {"available":true}
1.4.0-SNAPSHOT publish B -> {"inStock":true}
~~~

Two different artifacts can be requested using **the exact same logical version string**. This makes consumer test results hard to reproduce unless timestamps/build identities or checksums are recorded.

SNAPSHOTs remain useful for **continuous development**. Yet when deciding “does this PR break older consumers?”, prefer an **immutable candidate version** or a snapshot with pinned identity and provenance.

## 5. What Is a Timestamped SNAPSHOT?

Maven-compatible repositories can store a logical SNAPSHOT such as:

~~~text
1.4.0-SNAPSHOT
~~~

under timestamped files (for example):

~~~text
inventory-service-1.4.0-20261124.051500-12-stubs.jar
inventory-service-1.4.0-20261124.051500-12.pom
maven-metadata.xml
~~~

where `20261124.051500` is an illustrative timestamp and `12` is an illustrative build number. Depending on the repository and deploy tool, successive timestamped versions represent sequential publishes.

~~~mermaid
flowchart LR
    A["Consumer declares 1.4.0-SNAPSHOT"] --> B["Resolver reads metadata"]
    B --> C["Selects matching timestamp/build"]
    C --> D["Downloads stubs classifier JAR"]
    D --> E["Stub Runner loads mappings"]
    E --> F["WireMock serves HTTP"]
~~~

You cannot conclude “the consumer is using the latest snapshot on the server” simply from a configuration containing `-SNAPSHOT`. Resolution is also affected by update policies, metadata caches, proxies, request timing, and Stub Runner state.

## 6. How Does `maven-metadata.xml` Determine the Version?

The `maven-metadata.xml` file in a Maven repository can describe snapshot timestamps, build numbers, and `snapshotVersions` entries by extension/classifier.

**Abbreviated example, strictly for understanding the mechanism**:

~~~xml
<metadata>
  <groupId>com.example</groupId>
  <artifactId>inventory-service</artifactId>
  <version>1.4.0-SNAPSHOT</version>
  <versioning>
    <snapshot>
      <timestamp>20261124.051500</timestamp>
      <buildNumber>12</buildNumber>
    </snapshot>
    <snapshotVersions>
      <snapshotVersion>
        <extension>jar</extension>
        <classifier>stubs</classifier>
        <value>1.4.0-20261124.051500-12</value>
        <updated>20261124051500</updated>
      </snapshotVersion>
    </snapshotVersions>
  </versioning>
</metadata>
~~~

Metadata can hold multiple entries (POM, main artifact, stubs JAR, etc.). When diagnosing:

- Is metadata at the **remote origin** up to date?
- Is a proxy/mirror returning **stale metadata**?
- Does metadata in the local cache point to an old timestamp?
- Does metadata contain a `classifier=stubs` entry for the new publish?
- Which timestamp did Stub Runner actually resolve?
- Does the downloaded artifact's checksum match the producer CI output?

**Never equate fresh metadata with fresh bytes currently served by WireMock.** A server that already loaded an older JAR will keep serving stale responses.

## 7. A Timeline That Causes a False Green

~~~mermaid
sequenceDiagram
    participant P as Producer CI
    participant R as Snapshot Repository
    participant C as Consumer CI
    participant S as Stub Runner
    P->>R: 09:00 publish SNAPSHOT A
    C->>R: 09:05 resolve A
    R-->>C: JAR A
    C->>S: Load mappings A
    P->>R: 09:30 publish SNAPSHOT B
    Note over S: WireMock still holds mapping A
    C->>S: 09:35 GET inventory
    S-->>C: JSON from A
    Note over C: Test can falsely PASS
~~~

Two independent questions:

1. **Did the resolver download the new stubs JAR?**
2. **Did the running Stub Runner/WireMock instance load the new JAR?**

A pipeline that refreshes the repository yet **does not restart the server** can keep serving pre-publish mappings.

## 8. Caching Has Multiple Layers, Not One Place

| Layer | What can be cached | Risk |
|---|---|---|
| **Producer build output** | `target`/`build`, generated mappings | JAR published from stale output |
| **Artifact repository** | Timestamped snapshots, metadata | Missing or wrong artifact classifier |
| **Repository proxy/mirror** | Cached metadata + bytes | New build from origin not yet visible |
| **Maven local repository** | `~/.m2/repository` and metadata | Resolver picks older snapshot |
| **Gradle dependency cache** | Module metadata and artifacts | Dynamic/changing dependencies unrefreshed |
| **Stub Runner resolver/cache** | Resolved/extracted artifacts | Runner picks file from previous run |
| **WireMock in-memory mappings** | Mappings loaded at startup | New publish does not hot-reload automatically |
| **CI workspace/cache** | Local repository, compiled tests, cached processes | Subsequent jobs reuse prior state |

A single `mvn -U` action only affects the corresponding Maven resolution; it does not refresh all layers. Take corrective action only after **identifying where data became stale**.

## 9. Maven `updatePolicy`: Always, Daily, Interval, Never

A repository SNAPSHOT policy can declare:

| Policy | General meaning |
|---|---|
| `always` | Checks for updates whenever the resolver runs |
| `daily` | Checks roughly once per day |
| `interval:N` | Checks after N minutes |
| `never` | Does not proactively update |

**Illustrative** POM example:

~~~xml
<repositories>
    <repository>
        <id>company-snapshots</id>
        <url>https://repo.example.invalid/repository/snapshots</url>
        <releases>
            <enabled>false</enabled>
        </releases>
        <snapshots>
            <enabled>true</enabled>
            <updatePolicy>always</updatePolicy>
        </snapshots>
    </repository>
</repositories>
~~~

`repo.example.invalid` is intentionally a dummy address, not a real endpoint. Maven has default policies and overrides via settings/mirrors; in many cases the default is `daily`. Repository managers also enforce cache TTLs or their own mechanisms.

**Enabling `always` for every dependency is not recommended**: it can overload repositories without guaranteeing Stub Runner reloaded new mappings. For CI requiring reproducibility, immutable candidate versions are far more reliable.

## 10. What Does `mvn -U` Do and Not Do?

~~~bash
./mvnw -U clean verify
~~~

`-U` instructs Maven to check/update snapshots through **that Maven process's** resolver according to Maven version semantics. It can also affect re-checking previously missing release dependencies.

However, it:

- Does not force a **separate Stub Runner JVM** to re-download artifacts.
- Does not hot-reload a **running WireMock instance**.
- Does not conjure up a JAR if the producer never published or published to the wrong repo.
- Does not fix a proxy returning stale metadata.
- Does not bind a logical `SNAPSHOT` to a specific commit.
- Does not ensure Gradle's dependency cache is refreshed either.

When you need to prove freshness, you need **resolved snapshot identity + content digest + commit provenance**, not just a log saying “ran Maven -U.”

## 11. Gradle `--refresh-dependencies` Is Not a Stub Runner Refresh Command

If the consumer/producer uses Gradle:

~~~bash
./gradlew --refresh-dependencies test
~~~

This refreshes/checks the **Gradle dependency resolver** cache. Dynamic or changing modules (such as Maven `-SNAPSHOT`s recognized by Gradle as changing) follow dedicated caching semantics.

Illustrative example of altering cache policy:

~~~groovy
configurations.configureEach {
    resolutionStrategy {
        cacheChangingModulesFor 0, 'seconds'
        cacheDynamicVersionsFor 0, 'seconds'
    }
}
~~~

This configuration can increase network traffic and slow builds; **do not copy it into every project**. If Stub Runner uses a separate resolver/cache, `--refresh-dependencies` also does not guarantee its runtime swapped stubs.

**Dynamic version** (e.g., `1.+`) and **changing module** (`1.4.0-SNAPSHOT`) are not the same concept. Never use `+` in compatibility gates when the goal is verifying a specific producer commit.

## 12. Where Does Stub Runner LOCAL Get Stubs From?

Consumer test example:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.cloud.contract.stubrunner.spring.AutoConfigureStubRunner;
import org.springframework.cloud.contract.stubrunner.spring.StubRunnerProperties;

@SpringBootTest(properties =
    "inventory.base-url=http://localhost:18081")
@AutoConfigureStubRunner(
    ids = "com.example:inventory-service:1.4.0-SNAPSHOT:stubs:18081",
    stubsMode = StubRunnerProperties.StubsMode.LOCAL
)
class InventoryLocalStubTest {
    @Test
    void consumerUsesStub() {
        // Call Checkout's real InventoryClient against Stub Runner.
    }
}
~~~

`LOCAL` typically pulls artifacts from the **Maven local repository** or local sources supported by Stub Runner. If the producer updates a contract while the developer only runs `mvn test` or `mvn package`, the new JAR is not necessarily **installed** into the local repo.

A sound LOCAL development flow:

~~~text
Producer updates contract + code
  -> Generates/runs producer tests
  -> Packages stubs JAR
  -> Installs JAR into Maven local repo
  -> Restarts consumer test/Stub Runner
  -> Verifies new mapping
~~~

In a Maven producer with the plugin configured, an example command is:

~~~bash
./mvnw clean install
~~~

**Do not assume** a build command always creates/attaches the `stubs` classifier; inspect plugin output/logs. With Gradle, `build` likewise does not automatically publish to Maven local unless the project wires the appropriate task.

## 13. How Does Stub Runner REMOTE Fetch Artifacts?

When producer and consumer run in separate CI jobs/containers, a **remote repository** is usually required.

Skeleton configuration example:

~~~java
import org.springframework.cloud.contract.stubrunner.spring.AutoConfigureStubRunner;
import org.springframework.cloud.contract.stubrunner.spring.StubRunnerProperties;

@AutoConfigureStubRunner(
    ids = "com.example:inventory-service:1.4.0-SNAPSHOT:stubs:18081",
    stubsMode = StubRunnerProperties.StubsMode.REMOTE,
    repositoryRoot = "https://repo.example.invalid/repository/snapshots"
)
class InventoryRemoteStubTest {
    // Complete with Spring test and real consumer client.
}
~~~

Verify annotation `repositoryRoot`, authentication, repository URL, and resolver semantics for **the SCC version in use**. This is not a complete test class.

With REMOTE:

1. Producer publishes the `stubs` JAR after generated producer tests pass.
2. Repository/proxy must expose the artifact and accurate metadata.
3. Consumer resolver holds read access to the repository.
4. Stub Runner logs show which artifact was resolved.
5. Stub server starts after the artifact is present.
6. Consumer's real HTTP client hits the right port and checks the response.

**REMOTE is not automatically “newer” than LOCAL.** Repository proxies also cache; a freshly installed local build can be newer than stale remote metadata served by a proxy.

## 14. One Logical Version Is Not Enough to Conclude Freshness

Two logs both printing:

~~~text
com.example:inventory-service:1.4.0-SNAPSHOT:stubs
~~~

can still use **two different JARs**. Stronger evidence includes:

- Resolved **timestamped SNAPSHOT**;
- SHA-256 digest of the actual downloaded JAR;
- Producer **Git commit SHA** and build/job ID;
- Contract revision accompanying the producer build;
- Actual mapping JSON inside the JAR;
- Stub Runner startup logs and active WireMock mappings;
- Consumer tests asserting against the new behavior.

| Observation | Confidence |
|---|---|
| Only `1.4.0-SNAPSHOT` seen | Unknown bytes |
| Resolved timestamp A seen | Identifies a snapshot build, not necessarily the right PR |
| Timestamp B + digest matching producer CI | Strong evidence of the exact candidate |
| Unique candidate version + digest + immutable repository policy | Most reproducible/auditable |

**Immutability must be enforced**, not merely written into the version name.

## 15. A New Publish Does Not Automatically Update a Running WireMock

~~~text
T1: Stub Runner starts -> loads mappings A
T2: Producer publishes new JAR containing mappings B
T3: Checkout calls Stub Runner instance from T1
T4: Server still returns mappings A
~~~

To inspect and fix:

1. Check Stub Runner startup time.
2. Verify the artifact resolved when the server started.
3. If needed, stop/create a fresh test context and **start Stub Runner after the new candidate is ready**.
4. Control caches/resolvers so the new startup does not reload file A.
5. Call the endpoint with the new property and inspect the raw response.
6. Confirm the real consumer client handles behavior B properly.

Watch out for Spring test **application-context caching**: re-running a test method does not necessarily recreate the Stub Runner server. Never assume hot reload happens just because a SNAPSHOT changed in the repository.

## 16. Local Files, Maven Cache, and Remote Artifacts Can Diverge

These three locations are independent:

~~~text
Producer source:
  src/test/resources/contracts/inventory/get-stock.groovy

Producer build output:
  target/inventory-service-1.4.0-SNAPSHOT-stubs.jar

Consumer local repository:
  ~/.m2/repository/com/example/inventory-service/1.4.0-SNAPSHOT/
~~~

The producer may have edited a contract without regenerating mappings; it may have built a new JAR without running `install`; or the consumer runs in another container lacking that local artifact.

**Important boundary example:**

~~~text
Producer CI:
  ./mvnw clean install
  -> writes to producer runner's ~/.m2/repository

Consumer CI in another container:
  stubsMode=LOCAL
  -> reads consumer runner's ~/.m2/repository
~~~

Those two `~/.m2` directories are not shared automatically. In split-job CI, publish to a remote repository or pass artifacts via provenance-checked CI artifact mechanisms instead of assuming local caches sync.

## 17. Dynamic Versions and `latest` Break Reproducibility

Some Stub Runner configs support dynamic versions:

~~~text
com.example:inventory-service:+:stubs:18081
~~~

This is an **example to avoid for release gates** unless the system records and pins the resolved result. Risks:

- Job A and Job B download two different versions for the same consumer commit.
- A new build appears between two test runs.
- Metadata caches make “latest” inconsistent.
- Branches publish SNAPSHOTs into the same slot.
- Passing tests cannot be tied to the producer commit under review.

**Recommendation:** pass the exact candidate coordinates from the producer pipeline to the consumer pipeline; if SNAPSHOTs are unavoidable, record the **timestamped identity and digest** of what was downloaded.

## 18. Do Not Fix Everything by Wiping Caches

When the consumer sees stale responses, classify the failure first:

1. Did the producer actually publish **new mappings**?
2. Does the remote repository hold the right **`stubs` classifier JAR**?
3. Does snapshot metadata point to the new build?
4. Is a proxy/mirror caching stale metadata?
5. Did the Maven/Gradle resolver refresh per policy?
6. Did Stub Runner restart and resolve the right artifact?
7. Is the consumer client calling the **right server/port**?
8. Could the test be hitting a different mock/fixture?

Only after pinpointing the **stale cache layer** should you pick the right cleanup action. Wiping the entire `~/.m2/repository` or `~/.gradle/caches` is expensive, impacts other projects, and may not fix a proxy or WireMock runtime issue.

## 19. Per-Commit Candidate Versions Eliminate SNAPSHOT Ambiguity

A stronger strategy than constantly busting caches is publishing a **unique candidate version per PR/commit**:

~~~text
producerCommit: a1b2c3d4
pullRequest: 173
candidateVersion: 1.4.0-rc.pr173.a1b2c3d4

Maven coordinate:
com.example:inventory-service:1.4.0-rc.pr173.a1b2c3d4:stubs
~~~

Pros:

- Unambiguously identifies which artifact to use.
- Two PRs never overwrite the same logical SNAPSHOT.
- Immutable version caches will never accidentally pull another commit's build.
- Consumer CI receives **exact coordinates** from the producer job instead of guessing `latest`.
- Reports can record commit SHA, build ID, and digest.
- Consumer tests can compare multiple candidates side-by-side when needed.

**Mandatory condition:** the repository must forbid **redeploying the same coordinates with different bytes**. Merely embedding a commit SHA in the version string while still allowing overwrites does not guarantee immutability.

## 20. Distinguishing Continuous SNAPSHOT Workflows from PR Compatibility Gates

| Context | Version strategy | Reason |
|---|---|---|
| Developer quick local testing | `1.4.0-SNAPSHOT`, Stub Runner LOCAL | Simple, provided you install and restart |
| Main/develop integration | Branch-scoped SNAPSHOTs | Fits ongoing integration |
| PR compatibility gate | Unique candidate version | Traceable to one commit and avoids races |
| Official release | Immutable release version | Reproducible for consumers |
| A/B comparison | Two distinct versions | Prevents mixed mappings |

If SNAPSHOTs must be used in a PR, pin the **resolved timestamped build or SHA-256 digest** for that CI run rather than re-resolving a logical version arbitrarily.

Not every Stub Runner version supports passing timestamped snapshots directly inside `ids`. When unsupported, **publishing a unique candidate version** is usually simpler and safer.

## 21. Snapshot and Release Repositories Serve Different Purposes

Example separated artifact repositories:

~~~text
Snapshots:
com.example:inventory-service:1.4.0-SNAPSHOT:stubs

Releases:
com.example:inventory-service:1.4.0:stubs
~~~

In Maven, the **deploy target** can be declared as:

~~~xml
<distributionManagement>
    <snapshotRepository>
        <id>company-snapshots</id>
        <url>https://repo.example.invalid/repository/snapshots</url>
    </snapshotRepository>
    <repository>
        <id>company-releases</id>
        <url>https://repo.example.invalid/repository/releases</url>
    </repository>
</distributionManagement>
~~~

Conversely, `<repositories>`, Maven settings/mirrors, and Stub Runner configuration govern **where to download/resolve**. Publish and resolve do not automatically share the same URL.

Examples of real-world failures:

- Producer deploys to repository A while consumer reads repository B.
- Release repository rejects SNAPSHOT resolution.
- Producer publishes main JAR, omitting the `stubs` classifier.
- Fresh metadata has the main JAR entry while the stubs entry is still stale.
- Consumer CI lacks read rights or traverses a different proxy cache than a laptop.
- Repository retention cleans up old snapshots, breaking historical test replay.

`example.invalid` is illustrative only, not real. Never place credentials in POMs, annotations, Markdown fixtures, or logs.

## 22. Watch Out for Proxy Caches and Retention

Repository managers often expose **repository groups/proxies** with metadata TTLs, snapshot cleanup policies, and per-project permissions.

If origin holds snapshot B while a proxy still serves metadata A, the consumer downloads the artifact matching the proxy's metadata—even though it is stale. Likewise, a timestamped snapshot tested last month may be purged when retention runs.

To investigate:

1. Check producer deploy logs and confirm origin received the `stubs` artifact.
2. Compare origin metadata against metadata read by the consumer resolver.
3. Inspect the actual mirror/repository group and update policy.
4. Check whether snapshot retention deleted the needed artifact.
5. Record the timestamped build or digest in test reports.
6. For builds requiring long-term audits, store artifacts/metadata under a matching retention policy.

**Never use “the repository proxy takes a while” as an excuse to skip provenance.** CI needs deterministic artifact identities rather than luck-based propagation delays.

## 23. Inspect the Resolved JAR, Not Just Files in `target`

Suppose a contract changes from:

~~~json
{"sku":"SKU-123","available":true}
~~~

to:

~~~json
{"sku":"SKU-123","inStock":true}
~~~

If the producer built a new JAR while Stub Runner LOCAL still reads an older copy from the Maven local repo, inspecting `target/...-stubs.jar` **is not enough**.

Inspect **the exact JAR used by Stub Runner**. Reference command when Java CLI is available:

~~~bash
jar tf target/inventory-service-1.4.0-SNAPSHOT-stubs.jar
~~~

JAR structure may look like:

~~~text
META-INF/
  com.example/
    inventory-service/
      1.4.0-SNAPSHOT/
        mappings/
          get-stock.json
        contracts/
          inventory/get-stock.groovy
        __files/
          stock-response.json
~~~

This structure is **illustrative**, not a layout guarantee across all SCC versions. Fields to inspect in mappings:

- `request.method` and URL/path/query predicates.
- Headers and `bodyPatterns` if checked by the contract.
- `response.status`, headers, and JSON body.
- Presence of the new `inStock` field and removal of the old field if an intentional breaking change.
- Every `bodyFileName` has its response file packaged.
- No duplicate/overlapping mappings causing the wrong scenario to match.
- Error cases consumers depend on were generated.

If a JAR published after the new commit still contains old mappings, the root cause may lie in **producer generation or packaging**, not Stub Runner's cache.

## 24. SHA-256 Confirms Artifact Contents

A checksum computed on the **downloaded JAR** can be compared against the digest published by producer CI.

Unix:

~~~bash
sha256sum inventory-service-1.4.0-SNAPSHOT-stubs.jar
~~~

Windows PowerShell:

~~~powershell
Get-FileHash -Algorithm SHA256 -Path .\inventory-service-1.4.0-SNAPSHOT-stubs.jar
~~~

Example report schema:

~~~text
producerCommit: a1b2c3d4
candidateVersion: 1.4.0-rc.pr173.a1b2c3d4
groupId: com.example
artifactId: inventory-service
classifier: stubs
producerArtifactSha256: <real digest from producer job>
consumerArtifactSha256: <real digest of JAR downloaded by consumer>
digestMatched: true / false
~~~

Values in `<...>` must be collected from real systems. A checksum **only proves provenance when compared against the expected checksum**. Local file modification timestamps cannot replace content checks; a freshly copied file can still hold old mappings.

## 25. Producer Code Changes and Contract Changes Can Create Two Failure Modes

| Scenario | Producer verification | Consumer verification |
|---|---|---|
| Only producer implementation changes, contract unchanged | Must catch if code violates contract | Stub does not necessarily change |
| Contract changes, implementation unchanged | Generated tests may turn red | Not yet eligible to publish candidate as standard |
| Both code and contract change | Generated tests may be green | Existing consumer must test **new candidate stub** |
| Only consumer changes | Producer artifact can stay as-is | Test against producer versions still supported |

Example:

~~~text
Producer A/contract A:
  {"available": true}

Producer B/contract B:
  {"inStock": true}

Old Checkout consumer:
  still reads available
~~~

If Checkout tests run with stub A, they may pass yet **haven't tested B**. With stub B, old client/DTOs should fail or return wrong business results. If tests remain green, check whether the deserializer defaults missing booleans to `false`, whether assertions are strong enough, and whether the client actually hit mapping B.

## 26. Consumer Tests Must Use the Real HTTP Client

A Stub Runner test with a unique candidate version:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.cloud.contract.stubrunner.spring.AutoConfigureStubRunner;
import org.springframework.cloud.contract.stubrunner.spring.StubRunnerProperties;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(properties =
    "inventory.base-url=http://localhost:18081")
@AutoConfigureStubRunner(
    ids = "com.example:inventory-service:1.4.0-rc.pr173.a1b2c3d4:stubs:18081",
    stubsMode = StubRunnerProperties.StubsMode.REMOTE,
    repositoryRoot = "https://repo.example.invalid/repository/candidates"
)
class InventoryCandidateContractTest {
    @Autowired
    InventoryClient inventory;

    @Test
    void consumerReadsCandidateResponse() {
        StockResponse result = inventory.getStock("SKU-123");

        assertThat(result.sku()).isEqualTo("SKU-123");
        assertThat(result.inStock()).isTrue();
    }
}
~~~

`InventoryClient`/`StockResponse` represent **hypothetical consumer code** to be built in a real project. The repository URL does not exist and must be replaced with an authorized CI repo. Annotation property support, dependencies, and test context must be checked against your SCC version.

**Never mock `inventory.getStock(...)` itself in this test**: mocking the HTTP client to return a sample DTO bypasses the stub and cannot detect differences between artifacts A and B. Consumer verification must exercise the real client's method/path/headers, deserialization, and error mapping.

## 27. Multi-Producer: Each Artifact Needs Its Own Provenance

Checkout may depend on both Inventory and Pricing:

~~~text
Inventory candidate:
com.example:inventory-service:1.4.0-rc.pr173.a1b2c3d4:stubs:18081

Pricing stable:
com.example:pricing-service:2.2.0:stubs:18082
~~~

When only Inventory changes, testing against pinned stable Pricing is valid. However, avoid storing a single shared `STUB_VERSION` variable that causes one producer to accidentally pick up another's version.

Example with multiple `ids`:

~~~java
@AutoConfigureStubRunner(
    ids = {
        "com.example:inventory-service:1.4.0-rc.pr173.a1b2c3d4:stubs:18081",
        "com.example:pricing-service:2.2.0:stubs:18082"
    },
    stubsMode = StubRunnerProperties.StubsMode.REMOTE
)
~~~

This is an illustrative config snippet; add repository URL, credentials, and real HTTP client wiring. If any producer uses a SNAPSHOT, record the **resolved timestamp/digest** for that specific producer.

## 28. Immutable Candidate Versions Do Not Eliminate Real Producer Testing

A consumer test can pass against the right fresh candidate artifact while the real producer implementation **fails to satisfy the contract** due to a broken controller/service refactor. Stubs simulate contracts; they do not invoke producer code.

Therefore you need **two separate gates**:

1. **Generated producer tests** running against the candidate's producer code, never using a fake controller returning sample responses.
2. **Consumer tests** running the real client/handler against the stub artifact generated from that candidate contract.

If only gate 2 is green, real producer behavior is unproven. If only gate 1 is green, legacy consumer compatibility with the new API is unproven. Provenance links both gates by **commit, contract revision, and specific stubs JAR**.

## 29. CI Gate Confirming Fresh Stubs Before Consumer Testing

A compatibility pipeline must verify **the exact artifact** at every stage:

~~~mermaid
flowchart TD
    A["Producer PR: contract + code"] --> B["Generate producer tests"]
    B --> C{"Tests executed & PASS?"}
    C -- "No" --> X["BLOCK"]
    C -- "Yes" --> D["Build stubs JAR from same commit"]
    D --> E["Publish unique candidate version"]
    E --> F["Consumer CI receives exact coordinate + checksum"]
    F --> G["Resolve, compare checksum, and inspect mappings"]
    G --> H["Start fresh Stub Runner"]
    H --> I["Consumer real HTTP client runs tests"]
    I --> J{"Compatibility passes?"}
    J -- "No" --> X
    J -- "Yes" --> K["Proceed to release gates"]
~~~

Mandatory checks:

1. Producer generated test count is **greater than 0** and all assertions pass.
2. Artifact is packaged from **the exact producer commit/contract revision**.
3. JAR contains the `stubs` classifier and non-empty required mappings.
4. Candidate has unique `group:artifact:version:classifier` coordinates.
5. Repository published the artifact and consumer resolver has read rights.
6. If using SNAPSHOTs, resolved timestamp or digest is recorded.
7. Consumer tests do not hit a leftover Stub Runner server from an older job.
8. Tests use the consumer's **real client**, not just raw HTTP test helpers or Mockito.
9. Both success/error response schemas are verified where consumers depend on them.
10. CI blocks if coordinates/digest mismatch the candidate or the artifact is missing.
11. Logs retain commit, artifact, plugin version, and test reports for traceability.

Within a single CI run, **never swap artifacts between test phases** by re-resolving a logical SNAPSHOT. One test passing on version A and another passing on version B does not prove the same candidate is safe.

## 30. When Two Pipelines Publish the Same Logical SNAPSHOT

Suppose:

~~~text
Branch feature-a:
  publishes inventory-service:1.4.0-SNAPSHOT
  body: {"available":true}

Branch feature-b:
  publishes inventory-service:1.4.0-SNAPSHOT
  body: {"inStock":true}

Consumer PR feature-a:
  resolves 1.4.0-SNAPSHOT
  unclear which branch's build the resolver picks
~~~

The repository may still store **separate timestamped snapshots**, yet the logical version's metadata usually points to whichever snapshot arrived last. Producer/consumer CI can therefore hit a **race condition**.

How to prevent it:

- Never share one logical SNAPSHOT across multiple branches needing independent verification.
- Include PR/commit/build IDs in candidate versions.
- Restrict main logical SNAPSHOT publish rights to the appropriate pipeline.
- Pass exact candidate coordinates from producer job to consumer job.
- Compare artifact digest against producer output.
- Record resolved timestamps when SNAPSHOTs are unavoidable.
- Never use `latest` or `+` at release gates without logging/pinning versions.

Shared SNAPSHOTs can serve nightly integration, yet **should never be the sole identifier** for a PR compatibility check.

## 31. Stale Stub Symptoms and How to Investigate

| Symptom | Possible cause | Appropriate action |
|---|---|---|
| New JAR sits in producer `target`, LOCAL still uses old | Not installed into Maven local | Install artifact, check path, restart consumer |
| New remote snapshot published, yet HTTP response is stale | WireMock process loaded before publish | Restart Stub Runner and verify resolved mappings |
| `mvn -U` does not change stub | Stub Runner resolver differs from Maven process or old server | Inspect runner logs, JAR file, digest |
| Gradle refreshed, yet Stub Runner still stale | Only Gradle cache refreshed | Inspect Stub Runner's resolver |
| Origin metadata fresh, consumer metadata stale | Proxy/mirror TTL or update policy | Compare repository endpoints and metadata |
| Artifact has right version yet old field | Stale SNAPSHOT timestamp or producer packaging bug | Compare build timestamp, JAR mappings, and checksum |
| JAR has `inStock`, yet client still receives `available` | Consumer calling wrong port/server | Check URL and WireMock request journal |
| New JAR missing response body file | `__files` packaging error | Open JAR, inspect `bodyFileName` |
| Stub returns unexpected 404 | WireMock unmatched request | Compare request method/path/headers/body |
| Pipeline flips pass/fail with no code changes | Mutable version/race/cache TTL | Pin unique candidate + provenance |
| Producer tests green yet real API wrong | Base class fakes implementation or tests skipped | Inspect generated tests and try mutation |
| Consumer tests green despite breaking candidate | Used stale stub, mocked client, or weak assertions | Inspect artifact and real client requests |

Useful debugging order:

~~~text
Producer commit and contract
  -> Generated producer tests
  -> Generated stub mappings
  -> Published JAR with checksum
  -> Repository metadata / proxy
  -> Resolver + local cache
  -> Stub Runner startup
  -> Loaded WireMock mappings
  -> Consumer HTTP request
  -> Deserialization + business assertions
~~~

Find the **first layer showing mismatched evidence** before deciding to wipe caches, alter policies, or edit contracts.

## 32. Recording a Provenance Report for Every Verification Run

A useful CI report:

~~~text
producerService: inventory-service
producerCommit: a1b2c3d4

artifactGroup: com.example
artifactName: inventory-service
artifactVersion: 1.4.0-rc.pr173.a1b2c3d4
classifier: stubs
repository: company-candidates
artifactSha256: <digest downloaded and verified by consumer>
stubMappingsCount: <actual mapping count>
stubRunnerPort: <actual port>
consumerService: checkout-service
consumerCommit: <consumer commit>
producerTestsExecuted: <test count>
consumerTestsExecuted: <test count>
result: PASS/FAIL
~~~

If using SNAPSHOTs, also record:

~~~text
logicalVersion: 1.4.0-SNAPSHOT
resolvedTimestampedVersion: 1.4.0-20261124.051500-12
metadataSource: <specific origin/proxy>
metadataCheckedAt: <actual timestamp>
~~~

Values inside `<...>` must be **collected** by the pipeline, never filled with fake numbers. A `PASS` status only means something when you can answer **which producer commit** and **which stub artifact bytes** were tested.

## 33. Practice Exercise A — Compare Two SNAPSHOT Builds

**Goal:** observe one logical version holding different contents.

1. Write an Inventory contract returning `{"available":true}`.
2. Run generated producer tests and package the stubs JAR.
3. Publish `1.4.0-SNAPSHOT` to an **authorized test repository**.
4. Record the timestamped identity and SHA-256 of the first artifact.
5. Update code and contract to `{"inStock":true}` and re-run producer tests.
6. Publish the new SNAPSHOT per repository policy.
7. Compare metadata, timestamps, checksums, and WireMock mappings of both builds.
8. Explain why a consumer declaring `1.4.0-SNAPSHOT` may not be able to reproduce the test.

**Evidence:** two artifacts/identities, mapping diff, digests, and producer test reports.

## 34. Practice Exercise B — Locate Caches in LOCAL, REMOTE, and WireMock

1. Have Checkout run Stub Runner in `LOCAL`; record which artifact loaded.
2. Edit the producer contract **without running install**, then re-run the consumer.
3. Install the new stubs JAR into the right Maven local repository.
4. Restart Stub Runner and verify whether the response changed.
5. Repeat with an experimental `REMOTE` snapshot repository.
6. Compare the effect of `mvn -U` and Gradle `--refresh-dependencies` on your resolver.
7. Inspect startup timing and Spring application-context caching.
8. Build a table of “stale layer → evidence → corrective action.”

**Evidence:** JAR contents, repository metadata, Stub Runner logs, before/after responses, and observations.

## 35. Practice Exercise C — Block False Greens on Breaking APIs

1. Old Checkout reads `available`; producer A has the matching contract.
2. Candidate producer B renames the field to `inStock` and passes generated producer tests.
3. Publish stubs JAR B with a **unique** candidate version.
4. Run **the same old Checkout** against stable stub A and record results.
5. Run old Checkout against candidate B, expecting failure on incompatibility.
6. If it stays green, investigate whether the client is mocked, DTO defaults fields, assertions are weak, or the wrong version ran.
7. Restore compatibility via an API expansion phase or intentional versioning.
8. Re-run producer tests + consumer tests with the new artifact.
9. Save both coordinates, commits, digests, and test reports.

**Evidence:** before/after test reports, mapping changes, candidate version, and migration decision.

## 36. Pre-Merge Checklist

- [ ] Generated producer tests are generated and executed against real producer code.
- [ ] Contract test count > 0; never treat skipped/zero tests as success.
- [ ] Stubs JAR built from the same producer commit and contract revision.
- [ ] `stubs` classifier, artifact version, and repository are accurate.
- [ ] SNAPSHOT resolved timestamp/digest recorded, not just logical version.
- [ ] Candidate version is unique or enforced immutable by repository policy.
- [ ] No ambiguous `latest`/`+` used for PR compatibility gates.
- [ ] Repository deploy/resolve endpoints and credentials clearly separated.
- [ ] Maven/Gradle/Stub Runner/proxy caches handled at the **right layer**.
- [ ] Stub Runner loaded mappings from the current JAR.
- [ ] Consumer real HTTP client/handler hits the stub at the right host/port.
- [ ] Stub mappings include key error cases and matchers.
- [ ] Negative test proves breaking changes turn consumer tests red.
- [ ] When multiple producers exist, coordinates/commits/digests recorded per dependency.
- [ ] CI logs include full provenance and artifact checksums.
- [ ] Snapshot retention and release immutability are governed.
- [ ] No secrets, tokens, or real customer data in stub fixtures.
- [ ] Compatibility gate blocks if the artifact does not match the candidate.

## 37. Self-Check Questions

**1. Does `1.4.0-SNAPSHOT` always represent an immutable artifact?**

No. A logical SNAPSHOT can map to multiple builds over time. To know what the consumer actually used, check the timestamped identity or digest.

**2. Why might `mvn -U` fail to make Stub Runner return new responses?**

Because its scope is Maven resolution for that build, rather than automatically updating a separate Stub Runner resolver or reloading already-loaded WireMock mappings.

**3. Is LOCAL always older than REMOTE?**

No. A freshly installed LOCAL build can be newer while a REMOTE proxy still caches old metadata; check specific artifact evidence.

**4. If producer tests B pass while the consumer passes against stub A, is that enough to release B?**

No. The consumer must test against **candidate stub B**, because contract B can differ from A.

**5. Why is a commit-tagged unique version better than a logical SNAPSHOT for PRs?**

It prevents races across concurrent candidates and ensures reproducibility, provided the repository blocks overwriting published coordinates.

**6. Why inspect the JAR and compare checksums?**

Because logical version names do not reflect bytes. JAR mappings and checksums reveal the actual content loaded.

**7. Stub Runner started at 09:00, producer published at 09:30: why does 09:35 still return old responses?**

WireMock loaded mappings at startup. Publishing a new artifact does not hot-reload the running server.

**8. Should you wipe the entire Maven repository whenever a consumer test fails?**

No. Identify the stale layer—build output, remote metadata, proxy, local resolver, Stub Runner, or client URL—and fix it directly.

**Key takeaway:** `-SNAPSHOT` is a **mutable logical version**, and caching can sit at many layers from Maven/Gradle to repository proxies, Stub Runner, and WireMock in-memory mappings. The decisive question is therefore not “did we use SNAPSHOT?” but **“which producer commit generated the stubs JAR that the consumer test actually ran against?”**. To catch incompatible API changes, verify real producer code, publish candidates with clear provenance, load the exact stubs, and run **real consumer clients** in CI.
