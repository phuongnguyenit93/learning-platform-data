# Handler Endpoint

## Lesson Objectives

In Spring Integration Core, a handler is the component that performs work when a message arrives at a processing point: invoking business logic, transforming data, writing to a target system, or producing a reply. Understanding handlers helps you design the right combination of `Message`, `MessageChannel`, endpoints, and gateways instead of stuffing every behavior into a single message-receiving callback.

After this lesson, you will be able to:

- Distinguish between `MessageHandler`, consumer endpoints, and service activators.
- Choose between one-way processing and reply-producing processing.
- Declare handlers using annotations and Java DSL.
- Explain reply routing, execution threads, and errors at the handler.
- Test business behavior together with how a handler participates in an integration flow.

## 1. Where Does the Handler Sit Inside an Endpoint?

Consider an invoice creation request flow:

```text
Application calls gateway
        |
        v
invoiceRequests (MessageChannel)
        |
        v
Consumer endpoint
        |
        v
Handler invokes InvoiceProcessor.process(...)
        |
        v
Reply message -> replyChannel -> gateway -> application
```

A **consumer endpoint** connects an input channel to processing logic. The **handler** is the object the endpoint invokes when a message arrives. An endpoint can use a handler you write directly or a handler generated by Spring Integration to invoke a POJO method.

Three layers of responsibility should be kept separate:

| Component | Primary Responsibility | Example |
| --- | --- | --- |
| Message channel | Delivers or holds messages according to channel semantics | `DirectChannel`, `QueueChannel` |
| Consumer endpoint | Attaches the handler to an input and manages consumption | `EventDrivenConsumer`, `PollingConsumer` |
| Message handler | Executes the processing action on the message | `ServiceActivatingHandler`, a `MessageHandler` implementation |

With a `SubscribableChannel` such as `DirectChannel`, the endpoint typically subscribes the handler to receive messages when sent. With a `PollableChannel` such as `QueueChannel`, the endpoint needs a poller to pull messages and pass them to the handler.

Thus, "handler endpoint" in this lesson refers to a message-processing point composed of a consumer endpoint and its handler. Do not assume every `MessageHandler` object inherently knows how to subscribe to channels, schedule polling, or manage a full lifecycle.

## 2. The `MessageHandler` Contract

The foundational interface has a single method returning no value:

```java
package org.springframework.messaging;

public interface MessageHandler {
    void handleMessage(Message<?> message) throws MessagingException;
}
```

The handler receives the entire message, including payload and headers. A simple implementation might log it:

```java
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHandler;

public class AuditHandler implements MessageHandler {

    @Override
    public void handleMessage(Message<?> message) {
        System.out.println("Payload: " + message.getPayload());
        System.out.println("Message id: " + message.getHeaders().getId());
    }
}
```

This is a handler that terminates a processing branch: it performs a side effect and does not produce a reply via a return value.

A common point of confusion is that Spring Integration still supports request–reply even though `handleMessage(...)` has a `void` return type. Reply-producing handlers send the reply message internally during execution. For instance, `ServiceActivatingHandler` invokes a business method, obtains the return value, and forwards it as the flow's output.

```text
MessageHandler.handleMessage(message): void
        |
        +-- invokes business logic -> result
        |
        +-- sends message containing result to output channel/replyChannel
```

You cannot turn a raw `MessageHandler` into a reply-producing handler simply by configuring `outputChannel` somewhere else. The handler or its surrounding mechanism must actually be capable of building and sending a reply.

## 3. Service Activator: Bringing a Business Method into a Flow

A service activator is the standard choice when you want to invoke a Java method from a message flow. Spring Integration creates an adapter to bridge the messaging model and the business method.

Example business method:

```java
public InvoiceResult process(InvoiceRequest request) {
    // Validate request and perform business logic.
    return new InvoiceResult(request.orderId(), "ACCEPTED");
}
```

When attached to a service activator:

1. The handler receives `Message<?>` from the endpoint.
2. The framework resolves which method to call and binds arguments.
3. The method executes with the payload or required message data.
4. Any non-`null` return value is used to create a reply.
5. The reply is sent according to the output configuration.

Handlers are not limited to calling HTTP endpoints or writing to databases. They can also orchestrate an in-memory business step. However, if the intent is transforming, routing, filtering, or aggregating messages, use the endpoint that expresses the corresponding integration pattern.

| Processing Step Intent | Typically Suitable Construct |
| --- | --- |
| Call a business service and obtain a result | Service activator, `.handle(...)` |
| Convert a payload from one form to another | Transformer, `.transform(...)` |
| Choose the next channel based on content | Router, `.route(...)` |
| Accept or discard a message based on a condition | Filter, `.filter(...)` |
| Combine multiple messages into one result | Aggregator, `.aggregate(...)` |
| Record or send to a target system, no reply needed | One-way handler or outbound channel adapter |

A single Java method could perform several tasks in this table, but using the right endpoint helps readers understand the flow's semantics, configuration, and testing expectations.

## 4. Mapping Payloads and Headers to Method Parameters

A handler method does not have to take `Message<?>`. You can declare only the data the business logic actually needs.

### 4.1. Receiving Only the Payload

```java
public InvoiceResult process(InvoiceRequest request) {
    return new InvoiceResult(request.orderId(), "ACCEPTED");
}
```

This keeps the business class lightly coupled to messaging. When the payload already matches the expected type, reading and testing the method is straightforward. Do not expect arbitrary payloads to convert automatically to the target type; conversion depends on converters, configuration, and input data.

### 4.2. Receiving the Payload Along with a Header

```java
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.messaging.handler.annotation.Payload;

public InvoiceResult process(
        @Payload InvoiceRequest request,
        @Header(name = "tenantId", required = false) String tenantId) {

    String effectiveTenant = tenantId == null ? "default" : tenantId;
    return new InvoiceResult(
            request.orderId(),
            "ACCEPTED_FOR_" + effectiveTenant);
}
```

If a required header is missing, argument resolution can fail before the method body runs. For optional headers, use a nullable parameter type, avoiding primitives when there is no suitable default value.

### 4.3. Receiving the Entire Message

```java
import org.springframework.messaging.Message;

public InvoiceResult process(Message<InvoiceRequest> message) {
    InvoiceRequest request = message.getPayload();
    Object correlationId = message.getHeaders().get("correlationId");

    // correlationId can be used for logging/tracing if provided by the application.
    return new InvoiceResult(request.orderId(), "ACCEPTED");
}
```

Receiving the entire message fits when processing logic needs to inspect multiple headers or control reply metadata. In return, the handler class depends directly on Spring Messaging.

If a class has multiple methods or overloads, explicitly specify the method name in the DSL and keep signatures unambiguous. Selecting the right method also depends on payload type and argument binding; do not use complex overloading as an implicit routing mechanism.

## 5. Request–Reply Example with Annotations and a Gateway

The following example accepts an invoice creation request and returns an acceptance result. It does not yet persist the invoice, call external services, or enforce business deduplication. Pieces such as Spring Integration Core and Spring context initialization are assumed to be present in the application.

The `record` types require Java 16 or later; older Java projects can use equivalent POJOs. Each `public` type below resides in its own Java file in the `example.invoice` package.

### 5.1. Data Model

```java
package example.invoice;

import java.math.BigDecimal;

public record InvoiceRequest(String orderId, BigDecimal amount) {
}
```

```java
package example.invoice;

public record InvoiceResult(String orderId, String status) {
}
```

### 5.2. Business Class Invoked by the Handler

```java
package example.invoice;

import org.springframework.integration.annotation.ServiceActivator;

public class InvoiceProcessor {

    @ServiceActivator(
            inputChannel = "invoiceRequests",
            requiresReply = "true")
    public InvoiceResult process(InvoiceRequest request) {
        if (request.orderId() == null || request.orderId().isBlank()) {
            throw new IllegalArgumentException("orderId must not be blank");
        }
        if (request.amount() == null || request.amount().signum() <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }

        return new InvoiceResult(request.orderId(), "ACCEPTED");
    }
}
```

`requiresReply = "true"` expresses a contract: this step must produce a result. If the method returns no result, the framework raises an error instead of silently ending the branch.

### 5.3. Gateway as the Application Entry Point

```java
package example.invoice;

import org.springframework.integration.annotation.MessagingGateway;

@MessagingGateway(defaultRequestChannel = "invoiceRequests")
public interface InvoiceGateway {

    InvoiceResult submit(InvoiceRequest request);
}
```

The gateway hides message construction and reply waiting from business calling code. For this request–reply call, the gateway mechanism provides reply-channel metadata so the handler can send the result back.

### 5.4. Infrastructure Configuration

```java
package example.invoice;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.IntegrationComponentScan;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.messaging.MessageChannel;

@Configuration
@EnableIntegration
@IntegrationComponentScan(basePackageClasses = InvoiceGateway.class)
public class InvoiceIntegrationConfig {

    @Bean
    public MessageChannel invoiceRequests() {
        return new DirectChannel();
    }

    @Bean
    public InvoiceProcessor invoiceProcessor() {
        return new InvoiceProcessor();
    }
}
```

`@EnableIntegration` enables the required integration infrastructure. The `InvoiceProcessor` bean is processed to create an endpoint from `@ServiceActivator`. `@IntegrationComponentScan` discovers the gateway interface; merely annotating an interface does not generate a regular Java implementation class by itself.

Example invocation from a bean injected with the gateway:

```java
InvoiceResult result = invoiceGateway.submit(
        new InvoiceRequest("ORD-1001", new BigDecimal("125000")));
```

With the `DirectChannel` configuration above, the endpoint invokes the processor on the thread sending the request. The handler returns `InvoiceResult`, the framework creates a reply, and the gateway receives and returns the result to the caller.

## 6. Equivalent Configuration with Java DSL

Java DSL expresses processing steps as a fluent configuration chain. With the same payloads and gateway, you can declare the endpoint using `.handle(...)`.

This is an **alternative** to the annotation configuration in the previous section. When using this option:

- Remove `@ServiceActivator` from `InvoiceProcessor.process(...)`, keeping the business logic intact.
- Use the DSL configuration below instead of `InvoiceIntegrationConfig` above.
- Keep the `InvoiceGateway` interface and the data model types.

```java
package example.invoice;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.IntegrationComponentScan;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.messaging.MessageChannel;

@Configuration
@EnableIntegration
@IntegrationComponentScan(basePackageClasses = InvoiceGateway.class)
public class InvoiceDslConfig {

    @Bean
    public MessageChannel invoiceRequests() {
        return new DirectChannel();
    }

    @Bean
    public InvoiceProcessor invoiceProcessor() {
        return new InvoiceProcessor();
    }

    @Bean
    public IntegrationFlow invoiceFlow(InvoiceProcessor processor) {
        return IntegrationFlow.from("invoiceRequests")
                .handle(processor, "process",
                        endpoint -> endpoint.id("invoiceHandlerEndpoint"))
                .get();
    }
}
```

`.handle(processor, "process", ...)` creates a service activator calling the specified method. `invoiceHandlerEndpoint` is the ID of the created consumer endpoint; it is useful when monitoring and managing the endpoint, and is not an input channel name.

This DSL example requires the method to always return a result through `process(...)`'s own logic. It does not explicitly configure `requiresReply` like the annotation option. If the contract requires detecting `null` right at the handler, configure a reply-capable handler with `requiresReply` or use the annotation option shown earlier.

Do not enable both options simultaneously on the same `invoiceRequests` channel intending "each request calls the processor once via a single endpoint". When multiple subscribers exist on a `DirectChannel`, the dispatcher picks a subscriber according to its configuration; this is neither a sequential pipeline nor a broadcast.

### Lambda-Based Handler

A short business step can also be written using `GenericHandler` in the DSL:

```java
@Bean
public IntegrationFlow invoiceFlow() {
    return IntegrationFlow.from("invoiceRequests")
            .<InvoiceRequest>handle((request, headers) -> {
                if (request.amount() == null
                        || request.amount().signum() <= 0) {
                    throw new IllegalArgumentException(
                            "amount must be positive");
                }
                return new InvoiceResult(request.orderId(), "ACCEPTED");
            })
            .get();
}
```

This snippet is also an alternative for the `invoiceFlow` bean, not something to declare alongside the old flow. The two-argument lambda receives payload and headers and returns a result; it differs from a raw `MessageHandler`, which receives a `Message<?>` and has a `void` method.

For multi-branch or reusable business logic, extracting a separate class usually makes testing and reading the flow easier.

## 7. Reply Rules and Flow Termination

### 7.1. Where Does the Reply Go?

For a reply-capable handler, distinguish two main cases:

| Scenario | Output Handling |
| --- | --- |
| An output channel is configured | The reply is sent to that output channel |
| No output channel is configured | The handler resolves the reply target via the request's `replyChannel` mechanism |

Example of an explicit processing chain:

```java
return IntegrationFlow.from("invoiceRequests")
        .handle(processor, "process")
        .channel("invoiceResults")
        .get();
```

The result is sent to `invoiceResults`. If the request entered from a gateway and the caller is waiting for a reply, the flow downstream of `invoiceResults` must continue processing and return the result to the appropriate reply channel. Naming an output channel alone does not make a gateway automatically receive replies from arbitrary channels.

If a handler produces a result without a resolvable output target, sending the reply can fail. `channel.send(message)` merely performs a send per the channel's contract; it does not act as a request–reply gateway on its own.

### 7.2. `null`, `void`, and `requiresReply`

| Method Return Outcome | Typical Meaning |
| --- | --- |
| Non-`null` payload | Creates a reply carrying that payload |
| A `Message<?>` | Supplies payload and headers for the reply per handler mechanics |
| `null` or `void` method | No reply; may end the branch |
| No reply while `requiresReply` is enabled | Raises a missing-reply error, typically `ReplyRequiredException` |

Returning `null` can fit a one-way step. In a gateway flow expecting a response, it can cause the caller to wait until timeout or receive an empty result if configuration permits. When you need a business outcome like "not found", consider returning an object representing that status instead of an ambiguous `null`.

### 7.3. Preserving Headers

When a method returns a normal payload, a reply-capable handler typically copies appropriate headers from the request to the reply. Header propagation is still governed by framework rules and handler configuration; do not assume every header is copied verbatim.

If you build messages manually in another layer or send manually inside a custom handler, explicitly review headers used for tracing and replies, such as `correlationId`, `replyChannel`, and `errorChannel`. Losing `replyChannel` along the way can cause a request to succeed in business logic while failing to deliver the response to the caller.

Do not persist or serialize a raw `replyChannel` as a durable business field. Temporary in-memory reply channels are not addresses you can arbitrarily reuse after an application restart or across transports.

## 8. Execution Threads, Polling, and Processing Load

A handler does not by itself dictate the entire execution model. The channel and consumer endpoint determine when and on which thread the handler is called.

| Input | Thread Typically Calling Handler | Things to Watch |
| --- | --- | --- |
| `DirectChannel` | Message-sending thread | Slow handler blocks caller thread; errors usually unwind up the call stack |
| `ExecutorChannel` | Thread provided by executor | Introduces async boundary; does not inherit caller's transaction/thread-locals by default |
| `QueueChannel` with poller | Polling task thread, or executor configured for poller | Requires polling metadata; a message in the queue does not mean processing succeeded |

With a queued input, a service activator can be declared as follows in a separate configuration:

```java
import org.springframework.integration.annotation.Poller;
import org.springframework.integration.annotation.ServiceActivator;

@ServiceActivator(
        inputChannel = "pendingInvoices",
        poller = @Poller(fixedDelay = "500"))
public void consume(InvoiceRequest request) {
    // Perform a one-way task.
}
```

In this example, `pendingInvoices` must be a pollable channel bean, such as `QueueChannel`. The poller is configured with a 500 ms fixed delay; that does not mean every message is guaranteed to be processed in exactly 500 ms. Actual timing also depends on processing duration, messages per poll, schedule, and system load.

When multiple threads can call a handler, inspect shared state. A handler bean is usually reused as a singleton; an instance field such as `currentRequest` can be overwritten by concurrent executions. Keep per-request data in local variables and synchronize access to shared resources when necessary.

## 9. Error Handling at the Handler

### 9.1. Synchronous Flows

If `InvoiceProcessor` throws `IllegalArgumentException` while processing a message over `DirectChannel`, the error typically propagates back to the caller through the call stack, possibly wrapped in a messaging exception. With a gateway, how the error is forwarded also depends on the gateway's configuration.

Do not assume every error from a handler is sent to a bean named `errorChannel`. In synchronous flows, direct exception propagation is the primary behavior to account for.

### 9.2. Asynchronous and Polling Flows

With an executor or polling, the caller is no longer on the same call stack when the handler executes. Spring Integration's infrastructure provides error-handling mechanisms and `ErrorMessage` publishing, typically involving the `errorChannel` header, the default error channel, and the execution component's error handler configuration.

At an asynchronous boundary, define clearly:

- Which channel receives errors and who consumes that channel.
- How the original message or processing context can be recovered.
- Whether a caller waiting for a reply receives an error, times out, or gets a business outcome.
- Whether failed work is retried, stored for reprocessing, or stopped there.

Using a custom executor or custom error handler can change default behavior. Configuring an error channel must be accompanied by testing the actual error path.

### 9.3. Retries and Side Effects

Request handler advice can wrap the handler invocation step, such as using retry advice to retry transient failures. However, retries do not solve business duplication on their own.

For example, the invoicing service creates an invoice, but a network error occurs before the response returns. The next retry could create a second invoice if the target system does not deduplicate.

Choose a suitable idempotency key, such as a stable invoice-request identifier. `orderId` is only suitable if business rules confirm each order has at most one corresponding invoicing operation. Do not use a newly generated message ID per resend as a deduplication guarantee across attempts.

Transactions also do not automatically span every target system just because a handler sits in an integration flow. Transaction scope depends on threads, transaction managers, participating resources, and endpoint/advice configuration. An HTTP call from a handler usually does not roll back automatically with a local database transaction.

## 10. Testing Handlers at Two Levels

### 10.1. Testing Business Logic

Because the processor takes and returns business types, it can be called directly in unit tests without initializing an integration flow.

```java
package example.invoice;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

class InvoiceProcessorTest {

    private final InvoiceProcessor processor = new InvoiceProcessor();

    @Test
    void acceptsPositiveAmount() {
        InvoiceResult result = processor.process(
                new InvoiceRequest("ORD-1001", new BigDecimal("125000")));

        assertEquals("ORD-1001", result.orderId());
        assertEquals("ACCEPTED", result.status());
    }

    @Test
    void rejectsNonPositiveAmount() {
        assertThrows(IllegalArgumentException.class,
                () -> processor.process(new InvoiceRequest(
                        "ORD-1001", BigDecimal.ZERO)));
    }
}
```

This test verifies business values and rules. It does not prove the endpoint is subscribed to the right channel or that the gateway receives a reply.

### 10.2. Integration Testing Through the Gateway

With the annotation approach from Section 5, a test that boots the Spring context and invokes the gateway verifies the full request–reply path:

```java
package example.invoice;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

import static org.junit.jupiter.api.Assertions.assertEquals;

@SpringJUnitConfig(InvoiceIntegrationConfig.class)
class InvoiceFlowTest {

    @Autowired
    private InvoiceGateway gateway;

    @Test
    void returnsReplyThroughGateway() {
        InvoiceResult result = gateway.submit(
                new InvoiceRequest("ORD-1001", new BigDecimal("125000")));

        assertEquals("ORD-1001", result.orderId());
        assertEquals("ACCEPTED", result.status());
    }
}
```

This test requires JUnit Jupiter and Spring Test in addition to the example's dependencies. It verifies the path through gateway, channel, endpoint, and reply. If using the DSL approach, swap the configuration class to `InvoiceDslConfig` after removing the service activator annotation from the processor.

Additional cases to cover when applying to a real application:

| Case | What to Verify |
| --- | --- |
| Wrong payload type or missing required header | Mapping error is handled at the right boundary |
| Method returns `null` | Ends one-way or reports missing reply per contract |
| Handler throws in a synchronous flow | Caller receives the error with diagnostic cause preserved |
| Handler throws after an async boundary | Error flow receives the error; caller gets outcome or timeout as configured |
| Retry after side effects already occurred | No duplicate business outcome is created |
| Concurrent message processing | No state leaks between requests |

For tests through a queue or error channel, use bounded-timeout receive calls or condition-waiting tools. Avoid relying on fixed `Thread.sleep(...)` calls because execution timing varies across environments.

## 11. Common Design Mistakes

| Symptom | Cause to Check | Remediation |
| --- | --- | --- |
| Gateway waits and receives no result | `void`/`null` handler, reply went to another branch, lost `replyChannel` | Define reply contract and trace the entire output path |
| Sending to channel reports no subscribers | Endpoint not created, not started, or not subscribed | Check Spring beans, annotation processing, channel names, and endpoint lifecycle |
| Queue has messages but none are consumed | Missing poller, poller stopped, or previous step blocked | Inspect polling metadata, endpoint status, and logs |
| Step after handler does not run | One-way handler or `null` return value | Use a reply-producing handler if the flow must continue |
| Two handlers on same channel do not run in expected order | Confused multiple subscribers with a pipeline | Connect steps with separate channels or a DSL chain |
| Error does not appear on `errorChannel` | Synchronous path propagated exception directly or used a different error handler | Check thread, gateway, and actual error handling |
| Retry creates two invoices | Non-idempotent operation without suitable deduplication key | Design deduplication around a business identifier |
| Data from one request appears in another | Mutable state in handler shared concurrently | Use local variables or proper synchronization |

## 12. Key Reminders for Designing Handler Endpoints

A well-designed handler endpoint clearly states its input, business behavior, and output contract. Determine whether the step requires a reply before writing code, choose the channel and endpoint according to the needed execution model, and test error paths alongside the success path.

`MessageHandler` is the execution contract at the messaging layer. A service activator bridges that contract to a business method. A consumer endpoint delivers messages from a channel to a handler. A gateway provides a convenient entry point for application code and can manage request–reply calls. These four roles work together to form an integration flow that is readable, observable, and testable.
