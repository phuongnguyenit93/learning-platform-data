# JDBC Outbound Channel Adapter Running DML in Spring Integration

## 1. Problem Statement: Receiving a Message and Persisting Changes to a Database

In an integration application, an event may arrive from HTTP, Kafka, JMS, AMQP, a file, or SFTP. After validation and normalization, the system needs to **persist data to a database**: insert an order, change status, update inventory, or delete expired records. Calling `JdbcTemplate.update(...)` directly inside a Java service is one way; a **JDBC outbound channel adapter** is the way to model SQL write operations as a **message-handling endpoint** in Spring Integration.

For example: receiving a `Message<OrderSnapshot>` with payload `orderId`, `status`, and `totalAmount`, then executing:

~~~sql
INSERT INTO order_projection (order_id, status, total_amount)
VALUES (?, ?, ?);
~~~

With Spring Integration, the SQL runs when a message arrives on the **input channel**. The adapter **does not send a business reply** to an output channel. It is appropriate when the purpose of this stage is a **database write side effect** rather than reading data or retrieving a row count as the payload for a subsequent step.

This article belongs to the **Adapter JDBC** chapter of the **SPRING_INTEGRATION_ADAPTERS** module. The entire module focuses on connecting external systems using inbound/outbound adapters, gateways, pollers, and `MessageChannel`; for JDBC, key concerns are message–SQL contracts, parameter safety, transactions, retries, and connection lifecycle.

~~~mermaid
flowchart LR
    A["HTTP / Kafka / JMS / File / SFTP"] --> B["Transformer / Filter"]
    B --> C["Message<OrderSnapshot>"]
    C --> D["orderWrites: MessageChannel"]
    D --> E["JDBC outbound channel adapter"]
    E --> F["PreparedStatement / JdbcOperations"]
    F -->|"INSERT, UPDATE, DELETE"| G["Database"]
    F -.->|"DataAccessException on error"| H["Caller / error flow"]
~~~

**Do not confuse the naming:** outbound here means the direction **Spring Integration → database**. It does not open an HTTP port; it is not a JDBC inbound poller; nor is it an outbound gateway that returns a reply.

## 2. Distinguishing the Outbound Adapter from Other JDBC Endpoints

| Component | Data direction | Primary SQL | Reply message? | Purpose |
|---|---|---|---|---|
| **JDBC inbound channel adapter** | Database → MessageChannel | Polled `SELECT`; may include status update | No request-reply | Poll new records and emit messages |
| **JDBC outbound channel adapter** | MessageChannel → Database | `INSERT`, `UPDATE`, `DELETE` | **No** | One-way DML, write side effect |
| **JDBC outbound gateway** | MessageChannel → DB → reply channel | `SELECT` or DML | **Yes** | Return rows, affected row count, or generated keys as configured |
| **Stored procedure adapter/gateway** | Inbound/outbound depending on endpoint | Stored procedure/function | Depends on adapter/gateway | Procedure call contract |
| **JdbcTemplate in a service activator** | Message → service → DB | Business-specific SQL | Depends on service return value | When multiple branches, row counts, or complex domain logic are needed |

**Selection scenario:** If the requirement is “write the event to an audit table, no need to know the row count in the flow”, the outbound channel adapter fits. If you must decide “if UPDATE affects exactly one row then emit the next event, otherwise report a conflict”, consider the **JDBC outbound gateway** or a service activator using `JdbcTemplate` that returns the row count.

## 3. Data Contract and SQL DML

Suppose the application builds a fast read table `order_projection` from order events. For the demo, use H2 or a compatible SQL RDBMS:

~~~sql
CREATE TABLE order_projection (
    order_id      VARCHAR(64) PRIMARY KEY,
    status        VARCHAR(32) NOT NULL,
    total_amount  DECIMAL(18, 2) NOT NULL,
    updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

Business message:

~~~java
import java.math.BigDecimal;

public record OrderSnapshot(
    String orderId,
    String status,
    BigDecimal totalAmount) {
}
~~~

Contract for INSERT:

| Source | SQL Target | Constraint |
|---|---|---|
| `payload.orderId` | `order_id` | Non-null, unique, max 64 characters |
| `payload.status` | `status` | Valid domain status |
| `payload.totalAmount` | `total_amount` | Use `BigDecimal` for monetary values |
| DB clock | `updated_at` | Generated by DB via `CURRENT_TIMESTAMP` |
| `headers["eventId"]` (if used) | Audit column or separate idempotency table | Kept stable across redelivery/retry |

**What JDBC does not do automatically:** reorder events into the right state sequence, deduplicate messages, enforce business versioning, and decide when to ACK the source. You must design these rules separately before enabling writes.

Three fundamental DML statements:

~~~sql
-- Insert a new record
INSERT INTO order_projection (order_id, status, total_amount)
VALUES (?, ?, ?);

-- Conditional status transition
UPDATE order_projection
SET status = ?, updated_at = CURRENT_TIMESTAMP
WHERE order_id = ? AND status = ?;

-- Delete by key
DELETE FROM order_projection WHERE order_id = ?;
~~~

`?` are placeholders for **data values**, not a way to interpolate table/column names. With `PreparedStatement`, the JDBC driver binds typed parameters and prevents SQL injection from untrusted values.

## 4. Preparing Dependencies and Version Differences

Examples use Spring Boot, Spring JDBC, and the Spring Integration JDBC module. Let the Spring Boot BOM manage compatible versions:

~~~groovy
// build.gradle - dependencies
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-integration'
    implementation 'org.springframework.boot:spring-boot-starter-jdbc'
    implementation 'org.springframework.integration:spring-integration-jdbc'

    // H2 is for demo only. Production uses the real DB JDBC driver.
    runtimeOnly 'com.h2database:h2'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
~~~

~~~yaml
# application.yml - H2 demo configuration
spring:
  datasource:
    url: jdbc:h2:mem:integration_demo;DB_CLOSE_DELAY=-1
    username: sa
    password: ""
  sql:
    init:
      mode: always
~~~

If you place `CREATE TABLE` statements in `src/main/resources/schema.sql`, Spring Boot can initialize the schema at startup when configured accordingly. In production, use a migration tool like Flyway/Liquibase to version-control schema changes instead of relying on automatic table creation.

**Very important regarding the API:**

- **Spring Integration 7.0+** introduces the Java DSL factory `org.springframework.integration.jdbc.dsl.Jdbc` with `Jdbc.outboundAdapter(...)`.
- **Spring Integration 6.x** still provides the `JdbcMessageHandler` endpoint and `@ServiceActivator`/XML configuration; **do not use `Jdbc.outboundAdapter(...)`** as if it existed in 6.x.
- `JdbcMessageHandler` lives in package `org.springframework.integration.jdbc.JdbcMessageHandler` in 6.x; in the 7.x API, the package is `org.springframework.integration.jdbc.outbound.JdbcMessageHandler`. Pick imports matching your actual version and do not mix code from both generations.

The following Java DSL examples target **Spring Integration 7.x**. Section 9 covers 6.x by instantiating the handler directly.

## 5. Java DSL 7.x: INSERT with the JDBC Outbound Channel Adapter

### 5.1. MessageChannel Bean and IntegrationFlow

~~~java
package com.example.orders;

import java.math.BigDecimal;
import javax.sql.DataSource;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.integration.jdbc.dsl.Jdbc;
import org.springframework.messaging.MessageChannel;

@Configuration
@EnableIntegration
public class OrderWriteFlow {

    public record OrderSnapshot(
        String orderId, String status, BigDecimal totalAmount) {
    }

    @Bean
    public MessageChannel orderWrites() {
        return new DirectChannel();
    }

    @Bean
    public IntegrationFlow insertOrders(
            DataSource dataSource,
            @Qualifier("orderWrites") MessageChannel orderWrites) {

        return IntegrationFlow.from(orderWrites)
            .handle(Jdbc.outboundAdapter(dataSource,
                    "INSERT INTO order_projection "
                  + "(order_id, status, total_amount) VALUES (?, ?, ?)")
                .preparedStatementSetter((ps, requestMessage) -> {
                    OrderSnapshot order =
                        (OrderSnapshot) requestMessage.getPayload();
                    ps.setString(1, order.orderId());
                    ps.setString(2, order.status());
                    ps.setBigDecimal(3, order.totalAmount());
                }))
            .get();
    }
}
~~~

**Explanation:**

1. `DirectChannel` receives a message and dispatches it immediately to the subscriber/handler on the sender's calling thread, unless another component changes the execution boundary.
2. `Jdbc.outboundAdapter(dataSource, sql)` creates the outbound JDBC endpoint; under the hood it uses `JdbcMessageHandler` to execute the SQL update.
3. `preparedStatementSetter((ps, requestMessage) -> ...)` is called with the JDBC `PreparedStatement` and source message, allowing parameter binding from payload/headers.
4. There is only an `INSERT` and **no `replyChannel`/output channel** for DML results in this flow.
5. The SQL uses placeholders so `orderId`, `status`, and `totalAmount` are **bound values**, never concatenated into the SQL string.

For this example, you do not need both `SqlParameterSourceFactory` and `preparedStatementSetter`: they are **two alternative binding strategies**, not configured simultaneously.

### 5.2. Sending Messages to the Adapter

A business component can inject the channel and publish events:

~~~java
package com.example.orders;

import java.math.BigDecimal;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.stereotype.Component;

@Component
public class OrderWritePublisher {

    private final MessageChannel input;

    public OrderWritePublisher(
            @Qualifier("orderWrites") MessageChannel input) {
        this.input = input;
    }

    public void persist(String orderId, BigDecimal amount) {
        var snapshot = new OrderWriteFlow.OrderSnapshot(
            orderId, "RECEIVED", amount);

        boolean delivered = input.send(
            MessageBuilder.withPayload(snapshot)
                .setHeader("eventId", "evt-" + orderId)
                .build());

        if (!delivered) {
            throw new IllegalStateException(
                "Message was not accepted by orderWrites");
        }
    }
}
~~~

Example invocation:

~~~java
publisher.persist("ORD-1001", new BigDecimal("125000.00"));
~~~

When the `INSERT` succeeds inside a committed transaction, the database contains:

| order_id | status | total_amount |
|---|---|---:|
| ORD-1001 | RECEIVED | 125000.00 |

**`input.send(...) == true` is not a commit receipt** for every channel type. With `DirectChannel` and a synchronous JDBC handler, the SQL runs on the sender's call path; however, **an outer transaction can still roll back after `send` returns true**. If replaced by an `ExecutorChannel` or queue/poller, execution may occur on a different thread and at a different time.

## 6. UPDATE and DELETE: Writing Conditionally, Not Blindly Overwriting

### 6.1. UPDATE Based on Current State

Transitioning an order from `RECEIVED` to `PROCESSING`:

~~~java
public record OrderStatusChange(
    String orderId, String expectedStatus, String newStatus) {
}

@Bean
IntegrationFlow updateOrderStatus(DataSource dataSource) {
    return IntegrationFlow.from("orderStatusChanges")
        .handle(Jdbc.outboundAdapter(dataSource,
                "UPDATE order_projection "
              + "SET status = ?, updated_at = CURRENT_TIMESTAMP "
              + "WHERE order_id = ? AND status = ?")
            .preparedStatementSetter((ps, message) -> {
                OrderStatusChange change =
                    (OrderStatusChange) message.getPayload();
                ps.setString(1, change.newStatus());
                ps.setString(2, change.orderId());
                ps.setString(3, change.expectedStatus());
            }))
        .get();
}
~~~

`UPDATE ... WHERE order_id = ? AND status = ?` avoids overwriting when the state is no longer as expected. However, when no record matches, JDBC can return **0 rows affected without throwing an exception**. Because the outbound channel adapter produces no reply, the flow cannot rely on this adapter to automatically detect a “0 rows” condition. If business rules require that exactly one row must be updated, **use an outbound gateway or a `JdbcTemplate` handler that checks the update count**.

In the example, `orderStatusChanges` is a channel referenced by name in the DSL, so a producer must send `OrderStatusChange` messages to it. This is a **separate flow** from the INSERT flow in section 5 and does not run automatically just by declaring the bean.

### 6.2. Safe DELETE by Key

~~~java
public record DeleteOrderCommand(String orderId) { }

@Bean
IntegrationFlow deleteOrder(DataSource dataSource) {
    return IntegrationFlow.from("orderDeletes")
        .handle(Jdbc.outboundAdapter(dataSource,
                "DELETE FROM order_projection WHERE order_id = ?")
            .preparedStatementSetter((ps, message) -> {
                DeleteOrderCommand command =
                    (DeleteOrderCommand) message.getPayload();
                ps.setString(1, command.orderId());
            }))
        .get();
}
~~~

Never construct a SQL DELETE without a `WHERE` clause from untrusted data. In many domains, prefer a *soft delete* (setting `deleted_at` or a status) for auditing, recovery, and compliance.

### 6.3. INSERT, UPDATE, and DELETE Have Different Properties

| Statement | Common scenario | Issues to handle |
|---|---|---|
| `INSERT` | Create a new row | Primary key collisions, idempotency |
| `UPDATE` | Change status/values | Stale events, race conditions, row count = 0 |
| `DELETE` | Remove a record | Accidental deletion, row count = 0, foreign key constraints |
| `UPSERT/MERGE` | Create or update | DB-dependent syntax and conflict policy |

Only use `UPSERT` when you have a clear contract: which events may overwrite and how to guard against out-of-order events. A blanket “upsert everything” statement can revert data back to an old state if messages are reprocessed out of order.

## 7. Parameter Binding: Default, SpEL, and PreparedStatement

Spring Integration JDBC supports multiple ways to extract SQL parameters from a message.

### 7.1. Default Named Parameter Syntax

XML example from the Spring Integration documentation:

~~~xml
<int-jdbc:outbound-channel-adapter
    data-source="dataSource"
    channel="inventoryAudit"
    query="INSERT INTO audit_event (event_id, description)
           VALUES (:headers[eventId], :payload[text])"/>
~~~

The input is a message with an `eventId` header and a Map payload containing key `text`. Parameters `:headers[eventId]` and `:payload[text]` are resolved from the **message structure** through the default `SqlParameterSource`; this is **not arbitrary SpEL syntax**. Do not put quotes around the header name inside `:headers[eventId]` assuming SpEL map indexing.

XML is an **alternative configuration style** and does not need to be combined with the Java DSL examples above. When using XML for real, the application must include the proper namespace/schema configuration.

### 7.2. Using a Custom SqlParameterSourceFactory

When SQL needs parameter transformations (dates, text, headers, etc.) via SpEL, you can configure `ExpressionEvaluatingSqlParameterSourceFactory` with expressions like `headers['eventId']` or `payload.orderId`. This differs from default binding and must be **explicitly registered**.

Since Spring Integration **6.5**, `JdbcMessageHandler#setUsePayloadAsParameterSource(true)` lets you use the **payload directly** as the parameter binding source instead of the entire message. For example, SQL parameters `:orderId`, `:status` bind against the corresponding payload; property names must actually be readable by the parameter source.

### 7.3. PreparedStatement Callback

`MessagePreparedStatementSetter` is the explicit choice when you need `setString`, `setBigDecimal`, `setTimestamp`, `setBlob`, or specific JDBC type handling. It pairs well with Java records/DTOs and avoids relying on nested property path lookup. In the examples in sections 5 and 6, `?` corresponds to **1-based JDBC parameter indices**, not 0-based.

| Mechanism | SQL | Bound data | When to use |
|---|---|---|---|
| Default binding | `:headers[eventId]`, `:payload[key]` | Message headers/payload by property path | Concise config, simple messages |
| Custom `SqlParameterSourceFactory` | `:id`, `:createdDate` | App-defined expressions/mapper | Complex parameter transformations |
| `MessagePreparedStatementSetter` | `?`, `?`, `?` | `ps.setXxx(index, value)` | Explicit JDBC types, BLOB/CLOB, records |

**SQL safety:** named parameters and `?` apply to **values**, not table or column names. If the table name varies by tenant, select from a pre-designed allowlist/schema; never interpolate `payload.tableName` directly into SQL.

## 8. Batch DML: Iterable Payloads

Since Spring Integration 5.1, `JdbcMessageHandler` supports **batch updates** when the request message payload is an `Iterable`. Each element can be wrapped into a message carrying headers from the source message; the adapter uses `JdbcOperations.batchUpdate(...)` or the `MessagePreparedStatementSetter`-based variant.

~~~java
import java.math.BigDecimal;
import java.util.List;
import org.springframework.messaging.support.MessageBuilder;

List<OrderWriteFlow.OrderSnapshot> batch = List.of(
    new OrderWriteFlow.OrderSnapshot(
        "ORD-2001", "RECEIVED", new BigDecimal("50000.00")),
    new OrderWriteFlow.OrderSnapshot(
        "ORD-2002", "RECEIVED", new BigDecimal("75000.00"))
);

// Same input channel orderWrites, payload this time is an Iterable.
orderWrites.send(MessageBuilder.withPayload(batch)
    .setHeader("batchId", "batch-001")
    .build());
~~~

When the handler is already configured with a `preparedStatementSetter` for `OrderSnapshot` as in section 5, it can bind each element of the batch; headers from the original message are preserved for each item per handler rules. **Batching does not automatically split transactions**, and when one row fails, drivers may report different per-statement update counts/statuses.

Notes:

- Do not enable `keysGenerated` with batches: **batch updates are not supported in generated keys mode** of `JdbcMessageHandler`.
- For critical records, use an explicit transaction to avoid undesirable “partial success” states; exact behavior also depends on the JDBC driver and database.
- Bound batch sizes to avoid holding oversized messages, long transactions, or prolonged locks.
- A huge `Iterable` does not create backpressure by itself; control the source, chunking, pool, and processing rate.
- Avoid sending a `List<?>` payload if the business intent is actually **one** JSON/list stored in **one** column, as the handler may interpret it as a batch.

## 9. Spring Integration 6.x Compatibility with JdbcMessageHandler

In Spring Integration 6.x, you can declare `JdbcMessageHandler` directly and attach it to `@ServiceActivator`, instead of using the `Jdbc.outboundAdapter(...)` factory that did not yet exist in that version.

~~~java
package com.example.orders;

import java.math.BigDecimal;
import javax.sql.DataSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.ServiceActivator;
import org.springframework.integration.jdbc.JdbcMessageHandler;
import org.springframework.messaging.MessageHandler;

@Configuration
public class LegacyJdbcAdapterConfiguration {

    // Standalone DTO independent of the 7.x Java DSL section in section 5.
    public record OrderSnapshot(
        String orderId, String status, BigDecimal totalAmount) { }

    @Bean
    @ServiceActivator(inputChannel = "legacyOrderWrites")
    public MessageHandler insertOrderHandler(DataSource dataSource) {
        JdbcMessageHandler handler = new JdbcMessageHandler(
            dataSource,
            "INSERT INTO order_projection "
          + "(order_id, status, total_amount) VALUES (?, ?, ?)");

        handler.setPreparedStatementSetter((ps, message) -> {
            OrderSnapshot order = (OrderSnapshot) message.getPayload();
            ps.setString(1, order.orderId());
            ps.setString(2, order.status());
            ps.setBigDecimal(3, order.totalAmount());
        });
        return handler;
    }
}
~~~

This is an **alternative** to the INSERT flow in section 5. If the same application runs both configurations and both receive the same message, duplicate writes can occur. Do not enable both simultaneously if the goal is a single INSERT per event.

In **Spring Integration 7.x**, if you choose to instantiate `JdbcMessageHandler` manually instead of using Java DSL, import `org.springframework.integration.jdbc.outbound.JdbcMessageHandler`. Core behavior remains receiving messages and running SQL DML; verify package/API details against your exact version.

## 10. Transactions: When Is an INSERT Actually Committed?

### 10.1. DirectChannel Preserves the Sender's Thread and Transaction

By Spring Integration contract, if the input is a `DirectChannel`, the JDBC handler runs on the **same thread** as the caller. When the caller is inside a transaction managed by the same `DataSource` and appropriate transaction manager, the JDBC update can join that transaction.

~~~mermaid
sequenceDiagram
    participant Service as @Transactional Service
    participant Channel as DirectChannel
    participant Handler as JDBC outbound adapter
    participant DB as Database
    Service->>Service: Begin transaction
    Service->>Channel: send(Message<OrderSnapshot>)
    Channel->>Handler: handleMessage
    Handler->>DB: INSERT (within transaction)
    DB-->>Handler: SQL executed
    Handler-->>Channel: Return
    Channel-->>Service: send returns
    Service->>DB: COMMIT when method completes
~~~

Example:

~~~java
import java.math.BigDecimal;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
class TransactionalOrderCommand {
    private final MessageChannel orderWrites;

    TransactionalOrderCommand(
            @Qualifier("orderWrites") MessageChannel orderWrites) {
        this.orderWrites = orderWrites;
    }

    @Transactional
    public void accept(String orderId, BigDecimal amount) {
        boolean sent = orderWrites.send(
            MessageBuilder.withPayload(
                new OrderWriteFlow.OrderSnapshot(
                    orderId, "RECEIVED", amount))
                .build());
        if (!sent) {
            throw new IllegalStateException("No JDBC subscriber");
        }
        // Commits after method returns, not at the send() call.
    }
}
~~~

The example assumes `@Transactional` is invoked through a Spring-managed proxy, has a JDBC transaction manager matching the `DataSource` injected into the adapter, and has no asynchronous boundary. Do not assume a transaction exists if calling an internal method via `this.accept(...)` bypassing the proxy or using the wrong transaction manager.

### 10.2. ExecutorChannel, QueueChannel, and Pollers

If you replace `DirectChannel` with `ExecutorChannel`, dispatching switches to an executor thread. Thread-bound transactions on the caller **do not propagate automatically** to the handler. With `QueueChannel`, the message waits for a poller to consume it; the sender's transaction may commit before the JDBC adapter ever runs.

~~~mermaid
flowchart TB
    A["Sender @Transactional"] --> B{"Channel type"}
    B -->|"DirectChannel"| C["Same-thread handler; can share TX"]
    B -->|"ExecutorChannel"| D["Different thread; needs its own TX"]
    B -->|"QueueChannel + poller"| E["Different timing; poller manages TX"]
~~~

Therefore, **choosing a channel is choosing transaction boundaries and error-handling semantics**, not just performance characteristics. With Kafka/JMS sources and JDBC writes, verify the exact timing of source ACK/commit; a local database transaction does not turn Kafka + database into an atomic distributed transaction.

### 10.3. Outbox When Events Must Be Published After DB Commit

If the business requirement is “save order then publish to Kafka”, a common safe pattern is the **transactional outbox**: write both the business table and an outbox table in the **same local DB transaction**, then let a separate publisher read the outbox and send to the broker, marking the outbox status on success. This design supports retries after restarts, though idempotency is still required because the publisher may send duplicates if it crashes.

Do not claim that chaining `JDBC outbound adapter → Kafka outbound adapter` automatically provides a transaction across both systems.

## 11. JDBC Errors, Retries, and Idempotency

Spring JDBC translates many `SQLException`s into `DataAccessException` subclasses; in some cases the framework further wraps them in `MessagingException` or endpoint errors. Policies should classify errors by root cause:

| Error category | Example | Handling strategy |
|---|---|---|
| Key collision | `DuplicateKeyException` | Verify if event was already processed; do not retry indefinitely |
| NOT NULL/FK/check violation | `DataIntegrityViolationException` | Validate data and contract, route as business error |
| Database connection loss | Certain `DataAccessResourceFailureException`s | Bounded retry when conditions allow |
| Deadlock/serialization conflict | DB-specific concurrency/transient error | Backoff/jitter, retry **the entire transaction** when safe |
| Lock/statement timeout | Driver/DB exception | Tune transactions, indexes, timeouts, load |
| UPDATE 0 rows | Not necessarily an exception | Use a gateway/service to check row count |
| Invalid payload type | `ClassCastException`/conversion error | Fix transformer/validation; do not retry like a network error |

**JDBC is blocking I/O.** On a WebFlux event loop, do not run a synchronous JDBC adapter directly as if it were a non-blocking publisher. Offload JDBC work to an executor/`boundedElastic` or use a messaging model with worker threads, bounding connection pool/concurrency; switching threads does not make JDBC non-blocking.

### 11.1. Retry the Right Transaction Unit

If a transaction contains two interdependent UPDATEs, a deadlock requires retrying **the entire transactional unit** after rollback, not just retrying a single statement while assuming earlier state still holds. For database lock timeouts or transient network errors after an ambiguous commit, the outcome may be **unknown** to the caller; idempotency and querying state help prevent duplicate writes.

### 11.2. Do Not Treat Key Collisions as Always Successful

Suppose `order_id` is the PRIMARY KEY. When receiving the same event again, a second INSERT may throw `DuplicateKeyException`. If the stored data **matches the previous event exactly**, the system can treat it as an already-processed duplicate. If the same `orderId` arrives with a different amount or status, that could be a serious conflict. Compare **business event ID/version and payload hash or domain rules**, rather than “catching every duplicate key and ignoring it”.

With Kafka/JMS consumers, you can maintain a `processed_event(event_id UNIQUE, ...)` table written in the same transaction as the business change. On redelivery, check the key and committed state before deciding to ACK. If you need an exactly-once effect in the database, design explicit DB idempotency boundaries instead of expecting the broker never to redeliver.

## 12. When You Need Update Counts or Generated Keys

The outbound channel adapter only performs a side effect; it **does not publish the affected row count to a reply channel**.

- For `UPDATE ... WHERE ...`, **0 rows affected** may mean not found or that the expected old status no longer matches. If the workflow needs to know, use `JdbcOutboundGateway` or a `JdbcTemplate.update(...)` service activator returning the row count as a reply message.
- For auto-generated IDs, the JDBC outbound adapter has a `keysGenerated` option, but that is **not a response message** sent downstream. If you need generated keys to continue the flow, use an appropriately configured outbound gateway.
- For batches, generated keys mode in `JdbcMessageHandler` is not supported.

Conceptual DML gateway example:

~~~text
Message<StatusChange>
    -> JDBC outbound gateway runs UPDATE
    -> Reply payload contains UPDATED count per gateway contract
    -> Router: UPDATED == 1 ? success : conflict/not-found
~~~

Do not use an outbound adapter and then write a router reading `headers["UPDATED"]` if no stage actually produces that header/result. Verify the output of the chosen endpoint.

## 13. Performance, Locking, and Production Operations

### 13.1. Connection Pool and Concurrency Limits

Every JDBC operation uses a connection from the `DataSource` pool. If the message source sends faster than the database can process, you can hit pool exhaustion, lock contention, long transactions, or queue backlogs.

Metrics to monitor:

1. **INSERT/UPDATE/DELETE throughput:** messages received, rows executed, and commit rate.
2. **Latency:** connection wait time, SQL execution time, commit time, p95/p99.
3. **Pool:** active/idle/pending connections and connection timeouts; do not grow the pool indefinitely.
4. **DB:** locks, deadlocks, CPU, I/O, wait events, slow queries, index usage.
5. **Message flow:** queue depth, consumer lag, retries, DLQ, duplicate records, and time-to-persist.
6. **Transactions:** rollbacks and duration transactions hold locks.

Size input capacity, executor concurrency, and batch size to **database capacity**, not incoming message volume. A `DirectChannel` directly coupled to the sender exposes the caller to DB write latency; an `ExecutorChannel` decouples timing but needs bounded queues/pools and its own transactional policy.

### 13.2. Timeouts and Locks

`DataSource` pool connection timeout is different from `JdbcTemplate` query timeout or DB lock wait timeout. A query timeout does not prove a transaction rolled back unless handled properly by the transaction manager. Do not use `Thread.sleep` manually for retries inside a poller, holding threads for long periods; for high-throughput systems, consider scheduling backoff at the consumer layer.

### 13.3. SQL Security

- Use prepared statements or named parameters for **all values from payload/headers**.
- Do not let arbitrary payloads determine table names, column names, or entire SQL statements.
- Apply least-privilege DB accounts limited to required tables/operations.
- Do not log sensitive SQL parameter values or JDBC credentials.
- Use migrations to control schema and indexes based on real queries.
- Verify tenant/authorization before writing; an untrusted `tenantId` header does not replace authorization checks.

## 14. Testing the JDBC Outbound Channel Adapter

An integration test must verify **database state after the transaction completes**, not just check `send()`. Example test with Spring Boot + H2 and the schema from section 3:

~~~java
package com.example.orders;

import static org.junit.jupiter.api.Assertions.assertEquals;
import java.math.BigDecimal;
import java.util.UUID;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.support.MessageBuilder;

@SpringBootTest
class JdbcOutboundAdapterTest {

    @Autowired
    @Qualifier("orderWrites")
    MessageChannel orderWrites;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void insertsOrderIntoProjection() {
        String id = "ORD-" + UUID.randomUUID();
        var payload = new OrderWriteFlow.OrderSnapshot(
            id, "RECEIVED", new BigDecimal("20000.00"));

        boolean dispatched =
            orderWrites.send(MessageBuilder.withPayload(payload).build());
        assertEquals(true, dispatched);

        String savedStatus = jdbc.queryForObject(
            "SELECT status FROM order_projection WHERE order_id = ?",
            String.class, id);
        assertEquals("RECEIVED", savedStatus);
    }
}
~~~

The test uses `DirectChannel` and is not wrapped in a test-level rolling-back transaction. If a test uses `@Transactional` on the test method, understand that uncommitted data can still be visible from the same thread/connection; to verify an actual commit, query in a separate transaction or test via a real service call after the transaction finishes.

### 14.1. Key Test Matrix

| Case | Outcome to verify |
|---|---|
| Valid INSERT message | DB has one row with expected data |
| Resend same message | Duplicate key or idempotency behaves as designed |
| Valid UPDATE state | Modifies exactly one row, leaves others untouched |
| Stale UPDATE state | 0 rows; gateway/service detects if contract requires |
| DELETE by orderId | Deletes only the target row |
| Invalid payload | Validation/mapper fails before writing |
| Driver/DB unavailable | Error flow, rollback, and retry per policy |
| Batch with one duplicate row | Rollback/partial failure per transaction and DB driver |
| ExecutorChannel replacing DirectChannel | Transaction boundary changes; test timing/ACK |
| Kafka/JMS redelivery | Does not duplicate event effects |
| Restart after DB write before broker publish | Outbox continues publishing and idempotency prevents duplicates |

## 15. Common Design Mistakes

| Misconception | Accurate understanding |
|---|---|
| “JDBC outbound adapter uses a poller to run DML” | It handles **incoming messages**; pollers belong to the respective source/queue |
| “`Jdbc.outboundAdapter` works in all Spring Integration 6.x” | This Java DSL factory only exists from 7.0 onward |
| “`send() == true` means the database definitely committed” | The transaction may still be open or the handler may run asynchronously |
| “Duplicate-key INSERTs should be retried forever” | Usually a conflict/idempotency case, not a transient network error |
| “An UPDATE affecting 0 rows automatically throws an error” | Many valid JDBC updates return a row count of 0 |
| “Outbound adapter emits an `UPDATED=1` reply” | Returning update counts belongs to a gateway or result-returning service |
| “Using `:headers[eventId]` is arbitrary SpEL” | Default is parameter property path; SpEL requires the appropriate factory |
| “Using a prepared statement allows dynamic table names from input” | Parameter placeholders only bind **values**, not identifiers |
| “Batches are guaranteed atomic without declaring a transaction” | Explicit TX is needed; drivers/DBs may partially execute |
| “JDBC on a WebFlux event loop is automatically non-blocking” | JDBC is blocking; avoid blocking the event loop |
| “DirectChannel and ExecutorChannel preserve the same transaction” | Executors usually switch threads; transactions do not follow automatically |
| “A DB transaction can commit Kafka simultaneously” | Requires a designed outbox/XA, never automatic |

## 16. Practice Exercises

1. Create the `order_projection` schema and run the INSERT flow. Verify an `OrderSnapshot` is written with the right columns and `updated_at`.
2. Send two messages with the same `orderId` and analyze `DuplicateKeyException`; add a `processed_event` table to handle idempotency.
3. Build a conditional UPDATE flow with `WHERE order_id=? AND status=?`. Send matching and non-matching states; explain why a one-way adapter does not return the row count.
4. Replace the UPDATE flow with a JDBC outbound gateway or `JdbcTemplate` service activator returning the update count; route `0` to conflict and `1` to success.
5. Write a DELETE flow by key; compare it with soft delete and audit rules.
6. Send a `List<OrderSnapshot>` payload as a batch update. Observe SQL statements, transactions, and test when one row has a duplicate key.
7. Try mapping with `:headers[eventId]` and `:payload[text]`, then switch to `MessagePreparedStatementSetter`. Distinguish default property paths from SpEL.
8. Run with `DirectChannel` and a `@Transactional` service; deliberately throw an exception after `send` to verify rollback.
9. Switch to `ExecutorChannel` and verify the transaction does not propagate to the handler; decide where to open a new transaction.
10. Simulate a DB disconnect and recovery; design bounded retries, backoff, and dead-lettering instead of blocking threads indefinitely.
11. Connect a Kafka/JMS source or poller to the channel; determine ACK/commit timing and redelivery handling after the DB has already committed.
12. Design an outbox written in the same transaction as `order_projection`, with a separate publisher reading the outbox to send events to the broker.

**Scenario question:** An `order.paid` message is redelivered by the broker after the database already saved status `PAID`, but before the application sends ACK. If you use a JDBC outbound adapter doing a direct INSERT, what happens with the primary key? How would you design the event ID, idempotent update/outbox, transactions, and ACK so you neither lose events nor apply updates out of order?

> **Remember:** The JDBC outbound channel adapter is a **one-way message handler that runs DML**. It takes payload/headers from a `MessageChannel`, binds values into SQL, and executes INSERT/UPDATE/DELETE through `DataSource`, **without emitting an update-count reply**. To operate reliably, distinguish Java DSL versions, channel types, transaction boundaries, batching, JDBC errors, and idempotency when messages are redelivered.
