# Testing Request-Reply Gateways in Spring Integration

In integration systems, **one-way messaging** differs fundamentally from **request-reply messaging**. An outbound adapter can emit a message to a broker without waiting for a business outcome; conversely, a gateway typically matches each request with the right reply, handling errors and timeouts per contract. If tests only check `MessageChannel.send() == true`, they can miss cases where the gateway receives no reply, gets the wrong response, mixes up callers, times out, or marks success when the external system merely accepted the request.

**Testing request-reply gateways** means testing the **request → channel → processing → reply** path, including the *happy path*, invalid requests, handler errors, missing replies, late replies, concurrency, and external-system interactions. This lesson belongs to the **Testing** chapter of the `SPRING_INTEGRATION_ADAPTERS` module, where Spring Integration connects File, SFTP, HTTP, JMS, AMQP, Kafka, and databases via inbound/outbound adapters, gateways, pollers, and `MessageChannel`s.

A key distinction throughout this lesson: **internal Spring Integration gateways can be tested completely in-memory**, whereas **gateways connecting to real HTTP endpoints or brokers** also require protocol and target-state testing at the other end.

## 1. Learning Objectives

After completing this lesson, you will be able to:

1. Distinguish **gateways**, **inbound/outbound adapters**, **request-reply**, and **fire-and-forget**.
2. Explain `@MessagingGateway`, `@Gateway`, `MessageChannel`, `replyChannel`, `errorChannel`, and send/receive timeouts.
3. Write flow tests using JUnit Jupiter and Spring Test, invoking a gateway interface like a Java API.
4. Test reply payloads/types, business headers, correlation, and routing accuracy.
5. Use `GenericMessagingTemplate` to test request-reply channels directly without a gateway proxy.
6. Isolate outbound boundaries using `@SpringIntegrationTest`, `MockIntegrationContext`, or a **reply-capable** fake handler, avoiding false timeouts caused by one-way Mockito mocks.
7. Design tests for timeouts, exceptions, slow replies, concurrency, cancellation, and recovery with clear observation points.
8. Apply request-reply testing to HTTP, JMS/AMQP, Kafka, or systems without native RPC.
9. Layer unit, flow isolation, contract, transport integration, and end-to-end tests without confusing mock passes with real connectivity success.
10. Build a test matrix, fixtures, CI checklist, and exercises for operating gateways reliably.

## 2. What Is a Request-Reply Gateway?

A gateway bridges **the semantics of a response-returning operation** and **Spring Integration's messaging world**.

~~~mermaid
sequenceDiagram
    participant Caller as Java caller / HTTP client
    participant Gateway as Messaging Gateway
    participant Channel as Request Channel
    participant Handler as Service / Outbound Gateway
    participant Reply as Reply Channel
    Caller->>Gateway: submit(request)
    Gateway->>Channel: Message(payload, headers)
    Channel->>Handler: request message
    Handler->>Reply: response message
    Reply->>Gateway: matched reply
    Gateway-->>Caller: response object
~~~

A gateway can be a **Java interface proxy** generated by `@MessagingGateway`, an HTTP inbound gateway turning HTTP requests into messages and returning HTTP responses, or an outbound gateway executing request/reply against HTTP/JMS/AMQP targets.

| Component | Semantics | Example |
|---|---|---|
| **Inbound channel adapter** | Reads data and emits messages into flow, usually without replying to source. | File inbound polling adapter. |
| **Outbound channel adapter** | Receives messages and sends one-way to target. | Publish events to a Kafka topic. |
| **Inbound gateway** | Receives external requests, runs flow, returns reply. | HTTP POST returning HTTP 200 with body. |
| **Outbound gateway** | Sends requests from flow to external system, awaits response. | HTTP GET/POST calling a partner service. |
| **Messaging gateway proxy** | Lets Java code invoke a flow via a strongly typed method. | `OrderReply submit(OrderRequest request)`. |

**Not every transport natively supports RPC.** HTTP has protocol-level request/response. JMS/AMQP can implement request/reply via reply destinations and correlation. Kafka is primarily an event log; request/reply requires dedicated topic, key, correlation, and wait-state conventions if business needs demand it.

## 3. Gateway Testing Contract

Before writing tests, define what the gateway promises:

| Contract Area | Test Question | Example |
|---|---|---|
| **Request payload** | What type does the gateway accept, and which fields are required? | `OrderRequest(orderId, tenantId)`. |
| **Request headers** | Which headers carry business or tracing value? | `traceId`, `schemaVersion`. |
| **Reply payload** | Does the result have the expected type, content, and status? | `OrderReply("PO-1", "ACCEPTED")`. |
| **Reply correlation** | Do replies return to the matching request under concurrency? | Caller A never receives B's response. |
| **Reply cardinality** | Does one request expect one reply or a sequence? | Order status query returns exactly one snapshot. |
| **Timeout** | What happens if no reply arrives on time? | Returns error or timeout outcome per contract. |
| **Error mapping** | How are validation/network/5xx errors represented? | `INVALID_REQUEST`, `UPSTREAM_TIMEOUT`. |
| **No reply** | Is a missing reply falsely treated as success? | Never report `ACCEPTED` when target is silent. |
| **Late reply** | How are replies arriving after timeout handled? | Never matched to a new request. |
| **Security** | Are tenant/identity derived from trusted sources? | Never trust client-sent `role=admin` headers. |
| **Side effects** | Was the request merely sent or business-completed? | HTTP 202 differs from confirmed completion. |

**Result terminology must stay consistent.** `REQUESTED`/`SENT` differs from `ACKNOWLEDGED`, which differs from verified `COMPLETED`. If a partner service returns `202 Accepted`, that usually means the request was queued for processing, not that data is already persisted.

## 4. Map of Related Spring Integration Components

| API / Concept | Purpose | Testing Risk |
|---|---|---|
| `@MessagingGateway` | Declares a Java interface for a message flow. | Proxy not registered or pointing to wrong request channel. |
| `@Gateway` | Configures a gateway method (request/reply channel, timeout...). | Misplaced annotation or timeout not applied as expected. |
| `GatewayProxyFactoryBean` | Underlying component creating gateway proxies. | Not every flow test needs direct config of this class. |
| `MessageChannel` | Delivers requests to handlers/flows. | `send()` accepted yet no reply produced. |
| `MessageHeaders.REPLY_CHANNEL` | Reply destination when messages expect a response. | Handler emits no reply or overwrites header incorrectly. |
| `MessageHeaders.ERROR_CHANNEL` | Configured error path when flow uses it. | Falsely assuming every exception goes to error channel. |
| `MessagingTemplate` / `GenericMessagingTemplate` | Sends and receives messages directly via template. | Confusing `null` from timeout with a business result. |
| `DirectChannel` | Synchronous dispatch to subscriber. | Exceptions may propagate straight back to caller. |
| `ExecutorChannel` | Hands execution off to executor. | `send()` returns before handler finishes. |
| `QueueChannel` | Channel supporting `receive(timeout)`. | Leftover messages from other tests break assertions. |
| `@SpringIntegrationTest` | Enables Spring Integration test context support. | Does not automatically mock external endpoints. |
| `MockIntegrationContext` | Temporarily substitutes handler/source on matching endpoints. | Mock handler without reply causes gateway timeouts. |

### Default Reply Channel Is Not Always a Fixed Bean Name

A gateway proxy may attach a **temporary reply channel for the awaiting request** in headers. In flows without an explicit output channel, reply-producing handlers send responses back to that channel. Some gateways configure dedicated reply channels. Tests must understand **the actual path in the application context** rather than assuming "all replies go to a bean named `replyChannel`."

Never assign or cast `replyChannel` arbitrarily to a string or `QueueChannel` in business code. When building fake handlers, use the exact type and mechanism expected by that endpoint.

## 5. Choosing the Right Testing Layer

| Test Layer | Gateway Proxy? | Real Transport? | What Is Proven |
|---|---|---|---|
| **Unit test** | Optional (not required) | No | Validators, mappers, business rules. |
| **Flow test** | May be included | No | Request enters flow, handler returns reply, proxy maps types. |
| **Mock boundary test** | Yes | No | Message reaches right outbound handler and fake sends matching reply. |
| **Contract test** | May be included | Stub/mock server | Request/response schemas, headers, status/errors, versions. |
| **Transport integration** | Yes | Yes | Real HTTP/SFTP/JMS/AMQP/Kafka/DB behavior. |
| **End-to-end** | Yes | Yes, multiple systems | Final outcome and recovery across multiple boundaries. |

A strong test suite combines many fast tests for **payloads, routing, correlation, and failure mapping**, plus enough slower tests for **TLS, broker acknowledgments, transactions, and network recovery**.

~~~mermaid
flowchart TB
    U["Unit tests<br/>DTO / validation / mapping"] --> F["Flow tests<br/>Gateway + channels"]
    F --> M["Mock boundary tests<br/>Fake reply / timeout / error"]
    M --> T["Transport tests<br/>HTTP server / broker / DB"]
    T --> E["End-to-end tests<br/>Verified business outcome"]
~~~

## 7. Example 1 — Testing @MessagingGateway with Java DSL and JUnit

Build an internal service accepting order requests, validating `orderId`, and returning `OrderReply`. **No real HTTP or broker**: the goal is verifying the Java gateway proxy, channel wiring, and reply mapping.

### 7.1. DTOs and Interface

~~~java
package example.gateway;

public record OrderRequest(String orderId, String tenantId) {}

public record OrderReply(String orderId, String status) {}
~~~

~~~java
package example.gateway;

import org.springframework.integration.annotation.MessagingGateway;

@MessagingGateway(
        defaultRequestChannel = "orderRequests",
        defaultReplyTimeout = 2_000)
public interface OrderGateway {
    OrderReply submit(OrderRequest request);
}
~~~

Note `@MessagingGateway` goes on the **interface**, while Spring Integration generates the implementation. The project must enable appropriate gateway scanning/registration.

### 7.2. IntegrationFlow Configuration

~~~java
package example.gateway;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.IntegrationComponentScan;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;

@Configuration
@EnableIntegration
@IntegrationComponentScan(basePackageClasses = OrderGateway.class)
public class OrderGatewayTestConfig {

    @Bean
    DirectChannel orderRequests() {
        return new DirectChannel();
    }

    @Bean
    IntegrationFlow orderFlow(DirectChannel orderRequests) {
        return IntegrationFlow.from(orderRequests)
                .handle(OrderRequest.class, (request, headers) -> {
                    if (request.orderId() == null
                            || request.orderId().isBlank()) {
                        throw new IllegalArgumentException(
                                "orderId is required");
                    }
                    if (request.tenantId() == null
                            || request.tenantId().isBlank()) {
                        throw new IllegalArgumentException(
                                "tenantId is required");
                    }
                    return new OrderReply(
                            request.orderId().strip(), "ACCEPTED");
                })
                .get();
    }
}
~~~

The flow has a **reply-producing handler** returning `OrderReply`. No fixed output channel is attached in this example; in request/reply flows, replies route back to the reply channel established by the gateway. In real code using outbound HTTP/JMS gateways, the remote adapter's reply flows through matching handlers/mappings before returning to the proxy.

### 7.3. Test Class

~~~java
package example.gateway;

import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(OrderGatewayTestConfig.class)
class OrderGatewayFlowTest {

    @Autowired
    OrderGateway gateway;

    @Test
    void returnsTypedReplyForValidRequest() {
        OrderReply reply = gateway.submit(
                new OrderRequest("  PO-2048  ", "VN"));

        assertNotNull(reply);
        assertEquals("PO-2048", reply.orderId());
        assertEquals("ACCEPTED", reply.status());
    }

    @Test
    void rejectsMissingOrderId() {
        RuntimeException exception = assertThrows(
                RuntimeException.class,
                () -> gateway.submit(
                        new OrderRequest("  ", "VN")));

        assertNotNull(exception);
        // Depending on version/flow, the cause may be wrapped
        // in MessagingException or propagated to the caller.
    }
}
~~~

**What was tested:** gateway proxy registered, request enters `orderRequests`, handler transforms data, and reply maps back to `OrderReply`. **What was not tested:** HTTP, JDBC, broker, TLS, or actual external system actions.

**Error testing note:** if you need to assert exact exception types/`cause`s, define and test the project's gateway error contract. Never assume every exception propagates unwrapped through the proxy; wrapping, error channel handling, and return types vary by configuration.

## 8. Example 2 — Testing Request-Reply Directly with GenericMessagingTemplate

Sometimes you want to test **channels and handlers** without depending on the proxy interface. `GenericMessagingTemplate` supports sending a `Message<?>` and awaiting a reply.

~~~java
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.core.GenericMessagingTemplate;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(OrderGatewayTestConfig.class)
class DirectRequestReplyChannelTest {

    @Autowired
    @Qualifier("orderRequests")
    MessageChannel requestChannel;

    @Test
    void sendsMessageAndReceivesReply() {
        GenericMessagingTemplate template =
                new GenericMessagingTemplate();
        template.setReceiveTimeout(1_000);

        Message<OrderRequest> request = MessageBuilder
                .withPayload(new OrderRequest("PO-77", "VN"))
                .setHeader("traceId", "trace-77")
                .build();

        Message<?> reply = template.sendAndReceive(
                requestChannel, request);

        assertNotNull(reply);
        assertInstanceOf(OrderReply.class, reply.getPayload());
        OrderReply body = (OrderReply) reply.getPayload();
        assertEquals("PO-77", body.orderId());
        assertEquals("ACCEPTED", body.status());
    }
}
~~~

This test goes straight through `MessageChannel` and **does not exercise method mapping/conversion annotations on `@MessagingGateway`**. Keep at least one test invoking the **real proxy** if production uses that proxy.

### 8.1. Message IDs vs. Business Correlation

Every `Message<?>` has framework-managed metadata headers, yet **`MessageHeaders.ID` should not be relied upon as a cross-transport business event ID**. Across transformers, serializers, replies, or brokers, message IDs can change. Business tracing should use a contract-defined `requestId`/`traceId`.

Never assert `request.getHeaders().getId() == reply.getHeaders().getId()` unless the flow explicitly guarantees it. What matters is **matching the reply to the right request/business entity**.

## 9. Testing Request/Reply Headers and Correlation

A multi-tenant gateway must preserve security, routing, and tracing metadata:

| Header / Reference | Role | What to Test |
|---|---|---|
| `requestId` or `correlationId` | Business request identifier | Reply returns to right request after transforms/routing. |
| `traceId` | Links logs/traces | Survives outbound boundary; response logs correlate. |
| `tenantId` | Tenant context | Verified from trusted source; no cross-tenant routing. |
| `schemaVersion` | Selects payload contract | Response matches version or rejects cleanly. |
| `replyChannel` | Reply address in Spring Messaging | Not overwritten erroneously by transformers; handler replies properly. |
| `errorChannel` | Configured error path | Exceptions/business errors handled per policy, not swallowed. |
| `contentType` | Serialization convention | HTTP/JMS/AMQP/Kafka mapping preserves data types. |

### 9.1. Do Not Blindly Copy Every Header into Replies

When building replies, **preserve only contract-required metadata**. Specifically:

- `replyChannel` and `errorChannel` are Spring control headers; mishandling them can cause reply loops or leak internal channels.
- Message `id`/`timestamp` carry their own framework semantics.
- Client-supplied headers are not inherently authenticated.
- Transports have distinct headers (JMS correlation, HTTP status, Kafka topic/key); **no single fixed mapping applies to every adapter**.

### 9.2. Correlation Under Concurrent Load

~~~mermaid
sequenceDiagram
    participant A as Caller A
    participant B as Caller B
    participant G as Gateway
    participant H as Handler / Partner
    A->>G: req A, requestId=A
    B->>G: req B, requestId=B
    G->>H: req A
    G->>H: req B
    H-->>G: reply B first
    G-->>B: response B
    H-->>G: reply A second
    G-->>A: response A
~~~

In concurrency tests, force **reply B to arrive before reply A** using latches/barriers and verify both callers get the right results. Never rely on **response arrival order** to pair requests; channels, gateways, and transports must use proper correlation semantics.

## 10. Mocking an Outbound Gateway Boundary: Must Produce a Reply

`MockIntegrationContext` can substitute a compatible endpoint's handler to test **internal flow paths** without calling partners. However, for a request-reply gateway, a default Mockito mock handler sends no reply. Consequently, **the caller keeps waiting**, rather than completing the happy path.

### 10.1. The Problem with One-Way Mocks

~~~java
MessageHandler noReply = message -> {
    // Captures request but sends NO reply.
};

mockContext.substituteMessageHandlerFor(
        "partnerBoundaryEndpoint", noReply);
~~~

When the gateway awaits a response, this only works for testing **no-reply/timeouts**, not the happy path.

### 10.2. Fake Handler Replying via replyChannel

In a **synchronous flow carrying a reply channel in headers** on a substitutable endpoint, tests can use a fake:

~~~java
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.MessageHandler;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.support.MessageBuilder;

MessageHandler fakePartner = requestMessage -> {
    Object replyDestination = requestMessage
            .getHeaders().get(MessageHeaders.REPLY_CHANNEL);

    if (!(replyDestination instanceof MessageChannel replyChannel)) {
        throw new IllegalStateException(
                "Test request does not contain a MessageChannel reply");
    }

    OrderRequest request = (OrderRequest) requestMessage.getPayload();
    OrderReply reply = new OrderReply(
            request.orderId(), "PARTNER_CONFIRMED");

    replyChannel.send(MessageBuilder.withPayload(reply)
            .setHeader("traceId",
                    requestMessage.getHeaders().get("traceId"))
            .build());
};

mockContext.substituteMessageHandlerFor(
        "partnerBoundaryEndpoint", fakePartner);
~~~

**Limitation:** this fakes a **`MessageHandler` boundary** that explicitly carries a `MessageChannel` reply destination. A specific outbound gateway may use a different reply mechanism requiring mock/fake patterns suited to that endpoint and version. Never assume every outbound adapter exposes `MessageHeaders.REPLY_CHANNEL` as a `MessageChannel` or supports replacing it this way.

### 10.3. Tests Must Not Bypass the Logic Under Test

If the goal is testing transformer → router → outbound gateway, substitute **at the outbound boundary** and keep real transformers/routers. Substituting too early on the input channel lets tests pass even when flow wiring is broken.

~~~mermaid
flowchart LR
    JAVA["Gateway proxy"] --> IN["Request channel"]
    IN --> VALID["Validation"]
    VALID --> TRANSFORM["Transformer"]
    TRANSFORM --> BOUND["Outbound gateway boundary<br/>Fake handler + reply"]
    BOUND --> RESP["Reply to caller"]
    MC["MockIntegrationContext"] -. "Replace at boundary" .-> BOUND
~~~

## 11. @SpringIntegrationTest and Mock Lifecycle

A test pattern using `MockIntegrationContext`:

~~~java
import org.junit.jupiter.api.AfterEach;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.integration.test.context.MockIntegrationContext;
import org.springframework.integration.test.context.SpringIntegrationTest;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(PartnerGatewayFlowTestConfig.class)
@SpringIntegrationTest
class PartnerGatewayFlowTest {

    @Autowired
    MockIntegrationContext mockContext;

    @Autowired
    PartnerGateway gateway;

    @AfterEach
    void restore() {
        mockContext.resetBeans();
    }

    // In each @Test:
    // 1. Create a reply-capable fake handler.
    // 2. Substitute the exact endpoint ID.
    // 3. Call the gateway and assert response/correlation.
    // 4. Never hit real networks in isolation tests.
}
~~~

This serves as a **test organization skeleton**: `PartnerGateway` and `PartnerGatewayFlowTestConfig` represent your project's gateway interface/config. Key rules: assign clear endpoint IDs, substitute before invoking requests, and always run `resetBeans()`.

`resetBeans()` restores endpoint substitutions, yet **does not drain `QueueChannel`s, cancel pending requests, shut down test threads/executors, or clean external servers**. For async flows, await in-flight work or isolate contexts/fixtures before teardown.

## 12. Timeouts: Multiple Distinct Kinds

A gateway can time out at several points, so tests must identify **start point – end point – return behavior**.

| Timeout Type | Occurs When | What Tests Should Verify |
|---|---|---|
| **Request send timeout** | Cannot enqueue request to channel within limit. | Fails/times out per gateway/channel policy without duplicate sends. |
| **Reply receive timeout** | Request sent, no reply received on time. | Caller does not hang; returns null/error/exception per contract. |
| **Outbound HTTP timeout** | Connect/read to HTTP server exceeds limit. | Exception/mapping, retry/backoff, correlation. |
| **JMS/AMQP reply timeout** | Broker received request, no matching reply arrives on reply destination. | Timeout and cleanup of pending correlation. |
| **Business deadline** | Business validity window of request expired. | No side effects executed past deadline if policy forbids it. |
| **Test harness timeout** | Test itself hangs due to deadlock/bug. | Fails test with diagnostics without hanging CI. |

**Distinguish `defaultRequestTimeout` from `defaultReplyTimeout`** in gateway configs: the first governs sending the request, the second waiting for the reply. Exact handling depends on channel type, gateway proxy, return type, and version configuration. Assert **the defined contract**, rather than assuming every timeout throws the same exception.

### 12.1. No-Reply Scenario

~~~text
Given:
  gateway method expects OrderReply
  reply timeout is configured to a finite duration
  fake handler receives request but sends no reply
When:
  caller invokes gateway
Then:
  request reached the right boundary
  caller completes per defined timeout/error contract
  partner is not marked as having succeeded
  reply-wait/correlation resources are released
~~~

In some gateway setups, methods return `null` when reply timeout expires; in others, missing replies become exceptions or error results. **Define one policy at the application layer**, test against it, and document your library's actual behavior.

### 12.2. Testing Timeouts Without Using Sleep as Primary Signal

When testing missing replies, configure a **short yet realistic timeout** alongside a test safety deadline. Use a fake handler with a latch to confirm the request reached the boundary before reply timeout elapses. Never write `Thread.sleep(2_000)` assuming the gateway timed out; sleeping does not prove the request ever hit the boundary.

## 13. Example 3 — Testing a PartnerGateway with a Substitutable Outbound Boundary

Example 1 used an in-memory service activator. Now let's test a gateway that **travels to the partner boundary** without making real HTTP/JMS calls, assigning a fixed endpoint ID so `MockIntegrationContext` can substitute the handler.

### 13.1. Proxy Interface

~~~java
package example.gateway;

import org.springframework.integration.annotation.MessagingGateway;

@MessagingGateway(
        defaultRequestChannel = "partnerRequests",
        defaultReplyTimeout = 1_000)
public interface PartnerGateway {
    OrderReply submit(OrderRequest request);
}
~~~

### 13.2. Flow Config with a Sentinel Handler

~~~java
package example.gateway;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.IntegrationComponentScan;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.messaging.MessageHandler;

@Configuration
@EnableIntegration
@IntegrationComponentScan(basePackageClasses = PartnerGateway.class)
public class PartnerGatewayFlowTestConfig {

    @Bean
    DirectChannel partnerRequests() {
        return new DirectChannel();
    }

    @Bean
    IntegrationFlow partnerFlow(DirectChannel partnerRequests) {
        MessageHandler sentinel = message -> {
            throw new IllegalStateException(
                    "Unexpected invocation of real partner boundary");
        };

        return IntegrationFlow.from(partnerRequests)
                .handle(sentinel,
                        endpoint -> endpoint.id("partnerBoundaryEndpoint"))
                .get();
    }
}
~~~

In this test context, the **sentinel handler** represents the replaceable boundary. In production, that boundary could be an `HttpRequestExecutingMessageHandler`, JMS/AMQP outbound gateway, or custom handler. The substitution mechanism must fit the endpoint type.

### 13.3. Happy-Path Test with a Fake Reply

~~~java
package example.gateway;

import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.integration.test.context.MockIntegrationContext;
import org.springframework.integration.test.context.SpringIntegrationTest;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.MessageHandler;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(PartnerGatewayFlowTestConfig.class)
@SpringIntegrationTest
class PartnerGatewayReplyTest {

    @Autowired
    MockIntegrationContext mocks;

    @Autowired
    PartnerGateway gateway;

    @AfterEach
    void cleanup() {
        mocks.resetBeans();
    }

    @Test
    void gatewayReturnsReplyFromFakePartner() {
        MessageHandler fake = requestMessage -> {
            Object destination = requestMessage.getHeaders()
                    .get(MessageHeaders.REPLY_CHANNEL);
            assertInstanceOf(MessageChannel.class, destination);

            MessageChannel replyChannel =
                    (MessageChannel) destination;
            OrderRequest request =
                    (OrderRequest) requestMessage.getPayload();

            boolean delivered = replyChannel.send(
                    MessageBuilder.withPayload(new OrderReply(
                            request.orderId(), "PARTNER_CONFIRMED"))
                            .build());
            assertTrue(delivered);
        };

        mocks.substituteMessageHandlerFor(
                "partnerBoundaryEndpoint", fake);

        OrderReply reply = gateway.submit(
                new OrderRequest("PO-123", "VN"));

        assertNotNull(reply);
        assertEquals("PO-123", reply.orderId());
        assertEquals("PARTNER_CONFIRMED", reply.status());
    }
}
~~~

This example aims to **simulate a reply at a synchronous flow boundary**. If your app's gateway uses complex reply mechanics, payload conversion, or transport-specific reply destinations, adapt the fake to match that contract. The test only verifies that the proxy/flow delivers requests to the boundary and returns replies to the caller; it **does not** test real network requests.

### 13.4. Known Limitation of This Pattern

Flow tests have no HTTP client, JMS session, serializer, or remote endpoint. Even if you replace the sentinel with the real adapter in production while tests keep mocking the handler, transport bugs remain unmeasured. That **does not make the test useless**; it simply defines its boundary of responsibility.

## 14. Reproducible No-Reply/Timeout Testing

When testing missing responses, verify the mock **received the request** before observing the caller's outcome.

### 14.1. Controlled Scenario

~~~java
import java.util.concurrent.CountDownLatch;

CountDownLatch received = new CountDownLatch(1);
MessageHandler noReply = requestMessage -> {
    received.countDown();
    // Intentionally send NO reply to test timeout.
};

mocks.substituteMessageHandlerFor(
        "partnerBoundaryEndpoint", noReply);
~~~

With a 1-second `defaultReplyTimeout`, verify:

1. The boundary received the request (latch/counter).
2. The caller does not wait forever.
3. The outcome is `null`, an exception, or a mapped business error **matching the chosen contract** rather than guessing.
4. The partner is not marked as having completed the request.
5. No pending request/correlation or blocked wait thread leaks after timeout.

**Note:** `CountDownLatch` only confirms the boundary ran; **it does not control the gateway's internal clock**. For business-time rules (like event deadlines), separate unit tests using `Clock`. Some gateways configure reply timeouts independently; check actual measurement points and behavior in your version.

### 14.2. Never Equate Timeout with Confirmed Target Failure

If an HTTP client times out after sending a POST, the partner service **may have succeeded** while the response was lost. Likewise, a JMS/AMQP reply may simply be delayed even though the request was consumed.

Therefore:

- **Gateway timeout** means **the caller did not receive confirmation on time**.
- **Business failure** means evidence exists that the target did not execute the request.
- **Unknown outcome** requires lookup/readback, especially for non-idempotent actions.

Never blindly auto-retry money transfers, invoice creation, or permission grants without an idempotency key and state verification.

## 15. Error Handling: Technical Errors, Business Errors, and errorChannel

Errors can arise at multiple layers:

| Error Layer | Example | How to Test |
|---|---|---|
| **Validation/domain** | Missing `orderId` or tenant | Unit + flow tests; outbound boundary never called. |
| **Synchronous handler exception** | Service activator throws | Caller receives exception or mapped error per policy. |
| **Async handler failure** | Handler runs on executor and throws | Observe error channel/callback/future. |
| **HTTP transport** | 4xx/5xx, connect/read timeout | HTTP stub/test server. |
| **JMS/AMQP transport** | Broker unavailable, broken reply destination | Broker integration test. |
| **Serialization** | Cannot deserialize response JSON/DTO | Contract + transport tests. |
| **Protocol-level negative response** | HTTP 409, business reject code | Verify mapping never turns rejection into success. |
| **Late/misrouted reply** | Reply arrives after request stopped waiting | Never matched to new request; logged/metered properly. |

### 15.1. Do Not Assume Every Exception Goes Through errorChannel

With `DirectChannel` and synchronous handlers, exceptions propagate to the caller. With `ExecutorChannel` or async listeners, errors route through `ErrorMessage`/error handlers if configured. With outbound gateways, client exceptions or response error mappings may become error messages or exceptions.

Tests must follow **the flow's actual error path**. Never assert on `errorChannel` if config doesn't publish errors there, and never expect `assertThrows` on the calling thread when errors happen on an executor.

### 15.2. Inspect Root Causes Rather Than Only Wrapper Classes

When a handler throws `IllegalArgumentException`, Spring Messaging may wrap it in a messaging exception. Check:

- Expected error type/cause or mapped application error code.
- `requestId`/`traceId` preserved along the error path.
- Never return `ACCEPTED` after a handler fails.
- Error payloads leak no tokens, passwords, unnecessary stack traces, or customer PII.

If the public API specifies returning `INVALID_REQUEST`, testing **the public contract** matters more than internal wrapper classes that may change across framework upgrades.

## 16. Testing Slow Replies or Replies Arriving After Timeout

Slow replies cause subtler bugs than missing replies:

1. The gateway times out and the caller handles the failure, yet the worker still processes the request.
2. The partner emits reply A after request A expired.
3. A new request B shares a business key or reuses correlation IDs carelessly.
4. The stale reply is read by a consumer and wrongly paired with request B.

### 16.1. Scenario to Construct

~~~mermaid
sequenceDiagram
    participant A as Caller A
    participant G as Gateway
    participant P as Partner
    A->>G: request A (correlation A)
    G->>P: request A
    Note over G: Reply timeout expires
    G-->>A: Timeout / Unknown outcome
    P-->>G: Late reply A
    Note over G: Never paired with request B
~~~

### 16.2. Meaningful Assertions

- Pending correlation A was released or managed per retention policy.
- Late reply A is discarded, logged, or routed to a late-reply queue per design.
- Request B receives no mismatched reply.
- Audit trail by `requestId` enables state reconciliation if side effects occurred.
- Retries enforce idempotency and bounds if caller retries after timeout.

Avoid long `Thread.sleep` calls in fakes; use latches/barriers to hold the partner's reply and release it explicitly past the configured timeout inside a bounded integration test.

## 17. Testing Concurrent Requests

When a gateway serves 100 parallel requests, a classic bug is **shared mutable state** storing "the latest request" or "the pending reply," causing caller A to receive caller B's response.

### 17.1. Out-of-Order Reply Scenario

~~~text
Caller A sends order PO-A
Caller B sends order PO-B
Partner receives both
Partner replies PO-B first
Partner replies PO-A second

Expected:
  Caller A → reply orderId PO-A
  Caller B → reply orderId PO-B
~~~

In the test:

1. Use two requests with distinct `requestId`/`orderId` values.
2. Launch two tasks/futures and use a barrier to confirm both requests arrived.
3. Have the fake or test server hold reply A and send reply B first.
4. Assert each caller receives the reply matching its business key.
5. Verify no lost/duplicated responses and no lingering pending requests afterward.
6. Enforce timeouts and cleanup so failures never hang.

### 17.2. Avoid Fake Concurrency Tests

If the flow uses `DirectChannel` and the fake handler replies inline, two sequential calls on the same thread **do not test concurrency**. Create genuine concurrency at a controlled boundary or use a server/broker responding out of order.

With JMS/AMQP, correlation typically ties together request ID, reply destination, and message ID per contract; with HTTP, each connection/request carries its own request/response pairing, though application code can still mismatch if it uses shared state. **Reply matching must be tested against the real transport.**

## 18. Request-Reply on HTTP Outbound Gateways

HTTP is intuitive: the gateway sends a request to a server, waits for status, headers, and body, and maps them into a reply.

~~~mermaid
sequenceDiagram
    participant Flow as Integration Flow
    participant GW as HTTP Outbound Gateway
    participant S as Partner HTTP Server
    Flow->>GW: Message<OrderRequest>
    GW->>S: HTTP POST /orders
    S-->>GW: HTTP status + JSON body
    GW-->>Flow: Message<OrderReply> or error
~~~

### 18.1. HTTP Contract Matrix

| Case | Test Server Returns | What to Verify |
|---|---|---|
| Synchronous success | 200 + JSON | Accurate payload, status/header mapping, reply reaches caller. |
| Created | 201 + body/location | Not confused with 200; response schema accurate. |
| Accepted for background work | 202 + tracking ID | Status is `ACCEPTED`, not falsely `COMPLETED`. |
| Invalid input | 400 + error JSON | Structured error mapping; no pointless retries. |
| Unauthorized | 401/403 | Credentials never logged; matches public error contract. |
| Conflict | 409 | Deduplication policy and business key enforced. |
| Rate limited | 429 + retry metadata | Backoff per policy; never floods partner. |
| Server error | 500/503 | Bounded retries, circuit breaker/alerting if configured. |
| No response | Read timeout | Unknown/timeout outcome; look up before retrying side effects. |
| Slow HTTP response | Controlled delay | Reply timeout, cleanup, and late completion. |
| Broken schema | 200 with missing JSON fields | Never treat HTTP 200 as automatic business success. |

### 18.2. Choosing HTTP Testing Tools

- **Flow isolation:** mock outbound handler with a reply-capable fake, no sockets opened.
- **Mock HTTP client/server:** use `MockRestServiceServer` for `RestTemplate`-based clients when configuration allows; choose matching tools for other stacks.
- **HTTP stub test server:** WireMock, MockWebServer, or ephemeral servers verify method, path, headers, JSON body, status, and timeouts at the HTTP boundary.
- **End-to-end:** against real sandbox targets, verify side effects and recovery—not just status codes.

**Never treat `MockRestServiceServer` as a real socket server.** It tests the configured client layer; TLS, proxies, and connection pooling require real network-level tests.

### 18.3. HTTP Inbound Gateways

For an inbound HTTP gateway, **the caller is an HTTP client**, not a Java method:

~~~text
Given: POST /orders with valid JSON request
When:  request enters Spring Integration HTTP inbound gateway
Then:  request maps to a message on the right channel
And:   flow builds reply of the right type
And:   HTTP status/body/headers match contract
And:   timeout/validation/errors map to consistent responses
~~~

When using Spring MVC, `MockMvc` works in a matching context. Verify **HTTP status codes**, not just internal message payloads. If the inbound adapter runs on another stack, use an appropriate client/test server rather than forcing everything into `MockMvc`.

## 19. JMS and AMQP Request-Reply

JMS/AMQP are environments where requests and replies can travel over **two queues/destinations** or temporary reply destinations. Replies can arrive late, get redelivered, or disappear if the broker is unavailable.

### 19.1. Factors to Test

| Aspect | JMS | AMQP (e.g., RabbitMQ) |
|---|---|---|
| Request destination | Configured JMS queue/topic | Exchange/routing key/queue per binding |
| Reply destination | `JMSReplyTo` or request-reply convention | `reply-to`/queue or direct reply-to per setup |
| Correlation | `JMSCorrelationID` / message ID per contract | Correlation ID and `reply-to` per convention |
| Reply timeout | Gateway reply wait duration | Template/gateway reply wait duration |
| Failure semantics | Sessions, transactions, acknowledgments | Consumer ACK/NACK, requeue, and publisher confirms |
| Duplicate handling | Provider redelivery/transactions | Requeue/redelivery/retries |

Never equate a **broker ACK** with a **business reply**. A broker ACK may confirm only that a message was accepted or consumed, while the partner may not even have computed the response yet.

### 19.2. What Broker Integration Tests Must Cover

1. Request publishes to the expected destination.
2. Worker consumes request and emits reply with matching correlation.
3. Gateway returns the right reply under concurrency.
4. Worker sends no reply; caller times out cleanly.
5. Worker replies too late; pending correlation is handled safely.
6. Broker disconnects before/between request and reply; recovery works.
7. Reply payload fails schema check; never marked successful.
8. Worker redelivers request; business side effects stay idempotent.
9. Shutdown/restart while requests are pending; no leaks.
10. Replies arriving from the wrong tenant or destination are rejected.

Use a test broker or compatible container to verify **queues, reply-to, TTL, acks, and redelivery**. Mockito mocking a handler cannot prove any of these semantics.

### 19.3. Reply Destinations and Security

Reply destinations must never be constructed from unvalidated client inputs in a way that sends sensitive responses to another user's queue/tenant. Test tenant isolation, authorization, and redacted logging.

## 20. Kafka: Request-Reply Is an Application-Defined Protocol

Kafka is primarily built for **event streaming**, not short-lived RPC by default. If an organization implements request/reply over Kafka, define:

- Request topic and reply topic; matching topic/key/partitioning.
- Stable `requestId`/`correlationId`.
- Which consumer/group reads replies and how it pairs them with pending requests.
- Timeouts and retention when responses arrive late.
- Duplicates/redelivery and business idempotency.
- Serializer/schema versions and topic ACLs.
- Behavior when the caller restarts with pending requests in flight.

### 20.1. Why Kafka Replies Differ from HTTP

An HTTP response is bound to one request/connection; Kafka stores records in topics and consumers read independently by partition/offset. An **application-layer correlation mechanism** is mandatory to route replies back to the right caller.

~~~mermaid
sequenceDiagram
    participant C as Caller
    participant A as Gateway application
    participant R as Kafka request topic
    participant W as Worker
    participant P as Kafka reply topic
    C->>A: requestId=R-41
    A->>R: event R-41
    R->>W: event R-41
    W->>P: response correlation R-41
    P->>A: response R-41
    A-->>C: matched response
~~~

### 20.2. Minimum Tests

1. A/B correlation when replies arrive in reverse order.
2. Missing reply before timeout.
3. Reply arriving after timeout—never paired with another request.
4. Consumer restart/rebalance with pending requests.
5. Duplicate reply never completes the caller twice.
6. Offset commit/redelivery and consumer idempotency.
7. Invalid schema and replies from the wrong tenant.

Never claim end-to-end exactly-once merely because Kafka supports transactions in part of the pipeline. A worker writing to a DB or calling HTTP outside Kafka still needs idempotency, outbox/inbox, or readback per design.

## 21. File, SFTP, and JDBC: Not Every Inbound Has a Direct Reply

File and SFTP inbound adapters normally **emit messages via polling**, with no caller waiting for an HTTP-like reply. JDBC inbound adapters likewise query due rows and push them into the flow.

| Source | Common Pattern | What to Test |
|---|---|---|
| **File inbound** | Polls files and emits `Message<File>` | File readiness, filters, retries, metadata; no reply expected by file producer. |
| **SFTP inbound** | Syncs remote files and emits messages | Downloads, host keys, duplicates, reconnects; no automatic RPC reply. |
| **JDBC polling inbound** | Queries pending records and emits messages | Due times, transactions, claims/locks, rollbacks. |
| **JDBC outbound gateway** | Request returns DB query/update results per config | SQL, mapping, transactions, and reply payloads. |
| **Specialized File/SFTP outbound gateway** | Some flows return I/O metadata/results | Verify what replies the gateway actually builds; don't assume every adapter replies. |

If a business workflow wants to send results back to the file uploader, design an **explicit response channel** such as a result file, callback API, or event; that is a separate contract, not a default reply channel on file inbound.

## 22. Testing Operations with Side Effects and Idempotency

Request-reply does not guarantee exactly-once side effects. Example:

~~~text
T0 caller sends requestId=R-9 "create invoice"
T1 worker persists invoice in database
T2 reply is lost on the network
T3 caller times out and retries R-9
T4 worker receives request R-9 again
~~~

Without idempotency, two invoices can be created. Gateway tests must pair with business side-effect tests:

| Scenario | Expected Outcome |
|---|---|
| New request R-9 | Creates exactly one invoice and returns ID. |
| Retry same R-9 after timeout | Returns existing result or matching state; creates no second invoice. |
| Two concurrent callers with same idempotency key | Single final outcome per policy; no race duplicate. |
| Same key with different payload | Handles conflict per contract; never silently overwrites. |
| Reply received, caller crashes before recording | Safe lookup by request ID and safe retry. |

### Sample Request Contract

~~~json
{
  "requestId": "req-invoice-009",
  "operation": "CREATE_INVOICE",
  "schemaVersion": 2,
  "tenantId": "VN",
  "invoiceSourceId": "order-2048",
  "requestedAt": "2026-11-23T09:20:00Z"
}
~~~

Never assume framework message IDs or JMS/Kafka IDs serve as business idempotency keys. Business conventions should specify **`tenant + operation + requestId` scope** or an equivalent key to prevent collisions.

## 23. Synchronous vs. Asynchronous Gateways

### 23.1. Synchronous Gateways

A method like `OrderReply submit(OrderRequest)` typically blocks the caller until a response or timeout. With `DirectChannel` and an inline-replying handler, tests can assert immediately after the call.

### 23.2. Asynchronous Gateways

Depending on version and config, apps may use `Future`/`CompletableFuture`, reactive types, or event-driven callbacks. In those cases:

- Verify when the result/future completes, not merely when the message was sent.
- Verify error/timeout propagation to the future/callback.
- Verify whether cancellation aborts work or only stops the caller from waiting.
- Avoid shared mutable state that mixes replies across requests.
- Ensure executors and pending tasks are cleaned up.

**Cancelling a `Future` does not automatically undo side effects at target HTTP/DB/brokers.** If business rules allow true cancellation, build and test a dedicated cancellation protocol or compensating action.

### 23.3. Using Latches/Barriers Instead of Sleep

An out-of-order reply test can use:

~~~java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

CountDownLatch bothRequestsReceived = new CountDownLatch(2);
CountDownLatch allowReplyA = new CountDownLatch(1);

// Fake handler A:
//   bothRequestsReceived.countDown()
//   allowReplyA.await(timeout, TimeUnit.SECONDS)
//   send reply A
//
// Fake handler B:
//   bothRequestsReceived.countDown()
//   send reply B first
//
// Test:
//   start callers A and B
//   assert bothRequestsReceived.await(...)
//   assert reply B returns to caller B
//   allowReplyA.countDown()
//   assert reply A returns to caller A
~~~

This is a **Java concurrency fixture scenario/pseudocode**, not a complete program. Implement thread-safe fakes, bounded timeouts, and cleanup in `finally`/`@AfterEach`. If the flow still runs synchronously on a single thread, fake B cannot run while A blocks the thread; configure an executor or parallel callers appropriately.

## 24. Defining Completion Points and Measuring Latency

A gateway has multiple observation timestamps:

~~~mermaid
flowchart LR
    START["callerAt<br/>Caller starts"] --> SENT["sentAt<br/>Sent to channel"]
    SENT --> OUT["outboundAt<br/>Sent to transport"]
    OUT --> ACK["ackAt<br/>Transport responds"]
    ACK --> REPLY["replyAt<br/>Gateway receives reply"]
    REPLY --> DONE["businessVerifiedAt<br/>Target outcome verified"]
~~~

| Metric | Suggested Formula | Distinction to Keep |
|---|---|---|
| **Gateway response latency** | `replyAt − callerAt` | Time until caller gets response; business work may still be pending. |
| **Channel dispatch latency** | `sentAt − callerAt` | Reveals queuing/backpressure before handler. |
| **Transport round-trip time** | Time from outbound send to transport response | Does not mean business state persisted. |
| **Gateway timeout rate** | Timed-out requests / cohort requests | Target outcome may be unknown. |
| **Late reply rate** | Replies arriving after pending timeout / total observed replies | Requires consistent detection and denominator. |
| **Correlation mismatch count** | Replies failing to match valid pending requests | KRI for lost data or cross-caller leaks. |
| **Business confirmation latency** | `businessVerifiedAt − callerAt` | Requires side-effect evidence at target system. |
| **Pending request age** | Age of unresolved requests | Critical when external partners stall. |

**Use the right clock:** within one process, `System.nanoTime()` fits elapsed duration measurements; timestamps in logs/traces need UTC or explicit offsets. Across machines, account for clock skew and never claim millisecond precision without synchronized clocks.

For percentiles (P50/P95/P99), never measure only completed requests: report **pending count, overdue count, and timeout count** too. Excluding 5% hung requests makes successful-request P99 look artificially great.

## 25. Ensuring Valid Replies, Security, and Tenant Isolation

Gateways sit at the caller boundary. Routing or serialization bugs can leak responses into another tenant.

### Cases to Verify

| Risk Area | What Tests Must Prove |
|---|---|
| **Tenant isolation** | Tenant A's request never receives Tenant B's response even with identical `orderId`. |
| **Authorization** | Only data the caller is permitted to see enters the reply. |
| **Untrusted headers** | Client-supplied `role` or `tenantId` is never trusted without validation. |
| **Response redaction** | HTTP/broker errors never leak secrets, bearer tokens, or internal system details. |
| **Replay attacks** | Repeated request IDs/keys never re-execute sensitive side effects outside policy. |
| **Payload validation** | Schema/version-invalid responses are rejected or quarantined. |
| **Message size** | Oversized payloads are bounded cleanly without exhausting memory. |
| **TLS/certificates** | Real transports validate server certs; never disable verification to pass tests. |
| **Reply spoofing** | Unauthorized workers/reply senders cannot forge responses. |
| **Correlation collisions** | Identical request IDs across two tenants never collide. |

Never dump entire messages into logs on timeout just for debugging convenience if payloads hold personal data, tokens, or credentials. Log `requestId`, `traceId`, status, timestamps, and redacted fields.

### External Error Contracts Differ from Internal Errors

An internal handler might throw `NullPointerException`; an HTTP gateway must never return a raw stack trace to clients. Map it to an opaque error code, log with appropriate access controls, and retain correlation for troubleshooting. Tests must assert both **the public response contract** and **internal audit/tracing**.

## 26. MockIntegrationContext: Safety Rules and Limits

Effective use of `MockIntegrationContext` requires:

1. **Exact endpoint ID.** A `MessageChannel` or `IntegrationFlow` name is not automatically the endpoint ID.
2. **Substitute before the flow runs.** Active inbound pollers/listeners can fire side effects before mocking takes effect.
3. **Match endpoint semantics.** Reply-expecting gateways suffer false timeouts with one-way mocks.
4. **Do not mock too deeply.** Keep transformers, validators, routers, and correlation logic under test.
5. **Never spy on network-hitting adapters** without blocking real calls.
6. **Reset after tests.** `resetBeans()` does not replace queue/executor/broker cleanup.
7. **Avoid parallel runs on shared contexts.** Two tests must not concurrently substitute the same endpoint in one Spring context.
8. **Respect evidence boundaries.** Mock passes do not prove HTTP/TLS, JMS transactions, or Kafka offsets.

### 26.1. Inbound Gateway Testing Differs from Outbound Gateway Testing

When testing an **HTTP inbound gateway**, HTTP request/response mapping and status codes must be exercised at the HTTP port. Replacing an internal handler only tests message processing, not whether the web endpoint receives requests and sends responses properly.

When mocking an **outbound gateway**, the fake must satisfy reply semantics; transport-specific mappings still require separate contract tests.

### 26.2. Never Leak Pending Replies into Subsequent Tests

In `@AfterEach`:

- Await/cancel tasks per test contract and ensure in-flight work settles.
- Stop endpoints/lifecycles started by the test if applicable.
- Call `resetBeans()` for substituted endpoints.
- Drain test channels and clear fake state.
- Close test-owned clients, servers, and broker containers.

Cached contexts can expose substituted handlers or stale replies to the next test. If safe cleanup isn't possible, isolate the context or use `@DirtiesContext`, without using it to hide sloppy fixture design.

## 28. Case Study: Order Status Gateway Over Partner HTTP

### 28.1. Business Requirements

An application exposes `lookup(orderId, tenantId)`, calls a partner API, and returns order status. The partner may return `200`, `404`, `429`, `503`, or drop connections. Requirements:

- Every caller receives data **strictly for its order and tenant**.
- Valid responses return a DTO with `requestId`/`orderId`, status, and observation timestamp.
- Missing replies must never become `ORDER_NOT_FOUND`.
- Bounded retries avoiding partner overload.
- Error messages never expose API tokens.

~~~mermaid
flowchart LR
    CALLER["Caller"] --> GW["OrderStatusGateway"]
    GW --> VALID["Validate tenant / requestId"]
    VALID --> REQ["Build HTTP request"]
    REQ --> HTTP["HTTP outbound gateway"]
    HTTP --> MAP["Map partner response"]
    MAP --> GW
    HTTP --> ERR["Timeout / HTTP error mapping"]
    ERR --> GW
~~~

### 28.2. Layer A — Unit Tests

Test request validation, tenant authorization, mapping `PartnerStatusDto` to `OrderStatusReply`, and distinguishing `NOT_FOUND` from `UNKNOWN_UPSTREAM`.

Output: valid DTOs and error codes with zero Spring context or HTTP.

### 28.3. Layer B — Flow Isolation

Register `@MessagingGateway` and the real request channel; replace the HTTP outbound boundary with a reply-capable fake handler.

Output: business headers intact, request passes transformers/routers, reply reaches Java method cleanly without network calls.

### 28.4. Layer C — HTTP Transport Tests

Use an HTTP test server returning:

| Response | Expectation |
|---|---|
| 200 + valid JSON | Returns partner status and trace. |
| 404 + valid error body | Maps to `ORDER_NOT_FOUND` if contract permits. |
| 429 + `Retry-After` | Backs off per policy without infinite retries. |
| 503 | Transient error or recovery path; never reports order absent. |
| Timeout after server receives request | Unknown outcome; handling depends on operation semantics. |
| 200 + schema-invalid JSON | Reports contract error, never fabricates a reply. |

Output: verifies HTTP method, URL, body, response mapping, and client-layer errors.

### 28.5. Layer D — Concurrency and E2E

Send two concurrent requests for distinct orders and make the server reply in reverse order. Verify responses never cross. Test restarts/gateway timeouts and inspect pending counts/metrics. Read-only lookup APIs carry lower duplicate-side-effect risk on retry than mutating APIs, yet still require load caps and accurate response handling.

### 28.6. Acceptance Evidence

- Passing tests at every layer with names matching their exact scope.
- Tenant-isolated source/target fixtures.
- `requestId` and `traceId` present in redacted logs/test evidence.
- Tests covering errors, timeouts, late replies, and concurrency.
- Clear documentation of what was proven vs. what remains unverified.

## 30. Organizing the Test Suite and CI/CD

Suggested layout:

~~~text
src/test/java/...
  gateway/
    OrderGatewayFlowTest.java
    OrderGatewayValidationTest.java
    PartnerGatewayBoundaryTest.java
    GatewayTimeoutTest.java

  e2e/
    OrderStatusWorkflowTest.java
~~~

### Execution and Isolation

1. **Unit/flow tests run frequently** on every pull request.
2. **HTTP/broker integration tests** run in isolated or ephemeral environments on adapter changes or pre-release.
3. **Concurrency/timeout tests** use latches, barriers, controlled test servers, and bounded timeouts.
4. **End-to-end tests** prove target outcomes for critical workflows.
5. Each test uses **distinct `requestId`, tenant, queue/topic, and data** to avoid cross-contamination.
6. Tests never share Mockito mocks or static pending maps across parallel runs.
7. After each test, stop test-owned endpoints, reset substitutions, and close resources.
8. Include correlation in test reports/logs without passwords, tokens, or unnecessary PII.

### Distinguishing Infrastructure Failures

When a test broker/server fails to start, that is a **test infrastructure failure**, not a gateway logic bug. Reports should separate:

- Context bean failed to initialize;
- Request never reached channel;
- Mock failed to emit reply;
- Response mapped incorrectly;
- Logic-induced timeout;
- Transport endpoint unavailable;
- Target side effect wrong.

Never mark tests as passed when transports are unavailable. If CI skips container tests due to environment limits, report the **coverage gap** openly rather than calling a mock-only suite transport-verified.

## 31. Common Anti-Patterns

| Anti-Pattern | Consequence | Fix |
|---|---|---|
| Asserting only `send() == true` | Unknown whether caller received valid reply. | Invoke gateway and assert payload/error. |
| One-way Mockito mock on a gateway | Gateway times out even when upstream flow works. | Use a reply-capable fake per contract. |
| Mocking the whole flow | Misses wiring/routing bugs. | Mock strictly at the external boundary. |
| Treating HTTP 202 as completed | Target still processes asynchronously. | Track via ID and verify final confirmation. |
| Treating broker ACK as business reply | Worker may not have processed request. | Separate reply message/correlation. |
| Skipping correlation checks | Callers receive wrong replies under load. | Test out-of-order replies. |
| Testing only sequential single requests | Misses shared mutable state bugs. | Run parallel callers with barriers/latches. |
| Skipping missing/late reply tests | Pending requests hang or leak. | Test timeouts and cleanup. |
| Hardcoded 2-second sleep | Flaky in CI; proves nothing at boundary. | Bounded waits and observation points. |
| Retrying write requests after timeout unchecked | Duplicates side effects. | Idempotency keys and readback. |
| Catching all exceptions and returning SUCCESS | Hides mapping/transport bugs. | Explicit error contract; no false success. |
| Pairing replies by arrival order | Slow/out-of-order replies hit wrong caller. | Transport-appropriate correlation keys. |
| Using Spring message ID as sole business ID | Changes across transforms/replays. | Stable business request ID. |
| Conflating send and reply timeouts | Hard to diagnose backpressure vs. downstream lag. | Separate milestone metrics. |
| Ignoring tenant/security headers | Cross-tenant data leaks. | Validate trusted sources; test authorization. |
| Forgetting `MockIntegrationContext.resetBeans()` | Mocks leak into next test. | `resetBeans()` and task cleanup. |
| Never testing against real server/broker | Misses protocol/serialization bugs. | Transport integration tests. |

## 33. Acceptance Checklist

- [ ] **Gateway classified accurately**: inbound, outbound, or Java messaging proxy.
- [ ] **Request/reply contract documented**: payload, type, headers, correlation, outcome, timeout.
- [ ] **Real `@MessagingGateway` proxy tested** when production uses a proxy.
- [ ] **Channel request-reply tested** independently for wiring where appropriate.
- [ ] **Reply payload and type asserted**, not merely request sending.
- [ ] **Business and security headers verified**, never trusting client-supplied role/tenant.
- [ ] **Outbound gateway fakes emit proper replies**, avoiding one-way mocks for happy paths.
- [ ] **Missing replies, timeouts, and late replies** have dedicated scenarios.
- [ ] **Concurrency/out-of-order reply tests** included rather than matching by arrival order.
- [ ] **Sync/async errors observed properly** via exceptions, error paths, or futures.
- [ ] **Retries/idempotency and reconciliation** tested where side effects can finish before reply loss.
- [ ] **HTTP/JMS/AMQP/Kafka tested per transport semantics**, never mistaking ACKs for business replies.
- [ ] **Real transport tests run in isolated environments** for in-scope protocols.
- [ ] **Bounded timeouts, isolated fixtures, `resetBeans()`, and cleanup** in place.
- [ ] **Zero credentials/PII leaked in logs or test fixtures**.
- [ ] **Test results carry boundary-accurate evidence**, stating what remains unproven.

## 34. Summary

**Testing request-reply gateways** in Spring Integration goes well beyond seeing `send()` succeed. A sound gateway **accepts requests, routes to the right handler/target, returns replies of the right type and content, preserves per-caller correlation, handles timeouts and errors per contract, and prevents mismatched responses or duplicate side effects on retry**.

`@MessagingGateway` and Java DSL enable fast in-memory **flow tests**; `GenericMessagingTemplate` tests message channels directly; and `MockIntegrationContext` substitutes outbound boundaries with **reply-capable fakes** to observe orchestration without network calls. Even so, **HTTP statuses/TLS, JMS/AMQP reply-to and acknowledgments, Kafka correlation/offsets, transactions, network timeouts, and target business outcomes** still require transport or end-to-end tests where appropriate.

A trustworthy gateway test suite always answers: **where each request went, which reply belongs to which caller, when timeouts fire, which boundary failed, which side effects are verified, and which outcomes remain unknown**. That foundation keeps external adapter and gateway integrations predictable, diagnosable, and safe.
