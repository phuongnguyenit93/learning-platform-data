# @MessagingGateway Calling an Integration Flow

## 1. Objectives and Role of a Messaging Gateway

In the **Integration Flow Creation** chapter of the **SPRING_INTEGRATION_ADAPTERS** module, we saw that a Spring Integration flow exchanges data through `Message<?>`, `MessageChannel`, and endpoints. The module aims to connect external systems using inbound/outbound adapters, gateways, and pollers across scenarios involving files, SFTP, HTTP, JMS, AMQP, Kafka, and databases, while controlling message contracts, errors, and connection lifecycles.

**`@MessagingGateway`** is an annotation used to declare a **Java interface** that the application can call like a normal service, while Spring Integration generates a proxy that turns each method invocation into a message sent to an integration flow. If the flow returns a result, the proxy converts the reply message back into the method's return value.

For example, business code only needs:

~~~java
PaymentResponse response = paymentGateway.submit(
        new PaymentRequest("ORD-1001", new BigDecimal("250000")),
        "trace-ord-1001");
~~~

Meanwhile, behind that call may sit a **validate → transform → service activator** pipeline, or connections to HTTP, SFTP, JMS, AMQP, Kafka, and databases.

After this lesson, learners will be able to:

- Declare a `@MessagingGateway` interface and register its proxy with Spring.
- Distinguish `defaultRequestChannel`, `requestChannel`, `replyChannel`, and `errorChannel`.
- Map method parameters to **payload/headers** and convert replies into Java types.
- Build **request–reply** and **one-way** flows matching explicit contracts.
- Analyze threading, timeouts, exceptions, retries, and missing-reply scenarios.
- Test through the real gateway within a Spring context.
- Choose a messaging gateway when a Java API is needed instead of confusing it with external protocol inbound/outbound gateways.

**Core point:** the gateway here is a **Java-method entry point** into an integration flow. It does not create HTTP connections by itself, does not actively poll files, and does not guarantee that an external system succeeded.

## 2. From a Method Call to a Message

Suppose a business class needs to process an order. Without Spring Integration, it would call a chain of services directly. With a messaging gateway, the business class depends on an interface while the integration steps live inside the flow.

~~~mermaid
sequenceDiagram
    participant C as Java caller
    participant G as @MessagingGateway proxy
    participant CH as request MessageChannel
    participant F as IntegrationFlow
    participant H as handler
    C->>G: submit(PaymentRequest, traceId)
    G->>CH: Message<PaymentRequest> + headers
    CH->>F: filter → transform
    F->>H: Message<PaymentCommand>
    H-->>G: PaymentResponse via reply channel
    G-->>C: PaymentResponse
~~~

| Concept | Role |
| --- | --- |
| **Gateway interface** | Defines the Java API for callers, e.g. `submit(PaymentRequest)`. |
| **Gateway proxy** | Generated by Spring Integration; builds a message from arguments and sends it to the request channel. |
| **Request channel** | Delivers the message from the proxy to the flow or endpoint. |
| **Payload** | Business data, e.g. `PaymentRequest`. |
| **Headers** | Metadata such as `traceId`, `correlationId`, `replyChannel`, `errorChannel`. |
| **IntegrationFlow** | Validates, transforms, routes, and invokes services or adapters. |
| **Reply channel** | Return path back to the gateway when the method returns a result. |
| **Method result** | Reply payload or message converted into the gateway method's return type. |

In request–reply mode, the gateway attaches routing metadata so replies return to the specific waiting invocation. If the final stage of the flow returns an object, the framework builds a reply message and sends it to the corresponding `replyChannel`. When a handler produces no reply, a method expecting a return value may block until timeout.

## 3. Distinguishing Four Commonly Confused Gateway Concepts

| Concept | Input | Output | When to Use |
| --- | --- | --- | --- |
| `@MessagingGateway` | Java method called by internal code. | Message into Spring Integration and reply back to the method. | Providing a typed Java API for a flow. |
| HTTP inbound gateway | HTTP request from an external client. | Message into the flow and HTTP response to the client. | Building a request–reply HTTP endpoint. |
| Outbound gateway | Message inside a flow. | Request to an external system with reply brought back into the flow. | Calling HTTP/JMS/AMQP/... and processing the response. |
| Polling inbound adapter | Poll schedule triggers `MessageSource`. | One-way message into a channel. | Files, SFTP, JDBC, or sources requiring periodic polling. |

`@MessagingGateway` operates at the **Java caller ↔ message flow boundary**. An outbound gateway operates at the **message flow ↔ external request–reply system boundary**. Both can work together: Java code calls a messaging gateway, the flow uses an HTTP outbound gateway to call a partner API, and the response returns to the caller.

For a one-way pipeline, a service activator or outbound adapter can terminate the flow without producing a reply. The gateway method signature should match (for example returning `void`), rather than leaving the caller waiting for a non-existent result.

## 4. Minimal Configuration

In a Spring Boot project using Spring Boot's dependency management, Maven can declare:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-integration</artifactId>
</dependency>
~~~

A typical gateway interface:

~~~java
@MessagingGateway(defaultRequestChannel = "payments.requests")
interface PaymentGateway {
    PaymentResponse submit(PaymentRequest request);
}
~~~

For Spring to generate a proxy for the interface, gateway scanning/registration is needed. In a Spring Boot application, you can place `@IntegrationComponentScan` on the configuration or application class:

~~~java
@SpringBootApplication
@IntegrationComponentScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
~~~

`@IntegrationComponentScan` discovers gateway interfaces within the scanned package scope. `@SpringBootApplication` performs standard component scanning for regular Java beans, but do not assume a `@MessagingGateway` interface will always be registered without proper gateway scanning/registration.

The `@MessagingGateway` annotation goes on an **interface** representing the contract used by callers. Never call `new PaymentGateway()`: the proxy is managed by Spring and injected via constructor or retrieved from the application context.

## 5. Complete Example: Java Method Calling an IntegrationFlow

Problem: the order intake service must check that an order has a valid ID and a positive amount, transform it into a processing command, and return an `ACCEPTED` status. Everything runs in memory to keep focus on the gateway. This example does not capture real money or call a bank system.

### 5.1. Creating the Application and Flow

Place the following code in `PaymentGatewayApplication.java`, package `demo.gateway`. The example uses Java 17+ with `record` types and compatible Spring Integration 6.x / Spring Boot.

~~~java
package demo.gateway;

import java.math.BigDecimal;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.integration.annotation.IntegrationComponentScan;
import org.springframework.integration.annotation.MessagingGateway;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.messaging.handler.annotation.Payload;

@SpringBootApplication
@IntegrationComponentScan
public class PaymentGatewayApplication {

    public static void main(String[] args) {
        SpringApplication.run(PaymentGatewayApplication.class, args);
    }

    @Bean(name = "payments.requests")
    MessageChannel paymentRequestChannel() {
        return new DirectChannel();
    }

    @Bean
    IntegrationFlow paymentFlow() {
        return IntegrationFlow.from("payments.requests")
                .filter(PaymentRequest.class,
                        request -> request.orderId() != null
                                && !request.orderId().isBlank()
                                && request.amount() != null
                                && request.amount().signum() > 0,
                        endpoint -> endpoint.throwExceptionOnRejection(true))
                .transform(PaymentRequest.class,
                        request -> new PaymentCommand(
                                request.orderId(), request.amount()))
                .handle(PaymentCommand.class,
                        (command, headers) -> new PaymentResponse(
                                command.orderId(),
                                "ACCEPTED",
                                (String) headers.get("traceId")))
                .get();
    }

    @Bean
    CommandLineRunner demo(PaymentGateway gateway) {
        return args -> {
            var request = new PaymentRequest(
                    "ORD-1001", new BigDecimal("250000"));
            var response = gateway.submit(request, "trace-ord-1001");
            System.out.println(response);
        };
    }
}

@MessagingGateway(
        defaultRequestChannel = "payments.requests",
        defaultReplyTimeout = "5000")
interface PaymentGateway {

    PaymentResponse submit(
            @Payload PaymentRequest request,
            @Header("traceId") String traceId);
}

record PaymentRequest(String orderId, BigDecimal amount) {}

record PaymentCommand(String orderId, BigDecimal amount) {}

record PaymentResponse(
        String orderId, String status, String traceId) {}
~~~

The `record` types and interface in the example are package-private in the same file for brevity. In a real application, put each interface/DTO in its own file and maintain an appropriate scan package.

### 5.2. Data Flow

With the invocation:

~~~java
gateway.submit(
        new PaymentRequest("ORD-1001", new BigDecimal("250000")),
        "trace-ord-1001");
~~~

Execution steps:

1. Spring injects a proxy implementing `PaymentGateway`.
2. The proxy uses `@Payload` to set `PaymentRequest` as the payload and `@Header("traceId")` to add the header.
3. The proxy sends `Message<PaymentRequest>` to channel `payments.requests`. The flow registers a consumer on this channel.
4. `filter` validates `orderId` and `amount`. If the data is invalid, `throwExceptionOnRejection(true)` raises an exception instead of silently dropping the message.
5. `transform` converts `PaymentRequest` into `PaymentCommand`. Essential headers, including `traceId` and the reply path, are preserved by the framework across standard payload transformation.
6. `handle` constructs `PaymentResponse` from the payload and headers. Because the gateway expects a result, the reply returns to the proxy via the corresponding reply channel.
7. The caller receives `PaymentResponse("ORD-1001", "ACCEPTED", "trace-ord-1001")` as a Java object.

The example uses `DirectChannel`, so flow steps normally execute on the thread calling the gateway. Using a gateway **does not automatically make execution asynchronous**.

### 5.3. Why Doesn't the Example Need an Explicit Reply Channel?

The gateway sets up reply routing when a method with a return value is called; the final handler returns an object so the framework builds the reply message. Because this is a simple request–reply chain, there is no need to declare `.channel("payments.replies")`.

If the flow explicitly transfers messages to another channel, uses a router, split/aggregate, or protocol endpoints with different reply conventions, verify that the reply path remains intact and is not overwritten or lost. Only specify `outputChannel`, `defaultReplyChannel`, or `replyChannel` when there is a concrete architectural reason and you understand where replies are consumed.

## 6. Mapping Gateway Parameters to Payload and Headers

A gateway method is a **Java contract** for an integration flow. Explicitly indicate whether each parameter represents business payload or metadata.

~~~java
@MessagingGateway(defaultRequestChannel = "orders.input")
interface OrderGateway {

    OrderResult submit(
            @Payload OrderCommand command,
            @Header("tenantId") String tenantId,
            @Header("correlationId") String correlationId);
}
~~~

`OrderCommand` and `OrderResult` in this snippet are application-defined DTOs.

| Method Element | Resulting Message | Notes |
| --- | --- | --- |
| `@Payload OrderCommand command` | Payload is `OrderCommand`. | Caller's Java type does not have to match the payload type after a transformer. |
| `@Header("tenantId") String tenantId` | `tenantId` header contains the string. | Consumers may use it for routing, but must authorize data before trusting it. |
| `@Header("correlationId") String correlationId` | Header for tracing/reconciliation. | Must be preserved across steps if still needed. |
| Return type `OrderResult` | Reply payload must be convertible to `OrderResult`. | Mismatched types can cause conversion errors at the caller. |

Spring Integration supports many parameter-mapping styles, but an explicit gateway interface with **one typed payload + named headers** is usually easiest to read and test.

**Do not use headers as a dumping ground for all business data.** The payload represents the command or event; headers carry coordination, reconciliation, and routing metadata. When crossing HTTP, JMS, or Kafka, internal headers such as `replyChannel` may be Spring `MessageChannel` objects—do not serialize and broadcast all headers externally. Use protocol-appropriate header mappers or DTOs.

### 6.1. Preserving Headers Across Transformers

In the section 5 example, `transform` changes the payload while `traceId` is still needed afterward. When returning a plain payload object, Spring Integration's transformer preserves necessary context on the outbound message. If a handler constructs `Message<?>` manually or strips headers via a custom mapper, verify that critical headers (`correlationId`, `replyChannel`, `errorChannel`) remain intact.

Never repurpose `replyChannel` just to carry a correlation ID. They serve different roles: correlation IDs track business operations, whereas the reply channel dictates **where the reply message must be sent**.

## 7. Per-Method Channel Configuration with @Gateway

If one gateway interface exposes multiple operations targeting different flows, use `@Gateway` to specify the channel per method:

~~~java
@MessagingGateway
interface ShippingGateway {

    @Gateway(requestChannel = "shipping.estimate")
    Quote estimate(ShippingRequest request);

    @Gateway(requestChannel = "shipping.submit")
    void submit(ShippingRequest request);
}
~~~

In this example, `ShippingRequest` and `Quote` are application-defined types; channels `shipping.estimate` and `shipping.submit` must have corresponding receiving endpoints.

- `estimate(...)` is request–reply because it returns `Quote`.
- `submit(...)` is one-way because it returns `void`; the flow is not required to produce a reply.
- `@Gateway(requestChannel = ...)` sets the channel for a specific method.
- `@MessagingGateway(defaultRequestChannel = ...)` fits when most methods share one default channel.

Do not point multiple methods at a single channel and assume Spring automatically distinguishes business operations by method name. If multiple command types share a channel, use distinct payload types, a command header, or a router with a clear contract.

## 8. Request–Reply vs. One-Way Gateways

### 8.1. Request–Reply

This applies when the method has a return value:

~~~java
@MessagingGateway(defaultRequestChannel = "inventory.check")
interface InventoryGateway {
    InventoryResult check(InventoryQuery query);
}
~~~

A flow receiving `InventoryQuery` must emit an appropriate reply so the caller receives `InventoryResult`. If the final handler returns `null`, a filter drops the message, or an adapter reaches a target that does not reply, the gateway may wait until its timeout expires.

### 8.2. One-Way (Fire-and-Forget at the Contract Level)

When the caller only needs to submit a command into a flow:

~~~java
@MessagingGateway(defaultRequestChannel = "audit.events")
interface AuditGateway {
    void record(AuditEvent event);
}
~~~

The terminal endpoint can be a `@ServiceActivator` returning `void` or a one-way outbound adapter:

~~~java
@ServiceActivator(inputChannel = "audit.events")
public void publishAudit(AuditEvent event) {
    auditClient.send(event);
}
~~~

`AuditEvent` and `auditClient` are provided by the application; the snippet assumes the method sits in a component-scanned Spring bean.

**Note:** a `void` method does not mean sending happens in the background. With a `DirectChannel`, the caller can still block until the outbound handler finishes, and synchronous exceptions can still propagate back to the caller. If a channel offloads work to another thread, the method may return sooner, but you must design separate error handling, durability, and acknowledgements.

### 8.3. Designing Business Outcomes Instead of Ambiguous Booleans

If the caller needs to know whether a partner accepted a request, do not just return `true` when `MessageChannel.send(...)` succeeds. Define a `SubmissionResult` or `PaymentResponse` with clear business codes, statuses, timestamps, partner references, and semantics.

Distinguish clearly:

- **Accepted:** the integration layer accepted the request.
- **Submitted:** the request was sent to the external system and acknowledged at the protocol level.
- **Completed:** the external system finished business processing per reconciliation rules.

These states do not necessarily happen at the same time. Request–reply gateways suit targets with reasonable response times; for long-running processes, return a tracking ID first and notify completion later.

## 9. Timeouts: How requestTimeout and replyTimeout Differ

`@MessagingGateway` supports timeout settings, commonly:

~~~java
@MessagingGateway(
        defaultRequestChannel = "orders.requests",
        defaultRequestTimeout = "2000",
        defaultReplyTimeout = "5000")
interface OrdersGateway {
    OrderResult submit(OrderCommand command);
}
~~~

`OrderCommand` and `OrderResult` are application-defined DTOs.

| Attribute | What It Bounds | Accurate Interpretation |
| --- | --- | --- |
| `defaultRequestTimeout` | Wait time to **send the message into the request channel** when the channel supports blocking sends. | Most relevant for bounded queues/channels where sending can block. |
| `defaultReplyTimeout` | Time the gateway **waits for a reply message** after sending the request. | When no reply arrives on the return path, defines caller timeout behavior. |
| HTTP/JDBC/JMS client timeout | Communication time with the external system. | Must be configured on the client/adapter; cannot simply be replaced by gateway reply timeout. |

**Common misconception:** with `DirectChannel`, invoking the handler happens synchronously inside the send call. If an internal handler holds the thread for 30 seconds, `defaultReplyTimeout = "5000"` does not interrupt that call right at 5 seconds. Configure network client timeouts and execution bounds accordingly.

A flow using `ExecutorChannel`, `QueueChannel`, or a broker can switch execution to another thread; the gateway then finishes sending the request and waits for the reply up to the timeout. If a reply arrives after the gateway has timed out, decide how to log late responses and prevent duplicate submissions if the caller retries.

### 9.1. Setting Timeouts Based on End-to-End Time Budgets

If a request passes through:

~~~text
Gateway → Queue → Validation → HTTP outbound gateway → Partner API
~~~

the overall budget must account for queue dwell time, processing time, network timeouts, retries, and response latency. Setting a reply timeout shorter than a normal retry cycle can make callers report errors while the target is still processing. Setting it too long holds waiting requests and can exhaust resources.

Define explicit policies for in-flight requests, expired requests, late replies, and indeterminate outcomes.

## 10. Exceptions, Error Channels, and Failure Paths

### 10.1. Errors on Synchronous Flows

In the section 5 flow using `DirectChannel`, `filter` is configured with `throwExceptionOnRejection(true)`. When a request is invalid, the framework throws an exception and the gateway can propagate it back to the Java caller rather than returning a successful `PaymentResponse`.

Similar errors can arise from transformers, service activators, or outbound clients. The exception type observed by the caller may depend on how the framework wraps exceptions, so tests should check the appropriate exception type and root cause when needed.

### 10.2. Errors in Asynchronous Handlers

Once a message leaves the gateway-calling thread, worker exceptions do not automatically jump back into a Java method call that already returned. Spring Integration can publish an `ErrorMessage` to an error channel when the endpoint, poller, or adapter is configured to do so. A consumer is needed to handle it and decide how to respond to the caller.

If you configure `errorChannel` on the gateway or message, do not just log the error and forget to send a reply to a method waiting for one. A clear error policy specifies **where error messages are recorded**, **what the caller receives**, **whether retries occur**, and **which events require reconciliation**.

### 10.3. Filters Silently Dropping Messages

In request–reply flows, a filter returning `false` and dropping the message can leave the caller waiting until timeout. Two design paths exist:

- Invalid requests are **errors**: the filter throws an exception or routes to a branch producing a business error.
- Rejected requests are **normal business outcomes**: the flow returns a response indicating rejection instead of dropping the message.

Avoid letting timeouts serve as an implicit signal for "invalid data".

### 10.4. When the External System Processed the Request, Yet the Gateway Timed Out

Suppose a flow sends an invoice-creation command to an HTTP outbound gateway. The partner creates the invoice, but the response is lost. The Java method times out; a caller retry could create a second invoice.

Design a stable **idempotency key** per business operation, partner status-check mechanisms, or transactional outbox and reconciliation. Retries must distinguish confirmed non-processed errors from indeterminate outcomes. `@MessagingGateway` does not turn message delivery into exactly-once on its own.

## 11. Combining Gateways with Different MessageChannel Types

| Channel | Typical Behavior | Impact on Gateway |
| --- | --- | --- |
| `DirectChannel` | Subscriber runs directly on sender's thread. | Gateway method may block while handler runs; synchronous exceptions usually propagate. |
| `QueueChannel` | Messages buffered in queue for another endpoint to poll. | Requires poller/consumer; if method expects a reply, budget for queue wait time. |
| `ExecutorChannel` | Hands off execution to a `TaskExecutor`. | Request/reply crosses thread boundaries; requires appropriate timeouts and error handling. |
| `PublishSubscribeChannel` | Sends the same message to multiple subscribers. | If used for request–reply, define which subscriber replies and how multiple replies are handled. |

An application can use a request–reply gateway over `DirectChannel` for fast validation, offload long tasks to a queue, return a tracking ID early, and notify completion via events or callbacks.

Do not blindly swap `DirectChannel` for `ExecutorChannel` just to "speed things up": if ingress outpaces egress, you will build up backlogs, exhaust threads or queues, or lose error visibility without proper resource bounds.

## 12. Combining Messaging Gateways with External System Adapters

The gateway is the Java API into the flow, while other adapters/gateways determine how the flow interacts with external systems:

~~~mermaid
flowchart TB
    APP["Java service / REST controller"]
    G["@MessagingGateway"]
    CH["MessageChannel"]
    FLOW["Validate → Transform → Route"]
    H1["HTTP outbound gateway"]
    H2["JMS / AMQP / Kafka outbound adapter"]
    H3["File / SFTP outbound adapter"]
    H4["JDBC / database service activator"]
    APP --> G --> CH --> FLOW
    FLOW --> H1
    FLOW --> H2
    FLOW --> H3
    FLOW --> H4
    H1 -. "Response if any" .-> G
~~~

| Need | Suitable Design | What to Verify |
| --- | --- | --- |
| Java service calls partner HTTP API and needs the result. | `@MessagingGateway` → transform → HTTP outbound gateway → reply. | Timeouts, HTTP status codes, response schema, idempotency. |
| Java service requests publishing a Kafka event. | `void` gateway method → outbound adapter. | Producer ack/timeout, delivery semantics, callback error handling. |
| Generate file or upload via SFTP. | Gateway → transform to file/content → outbound adapter. | Temp write + rename, already-sent files, retries/duplicates. |
| Persist order to database. | Gateway → service activator/JDBC outbound. | Transactions, unique constraints, rollback/retries. |
| File/SFTP inbound poller already pushes messages into the flow. | Inbound adapter + poller → channel → flow; business services can be reused. | No need to invoke a gateway to trigger an already-polling source. |

A single flow can serve multiple entry points if they standardize on the same **payload type and header contract**. However, a Java request's reply path differs from one-way file polling: files have no caller waiting synchronously for a result. When feeding both sources into one flow, specify where results and errors go for each source.

## 13. Testing Through the Real Gateway

Unit tests calling a transform method directly only prove transformation logic. To verify that the proxy, channels, flow, and replies work together, write an integration test booting the Spring context and calling the **gateway interface**.

Add `spring-boot-starter-test` in test scope:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

Place the following JUnit 5 example in `PaymentGatewayApplicationTest.java` under package `demo.gateway`:

~~~java
package demo.gateway;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import java.math.BigDecimal;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.messaging.MessagingException;

@SpringBootTest
class PaymentGatewayApplicationTest {

    @Autowired
    PaymentGateway gateway;

    @Test
    void returnsTypedResponseWithTraceId() {
        PaymentResponse result = gateway.submit(
                new PaymentRequest(
                        "ORD-2001", new BigDecimal("120.50")),
                "trace-test-2001");

        assertEquals("ORD-2001", result.orderId());
        assertEquals("ACCEPTED", result.status());
        assertEquals("trace-test-2001", result.traceId());
    }

    @Test
    void rejectsNonPositiveAmount() {
        assertThrows(MessagingException.class, () -> gateway.submit(
                new PaymentRequest("ORD-2002", BigDecimal.ZERO),
                "trace-test-2002"));
    }
}
~~~

The test verifies that:

1. Spring creates the `PaymentGateway` proxy bean.
2. Method calls route to the right channel and enter `IntegrationFlow`.
3. Filter/transform/handler execute and preserve the `traceId` header.
4. The gateway converts the reply into `PaymentResponse`.
5. Invalid requests fail instead of returning success.

With other configurations or versions, exceptions may be wrapped in a different `MessagingException` subtype; in that case, assert the root cause related to message rejection. Note that this test does **not** exercise external systems or real delivery semantics.

### 13.1. Testing Timeouts and Late Replies

To test reply timeouts meaningfully, use a flow with an asynchronous endpoint or queue so sending the request finishes before a reply is produced. Test specifically:

- Messages with no consumer or no reply produced.
- Handlers returning replies later than the timeout threshold.
- Handlers throwing exceptions on worker threads, both with and without an error channel consumer.
- Callers retrying after a timeout while the first business operation is still running.
- Concurrent requests requiring accurate correlation.

Do not rely on arbitrary sleeps as definitive proof of timeout behavior; use test synchronization primitives with explicit timeouts, and inspect outcomes and logs via correlation IDs.

## 14. Common Errors and How to Fix Them

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| Spring reports gateway bean not found. | Interface not scanned by `@IntegrationComponentScan`; package outside scan scope. | Check annotations and package placement, or register the gateway bean explicitly. |
| Gateway call does not reach the flow. | Wrong `defaultRequestChannel` name or no endpoint subscribed to the channel. | Match channel bean names with `IntegrationFlow.from(...)`/`@ServiceActivator`. |
| Gateway waits until timeout. | Flow produces no reply, filter drops message, reply goes to wrong channel, or handler takes too long. | Trace request/reply paths, filter rejections, timeout config, and endpoints. |
| `@Header` missing in handler. | Missing annotation, misspelled header name, or stripped by a mapper. | Verify contract and test messages through the proxy. |
| Returned data has wrong type. | Reply payload incompatible with Java return type. | Standardize response DTO or add an appropriate transformer. |
| `void` still blocks the caller. | `DirectChannel` and outbound client operate synchronously. | Enforce client timeouts; adopt async/queues if needed with proper backpressure. |
| Retrying after timeout creates duplicates. | Target succeeded but response was lost, or retries lack stable IDs. | Idempotency keys, reconciliation, outbox, or transaction status checks. |
| Caller cannot catch exceptions. | Processing moved to another thread. | Design `errorChannel`, DLQ/quarantine, and business error feedback channels. |
| Reply timeout does not abort a slow HTTP call. | Timeout only governs waiting for gateway reply while synchronous handler blocks. | Configure timeouts on the HTTP client/outbound gateway and end-to-end time budgets. |
| Two sources share a flow, yet one waits forever for a reply. | Request–reply and one-way contracts were not separated. | Define distinct entry points, output conventions, and error flows per source. |

## 15. Extended Practice

**Problem:** build an `OrderGateway` for a Java application sharing a flow that normalizes orders before sending them to a partner system.

Functional requirements:

1. Create a `@MessagingGateway` interface with `submit(OrderRequest request, @Header("traceId") String traceId)` returning `OrderReceipt`.
2. The flow validates non-empty `orderId`, `quantity > 0`, and supported `currency`; invalid messages must produce a clear error outcome.
3. A transformer converts `OrderRequest` to `PartnerOrder` and sends it to a simulated client. The client returns a partner reference code on success.
4. Add another gateway method `enqueue(...)` returning `void`, backed by a channel and handler suited for background execution.
5. Add tests for success, validation failure, header propagation, and reply timeout when an async endpoint produces no result.
6. Simulate a request processed by the partner whose reply was lost; design an `idempotencyKey` and reconciliation logic to prevent duplicates.
7. If replacing the target with an HTTP outbound gateway or Kafka outbound adapter, document which completion point counts as success for the Java method.

**Pass criteria:** callers need no knowledge of internal flow endpoints; gateway methods have explicit return types; tests invoke the real proxy interface; errors and timeouts follow clear conventions; and all parties agree on payload/headers, acks, and deduplication.

**Hints:** the gateway is a proxy turning Java calls into messages; request/reply flows depend on channels, method contracts, and endpoints; timeouts must distinguish message sending, reply waiting, and external calls. Reliability also depends on transactions, acknowledgements, and idempotency.

## 17. Key Takeaways

`@MessagingGateway` lets you **invoke an integration flow as a typed Java API**. The interface defines how callers pass payloads and headers into the system, the request channel delivers messages to the flow, and the reply channel returns results when the contract requires a response.

When connecting files, SFTP, HTTP, JMS, AMQP, Kafka, or databases, a Java gateway provides a clean entry point for internal services while adapters and outbound gateways handle external communication. A complete design must clarify **one-way vs. request–reply**, timeouts, data mapping, error paths, completion semantics, and duplicate prevention after retries.
