# Last will and keep alive

## 1. Why does MQTT need Last Will and Keep Alive?

In an IoT system, a device can lose power, drop Wi-Fi, hang, or leave the network without sending an "I am offline" message. If the backend only waits for devices to actively report their status before disconnecting, an `ONLINE` status may linger forever even after the device has vanished.

MQTT provides two related mechanisms for this situation:

- **Last Will and Testament (LWT), often shortened to Last Will:** the client declares in advance a message that the **broker** will publish when the broker determines the client's connection ended abnormally per MQTT conditions.
- **Keep Alive:** the client/broker maintains detection of an inactive connection by bounding the interval without MQTT Control Packets and, when needed, exchanging `PINGREQ`/`PINGRESP`.

They have a causal relationship: Keep Alive helps the broker **detect** that a client lost its connection; LWT specifies **what the broker should publish** after detecting that kind of disconnect. However, Last Will can also be emitted when a TCP connection closes abnormally without waiting for the keepalive interval to expire.

This lesson sits in the **Adapter MQTT** chapter of the **SPRING_INTEGRATION_ADAPTERS** module. The module focuses on integrating external systems via inbound/outbound adapters, gateways, pollers, and `MessageChannel`; practicing with files, SFTP, HTTP, JMS, AMQP, Kafka, and databases while managing message contracts, errors, and connection lifecycles. Here, Spring Integration can subscribe to status messages via an MQTT inbound message-driven adapter, route them through an `IntegrationFlow`, and update device state in a database.

## 2. Last Will flow from client to broker and Spring Integration

~~~mermaid
flowchart LR
    DEVICE["Device MQTT client<br/>configures Will before CONNECT"]
    BROKER[("MQTT broker")]
    OBS["Spring MQTT inbound adapter<br/>subscribes devices/+/availability"]
    CH["mqtt.presence.in<br/>MessageChannel"]
    FLOW["IntegrationFlow<br/>validate / classify"]
    DB[("Presence store / monitoring")]
    DEVICE -->|"CONNECT with Will"| BROKER
    DEVICE -->|"PUBLISH ONLINE after CONNECT"| BROKER
    DEVICE -. "power loss / network drop / no DISCONNECT" .-> BROKER
    BROKER -->|"PUBLISH Will OFFLINE"| OBS
    OBS --> CH --> FLOW --> DB
~~~

The broker only knows about the **MQTT client's connection**, not whether the underlying business process is actually healthy. The backend receives a device's Last Will via a **regular subscription**: the Will is an MQTT PUBLISH generated by the broker from content the client declared beforehand, not a Java exception pushed straight into a service.

| Step | Responsible party | What happens |
| --- | --- | --- |
| 1 | Device / Paho client | Before connecting, declares Will Topic, payload, QoS, and retained flag. |
| 2 | MQTT broker | On valid CONNECT, records the Will for that connection/session per MQTT rules. |
| 3 | Device | After connecting successfully, publishes `ONLINE` status on the agreed topic. |
| 4 | MQTT client and broker | Maintain the connection, exchanging MQTT packets and keepalive pings. |
| 5 | Broker | If the connection ends abnormally under protocol conditions, publishes the `OFFLINE` Will. |
| 6 | Spring MQTT inbound adapter | Receives PUBLISH via subscription callback and converts it to a Spring `Message<?>`. |
| 7 | IntegrationFlow/handler | Validates topic/payload, reconciles state, and writes to the target system. |

**Boundary note:** if **a device** needs LWT, the **MQTT client on the device itself** must declare the Will at CONNECT. Configuring LWT on the **Spring backend's** Paho client only reports whether the backend client lost its connection; it cannot register a device's Will on the device's behalf.

## 3. What fields make up an MQTT Last Will?

In MQTT 3.1.1, CONNECT can carry Will details when the Will Flag is set. With Paho MQTT v3, configure it via:

~~~java
options.setWill(
        "devices/device-17/availability",
        "OFFLINE".getBytes(StandardCharsets.UTF_8),
        1,
        true);
~~~

Parameters:

| Parameter | Example | Meaning |
| --- | --- | --- |
| **Will Topic** | `devices/device-17/availability` | Concrete MQTT topic where the broker will publish the Will. |
| **Will Payload** | UTF-8 bytes of `OFFLINE` | Message body emitted when the connection drops abnormally. |
| **Will QoS** | `1` | QoS of the Will publication emitted by the broker. |
| **Will Retain** | `true` | Tells the broker to store the Will as the latest retained snapshot for the topic. |

The Will Topic is a **PUBLISH topic**, not a wildcard subscription filter; therefore never set `devices/+/availability` as a specific device's Will Topic.

The Will Payload is a **`byte[]`**, not necessarily text. If the backend needs fields like `deviceId`, `timestamp`, `sessionEpoch`, or `schemaVersion`, agree on a JSON/protobuf format and keep size within broker limits. Because the Will payload is registered **before** any incident occurs, it cannot contain an exact timestamp generated by the client at the moment the network drops. To record when the broker emitted the Will, consumers can attach a `receivedAt` timestamp from a trusted system clock.

### 3.1. Is a Will automatically present for every MQTT client?

**No.** If a client does not declare a Will, the broker has no Will payload to publish when the connection disappears. Spring Integration inbound/outbound components built on Paho do not automatically generate `OFFLINE` for devices either.

If the Spring backend should announce its own connection state, configure a Will on **that backend client's factory options** and publish an `ONLINE` birth message once the client actually connects. Never share one Will Topic across multiple Client IDs: multiple clients would overwrite each other's retained status, corrupting observability.

### 3.2. Is a Will sent by the client as it dies?

**No.** When a client loses power or drops off the network, it can no longer actively transmit. The client supplies the Will content in advance during `CONNECT`; the **broker** decides when to emit the PUBLISH upon detecting an abnormal connection termination.

That is also why **the broker must still be alive** to emit a Will. You cannot treat LWT as a guarantee that observers immediately see `OFFLINE` when the broker itself or the network to the broker fails.

## 4. When does the broker publish a Last Will?

In MQTT 3.1.1, a Will is typically published when the connection closes without the client having sent a valid **DISCONNECT** first, or when other protocol-defined abnormal connection-termination conditions apply.

| Situation | Expected for broker to emit Will? | Notes |
| --- | --- | --- |
| Device loses power while connected | **Yes**, once the broker detects the lost connection. | Detection is not instantaneous. |
| Wi-Fi drops, client stops responding | **Yes**, after the broker determines the connection is lost, usually via keepalive/TCP. | A stale `ONLINE` window can remain briefly. |
| Client process crashes abruptly | **Yes**, if the connection terminates abnormally. | Depends on broker socket/keepalive detection. |
| Client sends a clean MQTT `DISCONNECT` | **No**, the Will is normally discarded rather than published. | To show `OFFLINE`, publish it explicitly before disconnecting. |
| Client never completed CONNECT | **Cannot expect a Will for a connection that never formed.** | Broker never registered a valid Will. |
| Client reconnects after network loss | A Will may have already been emitted earlier. | Client must publish a fresh `ONLINE` to update presence. |
| Broker crashes at the same time as the client | **Cannot assume the Will was delivered to observers.** | Broker is down and cannot publish; reconcile on recovery. |
| Connection replaced by duplicate Client ID | May be treated as abnormal disconnect of the old client. | Avoid duplicate Client IDs; test your specific broker's behavior. |

Do not interpret this table as a promise of exact timing or every failure mode. MQTT presence is a **best-effort signal of connection state**; critical workloads need application-level heartbeats, timestamps, and confirmation policies.

### 4.1. What must graceful shutdown do?

When software shuts down cleanly, the client can publish:

~~~text
topic   = devices/device-17/availability
payload = OFFLINE
qos     = 1
retain  = true
~~~

After the MQTT publish completes per policy, it calls `disconnect()`. The broker will **not emit the Will** because the disconnect was clean; however, retained `OFFLINE` was actively updated so new subscribers still see the right status.

If a client sends `DISCONNECT` and forgets to publish `OFFLINE`, the broker can keep a stale retained `ONLINE`. That is a classic presence design bug. Conversely, when a connection dies abruptly, the client has no chance to publish `OFFLINE`, so the Will acts as the fallback.

### 4.2. A Will is not a Java shutdown hook

A JVM shutdown hook may never run on power loss, `SIGKILL`, crashes, or kernel panics. LWT is executed by the broker after detecting an abnormal connection drop, so it does not depend on the JVM staying alive to emit the message. Yet LWT also **does not replace** resource cleanup, transactions/outboxes, or target system state design.

## 5. How does Keep Alive work?

In MQTT 3.1.1, Keep Alive is the maximum interval a client commits not to let elapse between MQTT Control Packets sent to the broker while connected, under protocol rules.

Paho example:

~~~java
MqttConnectOptions options = new MqttConnectOptions();
options.setKeepAliveInterval(20); // 20 SECONDS
~~~

If no other packet needs to be sent, the client sends `PINGREQ` to keep the connection alive, and the broker replies with `PINGRESP`. While the application is actively publishing/subscribing data, those other MQTT packets already refresh activity, so `PINGREQ` is not necessarily sent on a rigid clock tick.

~~~mermaid
sequenceDiagram
    participant C as MQTT client
    participant B as MQTT broker
    C->>B: CONNECT KeepAlive=20s + Will
    B-->>C: CONNACK
    Note over C,B: No other MQTT packet needs to be sent
    C->>B: PINGREQ
    B-->>C: PINGRESP
    Note over C,B: Connection remains active
    C--xB: Network drop / packets lost
    Note over B: No control packet received for too long
    B->>B: Declare connection lost
    B->>B: Publish configured Will
~~~

### 5.1. The ~1.5× Keep Alive rule

Under the MQTT 3.1.1 model, if the broker receives no MQTT Control Packet from the client within **1.5 times Keep Alive**, the broker must consider the connection invalid and close it per protocol rules.

Example:

~~~text
Client Keep Alive = 20 seconds
1.5 x Keep Alive = approximately 30 seconds
~~~

This is a **protocol operating threshold**, not an SLA stating "the device is guaranteed `OFFLINE` after exactly 30 seconds." Factors that shift observed timing include:

- The broker detects TCP socket closure earlier via RST/FIN or I/O error.
- Scheduling, network partitions, and overload delay processing.
- The moment the network drops may not align with the last packet the broker received.
- The broker/cluster is degraded or restarting and cannot emit the Will immediately.
- The Spring observer itself is offline or slow to consume messages.

**Do not set `keepAlive=20` and configure an alert claiming "disconnected for exactly 20 seconds" without measuring in practice.** To commit to a business presence-detection SLA, define an explicit SLA and test under unstable network/broker conditions.

### 5.2. What does Keep Alive = 0 mean?

In MQTT 3.1.1, `Keep Alive = 0` disables the MQTT-level keepalive timeout mechanism for that client. It does not mean the TCP connection can never die, nor does it prevent the broker from closing the connection for other reasons.

For devices requiring offline detection, a reasonable Keep Alive is usually better than `0`, though too short an interval drains battery, consumes bandwidth, and increases false positives on weak networks. Balance SLA requirements, cellular links, sleeping devices, power budgets, and broker capacity.

### 5.3. Keepalive vs. Paho connection timeout

~~~java
options.setConnectionTimeout(10); // SECONDS: connection establishment time
options.setKeepAliveInterval(20); // SECONDS: maintaining/detecting connection
~~~

`connectionTimeout` applies when the client is **opening a new connection**; `keepAliveInterval` applies to an active connection. For MQTT outbound publishing, `MqttPahoMessageHandler.setCompletionTimeout(5000)` bounds **waiting for a publish operation** and is measured in milliseconds. Never raise keepalive to fix publish timeout errors.

## 6. Combining retained presence: ONLINE and OFFLINE

Common pattern for a device:

1. The device creates Paho options with Will `OFFLINE`, Will QoS=1, Will Retain=true.
2. Client sends CONNECT and the broker stores the Will.
3. After CONNECT succeeds, the device actively PUBLISHes `ONLINE` with QoS=1, `RETAIN=true` on **the same availability topic**.
4. On abnormal disconnect, the broker PUBLISHes Will `OFFLINE`, `RETAIN=true`.
5. When the device reconnects, it must PUBLISH a fresh `ONLINE` after connecting.
6. On clean shutdown, the device PUBLISHes `OFFLINE` and then sends a clean MQTT `DISCONNECT`.

~~~mermaid
sequenceDiagram
    participant D as Device client
    participant B as Broker
    participant S as Spring observer
    D->>B: CONNECT(Will=OFFLINE, retain=true, QoS=1)
    B-->>D: CONNACK
    D->>B: PUBLISH ONLINE (retain=true)
    B->>S: ONLINE
    Note over D,B: Power loss / network drop
    B->>B: Detects inactive connection
    B->>S: Will OFFLINE
    Note over D,B: Device comes back online
    D->>B: CONNECT(Will=OFFLINE)
    B-->>D: CONNACK
    D->>B: PUBLISH ONLINE (retain=true)
    B->>S: ONLINE
~~~

Retained presence saves a new subscriber from waiting for the device to re-send its latest status. Yet this is a **broker-side snapshot**, not an event history. A retained `ONLINE` message can become stale if the broker has not emitted the Will yet, if a Will was missed, or if the broker lost data or went down.

### 6.1. Why must ONLINE and Will OFFLINE share the same topic?

Suppose `device-17` uses:

~~~text
topic = devices/device-17/availability
ONLINE:  QoS=1, RETAIN=true
OFFLINE: QoS=1, RETAIN=true (Will)
~~~

The broker keeps only the latest retained snapshot on that topic; when the Will fires, retained `OFFLINE` **replaces** retained `ONLINE`. If the device publishes `ONLINE` to `devices/device-17/online` while its Will `OFFLINE` goes to `devices/device-17/offline`, subscribers receive two competing states and must merge them manually. A single availability topic with the state in the payload is far easier to reconcile.

### 6.2. Retain=false does not overwrite prior retained state

If retained `ONLINE` already exists and the device later publishes `OFFLINE` with `RETAIN=false`, the broker does not delete or overwrite the stored retained `ONLINE`. New subscribers will still see the stale state. Therefore, under a **retained presence** policy, all snapshot updates must consistently use the same topic and `RETAIN=true`.

When decommissioning a device, an authorized administrator can ask the broker to clear retained state by publishing a **zero-byte payload** with `RETAIN=true` to that exact topic in MQTT 3.1.1. Follow strict security controls so another tenant's retained state is never accidentally cleared.

### 6.3. Last Will cannot carry the exact disconnect timestamp

Because the Will payload is supplied by the device at CONNECT, a JSON field like `disconnectedAt` computed before connecting would be misleading. If an `OFFLINE` timestamp is required, the observer should attach `receivedAt` from its own trusted clock or broker monitoring, noting the detection lag.

Stable fields you can include:

~~~json
{
  "deviceId": "device-17",
  "status": "OFFLINE",
  "connectionEpoch": "boot-20261123-001",
  "reason": "LAST_WILL"
}
~~~

`connectionEpoch` is generated by the device application before CONNECT; it helps downstream identify a logical connection session and reduce stale-state overwrites, though it alone does not guarantee ordering across multiple brokers or asynchronous consumers.

## 7. Configuring LWT with Eclipse Paho MQTT v3

A Java example for a simulated device:

~~~java
import java.nio.charset.StandardCharsets;

import org.eclipse.paho.client.mqttv3.MqttConnectOptions;

String availabilityTopic = "devices/device-17/availability";
byte[] offline = "OFFLINE".getBytes(StandardCharsets.UTF_8);

MqttConnectOptions options = new MqttConnectOptions();
options.setServerURIs(new String[] {"tcp://localhost:1883"});
options.setConnectionTimeout(10);   // seconds
options.setKeepAliveInterval(20);   // seconds
options.setCleanSession(true);
options.setAutomaticReconnect(false); // demo to observe disconnection

options.setWill(availabilityTopic, offline, 1, true);
~~~

Key points:

- `setWill(topic, byte[], qos, retained)` must be called **before CONNECT** so the Will appears in the CONNECT packet.
- QoS must be one of the supported MQTT levels: 0, 1, or 2.
- The topic must be a concrete publish topic name without subscription wildcards.
- Will `retained=true` makes sense when the backend wants an `ONLINE/OFFLINE` snapshot for new observers.
- The client must have a **unique Client ID** among concurrent connections; the Will is bound to that client's connection.
- `cleanSession=true/false` does not enable or disable the Will; that is a separate session/subscription choice.
- To retain long-term offline event history, use a persistent event store; a retained Will does not replace an event log.

This example uses plaintext TCP for local execution. In production, use TLS, broker authentication, and ACLs restricting each device's availability publishing rights. Never put passwords or private keys in source code.

### 7.1. Can a Will be configured on a Spring Integration client factory?

Yes. When a Java backend uses `MqttPahoMessageHandler` or `MqttPahoMessageDrivenChannelAdapter`, the Paho client uses `MqttPahoClientFactory`; the factory accepts `MqttConnectOptions` which may include a Will.

~~~java
@Bean("bridgeClientFactory")
MqttPahoClientFactory bridgeClientFactory() {
    var options = new MqttConnectOptions();
    options.setServerURIs(new String[] {
            "tcp://localhost:1883"
    });
    options.setKeepAliveInterval(20);
    options.setConnectionTimeout(10);
    options.setWill(
            "services/integration-bridge/availability",
            "OFFLINE".getBytes(StandardCharsets.UTF_8),
            1,
            true);

    var factory = new DefaultMqttPahoClientFactory();
    factory.setConnectionOptions(options);
    return factory;
}
~~~

This snippet requires importing `StandardCharsets`, `MqttConnectOptions`, `MqttPahoClientFactory`, `DefaultMqttPahoClientFactory`, and `@Bean`.

**Limitation to remember:** a Will on this factory represents the state of the **backend MQTT client** created from those options, not the state of all devices. If multiple adapters share a factory with the same Will Topic, they can overwrite each other's retained presence. Assign separate factories/Will Topics per client role or logical client with distinct Client IDs.

### 7.2. When does the backend's Will take effect?

Creating the factory bean does not mean the client has sent CONNECT. The Will is only registered with the broker after a valid CONNECT succeeds. If `MqttPahoMessageHandler` connects lazily on its first publish, do not assume the mere existence of the bean means the backend has "registered its Will." Verify actual lifecycle, successful connection, and birth messages for your adapter/client.

## 8. Device simulator example: sending ONLINE and declaring OFFLINE Will

The Java snippet below simulates an MQTT device using Paho v3. Run it in a separate process from the Spring observer in section 9.

~~~java
package demo.mqttpresence;

import java.nio.charset.StandardCharsets;

import org.eclipse.paho.client.mqttv3.MqttClient;
import org.eclipse.paho.client.mqttv3.MqttConnectOptions;
import org.eclipse.paho.client.mqttv3.persist.MemoryPersistence;

public class DeviceWillSimulator {

    public static void main(String[] args) throws Exception {
        String brokerUrl = args.length > 0
                ? args[0] : "tcp://localhost:1883";
        String topic = "devices/device-17/availability";

        var options = new MqttConnectOptions();
        options.setServerURIs(new String[] {brokerUrl});
        options.setConnectionTimeout(10);
        options.setKeepAliveInterval(20);
        options.setCleanSession(true);
        options.setAutomaticReconnect(false);
        options.setWill(
                topic,
                "OFFLINE".getBytes(StandardCharsets.UTF_8),
                1,
                true);

        var client = new MqttClient(
                brokerUrl, "sim-device-17", new MemoryPersistence());

        client.connect(options);

        // Birth message: update retained ONLINE after CONNECT.
        client.publish(
                topic,
                "ONLINE".getBytes(StandardCharsets.UTF_8),
                1,
                true);

        System.out.println(
                "Simulator ONLINE. Press Enter for clean DISCONNECT.");
        System.in.read();

        // Graceful shutdown: publish OFFLINE before DISCONNECT.
        client.publish(
                topic,
                "OFFLINE".getBytes(StandardCharsets.UTF_8),
                1,
                true);

        client.disconnect();
        client.close();
    }
}
~~~

**How to read this example:**

- Pressing Enter makes the simulator publish retained `OFFLINE` and cleanly disconnect; the broker has no reason to emit the Will.
- If the process is **forcibly killed** while the broker is still running so the client never sends DISCONNECT, the broker emits the Will upon detecting the abnormal disconnect.
- Time until `OFFLINE` is observed depends on broker TCP/keepalive detection and conditions, not always exactly 20 seconds.
- Stopping only the broker itself will prevent the broker from emitting the Will to observers connected to that broker; that is not a valid test of "device died while broker stayed up."
- In real products using `automaticReconnect=true`, you must add logic to **publish `ONLINE` after every successful reconnect**, not only after the very first CONNECT.

### 8.1. Why is automatic reconnect disabled in this short simulator?

The demo aims to observe an abnormal connection drop and the broker emitting the Will. Enabling auto-reconnect without writing a reconnect birth-message callback could bring the client back online while retained `OFFLINE` remains on the broker, yielding misleading state. In production, client auto-reconnect is fine as long as it is paired with birth-message `ONLINE` publishing and state-ordering checks.

### 8.2. A running process is not the same as a live connection

In the demo, the Java process blocks at `System.in.read()` with no business traffic, yet Paho keeps MQTT keepalive active. If business worker threads in Java deadlock while the networking/client thread still pings the broker normally, MQTT Keep Alive still reports the **connection as alive** even though business functionality has stalled. Hence Last Will is not a complete application health check.

## 9. Spring Integration: observing device Wills and presence

Now let's build the **backend observer**: subscribe to `devices/+/availability` via an MQTT inbound message-driven adapter, receive `ONLINE`/`OFFLINE` from devices, and record events in an illustrative sink. This is an inbound flow—it does **not** create Wills on behalf of devices.

### 9.2. Spring Boot application

### 9.3. application.properties


Local broker `localhost:1883` is strictly test infrastructure; Spring Boot does not start a broker. Inside a container, `localhost` refers to the container itself, not a broker on the host. In other environments, use the right broker URL, TLS, credentials, and ACLs.

### 9.4. MQTT factory and inbound adapter

~~~java
package demo.mqttpresence;

import org.eclipse.paho.client.mqttv3.MqttConnectOptions;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.mqtt.core.DefaultMqttPahoClientFactory;
import org.springframework.integration.mqtt.core.MqttPahoClientFactory;
import org.springframework.integration.mqtt.inbound.MqttPahoMessageDrivenChannelAdapter;
import org.springframework.integration.mqtt.support.DefaultPahoMessageConverter;
import org.springframework.messaging.MessageChannel;

@Configuration
class PresenceTransportConfiguration {

    @Bean
    MqttPahoClientFactory presenceClientFactory(
            @Value("${app.mqtt.broker-url}") String brokerUrl) {

        var options = new MqttConnectOptions();
        options.setServerURIs(new String[] {brokerUrl});
        options.setConnectionTimeout(10);
        options.setKeepAliveInterval(30);
        options.setCleanSession(false);
        options.setAutomaticReconnect(false);

        var factory = new DefaultMqttPahoClientFactory();
        factory.setConnectionOptions(options);
        return factory;
    }

    @Bean
    MqttPahoMessageDrivenChannelAdapter mqttPresenceAdapter(
            MqttPahoClientFactory presenceClientFactory,
            @Qualifier("mqtt.presence.in") MessageChannel output,
            @Value("${app.mqtt.observer-client-id}") String clientId,
            @Value("${app.mqtt.presence-topic-filter}") String topicFilter) {

        var adapter = new MqttPahoMessageDrivenChannelAdapter(
                clientId, presenceClientFactory, topicFilter);

        adapter.setQos(1);
        adapter.setRecoveryInterval(10000);
        adapter.setConverter(new DefaultPahoMessageConverter());
        adapter.setOutputChannel(output);
        return adapter;
    }
}
~~~

Key details:

1. `presenceClientFactory` uses the Client ID passed by the adapter when creating the MQTT client; broker, keepalive, and session settings apply to the observer.
2. `setCleanSession(false)` illustrates an MQTT 3.1.1 persistent session for the observer. The Client ID must stay stable to resume the session and must not be shared across concurrent instances.
3. `setAutomaticReconnect(false)` lets the inbound adapter manage recovery via `setRecoveryInterval(...)` in this example; test against your deployed version.
4. `setQos(1)` sets the observer's subscription QoS. The device's Will is emitted by the broker at QoS 1; effective delivery QoS also depends on the subscription.
5. `setOutputChannel(output)` sends inbound messages to Spring channel `mqtt.presence.in`.
6. MQTT inbound is **message-driven**, so no `@Poller` is needed to receive broker callbacks.

**Distinction:** the observer factory **does not declare a device's Will**. Each device's Will is registered by `DeviceWillSimulator` when that device client itself sends CONNECT.

### 9.5. Presence flow and sink

~~~java
package demo.mqttpresence;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.integration.mqtt.support.MqttHeaders;
import org.springframework.messaging.MessageChannel;

@Configuration
@EnableIntegration
class PresenceFlowConfiguration {

    @Bean(name = "mqtt.presence.in")
    MessageChannel presenceInput() {
        return new DirectChannel();
    }

    @Bean
    PresenceSink presenceSink() {
        return new PresenceSink();
    }

    @Bean
    IntegrationFlow presenceFlow(PresenceSink sink) {
        return IntegrationFlow.from("mqtt.presence.in")
                .handle(String.class, (payload, headers) -> {
                    String topic = (String)
                            headers.get(MqttHeaders.RECEIVED_TOPIC);

                    if (topic == null
                            || !topic.matches(
                                    "devices/[A-Za-z0-9_-]{1,40}/availability")) {
                        throw new IllegalArgumentException(
                                "Invalid presence topic: " + topic);
                    }
                    if (!"ONLINE".equals(payload)
                            && !"OFFLINE".equals(payload)) {
                        throw new IllegalArgumentException(
                                "Unsupported presence status: " + payload);
                    }

                    sink.record(new PresenceEvent(topic, payload));
                    return null;
                })
                .get();
    }
}
~~~

~~~java
package demo.mqttpresence;

record PresenceEvent(String topic, String status) {
}
~~~

~~~java
package demo.mqttpresence;

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

class PresenceSink {

    private final List<PresenceEvent> events =
            new CopyOnWriteArrayList<>();

    void record(PresenceEvent event) {
        events.add(event);
        System.out.println(
                "MQTT presence: " + event.topic()
                + " = " + event.status());
    }

    List<PresenceEvent> snapshot() {
        return List.copyOf(events);
    }

    void clear() {
        events.clear();
    }
}
~~~

Whenever a device sends retained `ONLINE` or the broker emits Will `OFFLINE`, the adapter receives an MQTT message on the corresponding topic; the flow validates its shape and payload and records the event.

**This is a wiring demo, not a production presence store:** it only uses an in-memory `CopyOnWriteArrayList`. A real system must update a DB keyed by device/session identity, check timestamps, handle stale retained/duplicate/out-of-order deliveries, and avoid letting validation exceptions stall MQTT callbacks. Instead of throwing endlessly on malformed payloads, route them to a quarantine/error flow with an explicit policy.

### 9.6. Role of message headers

`MqttHeaders.RECEIVED_TOPIC` indicates the **actual topic received**. Depending on version, the MQTT converter may also add QoS, retained, and duplicate flags to received headers.

Never use outbound `MqttHeaders.TOPIC` to guess inbound topics. With a `retained=true` Will, new subscribers can receive retained `OFFLINE` on subscribe; stale status can also arrive via broker/session/replay, so store `receivedAt`, epoch/session identifiers, and clear update rules.

## 10. When is LWT insufficient to judge device health?

Last Will only indicates that **the broker detected an abnormal MQTT connection termination**. It does not prove sensors, actuators, or business logic are functioning.

| Scenario | Observable by MQTT Keep Alive/LWT? | Additional condition required |
| --- | --- | --- |
| Device loses Wi-Fi or power | Can detect MQTT connection loss and emit Will. | Broker and observer must still be up. |
| Device app hangs while MQTT networking thread still pings | Connection may still look online. | Business heartbeat and worker/sensor checks. |
| Sensor broken while MQTT app runs | May still show `ONLINE`. | Sensor data validation, read errors, freshness checks. |
| Spring subscriber server stopped | Device connection may still be online; observer misses events. | Dedicated backend monitoring. |
| Broker crashed | Will may not be emitted while broker is offline. | Broker/cluster monitoring and reconciliation. |
| Device cleanly DISCONNECTs without publishing `OFFLINE` | Will is not emitted. | Graceful shutdown contract. |
| Stale retained `ONLINE` data | Client may have vanished before Will was observed. | Timestamp/TTL in presence store or last-seen checks. |

### 10.1. Keep Alive vs. business heartbeat

- **Keep Alive:** protocol mechanism maintaining and monitoring the MQTT connection.
- **Heartbeat:** periodic business message—such as `{"deviceId":"device-17","seq":102,"health":"OK"}`—proving application code is running.
- **Health check:** may verify sensors, disk, CPU, DB access, and command execution capability.
- **Last Will:** broker-emitted message when the connection terminates abnormally.

A device can maintain a healthy MQTT connection while its sensor produces no readings for hours. The backend should combine `lastSeenAt`, `lastHealthyReadingAt`, heartbeats, LWT, and broker health to derive states like `ONLINE`, `OFFLINE`, `STALE`, and `UNKNOWN` instead of a single boolean.

### 10.2. Designing a presence state machine

~~~mermaid
stateDiagram-v2
    [*] --> UNKNOWN
    UNKNOWN --> ONLINE: Birth ONLINE confirmed
    UNKNOWN --> OFFLINE: LWT OFFLINE
    ONLINE --> STALE: No business heartbeat for too long
    STALE --> ONLINE: New heartbeat / birth
    ONLINE --> OFFLINE: Last Will / Graceful OFFLINE
    STALE --> OFFLINE: Last Will / Graceful OFFLINE
    OFFLINE --> ONLINE: New session birth ONLINE
    ONLINE --> UNKNOWN: Broker/observer lost trustworthy state
    OFFLINE --> UNKNOWN: Current state cannot be verified
~~~

These states and events are **application policy**, not built-in Spring Integration features. When a service exposes a "device online" dashboard, clearly surface the evidence source and update timestamp, especially if retained snapshots are stale or the system recently failed over.

## 11. Retained presence, sessions, and Client IDs

### 11.1. Retained ≠ persistent session

The two mechanisms solve different problems:

| Mechanism | Bound to | Purpose |
| --- | --- | --- |
| Retained message | MQTT topic on the broker. | Stores the latest snapshot like `ONLINE/OFFLINE` for new subscribers. |
| Persistent session (`cleanSession=false`) | Subscriber's MQTT Client ID/session. | Can retain subscriptions and certain QoS 1/2 messages while subscriber is offline. |
| Will | Connected MQTT client's connection. | Broker publishes the predefined message when the connection ends abnormally. |
| Keep Alive | Active connection. | Detects when a client stops sending MQTT packets over time. |

A new subscriber with `cleanSession=true` can still receive a retained `OFFLINE` if the topic holds that snapshot. A subscriber with a persistent session does not eliminate the need for devices to configure Wills.

### 11.2. Duplicate Client IDs corrupt presence

If two devices both use `device-17-client` as their Client ID, the broker can drop the earlier connection when the new one connects. The older client being kicked abruptly can trigger its Will to emit `OFFLINE` right after the new device published `ONLINE`, depending on ordering and broker behavior.

Consequence: flapping `ONLINE → OFFLINE → ONLINE` retained state, false dashboard alerts, reconnect loops, and duplicate messages. **Client IDs must be managed as unique connection identities**, not arbitrary demo strings.

### 11.3. Reconnecting after a Will must republish ONLINE

If a client sets `options.setAutomaticReconnect(true)`, Paho can automatically restore the MQTT connection after a network drop. However, **never assume** the application automatically publishes a fresh `ONLINE` after every reconnect. You need a lifecycle callback/hook appropriate for Paho and your Spring Integration version to:

1. Confirm the new connection actually succeeded.
2. Republish retained `ONLINE` on the proper topic.
3. Optionally increment a connection epoch/version.
4. Verify required subscriptions were restored.
5. Track state transitions to avoid trusting stale `OFFLINE` messages.

A Paho v3 callback like `MqttCallbackExtended.connectComplete(...)` helps detect reconnects; when using callbacks, avoid unbounded blocking on the callback thread and monitor birth-message publish failures.

## 12. Backend client Wills: who is being monitored?

A Spring Integration application can also declare an LWT so other systems detect when the **backend MQTT connector** disconnects:

~~~text
Client ID: inventory-bridge-01
Will topic: services/inventory-bridge-01/availability
Will payload: OFFLINE
Will QoS: 1
Will Retain: true
~~~

After the backend MQTT client connects, it publishes retained `ONLINE`. When that connection drops abnormally, the broker emits `OFFLINE`. This lets dashboards track the **backend bridge's MQTT connection**, though it does not prove every file/SFTP/Kafka inbound adapter or DB service is healthy.

### 12.1. Avoid sharing one Will across multiple adapters

If a single factory bean configures Will Topic `services/integration-bridge/availability` and is injected into **two adapters creating two MQTT clients**, the broker binds Wills for both clients to the **same topic**. One adapter disconnecting can cause dashboards to show the entire service `OFFLINE` while the other adapter is still running.

Solution: separate factories/Will Topics by client role, or build a service-level health aggregator from multiple signals. Never assume a single factory bean means all adapters share one physical MQTT connection.

### 12.2. Lifecycle at startup and shutdown

- `MqttPahoClientFactory` bean created: **no active Will yet** until a client connects.
- MQTT client connects successfully: broker registers the Will for that connection.
- Publisher/observer sends birth `ONLINE`: retained status is updated.
- Graceful shutdown: publish `OFFLINE` per policy, wait for publish completion appropriately, then `DISCONNECT`.
- Crash/network loss: broker emits Will if it detects the drop and remains up.
- Reconnect: publish a new `ONLINE` and verify session/subscriptions.

Do not rely on an unguarded `@PreDestroy` to guarantee retained `OFFLINE` reached the broker: shutdown has time limits and can be interrupted, so handle uncertain states cleanly.

## 13. Race conditions: OFFLINE/ONLINE arriving out of order

Systems with many devices, multiple clients, or broker clusters can observe events out of order.

Example:

~~~text
T0: client epoch A CONNECTs, PUBLISHes ONLINE(A)
T1: epoch A network drops
T2: client epoch B CONNECTs, PUBLISHes ONLINE(B)
T3: broker/observer receives delayed Will OFFLINE(A)
T4: database overwrites ONLINE(B) with OFFLINE(A) if epoch is not checked
~~~

Not every broker exhibits this exact ordering on a single connection; this is a **design scenario for evaluating races** under failover, multiple clients, retries, queues, and async consumers.

Mitigations:

1. Attach a **connection epoch/generation** generated by the device/application before CONNECT and include it in both birth and Will payloads.
2. Record `receivedAt`/`lastSeenAt`, without relying solely on an untrusted clock.
3. When updating state, apply a **newer epoch wins** rule if a reliable generation source exists.
4. Associate device state with the **Client ID/session owner** and reconcile against the broker/heartbeats.
5. Use idempotency to avoid recording the same event twice.
6. Never trigger dangerous actions from a single `OFFLINE`/`ONLINE` transition without a debounce policy.

### 13.1. Last Will lacks the latest client timestamp

A Will is transmitted as a **pre-registered** payload. Thus an `emittedAt` field computed at CONNECT reflects registration time, not disconnect time. If you need a "broker detected OFFLINE" timestamp, generate it on the server/observer upon receiving the Will and record its source explicitly.

### 13.2. OFFLINE presence may be transient

A device drops Wi-Fi for 3 seconds on a cellular link, the broker sees a socket reset and emits the Will, and the device immediately reconnects. Sending "device offline"/"device online" emails on every blip will spam users. Apply debouncing, hysteresis, alert thresholds, and SLA-based event classification.

## 14. Securing Last Will and availability topics

Presence topics can be spoofed if the broker allows untrusted publishers to send `ONLINE` or `OFFLINE` on another device's behalf.

| Risk | Control |
| --- | --- |
| Arbitrary publisher writes `devices/device-17/availability` | Broker ACLs binding identity to allowed topics, plus application validation. |
| LWT payload contains tokens or PII | Store only necessary status/IDs; never put secrets in Wills or retained messages. |
| Plaintext MQTT over external networks | TLS, broker certificate verification, proper credentials/mTLS. |
| Duplicate or spoofed Client ID | Issue unique Client IDs; bind identity at the broker where supported. |
| Subscriber reads another tenant's presence | Per-tenant/device subscribe ACLs; avoid broad wildcards when unnecessary. |
| Stale retained `OFFLINE` left after device deletion | Authorized, audited retained cleanup procedure. |
| Stale status triggers dangerous actions | Business TTL, state freshness, idempotency, business authorization. |
| Broker/observer downtime | Monitor broker health; transition to `UNKNOWN` when fresh evidence is missing. |

**Client IDs or topic names are not proof of device authentication.** Seeing `devices/device-17/availability` on a message does not prove `device-17` sent it. Broker authentication/ACLs and business contracts must bind the data origin.

## 15. Error handling and resilience

Last Will is a connection signal, not a retry mechanism for business flows. A pipeline can fail at several layers:

~~~mermaid
flowchart TD
    DEV["Device MQTT client"]
    BROKER[("Broker holding Will and retained")]
    ADAPTER["Spring inbound MQTT adapter"]
    CH["mqtt.presence.in"]
    FLOW["Validate / Presence store"]
    ERROR["Error flow / quarantine / retry"]
    DEV -->|"CONNECT Will + PUBLISH ONLINE"| BROKER
    DEV -. "connection lost" .-> BROKER
    BROKER -->|"Will OFFLINE"| ADAPTER --> CH --> FLOW
    ADAPTER -. "subscribe / converter error" .-> ERROR
    CH -. "consumer unavailable" .-> ERROR
    FLOW -. "DB error" .-> ERROR
~~~

| Failure | Does LWT resolve it automatically? | Appropriate strategy |
| --- | --- | --- |
| Device disconnects abnormally | Broker can emit Will if registered. | Status consumer, retained presence, monitoring. |
| Graceful device disconnect | **Does not** emit Will. | Actively publish `OFFLINE` before DISCONNECT. |
| Broker offline | Cannot emit/deliver Wills while broker is down. | Broker monitoring/HA, post-recovery reconciliation. |
| Spring observer disconnects | Device may still be online. | Client recovery, session/subscriptions, status reconciliation on reconnect. |
| Invalid presence JSON/payload | No. | Validate, quarantine, audit topic/device ID. |
| Database presence update fails | No. | Retry handler/idempotency/outbox/persistent queue. |
| Device business worker hangs while network thread pings | Will does not fire because connection stays alive. | Business heartbeats and health checks. |
| Duplicate command processing | No. | Command ID, unique constraints, ACK/reconciliation. |

### 15.1. Spring Integration error channels

With `DirectChannel`, exceptions from handlers can propagate back up the sending endpoint's call stack. On inbound MQTT, the path from Paho callbacks to the Spring flow and how `ErrorMessage` instances are emitted depend on the configured endpoint/error channel. Never assume an exception thrown in `PresenceFlowConfiguration` always makes the broker redeliver the same message or rolls back MQTT acknowledgment.

If a presence message fails schema validation, route it to quarantine with reason and metadata. If the database is unavailable, apply bounded retries and idempotent updates. If the observer lost network access, check session/reconnection and retained status rather than reading error logs alone.

### 15.2. QoS 1/2 and duplicate statuses

A QoS 1 Will publication can be redelivered at the MQTT layer; applications can also re-receive retained `OFFLINE` on fresh subscriptions. Handling duplicate `OFFLINE` events must be **idempotent**. In the presence store, writing the same status multiple times should not fire duplicate alerts or side effects when no real state change occurred.

### 15.3. Never trigger uncontrolled actions from LWT

For example, "device OFFLINE → auto power-cycle outlet" can be dangerous if triggered by a brief network drop, stale retained state, or a spoofed publisher. Whenever LWT drives physical actions, require extra state verification, authorization, debouncing, rate limits, and safe recovery mechanisms.

## 16. Testing the Spring flow without a broker

Processing logic after the MQTT inbound adapter should be unit/integration tested independently of the network. `PresenceFlowConfiguration` in section 9 only needs the channel, sink, and `IntegrationFlow`; we can boot a Spring test context **without loading `PresenceTransportConfiguration`**.

Maven test dependency:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

Create `PresenceFlowTest.java`:

~~~java
package demo.mqttpresence;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.util.List;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.integration.mqtt.support.MqttHeaders;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(classes = PresenceFlowConfiguration.class)
class PresenceFlowTest {

    @Autowired
    @Qualifier("mqtt.presence.in")
    MessageChannel input;

    @Autowired
    PresenceSink sink;

    @BeforeEach
    void reset() {
        sink.clear();
    }

    @Test
    void recordsOnlineAndOffline() {
        input.send(MessageBuilder.withPayload("ONLINE")
                .setHeader(MqttHeaders.RECEIVED_TOPIC,
                        "devices/device-17/availability")
                .build());

        input.send(MessageBuilder.withPayload("OFFLINE")
                .setHeader(MqttHeaders.RECEIVED_TOPIC,
                        "devices/device-17/availability")
                .build());

        assertEquals(
                List.of(
                        new PresenceEvent(
                                "devices/device-17/availability",
                                "ONLINE"),
                        new PresenceEvent(
                                "devices/device-17/availability",
                                "OFFLINE")),
                sink.snapshot());
    }

    @Test
    void rejectsWrongTopicFormatBeforeRecording() {
        assertThrows(RuntimeException.class,
                () -> input.send(
                        MessageBuilder.withPayload("ONLINE")
                                .setHeader(MqttHeaders.RECEIVED_TOPIC,
                                        "devices/other/tenant/availability")
                                .build()));

        assertTrue(sink.snapshot().isEmpty());
    }

    @Test
    void rejectsUnsupportedPresenceStatus() {
        assertThrows(RuntimeException.class,
                () -> input.send(
                        MessageBuilder.withPayload("NOT_SURE")
                                .setHeader(MqttHeaders.RECEIVED_TOPIC,
                                        "devices/device-17/availability")
                                .build()));

        assertTrue(sink.snapshot().isEmpty());
    }
}
~~~

Both rejection tests catch `RuntimeException` at the caller boundary to avoid coupling to specific Spring Integration wrapper exceptions across versions; in real applications, inspect the root cause and assert your error policy. With `DirectChannel`, normal handler calls execute synchronously, so `sink.snapshot()` can be read right after `send(...)`.

This test proves **channel wiring, payload validation, and the presence sink**, yet **does not** prove the broker emits Last Wills, Keep Alive works, retained flags are right, or adapters reconnect. Broker integration tests are required for those.

## 17. Testing Last Will with a real MQTT broker

Only run this on a test broker you control. Example broker running at `tcp://localhost:1883` with Mosquitto CLI installed.

### 17.1. Step 1: observe availability

Open a terminal and subscribe:

~~~bash
mosquitto_sub -h localhost -p 1883 \
  -i demo-presence-observer-cli-1 \
  -q 1 -t 'devices/+/availability' -v
~~~

When no retained status exists yet, the subscriber waits for messages. If the broker holds an older snapshot, the CLI displays it right upon subscribing; distinguish retained snapshots from new publications.

### 17.2. Step 2: run the simulator and observe ONLINE

Start `DeviceWillSimulator` in a separate process. Once CONNECT succeeds, it publishes retained `ONLINE`:

~~~text
devices/device-17/availability ONLINE
~~~

The Spring observer from section 9 also receives the message via `MqttPahoMessageDrivenChannelAdapter`.

### 17.3. Step 3a: clean shutdown

Press Enter in the simulator so the code publishes retained `OFFLINE` and calls `disconnect()`.

Expected: the observer receives `OFFLINE` **actively published by the device**; the broker does not need to emit the Will. If the device only called `DISCONNECT` without publishing `OFFLINE`, a stale retained `ONLINE` could remain.

### 17.4. Step 3b: abnormal disconnect

Restart the simulator, wait for `ONLINE`, then **forcibly kill the client process without letting it send DISCONNECT**. Keep the broker and observer running.

Expected: the broker detects the lost client connection and publishes Will `OFFLINE` to the availability topic. Observed delay depends on broker socket or keepalive detection; do not assume exactly 20 seconds.

Note: only terminate your simulator in a test environment; **never** disrupt production devices, brokers, or applications. Never use stopping the broker as your sole LWT test, because an offline broker cannot deliver Wills immediately.

### 17.5. Step 4: verify retained OFFLINE

After the Will has been emitted, open a new subscriber:

~~~bash
mosquitto_sub -h localhost -p 1883 \
  -i demo-presence-observer-cli-2 \
  -q 1 -t 'devices/device-17/availability' -v
~~~

Because the broker retained the Will, the new subscriber immediately receives `OFFLINE` upon subscribing. This shows how `RETAIN=true` keeps the snapshot useful for late-arriving consumers.

### 17.6. Step 5: reconnect and come back online

Restart the simulator. It connects and publishes retained `ONLINE` on the same topic, replacing retained `OFFLINE`. A new subscriber joining afterward receives `ONLINE`.

If a real product uses Paho auto-reconnect, you need a callback/hook publishing `ONLINE` **after every reconnect**, not only at process startup. Verify the status is not overwritten by stale retained `OFFLINE` or an event from an earlier connection epoch.

### 17.7. Essential test matrix

| Scenario | Action | What to verify |
| --- | --- | --- |
| CONNECT with Will | Device declares `setWill(...)` then connects. | Broker registers Will upon successful CONNECT. |
| Clean DISCONNECT | Device actively sends `OFFLINE` then DISCONNECTs. | No unintended Will emitted; retained state is `OFFLINE`. |
| Process crash | Kill device client abnormally while broker stays up. | Broker publishes Will upon detecting lost connection. |
| Network blackhole | Block traffic for one device client in test. | Detected via keepalive/TCP without assuming a hard SLA. |
| Late-joining subscriber | Subscribe after retained `OFFLINE`. | Receives the matching retained snapshot. |
| Device reconnect | CONNECT and publish `ONLINE`. | New state replaces retained `OFFLINE`. |
| Duplicate Client ID | Start two active clients with the same ID. | Observe connection replacement; fix ID allocation. |
| Broker downtime | Stop test broker. | Do not assume Wills are emitted while the broker itself is down. |
| Backend observer offline | Stop Spring subscriber, then restart it. | Subscriptions/sessions/retained align with policy. |
| Graceful shutdown missing `OFFLINE` | Send only DISCONNECT. | Stale retained `ONLINE` may remain; confirm policy bug. |
| Business worker hung | MQTT networking still responds to pings. | LWT may **not** fire; business heartbeat is needed. |
| Will with QoS 1 | Simulate redelivery. | Presence store is idempotent and does not send duplicate alerts. |

## 18. Observability, operations, and troubleshooting

### 18.1. Metrics to capture

| Suggested metric/field | Purpose |
| --- | --- |
| `mqtt_client_connected` | Tracks MQTT connection state by client role. |
| `mqtt_last_packet_at` | Assists keepalive and network analysis. |
| `mqtt_keepalive_seconds` | Verifies configuration, avoiding seconds vs. milliseconds confusion. |
| `mqtt_reconnect_attempts_total` | Detects reconnect loops. |
| `mqtt_last_will_received_total` | Counts Will events observed once source is verified. |
| `device_presence_last_seen_at` | Shows when the backend last observed a status/heartbeat. |
| `device_presence_epoch` | Reconciles status against connection generation. |
| `device_heartbeat_lag_seconds` | Flags stalled business workers/sensors even while MQTT stays connected. |
| `mqtt_inbound_error_total` | Flags invalid payloads, channel dispatch failures, and adapter issues. |
| `broker_available` | Tracks reliability of the Last Will emission source. |

These metric names are **design suggestions**, not metrics automatically emitted with these exact names by Spring Integration/Paho. Never put credentials, tokens, or sensitive full payloads into logs.

### 18.2. Common failure symptoms

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| No `OFFLINE` seen when device loses power. | Client never declared Will, broker hasn't detected drop yet, broker offline, or observer not subscribed. | Check CONNECT Will, topic filter, keepalive, broker logs, and subscriber. |
| Device cleanly DISCONNECTs, yet dashboard stays `ONLINE`. | Device did not actively publish retained `OFFLINE`. | Add graceful-shutdown presence policy. |
| Retained `OFFLINE` still appears after reconnect. | Device did not publish fresh `ONLINE` after reconnecting. | Publish birth message in connect-complete lifecycle. |
| `ONLINE`/`OFFLINE` flaps rapidly. | Flaky network, duplicate Client ID, or stale event overwrite. | Check reconnects, epoch/ordering, and debouncing. |
| Need offline detection in 5s, yet `Keep Alive=60`. | Detection SLA mismatches parameters and network conditions. | Measure from last packet to detection; combine heartbeats and alert thresholds. |
| Short Keep Alive drains device battery. | Too-frequent pings during idle periods. | Pick an interval balanced for power and network SLAs. |
| Changed connection timeout without changing Will emission delay. | Connection timeout differs from Keep Alive. | Inspect `setKeepAliveInterval(...)` and broker behavior. |
| Retained `OFFLINE` lost after broker restart. | Non-durable broker persistence or different cluster node. | Test broker persistence, HA, and reconciliation. |
| Subscriber misses Will after restart. | Wrong session/topic filter or adapter hasn't reconnected. | Check observer Client ID, QoS, subscriptions, and error flow. |
| LWT shows `ONLINE` while sensor is broken. | LWT only reflects MQTT connection state. | Implement business heartbeats and health checks. |
| One Will `OFFLINE` marks the entire backend `OFFLINE`. | Multiple clients share the same Will Topic. | Separate Will namespaces and factory/client identities. |
| LWT causes repeated command execution. | Presence event triggers side effects without dedup/policy. | Add idempotency, limit automation, enforce business ACKs and validation. |

## 19. Practice exercise: building a safe device monitoring system

**Context:** a system monitors hundreds of temperature sensors. Devices may experience short network drops. The dashboard must display connectivity status, yet must never treat `ONLINE` as proof that the sensor works properly, nor trigger dangerous actions on a stale `OFFLINE` event.

### Requirements

1. Define topics `devices/{deviceId}/availability`, `devices/{deviceId}/heartbeat`, and `sensors/{deviceId}/temperature`.
2. Device clients configure Will Topic availability, payload `OFFLINE`, QoS 1, `retained=true`, and Keep Alive 20 seconds before CONNECT.
3. After CONNECT, devices publish retained `ONLINE`; on clean shutdown, publish retained `OFFLINE` before DISCONNECT.
4. After reconnecting, devices must publish a fresh `ONLINE` and record a connection epoch.
5. A Spring Integration MQTT inbound adapter subscribes to `devices/+/availability` and routes messages to `mqtt.presence.in`.
6. The flow validates topic shape, payload schema, device/tenant permissions, and connection generation; invalid messages go to quarantine.
7. Persist presence in a database via idempotent updates; add `receivedAt`, `lastHeartbeatAt`, and an `UNKNOWN`/`STALE` policy.
8. Write brokerless flow tests, then broker-backed tests for client crash, network blackhole, and clean shutdown.
9. Test retained status before and after device reconnect; verify stale retained snapshots are not treated as the newest evidence when details are missing.
10. Run two device instances with the same Client ID in a test environment; explain the reconnect loop and fix it.
11. Test broker restart/failover; identify cases where Wills cannot be observed immediately.
12. Design alert debouncing and business heartbeats to avoid confusing MQTT network health with sensor health.
13. Restrict ACLs so each device can only publish its own availability/telemetry; prevent other clients from spoofing status.
14. Reconcile the dashboard after the Spring observer stays offline for several minutes and re-subscribes.

**Completion criteria:** clean DISCONNECT is distinguished from crashes, broker Will timing is explained as non-exact, retained `OFFLINE` is replaced by retained `ONLINE` on reconnect, Spring flow rejects invalid tenants/topics, the presence store is idempotent, and the dashboard shows `UNKNOWN`/`STALE` when evidence is insufficient.

## 21. Conclusion

**Last Will and Keep Alive** work together so MQTT can provide connection presence signals:

- **Last Will** is declared in advance by the client during CONNECT. When the connection ends abnormally, the broker publishes the configured Will Topic/Payload with its QoS and retained policy; on clean client DISCONNECT, the Will is normally not emitted.
- **Keep Alive** defines the MQTT activity window and uses `PINGREQ`/`PINGRESP` when needed. The broker detects inactive connections under protocol rules, though `OFFLINE` observation timing is not an exact SLA.
- **Retained ONLINE/OFFLINE** provides a presence snapshot for new subscribers. Devices must publish `ONLINE` after connecting/reconnecting and actively publish `OFFLINE` during clean shutdowns.
- **Spring Integration's MQTT inbound adapter** receives those PUBLISHes via `MessageChannel` and `IntegrationFlow` to update the presence store, handle errors, and integrate with DB/HTTP/Kafka or monitoring systems.

In the **SPRING_INTEGRATION_ADAPTERS** module, a reliable design combines Client IDs, QoS, retained/sessions, reconnection, TLS/ACLs, metadata, and real broker testing. **LWT only reports MQTT connection state, not device business health**; therefore add heartbeats, freshness checks, idempotency, error handling, and reconciliation rules before letting presence drive critical decisions.
