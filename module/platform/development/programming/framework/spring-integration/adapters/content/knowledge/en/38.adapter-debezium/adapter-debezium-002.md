# Change Event Payload in Spring Integration Debezium

## 1. Context: How Does a Database Change Flow Through a Spring Message?

Suppose a `public.orders` table in PostgreSQL has an order `ORD-101`. The application updates the order status from `CREATED` to `PAID`. Debezium reads the change from the transaction log and generates a **change event** that can contain the row key, before/after state, operation type, and source metadata. The Spring Integration Debezium inbound adapter sends this event into a `MessageChannel` for downstream components such as transformers, routers, gateways, and JDBC/Kafka/JMS outbound adapters to process.

~~~mermaid
flowchart LR
    A["BEGIN / UPDATE orders / COMMIT"] --> B[("PostgreSQL WAL")]
    B --> C["Debezium connector"]
    C --> D["ChangeEvent KEY + VALUE"]
    D --> E["DebeziumMessageProducer"]
    E --> F["Message<byte[]> + headers"]
    F --> G["Parse → Normalize → Validate"]
    G --> H["Route c/u/d/r"]
    H --> I["JDBC read model / Inbox / Kafka / JMS"]
~~~

A common point of confusion is that **`ChangeEvent` does not contain only a single JSON payload**. It usually carries a separate **key**, **value**, and **destination**; inside the value there is also an **envelope** indicating the change type and source metadata. After Spring Integration maps it, much of that information resides in **message headers**, not everything in `message.payload`.

This **Change event payload** lesson belongs to the **Adapter Debezium** chapter of the **SPRING_INTEGRATION_ADAPTERS** module. The module focuses on connecting external systems using inbound/outbound adapters, gateways, pollers, and `MessageChannel`; practicing with files, SFTP, HTTP, JMS, AMQP, Kafka, and databases, while addressing message contracts, errors, and connection lifecycles. This lesson dives into the **CDC data contract**, rather than being a guide to deploying a Kafka Connect cluster.

After this lesson, you will be able to read a standard change event, distinguish snapshots from streaming and DELETEs from tombstones, configure JSON/schema handling, and parse safely in Spring Integration; you will also learn how to build contracts for idempotency, routing, testing, and observability as payloads evolve across versions.

## 2. From Database Row to ChangeEvent, Then to Spring Message

A Debezium row change event can be described by three components:

| Debezium Engine Component | Meaning | Typical Location in Spring Integration |
|---|---|---|
| `ChangeEvent.key()` | Record key per table/connector, may be null | `DebeziumHeaders.KEY` header, typically `byte[]` with JSON byte-array |
| `ChangeEvent.value()` | Serialized change-event envelope or tombstone | `Message.getPayload()`, typically `byte[]` in single-event mode |
| `ChangeEvent.destination()` | Logical destination/topic set by the connector | `DebeziumHeaders.DESTINATION` header |
| `ChangeEvent.headers()` | Additional headers produced by source/SMT | Header mapper determines which ones are mapped |
| `MessageHeaders.ID/TIMESTAMP` | Metadata generated by Spring Messaging | **Not** the DB LSN/txId/op by default |

~~~text
Debezium ChangeEvent<byte[],byte[]>
  key()         = {"schema": {...}, "payload": {"id": 101}}
  value()       = {"schema": {...}, "payload": {"before":..., "after":..., "op":"u"}}
  destination() = "orders_source.public.orders"
                   |
                   v
Spring Message:
  payload: byte[] containing JSON VALUE
  headers:
    DebeziumHeaders.KEY         -> byte[] containing JSON KEY
    DebeziumHeaders.DESTINATION -> "orders_source.public.orders"
    id, timestamp              -> Spring Message metadata
~~~

**Note:** the representation above shows decoded JSON for readability; in Java, the actual data is usually bytes. With other converters/serializers, the key/value might not be JSON bytes. If a table lacks a primary/unique key or an operation has no record key, the key header may be absent or empty. Do not blindly cast every header to `byte[]`.

## 3. Choosing Compatible APIs and Versions

Spring Integration provides `DebeziumMessageProducer` and the Java DSL `Debezium.inboundChannelAdapter(...)` starting in **Spring Integration 6.2**. Standard examples use `DebeziumEngine.Builder<ChangeEvent<byte[],byte[]>>` when the Engine selects the `JsonByteArray` format. The Java DSL factory also accepts `java.util.Properties` and configures appropriate JSON serialization.

| API | Package | Role |
|---|---|---|
| `DebeziumMessageProducer` | `org.springframework.integration.debezium.inbound` | Converts Debezium events into Spring messages |
| `Debezium.inboundChannelAdapter(...)` | `org.springframework.integration.debezium.dsl` | DSL factory for creating the inbound endpoint |
| `DebeziumHeaders.KEY` | `org.springframework.integration.debezium.support` | Header name for the CDC record key |
| `DebeziumHeaders.DESTINATION` | Same `DebeziumHeaders` | Header name for the logical destination |
| `ChangeEvent<K,V>` | `io.debezium.engine` | Event from the Debezium Engine |
| `DebeziumEngine.create(JsonByteArray.class)` | Debezium Engine | Selects JSON `byte[]` format for key/value |
| `ObjectMapper/JsonNode` | Jackson | Parses JSON value/key after type checking |

**Do not mechanically apply** the JDBC Java DSL examples introduced in Spring Integration 7.0 to Debezium. Each API has its own version history. Verify compatible BOM, Spring Integration, Debezium Engine, and connector versions before running.

### 3.1. Illustrative Dependencies

~~~groovy
// Gradle snippet: pick a Debezium connector version compatible
// with the running Spring Integration/BOM.
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-integration'
    implementation 'org.springframework.integration:spring-integration-debezium'
    implementation 'org.springframework.boot:spring-boot-starter-json'

    runtimeOnly 'io.debezium:debezium-connector-postgres:COMPATIBLE_VERSION'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
~~~

`COMPATIBLE_VERSION` is a placeholder that must be replaced with the version pinned in your dependency management, **not** a literal build coordinate to run verbatim. You need the connector corresponding to your database; having `spring-integration-debezium` does not automatically include every database connector.

## 4. Key and Value Are Two Separate JSON Documents

Debezium with a JSON converter can produce a schema wrapper for **both key and value**. For example, a row with primary key `id=101`:

~~~json
{
  "schema": {
    "type": "struct",
    "name": "orders_source.public.orders.Key",
    "fields": [
      {"type": "int64", "field": "id", "optional": false}
    ]
  },
  "payload": {
    "id": 101
  }
}
~~~

This is the **JSON of the key**, not the row value.

An abbreviated CREATE event value:

~~~json
{
  "schema": {
    "type": "struct",
    "name": "orders_source.public.orders.Envelope"
  },
  "payload": {
    "before": null,
    "after": {
      "id": 101,
      "status": "CREATED",
      "total_cents": 120000
    },
    "source": {
      "connector": "postgresql",
      "db": "appdb",
      "schema": "public",
      "table": "orders",
      "snapshot": "false",
      "lsn": 26504000
    },
    "op": "c",
    "ts_ms": 1730000000123
  }
}
~~~

The `schema` objects in the JSON above have **fields omitted**; they illustrate structure rather than being a verbatim full output of a Debezium version. An actual envelope may contain `ts_us`, `ts_ns`, `transaction`, `source.ts_ms`, and many more fields.

**Do not parse `message.payload` by default just to get `key.id`**: the event key is separate and Spring Integration typically maps it into the `DebeziumHeaders.KEY` header. When an UPDATE changes the primary key, the old key and new key may appear across separate events.

## 5. JSON Schema Wrapper Can Be Enabled or Disabled

A common JSON representation includes the wrapper:

~~~json
{
  "schema": { "type": "struct", "name": "orders.Envelope" },
  "payload": {
    "before": null,
    "after": {"id": 101, "status": "CREATED"},
    "source": {"connector": "postgresql", "table": "orders"},
    "op": "c",
    "ts_ms": 1730000000123
  }
}
~~~

When configured with `value.converter.schemas.enable=false`, **for JSON converters supporting this option**, the value format can omit the wrapper:

~~~json
{
  "before": null,
  "after": {"id": 101, "status": "CREATED"},
  "source": {"connector": "postgresql", "table": "orders"},
  "op": "c",
  "ts_ms": 1730000000123
}
~~~

Similarly, `key.converter.schemas.enable=false` can reduce the key JSON to just the object containing key columns:

~~~json
{"id": 101}
~~~

**Do not assume all serializers apply these two properties identically.** Across `JsonByteArray`, `Json`, Kafka Connect `JsonConverter`, Avro/Protobuf/JSON Schema converters, and different major versions, verify the exact configuration and actual emitted bytes. This lesson uses a parser that tolerates **both wrapped and unwrapped JSON**; however, if the input is not JSON, a different deserializer is required.

## 6. Row Change Envelope: The Minimal Contract

Once the wrapper is unwrapped, a row-change envelope typically contains:

| Field | Meaning | Can Be Missing/Null? |
|---|---|---|
| `before` | Image of the row before the event | Yes; null on CREATE/SNAPSHOT, UPDATE depends on DB |
| `after` | Image of the row after the event | Yes; null on DELETE, TRUNCATE is not a row change |
| `op` | Operation code `r/c/u/d`; also `t/m` when supported by connector | Required for row change envelopes, not for every control record |
| `source` | Metadata about source DB/schema/table/log | Inner fields depend on the connector |
| `ts_ms` | Event processing timestamp (milliseconds) | May be null/missing depending on the event |
| `ts_us/ts_ns` | Higher-resolution timestamps | Depends on Debezium/connector version |
| `transaction` | Transaction metadata when enabled | Usually null if not enabled |
| `source.snapshot` | Snapshot information from connector | Can be boolean, string, or null depending on output/serializer |

UPDATE example:

~~~json
{
  "before": {"id": 101},
  "after": {"id": 101, "status": "PAID", "total_cents": 120000},
  "source": {
    "connector": "postgresql",
    "db": "appdb",
    "schema": "public",
    "table": "orders",
    "lsn": 26504123,
    "txId": 712
  },
  "op": "u",
  "ts_ms": 1730000054000
}
~~~

Do not assume `before.status` always exists. PostgreSQL `REPLICA IDENTITY DEFAULT` usually provides only the primary key in the before image of UPDATE/DELETE; getting the full before image may require `REPLICA IDENTITY FULL` at the cost of extra WAL volume. Debezium connectors also have rules per column type and version.

## 7. Operation Codes: r, c, u, d, t, and m

| `op` | Situation | Typical Handling | Warning |
|---|---|---|---|
| `r` | READ during snapshot | Upsert read model | Not a new business INSERT |
| `c` | CREATE/INSERT | Upsert/projection or domain logic | Can be replayed |
| `u` | UPDATE | Apply `after`, version check | `before` is not necessarily full |
| `d` | DELETE | Delete by key/before | May be followed by a tombstone |
| `t` | TRUNCATE (connector supported) | Handle full-table clear or controlled cache invalidation | Usually has no row key |
| `m` | Logical message (PostgreSQL, if enabled) | Route to dedicated control/metadata handler | Does not have a row before/after shape |

`op="r"` is usually associated with an initial/incremental snapshot; it represents an existing row being read. When a snapshot re-runs because offsets were lost, `r` events can be replayed multiple times. Projections must implement corresponding upsert/idempotency logic.

`op="t"` typically has **no** key and no `after.id`. If a consumer only handles `r/c/u/d`, it must **explicitly reject or route** `t` instead of accessing `after.id`, causing a NullPointerException and endless retries. `op="m"` is also a special type; verify config and connector version.

## 8. CREATE: New Key and After Image

~~~sql
INSERT INTO public.orders(id, status, total_cents)
VALUES (101, 'CREATED', 120000);
~~~

Value (schema wrapper removed for readability):

~~~json
{
  "before": null,
  "after": {"id": 101, "status": "CREATED", "total_cents": 120000},
  "source": {"connector": "postgresql", "table": "orders"},
  "op": "c",
  "ts_ms": 1730000000123
}
~~~

**Contract:** the key from `DebeziumHeaders.KEY` indicates the row identity; `after` is the current image; `before` is null. When writing to `order_projection` downstream, you can use an UPSERT by `order_id` or a checked insert depending on business policy. Never use `ts_ms` as a unique global sequence.

## 9. UPDATE: Before Is Not a Full Copy

~~~sql
UPDATE public.orders
SET status='PAID'
WHERE id=101;
~~~

Illustrative value:

~~~json
{
  "before": {"id": 101},
  "after": {"id": 101, "status": "PAID", "total_cents": 120000},
  "source": {
    "connector": "postgresql",
    "table": "orders",
    "snapshot": "false",
    "lsn": 26504123
  },
  "op": "u",
  "ts_ms": 1730000054000
}
~~~

**A classic bug:** checking `before.status == "CREATED"` and failing when `REPLICA IDENTITY DEFAULT` does not include the `status` column in `before`. Consumers can use only `after` to upsert the read model and rely on a version/LSN/business sequence to prevent stale data from overwriting newer data.

If business logic strictly requires computing a delta between before and after images, verify that the source actually provides the complete `before` image; otherwise, emit a business event in a transactional outbox rather than guessing from a CDC row update.

## 10. DELETE: Before May Contain Only the Key, After Is Null

~~~sql
DELETE FROM public.orders WHERE id=101;
~~~

Illustrative delete envelope:

~~~json
{
  "before": {"id": 101},
  "after": null,
  "source": {"connector": "postgresql", "table": "orders"},
  "op": "d",
  "ts_ms": 1730000099000
}
~~~

A DELETE event has a **value envelope** (still containing `op="d"`). When deleting a row in a read model, you can extract the key from the JSON key header or `before.id`; if both are missing, **do not** guess the ID from timestamp or destination.

After a DELETE, Debezium may emit a **tombstone** with the same key and a **null value**. A tombstone is not `op="d"` and has no `after`; section 12 covers this further.

## 11. Snapshot READ: source.snapshot Is Not Always a Boolean

During a snapshot, `op="r"`; some outputs emit `source.snapshot=true`, while others represent it as the string `"true"` or `"last"` when marking the final record depending on the version/connector. Consumers must interpret snapshot markers according to the version contract rather than forcing a single type.

~~~json
{
  "before": null,
  "after": {"id": 102, "status": "CREATED", "total_cents": 89000},
  "source": {
    "connector": "postgresql",
    "table": "orders",
    "snapshot": "true"
  },
  "op": "r",
  "ts_ms": 1730000150000
}
~~~

**Do not turn a snapshot READ into a new "OrderCreated" business event.** A snapshot only builds initial state; if you need to emit business events for genuine creations, use streaming `op="c"` events or outbox business events carrying an event ID.

## 12. Tombstone: Empty Value, Different from a DELETE Envelope

Deleting a row can produce the following sequence (depending on connector/tombstone configuration):

~~~text
DELETE event:
  key   = {"id":101}
  value = {"before":{"id":101},"after":null,"op":"d",...}

Tombstone event:
  key   = {"id":101}
  value = null
~~~

Tombstones serve **log compaction** and deletion policies in sinks that require a null-value event with the same key. In the Spring Integration Debezium adapter, `enableEmptyPayload` defaults to `false`. When `enableEmptyPayload(true)` is enabled, the adapter documentation represents the tombstone value as `Optional.empty()` — not a JSON string `"null"`.

~~~java
import java.util.Optional;
import org.springframework.messaging.Message;

void inspect(Message<?> message) {
    Object payload = message.getPayload();

    if (payload instanceof Optional<?> option && option.isEmpty()) {
        // Tombstone: extract the key from DebeziumHeaders.KEY.
    } else if (payload instanceof byte[] jsonBytes) {
        // JSON envelope: could be c/u/d/r/t/m.
    } else {
        // Unsupported payload format/batch: do not cast blindly.
    }
}
~~~

**The snippet above shows type-checking logic**, not a full Spring bean. Do not treat every tombstone as a new business DELETE: if `op="d"` was already handled, the tombstone may only need to be forwarded to a compacted Kafka topic; applications must avoid invoking a delete service twice if side effects are not idempotent.

## 13. UPDATE Changing Primary Key: One Update Can Become Multiple Records

Some Debezium connectors, including PostgreSQL, represent a primary key change as a sequence of change events rather than a single regular UPDATE keeping one record key:

~~~text
Old row: id=101, status=PAID
SQL: UPDATE orders SET id=205 WHERE id=101

Record 1: DELETE envelope for old key id=101
Record 2: Tombstone value=null with old key id=101 (if enabled)
Record 3: CREATE envelope for new key id=205
~~~

Depending on connector and version, extra headers may link the old key and new key. Therefore:
- **Do not assume one SQL statement always produces exactly one CDC message.**
- Do not group all records by a fixed primary key value if keys can change.
- Projections with foreign-key references need an appropriate rekey policy or explicit business events.
- Consumer idempotency must evaluate per-record/aggregate version rather than blindly deleting/inserting if events arrive out of order.

If atomic rekeying across multiple target tables is required, a raw CDC sequence alone does not provide an atomic downstream transaction. Consider a transactional outbox/domain command with appropriate transaction logic.

## 14. TRUNCATE and Logical Messages: Not a Row with an ID

The PostgreSQL connector can emit `op="t"` when receiving `TRUNCATE`. Truncate events usually **have no record key**, and `before`/`after` do not have a row shape like CREATE/UPDATE. It represents an action on **an entire table**, not individual row deletes.

~~~json
{
  "source": {
    "connector": "postgresql",
    "db": "appdb",
    "schema": "public",
    "table": "orders"
  },
  "op": "t",
  "ts_ms": 1730000160000
}
~~~

Across multiple partitions or consumers, ordering `TRUNCATE` relative to row updates can be problematic. Do not automatically map `t` into thousands of asynchronous `DELETE`s without a sequencing policy. Cache/read-model systems may need a "clear projection" with its own transaction or generation ID.

PostgreSQL also supports logical messages (`op="m"`) when the connector enables capturing them. Those events may contain `message` metadata such as prefix and content, **without** `after.id`. Route them to a dedicated control-message handler or quarantine them if they are outside the business contract.

## 15. Timestamps: Source Event Time vs. Processing Time

A value can contain:
- `payload.ts_ms`: time Debezium **processed the event** in the connector JVM.
- `payload.ts_us`/`payload.ts_ns`: higher resolution if provided.
- `payload.source.ts_ms`: time of the change at the **source database** if provided by the connector.
- `MessageHeaders.TIMESTAMP`: time the **Spring Message** was created, not the DB commit timestamp.

Example:

~~~json
{
  "op": "u",
  "source": {
    "connector": "postgresql",
    "table": "orders",
    "ts_ms": 1730000100000
  },
  "ts_ms": 1730000102400,
  "ts_us": 1730000102400123
}
~~~

Approximate lag measurement:

\[
\mathrm{lag}_{CDC} = \mathrm{payload.ts\_ms} - \mathrm{payload.source.ts\_ms}
\]

Do not treat this difference as end-to-end latency including Kafka/JMS ACKs or read-model updates. Timestamps may be missing or clocks may drift; collect `cdc_capture_lag`, `inbox_commit_lag`, `publish_lag`, and `consumer_apply_lag` separately.

**Never use timestamps as unique event IDs or absolute ordering keys.** Multiple events can share the same millisecond; timestamps may not be monotonic across connections, DB transactions, or clocks.

## 16. Source Metadata: PostgreSQL, MySQL, and Other Connectors

`source` is structured by the source connector, not a contract where all DBs share every field:

| Illustrative Field | PostgreSQL | MySQL | Notes |
|---|---|---|---|
| `connector` | `postgresql` | `mysql` | Identifies the source |
| `db` | Database name | Database name | Not automatically a tenant |
| `schema` | `public` | Typically differs from PostgreSQL | May be null/absent |
| `table` | Table name | Table name | Not a business topic |
| `lsn` | WAL log sequence number | Does not use PostgreSQL LSN | PG-specific |
| `txId` | May be present | May differ | Not a global event ID |
| `file/pos/row` | Not a PG LSN | Binlog position/row | Depends on MySQL version |
| `snapshot` | Boolean/string/marker | Boolean/string/marker | Do not force a rigid type |
| `ts_ms` | Source event time | Source event time | May be null |

Correspondingly, PostgreSQL source offsets relate to WAL/LSN; MySQL uses binlog filename/position and metadata. **Do not write a mandatory `Long.parseLong(source.lsn)` method across all database adapters**.

### 16.1. What Is Needed to Determine Event Identity?

`(database, table, primaryKey)` identifies a row, not individual UPDATEs. `(source.lsn)` can help locate a log position in PostgreSQL, but it **is not automatically a unique event ID** if one transaction/LSN produces multiple records or Debezium changes granularity. If source-level deduplication is needed, design a connector/version-specific tuple including log position, transaction, collection, and record ordering.

Simpler and more durable for domain events is writing a **unique business `event_id` in a transactional outbox**, so downstream deduplication does not depend on DB-specific offset syntax.

## 17. Transaction Metadata: Conditional Grouping and Ordering

When transaction metadata is enabled, Debezium can emit transaction boundary records (BEGIN/END) along with `transaction` metadata inside each data envelope.

~~~json
{
  "before": null,
  "after": {"id": 101, "status": "PAID"},
  "source": {
    "connector": "postgresql",
    "table": "orders",
    "lsn": 26504123
  },
  "op": "c",
  "transaction": {
    "id": "712:26504123",
    "total_order": 2,
    "data_collection_order": 1
  }
}
~~~

This is an **illustrative shape**, not a guarantee that every connector uses the exact same `id` format. `transaction.total_order` describes the event's position within the transaction, while `data_collection_order` is the order within that collection/table; they are usually **absent** if transaction metadata is not enabled or transactions occurred before the connector began tracking.

Example boundary event:

~~~json
{
  "status": "END",
  "id": "712:26504123",
  "event_count": 2,
  "data_collections": [
    {"data_collection": "public.orders", "event_count": 2}
  ]
}
~~~

**BEGIN/END boundary records are not row change envelopes.** If you want to consume them, choose an appropriate destination/handler; never route them into a parser expecting `before/after/op`.

**Do not equate an Engine batch with a single database transaction.** A Debezium batch may contain records from multiple transactions or only part of a large transaction; transaction grouping must rely on actual metadata, not merely event counts in a callback.

## 18. Serialization Formats: JSON Bytes, Avro, Protobuf, and Schema Registry

In Spring Integration Debezium inbound:
- Java DSL `Debezium.inboundChannelAdapter(Properties)` is convenient for JSON serialization.
- A pre-configured `DebeziumEngine.Builder<ChangeEvent<byte[],byte[]>>` uses `JsonByteArray` for JSON bytes.
- `DebeziumMessageProducer#setContentType(...)` attaches the content-type contract; it must **match the actual format**.
- Enabling Avro/Protobuf requires matching serializers/deserializers and schema handling; you cannot parse Avro bytes with a Jackson JSON tree.

~~~java
import io.debezium.engine.ChangeEvent;
import io.debezium.engine.DebeziumEngine;
import io.debezium.engine.format.JsonByteArray;

// Illustrative builder: config Properties must contain valid connector,
// offset, database, and security settings.
DebeziumEngine.Builder<ChangeEvent<byte[], byte[]>> builder =
    DebeziumEngine.create(JsonByteArray.class).using(config);
~~~

Avoid writing `new String(bytes)` with the default charset; JSON should be decoded using UTF-8. With Avro/Protobuf and a registry, payloads may carry a schema identifier/wire format; use a compatible deserializer and watch schema evolution and message size.

## 19. Single-Event vs. Batch-Mode Adapter Payloads

`DebeziumMessageProducer` has `enableBatch`:

| Mode | Payload Sent in Spring Message | Analysis |
|---|---|---|
| `enableBatch(false)` (default) | Typically `byte[]` per `ChangeEvent` (JSON byte-array) | Fits per-event parsing/routing |
| `enableBatch(true)` | `List<ChangeEvent>` from the Engine batch | **Not serializable** per adapter docs; must be converted to a DTO if sent over a persistent channel |

~~~text
Engine callbacks: [E1, E2, E3]

enableBatch(false):
    Message<byte[]>(E1.value)
    Message<byte[]>(E2.value)
    Message<byte[]>(E3.value)

enableBatch(true):
    Message<List<ChangeEvent>>(E1, E2, E3)
~~~

In batch mode, **do not** cast the list to `List<byte[]>`; each element is a `ChangeEvent` with `key()`, `value()`, and `destination()`. Before using a JDBC outbound batch, transform it into `List<DomainCommand>` with explicit SQL parameter semantics; a list of raw CDC events is not a command list.

### 19.1. Serialized Persistence Issue

An in-memory `QueueChannel` or `ExecutorChannel` can hold references to a `List<ChangeEvent>`, but that does not guarantee it can be serialized into a `JdbcMessageStore` or JMS. For workloads requiring durable retry, normalize/validate and stage a serializable DTO or inbox row before the async boundary.

## 20. Java DSL: Creating a Debezium Inbound Source and Parse Channel

This example uses a PostgreSQL connector configured for the appropriate database, snapshot, and offset settings. Properties are externalized rather than hardcoding DB secrets:

~~~java
package com.example.cdc.payload;

import java.util.Properties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.debezium.dsl.Debezium;
import org.springframework.integration.dsl.IntegrationFlow;

@Configuration
public class CdcInputConfiguration {

    @Bean
    public IntegrationFlow ordersCdcInputFlow(
            Properties debeziumConfiguration) {
        return IntegrationFlow
            .from(Debezium.inboundChannelAdapter(
                    debeziumConfiguration)
                .contentType("application/json")
                .enableBatch(false)
                .enableEmptyPayload(true))
            .channel("rawOrderChanges")
            .get();
    }
}
~~~

Here, `debeziumConfiguration` is a **Spring `Properties` bean created by the application**, using a specific bean name/`@Qualifier` if multiple `Properties` beans exist. It must contain `connector.class`, PostgreSQL credentials, `topic.prefix`, `table.include.list`, and replication/offset store settings. This is a messaging-layer skeleton; it does not create the database, parser, or downstream handlers.

If tombstones are not needed, omit `enableEmptyPayload(true)` and focus on handling `op="d"`; if you want to forward null-value records into a compacted Kafka topic, retain tombstones with their proper key.

## 21. Normalized DTO: Separating Technical Events from Business Commands

Handlers should not all directly know about the raw `schema/payload/source/op` structure. A **Normalization** layer creates a stable internal contract:

~~~java
package com.example.cdc.payload;

import com.fasterxml.jackson.databind.JsonNode;
import java.time.Instant;

// Immutable DTO; key/source/rows may be null depending on the operation.
public record NormalizedCdcEvent(
        CdcOp op,
        String destination,
        JsonNode key,
        JsonNode before,
        JsonNode after,
        String database,
        String schema,
        String table,
        Long sourceLsn,
        Instant capturedAt,
        Instant processedAt,
        boolean fromSnapshot) {

    public enum CdcOp {
        READ, CREATE, UPDATE, DELETE, TRUNCATE, MESSAGE, TOMBSTONE
    }
}
~~~

Distinguish:
- `destination`: Debezium logical route, not implicitly a trusted tenant.
- `key`: decoded record key (may be null on TRUNCATE or no-PK tables).
- `before/after`: kept as `JsonNode` before mapping to business entities for schema validation.
- `sourceLsn`: nullable because the source might not be PostgreSQL.
- `capturedAt/processedAt`: nullable when timestamps are absent.
- `fromSnapshot`: parsed according to the version contract; do not force `source.snapshot` to `Boolean` across all connectors.
- `TOMBSTONE`: a distinct internal kind, **without a JSON row envelope**.

**Do not fabricate an `eventId` field by using the row PK as the ID for every UPDATE.** If downstream requires exactly-once business effects, identity must come from an outbox `event_id` or a designed and verified source tuple/sequence.

## 22. Jackson Parser: Accepting Both Schema-Wrapped and Unwrapped Forms

A parser should:
1. Check that bytes are non-null and non-empty.
2. Parse JSON using `ObjectMapper` (with size limits at the boundary).
3. If the root contains a `payload` object (with `schema`), take it as the envelope; if the root directly contains `op`, take the root.
4. Validate `op`; never guess `op="c"` if missing.
5. Require `after` only for row changes `r/c/u`.
6. Do not force `before` to exist on `u/d`; use the record key or DB contract for deletes.
7. Parse `source`/timestamps conditionally and do not confuse `source.ts_ms` with `envelope.ts_ms`.

~~~java
package com.example.cdc.payload;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.io.IOException;
import java.time.Instant;
import org.springframework.stereotype.Component;

@Component
public final class DebeziumEnvelopeDecoder {

    private final ObjectMapper mapper;

    public DebeziumEnvelopeDecoder(ObjectMapper mapper) {
        this.mapper = mapper;
    }

    public DecodedEnvelope decode(byte[] json) throws IOException {
        if (json == null || json.length == 0) {
            throw new IllegalArgumentException("Empty CDC value");
        }

        JsonNode root = mapper.readTree(json);
        if (root == null || !root.isObject()) {
            throw new IllegalArgumentException("CDC JSON root must be object");
        }

        JsonNode candidate = root.path("payload");
        JsonNode envelope = candidate.isObject() && root.has("schema")
            ? candidate : root;
        // schemas=false configuration can produce the root envelope directly.
        // If there is a wrapper without a schema field, detect it
        // via a declared contract rather than guessing arbitrary JSON objects.
        if (!envelope.isObject()) {
            throw new IllegalArgumentException("Missing CDC envelope");
        }

        String op = envelope.path("op").asText("");
        if (!op.equals("r") && !op.equals("c")
                && !op.equals("u") && !op.equals("d")
                && !op.equals("t") && !op.equals("m")) {
            throw new IllegalArgumentException("Unsupported op: " + op);
        }

        JsonNode before = nullable(envelope.path("before"));
        JsonNode after = nullable(envelope.path("after"));
        JsonNode source = nullable(envelope.path("source"));

        if ((op.equals("r") || op.equals("c") || op.equals("u"))
                && (after == null || !after.isObject())) {
            throw new IllegalArgumentException(
                "Missing after for row change: " + op);
        }

        return new DecodedEnvelope(
            op, before, after, source,
            millis(envelope.path("ts_ms")));
    }

    private static JsonNode nullable(JsonNode node) {
        return node == null || node.isMissingNode() || node.isNull()
            ? null : node;
    }

    private static Instant millis(JsonNode node) {
        if (node == null || !node.canConvertToLong()) {
            return null;
        }
        return Instant.ofEpochMilli(node.longValue());
    }

    public record DecodedEnvelope(
        String op,
        JsonNode before,
        JsonNode after,
        JsonNode source,
        Instant processedAt) { }
}
~~~

**This is a parser for declared JSON row envelopes**, not a parser for every Debezium control event or Avro/Protobuf. If a custom converter emits `{"payload": {...}}` **without `schema`**, extend it with an explicit contract/config flag. Avoid guessing schema wrappers based on uncertain business field names.

### 22.1. Do Not Conflate Null and Missing Using `asText("")` Across All Fields

A JSON field can be in one of three states:
- Absent (`MissingNode`);
- Present as `null`;
- Present with a real value, including an empty string `""` or `0`.

In CDC, **a missing `before.status` does not mean `status=""`**, and `after=null` on DELETE is not a parser failure. Use `isMissingNode()`/`isNull()`/`isObject()` to distinguish states before applying business logic.

## 23. Decoding Keys from DebeziumHeaders.KEY According to Real Format

~~~java
package com.example.cdc.payload;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.io.IOException;
import org.springframework.integration.debezium.support.DebeziumHeaders;
import org.springframework.messaging.Message;
import org.springframework.stereotype.Component;

@Component
public final class DebeziumKeyDecoder {

    private final ObjectMapper mapper;

    public DebeziumKeyDecoder(ObjectMapper mapper) {
        this.mapper = mapper;
    }

    public JsonNode decode(Message<?> message) throws IOException {
        Object raw = message.getHeaders().get(DebeziumHeaders.KEY);

        if (raw == null) {
            return null;
        }
        if (!(raw instanceof byte[] bytes)) {
            throw new IllegalArgumentException(
                "Unsupported Debezium KEY type: "
                + raw.getClass().getName());
        }
        JsonNode root = mapper.readTree(bytes);
        if (root == null || root.isNull()) {
            return null;
        }
        JsonNode wrapped = root.path("payload");
        if (root.has("schema") && wrapped.isObject()) {
            return wrapped;
        }
        return root;
    }
}
~~~

In the PostgreSQL connector, a table with primary key `id` usually produces a JSON key containing `id`. Keyless tables, TRUNCATEs, and certain control records can produce a null key. If the application contract requires a key, validate it in the corresponding route — **do not force all events to have a key**.

For Avro/Protobuf payload modes, the key header may need to be decoded with a dedicated schema-aware deserializer. Using `new String((byte[]) header)` is only valid for debugging JSON bytes, not as a universal key parser.

## 24. Spring Integration Handler: Classifying Tombstones Before Parsing

~~~java
package com.example.cdc.payload;

import com.fasterxml.jackson.databind.JsonNode;
import java.io.IOException;
import java.util.Optional;
import org.springframework.integration.annotation.ServiceActivator;
import org.springframework.integration.debezium.support.DebeziumHeaders;
import org.springframework.messaging.Message;
import org.springframework.stereotype.Component;

@Component
public final class OrdersChangeDispatcher {

    private final DebeziumEnvelopeDecoder envelopes;
    private final DebeziumKeyDecoder keys;
    private final CdcApplicationService service;

    public OrdersChangeDispatcher(
            DebeziumEnvelopeDecoder envelopes,
            DebeziumKeyDecoder keys,
            CdcApplicationService service) {
        this.envelopes = envelopes;
        this.keys = keys;
        this.service = service;
    }

    @ServiceActivator(inputChannel = "rawOrderChanges")
    public void onChange(Message<?> message) throws IOException {
        Object rawDestination =
            message.getHeaders().get(DebeziumHeaders.DESTINATION);
        if (!(rawDestination instanceof String destination)
                || destination.isBlank()) {
            throw new IllegalArgumentException(
                "Missing or invalid Debezium destination");
        }
        JsonNode key = keys.decode(message);
        Object value = message.getPayload();

        if (value instanceof Optional<?> option && option.isEmpty()) {
            service.onTombstone(destination, key);
            return;
        }
        if (!(value instanceof byte[] bytes)) {
            throw new IllegalArgumentException(
                "Unexpected CDC payload type: "
                + value.getClass().getName());
        }

        DebeziumEnvelopeDecoder.DecodedEnvelope decoded =
            envelopes.decode(bytes);

        switch (decoded.op()) {
            case "r", "c", "u" ->
                service.upsert(destination, key, decoded.after(), decoded);
            case "d" ->
                service.delete(destination, key, decoded.before(), decoded);
            case "t" ->
                service.truncate(destination, decoded);
            case "m" ->
                service.onLogicalMessage(destination, decoded);
            default -> throw new IllegalStateException("Unexpected op");
        }
    }
}
~~~

`CdcApplicationService` is an **application-defined interface** with illustrative methods `onTombstone`/`upsert`/`delete`/`truncate`/`onLogicalMessage`. It must validate destination, key, schema, and authorization; durably persist business state/inbox/outbox; and perform idempotency/version checks. This is an example of **code organization**, not a complete production implementation.

**Never log raw `message.payload` when customer PII is present.** When a handler encounters an unfamiliar format, route the record into a controlled quarantine instead of logging `toString()` on multi-megabyte events.

## 25. CDC Data Types: Decimal, Timestamp, UUID, Binary, and JSON

An `after` value contains JSON fields, but **the original DB type does not necessarily match default Java/Jackson types**. Debezium and Kafka Connect have logical types; serialization depends on the connector, precision, and converter:

| Source | Possible Representation | Safe Rule |
|---|---|---|
| PostgreSQL `BIGINT` | JSON integer | Use `long` with range checks; do not narrow to `int` |
| `NUMERIC/DECIMAL` | Decimal string, binary/Base64, or number depending on mode | Use `BigDecimal`; never use `double` for money |
| `TIMESTAMP/TIMESTAMPTZ` | Epoch integer in ms/us/ns or ISO string | Pin `time.precision.mode`/formatter and timezone |
| `UUID` | UUID string or specific logical type | Validate with `UUID.fromString` if contract is UUID text |
| `BYTEA/BLOB` | Base64/byte-array per converter and binary mode | Do not log sensitive Base64 |
| PostgreSQL `JSON/JSONB` | Can be a JSON-encoded string or a mapped JSON structure | Parse per connector/serialization contract |
| SQL `NULL` | JSON null | Distinct from a field absent due to schema/masking |
| Enum/array/geography | Converter-specific representation | Use versioned mappings and DB-backed tests |

Decoded JSON bytes example:

~~~json
{
  "after": {
    "id": 101,
    "total_cents": 120000,
    "exchange_rate": "1.234567890123456789",
    "placed_at": 1730000000123456,
    "customer_ref": "b7a91944-30ac-4f30-8cd2-5d8dbaf1db72"
  },
  "op": "u",
  "source": {"connector": "postgresql"}
}
~~~

This is an **illustrative format**, not a mandatory default across all converters. `placed_at` may be epoch **microseconds**, not milliseconds. `Instant.ofEpochMilli(1730000000123456L)` would yield a date thousands of years off if the true value is microseconds.

### 25.1. Decimals Should Not Pass Through double

~~~java
import com.fasterxml.jackson.databind.JsonNode;
import java.math.BigDecimal;

BigDecimal readDecimal(JsonNode row, String field) {
    JsonNode value = row.path(field);
    if (value.isMissingNode() || value.isNull()) {
        return null;
    }
    if (!value.isTextual() && !value.isNumber()) {
        throw new IllegalArgumentException(
            "Unsupported decimal representation");
    }
    return new BigDecimal(value.asText());
}
~~~

This snippet only handles **string or JSON-number decimals**. If the converter emits a binary logical decimal in Base64, you must decode scale/precision properly; do not treat Base64 as a decimal string.

### 25.2. Timestamps Require Explicit Units and Timezone

~~~java
import java.time.Instant;

// Only when the source contract confirms the value is epoch MICROSECONDS.
long micros = 1730000000123456L;
Instant instant = Instant.ofEpochSecond(
    Math.floorDiv(micros, 1_000_000L),
    Math.floorMod(micros, 1_000_000L) * 1_000L);
~~~

Do not guess the unit by counting digits in a timestamp when DB/connector resolutions vary. Keep `capturedAt`, `processedAt`, and `businessOccurredAt` in separate fields if the contract requires all three.

## 26. Schema Evolution: Consumers Must Tolerate Controlled Changes

Suppose the initial schema is:

~~~json
{"after":{"id":101,"status":"CREATED","total_cents":120000},"op":"c"}
~~~

After a migration adding `discount_cents` and renaming `total_cents` to `gross_total_cents`:

~~~json
{
  "after": {
    "id": 101,
    "status": "CREATED",
    "gross_total_cents": 120000,
    "discount_cents": 5000
  },
  "op": "u"
}
~~~

An older consumer reading only `after.total_cents` might silently return 0 or null if it uses `asLong(0)` without checking for missing fields. Strategies:

1. **Additive changes:** add nullable/defaulted fields; consumers ignore unused fields.
2. **Breaking renames:** run dual-read/dual-write during the migration window or version the DTO.
3. **Type changes:** validate range/precision and avoid coercing ambiguous string numbers.
4. **Schema Registry:** when using Avro/Protobuf, check compatibility modes and subject/key/value schema versions.
5. **Contract tests:** use golden CDC events from both before and after the migration.
6. **Control events:** explicitly handle or route heartbeat, transaction, truncate, and schema control messages without throwing NPEs on missing `after`.
7. **EventRouter/SMT:** may transform the envelope before it reaches the application; downstream contracts must reflect the **post-SMT** format.

**Do not treat Debezium schema field names as a permanently stable business API.** CDC mirrors the source table; business event contracts should be versioned independently when consumed by multiple critical downstream systems.

### 26.1. Replica Identity and Migration Impact

PostgreSQL:

~~~sql
-- Lab example; weigh WAL cost and DBA privileges.
ALTER TABLE public.orders REPLICA IDENTITY FULL;
~~~

`REPLICA IDENTITY FULL` enriches `before` on UPDATE/DELETE, but increases WAL volume and overhead. Avoid enabling it across all tables merely for easier debugging; prefer a business outbox when full events are needed, and evaluate sensitive data exposure in before images.

## 27. Debezium Single Message Transforms Can Alter the Payload

Debezium supports **Single Message Transforms (SMTs)**. For instance, `ExtractNewRecordState` can "unwrap" an envelope and keep only the `after` row, with configurable DELETE handling and metadata fields. After that SMT, the payload may look like:

~~~json
{"id": 101, "status": "PAID", "total_cents": 120000}
~~~

This is **no longer** an envelope with `op`, `source`, and `before/after` in the original structure. A consumer using `DebeziumEnvelopeDecoder` will report `Missing op` — rightly so, because the contract changed.

**Rule:** explicitly document where `SMT`s are applied (connector/Engine/Kafka Connect), which output format is permitted into Spring Integration, and whether `op`/`table`/`source` headers are preserved. Do not write a parser that silently guesses between the original envelope and unwrapped records without an explicit version/config flag.

SMTs such as the outbox EventRouter can rewrite the key, route, payload, and headers into a business event. In that case, `DebeziumHeaders.KEY` reflects the **post-transform** event key, not automatically the original `orders.id` primary key.

## 28. Routing Safely by Destination and Operation

A single flow may receive changes from multiple tables. Define an allowlist:

~~~text
orders_source.public.orders
    + op in [r,c,u] -> order projection upsert
    + op=d          -> order projection delete
    + tombstone     -> compacted Kafka forwarding policy
    + op=t          -> controlled full-invalidation handler

orders_source.public.customers
    + op in [r,c,u] -> customer projection
    + op=d          -> customer delete
    + unrecognized  -> quarantine
~~~

**Never** concatenate `DebeziumHeaders.DESTINATION` into a SQL table name:

~~~java
// Never do this with an untrusted destination:
// jdbc.execute("DELETE FROM " + destination);
~~~

Even though destinations are generated by the connector, schemas can change, header mappers can be customized, and messages may originate from another endpoint. Use a fixed allowlist mapping destination → configured handler/repository and validate tenant authorization.

### 28.1. Routing by Event Data Instead of Arbitrary JSON Manipulation

A `@ServiceActivator` like in section 24 can delegate to `CdcApplicationService`; the service should separate:
- `OrderProjectionService` for `r/c/u`;
- `DeleteProjectionService` for `d`;
- `TruncateControlService` when permitted;
- `TombstoneForwarder` if Kafka compaction is needed;
- `QuarantineService` for unsupported schemas/operations.

Do not execute `DELETE FROM orders` against the source operational table when receiving a CDC DELETE; the handler must update the **corresponding sink/read model** to avoid an infinite CDC loop.

## 29. Ordering: Spring Message Order Is Not Guaranteed to Match Source Commit Order

For a given row key, an application might expect `CREATED → PAID → SHIPPED`. However:
- The Engine may emit sequentially per connector task, yet versions support asynchronous execution;
- Multi-threaded `ExecutorChannel`s can reorder processing;
- Multi-partition Kafka topics preserve order **within a single partition**, with no global ordering;
- Primary-key changes generate multiple events;
- Snapshots and streaming have distinct semantics;
- Retries and replays can reintroduce an older event after the sink has reached a newer version.

**A practical solution:** conditional downstream updates using an `aggregate_version` generated at the source database:

~~~sql
-- Read model example where source events carry a monotonic version.
UPDATE order_read_model
SET status = :newStatus, version = :newVersion
WHERE id = :orderId
  AND version < :newVersion;
~~~

This is a simple optimistic check; for records that do not yet exist, use a vendor-appropriate **version-guarded UPSERT**. `version` must be incremented at the source per business mutation; never use `MessageHeaders.TIMESTAMP` as a version.

If gaps in the event sequence can occur and the business cannot tolerate skipping intermediate states, use per-aggregate queuing/partitioning, gap detection, and reconciliation. Do not rely solely on `version < newVersion` and assume missing events are harmless.

## 30. Idempotency and Replay: A Row Key Is Not an Event ID

Network failures or offset flush timing can cause Debezium to replay an event already processed downstream. With raw row changes:

~~~text
E1: row id=101, op=u, status=PAID
E2: row id=101, op=u, status=SHIPPED
Replay of E1 arrives after E2
~~~

If a consumer deduplicates solely on `rowId=101`, E2 could be dropped as a duplicate. If it blindly applies E1 when replayed after E2, the status regresses from SHIPPED back to PAID. A clear identity/version contract is needed.

| Case | Common Choice |
|---|---|
| Current-state read model | UPSERT guarded by aggregate version |
| Immutable business event | Outbox table with stable/UNIQUE `event_id` |
| Raw CDC offset deduplication | Event identity tuple verified per connector and record position |
| Kafka/JMS redelivery | Durable processed-event table + unique event ID |
| HTTP side effect | Remote idempotency key or reconciliation |
| DELETE/rekey | Tombstone/key semantics and version/order policy |

Outbox table example:

~~~sql
CREATE TABLE order_outbox (
    event_id       UUID PRIMARY KEY,
    aggregate_id   BIGINT NOT NULL,
    aggregate_ver  BIGINT NOT NULL,
    event_type     VARCHAR(80) NOT NULL,
    payload_json   JSONB NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (aggregate_id, aggregate_ver)
);
~~~

The business transaction **UPDATEs `orders` and INSERTs into `order_outbox`** within the same local DB transaction. Debezium captures the outbox and downstream consumers deduplicate on `event_id`. Do not mistake Debezium publishing to a Spring channel for a distributed database+Kafka XA transaction.

## 31. Offset, Commit, and Downstream Transactions Are Separate Boundaries

~~~mermaid
sequenceDiagram
    participant DB as PostgreSQL
    participant Eng as Debezium Engine
    participant SI as Spring Integration
    participant Inbox as Inbox database
    participant K as Kafka/JMS
    DB-->>Eng: ChangeEvent E1
    Eng->>SI: Message E1
    SI->>Inbox: INSERT inbox(eventId) + COMMIT
    Note over SI,Inbox: Work durable in local DB
    Eng->>Eng: Mark/flush source offset per Engine
    Inbox->>K: Publisher retries sending E1
    K-->>Inbox: Broker ACK (redelivery possible)
~~~

A successful `MessageChannel.send()` call is not a transaction commit receipt. Spring Integration's `DirectChannel` keeps the handler synchronous on the callback thread, but does not open a JDBC transaction automatically; `ExecutorChannel`/`QueueChannel` introduce async boundaries, so the Engine callback may return before the worker durably stages data.

Scenarios:
- **Crash after inbox COMMIT before offset flush:** the event may replay; the unique event ID must deduplicate it.
- **Offset advances before async job is durable:** the job risks being lost on process crash.
- **Kafka ACKs before outbox is marked published:** the publisher may resend; consumers must be idempotent.
- **External HTTP effect succeeds but response is lost:** requires an idempotency token/reconciliation, not blind retries.

**For raw CDC events lacking a stable business event ID, an inbox requires a deduplication key designed for the source/connector.** Never concatenate `db.table + rowPK` and assume every update is unique. Without a strong deduplication contract, rely on snapshot rebuilds, versioned materialized views, or a source transactional outbox.

## 32. Security: CDC Payloads Can Contain PII and Secrets

A change event can contain **both the full new and old images** of a row. If a table stores `email`, `phone`, tokens, addresses, or payment metadata, CDC spreads them to sinks, logs, dead-letter queues, traces, and backups.

Checklist:
- Capture only required tables via `table.include.list` and filter columns per connector capabilities.
- Apply column masking/tokenization/transformations at the right pipeline stage, **before leaving for other systems**.
- Never log raw `key`/`payload` containing PII when parsing fails.
- Restrict access to raw CDC events, dead-letter storage, and sample snapshots.
- Validate max JSON bytes, nesting depth, schema/field types, and destination allowlists.
- Use TLS for DB/brokers, a secret manager for credentials, and strict replication role controls.
- Review new columns during migrations: if a consumer serializes all of `after`, a newly added sensitive column can leak unintentionally.
- Enforce DELETE/tombstone policies for downstream caches, search indexes, and retention compliance.
- Log correlation IDs and source positions for debugging rather than persisting full payloads.

**Do not** use Java serialization on raw `ChangeEvent` objects in a persistent `MessageStore` just because they are Java objects; Spring Integration documentation explicitly notes that batch `List<ChangeEvent>` is **not serializable** by default.

## 33. Metrics, Backpressure, and Payload Size Control

| Metric | Used to Detect |
|---|---|
| `cdc_value_bytes` and `cdc_key_bytes` | Oversized events / JSON schema wrapper overhead |
| `cdc_envelope_parse_failures` | Format/schema drift |
| `cdc_unknown_op` | Truncates / logical messages / misrouting |
| `cdc_tombstones_received` | Delete compaction stream behavior |
| `cdc_snapshot_records` | Snapshot progress/anomalies |
| `cdc_capture_lag_ms` | Difference between source and processing timestamps when available |
| `cdc_messages_per_second` | CDC ingest throughput |
| `cdc_inbox_oldest_age` | Downstream backlog |
| `cdc_idempotent_replay_count` | Offset/ACK retries |
| `cdc_wal_retained_bytes` | WAL retained by PostgreSQL replication slot |
| `cdc_dispatch_queue_depth` | Async channel/worker overload |
| `cdc_quarantine_pending` | Poison events needing contract fixes |

If a sink slows down, do not push unbounded payload bytes into an unbounded executor. Use bounded concurrency and a **durable inbox/outbox**; pick retry/backoff policies to prevent OOM crashes and runaway WAL retention.

A 2MB payload can expand to 10MB+ when parsed into a JSON tree, copied across channels, wrapped in schemas, and logged. Set max payload sizes and memory budgets from measurements; explicitly flag when valid oversized events require blob/object-store references instead of raw JSON.

## 34. Layered Payload Error Handling

| Error | Correct Response | Mistake to Avoid |
|---|---|---|
| Not JSON bytes | Route per registered format/serializer | Casting everything to `byte[]` |
| Malformed JSON parse | Quarantine with source metadata, alert | Infinite retries |
| Missing `op` on row envelope | Report contract violation/SMT mismatch | Defaulting to CREATE |
| `before` null on UPDATE | Use `after`, or adjust replica identity | Dereferencing `before.status` |
| `after` null on DELETE | Extract key/`before` per contract | Parsing into a new-row DTO |
| Tombstone `Optional.empty()` | Route to compaction/tombstone policy | Running Jackson on `Optional` |
| `op=t`/`m` | Control handler or explicit reject | Reading `after.id` |
| Bad decimal/timestamp | Validate types/precision and reprocess after fix | Silently defaulting to 0 |
| Unknown destination | Quarantine/reject via allowlist | Concatenating into SQL table name |
| Schema column change | Version migration/dual-read | Treating missing fields as empty strings |
| Downstream DB outage | Retry transactional unit with backoff | Dropping the event after logging |
| Kafka ACK timeout | Outbox/remote deduplication | Assuming error = never sent |

Every `catch (Exception)` in a synchronous handler must honor the failure policy: swallowing an exception after writing partial DB state can commit unwanted changes. Even if you throw the exception, verify **redelivery and dead-letter persistence** under your exact adapter/Engine version's retry and offset-advancement policy.

## 35. Unit Testing the Parser Across Payload Shapes

                .getBytes(StandardCharsets.UTF_8);

        assertThrows(IllegalArgumentException.class,
            () -> decoder.decode(invalid));
    }
}
~~~

This is a **parser unit test**; it does not prove that a real PostgreSQL Debezium connector emits that exact format. In integration tests, capture golden events from your compatible Debezium connector and test with the exact schema wrapper and SMT configuration you deploy.

### 35.1. Testing the Key Decoder and Tombstones

Also test:
1. Key header bytes `{"schema":{...},"payload":{"id":101}}` → `id=101`.
2. Key header bytes `{"id":101}` → `id=101`.
3. Absent key header on TRUNCATE → accepted by the operation route.
4. Tombstone value `Optional.empty()` → handler calls `onTombstone`, **not** `envelopes.decode`.
5. A `String` payload when the handler only supports JSON bytes → reports unsupported type.
6. `enableBatch(true)` → `List<ChangeEvent>` payload requires a batch-specific handler.

Do not test by constructing `new Message<>(null)`: Spring Messaging rejects ordinary null payloads. Use the actual payload types produced by the adapter and set message headers accurately.

## 36. Integration Testing PostgreSQL CDC and Schema Evolution

Test end-to-end against PostgreSQL with logical replication and a compatible Debezium connector (Testcontainers or a test DB of the same vendor). Configuration:
- `orders` table with a PK and the `REPLICA IDENTITY` under test.
- Connector `table.include.list=public.orders`, `plugin.name=pgoutput`, dedicated test publication/slot.
- File/JDBC offset backing store using an isolated directory/location.
- Spring Integration inbound source with `enableBatch(false)`; test handler captures bytes/headers.
- At most **one Engine** on the same slot/offset during tests, unless intentionally testing collisions.
- Do not use fixed sleeps; use `CountDownLatch`/await conditions with timeouts.

Matrix:

| Operation | What to Assert |
|---|---|
| Initial snapshot | `op=r` and `after.id` match existing rows |
| INSERT | `op=c`, `key.id` and `after.id` match |
| UPDATE | `op=u`, `before` reflects replica identity, updated `after` |
| DELETE | `op=d` and null `after`; separate tombstone if enabled |
| TRUNCATE | If captured and supported, `op=t` without assuming key/after |
| PK update | Delete/tombstone/create sequence per connector behavior |
| Wrapper on/off | Parser handles both configured modes |
| Schema add column | Consumer ignores unused new fields |
| Rename column | Contract test fails intentionally / dual-read works |
| DECIMAL/TIMESTAMP | Scale, precision, and timezone are accurate |
| Batch mode | Payload is a list of raw events, not cast to `byte[]` |
| Offset restart | Replay possible; projection remains idempotent |
| Kafka/JMS sink outage | Retries/reconciliation do not lose durable work |
| Oversized event | Byte limit enforced and quarantined per policy |
| Unknown destination | No dynamic SQL generated |
| Engine slot collision | Prevent two producers accidentally sharing one slot |

**Distinguish parser tests from delivery tests:** unit tests verify syntax and normalization logic; integration tests verify real representations; fault-injection tests verify offsets, transactions, and replays. Only with evidence across all three can you claim the corresponding delivery guarantees.

## 37. Practical Checklist for Change Event Payloads

When designing a Spring Integration consumer receiving Debezium CDC, answer clearly:

1. **Source connector:** PostgreSQL, MySQL, SQL Server, Oracle, or MongoDB? `source` metadata differs.
2. **Serialization:** JSON `byte[]`, JSON `String`, Avro, Protobuf, or `SourceRecord`? A matching decoder is required.
3. **Schema wrapper:** Does `schema/payload` exist? Which versions and SMTs apply?
4. **Key:** How is `DebeziumHeaders.KEY` formatted? Does the table have a PK?
5. **Destination:** How is `DebeziumHeaders.DESTINATION` allowlisted and routed?
6. **Operations:** Are `r/c/u/d/t/m`, tombstones, and transaction control events handled?
7. **Before image:** Which columns does the DB emit? Is `REPLICA IDENTITY`/binlog row image sufficient?
8. **After image:** When can it be null/missing? Does the consumer validate fields?
9. **Timestamps:** Are units (ms/us/ns) and time source fixed?
10. **Data types:** Are DECIMAL/UUID/TIMESTAMP/BINARY/JSON parsed with exact precision?
11. **Schema evolution:** Are there golden tests for added/changed fields and connector upgrades?
12. **SMTs:** Do unwrap, masking, routing, or outbox transforms run before the adapter?
13. **Transactions:** Is `transaction` metadata enabled and scoped properly?
14. **Ordering:** Is there versioning or partition ownership preventing old events from overwriting new ones?
15. **Deduplication:** Does the business event ID or source position tuple provide sufficient uniqueness?
16. **Delivery:** How do callbacks/offset flushes relate to inbox/outbox COMMITs and broker ACKs?
17. **Backpressure:** Are payloads/queues bounded, and where are events held if the sink slows down?
18. **Security:** Are PII fields in before/after filtered, masked, logged safely, and subject to retention?
19. **Observability:** Are parse errors, tombstones, lag, slot WAL, and redeliveries measured?
20. **Recovery:** Is there a runbook for lost offsets, schema drift, truncates, or dropped source slots?

If any item in **serialization, key, operation, or idempotency** is undefined, do not consider the pipeline safe merely because the handler receives `Message<?>`.

## 38. Hands-On Exercises

18. Parse large decimals using `BigDecimal`; compare against `double` and demonstrate precision loss.
19. Parse microsecond timestamps using `Instant.ofEpochSecond`, avoiding unit bugs with `ofEpochMilli`.
20. Create a schema migration adding a column and verify the consumer ignores unused fields.
21. Create a column-rename migration and add a golden test confirming contract breakage is detected.
22. Enable transaction metadata and observe `transaction.total_order` and transaction boundary records.

24. Create an inbox table with a unique business `event_id`, simulate offset replay, and verify no duplicate business effects.

26. Attach a Kafka/JMS outbox publisher; simulate a successful broker ACK followed by an app crash before marking `published`.
27. Enable `enableBatch(true)` on a separate test flow and verify `List<ChangeEvent>` is not `List<byte[]>`.
28. Write a batch transformer converting raw change events into serializable DTOs before a persistent store.
29. Test the `ExtractNewRecordState` unwrap SMT and confirm the original envelope parser no longer applies and a new contract must be chosen.
30. Write integration tests with PostgreSQL Testcontainers with logical replication, verifying `r/c/u/d` and tombstones.
31. Feed malformed JSON, an event missing `op`, and a mismatched converter format; distinguish quarantine from transient retry.
32. Add payload size / JSON depth limits and parse-failure metrics.
33. Measure `source.ts_ms` vs. `ts_ms` lag and compare with inbox COMMIT latency to avoid confusing latency types.
34. Run two pods with `ExecutorChannel` and Kafka partitions and check per-aggregate ordering.
35. Build a dashboard for CDC rate, payload bytes, tombstones, parse failures, inbox backlog, and slot WAL retention.
36. Write a recovery runbook for schema drift, lost offset files, or an invalid PostgreSQL replication slot.

**Capstone scenario:** an application receives Debezium CDC for orders via Spring Integration. It enables `enableBatch(false)`, maps the JSON key into a header, transforms the value byte-array into a read model, and sends to Kafka. A DBA alters `REPLICA IDENTITY`, a transaction changes a primary key and the source emits DELETE + tombstone + CREATE. After Kafka receives CREATE, the application crashes before saving the offset; a new pod re-reads the old event while `after.total_cents` has just been renamed. Lay out the **parser contract, versioning/ordering, tombstone handling, schema migration, durable inbox/outbox, offset replay, idempotency, and tests** so the read model is neither wrongly deleted nor rolled back to stale state.

> **Key Takeaway:** A **Debezium change event payload** is more than just JSON `after`. Spring Integration typically receives **value bytes** in `Message.payload`, with **record key** and **destination** in headers; the value may include a `schema/payload` wrapper and an envelope containing `before/after/source/op/ts_ms/transaction`. Distinguish **snapshot `r`, CREATE `c`, UPDATE `u`, DELETE `d`, empty-value tombstones, TRUNCATE `t`**, and control records. Normalization must check types/shapes, schema evolution, precision, keys, ordering, and idempotency; Debezium offsets, JDBC transactions, and broker ACKs are separate boundaries that do not automatically guarantee exactly-once business effects.
