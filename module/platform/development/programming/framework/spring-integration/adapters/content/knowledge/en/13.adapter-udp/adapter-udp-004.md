# UDP message headers and source addresses in Spring Integration

## Learning objectives

After this lesson, you will be able to:

- Distinguish between the **UDP payload**, **network-layer source address/port**, and **Spring Integration `Message` headers**.
- Properly read `ip_address`, `ip_port`, `ip_hostname`, and `ip_packetAddress` headers from an inbound UDP message.
- Use `IpHeaders` instead of scattering string header names; understand the meaning, data types, and differences between UDP and TCP headers.
- Configure a UDP receiving adapter, inspect the source address inside a service activator, and test with a real client.
- Know when `ip_packetAddress` can be used to **send a reply datagram back to the sender** via an outbound adapter.
- Analyze the impact of NAT, DNS, IP spoofing, datagram limits, and socket lifecycle on using source addresses.

This lesson belongs to the **Adapter UDP** chapter of the **SPRING_INTEGRATION_ADAPTERS** module. This module focuses on connecting external systems into Spring Integration using inbound/outbound adapters, gateways, pollers, and `MessageChannel`, applied to files, SFTP, HTTP, JMS, AMQP, Kafka, and databases. **UDP message headers and source addresses** are an important part of the *message contract*: handlers receive both business data and metadata about the datagram that entered the system.

## 1. The problem: identical data from multiple devices

A collector opens UDP port `12004` to receive telemetry:

~~~text
sensor=node-7;tempC=26.5
~~~

Two senders might send the exact same content:

- Device A sends from `192.0.2.31:51234`.
- Device B sends from `192.0.2.32:60127`.

If the handler only reads the payload string, both datagrams look identical. However, the UDP adapter knows the **source address observed on the socket** and can attach this information to the **message headers** so the handler can diagnose issues, record metrics, apply network controls, or route replies.

~~~mermaid
flowchart LR
    A["Device A\n192.0.2.31:51234"] -->|"UDP: sensor=node-7..."| S["UDP inbound socket\n:12004"]
    B["Device B\n192.0.2.32:60127"] -->|"UDP: sensor=node-7..."| S
    S --> M["DatagramPacketMessageMapper"]
    M --> I["Spring Integration Message\npayload = byte[]\nheaders = ip_address / ip_port / ip_packetAddress"]
    I --> C["MessageChannel"]
    C --> H["Validate / Service Activator"]
~~~

**Key point:** source information in headers is derived by the receiver from the datagram/socket. The sender **does not send a JSON header named `ip_address`** by default, and a datagram's source address does not prove a device's business identity.

The `192.0.2.x` addresses in this lesson are documentation-range examples. When testing in practice, use your deployment environment's addresses or `127.0.0.1`.

## 2. Three data layers not to confuse

| Concept | Example | Where is it produced? | Meaning |
|---|---|---|---|
| **UDP payload** | UTF-8 bytes of `sensor=node-7;tempC=26.5` | Sender application | Data that both parties agree to transmit. |
| **Source UDP/IP endpoint** | `192.0.2.31:51234` | Information on the datagram/socket delivered by the network | Source address and port *observed* by the receiver. |
| **Spring Message headers** | `ip_address`, `ip_port`, `id` | Created by the framework when mapping a datagram to a `Message` | Internal metadata for processing, routing, or tracking. |

A `Message<byte[]>` in Spring Integration can be visualized as:

~~~text
Message
├── payload: byte[] -> "sensor=node-7;tempC=26.5"
└── headers:
    ├── ip_address: "192.0.2.31"
    ├── ip_port: 51234
    ├── ip_hostname: "192.0.2.31"
    ├── ip_packetAddress: InetSocketAddress(192.0.2.31, 51234)
    ├── id: UUID generated by Spring
    └── timestamp: Message creation timestamp
~~~

The values above are **illustrative** for unicast UDP with `lookupHost=false`. The actual header set depends on the adapter, version, configuration, and processing path. `id` and `timestamp` are standard Spring Messaging metadata; they are not the `sequence` or business timestamp generated by the device.

**Do not assume all message headers are serialized over the network:** with a standard UDP outbound adapter, the payload is encoded as bytes in the datagram; remaining Spring Integration headers are internal data unless you explicitly design a protocol to transmit them.

## 3. UDP headers you should know

The `org.springframework.integration.ip.IpHeaders` class provides the official header names. Using these constants avoids typos when calling `message.getHeaders().get(...)`.

| Actual header name | Constant in `IpHeaders` | Meaning | Typical data type |
|---|---|---|---|
| `ip_address` | `IpHeaders.IP_ADDRESS` | Source IP address of the received UDP packet | `String` |
| `ip_port` | `IpHeaders.PORT` | **Remote UDP source port**, not the server's listening port | `Integer` |
| `ip_hostname` | `IpHeaders.HOSTNAME` | Source hostname, or the IP string when reverse lookup is disabled | `String` |
| `ip_packetAddress` | `IpHeaders.PACKET_ADDRESS` | Full source socket address obtained from `DatagramPacket.getSocketAddress()` | `SocketAddress`, typically `InetSocketAddress` |
| `ip_localInetAddress` | `IpHeaders.LOCAL_ADDRESS` | Local address bound to the socket/endpoint when available in the corresponding context | `InetAddress`, not always present |
| `ip_ackTo` | `IpHeaders.ACK_ADDRESS` | Address used for Spring Integration UDP's application-level acknowledgment mechanism | Depends on ACK mechanism |
| `ip_ackId` | `IpHeaders.ACK_ID` | Correlation ID for acknowledgments in the UDP ACK mechanism | Depends on ACK mechanism |

**Clearly distinguish easily confused headers:**

- `IpHeaders.PORT` is the **UDP** source port. `IpHeaders.REMOTE_PORT` corresponds to `ip_tcp_remotePort` for **TCP**; do not use the TCP constant to read the source port of a UDP datagram.
- `IpHeaders.PACKET_ADDRESS` holds the **IP + port pair**, which can be passed directly as the target of a UDP outbound handler with `destination-expression`.
- `ip_address` and `ip_hostname` may match when host lookup is disabled, yet they represent two distinct concepts.
- `ip_ackTo` and `ip_ackId` are not present on every datagram; they only apply when endpoints use a compatible ACK protocol.
- `MessageHeaders.REPLY_CHANNEL` and `MessageHeaders.ERROR_CHANNEL` (if present) belong to the internal messaging model; they are not equivalent to a **UDP source address**.

Because headers depend on context, check for null and verify types before using them rather than blindly casting values upon receiving a message.

## 4. How does the UDP inbound adapter populate these headers?

A simple unicast receiving flow consists of:

~~~mermaid
flowchart LR
    D["UDP datagram"] --> R["UnicastReceivingChannelAdapter"]
    R --> P["DatagramPacketMessageMapper"]
    P --> M["Message<byte[]> with IP headers"]
    M --> C["MessageChannel"]
    C --> H["Business handler"]
~~~

In Spring Integration, **`DatagramPacketMessageMapper`** maps a received `DatagramPacket` to a `Message<byte[]>`. `ip_packetAddress` reflects the result of `DatagramPacket.getSocketAddress()`; from it, the datagram's source address and port are also extracted.

This data is **supplied by the network and socket**, not a JSON field self-reported by the device. If the payload contains `sensorId`, that is a **business** identifier, whereas `ip_address` is the **network address observed at the receiver**. Both identifiers can be cross-checked, but should not be treated as equivalent.

### 4.1. Source port differs from destination port

Suppose a client creates a UDP socket assigned ephemeral port `51234` by the OS and sends to server `127.0.0.1:12004`:

~~~text
Client socket: 127.0.0.1:51234
              UDP send
Server socket: 127.0.0.1:12004

Headers on received message:
  ip_address        = "127.0.0.1"
  ip_port           = 51234
  ip_packetAddress  = 127.0.0.1:51234
~~~

Port `12004` is the **port the server binds to listen**. It is not the `ip_port` value of the received datagram. If the client closes the socket and opens a new one, the source port may change.

### 4.2. Hostname lookup and DNS

By default, the UDP inbound adapter **does not perform reverse DNS lookup** (`lookup-host=false`). In that mode `ip_hostname` usually holds the IP string itself, avoiding DNS wait times in environments such as Docker or internal networks without PTR records.

When `lookup-host=true` is enabled, the framework may look up the source hostname via DNS. Doing so has several consequences:

- Reverse DNS can be slow, missing, or return unexpected values.
- A hostname is not an identity certificate and is insufficient to authenticate a device.
- Recording metrics keyed by hostname can increase cardinality or complicate correlation when DNS changes.

Enable reverse DNS only when there is a clear requirement, a reliable DNS system, and measured performance impact. For reply routing, **`ip_packetAddress`** is generally preferable to a reverse-looked-up hostname.

## 5. Java example: receiving UDP and reading headers

### 5.1. Dependencies

In a Spring Boot project with dependency management, declare the integration libraries:

~~~xml
<!-- pom.xml: inside <dependencies> -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-integration</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.integration</groupId>
    <artifactId>spring-integration-ip</artifactId>
</dependency>
~~~

### 5.2. Declaring the inbound flow and channel

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.annotation.EnableIntegration;
import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.integration.ip.dsl.Udp;
import org.springframework.messaging.MessageChannel;

@Configuration
@EnableIntegration
public class UdpHeaderFlowConfig {

    @Bean("udpRawInput")
    public MessageChannel udpRawInput() {
        return new DirectChannel();
    }

    @Bean
    public IntegrationFlow udpInboundFlow() {
        return IntegrationFlow.from(Udp.inboundAdapter(12004))
                .channel("udpRawInput")
                .get();
    }
}
~~~

`Udp.inboundAdapter(12004)` listens for unicast UDP datagrams; `channel("udpRawInput")` sends messages to an internal channel. This endpoint **receives on socket events**, so no poller needs to be configured to read individual datagrams.

### 5.3. Service Activator inspecting source headers

~~~java
import java.net.InetSocketAddress;
import java.net.SocketAddress;
import java.nio.charset.StandardCharsets;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.integration.annotation.ServiceActivator;
import org.springframework.integration.ip.IpHeaders;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.stereotype.Component;

@Component
public class UdpHeaderInspector {

    private static final Logger log =
            LoggerFactory.getLogger(UdpHeaderInspector.class);

    @ServiceActivator(inputChannel = "udpRawInput")
    public void inspect(Message<byte[]> message) {
        byte[] bytes = message.getPayload();
        if (bytes.length == 0 || bytes.length > 512) {
            log.warn("Discard UDP datagram of size {}", bytes.length);
            return;
        }

        MessageHeaders headers = message.getHeaders();

        String sourceIp = headers.get(IpHeaders.IP_ADDRESS, String.class);
        Integer sourcePort = headers.get(IpHeaders.PORT, Integer.class);
        String sourceHost = headers.get(IpHeaders.HOSTNAME, String.class);
        SocketAddress sourceAddress =
                headers.get(IpHeaders.PACKET_ADDRESS, SocketAddress.class);

        if (sourceIp == null || sourcePort == null
                || !(sourceAddress instanceof InetSocketAddress)) {
            log.warn("Discard message without usable UDP source metadata");
            return;
        }

        // For illustration only; production must validate encoding and schema.
        String payload = new String(bytes, StandardCharsets.UTF_8);

        log.info("UDP from {}:{} (host={}, packetAddress={})",
                sourceIp, sourcePort, sourceHost, sourceAddress);
        log.info("UDP sample payload={}", payload);
    }
}
~~~

Sample output when sent from a client on the receiving host:

~~~text
UDP from 127.0.0.1:51234 (host=127.0.0.1, packetAddress=/127.0.0.1:51234)
UDP sample payload=sensor=node-7;tempC=26.5
~~~

The source port may differ from `51234`; the string representation of `InetSocketAddress` can also vary depending on Java version and environment.

**Do not treat logging code as a production parser:** UDP data must be validated for UTF-8 encoding, size limits, version, schema, and business constraints. Printing payloads unchecked can expose sensitive data or formatting-breaking characters in logs. In production, prefer logging normalized fields and correlation IDs with appropriate sampling.

### 5.4. Reading headers in SpEL

Alongside Java, headers can be read from Spring Integration expressions, for example:

~~~text
headers['ip_address']
headers['ip_port']
headers['ip_packetAddress']
~~~

Use expressions when routing via a router or specifying a dynamic outbound adapter target; use `IpHeaders` in Java code so your IDE checks constant names. Both read **message headers**, not the payload contents directly.

## 6. Testing to confirm the real source address

Start the Spring Boot application containing the two classes above. From PowerShell on **the same machine**, create a `UdpClient` and let the OS assign an ephemeral source port:

~~~powershell
$client = [System.Net.Sockets.UdpClient]::new(0)
try {
    $local = [System.Net.IPEndPoint]$client.Client.LocalEndPoint
    Write-Host "UDP source port: $($local.Port)"

    $text = "sensor=node-7;tempC=26.5"
    $bytes = [System.Text.Encoding]::UTF8.GetBytes($text)

    [void]$client.Send($bytes, $bytes.Length, "127.0.0.1", 12004)
}
finally {
    $client.Dispose()
}
~~~

Once `udpInboundFlow` is listening on `12004`, compare the **UDP source port** printed by the client against `ip_port` in `UdpHeaderInspector`'s log. Both numbers must match in this loopback test; `sourceIp` is expected to be `127.0.0.1`.

Try running the PowerShell snippet several times. You may see the source port change, while the server's destination port remains `12004`.

| Action | What to observe |
|---|---|
| Send from a client bound to an ephemeral port | `ip_port` is the client's chosen port, not 12004 |
| Keep one `UdpClient` and send multiple datagrams | Source port usually remains stable for that socket's lifetime |
| Close and create a new client | Source port may change |
| Send from another machine | `ip_address` is typically the source IP seen by the network, possibly translated by NAT |
| Send oversized data | Must handle receive buffer limits; datagram may be lost or truncated |

A successful send on the client **does not prove** the Spring Integration handler executed. If there is no log, verify the server is bound to the right UDP port, check firewalls, container networking, and confirm `udpRawInput` has a subscriber.

## 7. Using the source address to send a UDP reply

### 7.1. Why source IP alone is not enough

A datagram from `203.0.113.10:53021` cannot be replied to accurately if the handler only saves `203.0.113.10` and guesses the port. The sender may use an ephemeral port, and a device behind NAT may be mapped to a different port.

The **`ip_packetAddress`** header holds the `IP:port` pair from `DatagramPacket.getSocketAddress()`, making it suitable as a reply target *within the same exchange context*.

~~~mermaid
sequenceDiagram
    participant C as UDP client
    participant I as Inbound adapter
    participant H as Message handler
    participant O as Outbound adapter
    C->>I: Datagram from source IP:port
    I->>H: Message + ip_packetAddress
    H->>O: ACK payload + preserve source headers
    O-->>C: Datagram sent back to ip_packetAddress
~~~

This is an application-built reply workflow. **The UDP inbound adapter does not automatically reply to every datagram.**

### 7.2. Java DSL example: replying to the exact sender

The Spring Integration UDP outbound handler supports **`destination-expression`** to determine the target dynamically from the message. Additionally, **`socket-expression`** allows reusing the inbound adapter's socket to send replies from the same server port that received the packet, which helps when clients sit behind NAT.

Example of a minimal UDP echo/ACK on **a separate port, 12005**:

~~~java
import java.nio.charset.StandardCharsets;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.integration.ip.dsl.Udp;

@Configuration
public class UdpReplyFlowConfig {

    @Bean
    public IntegrationFlow udpReplyFlow() {
        return IntegrationFlow
                .from(Udp.inboundAdapter(12005).id("udpReplyIn"))
                .<byte[], byte[]>transform(
                        bytes -> "ACK".getBytes(StandardCharsets.UTF_8))
                .handle(
                        Udp.outboundAdapter(
                                "headers['ip_packetAddress']")
                           .socketExpression("@udpReplyIn.socket"))
                .get();
    }
}
~~~

How it works:

1. The inbound adapter receives a datagram on **12005** and creates a message containing `ip_packetAddress`.
2. The transformer replaces the payload with `ACK`; standard Spring Integration transformers **preserve incoming headers** when constructing the output message.
3. `Udp.outboundAdapter("headers['ip_packetAddress']")` resolves the destination to the sender's socket address.
4. `.socketExpression("@udpReplyIn.socket")` reuses the receiving adapter's socket so the reply datagram leaves from **port 12005**.

**Important condition:** if a step in the flow builds a brand-new `Message`, it must **preserve `IpHeaders.PACKET_ADDRESS`** if downstream steps need to reply. Do not replace it with a payload-only message and inadvertently drop routing metadata.

`socket-expression` cannot be combined with the **multicast** and **acknowledge** options of the UDP outbound adapter. If you need a dedicated ACK mechanism, define an explicit contract and compatible configuration on both sides.

### 7.3. Testing ACK with PowerShell

Run the application with `udpReplyFlow`. In PowerShell, send a datagram to `127.0.0.1:12005` and wait for the ACK on **the same `UdpClient`**:

~~~powershell
$client = [System.Net.Sockets.UdpClient]::new(0)
$client.Client.ReceiveTimeout = 3000

try {
    $bytes = [System.Text.Encoding]::UTF8.GetBytes("ping")
    [void]$client.Send($bytes, $bytes.Length, "127.0.0.1", 12005)

    $remote = [System.Net.IPEndPoint]::new(
        [System.Net.IPAddress]::Any, 0
    )
    $reply = $client.Receive([ref]$remote)

    Write-Host "Response from $remote"
    Write-Host ([System.Text.Encoding]::UTF8.GetString($reply))
}
finally {
    $client.Dispose()
}
~~~

You should see **`ACK`** from port `12005`. If no reply arrives within 3 seconds, `Receive` throws a timeout exception. Causes may include the server not listening, network/firewall blocking, or lost headers/destination in the flow. Receiving an ACK proves *a reply datagram* reached the client; **it does not prove a business transaction was committed**.

This is a localhost demonstration. **Never deploy an unrestricted public UDP echo**: UDP source addresses can be spoofed, turning the service into a packet reflector. Restrict allowed source networks, rate-limit, bound reply sizes, authenticate per contract, and control flow before exposing a port externally.

## 8. Source addresses under NAT and multiple network interfaces

### 8.1. NAT can alter what the receiver observes

Suppose a sender on a private network has address:

~~~text
Internal sender: 10.0.1.5:53021
NAT gateway:     198.51.100.8:62044
External server: 203.0.113.20:12004
~~~

When the datagram passes through NAT, the external server may see:

~~~text
ip_address       = "198.51.100.8"
ip_port          = 62044
ip_packetAddress = 198.51.100.8:62044
~~~

That is the **network address observed by the server**, not the sender's private IP. The port mapping may change after a timeout or when the sender opens a new socket. Saving `ip_packetAddress` and replying minutes later risks hitting an expired mapping.

Replying from the **same socket/port** often improves compatibility with certain NAT types, yet you must still test actual NAT/firewall policies; there is no guarantee replies always reach the device.

### 8.2. Multi-homed hosts and local addresses

A server may have multiple interfaces: Ethernet, Wi-Fi, VPN, container networks. The **source** headers identify the remote endpoint; they do not necessarily tell you which NIC the datagram arrived on.

To control which address the inbound adapter binds to, configure an appropriate **`local-address`** and verify routing/network policies. Do not assume `ip_localInetAddress` is always populated or sufficient to identify the interface in every UDP scenario; verify on your specific version and topology.

### 8.3. When should source address be used as a key?

**Do not use `IP:port` as a long-term device identity.** DHCP, NAT, mobile networks, VPNs, container lifecycles, and ephemeral ports can change addresses. One device may change endpoints, and multiple devices may share a single public IP.

If you need to identify sensors accurately, the payload should include `deviceId`, version, timestamp/sequence, and appropriate authentication. Network source info can then be stored as observability metadata, useful for anomaly detection or debugging.

## 9. Structuring the message contract to retain critical metadata

A safe design separates:

| Data group | Examples | Purpose |
|---|---|---|
| **Business payload** | `deviceId`, `seq`, `tempC` | Schema validation, DB persistence, computation |
| **Network metadata** | `ip_address`, `ip_port`, `ip_packetAddress` | Diagnostics, short-lived reply routing |
| **Spring Messaging metadata** | `id`, `timestamp`, `correlationId` if present | Internal flow tracing |
| **Application context** | Authenticated device ID, tenant, trace ID | Authorization and observability once verified by the system |

When forwarding to JMS, AMQP, Kafka, HTTP, or storing in a database, decide **which fields belong to business data** and **which are merely ingress processing metadata**. Do not blindly copy all headers into an externally emitted event: doing so can leak source IPs, internal topology details, or non-serializable Java objects.

When using transformers/filters/routers in Spring Integration, verify that steps preserve required headers. For instance, an outbound adapter using `destination-expression="headers['ip_packetAddress']"` will fail if that header is stripped before reaching the endpoint.

### Example preserving headers when creating a new Message

~~~java
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

public Message<byte[]> createReply(
        Message<byte[]> incoming, byte[] replyBytes) {

    return MessageBuilder.withPayload(replyBytes)
            .copyHeaders(incoming.getHeaders())
            .build();
}
~~~

This example retains headers so an outbound endpoint can read `IpHeaders.PACKET_ADDRESS`. In practice, forward only **permitted and necessary metadata**. If receiving messages from another untrusted source, sanitize incoming headers instead of letting any caller dictate arbitrary target addresses.

## 10. Distinguishing Spring Integration ACK from custom replies

Spring Integration UDP has options for **application-level acknowledgment**. When using this mechanism, payload/framing may carry ACK metadata; headers such as `ip_ackTo` and `ip_ackId` relate to identifying the ACK destination and correlating responses.

| Mechanism | How does it arise? | Meaning |
|---|---|---|
| **UDP source info** | Inbound adapter receives a datagram | Reveals the IP/port observed by the network |
| **`ip_packetAddress`** | Mapper fills in the source socket address | Can be used to send a datagram back to the sender |
| **Spring Integration UDP ACK** | Both endpoints enable and speak the same ACK protocol | Confirmation under the adapter's technical contract |
| **Business ACK** | Receiver defines when to send it | Can confirm parsing, durable persistence, or successful processing per contract |
| **Internal `replyChannel`** | Used by Spring Messaging/gateways to return results inside the app | Not automatically a UDP destination address |

For critical flows, clearly distinguish three states: **sent**, **received by receiver**, and **business transaction committed**. A technical ACK does not automatically equal `database transaction committed`. Retries after timeouts must carry an ID/sequence and be idempotent because the receiver may already have processed the earlier packet.

## 11. Common pitfalls

| Symptom | Common misconception | How to fix |
|---|---|---|
| Logs show `ip_port=51234` while server listens on 12004 | Assuming `ip_port` is the server port | It is the sender's **source port**; keep the listening port in server config |
| No real hostname appears | Thinking `ip_hostname` is broken | Default `lookupHost=false` returns the IP string; reverse DNS is optional |
| Reading `ip_tcp_remotePort` returns null | Using a TCP header for UDP | Use `IpHeaders.PORT` |
| Cannot reply to client | Saving only IP without source port, losing headers, or using wrong local socket | Preserve `ip_packetAddress`, check destination-expression/socket-expression |
| Response goes to wrong device behind NAT | Using an expired source address or replay | Do not treat NAT mappings as permanent; reply within active exchange |
| Using `ip_address` for access control | Source IP can be spoofed, NATed, or untrusted | Authenticate messages/devices using a proper security protocol |
| UDP sent but no handler logs | Dropped packet, wrong bind, firewall, or unstarted adapter | Check packet captures, lifecycle, and channel subscriptions |
| `ip_packetAddress` missing after transform | Creating a new message without copying headers | Inspect each step in the integration flow |
| Publishing all headers to a broker | Leaking IPs or sending unsuitable Java objects | Normalize an event DTO and keep only required metadata |
| `ip_ackId` header is missing | Not using a compatible UDP ACK protocol | Do not assume ACK headers exist on every packet |

When debugging, follow the sequence **packet reaches host → inbound adapter turns datagram into message → header mapper attaches metadata → channel dispatches → handler reads headers → outbound sends reply (if any)**. Verify each step with rate-limited logs, metrics, and packet captures instead of guessing from a single sender log line.

## 12. Testing suited to each layer

| Layer | How to test | What it verifies |
|---|---|---|
| Handler unit test | Construct `Message<byte[]>` with `IpHeaders` explicitly set | Handler handles null headers, wrong types, and byte limits properly |
| UDP integration test | Send a real datagram to a test port | Framework maps source IP/port into headers |
| Echo/reply test | Send and wait for ACK using a socket client | Reply destination correctly uses `ip_packetAddress` and source port |
| NAT/network test | Sender in a different network/subnet/container | Observed IP/port at the receiver and real reply reachability |
| Security test | Malformed datagrams, packet floods, simulated schema errors | Does not reflect arbitrary payloads or exhaust resources |

To test exact source handling in a unit test, you can build a mock message:

~~~java
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

import org.springframework.integration.ip.IpHeaders;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

Message<byte[]> sample = MessageBuilder
        .withPayload("sensor=node-7;tempC=26.5"
                .getBytes(StandardCharsets.UTF_8))
        .setHeader(IpHeaders.IP_ADDRESS, "127.0.0.1")
        .setHeader(IpHeaders.PORT, 53021)
        .setHeader(IpHeaders.PACKET_ADDRESS,
                new InetSocketAddress("127.0.0.1", 53021))
        .build();
~~~

Hand-built messages help test service logic, yet **they do not prove `DatagramPacketMessageMapper` actually extracts metadata as expected**. To verify adapter mapping, test over a real socket and compare the client's source port with server logs/headers.

## 13. Security and observability when using IP headers

The network-layer UDP source address is **observed information**, not a trusted identity. Datagrams can be crafted with spoofed source addresses on certain network paths, and NAT/proxies can alter the address seen by the receiver. Therefore:

1. **Do not authenticate or authorize** solely by `ip_address` when the source is not fully trusted.
2. **Do not send UDP responses unconditionally to arbitrary `ip_packetAddress` values** on public ports; mitigate UDP reflection/amplification with rate limits, allowlists, small replies, and authentication/nonces where appropriate.
3. **Keep network identity separate from device identity**. Device ID, tenant, and permissions must be verified per application policy.
4. **Bound payloads and logs**; do not record raw data or make every IP address a metric label if there are large numbers of IPs.
5. **Monitor socket lifecycle and infrastructure**: bound ports, firewalls, NAT timeouts, listener health, and receive/error/ACK counts; UDP has no persistent connection signal like TCP.
6. **If payload confidentiality is required**, use appropriate application-layer encryption/authentication or a protected transport/network; plain UDP does not provide TLS.

A minimal metric set might include `udp_datagrams_received_total`, `udp_payload_invalid_total`, `udp_handler_failure_total`, `udp_reply_attempt_total`, and `udp_reply_error_total`. Never use `udp_reply_attempt_total` alone to claim the sender received the reply.

## 14. Extended practice exercise

Build a telemetry receiver on `12004` and a lab-only echo server on `12005`.

**Part A — Identifying the source:**

1. Send three datagrams from **the same** `UdpClient` and record `ip_address`, `ip_port`, and `ip_packetAddress`.
2. Close the socket, open a new `UdpClient`, and send again. Observe whether the source port changes.

## Conclusion

**UDP message headers** let Spring Integration combine received payloads with information about the network endpoint that sent the datagram. In basic unicast processing, **`ip_address`**, **`ip_port`**, **`ip_hostname`**, and especially **`ip_packetAddress`** allow inspecting the sender source and, when configured appropriately, routing replies back to the sender.

Use them strictly according to their meaning as **network metadata**: distinguish source IP/port from the listening port, preserve required headers across transformers or routers, account for reverse DNS/NAT, and never use source addresses in place of device authentication. From this UDP boundary, subsequent flows in **SPRING_INTEGRATION_ADAPTERS** can process data through `MessageChannel` and connect to databases, HTTP, SFTP, JMS, AMQP, Kafka, or other systems according to the defined message contract.
