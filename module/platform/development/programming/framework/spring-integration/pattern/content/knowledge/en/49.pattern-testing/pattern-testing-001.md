# Testing Each Pattern with Minimal Messages

## 1. Objectives and Scope

Enterprise Integration Patterns (EIP) decouple components through messages and communication channels. In Spring Integration, a flow can pass through a **Router**, **Filter**, **Transformer**, **Splitter**, **Aggregator**, **Gateway**, **retry** mechanisms, and an **error channel**. A flow may work during manual testing yet still fail on a rare branch, drop headers, or misgroup messages belonging to two different requests.

This lesson belongs to the **Pattern Testing** chapter of the **SPRING_INTEGRATION_PATTERN** module. The goal is to learn how to test each pattern using the **smallest set of messages that still proves the expected behavior**, and then compose checks to keep the message flow loosely coupled, extensible, and observable:

- Define the input, output, and side-effect contract of a pattern.
- Construct messages with only the required payload and headers; no broker, HTTP server, or database needs to be started when testing internal logic.
- Test the success branch, discarded branch, error branch, and message routing path.
- Verify message count, ordering when guaranteed, correlation, retry behavior, and group completion timing.
- Keep tests independent, repeatable, and failing with messages clear enough to pinpoint the faulty pattern.

**Minimal messages** do not necessarily mean *a single message*. A Router usually needs one message per branch; a Splitter needs a message with at least two elements to prove splitting occurs; an Aggregator needs enough messages in a group to test the release condition. To prove that two groups are not mixed together, at least two correlation IDs are required.

## 2. Testing Contract: What to Observe in Each Pattern?

A Spring Integration message typically consists of two parts:

~~~text
Message<T>
├── payload: business data (e.g., "order-1", 3, List<String>)
└── headers: routing, correlation, and reply metadata
    ├── id, timestamp       (generated by the framework)
    ├── kind, tenantId      (business headers if required by the flow)
    ├── correlationId        (groups related messages)
    ├── sequenceNumber       (position within the group)
    ├── sequenceSize         (expected number of elements)
    ├── replyChannel         (destination for replies, when needed)
    └── errorChannel         (destination for error handling, when needed)
~~~

Do not put every header into every test. Provide only the headers that the branch under test actually reads; system headers can be generated by the framework. Avoid asserting the exact auto-generated \`id\` or \`timestamp\` values, as they are not part of the business contract.

| Pattern | Minimal Input Message | What to Assert | Control Case |
| --- | --- | --- | --- |
| Router | Payload \`"m1"\` and \`kind=VIP\` | Only the VIP branch receives the message | \`kind=STANDARD\` goes to the other branch; unrelated branches remain empty |
| Filter | Payload \`"ok"\` | Valid message is forwarded | Blank payload is dropped or sent to the discard channel |
| Transformer | Payload \`"  a  "\` | Output payload becomes \`"a"\`; required headers are preserved | Unsupported input is handled according to the contract |
| Splitter | Payload \`["A", "B"]\` | Exactly two child messages, each carrying one element | Single-element list; empty list according to the chosen policy |
| Aggregator | Two messages with the same \`correlationId\`, \`sequenceSize=2\`, sequence numbers 1 and 2 | No result emitted after the first message, exactly one result emitted after the second | Another group is not merged together |
| Gateway | One call \`normalize(" a ")\` | The call receives \`"a"\` via the request/reply path | Timeout or error when there is no reply |
| Retry | One message and a handler that fails transiently on the first attempt | Handler is invoked twice and succeeds if configured for a maximum of two attempts | Persistent failure stops at the exact limit |
| Error channel | One message causing an error, with an appropriate error channel | Receives an \`ErrorMessage\` containing the cause | Synchronous exceptions must not be confused with errors published to an asynchronous channel |
| Correlation | Two groups A/B, two messages per group | Each result contains only elements from the same group | Send interleaved A1, B1, B2, A2 |

**Measurement principle:** Verify both what happened and what must *not* happen. A Router test that confirms VIP receives the message without checking whether the STANDARD branch is empty will still miss duplicate-dispatch bugs.

## 3. Choosing the Test Level

| Level | Scope | When to Use |
| --- | --- | --- |
| Unit test | Branch selection function, predicate, transformation function, correlation function | Pure Java logic, no ApplicationContext needed yet |
| Flow/component test | Channel → one or a few Spring Integration endpoints → observable channel | To prove that Router, Filter, Splitter, Aggregator, and header configurations actually work |
| Integration test | Gateway, broker, database, HTTP, transactions, and external systems | To verify I/O contracts, timeouts, and retries against real infrastructure or simulated environments |

Prefer unit tests for pure logic, and use flow tests to catch wiring mistakes. Only connect external services in tests whose correctness depends on those services. This keeps tests fast, stable, and accurate in pointing to the root cause.

For Spring Boot projects using Spring Integration, typical test dependencies are:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-integration</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>
    <dependency>
        <groupId>org.springframework.integration</groupId>
        <artifactId>spring-integration-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
~~~

The examples below illustrate Java 17, JUnit 5, AssertJ, and the Spring Integration 6.x Java DSL. In other projects, use compatible versions of Spring Boot and Spring Integration. The tests only use \`DirectChannel\` and \`QueueChannel\` and do not require a message broker.

## 4. Runnable Example: Five Core Patterns

Place the following class in your test sources, for example \`src/test/java/example/PatternMessageTest.java\`. The flows start at channels named \`*.in\`; the outputs are \`QueueChannel\` instances so the tests can receive messages and assert the results. Each test creates only the exact number of messages needed.

~~~java
package example;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.List;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.integration.IntegrationMessageHeaderAccessor;
import org.springframework.integration.channel.QueueChannel;
import org.springframework.integration.config.EnableIntegration;
import org.springframework.integration.dsl.IntegrationFlow;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;

@SpringJUnitConfig(PatternMessageTest.Flows.class)
class PatternMessageTest {

    @Autowired
    ApplicationContext context;

    private MessageChannel input(String name) {
        return context.getBean(name, MessageChannel.class);
    }

    private QueueChannel output(String name) {
        return context.getBean(name, QueueChannel.class);
    }

    private Message<?> received(String channel) {
        Message<?> message = output(channel).receive(1_000);
        assertThat(message).as("Expected message from %s", channel).isNotNull();
        return message;
    }

    @Test
    void router_goes_to_exactly_one_branch() {
        Message<String> message = MessageBuilder.withPayload("order-1")
                .setHeader("kind", "VIP")
                .build();

        assertThat(input("router.in").send(message)).isTrue();

        assertThat(received("router.vip").getPayload()).isEqualTo("order-1");
        assertThat(output("router.standard").receive(0)).isNull();
    }

    @Test
    void filter_accepts_valid_and_sends_invalid_to_discard() {
        input("filter.in").send(MessageBuilder.withPayload("ok").build());
        input("filter.in").send(MessageBuilder.withPayload("  ").build());

        assertThat(received("filter.accept").getPayload()).isEqualTo("ok");
        assertThat(received("filter.discard").getPayload()).isEqualTo("  ");
        assertThat(output("filter.accept").receive(0)).isNull();
    }

    @Test
    void transformer_changes_payload_and_keeps_business_header() {
        Message<String> message = MessageBuilder.withPayload("  abc  ")
                .setHeader("tenantId", "tenant-7")
                .build();

        input("transform.in").send(message);

        Message<?> result = received("transform.out");
        assertThat(result.getPayload()).isEqualTo("abc");
        assertThat(result.getHeaders().get("tenantId")).isEqualTo("tenant-7");
    }

    @Test
    void splitter_emits_one_message_for_each_element() {
        input("split.in").send(
                MessageBuilder.withPayload(List.of("A", "B")).build());

        Message<?> first = received("split.out");
        Message<?> second = received("split.out");

        assertThat(List.of(first.getPayload(), second.getPayload()))
                .containsExactly("A", "B");
        assertThat(first.getHeaders().get(
                IntegrationMessageHeaderAccessor.SEQUENCE_SIZE)).isEqualTo(2);
        assertThat(output("split.out").receive(0)).isNull();
    }

    @Test
    void aggregator_waits_for_the_whole_group() {
        input("aggregate.in").send(part("batch-1", 1, 2, "A"));
        assertThat(output("aggregate.out").receive(0)).isNull();

        input("aggregate.in").send(part("batch-1", 2, 2, "B"));
        Message<?> result = received("aggregate.out");

        assertThat(result.getPayload()).isInstanceOf(List.class);
        assertThat((List<?>) result.getPayload())
                .containsExactlyInAnyOrder("A", "B");
        assertThat(output("aggregate.out").receive(0)).isNull();
    }

    private static Message<String> part(
            String groupId, int sequence, int size, String value) {
        return MessageBuilder.withPayload(value)
                .setHeader(IntegrationMessageHeaderAccessor.CORRELATION_ID, groupId)
                .setHeader(IntegrationMessageHeaderAccessor.SEQUENCE_NUMBER, sequence)
                .setHeader(IntegrationMessageHeaderAccessor.SEQUENCE_SIZE, size)
                .build();
    }

    @Configuration
    @EnableIntegration
    static class Flows {

        @Bean("router.vip")
        QueueChannel vip() {
            return new QueueChannel();
        }

        @Bean("router.standard")
        QueueChannel standard() {
            return new QueueChannel();
        }

        @Bean
        IntegrationFlow router() {
            return IntegrationFlow.from("router.in")
                    .route("headers['kind']", r -> r
                            .channelMapping("VIP", "router.vip")
                            .channelMapping("STANDARD", "router.standard"))
                    .get();
        }

        @Bean("filter.accept")
        QueueChannel accepted() {
            return new QueueChannel();
        }

        @Bean("filter.discard")
        QueueChannel discarded() {
            return new QueueChannel();
        }

        @Bean
        IntegrationFlow filter() {
            return IntegrationFlow.from("filter.in")
                    .filter(String.class, text -> !text.isBlank(),
                            f -> f.discardChannel("filter.discard"))
                    .channel("filter.accept")
                    .get();
        }

        @Bean("transform.out")
        QueueChannel transformed() {
            return new QueueChannel();
        }

        @Bean
        IntegrationFlow transformer() {
            return IntegrationFlow.from("transform.in")
                    .transform(String.class, String::trim)
                    .channel("transform.out")
                    .get();
        }

        @Bean("split.out")
        QueueChannel splitOutput() {
            return new QueueChannel();
        }

        @Bean
        IntegrationFlow splitter() {
            return IntegrationFlow.from("split.in")
                    .split()
                    .channel("split.out")
                    .get();
        }

        @Bean("aggregate.out")
        QueueChannel aggregateOutput() {
            return new QueueChannel();
        }

        @Bean
        IntegrationFlow aggregator() {
            return IntegrationFlow.from("aggregate.in")
                    .aggregate()
                    .channel("aggregate.out")
                    .get();
        }
    }
}
~~~

**How to interpret the results:**

1. The Router confirms both the **correct output** and that the **other branch has no message**. To cover the STANDARD branch, add a symmetric test with \`kind=STANDARD\`; to cover unrecognized branches, clearly define the policy—*throw an error*, *route to a default channel*, or *ignore*—and test that exact policy.
2. The Filter sends two messages: \`"ok"\` is accepted and \`"  "\` is routed to the discard channel. When no discard channel is configured, a rejected message may terminate at the Filter without producing output; in that case, only assert that the output channel is empty.
3. The Transformer modifies only the payload. The test also checks \`tenantId\`, because dropping critical metadata is an integration bug even when the returned value is right.
4. The Splitter produces two child messages with sequence metadata. With a two-element list and synchronous channels as in the example, we can assert the \`A, B\` order; in a parallel processing system, do not assert ordering if the architecture does not guarantee it.
5. The Aggregator does not emit a result when only element 1/2 is present. Only after element 2/2 arrives does the group complete. The default aggregator uses correlation and sequence metadata to group messages; custom release strategies must be tested against their own contracts.

### Do Not Abuse Wait Timeouts

\`receive(0)\` is a useful immediate check for **synchronous** flows like the example. With an ExecutorChannel, broker, or asynchronous tasks, \`receive(0) == null\` right after sending does not prove that a message will not arrive late. When you need to verify *no message arrives within an observation window*, use a finite timeout and understand the scheduling assumptions; when expecting a message, use \`receive(1_000)\` or a condition-based wait, avoiding fixed \`Thread.sleep\` calls.

## 5. Gateway: Testing Request/Reply with a Single Call

A Gateway turns a Java method call into a message entering a flow and converts the reply message back into a return value. Minimal testing requires **one request**, **one reply**, and a timeout constraint. For example, declare this in a package scanned by Spring Integration:

~~~java
@MessagingGateway(defaultRequestChannel = "gateway.in")
public interface NormalizeGateway {
    String normalize(String input);
}
~~~

Configure the flow handling the request (in the same ApplicationContext as the gateway):

~~~java
@Bean
IntegrationFlow normalizeFlow() {
    return IntegrationFlow.from("gateway.in")
            .transform(String.class, String::trim)
            .get();
}
~~~

In a test with a Spring context and the gateway registered (for example via \`@IntegrationComponentScan\`):

~~~java
@Autowired
NormalizeGateway gateway;

@Test
void gateway_returns_the_reply() {
    assertThat(gateway.normalize("  hello  ")).isEqualTo("hello");
}
~~~

A Gateway needs a reply path back to the \`replyChannel\` set up by the framework. If the final endpoint does not produce a reply, the call may wait until the configured timeout expires. Tests for no-reply branches must configure a finite timeout so the test suite does not hang. For asynchronous operations, determine whether the Gateway truly returns immediately, returns a \`Future\`/\`CompletableFuture\`, or provides a callback mechanism; do not assume every gateway is synchronous.

## 6. Retry: One Message, Multiple Attempts

In integration flows, retry is typically applied to **transient** failures such as timeouts or temporary service unavailability. Tests must prove both the **number of attempts** and the **final outcome**, rather than only observing a successful result:

~~~java
AtomicInteger attempts = new AtomicInteger();

GenericHandler<String> occasionallyFailingHandler = (payload, headers) -> {
    int current = attempts.incrementAndGet();
    if (current == 1) {
        throw new IllegalStateException("temporary failure");
    }
    return "processed:" + payload;
};
~~~

Attach this handler to an endpoint configured with retry advice (for example \`RequestHandlerRetryAdvice\` with a \`RetryTemplate\`, up to **2 attempts**). Send a single message with payload \`"M1"\` and verify:

~~~java
assertThat(received("retry.out").getPayload()).isEqualTo("processed:M1");
assertThat(attempts.get()).isEqualTo(2);
~~~

This is an **illustrative snippet of the handler and assertions**; to execute it, wire the handler, retry advice, and output channel inside a flow. The control case is a handler that always throws: verify at most two attempts, no success message emitted, and the error is routed to the expected channel or thrown to the caller as configured. If the policy includes backoff, use very short delays in tests. If there is a recovery callback, verify the recovery outcome instead of assuming an exception must be thrown.

**Distinguish three concepts:** \`maxAttempts=2\` usually means **one initial attempt + one retry**; retrying may cause the handler to run multiple times for the same message; therefore, operations with side effects (recording orders, charging payments, publishing events) must consider idempotency. A passing retry test does not prove that external transactions are safe against duplicate processing.

## 7. Error Channel: Distinguishing Synchronous and Asynchronous Errors

Spring Integration's error path depends on the execution model:

~~~mermaid
flowchart TD
    A[Message enters flow] --> B{How does the channel / endpoint run?}
    B -->|Synchronous: DirectChannel| C[Handler throws exception]
    C --> D[send caller or Gateway receives exception]
    B -->|Asynchronous: ExecutorChannel| E[Handler throws exception]
    E --> F[ErrorMessage is published]
    F --> G[Configured errorChannel]
~~~

With a synchronous \`DirectChannel\`, errors normally propagate to the caller of \`send()\` or the Gateway:

~~~java
assertThatThrownBy(() ->
        input.send(MessageBuilder.withPayload("invalid").build()))
        .isInstanceOf(MessagingException.class);
~~~

With an asynchronous flow that has an error handler publishing errors, send a message carrying an \`errorChannel\` header (or use a properly configured global \`errorChannel\`), then inspect the error channel:

~~~java
Message<String> badMessage = MessageBuilder.withPayload("invalid")
        .setHeader(MessageHeaders.ERROR_CHANNEL, "flow.errors")
        .build();

input.send(badMessage);
ErrorMessage error = (ErrorMessage) errors.receive(1_000);

assertThat(error).isNotNull();
assertThat(error.getPayload()).isInstanceOf(MessagingException.class);
~~~

The latter snippet assumes \`input\` passes through an asynchronous endpoint, \`errors\` is a \`QueueChannel\` registered under the name \`flow.errors\`, and an error handler is configured to publish \`ErrorMessage\` instances. You cannot simply add an \`errorChannel\` header to a synchronous flow and assume the exception will appear on that channel. In real tests, also check the root cause exception type, a diagnostic-friendly error message, and the ability to trace back to the failed message.

## 8. Correlation: Proving Two Groups Do Not Mix

An Aggregator typically groups messages by \`correlationId\`. To catch group-mixing bugs, a single group is not enough. Use **four messages** forming two groups of size 2 each; send them interleaved:

~~~text
A1 (correlationId=A, sequenceNumber=1, sequenceSize=2)
B1 (correlationId=B, sequenceNumber=1, sequenceSize=2)
B2 (correlationId=B, sequenceNumber=2, sequenceSize=2) -> only B completes
A2 (correlationId=A, sequenceNumber=2, sequenceSize=2) -> A completes
~~~

Extend the test class in section 4 with this check:

~~~java
@Test
void aggregator_keeps_interleaved_groups_separate() {
    input("aggregate.in").send(part("A", 1, 2, "A1"));
    input("aggregate.in").send(part("B", 1, 2, "B1"));
    assertThat(output("aggregate.out").receive(0)).isNull();

    input("aggregate.in").send(part("B", 2, 2, "B2"));
    Message<?> groupB = received("aggregate.out");
    assertThat((List<?>) groupB.getPayload())
            .containsExactlyInAnyOrder("B1", "B2");

    input("aggregate.in").send(part("A", 2, 2, "A2"));
    Message<?> groupA = received("aggregate.out");
    assertThat((List<?>) groupA.getPayload())
            .containsExactlyInAnyOrder("A1", "A2");
    assertThat(output("aggregate.out").receive(0)).isNull();
}
~~~

This test detects faulty grouping using only **four messages**. For real production flows, you must also explicitly decide how to handle: duplicate \`sequenceNumber\` values, late-arriving messages, incomplete groups, expired groups, empty correlation keys, and group state after a restart. Those behaviors depend on the configured \`MessageGroupStore\`, \`ReleaseStrategy\`, \`MessageGroupProcessor\`, and timeout/expiry policies; they should never be assumed.

## 9. Testing a Chain of Patterns End-to-End

After testing each pattern individually, add a few main-path tests to ensure endpoints are wired together properly:

~~~mermaid
flowchart LR
    IN[Minimal message] --> R{Router}
    R -->|VIP| F{Filter}
    R -->|STANDARD| OUT2[Standard output]
    F -->|Valid| T[Transformer]
    F -->|Rejected| DROP[Discard channel]
    T --> S[Splitter]
    S --> A[Aggregator]
    A --> OUT[Result / Gateway reply]
    F -. Processing error .-> ERR[Error channel or exception]
~~~

Business example: a VIP request containing two item codes \`[" P01 ", " P02 "]\`. The Router selects the VIP branch, the Filter drops invalid requests, the Transformer normalizes the data, the Splitter emits two line items, and the Aggregator waits for both items before returning the result. A minimal end-to-end test must answer: was the right branch chosen, were any item codes lost, is the message count before/after the Splitter correct, does the Aggregator emit a result only when the group is complete, and does the Gateway receive the reply?

To make tests easy to diagnose, give channels clear names and place \`QueueChannel\` instances at observation points. Do not write assertions against logs: log levels or formats can change without altering flow behavior. When you need to verify a branch, check the message received on that channel. When you need to verify an error, catch the exception or read the \`ErrorMessage\` depending on the execution model.

### Happy Path and Edge Case Matrix

| Scenario | Minimal Input | What Bug Does It Catch? |
| --- | --- | --- |
| Select VIP | One message \`kind=VIP\` | Wrong mapping, dispatching to multiple branches |
| Select STANDARD | One message \`kind=STANDARD\` | Missing or swapped branches |
| Reject blank payload | One message with payload \`" "\` | Filter missing a condition |
| Preserve metadata | One message with \`tenantId\` | Transformer dropping required headers |
| Split two elements | One message with payload \`["A","B"]\` | Missing/extra outputs, broken sequence metadata |
| Complete group | Two messages A1, A2 | Early release, never releasing, or emitting multiple times |
| Keep groups separate | A1, B1, B2, A2 | Broken correlation |
| Gateway reply | One request \`" a "\` | Lost reply, wrong reply payload |
| Transient error | One message, handler fails on first attempt | Missing retry or exceeding retry limit |
| Permanent error | One message, handler always fails | Infinite hang, swallowed error, published to wrong channel |

## 10. Keeping the Test Suite Stable and Scalable

1. **Isolate state:** Each test should use its own correlation ID; do not share group stores, queues, or retry counters across tests without cleaning up state. If tests run in parallel, prefer creating independent contexts/beans and channels.
2. **Bound wait times:** Set finite timeouts for QueueChannel, Gateway, and asynchronous task waits. Avoid \`Thread.sleep\` and assumptions about CI machine speed.
3. **Do not assert unguaranteed ordering:** Assert payload sets when processing may run in parallel; only assert ordering when the flow uses a synchronous path or a defined ordering mechanism.
4. **Separate logic from wiring:** Unit test predicates, mappers, and correlation functions in plain Java; use flow tests with a Spring context to catch wrong channel names or wrong headers.
5. **Mock at integration boundaries:** For HTTP, databases, and brokers, use stubs or test adapters when real infrastructure is not yet needed. Spring Integration provides \`spring-integration-test\`, \`@SpringIntegrationTest\`, and \`MockIntegrationContext\` to replace endpoints in appropriate tests.
6. **Observe purposefully:** Record message IDs/correlation IDs at entry points, key branches, and error handlers when investigation is needed. Tests should rely on payloads, headers, and output channels rather than log strings.
7. **Control side effects:** With retry, verify both invocation count and idempotency when writing data; with Aggregator, test expiration rules or invalid-group handling if required by the product.

## 11. Self-Check Practice Exercises

Add four tests yourself to the example in section 4:

1. **Router STANDARD branch:** Send one message with \`kind=STANDARD\`; verify that only \`router.standard\` receives it.
2. **Filter all rejected:** Send one message with payload \`" "\`; assert that \`filter.accept\` is empty and \`filter.discard\` receives the exact payload.
3. **Aggregator multiple groups:** Use the sequence A1, B1, B2, A2. Prove that the first result is only B and the second result is only A.
4. **Retry exhausted:** Handler always fails; configure at most two attempts; verify the invocation count equals 2 and the final outcome matches the error/recovery policy.

A solution meets the standard when each test can run independently, uses the minimal required number of messages, and clearly demonstrates three things: **where the message went**, **what the final payload/headers are**, and **what must not happen**. This is the foundation for testing multi-branch Spring Integration flows while keeping them maintainable as more patterns are added.
