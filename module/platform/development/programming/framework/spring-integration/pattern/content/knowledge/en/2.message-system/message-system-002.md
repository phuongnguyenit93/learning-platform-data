# MessageHeaders and metadata immutability

In Spring Integration, a `Message<T>` carries a **payload** (business data) and **headers** (metadata describing how the message should be processed). When implementing Enterprise Integration Patterns (EIP), components such as Router, Filter, Transformer, Splitter, Aggregator, and Gateway often do not need to know the entire payload structure; they can make flow decisions based on metadata. `MessageHeaders` exposes this key–value set through an interface close to `Map<String, Object>`, but there is an important design rule: **you cannot directly modify the header map of an already created message**.

This lesson belongs to the **Message system** chapter of the **SPRING_INTEGRATION_PATTERN** module. The goal is to understand how metadata operates in a loosely coupled message flow, know how to create a new message when headers need to change, and avoid consistency bugs when routers, retries, error channels, splitters/aggregators, or multiple consumers process messages concurrently.

## 1. Learning objectives

After this lesson, you can:

1. Distinguish payload, metadata, `Message`, and `MessageHeaders` in Spring Messaging / Spring Integration.
2. Accurately explain the immutability of the header structure and the limits of that immutability regarding header **values**.
3. Read standard headers, Spring Integration headers, and business headers using the appropriate API.
4. Use `MessageBuilder` to add, replace, remove, or copy headers when creating a **new message**.
5. Handle `id`, `timestamp`, `correlationId`, `sequenceNumber`, `replyChannel`, and `errorChannel` according to their roles.
6. Design and test metadata propagation flows, avoiding lost headers or shared mutable references.

## 2. Where do Message and MessageHeaders sit in the architecture?

The core abstraction belongs to the `spring-messaging` module:

~~~java
package org.springframework.messaging;

public interface Message<T> {
    T getPayload();
    MessageHeaders getHeaders();
}
~~~

For an order, the payload might contain the order ID, items, and amount; headers might contain the tenant ID, trace ID, priority, or reply destination. A message only provides getters for payload and headers, with no setters to modify an existing message.

~~~mermaid
flowchart LR
    A["Message&lt;Order&gt;"] --> B["Payload: Order"]
    A --> C["MessageHeaders"]
    C --> D["tenantId, traceId: business metadata"]
    C --> E["id, timestamp: system metadata"]
    C --> F["replyChannel, errorChannel: flow control"]
    A --> G["Channel / Handler / Router"]
~~~

At the Java type level, `MessageHeaders` implements `Map<String, Object>`. This allows reading via `get`, `containsKey`, `entrySet`, etc., but **does not** mean you can modify the key–value set after the message is initialized.

In EIP, headers help:

- **Router** select a processing branch by `region`, `priority`, or `tenantId`.
- **Filter** allow or discard a message based on metadata attributes.
- **Transformer** alter the payload or create a new message while deciding which headers to keep.
- **Splitter / Aggregator** use correlation and sequence information to group messages.
- **Gateway** and **error flow** know where to send replies or handle errors.
- **Retry / logging / tracing** track processing attempts and a business flow spanning multiple steps.

## 3. Which headers are commonly encountered?

### 3.1. Standard Spring Messaging headers

The key constants reside in `org.springframework.messaging.MessageHeaders`:

| Header | Typical data type | Role | Usage notes |
|---|---|---|---|
| `MessageHeaders.ID` | `UUID` | Identifies a **message instance** | Generated by the framework; do not use in place of order ID or correlation ID |
| `MessageHeaders.TIMESTAMP` | `Long` | Message creation time, in epoch milliseconds | Do not use as a unique key; multiple messages can share the same timestamp |
| `MessageHeaders.REPLY_CHANNEL` | `String` or `MessageChannel` | Reply destination in request–reply exchanges | Framework control header; avoid overwriting arbitrarily |
| `MessageHeaders.ERROR_CHANNEL` | `String` or `MessageChannel` | Channel receiving errors | Meaningful in integration flow error handling |
| `MessageHeaders.CONTENT_TYPE` | Value suitable for conversion mechanism | Content type hint for converters or adapters | Content and representation depend on protocol and adapter |

System values can be read quickly:

~~~java
import java.util.UUID;
import org.springframework.messaging.Message;

void inspect(Message<?> message) {
    UUID id = message.getHeaders().getId();
    Long timestamp = message.getHeaders().getTimestamp();
    Object replyChannel = message.getHeaders().getReplyChannel();
    Object errorChannel = message.getHeaders().getErrorChannel();

    System.out.printf("id=%s, timestamp=%s%n", id, timestamp);
}
~~~

`id` and `timestamp` are managed as **read-only** headers in standard Spring Integration message construction. When message content changes and a new message instance is created, a new ID is usually generated; timestamp reflects the new creation time. Do not manually set these two headers with `setHeader` trying to force the same identity.

### 3.2. Spring Integration headers

Specific key constants reside in `org.springframework.integration.IntegrationMessageHeaderAccessor`.

| Header | Role when using EIP |
|---|---|
| `CORRELATION_ID` | Groups messages belonging to the same unit of work, especially useful for Aggregator |
| `SEQUENCE_NUMBER` | Ordinal number of a message within a split group |
| `SEQUENCE_SIZE` | Expected number of messages in the group, if known |
| `PRIORITY` | Priority level, used by components such as `PriorityChannel` |
| `EXPIRATION_DATE` | Expiration timestamp metadata; by itself it does not cause the framework to drop messages everywhere |
| `DUPLICATE_MESSAGE` | Indicator of duplicate message detection in idempotent receiver mechanisms |
| `DELIVERY_ATTEMPT` | Delivery/processing attempt count in certain retry-capable adapters |
| `ACKNOWLEDGMENT_CALLBACK` | Callback to acknowledge/reject or requeue depending on the adapter |

Distinguish clearly: `id` is the identifier **of a single message**, whereas `correlationId` can stay stable across **multiple messages** belonging to the same transaction or group. Do not assume every adapter or endpoint automatically attaches all headers in the table above; many headers appear only when using supporting components.

`IntegrationMessageHeaderAccessor` provides typed reading for several headers:

~~~java
import org.springframework.integration.IntegrationMessageHeaderAccessor;
import org.springframework.messaging.Message;

void inspectIntegrationHeaders(Message<?> message) {
    IntegrationMessageHeaderAccessor accessor =
            new IntegrationMessageHeaderAccessor(message);

    Object correlationId = accessor.getCorrelationId();
    int sequenceNumber = accessor.getSequenceNumber();
    int sequenceSize = accessor.getSequenceSize();

    System.out.printf("group=%s, part=%d/%d%n",
            correlationId, sequenceNumber, sequenceSize);
}
~~~

When a message does not carry sequence information, do not assume it is the sole element of a group. Check the relevant headers or endpoint contract before processing the result.

### 3.3. Application-defined business headers

You can also use custom headers like `tenantId`, `region`, `schemaVersion`, `sourceSystem`, and `traceId`. Name them consistently, and document their data types and propagation rules across steps. For example, `tenantId` is an immutable `String`; `schemaVersion` can be an `Integer`; `traceId` should be a safe string for logging according to system policy.

Do not put secrets, access tokens, or sensitive personal data into headers merely for debugging convenience: many systems log entire messages, including metadata.

## 4. Immutability of MessageHeaders: how far does it go?

### 4.1. Structural immutability of the header set

`MessageHeaders` has a `Map`-like reading API, but operations that modify the header set such as `put`, `putAll`, `remove`, or `clear` throw `UnsupportedOperationException`.

~~~java
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

Message<String> message = MessageBuilder.withPayload("ORDER-1001")
        .setHeader("tenantId", "shop-a")
        .build();

// Reading: valid
String tenantId = message.getHeaders().get("tenantId", String.class);

// Direct mutation: throws UnsupportedOperationException
message.getHeaders().put("tenantId", "shop-b");
~~~

The message does not turn into `shop-b` after the last line; the mutation fails. Therefore, a component holding the old message cannot have its **metadata structure** altered by another component calling `put` on that same `MessageHeaders` object.

### 4.2. Not automatically deeply immutable

**Immutability of the map does not imply immutability of the objects referenced by the map.** A header value and the payload itself can be a mutable `List`, `Map`, or object. If other code still holds a reference to that object, content mutations can still be observed from the message.

~~~java
import java.util.ArrayList;
import java.util.List;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

List<String> tags = new ArrayList<>(List.of("urgent"));

Message<String> message = MessageBuilder.withPayload("ORDER-1001")
        .setHeader("tags", tags)
        .build();

tags.add("review"); // Valid on ArrayList; mutates the same referenced object

System.out.println(message.getHeaders().get("tags"));
// May observe [urgent, review] because the header value is still a mutable List.
~~~

To keep metadata stable, create an unmodifiable copy **before placing it in the header**:

~~~java
List<String> mutableTags = new ArrayList<>(List.of("urgent"));
List<String> snapshot = List.copyOf(mutableTags);

Message<String> safe = MessageBuilder.withPayload("ORDER-1001")
        .setHeader("tags", snapshot)
        .build();

mutableTags.add("review"); // snapshot in the message still contains only "urgent"
~~~

`List.copyOf` works well when the elements themselves are sufficiently immutable. For nested structures, you must copy and lock child objects; `Map.copyOf` or `List.copyOf` does not automatically deep-copy every value. This rule is especially important for `PublishSubscribeChannel`, asynchronous channels, retries, and processing that may run concurrently.

### 4.3. Distinguishing three ideas

| Question to ask | Conclusion |
|---|---|
| Can keys be added/removed directly on `message.getHeaders()`? | No, `MessageHeaders` blocks mutating operations |
| Can the payload be replaced via a setter on `Message`? | There is no setter on the `Message` interface; you must create another message when changing payload |
| Can a mutable object inside the payload/header be mutated via reference? | Yes; the developer must choose immutable data, snapshots, or controlled sharing |

Immutability here is **the contract of the message and header structure in normal usage**, not a guarantee that every object referenced inside is immutable. Spring Integration also has `MutableMessage` for cases intentionally optimizing for mutable content; this lesson focuses on the default usage with `GenericMessage` and `MessageBuilder`.

## 5. Creating and updating metadata properly with MessageBuilder

For an existing message, build a **new message** with the desired payload/headers. In the following examples, `org.springframework.messaging.support.MessageBuilder` is used (the Spring Messaging API; Spring Integration also has a corresponding builder in the `org.springframework.integration.support` package).

### 5.1. Creating a message with business metadata

~~~java
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

Message<String> incoming = MessageBuilder.withPayload("ORDER-1001")
        .setHeader("tenantId", "shop-a")
        .setHeader("traceId", "trace-2026-001")
        .setHeader("region", "north")
        .setHeaderIfAbsent("sourceSystem", "checkout")
        .build();

String tenant = incoming.getHeaders().get("tenantId", String.class);
String region = incoming.getHeaders().get("region", String.class);
~~~

`setHeaderIfAbsent` sets a value only if that header is not already present; `setHeader` sets or updates the value on the builder being configured.

### 5.2. Changing headers by creating a new message

~~~java
Message<String> routed = MessageBuilder.fromMessage(incoming)
        .setHeader("route", "orders.north")
        .removeHeader("debugFlag")
        .build();

// incoming is not modified
System.out.println(incoming.getHeaders().get("route")); // null
System.out.println(routed.getHeaders().get("route"));   // "orders.north"
System.out.println(routed.getHeaders().get("tenantId")); // "shop-a"
~~~

`fromMessage` is convenient when keeping the original payload and wanting to modify some headers. A new message is created, so having the same payload does not mean having the same message identity. Also note: if the payload is a mutable object, the builder does not deep-copy the payload by default.

### 5.3. Replacing the payload and copying necessary headers

~~~java
Message<String> normalized = MessageBuilder
        .withPayload(incoming.getPayload().trim().toUpperCase())
        .copyHeaders(incoming.getHeaders())
        .setHeader("normalized", true)
        .build();

Message<String> outbound = MessageBuilder
        .withPayload("ORDER-SUMMARY-1001")
        .setHeader("region", "central")
        .copyHeadersIfAbsent(incoming.getHeaders())
        .build();

// outbound.region stays "central" because copyHeadersIfAbsent does not overwrite.
~~~

Use `copyHeaders` when you want to carry values into the new message; use `copyHeadersIfAbsent` when headers set by the current step must take precedence. In standard Spring Integration construction, `id` and `timestamp` are read-only headers handled separately; do not use copying to force an old message ID onto a new message.

If a message crosses a trust boundary (for example from HTTP into an internal queue), do not automatically copy every header. Whitelist valid, properly typed headers that are permitted to continue.

### 5.4. Accessor vs. mutating MessageHeaders

`MessageHeaderAccessor` supports a workflow for **preparing** metadata; whereas `MessageHeaders` of a published message represents a header map meant for reading. When you need to create/update a message, prefer `MessageBuilder` or configure a `Header Enricher` / `Header Filter` in the integration flow. Avoid relying on internal mechanisms or casting to bypass immutability.

## 6. How does metadata flow through Router, Transformer, Splitter, and Aggregator?

Consider an order processing flow:

~~~mermaid
flowchart LR
    A["Gateway / inbound adapter"] --> B["Enrich headers"]
    B --> C{"Router: region / priority"}
    C -->|fast| D["Fast lane"]
    C -->|normal| E["Normal lane"]
    D --> F["Transformer"]
    E --> F
    F --> G["Splitter"]
    G --> H["Aggregator"]
    H --> I["Outbound adapter"]
    F -.->|exception| J["errorChannel"]
~~~

Each step must have a clear contract on what metadata will be present at the output. For example:

| Component | Headers that may be used | What to control |
|---|---|---|
| Header Enricher | `sourceSystem`, `tenantId`, `traceId` | Only add verified data; avoid overwriting control metadata |
| Router | `region`, `priority` | Define a default branch when the header is missing/wrongly typed |
| Filter | `schemaVersion`, `tenantId` | Do not blindly trust headers sent by external clients |
| Transformer | `traceId`, `tenantId` | Understand header propagation rules when returning a payload vs. returning a full `Message` |
| Splitter | `correlationId`, `sequenceNumber`, `sequenceSize` | Need consistent correlation to group parts |
| Aggregator | `correlationId`, sequence metadata | Avoid accidentally grouping two transactions; have a timeout/expiry strategy |
| Gateway / error flow | `replyChannel`, `errorChannel` | Ensure replies/errors reach the right place; do not alter arbitrarily |
| Retry / observability | `deliveryAttempt`, `traceId` | Do not assume retry creates a new business ID; control idempotency |

### 6.1. Example of header-based routing

A Router method in Spring Integration can directly read a header using the `@Header` annotation:

~~~java
import org.springframework.integration.annotation.Router;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.stereotype.Component;

@Component
public class OrderRouter {

    @Router(inputChannel = "orders.toRoute")
    public String destination(@Header("region") String region) {
        return "north".equalsIgnoreCase(region)
                ? "orders.north"
                : "orders.other";
    }
}
~~~

This is an example for a router based on a normalized value. Before deploying to a real flow, determine how to handle `region` being missing, blank, or invalid; when appropriate, add validation or a default channel. The Router only reads metadata to select a channel and does not need to modify headers directly.

### 6.2. Transformer returning a payload vs. returning a Message

Under Spring Integration's header propagation mechanism, many endpoints producing output carry over input headers by default. For **Transformer**, there is an important distinction:

- If a transformer returns only a **new payload**, the framework can normally propagate input headers to the output message.
- If a transformer returns **a complete `Message`**, the transformer code is responsible for determining the entire content and headers of the output message. Do not assume all old headers remain.
- Headers already present on the output message normally take precedence; specific endpoints also have configurations that suppress certain headers.

Example of proactively copying metadata when returning a `Message` directly:

~~~java
import org.springframework.integration.annotation.Transformer;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.stereotype.Component;

@Component
public class OrderNormalizer {

    @Transformer(inputChannel = "orders.raw",
                 outputChannel = "orders.normalized")
    public Message<String> normalize(Message<String> input) {
        String cleaned = input.getPayload().strip().toUpperCase();

        return MessageBuilder.withPayload(cleaned)
                .copyHeaders(input.getHeaders())
                .setHeader("normalized", true)
                .build();
    }
}
~~~

In this example, there is no mutation of `input.getHeaders()`. The returned message keeps the copied metadata and adds `normalized`, while ID/timestamp are handled by the framework per the message creation contract.

### 6.3. Correlation and sequence when splitting/aggregating

When an order is split by a Splitter into three line items, the child messages typically need a shared correlation key, distinct sequence numbers, and a sequence size reflecting the number of parts. The Aggregator uses this information (or configured correlation/release strategies) to assemble the right group.

Example of **metadata meaning** (illustrative, not a requirement to attach every header manually):

| Message | Correlation ID | Sequence number | Sequence size |
|---|---|---:|---:|
| Line item A | `order-1001` | 1 | 3 |
| Line item B | `order-1001` | 2 | 3 |
| Line item C | `order-1001` | 3 | 3 |

If you arbitrarily change the correlation ID in one branch, the Aggregator may fail to gather all parts. Conversely, using `MessageHeaders.ID` as the correlation key for each individual part can put each part into a different group. A transaction ID / order ID should be clearly defined from the start, along with timeouts and a strategy for handling incomplete groups.

### 6.4. Reply, error, and retry headers

`replyChannel` and `errorChannel` are flow-control metadata understood by the framework. They can be channel names or appropriate `MessageChannel` objects. Gateway, asynchronous processing, and error handling mechanisms can depend on these values, so avoid stripping them in a header filter step without verifying reply/error conditions.

`deliveryAttempt` in some contexts is an `AtomicInteger` object. This is a prime example of the limits of “immutable headers”: the **entry** in the map is read-only, but the **value object** can change its count. Therefore, do not conclude from `MessageHeaders` immutability that retry counters or all other metadata cannot change.

## 7. Common design mistakes

### Mistake 1 — Directly mutating headers after receiving a message

~~~java
// Wrong: MessageHeaders does not allow structural changes after creation.
message.getHeaders().put("status", "processed");

// Right: create a new message with the desired metadata.
Message<String> processed = MessageBuilder.fromMessage(message)
        .setHeader("status", "processed")
        .build();
~~~

### Mistake 2 — Using message ID as a business key across the flow

`MessageHeaders.ID` identifies a message instance, so it may differ after a transform or rebuild step. Use `orderId` in the payload, an application-defined `businessCorrelationId`, or `correlationId` per the EIP contract. The message ID remains useful for observing a specific emission.

### Mistake 3 — Mixing routing information with unverified data

A client sending `tenantId=admin` or `priority=999` does not mean the system should trust it and route the message into a privileged branch. Normalize, validate, and constrain headers before a router/filter uses them; do not let external metadata overwrite controlled internal metadata.

### Mistake 4 — Sharing mutable objects across multiple consumers

If two consumers receive the same message and one modifies a `List` in a header or a field of the payload, the other may observe the mutated state. Use immutable DTOs, records with immutable fields, defensive copies for collections, and processing logic that does not mutate inputs.

### Mistake 5 — Transformer creates a new Message but forgets headers

A transformer returning a full `Message` can drop `traceId`, `tenantId`, or correlation metadata if it does not explicitly copy them. Establish a header contract per endpoint; test split–aggregate and error scenarios to catch dropped headers. Do not copy everything out of habit if there are sensitive headers or headers valid only for one hop.

### Mistake 6 — Assuming metadata enforces business behavior by itself

Setting `expirationDate` does not mean every channel automatically discards expired messages; setting `priority` does not make every channel sort by priority. Metadata only takes effect when an endpoint, channel, selector, or handler is configured to interpret it.

## 8. Testing immutability behavior and header preservation

The following examples use Java 17+ and JUnit Jupiter 5, illustrating API-level tests. They are independent of booting the full integration flow.

~~~java
import static org.junit.jupiter.api.Assertions.*;

import java.util.ArrayList;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

class MessageHeadersTest {

    @Test
    void directHeaderMutationIsRejected() {
        Message<String> input = MessageBuilder.withPayload("ORDER-1001")
                .setHeader("tenantId", "shop-a")
                .build();

        assertThrows(UnsupportedOperationException.class,
                () -> input.getHeaders().put("tenantId", "shop-b"));

        assertEquals("shop-a", input.getHeaders().get("tenantId"));
    }

    @Test
    void buildingUpdatedMessageDoesNotModifyOriginal() {
        Message<String> original = MessageBuilder.withPayload("ORDER-1001")
                .setHeader("traceId", "trace-001")
                .build();

        Message<String> updated = MessageBuilder.fromMessage(original)
                .setHeader("route", "orders.fast")
                .build();

        assertNotSame(original, updated);
        assertNull(original.getHeaders().get("route"));
        assertEquals("orders.fast", updated.getHeaders().get("route"));
        assertEquals("trace-001", updated.getHeaders().get("traceId"));
    }

    @Test
    void mutableHeaderValueIsNotDeeplyFrozen() {
        List<String> tags = new ArrayList<>(List.of("urgent"));

        Message<String> input = MessageBuilder.withPayload("ORDER-1001")
                .setHeader("tags", tags)
                .build();

        tags.add("review");

        assertEquals(List.of("urgent", "review"),
                input.getHeaders().get("tags"));
    }

    @Test
    void copyingValueBeforePublishKeepsStableSnapshot() {
        List<String> tags = new ArrayList<>(List.of("urgent"));

        Message<String> input = MessageBuilder.withPayload("ORDER-1001")
                .setHeader("tags", List.copyOf(tags))
                .build();

        tags.add("review");

        assertEquals(List.of("urgent"), input.getHeaders().get("tags"));
    }
}
~~~

With an actual integration flow, add tests traversing channels, transformers, and routers to verify metadata is propagated according to **that specific endpoint's** configuration. Avoid writing assertions expecting `timestamp` to be strictly different between two messages created almost simultaneously, because two instants can fall within the same millisecond.

## 9. Hands-on exercise: stable metadata in an order flow

Suppose you build the flow `orders.inbound → orders.validate → orders.route → orders.process → orders.outbound`. A request arriving from the checkout application carries an order payload and headers `tenantId`, `region`, `traceId`.

**Requirements:**

1. Create an input message with the three headers above and a payload containing the order ID.
2. After the validation step, add `validated=true` by creating a new message; preserve `tenantId` and `traceId` from the previous message.
3. Have the Router choose `orders.north` when `region=north`, and `orders.other` otherwise.
4. In the payload normalization step, create a new message and ensure `traceId` still exists.
5. Write three checks: mutating via `getHeaders().put(...)` must fail; the old message does not have `validated`; the message after normalization still has `traceId`.
6. Add an advanced scenario: the payload or a header contains a mutable collection; demonstrate the shared-reference risk and fix it using an immutable snapshot.

**Implementation hint:**

~~~java
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

Message<String> input = MessageBuilder.withPayload(" order-1001 ")
        .setHeader("tenantId", "shop-a")
        .setHeader("region", "north")
        .setHeader("traceId", "trace-001")
        .build();

Message<String> validated = MessageBuilder.fromMessage(input)
        .setHeader("validated", true)
        .build();

Message<String> normalized = MessageBuilder
        .withPayload(validated.getPayload().strip().toUpperCase())
        .copyHeaders(validated.getHeaders())
        .build();
~~~

Self-check questions: **Why does `input` not have the `validated` header while `validated` does? Why is the message ID not an appropriate key for aggregating line items of the same order? If you want to remove `tenantId` when sending to a partner, at which step would you do it and what would you test?**

## 10. Design checklist for production projects

- Identified which business headers are required, their data types, and their trusted sources.
- Handlers treat incoming messages as read-only data; changes use builders or corresponding enrich/filter mechanisms.
- Header values shared across branches are immutable or defensively copied.
- `id` and `timestamp` are managed by the framework; business correlation IDs are maintained under a separate contract.
- Routers/filters have handling paths when metadata is missing or mistyped.
- Transformers returning a full `Message` explicitly decide which headers to copy.
- Splitters/Aggregators use a consistent correlation key and have a policy for incomplete groups.
- Reply/error control headers are not stripped unintentionally.
- Logs and tracing avoid exposing sensitive headers; `traceId` is observable across necessary hops.
- Tested happy paths, error branches, retries, and multiple-consumer cases.

## 11. Summary

`MessageHeaders` carries metadata that helps Enterprise Integration Patterns collaborate without forcing every component to understand payload details. The immutability **of the header structure** gives a created message a stable key–value set against direct mutation calls, making branching and message passing more predictable. When you need to change metadata or payload, create a **new message** using `MessageBuilder` and clearly define which headers are copied.

However, the objects used as header/payload values themselves can be mutable. To stay safe during concurrent execution or publish–subscribe, choose immutable data or defensive snapshots. At the same time, distinguish a message instance's ID from a transaction's correlation key, and verify the header propagation behavior of each endpoint (especially Transformer and Splitter/Aggregator).
