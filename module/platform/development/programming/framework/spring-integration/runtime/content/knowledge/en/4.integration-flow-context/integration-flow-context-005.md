# Dynamic Flows with an Input Channel or Gateway

In a typical Spring Integration application, `IntegrationFlow` instances are declared as beans and registered when the Spring `ApplicationContext` starts. This approach works well for fixed processing flows. However, some systems need to create or remove flows while the application is running—for example, when each tenant has its own processing flow, a partner connection has just been activated, or a business configuration is loaded from a database.

`IntegrationFlowContext` provides the API to register and manage such flows at runtime. After registration, the application can send messages into the flow via an input channel or invoke a gateway wired to that channel. When the flow is no longer needed, the application removes the registration so the endpoints and components created by the flow are stopped and released.

The key design principle to keep clear is that **the flow definition, the flow entry point, and the caller invoking the flow are three distinct concepts**. `IntegrationFlow` describes the processing steps; the input channel receives messages; and a gateway or `MessageChannel`/`MessagingTemplate` is how application code sends requests into the flow.

## 1. When is a dynamic IntegrationFlow needed?

Flows declared with `@Bean` are suitable when the topology is stable and known at startup. Dynamic flows are suitable when the number or configuration of flows changes based on runtime data.

Common scenarios include:

- Each tenant has its own endpoint, filters, mappings, or connection details.
- A partner integration is enabled or disabled without restarting the entire application.
- An administrator creates a processing pipeline based on saved configuration.
- A task needs to create a temporary flow, receive a batch of messages, and then remove the flow.
- The application needs to isolate endpoints and channels created for each processing session.

Do not turn every minor variation into a separate flow. If only a single value changes, a router or configuration-driven service may be simpler. Dynamic flows are appropriate when you genuinely need to change the topology or the lifecycle of endpoints.

## 2. Participating components

| Component | Role |
|---|---|
| `IntegrationFlow` | Defines the chain of endpoints, channels, and processing steps. |
| `IntegrationFlowContext` | Registry and control point for registering, looking up, and removing dynamic flows. |
| `IntegrationFlowRegistration` | Handle representing a registered flow; provides the ID, input channel, and messaging template when applicable. |
| Registration ID | Identifier for a single flow registration within `IntegrationFlowContext`. |
| Input channel | Entry point receiving inbound messages for the flow. |
| Gateway | Business-oriented API for application code to send requests and optionally receive replies from the flow. |

In an application with Spring Integration infrastructure enabled, you can inject `IntegrationFlowContext` into a flow-management service:

```java
@Service
public class DynamicFlowManager {

    private final IntegrationFlowContext flowContext;

    public DynamicFlowManager(IntegrationFlowContext flowContext) {
        this.flowContext = flowContext;
    }
}
```

Typically, this infrastructure is provided when Spring Integration configuration is activated, such as via `@EnableIntegration` or the corresponding Spring Boot auto-configuration. You do not need to create a new `IntegrationFlowContext` per flow; registrations should be managed through the application's shared context.

## 3. Registering a dynamic flow

The basic workflow has four steps:

1. Build an `IntegrationFlow` object using the Java DSL.
2. Register the flow through `IntegrationFlowContext` and assign a stable ID.
3. Obtain the registration handle to access the input channel or messaging template.
4. Send messages into the flow and retain the handle to remove the flow when needed.

Example creating a string-transformation flow:

```java
IntegrationFlow flow = IntegrationFlow
    .from(MessageChannels.direct())
    .<String, String>transform(String::trim)
    .<String, String>transform(String::toUpperCase)
    .get();

IntegrationFlowRegistration registration = flowContext
    .registration(flow)
    .id("uppercaseFlow")
    .useFlowIdAsPrefix()
    .register();
```

`registration(...)` creates a builder for the registration. `.id("uppercaseFlow")` sets the registration ID. `.useFlowIdAsPrefix()` requests using the flow ID as a prefix for component names generated by the flow, reducing the risk of name collisions when registering multiple flows with the same structure. `.register()` performs the registration and returns an `IntegrationFlowRegistration`.

When registration succeeds, Spring Integration creates and manages the required components, wires them into the context, and starts endpoints according to the flow's startup configuration. If the ID or component names collide, registration can fail; the application must handle registration errors instead of assuming the flow is ready.

## 4. Sending messages via the input channel

For a flow with an input channel managed by the registration, you can obtain the channel via `registration.getInputChannel()`:

```java
MessageChannel input = registration.getInputChannel();

boolean accepted = input.send(
    MessageBuilder.withPayload("  hello spring integration  ").build()
);
```

`send()` places the message onto the channel. A return value of `true` indicates the channel accepted the message according to that channel's semantics; it does not by itself prove all downstream business logic has completed. With `DirectChannel`, handlers typically execute immediately on the sending thread so exceptions can propagate back to the caller. With asynchronous or queued channels, a successful send may only mean the message has been accepted for later processing.

If the flow uses a pre-existing `MessageChannel` bean as its entry point, keep a reference to that bean and send to that channel directly. `getInputChannel()` is especially useful for input channels created alongside the registration; when using an external channel, the channel bean reference is the clear access point.

Example with a pre-declared channel:

```java
@Bean
public MessageChannel partnerInput() {
    return new DirectChannel();
}
```

A dynamic flow can start from this channel bean:

```java
public IntegrationFlowRegistration registerPartnerFlow(
        IntegrationFlowContext flowContext,
        @Qualifier("partnerInput") MessageChannel partnerInput,
        PartnerService partnerService) {

    IntegrationFlow partnerFlow = IntegrationFlow
        .from(partnerInput)
        .handle(partnerService, "process")
        .get();

    return flowContext.registration(partnerFlow)
        .id("partnerAFlow")
        .useFlowIdAsPrefix()
        .register();
}
```

In this example, `@Qualifier` selects the right channel bean if the context has multiple `MessageChannel` beans. If multiple flows subscribe to the same `DirectChannel`, the channel may distribute messages across subscribers according to its dispatch strategy. Therefore, do not share one direct input channel across multiple tenant flows when each message must go to that specific tenant's flow. Create a dedicated channel per registration or place a router in front of the flows.

## 5. Sending requests and receiving replies with MessagingTemplate

Some flows need to return a result immediately to the caller. `IntegrationFlowRegistration` provides `getMessagingTemplate()` to send a request and wait for a reply using Spring Messaging's request/reply mechanism:

```java
Message<?> reply = registration.getMessagingTemplate()
    .sendAndReceive(
        MessageBuilder.withPayload("  hello spring integration  ").build()
    );

if (reply != null) {
    String result = (String) reply.getPayload();
}
```

`sendAndReceive()` uses the registration's input channel and sets up the reply information needed for the request. The result can be `null` if no reply arrives within the wait period or if the flow produces no reply. Configure timeouts appropriate for the business SLA and handle the no-result case.

Request/reply only works when endpoints in the flow produce a reply and that reply is routed back to the appropriate `replyChannel`. A `void` handler or a one-way terminating branch does not automatically produce a return payload. For asynchronous flows, pay special attention to timeouts, reply channels, and the fact that the caller may time out before processing finishes.

You can use `convertSendAndReceive(...)` when you want Spring to convert the reply payload to a desired type. Either way, clearly define request/reply types and timeout behavior; do not treat sending a message to a channel as proof that a business result was received.

## 6. Using a gateway as the API to invoke flows

`@MessagingGateway` lets you provide a business interface so application code can invoke a flow just like calling a service. The gateway sends requests to the specified channel and can receive a reply if the method declares a return type.

In pure Java configuration, enable gateway scanning with `@IntegrationComponentScan` on a configuration class (along with the appropriate Spring Integration infrastructure). With Spring Boot, verify the application's gateway scanning configuration rather than assuming every `@MessagingGateway` interface automatically gets a proxy.

Example declaring a stable channel and gateway:

```java
@Bean
public MessageChannel tenantOrdersInput() {
    return new DirectChannel();
}

@MessagingGateway
public interface TenantOrdersGateway {

    @Gateway(requestChannel = "tenantOrdersInput")
    OrderResult submit(OrderRequest request);
}
```

A flow can be dynamically registered on that channel:

```java
public IntegrationFlowRegistration registerTenantFlow(
        IntegrationFlowContext flowContext,
        @Qualifier("tenantOrdersInput") MessageChannel tenantOrdersInput,
        OrderService orderService) {

    IntegrationFlow tenantFlow = IntegrationFlow
        .from(tenantOrdersInput)
        .handle(orderService, "submit")
        .get();

    return flowContext.registration(tenantFlow)
        .id("tenantAOrders")
        .useFlowIdAsPrefix()
        .register();
}
```

The gateway is a stable facade for business code; the flow is attached to the channel when the registration is created. The gateway can only send successfully after the flow has been registered and the endpoint has subscribed to the channel. When the flow is removed, the channel bean may still exist, but it no longer has that flow's subscriber; the application must block requests or return an appropriate status while the flow is inactive.

In the example above, `OrderService.submit` must return an `OrderResult` so the gateway can receive a reply. If the handler only writes data and returns nothing, use a `void` gateway method or design an explicit reply.

### One gateway for multiple dynamic flows

A `@MessagingGateway` is typically configured with a stable channel. It does not automatically generate a separate gateway proxy for each dynamic registration. When supporting multiple tenants, there are two common design approaches:

- The gateway sends to a shared channel; a router reads `tenantId` from a header or payload and forwards the request to the input channel of the corresponding flow.
- Each registration has its own input channel; a flow-management service holds references to the corresponding channels or messaging templates and selects the right registration by tenant.

Do not register multiple tenant flows on the same `DirectChannel` expecting the channel to route by tenant automatically. With multiple subscribers, dispatching can distribute messages among subscribers rather than choosing a subscriber based on business data. Routing must be expressed explicitly using a router or separate channels.

## 7. Choosing an input channel aligned with flow semantics

Dynamic flows still follow Spring Integration's channel semantics. Channel choice affects threading, processing timing, back-pressure, and how errors are observed.

| Channel | Processing behavior | Consequence when used as entry point |
|---|---|---|
| `DirectChannel` | Calls subscriber synchronously on sender thread | Good for simple request/reply; exceptions can propagate back to caller. |
| `PublishSubscribeChannel` | Broadcasts messages to multiple subscribers | Use when fan-out is needed; clarify whether an executor is used and how each branch handles errors. |
| `QueueChannel` | Buffers messages in a queue for later consumption | Decouples producer and consumer; requires an appropriate poller or consumer to pull messages. |
| `ExecutorChannel` | Dispatches work through an executor | Separates sender and processing threads; requires configuring executor, error handling, and load limits. |

Do not choose `QueueChannel` just to get asynchronous processing while forgetting the consumer/poller. Without a consumer pulling messages, messages sit in the queue and the flow makes no progress. Similarly, `ExecutorChannel` needs a sensibly bounded executor; if the task queue grows unboundedly, dynamic flows can amplify load instead of resolving bottlenecks.

## 8. Assigning IDs and avoiding collisions between flows

The registration ID identifies the flow in `IntegrationFlowContext`, while endpoint IDs and channel names identify components inside the flow. These are different scopes.

For example, a tenant has registration ID `tenantAOrders`, while endpoints inside the flow can still carry IDs such as `validate` or `persist`. When creating multiple flows with the same structure, `.useFlowIdAsPrefix()` gives generated component names a unique prefix based on the flow ID. If you assign explicit IDs to individual endpoints or channels, check prefixing rules and ensure final names do not collide with existing beans.

A useful convention is:

| Object | Example |
|---|---|
| Registration ID | `tenantAOrders` |
| Dedicated input channel | `tenantA.orders.input` |
| Validate endpoint | `tenantA.orders.validate` |
| Persist endpoint | `tenantA.orders.persist` |
| Business correlation ID | `ORDER-9001` |

Do not use a message ID or correlation ID as a registration ID. Message IDs normally change per message; correlation IDs belong to a business operation or message group; registration IDs belong to the lifecycle of a managed flow.

## 9. Removing flows and managing lifecycle

When a flow is no longer needed, remove the registration by ID:

```java
flowContext.remove("tenantAOrders");
```

You can also retain the `IntegrationFlowRegistration` and use the ID from the handle itself:

```java
flowContext.remove(registration.getId());
```

Removing the registration instructs the framework to stop endpoints and release components managed by that flow registration. Do not try to locate and delete generated beans one by one by guessing names; doing so risks leaving behind endpoints, channels, or dependency links.

A flow-management service typically stores registrations keyed by tenant or configuration key:

```java
@Service
public class TenantFlowRegistry {

    private final IntegrationFlowContext flowContext;
    private final Map<String, IntegrationFlowRegistration> registrations =
        new ConcurrentHashMap<>();

    public TenantFlowRegistry(IntegrationFlowContext flowContext) {
        this.flowContext = flowContext;
    }

    public void remove(String tenantId) {
        IntegrationFlowRegistration registration = registrations.remove(tenantId);
        if (registration != null) {
            flowContext.remove(registration.getId());
        }
    }
}
```

This is minimal handle management; the registration method needs to add ID checks, error handling, and an appropriate concurrency policy. In a system where concurrent requests may create or delete flows for the same tenant, use per-tenant locking or synchronization to prevent creating two registrations simultaneously or accidentally removing a registration that was just replaced.

Before removing a flow that is under load, decide how to handle in-flight messages and messages waiting in queues. Stop accepting new requests, wait for or drain tasks that must finish, and only then remove the registration. Do not assume that calling remove will automatically preserve messages sitting in channels or executor queues.

Dynamic registration is runtime state. If the application restarts, dynamic flows are not automatically restored just because they were previously registered. If flow configurations are stored in a database or external configuration store, the application must reload and re-register them during startup.

## 10. Retries, transactions, and error handling in dynamic flows

Dynamically registered flows still use Spring Integration's standard runtime mechanisms. You can attach advice to endpoints, configure transactions on pollers or consumers, choose synchronous/asynchronous channels, and configure error channels as needed.

Key points to decide when building flows from runtime configuration:

- Which endpoints have retries applied, which exceptions are retried, and up to how many attempts.
- At which step transactions start; whether the transaction stays on the processing thread or crosses an executor boundary.
- Whether synchronous errors are returned to the caller or asynchronous errors are published as `ErrorMessage`.
- Whether a per-message error channel is set and which component consumes it.
- Once retries are exhausted, where messages are durably stored and who is authorized to redrive them.

For example, a flow starting from a `DirectChannel` can propagate exceptions from a handler back to the gateway caller. If switched to an `ExecutorChannel`, the handler runs on the executor; the caller may only know that the message was sent, while errors must be handled on an error channel. Changing channels when creating dynamic flows can therefore alter the observable semantics of the API.

With request/reply, do not keep a gateway waiting for an operation that may take several minutes while endpoints actually run asynchronously. Use an accept-request-and-return-operation-ID pattern if business processing is long-running; results can be queried or delivered later via callbacks or events.

## 11. Diagnosing dynamic flows at runtime

When a flow registers successfully but does not process messages as expected, check in order:

1. **Does the registration exist?** Verify the ID was registered and the corresponding handle has not been removed.
2. **Is the input channel correct?** Compare the channel being sent to with the channel the flow starts from. If using a channel bean, verify both the bean name and object reference.
3. **Have endpoints started and subscribed?** Having a registration exist is not enough if endpoints are not active under startup configuration or have been stopped.
4. **Does the channel have the right semantics?** Inspect `DirectChannel`, `QueueChannel`, `PublishSubscribeChannel`, or `ExecutorChannel`, along with associated consumers/pollers and executors.
5. **Are there name collisions?** Check registration IDs, prefixes, endpoint IDs, and channel names when creating multiple flows with the same structure.
6. **Is a reply produced?** Check whether handlers return a payload, whether the reply channel is preserved, and whether gateway/template timeouts are too short.
7. **Where do errors go?** Check exceptions at the caller, error channels in headers, the global `errorChannel`, and poller/adapter error flows.
8. **Is flow removal aligned with lifecycle?** Verify the service does not remove a registration still in use by other requests and does not leave stale handles in the application registry.

When logging activity, include the registration ID, sanitized tenant or configuration key, endpoint ID, channel, message ID, and correlation ID. Avoid logging tokens, connection secrets, or full sensitive payloads. With many dynamic flows, the registration ID in logs helps pinpoint which topology processed a message when an error occurred.

## 12. Common design mistakes

- **Registering a flow without keeping its ID or handle.** Makes it difficult for the application to look up and remove the right flow when configuration changes.
- **Using a single `DirectChannel` input for multiple tenant flows.** Messages may be distributed across subscribers instead of reaching the intended tenant; use a router or separate channels.
- **Assuming a gateway is automatically created per registration.** `IntegrationFlowContext` manages flows; `@MessagingGateway` is a separate proxy and must be configured with the appropriate request channel.
- **Sending messages before the flow is registered.** The channel may have no subscribers yet, or request/reply may have nowhere to be handled.
- **Using a queue without a poller/consumer.** Messages accumulate in the queue without being pulled for processing.
- **Omitting prefixes or stable IDs.** Multiple flows with similar structures can collide on component names.
- **Removing a flow while requests are still running.** Can fail new requests or interrupt in-flight execution.
- **Expecting flows to survive restarts automatically.** Dynamic registrations must be recreated from durable configuration.
- **Leaving flow count unbounded.** Creating flows per request without a reclamation policy can exhaust beans, endpoints, threads, and connection resources.

## 13. Design checklist

Before putting dynamic flows into operation, determine:

- What condition creates a flow, and what condition removes it?
- Which key is the registration ID derived from, and how is uniqueness guaranteed?
- Is the input channel created with the flow or is it a shared bean?
- Do callers send messages directly, use `MessagingTemplate`, or invoke a gateway?
- Does the flow require request/reply or only acknowledgment that the request was received?
- Which thread boundaries do the channels and executors introduce?
- Where are retries, transactions, error channels, and redrive configured?
- How are in-flight or queued messages handled when removing the flow?
- From which configuration are flows restored after an application restart?

When these questions are clearly answered, `IntegrationFlowContext` lets an application alter message flow topologies at runtime while keeping entry points, invocation paths, identification, and per-flow lifecycles under control.
