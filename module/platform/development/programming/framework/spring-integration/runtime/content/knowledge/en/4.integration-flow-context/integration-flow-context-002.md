# Registering an IntegrationFlow by Flow Name

In Spring Integration, most message flows can be declared statically as an `IntegrationFlow` bean. However, some applications only know which flows to create at runtime: each tenant has its own flow, a new connection requires its own processing pipeline, or configuration is loaded after the application has started. In those cases, `IntegrationFlowContext` allows registering an `IntegrationFlow` into the Spring context under an identifier chosen by the application.

This identifier is commonly referred to as the **flow ID** or **flow name**. It helps the application look up and manage the corresponding registration, and can also be used as a prefix for the names of components generated by the DSL. Understanding flow IDs, component IDs, and input channels correctly helps prevent name collisions when multiple dynamic flows coexist.

## 1. Static flows and runtime-registered flows

If the flow structure is known when configuring the application, declaring it with `@Bean` is the simplest approach:

```java
@Configuration
class OrderFlowConfiguration {

    @Bean
    IntegrationFlow orderFlow(OrderHandler handler) {
        return IntegrationFlow.from("orders.input")
            .handle(handler, "handle")
            .get();
    }
}
```

Spring initializes the bean, Spring Integration registers the flow's channels/endpoints, and the context manages their lifecycle. There is no need to hold a registration handle yourself for static flows.

Dynamic flows are appropriate when the number or structure of flows depends on runtime data. For example, a multi-tenant integration system can register an order-processing flow for each tenant after loading tenant configuration. When a tenant is removed, the application destroys that tenant's specific registration.

| Criterion | `@Bean IntegrationFlow` | `IntegrationFlowContext` |
| --- | --- | --- |
| Creation time | During context initialization | Whenever the application explicitly registers one |
| Number of flows | Typically fixed in configuration | Can vary at runtime |
| Identifier | Bean name and component IDs | Registration ID assigned by the application |
| Lifecycle management | Spring context | Application holds `IntegrationFlowRegistration` and destroys it when needed |
| Typical use case | Fixed application pipelines | Flows per tenant, connection, device, or runtime configuration |

You should not turn every static flow into a dynamic flow. Runtime registration adds the responsibility of storing registrations, preventing duplicate IDs, handling registration errors, and cleaning up flows when the corresponding resource ends.

## 2. `IntegrationFlowContext` and flow IDs

`IntegrationFlowContext` is a dedicated registry for registering and removing `IntegrationFlow` instances while the application is running. Instead of manually adding bean definitions via `BeanFactory` or `ApplicationContext`, the application builds the flow and passes it to the registration API:

```java
IntegrationFlowContext.IntegrationFlowRegistration registration = flowContext
    .registration(flow)
    .id("tenant-acme-orders")
    .useFlowIdAsPrefix()
    .register();
```

Key parts:

- `registration(flow)` starts configuring a registration for a flow.
- `id(...)` sets the registration's identifier. This is the flow ID the application uses to distinguish the flow within the context.
- `useFlowIdAsPrefix()` requests using the flow ID as a prefix for the names of components in the flow; this option requires `id(...)` to be set.
- `register()` performs the registration and returns an `IntegrationFlowRegistration` for the application to manage the newly created flow.

`id(...)` is an identifier at the flow-registration level. It is distinct from the ID of a specific endpoint configured inside the DSL, and it does not automatically become the name of a business channel to which external systems send messages. If you need to name a channel, configure the channel explicitly in the flow or use the input channel provided by the registration.

### Choosing a flow ID

A flow ID must be stable and unique within the scope of the application context managing those flows. Any existing registration using an ID must be destroyed before that ID can be reused for a new flow instance. For example:

```java
String flowId = "tenant-" + tenantKey + "-orders";
```

A structured ID makes it easier to find the registration, write logs, and remove the right flow. `tenantKey` should be a validated and normalized identifier key; avoid passing arbitrary request data directly into bean names. If there are multiple flow types for the same tenant, include the flow type in the ID, such as `tenant-acme-orders` and `tenant-acme-invoices`.

Do not reuse the same ID for two coexisting registrations. If the application needs to replace a flow according to new configuration, define a clear replacement strategy: stop/destroy the old registration and then register the new version, or create a versioned ID and shift traffic in a controlled manner. Avoid leaving two flows reading from the same input because the application forgot to destroy the old registration.

## 3. Why is `useFlowIdAsPrefix()` needed?

A single `IntegrationFlow` can create many internal beans: channels, message handlers, endpoints, bridges, and other components. If multiple dynamic flows use the same default component names or identical explicit names, registration can fail due to bean name collisions.

Since Spring Integration 5.0.6, bean names generated for components in a flow have a mechanism to use the flow ID as a prefix. `useFlowIdAsPrefix()` lets you explicitly apply this prefix to components with IDs in the DSL, which is especially useful when registering multiple instances of the same flow whose instances share component IDs. For example, components of the `tenant-acme-orders` flow are placed in a namespace tied to that flow, separate from components of `tenant-globex-orders`.

```java
IntegrationFlowContext.IntegrationFlowRegistration registration = flowContext
    .registration(createOrderFlow(tenant))
    .id("tenant-" + tenant.key() + "-orders")
    .useFlowIdAsPrefix()
    .register();
```

Prefixing resolves component name collisions generated by the flow. It does not replace designing communication channel names between systems. For channels intentionally shared across multiple flows, declare and manage that channel as a separate dependency. For channels private to each flow, prefer having the flow own the channel or naming it specifically per tenant/flow.

A flow ID also does not automatically isolate payloads, headers, or correlation keys. If two flows receive similar messages and share a store or correlation key, the application must still design namespaces for the corresponding runtime data.

## 4. Registering a flow and obtaining the input channel

The example below creates an order-processing flow for a tenant. The flow is built from a dedicated input channel and then registered with a structured ID:

```java
@Component
final class TenantOrderFlowManager {

    private final IntegrationFlowContext flowContext;
    private final Map<String, IntegrationFlowContext.IntegrationFlowRegistration> registrations =
        new ConcurrentHashMap<>();

    TenantOrderFlowManager(IntegrationFlowContext flowContext) {
        this.flowContext = flowContext;
    }

    synchronized MessageChannel register(String tenantKey,
                                         TenantOrderHandler handler) {
        if (registrations.containsKey(tenantKey)) {
            throw new IllegalStateException("Flow already registered for tenant");
        }

        String flowId = "tenant-" + tenantKey + "-orders";
        MessageChannel input = new DirectChannel();

        IntegrationFlow flow = IntegrationFlow.from(input)
            .handle(handler, "handle")
            .get();

        IntegrationFlowContext.IntegrationFlowRegistration registration = flowContext
            .registration(flow)
            .id(flowId)
            .useFlowIdAsPrefix()
            .register();

        registrations.put(tenantKey, registration);
        return input;
    }
}
```

In this example:

1. The manager checks whether the tenant already has a flow.
2. It creates an input channel and builds the flow with the injected handler.
3. It sets the flow ID according to the tenant and business type.
4. It registers the flow, then stores the `IntegrationFlowRegistration` for lifecycle management.
5. It returns the input channel to the component that needs to send messages into the flow.

`DirectChannel` dispatches messages to subscribers on the sender's thread. If the flow needs a queue or asynchronous processing, choose an appropriate channel such as `QueueChannel` or `ExecutorChannel`; registering by flow ID does not by itself change channel threading semantics.

In a real application, you should validate `tenantKey` before constructing the ID, bound the number of flows that can be registered, and ensure the handler is configured for the right tenant. If the channel is created outside the flow as in the example, the manager must retain the exact channel reference corresponding to the registration.

### Obtaining the input channel from the registration

When a flow declares its input channel in a way that allows the registration to manage/resolve the input, you can retrieve the channel from the registration:

```java
IntegrationFlowContext.IntegrationFlowRegistration registration = flowContext
    .registration(IntegrationFlow.from("tenant-acme.orders.input")
        .handle(orderHandler, "handle")
        .get())
    .id("tenant-acme-orders")
    .useFlowIdAsPrefix()
    .register();

MessageChannel inputChannel = registration.getInputChannel();
inputChannel.send(new GenericMessage<>(order));
```

`getInputChannel()` is convenient when the caller does not need to know how the flow creates or resolves its input channel. For a flow starting from a channel object already held by the manager, using that reference directly is also valid. `getMessagingTemplate()` provides a `MessagingTemplate` bound to the input channel when the application wants to send messages via a template.

If a flow does not have an input channel in a form the registration can expose, do not assume `getInputChannel()` always returns a usable channel. Design the flow with a clear input source and check the flow type before exposing a message-sending API.

## 5. Managing multiple flows by tenant or configuration

A manager typically needs to map a business key to a registration:

```java
private final Map<String, IntegrationFlowContext.IntegrationFlowRegistration> registrations =
    new ConcurrentHashMap<>();
```

`IntegrationFlowRegistration` is a nested interface inside `IntegrationFlowContext`. The map lets the manager look up the registration to send data, check management state, or remove the flow. The map key should carry the same meaning as the flow identifier, such as a tenant key or connection key. Do not retain only the `IntegrationFlow` object while discarding the registration handle: the registration is the handle for removing components that were added to the context.

Management principles:

- Check for duplicate keys before registering and handle concurrent requests trying to create the same flow.
- Use a deterministic ID derived from tenant/flow type; log the ID on registration and destruction for traceability.
- Store the registration immediately after registration succeeds.
- If storing the registration or a subsequent configuration step fails, destroy the newly created registration to avoid orphaned flows.
- When a tenant is deleted or a connection ends, retrieve the exact registration and call `destroy()`.
- Enforce a limit on the number of flows, monitor active registration counts, and clean up flows that are no longer used.

Do not register a new flow for every single message. Flow registration creates endpoints and components in the context; it is a runtime structure management operation, not a per-message processing operation. Register according to the lifecycle of the tenant, device, connection, or configuration that needs to be maintained.

## 6. Destroying a registration and flow lifecycle

When a flow is no longer needed, call `destroy()` on the registration:

```java
synchronized void unregister(String tenantKey) {
    IntegrationFlowContext.IntegrationFlowRegistration registration =
        registrations.remove(tenantKey);

    if (registration != null) {
        registration.destroy();
    }
}
```

`destroy()` instructs `IntegrationFlowContext` to remove the flow and the components registered with it from the context, while cleaning up the associated endpoints. This is a critical step to prevent endpoints from continuing to receive messages and to avoid retaining unused beans/channels.

Destroying a flow does not mean all messages being processed in external systems have finished. If the flow uses queues, executors, or asynchronous adapters, the application must define drain policies, timeouts, and in-flight message handling before calling destroy. With `DirectChannel`, sending and processing typically happen synchronously on the sender thread, though downstream steps can still hand off to an executor or queue.

The manager should make removal consistent: remove the registration from the management registry, block new requests from entering the flow, execute the application's stop/drain policy, and then call `destroy()`. If destroy fails, log the error and have an operational mechanism to detect leftover registrations.

When the entire `ApplicationContext` closes, Spring manages the lifecycle of remaining registered beans. Even so, the manager should still remove dynamic flows when the tenant/connection lifecycle ends rather than waiting until application shutdown.

## 7. Configuring registration and component IDs

`IntegrationFlowContext` provides a builder to configure the registration before calling `register()`. Common options include:

| Option | Meaning |
| --- | --- |
| `id(flowId)` | Sets the ID for the registration. |
| `useFlowIdAsPrefix()` | Uses the flow ID as a prefix for component names generated by the flow. |
| `autoStartup(boolean)` | Controls whether the flow starts automatically after registration; defaults to `true`. |
| `register()` | Performs registration and returns the registration handle. |

Example of deferring startup:

```java
IntegrationFlowContext.IntegrationFlowRegistration registration = flowContext
    .registration(flow)
    .id("tenant-acme-orders")
    .useFlowIdAsPrefix()
    .autoStartup(false)
    .register();

// After the application completes the required preparation steps:
registration.start();
```

`IntegrationFlowRegistration` provides `start()` and `stop()` to control the registration's lifecycle. `autoStartup(false)` should only be used when the application plans to call `start()` at an appropriate time. Do not treat stop/start as a safe pause/resume mechanism for every channel: sending behavior while an endpoint is stopped still depends on the channel type and flow topology. When the flow is no longer needed, call `destroy()` to remove the registration and dependent components.

The registration ID, endpoint IDs, and channel names may all appear together in logs, but they serve different purposes:

| Identifier | Scope | Example |
| --- | --- | --- |
| Flow ID | Entire dynamic flow registration | `tenant-acme-orders` |
| Component ID | A specific endpoint/handler within the flow | `validateOrder`, `persistOrder` |
| Channel name | Message communication point between endpoints | `orders.input`, `orders.validated` |
| Correlation ID | A group of messages within a single processing run | `order-run-81` |

Do not use the flow ID in place of a correlation ID. A single flow can process thousands of orders; the correlation ID must distinguish each individual order-processing run within that flow.

## 8. Replacing a flow when configuration changes

Suppose a tenant changes its target endpoint or processing rules. There are two common strategies:

**In-place replacement:** block new work, drain or finish in-flight messages, destroy the old registration, and then register the new flow with the same flow ID. This approach is simple, but requires a brief period where the flow is inactive or a traffic coordination mechanism.

**Parallel versioned registration:** create a new flow with a versioned ID, such as `tenant-acme-orders-v2`, verify the new flow is ready, switch senders to the new input channel, and then drain and destroy the old flow `tenant-acme-orders-v1`. This approach allows a controlled cutover, though the manager must manage both registrations during the transition period.

Do not register two flows with the same ID expecting the new flow to overwrite the old one. Destroy the old registration or use a separate versioned ID, and explicitly shift traffic.

## 9. Observing and diagnosing registrations

When a dynamic flow does not receive messages or continues operating after a tenant has been removed, inspect both the registry and the message path.

| Symptom | Possible cause | Remediation |
| --- | --- | --- |
| Flow registration fails due to duplicate name | Flow ID or component bean name is already in use. | Check existing IDs; use unique IDs and `useFlowIdAsPrefix()`. |
| Flow is registered but receives no messages | Caller sends to the wrong input channel, input channel is not connected to the flow, or endpoints have not started. | Inspect `registration.getInputChannel()`, channel topology, and auto-startup configuration. |
| Two tenants receive each other's messages | Unintended shared input channel or incorrect tenant routing. | Use dedicated input channels or a router checking the tenant key; inspect headers and logs. |
| Old flow continues receiving messages | Old registration was not destroyed or a producer still sends to a shared channel. | Look up the registration by tenant and call `destroy()`; check active producers. |
| Bean/endpoint count grows continuously | Repeated registration per request/message or forgotten cleanup. | Register only per resource lifecycle; monitor registration count and remove expired flows. |
| New registration fails on configuration update | Old flow still holds the ID or component names. | Follow a controlled replacement procedure or use versioned IDs. |
| Messages lost when destroying a flow | Registration destroyed while queues/executors still hold pending messages. | Design drain, timeout, and message forwarding/discard policies before calling destroy. |

Log at least these fields: flow ID, tenant/resource key, register/destroy timestamp, input channel, configuration version, and operation outcome. Useful metrics include current registration count, registration failure count, destroyed flow count, registration age, and pending message count on queued channels.

`IntegrationFlowContext` is a registry in the current process's application context. Registering a flow on one instance does not automatically create the corresponding flow on other instances in a cluster. If the application runs multiple nodes, each node must receive the configuration and perform registration under a consistent strategy; routing messages to the node holding the right flow is the responsibility of the deployment architecture.

## 10. Workflow for registering a flow by name

1. Determine why the flow must be created at runtime; if the structure is fixed, declare it with `@Bean`.
2. Choose a stable resource key and build a unique flow ID combining resource and business type.
3. Construct the `IntegrationFlow` with its input channel, handlers, and injected dependencies.
4. Call `flowContext.registration(flow).id(flowId).useFlowIdAsPrefix().register()`.
5. Store the `IntegrationFlowRegistration` keyed by resource; expose the input channel or messaging template to appropriate producers.
6. Monitor registrations, errors, and the number of active flows.
7. When the resource ends, block new messages, apply the drain policy, and call `registration.destroy()`.
8. When configuration changes, follow a replacement procedure or use versioned IDs with explicit traffic cutover.

## 11. Key takeaways

- `IntegrationFlowContext` registers flows while the application is running; `IntegrationFlowRegistration` is the handle for the application to manage that flow.
- `.id(flowId)` sets the registration's identifier. Flow ID differs from component ID, channel name, and correlation ID.
- `.useFlowIdAsPrefix()` prevents internal component names of dynamic flows from colliding.
- Store the registration after registering and call `destroy()` when the tenant/connection/configuration no longer needs the flow.
- Do not register flows per message; registrations belong to the lifecycle of a resource or runtime configuration.
- A dynamic flow exists only in the application context where it was registered; multi-node clusters require separate registration and routing strategies.
