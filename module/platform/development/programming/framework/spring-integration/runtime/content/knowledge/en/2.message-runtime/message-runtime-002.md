# MessageHeaders, message id, and timestamp

In Spring Integration, a message traveling through channels and endpoints always carries two parts: the **payload** containing the data to be processed, and the **headers** containing metadata describing the message. The payload answers the question "what data is being processed"; headers help the runtime and application know where the message came from, how it should be routed or correlated, and under what identifier it is being observed.

`MessageHeaders` is where that metadata is stored. Two default headers that must be clearly understood are `id` and `timestamp`: `id` identifies a message instance, while `timestamp` records the time the message was created. Understanding the lifecycle of these two values helps with reading logs, tracing messages through a flow, and avoiding misusing them as business identifiers or event occurrence times.

After this lesson, you will be able to:

- Read payloads and headers from `Message<T>`.
- Explain the role, data type, and lifecycle of `MessageHeaders.ID` and `MessageHeaders.TIMESTAMP`.
- Create new messages, copy headers, and recognize when ID/timestamp are regenerated.
- Distinguish between message ID, correlation ID, business ID, and event time when tracking a flow.

## 1. A message consists of payload and headers

Spring Messaging defines a message through the `Message<T>` interface. A message has a payload of type `T` and a `MessageHeaders` object:

```text
Message<T>
├── payload: T
└── headers: MessageHeaders
    ├── id
    ├── timestamp
    └── other headers
```

For example, when a flow receives an order, the payload can be `Order`; headers can contain `source`, `tenantId`, `correlationId`, or routing information. This information adds context to the payload without turning it into fields of the business object.

```java
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.support.MessageBuilder;

Message<Order> message = MessageBuilder
        .withPayload(order)
        .setHeader("source", "checkout")
        .setHeader("tenantId", "tenant-01")
        .build();

Order payload = message.getPayload();
MessageHeaders headers = message.getHeaders();
```

Channels pass `Message<?>` between producers and consumers. A `DirectChannel`, `QueueChannel`, or `ExecutorChannel` has different delivery mechanics and effects on execution threads, but the message an endpoint receives still contains both payload and headers. Therefore, headers are metadata attached to the message during orchestration, not a shared state store of the channel.

## 2. MessageHeaders is immutable metadata

`MessageHeaders` implements `Map<String, Object>`, so headers can be read by name. However, this map is **immutable**: you cannot call `put`, `remove`, or directly mutate a header after the message has been created. Attempting to modify the map will fail with `UnsupportedOperationException`.

To change metadata, build a new message with `MessageBuilder` or use a dedicated endpoint such as a header enricher. This preserves the immutable message model: a message that has been dispatched cannot have its metadata silently altered by a consumer.

```java
String source = message.getHeaders().get("source", String.class);
Object tenant = message.getHeaders().get("tenantId");
```

When you know the expected data type, use the `get(name, Type.class)` overload. This explicitly states the expected type and avoids manual casting. For application-defined headers, agree on the name, data type, and meaning between producer and consumer.

An immutable headers map does not mean every object placed inside is automatically immutable. If a header contains a mutable `List`, `Map`, or custom object, code elsewhere can still modify that object if it holds a reference. Prefer simple, immutable, and serializable values when the message needs to pass through a message store or system boundary.

## 3. Two default headers: id and timestamp

Spring Messaging provides standard header names via constants in `MessageHeaders`, avoiding arbitrary string literals:

| Header | Data type | Meaning |
|---|---|---|
| `MessageHeaders.ID` | `UUID` | Identifier of a message instance. |
| `MessageHeaders.TIMESTAMP` | `Long` | Time the message was created, in milliseconds since the Unix epoch. |

You can read these two values via dedicated getters:

```java
import java.time.Instant;
import java.util.UUID;

UUID messageId = message.getHeaders().getId();
Long timestampMillis = message.getHeaders().getTimestamp();

Instant createdAt = timestampMillis == null
        ? null
        : Instant.ofEpochMilli(timestampMillis);
```

Normally, the framework generates both headers automatically when creating a message. `id` defaults to a UUID generated by the configured ID generator mechanism. `timestamp` is the system clock time when the headers were constructed. The getters can be annotated as nullable, so shared code or code working with deserialized messages should handle missing values.

These two headers are read-only headers in normal message creation flows. Do not use `setHeader("id", ...)` or `setHeader("timestamp", ...)` to assign arbitrary values. `MessageBuilder` does not allow overwriting these read-only headers; when creating a new message, the framework manages the ID and timestamp of the new instance.

### 3.1. Message ID identifies an instance

The Message ID answers the question: **which message instance is this?** It is useful when writing logs, reconciling a delivery attempt, or recognizing which message an endpoint has processed.

ID is not an order ID, customer ID, or idempotency key. One order can generate multiple messages over its processing lifecycle; each message instance has its own ID. Conversely, if you need to recognize multiple messages belonging to the same business operation, use a business ID or correlation ID with stable semantics.

The Message ID also does not represent processing order. UUIDs do not indicate which message arrived earlier or later, and IDs should not be used to sort messages.

### 3.2. Timestamp records the message creation time

Timestamp is represented as milliseconds since `1970-01-01T00:00:00Z` (Unix epoch). It can be converted to `Instant` for logging or display:

```java
Long value = message.getHeaders().getTimestamp();
if (value != null) {
    log.debug("message createdAt={}", Instant.ofEpochMilli(value));
}
```

This timestamp is the time the message was created in the runtime, not necessarily the time the user placed the order, the time an event occurred in the source system, or the time the consumer began processing. If you need to preserve business time, pass a separate header such as `eventCreatedAt` or store that timestamp in the payload.

Timestamp uses the machine's wall-clock time. Clocks can be synchronized or adjusted, and two nodes can experience clock skew. Therefore, do not use timestamp as a high-precision duration timer or as the sole basis for ordering messages across multiple machines.

## 4. ID and timestamp change when a new message is created

An important point in Spring Integration is that a message is treated as immutable. When a component creates a new message based on an old message, that is a new message instance. `id` and `timestamp` are regenerated for the new instance; other business headers may be copied depending on the API and configuration.

For example, `MessageBuilder.fromMessage(...)` initializes the builder from the input message's payload and headers. When `build()` is called, the builder creates a new message. The two read-only headers `id` and `timestamp` are not copied to overwrite the new message's values:

```java
Message<Order> normalized = MessageBuilder
        .fromMessage(message)
        .setHeader("validated", true)
        .build();

UUID originalId = message.getHeaders().getId();
UUID normalizedId = normalized.getHeaders().getId();
// normalized is a new message instance with a new ID.
```

Headers such as `source` or `tenantId` are copied from the input message unless the builder removes or replaces them. The `validated` header is added to the new message. The headers map of the original message remains unchanged.

Conversely, if an endpoint forwards the original message as-is without building a new instance, the existing ID and timestamp remain attached to that message. When reading logs, determine whether an endpoint creates a new message or merely forwards the message before concluding why the ID or timestamp changed.

This rule also explains why timestamp cannot always measure total time from the start of the flow. If a transformer or enricher creates a new message mid-flow, the timestamp reflects that new creation. To measure latency, use metrics/observation or tracing mechanisms; if measuring manually, clearly define the start and end milestones.

## 5. Distinguishing message ID, correlation ID, and business IDs

Three types of identifiers often appear alongside each other but serve different purposes:

| Value | Question answered | Example usage |
|---|---|---|
| Message ID (`id`) | Which message instance is this? | Correlating logs for a single delivery. |
| Correlation ID (`correlationId`) | Which group or business flow does this message belong to? | Grouping messages produced by a splitter for an aggregator to combine. |
| Business ID (`orderId`) | Which business entity is being processed? | Looking up an order in the database or business API. |
| Trace ID | Which trace do these distributed operations belong to? | Tracking a request across multiple services and spans. |

Spring Integration provides headers for correlation and sequence, such as `CORRELATION_ID`, `SEQUENCE_NUMBER`, and `SEQUENCE_SIZE` in `IntegrationMessageHeaderAccessor`. For a group of messages created by a splitter, correlation ID identifies them as belonging to the same group; sequence number and sequence size describe position and group size. These values do not replace the message ID of each individual element.

For example, an order `order-42` can produce three child messages:

```text
orderId = order-42
correlationId = group-7
├── message id = UUID-A, sequenceNumber = 1
├── message id = UUID-B, sequenceNumber = 2
└── message id = UUID-C, sequenceNumber = 3
```

The three messages have different IDs but share the same correlation ID and business ID. When the aggregator emits the result message, that result is again a new message instance with its own ID and timestamp. Therefore, operational logs should record the relevant identifiers together rather than logging only `id`.

## 6. Observing headers in a message flow

You can receive the full `Message<?>` in a consumer to inspect both payload and metadata:

```java
@ServiceActivator(inputChannel = "orders")
public void handle(Message<Order> message) {
    UUID id = message.getHeaders().getId();
    Long timestamp = message.getHeaders().getTimestamp();
    String tenantId = message.getHeaders().get("tenantId", String.class);

    log.info("received messageId={}, timestamp={}, tenantId={}, orderId={}",
            id,
            timestamp,
            tenantId,
            message.getPayload().getId());

    // Process the order payload.
}
```

When diagnosing a flow, compare IDs at message reception points:

1. Log ID, timestamp, correlation ID, and business ID at the flow entry point.
2. Log the same values again after transformers, enrichers, or handlers that create new messages.
3. If the ID changes, check which component just created a new message and how it copies headers.
4. If the timestamp increases at a stage, verify whether it is the creation time of a new message or a business timestamp.
5. If the message passes through an adapter or broker, check the adapter's header mapping; do not assume all internal headers are transferred intact to an external protocol.

Channels affect when a consumer receives and processes a message. With `DirectChannel`, the consumer is typically invoked synchronously on the sending thread. With `QueueChannel` or `ExecutorChannel`, the message may wait or be processed on a different thread. The message's timestamp remains the previously created timestamp unless a component rebuilds the message. Thus, a message waiting a long time in a queue does not automatically receive a new timestamp when the consumer begins running.

When a message is saved to a message store or sent over an external protocol, header persistence/transfer also depends on data types and serializer/header mapper configuration. Use headers with stable, serializable data types, and explicitly verify which headers are preserved across system boundaries.

## 7. Common pitfalls and how to avoid them

| Error-prone practice | Why it is unsuitable | How to handle it |
|---|---|---|
| Using `id` as `orderId` or duplicate-processing key | ID identifies a message instance and can change when a new message is created. | Use a separate business ID or idempotency key. |
| Using `timestamp` as the business occurrence time | Timestamp records when the message was created in the runtime. | Pass a separate `eventCreatedAt` and specify timezone/format clearly. |
| Calling `headers.put(...)` directly | `MessageHeaders` is immutable. | Use `MessageBuilder` or a header enricher. |
| Trying to manually set `id`/`timestamp` | These are read-only headers managed by the framework. | Use a separate header if you need an application-controlled ID or timestamp. |
| Logging only the message ID | Does not show whether messages belong to the same business operation. | Also log correlation ID, business ID, and trace ID when available. |
| Placing mutable objects or sensitive data in headers | Can cause unexpected mutations, serialization errors, or data leaks in logs. | Prefer small, immutable metadata; log only necessary fields. |

A note when investigating issues: two logs with the same message ID usually indicate the same message instance observed at multiple points; two logs with different IDs are not enough to conclude they represent two different business operations. Cross-check correlation ID and business ID as well.

## 8. Self-check

**Scenario:** A flow receives an `Order`, adds the header `validated=true`, and then sends the message to a `QueueChannel`. The consumer logs a different ID than the ID logged at the start of the flow.

1. If the header-adding step creates a message via `MessageBuilder.fromMessage(...).build()`, is a new ID normal behavior?
2. If the consumer receives the message after waiting several seconds in the queue, does the timestamp automatically update to when the consumer starts processing?
3. If you want to find all messages related to the same order, which header should you check?

**Suggested answers:** (1) Yes. The builder creates a new message instance, so ID and timestamp are regenerated. (2) No. The timestamp remains the most recent message creation time unless a subsequent step creates a new message. (3) Use a business ID such as `orderId`; if you need to group messages within a processing branch, use correlation ID. Message ID remains useful for tracing individual instances.
