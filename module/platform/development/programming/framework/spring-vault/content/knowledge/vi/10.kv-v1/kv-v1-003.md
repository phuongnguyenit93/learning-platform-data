# Mount path và đường dẫn secret tương đối trong KV v1

## Mục tiêu học tập

Sau bài học, bạn có thể:

- Phân biệt **mount path** của KV secrets engine với **đường dẫn secret tương đối** và đường dẫn Vault đầy đủ.
- Xây dựng đúng đường dẫn khi dùng HashiCorp Vault CLI, REST API và **Spring Vault** (`VaultTemplate`, `VaultOperations`, `VaultKeyValueOperations`).
- Giải thích vì sao `opsForKeyValue(mount, KeyValueBackend.KV_1)` nhận tên mount, còn `get`, `put`, `list`, `delete` nhận đường dẫn nằm **bên trong** mount.
- Viết policy truy cập theo đúng đường dẫn thực tế, xác định lỗi lặp mount/nhầm KV v2 và kiểm thử tích hợp.

## 1. Ba loại đường dẫn dễ bị nhầm

HashiCorp Vault quản lý nhiều **secrets engine** được gắn (*mount*) vào các tiền tố đường dẫn khác nhau. Trong chương **KV phiên bản 1**, ta xét một KV v1 engine được mount ở `kv-demo/`.

Giả sử ứng dụng Java cần đọc tài khoản thử nghiệm của dịch vụ đơn hàng tại `apps/orders/database`:

```text
             Vault (logical API)
                     |
               kv-demo/                      ← mount path
                     |
                  apps/
                     |
                  orders/
                     |
                 database                    ← secret path tương đối

  Đường dẫn secret đầy đủ: kv-demo/apps/orders/database
```

Ta có ba khái niệm:

| Khái niệm | Ví dụ | Dùng khi nào? |
| --- | --- | --- |
| **Mount path** | `kv-demo` (thường được hiển thị thành `kv-demo/`) | Chỉ ra **secrets engine** nào xử lý request. Truyền vào `opsForKeyValue` của Spring Vault. |
| **Đường dẫn secret tương đối** | `apps/orders/database` | Chỉ ra bản secret **bên trong mount**. Truyền vào `kv.get`, `kv.put`, `kv.delete`. |
| **Đường dẫn Vault đầy đủ** | `kv-demo/apps/orders/database` | Kết hợp mount + secret path. Dùng trong Vault ACL policy và với `VaultOperations.read` cấp thấp. |
| **Đường dẫn HTTP REST** | `/v1/kv-demo/apps/orders/database` | Đường dẫn API của Vault, bao gồm tiền tố HTTP `/v1/`; client Spring Vault tự thêm tiền tố API. |

Công thức với **KV v1**:

```text
fullLogicalPath = mountPath + "/" + relativeSecretPath
httpPath        = "/v1/" + fullLogicalPath
```

Trong ví dụ:

```text
mountPath          = kv-demo
relativeSecretPath = apps/orders/database
fullLogicalPath    = kv-demo/apps/orders/database
httpPath           = /v1/kv-demo/apps/orders/database
```

**Không nhầm `/v1` với tên mount.** `/v1` là phần của HTTP API của Vault, không phải vị trí lưu secret và cũng không phải dữ liệu truyền vào `opsForKeyValue`.

### Mount path không phải thư mục trên ổ đĩa

Vault dùng **không gian đường dẫn logic**. Gắn engine tại `kv-demo/` nghĩa là các request có tiền tố đó được chuyển cho KV engine tương ứng; nó không có nghĩa Vault tạo một thư mục `kv-demo` trên hệ điều hành. Phần `apps/orders/database` là tên logic của một secret. Dấu `/` tạo cấu trúc tiền tố giúp tổ chức và liệt kê, không mặc định biến từng thành phần thành một file hay thư mục thật.

Một secret KV v1 tại `apps/orders/database` chứa **một đối tượng dữ liệu hiện hành**, có thể gồm nhiều trường:

```json
{
  "username": "demo_orders",
  "password": "not-a-real-password",
  "engine": "postgresql"
}
```

Ở đây `database` là phần cuối của **đường dẫn secret**; `username`, `password`, `engine` là **các trường dữ liệu** của cùng secret, không phải ba secret con khác nhau.

## 2. Mount tách biệt các không gian bí mật

Vault có thể có nhiều KV engine khác nhau, chẳng hạn:

```text
Vault
├── kv-dev/  (KV v1)
│   └── apps/orders/database
└── kv-prod/ (KV v1)
    └── apps/orders/database
```

Cùng đường dẫn tương đối `apps/orders/database` nhưng:

- `kv-dev/apps/orders/database` và `kv-prod/apps/orders/database` là **hai đường dẫn đầy đủ khác nhau**.
- Gọi vào mount `kv-dev` không tự đọc secret của `kv-prod`.
- Mỗi mount có cấu hình engine và ACL liên quan; tên mount tự nó **không chứng minh** đó là KV v1 hay KV v2.

Vì vậy, khi lỗi đọc sai secret xảy ra, cần xác minh cả **mount** và **đường dẫn tương đối**. Chỉ kiểm tra phần `apps/orders/database` là chưa đủ.

### Tạo và kiểm tra mount KV v1 trong môi trường thử nghiệm

Nếu chưa có mount và bạn được phép quản trị Vault thử nghiệm:

```bash
vault secrets enable -path=kv-demo -version=1 kv
```

Lệnh này gắn một **KV engine phiên bản 1** ở `kv-demo/`. Nếu mount đã tồn tại, không chạy lại lệnh `enable`; kiểm tra cấu hình hiện tại:

```bash
vault secrets list -detailed
```

Trong kết quả, tìm mount `kv-demo/`, xác nhận loại engine là `kv` và cấu hình phiên bản là `1`. Không mặc định một mount tên `secret/` hay `kv/` có phiên bản cụ thể.

## 3. Truy cập bằng Spring Vault: mount riêng, secret riêng

Trong ứng dụng Java, `VaultTemplate` triển khai interface `VaultOperations` và xử lý các request tới Vault bằng cấu hình kết nối/xác thực đã có. Để thao tác KV v1 theo API chuyên biệt, hãy lấy `VaultKeyValueOperations`:

```java
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;

VaultKeyValueOperations kv = vaultOperations.opsForKeyValue(
        "kv-demo",                // mount path
        KeyValueBackend.KV_1     // phiên bản engine của mount
);
```

**Điểm cần nhớ:** `opsForKeyValue("kv-demo", KV_1)` cố định mount cho đối tượng `kv`; mọi thao tác sau đó nhận **đường dẫn tương đối dưới mount**.

```java
// Đúng: truyền đường dẫn tương đối
kv.get("apps/orders/database");

// Sai: đã lặp lại tên mount
kv.get("kv-demo/apps/orders/database");

// Sai: đã đưa tiền tố HTTP API vào API Java
kv.get("/v1/kv-demo/apps/orders/database");

// Sai với KV v1 ở kv-demo: /data/ là phân đoạn API của KV v2
kv.get("data/apps/orders/database");
```

Với một đối tượng `kv` được tạo từ mount `kv-demo`, lệnh `kv.get("apps/orders/database")` tương ứng với request đọc KV v1:

```http
GET /v1/kv-demo/apps/orders/database HTTP/1.1
X-Vault-Token: <token-được-client-quản-lý>
```

Đây là **minh họa đường dẫn giao thức**, không phải mẫu yêu cầu ghi token vào mã nguồn. Spring Vault quản lý việc gửi thông tin xác thực qua client đã được cấu hình; trong ứng dụng thật, nên dùng phương thức xác thực theo workload, ví dụ AppRole hoặc Kubernetes auth, tùy môi trường triển khai.

### So sánh với VaultOperations.read cấp thấp

Một nguồn nhầm lẫn phổ biến là dùng lẫn hai cấp API:

```java
// API KV chuyên biệt: mount riêng, đường dẫn secret tương đối.
VaultKeyValueOperations kv =
        vaultOperations.opsForKeyValue("kv-demo", KeyValueBackend.KV_1);
kv.get("apps/orders/database");

// API Vault cấp thấp: truyền đường dẫn Vault đầy đủ.
vaultOperations.read("kv-demo/apps/orders/database");
```

`VaultOperations.read` làm việc với đường dẫn logic đầy đủ, trong khi `VaultKeyValueOperations.get` làm việc với đường dẫn tương đối vì mount đã được chọn trước đó. Cả hai không nhận tiền tố HTTP `/v1/`. Đối với thao tác KV thông thường, API chuyên biệt giúp tách rõ mount và dữ liệu, đồng thời giúp triển khai chọn đúng backend.

## 4. Ví dụ Java hoàn chỉnh

Đoạn mã giả định ứng dụng Spring đã có bean `VaultOperations` được cấu hình kết nối, xác thực và chính sách truy cập Vault. Ví dụ sử dụng một secret KV v1 chứa ba trường `username`, `password`, `engine` như phần đầu bài.

```java
import java.util.Map;

import org.springframework.stereotype.Service;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.support.VaultResponse;

@Service
public class OrdersDatabaseSecretReader {

    private static final String MOUNT = "kv-demo";
    private static final String RELATIVE_PATH = "apps/orders/database";

    private final VaultKeyValueOperations kv;

    public OrdersDatabaseSecretReader(VaultOperations vaultOperations) {
        this.kv = vaultOperations.opsForKeyValue(MOUNT, KeyValueBackend.KV_1);
    }

    public DatabaseCredentials loadRequired() {
        // Chỉ dùng đường dẫn tương đối: Spring Vault đã biết mount.
        VaultResponse response = kv.get(RELATIVE_PATH);
        if (response == null || response.getData() == null) {
            throw new IllegalStateException(
                    "Không tìm thấy cấu hình Vault tại " + MOUNT + "/" + RELATIVE_PATH);
        }

        Map<String, Object> data = response.getData();
        String user = requiredString(data, "username");
        String password = requiredString(data, "password");

        // Không ghi các giá trị secret vào log hoặc thông báo lỗi.
        return new DatabaseCredentials(user, password);
    }

    private static String requiredString(Map<String, Object> data, String field) {
        Object value = data.get(field);
        if (!(value instanceof String) || ((String) value).isBlank()) {
            throw new IllegalStateException("Secret thiếu trường bắt buộc: " + field);
        }
        return (String) value;
    }

    public record DatabaseCredentials(String username, String password) {}
}
```

Ví dụ dùng Java hỗ trợ `record` (Java 16 trở lên). `DatabaseCredentials` là kiểu trả về để chuyển dữ liệu đến thành phần kết nối cơ sở dữ liệu cần dùng; trong ứng dụng thực tế, cần tránh vô tình log object này hoặc để lộ mật khẩu qua cơ chế in giá trị mặc định của `record`.

Chú ý ba đặc điểm của cách triển khai:

1. Hai hằng `MOUNT` và `RELATIVE_PATH` đại diện cho **hai phần khác nhau** của đường dẫn. Không đưa `MOUNT` vào đối số của `kv.get`.
2. Khi không tìm thấy secret, `get` có thể trả `null`. Phải kiểm tra trước khi lấy `getData()`, và kiểm tra cả các trường dữ liệu cần thiết.
3. Lỗi không tìm thấy secret khác với lỗi **token hết hạn, thiếu quyền hoặc mạng/TLS**. Không nên bắt mọi ngoại lệ từ Vault rồi coi như secret rỗng.

Ứng dụng có thể thay mount `kv-demo` bằng mount dành riêng cho môi trường triển khai, nhưng cần thay **đồng bộ** cấu hình mount và policy ACL. Đường dẫn tương đối chỉ thay đổi khi cách tổ chức dữ liệu bên trong mount thay đổi.

## 5. CLI và REST API dùng đường dẫn nào?

Với Vault CLI hiện đại, tham số `-mount` nêu rõ mount; phần sau là **secret path tương đối**:

```bash
# Tạo dữ liệu giả ở đúng mount và đúng đường dẫn tương đối.
vault kv put -mount=kv-demo apps/orders/database \
  username="demo_orders" password="not-a-real-password" engine="postgresql"

# Đọc cùng secret.
vault kv get -mount=kv-demo apps/orders/database

# Liệt kê các tên con ngay dưới apps/orders.
vault kv list -mount=kv-demo apps/orders

# Xóa secret thử nghiệm.
vault kv delete -mount=kv-demo apps/orders/database
```

Trong CLI, cú pháp tương đương có thể kết hợp mount và đường dẫn thành một full path tùy phiên bản/cách gọi, nhưng dùng `-mount=kv-demo` giúp tách rõ hai phần và khớp trực tiếp với tư duy dùng `VaultKeyValueOperations`.

Bảng đối chiếu cùng một thao tác:

| Mục đích | Spring Vault KV API | Vault CLI | KV v1 REST path |
| --- | --- | --- | --- |
| Đọc secret | `kv.get("apps/orders/database")` | `vault kv get -mount=kv-demo apps/orders/database` | `GET /v1/kv-demo/apps/orders/database` |
| Ghi/thay thế | `kv.put("apps/orders/database", data)` | `vault kv put -mount=kv-demo apps/orders/database ...` | `POST /v1/kv-demo/apps/orders/database` |
| Liệt kê tên ở tiền tố | `kv.list("apps/orders")` | `vault kv list -mount=kv-demo apps/orders` | `LIST /v1/kv-demo/apps/orders` |
| Xóa secret | `kv.delete("apps/orders/database")` | `vault kv delete -mount=kv-demo apps/orders/database` | `DELETE /v1/kv-demo/apps/orders/database` |

Không truyền tiền tố `/v1/` cho phương thức của `VaultOperations`/`VaultKeyValueOperations`: đó là phần đường dẫn được HTTP client ghép khi gửi request.

### Liệt kê tên khác với đọc nội dung

`kv.list("apps/orders")` trả về tên các mục con tại tiền tố đó, chẳng hạn `database`, chứ không trả `username` hay `password`. Khi trong cây có cấp con, Vault có thể hiển thị tên tiền tố với dấu `/` ở cuối, ví dụ `orders/`, để phân biệt với tên secret trực tiếp.

Đường dẫn dùng khi **list** vì thế thường là một *tiền tố cha*, còn đường dẫn dùng khi **get** là vị trí của secret cần đọc. Quyền `list` và `read` là hai capability độc lập của Vault.

## 6. ACL policy dùng đường dẫn đầy đủ

Dù `VaultKeyValueOperations.get` chỉ nhận phần tương đối, **ACL policy** của Vault áp dụng vào đường dẫn logic **đầy đủ**, gồm cả mount.

Policy chỉ cho workload đơn hàng đọc secret được giao:

```hcl
path "kv-demo/apps/orders/database" {
  capabilities = ["read"]
}
```

Nếu nghiệp vụ cần liệt kê tên ở tiền tố `apps/orders`:

```hcl
path "kv-demo/apps/orders" {
  capabilities = ["list"]
}
```

Chỉ cấp `list` khi thật sự cần biết tên các secret; việc liệt kê có thể làm lộ cấu trúc tên dù không lộ nội dung. Quy trình cập nhật secret sẽ cần `create`/`update` ở đường dẫn đích, quy trình xóa cần `delete`; không mở rộng quyền cho workload chỉ đọc.

Ví dụ một policy **sai** khi định cấp quyền đọc ở KV v1:

```hcl
# Sai nếu mount KV v1 là kv-demo/:
path "kv-demo/data/apps/orders/database" {
  capabilities = ["read"]
}
```

Phần `data/` là thành phần giao thức thường thấy ở **KV v2**. Với KV v1, nó không được tự chèn vào đường dẫn ACL. Nếu người quản trị cấp sai policy, code có thể nhận lỗi quyền truy cập dù phần tên secret trong ứng dụng trông hợp lý.

Một điểm nữa: danh tính workload phải xác thực thành công trước khi policy được xét. Token có thời hạn (TTL) và có thể bị gia hạn hoặc thu hồi, nhưng vòng đời token **không làm thay đổi** bản dữ liệu tĩnh ở đường dẫn KV v1. Bản secret KV v1 không có lease tự động tương tự credential động. Các API Transit encryption và PKI trong hệ sinh thái Vault phục vụ bài toán mã hóa và cấp chứng chỉ khác với lưu một secret KV.

## 7. Khi chọn sai phiên bản backend

`KeyValueBackend.KV_1` và `KeyValueBackend.KV_2` quyết định cách Spring Vault tạo URL request tương ứng với engine.

Với cùng tên mount `kv-demo` và đường dẫn tương đối `apps/orders/database`:

```text
KV v1: GET /v1/kv-demo/apps/orders/database
KV v2: GET /v1/kv-demo/data/apps/orders/database
```

Sự khác biệt ở `data/` thuộc cấu trúc API của **KV v2**. Nếu mount đang là KV v1 nhưng ứng dụng chọn `KV_2`, request bị gửi vào đường dẫn không đại diện cho secret v1 mong muốn. Ngược lại, chọn `KV_1` trên mount KV v2 cũng không dùng đúng endpoint đọc dữ liệu v2.

**Không dự đoán phiên bản từ tên mount.** Trước khi dùng `KV_1`, kiểm tra cấu hình thật với `vault secrets list -detailed` hoặc kênh cấu hình mà đội vận hành cung cấp.

## 8. Các lỗi đường dẫn thường gặp

| Triệu chứng | Nguyên nhân điển hình | Cách sửa |
| --- | --- | --- |
| CLI đọc được nhưng Java không đọc được | Java dùng `kv.get("kv-demo/apps/orders/database")` sau khi đã chọn mount `kv-demo`. | Chỉ truyền `"apps/orders/database"` vào `kv.get`. |
| Lỗi không tìm thấy do đường dẫn có `/v1/` | Đưa HTTP API path vào tham số của Spring Vault. | Bỏ `/v1/`; Spring Vault quản lý prefix HTTP. |
| Không đọc được vì thêm `data/` | Áp dụng cú pháp endpoint KV v2 cho KV v1. | Kiểm tra phiên bản mount; với KV v1 không tự thêm `data/`. |
| Đọc được tên secret nhưng không đọc được giá trị | Chỉ có quyền `list` trên tiền tố, thiếu `read` ở đường dẫn secret. | Bổ sung `read` tối thiểu ở full logical path cần đọc. |
| `get` được nhưng `list` báo permission denied | Policy có `read` cho secret, thiếu `list` ở đường dẫn cha. | Cấp `list` riêng nếu nghiệp vụ cần. |
| Truy cập đúng phần tương đối nhưng vẫn là dữ liệu khác | Chọn nhầm mount, ví dụ `kv-dev` thay vì `kv-prod`. | Xác minh đồng thời mount, environment và đường dẫn tương đối. |
| Đọc không thành công sau khi thay token | Token hết hạn/không có quyền hoặc cấu hình auth chưa đúng. | Kiểm tra auth method, chính sách workload, mạng/TLS; không ghi token ra log. |
| Ghi nhầm đường dẫn làm thiếu trường | `put` đã gửi object không đầy đủ hoặc ghi đè một secret khác. | Kiểm tra tên mount/relative path và gửi đầy đủ các trường cần lưu. |

### Quy tắc đặt tên và xử lý chuỗi đường dẫn

- Chọn một quy ước rõ ràng, ví dụ `apps/<service>/<purpose>`, và dùng thống nhất giữa CLI, Java và ACL.
- Không coi đường dẫn tương đối là đường dẫn file của hệ điều hành; dấu `/` tổ chức tên logic trong Vault.
- Không tự ghép hoặc cắt chuỗi tùy tiện trong nhiều nơi. Đặc biệt, tránh đưa lặp mount, đưa `/v1/` hoặc dấu `/` đầu đường dẫn vào API KV.
- Phân biệt chữ hoa/chữ thường theo tên đường dẫn đã ghi, ví dụ `apps/Orders/database` không nên được mặc định là cùng một secret với `apps/orders/database`.
- Không cho người dùng cuối truyền trực tiếp đường dẫn tùy ý vào tác vụ đọc secret có quyền rộng. Dùng đường dẫn được cấu hình rõ ràng, kết hợp policy giới hạn quyền.

## 9. Bài thực hành kiểm tra end-to-end

Thực hiện trong Vault thử nghiệm, dùng **dữ liệu giả** và không sửa secret môi trường thật.

**Bước 1 — Tạo mount đúng phiên bản.** Nếu chưa tồn tại, bật KV v1 ở `kv-demo` và xác nhận bằng `vault secrets list -detailed`.

**Bước 2 — Ghi một secret.** Dùng:

```bash
vault kv put -mount=kv-demo apps/orders/database \
  username="demo_orders" password="not-a-real-password" engine="postgresql"
```

**Bước 3 — Đọc bằng Java.** Khởi tạo `VaultKeyValueOperations` với mount `kv-demo` và `KV_1`, gọi `kv.get("apps/orders/database")`. Xác nhận nhận được `username`, `password` và `engine`.

**Bước 4 — So sánh cấp API.** Dùng cùng `VaultOperations` gọi `read("kv-demo/apps/orders/database")`; xác nhận full path ở cấp thấp tương ứng với mount + relative path ở cấp KV.

**Bước 5 — Thử một lỗi có chủ đích.** Gọi `kv.get("kv-demo/apps/orders/database")` và quan sát request bị nhắm sai đường dẫn. Sửa về `kv.get("apps/orders/database")` rồi xác minh đọc thành công.

**Bước 6 — Kiểm tra quyền.** Dùng token workload chỉ có `read` trên `kv-demo/apps/orders/database`. Đọc phải thành công; `list("apps/orders")` chỉ thành công khi policy có quyền `list` tương ứng. Lỗi quyền và lỗi secret không tồn tại phải được phân biệt.

**Bước 7 — Dọn dữ liệu thử nghiệm.** Dùng danh tính có quyền `delete` xóa đúng đường dẫn `apps/orders/database` của mount `kv-demo` và xác nhận lần đọc tiếp theo không còn dữ liệu.

Nên đưa các bước đọc đúng mount, đọc sai mount, đọc sai phiên bản và kiểm tra ACL vào kiểm thử tích hợp với Vault thử nghiệm (có thể dùng Testcontainers). Mock interface chỉ kiểm chứng lời gọi Java, chưa chứng minh request thực tế được định tuyến vào đúng secrets engine. Không log giá trị secret/token trong đầu ra test, báo lỗi hoặc công cụ giám sát.

## Câu hỏi tự kiểm tra

1. Với mount `kv-demo` và relative path `apps/orders/database`, `kv.get` cần nhận chuỗi nào? `VaultOperations.read` cần nhận chuỗi nào?
2. Vì sao `kv.get("kv-demo/apps/orders/database")` là sai khi `kv` đã được khởi tạo bằng `opsForKeyValue("kv-demo", KV_1)`?

## Tổng kết

Đối với **Spring Vault truy cập KV phiên bản 1**, luôn tách rõ hai phần: **mount path** xác định secrets engine, còn **đường dẫn secret tương đối** xác định secret bên trong engine. `VaultOperations.opsForKeyValue("kv-demo", KeyValueBackend.KV_1)` chọn mount; `kv.get("apps/orders/database")` chỉ nhận phần tương đối. Trong khi đó, `VaultOperations.read` và ACL policy dùng đường dẫn logic đầy đủ `kv-demo/apps/orders/database`; HTTP REST mới thêm `/v1/`. Phân biệt đúng các lớp đường dẫn giúp tránh lỗi nhân đôi mount, nhầm API KV v2, cấp sai quyền và đọc nhầm môi trường.
