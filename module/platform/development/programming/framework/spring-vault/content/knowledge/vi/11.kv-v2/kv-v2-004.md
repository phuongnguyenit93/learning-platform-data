# KV v2: Đường dẫn logic so với endpoint `data`, `metadata`, `delete` và `destroy`

## Mục tiêu

Trong **Spring Vault**, ứng dụng Java thường làm việc với một **đường dẫn secret logic** như `apps/payment` thông qua `VaultTemplate` hoặc `VaultOperations`. Tuy nhiên, HashiCorp Vault **KV secrets engine phiên bản 2 (KV v2)** lại định tuyến các thao tác HTTP theo nhiều nhánh riêng: `data/`, `metadata/`, `delete/`, `undelete/` và `destroy/`. Nhầm lẫn hai cách viết đường dẫn là nguyên nhân phổ biến của lỗi `404`, `403` và xóa nhầm dữ liệu.

Bài này thuộc chương **KV phiên bản 2** của module **SPRING_VAULT**, kết nối cách Java truy cập secret với xác thực theo workload, quyền Vault policy, vòng đời phiên bản, giám sát và kiểm thử tích hợp. Sau khi học, bạn có thể:

- Phân biệt **mount path**, **key tương đối**, **đường dẫn logic** và **HTTP API path**.
- Ánh xạ các thao tác đọc/ghi, xem lịch sử, xóa mềm và hủy version sang endpoint đúng.
- Biết lúc nào `DELETE data/`, `POST delete/`, `POST destroy/` và `DELETE metadata/` có hậu quả khác nhau.
- Viết policy HCL trên đường dẫn mà Vault **thực sự nhận**, dù ứng dụng Java chỉ truyền key logic.
- Dùng Spring Vault hoặc Vault CLI mà không tự thêm sai tiền tố `data/`; kiểm tra lỗi bằng các bước xác minh ngắn.

## 1. Một secret có nhiều cách biểu diễn đường dẫn

Giả sử Vault đang mount một KV v2 engine ở `secret/`. Nhóm thanh toán đặt cấu hình tại key `apps/payment`. Ta có:

| Thành phần | Ví dụ | Ai sử dụng? |
| --- | --- | --- |
| **Mount path** | `secret/` | Cấu hình Vault secrets engine, client chọn mount |
| **Key tương đối trong mount** | `apps/payment` | Tham số `path` trong Spring Vault KV operations |
| **Đường dẫn logic đầy đủ** | `secret/apps/payment` | Cách nói ngắn gọn về vị trí một secret |
| **Đọc/ghi dữ liệu qua HTTP** | `/v1/secret/data/apps/payment` | KV v2 HTTP API |
| **Đọc metadata qua HTTP** | `/v1/secret/metadata/apps/payment` | KV v2 HTTP API |
| **Xóa mềm version chỉ định** | `/v1/secret/delete/apps/payment` | KV v2 HTTP API |
| **Hủy vĩnh viễn version chỉ định** | `/v1/secret/destroy/apps/payment` | KV v2 HTTP API |

**Quy tắc:** `secret` là **mount**; `apps/payment` là **key logic tương đối**. `data`, `metadata`, `delete` và `destroy` là **các nhánh endpoint nội bộ của KV v2**, không phải những folder con người dùng cần tạo bên trong key.

Nhánh endpoint xuất hiện **giữa mount và key**, không phải ở cuối key:

~~~text
Đường dẫn logic:        secret / apps/payment
                           |       |
                        mount     key

HTTP API đọc dữ liệu:  /v1/secret/data/apps/payment
                          |    |          |
                        mount nhánh      key
                              data

HTTP API metadata:     /v1/secret/metadata/apps/payment
HTTP API xóa mềm:      /v1/secret/delete/apps/payment
HTTP API hủy version:  /v1/secret/destroy/apps/payment
~~~

Số `/v1` ở đầu URL trên là **phiên bản của Vault HTTP API**, không phải KV version 1. Mặc dù KV engine là **v2**, các endpoint vẫn bắt đầu bằng `/v1/...`. Hai khái niệm này độc lập.

### KV v1 và KV v2 dễ bị nhầm ở đâu?

Nếu KV v1 được mount tại `legacy/`, một lệnh đọc dữ liệu thường truy cập `/v1/legacy/apps/payment`. Với KV v2 mount `secret/`, lệnh đọc lại dùng `/v1/secret/data/apps/payment`.

| Điều cần nhớ | KV v1 | KV v2 |
| --- | --- | --- |
| Endpoint đọc/ghi | `{mount}/{key}` | `{mount}/data/{key}` |
| Liệt kê key | LIST trên đường dẫn của KV v1 | LIST `{mount}/metadata/{folder}` |
| Đọc lịch sử version | Không có | GET `{mount}/metadata/{key}` |
| Xóa mềm version được chỉ định | Không có khái niệm version KV v2 | POST `{mount}/delete/{key}` |
| Hủy dữ liệu version cụ thể | Không có | POST `{mount}/destroy/{key}` |

Chỉ nhìn tên mount `secret` **không đủ** để biết engine là KV v1 hay KV v2. Kiểm tra cấu hình mount trước khi viết policy hoặc gọi HTTP thủ công:

~~~bash
vault secrets list -detailed
~~~

Trong thông tin của mount cần thấy tùy chọn phiên bản phù hợp, ví dụ `options: map[version:2]`. Lệnh kiểm tra mount thường đòi quyền phù hợp; nếu workload không có quyền đó, người vận hành có thể xác nhận loại engine từ cấu hình triển khai.

## 2. Bảng ánh xạ thao tác sang endpoint KV v2

Giả sử cùng một mount `secret` và key `apps/payment`:

| Mục đích | HTTP request | Capability thường cần | Tác động |
| --- | --- | --- | --- |
| Đọc version hiện hành | `GET /v1/secret/data/apps/payment` | `read` trên `secret/data/apps/payment` | Trả dữ liệu và metadata của version |
| Đọc version 2 | `GET /v1/secret/data/apps/payment?version=2` | `read` trên `secret/data/apps/payment` | Chỉ trả version 2 nếu còn khả dụng |
| Ghi bản dữ liệu mới | `POST /v1/secret/data/apps/payment` | `create` hoặc `update` trên `data/` tùy trạng thái key | Tạo version mới |
| Cập nhật một phần | `PATCH /v1/secret/data/apps/payment` | `patch` trên `data/` | Tạo version mới từ bản đã hợp nhất |
| Đọc metadata của key | `GET /v1/secret/metadata/apps/payment` | `read` trên `metadata/` | Trả chính sách và lịch sử version, không trả payload secret |
| Liệt kê tên key | `LIST /v1/secret/metadata/apps/` | `list` trên `metadata/apps` hoặc đường dẫn thư mục tương ứng | Trả tên, kể cả folder con |
| Xóa mềm version mới nhất | `DELETE /v1/secret/data/apps/payment` | `delete` trên `data/` | Đánh dấu version hiện hành đã xóa |
| Xóa mềm các version chỉ định | `POST /v1/secret/delete/apps/payment` | `update` trên `delete/` | Đánh dấu những version được chọn đã xóa |
| Khôi phục các version xóa mềm | `POST /v1/secret/undelete/apps/payment` | `update` trên `undelete/` | Cho phép đọc lại version chưa bị destroy |
| Hủy dữ liệu các version chỉ định | `POST /v1/secret/destroy/apps/payment` | `update` trên `destroy/` | **Không thể phục hồi dữ liệu** của những version này |
| Xóa toàn bộ key và metadata | `DELETE /v1/secret/metadata/apps/payment` | `delete` trên `metadata/` | **Xóa vĩnh viễn toàn bộ version và metadata của key** |

Sự khác biệt chủ chốt nằm ở cả **HTTP verb** lẫn **nhánh path**. Ví dụ `DELETE .../data/...` không tương đương `POST .../destroy/...` hoặc `DELETE .../metadata/...`, dù cùng chỉ đến một key logic.

Lưu ý khi thiết kế policy: `create` và `update` được Vault phân biệt theo trạng thái ghi. Nếu ứng dụng cần ghi cả key mới lẫn key đã tồn tại, quyền ở `data/` thường phải bao gồm cả hai; nếu chỉ có quyền `read` thì mọi thao tác ghi đều bị từ chối.

## 3. Endpoint `data/`: giá trị secret, version và xóa mềm bản hiện hành

Nhánh `data/` phục vụ các thao tác trên **payload secret**.

### 3.1. Ghi dữ liệu

Với HTTP API thô:

~~~http
POST /v1/secret/data/apps/payment
X-Vault-Token: <TOKEN_DO_MOI_TRUONG_CUNG_CAP>
Content-Type: application/json
~~~

~~~json
{
  "data": {
    "client_id": "demo-client",
    "region": "vn"
  }
}
~~~

Payload phải được đặt trong trường `data` ở cấp ngoài, theo cấu trúc KV v2. Một lần POST thành công tạo **một version mới** cho key. Các version trước có thể còn trong lịch sử nếu chưa bị xóa vĩnh viễn hoặc vượt giới hạn lưu giữ.

Ví dụ ghi với CAS để bảo đảm đang cập nhật đúng version 3:

~~~json
{
  "options": {
    "cas": 3
  },
  "data": {
    "client_id": "demo-client-next",
    "region": "vn"
  }
}
~~~

Vault sẽ từ chối nếu version hiện tại khác 3. `cas=0` có nghĩa chỉ cho phép ghi nếu key chưa tồn tại. CAS kiểm soát **cạnh tranh ghi**, không phải đường dẫn đọc khác.

### 3.2. Đọc dữ liệu và lớp JSON lồng nhau

Gọi `GET /v1/secret/data/apps/payment?version=2` có thể trả về JSON rút gọn như sau:

~~~json
{
  "data": {
    "data": {
      "client_id": "demo-client",
      "region": "vn"
    },
    "metadata": {
      "created_time": "2026-02-10T09:00:00Z",
      "deletion_time": "",
      "destroyed": false,
      "version": 2
    }
  }
}
~~~

- `data.data` là **payload của secret**.
- `data.metadata` là **metadata của version vừa đọc**, không phải danh sách tất cả version.
- `version=2` trong query chọn version dữ liệu; không liên quan đến `/v1` trong prefix HTTP.

Nếu ứng dụng cần lịch sử và metadata cấp key, chuyển sang endpoint `metadata/`. Không dựa vào response của một lần GET data để suy luận đầy đủ về tất cả version.

### 3.3. DELETE trên `data/` chỉ xóa mềm bản mới nhất

~~~http
DELETE /v1/secret/data/apps/payment
~~~

Lệnh trên **đánh dấu xóa mềm version mới nhất**, chứ không xóa tất cả các bản đã từng tồn tại. Metadata vẫn được giữ theo chính sách; nếu chưa bị destroy, version có thể được undelete. Đọc key không ghi rõ version sau khi xóa mềm thường không trả về dữ liệu, mặc dù các version cũ có thể vẫn còn.

Vì vậy, khi phát hiện secret biến mất sau một lệnh xóa, cần kiểm tra đã gọi `DELETE data/` hay `DELETE metadata/`; hậu quả và cách phục hồi khác nhau hoàn toàn.

## 4. Endpoint `metadata/`: quản lý lịch sử, chính sách và tên key

Endpoint `metadata/` có hai nhóm thao tác chính:

1. `GET /v1/secret/metadata/{key}`: xem thông tin quản lý **một key** và lịch sử version.
2. `LIST /v1/secret/metadata/{folder}`: xem **tên** các key/thư mục con trong folder.

Ví dụ kết quả rút gọn của GET metadata:

~~~json
{
  "data": {
    "created_time": "2026-02-10T09:00:00Z",
    "updated_time": "2026-02-10T10:00:00Z",
    "current_version": 3,
    "max_versions": 5,
    "cas_required": true,
    "custom_metadata": {
      "owner": "payments"
    },
    "versions": {
      "1": {
        "created_time": "2026-02-10T09:00:00Z",
        "deletion_time": "",
        "destroyed": false
      },
      "2": {
        "created_time": "2026-02-10T09:30:00Z",
        "deletion_time": "",
        "destroyed": false
      },
      "3": {
        "created_time": "2026-02-10T10:00:00Z",
        "deletion_time": "",
        "destroyed": false
      }
    }
  }
}
~~~

Trường `current_version` phản ánh version mới nhất đã được cấp, **không đồng nghĩa** số version còn có dữ liệu khả dụng. Dữ liệu một version có thể đã soft-delete, destroy hoặc bị loại do `max_versions`. `created_time` và `updated_time` ở mức key cũng khác `created_time` trong từng mục `versions`.

`custom_metadata` là nhãn quản lý của **key**. Vault có thể gắn nó trong phản hồi đọc secret, nên không đặt password, token hoặc dữ liệu nhạy cảm vào custom metadata, kể cả khi cố giới hạn quyền đọc `metadata/`.

### Liệt kê key dùng `metadata/`, dù không định đọc metadata chi tiết

~~~http
LIST /v1/secret/metadata/apps/
~~~

Kết quả có thể là `payment`, `billing` và `archive/` (folder con). Tên key có thể được nhìn thấy bởi token có quyền `list` trên thư mục, ngay cả khi token không thể đọc giá trị secret. Không đưa thông tin riêng tư vào tên key hoặc thư mục.

### Cảnh báo riêng cho `DELETE metadata/`

~~~http
DELETE /v1/secret/metadata/apps/payment
~~~

Thao tác này xóa **metadata của key cùng toàn bộ dữ liệu các version**, không phải chỉ dọn nhãn custom metadata. Đây là thao tác phá hủy rộng hơn nhiều so với `DELETE data/` hay `POST destroy/` một vài version. Cần cấp quyền `delete` trên metadata cho quy trình quản trị thực sự cần, không cấp rộng cho ứng dụng chỉ đọc/ghi secret.

## 5. `delete/`, `undelete/` và `destroy/`: ba nhánh khác nhau

Ba endpoint này nhận một **danh sách số version** trong request body. Chúng không được sử dụng bằng cách gắn thêm số version vào cuối đường dẫn.

### 5.1. Xóa mềm một số version: `POST delete/`

~~~http
POST /v1/secret/delete/apps/payment
Content-Type: application/json
~~~

~~~json
{
  "versions": [1, 2]
}
~~~

Vault đánh dấu version 1 và 2 đã bị xóa mềm, không xóa toàn bộ key. Lúc này các version được chọn không còn đọc được theo cách thông thường; lịch sử metadata có thể còn ghi nhận `deletion_time` của chúng.

### 5.2. Khôi phục version xóa mềm: `POST undelete/`

~~~http
POST /v1/secret/undelete/apps/payment
Content-Type: application/json
~~~

~~~json
{
  "versions": [2]
}
~~~

Nếu version 2 chỉ bị **soft-delete** và chưa bị phá hủy hoặc loại khỏi lịch sử, nó có thể đọc lại được sau undelete. Việc khôi phục **không tạo version mới** và không thay đổi thời điểm tạo ban đầu của version 2.

### 5.3. Hủy version vĩnh viễn: `POST destroy/`

~~~http
POST /v1/secret/destroy/apps/payment
Content-Type: application/json
~~~

~~~json
{
  "versions": [1]
}
~~~

Sau khi destroy thành công, payload của version 1 **không thể khôi phục** bằng undelete. Metadata lịch sử có thể vẫn thể hiện version 1 với `destroyed=true`. Hủy một version cụ thể không có nghĩa là mọi version khác đều bị hủy.

### So sánh bốn kiểu xóa

| Cách gọi | Đối tượng bị ảnh hưởng | Có thể undelete? | Metadata key còn? |
| --- | --- | --- | --- |
| `DELETE data/{key}` | Version **hiện hành** | Có, nếu chưa destroy hoặc loại bỏ | Có |
| `POST delete/{key}` + `versions` | Những version được chỉ định | Có, nếu còn đủ điều kiện | Có |
| `POST destroy/{key}` + `versions` | Payload của những version được chỉ định | **Không** | Có thể còn thông tin version đã destroy |
| `DELETE metadata/{key}` | **Toàn bộ version và metadata của key** | **Không** | **Không** |

~~~mermaid
flowchart TB
    A["Một key KV v2"] --> B["Version N đang đọc được"]
    B -->|DELETE data hoặc POST delete| C["Version N xóa mềm"]
    C -->|POST undelete| B
    B -->|POST destroy| D["Version N bị hủy vĩnh viễn"]
    C -->|POST destroy| D
    A -->|DELETE metadata| E["Xóa toàn bộ key và lịch sử"]
    D --> F["Không thể undelete version N"]
    E --> G["Không thể undelete key"]
~~~

Ngoài các lệnh thủ công, `delete_version_after` có thể đưa version vào trạng thái xóa mềm theo thời hạn và `max_versions` có thể khiến version cũ bị loại vĩnh viễn. Cơ chế này khác **TTL và lease** của token hoặc dynamic secret. Không coi version KV v2 là một lease có thể gia hạn.

## 6. Vault CLI và Spring Vault che giấu phần đường dẫn endpoint

Trong CLI và các API Java chuyên dụng, người dùng chủ yếu làm việc với **key logic**, còn công cụ tự chọn HTTP endpoint KV v2.

### 6.1. So sánh Vault CLI với endpoint thực tế

Giả định đã xác thực Vault CLI, `secret/` là mount KV v2 và `apps/payment` là key trong môi trường test:

| CLI | Endpoint được nhắm tới |
| --- | --- |
| `vault kv get -mount=secret apps/payment` | GET `secret/data/apps/payment` |
| `vault kv get -mount=secret -version=2 apps/payment` | GET `secret/data/apps/payment?version=2` |
| `vault kv put -mount=secret apps/payment region=vn` | POST `secret/data/apps/payment` |
| `vault kv metadata get -mount=secret apps/payment` | GET `secret/metadata/apps/payment` |
| `vault kv list -mount=secret apps/` | LIST `secret/metadata/apps/` |
| `vault kv delete -mount=secret apps/payment` | DELETE `secret/data/apps/payment` |
| `vault kv delete -mount=secret -versions=2 apps/payment` | POST `secret/delete/apps/payment` với version 2 |
| `vault kv undelete -mount=secret -versions=2 apps/payment` | POST `secret/undelete/apps/payment` với version 2 |
| `vault kv destroy -mount=secret -versions=2 apps/payment` | POST `secret/destroy/apps/payment` với version 2 |
| `vault kv metadata delete -mount=secret apps/payment` | DELETE `secret/metadata/apps/payment` |

**Không thực hiện `destroy` hoặc `metadata delete` trên key đang phục vụ ứng dụng** chỉ để xem kết quả lệnh. Hai lệnh cuối được nêu để phân biệt endpoint và hậu quả.

### 6.2. Spring Vault: truyền mount và key tương đối

Với Spring Vault, hai API thông dụng dành cho KV v2 là:

~~~java
import java.util.Map;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultVersionedKeyValueOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.support.VaultResponse;
import org.springframework.vault.support.Versioned;

// vaultOperations là bean được cấu hình sẵn; thường do VaultTemplate triển khai.
VaultKeyValueOperations latestOps =
    vaultOperations.opsForKeyValue("secret", KeyValueBackend.KV_2);

VaultVersionedKeyValueOperations versionedOps =
    vaultOperations.opsForVersionedKeyValue("secret");

// Cả hai API đều nhận "apps/payment", KHÔNG có "secret/data/".
VaultResponse latest = latestOps.get("apps/payment");
Versioned<Map<String, Object>> second =
    versionedOps.get("apps/payment", Versioned.Version.from(2));
~~~

`latestOps.get("apps/payment")` tự gọi nhánh `data/` rồi xử lý lớp dữ liệu theo KV v2. `versionedOps.get(..., Version.from(2))` chọn version 2 bằng query parameter. Nếu cần đọc metadata của key:

~~~java
import org.springframework.vault.support.VaultMetadataResponse;

VaultMetadataResponse metadata =
    versionedOps.opsForKeyValueMetadata().get("apps/payment");

if (metadata != null) {
    System.out.println("currentVersion=" + metadata.getCurrentVersion());
}
~~~

API metadata nhắm tới `secret/metadata/apps/payment`. Quyền đọc data không tự cấp quyền đọc endpoint metadata.

### 6.3. Khi sử dụng `VaultTemplate.read(...)` ở mức thấp

Nếu chủ đích gọi trực tiếp một HTTP path bằng `VaultTemplate`, cần đưa đúng **endpoint KV v2**:

~~~java
// Phương thức mức thấp: tự biết và ghi rõ nhánh data/ của KV v2.
org.springframework.vault.support.VaultResponse raw =
    vaultOperations.read("secret/data/apps/payment");

if (raw != null) {
    // Phản hồi thô chứa cấu trúc lồng data.data và data.metadata.
    // Không giả định raw.getData() đã là map payload cuối cùng.
    System.out.println("Đã đọc phản hồi KV v2 thô");
}
~~~

Nhìn chung, dùng `opsForKeyValue(..., KV_2)` hoặc `opsForVersionedKeyValue(...)` sẽ giảm rủi ro truyền sai prefix. Chỉ dùng API mức thấp khi cần thao tác mà abstraction chuyên dụng không đáp ứng.

**Không nhầm `secret/data/apps/payment` với một key logic mang tên `data/apps/payment`.** Nếu người vận hành tạo một key thực sự có tên bắt đầu bằng `data/` thì API KV v2 sẽ có dạng `secret/data/data/...`. Vì vậy, quy ước đặt tên key rõ ràng rất hữu ích để tránh hiểu nhầm.

## 7. Vault policy phải viết theo API path, không theo tên logic

Ứng dụng có thể chỉ gọi `latestOps.get("apps/payment")`, nhưng Vault thực tế kiểm tra policy trên `secret/data/apps/payment`. Policy:

~~~hcl
path "secret/apps/payment" {
  capabilities = ["read"]
}
~~~

không cấp quyền đọc KV v2 data theo cách API chuyên dụng yêu cầu. Chính sách đúng cho workload chỉ đọc secret này là:

~~~hcl
path "secret/data/apps/payment" {
  capabilities = ["read"]
}
~~~

Nếu cần xem metadata key và liệt kê tên dưới `apps/`, thêm **chính xác quyền đó**:

~~~hcl
path "secret/metadata/apps/payment" {
  capabilities = ["read"]
}

path "secret/metadata/apps" {
  capabilities = ["list"]
}

path "secret/metadata/apps/" {
  capabilities = ["list"]
}
~~~

Không cấp quyền `list` trên toàn mount nếu workload chỉ truy cập một key cố định. Quyền `list` có thể làm lộ tên key dù payload vẫn bị bảo vệ.

### Phân tách policy cho các tác vụ xóa

Giả sử có một tiến trình vận hành riêng được phép xóa mềm version chỉ định và undelete:

~~~hcl
path "secret/delete/apps/payment" {
  capabilities = ["update"]
}

path "secret/undelete/apps/payment" {
  capabilities = ["update"]
}
~~~

Quyền hủy vĩnh viễn phải được cấp **độc lập** nếu thực sự cần:

~~~hcl
path "secret/destroy/apps/payment" {
  capabilities = ["update"]
}
~~~

Quyền `delete` tại `secret/metadata/apps/payment` còn nguy hiểm hơn trong trường hợp muốn giữ lịch sử, bởi nó cho phép xóa toàn bộ key. Tách vai trò đọc cấu hình, vận hành version và phá hủy dữ liệu giúp giới hạn hậu quả khi token bị lạm dụng hoặc lệnh chạy nhầm.

| Vai trò | Quyền tối thiểu tiêu biểu | Không cần cấp khi chỉ làm đúng vai trò |
| --- | --- | --- |
| Dịch vụ đọc cấu hình | `read` trên `data/apps/payment` | `update`, `delete`, `destroy`, `list` metadata |
| Dịch vụ ghi cấu hình có CAS | `read`, `create`/`update` trên `data/apps/payment` | Quyền phá hủy lịch sử |
| Công cụ xem lịch sử | `read` trên `metadata/apps/payment` | Quyền đọc payload hoặc hủy version nếu không cần |
| Tiến trình xóa mềm theo version | `update` trên `delete/apps/payment` | `update` trên `destroy/apps/payment` |
| Tiến trình destroy có kiểm soát | `update` trên `destroy/apps/payment` | `delete` trên `metadata/apps/payment` nếu không xóa toàn bộ key |

Trong môi trường thật, các policy áp dụng cho **token sinh ra từ phương thức đăng nhập workload** (Kubernetes, AppRole, cloud IAM...). Kiểm tra chính sách gắn với danh tính thực của ứng dụng, tránh dùng token root để kiểm thử rồi kết luận workload đã đủ quyền.

## 8. Chẩn đoán lỗi đường dẫn và vòng đời version

| Dấu hiệu | Khả năng gây ra | Việc cần kiểm tra |
| --- | --- | --- |
| `404 unsupported path` khi GET | Dùng `secret/apps/payment` như KV v1; mount sai; hoặc thêm `data/` hai lần | Xác minh mount KV v2 và endpoint `secret/data/apps/payment` |
| Java gọi `get("secret/data/apps/payment")` không ra dữ liệu | Đã truyền cả mount và nhánh endpoint vào tham số key | Chỉ truyền `apps/payment` cho KV operations |
| `403 permission denied` khi đọc | Policy đang cấp `secret/apps/payment` thay vì `secret/data/apps/payment` | Sửa quyền theo endpoint HTTP thực tế |
| Đọc được secret nhưng `list` thất bại | `list` dùng nhánh `metadata/` | Cấp capability `list` đúng folder khi nghiệp vụ cần |
| `DELETE data` rồi `get` không có dữ liệu | Version hiện hành bị xóa mềm | Xem metadata; cân nhắc undelete nếu phù hợp |
| Gọi `POST delete` nhưng không ảnh hưởng version mong đợi | Body thiếu/sai danh sách `versions` | Xác nhận version hiện tại và request body |
| `undelete` không phục hồi được | Version đã `destroy` hoặc bị loại theo `max_versions` | Kiểm tra cờ `destroyed` và lịch sử metadata |
| Dữ liệu không thể khôi phục sau `DELETE metadata` | Toàn bộ key, lịch sử và version đã bị xóa vĩnh viễn | Khôi phục từ backup hợp lệ nếu có; undelete không áp dụng |
| Ghi trả lỗi CAS dù endpoint đúng | Version kỳ vọng không còn hiện hành hoặc key bắt buộc CAS | Đọc metadata/version và giải quyết xung đột trước khi thử lại |
| Lỗi `403` trên nhiều endpoint cùng lúc | Token workload thiếu policy, hết hạn hoặc đăng nhập sai | Kiểm tra auth/session, Vault audit log và chính sách gán cho token |

Lỗi `404` không phải lúc nào cũng chỉ ra sai đường dẫn: key không tồn tại hoặc version đã bị xóa cũng có thể khiến thao tác đọc không trả dữ liệu. Để chẩn đoán, tách kiểm tra **mount**, **key**, **API path**, **permission** và **trạng thái version**; không tự động cấp quyền rộng hơn chỉ để một request thành công.

Về giám sát, log loại thao tác (`data-read`, `metadata-read`, `soft-delete`, `destroy`), path logic đã được chuẩn hóa, version nếu cần, mã lỗi và độ trễ. Không ghi Vault token, payload secret hoặc toàn bộ `VaultResponse` vào log. Audit log của Vault hỗ trợ điều tra tác nhân và các request API; `created_time` chỉ cho biết thời điểm ghi version.

## 9. Thực hành đối chiếu CLI, HTTP và Java

Thực hành trong Vault dev/test đã được cấp phép với mount KV v2 `secret/`, key riêng `training/path-demo` và dữ liệu giả. Không dùng token hay secret thật.

### Bước 1 — Tạo hai version bằng CLI

~~~bash
vault kv put -mount=secret training/path-demo region=vn
vault kv put -mount=secret training/path-demo region=sg

vault kv get -mount=secret training/path-demo
vault kv get -mount=secret -version=1 training/path-demo
~~~

Ghi lại: CLI chỉ nhận mount và key logic, nhưng Vault vẫn lưu version qua endpoint `data/`.

### Bước 2 — Đọc metadata, liệt kê tên

~~~bash
vault kv metadata get -mount=secret training/path-demo
vault kv list -mount=secret training/
~~~

Đối chiếu: lệnh đầu sử dụng GET `metadata/training/path-demo` và có thể xem lịch sử; lệnh thứ hai dùng LIST `metadata/training/` và chỉ trả về tên.

### Bước 3 — So sánh hai cách xóa mềm

~~~bash
# Xóa mềm version hiện hành (trong ví dụ là 2).
vault kv delete -mount=secret training/path-demo

# Khôi phục version 2 để tiếp tục thử nghiệm.
vault kv undelete -mount=secret -versions=2 training/path-demo

# Xóa mềm riêng version 1.
vault kv delete -mount=secret -versions=1 training/path-demo

# Kiểm tra metadata lịch sử và trạng thái version 1.
vault kv metadata get -mount=secret training/path-demo
~~~

Giải thích: `vault kv delete` không có `-versions` chọn HTTP `DELETE data/`; khi có `-versions`, CLI nhắm tới `POST delete/`. Cả hai xóa mềm, nhưng **đối tượng được chọn khác nhau**.

### Bước 4 — Đọc bằng Spring Vault

~~~java
VaultKeyValueOperations ops =
    vaultOperations.opsForKeyValue("secret", KeyValueBackend.KV_2);

VaultResponse now = ops.get("training/path-demo");

VaultVersionedKeyValueOperations history =
    vaultOperations.opsForVersionedKeyValue("secret");

Versioned<Map<String, Object>> v1 =
    history.get("training/path-demo", Versioned.Version.from(1));

// V1 có thể không khả dụng vì bước 3 đã xóa mềm nó.
if (v1 == null || !v1.hasData()) {
    System.out.println("Version 1 hiện không đọc được");
}
~~~

Ở đây các import tương ứng với những kiểu ở phần 6 và hai đoạn cần đặt trong phương thức của ứng dụng đã có biến `vaultOperations`. Không thêm `data/` hay `metadata/` vào path Java.

### Bước 5 — Tự trả lời

1. Vì sao `GET /v1/secret/data/training/path-demo` khác `GET /v1/secret/metadata/training/path-demo` mặc dù cùng một key?
2. `DELETE /v1/secret/data/training/path-demo` có xóa tất cả version không?
3. Với token chỉ có `read` ở `secret/data/training/path-demo`, có thể `LIST secret/metadata/training/` không? Vì sao?
4. Đường dẫn policy nào cho phép destroy version 1, và vì sao không nên cấp nó cho ứng dụng chỉ đọc cấu hình?
5. Trong Spring Vault, khi đã gọi `opsForKeyValue("secret", KV_2)`, phải truyền `training/path-demo` hay `secret/data/training/path-demo`?

**Kết quả kỳ vọng:** Bạn phân biệt được **mount + key logic** với **HTTP endpoint**, xác định đúng đường dẫn policy, hiểu xóa mềm và destroy có phạm vi khác nhau, đồng thời sử dụng API Java KV v2 mà không ghép prefix thủ công.

### Gợi ý kiểm thử tích hợp

Trong một Vault test instance cô lập, tạo key riêng cho từng test và kiểm tra mapping thực tế của các endpoint. Có thể thêm các ca kiểm tra: một token chỉ đọc data không list được metadata; xóa mềm version N không hủy version khác; undelete khôi phục N; yêu cầu destroy cần policy riêng; truyền nhầm prefix ở API Java gây lỗi. Không chạy destroy hoặc metadata delete trên key dùng chung, không log secret trong output CI.

## Ghi nhớ

- **Đường dẫn logic** thường là `secret/apps/payment`; **key tương đối** trong Spring Vault là `apps/payment`.
- KV v2 dùng **`data/`** để đọc/ghi dữ liệu và xóa mềm version hiện hành; **`metadata/`** để đọc lịch sử, liệt kê và quản trị key.
- **`POST delete/`** xóa mềm các version được chỉ định; **`POST undelete/`** khôi phục version chưa bị hủy; **`POST destroy/`** hủy vĩnh viễn dữ liệu các version được chỉ định.
- **`DELETE metadata/`** xóa vĩnh viễn **toàn bộ key và lịch sử**, phạm vi rộng hơn destroy vài version.
- Spring Vault KV operations tự chọn endpoint nếu bạn khai báo mount và `KV_2` đúng. Vault policy phải cấp quyền theo **HTTP API path**, không phải chỉ theo đường dẫn logic.
- Phân quyền tối thiểu, xác thực workload phù hợp và giám sát không ghi payload bí mật giúp tránh biến lỗi đường dẫn thành sự cố bảo mật.
