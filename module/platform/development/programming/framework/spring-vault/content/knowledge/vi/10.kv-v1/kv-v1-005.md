# Đọc lại dữ liệu và kiểm tra kiểu giá trị trong KV v1

## Mục tiêu học tập

Sau bài này, bạn có thể:

- Dùng **Spring Vault** đọc lại secret vừa ghi vào HashiCorp Vault **KV phiên bản 1** thông qua `VaultOperations`, `VaultTemplate` và `VaultKeyValueOperations`.
- Giải thích cấu trúc `VaultResponse` và cách lấy các trường của secret bằng `getData()`.
- Kiểm tra **sự tồn tại, kiểu dữ liệu và giá trị hợp lệ** của các trường `String`, `Boolean`, `Number`, `Map` và `List` trong Java.
- Đọc secret thành DTO/POJO có kiểu bằng `get(path, Class<T>)` và hiểu giới hạn của việc ánh xạ tự động.
- Phân biệt dữ liệu chưa tồn tại, dữ liệu sai schema và lỗi kết nối/xác thực/ACL; thiết kế kiểm thử round-trip an toàn.

## 1. Vì sao cần kiểm tra kiểu sau khi đọc KV v1?

Vault KV v1 lưu **một đối tượng dữ liệu hiện hành tại mỗi đường dẫn secret**. Nó không áp một schema nghiệp vụ cố định lên các trường. Vì vậy, cùng đường dẫn có thể lần lượt chứa những payload khác nhau tùy chương trình ghi dữ liệu.

Ví dụ, một ứng dụng thanh toán dùng Spring Vault lưu cấu hình client tại mount `kv-lab/`, đường dẫn tương đối `apps/checkout/client`:

```json
{
  "api_key": "fake-key-for-learning",
  "enabled": true,
  "timeout_seconds": 30,
  "labels": {
    "environment": "lab",
    "owner": "checkout"
  }
}
```

Bốn trường có các kiểu JSON khác nhau. Java cần đọc chúng đúng kiểu trước khi sử dụng:

| Trường dữ liệu | Kiểu JSON mong muốn | Kiểu kiểm tra ở Java | Quy tắc nghiệp vụ ví dụ |
| --- | --- | --- | --- |
| `api_key` | String | `value instanceof String` | Không rỗng/không toàn khoảng trắng. |
| `enabled` | Boolean | `value instanceof Boolean` | Nhận `true` hoặc `false`; không chấp nhận chuỗi `"true"`. |
| `timeout_seconds` | Number | `value instanceof Number` | Là số nguyên trong khoảng 1–300 giây. |
| `labels` | Object | `value instanceof Map<?, ?>` | Nếu có, mọi key/value đều là String. |

**Khác biệt quan trọng:** JSON `true` là boolean, còn JSON `"true"` là chuỗi. JSON `30` là số, còn JSON `"30"` là chuỗi. Một phép ép kiểu bất cẩn có thể làm ứng dụng lỗi lúc chạy hoặc chấp nhận sai cấu hình mà không nhận ra.

KV v1 cũng cho phép ghi lại một đối tượng chỉ chứa một phần các trường. Lần `put` mới **thay thế toàn bộ bản ghi hiện hành**: nếu bên ghi quên `timeout_seconds`, lần đọc tiếp theo không còn trường này. Do đó, kiểm tra dữ liệu sau khi ghi và trước khi dùng là một phần quan trọng của hợp đồng giữa bên cấp phát secret và workload đọc secret.

## 2. Phân biệt đường dẫn và phiên bản KV

Ví dụ xuyên suốt bài:

```text
HashiCorp Vault
└── kv-lab/                    ← mount của secrets engine KV v1
    └── apps/
        └── checkout/
            └── client         ← một secret chứa nhiều trường
```

- Mount path: `kv-lab`.
- Đường dẫn secret tương đối: `apps/checkout/client`.
- Đường dẫn logic đầy đủ trong Vault: `kv-lab/apps/checkout/client`.
- HTTP API của KV v1 để đọc: `GET /v1/kv-lab/apps/checkout/client`.

Trong Spring Vault, lấy client chuyên biệt cho KV v1 như sau:

```java
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;

VaultKeyValueOperations kv = vaultOperations.opsForKeyValue(
        "kv-lab",
        KeyValueBackend.KV_1
);
```

`VaultOperations` thường được triển khai bởi `VaultTemplate`. Các ví dụ giả định ứng dụng đã cấu hình bean này với Vault endpoint, TLS và phương thức xác thực theo workload (chẳng hạn Kubernetes hoặc AppRole).

Sau khi chọn mount, `kv.get("apps/checkout/client")` chỉ nhận **đường dẫn tương đối**. Không thêm `kv-lab/`, `/v1/` hoặc `data/` vào đầu đường dẫn. Phân đoạn `data/` trong REST API thuộc KV v2; không được tự thêm vào KV v1.

## 3. Ghi dữ liệu mẫu có kiểu bằng Map

Để kiểm chứng kiểu khi đọc, cần tạo payload có kiểu rõ ràng. Trong Java, `Map<String, Object>` có thể giữ String, Boolean, Integer và Map lồng nhau:

```java
import java.util.LinkedHashMap;
import java.util.Map;

Map<String, Object> payload = new LinkedHashMap<>();
payload.put("api_key", "fake-key-for-learning");
payload.put("enabled", Boolean.TRUE);
payload.put("timeout_seconds", 30);
payload.put("labels", Map.of(
        "environment", "lab",
        "owner", "checkout"
));

kv.put("apps/checkout/client", payload);
```

Lệnh `put` ở đây lưu một đối tượng tại **một** đường dẫn secret. `enabled` được gửi như boolean, `timeout_seconds` là số, `labels` là đối tượng lồng nhau khi dùng bộ chuyển đổi JSON phù hợp.

Trong Vault CLI, các giá trị truyền theo cú pháp `key=value` có thể được hiểu là **chuỗi**, kể cả khi biểu diễn trông như số hoặc boolean. Vì vậy, khi cần kiểm thử kiểu JSON thật, ưu tiên dữ liệu được ghi bằng Map Java như ví dụ, hoặc dùng đầu vào JSON có kiểu rõ ràng; đừng suy ra rằng `enabled=true` trong một dòng CLI chắc chắn sinh ra boolean.

Một lần ghi lại cùng đường dẫn chỉ với `{"api_key": "..."}` sẽ xóa các trường `enabled`, `timeout_seconds` và `labels` khỏi bản hiện hành của KV v1. Khi cần sửa một trường mà vẫn giữ những trường khác, quy trình ghi phải cung cấp lại đầy đủ dữ liệu cần bảo toàn.

## 4. Đọc VaultResponse và Map<String, Object>

Với KV v1, `VaultKeyValueOperations.get(String path)` trả về `VaultResponse`. Dữ liệu của secret nằm ở `response.getData()`, thường được biểu diễn bằng `Map<String, Object>`:

```java
import java.util.Map;

import org.springframework.vault.support.VaultResponse;

VaultResponse response = kv.get("apps/checkout/client");

if (response == null || response.getData() == null) {
    throw new IllegalStateException("Chưa có secret apps/checkout/client");
}

Map<String, Object> data = response.getData();

Object apiKeyValue = data.get("api_key");
Object enabledValue = data.get("enabled");
Object timeoutValue = data.get("timeout_seconds");
Object labelsValue = data.get("labels");
```

`Map.get` trả về `Object`, do đó cần kiểm tra kiểu **trước khi** ép kiểu. Nếu một key không tồn tại, `get` trả `null`; nếu key tồn tại nhưng giá trị được ghi là JSON `null`, kết quả `get` cũng là `null`. Khi cần phân biệt hai trường hợp, dùng `containsKey`:

```java
if (!data.containsKey("api_key")) {
    throw new IllegalStateException("Thiếu trường api_key");
}

if (data.get("api_key") == null) {
    throw new IllegalStateException("Trường api_key có giá trị null");
}
```

Chỉ kiểm tra `response != null` là chưa đủ: map có thể thiếu trường hoặc chứa kiểu dữ liệu không đúng kỳ vọng. Ngược lại, **không nên** coi mọi lỗi đọc Vault đều là thiếu dữ liệu. Thiếu quyền, token hết hạn hay lỗi mạng/TLS có thể khiến lời gọi ném ngoại lệ và cần được xử lý riêng ở tầng kết nối/vận hành.

### Hình dạng phản hồi của KV v1 và KV v2

Ví dụ phản hồi HTTP của KV v1 có phần dữ liệu trực tiếp dưới `data`:

```json
{
  "request_id": "example-request-id",
  "lease_id": "",
  "renewable": false,
  "lease_duration": 0,
  "data": {
    "api_key": "fake-key-for-learning",
    "enabled": true,
    "timeout_seconds": 30
  }
}
```

Đây là **minh họa cấu trúc**, không phải cam kết mọi bản phản hồi đều có giá trị metadata giống hệt. KV v1 lưu secret tĩnh, nên không có lease động riêng cho mỗi bản secret giống các secrets engine cấp credential động.

Với KV v2, endpoint và cấu trúc JSON có thêm lớp dữ liệu/metadata phiên bản. Khi dùng `VaultKeyValueOperations` với backend tương ứng, Spring Vault xử lý khác biệt giao thức. Bài này chỉ tập trung vào `KeyValueBackend.KV_1` và đọc **bản hiện hành**.

## 5. Kiểm tra String và Boolean một cách tường minh

Không nên ép kiểu trực tiếp ngay sau `get`:

```java
// Dễ lỗi ClassCastException nếu data chứa số hoặc cấu trúc khác.
String apiKey = (String) data.get("api_key");
```

Thay vào đó, kiểm tra giá trị:

```java
private static String requiredNonBlankString(
        Map<String, Object> data, String field) {

    Object value = data.get(field);

    if (!(value instanceof String)) {
        throw new IllegalStateException(
                "Trường " + field + " phải có kiểu String");
    }

    String text = (String) value;
    if (text.isBlank()) {
        throw new IllegalStateException(
                "Trường " + field + " không được để trống");
    }

    return text;
}
```

Với Boolean:

```java
private static boolean requiredBoolean(
        Map<String, Object> data, String field) {

    Object value = data.get(field);

    if (!(value instanceof Boolean)) {
        throw new IllegalStateException(
                "Trường " + field + " phải có kiểu Boolean");
    }

    return (Boolean) value;
}
```

Phải phân biệt `false` với giá trị thiếu. Cách viết `if (!Boolean.TRUE.equals(data.get("enabled")))` có thể hữu ích khi chỉ muốn biết một tính năng được bật hay không, nhưng sẽ **gộp** trường hợp `false` hợp lệ với trường hợp thiếu/sai kiểu. Khi kiểm tra schema bắt buộc, dùng `instanceof Boolean` như trên.

Cũng không nên tự động gọi `Boolean.parseBoolean(String.valueOf(value))` trong validation chặt: cách chuyển đổi này có thể nhận các giá trị chuỗi ngoài hợp đồng dữ liệu và khiến lỗi bên ghi khó được phát hiện.

## 6. Kiểm tra Number mà không phụ thuộc Integer/Long

Một số nguyên trong JSON có thể được thư viện JSON ánh xạ thành `Integer`, `Long`, `BigInteger` hoặc một dạng `Number` khác tùy giá trị và cấu hình. Việc ép kiểu cứng có thể gây lỗi:

```java
// Không nên giả định mọi số nguyên JSON đều trở thành Integer.
Integer timeout = (Integer) data.get("timeout_seconds");
```

Nếu chỉ cần xác nhận đó là một giá trị số, dùng `instanceof Number`. Tuy nhiên `number.intValue()` **có thể cắt phần thập phân hoặc tràn giá trị**, nên với timeout cần kiểm tra số nguyên và giới hạn chính xác.

Một cách đọc số nguyên chặt chẽ:

```java
import java.math.BigDecimal;
import java.util.Map;

private static int requiredIntInRange(
        Map<String, Object> data,
        String field,
        int min,
        int max) {

    Object value = data.get(field);

    if (!(value instanceof Number)) {
        throw new IllegalStateException(
                "Trường " + field + " phải có kiểu Number");
    }

    final int parsed;
    try {
        // intValueExact() từ chối phần thập phân và số vượt miền int.
        parsed = new BigDecimal(value.toString()).intValueExact();
    } catch (ArithmeticException | NumberFormatException ex) {
        throw new IllegalStateException(
                "Trường " + field + " phải là số nguyên hợp lệ", ex);
    }

    if (parsed < min || parsed > max) {
        throw new IllegalStateException(
                "Trường " + field + " nằm ngoài khoảng cho phép");
    }

    return parsed;
}
```

Với `timeout_seconds`, gọi:

```java
int timeoutSeconds =
        requiredIntInRange(data, "timeout_seconds", 1, 300);
```

Các trường hợp:

| Dữ liệu đầu vào | Kết quả kiểm tra |
| --- | --- |
| `"timeout_seconds": 30` | Hợp lệ. |
| `"timeout_seconds": 30.0` | Có thể hợp lệ nếu Number biểu diễn đúng giá trị nguyên 30. |
| `"timeout_seconds": 30.5` | Từ chối vì không phải số nguyên. |
| `"timeout_seconds": "30"` | Từ chối vì là String, dù có thể parse ra số. |
| `"timeout_seconds": 0` | Từ chối vì nhỏ hơn 1. |
| `"timeout_seconds": 9999999999999999999` | Từ chối nếu vượt phạm vi `int`. |

Trong ví dụ trên, việc kiểm tra `Number` xảy ra **trước** chuyển đổi. Nếu hợp đồng dữ liệu cho phép chuỗi số, hãy thiết kế một hàm chuyển đổi riêng và ghi rõ quy tắc, thay vì tự động chấp nhận mọi kiểu có thể chuyển thành chuỗi.

## 7. Kiểm tra Map hoặc List lồng nhau

KV cho phép lưu dữ liệu lồng nhau. Trong ví dụ, `labels` là một object có key/value đều là String. Tại thời điểm đọc, không được ép kiểu thẳng thành `Map<String, String>` vì Java sử dụng *type erasure* đối với generic:

```java
// Không chứng minh được toàn bộ key và value bên trong đều là String.
// Có thể gây lỗi muộn khi sử dụng dữ liệu.
@SuppressWarnings("unchecked")
Map<String, String> labels =
        (Map<String, String>) data.get("labels");
```

Thay vào đó, kiểm tra từng phần tử:

```java
import java.util.LinkedHashMap;
import java.util.Map;

private static Map<String, String> optionalStringLabels(
        Map<String, Object> data, String field) {

    if (!data.containsKey(field)) {
        return Map.of();
    }

    Object value = data.get(field);

    if (!(value instanceof Map<?, ?>)) {
        throw new IllegalStateException(
                "Trường " + field + " phải là JSON object");
    }

    Map<?, ?> raw = (Map<?, ?>) value;
    Map<String, String> result = new LinkedHashMap<>();

    for (Map.Entry<?, ?> entry : raw.entrySet()) {
        if (!(entry.getKey() instanceof String)
                || !(entry.getValue() instanceof String)) {
            throw new IllegalStateException(
                    "Mỗi key và value của " + field + " phải là String");
        }

        result.put((String) entry.getKey(), (String) entry.getValue());
    }

    return Map.copyOf(result);
}
```

Trong hợp đồng trên, `labels` là trường **tùy chọn**: thiếu trường cho kết quả map rỗng, nhưng `labels: null` hoặc sai kiểu sẽ bị từ chối. Nếu muốn chấp nhận `null` hoặc quy định `labels` bắt buộc, cần sửa hàm đúng theo hợp đồng ứng dụng.

Tương tự, nếu secret có danh sách:

```json
{
  "allowed_regions": ["ap-southeast-1", "eu-west-1"]
}
```

thì kiểm tra `value instanceof List<?>`, sau đó duyệt từng phần tử và xác nhận tất cả là `String`. Đừng ép kiểu `List<String>` rồi giả định mọi phần tử đều đúng; lỗi có thể chỉ xuất hiện khi duyệt danh sách.

## 8. Service Java đọc lại và kiểm tra dữ liệu

Ví dụ sau kết hợp các nguyên tắc trên vào một service Spring. Để đoạn mã dễ áp dụng, service dùng các hàm kiểm tra kiểu cho ba trường bắt buộc và một trường tùy chọn. Những hàm ở các phần trước có thể được đặt thành các phương thức `private static` trong cùng class.

```java
import java.util.Map;

import org.springframework.stereotype.Service;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.support.VaultResponse;

@Service
public class CheckoutSecretReader {

    private static final String MOUNT = "kv-lab";
    private static final String PATH = "apps/checkout/client";

    private final VaultKeyValueOperations kv;

    public CheckoutSecretReader(VaultOperations vaultOperations) {
        this.kv = vaultOperations.opsForKeyValue(MOUNT, KeyValueBackend.KV_1);
    }

    public CheckoutSettings loadRequired() {
        VaultResponse response = kv.get(PATH);

        if (response == null || response.getData() == null) {
            throw new IllegalStateException(
                    "Không tìm thấy secret checkout/client trong Vault");
        }

        Map<String, Object> data = response.getData();

        String apiKey = requiredNonBlankString(data, "api_key");
        boolean enabled = requiredBoolean(data, "enabled");
        int timeout = requiredIntInRange(
                data, "timeout_seconds", 1, 300);
        Map<String, String> labels =
                optionalStringLabels(data, "labels");

        // Giữ secret trong đối tượng chuyên dụng, không in ra log.
        return new CheckoutSettings(apiKey, enabled, timeout, labels);
    }

    public static final class CheckoutSettings {

        private final String apiKey;
        private final boolean enabled;
        private final int timeoutSeconds;
        private final Map<String, String> labels;

        public CheckoutSettings(
                String apiKey,
                boolean enabled,
                int timeoutSeconds,
                Map<String, String> labels) {
            this.apiKey = apiKey;
            this.enabled = enabled;
            this.timeoutSeconds = timeoutSeconds;
            this.labels = Map.copyOf(labels);
        }

        public String getApiKey() { return apiKey; }
        public boolean isEnabled() { return enabled; }
        public int getTimeoutSeconds() { return timeoutSeconds; }
        public Map<String, String> getLabels() { return labels; }
    }

    // Đặt ở đây nội dung bốn hàm kiểm tra kiểu đã giới thiệu:
    // requiredNonBlankString, requiredBoolean, requiredIntInRange,
    // optionalStringLabels.
}
```

Đây là ví dụ sắp xếp các hàm đã trình bày trong bài, vì vậy **để biên dịch**, bạn cần đưa cả bốn phương thức kiểm tra ở các phần 5–7 vào class `CheckoutSecretReader` và bổ sung các import `BigDecimal`, `LinkedHashMap` cần thiết. Các giá trị secret không được đưa vào `toString()`, exception message hay logging. Nếu chỉ cần một trường, vẫn nên kiểm tra kiểu đúng và không trả dữ liệu không hợp lệ vào tầng nghiệp vụ.

### Kiểm tra sau put và trước khi dùng

Một kiểm thử round-trip có thể ghi payload đầy đủ rồi đọc ngay:

```java
Map<String, Object> writeData = Map.of(
        "api_key", "fake-key-for-learning",
        "enabled", true,
        "timeout_seconds", 30,
        "labels", Map.of("environment", "lab")
);

kv.put("apps/checkout/client", writeData);

VaultResponse afterWrite = kv.get("apps/checkout/client");
if (afterWrite == null || afterWrite.getData() == null) {
    throw new IllegalStateException("Không đọc lại được secret vừa ghi");
}

Map<String, Object> actual = afterWrite.getData();

// Gọi các hàm kiểm tra kiểu ở trên.
String key = requiredNonBlankString(actual, "api_key");
boolean enabled = requiredBoolean(actual, "enabled");
int timeout = requiredIntInRange(
        actual, "timeout_seconds", 1, 300);
Map<String, String> labels =
        optionalStringLabels(actual, "labels");
```

Ví dụ chỉ dùng trong môi trường được phép ghi và đọc bằng danh tính có ACL tương ứng. **Đọc ngay sau khi ghi kiểm tra dữ liệu hiện hành tại thời điểm đọc**; nó không phải cơ chế khóa giao dịch. Một tác nhân khác vẫn có thể ghi đè secret sau lần kiểm tra. KV v1 không cung cấp CAS theo phiên bản để ngăn *lost update* giữa nhiều bên ghi.

## 9. Đọc theo DTO với get(path, Class<T>)

Nếu schema ổn định, `VaultKeyValueOperations` hỗ trợ đọc dữ liệu vào một kiểu Java cụ thể:

```java
import org.springframework.vault.support.VaultResponseSupport;

VaultResponseSupport<CheckoutSecretDto> response =
        kv.get("apps/checkout/client", CheckoutSecretDto.class);

if (response == null || response.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret checkout/client");
}

CheckoutSecretDto dto = response.getData();
```

DTO có thể khai báo:

```java
import com.fasterxml.jackson.annotation.JsonProperty;
import java.util.Map;

public class CheckoutSecretDto {

    @JsonProperty("api_key")
    private String apiKey;

    private Boolean enabled;

    @JsonProperty("timeout_seconds")
    private Integer timeoutSeconds;

    private Map<String, String> labels;

    public CheckoutSecretDto() {}

    public String getApiKey() { return apiKey; }
    public void setApiKey(String apiKey) { this.apiKey = apiKey; }

    public Boolean getEnabled() { return enabled; }
    public void setEnabled(Boolean enabled) { this.enabled = enabled; }

    public Integer getTimeoutSeconds() { return timeoutSeconds; }
    public void setTimeoutSeconds(Integer timeoutSeconds) {
        this.timeoutSeconds = timeoutSeconds;
    }

    public Map<String, String> getLabels() { return labels; }
    public void setLabels(Map<String, String> labels) {
        this.labels = labels;
    }
}
```

`@JsonProperty` giúp thể hiện hợp đồng JSON có tên `api_key` và `timeout_seconds` trong môi trường dùng Jackson và các thành phần mapping tương ứng. Nếu cấu hình chuyển đổi của ứng dụng có quy tắc khác, kết quả thực tế cần được xác minh bằng integration test.

**Đọc vào DTO không tự thay thế validation.** Ví dụ:

- DTO có `Integer timeoutSeconds` cho phép nhận `null` nếu trường bị thiếu; dùng `int` nguyên thủy có thể làm mất khả năng phân biệt trường thiếu với giá trị mặc định `0`.
- Bộ chuyển đổi dữ liệu có thể có quy tắc ép kiểu chuỗi sang số hoặc boolean. Nếu hợp đồng bắt buộc JSON gốc phải là Number/Boolean, hãy kiểm tra trên `Map` trước khi cho phép dữ liệu đi vào nghiệp vụ.
- DTO có `Map<String, String> labels` vẫn cần kiểm tra tính hợp lệ nghiệp vụ của key, value; chỉ có trường Java đúng kiểu chưa chứng minh mọi giá trị đáp ứng quy tắc ứng dụng.
- Dữ liệu có thể có trường không mong muốn hoặc thiếu trường tùy cấu hình mapper; nên xác định rõ field nào là bắt buộc, field nào tùy chọn và xử lý trường dư theo yêu cầu hệ thống.

Đối với secret nhạy cảm, không log toàn bộ DTO. Khi ánh xạ không thành công, log thông tin loại lỗi an toàn mà không in payload chứa API key/password.

## 10. Phân biệt các trạng thái lỗi khi đọc

| Tình huống | Ý nghĩa | Hướng xử lý |
| --- | --- | --- |
| `get` trả `null` hoặc `getData()` không có dữ liệu | Secret có thể không tồn tại ở đường dẫn yêu cầu. | Báo thiếu cấu hình với tên đường dẫn an toàn; không tiếp tục dùng giá trị giả định. |
| Thiếu `api_key` | Bản dữ liệu hiện hành không đáp ứng schema. | Kiểm tra bên ghi; KV v1 có thể đã bị ghi đè thiếu trường. |
| `enabled` là `"true"` thay vì `true` | Bên ghi đã lưu String, trái hợp đồng boolean. | Từ chối hoặc chuyển đổi theo quy tắc đã định; không ép kiểu ngầm. |
| `timeout_seconds` là `30.5` hoặc vượt phạm vi | Số không đạt quy tắc nghiệp vụ. | Báo lỗi validation; không đưa vào cấu hình thời gian chờ. |
| `labels` là List, không phải Map | Cấu trúc lồng nhau sai schema. | Xác minh payload và cách serialize ở bên ghi. |
| Đường dẫn đúng nhưng Vault trả lỗi quyền truy cập | Workload chưa có `read` hoặc token không hợp lệ. | Kiểm tra auth, ACL trên full path và vòng đời token. |
| Vault không thể kết nối | Lỗi endpoint, mạng, TLS hoặc Vault không sẵn sàng. | Theo dõi trạng thái hạ tầng, xử lý retry có giới hạn nếu phù hợp. |
| CLI đọc được nhưng Java không | Có thể khác mount, khác identity/policy hoặc chọn sai `KV_1`/`KV_2`. | Đối chiếu mount, relative path, phiên bản engine và workload identity. |

Không nên viết:

```java
try {
    return kv.get("apps/checkout/client");
} catch (Exception ex) {
    return null; // Che giấu cả lỗi mạng/ACL thành "không có secret".
}
```

Đối với lỗi hệ thống, giữ ngữ cảnh để vận hành phân biệt thiếu secret với lỗi xác thực và lỗi kết nối. Đặt metric cho kết quả đọc thành công/thất bại, loại lỗi và độ trễ theo chính sách giám sát của tổ chức. Không đưa giá trị bí mật, token hoặc toàn bộ `VaultResponse` vào log, trace, metric label hay báo cáo kiểm thử.

## 11. ACL và vòng đời token/lease

Đối với mount KV v1 `kv-lab`, API `get("apps/checkout/client")` cần ACL `read` ở đường dẫn **đầy đủ**:

```hcl
path "kv-lab/apps/checkout/client" {
  capabilities = ["read"]
}
```

Nếu bài kiểm thử cần cả `put`, danh tính tạo/ghi secret cần các capability thích hợp, ví dụ `create` và `update`:

```hcl
path "kv-lab/apps/checkout/client" {
  capabilities = ["create", "update", "read"]
}
```

Trong triển khai thật, nên tách workload chỉ đọc secret khỏi quy trình cấp phát/luân chuyển có quyền ghi. Quyền `list` trên đường dẫn cha chỉ cho phép liệt kê tên, **không** cấp quyền đọc giá trị secret.

Token được cấp cho workload có TTL và quy tắc gia hạn/thu hồi riêng. Token hết hạn có thể khiến `kv.get` bị từ chối dù dữ liệu vẫn tồn tại. Secret tĩnh trong KV v1 không tự hết hạn theo TTL của token và không có lease động riêng như credential do một số secrets engine khác cấp.

Trong cùng hệ sinh thái Vault, Transit phục vụ thao tác mã hóa/giải mã qua engine chuyên biệt, PKI phục vụ phát hành/quản lý chứng chỉ. Bài này tập trung vào **đọc dữ liệu KV v1 và kiểm tra schema** trước khi ứng dụng dùng dữ liệu đó.

## 12. Bài thực hành kiểm thử tích hợp

Dùng một Vault thử nghiệm riêng biệt, mount `kv-lab` là KV **phiên bản 1**, dữ liệu giả. Trước khi chạy, kiểm tra cấu hình mount với `vault secrets list -detailed`; nếu chưa có và bạn có quyền quản trị lab, có thể bật bằng `vault secrets enable -path=kv-lab -version=1 kv`.

1. **Ghi dữ liệu đúng kiểu:** Dùng `Map` Java để ghi String, Boolean, Integer và Map lồng nhau như phần 3. Xác nhận request ghi thành công qua client được cấu hình.
2. **Đọc và kiểm tra:** Gọi `get(path)`, lấy `getData()`, kiểm tra `api_key` là String không rỗng, `enabled` là Boolean, `timeout_seconds` là Number nguyên hợp lệ trong khoảng 1–300, `labels` là Map có key/value String.
3. **Kiểm tra kiểu string/số:** Ghi payload có `"timeout_seconds": "30"` dưới dạng **String**; xác nhận validator từ chối và trả thông báo loại lỗi phù hợp, không lộ API key.
4. **Kiểm tra kiểu boolean:** Ghi `"enabled": "true"` dưới dạng **String**; xác nhận validator không âm thầm nhận như Boolean.
5. **Kiểm tra thiếu trường:** Ghi lại cùng secret chỉ có `api_key`; xác nhận các trường còn lại biến mất khỏi dữ liệu hiện hành và lớp đọc báo thiếu schema. Đây là kiểm thử ngữ nghĩa *replace* của KV v1.
6. **Kiểm tra biên số:** Thử `timeout_seconds` lần lượt là `0`, `300`, `301` và `30.5`; chỉ các giá trị nguyên nằm trong khoảng quy định được chấp nhận.
7. **Kiểm tra kiểu lồng nhau:** Ghi `labels` là một List hoặc Map có value không phải String; xác nhận việc kiểm tra cấu trúc phát hiện sai kiểu.
8. **Đọc theo DTO:** Sau khi ghi lại payload hợp lệ, gọi `get(path, CheckoutSecretDto.class)` và xác nhận ánh xạ `api_key` ↔ `apiKey`, `timeout_seconds` ↔ `timeoutSeconds` đúng theo cấu hình mapper.
9. **Kiểm tra phân quyền:** Dùng một workload chỉ có `read`; xác nhận đọc thành công nhưng ghi bị từ chối. Dùng workload không có `read` để xác minh lỗi ACL không bị biến thành kết quả secret rỗng.
10. **Kiểm tra dữ liệu không tồn tại:** Xóa secret bằng danh tính được phép rồi gọi `get`; xác nhận ứng dụng có nhánh xử lý thiếu cấu hình rõ ràng.

Có thể tích hợp các tình huống trên với Testcontainers và một Vault instance dành riêng cho test. Unit test dùng mock `VaultKeyValueOperations` giúp kiểm tra validator và cách service dùng `get`, còn integration test với Vault thật giúp chứng minh kiểu JSON round-trip, cấu trúc phản hồi, ghi đè và ACL. Mỗi test cần dọn dữ liệu thử nghiệm và tránh in secret hoặc token vào log CI.

### Câu hỏi tự kiểm tra

1. Vì sao `(Integer) response.getData().get("timeout_seconds")` có thể gây lỗi dù Vault đang lưu một số hợp lệ?
2. JSON `{"enabled": "true"}` có tương đương `{"enabled": true}` về kiểu dữ liệu không?
3. Vì sao cần kiểm tra `response == null` và `response.getData() == null` trước khi đọc trường?
4. Khi đọc một `Map<String, Object>`, vì sao phép ép `(Map<String, String>) value` chưa chứng minh được các value đều là String?
5. Sau khi ghi lại KV v1 chỉ với `api_key`, cần mong đợi điều gì khi kiểm tra `timeout_seconds`?
6. Đọc thành DTO có đảm bảo loại trừ mọi lỗi kiểu dữ liệu, giá trị thiếu và phạm vi không?

## Tổng kết

Khi dùng **Spring Vault** với `KeyValueBackend.KV_1`, đọc secret qua `VaultKeyValueOperations.get(relativePath)` và lấy `VaultResponse.getData()` để kiểm tra từng trường của bản dữ liệu hiện hành. Hãy phân biệt String với Boolean/Number, kiểm tra giới hạn số nguyên, duyệt các cấu trúc Map/List lồng nhau và xác định rõ trường bắt buộc hay tùy chọn. `get(path, Class<T>)` hữu ích để ánh xạ sang DTO nhưng không thay thế validation nghiệp vụ hoặc kiểm tra kiểu JSON chặt chẽ khi cần. Kết hợp đọc lại sau `put`, phân quyền `read` tối thiểu, xử lý lỗi xác thực/kết nối riêng và kiểm thử round-trip trên Vault KV v1 để ứng dụng sử dụng secret đúng và an toàn.
