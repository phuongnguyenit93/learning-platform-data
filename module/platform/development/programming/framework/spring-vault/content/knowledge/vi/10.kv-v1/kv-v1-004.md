# Ghi Map hoặc đối tượng Java vào một khóa KV v1

## Mục tiêu học tập

Sau bài này, bạn có thể:

- Dùng **Spring Vault** ghi một secret vào HashiCorp Vault KV phiên bản 1 với `VaultKeyValueOperations.put(path, data)`.
- Phân biệt **khóa là đường dẫn secret** với các **trường dữ liệu** nằm trong một secret; hiểu vì sao một lần `put` có thể lưu nhiều trường.
- Tạo payload bằng `Map<String, Object>` hoặc một đối tượng Java (POJO/DTO), dự đoán JSON mà Vault nhận và xử lý khác biệt trong ánh xạ tên thuộc tính.
- Giải thích tính chất **ghi đè toàn bộ** của KV v1, nguy cơ mất trường dữ liệu và xung đột ghi đồng thời.
- Kiểm tra dữ liệu đã ghi, phân quyền cho workload và thiết kế tình huống kiểm thử tích hợp an toàn.

## 1. “Ghi vào một khóa” nghĩa là gì?

Trong **KV (Key/Value) secrets engine phiên bản 1**, mỗi đường dẫn secret dưới mount chứa **một đối tượng dữ liệu hiện hành**. “Một khóa” ở đây là **đường dẫn logic của secret**; nó có thể chứa một hoặc nhiều cặp *tên trường → giá trị*.

Ví dụ, mount KV v1 tại `kv-lab/` và lưu secret tại đường dẫn tương đối `payments/gateway`:

```text
HashiCorp Vault
└── kv-lab/                     ← mount của KV engine v1
    └── payments/
        └── gateway            ← MỘT khóa/đường dẫn secret
            ├── api_key        ← trường dữ liệu thứ nhất
            └── endpoint       ← trường dữ liệu thứ hai
```

Một bản dữ liệu tại khóa này có dạng:

```json
{
  "api_key": "fake-key-a",
  "endpoint": "https://sandbox.example.invalid"
}
```

Trong ví dụ:

| Thành phần | Giá trị | Ý nghĩa |
| --- | --- | --- |
| Mount path | `kv-lab` | Xác định KV engine trong Vault. |
| Đường dẫn secret tương đối | `payments/gateway` | Khóa mà Spring Vault đọc/ghi bên trong mount. |
| Đường dẫn logic đầy đủ | `kv-lab/payments/gateway` | Đường dẫn dùng khi viết policy ACL. |
| Nội dung secret | `{"api_key": "...", "endpoint": "..."}` | Một đối tượng gồm hai trường tại **cùng một khóa**. |

Trường `api_key` không phải một secret ở đường dẫn `kv-lab/payments/gateway/api_key`. Hai trường trong bảng cùng thuộc dữ liệu của `kv-lab/payments/gateway`.

KV v1 chỉ có **bản hiện hành** của đường dẫn. Ghi lại cùng đường dẫn sẽ thay thế bản dữ liệu trước đó; không có số phiên bản để đọc lại lịch sử như KV v2.

## 2. Chọn đúng API Spring Vault trước khi ghi

Spring Vault cung cấp `VaultTemplate` — một triển khai của `VaultOperations` — làm client truy cập Vault sau khi được cấu hình endpoint, phiên xác thực và các thành phần kết nối.

Để thao tác chuyên biệt với KV v1, dùng:

```java
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;

// vaultOperations: bean đã được cấu hình kết nối và xác thực với Vault.
VaultKeyValueOperations kv = vaultOperations.opsForKeyValue(
        "kv-lab",             // chỉ là tên mount
        KeyValueBackend.KV_1 // backend phải khớp KV v1 trên Vault
);
```

Sau đó, ghi **đường dẫn tương đối** bên trong mount:

```java
kv.put("payments/gateway", payload);
```

Không truyền `"kv-lab/payments/gateway"` cho `kv.put` nếu đã khởi tạo `kv` với mount `"kv-lab"`. Cũng không thêm `/v1/` hoặc phân đoạn `data/` từ REST API KV v2. Với KV v1, lời gọi ghi ở trên tương ứng với request REST tới `POST /v1/kv-lab/payments/gateway`.

Chữ `KV_1` quyết định cách Spring Vault gửi request; nó **không tự tạo** hoặc chuyển phiên bản secrets engine trên máy chủ. Trước khi thực hành, quản trị viên có thể tạo mount thử nghiệm bằng:

```bash
vault secrets enable -path=kv-lab -version=1 kv
```

Nếu `kv-lab/` đã tồn tại thì không bật lại. Có thể kiểm tra mount với `vault secrets list -detailed` và xác nhận loại `kv`, phiên bản `1`. Một mount có tên `secret/` chưa chắc là KV v1.

### Cú pháp put

`VaultKeyValueOperations` cung cấp thao tác:

```java
kv.put(String path, Object data);
```

`path` là secret path tương đối; `data` là đối tượng nguồn để chuyển thành payload gửi Vault. Cả `Map` lẫn một Java bean tương thích bộ chuyển đổi dữ liệu đều có thể làm đối số `data`. Đây là **một lần ghi một đối tượng** tại `path`, không phải yêu cầu tạo nhiều khóa độc lập.

Khi ứng dụng dùng HTTP message converter hỗ trợ JSON (thường là Jackson trong môi trường Spring), dữ liệu Java được chuyển thành JSON. Cấu trúc và tên trường trong JSON là điều quan trọng cần xác minh; Vault không hiểu “ý nghĩa” tên thuộc tính Java.

## 3. Cách 1: ghi bằng Map

`Map<String, Object>` là cách đơn giản khi muốn kiểm soát trực tiếp những tên trường gửi tới Vault. Đây cũng là cách phù hợp khi schema tương đối nhỏ hoặc được xây dựng từ cấu hình có kiểm soát.

```java
import java.util.LinkedHashMap;
import java.util.Map;

Map<String, Object> payload = new LinkedHashMap<>();
payload.put("api_key", "fake-key-a");
payload.put("endpoint", "https://sandbox.example.invalid");

kv.put("payments/gateway", payload);
```

Payload JSON mong muốn ở API KV v1:

```http
POST /v1/kv-lab/payments/gateway HTTP/1.1
Content-Type: application/json

{
  "api_key": "fake-key-a",
  "endpoint": "https://sandbox.example.invalid"
}
```

Đoạn HTTP chỉ minh họa **cấu trúc request và đường dẫn**; client Vault thật chịu trách nhiệm thêm xác thực. Không tự nhúng token vào mã nguồn hoặc tài liệu ghi log.

Ưu điểm của `Map` là thấy ngay tên trường và kiểu dữ liệu:

```java
Map<String, Object> settings = new LinkedHashMap<>();
settings.put("api_key", "fake-key-a");        // String
settings.put("enabled", true);               // Boolean
settings.put("max_retries", 3);              // Integer
settings.put("labels", Map.of("env", "dev")); // đối tượng JSON lồng nhau

kv.put("payments/gateway", settings);
```

KV v1 lưu các giá trị đã được tuần tự hóa, không áp một schema Java cố định cho chúng. Nếu code đọc đang kỳ vọng `max_retries` là số nhưng bên ghi đổi thành chuỗi, lỗi ánh xạ hoặc lỗi nghiệp vụ có thể xuất hiện về sau.

Một số lưu ý với `Map`:

- `Map.of(...)` tiện cho giá trị cố định, nhưng **không chấp nhận key hoặc value `null`**; thao tác tạo Map sẽ báo lỗi khi chứa `null`. `LinkedHashMap` cho phép xây dựng từng trường và kiểm tra đầu vào.
- Không để dữ liệu do người dùng bên ngoài tự quyết định tên khóa hoặc đường dẫn secret mà không có kiểm tra. Hãy giữ schema và đường dẫn ghi ở tầng ứng dụng được kiểm soát.
- Dù `Map` có nhiều phần tử, `kv.put` vẫn ghi **một secret** tại đường dẫn `payments/gateway`.
- Việc thứ tự thêm trường vào `LinkedHashMap` được giữ trong cấu trúc Java không có nghĩa ứng dụng nên phụ thuộc vào thứ tự trường JSON hoặc thứ tự Vault trả về.

## 4. Cách 2: ghi một đối tượng Java

Khi ứng dụng có schema ổn định, một DTO/POJO diễn đạt rõ các trường bắt buộc và giúp trình biên dịch kiểm tra tên thuộc tính. Spring Vault có thể ghi đối tượng đó nếu bộ chuyển đổi JSON của ứng dụng hỗ trợ kiểu dữ liệu được truyền vào.

Ví dụ DTO có tên trường JSON `api_key`, trong khi tên thuộc tính Java tuân theo camelCase `apiKey`:

```java
import com.fasterxml.jackson.annotation.JsonProperty;

public class GatewaySecret {

    @JsonProperty("api_key")
    private String apiKey;

    private String endpoint;

    public GatewaySecret() {
        // Hữu ích khi framework cần tạo đối tượng khi đọc dữ liệu.
    }

    public GatewaySecret(String apiKey, String endpoint) {
        this.apiKey = apiKey;
        this.endpoint = endpoint;
    }

    public String getApiKey() {
        return apiKey;
    }

    public void setApiKey(String apiKey) {
        this.apiKey = apiKey;
    }

    public String getEndpoint() {
        return endpoint;
    }

    public void setEndpoint(String endpoint) {
        this.endpoint = endpoint;
    }
}
```

Khi lưu, chỉ cần:

```java
GatewaySecret secret = new GatewaySecret(
        "fake-key-a",
        "https://sandbox.example.invalid"
);

kv.put("payments/gateway", secret);
```

Với cấu hình Jackson áp dụng `@JsonProperty("api_key")`, đối tượng được tuần tự hóa thành cùng nội dung:

```json
{
  "api_key": "fake-key-a",
  "endpoint": "https://sandbox.example.invalid"
}
```

Nếu bỏ `@JsonProperty` và dùng cấu hình Jackson mặc định, thuộc tính Java `apiKey` thường tạo trường JSON `apiKey`, **khác** `api_key`. Vault sẽ lưu đúng trường mà client gửi, nên code đọc bằng `data.get("api_key")` sẽ không tìm thấy trường `apiKey`. Do đó, **tên trường là một phần của hợp đồng dữ liệu** giữa bên ghi và bên đọc.

### Vì sao nên dùng DTO chuyên dụng?

Trong ứng dụng thực tế, tránh ghi trực tiếp cả đối tượng nghiệp vụ lớn vào Vault:

```java
// Không nên dùng một entity có nhiều thuộc tính nội bộ,
// rồi vô tình ghi tất cả getter được JSON serializer nhìn thấy.
kv.put("payments/gateway", fullPaymentAccountEntity);
```

Một DTO nhỏ chỉ chứa những trường dự kiến lưu (`api_key` và `endpoint`) giúp tránh ghi thừa dữ liệu, tránh thay đổi ngoài ý muốn khi entity có thêm thuộc tính, và dễ kiểm tra schema trước khi ghi. Nếu dùng annotation như `@JsonProperty`, `@JsonIgnore` hoặc cấu hình custom serializer, cần xác minh payload thực tế trong kiểm thử tích hợp.

## 5. Ví dụ service hỗ trợ cả Map và POJO

Đây là một service Spring dùng chung **một mount và một đường dẫn secret**. Nó minh họa hai lựa chọn payload; mỗi thao tác `write...` đều ghi một bản đầy đủ. Giả định ứng dụng đã cung cấp bean `VaultOperations` kết nối tới Vault và có xác thực phù hợp.

```java
import java.util.LinkedHashMap;
import java.util.Map;

import org.springframework.stereotype.Service;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.support.VaultResponse;
import org.springframework.vault.support.VaultResponseSupport;

@Service
public class GatewaySecretService {

    private static final String MOUNT = "kv-lab";
    private static final String PATH = "payments/gateway";

    private final VaultKeyValueOperations kv;

    public GatewaySecretService(VaultOperations vaultOperations) {
        this.kv = vaultOperations.opsForKeyValue(MOUNT, KeyValueBackend.KV_1);
    }

    public void writeWithMap(String apiKey, String endpoint) {
        validate(apiKey, endpoint);

        Map<String, Object> data = new LinkedHashMap<>();
        data.put("api_key", apiKey);
        data.put("endpoint", endpoint);

        kv.put(PATH, data);
    }

    public void writeWithPojo(String apiKey, String endpoint) {
        validate(apiKey, endpoint);

        GatewaySecret data = new GatewaySecret(apiKey, endpoint);
        kv.put(PATH, data);
    }

    public Map<String, Object> readCurrentFields() {
        VaultResponse response = kv.get(PATH);
        if (response == null || response.getData() == null) {
            throw new IllegalStateException("Thiếu secret payments/gateway");
        }
        return response.getData();
    }

    public GatewaySecret readCurrentPojo() {
        VaultResponseSupport<GatewaySecret> response =
                kv.get(PATH, GatewaySecret.class);

        if (response == null || response.getData() == null) {
            throw new IllegalStateException("Thiếu secret payments/gateway");
        }
        return response.getData();
    }

    private static void validate(String apiKey, String endpoint) {
        if (apiKey == null || apiKey.isBlank()) {
            throw new IllegalArgumentException("apiKey không được để trống");
        }
        if (endpoint == null || endpoint.isBlank()) {
            throw new IllegalArgumentException("endpoint không được để trống");
        }
    }
}
```

Trong ví dụ này, `GatewaySecret` là DTO được định nghĩa ở phần trước. Service sử dụng Java có `String.isBlank()` (Java 11 trở lên).

**Cách dùng trong thử nghiệm:**

```java
service.writeWithMap("fake-key-a", "https://sandbox.example.invalid");

Map<String, Object> fromMap = service.readCurrentFields();
// fromMap.get("api_key") == "fake-key-a"

service.writeWithPojo("fake-key-b", "https://sandbox.example.invalid");

GatewaySecret fromPojo = service.readCurrentPojo();
// fromPojo.getApiKey() == "fake-key-b"
```

Giá trị `api_key` minh họa luôn là giả. Trong dịch vụ thật, không log toàn bộ `fromMap` hay `fromPojo` vì chúng chứa dữ liệu bí mật. Service trên mô tả API lưu trữ; trong thực tế, **workload chỉ đọc** nên dùng thành phần chỉ cung cấp phương thức đọc, còn quy trình ghi/luân chuyển nên được cấp danh tính và quyền riêng.

## 6. Map và POJO: chọn phương án nào?

| Tiêu chí | `Map<String, Object>` | DTO/POJO |
| --- | --- | --- |
| Khai báo schema | Tên trường được điền bằng chuỗi tại chỗ. | Thuộc tính Java được khai báo rõ, có thể thêm validation. |
| Hỗ trợ dữ liệu linh hoạt | Thuận tiện với tập trường thay đổi hoặc dữ liệu lồng nhau. | Hợp với cấu trúc tương đối ổn định. |
| Lỗi sai tên trường | Dễ gõ nhầm chuỗi `"api_key"`. | Có thể sai giữa tên getter/field và tên JSON; cần kiểm soát mapping. |
| Kiểm tra kiểu ở thời điểm biên dịch | Phần giá trị thường là `Object`. | Các thuộc tính có kiểu Java cụ thể. |
| Kiểm soát trường được ghi | Xây dựng Map tường minh. | Dùng DTO chuyên dụng và annotation/serializer phù hợp. |
| Phù hợp với | Công cụ cấu hình, dữ liệu động có kiểm soát. | Secret có hợp đồng dữ liệu ổn định trong ứng dụng. |

**Cả hai đều được Vault tiếp nhận dưới dạng dữ liệu JSON tại cùng một secret path.** Vault không đánh dấu “bản ghi này từng đến từ Map” hay “bản ghi này từng đến từ Java bean”. Khả năng đọc lại phụ thuộc vào schema thực tế đã ghi.

### Giá trị null, thiếu trường và kiểu dữ liệu

Cần định nghĩa quy tắc trước khi lưu:

- Nếu một trường **không có trong payload**, nó sẽ không có trong bản dữ liệu hiện hành sau lần `put` đó. KV v1 không tự kế thừa trường từ bản cũ.
- Nếu một serializer ghi trường JSON với giá trị `null`, đó là dữ liệu được gửi đi; **không đồng nghĩa** bảo toàn giá trị cũ. Một số cấu hình Jackson có thể loại bỏ trường `null`. Hãy xác minh cấu hình serialization thực tế.
- Với các kiểu đặc biệt như ngày giờ, enum, số lớn hoặc object lồng nhau, cần thống nhất JSON mong muốn và bộ chuyển đổi; không giả định tự động khôi phục đúng kiểu Java từ mọi giá trị.
- Với bí mật bắt buộc như `api_key`, nên kiểm tra đầu vào hợp lệ trước khi ghi và kiểm tra lại sau khi đọc. Không dùng giá trị mặc định trống để che giấu việc thiếu secret.

## 7. KV v1 ghi đè toàn bộ bản dữ liệu

Đây là điểm dễ mắc lỗi nhất khi viết chức năng ghi bằng `Map` hoặc POJO. Giả sử tại thời điểm đầu tiên:

```java
kv.put("payments/gateway", Map.of(
        "api_key", "fake-key-a",
        "endpoint", "https://sandbox.example.invalid"
));
```

Bản dữ liệu hiện hành:

```json
{
  "api_key": "fake-key-a",
  "endpoint": "https://sandbox.example.invalid"
}
```

Một tiến trình khác ghi **chỉ một trường**:

```java
kv.put("payments/gateway", Map.of("api_key", "fake-key-b"));
```

Kết quả là:

```json
{
  "api_key": "fake-key-b"
}
```

Trường `endpoint` đã bị **mất khỏi bản dữ liệu hiện hành**. `put` trong KV v1 là *replace*, **không phải partial update/merge**. Ghi POJO cũng tương tự: nếu POJO chỉ được serialize ra `api_key`, các trường còn lại không được giữ.

Một quy trình đổi API key an toàn hơn về mặt cấu trúc sẽ xây dựng **payload đầy đủ** từ nguồn cấu hình đáng tin cậy:

```java
kv.put("payments/gateway", Map.of(
        "api_key", "fake-key-c",
        "endpoint", "https://sandbox.example.invalid"
));
```

### Vì sao đọc rồi sửa rồi ghi vẫn có rủi ro?

Một cách tưởng như hợp lý là:

1. Tiến trình A đọc dữ liệu hiện hành.
2. Tiến trình B đọc dữ liệu hiện hành.
3. A sửa `api_key` rồi ghi toàn bộ đối tượng.
4. B sửa `endpoint` trên **bản đã đọc trước khi A ghi**, rồi ghi toàn bộ.

Kết quả: B có thể vô tình ghi đè `api_key` mới của A bằng giá trị cũ. Đây là lỗi **lost update**. KV v1 không có số phiên bản hay cơ chế CAS của KV v2 để từ chối việc ghi trên snapshot cũ.

Đối với dữ liệu cần bảo toàn đồng thời:

- Tổ chức **một luồng ghi có thẩm quyền** hoặc một cơ chế điều phối các lần cập nhật.
- Nếu yêu cầu gồm lịch sử phiên bản hoặc CAS, cân nhắc **KV v2**, thay vì cố mô phỏng CAS bằng thao tác `get` rồi `put` ở KV v1.
- Phân tách các secret có vòng đời khác nhau thành đường dẫn khác nhau khi phù hợp, chẳng hạn một secret cho API key và một secret cho cấu hình ít thay đổi. Mỗi đường dẫn vẫn có semantics ghi đè của KV v1.

## 8. Quyền truy cập và vòng đời xác thực

Một ứng dụng Java dùng `VaultTemplate`/`VaultOperations` phải xác thực với Vault trước khi gọi `kv.put`. Có thể sử dụng token gắn với danh tính workload qua phương thức được tổ chức cho phép, chẳng hạn Kubernetes auth hoặc AppRole. Xác thực xác định **ai đang gọi**, còn ACL policy xác định **đường dẫn nào được ghi**.

Với mount `kv-lab` và secret `payments/gateway`, policy cấp quyền ghi tối thiểu cho quy trình quản trị:

```hcl
path "kv-lab/payments/gateway" {
  capabilities = ["create", "update"]
}
```

`create` cho phép tạo dữ liệu tại đường dẫn chưa tồn tại, `update` cho phép ghi đè đường dẫn đã có. Nếu workload cần đọc để kiểm tra, cấp `read` theo nhu cầu, tốt nhất bằng danh tính/role phù hợp. Đừng cấp `delete` chỉ để gọi `put`.

Một workload chỉ đọc có policy riêng:

```hcl
path "kv-lab/payments/gateway" {
  capabilities = ["read"]
}
```

**Lưu ý đường dẫn ACL:** policy dùng **full logical path** `kv-lab/payments/gateway`, còn Java gọi `kv.put("payments/gateway", ...)` vì mount đã khai báo tại `opsForKeyValue("kv-lab", KV_1)`. Với KV v1 không tự thêm `data/` như KV v2.

Token có thể hết hạn hoặc bị thu hồi; lỗi xác thực hoặc ACL có thể làm thao tác ghi thất bại. Tuy nhiên, bản secret KV v1 là dữ liệu tĩnh, không có lease riêng để tự thu hồi như dynamic credentials. Vòng đời token **không tự xóa** một secret đã được ghi. Các chức năng Transit encryption và PKI là API của những secrets engine khác; `kv.put` dùng để lưu dữ liệu KV.

## 9. Đọc lại và xác minh sau khi ghi

Khi `put` hoàn tất, có thể đọc lại bằng cùng `VaultKeyValueOperations` nếu danh tính có `read`:

```java
VaultResponse response = kv.get("payments/gateway");

if (response == null || response.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret sau khi ghi");
}

Map<String, Object> current = response.getData();
Object key = current.get("api_key");
Object endpoint = current.get("endpoint");

// Kiểm tra sự có mặt/kiểu dữ liệu; không in các giá trị vào log.
if (!(key instanceof String) || !(endpoint instanceof String)) {
    throw new IllegalStateException("Schema secret sau ghi không hợp lệ");
}
```

Với DTO có mapping tương thích, cũng có thể dùng:

```java
import org.springframework.vault.support.VaultResponseSupport;

VaultResponseSupport<GatewaySecret> response =
        kv.get("payments/gateway", GatewaySecret.class);

if (response == null || response.getData() == null) {
    throw new IllegalStateException("Thiếu secret payments/gateway");
}

GatewaySecret current = response.getData();
// Kiểm tra các trường bắt buộc thay vì log toàn bộ đối tượng.
```

Hai phương thức `get` đều đọc bản hiện hành của cùng secret. `get(path)` cho phép quan sát `Map`, còn `get(path, GatewaySecret.class)` ánh xạ dữ liệu vào Java bean.

Nếu chỉ cần kiểm tra thủ công trong môi trường thử nghiệm, sử dụng CLI:

```bash
vault kv get -mount=kv-lab payments/gateway
```

Lệnh có thể hiển thị **giá trị secret** trong terminal. Chỉ dùng dữ liệu giả trong bài lab, không chuyển toàn bộ đầu ra chứa secret vào log CI, báo cáo lỗi hoặc hệ thống giám sát.

## 10. Xử lý các lỗi điển hình

| Tình huống | Biểu hiện/Nguyên nhân | Hướng xử lý |
| --- | --- | --- |
| `put` bị từ chối với lỗi quyền | Token không có `create` khi tạo mới hoặc `update` khi ghi đè. | Kiểm tra ACL policy trên **full path** của secret và danh tính workload. |
| Ghi thành công nhưng `get` không có dữ liệu mong đợi | Dùng sai mount, sai đường dẫn tương đối hoặc đọc ở mount khác. | Đối chiếu `opsForKeyValue("kv-lab", KV_1)` và `put/get("payments/gateway")`. |
| Dữ liệu trong Vault có `apiKey`, code đọc `api_key` | Tên field POJO serialize khác hợp đồng dữ liệu. | Thống nhất schema, cấu hình `@JsonProperty` hoặc key Map. |
| Một trường cũ biến mất sau khi ghi | Lần `put` mới không chứa trường đó. | Luôn gửi toàn bộ schema cần lưu; không coi `put` là merge. |
| Mất cập nhật khi hai tiến trình cùng ghi | KV v1 không có phiên bản/CAS; ghi sau thay thế ghi trước. | Dùng một luồng ghi, điều phối hoặc cân nhắc KV v2. |
| `Map.of` lỗi trước khi gọi Vault | Key hoặc value truyền vào là `null`. | Kiểm tra đầu vào; chủ động định nghĩa chính sách trường tùy chọn. |
| DTO ghi ra JSON không mong đợi | Getter/annotation hoặc converter làm thay đổi tên/kiểu/những trường được serialize. | Dùng DTO nhỏ, kiểm thử round-trip thực tế và kiểm tra cấu hình JSON. |
| Không ghi được do sự cố Vault | Hết hạn token, lỗi mạng/TLS hoặc Vault không sẵn sàng. | Phân biệt lỗi xác thực, ACL, kết nối; retry có giới hạn nếu phù hợp và chú ý `put` là ghi đè. |

Không bắt mọi lỗi rồi ghi lại bằng một payload trống; thao tác đó có thể làm dữ liệu bí mật bị thay thế. Khi ghi log và metric, nên ghi **tên thao tác, trạng thái, loại lỗi** ở mức cần thiết; không đưa token, password, API key hoặc toàn bộ JSON secret vào log.

## 11. Bài thực hành và kiểm thử tích hợp

Thực hiện trong Vault thử nghiệm riêng biệt, dùng **giá trị giả** và hai danh tính: một danh tính được phép tạo/cập nhật secret, một danh tính chỉ có quyền đọc.

1. **Xác nhận engine:** Dùng `vault secrets list -detailed` để đảm bảo `kv-lab/` thực sự là KV v1; nếu chưa có và đủ quyền, tạo bằng `vault secrets enable -path=kv-lab -version=1 kv`.
2. **Ghi bằng Map:** Gọi `writeWithMap("fake-key-a", "https://sandbox.example.invalid")`. Dùng `get` hoặc CLI xác nhận secret chứa đúng hai trường `api_key` và `endpoint`.
3. **Ghi bằng POJO:** Gọi `writeWithPojo("fake-key-b", "https://sandbox.example.invalid")`. Đọc lại cả dạng `Map` và `GatewaySecret`; xác nhận cả hai dùng cùng tên field và dữ liệu hiện hành là bản B.
4. **Thử ghi thiếu trường:** Gọi `kv.put("payments/gateway", Map.of("api_key", "fake-key-c"))` với danh tính có quyền ghi. Đọc lại và xác nhận `endpoint` **không còn**. Đây là phép thử quan trọng để chứng minh semantics của KV v1.
5. **Khôi phục schema đầy đủ trong lab:** Ghi lại hai trường bằng Map hoặc POJO đầy đủ. Không dựa vào “version trước” vì KV v1 không lưu lịch sử cho thao tác đọc lại.
6. **Kiểm tra ACL:** Dùng danh tính chỉ có `read`; xác nhận đọc được nhưng `put` bị từ chối. Dùng danh tính ghi được cấp đúng `create`/`update` để xác nhận thao tác ghi hợp lệ.
7. **Kiểm tra lỗi ánh xạ:** Tạo DTO không có `@JsonProperty("api_key")` trong một thử nghiệm cô lập. Đối chiếu JSON thực tế của `apiKey` với `api_key`, sau đó sửa annotation hoặc quy ước tên trường.
8. **Kiểm tra đường dẫn sai:** Cố ý gọi `kv.put("kv-lab/payments/gateway", payload)` để thấy request bị nhắm sang đường dẫn khác trong mount; kiểm chứng đường dẫn đúng trước khi dọn dữ liệu lab.
9. **Kiểm tra đầu vào sai:** Thử `apiKey` rỗng và `endpoint` rỗng, xác nhận validation từ chối **trước** lời gọi `kv.put`, tránh ghi đè secret bằng dữ liệu không hợp lệ.

Khi viết integration test, có thể dùng Vault được khởi tạo riêng qua Testcontainers hoặc một Vault test server có cấu hình kiểm soát được. Mock `VaultKeyValueOperations` hữu ích để kiểm tra service có gọi `put` với đúng đường dẫn và payload, nhưng **không đủ** để chứng minh hành vi ghi đè, chuyển đổi JSON hoặc ACL của Vault thật.

### Tự kiểm tra

1. Gọi `kv.put("payments/gateway", Map.of("api_key", "x", "endpoint", "y"))` ghi bao nhiêu **đường dẫn secret** trong KV v1?
2. Vì sao `Map` với key `"api_key"` và POJO với property `apiKey` có thể tạo kết quả khác nhau?
3. Nếu lần ghi đầu có `api_key` và `endpoint`, nhưng lần sau chỉ ghi `api_key`, điều gì xảy ra với `endpoint`?
4. Nếu policy chỉ có `read` thì `kv.put` có hoạt động không? Khi nào cần `create` hoặc `update`?
5. Khi hai tiến trình cùng đọc rồi ghi một đường dẫn KV v1, vì sao một lần `get` trước khi `put` không đủ để bảo vệ khỏi *lost update*?

## Tổng kết

Để ghi dữ liệu vào **một khóa KV v1** từ ứng dụng Java, lấy `VaultKeyValueOperations` qua `VaultOperations.opsForKeyValue("kv-lab", KeyValueBackend.KV_1)` rồi gọi `kv.put("payments/gateway", data)`. `data` có thể là `Map` hoặc DTO/POJO; cả hai đều được chuyển thành các trường dữ liệu của **cùng một secret**. Cần nhất quán tên field JSON, kiểm tra dữ liệu trước khi ghi, nhớ rằng `put` **thay thế toàn bộ** bản hiện hành, cấp quyền `create`/`update` tối thiểu và kiểm thử round-trip cùng semantics ghi đè trên Vault thử nghiệm.
