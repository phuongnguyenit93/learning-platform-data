# Lựa chọn API KV chuyên biệt hoặc thao tác đường dẫn trực tiếp trong Spring Vault

## Mục tiêu học tập

Sau bài học, bạn có thể:

- Phân biệt **API KV chuyên biệt** (`VaultKeyValueOperations`) và **API thao tác đường dẫn trực tiếp** (`VaultOperations.read/write/list/delete`) trong **Spring Vault**.
- Quyết định khi nào nên dùng `VaultTemplate`/`VaultOperations.opsForKeyValue(..., KeyValueBackend.KV_1)` để thao tác với **HashiCorp Vault KV phiên bản 1**, và khi nào cần gọi endpoint Vault cấp thấp.
- Xác định đúng **mount path**, **secret path tương đối**, **full logical path** và phần tiền tố `/v1/` của HTTP API.
- Hiểu cách JSON request/response của KV v1 khác KV v2, đặc biệt khi dùng API cấp thấp không tự xử lý giao thức KV.
- Áp dụng ACL tối thiểu, phân loại lỗi và kiểm thử tích hợp để tránh đọc hoặc ghi nhầm đường dẫn, sai phiên bản engine hay làm mất dữ liệu.

## 1. Hai mức trừu tượng của Spring Vault

HashiCorp Vault cung cấp một HTTP API cho các secrets engine, authentication methods và endpoint hệ thống. Trong ứng dụng Java, **Spring Vault** cung cấp `VaultTemplate` — một triển khai của interface `VaultOperations` — để giao tiếp với Vault bằng cấu hình endpoint, HTTP client, TLS và xác thực đã thiết lập.

Khi làm việc với secrets engine **KV**, có hai cách sử dụng phổ biến:

1. **API KV chuyên biệt:** Lấy `VaultKeyValueOperations` từ `VaultOperations.opsForKeyValue(mount, backend)`. Ứng dụng truyền **đường dẫn secret tương đối**, còn Spring Vault xây dựng endpoint phù hợp với backend đã chọn.
2. **API cấp thấp theo đường dẫn:** Gọi trực tiếp `VaultOperations.read`, `write`, `list` hoặc `delete` bằng **đường dẫn logic đầy đủ**. Ứng dụng chịu trách nhiệm chọn đúng đường dẫn endpoint và đúng cấu trúc payload mà Vault yêu cầu.

```text
Ứng dụng Java
    |
    v
VaultOperations / VaultTemplate
    |
    +-- opsForKeyValue("kv-orders", KV_1) --> VaultKeyValueOperations
    |                                      |
    |                                      +-- get("orders/api")
    |                                      +-- put("orders/api", data)
    |                                      +-- list("orders")
    |                                      +-- delete("orders/api")
    |
    +-- read("kv-orders/orders/api")
    +-- write("kv-orders/orders/api", data)
    +-- list("kv-orders/orders")
    +-- delete("kv-orders/orders/api")
                       |
                       v
           HashiCorp Vault KV v1
```

Hai nhánh có thể cùng truy cập một secret. Khác biệt nằm ở **mức độ trừu tượng, quy tắc truyền đường dẫn và trách nhiệm xử lý giao thức**; chúng không đại diện cho hai hệ thống lưu trữ khác nhau.

### Các thành phần cần nhớ

| Thành phần | Trách nhiệm |
| --- | --- |
| `VaultTemplate` | Client Spring Vault triển khai `VaultOperations`; gửi request tới Vault bằng cơ chế kết nối/xác thực được cấu hình. |
| `VaultOperations` | Interface hỗ trợ thao tác Vault tổng quát, bao gồm đọc, ghi, liệt kê, xóa theo đường dẫn và truy cập API của secrets engine. |
| `VaultKeyValueOperations` | API chuyên biệt cho secret KV, với các thao tác `get`, `put`, `list`, `delete` và đọc dữ liệu có ánh xạ kiểu. |
| `KeyValueBackend.KV_1` | Chọn **giao thức KV v1** cho API KV; không tự bật hoặc chuyển đổi secrets engine ở Vault. |
| `KeyValueBackend.KV_2` | Chọn giao thức KV v2, có endpoint và định dạng dữ liệu khác; không có nghĩa đọc data version 2 của một secret. |

**Quy tắc lựa chọn mặc định:** Với các thao tác CRUD thông thường trên KV v1, ưu tiên **`VaultKeyValueOperations`**. Dùng API đường dẫn trực tiếp khi bạn có lý do rõ ràng để truy cập endpoint cấp thấp, cần kiểm soát HTTP payload hoặc cần làm việc với một Vault API không được API KV chuyên biệt biểu diễn thuận tiện.

## 2. Một ví dụ xuyên suốt: mount khác đường dẫn secret

Giả sử môi trường thực hành có một KV engine **phiên bản 1** được mount ở `kv-orders/`. Ta lưu cấu hình cho client gọi API thanh toán tại `orders/api`:

```text
HashiCorp Vault
└── kv-orders/                  ← mount KV v1
    └── orders/
        └── api                 ← một secret có các field
            ├── api_key
            └── endpoint
```

Đường dẫn cụ thể:

| Loại | Giá trị | API tương ứng |
| --- | --- | --- |
| Mount path | `kv-orders` | `opsForKeyValue("kv-orders", KV_1)` |
| Relative secret path | `orders/api` | `kv.get("orders/api")`, `kv.put("orders/api", ...)` |
| Full logical path | `kv-orders/orders/api` | `vaultOperations.read("kv-orders/orders/api")` |
| HTTP API path KV v1 | `/v1/kv-orders/orders/api` | Request REST gửi đến Vault |

Nếu gọi `get` trên một đối tượng `VaultKeyValueOperations` đã chọn mount `kv-orders`, **không** truyền thêm `kv-orders/` vào `get`. Nếu gọi `VaultOperations.read` cấp thấp, lại **phải** truyền đường dẫn đầy đủ gồm mount.

Tiền tố `/v1/` thuộc giao thức HTTP Vault, **không phải** phiên bản secrets engine KV. Không thêm `/v1/` vào các tham số đường dẫn của Spring Vault.

### Kiểm tra mount trước khi viết code

Trong Vault thử nghiệm, nếu mount chưa tồn tại và người dùng có quyền quản trị:

```bash
vault secrets enable -path=kv-orders -version=1 kv
```

Nếu mount đã tồn tại, không bật lại. Kiểm tra:

```bash
vault secrets list -detailed
```

Đối chiếu mount `kv-orders/` có loại `kv` và cấu hình `version=1`. Một tên mount như `secret/`, `kv/` hoặc `kv-orders/` **không cho biết chắc** phiên bản KV. Với mount KV v2, cách xây URL và payload sẽ khác.

## 3. Cách ưu tiên: dùng VaultKeyValueOperations cho KV v1

Khởi tạo API KV từ bean `VaultOperations` đã được Spring cung cấp:

```java
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;

VaultKeyValueOperations kv = vaultOperations.opsForKeyValue(
        "kv-orders", KeyValueBackend.KV_1);
```

Sau khi tạo `kv`, mọi thao tác với secret bên trong mount dùng **đường dẫn tương đối**:

```java
import java.util.Map;
import org.springframework.vault.support.VaultResponse;

// Ghi toàn bộ object hiện hành của secret.
kv.put("orders/api", Map.of(
        "api_key", "fake-key-for-learning",
        "endpoint", "https://sandbox.example.invalid"
));

// Đọc secret hiện hành.
VaultResponse response = kv.get("orders/api");
if (response == null || response.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret orders/api");
}

Object apiKey = response.getData().get("api_key");
if (!(apiKey instanceof String) || ((String) apiKey).isBlank()) {
    throw new IllegalStateException("Secret thiếu api_key hợp lệ");
}

// Liệt kê tên ở tiền tố orders/ (cần capability list).
java.util.List<String> names = kv.list("orders");

// Xóa một secret tại đúng đường dẫn (chỉ thực hiện trong lab).
// kv.delete("orders/api");
```

Ở đây `put`, `get`, `list` và `delete` đều cùng làm việc dưới mount `kv-orders`. Chương trình không phải tự nối mount vào mỗi lời gọi.

### API chuyên biệt giúp gì?

- **Giảm sai đường dẫn:** Mount được chọn một lần ở `opsForKeyValue`; các lời gọi chỉ nhận path bên trong mount.
- **Che bớt khác biệt giao thức:** Khi chọn đúng backend, API chuyên biệt biết phải giao tiếp với KV v1 hay KV v2 như thế nào đối với các thao tác phổ biến.
- **Hỗ trợ đọc có kiểu:** Có thể dùng `get("orders/api", ClientSecret.class)` để ánh xạ nội dung secret thành một DTO thay vì tự thao tác map thô.
- **Mã nguồn dễ đọc:** `kv.put` nói rõ đây là thao tác lưu KV, thay vì một lời gọi `write` mà người đọc phải suy ra endpoint.
- **Dễ kiểm thử tại ranh giới module:** Có thể mock `VaultKeyValueOperations` để kiểm tra service truyền đúng path và payload mà không phải mô phỏng cấu trúc HTTP.

Tuy nhiên, API này **không tự xác minh mount thật** đã là KV v1 vào lúc tạo đối tượng. Nếu chọn sai backend, lỗi có thể chỉ xuất hiện khi request được gửi. Nó cũng không tự cấp ACL, tự phục hồi token hết hạn hay biến KV v1 thành engine có lịch sử phiên bản.

## 4. Thao tác trực tiếp bằng VaultOperations

Cùng secret ở `kv-orders/orders/api` có thể truy cập qua `VaultOperations` cấp thấp:

```java
import java.util.Map;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.support.VaultResponse;

// Ghi dữ liệu KV v1 bằng full logical path.
vaultOperations.write("kv-orders/orders/api", Map.of(
        "api_key", "fake-key-for-learning",
        "endpoint", "https://sandbox.example.invalid"
));

// Đọc dữ liệu ở full logical path.
VaultResponse raw = vaultOperations.read("kv-orders/orders/api");
if (raw == null || raw.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret orders/api");
}

Map<String, Object> data = raw.getData();
Object apiKey = data.get("api_key");
if (!(apiKey instanceof String)) {
    throw new IllegalStateException("Trường api_key không phải String");
}

// LIST cấp thấp: vẫn cần full logical path.
java.util.List<String> entries = vaultOperations.list("kv-orders/orders");

// DELETE cấp thấp: xóa đúng một secret, không xóa đệ quy.
// vaultOperations.delete("kv-orders/orders/api");
```

Điểm khác ở đây là `VaultOperations` **không được cố định sẵn mount** qua một đối tượng KV riêng. Bạn chỉ định một **đường dẫn logic đầy đủ** trong mỗi lời gọi. Với KV v1, payload gửi tới endpoint ghi có các trường secret trực tiếp trong JSON:

```http
POST /v1/kv-orders/orders/api HTTP/1.1
Content-Type: application/json

{
  "api_key": "fake-key-for-learning",
  "endpoint": "https://sandbox.example.invalid"
}
```

Đây là **minh họa cấu trúc request**; phần xác thực được Vault client quản lý theo cấu hình. Không viết token trực tiếp vào mã nguồn hoặc đưa token vào ví dụ log.

Với KV v1, dữ liệu của một phản hồi đọc REST nằm trực tiếp trong trường JSON `data`. `VaultResponse.getData()` của Spring Vault cung cấp map các field đó. Với API cấp thấp, ứng dụng cần biết rõ endpoint đang gọi và hình dạng phản hồi tương ứng.

### Những trường hợp API cấp thấp hữu ích

- Bạn cần giao tiếp với một **endpoint Vault cụ thể** mà interface KV chuyên biệt không biểu diễn đầy đủ.
- Bạn đang viết công cụ tích hợp hoặc chẩn đoán, cần đối chiếu request thực tế với tài liệu HTTP API Vault.
- Bạn xây dựng một adapter chung cho nhiều loại endpoint được cho phép, với kiểm soát đường dẫn và kiểu payload rõ ràng.
- Bạn cần thao tác cấp hệ thống hoặc tính năng nâng cao riêng của một engine, và đã xác nhận không có interface Spring Vault chuyên biệt phù hợp hơn.

Tuy nhiên, **không nên** chuyển mọi thao tác KV thông thường sang `read`/`write` cấp thấp chỉ để giảm một bước tạo `VaultKeyValueOperations`. Khi đó code phải tự quản lý mount, URL logic, dữ liệu lồng nhau và khác biệt phiên bản ở nhiều nơi.

## 5. Bảng so sánh và tiêu chí chọn API

| Câu hỏi | `VaultKeyValueOperations` | `VaultOperations` trực tiếp |
| --- | --- | --- |
| Gọi API như thế nào? | `get`, `put`, `list`, `delete` | `read`, `write`, `list`, `delete` |
| Chọn mount ở đâu? | Một lần trong `opsForKeyValue(mount, backend)` | Trong full logical path của từng request |
| Đường dẫn truyền vào | `orders/api` | `kv-orders/orders/api` |
| Có tự xử lý khác biệt KV v1/v2? | Theo `KeyValueBackend` đã chọn, với các thao tác được hỗ trợ | **Không**: code phải chọn endpoint/payload chính xác |
| Đọc đối tượng Java theo schema | Có `get(path, Class<T>)` | Có thể xử lý phản hồi, nhưng phải chú ý envelope của từng endpoint |
| Phù hợp CRUD KV thông thường | **Ưu tiên** | Dùng khi có lý do kỹ thuật rõ ràng |
| Phù hợp endpoint Vault khác KV | Không phải mục tiêu | Có thể, với đường dẫn/payload được kiểm soát |
| Có bỏ qua xác thực/ACL? | Không | Không |
| Có tạo history/CAS cho KV v1? | Không | Không |
| Nguy cơ chính | Chọn sai mount/backend; dữ liệu sai schema | Chọn sai full path, sai envelope, nhầm endpoint giữa các phiên bản |

Một quy tắc ra quyết định:

```text
Cần truy cập Vault?
    |
    +-- Thao tác CRUD secret KV thông thường?
    |       |
    |       +-- Có --> Dùng VaultKeyValueOperations
    |                  và KeyValueBackend khớp mount thật.
    |
    +-- Cần tính năng versioning KV v2?
    |       |
    |       +-- Có --> Kiểm tra API versioned KV chuyên biệt
    |                  trước khi tự viết request cấp thấp.
    |
    +-- Cần endpoint không được API chuyên biệt hỗ trợ?
            |
            +-- Có --> Cân nhắc VaultOperations cấp thấp,
                       kiểm soát đường dẫn, payload và ACL.
```

Khi chọn một hướng, nên **đóng gói** nó ở một service/repository chịu trách nhiệm truy cập Vault. Những lớp nghiệp vụ còn lại chỉ làm việc với cấu hình đã được kiểm tra kiểu; không cần biết toàn bộ đường dẫn HTTP của Vault.

## 6. Cạm bẫy lớn: dùng trực tiếp API KV v2 như KV v1

Với KV v1, đọc tại `GET /v1/kv-orders/orders/api`; dữ liệu nằm ngay dưới `data` của phản hồi. Nhưng KV v2 có **endpoint riêng**:

```text
KV v1:
  GET  /v1/kv-orders/orders/api
  POST /v1/kv-orders/orders/api

KV v2 (mount giả định: kv-orders-v2):
  GET  /v1/kv-orders-v2/data/orders/api
  POST /v1/kv-orders-v2/data/orders/api
  LIST /v1/kv-orders-v2/metadata/orders
```

Khi gọi REST trực tiếp vào KV v2, **request ghi** phải có envelope `data`:

```json
{
  "data": {
    "api_key": "fake-key-for-learning",
    "endpoint": "https://sandbox.example.invalid"
  }
}
```

Và phần dữ liệu của **phản hồi đọc** có một lớp lồng nhau:

```json
{
  "data": {
    "data": {
      "api_key": "fake-key-for-learning",
      "endpoint": "https://sandbox.example.invalid"
    },
    "metadata": {
      "version": 1,
      "created_time": "2026-01-01T00:00:00Z",
      "deletion_time": "",
      "destroyed": false
    }
  }
}
```

Các giá trị và thời gian trên chỉ mang tính minh họa cấu trúc; không phải phản hồi từ hệ thống đang chạy.

### Gọi KV v2 qua VaultOperations cấp thấp

Nếu có mount **KV v2 thật** tên `kv-orders-v2/`, một lời gọi cấp thấp cần tự xử lý envelope:

```java
import java.util.Map;
import org.springframework.vault.support.VaultResponse;

Map<String, Object> secretData = Map.of(
        "api_key", "fake-key-for-learning",
        "endpoint", "https://sandbox.example.invalid"
);

// API cấp thấp: caller phải cung cấp "data" envelope của KV v2.
vaultOperations.write(
        "kv-orders-v2/data/orders/api",
        Map.of("data", secretData)
);

VaultResponse rawV2 =
        vaultOperations.read("kv-orders-v2/data/orders/api");

if (rawV2 == null || rawV2.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret KV v2");
}

// VaultResponse.getData() của lời gọi trực tiếp chứa
// phần bên trong outer JSON "data": gồm "data" và "metadata".
Object nested = rawV2.getData().get("data");
if (!(nested instanceof Map<?, ?>)) {
    throw new IllegalStateException("Phản hồi KV v2 sai cấu trúc");
}

Map<?, ?> fields = (Map<?, ?>) nested;
Object key = fields.get("api_key");
if (!(key instanceof String)) {
    throw new IllegalStateException("Thiếu api_key kiểu String");
}
```

Đây là ví dụ đối chiếu để hiểu **trách nhiệm của API cấp thấp**, không phải lời khuyên bỏ API KV chuyên biệt. Với các thao tác KV v2 thông thường, có thể chọn `opsForKeyValue("kv-orders-v2", KeyValueBackend.KV_2)`; khi thực sự cần thao tác theo phiên bản, cân nhắc API versioned KV của Spring Vault phù hợp với phiên bản thư viện.

**Cảnh báo đường dẫn:** Nếu mount thật là KV v1 nhưng bạn gọi `write("kv-orders/data/orders/api", ...)`, Vault KV v1 có thể coi `data/orders/api` là **một secret path khác** bên trong mount — không phải “bật phiên bản 2”. Nếu ACL cho phép, dữ liệu có thể bị ghi nhầm chỗ. Điều này đặc biệt nguy hiểm khi công cụ kiểm thử chỉ xem HTTP request có thành công mà không xác minh đúng secret đích.

## 7. Ví dụ service đóng gói cả hai cách trên KV v1

Một service có thể cung cấp hai cách thực hiện để học và so sánh; trong ứng dụng sản xuất, nên **chọn một cách nhất quán** theo nhu cầu thay vì để lớp nghiệp vụ tùy ý thay đổi API và đường dẫn.

Ví dụ sau dùng Spring bean `VaultOperations` đã được cấu hình xác thực. Đường dẫn cố định, dữ liệu giả và không ghi secret vào log.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

import org.springframework.stereotype.Service;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.support.VaultResponse;

@Service
public class OrdersSecretGateway {

    private static final String MOUNT = "kv-orders";
    private static final String RELATIVE = "orders/api";
    private static final String FULL = "kv-orders/orders/api";

    private final VaultOperations vault;
    private final VaultKeyValueOperations kv;

    public OrdersSecretGateway(VaultOperations vaultOperations) {
        this.vault = vaultOperations;
        this.kv = vaultOperations.opsForKeyValue(MOUNT, KeyValueBackend.KV_1);
    }

    // Lựa chọn ưu tiên cho CRUD KV v1.
    public void replaceViaKvApi(String apiKey, String endpoint) {
        kv.put(RELATIVE, validatedPayload(apiKey, endpoint));
    }

    // Chỉ minh họa API cấp thấp: full logical path là bắt buộc.
    public void replaceViaDirectPath(String apiKey, String endpoint) {
        vault.write(FULL, validatedPayload(apiKey, endpoint));
    }

    public String readApiKeyViaKvApi() {
        return requiredApiKey(kv.get(RELATIVE));
    }

    public String readApiKeyViaDirectPath() {
        return requiredApiKey(vault.read(FULL));
    }

    public List<String> listViaKvApi() {
        return sortedNames(kv.list("orders"));
    }

    public List<String> listViaDirectPath() {
        return sortedNames(vault.list("kv-orders/orders"));
    }

    // Chỉ gọi trong lab với danh tính có quyền xóa.
    public void deleteViaKvApi() {
        kv.delete(RELATIVE);
    }

    // Tác động đến đúng secret tương tự, nhưng truyền full logical path.
    public void deleteViaDirectPath() {
        vault.delete(FULL);
    }

    private static Map<String, Object> validatedPayload(
            String apiKey, String endpoint) {

        if (apiKey == null || apiKey.isBlank()
                || endpoint == null || endpoint.isBlank()) {
            throw new IllegalArgumentException("Thiếu trường secret bắt buộc");
        }

        return Map.of(
                "api_key", apiKey,
                "endpoint", endpoint
        );
    }

    private static String requiredApiKey(VaultResponse response) {
        if (response == null || response.getData() == null) {
            throw new IllegalStateException("Không tìm thấy secret orders/api");
        }

        Object value = response.getData().get("api_key");
        if (!(value instanceof String) || ((String) value).isBlank()) {
            throw new IllegalStateException("Secret thiếu api_key hợp lệ");
        }

        return (String) value; // Không log giá trị trả về.
    }

    private static List<String> sortedNames(List<String> names) {
        if (names == null || names.isEmpty()) {
            return List.of();
        }

        List<String> copy = new ArrayList<>(names);
        copy.sort(String::compareTo);
        return List.copyOf(copy);
    }
}
```

Đoạn mã này dùng Java 11 trở lên do `String.isBlank()`, cũng như `Map.of` và `List.copyOf`. Trong ứng dụng thật, xử lý secret bằng một kiểu dữ liệu nghiệp vụ chuyên dụng, tránh để object chứa API key bị in qua `toString()` hoặc được tự động serialize vào HTTP response.

**Hai phương thức ghi ở ví dụ là hai lựa chọn thay thế, không phải hai bước cần chạy liên tiếp.** Nếu gọi cả hai, lần ghi thứ hai vẫn **thay thế toàn bộ** bản dữ liệu tại cùng đường dẫn KV v1. Đối với test, sử dụng dữ liệu giả và danh tính có quyền phù hợp để so sánh kết quả đọc.

### Đọc DTO có kiểu thay vì Map

Với API KV chuyên biệt, cũng có thể ánh xạ dữ liệu sang một Java bean:

```java
import org.springframework.vault.support.VaultResponseSupport;

VaultResponseSupport<OrdersClientSecret> typed =
        kv.get("orders/api", OrdersClientSecret.class);

if (typed == null || typed.getData() == null) {
    throw new IllegalStateException("Thiếu secret orders/api");
}

OrdersClientSecret secret = typed.getData();
```

DTO cần có cách ánh xạ phù hợp với tên trường Vault, ví dụ `api_key` sang `apiKey` qua `@JsonProperty("api_key")` nếu dùng Jackson. Ánh xạ tự động **không thay thế validation**: trường có thể vắng, giá trị `null`, sai kiểu hoặc ngoài phạm vi nghiệp vụ.

Nếu ứng dụng cần những endpoint không có mapping kiểu tiện dụng, API cấp thấp vẫn khả thi, nhưng nên chuyển phản hồi thô thành kiểu nghiệp vụ tại **một lớp adapter**, không phân tán xử lý JSON ra mọi service.

## 8. ACL: hai API không có mức quyền khác nhau

Lựa chọn API Java **không bỏ qua cơ chế bảo mật Vault**. Cả `kv.get("orders/api")` và `vaultOperations.read("kv-orders/orders/api")` đều cần danh tính workload được xác thực và capability `read` ở **full logical path**:

```hcl
path "kv-orders/orders/api" {
  capabilities = ["read"]
}
```

Nếu một quy trình được phép tạo/cập nhật secret:

```hcl
path "kv-orders/orders/api" {
  capabilities = ["create", "update"]
}
```

Nếu cần liệt kê tên trong `orders/`:

```hcl
path "kv-orders/orders" {
  capabilities = ["list"]
}
```

Quyền xóa phải được cấp riêng tại secret đích:

```hcl
path "kv-orders/orders/api" {
  capabilities = ["delete"]
}
```

**Không mặc nhiên cấp tất cả quyền** cho ứng dụng chỉ cần đọc secret. Quy trình cấp phát, luân chuyển hoặc dọn dẹp dữ liệu nên có danh tính và ACL tách biệt. Danh tính có `read` một secret không tự có `list` ở tiền tố cha; `list` có thể tiết lộ tên các secret ngay cả khi không đọc được nội dung.

### Token, lease và dữ liệu KV là ba mối quan tâm riêng

- **Xác thực workload:** Spring Vault sử dụng cấu hình đăng nhập/token tương ứng, ví dụ qua AppRole hoặc Kubernetes auth, tùy môi trường.
- **Token TTL, renew và revoke:** Quyết định request còn được chấp nhận hay không; chúng **không** quyết định dùng API KV chuyên biệt hay API cấp thấp.
- **KV v1 secret:** Dữ liệu tĩnh hiện hành tại một đường dẫn, không có lease động riêng hay lịch sử phiên bản.
- **Transit encryption và PKI:** Là các API/chức năng khác của HashiCorp Vault; chọn `VaultOperations` cấp thấp hay một interface chuyên biệt của engine đó phải theo nhu cầu riêng, không lấy cách dùng KV v1 áp đặt lên chúng.

Một token hết hạn có thể làm cả `kv.get` và `vaultOperations.read` thất bại như nhau. Không nên diễn giải lỗi xác thực thành “secret trống” hoặc tự ghi một bản cấu hình mặc định lên Vault.

## 9. Lỗi thường gặp và cách chẩn đoán

| Triệu chứng | Nguyên nhân điển hình | Hướng xử lý |
| --- | --- | --- |
| `kv.get("kv-orders/orders/api")` không đọc đúng secret | Đã truyền **full path** cho API KV vốn chỉ cần relative path. | Dùng `kv.get("orders/api")`. |
| `vaultOperations.read("orders/api")` không trả dữ liệu | API cấp thấp thiếu tiền tố mount `kv-orders/`. | Dùng `read("kv-orders/orders/api")`. |
| Đưa `/v1/` vào `read` hoặc `get` | Nhầm HTTP API path với logical path Java. | Bỏ `/v1/`; Spring Vault tự quản lý HTTP prefix. |
| Dùng `data/` trong mount KV v1 | Nhầm quy tắc endpoint KV v2, có thể nhắm sai secret path. | Xác minh engine version tại mount trước khi xây URL. |
| API cấp thấp đọc KV v2 nhưng tìm `api_key` trực tiếp ở `getData()` | Chưa bóc lớp `data` lồng nhau của phản hồi KV v2. | Xử lý envelope KV v2 hoặc dùng API KV chuyên biệt. |
| API cấp thấp ghi KV v2 với JSON KV v1 | Thiếu trường bao `data` theo giao thức KV v2. | Gửi body dạng `{"data": {...}}` hoặc dùng API chuyên biệt. |
| `list` bị từ chối dù `get` thành công | Token có `read` ở secret nhưng không có `list` ở tiền tố. | Chỉ cấp `list` khi nghiệp vụ thực sự cần liệt kê tên. |
| Một trường cũ mất sau `put`/`write` | KV v1 **ghi đè toàn bộ** object, lần ghi mới thiếu trường. | Xây payload đầy đủ; không xem write là merge. |
| CLI thành công nhưng Java báo lỗi quyền | CLI và ứng dụng có thể sử dụng danh tính/token khác nhau. | Đối chiếu workload identity và ACL đúng full logical path. |
| Code trả `null` khi Vault không sẵn sàng | Bắt mọi ngoại lệ rồi đổi thành kết quả thiếu dữ liệu. | Phân loại lỗi ACL, token, mạng/TLS và dữ liệu không tồn tại. |

### Đừng đoán đường dẫn từ tên mount

Tên `kv-orders/` không chứng minh đó là KV v1; `secret/` cũng không chứng minh đó là KV v2. Hãy kiểm tra mount thật qua `vault secrets list -detailed` trong môi trường được phép hoặc lấy cấu hình đáng tin cậy từ đội vận hành. Sau đó mới chọn `KeyValueBackend`.

Khi chẩn đoán, cần quan sát **đường dẫn logic được gọi**, HTTP status và loại lỗi ở mức an toàn; không ghi toàn bộ request body/response body chứa secret, token hoặc thông tin nhạy cảm vào log.

### Không biến lỗi thành danh sách rỗng hoặc “secret không tồn tại”

Ví dụ không nên viết:

```java
try {
    return kv.list("orders");
} catch (Exception ex) {
    return List.of(); // Sai: lỗi ACL/mạng bị biến thành "không có secret".
}
```

Nếu `list` thực sự trả `null` hoặc danh sách rỗng, adapter có thể chuyển thành `List.of()` theo hợp đồng của mình. Nhưng khi Vault trả lỗi quyền hoặc kết nối, hãy giữ thông tin lỗi ở mức an toàn để tầng xử lý/phần giám sát phân biệt chính xác.

## 10. Thiết kế lớp truy cập Vault có thể thay đổi

Lựa chọn API nên được thể hiện ở **một ranh giới kỹ thuật rõ ràng**, không để các lớp nghiệp vụ tự ghép path. Ví dụ:

```text
OrdersService
    |
    | loadApiClientSettings()
    v
OrdersSecretRepository (interface ứng dụng)
    |
    +-- SpringVaultOrdersSecretRepository
            |
            +-- VaultKeyValueOperations (KV v1)
```

Lớp `OrdersService` chỉ biết mình cần cấu hình client. `SpringVaultOrdersSecretRepository` chịu trách nhiệm:

1. Chọn mount và backend theo cấu hình đã xác minh.
2. Gọi `get` bằng relative path hoặc `read` bằng full path.
3. Kiểm tra dữ liệu thiếu/sai kiểu rồi tạo DTO an toàn.
4. Phân biệt lỗi xác thực, quyền, hạ tầng và schema.
5. Không đưa giá trị secret vào log hoặc message.
6. Định nghĩa cách refresh/cache khi secret được luân chuyển.

Nếu sau này phải đổi từ API đường dẫn trực tiếp sang API KV chuyên biệt, hoặc cần chuyển sang KV v2, phần thay đổi nên nằm chủ yếu ở adapter và cấu hình ACL/test. **Đổi backend/đường dẫn** không phải là thay đổi “nhẹ” chỉ ở code: nó ảnh hưởng tới endpoint thực tế, security policy và cách xử lý dữ liệu.

Đối với ứng dụng chỉ cần một hoặc vài secret đã biết path, **không bắt buộc `list` trước `get`**. Đọc trực tiếp một secret cố định giảm số request và không cần thêm quyền liệt kê tên.

## 11. Bài thực hành và kiểm thử tích hợp

Dùng một Vault instance thử nghiệm độc lập, có thể được quản lý bởi Testcontainers, với secret hoàn toàn giả. Thực hành trên `kv-orders/` đang chạy KV v1; nếu có mount KV v2 riêng cho phần đối chiếu, luôn cô lập tên mount và path.

1. **Kiểm tra mount:** Dùng `vault secrets list -detailed` hoặc dữ liệu cấu hình đáng tin cậy để xác nhận `kv-orders/` là KV engine version 1.
2. **Ghi bằng API KV:** Tạo `kv` với `opsForKeyValue("kv-orders", KeyValueBackend.KV_1)`, rồi `put("orders/api", payload)` với `api_key` và `endpoint` giả.
3. **Đọc bằng API cấp thấp:** Gọi `vaultOperations.read("kv-orders/orders/api")`. Kiểm tra `getData()` có cùng field với lời gọi `kv.get("orders/api")`.
4. **Ghi bằng API cấp thấp:** Gọi `vaultOperations.write("kv-orders/orders/api", fullPayload)`. Đọc lại bằng `kv.get("orders/api")`; xác nhận cùng một secret đã được cập nhật.
5. **Kiểm chứng ghi đè:** Thử ghi chỉ `api_key` bằng một trong hai API. Đọc lại và xác nhận `endpoint` mất ở **cả hai cách**, vì đó là semantics KV v1 chứ không phải khác biệt của Spring Vault.
6. **Kiểm tra LIST:** Tạo thêm `orders/database` giả. Cấp `list` cho danh tính thử nghiệm, so sánh tập tên từ `kv.list("orders")` và `vaultOperations.list("kv-orders/orders")`; không giả định thứ tự.
7. **Kiểm tra ACL:** Dùng token chỉ có `read` để xác nhận hai cách đọc đều thành công nhưng cả hai cách ghi đều bị từ chối. Kiểm tra `list` cần quyền riêng.
8. **Kiểm tra đường dẫn sai:** Cố ý gọi `kv.get("kv-orders/orders/api")` và `vaultOperations.read("orders/api")` trong các test âm tính; xác nhận chúng không thay thế được cách gọi đúng. Tránh ghi/xóa nhầm trên các path sai.
9. **Kiểm tra response schema:** Ghi payload có trường thiếu, sai kiểu hoặc Map lồng nhau. Kiểm tra adapter xác thực dữ liệu và không trả secret không hợp lệ cho nghiệp vụ.
10. **So sánh KV v2 riêng:** Nếu có mount KV v2 thử nghiệm, đối chiếu `data/`, `metadata/` và JSON wrapper qua API cấp thấp. Dùng `KeyValueBackend.KV_2` khi chọn API KV chuyên biệt.
11. **Kiểm tra lỗi:** Thử token hết hạn, thiếu quyền hoặc Vault test không sẵn sàng; xác nhận lỗi không bị chuyển thành kết quả `null`/danh sách rỗng.
12. **Dọn dẹp:** Dùng danh tính quản trị xóa **đúng secret giả** đã tạo trong `kv-orders`; không dùng gỡ mount để xóa một secret và không dùng dữ liệu thật.

### Tiêu chí chấp nhận

| Kiểm tra | Kết quả kỳ vọng |
| --- | --- |
| `kv.get("orders/api")` và `vaultOperations.read("kv-orders/orders/api")` | Cùng đọc secret hiện hành trên KV v1. |
| `kv.put` và `vaultOperations.write` khi gửi full payload | Cùng ghi thành công vào đúng một secret path được phép. |
| Ghi chỉ một trường | Các field còn lại bị loại khỏi bản hiện hành của KV v1. |
| `kv.list("orders")` và `vaultOperations.list("kv-orders/orders")` | Cùng tập tên khi ACL và trạng thái dữ liệu không thay đổi. |
| Token chỉ `read` | Không thể `write`/`put` hoặc `delete` nếu chưa có quyền tương ứng. |
| Backend và path sai | Không được diễn giải là thành công chỉ vì có HTTP response; phải xác minh **đúng dữ liệu mục tiêu**. |
| Lỗi ACL, token hoặc kết nối | Được phân loại riêng, không bị che thành “không có secret”. |

Unit test với mock `VaultKeyValueOperations` hoặc `VaultOperations` có thể kiểm tra logic path/payload, nhưng **không đủ** để chứng minh semantics thực tế của Vault KV, URL và ACL. Integration test với Vault thật hoặc instance được cô lập sẽ xác nhận hai cách gọi cùng truy cập đúng endpoint.

## Tổng kết

Khi ứng dụng Java truy cập **HashiCorp Vault KV phiên bản 1**, hãy **ưu tiên `VaultKeyValueOperations`** cho thao tác CRUD thông thường: chọn mount bằng `opsForKeyValue("kv-orders", KeyValueBackend.KV_1)` rồi gọi `get/put/list/delete` với **đường dẫn secret tương đối**. `VaultOperations.read/write/list/delete` cấp thấp vẫn hữu ích khi cần truy cập endpoint Vault trực tiếp, nhưng phải truyền **full logical path** và tự xử lý cấu trúc payload/response phù hợp với engine. Hai cách dùng chung cơ chế xác thực, ACL và semantics KV v1: ghi là **thay thế toàn bộ** bản hiện hành, xóa tác động lên secret tại một path, và KV v1 không có history/CAS. Đóng gói truy cập trong adapter, xác minh mount thực, giới hạn quyền và kiểm thử hai cấp API với Vault thử nghiệm để tránh đọc sai đường dẫn hoặc hiểu nhầm kết quả.
