# Spring Vault: `VaultKeyValueOperations` với `KV_2`

## Mục tiêu bài học

Trong **Spring Vault**, ứng dụng Java truy cập HashiCorp Vault bằng `VaultTemplate` hoặc giao diện `VaultOperations`. Với **KV secrets engine phiên bản 2 (KV v2)**, Vault lưu nhiều phiên bản của một key và dùng API HTTP có cấu trúc khác KV v1. `VaultKeyValueOperations` cung cấp cách đọc, ghi và quản lý các secret thông dụng mà không phải tự xây dựng URL hay tự giải mã JSON lồng nhau.

Bài này thuộc chương **KV phiên bản 2** của module **SPRING_VAULT**. Ta sẽ dùng `VaultKeyValueOperations` với `KV_2` để viết mã Java có thể áp dụng cho ứng dụng xác thực theo workload và chịu ràng buộc Vault policy. Các phần về token/lease, Transit encryption, PKI, giám sát và kiểm thử tích hợp được liên hệ khi chúng ảnh hưởng trực tiếp đến việc sử dụng KV v2.

Sau bài học, bạn có thể:

- Khai báo `KV_2` đúng mount của Vault và phân biệt đường dẫn logic với endpoint HTTP.
- Dùng `get`, `put`, `patch`, `list`, `delete` và ánh xạ một secret thành đối tượng Java.
- Phân biệt ghi đè toàn bộ với patch, quyền đọc dữ liệu với quyền liệt kê tên key.
- Phát hiện khi nào phải dùng `VaultVersionedKeyValueOperations` để đọc một version cụ thể, lấy metadata hoặc ghi có điều kiện CAS.
- Xử lý trường hợp secret không tồn tại, lỗi quyền, lỗi kết nối và nguy cơ lộ bí mật qua log.

## 1. Tại sao phải chỉ rõ `KV_2`?

Vault KV có hai kiểu mount:

| Tính chất | KV v1 | KV v2 |
| --- | --- | --- |
| Lưu version cũ | Không | Có, theo chính sách giữ version |
| Endpoint ghi/đọc dữ liệu | `secret/{key}` | `secret/data/{key}` |
| Endpoint liệt kê tên | `secret/{folder}` | `secret/metadata/{folder}` |
| Ghi có CAS theo version | Không có cơ chế KV v2 | Có |
| Enum Spring Vault | `KeyValueBackend.KV_1` | `KeyValueBackend.KV_2` |

Giả sử nhóm vận hành mount KV v2 tại `secret/` và muốn lưu key `training/payment`. Đây là các đường dẫn tương ứng:

| Vai trò | Giá trị |
| --- | --- |
| Tên mount đưa vào Spring Vault | `secret` |
| Đường dẫn key đưa vào `put/get/patch/delete` | `training/payment` |
| API Vault nhận request đọc/ghi | `/v1/secret/data/training/payment` |
| API Vault nhận request liệt kê thư mục | `/v1/secret/metadata/training/` |

Ví dụ tạo API chuyên dụng:

~~~java
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.core.VaultOperations;

VaultKeyValueOperations kv =
    vaultOperations.opsForKeyValue("secret", KeyValueBackend.KV_2);

assert kv.getApiVersion() == KeyValueBackend.KV_2;
~~~

Trong ví dụ, `vaultOperations` là bean đã được ứng dụng cấu hình với Vault endpoint, TLS và phương thức xác thực. Spring Vault có thể được cấu hình đăng nhập bằng AppRole, Kubernetes hoặc cơ chế workload phù hợp với hạ tầng; không nhúng token dài hạn vào source code.

**Quy tắc quan trọng:** Sau khi chọn mount `secret`, các lời gọi `kv.get(...)` và `kv.put(...)` chỉ nhận **key tương đối** (ví dụ `training/payment`). Không thêm `secret/`, `data/` hay `/v1/` vào đối số này. Thư viện tự điều hướng đến endpoint KV v2.

### Kiểm tra điều kiện tiên quyết

Trước khi chạy ví dụ, cần có Vault đã mở KV v2 tại mount `secret/`, token/phiên đăng nhập có policy phù hợp và ứng dụng đã khởi tạo được `VaultOperations`. Có thể dùng Vault CLI ở môi trường thử nghiệm:

~~~bash
# Kiểm tra mount: xem options của secret/ có version=2.
vault secrets list -detailed

# Tạo dữ liệu giả trên một key dành riêng cho bài tập.
vault kv put -mount=secret training/payment \
  endpoint=https://sandbox.example.invalid \
  region=vn \
  timeoutSeconds=5
~~~

Không chạy lệnh bật mount mới nếu mount `secret/` đã tồn tại. Chọn `KV_2` trong Java **không thay đổi** loại mount phía Vault; nếu chọn sai version, request sẽ gửi đến endpoint không phù hợp và có thể bị từ chối.

## 2. Các phương thức cần biết

| Phương thức | Công dụng | Endpoint KV v2 | Kiểu kết quả |
| --- | --- | --- | --- |
| `get(path)` | Đọc secret phiên bản hiện hành | `GET /secret/data/{path}` | `VaultResponse` hoặc `null` |
| `get(path, Type.class)` | Đọc và chuyển dữ liệu thành Java type | `GET /secret/data/{path}` | `VaultResponseSupport<Type>` hoặc `null` |
| `put(path, body)` | Ghi một bản dữ liệu hoàn chỉnh, tạo version | `POST /secret/data/{path}` | `void` |
| `patch(path, fields)` | Cập nhật một phần trên secret hiện có | `PATCH /secret/data/{path}` | `boolean` |
| `list(folder)` | Liệt kê tên key và thư mục con | `LIST /secret/metadata/{folder}` | `List<String>` hoặc `null` |
| `delete(path)` | Xóa mềm version mới nhất của key | `DELETE /secret/data/{path}` | `void` |
| `getApiVersion()` | Kiểm tra enum backend được chọn | Không đọc secret | `KeyValueBackend` |

`VaultKeyValueOperations` nằm ở mức API thuận tiện cho **dữ liệu hiện hành**. Dù backend lưu nhiều phiên bản, bản thân API này không có tham số version trong `get`, và `put` không cung cấp CAS. Ta sẽ xem cách xử lý nhu cầu đó ở phần 6.

### Thư viện tự bọc và giải mã dữ liệu

Khi bạn ghi:

~~~java
kv.put("training/payment",
    Map.of("endpoint", "https://sandbox.example.invalid", "region", "vn"));
~~~

Spring Vault gửi cấu trúc tương đương đến KV v2:

~~~http
POST /v1/secret/data/training/payment
Content-Type: application/json
~~~

~~~json
{
  "data": {
    "endpoint": "https://sandbox.example.invalid",
    "region": "vn"
  }
}
~~~

Khi đọc, Vault trả các trường `data.data` và `data.metadata`. `VaultKeyValueOperations.get(...)` giải mã phần dữ liệu secret để `VaultResponse.getRequiredData()` trả về map các trường như `endpoint` và `region`. **Không tự bọc payload thêm một cấp `data`** khi dùng `kv.put(...)`: cách đó có thể khiến Vault lưu nhầm một trường tên `data` bên trong secret.

## 3. Ví dụ Spring service đọc, ghi và cập nhật KV v2

Giả sử Spring Boot đã cung cấp bean `VaultOperations` thông qua cấu hình Spring Vault/Spring Cloud Vault. Ví dụ này thao tác với **key test**, tuyệt đối không dùng thông tin bí mật thật:

~~~java
package example.vault;

import java.util.List;
import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.vault.core.VaultKeyValueOperations;
import org.springframework.vault.core.VaultKeyValueOperationsSupport.KeyValueBackend;
import org.springframework.vault.core.VaultOperations;
import org.springframework.vault.support.VaultResponse;

@Service
public class TrainingKvService {

    private static final String MOUNT = "secret";
    private static final String KEY = "training/payment";

    private final VaultKeyValueOperations kv;

    public TrainingKvService(VaultOperations vaultOperations) {
        this.kv = vaultOperations.opsForKeyValue(MOUNT, KeyValueBackend.KV_2);
    }

    // Ghi toàn bộ payload mới; mỗi lần ghi thành công tạo một version.
    public void saveExample() {
        kv.put(KEY, Map.of(
            "endpoint", "https://sandbox.example.invalid",
            "region", "vn",
            "timeoutSeconds", 5
        ));
    }

    // Không tìm thấy phiên bản khả dụng: Optional.empty().
    public Optional<Map<String, Object>> findCurrent() {
        VaultResponse response = kv.get(KEY);
        if (response == null || response.getData() == null) {
            return Optional.empty();
        }
        return Optional.of(response.getRequiredData());
    }

    // Chỉ thay đổi một trường; giữ các trường không bị patch.
    public boolean changeRegion(String region) {
        return kv.patch(KEY, Map.of("region", region));
    }

    // Liệt kê tên các key dưới training/.
    public List<String> listTrainingKeys() {
        List<String> keys = kv.list("training/");
        return keys == null ? List.of() : keys;
    }

    // Chỉ dùng cho key demo: xóa mềm phiên bản mới nhất.
    public void softDeleteLatestDemo() {
        kv.delete(KEY);
    }
}
~~~

Một số điểm cần ghi nhớ:

1. `kv.put(...)` trả về `void`. Không dựa vào kết quả này để tìm số version vừa ghi; nếu cần version và thời điểm tạo phải dùng API versioned.
2. `kv.get(...)` có thể trả `null` khi key không tồn tại hoặc phiên bản mới nhất không khả dụng. Kiểm tra trước khi gọi `getRequiredData()`.
3. Lỗi xác thực, quyền hoặc kết nối thường được ném ra thành exception. Không bắt mọi exception rồi chuyển thành `Optional.empty()` vì điều đó che mất sự cố vận hành.
4. `kv.list("training/")` trả tên tương đối như `payment` hoặc `reports/`; dấu `/` ở cuối biểu thị một thư mục con, không phải giá trị secret.
5. `changeRegion(...)` dùng `Map.of`, nên cần kiểm tra `region` khác `null` trong phần nghiệp vụ. Không log map trả về từ `findCurrent()` vì có thể chứa dữ liệu nhạy cảm.

### 3.1. Đọc thành JavaBean thay vì `Map`

Với một secret có schema ổn định, dùng overload `get(path, Class<T>)` để ánh xạ dữ liệu:

~~~java
import org.springframework.vault.support.VaultResponseSupport;

// JavaBean: public constructor rỗng cùng getter/setter cho endpoint, region.
VaultResponseSupport<PaymentSettings> response =
    kv.get("training/payment", PaymentSettings.class);

if (response == null || response.getData() == null) {
    throw new IllegalStateException("Không tìm thấy secret training/payment");
}

PaymentSettings settings = response.getRequiredData();
System.out.println("Đã nạp cấu hình KV v2"); // Không in settings ra log.
~~~

JavaBean tối thiểu có thể khai báo như sau:

~~~java
public class PaymentSettings {
    private String endpoint;
    private String region;

    public PaymentSettings() { }

    public String getEndpoint() { return endpoint; }
    public void setEndpoint(String endpoint) { this.endpoint = endpoint; }

    public String getRegion() { return region; }
    public void setRegion(String region) { this.region = region; }
}
~~~

Hai đoạn trên là **mảnh mã minh họa** nằm trong các class/phương thức tương ứng của ứng dụng. Bộ chuyển đổi JSON (thường là Jackson) phải hỗ trợ kiểu đích; tên field trong secret cần khớp với thuộc tính Java hoặc có mapping rõ ràng. Kiểm tra các trường bắt buộc sau deserialize, vì một phản hồi thành công không đảm bảo mọi trường nghiệp vụ đều có giá trị hợp lệ.

## 4. Khác nhau giữa `put` và `patch`

Giả sử bản dữ liệu hiện hành của `training/payment` là:

~~~json
{
  "endpoint": "https://sandbox.example.invalid",
  "region": "vn",
  "timeoutSeconds": 5
}
~~~

**Ghi bằng `put`:**

~~~java
kv.put("training/payment", Map.of("region", "sg"));
~~~

Version mới chỉ có `{"region":"sg"}`. Các trường `endpoint` và `timeoutSeconds` không tự được giữ lại.

**Cập nhật một phần bằng `patch`:**

~~~java
boolean changed = kv.patch(
    "training/payment",
    Map.of("region", "sg")
);
~~~

Nếu thực hiện patch trên bản ban đầu có ba trường, version mới sẽ là:

~~~json
{
  "endpoint": "https://sandbox.example.invalid",
  "region": "sg",
  "timeoutSeconds": 5
}
~~~

Spring Vault hỗ trợ `patch` từ phiên bản 2.3; nó dành cho KV v2, trả `boolean` và tạo version mới khi thành công. Secret cần **đã tồn tại và còn khả dụng**. Phía Vault sử dụng **JSON Merge Patch**: với object lồng nhau và giá trị `null`, thao tác có thể có ngữ nghĩa xóa trường. Hãy xác định chính xác ý nghĩa của payload trước khi dùng patch cho dữ liệu production.

Đây không phải lời gọi đồng nghĩa với `put`: quyền `patch` được phân biệt với quyền `create`/`update`. Khi thao tác thất bại, xác định nguyên nhân từ Vault và trạng thái key; không tự động thay patch bằng put vì có thể làm mất các trường không nằm trong payload.

## 5. Policy: vì sao `list` cần quyền metadata?

KV v2 tách đường dẫn **dữ liệu** và **metadata**. Ví dụ Vault policy HCL cho workload chỉ được **đọc** key đào tạo và **liệt kê** trong thư mục `training/`:

~~~hcl
path "secret/data/training/payment" {
  capabilities = ["read"]
}

path "secret/metadata/training" {
  capabilities = ["list"]
}

path "secret/metadata/training/" {
  capabilities = ["list"]
}
~~~

Nếu có một tiến trình đào tạo cần thực hiện đầy đủ `put`, `patch` và `delete` trên **đúng key đó**, có thể dùng một policy riêng:

~~~hcl
path "secret/data/training/payment" {
  capabilities = ["create", "read", "update", "patch", "delete"]
}
~~~

Trong production, workload chỉ **đọc cấu hình** thường chỉ cần `read` ở nhánh `data/`; không cấp quyền ghi, xóa hoặc liệt kê hàng loạt nếu nghiệp vụ không cần. Quyền `list` áp dụng trên `secret/metadata/training` (hoặc chính đường dẫn thư mục có dấu `/` tùy chuẩn hóa path), trong khi `get("training/payment")` yêu cầu `read` ở `secret/data/training/payment`.

Đọc thông tin chi tiết của một key qua `GET secret/metadata/{key}` còn cần quyền `read` metadata, độc lập với `list`. Tên key được liệt kê có thể nhìn thấy ngay cả khi token không có quyền đọc giá trị; vì vậy không đặt mật khẩu hoặc dữ liệu riêng tư trong tên key/thư mục.

## 6. Giới hạn của API: đọc version cũ và CAS

`VaultKeyValueOperations` thuận tiện khi ứng dụng chỉ xử lý bản hiện hành. Nếu cần **version 2 cụ thể**, thông tin metadata/version hoặc **Compare-and-Set (CAS)** khi nhiều instance ghi đồng thời, chọn `VaultVersionedKeyValueOperations`:

~~~java
import java.util.Map;
import org.springframework.vault.core.VaultVersionedKeyValueOperations;
import org.springframework.vault.support.Versioned;

VaultVersionedKeyValueOperations versions =
    vaultOperations.opsForVersionedKeyValue("secret");

// Đọc version 1 (nếu còn tồn tại và chưa bị xóa/hủy).
Versioned<Map<String, Object>> v1 =
    versions.get("training/payment", Versioned.Version.from(1));

// Đọc version hiện hành rồi dùng số version đó làm điều kiện CAS.
Versioned<Map<String, Object>> latest =
    versions.get("training/payment");

if (latest != null && latest.hasData()) {
    Versioned<Map<String, Object>> next = Versioned.create(
        Map.of("endpoint", "https://sandbox.example.invalid",
               "region", "sg", "timeoutSeconds", 5),
        latest.getVersion()
    );
    versions.put("training/payment", next);
}
~~~

Đoạn mã minh họa tạo **payload đầy đủ** cho lần ghi có điều kiện. Nếu version hiện hành đã thay đổi từ thời điểm đọc, Vault từ chối ghi CAS; ứng dụng phải đọc lại và giải quyết xung đột. Tránh retry bằng cách bỏ CAS vì có thể ghi đè cập nhật của tiến trình khác.

Tại key/mount có `cas_required=true`, `VaultKeyValueOperations.put(path, body)` thông thường không có tham số CAS và có thể bị từ chối. Đây là lúc cần dùng API versioned.

| Nhu cầu | API phù hợp |
| --- | --- |
| Đọc/ghi phiên bản hiện hành | `VaultKeyValueOperations` với `KV_2` |
| Sửa vài trường bằng JSON Merge Patch | `VaultKeyValueOperations.patch` |
| Đọc version cụ thể, lấy version/time/metadata, ghi CAS | `VaultVersionedKeyValueOperations` và metadata operations |
| Gia hạn token/lease hoặc tạo dynamic secrets | Cơ chế Vault auth/session/lease tương ứng |
| Mã hóa Transit, phát hành/chứng thực PKI | Các API Transit/PKI tương ứng của Spring Vault |

## 7. Xóa: `delete` với KV v2 có ý nghĩa gì?

~~~java
kv.delete("training/payment");
~~~

Lệnh trên xóa mềm **version mới nhất** bằng endpoint `DELETE /v1/secret/data/training/payment`. Dữ liệu của version đó không được trả về khi đọc thông thường, nhưng vẫn có thể được khôi phục bằng cơ chế undelete nếu chưa bị destroy hay loại bỏ theo chính sách. Nó **không xóa toàn bộ lịch sử và metadata của key**.

Đừng hiểu `get(path) == null` sau khi xóa mềm là Vault đã tự lùi về version cũ: lần đọc mặc định tìm version hiện hành, còn version cũ phải đọc bằng API versioned. Thao tác destroy vĩnh viễn và xóa toàn bộ metadata có đường dẫn/đặc quyền khác; không dùng `delete` như một cách dọn sạch mọi version.

## 8. Xử lý lỗi và giám sát trong ứng dụng

| Triệu chứng | Điều cần kiểm tra | Hướng xử lý |
| --- | --- | --- |
| `get` trả `null` | Key không tồn tại hoặc version hiện hành không còn khả dụng | Kiểm tra mount, key, trạng thái version nếu có quyền |
| `403 permission denied` | Policy thiếu quyền trên endpoint thực tế | Kiểm tra `read/create/update/patch/delete` ở `data/`, `list` ở `metadata/` |
| `404` hoặc URL không hợp lệ | Sai mount, chọn `KV_1` cho engine KV v2, lặp `secret/data/` trong key | Đối chiếu `vault secrets list -detailed` và đường dẫn logic |
| `patch` bị từ chối | Key không tồn tại/đã xóa, thiếu quyền `patch`, CAS bắt buộc hoặc backend không hỗ trợ | Kiểm tra điều kiện ghi, không thay patch bằng put tùy tiện |
| `put` bị từ chối do CAS | Engine hoặc key cấu hình `cas_required` | Chuyển sang `VaultVersionedKeyValueOperations` |
| `list` lỗi trong khi `get` hoạt động | Không có quyền `list` trên thư mục `metadata/` | Cấp `list` đúng phạm vi khi thực sự cần |
| Kết nối hoặc TLS/xác thực lỗi | Vault tạm không khả dụng, truststore sai, workload token hết hạn | Kiểm tra TLS, phiên đăng nhập, health và cơ chế quản lý token |

Các lỗi Vault thường thể hiện qua exception Spring Vault/Spring và thông tin HTTP từ Vault. Hãy phân biệt trường hợp **secret tùy chọn không tồn tại** với **không thể truy cập Vault**; không bắt mọi exception rồi trả về map rỗng. Khi cần retry lỗi tạm thời, dùng chính sách retry hữu hạn và tránh ghi lặp không kiểm soát.

Trong giám sát, có thể theo dõi số thao tác thành công/thất bại, độ trễ và thống kê lỗi quyền/kết nối. Không log `VaultResponse`, map dữ liệu, token, secret hoặc các trường nhạy cảm như nhãn metrics. KV v2 lưu lịch sử secret nhưng **không thay thế** quản lý vòng đời token và lease động của Vault.

## 9. Thực hành và tự kiểm tra

Thực hiện với một Vault test hoặc namespace được cấp phép; chỉ dùng key `training/payment` và các giá trị giả:

1. Ghi key bằng Vault CLI rồi gọi `findCurrent()` để xem ba trường `endpoint`, `region`, `timeoutSeconds`. Xác minh chương trình không cần truyền prefix `data/` vào `get`.
2. Chạy `changeRegion("sg")` rồi đọc lại. Vì sao hai trường còn lại vẫn có trong version mới?
3. Chạy `saveExample()`; dự đoán `region` chuyển về `vn` và số version tăng ra sao.
4. Chạy `listTrainingKeys()`. Thử token có quyền `read` data nhưng thiếu `list` metadata; giải thích sự khác biệt.
5. Gọi `softDeleteLatestDemo()` chỉ với key test, sau đó gọi `findCurrent()`. So sánh xóa mềm với hủy vĩnh viễn.
6. Bật `cas_required` trên key test bằng quyền quản trị, thử `put` thông thường và ghi có điều kiện bằng API versioned. Vì sao cấu hình CAS có ích khi nhiều instance ghi cùng lúc?

### Hướng kiểm thử tích hợp

Có thể dùng Vault chạy trong một test container/instance cô lập, sau đó kiểm thử luồng `put → get → patch → list → delete → get không còn dữ liệu hiện hành`. Tạo key riêng cho từng test; kiểm tra thêm trường hợp thiếu quyền `list` và key bật CAS. Không chạy các kiểm thử thay đổi secret trên Vault production, không commit token hoặc credential demo có khả năng sử dụng thật.

## Ghi nhớ

- `opsForKeyValue("secret", KeyValueBackend.KV_2)` chọn đúng API KV v2; các phương thức tiếp theo dùng **key tương đối**.
- `VaultKeyValueOperations` tự xử lý các tiền tố HTTP và lớp `data`, cho phép đọc/ghi thuận tiện qua Java.
- `put` thay **toàn bộ bản dữ liệu**; `patch` chỉ sửa các trường được chỉ định trên secret đã có.
- `list` sử dụng endpoint **metadata**, cần policy `list` tương ứng; `get` dùng endpoint **data**.
- `delete` xóa mềm **version mới nhất**. Khi cần version lịch sử, metadata hoặc CAS, dùng `VaultVersionedKeyValueOperations`.
- Xác thực workload, ACL tối thiểu, xử lý lỗi và hạn chế log secret là yêu cầu vận hành xuyên suốt.
